# 설계: 로컬 kind 클러스터와 CI 구성, 서비스별 Outbox 릴레이 배포

## Context

- docs/infra.md §3 '로컬': kind나 k3d로 띄운 쿠버네티스 + LocalStack(S3·KMS·Secrets Manager 흉내) + Strimzi(로컬 Kafka), CI도 같은 구성. LocalStack은 계정·인증 토큰이 있어야 뜨고, 막히면 S3 호환 저장소와 시험용 어댑터로 바꾼다고 적었다.
- 소유자 결정(2026-10-31): 외부 서비스 계정은 만들지 않고 계정 없이 되는 대역으로 한다. 비용이 드는 클라우드 실행은 하지 않는다. 로컬 PC에서 Docker를 쓴다.
- ADR-0116: 서비스별 `<서비스>-outbox-relay`(복제 2·Lease·전용 DB/MSK 역할). FND-080이 릴레이·Lease, FND-090이 정비 반복·`/ready`·`PEAKET_POD` 소비자 그룹을 만들었고 배포와 실제 Lease 확인을 이 단계로 넘겼다.
- docs/devops.md §9.4: Kafka는 MSK 3.9.x로 시작하고 로컬 Strimzi도 같은 판으로 맞춘다.

## Goals / Non-Goals

- 목표: 한 명령으로 뜨는 로컬 클러스터(로컬·CI 같은 스크립트), 계정 없는 AWS 흉내, 릴레이 프로세스와 그 배포(차트), 실제 Lease 이어받기 확인, CI 잡과 포크 PR 표시.
- 목표 아님: 부하를 건 V-T28 전체와 성능 장부(wbs 2.12.3), 차트의 Rollout·PDB·KEDA·NetworkPolicy·ExternalSecret·Kyverno(wbs 0.4.4), DB 역할 마이그레이션(BAS-060), 이미지 서명·게시(build-image.yml), 관측 스택(로컬 Prometheus 등).

## Decisions

1. **kind를 고른다(k3d가 아니라).** 정본은 둘 중 하나다. kind는 쿠버네티스 SIG가 내는 판별 노드 이미지를 다이제스트로 고정할 수 있고(릴리스 노트가 다이제스트 고정을 요구한다), 노드 컨테이너 안에서 `crictl`로 파드 프로세스에 신호를 보낼 수 있어 V-T28 ①의 프로세스 정지(SIGSTOP)를 그대로 할 수 있다. 쿠버네티스 1.35.8(kind v0.33.0이 만든 이미지)을 쓴다. kubectl을 같은 판으로 받아 판 차이를 없앤다.
2. **도구는 고정 판·해시로 받는다.** kind·kubectl·helm을 각 프로젝트의 공식 주소(GitHub 릴리스, dl.k8s.io, get.helm.sh)에서 받아 표에 적은 SHA-256과 견주고, 다르면 쓰지 않는다. 압축으로 받는 helm은 푼 실행 파일의 해시도 고정해 받아 둔 것을 그것과 견준다(처음에는 스스로 적은 옆 파일과 견줘 둘을 함께 바꾸면 그대로 썼다, 코드 리뷰). Strimzi 운영자 이미지는 운영자 자신과 그가 띄우는 엔티티 운영자·초기화 컨테이너(환경 변수 값) 모두 다이제스트로 바꾼다. 받은 것은 저장소 안 `.cache/peaket-tools`(커밋하지 않음)에 둔다. GitHub 러너에 미리 깔린 판에 기대지 않는다(판이 바뀌면 결과가 달라진다). helm은 3.22.1이다(ArgoCD가 그리는 차트와 같은 v2 차트 형식, 4.x로 갈 이유가 아직 없다).
3. **사용자의 kubeconfig를 건드리지 않는다.** 클러스터를 만들 때와 모든 kubectl·helm 호출에 전용 kubeconfig(`.cache/peaket-tools/kubeconfig-peaket`)를 준다.
4. **LocalStack 대신 moto 서버(5.2.5, Apache-2.0)를 쓴다(추천 적용 2026-11-01).** 정본의 대안(S3는 MinIO 같은 S3 호환 저장소, KMS·Secrets Manager는 시험용 어댑터)보다, 세 서비스를 한 컨테이너로 계정 없이 흉내 내는 쪽이 같은 AWS CLI·SDK 호출을 그대로 시험할 수 있다. 확인할 기능은 S3 Object Lock 보존 기한(COMPLIANCE)·법적 보존이 판 지우기를 막는지, KMS ECC_NIST_P256 서명·검증과 공개키 꺼내기, Secrets Manager 새 판과 AWSPREVIOUS다. 흉내 서버는 서명·권한을 검사하지 않으므로 IAM 정책 시험은 이것으로 하지 않는다.
5. **Strimzi 0.47.0 + Kafka 3.9.1(추천 적용 2026-11-01).** Strimzi 1.x(최신 1.3.0)는 Kafka 4.2·4.3만, 0.48은 4.x만 받는다(0.48.0이 3.9.0·3.9.1을 뺐다). 운영 MSK와 같은 3.9.x를 쓰려면 0.47.0이 마지막이다. Strimzi는 3.9.2 이미지를 내지 않아 3.9.1이다(통합 시험의 공식 Kafka 컨테이너는 3.9.2). 0.47.0은 더 고쳐지지 않는 판이라 로컬·CI에서만 쓰고, MSK를 4.1.x로 올릴 때(§9.4의 조건) 최신 Strimzi로 바꾼다. 운영자 메모리 한도는 384Mi에서 메모리 초과로 죽어(2026-11-01 kind 확인) 512Mi로 올린다. 브로커 겸 컨트롤러 하나, 임시 저장소, 자동 토픽 만들기 끔.
6. **릴레이는 같은 이미지·다른 시작 명령의 프로세스다.** 시작 함수가 Lease 선출·릴레이·정비 반복·관리 포트를 묶고, DB·Kafka 생산자·Lease API는 서비스의 `relay.ts`가 만들어 넘긴다(네이티브 모듈을 핵심 묶음에 싣지 않는다). 설정 넷이 없으면 이름을 모두 대며 시작하지 않는다. Lease 이름은 `<서비스>-outbox-relay`, 보유자는 `PEAKET_POD`다. 리더 지표는 바뀌는 즉시 고친다.
7. **리더가 되면 정비를 바로 깨운다.** 정비 반복은 시작할 때 한 번 깨어난 뒤 10분 [가정]을 쉰다. 그 순간 리더가 아니면 새 리더가 10분 동안 Outbox 파티션을 만들지 않아 첫 쓰기가 실패할 수 있었다(이 단계의 시험에서 찾음). 정비 실행기에 깨우기를 두고, 도는 중이면 끝난 뒤 한 번 더 돈다(겹쳐 돌지 않는다).
8. **끝낼 때 순서**: 보내던 묶음을 마치기와 정비 멈추기를 함께 하고(그동안 Lease 반복은 계속 갱신) → Lease를 놓고(보유자 비움) → 관리 포트를 닫는다. 정비 일은 멈춤 신호를 받고(나눠 지우는 멱등 기록·보존 지우기는 묶음 사이에 보고 멈춘다), 끝나기를 10초 [가정]까지만 기다린다. 처음에는 정비 일이 끝날 때까지 한없이 기다려, 정비 시간에 SIGTERM을 받으면 Lease를 쥔 채 아무도 보내지 않다가 SIGKILL을 맞았다(코드 리뷰 2026-11-01). 멈춘 뒤 끝난 일은 성공으로 적지 않는다. 대기 복제는 Lease 기간(12초)을 기다리지 않고 다음 시도(2초)에 잡는다. 서비스의 `relay.ts`가 SIGTERM·SIGINT에 이것을 부른 뒤 생산자와 DB를 닫는다.
9. **차트의 권한은 그 Lease 하나다.** Role은 `coordination.k8s.io` `leases`의 읽기·고치기를 `resourceNames`로 그 이름 하나에 좁힌다. 만들기는 RBAC가 이름으로 좁히지 못해(뚫린 파드가 같은 네임스페이스의 아직 없는 다른 서비스의 Lease를 먼저 만들어 그 리더 선출을 막을 수 있다) 주지 않고, 차트가 빈 Lease를 미리 만든다(정본의 'get·create·update'에서 만들기를 뺀다, 추천 적용 2026-11-01, 코드 리뷰). 차트는 Lease의 spec을 적지 않아 배포가 보유자를 지우지 않는다. 차트 없이 띄울 때를 위해 코드는 Lease가 없으면 만들기를 그대로 시도한다. Lease 고치기는 전체 바꾸기(PUT)라, 마지막으로 읽은 판의 라벨·주석·소유자 참조·종료자를 본문에 그대로 싣는다(client-go LeaseLock과 같다). 처음에는 이름·판만 실어, 차트·ArgoCD가 붙인 라벨과 주석이 2초마다 지워졌다(확인 리뷰 2026-11-01). 고치기 대신 부분 고치기(PATCH)를 쓰면 Role에 `patch`가 더 들어 고르지 않았다. 서비스 계정 토큰은 릴레이 파드에만 붙이고 서비스 파드는 붙이지 않는다. 컨테이너는 제한 파드 보안 기준(루트 아님, 권한 상승 없음, 읽기 전용 루트 파일 시스템, 능력 모두 뺌)으로 돈다. 이미지 태그는 `PEAKET_ENV` local·ci에서만 받고, 다른 환경은 다이제스트만 받는다.
10. **프로브**: 서비스·릴레이 모두 관리 포트의 준비 `/ready`, 생존 `/livez`(10초마다, 5초 한도, 6번 실패 = 약 1분), 시작 `/livez`(최대 60초). `/livez`는 이벤트 루프가 답하는지만 본다(architecture §5). 릴레이 Deployment는 한 파드씩 바꾼다(`maxUnavailable: 1`, `maxSurge: 0`, devops §6.1).
11. **kind 이어받기 시험**(V-T28 ①의 kind 부분): 쓰기를 흘리는 동안 리더 컨테이너 프로세스를 노드 컨테이너 안에서 SIGSTOP으로 멈추고(컨테이너 안 PID 1에는 닿지 않는다), 다른 복제가 Lease를 잡는 시간을 재고(20초 이하), 보내지 않은 행이 0이 될 때까지 기다린다. 멈춘 리더가 묶음 트랜잭션을 쥐고 있으면 새 리더는 그 행의 잠금을 기다리고, 트랜잭션은 쉬는 한도(30초 [가정])에 DB가 끊는다. 깨운 뒤 옛 리더가 Lease를 되가져가지 않고 리더 지표가 0인지, Kafka에서 서로 다른 행이 모두 왔고 같은 키의 첫 도착 순서가 쓴 순서인지(다시 보낸 것은 처음 자리로 본다) 본다. 릴레이는 Outbox 읽기와 `sent_at` 고치기만 받은 전용 DB 역할로 돈다.
12. **CI**: `ci-kind.yml`이 로컬과 같은 스크립트를 부른다. 무거워서 바뀐 범위 `kind`(클러스터 정의·차트·클러스터 도구, 서비스 이미지에 드는 것 전부: 플랫폼 패키지와 서비스 뼈대·공용 설정 패키지·작업 공간 파일)일 때와 `develop` 푸시에서만 돈다. 처음에는 릴레이 관련 파일만 골랐으나 이미지 시작 경로(내보내기 목록·설정·OTel 등록)가 빠져 플랫폼 패키지 전부로 넓혔다(리뷰 2026-11-01). 비밀이 필요 없어 포크 PR에서도 돈다. 비밀이 필요한 단계를 위해 `fork-guard.mjs`를 둔다: 포크 PR이면 `run=false`와 알림·잡 요약 표시, 조직 안 PR·푸시에서 비밀이 빠졌으면 실패. 지금 PR에서 비밀을 쓰는 단계는 없다(Infracost 같은 것이 생길 때 쓴다).
13. **찾은 결함(FND-080 코드)**: 릴레이 질의가 `seq::text as seq`로 이름을 바꾼 뒤 `order by seq`로 정렬해, PostgreSQL이 출력 열(글자)을 골라 '10'이 '2'보다 먼저 나갔다. 같은 묶음에 자릿수가 다른 번호(9와 10, 99999와 100000)가 섞이면 같은 키의 순서가 뒤집힌다. 정렬을 표의 열로 콕 집어 고치고 재현 시험을 남긴다.

## Risks / Trade-offs

- Strimzi 0.47.0은 고쳐지지 않는 판이다. 로컬·CI에만 쓰고, 운영 판을 올릴 때 바꾼다.
- moto는 AWS의 권한 검사·한도·지연을 흉내 내지 않는다. 기능 흐름만 본다.
- kind 시험은 노드 하나다. 영역(AZ) 나눔과 노드 장애는 이 시험이 보지 않는다(Game Day G-26 등).
- kind 시험이 무거워(약 10분) PR마다 돌지 않는다. 범위 밖 변경이 릴레이 배포를 깨면 `develop` 푸시에서 잡힌다.
