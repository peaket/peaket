# 설계: 릴리스·핫픽스 워크플로

## Context

- git flow 출시 경로의 정본은 devops §2.2.2~§2.2.6이다. 판은 시스템 전체에 하나이고(ADR-0165), 릴리스 가지와 핫픽스 가지는 저장소에 하나씩만 연다.
- 지금 있는 것(R-202): `ci.yml`, `branch-policy.yml`(가지 쌍·PR 제목·절차 변경 분리·작업 가지 나이), `merge-tree.yml`과 `tools/ci/check-merge-tree.mjs`. 규칙 세트(`infra/modules/github`)는 `release/*`·`hotfix/*` 만들기와 `v*` 태그를 릴리스 봇만 하게 하고, `main`은 봇도 PR·필수 검사·데모 배포 성공을 거쳐야 병합한다.
- 저장소 설정 `delete_branch_on_merge = true`(`infra/stacks/global/github/repositories.tf`): 병합한 PR의 머리 가지를 GitHub가 지운다. GitHub 문서는 규칙 세트가 이 삭제를 막을 수 있다고만 하고, 그 가지를 머리로 쓰는 다른 열린 PR이 있을 때 지우지 않는다는 말은 없다(2026-10-31 확인).
- 배포 단위(서비스·앱·dbt)와 이미지 빌드(`build-image.yml`), 배포 상태(`deploy/`)와 승격(`promote.yml`)은 아직 없다.
- 확인한 외부 사실(2026-10-31, GitHub API): `actions/create-github-app-token` v3.3.0 = `64ab729a6294000f5aa4a4bc0b73d1f32bc45510`(2026-10-12 게시, 3일 지남). 입력 `client-id`(앱 ID 입력 `app-id`는 폐기 예정), `private-key`, `permission-contents`, `permission-pull-requests`.

## Goals / Non-Goals

**Goals:**

- 릴리스 자르기(주 1회 예약과 수동), 핫픽스 열기, 마무리(병합 직전 트리 검사 → `main` 병합 → 병합 뒤 트리 확인 → 태그·GitHub Release → 역병합 PR → 릴리스 가지 지우기)를 `release.yml` 하나로 한다.
- 버전 계산, 변경 기록, 바뀐 배포 단위, 역병합 대상, 병합 뒤 확인은 모두 `tools/ci/release-plan.mjs`가 판단하고 로컬 git 저장소로 시험한다.

**Non-Goals:**

- 운영 승격 PR과 데모 승격(배포 상태 `deploy/`와 `promote.yml`이 생기는 wbs 0.4.4, BUILD_ORDER BAS-140)
- GitHub Release의 서비스별 후보 다이제스트와 SBOM 요약(이미지 빌드가 생기는 BSL-050, 공급망 증명 BAS-020)
- 작업 가지 수 경고와 `develop` 병합 방식 주간 점검(정본대로 원격을 만든 뒤, FND-160)
- 마무리 뒤 트리가 다를 때의 SEV3 경보 경로(관측 스택이 생긴 뒤). 지금은 잡이 실패하고 태그를 달지 않는다.

## Decisions

1. **판단은 스크립트, 쓰기는 GitHub API.** `release-plan.mjs`는 git만 읽고 결과를 `GITHUB_OUTPUT`(로컬은 JSON)과 파일로 낸다. 가지·커밋·태그·PR은 워크플로가 릴리스 봇의 설치 토큰으로 `gh api`·`gh pr`·`gh release`를 불러 만든다. 체크아웃에 자격 증명을 남기지 않고(`persist-credentials: false`), `git push`도 하지 않는다. 버전 올림 커밋은 내용 API로 만들어 앱 이름으로 남는다.
2. **버전 계산(§2.2.5, D-T41 ④)**: 마지막 출시 태그(`vX.Y.Z` 꼴 가운데 SemVer로 가장 큰 것) 뒤 `develop`에만 있는 커밋(병합 커밋 제외)의 제목을 읽는다. `!`나 본문의 `BREAKING CHANGE:`는 MAJOR, `feat`는 MINOR, 그 밖(형식에 맞지 않는 제목 포함)은 PATCH다. 운영 출시 전(0.y.z)에는 MAJOR 대신 y를 올린다. 출시 태그가 하나도 없으면 첫 판은 `0.1.0`이다(추천 적용 2026-10-31). 태그 커밋은 `main`의 병합 커밋이라 `develop`의 조상이 아니므로 `git describe`를 쓰지 않는다. 범위 `<태그>..develop`은 역병합으로 들어온 릴리스 가지 커밋을 빼고 센다.
3. **제목 해석은 한 곳**: `tools/ci/conventional.mjs`가 허용 종류·제목 형식·호환을 깨는 표시를 정하고, `branch-policy.mjs`(제목 검사)와 `release-plan.mjs`(버전 계산)가 함께 쓴다. 검사가 통과시킨 제목을 버전 계산이 다르게 읽는 일이 없게 한다.
4. **첫 커밋과 변경 기록(§2.2.2·§2.2.5)**: 릴리스·핫픽스 가지의 첫 커밋은 뿌리 `package.json`의 `version`만 올린다(`chore(release): X.Y.Z`). 변경 기록 파일은 두지 않고, 시작 때는 릴리스 PR 본문에, 마무리 때는 GitHub Release에 붙인다. 마무리 때 다시 만들어야 릴리스 가지에 들어온 버그 수정까지 담기고, 핫픽스는 시작 때 담을 수정이 없기 때문이다(추천 적용 2026-10-31, §2.2.2 1번 문구를 고친다). 변경 기록은 범위(가상 팀 이름)별로 묶고, 묶음 안에서는 호환을 깨는 변경·기능·수정·그 밖 순서로 둔다. 제목의 `@이름`은 코드 표시로 감싸 알림이 가지 않게 한다.
5. **바뀐 배포 단위(§2.2.5 서비스 식별)**: 배포 단위는 `services/<이름>`, `apps/<이름>`(관제 위젯은 `apps/widgets/<이름>`), `data/dbt_project.yml`이 있을 때의 `data`다. 마지막 출시 태그와 후보의 트리 차이로 고른다. `packages/`·`docs/api/`·뿌리 작업 공간 파일·`.nvmrc`·`build-image.yml`이 바뀌면 자바스크립트 배포 단위를 모두 고른다. 작업 공간 의존 그래프가 생기면(FND-030) Turborepo 그래프로 좁힌다. 지금은 배포 단위가 없어 늘 빈 목록이다.
6. **하나씩만 연다**: 릴리스를 자를 때 `release/*`가 이미 있으면 아무것도 열지 않는다(예약 실행이 실패로 보이지 않게 경고만). 핫픽스를 열 때 `hotfix/*`가 이미 있으면 실패한다. 마무리할 가지 이름은 `^(release|hotfix)/X.Y.Z$`만 받고, 같은 태그가 이미 있거나 판이 마지막 출시 태그보다 크지 않으면 실패한다.
7. **역병합은 `merge/*` 가지로(추천 적용 2026-10-31)**: `main` 병합 뒤 후보 커밋에 `merge/<종류>-<판>-to-<대상>` 가지를 만들어 역병합 PR(병합 커밋)을 연다. 릴리스 가지를 머리로 쓰면 `main` 병합 순간 저장소 설정이 그 가지를 지워 역병합 PR이 닫힐 수 있다. 내용은 릴리스 가지 끝과 같고, 충돌이 나면 정본대로 그 `merge/*` 가지에서 사람이 푼다(§2.2.1 '역병합' 행 문구를 고친다). 대상은 릴리스면 `develop`, 핫픽스는 열린 릴리스 가지가 있으면 그 가지(D-T25), 없으면 `develop`이다.
8. **마무리 순서(§2.2.2 4·5번, §2.2.4)**: 가지 이름 검사 → `check-merge-tree.mjs`로 병합 직전 다시 검사 → 그 가지에서 `main`으로 가는 열린 PR을 찾아 `--match-head-commit <후보>`로 병합 커밋 병합(머리가 움직였으면 GitHub가 거부한다) → 병합 커밋의 두 번째 부모가 후보이고 트리가 같은지 확인(`verify`) → 주석 태그와 GitHub Release(변경 기록, 바뀐 배포 단위, 태그 커밋·후보 커밋·트리 해시) → 역병합 PR → 남아 있으면 릴리스 가지를 지운다. 병합 뒤 확인이 실패하면 태그를 달지 않고 잡이 실패한다.
9. **가지 규칙 검사의 절차 변경 분리는 변경을 만드는 PR에만(추천 적용 2026-10-31)**: `release/*`·`hotfix/*`·`merge/*`가 보내는 PR은 이미 병합된 변경을 옮길 뿐이다. 지금 검사는 모든 PR에 걸려, 지난 출시 뒤 워크플로가 바뀐 적이 있으면 릴리스 PR이 늘 실패한다. 이 셋에는 분리 검사를 걸지 않는다(§2.2.6 문구를 고친다). 재현 시험을 먼저 만들어 실패를 본 뒤 고친다.
10. **예약과 시각**: 릴리스 자르기 예약은 월요일 10:00 KST(`cron: '0 1 * * 1'`, UTC)다(주 1회 [가정], 요일과 시각은 추천 적용 2026-10-31). 예약은 기본 가지 `develop`에서 돈다. 동시 실행은 `concurrency: release`로 하나씩만 하고 진행 중인 실행은 취소하지 않는다.
11. **토큰 권한**: 워크플로 토큰은 `contents: read`뿐이다. 앱 설치 토큰은 필요한 잡 단계에서만 만들고 `contents: write`·`pull-requests: write`로 좁힌다. 앱 클라이언트 ID는 `release` 환경 변수 `RELEASE_BOT_CLIENT_ID`, 개인 키는 `release` 환경 비밀 `RELEASE_BOT_PRIVATE_KEY`다(secrets-and-keys '릴리스 봇' 행). 수동 입력(`branch`)은 식으로 셸에 넣지 않고 환경 변수로 넘겨 스크립트가 검사한다.

12. **워크플로 검사의 사용자 입력 판정(구현 중 찾음, 2026-10-31)**: `check-workflows.mjs`는 `github.event`로 시작하고 `name`으로 끝나는 경로를 사용자 입력으로 보는데, 사건 종류 `github.event_name`도 그 꼴이라 막혔다. `github.event` 자체와 `github.event.`·`github.event[` 아래 경로만 사건 본문으로 본다. 재현 시험을 먼저 만들어 실패를 본 뒤 고쳤다.

13. **코드 리뷰 반영(2026-10-31, 새 맥락의 리뷰 에이전트가 4건을 찾음, 모두 재현 시험을 먼저 만들어 실패를 본 뒤 고침)**:
    - **앱 토큰의 workflows 권한과 이어 가기**: 워크플로가 바뀐 커밋에 가지·태그를 만들 때 GitHub는 앱의 workflows 권한을 요구한다(GitHub 문서 'Permissions required for GitHub Apps'). 토큰에 `permission-workflows: write`를 더한다. 그리고 `main` 병합 뒤 단계에서 멈추면 릴리스 가지가 이미 지워져 다시 돌릴 수 없었다. 그래서 `finish`는 병합된 PR이 있으면 그 병합 커밋을 `--merged`로 받아 후보를 두 번째 부모로 잇고, 그 병합 커밋에 이미 단 태그는 받아들인다. 태그·Release·역병합 가지·역병합 PR은 이미 있으면 건너뛴다.
    - **판 겹침**: 릴리스는 열린 핫픽스 판보다 큰 판을 받는다. 핫픽스는 같은 판의 릴리스가 열려 있으면 열지 않고, 릴리스를 닫은 뒤(§2.2.2 6번) 다시 자르게 한다.
    - **분리 검사 면제의 범위(결정 9를 좁힘)**: 가지 이름만 보면 포크 PR이나 사람이 `merge/*`에 얹은 커밋이 그냥 통과한다. 같은 저장소의 PR일 때만, 그리고 보호 가지(`main`·`develop`·`release/*`·`hotfix/*`)에 아직 없는 새 커밋이 바꾼 파일만(병합 커밋은 `--cc`로 손으로 고친 파일만) 검사한다.
    - **핫픽스 역병합 충돌**: 핫픽스를 열린 릴리스로 보내면 두 가지가 `package.json`의 판 줄을 다르게 바꿔 늘 충돌한다. 역병합 가지에 대상의 판으로 맞춘 커밋을 얹어 두 쪽의 바꿈을 같게 한다.

## Risks / Trade-offs

- [GitHub에서 돌려 보지 못함] → 스크립트는 로컬 git 저장소 시험으로, 워크플로는 규칙 검사와 YAML 읽기로만 확인한다. 원격과 앱을 만든 뒤 첫 릴리스에서 D-T23·D-T24·D-T25를 실제로 돌린다.
- [`main` 규칙 세트가 데모 배포 성공을 요구함] → 데모 승격(wbs 0.4.4)이 생기기 전에는 마무리의 병합 단계가 거부된다. 그 전에는 마무리를 하지 않는다. 규칙 세트를 바꾸지 않는다.
- [병합한 뒤 트리가 다름] → 태그를 달지 않고 실패한다. 원인을 고친 새 후보로 다시 마무리하는 절차는 런북으로 둔다(wbs 4.7.1).
- [예약 실행이 출시할 변경 없이 매주 돎] → 변경이 없으면 아무것도 만들지 않고 성공으로 끝난다.
- [릴리스 봇의 workflows 권한] → 봇이 워크플로 파일을 바꿀 수 있는 권한이 생긴다. 봇은 버전 줄 말고는 내용을 쓰지 않고, 키는 `release` 환경 비밀로만 쓰며, 노출 대응은 secrets-and-keys의 '릴리스 봇' 행(RB-26)을 따른다.
