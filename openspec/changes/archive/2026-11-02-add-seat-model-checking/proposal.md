# 제안: 좌석 규칙 모델 검사 명세(wbs 0.9.2, BUILD_ORDER FND-140)

## Why

docs/verification.md §2.1은 좌석 규칙을 명세 `seat`로 쓰고 작은 범위의 모든 순서를 기계로 검사하라고 한다(ADR-0057). 지킬 약속은 ① 좌석당 판매 1건 이하(오버셀 0) ② 1인 한도 초과 판매 0 ③ 만료된 홀드(펜싱 토큰이 낡은 것)로 판매 확정 0이다. 좌석 Redis 장애 전환(복제 전 쓰기 유실, 원장 적재 전 홀드 유실, 장애 조치 동안 미룸, 세대 키가 없으면 거절, ADR-0121)과 비트맵 다시 만들기(RB-06)가 섞이면 타이밍에 따라서만 드러나는 틈이 생길 수 있어, 부하 시험보다 먼저 규칙 단계에서 본다. 0.9.1(FND-130)이 만든 검사 도구와 목록에 이 명세를 더하고, 전수 검사가 끝나는 범위는 시간을 재서 정한다(작은 범위 [가정, 0.9.2에서 확정]).

## What Changes

- **명세** `specs/seat.qnt`: 홀드 Lua(비트·홀드·1인 한도·펜싱 토큰, 세대 키 확인), 시간이 다 됨과 만료 작업, 1회 연장, 결제 접수의 홀드 확인(내 홀드 또는 빈 좌석), 판매 확정 트랜잭션(좌석 ID 순 PENDING 삽입, 활성 판매 부분 유니크, `purchase_quota` 조건부 갱신), 승인·거절과 좌석 해제, 홀드 원장 적재(Redis Stream → 원장), 좌석 Redis 비동기 복제와 장애 전환(주 노드 승격으로 복제 전 쓰기 유실, 클러스터 전체 유실), RB-06 다시 만들기(세대 키를 마지막에 씀).
- **불변식**: §2.1의 ①②③과, 정본이 적은 두 약속을 더 본다: ④ 펜싱 토큰은 홀드 순서대로 커진다(seat-hold §3 '엄격한 단조 증가', 원장 적재·델타가 기댄다) ⑤ 판매 확정 트랜잭션끼리 교착 0(좌석 ID 정렬의 목적, K3).
- **변형**(검사가 살아 있는지, V-T1): 부분 유니크, 한도 행 조건부 갱신, 좌석 ID 순 삽입, 세대 키 확인을 하나씩 끈 모듈. 그 불변식의 반례가 나와야 한다.
- **검사 목록**(`specs/specs.json`)에 `seat`를 더하고, 실행기(`tools/spec-check/spec-check.mjs`)의 목록 검사가 명세 이름 중복을 거절하게 한다(명세가 둘이 되면 결과 파일이 겹칠 수 있다).
- **찾은 것을 묻는다**: 정본 그대로에서 깨지는 약속이 나오면, 막는 추천안을 더한 모듈을 '지켜져야 하는 모듈'로 두고 정본 그대로의 모듈은 '반례가 남는 모듈'로 둔 채 PROGRESS의 미해결로 묻는다(FND-130과 같은 방식).

## Impact

- 정본: docs/verification.md §2.1(범위 확정)·§2.6(검사 기록), docs/features/seat-hold.md §12 머리말, ADR-0014·0057·0121 상태 줄, wbs 0.9.2, BUILD_ORDER(넘기는 것), 00-summary·consistency-review R 번호.
- 코드: `specs/seat.qnt`, `specs/specs.json`, `specs/results/seat*`, `specs/README.md`, `tools/spec-check/spec-check.mjs`·시험.
- CI: 바뀌지 않는다. `specs_full` 범위는 검사 목록의 `adrs`를 읽으므로 좌석 ADR(0014·0121)이 바뀌어도 전수 검사가 돈다.
- 보안: 화면·API·데이터가 없는 검사 도구 변경이다(ASVS 추적 표는 FND-130과 같이 docs/security/asvs/delivery.md 15.2.4의 범위 안).
