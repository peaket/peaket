# 설계: 문서 점검 도구 openapi 계약 검사의 시험

## Context

- 문서 점검 도구는 `tools/doc-check/check_all.py` 한 파일이다. 표준 라이브러리만 쓰고(Python 3.10 이상), 저장소 뿌리를 스크립트 위치로 정해 문서를 모두 읽은 뒤 검사 함수를 차례로 부른다(`main()`). 시험 파일은 없다.
- openapi 계약 검사는 두 함수다. `check_api`가 줄 규칙으로 경로·작업 수를 세고 경로 이름 규칙을 보며, `check_api_contract`가 YAML로 읽은 명세로 호스트·인증·Problem·If-Match를 보고 숫자를 보고한다. 둘이 센 작업 수가 다르면 오류다.
- CI(`docs-check.yml`)는 `python3 tools/doc-check/check_all.py`를 돌린다. `tools/doc-check/`가 바뀌면 `tools/ci/changes.mjs`가 `docs` 범위로 잡아 이 워크플로가 돈다.
- 2026-11-01 이 저장소의 보고: 경로 244, 작업 271, 4xx·5xx 응답 602 중 Problem 598, 예외 4(정적 파일 404 셋, 기기 승인 토큰 400), `operationId` 없음 271(wbs 0.2.3에서 붙인다), 호스트 없음 0, `security` 없음 0, 공개 22, If-Match 16·예외 3. 오류 0.

## Goals / Non-Goals

**Goals:**

- 기술 검토 낮음-031(호스트·인증 검사)과 낮음-032(숫자 보고)가 정한 것을 시험이 지킨다. 검사가 잡아야 할 명세는 오류가 나고, 맞는 명세는 오류가 없으며, 보고 숫자가 명세와 같다.
- 시험이 CI에서 돈다.

**Non-Goals:**

- 다른 검사(ids·paths·links·roles·blockers·wbs·mermaid 등)의 시험. 이 단계의 범위가 아니다. 이 파일을 본보기로 뒤에 더할 수 있다.
- 검사 동작 바꾸기. 시험을 쓰다 결함을 찾으면 재현 시험부터 만들어 이 변경에서 고친다(architecture §8.6의 3).
- `operationId`를 붙이는 일(wbs 0.2.3).

## Decisions

1. **시험의 경계는 'openapi 글 → 오류와 보고'다.** 도구의 바깥 경계는 저장소 전체를 읽는 명령이지만, 저장소 뿌리가 스크립트 위치로 고정이라 시험용 저장소를 통째로 만들어야 한다. 대신 시험은 `main()`이 부르는 순서 그대로(`check_yaml` → `check_api` → `check_api_contract`) openapi 글 하나를 `docs/api/openapi.yaml` 이름으로 넣고, 결과 `Report`의 오류와 정보 줄을 본다. 이 함수들은 이미 모듈의 함수이고 시험 때문에 새로 내놓거나 바꾸는 것이 없다(architecture §8.6의 5 '시험하려고 내부 함수를 공개하지 않는다'). YAML 글로 넣으므로 도구의 작은 YAML 읽개가 흐름 매핑(`{ prefix: …, server: … }`)을 읽는 길도 함께 지난다(추천 적용 2026-11-01).
2. **시험 틀은 표준 라이브러리 `unittest`다.** 도구가 표준 라이브러리만 쓰는 규칙(README '실행 환경')을 시험에도 지킨다. 실행: `python -I -X utf8 -m unittest discover -s tools/doc-check -p "test_*.py"`. `discover`가 시작 폴더를 가져오기 경로에 넣어 `check_all`을 읽는다(시험 파일도 자기 폴더를 넣어 파일을 바로 돌려도 된다). 격리 모드(`-I`)는 현재 폴더의 다른 파일과 `PYTHON…` 환경 변수를 읽지 않게 한다. 그래서 출력 글자 판을 환경 변수 대신 `-X utf8`로 정한다(윈도우에서 실패 메시지가 깨지지 않게).
3. **시험 이름에 검토 ID를 단다.** `test_낮음031_…`, `test_낮음032_…`처럼 기술 검토 항목 번호를 머리에 둔다(architecture §8.6의 5). 정본에 doc-check 시험 ID가 따로 없어 검토 항목 번호를 쓴다(추천 적용 2026-11-01).
4. **경우(낮음-031)**: ① 처음 맞는 접두사의 서버로 호스트를 센다(더 넓은 접두사가 뒤에 있어도 앞의 것이 이긴다) ② 경로 `servers`가 규칙을 이긴다 ③ 작업 `servers`가 경로 `servers`를 이긴다 ④ 맞는 규칙도 `servers`도 없으면 오류이고 `missing_host`로 센다 ⑤ `servers`에 다른 서버가 둘이면 오류 ⑥ 작업 `security`의 이름이 `securitySchemes`에 없으면 오류 ⑦ 전역 `security`의 이름이 없으면 오류 ⑧ `security`를 적지 않았는데 전역도 없으면 오류(전역이 빈 목록 `security: []`이어도 기본 인증이 없으므로 오류), 전역이 있으면 오류가 아니고 `missing_security`로만 센다 ⑨ `security: []`는 오류가 아니고 `public`으로 센다 ⑩ openapi를 YAML로 읽지 못하면 계약 검사가 조용히 건너뛰지 않고 오류를 낸다.
5. **경우(낮음-032)**: ① 작업 수, 4xx·5xx 수와 그중 Problem 선언 수(`application/problem+json` 직접 선언, `components/responses` 참조, 다른 형식 아래 `Problem` 스키마 참조), `operationId` 없음 수, 호스트별 작업 수가 명세와 같다 ② Problem 예외(기기 승인 토큰 400, 확장자 경로 404)는 오류가 아니고 예외 목록에 나온다 ③ 예외가 아닌 4xx가 Problem을 선언하지 않으면 오류 ④ 줄 규칙과 YAML 읽기가 센 작업 수가 다르면 오류(줄 규칙이 세지 않는 `head` 작업을 둔다). 숫자를 손으로 적지 않는다는 결정(낮음-032)은 이 대조가 있어야 지켜진다.
6. **실패를 보는 방법.** 검사가 이미 있으므로 시험을 먼저 써도 바로 통과한다. 그래서 시험이 검사를 실제로 지키는지 보려고, 저장소 밖(세션 임시 폴더)에 `check_all.py`를 복사해 검사 한 줄씩을 끈 변형을 만들고 그 변형으로 시험을 돌려 해당 시험이 실패하는 것을 본다. 저장소의 파일은 고치지 않는다. 변형마다 어느 시험이 실패했는지 tasks.md에 적는다.
7. **CI**: `docs-check.yml`에서 문서 점검 바로 앞에 시험 단계를 둔다. 시험이 실패하면 도구가 믿을 수 없으므로 문서 점검을 돌리지 않고 실패한다. ubuntu 실행기의 `python3`(3.12)를 그대로 쓴다.

8. **코드 리뷰 반영(2026-11-01).** 새 맥락의 리뷰는 동작·보안 결함과 회귀가 없다고 했고, 시험이 지키지 않는 곳 둘을 찾았다. ① 전역 `security: []`를 '전역 있음'으로 잘못 보게 바꿔도 시험이 통과했다(결정 4 ⑧에 더함) ② `Problem` 스키마 참조로 선언한 응답을 Problem으로 안 받게 바꿔도 시험이 통과했다. 실제 openapi도 이 방식을 쓰지 않아 CI의 실제 점검으로도 잡히지 않는다(결정 5 ①에 더함). 둘 다 그 변형으로 시험이 통과하는 것을 먼저 본 뒤 시험을 더했다.

## Risks / Trade-offs

- 시험이 함수 순서를 `main()`과 따로 적어 두므로, `main()`의 순서가 바뀌면 시험도 고쳐야 한다. 함수가 셋뿐이라 받아들인다.
- 저장소 전체를 읽는 명령 자체(파일 찾기, 출력 형식, 종료 코드)는 이 시험이 보지 않는다. CI가 실제 저장소로 매번 돌리는 것으로 갈음한다.
