# 설계: 사후 포렌식 법률 검토 결과를 퍼블리싱 화면에 옮기기

## Context

- 화면 모양·상태·문구의 정본은 d5다. FRN-080(커밋 `a92695b`)이 d5에 '(추천 적용 2026-10-31, ADR-0173)'로 더하거나 고친 줄이 이번 변경의 범위다. d2 CMP-060·063과 d3 SCR-042·046·056·071 행도 같은 커밋에서 고쳤다.
- 앞선 퍼블리싱(ADR-0170, 보관한 `add-screen-publishing`·`align-screens-with-canon`·`add-fraud-investigation-screens`)의 방식을 그대로 쓴다: 키트 CSS는 `@peaket/ds`, 상태는 `?state=`, 앱마다 `/preview` 목록, 목업 데이터는 합성 고정 값, 관제는 창 폭으로 보드별 배치(`board-d/t/m`)를 고르고 새 화면(SCR-070·071)은 한 벌의 반응형 마크업이다.
- 이번에 바꾸는 변형(SCR-042 받은 사람·조치 결과·이의 결과, SCR-046 판단 이유·범위 줄이기, SCR-071 잠금 기한 등)은 원래 디자인 캔버스 보드에 없다. d5 그림이 시각 기준이다.
- 화면 앱의 시험은 Node 내장 시험 실행기(`node --test`, 타입 지우기로 `.ts`를 그대로 읽음)다. 시험 도구(화면 시험 라이브러리)는 FND-030의 몫이다.

## Goals / Non-Goals

**Goals**

- FRN-080이 d5에 고친 화면 문구·상태를 퍼블리싱 화면에 빠짐없이 옮기고, FRN-070이 넘긴 두 가지(SCR-070 '후보 만들기 다시 시도 중', SCR-027 [부정 예매 조치] 탭)를 그린다.
- 법률 검토가 화면에 요구한 성질이 화면에서 보이게 한다: 잠금에 끝이 있음, 받은 사람도 알림을 받고 진술할 수 있음, 승인자는 요약을 연 뒤 자기 이유를 적고 범위를 줄일 수 있음, 여러 건을 한꺼번에 승인할 수 없음, 묶음 계정의 행동 값을 나란히 견주는 보기가 없음, 외부 게시물은 공개 글 한 건만.

**Non-Goals**

- 데이터 연결과 API 클라이언트, 재인증 실제 흐름, 실제 캡처 칠하기(서버 몫).
- 디자인 캔버스 보드 고침. 이 계정의 'PEAKET 사후 포렌식 화면 보드'(FRN-070)는 퍼블리싱 화면을 옮긴 그림이고, 캔버스는 소유자가 요청할 때만 고친다.
- 알림 문안(이메일)은 화면이 아니라 뺀다(d5 §9.1은 문서로 끝).

## Decisions

### 1. 범위는 FRN-080 d5 diff의 화면 줄 전부

BUILD_ORDER FRN-090 설명의 목록(SCR-041·042·046·070·071·012·017·027)은 머리 항목이고, 설명 첫 문장이 'FRN-080에서 d5에 고친 것을 퍼블리싱 화면에 옮긴다'이다. 그래서 그 diff에서 화면에 보이는 줄을 모두 옮긴다. 목록에 없던 것으로 SCR-014 '부정 예매 조사로 잠김'(§5.14, §9.2 409 `transfer-locked`), SCR-056 문의 유형 '외부 되팔이 게시물 신고'(§5.30), SCR-070 외부 게시물 등록의 최소화, SCR-069 연구 원천 만료 문구가 있다. 대안(목록만 하기)은 같은 법률 검토의 화면 반영이 두 단계로 갈라져 버렸다.

### 2. 'SCR-012 잠금 안내'는 SCR-011의 상태

d5에서 '부정 예매 조사로 양도가 잠기는 회차'는 §5.11 SCR-011 주문·결제의 상태 표에 있다("결제 버튼은 그대로", 결제 전에 알린다는 약관법 설명의무). SCR-012 결제 결과에는 고친 줄이 없다. 그래서 SCR-011에 그린다(추천 적용 2026-10-31). PROGRESS '다음 할 일'도 011로 적었다.

### 3. 상태 이름은 d5 상태 표의 이름 그대로

각 화면의 `?state=` 목록과 `/preview`에 d5 상태 표 첫 칸의 이름을 그대로 더한다(예: '양도 잠금 풀림 · 부정 예매', '받은 표 확인 요청', '부정 예매 조치 · 범위를 줄임'). 오류 응답(§9.2)으로 보이는 화면은 그 상태가 따로 없으면 `?state=`에 '오류 · <type>' 꼴로 더한다(추천 적용 2026-10-31).

### 4. 목업 값은 d5 그림의 예

소명 요청 10/18(일) 16:00, 기한 3일, 잠금 기한 11/1(일) 16:00, 공연 LUMEN 콘서트 2026 서울 10/25(일) 18:00, 사건 CASE-2610-0004·0007 같은 d5 예를 쓴다. 받은 사람의 표는 A구역 3열 16번이다. 조사관이 적은 이유처럼 사람이 쓰는 글은 '[조사관이 적은 이유]' 자리 표시다(d5). 시각은 모두 KST 표기 글이다.

### 5. 계산·판정·문구는 시험을 먼저(TDD)

화면이 쓰는 규칙은 모듈의 공개 함수로 두고 `node --test` 시험을 먼저 써서 실패를 본 뒤 만든다(architecture §8.6의 5, 시험 이름에 요구사항 ID).

- 웹: 잠금 기한 문장(`lockExpiresAt` 글을 넣음), 받은 사람 변형의 문구와 표마다 결과 글, 조치 결과 문장(취소한 표·전액 환급·이용 제한 끝·이의 기한), 받은 사람에게는 사유 범주·이의가 없다는 것, 문의 유형 열두 개가 openapi `InquiryCategory`와 같다는 것.
- 관제: SCR-046 승인 판정(요약을 열었는가·판단 이유가 1~1000자인가·남은 대상이 있는가 → 승인 가능 여부와 비활성 이유), 범위에 따른 단추 글("표 15장 취소와 환급을 승인합니다(3장 뺌)"), SCR-071 이용 제한 끝이 요청 + 1년 [가정]을 넘는지, SCR-070 외부 게시물 등록 단추가 확인 칸 셋을 모두 체크해야 켜지는지와 신고 출처 규칙, 내보내기 종류 셋이 openapi와 같다는 것.
- 파트너: 부정 예매 조치 집계의 글(사람 단위 행 없음)과 집계 전 상태.

### 6. 화면은 확인 스크립트를 먼저

E2E 시험은 쓰지 않는다(ADR-0167 결정 6). 화면을 고치기 전에 저장소 밖(세션 임시 폴더)의 Playwright(Python) 확인 스크립트를 먼저 써서 새 상태·문구가 없어 실패하는 것을 보고, 고친 뒤 통과를 본다. 항목은 주소마다 `h1` 하나, 가로 넘침 없음, 정본 문구, 없어야 할 글(받은 사람 화면의 사유 범주·이의 단추, 승인 목록의 여러 건 고르기, 행동 값 나란히 보기, 원문 IP)이다.

### 7. 행동 값 나란히 보기가 없음은 확인으로 끝낸다

SCR-071·SCR-069에는 지금도 묶음 계정의 행동 값을 견주는 보기가 없다(FRN-050). 새로 그리지 않고, 확인 스크립트와 코드 검색으로 없음을 보며, SCR-071 조치 요청 의견 칸에 d5 안내 문장("행동 요약은 세션 하나가 자동화인지 보는 근거로만 적습니다…")을 더한다.

### 8. 부품은 쓰는 앱에 둔다

CMP-063 AppealForm·AppealCaseCard는 `packages/ds`에 있으므로 거기서 칸을 더한다(받은 사람 변형, 조치 결과·이의 결과 자리). CMP-060 fraud-action은 지금처럼 관제 앱의 `FraudActionPanel`에서 고친다. 새 CMP 번호는 만들지 않는다(d2가 변형만 더했다).

### 9. 브라우저 확인

대조 뒤 peaket-browser-check 절차로 Claude in Chrome에서 한다(이번 턴 연결 있음). 사람 확인(화면 낭독기 완주 등)은 확인 목록만 남긴다(PROGRESS 턴 규칙).

### 10. 새 맥락 리뷰로 더하고 고친 것

리뷰가 결정 1의 범위에서 빠진 줄(SCR-002 예매 안내사항의 '부정 예매 조사', SCR-070 게시 시각 칸, SCR-014 409 상태)을 찾아 더했다. 상태를 화면 안 이동으로 바꿀 때 처음 값이 남던 칸(SCR-071 이용 제한 끝·내보내기 종류, SCR-070 확인 칸·신고 건)은 `key={state}`로 다시 그린다. SCR-002 안내 문장은 d5가 내용만 정해 추천 적용이고, 조사 시점은 POL-046 ②대로 '온세일이 끝난 뒤'다. 409 뒤에는 표가 이미 잠겼으므로 SCR-014는 잠김 구성(③④⑤ 숨김)에 §9.2 오류 띠를 둔다.

## Risks / Trade-offs

- [화면 셋을 여러 손으로 나눠 고침] → 앱마다 맡는 폴더를 나누고(웹+AppealForm, 관제+포렌식, 파트너), `packages/ds`는 웹 쪽만 고친다. 통합 확인은 한 번에 한다.
- [d5 문장과 화면 글이 어긋남] → 고정 문구는 시험과 확인 스크립트가 d5 글자 그대로를 본다.
- [목업 회차로는 생길 수 없는 그림 상태] SCR-071 '양도 잠금 최대 기한 지남'은 목업 회차의 입장 시작(10/25)이 첫 후보 묶음(10/14) + 14일보다 먼저라 날짜로는 생기지 않는다 → 그 상태에서는 날짜 대신 규칙과 지난 계정 수만 적고, 주석에 그림 상태임을 남긴다. 데이터 연결 때 실제 `members[].lockExpiresAt`으로 그린다.
- [목업이 서버 규칙처럼 보임] → 판정 함수는 화면 안내용이고 서버 규칙(422·409)의 정본은 openapi와 기능 설계서다. 모듈 머리 주석에 적는다.
