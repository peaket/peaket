# 제안: 규칙 모델 검사 도구와 대기열·입장 제어 명세(wbs 0.9.1, BUILD_ORDER FND-130)

## Why

docs/verification.md §2는 핵심 규칙을 실행할 수 있는 명세로 쓰고 작은 범위의 모든 순서를 기계로 검사하라고 한다(ADR-0057). 타이밍이 맞아야 드러나는 버그(멈췄다 깨어난 옛 리더의 쓰기, 장애 전환으로 사라진 키)는 부하 시험으로 잘 나오지 않기 때문이다. 0.9.1의 몫은 검사 도구(Quint·TLC, CI 실행·결과 기록)와 첫 명세 `queue`(대기열·입장 제어)다. 0.9.2(좌석)·0.9.3(결제)·5.2.2(입장·양도)가 이 도구를 쓰고, 모델 기반 시험(2.3.4)이 같은 동작 이름을 쓴다. 정본의 '시뮬레이션 1만 회'와 작은 범위는 [가정, 0.9.1에서 확정]으로 남아 있다.

## What Changes

- **명세** `specs/queue.qnt`: 진입 세 단계(사람 슬롯 선점 → 회차 슬롯 `INCR` → 사람 슬롯 기록), 동시 도착 구간 묶음(닫힘 표시 `HSETNX`), 리더 교체(Lease, 리더 세대)와 세대 확인 Lua, 멈췄다 깨어난 옛 리더의 쓰기, 대기열 Redis 비동기 복제와 장애 전환(회차 슬롯·사람 슬롯), RB-05(카운터 건너뛰기·세대 올리기), 이탈, 입장 확정(serving·빠진 번호·건너뛴 구간·1인 1순번 재확인). 불변식은 §2.1의 ①~④와, 1인 1순번(POL-002)을 보는 ⑤다.
- **변형**: 세대 확인(V-T1), 입장 확정의 serving 확인, 1인 1순번 재확인을 하나씩 끈 모듈. 그 불변식의 반례가 나와야 검사가 살아 있다.
- **검사 목록과 실행기**(`specs/specs.json`, `tools/spec-check/`): 형식 검사, 고정 시드 시뮬레이션, TLC 전수 검사, 결과 파일(명세 해시·커밋·범위·도구 판·상태 수·깊이·지문 충돌 확률·위반 여부·반례 경로, `specs/results/`). 도구는 고정 판·고정 해시로 받는다(외부 계정 없음). 이 PC에서는 Java가 없어 컨테이너로 돌린다.
- **CI**(`.github/workflows/spec-check.yml`, `tools/ci/changes.mjs`의 `specs`·`specs_full`): 명세·도구가 바뀌는 PR마다 형식 검사와 시뮬레이션 1만 회, 주 1회와 관련 ADR이 바뀔 때 전수 검사.
- **찾은 것**: 정본에 적힌 그대로는 장애 전환 뒤 RB-05가 세대를 올리기 전에 들어온 진입이 잃은 번호와 같은 번호·세대를 받아 ②가 깨진다(OPEN[13]). 묶음 참가자의 선점 값을 정본대로(PENDING, 수명 10초) 두면 결과 게시 전에 만료돼 장애 전환 없이 같은 사람이 대기표를 하나 더 받는다(1인 1순번 ⑤, OPEN[14]). 두 추천안을 더하면 다섯 불변식이 모두 지켜진다. 정본에 없고 진입 경로를 바꾸는 결정이라 소유자에게 묻는다. 그동안 검사 목록은 정본 그대로의 모듈을 '반례가 남는 모듈'로, 추천안 모듈을 '지켜져야 하는 모듈'로 둔다.
