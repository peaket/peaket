# K5 PoC 결과 — 5만 석 Canvas(BUILD_ORDER BAS-190, wbs 0.5.4)

- **언제·무엇으로**: 2026-11-04. 5만 석(무대 앞 두 줄의 직사각 구역 10 × 50열 × 100석, 좌표에 ±5cm 흔들림)을 만들어(`layout.mjs`) 열 단위 JSON으로 내고, PoC 페이지(`page/`)가 Worker에서 받아 형식 배열로 풀고 구역별 격자 색인을 만든 뒤 OffscreenCanvas에 그린다. Playwright 1.64.1, 판을 고정한 리눅스 컨테이너(`mcr.microsoft.com/playwright:v1.64.1-noble`)의 Chromium 156·Firefox 157·WebKit 27.2. 화면 412×915·배율 2.625(K5 랩 조건, docs/verification.md §3.10). 프로젝트마다 다섯 번 재 중앙값과 최댓값을 적었다.
- **판정 조건**: docs/frontend.md §5.2의 예산을 Chromium(CPU 4배 느리게)에서 매번 본다. 단계 3 'Worker 시작·캔버스 넘기기·파일 풀기 250ms'(격자 색인 포함), 단계 5 '전체 배치도 첫 그림 100ms', 메시지 처리 p95 2ms, 메인 스레드 긴 작업 0(§5.8 좌석 화면).
- **결과**: 통과(다섯 번 모두). 단계 3 어림 140ms(최대 162), 단계 5 어림 44ms(최대 46), 메시지 처리 p95 0.1ms, 긴 작업 0. 아래 '남는 것'의 WebKit 흔들림은 실기기로 확인한다.

## 재는 법과 한계

- **그리기 끝내기**: Chromium 캔버스는 그리기 명령을 모아 두었다가 나중에 그린다. 잰 구간 끝에서 한 화소를 읽어(`getImageData`) 그리기를 끝내게 했다. 읽기 비용이 더해져 보수적인 값이다(특히 WebKit). 처음 잰 값(읽지 않음)은 명령을 적는 시간이라 버렸다(새 맥락 리뷰가 짚음).
- **메시지 처리**: 받은 메시지는 `data`를 처음 읽을 때 풀리므로(구조화 복제 풀기), 처리 시간은 처리기 첫 줄부터 잰다.
- **CPU 느리게 하기는 Worker에 걸리지 않는다**: 개발자 도구 규약의 CPU 느리게 하기는 메인 스레드에만 걸렸다(Worker 단계가 느리게 하지 않은 때의 1.0~1.3배). 그래서 판정은 Worker 몫(받기·풀기·색인, 첫 그림 그리기)에 4를 곱한 어림으로 한다.
- **첫 그림 시각**: Worker의 다음 프레임 콜백이 불린 시각이다. 화면에 실제로 내보낸 시각(합성)은 재지 않았다.
- **시계 단위**: Firefox·WebKit은 시계를 1ms로 잘라, 0은 '1ms 미만'이다.
- **받기**: 정적 서버가 압축 없이 매번 새로 준다(`no-store`). 실제 길(대기 중에 받아 둔 HTTP 캐시에서 brotli 풀기)은 재지 않았다.

## 설계에 주는 것

1. **팬 좌석맵 파일은 열 단위로 낸다**: 압축 전 3.4배·brotli 3.0배 작고, 형식 배열로 옮겨 풀기가 5ms 안팎이다. openapi `SeatMapLayout`(파트너 에디터가 저장하는 문서)은 좌석을 객체 배열로 적는다. 팬이 받는 좌석맵 파일(`seatmap-layouts/{layoutVersion}.json`)의 응답 형식을 열 단위로 나눠 적는 계약 일은 HOT-110이 한다.
2. **구역 비트맵은 작을 때만 만든다**: 구역 전체가 화면에 들어오는 중간 배율의 구역 비트맵은 4.0MB(10구역 40MB)라 §5.2의 64MB 상한 안이다. 좌석을 고를 수 있는 배율(24 CSS px)의 구역 비트맵은 6,376×5,696 기기 화소(약 3,630만 화소, 145MB)라 64MB 상한과 iOS Safari 캔버스 넓이 상한(약 1,680만 화소)을 모두 넘는다. 그 배율에서는 보이는 좌석만 바로 그린다(Chromium 1.4ms·Firefox 5ms). 그 사이 배율에서는 구역 비트맵이 정한 크기 [가정] 이하일 때만 만든다. 리눅스 WebKit은 바로 그리기가 화소 읽기를 넣어 28ms(최대 127ms)라, iOS 실기기에서 프레임 시간을 보고 넘으면 작은 타일 비트맵으로 바꾼다(HOT-110).
3. **메시지 길 하나로 충분하다**: 풀기를 넣은 처리 p95가 0.1ms라 §5.2의 예산(p95 2ms)을 크게 밑돈다. 공유 메모리 길(COEP)을 다시 볼 까닭이 없다.
4. **CPU 4배 느리게 하기는 Worker에 걸리지 않는다**: v0는 메인 스레드에서 그리고 v1은 Worker로 옮기므로, 같은 조건의 K5 랩 비교(wbs 7.5.2, FE-T10)는 v1의 Worker 몫을 보정하거나 기기 벤치로 본다(BUILD_ORDER LCH-200).

## 남는 것(실기기 확인 목록, 소유자 몫)

- [ ] iOS 16.4~17 Safari(실기기)에서 PoC 페이지를 열어 첫 그림까지의 시간과 확대·끌기 동안의 프레임 시간을 본다. 리눅스 WebKit 27.2는 전체 배치도 그리기가 중앙값 28ms이지만 한 번 175ms였고, 보이는 418석 그리기가 한 번 127ms였다(Chromium·Firefox에는 이런 튐이 없었다). 실기기에서도 단계 5가 100ms를 넘으면 구역 도형만 담은 작은 자료로 위에 겹친 임시 캔버스에 첫 그림을 그리는 길을 HOT-110에서 본다(Worker로 넘긴 캔버스에는 메인 스레드가 그릴 수 없다).
- Windows용 Playwright WebKit 빌드에는 OffscreenCanvas가 없어(이 PC) WebKit은 리눅스 컨테이너에서만 쟀다. 그런 브라우저의 대체 길은 FE-T15다.
