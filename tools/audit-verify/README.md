# 감사 체크포인트 공개 검증 도구(`audit-verify`)

피켓이 내놓은 감사 기록 요약을 피켓을 믿지 않고 확인하는 도구다. 결정과 바이트 꼴의 정본은 [ADR-0075](../../docs/adr/0075-public-audit-anchor-signed-merkle-checkpoints.md)(공개 앵커)와 [ADR-0348](../../docs/adr/0348-public-audit-checkpoint-standard-merkle-ecdsa-ots-publish-verify-tool.md)(첫 구현 세부)이고, 이 글은 쓰는 법만 적는다.

## 낱말

- **체크포인트**: 감사 기록 여러 건을 묶은 요약 파일이다. 번호(`no`)가 1부터 빈틈 없이 붙고, 앞 체크포인트의 해시(내용이 한 글자만 달라도 완전히 달라지는 고정 길이 지문)를 담아 사슬처럼 이어진다.
- **머클 루트**: 기록마다 만든 지문을 둘씩 묶어 다시 지문을 내기를 반복해 남은 하나다. 기록 하나가 바뀌면 루트가 바뀐다.
- **포함 증명**: 기록 하나와 몇 개의 지문만으로 그 기록이 어떤 루트에 들어 있음을 보이는 값이다(RFC 9162).
- **정규형 JSON**: 같은 내용이면 늘 같은 바이트가 되도록 공백·키 차례·숫자 꼴을 정한 JSON이다(RFC 8785). 서명과 해시는 이 바이트에 건다.
- **서명**: 피켓의 체크포인트 서명 키(ECDSA P-256)로 만든 값이다. 공개키(`public-keys.json`)로 누구나 확인한다.
- **공개 타임스탬프**: OpenTimestamps(비트코인 블록에 지문을 기대어 '그때 이미 있었다'를 보이는 공개 서비스)의 증명 파일(`.ots`)이다.
- **검증 묶음**: 분쟁 당사자가 받는 파일로, 기록 하나의 원문과 잎 솔트(기록마다 섞은 비밀 난수), 포함 증명, 체크포인트를 담는다.

## 쓰는 법

파이썬 3.11 이상과 시스템 `openssl`(서명 확인)이 있으면 된다. 표준 라이브러리만 쓴다.

```bash
# 내려받은 공개 폴더(transparency/v1 또는 그 위 폴더)
python tools/audit-verify/audit_verify.py <폴더>
# 두 곳에서 받은 폴더를 함께 주면 같은 번호끼리도 견준다(사람마다 다른 체크포인트를 보였는지)
python tools/audit-verify/audit_verify.py <폴더1> <폴더2>
# 검증 묶음: 폴더를 함께 줘야 묶음의 공개키를 공개 키 목록과 대조한다
python tools/audit-verify/audit_verify.py <폴더> --bundle <묶음.json>
# 기계용 출력, 비트코인 단계를 공식 클라이언트로 따로 봤을 때, openssl 경로 지정
python tools/audit-verify/audit_verify.py <폴더> --json --skip-bitcoin --openssl /usr/bin/openssl
```

## 확인하는 것

| 단계 | 무엇을 보나 |
| --- | --- |
| `checkpoint-json` | 칸 꼴과 정규형 바이트인지, 파일 이름 번호와 JSON의 `no`가 같은지 |
| `numbers` | 1부터 가장 큰 번호까지 빈틈이 없는지(목록 `index.json`과 파일을 합쳐 본다) |
| `same-number` | 같은 번호에 다른 체크포인트가 있는지(목록 안 중복, 목록과 파일, 폴더 사이, 묶음과 폴더). 다르면 둘 다 보인다 |
| `chain` | 앞 체크포인트 해시가 이어지고, 첫 체크포인트가 기록 1번부터 덮고, 기록 구간이 빈틈 없이 이어지는지 |
| `signature` | `openssl dgst -sha256 -verify`로 서명을 확인한다. 공개키가 P-256인지도 본다 |
| `ots` | 증명 파일의 머리·판·해시 연산·대상 해시(= 체크포인트 해시)와 연산 갈래 |
| `record`·`leaf`·`inclusion` | 묶음만: 기록 원문 → 기록 해시 → 잎 → 포함 증명 → 체크포인트의 머클 루트 |
| `access-log-day-anchor` | 일 앵커 칸이 없으면 '없음'으로 알리고 실패로 세지 않는다 |

공개 폴더에는 기록 원문과 잎 솔트가 없다. 그래서 폴더만으로는 사슬·서명·증명 머리까지 보고, 기록 단계는 검증 묶음이 있을 때만 본다.

## 확인하지 못하는 것

- **비트코인 단계**: 증명이 실제 비트코인 블록에 들었는지는 이 도구가 보지 않는다. 공식 OpenTimestamps 클라이언트로 `ots verify <번호>.complete.ots`를 돌린다. 따로 봤으면 `--skip-bitcoin`을 준다. 주지 않으면 이 단계는 '확인 못 함'이다.
- `openssl`이 없으면 서명 단계가 '확인 못 함'이다.
- 처음부터 기록하지 않았거나 거짓으로 기록한 것은 막지 못한다(ADR-0075).

## 끝 코드

| 코드 | 뜻 |
| --- | --- |
| 0 | 모두 통과 |
| 1 | 어긋남이 하나라도 있음(확인 못 한 단계가 함께 있어도 1). 받은 체크포인트 파일의 꼴이 틀린 것도 어긋남이다 |
| 2 | 입력 오류: 폴더가 없음, 목록·키 목록·묶음 파일을 읽지 못함, 명령줄이 틀림 |
| 3 | 어긋남은 없지만 일부 단계를 확인하지 못함(비트코인 단계, openssl 없음, 받지 못한 파일) |

## 시험

시험은 이 폴더의 `*.test.mjs`(node `--test`, 파이썬을 불러 끝 코드와 `--json` 결과를 본다) 자리에 시험 담당이 둔다(BAT-360 계획 9절).
