# specs — 규칙 모델 검사 명세

핵심 업무 규칙을 실행할 수 있는 명세로 쓰고, 작은 범위에서 일어날 수 있는 모든 순서를 기계로 검사하는 곳입니다(docs/verification.md §2, ADR-0057, wbs 0.9). 명세 언어는 Quint입니다. Quint는 문법이 일반 프로그래밍 언어에 가깝고 TLA 논리를 씁니다. 전수 검사는 TLC(TLA+의 모델 검사기)가 합니다.

이 폴더의 명세는 정본이 아닙니다. 규칙의 정본은 docs/ 아래 설계 문서와 ADR입니다. 둘이 다르면 정본이 이기고, 명세를 고칩니다.

## 파일

| 파일 | 내용 |
| --- | --- |
| `queue.qnt` | 대기열·입장 제어 명세(wbs 0.9.1). 진입 세 단계(선점 → 번호 → 기록), 동시 도착 구간 묶음, 리더 교체와 세대 확인, 대기열 Redis 장애 전환과 RB-05, 입장 확정의 1인 1순번 재확인 |
| `seat.qnt` | 좌석 홀드·판매 확정 명세(wbs 0.9.2). 홀드 Lua(비트·1인 한도·펜싱 토큰·세대 키), 시간이 다 됨과 만료, 연장, 결제 접수의 홀드 확인, 판매 예약 트랜잭션(좌석 ID 순 PENDING, 부분 유니크, 한도 행), 승인·거절과 좌석 해제, 홀드 원장 적재, 좌석 Redis 장애 전환(주 노드 승격, 클러스터 전체 유실)과 RB-06 다시 만들기 |
| `specs.json` | 검사 목록. 명세마다 범위, 관련 ADR, 불변식, 검사할 모듈과 기대(지켜짐 또는 반례)를 적습니다 |
| `results/<명세>.json` | 마지막 전수 검사 결과. 명세 해시와 커밋, 범위, 도구 판, 탐색한 상태 수와 깊이, 지문 충돌 확률, 위반 여부를 남깁니다 |
| `results/<명세>/<모듈>.tlc.txt` | TLC가 찾은 가장 짧은 반례 경로. 처음 상태에서 불변식이 깨지는 상태까지의 상태 목록입니다(TLA+ 표기) |
| `results/<명세>/<모듈>.itf.json` | 같은 불변식의 반례를 고정 시드 시뮬레이션으로 다시 찾은 동작 기록(ITF 형식 JSON, 걸음마다 고른 동작 이름 포함). 모델 기반 시험의 재생(wbs 2.3.4)이 읽습니다. TLC 반례보다 길 수 있습니다 |

## 명세를 읽는 법

- **불변식**(언제나 참): 어떤 순서로 일이 벌어져도 깨지면 안 되는 약속입니다. 이름이 `inv_`로 시작합니다.
- **검사 모듈**: 같은 명세를 상수만 바꿔 여러 번 씁니다. `queue_proposed`처럼 지켜져야 하는 모듈과, 설계 장치 하나를 일부러 끈 변형(`queue_no_fencing` 등)이 있습니다. 변형은 반례가 나오는 작은 범위로 줄여 둘 수 있습니다(PR마다 도는 시뮬레이션이 그 반례를 찾아야 하기 때문입니다).
- **변형**: 장치를 끄면 그 장치가 막던 반례가 나와야 합니다. 반례가 안 나오면 검사가 아무것도 보지 않는 것이라 실패로 봅니다(V-T1).
- **작은 범위**: 사람·탭·서버·장애 횟수를 작게 두고 그 안의 모든 순서를 봅니다. 주장하는 범위는 '이 범위 안에서 위반 없음'까지입니다(docs/verification.md §2.3).

## 돌리는 법

Windows 개발 PC에는 Java가 없어 Linux 컨테이너로 돌립니다(Docker가 켜져 있어야 합니다).

```bash
node tools/spec-check/run-local.mjs typecheck     # 형식 검사
node tools/spec-check/run-local.mjs pr            # 형식 검사 + 검사마다 시뮬레이션 1만 회(PR마다 CI가 하는 것)
node tools/spec-check/run-local.mjs full --write  # TLC 전수 검사, 결과를 results/에 씀
```

CI는 `.github/workflows/spec-check.yml`에서 같은 스크립트를 돌립니다. 도구 판과 해시 고정은 `tools/spec-check/README.md`에 있습니다.

## 지금 결과(2026-11-02)

- `queue`의 범위: 정본 범위(사람 2명 탭 2개씩, admission-ctrl 2대, 장애 전환 2회, 리더 교체 2회)는 TLC 전수 검사가 끝나지 않아(리더 교체를 빼고 대기표 4장만 두어도 상태 4,400만 개를 넘음) 전수 검사를 두 범위로 나눴습니다. 진입 범위(사람 2명, 한 사람은 탭 2개라 대기표 3장, admission-ctrl 1대, 장애 전환 2회)와 리더 범위(대기표 1장, admission-ctrl 2대, 리더 교체 2회, 회차 슬롯 장애 전환 2회)입니다. 정본 범위 전체는 시뮬레이션 1만 회로 봅니다(`queue_proposed_full`).
- 정본에 적힌 그대로(`queue_canon`)는 같은 세대 안에서 번호가 겹치는 반례가 나옵니다. 대기열 Redis 장애 전환으로 카운터가 되돌아간 뒤 RB-05가 세대를 올리기 전에 들어온 진입이, 잃은 번호와 같은 번호·세대를 받습니다(PROGRESS OPEN[13]).
- 그 틈을 막아도(`queue_canon_batch_dup`) 1인 1순번이 깨지는 반례가 나옵니다. 동시 도착 구간 묶음에 들어간 탭의 선점 값(PENDING, 수명 10초)이 결과 게시 전에 만료되면, 같은 사람의 다른 탭이 장애 전환 없이 번호를 하나 더 받습니다. 정본은 묶음 참가자의 선점 값을 정하지 않았습니다(PROGRESS OPEN[14]).
- 두 추천안('RB-05가 끝날 때까지 번호를 내지 않는다', '묶음에 넣은 뒤 선점 값을 묶음 기록으로 바꾼다')을 더한 모듈(`queue_proposed`)은 다섯 불변식을 모두 지킵니다. 어느 쪽으로 정할지는 소유자 결정을 기다립니다.
- 수치(상태 수, 깊이, 지문 충돌 확률, 걸린 시간)는 `results/queue.json`과 docs/verification.md §2.6에 있습니다.
- 진행성('serving이 멈추지 않으면 앞사람부터 입장 자격을 얻는다')은 아직 검사하지 않습니다. 공정성 가정을 적은 시간 논리 검사가 필요해 모델 기반 시험(wbs 2.3.4) 전에 범위를 줄인 모듈로 더합니다.
- `seat`의 범위(wbs 0.9.2): 정본 범위(좌석 3석, 사람 3명 홀드 시도 2번씩, 1인 한도 2매, 장애 전환 1회)는 TLC가 10분 동안 상태 2,000만 개를 넘어도 깊이 11에 머물러 끝나지 않아, 전수 검사는 사람 2명(한 사람은 시도 2번이라 시도 3개)·요청 4가지로 줄였습니다(`seat_proposed`). 정본 범위 전체는 시뮬레이션 1만 회로 봅니다(`seat_proposed_full`). 변형은 반례가 나오는 작은 범위로 줄였고, 반례가 드문 `seat_no_ready_check`는 장애 전환을 전체 유실만 두고 시뮬레이션을 10만 회 돕니다(검사 목록의 `samples`).
- `seat`의 불변식은 §2.1의 ①오버셀 0 ②1인 한도 초과 0 ③만료된 홀드로 판매 확정 0에, 정본이 적은 ④펜싱 토큰은 홀드 순서대로 커진다 ⑤판매 확정 트랜잭션끼리 교착 0을 더한 다섯입니다. ③은 판매 예약이 커밋되는 순간 그 좌석의 가장 새 펜싱 토큰을 받은 시도가 따로 있고 그 시도가 결제 접수까지 와 있는지로 셉니다(좌석 Redis가 장애로 잊었어도 셉니다. 결제 접수 전에 잃은 홀드는 ADR-0121이 받아들인 손실이라 세지 않습니다).
- 정본에 적힌 그대로(`seat_canon`)는 ③이 장애 전환 없이 깨집니다. 결제 접수의 홀드 확인은 좌석을 바꾸지 않아, 확인과 판매 예약 사이에 홀드가 만료되고 다른 시도가 그 좌석을 잡아도 앞 주문의 판매 예약이 성공합니다(PROGRESS OPEN[15]).
- 그 틈을 막아도(`seat_canon_fencing`) ④가 깨집니다. 펜싱 카운터를 회차 슬롯에 두면 주 노드 승격이 복제 전의 증가를 잃어 같은 토큰이 다시 나옵니다(PROGRESS OPEN[16]).
- 두 추천안('판매 예약 앞에서 좌석을 묶고, 다시 만들기 판 번호로 다시 만든 뒤의 커밋을 묶기부터 다시 한다', '펜싱 토큰에 시계 하한을 둔다')을 더한 모듈은 ①②③⑤를 지킵니다. ③은 '주 노드 승격 한 번에 1건 이하'로 세며, 추천안에서도 승격이 다시 잡은 묶기 쓰기를 잃으면 1건이 실제로 생깁니다(그래서 남는 한계로 둘지 함께 묻습니다). ④는 시계 하한을 모형에 전제로 넣어 늘 참이므로 추천안 모듈에서는 세지 않습니다(검사 목록의 `invariants`).
- `seat`의 진행성('홀드는 판매나 만료로 끝난다')도 아직 검사하지 않습니다. 모델 기반 시험(wbs 2.5.5) 전에 범위를 줄인 모듈로 더합니다.
