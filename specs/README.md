# specs — 규칙 모델 검사 명세

핵심 업무 규칙을 실행할 수 있는 명세로 쓰고, 작은 범위에서 일어날 수 있는 모든 순서를 기계로 검사하는 곳입니다(docs/verification.md §2, ADR-0057, wbs 0.9). 명세 언어는 Quint입니다. Quint는 문법이 일반 프로그래밍 언어에 가깝고 TLA 논리를 씁니다. 전수 검사는 TLC(TLA+의 모델 검사기)가 합니다.

이 폴더의 명세는 정본이 아닙니다. 규칙의 정본은 docs/ 아래 설계 문서와 ADR입니다. 둘이 다르면 정본이 이기고, 명세를 고칩니다.

## 명세를 읽는 법

- **불변식**(언제나 참): 어떤 순서로 일이 벌어져도 깨지면 안 되는 약속입니다. 이름이 `inv_`로 시작합니다.
- **진행성**(결국 일어남): 멈추지 않으면 결국 끝나야 하는 일입니다. `temporal`로 적고, 공정성 가정(시스템이 할 수 있는 일은 결국 한다)을 앞에 단 속성(`fairLiveness`)을 TLC가 상태 그래프 전체에서 봅니다. 시뮬레이션은 시간 논리를 보지 않아 PR 검사에서는 건너뜁니다(wbs 0.9.3).
- **검사 모듈**: 같은 명세를 상수만 바꿔 여러 번 씁니다. `queue_proposed`처럼 지켜져야 하는 모듈과, 설계 장치 하나를 일부러 끈 변형(`queue_no_fencing` 등)이 있습니다. 변형은 반례가 나오는 작은 범위로 줄여 둘 수 있습니다(PR마다 도는 시뮬레이션이 그 반례를 찾아야 하기 때문입니다).
- **변형**: 장치를 끄면 그 장치가 막던 반례가 나와야 합니다. 반례가 안 나오면 검사가 아무것도 보지 않는 것이라 실패로 봅니다(V-T1).
- **작은 범위**: 사람·탭·서버·장애 횟수를 작게 두고 그 안의 모든 순서를 봅니다. 주장하는 범위는 '이 범위 안에서 위반 없음'까지입니다(docs/verification.md §2.3).

## 돌리는 법

Windows 개발 PC에는 Java가 없어 Linux 컨테이너로 돌립니다(Docker가 켜져 있어야 합니다).

```bash
node tools/spec-check/run-local.mjs typecheck     # 형식 검사
node tools/spec-check/run-local.mjs pr            # 형식 검사 + 검사마다 시뮬레이션 1만 회(PR마다 CI가 하는 것)
node tools/spec-check/run-local.mjs full --write  # TLC 전수 검사, 결과를 results/에 씀
node tools/spec-check/run-local.mjs traces --spec queue  # 모델 기반 시험의 재생 기록을 다시 만듦(명세를 고친 뒤)
# 진행성 검사(temporal)와 simulate false인 변형은 pr에서 건너뛰고 full에서만 돕니다
```

CI는 `.github/workflows/spec-check.yml`에서 같은 스크립트를 돌립니다. 도구 판과 해시 고정은 `tools/spec-check/README.md`에 있습니다.

명세에 동작을 더하거나 이름을 바꾸면 모델 기반 시험의 `SPEC_ACTIONS`와 명령을 함께 고치고 재생 기록을 다시 만듭니다. 형식 검사가 이름 목록과 기록의 명세 해시를 견줘, 따라가지 않으면 병합을 막습니다(docs/verification.md §2.4, V-T40).

## 지금 결과(2026-11-02)

- `queue`의 범위: 정본 범위(사람 2명 탭 2개씩, admission-ctrl 2대, 장애 전환 2회, 리더 교체 2회)는 TLC 전수 검사가 끝나지 않아(리더 교체를 빼고 대기표 4장만 두어도 상태 4,400만 개를 넘음) 전수 검사를 두 범위로 나눴습니다. 진입 범위(사람 2명, 한 사람은 탭 2개라 대기표 3장, admission-ctrl 1대, 장애 전환 2회)와 리더 범위(대기표 1장, admission-ctrl 2대, 리더 교체 2회, 회차 슬롯 장애 전환 2회)입니다. 정본 범위 전체는 시뮬레이션 1만 회로 봅니다(`queue_proposed_full`).
- 2026-11-02 정본에 적힌 그대로(`queue_canon`)는 같은 세대 안에서 번호가 겹치는 반례가 나왔습니다. 대기열 Redis 장애 전환으로 카운터가 되돌아간 뒤 RB-05가 세대를 올리기 전에 들어온 진입이, 잃은 번호와 같은 번호·세대를 받습니다(PROGRESS OPEN[13]). 2026-11-03 BUILD_ORDER PRF-080이 추천안('RB-05가 끝날 때까지 번호를 내지 않는다')을 정본과 코드에 넣어(ADR-0181), 이 모듈은 이제 지켜짐을 기대하고 `queue_proposed`와 같습니다(시뮬레이션만, 결과 파일은 PRF-085의 전수 검사가 다시 씁니다). 이 장치를 끈 변형(`queue_no_rb05_wait`)은 반례를 기대하며 전수 검사에서만 돕니다.
- 그 틈을 막아도(`queue_canon_batch_dup`) 2026-11-02까지는 1인 1순번이 깨지는 반례가 나왔습니다. 동시 도착 구간 묶음에 들어간 탭의 선점 값(PENDING, 수명 10초)이 결과 게시 전에 만료되면, 같은 사람의 다른 탭이 장애 전환 없이 번호를 하나 더 받았습니다. 2026-11-03 BUILD_ORDER PRF-060이 OPEN[14]의 추천안(묶음에 넣은 뒤 선점 값을 판매 종료까지 남는 묶음 기록으로 바꾸고 `q:adm`도 봄, 결과에 없는 참가의 묶음 기록 지우기)을 정본과 코드에 넣어, 이 모듈은 이제 지켜짐을 기대하고 `queue_proposed`와 같습니다(시뮬레이션만).
- 두 추천안('RB-05가 끝날 때까지 번호를 내지 않는다', '묶음에 넣은 뒤 선점 값을 묶음 기록으로 바꾼다')을 더한 모듈(`queue_proposed`)은 다섯 불변식을 모두 지킵니다. 소유자가 2026-11-02 두 안을 추천대로 정했고(OPEN[13]·[14]), OPEN[14]는 BUILD_ORDER PRF-060이, OPEN[13]은 PRF-080이 정본과 코드에 넣었습니다(2026-11-03).
- 수치(상태 수, 깊이, 지문 충돌 확률, 걸린 시간)는 `results/queue.json`과 docs/verification.md §2.6에 있습니다.
- 진행성('serving이 멈추지 않으면 앞사람부터 입장 자격을 얻는다')은 사람 2명·회차 슬롯 장애 전환 1회에서 TLC가 공정성 가정과 함께 봅니다(`queue_live`, 2026-11-04 wbs 2.3.4). 진입한 탭은 결국 대기표를 받거나 끝나고, 대기표를 든 탭은 결국 차례가 옵니다(장애 전환으로 잃은 번호도 RB-05가 건너뛴 구간을 지나 serving이 닿습니다). 닫힌 묶음의 참가자 목록에 없는 참가에 다시 진입하라고 알리는 장치를 뺀 변형은 진행성 반례가 나옵니다.
- 2026-11-04 명세를 구현에 맞췄습니다(ADR-0184): RB-05는 세대 키와 설정 세대로 알아채고 잃은 묶음 표시를 다시 닫으며, 입장 확정은 네 호출, 리더 전진은 다음 유효 번호까지·첫 전진 문까지, 묶음 게시는 리더가 표시의 복제를 확인한 뒤입니다. 처음에는 설정 세대가 오른 수만큼 건너뛰기를 곱했으나, 첫 장애 전환에서 설정 세대가 3 이상 오르면 곱하기 상한 3을 이미 다 써서 RB-05와 그 뒤 번호를 함께 잃은 뒤 같은 번호·세대가 다시 나가는 반례가 나왔습니다(docs/review/open-items.md 105번). 소유자 결정(2026-11-04, ADR-0186)으로 RB-05가 '확인 전' 표시를 쓰고 붙은 복제본이 받은 것을 확인한 뒤(`rb05Confirm`)에야 번호를 다시 내게 바꾸고 곱하기를 뺐습니다. 이제 복제되지 않은 쓰기를 둘까지 두는 범위(`queue_lag2`)와 설정 세대가 한 번에 1 또는 3 오르는 범위(`queue_lag2_jump`)가 지켜지고, 확인을 뺀 변형(`queue_lag2_no_confirm`)은 같은 번호·세대를 다시 내는 반례가 나옵니다. 리더는 회차마다 1초에 한 번 RB-05와 그 확인을 불러(ADR-0184·0186), 진행성 검사의 RB-05 공정성이 구현과 맞습니다.
- 2026-11-04 RB-05 복제 확인(ADR-0186)을 모델에 넣으며 일부러 줄인 것: 확인의 호출들(연결 표지·표시·`WAIT`·지우기)을 한 걸음 `rb05Confirm`으로 보고, 보호 조건을 '복제되지 않은 쓰기가 하나도 없음'으로 둡니다. 실제 `WAIT`는 표시를 쓴 연결의 쓰기까지의 복제만 보장해 이보다 약하지만, 확인 중에는 번호를 내는 쓰기가 막혀 있어 번호와 상관있는 결과는 같습니다. 복제본은 하나이고 그것이 승격된다고 둡니다. 호출 사이에 연결이 바뀌거나 장애 전환이 끼는 경우는 모델 밖이고, 연결 번호 확인과 '표시한 노드에서만 지우기'가 맡습니다(시험: queue-svc `redis-adapters.test.ts`·`rb05-replica.int.test.ts`, 클러스터 실측 `rb05-confirm`·`pin-routing`). 모델 기반 시험의 노드에는 복제본이 없어 `WAIT` 가지를 돌지 않고, 그 가지는 진짜 복제본 짝 시험이 맡습니다.
- 2026-11-09 진입 Degraded의 도착 시각 칸을 명세에 넣었습니다(BUILD_ORDER HOT-061, 소유자 결정 OPEN[26] (가), ADR-0223 결정 12). 모듈 `queue_arrival`은 칸 떼기·닫기와 장애 전환으로 칸 기록(쓴 번호 수)을 잃는 경우를 넣어도 일곱 불변식을 지키는지 봅니다. 새 불변식은 ⑥ 같은 세대 안에서 칸이 낸 번호가 겹치지 않음(`inv_noDuplicateArrivalNumber`)과 ⑦ 받은 번호가 빠진 번호가 되지 않음(`inv_receivedNumberNotRemoved`)입니다. ②(같은 세대 안 순번 중복 0)는 칸 번호도 그대로 셉니다. 장치를 하나씩 끈 변형은 반례를 냅니다: 세대 확인 없는 닫기(`queue_arrival_close_no_gen`)는 장애 전환으로 쓴 번호 수를 잃은 칸의 '쓰지 않은 번호'에 이미 나간 번호가 들어가 받은 번호가 빠진 번호가 되고(⑦), 세대 확인 없는 진입(`queue_arrival_entry_no_gen`)은 옛 칸에서 이미 나간 번호를 새 세대로 다시 내어, 기록된 반례에서는 뒤 사람이 그 번호를 돌려 앞 사람의 번호가 빠진 번호가 되며(⑦), 칸이 찼는지 보지 않는 변형(`queue_arrival_no_overflow`)은 칸을 넘어 준 번호가 다음 칸의 첫 번호와 겹칩니다(⑥). 명세가 시각을 담지 않아 '칸 끝 + 20초'와 칸 크기 규칙(직전 100칸, 빈 칸 건너뛰기), 한 Lua의 떼기 상한은 뺐고(명세 머리말), 그 몫은 Q-T16 통합 시험이 봅니다.
