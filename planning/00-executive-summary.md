# 경영진용 요약: PEAKET 한눈에

- **독자와 용도**: 시간이 짧은 의사결정자(경영진, 투자·채용 검토자)가 PEAKET이 무엇을 약속하고, 얼마나 걸리고 드는지, 무엇이 위험한지를 5분 안에 판단할 때 읽는다.
- **원본 출처**: planning/01-overview.md, wbs/wbs.md, docs/verification.md, review/consistency-review.md §9. 새 결정은 담지 않고, 숫자가 정본과 다르면 정본을 따른다.
- **기준 기획 버전**: v1.0. 2026-10-22 작성, 2026-10-26 갱신.

## 1. 한 문단 요약

PEAKET(피켓)은 공연 티켓 예매·관제 시스템이다. 100만 명이 한꺼번에 몰려도 서버가 멈추지 않게 하고, 같은 좌석이 두 사람에게 팔리는 오버셀을 0건으로 막고, 자동 예매 프로그램(봇)보다 사람에게 표가 가게 하는 것이 목표다. 한 사람이 AI 코딩 도구와 함께 리드 엔지니어의 역량을 보이려고 만드는 프로젝트이고(planning/01-overview.md §3.3), 기획(v1.0)과 설계를 마쳐 구현을 시작하기 전이다.

## 2. 왜 필요한가

- **몰리면 멈춘다**: 2022년 Eras Tour 예매 때 요청 35억 건이 몰려 상호작용의 약 15%가 실패했다(planning/01-overview.md §1.1).
- **봇과 암표는 법 문제다**: 2026-08-28 시행된 개정 공연법은 공정한 구입 과정을 우회해 되팔 목적으로 사는 부정구매와, 판매자 동의 없이 상습·영업으로 산 값보다 비싸게 파는 부정판매를 금지했다(§4의2①). 판매자와 통신판매중개업자(판매자와 구매자의 거래를 알선하는 사업자)에게는 방지 조치 의무를 두었고(§4의2②), 부정판매한 사람에게 판매금액의 50배 이하 과징금을 매길 수 있게 했다(§4의4①). 과징금을 받는 쪽은 부정판매한 사람이다(2026-10-28 원문 확인, 기술 검토 중간-103).
- **순번을 믿지 못한다**: 국내 주요 예매처 4곳은 순번 방식을 공개하지 않는다. PEAKET은 추첨 결과를 검증할 수 있게 공개한다(POL-005, ADR-0012).

## 3. 무엇을 약속하나

목표는 측정 전 가설이고 잰 결과를 그대로 기록한다(planning/01-overview.md §3.1). p99·p95는 요청 100건 가운데 99건·95건이 그 시간 안에 끝난다는 뜻이다. 약속마다 증명 방식이 다르므로 같은 무게로 읽지 않는다. '증명 방식' 칸의 말은 docs/verification.md §1.1·§1.3과 같다. 규칙 검사는 작은 범위의 모든 순서를 기계로 따져 보는 검사, 실측(PC)은 PC에서 잰 값, 외삽은 잰 범위의 결과를 식으로 늘린 값, 문서 인용은 제공사 문서에만 근거한 값이다(기술 검토 낮음-112).

| 약속 | 목표 | 증명 방식 |
| --- | --- | --- |
| 몰려도 멈추지 않는다 | 100만 명 대기, 진입 최고 초당 20만 건에서 p99 0.2초 이하, 오류율 0.1% 미만 | 외삽(1천~10만 명 실측(PC)을 설계 식으로 늘린다). CDN이 받는 몫은 문서 인용 |
| 좌석을 두 번 팔지 않는다 | 한 좌석에 1,000명이 몰려도 오버셀 0건 | 규칙 검사 + 실제 크기 실측(PC) |
| 돈 문제를 남기지 않는다 | 장애를 넣은 결제 1만 건에서 이중 결제 0건, 결제 뒤 60초 안에 발권도 발권 재시도도 시작하지 못한 결제 0건, 발권 서버가 5분 멈춰도 산 표는 환불 없이 발급 | 규칙 검사 + 가짜 결제사에 장애를 넣은 합성 시험의 실측(PC). 실제 결제사의 한도는 추정 |
| 봇보다 사람에게 | 정교함 1·2단계 봇 탐지 95% 이상, 오탐(사람을 봇으로 보는 비율)의 95% 신뢰상한 0.5% 이하 | 합성 봇과 판정용 사람 세션의 실측(PC). 운영의 봇 비율은 출시 뒤 하한으로만 안다 |
| 문제를 빨리 안다 | 일부러 넣은 장애마다 60초 안에 탐지, 운영 명령 반영 p99 3초 이하 | 로컬에서 대체 장애를 넣은 Game Day(일부러 장애를 내고 대응을 연습하는 날)의 실측(PC, 최댓값 기준) |
| 통신이 끊겨도 입장한다 | 오프라인 판정 p95 0.15초 이하, 두 기록이 모두 서버에 올라오면 중복 입장 100% 탐지 | 시뮬레이션과 기기 벤치의 실측. 실제 현장 망은 설계만 |

사업 목표(5만 석, 주문 2.5만 건 기준)는 매진 22분 이하, 입장 뒤 구매 전환 83% 이상, 봇 점유율 5% 이하, 예상 고객 문의 2,600건 이하다(planning/01-overview.md §3.2).

## 4. 어떻게 푸는가

- **접속 폭주**: 오픈 10분 전 로비(미리 들어와 기다리는 곳)를 열고 정각에 추첨해 순번을 정한다. 대기 상태는 콘텐츠 전송망(CDN)의 파일로 알리고, CDN 기본 한도(배포당 초당 25만 건)와 피크에 맞춰 배포를 셋으로 나누고 한도를 미리 올린다(ADR-0058).
- **좌석·결제**: 좌석을 잠시 잡아 두는 홀드 뒤 결제가 끝나야 판매를 확정한다. 결제사 하나가 멈추면 운영자 2인 승인으로 공연의 대체 결제사로 바꾼다. 바꾸기 전까지 새 결제는 멈춘다(ADR-0044). 들어온 뒤에도 먼저 누른 사람이 좌석을 잡는 경쟁은 남는다.
- **봇**: 휴대폰 본인확인으로 1인 1순번을 지키고(ADR-0006), 위험 점수가 높으면 추가 검증으로 보낸다. 남의 명의로 검증까지 통과한 계정은 가려내지 못한다.
- **운영·현장**: 관제 콘솔에서 들어오는 속도를 조절한다. 현장은 회전 QR로 통신 없이 판정하지만(ADR-0051), 오프라인 스캐너는 마지막 변경분 뒤의 양도·취소를 모른다.
- **돈의 흐름**: 통신판매중개자(판매 당사자는 파트너)로서 정산은 결제사 지급대행으로 한다(ADR-0045, ADR-0047). 토스페이먼츠 지급대행 이용료의 공개 안내(월 30만 원, 부가세 별도)는 확인했으나, 포트원 이용료와 PEAKET 몫을 받는 방식 같은 실제 계약 조건은 출시 전 계약 단계에서 확정한다(docs/features/settlement.md §14).

## 5. 하지 않는 것

스포츠 입장권, 되팔기 중개, 여러 리전(클라우드 데이터센터 지역) 동시 운영, 네이티브 앱, 외화 결제는 범위 밖이다(planning/01-overview.md §4.2). 운영 환경은 설계로만 두고 데모는 녹화 영상으로 한다(ADR-0057).

## 6. 일정·인력·비용

- **인력**: 1인 풀타임(주 40시간)과 AI 코딩 도구. 단계를 차례로 진행한다.
- **일정**: 작업 207개, 523일(104.6주)의 어림이다. 실제 개발 속도를 재기 전의 숫자이고, ±20%(83.7~125.5주)도 근거 있는 오차가 아니라 표시용 폭이다. 처음 끝내는 묶음을 마친 뒤 실제 속도로 다시 어림한다(wbs/wbs.md §1, 기술 검토 중간-001). 처음 계획 29~41주에서 추가 요청으로 353.5일이 늘었다(wbs/wbs.md §2. 2026-10-28 기술 검토 나머지 반영으로 69.75일, 2026-10-29 카프카·단일 장애점 분석 반영으로 4.5일). 마일스톤 어림은 M2a 증명 핵심 29.6주, M2 판매 핵심 경로 49.6주, M4 관제·관측 78.0주, M7 출시 준비 104.6주다(wbs/wbs.md §4).
- **비용**: 지출 상한은 총 5만 원이다(planning/01-overview.md §5.1). 100만 명 70분의 대기 조회 요청 요금만 약 273달러(HTTPS 1만 건당 0.012달러, 1,400원/달러 가정 시 약 38만 원)라 100만 명 실측은 하지 않는다. 처음 계산은 HTTP 단가로 약 205달러였고, 고친 뒤에도 결론은 같다(단가 정정 2026-10-28, 기술 검토 중간-102).

## 7. 어떻게 증명하나

처음 만들 법한 단순한 설계(v0)와 v1을 같은 부하로 재서 비교하고, v1 합격은 목표 절대값으로 판정한다. 1천~10만 명을 실측하고 100만 명은 외삽(잰 범위 밖을 식으로 늘려 추정)한다. 오버셀 0건 같은 규칙은 규칙 모델 검사(작은 범위의 모든 순서를 기계로 따져 보는 검사)로 본다. 숫자마다 실측·외삽·문서 인용을 붙인다(docs/verification.md §1.3). 100만 명이 동시에 돌 때만 생기는 일은 증명하지 못한다(docs/verification.md §8).

## 9. 지금 상태와 정할 일

기획(v1.0)과 아키텍처 의사결정(ADR 98건)을 마쳤고(review/consistency-review.md §9), 이제 코드 저장소와 자동 검사 체계(공용 CI)를 구축하는 첫 개발 단계(Phase 0)를 시작하기 직전이다. 본격 구현에 앞서 경영진(소유자)의 판단이 필요한 핵심 안건은 다음 4가지다. 안건마다 포트폴리오 일정에 영향이 있는지 붙였다(기술 검토 낮음-113). 1·4번은 00-summary.md §7 질문 44에서, 2·3번은 출시 전에 할 법률 검토와 결제사 계약에서 나왔다.

1. **문서 공개 범위**: 공개용 저장소에 서버 내부 배치도와 관리자 권한을 담은 '인수 문서'까지 모두 공개할지, 보안을 위해 비공개로 분리할지 결정(docs/devops.md §2.1). **포트폴리오 일정 영향 없음(운영 설계 결정)**: 띄운 시스템이 없어 배치도를 공개해도 위험은 낮다. 상시 데모를 띄우면 다시 본다. 저장소를 공개하기 전에만 정하면 된다.
2. **법률 검토**: 개정 공연법(암표 방지), 개인정보 보호법 관련 자체 해석에 대해 전문 변호사의 정식 법률 자문을 언제, 어느 범위까지 받을지 결정(POL-027의 확인 필요 27건, wbs 7.4.1). **포트폴리오 일정 영향 없음(출시 전 결정)**: 포트폴리오는 출시하지 않으므로 7.4.1은 검토할 목록과 문서 초안까지 만든다.
3. **결제사 계약 조건**: 파트너 정산 지급 기능을 구현하기 전(wbs 7.2.3), 토스·포트원과 정식 계약을 맺고 플랫폼 수수료 회수 방식과 최종 요율을 확정(ADR-0047, docs/features/settlement.md §14). **포트폴리오 일정 영향 있음**: 7.2.3 앞에서 정해야 한다. 계약을 맺지 못하면 결제사 테스트 환경과 [가정] 회수 방식으로 구현할지도 함께 정한다.
4. **장애 연습 범위**: 사전 모의 장애 훈련(Game Day)에 '클라우드 데이터센터 구역(AZ) 하나가 통째로 멈추는 극단적 재해' 시나리오까지 포함할지 결정(docs/infra-handover.md §9). **포트폴리오 일정 영향 없음(운영 설계 결정)**: 포트폴리오는 운영 환경을 띄우지 않고 Game Day를 로컬 대체 장애로 하므로, AZ 전체 장애 연습은 설계만이다(docs/verification.md §5.2).

*(부속 실무 과제였던 시연 방식은 2026-10-29에 실제 앱 녹화와 재현 스크립트로 정했고(클릭 시연은 만들지 않음, ADR-0153), 이벤트 데이터 스키마(Avro)의 필수 필드도 같은 날 정했으며(ADR-0150), 옛 결정 기록이 기각 근거로 약속한 확인 실험 4건은 2026-10-27에 넣지 않기로 했다(질문 48, ADR-0097). 2026-10-30에는 미룬 문서 가운데 100만 명 시나리오에 닿는 알림·봇 탐지와 예정 보안 문서 다섯을 썼다(ADR-0154~0160). 같은 날 남은 소유자 결정 거리와 지금 쓸 빈칸을 정했다(ADR-0161~0164: 로비 참가 퍼뜨리기, 재홀드 30초, 수사기관 자료의 commander 승인, 관리 계정 관리 API, 모든 API 작업의 허용 역할 검사). 채팅으로 기다리는 소유자 질문은 없고, 소유자가 정할 일과 때가 되면 정할 일은 review/open-items.md에 있다(2026-10-30 기준 소유자 결정 거리는 계약 때 정해지는 것뿐이다).)*
