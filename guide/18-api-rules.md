> [← 17편: 화면 만들기](17-frontend.md) | [목차로 돌아가기](README.md)

## 1. 상황: 새로 온 개발자가 '양도 수락' 버튼을 만든다

새로 합류한 개발자 민수 씨가 마이 티켓 화면에 [양도 받기] 버튼을 만든다. 버튼을 누르면 화면은 서버에 요청을 보내야 한다. 이때 화면과 서버가 주고받는 약속이 **API**(프로그램끼리 주고받는 주문서의 양식)이고, 요청마다 붙는 **주소**(`/v1/transfers/…`)와 **동사**(GET·POST 같은 HTTP 메서드)가 그 주문서의 겉봉이다.

예전 설계에서 민수 씨가 본 주소는 이랬다.

- 양도 수락(예전) `POST /v1/transfers/{offerId}/accept`
- 홀드 연장(예전) `POST /v1/holds/{holdId}/extend`
- 대기 취소(예전) `DELETE /v1/queue/{eventId}/entries`

하나씩 보면 이해는 된다. 그런데 주소에 '수락하다'·'연장하다' 같은 동사가 들어가 있어 POST(무언가를 만든다)와 뜻이 겹치고, `queue`는 단수인데 뒤에 회차 ID가 붙어 모음인지 하나인지 헷갈리며, 대기 취소는 '대기열 전체를 지우는' 주소처럼 읽힌다. 이런 주소가 작업 182개에 조금씩 섞여 있으면 새 사람은 규칙을 외우는 대신 매번 명세를 뒤져야 한다.

2026-10-21 소유자가 REST API 설계 기준을 보여 주며 "이 기준에 걸맞는지 보고 아니면 고쳐 달라"고 했다. 이 편은 그 점검으로 정한 주소·응답 규칙을 설명한다. 지금 주소는 이렇다.

- 양도 수락 `POST /v1/transfers/{offerId}/acceptance`(수락 기록을 하나 만든다)
- 홀드 연장 `POST /v1/holds/{holdId}/extension`(연장 기록을 하나 만든다)
- 대기 취소 `DELETE /v1/queues/{eventId}/entries/me`(대기열 가운데 '내 줄'을 지운다)

## 2. 왜 어려운가

| 어려움 | 왜 어려운가 | 그래서 |
| --- | --- | --- |
| **1. 만드는 사람이 많다** | 대기열·좌석·결제·파트너·관제·스캐너를 여러 사람이 나눠 만들면 주소를 짓는 습관이 사람마다 다르다 | 주소 짓는 규칙을 문서(guidelines §10)에 적고 도구가 검사한다 |
| **2. 동작이 '만들기·읽기·고치기·지우기'로 다 나뉘지 않는다** | 승인·거절·되돌리기·연장처럼 상태를 바꾸는 일이 많다 | 그 동작이 남기는 기록의 이름(명사)을 주소로 쓴다 |
| **3. 주소가 길어진다** | 회차 아래 스태프 아래 초대처럼 관계를 다 적으면 주소가 깊어지고, 위쪽 ID를 모두 알아야 부를 수 있다 | 깊이를 2단계로 묶는다 |
| **4. 목록이 크다** | 정산서·기기·티켓 목록을 한 번에 다 주면 서버와 휴대폰이 버겁다 | 목록은 나눠 준다(책갈피 방식) |
| **5. 오류의 모양이 제각각이면 화면이 문구를 못 고른다** | 서비스, 서버 앞 관문(게이트웨이), 전 세계에 흩어진 캐시 서버(CDN)가 각자 다른 모양으로 오류를 내면 화면이 어느 오류인지 모른다 | 어디서 나든 같은 모양의 '오류 쪽지'를 쓴다 |
| **6. 오류 쪽지에 내부 정보가 새면 공격의 실마리가 된다** | 스택(오류가 난 코드 줄 목록)에는 쓰는 기술과 파일 위치가 드러난다 | 응답에는 추적 번호만 주고 스택은 서버 기록에만 남긴다 |

## 3. 어떻게 푸는가

### 3.1 주소는 '무엇', 동사는 '어떻게'

주소는 서랍 이름이고 HTTP 메서드는 그 서랍에 하는 일이다. 서랍 이름에 하는 일을 적지 않는다.

| 메서드 | 하는 일 | 다시 보내도 괜찮나 |
| --- | --- | --- |
| GET | 꺼내 보기(읽기만 한다) | 괜찮다. 그래서 브라우저나 캐시가 미리 보내거나 다시 보낼 수 있고, 그러니 GET으로 무언가를 바꾸면 안 된다 |
| POST | 새로 넣기, 그 밖의 처리 | 두 번 보내면 두 번 일어날 수 있다. 결제처럼 중요하면 멱등키(`Idempotency-Key`)를 붙인다 |
| PUT | 통째로 바꿔 넣기 | 괜찮다(같은 내용으로 바꾸면 결과가 같다) |
| PATCH | 일부만 고치기 | 경우에 따라 다르다 |
| DELETE | 빼기 | 괜찮다(이미 없으면 그대로 없다) |

### 3.2 동작은 '기록의 이름'으로 쓴다

'승인하다'를 주소에 쓰는 대신 '승인 기록'이라는 서랍에 기록을 하나 넣는다. 주문을 취소하라는 편지를 '취소 우편함'에 넣는 것과 같다.

| 예전 | 지금 | 읽는 법 |
| --- | --- | --- |
| `…/commands/{commandId}/approve` | `…/commands/{commandId}/approvals` | 이 명령에 승인 기록을 하나 더한다 |
| `…/transfers/{offerId}/accept` | `…/transfers/{offerId}/acceptance` | 이 양도 요청의 수락을 만든다 |
| `…/holds/{holdId}/extend` | `…/holds/{holdId}/extension` | 이 홀드의 연장을 만든다 |
| `…/identity/token/refresh` | `…/identity/access-tokens` | 새 액세스 토큰을 만든다 |
| `…/partner/auth/login` | `…/partner/auth/sessions` | 로그인 세션을 만든다 |

여러 번 쌓일 수 있는 기록은 복수형(`approvals`), 한 번만 생기는 결과는 단수형(`acceptance`)이다. 운영 명령의 승인은 처음 승인과 되돌리기 승인처럼 여러 번 생길 수 있고, 양도 요청은 한 번 수락되면 끝이기 때문이다.

### 3.3 모음은 복수형, 하나뿐인 것은 단수형, '나'는 `me`

- 같은 종류의 모음은 복수형이다(`/tickets`, `/holds`, `/queues`). 그 뒤에 ID를 붙여 하나를 가리킨다(`/queues/{eventId}`).
- 부모마다 하나뿐인 것은 단수형이다(공연 회차의 좌석맵 `/seatmap`, 내 찜 `/wish`).
- 모음 바로 뒤 자리는 ID 자리라 고정 단어를 두지 않는다. 그래서 후기 사진 올리기는 `/reviews/images`가 아니라 `/review-images`다(`/reviews/{reviewId}`와 헷갈리지 않게).
- 로그인한 내 것은 `me`로 가리킨다. 다른 기기에서 대기를 취소할 때 대기표 번호를 몰라도 되게 하려는 것이다.

### 3.4 주소는 2단계까지

`모음/{ID}` 한 쌍이 1단계다. `/users/{userId}/orders/{orderId}`가 2단계이고, 그보다 깊게 가지 않는다.

- 깊어지면 하위 항목을 위로 올린다. 스태프 명단은 회차 아래에서 보지만(`/partner/events/{eventId}/staff`), 한 사람의 해제와 초대 재발송은 배정 ID만으로 부른다(`/partner/staff/{assignmentId}`). 서버는 그 배정이 이 파트너의 것인지 확인한다.
- 두 단어를 하이픈으로 이어 한 단계로 만든다(`/seatmap/snapshot` → `/seatmap-snapshot`).
- 주소는 소문자이고 단어는 하이픈으로 잇는다(`/order-items`). 끝에 `/`를 붙인 주소는 없는 주소로 본다(404). 주소가 둘이면 캐시도 둘로 갈리기 때문이다.

### 3.5 큰 목록은 책갈피로 나눈다

목록은 한 번에 `limit`개씩 준다. 다음 쪽은 서버가 준 책갈피(`nextCursor`)를 돌려주며 요청한다. '100번째부터 25개'처럼 위치로 나누는 방식(offset)은 뒤쪽으로 갈수록 앞의 것을 다 세고 건너뛰어야 해서 느리고, 그사이 새 항목이 끼면 같은 것이 두 번 나오거나 빠진다. 다만 화면이 '1 2 3 … 다음' 쪽 번호를 보여 주는 공연 검색과 내 문의 내역은 쪽 번호(`page`)를 쓴다. 어느 방식이든 한 번에 받을 개수의 이름은 `limit` 하나다.

### 3.6 검색, 필요한 칸만 받기, 다음 할 일 알려 주기

- **검색**은 GET과 주소 뒤 물음표 조건이다. 모든 공연을 찾는 전역 검색은 `/v1/search?q=`이고, 특정 목록 안의 검색은 그 목록에 조건을 붙인다. 조건 이름은 응답 칸 이름과 같게 하고, 쪽 나누기용 이름(`q`·`cursor`·`limit`·`page`·`sort`·`fields`)과 겹치지 않게 한다. 조건을 `q` 하나에 이어 붙이는 방식은 쓰지 않는다. 같은 검색도 순서만 달라 캐시가 갈리고, 칸마다 입력 검사를 할 수 없어서다.
- **필요한 칸만 받기**(`?fields=`)는 이름과 쓰는 법만 정해 두었다. 응답이 커서 실제로 느려진 목록에서만 켠다.
- **다음에 할 일 알려 주기**는 응답에 링크를 잔뜩 싣는 대신 표준 헤더와 응답 칸으로 한다. 새로 만든 것의 주소(`Location`), 다시 시도할 시각(`Retry-After`), 다음 쪽 책갈피(응답 본문의 `nextCursor`)다.

### 3.7 성공과 실패는 상태 코드가 말한다

| 코드 | 뜻 | 예 |
| --- | --- | --- |
| 200 | 됐다(본문 있음). 검색 결과가 0건이어도 200과 빈 목록 | 목록 조회, 상태 바꾸기의 결과 |
| 201 | 새로 만들었다. 다시 읽을 주소가 있으면 `Location`으로 알려 준다 | 양도 요청, 후기, 문의 |
| 202 | 받아 두었고 처리는 곧 한다 | 결제 접수, 예매 취소 접수 |
| 204 | 됐고 돌려줄 내용이 없다 | 대기 취소, 찜 해제 |
| 400 | 양식이 틀렸다 | 날짜 형식 오류 |
| 401 | 누구인지 모르겠다(로그인 필요) | 로그인 만료 |
| 403 | 누구인지는 알지만 안 된다 | 권한 없음, 재인증 필요 |
| 404 | 그런 것이 없다 | 없는 후기, 남의 문의(있는지조차 알리지 않으려고 404) |
| 409 | 지금 상태와 부딪친다 | 이미 수락된 양도 요청 |
| 410 | 다시 오지 않는 끝 | 판매 종료, 만료된 초대 |
| 422 | 양식은 맞지만 규칙에 어긋난다 | 1인 매수 한도 초과 |
| 429·503 | 잠시 뒤 다시 | 요청이 너무 많음, 일시 장애(`Retry-After`로 언제 다시 할지 알려 줌) |

실패를 200에 '실패'라고 적어 돌려주지 않는다. 화면·캐시·모니터링이 모두 상태 코드로 성공과 실패를 가르기 때문이다.

### 3.8 오류 쪽지는 한 모양이다

오류가 나면 국제 표준 모양(RFC 9457 Problem Details)의 쪽지를 준다. 쪽지에는 오류 종류의 이름(`type`, 예: `sale-ended`), 짧은 제목, 상태 코드, 이번 일의 설명, 추적 번호가 들어 있다. 화면은 오류 종류 이름을 보고 사람에게 보일 문구를 고른다.

- 서비스뿐 아니라 서버 앞 관문이 직접 거절할 때(요청이 너무 많음 등)와 CDN이 매진을 알릴 때도 같은 모양이다. 다만 CDN이 바로 내는 정적 파일(셔플 결과·묶음 결과·좌석맵 파일)의 404는 쪽지를 약속하지 않아, 화면은 상태 코드만 본다.
- 한 오류 종류는 언제나 같은 상태 코드와 같은 제목으로 낸다.
- 오류가 난 코드 줄 목록(스택)은 응답에 넣지 않는다. 개발자 컴퓨터와 자동 시험에서만 설정으로 켜고, 운영과 시연 환경에서 켜 두면 서버가 아예 시작하지 않게 한다.

### 3.9 규칙은 사람이 아니라 도구가 지킨다

문서 점검 도구(`tools/doc-check`)의 `api` 검사가 API 명세의 모든 주소를 규칙에 대 본다. 동사로 읽히는 단어, 모음 이름의 단수형, 3단계 이상, 대문자·밑줄, 끝 슬래시, ID 자리의 고정 단어가 있으면 오류로 멈춘다. 문서가 이름을 댄 주소가 명세에 없어도 오류다. 이번에 바꾸기 전의 명세에 이 검사를 돌리면 57개 주소에서 75건을 잡았고, 바꾼 뒤에는 0건이다.

## 4. 규칙

| 항목 | 규칙 |
| --- | --- |
| 주소 | 명사만. 동작은 그 기록의 이름(`approvals`, `acceptance`) |
| 이름 | 모음은 복수형, 하나뿐인 것은 단수형, 내 것은 `me`. 소문자와 하이픈 |
| 깊이 | 2단계까지. 깊으면 위로 올리거나 하이픈으로 잇는다 |
| 끝 슬래시 | 쓰지 않는다. 붙이면 없는 주소(404) |
| 목록 | 책갈피(`cursor`·`limit`·`nextCursor`). 쪽 번호는 검색·문의만. 개수 이름은 `limit` |
| 검색 | GET과 물음표 조건. 조건 이름은 응답 칸 이름과 같게 |
| 성공 | 만들면 201(다시 읽을 주소가 있으면 `Location`), 받아 두면 202, 내용이 없으면 204 |
| 실패 | 한 모양의 오류 쪽지. 상태 코드와 오류 종류는 짝이 고정. 스택은 응답에 없음 |
| 예외 | 기기 로그인 토큰 주소(`/v1/scanner/token`)는 국제 표준(OAuth)의 이름과 오류 모양을 따른다. 정적 파일(셔플 결과·묶음 결과·좌석맵 파일)의 404는 오류 쪽지 없이 상태 코드만 준다. 비밀번호처럼 주소에 넣으면 안 되는 값으로 찾는 조회는 POST로 받는다 |

## 5. 솔직한 한계

| 한계 | 그래서 |
| --- | --- |
| 기준은 쪽 번호·위치 방식을 예로 들지만 우리는 책갈피를 기본으로 해서, 원하는 쪽으로 바로 건너뛸 수 없다 | 쪽 번호가 꼭 필요한 화면(검색·문의)만 쪽 번호를 쓴다 |
| 기준이 권한 '조건을 `q` 하나에 이어 붙이기'와 'QA 환경에서 스택 켜기'는 따르지 않았다 | 이유를 결정 기록(ADR-0081)에 적고 소유자 검토 목록에 올렸다 |
| 로그인이 필요하다는 401 응답에 붙이는 인증 방식 이름(`Cookie`)은 국제 등록부에 없는 우리 이름이다(쿠키 로그인에는 등록된 이름이 없다) | 브라우저는 모르는 이름을 무시하므로 동작에는 영향이 없다. 등록된 이름이 생기면 바꾼다 |
| 단수형·복수형은 '한 번만 생기나'로 판단해서 애매한 곳이 남는다(입장 확정은 단수형이지만 차례가 올 때까지 여러 번 보낸다) | 애매하면 결정 기록에 적고 같은 판단을 따른다 |
| 각 요청의 프로그램 속 이름(`operationId`)과 오류 종류 전체 목록은 아직 없다 | 화면이 쓰는 API 계약을 보강하는 작업(wbs 0.2.3)에서 단다 |
| 설계 단계라 옛 주소를 남기지 않고 바로 바꿨다. 운영에 나간 뒤라면 이렇게 할 수 없다 | 운영 뒤에 호환을 깨는 주소 변경은 새 메이저 버전으로 내고, 파트너 공개 API는 폐기를 알린 날부터 최소 90일 옛 버전과 함께 운영한다(guidelines §1) |

---

## 6. 한 줄 요약

> **주소는 '무엇'만 명사로, 하는 일은 HTTP 메서드로 나타내고, 모음은 복수형·깊이는 2단계까지, 목록은 책갈피로 나누며, 성공과 실패는 상태 코드와 한 모양의 오류 쪽지로 알린다. 규칙은 문서 점검 도구가 지킨다.**
