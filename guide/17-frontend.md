## 1. 상황: 오픈 2분 전, 지하철에서 대기실을 연다

저녁 7시 58분, 지민 씨는 퇴근길 지하철에서 휴대폰으로 콘서트 대기실 주소를 연다. 신호는 약하고, 같은 순간 수십만 명이 같은 화면을 연다. 8시가 되자 '앞에 3만 2천 명'이 뜨고, 숫자가 줄어드는 동안 지민 씨는 메신저를 잠깐 본다.

차례가 오자 좌석 지도가 1초 안에 뜨고, 다른 사람이 막 고른 좌석이 회색으로 바뀌는 것이 보인다. 좌석을 고르고 결제 앱으로 넘어갔다가 돌아오니 결과 화면이 그대로 이어진다. 공연 날 공연장 입구는 인터넷이 잘 안 되지만 티켓 QR은 그대로 뜨고, 스태프의 휴대폰은 인터넷 없이 진짜 표인지 가린다.

이 편은 이 화면들, 곧 **프론트엔드**(사용자가 보는 화면과 그 화면 안에서 도는 프로그램)를 어떻게 설계했는지 설명한다. 서버 쪽 이야기는 2~6편에 있고, 이 편은 '휴대폰과 브라우저 안에서 무슨 일이 일어나나'에 집중한다.

## 2. 왜 어려운가

| 어려움 | 왜 어려운가 | 그래서 |
| --- | --- | --- |
| **1. 수십만 명이 같은 순간 같은 화면을 연다** | 화면을 사람마다 서버가 새로 만들면 서버가 먼저 넘어진다 | 화면마다 '서버가 매번 그리나, 미리 만든 파일을 나눠 주나'를 표로 정한다. 대기실은 미리 만든 파일을 전 세계 캐시 서버(CDN)가 나눠 준다 |
| **2. 휴대폰과 통신이 느리다** | 처음 내려받는 프로그램이 크면 화면이 늦게 뜨고, 그사이 사람들이 새로고침을 누른다 | 대기실 프로그램은 압축한 크기로 50KB 이하라는 상한을 두고, 넘으면 코드를 합치지 못하게 막는다 |
| **3. 좌석 상태가 1초에도 수없이 바뀐다** | 바뀔 때마다 화면 전체를 다시 그리면 휴대폰이 버벅이고 손가락 반응이 늦어진다 | 좌석 지도는 화면 뒤에서 따로 일하는 일꾼이 그리고, 바뀐 좌석만 덧칠한다 |
| **4. 결제는 다른 회사 화면을 다녀온다** | 결제 앱에 다녀오면 원래 화면이 기억하던 것이 사라진다 | 다녀와도 남는 브라우저 안 작은 데이터베이스에, 꺼낼 수 없는 형태로 서명 키를 둔다 |
| **5. 공연장은 인터넷이 끊긴다** | 서버에 묻지 않고 티켓을 보여 주고 진짜인지 가려야 한다 | 티켓 화면은 휴대폰에 저장해 두고, 스캐너는 미리 받은 키로 혼자 판정한다 |
| **6. 운영자 화면은 여러 팀이 따로 만든다** | 한 팀이 만든 부품 하나가 깨지면 운영자 화면 전체가 멈출 수 있다 | 부품과 화면 사이의 약속(계약)을 정하고, 깨진 부품의 칸만 대체 카드로 바꾼다 |
| **7. 화면은 공격의 입구다** | 남의 스크립트가 우리 화면에 끼어들면 표를 대신 사거나 정보를 빼 갈 수 있다 | 화면 묶음마다 '어디서 받은 프로그램만 돌려도 되나'를 적은 허용 목록을 따로 둔다 |

## 3. 어떻게 푸는가

### 3.1 설계 순서: RADIO

화면 설계는 빠뜨리기 쉬운 것이 많아서, 다섯 단계로 나눠 차례로 보는 틀(RADIO)을 썼다. 프론트엔드 면접 준비 사이트 GreatFrontEnd가 정리한 틀이다.

| 단계 | 묻는 것 | 피켓에서는 |
| --- | --- | --- |
| **R** 요구사항 | 무엇을 해야 하나, 어떤 기기에서, 얼마나 빨라야 하나 | 앱 다섯 개의 핵심 기능, 숫자 목표, 기기마다 안 되는 기능과 그때의 대체 동작 |
| **A** 구조 | 앱과 부품을 어떻게 나누나, 화면을 어디서 그리나 | 저장소와 공용 부품, 주소마다 '누가 그리고 얼마나 캐시하나' 표 |
| **D** 데이터 | 화면이 무엇을 기억하나, 어디에 두나 | 대기실·좌석·결제 흐름의 상태표, 브라우저 저장소 규칙 |
| **I** 약속 | 서버·부품과 무엇을 어떤 모양으로 주고받나 | 서버 호출 공통 규칙, 실시간 채널 형식, 운영자 화면 부품 계약 |
| **O** 깊이 파기 | 빠르고 안전하고 누구나 쓸 수 있게 | 성능 예산, 접근성, 보안 머리말, 지표 수집, 시험 |

원문은 시간을 대략 R 10%, A 20%, D 10%, I 20%, O 40%로 나누라고 권하고, 순서는 꼭 지키지 않아도 된다고 한다. 피켓의 정본 문서(docs/frontend.md)가 이 순서로 쓰였다.

### 3.2 앱 다섯 개와 공용 부품

- **소비자 웹**: 공연 보기, 대기, 좌석 고르기, 결제, 티켓 지갑(월렛). 화면은 Next.js(서버와 브라우저가 화면을 나눠 그리는 도구)와 React(화면 부품 라이브러리)로 만든다.
- **대기실 경량 페이지**: 소비자 웹 안에 있지만 따로 만드는 가벼운 페이지다(3.3).
- **파트너 콘솔**: 기획사가 공연을 등록하고 좌석 지도를 그리고 판매 승인을 요청하는 화면.
- **관제 콘솔**: 운영자가 온세일을 지켜보고 명령을 내리는 화면. 여러 팀이 만든 부품을 끼워 쓴다(3.8).
- **스캐너**: 현장 스태프 휴대폰에서 도는 검표 앱.
- **공용 부품 여섯**: 디자인 부품, 지표 보내기, 입력 검사, 서버 호출, 관제 부품 계약, 좌석 지도 그리기(포렌식 리플레이와 같이 씀). 앱들이 같은 부품을 써서 규칙이 앱마다 달라지지 않게 한다.

### 3.3 대기실은 화면 라이브러리 없이 가볍게

대기실은 프로그램 크기 상한이 압축한 크기로 50KB(디자인 꾸밈 파일은 10KB 미만)다. 그런데 직접 재 보니 React로 버튼 하나짜리 최소 화면만 만들어도 압축한 크기가 66.0KiB였다. 라이브러리만으로 상한을 넘는 것이다. 같은 일을 라이브러리 없이 만든 모형은 2.73KiB였다(둘 다 PC에서 잰 값).

대기실 화면에 있는 것은 앞 인원, 진행 막대, 예상 시간, 대기 취소 버튼과 가끔 뜨는 안내뿐이다. 그래서 대기실은 React 없이, 상태마다 무엇을 보일지 적은 표와 그 표대로 화면 글자를 바꾸는 작은 프로그램으로 만든다. 목표는 15KB다(잠정값: 아직 재 보지 않고 정해 둔 값이라 측정해서 바꾼다. 이 편에서 '잠정값'은 모두 이 뜻이다).

이 페이지는 서버가 그리지 않는다. 미리 만든 파일을 저장소에 올려 두고, 대기실 주소(`/queue/…`)로 들어오면 캐시 서버가 그 파일을 돌려준다. 화면을 만드는 일에 앱 서버를 쓰지 않는 것이다.

검색 결과 화면(`/search`)도 같은 생각으로 만든다. 미리 만든 빈 틀을 캐시하고, 결과는 브라우저가 검색 API를 불러 그린다. 오픈 직전에 검색이 몰려도 화면 서버로 가지 않는다. 검색 결과 화면은 검색 엔진에 올리지 않고(noindex), 검색 엔진에는 공연 상세만 알린다. 검색창은 한글을 조합하는 동안(예: '루'에서 '룸'으로 바뀌는 중) 누른 Enter와 화살표를 처리하지 않는다. 조합이 끝나기 전에 후보가 골라지거나 검색이 나가지 않게 하려는 것이다. 후보 요청은 입력이 0.3초(잠정값) 멈춘 뒤 보내고, 입력이 바뀌면 앞 요청을 취소한다(2026-10-27, [ADR-0094](../docs/adr/0094-search-redesign-autocomplete-read-model-search-port.md)).

### 3.4 기다리는 동안 화면이 하는 일

- **얼마나 자주 묻나**: 남은 예상 시간에 따라 0.5초, 5초, 20초마다 '지금 몇 번까지 들어갔나' 파일을 다시 읽는다(2편의 적응형 폴링). 이때 브라우저 자신의 캐시는 건너뛰고 늘 CDN에 묻는다. 브라우저 캐시가 옛 파일을 1초 가까이 더 내줄 수 있어서다.
- **차례를 얼마나 빨리 봤나 재기**: 대기 상태 파일에는 '몇 시 몇 분 몇 초 몇 밀리초에 몇 번까지 불렀다'는 기록이 실려 있다. 화면은 내 차례를 그린 시각과 그 기록을 견줘, 차례를 보기까지 걸린 시간을 잰다. 휴대폰 시계는 CDN이 캐시한 응답의 시각이 아니라, 대기열 서버가 응답 본문에 밀리초로 적어 준 시각으로 맞춘다. 캐시한 응답의 시각은 원본이 만든 때 그대로라 몇 초씩 늦기 때문이다([ADR-0110](../docs/adr/0110-latency-budgets-nfr002-nfr004-aligned-expiry-100ms-batches-ms-clock.md)).
- **실패하면**: 다시 묻기 전 기다리는 시간을 두 배씩 늘리고(최대 60초, 잠정값), 그 시간을 ±20% 흔들어 모두가 같은 순간에 다시 묻지 않게 한다.
- **다른 앱을 보는 동안**: 화면이 숨겨지면 최소 5초(잠정값) 간격으로만 묻는다.
- **서버가 '천천히'라고 하면**: 서버가 대기 상태 파일 안에 적어 준 '이만큼 뒤에 다시 물어 주세요'(`pollHintMs`)나, 잠시 거절하며 보낸 '다시 물을 시간'(`Retry-After`)보다 빨리 묻지 않는다. 서버가 버거울 때 모두의 주기를 한꺼번에 늘리는 손잡이다. 힌트를 파일 안에 적는 까닭은, 비상 때 파일을 대신 내주는 저장소(S3)가 그런 머리글을 붙일 수 없어서다. 그 시각에 모두 함께 다시 오지 않도록, 그보다 0~20%만 늦게 흩어서 묻는다(기술 검토 중간-032·038).
- **탭을 여러 개 열어도**: 같은 회차를 연 탭이 여럿이면 한 탭만 묻고 나머지 탭은 그 결과를 나눠 받는다. 탭을 많이 연다고 빨라지지 않고 서버 부담만 늘기 때문이다. 묻는 탭은 지금 보고 있는 탭이 맡는다. 숨긴 탭이 맡으면 브라우저가 그 탭을 1분에 한 번만 깨워, 보고 있는 탭까지 늦어지기 때문이다. 차례가 오면 입장도 보고 있는 탭이 한다(기술 검토 중간-037).
- **휴대폰 시계가 틀려도**: 대기열 서버가 응답 본문에 밀리초로 적어 준 시각과 오가는 데 걸린 시간으로 내 시계가 얼마나 틀렸는지 잰다. CDN이 캐시한 응답의 시각은 원본이 만든 때 그대로라 쓰지 않는다. 대기실 밖 화면은 캐시하지 않은 응답 머리의 시각(초 단위)을 써서 ±1초 안팎은 틀릴 수 있다([ADR-0110](../docs/adr/0110-latency-budgets-nfr002-nfr004-aligned-expiry-100ms-batches-ms-clock.md)).
- **차례 직전**: 차례 1분(잠정값) 전에 로그인 표를 미리 새로 받고, 좌석 지도 파일을 조용히 미리 받아 둔다. 그래서 차례가 오면 바로 좌석 화면이 뜬다.

### 3.5 좌석 지도: 1초 안에, 버벅이지 않게

브라우저에는 화면을 그리고 손가락 입력을 받는 주 일꾼이 하나 있다. 이 일꾼이 5만 석을 계산하느라 바쁘면 손가락을 눌러도 반응이 늦다. 그래서 좌석 계산과 그리기는 **화면 뒤 일꾼**(Web Worker: 화면과 따로 도는 계산 담당)에게 맡기고, 주 일꾼은 입력만 받는다.

| 순서 | 하는 일 | 예산(잠정값) |
| --- | --- | --- |
| 1 | 대기 중 미리 받아 둔 좌석 지도 파일을 쓴다 | 0초(대기 중에 끝남) |
| 2 | 좌석 화면을 띄운다 | 0.3초 |
| 3 | 화면 뒤 일꾼을 깨우고 좌석 지도를 푼다 | 0.25초 |
| 4 | 지금 좌석 상태를 받는다 | 0.25초 |
| 5 | 무대와 구역을 처음 그린다 | 0.1초 |
| 합 | 대기실 통과부터 첫 그림까지 | 0.9초(목표 1초 미만) |

- **실시간 변화**: 서버는 바뀐 것이 있을 때 0.1초마다 '바뀐 좌석만' 묶어서 보낸다(묶음 하나가 약 200바이트. 2026-10-28에 0.25초에서 줄였다, [ADR-0110](../docs/adr/0110-latency-budgets-nfr002-nfr004-aligned-expiry-100ms-batches-ms-clock.md)). 확대해서 좌석이 보이는 구역만 받고, 멀리서 보는 전체 배치도는 구역 색만 가끔 새로 받는다.
- **연결이 끊기면**: 0.5초에서 10초까지 기다림을 늘려 가며 다시 연결하고, 그사이 놓친 변화는 구역 상태를 통째로 다시 받아 메운다.
- **누구나 고를 수 있게**: 좌석은 고를 수 있는 배율에서 손가락으로 누를 만한 크기(24×24 화면 점 이상)로 그린다. 화면을 볼 수 없는 사람을 위해 지금 구역의 좌석을 글 목록으로도 만들어 화면 읽기 프로그램이 읽게 한다.

### 3.6 결제: 다른 회사 화면을 다녀와도 이어지게

좌석 홀드부터 결제까지의 요청에는 '구매 세션 서명'이 붙는다. 서버가 '이 요청은 차례를 받은 그 브라우저가, 순서대로 보낸 것'인지 확인하는 장치다(4·5편).

- **키를 어디에 두나**: 결제 앱에 다녀오면 원래 화면의 기억은 사라진다. 그래서 서명 키를 브라우저 안 작은 데이터베이스(IndexedDB)에 둔다. 다만 **꺼낼 수 없는 키**로 둔다. 화면 프로그램도 키 값을 꺼내 읽지 못하고 '이 내용에 서명해 줘'만 시킬 수 있어, 스크립트가 키 값을 복사해 다른 곳으로 보내지는 못한다. 대신 그 화면 안에서 서명을 시키는 일은 막지 못한다(5장).
- **순서 지키기**: 같은 화면을 탭 두 개로 열어도 요청 번호가 뒤바뀌지 않게, 서명하는 동안 브라우저의 잠금을 잡고 한 번에 하나씩 보낸다.
- **결과 받는 방법을 하나로**: 두 결제사(토스페이먼츠·포트원) 모두 결제가 끝나면 우리 결과 주소로 '페이지를 옮겨' 알려 주게 맞췄다. 결제 팝업 창이 보내는 메시지에는 기대지 않는다.
- **주소에 실린 결제 값**: 결제사가 돌아오는 주소에 실어 보낸 값은 읽자마자 주소창에서 지우고 어디에도 저장하지 않는다.
- **두 번 결제되지 않게**: 결제 접수에는 '같은 요청이면 같은 번호'(멱등키)를 붙인다. 새로고침해서 다시 보내도 서버는 한 번으로 처리한다.

### 3.7 티켓과 스캐너: 인터넷이 끊겨도

- **티켓 화면만 맡는 대리인**: 티켓 화면에는 서비스 워커(브라우저 안 대리인: 인터넷이 없어도 저장해 둔 화면을 띄워 준다)를 둔다. 맡는 범위를 티켓 화면 주소로만 좁혀서 대기실·좌석·결제 화면은 가로채지 않는다(서비스 워커는 자기 범위 밖 주소를 맡지 못한다). 대리인이 저장하는 것은 화면 틀뿐이고 티켓 값은 IndexedDB에 따로 둔다.
- **15초마다 바뀌는 QR**: 휴대폰 안의 꺼낼 수 없는 기기 키로 15초마다 새로 서명해 QR을 그린다(6편).
- **아이폰의 7일 규칙**: 아이폰 Safari는 사이트를 7일 동안 쓰지 않으면 그 사이트의 저장소를 지울 수 있다. 그래서 홈 화면 앱으로 등록하라고 권하고, 저장소를 지우지 말아 달라고 브라우저에 요청하고, 공연 전날과 당일에 '티켓 화면을 한 번 열어 주세요'라고 알린다. 열면 7일 계산이 다시 시작되기 때문이다. 그래도 키가 사라졌으면 입장 시작 전에는 다시 등록하게 하고(티켓마다 하루 한 번), 입장이 시작된 뒤에는 현장 부스로 안내한다.
- **스캐너의 0.15초**: 스캐너는 판정 하나를 약 0.106초(잠정값) 안에 끝내도록 단계마다 시간을 나눴다(목표는 95%가 0.15초 안). 카메라 그림을 받고, QR을 읽고, 내용을 풀고, 휴대폰 안 목록을 찾아보고, 서명을 확인한 뒤 결과를 보인다. 판정 중에 오류가 나면 통과가 아니라 '다시 찍어 주세요'다. 기록은 먼저 휴대폰에 쓰고 인터넷이 될 때 올린다.

### 3.8 파트너와 관제 화면

- **좌석 지도 에디터**: 기획사가 5만 석짜리 지도를 그리는 화면이다. 자동 채우기, 겹침 검사, 내보내기 같은 무거운 계산은 화면 뒤 일꾼이 한다. 가져온 파일(SVG·JSON·CSV)은 서버가 해석하고, 에디터는 서버가 돌려준 도형·좌표만 그린다. 끌어서 옮기는 일은 모두 숫자 입력과 키보드로도 할 수 있다. 되돌리기는 200단계(잠정값)까지다. 도형을 고르면 나오는 손잡이, 돌리기, 끌기는 흔한 편집기의 일이라 직접 만들지 않고 무료 공개 라이브러리 Konva(MIT)에 맡긴다. 좌석 5만 개는 하나하나 따로 만들지 않고 구역마다 한 번에 그린다. 손잡이가 실제로 부드럽게 움직이는지는 FE-T33 시험으로 재고, 못 맞추면 좌석 그리기를 라이브러리 밖으로 뺀다(2026-10-28, 기술 검토 중간-016).
- **여러 팀이 만든 부품을 끼우는 관제 화면**: 관제 화면은 대기열 팀, 구매 팀이 따로 만들어 따로 내보낸 부품(원격 위젯)을 실행 중에 불러와 끼운다. 그래서 부품과 화면 사이의 약속을 정했다.
  - 부품이 알려야 하는 것(이름·필요한 권한·약속의 판 번호)과 화면이 부품에 주는 것(숫자 받기, 경보·명령 확인 받기, 공용 상태 읽기)을 정한다. 부품은 자기 마음대로 서버에 연결하지 않는다.
  - 부품은 공용 상태(고른 회차, 입장 제어 상태, 자동 조치, 경보, 접속자)를 읽기만 한다. 공용 상태를 바꾸거나 명령을 보내는 통로는 없고, 로그인 세션과 명령 목록은 아예 받지 못한다. 바꿀 일이 있으면 화면에 '이걸 열어 달라'고만 알리고, 명령은 화면 쪽 명령 화면(SCR-030)에서만 만든다. 부품의 결함이 세션이나 자동 제어 상태를 건드리지 못하게 하려는 안전 경계다. 부품마다 자기 상태는 자기 안의 작은 저장소에 두고, 자리가 없어지면 버린다. 상태 도구는 네 앱 모두 Zustand 하나다(2026-10-27, [ADR-0092](../docs/adr/0092-single-client-state-library-zustand.md)).
  - 화면은 부품 파일의 지문(내용이 바뀌면 달라지는 값)을 확인하고, 약속의 큰 판 번호가 다르면 싣지 않는다. 부품 하나가 실패하면 그 칸만 '불러오지 못했습니다' 카드로 바꾸고 나머지는 계속 그린다.
  - 온세일 동안(오픈 10분 전부터 60분 뒤까지)에는 규모와 상관없이 부품을 바꾸지 않는다(잠정 규칙).
  - 이렇게 따로 끼우는 방식(Module Federation)은 '여러 팀이 따로 내보내는 구조'를 보이려는 쇼케이스다. 같은 부품을 한 앱에 함께 묶은 판도 만들어 첫 화면 속도와 실패 처리를 견주고, 따로 끼우는 쪽이 나쁘면 한 앱으로 바꾸는 조건을 정해 두었다(2026-10-28 추천 적용, ADR-0100).
- **명령은 보통 요청으로**: 운영 명령을 만들고 승인하는 일은 일반 요청으로 하고, 실시간 연결은 '명령이 전달됐다'는 확인과 경보 알림만 맡는다. 실시간 연결이 끊겨도 명령 기록이 꼬이지 않게 하려는 것이다.
  - 실시간 연결은 서버가 한 방향으로 계속 보내 주는 흐름(SSE) 둘이다. 하나는 화면을 여는 동안 늘 열어 두는 흐름(명령 확인·승인 대기·경보·접속자)이고, 하나는 지금 보이는 위젯의 숫자 흐름이다. 끊겼다 다시 붙으면 브라우저가 마지막으로 받은 번호를 알려, 그 뒤의 일만 다시 받는다(2026-10-28 추천 적용, ADR-0100).
  - 파트너 콘솔은 화면이 서버 기능을 바로 부르는 요청 도구로 업무 서버를 직접 부르고, 앱 서버는 로그인과 몇 화면의 묶어 읽기만 한다(2026-10-28 추천 적용, ADR-0100).
- **하루 종일 켜 두는 콘솔의 부담**: 콘솔은 처음 열 때보다 켜 둔 동안이 더 문제다. 숫자가 계속 바뀌어 화면을 다시 그리고, 쌓인 데이터가 메모리를 차지하기 때문이다. 다만 관제 화면은 1초에 3만 건씩 생기는 사건을 하나하나 받지 않고, 서버가 1초 단위로 합친 숫자만 받는다. 그래서 아래 네 가지를 정했다(2026-10-27).
  - **화면마다 필요한 코드만 받는다**: 관제 화면 16개를 처음에 한꺼번에 받지 않고, 들어가는 화면의 코드만 받는다. 비상 때 쓰는 명령 화면은 미리 받아 둔다. 파트너 콘솔의 좌석 지도 에디터, 판매 규칙 시험기, 그래프도 쓸 때 받는다.
  - **안 보이는 위젯은 쉰다**: 고르지 않은 탭의 위젯은 10초(잠정값) 뒤에, 브라우저 탭을 30초(잠정값) 넘게 숨기면 모든 위젯이 숫자 받기를 멈춘다. 경보와 명령 확인은 계속 받고, 숨긴 동안에는 탭 제목에 경보와 승인 대기 수를 띄운다. 다시 보면 1초 안팎에 새 숫자로 바뀐다. 접어 둔 위젯은 제목과 핵심 숫자 한 줄만 그린다.
  - **그래프는 그림 한 장에 그린다**: 점마다 화면 요소를 만들지 않고 한 장의 그림(Canvas)에 그려, 점이 많아도 무거워지지 않는다. 그래프 선 하나는 최근 15분(잠정값)만 들고 있고, 더 긴 기간은 Grafana에서 본다.
  - **몇 시간 켜 두는 시험을 한다**: 가짜 데이터를 4시간(잠정값) 흘리며 메모리가 계속 늘지 않는지, 조작 반응이 느려지지 않는지 잰다.

### 3.9 브라우저에 무엇을 남기나

브라우저 저장소에는 정본의 저장소 규칙 표([docs/frontend.md §3.12](../docs/frontend.md))에 적은 것만 남긴다. 그 표에 없는 값은 저장하지 않는다. 특히 이름, 전화번호, 이메일, 주소, 카드 값, 결제사가 준 값, 비밀번호는 브라우저에 남기지 않는다. 아래 표는 그 가운데 주요 항목이다(전체 목록은 정본 표).

| 무엇(주요 항목) | 어디에 | 언제 지우나 |
| --- | --- | --- |
| 이 브라우저 표시값(무작위 번호) | 그 브라우저 | 사용자가 사이트 데이터를 지울 때(대기표가 기기와 묶여 있어 로그아웃에는 남김) |
| 대기 정보(참가 표, 대기표, 받은 순번) | 그 브라우저 | 로그아웃, 대기 취소, 대기표 만료, 판매 종료 |
| 구매 세션 자격(입장 표, 서명 키) | 그 탭과 IndexedDB(꺼낼 수 없는 키) | 구매 세션이 끝날 때, 로그아웃, 만료 |
| 자동 배정 희망 조건(등급, 매수, 휠체어석, 떨어진 좌석 허용) | 그 브라우저 | 로그아웃, 배정 확정, 판매 종료 |
| 최근 검색어(최대 10개, 잠정값) | 그 브라우저 | 사용자가 하나씩 또는 전체를 지울 때. 로그인하지 않아도 쓰는 값이라 로그아웃에는 남김 |
| 오프라인 티켓 | IndexedDB | 공연 끝 + 7일(잠정값) |

**로그아웃하면**: 서버는 그 앱이 준 로그인 쿠키만 지운다. 같은 브라우저의 다른 앱(파트너 콘솔, 관제 콘솔) 로그인까지 끊지 않으려고 '이 사이트의 쿠키를 모두 지우라'는 머리말은 쓰지 않는다. 소비자 웹은 '이 사이트의 캐시를 지우라'는 머리말만 보낸다(2026-10-28, 기술 검토 중간-067). 화면 쪽 정리 프로그램은 서버 응답을 기다리지 않고 정본 표에서 '로그아웃'에 지우게 된 저장물을 지우며 열린 다른 탭에도 알린다. 기기 식별값과 최근 검색어는 남긴다. 티켓의 입장 키도 기본으로 남긴다. 지우면 다시 등록해야 하는데, 다시 등록은 티켓마다 하루 한 번이고 입장이 시작되면 현장 부스로 가야 하기 때문이다. 로그아웃 창에서 '이 기기의 입장 키도 지우기'를 고르면 그때는 지운다.

### 3.10 화면을 지키는 규칙

- **화면 묶음마다 허용 목록**: 브라우저에 '이 화면은 이런 곳에서 받은 프로그램만 돌려라'를 알려 주는 허용 목록(CSP)을 화면 묶음마다 따로 둔다. 미리 만든 화면은 파일 지문으로, 대기실은 우리 사이트 파일만, 매번 그리는 화면은 그때그때 바뀌는 일회용 번호로 확인한다. 결제 화면은 결제사 주소를, 좌석 화면은 실시간 연결 주소를, 스캐너는 QR 읽기 부품(WebAssembly)을 더 허용한다. 꾸밈(스타일) 파일과 꾸밈 묶음은 우리 사이트 것과 일회용 번호가 붙은 것만 받는다. 다만 디자인 부품이 요소마다 붙이는 꾸밈 값(여백·색·글자 크기)은 서버가 미리 그린 화면에서도 빠지지 않게 받는다. 일회용 번호는 이런 요소별 값에 붙일 수 없기 때문이다. 프로그램을 돌리는 규칙은 그대로이고, 이 방식이 세 브라우저 엔진에서 되는지는 작은 시험으로 먼저 확인한다(ADR-0111).
- **지표는 한 입구로**: 모든 앱이 화면 지표와 오류를 같은 사이트 안의 한 주소(`/_t/…`)로 보내고, 그 길을 서버 입구 하나로 모은다. 외부 도구 주소를 허용 목록에 넣지 않아도 된다.
- **위험한 부품 목록**: 안정판이 없거나 오래 갱신되지 않은 라이브러리(예: 아직 베타인 로그인 라이브러리)를 따로 표로 두고, 언제 바꿀지와 대안을 적는다.
- **코드 지도는 숨긴다**: 압축 전 코드를 되짚는 지도(소스 맵)는 오류 분석 도구에만 올리고 누구나 받는 저장소에는 올리지 않는다.

### 3.11 빠른지 어떻게 아나

- **크기 예산**: 주소 묶음마다 처음 내려받는 프로그램 크기의 상한을 정했다(예: 대기실 50KB, 공연 상세 170KB, 좌석 화면 200KB. 대기실 밖의 숫자는 측정 캠페인에서 바꿀 잠정값이다). 넘으면 코드를 합치지 못하게 막는다.
- **실제 사용자 숫자가 기준**: 개발자 컴퓨터의 시험 숫자는 나빠지는 것을 막는 장치일 뿐이다. 목표를 지켰는지는 실제 사용자 휴대폰에서 잰 숫자로 판정한다. 사용자 네 명 가운데 세 명이 그보다 빠른 숫자(p75)를 휴대폰과 컴퓨터로 따로 본다.
- **화면 시험 42가지**: 대기실 크기, 좌석 지도 1초, 서명 계산을 서버와 같은 정답표로 맞춰 보기, 인터넷을 끊고 QR 띄우기, 관제 부품이 실패할 때 대체 카드, 안 보이는 위젯이 쉬는지, 콘솔을 몇 시간 켜 두기, 한 앱에서 로그아웃해도 다른 앱 로그인은 남는지, 화면 그림이 전과 달라졌는지 같은 것을 자동 시험으로 둔다(FE-T1~FE-T42).

### 3.12 지난 온세일을 다시 보는 화면: 포렌식 리플레이

오픈 직후 몇 분 동안 무슨 일이 있었는지를 좌석 지도 위에서 다시 보는 화면도 설계했다. 타임라인을 끌면 그 순간의 좌석 상태(빈 좌석, 홀드, 결제 중, 판매)로 지도가 바뀌고, 어느 구역에 경합이 몰렸는지, 어떤 세션이 사람답지 않게 빨랐는지를 함께 본다.

- **두 단계로 나눴다**: 먼저 '가상의 온세일'(합성 시나리오)을 만들어 보여 주는 데모를 만든다. 서버도 개인정보도 없어서 누구나 브라우저에서 눌러 볼 수 있다. 실제 온세일 기록을 쓰는 운영 연결은 출시 뒤에 법률 검토를 거쳐 고를 수 있게만 열어 두었다.
- **같은 부품을 다시 쓴다**: 좌석 지도는 예매 화면과 같은 부품(화면 뒤 일꾼이 바뀐 좌석만 덧칠)을 공용 꾸러미로 옮겨 같이 쓴다.
- **무거운 도구를 쓰지 않는다**: 브라우저 안에서 도는 분석용 데이터베이스(압축해도 7MB가 넘는다)나 아직 모든 브라우저가 지원하지 않는 최신 그래픽 기능 대신, 열 단위 숫자 배열과 '조건에 맞음·안 맞음'을 적은 비트로 거른다.
- **봇은 '후보'까지만**: 산점도에서 빠르고 마우스 움직임이 단조로운 세션을 고르면 그 세션들이 잡은 좌석이 지도에 표시된다. 하지만 이것은 후보 찾기다. 봇 판정은 정해진 규칙과 사람의 표본 검토로만 한다. 가상 데이터에는 정답이 있어 '고른 것 가운데 실제 봇 비율'을 함께 보여 준다.
- **운영 연결의 울타리**: 실제 기록은 이름을 가린 기록(가명정보)이라도 많이 모으면 사람을 알아볼 수 있다. 그래서 지정된 담당자만, 한 회차의 짧은 구간만, 이유를 적고 내려받는다. 결과는 다음 회차 규칙을 고치는 데만 쓰고 특정 사람을 찾아 조치하지 않는다. 마우스 움직임 같은 행동 요약과 같은 기기 묶음은 운영 연결에서 내려받지 않는다. 분석 기록과 봇 판정 기록을 서로 잇지 않는다는 원칙을 지키려는 것이라, 운영 연결의 후보 그림은 '얼마나 빨리 좌석을 잡았나' 한 축으로 본다.
- **어느 브라우저에서나 같은 데모**: 같은 '씨앗 값'(시드)이면 어느 브라우저에서 열어도 같은 가상 온세일이 나와야 공유 주소가 뜻이 있다. 그런데 로그·지수 같은 수학 함수는 브라우저마다 마지막 자리가 조금 다를 수 있어, 생성기는 사칙연산과 결과가 하나로 정해진 함수만 쓰고, 그런 분포는 미리 만들어 둔 표에서 읽는다. 세 브라우저 엔진에서 만든 파일이 같은지 시험으로 확인한다.
- **운영 연결은 관제 콘솔에 붙이되 따로 연다**: 실제 기록을 보는 화면은 관제 콘솔의 로그인, 접속 제한, 감사 기록을 그대로 쓴다. 다만 콘솔 화면 안에 넣지 않고 새 탭으로 따로 연다. 무거운 분석이 실시간 관제 화면을 느리게 하거나 함께 멈추게 하지 않으려는 것이고, 이 탭에서만 빠른 공유 메모리 방식을 켤 수 있다.

## 4. 규칙

| 규칙 | 내용 |
| --- | --- |
| 대기실 크기 | 프로그램은 압축해 50KB 이하, 꾸밈 파일은 10KB 미만. 넘으면 코드를 합치지 못한다 |
| 다시 묻는 간격 | 0.5·5·20초. 실패하면 두 배(최대 60초, 잠정값), ±20% 흔들기. 서버가 보낸 '다시 물을 시간'이 있으면 그보다 빨리 묻지 않고 그 위로만 0~20% 흔들기, 같은 회차는 보고 있는 한 탭만 |
| 좌석 지도 | 대기실 통과 뒤 1초 안에 첫 그림. 무거운 계산은 화면 뒤 일꾼이 |
| 결제 | 결과는 페이지 이동으로 받는다. 서명 키는 꺼낼 수 없게 둔다. 결제사가 준 값은 저장하지 않는다 |
| 저장 | 저장소 규칙 표에 없는 값은 브라우저에 남기지 않는다 |
| 로그아웃 | 그 앱의 로그인 쿠키와 표에서 로그아웃 때 지우는 저장물을 지운다. 기기 식별값과 최근 검색어는 남기고, 티켓 입장 키는 사용자가 고를 때만 지운다 |
| 관제 부품 | 지문과 약속 판 번호를 확인하고, 실패하면 그 칸만 대체한다. 온세일 동안 바꾸지 않는다 |
| 허용 목록 | 화면 묶음마다 따로 둔다. 지표와 오류는 같은 사이트 주소로만 보낸다 |

## 5. 솔직한 한계

| 한계 | 그래서 |
| --- | --- |
| 대기실을 가벼운 별도 페이지로 만들어서, 대기 화면 요소를 React 화면과 두 벌로 관리한다 | 디자인 값과 문구를 같은 곳에서 가져오고, 화면을 사진으로 비교하는 시험으로 맞춘다 |
| 서명 키는 꺼낼 수 없어도, 공격자가 우리 화면 안에 스크립트를 끼워 넣으면(XSS) 그 스크립트가 서명을 시킬 수는 있다 | 허용 목록과 출력 규칙으로 줄인다. 화면에 글자를 넣는 위험한 통로를 브라우저가 검사하는 기능(Trusted Types)은 관제 화면부터 '보고만' 하고, 30일(잠정값) 동안 위반이 없으면 다른 앱으로 넓힌다. 실제로 막을지는 따로 정한다 |
| 구매 단계 요청은 다른 주소의 서버로 가서, 주소마다 브라우저가 '보내도 되나요'를 먼저 묻는 왕복(사전 요청)이 한 번씩 붙는다 | 지연 예산에 넣고 실제로 잰다. 예산을 넘으면 다른 방식을 새로 검토한다 |
| 좌석 실시간 연결에 입장 표를 싣는 방법은 서버 입구가 그 값을 확인할 수 있는지 아직 시험 전이다 | 안 되면 연결 직후 첫 메시지로 표를 보내는 방식으로 바꾼다 |
| 화면 흔들림 지표(CLS)는 크롬 계열에서만, 반응 속도 지표(INP)와 첫 화면 지표(LCP)는 Safari 26.2부터 잴 수 있어, 그 전 아이폰의 체감 숫자가 비어 있다 | 그 지표 칸은 0으로 채우지 않고 비워 둔다. 대기 반영·좌석 첫 그림·결제 확정처럼 서버 시각으로 직접 재는 흐름 숫자는 그 기능에 기대지 않아 아이폰에서도 잰다 |
| 포트폴리오 기간에는 실제 사용자가 없어, 체감 성능을 실제 사용자 브라우저에서 잰 값(RUM)으로 판정할 수 없다 | 정해 둔 휴대폰 조건(CPU 4배 느림)에서 스크립트로 같은 조작을 20번 [가정] 되풀이해 잰 '랩 판정'으로 대신하고, 그것을 실제 사용자 측정이라고 부르지 않는다. 출시 뒤에는 실제 사용자 측정으로 판정한다(docs/frontend.md §5.8) |
| 휴대폰 시계를 서버에 맞출 때 오가는 시간이 한쪽으로 치우친 몫(대개 수십 밀리초, 추정)만큼은 틀릴 수 있다. 대기실과 좌석 화면 밖의 화면은 초 단위 시각이라 ±1초 안팎 틀릴 수 있다 | 대기실은 대기열 서버가 밀리초로 적어 준 시각으로, 좌석 화면은 실시간 연결로 한 번 오가며 맞춘다. CDN이 캐시한 응답의 시각은 쓰지 않는다 |
| 미리 만들어 두는 캐시 화면과, 열 때마다 새 비밀 값(nonce)을 넣어 그리는 로그인·마이·결제 화면을 한 앱 안에서 바깥 틀을 따로 두어 나눴다. 그래서 둘 사이를 오가면 화면 전체를 새로 불러온다 | 대기실 → 좌석 → 결제는 원래 전체를 새로 부르므로 그대로이고, 홈에서 로그인처럼 몇 이동만 한 번 새로 그려진다. 이 나눔이 실제로 도는지는 작은 시험(PoC) 전이고, 안 되면 앱을 둘로 나눈다 |
| 아이폰의 7일 저장소 삭제는 줄일 뿐 막지 못한다 | 홈 화면 앱, 저장 유지 요청, 공연 전 알림, 다시 등록과 부스 안내로 대비한다 |
| 배터리가 적을 때 움직이는 효과를 끄는 기능은 안드로이드 크롬에서만 된다 | 다른 기기에서는 사용자가 설정한 '움직임 줄이기'를 따른다 |
| 브라우저는 오래 숨긴 탭을 얼리거나 잠재울 수 있어, 그동안 관제 화면의 경보와 승인 요청이 늦게 보일 수 있다 | 숨긴 동안 위젯을 쉬게 해 그럴 가능성을 줄이고, 관제 PC에서는 콘솔 주소를 '항상 활성' 목록에 넣는다. 경보는 온콜 알림으로도 간다. 승인 요청을 온콜로도 보낼지는 아직 정하지 않았다 |
| 카카오톡 같은 앱 안 브라우저를 알아보는 방법은 브라우저 이름표에 기대서, 새 앱이나 이름표를 바꾼 앱은 못 알아본다 | 안내용으로만 쓰고 서버 판정에는 쓰지 않는다 |
| 대기 순번 파일 규칙, 좌석 변화의 바이트 모양, 서명 입력, 실시간 채널 형식은 서버와 맞추기 전의 초안이다 | 서버 계약을 먼저 보강하는 작업에서 확정한다 |
| 포렌식 리플레이 데모는 가상의 온세일이라 실제 온세일을 증명하지 않는다. 사람의 반응 속도 분포도 설명용으로 정한 값이다 | 화면에 '합성 데이터' 표시를 늘 두고, 실제 측정은 성능 장부에 따로 남긴다 |
| 실제 기록을 쓰는 운영 연결은 법률 검토 결과에 따라 열리지 않을 수 있고, 좌석 하나하나의 경합은 기록 형식을 고치기 전까지 구역 단위로만 보인다 | 출시 뒤 조건 넷(법률 검토, 보안 표 재판정, 기록 형식 보강, 새 결정 기록)을 채운 뒤에만 연다 |

## 6. 한 줄 요약

> **수십만 명이 여는 대기실은 화면 라이브러리 없이 미리 만든 가벼운 파일로 나눠 주고, 좌석 지도는 화면 뒤 일꾼이 바뀐 좌석만 그리며, 결제는 다른 회사 화면을 다녀와도 꺼낼 수 없는 키로 이어 서명하고, 티켓과 스캐너는 인터넷 없이도 돌게 만들며, 브라우저에 무엇을 남기고 어디서 받은 프로그램을 돌릴지는 화면마다 표로 정한다.**
