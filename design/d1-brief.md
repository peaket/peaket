# D1. 디자인 브리프

- **독자와 용도**: 프로덕트 디자이너와 프론트엔드 엔지니어가 화면 UI를 설계하고 구현하기에 앞서 사용 맥락, 핵심 원칙, 플랫폼 제약 사항, 웹 접근성 목표에 대해 상호 합의하고 정렬하기 위해 참조한다.
- **원문 출처**: 설계서 §3(4개 클라이언트 앱 및 사용자 페르소나), §6(대기실 저전력 모드, 좌석맵 웹 접근성 대안 UI, 관제 다크 모드, 오프라인 상태 배너), 6장(디자인 시스템 및 토큰 도구), 9장(모션 토큰 및 접근성 애니메이션), 11장(대기실 자바스크립트 번들 예산), 13장(WCAG 2.2 AA, 색각이상 패턴 병행, 명도 대비 4.5:1), 13장 다국어 i18n 요구사항.
- **기준 기획 버전**: v1.0.
- **표시 규칙**: 원문에는 구체적인 시각 디자인 결정(브랜드 아이덴티티, 주조색, 톤앤매너)이 정의되어 있지 않았다. 사용 맥락, 접근성, 플랫폼 제약은 원문 설계를 계승하였으며, 디자인 원칙, 톤앤매너, 반응형 브레이크포인트는 [보완]으로 규정하였다. 브랜드 명칭, 지원 플랫폼 범위, 브레이크포인트, 다크 모드 정책은 제품 소유자가 추천대로 정하도록 맡겨 추천안을 적용해 확정하였고(추천 적용, 2026-10-09, §3·§4 참조), 콘솔의 휴대폰·태블릿 지원과 스캐너 태블릿은 2026-10-14 소유자 결정으로 더했으며(`ADR-0061`), 게이트 스캐너의 물리적 사용 환경은 실제 현장 부하 시험 전까지 [가정]으로 유지한다.

## 1. 사용 맥락과 정보 밀도

| 앱 | 사용 맥락(원문) | 정보 밀도 [보완] |
| --- | --- | --- |
| 소비자 웹 — 대기실 | 최대 100만 명이 동시에 접속하여 체류하는 대규모 트래픽 페이지이다. 모바일 디바이스 접속 비중이 압도적으로 높다. 배터리 잔량이 15% 이하인 경우 CPU 부하를 줄이기 위해 CSS 애니메이션을 비활성화한다(폴링 주기는 queue-admission §4의 예상 대기·Retry-After 규칙만 따른다). 대기 시간이 30분 이상 지속될 수 있으며, 5분 이상 백그라운드에 머문 탭은 브라우저 타이머 스로틀링으로 1분에 1회만 갱신될 수 있다(queue-admission §4). | 매우 낮음. 대기열 기본 화면은 내 앞 대기 인원, 진행 막대, 예상 대기 시간, 대기 취소 네 가지뿐이고(소유자 결정 2026-10-14, ADR-0063), 판매 일시정지·조건부 유의 경고·운영 공지 등은 생길 때만 뜨며 정렬 방식·형사처벌 고지는 '순번 안내' 시트에 둔다(planning/04 SCR-008 ①~⑩). 진행 막대의 움직임은 CSS `transform`·`opacity`로만 그려 번들 예산 안에 둔다. 번들 크기는 Gzip 기준 JavaScript 50KB 이하, CSS 10KB 미만으로 엄격히 제한한다. |
| 소비자 웹 — 좌석 선택 | 5만석 규모의 대규모 좌석맵을 1초 이내에 렌더링하고, 사용자 인터랙션은 INP 200ms 이하·50ms 넘는 Long Task 0건(NFR-012)으로 반응하고, 좌석 홀드 응답은 p99 50ms(NFR-003, 서버)다. 인기 좌석 1석당 최대 1,000명이 동시 경합하여 홀드에 실패하는 상황이 빈번하게 발생한다. 좌석 홀드 유효시간 카운트다운 타이머가 표시된다. | 높음. 캔버스 좌석 지도, 등급별 범례, 선택 좌석 요약 패널, 잔여 홀드 타이머가 유기적으로 결합된다. 정보량은 방대하지만 사용자의 인지 부하를 줄이고 오직 '좌석 선택 및 홀드'라는 단일 목표에 집중하도록 설계한다. |
| 소비자 웹 — 결제·월렛 | 전자결제는 수 초 이내에 신속히 체결되어야 하며, 좌석 홀드 실패나 시간 초과 시 사용자에게 어떠한 과금도 발생하지 않았음을 명확히 안심시켜야 한다. 마이 티켓 월렛은 통신 환경이 열악하고 직사광선이 내리쬐는 야외 공연장 현장에서도 식별 가능해야 한다. | 중간. 결제 단계는 결제 수단과 약관 동의에 집중하며, 월렛 화면에서는 야외 스캔 인식률을 극대화하기 위해 Dynamic QR 코드가 화면 가로 폭의 90%를 차지하도록 배치한다(design/d3 SCR-013). |
| 파트너 콘솔 | 티켓 판매 기획 및 정산 실무자가 업무용 데스크톱 환경에서 다단계 등록 위저드와 대용량 좌석맵 에디터를 조작한다. 수천 개의 좌석 노드를 시각적으로 정밀하게 편집한다. 공연 당일에는 현장에서 휴대폰으로 입장 현황을 보고 스태프 권한과 기기 배치를 다루며, 태블릿에서는 데스크톱과 같은 일을 한다 [보완, `ADR-0061`]. | 높음. 복잡한 폼 입력 필드, 대규모 데이터 그리드 테이블, 캔버스 에디터 패널이 밀도 높게 구성된다. 휴대폰은 보기와 현장 운영 중심으로 한 화면에 한 가지 일을 둔다. |
| 관제 콘솔 | 최대 50명의 운영 엔지니어(콘솔 최대 설계 용량 기준, 공식 SLO 측정 조건은 10명 기준, C-02 결정 2026-10-08)가 티켓 오픈 전후 70분 동안 다크 모드 데스크톱 환경에서 수십 개의 시스템 패널을 집중 감시한다. "현재 전체 시스템이 정상 작동 중인가?"라는 질문에 지체 없이 즉각 판단할 수 있어야 한다. 자리를 비운 운영자는 휴대폰으로 상태를 보고 이미 요청된 일을 승인·반려하며, 태블릿에서는 데스크톱과 같은 일을 한다 [보완, `ADR-0061`]. | 매우 높음. 모든 모니터링 패널에 SLO 임계 기준선을 명시하며, 특정 위젯 장애가 전체 화면으로 전파되지 않도록 위젯 단위 Error Boundary 격리를 적용한다. |
| 관제 콘솔 — CS 업무 | CS 담당자가 평상시 데스크톱에서 CS 처리함의 건을 기한 안에 처리하고 승인 업무를 요청하며, 가린 개인정보는 사유를 입력한 뒤에만 연다(planning/01 사용자 유형, POL-038) [보완]. | 중간. 건 목록과 상세, 기한 배지, 팬 조회가 한 화면에 놓이고 영업일 기한을 글자로 읽는다. |
| 소비자 웹 — 현장 스태프 휴대폰 | 현장 스태프가 자기 휴대폰으로 초대를 수락하고 스캐너 로그인을 승인하며 내 배정을 본다(web-staff 셸, design/d5 §3.1) [보완]. | 낮음. 한 화면에 한 가지 일과 큰 확인 코드만 둔다. |
| 게이트 스캐너 | 현장 스태프가 저사양 모바일 단말기(관리형 휴대폰, 거치나 손에 드는 관리형 태블릿 포함, `ADR-0061`)를 파지하고 야외 및 실내 게이트에서 분당 60명의 관람객을 신속히 검표한다. 전면적인 오프라인 로컬 판정을 기본 전제로 하며, 방한 장갑 착용 및 역광 환경에 노출될 수 있다 [가정]. | 매우 낮음. 티켓 유효성 판정 결과(통과, 거부, 확인 필요. 이미 입장한 티켓은 거부 사유다)가 화면 절반 이상에 색·아이콘·글자로 즉각 노출되며, 거부 사유는 직관적인 단일 텍스트 행으로만 간결하게 표시한다. |

## 2. 디자인 원칙 [보완]

| # | 원칙 | 의미와 구현 방향 | 근거(원문) |
| --- | --- | --- | --- |
| 1 | 공정함의 시각화 | 앞선 대기 인원과 셔플 추첨 결과는 가공되지 않은 정확한 수치로 제공하며(대기실·대기열 화면에는 내 번호와 현재 입장 번호를 내지 않는다, ADR-0060 결정 2. 셔플 검증 화면은 시드 공개 뒤 다시 계산한 순번을 결과 파일 값과 함께 보인다) 사용자가 임의로 추측하게 만들지 않는다. 오픈 이전 로비 상태에서는 순번으로 오인될 수 있는 어떠한 임의의 숫자도 표시하지 않는다. 무작위성의 검증 근거와 증적을 투명하게 공개한다. | POL-004, POL-005, POL-007 |
| 2 | 100만 명의 최약자를 위한 경량화 | 대규모 트래픽이 몰리는 대기실은 저사양 단말기와 저전력 배터리 상태에서도 절대 멈추거나 튕기지 않아야 한다. 화려한 장식용 애니메이션보다 초경량 번들 크기와 안정적인 프레임 유지를 절대적 우선순위로 둔다. | NFR-012 번들 예산, 저전력 모드 가이드, K5 |
| 3 | 실패 상태의 우선적 설계 | 모든 UI 컴포넌트는 기본 상태뿐만 아니라 로딩, 빈 화면, 에러, 권한 없음의 5대 상태를 사전에 완벽히 정의한다. 좌석 홀드 실패, 무과금 결제 취소, 세션 만료는 정상적인 비즈니스 예외 흐름이다. 모든 실패 안내는 '무엇이 발생했는가'와 '사용자가 취해야 할 다음 행동은 무엇인가'를 명확히 제시한다. | SCR 상태 5종 정의, POL-013 |
| 4 | 다중 감각 정보 전달 (색상 의존 탈피) | 좌석 예매 상태나 게이트 판정 결과는 단일 색상에만 의존하지 않고, 시각적 패턴 및 명확한 텍스트를 반드시 병행하여 전달한다. 텍스트 명도 대비 4.5:1(대형 텍스트 3:1)을 엄격히 준수하며 키보드 포커스 링을 명확히 노출한다. 시스템의 움직임 축소(prefers-reduced-motion) 설정을 충실히 존중한다. | NFR-020, 13장 접근성, 9장 모션 |
| 5 | 운영 상황의 즉각적 인지 | 중앙 관제 콘솔은 이상 징후를 한눈에 파악할 수 있도록 정상 기준선과 실시간 관측치를 중첩하여 시각화한다. 시스템에 큰 영향을 미치는 위험 명령은 단계적 안전장치(사유 입력 → dry-run 시뮬레이션 → 2인 승인)로 한 사람의 실수가 곧바로 반영되지 않게 한다. 두 사람이 함께 잘못 판단한 명령은 막지 못하므로 모든 명령에 되돌리기(Revert)를 둔다. | SCR-029, POL-021 |

**원칙 상충 시 우선순위 기준**: 1원칙(공정·정확성) > 4원칙(웹 접근성) > 3원칙(실패 상태 복원력) > 2원칙(경량 최적화) > 5원칙(관제 가독성) > 일반 심미성 순으로 적용한다. (예: 공정한 대기 인원 표시를 위한 비트맵 125바이트 전송과 번들 경량화가 상충할 경우, 정확한 숫자 제공을 위해 1원칙을 우선 채택한다.)

## 3. 브랜드, 톤앤매너, 레퍼런스

브랜드 아이덴티티는 원문에 누락되어 있어 제품 소유자가 추천대로 정하도록 맡겨 추천안을 적용해 확정하였다(추천 적용, 2026-10-09, `00-summary §7` 질문 6). 시각적 디자인 토대는 소유자 의사결정(2026-10-11, `00-summary §7` 추가 요청의 NOL·SEED 행)에 의거하여 오픈소스 아파치 라이선스 디자인 시스템인 SEED Design을 기반으로 채택하였다(`ADR-0040`). 서비스 상표권의 경우 포트폴리오 전시 기간에는 현행 명칭을 유지할 수 있는 것으로 추정하고(`POL-027` 추정, `ADR-0036`), 정식 상용 서비스 론칭 이전에 특허청 KIPRIS를 통해 최종 등록 가능성을 검증한다(`wbs 0.6.3`).

| 항목 | 결정 사항 | 채택 사유 및 가이드 |
| --- | --- | --- |
| 서비스명 표기 | 공식 로고, 영문 표기, 소스코드, 도메인은 'PEAKET'으로 표기하며, 한국어 UI 문맥 내에서는 '피켓'으로 표기한다. 최초 서비스 소개, 이용약관, 법정 의무 고지문에서는 'PEAKET(피켓)'으로 병기한다. | 영문 명칭은 정점을 의미하는 PEAK와 TICKET의 합성어로 철자 자체에서 서비스의 본질이 드러나며, 한국어 사용자는 직관적으로 '피켓팅'의 '피켓'으로 발음한다. 법적 고지에서는 병기를 통해 법적 동일성을 명확히 한다. |
| 명칭의 시각적 연상 | 콘서트 현장에서 관객이 들어 올리는 응원 피켓의 이미지와 연결한다. | K-POP 및 공연 팬덤 문화와의 자연스러운 정서적 유대를 형성한다. 단, 사회적 시위 피켓과의 불필요한 연상을 방지하기 위해 과격한 손팻말이나 구호 형태의 그래픽 모티프는 배제한다. |
| 톤앤매너 | 차분하고 신뢰감을 주는 전문 안내자의 어조를 견지한다. 간결하고 명확하게 수치 중심으로 소통하며, 사용자를 불안하게 재촉하지 않고, 시스템 공정성의 근거를 투명하게 공개한다. | 티켓 오픈 직전 사용자가 겪는 극심한 심리적 긴장감(`01-overview §1.3`)을 UI가 불필요하게 가중시키지 않도록 배려한다. 이는 디자인 1원칙 및 3원칙과 일치하는 방향이다. |
| 문체 | 화면 내 모든 대고객 안내 문구는 정중한 평서형 경어체인 '~합니다'체(`design/d2 §4`)로 통일하며, 비격식 구어체인 해요체로 변형하지 않는다. | 대고객 문장의 톤을 하나로 맞춰 혼선을 막는다. 법정 고지 원문(`POL-004`, `POL-024`)은 '~할 수 있음'처럼 원문 문체를 그대로 쓰는 예외다(`design/d2 §4`). |
| 브랜드 주조색 | 딥 인디고 단일 색상(`color.primitive.indigo.600`, #4338CA)과 뉴트럴 그레이를 브랜드 주조색으로 사용하며, 여타 유채색은 UI 상태 표현 전용으로만 제한한다. | 시스템 상태를 나타내는 기능성 색상(초록, 호박색, 빨강)과 시각적으로 겹치지 않게 하며, 순백색 텍스트 배경 대비 7.90:1의 탁월한 명도비를 확보한다(`design/d2 §5`). |
| 좌석 상태 색상 보정 | 사용자가 직접 선택한 좌석은 브랜드 인디고를 적용하고, 휠체어석은 기존 보라색(#6F4BD8) 대신 마젠타 자홍색(#A3207E)을 지정한다. | 보라색 계열은 인디고 주조색과 색상환에서 지나치게 인접하여 식별이 어렵기 때문이다. 시각 패턴(체크 표시(✓) 및 휠체어 픽토그램 아이콘)은 색상과 반드시 병행하여 표시한다. |
| 로고 및 심벌마크 | 'PEAKET' 영문 워드마크와 티켓 절취선 상단에 산봉우리가 솟아오른 미니멀 심벌을 조합한다. 해당 심벌은 파비콘, PWA 홈 화면 아이콘, 스캐너 앱 아이콘에 적용하며 단색 및 네거티브 반전 버전을 함께 구비한다. | 모바일 사용자가 마이 티켓 월렛을 홈 화면에 바로가기로 추가했을 때 텍스트 없이도 단번에 식별할 수 있는 강력한 시각적 앵커를 제공한다. |
| 시각 토대 시스템 | 당근마켓의 오픈소스 디자인 시스템인 SEED Design 3.0(Apache-2.0 라이선스)의 토큰 및 기본 UI 컴포넌트를 기반으로 차용하고, 브랜드 역할 색상만을 인디고 팔레트로 오버라이드한다(소유자 선택 B, 2026-10-11, `ADR-0040`). 단, 당근마켓의 로고, 상호, 마스코트 캐릭터, 시그니처 당근 주황색은 일체 사용하지 않는다. | 명확한 오픈소스 라이선스에 기반하여 저작권 리스크가 없고, 모바일 및 웹에 최적화된 토큰 체계, 라이트·다크 테마가 완비되어 있기 때문이다. 단, SEED의 APCA 명도 기준과 피켓의 WCAG 2.2 AA 기준 간 차이로 인해 일부 텍스트 명도는 재정의하였다(`design/d2 §5`). |

- **벤치마크 레퍼런스 차용 포인트** (원문 설계 기준): Ticketmaster의 동적 좌석맵 인터랙션 및 수 초 주기로 회전 갱신되는 SafeTix 다이내믹 바코드 구조, Cloudflare Waiting Room의 20초 주기 자동 리프레시 진행률 안내 UI, AWS Virtual Waiting Room의 serving(현재 입장 번호) 메커니즘을 적극 차용한다. 대기열 화면에는 내 번호와 현재 입장 번호를 내지 않고 앞 인원과 예상 대기만 보인다(ADR-0060).
- **레퍼런스 분석 및 도용 방지 준칙** [보완, 2026-10-11]: 외부 레퍼런스 서비스는 공개된 웹/앱 화면을 엔지니어가 직접 육안으로 관찰하여 일반적인 UX 패턴(정보 구조, 화면 밀도, 플로우)을 학습하고 벤치마킹하는 용도로만 엄격히 제한한다. 자동화된 크롤러, 스크레이퍼, 토큰 추출기를 통한 데이터 수집과 타사 브랜드, 로고, 페이지 레이아웃, 독점적 그래픽 자산의 무단 복제는 절대 금지한다. 인터파크·야놀자(NOL) 서비스 이용약관은 제23조(이용자의 의무) ④ 제15호에서 사전 서면 허가 없는 자동화 수단·수동 프로세스로 콘텐츠를 모니터링·복제·수집·확인하는 것을, 같은 항 제20호에서 사전 서면 승인 없이 브랜딩·페이지 레이아웃·디자인을 사용·복제·전시·미러링·프레이밍·딥링크하는 것을 금지한다(2026-09-29 시행본, 2026-10-14 원문 확인. 2026-10-11 기록의 '제15조·제20조'는 조항 표기를 잘못 적은 것이라 고쳤다). 타사 서비스에도 같은 기준을 적용한다. **예외(홈 구조)**: 소유자는 제20호의 위험(특히 페이지 레이아웃)을 알고 홈(SCR-001)의 섹션 구조를 NOL 티켓 메인에서 따르기로 했다(소유자 결정 2026-10-14, ADR-0063). 따르는 것은 섹션 순서·배치·크기 비율뿐이고, NOL의 로고·이미지·문구·배지 이름·아이콘 그림·색은 쓰지 않으며 시각은 피켓(SEED 토큰, 인디고)으로 그린다. 섹션 내용은 피켓 기획에 있는 기능만 넣고 NOL에만 있는 기능(포인트·결제 혜택, 타임딜·할인, 영상 클립, 쿠폰·특가)은 넣지 않거나 피켓 기능으로 바꾼다. 관찰은 사람이 공개 화면을 보고 배치를 말로 적는 데 그치고 자동 수집·스크린샷 저장을 하지 않는다(제15호). 남는 위험은 `planning/01 §5.2`에 적었다. 공연 상세(SCR-002)의 2단 배치·섹션 바로가기·안내 모달도 NOL 상세 화면을 보고 정했으므로 같은 규칙(구조만 따르고 시각·문구·기능은 피켓)을 적용한다. 디자인 토큰 추출 검증 도구는 피켓 자체 배포 결과물의 디자인 드리프트를 점검하는 내부 CI/CD 목적으로만 사용한다. 스타일 기준의 최종 확정은 `00-summary §7` 추가 요청(2026-10-11) NOL·SEED 행의 결정(`ADR-0040`)을 따른다.
- **철저히 배제해야 할 다크 패턴**: Ticketmaster가 겪었던 대기열 불투명성 논란(순번 배정 기준이 모호한 설명), '선착순'이라는 기만적 표현(`POL-004`), 교묘한 다크 패턴(선택 동의를 필수처럼 위장하기, 되돌릴 수 없는 취소/탈퇴 처리를 확인 절차 없이 즉시 실행하기), 사용자의 불안감을 조장하는 인위적 마케팅 연출('마감 임박', '잔여 1석' 깜빡임 효과 등)을 철저히 배제한다. 홈의 '지금 판매 중'이 보이는 남은 판매 기간도 글자로만 쓰고 깜빡임·재촉 배지를 붙이지 않는다(ADR-0063).

## 4. 지원 플랫폼, 브레이크포인트, 다크 모드

- **지원 플랫폼 기준**: `NFR-019` 준수(추천 적용, 2026-10-09). 소비자 웹은 모바일 퍼스트 원칙을 적용하며 웹 표준 Baseline의 'Widely available' 기능을 기본 스펙으로 사용한다. 카카오톡이나 인스타그램 등 인앱 브라우저 접속 환경은 공연 탐색 및 상세 조회 단계까지만 지원하며, 대기열 로비 진입 이전에 그 기기의 기본 외부 브라우저(iPhone·iPad는 Safari, Android는 Chrome이나 삼성 인터넷, Windows는 Edge나 Chrome, Mac은 Safari나 Chrome. Whale도 지원 대상, NFR-019)로 안전하게 전환하도록 안내한다(SCR-058, ADR-0063). 파트너 콘솔과 관제 콘솔은 데스크톱(해상도 1280×800 이상에서 기본 밀도)을 기준으로 설계하되 태블릿과 휴대폰(폭 360px부터)에서도 쓴다. 태블릿은 데스크톱과 기능이 같고, 휴대폰은 보기·이미 요청된 일의 승인·안전 쪽 조치와 공연 당일 현장 운영, 정산서 내려받기·정산 이의, 반품 도착 확인, 내 계정 보안 설정(재인증)까지만 하며 나머지는 '태블릿이나 데스크톱에서 합니다' 안내로 대신한다(소유자 결정 2026-10-14, `ADR-0061`, 화면별 범위는 `design/d5 §3.9`). 게이트 스캐너는 사내에서 승인된 관리형 Android 휴대폰·태블릿으로 한정한다.
- **반응형 브레이크포인트** (추천 적용, 2026-10-09): `sm` 360px(모바일 최소 기준선), `md` 768px(태블릿 및 스캐너 가로 모드), `lg` 1024px(데스크톱 기본 레이아웃 개시점), `xl` 1440px(관제 콘솔 다중 모니터링 패널). 파트너 콘솔과 관제 콘솔은 `sm`에서 휴대폰 배치(메뉴 서랍, 표는 카드 목록, 관제는 아래 탭 막대), `md`에서 태블릿 배치(메뉴 서랍, 위젯 2열, 표는 가로 스크롤 상자), `lg`부터 데스크톱 배치(왼쪽 내비)를 쓰고 1440px 이상 환경에서 `xl` 고밀도 레이아웃으로 확장된다(`ADR-0061`). 게이트 스캐너 태블릿은 `md` 세로 배치다. 토큰 세부값은 `tokens.json`의 `breakpoint` 항목에 정의되어 있다.
- **뷰포트 높이 단위**: 모바일 전체 화면 대기실 렌더링 시 모바일 브라우저 주소창의 동적 축소·확장에 안정적으로 대응하기 위해 `100dvh` 및 `svh` 단위를 채택한다(원문 9장).
- **다크 모드 운영 방침**: 중앙 관제 콘솔은 관제실 조명 환경과 엔지니어의 시각 피로를 고려하여 다크 모드를 기본 고정 테마로 적용한다(원문 6장 '다크 모드(관제실)'). 소비자 웹과 파트너 콘솔은 사용자 OS 시스템 테마 설정을 자동으로 추종하며, 게이트 스캐너는 강한 야외 직사광선 아래에서의 시인성을 확보하기 위해 라이트 모드로 고정 운용한다(추천 적용, 2026-10-09).
- **다국어 국제화 (i18n)**: 한국어(ko), 영어(en), 일본어(ja), 중국어 간체(zh) 4개 언어를 기본 지원한다(`NFR-024`). 언어별 문자열 길이에 유연하게 대응하기 위해 액션 버튼 및 배지 컴포넌트는 고정 픽셀 폭 지정을 금지하고 콘텐츠 너비 기반(Intrinsic Width)으로 유연하게 늘어나도록 구현한다. 팬 화면의 날짜·시간은 공연장 현지 시각으로 쓰고 기기 시간대가 다르면 기기 시각을 함께 쓴다(`NFR-024`). 파트너·관제 콘솔은 시간대를 붙인 KST, 로그는 UTC다(`ADR-0060` 결정 4). 언어는 주소 접두로 나눈다(한국어 기본 주소, `/en`·`/ja`·`/zh`, hreflang, 자동 이동과 언어 쿠키 없음, `ADR-0060` 결정 3).
- **그리드 레이아웃 너비** (`ADR-0040`): SEED Design의 레이아웃 가이드라인을 준용한다. 소비자 웹 콘텐츠 최대 너비는 1040px, 공연 탐색 및 좌석맵 캔버스 영역은 최대 1280px로 설정하며 데스크톱 거터는 24px, 외부 마진은 32px를 적용한다. 홈(SCR-001)의 본문은 최대 1240px(배너 슬라이드 폭)이고, 화면이 1240px + 양쪽 외부 마진보다 좁으면 외부 마진 32px를 지키고 본문을 줄인다(1280px 화면에서 1216px, 추천 적용 2026-10-14, ADR-0063). 파트너 및 관제 콘솔은 SEED 대시보드 레이아웃을 채택하여 중밀도 영역은 12열 1040px 그리드를, 관제 종합 패널은 고밀도 풀스크린(100% 폭)을 적용한다. 콘솔의 휴대폰 배치는 4열·바깥 여백 16px(관제 12px), 태블릿 배치는 8열·바깥 여백 24px이다(`ADR-0061`).

## 5. 접근성 목표

- WCAG 2.2 AA 기준 위반 0건을 목표로 달성한다(원문 설계, `NFR-020`). 지속적인 자동화 접근성 검사 도구(axe-core) 검증과 함께 시각장애인 스크린리더(NVDA, VoiceOver) 환경에서의 수동 테스트 시나리오를 정기적으로 수행한다.
- HTML5 Canvas 기반 좌석맵은 스크린리더가 시각 요소를 직접 읽어낼 수 없으므로, 동일 화면 내에 '구역 → 열 → 좌석 번호' 순서로 키보드 방향키 탐색이 가능한 웹 접근성 텍스트 목록과 '자동 좌석 배정' 버튼을 동등한 위계로 기본 제공한다.
- 대기열의 앞 인원·예상 대기와 좌석 홀드 잔여 시간 정보는 `aria-live` 속성을 통해 음성 안내하되, 과도한 알림 폭주를 방지하기 위해 폴링 주기별로 안내 빈도를 스로틀링한다. 좌석 홀드 시간은 남은 시간을 표시하고 1회 연장 컨트롤을 반드시 제공한다. WCAG 2.2.1(Timing Adjustable)의 연장 방식은 만료 전 경고와 10회 이상 연장을 요구하므로 '1회 연장'만으로는 맞지 않는다. 좌석 홀드와 구매 세션 최대 체류는 온세일이라는 실시간 경쟁에서 다른 사람이 살 좌석과 입장 자리를 묶는 제한이라 2.2.1의 실시간 예외로 보고, 관리 계정 유휴 만료와 구매 세션 무활동 만료는 만료 전 경고와 [계속] 버튼으로 연장한다(ADR-0060).
- 모든 좌석 상태는 색각이상 사용자를 고려하여 안전한 색상 팔레트와 시각적 패턴(점박이, 빗금, 아이콘)을 반드시 병행 표기한다(WCAG 1.4.1). 일반 본문 텍스트 명도비 4.5:1 이상, 대형 텍스트 3:1 이상, 핵심 그래픽 인터페이스 요소 3:1 이상의 명도 대비를 엄격히 유지한다.
- 시스템의 움직임 축소(`prefers-reduced-motion: reduce`) 설정이 활성화된 경우, 위치 이동이나 스케일 변형 애니메이션을 부드러운 불투명도(opacity) 전환으로 자동 대체한다. '곧 입장합니다' 등 텍스트 단위 글자별 등장 모션의 경우 원본 문장을 `aria-label`로 선언하고 개별 글자 span 태그에는 `aria-hidden="true"`를 부여하여 스크린리더의 중복 낭독을 방지한다.
- 마우스 및 터치 대상의 최소 클릭 영역은 24×24px 이상을 유지하며, 모바일 주요 액션 버튼(좌석 홀드, 결제하기, 티켓 스캔)은 한 손 조작 환경을 고려하여 최소 44×44px 이상의 터치 타깃을 확보한다 [보완].
