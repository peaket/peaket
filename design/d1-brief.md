# D1. 디자인 브리프

- **독자와 용도**: 프로덕트 디자이너와 프론트엔드 엔지니어가 화면 UI를 설계하고 구현하기에 앞서 사용 맥락, 핵심 원칙, 플랫폼 제약, 웹 접근성 목표를 서로 합의해 맞추려고 참고한다.
- **원문 출처**: 설계서 §3 <제품 범위와 온세일 타임라인>, 설계서 §6 <시스템 아키텍처>, 6장(디자인 시스템과 토큰), 설계서 9장 <애니메이션>, 11장(번들 예산), 설계서 13장 웹 접근성 WCAG 2.2 AA 및 다국어 요구사항.
- **기준 기획 버전**: v1.0.
- **표시 규칙**: 원문에는 구체적인 시각 디자인 결정(브랜드 아이덴티티, 주조색, 톤앤매너)이 정해져 있지 않았다. 사용 맥락, 접근성, 플랫폼 제약은 원문 설계를 이어받았고, 디자인 원칙, 톤앤매너, 반응형 브레이크포인트는 [보완]으로 정했다. 브랜드 명칭, 지원 플랫폼 범위, 브레이크포인트, 다크 모드 정책은 제품 소유자가 추천대로 정하라고 맡겨 추천안으로 확정했다(추천 적용, 2026-10-09, §3·§4 참조). 콘솔의 휴대폰·태블릿 지원과 스캐너 태블릿은 2026-10-14 소유자 결정으로 더했다(`ADR-0061`). 게이트 스캐너의 물리적 사용 환경은 실제 현장 부하 시험 전까지 [가정]으로 둔다.

| 관제 콘솔 | 최대 50명의 운영 엔지니어(콘솔 최대 설계 용량 기준. 팀이 정한 목표인 SLO의 공식 측정 조건은 10명 기준, C-02 결정 2026-10-08)가 티켓 오픈 전후 70분 동안 다크 모드 데스크톱에서 수십 개의 시스템 패널을 집중해서 지켜본다. "현재 전체 시스템이 정상 작동 중인가?"라는 질문에 곧바로 판단할 수 있어야 한다. 자리를 비운 운영자는 휴대폰으로 상태를 보고 이미 요청된 일을 승인·반려한다. 태블릿에서는 데스크톱과 같은 일을 한다 [보완, `ADR-0061`]. | 매우 높음. 모든 모니터링 패널에 SLO 기준선을 표시한다. 위젯 하나의 장애가 전체 화면으로 번지지 않게 위젯마다 Error Boundary로 격리한다. |

## 2. 디자인 원칙 [보완]

| # | 원칙 | 의미와 구현 방향 | 근거(원문) |
| --- | --- | --- | --- |
| 1 | 공정함의 시각화 | 내 앞 대기 인원과, 순번을 무작위로 섞는 셔플 추첨의 결과는 가공하지 않은 정확한 수치로 보여 준다(로비·대기열 화면에는 내 번호와 현재 입장 번호를 내지 않는다, ADR-0060 결정 2. 셔플 검증 화면은 시드 공개 뒤 다시 계산한 순번을 결과 파일 값과 함께 보인다). 사용자가 어림짐작하게 두지 않는다. 오픈 전 로비 상태에서는 순번으로 잘못 알 수 있는 숫자를 하나도 표시하지 않는다. 무작위성의 검증 근거와 증거 기록을 투명하게 공개한다. | POL-004, POL-005, POL-007 |
| 2 | 100만 명의 최약자를 위한 경량화 | 트래픽이 크게 몰리는 대기실은 저사양 단말기와 배터리가 적게 남은 상태에서도 멈추거나 튕기지 않아야 한다. 화려한 장식용 애니메이션보다 아주 작은 번들 크기와 안정적인 프레임 유지를 최우선으로 둔다. | NFR-012 번들 예산, 저전력 모드 가이드, K5 |
| 3 | 실패 상태의 우선적 설계 | 모든 UI 컴포넌트는 기본 상태뿐 아니라 로딩, 빈 화면, 에러, 권한 없음을 더한 5대 상태를 모두 미리 정한다. 좌석 홀드 실패, 무과금 결제 취소, 세션 만료는 정상적인 업무상 예외 흐름이다. 모든 실패 안내는 '무엇이 발생했는가'와 '사용자가 취해야 할 다음 행동은 무엇인가'를 분명히 보여 준다. | SCR 상태 5종 정의, POL-013 |
| 4 | 다중 감각 정보 전달 (색상 의존 탈피) | 좌석 예매 상태나 게이트 판정 결과는 색 하나에만 기대지 않고, 시각적 패턴과 분명한 글자를 반드시 함께 써서 전달한다. 글자 명도 대비 4.5:1(큰 글자 3:1)을 지키고, 키보드 포커스 링을 분명히 보여 준다. 시스템의 움직임 줄이기(prefers-reduced-motion) 설정을 따른다. | NFR-020 |
| 5 | 운영 상황의 즉각적 인지 | 중앙 관제 콘솔은 이상 징후를 한눈에 알아볼 수 있게 정상 기준선과 실시간 관측치(시스템에서 실제로 잰 값)를 겹쳐 그린다. 시스템에 큰 영향을 주는 위험 명령은 단계별 안전장치(사유 입력 → dry-run 시뮬레이션 → 2인 승인)를 두어 한 사람의 실수가 곧바로 반영되지 않게 한다. 두 사람이 함께 잘못 판단한 명령은 막지 못하므로 모든 명령에 되돌리기(Revert)를 둔다. | SCR-029, POL-021 |

**원칙 상충 시 우선순위 기준**: 1원칙(공정·정확성) > 4원칙(웹 접근성) > 3원칙(실패 상태 복원력) > 2원칙(경량 최적화) > 5원칙(관제 가독성) > 일반 심미성 순으로 적용한다. (예: 저사양·저전력 기기에서 앞 인원 숫자가 굴러가는 효과(SCR-008)를 꺼 가볍게 하더라도, 앞 인원은 반올림하거나 '약 3천 명'처럼 뭉뚱그리지 않고 받은 정확한 값을 그대로 보인다. 가볍게 하려고 정확성을 깎지 않으므로 1원칙이 2원칙보다 앞선다. 추천 적용 2026-10-28, 기술 검토 낮음-103)

## 3. 브랜드, 톤앤매너, 레퍼런스

브랜드 아이덴티티는 원문에 빠져 있어서 제품 소유자가 추천대로 정하라고 맡겨 추천안으로 확정했다(추천 적용, 2026-10-09, `00-summary §7` 질문 6). 시각 디자인의 토대는 소유자 결정(2026-10-11, `00-summary §7` 추가 요청의 NOL·SEED 행)에 따라, 당근이 공개한 오픈소스 아파치 라이선스 디자인 시스템인 SEED Design으로 정했다(`ADR-0040`). 서비스 상표권은 포트폴리오 전시 기간에는 지금 이름을 계속 쓸 수 있다고 추정하고(`POL-027` 추정, `ADR-0036`), 상용 서비스를 출시하기 전에 특허청 KIPRIS로 최종 등록 가능성을 확인한다(`wbs 0.6.3`).

| 항목 | 결정 사항 | 채택 사유 및 가이드 |

- **참고 사례에서 가져올 점** (원문 설계 기준): Ticketmaster의 동적 좌석맵 조작과 수 초 주기로 새로 바뀌는 SafeTix 다이내믹 바코드 구조, Cloudflare Waiting Room의 20초 주기 자동 새로 고침 진행률 안내 UI를 적극적으로 가져다 쓴다. AWS Virtual Waiting Room의 serving(현재 입장 번호) 방식은 서버의 차례 계산에 쓰고 화면에는 내지 않는다(추천 적용 2026-10-28, 기술 검토 낮음-103). 대기열 화면에는 내 번호와 현재 입장 번호를 내지 않고 앞 인원과 예상 대기만 보인다(ADR-0060).
- **참고 사례 분석과 도용 방지 규칙** [보완, 2026-10-11]: 외부 참고 사례 서비스는 엔지니어가 공개된 웹/앱 화면을 직접 눈으로 보고 일반적인 UX 패턴(정보 구조, 화면 밀도, 플로우)을 배우고 참고하는 데만 쓴다. 자동화된 크롤러, 스크레이퍼, 토큰 추출기로 데이터를 모으는 일과, 다른 회사의 브랜드, 로고, 페이지 레이아웃, 독점 그래픽 자산을 무단으로 복제하는 일은 금지한다. 인터파크·야놀자(NOL) 서비스 이용약관은 제23조(이용자의 의무) ④ 제15호에서 사전 서면 허가 없는 자동화 수단·수동 프로세스로 콘텐츠를 모니터링·복제·수집·확인하는 것을, 같은 항 제20호에서 사전 서면 승인 없이 브랜딩·페이지 레이아웃·디자인을 사용·복제·전시·미러링·프레이밍·딥링크하는 것을 금지한다(2026-09-29 시행본, 2026-10-14 원문 확인. 2026-10-11 기록의 '제15조·제20조'는 조항 표기를 잘못 적은 것이라 고쳤다). 다른 회사 서비스에도 같은 기준을 적용한다. **예외(홈 구조)**: 소유자는 제20호의 위험(특히 페이지 레이아웃)을 알고 홈(SCR-001)의 섹션 구조를 NOL 티켓 메인에서 따르기로 했다(소유자 결정 2026-10-14, ADR-0063). 따르는 것은 섹션 순서·배치·크기 비율뿐이다. NOL의 로고·이미지·문구·배지 이름·아이콘 그림·색은 쓰지 않고, 보이는 모습은 피켓(SEED 토큰, 인디고)으로 그린다. 섹션 내용은 피켓 기획에 있는 기능만 넣고, NOL에만 있는 기능(포인트·결제 혜택, 타임딜·할인, 영상 클립, 쿠폰·특가)은 넣지 않거나 피켓 기능으로 바꾼다. 관찰은 사람이 공개 화면을 보고 배치를 말로 적는 데 그치고, 자동 수집·스크린샷 저장은 하지 않는다(제15호). 남는 위험은 `planning/01 §5.2`에 적었다. 공연 상세(SCR-002)의 2단 배치·섹션 바로가기·안내 모달도 NOL 상세 화면을 보고 정했으므로, 같은 규칙(구조만 따르고 시각·문구·기능은 피켓)을 적용한다. 디자인 토큰(색·글자 크기·간격 같은 디자인 값에 이름을 붙여 정해 둔 것)을 뽑아 검증하는 도구는, 피켓이 직접 배포한 결과물이 정해 둔 디자인에서 어긋났는지(디자인 드리프트) 점검하는 내부 CI/CD(코드를 올릴 때마다 자동으로 검사하고 빌드해 배포하는 과정) 용도로만 쓴다. 스타일 기준의 최종 확정은 `00-summary §7` 추가 요청(2026-10-11) NOL·SEED 행의 결정(`ADR-0040`)을 따른다.
- **배제해야 할 다크 패턴**: Ticketmaster가 겪었던 대기열 불투명성 논란(순번 배정 기준이 모호한 설명), '선착순'이라는 속이는 표현(`POL-004`), 교묘한 다크 패턴(선택 동의를 필수처럼 꾸미기, 되돌릴 수 없는 취소/탈퇴 처리를 확인 절차 없이 바로 실행하기), 사용자의 불안을 부추기는 꾸며 낸 마케팅 연출('마감 임박', '잔여 1석' 깜빡임 효과 등)을 모두 뺀다. 홈의 '지금 판매 중'이 보여 주는 남은 판매 기간도 글자로만 쓰고, 깜빡임·재촉 배지를 붙이지 않는다(ADR-0063).

## 4. 지원 플랫폼, 브레이크포인트, 다크 모드

- **지원 플랫폼 기준**: `NFR-019`를 따른다(추천 적용, 2026-10-09). 소비자 웹은 모바일 퍼스트 원칙을 적용하고, 웹 표준 Baseline의 'Widely available' 기능을 기본 스펙으로 쓴다. 카카오톡이나 인스타그램 같은 인앱 브라우저에서는 공연 탐색과 상세 조회 단계까지만 지원한다. 대기열 로비에 들어가기 전에 그 기기의 기본 외부 브라우저(iPhone·iPad는 Safari, Android는 Chrome이나 삼성 인터넷, Windows는 Edge나 Chrome, Mac은 Safari나 Chrome. Whale도 지원 대상, NFR-019)로 안전하게 옮기도록 안내한다(SCR-058, ADR-0063). 파트너 콘솔과 관제 콘솔은 데스크톱(해상도 1280×800 이상에서 기본 밀도)을 기준으로 설계하되, 태블릿과 휴대폰(폭 360px부터)에서도 쓴다. 태블릿은 데스크톱과 기능이 같다. 휴대폰에서는 보기·이미 요청된 일의 승인·안전 쪽 조치와 공연 당일 현장 운영, 정산서 내려받기·정산 이의, 반품 도착 확인, 내 계정 보안 설정(재인증)까지만 하고, 나머지는 '태블릿이나 데스크톱에서 합니다' 안내로 대신한다(소유자 결정 2026-10-14, `ADR-0061`, 화면별 범위는 `design/d5 §3.9`). 게이트 스캐너는 사내에서 승인한 관리형 Android 휴대폰·태블릿만 쓴다.
- **반응형 브레이크포인트**(중단점: 화면 배치가 바뀌는 폭. 추천 적용 2026-10-28, 기술 검토 중간-096. 처음 값은 2026-10-09 추천 적용의 360·768·1024·1440px였다): SEED 값을 그대로 쓴다. `sm` 480px, `md` 768px(태블릿과 스캐너 가로 모드), `lg` 1280px(데스크톱 기본 배치가 시작되는 폭. 콘솔의 데스크톱 기본 밀도 1280×800과 같다), `xl` 1440px(관제 콘솔 다중 모니터링 패널)이다. SEED 부품의 반응형 속성(Box의 `hideFrom`, 반응형 스타일 값, `ResponsiveDialog`)과 SEED가 미리 만든 CSS의 매체 질의(입력 칸·선택 상자의 `responsive` 크기, 레이아웃 폭)는 SEED 값에서 바뀐다. 매체 질의는 CSS 변수로 덮어쓸 수 없다. 그래서 피켓 값을 따로 두면 Tailwind의 `sm:`·`lg:`와 SEED 부품이 360~479px와 1024~1279px에서 서로 다르게 바뀐다. 배치는 셋에 고밀도 하나다. 휴대폰 배치는 `md` 미만, 태블릿 배치는 `md` 이상 `lg` 미만(768~1279px. 가로로 든 태블릿과 작은 노트북이 여기 든다), 데스크톱 배치는 `lg` 이상, 고밀도는 `xl` 이상이다. `sm` 480은 배치를 바꾸지 않고, 큰 휴대폰의 작은 조정에만 쓴다. 휴대폰 시안은 폭 360px로 그린다. 360은 그리는 기준 폭이고 중단점이 아니다. 화면 문서(design/d3·d5)에서 배치를 부르는 'sm'·'sm 360'은 휴대폰 배치, 'md'는 태블릿 배치, 'lg'는 데스크톱 배치, 'xl'은 고밀도를 뜻한다. 파트너 콘솔과 관제 콘솔은 휴대폰 배치(메뉴 서랍, 표는 카드 목록, 관제는 아래 탭 막대), 태블릿 배치(메뉴 서랍, 위젯 2열, 표는 가로 스크롤 상자), 데스크톱 배치(왼쪽 내비)를 쓰고, 1440px 이상에서는 고밀도 배치로 넓어진다(`ADR-0061`). 게이트 스캐너 태블릿은 `md` 세로 배치다. 토큰 값은 `tokens.json`의 `breakpoint` 항목에 있다.
- **재배치 하한**(추천 적용 2026-10-28, 기술 검토 높음-28): 중단점은 배치가 바뀌는 폭이고, 화면이 깨지지 않아야 하는 가장 좁은 폭은 따로 둔다. 소비자 웹과 두 콘솔의 모든 화면은 폭 320 CSS px(CSS px는 브라우저가 배치에 쓰는 픽셀 단위다. 1280 화면을 400% 확대하면 이 폭이 된다)까지 두 방향 스크롤 없이 쓸 수 있어야 한다(WCAG 1.4.10). 360보다 좁은 폭에서는 가장 작은 배치를 그대로 쓰되 깨지지 않게 한다. 두 방향 배치가 필요한 표·좌석맵·좌석맵 에디터·그래프는 예외이고, 그 부분만 상자 안에서 두 방향으로 밀어 본다. 만드는 규칙은 design/d2 §1, 점검 기준은 design/d4 §1 #18이다.
- **뷰포트 높이 단위**: 모바일에서 대기실을 전체 화면으로 그릴 때 브라우저 주소창이 줄었다 늘었다 하는 변화에 안정적으로 맞추려고 `100dvh`와 `svh` 단위를 쓴다(원문 9장).
- **다크 모드 운영 방침**: 중앙 관제 콘솔은 데스크톱 배치(`lg` 이상)에서 관제실 조명과 엔지니어의 눈 피로를 생각해 다크 모드를 기본으로 쓴다. 휴대폰·태블릿 배치는 OS의 테마 설정을 따른다. 자리를 비운 운영자가 밝은 곳이나 야외에서 휴대폰으로 상태를 보고 승인하며(`ADR-0061`), 밝은 테마가 더 잘 읽히는 사람도 있기 때문이다. 운영자는 내 계정(`/me`)의 [화면 테마](자동·다크·라이트)로 바꿀 수 있다. 자동이 처음 값이고, 데스크톱 배치는 다크, 휴대폰·태블릿 배치는 OS 설정이다. 고른 값은 그 브라우저에만 둔다. 토큰은 라이트·다크가 모두 있어 명도 대비 검증(design/d2 §5)은 그대로 쓴다(추천 적용 2026-10-28, 기술 검토 낮음-104). 소비자 웹과 파트너 콘솔은 사용자 OS의 시스템 테마 설정을 자동으로 따른다. 게이트 스캐너는 강한 햇빛이 바로 내리쬐는 야외에서도 잘 보이도록 라이트 모드로 고정해 운용한다(추천 적용, 2026-10-09).
- **다국어 국제화 (i18n)**: 한국어(ko), 영어(en), 일본어(ja), 중국어 간체(zh) 4개 언어를 소비자 웹에서 지원한다(`NFR-024`). 구매는 언어와 관계없이 한국 휴대폰 본인확인이 필요하므로, en·ja·zh 화면은 공연 상세의 예매 버튼 가까이와 로그인 화면에 이 조건을 한 줄로 미리 알린다(`POL-001`, docs/frontend.md §5.12, 추천 적용 2026-10-28, 기술 검토 중간-113). 파트너·관제·스캐너는 v1에서 한국어만 내되 문구 키 구조는 같게 둔다(ADR-0079 결정 29). 언어마다 다른 문자열 길이에 맞추려고, 액션 버튼과 배지 컴포넌트는 고정 픽셀 폭 지정을 금지하고 콘텐츠 너비 기반(Intrinsic Width)으로 늘어나게 만든다. 팬 화면의 날짜·시간은 공연장 현지 시각으로 쓰고, 기기 시간대가 다르면 기기 시각을 함께 쓴다(`NFR-024`). 파트너·관제 콘솔은 시간대를 붙인 KST, 로그는 UTC다(`ADR-0060` 결정 4). 언어는 주소 접두로 나눈다(한국어 기본 주소, `/en`·`/ja`·`/zh`, hreflang, 자동 이동과 언어 쿠키 없음, `ADR-0060` 결정 3). 쿠키는 브라우저가 사이트별로 저장했다가 요청마다 함께 보내는 작은 값이다.
- **그리드 레이아웃 너비** (`ADR-0040`): SEED Design의 레이아웃 가이드라인을 따른다. 소비자 웹 콘텐츠의 최대 너비는 1040px, 공연 탐색과 좌석맵 캔버스 영역은 최대 1280px로 정한다. 데스크톱 거터는 24px, 외부 마진은 32px를 쓴다. 홈(SCR-001)의 본문은 최대 1240px(배너 슬라이드 폭)이고, 화면이 1240px + 양쪽 외부 마진보다 좁으면 외부 마진 32px를 지키고 본문을 줄인다(1280px 화면에서 1216px, 추천 적용 2026-10-14, ADR-0063). 파트너와 관제 콘솔은 SEED 대시보드 레이아웃을 써서, 중밀도 영역은 12열 1040px 그리드를, 관제 종합 패널은 고밀도 전체 화면(100% 폭)을 쓴다. 콘솔의 휴대폰 배치는 본문 1열·바깥 여백 16px(관제 12px), 태블릿 배치는 8열·바깥 여백 24px이다(`ADR-0061`).

## 5. 접근성 목표

- WCAG 2.2 AA 기준 위반 0건을 목표로 한다(원문 설계, `NFR-020`). 자동 접근성 검사 도구(axe-core)로 계속 검증하고, 시각장애인용 화면 낭독기(NVDA, VoiceOver. 화면의 글자를 소리로 읽어 주는 프로그램) 환경에서 하는 수동 테스트 시나리오도 정기적으로 한다.
- HTML5 Canvas로 그린 좌석맵은 화면 낭독기가 그림 요소를 직접 읽을 수 없다. 그래서 같은 화면 안에 '구역 → 열 → 좌석 번호' 순서로 키보드 방향키 탐색이 가능한 접근성 텍스트 목록과 '자동 좌석 배정' 버튼을 같은 위계로 기본 제공한다.
- 대기열의 앞 인원·예상 대기와 좌석 홀드 남은 시간은 `aria-live` 속성으로 소리 내어 알린다. 다만 알림이 한꺼번에 쏟아지는 것을 막으려고 안내 횟수를 줄인다(스로틀링: 대기열은 앞 인원과 진행 막대를 합쳐 1분에 한 번, 좌석 홀드는 만료 1분 전에 한 번, design/d4 8번). 로비(오픈 전 대기실)의 오픈 카운트다운은 남은 5분·1분·10초에 한 번씩만 읽는다. 그 사이의 남은 시간은 사용자가 화면 낭독기의 읽기 커서나 초점을 카운트다운으로 옮기면 그때 읽는다. 카운트다운 요소의 `role="timer"`는 기본으로 바뀔 때마다 읽지 않으므로(WAI-ARIA 1.2), 이정표 문장은 따로 둔 `aria-live="polite"` 영역이 읽는다. 로비는 기본으로 오픈 10분 전에 열리므로 30초마다 읽으면 원칙 안내·공지를 읽는 사이에 약 20번 끼어든다(추천 적용 2026-10-28, 기술 검토 낮음-102). 좌석 홀드는 남은 시간을 표시하고, 1회 연장 컨트롤을 반드시 제공한다. WCAG 2.2.1(Timing Adjustable)의 연장 방식은 만료 전 경고와 10회 이상 연장을 요구하므로 '1회 연장'만으로는 맞지 않는다. 좌석 홀드와 구매 세션 최대 체류는 온세일(판매가 열리는 시각 앞뒤로 접속이 몰리는 기간)이라는 실시간 경쟁에서 다른 사람이 살 좌석과 입장 자리를 묶어 두는 제한이라 2.2.1의 필수 예외(Essential, W3C 해설의 온라인 티켓 구매 예)로 본다. 경쟁 판매라는 점에서 실시간 예외로도 읽히지만, 근거로 드는 예외는 필수 예외다(기술 검토 낮음-154). 관리 계정 유휴 만료와 구매 세션 무활동 만료는 만료 전 경고와 [계속 사용]·[계속하기] 버튼으로 연장한다(ADR-0060).
- 모든 좌석 상태는 색각이상 사용자를 생각해 안전한 색상 팔레트와 시각적 패턴(점박이, 빗금, 아이콘)을 반드시 함께 표시한다(WCAG 1.4.1). 명도 대비는 일반 본문 글자 4.5:1 이상, 큰 글자 3:1 이상, 핵심 그래픽 인터페이스 요소 3:1 이상을 지킨다.
- 시스템의 움직임 줄이기(`prefers-reduced-motion: reduce`) 설정이 켜져 있으면, 위치 이동이나 크기 변형 애니메이션을 부드러운 불투명도(opacity) 전환으로 자동으로 바꾼다. '곧 입장합니다'처럼 글자가 하나씩 나타나는 모션은 원래 문장을 화면에서만 숨긴 글(눈에는 안 보이고 화면 낭독기는 읽는 `visually-hidden` 클래스)로 두고, 글자 하나씩 그리는 span 묶음에는 `aria-hidden="true"`를 붙여 화면 낭독기가 같은 내용을 겹쳐 읽는 것을 막는다. 바깥 span·div에 `aria-label`을 다는 방식은 쓰지 않는다. 역할이 없는 span·div(ARIA의 `generic`)는 이름을 받을 수 없어 `aria-label`이 금지되고, 낭독기가 무시할 수 있기 때문이다. `aria-label`은 이름을 받는 역할(버튼·링크·제목·랜드마크 등)에만 쓴다(추천 적용 2026-10-28, 기술 검토 중간-100).
- 마우스와 터치 대상의 최소 클릭 영역은 24×24px 이상으로 한다. 모바일 주요 액션 버튼(좌석 홀드, 결제하기, 티켓 스캔)은 한 손으로 조작하는 환경을 생각해 터치 대상을 최소 44×44px 이상으로 잡는다 [보완]. 게이트 스캐너는 방한 장갑을 낀 손으로도 누를 수 있게(§1 [가정]) 현장에서 누르는 주요 버튼([예외 통과]·[확인 스캔]·[지금 동기화]·[스캔 시작])을 높이 56px 이상으로, 버튼 사이를 16px 이상으로 잡는다 [가정, wbs 5.7.1 현장 검표 시험에서 장갑을 끼고 눌러 보고 확정]. 44px는 대략 손가락 끝 하나 크기라 장갑 낀 손에는 작기 때문이다(추천 적용 2026-10-28, 기술 검토 낮음-111).
- WCAG 2.2 AA 가운데 배치·글자·키보드·입력에서 놓치기 쉬운 기준도 목표에 넣는다(추천 적용 2026-10-28, 기술 검토 높음-28): 재배치(1.4.10, 폭 320 CSS px에서 두 방향 스크롤 없음), 글자 확대(1.4.4, 200%에서 내용·기능을 잃지 않음), 글자 간격(1.4.12, 줄 높이 1.5배·문단 뒤 2배·글자 사이 0.12배·단어 사이 0.16배에서 잘림 없음), 한 글자 단축키(2.1.4, 끌 수 있고 입력 칸에 초점이 있으면 동작하지 않음), 초점 가림(2.4.11, 고정 머리·하단 바가 초점을 다 가리지 않음), 도움말 위치(3.2.6, 여러 화면에 되풀이되는 고객센터 링크는 같은 순서), 다시 입력(3.3.7, 같은 과정에서 앞서 넣은 값을 채우거나 고르게 함), 접근 가능한 인증(3.3.8, 붙여넣기·비밀번호 관리자 허용). 기준마다의 통과 기준과 막는 자동 장치는 design/d4 §1 #18~#25에 둔다.
