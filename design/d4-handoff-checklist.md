# D4. 핸드오프 체크리스트

- **독자와 용도**: 제품 디자이너가 프로토타입 UI 시안을 프론트엔드 개발자에게 넘기기(핸드오프) 전, 그리고 프론트엔드 개발자가 구현을 마치고 코드 리뷰를 요청하기 전에 같은 기준표로 서로 점검할 때 쓴다. 체크리스트 항목은 표준 핸드오프 템플릿에 이 프로젝트의 핵심 디자인 원칙(`design/d1-brief.md`)과 운영 정책(`planning/03-policies-glossary.md`)에서 뽑은 필수 요건을 더해 만들었다.
- **원문 출처**: 설계서 13장(웹 접근성 국제 기준인 WCAG 2.2 AA, 명도 대비, 색상과 시각 패턴 함께 쓰기), 9장(모션 접근성), 7장(폼 입력 UX 규칙), 6장(디자인 토큰 단일 소스 원칙), `POL-004`·`006`·`013`·`024`(고객에게 보이는 고지 문구).
- **기준 기획 버전**: v1.0. 점검 세부 항목은 빠져 있던 핸드오프 기준을 정리한 것이므로 전체에 [보완] 표기를 붙인다.

## 1. 모든 화면 공통 체크리스트

| # | 점검 항목 | 구체적 통과 기준 |
| --- | --- | --- |
| 1 | 5대 표준 상태와 화면별 특수 상태가 모두 설계되었는가 | 기본(Default), 로딩(Loading), 빈 화면(Empty), 에러(Error), 권한 없음(Forbidden)의 5대 UI 상태와 화면별 특수 라이프사이클 상태(stale, soon, expired, degraded, offline)를 미리 모두 정의해 두어야 한다. |
| 2 | 모든 시각 속성(색상, 간격, 타이포그래피)이 토큰(색·글자 크기·간격 같은 디자인 값에 이름을 붙여 정해 둔 것)에 연결되었는가 | 원시 색상 값을 코드에 바로 적는 하드코딩이 0건, 임의 픽셀(px) 값을 인라인 스타일로 쓰는 경우가 0건이어야 한다. `tokens.json`에 정의된 시맨틱 토큰(space, size, typography)만 참조해야 한다. |
| 3 | 본문 텍스트 명도 대비 기준을 충족하는가 | 일반 본문 텍스트는 4.5:1 이상, 큰 텍스트(24px 이상 또는 19px 이상 볼드)는 3.0:1 이상의 명도 대비를 라이트 모드와 다크 모드 양쪽에서 모두 충족해야 한다. 토큰 값을 고치면 `design/d2 §5`의 상대 휘도 계산표로 다시 검증해 반영해야 한다. |
| 4 | 핵심 그래픽 UI 요소 명도 대비 기준을 충족하는가 | 폼 테두리선, 아이콘, 키보드 포커스 링, 조작 가능한 좌석 요소는 배경과의 명도 대비가 3.0:1 이상이어야 한다. |
| 5 | 마우스 클릭과 모바일 터치 타깃 영역이 충분한가 | 모든 조작 요소는 최소 24×24px 이상의 클릭 영역을 가져야 한다. 모바일의 주요 액션 버튼인 좌석 홀드(결제하는 동안 다른 사람이 가져가지 못하게 좌석을 잠시 잡아 두는 것)·결제하기·바코드 스캔·로비 입장은 최소 44×44px 이상의 터치 타깃을 확보해야 한다. |
| 6 | 키보드 포커스 탐색 순서와 시각적 포커스 링이 유효한가 | DOM 트리 구조 순서와 화면의 시각적 읽기 순서가 같아야 한다. 키보드 Tab으로 옮길 때 포커스 링이 선명하게 보여야 한다. 모달 다이얼로그는 포커스 트랩(Focus Trap)을 적용하고, 닫은 다음에는 포커스를 트리거 요소로 되돌려야 한다. |
| 7 | 모든 사용자 행동을 키보드만으로 끝까지 해낼 수 있는가 | 마우스 드래그 앤 드롭 조작(가격 등급 순서 바꾸기, 파트너 좌석맵 편집 등)에는 같은 기능을 하는 키보드 조작 대안(위/아래 방향키 또는 조작 버튼)을 두어야 한다. |
| 8 | 보조기기인 화면 낭독기(화면의 글자를 소리로 읽어 주는 프로그램)용 레이블이 누락 없이 제공되는가 | 아이콘만 있는 버튼에는 `aria-label`을 분명히 선언해야 한다. 내용이 바뀌는 라이브 영역(로비 카운트다운은 30초 간격, 대기열의 앞 인원·진행 막대는 합쳐서 1분에 한 번(ADR-0063), 좌석 홀드 타이머는 만료 1분 전 시점에만 낭독)은 알림 빈도를 조절해야 한다. |
| 9 | 시스템의 움직임 축소 설정을 충실히 반영하는가 | `prefers-reduced-motion: reduce` 설정을 감지하면 모든 공간 이동 애니메이션이 부드러운 불투명도(opacity) 전환으로 자동으로 바뀌어야 한다. 모션에 쓰는 속성은 `transform`과 `opacity`만으로 한정해야 한다. |
| 10 | 안내 문구가 용어 사전과 UX 라이팅 가이드라인을 따르는가 | 기획 문서(`planning/03-policies-glossary.md`)의 공식 용어 사전과 `design/d2 §4` 라이팅 규칙을 따라야 한다. 특히 셔플(순번을 무작위로 섞는 것)이나 하이브리드 대기열을 쓰는 공연에서 '선착순'이라는 기만적 표현이 0회여야 한다. |
| 11 | 법정 의무 고지 문안이 원래 모양 그대로 정확히 실렸는가 | 대기열 정렬 방식 법정 고지(`POL-004`), 부정구매·부정판매 형사처벌·과징금 법정 고지(`POL-024` 라목), 부정 게시물 노출 제한 고지(다목), 통신판매중개자(직접 팔지 않고 판매자와 구매자의 거래를 알선하는 사업자) 고지와 판매자 정보(`POL-037`)가 글자 그대로 실려야 한다. 법정 고지는 안내 모달로만 숨기지 않고 본문에 늘 보여야 한다(공연 상세의 정렬 방식·판매 조건 요약·라목 고지·판매자 줄. 대기열은 화면 아래 '순번 안내 ›' 시트에 전문, ADR-0063). 자동화된 시스템 결정 안내(`POL-006`)는 고정 문안이 없으므로, 필수 내용(자동으로 확인된 사실, 설명 요청·재검토 신청 권리)이 빠짐없이 들어갔는지 확인한다(문구는 planning/04 SCR-009). |
| 12 | 에러 메시지가 표준 2단계 구조를 갖추었는가 | 모든 오류 문구는 '[무엇이 문제인가] + [어떻게 해결하는가]' 구조를 갖추어야 한다. 과금이 없는 실패(payment §4에서 0원으로 끝난 실패)의 안내문에는 "요금은 청구되지 않습니다"를 붙여야 하고, 결과 불명·자동 취소 안내에는 쓰지 않는다(`design/d2 §4`). |
| 13 | 새 UI 컴포넌트가 디자인 시스템(D2)에 공식 등록되었는가 | 새 컴포넌트는 CMP 식별자를 받고 Storybook 스토리(모든 상태와 variant를 담는다)를 등록하고, Storybook 접근성 애드온(`addon-a11y`) 검사를 오류 없이 통과해야 한다. |
| 14 | 다크 모드와 라이트 모드 환경이 모두 검증되었는가 | 중앙 관제 콘솔은 상시 다크 모드 환경에서 검증되어야 한다. 소비자 웹과 파트너 콘솔은 라이트 모드와 다크 모드 두 환경 모두에서 시각적 결함이 없음을 입증해야 한다. |
| 15 | 4개 언어(ko, en, ja, zh) 환경에서 텍스트 오버플로우가 없는가 | 한국어, 영어, 일본어, 중국어 번역을 적용했을 때 고정 폭 때문에 버튼과 배지의 텍스트가 잘리는 일이 없어야 한다(내용 너비에 맞춰 늘어난다). 날짜와 통화 표기는 표준 `Intl` API(프로그램끼리 요청과 응답을 주고받는 창구) 형식을 따라야 한다. |
| 16 | SEED Design(당근이 공개한 디자인 시스템) 기반 컴포넌트를 우선 재사용했는가 | `design/d2 §1.1` 대응표의 'SEED 순수 활용'과 'SEED 기반 피켓 커스텀 확장' 항목에 적힌 컴포넌트는 직접 구현하는 대신 `@seed-design/react`를 바탕으로 구성해야 한다. 브랜드 역할색과 텍스트 색상은 피켓 토큰으로 덮어쓰되(`ADR-0040`), 당근 브랜드 자원 사용은 0건이어야 한다. |
| 17 | 반응형 브레이크포인트에서 불필요한 가로 스크롤이 생기지 않는가 | 정해 둔 브레이크포인트(360, 768, 1024, 1440px) 전 구간에서 비정상적인 가로 스크롤이 생기지 않아야 한다(파트너와 관제 콘솔도 360px부터 같다. 1280×800은 데스크톱 기본 밀도, ADR-0061). 모바일 대기실 화면은 `100dvh`를 충족해야 한다. |

## 2. 화면 유형별 추가 점검

| 대상 화면군 | 상세 점검 요건 |
| --- | --- |
| 대기실 (`SCR-007`, `SCR-008`) | 오픈 전 로비에서는 순번으로 오해할 수 있는 임의의 숫자가 보이지 않아야 한다. 내 앞 대기 인원수는 반올림 없는 정확한 실제 값으로 보이고, 내 번호와 현재 입장 번호는 보이지 않아야 한다(ADR-0060 결정 2). 다른 기기·탭에서 이미 참가했으면 처음 기기에서 계속하라는 안내와, 이전 참가를 취소하고 다시 참가하는 확인 대화상자(오픈 뒤는 새 순번)가 있어야 한다(ADR-0060 결정 1). 배터리 15% 이하의 저전력 모드에 들어가면 모든 애니메이션이 꺼져야 한다. 좌석 자동 배정 공연의 희망 조건 카드(CMP-057)는 키보드만으로 입력·수정할 수 있어야 하고, 저장했는지를 시각 표시와 텍스트로 함께 알려야 한다. 대기열 기본 화면은 앞 인원·진행 막대·예상 시간·대기 취소 네 가지뿐이고 등급별 매진 현황이 없어야 한다. 진행 막대는 0~100% 안에 있어야 한다. 처음 앞 인원이 0이면 100%다. 더 오래된 대기 상태 파일 때문에 앞 인원이 늘어 보이면 실제 값대로 물러나야 한다. 같은 탭에서 새로고침해도 처음 앞 인원(세션 저장소)이 남아 있어야 한다. 모션 축소·저전력에서는 효과 없이 값만 바뀌고, `aria-valuetext`는 "앞에 N명, 약 M분 남음"이어야 한다. '순번 안내 ›' 시트에 POL-004 문구와 POL-024 라목 고지가 접히지 않고 있어야 한다(ADR-0063). 그 회차의 판매 종료(공연 시작 24시간 전) 뒤에는 대기 화면이 ended("판매 시간이 끝났습니다")로 바뀌고 폴링(정해진 간격으로 다시 물어보는 방식)이 멈춰야 하며, 사전 셔플 공연의 만료 화면도 다른 공연과 같은 [다시 줄 서기] 문구여야 한다(ADR-0064). 번들(브라우저가 내려받는 코드 묶음) 크기는 Gzip 기준으로 JavaScript 50KB 이하, CSS 10KB 미만으로 엄격히 유지해야 한다. |
| 좌석 선택 (`SCR-010`) | 좌석의 6대 상태는 색상, 시각 패턴, 텍스트의 3중 신호로 분명하게 구별되어야 한다(처음 그림의 점유 좌석은 '선택 불가', 휠체어석은 다른 상태와 함께 그리는 속성, seat-hold §2). 주문서를 만들기 전 무활동 4분 [가정]이 되면 경고 대화상자(`role="alertdialog"`, 초점은 [ 계속하기 ])가 떠야 한다(ADR-0060 결정 7). 비활성 좌석(타인 홀드, 이미 판매, 판매 불가)은 WCAG 1.4.11의 비활성 예외 조항을 적용받지만, 빈 좌석과의 명도 차이는 뚜렷해야 한다(`design/d2 §5`). 화면 낭독기용 대안 컴포넌트인 SeatList로 좌석 탐색부터 홀드까지 혼자 끝낼 수 있어야 한다. 처음 그림은 전체 배치(구역 색·상태)이고, 확대·축소는 휠·핀치 말고도 [+]·[−]·[전체 보기]로 할 수 있어야 하며(WCAG 2.5.7), 좌석이 보이는 구역만 실시간 채널을 구독해야 한다(ADR-0063). 홀드 경쟁에서 지면 가까운 대체 좌석을 추천해야 한다. 좌석 홀드 시간을 1회 연장하는 컨트롤을 제공해야 한다. 판매 종료(공연 시작 24시간 전) 뒤 새 홀드 요청에 410 `sale-ended`가 오면 판매 종료 배너가 뜨고, 이미 고른 좌석은 남은 시간 안에 결제로 이어질 수 있어야 한다(ADR-0064). |
| 주문 및 결제 (`SCR-011`, `SCR-012`) | 결제창을 그리는 영역은 두 결제사(토스페이먼츠·포트원)의 Cross-Origin Opener Policy(COOP) 가이드를 충실히 따라야 한다. CSP(페이지가 실행할 수 있는 스크립트의 출처를 정하는 브라우저 규칙)는 두 결제사 SDK와 결제창 출처만 허용하고, 결제창 복귀 주소의 결제 값은 읽은 즉시 주소창에서 지워야 한다(ADR-0044). 좌석맵 라우트의 엄격한 COOP/COEP 헤더가 결제 라우트에 끼어들지 않도록 아키텍처가 격리되어 있는지 확인해야 한다. 과금이 없는 결제 실패에는 무과금 안심 고지를 붙여야 한다(결과 불명은 "중복 청구는 발생하지 않습니다"). 결제사 전환 뒤 다시 시도할 때는 다른 결제 대행사로 결제한다는 안내(CMP-027 `pg-switched`)를 보여야 한다. |
| 마이 티켓 월렛 (`SCR-013`) | 인터넷이 완전히 끊긴 비행기 탑승 모드에서도 휴대폰 안에서 Dynamic QR 코드가 제대로 만들어지고 갱신되는지 확인해야 한다. QR 이미지 대체 텍스트에 티켓 ID를 적고, PWA(설치형 앱처럼 쓰는 웹 앱) 홈 화면 추가 바로가기 안내를 제공해야 한다. |

| CS 처리함·승인 업무·회차 취소·판매 승인·정산 지급 (`SCR-045`~`SCR-049`) | 요청자 본인 화면에서는 승인 버튼이 비활성화되고 이유가 읽혀야 한다. 기한 배지는 시간과 영업일 단위를 텍스트로 구분해야 한다. 승인 업무 실행(`SCR-046`)과 회차 취소 확정(`SCR-047`) 직전 재인증과 '되돌릴 수 없음' 확인이 있어야 한다. 가려진 개인정보는 열람 사유를 입력한 뒤에만 보여야 한다. |
| 콘솔의 휴대폰·태블릿 배치 (파트너·관제 콘솔 전 화면) | 휴대폰 배치에서 `design/d5 §3.9` 범위 밖의 일은 숨기지 않고 '태블릿이나 데스크톱에서 합니다' 안내 카드와 [ 링크 복사 ]로 바뀌어야 한다. 휴대폰 승인자 화면은 요청자·사유·파라미터·dry-run 결과를 줄이지 않고 보여 주고, 승인 버튼 바로 위에 승인 대상을 한 줄로 다시 적어야 한다. 휴대폰에서는 개인정보 가림 해제 버튼이 없어야 한다. 태블릿에서는 데스크톱과 같은 일을 모두 할 수 있어야 한다. 메뉴 서랍은 포커스를 가두고, 닫으면 메뉴 버튼으로 초점이 돌아가야 한다(ADR-0061). |

| 앱 셸·전역 화면 (CMP-065, SCR-059) | 네 앱 모두 로그인한 화면이면 어디서나 로그아웃에 닿아야 한다(웹 앱 보안 검증 항목 목록인 ASVS 7.4.4). 오류 화면은 원인 내부 정보를 보이지 않아야 한다. 대기실(`SCR-007`·`SCR-008`·`SCR-018`)의 집중 셸은 대기실 번들 예산 안에 들어야 한다. 세션 종료 사유별 문구가 있어야 한다(`design/d5-screen-blueprint.md` §3). 파트너·관제 셸은 유휴 만료 2분 전 [가정] 경고(`role="alertdialog"`, [ 계속 사용 ])가 있어야 하고, 유휴로 세션이 끝나면 다시 로그인한 뒤 원래 화면으로 돌아와야 한다(ADR-0060 결정 7, POL-019). |
| 재인증·알림 권한 (CMP-064, CMP-068) | 재인증 토큰이 5분을 넘으면 다시 요청해야 한다. 소셜 로그인 버튼은 제공자 가이드(색·문구·같은 비중)를 따라야 한다. 웹 푸시 권한은 사용자가 버튼을 누른 뒤에만 요청해야 한다. |

| 새 소비자·파트너 화면 (`SCR-054`, `SCR-058`, `SCR-061`, `SCR-062`, `SCR-063`) | 관심 공연·알림 화면은 오프라인일 때 저장 대기와 연결 뒤 저장을 글자로 알려야 한다(FR-019). 외부 브라우저 전환 안내는 Android·iOS·Windows·Mac의 문구를 나누고 Edge를 빠뜨리지 않아야 한다(NFR-019, ADR-0063). 내 현장 배정은 스태프 셸을 쓰고 외부 분석 스크립트를 싣지 않아야 한다. 파트너 공연 목록·개요는 판매 승인 상태·반려 사유와 재승인 배너를 글자로 보여야 한다(FR-052). |

[후기 쓰기]는 자격이 없어도 숨기지 않고, 누르면 이유를 보여야 한다. 후기 작성자는 닉네임 첫 글자와 '**', 관람 회차로만 보이고 이메일·전화번호·실명이 없어야 한다. 별점은 별 아이콘과 '5점 만점에 N점' 글자를 함께 둬야 한다. 모달은 제목 연결·포커스 가둠·Esc·뒤로 가기 닫기를 지키고, 모달 위에 모달을 겹치지 않아야 한다(`POL-042`, ADR-0063). 후기 사진마다 대체 텍스트가 있고 QR이 찍힌 사진은 올리기에서 거절해야 하며, 신고 모달과 보내기 전 확인 모달은 같은 자리에서 바꿔 열어야 한다(겹치지 않게, `POL-044`, ADR-0066). 공연 카드의 아이콘 버튼(찜·오픈 알림 종)은 44px이고 `aria-label`을 갖춰야 하며, 종 토글은 `aria-pressed`여야 한다(ADR-0066). |
| 검색 (`SCR-003`) | 소비자 웹의 검색 입력은 전역 머리의 검색창 하나뿐이어야 한다(화면 안 두 번째 입력 0개). 연관 검색어 창은 ARIA combobox(listbox·option·`aria-activedescendant`)이고 ↑↓·Enter·Esc로 조작되며, 페이지 번호의 현재 페이지에는 `aria-current="page"`가 있어야 한다(ADR-0063). |
| 본인확인 흐름 (`SCR-006`) | 본인확인기관 창은 사용자가 버튼을 누른 동작 안에서만 열리고, 서버 응답 뒤 자동으로 열리지 않아야 한다. 결과(완료·창 닫음·기관 장애·다른 계정·만 14세 미만·부스 대조 불일치·동의 없음·팝업 차단)는 부르는 화면 위의 대화상자로 보이고, 복귀 화면 `/verify/return`은 진행 표시만 보인 뒤 `next` 화면으로 돌아가야 한다(ADR-0063). |
| 좌석맵 에디터 (`SCR-022`) | 배치 층과 좌석 층을 오갈 수 있고, 미리보기는 팬 화면처럼 전체 → 확대 순서로 보여야 한다. 도형 꼭짓점과 좌석 위치를 끌지 않고 숫자 입력으로도 바꿀 수 있어야 한다(WCAG 2.5.7). 구역 도형 밖 좌석은 경고하되 저장은 막지 않아야 한다(ADR-0063). 도구 막대 네 단계([① 배치 그리기] [② 좌석 채우기] [③ 좌석 다듬기] [미리보기])가 현재 단계를 알리고, 템플릿 고르기 대화상자와 좌석 겹침 경고(저장은 막지 않는다)가 글자로 보여야 한다(ADR-0066). |

## 3. 핸드오프 산출물 요건

- 화면별 시안 링크(`design/d3-screens.md`의 '시안' 열). 지금은 `design/d5-screen-blueprint.md`의 와이어프레임 절을 가리키고, 그림 시안이 생기면 같은 칸에 더한다.
- 지원해야 하는 5대 상태별 UI 디자인 프레임(기본, 로딩, 빈 화면, 에러, 권한 없음).
- 화면별 디자인 토큰 적용 대응표 (어떤 시맨틱 토큰을 썼는지 적는다).
- 조작과 모션 명세 노트 (적용한 `motion.duration`과 `easing` 토큰 이름을 적는다).
- 웹 접근성 명세 노트 (키보드 탭 탐색 순서, WAI-ARIA 역할, 화면 낭독기 낭독 레이블).
- UI 텍스트 문구 대조표 (용어 사전과 법정 고지 문안에 100% 맞는지 검증한 결과).
