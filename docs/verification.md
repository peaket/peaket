## 1. 무엇을 어디까지 증명하나

'100만 명을 버틴다'는 한 가지 주장이 아니다. **규칙이 맞는지(Safety Invariants)**와 **양을 버티는지(Scale Extrapolation)**를 따로 증명하고 따로 표시한다(§1.1):

- **1축. 규칙 모델 검증 (Formal Verification & Invariants)**:
  - 동시성 타이밍 버그는 트래픽 규모와 무관하게 생기므로, Quint/TLA+ 명세의 모델 검사로 차례 전 입장 0건, 좌석 오버셀 0건, 이중 결제 0건 같은 핵심 불변식을 작은 범위 안의 모든 순서에서 검사한다. 결과는 '검사한 범위 안에서 위반 없음'까지만 말하고, 모델과 코드의 차이는 모델 기반 시험과 장애 기록 검사로 메운다(§2.3·§2.4·§2.5).
- **2축. 국소 실측 및 수학적 외삽 (Extrapolation Rules)**:
  - 대기 인원에 비례하는 부하는 오픈 순간의 진입, CDN의 대기 상태 조회, 셔플 결과 조회 세 곳이다. 진입은 PC에서 진입 서버 수를 늘려 가며 잰 처리량 곡선(USL)으로, 원본 서버의 대기 상태 응답은 설계 식으로 100만 값을 구해 '외삽'으로 표시한다. CDN이 받는 몫과 셔플 결과 조회는 공개 한도와 대조해 '문서 인용'으로 표시한다(§3.1, [ADR-0057](adr/0057-verification-without-full-scale-infra.md)).

### 1.1 두 질문

| 질문 | 성질 | 방법 | 실행 환경 | 결과 표시 |
| --- | --- | --- | --- | --- |
| 규칙이 맞는가(차례 전 입장 0, 오버셀 0, 이중 결제 0) | 사람 수와 상관없다. 타이밍이 맞아야 드러나는 버그가 많다 | 규칙 모델 검사(§2.1~§2.3), 모델 기반 시험(§2.4), 장애 주입과 기록 검사(§2.5) | PC | '검사한 범위 안에서 위반 없음'과 그 범위 |
| 양을 버티는가 | 대기 인원에 비례하는 부하는 세 곳뿐이다. 오픈 순간의 진입, CDN(사용자 가까운 곳에 파일을 복사해 두고 대신 응답하는 전송망)의 대기 상태 조회, 셔플(순번을 무작위로 섞는 것) 결과 조회다 | 부하 분해(§3.1), 실제 크기 측정(§3.2), 진입 처리량 곡선(§3.3), 설계 식 대조(§3.4), 외부 한도 대조(§4) | PC, 선택 보정(§6) | 실측(PC)·외삽(잰 범위의 결과를 식으로 늘려 더 큰 규모의 값을 구한 것)·문서 인용 |

### 1.2 하지 않는 것

- **100만 명 전체를 한 번에 돌리는 실측.** 100만 명 규모 온세일(판매가 열리는 시각 앞뒤로 접속이 몰리는 기간) 70분 동안의 대기 상태 조회만 약 2.2억 건이다. CloudFront(AWS의 CDN)의 한국 요청 단가(1만 건당 0.009달러)로 계산하면 약 198달러다. 소유자 지출 상한(총 5만 원)을 넘는다(ADR-0057).
- **운영·스테이징 환경의 가동.** 코드와 정적 검사까지 만들고, 환경은 띄우지 않는다(§5).

### 1.3 숫자 표시

결과 숫자는 실측(PC), 실측(클라우드), 외삽, 문서 인용, 설계 목표, 하한선 중 하나로 표시한다. 정의는 [perf-ledger.md](perf-ledger.md) §7에 있다. 외삽에는 근거 실행, 식과 계수, 측정 범위, 외삽 배수를 붙인다. 문서 인용에는 문서 주소와 확인 날짜를 붙인다.

## 2. 규칙 검사

### 2.1 대상과 지킬 약속

핵심 규칙 다섯 가지를 명세 네 개로 쓴다. '언제나 참'은 어떤 순서로 일이 벌어져도 깨지면 안 되는 약속(안전성)이다. '결국 일어남'은 멈추지 않으면 결국 끝나야 하는 일(진행성)이다. 작은 범위는 검사 시간을 보고 정한다 [가정, 0.9.1·0.9.2·0.9.3·5.2.2에서 확정].

- 시간 목표(예: 60초 안 보상, 판정 150ms)와 처리량은 이 검사로 판정하지 않는다. §3이 맡는다.
- 남는 한계로 문서에 적어 둔 틈(ADR-0056의 겹친 장애, ADR-0051의 올라오지 않은 기록)은 반례가 나오는 것이 정상이다. 그 반례가 문서에 적은 크기를 넘는지를 본다.

### 2.3 결과를 읽는 법과 한계

- 주장하는 범위는 '검사한 범위 안에서 위반 없음'까지다. 작은 범위 가설(Jackson·Vaziri, ISSTA 2000: 많은 버그가 작은 범위에서 드러난다)은 경험칙이다. 범위 밖에서만 생기는 버그는 남는다.
- TLC는 유한 모델에서만 전수 검사한다. 상태가 너무 많으면 전수 검사를 못 한다. 또 상태 지문 충돌로 일부 상태를 놓칠 수 있다(Specifying Systems 14장).
- 진행성은 공정성 가정을 적어 따로 검사한다. AWS 사례에서 진행성을 검사하지 않은 명세는 진행성 버그를 놓쳤다(CACM 58(4), 2015).
- 모델은 코드가 아니다. 모델과 코드의 차이는 §2.4가 메운다.

### 2.4 모델 기반 시험(코드에 같은 규칙)

- 명세와 같은 이름의 동작을 명령으로 만든다(명령마다 `check`·`run`·`toString`). `fc.commands`가 명령 순서를 무작위로 만들고, 실패하면 가장 짧은 순서로 줄인다.
- 실행기는 `fc.asyncModelRun`이다. 비동기 응답이 돌아오는 순서에 따라 생기는 경쟁 조건은 `fc.scheduledModelRun`과 `fc.scheduler`로 순서를 바꿔 가며 찾는다.
- 대상은 대기열 Lua와 리더 세대 확인 Lua(wbs 2.3.4), 좌석 Lua와 판매 확정 SQL(2.5.5), 결제 Saga(여러 서비스에 걸친 일을 단계별로 처리하고, 중간에 실패하면 앞 단계를 되돌리는 방식)와 웹훅 처리(2.7.6)다. 실제 Redis와 관계형 데이터베이스 PostgreSQL을 컨테이너(앱과 실행 환경을 한 묶음으로 만든 실행 단위)로 띄워 그 위에서 돌린다.
- 실패한 순서는 회귀 시험으로 고정한다. 도구는 fast-check 4.x(MIT)다.

### 2.5 장애 주입과 기록 검사

- **구성**: 로컬에서 서비스와 Redis·PostgreSQL·결제 시뮬레이터 사이에 Toxiproxy를 둔다. 지연, 끊김, 대역폭 제한, 느린 종료, 시간 초과, TCP 리셋을 넣는다. 현재 릴리스(v2.12.0)의 제어 API(프로그램끼리 요청과 응답을 주고받는 창구)에는 인증이 없으므로 루프백에만 묶는다.
- **기록**: 요청마다 시작·끝 시각, 결과(성공·실패·모름), 대기표·좌석·주문·결제 키를 남긴다.
- **판정**: 시험이 끝난 뒤 불변식 SQL(wbs 1.2.3)과 기록을 대조한다. 차례 전 입장, 같은 세대 순번 중복, 오버셀, 1인 한도 초과, 이중 결제, 60초 넘게 정리되지 않은 결제-발권 불일치를 센다. 결과를 모르는(시간 초과) 요청은 성공과 실패 둘 다 가능했던 것으로 보고 판정한다(Jepsen 방식).
- 결과는 성능 장부 실행 폴더의 `invariants.csv`와 같은 자리에 둔다(wbs 2.12.3). Jepsen의 이력 검사기 Elle는 데이터베이스 격리 수준의 이상 현상을 찾는 도구라서 그대로 쓰지 않는다. 기록한 뒤 판정하는 방법만 따른다.

### 2.7 경보 규칙 시험(ADR-0069)

경보도 코드와 같은 기준으로 시험한다. SRE Workbook 4장의 세 층을 따른다. 모두 로컬과 CI(코드를 올릴 때마다 자동으로 검사하고 빌드하는 과정)에서 돌고, 비용이 들지 않는다.

| 층 | 무엇을 보나 | 도구 |
| --- | --- | --- |

JSON이었다면 진입 주소가 회차마다 달라 사전 요청 캐시를 미리 데울 수 없었고, 같은 수의 사전 요청과 왕복 한 번이 더해졌을 것이다. 다만 부하 시험 도구 k6는 브라우저가 아니라 요청 형식만 따른다. 그래서 부하 시험은 `text/plain` 형식으로 20만 RPS의 지연을 재고(Q-T41 ⑧), '사전 요청이 없다'는 점은 브라우저 시험(Q-T41 ①, Phase 2)이 증명한다. 아직 실측 전이다.

위 표의 예매 계층 네 줄은 설계가 '대기 인원이 늘어도 입장 속도가 부하를 정한다'고 주장하는 부분이다. 그래서 PC에서 실제 크기로 잰 숫자가 곧 100만 명일 때의 숫자다. PC와 클라우드 서버의 성능 차이는 §6의 환산 계수로만 메운다.

### 3.2 실제 크기 측정(PC)

- 측정마다 CPU·메모리·WSL 설정을 `infra.txt`에 남긴다. 현재 PC는 고성능 코어와 저전력 코어가 섞인 24코어(i9-14900HX), 메모리 약 32 GB다. WSL 안에서 CPU를 고정해도 실제 코어에 고정된다는 보장이 없다. 그래서 반복 측정 사이의 편차를 함께 적는다.
- k6 가상 사용자 하나가 약 1~5 MB를 쓰므로(k6 대규모 시험 문서), 좌석 연결 5,000개를 한 발생기로 만들면 메모리가 빠듯할 수 있다. 그래서 가벼운 전용 클라이언트를 쓰거나 발생기를 나눈다.
- 결제 300 TPS는 PG(온라인 결제를 대신 처리해 주는 결제사) 시뮬레이터 어댑터로 잰다. 토스 샌드박스는 엔드포인트(API를 부르는 주소 하나)별로 분당 100건 제한이라서 쓰지 않는다(POL-026).

### 3.3 진입 처리량 곡선(USL)

- **측정**: 진입 서버를 N = 1, 2, 3, 4, 6, 8대 [가정, 6.1.1에서 확정]로 늘려 간다. 도착률을 단계적으로 올리면서, NFR-001의 SLO(요청 백 건 중 아흔아홉 건이 끝나는 시간인 p99가 200ms 이하, 오류율 0.1% 미만)를 지키는 가장 높은 도착률을 X(N)으로 적는다. 각 N의 값은 3회 측정의 중앙값이다. 이때 Redis에는 따로 코어를 주어 병목이 되지 않게 하고, Redis 한 키의 처리량은 PoC 0.5.1에서 따로 잰다.
- **적합**: C(N) = N / (1 + α(N−1) + βN(N−1)), X(N) = X(1)·C(N). α는 공유 자원을 기다리는 경합이고, β는 서버끼리 데이터를 맞추는 지연이다. N/C(N) − 1 = α(N−1) + βN(N−1)을 최소제곱으로 푼다. 점은 6개 이상 쓴다(Gunther 권장).
- **결과**: α, β, 정점 N_max = √((1−α)/β), 20만 RPS에 필요한 N, 외삽 배수(필요한 N ÷ 측정한 최대 N)를 낸다. `charts.py usl`이 계산하고, 측정 범위 밖 구간은 점선으로 그린다(tools/perf-ledger/README.md).
- **진입 용량**: min(진입 서버 N대의 X(N), Redis 한 키의 처리량).
- **판정**: 곡선이 20만에 닿지 않으면(정점이 목표 아래), 서버를 늘려도 풀리지 않는 공유 자원이 있다는 뜻이다. 이때 묶음 증가(`INCRBY`), 진입 경로 나누기, 도착 시각 쿠키(브라우저가 사이트별로 저장했다가 요청마다 함께 보내는 작은 값)를 검토한다(docs/architecture.md §9.2). 외삽 배수가 4 [가정, 6.1.1에서 확정]를 넘으면 '외삽(측정 범위의 4배 초과)'으로 표시한다. USL(서버를 늘릴 때 처리량이 덜 늘어나는 모양을 나타낸 확장성 법칙)을 만든 Gunther도 측정 범위 밖은 예측하지 못한다고 쓴다.

### 3.4 설계 식 대조와 비례 불변 곡선

- **v1 설계 식**: 원 서버의 대기 상태 파일 응답 ≈ Σ(활성 파일 ÷ 캐시 수명). 파일은 1,000명당 1개이고, 캐시 수명은 기본 1초라서 '파일 수 ÷ 1초'가 상한이다. 거리별 수명(예상 대기 1분 이내 1초, 1~5분 5초, 그 밖 10초 [가정], queue-admission §4)을 쓰면 이보다 줄어든다. CDN 안의 갱신은 '엣지 수 × 활성 파일 수 ÷ 1초'가 상한이다. 로컬 캐시는 엣지(CDN이 사용자 가까이에 둔 서버) 1곳과 같다.
- **v0 식**: 원 서버 요청 ≈ 대기 인원 ÷ 폴링 주기(폴링: 정해진 간격으로 다시 물어보는 방식. v0는 1초 폴링, docs/architecture.md §9.3 K1).
- **측정**: `local-1k`·`local-10k`·`local-100k`에서 v0와 v1을 같은 시나리오로 돌려 원 서버 요청, DB 쓰기, 좌석 화면 동시 인원을 잰다(`charts.py scale`). 대기자는 연결을 유지하지 않고 주기적으로 묻기만 한다. 그래서 사람 수만큼 연결을 만들 필요가 없고, 그들이 만드는 도착률만 만들어 낸다. 10만 명이면 예상 대기 1분 이내가 약 1,700명(폴링 주기 1초), 1~5분이 약 6,700명(5초), 나머지가 약 9.16만 명(20초)이라서 초당 약 7,600건이다. 폴링 주기는 queue-admission §4 표의 초기값이고, 위 설계 식의 캐시 수명(1초·5초·10초)과는 다른 값이다.
- **판정**: 세 점의 실측이 식의 ±10% [가정, 6.1.1에서 확정] 안이면, 식으로 계산한 100만 값을 '외삽(설계 식)'으로 적는다. 벗어나면 식을 쓰지 않고 원인을 찾는다. 다항식 맞추기는 쓰지 않는다(ADR-0057).
- **로컬 캐시 설정**: nginx `proxy_cache_lock`(새 캐시 항목은 한 요청만 채우고 나머지는 기다린다), `proxy_cache_use_stale updating`, `proxy_cache_background_update`. CloudFront의 요청 병합·Origin Shield(원본 서버인 오리진 앞에 덧붙이는 캐시 층)와 원리는 같지만 구현이 같지는 않다. 그래서 CDN의 동작은 문서 인용으로 둔다.

### 3.5 측정 정직성 규칙

1. 요청은 정해진 도착률로 보낸다(k6 `constant-arrival-rate`·`ramping-arrival-rate`). 응답을 받은 뒤 다음 요청을 보내면, 서버가 느릴 때 요청을 덜 보내게 되어 지연이 좋게 나온다. k6 문서는 이를 coordinated omission이라고 부른다.
2. 부하 발생기가 시작하지 못한 반복(`dropped_iterations`)이 하나라도 있으면 그 측정은 무효다(collect.py가 `valid: false`로 적는다).
3. 발생기 CPU는 80% 이하, 메모리는 90% 이하로 둔다(k6 권고).
4. 3회 반복의 중앙값과 편차를 적고, 예열 구간은 뺀다(perf-ledger §3).
5. 같은 PC에서 발생기와 대상을 함께 돌리면 CPU를 나눠 배정하고, 그 배치를 `infra.txt`에 적는다.

### 3.6 장시간 시험(추천 적용 2026-10-20, ADR-0070, NFR-027)

짧은 부하 시험은 시간이 지나야 드러나는 문제(메모리·파일 디스크립터·연결이 서서히 느는 누수, 응답 시간이 조금씩 늦어지는 일)를 보지 못한다. Grafana가 펴낸 k6 문서는 평균 부하 시험과 같은 세기를 몇 시간에서 며칠 동안 이어 이런 문제를 찾는 시험을 soak test라고 부른다. 그리고 스모크·평균 부하 시험 다음에 하라고 한다.

- **대상**: 오래 떠 있는 서비스다. queue-svc, purchase-svc, payment-svc, realtime-gw(웹소켓 연결 유지), Outbox(데이터베이스를 바꿀 때 보낼 이벤트를 같은 트랜잭션으로 데이터베이스 표에 먼저 적어 두고 나중에 보내는 방식) 릴레이와 Kafka(이벤트를 순서대로 쌓아 두고 여러 곳에 나눠 주는 메시지 시스템) 소비자.
- **방법**: 로컬(PC)에서 서비스를 하나씩 6시간 [가정] 돌린다. 각본은 그 서비스의 평균 부하 시험을 그대로 쓴다. 세기는 그 서비스가 SLO 안에서 견딘 최대 도착률의 50% [가정]다. 의존 저장소(Redis·PostgreSQL·Kafka)는 로컬 컨테이너로 띄운다.
- **기록**: 성능 장부 형식 그대로 남기고, `kpi`는 `NFR-027`로 적는다. 1분마다 GC 뒤 힙, RSS, 열린 FD, 활성 핸들, DB·Redis 연결 수, p99, 오류율을 시계열로 남긴다(perf-ledger §2.3).
- **판정**: 첫 30분 [가정]은 예열로 보고 뺀다. 나머지 구간에서 자원 지표마다 1차 회귀 기울기가 시작값의 시간당 1% [가정] 이하이고, 재시작이 0회, p99 변화가 10% [가정] 이내, 오류율이 SLO 안이면 통과다. 기울기 계산은 collect.py에 더한다(wbs 6.5.1).
- **비용**: PC에서 돌려 0원이다. 서비스 다섯 개 × 6시간을 클라우드에서 돌리면 지출 상한(5만 원)을 넘기므로 하지 않는다.
- **한계**: 서비스 한 대만 보므로 클러스터 규모에서만 생기는 누수(연결 수 폭증 등)와 6시간보다 긴 주기의 누수는 놓칠 수 있다. 운영에서는 자원 누수 의심 경보(docs/observability.md §5)가 같은 판정을 이어서 한다.

### 3.7 관제 실시간 표 시험(추천 적용 2026-10-20, ADR-0071, NFR-009)

NFR-009(관제 실시간 표 반영 p95 5초 미만, 누락률 0.1% 미만. p95: 백 건 중 아흔다섯 건이 이 시간 안에 반영된다는 뜻)는 이전에 시험이 없었다. 흘러드는 이벤트를 실시간으로 계산하는 Flink 안의 워터마크(이 시각보다 이른 사건은 다 왔다고 보는 시각)로 재면, 분석용 데이터베이스 ClickHouse의 반영·조회·푸시가 빠진다. 그래서 심장 박동 사건으로 끝에서 끝까지 잰다(docs/streaming.md §4.5).

- **환경**: 로컬(PC) 컨테이너로 Kafka, Flink(`ops-rt`, 버전은 docs/streaming.md §2.1), ClickHouse, ops-svc 읽기 경로, `rt-pulse`를 띄운다. 발생기는 정해진 도착률로 초당 3만 건을 보내되, 모두 한 회차에 몰아 키 쏠림이 가장 나쁜 경우를 만든다(§3.5 규칙 1). 홀드 시도·판정·대기열 집계·거래 사건은 표준 시나리오(planning/01 §3.2)의 비율로 섞는다 [가정, 4.3.9에서 확정].
- **측정**: 30분 [가정] 동안 ops-svc가 낸 `rt_freshness_seconds`의 1분 p95, 누락률(늦어서 버린 수 + 싱크가 버린 수 + 읽지 못해 거절한 수 + 생산자가 버린 수 ÷ 전체), 체크포인트(작업 상태를 주기적으로 저장해 두는 지점) 소요 시간, 중복 제거 상태 크기를 잰다. 판매 좌석·금액 누적은 발생기가 보낸 정답과 비교한다.
- **장애 주입**: 중간에 TaskManager 강제 종료(V-T13), 파티션(토픽을 나눈 칸) 하나에만 사건이 오고 나머지가 빈 상태(V-T14), ClickHouse 30초 정지(V-T15)를 넣는다.
- **판정**: 신선도 p95 5초 미만, 누락률 0.1% 미만이고, 장애 주입 뒤 누적이 정답과 같으면 통과다. 결과는 '실측(PC)'으로 적는다. AWS가 운영해 주는 관리형 Kafka(MSK)와 운영 ClickHouse의 지연은 재지 않으므로 §8 한계에 남긴다.
- **비용**: PC에서 돌려 0원이다.

| 대기열·좌석 Redis 장애 조치(AWS FIS, queue-admission Q-T13, seat-hold S-T9) | 로컬 Redis 주 노드 강제 종료로 세대 번호·카운터 건너뛰기·좌석 DB 경로를 확인한다 | 실측(PC) |
| PITR 복원 연습 | 로컬 PostgreSQL 기본 백업과 WAL 재생으로 시점 복원 절차를 연습한다 | 리허설 |
| 교차 리전 복원 | 복구 Terraform 계획과 런북(장애가 났을 때 따라 하는 절차서)을 대조하고, 걸릴 시간을 계산한다 | 모의 진행 |
| 노드 기동(Karpenter, K9) | AWS 문서 인용. 선택 보정에서도 재지 않는다(§6) | 문서 인용 |

### 5.4 IaC 검증 범위

`terraform fmt`·`validate`와 IaC 정적 검사(wbs 0.1.4)까지 한다. `plan`과 `apply`는 AWS 계정과 자격 증명이 있어야 하므로 선택 보정 때만 한다. 그래서 IaC는 '정적 검사까지 검증'으로 표시한다.

## 7. 데모

- **기본(0원)**: 로컬에서 실행한 모습을 녹화한 영상과 재현 스크립트다. 재현 스크립트는 한 명령으로 kind 클러스터 만들기, 데모 오버레이로 차트 설치, 합성 데이터 넣기, 시연 시나리오(소규모 부하, 봇 시뮬레이터 일부, 관제 명령) 재생까지 한다(wbs 0.4.3). 녹화 영상은 관제 데모 영상(7.6.1)과 함께 만든다.
- **선택**: 면접·발표 때만 몇 시간 켜는 임시 클라우드 데모다. 같은 재현 스크립트를 쓰고 TTL과 예산 경보를 건다. 구성 크기는 데모 범위에 맞춰 정한다. 실행 전에 가격표로 비용을 계산해 남긴다.
- **보여 줄 것**: 대기실·좌석·결제 흐름, 관제 명령과 감사 기록, 환경 승격·카나리·변경 동결 창(로컬 kind 데모 오버레이), 성능 장부 그래프와 규칙 검사 결과.
- **상시 데모를 두지 않는 이유**: AWS EKS(AWS가 운영해 주는 쿠버네티스)로 상시 데모를 두면 노드와 DB를 빼고도 월 약 133달러다(docs/devops.md §11). 무료 상시 VM(Oracle Cloud 무료 Arm A1)은 2026년 6월에 월 1,500 OCPU-시간·9,000 GB-시간(2 OCPU·12 GB)으로 줄었다. 한국 춘천 리전은 A1 대상에서 빠졌다. 또 7일 동안 CPU 95퍼센타일·네트워크·메모리 사용률이 모두 20% 미만이면 회수될 수 있다. 한가한 데모 서버는 이 회수 조건에 걸리기 쉽다(2026-10-13 문서 확인).
