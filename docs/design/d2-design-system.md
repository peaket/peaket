# D2. 디자인 시스템

- **독자와 용도**: 제품 디자이너가 일관된 UI 화면을 조립할 때와, 프론트엔드 엔지니어가 디자인 시스템 패키지(`@peaket/ds`)를 만들고 배포할 때 기준으로 삼는 문서다. 모든 디자인 토큰(색·글자 크기·간격 같은 디자인 값에 이름을 붙여 정해 둔 것)의 기준이 되는 단일 소스(SSOT)는 `tokens.json`이다. 이 문서는 토큰을 쓰는 원칙, 컴포넌트 명세, 조작 패턴을 정한다.
- **원문 출처**: 설계서 6장 <스타일링>, 설계서 7장 <폼 관리>, 설계서 9장 <애니메이션>, 설계서 3장 <컴포넌트 디자인 패턴>, 11장(번들 예산), 설계서 §6 각 화면별 UI 구성 요소.
- **기준 기획 버전**: v1.0.
- **표시 규칙**: 컴포넌트 카탈로그(CMP) 목록은 화면설계서의 UI 요구사항에서 끌어낸 것이라 전체에 [보완] 표시를 붙인다. 원문 설계서에 이미 적혀 있던 컴포넌트 이름(Button, SeatStatusBadge, PriceTierLegend, Countdown, SeatPicker, QueuePanel, Widget)은 원래 이름을 그대로 이어받았다. 원문의 CheckoutForm은 따로 두지 않고 SCR-011에서 CMP-025·027·009 등으로 조립한다.

## 1. 토큰 규칙

- **디자인 토대**: 당근마켓의 오픈소스 디자인 시스템인 SEED Design 3.0(Apache-2.0 라이선스)의 토큰 체계와 컴포넌트를 토대로 삼는다(`ADR-0040`, 2026-10-11 제품 소유자 최종 결정). `@seed-design/css`로 CSS 변수와 테마 시스템을 구성하고, `@seed-design/react`로 기본 UI 컴포넌트를 조립한다. 피켓 고유의 브랜드 주조색과, 웹 접근성 국제 기준인 WCAG 2.2 AA에 미달하는 일부 글자 색만 피켓 토큰으로 덮어써서 쓴다(§5 참조).
- **단일 소스 관리 체계**: `tokens.json`을 SSOT로 관리한다. 형식은 W3C 디자인 토큰 커뮤니티 그룹(DTCG)의 형식이다. 다만 값은 이전 초안의 문자열 표기('#ffffff', '16px', '200ms')로 적는다. 2025.10 판(첫 최종 보고서)은 색·치수·시간 값을 객체(`{colorSpace, components}`, `{value, unit}`)로 적게 하는데, 토큰 빌드 도구 Style Dictionary 5가 아직 그 판을 다 지원하지 않기 때문이다. 도구가 지원하면 객체 표기로 옮긴다(docs/review/open-items.md 46번). 판과 상관없이 지키는 규칙은 셋이다. 토큰·그룹 이름에 마침표·중괄호를 쓰지 않고 `$`로 시작하지 않는다(간격 `0_5`·`1_5`는 SEED처럼 밑줄). 모든 토큰은 명세가 정한 형식을 쓴다. 그래서 명세에 형식이 없는 좌석 무늬 이름은 토큰으로 두지 않고 `pattern` 그룹의 확장 칸(`$extensions`의 `com.peaket.pattern`)에 두며, 빌드가 TS 상수 `pattern.seat.*`로 만든다. 별칭(`{space.1_5}`)은 모두 풀려야 한다. 토큰 CI(wbs 0.6.1, docs/frontend.md FE-T45)가 이 셋과 형식 검사를 PR마다 돌린다. 확장 키를 역도메인 이름으로 쓰라는 명세의 권고는 새 키(`com.peaket.pattern`)에만 따르고, 먼저 있던 SEED 대응 키 `seed`와 SEED 값을 덮은 까닭을 적는 `override`는 그대로 둔다(추천 적용 2026-10-28, 기술 검토 중간-099. `override`를 이름으로 적은 것은 추천 적용 2026-11-04). `seed`의 값은 SEED 변수 경로(`$color.fg.neutral` → `--seed-color-fg-neutral`), 변수 이름 그대로(`--seed-font-family`), 중단점(`breakpoints.md`) 셋 가운데 하나다. 값은 SEED 토큰 값을 바탕으로 정하고, `$extensions.seed` 메타데이터에 원본 SEED 토큰 이름을 적는다. 빌드할 때 Style Dictionary로 CSS 변수(SEED 변수 덮어쓰기), Tailwind CSS v4 `@theme` 설정(`@seed-design/tailwind4-theme` 확장), TypeScript 상수를 자동으로 만들어 낸다. HTML5 Canvas로 그리는 좌석맵은 CSS 변수를 직접 읽을 수 없으므로 TypeScript 상수 토큰을 연결해 그린다(원문 6장).
- **원시 팔레트와 시맨틱 토큰의 엄격한 분리**: 모든 프론트엔드 UI 코드는 `color.semantic.*` 시맨틱 토큰만 참조해야 한다. 컴포넌트 스타일에서 원시 색상 토큰(`color.primitive.*`)을 직접 참조하는 것은 ESLint 린트 규칙으로 막는다.
- **SEED 스타일 속성과 화면 CSP**(추천 적용 2026-10-28, ADR-0111): SEED 부품의 스타일 속성(`p`·`gap`·`bg`·`color` 등)은 CSS 변수(`--seed-box-padding` 같은 이름 붙인 스타일 값)로 바뀌어 HTML 요소의 `style` 속성으로 나간다. 소비자 웹과 파트너 콘솔은 이것을 서버에서 그리므로, 화면 CSP(페이지가 적용할 수 있는 스크립트·스타일의 출처를 정하는 브라우저 규칙)는 `style` 속성만 `style-src-attr 'unsafe-inline'`으로 받고 `<style>` 요소는 계속 막는다(docs/frontend.md §5.14.1). 그래서 스타일 속성에는 토큰 이름과 코드에 적은 값만 넣는다. 사용자·파트너가 넣은 값은 넣지 않고, 코드에서 `<style>` 요소를 만들지 않는다. 토큰 린트가 SEED 스타일 속성에 토큰 밖의 값과 바깥 입력에서 온 변수를 넣는 것을 막는다(docs/design/d4 #2). PoC FE-T30(wbs 2.10.1)이 실패하면 서버가 그리는 부품은 SEED 스타일 속성 대신 클래스(Tailwind·SEED 레시피)만 쓴다(ADR-0111 결정 5).
- **SEED CSS 싣기**(추천 적용 2026-10-28, 기술 검토 중간-097. SEED를 쓰는 것은 소유자 결정 ADR-0040): SEED 전체 CSS(`all.css`·`all.min.css`, gzip 42.2KiB. 2026-11-04에 붙인 3.1.0은 43.9KiB)는 경로별 CSS 예산(20~30KB, docs/frontend.md §5.8)을 넘으므로 싣지 않고, 가져오면 린트가 막는다. 부품 CSS는 그 화면이 쓰는 부품의 recipe(부품마다 따로 낸 CSS)만 싣는다. `@seed-design/react` 부품은 자기 recipe 모듈을 가져오고 recipe 모듈이 자기 CSS를 가져오므로(3.0.x 패키지에서 확인), 앱이 따로 가져오지 않는다. React 밖에서 SEED 클래스를 쓸 때만 `@seed-design/css/recipes/<부품>.layered.css`를 직접 가져온다. base(색·간격 변수와 SEED 기본 규칙)는 층 판 `base.layered.css`(gzip 7.8KiB, 3.1.0은 8.2KiB)를, recipe도 층 판(`recipes/*.layered.css`)을 쓴다. 붙인 판은 `@seed-design/css` 3.1.0이다(2026-11-04, BUILD_ORDER BAS-170. `@seed-design/react` 3.1이 3.1.0 이상을 요구한다). `@peaket/ds/styles.css`가 맨 앞에서 base 층 판을 싣고, 그 뒤 피켓 토큰(`components` 층)이 같은 이름의 `--seed-*` 변수를 덮는다(추천 적용 2026-11-04). 층 판은 SEED 패키지의 내보내기 조건 `seed-layered`로 고른다. Vite(스캐너·포렌식)는 `resolve.conditions`에, webpack(관제 호스트)은 `resolve.conditionNames`에 이 조건을 넣는다. SEED의 Vite·webpack 플러그인(2.1.1)은 색 모드 스크립트와 `color-scheme` 메타를 HTML에 넣는 일만 하고 CSS는 넣지 않는다(소스에서 확인. Vite 플러그인 설명서의 'recipe 주석으로 CSS 자동 가져오기'는 2.1.1 소스에 없다). webpack 플러그인은 HTML 생성 플러그인이 있어야 돌아 Next.js에는 맞지 않는다. 그래서 Next.js 앱(웹·파트너)은 SEED 색 모드 스크립트(`@seed-design/css/theming`이 만든다)를 같은 출처 파일로 루트 레이아웃에 싣는다(묶음 A는 `'self'`, B·E·F는 그 응답의 nonce). 소비자 웹은 2026-11-05(BUILD_ORDER HOT-291)에 실었다: `public/seed-color-mode.js`(붙인 SEED 판이 만든 system 모드 스크립트 글자 그대로, `@peaket/ds/color-mode-script`, 시험이 판과 같은지 본다)를 루트 레이아웃 `<head>`에서 싣고, 키트 다크 변수(`kit-tokens.css`)와 맨 바깥 `color-scheme`(`ds.css`)이 `data-seed-user-color-scheme="dark"`에서도 다크가 된다. 그래서 소비자 웹은 운영체제 테마를 따른다(d1 §4). 대기실 경량 페이지와 파트너 콘솔은 아직 싣지 않는다.
- **CSS 층 순서**(추천 적용 2026-10-28, 기술 검토 중간-097): CSS 층(cascade layer: 규칙을 층으로 묶어 어느 쪽이 이기는지 정하는 CSS 기능)의 순서는 `@layer theme, base, seed-base, seed-components, components, utilities;` 하나로 정한다. `theme`·`base`·`components`·`utilities`는 Tailwind v4 층이고 `seed-base`·`seed-components`는 SEED 층 판의 층이다. 그래서 Tailwind 초기화 규칙(preflight, `base` 층)이 가장 약하고, SEED base(색 변수·iOS 글자 확대), SEED 부품, 피켓 부품(`components`), Tailwind 유틸 순으로 이긴다. 같은 요소에 SEED 부품 클래스와 Tailwind 유틸이 겹치면 유틸이 이긴다. 층 순서는 처음 나온 순서로 정해지므로, 이 선언은 앱이 가장 먼저 싣는 CSS 파일의 맨 앞에 둔다. 부품 CSS가 먼저 실리면 그 층이 가장 약한 층이 되기 때문이다. 피켓이 쓰는 CSS도 층 안(`components`)에 둔다. 층 밖 규칙은 모든 층을 이긴다. 예산은 size-limit의 CSS 항목으로 PR에서 지킨다. Next.js 앱의 번들러(브라우저가 내려받는 자바스크립트 묶음인 번들을 만드는 도구) Turbopack은 조건부 별칭에서 `browser` 조건만 받아 `seed-layered`를 고르지 못한다. 그래서 `turbopack.resolveAlias`로 recipe를 층 판으로 돌릴 수 있는지, 빌드 산출물의 첫 CSS가 이 층 선언으로 시작하는지를 PoC(wbs 0.6.1, docs/frontend.md FE-T36)에서 본다. 안 되면 Next.js 앱에서는 SEED 부품 CSS가 층 밖에 실려 Tailwind 유틸을 이긴다. 그때는 SEED 부품 요소에 Tailwind 유틸을 겹치지 않고 SEED 부품 속성(변형·크기·스타일 속성)으로만 모양을 바꾸며, 린트가 이를 막는다. PoC 결과(2026-11-04, BUILD_ORDER BAS-170, `tools/web-checks/seed-css/RESULT.md`): Next.js 앱도 층 판을 고른다. `@peaket/ds/seed-layered-alias`가 붙인 SEED 판의 recipe마다 층 판 파일 경로를 별칭으로 만든다(패키지 이름을 별칭 대상으로 주면 Turbopack이 앱 폴더에서 풀다 못 찾고 오류 없이 층 없는 판을 쓴다). 빌드 도구는 층 순서 선언문을 그 차례의 층 블록으로 바꾸고 Tailwind는 자기 `properties` 층을 맨 앞에 두므로, '첫 CSS가 선언으로 시작하는지' 대신 '층을 가진 첫 CSS가 여섯 층을 정한 차례로 처음 선언하는지'를 본다. Vite·webpack 앱은 CSS를 가져온 차례대로 한 파일에 잇기 때문에, 진입점이 부품을 전역 CSS보다 먼저 가져오면 그 부품 CSS의 층이 가장 약한 층이 된다. 그래서 진입점은 전역 CSS를 맨 먼저 가져온다(추천 적용 2026-11-04).
- **라이트·다크 모드 제어**: `color.semantic.light`와 `color.semantic.dark`는 같은 키 구조를 쓰고, SEED의 `data-seed-color-mode`(system, light-only, dark-only)와 `data-seed-user-color-scheme` 속성으로 실행 중에 전환된다. 관제 콘솔은 데스크톱 배치(`lg` 이상)에서 `dark-only`, 휴대폰·태블릿 배치에서 `system`이 처음 값이고, 운영자가 내 계정의 [화면 테마](자동·다크·라이트)로 바꿀 수 있다(docs/design/d1 §4, 추천 적용 2026-10-28, 기술 검토 낮음-104). 현장 게이트 스캐너는 낮에 잘 보이도록 `light-only`, 소비자 웹과 파트너 콘솔은 OS 설정을 따르는 `system` 모드를 쓴다.
- **좌석 상태의 다중 감각 표현**: 좌석 상태를 나타낼 때는 반드시 `color.semantic.*.seat.*` 색상 토큰과 `pattern.seat.*` 시각 패턴 값(tokens.json 확장 칸에서 만든 TS 상수, 위 '단일 소스 관리 체계')을 함께 쓴다. 색상만으로 예매 가능, 홀드 중(결제하는 동안 다른 사람이 가져가지 못하게 좌석을 잠시 잡아 두는 것), 판매 완료 같은 좌석 상태를 구분하는 구현은 웹 접근성 지침 위반으로 보고 엄격히 금지한다.
- **타이포그래피 스케일**: SEED의 서체 스케일을 따른다. font-size는 xs 12px, sm 14px, md 16px, lg 20px, xl 24px, 2xl 32px, display 48px(SEED t2, t4, t5, t7, t9, t12, t14 대응)로 이루어지고, line-height는 각 단계에 맞는 SEED 표준값을 대응시킨다. font-weight는 regular, medium, bold 3단계를 지원한다. 글꼴 패밀리는 SEED의 `--seed-font-family`(시스템 기본 글꼴 우선)를 기본으로 하되, Windows에서도 글자가 깔끔하게 그려지도록 Pretendard 가변 글꼴의 동적 서브셋(글자 범위별 조각 92개를 `unicode-range`로 나눈 것, 화면에 쓰인 글자의 조각만 받는다)을 직접 호스팅한다(2026-11-05 BUILD_ORDER HOT-291: 소비자 웹이 가변 글꼴 전체 2MB를 미리 받던 `next/font`를 바꿨다). 대기실 경량 페이지는 번들 예산 때문에 글꼴을 싣지 않고 시스템 글꼴을 쓴다(docs/frontend.md §5.1). 대기실 앞 인원과 게이트 판정의 핵심 숫자에는 `display` 스케일을 쓴다(로비·대기열 화면에는 내 번호와 현재 입장 번호를 내지 않는다, ADR-0060 결정 2).
- **간격, 라운드, 그림자, 모션**: 간격(spacing)은 SEED dimension(4px 그리드 기반)과 의미별 간격(global-gutter 16px, component-default 12px, nav-to-title 20px, screen-bottom 56px, between-chips 8px)을 따른다. 테두리 반경(radius)은 4, 8, 12, 16, 24px 단계로 두고, 카드와 바텀 시트에는 16px를 쓴다. 그림자(elevation)는 3단계(SEED s1, s2, s3, 다크 모드는 더 짙은 검정 그림자)로 나눈다. 모션 트랜지션은 150ms, 200ms, 300ms 길이와 SEED 표준 이징 곡선을 쓴다. 성능을 위해 `transform`과 `opacity` 속성만 바꾸고, `will-change` 속성을 함부로 쓰는 것은 금지한다. 반응형 브레이크포인트(중단점)는 SEED 값 480, 768, 1280, 1440px이다(docs/design/d1 §4, 추천 적용 2026-10-28, 기술 검토 중간-096). 토큰 빌드는 Tailwind 기본 중단점을 지우고(`--breakpoint-*: initial`) 이 넷만 만든다. 토큰 CI는 이 값이 `@seed-design/css/breakpoints`와 같은지 본다. 그래서 SEED 부품의 반응형 속성(`hideFrom`, 반응형 스타일 값, `ResponsiveDialog`)과 Tailwind 접두사(`md:`·`lg:`)가 같은 폭에서 바뀐다. 레이아웃 최대 너비는 소비자 웹 1040px(공연 탐색과 좌석맵 1280px, 홈 본문 1240px, ADR-0063), 데스크톱 거터 24px, 외부 마진 32px로 정한다. 홈 배너 슬라이드 모서리 20px은 SEED 눈금 밖의 홈 전용 값이라 토큰 `radius.banner`로 둔다(추천 적용 2026-10-20, ADR-0073).
- **재배치와 글자 확대**(추천 적용 2026-10-28, 기술 검토 높음-28): 중단점과 따로, 휴대폰 배치는 시안 기준 폭 360부터 그리되 폭 320 CSS px(1280 화면을 400% 확대한 것과 같은 폭)에서도 두 방향 스크롤 없이 쓸 수 있게 만든다(WCAG 1.4.10). 두 방향 배치가 필요한 표·좌석맵·좌석맵 에디터·그래프는 예외이고, 그 부분만 상자 안에서 두 방향으로 밀어 본다. 글자가 든 타일·배지·버튼·하단 고정 바는 높이를 고정하지 않고(최소 높이만 둔다) 넘친 글자를 숨겨 자르지 않는다. 그래서 글자 200% 확대(1.4.4)와 글자 간격 조정(1.4.12: 줄 높이 1.5배·문단 뒤 2배·글자 사이 0.12배·단어 사이 0.16배)에서도 내용이 남는다. 줄임표로 줄인 글은 상세 화면이나 펼치기로 전체를 볼 수 있어야 한다. SEED 글자 크기는 브라우저 기본 글자 크기를 따라 커지되 1.5배(`--seed-font-size-limit-max`, SEED 기본값)에서 멈춘다. 그래서 1.4.4의 200%는 화면 전체 확대로 맞추고(W3C 이해 문서가 인정하는 방법), 글자 크기 설정만으로 2배까지 키울지는 docs/review/open-items.md 43번에서 정한다. 시험은 docs/frontend.md FE-T31, 점검 기준은 docs/design/d4 §1 #18~#20이다.
- **버전 관리 및 시각 회귀 테스트**: `@peaket/ds`는 모노레포 `peaket`의 `packages/ds`에 두고 게시하지 않는다. 쓰는 앱은 `workspace:`로 잇고, 판은 저장소의 출시 태그(SemVer)를 따른다(ADR-0165). 디자인 토큰 변경이 들어간 모든 Pull Request는 Storybook 기반 시각적 회귀 테스트(Visual Regression Test)의 스크린샷 대조 통과를 필수 조건으로 둔다. 도구는 Playwright의 화면 비교 `toHaveScreenshot` 하나이고, 유료 시각 회귀 서비스는 쓰지 않는다(측정 예산 5만 원 상한 안). Storybook 정적 빌드의 이야기(부품 상태마다 하나)와 대기실 경량 페이지 셸을 판을 고정한 같은 Playwright 컨테이너 이미지에서 찍어 기준 이미지와 견준다. 브라우저 그리기는 OS·판·설정에 따라 달라, 기준 이미지를 만든 환경과 같은 환경에서 찍어야 하기 때문이다(Playwright 문서). 시험은 docs/frontend.md FE-T40이다(추천 적용 2026-10-28, 기술 검토 낮음-100).
- 색상 값은 SEED 기본 팔레트에, 추천 적용(d1 §3, 2026-10-09)으로 정한 브랜드 인디고 팔레트를 합친 것이다. WCAG 2.2 AA 명도 대비는 모두 다시 계산해 검증을 마쳤다(§5 참조). 타이포그래피, 간격, 라운드, 그림자, 모션은 SEED에서 검증된 스펙을 이어받았으므로 임의로 정한 초기 추정치가 아니다. 앞으로 SEED 원본(업스트림) 버전이 바뀌면 `$extensions.seed` 매핑 메타데이터를 바탕으로 안전하게 맞춘다.
- **UI 아이콘**: 24 격자·2px 선·둥근 끝의 선 아이콘을 글자색(`currentColor`)으로 칠하고, 아이콘만 있는 버튼은 CMP-003 규칙(`aria-label`)을 따른다. 장르 타일 아이콘 10개의 정본 SVG는 docs/design/icons/genre/에 있고, 나머지 UI 아이콘은 그림 시안(디자인 캔버스)의 공용 스타일에 `ic-이름`으로 둔다. 2026-10-19에 13개를 더했다(장바구니 아이콘은 소유자 요청 2026-10-19, 나머지는 추천 적용 2026-10-19, ADR-0066): 카드 아이콘 버튼의 `ic-cart`(장바구니. SCR-015 셸 머리의 장바구니 버튼도 `ic-bag` 대신 이것을 쓴다. 같은 뜻은 같은 아이콘으로: `ic-cart`는 장바구니, `ic-bag`은 굿즈 상점(상점 띠 배너·상점 메뉴), `ic-genre-goods`는 장르 타일의 굿즈 스토어)·`ic-bell-fill`(신청한 오픈 알림), 좌석맵 에디터의 `ic-cursor`(선택)·`ic-rect`(무대·사각형 구역)·`ic-polygon`(다각형 구역)·`ic-sector`(부채꼴 구역)·`ic-arcband`(곡선 띠 구역)·`ic-seat`(좌석)·`ic-wand`(템플릿 기본값으로 채우기)·`ic-mirror`(좌우 대칭 복제)·`ic-rotate`(회전 손잡이)·`ic-layers`(층)·`ic-handle`(도형 손잡이).

## 3. 공통 패턴

### 3.1 폼 입력 및 검증 패턴 (원문 7장)
- React Hook Form(RHF)과 Zod를 함께 써서, 프론트엔드와 백엔드가 `nestjs-zod`로 같은 스키마(데이터의 구조 정의)를 나눠 쓴다. 요청·응답의 형·필수·길이·형식은 openapi 계약에서 orval이 만든 Zod 스키마가 원본이다. 손으로 쓰는 Zod는 계약에 적을 수 없는 화면 규칙(아래 grapheme 단위 길이, 금칙어, 판매 정책 DSL)만이고, 그 규칙의 이름은 그 필드의 openapi 설명에 적는다(docs/api/guidelines.md §1, 추천 적용 2026-10-28, 기술 검토 중간-085). 입력 필드에서 포커스가 빠져나가는 `onBlur` 때 1차 검증하고, 그 뒤로는 `onChange` 이벤트로 실시간 다시 검증한다. 검증에 실패하면 맨 위에 에러 요약(`CMP-012`)을 띄우고, 첫 번째 에러 입력 필드로 포커스를 자동으로 옮긴다.
- 모바일 가상 키보드에 맞도록 알맞은 `inputmode`와 `autocomplete`(`tel`, `one-time-code`, `current-password` 등)를 지정한다. 모든 입력 필드에는 명시적인 `label`을 연결한다. placeholder는 예시 텍스트로만 쓰고, 보조 안내는 `aria-describedby`로 연결한다.
- 문자열 길이 제한은 `Intl.Segmenter`를 써서 grapheme 클러스터 단위로 엄격히 센다. 금칙어와 악성 키워드는 Unicode NFKC 정규화를 하고 제로폭 문자(Zero-width space 등)를 지운 다음 매칭한다. 저장할 때는 Unicode NFC 정규화를 거치고, 앞뒤 공백 trim, 연속 공백을 하나로 줄이기, 보이지 않는 제어 문자 지우기를 자동으로 한다.
- 필드별 허용 문자: 성명은 문자 집합을 제한하지 않고 길이(상한은 `@peaket/validation` 스키마 값)와 보이지 않는 제어 문자만 거른다. 한글·영문만 받으면 ja·zh 로케일(NFR-024)과 하이픈·아포스트로피가 든 이름이 막히기 때문이다. 본인확인에서 받은 이름은 고치지 않고 그대로 쓴다. 전화번호는 숫자만, 예매번호는 영문 대문자와 숫자만 받는다. 서비스 닉네임은 이모지 입력을 금지하고, 관람 후기는 이모지 입력을 허용한다(추천 적용 2026-10-28, 기술 검토 중간-098).
- 아주 빠른 입력이나 같은 문자의 반복(예: 'ㅋㅋㅋㅋㅋ')은 화면에서 막지 않는다. 붙여넣기·비밀번호 관리자·음성 입력처럼 한꺼번에 들어오는 정상 입력과 흔한 한국어 표현이 막히고, 봇은 화면 검사를 거치지 않아 막는 효과도 없기 때문이다. 악용 판정은 서버가 한다(후기 금칙어·같은 내용 자동 숨김, docs/security/asvs/catalog-review.md 16.3.3, 게이트웨이 속도 제한)(추천 적용 2026-10-28, 기술 검토 중간-098). 비동기 검증(닉네임 중복, 이메일 검증, 양도 받는 사람 확인. 쿠폰은 두지 않는다, ADR-0060)에는 300ms 디바운스와 `AbortController`를 함께 써서, 새 요청을 보낼 때 앞선 요청을 취소한다. 그래서 늦게 도착한 이전 응답이 최신 결과를 덮어쓰는 응답 역전(Race Condition)이 생기지 않는다.
- 양식 중복 제출을 막으려고 제출 버튼을 바로 비활성화하고, 고유한 `Idempotency-Key` 헤더를 만들어 함께 보낸다. 네트워크가 실패하면 입력 내용은 화면(메모리)에 그대로 두고 다시 보내게 한다. 개인정보·계좌·비밀번호·인증 앱 코드·소명·문의 본문은 브라우저 저장소(SessionStorage 등)에 남기지 않는다(asvs 14.3.3, docs/design/d5 §3.7). 개인정보가 없는 입력(검색어, 공연 설명 초안 등)만 SessionStorage 초안 복구를 쓴다. 이미 입력된 회원 기본 정보는 자동 완성(Auto-fill)을 지원한다. 단계별 입력 화면은 위쪽 Stepper로 현재 진행률(1/N)을 보여 준다. 같은 과정(예매·주문·탈퇴, 공연 등록 위저드 같은 단계별 입력) 안에서 앞서 넣었거나 이미 아는 값은 다시 묻지 않고, 다시 보여야 하면 채워 두거나 고르게 한다(예: 앞 단계에서 넣은 연락처·배송지를 확인 단계에서 다시 묻지 않고, 앞 단계로 돌아가도 입력값이 남는다). 브라우저 자동 완성은 이것을 대신하지 않는다. 재인증 비밀번호·인증 앱 코드처럼 보안 때문에 다시 넣는 값과 만료된 값은 예외다. 채운 값은 위 규칙대로 화면 메모리에만 둔다(WCAG 3.3.7, 추천 적용 2026-10-28, 기술 검토 높음-28).
- 낙관적 UI(Optimistic UI): 좌석을 누르는 즉시 화면에 '선택됨' 상태로 미리 표시한다. 백엔드의 분산 잠금 경쟁에서 지면 선택을 롤백하고(이전 상태로 되돌리고), 흔들림 모션(`motion.seat-shake`)과 함께 가까운 다른 좌석을 추천한다. 관심 공연 찜하기 토글은 React 19(화면 라이브러리)의 `useOptimistic` 훅을 쓴다.

### 3.2 테이블 및 대규모 데이터 그리드 패턴
- 정렬 상태는 WAI-ARIA 표준인 `aria-sort`(ascending, descending, none)를 따른다. 적용된 필터 조건은 위쪽에 태그 칩으로 한꺼번에 보인다.
- 큰 목록에는 커서 기반 페이지네이션을 쓰고, 페이지당 보이는 개수는 25, 50, 100건 단위로 설정하게 한다 [가정]. 소비자 검색 결과(SCR-003)는 표가 아니라 카드 목록이고, 페이지 번호(이전 · 1 2 3 … n · 다음, 한 페이지 20개 [가정], 현재 페이지 `aria-current="page"`, 주소 `?page=`)로 나눈다. 다른 팬 목록(후기 전체 모달 등)은 무한 스크롤 대신 '더 보기' 버튼을 쓴다(ADR-0063).
- 일괄 작업(Batch Action)은 고른 항목의 총 개수를 분명히 보인다. 데이터 삭제처럼 취소할 수 없는 일괄 작업은 반드시 위험 확인 다이얼로그(`CMP-020 DangerConfirm`)를 거친다.
- 5만 행 규모의 전체 좌석 목록, 관제 콘솔 이벤트 감사 로그, 대규모 예매자 명단에는 브라우저의 그리기 성능을 위해 TanStack Virtual 기반 가상 스크롤(Virtual Scrolling)을 쓴다.

### 3.3 빈 화면, 로딩, 에러, 권한 없음 패턴
- 빈 화면(Empty State)은 비어 있다고 알리는 데서 그치지 않고, '데이터가 없는 분명한 이유'와 '사용자가 할 수 있는 다음 행동을 안내하는 버튼'을 함께 둔다.
- 로딩 상태에서는 화면 전체를 막는 스피너를 되도록 피하고, 위젯·카드 단위의 스켈레톤 UI(`CMP-044 Skeleton`)를 우선 그린다.
- 에러 상태는 '발생한 문제의 원인'과 '해결 방법'을 밝히고, 바로 다시 시도하는 버튼을 둔다. 권한 없음 상태는 접근할 수 없는 이유와 함께 로그인 안내나 안전한 이전 화면으로 돌아가는 링크를 보인다.
- 관제 대시보드는 위젯 하나에 장애가 나도 화면 전체가 막히지 않도록, 위젯마다 오류 경계(Error Boundary, CMP-035)로 결함을 그 칸에 가둔다. [다시 시도]는 그 위젯의 조회만 다시 실행한다(관제 콘솔의 서버 데이터 도구는 REST 위젯 조회와 SSE 위젯 흐름이다, docs/frontend.md §3.1·§5.7. 2026-10-27 고침, ADR-0091. 2026-10-28 urql에서 바꿈, ADR-0100).
- 오프라인을 감지하면 위쪽에 고정 알림 배너(`CMP-017 NoticeBanner offline`)를 띄우고, 마지막으로 동기화한 시각을 알린다. 티켓 예매처럼 온라인 연결이 필수인 버튼은 이유를 알리고 비활성화한다(§3.6). 오프라인 동작이 정해진 기능(마이 티켓 월렛의 회전 QR, 찜 저장 대기 FR-019, 스캐너 판정 offline-gate §6, 로비 카운트다운)은 그대로 둔다.

### 3.4 토스트 및 모달 다이얼로그 패턴
- 토스트(`CMP-018 Toast`)는 가벼운 작업의 결과(완료와 가벼운 실패)만 알리는 데 쓴다(5초 뒤 자동으로 사라지고, 마우스를 올리면 멈춘다). 사용자의 판단과 결정이 필요한 중요한 작업에는 모달 다이얼로그(`CMP-019 Dialog`)를 쓴다. 모바일 뷰포트에서는 다이얼로그를 바텀 시트 모양으로 바꿔 보인다 [가정]. 목록·입력 모달(CMP-019 list·form)과 신고 모달(CMP-075)은 전체 화면으로 연다(ADR-0063·ADR-0066).
- 대화상자·바텀 시트·메뉴 서랍 뒤에는 화면 전체를 덮는 반투명 검정 덮개를 깔아 뒤 화면을 물러나 보이게 한다. 색은 `scrim` 토큰(라이트 약 48%, 다크 약 64%)이다(추천 적용 2026-10-31, 그림 시안의 공용 스타일 값을 토큰으로 옮김).
- 모든 모달 다이얼로그는 포커스 트랩(Focus Trap)을 걸어 포커스가 배경 요소로 빠져나가는 것을 막는다. Esc 키로 닫기를 지원하고, 닫힌 다음에는 모달을 불렀던 원래 트리거 요소로 키보드 포커스를 정확히 돌려보낸다.
- 모달 위에 모달을 겹치지 않는다. 후기 전체 모달에서 내 후기 [수정]을 누르면 같은 자리가 쓰기 모달로 바뀌고, 닫으면 전체 모달로 돌아간다. 신고도 같다. 신고 모달(CMP-075)은 전체 모달 자리를 바꿔 열고, 신고 확인 모달은 신고 모달 자리를 바꿔 연다. 닫으면 앞 모달의 같은 위치로 돌아간다. 후기 사진 보기는 같은 모달 안에서 바뀐다(ADR-0066). 법정 고지는 모달로만 숨기지 않고 본문에 늘 보이게 둔다. 안내 모달(CMP-019 info)은 자세한 내용을 더 보는 곳이다. 본인확인 결과는 부른 화면 위의 대화상자로 보이고, 완료만 토스트로 알린다(ADR-0063).

### 3.5 취소 불가능한 중요 작업의 단계적 확인 절차
- 일반 사용자 여정: 회원 탈퇴, 티켓 양도, 예매 취소처럼 되돌릴 수 없는 작업은 위험 확인 다이얼로그(`CMP-020 DangerConfirm` fan 변형)를 필수로 거친다. 버튼에는 그냥 '확인' 대신 실제로 일어날 결과를 문구로 적는다(예: "탈퇴합니다. 주문·결제 기록은 법에 따라 분리 보관 후 파기됩니다", "예매를 취소하고 ₩108,000을 환급받습니다"). 티켓 양도·돌려주기·예매 취소·탈퇴는 그에 앞서 소셜 제공자 재인증(`CMP-064`)을 받는다. 예매 취소와, 미사용 티켓을 가진 채 하는 탈퇴 신청에서는 환급 상세 명세서(`CMP-054 RefundQuote`)를 최종 확인 버튼보다 먼저 화면 낭독기가 읽도록 배치한다.
- 관제 엔지니어 여정: 운영 명령을 실행할 때는 '사유 입력(필수) → dry-run 영향도 시뮬레이션 → 위험 등급 명령 재인증 → 1인 또는 2인 승인 절차(두 번째 승인자도 재인증) → 명령 일괄 전파 → 파드(쿠버네티스에서 앱이 실행되는 가장 작은 단위)별 전파 ack 수신 → 되돌리기 활성화(시간 제한 없음, 만료 있는 명령은 자동 만료)' 파이프라인을 엄격히 지킨다. 판매 재개·봇 판정 강도 같은 2인 합의(Dual-control) 명령에서는 제2 승인권자의 승인 화면에 요청자 정보, 사유, dry-run 시뮬레이션 결과를 원문 그대로 보인다.

### 3.6 이유를 알려야 하는 비활성 버튼(추천 적용 2026-10-28, 기술 검토 중간-101)
- 권한이 모자라거나(관리자 전용 버튼, 권한 밖 운영 명령), 조건이 아직 안 됐거나(필수 동의 전의 결제, 요청자 본인의 승인, 결제사 준비 전의 판매 승인), 품절이라 누를 수 없는 버튼은 숨기지 않고 비활성으로 보이되, 왜 못 누르는지 알린다. 이런 버튼은 HTML `disabled` 대신 `aria-disabled="true"`를 쓴다. `disabled` 버튼은 초점을 받지 못해 Tab으로 가면 건너뛰고, 마우스 사건도 받지 않아 툴팁이 뜨지 않으며, 휴대폰에는 마우스 올리기가 없기 때문이다. `aria-disabled` 버튼은 초점을 받으므로 공용 버튼 부품(CMP-001)이 누르기·Enter·Space를 막는다. 모양은 SEED의 비활성 표시(`data-disabled`)를 함께 붙여 SEED와 같은 비활성 모양을 쓴다.
- 이유는 버튼 바로 위나 아래에 늘 보이는 글로 두고 `aria-describedby`로 버튼에 잇는다(예: "판매 일시정지는 commander만 실행할 수 있습니다", "필수 동의 두 개에 체크하면 결제할 수 있습니다"). 툴팁(마우스를 올려야 뜨는 작은 설명)만으로 이유를 전하지 않는다(WCAG 2.1.1 키보드, 1.4.13 마우스 올림·초점 때 뜨는 내용). 툴팁을 둔다면 늘 보이는 글을 되풀이하는 보조로만 쓴다. 이유 글은 본문 글자 대비(4.5:1)를 지킨다. 한 화면에서 같은 이유로 여러 버튼이 막히면(예: 파트너 실무자 보기의 SCR-025 버튼 넷) 이유 글을 버튼마다 되풀이하지 않고, 그 버튼들보다 먼저 읽히는 화면 머리 배너 하나에 두어 모든 버튼의 `aria-describedby`로 잇는다(추천 적용 2026-10-28. 디자인 캔버스를 그리며 정한 배치 기준).
- 이유를 알릴 필요가 없는 잠깐의 막기(누른 소셜 로그인 버튼이 도는 동안 나머지 버튼 막기 등)는 이 규칙 밖이다.
- 이 화면 장치는 보안 통제가 아니다. 권한과 조건은 서버가 다시 확인한다(docs/planning/03 §3, ADR-0061 결정 4).
- 점검은 docs/design/d4 §1 #26, 시험은 docs/frontend.md FE-T18이다.

## 4. UX 라이팅 규칙 [보완]
- **문체 통일**: 고객에게 보이는 모든 UI 문장은 정중하고 격식 있는 평서형 경어체인 '~합니다'체로 통일한다. 필요 없는 명령형 끝맺음은 피한다("~하세요"는 필수적인 사용자 조작 안내에만 제한적으로 허용한다. 사용자에게 묻는 확인 질문("~할까요?")은 예외로 쓸 수 있다). 법정 의무 고지 문구는 기획 문서(`docs/planning/03-policies-glossary.md`)에 정한 법정 문안을 한 글자의 변형도 없이 그대로 쓴다(`POL-004`, `POL-024`. 원문 문체가 '~할 수 있음'처럼 달라도 바꾸지 않는, 문체 통일의 예외다).
- **서비스명 표기 표준**: 한국어 UI 문장 안에서는 한글 '피켓'으로 쓴다. 공식 로고, 영문 화면, 소스코드, 도메인은 영문 대문자 'PEAKET'으로 쓴다. 첫 서비스 소개 페이지, 이용약관, 법정 고지문에서는 'PEAKET(피켓)'으로 함께 적는다(`docs/design/d1 §3`).
- **톤앤매너**: 차분하고 믿음을 주는 전문 안내자의 말투를 한결같이 유지한다(`docs/design/d1 §3`). '서두르세요', '마감 임박', '놓치면 후회'처럼 사용자의 심리적 불안을 부추기는 인위적인 마케팅 문구는 모두 금지한다.
- **버튼 레이블링**: 버튼은 모호한 명사형이 아니라 분명한 동사형으로 써서, 누르면 무슨 일이 일어나는지 미리 알린다("오픈 알림 받기", "좌석 홀드하기", "이 회차의 판매를 일시정지합니다"). "확인 / 취소"만으로 된 레이블은 금지한다.
- **에러 메시지 작성 표준 공식**: `[무엇이 문제인가]` + `[사용자가 취해야 할 해결책은 무엇인가]`의 2단계 구조를 엄격히 지킨다. (예: "이 좌석은 방금 다른 분이 선택했습니다. 가까운 인접 좌석 B-13, B-14를 선택해 보세요.")
- **전문 용어 체계**: `docs/planning/03-policies-glossary.md`의 용어 사전을 기준으로 일관되게 쓴다. 무작위 셔플과 하이브리드 대기열 공연에서는 '선착순'이라는 기만적 표현을 절대 쓰지 않는다. 고객 화면에서는 엔지니어링 용어인 '순번' 대신 '대기번호'를 쓸 수 있다. 계정 병합의 팬 화면 문구는 '두 계정을 합칠까요?'처럼 '합치다'를 쓸 수 있다(화면 이름과 설명은 '계정 병합', 소유자 결정 2026-10-22). 내부 시스템 코드명(`admission_token` 등)은 화면 UI에 그대로 드러내지 않는다. 관리 계정 2차 인증은 화면에서 '인증 앱'·'인증 앱 코드'로만 쓰고, 'OTP'·'TOTP'·단독 '인증 코드'를 쓰지 않는다(설명 문서·코드 이름은 TOTP, docs/planning/03 §4, 추천 적용 2026-10-14, ADR-0062).
- **숫자 및 단위 표기**: 천 단위 구분 쉼표(,)를 필수로 쓴다. 시간은 "약 2분", "09:58"처럼, 금액은 원화 기호를 붙여 "₩120,000"처럼 적는다. 내 앞 대기 인원수는 공정성 보장 원칙에 따라 반올림하지 않고 정확한 실제 숫자로 보인다. 팬 화면의 시각은 공연장 현지 시각으로 쓰고, 기기 시간대가 다르면 기기 시각을 함께 쓴다(NFR-024). 파트너·관제 콘솔은 시간대를 붙인 KST, 로그는 UTC다(ADR-0060 결정 4).
- **과금 여부 안심 고지**: 과금이 없는 실패(좌석 홀드 실패, 시간 초과, 결제창 단계 실패, 승인 거절 등 payment §4에서 0원으로 끝난 실패)의 안내 문구에는 "요금은 청구되지 않습니다"를 붙인다(`POL-013`). 결과 불명은 "확인 중이며 중복 청구는 발생하지 않습니다", 결제는 됐지만 발권을 끝내 못 해 결제를 취소한 경우는 "티켓을 발급하지 못해 결제를 취소(환불)했습니다"로 나눠 쓴다. 이 경우는 결제 뒤 환불이라 "요금은 청구되지 않습니다"를 붙이지 않는다(payment §4. 2026-10-28 결제 승인 뒤 발권 실패는 앞으로 다시 하기로 바뀌어 '자동 취소'라는 말을 뺐다. 결제 취소는 회차 취소 확정이나 발권 기한을 넘겨 CS가 확인한 때만 한다, ADR-0106, docs/design/d5 §5.12).
- **자동화된 의사결정의 설명권 고지**: 부정행위 탐지 때문에 추가 검증으로 격리할 때 보이는 안내문에는, 자동으로 확인된 사항이 있어 한 번 더 확인한다는 사실과 설명 요청·재검토 신청 권리를 넣는다(`POL-006`. 문구 정본은 docs/planning/04 SCR-009 "자동으로 확인된 사항이 있어 한 번 더 확인합니다").

## 5. 색 대비 검증

`tokens.json`에 정의된 모든 시맨틱 색상 토큰 쌍을 WCAG 2.2 상대 휘도(Relative Luminance) 공식으로 계산해 검증했다(2026-10-11 SEED Design 토대 전환 뒤 재계산 완료, `ADR-0040`). 명도 대비 기준은 일반 본문 텍스트가 4.5:1 이상(WCAG 1.4.3)이다. 키보드 포커스 링, 폼 입력 테두리선, 조작 가능한 좌석 요소, SLO 상태 표시등은 3.0:1 이상(WCAG 1.4.11)이다. 다른 사람이 홀드한 좌석, 이미 판매된 좌석, 판매 불가 좌석, 비활성화된 보조 문구는 사용자가 조작할 수 없는 비활성 UI 요소다. 그래서 WCAG 1.4.11의 '비활성 컴포넌트(Inactive Components)' 예외 조항을 적용받는다(W3C WCAG 2.2 원문 규정 확인). 다만 이런 비활성 요소도 빈 좌석과의 명도 차이를 가능한 한 크게 하고, 시각 패턴을 의무적으로 함께 써서 구별되게 한다(§1 참조). SEED Design은 APCA(본문 Lc 75) 기준을 써서 WCAG 2.2 AA 기준과 다르다. 그래서 SEED 기본 색상을 그대로 받아들이지 않고, 아래 검증 표로 기준에 맞는다는 것을 엄격히 입증했다. 앞으로 디자인 토큰 값이 바뀌면 같은 상대 휘도 알고리즘을 다시 돌려 이 대비표를 갱신해야 한다(`docs/design/d4-handoff-checklist.md` 3·4번 항목 참조). 토큰 대비 계산 CI(docs/frontend.md FE-T44)가 PR마다 이 표의 짝을 tokens.json으로 다시 계산해, 기준을 넘는지와 표의 측정치가 계산값(소수 둘째 자리)과 같은지 본다. 그래서 짝을 더하거나 바꿀 때는 이 표의 행 모양(`` `전경` / `배경` ``, 요구 기준, 라이트, 다크)을 지킨다(추천 적용 2026-11-04).

SEED 기본값과 비교해 피켓이 일부러 조정한 핵심 변경 사항:
- 라이트 모드의 성공, 경고, 위험 텍스트 색상은 SEED 기본 전경 토큰(green-700, yellow-700, red-700)이 순백색 배경에서 각각 3.96, 4.12, 3.76:1로 WCAG 4.5:1 기준에 미달했다. 그래서 피켓은 800 스케일(5.73, 6.41, 5.68:1)로 명도를 낮춰 오버라이드했다. 다크 모드는 SEED 700 토큰이 6.4:1 이상의 높은 대비를 유지하므로 그대로 두었다.
- 키보드 포커스 링은 SEED의 `stroke.focus-ring`(blue-600)이 흰 배경에서 2.84:1로 3.0:1 기준에 미달해, 피켓의 indigo.500(5.11:1) 토큰으로 바꿨다.
- SEED의 `fg.neutral-subtle`(gray-700, 3.42:1)은 텍스트 전경색으로 쓰지 않는다. 보조 안내 텍스트에는 `text-muted`(gray-800, 6.62:1)를 쓴다.
- 브랜드 주조색은 SEED의 carrot 오렌지 대신 피켓 딥 인디고를 적용했다(`ADR-0040` 결정 2). 순백색 글자 대비는 라이트 모드 7.90:1로 WCAG 2.2 AAA 기준(보통 글자 7:1)을 넘는다. 다크 모드는 5.11:1로 AA 기준(4.5:1)을 넘는다.
- 제공자 버튼(CMP-001 provider)의 색은 토큰이 아니라 제공자 지정값이라 따로 쟀다(2026-10-14). 카카오 글자 #000000 85%/#FEE500 12.52:1, Google 글자 #1F1F1F/#FFFFFF 16.48:1, 네이버 흰 바탕 세트 글자 #000000/#FFFFFF 21.00:1이다. 네이버 녹색 세트(글자 #FFFFFF/#03A94D)는 3.09:1로 보통 크기 글자의 4.5:1에 못 미쳐 쓰지 않는다(추천 적용 2026-10-14, ADR-0062). W3C 해설은 로고 밖의 글자를 브랜드 지침을 이유로 예외로 두지 않는다. 레이블은 세 버튼 모두 14px/20px·500이다(Google 가이드 영어 원문 2026-07-07의 Google Sans Medium 14/20, 추천 적용 2026-10-14, ADR-0062).
- 데이터 시각화 팔레트 `heat.1~3`(추천 적용 2026-10-26, ADR-0089)은 SEED에 같은 단계가 없어, 좌석 상태와 SLO가 쓰지 않는 파랑 한 색의 명도 3단계로 새로 정했다(OKLCH 색 공간에서 계산, 라이트 #E0F1FF·#A9D2FE·#6DB0F4, 다크 #192D41·#1A4268·#1D5B92). 면은 늘 글자(등급 이름, 남은 좌석 수)나 표 보기와 함께 쓰는 보조 표시라 면과 배경 사이 대비는 따지지 않고(WCAG 1.4.1, 배경과 1.15~2.53:1), 면 둘레에 `border`를 긋는다. 면 위 글자는 `text`만 쓴다(같은 값을 가리키는 토큰 `heat.ink`, 추천 적용 2026-10-31). `text-muted`는 라이트 모드 heat.2·heat.3 위에서 4.20·2.89:1이라 4.5:1에 못 미친다. 이웃 단계끼리는 1.36~1.46:1로 갈린다.
