# 성능 장부 (Performance Ledger)

- **독자와 용도**: 성능 측정 엔지니어가 객관적 증거력을 갖추기 위해 기록해야 할 필수 산출물과 절차를 확인할 때, 그리고 기술 면접관과 코드 검토자가 10대 핵심 KPI 수치의 신뢰성 근거(실험 조건, 원천 데이터, 재현 스크립트)를 검증할 때 참조하는 기준 문서이다. 개별 측정의 원시 데이터는 저장소의 `perf-ledger/runs/` 디렉터리 하위에 1회 실행당 독립 폴더로 보존되며, 본 문서의 장부 요약 표는 해당 폴더들의 메타데이터를 기반으로 자동화 도구가 일괄 생성한다.
- **원본 출처**: 설계서 §10 KPI 10선과 '측정 방식', planning/01-overview.md §3(핵심 KPI 및 벤치마크 도구), docs/architecture.md §9.3(초기 v0 병목 분석과 v1 아키텍처 해결책), docs/observability.md §12(SLO 부하 시험 및 Game Day 훈련), POL-026(부하 및 침투 테스트 규칙), docs/verification.md(규칙 검사와 100만 외삽, ADR-0057).
- **기준 기획 버전**: v1.0. 벤치마크 프레임워크 틀은 2026-10-10에 구축되었으며 실제 데이터는 Phase 1(WBS 1.4.1)부터 순차 적재된다. 본 문서에 수록된 예시 데이터 행은 서식 표준을 제시하기 위한 목적으로 작성되었다.
- **자동화 도구 체계**: `tools/perf-ledger/` 하위 스크립트(데이터 수집기 `collect.py`, 색인 갱신 도구 `index.py`, 벡터 시각화 도구 `charts.py`, k6 결과 파서 `k6-summary.js`)를 통해 관리된다. 세부 사용 지침은 `tools/perf-ledger/README.md`에 기술되어 있다.

## 1. 객관적 성능 증거의 3대 조건

| 필수 조건 | 조건의 의미 | 충족 및 보증 방법 |
| --- | --- | --- |
| 재현 가능성 (Reproducibility) | 동일한 소스 코드, 동일한 측정 환경 사양(로컬 PC 또는 클라우드), 동일한 부하 시나리오를 단일 자동화 명령으로 언제든 다시 실행할 수 있어야 한다. 결과 수치는 실행마다 흔들리므로 반복 횟수와 중앙값을 함께 적는다(§3의 6). | `manifest.json`에 대상 Git 커밋 해시, 시나리오 파일 경로, 부하 매개변수, 인프라 프로파일 명칭을 박제하고 단일 실행 쉘 명령을 기록한다. |
| 원천 데이터 무결성 (Raw Data Auditability) | 시각화 차트는 2차 가공물에 불과하므로, 가공되지 않은 기계 측정 원본 데이터가 반드시 원형 보존되어야 한다. | k6 실행 요약 JSON, 서버 시계열 메트릭 CSV, 비즈니스 불변식 검증 결과 CSV를 실행 폴더에 보존하며, 모든 차트는 해당 파일로부터 스크립트를 통해 결정론적으로 렌더링한다. |
| 측정 환경 조건의 투명성 (Context Completeness) | 측정 일시, 동시 접속 규모, 인프라 노드 대수 및 스펙, 부하 발생기(Load Generator) 상태, 클라우드 비용까지 측정 배경이 완전하게 공개되어야 한다. | `manifest.json`의 모든 필수 메타데이터 필드(§2.2)를 누락 없이 채운다. 필수 항목이 공란인 경우 해당 측정은 무효 처리한다. |

수작업으로 캡처한 단순 스크린샷과 화면 녹화 영상은 보조적 설명 자료에 불과하며, 핵심 성능 지표의 공학적 근거로 채택하지 않는다.

## 2. 측정 1회의 표준 산출물 구조

### 2.1 디렉터리 구조

```
perf-ledger/
  runs/<run-id>/            단일 측정 실행 디렉터리 (예: 2026-11-02-k1-v0-local-10k)
    manifest.json           실행 환경 및 파라미터 메타데이터 (§2.2)
    k6-summary.json         k6 부하 도구 출력 원시 요약 JSON
    metrics/<name>.csv      Prometheus 시계열 메트릭 원본 (쿼리 식별자별 분리)
    invariants.csv          비즈니스 불변식 검증 결과 (총 판매 수 ≤ 좌석 재고, 좌석당 판매 1건, 인당 구매 수 ≤ 한도, 이중 결제 0건)
    traces/                 p99 이상치 요청의 OpenTelemetry 분산 트레이스 JSON (선택 사항)
    grafana/                측정 구간 Grafana 대시보드 렌더링 이미지 및 스냅샷 URL (보조 자료)
    infra.txt               실행 당시 측정 환경 사양(로컬은 CPU·메모리·WSL 설정과 CPU 배치, 클라우드는 인스턴스 타입), 커널 및 소프트웨어 버전 원본
    stdout.log              벤치마크 러너 스크립트 실행 콘솔 전체 출력 로그
    cost.csv                AWS 비용 할당 태그 기반 실측 인프라 비용 (클라우드 실행 한정)
    timeline.csv            Game Day 장애 주입 및 대응 시간선 로그 (§8, 관제 KPI 전용)
    confusion.csv           봇 탐지 등급·라운드별 오차 행렬과 사람 층별 집계 (K6 봇 탐지 한정, ADR-0039·0048)
    bot_cost.csv            등급·라운드별 1장당 획득 비용 원본 수량 (K6, §10.4)
    bot_prices.json         1장당 획득 비용 단가 (K6, §10.4)
    SHA256SUMS              디렉터리 내 전체 산출물 파일의 암호학적 해시 지문 목록
  charts/                   charts.py가 원시 CSV로부터 생성한 표준 SVG 차트
```

### 2.2 manifest.json 필수 메타데이터 필드

| 필드명 | 설명 및 데이터 유형 | 입력 예시 |
| --- | --- | --- |
| `run_id` | 일시-KPI-버전-프로파일 조합의 고유 식별자 | `2026-11-02-k1-v0-local-10k` |
| `kpi` | 검증 대상 KPI 식별자 (K1~K10, Game Day `G-nn`, 또는 NFR 번호) | `K1` |
| `version` | 아키텍처 버전 (`v0`: 단순 동기식 베이스라인, `v1`: 최종 아키텍처) | `v0` |
| `profile` | 표준 인프라 환경 프로파일 (§4, docs/infra.md §3) | `local-10k`, `cloud-calib` |
| `scale` | 부하 규모 객체 (`users`: 가상 대기자 수, `arrival_rps`: 도착률, `duration_s`, `warmup_s`) | 동시 10,000명, 20,000 RPS, 유지 600초, 예열 120초 |
| `scenario` | k6 실행 스크립트 상대 경로, 런타임 인자, 오픈 모델 여부 | `peaket-loadtest/k1-entry.js`, `open_model: true` |
| `commit` | 벤치마크 대상 소스 코드 저장소 커밋 해시 및 문서 커밋 해시 | `git rev-parse HEAD` 해시값 |
| `generator` | 부하 발생기 대수, 인스턴스 사양, k6 버전, 발생기 병목 지표 `dropped_iterations` | 1대(PC, 코어 8개 배정), k6 v0.50.0, `dropped_iterations: 0` |
| `started_at`, `ended_at` | 부하 시험 시작 및 종료 ISO8601 UTC 타임스탬프 | `2026-11-02T05:00:00Z` |
| `region` | 클라우드 실행 배포 리전 또는 `local` 표기 | `local`, `ap-northeast-2` |
| `cost_krw`, `exchange_rate` | 부하 시험에 소요된 실측 AWS 인프라 비용(원) 및 적용 환율 | 0 (로컬) 또는 실측 비용 |
| `valid` | 벤치마크 유효성 판정 플래그(`true`/`false`) 및 무효 사유 `invalid_reason` | 부하 발생기 CPU 포화 시 `false` 마킹 |
| `verdict` | 최종 검증 판정 결과 (`pass`, `fail`, `baseline`) | `pass` |
| `notes` | 스팟 인스턴스 축출, 캐시 웜업 구간 예외 처리 등 특이 사항 | 자유 기술 |
| `k6_eval`, `k6_plan`, `k6_cost` | K6 봇 탐지 한정: 등급·라운드별 탐지율과 Wilson 95% 구간(3단계는 목표 없음), 등급별 하락폭, 사람 오탐과 Clopper-Pearson 단측 95% 상한, 층별 오탐 수, 사전 등록 계획 판정, 1장당 획득 비용과 웃돈별 손익(`collect.py --confusion --k6-plan --bot-cost --bot-prices`, §10) | 1단계 물량형 봇 탐지 96.2%(94.8~97.2%), 사람 오탐 1/947(상한 0.50%, 계획 통과) |
| `latency_crosscheck` | 같은 시간 창의 k6 p99와 서버 SLI(같은 경로 서버 히스토그램의 p99와 기준값 안 비율), 둘의 차이, '측정 지점 의심' 표시(서버 SLI는 목표 안인데 k6 값이 목표 밖일 때, ADR-0077) | 진입 k6 p99 182ms, 서버 p99 151ms·200ms 안 99.6%, 차이 31ms, 의심 아님 |

### 2.3 서버 시계열 메트릭 규약 (Prometheus Query Alias)

| 쿼리 식별자 | 메트릭의 의미 | 연계 시각화 차트 |
| --- | --- | --- |
| `origin_rps` | 백엔드 인그레스 게이트웨이에 최종 도달한 초당 HTTP 요청 수 | 비례 불변 스케일링 곡선 |
| `cdn_hit_ratio` | CloudFront 엣지 캐시 적중률 백분율 | 비례 불변 곡선 보조 지표 |
| `p99_ms` | 검증 대상 핵심 경로의 서버 측 레이턴시 p99 백분위수 (ms) | 트래픽 폭발 타임라인 차트 |
| `error_rate` | HTTP 5xx 서버 오류 및 타임아웃 발생 비율 (%) | 트래픽 폭발 타임라인 차트 |
| `redis_cpu` | 대기열 및 좌석 Redis 클러스터 인스턴스 CPU 사용률 | 병목 분석 차트 |
| `event_loop_lag_ms` | 핫패스 마이크로서비스의 Node.js 이벤트 루프 지연시간 p99 (ms) | 내부 런타임 병목 차트 |
| `heap_after_gc_mb`, `rss_mb`, `open_fds`, `active_handles`, `db_conns`, `redis_conns` | 장시간 시험의 자원 시계열(1분 간격, GC 뒤 힙·RSS·열린 FD·활성 핸들·DB·Redis 연결 수). 데우기 30분 [가정] 뒤 구간의 시간당 기울기로 NFR-027을 판정한다(docs/verification.md §3.6, ADR-0070) | 장시간 시험 자원 추세 차트 |
| `rt_freshness_p95_s`, `rt_loss_ratio`, `rt_checkpoint_ms` | 관제 실시간 표 시험(NFR-009)의 심장 박동 신선도 1분 p95(초), 누락률(늦어서 버린 수 + 싱크가 버린 수 + 읽지 못해 거절한 수 + 생산자가 버린 수 ÷ 전체), 체크포인트 소요(ms). `kpi`는 `NFR-009`이고 결과는 '실측(PC)'이다(docs/verification.md §3.7, ADR-0071) | 트래픽 폭발 타임라인 차트 |

실제 메트릭 쿼리 명세는 `tools/perf-ledger/queries.example.txt`에 정의되어 있으며, 서비스 공통 템플릿의 Recording Rule 표준에 맞춰 동기화된다.

## 3. 표준 부하 측정 절차

1. **로컬 사전 리허설**: 본 측정과 선택 보정(클라우드) 전에 같은 k6 부하 스크립트를 작은 규모로 끝까지 돌려 스크립트 무결성을 확인한다.
2. **부하 발생기 용량 보정 (Calibration)**: 부하 발생기 단말 1대가 왜곡 없이 송출 가능한 최대 초당 요청률을 사전 계측하여 장부에 기록한다. 실제 측정 중 k6의 `dropped_iterations`가 1건이라도 발생하면 부하 발생기 자체 병목으로 판정하여 측정을 즉시 무효화한다.
3. **분산 시계 동기화 검증**: 측정 착수 직전 부하 발생기와 대상 서버 클러스터의 NTP 시계 동기화 상태를 필수 점검하고 오차 범위를 `stdout.log`에 기록한다.
4. **개방형 부하 모델 강제 (Open Workload Model)**: k6의 arrival-rate(open model) 방식을 적용하여 가상 사용자가 도착하는 속도를 강제 고정한다. 대상 서버가 지연되더라도 유입 트래픽이 감소하지 않는 실환경의 파괴적 특성을 그대로 재현한다.
5. **초기 웜업 구간 분리**: 벤치마크 시작 후 초기 `warmup_s` 동안의 데이터는 JIT 컴파일 및 캐시 적재 단계로 간주하여 최종 집계에서 엄격히 제외하며, 실제 분석 구간을 manifest에 명시한다.
6. **통계적 반복 검증**: 로컬 환경은 동일 조건으로 최소 3회 반복 실행하여 지표 중앙값과 신뢰 범위를 산출한다. 클라우드 환경은 FinOps 예산 범위(planning/01 §5.1) 내에서 가용한 실행 횟수를 있는 그대로 기록한다.
7. **동일 조건 대조 원칙**: 초기 베이스라인(v0)과 개선 아키텍처(v1)는 동일한 환경 프로파일에서 실행되어야 하며, `infra.txt` 대조를 통해 하드웨어 자원의 동등성을 증명한다.
8. **산출물 자동 수집**: `collect.py` 자동화 스크립트를 통해서만 결과 디렉터리를 생성하고 산출물을 취합한다. 엔지니어의 수동 파일 이동 및 편집을 금지한다.
9. **장부 인덱스 자동 갱신**: `index.py` 스크립트를 실행하여 본 문서 §5의 요약 표를 자동 동기화한다. 마크다운 표의 수작업 수정을 금지한다.
10. **무효 측정의 투명한 보존**: 부하 발생기 병목, 스팟 인스턴스 중도 축출, NTP 시계 오차, 인프라 사양 불일치, 데이터 불변식 위반이 적발된 경우 삭제하지 않고 `valid: false` 플래그와 상세 결격 사유를 명시하여 영구 보존한다.
11. **같은 PC에서의 측정**: 발생기와 대상을 같은 PC에서 돌리면 CPU를 나눠 쓰고 그 배치를 `infra.txt`에 적는다. 발생기 CPU는 80% 이하로 둔다(k6 권고). WSL 안의 CPU 고정은 실제 코어 고정을 보장하지 않으므로 반복 사이 편차를 함께 적는다(docs/verification.md §3.2·§3.5).
12. **클라이언트·서버 지연 대조(ADR-0077)**: 측정마다 같은 시간 창의 k6 p99와 서버 SLI를 `latency_crosscheck`에 함께 남긴다. 차이는 네트워크·게이트웨이·클라이언트 쪽 지연이다. 서버 SLI는 목표 안인데 k6 값이 목표 밖이면 '측정 지점 의심'으로 표시하고, SLI를 재는 위치(게이트웨이·서비스)를 다시 본다.

## 7. 수치의 학술적 표시 규칙

| 표기 범주 | 정의 및 서술 원칙 |
| --- | --- |
| 실측 (Measured) | 본 장부의 개별 실행 폴더에 원본 데이터가 영구 보존된 수치. 반복 측정 횟수를 반드시 병기하고(예: 로컬 3회 실행 중앙값, 클라우드 1회 실행), 환경을 '실측(PC)'과 '실측(클라우드)'로 나눠 적는다. |
| 외삽 (Extrapolated) | 잰 범위의 결과를 식으로 늘려 구한 수치. 식은 설계가 예측하는 식(예: 원 서버 응답 = 활성 파일 수 ÷ 캐시 수명)이나 USL처럼 의미가 있는 모델만 쓰고 다항식 맞추기는 쓰지 않는다. 근거 실행 ID, 식과 계수, 측정 범위, 외삽 배수(목표 ÷ 측정 최대치)를 반드시 적는다 (예: 100만 명 원 서버 응답은 local-1k·10k·100k 실측과 맞는지 확인한 설계 식으로 계산, docs/verification.md §3, ADR-0057). |
| 문서 인용 (Cited) | 우리가 재지 않고 제공사 공식 문서에만 근거한 수치(예: CloudFront 배포 하나의 한도, 관리형 장애 조치 시간, 노드 기동 시간). 문서 주소와 확인 날짜를 적고 실측처럼 쓰지 않는다. |
| 설계 목표 (Target) | 개발 구현 전 아키텍처 요구사항으로 정의된 목표 수치 (planning/02 NFR 규약). |
| 하한선 (Lower Bound) | 상용 환경의 악의적 봇 트래픽처럼 전수 정답지가 존재하지 않아 허니팟 트랩, 표본 검토, 사후 이상 분석으로 적발한 최소 수치. 실제 침투 규모는 이보다 크거나 같음을 의미한다 (FR-049). |

기술 문서와 면접 답변 시에는 상기 5가지 표기 범주를 엄격히 구분하여 서술하며 상호 혼용하지 않는다.

## 8. Game Day 장애 복구 시간선

관제 관련 핵심 기술 지표(K8: 10대 장애 60초 이내 탐지, 비상 제어 명령 3초 이내 파드 반영)는 분산 타임스탬프 실측으로 증명한다. 시나리오마다 다음 타임라인을 `runs/<run-id>/timeline.csv`로 영구 보존하며, Grafana 대시보드 주석 및 ops-svc 감사 로그와 상호 교차 검증한다.

| 시각 (UTC) | 발생 사건 | 데이터 원천 |
| --- | --- | --- |
| 주입 시점 ($T_0$) | 카오스 장애 주입 명령 실행 | Chaos Mesh·Toxiproxy 실행 이벤트 로그(운영 설계는 AWS FIS 포함, 포트폴리오 기간의 실행 방식은 docs/verification.md §5.2) |
| 알림 시점 ($T_1$) | 다중 윈도우 번 레이트 경보 발생 | Alertmanager 웹훅 수신 로그 |
| Datadog 이상 표시 ($T_{1d}$, wbs 4.8.2 비교에서만) | Watchdog 이상 또는 이상 탐지 모니터(`basic`)가 처음 표시한 시각. 사람을 부르지 않는다 | Datadog Watchdog 목록·모니터 이벤트 내보내기 |
| 명령 접수 ($T_2$) | 운영자의 비상 제어 명령 접수 및 2인 승인 완료 | ops-svc 이벤트 소싱 감사 원장 |
| 파드 반영 ($T_3$) | 대상 마이크로서비스 파드의 제어 명령 적용 ack 수신 | ops-svc 이벤트 소싱 감사 원장 |
| 서비스 정상 복구 ($T_4$) | 핵심 SLI 지표가 정상 허용치 이내로 복원 완료 | Prometheus 시계열 메트릭 |

- 장애별 탐지 시간 = $T_1 - T_0$. K8은 주입한 장애마다 60초 이내인지 판정하고(최댓값 기준), 평균은 쓰지 않으며 모든 값을 기록한다(ADR-0049)
- 제어 명령 전파 반영 시간 = $T_3 - T_2$
- Game Day 시나리오 26종 전체 목록은 docs/observability.md §12에 명시되어 있다.
- Datadog 이상 탐지 힌트 비교(소유자 결정 2026-10-21, ADR-0076 상태 줄, docs/observability.md §13): 장애마다 $T_0$·$T_1$·$T_{1d}$, 우리 규칙과 Datadog 각각의 탐지 여부, 표시한 쪽(Watchdog 로그 이상·Watchdog 지표 이상·이상 탐지 모니터)을 `runs/<run-id>/hint_compare.csv`로 남긴다. 주입과 관계없는 이상 표시는 헛경보 행으로 같은 파일에 남기고, 같은 시간 우리 규칙의 헛경보도 센다. Datadog이 먼저 잡은 시간은 $T_1 - T_{1d}$다. 체험이 14일이라 Watchdog 지표 이상이 기준선 부족으로 동작하지 않았으면 그 사실을 `valid` 사유에 적는다.

## 9. 장기 보관 및 아카이빙 정책

- 모든 측정 원본 디렉터리는 Git 저장소에 형상 관리한다. 대용량 CSV 파일은 gzip으로 압축 보존하며, 단일 실행 디렉터리의 크기가 50MB를 초과할 경우 분산 트레이스 표본을 선별 압축한다.
- 저장소 형상 관리와 별개로 클라우드 S3 아카이브 버킷에 장기 백업 사본을 동기화한다(docs/observability.md §9). 백업 아카이브에는 `SHA256SUMS` 해시 지문 목록을 필수로 동봉한다.
- 실험 도중 실패하거나 규격을 만족하지 못한 무효 측정 결과라 할지라도 임의로 폐기하지 않는다. `valid: false` 플래그와 상세 결격 사유를 기록하여 남기는 것 자체가 투명한 엔지니어링의 핵심 자산이다.

### 10.2 12칸 등급표

등급 이름은 `<유형>-L<단계>`로 쓴다. 유형은 `volume`(물량형), `speed`(속도형), `account`(계정 대량 생성형), `queue`(대기열 새치기형)다.

| 유형(OAT) | 1단계 HTTP 스크립트 | 2단계 브라우저 자동화 | 3단계 사람 입력 재생 |
| --- | --- | --- | --- |
| 물량형(OAT-005 Bulk purchase, OAT-021) | 여러 대여 명의 계정으로 홀드·주문 API를 반복 호출 | Playwright로 여러 계정이 동시에 좌석 선택과 결제를 진행 | 조정용 사람 궤적을 변형해 여러 계정으로 재생 |
| 속도형(OAT-006, OAT-013) | 오픈 정각에 입장 확정·홀드 API를 가장 먼저 호출 | 브라우저에서 클릭 최단 경로를 자동화 | 사람 궤적을 시간 압축해 재생 |
| 계정 대량 생성형(OAT-019) | 대여 명의 풀로 가입·본인확인 API를 연속 호출 | 브라우저로 가입 흐름을 자동화 | 녹화한 가입 흐름을 변형해 재생 |
| 대기열 새치기형(OAT-005 Queue jumping) | 입장 토큰 재사용, 순번 위조, 절차 건너뛰기 요청 | 브라우저 저장소·쿠키 조작 | 정상 흐름을 재생하면서 토큰을 바꿔치기 |

| 항목 | 규칙 |
| --- | --- |
| 1단계 수단 | JavaScript를 실행하지 않는 HTTP 클라이언트(k6, Node), 고정 IP 몇 개 |
| 2단계 수단 | Playwright(headless·headed), 지문 위장(`navigator.webdriver` 숨김, 화면·글꼴·WebGL 값 바꿈), 시험망 프록시 컨테이너로 IP·ASN 회전 |
| 3단계 수단 | 2단계에 더해, 조정용 사람 궤적(포인터·키 입력 시각)에 잡음과 시간 늘이기를 넣어 재생 |
| 사람 확인 | 시험 키는 늘 통과하거나 늘 실패하므로 사람 확인 시뮬레이터 어댑터를 쓴다. 풀이 성공률 0%·50%·95%, 풀이 지연 10~30초 [가정, 3.7.1에서 확정]. 설정마다 따로 보고한다 |
| 명의 | 본인확인 시뮬레이터가 합성 신원을 '대여 명의 풀'로 내준다. 쓴 명의 수를 `bot_cost.csv`에 적는다. 1인 1계정과 1인 한도(POL-011)는 실서비스와 같다 |
| 세션 수 | 등급마다, 라운드마다 1,000세션(12등급 × 3라운드 = 36,000세션, `local-bot` 0원) |
| 탐지의 정의 | trust-svc가 추가 검증 큐로 보내거나 차단하면 봇 판정이다. 사람 세션이 그렇게 되면 오탐이다 |
| 판정 강도 | 합격 판정은 '기본'으로 한다. '완화'·'강화'는 장부 실행을 나눠 민감도로 함께 남긴다 |
| 목표 | 1·2단계는 등급마다 탐지율 95% 이상(점추정, Wilson 95% 구간을 함께 적는다). 3단계는 §10.4의 비용 목표 |

### 10.3 적응 라운드 [가정, 3.7.1에서 확정]

1. 라운드를 시작하기 전에 공격 변경 계획과 방어 규칙 버전을 장부 `notes`에 적는다.
2. 예산은 라운드마다 등급당 1,000세션, 봇 수정 8시간, 레이트 리밋 안의 요청이다.
3. 공격 스크립트는 세션 결과(통과·추가 검증·차단)만 입력으로 받고 점수나 규칙은 보지 않는다.
4. 라운드 사이의 방어 규칙 변경은 허용하고 변경 내용을 같은 장부에 남긴다.
5. 등급마다 라운드 1 대비 마지막 라운드의 하락폭(%p)을 `k6_eval.tier_drops`로 보고한다. 2단계가 95% 아래로 떨어지면 ADR-0039의 되돌릴 조건을 따른다.

### 10.4 1장당 획득 비용

```text
1장당 획득 비용 = (명의 수 × 명의 단가 + 프록시 GB × GB 단가 + 풀이 수 ÷ 1,000 × 1,000건 단가
                  + 운영 시간 × 시간 단가 + 시험 인프라 비용) ÷ 얻은 장수
기대 처벌 비용 = 적발 확률 × 50 × (정가 + 웃돈)
1장 손익 = 웃돈 − 1장당 획득 비용 − 기대 처벌 비용
```

| 단가 | 기본값 | 근거 | 표시 |
| --- | --- | --- | --- |
| 명의 1개 | 5만 원(민감도 2만 원·10만 원) | 아이디 옮기기 수고비 2만 원에서 10만 원 넘게(아시아경제 2024-04-17 보도) | 추정 |
| 프록시 1GB | 7.00달러 | IPRoyal 주거용 프록시 종량제(2026-10-13 가격표) | 공개 가격 |
| 사람 확인 풀이 1,000건 | 1.45달러 | 2Captcha Cloudflare Turnstile(2026-10-13 가격표) | 공개 가격 |
| 운영 1시간 | 1만 원 | 1인 운영 인건비 | [가정, 3.7.1에서 확정] |
| 환율 | `usd_krw` 또는 manifest `exchange_rate` | 측정일 환율 | 측정 |
| 웃돈 | 20만 원, 90만 원 | 인기 공연 보도 사례 20만 원(아시아경제 2024-04-17), 정가 9만 9천 원 좌석을 100만 원 넘게 판 사례(데일리안 2026-08-28) | 추정 |
| 정가 | 15만 원 | 기대 처벌 계산용 기준값 | [가정, 3.7.1에서 확정] |
| 적발 확률 | 1%, 5% | 공개 자료 없음 | [가정, 3.7.1에서 확정] |

- 시험에서 재는 값은 명의 수, 프록시 GB, 풀이 수, 운영 시간, 인프라 비용, 얻은 장수다. 얻은 장수가 0이면 1장당 비용은 '획득 없음'이다.
- 기대 처벌은 과징금 상한(판매금액의 50배, 공연법 §4의4)으로 계산하므로 크게 잡힌 값이다. 형사처벌(§41)은 금액으로 넣지 않는다.
- 단가는 측정할 때마다 그날의 가격표로 다시 확인하고 날짜를 남긴다. 명의 단가와 웃돈은 불법 시장 가격이라 공식 자료가 없어 보도 사례 범위로 민감도를 본다.
- 3단계 목표 형식: 등급마다 '1장당 획득 비용 + 기대 처벌 비용 ≥ 기준 웃돈'. 기준 웃돈은 첫 측정 뒤 정한다 [가정, 3.7.1에서 확정].

### 10.5 장부 입력 파일과 필드

| 파일·옵션 | 형식 |
| --- | --- |
| `confusion.csv` | `tier,round,label,predicted,count[,stratum]`. 사람 행의 tier는 `-`. stratum은 사람 행의 층 이름(예: `device-ios`, `assistive`, `age60`, `shared-ip`)이다. stratum이 빈 사람 행만 합계에 쓰고, 층 행은 층별 집계에만 쓴다(한 세션이 여러 층에 속할 수 있다) |
| `--k6-plan N:C` | 사전 등록한 판정용 사람 표본 수와 합격 오탐 수(예: `947:1`). 오탐 C건의 상한이 0.5%를 넘는 조합은 도구가 거부한다 |
| `bot_cost.csv` | `tier,round,ids,proxy_gb,solves,ops_hours,infra_krw,tickets` |
| `bot_prices.json` | `id_krw`, `proxy_usd_per_gb`, `solve_usd_per_1k`, `hour_krw`, `usd_krw`(없으면 manifest 환율), `face_krw`, `premiums_krw`(목록), `catch_probs`(목록) |
| manifest `k6_eval` | 등급·라운드별 탐지율과 Wilson 구간(3단계는 `meets_target: null`), `tier_drops`, 라운드별 사람 오탐과 단측 상한, `human_strata`, `plan_verdict`(PASS·FAIL·INSUFFICIENT) |
| manifest `k6_plan`, `k6_cost` | 사전 등록 계획, 등급·라운드별 1장당 획득 비용과 웃돈·적발 확률 경우별 기대 처벌과 손익 |
