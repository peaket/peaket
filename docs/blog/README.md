# 기술 블로그 초안

PEAKET 측정을 마칠 때마다 쓰는 기술 블로그의 초안을 둔다(docs/planning/01-overview.md §3.3 '지식 전파', ADR-0128 중간-006). 블로그는 면접 전에 밖에서 볼 수 있는 증거라, 무엇을 왜 바꿨는지가 흐려지기 전에 그 측정 직후에 쓴다.

- **규범이 아니다**: 이 폴더의 글은 정본(docs/verification.md, 성능 장부 docs/perf-ledger/ 등)을 풀어 쓴 것이다. 새 결정이나 새 숫자를 담지 않는다. 글과 정본이 다르면 정본이 맞고, 글을 고친다.
- **숫자 표시**: 숫자는 정본과 성능 장부에서만 가져오고 실측(PC)·실측(클라우드)·외삽·문서 인용·설계 목표·하한선 가운데 하나를 붙인다(ADR-0057 결정 9, docs/planning/02-requirements.md §3.1). 근거로 쓴 장부 실행 ID를 글 끝에 적는다.
- **쓰는 말**: 기획 문서와 같은 쓰기 규칙을 따른다(docs/planning/03-policies-glossary.md §5). 전문 용어는 글마다 처음 나올 때 푼다.
- **게시**: WBS의 블로그 작업은 담당이 소유자다. 루프는 BUILD_ORDER의 블로그 단계(예: BSL-100 '초안(게시는 소유자 몫)')대로 초안까지 쓴다. 밖에 게시하는 일(블로그 플랫폼에 올리기, 공유)은 외부 게시라 소유자가 한다(docs/architecture.md §8.6). 게시하면 아래 표의 상태 칸에 날짜와 주소를 적는다.
- **파일 이름**: `m<마일스톤 번호>-<주제>.md`(추천 적용 2026-11-03. 이 폴더를 처음 만든 BSL-100에서 정했다). 10편의 목차 정리는 F-08-7(2026-11-25)에서 했다.

## 10편 목차

- **차례의 원칙**: 측정을 마친 직후에 쓴다(ADR-0128). 그래서 아직 초안이 없는 글은 '측정이 끝났는가'로 차례를 정한다. M0·M1은 이미 초안이 있고, M2 3편은 2026-11-24~25 측정이 끝났으며, M6은 100만 외삽을 판정하지 못한 사실을 정리하는 글이라 M2 다음에 쓴다. M5는 S8 데모 화면이 근거이고 측정은 없다. M3·M4는 이번 측정에 측정 증거가 없어 보류다.

- **M2 3편의 범위**: '진입·대기 상태 파일'은 F-08-8 K1(1천·2천·4천·6천·1만·10만)과 F-08-2 MSR-020(X₁=800, 8대까지, 외삽 31.25배)을 쓴다. '좌석 홀드·변경 방송'은 K2 인기 좌석 r2·r3만 유효하고 S-T1에 미달했다는 사실을 숨기지 않는다. '결제 멱등·결과 모름'은 K7 ②의 불변식(이중 결제 0·P6 0·좌석 누수 0)이 3회 깨끗했지만 발생기 무효로 실행 자체는 유효하지 않다는 점을 함께 쓴다.
- **M4·M6의 수치**: 30,000건/초(NFR-009)는 이 PC에서 불가였고 hash 조건 10분 안정은 5,000건/초였다(F-04-8). 100만 외삽은 V-T4를 판정하지 못했고, K1·K2는 미달·무효, K7 ②는 불변식만 깨끗하다(F-08-2·F-08-8). 이 글들은 이 값을 '달성'이 아니라 **'보류·측정 한계'**로만 쓴다. K 수치를 합격처럼 읽히게 쓰지 않는다.
- **M0·M1의 상태**: 두 편은 초안이 있지만 게시 전이다. 게시는 소유자 몫이고, 게시하면 상태 칸에 날짜와 주소를 적는다.
- **새 글을 쓸 때**: 위 표의 행을 바꾸지 않고 상태·날짜만 고친다. 새 측정이 생겨 순서가 바뀌면 이 표의 '순서'와 '상태'를 함께 고치고, 왜 순서를 바꿨는지 이 절에 한 줄 남긴다.
