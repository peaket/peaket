# M4 ② 확장 시간과 비용 — 초안

- **상태**: 초안(2026-11-28, 게시 전)
- **근거**: F-08-14(K9 미측정)
- **숫자 표시**: 측정값은 미측정이고, 비용은 [추정] 또는 미계산이다.
- **게시**: 소유자 몫(publish: owner, draft)

## 1. 무엇을 설명하나

부하가 몰릴 때 앱 복제가 늘어나고 새 파드가 준비되기까지 걸리는 시간(K9)과, 관측 백엔드·온세일 1회·티켓 1,000장당 비용을 어떻게 계산하는지 설명한다. 노드 기동 시간은 AWS가 보장하지 않으므로 문서 인용으로만 다룬다.

## 2. 설계

- K9는 앱 복제 1에서 시작해 부하 시작 → HPA가 복제를 늘린 시각 → 새 파드가 준비된 시각을 읽는다. 목표는 준비까지 60초 미만이다.
- 측정은 기존 진입 측정 실행에 `--hpa-timeline`을 붙여 얻는다. 이 기능은 새 부하를 만들지 않는다.
- 비용은 관측 백엔드 비교 계산(AMP·AMG·Datadog·X-Ray·S3 가격표)과 운영 시간 추정식을 쓴다. 가격표 조회 날짜를 함께 적는다.
- 온세일 1회·티켓 1,000장당 비용은 연간 비용에서 나누는 식만 적고, 실제 값은 유효한 측정 실행이 있을 때 채운다.
- 정본 위치는 `docs/verification.md` §3.10과 `docs/perf-ledger.md` §11이다. 값을 옮겨 적지 않는다.

## 3. 측정 근거

- F-08-14 K9는 **미측정**이다. `--hpa-timeline` 요약이 없어 이 글은 새 측정을 하지 않는다.
- 비용은 **`[추정]`**이다. 입력이 없으면 `미계산`으로 적는다. 청구서나 실측이 아니다.
- 노드 기동 시간은 **문서 인용**이며 실측이 아니다.
- 측정하지 않은 값은 `미측정`으로 적는다.

## 4. 한계

- 로컬 파드 확장 시간은 운영 노드 기동 시간을 대신하지 않는다.
- 가격표는 조회 날짜의 공개 가격이고, 실제 청구서와 다를 수 있다.
- 이 글은 K9 달성이나 비용 절감을 주장하지 않는다.
