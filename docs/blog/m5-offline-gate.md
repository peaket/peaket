# 통신이 끊겨도 입장하는 판정 (M5)

- 이 글은 F-05-9 측정 창 3의 결과를 풀어 쓴 **초안**이다. 게시는 소유자 몫이고, 이 글은 정본이 아니다. 숫자·판정은 [F-05-9 K10 측정 보고서](../review/measurements/F-05-9-k10.md)와 성능 장부 실행 `2026-11-27-f059-k10-r2`에서만 가져왔다.

## 1. 문제: 공연장 망이 끊기면 검표가 멈춘다

티켓 검표를 서버에 매번 물어보는 설계는 공연장에서 약하다. 사람이 몰린 공연장의 기지국은 포화되고, 지하 주차장이나 콘크리트 벽 안에서는 신호가 끊긴다. 그때 스캐너가 서버 응답을 기다리면 입장 줄이 그대로 멈춘다. PEAKET은 이 문제를 K10(오프라인 입장)으로 부르고, v0(처음 만들 법한 온라인 전용 검표)와 v1(단말 로컬 판정)을 같은 조건에서 견준다. v0의 한계는 [v0 기준선 글](m1-v0-breaking-point.md)과 [검증 계획 §3.10](../verification.md)에 이미 적혀 있다.

## 2. 설계: 판정을 단말 안으로 옮긴다

- 지갑은 기기 키로 15초마다 새 QR을 서명한다(ECDSA P-256). 스캐너는 서버에 묻지 않고 그 서명을 단말 안에서 확인한다.
- 스캐너는 회차 목록·키·폐기·입장 상태를 IndexedDB에 저장하고, 60초마다 변경분을 받는다.
- 판정 기록은 먼저 로컬 큐에 `strict`로 쓰고, 온라인이면 5초 묶음으로 올린다. 끊겼다가 돌아오면 바로 올린다. 자세한 정본은 [offline-gate](../features/offline-gate.md) §6·§7이다.

핵심은 "네트워크가 없어도 판정은 단말 안에서 끝난다"이다. 네트워크는 목록·키·입장 상태를 맞추는 데만 쓴다.

## 3. 측정: 무엇을, 어떻게

- 무대: 이 PC의 Chromium 하나에 스캐너 운영 빌드를 띄우고, 스캐너 API는 가짜로 두었다. 판정·큐·화면은 실제 앱 코드다. 실제 관리형 기기·공연장 망·iPhone은 이번에 재지 않았다.
- 표시: **실측(PC, Chromium 흉내)**. 실제 기기 값이 아니다.
- O-T41: 스캐너 한 대·스태프 한 명의 레인을 닫힌 고리(판정 화면이 사라진 뒤 다음 사람)로 10분씩, 온라인 3회·오프라인 3회 돌렸다. 사람 역할 20명이 다음 사람으로 이어지고, 지나가는 사람마다 새 티켓을 썼다.
- O-T40: 300건을 2초 목표로 대고, 150번째에 끊었다가 다시 연결하는 전환 시험이다. 이번 실행은 2초 간격 조건을 지키지 못해 **무효**로 남겼다. 아래 숫자는 O-T41의 유효한 실행에서만 가져온다.

## 4. 결과: 온라인과 오프라인이 같았다

| 항목 | 온라인 | 오프라인 |
| --- | --- | --- |
| 분당 통과 인원(3회) | 27.56·27.59·27.61명/분 | 27.59·27.59·27.60명/분 |
| 판정 p50 | 157.0~158.4ms | 158.7~159.2ms |
| 판정 p95 | 166.4~175.6ms | 167.7~169.2ms |
| 결과 없음·PASS 아님·중복 티켓 | 0·0·0 | 0·0·0 |
| 다시 연결한 뒤 큐 소진 | - | 291~292건, 123~136ms |

- 오프라인 중앙값 ÷ 온라인 중앙값은 **100.02%**로, 기준 90% [가정]를 넘었다. 3+3회 모두 유효했다.
- 끊긴 동안 쌓인 기록 291~292건이 다시 연결한 뒤 123~136ms에 모두 올라갔다. 판정은 네트워크와 무관하게 단말 안에서 끝났다.
- **다만 절대 속도는 분당 27.6명**이다. NFR-010이 가정한 게이트당 분당 60명 환경에는 못 미친다. 이 값은 서버 처리량이 아니라, 앱이 판정 결과를 2초 동안 화면에 유지하고 그 사이 QR 루프를 멈추는 데서 나온 **닫힌 고리 레인의 값**이다.
- 판정 p95도 166~176ms로, 150ms 목표(QR-PE-4)를 넘었다. 화면 스레드에서 QR을 디코딩하고 판정·큐 쓰기·화면 갱신을 하는 현재 구조의 한계다. 판정 Worker로 옮기는 F-05-10 뒤에 같은 하네스로 다시 잰다.

## 5. 배운 것

1. **네트워크가 병목이 아니었다.** 온라인과 오프라인의 분당 인원·판정 지연이 사실상 같았다. 끊긴 동안에도 판정이 멈추지 않았고, 큐는 다시 연결되면 비었다.
2. **병목은 화면 유지와 판정 시간이었다.** 2초 판정 화면 유지 + 약 160ms 판정이 한 건을 약 2.17초로 만들었다. 그래서 2초 고정 간격 시험(O-T40)은 조건을 지키지 못해 무효가 됐고, 레인도 분당 27.6명에 머물렀다.
3. **상대 기준과 절대 기준을 나눠 읽어야 한다.** O-T41의 "오프라인이 온라인의 90% 이상"은 통과했지만, "분당 60명", "판정 p95 150ms"는 아직 아니다. 상대 기준 통과를 절대 성능 달성으로 쓰면 안 된다.

## 6. 한계

- 실제 관리형 기기·공연장 망·iPhone은 미실행이다(F-05-1·F-05-10 경계). 이 글의 값은 Chromium 흉내의 `실측(PC)`다.
- 서버 쪽 판정·중복 입장 표시·입장 기록 마감은 이 하네스가 아니라 F-05-4·F-05-6 통합 시험이 본다.
- O-T40은 이번에 무효다. 2초 간격 조건을 지키지 못했으므로 "전환 중 판정 통과"로 쓰지 않는다.
- 30k/s(F-04-8), 100만·K1·K2·K7(F-08-2·F-08-8)은 이 글의 숫자가 아니다.
- 이 글은 정본이 아니다. 정본과 다르면 정본이 이긴다.
