# API 가이드라인

- **독자와 용도**: 프로그램끼리 요청과 응답을 주고받는 창구인 API를 설계·구현·호출하는 프론트엔드와 백엔드 엔지니어가 보는 기준 문서다. API 버전 관리, RFC 9457 표준 에러 규약, 커서 기반 페이지네이션, 경로 이름과 메서드·상태 코드 규칙(§10~§12), 분산 멱등성(같은 요청이 여러 번 와도 한 번 처리한 것과 결과가 같은 성질), 재시도와 데드라인 전파, 분산 레이트 리밋(일정 시간에 받는 요청 수의 상한), 인증·인가 흐름, 외부 연동 결함 격리 규칙을 여기서 확인한다. 실제 엔드포인트(API를 부르는 주소 하나) 명세는 `openapi.yaml`(REST API)과 `asyncapi.yaml`(비동기 이벤트와 실시간 웹소켓)이 단일 진실 원천, 곧 유일한 기준이다. 코드에서 만든 문서는 이 기준과 견주는 데만 쓴다(§1).
- **원문 출처**: 설계서 22장(버저닝 및 Swagger), 16장(Exception Filters RFC 9457), §6 API 게이트웨이(클라이언트 종류별로 앞에 둔 입구 서버)·장애 격리·계정·인증·결제 연동 아키텍처, 29장 멱등성 제어, 24장 웹훅(일이 생기면 상대 서버가 우리 주소를 불러 알려 주는 방식) 규약, 20장 분산 레이트 리밋, ADR-0008·0009·0011·0015. §10~§12와 §2·§3의 2026-10-21 규칙은 소유자가 준 REST 설계 기준으로 점검해 정했다(ADR-0081).
- **기준 기획 버전**: v1.0.

## 1. 버전 정책과 하위 호환·폐기 절차
- RESTful API는 URI 경로에 버전을 넣는 방식(`/v1`, `/v2`)과 NestJS(Node.js 서버 프레임워크)의 Route Versioning 기능을 쓴다. 필드 추가나 선택적 쿼리 파라미터 추가 같은 하위 호환 변경은 같은 버전 안에서 점진적으로 배포한다. 기존 클라이언트와의 호환을 깨는 변경(브레이킹 체인지)은 새 메이저 버전을 내서 갈라낸다.
- 폐기 예정(Deprecation) API는 응답에 `Deprecation`과 `Sunset` 표준 헤더를 넣어 알리고, `Sunset` 날짜까지 옛 버전과 새 버전을 함께 운영한다. `Sunset` 날짜는 옛 버전이 응답을 멈추는 때다(RFC 8594 §3). `Deprecation`은 RFC 9745(2025-03)의 헤더다. 값은 HTTP 구조화 필드(RFC 9651)의 날짜, 곧 `@`과 유닉스 초다. 폐기 안내 문서는 `Link`의 `rel="deprecation"`으로 건다. `Sunset` 시각은 `Deprecation` 시각보다 이르면 안 된다(RFC 9745 §4 MUST NOT). 두 헤더는 날짜 형식이 다르다(RFC 9745 §4, 2026-10-28 확인, 추천 적용 2026-10-28, 기술 검토 낮음-023). 예:

  ```http
  Deprecation: @1798761600
  Sunset: Thu, 01 Apr 2027 00:00:00 GMT
  Link: <https://developers.peaket.example/deprecations/v1-holds>; rel="deprecation"; type="text/html"
  ```

- **차이 검사 도구와 '깨짐' 기준(추천 적용 2026-10-28, 기술 검토 낮음-019)**: `peaket` 저장소의 `contract-check`(docs/devops.md §3.1)가 PR의 계약을 대상 가지의 계약과, 마지막 출시 태그(운영에 나간 판)의 계약과 둘 다 견준다. 다만 출시 태그가 하나도 없을 때(첫 출시) `main`으로 가는 PR은 견주지 않는다. 운영에 나간 계약이 아직 없고, `main`이 저장소 첫 기록(옛 초안)이라 견주면 모든 정리가 깨짐으로 보이기 때문이다(소유자 결정 2026-11-03, FND-160의 첫 릴리스에서 약 160건으로 막힘). 한 PR이 계약과 양쪽 코드를 함께 바꾸면 같은 커밋끼리의 검사는 통과하지만, 배포 단위마다 따로 나가는 동안 운영의 옛 판과 함께 돌기 때문이다(ADR-0165). 도구는 형식마다 하나다. OpenAPI는 `oasdiff breaking --fail-on ERR`(oasdiff 1.34.1, Apache-2.0, OpenAPI 3.1 지원. 확실히 깨지는 ERR 수준이면 실패하고, WARN 수준은 PR 댓글로만 남긴다), AsyncAPI는 `asyncapi diff <옛> <새> -t breaking`(AsyncAPI CLI 6.2.2. 깨지는 변경이 있으면 실패한다), proto는 `buf breaking`(FILE 규칙), Avro는 로컬 레지스트리(지난 출시 태그의 스키마를 모두 올린 것)의 BACKWARD_TRANSITIVE 검사와 열거 규칙 검사다(2026-10-28 각 도구 문서 확인). Pact(소비자인 프론트엔드가 기대하는 요청·응답을 적은 계약 시험 파일)는 브로커 없이 `packages/contracts/pacts/`에 두고, 제공자가 지금 소비자의 Pact와 마지막 출시 태그의 소비자 Pact를 모두 검증한다(ADR-0165). 이 API에서 '깨짐'은 지금 클라이언트가 고치지 않으면 실패하는 변경이다. 경로·메서드·응답 필드·열거 값·응답 상태 코드를 지우거나 이름을 바꾸기, 선택 입력을 필수로 바꾸기, 요청·응답 필드의 타입·형식을 바꾸기, 오류 `type`의 이름이나 상태 코드를 바꾸기(§2), 이벤트 메시지의 필드·열거 기호를 지우기가 여기에 든다. 깨지는 변경은 이 절의 폐기 절차(새 버전, `Deprecation`·`Sunset`)나 웹훅의 새 `type`, 확장·축소(docs/devops.md §6.5)로만 낸다. 의도해서 깨는 변경(초안 판 안의 정리 등)은 PR에 `breaking-approved` 라벨과 도구의 예외 목록(oasdiff는 `--err-ignore` 파일)에 이유를 적어야 통과한다. 도구 설정(추천 적용 2026-11-01, openspec 변경 `add-contract-breaking-check`): 수준·예외 파일은 docs/api/breaking/에 있다. oasdiff 1.34.1이 INFO로 두는 선택 응답 칸 지우기, 응답 열거 값 지우기, 오류 응답 상태 코드 지우기는 ERR로 올린다. AsyncAPI CLI 6.2.2의 diff는 AsyncAPI 3.0 메시지 본문의 필드·열거 기호 지우기를 분류하지 않아(2026-11-01 확인), 채널·작업은 그 도구가, 메시지 본문은 메시지마다 읽기 작업을 붙인 OpenAPI로 바꿔 oasdiff가 본다. 이벤트의 열거 기호 더하기는 Avro 메시지만 WARN이고(Avro 열거의 `UNRECOGNIZED` 규칙), JSON 메시지는 화면이 생성 Zod로 읽어 깨짐(ERR)이다. 견줄 기준의 대상 가지는 지금 커밋과 갈라진 점이다. 예외가 늘거나 수준 파일을 낮춘 PR에는 `breaking-approved` 라벨이 있어야 한다. 원격 저장소가 생기기 전까지 WARN은 PR 댓글 대신 CI 화면의 경고 표시로 남긴다. 형식(`format`) 바꾸기와 오류 `type` 이름 바꾸기는 이 도구들이 잡지 못해 PR 검토로 본다.
- **파트너에게 약속하는 폐기 기간은 웹훅에 둔다(추천 적용 2026-10-28, 기술 검토 중간-085)**: 파트너 서버가 부르는 공개 API는 없고(ADR-0066), 파트너 시스템이 기대는 계약은 웹훅(이벤트 8종, §8)뿐이다. 웹훅은 같은 `type`의 `data` 구조를 바꾸지 않는다. 바꿔야 하면 판을 붙인 새 `type`(예: `order.confirmed.v2`)을 만들어 옛 `type`과 함께 보내고, 옛 `type`은 폐기를 처음 알린 날부터 최소 90일 뒤에 보내기를 멈춘다(90일은 2026-10-09 추천 적용을 이어받는다). 폐기 예정 `type`은 개발자 포털의 웹훅 문서에 적고, 그 `type`을 구독한 파트너에게 알린다.
- **스캐너 API는 최근 앱 판 2개와 호환한다(docs/devops.md §6.6, 추천 적용 2026-10-29, ADR-0145 결정 4)**: 스캐너 PWA는 새 판을 근무 준비 때만 적용하므로, 현장에는 판이 다른 기기가 함께 있을 수 있다. 그래서 스캐너 API(`/v1/scanner/*`)는 최근 앱 판 2개와 호환되게 하고, 호환을 깨는 변경은 이 절의 폐기 절차를 따른다. 서버가 지원하는 가장 낮은 앱 판은 회차 목록(`GET /v1/scanner/events/{eventId}/package`)과 변경분(`GET /v1/scanner/events/{eventId}/changes`) 응답의 `minAppVersion`(SemVer 문자열)으로 알린다. 모든 응답에 붙여야 하고 교차 출처 노출 헤더가 느는 응답 헤더 방식은 쓰지 않는다. 입장 시간 중에는 판이 낮다고 거부하지 않는다(docs/features/offline-gate.md §6.2).
- **금액 칸의 형식(docs/data.md §2 '금액 칸 자료형', 기술 검토 높음-20)**: API 금액은 원 단위 정수다. 결제 한 건에 딸린 금액(주문·결제·취소 환급·배상·가격)은 `integer`이고, 여러 건을 모은 금액(정산서 항목, 지급 묶음 합계, 지급 건, 미수금, 결제사 잔액, 판매 요약의 합계)은 `format: int64`를 붙인다. 형식이 없는 `integer`를 32비트로 만드는 코드 생성기가 큰 공연 하나의 정산서(25억 원, docs/features/settlement.md J-T4)에서 넘치지 않게 하려는 것이다. 나중에 형식을 바꾸면 §1의 '깨짐'이 되므로 처음부터 붙인다.
- 이벤트를 순서대로 쌓아 두고 여러 곳에 나눠 주는 메시지 시스템인 Kafka의 이벤트 메시지 스키마(데이터의 구조 정의)는 Apache Avro와 Confluent Schema Registry로 BACKWARD_TRANSITIVE 호환성 모드를 강제한다. BACKWARD는 바로 앞 판하고만 대조한다. 그런데 분석 재적재처럼 보관 7일 안의 옛 메시지를 최신 스키마로 다시 읽는 소비자가 있으므로, 모든 이전 판과 대조한다. BACKWARD 계열이므로 소비자를 먼저, 생산자를 나중에 배포한다(docs/devops.md §6.5, ADR-0054). 내부 gRPC(서비스끼리 함수를 부르듯 빠르게 호출하는 통신 방식) 프로토콜은 코드를 올릴 때마다 자동으로 검사하고 빌드하는 과정인 CI에서 `buf breaking` 검증을 거친다. 계약에서 만든 코드(`packages/contracts`)는 패키지로 게시하지 않고 같은 저장소 안에서 `workspace:` 프로토콜로만 쓰므로 패키지마다 판을 매기지 않는다. 계약의 판은 시스템 출시 태그(`vX.Y.Z`)가 말한다(ADR-0165). 모든 API와 이벤트 계약 변경은 `peaket` 저장소의 docs/api/ 한 곳에서만 관리한다.
- **계약 파일이 원본이다(추천 적용 2026-10-28, 기술 검토 중간-085)**: API 계약의 원본은 `peaket` 저장소 docs/api/의 openapi·asyncapi 하나다. 코드에서 만든 문서는 원본이 아니라 대조용이다.
  - 개발자 포털은 docs/api/의 openapi·asyncapi에서 정적 사이트로 만든다(`main` 병합 뒤, docs/devops.md §3.2 계약 행). 공개하는 것은 파트너 웹훅(이벤트 8종의 본문·서명·다시 보내기 규칙)과 오류 `type` 설명 문서(§2)뿐이다. 파트너가 부르는 서버 API가 없기 때문이다(ADR-0066). 서비스는 API 문서 경로를 내지 않는다(ASVS v5.0.0-13.4.5).
  - 서비스의 `@nestjs/swagger` 출력은 CI 안에서만 파일로 뽑아 계약과 견주고, 어긋나면 PR을 실패시킨다(docs/devops.md §3.1 `contract-check`, D-T38). NestJS의 `SwaggerModule.createDocument()`가 만든 문서는 HTTP로 내지 않고 JSON·YAML 파일로 저장할 수 있다(NestJS 문서 'OpenAPI 소개', 2026-10-28 확인).
  - 프론트엔드는 `orval` 코드 생성기로 TypeScript 타입, API 호출 클라이언트, MSW 모킹 핸들러, 요청·응답 Zod 스키마를 모두 계약에서 만든다(orval의 `client: 'zod'`는 OpenAPI에서 Zod 스키마를 만든다, orval 문서 2026-10-28 확인). 화면과 서버(`nestjs-zod`)가 함께 쓰는 입력 검사도 이 생성 스키마가 원본이다. `@peaket/validation`에는 계약에 적을 수 없는 규칙(사람이 한 글자로 보는 grapheme 단위의 길이, 금칙어, 판매 정책 DSL)만 손으로 쓰고, 그 규칙의 이름을 그 필드의 openapi 설명에 적는다(docs/design/d2 §3.1, docs/frontend.md §2.2).
  - **핫패스 경로의 서버 검사(추천 적용 2026-10-28, 기술 검토 낮음-001)**: 입장 확정(queue-svc)과 좌석 홀드·해제·연장·결제 접수(purchase-svc)는 Zod 파이프(`nestjs-zod`) 대신 Fastify 경로 스키마(`@RouteSchema()`의 요청·응답 JSON Schema)로 검사하고 응답을 직렬화한다. 스키마는 같은 생성 Zod 스키마를 빌드 때 Zod 4의 `z.toJSONSchema()`(요청은 `io: "input"`, 형식은 Fastify 예시와 같은 `target: "draft-07"`)로 바꾼 것이라 원본은 그대로 계약 하나다(Zod·Fastify 문서, 2026-10-28 확인). 이 경로들에는 손으로 쓰는 규칙이 없다. 대기열 진입은 2026-11-01 기반 PoC에서 경로 스키마가 요청당 CPU를 줄이지 못해(본문 칸 1~3개) Zod 파이프로 검사한다(ADR-0176 결정 4, 2026-11-02 정합 점검). 사전 요청을 피하려고 `text/plain`으로 받는 대기열 진입·입장 확정(ADR-0065)은 그 형식의 본문 해석기가 JSON으로 읽는다. 본문 스키마는 형식별(`content`)로 나누지 않고 하나만 둔다. Fastify는 본문 스키마 하나를 해석기가 낸 값에 형식과 관계없이 걸지만, 형식별 스키마는 들어온 형식과 맞는 것이 없으면 검사를 건너뛰어 본문 없는 POST가 통과했다(코드 리뷰 2026-11-01, 2026-11-01 확인). 응답 스키마에 없는 칸은 내보내지 않는다. 검사에 실패하면 §2의 Problem 400으로 바꾼다. 두 검사가 같은 값을 받고 거르는지는 CI의 같은 표본 시험(V-T41의 표본 묶음, 서비스 템플릿 시험 `request-checks.test.ts`)으로 본다. V-T41에서 이 방식이 Zod 파이프보다 요청당 CPU를 5% [가정] 넘게 줄이지 못하면 핫패스도 Zod 파이프 하나로 되돌린다(검사 방식이 둘인 비용이 더 크다).
  - **서비스 템플릿의 요청 검사(추천 적용 2026-11-01, openspec 변경 `add-service-structure-and-request-checks`, BUILD_ORDER FND-070)**: `packages/platform`이 두 검사를 이렇게 낸다.
    - Zod 파이프는 처리기 매개변수 장식자 `@ContractBody`·`@ContractQuery`·`@ContractParams`·`@ContractHeaders`(계약 생성 Zod를 받는다)다. `nestjs-zod` 5.5.0은 peer가 NestJS 11까지라(NestJS 12를 쓴다) 같은 일을 하는 파이프를 플랫폼에 두었다.
    - 경로 스키마는 처리기에 `@ContractRouteSchema({ params, query, headers, body, responses })`로 단다(`@RouteSchema()` 대신. 속의 스키마는 `contractRouteSchema()`가 만든다). 플랫폼 검사기는 Ajv 8에서 형 바꾸기(`coerceTypes`)와 칸 지우기(`removeAdditional`)를 끄고 `strictNumbers`를 켠다. Fastify 기본값은 본문의 `"1"`을 숫자로 바꾸고 `additionalProperties: false`의 정의 밖 칸을 지운 뒤 통과시켜 Zod와 달랐고, `strictNumbers`가 꺼지면 JSON의 `1e400`(무한대)이 숫자 칸을 통과했다(코드 리뷰 2026-11-01).
    - `@ContractRouteSchema`를 단 처리기는 검사 결과를 요청에 붙여 두기만 하고(`attachValidation`, 그 장식자만 경로 설정에 미루기 표시를 단다), 인증 가드가 신원·역할을 판정한 뒤 400을 낸다. 인증 가드를 지나지 않는 경로(서비스가 Fastify에 바로 붙인 경로)는 같은 스키마를 써도 이 표시가 없어 Fastify 기본대로 바로 거절한다(다시 본 리뷰·세 번째 리뷰 2026-11-01). 같은 처리기에 경로 스키마와 Zod 파이프를 함께 달지 않는다(경로 스키마가 바꾼 배열을 파이프가 겹친 쿼리로 본다). 그래서 두 길 모두 익명 요청은 본문이 틀려도 먼저 401이다(검사 규칙을 떠보지 못하게, 코드 리뷰 2026-11-01).
    - 남는 차이: 닫지 않은 객체(계약에 `additionalProperties: false`가 없는 것)의 정의 밖 칸을 Zod 파이프는 버리고 경로 스키마는 처리기까지 넘긴다. 처리기는 본문을 통째로 저장소에 펼치지 않고 쓸 칸을 골라 쓴다. 핫패스 요청 본문을 계약에서 닫는 일은 BUILD_ORDER BAS-040이다(authz-matrix §4의 '요청 스키마는 허용한 칸만', 코드 리뷰 2026-11-01).
    - 쿼리·경로·머리는 두 길 모두 검사 전에 계약의 형식대로 문자열을 바꾼다. 머리는 계약에 적힌 칸만 넘기고, 쿼리·경로는 모르는 키도 넘겨 닫은 스키마(`.strict()`)면 거절한다. 숫자는 JSON 숫자 문법만, 불리언은 `true`·`false`만, 배열은 쉼표로 이은 값만 바꾸고, 머리 이름은 대소문자를 가리지 않는다. 같은 이름이 겹쳐 온 쿼리는 형과 관계없이 400이다(asvs/delivery.md 15.3.7).
    - 생성 스키마의 검사 규칙(중복 금지·칸 수·칸 이름 길이)은 생성기가 같은 JSON Schema 낱말을 Zod 메타데이터로도 달아 `z.toJSONSchema()` 결과에 남는다(packages/contracts/README.md).
    - 본문은 `application/json`만 받고, `@AcceptTextPlain()`을 단 경로만 `text/plain`을 JSON으로 읽는다. 그 밖은 415다(asvs/delivery.md 3.5.2).

## 2. 에러 응답 형식 (RFC 9457 Problem Details)
```json
{
  "type": "https://peaket.example/problems/seat-already-held",
  "title": "좌석이 이미 선택되었습니다",
  "status": 409,
  "detail": "A-12는 방금 다른 분이 선택했습니다.",
  "instance": "/v1/events/evt_1/holds/req_9",
  "suggestedSeats": ["A-13", "A-14"],
  "traceId": "0af7651916cd43dd8448eb211c80319c"
}
```
- 도메인 계층의 `Result` 실패 객체는 NestJS 전역 Exception Filter에서 RFC 9457 표준 Problem Details 형식으로 바꿔 돌려준다. 보안을 위해 스택 트레이스(오류가 날 때까지 호출된 함수 목록)나 내부 SQL 쿼리 같은 시스템 민감 정보는 에러 본문에 일체 드러내지 않는다(웹 보안 기준을 만드는 비영리 단체 OWASP의 A10, 그 단체가 만든 웹 앱 보안 검증 항목 목록 ASVS의 v5.0.0-16.5.1). 알 수 없는 예외는 500과 일반 문구, `traceId`만 낸다. 원본 예외와 스택은 같은 `traceId`로 서버 로그와 오류 수집 도구에만 남긴다.
- **디버그 정보(추천 적용 2026-10-21, ADR-0081)**: Problem의 `debug` 확장 필드(예외 종류와 스택 요약)는 로컬·CI(kind)에서 `PEAKET_DEBUG_ERRORS=true`일 때만 싣는다. 기본값은 꺼짐이다. 데모·스테이징·운영 환경 설정에서 켜져 있으면 서비스가 시작하지 않는다(시작 때 설정 검증, ASVS v5.0.0-13.4.2). 소유자가 준 REST 기준(2026-10-21, ADR-0081)은 개발·QA 환경에서 켜는 것을 허용한다. 하지만 데모는 운영과 같은 다이제스트를 검증하는 곳이고, 임시 클라우드 데모로 외부에 열릴 수 있어서 켜지 않는다.
- **오류 본문은 한 형식이다(추천 적용 2026-10-21, ADR-0081)**: 서비스뿐 아니라 게이트웨이가 직접 내는 오류(레이트 리밋 429, 본문 상한 413, 차단기 503, 없는 경로 404)도 같은 Problem 본문을 낸다. 이때 Envoy(요청을 받아 안쪽 서비스로 넘기는 프록시 서버) `local_reply_config`의 `json_format`과 `content_type: application/problem+json`을 쓴다. **게이트웨이 Problem의 요청별 값(추천 적용 2026-10-28, 기술 검토 낮음-023)**: 게이트웨이 정책으로 거는 응답 덮어쓰기(Envoy Gateway `responseOverride`)는 상태 코드마다 고정 본문을 낸다. 본문에 요청마다 다른 값(`traceId`, `instance`)을 넣는 법은 Envoy Gateway 안내서 'Response Override'에 없다. 다만 소스를 보면 Envoy Gateway는 덮어쓸 본문을 Envoy의 치환 형식 문자열(`body_format`의 `text_format`)로 넘긴다. 그래서 본문에 적은 `%TRACE_ID%`(그 요청의 trace-id를 넣는 Envoy 치환 명령) 같은 값이 요청마다 채워질 수 있다(envoyproxy/gateway PR #6297 '응답 덮어쓰기의 동적 변수', 2025-06 병합, `internal/xds/translator/custom_response.go`, Envoy 치환 형식 문서의 `%TRACE_ID%`, 2026-10-29 확인, https://github.com/envoyproxy/gateway/pull/6297 ). 게이트웨이가 스스로 만든 응답에만 거는 `source: Local`은 v1.8.0부터다. 실제로 trace-id가 채워지는지는 아직 확인 필요다. 그래서 기본은 게이트웨이가 만든 Problem에 `type`·`status`·`title`만 싣고(`detail`은 고정 문구), `traceId`·`instance`는 싣지 않는다. 그 요청의 추적 값은 응답 헤더 `X-Trace-Id`(§9)로 잇는다. 먼저 `responseOverride` 본문의 `%TRACE_ID%`가 채워지는지를 PoC로 보고, 안 되면 원시 설정 패치(`EnvoyPatchPolicy`)로 `local_reply_config`를 본다(D-T43, wbs 2.11.1). 되면 그때 본문에 `traceId`를 더한다. `instance`(요청 경로)는 `text_format`이 따옴표 같은 글자를 JSON에 맞게 바꿔 주지 않을 수 있어 싣지 않는다(해석). 화면은 게이트웨이 Problem과 서비스 Problem을 `type`으로만 가르고, `traceId`가 없어도 동작한다. API 경로의 엣지 정적 응답(매진 410)도 CloudFront(AWS의 CDN) Function이 응답 `body`로 Problem 본문(`type` `sold-out`)을 만든다. 예외는 둘이다. 기기 승인 토큰 엔드포인트의 400(아래)과, 대기열 파일 배포처럼 정적 파일을 내는 배포의 404다. 정적 파일 404는 본문을 약속하지 않고, 클라이언트는 상태 코드만 본다(순번을 무작위로 섞은 셔플 결과를 게시하기 전의 404, ADR-0058). openapi의 4xx·5xx 응답은 이 두 예외를 빼고 모두 Problem을 선언한다(`$ref`와 `description` 덮어쓰기, OpenAPI 3.1.0 Reference Object).
- **`type`·상태 코드·`title`은 한 묶음이다(ADR-0081)**: 한 `type`은 언제나 같은 상태 코드와 같은 `title`로 낸다(`title`은 번역만 달라진다, RFC 9457 §3.1.3). 같은 원인을 두 상태 코드로 내지 않는다. 2026-10-21 점검에서 openapi 응답 설명에 이름이 있는 `type`은 모두 상태 코드가 하나였다. 이름 없는 오류의 `type`과 전체 목록(`@peaket/api-client`의 표)은 wbs 0.2.3에서 만든다. `type` URI를 열면 그 오류의 설명 문서가 나오게 한다(RFC 9457 §3.1.1 SHOULD). 설명 문서는 계약(docs/api/)의 `type` 목록에서 개발자 포털 정적 사이트로 만든다(§1). 서비스가 실행 중에 만드는 문서가 아니다. 포털을 올릴 곳(정적 파일 배포와 호스트)은 wbs 0.2.3에서 정한다(추천 적용 2026-10-28, 기술 검토 중간-085).
- **서비스 템플릿의 Problem(추천 적용 2026-11-01, openspec 변경 add-service-template, BUILD_ORDER FND-050)**: 공용 서버 패키지 `packages/platform`의 전역 필터가 위 규칙을 이렇게 낸다.
  - 이름 붙은 오류는 `type`(`https://peaket.example/problems/<이름>`)·`title`·`status`·`detail`(있을 때)·`instance`(쿼리를 뺀 요청 경로)·`traceId`와 그 응답의 확장 필드를 싣는다. 확장 필드가 표준 칸을 덮으면 오류를 만들 때 실패한다.
  - 이름이 아직 없는 HTTP 오류(없는 경로, JSON이 아닌 본문, 본문 상한 등)는 `type: about:blank`와 HTTP 상태 문구(예: `Not Found`)를 제목으로 낸다(RFC 9457 §4.2.1). 설명은 싣지 않는다. 이름 붙은 `type` 목록은 wbs 0.2.3에서 만든다.
  - 알 수 없는 예외는 위 규칙대로 500·`about:blank`·`Internal Server Error`·`traceId`만 내고 `instance`도 싣지 않는다. 오류가 단 `statusCode`(다른 서비스를 부른 HTTP 클라이언트 오류 등)는 믿지 않는다. 응답 상태로 믿는 것은 HTTP 예외의 4xx·5xx와 웹 서버(Fastify) 자체 오류의 상태뿐이다.
  - 처리기를 찾기 전에 웹 서버가 거절한 요청(잘못된 URL 등)도 `about:blank` Problem으로 답하고, 잘못된 경로를 되비추지 않게 `instance`를 싣지 않는다.
  - `traceId`는 그 요청의 OTel 요청 기록 trace-id이고, 기록이 없으면 요청마다 새로 만든 32자리 16진수다. 같은 값이 그 요청의 정규 로그 줄(docs/observability.md §7)에 남는다.
  - 디버그 정보의 '로컬·CI'는 환경 변수 `PEAKET_ENV`(`local`·`ci`·`demo`·`staging`·`prod`)로 가른다. 값이 없으면 운영으로 보고, 그때 `PEAKET_DEBUG_ERRORS=true`면 시작이 실패한다.
  - 요청 검사 실패(두 검사 길, 겹친 쿼리, 깨진 JSON)는 `about:blank`·`Bad Request`·400과 `instance`·`traceId`만 싣는다. 검사기마다 문구가 달라 두 길의 본문이 같도록 `detail`을 싣지 않고 값을 되비추지 않는다. 본문 형식 거절은 `about:blank`·`Unsupported Media Type`·415다. 인증 가드의 거절은 401(`about:blank`, `WWW-Authenticate: Cookie realm="peaket"`)·403(`about:blank`)이고, 역할을 판정할 수 없으면 503 `authz-unavailable`·`Retry-After` 1초 [가정]다. DB 연결 풀 대기 초과는 429 `server-busy`·`Retry-After` 1초 [가정]다(추천 적용 2026-11-01, openspec 변경 `add-service-structure-and-request-checks`). 이름 붙은 400(예: `idempotency-key-invalid`)은 그 모듈이 먼저 낸다.
- 좌석 홀드(결제하는 동안 다른 사람이 가져가지 못하게 좌석을 잠시 잡아 두는 것) 경합에서 정상적으로 진 경우(HTTP 409 Conflict)는 시스템 장애가 아니라 업무상 정상 분기로 보고, 에러 모니터링 통계에서 따로 센다(NFR-003). 서비스 템플릿에서는 오류를 내는 코드가 Problem에 정상 분기 표시를 달고, 그 응답은 `http_server_business_rejections_total`로 센다(docs/observability.md §3, 추천 적용 2026-11-01).
- 서킷 브레이커(계속 실패하는 호출을 잠시 끊어 장애가 번지지 않게 하는 장치)가 열리거나 게이트웨이가 과부하로 차단할 때는 HTTP 503 Service Unavailable 응답과 함께 `Retry-After` 헤더를 필수로 돌려준다. 서비스가 자기 과부하(연결 풀 대기 초과, 벌크헤드 가득)로 거절할 때는 429와 `Retry-After`, Problem `server-busy`로 답한다. 게이트웨이와 메시의 이상 파드 퇴출은 연속 5xx만 세므로, 바쁜 파드가 503을 내면 그 파드가 빠지고 남은 파드에 부하가 몰리기 때문이다(docs/architecture.md §5 부하 관리 장치 표, 추천 적용 2026-10-28, 기술 검토 낮음-140). 서비스 템플릿의 차단기가 열려 의존성을 부르지 않을 때는 503 `dependency-unavailable`(제목 '의존 서비스를 잠시 쓸 수 없습니다')과 시험 호출까지 남은 초의 `Retry-After`를 낸다. 본문에 의존성 이름을 싣지 않는다. 그 의존성의 대체 응답이나 더 알맞은 오류(`seat-store-unavailable` 등)가 있으면 서비스가 그것으로 바꾼다. 이름 붙은 `type` 목록(wbs 0.2.3)에 넣는다(추천 적용 2026-11-01, openspec 변경 add-breakers-purchase-auth-and-grpc-channel). 브라우저는 429와 503을 같은 규칙(`Retry-After` 하한 + 지터)으로 다시 보낸다. 전석 매진 이후 들어온 예매 요청은 CloudFront 엣지(CDN이 사용자 가까이에 둔 서버) 계층에서 HTTP 410 Gone(추천 적용 2026-10-09)과 매진 정적 응답(API 경로는 Problem `sold-out`, 화면 경로는 매진 안내 페이지, ADR-0081)으로 바로 막는다. 회차의 판매 종료(공연 시작 24시간 전) 뒤의 대기열 진입·입장 확정·새 좌석 홀드·주문 생성(판매 종료 전 홀드의 주문은 제외)·취소표 알림 신청은 410 Gone과 `sale-ended` 오류로 거절한다(소유자 결정 2026-10-14, 오류 형식은 추천 적용 2026-10-14, ADR-0064).
- 프론트엔드 애플리케이션은 에러 객체의 `type` URI 식별자에 맞춰 다국어 UX 안내 메시지를 골라 보여 준다(d2 §4).
- 오류 식별자는 `type` URI의 마지막 경로(케밥 표기, 예: `seat-already-held`)로 통일한다. openapi 응답 설명의 대문자 이름(`DUPLICATE_ADMISSION`, `ENTRY_STARTED`, `TRIGGER_DEFERRED`, `NO_PLACEMENT` 등)은 같은 오류의 별칭이고, `type`은 그 이름의 케밥 표기다(예: `DUPLICATE_ADMISSION` → `…/problems/duplicate-admission`). 예외로 기기 승인 토큰(권한이나 상태를 증명하려고 주고받는 서명된 문자열) 엔드포인트(`POST /v1/scanner/token`)는 RFC 8628 §3.5의 OAuth(다른 서비스 계정으로 로그인하게 하는 표준) 오류 형식(`authorization_pending`, `slow_down` 등)을 그대로 쓴다.

## 3. 페이지네이션 (Pagination)
- 대량 목록 조회 API는 커서 기반 페이지네이션(`cursor`, `limit`, 최대 한도 100건(추천 적용 2026-10-09))을 표준으로 쓴다. 정렬 기준은 `sort`에 그 목록이 정한 정렬 이름(예 `LATEST`·`RATING_DESC`·`RELEVANCE`, openapi 열거값)으로 받고, 다음 페이지를 조회할 불투명(Opaque) 커서 식별자를 응답 본문의 `nextCursor` 필드로 준다. 오프셋(건너뛸 앞쪽 행 수)이 커질 때 생기는 건너뛰기 부하를 막으려고 오프셋 기반 페이지네이션(`offset`, `page`)은 엄격히 배제하고, 파트너 콘솔의 대량 명단 다운로드는 청크 스트리밍 API로 따로 지원한다. 예외로 서버 변경 일련번호로 이어 받는 동기화 API(스캐너 변경분 `GET /v1/scanner/events/{eventId}/changes`)는 `after`·`limit`(최대 5,000)·`hasMore`를 쓴다(빠짐 없이 일련번호로 이어 받아야 해서다). 또 하나의 예외는 공연 검색(`GET /v1/search`)이다. 결과 화면이 페이지 번호(이전 · 1 2 3 … n · 다음)와 주소 `?q=&page=`를 쓰므로(소유자 결정 2026-10-14, ADR-0063) `page`와 `limit`(20 [가정] 하나만 받는다. 같은 검색이 `limit` 값마다 다른 캐시로 쪼개지지 않게 다른 값은 400이다, ADR-0094)를 받고 `total`·`totalPages`를 준다. 오프셋 부하는 `page × 20` 1,000 [가정] 상한과, 결과를 CDN(사용자 가까운 곳에 파일을 복사해 두고 대신 응답하는 전송망)에 복사해 두는 30초 [가정] 캐시로 묶는다(추천 적용 2026-10-14, ADR-0063). 내 문의 내역(`GET /v1/inquiries`)도 화면이 페이지 번호를 써서 같은 `page`·`limit`를 받고 `total`을 준다. 한 계정의 목록이라 오프셋 부하가 작다(추천 적용 2026-10-19, ADR-0066).
- **한 번에 받을 건수의 이름은 `limit` 하나다(추천 적용 2026-10-21, ADR-0081)**: 커서 방식이든 페이지 번호 방식이든 `limit`이다(소유자 기준의 예 `?page=2&limit=50`과 같다). 예전 이름 `size`는 쓰지 않는다. 페이지 번호는 1부터 센다. `limit`이 최대값을 넘으면 400이다(잘라서 받지 않는다).
- **목록이면 나눈다(ADR-0081)**: 목록을 주는 GET은 커서(`cursor`·`limit`·`nextCursor`)나 위의 예외 방식으로 나눈다. 나누지 않는 목록은 건수 상한이 정해진 작은 목록뿐이다(로그인한 기기 최대 5대(POL-019), 로그인 수단 3종, 좌석맵 템플릿 10종, 공연 리포트 판 R0~R3, 회차 하나의 결제사별 정산서). 2026-10-21에 마이 티켓·굿즈 상품·미수금(파트너에게서 돌려받을 돈)·스캐너 기기·스캐너 이상 표시 목록에 커서를 더했다. 결과가 0건이면 404가 아니라 200과 빈 `items`다(§12).
- **왜 오프셋이 아니라 커서인가**: 소유자 기준은 페이지 번호와 offset 방식을 예로 든다. 오프셋 방식은 뒤 페이지로 갈수록 앞 행을 모두 건너뛰므로 큰 목록에서 느려진다. 그사이 새 행이 들어오면 중복·누락이 생긴다. 그래서 기본은 커서이고(Zalando RESTful API 지침 [160]도 커서를 권한다) 화면이 페이지 번호를 보여 주는 두 목록만 페이지 번호 방식이다. 커서 방식에서 '필요한 페이지를 요청한다'는 기준은 `nextCursor`로 다음 페이지를 고르는 것으로 채운다. 원하는 번호로 바로 건너뛸 수 없는 것은 커서 방식의 한계로 받아들인다. 큰 목록에는 전체 건수를 주지 않는다(Zalando [254]). 검색의 `total`은 위의 `page × limit` 상한으로 묶는다.

## 4. 멱등성 키 (Idempotency Key)
- 다시 보내면 효과가 두 번 생길 수 있는 쓰기 요청(좌석 홀드, 주문 생성, 결제 접수, 예매 취소, 티켓 양도(요청·수락·거절·철회)·돌려주기, 굿즈 주문, 운영 명령, 승인 업무 요청, 게시물 신고, 고객 문의 접수·추가 문의와 답변, 판매자 정보 변경 요청 등 openapi에서 `IdempotencyKey` 파라미터가 붙은 작업)은 클라이언트가 만든 UUID v4 형식의 `Idempotency-Key` 헤더를 필수로 요구한다. 원래 멱등인 작업(DELETE, 같은 요청이 다시 와도 결과가 같은 상태 전이·승인)과 기록마다 ID를 가진 동기화(게이트 스캔 업로드는 단말이 만든 스캔 ID로 거른다)는 이 헤더를 요구하지 않는다. 같은 멱등키로 다시 요청이 들어오면 비즈니스 로직을 다시 실행하지 않고, 처음 커밋한 캐시 응답을 바로 돌려준다.
- **키 규칙(추천 적용 2026-10-28, 기술 검토 중간-046)**: IETF 초안 'The Idempotency-Key HTTP Header Field'(draft-ietf-httpapi-idempotency-key-header-08)의 처리 규칙을 따른다. 초안은 같은 키를 다른 본문에 다시 쓰면 422, 첫 요청이 아직 처리 중이면 409, 키가 없으면 400으로 답하라고 권하고, 키의 보관 기간을 서버가 정해 알리라고 한다(2026-10-28 원문 확인).

  | 항목 | 규칙 |
  | --- | --- |
  | 범위 | 키는 '부른 계정 × 작업' 안에서만 같은 키로 본다. 작업은 메서드와 경로 틀이다(예: `POST /v1/orders/{orderId}/payments`). 다른 계정이 같은 키를 보내면 남의 응답을 받지 않고 따로 처리된다 |
  | 요청 지문 | 첫 요청을 받을 때 키와 함께 요청 지문(메서드, 실제 경로, 본문 바이트의 SHA-256)을 저장한다. 헤더는 지문에 넣지 않는다. 구매 세션 일련번호·요청 서명·재인증 토큰·추적 헤더는 다시 보낼 때마다 새로 만들기 때문이다(docs/frontend.md §4.1). 그래서 클라이언트는 같은 동작을 다시 보낼 때 처음 만든 본문 문자열을 그대로 보낸다 |
  | 다른 본문 | 같은 범위·같은 키에 지문이 다른 요청이 오면 처리하지 않고 422 `idempotency-key-reused`로 답한다. 클라이언트 버그이므로 클라이언트는 자동으로 다시 보내지 않고 오류 수집에 남긴다. 내부 gRPC의 `ALREADY_EXISTS`(docs/api/proto/README.md §2)와 같은 경우다 |
  | 처리 중 | 첫 요청이 아직 끝나지 않았을 때 같은 키·같은 지문이 오면, 첫 요청이 끝나기를 짧게(1초 [가정]) 기다렸다가 그 응답을 돌려준다. 그 안에 끝나지 않으면 409 `idempotency-request-in-progress`와 `Retry-After: 1` [가정]로 답하고, 클라이언트는 같은 키로 다시 보낸다. PostgreSQL에 키를 두는 작업은 키 행을 넣는 문장에 `SET LOCAL lock_timeout`을 걸어 이 기다림을 묶는다 |
  | 돌려주는 응답 | 처음 요청이 커밋한 결과만 저장해, 같은 상태 코드와 본문으로 돌려준다. 아무것도 바꾸지 않고 끝난 실패(검증 오류, 좌석 경합 409, 한도 초과 422, 429, 5xx)는 저장하지 않으므로, 같은 키로 다시 보내면 다시 처리한다 |
  | 보관 기간 | 좌석 홀드는 홀드 TTL(7분, POL-012)과 같다. 주문 생성·결제 시도 시작·결제 접수와 그 밖의 쓰기는 24시간 [가정]이다. 기간이 지난 키는 새 요청으로 처리한다. 결제사로 보내는 키의 보관 기간은 결제사가 정한다(아래) |
  | 형식 | 값은 따옴표 없는 UUID다(RFC 9562 v4, 브라우저의 `crypto.randomUUID()` 값). 초안은 이 헤더를 구조화 필드의 문자열(큰따옴표로 감싼 값)로 정하지만, PEAKET API는 브라우저 값을 그대로 쓰려고 따옴표 없는 UUID만 받는다(의도한 차이). 키가 없거나 UUID가 아니면(큰따옴표로 감싼 값 포함) 400 `idempotency-key-invalid`다. 초안대로 따옴표를 붙이는 외부 클라이언트를 받게 되면 따옴표를 벗겨 받는 쪽으로 바꾼다. 결제사로 보내는 키는 결제사 규격을 따른다(포트원은 큰따옴표로 감싼다, 아래) |

- **공용 멱등 모듈(추천 적용 2026-11-01, openspec 변경 add-idempotency-and-outbox)**: 서비스 템플릿(`packages/platform`)의 처리기 장식자 `@Idempotent({ operation })`가 위 규칙을 한곳에서 한다.
  - 키는 머리 스키마가 아니라 멱등 모듈만 본다. 두 검사 길의 Nest 장식자(`@ContractHeaders`, `@ContractRouteSchema`)가 머리 스키마에서 `Idempotency-Key` 칸을 빼고, 인증 가드가 신원을 판정한 바로 뒤에 키를 본다. 그래서 순서는 두 길 모두 '익명 401 → 키 400 `idempotency-key-invalid` → 모양 400 `about:blank`'다. 계약이 키를 요구하는 머리 스키마를 단 처리기에 `@Idempotent`가 없으면 서비스가 시작하지 않는다(빠뜨리면 키 없는 요청이 통과해 다시 보낸 요청을 두 번 처리한다). 인증 가드를 지나지 않는 경로(서비스가 Fastify에 바로 붙인 경로)의 경로 스키마 함수는 키를 스키마에 남긴다(코드 리뷰 2026-11-01).
  - 형식: 머리가 정확히 하나이고 값이 따옴표 없는 UUID v4(판 자리 4, 변형 자리 8~b)일 때만 받는다. 같은 머리 둘, 큰따옴표로 감싼 값, 다른 판(v1·v7)은 400이다. 대소문자는 가리지 않고 소문자로 맞춰 저장한다.
  - 지문: SHA-256(메서드 + LF + 요청 대상 + LF + 본문 바이트). '실제 경로'는 받은 그대로의 경로와 쿼리다(구매 세션 요청 서명의 '경로와 쿼리'와 같다). 본문 바이트는 플랫폼 본문 해석기가 해석 전에 남긴 원시 바이트(`rawBodyOf()`)이고, 본문이 없으면 빈 바이트다.
  - 예외 하나(추천 적용 2026-11-04): 좌석 홀드(`POST /v1/events/{eventId}/holds`)는 이 지문을 쓰지 않고, 처리기가 좌석 선택(정렬한 `seatIds`)만으로 지문을 만들어 홀드 Lua에 넘긴다. 구매 세션의 첫 홀드 요청에만 싣는 행동 요약(`behavior`)이 달라도 같은 요청으로 보려는 것이다. 키 형식 검사·검사 순서·범위는 이 모듈이 그대로 맡는다(docs/features/seat-hold.md §3 '멱등키').
  - 범위의 '작업'은 장식자의 `operation`(그 서비스 작업 목록의 이름, 멱등 기록 표의 `CHECK`)이다. 공개 역할을 허용한 처리기에는 달 수 없다(계정이 없을 수 있어 시작 때 실패).
  - PostgreSQL에 키를 두는 작업은 `IdempotencyStore.run(tx, 요청, { execute, replay })`로 키 행을 업무 쓰기와 같은 트랜잭션의 첫 쓰기로 넣는다. 키 행을 넣는 문장만 `lock_timeout` 1초 [가정]로 묶고 곧 역할 기본값으로 돌린다. 핫패스 역할의 문장 한도(1초)나 남은 데드라인으로 건 한도가 키 기다림보다 먼저 끝나도 같은 409다(코드 리뷰 2026-11-01). 409 처리 중은 정상 분기로 센다(오류율에 넣지 않는다).
- 멱등 상태 저장소: 좌석 홀드 멱등키는 메모리에 데이터를 두는 빠른 저장소인 좌석 Redis 클러스터의 회차 샤드 키 `s:{event:E}:idem:{account}:{key}`에 둔다. 홀드 Lua가 좌석을 잡는 같은 원자 연산에서 키를 확인하고, 처음 잡을 때 지문과 응답을 함께 적는다. 그래서 같은 키의 두 요청이 함께 와도 좌석은 한 번만 잡히고 둘 다 같은 응답을 받는다(추천 적용 2026-10-28, 기술 검토 중간-046. 이전의 `s:idem:{key}`는 해시 태그가 멱등키라 Lua 전에 따로 확인해야 했고, 그사이 같은 키의 동시 요청을 막지 못했다, docs/data.md §3, docs/features/seat-hold.md §3). 주문·결제 멱등키는 관계형 데이터베이스인 PostgreSQL의 원장 테이블과 같은 트랜잭션(여러 변경을 한꺼번에 반영하거나 한꺼번에 취소하는 작업 단위) 안에서 원자적으로 커밋한다. PG사(온라인 결제를 대신 처리해 주는 결제사)의 결제 승인은 `Idempotency-Key: confirm-{orderId}`, 결제 취소는 `cancel-{cancellationId}` 형식으로 통일한다. PEAKET이 연동하는 외부 결제사는 멱등키 유효 수명이 서로 달라서(토스페이먼츠 15일, 포트원 3시간), 재시도 유효 윈도우는 보수적으로 3시간 이내로 묶는다. 이 시한을 초과하면 결제 단건 조회 API로 그전 상태를 확인하고 나서 처리를 이어 간다. 포트원 어댑터는 HTTP 구조화 필드 규약(RFC 9651. RFC 8941을 대체했다, 2026-10-28 확인, 기술 검토 낮음-023)의 문자열 형식에 따라 멱등키 값을 큰따옴표로 감싸 보낸다.
- 비동기 Kafka 컨슈머(메시지를 읽는 쪽)는 이벤트 고유 ID로 거르는 멱등 컨슈머 패턴을 필수로 쓴다. 현장 게이트 스캔 로그는 클라이언트 단말이 직접 만든 UUID를 기준으로 중복 처리를 막는다.

## 5. 재시도와 데드라인 전파 (Timeouts and Deadlines)
- Envoy API 게이트웨이가 들어온 요청의 경로별로 최대 허용 시간(Deadline)을 정해 헤더에 넣는다. 백엔드 마이크로서비스는 gRPC 컨텍스트로 남은 유효 시간을 이어받고, 이 시간은 줄어들기만 한다.
  - **헤더와 서비스 쪽 받기(추천 적용 2026-11-01, openspec 변경 add-service-template, BUILD_ORDER FND-050)**: 헤더는 `x-peaket-deadline-ms`(밀리초 양의 정수)다. 게이트웨이는 HTTPRoute의 요청 헤더 바꾸기(`set`)로 경로마다 정한 값을 덮어써 넣으므로, 바깥에서 보낸 같은 이름의 값은 남지 않는다(게이트웨이 설정은 wbs 2.11.x). Envoy가 붙이는 `x-envoy-expected-rq-timeout-ms`는 Envoy 문서가 '내부 요청에 붙인다'고만 적어(2026-11-01 원문 확인) 바깥 요청의 첫 구간에서 믿을 수 없어 쓰지 않는다.
  - 서비스 템플릿(`packages/platform`)은 받은 때부터 min(헤더 값, 서비스 상한)을 남은 시간으로 둔다. 헤더가 없거나 양의 정수가 아니면 서비스 상한이다. 상한 기본값은 15,000ms(Envoy 경로 시간 초과 기본값, docs/infra.md §4.1)이고 `PEAKET_MAX_DEADLINE_MS`로 바꾼다. 다음 호출에는 min(남은 시간, 그 호출의 상한)을 주고, gRPC에는 절대 시각으로 준다.
  - 남은 시간이 다음 단계에 필요한 시간보다 모자라면 시작하지 않고 504와 Problem `deadline-exceeded`로 끝낸다. 게이트웨이 시간 초과도 504라 클라이언트가 보는 결과가 같다. 시각은 주입한 시계로 잰다. 다음 단계(다운스트림)에 남은 실행 시간이 기준값 미만이면 불필요한 연산을 막으려고 바로 실패(Fail-Fast) 처리한다(예: 좌석 홀드 전체 데드라인 40ms, 승인 명령 접수 데드라인 200ms [가정], 주문-결제-발권 종단 확정 3초). 결제사 승인 HTTP 호출은 데드라인으로 끊지 않는다. 두 결제사 권장대로 읽기 시간 초과 60초 [가정]까지 기다리고, 2초는 '임박' 경보와 측정의 기준으로만 쓴다(docs/architecture.md §5, 추천 적용 2026-10-28, 기술 검토 높음-16).
  - **좌석 Redis 호출(추천 적용 2026-11-04, BUILD_ORDER PRF-135, docs/features/seat-hold.md §3 '좌석 Redis 호출 마감')**: purchase-svc는 좌석 Redis를 부르기 전에 남은 시간이 5ms [가정] 미만이면 부르지 않고 504 `deadline-exceeded`로 끝낸다. 부를 때의 마감은 min(남은 시간, 100ms)이다(100ms는 핫패스 Redis 호출 상한, docs/architecture.md §5 '시간 초과 기본값'). 호출 도중 마감을 넘기면 504가 아니라 지금처럼 503 `seat-store-unavailable`과 `Retry-After`다. 같은 멱등키로 다시 보내면 처음 결과를 받는다(§4).
- 일시적인 네트워크 전송 오류의 재시도는 서비스 메시(서비스끼리 주고받는 통신을 앱 대신 처리하는 층) 제품인 Istio의 프록시 계층에서, 미리 정한 재시도 예산(Retry Budget) 한도 안에서만 한다(기본값 덮어쓰기는 docs/architecture.md §5, ADR-0082). API 게이트웨이와 애플리케이션 코드는 네트워크 레벨에서 무분별하게 재시도하지 않는다. 상태 변경 요청은 멱등키가 있더라도 게이트웨이 레벨에서 자동 재시도하지 않는다. 같은 요청을 겹쳐 보내는 헤지 요청은 어느 경로에도 쓰지 않는다. 좌석 배치도 스냅샷 재요청도 헤지하지 않고, 늦거나 503이면 브라우저가 `Retry-After`와 지터를 지켜 다시 묻는다. 같은 구역은 한 번에 하나만 묻는다(ADR-0117. ADR-0087 결정 21의 스냅샷 헤지를 대신한다, docs/architecture.md §5).
- 외부 결제 대행사의 승인 실패를 다시 시도하는 업무 재시도는 payment-svc가 내부 작업 큐와 PG사 유효시간(토스 10분)을 기준으로 세밀하게 통제한다. 예매 취소와 환불 실패 건의 재시도도 payment-svc 워커가 맡는다.
- 클라이언트 브라우저는 서버가 준 다시 시도 시각(`Retry-After` 헤더, 본문의 `retryAfterSeconds`·`pollHintMs`)을 하한으로 지켜 그보다 이르게 보내지 않고, 그 위로만 0~20% 지터(Jitter: 재시도 시각을 일부러 조금씩 흩뜨리는 것)를 더해 재시도 폭주를 흩는다. 기다림은 `하한 × (1 + U(0, 0.2))`(U는 고른 무작위 값)다. 하한을 지키는 지터를 아래쪽으로도 주면 하한이 깨지고, 하한으로 자르면 503을 같은 1초에 받은 사람들이 정확히 같은 때 다시 온다(추천 적용 2026-10-28, 기술 검토 중간-038). 하한이 없는 주기 요청은 ±20% 지터를 쓴다. 대기실 상태를 정해진 간격으로 다시 물어보는 폴링은 예상 대기 시간에 따라 0.5초, 5초, 20초의 적응형 주기로 자동으로 바뀐다(ADR-0110).
- Google SRE Book 22장 지침에 따라 요청 하나당 최대 재시도 횟수를 제한하고, 서비스 사이 네트워크 재시도 예산은 메시 DestinationRule `retryBudget`(진행 중 요청의 10% [가정, wbs 4.6.1에서 확정], docs/architecture.md §5)으로 지킨다. 브라우저 자동 재시도는 한 페이지에 분당 60회를 넘지 않는다(docs/frontend.md §4.1).
- **gRPC 클라이언트 채널 규칙(추천 적용 2026-10-22, ADR-0082)**: 서비스 사이 gRPC 채널은 서비스 템플릿의 채널 생성 함수 하나로만 만든다.
  - 재시도·헤지 정책(서비스 설정의 `retryPolicy`·`hedgingPolicy`)을 넣지 않고 `grpc.enable_retries`를 끄지 않는다. 그러면 라이브러리는 서버 앱이 받기 전에 실패한 요청만 투명하게 다시 보낸다(gRPC A6). 메시 없는 포트폴리오 실행에서 남는 재시도는 이것뿐이다.
  - 받은 데드라인에서 남은 시간을 계산해 넘기고, 추적 헤더는 OTel SDK가 넘긴다. 메시는 이 둘을 대신하지 못한다(docs/architecture.md §5 '메시와 앱의 책임 경계').
  - 부하 분산 방식은 설정 값 `grpcLbProfile` 하나로 고른다. `service`(기본)는 Service 이름과 pick_first를 쓰고, 운영에서는 메시 웨이포인트가 요청 단위로 나눈다. `headless-round-robin`은 메시 없는 로컬에서 서비스 사이 gRPC를 여러 벌로 재는 측정 전용이며, 헤드리스 Service·`round_robin`·서버 `grpc.max_connection_age_ms`를 쓴다. 앰비언트 메시에서 파드(쿠버네티스에서 앱이 실행되는 가장 작은 단위) 주소로 보내면 웨이포인트를 건너뛰므로 운영 오버레이에서는 쓸 수 없다(docs/devops.md §4.3).
  - 채널 생성 함수(추천 적용 2026-11-01, openspec 변경 add-breakers-purchase-auth-and-grpc-channel): `packages/platform`의 `createGrpcClient`다. 주소는 `dns:///<호스트>:<포트>`이고, 채널 설정은 `grpcChannelOptions`가 만든다. 서비스 설정(JSON)에는 부하 분산 방식만 넣고(`service`는 `pick_first`, `headless-round-robin`은 `round_robin`), DNS TXT로 오는 서비스 설정은 읽지 않으며(`grpc.service_config_disable_resolution`, 바깥 설정으로 재시도 정책이 들어오지 않게), 의존성마다 따로 연결을 둔다(`grpc.use_local_subchannel_pool`, 벌크헤드). 이 넷과 `grpc.enable_retries`는 덧붙일 설정으로 바꿀 수 없다(바꾸려 하면 예외). 호출마다 붙는 가로채기가 남은 시간과 호출 상한 가운데 짧은 쪽을 데드라인으로 걸고(이미 건 데드라인이 더 짧으면 그대로), 호출 span(CLIENT, `rpc.system` grpc)을 열어 추적 머리를 메타데이터에 싣고, 소요 시간을 정규 로그 줄 `dep[<의존성>]`에 더한다. 채널 자격 증명은 평문이다(파드 사이 mTLS는 메시가 맡는다). `headless-round-robin`의 서버 `grpc.max_connection_age_ms`는 30초 [가정]이다(`grpcServerOptions`, 새 파드가 늘어도 연결이 다시 고르게 퍼지게). 설정 값은 `PEAKET_GRPC_LB_PROFILE`(기본 `service`)이고 `headless-round-robin`은 `local`·`ci` 환경에서만 받는다(그 밖에서는 서비스가 시작하지 않는다).
  - 앱 코드에 일반 네트워크 재시도, 클라이언트 쪽 분산 로직, 파드 사이 TLS(통신을 암호화하는 표준)를 넣지 않는다. 저장소 클라이언트(PostgreSQL·Redis·Kafka)의 재시도·시간 초과는 docs/architecture.md §5 '시간 초과 기본값'을 따른다.

## 6. 분산 레이트 리밋 (Rate Limiting)
- 요청이 가장 많이 지나 트래픽이 몰리는 핫패스 구간(대기열 순번 진입, 좌석 홀드, 결제 주문 접수)은 외부 메모리 저장소를 조회하는 부담을 피하려고 Envoy 게이트웨이 각 파드의 로컬 메모리 토큰 버킷으로 1차 분산 방어를 한다. 반면 사용자 계정 단위의 전역 레이트 리밋은 Envoy Gateway 전역 레이트 리밋(Envoy가 gRPC로 묻는 레이트 리밋 서비스, Envoy Gateway가 배포한다. 카운터는 Redis 세션·캐시 클러스터)으로 일반 API 경로에만 골라 적용한다. 판정을 받지 못하면 열림(통과)이고 로컬 토큰 버킷이 남는다(docs/architecture.md §4 '전역 레이트 리밋 서비스', 추천 적용 2026-10-28, 기술 검토 중간-084). 판정 시간 상한은 20ms이고 `failClosed`는 끈다(Envoy Gateway 기본값). 열림이 이어지면 SEV3(`kind` cause)로 알린다 [가정, wbs 2.11.1에서 확정]. 전역 한도의 카운터는 경로마다 따로다. 그래서 로그인 사용자당 60회/분처럼 여러 경로를 함께 세는 한도는 공유 설정(`shared`)으로 한 버킷에 묶는다 [가정, PoC에서 확인]. 묶지 않으면 같은 한도가 경로마다 따로 걸린다. 관제 경로(gw-ops)는 전역 레이트 리밋에 붙이지 않는다. 전역 레이트 리밋은 세션·캐시 Redis와 일반 노드 풀에 기대는데, 관제 입구는 거기서 뗐기 때문이다(ADR-0102). gw-ops의 계정당 한도는 게이트웨이가 넣은 내부 사용자 헤더 기준의 파드별 로컬 토큰 버킷이다(추천 적용 2026-10-29, ADR-0145 결정 1). 한도를 초과하면 HTTP 429 Too Many Requests 응답과 함께 `Retry-After` 헤더를 돌려준다.
- **로컬 한도는 파드별이다(추천 적용 2026-10-28, 기술 검토 낮음-022)**: 로컬 토큰 버킷은 Envoy 파드마다 따로 센다. CloudFront와 NLB를 거친 한 기기의 요청은 여러 게이트웨이 파드로 흩어질 수 있으므로, 실제로 받아 주는 양의 상한은 '파드 수 × 파드별 한도'다(예: 기기당 10회/10초에 파드 30개면 최대 300회/10초). 그래서 로컬 한도는 몰리는 양을 덜어 내는 장치로만 쓰고, 정확한 사람·기기당 한도는 뒤층이 맡는다: 대기열 진입은 1인 1순번 선점(같은 사람이 번호를 둘 받지 못한다, docs/features/queue-admission.md §3), 사전 검증 토큰과 위험 판정(trust-svc), 구매 경로는 한 구매 세션에 묶인 입장 토큰이다. 봇 방어 계산과 부하 시험의 기대값은 이 상한으로 잡는다. 파드 수별 실효 한도 표는 docs/features/queue-admission.md §3에 있다.
- 초기 제한 기준값 [가정, Phase 2 부하 시험에서 확정]: 대기열 진입 경로는 단말 기기당 10회/10초, 일반 REST 엔드포인트는 로그인 사용자당 60회/분, 파트너 콘솔은 테넌트당 600회/분을 기본으로 한다. 스테이징 부하 시험 결과에 따라 조정한다. 분석 저장소를 읽는 리포트·결정 기록 API는 따로 낮춘다(추천 적용 2026-10-26, ADR-0089): 리포트 조회(`GET /v1/ops/events/{eventId}/reports`, `GET /v1/ops/events/{eventId}/reports/{stage}`, `GET /v1/partner/events/{eventId}/report`)는 계정당 30회/분, 결정 기록 쓰기(`POST /v1/ops/decisions`, `PATCH /v1/ops/decisions/{decisionId}`)는 계정당 10회/분 [가정, Phase 4 4.3.6에서 확정]이다. 관제(gw-ops) 경로의 이 한도는 파드별 로컬 버킷이라 실효 상한은 'gw-ops 파드 수 × 한도'다. 관제 사용자가 적어 이만큼 느슨한 것을 받아들이고, 정확한 계정당 상한이 필요해지면 ops-svc가 ops DB로 센다(추천 적용 2026-10-29, ADR-0145 결정 1). 파트너 리포트 조회는 테넌트당 600회/분에도 함께 센다. 그 뒤에서 ClickHouse 사용자마다 거는 상한은 docs/features/analytics.md §11에 있다.

## 7. 인증 및 인가 아키텍처 흐름
- 일반 사용자 소셜 로그인: 소비자 웹 앱 서버의 얇은 OIDC 클라이언트(로그인 중 가로챈 코드를 못 쓰게 하는 PKCE, state, nonce 검증. 자체 세션 쿠키 없음, 추천 적용 2026-10-28, ADR-0119) → 소셜 제공자 인가 → ID 토큰 서명 검증 → 내부 서비스 메시의 mTLS 경로로 identity-svc 세션 생성 → 마지막으로 ES256 서명 JWT(서명된 정보 묶음 형식의 토큰) 액세스 토큰(유효기간 15분, `sub`, `sid`, `scope`, `pid`, `aud` 클레임 포함)과 참조형 리프레시 토큰(토큰 패밀리 기반 회전과 재사용 감지)을 발급한다. 두 토큰은 `httpOnly`, `Secure`, `SameSite=Strict` 쿠키(브라우저가 사이트별로 저장했다가 요청마다 함께 보내는 작은 값)에 담아 단말에 격리해 보관한다. 두 쿠키는 소비자 웹 앱 서버가 주고 다른 호스트의 게이트웨이(액세스는 `gw-fan`·`gw-queue`, 리프레시는 `gw-fan`의 토큰 갱신)가 읽으므로 `Domain=peaket.example`과 `__Secure-` 접두사를 붙인다(액세스 `__Secure-peaket_at`, 리프레시 `__Secure-peaket_rt`는 경로를 토큰 갱신으로 제한). 한 호스트만 쓰는 쿠키는 `__Host-` 접두사다(추천 적용 2026-10-15, docs/features/identity.md §3).
- 게이트웨이 무상태 검증: 인그레스 게이트웨이는 메모리에 캐시한 JWKS 공개키로 서명 무결성, 토큰 만료, 토큰 유형(`typ`), 발급자(`iss`), 대상자(`aud`), 경로 접근 권한을 빠르게 검증한다(ADR-0050 결정 9). 그다음 검증된 사용자 ID, 세션 ID, 권한 스코프, 가명 식별자 `pid`(ADR-0053)를 표준 내부 헤더에 넣어 업스트림으로 넘긴다. 역할과 파트너 테넌트는 토큰에 없고, 서비스가 요청마다 identity에 물어 판정한다(소유자 결정 2026-10-31, ADR-0172). 바깥 요청에 붙은 같은 이름의 헤더는 먼저 지운다(docs/security/authz-matrix.md §3.1, ADR-0157 결정 8). 백엔드 서비스는 팬 요청에서는 넣어 준 내부 헤더와 메모리 안의 세션 무효화 목록(세션 종료 이벤트를 받아 15분 보존)만 조회해서, 실행 중 데이터베이스 부하를 0으로 묶는다. 관리 경로는 여기에 더해 공통 가드가 요청마다 identity-svc `AdminAuthzService.GetAdminAuthz`로 역할·테넌트를 묻고, 파드마다 (계정, 세션)으로 5초 [가정] 캐시한다. 현장 스태프 요청은 요청마다 부르는 `ScannerSessionCheckService.CheckScannerSession`의 역할로 판정한다(2026-11-01 정합 점검, ADR-0172 결정 2). 내부 인증 헤더는 양쪽이 서로 인증서를 확인하는 mTLS의 신뢰 경계 덕분에 게이트웨이와 인가된 내부 파드만 넣을 수 있다.
- 예매 핵심 경로 인가: 본인확인을 마친 계정의 액세스 토큰에만 `ticket:buy` 권한 스코프를 준다. 실제로 예매에 들어갈 때는 1회성 입장 토큰(구매 세션 전용)이 필수다. purchase-svc는 입장 토큰의 고유 식별자(`jti`)를 처음 쓸 때 Redis `SET NX`로 한 구매 세션에 묶는다. 그리고 토큰의 `sid`가 요청자의 세션과 같은지 확인하고, 이후 요청은 그 구매 세션의 키로 서명해야 받는다(ADR-0050 결정 8). 그래서 토큰 사본만으로는 다른 세션에서 쓰지 못한다. 좌석 Redis 페일오버(고장 난 쪽 대신 예비 쪽으로 넘기는 것) 때 복제되지 않은 묶음은 사라질 수 있다. 그때 다시 묶을 수 있는 요청은 같은 `sid`의 것뿐이다.
- 관리자 및 파트너 계정: 파트너 콘솔은 `gw-partner`(`POST /v1/partner/auth/sessions`)를, 내부 운영자는 전용 `gw-ops`를 거쳐 identity-svc 관리 계정 로그인 API를 부른다. 둘 다 identity-svc가 다중 인증(MFA TOTP, 인증 앱이 시간에 따라 새로 만드는 일회용 코드)을 검증한다(추천 적용 2026-10-28, ADR-0119). 파트너 액세스 토큰은 `gw-partner`가 주고 `gw-partner`와 파트너 콘솔 앱 서버가 읽는 `__Secure-peaket_partner_at`이다. 운영자 액세스 토큰은 `gw-ops`만 주고 읽는 `__Host-peaket_ops_at`이다(openapi `partnerCookie`·`opsCookie`). 두 액세스 토큰(15분)은 리프레시 쿠키(파트너 `__Secure-peaket_partner_rt`, 운영자 `__Host-peaket_ops_rt`)로 `POST /v1/partner/auth/access-tokens`·`POST /v1/ops/auth/access-tokens`에서 갱신한다. 이 요청은 본문이 없어서 게이트웨이가 `Origin`을 콘솔 출처와 대조한다(openapi `partnerRefreshCookie`·`opsRefreshCookie`, 추천 적용 2026-10-15, ADR-0065 결정 11). 로그아웃은 `DELETE /v1/partner/auth/sessions/me`·`DELETE /v1/ops/auth/sessions/me`이고, 204로 답하며 그 앱의 쿠키만 같은 이름·`Domain`·`Path`의 `Max-Age=0`으로 지운다(`Clear-Site-Data`는 보내지 않는다). 소비자 웹 로그아웃은 로그인처럼 소비자 웹 앱 서버 경로라 openapi에 없다(추천 적용 2026-10-29, ADR-0145 결정 2, docs/features/identity.md §3). 관리자 세션은 유휴 상태로 1시간이 지나면 전면 재인증을 요구한다. 파괴적인 운영 명령을 실행할 때는 실시간 2차 인증을 강제한다.
- 재인증 토큰: 팬 민감 작업(POL-019 목록)과 관리 계정의 위험 명령·승인 실행은 5분짜리 1회용 재인증 토큰(`typ` reauth+jwt)을 `X-Reauth-Token` 헤더로 보낸다. 본문 필드나 URL로는 받지 않는다(2026-10-13 전수 점검에서 통일, openapi `ReauthToken`). 토큰은 그 세션(`sid`)과 작업 묶음(`act`)에 묶여 다른 세션·다른 작업 묶음에는 쓰지 못하고, 패스키가 필요한 작업은 `factors`에 passkey가 있어야 한다(docs/security/authz-matrix.md §6, ADR-0157 결정 11). 토큰이 없거나 만료·재사용이거나 세션·작업 묶음·요소가 맞지 않으면 403 `reauth-required`(별칭 `REAUTH_REQUIRED`)로 답하고, 같은 경로의 다른 403(예: 결제자가 아님 `NOT_PAYER`)과는 `type`으로 가른다.
- 현장 게이트 스캐너 단말: 기기 키 DPoP(운영자가 등록한 기기 안의 키로 요청마다 서명한 증명, `DPoP` 헤더, RFC 9449)와 현장 스태프 세션 토큰(`Authorization: DPoP <토큰>`)을 함께 쓴다. `gw-scanner`가 TLS를 종단하고, 하드웨어 키가 필요한 운영 환경의 선택지는 cert-manager가 관리하는 기기 인증서의 mTLS다(docs/features/offline-gate.md §6.1, 추천 적용 2026-10-28, 기술 검토 중간-057). 현장 요원은 RFC 8628 기반 기기 간편 승인 절차(`POST /v1/scanner/device-authorizations` → 모바일 승인 → `POST /v1/scanner/token`)로 로그인한다. 발급된 스캐너 토큰에는 ES256 서명, `scanner` 대상자 클레임, 회차와 배정 역할, 기기 키 지문(`cnf.jkt`. mTLS 선택지는 인증서 지문 `cnf.x5t#S256`)이 들어 있고, 역할 유효 끝(공연 종료 2시간 뒤)에 만료된다. 스캐너 경로는 요청마다 세션·배정 상태를 확인한다(ADR-0030·0051).
- 분산 토큰 수명 주기의 전체 설계 결정은 ADR-0011에 자세히 적혀 있다.

## 9. 공통 헤더 및 캐싱 규약
- 모든 HTTP 응답에는 분산 추적 식별자(trace-id)가 필수로 들어간다. 이 식별자는 지표·로그·요청 기록을 모으는 공통 표준과 도구인 OpenTelemetry의 표준을 따른다. **헤더 이름과 싣는 범위(추천 적용 2026-10-28, 기술 검토 낮음-023)**: 응답 헤더는 `X-Trace-Id`(trace-id 32자리 16진수만, span-id·표본 표시는 싣지 않는다)이고, 게이트웨이가 붙인다. W3C Trace Context Level 2(후보 권고 초안 2024-03-28)에는 응답용 헤더가 없고, 응답에 `traceparent`를 실으면 그 trace에 참여하지 않은 교차 출처 호출자에게 값이 갈 수 있으니 조심하라고 한다(§6.3, 2026-10-28 확인). 바깥 요청의 trace는 게이트웨이가 새로 시작하므로(아래), 표준 헤더 대신 프로젝트가 정한 이름을 쓴다. CDN이 캐시하는 공개 응답(홈·검색·자동완성·후기 요약·회차 공개 요약, 대기 상태·셔플·묶음 결과 파일, 정적 파일)에는 싣지 않는다. 캐시된 응답이 다른 사람에게 가면 다른 요청의 값이 실리기 때문이다. 화면의 오류 수집이 읽도록 교차 출처 API는 `Access-Control-Expose-Headers`에 `X-Trace-Id`를 더한다(아래 CORS 응답 헤더). Problem 본문의 `traceId`(§2)는 같은 값이다. §4의 대상 쓰기 요청에는 `Idempotency-Key` 헤더가 필수다. API 응답 본문과 대기 상태 파일은 언어와 무관하고, 다국어 문구는 화면이 오류 `type`과 문구 키로 고른다(ADR-0060 결정 3, docs/frontend.md §5.12).
- **들어오는 추적 헤더(추천 적용 2026-10-28, 기술 검토 중간-066)**: 게이트웨이는 클라이언트가 보낸 `traceparent`·`tracestate`·`baggage`를 라우팅·추적 전에 지우고 새 trace를 시작한다(Envoy Gateway `ClientTrafficPolicy`의 `earlyRequestHeaders`). 사용자 식별 내부 헤더를 지우고 다시 쓰는 것(docs/architecture.md §4 '프로토콜 변환 및 헤더 정리')과 같은 자리다. 그래서 바깥 호출자는 PEAKET의 trace-id·표본 여부를 정하지 못한다. 응답의 `traceId`는 PEAKET이 시작한 trace의 값이다(docs/observability.md §6).
- 인증 토큰, 비밀번호, 본인확인 정보 등 일체의 민감 정보와, 그 값만으로 권한이 생기는 비밀(1회용 토큰·코드)은 URL 경로와 쿼리 파라미터에 넣을 수 없다. 이런 값은 TLS로 보호되는 HTTP 요청 본문이나 보안 헤더로만 보낸다. 인증이 필요한 모든 API 경로는 CDN 캐싱에서 엄격히 빼고 `Cache-Control: no-store` 헤더를 강제한다. 다른 자격(임시 쿠키, 로그인 세션과 재인증 토큰)이 함께 있어야 쓸 수 있는 식별자(계정 연결·병합 제안 ID)는 경로에 둘 수 있다. 다만 로그·트레이스에는 경로 템플릿만 남긴다. OAuth `code`·`state`는 프로토콜 규격상 예외다(ADR-0053 결정 14). 신청 알림 이메일의 한 번 누름 수신 거부 토큰(`POST /v1/subscription-opt-outs/{optOutToken}`)도 규격상 예외다. RFC 8058은 메일 프로그램이 쿠키·인증 없이 `List-Unsubscribe` 주소로 `List-Unsubscribe=One-Click` 한 줄만 담은 본문을 POST하게 하므로 누구의 무엇을 끄는지가 주소에 들어 있어야 한다. 예외를 좁히려고 토큰의 힘은 '그 신청 하나 지우기'뿐이고(로그인·조회를 하지 못한다), 저장하지 않는 HMAC 값이며, 토큰이 틀리거나 신청이 없어도 같은 200을 주고, GET은 상태를 바꾸지 않으며, 로그·요청 기록에는 경로 템플릿만 남긴다(추천 적용 2026-10-30, docs/features/notify.md §7.4, ADR-0155 결정 9).
- 대기열 실시간 상태 캐시 파일과 셔플 결과 파일은 무인증·무쿠키(Cookie 헤더 제거) 엔드포인트로 낸다. 대기 순번 파일에는 `Cache-Control: public, max-age=1`(기본. 입장 임박 구간 파일은 `max-age` 없이 다음 생성 시각을 `Expires`로 준다, ADR-0110. 차례에서 먼 구간의 수명을 늘리는 방식은 Phase 2에서 정한다, queue-admission §4), 셔플·묶음 결과 파일에는 `Cache-Control: public, max-age=60` [가정, Phase 2 부하 시험에서 확정](게시 전 404는 오류 캐시 1초, ADR-0058) 헤더를 붙여, 엣지 캐시가 되도록 많이 대신 응답하게 한다. 폴링을 늦추라는 서버 힌트는 대기 상태 파일 본문의 `pollHintMs`(다음 폴링까지의 최소 간격, 밀리초)로 준다. S3 대체 원본은 객체마다 `Retry-After` 같은 응답 헤더를 줄 수 없기 때문이다. `Retry-After` 헤더는 503 응답의 재시도 하한으로만 쓰고, 200 응답의 본문 힌트가 늘 앞선다(추천 적용 2026-10-28, 기술 검토 중간-032).
- 공개 카탈로그 읽기(홈 피드 `GET /v1/home`, 검색 `GET /v1/search`, 자동완성 `GET /v1/search/suggestions`, 후기 요약 `GET /v1/events/{eventId}/review-summary`, 회차 공개 요약 `GET /v1/events/{eventId}`, ADR-0163 결정 6)는 인증 없이 부른다. CDN 캐시 정책에서는 쿠키를 캐시 키와 원본 요청에서 뺀다. 캐시 키에는 정규화한 검색어(NFKC·소문자·제로폭 문자 지움·공백 정리, docs/features/search.md §3.1)와 명시한 쿼리 파라미터만 넣어, 같은 질의가 한 캐시를 쓰게 한다. CloudFront는 매개변수의 순서나 대소문자만 달라도 다른 캐시로 보므로(AWS 문서, 2026-10-27 확인), 브라우저가 정규화하고 매개변수를 정해진 순서로 실으며 기본값은 싣지 않는다. 수명은 홈 30초·검색 30초·자동완성 60초·후기 요약 60초·회차 공개 요약 300초 [가정]이고(검색·자동완성은 `stale-while-revalidate`도 둔다), 원본 장애 때는 `stale-if-error`로 마지막 응답을 낸다. 장르별 랭킹 파일과 회차 좌석맵 파일은 공연 페이지 배포의 정적 파일이다(랭킹은 게시 때 무효화, 좌석맵은 판이 이름에 들어 `immutable`). 개인 값이 섞이는 후기 목록·단건은 `Cache-Control: private, no-store`다(추천 적용 2026-10-14, ADR-0063).
- **쓰기 요청의 출처 확인(CSRF, 추천 적용 2026-10-15, ADR-0065 결정 5)**: 사용자가 모르게 다른 사이트가 요청을 보내게 하는 공격을 막으려고, 쿠키로 인증하는 쓰기 요청(POST·PUT·PATCH·DELETE)은 게이트웨이가 `Origin`(요청을 보낸 화면의 출처)을 그 게이트웨이의 허용 출처 목록과 대조하고, `Origin`이 없거나 목록에 없으면 403으로 거절한다. 구현은 Envoy Gateway의 내장 CSRF 필터에 허용 출처를 `additionalOrigins`로 넣는 것이고, 이전의 `Sec-Fetch-Site` 대체 확인은 지웠다. 화면의 쓰기는 모두 교차 출처 CORS 요청이라 브라우저가 `Origin`을 늘 싣기 때문이다(docs/architecture.md §4, 추천 적용 2026-10-28, 기술 검토 낮음-139). 결제사·파트너 웹훅(서명 검증)과 서버 사이 호출은 쿠키를 받지 않으므로 예외다. 신청 알림 이메일의 한 번 누름 수신 거부(`POST /v1/subscription-opt-outs/{optOutToken}`)도 메일 프로그램이 쿠키와 `Origin` 없이 보내므로 이 확인을 붙이지 않은 경로로 받는다(토큰의 힘은 신청 하나 지우기뿐이다, 위 URL 비밀 항목, 추천 적용 2026-10-30, docs/features/notify.md §7.4). ADR-0008의 'Origin/Referer 검증'은 이 규칙으로 읽는다. 쿠키의 `SameSite` 설정은 이 확인을 대신하지 않고, 함께 겹쳐 막는다(docs/architecture.md §4).
- **사전 요청이 생기지 않는 교차 출처 쓰기(ADR-0065 결정 6)**: www에서 `queue` 호스트로 가는 대기열 진입(`POST /v1/queues/{eventId}/entries`)과 입장 확정(`…/admission`)만 이 형식이다. 본문은 JSON 문자열이지만 `Content-Type: text/plain;charset=UTF-8`로 보낸다. 또 safelisted가 아닌 헤더(`Idempotency-Key`, `traceparent` 같은 추적 헤더 포함)를 붙이지 않아, 브라우저가 사전 요청(OPTIONS)을 보내지 않게 한다. 서버는 이 두 경로에서 `text/plain`과 `application/json`만 받고(그 밖은 415) 본문을 JSON으로 검사한다. 사전 요청이 없으니 위조 방지는 본문의 사전 검증 토큰·대기표(허용한 출처만 응답을 읽어 얻는 값), 위 `Origin` 확인, `SameSite=Strict` 쿠키가 맡는다(ASVS v5.0.0-3.5.1). 그 밖의 교차 출처 API는 JSON과 사전 요청을 그대로 둔다.
- **CORS 응답 헤더(ADR-0065 결정 3·7)**: 브라우저가 다른 주소에서 온 요청을 허용할지 정할 때 쓰는 허용 출처는 게이트웨이마다 화면 호스트 하나로 고정하고, 요청의 `Origin`을 그대로 되돌려 주지 않는다. 쿠키를 받는 API는 `Access-Control-Allow-Credentials: true`와 `Vary: Origin`을 두고, 사전 요청 응답은 `Access-Control-Max-Age: 7200`이다(Chromium 상한 2시간, MDN). `queue` API는 소비자 웹이 503의 `Retry-After`와 `Date`를 읽도록 `Access-Control-Expose-Headers: Retry-After, Date`를 더하고, `queue-files` 배포(AWS의 파일 저장소인 S3에 둔 대체 원본 포함)는 `Retry-After`만 더한다. `Date`는 캐시하지 않는 응답에서만 브라우저 시계 보정에 쓰고 `api`·`scanner-api`도 노출한다. 캐시하지 않는 교차 출처 API(`queue`·`api`·`partner-api`·`ops-api`·`scanner-api`)는 `X-Trace-Id`도 노출한다(§9 첫 항목, 추천 적용 2026-10-28, 기술 검토 낮음-023). 고치기 작업이 있는 `api`·`partner-api`·`ops-api`·`scanner-api`는 `ETag`를 노출하고 사전 요청에서 `If-Match`를 허용한다(§12 '동시 수정', 기술 검토 낮음-030). `queue-files`는 CDN이 캐시한 응답이라 `Date`가 원본이 만든 시각 그대로여서 노출하지 않는다(추천 적용 2026-10-21, ADR-0079 결정 3. 2026-10-28 ADR-0110). 대기실은 대기열 API 응답 본문의 `serverTimeMs`(밀리초)로 시계를 맞춘다(docs/frontend.md §3.3). 쿠키가 없는 `queue-files`에는 Credentials를 두지 않는다. 값을 붙이는 곳은 docs/infra.md §9다.
- **CSV·XLSX 내려받기(ADR-0065 결정 12)**: 정산 리포트·예매자 명단·좌석맵 내보내기 같은 파일 응답은 `Content-Disposition: attachment`와 정확한 `Content-Type`으로 낸다. 칸 값이 `=`·`+`·`-`·`@`·탭·CR로 시작하면 그 앞에 작은따옴표를 붙여, 스프레드시트가 수식으로 읽지 않게 한다. 인코딩이 아니라 칸 값 규칙이므로 서버가 파일을 만들 때 적용한다. 브라우저가 만드는 내보내기(파트너 좌석맵 에디터의 CSV)는 화면 코드가 같은 규칙을 지킨다(추천 적용 2026-10-21, docs/frontend.md §5.6).
- **브라우저 텔레메트리 입구 `/_t/*`(추천 적용 2026-10-29, ADR-0145 결정 6)**: 텔레메트리는 시스템이 내보내는 지표·오류 같은 운영 신호다. `/_t/rum`(성능·오류 지표), `/_t/csp`(CSP 위반 보고), `/_t/err`(오류 도구 터널)는 화면 호스트 넷(www·partner·console·scanner)의 같은 출처 POST 전용 경로이고, `/v1` REST 규칙(§10~§12)의 예외다. 외부 API가 아니어서 openapi에는 넣지 않는다. 넣으면 경로 규칙 검사(doc-check `api`)의 예외만 늘고 외부 API로 오해된다. 계약은 이 항목이 정본이다.
  - 전달: CloudFront가 원본 요청에 원본 확인 헤더와 화면 앱 이름 `X-Peaket-App`(web·partner·console·scanner)을 붙여 gw-fan의 텔레메트리 입구로 보낸다. 게이트웨이는 원본 확인 헤더가 맞을 때만 그 값을 앱 라벨로 쓰고, `Cookie`·`Authorization`을 지운 뒤 게이트웨이 수집기로 넘긴다(`sendBeacon`과 CSP 보고는 같은 출처에 쿠키를 싣기 때문이다).
  - 본문: `/_t/rum`은 asyncapi `RumSample`, `/_t/csp`는 Reporting API 보고, `/_t/err`는 오류 도구의 봉투 형식이다. 본문은 64KiB가 상한이고, WAF로 IP당 속도를 제한한다 [가정]. 형식이 맞지 않으면 버린다. 사용자 식별값은 싣지 않는다.
  - 라우트: 게이트웨이 라우트 생성기는 openapi 작업과 이 고정 목록(세 경로와 아래 허니팟 경로)을 함께 읽어 HTTPRoute를 만든다(D-T42). 그 밖의 규칙은 docs/observability.md §11에 있다.
  - 허니팟 경로(추천 적용 2026-10-30, docs/features/bot-defense.md §7, ADR-0156 결정 9): 소비자 웹(www)의 `/_t/` 아래에 숨긴 링크 경로 하나를 둔다. 정확한 경로는 [가정, wbs 3.2.3에서 확정]이고 위 세 경로와 겹치지 않는다. gw-fan은 이 경로만 텔레메트리 수집기가 아니라 trust-svc의 허니팟 기록 처리기(HTTP)로 보낸다. 브라우저가 실어 보낸 팬 로그인 쿠키(`__Secure-peaket_at`)가 있으면 gw-fan이 그 팬 액세스 토큰을 검증해 사람 식별값(pid)만 내부 헤더로 넘기고, 쿠키 원문은 다른 텔레메트리 경로처럼 지워 trust-svc로 보내지 않는다. 토큰이 없거나 틀리면 pid 없이 넘긴다(로그인하지 않은 적중). `Sec-Fetch-Site`·`Sec-Purpose`·`Next-Router-Prefetch`는 그대로 넘긴다(추천 적용 2026-10-30, docs/infra.md §4.1 '허니팟 경로', 지난 판의 '쿠키를 지우지 않고'를 바로잡음). 메서드는 GET이다. `/_t/*`의 'POST만' 규칙에서 이 경로 하나만 GET을 받는다(숨긴 `<a>` 링크라 브라우저가 GET으로 부른다). 응답은 언제나 204·빈 본문이라, 이 경로는 GET이 상태를 바꾸지 않는다는 §12의 규칙에서 벗어난다. 남기는 것은 '적중 표시'뿐이고 사람에게 해가 가는 처리가 없어 받아들인다(적중은 확정 라벨이 아니라 다음 판정의 추가 검증 신호다). 처리 규칙은 trust.proto 끝 주석에 있다.

## 10. URI 설계 규칙 (ADR-0081)

소유자가 준 REST 설계 기준(2026-10-21)을 이 API에 맞춘 규칙이다. 기준 원문 요약, 점검 결과, 바꾼 경로의 옛 경로 대응표는 ADR-0081에 있다. 따로 적지 않은 것은 추천 적용 2026-10-21이다. 경로 규칙과 문서가 이름을 댄 경로가 openapi에 있는지는 `tools/doc-check`의 `api` 검사가 확인한다(바꾸기 전 명세에서는 경로 57개에서 75건을 잡았다).

- **경로의 호스트와 인증을 명세에 적는다(추천 적용 2026-10-28, 기술 검토 낮음-031).** 어느 게이트웨이(호스트)가 그 경로를 받는지는 openapi 맨 위의 `x-peaket-gateways` 규칙(경로 접두사 → 서버, 위에서부터 처음 맞는 것)이 정하고, 경로에 `servers`가 있으면 그것이 이긴다(정적 파일, 소비자 웹 앱 서버가 받는 계정 연결 제안). 태그는 화면 묶음이라 게이트웨이와 일대일이 아니어서 태그별 `servers` 대신 접두사 규칙을 골랐고, 모든 경로에 같은 값을 베끼면 어긋날 곳만 늘어서 한 표로 둔다. 인증은 전역 `security`(팬 쿠키)가 기본이고, 인증 없는 작업은 `security: []`로 적는다. 그래서 '인증을 빠뜨린 작업'과 '공개 작업'이 기계로 갈린다. 쓰는 인증 방식은 모두 `securitySchemes`에 있다(계정 연결 임시 쿠키 `linkCookie`, 기기 키 DPoP `deviceDpop`·`staffToken` 포함). doc-check `api` 검사는 이 규칙을 이미 오류로 잡는다. 접두사 규칙이나 경로 `servers`로 호스트 하나에 정해지지 않는 작업, `security`가 가리키는 이름이 `securitySchemes`에 없는 작업, `security`를 적지 않았는데 전역 `security`도 없는 작업이다(tools/doc-check/README.md, 추천 적용 2026-10-28, 기술 검토 낮음-150·l2 묶음).
- **경로는 자원(명사)을 가리킨다.** 동작은 HTTP 메서드로 나타내고, 경로에는 동사(`getUsers`, `approve`, `refresh`, `login`)를 쓰지 않는다. 만들기·읽기·고치기·지우기로 나타낼 수 없는 상태 바꾸기는 그 동작이 남기는 기록의 이름을 하위 자원으로 두고 POST한다(Zalando RESTful API 지침 [141]의 '취소 우편함' 방식). 예: 승인 `…/approvals`, 거절 `…/rejections`, 양도 수락 `…/acceptance`, 홀드 연장 `…/extension`, 되돌리기 `…/reversions`, 기기 폐기 `…/revocation`. 여러 번 쌓일 수 있는 기록은 복수형이고(명령의 승인·거절·되돌리기, 명령 2의 연장, 일괄 환불의 정지·재개, 받은 티켓 돌려주기), 부모마다 한 번만 생기는 결과는 단수형이다(양도 수락·거절·철회, 홀드 1회 연장, 기기 폐기, 병합 확인).
- **컬렉션은 복수형, 싱글턴은 단수형이다.** 같은 종류의 모음은 복수 명사(`/tickets`, `/holds`)이고 단건은 그 뒤에 ID를 붙인다. 부모마다 하나뿐인 하위 자원(싱글턴)은 단수 명사다(`/seatmap`, `/entry-policy`, `/wish`, `/payout-account`, Google AIP-156). 컬렉션 바로 뒤 자리는 ID 자리이므로 고정 단어를 두지 않는다(`/reviews/images`가 아니라 `/review-images`. Google AIP-122의 '컬렉션 이름과 ID를 번갈아 둔다').
- **나를 가리키는 예약 ID `me`.** 로그인한 사람의 항목을 ID 없이 가리킬 때는 `me`를 쓴다(`DELETE /v1/queues/{eventId}/entries/me`). 처음 쓴 기기가 없어도 다른 기기에서 취소할 수 있어야 해서 대기표 ID를 요구하지 않는다(ADR-0060). 컬렉션 자체에는 DELETE를 보내지 않는다(컬렉션 전체 삭제로 읽힌다). 예외로 알림 신청 끄기(`DELETE /v1/events/{eventId}/subscriptions?kind=`)는 `kind`로 고른 내 신청만 지우는 필터 삭제이고, 같은 요청을 다시 보내도 204다.
- **깊이는 2단계까지다.** `컬렉션/{ID}` 한 쌍이나 싱글턴 하나가 1단계다(소유자 기준의 예: `/users/{userId}/orders/{orderId}`는 2단계). 버전(`v1`)과 정해진 네임스페이스는 세지 않는다. 네임스페이스는 호출 주체(`partner`, `ops`, `scanner`)와 모듈(`identity`, `shop`, `auth`, `compliance`, `webhooks`)뿐이고, 네임스페이스 바로 뒤에는 ID가 오지 않는다(그래서 `/v1/queue/{eventId}`가 아니라 `/v1/queues/{eventId}`다). 3단계가 되면 ① 하위 자원이 전역 ID를 가지면 목록·생성만 부모 아래 두고 단건 경로는 위로 올리거나(얕은 중첩, Rails 라우팅 안내서 'Shallow Nesting'. 예: `GET /v1/partner/events/{eventId}/staff`와 `DELETE /v1/partner/staff/{assignmentId}`) ② 두 단어를 하이픈으로 이어 한 단계로 만든다(`/seatmap/snapshot` → `/seatmap-snapshot`). Microsoft의 웹 API 설계 지침도 collection/item/collection보다 복잡한 URI를 피하라고 한다. Zalando [147]은 하위 단계를 3 이하로 권한다.
- **표기.** 경로는 소문자이고 여러 단어는 하이픈으로 잇는다(`/order-items`, 밑줄 없음, Zalando [129]). 쿼리 파라미터 이름은 본문 JSON 필드와 같은 camelCase다(`dueWithinDays`). Zalando [130]은 snake_case를 요구하지만, 이 API는 쿼리와 본문의 필드 이름을 하나로 맞추는 쪽을 택했다(orval이 만드는 타입 이름과 같다).
- **끝 슬래시를 쓰지 않는다.** `/v1/tickets`와 `/v1/tickets/`는 RFC 3986에서 서로 다른 URI다. 끝 슬래시가 붙은 요청과 빈 단계(`//`)가 든 요청은 404이고 리디렉션하지 않는다. 리디렉션은 왕복을 늘리고, 같은 자원에 주소가 둘이면 CDN 캐시도 둘로 나뉜다(RFC 9110 §4.2.3은 정규화하면 같아지는 URI로 서로 다른 자원을 가리키지 말라고 한다). 모든 서비스가 Fastify 어댑터를 쓰므로(ADR-0023 상태 줄, 기술 검토 낮음-143) 기본값(`routerOptions.ignoreTrailingSlash: false`, 두 주소를 다르게 봄)을 그대로 둔다. Express 어댑터를 예외로 쓰는 서비스가 생기면, Express가 기본으로 두 주소를 같게 보므로 `strict` 라우팅을 켠다.
- **확장자는 CDN이 내는 정적 파일에만 쓴다**(`/v1/queues/{eventId}/segment-states/{segment}.json`, `/v1/home/rankings.json`, `/v1/events/{eventId}/seatmap-layouts/{layoutVersion}.json`). S3 객체 키와 경로가 같아야 해서다. 그 밖의 형식은 `Accept` 헤더로 고른다(공연 리포트의 `text/markdown`).
- **예외(이유와 함께 고정한다).** ① 기기 승인 토큰 엔드포인트 `POST /v1/scanner/token`은 OAuth 관례의 단수 이름과 오류 형식을 따른다(RFC 8628) ② 결제사 웹훅 수신 `POST /v1/webhooks/toss`·`/portone`은 결제사 이름이 ID 자리에 온다 ③ 비밀값으로 찾는 조회는 GET 대신 POST `…-lookups`로 받는다(§12) ④ 관제 SSE 흐름 `/v1/ops/live`·`/v1/ops/events/{eventId}/live`는 `text/event-stream`을 계속 내보내는 GET이다(2026-10-28 ADR-0100. 관제의 `/graphql`은 이때 지웠다) ⑤ 전역 검색 `GET /v1/search`는 기능 이름이 경로다(소유자 기준의 '전역 검색' 예와 같다).

## 11. 검색·부분 응답·하이퍼미디어 (ADR-0081)

- **검색은 GET과 쿼리 문자열이다.** 전체 검색은 `GET /v1/search?q=`(공연·아티스트·공연장)이다. 특정 자원 안에서 찾을 때는 그 컬렉션의 GET에 필터를 붙인다(`GET /v1/ops/cases?kind=&dueWithinDays=`). 자유롭게 입력한 검색어는 `q` 하나로 받는다.
- **조건과 페이지 파라미터를 섞지 않는다.** 예약 이름 `q`·`cursor`·`limit`·`page`·`sort`·`fields`는 정해진 뜻으로만 쓰고 필터 이름으로 쓰지 않는다. 필터 이름은 응답 필드 이름과 같게 한다(`status`, `genre`, `placeId`, `artistId`). 그래서 `?status=ON_SALE&page=2&limit=20`에서 어느 것이 조건인지 이름만으로 갈린다.
- **같은 쿼리 매개변수가 두 번 오면 400이다(추천 적용 2026-10-30, docs/security/asvs/seat-hold.md 15.3.7, ADR-0159 결정 6).** 여러 값을 받는 매개변수도 쉼표로 이은 한 값으로 받으므로(openapi `style: form, explode: false`, 예: `?status=RECEIVED,IN_PROGRESS`), 어떤 매개변수든 한 요청에 한 번만 온다. `?section=1&section=7`처럼 같은 이름이 두 번 오면, 앞이나 뒤 하나를 골라 쓰지 않고 서비스의 공통 요청 검사가 400으로 거절한다. 게이트웨이·캐시·서비스가 서로 다른 값을 골라 검사와 처리가 어긋나는 HTTP 파라미터 오염(ASVS 15.3.7)을 막으려는 것이다.
- **조건을 `q` 하나에 이어 붙이는 형식(`?q=name%3Dcho,region%3Dseoul`)은 쓰지 않는다(추천 적용 2026-10-21).** 소유자 기준이 권하는 형식이지만, 이 API에는 세 가지 점에서 맞지 않는다. ① 공개 검색은 CDN이 캐시하고, 캐시 키는 정규화한 `q`와 지정한 필터 파라미터다(§9). 조건을 한 문자열에 넣으면 같은 조건이라도 순서나 구분자만 달라져 다른 캐시 키가 된다. ② 필터마다 openapi 스키마(열거값·날짜 형식·최대 길이)로 입력을 검사한다. 한 문자열로 받으면 해석기를 따로 만들어야 하고, 값에 `,`·`=`가 들어갈 때의 이스케이프 규칙도 필요하다. ③ 위의 예약 이름 규칙만으로도 '조건과 페이지 파라미터가 섞여 헷갈리는' 문제가 풀린다. 조건을 AND·OR로 묶어야 할 만큼 복잡해지면, 그때 한 파라미터에 쓰는 문법(Google AIP-160의 `filter`)을 따로 정한다.
- **부분 응답 `fields`.** 이름과 문법은 정해 두었지만 지금 쓰는 경로는 없다. 문법은 필드를 쉼표로 늘어놓고, 하위 객체는 점으로 잇는다(`?fields=eventId,title,venue.name`, Zalando [157]과 Google API 시스템 파라미터 `fields`). 모르는 필드는 400으로 답한다. `fields`는 보여 줄 범위를 줄이기만 하므로 권한 검사를 바꾸지 않는다. CDN이 캐시하는 공개 읽기에는 쓰지 않는다(필드 조합마다 캐시 키가 갈린다). 응답 크기나 조인 비용이 측정에서 문제로 드러난 목록에만 그 경로에서 켠다. 관제 읽기는 2026-10-28부터 위젯마다 정한 REST 조회(`GET /v1/ops/widgets/{widgetKey}`)라, 화면이 쓰는 필드만 담아 낸다(ADR-0100. 그 전에는 GraphQL로 필드를 골라 받았다).
- **하이퍼미디어(HATEOAS)는 기본으로 넣지 않는다.** 클라이언트가 모두 openapi에서 생성한 우리 앱이라, 응답 속 링크에 기대서 얻는 이득이 작다. 또 링크는 응답을 키우고, 클라이언트를 링크 이름에 묶어 바꾸기 어렵게 만든다(소유자 기준의 지적과 같고, Zalando [163]도 일반적으로 권하지 않는다). 대신 표준 헤더와 필드로 다음 행동을 알린다. 만든 자원의 주소는 `Location`(§12), 다시 보낼 시점은 `Retry-After`, 다음 페이지는 `nextCursor`, 오류 설명 문서로 가는 주소는 `type` URI(§2)다. 상태에 따라 할 수 있는 행동이 바뀌는 화면(양도·취소 가능 여부)은 응답의 상태·기한 필드(`transferable`, `cancelDeadline`)로 알린다.

## 12. 메서드와 상태 코드 (ADR-0081)

- **메서드.** 조회는 GET, 만들기와 그 밖의 처리는 POST, 통째로 바꾸기는 PUT, 일부 고치기는 PATCH, 지우기는 DELETE다. GET·HEAD·OPTIONS는 상태를 바꾸지 않는다(RFC 9110 §9.2.1. 브라우저·크롤러·프록시가 이 요청을 미리 보내거나 다시 보낸다). PUT·DELETE는 같은 요청을 다시 보내도 결과가 같게 만든다(§9.2.2). POST로 읽기만 하는 경로는 비밀값으로 찾는 조회 한 종류뿐이다(관제 GraphQL `/graphql`은 2026-10-28 ADR-0100으로 지웠다). ① 비밀값으로 찾는 조회. 초대 토큰·기기 확인 코드·휴대폰 번호는 URL에 넣지 않으므로(§9), 본문에 담아 `POST …-lookups`(`/v1/staff-invitation-lookups`, `/v1/device-approval-lookups`, `/v1/transfer-recipient-lookups`)로 받는다. 응답은 200과 `Cache-Control: no-store`이며, 상태를 바꾸지 않는다. 본문을 싣는 안전한 메서드 QUERY(RFC 10008, 2026-06)는 CloudFront 캐시 동작에서 고를 수 있는 메서드 묶음(GET·HEAD, +OPTIONS, +PUT·PATCH·POST·DELETE)에 없어서 쓰지 않는다. 2026-10-21 점검에서 상태를 바꾸는 GET은 없었다. 근무 정보를 POST로 읽던 스캐너 근무 준비는 `GET /v1/scanner/shift`와 `PUT /v1/scanner/shift/readiness`로 나눴다.
- **성공 코드.** 자원을 만들면 201이다. 만든 자원을 GET으로 읽을 수 있으면 `Location`을 준다(RFC 9110 §15.3.2. 지금은 양도 요청·후기·문의·관리 계정 초대와 법정 조치의 통보·자료 요청·보안 사고 등록). 읽는 경로가 없는 기록을 만들면 201과 함께 본문에 ID를 준다. 동작 기록 하위 자원에 POST해서 상태를 바꾸면 바뀐 상태를 200으로 돌려준다. 나중에 처리하는 접수는 202, 돌려줄 본문이 없으면 204다. 실패를 200 본문(`{"success": false}`)으로 감싸지 않는다.
- **오류 코드의 뜻.** 400은 형식이 틀린 경우다(JSON 깨짐, 타입·범위 밖, 모르는 `fields`). 422는 형식은 맞지만 업무 규칙에 어긋난 경우다(매수 한도, 동의 누락, 검증 오류 목록). 401은 누구인지 모르는 경우다(로그인·토큰 필요). 403은 누구인지 알지만 안 되는 경우다(역할 밖, 재인증 필요 `reauth-required`). 404는 그 ID의 자원이 없는 경우다. 개인·거래 기록(양도 요청·문의·정산서)은 남의 것이면 있는지조차 알리지 않도록 403 대신 404로 답한다(RFC 9110 §15.5.4). 공연·회차처럼 있다는 사실이 이미 공개된 자원과 그 회차의 하위 자원(이미지·좌석맵·리포트)은 남의 것이면 403이다. 409는 지금 상태와 부딪치는 경우다(이미 처리됨, 오픈 뒤 잠긴 좌석맵 도형처럼 업무 상태가 막음). 고치기 작업의 판 불일치는 412이고 판을 보내지 않으면 428이다(아래 '동시 수정'). 410은 다시 오지 않는 끝이다(판매 종료 `sale-ended`, 만료된 초대·코드, 보존 기간 끝). 다만 짧아서 추측할 수 있는 확인 코드로 찾는 조회(스캐너 승인 확인 코드, 계정 연결·병합 제안)는 없음과 만료를 가리지 않고 같은 404로 답한다(추천 적용 2026-10-23). 423은 운영자가 잠근 자원이다(판매 일시정지, 잠긴 계정. WebDAV의 Locked를 이 뜻으로 쓴다). 429·503은 잠시 뒤 다시 보내라는 뜻이다(`Retry-After` 필수).
- **동시 수정(추천 적용 2026-10-28, 기술 검토 낮음-030)**: 여러 사람(같은 파트너의 직원, 여러 운영자)이 함께 고칠 수 있는 자원은 한 규칙을 쓴다. 나중에 저장한 사람이 앞사람의 값을 모르는 채 덮어쓰는 일을 막으려는 것이다.
  - 그 자원을 돌려주는 응답(단건 GET, PUT·PATCH의 200)에 강한 `ETag`를 싣는다. 값은 그 자원의 판(`version`, 저장할 때마다 1씩 느는 정수)을 큰따옴표로 감싼 것이다(예: `ETag: "7"`). 단건 GET이 없는 자원은 목록·부모 응답의 `version` 칸으로 같은 값을 준다. 판 칸이 없는 표에는 구현 때 더한다.
  - PUT·PATCH는 `If-Match`(openapi `IfMatch` 파라미터)를 필수로 받는다. 지금 판과 다르면 처리하지 않고 412 `precondition-failed`(RFC 9110 §13.1.1·§15.5.13), 없으면 428 `precondition-required`(RFC 6585 §3)로 답한다. 화면은 412를 받으면 '다른 곳에서 바뀌었습니다'와 지금 값과의 비교 보기를 띄우고, 사람이 고른 뒤 새 판으로 다시 보낸다(자동으로 다시 보내지 않는다).
  - 좌석맵(`layoutVersion`)과 홈 구성(`version`)이 본문의 판으로 409를 내던 규칙도 이 규칙으로 바꾼다. 본문의 판 칸은 읽기 전용으로 남긴다.
  - 예외: 부른 사람 혼자 바꾸는 자기 상태는 마지막 저장이 이긴다. 내 찜(`PUT /v1/productions/{productionId}/wish`), 그 기기의 근무 준비(`PUT /v1/scanner/shift/readiness`), 작성자만 고치는 내 후기(`PATCH /v1/reviews/{reviewId}`)다.
  - 교차 출처로 부르는 콘솔·스캐너가 `ETag`를 읽도록 `Access-Control-Expose-Headers`에 `ETag`를 더하고, 사전 요청 응답의 `Access-Control-Allow-Headers`에 `If-Match`를 더한다(§9 CORS 응답 헤더, docs/infra.md §9).
- **조회 성공 + 데이터 없음 = 200.** 목록·검색 결과가 0건이면 200과 빈 `items`를 준다. 특정 ID 하나를 집어 물었는데 없으면 404다. 아직 만들어지지 않은 단건(R3 전의 파트너 판매 요약, 게시 전 셔플 결과 파일)도 그 주소의 자원이 아직 없으므로 404다. 서비스가 내는 404는 `type`으로 '아직 없음'과 '없는 ID'를 가른다.
- **401에는 `WWW-Authenticate`를 싣는다(RFC 9110 §15.5.2 MUST, 추천 적용 2026-10-21).** 스캐너 경로는 기본안(기기 키 DPoP)이 `DPoP realm="peaket-scanner"`(RFC 9449 §7.1. 토큰이 틀렸거나 만료되었으면 `error="invalid_token"`, DPoP 증명이 틀렸으면 `error="invalid_dpop_proof"`)이고, mTLS 선택지는 `Bearer realm="peaket-scanner"`(RFC 6750 §3)다(추천 적용 2026-10-28, 기술 검토 낮음-074). 쿠키 경로는 `Cookie realm="peaket"`, 입장 토큰 경로는 `AdmissionToken realm="peaket"`이다. 쿠키로 보내는 인증에는 IANA 인증 방식 등록부에 오른 이름이 없다(2026-10-21 확인). RFC 6750이 정한 Bearer 토큰 전달 방법(헤더·폼 본문·쿼리)에도 쿠키는 없다. 그래서 Bearer라고 쓰지 않고 프로젝트가 정한 이름을 쓴다. 등록되지 않은 이름이라 브라우저는 로그인 창을 띄우지 않고 무시한다. 화면은 지금처럼 401을 보고 토큰 갱신이나 로그인으로 간다. 405에는 `Allow`를 싣는다(RFC 9110 §15.5.6 MUST).
- **자기 서술성 점검.** 모든 작업에 `summary`와 `description`이 있고, 설명에는 근거인 FR(기능 요구사항)·POL·ADR(아키텍처 결정과 그 이유를 남긴 기록)이 적혀 있다. 오류 응답은 Problem을 선언한다(예외는 기기 승인 토큰 엔드포인트의 OAuth 오류와 정적 파일 404뿐이다, §2). 모든 작업에는 `operationId`를 붙인다. 이름은 camelCase 동사 + 자원이다(예: `createHold`, `getPaymentStatus`, `createPartnerAuthSession`). 화면 코드 생성기(orval)가 이 이름으로 호출 훅(`useCreateHold`)을 만들므로, 이름 규칙이 계약 쪽에 있어야 화면과 서비스가 같은 이름을 쓴다(추천 적용 2026-10-29, ADR-0145 결정 3. tRPC 프로시저 이름에 맞춘다던 옛 규칙은 ADR-0100으로 tRPC가 빠져 지웠다). 지금은 붙이지 않았고, wbs 0.2.3에서 이 규칙대로 붙인다. 이 문서는 기준만 적고 숫자를 손으로 적지 않는다(추천 적용 2026-10-28, 기술 검토 낮음-032). 작업 수, Problem을 선언한 4xx·5xx 수와 예외 목록, `operationId`·`servers`·`security`가 빠진 작업 수는 doc-check `api` 검사가 돌 때마다 보고로 낸다. 명세가 늘어도 문서끼리 숫자가 어긋나지 않게 하려는 것이다.
- **허용 역할 칸 `x-peaket-roles`(소유자 결정 2026-10-30, open-items 71번)**: 모든 작업에 그 작업을 부를 수 있는 역할을 대괄호 목록으로 단다(예: `x-peaket-roles: [partner_admin]`). 인증 없는 작업(`security: []`)은 `[public]`이고, 로그인 없이도 되는 작업에 팬 세션을 더 받으면 `[public, fan]`이다. 쓸 수 있는 값, 값과 `security`를 맞추는 규칙, 값을 고르는 기준의 정본은 docs/security/authz-matrix.md §5.5다. 칸이 없는 작업, 표에 없는 값, `security`와 맞지 않는 값은 doc-check `roles` 검사의 오류다. 이 칸은 서비스 가드의 거친 역할 검사만 적고(게이트웨이는 역할을 보지 않는다, ADR-0172), 본인·테넌트·상태 같은 대상 조건은 작업 설명과 권한 표가 정한다. 새 작업을 더할 때 칸도 함께 단다.
- **드문 경로 표시 `x-peaket-trace-rare`(추천 적용 2026-10-29, ADR-0145 결정 7)**: 요청 기록(trace)은 꼬리 표본으로 일부만 남기므로, 하루 수십 건 아래의 쓰기는 성공 사례가 거의 남지 않는다. 그래서 그런 작업에는 openapi 확장 필드 `x-peaket-trace-rare: true`를 단다. 대상은 회차 취소 환불(일괄 환불을 시작하는 확정 승인 `POST /v1/ops/event-cancellations/{requestId}/approvals`), 양도(`POST /v1/tickets/{ticketId}/transfers`, `POST /v1/transfers/{offerId}/acceptance`), 정산 지급(`POST /v1/ops/payout-batches`), 포트원 실행(`POST /v1/ops/payout-batches/{batchId}/portone-execution`), 계정 병합(`POST /v1/identity/merge-proposals/{proposalId}/confirmation`), 관리 계정의 시간 잠금 본인 해제(`POST /v1/partner/auth/unlocks`, `POST /v1/ops/auth/unlocks`)와 비밀번호 바꾸기(`POST /v1/partner/auth/password-changes`, `POST /v1/ops/auth/password-changes`), 법정 조치 원본 올리기(`POST /v1/ops/compliance/notices/{noticeId}/documents`, `POST /v1/ops/compliance/data-requests/{requestId}/documents`)다. 뒤의 셋은 2026-10-30에 더한 드문 쓰기다. 하루 몇 건 아래라 꼬리 표본에 성공 사례가 거의 남지 않고, 잠금·비밀번호·법정 기한처럼 실패를 따질 때 성공 흐름과 견줘야 하는 쓰기라 같은 성격으로 보고 넣었다(추천 적용 2026-10-30). 해제 링크 다시 받기(`…/auth/unlock-links`)는 늘 같은 202를 주고 메일 발송만 맡기는 경로라 넣지 않았다. 같은 날 관리 계정 관리의 쓰기 여덟(초대 `POST /v1/ops/admin-accounts`, 역할 변경 `PUT /v1/ops/admin-accounts/{adminAccountId}/role`, 재초대 `POST /v1/ops/admin-accounts/{adminAccountId}/invitation`, 삭제 `POST /v1/ops/admin-accounts/{adminAccountId}/removal`, 지정 `POST /v1/ops/admin-accounts/{adminAccountId}/designations`와 거두기 `DELETE /v1/ops/admin-accounts/{adminAccountId}/designations/{kind}`, 세션 강제 종료 `DELETE /v1/ops/admin-accounts/{adminAccountId}/sessions`·`DELETE /v1/ops/admin-accounts/{adminAccountId}/sessions/{sessionId}`, open-items 73번)과 수사기관 제공 자료의 쓰기 넷(추출 요청 `POST /v1/ops/compliance/data-requests/{requestId}/extraction-requests`, 추출 승인 `…/approvals`, 거부 `…/rejections`, 제출 기록 `…/submission`, open-items 68번)도 더했다. 권한 부여·말소와 법정 제공은 하루 몇 건 아래이고, 사고 뒤 '누가 언제 무엇을 바꿨나'를 성공 흐름과 견줘야 하는 쓰기라 같은 성격으로 본다(추천 적용 2026-10-30). 위 목록은 지금 표시를 단 작업이다. 게이트웨이 수집기 설정 생성기가 이 표시를 단 작업의 경로 템플릿(`http.route`)으로, 비율과 관계없이 성공 사례도 남기는 하위 정책(경로 거르기 + 속도 제한)을 만든다(docs/observability.md §6, ADR-0125). 새 드문 쓰기를 더할 때 표시도 함께 단다.
