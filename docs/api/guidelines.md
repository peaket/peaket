# API 가이드라인

- **독자와 용도**: API를 설계, 구현, 호출하는 프론트엔드 및 백엔드 엔지니어가 API 버전 관리, RFC 9457 표준 에러 규약, 커서 기반 페이지네이션, 경로 이름과 메서드·상태 코드 규칙(§10~§12), 분산 멱등성, 재시도 및 데드라인 전파, 분산 레이트 리밋, 인증·인가 흐름, 외부 연동 결함 격리 규칙을 파악할 때 참조하는 기준 문서이다. 실제 엔드포인트 명세의 단일 진실 원천은 `openapi.yaml`(REST API)과 `asyncapi.yaml`(비동기 이벤트 및 실시간 웹소켓)에 정의되어 있다.
- **원문 출처**: 설계서 22장(버저닝 및 Swagger), 16장(Exception Filters RFC 9457), §6 API 게이트웨이·장애 격리·계정·인증·결제 연동 아키텍처, 29장 멱등성 제어, 24장 웹훅 규약, 20장 분산 레이트 리밋, ADR-0008·0009·0011·0015. §10~§12와 §2·§3의 2026-10-21 규칙은 소유자가 준 REST 설계 기준을 점검해 정한 것이다(ADR-0081).
- **기준 기획 버전**: v1.0.

## 1. 버전 정책과 하위 호환·폐기 절차
- RESTful API는 URI 경로 기반 버저닝(`/v1`, `/v2`)과 NestJS의 Route Versioning 메커니즘을 채택한다. 필드 추가나 선택적 쿼리 파라미터 추가와 같은 하위 호환 변경은 동일 버전 내에서 점진 배포하며, 기존 클라이언트와의 호환성이 파괴되는 브레이킹 체인지는 신규 메이저 버전을 발행하여 분기한다.
- 폐기 예정(Deprecation) API는 응답 헤더에 `Deprecation` 및 `Sunset` 표준 헤더를 명시하여 통지하며, 파트너 공개 API의 경우 Sunset 지정일로부터 최소 90일간(추천 적용 2026-10-09) 구버전과 신버전을 병행 운영한다.
- Kafka 이벤트 메시지 스키마는 Apache Avro 및 Confluent Schema Registry 기반의 BACKWARD_TRANSITIVE 호환성 모드를 강제한다. BACKWARD는 직전 판하고만 대조하는데, 분석 재적재처럼 보관 7일 안의 옛 메시지를 최신 스키마로 다시 읽는 소비자가 있으므로 모든 이전 판과 대조한다. BACKWARD 계열이므로 소비자를 먼저, 생산자를 나중에 배포한다(docs/devops.md §6.5, ADR-0054). 내부 gRPC 프로토콜은 `buf breaking` CI 검증을 거치며, 공유 계약 패키지는 Changesets 도구를 통한 SemVer 표준을 엄격히 준수한다. 모든 API 및 이벤트 계약 변경은 `peaket-contracts` 공용 저장소를 통해서만 단일 관리된다.
- 개발자 포털 및 파트너용 기술 문서는 `@nestjs/swagger`를 통해 실시간 생성하며, 프론트엔드 클라이언트는 `orval` 코드 생성기를 통해 TypeScript 타입, API 호출 클라이언트, MSW 모킹 핸들러를 완전 자동 생성한다.

## 2. 에러 응답 형식 (RFC 9457 Problem Details)
```json
{
  "type": "https://peaket.example/problems/seat-already-held",
  "title": "좌석이 이미 선택되었습니다",
  "status": 409,
  "detail": "A-12는 방금 다른 분이 선택했습니다.",
  "instance": "/v1/events/evt_1/holds/req_9",
  "suggestedSeats": ["A-13", "A-14"],
  "traceId": "0af7651916cd43dd8448eb211c80319c"
}
```
- 도메인 계층의 `Result` 실패 객체는 NestJS 전역 Exception Filter를 통해 RFC 9457 표준 Problem Details 형식으로 변환하여 반환한다. 보안 강화를 위해 스택 트레이스나 내부 SQL 쿼리와 같은 시스템 민감 정보는 에러 본문에 일체 노출하지 않는다(OWASP A10, ASVS v5.0.0-16.5.1). 알 수 없는 예외는 500과 일반 문구, `traceId`만 내고 원본 예외와 스택은 같은 `traceId`로 서버 로그와 오류 수집 도구에만 남긴다.
- **디버그 정보(추천 적용 2026-10-21, ADR-0081)**: Problem의 `debug` 확장 필드(예외 종류와 스택 요약)는 로컬·CI(kind)에서 `PEAKET_DEBUG_ERRORS=true`일 때만 싣는다. 기본값은 꺼짐이고, 데모·스테이징·운영 환경 설정에서 켜져 있으면 서비스가 시작하지 않는다(시작 때 설정 검증, ASVS v5.0.0-13.4.2). 소유자가 준 REST 기준(2026-10-21, ADR-0081)은 개발·QA 환경에서 켜는 것을 허용하지만, 데모는 운영과 같은 다이제스트를 검증하는 곳이고 임시 클라우드 데모로 외부에 열릴 수 있어 켜지 않는다.
- **오류 본문은 한 형식이다(추천 적용 2026-10-21, ADR-0081)**: 서비스뿐 아니라 게이트웨이가 직접 내는 오류(레이트 리밋 429, 본문 상한 413, 차단기 503, 없는 경로 404)도 Envoy `local_reply_config`의 `json_format`과 `content_type: application/problem+json`으로 같은 Problem 본문을 낸다. API 경로의 엣지 정적 응답(매진 410)도 CloudFront Function이 응답 `body`로 Problem 본문(`type` `sold-out`)을 만든다. 예외는 둘이다. 기기 승인 토큰 엔드포인트의 400(아래)과, 대기열 파일 배포처럼 정적 파일을 내는 배포의 404다. 정적 파일 404는 본문을 약속하지 않고 클라이언트는 상태 코드만 본다(셔플 결과 게시 전 404, ADR-0058). openapi의 4xx·5xx 응답은 모두 Problem을 선언한다(`$ref`와 `description` 덮어쓰기, OpenAPI 3.1.0 Reference Object).
- **`type`·상태 코드·`title`은 한 묶음이다(ADR-0081)**: 한 `type`은 언제나 같은 상태 코드와 같은 `title`로 낸다(`title`은 번역만 달라진다, RFC 9457 §3.1.3). 같은 원인을 두 상태 코드로 내지 않는다. 2026-10-21 점검에서 openapi 응답 설명에 이름이 있는 `type`은 모두 상태 코드가 하나였다. 이름 없는 오류의 `type`과 전체 목록(`@peaket/api-client`의 표)은 wbs 0.2.3에서 만든다. `type` URI를 열면 그 오류의 설명 문서가 나오게 한다(RFC 9457 §3.1.1 SHOULD, 개발자 포털 문서와 함께 wbs 0.2.3).
- 정상적인 좌석 홀드 경합 패배(HTTP 409 Conflict)는 시스템 장애가 아닌 비즈니스 정상 분기로 취급하여 에러 모니터링 통계에서 분리 집계한다(NFR-003).
- 서킷 브레이커 트립 및 게이트웨이 과부하 차단 시에는 HTTP 503 Service Unavailable 응답과 함께 `Retry-After` 헤더를 필수 반환한다. 전석 매진 이후 인입된 예매 요청은 CloudFront 엣지 계층에서 HTTP 410 Gone(추천 적용 2026-10-09)과 매진 정적 응답(API 경로는 Problem `sold-out`, 화면 경로는 매진 안내 페이지, ADR-0081)으로 즉시 차단 응답한다. 회차의 판매 종료(공연 시작 24시간 전) 뒤의 대기열 진입·입장 확정·새 좌석 홀드·주문 생성(판매 종료 전 홀드의 주문은 제외)·취소표 알림 신청은 410 Gone과 `sale-ended` 오류로 거절한다(소유자 결정 2026-10-14, 오류 형식은 추천 적용 2026-10-14, ADR-0064).
- 프론트엔드 애플리케이션은 에러 객체의 `type` URI 식별자를 기준으로 다국어 UX 안내 메시지를 매핑 표출한다(d2 §4).
- 오류 식별자는 `type` URI의 마지막 경로(케밥 표기, 예: `seat-already-held`)로 통일한다. openapi 응답 설명의 대문자 이름(`DUPLICATE_ADMISSION`, `ENTRY_STARTED`, `TRIGGER_DEFERRED`, `NO_PLACEMENT` 등)은 같은 오류의 별칭이고 `type`은 그 이름의 케밥 표기다(예: `DUPLICATE_ADMISSION` → `…/problems/duplicate-admission`). 예외로 기기 승인 토큰 엔드포인트(`POST /v1/scanner/token`)는 RFC 8628 §3.5의 OAuth 오류 형식(`authorization_pending`, `slow_down` 등)을 그대로 쓴다.

## 3. 페이지네이션 (Pagination)
- 대량 목록 조회 API는 커서 기반 페이지네이션(`cursor`, `limit`, 최대 한도 100건(추천 적용 2026-10-09))을 표준으로 적용한다. 정렬 기준은 `sort=field:asc` 포맷을 사용하며, 다음 페이지 조회를 위한 불투명(Opaque) 커서 식별자를 응답 본문의 `nextCursor` 필드로 제공한다. 대규모 오프셋 건너뛰기 부하를 방지하기 위해 오프셋 기반 페이지네이션(`offset`, `page`)은 엄격히 배제하며, 파트너 콘솔의 대량 명단 다운로드는 청크 스트리밍 API로 분리 지원한다. 예외로 서버 변경 일련번호로 이어 받는 동기화 API(스캐너 변경분 `GET /v1/scanner/events/{eventId}/changes`)는 `after`·`limit`(최대 5,000)·`hasMore`를 쓴다(빠짐 없이 일련번호로 이어 받아야 해서다). 또 하나의 예외는 공연 검색(`GET /v1/search`)이다. 결과 화면이 페이지 번호(이전 · 1 2 3 … n · 다음)와 주소 `?q=&page=`를 쓰므로(소유자 결정 2026-10-14, ADR-0063) `page`·`limit`(기본 20 [가정], 최대 50)를 받고 `total`·`totalPages`를 준다. 오프셋 부하는 `page × limit` 1,000 [가정] 상한과 30초 [가정] CDN 캐시로 묶는다(추천 적용 2026-10-14, ADR-0063). 내 문의 내역(`GET /v1/inquiries`)도 화면이 페이지 번호를 써서 같은 `page`·`limit`를 받고 `total`을 준다. 한 계정의 목록이라 오프셋 부하가 작다(추천 적용 2026-10-19, ADR-0066).
- **한 번에 받을 건수의 이름은 `limit` 하나다(추천 적용 2026-10-21, ADR-0081)**: 커서 방식이든 페이지 번호 방식이든 `limit`이다(소유자 기준의 예 `?page=2&limit=50`과 같다). 예전 이름 `size`는 쓰지 않는다. 페이지 번호는 1부터 센다. `limit`이 최대값을 넘으면 400이다(잘라서 받지 않는다).
- **목록이면 나눈다(ADR-0081)**: 목록을 주는 GET은 커서(`cursor`·`limit`·`nextCursor`)나 위의 예외 방식으로 나눈다. 나누지 않는 목록은 건수 상한이 정해진 작은 목록뿐이다(로그인한 기기 최대 5대(POL-019), 로그인 수단 3종, 좌석맵 템플릿 10종, 공연 리포트 판 R0~R3, 회차 하나의 결제사별 정산서). 2026-10-21에 마이 티켓·굿즈 상품·미수금·스캐너 기기·스캐너 이상 표시 목록에 커서를 더했다. 결과가 0건이면 404가 아니라 200과 빈 `items`다(§12).
- **왜 오프셋이 아니라 커서인가**: 소유자 기준은 페이지 번호와 offset 방식을 예로 든다. 오프셋 방식은 뒤 페이지로 갈수록 앞 행을 모두 건너뛰어 큰 목록에서 느려지고, 그사이 새 행이 들어오면 중복·누락이 생긴다. 그래서 기본은 커서이고(Zalando RESTful API 지침 [160]도 커서를 권한다) 화면이 페이지 번호를 보여 주는 두 목록만 페이지 번호 방식이다. 커서 방식에서 '필요한 페이지를 요청한다'는 기준은 `nextCursor`로 다음 페이지를 고르는 것으로 채운다. 원하는 번호로 바로 건너뛸 수 없는 것은 커서 방식의 한계로 받아들인다. 큰 목록에는 전체 건수를 주지 않는다(Zalando [254]). 검색의 `total`은 위의 `page × limit` 상한으로 묶는다.

## 4. 멱등성 키 (Idempotency Key)
- 다시 보내면 효과가 두 번 생길 수 있는 쓰기 요청(좌석 홀드, 주문 생성, 결제 접수, 예매 취소, 티켓 양도(요청·수락·거절·철회)·돌려주기, 굿즈 주문, 운영 명령, 승인 업무 요청, 게시물 신고, 고객 문의 접수·추가 문의와 답변, 판매자 정보 변경 요청 등 openapi에서 `IdempotencyKey` 파라미터가 붙은 작업)은 클라이언트가 생성한 UUID v4 형식의 `Idempotency-Key` 헤더를 필수 요구한다. 원래 멱등인 작업(DELETE, 같은 요청이 다시 와도 결과가 같은 상태 전이·승인)과 기록마다 ID를 가진 동기화(게이트 스캔 업로드는 단말이 만든 스캔 ID로 거른다)는 이 헤더를 요구하지 않는다. 동일한 멱등키로 재요청이 인입될 경우 비즈니스 로직을 재실행하지 않고 최초 커밋된 캐시 응답을 즉시 반환한다.
- 멱등 상태 저장소: 좌석 홀드 멱등키는 좌석 Redis 클러스터의 동일 샤드에 저장하며, 주문 및 결제 멱등키는 PostgreSQL 원장 테이블과 동일한 트랜잭션 경계 내에서 원자 커밋한다. PG사 결제 승인은 `Idempotency-Key: confirm-{orderId}`, 결제 취소는 `cancel-{cancellationId}` 형식을 표준화한다. 외부 결제사의 멱등키 유효 수명(토스페이먼츠 15일, 포트원 3시간) 차이를 고려하여 재시도 유효 윈도우는 보수적으로 3시간 이내로 통제하며, 시한 초과 시 결제 단건 조회 API로 사전 상태를 검증한 후 진행한다. 포트원 어댑터는 RFC 8941 구조화 필드 규약에 따라 멱등키 값을 큰따옴표로 감싸 전송한다.
- 비동기 Kafka 컨슈머는 이벤트 고유 ID 기반의 멱등 컨슈머 패턴을 필수 적용하며, 현장 게이트 스캔 로그는 클라이언트 단말이 로컬 생성한 UUID를 기준으로 중복 처리를 차단한다.

## 5. 재시도와 데드라인 전파 (Timeouts and Deadlines)
- Envoy API 게이트웨이가 인입 요청 경로별 최대 허용 타임아웃(Deadline)을 설정하여 헤더로 주입하며, 백엔드 마이크로서비스는 gRPC 컨텍스트를 통해 남은 유효 시간을 단조 감소 방식으로 이어받는다. 다운스트림 잔여 실행 시간이 임계치 미만일 경우 불필요한 연산을 방지하기 위해 즉시 조기 실패(Fail-Fast) 처리한다 (예: 좌석 홀드 전체 데드라인 40ms, 결제 승인 PG사 호출 데드라인 2초, 주문-결제-발권 종단 확정 3초).
- 일시적 네트워크 전송 오류에 대한 재시도는 서비스 메시(Istio) 프록시 계층에서 사전에 정의된 재시도 예산(Retry Budget) 한도 내에서만 제한 집행한다(기본값 덮어쓰기는 docs/architecture.md §5, ADR-0082). API 게이트웨이 및 애플리케이션 코드는 네트워크 레벨의 무분별한 재시도를 수행하지 않는다. 상태 변경 요청은 멱등키가 존재하더라도 게이트웨이 레벨에서 자동 재시도하거나 헤지 요청을 발행하지 않으며, 헤지 요청은 읽기 전용 작업(좌석 배치도 스냅샷 조회)에만 국한 적용한다.
- 외부 결제 대행사 승인 실패에 대한 비즈니스 재시도는 payment-svc가 내부 작업 큐와 PG사 유효시간(토스 10분)을 기준으로 정밀 통제하며, 예매 취소 및 환불 실패 건의 재시도 역시 payment-svc 워커가 전담한다.
- 클라이언트 브라우저는 서버가 응답한 `Retry-After` 헤더 값과 ±20% 지터(Jitter)를 준수하여 재시도 폭주를 분산한다. 대기실 상태 조회 폴링은 예상 대기 시간에 따라 1초, 5초, 20초의 적응형 주기로 자동 전환된다.
- Google SRE Book 22장 지침에 따라 단일 요청당 최대 재시도 횟수를 제한하고, 프로세스 단위 재시도 예산(예: 분당 60회 초과 차단)을 엄격히 집행한다.
- **gRPC 클라이언트 채널 규칙(추천 적용 2026-10-22, ADR-0082)**: 서비스 사이 gRPC 채널은 서비스 템플릿의 채널 생성 함수 하나로만 만든다.
  - 재시도·헤지 정책(서비스 설정의 `retryPolicy`·`hedgingPolicy`)을 넣지 않고 `grpc.enable_retries`를 끄지 않는다. 그러면 라이브러리는 서버 앱이 받기 전에 실패한 요청만 투명하게 다시 보낸다(gRPC A6). 메시 없는 포트폴리오 실행에서 남는 재시도는 이것뿐이다.
  - 받은 데드라인에서 남은 시간을 계산해 넘기고, 추적 헤더는 OTel SDK가 넘긴다. 메시는 이 둘을 대신하지 못한다(docs/architecture.md §5 '메시와 앱의 책임 경계').
  - 부하 분산 방식은 설정 값 `grpcLbProfile` 하나로 고른다. `service`(기본)는 Service 이름과 pick_first이고, 운영에서는 메시 웨이포인트가 요청 단위로 나눈다. `headless-round-robin`은 메시 없는 로컬에서 서비스 사이 gRPC를 여러 벌로 재는 측정 전용으로, 헤드리스 Service·`round_robin`·서버 `grpc.max_connection_age_ms`를 쓴다. 앰비언트 메시에서 파드 주소로 보내면 웨이포인트를 건너뛰므로 운영 오버레이에서는 쓸 수 없다(docs/devops.md §4.3).
  - 앱 코드에 일반 네트워크 재시도, 클라이언트 쪽 분산 로직, 파드 사이 TLS를 넣지 않는다. 저장소 클라이언트(PostgreSQL·Redis·Kafka)의 재시도·시간 초과는 docs/architecture.md §5 '시간 초과 기본값'을 따른다.

## 6. 분산 레이트 리밋 (Rate Limiting)
- 극심한 트래픽이 집중되는 핫패스 구간(대기열 순번 진입, 좌석 홀드, 결제 주문 접수)은 외부 인메모리 저장소 조회 오버헤드를 배제하기 위해 Envoy 게이트웨이 파드 로컬 메모리 토큰 버킷으로 1차 분산 방어한다. 반면 사용자 계정 단위의 전역 레이트 리밋은 rate-limit-svc 및 Redis 세션 클러스터를 통해 일반 API 경로에 한하여 선별 적용한다. 한도 초과 시 HTTP 429 Too Many Requests 응답과 함께 `Retry-After` 헤더를 반환한다.
- 초기 제한 임계치 [가정, Phase 2 부하 시험에서 확정]: 대기열 진입 경로 단말 기기당 10회/10초, 일반 REST 엔드포인트 로그인 사용자당 60회/분, 파트너 콘솔 테넌트당 600회/분을 기본 적용하며, 스테이징 부하 시험 결과에 따라 조정한다.

## 7. 인증 및 인가 아키텍처 흐름
- 일반 사용자 소셜 로그인: 프론트엔드 Auth.js(PKCE, state, nonce 검증) → 소셜 제공자 인가 → ID 토큰 서명 검증 → 내부 서비스 메시 mTLS 경로를 통해 identity-svc 세션 생성 → 최종 ES256 서명 JWT 액세스 토큰(유효기간 15분, `sub`, `sid`, `scope`, `pid`, `aud` 클레임 포함)과 참조형 리프레시 토큰(토큰 패밀리 기반 회전 및 재사용 감지)을 발급하여 `httpOnly`, `Secure`, `SameSite=Strict` 쿠키로 단말에 격리 보관한다. 두 쿠키는 소비자 웹 앱 서버가 주고 다른 호스트의 게이트웨이(액세스는 `gw-fan`·`gw-queue`, 리프레시는 `gw-fan`의 토큰 갱신)가 읽으므로 `Domain=peaket.example`과 `__Secure-` 접두사를 붙인다(액세스 `__Secure-peaket_at`, 리프레시 `__Secure-peaket_rt`는 경로를 토큰 갱신으로 제한). 한 호스트만 쓰는 쿠키는 `__Host-` 접두사다(추천 적용 2026-10-15, docs/features/identity.md §3).
- 게이트웨이 무상태 검증: 인그레스 게이트웨이는 인메모리 캐시된 JWKS 공개키로 서명 무결성, 토큰 만료, 토큰 유형(`typ`), 발급자(`iss`), 대상자(`aud`), 경로 접근 권한을 신속 검증한 뒤(ADR-0050 결정 9), 검증된 사용자 ID, 세션 ID, 권한 스코프, 가명 식별자 `pid`(ADR-0053)를 표준 내부 헤더로 주입하여 업스트림으로 전달한다. 백엔드 서비스는 주입된 내부 헤더와 메모리 내 세션 무효화 목록(세션 종료 이벤트 수신 기반 15분 보존)만을 조회하여 런타임 데이터베이스 부하를 0으로 통제한다. 내부 인증 헤더는 mTLS 신뢰 경계에 의해 게이트웨이와 인가된 내부 파드만이 주입할 수 있다.
- 예매 핵심 경로 인가: 본인확인이 완료된 계정의 액세스 토큰에만 `ticket:buy` 권한 스코프가 부여되며, 실제 예매 진입 시 1회성 입장 토큰(구매 세션 전용)이 필수 요구된다. purchase-svc는 입장 토큰의 고유 식별자(`jti`)를 처음 쓸 때 Redis `SET NX`로 한 구매 세션에 묶고, 토큰의 `sid`가 요청자의 세션과 같은지 확인하며, 이후 요청은 그 구매 세션의 키로 서명해야 받는다(ADR-0050 결정 8). 그래서 토큰 사본만으로는 다른 세션에서 쓰지 못한다. 좌석 Redis 페일오버 때 복제되지 않은 묶음은 사라질 수 있으며, 그때 다시 묶을 수 있는 요청은 같은 `sid`의 것뿐이다.
- 관리자 및 파트너 계정: 파트너 콘솔은 Auth.js Credentials 공급자를 통해 identity-svc에서 다중 인증(MFA TOTP)을 검증하며, 내부 운영자는 전용 `gw-ops`를 경유하여 identity-svc 로그인 API를 호출한다. 파트너 액세스 토큰은 파트너 콘솔 앱 서버가 주고 `gw-partner`가 읽는 `__Secure-peaket_partner_at`, 운영자 액세스 토큰은 `gw-ops`만 주고 읽는 `__Host-peaket_ops_at`이다(openapi `partnerCookie`·`opsCookie`). 두 액세스 토큰(15분)은 리프레시 쿠키(파트너 `__Secure-peaket_partner_rt`, 운영자 `__Host-peaket_ops_rt`)로 `POST /v1/partner/auth/access-tokens`·`POST /v1/ops/auth/access-tokens`에서 갱신하고, 본문이 없는 요청이라 게이트웨이가 `Origin`을 콘솔 출처와 대조한다(openapi `partnerRefreshCookie`·`opsRefreshCookie`, 추천 적용 2026-10-15, ADR-0065 결정 11). 관리자 세션은 유휴 1시간 경과 시 전면 재인증을 요구하며, 파괴적 운영 명령 집행 시 실시간 2차 인증을 강제한다.
- 재인증 토큰: 팬 민감 작업(POL-019 목록)과 관리 계정의 위험 명령·승인 실행은 5분 1회용 재인증 토큰(`typ` reauth+jwt)을 `X-Reauth-Token` 헤더로 보낸다. 본문 필드나 URL로는 받지 않는다(2026-10-13 전수 점검에서 통일, openapi `ReauthToken`). 토큰이 없거나 만료·재사용이면 403 `reauth-required`(별칭 `REAUTH_REQUIRED`)로 답하고, 같은 경로의 다른 403(예: 결제자가 아님 `NOT_PAYER`)과는 `type`으로 가른다.
- 현장 게이트 스캐너 단말: cert-manager 기반 단말 기기 인증서 mTLS 상호 인증(`gw-scanner`가 TLS 종단)과 현장 스태프 세션 토큰을 병용한다. 현장 요원은 RFC 8628 기반 기기 간편 승인 절차(`POST /v1/scanner/device-authorizations` → 모바일 승인 → `POST /v1/scanner/token`)로 로그인하며, 발급된 스캐너 토큰은 ES256 서명, `scanner` 대상자 클레임, 회차 및 배정 역할, 기기 인증서 지문(`cnf`)을 포함하고 역할 유효 끝(공연 종료 2시간 뒤)에 만료된다. 스캐너 경로는 요청마다 세션·배정 상태를 확인한다(ADR-0030·0051).
- 분산 토큰 라이프사이클의 전체 설계 결정은 ADR-0011에 상세 기술되어 있다.

## 9. 공통 헤더 및 캐싱 규약
- 모든 HTTP 응답 헤더에는 분산 추적 식별자인 `traceId`(OpenTelemetry 표준)가 필수 포함되며, §4의 대상 쓰기 요청에는 `Idempotency-Key` 헤더가 필수다. 다국어 지원을 위해 `Accept-Language`(ko, en, ja, zh)를 협상한다.
- 인증 토큰, 비밀번호, 본인확인 정보 등 일체의 민감 정보와 그 값만으로 권한이 생기는 비밀(1회용 토큰·코드)은 URL 경로 및 쿼리 파라미터에 포함할 수 없으며 TLS로 보호되는 HTTP 요청 본문이나 보안 헤더로만 전달한다. 인증이 수반되는 모든 API 경로는 CDN 캐싱에서 엄격히 제외되며 `Cache-Control: no-store` 헤더를 강제한다. 다른 자격(임시 쿠키, 로그인 세션과 재인증 토큰)이 함께 있어야 쓸 수 있는 식별자(계정 연결·병합 제안 ID)는 경로에 둘 수 있되, 로그·트레이스에는 경로 템플릿만 남긴다. OAuth `code`·`state`는 프로토콜 규격상 예외다(ADR-0053 결정 14).
- 대기열 실시간 상태 캐시 파일 및 셔플 결과 파일은 무인증, 무쿠키(Cookie 헤더 제거) 엔드포인트로 서빙되며, 대기 순번 파일은 `Cache-Control: public, max-age=1`(기본. 차례에서 먼 구간의 수명을 늘리는 방식은 Phase 2에서 정한다, queue-admission §4), 셔플·묶음 결과 파일은 `Cache-Control: public, max-age=60` [가정, Phase 2 부하 시험에서 확정](게시 전 404는 오류 캐시 1초, ADR-0058) 헤더를 적용하여 엣지 캐시 오프로드를 극대화한다.
- 공개 카탈로그 읽기(홈 피드 `GET /v1/home`, 검색 `GET /v1/search`, 연관 검색어 `GET /v1/search/suggestions`, 후기 요약 `GET /v1/events/{eventId}/review-summary`)는 인증 없이 부르고, CDN 캐시 정책에서 쿠키를 캐시 키와 원본 요청에서 뺀다. 캐시 키에는 정규화한 검색어(NFKC·소문자·앞뒤 공백 제거)와 명시한 쿼리 파라미터만 넣어 같은 질의가 한 캐시를 쓰게 한다. 수명은 홈 30초·검색 30초·연관 검색어 60초·후기 요약 60초 [가정]이고 원본 장애 때는 `stale-if-error`로 마지막 응답을 낸다. 장르별 랭킹 파일과 회차 좌석맵 파일은 공연 페이지 배포의 정적 파일이다(랭킹은 게시 때 무효화, 좌석맵은 판이 이름에 들어 `immutable`). 개인 값이 섞이는 후기 목록·단건은 `Cache-Control: private, no-store`다(추천 적용 2026-10-14, ADR-0063).
- **쓰기 요청의 출처 확인(CSRF, 추천 적용 2026-10-15, ADR-0065 결정 5)**: 쿠키로 인증하는 쓰기 요청(POST·PUT·PATCH·DELETE)은 게이트웨이가 `Origin`을 그 게이트웨이의 허용 출처 목록과 대조한다. `Origin`이 없으면 `Sec-Fetch-Site`가 `same-origin`이나 `same-site`인지 보고, 둘 다 없으면 거절한다. 결제사·파트너 웹훅(서명 검증)과 서버 사이 호출은 쿠키를 받지 않으므로 예외다. ADR-0008의 'Origin/Referer 검증'은 이 규칙으로 읽고, 쿠키의 `SameSite` 설정은 이 확인을 대신하지 않고 겹쳐 막는다(docs/architecture.md §4).
- **사전 요청이 생기지 않는 교차 출처 쓰기(ADR-0065 결정 6)**: www에서 `queue` 호스트로 가는 대기열 진입(`POST /v1/queues/{eventId}/entries`)과 입장 확정(`…/admission`)만 이 형식이다. 본문은 JSON 문자열이지만 `Content-Type: text/plain;charset=UTF-8`로 보내고 safelisted가 아닌 헤더(`Idempotency-Key`, `traceparent` 같은 추적 헤더 포함)를 붙이지 않아 브라우저가 사전 요청(OPTIONS)을 보내지 않게 한다. 서버는 이 두 경로에서 `text/plain`과 `application/json`만 받고(그 밖은 415) 본문을 JSON으로 검사한다. 사전 요청이 없으니 위조 방지는 본문의 사전 검증 토큰·대기표(허용한 출처만 응답을 읽어 얻는 값), 위 `Origin` 확인, `SameSite=Strict` 쿠키가 맡는다(ASVS v5.0.0-3.5.1). 그 밖의 교차 출처 API는 JSON과 사전 요청을 그대로 둔다.
- **CORS 응답 헤더(ADR-0065 결정 3·7)**: 허용 출처는 게이트웨이마다 화면 호스트 하나로 고정하고 요청의 `Origin`을 그대로 되돌려 주지 않는다. 쿠키를 받는 API는 `Access-Control-Allow-Credentials: true`와 `Vary: Origin`을 두고, 사전 요청 응답은 `Access-Control-Max-Age: 7200`이다(Chromium 상한 2시간, MDN). `queue` API와 `queue-files` 배포(S3 대체 원본 포함)는 소비자 웹이 `Retry-After`를 읽도록 `Access-Control-Expose-Headers: Retry-After, Date`를 더하고(`Date`는 브라우저 시계 보정용이고 `api`·`scanner-api`도 `Date`를 노출한다, 추천 적용 2026-10-21, ADR-0079 결정 3), 쿠키가 없는 `queue-files`에는 Credentials를 두지 않는다. 값을 붙이는 곳은 docs/infra.md §9다.
- **CSV·XLSX 내려받기(ADR-0065 결정 12)**: 정산 리포트·예매자 명단·좌석맵 내보내기 같은 파일 응답은 `Content-Disposition: attachment`와 정확한 `Content-Type`으로 내고, 칸 값이 `=`·`+`·`-`·`@`·탭·CR로 시작하면 그 앞에 작은따옴표를 붙여 스프레드시트가 수식으로 읽지 않게 한다. 인코딩이 아니라 칸 값 규칙이므로 서버가 파일을 만들 때 적용한다. 브라우저가 만드는 내보내기(파트너 좌석맵 에디터의 CSV)는 화면 코드가 같은 규칙을 지킨다(추천 적용 2026-10-21, docs/frontend.md §5.6).

## 10. URI 설계 규칙 (ADR-0081)

소유자가 준 REST 설계 기준(2026-10-21)을 이 API에 맞춘 규칙이다. 기준 원문 요약, 점검 결과, 바꾼 경로의 옛 경로 대응표는 ADR-0081에 있다. 따로 적지 않은 것은 추천 적용 2026-10-21이다. 경로 규칙과 문서가 이름을 댄 경로가 openapi에 있는지는 `tools/doc-check`의 `api` 검사가 확인한다(바꾸기 전 명세에서는 경로 57개에서 75건을 잡았다).

- **경로는 자원(명사)을 가리킨다.** 동작은 HTTP 메서드가 나타내고 경로에 동사(`getUsers`, `approve`, `refresh`, `login`)를 쓰지 않는다. 만들기·읽기·고치기·지우기로 나타낼 수 없는 상태 바꾸기는 그 동작이 남기는 기록의 이름을 하위 자원으로 두고 POST한다(Zalando RESTful API 지침 [141]의 '취소 우편함' 방식). 예: 승인 `…/approvals`, 거절 `…/rejections`, 양도 수락 `…/acceptance`, 홀드 연장 `…/extension`, 되돌리기 `…/reversions`, 기기 폐기 `…/revocation`. 여러 번 쌓일 수 있는 기록은 복수형이고(명령의 승인·거절·되돌리기, 명령 2의 연장, 일괄 환불의 정지·재개, 받은 티켓 돌려주기), 부모마다 한 번만 생기는 결과는 단수형이다(양도 수락·거절·철회, 홀드 1회 연장, 기기 폐기, 병합 확인).
- **컬렉션은 복수형, 싱글턴은 단수형이다.** 같은 종류의 모음은 복수 명사(`/tickets`, `/holds`)이고 단건은 그 뒤에 ID를 붙인다. 부모마다 하나뿐인 하위 자원(싱글턴)은 단수 명사다(`/seatmap`, `/entry-policy`, `/wish`, `/payout-account`, Google AIP-156). 컬렉션 바로 뒤 자리는 ID 자리이므로 고정 단어를 두지 않는다(`/reviews/images`가 아니라 `/review-images`. Google AIP-122의 '컬렉션 이름과 ID를 번갈아 둔다').
- **나를 가리키는 예약 ID `me`.** 로그인한 사람의 항목을 ID 없이 가리킬 때는 `me`를 쓴다(`DELETE /v1/queues/{eventId}/entries/me`). 처음 기기가 없어도 다른 기기에서 취소할 수 있어야 해서 대기표 ID를 요구하지 않는다(ADR-0060). 컬렉션 자체에는 DELETE를 보내지 않는다(컬렉션 전체 삭제로 읽힌다). 예외로 알림 신청 끄기(`DELETE /v1/events/{eventId}/subscriptions?kind=`)는 `kind`로 고른 내 신청만 지우는 필터 삭제이고 같은 요청을 다시 보내도 204다.
- **깊이는 2단계까지다.** `컬렉션/{ID}` 한 쌍이나 싱글턴 하나가 1단계다(소유자 기준의 예: `/users/{userId}/orders/{orderId}`는 2단계). 버전(`v1`)과 정해진 네임스페이스는 세지 않는다. 네임스페이스는 호출 주체(`partner`, `ops`, `scanner`)와 모듈(`identity`, `shop`, `auth`, `compliance`, `webhooks`)뿐이고, 네임스페이스 바로 뒤에는 ID가 오지 않는다(그래서 `/v1/queue/{eventId}`가 아니라 `/v1/queues/{eventId}`다). 3단계가 되면 ① 하위 자원이 전역 ID를 가지면 목록·생성만 부모 아래 두고 단건 경로는 위로 올리거나(얕은 중첩, Rails 라우팅 안내서 'Shallow Nesting'. 예: `GET /v1/partner/events/{eventId}/staff`와 `DELETE /v1/partner/staff/{assignmentId}`) ② 두 단어를 하이픈으로 이어 한 단계로 만든다(`/seatmap/snapshot` → `/seatmap-snapshot`). Microsoft의 웹 API 설계 지침도 collection/item/collection보다 복잡한 URI를 피하라고 하고, Zalando [147]은 하위 단계를 3 이하로 권한다.
- **표기.** 경로는 소문자이고 여러 단어는 하이픈으로 잇는다(`/order-items`, 밑줄 없음, Zalando [129]). 쿼리 파라미터 이름은 본문 JSON 필드와 같은 camelCase다(`dueWithinDays`). Zalando [130]은 snake_case를 요구하지만, 이 API는 쿼리와 본문의 필드 이름을 하나로 맞추는 쪽을 택했다(orval이 만드는 타입 이름과 같다).
- **끝 슬래시를 쓰지 않는다.** `/v1/tickets`와 `/v1/tickets/`는 RFC 3986에서 서로 다른 URI다. 끝 슬래시가 붙은 요청과 빈 단계(`//`)가 든 요청은 404이고 리다이렉트하지 않는다. 리다이렉트는 왕복을 늘리고, 같은 자원에 주소가 둘이면 CDN 캐시도 둘로 나뉜다(RFC 9110 §4.2.3은 정규화하면 같아지는 URI로 서로 다른 자원을 가리키지 말라고 한다). Fastify 어댑터 서비스는 기본값(`routerOptions.ignoreTrailingSlash: false`, 두 주소를 다르게 봄)을 그대로 두고, Express 어댑터 서비스(NestJS 기본)는 Express가 기본으로 두 주소를 같게 보므로 `strict` 라우팅을 켠다.
- **확장자는 CDN이 내는 정적 파일에만 쓴다**(`/v1/queues/{eventId}/segment-states/{segment}.json`, `/v1/home/rankings.json`, `/v1/events/{eventId}/seatmap-layouts/{layoutVersion}.json`). S3 객체 키와 경로가 같아야 해서다. 그 밖의 형식은 `Accept` 헤더로 고른다(공연 리포트의 `text/markdown`).
- **예외(이유와 함께 고정한다).** ① 기기 승인 토큰 엔드포인트 `POST /v1/scanner/token`은 OAuth 관례의 단수 이름과 오류 형식을 따른다(RFC 8628) ② 결제사 웹훅 수신 `POST /v1/webhooks/toss`·`/portone`은 결제사 이름이 ID 자리에 온다 ③ 비밀값으로 찾는 조회는 GET 대신 POST `…-lookups`로 받는다(§12) ④ `/graphql`은 REST가 아니다(관제 대시보드·감사 로그 읽기) ⑤ 전역 검색 `GET /v1/search`는 기능 이름이 경로다(소유자 기준의 '전역 검색' 예와 같다).

## 11. 검색·부분 응답·하이퍼미디어 (ADR-0081)

- **검색은 GET과 쿼리 문자열이다.** 전역 검색은 `GET /v1/search?q=`(공연·아티스트·공연장)이고, 특정 자원 안의 검색은 그 컬렉션의 GET에 필터를 붙인다(`GET /v1/ops/cases?kind=&dueWithinDays=`). 자유 입력 검색어는 `q` 하나로 받는다.
- **조건과 페이지 파라미터를 섞지 않는다.** 예약 이름 `q`·`cursor`·`limit`·`page`·`sort`·`fields`는 그 뜻으로만 쓰고 필터 이름으로 쓰지 않는다. 필터 이름은 응답 필드 이름과 같게 한다(`status`, `genre`, `venueId`). 그래서 `?status=ON_SALE&page=2&limit=20`에서 무엇이 조건인지 이름만으로 갈린다.
- **조건을 `q` 하나에 이어 붙이는 형식(`?q=name%3Dcho,region%3Dseoul`)은 쓰지 않는다(추천 적용 2026-10-21).** 소유자 기준이 권하는 형식이지만 이 API에서는 세 가지가 맞지 않는다. ① 공개 검색은 CDN이 캐시하고 캐시 키는 정규화한 `q`와 명시한 필터 파라미터다(§9). 조건을 한 문자열에 넣으면 같은 조건도 순서·구분자만 달라 다른 캐시 키가 된다. ② 필터마다 openapi 스키마(열거값·날짜 형식·최대 길이)로 입력을 검사하는데, 한 문자열이면 따로 해석기를 만들어야 하고 값에 `,`·`=`가 들어갈 때의 이스케이프 규칙도 필요하다. ③ 위의 예약 이름 규칙만으로 '조건과 페이지 파라미터가 섞여 헷갈리는' 문제가 풀린다. 조건을 AND·OR로 묶어야 할 만큼 복잡해지면 그때 한 파라미터 문법(Google AIP-160의 `filter`)을 따로 정한다.
- **부분 응답 `fields`.** 이름과 문법을 정해 두되 지금 쓰는 경로는 없다. 문법은 필드를 쉼표로 나열하고 하위 객체는 점으로 잇는다(`?fields=eventId,title,venue.name`, Zalando [157]과 Google API 시스템 파라미터 `fields`). 모르는 필드는 400이고, `fields`는 보여 줄 범위를 줄이기만 해서 권한 검사를 바꾸지 않는다. CDN이 캐시하는 공개 읽기에는 쓰지 않는다(캐시 키가 필드 조합마다 갈린다). 응답 크기나 조인 비용이 측정으로 문제가 된 목록에만 그 경로에서 켠다. 화면마다 필요한 필드가 다른 관제 읽기는 GraphQL(`/graphql`)이 이미 필드를 고르게 한다.
- **하이퍼미디어(HATEOAS)는 기본으로 넣지 않는다.** 클라이언트가 모두 openapi에서 생성한 우리 앱이라 응답 속 링크에 기대는 이득이 작고, 링크는 응답을 키우고 클라이언트를 링크 이름에 묶어 바꾸기 어렵게 한다(소유자 기준의 지적과 같고, Zalando [163]도 일반적으로 권하지 않는다). 대신 표준 헤더와 필드로 다음 행동을 알린다: 만든 자원의 주소 `Location`(§12), 다시 보낼 때 `Retry-After`, 다음 페이지 `nextCursor`, 오류 설명 문서로 가는 `type` URI(§2). 상태에 따라 할 수 있는 행동이 바뀌는 화면(양도·취소 가능 여부)은 응답의 상태·기한 필드(`transferable`, `cancelDeadline`)로 알린다.

## 12. 메서드와 상태 코드 (ADR-0081)

- **메서드.** 조회는 GET, 만들기와 그 밖의 처리는 POST, 통째로 바꾸기는 PUT, 일부 고치기는 PATCH, 지우기는 DELETE다. GET·HEAD·OPTIONS는 상태를 바꾸지 않는다(RFC 9110 §9.2.1. 브라우저·크롤러·프록시가 미리 보내거나 다시 보낸다). PUT·DELETE는 같은 요청을 다시 보내도 결과가 같게 만든다(§9.2.2). POST로 읽기만 하는 경로는 두 종류뿐이다. ① 비밀값으로 찾는 조회: 초대 토큰·기기 확인 코드·휴대폰 번호는 URL에 넣지 않으므로(§9) 본문에 담아 `POST …-lookups`(`/v1/staff-invitation-lookups`, `/v1/device-approval-lookups`, `/v1/transfer-recipient-lookups`)로 받는다. 응답은 200과 `Cache-Control: no-store`이고 상태를 바꾸지 않는다. 본문을 싣는 안전한 메서드 QUERY(RFC 10008, 2026-06)는 CloudFront 캐시 동작이 고를 수 있는 메서드 묶음(GET·HEAD, +OPTIONS, +PUT·PATCH·POST·DELETE)에 없어 쓰지 않는다. ② GraphQL `/graphql`. 2026-10-21 점검에서 상태를 바꾸는 GET은 없었고, 근무 정보를 POST로 읽던 스캐너 근무 준비는 `GET /v1/scanner/shift`와 `PUT /v1/scanner/shift/readiness`로 나눴다.
- **성공 코드.** 자원을 만들면 201이고, 만든 자원을 GET으로 읽을 수 있으면 `Location`을 준다(RFC 9110 §15.3.2. 지금은 양도 요청·후기·문의). 읽는 경로가 없는 기록 생성은 201과 본문의 ID다. 동작 기록 하위 자원에 POST하는 상태 바꾸기는 바뀐 상태를 200으로 돌려준다. 나중에 처리하는 접수는 202, 돌려줄 본문이 없으면 204다. 실패를 200 본문(`{"success": false}`)으로 감싸지 않는다.
- **오류 코드의 뜻.** 400은 형식이 틀림(JSON 깨짐, 타입·범위 밖, 모르는 `fields`), 422는 형식은 맞지만 업무 규칙에 어긋남(매수 한도, 동의 누락, 검증 오류 목록), 401은 누구인지 모름(로그인·토큰 필요), 403은 누구인지 알지만 안 됨(역할 밖, 재인증 필요 `reauth-required`), 404는 그 ID의 자원이 없음이다. 개인·거래 기록(양도 요청·문의·정산서)은 남의 것이면 있는지조차 알리지 않도록 403 대신 404로 답한다(RFC 9110 §15.5.4). 공연·회차처럼 있다는 사실이 이미 공개된 자원과 그 회차의 하위 자원(이미지·좌석맵·리포트)은 남의 것이면 403이다. 409는 지금 상태와 부딪침(이미 처리됨, 판(version) 불일치), 410은 다시 오지 않는 끝(판매 종료 `sale-ended`, 만료된 초대·코드, 보존 기간 끝), 423은 운영자가 잠근 자원(판매 일시정지, 잠긴 계정. WebDAV의 Locked를 이 뜻으로 쓴다), 429·503은 잠시 뒤 다시(`Retry-After` 필수)다.
- **조회 성공 + 데이터 없음 = 200.** 목록·검색이 0건이면 200과 빈 `items`다. 특정 ID 하나를 집어 물었는데 없으면 404다. 아직 만들어지지 않은 단건(R3 전의 파트너 판매 요약, 게시 전 셔플 결과 파일)도 그 주소의 자원이 아직 없으므로 404이고, 서비스가 내는 404는 `type`으로 '아직 없음'과 '없는 ID'를 가른다.
- **401에는 `WWW-Authenticate`를 싣는다(RFC 9110 §15.5.2 MUST, 추천 적용 2026-10-21).** 스캐너 경로는 `Bearer realm="peaket-scanner"`(RFC 6750 §3, 토큰이 틀리거나 만료면 `error="invalid_token"`), 쿠키 경로는 `Cookie realm="peaket"`, 입장 토큰 경로는 `AdmissionToken realm="peaket"`이다. 쿠키로 보내는 인증에는 IANA 인증 방식 등록부에 오른 이름이 없고(2026-10-21 확인) RFC 6750이 정한 Bearer 토큰 전달 방법(헤더·폼 본문·쿼리)에도 쿠키가 없어서, Bearer라고 쓰지 않고 프로젝트가 정한 이름을 쓴다. 등록되지 않은 이름이라 브라우저는 로그인 창을 띄우지 않고 무시하며, 화면은 지금처럼 401을 보고 토큰 갱신이나 로그인으로 간다. 405에는 `Allow`를 싣는다(RFC 9110 §15.5.6 MUST).
- **자기 서술성 점검.** 모든 작업에 `summary`와 `description`(FR·POL·ADR 근거)이 있고 오류 응답은 Problem을 선언한다(2026-10-21 기준 4xx·5xx 244개 가운데 243개, 나머지 1개는 기기 승인 토큰 엔드포인트의 OAuth 오류). `operationId`는 아직 없다(0/181). 이름 규칙(docs/frontend.md의 프로시저 이름과 같게)과 함께 wbs 0.2.3에서 단다.
