# ADR-0003: 대기실 상태 갱신은 적응형 폴링, SSE는 쓰지 않음

- **상태**: 채택 (2026-10-07). ADR-0043(2026-10-12)이 좌석 자동 배정 공연에 한해 차례 직전 직접 확인(예상 대기 10초 이내 입장 확정 요청 직접 시도)을 더한다 ADR-0058(2026-10-13): 대기 상태 파일은 대기열 파일 배포(`queue-files`)로 나가고 배포별 한도를 미리 올린다. 2026-10-21(ADR-0079): 폴링 세부(실패 대기 상한 60초, '연결 확인 중' 조건, 숨긴 탭 최소 5초, 같은 회차는 한 탭만 폴링, `Date` 헤더 시계 보정)를 docs/frontend.md §5.1에 적었다. 대기실은 SWR이 아니라 프레임워크 없는 경량 페이지다. 2026-10-26(4차 점검 3부): 결과의 '완벽히 통제된다'(ADR-0002 결과의 '상한이 고정된다'도 같다)는 CloudFront 요청 병합과 Origin Shield가 기대대로 묶어 줄 때의 목표로 읽는다. 원본 요청은 파일당 초당 약 1건이 목표이고, 병합이 온전하지 않아 초당 1,000건을 넘으면 대기 상태 파일을 S3에 매초 직접 올리는 경로로 바꾼다. 엣지와 그 위 캐시 사이 갱신은 '엣지 수 × 활성 파일 수 ÷ 1초'까지 는다(docs/features/queue-admission.md §4·§12). 2026-10-28(ADR-0110, 소유자 승인 '추천안 동의'): 결정 1의 'CDN 에지에 1초간 캐싱'은 입장 임박 구간(그 구간의 첫 번호까지 예상 대기 60초 이내) 파일에서는 '다음 생성 시각까지(`Expires`, 낡은 값 허용 없음)'로 읽는다. 결정 2의 '잔여 시간 1분 이내는 1초'는 0.5초로 바꾼다. 그래서 결과의 'CDN 요청 초당 약 5.3만 건'은 약 5.4만 건으로 읽는다. 재검토 조건 둘째(p99 2초)는 단계별 지연 예산 표와 Q-T47로 판정한다. 2026-10-28(기술 검토 중간-032·038, 소유자 승인 '추천안 동의'): 폴링을 늦추는 백프레셔는 응답 헤더 `Retry-After`가 아니라 대기 상태 파일 본문의 `pollHintMs`(다음 폴링까지의 최소 간격)로 준다. 비상 경로의 S3 객체로는 `Retry-After`를 줄 수 없어, queue-svc 파일 생성 작업과 S3 사본이 같은 값을 싣는다. `Retry-After`는 503 응답의 재시도 하한으로만 쓰고 본문 값이 늘 앞선다. 서버가 하한을 주면 브라우저는 그 하한을 지키고 위쪽으로만 0~20% 지터를 더한다(기다림 = 하한 × (1 + U(0, 0.2))). 하한이 없는 폴링은 ±20% 그대로다(docs/features/queue-admission.md §4·§9, docs/frontend.md §4.1·§5.1). 2026-11-01(정합 점검, ADR-0177 해설서 검토 세 번째 묶음): 결정 3의 'SSE는 파트너 콘솔의 실시간 판매 현황 집계에만'은 파트너 판매 현황을 1분 주기 REST 조회(`live-snapshot`)로 바꾸고(ADR-0133 낮음-024), SSE는 관제 콘솔의 두 흐름에만 쓴다로 읽는다(ADR-0100 결정 1, docs/frontend.md §4.4.3). 대기실에서 SSE를 쓰지 않는 결정은 그대로다.
- **관련**: 설계서 섹션 6 '대기열'·'매진 처리', 섹션 8 '대기 상태 조회', 섹션 9 '대기 상태 전파' SLO, ADR-0002
- **관련 ID**: FR-007, POL-007, POL-008, POL-015, NFR-002, SCR-008

## 맥락

과거 초기 설계는 대기실 상태 갱신을 SSE(Server-Sent Events) 스트리밍으로 전달하고, 방화벽 등으로 SSE가 차단된 환경에 한해서만 CDN 폴링을 폴백(fallback)으로 적용하도록 구성했다. 그러나 동시 대기 100만 명 규모를 수용하는 아키텍처로 확장하면서 다음과 같은 물리적 한계가 발생했다.

- 100만 개의 TCP 지속 연결(Persistent Connection)을 유지하려면 게이트웨이 파드가 50~100개 이상 필요하며, 시스템 파일 디스크립터(FD) 및 상단 로드밸런서의 동시 연결 한도를 방대하게 프로비저닝해야 한다.
- 대기열 후미에 위치한 사용자에게까지 1초 미만 단위의 실시간 브로드캐스트를 제공하는 것은 자원 낭비이다.
- 글로벌 프로덕션 대기열 서비스 역시 폴링 방식을 표준으로 채택한다. Cloudflare Waiting Room은 대기 화면을 20초 주기로 갱신한다([Cloudflare 문서](https://developers.cloudflare.com/waiting-room/about/)). AWS Virtual Waiting Room 역시 대기 화면이 serving 번호를 주기적으로 폴링 갱신하는 구조를 취한다([GitHub 문서](https://github.com/aws-solutions/virtual-waiting-room-on-aws/blob/main/docs/software-architecture.md)).

## 결정

1. 대기 상태는 번호 1,000개 구간마다 정적 파일 하나로 집계하며, 1초 주기로 갱신하여 CDN 에지에 1초간 캐싱한다. 파일 페이로드에는 serving 번호, 차례 전진 속도(1초당 serving 통과 유효 번호 수), 판매 매진 상태, 구간 결번 비트맵을 포함한 정밀 인원 계산 메타데이터(ADR-0002)가 수록된다. 동일 구간에 속한 사용자는 완전히 동일한 파일을 수신한다.
2. 클라이언트는 본인의 예상 대기 시간에 따라 폴링 주기를 적응형(adaptive)으로 동적 조절한다. 잔여 시간 1분 이내는 1초, 1~5분 구간은 5초, 5분 초과 구간은 20초(Cloudflare 준용)를 적용하며, 모든 요청에 ±20% 지터(jitter)를 부여한다. 또한 서버는 과부하 시 `Retry-After` 헤더를 통해 능동적으로 주기를 연장할 수 있다.
3. 대기실 구간에서는 SSE 스트리밍을 전면 배제한다. SSE는 동시 접속자가 수백 명 규모로 통제되며 단방향 상태 갱신이 필요한 파트너 콘솔의 실시간 판매 현황 집계에만 국한하여 활용한다.
4. 대기 상태 파일에는 개별 사용자별 고유 식별값을 일절 포함하지 않는다. 사용자별 데이터가 포함되는 즉시 CDN 캐시 적중률이 파괴되기 때문이다. 프리큐(Pre-queue) 셔플 결과 역시 개인별 조회가 아닌 참가 토큰 해시 접두사로 파티셔닝된 셔플 결과 정적 파일을 CDN에 배포함으로써, 오픈 시점(T=0)에 origin 서버로 인입되는 개인화 조회 트래픽을 원천 차단한다(ADR-0012).

## 결과

- origin 서버 부하는 전체 접속자 수 및 클라이언트 폴링 주기와 무관하게 1초당 대기 상태 파일 개수(100만 번호 기준 약 1,000건) 수준으로 완벽히 통제된다.
- 대기실 단계의 TCP 지속 연결이 제거되어 게이트웨이 메모리, 파일 디스크립터, L4/L7 로드밸런서의 커넥션 고갈 위험이 근본적으로 해소된다.
- 대규모 부하 시험(Load Test) 시 100만 가상 사용자를 무거운 지속 연결이 아닌 순수 HTTP 요청률(초당 약 5.3만 건의 상태 조회) 모델로 안정적으로 시뮬레이션할 수 있다.
- 매진 공지 이벤트가 클라이언트의 개별 폴링 주기에 분산되어 점진적·자연스럽게 에지 단에서 전파된다.
- 트레이드오프: 대기열 후미 사용자의 화면 갱신이 최대 20초 지연될 수 있다. 이에 따라 '대기 상태 전파' SLO(p99 2초)는 입장 임박(예상 대기 1분 이내) 사용자 군을 기준으로 재정의했다.
- 트레이드오프: 인프라 비용이 CDN 요청 건수(초당 약 5.3만 건)에 비례하여 발생한다. 공연 1회당 발생하는 실질 CDN 비용은 KPI K9 측정을 통해 철저히 검증한다.

## 재검토 조건

- CDN 에지 요청 비용이 공연 1회당 책정된 인프라 예산 상한을 초과할 때
- 입장 임박 사용자에 대한 반영 지연 SLO(p99 2초)가 CDN 캐싱 폴링 환경에서 충족되지 못할 때
