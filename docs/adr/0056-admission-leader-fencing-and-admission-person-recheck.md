# ADR-0056: 입장 제어 리더의 쓰기는 리더 세대로 막고(펜싱), 입장 확정 때 1인 1순번을 다시 확인한다

- **상태**: 채택 (2026-10-13. R-56에서 남는 한계로 적은 두 틈을 막자는 제안을 소유자가 '그 안으로 보강해주세요'로 승인했다. 키 이름, 리더 상태를 Redis에 두는 범위, 응답 코드, 시험 번호는 추천 적용(2026-10-13)이다. ADR-0010 결정 5와 ADR-0005를 보완한다.) 2026-10-14 추천 적용(ADR-0062 결정 29·30): 입장 확정의 빠진 번호 검사에 추가 검증 통과 예외(`q:{event:E}:verify` PASSED)를 둔다. 만료 410 때 1인 1순번 중복 확인 키를 지우고, 이 회차에 이미 입장한 사람은 진입 때 409 `ALREADY_ADMITTED`로 막는다(queue-admission §3·§6·§7). 2026-10-14(ADR-0063 결정 11·ADR-0064): 결정 5의 `q:adm`은 온세일 윈도우가 아니라 그 회차의 판매 종료(공연 시작 24시간 전) TTL로 지운다(docs/data.md §3. 2026-10-20 3차 전수 점검에서 상태 줄에 적음). 2026-10-26(4차 점검 3부): 결정 4의 리더 상태에는 판매 일시정지(명령 3, 만료 없음. 회차 범위는 `q:{event:E}:ctl`, 전체 범위는 `q:{admission}:ctl`, ADR-0062)와 제어 입력 없음 상태·시작 시각(`q:{event:E}:ctl`, ADR-0069)도 둔다(docs/data.md §3). 2026-10-28(ADR-0103, 소유자 승인 '추천안 동의'): 결정 4의 '상태를 저장소에 먼저 두고 새 리더가 그 값으로 시작한다'를 다른 받는 쪽에도 넓힌다. purchase-svc는 판매 일시정지를 purchase DB `sale_control`(원본)과 좌석 Redis `s:{event:E}:ctl`(홀드 Lua가 읽는 사본)에, queue-svc는 판매 상태·공지를 `q:{event:E}:notice`에 두고, 모든 상태에 판 번호를 붙인다. 리더 상태 쓰기에도 판 번호를 함께 적는다. 2026-10-28(기술 검토 중간-028, 소유자 승인 '추천안 동의'): 결정 2·3의 '묶음 셔플 뒤 순번 카운터 전진'은 '구간이 닫히는 순간의 카운터 전진'으로 읽는다. 이 전진은 `q:{event:E}:batch_done`의 `HSETNX`로 묶음마다 한 번만 되므로, 리더가 늦거나 멈춰 있으면 구간이 지난 뒤 첫 진입 Lua도 리더 세대 확인 없이 같은 일을 한다. 로비 몫(`lobby` 필드)도 같다. serving 전진과 리더 상태 쓰기는 지금처럼 리더 세대를 확인한다(docs/features/queue-admission.md §3, docs/data.md §3). 2026-11-02(wbs 0.9.1 규칙 모델 검사, 리더 범위(대기표 1장, admission-ctrl 2대, 리더 교체 2회, 회차 슬롯 장애 전환 2회)): 결정 1~3의 세대 확인으로 옛 리더 쓰기는 장애 전환이 없으면 반영 0, 겹치면 장애 전환마다 1회 이하다(남는 한계의 수). 세대 확인을 빼면 장애 전환 없이도 반영되는 반례가(V-T1), 결정 5의 재확인을 빼면 장애 전환으로 대기표를 두 장 받은 사람이 두 번 입장하는 반례가 나온다. 또 묶음 참가자의 선점 값이 정해지지 않아(결과 게시 전에 PENDING이 만료됨) 장애 전환 없이도 한 사람이 대기표를 두 장 받는 반례가 나왔다. 재검토 조건 셋째('입장 확정 재확인 거절이 장애 전환 없이도 생길 때')의 원인 하나이고, 소유자 결정 대기다(PROGRESS OPEN[14], docs/verification.md §2.6). 2026-11-01(정합 점검, ADR-0177 해설서 검토 네 번째 묶음): 남는 한계의 '장애 전환 두 번이 겹칠 때'에 장애 전환 한 번으로 생기는 경우를 더해 읽는다. 첫 입장 확정 뒤 복제 지연(수백 ms) 안에 쓴 사람별 입장 키 `q:adm`과 1인 1순번 키 `q:dup`이 장애 조치로 사라지면, 그 사람은 다시 줄을 서 한 번 더 입장할 수 있다. 1인 매수 한도는 판매 확정 때 DB 원장 `purchase_quota`가 지킨다(docs/features/queue-admission.md §9 '대기열 Redis 페일오버' 행, docs/infra.md §6).

- **관련 ID**: FR-008, FR-037, POL-002, POL-008, POL-010, NFR-015, NFR-025

## 맥락

- **Lease 재확인은 확인과 쓰기 사이의 틈을 막지 못한다.** admission-ctrl은 쿠버네티스 Lease로 리더 하나를 뽑고, 명령을 실행하기 직전에 Lease를 다시 확인한다(ADR-0010 결정 5, docs/infra.md §8). 하지만 Lease 기반 선출은 한 순간에 리더가 하나뿐임을 보장하지 않는다. Kubernetes client-go `leaderelection` 패키지 설명은 이 구현이 한 클라이언트만 리더로 행동함을 보장하지 않는다(펜싱)고 적는다(2026-10-13 원문 확인). 재확인 뒤 GC로 멈추거나 API 서버와 끊긴 옛 리더가 Lease를 잃은 뒤 깨어나면, 새 리더와 함께 serving을 한 주기 더 올리거나 묶음 셔플 뒤 순번 카운터를 한 번 더 올릴 수 있다. ASVS 5.0 15.4.2(L3)가 말하는 확인 시점과 사용 시점의 경합이다.
- **리더가 바뀌면 운영자가 건 상태가 남는 곳이 없다.** 입장 일시정지(명령 2, 최대 10분), 동시 입장 목표의 수동 고정(명령 1, FR-037의 15분 유예), 자동 제어 긴급 정지(명령 11), AIMD가 낮춘 현재 목표를 어디에 두는지 문서에 없다. 리더 메모리에만 있으면 리더가 바뀔 때 일시정지가 풀리거나 낮춘 목표가 초기값(5,000명)으로 돌아간다.
- **장애 전환으로 1인 1순번 선점 키가 사라지면 같은 사람이 대기표를 두 장 가진다.** 대기열 Redis는 비동기 복제다(복제 지연 수백 ms 이내, docs/infra.md §6). 선점 키 `q:dup:{pid}:E`가 복제되기 전에 장애 전환이 일어나면 같은 사람의 다른 탭·기기 요청이 새 세대에서 순번을 하나 더 받는다. 입장 확정은 대기표 서명·세대·serving·빠진 번호·15분만 보고 사람별 중복을 다시 보지 않아(queue-admission §6) 두 대기표로 두 번 입장할 수 있다. POL-002는 1인 1순번을 어긴 번호를 무효화한다고 하지만 이 경우를 찾는 단계가 없었다.
- **원문 확인(2026-10-13)**: 쿠버네티스 API 문서는 Lease의 `leaseTransitions`를 '보유자가 바뀐 횟수'로 정의하고, client-go는 보유자가 바뀔 때 이 값에 1을 더해 저장한다. Lease 갱신은 쿠버네티스 API의 낙관적 동시성(resourceVersion)을 따르므로 같은 판에서 한 후보만 성공한다. Redis 문서는 `WAIT`가 Redis를 강한 일관성 저장소로 만들지 않으며 동기 복제한 쓰기도 장애 전환에서 잃을 수 있다고 적는다. ASVS 5.0 2.3.2(L2)는 문서화한 업무 한도를 구현하라고, 2.3.4(L2)는 한정 자원의 이중 예약을 업무 수준 잠금으로 막으라고 한다.

## 검토한 대안

| 대안 | 문제 |
| --- | --- |
| 1. 지금처럼 쓰기 직전 Lease 재확인만 | 확인 뒤 멈춘 옛 리더의 쓰기를 막지 못한다 |
| 2. 리더 선출을 Redis 락으로 바꿈 | 선출 방식을 바꿔도 쓰는 쪽이 세대를 확인하지 않으면 같은 틈이 남는다. Lease는 이미 쓰고 있고 세대 값(`leaseTransitions`)도 준다 |
| 3. 선점 키를 `WAIT`로 복제본까지 쓴 뒤 대기표 발급 | 진입 피크(초당 20만 건) 경로의 요청마다 복제 응답을 기다린다. Redis 문서도 장애 전환에서 잃을 수 있다고 한다 |
| 4. 입장 확정 때 PostgreSQL로 사람별 중복 확인 | 대기열 경로에 DB를 넣지 않는다는 원칙과 어긋난다(ADR-0005, ADR-0008) |
| **5. 리더 세대 펜싱과 입장 확정 때 사람별 입장 키(채택)** | 리더 쓰기마다 Lua 하나, 입장 확정마다(초당 약 28건) Redis 키 하나가 는다 |

## 결정

1. **리더 세대(펜싱 토큰).** admission-ctrl은 Lease를 얻을 때 `leaseTransitions`를 1 올려 저장하고, 그 값을 리더 세대로 쓴다. Lease를 갱신하는 동안 세대는 그대로다. 쓰는 Node 구현이 이 값을 올리지 않으면 직접 올린다.
2. **세대를 확인하고 쓴다.** 회차마다 `q:{event:E}:leader`(가장 큰 리더 세대)를 둔다. 리더가 대기열 Redis에 쓰는 일은 모두 Lua 하나에서 '내 세대가 저장된 세대보다 작으면 아무것도 쓰지 않고 `FENCED`를 돌려주고, 아니면 저장된 세대를 내 세대로 올린 뒤 쓴다'로 한다. 대상은 serving 전진, 묶음 셔플 뒤 순번 카운터 전진, 리더 상태 기록(결정 4)이다. 이 키들은 `{event:E}` 해시 태그를 같이 써서 한 Lua에서 다룬다. 회차와 무관한 상태(자동 제어 긴급 정지)는 `q:{admission}:leader`와 `q:{admission}:ctl`에 같은 방식으로 둔다. 셔플 결과(`q:lobby:{hash}`)는 공시한 시드로 정해진 같은 값이라 두 번 써도 결과가 같으므로 세대 확인에서 뺀다.
3. **리더 교체 순서.** 새 리더는 Lease를 얻으면 진행 중인 회차마다 세대부터 올리고, 리더 상태를 읽은 뒤 루프와 명령 처리를 시작한다. `FENCED`를 받은 파드는 곧바로 루프와 명령 처리를 멈추고 리더 라벨을 내린 뒤 대기 파드로 돌아간다. 갱신 기한 안에 Lease를 갱신하지 못한 리더도 쓰기를 멈추고, 종료 신호를 받은 리더는 쓰기를 멈춘 뒤 Lease를 놓는다. 묶음 셔플 뒤 카운터 전진은 묶음 번호마다 한 번만 한다(`q:{event:E}:batch_done`에 `HSETNX`로 묶음 번호를 남기는 일과 전진을 같은 Lua에서).
4. **리더 상태는 Redis에 둔다.** 운영자가 정한 동시 입장 목표와 수동 고정 만료 시각, 입장 일시정지와 만료 시각, AIMD가 정한 현재 목표는 회차별 `q:{event:E}:ctl` 해시에, 자동 제어 긴급 정지는 `q:{admission}:ctl`에 세대 확인 쓰기로 둔다. 새 리더는 이 값으로 시작하므로 리더 교체로 일시정지가 풀리거나 낮춘 목표가 초기값으로 돌아가지 않는다. 명령의 ack는 이 기록을 마친 뒤 보낸다. `FENCED`로 기록하지 못한 명령은 ack가 없으므로 ops-svc가 새 리더에게 다시 보낸다.
5. **입장 확정 때 1인 1순번을 다시 확인한다.** 회차마다 사람별 입장 키 `q:adm:{pid}:E`(값: 입장한 대기표 또는 참가 토큰의 해시)를 둔다. queue-svc는 대기표 서명·세대·serving·빠진 번호·15분을 확인한 다음, 입장 자리를 잡기 전에 Lua 하나로 '키가 비었으면 이 대기표로 채우고 통과, 같은 대기표면 통과(입장 자리가 회수된 뒤 같은 대기표로 다시 입장), 다른 대기표면 409 `DUPLICATE_ADMISSION`으로 거절'한다. 거절한 대기표의 번호는 빠진 번호 비트맵에 '1인 1순번 위반 무효화'(POL-002)로 기록하고 보안 이벤트로 남긴다. 키 수명은 `q:dup`과 같다(온세일 윈도우가 끝나면 TTL로 지우고, 탈퇴 계정 키는 5일 안에 지운다).
   - 먼저 입장 확정한 대기표가 남는다. 장애 전환 뒤 받은 번호는 카운터를 건너뛴 뒤라 이전 번호보다 뒤이므로 보통 먼저 받은 앞 번호가 남는다.
   - 브라우저는 409를 받으면 이 대기표가 무효라고 알리고 이미 입장한 기기나 탭에서 계속하라고 안내한다(SCR-008).
6. **지표와 시험.** 세대 확인으로 거절된 쓰기 수를 루프 지표에, 입장 확정 재확인으로 거절된 수를 입장 지표에 더한다. 새 경보는 두지 않는다. 시험은 Q-T30(옛 리더 펜싱과 리더 상태 이어받기)과 Q-T31(장애 전환으로 생긴 대기표 두 장의 입장)이다(queue-admission §11).

## 결과

- 리더가 둘이 되는 순간이 생겨도 serving과 묶음 카운터는 현재 세대의 리더만 바꾼다. 리더가 바뀌어도 운영자의 입장 일시정지, 수동 고정, 낮춘 목표가 이어진다.
- 장애 전환으로 대기표를 두 장 받은 사람도 입장은 한 번만 한다. 나머지 번호는 빠진 번호가 되어 뒤 대기자의 앞 인원에서 빠진다.
- **남는 한계**:
  - 대기열 Redis 장애 전환이 리더 교체와 겹쳐 새 세대 기록이 복제되기 전에 사라지면, 새 리더가 다시 쓸 때(다음 주기, 200ms 안)까지 옛 리더의 쓰기가 한 번 들어갈 수 있다. 그 몫은 주기당 전진 상한 안이고 실제 입장은 입장 자리 수가 묶는다.
  - Lease 객체를 지우고 다시 만들면 `leaseTransitions`가 0부터 시작해 새 리더의 세대가 저장된 세대보다 작아지고 모든 쓰기가 거절된다. 온세일 윈도우와 변경 동결 창에는 Lease를 지우지 않고, 다시 만들었으면 진행 중인 회차의 `q:{event:E}:leader`를 지운 뒤 리더를 띄운다(docs/infra.md §8).
  - 사람별 입장 키도 대기열 Redis에 있어, 첫 입장 확정과 두 번째 대기표의 입장 사이에 다른 장애 전환이 그 키를 지우면 막지 못한다(장애 전환 두 번이 겹칠 때).
  - 두 번째 대기표는 차례가 와서 거절될 때까지 번호를 차지하므로, 그 사이 뒤 대기자의 앞 인원이 1명 많게 보인다.
- **대가**: 리더 쓰기마다 Lua와 세대 키, 입장 확정마다 Redis 키 하나가 는다. Lease를 다시 만드는 절차에 규칙이 하나 생긴다. WBS 2.3.1 +0.5일(세대 펜싱, 교체 순서, 리더 상태, Q-T30), 2.3.3 +0.5일(사람별 입장 키, 409와 빠진 번호, Q-T31). 합계 276.5일.

## Well-Architected 기둥

| 기둥 | 영향 |
| --- | --- |
| 안정성 | 리더가 겹치는 순간과 리더 교체 뒤에도 serving·카운터·운영 상태가 하나로 유지된다 |
| 보안 | 장애 전환 틈으로 한 사람이 두 번 입장하는 길을 막는다(ASVS 2.3.2·2.3.4, 15.4.2) |
| 운영 우수성 | 거절된 쓰기와 거절된 입장을 세어 장애 뒤 확인할 수 있다 |
| 성능 효율 | 입장 확정(초당 약 28건)에 Redis 왕복 하나가 는다. 진입 피크 경로(초당 20만 건)는 바뀌지 않는다 |
