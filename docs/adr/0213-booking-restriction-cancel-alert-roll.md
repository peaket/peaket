# ADR-0213: 예매 버튼·대기실의 예매 제한, 매진 화면의 취소표 알림, 앞 인원 숫자 굴림을 잇는 데 필요한 빈칸을 채우고 선예매·판매 정책 표시는 나눈다

- **상태**: 채택(2026-11-05, 추천 적용). BUILD_ORDER HOT-344.
- **관련**: [docs/design/d5-screen-blueprint.md](../design/d5-screen-blueprint.md) §5.2 ⑦ 상태 표(예매 제한·판매 정책 자격 없음·선예매 대상)·§5.8 '예매 제한'·§5.18 SCR-018·§5.24 SCR-042·§1.6 18번, [docs/frontend.md](../frontend.md) §3.4·§4.1, [docs/features/notify.md](../features/notify.md) §3, [docs/features/queue-admission.md](../features/queue-admission.md) §6, openapi `getMyBookingRestriction`·`createAppeal`·`createEventSubscription`·`listSubscriptions`, ADR-0060 D6, ADR-0062 결정 37·52, ADR-0161, ADR-0207 결정 4·12, ADR-0211 결정 1
- **관련 ID**: SCR-002, SCR-008, SCR-018, Q-T59, N-T10, FE-T18

## 맥락

- HOT-342(ADR-0211 결정 1)가 공연 상세 예매 버튼의 예매 제한·선예매·판매 정책, 대기실 예매 제한 화면의 ( 소명하기 › ), 매진 화면의 [취소표 알림 받기], 앞 인원 숫자 굴림을 이 단계로 넘겼다.
- 정본을 모아 읽으니 빈칸이 있었다.
  - 선예매·판매 정책: 팬별 자격을 주는 계약이 없다. 공연 공개 요약에는 `PRESALE` 배지뿐이고, 선예매 창·일반 예매 시작 시각·단계별 1인 한도는 판매 정책(HOT-250)이 공개 값으로 더하기로 넘겨져 있다. 진입·로비에서 판매 자격 명단에 없다는 응답(Q-T36 '제한 안내')의 문제 유형도 없다. 한 회차에 판매 단계가 둘 이상일 때의 오픈은 K25로 아직 정하지 않았다.
  - 예매 제한: 다른 개인 상태(로그인·가입·본인확인)와의 차례, 소명 기한이 지난 경우, 조회가 실패한 경우가 없다.
  - 소명 링크: SCR-042 주소의 `[id]`는 소명 건인데, 제출 전에는 소명 건이 없고 `POST /v1/appeals` 201에도 ID가 없다(소명 건 조회 경로는 d5 §1.6 18번으로 남아 있다). 대기실의 입장 확정 403 `booking-restricted`에는 제한 ID가 없다.
  - 취소표 알림: 처음 그릴 때 이미 신청했는지 보는지, 비로그인·422·429·410 때의 화면, 밤 웹 푸시를 묻는지가 없다.
  - 숫자 굴림: 길이는 base(200ms)지만 곡선·방향·자릿수가 바뀔 때의 규칙이 없다. 움직임 줄이기 설정에서 d5 §5.8은 '바로 바꾼다', d1·d3·d4는 일반 규칙으로 '불투명도 전환'이라 어긋나 보인다.
  - docs/frontend.md §3.4 상태 표에 `restricted` 행이 없다.

## 결정

1. **나눔**: 선예매 대상·판매 정책 자격 없음 표시와 공연 상세의 매진 상태([취소표 알림 받기]·다른 회차)는 새 단계 HOT-346으로 나눈다. HOT-346은 판매 정책 공개 값(HOT-250)과 실시간 매진 출처(HOT-010) 뒤에 한다. HOT-250에는 팬별 자격(명단 대상 여부·자기 단계의 시작 시각·1인 한도)과 진입·로비의 명단 밖 문제 유형을 계약에 더하는 일을 넘긴다. 이 단계는 예매 제한·소명 링크·SCR-018 취소표 알림·숫자 굴림만 한다.
2. **공연 상세의 예매 제한(SCR-002 ⑦)**
   - 팬 세션이 회원(로그인)일 때만 `GET /v1/booking-restrictions/me`를 문서마다 한 번 부른다(api-client는 늦게 가져온다, 저장하지 않는다). 비로그인은 부르지 않는다. 401·연결 실패·5xx는 '제한 없음'으로 본다(이 값은 화면용 사본이라 늦을 수 있고, 집행은 입장 확정 403이 한다, queue-admission §6).
   - 차례: 로그인 필요 → **예매 제한** → 가입 마무리 → 본인확인 → 시각 상태. 제한된 팬은 가입·본인확인을 해도 예매하지 못하므로 제한을 먼저 보인다. 판매 종료·취소 회차는 제한보다 앞선다(살 수 있는 때가 없다).
   - 받는 동안은 로그인 상태를 받는 동안처럼, 들어갈 수 있는 때(로비 버튼 차례 기다림·로비·대기열)만 ⑦을 뼈대로 둔다. 로비 열리기 전·선착순 오픈 전은 지금 버튼을 두고 답이 오면 바꾼다(버튼이 뼈대로 깜빡이지 않게). 3초 [가정] 안에 답이 없으면 '제한 없음'으로 본다(늦은 답이 오면 그때 바꾼다).
   - 끝 시각(`endsAt`)이 지난 제한은 풀린 것으로 본다. 문서마다 한 번만 받으므로, 끝 시각 전에 연 화면도 오픈 시각에 상태를 다시 고를 때 버튼이 돌아온다.
   - 이 가게는 불러오기만 해도 만들어지므로 entities 묶음 입구에서 내보내지 않고 공연 상세만 가져온다(다른 화면의 첫 JS에 싣지 않는다).
   - 모양: d5 '예매 제한 중' 줄대로 ⑦ 자리에 버튼 대신 글 "예매가 제한되어 있습니다 · 소명 기한 M/D"와 ( 소명하기 › )를 둔다(판매 종료 줄과 같은 모양). 소명 기한이 지났으면 링크 없이 "예매가 제한되어 있습니다"이고, 끝이 정해졌으면 " · M/D까지"를 붙인다. 오픈 알림 토글은 두지 않는다.
   - 사전 사람 확인 카드(CMP-047)는 제한된 팬에게 보이지 않는다(받아도 입장 확정이 막는다).
3. **소명 링크의 주소**: ( 소명하기 › )는 `/my/appeals/{restrictionId}`(SCR-042)다. 예매 제한의 소명 건은 제한 하나에 하나라, 소명 건 조회 경로가 정해지기 전까지 SCR-042의 주소 id를 그 제한 ID로 본다. 제출(`kind` RESTRICTION, 사유 `reasonCode`가 FRAUD면 FRAUD_CASE와 그 사건 ID)과 조회는 SCR-042를 잇는 단계(LCH-310)가 이 id로 한다.
4. **대기실의 예매 제한(SCR-008)**: 입장 확정 403 `booking-restricted`로 `restricted`가 되면 폴링을 멈추고, 팬 API(`GET /v1/booking-restrictions/me`, 자격 증명 포함)를 한 번 불러 제한 ID와 소명 기한을 얻는다. 소명 기한이 아직이면 ( 소명하기 › )를 SCR-042로, 그 밖(실패·NONE·기한 지남)이면 ( 공연 상세 › )를 보인다. 대기표는 지우지 않는다(d5 §5.8). 제한 ID는 화면을 그린 뒤에 오므로 링크만 제자리에서 바꾼다(화면을 다시 그리면 같은 안내를 두 번 읽는다).
5. **매진 화면의 [취소표 알림 받기](SCR-018)**
   - 판매 종료 전 매진에서만 보인다. 처음 그릴 때 `GET /v1/subscriptions?eventIds={eventId}`로 이미 신청했는지 본다. 살아 있는 취소표 신청(`cancellationStatus` ACTIVE)이면 "알림 신청됨"이고, 판매 종료로 끝난 신청(`endReason` SALE_ENDED)이면 버튼을 숨긴다. 끝난 신청(SENT_MAX·BOOKED)은 다시 신청할 수 있다(200이 되살린다). 조회가 실패하거나 비로그인이면 버튼을 그대로 둔다.
   - 누르면 `POST /v1/events/{eventId}/subscriptions` `{kind: CANCELLATION, nightPush}`를 한 번 보낸다(자동으로 다시 보내지 않는다, §4.1). `nightPush`는 처음 확인한 신청의 값이고 없으면 false다(이미 있으면 서버가 nightPush만 바꾸므로, 다시 신청이 SCR-054에서 켠 '밤에도 받기'를 끄지 않게). 상태 확인과 신청 모두 401이면 토큰을 한 번 갱신하고 다시 보낸다(§4.1 '401'). 밤 웹 푸시는 묻지 않는다. 웹 푸시 구독 경로가 아직 없고(GAT-250), 이메일은 늘 간다(notify §7.2). '밤에도 받기'는 관심 공연·알림(SCR-054)에서 바꾼다.
   - 응답: 201·200 → "알림 신청됨" + ( 관심 공연·알림에서 보기 › ). 401 → 로그인 화면(돌아올 곳은 이 주소). 410 `sale-ended` → 버튼을 숨기고 "판매가 끝나 알림을 신청할 수 없습니다". 422 `subscription-limit` → 버튼 자리에 "신청한 알림이 너무 많아 더 신청할 수 없습니다. 관심 공연·알림에서 정리해 주세요" + ( 관심 공연·알림 › ). 429·5xx·연결 실패 → 토스트 "알림을 신청하지 못했습니다"(동작 버튼 없음)와 버튼 자리의 [다시 시도](d5 §5.18).
   - 대기실에서는 신청을 끄지 않는다(SCR-054가 끈다). '알림 신청됨'은 버튼 모양의 표시이고 누를 것이 없다.
   - 신청 상태와 보내는 중인 신청은 페이지에 하나다. 공연 요약이 늦게 와 화면을 다시 그려도 이어받는다. 결과는 늘 있는 낭독 영역 하나가 알리고, 실패의 [다시 시도]에는 까닭 글을 잇는다.
6. **앞 인원 숫자 굴림(SCR-008 ①)**
   - 바뀐 자리만 굴린다. 새 글자가 위에서 내려오고 앞 글자가 아래로 빠진다. 길이 base(200ms), 곡선 enter(`cubic-bezier(0, 0, .15, 1)`), `transform`만 쓴다.
   - 자릿수가 바뀌면 오른쪽 끝(일의 자리)을 맞춰 견주고, 새로 생긴 자리는 빈 글자에서 굴린다. 앞 인원이 늘어나는 예외(오래된 파일이 10초 넘게 이어질 때, d5 §5.8)도 같은 방식으로 굴린다.
   - 처음 그릴 때는 굴리지 않는다. 화면 낭독기는 숨긴 글(`3,214명`) 하나를 읽고, 굴리는 숫자는 `aria-hidden`이다(낭독은 1분 문장 하나, ADR-0063).
   - 움직임 줄이기 설정과 저전력(배터리 15% 이하)에서는 효과 없이 새 값만 보인다. d1·d3·d4의 '불투명도 전환'은 화면 전환·나타남의 일반 규칙이고, 이 숫자는 d5 §5.8의 요소별 규칙('바로 바꾼다')을 따른다. 깜빡이는 숫자가 정확한 값을 읽기 어렵게 하기 때문이다.
7. **docs/frontend.md §3.4**: `restricted` 행을 더한다(입장 확정 403 `booking-restricted` → 폴링 멈춤, 소명 링크, 대기표 유지).

## 결과

- 제한된 팬은 공연 상세에서 미리 알고 소명 화면으로 가며, 대기실에서 막혀도 소명으로 이어진다. 매진 화면에서 취소표 알림을 신청한다. 앞 인원 숫자가 정본 모션으로 바뀐다.
- 남는 한계: 화면용 사본이 늦으면 공연 상세는 '제한 없음'을 보인 뒤 입장 확정에서 막힌다(queue-admission §6). SCR-042가 아직 목업이라 ( 소명하기 › )로 간 화면은 LCH-310 전까지 데모 값이다. 선예매·판매 정책 표시는 HOT-346 전까지 없다(진입·입장 확정이 막는다).

## 다른 선택지

- 선예매 자격을 공개 요약의 `PRESALE` 배지와 `openAt`으로 짐작해 그리기: 대상이 아닌 팬에게 '대상입니다'를 보일 수 있고(1원칙 공정·정확성), 일반 예매 시작 시각의 출처가 없다. 그래서 나눴다.
- SCR-042 주소를 `/my/appeals/new?target=`처럼 새로 만들기: 화면 경로가 하나 늘고, 소명 건 조회가 정해지면 다시 바꿔야 한다. 제한 하나에 소명 건 하나라 제한 ID로 충분하다.
- 대기실의 403에 제한 ID를 싣기(계약 바꾸기): 입장 확정은 T=0에 몰리는 경로라 응답을 늘리지 않고, 이 화면은 드물게 열려 팬 API 한 번으로 충분하다.
