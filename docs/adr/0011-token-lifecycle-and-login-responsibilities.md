# ADR-0011: 토큰 수명주기 — 액세스 토큰은 자체 포함, 입장 토큰은 구매 세션 전용, 세션 종료는 이벤트로 전파

- **상태**: 채택 (2026-10-08). 같은 이메일 계정의 연결·병합은 ADR-0038(2026-10-10)이 보완한다. ADR-0050(2026-10-13)이 결정 6(페이로드 암호화 키)을 구매 세션 요청 인증(소지 증명)으로 대체하고, 결정 1의 한 서명 키를 팬·관리·현장 스태프 키로 나누며 `typ`·`iss`를 더한다. ADR-0053(2026-10-13)이 도착 시각 쿠키의 필드·수명·키 보관·재사용 방지를 정한다. 2026-10-15 추천 적용(ADR-0065 결정 2·11)으로 결정 4의 쿠키 이름에 접두사를 붙였다(액세스 `__Secure-peaket_at`, 리프레시 `__Secure-peaket_rt`, Auth.js `__Host-authjs.*`, 관리 계정은 파트너 `__Secure-peaket_partner_at`·운영자 `__Host-peaket_ops_at`, 관리 계정 리프레시는 파트너 `__Secure-peaket_partner_rt`·운영자 `__Host-peaket_ops_rt`와 갱신 경로, docs/features/identity.md §3, docs/security/asvs/auth.md V3) 2026-10-26(4차 점검 3부): 맥락의 ASVS 9.2.4 문장과 결정 1에 있던 깨진 글자(처음 기록할 때 백틱이 PowerShell 이스케이프로 제어 문자가 된 5곳)를 소유자 허락(ADR 본문을 고치지 않는다는 규칙의 일회성 예외, review R-102)으로 `aud`·`fan`·`ticket:buy`로 되돌렸다. 같은 괄호의 partner·ops도 `fan`과 같은 꼴로 맞췄다. 뜻은 바꾸지 않았다. 2026-10-28(ADR-0103, 소유자 승인 '추천안 동의'): 결정 2의 종료 세션 목록은 서비스 단위 소비자 그룹이 아니라 파드마다 따로(파드별 그룹 또는 직접 배정, 오프셋 커밋 없음) 모든 파티션을 읽어, 같은 서비스의 모든 파드가 받는다. 파드는 뜰 때 '지금 − 15분'의 위치부터 다시 읽어야 준비 상태가 된다(Kafka에 30초 [가정] 닿지 못하면 준비 상태로 가되 따라잡을 때까지 SEV2). 시험은 I-T48이다(docs/features/identity.md §3). 2026-10-28(기술 검토 중간-083, 소유자 승인 '추천안 동의'): 앱 서버 → identity-svc 세션 생성의 '메시 mTLS 내부 호출'은 gRPC `peaket.identity.v1.SessionService`(`CreateSession`·`EndSession`)로 정한다. 멱등 키는 로그인 시도마다 하나(로그인 진행 쿠키 state의 HMAC)이고, 같은 키로 다시 오면 같은 세션에 토큰만 다시 발급한다. 받는 쪽 웨이포인트의 허용 목록은 소비자 웹 앱 서버 신원만 들인다. 통신 표의 따로 있던 행은 gRPC 행에 합쳤다(docs/architecture.md §3.2, docs/api/proto/peaket/identity/v1/identity.proto, I-T50). 2026-10-28(ADR-0119, 소유자 승인 '추천안 동의'): 결정 5의 '소셜 OAuth 흐름은 소비자 웹의 Auth.js가'는 '소비자 웹 앱 서버의 얇은 OIDC 클라이언트(`oauth4webapi`)가'로 바꾼다. 앱 서버는 자기 세션을 두지 않아 결정 4의 Auth.js 세션 쿠키 자리는 로그인이 진행되는 10분 [가정] 동안의 진행 쿠키 `__Host-peaket_oidc` 하나가 된다. 결정 5의 파트너 콘솔 Auth.js(Credentials)는 빼고, 파트너 로그인은 관제처럼 gw-partner를 거쳐 identity의 관리 계정 로그인 API로 간다. 대안 표의 '로그인 담당' 1번 기각 이유("Next.js가 어차피 Auth.js로 콜백을 받으므로")는 Auth.js를 전제로 한 순환 근거였다. ADR-0119가 identity 콜백 안을 다시 견줘 이유를 적었다. 인증 구현 전 PoC(I-T51)에서 얇은 클라이언트가 떨어지면 Auth.js v5 고정 판으로 간다.

## 맥락

- **게이트웨이는 저장소 없이 토큰을 검증한다(ADR-0008).** 그런데 '계정·인증'은 로그아웃·탈퇴·강제 종료 때 세션을 '즉시 무효화'한다고 적었다. 자체 포함 토큰은 서명만 보므로, 아무 조치가 없으면 끝난 세션의 토큰이 남은 수명(15분) 동안 통하는 보안 허점이 생긴다.
- **ASVS 5.0.0 7.4.1(L1)은 자체 포함 토큰에 별도 해법을 요구한다.** 원문은 세션 종료 뒤 토큰을 더 쓸 수 없게 하라고 하면서, 자체 포함 토큰에는 종료 토큰 목록 유지, 사용자별 기준 시각 이전 토큰 거부, 사용자별 서명 키 교체 같은 해법이 필요하다고 명시한다([ASVS v5.0.0 V7](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x16-V7-Session-Management.md)). 9.2.4(L2)는 같은 키로 여러 대상에 토큰을 발급하면 대상(`aud`)을 넣으라고 규정한다([V9](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x18-V9-Self-contained-Tokens.md)).
- **입장 토큰은 '1회용·5분'으로 적혀 있었지만, 게이트웨이는 구매 요청마다 이 토큰을 확인한다.** 한 번 쓰면 재사용 차단에 걸리고, 5분이 지나면 결제창(30분)이 열려 있어도 홀드·결제·WebSocket 재연결이 게이트웨이에서 막힌다.
- **로그인을 누가 하는지 문서마다 달랐다.** 서비스 맵은 identity-svc가 OAuth를 한다고 했고, 비밀 목록과 ASVS 추적 표는 Next.js의 Auth.js(web BFF)가 OAuth 비밀을 갖고 ID 토큰을 검증한다고 했다. 게이트웨이가 읽는 액세스 토큰 쿠키와 Auth.js가 암호화한 쿠키의 관계도 정해져 있지 않았다.
- **페이로드 암호화 키를 '세션마다 생성해 메모리에만' 두면** 다음 요청이 다른 purchase-svc 파드로 갈 때 키가 없다.
- **1인 1순번 중복 확인 키는 연계정보 기준인데, 진입 경로에서 queue-svc가 연계정보를 알 방법이 없었다.** identity를 부르면 진입 경로에 조회가 생기고(ADR-0006 결정 3 위반), 연계정보 HMAC을 토큰에 그대로 넣으면 저장값과 맞춰 볼 수 있는 값이 브라우저 쿠키에 남는다.

## 결정

1. **액세스 토큰은 ES256 자체 포함 토큰(15분)으로 발행한다.** 클레임은 사용자 ID(sub), 세션 ID(sid), 권한(scope: `ticket:buy` 등), 사람 식별값(pid: 본인확인을 마친 계정만. 연계정보 HMAC을 별도 KMS HMAC 키로 다시 해시한 값이라 토큰만으로는 저장된 연계정보 HMAC과 맞춰 볼 수 없고, queue-svc가 1인 1순번 중복 확인 키로 씀), 대상(`aud`: `fan`·`partner`·`ops`), 키 ID(kid)이다. 게이트웨이는 서명·만료·`aud`·경로 권한만 무상태로 확인하고, 검증한 클레임(사용자 ID·세션 ID·권한·pid)을 내부 헤더로 넘긴다. 서비스는 토큰을 다시 검증하지 않고 이 헤더만 본다(메시 mTLS로 게이트웨이와 내부 신원만 이 헤더를 넣을 수 있음). 같은 서명 키로 세 대상에 발급하므로 `aud`를 경로별로 대조한다(ASVS 9.2.4).
2. **세션 종료는 이벤트로 전파한다.** identity는 로그아웃, 탈퇴, 관리자 강제 종료, 리프레시 토큰 재사용 탐지 때 '세션 종료' 이벤트(사용자 ID 키)를 제어·보안 이벤트 토픽(설계서 섹션 8)으로 보낸다. 각 서비스는 게이트웨이 헤더의 sid를 플랫폼 라이브러리의 종료 세션 목록(메모리, 액세스 토큰 수명인 15분 동안 보관)과 대조해 거부한다. 리프레시는 identity가 세션 존재를 확인하므로 즉시 끊긴다. 게이트웨이는 무상태로 둔다.
3. **입장 토큰은 한 구매 세션 전용이다.** 만료는 최대 체류 시각(ADR-0005 결정 7)과 같고, 발급 후 5분 안에 처음 써야 한다(첫 사용 기한). purchase-svc는 첫 사용 때(보통 입장 직후의 좌석 스냅샷 요청) jti를 SET NX로 기록하면서 구매 세션을 만들고 jti·세션·기기를 묶은 뒤, '구매 세션 시작' 이벤트를 보내 queue-svc가 입장 자리의 만료를 첫 사용 기한에서 최대 체류 시각으로 늘리게 한다(ADR-0005 결정 7). 이후 요청은 jti가 같은 세션에 묶여 있는지만 확인하고, 다른 기기·세션에서 같은 토큰이 오면 거부한다. 게이트웨이는 요청마다 서명·만료만 확인하고, 읽기 전용인 realtime-gw(WebSocket)는 게이트웨이의 확인만 신뢰한다.
4. **브라우저 쿠키는 세 개이다.**

   | 쿠키 | 내용 | 읽는 곳 | 수명 |
   | --- | --- | --- | --- |
   | Auth.js 세션 쿠키 | Auth.js가 암호화한 로그인 상태(OAuth 흐름의 state·PKCE 포함). 관제 콘솔에는 없음 | Next.js 서버(web·partner BFF)만 | Auth.js 설정값 |
   | 액세스 토큰 쿠키 | 위 1번의 JWT | 게이트웨이, Next.js 서버(사용자 대신 내부 API를 호출할 때 첨부) | 15분 |
   | 리프레시 토큰 쿠키 | 참조 토큰(원문은 쿠키에만, identity에는 해시). 경로를 토큰 갱신 엔드포인트로 제한 | identity(갱신·회전·재사용 탐지) | 세션 정책의 절대·유휴 만료 |

5. **소셜 OAuth 흐름은 소비자 웹의 Auth.js가, 계정·세션·토큰은 identity가 맡는다.** Auth.js가 제공자와 인가 코드를 교환하고(PKCE·state·nonce) ID 토큰을 검증한 뒤, 제공자 식별자를 identity로 보내 PEAKET 세션과 토큰을 받는다. 이 세션 생성 호출은 아무나 부르면 안 되는 서버 간 호출이라 외부 게이트웨이를 거치지 않고, 클러스터 안의 Next.js 서버가 메시 mTLS로 identity의 내부 엔드포인트를 부르며 identity는 메시 신원이 web·partner BFF일 때만 받는다. 제공자 토큰은 identity에 가지 않고 로그인 처리 후 버린다. OAuth 클라이언트 시크릿은 앱 서버에만 있다. 파트너 콘솔은 Auth.js(Credentials)가 이메일·비밀번호·TOTP 입력을 받아 같은 내부 경로로 identity에 검증을 맡기고, 관제 콘솔은 Next.js 서버가 없는 Module Federation 앱이라 로그인 화면이 gw-ops(허용 IP·VPN)를 거쳐 identity의 관리 계정 로그인 엔드포인트를 직접 부른다. 어느 경우든 비밀번호·TOTP 검증과 토큰 발급은 identity가 수행한다.
6. **페이로드 암호화 키는 파드와 무관하게 다시 계산할 수 있게 한다.** 서버 ECDH 키는 고정이고(Secrets Manager, kid) 공개키는 입장 때 클라이언트에 준다. 클라이언트는 임시 키쌍을 만들어 공개키를 첫 요청에 실어 보내고, purchase-svc는 이를 구매 세션에 저장한다. 구매 세션 키는 HKDF(공유 비밀, 세션 ID)로 만들므로 어느 파드에서든 같다.

   | 대기표 | queue-svc | HMAC(세대 번호 포함) | 차례 후 15분 유예까지 | queue-svc | 만료, 빠진 번호 표시 |
   | 입장 토큰 | queue-svc | ES256 | 최대 체류 시각(첫 사용 기한 5분) | 게이트웨이(서명·만료), purchase-svc(jti·세션 묶음) | 구매 세션 종료 |
   | 도착 시각 쿠키(Degraded Mode) | 엣지 함수 | HMAC | 수 분 | queue-svc | 만료 |

## 결과

- **로그아웃·탈퇴·강제 종료가 액세스 토큰에도 수 초 안에 반영되고, 게이트웨이는 그대로 무상태이다.**
- **입장 토큰 하나로 결제창이 열려 있는 동안의 모든 구매 요청을 처리한다.**
- **1인 1순번 중복 확인에 identity 조회가 필요 없고(pid), 연계정보 HMAC 저장값은 토큰에 실리지 않는다.**
- **ASVS 추적 표의 V9(자체 포함 토큰)를 '해당 없음'에서 '적용'으로 다시 판정한다.**
- **대가: 서비스마다 종료 세션 목록을 유지하고, 이벤트 전파 지연(초 단위) 동안은 끝난 세션의 토큰이 통할 수 있다.** 이 지연을 측정해 성능 장부에 남긴다.
- **대가: 구매 세션에 클라이언트 임시 공개키를 저장하므로 구매 세션 항목이 하나 늘어난다.**

## Well-Architected 기둥

| 기둥 | 영향 |
| --- | --- |
| 보안 | 세션 종료가 토큰에 반영되고, 대상 제한으로 토큰 혼용을 막음. 비밀은 발급 주체에만 있음 |
| 안정성 | 게이트웨이가 저장소에 의존하지 않아 진입 경로가 Redis 장애와 분리됨 |
| 성능 효율성 | 진입·구매 경로에 토큰 검증 외의 조회가 없음 |

## 재검토 조건

- 세션 종료 전파 지연이 보안 요구(관리자 강제 종료 즉시 반영)를 만족하지 못할 때: 관리 계정 토큰만 참조 토큰으로 바꾸는 방안을 검토한다.
- 구매 세션 전용 입장 토큰의 재사용 차단이 다중 기기 어뷰징을 막지 못한 사례가 나올 때
