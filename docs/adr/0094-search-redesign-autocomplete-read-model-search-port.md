# ADR-0094: 검색을 다시 설계한다 — 입력 중 후보는 '자동완성', 결과는 DB 읽기 모델, 자동완성은 서버 메모리 사전, 검색 엔진은 검색 포트 뒤에 두고 바꿀 조건을 정한다(2026-10-27)

- **상태**: 채택 (2026-10-27. 소유자가 "검색 기능이 어떻게 설계되어있는지 봐주세요. 연관검색어 기능이나, 자동완성, 검색결과 기능등이 실무 시니어 개발자 수준으로 고려를 하고 개발을 해야해요."라고 요청했다. 검토 보고와 Elasticsearch·Algolia 비교 답을 본 뒤 "검색 엔진은 안 B로 두고, 검색 포트와 바꿀 조건까지 넣어 지난번 제안 네 가지를 반영해 주세요."라고 했다. 이름 나눔(결정 1), 검색 기록으로 만드는 연관 검색어를 지금 두지 않고 관련 공연만 두기(결정 2), 안 B(결정 3), 검색 포트와 바꿀 조건(결정 4)은 소유자 결정(승인 2026-10-27, '추천대로')이다. 네 제안 가운데 남은 하나인 공연 엔터티는 ADR-0093이다. 결정 4의 수치와 결정 5~13의 세부는 추천 적용(2026-10-27)이다. 추천 적용은 소유자가 방향을 승인하고 세부를 맡긴 부분에서 제안해 적용한 것으로, 바꾸고 싶으면 언제든 바꾼다.) 2026-10-28(기술 검토 높음-25, 소유자 승인 '추천안 동의'): 결정 6의 정규화 첫 단계를 'NFKC 뒤 첫소리·가운뎃소리·끝소리 자모(U+1100~U+11FF)를 호환 자모로 되돌리기(고정 표)'로 바로잡는다. NFKC가 입력기의 호환 자모('ㄹ' U+3139)를 첫소리 자모(U+1105)로 바꿔, es-hangul이 초성만 친 입력을 초성으로 보지 않고 낱자만 친 입력이 낱자 키와 맞지 않았다. 보이지 않는 한글 채움 문자도 지우고, '초성만'은 정규화한 입력을 낱자로 푼 값으로 판정한다(겹자음 'ㄳ'은 'ㄱㅅ'). 검색의 방향(결정 1~4)은 그대로다(docs/features/search.md §3.1·§3.2·§12·§15, docs/data.md §2). 2026-10-28(기술 검토 중간-089, 소유자 승인 '추천안 동의'): 결정 5의 증분 갱신('그 판 뒤에 바뀐 줄만 다시 읽기')은 지운 줄을 알 수 없어, 오래 뜬 파드가 빠진 공연·지운 별칭을 계속 후보로 낼 수 있었다. 그래서 읽기 모델에서 줄을 지우는 트랜잭션이 지운 표시 표 `search_removal`(종류, 대상 ID, 판)을 함께 쓰고, 사전은 판·바뀐 줄·지운 표시를 같은 읽기 전용 복제본의 한 읽기 전용 트랜잭션에서 판을 먼저 읽는다. 지운 표시는 하루 [가정] 뒤 지우고, 마지막 갱신이 1시간 [가정]보다 오래된 파드는 통째로 읽는다. 판 지연 게이지가 잡지 못하는 어긋남은 사전 항목 수와 DB 행 수의 차이 게이지로 본다. 결정 5의 '자동완성 사전은 다음 판 확인 때 빠진다'가 이 장치로 지켜진다(docs/features/search.md §2.2·§2.3·§10·§12·§13, docs/data.md §2·§5.1, SR-T15). 2026-10-28(기술 검토 낮음-173, 소유자 승인 '추천안 동의'): 결정 2가 '검색어에 이름·전화번호 같은 개인정보가 섞일 수 있다'며 검색 기록 기능을 뺐는데, 검색 원본은 정규화한 검색어를 로그 줄 `search_query`에 그대로 남기고 운영자가 0건 검색어 상위 50개를 보았다. 그래서 줄을 남기기 전에 이메일 꼴은 `[이메일]`, 전화번호 꼴은 `[전화]`, 이어진 숫자 5자리 이상은 `[숫자]`로 가리고(검색 자체는 가리기 전 값으로 한다), 0건 목록에는 그 주에 서로 다른 요청으로 5번 [가정] 이상 나온 검색어만 올린다. 시험은 SR-T17이다. CDN·게이트웨이 접근 로그의 쿼리는 원래 값으로 남고 접속기록 기준을 따른다(docs/features/search.md §11, docs/security/data-classification.md). 2026-10-28(기술 검토 낮음-036, 소유자 승인 '추천안 동의'): 결정 7 브라우저의 '받은 후보 안에서 거르기'는 앞선 입력이 이미 두 글자(한글은 두 음절) 이상이고, 입력 종류(초성만·한글·로마자)가 그대로이며, 거른 결과가 0건이 아닐 때만 한다. 한 음절에서 두 음절로 넘어갈 때 새로 켜지는 중간 일치, 초성 비교에서 낱자 비교로의 전환, 로마자 0건 때 서버의 한/영 변환을 놓치지 않으려는 것이다. 골든 세트(SR-T12)에 입력을 한 글자씩 늘려 가는 순서 경우를 넣는다(docs/features/search.md §4.5·§12).
- **관련**: ADR-0063(검색 화면·연관 검색어 창·페이지 번호), ADR-0065(헤더 묶음·CSP), ADR-0067(국외 이전 판단 틀), ADR-0076(같은 출처 수집 경로), ADR-0081(REST 검색 규칙), ADR-0083·0086(PostgreSQL 유지, pg_trgm·pg_bigm), ADR-0093(공연·공연장·아티스트), FR-003, NFR-028, POL-043·045, [docs/features/search.md](../features/search.md), [docs/security/asvs/catalog-review.md](../security/asvs/catalog-review.md)

## 맥락

검토는 정본(FR-003, SCR-003, design/d5 §5.3, design/d2 CMP-004, openapi `/v1/search`·`/v1/search/suggestions`, docs/data.md §3·§5, docs/frontend.md §2.5, guidelines §3·§9·§11, catalog-review)과 바깥 원문으로 했다(2026-10-27).

- **있던 것**: 머리 검색창 하나, 입력 전 최근 검색어(이 기기에만), 2자부터 후보 최대 8개(공연·아티스트·공연장 구분), 0.3초 기다린 뒤 요청과 앞 요청 취소, 키보드·화면 낭독기용 combobox 규칙, 필터 4가지·정렬 3가지·페이지 번호 20개·깊은 쪽 상한, 쿠키 없는 공개 요청과 CDN 캐시, 검색어 50자 상한, 바인드 변수, 글자로만 그리기.
- **데이터의 빈틈**: 결과 한 줄이 회차였고, 공연명·아티스트 칸과 다른 이름(별칭)이 데이터에 없었다. 이는 ADR-0093으로 풀었다.
- **한글 처리의 빈틈**
  - '루멘'을 치면 입력창은 ㄹ → 루 → 룸 → 루메 → 루멘으로 바뀐다. '룸'은 글자로는 '루멘'과 맞지 않아 그 순간 후보가 0개가 된다. 유니코드 NFD로 풀어도 '룸'의 받침 ㅁ(U+11B7)과 '루멘'의 첫소리 ㅁ(U+1106)이 다른 문자라 앞부분이 맞지 않는다(계산 확인). 초성('ㄹㅁ'), 한/영 키 실수('fnaps'), 띄어쓰기('루멘콘서트') 처리도 없었다.
  - pg_trgm(3글자 조각 비교)의 함정: DB의 문자 분류 설정(LC_CTYPE)이 C면 한글을 단어 글자로 보지 않아 조각을 만들지 않는다(PostgreSQL 18 소스 `ts_locale.c`: 여러 바이트 글자도 C 설정이면 첫 바이트로만 판정). 짧은 한글 이름은 오타에 약하다. pg_trgm 계산 방식대로 세면 '루멘'과 '루맨'의 유사도는 0.2로 기본 기준 0.3에 못 미친다(pg_trgm 18 문서: 앞 공백 둘·뒤 공백 하나, 기준 0.3). 두 글자 부분 일치는 조각을 못 뽑아 인덱스 전체를 훑는다(같은 문서). 다만 데이터가 작아 속도는 문제가 아니라는 지금 문서의 판단은 맞다.
  - LIKE의 특수 문자: 검색어를 바인드 변수로 넘겨도 LIKE 안에서 `%`·`_`는 '아무 글자'로 동작한다. 이스케이프 규칙이 없었다.
- **자동완성의 빈틈**
  - 이름: 입력 중 후보 창을 '연관 검색어'라고 불렀다. 국내 포털은 이 창을 '자동완성'이라 부르고(네이버 검색어 고객센터의 '자동완성' 메뉴, 2026-10-27 확인), 보통 '연관 검색어'는 검색 뒤 보이는 '다른 사람들이 이어서 찾은 검색어'를 뜻한다.
  - 캐시가 빗나가면 키 입력마다 DB를 불렀다. 그 DB는 로그인(identity)과 같은 Aurora 공유 클러스터다(data.md §1). docs/infra.md도 이 피크를 아직 계산하지 않았다고 적었다.
  - Redis 키 `cat:suggest:{입력}`은 사람이 친 아무 글자나 키가 되어, 무작위 입력이면 끝없이 는다. 이 키는 로그인 세션·요청 한도 카운터와 같은 클러스터에 있다. ElastiCache의 기본 정리 규칙은 volatile-lru(만료 시간이 있는 키 가운데 오래 안 쓴 것부터 지운다, AWS 문서 2026-10-27 확인)라, 대기열에서 오래 기다리느라 건드리지 않은 세션이 새 키보다 먼저 지워질 수 있다.
  - CDN 캐시 키: CloudFront는 쿼리 매개변수의 순서나 대소문자만 달라도 다른 캐시로 본다(AWS 문서 2026-10-27 확인). `limit`를 1~50 아무 값이나 받으면 같은 검색이 50갈래로 쪼개진다.
  - 한글 입력기: 조합 중에 눌린 키도 keydown으로 들어온다. MDN은 `isComposing`이 참이거나 `keyCode`가 229인 keydown을 무시하라고 권한다(2026-10-27 확인). 이 규칙이 없었다.
  - 후보 순서와 일치 표시(다른 이름·낱자로 맞을 때) 규칙이 없었다.
- **결과의 빈틈**: '정확도' 순서와 동점 깨기가 없어 페이지 번호 방식에서 같은 공연이 두 번 나오거나 빠질 수 있었다. 기본 범위(끝난 공연), 날짜 필터의 뜻, 아티스트 필터가 없었다. 결과 0건 화면이 빈약했다. `/search` 화면은 요청마다 서버가 그리고 캐시를 막아, 오픈 직전 검색이 몰리면 화면 서버로 그대로 갔다. architecture는 `/search`를 검색 엔진 유입 페이지로 쓴다고 적었는데, 구글 스팸 정책은 '분명한 둘러보기 구조보다 검색 결과에 가까운 비슷한 페이지 만들기'를 도어웨이(유입용 중간 페이지) 남용의 예로 든다(2026-10-27 원문 확인).
- **재는 법의 빈틈**: 검색 응답 목표(NFR), 품질 지표, 기대 결과 묶음, 부하 분해 항목, 백엔드 검색 작업(WBS)이 없었다.
- **엔진 비교(2026-10-27 원문 확인)**
  - Elasticsearch: 2021년 SSPL·Elastic License 2.0으로 바꿨고 2024년 9월 AGPLv3을 선택지로 더했으며, 배포판은 Elastic License 2.0이다(Elastic 라이선스 FAQ). 이 라이선스의 제한은 '남에게 호스팅·관리형 서비스로 제공하는 것'이다. 한국어 분석기 nori는 mecab-ko-dic 사전으로 형태소를 나누고, 구성 요소는 토크나이저·품사 거르기·한자 읽기·숫자 정규화다. 낱자·초성 비교는 없다.
  - AWS OpenSearch Service(Apache-2.0, Nori 플러그인 1.3판부터): 권장 고가용성 구성은 Multi-AZ with Standby다(전용 마스터 3대와 데이터 3대 또는 3의 배수, 인덱스마다 복제본 2개, 99.99%). 서울 리전 가격표(2026-10-20판)로 `m6g.large.search`(시간당 0.156달러) 6대와 gp3 30GB면 월 약 687달러, 서버리스 검색 처리 단위(OCU, 6GiB 메모리와 CPU) 1개를 늘 켜 두면 월 약 214달러(시간당 0.293달러. 최소를 0으로 두면 처음 요청이 늦다), 고가용성 없는 `t3.small.search` 1대는 월 약 41달러다.
  - Algolia: 종량제(Grow)는 월 1만 건 뒤 1천 건당 0.5달러, 레코드 10만 개까지 포함이고, 서버 위치는 미국·영국·EU다. 가격표 FAQ는 '입력하면서 찾는 방식에서는 키 입력마다 요청 1건'이라고 적는다. 오타 1개 허용은 4글자 이상, 2개는 8글자 이상이 기본이고, 표의문자 언어에는 오타 허용이 없다. 한국어는 단어 나누기를 지원한다. 99.99% 가용성 약속은 연간 계약 요금제(Elevate)에 있다. 예시로 하루 1만 명이 요청 4건씩 보내면 월 약 595달러, 대형 오픈 직전 10만 명이 4건씩 보내면 그 한 번에 약 200달러다.
  - 어느 엔진을 쓰든 위 빈틈의 대부분(공연 단위, 칸·별칭, 조합 중·초성·한영, 즉시 내리기, CDN·입력기·검색 엔진 노출)은 엔진 밖이다. 검색 서버를 따로 두면 DB와 검색 서버 두 곳에 데이터를 두어, 옮기는 장치·다시 색인·건수 대조가 생기고 판매 승인 취소가 같은 트랜잭션으로 검색에서 빠지지 않는다.
  - 대상 크기: 성장 표(architecture §9.2)로 3년차 공연은 한 해 대형 48·중형 240·소형 4,500회다. 지난 공연까지 3년을 모아도 1만~2만 개 안팎이다(어림).

## 결정

1. **이름(소유자 결정).** 입력하는 동안 머리 검색창 아래에 뜨는 공연·아티스트·공연장 후보 창은 '자동완성'이다(영문 표기 `search_suggestion`, API 경로 `/v1/search/suggestions`는 그대로). 카탈로그 관계로 고른 공연 묶음은 '관련 공연'이다. '연관 검색어'는 다른 사람들이 이어서 찾은 검색어를 검색 기록으로 만드는 기능을 넣을 때 그 기능의 이름으로만 쓴다. 지금은 그 기능이 없다.
2. **연관 검색어와 인기 검색어(소유자 결정).** 검색 기록으로 만드는 연관 검색어와 인기 검색어는 지금 두지 않고 관련 공연(결정 10)을 둔다. 봇이 같은 검색을 되풀이해 조작할 수 있고, 검색어에 이름·전화번호 같은 개인정보가 섞일 수 있고, 서비스 초기에는 기록이 없기 때문이다. 요구가 생기면 최소 세션 수 기준, 봇 거르기, 운영자 차단 목록, 개인정보 거르기를 조건으로 새 ADR로 본다.
3. **엔진은 안 B다(소유자 결정).** 검색 결과는 PostgreSQL의 검색 읽기 모델(자주 읽는 값을 미리 모아 둔 사본 표)로 찾는다. 자동완성은 catalog 모듈(core-svc)의 서버 메모리 사전에서 찾는다. 검색 전용 서버(Elasticsearch·OpenSearch)와 외부 검색 서비스(Algolia)는 쓰지 않는다.
4. **검색 포트와 바꿀 조건(소유자 결정. 수치는 추천 적용).**
   - catalog 모듈 안에 검색 포트(`SearchIndex`. 검색 엔진을 바꿔 끼울 수 있게 정한 이음매)를 둔다. 하는 일은 자동완성(`suggest`), 검색(`search`), 관련 공연(`related`), 비슷한 이름 제안(`correct`) 넷이다. 지금 어댑터는 `PgSearchIndex`(검색·관련 공연)와 `MemorySuggestIndex`(자동완성·비슷한 이름)다. API와 화면은 포트만 알아서, 엔진을 바꿔도 바뀌지 않는다. 결제사 어댑터(ADR-0029·0044)와 같은 방식이다.
   - 바꿀 조건: 아래 가운데 하나가 생기면, 로컬에서 OpenSearch(+nori) 어댑터를 같은 기대 결과 묶음(골든 세트)과 부하로 비교 측정하고 그 결과로 새 ADR을 쓴다. ① 공연 설명 글이나 후기 본문까지 찾아야 한다는 요구 ② 검색 대상(공연·아티스트·공연장, 넣게 되면 굿즈)이 10만 건 [가정]을 넘음 ③ 골든 세트 정답률이 NFR-028에 못 미치고 순위 규칙 조정으로 풀리지 않음 ④ 검색 원본 응답 p95가 NFR-028을 넘고 쿼리·인덱스 조정으로 풀리지 않음.
5. **검색 대상과 갱신(추천 적용).**
   - 대상은 판매 승인된 공연(회차가 모두 취소된 공연은 뺀다)과 그 공연의 아티스트·공연장, 그리고 그 셋의 다른 이름이다. 승인 전·반려된 공연은 검색·자동완성 어디에도 나오지 않는다.
   - 읽기 모델은 두 표다. `search_document`는 공연 하나에 한 줄(카드 값, 판매 상태, 기간, 다음 오픈, 관심도)이다. `search_term`은 이름 하나에 한 줄(종류와 대상, 화면 이름, 정규화한 값, 띄어쓰기 없앤 값, 낱자, 초성, 다른 이름이면 원래 이름)이다. 카탈로그를 바꾸는 같은 트랜잭션에서 고친다. 그래서 판매 승인 취소는 검색 결과에서 바로 빠진다.
   - 자동완성 사전은 core-svc 파드(서버 실행 단위)마다 메모리에 둔다. 읽기 모델의 판(카탈로그 트랜잭션마다 올리는 번호)을 10초 [가정]마다 보고, 바뀌었으면 다시 읽는다. 공연 1~2만 개면 몇 MB다(어림).
   - 내리기: 판매 승인 취소나 회차 전부 취소로 공연이 빠지면, 같은 트랜잭션으로 읽기 모델에서 빼고 CDN의 검색 경로를 비운다(CloudFront 무효화 경로 `/v1/search*`. 끝의 `*`가 모든 검색어 변형을 덮는다, AWS 문서 확인). 자동완성 사전은 다음 판 확인 때 빠진다.
6. **한글 처리(추천 적용).**
   - 정규화 함수 하나를 브라우저와 서버가 같은 코드로 쓴다: NFKC → 소문자 → 제로폭 문자 지움 → 안쪽 연속 공백을 하나로 → 앞뒤 공백 지움. 캐시 키와 비교의 출발점이다.
   - 비교용 값: 띄어쓰기를 없앤 값, 낱자(호환 자모로 풀고 겹받침·겹모음도 푼다), 초성. 토스가 공개한 es-hangul(MIT, 2.4.0)의 `disassemble`('값' → 'ㄱㅏㅂㅅ')과 `getChoseong`을 쓴다(2026-10-27 확인). 유니코드 NFD는 받침과 첫소리를 다른 문자로 풀어 조합 중 글자가 맞지 않으므로 쓰지 않는다.
   - 입력 해석 순서: ① 정규화한 값 그대로 ② 낱자 앞부분(조합 중 '룸' → '루멘') ③ 입력이 초성만이면 초성 앞부분('ㄹㅁ' → '루멘') ④ 입력이 로마자만이고 ①~③의 결과가 0건이면 한/영 변환 값(`convertQwertyToHangul`, 'fnaps' → '루멘')으로 다시 찾고, 바꿔 찾았다고 알린다.
   - 최소 길이: 자동완성은 한글 음절이 하나라도 있으면 1자부터, 로마자·숫자·낱자만이면 2자부터 보낸다 [가정]. 최대는 50자다.
   - DB: DB를 만들 때 문자 분류 설정(LC_CTYPE)을 C·POSIX로 두지 않는다. 조각 비교 확장(pg_trgm·pg_bigm)을 쓰게 되면 한글 조각이 나오는지(`show_trgm('루멘')`이 비지 않는지) 시험한다. 오타는 질의에서 받지 않고 비슷한 이름 제안(결정 9 ②)으로 받는다.
   - LIKE: 사용자 값을 LIKE 패턴에 넣을 때 `\`·`%`·`_`를 이스케이프하고 `ESCAPE '\'`를 쓴다.
7. **자동완성(추천 적용).**
   - 후보: 이름(공연명·아티스트·공연장과 그 다른 이름)을 낱자 앞부분 일치, 낱말 앞부분 일치, 중간 일치 순으로 찾는다. 공연 후보는 기본 범위(결정 8)의 공연만, 아티스트·공연장 후보는 기본 범위의 공연이 하나 이상 있을 때만 낸다.
   - 순서: 일치 등급(정확히 같음 > 앞부분 같음 > 낱말 앞부분 > 중간 일치) → 판매 상태(판매 중·오픈 예정 > 매진) → 관심도(오픈 전 공연은 다음 오픈 회차의 오픈 알림 신청 수, 그 밖은 최근 7일 확정 판매 매수 [가정]) → 이름 가나다순 → ID. 종류별 몫은 공연 5·아티스트 2·공연장 1 [가정]이고, 빈 몫은 다른 종류로 채워 모두 8개 [가정]까지다.
   - 일치 표시: 서버가 화면 이름 위의 일치 위치(UTF-16)를 계산해 준다. 낱자나 초성으로 맞으면 그 낱자가 걸친 음절을, 다른 이름으로 맞으면 원래 이름에서 대응하는 부분(대응이 없으면 이름 전체)을 굵게 한다.
   - 캐시: Redis `cat:suggest` 키를 없앤다. CDN 60초 [가정]와 `stale-while-revalidate`만 둔다. 캐시가 빗나가도 메모리 사전이 답하므로 DB와 Redis를 부르지 않는다.
   - 브라우저: 정규화한 값으로 요청하고, 매개변수 순서를 정해 두며 기본값은 싣지 않는다. 입력이 멈추고 0.3초 [가정] 뒤 보내고, 입력이 바뀌면 앞 요청을 취소한다. 받은 후보가 8개보다 적으면, 그 입력으로 시작하는 더 긴 입력은 받은 후보 안에서 거르고 다시 요청하지 않는다.
   - 한글 입력기: keydown에서 `isComposing`이 참이거나 `keyCode`가 229면 Enter·↑↓·Esc를 처리하지 않는다. 조합 중에도 입력 값이 바뀌면 자동완성은 보낸다(결정 6 ②가 받쳐 준다).
   - 운영 원칙: 후보는 판매 승인된 카탈로그와 운영자가 확인한 다른 이름에서만 만들고, 사람들의 검색 기록으로 만들지 않는다. 국내 포털은 사생활 침해·명예훼손·개인정보 노출·욕설·자동화된 수단 같은 이유의 자동완성 제외 요청 창구를 따로 운영한다(네이버 검색어 고객센터 2026-10-27 확인). PEAKET은 후보를 기록으로 만들지 않아 그런 요청이 생길 길을 좁힌다. 다른 이름이 문제가 되면 운영자가 지우고, 다음 판 확인 때 빠진다.
8. **검색 결과(추천 적용).**
   - 한 줄은 공연이다(ADR-0093). 카드를 누르면 대표 회차 상세로 간다.
   - 기본 범위는 판매 중·오픈 예정·매진 공연이다. '지난 공연 포함'(`includePast`)을 켜면 끝난 공연도 보인다. 일부 회차만 취소된 공연은 남은 회차로 셈한다.
   - 필터: 장르, 일정(공연 기간이 고른 날짜 범위와 겹치는 공연), 예매 상태, 공연장(`placeId`), 아티스트(`artistId`, 새로 더한다).
   - 정렬: 검색어가 있으면 기본이 정확도, 없으면 오픈 임박이다. 정확도 = 일치 등급(공연명 정확 > 아티스트 정확 > 공연장 정확 > 공연명 앞부분 > 아티스트 앞부분 > 공연장 앞부분 > 중간 일치) → 판매 상태 → 관심도 → 공연 ID. 오픈 임박 = 다음 오픈 시각 → 공연 ID. 인기 = 최근 7일 확정 판매 매수(공연 합) → 공연 ID이고, 순위가 없는 공연은 뒤에 오픈 임박 순이다(POL-043과 같은 집계). 모든 정렬의 끝을 공연 ID로 두어, 쪽을 넘겨도 같은 공연이 두 번 나오거나 빠지지 않는다.
   - 쪽: 한 쪽 20개 [가정]로 고정하고 `limit`는 20만 받는다(다른 값은 400). `page × 20`은 1,000 [가정]을 넘지 않는다.
   - 개인화와 유료 노출은 없다. 같은 검색은 누구에게나 같은 결과라 CDN이 한 번만 계산하고, 배너·테마처럼 돈을 받고 올리지 않는다(POL-043·045).
9. **결과 0건과 바로잡기(추천 적용).** ① 로마자만인 입력의 결과가 0건이면 한/영 변환 값으로 찾은 결과를 보이고 "'루멘'으로 찾은 결과입니다 · 'fnaps'로 찾기"를 알린다. ② 그래도 0건이면 자동완성 사전에서 낱자 단위로 가장 가까운 이름 하나를 "혹시 '루멘'을 찾으셨나요?"로 제안한다(가까움의 기준은 [가정], 골든 세트로 정한다). ③ 필터가 걸려 있으면 필터를 뺀 결과 수를 보이고 필터 풀기를 권한다. ④ 오픈 예정 인기 공연을 관련 공연으로 보인다.
10. **관련 공연(추천 적용).** 결과의 맨 위 일치가 아티스트나 공연장이면 그 아티스트의 다른 공연이나 그 공연장의 오픈 예정 공연을 6개 [가정]까지 결과 아래에 보인다. 결과가 0건이면 결정 9 ④다. 검색 기록은 쓰지 않는다.
11. **화면 그리기·캐시·검색 엔진 노출(추천 적용).**
    - `/search`는 요청마다 서버가 그리던 것을 캐시되는 정적 셸(헤더 묶음 A)로 바꾸고, 결과는 브라우저가 검색 API(CDN 30초 [가정], `stale-while-revalidate`)를 불러 그린다. 오픈 직전 검색이 몰려도 화면 서버로 가지 않는다.
    - `/search`는 검색 엔진 색인에서 뺀다(`<meta name="robots" content="noindex, follow">`, sitemap에 넣지 않는다). 검색 엔진 유입은 공연 상세(구조화 데이터)와 sitemap이 맡는다. 장르·공연장·아티스트 유입 페이지는 나중에 정한다(review/open-items.md 37번).
12. **재는 법(추천 적용).**
    - 목표는 NFR-028이다: 자동완성 원본 응답 p95 50ms [가정], 검색 원본 응답 p95 300ms [가정], 골든 세트 1위 정답률 90% [가정]·3위 안 98% [가정].
    - 골든 세트: 기대 결과를 정한 검색어 100개 [가정](정확한 이름, 다른 이름, 조합 중 글자, 초성, 한/영 실수, 띄어쓰기, 오타, 두 글자, 특수 문자, 0건). CI가 고정 카탈로그로 돌리고, 순위 규칙을 고칠 때마다 앞뒤를 비교한다.
    - 품질 비율: 브라우저가 검색어 없이 사건 수만 같은 출처 수집 경로(`/_t/rum`, ADR-0076)로 보낸다(결과 0건, 자동완성 선택 위치·종류, 결과 클릭 위치, 10초 안에 다시 검색). 지표로만 모으고 원본 사건은 남기지 않는다. 결과 0건 비율, 자동완성 선택률, 결과 클릭률, 바로 다시 검색한 비율을 본다.
    - 0건 검색어 목록: 검색 원본의 요청 기록(정규 로그 줄)에 정규화한 검색어·결과 수·필터를 남긴다. 계정과 잇지 않는다(요청에 쿠키가 없다). 운영자는 주마다 0건 검색어 목록을 보고 다른 이름을 더한다. CDN이 같은 검색을 받아 주므로 횟수는 대략이다.
    - 부하: 부하 분해(docs/verification.md §3.1)에 오픈 직전 검색 몰림과 무작위 입력(캐시 우회) 시나리오를 넣는다.
13. **굿즈.** 머리 검색창은 지금 굿즈를 찾지 않는다. 굿즈에 아티스트 연결이 생기거나 요구가 보이면 다시 본다(review/open-items.md 36번).
14. **정본 반영.** 새 정본 docs/features/search.md와 함께 docs/security/asvs/catalog-review.md, docs/security/data-classification.md, docs/data.md, docs/api/openapi.yaml, docs/api/guidelines.md, planning/01(§4.1, §5.2), planning/02(FR-003, NFR-028), planning/03(POL-043·045, 용어 사전 '자동완성'·'관련 공연'·'연관 검색어'), planning/04(SCR-001·003), design/d2 CMP-004, design/d3, design/d4, design/d5 §5.3, docs/frontend.md, docs/architecture.md, docs/infra.md, docs/observability.md, docs/verification.md, docs/features/analytics.md·README.md, wbs, tools/doc-check(절 참조 이름 목록)를 고친다. ## 검토한 대안

| 대안 | 기각 이유 |
| --- | --- |
| 지금 설계 그대로(pg_trgm + Redis 후보 캐시) | 맥락의 빈틈이 그대로 남는다. 조합 중 글자·초성·한/영 실수를 맞히지 못하고, 무작위 입력이 Redis 키와 DB 질의를 늘린다 |
| 검색 전용 서버(Elasticsearch, AWS OpenSearch 관리형) | 한국어 형태소 분석과 검색 도구 묶음을 얻는다. 하지만 대상이 1~2만 건이고 검색어 대부분이 이름이라 얻는 것이 적다. AWS 권장 고가용성 구성은 월 약 687달러다. 데이터를 두 곳에 두어 옮기는 장치·다시 색인·건수 대조가 생기고, 승인 취소가 같은 트랜잭션으로 빠지지 않는다. nori에는 낱자·초성 비교가 없어 한글 처리는 어차피 직접 한다. 바꿀 조건(결정 4)에서 다시 본다 |
| OpenSearch 서버리스 | 검색 처리 단위 1개를 늘 켜 두면 월 약 214달러다. 0으로 줄이면 첫 요청이 늦다. 나머지는 위와 같다 |
| 외부 검색 서비스(Algolia) | 운영할 서버가 없고 분석과 인기 검색어를 기본으로 준다. 하지만 키 입력마다 요금이 붙고, 브라우저가 Algolia로 바로 물어 우리 CDN 캐시를 앞에 둘 수 없어 오픈 직전 몰림이 그대로 요금이 된다. 종량제 서버 위치가 미국·영국·EU라 키마다 왕복이 늘고(서울에서 미국 서부까지 빛이 광섬유로 오가는 시간만 약 0.09초), 검색어와 접속 IP가 국외로 가서 ADR-0067의 국외 이전 틀로 법률 검토가 필요하다. 오타 1개 허용이 4글자 이상부터라 두세 음절 이름에는 기본으로 듣지 않는다 |
| 결과도 서버 메모리에서 찾기 | 빠르지만 필터·정렬·쪽을 파드마다 같은 판으로 맞추는 일이 생기고, 실행 계획으로 진단하는 DB 규칙(ADR-0086)을 쓰지 못한다. 지금 규모에서는 DB 읽기 모델로 충분하다 |
| 자동완성 사전을 브라우저에 파일로 내려 주기 | 요청이 없어진다. 하지만 검색창을 누르는 사람마다 수십 KB를 받고, 자주 바뀌는 사전을 맞춰야 한다. 피크 측정에서 원본이 버거우면 다시 본다 |

## 결과와 트레이드오프

- 조합 중 글자·초성·한/영 실수·띄어쓰기·다른 이름을 맞히고, 한 공연이 결과를 덮지 않는다.
- 자동완성은 DB와 Redis를 부르지 않는다. 파드 메모리가 몇 MB 는다. 판 확인 간격(10초 [가정]) 동안 파드마다 사전이 조금 다를 수 있다.
- 오타를 바로잡는 것은 결과 0건일 때의 제안 하나다. 오타 섞인 검색어로도 결과가 나오면 바로잡지 않는다.
- 검색 서버를 운영하지 않는 대신, 순위 규칙과 한글 처리를 직접 만들고 골든 세트로 지킨다.
- 한 음절부터 자동완성을 보내 요청이 조금 는다. 한 음절 입력은 가짓수가 적어 CDN이 대부분 받는다.
- 검색 품질은 비율 지표와 0건 검색어 목록으로만 본다. 검색어마다의 정확한 횟수는 모르지만, 검색어를 계정과 잇지 않는 원칙(data-classification '최근 검색어')을 지킨다.

## 되돌릴 조건

- 결정 4의 바꿀 조건 넷.
- 자동완성 원본이 오픈 직전 피크에 버거우면(측정) 브라우저 사전 파일을 다시 본다.
- 결과 0건 비율이 높고 그 검색어가 공연 설명이나 굿즈 쪽이면 대상을 넓히는 것을 다시 본다.

## 남는 한계

- 공연 설명 글·후기 본문·굿즈는 찾지 않는다.
- 수치(최소 길이, 종류별 몫, 0.3초, 10초, 6개, 20개, 1,000, NFR-028 목표)는 아직 재지 않은 가정이다(wbs 2.10.8·2.12.4).
- 디자인 캔버스(소비자 홈·검색 보드)는 아직 고치지 않았다. 장르·공연장·아티스트 유입 페이지도 정하지 않았다(review/open-items.md 25번·37번).
- 원문 설계서와 지난 ADR 본문의 '연관 검색어'(입력 중 후보 창의 뜻)는 쓴 그대로 남는다. 읽을 때는 이 ADR이 앞선다.
