# ADR-0100: 관제 콘솔 통신을 REST와 SSE 둘로 줄이고, 파트너 콘솔의 tRPC를 빼며, Module Federation은 한 앱 기준선과 견주는 쇼케이스로 남긴다(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 높음-05 '콘솔의 학습 지도 선택(관제 실시간 통로 둘, 파트너 tRPC, Module Federation)을 ADR-0092와 같은 잣대로 다시 정한다'에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 방향은 소유자 결정(추천안 승인)이고, 안 고르기(관제는 REST + SSE, Module Federation은 남기고 재기)와 기준값 같은 세부는 추천 적용이다. ADR-0027 결정 표의 Socket.IO(관제) 행, ADR-0024 결정 2의 '관제 조회 GraphQL·파트너 tRPC', ADR-0079 결정 11의 tRPC 경계와 결정 12의 관제 실시간 계약, 결정 16의 원격 통로(`ConsoleServices`의 GraphQL·Socket.IO), ADR-0091 결정 3의 graphql-ws 구독 수명 수단을 대신한다. ADR-0091의 멈춤 규칙(무엇을 언제 멈추나)과 ADR-0092의 상태 도구는 그대로다) 2026-10-28(기술 검토 낮음-024, 소유자 승인 '추천안 동의'): 파트너 판매 현황은 SSE에서 1분 주기 REST 조회로 바뀌었다(ADR-0027 상태 줄). 그래서 '결과'의 '콘솔 실시간 규칙이 파트너 SSE와 하나가 된다'는 관제 SSE 두 흐름 안의 규칙 하나로 읽는다. 2026-10-30(ADR-0165): 결정 6의 위젯 패키지 `@peaket/widget-*`는 게시하지 않고 작업 공간 패키지로 둔다. 관제 콘솔 호스트가 `workspace:`로 묶어 한 앱 기준선을 빌드한다(docs/devops.md §6.6).
- **관련**: ADR-0016, ADR-0024, ADR-0027, ADR-0067, ADR-0079, ADR-0082, ADR-0091, ADR-0092, ADR-0102, ADR-0103, FR-026, FR-029, FR-031, NFR-008, NFR-009, NFR-012, [docs/frontend.md](../frontend.md) §2·§3·§4.4·§4.5·§4.6·§5.7·§5.9·§5.17, [docs/architecture.md](../architecture.md) §3·§4·§6, [docs/features/control-tower.md](../features/control-tower.md) §1·§12·§13, docs/api/asyncapi.yaml(`sse.ops-live`), docs/api/openapi.yaml, [docs/api/proto/README.md](../api/proto/README.md) §4, [docs/data.md](../data.md) §1, [docs/devops.md](../devops.md) §6.6, [docs/security/asvs/frontend.md](../security/asvs/frontend.md), wbs 4.5.1·4.5.6, [review/tech-review.md](../review/tech-review.md)(높음-05)

## 맥락

- **관제 콘솔의 통로 셋**: 콘솔 하나가 명령은 REST로, 위젯 조회와 구독은 GraphQL(urql, graphql-ws)로, 명령 확인(ack)·경보·접속자는 Socket.IO로 받는다(docs/frontend.md §4.4.4·§4.4.5).
  - 같은 `ops-api`에 WebSocket(연결을 열어 둔 채 서버와 브라우저가 주고받는 통신 방식)을 두 개 연다. 서버 라이브러리, 재연결 규칙, 쿠키·`Origin` 인증, 가짜 서버 시험(FE-T26)이 두 벌이다.
  - GraphQL은 영속 쿼리(미리 등록한 쿼리 ID)만 쓴다. 그래서 '위젯마다 필드를 고른다'는 장점이 작고, 스키마 산출물·인트로스펙션 끄기·깊이 제한 같은 일만 콘솔 하나를 위해 남는다. 시스템의 나머지는 REST·OpenAPI·Problem 규칙과 orval 생성 클라이언트로 통일돼 있다.
  - Socket.IO의 기본 전달 보장은 '많아야 한 번'이다(Socket.IO 문서, 기술 검토 §9). 문서의 'ack 수신 보장'과 다르고, 실제로는 다시 붙으면 명령 상태를 REST로 다시 읽는다.
  - Socket.IO의 파드 사이 전달(Redis 어댑터)은 로그인 세션·레이트 리밋·봇 피처·작업 큐와 같이 쓰는 세션·캐시 Redis에 있다. 독립 제어 평면이 데이터 평면 부하에 묶인다(높음-08과 같은 문제, ADR-0102).
  - ops-svc의 'gRPC 관제 지표 서버 스트리밍'은 받는 쪽이 없다(docs/api/proto/README.md §4가 스스로 적었다).
- **파트너 콘솔의 tRPC**: ADR-0079 결정 11 뒤로 tRPC 프로시저는 gw-partner REST 작업과 1:1인 얇은 껍질이다. 고른 이유('별도 API 명세서가 필요 없다', architecture §6.4)는 OpenAPI와 orval 생성 타입이 있는 지금 성립하지 않는다. 같은 입·출력을 Zod로 한 번 더 정의하고, 요청이 앱 서버를 한 번 더 거치며, api-client 정책(재시도·Problem·멱등키)을 tRPC 쪽에 다시 만들어야 한다. SSE·내려받기·올리기·토큰 갱신은 이미 브라우저가 `partner-api`를 직접 부른다.
- **관제 Module Federation**: 고른 ADR이 없다(원문에서 이어받음). 원격 위젯을 서비스 저장소가 따로 빌드하는 구조는 '위젯을 아는 팀이 함께 배포'하려는 것이다(ADR-0079 대안표). 실제 팀이 없어 이득은 가상 팀(wbs §1, ADR-0016) 시연에 그친다. 사용자에게 주는 효과(위젯 결함 격리, 화면별 늦게 싣기)는 한 앱 안의 경로별 늦게 싣기·오류 경계·위젯마다 저장소(ADR-0091·0092)로도 얻는다.
- **같은 잣대**: 2026-10-27 ADR-0092는 Jotai·Redux를 '학습 지도에서 온 도구 수'를 이유로 뺐다. 소유자 전제(2026-10-27)대로 개발량은 이유로 쓰지 않는다. 기술마다 '왜 이것인가·얼마나 나은가·언제 바꾸나'를 적고, 쇼케이스로 남기는 것은 그렇다고 밝히고 단순한 기준선과 함께 잰다.
- **확인한 사실(2026-10-28 원문)**:
  - MDN EventSource: SSE(서버가 브라우저로 한 방향으로 계속 보내는 통신 방식)는 HTTP/2가 아니면 브라우저당 열린 연결 수 한도(6개)에 걸린다. HTTP/2에서는 동시 스트림 수를 서버와 클라이언트가 협상한다(기본 100).
  - Envoy 경로 설정: 경로 시간 초과(`timeout`)는 지정하지 않으면 15초이고, 요청을 다 받은 뒤부터 응답을 다 받을 때까지를 잰다. 0이면 끈다.
  - Gateway API `HTTPRouteTimeouts`: `request`를 0초로 두면 시간 초과를 꺼야 한다(SHOULD). 끌 수 없는 구현은 가장 긴 값으로 읽는다.
  - NestJS `@Sse()` 데코레이터(`@nestjs/common`): 기본 메서드는 GET이고, 읽지 않는 클라이언트에 쌓이는 양의 상한(`maxPendingDataLength`, 기본 4M 글자)을 넘으면 연결을 끊는다.

## 결정

1. **관제 콘솔의 서버 통신은 REST(OpenAPI)와 SSE 둘이다(소유자 결정 '추천안 동의', 안은 추천 적용).** 검토가 '도구가 가장 많이 준다'고 적은 REST + SSE를 고른다. GraphQL(urql·graphql-ws·`schema.graphql`·영속 쿼리 목록)과 Socket.IO(서버 게이트웨이·Redis 어댑터·`socket.io-client`)를 쓰지 않는다.
   - 명령·승인·위젯 조회·감사 로그 조회는 REST다. 화면은 `@peaket/api-client`(orval)의 `ops` 묶음을 쓴다.
   - 서버가 미는 것은 SSE 흐름 둘이다.

   | 흐름 | 주소 | 실어 보내는 사건(`event:`) | 닫는 때 |
   | --- | --- | --- | --- |
   | 늘 여는 흐름 | `GET /v1/ops/live`(선택 `eventId`) | `command`(명령 상태가 바뀔 때. ack 포함), `approval`(내 승인 대기), `alert`(`OpsAlert`), `control`(자동 제어 다섯 값), `autoAction`(걸린 자동 조치와 풀림), `presence`(고른 회차의 접속 운영자) | 로그아웃·세션 종료·토큰 만료 때만. 탭을 숨겨도 닫지 않는다 |
   | 위젯 흐름 | `GET /v1/ops/events/{eventId}/live`(`widgets` = 보이는 위젯 키 목록) | `widget`(위젯 키마다 그 위젯의 전체 값) | 보이는 위젯 목록이 바뀌면 새 목록으로 다시 연다 |

   - 위젯을 처음 그리거나 다시 보일 때 필요한 지난 값(그래프의 최근 15분 창)은 `GET /v1/ops/widgets/{widgetKey}`로 받는다. 위젯 키별 응답 모양은 openapi에 위젯마다 적는다(wbs 0.2.3).

2. **SSE 흐름 규칙(추천 적용).**
   - **형식**: `event:` 종류, `id`, `data:` JSON 한 줄, `retry: 10000`. 15초 [가정]마다 주석 줄(`: hb`)을 보낸다. 브라우저는 35초 [가정] 동안 아무것도 오지 않으면 끊고 다시 연다.
   - **빠지지 않게 다시 붙기**: 늘 여는 흐름의 `id`는 ops DB 알림 표(결정 4)의 순번이다. 다시 붙을 때 브라우저가 보내는 `Last-Event-ID` 뒤의 사건을 서버가 다시 보낸다. 표에 남은 1시간 [가정]보다 오래된 번호면 `reset` 사건을 보내고, 화면은 명령·경보·승인 대기를 REST로 다시 읽는다. 위젯 흐름은 메시지마다 위젯의 전체 값이라 다시 붙으면 지금 값부터 받는다(파트너 SSE와 같다).
   - **명령 확인의 정본**: REST의 명령 상태다. SSE는 빨리 알리는 길이다. 'ack 수신 보장'이라는 말은 쓰지 않는다.
   - **인증**: 운영자 쿠키(`withCredentials: true`)와 gw-ops의 `Origin` 확인이다. EventSource는 요청 헤더를 붙일 수 없으므로 흐름에는 재인증 토큰 같은 헤더를 쓰지 않는다(명령은 REST라 상관없다). 서버는 액세스 토큰의 만료 시각과 세션 종료(종료 세션 목록, ADR-0103)에 흐름을 닫는다. 브라우저는 토큰을 갱신한 뒤 다시 붙는다.
   - **게이트웨이**: 두 흐름 경로는 HTTPRoute `timeouts.request: 0s`로 시간 초과를 끄고, 응답을 버퍼에 모으지 않는다. Envoy 경로 시간 초과의 기본값은 15초이고 응답이 끝날 때까지를 재므로, 그대로 두면 흐름이 15초마다 끊긴다. 파트너 SSE(`/v1/partner/events/{eventId}/live`)도 같다. 끊기지 않은 연결이 살아 있는지는 주석 줄로 본다.
   - **HTTP/2**: 콘솔과 `ops-api` 사이는 HTTP/2다. HTTP/1.1이면 브라우저가 한 곳에 여는 연결이 6개로 묶여, 탭 여러 개의 흐름이 서로를 막는다(MDN). 탭 하나는 흐름 둘과 REST를 한 연결에서 나눠 쓴다.
   - **서버**: ops-svc가 NestJS 기본 SSE(`@Sse()`)로 낸다. 클라이언트가 읽지 않아 쌓이는 양에 상한을 두고, 넘으면 연결을 끊는다(브라우저가 다시 붙는다).
   - **보이지 않는 위젯(ADR-0091 결정 3의 수단을 바꾼다)**: 호스트가 보이는 위젯 키를 모아, 목록이 바뀌면(고르지 않은 탭 10초 뒤, 숨긴 브라우저 탭 30초 뒤, 회차를 바꾸면 바로) 1초 [가정] 묶어 위젯 흐름을 새 `widgets`로 다시 연다. 같은 위젯 키는 한 번만 받아 나눠 준다. 늘 여는 흐름은 그대로라 경보·명령 확인·자동 제어 상태는 숨긴 동안에도 받는다. 무엇을 언제 멈추는지는 ADR-0091 그대로다.

3. **ops-svc의 'gRPC 관제 지표 서버 스트리밍'은 지운다(추천 적용).** 받는 쪽이 없다. 콘솔이 보는 숫자는 SSE가, 자동 제어의 입력은 클러스터 안 Prometheus가 맡는다(ADR-0068 결정 2).

4. **파드 사이 전달은 공유 Redis를 쓰지 않는다(추천 적용, ADR-0102 결정 4와 함께 정한다).**
   - ops-svc 파드는 자기에게 붙은 SSE 연결만 든다. 한 파드에서 생긴 사건(명령 상태, 승인 대기, 경보 수신, 자동 조치의 시작·끝)은 원래 기록과 같은 트랜잭션으로 ops DB 표 `ops_push_event`(순번 `seq`, 종류, 회차, 받을 역할, 본문 JSON, 만든 시각)에 쓴다.
   - 파드마다 0.5초 [가정]마다 마지막으로 읽은 `seq` 뒤를 읽어 자기 연결에 보낸다. 1시간 [가정] 지난 행은 정비 작업이 지운다.
   - 자동 제어 상태(admission-ctrl의 `q:{event:E}:ctl`)와 위젯 숫자(관제 실시간 표·Prometheus)는 지금처럼 파드마다 원천에서 읽는다(회차마다 한 번 계산해 그 파드의 연결에 나눠 준다, ADR-0099 결정 4).
   - 접속자: 흐름을 든 파드가 연결마다 15초 [가정]마다 `ops_presence`(계정 참조, 역할, 회차, 화면, 마지막 시각)를 고쳐 쓴다. 파드마다 5초 [가정]마다 회차별로 45초 [가정] 안의 행을 모아 `presence`로 보낸다.
   - 왜 DB인가: ops-svc가 명령을 쓰는 자기 저장소라 새 부품이 없고(ADR-0102 결정 4로 ops 전용 Aurora), 순번이 곧 `Last-Event-ID`가 된다. 운영자는 수십 명이고 명령은 분당 몇 건이라, 읽기는 파드 셋 × 초당 2회 [가정] 정도로 작다. 알림을 기다리는 장기 DB 연결(PostgreSQL `LISTEN/NOTIFY`)을 따로 두지 않으려고 주기 읽기로 한다.

5. **파트너 콘솔은 tRPC를 쓰지 않는다(추천 적용).**
   - 화면은 `@peaket/api-client`(orval)가 만든 TanStack Query 훅으로 `partner-api`를 직접 부른다. 소비자 웹과 같은 실행 정책(재시도·Problem·멱등키·시간 초과)을 쓴다.
   - 여러 호출을 묶어 첫 화면을 그리는 곳(예: 공연 허브 한 번에 읽기)만 파트너 앱 서버의 서버 컴포넌트가 REST를 묶어 읽는다. 쿠키는 그대로 넘기고, 화면이 쓰는 필드만 고른다.
   - 앱 서버는 로그인(Auth.js Credentials), 요청마다 그리는 셸(nonce CSP), 서버 컴포넌트 조합만 맡고 업무 규칙은 두지 않는다. 폼 검증은 `@peaket/validation`의 Zod 그대로다.
   - 다시 볼 조건: 앱 서버에 업무 로직이 생기거나, 서버에서 묶는 화면이 열 개 [가정]를 넘어 서버 쪽 조합에 따로 계약이 필요해질 때 tRPC를 다시 비교한다.

6. **관제 Module Federation은 쇼케이스로 남기고, 한 앱 기준선과 같은 화면으로 잰다(추천 적용).** 검토 2판(2026-10-27)이 추천을 '빼자'에서 '남기되 이유와 비교를 증거로 남기자'로 바꿨다.
   - **이유(쇼케이스임을 밝힌다)**: 가상 팀(wbs §1, ADR-0016)이 위젯을 자기 저장소에서 따로 빌드·배포하는 구조를 보인다. 사용자에게 주는 효과는 한 앱으로도 얻으므로, 이 선택의 이득은 '호스트를 다시 빌드하지 않고 위젯 하나를 내보내기'뿐이다. 그래서 그 이득과 비용을 잰다.
   - **기준선**: 원격 위젯을 가진 서비스 저장소는 원격 빌드와 함께 같은 소스를 위젯 패키지(`@peaket/widget-<원격 이름>`)로도 게시한다. 호스트 저장소는 같은 판의 패키지를 한 앱(경로별 `lazy` + 위젯 자리 오류 경계 + 위젯마다 Zustand 저장소)으로도 빌드한다. 두 빌드는 같은 `@peaket/console-contract`를 쓴다.
   - **잴 것(FE-T29, 같은 화면·같은 위젯 판, 3회 중앙값)**:
     1. 대시보드 첫 그림까지의 시간(4배 느린 CPU, 빈 캐시와 채운 캐시)
     2. 첫 화면 JS와 화면별 덩어리 크기(gzip)
     3. 원격 하나가 실패할 때(Module Federation은 원격 진입 파일, 한 앱은 위젯 덩어리를 막는다) 나머지 위젯·셸·경보 패널이 그대로인지
     4. 위젯 하나를 고쳐 운영에 내기까지 다시 빌드·배포하는 저장소 수와 걸린 시간
     
     결과는 성능 장부(`kpi: FE-T29`)에 둔다.
   - **바꿀 조건**: 1이 기준선보다 p75로 300ms [가정] 넘게 늦거나 2가 20% [가정] 넘게 크고, 4의 이득을 쓰는 원격이 하나뿐이면 한 앱으로 바꾼다. 그때 Module Federation은 '위젯을 따로 배포하는 팀이 둘 이상 생길 때'의 운영 설계로 남기고, 원격에 넘기는 읽기 전용 `host` 규칙은 패키지 경계 린트로 옮긴다. 반대로 위젯을 따로 배포하는 실제 팀이 생기면 그대로 간다.
   - **원격 계약은 통신만 바꾼다**: `ConsoleServices`의 `graphql`·`socket` 대신 `data`(`query(widgetKey, vars)`는 REST 위젯 조회, `subscribe(widgetKey, vars, next)`는 위젯 흐름)와 `live`(`on("alert" | "command" | "presence")`)를 넘긴다. 무결성(sha384)·계약 주판·대체 카드·`remotes.json`·공유 싱글턴 판 검사는 그대로다(ADR-0079 결정 16).

7. **보안·시험·계약(추천 적용).**
   - ASVS(OWASP의 웹 앱 보안 검증 항목 목록): V4.3(GraphQL) 행은 관제 콘솔에서 '해당 없음(GraphQL 미사용)'이다. V4.4.1(WSS)은 좌석 델타 WebSocket만 남고, 관제 흐름은 HTTPS SSE다. 파트너 콘솔의 필드 고르기(15.3.1)와 대량 할당 막기(15.3.3)는 서버 컴포넌트와 서비스 API의 스키마가 맡는다.
   - 시험: FE-T26의 가짜 GraphQL·Socket.IO 서버를 가짜 SSE 서버로 바꾼다. FE-T28(SSE 흐름 계약)을 둔다: 끊고 다시 붙을 때 `Last-Event-ID`로 빠진 명령·경보가 없고, 1시간 지난 번호면 `reset` 뒤 REST로 다시 읽고, 하트비트 15초·재연결 35초가 지켜지고, 토큰 만료·세션 종료 때 서버가 닫고 갱신 뒤 다시 붙으며, 위젯 목록이 바뀌면 위젯 흐름만 다시 연다. FE-T29는 결정 6의 비교다. C-T1의 'Socket.IO 룸과 presence'는 'SSE 흐름과 접속자'로 읽는다.
   - 계약: asyncapi의 `socketio.ops`를 `sse.ops-live`(늘 여는 흐름)와 `sse.ops-event-live`(위젯 흐름)로 바꾸고, openapi의 `/graphql`을 결정 1의 세 경로로 바꾼다. `CommandAck`·`OpsAlert` 메시지 모양은 그대로 쓴다.
   - architecture §6.1 '일부러 쓰지 않거나 미룬 기술' 표에 GraphQL·Socket.IO(관제)와 tRPC(파트너)를 더한다.

## 결과와 트레이드오프

- 관제 콘솔의 서버 통신 방식이 넷(REST·GraphQL·graphql-ws·Socket.IO)에서 둘(REST·SSE)로 준다. 브라우저 라이브러리 셋(urql·graphql-ws·socket.io-client), 서버 구성 둘(GraphQL 서버, Socket.IO 게이트웨이와 Redis 어댑터), 가짜 서버 둘이 빠진다.
- 콘솔 실시간 규칙이 파트너 SSE와 하나가 되고, 관제가 공유 세션·캐시 Redis에 기대지 않는다(ADR-0102).
- 파트너 콘솔은 계약 하나(OpenAPI)와 실행 정책 하나(api-client)만 쓴다. 요청이 앱 서버를 거치지 않아 홉이 하나 준다.
- Module Federation은 '왜 이것인가(가상 팀의 따로 배포)·얼마나 나은가(FE-T29)·언제 바꾸나(결정 6)'를 갖춘 쇼케이스가 된다.
- 대가:
  - 위젯 목록이 바뀔 때마다 위젯 흐름을 다시 연다(1초 묶음). 그 순간 위젯 값이 1초 안팎 늦게 온다.
  - 위젯 조회 REST 경로와 응답 모양을 위젯마다 계약에 적어야 한다(wbs 0.2.3).
  - 서비스 저장소는 위젯을 원격과 패키지 두 가지로 게시하고, 측정 작업이 1.5일 늘어난다.
  - 'GraphQL·Socket.IO·tRPC를 썼다'는 줄은 포트폴리오에서 빠진다. 이전 설계는 ADR-0024·0027·0079와 git 이력에 남는다.

## 되돌릴 조건

- 위젯 흐름을 다시 여는 횟수가 탭당 분당 6회 [가정]를 넘거나, 다시 열 때 위젯 값이 1초 [가정] 넘게 비면, 흐름을 열어 둔 채 구독 목록만 바꾸는 방식(흐름 ID와 같은 파드로 보내는 목록 갱신 호출)을 검토한다.
- 브라우저에서 서버로 자주 보내는 실시간 입력이 필요해지면 WebSocket을 다시 비교한다(대안 C).
- 알림 반영(사건이 생긴 때부터 화면까지) p99가 1초 [가정]를 넘으면 읽기 주기를 줄이거나 알림 전용 DB 연결을 검토한다.
- Module Federation은 결정 6의 바꿀 조건, tRPC는 결정 5의 다시 볼 조건을 따른다.

## 남는 한계

- SSE는 HTTP/2가 아니면 브라우저당 연결 6개 한도에 걸린다. 관제 PC가 HTTP/2를 쓰지 못하는 프록시 뒤에 있으면 탭 셋째부터 흐름이 막힌다.
- 접속자 표시는 15초 쓰기·45초 만료 [가정]라, 나간 운영자가 최대 45초 남아 보인다.
- 알림 표 보관(1시간 [가정])보다 오래 끊겼다 다시 붙으면 `reset` 뒤 REST로 다시 읽는 몇 초 동안 명령·경보 목록이 비어 보인다.
- Module Federation 비교는 한 PC에서, 한 사람이 만든 원격으로 잰다. 여러 팀이 공유 싱글턴 판을 두고 다투는 일은 재지 못한다.
- 파트너 콘솔 브라우저가 `partner-api`를 직접 부르므로, 앱 서버를 거칠 때보다 교차 출처 사전 요청이 는다(쓰기마다 한 번, 브라우저 캐시 시간 동안은 한 번). 파트너 트래픽이라 부하는 작다.
