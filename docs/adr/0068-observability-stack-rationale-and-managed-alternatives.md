# ADR-0068: 관측 스택 선택 근거 — 대안 비교와 AWS 관리형(AMP·AMG) 추가(2026-10-20)

- **상태**: 채택 (2026-10-20. 소유자가 "그라파나 대체제 대신 그라파나를 사용한 이유가 합리적이고 명확한가요?"라고 물었다. '방향은 합리적이지만 대안과 비교한 기록이 없고, 서울 리전의 AWS 관리형이 비교에서 빠졌다'는 답을 본 뒤 "관측 스택 선택 근거를 새 ADR로 남기고(대안 비교 표 포함), ADR-0067의 4.8.2 비교 측정에 AWS 관리형(AMP·AMG)을 더해 주세요"라고 요청했다. 결정 3·5는 소유자 요청을 적은 것이다. 결정 1·2·4·6과 판정 규칙의 정리·수치는 추천 적용이며 소유자 검토 대상이다. 외부 사실은 2026-10-19·20에 각 공식 문서와 GitHub 원문으로 확인했다) 2026-10-20(ADR-0069): 결정 2로 제어 입력이 클러스터 안 Prometheus에 묶이므로, 그 입력이 끊기거나 낡으면 입장 제어 자동화는 멈춰 목표를 유지한다(제어 입력 없음, 소유자 결정). 입력 없음이 측정에서 잦으면 결정 2를 다시 본다. 2026-10-20(ADR-0071): 결정 2를 지표 출처 표(docs/observability.md §8)로 구체화했다. 판단·제어 숫자는 Prometheus, 상세 퍼널·판매 누적·잔여석·파트너 현황·봇 잠정 숫자는 관제 실시간 표이고, NFR-009의 대상을 관제 실시간 표 지표로 좁혔다. 2026-10-21(ADR-0076): 결정 2를 넓혀 지표는 모두 클러스터 Prometheus가 긁고 텔레메트리 수집기를 거치지 않는다. 그래서 4.8.2 평가의 AMP 지표 복사는 수집기의 Remote Write Exporter 대신 Prometheus 원격 쓰기(SigV4)로 하고, Datadog 지표는 평가 기간에만 Datadog 에이전트의 OpenMetrics 점검으로 긁는다(긁은 지표는 기본으로 사용자 정의 지표로 셈). 2026-10-21(ADR-0077): ① Mimir 보존을 원본 90일·5분 집계 13개월(테넌트 분리)로 바꿨다(소유자 결정). 본문의 '13개월' 서술은 그 전 값이고, R1(긴 범위 조회)은 이 배치로 판정한다. AMP의 조회 범위 한도(95일)를 넘는 조회는 5분 집계의 긴 추세뿐이다. ② Mimir는 고전 구조(영역 인식 3중 복제)를 명시했다. Tempo의 쓰기 경로에 관측 전용 Kafka(세 번째 MSK)가 들어가 직접 운영 비용(R2)에 그 비용과 운영 시간이 더해진다. ③ Mimir는 다운샘플링을 지원하지 않는다(Mimir 문서, 2026-10-21 확인). Thanos는 이 점에서 다시 볼 이유가 하나 더 생겼다. 2026-10-28(기술 검토 높음-13, 소유자 승인 '추천안 동의'): 결정 2는 빠른 제어 입력과 판단 숫자에 걸린다. 28일 남은 예산·28일 SLO 보고·배포 잠금 판정은 로컬 Prometheus 보존(15일)보다 긴 창이라, Mimir `raw`(90일)에서 Mimir 규칙 평가기가 계산한 값 하나를 쓴다. 배포 잠금은 빠른 제어 루프가 아니라서 이 결정과 어긋나지 않는다. 그 값을 읽지 못하거나 낡으면 잠금 상태를 지금대로 유지한다(docs/observability.md §8). 2026-10-28(기술 검토 중간-021, 소유자 승인 '추천안 동의'): 결정 6의 Tempo 근거('객체 저장소만으로 돌아가 운영 부품이 적다')는 맞지 않게 됐다. Tempo 3.0이 인제스터를 빼 마이크로서비스 모드에 Kafka 호환 큐가 꼭 필요하고, 그래서 ADR-0077이 세 번째 MSK를 두었다(Tempo 배포 모드 문서·변경 기록, 2026-10-28 확인). 요청 기록은 관측 자료 3등급(docs/observability.md §9 등급표)이라, wbs 4.8.2에서 Tempo 마이크로서비스 + 관측 전용 MSK, Tempo 모놀리식 + 꼬리 표본 상한, AWS X-Ray(서울, 가격 목록으로 계산)를 견줘 요청 기록 저장소를 고른다(docs/observability.md §1). 2026-10-28(ADR-0120, 소유자 승인 '추천안 동의'): 결정 6의 Mimir 선택은 Thanos와 13개월 저장량·부품 수·AZ 장애 방식으로 견줘 그대로 두었다. 결정 3 표의 'Thanos·VictoriaMetrics … 뺌'은 ADR-0120의 비교로 읽고, 다시 볼 조건은 ADR-0120 결정 5다. 2026-10-28(기술 검토 중간-023, 소유자 승인 '추천안 동의'): 결정 5의 '방법'에서 '같은 지표를 AMP로도 보낸다'와 '무료 등급과 체험으로 0원에 맞춘다'는 둘로 나눠 읽는다. ① 계산: 로컬에서 센 양(활성 시계열, 초당 샘플, 로그·요청 기록 GB, 서버 수)을 4.8.1 규모로 외삽해 세 후보의 비용을 가격표로 낸다(보내지 않는다). ② 보내기: Datadog Watchdog 비교와 AMP·AMG 장기 조회 확인만 하고, 보낼 샘플을 미리 계산해 AMP 무료 등급 4천만 이하로 줄이며(`write_relabel_configs`) AWS 비용 경보를 건다. 활성 시계열 10만 개를 15초마다 그대로 보내면 하루 약 48달러다(AMP 서울 가격 목록 2026-10-14 게시본: 4천만 샘플 무료, 20억까지 1천만 샘플당 0.90달러). R2의 운영 시간은 로컬 측정값을 그대로 쓰지 않고, 부품 수·업그레이드 주기로 만든 연간 추정식(출처 표시, [가정])과 ±50% 민감도 표로 넣는다. 직접 운영을 고르려면 +50% 쪽에서도 1위여야 한다(docs/perf-ledger.md §11).
- **관련**: ADR-0067(결정 5의 비교 대상과 판정 규칙을 이 ADR이 넓힌다), ADR-0022, ADR-0032, ADR-0049, ADR-0052, ADR-0057, NFR-009, docs/observability.md §1·§3·§8·§9, docs/features/queue-admission.md §5, docs/infra.md §5, wbs 4.1.1·4.8.2

## 맥락

- 지금 관측 스택(OpenTelemetry, Prometheus → Mimir, Loki, Tempo, Pyroscope, Alertmanager, Grafana)은 원문 설계서 26장의 학습 항목 매핑에서 그대로 왔다. 부록 26장의 '채택 이유'는 쓰임새만 적었다("트레이스 ID로 로그 연결", "관측 스택 완성" 등). 왜 다른 도구 대신 이것인지는 적지 않았다. 이 선택을 다룬 ADR도 없었고, ADR-0067은 비교 상대를 Datadog 하나로 잡았다.
- 설계상 이 스택은 보는 데만 쓰이지 않는다.
  - 입장 제어 AIMD는 Prometheus 쿼리로 다운스트림 p99 지연과 오류율을 읽는다(queue-admission §5).
  - KEDA는 Prometheus 지표로 확장을 정한다(infra §5).
  - 관제 콘솔의 실시간 위젯과 수집 장애 때 축소 표출도 클러스터 안 Prometheus를 읽는다(observability §1·§10).
  - 보존 기간은 로컬 Prometheus 15일, Mimir 13개월이다(observability §9).
- 확인한 사실(2026-10-19·20 원문):
  - **AWS 관리형**
    - Amazon Managed Service for Prometheus(AMP)와 Amazon Managed Grafana(AMG)는 둘 다 서울 리전(ap-northeast-2)에 있다. AWS X-Ray도 서울에 있다.
    - AMP는 ADOT(AWS Distro for OpenTelemetry) 수집기의 Prometheus Remote Write Exporter와 SigV4 인증 확장으로 지표를 받는다.
    - AMP 기본 한도: 작업 공간당 활성 시계열 5천만 개(늘릴 수 있음), 초당 수집 샘플 1,666,666개, QueryMetrics API 초당 300건(늘릴 수 있음), 쿼리 하나의 기간 최대 95일.
    - AMP 보존은 기본 150일이고 최대 1,095일까지 늘릴 수 있다.
    - AMP 요금은 수집·저장·조회한 샘플만큼이다(조회 10억 샘플당 $0.10). 무료 등급은 수집 4천만 샘플, 조회 2천억 샘플, 저장 10GB다.
    - AMG 요금은 작업 공간별 활성 사용자당 월 Editor $9·Viewer $5다. 90일 무료 체험은 사용자 5명까지다.
    - KEDA의 Prometheus 스케일러는 AMP에도 붙는다.
  - **Grafana Cloud**: 같은 도구를 Grafana Labs가 운영한다. 리전 목록에 한국이 없다(가까운 곳은 일본 ap-northeast-1과 싱가포르). 무료 등급은 지표 1만 활성 시계열, 14일 보존이다.
  - **Datadog**: ADR-0067의 사실 그대로다. 한국 리전이 없고, 서버·지표 조합·로그 양으로 과금하며, 조회 한도 숫자를 공개하지 않는다.
  - **스택 구성 요소**(공급사 설명이므로 성능·비용 수치는 근거로 쓰지 않는다)
    - Loki는 로그 본문을 색인하지 않고 스트림의 라벨만 색인한다. 압축한 덩어리는 S3 같은 객체 저장소에 둔다.
    - Tempo는 객체 저장소만 있으면 돌아간다.
    - Mimir는 Prometheus의 장기 저장소이고 수평 확장, 객체 저장소, 복제, 멀티 테넌트를 내세운다.
    - Thanos는 기존 Prometheus 위에 얹어 객체 저장소로 장기 보존하는 구성 요소 묶음이다.
    - VictoriaMetrics에는 단일 서버판과 클러스터판이 있다.
  - **라이선스**(GitHub 저장소 기준): Grafana·Loki·Tempo·Mimir·Pyroscope는 AGPL-3.0이다. Prometheus·Alertmanager·Thanos·VictoriaMetrics·OpenSearch는 Apache-2.0이다.
  - **ClickHouse 기반**: SigNoz는 OpenTelemetry 기반 오픈소스 관측 플랫폼이다. PromQL과 ClickHouse SQL로 조회하고 직접 설치할 수 있다. ClickStack은 ClickHouse의 관측 스택이고 OpenTelemetry 수집기로 데이터를 받는다.

   - 이에 따라 ADR-0067의 R1(콘솔 갱신과 조회 한도)은 콘솔의 장기 조회(리플레이·지난 회차 비교)와 엔지니어 화면에만 적용해 읽는다.
   - 로컬 Prometheus는 어느 후보를 고르든 직접 운영으로 남는다.

   - 근거로 쓰는 것:
     - ① PromQL 호환. 필수 조건이다.
     - ② Loki가 라벨만 색인하고 Tempo가 객체 저장소만 쓰는 구조. 다만 비용 차이가 얼마나 되는지는 측정 전이다. 공급사의 '비용 효율' 주장은 근거로 쓰지 않는다.
     - ③ 데이터를 서울에 둔다.
     - ⑤ 오픈소스이고 계측이 OTel이다.
   - 근거로 쓰지 않는 것: 학습 로드맵에 있다는 사실, 공급사의 성능 수치(예: Mimir 내부 시험의 10억 시계열).
   - 아직 측정 전인 것: ④ 운영 부담, ⑥ 장기 조회.
5. **ADR-0067 결정 5의 비교에 AWS 관리형을 더한다(소유자 요청, 세부는 추천 적용)**:
   - **후보 셋**
     - 직접 운영(지금 구성)
     - AWS 관리형: AMP가 Mimir 자리, AMG가 Grafana 자리를 맡는다. 로그·요청 기록·프로파일은 직접 운영을 그대로 두는 구성을 기본으로 잰다. CloudWatch Logs·X-Ray로 옮기는 경우는 가격표로만 추정한다 [가정].
     - Datadog
   - **방법**
     - OTel Collector에 Prometheus Remote Write Exporter와 SigV4 인증 확장을 더해, 같은 지표를 AMP(서울)로도 보낸다.
     - AMG 작업 공간(서울)에서 AMP를 데이터 소스로 붙인다.
     - 비용은 AWS 무료 등급과 AMG 90일 체험으로 0원에 맞춘다.
     - 소유자의 AWS 계정이 필요하다. 계정이 없으면 가격표로만 추정하고 결과에 '추정'으로 표시한다.
   - **잴 것(AMP·AMG)**
     - 월 수집 샘플 수, 저장량, 조회 샘플 수를 서울 가격표로 환산한 비용
     - AMG 활성 사용자 비용(운영자·엔지니어 수 [가정])
     - 장기 조회(리플레이·지난 회차 비교)를 쿼리 한도(초당 300건, 기간 95일) 안에서 할 수 있는지
     - 직접 운영에서 빠지는 부품(Mimir·Grafana)의 운영 시간
   - **판정 규칙**: ADR-0067의 R1~R3를 세 후보에 함께 적용한다.
     - R1: 결정 2대로 장기 조회에 적용한다.
     - R3(개인정보 국외 이전 요건): 서울에 두는 직접 운영과 AWS 관리형은 통과한다. Datadog은 요건을 먼저 갖춰야 한다.
     - R2: R1·R3를 통과한 후보 가운데 연간 총비용이 가장 낮은 것을 고른다. 총비용은 서비스 요금, 서버·저장소·전송 비용, 운영 시간 × 시간 단가를 더한 값이다. 고른 것이 지금 구성과 다르면 새 ADR로 옮긴다. 다만 차이가 10% [가정] 안이면 옮기는 비용을 생각해 지금 구성을 유지한다.
6. **스택 안의 선택(추천 적용)**:
   - **Loki**: 로그를 traceId·라벨로 찾는 쓰임에 맞다. 본문을 색인하지 않아 폭주 때 색인이 커지지 않는다.
   - **Tempo**: 객체 저장소만으로 돌아가 운영 부품이 적다.
   - **Pyroscope**: 연속 프로파일링을 맡는다. AWS 관리형 후보에서도 직접 운영으로 남는다.
   - **Mimir**: Loki·Tempo와 같은 객체 저장소 운영 방식으로 13개월 장기 저장과 고가용성을 맞추려고 골랐다. 대안과 비교한 근거는 약하다. 4.8.2에서 Mimir 운영 시간이 직접 운영 시간의 큰 몫으로 나오면 Thanos·VictoriaMetrics를 새 ADR로 다시 본다.

## 검토한 대안

| 대안 | 고르지 않은 이유 |
| --- | --- |
| 비교 표 없이 지금 구성을 유지 | 소유자 질문대로 선택 근거가 명확하지 않다 |
| 지금 바로 AWS 관리형으로 옮김 | 운영 부담과 비용이 측정 전이다. 포트폴리오 기간에는 인프라를 설계로만 둔다(ADR-0057) |
| Grafana Cloud도 비교 측정에 넣음 | 한국 리전이 없다. 같은 도구를 맡기는 경우는 AWS 관리형(서울)이 다룬다 |
| 제어 입력도 외부 저장소에서 읽음 | 200ms 제어 루프에 원격 쓰기 지연, 외부 API 한도, 외부 장애가 들어온다 |

## 결과와 트레이드오프

- 관측 스택의 선택 근거가 기준별로 남고, 강한 근거(①②③⑤)와 측정 전 근거(④⑥)가 나뉜다.
- ADR-0067 대화에서 직접 운영의 근거로 든 '콘솔이 자주 읽어야 한다'는 이제 결정적 근거가 아니다. 결정 2로 어느 후보든 실시간 숫자는 로컬 Prometheus에서 읽기 때문이다. 후보 사이에 남는 차이는 장기 조회, 운영 부담, 비용, 데이터 위치다.
- 로컬 Prometheus는 어느 후보든 남는다. 그래서 '전부 맡기기'는 되지 않는다.
- AWS 관리형을 실제로 재려면 AWS 계정과 IAM 설정이 필요하다. 없으면 가격표 추정만 남는다.
- 반영 수치(2026-10-20): ADR 67 → 68. WBS 4.8.2는 1.5 → 2일이고 합계는 373.5 → 374일이다. 검토 기록은 R-77이다.

## 되돌릴 조건

- 4.8.2 판정이 AWS 관리형이나 Datadog으로 나오면 새 ADR로 옮긴다. 계측 코드는 그대로 두고 OTel 수집기 설정과 데이터 연결만 바꾼다.
- 로그 본문 전체 검색이 운영 요구가 되면 OpenSearch를 다시 본다.
- 운영 부담이 커서 분석용 ClickHouse와 관측 저장소를 합쳐 부품을 줄여야 하면 SigNoz·ClickStack을 다시 본다. 그때 KEDA용 Prometheus API를 확인한다.
- Mimir 운영 시간이 크면 Thanos·VictoriaMetrics를 다시 본다.
