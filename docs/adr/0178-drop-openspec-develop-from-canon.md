# ADR-0178: OpenSpec을 빼고 정본을 명세로 읽어 개발한다(소유자 결정, 2026-11-02)

- **상태**: 채택 (2026-11-02. 소유자가 BSL-010 뒤 "openspec을 매번 작업할때마다 작성을 해야 하나요?", "개발을 위해서 스펙을 작성하는건데 사용을 안할거면 필요없는거 아닌가요?", "openspec을 추가로 작성하게되면 그 과정에서 정합성이 깨지는 문제가 생길수 있거든요"라고 물은 뒤 "openspec을 모두 지우고 openspec을 빼고 정본 기준으로 개발 절차를 고칠게요"라고 정했다. 지우는 범위와 정본 기준 절차는 소유자 결정이고, 범위 목록·대조 스크립트·브라우저 확인 기록 자리·옛 기록 읽는 법은 추천 적용이다) 이 ADR은 [ADR-0167](0167-spec-driven-cycle-openspec-browser-check-after-verify.md)의 결정 1(도구)·2(사이클)·3의 `openspec/specs/` 부분·7(설정 자리)을 대체한다. ADR-0167의 결정 3의 '정본이 이긴다'·결정 4(시험 규칙, 2026-10-31부터 TDD 필수)·결정 5(브라우저 확인의 조건)·결정 6(E2E는 따로)은 아래 절차 안에서 그대로 쓴다. 2026-11-10: 결정 2의 단위(단계)와 docs/architecture.md §8.6의 'TDD 필수'는 [ADR-0256](0256-feature-batches-completion-ledger-risk-grades.md)이 기능 묶음과 '실패를 본 시험만 센다'로 바꿨다.
- **관련**: ADR-0167, ADR-0057, ADR-0170(화면 퍼블리싱), [docs/architecture.md](../architecture.md) §8.5·§8.6, [docs/PROGRESS.md](../PROGRESS.md) 턴 규칙, R-201(사이클 단위로 맡기기), R-232(BSL-010), R-233
- **관련 ID**: wbs 0.1.1·0.6.2(OpenSpec 설치·첫 사용, 완료된 일), D-T47(바뀐 범위)

## 맥락

- OpenSpec 사이클(ADR-0167)에서 명세의 값은 3단계 '계획 리뷰'에서 나온다. AI가 쓴 제안·명세를 사람이 구현 전에 읽고 고치는 단계다. 그런데 같은 날 R-201로 1인 기간의 계획 리뷰를 AI가 정본과 대조해 스스로 하게 했고, 감독 루프(Sidabari4Loop)도 사람에게 묻지 않고 돈다. 그래서 구현 전에 명세를 읽는 사람이 없었다.
- 명세는 정본(`docs/`)을 이번 변경 범위로 옮겨 적은 것이라, 숫자와 상태 값의 사본이 생긴다. 정본은 여러 작업이 함께 고친다(정합 점검 R 기록). 문서 점검 도구는 `openspec/`의 내용이 정본과 같은지 보지 않고, 보관한 명세(`openspec/specs/`)를 다시 읽는 단계도 없다. 정본이 바뀌면 사본이 소리 없이 낡는다.
- BSL-010(2026-11-02, R-232)에서 결함 6건은 모두 시험과 새 맥락 리뷰가 찾았다. 명세 덕에 찾은 것은 없었다. 정본에 없던 결정 셋은 정본보다 OpenSpec 설계 문서에 먼저 들어갔고(ADR-0167 결정 3의 '정본 먼저'와 어긋남), 대조(`/opsx:verify`)는 따로 돌리지 않았다.
- 명세를 실제 입력으로 쓴 곳은 화면 단계의 브라우저 확인(명세 시나리오를 대본 삼아 누름)뿐이었다.

## 결정

1. **OpenSpec을 뺀다(소유자 결정)**: `openspec/` 전부(설정 `config.yaml`, 보관한 변경 22개, 확인한 행동 목록 `openspec/specs/`), OpenSpec 스킬 7개(`.claude/skills/openspec-*`)와 명령 7개(`.claude/commands/opsx/`), 뿌리 개발 의존성 `@fission-ai/openspec`, 문서 CI의 `openspec validate`를 지운다. 지우기 직전 커밋에 git 태그 `archive-openspec`을 단다(로컬 태그. 원격에 올리는 일은 소유자 몫).
2. **정본 기준 절차(소유자 결정, 세부는 추천 적용)**: 코드를 바꾸는 단계는 범위 목록 → 정본 빈칸 먼저 → 시험 먼저 → 구현 → 대조 → (화면이면) 브라우저 확인 → 코드 리뷰·CI 순서로 한다(docs/architecture.md §8.6). 1인 기간에는 단계 하나를 범위 목록부터 커밋까지 한 번에 맡긴다(R-201 그대로).
3. **범위 목록에는 ID만 적는다(추천 적용)**: 이번에 맞출 정본의 ID(요구사항·정책·화면 번호, openapi `operationId`, ASVS 항목, 시험 ID, WBS ID)만 고르고 정본의 내용은 옮겨 적지 않는다. 사본이 없으니 정본과 어긋날 것이 없다. 자리는 루프의 `docs/PROGRESS.md` '다음 할 일'과 커밋 메시지다.
4. **대조는 기계로 한다(추천 적용)**: `tools/ci/trace-check.mjs`가 시험 보고서(vitest JSON, JUnit XML)를 읽어, 범위 목록의 시험 ID마다 이름에 그 ID를 단 시험이 통과했는지 본다. 통과한 시험이 없으면(없음, 실패만, 건너뜀만) 단계를 끝내지 않는다.
5. **브라우저 확인(추천 적용)**: 화면이 바뀌는 단계만 한다. 대본은 그 단계 범위의 화면 정본(`docs/design/d5-screen-blueprint.md`의 그 화면 절)과 시험 ID의 통과 기준이다. 결과는 `docs/review/browser-check/<단계 ID>.md`에 남긴다. 화면이 없는 단계는 기록을 만들지 않는다. 절차는 `.claude/skills/peaket-browser-check/SKILL.md`다.
6. **옛 기록을 읽는 법(추천 적용)**: 코드 주석과 문서의 'openspec 변경 `<이름>`'과 그 '결정 N'은 태그 `archive-openspec`의 `openspec/changes/archive/<날짜>-<이름>/`(결정 번호는 `design.md`)을 가리킨다. 근거 표시 수백 곳을 한꺼번에 고치지 않는다. 그 결정이 정본에 없으면 그 코드를 다음에 고칠 때 정본으로 옮긴다. 기술을 고른 이유는 지금처럼 ADR과 정본으로만 댄다.

## 검토한 대안

| 대안 | 기각 사유 |
| --- | --- |
| OpenSpec을 남기고 소유자가 코드 단계마다 구현 전에 명세를 승인한다 | 남은 코드 단계마다 소유자 검토가 필요하고, 사람에게 묻지 않는 감독 루프와 부딪힌다(소유자 기각) |
| 화면 단계에만 OpenSpec을 남긴다 | 절차가 둘이 된다. 브라우저 확인 대본은 화면 정본과 시험 ID에서 만들 수 있다(소유자가 모두 빼기로 정함) |
| 명세가 정본과 같은지 자동으로 견주는 검사를 더한다 | 사본을 없애면 견줄 것이 없다. 검사를 만들고 지키는 비용만 남는다 |

## 결과와 트레이드오프

- 코드 단계마다 쓰던 문서 4~6개(제안, 설계, 명세, 작업 목록, 브라우저 확인 기록)와 보관이 없어지고, 정본과 사본이 어긋날 자리가 사라진다.
- 잃는 것: 변경마다 한 폴더에 모인 계획·설계·작업 기록. 진행 로그(`docs/PROGRESS.md`), 커밋 메시지, 검토 기록(`docs/review/consistency-review.md`의 R 번호), 정본과 ADR이 나눠 맡는다. 구현한 바깥 행동의 따로 된 목록은 두지 않는다. 정본과 시험이 그 목록이다.
- 계획을 글로 먼저 정리하지 않으므로 AI가 정본을 잘못 읽을 위험이 남는다. 통과 기준마다 ID를 단 시험을 먼저 쓰기, 정본 빈칸 먼저 메우기, 기계 대조, 새 맥락 리뷰로 막는다.
- 사람의 사전 확인은 지금처럼 없다. 방향을 바꾸는 결정만 미해결(OPEN)로 멈추고 묻는다.
- 포트폴리오에서 '스펙 주도 개발 도구를 썼다'는 증거는 태그의 기록으로만 남는다. '정본을 먼저 쓰고 시험으로 맞춘다'는 과정은 정본, ADR, 시험 이름의 ID, 대조 결과로 보인다.

## 되돌릴 조건

- 소유자가 코드 단계마다 구현 전에 계획을 승인하기로 하면, 그 검토 단위(변경마다 짧은 계획 문서)를 다시 둔다. 도구는 그때 새 ADR로 정한다.
- 대조 스크립트가 시험 이름의 ID로는 정본 기준을 따라가지 못한다는 것이 드러나면(ID 없이 기준을 확인하는 시험이 많아지면) 대조 방법을 다시 정한다.
