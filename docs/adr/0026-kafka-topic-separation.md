# ADR-0026: 카프카(Kafka) 토픽의 도메인 성격별 3단계 분리 원칙 (거래·텔레메트리·제어/보안)

- **상태**: 채택 (2026-10-05 설계서 §8 Kafka 항목에 최초 수립, 2026-10-08 제어·보안 분리 정책을 추가하여 아키텍처 결정 레코드(ADR)로 공식 이관). 보완: ADR-0054(2026-10-13, 결정 3의 호환성 모드를 `BACKWARD`에서 `BACKWARD_TRANSITIVE`로 바꾸고 소비자 먼저 배포). 보완: ADR-0071(2026-10-20, 결정 1의 사용자 해시 키를 `telemetry.purchase`(구매 세션)·`telemetry.trust-verdicts`(대기 참여)에 되돌리고 `QueueAggregate` 키를 '회차:파드'로 고침. 관제 실시간 표의 이벤트 시각 창에 들어가는 텔레메트리 토픽에는 심장 박동 `PipelinePulse`를 넣고, 원본 적재의 오프셋 연속성 대조는 결정 3의 '트랜잭션을 쓰지 않음'을 전제로 한다) 2026-10-26(4차 점검 3부): 결정 1의 '결제 세션 시작/종료'는 구매 세션 시작·종료(`trade.purchase-sessions`)다. 대량 텔레메트리에는 queue-svc의 1초 집계 말고도 대기가 끝날 때 한 건씩 보내는 사람별 대기 기록 `QueueEntryRecord`가 있다(ADR-0052 결정 6). '클라이언트 핑'은 토픽으로 두지 않고(대기열은 하트비트를 받지 않는다, docs/architecture.md §9.1), 대기실 RUM은 Kafka를 거치지 않고 같은 출처 `/_t/rum`에서 게이트웨이 수집기를 거쳐 Prometheus로 간다(`telemetry.rum`은 예약 채널, docs/observability.md §11, ADR-0076). 결과 첫 줄의 '완벽히 격리한다'는 '텔레메트리 폭주가 거래·제어 클러스터의 브로커를 쓰지 않게 나눈다'로 읽는다(docs/infra.md §4). 2026-10-28(기술 검토 중간-021, 소유자 승인 '추천안 동의'): 맥락의 '대량 텔레메트리는 순간 피크 시 초당 200,000건 이상'은 지금 숫자와 맞지 않는다. 진입은 queue-svc가 1초 집계로 줄이고, 브라우저 RUM은 Kafka를 거치지 않는다(ADR-0076). 그래서 텔레메트리 클러스터의 피크는 초당 약 4천 건(홀드 시도 약 2,000·판정 약 1,700·1초 집계와 심장 박동 약 200, 거래는 약 6,300건, docs/infra-handover.md §3.2·docs/streaming.md §11 추정)이다. 결정 2의 물리 분리는 처리량이 아니라 장애 격리(텔레메트리가 멈추거나 밀려도 거래 사건은 영향 없다)와 권한·보존 분리의 근거로 읽는다. 두 클러스터를 생산 할당량을 둔 한 클러스터로 합칠지는 review/open-items.md 49번에 두었다(생산 할당량과 MSK IAM을 함께 쓸 수 있는지 확인 필요). 2026-10-29(ADR-0141·0142, 소유자 결정 '추천대로 반영'): 결정 1의 'acks=all·멱등 강제'는 공용 소비 모듈의 Kafka 클라이언트 필수 설정과 정적 검사 D-T45로 지킨다(쓰는 클라이언트의 기본값은 멱등 꺼짐·동시 요청 무제한이다). 결정 3의 'DLQ 구축'은 Kafka 데드 레터 토픽이 아니라 서비스 DB의 보류 표 `held_event`로 읽는다(ADR-0142 결정 2). 텔레메트리 피크는 초당 약 5,600건으로 고쳐 읽는다(`BehaviorSignal` 포함, ADR-0141 결정 6). 2026-10-29(원문 확인): 상태 줄의 '생산 할당량과 MSK IAM을 함께 쓸 수 있는지 확인 필요'는 확인됐다. MSK IAM에서도 Kafka 할당량을 쓸 수 있고, 대상 사용자 이름은 `arn:aws:sts::<계정>:assumed-role/<역할>/<세션 이름>`이며 브로커마다 센다(MSK 개발자 안내서 'Managing throughput with Kafka quotas'). 고정 세션 이름이 전제다(review/open-items.md 49번). 2026-11-01(정합 점검, ADR-0175 해설서 검토): 결정 1의 거래 토픽 파티션 키 '공연 ID'는 회차 ID `eventId`로 읽는다(docs/streaming.md, docs/architecture.md 통신 방식 표의 Kafka 행). 결정 2의 '거래용 클러스터와 텔레메트리용 클러스터' 둘에 관측 전용 클러스터가 더해져 MSK는 셋이다(ADR-0077 결정 2, docs/infra.md §1·§4).
- **관련 문서**: 설계서 §8(카프카 아키텍처), 28장(이벤트 기반 아키텍처 EDA), docs/api/asyncapi.yaml, ADR-0011(세션 종료 이벤트)
- **관련 ID**: NFR-006, NFR-009, NFR-017, FR-037, FR-040, FR-041

## 맥락
- 티켓 예매 시스템의 이벤트 스트림은 성격에 따라 요구되는 정합성과 처리량의 편차가 극심하다. 좌석 확정, 주문 생성, 결제 승인 등 핵심 금융/원장 거래 이벤트는 초당 수백 건 수준이지만 단 1건의 메시지 유실도 용납되지 않는 엄격한 신뢰성을 요구한다.
- 반면 대기열 진입, 사용자 브라우저 RUM(Real User Monitoring), 마우스 및 터치 행동 신호와 같은 대량 텔레메트리는 순간 피크 시 초당 200,000건 이상 폭증할 수 있으며, 일부 패킷의 누락보다 전체 시스템 지연 전파 방지가 우선된다.
- Apache Kafka는 동일 파티션 내부에서만 메시지의 순서를 엄격히 보장하므로, 모든 이벤트를 무분별하게 동일 토픽에 병합하거나 비즈니스 키를 단일하게 지정하면 특정 핫 파티션으로 트래픽이 쏠려 브로커가 고사하는 심각한 병목 현상이 발생한다.
- 또한 운영 제어 명령이나 토큰 세션 강제 무효화와 같은 보안 이벤트는 발생 빈도는 매우 낮으나, 클러스터 내 모든 마이크로서비스 인스턴스로 지연 없이 팬아웃(Fan-out)되어야 하는 특수한 전파 특성을 갖는다.

## 결정
1. 카프카 토픽을 데이터 신뢰성 및 유량 특성에 따라 다음 세 가지 계층으로 완전히 물리적·논리적으로 분리한다:
   - **거래 이벤트(Transactional Events)**: 주문 생성, 결제 승인, 좌석 영구 확정, 티켓 발권 이벤트는 PostgreSQL Transactional Outbox 패턴을 통해 발행하며, 좌석 홀드 및 결제 세션 시작/종료는 Redis Stream 릴레이를 거친다. 프로듀서 설정은 `acks=all`과 멱등성(`enable.idempotence=true`)을 강제하고, 이벤트 순서 보장을 위해 `공연 ID`를 메시지 파티션 키로 지정한다.
   - **대량 텔레메트리(High-volume Telemetry)**: 대기열 인입 신호, 클라이언트 핑, 행동 텔레메트리는 파티션 편향을 막기 위해 `사용자 ID(해시)`를 키로 사용하여 브로커 전 파티션에 균등 분산한다. `queue-svc`가 1초 윈도우로 사전 집계한 메트릭만 카프카로 전송하며, 대기실 RUM은 표본 샘플링을 적용한다(비율은 docs/observability.md의 RUM 수집 규칙을 따른다). 클라이언트 버퍼링이 한계에 도달하면 신규 텔레메트리를 과감히 드롭(Drop)하고 누락 카운트 지표를 프로메테우스로 방출하여 핵심 트래픽을 보호한다.
   - **제어 및 보안 이벤트(Control & Security Events)**: 운영 제어 정책 변경, 강제 로그아웃 세션 무효화 이벤트는 별도의 독립 토픽으로 분리하며, 높은 신뢰성이 보장되는 거래용 카프카 클러스터 내부에서 안전하게 발행한다.
2. 프로덕션 환경에서는 대량 텔레메트리의 폭주가 거래 이벤트의 인덱싱 및 디스크 I/O를 간섭하지 않도록 거래용 클러스터와 텔레메트리용 클러스터를 물리적으로 분리 운영하는 것을 원칙으로 한다.
3. 모든 이벤트 스키마는 Apache Avro 형식으로 정의하고 Schema Registry를 통해 엄격한 하위 호환성(`BACKWARD`)을 검증한다. 분산 환경의 중복 전달에 대비하여 카프카의 '정확히 한 번(Exactly-once)' 트랜잭션 오버헤드 대신 컨슈머 레벨의 멱등 처리(Idempotent Consumer)와 데드 레터 큐(DLQ)를 구축한다.

## 검토한 대안
| 대안 | 기각 사유 및 한계점 |
| --- | --- |
| 단일 공용 토픽으로 모든 이벤트 통합 | 20만 RPS에 달하는 대기열 텔레메트리 폭주가 동일 파티션 브로커의 I/O를 잠식하여 핵심 결제 승인 이벤트 전파가 수십 초 이상 지연되는 대형 장애를 초래한다. |
| 거래 이벤트에도 사용자 ID를 파티션 키로 적용 | 동일 공연 내에서 서로 다른 사용자가 동일 좌석을 경합하는 시나리오에서 좌석 상태 전이 이벤트의 인과적 선후 관계가 보장되지 않아 데이터 불일치가 발생한다. |

## 결과와 트레이드오프
- 거래 이벤트의 무결성과 대량 트래픽 수용 능력을 동시에 만족시키며, 노이즈가 많은 텔레메트리 장애로부터 핵심 결제 라인을 완벽히 격리한다.
- 클러스터 분리 및 다중 토픽 관리에 따른 인프라 프로비저닝 비용이 증가하며, 모든 다운스트림 컨슈머는 메시지 중복 수신을 전제로 한 멱등성 저장 로직을 갖추어야 한다.
