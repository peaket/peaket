# ADR-0095: 판매 일시정지는 commander 한 명이 바로 걸고 재개만 두 사람이 확인한다 — 2인 승인 시연은 데모 승인자 계정과 데모 막대로 한다(2026-10-27)

- **상태**: 채택 (2026-10-27. 기술 검토(review/tech-review.md)의 중간-077 '멈추는 쪽인 판매 일시정지에 2인 승인이 걸려 대응이 늦다'에 소유자가 "중간-077 건은 '멈춤은 1인, 재개는 2인' 으로 가겠습니다."라고 정했다. 같은 검토 §12.1에서 소유자가 "2인 승인은 구현은 하되 포트폴리오에서 데모를 보여줄수 있게 2인승인을 통과시켜주는 버튼을 따로 만드는건 어떨까요?"라고 제안했다. 이에 '건너뛰기 버튼이 아니라 데모 승인자 계정으로 실제 승인을 하는 버튼'을 추천했고, 소유자가 "2인 승인 데모는 추천방식으로 가겠습니다."라고 정했다. 두 방향은 소유자 결정이다. 아래 결정의 세부(사후 검토 보고서 항목, 비상 런북 서명 수, 데모 도우미의 배치와 막는 정책, 시험)는 추천 적용(2026-10-27)이다. 추천 적용은 소유자가 방향을 승인하고 세부를 맡긴 부분에서 제안해 적용한 것으로, 바꾸고 싶으면 언제든 바꾼다.)
- **관련**: POL-021, POL-022, FR-030, NFR-008, ADR-0049, ADR-0053(결정 11), ADR-0057, ADR-0062(결정 17), ADR-0073, [docs/features/control-tower.md](../features/control-tower.md) §3·§4·§5·§6·§13·§14, [review/tech-review.md](../../review/tech-review.md)(중간-077, §12.1)

## 맥락

- **판매 일시정지(명령 3)의 승인**: 지금은 commander가 요청하고, 요청자가 아닌 operator 이상 한 명이 승인해야 실행된다. 둘 다 재인증하고, 승인 대기는 최대 10분이다. ops-svc가 멈춘 때 쓰는 비상 런북(장애 때 따라 하는 절차를 명령 줄 도구로 만든 것)도 서로 다른 commander 두 명의 서명이 있어야 한다(ADR-0053 결정 11).
- **판단 순서와 어긋남**: 온세일 판단 순서는 "돈과 좌석에 의심이 1건이라도 있으면 판매 일시정지부터 검토한다"이다(docs/observability.md §13, ADR-0049). 그런데 오버셀(같은 좌석이 두 사람에게 팔리는 사고)이나 이중 결제가 이어지는 동안에도 두 번째 사람을 기다려야 한다. 같은 '멈추는 쪽' 명령인 자동화 정지(명령 11)는 commander 한 명이 바로 걸고, 사후 검토 보고서를 쓰며, 다시 켤 때만 2인이다(POL-021 C(4), ADR-0062 결정 17). 위험의 방향과 승인 강도가 어긋났다. 멈춤은 판매를 막는 안전 쪽이고, 재개는 판매를 다시 여는 위험 쪽이다.
- **2인 승인 시연**: 1인 프로젝트에는 두 번째 승인자가 없어 2인 승인을 보여 주기 어렵다(planning/01 §5.2 '1인 운영의 승인과 공급망의 한계'). 소유자는 데모에서 두 번째 승인을 통과시키는 버튼을 제안했다.
  - 서버에 '데모면 요청자와 승인자가 같아도 허용' 같은 분기를 두면, 그 코드가 운영 빌드에도 들어가 설정 하나로 켜지는 우회로가 된다.
  - 운영에 개발 기능을 두지 않는다는 기준(ASVS 13.4.2·15.2.3)과도 어긋난다.
  - 정본에는 이미 운영 묶음에서 빠지는 데모 막대(FE-T21)가 있다. 운영 네임스페이스에 들어오는 시뮬레이터 이미지를 거부하는 정책도 있다(docs/security/asvs/delivery.md 15.2.3).

## 결정

1. **멈춤은 1인, 재개는 2인(소유자 결정).** 판매 일시정지(명령 3)는 commander 한 명이 재인증하고 바로 실행한다. 승인 대기는 없고, 범위가 전체여도 같다.
   - 판매 재개는 지금처럼 2인이다. commander가 요청하고 요청자가 아닌 operator 이상 한 명이 승인한다(둘 다 재인증). 10분 안에 승인이 없으면 일시정지가 그대로 이어진다.
   - 자동화 정지(명령 11)와 같은 규칙이다. 다른 2인 명령(명령 4의 넓은 대역 차단, 명령 5, 명령 6)은 바꾸지 않는다.
   - 실행은 인시던트 선언 기준이라(POL-022) 포스트모템이 따른다.
2. **사후 검토 보고서(추천 적용).** 명령 3에도 명령 11의 사후 검토 보고서를 붙인다.
   - 실행한 commander가 48시간 안에 쓰고, 실행자가 아닌 commander가 7일 안에 검토한다. 기한을 넘기면 SEV3다.
   - 명령 3의 보고서는 그 인시던트 포스트모템의 한 절로 쓴다. 보고서는 재개의 조건이 아니다.
   - 항목의 '계기'는 명령 3용을 따로 둔다: 돈·좌석 의심, 가격·표시 오류, 시스템 장애 대응, 예방 정지, 그 밖이다. '2인 승인을 기다리지 않은 이유'는 명령 11에서만 쓴다.
   - API는 같은 `POST /v1/ops/commands/{commandId}/post-review`와 `POST /v1/ops/commands/{commandId}/post-review-confirmation`을 쓴다.
3. **비상 런북 서명(추천 적용).** ops-svc가 멈춘 때 런북으로 보내는 명령 3 정지 묶음은 commander 한 명의 서명으로 실행한다. 판매 재개 묶음과 비상 셔플(RB-35)은 지금처럼 서로 다른 commander 두 명의 서명이다. 그 밖의 묶음은 서로 다른 두 운영자의 서명이다(ADR-0053 결정 11 보완).
4. **2인 승인 시연(소유자 결정, 세부는 추천 적용).** 시연은 서버 검사를 건너뛰지 않고, 두 번째 계정으로 실제 승인한다.
   - **데모 승인자 계정**: 데모 시드 데이터(시연용으로 미리 넣는 가짜 데이터)에 두 번째 관리 계정 '데모 승인자'(역할 commander)를 둔다. 운영·스테이징 데이터에는 만들지 않는다. 비밀번호와 TOTP 비밀은 데모 비밀(로컬 `.env`, 커밋 금지)에만 둔다.
   - **데모 막대 버튼 둘**: 데모 빌드의 관제 콘솔 데모 막대에 둔다.
     - '데모 승인자로 승인'은 승인을 기다리는 요청(2인 명령, 판매·자동 제어 재개, 명령 3·11 사후 검토의 검토)을 데모 도우미에게 넘긴다.
     - '요청자 본인으로 승인 시도'는 지금 로그인한 요청자로 보통의 승인 API를 불러, 서버가 거절하는 장면(403)을 보인다.
   - **데모 도우미**: 데모 오버레이(`demo` 네임스페이스)에만 배포하는 작은 서비스다.
     - 데모 승인자 계정으로 로그인·재인증한 뒤 보통의 승인 API(`POST /v1/ops/commands/{commandId}/approvals`)를 부른다.
     - 공개 API만 쓰고 DB나 내부 경로에는 닿지 않는다.
     - 서버의 검사(요청자 ≠ 승인자, 역할, 재인증, 10분 기한)는 운영과 똑같이 돈다.
   - **서버**: 데모용 분기를 두지 않는다. 감사 로그에는 두 계정이 따로 남고, 데모 환경 표시가 붙는다.
   - **막는 장치**:
     - 데모 막대가 운영 묶음에 0건인지 운영 묶음 검사(FE-T21)가 확인한다.
     - 데모 도우미 이미지는 시뮬레이터 이미지와 함께 스테이징·운영 네임스페이스에서 Kyverno(쿠버네티스에 들어오는 설정을 규칙으로 검사하는 도구)가 거부한다.
     - gitops-check의 정책 시험도 운영 오버레이에 데모 도우미가 있으면 PR을 막는다.
   - **시험**: Playwright의 브라우저 맥락 둘(요청자·승인자)로 같은 흐름을 CI에서 돌린다(C-T47).
   - 버튼 없이도 같은 장면을 보일 수 있다. 두 번째 브라우저 창(다른 프로필)에서 데모 승인자로 로그인해 직접 승인하면 된다.
5. **정본 반영.**

   - docs/features: control-tower.md(§3·§4·§5·§6·§13, §14의 C-T13·C-T28과 새 C-T46·C-T47), seat-hold.md.
   - docs: api/openapi.yaml(사후 검토 API), infra.md(데모 환경, 비상 런북 통제), infra-handover.md, devops.md §4.3, frontend.md(데모 막대, FE-T21).
   - 보안: docs/security/asvs/payment.md·frontend.md·delivery.md.
   - 그 밖: design/d2·d5, guide/04·10·12, wbs 4.4.1·4.4.2.
   - ADR-0053·ADR-0062는 상태 줄에만 적는다.

## 검토한 대안

| 대안 | 기각 이유 |
| --- | --- |
| 명령 3을 지금처럼 2인으로 둔다 | 의심 1건에 바로 멈추라는 판단 순서와 어긋난다. 승인 대기(최대 10분) 동안 오버셀·이중 결제가 이어질 수 있다 |
| 범위가 '전체'인 명령 3만 2인으로 둔다 | 전체 범위가 필요한 때(결제 전체 장애, 여러 회차에 걸친 이중 결제 의심)가 오히려 가장 급하다. 규칙이 둘이 되어 화면과 시험이 는다 |
| operator도 명령 3을 바로 걸게 한다 | 판매를 멈추는 영향이 커서 commander의 판단으로 둔다(명령 11과 같다) |
| 서버에서 두 번째 승인을 건너뛰는 데모 버튼 | 그 분기가 운영 빌드에 들어가 설정 하나로 켜지는 우회로가 된다(ASVS 13.4.2·15.2.3). 데모가 '서버가 다른 계정을 요구한다'를 보이지 못한다 |
| 두 번째 브라우저 창에서만 데모 승인자로 승인한다 | 만들 것이 없고 효과는 같다. 다만 시연 중 창을 오가야 해서 버튼을 두고, 이 방법은 버튼 없이 쓰는 길로 남긴다 |

## 결과와 트레이드오프

- 의심 1건에 commander가 바로 판매를 멈출 수 있다. 승인 대기가 없고, 전파는 NFR-008의 p99 3초 그대로다.
- 대가: commander 한 명이 실수나 악의로 판매를 멈출 수 있다.
  - 줄이는 장치: 재인증(비밀번호 + TOTP), 관제 콘솔의 허용 IP·VPN(control-tower §10), 관제 화면의 '적용 중 명령'과 불변 감사 로그에 바로 남는 실행 기록, 포스트모템과 사후 검토 보고서.
  - 다시 열려면 두 사람이 필요하다. 그래서 잘못 멈췄을 때는 재개 승인이 올 때까지 판매가 멈춰 있다.
- 2인 승인 시연이 운영과 같은 서버 검사를 거친다. 그래서 시연 자체가 통제가 동작한다는 증거가 된다. 대가는 데모 도우미 서비스, 배포 정책 한 줄, 시험 하나다(wbs 4.4.1 +0.5일).
- 명령 3의 사후 검토는 명령 11의 흐름을 그대로 써서 일수를 늘리지 않는다.

## 되돌릴 조건

- 명령 3이 실수나 악의로 실행된 일이 한 분기에 한 번이라도 있거나, 사후 검토의 '적절하지 않았다'가 되풀이되면, '전체 범위만 2인' 같은 강화를 새 ADR로 다시 본다.

## 남는 한계

- 두 계정을 한 사람이 쥔다. 그래서 시연은 '시스템이 다른 계정을 요구한다'를 보일 뿐, '다른 사람이 확인했다'를 보이지는 않는다. planning/01 §5.2와 docs/devops.md의 1인 기간 한계는 그대로다.
- 1인 기간에는 명령 3의 사후 검토도 실행자가 직접 검토한다. 명령 11과 같이 감사 로그에 '1인 기간 자기 검토'로 남긴다.
- 데모 도우미가 데모 승인자의 비밀을 들고 있다. 데모 환경의 비밀이 새면 데모 안에서는 누구나 두 번째 승인을 할 수 있다. 데모에는 실제 돈과 개인정보가 없다(가벼운 합성 데이터, 결제사 샌드박스 테스트 키, docs/infra.md 데모 환경 행).
