# ADR-0074: 코드 저장소는 git flow 가지 규칙을 따른다 — 트렁크 기반에서 바꿈, 가지 종류·병합 방식·릴리스와 핫픽스·같은 산출물 승격·버전과 태그·강제 장치(2026-10-20)

- **상태**: 채택 (2026-10-20. 소유자 결정: "git flow 규칙을 추가해주세요. 이 프로젝트는 git flow 규칙을 따르겠습니다." 가지 모델(`main`·`develop`·작업 가지·릴리스 가지·핫픽스 가지)은 소유자 결정이고, 이 프로젝트의 CI·환경 승격·변경 동결에 맞춘 세부(병합 방식, 주기와 수명, 트리 검사, 예외 저장소, 강제 장치)는 추천 적용(2026-10-20)이다. 숫자는 측정 전 가정값이다. ADR-0054 결정 1·3·5의 트렁크 기반, 스쿼시 병합과 선형 이력, 'main 병합 → 이미지 빌드 → 승격', '서비스에는 사람용 버전 번호를 두지 않음'을 바꾼다.) 2026-10-28(기술 검토 낮음-162, 소유자 승인 '추천안 동의'): 결정 3이 git flow 대상에 넣은 문서 저장소는 원격 저장소를 만들기 전까지 예외로 둔다(검토의 안 (가), 추천 적용). 그동안 작업 가지·PR 없이 `develop`에 스쿼시 형식 커밋(작업 하나에 커밋 하나, Conventional Commits 제목)을 바로 쌓는다. 원격이 없어 결정 8의 'PR 필수·필수 검사'를 걸 곳이 없고, 여러 작업 세션이 한 작업 트리를 함께 써서 가지를 바꾸면 다른 세션이 고치던 파일이 섞이기 때문이다. 원격(GitHub `peaket-docs`)을 만든 날부터 결정 3·8과 규칙 세트를 그대로 건다. 원격을 바로 만드는 안 (나)는 공개 게시라 소유자가 정할 일이어서 이 예외로 실제와 규칙을 먼저 맞췄다(docs/devops.md §2.2.5, docs/architecture.md §8.5).

## 맥락

- ADR-0054 결정 3은 트렁크 기반 개발(작업 가지는 몇 시간~1일, 스쿼시 병합, 선형 이력)이었고, 결정 5는 'main 병합 → 이미지 빌드·서명 → 데모 승격 → 운영 승격'이었다. 근거는 DORA 역량 문서였다.
- 2026-10-20 소유자가 git flow를 따르기로 정했다. 원문 모델을 지금 설계에 그대로 옮기면 다음 다섯 곳이 맞지 않는다.
  1. **같은 산출물 원칙**: git flow는 릴리스 가지를 `main`에 병합 커밋으로 넣는다. `main` 병합마다 다시 빌드하면 데모에서 검증한 이미지와 운영에 가는 이미지가 달라진다(ADR-0054 결정 5 '한 번 만든 다이제스트만 승격').
  2. **데모 환경의 역할**: 지금 데모는 `main`의 모든 변경을 받는다. git flow의 `main`은 출시본이라 그대로 두면 데모가 출시가 끝난 뒤에야 변경을 본다.
  3. **병합 방식**: 원문은 모든 병합에 `--no-ff`를 쓴다. 지금 규칙 세트는 스쿼시와 선형 이력을 요구해 릴리스·핫픽스의 병합 커밋을 받을 수 없다.
  4. **원문 저자 메모와 DORA**: 원문 저자는 2020-03-05 메모에서 지속 배포하는 웹 앱이면 GitHub flow 같은 더 단순한 흐름을 권하고, git flow는 명시적으로 버전을 매기거나 여러 판을 함께 지원하는 소프트웨어에 맞는다고 적었다. DORA 역량 문서는 2016·2017 데이터 분석으로 활성 가지 3개 이하, 하루 한 번 이상 트렁크 병합, 코드 동결과 통합 단계 없음을 높은 전달 성과와 연결한다. git flow는 영구 가지 둘과 릴리스 안정화 단계를 두므로 이 조건과 어긋난다. 소유자 결정을 따르고, 이 어긋남은 대가로 기록한다.
  5. **기본 가지와 예약 작업**: GitHub의 예약 워크플로는 기본 가지의 최신 커밋에서만 돈다. 기본 가지를 `develop`으로 두면 운영 상태를 보는 예약 작업(IaC 드리프트 점검)이 출시 전 코드를 운영과 비교하게 된다.
- **외부 원문 확인(2026-10-20 열람)**: Vincent Driessen 'A successful Git branching model'(2010-01-05, 2020-03-05 메모: `master`·`develop` 영구 가지, 작업·릴리스·핫픽스 가지의 시작점과 병합 대상, 릴리스 시작 때 버전을 정함, 릴리스 가지는 버그 수정과 출시 메타데이터만, `master` 병합마다 태그, `--no-ff`의 이유, 열린 릴리스 가지가 있으면 핫픽스를 그 가지로 병합), DORA 'Trunk-based development', GitHub 문서 'Available rules for rulesets'(무료 등급은 공개 저장소에서 규칙 세트, 가지·태그 규칙 세트와 GitHub 앱 우회, 만들기·바꾸기·지우기 제한, 선형 이력은 병합 커밋을 막음, PR 규칙의 병합 방식 지정, 병합 전 배포 성공 요구, 필수 검사의 출처 앱 지정), GitHub 문서 'Events that trigger workflows'(예약 워크플로는 기본 가지에서만), Terraform GitHub 제공자 v6.10.0 릴리스 노트(규칙 세트의 `allowed_merge_methods` 지원), Git 문서 `git merge-tree --write-tree`(작업 트리와 색인을 건드리지 않고 병합 결과 트리를 만들고, 충돌이면 종료 코드 1), Conventional Commits 1.0.0(`fix` → PATCH, `feat` → MINOR, `!`·`BREAKING CHANGE` → MAJOR), SemVer 2.0.0(0.y.z는 초기 개발, 1.0.0이 공개 API를 정의).

## 결정

1. **가지 모델(소유자 결정).** 코드 저장소는 git flow를 따른다. 영구 가지는 `main`(운영 출시 상태, 원문의 `master`)과 `develop`(다음 출시를 모으는 통합 가지, 저장소의 기본 가지)이다. 짧은 가지는 작업 가지(`feature/<ID>-<요약>`, `bugfix/<ID>-<요약>`), 릴리스 가지(`release/X.Y.Z`), 핫픽스 가지(`hotfix/X.Y.Z`)다. 시작점과 병합 대상은 원문대로다: 작업 가지는 `develop`에서 나와 `develop`으로, 릴리스 가지는 `develop`에서 나와 `main`과 `develop`으로, 핫픽스 가지는 `main`의 출시 태그에서 나와 `main`과 `develop`으로 간다(열린 릴리스 가지가 있으면 `develop` 대신 그 가지). 버그 수정 작업 가지는 열린 릴리스·핫픽스 가지에서도 나올 수 있다. 역병합 충돌을 푸는 가지 `merge/<원천>-to-<대상>`을 둔다. 이름은 원문 예(`release-*`, `hotfix-*`)와 달리 종류 접두사를 써서 가지 규칙 검사가 종류를 알게 한다(docs/devops.md §2.2.1).
2. **병합 방식(추천 적용).** 릴리스·핫픽스·역병합은 원문대로 병합 커밋(`--no-ff`)이다. 스쿼시하면 `main`과 `develop`의 이력이 갈라져 다음 병합이 충돌한다. 작업 가지는 원문과 달리 스쿼시 병합이다. 원문이 `--no-ff`로 얻으려던 것(기능 하나의 커밋을 묶어 보이고 통째로 되돌림)을 스쿼시 커밋 하나와 PR 기록이 맡고, Conventional Commits 형식의 PR 제목 하나가 버전 계산과 변경 기록의 단위가 된다. 선형 이력 요구는 뺀다.
3. **적용 범위(추천 적용).** 코드를 담는 13개 저장소(서비스 5개, frontend, platform, contracts, infra, data, loadtest, docs, `.github`)가 따른다. `peaket-gitops`는 예외로 `main` 하나와 환경 디렉터리를 쓴다. GitOps 저장소는 병합이 곧 배포이고 환경 승격은 환경 디렉터리의 다이제스트를 바꾸는 PR이 맡으므로, `develop`·릴리스 가지를 두면 같은 환경의 원하는 상태가 두 벌이 되어 어긋난다. 비공개 `peaket-loadtest`는 GitHub 무료 등급에서 규칙 세트를 쓸 수 없어 관례로만 따른다(운영에 배포하지 않는 저장소). 문서 저장소의 태그는 기획 버전(review §9의 판정)과 별개다.
4. **릴리스(추천 적용).** `develop`에 출시할 변경이 있으면 기본 주 1회 [가정, Phase 4 운영 리허설에서 확정] 릴리스 가지를 자르고, 급한 기능은 주기 밖에서도 자른다. 버전은 자를 때 정한다(원문 규칙). 릴리스 가지의 첫 커밋은 버전 올림과 변경 기록이고, 그 뒤에는 버그 수정과 출시 메타데이터만 받는다. 저장소마다 열린 릴리스 가지는 하나이고 3영업일 [가정, 같은 리허설에서 확정] 안에 마무리한다. 넘기면 닫고(고친 버그는 `develop`으로 역병합) 다음 주기에 다시 자른다. 릴리스를 안정화하는 동안에도 `develop`은 다음 기능을 받는다(코드 동결 없음).
5. **같은 산출물 승격(추천 적용).** 데모는 릴리스·핫픽스 가지의 출시 후보만 받는다. `develop`의 통합 시험은 CI의 kind 클러스터에서 한다. 릴리스·핫픽스 가지 → `main` PR은 필수 검사로 `git merge-tree --write-tree origin/main <후보 커밋>`이 충돌 없이 끝나고 결과 트리가 후보 커밋의 트리와 같아야 병합된다. 다르면 `main`에 후보에 없는 변경(예: 릴리스 가지로 역병합하지 않은 핫픽스)이 있다는 뜻이다. 병합 뒤에는 릴리스 봇이 `main` 병합 커밋의 트리를 다시 확인하고, 같을 때만 태그 `vX.Y.Z`, GitHub Release, 운영 승격 PR(데모에서 검증한 후보 다이제스트, 다시 빌드 없음), 역병합 PR을 만든다. 운영 승격 필수 조건은 ADR-0054 결정 5와 같다. 출시 확정(`main` 병합과 태그)과 운영 배포는 다른 일이다. 변경 동결 창이면 병합과 태그는 되고 운영 승격 PR만 창이 끝날 때까지 기다린다.
6. **핫픽스(추천 적용).** 운영에 나간 출시본의 결함이 SEV1·SEV2의 원인이거나, commander가 다음 정기 릴리스까지 기다릴 수 없다고 판단할 때만 쓴다. 그 밖의 수정은 `develop`으로 간다. 핫픽스도 출시 후보 검증(데모 카나리와 체류)을 거친다. 변경 동결 창 안에서는 운영에 승격하지 않는다(ADR-0054 결정 13 유지. 핫픽스는 긴급 변경이 아니다). 창 안에서는 되돌리기와 릴리스 플래그 끄기로 버티고, 핫픽스는 만들고 데모 검증까지 한 뒤 창이 끝나면 승격한다. 되돌리기는 GitOps 일이라 `main`의 태그는 그대로 두고, 되돌린 출시본은 GitHub Release에 '철회'로 적는다.
7. **버전과 태그(추천 적용).** 모든 저장소는 SemVer 2.0.0이다. 지난 태그 뒤의 커밋 형식으로 정한다: `!`·`BREAKING CHANGE`는 MAJOR, `feat`는 MINOR, `fix`와 그 밖의 형식은 PATCH. 운영 출시 전에는 0.y.z로 두고(호환을 깨는 변경도 y만 올림) 운영 출시 때 1.0.0으로 올린다. 태그는 `main` 병합 커밋의 주석 태그 `vX.Y.Z`이고 릴리스 봇만 만들며 옮기거나 지우지 않는다. 서비스 이미지 태그(`sha-<커밋>`)와 다이제스트 배포는 그대로이고, 사람용 버전은 저장소 태그다. 라이브러리·계약 패키지는 릴리스를 자를 때 Changesets가 패키지 버전을 정하고 `main` 병합 뒤 게시한다. 공용 워크플로(`.github`)를 부르는 저장소는 출시 태그가 가리키는 커밋 SHA로 고정한다.
8. **강제 장치(추천 적용).** GitHub 규칙 세트(Terraform으로 관리)로 `main`은 PR 필수·병합 커밋만·필수 검사(공용 CI, 가지 규칙 검사, 병합 결과 트리 검사)·데모 배포 성공 요구·강제 푸시와 삭제 금지, `develop`은 PR 필수·스쿼시와 병합 커밋·필수 검사·강제 푸시와 삭제 금지, `release/*`·`hotfix/*`는 릴리스 봇만 만들기, 태그 `v*`는 릴리스 봇만 만들기·바꾸기·지우기로 둔다. 가지 규칙 검사는 PR의 머리 가지 종류와 대상 가지가 허용된 쌍인지 본다. 작업 가지는 3일 [가정]을 넘기면 경고하고, 저장소마다 열린 작업 가지는 3개 이하로 둔다. 기본 가지는 `develop`이고, 운영 상태를 보는 예약 작업은 대상 가지를 명시해 체크아웃한다. 가지·태그 작업은 릴리스 봇(GitHub 앱, 개인 키는 `release` 환경의 비밀)이 공용 워크플로로 하고, 규칙 세트 우회 목록에는 이 앱만 둔다. git-flow 명령줄 도구는 쓰지 않는다. 1인 기간에는 소유자가 릴리스 시작·마무리 워크플로를 실행한다.
9. **함께 바뀌는 것(추천 적용).** IaC 비운영 적용은 `develop` 병합 뒤, 운영 적용은 `main` 병합 뒤다. 계약 대조는 데모 승격 때 계약 저장소 `develop`의 Pact까지, 운영 승격 때 `main`(출시된 계약)의 Pact로 본다. DAST는 출시 후보마다 데모에서, 야간에는 `develop` 빌드를 CI의 kind에서 돌린다. 축소 성능 시험은 `develop` 야간이다. DORA 지표의 정의는 그대로이고 리드타임에 릴리스 대기가 들어간다. 파이프라인 지표에 릴리스 가지 수명, 역병합 충돌 수, 3일 넘은 작업 가지 수, `develop` 깨짐 시간을 더한다. 시험 D-T21~D-T26, 용어 6개(git flow, 작업 가지, 릴리스 가지, 핫픽스, 역병합, 출시 후보), WBS +2.5일 [가정](0.1.1 +0.5, 0.1.2 +1.5, 0.4.4 +0.5)을 더한다.

| 원문대로 작업 가지도 `--no-ff` | 스쿼시로 같은 목적(기능 묶음, 통째 되돌림)을 얻고 버전·변경 기록 계산이 커밋 하나로 단순해진다. 소유자가 원문 그대로를 원하면 `develop` 규칙 세트의 허용 방식을 병합 커밋으로 바꾸고 모든 커밋에 Conventional Commits 검사를 걸면 된다 |
| `main` 병합 뒤 다시 빌드해 운영에 | 데모에서 검증하지 않은 산출물이 운영에 간다. 같은 산출물 원칙(ADR-0054 결정 5)을 깬다 |
| `develop`을 데모에 계속 배포하고 출시 후보는 스테이징에 | 스테이징은 측정 캠페인 때만 띄운다(ADR-0057). 상시로 띄우면 지출 상한을 넘는다 |
| GitOps 저장소도 git flow(`develop` = 데모, `main` = 운영) | 환경의 원하는 상태가 가지마다 한 벌씩 생겨 어긋나고, 환경 디렉터리 승격과 겹친다 |
| git-flow 명령줄 도구 | 가지 병합과 태그를 로컬에서 만들어 밀어 넣는 방식이라 PR 필수·필수 검사·규칙 세트와 맞지 않는다. 같은 일을 공용 워크플로가 PR로 한다 |

## 결과와 트레이드오프

- **얻는 것**: 출시 단위(버전, 태그, 변경 기록, GitHub Release)가 분명해진다. 운영에 나간 판과 다음 판을 나눠 관리하고, 운영 결함을 다음 기능과 섞지 않고 핫픽스로 고친다. 데모에서 검증한 후보만 운영에 가는 길이 트리 검사로 기계적으로 지켜진다.
- **대가**:
  - 변경 리드타임에 릴리스 대기(주기 최대 1주와 릴리스 수명 최대 3영업일)가 더해진다. 역병합 충돌과 릴리스 관리 작업이 생긴다.
  - DORA가 높은 성과와 연결한 '활성 가지 3개 이하, 하루 한 번 트렁크 병합, 통합 단계 없음'과 어긋난다. 영구 가지가 둘이고 릴리스 안정화가 통합 단계다. 작업 가지를 하루 한 번 이상 `develop`에 병합하고 릴리스 수명을 짧게 두는 것으로 줄인다.
  - WBS +2.5일(Phase 0).
- **남는 한계**(planning/01 §5.2, docs/devops.md §15, 쉬운 설명서 16편):
  - 1인 기간에는 릴리스를 자르고 마무리하는 사람과 검토자가 같은 사람이다.
  - 규칙 세트는 대상 가지 단위로 병합 방식을 정하므로, `develop`에 작업 가지를 병합 커밋으로 넣는 실수는 막지 못한다. 역병합은 봇만 하고, 주간 점검이 `develop`의 병합 커밋 가운데 두 번째 부모가 릴리스·핫픽스·역병합 가지가 아닌 것을 경고한다.
  - 비공개 `peaket-loadtest`에는 규칙이 강제되지 않는다.
  - PR 병합은 GitHub가 하므로 병합 전 계산한 트리와 실제 병합 결과가 같은지를 병합 뒤에 다시 확인하고, 다르면 태그와 승격을 멈춘다.
