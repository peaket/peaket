# ADR-0163: 관리 계정 관리 API를 ops-svc를 거쳐 identity-svc가 처리하게 정하고, 스캐너 승인 화면의 파트너 이름은 회차 공개 요약에서 읽는다(소유자 결정, 2026-10-30)

- **상태**: 채택 (2026-10-30. 소유자가 review/open-items.md 73·78번의 추천을 "A B C 는 추천대로 해주시고요"라고 정했다. 지금 경로를 넣는 것과 새 내부 호출을 만들지 않는 것은 소유자 결정이다. 경로 모양, 처리 경로, 재초대 까닭, 공개 요약의 칸은 추천 적용이다.)
- **관련**: ADR-0008(클라이언트별 게이트웨이), ADR-0102(비상 접근), ADR-0148(내부 gRPC 초안), ADR-0157(인증 통제·권한 표), POL-020(관리 계정), POL-037(판매 구조와 판매자 신원정보), [docs/features/identity.md](../features/identity.md) §6·§6.1, [docs/security/authz-matrix.md](../security/authz-matrix.md) §6.1, [docs/security/auth-controls.md](../security/auth-controls.md) §3.2, [docs/api/openapi.yaml](../api/openapi.yaml)

## 맥락

- 관리 계정·세션 관리 화면(SCR-064)이 있는데, openapi에는 그 경로가 하나도 없었다. 서비스 사이 호출 `TerminateAdminSessions`와 지정 기록 표만 있었다(2026-10-30 API 계약 반영에서 찾음).
- 스캐너 기기 승인 화면(SCR-051)은 배정 파트너 이름을 보이는데, identity-svc가 기기를 찾는 응답에는 파트너 ID만 있다. 파트너 상호는 core 논리 DB의 `promoter`에 있다.
- 공개 회차 정보를 읽는 경로가 openapi에 없었다.
- 전자상거래법 제20조 제2항은 통신판매중개업자가 판매자의 신원정보를 청약 전에 소비자에게 제공하라고 한다(2026-10-30 원문 확인). 「개인정보의 안전성 확보조치 기준」 제5조 제3항은 권한 부여·변경·말소 내역을 3년 보관하라고 한다.

## 결정

1. **관리 계정 관리 경로를 넣는다(소유자 결정, 73번)**
   - 운영자 쪽 경로는 `/v1/ops/admin-accounts`와 그 아래 경로 10개(작업 12개)다:
     - 목록·상세, 초대
     - 역할 변경(PUT `/role`, If-Match)
     - 재초대(`/invitation`), 삭제(POST `/removal`, 사유 필요)
     - 지정·거두기(`/designations`, `/designations/{kind}`)
     - 세션 목록·강제 종료(`/sessions`, `/sessions/{sessionId}`)
     - 권한 내역(`/permission-changes`)
   - 파트너 관리자는 자기 팀 계정을 보기만 한다(`GET /v1/partner/team-accounts`).
2. **처리 경로는 gw-ops → ops-svc → identity-svc `AdminAccountService`다**
   - ops-svc가 역할·재인증을 보고 감사 기록을 남긴 뒤 identity-svc를 부른다. 세션 강제 종료가 이미 이 모양이다. 권한 내역 3년은 ops 감사 저장소에 두고, commander 2인 승인은 ops의 승인 업무이기 때문이다.
   - identity-svc는 요청자의 지금 역할을 DB로 다시 보고, 자기 자신은 바꾸지 못하게 하며, 파트너사의 마지막 partner_admin은 지우거나 역할을 바꾸지 못하게 지킨다. 15분 액세스 토큰의 옛 역할로 통과하는 틈을 막는다(authz-matrix §5.4).
3. **역할과 계정의 규칙**
   - commander는 초대로 주지 않는다. 역할 변경 202 → 승인 업무 `COMMANDER_ROLE_CHANGE`의 2인 승인으로만 준다. commander 계정은 역할을 먼저 거둔 뒤 지운다.
   - 파트너 역할과 관제 역할 사이는 바꾸지 않고, 파트너사도 바꾸지 않는다(삭제 뒤 새 초대).
   - partner_admin이 없는 파트너사에는 partner_admin으로만 초대한다.
   - 파트너 계정 삭제는 operator 이상이 한다(planning/03 §3의 빈칸을 같은 행의 초대·역할 변경 권한에 맞춤).
4. **재초대 까닭 셋**
   - RESEND는 링크를 다시 보낸다.
   - PROTECT_LOCK(보호 잠금 해제)과 CREDENTIAL_LOST(인증 수단 분실)는 패스키까지 포함한 인증 수단을 모두 지우고 다시 묶는다.
   - 링크는 등록된 업무 이메일로만 간다. 운영자가 받는 주소를 바꾸지 못한다.
5. **재인증·동시 수정·가림**
   - 세션 강제 종료를 뺀 쓰기는 모두 패스키까지 거친 재인증이다. 세션 강제 종료는 재인증 없이 휴대폰에서도 한다(안전 조치).
   - If-Match는 역할 변경만 받는다(`admin_account.version`). 상태를 바꾸는 나머지 쓰기는 지금 상태로 판정해 409다.
   - 목록·상세는 가린 이메일만 주고, 세션 목록에는 IP를 싣지 않는다.
   - 삭제하면 상태는 REMOVED가 되고, 업무 이메일과 인증 수단을 바로 파기한다. 행에는 ID·역할·삭제 시각만 3년 남긴다.
6. **스캐너 승인 화면의 파트너 이름은 회차 공개 요약에서 읽는다(소유자 결정, 78번)**
   - 새 내부 호출은 만들지 않는다.
   - 공개 경로 `GET /v1/events/{eventId}`(회차 공개 요약)를 새로 두고 상호 칸 `sellerName`을 넣는다. 상호는 판매자 신원정보로 공개 대상이다(전자상거래법 제20조 제2항, POL-037). 나머지 신원정보 항목은 공연 상세 계약 때 더한다.
   - 캐시는 `max-age=300, stale-if-error=86400` [가정]이다.
   - 기기 조회는 그 기기 파트너 회차의 유효 배정만 준다. 없으면 403 셋(배정 없음, 다른 파트너 기기, 운영 시간 밖) 가운데 하나다.
   - 공개 요약이 404(판매 승인 전·판매 중지 중)면 화면은 이름 없이 보이고 승인은 막지 않는다. 파트너 대조는 서버가 따로 한다.

7. **함께 정한 것(2026-10-30 후속 정리, 추천 적용)**
   - 관리 계정에 표시 이름 `display_name`(30자 [가정], 초대 때 필수, 삭제 때 바로 파기)을 둔다. 팀 계정, CS 처리함 담당자, 명단 내려받기 이력에 이름 칸이 이미 있었다.
   - 승인 업무에 바꿀 역할 칸(`approval_request.requested_role`, openapi `ApprovalRequest.requestedRole`)을 둔다. commander 역할 변경의 승인 업무가 새 역할을 담는다.

## 검토한 대안

- **gw-ops가 identity-svc로 바로 넘기기**: 감사 기록과 2인 승인이 ops-svc에 있어 두 곳에서 같은 일을 하게 된다. 기각.
- **계정 PATCH와 DELETE로 모두 처리하기**: 사유·재인증·승인이 동작마다 달라 한 경로에 섞인다. 기각.
- **보호 잠금 재초대에서 패스키는 남기기**: 잠금 원인이 인증 수단 탈취일 수 있다. 기각.
- **기기 조회 응답에 파트너 이름 싣기**: identity-svc가 core의 상호를 읽는 새 내부 호출이 필요하다(소유자가 뺀 안). 기각.
- **공개 요약에 판매자 신원정보 7항목을 모두 싣기**: 스캐너 화면에는 상호만 필요하고, 나머지는 공연 상세 계약에서 함께 정한다. 기각(나중에 더함).

## 결과와 트레이드오프

- 관리 계정의 생애(초대부터 삭제까지)가 계약으로 닫힌다. 초대 수락 때 인증 수단을 등록하는 경로는 wbs 0.2.3에서 패스키 등록과 함께 정한다.
- 현장 스태프 초대 화면의 파트너·회차 이름은 같은 문제가 남는다(review/open-items.md 80번).

## 되돌릴 조건

- 승인 업무의 2인 승인이 commander 역할 변경에 맞지 않는 것으로 드러나면(예: 기한·증빙), commander 역할 변경용 승인 종류를 따로 둔다.
