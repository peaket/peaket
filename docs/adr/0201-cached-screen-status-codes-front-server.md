# ADR-0201: 캐시 화면의 404·410 상태 코드는 화면이 그린 상태 표시를 앞 서버가 읽어 맞추고, 공연 상세의 없는 회차는 proxy가 먼저 거른다

- **상태**: 채택(2026-11-05, 추천 적용. wbs 2.10.1 세부는 추천 적용이라는 승인 2026-10-14·2026-10-28). BUILD_ORDER HOT-311. ADR-0200 결정 3의 판정 방법을 이 결정으로 바꾼다.
- **관련**: ADR-0193(응답 때 해시, 앞 서버), ADR-0200(공연 상세 계약), [docs/frontend.md](../frontend.md) §2.5, [apps/web/server/csp-hash-server.mjs](../../apps/web/server/csp-hash-server.mjs), [apps/web/proxy.ts](../../apps/web/proxy.ts)
- **관련 ID**: FR-052, SCR-002, POL-029

## 맥락

- 소비자 웹은 Cache Components를 켰다(HOT-290). 이때 화면이 `notFound()`를 불러도 메타데이터 등이 먼저 흘러 응답은 200에 `noindex`가 된다(Next.js 'Status codes', 2026-11-04 확인). 화면(서버 컴포넌트)은 응답 머리도 바꾸지 못한다.
- ADR-0200 결정 3은 공연 상세의 404·410을 `proxy.ts`가 서버 API에 물어 본문이 흐르기 전에 판정한다고 했다. 그런데 Next.js 16.4의 `NextResponse.rewrite`는 상태 코드를 넘기지 않는다(`next/dist/server/lib/router-utils/resolve-routes.js`가 재작성 응답의 상태를 버린다, 2026-11-05 확인). proxy가 응답 머리로 상태를 알리면 proxy의 기억(60초)과 화면의 ISR 데이터(300초)가 잠깐 어긋날 때 판매 중지 응답에 옛 본문이 실린다.
- 캐시 화면(묶음 A)의 HTML은 모두 앞 서버(ADR-0193)를 지나고, 앞 서버는 인라인 스크립트 해시를 내려고 HTML을 끝까지 모은 뒤에 머리를 쓴다.

## 결정

1. **화면이 상태 표시를 그린다**: 공연 상세의 판매 중지 안내는 `<meta name="peaket-status" content="410">`을 화면 내용으로 그린다. not-found 화면(SCR-059 404)도 `content="404"`를 그린다. 값은 404·410 둘뿐이다. 다만 화면 안에서 `notFound()`를 부르면 not-found 화면은 화면 데이터(RSC)로만 흘러 HTML에 표시 태그가 실리지 않는다(2026-11-05 실측: 첫 응답 200 `no-store`, 그 뒤 Next.js가 ISR로 기억한 404). 그래서 표시로 상태를 맞추는 것은 안내를 화면 내용으로 그리는 경우(판매 중지)이고, 없는 회차는 결정 3의 앞 거르기가 맡는다. 화면 글(설명 글·후기 등)은 이 표시를 만들 수 없다: 본문의 글은 React가 `<`를 바꿔 쓰고(asvs/frontend.md 1.2.1), 인라인 화면 데이터는 Next.js가 `<`를 `\u003c`로 바꿔 싣는다. React가 표시 태그를 `<head>`로 옮기지 않고 본문 흐름에 넣어도 같은 태그 글자다.
2. **앞 서버가 맞춘다**: 앞 서버(`csp-hash-server.mjs`)는 해시를 내려고 모은 HTML에서 처음 나온 상태 표시 태그(글자 그대로의 `<meta name="peaket-status" content="…"/>`)를 읽어, 위 서버의 상태가 200일 때만 그 값으로 바꾼다. 그때 `Cache-Control`은 `public, max-age=60` [가정]이다(공개가 시작되거나 판매가 다시 열리면 1분 안에 보이게, CDN도 같은 시간만 담는다). 해시를 내지 않는 응답(HTML이 아니거나 2MB를 넘는 본문, 304·HEAD)은 바꾸지 않는다. 화면 이동(RSC 데이터)은 상태 코드를 쓰지 않는다.
3. **없는 회차는 proxy가 먼저 거른다**: `proxy.ts`는 `/events/{id}`에서 ID 모양(UUID)이 틀리면 바로, 모양이 맞으면 서버 API(`GET /v1/events/{eventId}`)에 물어 404이면 어떤 경로에도 맞지 않는 내부 주소로 재작성한다(Next.js가 404 화면을 낸다). 없는 ID를 바꿔 넣는 요청마다 회차 주소별 ISR 항목이 생기지 않게 하려는 것이다. 시간 초과 300ms [가정], 실패하거나 시간을 넘기면 그대로 통과(원본 장애 때 POL-029 고정 문구·`stale-if-error`를 막지 않는다), 결과는 60초 [가정]·1만 개 [가정]까지 기억한다. 200과 410은 통과시키고 410은 화면이 그린다(결정 1·2).
4. **앞 서버가 없는 실행**: 개발 서버(`next dev`)와 앞 서버 없이 띄운 `next start`는 상태가 200으로 남는다. 화면은 같다. 운영과 화면 검사(`tools/web-checks`)는 앞 서버를 거친다(`apps/web/server/start.mjs`).

## 결과

- 공연 상세의 없는 회차는 앞 거르기로 404, 판매 중지는 410이고 본문과 상태가 같은 데이터에서 나온다. 앞 거르기가 원본 장애로 통과시킨 없는 회차는 화면 안 `notFound()`라 첫 응답 200(`no-store`), 그 뒤 Next.js의 404다.
- 상태 표시를 바꾸는 일은 앞 서버 한 곳이 한다. 다른 캐시 화면(문서·굿즈 상세 등)의 화면 안 `notFound()`는 여전히 200이다(HOT-290에서 남은 문제). 그 화면을 데이터에 잇는 단계가 없는 값을 앞 거르기나 화면 내용 안내로 다룬다.
- HEAD 요청은 앞 서버가 본문을 보지 않아 판매 중지 회차도 200이다(GET만 410).

## 다른 선택지

| 길 | 고르지 않은 까닭 |
| --- | --- |
| proxy가 응답 머리로 상태를 알린다 | proxy의 기억과 화면의 ISR 데이터가 잠깐 어긋나면 410 응답에 옛 본문이, 200 응답에 판매 중지 안내가 실린다 |
| proxy가 상태를 붙여 재작성한다 | Next.js가 재작성 응답의 상태를 버린다 |
| 판매 중지 안내를 따로 공개 경로로 두고 재작성한다 | 그 경로를 직접 열면 어느 공연에도 '판매 중지' 안내가 보인다 |
| Cache Components를 끈 앱으로 상세를 옮긴다 | 화면 묶음을 둘로 나눠 배포하고, 정적 셸 이득을 잃는다(docs/frontend.md §2.5 Cache Components) |
