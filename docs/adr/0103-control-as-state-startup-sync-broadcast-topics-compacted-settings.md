# ADR-0103: 제어는 메시지가 아니라 상태다 — 판매 일시정지·운영 설정·종료 세션 목록을 새로 뜬 파드도 받게 한다(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 높음-10 '판매 일시정지(킬스위치)·세션 무효화·운영 설정이 그 순간 떠 있는 파드에만 걸린다'에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 방향은 소유자 결정(추천안 승인)이고, 상태를 두는 곳·판 번호·시작 작업·압축 설정·기준값 같은 세부는 추천 적용이다. ADR-0011 결정 2(종료 세션 목록을 각 서비스가 메모리에 둔다)에 '모든 파드가 받고, 뜰 때 15분을 다시 읽는다'를 더하고, ADR-0022의 '파드 전체에 밀어 넣고 모두 ack하면 끝'을 '상태를 먼저 두고, 집행하는 모든 곳이 그 판을 적용하면 ack'로 바꾼다. ADR-0056 결정 4의 리더 상태 규칙을 다른 대상에도 넓힌다) 2026-10-28(ADR-0121, 소유자 승인 '추천안 동의'): 결정의 '좌석 Redis 장애 전환 중(DB 정렬 잠금 경로)'은 'DB 경로 없이 그 회차의 구매 요청을 503으로 미루는 동안'으로 읽는다. 결제 시도·접수의 정지 확인을 파드 메모리로 하는 것과, 장애 조치가 끝나면 다시 맞춤이 사본을 다시 쓰는 것은 그대로다. 전체 장애 뒤 비트맵 다시 만들기는 사본을 `sale_control`로 다시 쓴 뒤 세대 키를 쓴다. 2026-10-29(ADR-0143, 소유자 결정 '추천대로 반영'): 결정 5의 ack 대상에 명령 6 대체 결제사 전환을 받는 payment-svc 모든 파드(payment DB `pg_switch`)를 더한다. 나머지 설정형 명령(5·6의 나머지·7 purchase-svc 공지·8·9·12)은 ack 대신 받는 파드가 낸 적용 판 번호 지표로 30초 [가정] 안에 확인한다. `control.settings`와 `control.sessions-terminated`는 각 서비스 Outbox로 낸다. 2026-10-29(원문 확인): 인용한 Kafka 4.1 토픽 설정 문서의 내용(압축 토픽 기본값과 보장)은 Kafka 3.9 문서에서도 같다(review/open-items.md 62). 2026-11-01(BUILD_ORDER FND-090, openspec 변경 add-maintenance-control-and-consumers): 결정 2·3의 시작 작업·방송형 읽기·다시 맞춤·지표를 서비스 템플릿에 만들었다. 준비 표시는 관리 포트 `/ready`이고, 설정의 판 번호는 `SettingChanged`에 판 칸이 없어 `occurredAt`(밀리초)으로 읽으며, 방송형 소비자 그룹 이름은 토픽마다 `<서비스>-<파드 이름>.<토픽>`이다. 이 서비스의 로그 수준 설정은 플랫폼이 바로 적용한다(추천 적용). 온세일 구간의 로그 표본 비율 연결은 신호 출처가 없어 미해결이다(docs/PROGRESS.md OPEN[09]). 2026-11-01(정합 점검, ADR-0177 해설서 검토 세 번째 묶음): 결정 3의 소비자 그룹 이름 `<서비스>-<파드 이름>`은 위 줄대로 토픽마다 `<서비스>-<파드 이름>.<토픽>`으로 읽는다. 서비스 템플릿(packages/platform `stream-worker.ts`)이 이 이름을 쓴다(docs/features/identity.md §3).

## 맥락

- **판매 일시정지(명령 3, 킬스위치)**: ops-svc가 그 순간의 purchase-svc 파드 전부에 보내고 모두 ack하면 ACKED다(docs/features/control-tower.md §3). 그런데 정지 상태를 어디에 두는지, 명령 뒤 오토스케일·재시작으로 새로 뜬 파드가 그 상태를 어떻게 받는지가 정본에 없다. admission-ctrl만 상태를 `q:{event:E}:ctl`·`q:{admission}:ctl`에 쓴 뒤 ack한다(ADR-0056·0062). 새 파드는 정지를 모른 채 홀드와 결제를 받는다. 킬스위치는 이중 결제 의심 같은 최악의 순간에 쓰는 장치이고, 그런 장애 중에는 파드 재시작과 확장이 흔하다.
- **종료 세션 목록**: 로그아웃·탈퇴·강제 종료로 끝난 세션은 각 파드 메모리의 목록에 15분 둔다(ADR-0011 결정 2, docs/features/identity.md §3). 한 서비스의 파드들이 소비자 그룹 하나를 나눠 쓰면 이벤트가 그 그룹의 파드 하나에만 간다. 새로 뜬 파드는 빈 목록으로 시작해 최대 15분 동안 끝난 세션의 토큰을 받는다.
- **운영 설정 토픽**: `control.settings`(봇 판정 강도, 로그 레벨, 기능 플래그, Degraded, 결제사 지정 등)는 보존 7일이고 키와 압축 정책을 정하지 않았다(docs/api/avro/README.md §5). 8일 전에 끈 기능 플래그는 새 파드가 알 수 없다.
- **확인한 사실(2026-10-28, Apache Kafka 4.1 토픽 설정 문서)**: `cleanup.policy`의 기본값은 `delete`이고, `compact`는 키마다 마지막 값을 남긴다. 지우는 표시(값이 빈 메시지)는 `delete.retention.ms`(기본 1일) 동안 남는다. `min.compaction.lag.ms`는 메시지가 압축되지 않고 남는 최소 시간이다. `segment.ms` 기본값은 7일이다.

## 결정

1. **제어는 '메시지'가 아니라 '상태'다(소유자 결정 '추천안 동의').** 명령마다 범위(전체·회차)와 종류의 현재 상태와 **판 번호**(그 범위·종류에서 늘어나기만 하는 수)를 둔다. 바라는 상태의 원천은 ops-svc 명령 원장이다. 적용한 상태는 받는 서비스가 자기 저장소에 둔다. 제어 gRPC 전달(ADR-0102 결정 1)은 그 상태를 빨리 퍼뜨리는 길이다.

   | 명령(받는 쪽) | 적용한 상태를 두는 곳 | 집행 |
   | --- | --- | --- |
   | 명령 3(purchase-svc) | purchase DB `sale_control`(범위, 일시정지 여부, 판 번호, 명령 ID, 바꾼 시각)이 원본이고, 좌석 Redis `s:{event:E}:ctl`이 사본이다 | 홀드 Lua가 사본을 함께 읽어 423을 낸다. 결제 시도·결제 접수는 같은 상태를 파드 메모리로 확인한다(결정 2) |
   | 명령 1·2·3·6(대기열 진입)·11(admission-ctrl) | `q:{event:E}:ctl`·`q:{admission}:ctl`(지금 그대로, ADR-0056) | 리더 루프 |
   | 명령 3·7(queue-svc) | 대기열 Redis `q:{event:E}:notice`(판매 상태, 공지 템플릿, 판 번호) | 대기 상태 파일을 만들 때(1초) 읽는다 |
   | 명령 5·6(진입 밖)·7(purchase-svc 공지)·8·9·12 | 압축 토픽 `control.settings`(결정 4) | 서비스 메모리 |

   - 받는 쪽은 판 번호가 지금 것보다 클 때만 적용한다(비교하고 쓰기). 같은 판을 다시 받으면 적용한 판 번호만 돌려준다.
   - 좌석 Redis 사본 `s:{event:E}:ctl`은 그 회차에 걸린 정지(회차 범위 또는 전체 범위)를 담는다. 전체 범위 정지는 purchase-svc가 판매 중인 모든 회차(좌석 비트맵이 있는 회차의 목록 `s:ctl:events`)의 사본에 쓴다. 회차의 좌석 비트맵을 처음 만들 때는 그 회차를 목록에 먼저 넣고, 그다음 전체 범위 상태를 읽어 사본을 쓴다. 전체 정지는 전체 상태를 먼저 쓰고, 그다음 목록을 돈다. 그래서 둘이 동시에 일어나도 어느 한쪽이 정지를 본다.
   - 좌석 Redis 장애 전환 중(DB 정렬 잠금 경로, docs/features/seat-hold.md §9)에는 파드 메모리 상태로 확인한다. 장애 전환이 끝나면 다시 맞춤(결정 2)이 사본을 DB 원본대로 다시 쓴다.
   - queue-svc의 전체 범위 상태는 회차 자리에 `PLATFORM`을 쓴 키(`q:{event:PLATFORM}:notice`)에 둔다. 대기 상태 파일을 만드는 작업이 회차 키와 전체 키를 함께 읽어, 하나라도 일시정지면 일시정지로 쓴다. 홀드 Lua처럼 같은 샤드의 원자 판정이 필요하지 않아, 회차마다 사본을 쓰지 않는다(docs/data.md §3).

2. **파드는 시작할 때 셋을 읽어야 준비 상태가 된다(추천 적용, peaket-platform).** 플랫폼 라이브러리의 시작 작업에 아래 셋을 두고, 다 끝나야 준비 표시를 켠다. 준비 프로브는 그 표시만 본다. 프로브가 공유 의존성을 부르지 않는다는 규칙(ADR-0070)은 그대로다.
   1. **제어 상태**: 받는 서비스는 자기 저장소의 제어 상태를 읽는다(purchase-svc는 `sale_control`). 읽지 못하면 준비 상태가 되지 않는다. 정지 여부를 모르는 파드는 홀드를 받지 않는다.
   2. **설정**: 압축 토픽 `control.settings`를 처음부터, 시작할 때 잰 끝 위치까지 읽는다.
   3. **종료 세션 목록**: `control.sessions-terminated`를 '지금 − 15분'의 위치(Kafka의 시각으로 위치 찾기)부터 끝 위치까지 읽는다.

   - 2와 3은 Kafka에 닿지 못하면 30초 [가정]를 기다린 뒤 준비 상태로 간다. 설정은 마지막으로 받은 값(처음 뜬 파드면 배포에 든 기본값)을 쓰고, 종료 세션 목록은 Kafka가 돌아오면 '지금 − 15분'부터 다시 읽는다. 따라잡을 때까지 SEV2(`control_sync_lagging{kind}`)를 낸다. Kafka가 멈춘 동안 확장까지 막지 않으려는 것이다(남는 한계).
   - 시작한 뒤에는 2초 [가정]마다 제어 상태를 다시 읽어 맞추고, 설정과 종료 세션은 계속 읽는다. 메모리와 저장소가 다르면 판 번호가 큰 쪽을 따른다.
   - 준비 상태가 된 뒤에 의존성이 멈춰도 준비 상태를 내리지 않는다(ADR-0070).

3. **방송형 토픽은 파드마다 따로 읽는다(추천 적용).** `control.settings`와 `control.sessions-terminated`는 모든 파드가 모든 파티션을 읽는다. 소비자 그룹은 파드마다 다른 이름(`<서비스>-<파드 이름>`)이거나, 그룹 없이 모든 파티션을 직접 배정한다. 오프셋은 커밋하지 않는다(다시 뜨면 결정 2대로 다시 읽는다). 소비 지연 `control_consumer_lag_seconds{topic}`이 10초 [가정]를 넘으면 SEV3, 60초 [가정]를 넘으면 SEV2다.

4. **`control.settings`는 압축 토픽이다(추천 적용).**
   - `cleanup.policy=compact`. 메시지 키는 `<범위>:<종류>:<대상>`이다. 대상은 기능 플래그 이름, 로그 레벨을 바꿀 서비스, Degraded 모드 이름이고, 없으면 비운다(예: `PLATFORM:FEATURE_FLAG:reviews`, `E123:PG_ASSIGNMENT:`). 같은 키는 같은 파티션에 가므로 한 설정의 변경 순서가 지켜진다.
   - 설정을 없앨 때는 값이 빈 지우는 표시를 낸다. 지우는 표시는 7일 [가정](`delete.retention.ms`, 기본 1일보다 길게) 남겨, 일주일 안에 다시 읽는 소비자도 지운 것을 안다.
   - `min.compaction.lag.ms`는 1일 [가정]이다. 하루 안의 변경은 모두 남아 분석 원본 적재(analytics-ingest)가 밀려도 잃지 않는다.
   - `expiresAt`이 지난 값은 받는 쪽이 무시한다. ops-svc는 만료 때 되돌린 값을 다시 낸다.
   - Kafka 사건 토픽 보존 7일(docs/observability.md §9)의 예외다.

5. **ack의 뜻을 바꾼다(추천 적용, ADR-0022·0062).** 판 N의 ack는 '그 받는 쪽에서 집행하는 곳이 모두 판 N 이상을 적용했다'이다.
   - purchase-svc: DB 원본과 Redis 사본, 그리고 준비된 파드 전부.
   - admission-ctrl: 리더의 `q:{event:E}:ctl`(지금 그대로).
   - queue-svc: `q:{event:E}:notice`(파일 생성이 1초 안에 읽는다).
   - ops-svc는 EndpointSlice의 준비된 파드를 모두 부르고(제어 gRPC), 모두 판 N 이상이라고 답하면 목록을 다시 읽어 그사이 준비된 파드도 부른다. 새 파드는 시작할 때 저장소를 읽으므로(결정 2) 판 N 이상이다. 그래서 ACKED 뒤에 뜬 파드도 정지를 안다.
   - 명령 상태 표시(ack 3초 '전파 지연', 10초 실패)는 그대로다(ADR-0073).

6. **시험(추천 적용).**
   - C-T50 '킬스위치 중 확장·재시작': 명령 3이 ACKED인 회차에서 purchase-svc를 둘에서 여섯으로 늘리고, 다른 시험에서는 파드 하나를 강제로 다시 시작한다. 새 파드의 홀드·결제 시도·결제 접수는 모두 423이다. 다른 회차는 그대로 판다. 좌석 Redis 사본을 지워도 2초 [가정] 안에 다시 써진다.
   - C-T51 '오래 끈 기능 플래그': 관람 후기 기능 플래그를 끄고 시계를 8일 넘긴 뒤 core-svc를 다시 시작하면, 새 파드에서도 꺼져 있다. 만료가 지난 로그 레벨 값은 무시된다.
   - I-T48 '새 파드의 종료 세션': 로그아웃 직후(1초 안) 뜬 파드에서도 그 세션의 요청이 거부되고, 같은 서비스의 모든 파드가 그 이벤트를 받는다. Kafka를 막은 채 뜬 파드는 30초 뒤 준비 상태가 되고 SEV2가 뜨며, Kafka가 돌아오면 15분 창을 다시 읽어 거부한다.
   - D-T29 '시작 작업과 준비 상태': 시작 작업 셋이 끝나기 전에는 준비 상태가 아니고, 준비 프로브는 공유 의존성을 부르지 않는다(D-T19와 함께 템플릿 시험).

## 결과와 트레이드오프

- 킬스위치가 확장·재시작으로 새 파드에서 풀리지 않는다. ACKED는 '그 순간의 파드'가 아니라 '집행하는 모든 곳'에 대한 약속이 된다.
- 로그아웃·탈퇴가 서비스의 모든 파드와 새 파드에 걸린다. 오래 유지된 설정이 7일 보존에 지워지지 않는다.
- 대가:
  - 파드 시작이 시작 작업만큼 늦다(종료 세션 15분 되감기와 설정 압축 토픽 읽기). 시간은 측정 전이다.
  - 파드마다 다른 소비자 그룹이라, 그룹 수가 파드 수만큼 생긴다(커밋하지 않으므로 오프셋은 남기지 않는다).
  - 받는 쪽마다 상태 저장과 2초 다시 맞춤을 만든다.

## 되돌릴 조건

- 종료 세션 15분 되감기가 파드 시작을 10초 [가정] 넘게 늦추면, 되감기를 준비 상태 뒤로 미루고 그동안 그 파드의 요청을 identity-svc 세션 확인으로 받는 방식을 검토한다.
- 받는 파드의 과부하로 ack가 자주 늦으면(C-T48에서 p99 3초를 넘으면) 대안 B를 다시 본다.

## 남는 한계

- Kafka가 멈춘 동안 뜬 파드는 설정의 마지막 값(처음 뜬 파드면 기본값)과 비어 있는 종료 세션 목록으로 시작할 수 있다. 최대 15분이고 SEV2로 보인다.
- 결제 시도·결제 접수의 정지 확인은 파드 메모리라 ACKED 전에는 다시 맞춤 주기(2초 [가정])만큼 늦을 수 있다. ACKED 뒤에는 모든 준비된 파드가 적용했다.
- 전체 범위 정지는 판매 중인 회차 목록에 기대어 사본을 쓴다. 목록에서 빠진 회차는 파드 메모리 확인으로만 막힌다.
- 압축은 바로 일어나지 않아, 토픽이 압축 주기만큼 크다(설정 수가 적어 작다).
