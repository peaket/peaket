# ADR-0101: 상품 정의를 MongoDB에서 PostgreSQL `product` 표(JSONB 속성)로 옮기고 MongoDB를 운영 설계에서 뺀다(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 높음-06 '굿즈 상품 정의 하나 때문에 MongoDB를 직접 운영하고, 백업 주장은 사실과 다르다'에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 방향은 소유자 결정(추천안 승인)이고, 표 모양·인덱스·검사 규칙·일정 같은 세부는 추천 적용이다. ADR-0013의 결정 1·4를 대신하고, 결정 2·3은 그대로 이어받는다) 2026-11-01(정합 점검, ADR-0177 해설서 검토 네 번째 묶음): 맥락의 '`/shop/[productId]` 300초, docs/frontend.md §3'의 자리는 frontend §2.5 '경로별 렌더링·캐시·헤더 표'다. 결과와 되돌릴 조건의 'identity·ops와 같은 Aurora 공유 클러스터'는 identity와 같은 공유 클러스터(identity·core 논리 DB)로 읽는다. ops는 같은 날 ADR-0102로 전용 클러스터에 나갔다(docs/data.md §1).
- **관련**: ADR-0007(core-svc의 shop 모듈), ADR-0013(대신함), ADR-0031(결정 4의 백업), ADR-0037(Drizzle과 `sql.raw` 규칙), ADR-0053(결정 9 저장소 인증 표), ADR-0060(수수료율 고정), ADR-0062(상품 정산·반품 조건), ADR-0083(PostgreSQL 18), ADR-0086(검사 규칙·복사한 칸), ADR-0097(측정 근거 칸), FR-014, FR-015, FR-024, POL-016, POL-037, NFR-025, QR-FL-2, SCR-015, SCR-023, [docs/data.md](../data.md) §1·§2·§4, [docs/infra.md](../infra.md) §1·§4·§6·§9, [docs/infra-handover.md](../infra-handover.md) §1·§2·§3·§4·§6.1, [docs/devops.md](../devops.md) §7.5, [docs/features/settlement.md](../features/settlement.md) §4.5·§10, [docs/architecture.md](../architecture.md) §3.1·§6.1·§8.3, planning/01 §1.2(P-09)·§3.1, wbs 2.11.2·7.1.1, [review/tech-review.md](../review/tech-review.md)(높음-06)

## 맥락

- **지금 설계**: shop 모듈의 상품 정의(굿즈·주차권·VIP 패키지·패스트트랙 같은 티켓 연동 부가 상품)만 MongoDB(문서 형태로 저장하는 데이터베이스) 복제 세트 3노드에 두었다. 한정 재고(`product_stock`)와 굿즈 주문(`merch_order`), 정산은 이미 PostgreSQL core 논리 DB에 있다.
- **MongoDB 하나 때문에 생긴 장치**: 데이터 노드 풀의 큰 서버 3대 몫, 오퍼레이터, 인증·TLS·저장 암호화(ADR-0053), 하루 1회 백업과 분기 복원 훈련, 백업 신선도 경보, 데이터 분류·비밀 목록 행, `$jsonSchema` 검증 올리기 규칙(devops §7.5), 변경 알림(Change Stream) 소비자, 로컬·CI 시험 컨테이너, 판 올림이다.
- **사실과 다른 곳(2026-10-27 원문 확인, 기술 검토 §9)**: 문서는 'MongoDB 커뮤니티 오퍼레이터로 하루 1회 S3 스냅샷 백업'이라 적었다. 그런데 그 오퍼레이터 저장소는 폐기됐고(2025년 11월까지만 최선의 지원), 백업은 Enterprise 기능으로 분류된다. 그래서 RPO 1일(잃어도 되는 데이터의 시간 폭 1일) 주장은 지금 설계로 성립하지 않았다.
- **돈이 엉뚱한 곳에 있었다**: 정산에 쓰는 중개수수료율 `commission_rate_bp`가 MongoDB 상품 문서에만 있었다. ADR-0013 제목의 '돈과 재고는 PostgreSQL에'와 어긋나고, 정산(payment-svc)이 이 값을 받을 계약도 없었다(settlement §4.5).
- **두 저장소 사이 원자성이 없었다**: 상품을 만들 때 상품 정의(MongoDB)와 한정 수량 재고(PostgreSQL)를 한 트랜잭션(여러 변경을 한꺼번에 반영하거나 한꺼번에 취소하는 작업 단위)으로 쓰지 못했다.
- **기각 이유가 약했다**: ADR-0013은 PostgreSQL JSONB(JSON을 이진 형식으로 저장하고 안쪽 값으로 거를 수 있는 칸)를 '카테고리별 중첩 옵션의 동적 유효성 검증과 부분 업데이트 튜닝이 복잡하다'며 뺐다. 검증을 DB의 `$jsonSchema` 대신 코드의 Zod 스키마로 하면 이 이유는 사라진다. 화면과 서버는 이미 같은 Zod 스키마 묶음(`@peaket/validation`)을 쓴다(docs/frontend.md). 상품 하나의 속성은 작아서(수 KB [추정]) 고칠 때 통째로 다시 검사해 써도 된다.
- **부하**: 상품 정의는 파트너가 상품을 만들거나 고칠 때만 쓴다. 읽기는 상품 화면의 ISR(미리 그려 두고 정해진 주기로 다시 그리는 방식)과 CDN이 받는다(`/shop/[productId]` 300초, docs/frontend.md §3).
- **성공 지표가 선택의 근거가 되지 못했다**: '새 상품 유형을 낼 때 DB 마이그레이션 0건'(planning/01 P-09, QR-FL-2)은 스키마 없는 저장소를 고르면 저절로 맞는 지표다. 데이터 모양이 바뀌면 코드에서 옮기는 일은 어느 저장소든 남는다.
- **확인한 사실(2026-10-28 원문)**: PostgreSQL 18 문서에서 JSONB의 GIN 인덱스(값 안의 키·값마다 색인을 만드는 인덱스)는 기본 연산자 묶음 `jsonb_ops`와 `jsonb_path_ops`가 있다. `jsonb_path_ops`는 키가 있는지 묻는 연산자는 받지 않고 `@>`(이 구조를 품는가)·`@?`·`@@`만 받지만, 같은 데이터에서 보통 훨씬 작고 검색이 더 정확하다. 값이 없는 빈 구조(`{"a": {}}`)를 찾을 때는 색인 전체를 훑는다.

## 결정

1. **상품 정의는 core 논리 DB(PostgreSQL)의 `product` 표에 둔다(소유자 승인).** MongoDB는 운영 설계에서 뺀다. ADR-0013의 결정 1(상품 정의는 MongoDB)과 결정 4(MongoDB는 shop 모듈만 접근)를 대신한다. 결정 2(주문과 한정 재고 확정은 PostgreSQL, 빠른 차감은 Redis)와 결정 3(주문 때 가격·옵션을 주문 행에 복사)은 그대로다.

2. **표 모양(추천 적용).** 자세한 칸은 docs/data.md §2다.
   - 공통 칸: `id`(UUIDv7), `promoter_id`(판매자, POL-037), `type`, `schema_version`, `name`, `status`(DRAFT·PUBLISHED·HIDDEN), `price`, `shipping_fee`, `return_shipping_fee`, `return_address`, `limited_qty`, `transferable`, `ticket_linked`, `linked_event_id`, 판매 기간, `commission_rate_bp`, `version`, 시각.
   - 돈은 칸으로 둔다. 가격·배송비·반품 배송비·수수료율은 정수 칸이고 JSON 안에 두지 않는다.
   - 유형마다 다른 것(옵션 규격, VIP 혜택 목록, 주차권 차량 규칙 등)만 `attributes jsonb`에 둔다.
   - 판매 전·판매 중·품절은 저장하지 않고, 게시 상태·판매 기간·재고로 계산해 보인다(SCR-023).

3. **유형별 스키마는 코드에 두고, 새 유형에 DDL을 쓰지 않는다(추천 적용).**
   - 유형마다 Zod 스키마를 `@peaket/validation`의 상품 유형 묶음에 판(`schema_version`)으로 둔다. 상품 빌더 화면(SCR-023)과 core-svc shop 모듈이 같은 스키마를 쓴다.
   - 유형 목록은 참조 표 `product_type`(코드, 최신 스키마 판, 쓰는지 여부)의 행이다. `product.type`은 이 표를 가리키는 외래 키다. 행은 배포 때 넣는 읽기 전용 자료다(좌석맵 템플릿과 같은 방식, data.md §2). 그래서 새 유형은 스키마 파일 + 화면 설정 + 행 하나로 끝나고 DDL(표 구조를 바꾸는 SQL)은 없다.
   - 상태·종류 칸마다 CHECK를 둔다는 규칙(ADR-0086)에서 `product.type`만 빼고 외래 키로 지킨다. CHECK 목록을 늘리면 그것이 DDL이기 때문이다.
   - 스키마 판이 바뀌면 새 상품은 새 판으로 쓰고, 옛 판 상품은 읽을 때 옛 판으로 검사한다. 옛 판을 없앨 때는 백필 작업으로 옮긴 뒤 없앤다(devops §7.5).

4. **꼭 지킬 규칙만 DB가 검사한다(추천 적용).**
   - CHECK: 금액과 수수료율 범위(0 이상, 수수료율 0~10,000 만분율), `jsonb_typeof(attributes) = 'object'`, 티켓 연동이면 연결 회차가 있다(`ticket_linked = (linked_event_id IS NOT NULL)`), 게시한 상품에는 수수료율이 있다(`status = 'DRAFT' OR commission_rate_bp IS NOT NULL`).
   - 속성 안의 모양은 저장 전에 Zod가 검사한다. 상품 쓰기는 shop 모듈 한 곳뿐이다.
   - 매일 한 번 [가정] 속성 검증 잡이 모든 상품을 그 판의 스키마로 다시 검사해 실패 수(`product_attribute_invalid_total`)를 낸다. 0이 아니면 SEV3(`kind` hygiene)다. 코드를 거치지 않은 쓰기나 스키마 실수를 찾기 위해서다.

5. **속성 거르기는 GIN `jsonb_path_ops`로 한다(추천 적용).**
   - `attributes`에 GIN(`jsonb_path_ops`) 인덱스를 하나 두고, 거르기는 `attributes @> $1`(JSON 값을 매개변수로 넘김)로 한다.
   - 경로나 키 이름을 SQL 문자열에 이어 붙이지 않는다(`sql.raw` 허용 목록 규칙 그대로, ADR-0037).
   - 화면이 자주 거르는 속성이 생기면, 먼저 그 속성을 생성 열이나 표현식 인덱스로 올린다.
   - 목록의 기본 인덱스는 `(promoter_id, status)`와 `(linked_event_id) WHERE ticket_linked`다.

6. **변경 전파는 같은 트랜잭션의 Outbox로 한다(추천 적용).**
   - 상품을 만들거나 고치거나 게시 상태를 바꾸는 트랜잭션에 상품 행, 한정 수량 재고 행(처음 만들 때), Outbox 행을 함께 쓴다. 이제 한 DB라서 셋이 한 번에 반영되거나 한 번에 취소된다.
   - Outbox 사건을 받아 웹 앱 서버가 `product:{id}` 태그를 무효화해 페이지를 다시 그린다(공연 정보의 태그 무효화와 같은 길). 사건이 늦거나 빠져도 ISR 300초가 안전망이다.
   - 수정은 `version`으로 낙관적 잠금을 건다. 속성은 통째로 다시 검사해 쓴다. `jsonb_set` 같은 부분 수정은 운영 백필에만 쓴다.

7. **주문 항목은 상품 표를 가리키고 수수료율을 복사한다(추천 적용).**
   - `merch_order_item.product_id`는 `product.id`를 가리키는 외래 키다(같은 core 논리 DB).
   - `merch_order_item`에 `commission_rate_bp`(주문 때 상품의 고정 수수료율)와 `option_snapshot`(고른 옵션, 상품 이름·유형·스키마 판)을 더한다. 상품의 수수료율은 처음 게시할 때 고정되어 바뀌지 않지만(ADR-0060·0062), 항목에 복사해 두면 정산이 다른 논리 DB를 읽지 않고 항목만으로 계산한다(settlement §4.5).

8. **운영에서 빠지는 것(추천 적용).** MongoDB 복제 세트와 오퍼레이터, 데이터 노드 풀의 MongoDB 몫, 27017 포트와 SCRAM 사용자, MongoDB 백업과 분기 복원 훈련, MongoDB 백업 신선도 경보, Change Stream 소비자, `$jsonSchema` 올리기 규칙, 로컬·CI의 MongoDB 시험 컨테이너. 상품 정의는 이제 Aurora 공유 클러스터의 백업(시점 복구 35일, 일 스냅샷 도쿄 복제)과 인증·TLS·암호화를 그대로 쓴다.

9. **성공 지표는 기술 중립으로 바꾼다(추천 적용).** '새 상품 유형 추가 리드타임(유형 스키마·화면·배포 포함)'을 재고, 목표는 NFR-025의 5영업일 이내를 그대로 쓴다. 'DDL 0건'은 목표가 아니라 이 설계의 성질로 함께 확인한다(planning/01 P-09·§3.1, QR-FL-2).

10. **측정(추천 적용).** V-T26: 기본 유형 둘(굿즈·주차권)로 만든 뒤 셋째 유형(VIP 패키지)을 더하는 변경의 리드타임(첫 커밋부터 데모 배포까지)과 DDL 0건을 PR 기록으로 남긴다(wbs 7.1.1).

11. **일정(WBS, 추천 적용).** 2.11.2는 MongoDB 인증·TLS가 빠져 5일 → 4.75일이다. 7.1.1은 'MongoDB 상품 정의'를 'PostgreSQL `product`와 유형 스키마 목록, 속성 검증 잡, V-T26'로 바꾸고 5.5일 그대로다(MongoDB 드라이버·Change Stream 몫과 바뀐다) [가정].

| E. 속성 행 표(EAV, ADR-0013 대안 2) | 새 속성에 DDL이 없다 | 여러 속성을 함께 거르는 쿼리가 복잡하고 느리며, 값 검증이 어렵다 | 쓰지 않는다 | 없다 |

## 결과와 트레이드오프

- MongoDB 복제 세트 3노드와 그에 딸린 장치(결정 8)가 빠진다. 데이터 노드 풀에는 ClickHouse와 Keeper만 남는다.
- 상품 정의의 RPO는 1일(성립하지 않던 주장)에서 Aurora와 같은 0, RTO는 5분이 된다(같은 AZ 장애 기준, NFR-015).
- 수수료율이 PostgreSQL 칸에 있고 주문 항목에 복사되어, 상품 정산의 계산 원본이 모두 PostgreSQL에 있다.
- 대가는 셋이다. 속성 검증을 코드가 맡는다. 스키마 판을 관리해야 한다. 상품 정의가 identity·ops와 같은 Aurora 공유 클러스터에 쓰기를 더한다(쓰기는 드물다).
- '저장소를 여럿 다룬다'에서 MongoDB 줄은 포트폴리오에서 빠진다. 옛 설계는 ADR-0013과 git 이력(develop 70d37c3까지의 docs/data.md·infra.md)에 남는다.

## 되돌릴 조건

- 상품 유형이 수백 개로 늘고, 유형별 부분 갱신이나 속성 검색이 병목으로 재어질 때(먼저 결정 5의 생성 열·표현식 인덱스를 쓴다).
- 상품 정의 쓰기가 Aurora 공유 클러스터의 쓰기 지연을 눈에 띄게 늘린다고 재어질 때.
- V-T26에서 리드타임이 목표(5영업일)를 넘고, 그 원인이 저장 방식에 있을 때.

## 남는 한계

- 속성 검증은 코드가 한다. shop 모듈을 거치지 않은 쓰기(운영자의 직접 SQL 등)는 Zod 검사를 받지 않는다. 그래서 운영 변경은 마이그레이션 작업으로만 하고(docs/devops.md §7), 매일 속성 검증 잡이 어긋난 상품을 찾는다. 찾기 전까지는 잘못된 속성이 화면에 보일 수 있다.
- JSONB 속성의 통계가 약해, 여러 속성을 함께 거르는 쿼리는 계획이 빗나갈 수 있다. 지금 화면에는 그런 조회가 없다.
- 옛 스키마 판을 읽는 코드가 쌓일 수 있다. 판을 없애기 전에 백필해야 한다.
