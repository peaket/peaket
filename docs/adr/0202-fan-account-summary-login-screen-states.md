# ADR-0202: 로그인 여부·본인확인 상태는 팬 계정 요약 경로로 화면 스크립트가 받고, 로그인 경로의 실패는 로그인 화면 상태로 돌려보낸다

- **상태**: 채택(2026-11-05, 추천 적용. wbs 2.10.1 세부는 추천 적용이라는 승인 2026-10-14·2026-10-28). BUILD_ORDER HOT-321.
- **관련**: ADR-0065 결정 8(알림·외부 링크 착지 규칙), ADR-0119(얇은 OIDC 클라이언트), ADR-0180(공급자 호출 보호), ADR-0199(화면 먼저), [docs/frontend.md](../frontend.md) §2.5, [docs/features/identity.md](../features/identity.md) §2, [docs/design/d5-screen-blueprint.md](../design/d5-screen-blueprint.md) §5.2·§5.4
- **관련 ID**: FR-001, FR-002, SCR-001, SCR-002, SCR-004, POL-019

## 맥락

- 화면마다 위에 붙는 머리(셸 머리)는 로그인했으면 계정 메뉴를, 안 했으면 [로그인]을 보인다. 공연 상세의 예매 버튼도 같다. 비로그인이면 [[ 로그인하고 입장 ]]을, 본인확인 전이면 [[ 휴대폰 본인확인 ]]을 보인다(d5 §5.2).
- 그런데 지금 머리는 목업 사용자를 보인다. 로그인 여부를 알려 주는 계약 경로가 없기 때문이다.
  - 홈·상세·검색은 캐시 화면이다. 캐시 화면은 미리 그려 두고 누구에게나 같은 HTML을 주는 화면이라, 서버가 쿠키를 읽지 않는다.
  - 다른 사이트에서 오는 첫 이동에는 `SameSite=Strict` 팬 쿠키가 실리지 않는다. 그래서 요청마다 그리는 화면도 서버가 쿠키로 로그인 여부를 정하지 않는다(docs/frontend.md §2.5 '알림·외부 링크 착지 규칙').
  - 팬 액세스 토큰 쿠키는 HttpOnly다. HttpOnly는 화면 스크립트가 쿠키를 읽지 못하게 하는 속성이라, 화면 스크립트도 토큰을 열어 볼 수 없다.
- 공연 상세는 지금까지 찜·알림 상태 요청이 401(로그인이 필요하다는 응답)이면 비로그인으로 그렸다. 하지만 이 방법으로는 본인확인 여부를 알 수 없다.
- 로그인 경로(`POST /login/{provider}`와 콜백)는 실패하면 글자 한 줄을 답한다. 이 경로들은 화면 이동이다. 그래서 사람은 빈 페이지에 글자만 보게 된다. d5 §5.4는 로그인 화면 안에서 실패를 알린다. '에러'는 카드 위 안내로, '제공자 장애'는 그 버튼 아래 한 줄로 보인다.
- 로그인 화면은 아직 퍼블리싱 목업이다. 상태 미리보기(`?state=`)로만 상태를 바꾼다.

## 결정

1. **팬 계정 요약 경로 `GET /v1/identity/me`**(operationId `getIdentityMe`): 응답은 로그인한 팬의 요약 `FanAccountSummary`다.
   - 칸은 넷이다.
     - `nickname`: 가입을 마치기 전이면 null
     - `signupCompleted`: 만 14세 확인과 필수 동의를 마쳤는지
     - `verified`: 휴대폰 본인확인 기록이 있는지. 토큰의 `ticket:buy`와 같은 출처다
     - `hasStaffAssignment`: 지금 ASSIGNED인 현장 스태프 배정이 있는지
   - 이메일·휴대폰 번호·회원 코드는 싣지 않는다. 화면이 고르는 데 필요한 값만 둔다.
   - `Cache-Control: no-store`다. 세션이 없거나 끝났으면 401이다.
   - 서버 쪽 구현은 identity-svc가 맡는다(BUILD_ORDER BOT-047). 그 전에는 계약 모양 가짜 API(`apps/web/scripts/mock-api.mjs`, ADR-0199)가 답한다.
2. **화면 스크립트가 한 번 받아 나눠 쓴다**: 브라우저는 문서마다 이 경로를 한 번 부르고, 셸 머리와 공연 상세가 같은 답을 쓴다(`apps/web/src/entities/me` `useFanSession`, 가게 `session-store.ts`).
   - 401이면 갱신을 한 번 거친다(`withFanRefresh`). 그래도 401이면 비로그인이다.
   - 본인확인이 끝나면 다시 받는다. 버튼이 바뀐 뒤 초점은 버튼이 있던 자리 묶음의 새 자리로 옮긴다(d3 SCR-006 '초점을 돌린다').
   - 뒤로 가기로 페이지 보관(bfcache)에서 돌아오면 다시 받는다. 그 사이 로그아웃했을 수 있기 때문이다.
   - 답을 받기 전에는 머리의 계정 자리를 같은 크기의 빈자리로 둔다. 로그인한 사람에게 [로그인]이 잠깐 비치지 않게 하려는 것이다.
   - 5xx·연결 실패로 모르면 머리는 [로그인]을 보인다. 공연 상세 예매 버튼은 개인 상태로 바꾸지 않는다. 진입 경로가 다시 막기 때문이다(로비·대기열의 403).
   - 서버 API 출처가 없는 실행(퍼블리싱 미리보기 빌드)은 비로그인 모양이다.
3. **공연 상세 예매 버튼의 개인 상태**: 들어갈 수 있거나 곧 들어갈 수 있는 상태에만 개인 상태를 덮는다. 그 상태는 로비 버튼 차례 기다림·로비 열림·오픈 뒤 진입이다.
   - 비로그인: [[ 로그인하고 입장 ]] → `/login?next=<이 회차 주소>`
   - 본인확인 전: [[ 휴대폰 본인확인 ]](본인확인 흐름, SCR-006)
   - 가입을 마치지 않은 계정: [[ 가입을 마치고 입장 ]] → `/signup/consent?next=<이 회차 주소>` [가정]
   - 로비가 닫힌 때·선착순 오픈 전·판매 종료·취소는 그대로다.
   - 공연 정보의 ③ 줄은 본인확인 <완료>, 또는 '본인확인이 필요합니다'와 [ 휴대폰 본인확인 ]을 보인다. 비로그인이면 목적 문구만 보인다.
4. **로그인 경로의 실패는 로그인 화면으로 돌려보낸다**: 로그인 목적의 실패는 303으로 로그인 화면에 보낸다. `next`는 그대로 싣는다.
   - `/login?next=<돌아갈 주소>&error=failed`: 일반 실패. 공급자 동시 상한(ADR-0180의 429)도 이것이다.
   - `/login?next=<돌아갈 주소>&error=down&provider=<공급자>`: 끊긴 공급자. 시작과 콜백 둘 다 해당한다.
   - 이유 범주는 지금처럼 서버 로그에만 남긴다.
   - 재인증·로그인 수단 추가의 실패는 지금처럼 그 결과 화면으로 간다.
   - docs/architecture.md §5 '소셜 로그인 공급자 HTTP' 행의 429·503 응답이 로그인 경로에서는 이 이동이 된다. 기다리지 않고 바로 답하는 것은 같다.
5. **로그인 화면(SCR-004)은 주소의 상태로 그린다**: 퍼블리싱 상태 미리보기(`?state=`)와 상태 바꾸기 띠를 걷는다.
   - `error`(failed·down), `provider`, `ended`(세션 종료 사유)를 읽는다. 값은 허용 목록에 있는 것만 받는다.
     - `ended`가 받는 사유: LOGOUT·ADMIN_FORCE·REFRESH_REUSE·DEVICE_LIMIT·MERGED·DELETE
     - 모르는 값은 무시한다.
   - '진행 중'(누른 버튼만 스피너, 나머지 비활성)은 폼을 보낼 때 화면 스크립트가 그린다.
   - 세션 종료 사유를 화면에 알리는 쪽은 갱신 401의 오류 본문 `ended`다(BOT-047, ADR-0235).
6. **셸의 로그아웃은 `POST /logout` 폼이다**: 머리의 로그아웃 확인 뒤 같은 출처 폼을 보낸다. 앱 서버가 `Origin`을 확인하고 쿠키를 지운 뒤 홈으로 보낸다(identity §2).

## 결과

- 캐시 화면도 머리와 예매 버튼이 실제 로그인·본인확인 상태를 보인다. 첫 그리기는 계정 자리가 빈자리이고, 요약을 받은 뒤 바뀐다.
- 화면마다 요약 요청이 한 번 는다. 이 요청은 팬 경로라 gw-fan(팬 요청을 받는 관문)을 지나고 캐시하지 않는다.
  - 로비 개방 몰림 때 상세 화면을 여는 사람마다 한 번씩이다.
  - 그래서 docs/architecture.md §9.1의 상세 화면 호출 수에 더한다.
- 로그인 실패가 로그인 화면 안의 안내가 된다. 사람은 같은 화면에서 다시 누르거나 다른 수단을 고른다.
- 아직 목업 사용자(`entities/me`)로 내용을 그리는 화면은 남는다(계정 설정·월렛 등). 머리만 실제 상태다. 그 화면을 잇는 단계가 목업을 걷는다.

## 다른 선택지

| 길 | 고르지 않은 까닭 |
| --- | --- |
| 찜·알림 요청의 401로 로그인 여부만 본다 | 본인확인 여부를 알 수 없고, 찜·알림이 없는 화면(검색·로그인)에서는 쓸 요청이 없다 |
| 액세스 토큰을 화면 스크립트가 읽게 한다(HttpOnly를 뗀다) | 스크립트 주입 한 번에 토큰이 새어 나간다(docs/security/asvs/auth.md 3.3.4) |
| 앱 서버가 쿠키를 읽어 요약을 HTML에 넣는다 | 캐시 화면은 누구에게나 같은 HTML이고, 첫 이동에는 쿠키가 실리지 않는다(ADR-0065 결정 8) |
| 로그인 경로가 429·503 상태로 글자를 답한다(지금) | 화면 이동이라 사람에게는 빈 페이지다. 상태 코드는 로그·지표로 이미 남는다 |
