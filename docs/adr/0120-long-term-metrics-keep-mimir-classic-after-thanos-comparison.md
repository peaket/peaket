# ADR-0120: 장기 지표 저장소는 Mimir 고전 구조를 그대로 둔다 — Thanos와 저장량·부품·고가용성으로 견주고, 긴 창 계산과 5분 집계의 자리를 정한다(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 중간-022 'Mimir 선택 근거가 약하고 다운샘플링이 없어 우회 구성이 생겼다'에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 방향(4.1.1 착수 전에 Mimir와 Thanos를 견줘 새 ADR로 정하기)은 소유자 결정(추천안 승인)이고, 고른 결과와 측정 항목·바꿀 조건은 추천 적용이다. 보존 기간(원본 90일·5분 집계 13개월)은 2026-10-21 소유자 결정(ADR-0077)이라 바꾸지 않는다. 28일 에러 버짓은 Mimir `raw`(90일)의 규칙 값을 읽는다는 2026-10-28 규칙(기술 검토 높음-13)을 그대로 지킨다. 외부 사실은 2026-10-28에 각 GitHub 원문과 AWS 가격 목록으로 확인했다)
- **관련**: ADR-0067(결정 5), ADR-0068(결정 3·6), ADR-0077(결정 2·3), ADR-0057, NFR-014, [docs/observability.md](../observability.md) §1·§4·§8·§9·§12(G-26), [docs/architecture.md](../architecture.md) §5(28일 예산 배포 잠금), docs/devops.md §5.3, docs/perf-ledger.md §11, wbs 4.1.1·4.1.2·4.8.2, [review/tech-review.md](../../review/tech-review.md)(중간-022, 높음-13)

## 맥락

- ADR-0068 결정 6은 Mimir를 'Loki·Tempo와 같은 객체 저장소 운영 방식'이라 골랐고, 스스로 "대안과 비교한 근거는 약하다"고 적었다. 다시 볼 때는 '4.8.2에서 운영 시간을 잰 뒤'로 미뤘다.
- 그 뒤 ADR-0077이 지표 보존을 원본 90일·5분 집계 13개월로 정했다(소유자 결정). Mimir에는 다운샘플링(오래된 자료를 굵은 시간 간격으로 줄여 다시 저장하는 기능)이 없다. 그래서 테넌트 둘(`raw`·`agg5m`), 5분 기록 규칙, `write_relabel_configs`로 골라 보내기가 생겼다. 검토는 이것을 '우회 구성'이라 불렀고, 운영 시간을 잰 뒤에 저장소를 바꾸면 이미 만든 구성을 버려야 한다고 짚었다.
- 높음-13(2026-10-28)은 28일 남은 예산·28일 SLO 보고·배포 잠금 판정을 클러스터 Prometheus(15일 보존)가 아니라 Mimir `raw`(90일)에서 Mimir 규칙 평가기(ruler)가 계산한 값 하나로 읽게 했다.
- **확인한 사실**(2026-10-28 원문)
  - **Grafana Mimir** 3.2.3(2026-10-22)
    - 3.0부터 두 구조를 지원한다. ingest storage(권장, Kafka를 쓰기 경로로 쓴다)와 고전 구조(상태를 가진 인제스터와 로컬 WAL)다. 고전 구조는 지원 중단 목록에 없다(Mimir 판 정책 문서).
    - Thanos의 다운샘플링을 지원하지 않는다. Thanos가 만든 내려 만든 블록을 올리면 원본과 섞어 읽으므로 지워야 한다(Mimir 'Thanos에서 옮기기' 문서).
    - 규칙 평가기는 `source_tenants`를 둔 '연합 규칙 묶음'으로 여러 테넌트의 자료를 읽어 자기 테넌트에 결과를 쓸 수 있다(`-ruler.tenant-federation.enabled`, `-tenant-federation.enabled`).
  - **Thanos** v0.42.5(2026-10-27, 아직 1.0 전 판)
    - 압축기(compactor)는 한 버킷의 같은 블록 흐름에 하나만 돌아야 한다("Only one instance of Compactor may run against a single stream of blocks").
    - 압축기가 40시간 지난 블록에서 5분 해상도, 10일 지난 블록에서 1시간 해상도를 만든다. 보존은 `--retention.resolution-raw`·`-5m`·`-1h`로 해상도마다 따로 둔다.
    - 문서 스스로 다운샘플링은 저장 공간을 줄이지 않는다고 적는다. 원본 블록마다 크기가 조금 작거나 비슷한 블록을 둘 더 만들고, 해상도를 다 두면 저장량이 약 3배까지 늘 수 있다.
    - 쓰기를 받는 Receive의 AZ 인식 해시 링(복제본을 AZ마다 나눠 두는 배치)은 '실험(experimental)' 기능이다. 사이드카 방식은 Prometheus의 로컬 압축(블록 합치기)을 꺼야 한다.
  - **Prometheus**: 샘플 하나에 평균 1~2바이트를 쓴다(저장소 문서).
  - **S3 Standard(서울)**: GB·월 0.025달러(처음 50TB, AWS 가격 목록 2026-10-15 게시본).

## 결정

1. **장기 지표 저장소는 Mimir 고전 구조(테넌트 둘)를 그대로 둔다(추천 적용).** 비교는 아래 표와 같다.

   | 기준 | Mimir 고전 구조(지금) | Thanos(Receive 또는 사이드카) |
   | --- | --- | --- |
   | 13개월 저장 | 정해 둔 집계(`agg5m`)만 13개월. 아래 예에서 13개월 집계는 약 0.85GB [추정] | 모든 시계열을 5분·1시간 해상도로 두 벌 더 남긴다. 아래 예에서 13개월 해상도 둘이 약 92GB~680GB [추정] |
   | 원본 90일 | 약 78GB [추정] | 같다 |
   | 부품 종류 | 7종: distributor, ingester(AZ마다 한 벌), querier, query-frontend, store-gateway, compactor, ruler(캐시·query-scheduler는 선택) | 5종: receive 또는 사이드카, querier, store gateway, compactor(버킷마다 하나), ruler(query-frontend는 선택) |
   | AZ 하나 장애 | 영역 인식 3중 복제, 쓰기·읽기 정족수 2. Loki와 같은 모양이라 G-26 하나로 둘을 본다 | Receive는 AZ 인식 배치가 실험 기능이다. 사이드카는 제어 입력을 읽는 클러스터 Prometheus의 블록 설정을 바꾸고, 최근 2시간은 그 Prometheus 디스크에만 있다 |
   | 다른 후보로 옮기기 | 기록 규칙 집계와 테넌트별 보존은 AMP(작업 공간별 보존)·VictoriaMetrics에서도 같은 모양이다 | 내려 만든 블록은 Mimir·AMP가 읽지 못한다 |
   | 긴 창 계산(높음-13) | Mimir 규칙 평가기가 `raw`에서 28일 예산을 계산한다(지금 규칙) | Thanos Ruler가 querier를 거쳐 원본 해상도로 계산하면 같다 |
   | 사용권 | AGPL-3.0 | Apache-2.0 |

   - 저장량 예(측정 전, [추정]): 활성 시계열 10만 개 [가정]를 15초마다 긁으면 하루 약 5.76억 샘플이다. 샘플당 1.5바이트 [가정](Prometheus 문서의 1~2바이트 가운데)로 하루 약 0.86GB, 원본 90일 약 78GB다.
     - Mimir `agg5m`: 집계 시계열 5천 개 [가정]가 5분마다 한 점이면 하루 약 2MB, 13개월 약 0.85GB다.
     - Thanos 5분·1시간 해상도: 시계열마다 5분에 집계값 다섯 개를 두므로 표본 수로는 원본의 약 25%, 1시간은 약 2%다. 그러면 13개월에 약 92GB가 하한이다. 문서대로 내려 만든 블록이 원본 블록과 비슷한 크기라면 약 680GB다.
     - 돈으로는 서울 S3 기준 Mimir 쪽 월 약 2달러, Thanos 쪽 월 약 4~19달러다 [추정]. 저장 비용은 결정을 가르지 않는다. 가르는 것은 무엇을 13개월 두는지와 AZ 장애 방식이다.
   - 고른 이유: 13개월 둘 것은 서비스·여정·회차 단위의 4대 신호와 SLI 비율, 포화도 요약, 비용에 쓰는 사용량뿐이다(ADR-0077 결정 3). 모든 시계열을 두 해상도로 더 둘 이유가 없다. AZ 장애 방식은 문서화된 기본 기능(Mimir 고전 구조)을 쓴다. 제어 입력을 읽는 Prometheus(관측 자료 1등급, docs/observability.md §9)의 설정을 장기 저장소에 묶지 않는다.
   - 대가: 부품 종류가 Thanos보다 둘 많다. 기록 규칙에 넣지 않은 시계열은 90일이 지나면 다시 볼 수 없다.
2. **5분 집계는 지금 방식을 그대로 쓴다(추천 적용).** 클러스터 Prometheus가 평가 간격 5분인 기록 규칙을 돌리고, 그 결과만 `write_relabel_configs`로 골라 `agg5m` 테넌트로 보낸다(ADR-0077 결정 3). 이것은 다운샘플링이 없어서 만든 우회가 아니라, 저장소를 바꿔도 같은 모양으로 옮길 수 있는 설계로 읽는다. Mimir 규칙 평가기의 연합 규칙 묶음으로 `raw`에서 `agg5m`을 만드는 방법도 봤지만 쓰지 않는다(검토한 대안).
3. **긴 창 계산은 높음-13 규칙 그대로다(추천 적용).** 28일 남은 예산(`slo:error_budget_remaining:ratio28d`), 28일 SLO 보고, 배포 잠금 판정은 Mimir `raw`(90일)에서 Mimir 규칙 평가기가 계산한 값 하나를 읽는다. 그 값을 읽지 못하거나 15분 [가정]보다 낡으면 잠금 상태를 지금대로 둔다. 나중에 저장소를 바꾸면 새 저장소의 규칙 평가기가 원본 해상도로 같은 이름의 값을 낸다(Thanos면 Thanos Ruler, AMP면 AMP 규칙). 배포 승격 게이트와 ops-svc는 그 값 하나만 읽는다는 규칙도 그대로다.
4. **포트폴리오 로컬 측정은 Prometheus 하나로 한다(추천 적용).** 측정 캠페인은 로컬 보존 15일 안에 끝나므로 장기 저장소가 없어도 된다. Mimir는 두 때만 띄운다.
   - 규칙 확인(wbs 4.1.2): 모놀리식 한 프로세스(로컬 파일 저장소)로 28일 예산 규칙과 `agg5m` 골라 보내기, 테넌트별 보존이 도는지 본다.
   - G-26(관측 스택 AZ 하나 장애): 고전 구조(영역 셋)로 띄운다.
5. **잴 것과 바꿀 조건(추천 적용)**
   - 잴 것(wbs 4.1.1·4.1.2): 테넌트별 하루 저장량(`raw`·`agg5m`), 활성 시계열 수, compactor·store-gateway의 CPU·메모리, 28일 예산 규칙 한 번의 평가 시간, 부품별 운영 시간(docs/perf-ledger.md §11의 연간 추정식에 넣는다).
   - 바꿀 조건
     - 5분 집계로 답하지 못한 장기 질문이 분기에 두 번 넘게 나오고(ADR-0077 되돌릴 조건), 원본 보존을 늘리는 비용이 Thanos 다운샘플링보다 크면, Thanos를 새 ADR로 다시 견준다.
     - 4.8.2 연간 추정에서 Mimir 부품이 직접 운영 시간의 가장 큰 몫이면 Thanos·VictoriaMetrics를 새 ADR로 다시 본다(ADR-0068 결정 6).
     - G-26에서 고전 구조가 AZ 하나 장애에 쓰기나 읽기 빈칸을 내면, ADR-0077 되돌릴 조건대로 ingest storage를 먼저 검토한다.
     - 4.8.2가 AWS 관리형(AMP)을 고르면 이 ADR의 Mimir 부분은 빠진다. 테넌트 둘은 AMP 작업 공간 둘의 보존 설정으로 옮긴다(ADR-0077 되돌릴 조건).
6. **문서 반영(추천 적용)**: docs/observability.md §1(관측 저장소 쓰기 경로)·§9(시계열 메트릭 행), ADR-0068·0077 상태 줄. wbs 4.1.1·4.1.2는 메인 정리에서 고친다.

## 검토한 대안

| 대안 | 고르지 않은 이유 |
| --- | --- |
| Thanos로 바꿔 다운샘플링과 해상도별 보존을 쓴다 | 13개월에 필요한 것은 정해 둔 집계뿐인데 모든 시계열을 두 해상도로 더 둔다. 문서도 저장 공간이 줄지 않는다고 적는다. Receive의 AZ 인식 배치는 실험 기능이고, 사이드카는 제어 입력용 Prometheus의 설정을 바꾼다. 내려 만든 블록은 다른 후보로 옮기지 못한다 |
| Mimir ingest storage(Kafka 쓰기 경로) | 지표 쓰기가 관측 Kafka 장애에 묶인다(ADR-0077). G-26에서 고전 구조가 모자라다고 재어질 때 본다 |
| Mimir 규칙 평가기의 연합 규칙 묶음으로 `agg5m`을 만든다 | Prometheus 쪽 원격 쓰기가 하나로 줄고 긴 창 계산이 한 곳에 모이는 이점은 있다. 그러나 집계가 Mimir 읽기 경로에 기대게 되고(읽기 실패면 그 평가는 결과를 남기지 않는다), AMP로 옮길 때 다시 Prometheus 쪽으로 돌려야 한다 |
| 장기 저장소 없이 Prometheus 보존을 늘린다 | 운영 설계에서 AZ 장애와 13개월을 한 서버 디스크에 맡기게 된다. 포트폴리오 로컬에서는 이 방식이다(결정 4) |
| VictoriaMetrics | 단일 서버판·클러스터판이 있고 Apache-2.0이다. 이번 비교 기준(13개월 집계, AZ 장애)에서 Mimir보다 나은 근거를 찾지 못했다. 운영 시간 조건(결정 5)에 닿으면 함께 본다 |

## 결과와 트레이드오프

- Mimir를 고른 근거가 '같은 운영 방식'에서 13개월에 둘 것, AZ 장애 방식, 다른 후보로 옮기기의 비교로 바뀐다. 4.1.1을 시작하기 전에 정해, 만든 뒤 버리는 일을 피한다.
- 28일 예산 규칙(높음-13)과 5분 집계는 저장소를 바꿔도 같은 이름·같은 모양으로 남는다.
- 대가: 부품이 Thanos보다 많고, 기록 규칙에 없는 시계열의 긴 추세는 볼 수 없다.

## 되돌릴 조건

- 결정 5의 바꿀 조건 넷이다.

## 남는 한계

- 저장량은 측정 전 [추정]이다. Thanos 쪽은 문서의 '비슷한 크기'와 표본 수 어림이 네 배 넘게 벌어진다. 실제 차이는 Thanos를 띄우지 않는 한 재지 않는다.
- 부품 수와 운영 시간의 관계는 연간 추정식으로만 본다(docs/perf-ledger.md §11). 1년 운영을 재지는 않는다.
