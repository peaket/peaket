# ADR-0059: 전체 화면설계 기준: 화면 68개, 앱 셸 공통화, 와이어프레임 문서와 프로토타입 범위

- **상태**: 채택 (2026-10-13. 소유자 요청 "이제 프로젝트의 전체 화면설계를 합시다. 현재 설계되어있는 화면이 있나요? 있으면 해당 부분을 읽고 전체 설계를 전수조사해서 전체 화면설계를 해주세요. 해당 설계를 바탕으로 먼저 프로토타입을 만들겁니다." 새 화면의 구성, 앱 셸, 관제 메뉴의 권한 나눔 제안, 프로토타입 우선순위는 이 요청에 따라 이 ADR이 정했고, 소유자가 정할 항목 15개와 확인이 필요한 사실·문안 19개를 design/d5-screen-blueprint.md §11에 남겼다.) ADR-0060(2026-10-14, 소유자 결정 '추천안대로 가겠습니다')이 남은 결정 15개를 정해 이 ADR을 보완한다(결정 7의 구현 방식은 A안, 결과 절의 WBS는 반영). 2026-10-13 전수 점검(2026-10-14 2차): Must 화면 SCR-016·049·060을 P2에서 P1로 옮겨 P1 32개·P2 11개다. 시연 S7·S8은 P0 화면만으로 끝나게 고쳤다(d5 §10.2·§10.6). 결과 절의 '권한 매트릭스에 행이 없어 d5 §3.3 제안으로만'은 ADR-0060 결정 8로 planning/03 §3에 다섯 행이 더해져 풀렸다. 2026-10-14 추천 적용(ADR-0062 결정 1·46): 결정 6의 네이버 버튼은 네이버 로그인 버튼 사용 가이드(2025-11-25 개정본)의 흰 바탕 세트(바탕 #FFFFFF, N 로고 #03A94D, 글자 #000000)와 '네이버 로그인'으로 정한다(권장 녹색 세트는 글자 대비 3.09:1이라 NFR-020과 맞지 않는다). Google 버튼은 가이드 영어 원문(2026-07-07)의 Google Sans Medium 14/20과 그라데이션 G를 따르고 세 버튼 레이블을 14px/20px·500으로 맞춘다(한국어판 가이드는 AI 번역 옛 판이라 Roboto로 남아 있다).
- **관련 문서**: design/d5-screen-blueprint.md(새 문서), planning/04-ia-flows-screens.md §1·§2·§3·§4, design/d2-design-system.md §1·§2, design/d3-screens.md, design/d4-handoff-checklist.md §2·§3, review/consistency-review.md R-60
- **관련 ID**: SCR-054~068, CMP-064~070, FR-004, FR-018, FR-019, FR-021, FR-049, FR-053, FR-057, NFR-019

## 맥락

- 화면 명세는 planning/04 §3(목적·요소·상태·문구)와 design/d3(컴포넌트·상태 표현·접근성)에 53개가 있었다. 화면을 어디에 놓고 어떻게 오가는지(와이어프레임, 화면 흐름), 앱마다 화면을 감싸는 틀(셸), 알림 메시지와 오류 응답별 문구는 정의되지 않았고, d3의 '시안' 열은 모두 비어 있었다. 소유자는 이 화면설계를 바탕으로 프로토타입을 먼저 만들 계획이다.
- 2026-10-13 전수조사에서 문서 묶음 다섯 개(정책·요구사항, 소비자 쪽 기능 설계, 운영·파트너·현장 기능 설계, 아키텍처·운영·보안·API·안내서, archive 원문 설계서)를 SCR 53개와 대조했다(d5 §1.1). 결과는 다음과 같다.
  - **화면이 없는 기능**: IA가 `/accounts`를 'SCR-017 관리자 보기'로만 적은 관리 계정 관리, 계약 중개수수료율을 입력할 곳이 없는 파트너사 계약, CS의 팬 조회, 봇 판정 표본 수동 검토(FR-049), 대기실 공지 템플릿과 파트너 긴급 공지, 파트너 공연 목록·공연 개요, CS 처리함에 '분쟁 접수'가 들어오는데 팬이 접수할 화면(FR-057), 티켓 없는 주문·굿즈 주문·예매 확인서를 다시 볼 예매·주문 내역(FR-053), 관심 공연·알림 관리(FR-019), 약관·정책 문서, 인앱 브라우저의 외부 브라우저 전환(NFR-019), 오류·판매 중단 화면, 지연 환급 계좌 입력, 스태프의 내 배정.
  - **기존 화면의 빈 곳**: 53개 화면 모두에 응답 코드별 상태, 법정 고지 위치, 회차 선택 같은 요소·상태·문구가 빠져 있었다.
  - **문서 간 불일치 52건**(같은 날 정합성 점검 세션이 찾은 6건 포함): 2인 승인 대기 5분 대 10분, 양도 마감, 입장 시작 뒤 취소의 환급 시점, 형사처벌 고지 문안, 판정 순서가 다른 입장 흐름도, 컴포넌트 상태 이름 누락 등.
  - **외부 사실**: 카카오 로그인 디자인 가이드(2026-10-13 원문 확인)는 버튼 컨테이너 #FEE500, 기본 레이블 '카카오 로그인'·'로그인'을 정하고 정한 색 밖의 색과 카카오 버튼을 덜 강조하는 배치를 금한다. Google 로그인 브랜드 가이드라인(2025-12-10 갱신본, 2026-10-13 확인)은 'Google 계정으로 로그인·가입·계속' 문구, 표준 색 'G' 로고, 다른 제공자 버튼과 같은 수준의 눈에 띔을 요구한다. d3의 '소셜 variant는 secondary'와 planning/04의 문구 '카카오로 계속하기'는 이와 맞지 않았다. 네이버 로그인 버튼 사용 가이드 원문은 이 환경에서 열리지 않았다.

## 결정

1. **화면설계 문서의 역할을 셋으로 나눈다.** planning/04 §3은 무엇을 왜 보이고 어떤 문구를 쓰는지, design/d3는 어떤 컴포넌트·상태 표현·접근성으로 그리는지, 새 문서 design/d5-screen-blueprint.md는 어디에 놓고 어디서 와서 어디로 가는지(와이어프레임, 화면 흐름), 앱 셸, 알림·오류 문구, 프로토타입 범위를 맡는다. 셋이 어긋나면 내용은 planning/04, 표현은 d3를 따르고 d5를 고친다. d3 '시안' 열은 d5 절을 가리킨다.
2. **새 화면 15개를 더한다**(SCR-054~068, 합계 68개). 소비자 웹 8개(관심 공연·알림 신청, 예매·주문 내역, 고객센터·문의, 약관·정책 문서, 외부 브라우저 전환 안내, 시스템 안내, 지연 환급 계좌 입력, 내 현장 배정), 파트너 콘솔 2개(홈·공연 목록, 공연 개요), 관제 콘솔 5개(관리 계정·세션 관리, 파트너사·계약 관리, 팬 조회, 봇 판정 표본 검토, 공지 관리).
3. **앱 셸을 하나의 컴포넌트 변형으로 둔다**(CMP-065 AppShell). 소비자 웹은 일반·집중·스태프 세 변형이다. 집중 셸은 예매 흐름(로비부터 결제 결과까지)에서 전역 내비를 빼고 대기실 번들 예산을 지킨다. 파트너는 사이드 내비와 공연 문맥 탭, 관제는 환경·온세일 단계·자동 제어 상태·경보·내 승인 대기를 보이는 위 상태 바와 역할별 메뉴, 스캐너는 구역·모드·연결·업로드 대기 상태 띠를 둔다. 소비자 웹 모바일에는 아래 탭 바를 두지 않는다.
4. **공통 컴포넌트 일곱을 더한다**: CMP-064 ReauthPrompt(팬 소셜 재인증과 관리 계정 재인증, 5분 재인증 토큰), CMP-065 AppShell, CMP-066 RoundPicker(같은 공연의 회차 고르기, 회차마다 주소가 다르다), CMP-067 AddressForm, CMP-068 NotifyPermissionSheet(사용자 동작 뒤 웹 푸시 권한 요청, iOS 홈 화면 추가 안내), CMP-069 MediaUploader, CMP-070 RichTextEditor. 기존 CMP-009·015·017·028·036·049·059에는 정의 문서와 화면 명세가 쓰는 변형·상태 이름을 더하고, d2 '사용 화면' 열은 d3를 기준으로 다시 맞춘다.
5. **정본과 어긋난 화면 문서를 고친다.** 법정 고지 문안은 POL 원문으로, 숫자·시간은 정책과 기능 설계로, 입장 판정 흐름도(F-04)는 offline-gate §6.4의 순서로 맞춘다(d5 §1.5의 '고침'). 요구사항·정책 문장 자체가 어긋난 것과 정본이 정해지지 않은 것은 고치지 않고 d5 §11에 올린다.
6. **소셜 로그인 버튼은 제공자 가이드를 따른다.** 카카오는 #FEE500 컨테이너와 '카카오 로그인', Google은 'Google 계정으로 로그인'과 표준 색 'G'를 쓰고 세 버튼을 같은 크기·같은 비중으로 둔다. 네이버의 색·문구는 가이드 원문을 확인한 뒤 정한다.
7. **프로토타입 범위를 정한다.** P0는 네 시연 흐름(팬 예매, 파트너 등록과 판매 승인, T=0 관제, 공연 당일 입장)의 25개 화면, P1은 Must·법정 화면 29개, P2는 Should·Could 화면 14개다. 프로토타입은 가짜 연동과 데모 도구 막대(데모 시계, 상태 토글, 가짜 결제창·판정 결과 고르기)로 상태를 보이며 성능·보안의 증거가 아니다. 상시 데모는 두지 않는다(ADR-0057). 구현 방식은 d5 §10.5의 권장안(Vite + React 단일 프로토타입 앱, SEED와 tokens.json, openapi 응답 모양을 따르는 MSW 가짜 API)을 소유자가 확인한 뒤 정한다.

## 검토한 대안

| 대안 | 기각 사유 |
| --- | --- |
| d3 표에 와이어프레임 열을 더함 | 표 한 칸에 배치도를 넣을 수 없고 화면 흐름·셸·알림·프로토타입 계획을 둘 곳이 없다 |
| 그림 도구로 시안만 만들고 문서는 그대로 | 프로토타입이 곧 시안 역할을 하고, 저장소 안에 배치·상태의 글 기준이 없으면 문서 점검 도구로 대조할 수 없다 |
| 빠진 기능을 기존 화면의 상태로만 넣음(새 SCR 없음) | 관리 계정·팬 조회·고객센터처럼 경로와 권한이 따로 있는 화면은 ID가 있어야 권한 매트릭스·요구사항 추적과 이어진다 |
| 소비자 웹 모바일 아래 탭 바 | 대기실·좌석맵은 전체 화면을 쓰고 공연 상세·좌석 선택은 하단 고정 바를 써서 겹친다. 위 내비와 메뉴 시트로 충분하다 |
| 기존 소셜 버튼 문구·색 유지 | 카카오 가이드의 색·기본 레이블과 맞지 않아 제공자 정책 위반 위험을 남긴다 |

## 결과와 트레이드오프

- 화면이 53개에서 68개로, 컴포넌트가 63개에서 70개로 는다. 프론트엔드 작업도 늘지만 WBS에는 아직 넣지 않았다. 새 화면 15개를 화면당 0.5~1일로 보면 7.5~15일, 프로토타입 P0 25개 화면은 10~15일 [가정]이다. 소유자가 범위와 구현 방식을 정한 뒤 WBS에 반영한다(d5 §11 D15).
- 화면이 부르는 동작 14건이 docs/api/openapi.yaml에 없다(d5 §1.6). API 설계 때 반영한다.
- 관제 메뉴의 새 화면(계정·세션, 파트너사, 봇 표본, 공지 관리) 권한 나눔은 권한 매트릭스에 행이 없어 d5 §3.3의 제안으로만 있다.
- d5는 2,700행이 넘는다. 화면 하나를 고칠 때 planning/04·d3·d5를 함께 봐야 하는 부담이 생긴다. 이를 줄이려고 d3 '시안' 열의 d5 절 참조를 문서 점검 도구가 대조하게 했다(tools/doc-check).

## 되돌릴 조건

- 프로토타입 검토에서 새 화면이 필요 없다고 판단되면 그 SCR을 '보류'로 표시한다. ID는 지우지 않는다.
- 네이버 가이드 원문이 다른 문구·색을 요구하면 결정 6을 고친다.
- 그림 시안이 생기면 d5의 와이어프레임은 배치 기준으로 남기고 시안 링크를 d3 '시안' 열에 더한다.
