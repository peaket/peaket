# ADR-0070: 장애 대응 지침 대조와 보강 — 재시작 전 진단 증거, 프로브, 시간 초과 기본값, 처리량 급감 경보, 장시간 시험(2026-10-20)

- **상태**: 채택 (2026-10-20. 소유자가 Release It!의 장애 대응 지침(피해 격리 우선과 증거 동결, 블레임리스 포스트모템, 관리 제어판, 느린 쿼리·배치 강제 중단, 킬 스위치, 비상 밸브, 비즈니스 처리율 경보, 자율 정화, 원클릭 롤백, 하위 호환 배포)과 안정성 반패턴·패턴·프로덕션 운영 설계 목록을 붙여 "지금 이 프로젝트 설계가 되어있는지 검토해주세요"라고 요청했다. 대조 보고(권고 높음 4건·중간 3건·낮음 4건)를 본 뒤 "추천대로 가겠습니다. 승인"이라고 했다. 추천은 높음 1~4와 중간 5~7을 새 ADR 하나로 묶고 수치는 [가정]으로 두는 것이었다. 결정의 세부와 수치는 추천 적용이며 소유자 검토 대상이다. 낮음 4건은 반영하지 않고 남는 한계에 적었다. 외부 사실은 2026-10-20에 원문으로 확인했다) 2026-10-22(ADR-0083): 비상 경로의 짧은 잠금 대기는 세션 SET이 아니라 트랜잭션 범위 `SET LOCAL`로 건다(결정 3의 '세션 SET을 쓰지 않는다'는 그대로). Outbox 일 파티션은 ID 범위로 나누고 Debezium `publish.via.partition.root=true`로 부모 표 이름으로 발행한다. `max_slot_wal_keep_size`는 AWS Aurora PostgreSQL 매개변수 목록에 있고(기본값 없음), 바꿀 수 있는지와 값은 wbs 0.3.2에서 정한다(docs/data.md §4). 2026-10-26: 결정의 시간 초과 기본값 표에 분석 저장소의 네 행(ClickHouse 리포트 조회·마감 변환, Mimir 조회, S3)을 더했다(docs/architecture.md §5, ADR-0089).
- **관련**: ADR-0009, ADR-0010, ADR-0028, ADR-0049, ADR-0053, ADR-0054, ADR-0057, ADR-0069, POL-022, POL-027, POL-041, NFR-023, NFR-027, docs/architecture.md §5·§7, docs/observability.md §3·§5·§9·§12~§14, docs/infra.md §8~§10, docs/devops.md §4.1·§5.4·§6.4·§10·§12·§14, docs/data.md §3·§4, docs/verification.md §2.7·§3.6·§5.2, docs/perf-ledger.md §2.3, docs/security/data-classification.md, docs/security/asvs/delivery.md, docs/security/secrets-and-keys.md, docs/features/control-tower.md §2·§8·§14, design/d5 §7.2, wbs 0.3.2·0.3.6·2.11.2·4.1.1·4.2.4·4.7.1·6.5.1

## 맥락

- 소유자가 붙인 목록(장애 대응 행동 지침 네 묶음, 안정성 반패턴과 패턴, 프로덕션 운영 설계)을 지금 설계에 대 보았다. 바로 앞의 ADR-0069는 관제(자동 제어의 자기 안전, 경보 관리, 넓은 사건)를 보강했다. 이번 대조에서 드러난 빈 곳은 장애가 난 순간 사람이 손으로 다루는 부분이었다.
- 잘 맞는 것: 피해 격리를 먼저 하는 판단 순서와 되돌릴 수 있는 약한 명령부터 쓰는 규칙(ADR-0049), 명령 카탈로그와 대역 외 런북 CLI(ADR-0053), 킬 스위치(명령 3)·Degraded와 결제사 전환(명령 6)·비핵심 기능과 배경 작업 멈춤(명령 9)·입장 제어(명령 1·2), 블레임리스 포스트모템과 인시던트 선언 기준(ADR-0069), 카나리 자동 중단·Git 되돌리기·`rollbackWindow`(ADR-0054), 확장·축소 마이그레이션과 N-1 시험, 경로별 시간 초과·데드라인 전파·2단계 차단·격벽·즉시 503과 `Retry-After`(ADR-0009), 몰림 대책(로비 셔플, 0~8초 분산, 폴링 지터, 요청 병합), 설정의 세 종류(devops §5.4).
- 빈 곳:
  1. 재시작하면 사라지는 프로세스 안 상태(힙, 활성 핸들, 이벤트 루프, 연결 풀)를 남기는 설정과 런북이 없다. 쿠버네티스 이벤트는 기본 1시간 뒤 지워진다. DB·Redis의 그 순간 상태를 떠 두는 절차도 없다. 운영 이미지는 셸이 없어(devops §4.1) `kubectl exec`로 신호를 보낼 수도 없다.
  2. 프로브 규칙이 없다. ADR-0010은 '엄격한 readiness probe'만 적었고, 부록 학습 지도는 '의존성 헬스체크(Redis·Kafka·DB)'를 적었다. 공유 의존성을 준비 상태에 넣으면 그 의존성이 죽을 때 모든 파드가 함께 빠진다.
  3. 앱 쪽 DB·Redis 시간 초과와 연결 풀 대기 한도의 기본값이 없다. `statement_timeout`·`lock_timeout`은 마이그레이션에만 있다(devops §7.2). 느린 쿼리를 끊는 런북이 없다.
  4. 오류 없이 처리량만 떨어지는 장애를 잡는 경보가 없다. 결제 화면 오류로 결제 요청이 아예 오지 않으면 실패한 요청이 없어 SLO가 초록이다. 호출 규칙에 '비정상적 트래픽 급변'이라는 말만 있고(observability §3 규칙 5) 규칙은 없다.
  5. 판단 순서 ④가 '원인'이라 원인 분석부터 하라는 뜻으로 읽힌다. ⑤의 명령 목록에 '최근 변경이면 되돌리기'가 없다.
  6. 장시간 시험이 없고, 메모리·파일 디스크립터가 서서히 느는 것을 잡는 경보도 없다.
  7. 정리 규칙이 비어 있다. 처리 끝난 Outbox 행, Redis Stream에 쌓인 홀드 이벤트, CDC 복제 슬롯이 붙잡는 WAL, 연결 풀의 유휴 연결을 언제 어떻게 치우는지 정하지 않았다.
- 확인한 원문(2026-10-20):
  - Node.js 문서(v26 현행판): `--report-on-fatalerror`는 메모리 부족 같은 런타임 치명 오류로 끝날 때 힙·스택·이벤트 루프 상태·자원 사용을 담은 진단 보고서를 쓴다. 보고서는 기본으로 환경 변수를 담고 `--report-exclude-env`(v23.3.0·v22.13.0)로 뺀다. `--report-exclude-network`(v22.0.0·v20.13.0)는 네트워크 인터페이스를 뺀다. 보고서는 `process.report.writeReport()`로도 쓴다. `--heapsnapshot-near-heap-limit`는 v24.13.1·v22.22.1부터 실험 기능이 아니고, 스냅샷은 시간과 V8 힙 안팎의 메모리를 쓴다. v8 문서: 힙 스냅샷은 그때 힙의 약 두 배 메모리가 필요해 OOM 킬러에 죽을 수 있고, 만드는 동안 이벤트 루프를 막는다. `SIGUSR1`은 디버거 시작용으로 예약돼 있고 `--disable-sigusr1`(v23.7.0·v22.14.0, v24.8.0·v22.20.0부터 실험 아님)로 끈다.
  - 쿠버네티스 문서: 생존 프로브를 잘못 구현하면 부하 때 컨테이너 재시작으로 연쇄 장애가 난다. 준비 상태가 실패하면 EndpointSlice 컨트롤러가 그 파드의 IP를 일치하는 모든 Service에서 뺀다. Downward API 볼륨은 파드 주석을 파일로 보이고, 바뀌면 원자적으로 새로 쓴다(subPath로 붙이면 갱신되지 않는다). emptyDir의 데이터는 컨테이너가 죽어도 남는다. kube-apiserver `--event-ttl`의 기본값은 1시간이다. 임시 디버그 컨테이너(`kubectl debug --target`)는 다른 컨테이너의 프로세스 공간을 함께 쓴다.
  - AWS Builders' Library 'Implementing health checks'(David Yanacek, 2019-12): 공유 의존성 장애처럼 서버들이 함께 실패하는 이유로 아직 일할 수 있는 서버를 빼면 자동화가 해를 끼친다. Amazon 팀들은 빠르게 반응하는 부하 분산기 헬스 체크를 로컬 상태로 제한하는 편이다.
  - PostgreSQL 18 문서: `statement_timeout`은 문장이 서버에 도착해 끝날 때까지 잰다. `idle_in_transaction_session_timeout`은 열린 트랜잭션 안에서 기다리는 세션을 끊어 잠금과 테이블 팽창을 막는다. `idle_session_timeout`은 연결 풀을 거치는 연결에 걸지 말라고 경고한다. 세 값 모두 postgresql.conf 전체 설정은 권하지 않는다. `ALTER ROLE … SET`은 그 역할이 새 세션을 열 때(로그인 때만) 기본값이 된다. `SET LOCAL`은 그 트랜잭션 끝까지만 간다. `pg_cancel_backend`·`pg_terminate_backend(pid, timeout)`는 `pg_signal_backend` 권한으로 쓸 수 있고 슈퍼유저 세션은 끊지 못한다. `pg_monitor`는 통계 보기용 역할이다. `max_slot_wal_keep_size`의 기본값 -1은 복제 슬롯이 붙잡는 WAL에 한도가 없다는 뜻이다.
  - PgBouncer 문서: 트랜잭션 풀링에서 세션 `SET/RESET`은 지원하지 않는다. 추적하는 시작 매개변수 밖의 매개변수는 오류이고, `ignore_startup_parameters`에 넣으면 무시한다. `query_wait_timeout`은 서버 연결을 기다리는 쿼리의 상한(기본 120초)이다. `idle_transaction_timeout`의 기본값은 꺼짐이다. `query_timeout`은 서버 `statement_timeout`보다 조금 길게 두고 네트워크 문제에만 쓰라고 한다. `server_idle_timeout`은 600초, `server_lifetime`은 3,600초가 기본이다.
  - node-postgres(문서와 소스): `statement_timeout`·`lock_timeout`·`idle_in_transaction_session_timeout` 클라이언트 옵션은 연결 시작 매개변수로 보낸다(`getStartupConf`). 풀의 `connectionTimeoutMillis`는 새 연결뿐 아니라 꽉 찬 풀에서 연결을 기다리는 시간에도 걸리고 기본 0(무한 대기)이다. `idleTimeoutMillis`는 기본 10초다. `maxLifetimeSeconds`는 중간 장치를 지나는 연결을 돌려 쓰는 데 쓴다.
  - ioredis(소스 `RedisOptions`): `commandTimeout`이 지나면 'Command timed out' 오류를 낸다. `maxRetriesPerRequest`는 기본 20, `enableOfflineQueue`는 기본 켬, `connectTimeout`은 기본 10초다.
  - Debezium Outbox 라우터: Outbox 표의 변경은 INSERT만 기대하고 UPDATE는 허용하지 않으며 DELETE는 자동으로 걸러 낸다. Valkey `XTRIM … MINID`는 6.2.0부터다.
  - OpenTelemetry Collector `k8sobjects` 수신기(로그 beta)는 쿠버네티스 객체를 pull·watch로 읽고, events를 watch로 받는 설정을 예로 든다. `k8s_events` 수신기는 alpha다.
  - Grafana k6 문서(soak testing): 평균 부하 시험과 같은 세기를 몇 시간에서 며칠 이어 응답 시간 저하, 메모리 등 자원 누수, 저장 공간 고갈을 찾는다. 전형 값은 3·4·8·12·24·48~72시간이고 스모크·평균 부하 시험 다음에 한다. Prometheus `predict_linear()`·`deriv()`는 범위 벡터로 단순 선형 회귀를 하고 게이지에만 쓴다.
  - ElastiCache 지원 명령 문서: 노드 기반 캐시는 `config`·`debug` 등이 막히고, `SLOWLOG`·`CLIENT LIST`·`LATENCY`는 서버리스 캐시에서만 막힌다. PEAKET은 노드 기반 클러스터 모드다(infra §1).
  - 개인정보 보호법(2026-09-11 시행본) §15①(수집 목적의 범위에서 이용)·§15③(당초 목적과 합리적으로 관련된 범위의 추가 이용)·§18①(목적 외 이용 제한)·§29(안전조치의무) 원문.
  - Release It! 본문은 이번에도 대조하지 못했다. 소유자가 붙인 지침 목록과 출판사 목차를 기준으로 삼았다.

## 결정

1. **재시작 전에 진단 증거를 남긴다(추천 적용)**:
   - 자동(사람 없이):
     - 치명 오류 보고서: 모든 Node 서비스를 `--report-on-fatalerror --report-exclude-env --report-exclude-network`로 띄우고 보고서를 emptyDir `/diag`에 쓴다(`--report-directory`, 크기 한도는 메모리 한도의 2배 [가정]). emptyDir는 컨테이너가 죽어도 남으므로, 다시 뜬 프로세스가 시작할 때 남은 보고서를 진단 증거 저장소에 올리고 지운다.
     - 힙 부족이 커널 OOM보다 먼저 V8 치명 오류로 나게 V8 힙 상한(`--max-old-space-size`)을 컨테이너 메모리 한도의 75% [가정]로 둔다. 커널 OOM(SIGKILL)은 보고서를 남기지 못하기 때문이다.
     - 힙 상한 근처 스냅샷(`--heapsnapshot-near-heap-limit=1`)은 기본으로 끈다. 스냅샷에 힙의 약 두 배 메모리가 들어, 켜려면 힙 상한을 메모리 한도의 40% [가정]로 낮춰야 한다. 누수가 의심되는 서비스에만 표준 변경으로 한시적으로 켠다.
     - 쿠버네티스 이벤트: OTel Collector `k8sobjects` 수신기가 events를 watch로 받아 Loki에 30일(정형 로그 보존과 같음) 남긴다.
     - DB·Redis 순간 상태: 증거 수집기(`evidence-collector`, 플랫폼 네임스페이스, 복제 1개)가 Alertmanager 웹훅으로 SEV1, 의존성 원인 SEV2, 인시던트 선언을 받으면 그 의존성의 상태를 떠 진단 증거 저장소에 올린다. PostgreSQL은 유휴가 아닌 세션(`pg_stat_activity`의 상태·대기 이벤트·시작 시각·쿼리 ID와 문장), 막는 쪽(`pg_blocking_pids()`), 복제 슬롯이 붙잡은 WAL을 뜬다. Redis는 `INFO`, `SLOWLOG GET`, `CLIENT LIST`를 뜬다. 의존성마다 10분에 한 번 [가정]이다. PostgreSQL은 `pg_monitor` 역할, ElastiCache는 이 세 명령만 허용한 RBAC 사용자로 읽는다.
   - 수동(RB-31): 긴급 접근으로 파드 하나에 주석 `peaket.io/diagnose`를 단다. 값은 `report` 또는 `heap`과 요청 시각이다(예: `heap@2026-11-02T20:10Z`). 공용 시작 코드(`peaket-platform`)가 Downward API 파일로 주석을 보고 다음 순서로 한다. 처리한 요청 값은 `/diag`에 표시해 두므로, 다시 뜬 프로세스는 주석이 남아 있어도 같은 요청을 되풀이하지 않는다.
     1. 준비 상태를 내리고 새 일(요청, Kafka 소비)을 받지 않는다.
     2. 진행 중인 일을 최대 10초 [가정] 마감한다.
     3. 진단 보고서를 쓴다.
     4. `heap`이면 메모리 여유(한도 − 지금 RSS)가 지금 힙의 두 배보다 클 때만 힙 스냅샷을 쓴다. 모자라면 건너뛰고 그 사실을 남긴다.
     5. 진단 증거 저장소에 올린다.
     6. 종료해 컨테이너를 새로 띄운다.
   - 주석이 파일에 닿기까지 kubelet 동기화로 1분 [가정]쯤 걸릴 수 있다. 실제 시간은 wbs 0.3.6에서 잰다.
   - 셸, `kubectl exec`, 임시 디버그 컨테이너를 쓰지 않는다. 운영 이미지에는 셸이 없고, 프로세스 공간을 함께 쓰는 디버그 컨테이너는 대상의 환경 변수와 메모리를 읽을 수 있다. 진단용 HTTP 끝점도 만들지 않는다. `--disable-sigusr1`로 SIGUSR1 디버거 시작을 끈다.
   - 피해 격리를 늦추지 않는다. 재시작이 완화책이면 파드 하나만 먼저 진단하고 나머지는 바로 다시 띄운다. 보안 사고가 의심되면 RB-20의 증거 보존이 먼저다.
   - 진단 증거 저장소: 운영 계정의 전용 S3 버킷과 전용 KMS 키를 쓴다. 키 정책에서 복호화는 긴급 접근 역할만, 서비스 역할은 암호화만 한다. 공개 차단과 버전 관리를 켠다. 서비스는 자기 접두사에 쓰기만 한다. 읽기는 긴급 접근으로만 하고 CloudTrail S3 데이터 이벤트로 남겨 관리자 접속기록 월 점검(RB-21)에 넣는다. 14일 [가정] 뒤 수명 주기 규칙으로 지운다. 진행 중 인시던트에 묶인 증거는 commander가 30일 [가정]까지 늘릴 수 있다. Sentry 같은 외부 서비스에는 올리지 않는다.
   - 개인정보: 힙 스냅샷과 세션 목록에는 처리 중인 개인정보와 토큰이 섞일 수 있다. 새 항목을 모으지는 않지만 내용을 가릴 수 없으므로 P1 기준으로 보호한다(data-classification). 장애 분석에 쓰는 것을 처음 처리 목적(계약 이행, 개인정보 보호법 §15①) 안의 이용으로 보는 것은 해석이다(POL-027, data-classification 법률 #25, 법률 검토 wbs 7.4.1).
2. **프로브 세 종류의 규칙을 정한다(추천 적용)**:
   - 생존(liveness): 이벤트 루프가 응답하는지만 본다. 의존성과 부하는 보지 않는다. 앱 트래픽과 다른 포트의 `/livez`이고 게이트웨이 라우트에 두지 않는다. 10초마다, 시간 초과 5초, 연속 6회 [가정] 실패(약 1분)여야 재시작한다. 부하로 이벤트 루프가 몇 초 늦는 것으로는 재시작하지 않게 넉넉히 둔다.
   - 준비(readiness): '이 파드가 지금 받을 수 있나'만 본다. 시작 작업(설정·키 읽기, 캐시 데우기)이 끝났고, 종료 중(SIGTERM 뒤)이 아니며, 진단 수집 중이 아니다. 공유 의존성(DB·Redis·Kafka·결제사·본인확인)과 부하는 보지 않는다.
     - 공유 의존성이 죽을 때 준비 상태가 함께 내려가면 모든 파드가 Service에서 빠져 보낼 곳이 없어진다. 대체 경로(좌석 DB 정렬 잠금, 진입 Degraded)가 있는 서비스도 그 경로를 쓰지 못한다.
     - 온세일에는 모든 파드가 함께 과부하라 부하로 준비 상태를 내려도 같은 일이 생긴다. 과부하는 게이트웨이 상한과 앱의 즉시 503이 맡는다(architecture §5 부하 관리 장치 표).
   - 시작(startup): 시작이 긴 서비스(캐시 데우기 등)에 둔다. 최대 60초 [가정]이고 K9의 파드 확장 60초와 같다. 시작 프로브가 통과하기 전에는 생존·준비 프로브가 돌지 않는다.
   - 의존성 상태는 프로브가 아니라 지표와 경보(의존성 원인 SEV2), T-30분 점검의 저장소 헬스체크가 본다. 새 판의 설정 오류(잘못된 비밀 등)는 카나리 분석의 서버 오류 비율이 잡는다.
   - 공용 시작 코드가 세 프로브를 만든다. 준비 조건에 공유 의존성 호출이 들어가면 템플릿 시험이 실패한다(D-T19).
3. **앱 시간 초과 기본값을 정하고 느린 쿼리를 끊는 길을 둔다(추천 적용)**:
   - 표는 docs/architecture.md §5 '시간 초과 기본값'에 둔다. 값은 모두 [가정, wbs 0.3.6·2.11.2에서 재고 확정]이고 정적 설정이다(온세일 중 동결, devops §5.4).
   - PostgreSQL 서버 쪽 상한은 서비스 DB 사용자의 역할 기본값(`ALTER ROLE … SET`)으로 둔다. 마이그레이션 실행기의 별도 파일로 바꾸는 표준 변경이다.

     | 역할 | `statement_timeout` | `idle_in_transaction_session_timeout` |
     | --- | --- | --- |
     | 핫패스(purchase·payment·identity, POL-028의 핫패스 묶음 가운데 PostgreSQL을 쓰는 서비스) | 1초 | 10초 |
     | 일반 API(ticket·ops·core) | 5초 | 10초 |
     | 배치·마감·정산 작업 | 60초 | 60초 |

     - 마이그레이션은 devops §7.2 규칙(`lock_timeout` 3초 등) 그대로다.
     - 역할 기본값은 새 세션에만 걸리므로 PgBouncer의 서버 연결이 다시 맺어질 때(최대 `server_lifetime` 1시간)까지 옛 값이 남는다.
     - 요청의 남은 데드라인이 역할 상한보다 짧으면 트랜잭션 첫 문장으로 `SET LOCAL statement_timeout`을 보낸다. 트랜잭션이 끝나면 사라지므로 트랜잭션 풀링에서도 쓸 수 있다. 왕복이 하나 늘어 핫패스에 쓸지는 0.3.6에서 재고 정한다.
     - 쓰지 않는 것: node-postgres의 `statement_timeout`·`idle_in_transaction_session_timeout` 연결 옵션(시작 매개변수라 PgBouncer가 거절하거나, 무시 목록에 넣으면 조용히 버려진다), 세션 `SET`(트랜잭션 풀링에서 지원하지 않는다), `idle_session_timeout`(풀과 맞지 않는다).
   - PgBouncer(ADR-0028): `query_wait_timeout` 120초 → 5초, `idle_transaction_timeout` → 그 PgBouncer를 쓰는 역할의 가장 긴 `idle_in_transaction_session_timeout` + 5초, `query_timeout` → 가장 긴 `statement_timeout` + 5초(서버 값보다 조금 길게, PgBouncer 문서 권고)로 둔다. `server_idle_timeout`·`server_lifetime`은 기본값이다. 이 값은 PgBouncer 인스턴스 전체에 걸리고, PgBouncer 배치(클러스터별 또는 서비스별)가 아직 정해지지 않아 2.11.2에서 함께 정한다.
   - 앱 연결 풀(node-postgres `pg.Pool`): `connectionTimeoutMillis`는 핫패스 100ms·일반 1초다. 기본값 0은 무한 대기라 반드시 둔다. `idleTimeoutMillis`는 10초(기본값), `maxLifetimeSeconds`는 30분이다. 풀 크기 `max`는 PgBouncer 연결 수와 함께 정한다. 풀 대기가 한도를 넘으면 기다리지 않고 503과 `Retry-After`로 답한다.
   - Redis(ioredis): `commandTimeout`은 핫패스 100ms·일반 500ms다. 핫패스는 `enableOfflineQueue: false`와 `maxRetriesPerRequest: 1`로 연결이 끊긴 동안 명령을 쌓지 않고 바로 실패해 대체 경로(좌석 DB 정렬 잠금 등)로 간다.
   - gRPC 데드라인과 외부 HTTP 시간 초과는 지금 규칙(ADR-0009, 결제사 승인 호출 2초)을 그대로 둔다.
   - 지표: `db_pool_wait_timeout_total{service}`, `db_statement_timeout_total{role}`(SQLSTATE 57014), `redis_command_timeout_total{cluster}`.
   - 느린 쿼리 끊기(RB-32): 긴급 접근의 DB 조회 경로(devops §10.3의 SSM 세션, IAM DB 인증, pgAudit 세션 기록)로 `pg_signal_backend`를 가진 운영 역할 `ops_signal`을 쓴다.
     1. 증거 수집기 스냅샷이나 `pg_stat_activity`로 대상을 찾는다. 잠금을 쥔 쪽(`pg_blocking_pids()`) 가운데 가장 오래된 것부터 본다.
     2. `pg_cancel_backend(pid)`로 그 쿼리만 취소한다.
     3. 10초 [가정] 뒤에도 남으면 `pg_terminate_backend(pid, 5000)`로 세션을 끊는다. 그 트랜잭션은 되돌려진다.
     4. 앱 풀이 다시 연결하는지 본다.
     5. 쿼리 ID를 포스트모템에 남긴다. 슈퍼유저 세션은 끊지 못한다.
4. **처리량 급감 경보를 둔다(추천 적용)**:
   - 지표: `funnel_stage_total{event_id, stage}`(stage: admitted·first_hold·payment_accepted·approved·issued). queue-svc·purchase-svc·payment-svc·ticket-svc가 낸다. 알림에 쓰는 다섯 단계 카운터만 Prometheus에 두고(활성 회차 10개 이하 × 5), 상세 퍼널은 그대로 Flink → ClickHouse다(observability §8).
   - 온세일(SEV2, 종류 `flow`): 앞 단계가 분당 100건 [가정] 넘게 이어지는 동안 5분 창의 '다음 단계 ÷ 앞 단계'가 기준선의 절반 [가정] 아래면 울린다. 대상은 입장 → 첫 홀드 성공(`journey` hold)과 첫 홀드 성공 → 결제 접수(`journey` payment)다. 승인 → 발권은 결제-발권 불일치 불변식(60초)이 이미 본다.
   - 기준선: ops-svc가 T-30분 점검 때 같은 규모 회차의 중앙값(골드, observability §13의 기준선과 같은 출처)을 게이지 `funnel_baseline_ratio{event_id, transition}`로 내보낸다. 비교할 회차가 없으면 0.8 [가정]을 쓴다.
   - 평시(SEV2, `flow`): 로그인 성공·주문 접수의 30분 처리량이 지난주 같은 시각의 절반 [가정] 아래이고 지난주 값이 분당 20건 [가정] 이상이면 울린다. 두 주 가운데 한쪽이라도 온세일 창이면 판정하지 않는다.
   - 같은 회차·여정의 예산 SEV1이 울리면 알림이 억제된다(ADR-0069 결정 4). 회차 ID가 있어 콘솔 '이 회차 판단' 묶음에 뜬다.
   - 런북 RB-33:
     1. 퍼널에서 막힌 단계를 찾는다.
     2. 그 단계 화면의 브라우저 오류(Sentry 새 오류 종류), CSP 위반, 결제사 SDK 로드 실패, 최근 프런트엔드 배포를 본다.
     3. 최근 변경이면 되돌린다(RB-23).
     4. 결제 단계면 결제사 상태를 보고 명령 6을 검토한다.
     5. 원인을 모르면 명령 2(입장 일시정지)로 들어오는 사람을 멈추고 엔지니어를 부른다.
   - `OpsAlert.kind`에 `flow`를 더한다. 이 경보는 observability §3 규칙 5의 '비정상적 트래픽 급변'을 규칙으로 만든 것이다.
5. **판단 순서 ④⑤를 고쳐 쓴다(추천 적용)**:
   - ④는 '원인'이 아니라 손잡이를 고르는 몇 분짜리 분류다. 최근 변경인가(되돌리기), 외부 의존 서비스인가(명령 6), 포화인가(명령 1·2)만 가르고, 모르면 ⑤의 약한 명령부터 쓴다. 근본 원인 분석은 안정된 뒤 포스트모템에서 한다.
   - ⑤에 '최근 변경이면 되돌리기(RB-23, 긴급 변경)'를 넣는다. 재시작이 필요하면 격리를 늦추지 않는 범위에서 파드 하나의 진단 증거를 먼저 남긴다(RB-31).
   - observability §13과 guide/10 §6을 고친다. ADR-0049 본문은 그대로 두고 상태 줄에 적는다.
6. **장시간 시험과 자원 누수 의심 경보를 둔다(추천 적용)**:
   - 장시간 시험(docs/verification.md §3.6, NFR-027): 오래 떠 있는 서비스(queue-svc, purchase-svc, payment-svc, realtime-gw, Outbox 릴레이·소비자)를 로컬에서 하나씩 6시간 [가정] 돌린다. 세기는 그 서비스가 SLO 안에서 견딘 최대 도착률의 50% [가정]이고 각본은 평균 부하 시험 그대로다. 첫 30분 [가정]은 데우기로 뺀다.
   - 판정: GC 뒤 힙, RSS, 열린 FD, 활성 핸들, DB·Redis 연결 수의 시간당 기울기(1차 회귀)가 시작값의 1% [가정] 이하, 재시작 0회, p99 변화 10% [가정] 이내, 오류율 SLO 안.
   - 비용: PC에서 돌려 0원이다(소유자 지출 상한 5만 원).
   - 자원 누수 의심 경보(SEV3, `hygiene`): 컨테이너 작업 메모리, 열린 FD, 활성 핸들, DB 연결 수가 6시간 추세(`predict_linear`)로 24시간 [가정] 안에 한도에 닿는다고 나온 채 1시간 이어지면 울린다. 런북은 RB-31(파드 하나 진단)과 담당 팀 이슈다. 한도에 닿을 시각이 대형·중형 온세일 창 안이면 SEV2로 올리고, 창 전에 동결 창 밖에서 롤링 재시작한다 [가정].
7. **정리 규칙을 채운다(추천 적용)**:
   - DB Outbox: 운영(Debezium CDC 릴레이, data.md §4)에서는 행을 INSERT만 하고 고치지 않는다. Outbox 라우터는 UPDATE를 받지 않고 DELETE는 걸러 낸다. Outbox 표를 일 단위 범위 파티션으로 두고 3일 [가정] 지난 파티션을 정비 시간(04:00~06:00)에 떼어 지운다. 지우기 전에 CDC 커넥터가 그 파티션을 지났는지(커넥터 지연 1일 미만) 확인한다. 로컬·v0 폴링 릴레이는 보낸 행에 보낸 시각을 쓰고 같은 파티션 규칙으로 지운다.
   - CDC 복제 슬롯: 커넥터가 멈추면 슬롯이 WAL을 붙잡아 저장 공간이 는다(`max_slot_wal_keep_size` 기본값은 한도 없음). 슬롯이 붙잡은 WAL이 10GB [가정]를 넘거나 슬롯이 30분 [가정] 넘게 비활성이면 SEV2(`hygiene`)다. Aurora에서 `max_slot_wal_keep_size`를 쓸 수 있는지는 확인 필요(wbs 0.3.2)다.
   - Redis Stream(`s:{event:E}:stream`): 릴레이가 Kafka 전송 확인을 받은 항목까지 `XACK`한 뒤 `XTRIM … MINID`로 지우고, 키는 회차 판매 종료 + 1일 [가정] TTL로 지운다.
   - 연결 풀 유휴 회수: 결정 3의 `idleTimeoutMillis`·`maxLifetimeSeconds`와 PgBouncer `server_idle_timeout`·`server_lifetime` 기본값으로 한다. `idle_session_timeout`은 쓰지 않는다.

## 검토한 대안

| 대안 | 고르지 않은 이유 |
| --- | --- |
| 준비 상태에 의존성 연결 확인을 넣음 | 의존성 하나가 죽으면 모든 파드가 빠진다. 준비되지 않은 파드는 Service에서 빠지고, 다 빠지면 보낼 곳이 없다. 대체 경로도 쓰지 못한다 |
| 진단을 `kubectl exec`나 임시 디버그 컨테이너로 | 운영 이미지에 셸이 없다. 디버그 컨테이너는 대상의 환경 변수와 메모리를 읽을 수 있어 범위가 너무 넓다 |
| 진단용 HTTP 끝점(관리 포트) | 디버그 기능이 운영에 열리는 표면이 생긴다(ASVS 13.4.2). 주석은 쿠버네티스 감사 로그에 남는다 |
| 모든 서비스에서 힙 상한 근처 스냅샷을 자동으로 | 스냅샷에 힙의 두 배 메모리가 들어 힙 상한을 크게 낮춰야 하고, 만드는 동안 이벤트 루프가 멈춘다 |
| node-postgres 연결 옵션으로 `statement_timeout` | PgBouncer 트랜잭션 풀링에서 시작 매개변수가 거절되거나 조용히 버려진다 |
| 처리량 급감을 고정 숫자(분당 N건 아래)로 | 회차 규모가 수십 배씩 달라 한 숫자로 못 잡는다. 단계 비율과 기준선을 쓴다 |
| 장시간 시험을 클라우드에서 | 6시간 × 서비스 수의 클라우드 비용이 지출 상한(5만 원)을 넘는다. 로컬 한 대로 하고, 클러스터 규모의 누수는 운영 경보로 메운다 |
| 진단 수집을 콘솔 명령 13으로 | 화면·API·승인 흐름이 늘어난다. 드물게 쓰고 개인정보가 담긴 메모리를 다루므로 긴급 접근(쓰는 순간 경보, 세션 기록, 사후 검토)이 맞다 |

## 결과와 트레이드오프

- 재시작해도 원인 단서가 남는다. 증거는 개인정보가 섞인 메모리 사본이라 보관을 짧게(14일) 하고 읽기를 긴급 접근으로만 연다.
- 공유 의존성이 죽어도 파드가 빠지지 않고 빠른 실패와 대체 경로로 답한다. 대신 설정이 틀린 새 파드도 준비 상태가 되므로 카나리 분석에 기댄다.
- DB·Redis 대기가 데드라인 안에서 끊긴다. 상한이 짧으면 정상인 긴 쿼리가 실패할 수 있어 역할별로 나눈다.
- 오류 없는 장애를 퍼널 비율로 잡는다. 비교할 회차가 없는 초기에는 고정 기준선에 기대므로 놓칠 수 있다.
- 반영 수치(2026-10-20): ADR 69 → 70, NFR 26 → 27(NFR-027), 런북 30 → 33종(RB-31~33), Game Day 22 → 25종(G-23~25), 용어 167 → 172, POL-027 해석 26 → 27건. WBS 작업 172 → 174개(0.3.6·6.5.1 신설), 381.5 → 389일이다. 검토 기록은 R-79다.

## 되돌릴 조건

- 진단 수집이 Game Day에서 파드 재시작을 늦추거나 메모리 부족으로 실패하면 힙 스냅샷을 빼고 보고서만 남긴다.
- 준비 상태에서 의존성을 뺀 탓에 설정이 틀린 새 판이 카나리를 지나간 사례가 나오면, 시작 때 한 번 하는 의존성 확인을 시작 프로브에 넣는 것을 다시 본다.
- 처리량 급감 경보가 온세일당 1회 넘게 헛경보를 내면 기준선과 절반 기준을 다시 본다.
- 장시간 시험이 재현하지 못한 누수가 운영 경보로 잡히면 시험 시간과 세기를 늘린다.
