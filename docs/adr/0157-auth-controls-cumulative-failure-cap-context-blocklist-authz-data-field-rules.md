# ADR-0157: 관리 계정 로그인에 줄지 않는 실패 누계와 출발지 단위 계수를 두고, 금칙어는 비밀번호 전체로 대조하며, 권한은 데이터·칸 단위 규칙과 토큰 역할로 검사한다(2026-10-30)

- **상태**: 채택 (2026-10-30. 소유자가 ADR-0154 결정 3으로 예정 보안 문서인 인증 통제와 권한 표를 지금 쓰기로 정했다. 이 ADR의 설계 판단은 모두 추천 적용이다. 정본은 docs/security/auth-controls.md(잠금 규칙은 docs/features/identity.md §6에서 옮겼다)와 docs/security/authz-matrix.md다. 역할 × 기능 표는 그대로 planning/03 §3이다.) 2026-10-30(소유자 결정, ADR-0163·0164): 결정 12의 제안을 이행했다. openapi 작업 241개 모두에 `x-peaket-roles`를 달고 점검 도구 `roles` 검사가 본다(역할 값의 정본은 authz-matrix §5.5). 관리 계정 관리 API와 표시 이름 칸은 ADR-0163이다.
- **관련**: ADR-0001(팬은 소셜 로그인), ADR-0008(클라이언트별 게이트웨이가 경로별 역할을 본다), ADR-0102(비상 접근 계정), ADR-0154, POL-020(관리 계정), [docs/security/auth-controls.md](../security/auth-controls.md), [docs/security/authz-matrix.md](../security/authz-matrix.md), [docs/security/asvs/auth.md](../security/asvs/auth.md) 6.1.x·8.1.x, [planning/03-policies-glossary.md](../../planning/03-policies-glossary.md) §3

## 맥락

- 관리 계정(파트너·운영자·현장 스태프)의 잠금 규칙은 identity §6에 있었다. 5회 연속 실패에 15분, 다시 5회면 1시간 잠금이다.
- 정본(POL-020, data-classification)은 NIST SP 800-63B의 '연속 실패 100회 이하에서 인증 수단을 정지한다'를 지킨다고 적었다. 그러나 시간 잠금만으로는 연속 실패에 끝이 없었다. 2026-10-30에 NIST SP 800-63B-4 §3.2.2를 원문으로 확인했다(SHALL).
- 계정마다 한두 번만 넣는 크리덴셜 스터핑(유출된 아이디·비밀번호 목록을 다른 사이트에 대입하는 공격)은 계정 단위 계수에 거의 걸리지 않는다.
- 비밀번호 금칙어(ASVS 6.1.2)는 '이 문서 전까지 부분 적용'이었다. NIST §3.1.1.2는 비밀번호 전체를 대조하라고 하고, 부분 문자열 대조를 금한다.
- 권한 검사는 기능 단위 표(planning/03 §3)만 있었다. 데이터 단위 규칙(본인 것, 소속 파트너 것, 배정 회차)과 칸 단위 가림, 검사 위치가 없었다(ASVS 8.1.1·8.1.2). 또 게이트웨이가 경로별 역할을 본다는데(ADR-0008), 관리 토큰의 클레임에 역할이 없었다.

## 결정

1. **비밀번호 연속 실패 누계를 둔다**: 시간 잠금으로 줄지 않고 로그인에 성공해야 0이 된다. 50회면 계정 주인과 관제에 알리고, 100회면 보호 잠금을 건다. 보호 잠금은 2단계 인증 실패 5회 [가정]에도 걸리던 기존 상태(planning/03 §2.7의 A7)와 같다. 보호 잠금 중에는 모든 로그인과 재인증 토큰 발급을 거절하고 본인 해제 링크를 보내지 않으며, 운영자의 재초대로만 푼다(스스로 하는 재설정이 없으므로).
2. **출발지 단위 계수**: 한 IP에서 1시간에 서로 다른 이메일 5개 이상이 실패하면, 그 IP의 관리 계정 로그인에 1시간 사람 확인을 건다. 계정 하나에 1시간 서로 다른 IP 5곳 이상이면 그 계정의 로그인에 사람 확인을 걸고, 이것만으로 보호 잠금을 걸지는 않는다. 로그인 경로에는 웹 방화벽 속도 규칙(IP당 5분 50회)을 둔다.
3. **전체 실패율 경보**: 정한 실패 건수를 넘으면 SEV3를 내고, 모든 관리 계정 로그인에 1시간 사람 확인을 자동으로 건다. 새 운영 명령은 만들지 않는다.
4. **비밀번호만 맞은 로그인**: 새 출발지에서 비밀번호가 맞았는데 2단계 인증을 끝내지 않으면 계정 주인에게 알리고, 다음 로그인 뒤 비밀번호를 바꾸게 한다.
5. **계정 유무를 숨긴다**: 없는 이메일도 같은 수로 세고 같은 응답을 준다. 24시간 안에 잠긴 적이 있는 계정은 늘 사람 확인을 건다. 사람 확인 서비스가 멈추면 사람 확인이 필요한 로그인은 받지 않는다.
6. **해제 링크**: 토큰은 URL 조각에 두고, 링크당 코드를 3번 틀리면 무효다. 다시 받기는 시간당 3번이다.
7. **금칙어는 비밀번호 전체로 대조한다**: '맥락 말과 쉬운 덧붙임만으로 된 비밀번호'를 막는다. 기본·바꿈·두벌식 자판 사본 셋으로 대조한다.
   - 맥락 말은 영문 4자·한글 2자 이상이다. 파트너는 상호, 사업자등록번호, 통신판매업 신고번호, 업무 이메일 도메인을 쓴다.
   - 유출 목록은 로그인 때 30일마다 다시 본다. 비밀번호를 정할 때 유출 목록 조회에 닿지 못하면 그 비밀번호를 받지 않는다.
8. **관리 토큰에 역할과 테넌트를 싣는다**: `role`(문자열 하나)과 파트너 `tid`를 싣고, 게이트웨이가 내부 헤더 `X-User-Role`·`X-Tenant-Id`로 넘긴다. 가명정보 취급자 같은 지정은 토큰에 싣지 않고 ops-svc가 요청마다 확인한다.
9. **데이터 단위 규칙과 DB 2차 방어**: 본인 데이터·테넌트·배정 회차·자원 상태·시간 창·지정으로 거른다. 테넌트 표에는 PostgreSQL 행 보안 정책(RLS)을 켜고, 파트너 전용 DB 사용자와 트랜잭션 첫 문장의 `SET LOCAL app.tenant_id`로 거른다. 비용이 크면 조회 계층에서만 거르는 안으로 돌아간다.
10. **응답과 기록**: 비공개 자원은 404, 공개 자원 쓰기는 403이다. 인가 거절은 보안 이벤트로 남기고, 한 계정에서 10분에 20건이면 SEV3다.
11. **권한 변경과 재인증**: 역할을 바꾸면 그 계정의 세션을 모두 끝낸다(`ROLE_CHANGED`). 재인증 토큰은 세션(`sid`)과 작업 묶음(`act`)에 묶고, 발급할 때 DB의 지금 역할을 다시 본다.
12. **기본 거부**: 허용 역할을 적지 않은 처리기가 있으면 서비스가 시작하지 않는다. openapi 확장 칸으로 허용 역할을 적고 점검 도구로 검사하는 안은 제안으로 둔다.

13. **지정 기록 표와 조회(2026-10-30 맞추기·마지막 정리)**: 가명정보 취급자 같은 지정은 identity DB의 `admin_designation`에 한 행씩 두고(해제 시각, 해제한 행은 3년 뒤 삭제), ops-svc가 `GetAdminDesignations`로 요청마다 본다. 답이 없으면 지정 없음으로 보고 403이다. 관리 계정 표에 2단계 실패 수, 비밀번호 연속 실패 누계, 마지막 유출 확인 시각, 비밀번호 바꾸기 필요 표시를 둔다(docs/data.md §2 ①).
14. **본인 해제·비밀번호 바꾸기 경로**: 파트너·관제 각각에 `/auth/unlocks`, `/auth/unlock-links`, `/auth/password-changes`를 둔다. 다시 받기는 계정이 있든 없든 늘 202이고, 비밀번호를 바꾸면 다른 세션을 끝낸다(`PASSWORD_CHANGED`). 관리 계정 관리 API(초대·역할 변경·지정·삭제)는 아직 없어 review/open-items.md 73번에 남긴다.

## 검토한 대안

- **누계 상한에 닿으면 스스로 비밀번호를 다시 정하게 하기**: 관리 계정에 스스로 하는 재설정이 없다는 정본(asvs/auth.md 6.4.3)과 어긋난다. 기각.
- **금칙어가 '들어 있으면' 막기**: NIST가 금하는 부분 문자열 대조이고, 정상 비밀번호를 많이 거절한다. 기각.
- **지정까지 토큰에 싣기**: 지정이 바뀌어도 토큰이 끝날 때까지 남는다. 기각.
- **DB 2차 방어 없이 서비스 코드만 믿기**: 쿼리 하나의 실수가 테넌트를 넘는 노출이 된다. 기각.

## 결과와 트레이드오프

- 연속 실패에 끝이 생긴다. 공격자가 주인 로그인 없이 남의 계정을 계속 틀리면 약 20시간 [추정] 뒤 보호 잠금이 걸려 운영자 재초대를 기다린다. 50회에서 미리 알리고, 주인이 그 사이 한 번 로그인하면 누계가 0이 된다.
- 유출 목록 조회(외부 주소)가 비밀번호를 정하는 경로의 의존성이 된다.
- RLS는 쿼리 계획과 연결 묶음 설정을 함께 맞춰야 한다.
- AWS WAF의 유출 자격 대조 규칙 묶음(ATP) 요금과, 고친 고시 제5조 제6항의 대상에 팬도 드는데 팬 로그인 실패 제한을 소셜 제공자에 맡겨도 되는지는 [확인 필요]다.

## 되돌릴 조건

- 보호 잠금이 공격으로 자주 걸려 운영 부담이 크면, 보호 잠금 전에 사람 확인 강도를 올리는 단계를 더한다.
- RLS가 측정에서 핫패스 지연을 눈에 띄게 늘리면 조회 계층만으로 거르는 안으로 바꾼다.
