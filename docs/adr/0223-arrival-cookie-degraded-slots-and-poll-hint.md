# ADR-0223: 도착 시각 쿠키는 시청자 요청 함수가 바로 응답해 주고, 진입 Degraded의 번호는 칸마다 Lua로 뗀다

- **상태**: 채택(2026-11-09, 추천 적용. wbs 2.2.3 세부는 추천 적용이라는 승인 2026-10-28을 따른다). BUILD_ORDER HOT-020(wbs 2.2.3 ②). 결정 4는 소유자 결정 대기인 OPEN[25]의 판단 재료다. 같은 날 새 맥락 리뷰(높음 4, 중간 5, 낮음 7)로 결정 1·2·5·6·7·8·9·10을 고치고 결정 12를 더했다. 2026-11-09: OPEN[24]·OPEN[25]·OPEN[26]은 소유자가 추천안으로 정했다(엣지 저장소 쓰기는 ADR-0234, HOT-012는 AWS 계정이 생겨 배포하는 단계, 명세 보강은 HOT-061). 본문의 '대기' 표시는 그때의 기록이다.
- **관련**: ADR-0053 결정 2(도착 시각 쿠키), ADR-0065 결정 9(최초 방문 쿠키), ADR-0078 결정 2(S3 사본 고정), ADR-0110(입장 임박 구간의 만료 맞춤), ADR-0122(매진 처리), ADR-0179(진입 ② 파드별 묶음), ADR-0181·0186(장애 전환과 RB-05), ADR-0219 결정 1·4(엣지 매진 표시와 저장소 권한), [docs/features/queue-admission.md](../features/queue-admission.md) §4 '도착 시각 쿠키·진입 Degraded·비상 경로 힌트의 첫 구현'·§9·§10, [docs/data.md](../data.md) §3 `q:{event:E}:arr_slots`·`q:arr:{reqId}:E`·`q:{event:E}:notice`, [docs/infra.md](../infra.md) §4.1, [docs/security/secrets-and-keys.md](../security/secrets-and-keys.md), [docs/security/asvs/queue-admission.md](../security/asvs/queue-admission.md)

## 맥락

- 용어: HMAC은 비밀 키로 만든 위조 확인용 값이고 MAC은 그 값이다. base64url은 이진 값을 URL과 쿠키에 쓸 수 있는 글자로 바꾼 표기다. Lua는 Redis 안에서 여러 명령을 한 번에 실행하는 스크립트다. `SETRANGE`는 문자열의 일부 바이트를 한 번에 덮어쓰는 Redis 명령이다.
- 진입 Degraded(큰 장애 때 부가 기능을 미리 정한 범위에서 줄여 버티는 운영 모드)에서는 엣지(사용자 가까이에 둔 CDN 서버)가 도착 시각을 찍어 주고, 원본은 그 시각의 100ms 칸 순서대로 번호를 준다(queue-admission §9). 저장소에 엣지 함수 코드가 없고, 쿠키를 받는 코드, 칸을 떼고 닫는 코드도 없었다.
- 대기 상태 파일의 `pollHintMs`(다음 폴링까지의 최소 간격)는 늘 0이었고, S3 대체 원본 사본을 쓰는 곳도 없었다.
- AWS 문서에서 확인한 것(2026-11-09):
  - 시청자 응답 함수는 원본이 400 이상을 돌려주면 돌지 않는다: "CloudFront doesn't invoke edge functions for viewer response events when the origin returns HTTP status code 400 or higher"(Restrictions on all edge functions, https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/edge-function-restrictions-all.html ).
  - 함수 이벤트의 `request`는 시청자가 보낸 요청을 나타낸다고 적혀 있다. 시청자 요청 함수가 고친 헤더가 시청자 응답 함수의 이벤트에 보인다는 문장은 없다(CloudFront Functions event structure, https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/functions-event-structure.html ).
  - 캐시 동작 하나의 이벤트마다 함수는 하나다. 함수 하나에 붙는 키 값 저장소는 1개다(CloudFront 한도 표, ADR-0219).
  - 런타임 2.0은 `async`/`await`, `crypto.createHmac`, `Buffer`의 `base64url`을 지원하고, `Date`는 함수 시작 시각으로 고정된다. 저장소 읽기 `get()`은 키가 없으면 오류를 내므로 `try`로 감싸라고 적혀 있다(https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/functions-javascript-runtime-20.html , https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/functions-custom-methods.html ).

## 결정

1. **엣지 함수는 진입 경로의 시청자 요청 함수 하나다(`services/queue-svc/edge/entry-viewer-request.js`).** Q-T56 PoC 전이라 CloudFront Functions 런타임 2.0을 전제로 쓰고, 시험은 Node로 흉내 낸다(Q-T65, 함수 크기 10KB 한도와 런타임이 받지 않는 문법도 시험이 본다). 함수는 저장소를 읽기만 한다. 순서는 아래다.
   - 매진 표시 `sale:{회차 ID}`를 읽어 켜져 있으면 410을 바로 낸다(ADR-0219 결정 1).
   - 진입 Degraded 표시 `mode:entry`를 읽는다. 값은 JSON `{"on": 참·거짓, "expireAtMs": 유닉스 밀리초}`이고, 꺼져 있거나 만료됐거나 읽지 못하면 원본으로 그대로 보낸다.
   - Degraded면 쿠키가 있는 요청은 엣지에서 먼저 확인한다(MAC·회차·10분·`sid`). 맞으면 원본으로 보낸다. 없거나 틀리면 서명 키를 읽어 새 쿠키를 싣고, 원본에 보내지 않고 503을 바로 낸다. 이것이 평탄화다(원본에 닿는 요청을 다시 보내기 시간으로 흩는다).
   - 503의 `Retry-After`는 0~15초 고른 분포의 정수 [가정]이다(Q-T16의 다시 보내기 범위). 본문은 `dependency-unavailable` Problem JSON이다. 화면은 503을 이미 같은 진입 요청 ID로 다시 보내므로 화면 변경은 없다.
   - 저장소 읽기가 실패하면 그 기능만 건너뛰고 원본으로 보낸다(서명 키를 못 읽으면 서명 없이 보낸다, ADR-0219 결정 1). `sid`는 게이트웨이처럼 액세스 토큰 쿠키나 `Authorization` 머리의 JWT에서 읽는다. 읽지 못해도 서명 없이 보낸다(게이트웨이가 401로 끝낸다).
   - Degraded인데 서명 없이 보낼 때는 머리 `x-peaket-arrival: unsigned`를 단다. queue-svc가 `absent`로 세어, 서명 없이 지나간 진입을 드러낸다. 바깥이 보낸 같은 머리는 함수가 지운다.
   - 경로는 퍼센트 인코딩을 풀어 본다. 원본 라우터가 풀어 받는 경로가 엣지 판단을 비켜 가지 않게 하려는 것이다.
2. **저장소 키는 접두사로 겹치지 않게 나눈다.** `sale:{회차 ID}`(매진 표시), `mode:entry`(진입 Degraded 표시), `arr:cur`(지금 서명에 쓰는 kid), `arr:key:{kid}`(서명 키). 서명 키 값은 base64url 글자 그대로 HMAC 키로 쓴다(AWS의 런타임 2.0 예제가 저장소에서 읽은 글자를 그대로 `createHmac`의 키로 쓴다. `Buffer` 키는 문서로 확인하지 못했다). 양쪽이 같은 글자를 쓰고, 32바이트 이상의 무작위 값이라 엔트로피는 같다.
3. **쿠키 값의 꼴을 정한다.** `v1.{kid}.{회차 ID}.{도착 시각 밀리초}.{요청 ID base64url}.{sid}.{MAC base64url}`이고 MAC은 `HMAC-SHA256(키, "PEAKET-arrival-v1." ‖ 앞의 여섯 칸을 점으로 이은 글)`이다. CloudFront 요청 ID에는 `=`이 들어갈 수 있어(쿠키 글자로 허용되지 않음) base64url로 바꾼다. 도착 시각은 함수 시작 시각이다.
4. **OPEN[25]의 (나)(시청자 응답 함수로 서명을 옮겨 저장소를 나눔)는 쓸 수 없다고 판단한다.** 까닭은 셋이다.
   - 평탄화는 원본에 보내지 않고 엣지가 바로 응답하는 데서 나온다. 시청자 응답 함수는 원본 응답 뒤에 돌므로, 쿠키를 주려면 요청이 원본까지 가야 한다. 원본이 느릴 때 쓰는 모드인데 원본 부하를 줄이지 못한다.
   - 원본이 503을 내면(Degraded에서 흔한 응답) 시청자 응답 함수가 돌지 않아 쿠키를 줄 길이 없다.
   - 요청 때 잡은 시각을 응답 함수에 넘길 문서상 길이 없다. 함수 이벤트의 `request`는 시청자가 보낸 요청이다.
   - 그래서 매진 표시와 서명 키는 같은 시청자 요청 함수의 같은 저장소에 남는다. OPEN[25]는 (다)+(라) 추천을 그대로 둔다.
   - 최초 방문 쿠키 키는 나눈다. 그 쿠키는 사전 검증 경로(다른 캐시 동작)의 201 응답에 싣는 값이므로, 그 경로의 시청자 응답 함수와 따로 둔 저장소를 쓸 수 있다. 진입 함수의 저장소에는 넣지 않는다. 코드는 BUILD_ORDER BOT-055가 한다.
5. **queue-svc는 쿠키를 번호를 받기 직전에 한 번만 받는다.** 선점 뒤 번호를 받을 때(`PROCEED`)만 쿠키를 읽는다. 응답을 잃은 재시도(`RECORDED`)는 쿠키를 보지 않는다. MAC·회차·`sid`(게이트웨이가 확인한 세션)·10분 [가정]·시각이 5초 [가정] 넘게 앞서지 않음을 본 뒤 `q:arr:{요청 ID}:E`를 `SET NX`로 잡는다. 값은 진입 요청 ID다. 같은 진입 요청 ID의 다시 보내기는 받아 주고(응답 전에 다시 온 요청), 다른 진입 요청은 쿠키를 무시하고 일반 진입이다(ADR-0053 결정 2의 '한 번만'을 진입 요청 단위로 정한다). 요청 ID를 잡지 못하면(대기열 Redis 일시 장애) 쿠키를 버리지 않고 503으로 끝내, 같은 진입 요청 ID로 다시 오게 한다. 키 환경 값은 `PEAKET_ARRIVAL_COOKIE_KEY`·`PEAKET_ARRIVAL_COOKIE_KEY_PREVIOUS`(`{kid}:{키 글자}`)이고, 없으면 local·ci·demo는 쿠키를 읽지 않으며 staging·prod는 시작에 실패한다.
6. **칸 떼기는 진입 ② Lua에 넣는다(`NUMBER_BATCH_LUA`).** 판매 상태·세대 키·묶음 확인을 그대로 지나, 번호를 낼 때 쿠키가 있는 요청은 칸에서 준다. 인수와 키는 뒤에 붙여 측정 도구의 호출은 그대로 돈다.
   - 칸 k = `floor(도착 시각 ÷ 100)`. 칸 k를 처음 본 Lua가 `next`부터 k까지의 칸을 차례로 뗀다. 그래서 늦게 뗀 칸도 앞 칸보다 앞 번호가 되지 않는다.
   - 칸 크기: 처음 칸부터 100칸(10초) 동안은 첫 크기 3만 [가정](초당 20만 건 × 0.1초 × 1.5, ADR-0181 결정과 같이 회차 하나의 진입 상한을 쓴다). 그 뒤는 직전 100칸이 지금까지 쓴 번호 수의 최댓값 × 1.5(올림)다. 직전 100칸이 모두 비었으면 쉬었다가 다시 몰린 때로 보아, 빈 칸은 건너뛰고 그 칸을 새 첫 칸으로 삼아 첫 크기로 다시 뗀다.
   - 한 Lua에서 떼는 양은 10만 [가정]까지다. 칸을 여러 개 한 번에 떼면 RB-05가 건너뛰는 12만 [가정]을 넘어, 장애 전환으로 잃은 칸의 번호가 건너뛴 구간 밖으로 나갈 수 있기 때문이다. 남은 몫보다 큰 칸은 자르지 않고 다음 호출이 온전한 크기로 뗀다(작게 잘린 칸은 일찍 차서 넘침이 는다). 한 호출의 첫 칸만 상한까지 줄인다.
   - 칸이 닫혔거나(`closed_upto` 이하, 또는 칸 끝 + 20초 [가정]이 지남) 믿지 못하는 칸이거나(`lost_upto` 이하) 구간이 찼거나 시각이 지금보다 5초 [가정] 넘게 앞서면 그 요청은 카운터 끝의 일반 번호를 받는다. 20초는 화면의 다시 보내기 최댓값 15초 × 1.2 = 18초에 왕복 여유를 더한 값이다. 처음 10초로 정했더니 쿠키를 받은 사람의 약 40%가 닫힌 칸에 닿았다. 평탄화 폭(0~15초)을 줄이지 않고 닫는 시간을 늘렸다. Degraded가 끝나면 20초 안에 더 떼지 않는다(떼기는 닫히지 않은 칸의 쿠키가 올 때만 일어난다).
   - 장애 전환으로 세대가 바뀌면 진입 Lua나 리더의 닫기 중 먼저 온 쪽이 그때까지 뗀 칸을 믿지 못하는 칸으로 표시한다(`lost_upto`). 옛 칸의 `used`는 복제 지연 안에 쓴 값을 잃었을 수 있어 그 칸에서 번호를 다시 주면 같은 세대 안에서 번호가 겹칠 수 있기 때문이다.
   - 모형 시험(칸마다 20건, 30초, Retry-After 0~15초 × 1~1.2 + 왕복 0~0.5초)의 값: 닫힌 뒤 온 비율 0.33%, 구간이 넘친 비율 0%, 쓰지 않은 번호 21%다. 합격선은 각각 1%·5%·50% [가정]이다(Q-T16).
7. **리더가 칸을 닫고 쓰지 않은 번호를 빠진 번호로 돌린다(`admission-ctrl` `ARRIVAL_CLOSE_LUA`).** 1초마다 회차별로, 칸 끝 + 20초가 지난 칸을 닫고 `base + used` ~ `base + size − 1`을 빠진 번호 비트맵에 켠다(온전한 바이트는 `SETRANGE`로). 한 번에 200칸·20만 번호 [가정]까지만 하고 다음 주기에 잇는다. 닫기 전에 세대 키를 본다. 장애 전환 뒤 RB-05 전이거나 복제 확인 전이면 아무것도 하지 않는다(그때의 `used`는 복제 지연으로 줄어 있을 수 있다). 칸 기록의 세대가 지금 세대와 다르면 `lost_upto`를 먼저 적는다. `lost_upto` 이하의 칸은 돌려주지 않고 칸 기록만 지운다. `used`를 잃었을 수 있어 돌려주면 받은 사람의 번호가 빠진 번호가 된다. 칸 떼기를 다시 시작할 때 건너뛴 빈 칸의 범위(`gap_from`~`gap_to`)는 한 번에 넘어간다. `first` 앞을 통째로 건너뛰면 쉬기 전 칸의 기록(아직 닫히지 않은 칸)을 돌려주지 못한다.
8. **상태 조회 Degraded의 표시는 `notice`의 `stateDegraded` 칸이다.** 회차와 전체 범위(`q:{event:PLATFORM}:notice`) 어느 쪽이든 1이면 그 파일은 구간별 주기의 2배를 `pollHintMs`로 싣는다. 입장 임박 구간 1초, 1~5분 구간 10초, 그 밖 40초다(queue-admission §4). 임박 판정은 화면의 다음 폴링 규칙과 같다(속도가 0이면 serving 구간 + 1까지). 쓰는 쪽(명령 6)은 관제 단계(BUILD_ORDER OPS-310)다.
9. **S3 사본은 포트로 쓴다.** 저장 위치는 요청 경로와 같게 맞춘다: `queue/fallback/v1/queues/{회차 ID}/segment-states/{구간}.json`, CloudFront S3 원본의 원본 경로는 `/queue/fallback`이다(ADR-0078 결정 2의 '요청 경로와 같아야 한다'. 회차 ID가 키 앞부분에 있어 S3 접두사가 회차마다 갈린다). 메타데이터는 같은 `Expires`·`Cache-Control`이다. 파드마다 매초 파일을 만들지만 쓰는 것은 회차당 파드 하나다(`SET q:{event:E}:mirror NX PX 900` [가정]). 입장 임박 구간은 매초, 1~5분 구간 5초, 그 밖 10초 [가정]마다 쓴다. 쓰는 때는 `(초 + 구간) % 주기 = 0`으로 시각에서 정해, 쓰는 파드가 바뀌어도 주기가 같고 먼 구간의 쓰기가 초마다 나뉜다. 실패해도 파일 생성은 계속하고 실패 수를 센다. 실제 어댑터(AWS SDK)는 HOT-012에 넘긴다(OPEN[24]).
10. **배포 파이프라인 도구 `tools/edge/sync-kvs-keys.mjs`**: 원하는 항목(Secrets Manager의 서명 키, 지금 kid)을 저장소와 견주어, 없으면 넣고 다르면 다시 넣은 뒤 다른 키 이름을 경보(종료 코드 3)로 알린다. 값은 명령줄·출력에 싣지 않는다. 권한을 좁힌 임시 파일을 `--cli-input-json`으로 넘기고 끝나면 지우며, 실패 문구는 고정 글과 AWS 오류 이름만 싣는다. `peaket/peaket`이 공개 저장소이고 CI 기록도 공개이기 때문이다. 서명 키를 먼저 넣고 `arr:cur`를 마지막에 넣는다. `--rotate`를 주면 `arr:cur`만 달라진 정상 교체는 경보하지 않는다. `arr:cur`의 꼴과 서명 키 길이(32바이트 이상)를 본다. `sale:`·`mode:` 키는 건드리지 않는다. 실제 호출은 `aws cloudfront-keyvaluestore`를 부르는 드라이버이고 시험은 대역으로 한다.
11. **시험**: Q-T65(엣지 진입 함수), Q-T66(대기 상태 파일의 폴링 힌트와 S3 사본), Q-T16(칸 순서·떼기·닫기·돌리기, 비율은 모형 시험이고 장부 수치는 Phase 2 부하 시험), Q-T17(힌트 부분), Q-T29(쿠키 위조·재사용).
12. **`specs/queue.qnt`에 칸 떼기·닫기를 이번에 넣지 않는다.** 리뷰의 높음 1은 명세가 잡았을 종류의 장애 전환 버그다. 그래서 넣는 것이 맞다. 다만 지금 넣으면 비용이 크다. 칸 기록(칸마다 구간·쓴 수·세대)과 복제 지연으로 쓰기를 잃는 동작, 세대를 보지 않는 변형, 모델 기반 재생의 동작 대조(`test-int/queue-model`), 전수 검사 결과 갱신까지 0.5일 [가정]이 든다. wbs에도 없는 몫이다. 이번에는 Valkey 통합 시험으로 고정하고, 명세 추가는 BUILD_ORDER HOT-030에 넘겨 추가 요청으로 묻는다.

## 결과

- 진입 Degraded에서 엣지가 바로 쿠키를 주고 원본 요청을 시간으로 흩는다. 쿠키가 틀리면 일반 진입이라 안전 쪽으로 깨진다.
- 쿠키가 있는 요청은 칸 순서대로 번호를 받고, 쓰지 않은 번호는 10초 뒤 리더가 빠진 번호로 돌린다.
- 상태 조회 Degraded 표시를 켜면 파일과 S3 사본에 2배 힌트가 실린다.
- 남는 한계
  - 첫 크기는 Degraded 직전 1분의 실제 진입 수가 아니라 상한값이다(1초 집계는 OPS-190 뒤). 실제 진입이 적으면 번호 공간이 커지지만, 돌려주므로 앞 인원은 그대로다.
  - 장애 전환과 Degraded가 겹치면 옛 칸의 쓰지 않은 번호는 돌려주지 않는다(아무도 갖지 않은 번호로 남아 뒤 사람의 앞 인원이 그만큼 부푼다). 쓰기 지연 안에서 잃은 `used`를 알 수 없어서다.
  - 칸 떼기·닫기는 모델 검사 명세에 없다(결정 12).
  - 진입 Degraded와 상태 조회 Degraded를 켜는 쪽(명령 6)은 OPS-310이고, 그 전에는 저장소·Redis 값을 손으로 바꾸는 런북뿐이다. `mode:entry`는 지금 규칙상 배포 역할만 쓸 수 있다.
  - 엣지 함수와 실제 저장소·S3 호출은 AWS 계정이 없어 실제 CloudFront에서 돌려 보지 못했다(Q-T56, HOT-012).
  - 시청자 요청 함수와 서명 키가 같은 저장소라는 사실은 그대로다(OPEN[25]).
  - 칸 안 100ms의 순서, 엣지 거점끼리의 시계 차이, 닫힌 뒤 온 사람의 뒤로 밀림은 그대로 남는다(queue-admission §9).
