# ADR-0013: 굿즈·티켓 연동 부가 상품 정의는 MongoDB에, 돈과 재고는 PostgreSQL에

- **상태**: 채택 (2026-10-05 설계서 섹션 6 '굿즈·티켓 연동 부가 상품'에 기록, 2026-10-08 ADR로 옮김). ADR-0053(2026-10-13)이 MongoDB 인증(SCRAM-SHA-256), TLS, 저장과 백업 암호화를 정한다
- **관련**: 설계서 섹션 6 '굿즈·티켓 연동 부가 상품'(MongoDB 채택 근거 표), 25장, ADR-0007(core-svc의 shop 모듈), 섹션 2 B9
- **관련 ID**: FR-014, FR-015, FR-024, POL-016, NFR-025, SCR-015, SCR-023

## 맥락

- 상품은 유형에 따라 속성 구조, 배송 정책, 환불 규칙이 판이하게 다르다. MD 굿즈는 의류 사이즈/색상 옵션과 물리적 배송 주소를 요구하고, 공연장 주차권은 차량번호 및 제3자 전산 연동과 양도 불가 정책을 적용하며, VIP 패키지는 아티스트 기획마다 가변적인 혜택 번들 목록을 포함한다([Ticketmaster](https://blog.ticketmaster.com/vip-packages-upgrades-tickets/)).
- 아키텍처 성공 지표는 '새 상품 유형 출시 시 DB 스키마 마이그레이션 0건 달성'(B9)이다.
- 반면 금전 결제 및 실물 재고가 바인딩되는 데이터(주문서, 한정 수량 재고 확정)는 엄격한 ACID 트랜잭션과 무결성 외래키 제약이 필수적이다.

## 검토한 대안

| 대안 | 문제 |
| --- | --- |
| 1. PostgreSQL 상품 유형별 다중 테이블 | 신규 상품 카테고리가 출시될 때마다 DDL 마이그레이션 및 배포 수반 |
| 2. PostgreSQL EAV(Entity-Attribute-Value) | 복합 조건 필터링 쿼리가 복잡해지며 성능 저하 및 데이터 검증 난해 |
| 3. PostgreSQL JSONB 단일 컬럼 | 스키마 유연성은 확보되나 카테고리별 중첩 옵션의 동적 유효성 검증 및 부분 업데이트 튜닝 복잡 |
| **4. MongoDB 도큐먼트 모델 (채택)** | 인프라 운영 데이터베이스 종류가 하나 증가함(레플리카 세트 관리, 백업, 모니터링) |

## 결정

1. **가변 상품 카탈로그 정의(굿즈 및 티켓 연동 부가 상품)는 MongoDB에 영속화한다.** 상품 1건을 단일 BSON 도큐먼트로 모델링하고, 카테고리별 `$jsonSchema` 컬렉션 검증 룰을 적용하며, 속성 패턴(Attribute Pattern)과 멀티키 인덱스를 통해 이종 속성에 대한 고속 필터링을 지원한다. 또한 Change Streams를 활용하여 상품 카탈로그 수정 시 Next.js ISR 캐시 페이지 재검증(On-demand Revalidation) 파이프라인과 비동기 연동한다.
2. **주문서 데이터와 한정 재고의 영구 확정은 관계형 PostgreSQL에 격리하고, 고속 실시간 재고 차감은 Redis 인메모리에서 완결한다.** PG 결제 승인은 payment-svc를 그대로 재사용한다.
3. **주문 트랜잭션 생성 시점의 상품 판매 단가와 메타데이터 옵션 스냅샷을 주문서 테이블에 불변(Immutable) 복사한다.**
4. **MongoDB 클러스터는 core-svc의 shop 모듈만 전담 접근한다(ADR-0007의 저장소 직접 공유 금지 원칙 준수).**

## 결과

- 신규 상품 카테고리 추가 작업이 JSON 스키마 명세 및 프론트 검증 룰 추가만으로 완결되며, 아키텍처 목표인 '마이그레이션 0건' 및 출시 리드타임 단축을 달성한다.
- 트레이드오프: MongoDB 레플리카 세트 운영 비용이 발생한다. 금융 결제와 재고 트랜잭션을 PostgreSQL에 엄격히 격리함으로써 본 운영 부담을 카탈로그 정의 영역으로 한정 통제한다.

## 재검토 조건

- 비즈니스 상품 유형이 소수로 영구 고정되어 PostgreSQL JSONB 컬럼 모델로 충분해질 때
- MongoDB 인프라 운영 오버헤드가 상품 카탈로그 동적 유연성에서 얻는 비즈니스 가치를 상회할 때
