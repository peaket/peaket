# ADR-0168: 문서를 `docs/` 한 폴더로 모은다 — 코드가 중심이 되는 저장소(소유자 결정, 2026-10-30)

- **상태**: 채택 (2026-10-30. 소유자가 "일단 다음을 진행하기 전에 문서는 하나의 폴더로 모으는게 좋지 않을까요? 이제 문서가 메인이 아니라 코드가 메인이 될거잖아요"라고 물었다. 영향 범위를 잰 결과와 옮길 모양을 보고 "네, 옮겨요"라고 정했다. 문서를 `docs/` 한 폴더로 모으는 것과 ADR 본문 링크 주소만 고치는 예외는 소유자 결정이다. 옮길 목록, `00-summary.md` 이름 유지, 경로 표기를 고치는 방법, 점검 도구의 옛 경로 읽기는 추천 적용이다.) ADR-0165 결정 2의 '문서 경로와 링크는 바뀌지 않는다'를 대체한다.
- **관련**: ADR-0165(모노레포 `peaket`), ADR-0167(스펙 주도 개발 사이클), [docs/architecture.md](../architecture.md) §10·§11, [docs/devops.md](../devops.md) §2.1, review R-198

## 맥락

- ADR-0165는 문서 저장소를 그대로 모노레포의 뿌리로 쓰기로 했다. 그래서 저장소 첫 화면에 문서 폴더 여섯(`planning/`, `design/`, `docs/`, `review/`, `wbs/`, `guide/`)과 요약 파일 둘(`00-summary.md`, `00-diagnosis.md`), 측정 기록 폴더(`perf-ledger/`)가 코드 폴더(`apps/`, `services/`, `packages/`, `data/`, `infra/`, `tools/`, `openspec/`)와 섞여 있었다. 그때는 문서가 저장소의 중심이었다.
- 2026-10-30에 첫 코드 변경(R-197)이 들어가며 구현이 시작됐다. 이제 저장소를 여는 사람이 처음 보는 것은 코드 폴더여야 한다.
- 지금 옮기는 비용이 가장 작다. 아직 CI 워크플로와 코드가 문서 경로를 거의 쓰지 않는다. 계약 원본(`docs/api/`)은 이미 `docs/` 안이라 옮기지 않는다.
- 2026-10-30에 잰 영향 범위:
  - 옮긴 파일 49개(문서 47개와 측정 기록 안내 2개).
  - 다시 계산한 링크 312개. 이 가운데 ADR 본문의 링크가 43개(ADR 39건)다.
  - ADR 밖 본문의 경로 표기 약 2,950곳.
  - 경로를 박아 둔 도구 둘(문서 점검 도구, 성능 장부 도구)과 CODEOWNERS 한 줄.

## 결정

1. **문서를 `docs/` 아래로 모은다(소유자 결정)**

   | 옛 자리 | 새 자리 |
   | --- | --- |
   | `planning/`, `design/`, `review/`, `wbs/`, `guide/` | `docs/planning/`, `docs/design/`, `docs/review/`, `docs/wbs/`, `docs/guide/` |
   | `00-summary.md`, `00-diagnosis.md` | `docs/00-summary.md`, `docs/00-diagnosis.md` |
   | `perf-ledger/`(측정 실행 기록) | `docs/perf-ledger/` |
   | `docs/` 바로 아래 설계 문서, `docs/adr/`, `docs/api/`, `docs/features/`, `docs/security/`, `docs/quality/` | 그대로 |

   - 저장소 뿌리에는 `README.md`, `CLAUDE.md`, 코드 폴더, `docs/`, 작업 공간 설정 파일만 남는다.
   - `git mv`로 옮겨 파일 이력을 지킨다.
2. **`00-summary.md`는 이름을 그대로 둔다(추천 적용)**: 본문 곳곳이 '00-summary §7'처럼 이름으로 가리킨다. 이름을 바꾸면 고칠 곳만 늘어난다.
3. **링크와 경로 표기를 기계로 다시 쓴다(추천 적용)**
   - 링크: 옮기기 전 위치에서 대상을 풀고, 새 위치에서 상대 경로를 다시 만든다. 링크 해석은 문서 점검 도구와 같은 규칙(꺾쇠괄호 대상, 괄호가 든 대상)을 쓴다.
   - 본문의 경로 표기(예: `planning/03 §5`, `review/open-items.md`): 옮긴 폴더의 실제 하위 이름이 뒤따를 때만 앞에 `docs/`를 붙인다. 'code review/'처럼 우연히 같은 글자를 건드리지 않으려는 것이다. 이제 없는 옛 폴더를 가리키는 지난 기록(`design/canvas/`) 두 곳은 그대로 둔다.
   - 원문은 옮기기 전 커밋(9372f96)의 옛 경로에서 읽는다. 그래서 같은 스크립트를 몇 번 돌려도 결과가 같다.
4. **ADR 본문은 링크 주소만 고친다(소유자 결정, ADR 본문을 고치지 않는 규칙의 세 번째 예외)**
   - ADR 39건 본문의 링크 43개는 주소만 새 경로로 바꾼다. 링크 글자와 본문의 뜻은 바꾸지 않는다.
   - 본문에 글로 쓴 옛 경로(약 1,070곳)는 고치지 않는다. 2026-10-30 전에 쓴 ADR 본문의 `planning/`·`design/`·`review/`·`wbs/`·`guide/`·`perf-ledger/`·`00-summary.md`·`00-diagnosis.md`는 `docs/` 아래를 뜻한다. ADR 목록(architecture §11) 머리에 이 읽는 법을 적는다.
   - 예외는 지금까지 둘이었다: 표시 이름 바꾸기(R-92)와 깨진 글자 되돌리기(R-102). 이번이 셋째다(R-198).
5. **도구가 새 자리를 읽는다(추천 적용)**
   - 문서 점검 도구: 필수 문서·WBS·요약의 경로를 새 자리로 바꾼다. 'planning/03 §5' 같은 짧은 표기는 `docs/`를 붙인 꼴로도 같은 문서로 푼다. 경로 검사는 링크 대상을 링크 검사에 맡기고(상대 경로라 저장소 기준으로 읽으면 틀린다), ADR 본문의 옛 경로는 `docs/` 아래로 읽는다.
   - 성능 장부 도구: 실행 기록 폴더를 `docs/perf-ledger/runs/`, 시각 증명 폴더를 `docs/perf-ledger/timestamps/`로 읽는다.
   - CODEOWNERS: `/docs/perf-ledger/`는 플랫폼 팀이다. 나머지 `docs/`는 기본값(아키텍처 팀)이다.
6. **문서만 바뀌는 일이라 OpenSpec 사이클을 쓰지 않는다(ADR-0167 결정 1)**: 문서 점검 도구(오류 0)와 도구 자체 시험으로 확인한다.

## 검토한 대안

- **그대로 두기(ADR-0165 결정 2)**: 고칠 것이 없다. 하지만 코드가 중심이 된 뒤에도 첫 화면에 문서 폴더 여섯과 요약 파일 둘이 코드와 섞인다. 기각.
- **문서를 새 이름의 폴더(`documentation/` 등)로 모으고 지금 `docs/`도 그 안에 넣기**: `docs/api/` 경로가 바뀌어, 계약에서 코드를 만드는 일(wbs 0.2.1)과 문서 수백 곳을 더 고쳐야 한다. 폴더 안에 `docs/`가 또 생겨 읽기도 어렵다. 기각.
- **ADR 본문 링크를 깨진 채 두기**: 문서 점검이 오류를 낸다. 점검 도구에 예외를 두면 진짜 깨진 링크도 놓친다. 기각.
- **ADR 본문의 글로 쓴 경로까지 모두 고치기**: ADR은 그때의 판단을 그대로 남기는 기록이다. 링크는 눌러서 가야 하므로 주소만 고치고, 글은 읽는 법 한 줄로 푼다. 기각.
- **`00-summary.md`의 이름을 `docs/` 폴더의 README로 바꾸기**: GitHub가 `docs/`를 열 때 바로 보여 준다. 하지만 '00-summary'라는 이름으로 가리키는 곳이 많다. 저장소 첫 화면 README가 이미 이 문서로 안내한다. 기각.

## 결과와 트레이드오프

- 저장소 첫 화면이 코드 폴더와 `docs/` 하나로 정리된다. 모노레포에서 흔한 모양이라 처음 보는 사람이 길을 찾기 쉽다.
- 계약 원본(`docs/api/`)과 설계 문서의 경로는 그대로라, 계약에서 코드를 만드는 일과 CI 계획은 바뀌지 않는다.
- 2026-10-30 전 커밋과 ADR 본문의 글은 옛 경로를 쓴다. 읽는 법은 ADR 목록 머리에 있고, 문서 점검 도구도 ADR 본문의 옛 경로를 새 자리로 읽는다. `git log --follow`로 옮기기 전 이력을 따라갈 수 있다.
- 다른 곳에 남은 옛 경로(디자인 캔버스 아티팩트의 노트, 작업 메모)는 이 저장소 밖이라 고치지 않았다. 읽을 때 같은 규칙(옛 `planning/` = `docs/planning/`)으로 읽는다.
- WBS 작업 일수는 바뀌지 않는다.

## 되돌릴 조건

- 문서를 저장소에서 떼어 따로 공개해야 하면(예: 문서 사이트를 따로 둠), `docs/`를 통째로 옮기는 새 ADR을 쓴다. 한 폴더로 모아 두었으므로 그때 비용이 작다.
