# ADR-0031: 4단계 배포 환경 분리 및 리전 재난 복구(DR) 전략

- **상태**: 채택 (2026-10-09 수립). 보완: ADR-0054(2026-10-13, 정비 시간과 관리형 유지보수 창, 변경 동결 창, 측정 자원 TTL과 예산 경보). 결정 1의 상시 데모 환경(AWS 단일 AZ 최소 구성)은 소유자 지출 상한과 맞지 않아 00-summary §7 질문 24로 다시 정했고, ADR-0057(2026-10-13)이 상시 데모를 두지 않고(녹화 영상·재현 스크립트, 필요할 때만 임시 실행) 스테이징·운영을 설계로만 두기로 보완한다. 결과의 분기 복원 연습은 포트폴리오 기간에 로컬 리허설과 모의 진행으로 한다(docs/verification.md §5.3). R-56(2026-10-13)이 결과의 '완벽히 보전'과 '완벽하게 지켜낸다'를 바로잡는다: 도쿄 읽기 복제본은 복제 지연분을 잃을 수 있고, 주문·결제 원장은 스냅샷(RPO 24시간) 뒤 구간을 결제사 거래 대사로 다시 맞춘다(NFR-015) 2026-10-22(ADR-0083): ticket DB의 도쿄 읽기 복제본은 Aurora Global Database의 보조 클러스터로 만든다(Aurora PostgreSQL은 교차 리전 Aurora 복제본을 지원하지 않는다). 대안 표에서 기각한 것은 Global Database를 이용한 리전 자동 전환이고, 보조 클러스터는 평소 읽기에만 쓰며 리전 복구(RB-18) 때 사람이 떼어 내 독립 클러스터로 쓴다(docs/infra.md §4·§6). 2026-10-26(4차 점검 3부): 결정 3의 '외부 DNS 및 글로벌 CDN(Cloudflare) 상태 페이지'는 외부에 호스팅한 상태 페이지(Upptime, ADR-0032)와 대기실 진입 안내 화면으로 읽는다(CDN은 CloudFront다, docs/infra.md §4·§6). 위 R-56 문장의 '완벽히 보전'은 결과가 아니라 결정 3의 문장이다.
- **관련 문서**: ADR-0021(CockroachDB 배제 및 단일 리전 원칙), ADR-0025(오프라인 입장 검표), docs/infra.md §1·§3·§4·§6, NFR-015
- **관련 ID**: NFR-014, NFR-015, NFR-021, POL-026, POL-028

## 맥락
- 초기 아키텍처는 서울 단일 리전을 기본으로 하면서 도쿄 리전에 단순 티켓 DB 읽기 복제본만을 두는 불완전한 상태였으며, 목표 복구 시점(RPO)과 목표 복구 시간(RTO), 클라우드 배포 환경의 세부 계층이 명확히 정의되지 않고 [가정]으로 남아 있었다.
- 프로젝트의 인프라 예산 현실상 운영급 쿠버네티스 클러스터를 상시 멀티 리전으로 풀가동하는 것은 불가능하며, 100만 명 규모의 극한 부하 시험 또한 필요 시 단발성으로 프로비저닝하여 측정해야 한다.
- 한편 공연 당일의 현장 입장은 관람객의 로컬 월렛과 게이트 스캐너 간의 오프라인 P2P 비대칭 서명 검증(ADR-0025)으로 작동하므로, AWS 서울 리전 전체에 장애가 발생하더라도 현장 검표는 중단 없이 지속될 수 있다. 또한 모든 유료 결제의 원본 거래 내역은 외부 PG사 원장에도 안전하게 보존된다.

## 결정
1. 인프라 배포 환경을 목적에 따라 다음 4가지로 명확히 분리한다:
   - **로컬 개발 환경 (Local)**: 상시 운영. `kind` 또는 `k3d` 기반 로컬 경량 클러스터이며 GitHub Actions CI 파이프라인도 동일한 매니페스트로 통합 및 계약 테스트를 수행한다.
   - **측정용 스테이징 환경 (Staging)**: 운영과 100% 동일한 Terraform 모듈 및 인프라 사양으로 구성하되, 성능 벤치마크 및 Game Day 부하 시험 시점에만 온디맨드로 생성하고 계측 완료 즉시 클러스터를 자진 파기하여 비용을 절감한다.
   - **데모 및 시연 환경 (Demo)**: 상시 운영. 포트폴리오 시연 및 E2E 기능 검증을 위해 단일 AZ 최소 리소스 스펙으로 유지한다.
   - **운영 프로덕션 환경 (Prod)**: 아키텍처 및 보안 설계의 표준 목표 스펙이며, 실제 서비스 론칭 시점에 배포한다. (별도의 상시 dev 클러스터는 운영하지 않는다.)
2. 가용 영역(AZ) 장애는 클라우드 네이티브 자동 페일오버로 대응한다: Aurora 다중 AZ 복제는 RPO 0, RTO 5분 이내를 보장하며, Redis 센티널/클러스터는 RTO 30초 이내에 자동 승격한다.
3. 리전 전체 마비 재해(Region Disaster) 발생 시에는 액티브-액티브 자동 전환을 시도하지 않고 안전한 `판매 일시 중단 및 콜드 복구` 전략을 채택한다:
   - 티켓 예매 창구를 즉시 정지하고 외부 DNS 및 글로벌 CDN(Cloudflare) 상태 페이지를 통해 점검 안내를 송출한다.
   - 발권된 티켓 데이터는 타 리전(도쿄) 읽기 복제본과 오프라인 게이트 동기화 캐시로 완벽히 보전한다.
   - 주문 및 결제 원장은 일일 교차 리전 스냅샷(RPO 24시간 이내)과 외부 PG사 거래 대사 API를 상호 대조하여 복원한다. 사전 작성된 재해 복구 Terraform 스크립트로 대체 리전에 신규 인프라를 신속히 프로비저닝하여 RTO 24시간 이내에 판매를 재개한다.
4. 클러스터 노드 풀은 핫패스, 범용, 관측, 데이터의 4종으로 분리하며, 데이터 보존 주기는 Aurora PITR 35일, MSK 토픽 7일, ClickHouse/MongoDB 일일 백업 정책을 준수한다.

## 검토한 대안
| 대안 | 기각 사유 및 한계점 |
| --- | --- |
| 다중 리전 액티브-액티브 분산 구성 | 데이터베이스 간 크로스 리전 합의 네트워크 RTT로 인해 좌석 홀드 지연 시간이 급증하며, 상시 인프라 유지비가 3배 이상 폭증한다(ADR-0021). |
| Aurora Global Database 기반 자동 전환 | 상시 복제 비용이 두 배로 들 뿐만 아니라, 인메모리 Redis의 대기열 및 좌석 임시 홀드 상태는 리전 간 실시간 동기화가 불가능하여 어차피 예매 세션 단절이 불가피하다. |
| 리전 장애를 범위 밖으로 둠(이전 [가정]) | 복구 절차가 존재하지 않아 장애 발생 시 신속한 의사결정이 불가능하고 서비스 장기 중단으로 이어진다. |
| 상시 개발(dev) 클러스터 프로비저닝 | 유휴 리소스 대비 클라우드 비용 낭비가 심하므로 로컬 가상화 환경과 상시 데모 환경으로 대체한다. |

## 결과와 트레이드오프
- 불필요한 상시 멀티 리전 인프라 비용을 제로화하면서도, 최악의 리전 재난 시 관람객의 현장 입장과 결제 금전 정합성을 완벽하게 지켜낸다.
- 리전 재해 발생 시 실시간 티켓 판매는 일시 중단되며, 최근 발생한 결제 내역을 PG사 원장과 대조하여 복구하는 운영팀의 대사 절차가 수반된다.
- 분기 1회 스테이징에서 PITR 복원과 교차 리전 복원을 연습한다(RB-10·RB-18).
