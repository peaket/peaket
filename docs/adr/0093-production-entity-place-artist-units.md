# ADR-0093: 공연(회차 묶음)을 데이터에 정식으로 두고 공연장·아티스트를 따로 관리한다 — 판매 승인·카드·찜·후기 보기·랭킹은 공연 단위, 대기열·좌석·주문·정산은 회차 단위(2026-10-27)

- **상태**: 채택 (2026-10-27. 소유자가 검색 설계 검토를 보고 "검색 엔진은 안 B로 두고, 검색 포트와 바꿀 조건까지 넣어 지난번 제안 네 가지를 반영해 주세요."라고 했다. 네 제안 가운데 첫째가 '공연(회차 묶음)을 데이터에 정식으로 둔다(따로 ADR)'이다. 공연 엔터티(데이터에서 따로 관리하는 대상)를 두는 것은 소유자 결정(승인 2026-10-27, '추천대로')이다. 아래 결정 2~9의 세부(칸 나눔, 공연장·아티스트·별칭의 관리 절차, 단위 표, 대표 회차 규칙, API 경로)는 추천 적용(2026-10-27)이다. 추천 적용은 소유자가 방향을 승인하고 세부를 맡긴 부분에서 제안해 적용한 것으로, 바꾸고 싶으면 언제든 바꾼다.) 2026-10-28(기술 검토 중간-086, 소유자 승인 '추천안 동의'): 결정 10의 정본 반영 목록에 없던 proto·Avro·asyncapi 초안에 반영했다. core.proto `RecordSaleReviewResultRequest`의 대상을 `production_id`로 바꾸고(계약 저장소로 옮기기 전이라 번호 1을 다시 썼다), 결정 7의 승인 본문(회차별 규모 `scales`, 결정 3·4·5의 공연장·아티스트·다른 이름)을 함께 싣는다. 결제사 지정·전환·정산은 결정 2대로 회차 단위라 `PrepareCheckoutRequest.event_id`는 그대로 두고, asyncapi·Avro에서 '공연 ID'로 적은 회차 ID 설명(`SettingChanged.scope`, 좌석 델타 경로의 `eventId`, 주문 토픽 키)을 '회차'로 고쳤다(docs/api/proto/README.md §3, docs/api/asyncapi.yaml). 2026-10-28(ADR-0123, 소유자 승인 '추천안 동의'): 결정 7의 공연 단위 판매 승인 상태에 판매 중지(`SUSPENDED`)를 더한다. 승인한 공연을 operator 이상의 요청과 요청자가 아닌 commander의 승인(2인)으로 내리고(비공개·검색과 홈에서 빼기·새 판매 막기·정산 보류, 판 티켓은 유지), 판매 재개나 commander가 직접 만드는 회차 취소 요청으로 이어 간다(planning/03 §2.14·§2.11). 2026-10-29(소유자 결정, ADR-0153): '남는 한계'의 공연 단위 주소와 정규 주소를 정했다. 공연 단위 주소는 두지 않고, 회차 상세는 저마다 자기 주소를 정규 주소로 두며 그 회차 하나의 Event 표시를 둔다(docs/frontend.md §5.15, review/open-items.md 35번). 2026-11-02(정합 점검, ADR-0177 해설서 검토 다섯 번째 묶음): 결정 5의 공연 다른 이름은 파트너가 등록 때 적고, 운영자도 `PUT /v1/ops/productions/{productionId}/aliases`(core.proto `SetProductionAliases`, 사유 필수, 감사 로그)로 고친다고 읽는다. 판매 승인 뒤에 고쳐도 재승인 대상이 아니다(docs/api/openapi.yaml, docs/features/search.md §2.1).
- **관련**: ADR-0062(판매 승인 재승인과 변경분), ADR-0063(홈·검색·후기·좌석맵 소유 단위), ADR-0064(판매 종료), ADR-0066(좌석맵 템플릿), ADR-0078(공연 규모·수요 예측), ADR-0081(REST 설계 기준), ADR-0094(검색 설계), FR-003·016·019·022·052, POL-037·043, design/d5 §1.6 31번, [docs/data.md](../data.md) §2, [docs/api/openapi.yaml](../api/openapi.yaml), planning/03 §2.14

## 맥락

- **데이터의 `event`는 회차(공연의 한 번)다.** 같은 공연의 회차를 묶는 대상이 없다. 그래서 정본 여러 곳이 이 결정을 기다리며 '그 전에는 회차 단위'라고 적어 두었다.
  - 홈·검색·랭킹 카드(openapi `EventCard`)는 회차 단위다. 오래 하는 뮤지컬은 회차가 수십~수백 개라 한 공연이 목록을 덮는다. 그런데 화면 설계(design/d5 §5.3)의 결과 카드는 '공연명 · 회차 범위'로 그려져 있어 서로 어긋난다.
  - 장르별 랭킹(docs/features/analytics.md §8.5 '단위'), 후기 모아 보기(docs/data.md §2 후기 문단), 판매 승인 단위(docs/data.md `pending_revision` 설명, planning/03 §2.14 끝, design/d5 §1.6 31번)가 모두 이 결정을 기다린다.
  - 판매 승인: data.md는 회차 행이 `sale_review`를 갖는다. 그런데 화면(SCR-021·048·062)과 openapi는 공연 단위로 승인한다. 승인 요청 경로는 회차 ID(`{eventId}`)를 받고 승인 본문은 규모(`scale`) 하나를 받는데, 규모는 회차 칸이다(`event.scale`).
- **공연명·아티스트·공연 설명·관람 연령·러닝타임은 공연 등록 1단계(SCR-021)가 받지만 data.md에 칸이 없다.** 아티스트가 그냥 글자인지 따로 된 대상인지도 정해지지 않았다.
- **실제 공연장을 가리키는 대상이 없다.** `venue`는 좌석맵의 틀(TEMPLATE, 특정 공연장 이름을 쓰지 않는다)과 공연마다 복제한 배치본(LAYOUT)뿐이다. 그래서 홈 공연장 줄과 검색 공연장 필터의 `venueId`가 무엇을 가리키는지 정해지지 않았다. 배치본은 공연마다 달라서 같은 공연장의 다른 공연을 묶지 못한다. 공연 상세 장소 섹션의 주소(SCR-002 ⑮)가 어디서 오는지도 없다.
- **검색 설계(ADR-0094)가 이 셋을 전제로 한다.** 결과 한 줄은 공연이어야 하고, 아티스트·공연장 후보와 필터, 다른 이름(별칭. 예: 'KSPO DOME'과 옛 이름 '올림픽체조경기장', 위키백과 2026-10-27 확인)을 찾으려면 그 대상이 데이터에 있어야 한다.

## 결정

1. **공연 `production`을 둔다(소유자 결정).** 공연은 같은 파트너가 같은 공연장에서 같은 배치본으로 여는 회차의 묶음이다. 회차 `event`는 공연 하나에 속한다(`event.production_id`, 비지 않는다). 공연장이 다르면 다른 공연이다(전국 투어는 도시마다 공연 하나). 한 공연의 회차는 모두 같은 배치본을 쓴다. 이는 지금 규칙(data.md §2 '좌석맵의 소유 단위')과 같고, 공연 등록과 회차 더하기 때 서버가 검사한다.
2. **칸 나눔(추천 적용).**
   - 공연: 공연명(1~100자 [가정]), 장르(정본 7개, 지금의 `event.genre`를 옮긴다), 관람 연령, 러닝타임, 공연 설명 글, 포스터·상세 이미지(지금 회차에 달린 공연 이미지를 공연으로 옮긴다), 공연장, 아티스트 목록, 다른 이름, 공연예술통합전산망 항목 가운데 공연에 딸린 것(명칭·종류, 관람 가능 연령, 출연진·제작진 등), 판매 승인 칸(`sale_review`·`sale_approved_at`·`pending_revision`, 휠체어석 확인 `accessible_seating_check`).
   - 회차: 날짜·시각(오픈·입장 시작·공연 시작·공연 종료 예정·입장 기록 마감), 정렬 방식·좌석 배정 방식·1인 한도·판매 정책·결제사 지정·입장 정책, 공연 규모(`scale`), 중개수수료율(판매 승인 때 공연의 모든 회차에 같은 값으로 고정한다), 회차 상태(취소·연기). 회차 하나의 판매 상태(판매 전·판매 중·판매 종료)는 지금처럼 오픈 시각과 공연 시작 시각으로 계산한다(ADR-0064).
3. **공연장 `place`를 둔다(추천 적용).** 실제 장소다. 이름, 도로명 주소, 시·도, 운영 상태를 둔다. 운영자가 만들고 고친다(감사 로그). 파트너는 공연 등록 1단계에서 공연장을 고르고, 목록에 없으면 이름과 주소를 적어 새 공연장을 요청한다. 운영자가 판매 승인 때 기존 공연장에 잇거나 새로 만든다. 좌석맵 템플릿과 공연용 배치본(`venue`)은 그대로다. 공연이 공연장을 가리키고(`production.place_id`), 배치본은 공연장을 가리키지 않는다. 같은 공연장이라도 공연마다 무대와 구역이 달라 배치본은 지금처럼 공연마다 하나다.
4. **아티스트 `artist`를 두고 공연과 여러 대 여러로 잇는다(추천 적용).** 아티스트는 대표 이름 하나를 갖는다. 공연과는 잇는 표(`production_artist`, 보이는 순서)로 잇는다. 파트너는 공연 등록 1단계에서 기존 아티스트를 고르거나 새 이름을 적는다. 운영자가 판매 승인 때 기존 아티스트에 잇거나 새로 만든다. 같은 아티스트가 이름 표기만 달라 둘로 갈라지지 않게 하려는 것이다. 판매 승인의 확인 항목에 '아티스트·공연장 연결'을 더한다(SCR-048).
5. **다른 이름(별칭) `search_alias`를 둔다(추천 적용).** 공연·아티스트·공연장의 영문 표기와 옛 이름 같은 다른 이름이다. 파트너는 공연 등록 1단계에서 공연의 다른 이름을 5개 [가정]까지 적는다(예: 공연명 영문 표기). 아티스트·공연장의 다른 이름은 운영자가 판매 승인 화면에서 더하고 지운다(사유 필수, 감사 로그). 별칭은 검색에만 쓰고 화면에 보이는 이름을 바꾸지 않는다(ADR-0094).
6. **단위 표(추천 적용).**

   | 개념 | 단위 | 바뀌는 것 |
   | --- | --- | --- |
   | 공연 정보(이름·장르·설명·이미지·관람 연령·러닝타임·아티스트·공연장) | 공연 | 칸을 공연으로 옮긴다 |
   | 좌석맵(배치본) | 공연 | 지금도 같은 공연의 회차가 같은 배치본을 쓴다. API 경로를 공연으로 옮긴다 |
   | 판매 승인, 재승인 대기 변경분, 휠체어석 확인 | 공연 | 칸과 API 경로를 공연으로 옮긴다(결정 7) |
   | 공연 규모, 수요 예측 | 회차 | 칸은 그대로다. API 경로를 회차로 옮긴다(결정 9) |
   | 오픈 시각, 입장 정책, 정렬 방식, 좌석 배정, 1인 한도, 판매 정책, 결제사 지정 | 회차 | 그대로 |
   | 대기열·좌석·홀드·주문·결제·티켓·정산서·명단·현장 입장 | 회차 | 그대로 |
   | 홈·검색·랭킹·찜 카드 | 공연 | 카드 하나가 공연 하나다(결정 8) |
   | 찜 | 공연 | API 경로를 공연으로 옮긴다 |
   | 오픈 알림, 취소표 알림 | 회차 | 그대로. 공연 카드의 종 버튼은 그 공연에서 다음에 오픈하는 회차를 신청한다 |
   | 후기 쓰기 자격 | 회차 | 그대로(그 회차가 끝난 뒤 그 회차를 결제한 계정, 회차당 하나) |
   | 후기 보기·요약 | 공연 | 그 공연의 모든 회차 후기를 모아 보이고, 후기마다 관람 회차 일시를 보인다 |
   | 장르별 랭킹, 검색 인기순 | 공연 | 회차 판매 매수를 공연마다 더한다 |
   | 공연예술통합전산망 1일 전송 기록 | 회차 | 그대로(보내는 값 가운데 공연 정보는 공연에서 읽는다) |
   | 공연 상세 화면 주소 | 회차 | 그대로(`/events/[id]`, 결정 8) |

7. **판매 승인은 공연 단위다(추천 적용).** 승인 요청·승인·반려·변경 취소는 공연마다 하나다(planning/03 §2.14의 상태도 공연마다 하나). 승인은 그 공연의 회차를 모두 함께 판정하고, 공연 규모는 회차마다 정한다(승인 본문 `scales`). 대형 공연끼리의 오픈 30분 간격 검사도 회차마다 한다. 승인 뒤 회차를 더하거나 재승인 대상 항목(가격·회차·좌석 등급·좌석맵·판매 정책)을 바꾸면 그 공연이 재승인 대기가 되고, 그동안 마지막 승인 내용으로 공개·판매를 계속한다(지금 규칙과 같다). 대기열과 구매 경로는 회차를 읽을 때 공연의 승인 상태를 함께 실은 읽기 모델(자주 읽는 값을 미리 모아 둔 사본)을 쓴다. 그래서 바쁜 경로에 표 하나를 더 잇지 않는다. 판매자 신원정보는 지금처럼 파트너 단위다.
8. **카드와 대표 회차(추천 적용).** 홈·검색·랭킹·찜의 카드는 공연 하나에 하나다(openapi `ProductionCard`, 화면 컴포넌트 CMP-072 `ProductionCard`. 지금의 `EventCard`를 이름과 단위를 바꿔 이어 쓴다). 공연 상세 화면은 지금처럼 회차 주소다. 카드를 누르면 대표 회차로 간다. 대표 회차는 ① 판매 중인 회차 가운데 판매 종료가 가장 이른 것 → ② 없으면 오픈 예정 회차 가운데 오픈이 가장 이른 것 → ③ 없으면 매진 회차 가운데 공연 시작이 가장 이른 것 → ④ 없으면 가장 최근에 공연한 회차다. 취소된 회차는 고르지 않는다. 카드의 판매 상태는 판매 중인 회차가 하나라도 있으면 판매 중, 없고 오픈 예정 회차가 있으면 오픈 예정, 남은 회차가 모두 매진이면 매진, 모두 판매 종료면 끝남이다. 공연 단위 상세 주소(`/productions/[id]`)와, 같은 공연의 회차 상세들이 검색 엔진에 알릴 대표 주소(정규 주소)는 나중에 정한다(review/open-items.md 35번).
9. **API 경로(추천 적용).** ADR-0081의 자원 기준(guidelines §10)대로 공연에 딸린 자원은 공연 경로로, 회차에 딸린 자원은 회차 경로로 둔다. 같은 자원이 회차 수만큼 다른 주소를 갖지 않게 하려는 것이다.
   - 공연 경로로 옮긴다: 공연 등록 `POST /v1/partner/productions`(공연과 첫 회차들을 함께, 지금의 `POST /v1/partner/events`), 회차 더하기 `POST /v1/partner/productions/{productionId}/events`(새 경로), 공연 이미지 `…/productions/{productionId}/images`·`…/images/{imageId}`, 좌석맵 `…/productions/{productionId}/seatmap`·`…/seatmap-imports`, 판매 승인 요청과 변경 취소 `…/productions/{productionId}/sale-review`, 운영자의 승인·반려 `/v1/ops/sale-reviews/{productionId}/approvals`·`…/rejections`, 찜 `/v1/productions/{productionId}/wish`.
   - 회차 경로로 옮긴다: 수요 예측 `GET /v1/ops/events/{eventId}/demand-forecast`, 규모 올리기 `POST /v1/ops/events/{eventId}/scale-changes`.
   - 그대로 둔다: 회차의 입장 정책·취소와 연기·정산서·스태프·기기 배치·현장 상태·판매 현황·리포트·명단, 팬의 좌석·홀드·주문·오픈 알림·후기(목록·요약은 그 회차가 속한 공연의 후기를 모두 준다)·후기 자격.
   - 홈 구성(배너·테마)은 공연을 고른다(`productionId`). 홈 공연장 줄과 검색 공연장 필터는 공연장 ID(`placeId`)다.

## 검토한 대안

| 대안 | 기각 이유 |
| --- | --- |
| 회차 단위 그대로 두고 화면에서 공연명으로 묶기 | 같은 이름의 다른 공연(재공연, 다른 파트너)을 가르지 못한다. 판매 승인 단위와 공연 정보 칸의 문제가 그대로 남는다 |
| 회차에 묶음 키만 두기(`series_key`) | 공연 정보(이름·설명·이미지)가 회차마다 복제되어 어긋날 수 있다. 판매 승인 단위 문제가 남는다 |
| 공연장 이름·주소를 배치본에 두기 | 배치본은 공연마다 하나라 같은 공연장의 공연을 묶지 못한다. 공연장 필터·홈 공연장 줄·공연장 별칭이 안 된다 |
| 아티스트를 공연의 글자 칸으로 두기 | 같은 아티스트의 다른 공연 찾기(관련 공연, 아티스트 필터)와 아티스트 별칭이 안 된다. 표기가 조금만 달라도 다른 아티스트가 된다 |
| API 경로를 그대로 두고 회차 ID로 공연 자원에 닿기 | 고칠 경로가 적다. 하지만 공연 이미지·좌석맵·판매 승인 같은 한 자원이 회차 수만큼 다른 주소를 갖고, '그 공연의 아무 회차 ID'를 받는 규칙이 자원 기준(guidelines §10)과 맞지 않는다 |
| 공연 위에 시리즈(투어 묶음)까지 지금 두기 | 지금 요구가 없다. 도시마다 다른 공연으로 두고, 요구가 생기면 새 ADR로 더한다(되돌릴 조건) |

## 결과와 트레이드오프

- 홈·검색·랭킹이 공연 하나를 한 번만 보인다. 후기는 공연의 모든 회차 것을 모아 보여 후기 수가 늘고, 별점 평균이 회차 하나의 적은 후기에 흔들리지 않는다.
- 판매 승인의 단위가 화면·API·데이터에서 하나가 된다. 운영자의 확인 항목에 아티스트·공연장 연결이 하나 늘어난다.
- API 경로 11개를 옮기고(공연 경로로 9개, 회차 경로로 2개) 9개를 더한다(회차 더하기 1개, 공연장·아티스트를 찾고 만드는 경로·공연장 고치기·공연·아티스트·공연장의 다른 이름 고치기 8개). 운영에 나간 경로가 아직 없어 옛 경로를 남기지 않고 제자리에서 바꾼다(guidelines §1과 ADR-0081의 방식).
- 회차를 읽는 대기열·구매 경로는 공연의 승인 상태를 읽기 모델로 함께 읽는다. 공연을 승인하거나 승인을 거두면 그 읽기 모델도 함께 바꿔야 한다.
- 지금까지 문서에서 회차 ID(`eventId`)를 '공연 ID'라고 적은 곳이 남아 있다. 용어 사전의 '회차' 줄에 '회차를 공연이라고 적은 지난 문장은 회차로 읽는다'를 적고, 이번에 고치는 문서에서만 바로잡는다.

## 되돌릴 조건

- 공연장이 다른 회차를 한 상품으로 팔아야 하는 요구(전국 투어 한 번에 팔기)가 생기면 공연 위에 시리즈를 더하는 것을 새 ADR로 본다.
- 아티스트·공연장 연결 확인 때문에 판매 승인 처리 시간이 크게 늘면(관제 기록의 승인 처리 시간으로 잰다) 파트너 입력을 기본으로 받고 운영자는 표본만 확인하는 방식으로 바꾼다.

## 남는 한계

- 공연 단위 상세 주소와, 같은 공연 회차 상세들의 정규 주소는 아직 정하지 않았다(review/open-items.md 35번).
- design/d5 §1.6 31번의 나머지 두 가지(판매자 값의 신고번호 칸, 판매 승인 요청마다 정산 계좌를 받는 것)는 이 결정으로 풀리지 않아 그대로 남는다.
- 디자인 캔버스(소비자 홈·검색 보드, 파트너 등록 보드, 관제 판매 승인 보드)는 아직 고치지 않았다(review/open-items.md 25번).
- 원문 설계서와 지난 ADR 본문의 회차 단위 문장은 쓴 그대로 남는다. 읽을 때는 이 ADR이 앞선다.
