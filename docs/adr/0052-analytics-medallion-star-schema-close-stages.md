# ADR-0052: 분석 저장소를 확정·잠정으로 나누고 메달리온 층, 스타 스키마, 마감 단계, 결정 절차로 구체화한다 (ADR-0042 보완)

- **상태**: 채택 (2026-10-13. 소유자 질문 '데이터 웨어하우스를 왜 쓰나, 비즈니스 결정은 사후 분석인가 실시간 분석인가, 지표를 어떻게 모아 가공·표시·분석·결정하나, 지금 설계가 ELT·메달리온·스타 스키마인가'에 대한 검토와 설계안에 소유자가 "추천대로 승인". 결정 1·2·3·4·9·10·11은 소유자 결정이고, 필드·표 이름·일정 시각·임계값 같은 세부 규격은 추천 적용(2026-10-13)이다. 측정으로 정할 값은 [가정, Phase N …에서 확정]으로 표시한다. ADR-0042 결정 2의 '관제 읽기 모델을 2층 마트의 실시간 부분으로 흡수'를 대체하고, 나머지 결정은 그대로 두고 구체화한다.) 2026-10-20(ADR-0071): 실시간 표 `rt`를 덮어쓰기(누적 + 1초 칸, `ReplacingMergeTree(version)`)로 바꾸고 뷰로 합산하지 않는다. 실시간 대비 대조의 판매 좌석·금액 차이 0은 이 방식으로 지킨다. `telemetry.purchase`·`telemetry.trust-verdicts` 키를 ADR-0026 결정 1에 맞추고, 원본 적재 커버리지를 파티션별 오프셋 연속성 대조로 바꿨다(docs/streaming.md). 2026-10-20(ADR-0073, 3차 전수 점검): 실시간 대비 대조의 판매 금액은 승인 금액 합(지표 사전 26번, 정산서 '판매 대금'과 같은 총액, 입금 되돌림만 뺌)이고 판매 좌석은 지금 SOLD인 좌석 수다. 실시간 표의 판매 금액도 같은 규칙으로 센다. 2026-10-22(ADR-0086): 결정 4의 delete+insert는 실버에만 남긴다. 골드는 실행마다 `run_id`를 붙여 넣은 뒤 '회차별 현재 판' 표를 바꾸는 판 바꾸기로 한다. delete+insert는 도중에 실패하면 반쯤 지워진 회차가 남을 수 있기 때문이다(ClickHouse dbt 문서). ClickHouse 서버 판은 26.8 LTS다(analytics §4.1, docs/streaming.md §2.1). 2026-10-26(4차 점검 3부): 결정 7의 지표 사전은 ADR-0078이 31번 '수요 예측 오차'를 더해 31개다(analytics §6.3). 결정 7의 'ops-svc는 지표 뷰만 읽는다'는 지표 뷰(`mtr_*`)와 회차 요약(F11)·규칙 판정(F12)만 읽고 지표를 따로 계산하지 않는다는 뜻으로 읽는다(analytics §8.2·§11). 결정 5의 R3는 입장 기록 마감(offline-gate §7.3)이 그보다 늦으면 마감 뒤에 한다(analytics §4.2). 결과의 'Avro BACKWARD 호환'은 BACKWARD_TRANSITIVE로 읽는다(ADR-0054 결정 18, analytics §3.4). 2026-10-27(ADR-0099): 실시간 길은 'Flink 집계 → 실시간 표'가 아니라 '`ops-rt` 원시 적재 → 조회 시점 집계'다. 같은 지표 정의를 쓰되 실시간과 확정의 표를 섞지 않는 원칙은 그대로다. 2026-10-28(기술 검토 높음-23, 소유자 승인 '추천안 동의'): 결정 5의 '온세일 사실은 R2에 동결하고 R3 이후 계산은 동결된 골드를 읽는다'만으로는 R2 뒤에도 파는 비매진 회차의 판매가 R3에 들어가지 않는다. 그래서 결정 3의 사실 표에 날짜별 판매 사실 F15 `fct_sales_daily`(날짜 × 회차 × 등급 × 결제사: 판매 좌석·주문·판매 금액·되돌림·반환 좌석)를 더해 15개로 하고, 마감 실행기가 매일 전날 판매분을 넣는다(랭킹 일 집계와 같은 실행). R3의 판매 대금(지표 26)과 공연 전날 판매율(지표 7)은 F2가 아니라 F15의 합으로 구한다(analytics §4.3·§5·§6.3·§7, A-T18). 2026-10-28(ADR-0115, 소유자 승인 '추천안 동의'): 결정 2의 아카이브(동결된 회차 골드, Iceberg, 영구)는 회차·표마다 Parquet 파일 하나와 manifest로 S3에 두고, ClickHouse 뷰 `archive.<표>`(`s3()` 표 함수)로 읽는다. 2년보다 오래된 회차와의 비교에 읽는 길이 생겼다(analytics §5.5·§6.4, A-T19). 2026-10-28(기술 검토 낮음-042·044~048, 소유자 승인 '추천안 동의'): 결정 6의 수집 버킷 파일은 마감 실행기가 ClickHouse `s3()`로 크기·형식 검사를 거쳐 싣는다(analytics §3.2). 결정 7의 비율 규칙은 95% Wilson 구간으로 판정해 '경계'를 더하고, 결정 8의 같은 규모 기준선은 확정 회차 3회 미만 없음·3~9회 범위(근거 약함)·10회 이상 중앙값과 사분위로 나눠 직전 회차 하나와 견주지 않는다(analytics §6.4·§10.2). 데이터 품질의 시각 순서는 서비스 사이 40ms를 허용하고 같은 토픽 단계는 Kafka 위치로 견준다(§7). 결정 9의 골드 익명 근거에 사람에 대한 판단이 든 칸의 5건 [가정] 미만 합치기를 더하고 익명 판단을 법률 검토에 올린다(§11, POL-027). 포트폴리오에 비용 원천이 없다는 한계를 적는다(§14). 2026-10-28(기술 검토 낮음-026, 소유자 승인 '추천안 동의'): 결정 6이 모든 trade·telemetry 메시지에 더한 `schemaVersion`을 첫 등록 전에 뺀다. 메시지의 판은 Schema Registry 스키마 ID가 말하고, 뜻이 바뀌는 변경은 새 필드를 더하는 확장·축소로 하므로 손으로 적는 판이 필요 없다. 중복 제거 키는 `eventKey` 하나로 하고 `OrderEvent.idempotencyKey`도 뺀다(docs/api/asyncapi.yaml info '공통 필드', 세부는 추천 적용). 2026-10-29(review/open-items.md 2번, 소유자 결정 "B로 정함", ADR-0150): 결정 6이 '선택 필드'로 더한 칸들은 첫 등록 전이라 늘 값이 있으면 필수, 사건 종류에 따라 있으면 조건부로 다시 정했다(docs/api/avro/README.md §6). `OrderEvent.purchaseSessionId`는 CREATED에만 싣는다(주문 표에 저장하지 않는다). 2026-11-01(정합 점검, ADR-0175 해설서 검토): 결정 7의 지표 수는 32개다(2026-10-31에 32번을 더했다, docs/features/analytics.md §6.3, ADR-0171). 2026-11-01(정합 점검, ADR-0177 해설서 검토 네 번째 묶음): 결정 9의 '상업 목적 통계가 통계작성에 드는지 확인 필요'는 확인됨으로 읽는다. 가명정보 처리 가이드라인(2026.3.) p.25는 상업 목적의 통계도 통계작성에 넣고, 특정 개인 재식별을 전제로 한 활용은 뺀다(2026-10-31 확인, ADR-0171, docs/security/data-classification.md 법률 확인 22번). 봇 판정 규칙 개선은 같은 문서 31번의 과학적 연구로 따로 본다.

## 맥락

- ADR-0042(2026-10-12)는 ClickHouse를 사후 분석 저장소로 넓히며 보존 기간별 3층(원시 비즈니스 이벤트 90일, 공연 리포트 마트 2년, S3 Iceberg 비식별 집계 영구), 공연 리포트 자동 생성, 결정 규칙 표, 지표 4층을 정했다.
- 2026-10-13 소유자 질문으로 다시 검토하니, 정한 것은 '얼마나 오래 보관하나'까지였고 '어떻게 모델링하고 언제 확정하나'가 비어 있었다.
  - 메달리온으로 보면 1층은 브론즈, 2층은 골드에 해당하지만 실버(검증·중복 제거·늦은 이벤트·결합)가 없었다. 3층은 품질 단계가 아니라 보존 단계다.
  - 2층은 '리포트에 들어갈 항목 목록'이라 사실 표, 차원, 그레인 선언이 없었다. 비율('퍼널 전환율 요약')을 저장하면 회차 간 평균이 틀린다.
  - 변환 도구, 실행 시점, 재실행 단위, 품질 검사가 없었다(ADR-0042는 '머티리얼라이즈드 뷰 + 종료 후 배치', architecture §10은 dbt·Airflow, WBS 4.3.2는 2일).
  - 결정 2가 관제 읽기 모델(잠정 숫자)을 마트에 흡수해 잠정 숫자와 확정 숫자가 같은 표에 섞였다.
  - Kafka는 컨슈머 멱등 처리를 전제한다(ADR-0026). ClickHouse 머티리얼라이즈드 뷰는 삽입되는 블록에 대해 실행되는 트리거이고, ReplacingMergeTree의 중복 제거는 병합 때 결국 일어난다(ClickHouse 문서, 2026-10-13 확인). 원시 삽입에 뷰를 걸어 마트를 만들면 중복 전달분이 합산되고, 조인한 차원 표가 바뀌어도 다시 계산되지 않는다.
  - 이벤트 계약(asyncapi.yaml)에 지표 원천이 없었다. 결제 실패 사유, 홀드 경합(409) 이벤트, 티켓 이벤트의 회차 ID, 봇 판정 채널, 사람별 대기 기록 스키마, 고유 이벤트 키가 빠져, 결정 규칙 13개 중 분석 저장소에서 계산되는 것은 1개(입장 → 구매 전환율)였다. 2개는 좌석·등급 기준 자료가 있어야 하고, 5개는 Prometheus·비용 도구에만 있어 13개월 뒤 비교할 수 없고, 5개는 원천이나 연결 키가 없었다.
  - 기준 자료(core-svc), 운영 기록(ops-svc), 비용, SLO 결과를 싣는 경로가 없었고, 리포트 생성기(ops-svc)가 직접 집계해 관제·리포트·파트너 숫자가 갈라질 수 있었다.
  - 개인정보 분류표의 해당 행은 '가명정보 처리 정합성은 POL-027로 관리'라 적었지만 POL-027에 항목이 없었다. 가명정보 처리 기록과 추가 정보(키) 분리 보관이 설계에 없었다.
  - observability §9는 2층을 '정산 마트'라 불렀고, POL-030은 T+1일 회고 리포트를 '정산 리포트'라 불러 정산서(ADR-0047)와 이름이 겹쳤다.
- 외부 기준(2026-10-13 원문 열람): Databricks 문서는 메달리온을 데이터를 논리적으로 조직하는 설계 패턴이자 '권장 모범 사례이나 필수는 아님'이라 하고, 브론즈는 원본 보존과 재처리, 실버는 검증·중복 제거·늦은 데이터·결합, 골드는 차원 모델링과 집계로 정의한다. 킴볼 그룹 기법 목록은 4단계 설계(업무 과정, 그레인, 차원, 사실), 주기 스냅샷·누적 스냅샷 사실 표, 비가산 측정값은 가산 구성 요소를 저장하고 마지막에 계산, 적합 차원과 버스 매트릭스를 정한다. ClickHouse 문서는 조인이 비정규화된 단일 표보다 비싸므로 드물게 바뀌는 데이터를 비정규화하고 다대일 조회에는 딕셔너리를 쓰라고 권한다.

## 결정

1. **역할 원칙(소유자 결정).** 결정을 실행할 수 있는 속도보다 빠른 숫자는 쓰지 않는다. 판매 정책, 파트너 권고, 운영 기본값, 계약 같은 비즈니스 결정은 마감된 확정 숫자로만 하고, 실시간 숫자는 온세일 중 운영 명령과 '잠정' 표시에만 쓴다. 실시간 길(Flink 집계 → 실시간 표 `rt`)과 확정 길(원본 → 실버 → 골드)은 같은 지표 정의를 쓰되 표를 섞지 않는다. ADR-0042 결정 2의 흡수 문장을 대체한다.
2. **층(소유자 결정).** 브론즈(원본 그대로, 가명 처리와 금지 필드 제거만, 적재 뒤 90일), 실버(신설: 중복 제거·형 변환·늦은 이벤트·기준 자료 결합, 90일), 골드(스타 스키마 집계, 사람 단위 행 없음, 2년), 아카이브(동결된 회차 골드, Iceberg, 영구)로 둔다. ADR-0042의 1층은 브론즈, 2층은 골드, 3층은 아카이브다. 층마다 '보장하는 것과 읽는 사람'을 정한다(analytics §2).
3. **스타 스키마(소유자 결정).** 골드는 킴볼 4단계로 설계한다. 사실 표 14개(분 스냅샷, 판매, 퍼널 코호트, 홀드 시도, 결제 시도, 봇 결과, 대기 정확도, 환불·양도·CS·비용(날짜별), 현장 입장, 회차 요약, 규칙 판정)와 공통 차원(회차, 날짜, 등급, 구역, 결제사, 결과·사유, 봇 범주, 배정 방식, 게이트 구역 등)을 둔다. 비율·분위수는 저장하지 않고 분자·분모와 히스토그램 버킷을 저장한다. 원자 단위(구매 세션 누적 스냅샷, 시도 1행)는 실버에 90일 둔다. ClickHouse 물리 구현은 논리 스타 스키마에 오픈 뒤 바뀌지 않는 차원 속성의 비정규화와 딕셔너리 조회를 더한다(analytics §5).
4. **ELT와 실행(소유자 결정, 추천 (a)).** 원본을 먼저 싣고(E·L) 변환은 ClickHouse 안에서 dbt-core와 dbt-clickhouse로 한다(T). 재실행 단위는 회차이고 delete+insert로 멱등하게 다시 만든다. 마감 실행기는 10분마다 도는 쿠버네티스 CronJob(`close-runner`)이고 Airflow는 쓰지 않는다(architecture §10 수정). 머티리얼라이즈드 뷰는 실시간 표 안에서만 쓴다.
5. **마감 단계(추천 적용, 시각은 [가정, Phase 4 4.3.6에서 확정]).** R0 잠정(온세일 윈도우 종료 30분 뒤), R1(다음 영업일 10시: 결제·비용), R2(오픈 7일 뒤: 봇·이의 제기·CS), R3(회차 종료 다음 영업일 10시: 입장·환불·정산서 대조), 동결(R2·R3 중 늦은 것 + 7일)로 둔다. 원시는 적재 뒤 90일에 지워지므로 온세일 사실은 R2에 동결하고, R3 이후 계산은 동결된 골드를 읽는다. 마감마다 실시간 대비 차이(판매 좌석·판매 금액 0, 퍼널 0.1% [가정] 이내)와 정산서 대비 차이(0원)를 검사한다(NFR-026).
6. **원천과 계약(추천 적용).** 모든 trade·telemetry 메시지에 `eventKey`·`schemaVersion`을 더하고, `OrderEvent`(구매 세션, 좌석별 등급·구역·가격, 배정 방식), `PaymentEvent`(금액, 결제 수단 범주, 정규화 결과, 실패 범주, 시도 순번, 응답 시간), `SeatEvent`(홀드 ID, 구매 세션), `TicketEvent`(회차·주문·계정 ID)를 보강한다. `telemetry.purchase`(홀드 시도, 409 포함)와 `telemetry.trust-verdicts`(봇 판정과 사후 라벨)를 새로 두고 `telemetry.queue`에 사람별 대기 기록을 정의한다. 회차 기준 자료는 core-svc가 오픈 30분 전에 분석 수집 버킷(S3)에 스냅샷으로 쓰고, ops-svc는 운영 기록의 코드 열만, 비용은 OpenCost와 비용 할당 태그 자료를, SLO 결과는 R0에 Prometheus(Mimir)에서 스냅샷한다(analytics §3).
7. **지표 사전과 결정 규칙(추천 적용).** 목표 → 질문 → 지표(GQM)로 지표 30개를 정하고 `metrics.yml`에 정의(분자·분모, 차원, 확정 단계, 목표, 규칙)를 둔다. dbt가 지표 뷰(`mtr_*`)와 규칙 판정(`rules.yml`)을 만들고, ops-svc는 지표 뷰만 읽어 리포트를 렌더링한다. 결정 규칙 표에 '적용 조건'과 '확정' 열을 더하고, 실시간 규칙이던 '에러 버짓 전량 소진' 행을 사후 규칙('온세일 에러 버짓 50% [가정] 이상 사용 → 다음 회차 초기 목표·프리워밍 재검토')으로 바꾸고, 새 규칙 5행(차례 뒤 미입장, 홀드 만료, 1인 한도 소진, 비매진 판매율, 1,000장당 비용 대비 수수료)을 [가정]으로 더한다(planning/01 §3.2).
8. **결정 절차(추천 적용).** POL-040을 둔다. 마감 단계별 회의(R0 점검, R1 회차 리뷰, R2 공정성 리뷰, 월간 비교, 분기 정책), 결정 권한과 최소 근거(되돌리기 쉬운 운영 기본값은 1회차와 규칙 걸림, 판매 정책 기본값과 목표 수치는 같은 방향 2회차 이상이고 같은 규모 기준선 밖), 결정 기록(`decision_record`: 계기, 결정, 기대 효과, 확인 시점, 되돌릴 조건)과 다음 리포트의 자동 대조, 같은 회차 안에서 사람을 나눠 판매 규칙을 시험하지 않음, 파트너가 정하는 가격·등급·오픈 시각은 권고만 한다.
9. **개인정보(소유자 결정, 추천 (a)).** 브론즈·실버의 가명 사건 처리는 개인정보 보호법 §28의2①의 통계작성으로 본다(해석, POL-027). 상업 목적 통계가 '통계작성'에 드는지는 개인정보보호위원회 가명정보 처리 가이드라인 원문으로 확인한다(확인 필요, wbs 7.4.1). 식별값은 적재 때 회차별 가명(`HMAC(HMAC(분석 가명 키, "PEAKET-analytics-v1" ‖ 회차 ID), 식별값)`)으로 바꾸고, 분석 가명 키는 KMS에 두어 원본 적재 잡만 쓴다(시행령 §29의5①). 처리 기간은 90일(§28의4②), 가명정보 처리 기록은 파기 뒤 3년 이상 보관한다(§28의4③). 운영 DB와의 결합과 재식별을 금지한다(§28의5). 골드·아카이브는 사람 단위 행이 없는 집계이고, 파트너 축약본은 판매 5건 [가정] 미만 칸을 합친다. 실버 조회는 개인정보 보호책임자가 가명정보 취급자로 지정한 commander만 하고 접속기록 점검(FR-064) 대상에 넣는다.
10. **이름 정리(소유자 결정).** POL-030의 'T+1일 [정산 및 회고] … 정산 리포트'를 '[회고] 공연 리포트(R1), 봇 점유율은 R2 확정'으로, observability §9의 'ClickHouse 정산 마트'를 '골드(공연 리포트 마트)'로 고친다. 정산 숫자의 원본은 정산서(ADR-0047)이고 골드는 대조 대상이다.
11. **범위(소유자 결정, 전체).** WBS 4.3.2를 공연 리포트·규칙 판정·결정 기록(1.5일)으로 다시 정의하고 4.3.3~4.3.7(이벤트 계약 1.5, 원천 적재 2, dbt 변환 4.5, 마감 실행 1, 개인정보·보안 1)을 새로 둔다. 합계 +9.5일(244일 → 253.5일).
12. **새 식별자.** FR-068(공연 리포트 마감 단계와 결정 기록), NFR-026(분석 파이프라인 마감 품질), POL-040(분석 숫자와 결정 절차), 용어 7개(분석 저장소, 분석 층, 마감 단계, 지표 사전, 공연 리포트, 결정 규칙 표, 결정 기록), 테스트 포인트 A-T1~A-T15(analytics §13).

## 대안

| 대안 | 기각 사유 |
| --- | --- |
| ADR-0042대로 원시 삽입에 머티리얼라이즈드 뷰를 걸어 마트를 만들고 실시간 읽기 모델을 흡수 | 중복 전달분이 합산되고(ADR-0026, ClickHouse 문서), 차원 변경이 반영되지 않으며, 잠정 숫자와 확정 숫자가 섞인다 |
| 스트림 하나로 확정까지 계산(카파 구조) | 봇 표본 검토(종료 뒤), 환불(공연일까지), 입장(공연 당일)처럼 며칠 뒤 확정되는 숫자를 스트림 상태로 붙들어야 하고, 정의를 바꿀 때 재처리 비용이 크다 |
| 넓은 표 하나(사실을 모두 한 표에) | 사실마다 그레인이 달라(분 스냅샷, 시도, 날짜별 환불) 한 표로 합치면 반가산 측정값(대기 인원)을 잘못 더한다. 화면용 넓은 뷰를 골드 위에 두는 것은 허용한다 |
| 원자 단위 사실을 골드에 2년 보관 | 사람 단위 행이 2년 남는다(ADR-0042 결정 6). 대신 90일 뒤 새 기준으로 재분석하지 못하는 한계를 받아들인다 |
| Airflow로 마감 실행(추천 (b)) | 하루 몇 번 도는 단순한 의존이라 운영 부담(스케줄러·DB·워커)이 이득보다 크다 |
| 개인정보 보호법 §15③ 추가적 이용(추천 (b)) | §28의7의 적용 제외가 없어 삭제·처리정지 요구가 오면 회차마다 가명을 다시 계산해 행을 찾아 지워야 한다. 처리 기간·기록·키 분리로 관리하는 §28의2가 범위가 분명하다 |
| 비즈니스 결정도 실시간 숫자로 | 숫자가 늦게 확정되고, 온세일 중에는 판매 조건을 바꾸지 않으며(POL-028·037), 한 회차는 잡음이 크다 |

## 결과

- **얻는 것**: 결정 규칙 18개 모두 분석 저장소 안에 계산 원천이 생긴다. 관제·리포트·파트너가 같은 정의를 쓰고, 중복·늦은 이벤트에 강하며, 숫자마다 잠정·확정이 보인다. 결정 기록과 다음 회차 대조로 '데이터 → 결정 → 확인' 고리가 닫힌다. 가명정보 처리 근거와 기록이 생긴다.
- **대가**
  - WBS +9.5일(253.5일). 발행 서비스 여섯 곳(purchase, payment, ticket, queue, trust, core)의 이벤트 계약이 바뀐다(선택 필드 추가, Avro BACKWARD 호환).
  - ClickHouse 저장·연산이 늘어난다. 마감 실행은 낮은 우선순위 설정 프로필로 돌려 같은 시각 다른 회차의 관제 조회(NFR-009)를 막지 않는다 [가정, Phase 4 관측 비용 측정에서 확인].
  - 지표 사전, 규칙 파일, 결정 기록을 유지하는 수고가 든다.
- **남는 한계**(planning/01 §5.2, analytics §14): 포트폴리오에는 합성 데이터만 들어가 정책 결정이 옳은지는 검증하지 못한다. 원시 90일 뒤 새 기준으로 재분석하지 못한다. 회차가 적으면 비교 기준선이 넓다. 회차 안 무작위 시험을 하지 않아 원인 단정이 어렵다. 파트너 가격·등급은 권고만 한다.
- **되돌릴 조건**
  - 마감 실행이 관제 지표 반영(NFR-009 p95 5초)을 해치면 마감 실행을 읽기 전용 복제본으로 옮긴다.
  - 실시간 대비 대조가 3회차 연속 기준을 넘으면 적재 경로를 다시 설계한다.
  - 마감 실패를 사람이 다시 돌리는 일이 한 달에 2회 [가정]를 넘으면 오케스트레이터 도입을 새 ADR로 정한다.
  - 법률 검토에서 §28의2 해석이 뒤집히면 §15③으로 바꾸고 삭제·처리정지 요구 처리 경로를 더한다.
  - ADR-0042의 '공연 리포트가 두 공연 연속 결정에 쓰이지 않으면 자동 생성을 줄인다'는 그대로 둔다.
