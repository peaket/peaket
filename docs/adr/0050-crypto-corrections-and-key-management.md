# ADR-0050: 암호 사용을 정정하고 키 관리 기준과 보안 규칙 다섯 가지를 정한다 (기기 키의 실제 한계와 재발급 제한, 지연 환급 계좌 재입력, 키 목록·교체 주기, TLS 기준, 셔플 비콘 대기, 구매 세션 소지 증명, 고권한 토큰 키 분리와 관리자 페퍼)

- **상태**: 채택 (2026-10-13. 소유자 승인: 암호 사용 검토의 '사실 정정과 한계 기록'과 결정 다섯 건의 추천안에 "A부터 반영하고 B 추천대로 가도 됩니다. 승인합니다." 키 교체 주기, 재발급 한도, 비콘 대기 상한 같은 세부 수치는 추천 적용(2026-10-13)이다.) ADR-0051(2026-10-13)이 결정 2의 현장 부스 대조를 신분증·예매 정보 대조에서 관객 휴대폰 본인확인 결과(`ci_hmac`)와 보유 계정의 대조, 부스 코드, 현장 책임자 허용으로 바꾸고(양도받은 사람의 이름은 PEAKET에 없다), '수동 입장 처리'는 현장 책임자의 예외 통과로 바꾸며, 입장 시작 뒤 첫 키 등록(ISSUE)에 소셜 재인증과 알림을 더한다. ADR-0053(2026-10-13)이 이 ADR 검토 때 기록만 해 둔 보강 제안 18건(R-50)을 반영한다. ADR-0051 결정 13이 결정 3의 지연 환급 시점(입장 시작 뒤 취소)을 '공연 종료 뒤'에서 '입장 기록 마감 뒤'로 바꾼다 2026-10-13 전수 점검(2026-10-14 2차): 팬 재인증 목록(POL-019)에 회원 탈퇴를 더했다. POL-033이 이미 소셜 로그인 1회 재인증을 요구했고 openapi 탈퇴 API에 재인증 헤더를 붙였다. 재인증 실패는 403 `reauth-required`로 통일했다(guidelines §7). 2026-10-20(ADR-0073, 3차 전수 점검): 결정 7의 시드만 쓰는 비상 셔플은 운영 명령 카탈로그에 넣지 않고 런북 RB-35의 런북 CLI 작업으로 둔다. 서로 다른 commander 두 명이 각자 KMS 키로 서명해야 실행되고(ADR-0053 결정 11과 같은 서명 묶음), 비콘 대기 상한 초과 SEV1의 런북이 RB-35다. 2026-10-21(ADR-0079): 결정 8의 구매 세션 요청 인증 키는 브라우저 '페이지 메모리'가 아니라 추출 불가 키로 IndexedDB에 두고(결제창 복귀·새로고침에 이어 씀) 일련번호는 Web Locks로 직렬화한다. MAC 입력의 이어 붙이기 규칙도 정했다.

## 맥락

- 소유자 요청(2026-10-13)으로 문서 전체의 암호 사용 지점을 전수 조사했다(암호 관련 낱말이 나오는 86개 파일).
- 고른 알고리즘은 맞았다. ES256, HMAC-SHA256, AES-256-GCM, PBKDF2-HMAC-SHA256 60만 회, ECDH P-256은 모두 ASVS 5.0.0 부록 C의 승인(A) 목록과 KISA 검증대상 암호알고리즘(검증기준 V3.0)에 있다.
- 문제는 네 가지였다. 사실과 다른 보안 주장, 키 목록과 교체 주기의 빈칸, 재전송 방지·키 교체 절차 같은 세부 규칙 미정, 문서끼리 다른 값.
- 원문으로 확인한 사실(2026-10-13):

## 결정

1. **회전 QR 기기 키는 하드웨어에 있지 않다(주장 정정, ADR-0025 결정 2와 결과 첫 줄을 고친다).**
   - WebCrypto의 `extractable=false`는 페이지 스크립트가 키를 꺼낼 수 없다는 뜻이다. 키는 브라우저 프로필에 소프트웨어 키로 저장되고, Secure Enclave나 Android Keystore에 있다는 보장이 없다.
   - 막는 것: 캡처 이미지를 찍은 뒤 약 30초가 지나 쓰기(±30초 창), 스캐너 분실로 QR 위조(스캐너에는 공개키만 있다), 일반 사용자가 다른 기기로 옮기기.
   - 못 막는 것(남는 한계):
     - 화면 공유나 영상통화로 QR을 실시간 중계하기. 늘 새 QR이 보이므로 통과한다.
     - 계정을 넘긴 뒤 재발급하기. 재발급은 로그인한 기기에 새 키를 등록하므로 기기 결속은 사실상 계정 결속이다. 결정 2가 이 길을 줄인다.
     - 루팅한 기기나 데스크톱 브라우저 프로필을 복사해 키를 옮기기.
   - 하드웨어 결속은 네이티브 월렛(Android Keystore·iOS Secure Enclave와 앱 무결성 확인)으로만 된다. PWA 방침(NFR-019)과 부딪히므로 이번에는 하지 않는다.
2. **기기 키 재발급을 제한한다(소유자 승인, 숫자는 추천 적용).**
   - 입장 시작 전: 온라인 재발급은 소셜 제공자 재인증 뒤에만 한다. 티켓당 24시간에 1회까지다 [가정, Phase 5 5.1.2에서 확정]. 넘으면 고객센터로 안내한다. 재발급하면 계정 이메일과 이전 기기(웹 푸시)에 알리고 이전 키를 바로 폐기 목록에 올린다.
   - 입장 시작 뒤: 월렛에서 재발급하지 않는다. 현장 부스에서 `gate_lead`가 신분증과 예매 정보를 대조한 뒤 재발급하거나 수동 입장 처리한다(오프라인 유실 때의 기존 절차와 같다).
   - 이유: 재발급이 기기 결속을 무너뜨리는 가장 쉬운 길이다. 입장 직전에 재발급을 막으면 계정을 넘겨 되파는 경우 현장 신분 확인을 거쳐야 한다.
   - 대가: 입장 시작 뒤 저장소가 지워진 정상 관람객도 부스로 가야 한다. 공연 전날·당일 아침 동기화 안내와 홈 화면 추가 권유(POL-018)를 그대로 두어 줄인다.
3. **지연 환급의 계좌번호는 실행할 때 다시 받는다(소유자 승인).**
   - 가상계좌 결제의 환불 계좌번호는 결제사 취소 요청을 바로 보낼 수 있을 때만 받는다.
   - 바로 보낼 수 없으면 계좌번호를 받지 않는다. 입장 시작 뒤 취소라 환급을 공연 종료 뒤에 하거나, 결제사 장애로 재시도 큐에 들어가는 경우다. 실행할 수 있게 되면 알림으로 계좌를 다시 받고, 그 사이에는 CS 처리함 '환불 대기'로 둔다. 회차 취소 일괄 환불과 같은 방식이다(POL-014).
   - 같은 요청 안의 즉시 재시도(같은 멱등키, 수 초)만 메모리의 계좌를 쓰고, 요청이 끝나면 버린다.
   - 그래서 계좌번호를 계속 두는 곳이 없고 고시 §7②6호의 저장 암호화 대상도 생기지 않는다. 배상금 송금(ADR-0046)과 정산 계좌(ADR-0047)도 같은 규칙이다.
4. **키 목록을 채우고 교체 주기를 정한다(docs/security/secrets-and-keys.md, 주기는 추천 적용).**
   - 빠진 키를 넣는다: 토스페이먼츠 보안 키, 저장소 암호화 KMS 키, 관리자 비밀번호 페퍼 키, 관리 토큰·현장 스태프 토큰 서명 키(결정 9), 비상 런북 운영자 서명 키, 가상계좌 입금 콜백 `secret`.
   - 키마다 쓸 수 있는 곳과 쓸 수 없는 곳을 적는다(ASVS 11.1.2).
   - '추후 확정'이던 교체 주기 15개를 정한다. 주기는 NIST SP 800-57 Part 1의 표와 원문 대조를 하지 못해 자체 기준이다. 대조는 구현 전에 한다.
   - 토스페이먼츠 보안 키는 지급대행 JWE와 지급·셀러 웹훅 HMAC에 같이 쓴다. 결제사 규격이라 바꿀 수 없으므로 '키 분리 원칙의 예외'로 적는다. 노출되면 지급 요청과 웹훅을 모두 위조할 수 있으므로 1년 교체와 노출 의심 때 즉시 재발급을 지킨다.
   - 'payment-svc 지급 어댑터만 읽는다'(ADR-0047 결정 8)는 지킬 수 없다. 파드 권한(IRSA)은 서비스 계정 단위라 한 파드 안의 모듈을 나누지 못한다. `payment-svc`가 읽는다로 고친다.
   - 가상계좌 입금 콜백 `secret`은 결제 원장에 SHA-256 해시만 두고 상수 시간으로 비교한다. 입금이 확정되면 지운다.
5. **연계정보·pid 키 교체 절차를 정한다.**
   - 연계정보 HMAC 키는 버전마다 별도 KMS HMAC 키다(자동 교체 불가). 새 버전은 온세일 윈도우 밖에서만 만들고 새 기록에만 쓴다. 옛 버전은 그 버전으로 만든 기록이 남아 있는 동안 조회용으로 둔다.
   - 본인확인 때 보존 중인 모든 버전으로 HMAC을 계산해 중복을 찾는다. 키 교체 전후로 같은 사람이 계정을 하나 더 만드는 길을 막는다. 버전 수만큼 KMS를 부르지만 본인확인은 계정당 한 번이라 한도에 영향이 없다.
   - pid는 지금처럼 `HMAC(pid 키, ci_hmac)`로 계산한다. 본인확인 때 한 번 계산해 `identity_verification`에 pid, pid 키 버전, 연계정보 키 버전과 함께 저장하고, 토큰 발급 때는 KMS를 부르지 않는다.
     - 검토 보고 때는 'CI 원문에서 계산'을 추천했다. 그러나 CI 원문을 보관하지 않으므로 그렇게 하면 pid 키를 바꿀 때 모든 회원이 본인확인을 다시 해야 한다. 그래서 ci_hmac에서 계산하는 방식을 유지한다.
   - pid 키를 바꿀 때는 온세일 윈도우 밖에서 저장된 ci_hmac으로 모든 pid를 다시 계산해 저장하고, 다음 토큰부터 새 값을 싣는다. 연계정보 키 새 버전도 pid를 바꾸므로 POL-028의 '온세일 밖' 제약을 같이 받는다.
   - 리전 장애(ADR-0031) 뒤 복구할 수 있도록 연계정보·pid HMAC 키, 페퍼 키, TOTP 시드 암호화 키는 다중 리전 KMS 키로 만들고 복구 리전에 복제본을 둔다.
6. **TLS 기준을 하나로 정한다.**
   - 외부에서 PEAKET으로 들어오는 연결(브라우저, 스캐너, 결제사 웹훅): TLS 1.2 이상, 1.3 우선. TLS 1.2는 ECDHE와 AEAD 스위트(AES-GCM, ChaCha20-Poly1305)만 허용한다. CloudFront는 TLSv1.2_2021 이상 보안 정책을 쓰고, NLB에서 바로 받는 `gw-scanner`의 Envoy도 같은 기준이다.
   - PEAKET이 밖으로 나가는 연결(결제사, 본인확인 업체, 소셜 로그인): TLS 1.2 이상, 서버 인증서 검증. 상대가 정한 범위를 따른다(토스페이먼츠는 1.2 이상).
   - 내부 메시 mTLS: TLS 1.3.
   - 관리형 저장소: 서비스가 지원하는 가장 높은 버전을 쓰고 평문으로 내려가지 않게 한다.
     - Aurora PostgreSQL: `rds.force_ssl=1`, `ssl_min_protocol_version`은 TLS 1.2 이상(1.3을 지원하는 버전이면 1.3), `ssl_ciphers`는 순방향 비밀성 스위트만. 클라이언트는 RDS CA로 인증서와 호스트를 검증한다(`verify-full`).
     - ElastiCache: 전송 암호화를 켜고 TLS 1.2 이상.
     - MSK: TLS 1.2(서비스 제약).
   - 양자 내성: CloudFront는 TLS 1.3 클라이언트와 X25519MLKEM768 혼합 키 교환을 한다. ASVS 11.1.4(L3) 이행 계획은 '외부 구간은 CloudFront 기본값을 쓰고, 내부 구간과 서명은 AWS와 Node.js가 지원하면 다시 본다'로 둔다.
7. **셔플 비콘은 미리 정한 라운드를 기다린다(소유자 승인, ADR-0012·POL-005의 대체 규칙을 바꾼다).**
   - 커밋: 대기실 개방 때 `SHA-256("PEAKET-shuffle-v1" ‖ 공연 회차 ID ‖ 시드)`와 함께 사용할 drand 체인(quicknet), 라운드 번호, 알고리즘 버전을 공시한다. 라운드는 참가자 목록을 고정한 시각(T=0)에서 3초 이상 지나 나오는 첫 라운드다 [가정, Phase 2 2.4.1에서 확정].
   - 비콘이 늦으면 그 라운드를 기다린다. 여러 공개 중계 주소를 차례로 시도하고, 기다리는 동안 대기실에 '순서 계산 중'을 보여 준다.
   - 상한은 60초다 [가정, Phase 2 2.4.1에서 확정]. 넘으면 셔플을 멈춘 채 SEV1 경보를 낸다. 시드만으로 셔플하는 비상 처리는 commander 2인 승인으로만 하고, 검증 페이지에 사유와 '이 경우 시드를 아는 내부자가 결과를 미리 알 수 있다'는 한계를 함께 공시한다.
   - 직전 공개 라운드를 대신 쓰는 규칙은 없앤다. 이미 공개된 값이라 시드를 아는 내부자가 목록 고정 전에 결과를 계산할 수 있고, 비콘 수신을 막아 그 분기로 몰 수도 있기 때문이다.
   - 재현 규격(검증 페이지와 공개 스크립트가 같은 결과를 내도록):
     - 결합 키는 `K = SHA-256(시드 ‖ 비콘 값 ‖ 머클 루트 ‖ 공연 회차 ID)`다.
     - 난수는 `SHA-256(K ‖ i)` 블록(i는 64비트 카운터)에서 뽑고, Fisher–Yates는 거부 표본추출로 편향 없는 정수를 쓴다.
     - 셔플 전 배열은 참가 토큰 해시의 오름차순이다.
     - 머클 트리는 정렬한 잎에 `SHA-256(0x00 ‖ 토큰 해시)`, 노드에 `SHA-256(0x01 ‖ 왼쪽 ‖ 오른쪽)`을 쓴다(RFC 6962와 같은 구분 바이트).
   - 시드 공개 시점은 온세일 윈도우가 끝난 직후(T+60분)다.
   - 동시 도착 구간 묶음 셔플(ADR-0041)도 같은 방식이다.
     - 묶음마다 별도 시드를 쓰고, 커밋은 오픈 10분 전까지 공연 상세 화면에 공시한다(로비가 없는 선착순 공연 포함).
     - 머클 잎과 결과 파일 키는 pid가 아니라 사전 검증 토큰 해시다. 공개 파일에 pid에서 나온 값을 싣지 않아 공연을 넘나든 추적을 막는다.
8. **구매 세션 보호는 '소지 증명'으로 줄인다(소유자 승인, ADR-0011 결정 6을 대체한다).**
   - 목적: 쿠키나 입장 토큰만 훔쳐서는 구매 세션을 쓸 수 없게 한다. 기밀성은 TLS가 맡는다. 봇 방어 효과는 주장하지 않는다.
   - 방식:
     - 서버 ECDH P-256 키(kid)와 클라이언트 임시 키로 공유 비밀을 만든다(지금과 같다).
     - `HKDF-SHA256(공유 비밀, salt = 입장 토큰 jti, info = "PEAKET-purchase-v1")`로 요청 인증 키를 만든다.
     - 클라이언트는 요청마다 일련번호를 1씩 올리고 `HMAC-SHA256(키, 메서드 ‖ 경로 ‖ 일련번호 ‖ 본문 SHA-256)`을 헤더에 싣는다.
     - purchase-svc는 상수 시간으로 비교하고, 일련번호가 구매 세션(`s:session:{sid}`)에 저장된 마지막 번호보다 클 때만 받아 재전송을 거부한다.
     - 본문은 암호화하지 않는다.
   - 범위: 구매 세션 안의 쓰기 요청(홀드, 홀드 해제·연장, 주문, 결제 시도, 결제 접수). 예매 취소는 구매 세션 밖이라 재인증 토큰이 맡는다.
   - 재시도: 다시 보낼 때는 새 일련번호로 다시 서명한다. 같은 요청의 중복 처리는 멱등키가 맡는다.
   - 지연 예산: 홀드 경로의 '페이로드 복호화 5ms'를 '요청 인증 확인 1ms' [가정, Phase 2 2.12.1에서 확정]로 바꾸고 남는 4ms를 여유 예산에 더한다.
   - 효과 측정: K6 평가(ADR-0039·0048)에서 이 장치가 있을 때와 없을 때 HTTP 직접 호출형 봇의 1장당 획득 비용을 비교한다.
9. **고권한 토큰 서명 키를 나누고 관리자 비밀번호에 페퍼를 건다(소유자 승인).**
   - 서명 키를 셋으로 나눈다: 팬 토큰(액세스 토큰 aud fan과 팬의 민감 작업 재인증 토큰), 관리 토큰(aud partner·ops와 위험 명령 재인증 토큰), 현장 스태프 토큰(aud scanner). 팬 재인증 토큰(POL-019: 양도, 예매 취소, 계정 연결, 티켓 재발급)은 받는 서비스가 팬 공개키로 검증한다. 팬 재인증 토큰을 팬 키에 두는 것은 추천 적용(2026-10-13)이다. 게이트웨이는 자기 대상의 키만 신뢰한다(gw-fan·gw-queue는 팬 키와 입장 토큰 키, gw-partner·gw-ops는 관리 키, gw-scanner는 현장 스태프 키). 팬 경로의 키가 새도 운영자·현장 스태프 토큰은 위조되지 않는다.
   - 토큰 헤더 `typ`(액세스 `at+jwt`, 입장 `admission+jwt`, 재인증 `reauth+jwt`)과 발급자 `iss`를 넣고 검증한다(RFC 8725 3.11, RFC 9068). 두 발급자(identity, queue)의 ES256 토큰이 서로 바뀌어 받아들여지지 않는다.
   - 관리자 비밀번호와 비상 복구 코드:
     - PBKDF2-HMAC-SHA256(60만 회, 솔트 16바이트) 결과에 KMS HMAC 페퍼 키로 한 번 더 HMAC을 건다. 입력은 `"admin-pw-v1" ‖ 관리 계정 ID ‖ PBKDF2 결과`다.
     - 계정 ID를 넣었으므로 다른 계정 행으로 복사한 값은 통하지 않는다. 페퍼 키가 KMS 밖으로 나오지 않으므로 DB만 유출되면 오프라인으로 비밀번호를 대입해 볼 수 없다.
     - 저장 문자열에 페퍼 키 버전을 넣는다. 키를 바꾸면 다음 로그인 때 새 버전으로 다시 저장한다(ADR-0033 결정 3과 같은 방식).
     - 검증은 KMS `VerifyMac`으로 한다. 관리자 로그인은 드물어 KMS 한도와 비용에 영향이 없다.

## 결과

### 대가
- 데이터: `identity_verification`에 pid·키 버전 칼럼, `admin_account` 비밀번호 문자열에 페퍼 버전, `device_key`에 등록 사유, 구매 세션에 마지막 일련번호, 결제 원장에 입금 콜백 `secret` 해시가 생긴다.
- API: 기기 공개키 등록에 재인증 토큰과 한도 검사, 구매 세션 쓰기 요청에 일련번호·서명 헤더(`encryptedPayload` 제거), 예매 취소의 환불 계좌는 바로 실행할 때만 받기, 셔플 증명에 체인·라운드를 더한다.
- 운영: 키 교체 일정(secrets-and-keys '교체 주기'), 비콘 대기 상한을 넘을 때의 2인 승인 비상 처리, 입장 시작 뒤 현장 부스 재발급이 생긴다.

### 남는 한계
- 회전 QR은 실시간 중계, 입장 시작 전에 계정을 넘긴 뒤의 재발급(24시간 1회), 루팅·프로필 복사를 막지 못한다. 현장의 동시 스캔 경보와 실물 대조, 사후 적발에 기댄다.
- 결정 2는 재발급(REISSUE)만 다룬다. 판매자가 월렛을 한 번도 열지 않고 계정을 넘기면, 산 사람의 첫 키 등록(ISSUE)은 입장 시작 뒤에도 부스를 거치지 않는다. 같은 날 스캔 플랫폼 검토에서 찾았고 그 검토를 반영하는 결정에서 다룬다.
- 구매 세션 소지 증명은 브라우저를 조종하는 봇을 막지 못한다. 그 봇은 페이지가 대신 서명한다.
- 비상 셔플(시드만)을 쓰면 내부자가 결과를 미리 알 수 있다. 쓰면 공시한다.
- 키 교체 주기는 자체 기준이다(결정 4).
- 연계정보 키의 옛 버전은 그 버전 기록이 남아 있는 동안 지울 수 없다.

### 되돌릴 조건
- 계정 넘기기와 재발급을 통한 재판매가 적발 기록에서 크게 나타나면 네이티브 월렛을 다시 본다.
- K6에서 소지 증명이 HTTP 직접 호출형 봇의 1장당 획득 비용을 거의 바꾸지 못하면 없애고 지연 예산을 돌려받는다.
- 입장 시작 뒤 현장 부스 재발급이 회차 관람객의 0.5% [가정]를 넘으면 재발급 한도를 다시 정한다.
- drand가 1년에 두 번 이상 대기 상한을 넘기면 두 번째 비콘 출처를 더한다.
