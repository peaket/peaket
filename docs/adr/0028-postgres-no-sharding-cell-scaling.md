# ADR-0028: PostgreSQL 데이터베이스의 샤딩 배제 및 셀(Cell) 기반 수평 확장 전략

- **상태**: 채택 (2026-10-05 설계서 §8 PostgreSQL 항목, 21장 및 29장에 최초 수립, 2026-10-08 아키텍처 결정 레코드(ADR)로 공식 이관) 2026-10-20(ADR-0070): 결정 4의 PgBouncer 트랜잭션 풀링에 맞춰 서버 쪽 시간 초과는 서비스 DB 사용자의 역할 기본값으로 두고(연결 시작 매개변수와 세션 SET은 쓰지 않는다), PgBouncer `query_wait_timeout`·`idle_transaction_timeout`·`query_timeout`을 정한다. PgBouncer 배치는 wbs 2.11.2에서 정한다(docs/architecture.md §5 '시간 초과 기본값'). 2026-10-22(ADR-0083): 결정 3의 월 파티션은 각 표의 UUIDv7 `id` 범위로 나누고(경계는 한국 시각 매월 1일 0시), 파티션 키를 담지 못하는 전역 유일 규칙(주문 멱등키, 주문당 결제 1건)은 파티션하지 않는 유일 확인 표(`order_idempotency`·`payment_per_order`)가 맡는다. 파티션은 미리 만들고 기본 파티션은 두지 않는다. 결정 4의 PgBouncer를 마이그레이션 잡은 거치지 않는다(docs/data.md §2, docs/devops.md §7.2). 2026-10-22(ADR-0086): 결정 3의 '파티션째 지우기'는 주문·결제·티켓을 가리키는 자식 표도 부모와 같은 범위로 나눠, 자식 파티션을 먼저 지운 뒤 한다(그 범위를 가리키는 행이 남으면 떼어 내기가 오류다). 정비 잡이 파티션 부모 표를 ANALYZE한다. 결정 4의 PgBouncer는 `max_prepared_statements`를 켜고, 열 구조를 바꾸는 마이그레이션 뒤 `RECONNECT`한다(docs/data.md §2, docs/devops.md §7.2). 2026-10-28(ADR-0114, 소유자 승인 '추천안 동의'): 결정 3의 월 파티션을 주문·결제·티켓과 그 자식 표에서 거둔다. 5년치(주문 약 1,700만·티켓 약 3,500만)가 한 표로 감당할 크기라 이 표들은 나누지 않고, 보존 기한이 지난 행은 정비 잡이 정비 시간에 1만 건 [가정]씩 나눠 지운다(V-T29로 잰다). 파티션은 Outbox·회차 범위 표·발송 기록에만 남고, 잰 값이 필요를 보이면 다시 고른다(ADR-0114 결정 6, docs/data.md §2). 2026-10-28(ADR-0116, 소유자 승인 '추천안 동의'): 결정 4의 PgBouncer는 서비스 DB마다 공용 Deployment 하나(복제 3, AZ 셋)로 둔다(docs/infra-handover.md §3.2). 2026-10-28(기술 검토 낮음-144, 소유자 승인 '추천안 동의'): 결정 5의 클러스터 분리(지금은 purchase·payment·ticket·ops 전용·공유의 다섯, ADR-0102)를 더 단순한 안 '돈이 오가는 클러스터 하나(purchase·payment) + 나머지 하나'와 견준다. 쓰기량만 보면 하나로도 충분하다(맥락: 판매 확정 초당 약 28건, 결제 승인 피크 약 300 TPS). 그래서 나눠 두는 근거는 처리량이 아니라 격리다. payment는 결제 비밀과 결제사 장애의 영향, ticket은 현장 입장 가용성과 이 클러스터에만 붙이는 도쿄 Global Database(복제는 클러스터 통째로다), ops는 오픈 직전 로그인 몰림과의 분리다(docs/data.md §1). 결론(지금의 분리)은 그대로 두고, 바꾸는 판단은 잰 값으로 한다. 온세일 피크에 한 클러스터의 쓰기 인스턴스 CPU가 60% [가정]를 넘거나 연결 수가 상한의 70% [가정]를 넘으면 그 클러스터의 서비스를 더 나눈다. 비용 측정(wbs 4.8.1)에서 두 클러스터가 모두 30% [가정] 아래이고 위 격리 근거가 없는 쌍이면 합치기 후보로 docs/infra.md §11 '줄일 수 있는 후보' 표에 올린다.
- **관련 문서**: 설계서 §8(데이터 저장소), 21장(파티셔닝 및 커넥션 풀), 29장(샤딩 전략), docs/data.md, ADR-0014, ADR-0021
- **관련 ID**: NFR-013, NFR-018, NFR-021, NFR-025

## 맥락
- 티켓팅 시스템의 피크 트래픽은 대기열 진입(초당 20만 건)과 좌석 조회에 집중되며, 실제 최종 판매 확정 쓰기 빈도는 평균 초당 약 28건, 결제 승인 피크 시에도 약 300 TPS 수준이다. 아웃박스 이벤트 발행을 합산하더라도 초당 수천 건 미만이고 홀드 원장의 비동기 기록은 초당 약 500건으로 단일 Aurora PostgreSQL Writer 인스턴스의 하드웨어 처리 한계 내에 충분히 안착한다.
- `purchase-svc` 내부에서 수행되는 '주문 레코드 생성', '좌석 상태 SOLD 전이', '사용자별 1인 구매 한도 원자적 차감'은 강력한 단일 ACID 트랜잭션으로 묶여야 한다. 만약 데이터베이스 샤딩을 도입할 경우 2단계 커밋(2PC)이나 분산 사가 트랜잭션의 오버헤드로 인해 시스템 복잡도와 장애 확률이 기하급수적으로 증가한다.
- 또한 전체 트래픽 부하는 플랫폼 전체가 아니라 각 공연 오픈 시점의 '동시 입장 제어 상한'에 의해 물리적으로 상한선이 제어된다.

## 결정
1. 프로덕션 PostgreSQL 데이터베이스에 인위적인 애플리케이션 레벨 분산 샤딩(Application Sharding)을 도입하지 않는다.
2. 미래에 동시 티켓 오픈(On-sale) 규모가 대폭 확대되어 단일 DB 용량을 초과할 경우, 데이터베이스 내부 샤딩 대신 공연 단위로 독립된 Redis, RDS, 서비스 인스턴스를 통째로 격리 복제하는 `셀 기반 아키텍처(Cell-based Architecture)`로 수평 확장한다.
3. 주문, 결제, 티켓 테이블은 월 단위 범위 파티셔닝(Range Partitioning)을 적용하여, 전자상거래법상 5년 보관 연한이 경과한 콜드 데이터를 `DROP PARTITION` 명령으로 시스템 부하 없이 안전하게 일괄 삭제하고 B-Tree 인덱스 비대화를 억제한다.
4. 데이터베이스 커넥션 관리는 PgBouncer를 트랜잭션 풀링 모드로 구성하여 연결 급증을 흡수하며, 순수 조회 트래픽은 Aurora 읽기 복제본(Read Replica)으로 분산한다. 단, 예매 직후 주문서 조회와 같은 자신의 쓰기 즉시 읽기(Read-Your-Writes) 흐름은 주 인스턴스(Writer)로 라우팅한다.
5. 도메인 경계 분리를 위해 `purchase`, `payment`, `ticket` 서비스는 각각 독립된 Aurora 클러스터를 운영하며, 상대적으로 트래픽이 적은 `identity`, `ops`, `core` 서비스는 단일 클러스터 내에서 논리적 스키마와 DB 유저 역할로 분리한다.

## 검토한 대안
| 대안 | 기각 사유 및 한계점 |
| --- | --- |
| 공연 ID 기반 분산 샤딩 | 샤드 간 크로스 트랜잭션이 발생할 때 2PC 조정 비용으로 인해 p99 지연 시간이 심각하게 튀며, 특정 대형 콘서트 샤드로 부하가 집중되는 핫스팟 불균형 문제를 해소하기 어렵다. |
| 분산 NewSQL (CockroachDB 등) | 다중 리전 복제에 따른 쓰기 RTT 가산 및 상용 라이선스 종속 위험으로 인해 ADR-0021에서 기각되었다. |

## 결과와 트레이드오프
- 단일 관계형 데이터베이스의 친숙한 ACID 무결성과 단순한 개발 생산성을 완벽히 누릴 수 있다.
- 다수의 메가 이벤트가 동일 시간대에 동시 오픈되는 극단적 환경에서는 사전에 셀 단위 라우터와 인프라 프로비저닝을 준비해야 하는 운영 계획 수립이 요구된다.
