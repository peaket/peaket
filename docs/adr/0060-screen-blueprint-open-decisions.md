## 결정

1. **D1 다른 기기·탭에서 대기 중일 때: (나)를 채택한다.** 새 기기에서 로비나 대기열에 들어오면 먼저 '처음 기기에서 계속하세요'라고 안내하고, 처음 기기를 쓸 수 없는 사람(분실, 브라우저 저장소 초기화, 인앱 브라우저에서 외부 브라우저로 옮김)은 그 자리에서 기존 참가를 취소하고 다시 참가할 수 있다. 로비(오픈 전)에서는 셔플 전이라 다시 참가해도 불리하지 않고, 오픈 뒤 대기열에서는 새 순번(맨 뒤)을 받는다. 취소한 번호는 빠진 번호로 돌리고 중복 확인 키를 지운다. 처음 기기는 다음 요청에서 "다른 기기에서 이 참가를 취소했습니다"를 본다. 로비 참가 취소 API(`DELETE /v1/queue/{eventId}/lobby`)를 더한다.
   - 이유: FR-007(Must)과 POL-002 예외 열이 이미 정한 동작이다. (가)로 하면 처음 기기를 잃은 사람이 온세일 윈도우가 끝날 때까지 다시 들어오지 못하고(중복 확인 키가 남음), FR-007·POL-002를 낮춰야 한다.
   - 공정성: 로비에서 다시 참가해도 셔플 결과는 오픈 뒤에 정해지고(커밋-공개), 오픈 직후 동시 도착 묶음 안에서 다시 참가해도 묶음 결과는 공개 전이라 결과를 보고 다시 뽑을 수 없다. 오픈 뒤 다시 참가는 맨 뒤라 이득이 없다. 셔플 결과를 받는 시각의 분산(ADR-0058)은 순번과 무관하다.
   - 남는 것: 만료(차례 뒤 15분 초과) 뒤 같은 회차에 다시 들어오는 규칙은 정하지 않았다(d5 §11.2 K7).
2. **D2 대기 번호 표시: (가)를 채택한다.** 대기열 화면은 앞 인원과 예상 대기만 보인다. 내 대기 번호와 현재 입장 번호(serving)는 화면에 내지 않고 계산에만 쓴다. FR-007의 표시와 같고, 빠진 번호 때문에 두 번호의 차가 앞 인원과 달라 혼란을 준다. guide/02의 예시 문구를 이에 맞추고, design/d1의 'serving 표시 메커니즘 차용'은 계산 방식의 차용으로 적는다.
3. **D3 언어 주소: (가)를 채택한다(추천 적용).** 한국어는 접두 없이 기본 주소를 쓰고 영어·일본어·중국어 간체는 `/en/…`·`/ja/…`·`/zh/…`를 붙인다. 페이지마다 hreflang을 두고, 브라우저 언어로 자동 이동하지 않으며, 메뉴 시트·바닥글·로그인 화면의 언어 링크로 바꾼다. 언어 쿠키는 두지 않는다. 이유: Google 안내와 같고, 공연 페이지 CDN 캐시 키가 주소만으로 나뉘어 쿠키에 따라 캐시가 갈리지 않으며, 로케일별 정적 생성으로 대기실 번들 예산(JS 50KB)을 지킨다. 대기 상태 파일과 API 응답은 언어와 무관하다.
4. **D4 시각 표기: (가)를 채택한다.** 팬 화면의 공연 일시와 마감 시각은 공연장 현지 시각으로 적고, 기기 시간대가 다르면 기기 시각을 함께 적는다(NFR-024). 파트너·관제 콘솔은 시간대를 붙인 KST로 적는다. 로그와 기록은 UTC다. asvs/delivery 16.2.2의 '화면 표시만 KST'는 이 구분으로 고친다.
5. **D5 쿠폰: (가)를 채택한다.** 쿠폰 기능을 두지 않는다. design/d2 §3.1의 '쿠폰 유효성' 예시는 실제 비동기 검증(양도 받는 사람 확인)으로 바꾸고, ADR-0020에는 상태 줄로 쿠폰이 기능이 아닌 예시임을 적는다.
6. **D6 팬클럽 선예매 자격: (가)를 채택한다.** 자격은 판매 정책 규칙(SCR-024)으로만 판정하고 팬 쪽 자격 확인 단계는 두지 않는다. 자격이 없으면 공연 상세(SCR-002)의 예매 제한 버튼 상태로 안내한다.
7. **D7 시간 제한 경고: 두 경고를 둔다(추천 적용).**
   - 파트너·관제 콘솔: 유휴 만료(1시간, POL-019) 2분 전 [가정]에 경고 대화상자와 [ 계속 사용 ] 버튼을 띄운다. 누르면 유휴 시간이 다시 시작된다(WCAG 2.2.1 연장). 최대 수명 24시간은 늘리지 않는다(20시간 예외).
   - 구매 세션: 주문서를 만들기 전(좌석 선택, SCR-010) 무활동 4분 [가정]에 "1분 뒤 예매가 끝납니다" 경고와 [ 계속하기 ]를 띄운다. 누르면 구매 세션 유휴 연장 요청을 보낸다(API는 d5 §1.6에 추가). 주문서 생성 뒤에는 POL-009대로 무활동으로 끝내지 않는다.
   - 좌석 홀드(7분, 1회 연장)와 구매 세션 최대 체류(45분)는 온세일이라는 실시간 경쟁에서 다른 사람이 살 좌석과 입장 자리를 묶는 제한이므로 WCAG 2.2.1의 실시간 예외로 본다(판단). 남은 시간 표시, 만료 전 경고, 1회 연장은 그대로 둔다. design/d1과 POL-012의 '1회 연장으로 2.2.1을 맞춘다'는 이 판단으로 고친다.
   - 경고는 `role="alertdialog"`로 스크린리더에 알리고 초점을 [ 계속 ] 버튼에 둔다.
8. **D8 관제 메뉴 권한: d5 §3.3 제안을 채택해 planning/03 §3 권한 매트릭스에 다섯 행을 더한다.** 관리 계정(운영자·CS) 초대·역할 부여·회수·잠금 해제(재초대)·세션 강제 종료·지정(SCR-064), 파트너사·계약(SCR-065), 팬 조회(SCR-066), 봇 판정 표본 검토(SCR-067, FR-049대로 CS), 공지 관리(SCR-068). 세부(추천 적용): commander 역할의 부여·회수는 다른 commander의 승인(2인, SCR-046)으로 하고, 자기 역할은 바꾸지 못하며, 권한 부여·변경·말소 내역은 3년 보관한다(고시 §5③, data-classification).
9. **D9 수수료율·보증 변경 승인: (나)를 채택한다(추천 적용).** 계약 수수료율과 보증 조건의 변경은 operator가 요청하고 commander가 승인한다(2인, 요청자 제외, SCR-046). 바뀐 수수료율은 승인 뒤 판매 승인을 받는 공연부터 쓰고, 판매 승인 때 공연에 수수료율을 고정해 이미 판매 승인된 공연의 정산서는 고정한 값으로 계산한다. 판매자 정보와 결제사 등록 입력은 operator 1인이다. 이유: 정산서의 수수료율 정정이 이미 2인 승인이고, 파트너에게 갈 돈을 바꾸는 고가치 흐름이다(ASVS 5.0 2.3.5).
10. **D10 프로토타입 구현 방식: A를 채택한다.** Vite + React + TypeScript 앱 하나에 경로 묶음 넷(`/web`, `/partner`, `/console`, `/scanner`)을 두고, `@seed-design/css`·`@seed-design/react`와 tokens.json의 CSS 변수를 쓰며, 가짜 API는 MSW로 openapi.yaml의 응답 모양을 따른다. 컴포넌트 이름은 CMP 이름과 같게 짓는다. 코드는 이 저장소의 `prototype/` 폴더에 두고 버전은 시작할 때 고정한다(추천 적용). 실제 개인정보·비밀값·결제 키를 넣지 않고 가상 데이터만 쓰며, 상시 배포하지 않는다(ADR-0057). 운영 기능이 아니므로 ASVS 추적 표 대상이 아니다.
11. **D11 쿠키 동의 배너: (가)를 채택한다.** 배너를 두지 않는다. 쓰는 쿠키는 로그인(Auth.js 세션·액세스 토큰·리프레시 토큰), 대기열 공정성(도착 시각 쿠키), 봇 방어(최초 방문 쿠키)처럼 서비스와 보안에 필요한 것뿐이고, 처리방침의 자동 수집 장치 항목(§30①7호)에 이름·목적·보관 기간·거부 방법과 거부 때 영향을 적는다(SCR-057). 광고·분석용 제3자 쿠키를 쓰지 않는다. 쓰게 되면 다시 정한다. 언어는 주소로 나눠 언어 쿠키가 없다(결정 3).
12. **D12 소셜 로그인 버튼: 기본값을 채택한다.** '카카오 로그인'과 'Google 계정으로 로그인'은 2026-10-13 원문 확인대로 이미 반영했고, '네이버 로그인'은 가이드 원문을 확인한 뒤 확정한다(d5 §11.2 K1).
13. **D13 알림 채널: d5 §9.1의 '†' 제안을 채택한다(추천 적용).** 가상계좌 입금 안내, 지연 환급 계좌 요청, 회차 취소·연기, 배상 계좌 요청은 이메일에 알림톡을 더하고, 보안 사고 이용자 통지는 이메일에 문자를 더한다. 나머지 '†' 항목은 표대로 한다. 알림톡과 문자는 발송 대행 계약(wbs §7) 뒤에 켜고, 그 전에는 이메일과 웹 푸시로만 보낸다.
14. **D14 셔플 결과 발표 지연 문구: d5 §5.7의 문구를 채택한다.** 60초 넘게 늦으면 "순서 발표가 늦어지고 있습니다. 참가는 그대로 유지되고, 발표되면 자동으로 이어집니다"를 보인다.
15. **D15 WBS: 넣는다(추천 적용).** 프로토타입 P0는 Phase 0에 새 묶음 0.10(12.5일, ±20% 10~15일, ADR-0059의 추정 범위와 같음)으로, 새 화면 15개의 구현은 각 Phase의 해당 묶음에 12일로, D1의 로비 참가 취소는 2.4.3에 0.5일로 넣는다(합계 +25일). P1·P2 프로토타입은 P0 검토 뒤 범위를 다시 정하고 지금은 넣지 않는다.

| D1 기존 순번을 새 기기로 옮김 | 대기표를 처음 기기에 묶는 POL-002의 취지를 깨고, 계정을 넘겨 순번을 옮기는 거래를 쉽게 한다 |
| D2 내 번호와 현재 입장 번호도 표시 | 빠진 번호 때문에 두 번호의 차가 앞 인원과 달라 보이고, FR-007은 앞 인원과 예상 시간을 정했다 |
| D3 쿠키·Accept-Language로 언어 결정 | Google이 권하지 않고, 공연 페이지 캐시가 쿠키에 따라 갈린다 |

| D9 (가) operator 1인 | 정산서 수수료율 정정이 2인 승인인 것과 어긋나고, 한 사람이 파트너 지급액을 바꿀 수 있다 |
| D10 B 실제 앱 구조, C 디자인 도구 | d5 §10.5대로 B는 화면 검토가 늦어지고, C는 상태가 많은 화면을 흉내 내기 어렵다 |
| D11 쿠키 동의 배너 | 서비스·보안에 필요한 쿠키만 쓰므로 배너가 고를 것이 없고, 대기실 번들과 첫 화면을 무겁게 한다 |

## 결과와 트레이드오프

- API: 로비 참가 취소와 구매 세션 유휴 연장이 openapi에 없다. 로비 참가 취소는 이번에 openapi에 더하고, 유휴 연장은 d5 §1.6 목록에 더해 API 설계 때 반영한다.
- WBS가 25일 늘어난다(프로토타입 12.5일, 새 화면 12일, 로비 참가 취소 0.5일). 경고 시각 2분·4분은 사용성 시험에서 정할 값이다.
- 1인 기간에는 2인 승인(commander 역할 부여, 수수료율 변경)을 한 사람이 두 역할로 하게 되는 한계가 있다(docs/devops.md §15와 같은 한계).
- 좌석 홀드와 최대 체류를 WCAG 2.2.1 실시간 예외로 본 것은 프로젝트의 판단이고, 접근성 검토(wbs 7.5)에서 다시 확인한다.
- 알림톡·문자는 발송 대행 계약 전까지 쓰지 못하고, 그동안 iOS 웹 푸시 제약으로 안내가 늦을 수 있다(wbs §7의 남는 한계와 같음).

## 되돌릴 조건

- D1: 다시 참가가 봇이나 부하 문제를 만들면 회차당 다시 참가 횟수를 제한한다.
- D7: 사용성 시험에서 경고 시각이 너무 이르거나 늦으면 값을 고친다.
- D10: 프로토타입 컴포넌트를 실제 앱으로 옮기기 어려우면 그때 B로 바꾼다.
- D11: 광고·분석용 제3자 쿠키를 쓰게 되면 배너와 동의를 다시 정한다.
