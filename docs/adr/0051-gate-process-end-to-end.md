# ADR-0051: 현장 입장 과정을 처음부터 끝까지 설계한다 (스캐너 기기 등록, 초대 수락 조건, 해제의 서버 확인, 입장 상태 공유, 입장 중 소유권 동결, 현장 예외 절차, 입장 기록 마감)

- **상태**: 채택 (2026-10-13. 소유자 승인: 현장 입장 과정 검토의 결정 여섯 건(D1~D6)과 보안 결함·틀린 전제 정정 추천안에 "추천대로 승인". 화면·API·데이터 규격과 세부 수치는 추천 적용(2026-10-13)이고, 측정으로 정할 값은 [가정, Phase N …에서 확정]으로 표시한다.) 2026-10-13 전수 점검(2026-10-14 2차, 추천 적용): 결정 10의 '키는 등록 버튼으로만'을 양도 수락·돌려주기·회수 뒤 새 보유자의 첫 등록(reason TRANSFER)에도 적용했다. 결정 12·13의 취소 무효 확정 절차(이상 표시 → CS 확인)를 POL-032 예외 열과 planning/04 F-10에 반영했고, 양도 회수 시한을 POL-038 ③에서 '입장 시작 전'으로 맞췄다. 2026-10-14 프로토타입 점검: 결정 11의 예외 통과 사유는 '부스 통신 두절'을 더한 다섯 가지로 읽는다(docs/features/offline-gate.md §9.1·openapi와 같다. 같은 결정의 부스 절이 이 경우 예외 통과를 쓴다고 이미 적었다. ADR 본문은 고치지 않고 상태 줄로만 보완한다, 00-summary §1). 2026-10-14 추천 적용(ADR-0062 결정 27): 대안 B의 기기 등록 코드는 RFC 8628 §6.1 문자 집합 12자, 10분 [가정] 1회용, 서버는 SHA-256만 보관한다(offline-gate §6.1). 예외 통과의 사후 검토 표시는 책임자 스캐너의 이상 표시 목록에 넣지 않는다(결정 42). 2026-10-21: 본문의 REST 경로는 ADR-0081의 옛 경로 대응표로 새 경로를 읽는다(경로 이름 규칙 점검). 2026-10-22(ADR-0086): 회차별 변경 일련번호는 DB 시퀀스가 아니라 회차별 카운터 행(`scanner_seq`)을 같은 트랜잭션에서 올려 매겨, 번호 순서와 커밋 순서를 맞춘다. 이상 표시에 든 스캔은 자식 표 `gate_flag_scan`에 두고, `scan_event`·`scanner_change`는 회차 ID 범위로 달마다 나눈다(offline-gate §6.3, docs/data.md §2). 2026-10-26(4차 점검 3부): 결정 1의 인증서 PoC(wbs 5.4.3) 확인 항목과 되돌릴 조건의 '네 항목'은 ⑤ 스캐너 PWA(`scanner.peaket.example`)에서 `scanner-api`로 가는 교차 출처 요청(`fetch`와 서비스 워커 업로드)에도 기기 인증서가 실리고 PWA가 응답을 읽는지를 더한 다섯 항목으로 읽는다(offline-gate §6.1·§12, ADR-0065 결정 10). 결정 2의 카카오 검증 이메일 표시는 `is_email_verified`다(identity §6.1, POL-034).

## 맥락

- 2026-10-13 소유자 요청("스태프 초대부터 스캐너가 QR로 로그인하고 관객 티켓을 스캔해 처리하는 전체 과정이 잘 정리되고 상세설계가 완벽한지 검토")으로 현장 입장 과정을 단계별로 대조했다.
- 정상 흐름은 FR-035·036·046, POL-018·031, offline-gate, identity §6.1, ADR-0025·0030, SCR-033~037, 테스트 O-T·I-T까지 ID로 이어져 있었다. 그러나 처음부터 끝까지 보는 곳이 없었고, 단계마다 빈칸과 모순이 있었다.
  - **보안 결함 4건**: ① 스태프 해제를 서비스 메모리의 종료 세션 목록(15분 보관)으로만 막는데 스태프 토큰은 역할 유효 끝까지 살아 있어, 해제 15분 뒤 다시 통한다. ② 휴대폰이 없는 스태프 대신 책임자가 승인하면 그 기기에 책임자 권한(수동 입장, 플래그 해제)이 실린다. ③ 입장 중에도 돌려주기·양도 수락·첫 키 등록이 열려 있어, 오프라인 스캔이 올라오기 전에 한 장으로 두 명이 들어갈 수 있고, 첫 키 등록은 ADR-0050의 부스 확인을 거치지 않는다. ④ 초대 수락에서 '본인'을 판정하는 규칙이 없어 초대 링크가 전달되면 누구나 수락한다.
  - **틀린 전제 3건**: ① 1분 변경분을 주기적 백그라운드 동기화로 받는다고 적었지만 크롬의 최소 간격은 12시간이다. ② 스캐너 mTLS 인증서를 PWA가 어떻게 쓰는지, 누가 기기를 등록·폐기하는지가 없고, 분실 대응이 가리킨 RB-12는 다른 런북이다. ③ 버전 벡터 중복 탐지와 재입장 판정은 '다른 스캐너의 입장 기록을 받는가'가 정해지지 않아 성립하지 않는다.
  - **운영 공백**: 현장 부스·수동 입장·퇴장 스캔의 절차·화면·API, 동시 스캔 경보가 현장에 가는 길, 로그아웃·해제·만료 뒤 남은 기록, 입장 기록이 확정되는 시점, 공연 당일 관제 화면이 없었다.
  - **규격 빈칸**: 목록 응답 스키마, 변경분 기준값, 스캔 기록의 사유·방식, `scanner_device` 엔티티, 공연 종료 시각, 휴대폰 쪽 초대 수락·스캐너 승인 화면, 보안 추적표(docs/security/asvs/offline-gate.md 예정)가 없었다.

## 결정

1. **스캐너 기기는 PEAKET이 등록·관리하고 파트너에 배정한다(D1, 소유자 승인).**
   - operator가 관제 콘솔 '스캐너 기기 관리'(SCR-053)에서 기기를 만든다(기기 이름, 배정 파트너). 관리 앱(Android Enterprise 기기 관리)이 기기 안에서 키쌍을 만들고 PEAKET 사설 CA 인증서를 받는다. 개인키는 기기 밖으로 나오지 않게 하는 것이 목표다 [PoC로 확인].
   - 기기는 한 파트너(`promoter_id`)에 묶인다. 그 파트너 공연에 배정된 스태프만 그 기기로 로그인한다.
   - 인증서 수명은 30일 [가정, wbs 5.4.3 PoC에서 확정]이고 만료 7일 전에 관리 앱이 갱신한다. 회차마다 재발급하지 않는다. 회차 범위는 스태프 세션(결정 3)과 기기 배치(결정 5)가 정한다.
   - 폐기는 operator가 SCR-053에서 즉시 한다. 스캐너 API는 요청마다 기기 상태를 확인하므로(결정 4) 다음 요청부터 거부되고, 그 기기의 스태프 세션도 끝난다. 분실·도난 절차는 RB-22다.
   - 실물 소유(대여·구매)는 파트너 계약에서 정한다.
   - PoC(wbs 5.4.3)에서 관리형 Android 기기와 크롬 설치형 PWA로 네 가지를 확인한다. ① 사람에게 인증서 선택 창을 띄우지 않고 고르는가. 크롬 정책 자동 선택은 크롬이 프로비저닝한 인증서만 되므로, OS 인증서라면 관리 앱이 인증서 선택에 자동으로 답해야 한다. ② 서비스 워커가 보내는 업로드에도 인증서가 실리는가. ③ 갱신 중 끊김이 없는가. ④ 폐기가 몇 초 안에 반영되는가.
   - 하나라도 안 되면 대안 B로 간다. 기기 등록 때 스캐너 PWA가 WebCrypto 키(ECDSA P-256, `extractable=false`)를 만들어 SCR-053이 보여 주는 등록 코드로 기기 기록에 묶고, 요청마다 DPoP(RFC 9449) 증명을 붙인다. 스태프 토큰은 인증서 지문 대신 그 키의 지문에 묶는다. B의 키는 소프트웨어 키라 기기 결속이 월렛 키(ADR-0050 결정 1)만큼 약하다. 결과는 PoC 뒤 ADR로 남긴다.
2. **스태프 초대 수락 조건을 정한다(보안 결함 ④, 추천 적용).**
   - 수락할 수 있는 계정: 휴대폰 본인확인을 마쳤고, 초대 이메일이 계정의 검증된 이메일(구글·카카오의 `email_verified`)과 같아야 한다. 다르면 403과 '이 계정 이메일로 다시 초대를 요청하세요'를 보인다. 네이버는 검증 표시가 없어(identity §2.1) 구글이나 카카오를 연결해야 한다. 초대 링크가 전달돼도 다른 사람은 수락하지 못한다.
   - 수락 화면(SCR-050)은 파트너·회차·역할·유효 시간을 보이고 동의 두 개를 나눠 받는다(개인정보 보호법 §22①1호·2호). ① 수집·이용: 배정 정보와 스캔 기록에 계정 ID를 남긴다(§15②의 목적, 항목, 보유 기간, 거부권과 불이익). ② 파트너 제공: 닉네임, 역할, 수락 여부, 스캔·예외 통과 건수를 그 회차의 파트너에게 보인다(§17②의 받는 자, 이용 목적, 항목, 보유 기간, 거부권과 불이익). 파트너 제공이 제3자 제공인지 처리 위탁인지는 따지지 않고 동의를 받는다. 동의하지 않으면 배정을 받을 수 없다는 불이익도 함께 알린다.
   - 초대 토큰은 32바이트 난수이고 SHA-256 해시만 저장한다. 24시간, 한 번 쓰면 끝이며, 지나면 상태가 EXPIRED다. 같은 회차·같은 계정의 배정은 하나다. 재발송은 새 토큰을 만들고 옛 토큰을 무효로 한다. 한 번에 여러 이메일(최대 200명 [가정])을 초대할 수 있다.
   - 초대 링크는 토큰을 URL 조각(`#token=…`)에 담아 서버 접근 기록에 남지 않게 하고, 화면이 토큰을 요청 본문으로 보낸다(`POST /v1/staff-invitations/lookup`, `POST /v1/staff-invitations/accept`). 경로에 토큰을 넣던 `POST /v1/staff-invitations/{inviteToken}/accept`는 없앤다(ASVS 14.2.1).
3. **스캐너 로그인(기기 승인)을 고친다(보안 결함 ②, 추천 적용).**
   - 확인 코드(RFC 8628 user_code): 20개 문자 8자, 4자씩 하이픈(약 34.5비트, RFC 8628 §5.1). 수명 5분(ASVS 6.5.5의 10분 이내). 계정당 승인 실패 5회/10분, 기기당 코드 발급 10회/시간 [가정, wbs 5.5.2에서 확정]. QR로 넘기므로 길어져도 입력 부담이 없다.
   - 승인 화면(SCR-051, 휴대폰)은 기기 이름·배정 파트너·확인 코드와, 승인하는 사람의 지금 유효한 배정 목록을 보인다. 배정이 둘 이상이면(낮·저녁 공연) 여기서 고른다. 게이트 구역은 승인 화면에 보이지 않는다(결정 5).
   - 스캐너가 보여 주는 QR(`verification_uri_complete`)은 확인 코드를 URL 조각(`#code=…`)에 담고, 승인 화면이 코드를 요청 본문으로 보낸다(`POST /v1/device-approvals/lookup`, `POST /v1/device-approvals`). 경로에 코드를 넣던 `/v1/device-approvals/{userCode}`는 없앤다.
   - 스태프는 휴대폰의 '로그인된 기기 관리'(SCR-017)에서 자기 스캐너 세션을 보고 끝낼 수 있다.
   - 대리 승인: 휴대폰을 쓸 수 없는 스태프 대신 책임자가 승인하면 토큰 역할은 `gate_staff`로 낮춘다. 세션에 대리 표시와 책임자 배정을 남기고, 스캔 기록은 POL-031대로 책임자 계정으로 남는다.
   - 세션 수: 기기마다 활성 세션 1개다. 같은 기기의 새 승인은 이전 세션을 끝낸다(교대). 계정마다 활성 스캐너 세션 1개다. 다른 기기의 승인은 이전 기기의 세션을 끝낸다.
   - 로그아웃과 교대 뒤에도 큐에 남은 기록은 기기 인증으로 올라간다(결정 9).
4. **스태프 해제와 만료는 서버가 요청마다 확인한다(보안 결함 ①).**
   - 스캐너 경로(gw-scanner 뒤 ticket-svc·identity-svc)는 토큰 서명 검증에 더해 요청마다 `scanner_session`(끝나지 않았고 만료 전)과 `scanner_device`(ACTIVE)를 확인한다. 결과는 파드 메모리에 5초 [가정] 둔다. 스캐너 요청은 기기마다 1분에 몇 번이라 부담이 작다.
   - 서비스의 종료 세션 목록(15분 보관, identity §3)은 팬·관리 토큰에만 쓴다. 해제 15분 뒤 스태프 토큰이 다시 통하는 문제를 없앤다(ASVS 7.4.1, 8.3.2 L3 선별 채택).
   - 토큰과 기기를 묶는다. 스태프 토큰에 `cnf`(인증서 SHA-256 지문 `x5t#S256`, RFC 8705. 대안 B는 키 지문 `jkt`)를 싣고, gw-scanner가 요청의 인증서(또는 DPoP 키)와 비교한다(ASVS 10.3.5·10.4.14 L3 선별 채택).
5. **근무 준비와 기기 배치를 나눈다(추천 적용).**
   - '기기 등록'은 결정 1(operator)만 가리킨다. 스캐너 로그인 뒤 화면(SCR-033)은 '근무 준비'로 이름을 바꾼다. 목록 전체 받기, 시계 보정, 화면 꺼짐 방지(Screen Wake Lock), 준비 완료 보고를 한다.
   - 기기 배치는 그 회차에서 그 기기의 게이트 구역과 모드(입장 IN·퇴장 OUT)다. 파트너(SCR-037 '현장 운영' 탭)나 현장 책임자(스캐너 '현장 관리' SCR-052)만 정한다. 일반 스태프는 바꾸지 못한다. 배치가 없으면 근무 준비가 멈추고 '책임자에게 배치를 요청하세요'를 보인다. 서로 다른 문의 기기를 같은 구역으로 두는 실수를 책임자 권한으로 줄인다.
   - 배치 변경은 온라인에서만 된다. 오프라인에서 구역을 바꿔야 하면 기기를 바꾼다(남는 한계).
   - 퇴장 모드는 재입장 허용 회차에서만 배치할 수 있고, 스캐너 화면 위쪽에 모드를 크게 보인다.
   - API: `POST /v1/scanner/devices/register`를 `POST /v1/scanner/shift`(근무 준비, 응답에 서버 시각·입장 정책·기기 배치·목록 일련번호)로 바꾼다. 배치는 `PUT /v1/scanner/events/{eventId}/devices/{deviceId}/placement`(책임자)와 `PUT /v1/partner/events/{eventId}/devices/{deviceId}/placement`(파트너)다.
6. **목록·변경분 규격을 정하고 다른 스캐너의 입장 기록을 공유한다(D2 소유자 승인, 틀린 전제 ①·③).**
   - 전체 목록 `GET /v1/scanner/events/{eventId}/package`: 회차 정보(입장 정책, 구역 목록, 서버 시각), 티켓마다 {티켓 ID, 구역, 좌석 표시, 상태, 유효 키(keyId, 공개키), 입장 상태(마지막 방향·시각·기기)}, 폐기된 keyId 목록, 마지막 변경 일련번호. 압축 JSON으로 시작하고 5만 장 기준 크기를 PoC에서 잰다(목표 5MB 이하 [가정, wbs 5.4.4에서 확정]).
   - 변경분 `GET /v1/scanner/events/{eventId}/changes?after={seq}`: 회차별 변경 기록(ticket DB `scanner_change`, 서버가 매기는 일련번호)에서 그다음부터 준다. 종류는 키 등록·폐기, 티켓 상태, 다른 스캐너의 입장 상태, 입장 정책, 기기 배치, 이상 표시, 그 기기 세션의 종료다. 시각 대신 일련번호를 쓰므로 커밋 순서가 어긋나도 변경이 빠지지 않는다.
   - 주기: 스캐너 화면이 켜져 있는 동안 앱 타이머로 60초마다, 네트워크가 돌아오면 바로 받는다. 주기적 백그라운드 동기화는 쓰지 않는다. 업로드는 판정 뒤 앱이 5초 [가정] 묶음으로 바로 보내고, 일회성 Background Sync는 예비다. 크롬은 3번 시도한 뒤 포기하므로 화면이 다시 켜지면 앱이 다시 보낸다.
   - 현장 판정은 입장 상태를 쓴다. 재입장 불허 회차는 그 기기나 변경분에 입장 기록이 있으면 '이미 입장한 티켓'(빨강, 시각·구역 표시)으로 거부한다. 재입장 허용 회차는 마지막 방향이 IN이면 '퇴장 기록 없음'(노랑)이다. 다른 스캐너의 기록은 그 스캐너가 올리고 이 스캐너가 변경분을 받은 뒤에만 안다(둘 다 온라인이면 약 1~2분 [가정]).
   - 버전 벡터는 두 칸으로 정한다: (`knownSeq` 이 기기가 판정 때 반영한 서버 변경 일련번호, `deviceSeq` 이 기기의 일련번호). 모든 스캐너가 서버 하나와만 동기화하므로 이 두 값으로 '판정 때 다른 기록을 알았는가'를 정할 수 있다.
7. **QR 규격에 형식 버전과 키 식별자를 넣고, 키 증명은 PoC 뒤 정한다(D4 소유자 승인).**
   - QR v1: 형식 버전(1바이트) ‖ 티켓 ID(16) ‖ keyId(8, 공개키 SPKI의 SHA-256 앞 8바이트) ‖ 시각(4, 초) ‖ 서명(64, IEEE P1363). 서명 대상은 `"PEAKET-QR-v1" ‖ 티켓 ID ‖ keyId ‖ 시각`이다. 약 93바이트다.
   - keyId가 있으므로 스캐너가 '폐기된 키'(양도·취소·재발급된 옛 QR)와 '위조'를 나눠 보인다. 형식 버전으로 뒤에 규격을 바꿀 수 있다.
   - 키 증명(선택): 서버가 {티켓 ID, keyId, 공개키, 유효 끝}에 서명한 값(약 110바이트 [가정])을 QR에 붙이면, 변경분을 아직 못 받은 오프라인 스캐너도 입장 직전에 등록된 키를 검증할 수 있다. QR이 약 두 배로 촘촘해지므로 wbs 5.1.3 PoC에서 인식 시간과 실패율을 재고 채택을 정한다. 채택하면 '키 증명 서명 키'를 키 목록에 넣는다.
   - 키 증명이 없을 때 오프라인 스캐너가 모르는 키는 '키 미반영'으로 거부하고, 관객을 부스나 책임자 예외 통과로 안내한다.
8. **서버의 입장 판정 규칙을 표로 정한다(틀린 전제 ③, 추천 적용).**

   | 상황 | 판정 |
   | --- | --- |
   | 재입장 불허 회차에서 같은 티켓의 통과 기록이 둘 이상 | 보정 시각이 가장 이른 입장만 정상, 나머지는 '중복 입장' 이상 표시. 나중 기록의 `knownSeq`가 앞 기록이 변경 기록에 실린 일련번호보다 작으면 '몰랐음(동시)', 크거나 같으면 '알고도 통과'(책임자 예외 통과가 아니면 앱 오류·남용 의심) |
   | 재입장 허용 회차 | 보정 시각 순으로 IN·OUT이 번갈아야 정상. IN 다음 IN은 '퇴장 기록 없음' 이상 표시 |
   | 취소 접수(입장 시작 뒤 취소) 뒤의 입장 | '취소 뒤 입장' 이상 표시(POL-032) |
   | 기록 시각이 그 세션의 유효 구간 밖 | '세션 밖 기록' 이상 표시. 버리지 않는다 |
   | 입장 기록 마감 뒤 도착 | 받고 '마감 뒤 도착' 이상 표시 |
   | 책임자 예외 통과 | 정상으로 받고 사후 검토 목록에 올린다 |
   | 기기 시계가 마지막 보정 뒤 ±2분 [가정] 넘게 어긋남 | '시각 불확실' 표시. 순서 판정은 `deviceSeq`를 함께 본다 |

   - 보정 시각은 기기 시계에 마지막으로 잰 서버 오차를 더한 값이다.
   - '동기화 뒤 중복 입장 탐지율 100%'(NFR-025, K10)는 두 기록이 모두 서버에 올라온 경우의 목표다. 올라오지 않은 기록(분실·고장 기기)은 찾지 못한다.
9. **남은 기록은 기기 인증으로 올린다(운영 공백).**
   - `POST /v1/scanner/scans`는 기기 인증(mTLS, 대안 B는 DPoP)만 요구하고 스태프 토큰은 선택이다. 기록마다 `scannerSessionId`가 있어 서버가 '그 시각에 유효한 세션이었는가'를 본다(결정 8).
   - 로그아웃·교대·해제·만료 뒤에도 큐는 올라간다. 온라인이면 앱은 로그아웃 전에 큐를 비운다.
   - 폐기된 기기는 TLS에서 막혀 올리지 못한다. 회수한 기기는 재등록 뒤 남은 기록을 올리고, 폐기 시각 뒤 기록은 '세션 밖 기록'으로 표시한다.
   - I-T24의 '후속 업로드 차단'은 '새 스캔 차단, 남은 기록은 받고 해제 뒤 시각의 기록은 표시'로 고친다.
10. **입장 중에는 소유권과 키를 바꾸지 않는다(D3 소유자 승인, 보안 결함 ③).**
    - 입장 시작(`event.entry_opens_at`)부터 입장 기록 마감(결정 13)까지 돌려주기·양도 수락·양도 회수를 막는다(409 `ENTRY_STARTED`). 양도 요청 마감은 '공연 시작 2시간 전과 입장 시작 중 이른 때'다.
    - 첫 키 등록(ISSUE)은 입장 시작 뒤에도 허용한다. 대신 소셜 제공자 재인증을 받고 계정 이메일로 알린다. 판매자가 월렛을 한 번도 열지 않고 계정을 넘긴 경우 부스 확인을 거치지 않는 한계가 남는다. 입장 시작 뒤 첫 등록 비율을 지표로 본다.
    - 입장용 휴대폰 등록: 월렛은 티켓을 처음 열 때 키를 몰래 만들지 않는다. '이 휴대폰을 입장용으로 등록' 버튼을 눌러야 만든다. 데스크톱 브라우저로 보이면 휴대폰에서 등록하라고 먼저 안내한다(PC로 예매하고 당일 휴대폰으로 처음 열면 재발급으로 처리되는 함정을 줄인다). iOS는 홈 화면에 추가한 앱에서 등록하라고 안내한다. Safari와 홈 화면 앱이 저장소를 따로 쓰는지는 [가정, wbs 5.1.3 PoC에서 확인]이다. 입장 시작 24시간 전까지 등록이 없으면 안내를 보낸다.
    - 로그아웃해도 입장 키는 지우지 않는 것이 기본이다. 지우면 다시 등록해야 하고 재발급 한도(ADR-0050)에 걸리기 때문이다. 공용 기기라면 로그아웃 화면에서 '이 기기의 입장 키 지우기'를 고른다.
11. **현장 예외 절차를 정한다(D5 소유자 승인).**
    - 부스 재발급(ADR-0050 결정 2의 절차):
      1. 관객이 자기 휴대폰 월렛에서 '부스 재발급'을 누르고, 본인확인 결과를 계정 기록과 대조하는 목적에 따로 동의하면(정보통신망법 §23의5④ 단서) 휴대폰 본인확인 창이 열린다.
      2. 결과 연계정보 해시(`ci_hmac`)가 보유 계정의 값과 같으면 부스 코드(확인 코드와 같은 8자, 10분)가 QR과 글자로 나온다. 다르면 409로 거부한다. 연계정보 원문은 지금처럼 바로 버린다.
      3. 책임자가 스캐너 '현장 관리'(SCR-052)에서 그 QR을 찍으면 그 티켓의 BOOTH 등록을 10분 허용한다.
      4. 월렛이 새 키를 등록한다(reason=`BOOTH`). 스캐너에는 변경분으로 반영되고, 급하면 책임자가 예외 통과시킨다.
      - 이름을 화면에 보이지 않고, 양도받은 사람에게도 된다. 본인확인 비용이 부스 건수만큼 든다. 대조 목적은 따로 동의받으므로 기존 수집 목적에 들어가는지를 해석하지 않는다.
      - 부스에는 안정된 회선(유선이나 전용 무선)을 두고, 관객 휴대폰이 그 회선을 쓸 수 있게 한다 [운영 권고].
    - 부스 통신이 끊기면 본인확인을 할 수 없다. 책임자 판단으로 예외 통과시키고 사후 검토 목록에 올린다(남는 한계).
    - 예외 통과(OVERRIDE): '티켓 번호 16자리 수동 입력'을 없앤다. 책임자가 좌석 표시(관객 월렛 화면이나 예매 확인)로 기기 안 목록에서 티켓을 찾고, 사유(카메라 고장, 휴대폰 방전, 키 미반영, 기타)와 짧은 메모(100자, 개인정보 금지)를 남겨 통과시킨다. 모든 예외 통과는 CS 처리함의 사후 검토 대상이다.
    - 일반 스태프 기기의 카메라가 고장 나면 예비 기기로 바꾸거나 책임자를 부른다. 일반 스태프에게는 수동 입력 화면이 없다.
    - 확인 스캔(VERIFY): 책임자 스캐너에서 판정만 하고 입장 기록을 남기지 않는 모드다. 좌석 확인(결정 12)에 쓴다.
12. **이상 표시는 현장 책임자와 파트너에게 보낸다(D6 소유자 승인).**
    - 서버가 이상 표시를 만들면 변경분에 실어 그 구역 책임자의 스캐너(SCR-052)에 보이고, 파트너 콘솔 '현장 운영' 탭에 10초 [가정] 안에 보인다. 관제(SCR-029 입장 탭)는 감시만 한다. 같은 회차의 중복 입장이 10분에 10건 [가정]을 넘으면 관제에 SEV3 OpsAlert를 띄운다.
    - 현장 확인: 책임자가 좌석으로 가서 확인 스캔으로 지금 QR이 유효한지 보고, 월렛 화면의 계정 닉네임을 확인한다. 결과를 '정상 확인', '부정 의심', '판단 불가' 중 하나로 기록한다. 퇴장 조치는 파트너의 현장 규정을 따르고 PEAKET은 기록만 남긴다. 키가 복제되거나 QR이 실시간 중계되면 두 사람 모두 유효한 QR을 낼 수 있어 확인 스캔만으로는 가리지 못한다(남는 한계).
    - 티켓 상태도: Flagged에서 ScannedIn(정상 확인, 또는 취소 무효 확정)이나 Refunded(기록 오류로 취소가 유효)로 간다. '부정 의심'과 '판단 불가'는 CS 처리함에서 끝낸다.
    - 지정석이 아닌 구역(스탠딩·정리번호 입장)은 지금 범위 밖이라 좌석 확인 절차가 없다.
13. **입장 기록 마감을 정한다(운영 공백, 추천 적용).**
    - `event.ends_at`(공연 종료 예정 시각, 파트너 필수 입력)을 둔다. 역할 유효 끝은 `ends_at` + 2시간이다.
    - 마감 시각(`event.entry_closed_at`): 역할 유효 끝에 그 회차에 로그인했던 모든 기기가 큐를 비웠다고 보고했으면 바로 마감한다. 아니면 그 뒤 모두 보고하는 때와 24시간 [가정] 지난 때 중 이른 때 마감한다.
    - 마감 뒤 입장 기록이 없는 '취소 접수' 티켓은 환급하고, 기록이 있으면 이상 표시로 CS 처리함에 보낸다. 보고하지 않은 기기는 CS 처리함 '미보고 스캐너'로 올린다.
14. **공연 당일 화면, 스캐너 대수, 타임라인을 정한다(추천 적용).**
    - 관제 SCR-029에 '입장' 탭을 더한다: 로그인·준비 기기 수, 마지막 동기화 경과 최대값과 2분 넘은 기기 수(ADR-0049), 구역별 분당 입장 수, 거부 사유별 비율, 이상 표시 수, 부스·예외 통과 건수, 업로드 대기 건수, 마감 상태.
    - 파트너 콘솔 SCR-037에 '현장 운영' 탭을 더한다: 기기 배치, 준비 상태, 구역별 입장 수, 이상 표시 목록(개인정보 없음), 스태프별 스캔·예외 통과 건수.
    - 스캐너 대수 산정: 필요 대수 = 가장 붐비는 구간의 도착률(명/분) ÷ 1대 처리량(명/분) × 1.2 [가정]. 1대 처리량은 Phase 5 현장 시험(wbs 5.7.1)에서 잰다. 예: 5만 명 중 절반이 마지막 30분에 오면 분당 약 830명이고, 1명에 3~4초면 1대가 분당 15~20명이라 42~56대에 예비가 필요하다(측정 전 예시).
    - planning/04 F-04의 '초당 5,000명'은 대기열의 동시 입장 목표와 섞인 오기라 지운다.
    - 공연 당일 타임라인(offline-gate §0)을 둔다.

## 대안

| 대안 | 판단 |

| 종료 세션 목록 보관을 역할 유효 끝까지 늘림 | 기각. 파드가 다시 뜨면 목록이 사라지고 Kafka 재생 범위가 수 시간으로 늘어난다. 스캐너 요청은 적어 요청마다 확인해도 된다 |

## 결과

### 얻는 것

- 스태프 해제가 다음 요청부터 반영되고, 대리 승인이 권한을 올리지 않는다.
- 입장 시간대에는 소유권과 키가 바뀌지 않아 '들어간 뒤 돌려주기'로 두 명이 들어가는 길이 닫힌다.
- 온라인 스캐너는 다른 스캐너의 입장을 1~2분 안에 알아 두 번째 입장을 현장에서 거부한다. 서버는 표 하나로 중복·재입장·취소 뒤 입장을 판정한다.
- 초대부터 마감까지 단계마다 화면·API·데이터·테스트가 있다.

### 대가

- 데이터: `scanner_device`, `scanner_placement`, `scanner_change`, `gate_flag`, `booth_authorization` 엔티티. `scan_event`에 판정·사유·방식·구역·세션·keyId·`knownSeq`·`deviceSeq`·수신 시각. `event`에 `ends_at`·`entry_closed_at`. `staff_assignment`에 초대 토큰 해시·만료·EXPIRED. `scanner_session`에 역할·대리 표시·마지막 연락. `device_key`에 `key_id`.
- API: 운영자 기기 관리 3개, 스캐너 근무 준비·목록·변경분·배치·이상 표시·부스 허용, 파트너 배치·현장 운영, 초대 조회·여러 명 초대·재발송, 승인 배정 선택, 부스 요청과 본인확인 재확인.
- 화면: SCR-050(초대 수락), SCR-051(스캐너 승인), SCR-052(현장 관리), SCR-053(스캐너 기기 관리), SCR-029 입장 탭, SCR-037 현장 운영 탭.
- 보안 추적표 docs/security/asvs/offline-gate.md를 새로 쓴다(L1·L2 151개, L3 4개, 법률 6개).
- WBS가 10일 늘었다. 5.4.3 기기 등록·폐기와 인증서 PoC(2), 5.4.4 목록·변경분·서버 판정·마감(2), 5.4.5 현장 관리·예외 절차(2), 5.5.3 휴대폰 화면·수락 조건(1.5), 5.1.3 입장용 휴대폰 등록·QR v1·키 증명 PoC(1), 5.7.2 공연 당일 관제·파트너 현장 운영(1.5).
- 운영: 관리 앱(기기 관리) 계약, 부스 회선, 예비 기기, 본인확인 비용.

### 남는 한계

- 오프라인 스캐너는 마지막 변경분 뒤의 양도·취소·새 키·다른 스캐너 입장을 모른다. 그동안 옛 QR이 통하고 새 키는 거부된다(키 증명을 채택하면 새 키 거부는 줄어든다).
- 분실·고장 기기의 올라오지 않은 기록은 잃는다. 그 기록 속의 중복 입장과 취소 뒤 입장은 찾지 못한다.
- 해제된 스태프는 오프라인 스캐너에서 역할 유효 끝까지 쓸 수 있다(ADR-0030). 그 기록은 올라오면 '세션 밖 기록'으로 표시된다.
- 판매자가 월렛을 열지 않은 채 계정을 넘기면 산 사람의 첫 등록은 부스를 거치지 않는다.
- 부스 통신이 끊기면 본인 확인 없이 책임자 판단으로 들여보낸다.
- 키 복제와 실시간 중계는 현장 확인 스캔으로도 가리지 못한다(ADR-0050 결정 1).
- 기기 배치는 온라인에서만 바꾼다.
- 대안 B로 가면 스캐너 기기 키도 소프트웨어 키다.

### 되돌릴 조건

- 인증서 PoC(wbs 5.4.3)에서 네 항목 중 하나라도 실패하면 대안 B로 바꾸고 ADR을 남긴다.
- 입장 시작 뒤 첫 키 등록이 회차 관람객의 5% [가정]를 넘거나 계정 넘기기 재판매가 적발 기록에 나타나면 첫 등록 규칙을 다시 정한다.
- 온라인 상태에서 중복 입장 이상 표시가 회차당 10건 [가정]을 넘으면 변경분 주기(60초)를 줄인다.
- 마감을 24시간 기다리는 회차가 분기에 두 번을 넘으면 미보고 기기 처리 절차를 다시 본다.
