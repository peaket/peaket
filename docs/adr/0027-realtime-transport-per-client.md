# ADR-0027: 클라이언트 유스케이스별 실시간 전송 프로토콜 최적 분리 채택

- **상태**: 채택 (2026-10-05 설계서 24장에 최초 수립, 2026-10-08 아키텍처 결정 레코드(ADR)로 공식 이관) 2026-10-21(ADR-0079): 세 채널의 인증·하트비트·닫힘 코드·이벤트 형식 초안을 정했다. 좌석은 하위 프로토콜 인증, 파트너 SSE는 메시지마다 전체 상태, 관제 명령은 REST이고 Socket.IO는 ack·경보만 맡는다(docs/frontend.md §4.4). 2026-10-26(4차 점검 3부): 결정 표 Webhook 행의 수신에는 포트원 결제 웹훅(Standard Webhooks 서명 검증)이 더해졌다(ADR-0029, docs/features/payment.md §5). 2026-10-28(ADR-0100, 소유자 승인 '추천안 동의'): 결정 표의 Socket.IO(관제 콘솔) 행을 SSE로 바꾼다. 관제는 늘 여는 흐름(명령 상태·승인 대기·경보·자동 제어·접속자)과 위젯 흐름 둘을 SSE로 받고, 명령·조회는 REST다. 방·접속자는 흐름 주소와 ops DB 표로, 다시 붙기는 `Last-Event-ID`로 한다. Redis adapter는 쓰지 않는다(docs/frontend.md §4.4). 2026-10-28(기술 검토 낮음-024, 소유자 승인 '추천안 동의'): 파트너 실시간 현황의 SSE를 1분 주기 REST 조회(`GET /v1/partner/events/{eventId}/live-snapshot`, 응답의 다음 집계 시각에 맞춰 묻고 숨긴 탭은 5분 [가정])로 바꾼다. 값이 1분마다 바뀌는 전체 상태라 조회로 같은 신선도를 얻고, 열린 연결·게이트웨이 시간 초과 끄기·`Last-Event-ID` 복구가 필요 없어서다. 1분보다 짧은 지연을 약속하게 되면 SSE를 다시 견준다(docs/frontend.md §4.4.3, 세부는 추천 적용).
- **관련 문서**: 설계서 24장(실시간 통신 아키텍처), §6(실시간 좌석 전파·관제·파트너 판매 현황), ADR-0003(대기실 CDN 폴링)
- **관련 ID**: FR-007, FR-009, FR-011, FR-026, FR-029, NFR-002, NFR-004, NFR-009

## 맥락
- 티켓 예매 시스템의 실시간 통신 환경은 사용자 규모와 데이터 특성이 극단적으로 갈린다.
- 100만 명의 대기열 동시 접속자, 5,000명의 좌석맵 동시 선택자(양방향 바이너리 통신), 수십 명 규모의 관제 콘솔(룸 기반 브로드캐스트·ack·presence), 수백 명의 파트너(단방향 판매 현황 스트림), 그리고 수 초간 상태 변화 1회만 받는 결제 결과 대기 창구는 각각 네트워크 비용과 신뢰성 요구가 다르다.
- 모든 화면에 단일한 WebSocket이나 SSE를 획일적으로 적용하면, 대규모 연결 유지 비용으로 인프라가 붕괴하거나 불필요한 구현 복잡도가 생긴다.

## 결정
클라이언트의 접속 규모, 통신 방향성, 전송 빈도에 따라 전송 방식을 분리 채택한다.

| 기술 | 사용처 | 이유 |
| --- | --- | --- |
| Polling(CDN 캐시) | 대기실 상태 조회(100만 명) | 100만 명에게 같은 데이터를 주는 데는 1초 TTL의 CDN 캐시 폴링이 연결 유지보다 싸고 단순하며 오리진 요청을 99% 이상 흡수한다(ADR-0003). Cloudflare·AWS 레퍼런스도 같은 방식 |
| WebSocket(ws) | 좌석 홀드·해제 델타(동시 5,000명) | 양방향(섹션 구독·해제), 바이너리 프레임, 최소 오버헤드 |
| Socket.IO | 관제 콘솔(수십 명) | 룸(공연별), ack(명령 수신 확인), presence, 자동 재연결. 운영자는 수십 명이라 기능이 원시 성능보다 중요. Redis adapter로 멀티 파드 |
| SSE | 파트너 실시간 판매 현황(수백 명) | 단방향 집계 스트림. 자동 재연결 + `Last-Event-ID`, HTTP/2 필수(HTTP/1.1은 브라우저·도메인당 연결 6개 제한, MDN) |
| Long polling | 결제 결과 대기 | 승인 결과가 확정될 때까지 수 초간 상태 변화 1회만. 인프라가 가장 단순 |
| Webhook | 토스 수신, 파트너 발송 | 외부 시스템과의 비동기 계약. 발송은 HMAC 서명, 지수 백오프, DLQ, SSRF 방지 |

## 검토한 대안
| 대안 | 기각 사유 및 한계점 |
| --- | --- |
| 100만 대기열에 SSE/WebSocket 지속 연결 | 동시 100만 소켓 연결 유지에 게이트웨이 파드와 메모리가 낭비되고, 네트워크 단절 시 대량 재연결 폭풍으로 오리진이 마비된다(ADR-0003). |
| 관제 콘솔에 순수 WebSocket 직접 구현 | 파드 간 브로드캐스트, 룸 격리, ack, presence를 직접 구현해야 한다. |

## 결과와 트레이드오프
- 각 화면에 맞는 통신 모델을 채택하여 인프라 비용을 줄이고 화면별 지연을 낮춘다.
- 대가: 전송 방식이 다섯이라 클라이언트 SDK(`TransportFactory`)와 테스트(MSW WebSocket 모킹)가 늘어난다.
