# ADR-0176: 기반 PoC 판정(wbs 0.5.1) — Redis 한 키는 묶음 없이 `INCR`, Redis 클라이언트는 판정 보류(추천 node-redis), 좌석 샤드는 정본대로 큰 회차 배치 규칙을 두고 만료는 한 번에 100석, HTTP는 Fastify에 좌석 홀드는 경로 스키마·대기열 진입은 Zod 파이프, Kafka는 Confluent 클라이언트 확정

- **상태**: 채택(2026-11-01, 추천 적용. 판정 기준은 정본에 있던 것이고, 정본에 숫자가 없던 기준만 아래에 '추천 적용'으로 적었다). 결정 1은 ADR-0179가 바꿨다(2026-11-03, 진입 Lua로 다시 잰 값이 기준을 넘어 파드별 묶음). 2026-11-03(해설서 대조, R-255): 결정 2의 '판정 보류'는 소유자가 2026-11-02 PROGRESS OPEN[11]을 추천안대로 닫아 node-redis로 확정했으니(핫패스 연결에 호출 쪽 마감 100ms와 연결 오류 재시도 1회를 더함, PRF-050) node-redis로 읽는다
- **관련**: NFR-001, NFR-003, NFR-005, NFR-021, V-T33, V-T41, S-T27, ST-T14, ST-T18, wbs 0.5.1, BUILD_ORDER FND-120, openspec 변경 `add-foundation-poc`, [docs/architecture.md](../architecture.md) §5·§9.4, [docs/verification.md](../verification.md) §3.3·§3.5, [docs/streaming.md](../streaming.md) §2.1·§2.6, [docs/devops.md](../devops.md) §4.4, [docs/perf-ledger.md](../perf-ledger.md) §4, ADR-0023, ADR-0054 결정 19, ADR-0096, ADR-0127, ADR-0128, ADR-0133, ADR-0134, ADR-0137, ADR-0142, 기술 검토 중간-026·낮음-001·낮음-003·낮음-004·낮음-072·낮음-152·높음-26

## 맥락

- docs/architecture.md §9.4는 본 개발 전에 위험한 부분을 PoC로 먼저 재고, 정해 둔 공식 판정 기준으로 고르라고 한다. 이 ADR은 그 가운데 wbs 0.5.1의 몫을 잰 결과와 판정이다.
- 측정은 PC 한 대에서 했다(Intel Core i9-14900HX, 논리 프로세서 32개, Docker Desktop 29.8.1·WSL2 커널 6.18, 2026-11-01). kind 클러스터 대신 같은 Docker 망 안의 컨테이너로 측정 대상과 측정 도구를 띄우고 컨테이너마다 CPU 한도를 두었다(성능 장부 프로파일 `local-poc`, docs/perf-ledger.md §4). 숫자는 모두 '실측(PC)'이고, 원본은 성능 장부 `docs/perf-ledger/runs/2026-11-01-*-local-poc/`에 있다. 측정 틀은 `loadtest/poc/`(README에 규칙)다.
- 측정 규칙: 정해진 도착률로 보내고 지연을 '보내기로 한 시각'부터 잰다(오픈 모델). 보내지 못한 요청이 하나라도 있으면 무효다. 예열 구간은 뺀다. Redis 측정은 TLS를 켠 상태로 3회, 끈 상태로 1회 잰다(판정은 켠 값, docs/verification.md §3.5 7번). 표의 '중앙값'은 TLS 켬 3회의 가운데 값이다.

## 결정

### 1. Redis 한 키 `INCR` 20만/s: 묶음 없이 직접 `INCR`한다(NFR-001, §9.4 판정 기준)

| 방식(TLS 켬, 3회) | p99 | p99.9 | 오류·못 보낸 요청 | 엔진 스레드 CPU |
| --- | --- | --- | --- | --- |
| 직접 `INCR` | 19.7·50.3·42.9ms(중앙값 42.9ms) | 35.2~107.2ms | 0·0 | 30~42% |
| 파드별 `INCRBY` 2ms 묶음 | 4.2·4.1·4.1ms(중앙값 4.1ms) | 4.8~5.7ms | 0·0 | 12~14% |

- 진입 서버 넷을 프로세스 넷으로 흉내 내 초당 5만 건씩 보냈다(node-redis 6.3.0, 자동 파이프라이닝). 기준은 '묶음 없이도 20만 RPS에서 p99 200ms 이내면 묶음 없는 단순 구조'다. 직접 `INCR`이 세 번 모두 그 안이라 묶음을 쓰지 않는다. 묶음은 지연과 엔진 CPU를 더 줄이지만, 진입 서버가 죽으면 받은 범위가 비고(번호 건너뜀) 묶음 창만큼 진입 순서가 섞이는 대가가 있어, 기준을 넘을 때만 쓴다(docs/infra.md, docs/features/queue-admission.md §3).
- TLS 끔 짝(1회): 직접 p99 22.2ms·엔진 CPU 28%, 묶음 p99 4.4ms·14%.
- 직접 `INCR`의 꼬리 지연은 엔진이 아니라 발생기 쪽이다: 엔진이 잰 `INCR` p99는 1µs이고, 발생기 프로세스(초당 5만 건씩)의 CPU가 56~80%였다. 진입 서버 한 대가 내는 양이 적으면 꼬리도 준다.
- 한 키 최대 처리량 R(진입 용량 식의 상한, docs/verification.md §3.3): 진입 서버 여섯을 프로세스 여섯(동시 512씩, 닫힌 모델)으로 흉내 내 TLS 켬 3회 초당 49만 800·49만 7,800·49만 7,500건, 끔 56만 400건이었다. 엔진 스레드 CPU가 61%(끔 54%)라 엔진보다 발생기가 먼저 찼으므로 R은 '적어도 초당 49만 건'이다(실측(PC)). 20만 RPS 목표의 2.4배가 넘는다.
- 한계: 운영 진입은 순수 `INCR`이 아니라 진입 Lua 안의 `INCR`이다(로비 셔플 표시를 함께 본다, queue-admission §3). 진입 Lua가 생기면(wbs 2.2.1) 같은 도구로 다시 잰다.

### 2. Redis 클라이언트(V-T33): 판정 보류 — 셋 모두 기준을 다 채우지 못했다(PROGRESS 미해결 OPEN[11], 추천은 node-redis)

같은 Valkey 8.1.11 클러스터(주 노드 셋·복제 셋, TLS)에 node-redis 6.3.0·ioredis 6.0.0·Valkey GLIDE 2.5.3을 같은 핫패스 설정(명령 시간 초과 100ms, 연결이 끊긴 동안 쌓지 않음, ioredis는 재시도 1회)으로 붙였다. ①은 프로세스 하나·CPU 1개, ②~⑤는 클라이언트마다 3회(클러스터를 매번 새로 만듦)다.

| 보는 것 | node-redis | ioredis | GLIDE |
| --- | --- | --- | --- |
| ① 자동 파이프라이닝 최대 처리량(닫힌 모델, TLS 켬 3회 중앙값·범위 / 끔) | 95,000/s(69,600~104,300) / 120,400/s | 166,000/s(126,700~186,700) / 174,800/s | 74,100/s(71,400~76,600) / 69,300/s |
| ① `INCR` 4만/s p99(TLS 켬 중앙값)·발생기 CPU | 25.3ms·52~63% | 3.1ms·31~32% | 10.3ms·63~70%. 동시 요청 상한(기본 1,000)에 걸린 거절 1,328~10,668건 |
| ① 홀드 Lua 5천/s p99(TLS 켬 중앙값) | 3.4ms | 2.8ms | 2.7ms |

| ④ 샤드 구독 중 슬롯 옮기기 | 옮긴 뒤 471~472건 모두 받음 | 모두 받음 | 470~473건 중 348~349건만 받음 |

| ⑤ 마감에 걸린 명령이 나중에 서버에 닿음(망 떼기) | — | 29건 | 29건 |
| 유지 상태(npm 2026-11-01) | 12개월 정식 11·사전 2, 최신 6.3.1(2026-10-29) | 정식 10·사전 3, README가 '최선의 노력으로만 유지, 새 프로젝트는 node-redis 권장' | 정식 16·사전 25, AWS·GCP 지원. Windows 실행 파일 없음 |
| ⑦ OTel 자동 계측 | `@opentelemetry/instrumentation-redis` 0.72.0이 `@redis/client` ^6을 계측한다(코드, README는 판 표기가 엇갈림). 자체 `diagnostics_channel` 추적 채널도 있다 | `@opentelemetry/instrumentation-ioredis` 0.72.0(<7) | 내장 OTel(2.0부터, 자체 내보내기, 기본 표본 1%) |

- 정본 판정 규칙(docs/architecture.md §9.4, docs/verification.md V-T33)은 'node-redis가 ②~⑤에서 ioredis와 같고 ①이 ±10% 안이면 node-redis로 확정, 다르면 다른 쪽이나 GLIDE를 새 ADR로'다. node-redis는 ①에서 ioredis보다 43% 적고(±10% 밖), ⑤의 '응답 없이 사라진 노드'에서 100ms에 실패하지 않는다. 그런데 ioredis는 ②(슬롯 옮기기 때 `ASK`를 그대로 돌려줌)와 ⑤(주 노드가 죽으면 11초 매달림)에서, GLIDE는 ②와 ④(옮긴 뒤 샤드 구독 사건의 약 26%를 잃음)와 ①(가장 적음)에서 node-redis보다 나쁘다. 셋 모두 규칙을 다 채우지 못해, 어느 쪽을 고를지는 정본에 없다. 그래서 고르지 않고 소유자에게 묻는다(OPEN[11]).
- **추천: node-redis로 확정하고 핫패스 연결에 두 가지를 더한다.** ① 호출 쪽 마감 100ms(명령 시간 초과는 소켓에 쓰기 전까지만 듣는다. 마감에 걸린 명령도 나중에 서버에 닿으면 실행되는 것은 ioredis·GLIDE와 같다) ② 연결이 끊겨 거절된 명령('Disconnects client' 같은 연결 오류)의 재시도 1회(정본의 '핫패스 재시도 1회', §5. 홀드는 멱등 키가 같아 두 번 잡지 않고, 진입 `INCR`은 번호 하나가 빌 뿐이다). 까닭: 슬롯 옮기기·장애 조치·샤드 구독은 좌석 홀드와 좌석 전파의 정확성에 바로 닿고(오류는 503, 구독 손실은 화면이 다음 스냅샷까지 틀림), ioredis의 11초 매달림은 좌석 장애 조치 동안 빨리 실패해 503으로 답하려는 설계(§5, ADR-0121)와 맞지 않는다. 처리량 차이는 파드 CPU 비용이다: 진입 서버 하나가 초당 2만 건을 보내면 node-redis는 CPU 약 0.2개, ioredis는 약 0.12개를 Redis 클라이언트에 쓴다(①의 처리량에서 계산). 다른 길: ioredis로 가고 ②·⑤를 감싸는 코드(`ASK`·`MOVED` 다시 보내기, 장애 조치 때 연결 끊기)를 플랫폼에 둔다(유지가 줄어드는 판에 우리 고침을 얹는다). GLIDE는 ④를 고칠 수 없어 권하지 않는다.
- **이 판정과 상관없이 정본을 고친 것**: node-redis 클러스터 연결의 명령 시간 초과는 `createCluster({ commandOptions: { timeout } })` 맨 위에 둔다. `defaults` 안에 두면 클러스터가 명령마다 넘기는 기본 5초에 덮인다(@redis/client 6.3.0 `cluster/index.js`). GLIDE를 쓰면 `inflightRequestsLimit`(기본 1,000)을 피크 동시 요청에 맞춰 올려야 한다.
- 측정의 한계: ①은 발생기 프로세스 하나의 CPU가 다 찬 값이라 클라이언트 쪽 비용을 잰 것이다(엔진 CPU는 11~17%). TLS를 끄면 node-redis만 27% 늘었다. ②의 오류 수는 그 슬롯에 초당 5천 건을 보낸 값이다. ①의 p99는 '보내기로 한 시각'부터 재어 발생기의 1ms 박자 기다림(0~1ms 남짓)을 포함하고 세 클라이언트에 똑같이 들어간다(이 측정 뒤 도구가 '실제로 보낸 시각' 기준 지연도 함께 남기게 고쳤다, 코드 리뷰 2026-11-01). 그래서 1ms 아래 차이를 가리는 데는 쓰지 않는다.

### 3. 좌석 샤드 하나의 처리량(S-T27): 샤드 하나가 6,000/s를 견디지만 SLOWLOG 기준을 넘었다 — 정본대로 큰 회차 배치 규칙을 두고, 만료 작업은 한 번에 100석으로 한다

회차 키를 한 주 노드(CPU 2개)에 몰고 PoC 홀드 Lua(1~4석, 절반은 앞 10% 구역에 몰아 경합)를 정해진 도착률로 10분씩 넣었다. 같은 때 스냅샷 읽기(큰 회차 1,000/s, 중형 500/s), 1초 만료 작업, 성공한 홀드마다 샤드 Pub/Sub 발행을 돌렸다. 홀드가 끝없이 쌓이지 않게 TTL을 큰 회차 5초·중형 3초로 줄여 빈 좌석이 반쯤 남게 했다. 만료 작업은 Lua 한 번에 좌석을 최대 500석 또는 100석 푼다(seat-hold §5의 `LIMIT n`, 정본에 값이 없어 [가정]).

| 경우(TLS 켬) | 홀드 Lua p99(엔진) | 샤드 엔진 CPU | 홀드 p99(클라이언트, Redis 몫) | SLOWLOG(10ms) | 오버셀 |
| --- | --- | --- | --- | --- | --- |
| ① 한 회차 2,000/s, 만료 500석, 3회 | 85.5·64.3·83.5µs | 16~18% | 3.3~3.9ms | 1·0·0(만료 Lua 10.9ms) | 0 |
| ① 한 회차 2,000/s, 만료 100석, 1회 | 99.3µs | 21% | 2.7ms | 1(만료 Lua 10.2ms) | 0 |
| ② 다섯 회차 합 6,000/s 한 샤드, 만료 100석, 3회 | 75.3·68.1·72.2µs | 36~38% | 5.7ms | 0·0·1(만료 Lua 10.3ms) | 0 |
| ② 다섯 회차를 서로 다른 샤드에(큰 회차 혼자·중형 둘씩), 만료 100석, 1회 | 116·106·97µs(샤드마다) | 22~23% | 6.2ms | 0 | 0 |

- TLS 끔 짝(1회씩, 만료 100석): ① 97.3µs·21%·2.4ms·SLOWLOG 0, ② 70.1µs·35%·5.6ms·SLOWLOG 0.
- 홀드 Lua의 엔진 시간은 호출당 평균 19~28µs이고, 360만 번 넘게 돌았지만 SLOWLOG에 한 번도 남지 않았다. SLOWLOG에 남은 셋은 모두 만료 작업 Lua다(평소 100석에 0.6ms, 500석에 2.3ms, 가끔 10ms 남짓. 원인은 찾지 못했다). 그래서 만료 작업은 한 번에 100석 [가정]으로 둔다(500석이면 평소에도 그만큼 샤드를 막는다).
- 오버셀 검사: 홀드·만료 Lua가 회차마다 같은 순번을 늘려, 좌석마다 잡기·놓기가 번갈아 오는지 서버 실행 순서로 봤다. 끝에 켜진 비트 수 = 만료 인덱스 수다. 모든 유효 측정에서 오버셀 0, 짝이 맞지 않는 놓기 0이다.
- 판정: ①·②의 홀드 Lua p99(0.1ms 이하)·엔진 CPU(50% 이하)·홀드 p99(50ms 이하)·오버셀 0은 모두 지켰다. SLOWLOG 기록 0은 ② 3회 가운데 1회에서 넘었다. 정본은 '②에서 넘으면 큰 회차의 해시 태그 값을 슬롯 배치표로 골라 서로 다른 주 노드에 두고, 판매 승인 때 같은 샤드에 대형·중형이 겹치는지 확인하는 규칙을 새 ADR로 정한다'(§9.4)라서 그 규칙을 이 결정으로 둔다. 실제 슬롯 배치표와 판매 승인 확인은 운영 홀드 Lua와 함께 만든다(BUILD_ORDER PRF-130). 다만 넘은 원인은 샤드 포화가 아니라 만료 Lua의 가끔 10ms이고, 회차 하나만 둔 ①에서도 났으므로 배치 규칙만으로는 사라지지 않는다. 그래서 운영 만료 Lua로 다시 잴 때(PRF-130) SLOWLOG 0을 다시 보고, 남으면 만료 묶음을 더 줄인다.
- 서로 다른 샤드에 나누면 샤드 CPU는 줄었지만 샤드마다 호출당 엔진 시간은 오히려 늘었다(19µs → 30µs). 부하가 낮은 샤드의 PC 잡음(코어 절전 상태 등)으로 보며, 이 숫자로 배치의 이득을 말하지 않는다.
- 무효로 남긴 측정: 다섯 회차 첫 회(만료 500석)는 측정 도구가 오버셀 검사 기록을 좌석마다 자바스크립트 배열로 쌓아 GC가 길게 멈췄고, 모든 요청이 2.1~2.3초까지 늦어 홀드 0.96%가 100ms 마감에 걸렸다(엔진 지연은 정상). 기록을 정수 배열로 고친 뒤 다시 쟀다(성능 장부에 `valid: false`로 남김).
- 한계: PoC 홀드 Lua와 만료 Lua는 운영 스크립트가 아니다. 클라이언트 홀드 p99는 Redis 왕복 몫이고 S-T1(게이트웨이·서비스 포함)이 아니다.
- **후속(2026-11-04)**: 운영 홀드·만료 Lua로 다시 쟀고 기준을 넘어 ADR-0188로 정했다. 큰 회차 배치 규칙을 필수로 하고, 홀드 Lua 실행 시간 기준을 p99 0.1ms에서 0.3ms [가정]로 올렸다.

### 4. 핫패스 HTTP 어댑터와 검사 방식(V-T41): Fastify를 그대로 쓰고, 좌석 홀드는 경로 스키마, 대기열 진입은 Zod 파이프로 검사한다

같은 NestJS 처리기의 좌석 홀드 경로(JSON 본문)와 대기열 진입 경로(`text/plain` 본문)를 세 구성으로 띄웠다(`packages/platform/bench/vt41`, 앱 컨테이너 CPU 1개 고정, k6 1.4.2). 세 구성 모두 플랫폼 서비스 훅(지표·정규 로그 줄·추적·인증·멱등)은 빼고 같은 문제 응답 필터와 같은 가드 자리만 두어, 어댑터와 검사 방식의 몫만 쟀다. 표본 묶음 17개(정상·형식 오류·모르는 칸, `request-checks.test.ts`의 표본에서 머리 검사를 뺀 것)의 받기·거르기 결과와 Problem 400 본문은 세 구성에서 같았다(Express는 본문 해석 오류도 같은 Problem 본문을 내게 맞췄다).

| 구성 | 닫힌 모델 최대 처리량(CPU 1) 홀드·진입 | 그때 요청당 CPU | 오픈 모델 요청당 CPU(홀드 7,600/s·진입 8,000/s, 3회 중앙값) | 오픈 모델 p99 홀드·진입 | 이벤트 루프 지연 p99 |
| --- | --- | --- | --- | --- | --- |
| ① Express + Zod 파이프 | 15,307·16,095/s | 65.1·61.8µs | 104.3·102.7µs | 2.34·2.74ms | 0.58·0.70ms |
| ② Fastify + Zod 파이프 | 18,190·23,808/s | 54.6·41.6µs | 90.2·88.7µs | 1.48·1.66ms | 0.74·0.73ms |
| ③ Fastify + 경로 스키마 | 21,487·24,871/s | 45.9·39.7µs | 83.5·89.0µs | 1.09·1.57ms | 0.79·0.74ms |

- 도착률은 가장 느린 구성 최대 처리량의 50%다. 오픈 모델의 요청당 CPU가 닫힌 모델보다 큰 것은 이벤트 루프 차례마다 처리하는 요청이 적어 차례마다의 고정 비용을 나눠 지는 요청이 적기 때문이다(세 구성에 같다).
- ②는 ①보다 요청당 CPU가 두 경로 모두 약 14% 적고 최대 처리량이 19%·48% 많다. 그래서 ADR-0023(Fastify)을 다시 보지 않는다.
- ③은 ②보다 좌석 홀드에서 요청당 CPU를 7.4% 줄였고(5% [가정]를 넘음), 대기열 진입에서는 줄이지 못했다(+0.3%, 닫힌 모델에서도 −4.6%). 판정 기준('③이 ②보다 요청당 CPU를 5% 넘게 줄이지 못하면 핫패스도 Zod 파이프 하나로 되돌린다')을 경로마다 잰 값으로 적용해, 좌석 홀드는 경로 스키마(`@ContractRouteSchema`)를 쓰고 대기열 진입은 Zod 파이프(`@ContractBody` 등)로 되돌린다(추천 적용 2026-11-01). 진입 본문은 칸 1~3개라 검사 비용이 작고, 홀드 본문(좌석 배열·자동 배정·행동 요약)은 커서 미리 만든 검사기가 이긴다. 두 방식의 받기·거르기와 Problem 본문이 같은 것은 플랫폼 시험이 CI에서 늘 본다.
- 무효로 남긴 회차: 첫 회차는 k6가 가상 사용자를 200명만 미리 만들어 앱이 가끔 늦을 때(컨테이너 CPU 한도의 끊김) 보내지 못한 요청이 났고, 앱 통계를 k6가 끝난 뒤 읽어 쉬는 시간이 섞였다. 두 번째 회차는 가상 사용자 4,009명을 k6 CPU 4개로 돌려 k6가 버거웠다(응답 시간이 음수로 찍히고 연결 대기 1.2초. 앱은 같은 때 CPU 79%·이벤트 루프 지연 p99 1.6ms로 정상). 세 번째 회차(가상 사용자 400명·k6 CPU 8개, 앱 통계는 k6가 본구간 시작에 비우고 끝에 뜬다)는 18회 모두 보내지 못한 요청이 0이다. 앞의 두 회차는 성능 장부에 `valid: false`와 그 까닭으로 남겼다.
- 한계: 처리기는 고정 응답만 돌려준다. 서비스 코드(인증·멱등·지표 훅·Redis)를 단 경로에서는 검사 비용의 몫이 더 작다. 서비스가 생기면(wbs 2.2.1·2.5.1) 같은 시나리오로 다시 본다.

### 5. Kafka 기본 클라이언트 `@confluentinc/kafka-javascript`를 확정한다(§9.4 'Kafka 클라이언트 런타임', 기술 검토 낮음-152)

| 보는 것(Kafka 3.9.2 브로커 셋, 복제 3, `min.insync.replicas` 2, 평문, 3회) | 결과 |
| --- | --- |
| 텔레메트리 피크 5,600/s [추정](docs/streaming.md §5)와 거래 300/s(NFR-005 결제 접수 피크)를 함께 넣을 때 거래 토픽 `acks=all` 보내기 p99 | 7.8·7.9·7.8ms(p99.9 11.7~14.7ms), 텔레메트리 p99 8.0~8.1ms, 오류·못 보낸 요청 0 |
| 텔레메트리 생산자 하나의 최대 처리량(묶음 100건, 닫힌 모델) | 초당 19만 200건(피크의 34배) |
| 생산자 설정 | 플랫폼 공용 설정 함수와 같은 값(`acks=all`, 멱등, 동시 5, `murmur2_random`, 전달 상한 5·10초) |

- 거래 토픽 `acks=all` p99는 정본에 숫자가 없어 100ms [가정]를 기준으로 두었다(추천 적용 2026-11-01: Outbox 릴레이 전달 상한 10초와 릴레이 지연 경보 5초보다 훨씬 작고, 결제 확정 p99 3초(NFR-006)의 우리 몫 안에 든다). 세 번 모두 그 안이다.

- **MSK IAM 토큰 함수(ST-T14 ①)**: 공용 설정 함수에 붙였다(`packages/platform` `src/msk-iam.ts`, docs/streaming.md §2.6). 가짜 STS로 두 번 부르면 두 번 모두 세션 이름이 `<작업자>-<환경>`이고, 토큰은 맡은 역할의 자격으로만 서명되며, 역할 신뢰를 거두면 토큰을 만들지 않고 실패한다. 자격 갱신을 넘는 재인증(ST-T14 ②)은 실제 MSK와 EKS가 있어야 해 선택 클라우드 보정 `cloud-msk-iam`(소유자 몫, ADR-0154)으로 남는다. 그래서 확정 기준 가운데 '재인증이 끊기지 않으면'은 아직 확인 전이다. 재인증이 끊기면 이 결정을 다시 본다(되돌릴 조건).
- **키 단위 소비(ST-T18)**: 실제 Kafka로 처리 중 소비자 추가·프로세스 강제 종료에서 빠짐 0·두 번 반영 0·순서 뒤집힘 0이고, 커밋 위치가 늘 '앞의 사건이 모두 끝난 위치' 이하였다. 일시 실패로 멈춘 파티션이 돌아오면 이어 받고, 넘기기 기다림 30초 한도 뒤 버린 파티션은 새 주인이 빠짐 없이 받는다(`test-int/keyed-consumer.int.test.ts`). 공용 모듈에 결함은 없었다.
- **`js.consumer.max.batch.size`는 기본 32로 둔다**: 이 값은 `eachBatch`의 묶음 크기이고, 공용 모듈이 쓰는 `eachMessage`에서는 묶음 크기가 아니라 미리 받아 두는 양(캐시)에만 걸린다(1.11.0 `lib/kafkajs/_consumer.js` 208·749~761·1956~1967줄). 키 단위 소비(파티션 여섯을 넷씩 함께, 파티션마다 32키, 처리기 1ms, 사건 20만 개)로 재면 1·32·128·제한 없음(-1)이 초당 5만 300·4만 6,300·4만 3,200·5만 800건으로 같은 범위다. 사건마다 처리를 기다리는 소비(쓰지 않는 방식)에서는 제한 없음이 2.3배 빨랐지만, 제한 없음은 미리 받아 두는 양의 상한을 없애 밀린 토픽에서 메모리가 커질 수 있어 고르지 않는다. 처리량은 거래 토픽 피크(초당 수백 건)보다 훨씬 크다
- **외부 계측 패키지는 쓰지 않는다**: OTel 공식 묶음(opentelemetry-js-contrib)의 Kafka 계측은 kafkajs 모듈만 고친다(`@opentelemetry/instrumentation-kafkajs` 0.33.0, 계측 대상 `kafkajs >=0.3.0 <3`). Confluent 클라이언트용은 회사·개인이 낸 것뿐이다: `@instana/instrumentation-confluent-kafka-javascript` 1.1.0(Apache-2.0, 2026-08-04, 주간 약 3만 7천), `opentelemetry-instrumentation-confluent-kafka` 0.2.1(ISC, 2026-03-30, 주간 약 2천 7백, Confluent 패키지를 자기 의존성으로 끌고 온다), `@drazke/instrumentation-confluent-kafka-javascript` 1.0.0(2025-10-23)(npm 2026-11-01 확인). 공용 모듈이 이미 생산·소비 스팬과 추적 헤더 전달을 직접 하고 시험한다(FND-090, docs/observability.md §2). 외부 패키지를 더하면 같은 일을 하는 두 번째 고침 층이 생기고, 클라이언트 판을 올릴 때마다 그 패키지의 지원 범위를 따로 맞춰야 한다. OTel 공식 묶음에 Confluent 클라이언트 계측이 생기면 다시 본다.
- **네이티브 모듈 설치(docs/devops.md §4.4의 두 갈래 가운데)**: 이미지 빌드 단계에서 미리 빌드한 librdkafka 바인딩을 받는 쪽으로 정한다. 서비스 뼈대 이미지(FND-110)와 PoC 측정 도구 이미지가 빌드 도구 없이 이 방식으로 설치됐다. 소스로 빌드하면 빌드 단계에 Python·make·C++ 컴파일러가 들고 빌드가 몇 분 늘어난다. 대신 받은 묶음은 잠금 파일의 무결성 값이 지키지 않으므로, 빌드 단계에서 GitHub 릴리스가 게시한 다이제스트와 견준다(1.11.0, Node ABI 137: `linux-glibc-x64` `sha256:56b443c9339cb0ae423588599af1df7636eb426c1ac93bf54906e52a0ee77699`, `linux-glibc-arm64` `sha256:8ce2595cfe62bae5fafd206ed78d1d8a8188e2019534b063f51710a8e7798384`, GitHub API 2026-11-01 확인). 견주는 단계는 이미지 빌드 잡(`build-image.yml`, BUILD_ORDER BSL-050)에서 만든다. 받는 주소(`github.com` 릴리스 내려받기)는 빌드 단계의 나가는 연결 허용 목록에만 둔다.
- **Windows 개발 PC에서만 나는 문제**: 같은 프로세스에서 소비자가 도는 동안 관리 연결로 `fetchOffsets`를 거듭 부르면 프로세스가 네이티브 오류(0xC0000005)로 죽었다. Linux 측정 컨테이너에서는 30초 동안 110번 불러도 죽지 않았다. 운영 이미지는 Linux라 결정을 바꾸지 않고, 시험 도구는 커밋 위치를 브로커 쪽 도구로 읽는다(`test-int/containers.ts`).

## 검토한 대안

- **측정을 kind 클러스터에서 하기**: 정본 프로파일(`local-*`)과 같은 무대다. 그러나 kind에는 Strimzi·PostgreSQL·흉내 서버가 함께 돌아 구성 요소 하나를 재는 측정에 잡음이 되고, 측정 도구를 클러스터 밖에 두면 Docker Desktop 포트 전달 비용이 섞인다. 그래서 같은 Docker 망의 컨테이너로 재고 프로파일 `local-poc`를 더했다. 서비스 전체를 재는 측정(K1~K10)은 그대로 kind다.
- **Redis 클라이언트를 규칙대로 기계적으로 고르기**: 규칙은 'node-redis가 같지 않으면 다른 쪽'이지만 다른 둘이 더 나쁜 항목이 있어 규칙이 답을 주지 않는다. 고르지 않고 소유자에게 물었다(OPEN[11]).
- **Kafka 외부 계측 패키지(`@instana/instrumentation-confluent-kafka-javascript`)를 쓰기**: 판이 자주 나오고 내려받기도 많지만, 공용 모듈이 이미 같은 일을 하고 시험한다. 두 번째 고침 층의 판 맞춤 비용이 더 크다.
- **네이티브 바인딩을 소스로 빌드하기**: 받은 파일을 믿지 않아도 되지만 빌드 단계에 컴파일러가 들고 빌드가 몇 분 는다. 게시 다이제스트와 견주면 같은 무결성을 더 싸게 얻는다.
- **MSK IAM 대신 IRSA나 Pod Identity 자격을 바로 쓰기**: 자격이 바뀔 때 세션 이름이 바뀌어 재인증이 끊긴다(docs/streaming.md §2.1). 전용 역할을 고정 세션 이름으로 맡는 정본 결정을 그대로 따랐다.

## 결과와 트레이드오프

- 좋아지는 것: §9.4의 PoC 위험 가운데 wbs 0.5.1의 몫에 잰 값과 판정이 생겼다. 측정 틀(`loadtest/poc`)이 남아 운영 Lua·진입 Lua·서비스 코드가 생기면 같은 명령으로 다시 잰다. 공용 Kafka 모듈은 MSK IAM으로 모든 연결(생산자·소비자·관리·방송형 읽기)이 TLS + OAUTHBEARER로 붙고(로컬 SASL_SSL 브로커로 시험), 인증을 고르면 TLS 검증을 끄는 설정을 받지 않는다.
- PoC가 찾은 결함과 고침: ① node-redis 클러스터의 명령 시간 초과가 `defaults` 안에서는 듣지 않는다(정본 §5의 설정 이름을 고침) ② 공용 Kafka 모듈의 키 단위 소비자·방송형 읽기·관리 연결이 인증을 넘기지 않았다(새 맥락 리뷰가 찾음, 시험부터 고침) ③ OAUTHBEARER 관리 연결의 첫 관리 요청이 한도와 상관없이 끝나지 않아, 실패하면 관리 연결을 새로 만드는 방송형 읽기가 영영 시작하지 못했다(연결에서 메타데이터 요청으로 데우도록 고침, `test-int/kafka-auth.int.test.ts`) ④ 서비스 이미지에 CA 묶음이 없어 librdkafka가 MSK TLS를 검증하지 못한다(실행 단계에 `ca-certificates`).
- 비용: PoC 숫자는 PC 한 대의 값이다(실측(PC)). 운영 ElastiCache·MSK의 값은 다르고, 클라우드 보정은 하지 않았다(ADR-0057). 홀드 Lua와 V-T41 앱은 운영 코드가 아니라 대역이다.
- 남는 것: Redis 클라이언트 확정(OPEN[11]), 실제 MSK에서 자격 갱신을 넘는 재인증과 관리 연결 데우기 확인(ST-T14 ②, 소유자 몫), 진입 Lua·운영 홀드 Lua로 다시 재기(BUILD_ORDER PRF-050·PRF-130), 네이티브 바인딩 다이제스트 대조(BSL-050).

## 되돌릴 조건

- 실제 MSK(선택 클라우드 보정 `cloud-msk-iam` 또는 운영 계정 준비)에서 Confluent 클라이언트의 재인증이 끊기거나 관리 연결 데우기로도 첫 요청이 실패하면 결정 5를 다시 보고 kafkajs와 견준다(§9.4).
- 진입 Lua(wbs 2.2.1)로 다시 잰 20만/s의 p99가 200ms를 넘으면 결정 1을 바꿔 파드별 `INCRBY` 묶음을 쓴다.
- 운영 홀드 Lua(wbs 2.5.1)로 다시 잰 S-T27이 기준을 넘으면 결정 3의 배치 규칙을 새 ADR로 정한다.
- 서비스 코드(인증·멱등·지표 훅 포함)로 다시 잰 V-T41에서 결정 4의 차이가 사라지면 핫패스도 Zod 파이프 하나로 되돌린다.
