# ADR-0077: 관측 책 대조로 보강한다 — SLO 기준값 칸 경계, 관측 저장소 쓰기 경로와 관측 전용 Kafka, 지표 원본 90일·5분 집계 13개월, 보호 조치 알림, 처리 중 요청, 지연 대조, Iceberg 정리(2026-10-21)

- **상태**: 채택 (2026-10-21. 소유자가 관측 가능성 책의 몇 쪽을 보이며 우리 프로젝트에 피드백을 달라고 했다. 책 주제는 지표 측정과 선정, 운영 절차 그림 세 개, 2단계 커밋, 정족수·힌트 핸드오프·안정 해시, 시계열 데이터 집계다. 대조 보고(보강 제안 8건)를 본 뒤 "피드백 ①~⑧을 추천대로 ADR로 남기고 반영해 주세요. ②는 관측 전용 Kafka로, ③은 원본 90일과 5분 집계 13개월로 가 주세요"라고 정했다. 결정 2의 관측 전용 Kafka와 결정 3의 보존 기간은 소유자 결정이고, 나머지 세부는 추천 적용이며 소유자 검토 대상이다. 외부 사실은 2026-10-21에 각 공식 문서와 패키지 등록 정보로 확인했다). 2026-10-26(4차 점검 3부): 결정 1의 표준 칸 목록 18칸은 ADR-0087 결정 29로 0.8초·1.8초(NFR-012 FCP·TTFB 기준값)를 더해 20칸으로 읽는다(docs/observability.md §8). 2026-10-28(ADR-0126, 소유자 승인 '추천안 동의'): 결정 4의 '예산 50% 소진선 감축 → SEV2 예산 50% 감축 실행'은 좌석 홀드·좌석 상태 전파·결제 접수·결제 확정 여정에만 걸린다. 공연 상세·대기열 진입·대기 상태 전파의 50% 소진은 감축하지 않고 SEV2 '예산 50% 사용(입장 목표 그대로)'(`kind` slo)만 낸다. 2026-10-28(기술 검토 중간-021, 소유자 승인 '추천안 동의'): 결정 2는 관측 자료 내구성 등급표(docs/observability.md §9)로 다시 읽는다. 요청 기록은 Pyroscope와 같은 3등급(AZ 장애 때 일부 유실 허용)이라, 내구성은 세 번째 MSK의 이유가 되지 못한다. 세 번째 MSK는 Tempo 3.x 마이크로서비스 모드가 Kafka 호환 큐를 요구해서 둔다. 계속 둘지는 wbs 4.8.2의 요청 기록 저장소 비교(지금 구성, Tempo 모놀리식 + 꼬리 표본 상한, AWS X-Ray)로 정하고, 그 전까지 설계는 지금 구성이다(소유자 결정 유지). 대안 표의 'Tempo 모놀리식은 AZ 장애와 확장을 버티지 못한다'는 3등급 기준과 꼬리 표본 상한으로 다시 판정한다. 결정 2의 '텔레메트리 클러스터는 Flink를 거쳐'는 ADR-0099 뒤 스트림 작업자(`ops-rt`)로 읽는다. 2026-10-28(ADR-0120, 소유자 승인 '추천안 동의'): 결정 3의 테넌트 둘과 5분 기록 규칙 집계는 Thanos 다운샘플링과 견줘 그대로 두었다. 다운샘플링이 없어서 만든 우회가 아니라, 저장소를 바꿔도 같은 모양으로 옮길 수 있는 설계로 읽는다. 대안 표의 'Thanos로 바꿔 다운샘플링 — 4.8.2 판정과 함께 볼 일'은 ADR-0120으로 판정을 마쳤다. 2026-10-28(ADR-0115, 소유자 승인 '추천안 동의'): 결정 7(Iceberg 아카이브 정리: Glue Data Catalog, 작은 파일 합치기, 스냅샷 보존, 남은 파일 삭제)은 아카이브를 회차별 Parquet 파일로 바꿔 쓰지 않는다. 파일을 회차마다 한 번 쓰고 바꾸지 않으므로 정리 작업이 없다. 2026-10-29(ADR-0141 결정 1): 관측 전용 MSK는 `unclean.leader.election.enable`을 MSK 기본값(`true`)으로 둔다(요청 기록은 유실보다 가용성). 거래·제어와 텔레메트리 클러스터는 `false`다. 2026-11-11(소유자 결정 "추천안대로", open-items 99번): 표준 칸 목록에 0.25초·0.6초를 더해 22칸이 됐다(관제 실시간 표 조회 p95 0.25초와 검색 원본 p95 목표의 2배 600ms를 경계로 담는다, docs/observability.md §8).
- **관련**: ADR-0009(차단기·동시 처리 상한), ADR-0028(2단계 커밋 대신 사가·아웃박스), ADR-0042·0052(분석 저장소, 골드 스냅샷), ADR-0049(지연 히스토그램 상한 60초), ADR-0057(인프라는 설계만, 로컬 측정), ADR-0067·0068(관측 백엔드 판정 wbs 4.8.2), ADR-0069(제어 입력·경보 품질), ADR-0076(수집기 구성, 수집기 자체 감시), docs/observability.md §2·§3·§4·§5·§7·§8·§9·§12·§13, docs/infra.md §4·§6, docs/architecture.md §5, docs/features/analytics.md, docs/streaming.md, docs/perf-ledger.md §2·§3, docs/verification.md §5.2, planning/03 POL-022, wbs 0.3.1·1.4.1·4.1.2·4.1.4·4.2.1·4.2.4·4.3.6·4.7.1

## 맥락

- **이미 맞는 것**(대조 결과)
  - 구성 요소마다 4대 신호, 지연 분포(p50·p99·p99.9)와 실패 요청 지연 분리가 있다.
  - 동시 요청은 입장 정원으로 직접 다루고, "입장 자리 5,000명 ÷ 평균 체류 180초 ≈ 초당 28명"처럼 용량을 계산한다.
  - 2단계 커밋은 쓰지 않는다(ADR-0028). 사가·아웃박스·멱등키·결제사 대사·불변식 SEV1이 그 자리를 맡는다.
  - 늦게 오는 데이터는 R0~R3 마감과 오프라인 스캔 규칙으로 다루고, 회차 비교는 골드(오픈 시각 기준 분 단위)에서 한다.
- **빈칸**(대조 결과)
  - ① SLO 기준값과 히스토그램 칸 경계를 맞추라는 규칙이 없다. '표준 지수 간격 12~16칸'만 있다.
  - ② 관측 저장소의 쓰기 구조가 없다.
    - 문서에는 'Mimir 인제스터 영역 인식 3중 복제' 한 줄뿐이다. Loki·Tempo·Pyroscope의 복제 방식은 없다.
    - 그 복구의 검증으로 적힌 G-11은 관측 스택 전체 정지라, AZ 하나가 죽는 경우를 시험하지 않는다.
  - ③ Mimir 13개월 원본 보존의 이유는 '전년도 같은 규모 오픈 비교'다. 그런데 그 비교는 이미 R0 골드 스냅샷(2년)으로 한다(docs/features/analytics.md).
  - ④ 예산 50% 소진선의 자동 정원 감축에 자기 경보가 없다.
    - 콘솔 화면 문구는 있다(design/d5). 그러나 경보로 남지 않아 콘솔을 보고 있지 않으면 모른다.
    - 소진 속도가 3배 아래로 느리게 타면 SEV1·SEV2 없이 50%에 닿는다. 1.5배 속도면 약 23분 뒤다.
  - ⑤ 서비스별 처리 중 요청 수 지표가 없다. Envoy 동시 처리 상한은 설정값이고, 입장 점유 인원은 Redis에만 있다.
  - ⑥ 성능 장부의 p99는 k6(클라이언트) 값이다. 서버 히스토그램과 맞춰 보는 규칙이 없다.
  - ⑦ Iceberg 아카이브는 쓰는 방법만 있다. 파티션, 파일 크기, 스냅샷 만료, 작은 파일 합치기, 남은 파일 정리, 카탈로그, 담당이 없다.
  - ⑧ 작은 빈칸
    - ClickHouse 엔진 표기가 문서끼리 어긋난다(분석 문서는 MergeTree, 스트리밍·인프라 문서는 복제 엔진).
    - 법정 접속기록 DB와 `trust.behavior_raw`의 표 설계가 없다.
    - 파트 수 감시와 Loki 라벨 허용 목록이 없다.
    - 문서가 이름을 쓰는 `prom-client`는 지원이 끝났다.
- **확인한 사실**(2026-10-21 원문)
  - **Envoy**: 시간 히스토그램의 기본 칸(밀리초)은 0.5, 1, 5, 10, 25, 50, 100, 250, 500, 1000, 2500, 5000, 10000, 30000, 60000, 300000, 600000, 1800000, 3600000이다. `stats_config.histogram_bucket_settings`로 바꾼다. 클러스터 지표 `upstream_rq_active`는 처리 중 요청 수 게이지다.
  - **Prometheus 'Histograms and summaries'**
    - 고전 히스토그램에서 `le="0.3"` 비율 식은 그 경계가 정확히 있어야 한다.
    - 경계가 없으면 결과가 아예 없다. 일부 히스토그램에만 있으면 경고 없이 불완전한 결과가 나온다.
    - SLO를 미리 알면 고전 히스토그램의 고정 경계로 정확히 셀 수 있지만, SLO가 바뀌면 경계를 바꾸기 번거롭다.
    - 칸 배치가 다른 히스토그램을 합치면 낮은 해상도로 맞춰진다.
  - **Node용 Prometheus 계측 라이브러리**
    - npm `prom-client` 15.1.3에는 "replaced by @prometheus-io/client" 표시가 있다. `@prometheus-io/client` 0.16.1이고 저장소는 github.com/prometheus/client_js다.
    - README에 exemplar 절이 있고 네이티브 히스토그램 언급은 없다.
  - **OpenTelemetry HTTP 지표 규약**: `http.server.active_requests`는 처리 중 HTTP 요청 수 UpDownCounter다. 선택(opt-in) 지표이고 안정 단계는 Development다.
  - **Grafana Tempo(최신 문서)**
    - 마이크로서비스 모드는 Kafka 호환 큐가 꼭 필요하고 운영용으로 권장된다. 어떤 Kafka 호환 시스템이든 된다.
    - Kafka가 쓰기 경로의 WAL이라 쓰기 복제는 1이다. 분배기는 trace ID 해시로 파티션을 고른다.
    - 모놀리식 모드(`-target=all`, 기본값)는 Kafka가 필요 없다. 블록은 Apache Parquet(열 지향)이다.
    - 소비 지연 지표는 `tempo_ingest_group_partition_lag`·`_seconds`다.
  - **Grafana Mimir**
    - 권장 구조는 Kafka를 쓰는 ingest storage다.
    - 고전 구조는 복제 3이 기본이고 쓰기·읽기 정족수가 2다. 재시작한 인제스터는 그동안의 쓰기를 따라잡지 못해 빈칸이 생긴다. 영역 인식 복제를 지원한다.
    - 테넌트는 `X-Scope-OrgID` 헤더로 나눈다. 테넌트별 보존은 `compactor_blocks_retention_period` 재정의로 정한다. 여러 테넌트를 함께 조회하는 테넌트 연합이 있다.
    - Mimir는 Thanos의 다운샘플링을 지원하지 않는다. Thanos 압축기는 40시간 지난 블록에서 5분, 10일 지난 블록에서 1시간 해상도를 만들고 해상도마다 보존을 따로 둔다.
  - **Prometheus 원격 쓰기**: 사용자 HTTP 헤더(`headers`)와 보내기 전 거르기(`write_relabel_configs`)를 지원한다.
  - **Grafana Loki**
    - 쓰기는 복제 수만큼 보내고 과반 정족수로 성공한다.
    - 라벨은 고정값·낮은 종류 수(수십 개)로 쓴다. 라벨 조합이 많으면 스트림이 늘어 색인이 커지고 청크가 작게 쪼개진다.
    - trace ID·주문 ID는 라벨로 쓰지 않는다. 종류가 많은 값은 구조화 메타데이터로 둔다.
  - **ClickHouse**
    - 파티션은 조회 최적화가 아니라 데이터 관리 수단이다. 파티션 키는 종류 수 100~1,000개 아래가 좋다. 파트가 많으면 'too many parts' 오류가 난다.
    - `MaxPartCountForPartition`이 300을 넘으면 설정 오류·과부하·대량 적재의 신호다.
  - **Apache Iceberg**
    - 정기 정리 작업은 스냅샷 만료, 남은 파일 삭제, 데이터 파일 합치기, 매니페스트 다시 쓰기다.
    - `write.target-file-size-bytes` 기본값은 512MB다.
  - **AWS Glue Data Catalog**: Iceberg 표 최적화로 합치기(binpack 기본), 스냅샷 보존, 남은 파일 삭제를 자동으로 돌린다. 지원 리전에 서울이 있다.

## 결정

1. **SLO 기준값을 히스토그램 칸 경계에 넣는다(추천 적용)**:
   - 지연 히스토그램은 서비스 템플릿과 Envoy가 같은 표준 칸 목록을 쓴다.
     - 목록(초): 0.005, 0.01, 0.02, 0.05, 0.1, 0.15, 0.2, 0.3, 0.5, 1, 1.5, 2, 2.5, 3, 5, 10, 30, 60(+Inf). 18칸이다.
     - Envoy는 같은 값을 밀리초로 `histogram_bucket_settings`에 넣는다.
     - 칸 배치를 모두 같게 두는 이유: 서버를 합칠 때 해상도가 떨어지지 않고 비율 식이 늘 결과를 낸다.
   - 목록은 SLO·경보 기준값을 모두 포함한다.

     | 기준값(초) | 쓰는 곳 |
     | --- | --- |
     | 0.02 | 핫패스 기본 p99 |
     | 0.05 | 좌석 홀드 p99 |
     | 0.1 | gRPC 기본 p95 |
     | 0.15 | 좌석 홀드 p99.9, 진입 Degraded 자동 전환, 결제 접수 p99, 공연 상세 TTFB, 스캔 판정 p95 |
     | 0.2 | 대기열 진입 p99, INP |
     | 0.3 | WebSocket 좌석 갱신 p99, 좌석 Redis 장애 조치 p99 |
     | 0.5 | REST 기본 p95, 명령 접수 p95 |
     | 1 | 진입 Degraded 목표 p99 |
     | 1.5 | WebSocket Degraded |
     | 2 | 결제사 승인 호출 기한, 대기 상태 전파 p99 |
     | 2.5 | LCP |
     | 3 | 결제 확정 p99, 명령 전파 p99 |
     | 5 | 결제 확정 소요(RB-07), 대기 상태 전파 Degraded, 실시간 표 신선도 p95 |
     | 10 | 비상 경로 명령 전파 |
     | 60 | 결제 확정 Degraded p99(ADR-0049의 상한 60초) |

   - 지연 기준 경보와 자동 전환은 `histogram_quantile` 대신 그 경계 칸의 비율로 쓴다. 예: 'p99 > 150ms'는 '150ms 넘은 비율 > 1%'다. 화면의 백분위수 표시는 그대로 둔다.
   - 기준값을 바꾸거나 새로 만들 때는 목록을 먼저 고친다. 경보 시험 CI(wbs 4.2.4)는 두 가지를 검사한다.
     - 기록·경보 규칙이 쓰는 `le` 값과 SLO 표의 기준값이 모두 목록에 있는가.
     - Envoy 설정과 템플릿 목록이 같은가.
   - 브라우저 지표(INP·LCP)는 게이트웨이 수집기의 히스토그램 경계에 같은 값을 둔다(ADR-0076 결정 5).
2. **관측 저장소의 쓰기 경로를 정한다(관측 전용 Kafka는 소유자 결정, 세부는 추천 적용)**:
   - **Tempo**: 운영 설계는 마이크로서비스 모드다. 쓰기 경로의 WAL은 관측 전용 Kafka다.
     - 관측 전용 Kafka는 지금 있는 두 MSK 클러스터(거래·제어용, 텔레메트리용, ADR-0026)와 다른 세 번째 MSK 클러스터로 둔다. 3 AZ, 브로커 3대이고 크기·파티션·보존은 [가정, 4.1.4에서 확정]이다.
     - 따로 두는 이유 1: 거래 Kafka 장애 순간에 요청 기록까지 끊기지 않게 한다. 관측과 제어를 나눈 ADR-0022·0067·0068 원칙의 연장이다.
     - 따로 두는 이유 2: 오픈 피크의 요청 기록 쓰기가 거래 Kafka와 텔레메트리 Kafka의 처리량과 파티션을 나눠 쓰지 않게 한다. 텔레메트리 클러스터는 Flink를 거쳐 관제 실시간 표를 채우므로, 같이 쓰면 관제 화면의 데이터 경로에 부하가 얹힌다.
     - 따로 두는 이유 3: 권한과 보존 정책을 따로 둔다.
   - **Mimir**: 고전 구조를 명시한다. 인제스터는 영역 인식 3중 복제(AZ마다 한 벌)이고 쓰기·읽기 정족수는 2다. 권장 구조(ingest storage)는 지금 쓰지 않는다.
     - 이유: 지표 쓰기 경로를 Kafka에 묶지 않는다. Prometheus 원격 쓰기는 자기 쪽 WAL로 잠깐의 실패를 버틴다. 관측 Kafka 장애의 범위를 요청 기록으로 한정한다.
   - **Loki**: 영역 인식 3중 복제, 과반 정족수다.
   - **Pyroscope**: 원인 분석용 7일 자료다. AZ 장애 때 일부를 잃어도 되는 것으로 둔다.
   - **로컬 측정**: 부하 시험은 Tempo 모놀리식(Kafka 없음)으로 한다. 4.1.4 PoC와 G-26에서만 마이크로서비스 모드와 로컬 Kafka(Strimzi)를 띄워 쓰기 경로를 확인한다(ADR-0057).
   - **관측 저장소 신호**(SEV3 `kind` hygiene, [가정, 4.1.4에서 확정]):
     - Tempo 소비 지연(`tempo_ingest_group_partition_lag_seconds`)이 60초를 넘은 채 5분 지속
     - 관측 Kafka 브로커 오프라인
     - Prometheus 원격 쓰기 실패가 5분 넘게 이어짐
   - **G-26 관측 스택 AZ 하나 장애**(Game Day 관제 자체 감시, docs/observability.md §12)를 더한다. infra.md의 Prometheus·Mimir 복구 검증은 G-26과 G-11이다.
   - 관측 Kafka의 비용과 운영 시간은 wbs 4.8.2의 직접 운영 비용(R2)에 넣는다.
3. **지표 보존은 원본 90일, 5분 집계 13개월로 한다(소유자 결정, 구현 세부는 추천 적용)**:
   - Mimir 테넌트를 둘로 나눈다. 테넌트별 `compactor_blocks_retention_period`로 보존을 다르게 둔다.
     - `raw`: 원본, 보존 90일
     - `agg5m`: 5분 집계, 보존 13개월
   - 클러스터 Prometheus가 원격 쓰기를 둘로 한다.
     - 원본은 `raw` 테넌트로 보낸다.
     - 평가 간격 5분 기록 규칙의 결과만 `write_relabel_configs`로 골라 `agg5m` 테넌트로 보낸다(`X-Scope-OrgID` 헤더). 이름 끝이 `:rate5m`·`:avg5m` 같은 집계 규칙이 대상이다.
   - 집계 대상은 서비스·여정·회차 단위의 4대 신호와 SLI 비율, 포화도 요약, 비용에 쓰는 사용량(노드·파드 수)이다. `pod`·`instance`·`az` 라벨은 뺀다.
   - Grafana에는 '원본(90일)'과 '장기 추세(13개월)' 데이터 소스를 따로 둔다.
   - 전년도 같은 규모 오픈 비교는 지금처럼 R0 골드 스냅샷(2년)으로 한다. 기술 지표의 긴 추세는 5분 집계로 본다.
   - Prometheus 로컬 15일은 그대로다.
   - wbs 4.8.2의 R1(긴 범위 조회)은 이 배치로 판정한다.
     - AMP의 조회 범위 한도(95일)를 넘는 조회는 5분 집계의 긴 추세뿐이다.
     - 그 조회는 95일씩 나눠 보거나 골드에서 본다.
4. **사용자 용량을 줄이는 자동 보호 조치는 실행과 함께 알린다(추천 적용)**:
   - 한 번에 용량을 크게 줄이는 보호 조치는 실행과 동시에 콘솔 SEV2(`kind` control) 이상으로 알린다.
     - 새로 생긴 것: 예산 50% 소진선 감축 → SEV2 '예산 50% 감축 실행'
     - 원래 있던 것: 10배 소진 감축은 SEV1, Degraded 자동 전환·결제 신규 진입 멈춤·결제사 상한 낮춤은 SEV2
   - 기록과 상태 바로만 보이는 것: AIMD의 평소 조절, 확장(KEDA·Karpenter), 재시도, 이상 파드 퇴출, 폴링 간격 조절, 게이트웨이 동시 처리 상한 거절(SLO에 보임).
5. **처리 중 요청 수를 잰다(추천 적용)**:
   - 서비스 템플릿이 `http_server_active_requests` 게이지를 낸다. OpenTelemetry `http.server.active_requests`와 같은 뜻이고, 라벨은 지연 히스토그램과 같다.
   - Envoy `upstream_rq_active`를 포화도 요약과 대시보드에 둔다.
   - admission-ctrl은 예매 단계 지금 인원 `admission_slots_used{event_id}`를 낸다(Redis `ZCOUNT`).
   - 처리 중 요청 수 ÷ (초당 처리량 × 평균 처리 시간)이 1에서 크게 벗어나면 줄이 생긴 곳으로 본다(리틀의 법칙). 원인 패널용이고 경보는 아니다.
6. **부하 시험에서 클라이언트 지연과 서버 지표를 맞춰 본다(추천 적용)**:
   - 성능 장부는 측정마다 같은 시간 창의 두 값을 manifest `latency_crosscheck`에 남긴다.
     - k6 p99
     - 서버 SLI: 같은 경로의 서버 히스토그램 p99와 기준값 안 비율
   - 차이는 네트워크·게이트웨이·클라이언트 쪽 지연이다.
   - 서버 SLI는 목표 안인데 클라이언트 값이 목표 밖이면 '측정 지점 의심'으로 표시한다. 사용자 체감과 SLI가 어긋나는 것이므로 SLI를 재는 위치를 다시 본다.
7. **Iceberg 아카이브의 정리를 정한다(추천 적용)**:
   - 카탈로그는 AWS Glue Data Catalog(서울)다.
   - 파티션은 회차 오픈 월(`month(open_date)`)이다. 골드의 월 파티션과 같다.
   - 목표 파일 크기는 Iceberg 기본값 512MB다.
   - 동결은 회차마다 조금씩 써서 작은 파일이 생긴다. 그래서 Glue 표 최적화의 합치기(binpack), 스냅샷 보존(최근 10개·30일 [가정]), 남은 파일 삭제를 켠다. 담당은 데이터(가상 팀)다.
   - 로컬 PoC(wbs 4.3.6)는 쓰기와 파티션만 확인하고, 정리 작업은 운영 설계로 둔다.
   - 비용은 4.8.1 비용 추정에 넣는다.
8. **작은 정리(추천 적용)**:
   - ClickHouse 분석 표(브론즈·실버·골드)는 복제 엔진(ReplicatedMergeTree 계열)이다. 스트리밍·인프라 문서와 맞춘다.
   - 법정 접속기록 DB의 표는 아래와 같다. 쓰기는 에이전트 수집기의 clickhouse 내보내기다(ADR-0076 결정 7).
     - 엔진 ReplicatedMergeTree, `PARTITION BY toYYYYMMDD(ts)`. 일 해시 앵커·3개월 보존과 맞고 파티션은 약 92개다.
     - `ORDER BY (ts)`, 원문 IP 조회용 bloom filter 건너뛰기 색인 [가정, 4.1.4]
   - `trust.behavior_raw`는 `PARTITION BY toYYYYMMDD(ts)`다. 30일 보존과 맞다.
   - ClickHouse `MaxPartCountForPartition`이 300을 넘은 채 10분 [가정]이면 SEV3(`kind` hygiene)다.
   - Loki 라벨 허용 목록은 `namespace`, `service`, `env`, `cluster`다.
     - 수준(level)·traceId·경로·회차 ID는 본문 필드나 구조화 메타데이터로 둔다.
     - `loki_ingester_chunks_flushed_total{reason}`을 원인 패널에 둔다.
   - Node용 Prometheus 계측 라이브러리는 `@prometheus-io/client`(옛 이름 prom-client)다. exemplar 확인(4.1.1 PoC)도 새 패키지로 한다.

## 책과 다르게 가는 것

| 책의 내용 | 우리 선택과 이유 |
| --- | --- |
| 인공지능 운영: 이상 탐지 → 자동 복구 → 필요할 때만 알람 → 운영자 개입(그림 2.16) | 탐지는 규칙으로 한다(ADR-0076 결정 9). 자동 조치는 줄이는 쪽만이고 용량을 줄이면 항상 알린다(결정 4). 조용히 반복되는 자동 복구는 근본 문제를 숨긴다 |
| 장애 때 알람 → 추적 분석 → 로그 분석(그림 2.15) | 되돌릴 수 있는 약한 명령으로 피해부터 줄이고 원인 분석은 안정 뒤에 한다(observability §13 판단 순서) |
| '그라파나 관측 가능성은 다운샘플링된 시계열을 만든다' | Mimir는 다운샘플링을 지원하지 않는다(원문). 그래서 기록 규칙 집계와 테넌트별 보존으로 한다(결정 3) |
| 지표 선정 확인에 `kubectl top` | 순간값이라 증거로 남지 않는다. Prometheus 조회 결과를 성능 장부에 남기는 지금 방식을 유지한다 |
| 2단계 커밋으로 정합성 | 책도 비용·종속을 경고한다. 우리는 이미 쓰지 않는다(ADR-0028) |

## 검토한 대안

| 대안 | 고르지 않은 이유 |
| --- | --- |
| 서비스마다 지수 간격 칸을 따로 두고 기준값은 보간으로 계산 | 고전 히스토그램은 경계가 없으면 비율 식이 결과를 내지 않거나 경고 없이 틀린다. Node 라이브러리는 네이티브 히스토그램을 쓰지 못한다 |
| Tempo가 거래용 MSK를 같이 씀 | 거래 장애와 관측 장애가 묶이고 오픈 피크에 쓰기 부하가 겹친다 |
| Tempo 모놀리식을 운영에도 씀 | 한 프로세스라 AZ 장애와 확장을 버티지 못한다 |
| Mimir도 Kafka 구조(ingest storage) | 지표 경로가 관측 Kafka 장애에 묶인다. 고전 구조의 3중 복제로 충분한지 G-26에서 본다 |
| Mimir 13개월 원본 유지 | 다운샘플링이 없어 저장과 긴 조회 비용이 크고, 전년 비교는 이미 골드에서 한다 |
| Thanos로 바꿔 다운샘플링 | 저장소 교체는 4.8.2 판정과 함께 볼 일이다. 지금은 기록 규칙과 테넌트 보존으로 같은 효과를 낸다 |
| Iceberg 정리를 Spark 작업으로 직접 돌림 | 상시 Spark 실행 기반이 없다. Glue 표 최적화가 서울에서 같은 정리를 관리형으로 한다 |

## 결과와 트레이드오프

- **남는 한계**
  - 표준 칸 목록은 고정이라, SLO 기준값을 바꾸면 템플릿과 Envoy 설정을 함께 바꿔 다시 배포해야 한다. 바뀌는 동안 칸 배치가 섞인 기간이 생긴다.
  - 관측 Kafka가 멈추면 새 요청 기록이 Tempo에 쓰이지 않는다. 지표·경보·자동 제어는 영향이 없다.
  - 90일이 지난 지표는 파드·경로 단위로 다시 볼 수 없다. 긴 비교는 5분 집계와 골드의 해상도까지만 된다.
  - AIMD의 평소 조절은 여전히 알림 없이 상태 바와 기록으로만 보인다.
  - 이 한계들은 planning/01 §5.2에 적었다.
- **반영 수치(2026-10-21)**
  - ADR 76 → 77, Game Day 25 → 26(G-26)
  - WBS +4일(403.75 → 407.75일): 0.3.1 +0.5, 1.4.1 +0.25, 4.1.2 +0.5, 4.1.4 +1.25, 4.2.1 +0.25, 4.2.4 +0.25, 4.3.6 +0.5, 4.7.1 +0.5
  - 검토 기록 R-86

## 되돌릴 조건

- G-26에서 Mimir 고전 구조가 AZ 하나 장애에 쓰기나 읽기 빈칸을 내면, ingest storage(관측 Kafka 사용)를 새 ADR로 검토한다.
- 4.8.2 판정이 AWS 관리형이면, 결정 3의 테넌트 둘을 AMP 작업 공간 보존 설정으로 옮긴다. 이때 결정 2의 Mimir 부분은 빠진다.
- 기준값이 자주 바뀌어 칸 목록 변경이 부담이 되면, 네이티브 히스토그램을 지원하는 계측(OpenTelemetry SDK의 지수 히스토그램 등)으로 바꾸는 것을 다시 본다.
- 5분 집계로 답하지 못한 장기 질문이 분기에 두 번 넘게 나오면, 원본 보존 기간이나 집계 대상을 다시 정한다.
