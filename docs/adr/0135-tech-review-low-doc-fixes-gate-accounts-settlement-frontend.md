# ADR-0135: 기술 검토 낮음 항목의 문서 수정 묶음 3 — 현장 입장·계정·정산·환불·프론트엔드·화면(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 낮음 항목(영역: 현장 입장·계정, 정산·환불·후기, 프론트엔드·디자인 시스템, 화면 문서·접근성)에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 방향은 소유자 결정(추천안 승인)이고, 검토가 안을 고르지 않은 곳의 선택과 값 같은 세부는 추천 적용이다. 측정 전 값은 [가정]으로 표시했다)
- **관련**: review/tech-review.md(낮음-073·낮음-074·낮음-075·낮음-076·낮음-077·낮음-078·낮음-079·낮음-080·낮음-081·낮음-082·낮음-083·낮음-084·낮음-085·낮음-086·낮음-087·낮음-088·낮음-089·낮음-090·낮음-091·낮음-092·낮음-093·낮음-094·낮음-095·낮음-096·낮음-097·낮음-098·낮음-099·낮음-100·낮음-101·낮음-102·낮음-103·낮음-104·낮음-105·낮음-106·낮음-107·낮음-108·낮음-109·낮음-110·낮음-111), review/consistency-review.md R-153, 00-summary.md §6·질문 61, 같은 날 새 ADR-0100~0126(새 결정이 필요한 항목)

## 맥락

2026-10-27 기술 검토 2판은 설계의 모든 기술·기법을 시니어 개발자 관점에서 따져 높음·중간·낮음 항목으로 냈다. 2026-10-28 소유자가 남은 항목을 모두 추천안대로 고치라고 정했다. 새 결정이 필요한 항목은 따로 ADR(0100~0126)을 썼고, 이 ADR은 정본 문서를 고쳐 반영한 낮음 항목 39건의 문제와 결정을 한곳에 모은다. 검토 문서에서는 이 항목들의 본문을 지우고 이 ADR을 가리키는 한 줄만 남겼다(지운 본문은 git 이력에 있다).

## 결정

항목마다 검토의 추천 수정을 따랐다(소유자 승인). 검토가 안을 여럿 내고 고르지 않은 곳은 고른 안과 이유를 적었고 '추천 적용'으로 표시했다. 정본에는 `(추천 적용 2026-10-28, 기술 검토 <번호>)`로 표시했다.

### 현장 입장·계정

#### 낮음-073 '폐기된 기기는 TLS 단계에서 막힌다'는 문장이 설계와 다르다
- **처리**: 이미 반영됨(기술 검토 중간-057, m8). offline-gate §6.5 "폐기된 기기는 다음 요청부터 403(기기 폐기)으로 거부되어 … TLS 단계가 아니라 요청마다 하는 기기 상태 확인에서 막는다", docs/infra.md RB-22 같은 문장, ADR-0051 상태 줄 "'TLS 단계에서 막힌다'는 '다음 요청부터 403(기기 상태 확인)'으로 읽는다"를 확인했다.
- **문제**: '폐기된 기기는 TLS 단계에서 막힌다'는 문장이 설계와 다르다
- **결정**: 없음(중간-057 절에 든다)
- **바꾼 문서**: 없음

#### 낮음-074 시험 O-T21이 결정 9·O-T26·I-T24와 어긋난다
- **문제**: 시험 O-T21이 결정 9·O-T26·I-T24와 어긋난다
- **결정**: 해제·만료로 무효가 된 스태프 토큰을 붙인 업로드는 401 `invalid_token`으로 돌려주고, 앱이 토큰을 지운 뒤 같은 묶음을 기기 인증만으로 다시 보낸다(추천 적용, RFC 9449 §7.1). O-T21은 '목록·변경분·책임자 기능은 거부, 업로드는 다시 보내면 받고 세션 밖 기록으로 표시'로 고쳐 ADR-0051 결정 9·O-T26·I-T24와 맞췄다. 스캐너 401 도전은 기본안이 DPoP 방식이다.
- **바꾼 문서**: offline-gate §6.5·O-T21, openapi `/v1/scanner/scans`·`WWWAuthenticate`, guidelines §12, frontend §5.5

#### 낮음-075 QR v1의 글자 인코딩 후보와 시각 필드 형식을 좁힌다
- **문제**: QR v1의 글자 인코딩 후보와 시각 필드 형식을 좁힌다
- **결정**: 글자 인코딩은 base45(RFC 9285)로 정해 QR 영숫자 모드로 싣고, 시각 칸은 부호 없는 32비트 빅엔디언 UNIX 초로 적는다(ADR-0051 D4의 빈칸, 소유자 승인 방향·세부 추천 적용). BarcodeDetector가 글자만 돌려주기 때문이다. PoC는 오류 정정 수준과 인식 시간만 잰다.
- **바꾼 문서**: offline-gate §3·§12, frontend §3.7·§5.4·§5.5, ADR-0051 상태 줄

#### 낮음-076 월렛 QR 그리기의 시각·타이머 규칙을 '그릴 때마다 지금 보정 시각으로'로 바꾼다
- **문제**: 월렛 QR 그리기의 시각·타이머 규칙을 '그릴 때마다 지금 보정 시각으로'로 바꾼다
- **결정**: 다시 보일 때와 보이는 동안 15초마다 그 순간의 보정 시각으로 서명해 그리고, 켜진 동안은 단조 시계로 이어 센다. 잠든 동안 단조 시계가 멈추는 브라우저가 있어 다시 보이면 기준을 다시 잡는다. 저전력 문장은 지우고 Worker는 선택으로 둔다(추천 적용).
- **바꾼 문서**: offline-gate §3·O-T13, frontend §3.7·§5.4
- **남는 한계**: offline-gate §3 시계 보정 행에 적음(오프라인 중 기기 시계 변경). planning/01 §5.2에는 더하지 않았다(영향이 '거부 뒤 다시 켜기'로 작다).

#### 낮음-077 iOS 홈 화면 앱의 화면 꺼짐 방지가 18.4부터라는 점을 offline-gate에도 적는다
- **문제**: iOS 홈 화면 앱의 화면 꺼짐 방지가 18.4부터라는 점을 offline-gate에도 적는다
- **결정**: frontend §1.5의 지원 표와 맞춰, 18.4 미만 홈 화면 앱에서는 밝기·자동 잠금 안내만 보인다고 offline-gate에도 적는다(추천 적용, 문서 정합).
- **바꾼 문서**: offline-gate §3·§4

#### 낮음-078 스캐너 대수 산정에 목표 대기 시간을 넣는다
- **문제**: 스캐너 대수 산정에 목표 대기 시간을 넣는다
- **결정**: 줄 서는 시간 p95 10분 [가정]을 목표로, 도착 몰림을 넣은 1분 단위 어림 식과 작은 모의로 대수를 고르고 예비를 더한다(추천 적용). 값은 운영 설계이고 포트폴리오는 1대 처리량만 잰다.
- **바꾼 문서**: offline-gate §0, ADR-0051 상태 줄

#### 낮음-079 '현장 시험에서 확정' 표시를 '모의 확인'과 '현장 도입 때 확정'으로 나눈다
- **문제**: '현장 시험에서 확정' 표시를 '모의 확인'과 '현장 도입 때 확정'으로 나눈다
- **결정**: '[가정, Phase 5 현장 시험에서 확정]'을 모의 시험으로 확인할 값과 실제 도입 때 정할 값으로 나눠 표시한다(추천 적용, ADR-0057 결정 9). wbs 5.7.1은 모의 시험이라 경보 임계·마감 대기·대기 목표를 확정하지 못한다.
- **바꾼 문서**: offline-gate §0·§5·§12, observability §5, ADR-0051 상태 줄

#### 낮음-080 관리형 크롬 URL 허용 목록의 [가정] 일부를 원문으로 푼다
- **문제**: 관리형 크롬 URL 허용 목록의 [가정] 일부를 원문으로 푼다
- **결정**: `URLBlocklist`에 `*`, `URLAllowlist`에 스캐너 PWA·API·부스 주소(Android 86부터, 원문 확인)로 적고, 서비스 워커 요청 적용만 PoC 5.4.3에 남긴다(추천 적용, ADR-0065 결정 10의 [가정]).
- **바꾼 문서**: offline-gate §6.1·§12, ADR-0065 상태 줄

#### 낮음-081 '엄격한 브라우저 기기 바인딩'은 실제 통제보다 크게 적었다
- **문제**: '엄격한 브라우저 기기 바인딩'은 실제 통제보다 크게 적었다
- **결정**: 스스로 알리는 `deviceId`라 소지 증명이 아니므로 '기기 식별값 기록'으로 부르고 세션 결속 통제로 세지 않는다. 쿠키 탈취 사고가 확인되면 리프레시 요청을 추출 불가 키로 서명하는 안을 다시 본다(추천 적용, 과장 금지 원칙).
- **바꾼 문서**: identity §2·§7, POL-019, ADR-0001 상태 줄

#### 낮음-082 문구 정합: 6.3.3 '기준에 맞는'과 '메시 mTLS가 있으므로' 전제
- **문제**: 문구 정합: 6.3.3 '기준에 맞는'과 '메시 mTLS가 있으므로' 전제
- **결정**: 팬 6.3.3은 위험 수용이고 보완 통제는 그 근거라고 적는다. 게이트웨이가 내부 신원 헤더를 지우고 다시 쓰며, 호출자 제한은 운영 메시 mTLS·포트폴리오 NetworkPolicy로 나눠 적고 I-T15를 두 범위로 나눈다(추천 적용, ADR-0082와 맞춤).
- **바꾼 문서**: identity §2·§3·§7·I-T15

#### 낮음-083 6.1.1·6.1.2의 '적용' 판정을 근거 문서가 생길 때까지 '미정'으로 내린다
- **문제**: 6.1.1·6.1.2의 '적용' 판정을 근거 문서가 생길 때까지 '미정'으로 내린다
- **결정**: 6.1.2는 금칙어 목록 문서(auth-controls.md, wbs 3.5.1)를 쓰기 전까지 부분 적용으로 둔다(추천 적용). 6.1.1은 중간-052로 identity §6에 근거가 생겨 적용을 유지한다.
- **바꾼 문서**: asvs/auth.md 6.1.2·요약


### 정산·환불·후기

#### 낮음-084 지급 실패·장애 처리의 세부가 비어 있거나 과하다
- **문제**: 지급 실패·장애 처리의 세부가 비어 있거나 과하다
- **결정**: FAILED를 세 갈래로 나눠 처리하고, 재요청은 '가장 큰 순번 + 1'·같은 금액이면 처음 승인 범위(감사 로그)로 한다. 지급 API 장애는 서킷 브레이커 대신 같은 멱등키로 지급일 전 영업일 22시 [가정]까지 지수 간격 재시도, 넘으면 다음 영업일(추천 적용, ADR-0047 세부, 토스페이먼츠 원문 확인).
- **바꾼 문서**: settlement §5.2·§12·§13, asvs/settlement 15.2.2·16.5.2, guidelines 외부 연동 표

#### 낮음-085 영업일 달력의 출처와 은행 휴무일 처리가 없다
- **문제**: 영업일 달력의 출처와 은행 휴무일 처리가 없다
- **결정**: 지급·송금일은 은행 영업일 달력으로 세고, 결제사 날짜 오류면 다음 영업일로 한 번 다시 요청한다. 달력 출처는 wbs 5.3.1에서 정하고 공휴일과 다른 날이 있는지 원문으로 확인한다(추천 적용).
- **바꾼 문서**: settlement §5.1·§12, payment §12, transfer-refund §12

#### 낮음-086 예금주 이름 비교 규칙이 없다
- **문제**: 예금주 이름 비교 규칙이 없다
- **결정**: 예금주와 상호·대표자를 NFKC·법인 표기·공백·문장부호 제거·대소문자 무시로 정규화해 비교하고, 다르면 거부한 뒤 판매자 정보 확인 요청 경로를 안내한다. 운영자는 판매자 정보 표기만 바로잡고 계좌를 손으로 통과시키지 않는다(추천 적용, ADR-0047 세부).
- **바꾼 문서**: settlement §3·§6·J-T8

#### 낮음-087 승인 업무 상태도에 철회와 만료가 없다
- **문제**: 승인 업무 상태도에 철회와 만료가 없다
- **결정**: 승인 전 요청자 철회(Withdrawn)와 시스템 만료(Expired, 대상 변경·처리 기한 지남)를 상태도에 더하고, 종류별 만료 조건을 POL-038 공통에 둔다. 승인 직전에 만료를 다시 판정한다(추천 적용, ADR-0046 세부).
- **바꾼 문서**: planning/03 §2.10·POL-038, transfer-refund §7.2·R-T29, data.md, openapi, settlement §5.1

#### 낮음-088 배상 '재원 순서'의 표현과 송금 포트 이름이 오해를 부른다
- **문제**: 배상 '재원 순서'의 표현과 송금 포트 이름이 오해를 부른다
- **결정**: 배상금은 늘 PEAKET이 먼저 보내고 상계·보증·청구는 회수 순서로 적는다. 회수 상태는 미수금 하나에 두고(`compensation.receivable_id`), 송금 포트는 `CompensationTransferPort`로 바꿔 정산 지급과 구분한다(추천 적용, ADR-0046 결정 5 표현).
- **바꾼 문서**: transfer-refund §6·§8·§10·R-T10, data.md, architecture, guidelines, data-classification, settlement, d5, ADR-0046 상태 줄

#### 낮음-089 추적 표의 '시험 결과'를 CI 시험 태그로만 채우는 규칙에 검사 종류를 더한다
- **문제**: 추적 표의 '시험 결과'를 CI 시험 태그로만 채우는 규칙에 검사 종류를 더한다
- **결정**: 태그를 붙일 수 있는 검사를 자동 시험·정적 정책 검사·doc-check 규칙·설정 검사로 넓히고, 운영 설계로만 있는 행은 '설계 검사'로 적어 통과로 세지 않는다. L3 표기를 'L3' 하나로 맞춘다(추천 적용).
- **바꾼 문서**: architecture §8.2, asvs 13개 머리말과 L3 표기

#### 낮음-090 정산·양도 표가 V1(인코딩·삽입 방지)을 판정하지 않고, CSV 수식 삽입 방어를 어디서도 추적하지 않는다
- **문제**: 정산·양도 표가 V1(인코딩·삽입 방지)을 판정하지 않고, CSV 수식 삽입 방어를 어디서도 추적하지 않는다
- **결정**: 정산·양도 추적 표에 V1 L1·L2를 모두 판정하고, CSV·XLSX 수식 삽입 방어(ADR-0065 결정 12)를 settlement 선별 L3 1.2.10 행으로 추적한다(예매자 명단 내려받기 포함, 추천 적용).
- **바꾼 문서**: asvs/settlement.md, asvs/transfer-refund.md

#### 낮음-091 '5000.0은 정수가 아니면 거부' 예시는 구현할 수 없다
- **문제**: '5000.0은 정수가 아니면 거부' 예시는 구현할 수 없다
- **결정**: 금액은 `Number.isSafeInteger` 통과, 소수 부분(5000.5)은 거부로 적는다. 5000.0은 JSON에서 5000과 같아 구분하지 않는다(추천 적용).
- **바꾼 문서**: asvs/settlement.md 15.3.5

#### 낮음-092 양도 추적 표의 낡은 행과 빠진 판정
- **문제**: 양도 추적 표의 낡은 행과 빠진 판정
- **결정**: 수락 트랜잭션과 받는 사람 키 등록을 나눠 적고, 받는 사람 조회의 횟수 제한·기록을 추적한다. 회차 취소 증빙은 파일을 받지 않고 문서 종류·번호만 적는다(추천 적용).

#### 낮음-093 문의 내용에 섞이는 계좌번호에 값싼 완화를 더한다
- **문제**: 문의 내용에 섞이는 계좌번호에 값싼 완화를 더한다
- **결정**: 제출 전 확인 창과 담당자 화면 가림을 두고 저장값은 바꾸지 않는다. 휴대폰·예매번호 형식은 패턴에서 뺀다. 저장 전 가림은 법률 검토에서 정한다(추천 적용, ADR-0066 결정 5 세부).
- **바꾼 문서**: asvs/support 법률 행, data-classification, d5 §5.30

#### 낮음-094 공연 설명 정화기를 하나로 정하고 서버 쪽 DOM 조건을 적는다
- **문제**: 공연 설명 정화기를 하나로 정하고 서버 쪽 DOM 조건을 적는다
- **결정**: 서식 글 HTML 정화 대체안의 정화기는 DOMPurify 하나이고, 서버에서는 최신 jsdom과 쓰며 happy-dom은 쓰지 않는다. 허용 목록은 공용 패키지 하나(추천 적용). 기본안은 낮음-100의 구조 문서다.
- **바꾼 문서**: asvs/catalog-review 1.3.1, frontend §5.14.3

#### 낮음-095 공제액과 배상금의 원 미만 처리 규칙을 정한다
- **문제**: 공제액과 배상금의 원 미만 처리 규칙을 정한다
- **결정**: 공제액은 원 미만 버림, 배상금은 원 미만 올림으로 소비자에게 불리하지 않게 하고, 공제율은 기준점 정수로 두어 공용 함수 한 곳에서 정수 연산한다(추천 적용, POL-032·ADR-0046 세부의 빈칸). 소비자분쟁해결기준의 끝수 규칙 유무는 확인 필요.

#### 낮음-096 XState를 쓰는 이유(모델 기반 시험)가 시험에 없다
- **문제**: XState를 쓰는 이유(모델 기반 시험)가 시험에 없다

#### 낮음-097 관제 RxJS 어댑터와 브라우저 OTel SDK는 쓰는 조건을 적어야 한다
- **문제**: 관제 RxJS 어댑터와 브라우저 OTel SDK는 쓰는 조건을 적어야 한다
- **결정**: RxJS는 둘 이상의 흐름을 시간 창으로 합치는 곳이 있을 때만 둔다. 지금은 없어(경보 묶기는 서버, 명령 확인은 REST 정본 + 명령별 타이머) 호스트의 작은 함수 둘(`latestEvery`·`shareByKey`)로 바꾸고 공유 싱글턴에서 뺀다(추천 적용). 브라우저 추적 SDK 범위는 낮음-053이 'SDK를 싣지 않음'으로 정했다.
- **바꾼 문서**: docs/frontend.md §2.3·§3.1·§4.5·§5.7·§5.14.5·§6.2, architecture §6.4, control-tower, ADR-0091·0092 상태 줄

#### 낮음-098 작은 구조·도구 정리 네 가지(FSD 이름 충돌, 린터 둘, Trusted Types 빌드 정책, 끌어 놓기 라이브러리)
- **문제**: 작은 구조·도구 정리 네 가지(FSD 이름 충돌, 린터 둘, Trusted Types 빌드 정책, 끌어 놓기 라이브러리)
- **결정**: FSD 층을 `_app`·`_pages`로 두고 Next `app/`은 다시 내보내기만, 층 규칙은 Steiger 하나, 관제 Trusted Types 보고 모드는 빌드별 정책 이름·원격 적재 정책을 목록에 넣고 FE-T39로 위반 0을 본 뒤 켠다, 끌어 놓기는 버튼 방식만(추천 적용).

#### 낮음-099 허용 메서드 제한을 CloudFront에서 할 수 있다고 적었다
- **문제**: 허용 메서드 제한을 CloudFront에서 할 수 있다고 적었다
- **결정**: CloudFront 캐시 동작은 세 묶음 가운데 하나만 고를 수 있어 정적은 GET·HEAD, 동적·`/_t/*`는 전체 묶음으로 두고, 경로별 메서드 제한은 gw-fan 경로 규칙과 앱 서버가 405로 막는다. FE-T16이 PUT·DELETE·TRACE 응답을 본다.
