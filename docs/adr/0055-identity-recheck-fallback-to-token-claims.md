# ADR-0055: 주문 생성의 본인확인 재확인은 identity-svc가 응답하지 못하면 토큰의 본인확인 표시로 판정한다

- **상태**: 채택 (2026-10-13. 소유자 질문 '인증·계정 서비스가 따로 없는가'에 답하다 찾은 빈칸이다. 추천안을 소유자가 '추천안대로 가주세요'로 정했다(추천 적용, 2026-10-13). ADR-0006 결정 6을 보완한다.)
- **관련**: ADR-0006(결정 3·6, 간주 사항), ADR-0007(장애 격리), ADR-0008(게이트웨이 무상태 검증), ADR-0009(2단계 서킷 브레이커), ADR-0011(결정 1·2), docs/features/payment.md §2·§9·§11, docs/features/identity.md §5·§10, docs/security/asvs/payment.md
- **관련 ID**: FR-002, FR-011, POL-001, NFR-005, NFR-016

## 맥락

- **ADR-0006 결정 6과 POL-001은 결제 때 주문 계정의 본인확인 유효 상태를 다시 확인하라고 한다.** 흐름이 그려진 곳은 payment §2뿐이고, 거기서는 주문 생성(`POST /v1/orders`) 때 purchase-svc가 identity-svc를 gRPC로 한 번 부른다. 다른 문서는 시점을 '주문서 작성 및 결제 승인 시'(ADR-0006 결정 6), '최종 결제 접수 시점'(identity §5), '결제 직전'(architecture §3.2)으로 달리 적었다.
- **identity-svc가 응답하지 못할 때 이 재확인을 어떻게 할지 정해져 있지 않았다.** identity §10은 identity-svc가 멈추면 이미 받은 액세스 토큰이 최대 15분 통하고 새 로그인·토큰 갱신·본인확인이 멈춘다고만 적었다. 정하지 않으면 구현에 따라 모든 주문을 막거나(닫힘), 확인 없이 통과시킨다(열림).
- **구매 경로 요청은 이미 서명된 본인확인 표시를 가지고 온다.** 게이트웨이는 구매 경로에 `ticket:buy` 권한을 요구하고(architecture §4), `ticket:buy`와 `pid`는 본인확인을 마친 계정의 토큰에만 실린다(identity §5, ADR-0006 결정 3). 토큰은 identity-svc의 팬 토큰 키로 서명되고, 게이트웨이가 서명·만료·대상을 확인한 뒤 검증한 값을 내부 헤더로 넘긴다(ADR-0011 결정 1).
- **재확인이 토큰 확인보다 더 잡는 경우는 좁다.** 본인확인 기록에는 상태 열이 없고(docs/data.md의 `identity_verification`), 본인확인은 계정당 1회로 영구 유효하다고 간주한다(POL-001). 본인확인이 무효가 되는 길은 탈퇴와 병합뿐이고, 둘 다 세션 종료 이벤트로 그 계정의 토큰을 막는다(identity §2.1·§8, ADR-0011 결정 2). 따라서 재확인이 더 잡는 것은 세션 종료 이벤트가 아직 purchase-svc에 닿지 않은 동안의 탈퇴·병합 계정이다.
- **법정 의무와의 관계**: ADR-0006은 순번 발급 전 계정당 1회 본인확인을 공연법 시행령 §3의3 제1호 가목 의무의 충족으로 간주했다(간주 사항). 결제 때 재확인은 그 위에 더한 내부 통제다.
- **ASVS 5.0.0 원문(2026-10-13 확인)**: 16.5.2(L2)는 외부 자원 접근이 실패해도 서킷 브레이커나 우아한 저하 같은 방식으로 안전하게 동작하라고 하고, 16.5.3(L2)은 검증 로직의 오류에도 거래를 처리하는 fail-open을 막으라고 한다. 16.3.4(L2)는 보안 통제의 실패를 기록하라고 한다([V16](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md)).

## 검토한 대안

| 대안 | 문제 |
| --- | --- |
| 1. 막기(닫힘 실패) | identity-svc가 멈춘 동안 주문 생성이 모두 실패한다. 이미 입장해 좌석을 잡은 사람(동시 입장 목표 5,000명)의 결제가 멈추고 홀드가 만료된다. identity 장애가 구매 장애로 번져 ADR-0007의 장애 격리와 어긋난다 |
| 2. 확인 없이 통과 | 검증을 건너뛰는 fail-open이다(ASVS 16.5.3) |
| 3. purchase-svc가 재확인 결과를 캐시 | 계정마다 캐시를 둬야 하고, 첫 주문에는 캐시가 없어 효과가 작다. 같은 정보가 서명된 토큰에 이미 있다 |
| **4. 토큰의 본인확인 표시로 판정(채택)** | 토큰이 발급된 때의 상태(최대 15분 전)로 판정한다. 남는 범위는 '결과'에 적는다 |

## 결정

1. **재확인은 주문 생성 때 한 번 한다(payment §2).** ADR-0006 결정 6의 '주문서 작성 및 결제 승인 시'와 identity §5의 '최종 결제 접수 시점'은 이 한 번을 가리키는 것으로 정리한다(문서 정합). 결제 승인 때 따로 재확인하지 않는 것은 주문이 이미 확인된 계정으로 만들어졌고 결제창 유지 시간(최대 30분) 안의 변화는 세션 종료 이벤트가 막기 때문이다.
2. **identity-svc가 응답하지 못하면 토큰 값으로 판정한다.** purchase-svc의 재확인 호출이 서킷 브레이커 열림, gRPC 데드라인 초과, 연결 실패(`UNAVAILABLE`)로 끝나면 게이트웨이가 넘긴 권한과 pid 헤더(`X-User-Pid`)를 본다. `ticket:buy`와 pid가 모두 있으면 주문을 만들고, 하나라도 없으면 거부한다.
3. **identity-svc의 '무효' 응답은 그대로 따른다.** 계정 없음·탈퇴·병합·본인확인 없음으로 답하면 토큰과 관계없이 거부한다. 토큰 값으로 대신하는 것은 응답을 받지 못했을 때뿐이다.
4. **세션 종료 목록 검사는 대체 판정 때도 그대로 한다(ADR-0011 결정 2).**
5. **대체 판정을 남긴다.** 지표 `purchase_identity_recheck_fallback_total`(사유 라벨 `circuit_open`·`deadline`·`unavailable`)과 주문 ID가 든 보안 이벤트 로그를 남긴다(ASVS 16.3.4). 새 경보는 두지 않는다. identity-svc 장애를 알아차린 뒤 이 지표로 몇 건이 대체 판정됐는지 본다.
6. **시험**: payment P-T35(identity-svc 중단 중 주문 생성)로 확인한다.

## 결과

- identity-svc 장애가 주문 생성 장애로 번지지 않는다. 입장한 사람은 토큰이 유효한 동안 주문을 만들고 결제를 접수할 수 있다.
- **남는 위험**: 대체 판정은 토큰이 발급된 때의 상태(최대 15분 전)를 본다. 그 사이 탈퇴·병합된 계정은 세션 종료 이벤트가 purchase-svc에 닿았으면 막히고, 이벤트가 늦은 동안에만 주문을 만들 수 있다. identity §10 '세션 종료 Kafka 이벤트 지연'에서 이미 받아들인 대가와 같은 범위다. identity-svc가 멈춘 동안에는 새 탈퇴·병합이 일어나지 않는다.
- **이 결정으로 풀지 않는 한계**: identity-svc가 15분 넘게 멈추면 토큰을 갱신하지 못해, 사용자마다 토큰이 끝나는 때(늦어도 15분 뒤)부터 구매 경로 요청이 게이트웨이에서 거부된다. 결제창에서 인증을 마쳤어도 결제 접수를 하지 못하면 승인 API를 부르지 않으므로 과금은 되지 않지만 그 주문은 만료된다. 대체 판정은 토큰이 유효한 동안만 돕는다. planning/01 §5.2에 적는다.
- **대가**: purchase-svc의 재확인 호출에 분기 하나, 지표 하나, 시험 하나가 는다. 구현은 wbs 2.7.1(결제 접수)에 들어가고 추정은 바꾸지 않는다(0.5일 미만).

## Well-Architected 기둥

| 기둥 | 영향 |
| --- | --- |
| 안정성 | identity 장애를 구매 경로와 떼어 놓는다. 토큰 수명(15분)까지만 완충한다 |
| 보안 | 서명된 토큰으로 판정하고 '무효' 응답과 표시가 없는 토큰은 거부하므로 검증을 건너뛰지 않는다. 남는 범위는 세션 종료 이벤트 지연과 같다 |
| 운영 우수성 | 대체 판정 건수와 주문 ID를 남겨 장애 뒤 확인할 수 있다 |

## 재검토 조건

- 본인확인에 상태(만료·재확인 필요·정지)가 생길 때. 토큰 값만으로는 판정할 수 없게 되므로 대체를 다시 정한다.
- 주무관청이 구매 시점의 실시간 본인확인을 요구할 때
- 대체 판정으로 만든 주문에서 무효 계정의 주문이 나올 때
- identity-svc 장애가 15분을 넘는 일이 생길 때. 토큰을 갱신하지 못해 판매가 멈추는 한계를 다시 본다
