# ADR-0249: 최초 방문 쿠키를 사전 검증 응답에서 주고, 판정 기록·행동 신호는 버퍼를 넘기면 버리며, 허니팟 경로는 설정으로 넣는다

- **상태**: 채택(2026-11-09, 추천 적용. wbs 3.2.1 세부는 추천 적용이라는 승인 2026-10-28을 따른다). BUILD_ORDER BOT-055(wbs 3.2.1 ②).
- **관련**: POL-006, POL-026, POL-046, FR-039, FR-049, FR-072, ADR-0065 결정 9, ADR-0071, ADR-0141 결정 6, ADR-0171 결정 4, ADR-0219, ADR-0223 결정 4, ADR-0234, ADR-0248, [docs/features/bot-defense.md](../features/bot-defense.md) §3·§4·§7, [docs/features/queue-admission.md](../features/queue-admission.md) §7·§10, [docs/security/secrets-and-keys.md](../security/secrets-and-keys.md), [docs/security/asvs/bot-defense.md](../security/asvs/bot-defense.md)
- **관련 ID**: Q-T39, Q-T40, B-T17, B-T19, ASVS v5.0.0-3.3.1~3.3.4, 3.5.1, 3.5.3, 9.1.1, 16.3.3, 16.3.4

## 맥락

- 용어: 시청자 응답 함수는 CloudFront(AWS의 CDN)가 사용자에게 응답을 돌려주기 직전에 돌리는 작은 함수다. 키 값 저장소(KeyValueStore)는 그 함수가 읽는 값 저장소다. HMAC은 비밀 키로 만든 위조 확인용 값이고 MAC은 그 값이다. 허니팟은 사람이 볼 수 없게 숨긴 링크로, 그 링크를 부른 세션에 표시를 남기는 장치다.
- 정본은 최초 방문 쿠키의 이름·속성·서명 대상, 행동 신호 요약의 칸, 허니팟의 기록 조건을 정했다. 코드로 옮기려면 정본에 없는 세부를 정해야 한다.
- BOT-050(ADR-0248)은 판정 기록을 포트까지만 두고 Kafka(이벤트를 순서대로 쌓아 두고 여러 곳에 나눠 주는 메시지 시스템)로 내보내지 않았다.
- 결제 화면 요약을 싣는 결제 시도 API는 BUILD_ORDER PRF-191이고, 그 화면은 HOT-358이다. 아직 없다.

## 결정

1. **쿠키는 사전 검증 경로의 시청자 응답 함수 하나가 준다(`services/queue-svc/edge/preverify-viewer-response.js`).** POST의 201 응답에만 돈다. 진입 함수와 다른 키 값 저장소를 쓰고, 키는 `fv:cur`(지금 서명에 쓰는 kid)와 `fv:key:{kid}`(서명 키)다(ADR-0223 결정 4).
   - 값의 꼴은 `v1.{kid}.{발급 시각 밀리초}.{요청 ID base64url}.{MAC base64url}`이고 MAC은 `HMAC-SHA256(키 글자, "PEAKET-firstvisit-v1." ‖ 앞 네 칸을 점으로 이은 글)`이다. 속성은 `Secure; HttpOnly; SameSite=Strict; Path=/; Max-Age=31536000`(1년 [가정, wbs 3.2.1에서 확정])이고 `Domain`은 없다.
   - 쿠키가 없거나 모양·MAC이 틀릴 때만 새로 준다. '서명이 맞지 않으면 쿠키가 없는 것으로 본다'는 정본을 발급에도 똑같이 적용했다. 맞는 쿠키는 다시 주지 않는다.
   - 서명 키를 읽지 못하면 쿠키를 싣지 않고 응답을 그대로 보낸다. 들고 있던 쿠키의 키를 저장소 오류로 읽지 못해도 새로 주지 않는다. 새로 주면 사람의 쿠키 나이가 0으로 돌아가기 때문이다. 저장소에서 지운 kid의 쿠키(`exists()`가 거짓)는 쿠키가 없는 것으로 보고 새로 준다.
2. **queue-svc는 사전 검증과 로비 참가에서 쿠키를 읽어 발급 시각만 넘긴다.** `HmacFirstVisitCookies`가 MAC을 상수 시간으로 견준 뒤에만 칸을 읽는다. 키는 환경 값 `PEAKET_FIRST_VISIT_COOKIE_KEYS`(`{kid}:{키 글자}`를 쉼표로 이은 목록, 6개 [가정]까지)다. 서명 키는 90일마다 바꾸지만 옛 쿠키의 수명은 1년이라 옛 kid를 함께 받아야 한다. 없거나 틀리면 어느 환경이든 경고하고 쿠키를 읽지 않는다(시작은 막지 않고 `trust_first_visit_cookie_total{result="disabled"}`로 드러난다). 발급 시각이 지금보다 5초 [가정] 넘게 앞서거나 1년 + 1일 [가정]보다 오래됐으면 없는 것으로 본다. 쿠키 값은 저장하지 않고 로그에 싣지 않는다.
3. **허니팟은 내부 처리기 하나가 받고, 공개 경로는 저장소에 두지 않는다.** trust-svc는 `GET /internal/honeypot-hit`로 받는다(회차는 쿼리 `e`). 사람에게 보이지 않는 공개 경로(`/_t/` 아래 하나)는 설정으로 넣는다. 소비자 웹은 `PEAKET_HONEYPOT_PATH`, 대기실은 `VITE_PEAKET_HONEYPOT_PATH`이고, gw-fan이 그 경로를 내부 처리기로 잇는다. 값이 없으면 링크를 그리지 않는다.
   - 적중으로 세는 조건은 정본대로다(`Sec-Fetch-Site: same-origin`, `Sec-Purpose`에 `prefetch` 없음, `Next-Router-Prefetch` 없음). 응답은 조건과 상관없이 204·빈 본문이다.
   - 로그인한 적중(gw-fan이 넘긴 `x-user-pid`)은 `tr:hp:{pid}`를 24시간 [가정] 쓰고 `TrustVerdict`(source `HONEYPOT`)를 낸다. 쓰기는 응답 뒤로 미룬다. 회차를 모르면 표시만 쓰고 판정 기록은 내지 않는다(계약의 `eventId`가 필수다). 정밀도 표본 검토와 하한 계산은 BOT-070이다.
   - 판정 기록은 (pid, 회차)마다 24시간 [가정]에 한 번이고, pid 하나가 24시간에 기록하는 회차는 20개 [가정]까지다. pid마다 정렬 집합 키 하나(`tr:hp:{pid}:ev`, 점수는 시각)에 두고 Lua 한 번으로 세고 넣는다. 상한을 넘어도 응답은 204이고 표시(`tr:hp`)는 쓴다. trust-svc는 회차가 실제로 있는지 확인할 수단이 없어, 회차 값은 저장소의 회차 ID 형식(소문자 UUID)으로 좁힌다. 그 꼴이 아니면 회차를 모르는 것으로 본다.
   - pid 키 전환 기간에는 `x-user-pid-prev`를 우선해 판정의 읽기와 같은 pid에 쓴다.
4. **판정 기록·행동 신호는 버퍼를 지나 내보내고, 차면 버린다.** 공용 `TelemetrySink`(packages/platform)가 파드마다 1만 건 [가정]을 담고 500건 [가정]씩 보낸다. 한 묶음 안에서 토픽별로 모아 보낸다. 넘치거나 보내기에 실패한 기록은 `telemetry_dropped_total{record}`로 센다. 요청 처리는 기다리지 않고, 예외도 나오지 않는다(ADR-0141 결정 6). 실제 Kafka 클라이언트는 연결에 실패한 객체로 다시 연결하지 못하고 닫힌 포트에 81초를 끌어, `kafkaTelemetrySend`는 생산자 공장 함수를 받아 실패 때 새로 만들고, 연결 3초 [가정]·보내기 6초 [가정] 상한을 두며, 실패 뒤 5초 [가정]는 부르지 않고 바로 실패한다. 텔레메트리 클러스터 주소는 `PEAKET_TELEMETRY_KAFKA_BROKERS`다. 없거나 틀리면 어느 환경이든 경고하고 그 기능만 끈다(낼 기록은 버린 수로 센다). 브로커가 멈춰도, Kafka 클라이언트 모듈을 싣지 못해도 파드는 뜨고 판정은 이어진다. Avro 인코더(BAS-030) 전까지 값은 asyncapi 모양의 JSON 바이트다.
5. **판정 기록으로 내지 않는 것이 둘 있다.** 로그인 판정은 내지 않는다(계약의 `eventId`가 필수인데 회차가 없고, `source REALTIME`·`category PASS`면 `journeyId`도 있어야 한다). 사람 확인이 보류된 추가 검증 제출도 내지 않는다(실패로 세면 §13의 봇 쪽 하한이 부푼다). 둘 다 정규 로그 줄 `trust_score`에는 남는다.
6. **좌석 화면 요약은 구매 세션마다 하나다.** purchase-svc가 첫 직접 선택 홀드 본문의 `behavior`를 받으면 세션 상태의 `bs` 칸을 `HSETNX`로 잡고, 처음 잡았을 때만 `BehaviorSignal`(screen `SEAT`)을 낸다. 응답을 기다리지 않고, 실패해도 홀드를 막지 않는다. 결제 화면 요약(`PAYMENT`)의 내보내는 쪽(`BehaviorSignals.record`)은 함께 쓰게 두고, 부르는 쪽은 PRF-191이 잇는다.
7. **화면의 요약은 하나의 추적기로 잰다.** `apps/web/src/features/behavior-summary`가 수·간격·방향 엔트로피만 메모리에 두고 좌표와 입력 글자는 남기지 않는다. 좌석 화면은 첫 직접 선택 홀드에만 싣고, 같은 멱등 키의 재전송은 같은 값을 다시 싣는다. `windowMs` 밖의 칸에도 최댓값 [가정]을 둔다(이동·스크롤 수 100만, 엔트로피 3, 입력 간격 3,600,000ms, 스크롤 거리 10억 px). 계약에 `maximum`을 넣으면 깨지는 변경으로 잡혀(`request-property-max-set` 오류) 계약은 그대로 두었다. 추적기는 넘지 않게 멈추고, 받는 서비스는 넘는 칸을 내보낼 때 뺀다.

## 배포 단계의 필수 조건

이 저장소의 `deploy`·`infra`에는 아직 없다. 켜기 전에 함께 넣어야 한다.

- gw-fan: `PEAKET_HONEYPOT_PATH`의 값으로 `GET` 경로 하나를 trust-svc `/internal/honeypot-hit`로 잇고, 그 경로에서 팬 액세스 토큰을 검증해 `x-user-pid`(전환 기간에는 `x-user-pid-prev`도)만 넘기며, 바깥이 보낸 `x-user-*`와 `Cookie`를 지운다(docs/infra.md §4.1). 게이트웨이가 아직 없어 시험은 조건으로만 적어 둔다(HOT-400).
- gw-fan 호출 한도: 이 경로에 사람(pid, 로그인하지 않았으면 IP)마다 호출 한도를 건다(1분 60회 [가정]). 표시 쓰기가 Redis 명령을 쓰고, 회차 수 상한은 판정 기록만 줄이기 때문이다.
- 메시 허용 정책: trust-svc REST 포트를 부르는 신원을 gw-fan으로 줄인다(D-T36 ⑥). 지금 코드는 `x-user-pid`를 그대로 믿으므로, 이 둘이 없으면 위조할 수 있다.
- `www` 배포의 `/_t/*` 원본 요청 정책: `Sec-Fetch-Site`·`Sec-Purpose`·`Next-Router-Prefetch` 머리, 쿼리 `e`, 팬 쿠키를 원본까지 넘긴다.
- 대기열 API 배포의 사전 검증 경로: `__Host-peaket_fv` 쿠키를 원본까지 넘긴다. 공연 페이지 배포(`www`)에는 함수를 붙이지 않는다.
- 위 두 항목의 실제 전달은 BUILD_ORDER HOT-012(AWS 계정이 생겨 배포하는 단계)에서 확인한다.
- 값 있음은 배포 검사가 막는다: `PEAKET_FIRST_VISIT_COOKIE_KEYS`·`PEAKET_TELEMETRY_KAFKA_BROKERS`가 비었거나 틀리면 서비스는 시작하지만 그 기능만 꺼지므로(경고와 지표뿐이다), staging·prod 배포 검사가 값을 확인해야 한다.
- 대기열 API 배포의 사전 검증 경로 캐시 동작에 시청자 응답 함수를 붙이고, 진입 함수와 다른 키 값 저장소를 붙인다. `tools/edge/sync-kvs-keys.mjs --prefix fv`로 키를 넣는다.
- `PEAKET_FIRST_VISIT_COOKIE_KEYS`·`PEAKET_TELEMETRY_KAFKA_BROKERS`를 비밀 관리에서 넣는다.
- 소비자 웹 `PEAKET_HONEYPOT_PATH`는 실행 환경 값이다(빌드 때 미리 그린 화면에는 넣지 않고, 다시 그릴 때 읽는다).

## 대안

| 선택지 | 고르지 않은 까닭 |
| --- | --- |
| 쿠키를 진입 시청자 요청 함수에서 준다 | ADR-0223 결정 4. 진입 함수의 저장소에 키가 하나 더 들어가고, 저장소를 쓰는 함수가 다 같은 값을 읽게 된다 |
| 있는 쿠키는 어떤 값이든 건드리지 않는다 | 모양이나 MAC이 틀린 쿠키가 1년 동안 남아 그 사람은 쿠키 나이 신호를 얻지 못한다 |
| 허니팟 경로를 코드 상수로 둔다 | 공개 저장소에서 경로를 읽어 피해 갈 수 있다(POL-006). 값이 공개되면 잡는 비율이 떨어진다 |
| 처리기를 공개 경로 그대로 trust-svc에 연다 | 공개 경로가 trust-svc 설정과 라우트에도 퍼진다. 내부 경로는 값이 새어도 메시 밖에서 닿지 않는다 |
| 판정 기록을 요청 안에서 Kafka로 기다려 보낸다 | Kafka가 늦으면 판정이 늦어진다(§4.1 ⑤, NFR-001) |

## 결과

- 쿠키 나이 신호가 켜져 `AgeScore`가 값을 낸다. 키 없는 환경에서는 쿠키가 없는 것으로 판정한다.
- 판정 기록과 행동 신호가 나가므로 뒤의 재평가·관제·조사 적재가 받을 수 있다.
- 허니팟 적중의 표시와 지표가 쌓인다.

### 되돌릴 조건

- Q-T57에서 버퍼 1만 건이 평소에 꽉 차면 값을 다시 정한다.
- 정본 표의 1년이 wbs 3.2.1에서 바뀌면 `Max-Age`와 받는 쪽 상한을 함께 고친다.

## 남는 한계

- 함수와 키 값 저장소는 실제 CloudFront에서 돌려 보지 못했다(HOT-012, ADR-0223과 같다).
- JSON 바이트는 Avro로 바뀌기 전까지 소비자가 받지 못한다. BAS-030 전에 소비자를 켜지 않는다.
- 결제 화면 행동 요약은 결제 시도 API가 없어 아직 나가지 않는다(PRF-191, HOT-358).
- 재평가가 `SEAT`·`PAYMENT`를 건너뛰는 일과 `trust.behavior_raw` 행 수(B-T19 ④)는 작업자 `trust-reassess`(BUILD_ORDER OPS 구간) 전에는 볼 수 없다.
- `Sec-Fetch-*`를 보내지 않는 스크립트의 허니팟 접근은 기록되지 않는다(Q-T40 ⑤).
- 브라우저 안의 스크립트가 같은 출처로 부르는 요청은 기록 조건으로 가리지 못한다(정본의 기록 조건을 그대로 따랐다. 바꾸려면 정본을 고칠 결정이 필요하다).
- 쿠키 없음은 값 없음이라 위험 0이어서 쿠키를 갓 받은 브라우저만 불리하고, 오래된 쿠키를 나눠 쓰는 일은 가리지 못한다(소유자 결정 대기). 이 결정 전에는 비공개 규칙에서 `AgeScore`의 쿠키 몫 가중치를 0으로 둔다(bot-defense §4.4).
- 연결 시간 상한을 넘겨 버린 생산자의 실제 연결이 그 뒤에 늦게 맺어지면, 끊기가 끝날 때까지 그 연결이 잠시 남는다.
- 대기실의 허니팟 경로는 빌드 값이라 공개 JS 안에 들어간다(정적 묶음이라 실행 환경에서 읽을 수 없다). 값을 바꾸려면 다시 빌드한다.
- 도착 시각 쿠키(`HmacArrivalCookies.fromEnv`)는 ADR-0223 결정 5대로 staging·prod에서 시작에 실패한다. 최초 방문 쿠키·텔레메트리와 기준이 다르다.
