# ADR-0165: 저장소를 14개에서 4개로 줄인다 — 모노레포 `peaket`과 GitOps·조직 공용 워크플로·비공개 부하 시험(소유자 결정, 2026-10-30)

- **상태**: 채택 (2026-10-30. 소유자가 "저는 이거 모노레포로 관리하고 싶은데요. 합리적이지 않은건가요? 왜냐면 포트폴리오로 쓸거거든요"라고 묻고, 저장소 4개 안을 "4개로(추천)"로 정했다. 저장소 수와 각 저장소에 담는 범위는 소유자 결정이다. 폴더 구성, CI 구조, 계약 호환 기준, 권한 경계, 작업 가지 한도, 시연 바꾸기는 추천 적용이다.) ADR-0016을 대체한다. 보완(2026-10-30): 0167(`peaket`에 스펙 주도 개발 기록 `openspec/`과 브라우저 확인 스킬 `.claude/skills/peaket-browser-check`를 더함).
- **관련**: ADR-0016(폴리레포 하이브리드, 이 ADR이 대체한다), ADR-0054(배포 파이프라인), ADR-0074(git flow), ADR-0079 결정 21(프론트엔드 패키지 게시), ADR-0096(서비스 분리 효과 비교의 합본 빌드), ADR-0100(관제 위젯 패키지), ADR-0128 중간-112(저장소 14개의 근거), POL-026(봇 시뮬레이터 비공개), [docs/devops.md](../devops.md) §2·§3·§4, [docs/architecture.md](../architecture.md) §10

## 맥락

- 저장소 14개는 서비스를 나눈 기술 근거가 아니었다. 여러 가상 팀이 저장소·코드 주인·배포 경계를 나눠 일하는 거버넌스와, 저장소를 건너는 변경을 직접 보이려는 포트폴리오 목표였다(ADR-0128 중간-112). 같은 결정에서 모노레포(코드 전부를 저장소 하나에 폴더로 나눠 담는 방식)로도 경로별 CI, 서비스별 이미지, 폴더별 코드 주인으로 독립 배포와 팀 경계를 보일 수 있다고 적었다.
- 한 사람이 일하므로 가상 팀 경계 뒤에 실제 소통 구조가 없다(architecture §10). 기술 검토도 처음에는 저장소 14개를 '과함'(옛 높음-04)으로 짚었다.
- 공개 재현이 어려웠다. GitHub Packages는 공개 패키지도 설치할 때 토큰이 필요해, 저장소 하나를 받은 사람이 바로 빌드하지 못했다. 그래서 공개 저장소를 모아 잇는 작업 공간 스크립트를 따로 두어야 했다.
- 소유자는 포트폴리오를 읽는 사람이 한곳에서 전체를 보게 하려고 모노레포를 원했다.

## 결정

1. **저장소는 4개다(소유자 결정)**

   | 저장소 | 공개 | 담는 것 | 따로 두는 이유 |
   | --- | --- | --- | --- |
   | `peaket` | 공개 | 모노레포. 문서, 계약 원본, 화면 앱, 서버와 작업자, 공용 패키지, 데이터 모델, 인프라 코드, 점검 도구 | — |
   | `peaket-gitops` | 공개 | 클러스터 상태(환경 오버레이, 공용 Helm 차트, Kyverno 정책, 변경 동결 달력, 게이트웨이 공통 정책, 경보 규칙) | git flow에서 `main`은 릴리스·핫픽스 병합만 받는데, 배포 판 올림은 수시로 들어가야 한다. Argo CD 문서도 설정 저장소를 소스 저장소와 떼어 두기를 '강력히 추천'한다. 빌드 없이 매니페스트만 바꿀 수 있고, 배포 이력이 깨끗하며, 판 올림 커밋이 빌드를 다시 부르는 무한 반복을 막는다는 이유다(2026-10-30 확인) |
   | `.github` | 공개 | 조직 공용 재사용 워크플로(빌드·서명·출처 증명·승격·릴리스), 이슈·PR 양식, 조직 첫 화면 소개(`profile/README.md`) | 서명 인증서에는 '소스 저장소'와 '서명한 빌드 절차와 그 판'이 따로 들어간다(Sigstore Fulcio OID 문서의 Build Signer URI·Build Signer Digest, 2026-10-30 확인). 절차를 다른 저장소에 두고 검토한 커밋 SHA로 고정해야, 입장 검사가 '검토한 그 판의 절차로 만든 이미지만'을 기계로 확인한다. 같은 저장소에 두면 절차의 판이 코드 커밋과 같아져 고정할 수 없다. 조직 첫 화면 소개는 공개 `.github` 저장소에만 둘 수 있다(GitHub 문서, 2026-10-30 확인) |
   | `peaket-loadtest` | 비공개 | k6 시나리오, 합성 봇 시뮬레이터, 카오스 실험 스크립트 | 봇 시뮬레이터는 공개하지 않는다(POL-026). 공개 저장소 안에서 폴더 하나만 숨길 수는 없다 |

   - 운영 계정을 실제로 만들면(wbs 2.11.2) 실제 값이 든 부록과 운영 이슈를 둘 비공개 운영 저장소가 하나 더 생긴다(ADR-0153). 포트폴리오 기간의 저장소는 위 4개다.

2. **`peaket`의 폴더(추천 적용)**: 지금 문서 저장소를 그대로 뿌리로 쓴다. 그래서 문서 경로와 링크는 바뀌지 않는다.

   ```text
   peaket/
     00-summary.md, planning/, design/, docs/, review/, wbs/, guide/   문서(지금 그대로)
     docs/api/     계약 원본(openapi·asyncapi·proto·avro, 지금 그대로)
     apps/         화면 앱(web, partner, scanner, console-host, forensics)과 관제 원격 위젯(widgets/queue, widgets/purchase)
     services/     서버에서 도는 배포 단위 전부: 서비스 10개, 스트림 작업자, 작업(CronJob·Job) 이미지
     packages/     공용 패키지: 화면용(ds, telemetry, validation, api-client, console-contract, seatmap, config),
                   서버용(platform), 계약에서 만든 코드(contracts. Pact 파일은 contracts/pacts)
     data/         dbt 모델, rt 표·뷰 이전 파일
     infra/        Terraform(modules, stacks)
     tools/        doc-check, perf-ledger
     .github/      이 저장소의 워크플로(조직 공용 재사용 워크플로를 커밋 SHA로 부른다)와 CODEOWNERS
   ```

   - 코드 주인은 폴더 단위로 가상 팀 아홉에 나눈다(뿌리의 CODEOWNERS, architecture §10 표).
   - 내부 패키지는 게시하지 않는다. `@peaket/*` 의존성은 `workspace:` 프로토콜로만 적는다. 이 프로토콜은 작업 공간 밖의 패키지로 풀리기를 거부한다(pnpm 문서, 2026-10-30 확인). 그래서 공개 레지스트리에 같은 이름이 올라와도 설치되지 않는다. 린트가 이 표기를 검사한다.
   - 공개 재현: `peaket` 하나를 받아 토큰 없이 설치하고 빌드한다. 작업 공간 스크립트는 없앤다.

3. **CI는 항상 도는 워크플로 하나가 바뀐 범위만 고른다(추천 적용)**
   - 경로 필터로 건너뛴 워크플로는 필수 검사가 '대기'로 남아 PR 병합을 막는다(GitHub 워크플로 문법 문서, 2026-10-30 확인). 그래서 `ci.yml`은 모든 PR에서 돈다.
   - 첫 잡이 바뀐 범위를 고른다. 자바스크립트 작업 공간은 Turborepo `--affected`로 고른다. 현재 가지에서 바뀐 패키지와 그것에 기대는 패키지가 고른 범위다(Turborepo 문서, 2026-10-30 확인). 문서·계약·데이터·인프라는 `git diff --name-only`를 읽는 저장소 안 스크립트로 고른다. 제3자의 '바뀐 파일' 액션은 쓰지 않는다(tj-actions/changed-files 탈취, CVE-2025-30066).
   - 유형별 잡(서비스, 화면, 계약, 데이터, IaC, 문서)이 그 결과에 따라 돈다. 마지막 `ci-summary` 잡과 `branch-policy`가 필수 검사다.

4. **계약 호환은 '운영에 나간 판'과도 견준다(추천 적용)**
   - 저장소가 하나면 한 PR이 계약과 제공자·소비자 코드를 함께 바꿀 수 있고, 같은 커밋끼리의 검사는 통과한다. 그런데 운영 배포는 배포 단위마다 따로 나가므로, 배포 사이에 옛 판과 새 판이 함께 돈다.
   - 그래서 `contract-check`는 대상 가지와 함께 마지막 출시 태그(운영 판)와도 견준다. `buf breaking`, OpenAPI·AsyncAPI 차이, Avro 호환(지난 출시 태그의 스키마를 모두 올린 로컬 레지스트리), Pact(제공자가 지금 소비자의 Pact와 마지막 출시 태그의 소비자 Pact를 모두 검증)가 대상이다.
   - 호환을 깨야 하면 넓히기 → 옮기기 → 좁히기를 출시를 나눠 한다. 깨짐 기준은 docs/api/guidelines.md §1이다.

5. **출시는 저장소 하나에 릴리스 가지 하나다(추천 적용)**
   - git flow(ADR-0074)는 그대로다. `peaket`의 `release/X.Y.Z`가 시스템 전체의 출시이고, 태그 `vX.Y.Z`가 시스템 판이다.
   - 후보 빌드는 마지막 출시 태그 뒤에 바뀐 배포 단위만 새 이미지로 만든다. 승격 PR은 그 다이제스트만 바꾼다. 그래서 워크로드별 배포(ADR-0054)는 그대로다.
   - 내부 패키지를 게시하지 않으므로 Changesets는 쓰지 않는다. PR 제목의 범위(`feat(queue): …`)에는 폴더의 가상 팀 이름을 적는다.

6. **권한 경계는 저장소 대신 환경과 빌드 절차로 나눈다(추천 적용)**
   - AWS 역할의 신뢰 조건은 지금 `repo:<조직>/<저장소>:environment:<환경>`이다. 이를 조직의 OIDC 주체 사용자화(`include_claim_keys`: `repo`, `context`, `job_workflow_ref`)로 바꿔 '저장소·환경·부른 재사용 워크플로'까지 고정한다(GitHub OIDC 문서, 2026-10-30 확인). 그래서 이미지 게시 역할은 `.github`의 `build-image.yml` 게시 잡만 받는다.
   - 열린 작업 가지 한도는 '저장소마다 3개'에서 '가상 팀마다 3개'로 바꾼다 [가정]. 팀은 PR이 바꾼 파일의 CODEOWNERS 주인으로 센다.

7. **저장소를 건너는 변경 시연을 '운영 판과의 호환 검사' 시연으로 바꾼다(추천 적용)**: 계약을 깨는 변경과 양쪽 코드를 한 PR에 넣는다. 같은 커밋끼리의 검사는 통과하지만, 운영 출시 태그와 견주는 검사가 막는다. 이 과정을 녹화와 재현 스크립트로 보인다(wbs 0.4.3, docs/verification.md §7).

## 검토한 대안

- **저장소 14개 유지**: 저장소를 건너는 변경과 저장소별 권한을 직접 보일 수 있다. 하지만 혼자 하는 프로젝트에서는 연출에 가깝다. 읽는 사람이 한곳에서 보지 못하고, 공개 재현에 따로 스크립트가 든다. 기각.
- **저장소 2개(모노레포와 비공개 부하 시험)**: GitOps를 같은 저장소에 두면 판 올림이 git flow의 `main` 규칙과 부딪힌다. 빌드 절차를 같은 저장소에 두면 서명 절차의 판을 고정할 수 없다. 기각.
- **저장소 3개(조직 공용 워크플로를 모노레포에 합침)**: 같은 저장소의 재사용 워크플로로도 출처 증명은 만든다. 다만 절차를 바꾸는 변경과 코드를 바꾸는 변경을 구조로 떼어 놓지 못하고, 그 빈자리를 사람 검토로 메워야 한다. 혼자라 그 검토는 형식적이다. 기각.
- **경로 필터를 단 워크플로 여러 개**: 건너뛴 필수 검사가 대기로 남아 병합을 막는다. 기각.

## 결과와 트레이드오프

- 읽는 사람은 링크 하나로 문서와 코드를 함께 보고, 토큰 없이 빌드한다. 커밋 하나가 시스템 전체의 한 시점이라 v0와 v1을 같은 커밋으로 견주기 쉽다. ADR-0096의 합본 빌드에서 '여러 저장소의 커밋을 묶는 일'이 없어진다. 한 프로세스로 묶는 빌드와 갈래 스위치는 그대로 남는다.
- 잃는 것: 저장소를 건너는 변경(계약 게시 → 판 올림 PR → 각자 CI)과 저장소별 권한·규칙 세트를 직접 보이는 것.
- 저장소 쓰기 권한이 모든 서비스 코드에 걸친다. 이미지 게시 역할도 모든 서비스의 레지스트리에 쓸 수 있다. 서비스마다 게시 권한을 나누지 않는 것은 남는 위험이다. 서명 절차 고정과 출시 가지 조건(devops §4.3)으로 줄인다.
- 출시 가지가 하나라, 한 서비스의 출시가 막히면 다른 서비스 출시도 붙잡힌다. 릴리스 플래그(devops §5.4)와 핫픽스로 버틴다.
- 바뀐 범위 고르기가 틀리면 검사가 빠진다. 계약·플랫폼 패키지처럼 넓게 쓰이는 것이 바뀌면 그것에 기대는 모두를 돌린다(Turborepo의 의존 그래프). 문서·계약·데이터·인프라의 경로 규칙은 시험 D-T47로, 운영 판과 견주는 계약 검사는 D-T48로 확인한다(devops §14).
- WBS 작업 일수는 바꾸지 않았다. 작업 설명만 저장소 4개에 맞췄다.

## 되돌릴 조건

- 실제 팀이 생겨 팀마다 저장소 권한을 나눠야 하면, 그 팀의 폴더를 저장소로 떼어 내는 새 ADR을 쓴다.
- PR 검사가 10분 목표(devops §3.4)를 바뀐 범위 고르기와 원격 캐시로도 지키지 못하면 빌드 도구를 다시 본다.
