# ADR-0170: 화면 퍼블리싱을 기능 구현보다 먼저 한다 — 목업 데이터로 69개 화면을 그리고 연결은 원래 단계에서(소유자 요청, 2026-10-31)

- **상태**: 채택 (2026-10-31. 소유자가 "일단 초기 프로젝트 세팅을 해서 PEAKET 전체 화면 디자인부터 퍼블리싱하고 전체 페이지를 구성해주세요"라고 요청했다. 순서만 바꾸는 결정이라 세부는 추천 적용이다) 2026-10-31 소유자 "추천대로 진행": 퍼블리싱 때 보드를 따르고 소유자 확인으로 남긴 다섯 곳을 정리했다. 대기열 일시정지의 예상 대기는 frontend §3.4대로 숨기고 '잠시 멈춤'으로, 현장 운영의 입장 기록 마감 예정은 d5대로 22:00, SCR-021 휴대폰 요약의 토스페이먼츠 셀러 상태는 처음 판매 승인 전이면 데스크톱 보드·d5대로 '승인 필요', 승인 뒤면 '부분 승인'(셀러가 부분 승인 전이면 판매 승인을 못 함), 키트 변수 `--scrim`·`--heat-ink`는 tokens.json 의미 토큰 `scrim`·`heat.ink`로, 소비자 웹 공용 티켓 목업의 좌석은 보드 표기('R구역 12열 7번')로 맞췄다(R-205, openspec 변경 align-screens-with-canon). 2026-11-01(정합 점검, ADR-0175 해설서 검토): 제목과 본문의 '69개 화면'은 결정 시점의 수이고, 지금은 SCR-070·071을 더해 71개다(docs/design/d5-screen-blueprint.md §2, ADR-0171).
- **관련**: ADR-0040(SEED), ADR-0063·0066(화면 개편·피드백), ADR-0079(프론트엔드 RADIO), ADR-0165·0169(모노레포), ADR-0167(스펙 주도 사이클), [docs/wbs/wbs.md](../wbs/wbs.md) §1 '실행 방식', [docs/BUILD_ORDER.md](../BUILD_ORDER.md), [docs/frontend.md](../frontend.md) §2, [docs/design/d5-screen-blueprint.md](../design/d5-screen-blueprint.md)

## 맥락

- 빌드 순서(wbs §1, BUILD_ORDER)는 최소 기반 → v0 베이스라인 → 증명 핵심 → 나머지 기반 → 핫패스 순이다. 화면 앱 골격(wbs 0.6.x)은 '나머지 기반'에, 화면 구현(wbs 2.10.x 등)은 핫패스 단계에 있다.
- 화면 설계는 끝나 있다. 69개 화면의 셸·와이어프레임·상태 표(docs/design/d5), 화면별 컴포넌트·상태·접근성(d3), 토큰과 컴포넌트 카탈로그(d2, tokens.json)가 정본이다.
- 퍼블리싱(디자인을 실제 HTML·CSS·컴포넌트로 옮기는 일)은 서버·계약 코드 생성·실시간 연결 없이 목업 데이터로 끝난다. 화면 단계의 나머지 일(데이터 연결, 실시간, 결제·본인확인 SDK, 보안 헤더, 성능 예산, 시험)은 화면 모양과 따로 할 수 있다.

## 결정

1. **화면 앱 골격과 69개 화면 퍼블리싱을 지금 한다(소유자 요청)**. 기능 구현 순서(최소 기반 → v0 → 증명 핵심 → …)는 그대로다. 이 일은 BUILD_ORDER에 끝난 단계로 더하고, 겹치는 단계의 설명에 '퍼블리싱은 끝남, 남은 것은 연결'을 적어 같은 화면을 다시 그리지 않게 한다(추천 적용).
2. **구조와 판은 정본대로 둔다(추천 적용)**. 앱 나눔·프레임워크·판(frontend §2.2·§2.3)을 이번에 그대로 세워, 뒤 단계가 구조를 바꾸지 않고 데이터만 잇게 한다. 지금 하지 않는 것(Cache Components·CSP nonce, Module Federation 원격 적재, PWA, 다국어 주소, 린트·시각 회귀·성능 예산)은 정본의 그 단계에서 한다.
3. **목업과 상태 고르기는 연결 단계에서 걷어 낸다(추천 적용)**. 화면은 앱 안의 합성 목업에서 읽고, `?state=`로 캔버스 보드의 상태(없으면 d5 상태 표의 상태)를 고른다. 화면·상태 목록 페이지(`/preview`)는 개발 서버에서만 열린다. 데이터를 잇는 단계가 그 화면의 목업과 상태 고르기를 지운다.
4. **디자인 캔버스를 시각 기준으로 옮긴다**. 소유자가 넘겨준 캔버스(보드 417개, 공용 키트 `peaket.css`)의 보드를 그대로 옮기고, 키트를 `@peaket/ds`의 CSS로 둔다. 보드와 정본 문서가 다르면 보드를 따르되(법정 고지는 POL 원문), 다른 곳은 목록으로 남긴다. 캔버스 보드는 저장소에 복사하지 않는다(추천 적용).

## 결과

- 좋아지는 점: 포트폴리오를 보는 사람이 서버 없이 전체 화면을 볼 수 있다. 뒤 단계는 화면을 다시 그리지 않고 데이터 연결과 시험에 집중한다. 화면을 그리며 정본의 빈 곳(문구·상태·컴포넌트 변형)을 일찍 찾는다.
- 나빠지는 점: 목업이 실제 응답 모양과 어긋날 수 있다(계약 보강 wbs 0.2.3 전). 연결 단계에서 목업을 걷어 내며 맞춘다. 화면 코드가 먼저 생겨, 감독 루프의 작업 공간 골격 단계(FND-030)와 뿌리 설정 파일을 함께 고친다. 병합 때 맞춘다.

## 되돌릴 조건

- 연결 단계에서 퍼블리싱한 화면 구조(경로·FSD 층·컴포넌트 경계)를 절반 넘게 다시 짜야 하면, 남은 화면의 퍼블리싱은 연결과 함께 하는 원래 순서로 돌아간다.
