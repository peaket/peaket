# ADR-0044: 토스페이먼츠·포트원 동시 운영 (결제 시도마다 결제사를 고르고, 승인 요청 뒤에는 고정하며, 장애 전환은 운영자가 승인한다)

- **상태**: 채택 (2026-10-13 수립. 소유자 지시 "토스와 포트원 둘다 가능하도록 설계해야해요"에 따른 설계이고, 세부 규칙은 추천 적용(2026-10-13)이다. ADR-0029에 결제사 선택 규칙과 포트원 결제 접수 계약을 더한다. ADR-0036 결정 1 표의 포트원 API 호출 한도 행에 적힌 전제 '포트원 채널은 호환·계약 테스트용이라 피크를 받지 않는다'는 결정 6이 대체한다. 좌석을 먼저 확정하고 승인하는 2단계 원칙(ADR-0015)은 두 결제사 모두 그대로다) 2026-10-14 추천 적용(ADR-0062 결정 33): 판매 승인 때 공연 지정이 비어 있으면 그 시점의 플랫폼 기본값을 공연 지정으로 저장한다(결정 4의 '지정이 없으면 플랫폼 기본값'은 판매 승인된 공연에는 쓰이지 않는다). 2026-10-20(ADR-0073, 3차 전수 점검): 결정 5의 'commander 2인 승인'은 명령 6의 2인 상호 승인(commander 요청과 요청자 아닌 operator 이상 1인 승인, POL-021·docs/features/control-tower.md §3)으로 읽는다. 2026-10-21: 본문의 REST 경로는 ADR-0081의 옛 경로 대응표로 새 경로를 읽는다(경로 이름 규칙 점검). 2026-10-26(4차 점검 3부): 두 결제사의 결제창 결과는 기기와 관계없이 페이지 이동으로 받는다(포트원 `forceRedirect: true`, ADR-0079 결정 7). 그래서 '남는 한계' 4의 리디렉션은 모든 포트원 결제이고, P-T33에서 결제 토큰이 쿼리로 오지 않으면 모바일 결제만 막지 않고 능력 플래그로 포트원을 고르지 않으며, ADR-0079 되돌릴 조건대로 포트원의 결과 받기 방식을 다시 본다(docs/features/payment.md §2.2·§11).

## 맥락
- 소유자 질문(2026-10-13): "결제사를 고르는 로직이 왜 전략 패턴이 아니라 어댑터 패턴인가." 검토 결과, ADR-0029가 어댑터라고 부른 부분은 결제사마다 다른 API를 공통 포트로 바꾸는 변환이라 이름은 맞았다. 그러나 결제사를 고르는 규칙은 어디에도 없었다. 정해진 것은 환경별 연결뿐이었다(자동 시험과 부하 시험은 시뮬레이터, 운영은 토스). 같은 날 소유자가 "토스와 포트원 둘 다 가능하도록 설계해야 한다"고 지시했다.
- 포트원 결제를 실제로 받을 수 없게 만드는 빈칸이 있었다.
  - 결제 접수 API가 토스 값(`paymentKey`, `amount`)만 받고 결제사를 구분하는 값이 없었다. 포트원 승인에는 결제 ID와 결제 토큰이 필요하다.
  - ADR-0036은 포트원 채널이 '호환·계약 테스트용이라 피크를 받지 않는다'고 전제했다. 포트원이 실제 결제를 받으면 이 전제가 깨진다.
  - 쉬운 설명서 5편은 필체 수정 때 '포트원으로 즉시 전환할 수 있다'로 바뀌어 있었다. 원래 문장은 '같은 방식으로 붙일 수 있다'였다.
- 2026-10-13에 두 결제사 공식 문서로 다시 확인한 것:

| 항목 | 토스페이먼츠 | 포트원 V2 |
| --- | --- | --- |
| 결제창 | SDK v2 한 주소(`js.tosspayments.com/v2/standard`). '결제위젯'은 '주문서형·결제창형 결제'로 이름이 바뀌었다 | 브라우저 SDK(`cdn.portone.io/v2/browser-sdk.js`, npm `@portone/browser-sdk`). 결제수단과 채널을 가맹점이 지정한다 |
| 인증 뒤 돌아오는 값 | 성공 URL 쿼리의 `paymentKey`·`orderId`·`amount`(주문서형은 `paymentType`도) | 응답의 `paymentId`·`txId`(결제 시도 ID)·`paymentToken`(수동 승인 채널만). 리디렉션 방식은 결과가 쿼리로 온다. 공식 문서는 주요 필드만 표로 싣고 전체는 응답 형식 문서를 가리키며, 공식 React Native SDK는 리디렉션 쿼리 전체를 응답 객체로 바꾼다 |
| 서버 승인 | `POST /v1/payments/confirm`(paymentKey·orderId·amount) | `POST /payments/{paymentId}/confirm`. `paymentToken`은 필수이고 `txId`·`totalAmount`·`currency`·`isTest`는 검증용이다 |
| 주문 식별자 재사용 | `orderId`는 승인이나 취소가 된 뒤에만 다시 쓸 수 없다(`DUPLICATED_ORDER_ID`) | 같은 `paymentId`로 여러 번 결제를 시도할 수 있고 성공은 한 번뿐이다 |
| 대사용 조회 | 거래 조회 `GET /v1/transactions`(기간의 승인·취소 전체, 응답에 최대 60초) | 결제 대용량 다건 조회 `GET /payments-by-cursor`(기간 내 전체 결제 건) |
| 가상계좌 환불 | 취소 API에 환불 계좌를 넘긴다 | 취소 API의 `refundAccount` |
| 구매자 정보 | 결제창에 필수로 넘기지 않는다 | 하위 결제사에 따라 이메일·전화번호가 필수일 수 있다 |

- 두 결제사 모두 서버가 승인 API를 부르기 전에는 돈이 움직이지 않는다(POL-013). 그래서 승인 요청을 보내지 않은 결제 시도는 버리고 다른 결제사로 다시 시도해도 이중 결제가 생기지 않는다. 이 성질이 이번 결정의 안전 근거다.

## 결정
1. **변환은 어댑터, 고르기는 전략.** 결제사별 구현은 지금처럼 어댑터다. 외부 API를 `PaymentGatewayPort`로 바꾸고, 포트에 결제창 값을 만드는 `checkout()`을 더한다. 결제 시도마다 어댑터를 고르는 결제사 선택기(`PaymentGatewaySelector`)를 payment-svc에 둔다. 고른 어댑터는 같은 포트로 쓰이므로 이 구조는 전략 패턴이고, 각 어댑터가 전략 구현체를 겸한다. 주문 Saga(purchase-svc)는 어느 결제사인지 모른 채 payment-svc를 부르고, payment-svc는 결제 기록의 결제사 값으로 어댑터 등록부에서 어댑터를 찾는다. 결제사에 관한 지식(능력 플래그, 채널, 결제창 값, 상한)은 payment-svc 한곳에 모은다.
2. **결제 시도마다 고르고, 승인 요청 뒤에는 고정한다.**
   - 결제사는 결제 시도를 시작할 때(결제창을 열기 직전, `POST /v1/orders/{orderId}/payments`) 고른다. purchase-svc가 결제 시도를 만들고 payment-svc에서 결제사와 결제창 값을 받아 시도에 기록한다.
   - 주문당 활성 결제 시도는 1건이다(payment §4.2 1·2). 결제 접수 전의 시도는 새 시도가 대체하고, 새 시도는 그때의 규칙으로 결제사를 다시 고른다.
   - 결제 접수(`POST /v1/orders/{orderId}/payments/accept`)로 승인 요청 단계에 들어가면 그 주문은 기록된 결제사에 고정된다. 승인, 재시도, 조회, 취소, 환불, 웹훅, 대사는 모두 그 결제사로만 간다. 승인 요청을 보낸 결제를 다른 결제사로 옮기지 않는다.
   - 승인 멱등키 `confirm-{orderId}`는 그대로다. 주문당 승인 요청은 한 번이기 때문이다. 토스 `orderId`는 주문 식별자를 그대로 쓰고, 포트원 `paymentId`는 주문마다 하나(`pay-{orderId}`)를 쓴다. 두 결제사의 재사용 규칙(맥락 표)이 같은 주문의 재시도를 허용하고 성공은 한 번으로 막는다.
3. **선택 규칙(POL-036).** 결제사 선택기는 다음 순서로 고른다.
   1. 그 공연에 결제사 전환(결정 5)이 켜져 있고 대체 결제사가 있으면 대체 결제사.
   2. 아니면 공연에 지정된 기본 결제사(결정 4).
   3. 공연 지정이 없으면 플랫폼 기본값(기본 토스페이먼츠, 대체 포트원). 플랫폼 기본값은 설정 파일에 두고 배포로만 바꾼다.
   - 고른 결제사의 채널이 서버 승인을 지원하지 않거나 비활성이면 결제 시도를 만들지 않고 신규 결제 일시 정지 안내(payment §9)로 응답하며 경보를 낸다. 다른 결제사로 몰래 넘기지 않는다. 결제사는 운영자가 정한 규칙으로만 바뀐다.
   - 포트원은 구매자가 고른 결제수단을 받는 채널을 고른다. 쓰는 채널은 모두 수동 승인이 켜져 있어야 한다.
4. **공연별 결제사 지정.** 운영자가 운영 명령 12 '결제사 지정'(POL-021 B)으로 공연의 기본 결제사와 대체 결제사를 정한다. 1인 승인이고 온세일 윈도우(POL-028) 밖에서만 실행된다. dry-run은 바뀌는 동시 입장 목표 상한(결정 6)을 보여 준다. 기본과 대체는 달라야 하며 대체는 없을 수 있다. 공연 정보의 주인인 core-svc가 지정을 저장하고, payment-svc와 admission-ctrl은 설정 이벤트로 받는다. 파트너는 결제사를 고르지 않는다. 가맹점 계약·수수료·한도는 플랫폼의 책임이고, 결제사가 동시 입장 목표 상한을 바꾸기 때문이다.
5. **장애 시 결제사 전환은 운영자가 승인한다.** 결제사 장애 때 운영자가 명령 6(감내 모드 전환, commander 2인 승인)으로 결제 감내 모드 '대체 결제사 전환'을 켠다(POL-029). 범위는 공연 하나 또는 플랫폼 전체다.
   - 새 결제 시도부터 대체 결제사로 간다. 이미 접수된 결제는 원래 결제사의 재시도 큐에서 승인 기한 안에 처리되거나 과금 없이 만료된다(payment §9).
   - 전환 전에 원래 결제사 결제창을 연 사람이 그 결제창에서 실패하면, 같은 주문에서 다시 결제할 때 새 시도가 대체 결제사로 열린다(홀드 시간 안에서).
   - 시스템은 결제사 서킷 브레이커가 열린 상태가 이어지면 전환을 후보로 추천만 하고 스스로 켜지 않는다(POL-021 C-3). 해제하면 새 시도부터 기본 결제사로 돌아간다.
6. **결제사별 동시 입장 목표 상한.** admission-ctrl은 공연의 현재 결제사(전환 반영) 채널 상한으로 그 공연의 동시 입장 목표 상한을 정한다. 공식은 지금의 합산 상한과 같은 '승인 상한 ÷ 0.06 TPS/명'(docs/architecture.md §9.5)이다. 같은 결제사를 쓰는 공연들의 목표 합도 그 결제사 상한 안에 둔다.
   - 추정 상한 기준(ADR-0036)으로 토스 300 TPS는 5,000명, 포트원 채널 하나 초당 50건은 약 830명이다.
   - 결제사 지정이나 전환으로 상한이 낮아지면 admission-ctrl이 바로 목표를 낮춘다. 용량을 줄이는 방향이라 자동 실행이 허용된다(POL-021 C-3). 높아지는 방향은 지금처럼 AIMD가 천천히 올린다.
   - 이 결정이 ADR-0036 결정 1 표 포트원 API 호출 한도 행의 '피크를 받지 않는다' 전제를 대체한다. 포트원이 받는 양은 상한으로 묶이고, 그 상한이 추정이라는 점은 그대로다.
7. **결제 접수 계약.** 결제 시도 응답은 결제사와 결제창 값을 준다. 토스는 클라이언트 키, 구매자 키(계정 ID가 아닌 무작위 값), `orderId`, 주문명, 금액, 성공·실패 URL이다. 포트원은 상점 ID, 채널 키, `paymentId`, 주문명, 금액, 통화, 리디렉션 URL, 채널이 요구하는 구매자 항목이다. 결제 접수 본문은 `pg` 값으로 갈린다.
   - 토스: `paymentKey`, `amount`. 서버가 주문 금액과 대조한다(지금과 같다).
   - 포트원: `paymentId`, `paymentToken`, `txId`. `paymentId`는 결제 시도 응답 값과 같아야 한다. 금액은 클라이언트에게 받지 않고, 승인 API에 서버 금액을 `totalAmount`로 넣어 포트원이 대조하게 한다.
   - `pg`가 활성 결제 시도의 결제사와 다르면 409로 거절한다. 늦게 온 이전 시도의 접수도 여기서 막히고, 승인 요청을 보내지 않았으므로 과금되지 않는다.
   - 포트원 결제 토큰은 승인 결과가 정해질 때까지만 접수 Outbox와 결제 원장에 두고, 결과가 정해지면 지운다. 로그, 응답, 분석 이벤트에는 넣지 않는다.
8. **웹훅·대사·취소의 결제사 확인.** 웹훅은 들어온 경로의 결제사와 결제 기록의 결제사가 같을 때만 보조 신호로 쓴다. 다르면 무시하고 보안 이벤트로 기록한다. 일일 대사는 결제사별로 돌린다(토스 거래 조회, 포트원 결제 대용량 다건 조회). 취소와 환불은 결제 기록의 결제사로 보내고, 가상계좌 환불 계좌는 두 결제사 모두 취소 API 파라미터로 바로 넘긴다(저장하지 않음, POL-014).
9. **화면과 브라우저 보안.** 주문·결제 화면(SCR-011)의 결제 프레임(CMP-027)은 결제사별 변형을 가진다. 토스는 주문서형 결제 위젯이 결제수단을 그리고, 포트원은 결제수단 선택(CMP-010) 뒤 포트원 결제창을 연다. 결제 라우트의 CSP는 두 SDK 출처와 각 SDK가 여는 결제창 출처만 허용한다. 두 결제사 공식 문서에 CSP 허용 목록이 없어, 결제창이 여는 하위 결제사 출처는 스테이징에서 CSP 보고 모드로 모아 확정한다 [가정, Phase 2에서 확정]. 결제창에서 돌아온 주소의 결제 값은 읽은 즉시 주소창에서 지우고, 결제 라우트의 Referrer-Policy는 `strict-origin-when-cross-origin` 이상으로 두어 결제 값이 다른 출처로 새지 않게 한다.
10. **개인정보.** 포트원에는 쓰는 채널의 하위 결제사가 요구하는 구매자 항목만 넘긴다. 개인정보 처리방침(wbs 7.4.1)의 위탁 공개에 토스페이먼츠, 포트원, 쓰는 포트원 채널의 하위 결제사를 수탁자로 적는다. 개인정보 보호법 제26조 제2항은 위탁 업무와 수탁자(재수탁자 포함)를 정보주체가 언제든지 쉽게 확인할 수 있게 공개하라고 정한다(2026-09-11 시행본 원문 확인). 결제 대행을 제3자 제공이 아닌 처리 위탁으로 보는 판단은 '해석'으로 표시하고 POL-027 검토 목록에 올린다.
11. **시험.** 결제사 선택 규칙, 시도 대체와 재선택, 접수 계약 검증, 결제사 고정, 웹훅 결제사 확인, 결제사별 동시 입장 목표 상한과 전환 훈련, 결제사별 대사, 포트원 리디렉션의 결제 토큰 확인을 payment P-T26~P-T33으로 둔다. 시뮬레이터는 토스형과 포트원형 두 가지로 띄워 전환 훈련에 쓴다.

## 검토한 대안
| 대안 | 기각 사유 및 한계점 |
| --- | --- |
| 주문을 만들 때 결제사를 정하고 바꾸지 않음 | 장애 전환 뒤에도 이미 만든 주문은 고장 난 결제사로만 결제할 수 있다. 좌석을 잡은 사람이 홀드를 잃고 다시 경쟁해야 한다. |
| 서킷 브레이커가 열리면 대체 결제사로 자동 전환 | 포트원 추정 상한이 토스의 약 1/6이라 자동 전환이 순간 과부하를 만들 수 있고, 오탐이면 결제사를 괜히 바꾼다. 감내 모드 전환은 사람이 승인한다는 POL-021 C-3과도 어긋난다. 전환 시간이 문제로 확인되면 되돌릴 조건 2로 다시 본다. |
| 승인 요청까지 간 결제를 다른 결제사로 옮겨 재시도 | 같은 구매에 두 결제사의 승인이 겹칠 수 있다(이중 결제). 승인 요청 뒤에는 옮기지 않는다. |
| 한 공연 안에서 결제사를 비율로 나눠 쓰기 | 처리량은 늘지만 한 공연의 화면·대사·장애 대응이 두 결제사로 섞인다. 공연별 지정으로 충분한지 Phase 2 측정 뒤 다시 본다. |
| 구매자가 결제사를 고르기 | 구매자는 결제사보다 결제수단을 고른다. 결제사 상한과 장애는 플랫폼이 관리해야 한다. |
| 파트너가 공연 등록 위저드에서 결제사를 고르기 | 가맹점 계약·수수료·한도는 플랫폼의 책임이고, 결제사가 동시 입장 목표 상한을 바꾼다. |
| 선택기를 purchase-svc에 두기 | 결제사 능력 플래그·채널·결제창 값·상한이 두 서비스에 흩어진다. 결제사 지식은 payment-svc에 모은다. |
| 공연별 지정을 설정 파일로만 관리 | 배포가 필요하고 사유·dry-run·감사·되돌리기가 없다. |

## 결과와 트레이드오프
- 얻는 것
  - 토스와 포트원이 모두 실제 결제를 받는다. 결제사 장애 때 새 결제를 다른 결제사로 돌릴 수 있다.
  - 공연별 지정으로 결제사 상한을 나눠 써서 합산 처리량을 늘릴 길이 생긴다. 포트원 상한이 확인되거나 채널이 늘어야 실제로 커진다.
  - 이중 결제 방지와 Saga 규칙은 결제사 수와 관계없이 하나다. 고르기와 변환이 나뉘어 결제사를 더해도 선택기 설정과 어댑터만 바뀐다.
- 대가
  - 결제 시도 API, 결제사별 접수 계약, 결제사별 결제창 두 가지, 결제사별 대사·웹훅 확인, 운영 명령 1개, 결제 감내 모드 1개, 결제사별 동시 입장 목표 상한이 생긴다(wbs 2.7.5 2.5일, 2.10.2 +0.5일, 4.4.1 +0.5일, 합계 +3.5일).
  - 결제창이 열리기 전에 결제 시도를 만드는 요청이 하나 늘어 왕복이 한 번 더 든다. 결제 접수 지연(NFR-005)과는 무관하다.
- 남는 한계
  1. 포트원이 결제사인 공연은 추정 상한(채널 하나 초당 50건) 때문에 동시 입장이 약 830명으로 줄어 판매가 토스 공연보다 약 6배 느리다. 실제 상한이 확인되거나 채널을 늘리면 바뀐다.
  2. 전환은 사람이 승인하므로 장애 감지부터 전환까지(2인 승인 시간) 새 결제는 일시 정지된다.
  3. 전환 순간 원래 결제사 결제창을 연 사람은 그 결제창에서 실패할 수 있다. 같은 주문에서 다시 시도해야 하고, 홀드 시간이 지나면 좌석을 잃는다.
  4. 포트원 리디렉션 방식에서 결제 토큰이 쿼리로 오는지는 공식 문서와 공식 SDK 소스의 간접 근거로 판단했다. Phase 2 포트원 테스트 채널 스모크(P-T33)로 확인하고, 아니면 모바일 리디렉션 결제에는 포트원을 고르지 않도록 능력 플래그로 막는다.
  5. 포트원 하위 결제사마다 결제수단, 필수 구매자 항목, 승인 기한이 달라 채널을 더할 때마다 다시 확인해야 한다.
- 되돌릴 조건
  - 포트원 운영 상한이 확인되면 결정 6의 상한을 바꾸고 ADR-0036의 추정 표를 갱신한다.
  - Phase 2 전환 훈련(P-T31)에서 전환에 걸린 시간 때문에 결제 확정 완화 SLO(p99 60초)를 지키지 못하면, 전환 후보 추천을 자동 실행으로 바꾸는 것을 다시 검토한다. 그때도 동시 입장 목표 상한을 먼저 낮춘다.
  - 공연별 지정만으로 성장 전망(NFR-021)의 합산 상한을 맞추지 못하면 공연 안 비율 분할을 다시 검토한다.
