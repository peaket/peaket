# ADR-0042: ClickHouse 기반 사후 분석 데이터 웨어하우스 구축 및 비즈니스 의사결정 규칙 체계화

- **상태**: 채택 (2026-10-12 수립, 소유자 제안·승인. ADR-0004 원시 신호 30일 보존·S3 비식별 집계 및 NFR-009 실시간 관제 정책의 결정은 그대로 두고 비즈니스 데이터 웨어하우스로 확장). 일부 보완(2026-10-13, ADR-0052): 결정 2의 '관제 읽기 모델을 2층 마트의 실시간 부분으로 흡수'는 대체되어 실시간 표와 확정 표를 나눈다. 1층은 브론즈, 2층은 스타 스키마 골드, 3층은 아카이브로 구체화하고 실버를 새로 두며, 마감 단계(R0~R3)·지표 사전·결정 기록·가명정보 근거를 더한다. 이 ADR 본문은 고치지 않는다 2026-10-21(ADR-0077): Mimir 지표 보존이 원본 90일·5분 집계 13개월로 바뀌었다(소유자 결정). 검토한 대안 표의 '13개월'은 그 전 값이다. 회차 비교를 분석 저장소(골드)에 둔 이 ADR의 판단은 그대로이고, 더 짧아진 원본 보존이 그 판단을 뒷받침한다. 2026-10-26(4차 점검 3부): 결정 5의 '같은 규모 공연의 중앙값 밴드(아카이브)'는 골드의 최근 2년 확정 회차로 계산하고, 2년보다 오래된 회차와의 비교만 아카이브에서 하는 것으로 읽는다(docs/features/analytics.md §6.4, docs/observability.md §13, ADR-0052). 2026-10-27(ADR-0099): 결정 2의 '기존 Flink 경로'는 TypeScript 원본 적재 작업자 `analytics-ingest`로 바꿨다. 집계하지 않고 이벤트 그대로 쓰며 Kafka 재처리로 다시 만들 수 있다는 원칙은 그대로다. 2026-10-28(ADR-0115, 소유자 승인 '추천안 동의'): 결정 1의 3층 'S3 Iceberg'를 'S3의 회차별 Parquet 파일(ClickHouse `s3()`로 읽는다)'로 바꾼다. 영구 보존과 사람 단위 행이 없다는 규칙은 그대로다. 되돌릴 조건의 'Kafka → S3 Iceberg 직접 적재'는 그 조건이 오면 ADR-0115 결정 5의 표 형식 비교와 함께 본다. 2026-10-28(기술 검토 낮음-147, 소유자 승인 '추천안 동의'): 결정 6의 'pid 해시·계정 ID 해시'는 ADR-0052 결정 9의 회차별 키 HMAC 가명(`HMAC(HMAC(분석 가명 키, "PEAKET-analytics-v1" ‖ 회차 ID), 식별값)`, 분석 가명 키는 KMS)으로 대체됐다. 키 없는 해시는 후보 값을 넣어 보면 되돌릴 수 있어 쓰지 않는다(docs/features/analytics.md, docs/security/data-classification.md 분석 저장소 가명 사건 행).
- **관련 문서**: docs/data.md §1·§6, docs/observability.md §1·§9·§13, docs/features/control-tower.md §2·§11, planning/01-overview.md §3.2·§3.3, docs/security/data-classification.md, wbs 4.3.1·4.3.2
- **관련 ID**: FR-026, FR-029, FR-031, NFR-009, NFR-018, POL-022, POL-023, K8, K9

## 맥락
- 기존 관측 인프라에서 ClickHouse에는 세 가지가 있었다. Flink가 1초·10초로 집계한 실시간 관제 읽기 모델(90일 TTL), trust-svc 행동 신호 원시 데이터(30일 TTL), 법정 접속기록(별도 저장소, 3개월). 파트너 콘솔의 실시간 판매 현황도 같은 읽기 모델을 쓴다.
- 이러한 구조는 "현재 시스템이 정상 가동 중인가"라는 실시간 상태 판단에는 충분하지만, "다음 티켓 오픈 시 대기열 정렬 방식을 무엇으로 바꿀 것인가", "좌석 구역별 가격 책정과 1인 매수 한도를 어떻게 조정할 것인가", "봇 차단 임계값과 프로비저닝 용량을 어떻게 재설정할 것인가"와 같은 사후 비즈니스 의사결정에는 공연이 끝난 뒤 다시 꺼내 볼 데이터가 없었다. 종료 후 패널의 포스트모템 초안도 관제 타임라인 중심이었다.
- 소유자 제안(2026-10-11): 운영 관제와 공연별 지표를 모아 사후 분석으로 비즈니스 의사결정에 쓰자. 2026-10-12 승인.
- 제약: 원시 개인정보는 S3에 두지 않는다(ADR-0004, data.md §1). 행동 신호 원시는 30일 TTL이다. 파트너에게 보여 주는 데이터에는 개인정보·봇 세부를 넣지 않는다(control-tower §11). 분석 저장소가 라이브 트랜잭션 데이터 평면의 부하에 영향을 주면 안 된다(관측 경로 분리, observability §1).

## 결정
1. **3계층 데이터 파이프라인.** ClickHouse를 실시간 관제를 넘어선 종합 분석 저장소로 확장한다.

| 층 | 내용 | 저장 | 보존 |
| --- | --- | --- | --- |
| 1 원시 비즈니스 이벤트 | Kafka의 `trade.*`(순번·입장·홀드·주문·결제·발권·취소), `telemetry.queue`, `control.*`(명령·ack), trust-svc 판정 결과(점수 범주·집행 여부·허니팟 적중)를 공연 ID 기준으로 비동기 일괄 적재. 사용자는 pid 해시·계정 ID 해시만, 이름·연락처·연계정보·IP 원문 없음. 하트비트·폴링 요청은 넣지 않음 | ClickHouse(분석 DB, 공연·일 파티션) | 90일(TTL) |
| 2 공연 리포트 마트 | 공연×분 시계열(진입·입장·홀드 성공·경합 패배·주문·승인·발권·봇 분리·SLO 위반·명령), 퍼널 전환율 요약, 등급·섹션별 판매와 매진 소요 시간, 홀드 경합 탈락 분포, 결제 실패 사유 분포, 봇 지표 하한, 추가 검증 통과·이의 제기, 에러 버짓 사용, 온세일 1회·티켓 1,000장당 인프라 원가(K9) | ClickHouse 머티리얼라이즈드 뷰 + 종료 후 배치 | 2년(연간 비교) |
| 3 비식별 집계 아카이브 | 2층 마트를 공연 종료 뒤 내보낸 것. 공연 간·연도 간 트렌드 비교 | S3 Iceberg | 영구 |

2. **적재 경로.** 1층은 기존 Flink 경로를 공유하되 집계가 아니라 이벤트 그대로를 쓰고, Kafka 재처리로 재구성할 수 있다(infra §6의 ClickHouse 복원 원칙과 같음). 관제 읽기 모델(기존 90일)은 2층 마트의 실시간 부분으로 흡수한다.
3. **자동화된 공연 리포트(SCR-029).** 종료 후 패널(SCR-029 ④)의 포스트모템 초안을 '공연 리포트'로 확장한다. 내용은 2층 마트 항목 전부와 관제 타임라인, 결정 규칙 표의 판정 결과, 다음 공연을 위한 제안이다. `ops-svc`가 온세일 윈도우 종료 뒤 자동 생성해 Markdown과 JSON으로 저장하고, 파트너용 축약본(판매·매진·등급별·환불 집계만, 개인정보·봇 세부·내부 보안 규칙 제외)은 파트너 콘솔 정산 리포트 옆에 둔다.
4. **비즈니스 의사결정 규칙 표.** 비즈니스 KPI와 운영 지표마다 '값이 이러면 이 결정을 검토한다'를 planning/01 §3.2에 표로 두고, 공연 리포트가 표의 조건에 걸린 항목을 자동으로 표시한다. 규칙은 결정을 강제하지 않고 검토를 열며, 바꾼 결정은 ADR이나 판매 정책 변경으로 남긴다. 임계값의 구체적 수치는 그 표가 정한다.
5. **지표 체계와 판단 방식.** 지표는 네 층(인프라 포화, 서비스별 네 신호, 여정별 SLO·에러 버짓, 비즈니스 KPI)으로 두고, 보여 주는 곳은 세 곳(관제 4단계 탭, Grafana 서비스 대시보드, 파트너 콘솔)에 공연 리포트를 더한다. 실시간 판단은 SLO 기준선과 번 레이트, 사후 판단은 결정 규칙 표와 같은 규모 공연의 중앙값 밴드(아카이브)로 한다. 정리는 observability §13.
6. **개인정보.** 1층의 pid 해시·계정 ID 해시는 가명정보로 보고 P2 저장소 암호화, 90일 뒤 파기, 2·3층에는 개인 단위 행을 두지 않는다. 접속기록 저장소와 행동 신호 원시(30일)는 그대로 분리한다. data-classification에 행을 더한다.

## 검토한 대안
| 대안 | 기각 사유 및 한계점 |
| --- | --- |
| 지표만 Prometheus/Mimir 장기 보관(13개월)으로 비교 | 시계열 메트릭은 유지되지만, 공연 단위의 퍼널·등급·좌석 구역·결제 실패 사유 같은 복합 다차원 드릴다운 분석이 불가능하다. |
| 외부 BI 도구를 바로 도입 | 저장소가 먼저다. 마트가 있으면 Grafana 쿼리로 충분하고, 도구는 나중에 붙일 수 있다. |
| 원시 이벤트를 S3에만 적재 후 필요할 때 Athena 조회 | 공연 직후의 리포트 생성이 수십 분 이상 지연되고, 고빈도 쿼리 비용이 커진다. ClickHouse가 이미 있어 적재 비용이 작다. |
| 원시 이벤트를 영구 보관 | 가명정보를 오래 둘 이유가 없다. 집계는 영구, 원시는 90일. |

## 결과와 트레이드오프
- 얻는 것: 공연이 끝난 뒤 "무엇을 바꿀지"를 데이터로 정할 수 있고, 공연 간 비교로 목표치(매진 22분, 전환율 83%, 봇 점유율 5%)를 실측에 맞춰 조정할 근거가 생긴다. 포트폴리오에서는 기술 지표를 비즈니스 결정으로 잇는 피드백 루프가 된다(planning/01 §3.3).
- 대가
  - ClickHouse 저장량과 Flink 잡이 늘어난다(wbs 4.3.2 2일). 온세일 중 적재는 비동기 일괄 삽입이라 데이터 평면에는 영향이 없지만 관측 비용 측정(Phase 4)에 넣는다.
  - 결정 규칙의 임계값 일부는 측정 전이라 [가정]이고, 첫 공연 리포트 뒤 조정한다.
  - 공연 리포트 자동 생성은 템플릿 유지 비용이 있다.
- 되돌릴 조건
  - 1층 적재가 Flink 체크포인트 지연이나 관제 지표 반영(NFR-009 p95 5초)을 해치면 1층을 Kafka → S3 Iceberg 직접 적재로 바꾸고 ClickHouse에는 마트만 둔다.
  - 공연 리포트가 두 공연 연속 결정에 쓰이지 않으면 자동 생성을 줄이고 마트 쿼리만 남긴다.
