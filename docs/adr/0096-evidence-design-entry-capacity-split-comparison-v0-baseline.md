# ADR-0096: 핵심 증거의 실험을 다시 짠다 — 진입 용량은 설계 식으로 보고 USL은 보조로, 서비스 분리 효과는 세 구성으로, v1 합격은 목표 절대값으로 판정한다(2026-10-27)

- **상태**: 채택 (2026-10-27. 기술 검토(review/tech-review.md)의 높음-02 '핵심 증거(100만 외삽·서비스 분리 효과·v0 대비 개선)의 실험 설계가 결론을 받치지 못한다'에 소유자가 "높음-02 : 동의합니다. 추천안대로 가주세요."라고 정했다. 방향은 소유자 결정이고, 기준값과 일정 같은 세부는 추천 적용이다)
- **관련**: NFR-001, NFR-004, NFR-005, NFR-012, NFR-013, ADR-0007(결정 7), ADR-0057, [docs/verification.md](../verification.md) §1·§3·§8·§9, [docs/architecture.md](../architecture.md) §3·§9, [docs/perf-ledger.md](../perf-ledger.md), [docs/features/queue-admission.md](../features/queue-admission.md) Q-T2·Q-T3, [docs/features/seat-hold.md](../features/seat-hold.md) S-T12, planning/01 §3.1·§4.1·§5.2, wbs 1.1·2.12·6.1, [review/tech-review.md](../../review/tech-review.md)(높음-02)

## 맥락

포트폴리오의 핵심 증거는 셋이다. 100만 명일 때의 진입 처리량, 서비스를 나눈 효과, 단순한 첫 설계(v0) 대비 개선이다. 개발 양은 AI로 빠르게 소화할 수 있으므로(소유자 전제, 2026-10-27), 포트폴리오를 가르는 것은 이 증거가 결론을 정말 받치는지다. 지금 실험에는 세 가지 틈이 있다.

- **한 PC에서 맞춘 확장 곡선(USL)**: 진입 서버 1~8대와 부하 발생기(k6)를 한 PC에 함께 띄워 곡선을 맞춘다(docs/verification.md §3.3).
  - 이때 처리량을 깎는 공유 자원은 설계가 아니라 그 PC다. CPU 캐시, 메모리 대역, 같은 PC 안 네트워크(루프백)를 나눠 쓰고, 고성능 코어 8개를 넘는 배치는 저전력 코어에 놓인다.
  - 반대로 운영에서 진입 서버들이 실제로 나눠 쓰는 자원인 Redis 한 키는 따로 코어를 받아 곡선 밖에 있다.
  - 그런데 판정 문장은 '곡선이 20만에 닿지 않으면 서버를 늘려도 풀리지 않는 공유 자원이 있다'로 읽는다. 곡선이 꺾여도 그것이 설계 탓인지 PC 탓인지 가를 수 없다.
- **서비스 분리 효과의 비교**: '같은 v1 코드를 한 번에 배포한 모놀리스'와 '10개 서비스'만 비교한다(docs/architecture.md §3, Q-T3).
  - 두 구성의 CPU·메모리 합계와 배치를 고정하지 않았다.
  - 같은 이미지를 역할별로 따로 띄운 중간안이 없다. 그래서 차이가 나도 그것이 서비스로 나눈 덕인지, 프로세스와 자원 몫을 나눈 덕인지 가를 수 없다.
- **v0 대비 비율**: K1(원 서버 요청 99% 절감), K4(전송량 99% 절감), K5(힙 70% 감축)는 '일부러 실패하는 v0'에 기댄다.
  - 예를 들어 K4의 v0(좌석이 바뀔 때마다 5만 석 전체 JSON을 모두에게 보냄)는 재지 않아도 초당 약 10GB가 나온다(docs/architecture.md §9.1). 비율이 측정 전에 거의 정해진다.
  - 면접에서 '허수아비와 비교했다'는 지적을 받기 쉽다.

## 결정

1. **진입 용량은 설계 식으로 판단한다(추천 적용).** 진입 용량 = min(N × X₁, R)이다.
   - X₁은 CPU 몫을 고정한 진입 서버 1대(파드 하나에 1 vCPU [가정, 6.1.1에서 확정])가 NFR-001의 SLO(p99 200ms 이하, 오류율 0.1% 미만)를 지키며 받는 가장 높은 도착률이다. 3회 측정의 중앙값을 쓴다.
   - R은 Redis 한 키의 처리량이다(PoC 0.5.1, 단독 측정. 묶음 증가 `INCRBY`를 쓰면 그 방식의 값).
   - 20만 RPS에 필요한 대수는 ⌈200,000 ÷ X₁⌉이다. R이 20만보다 작으면 대수와 상관없이 R이 상한이고, 그때는 docs/architecture.md §9.2의 묶음 증가·진입 경로 나누기를 검토한다.
   - 이 값은 '외삽(설계 식)'으로 표시하고 근거 실행, X₁, R, 외삽 배수(필요한 대수 ÷ 잰 최대 대수)를 단다. 외삽 배수가 4 [가정, 6.1.1에서 확정]를 넘으면 지금처럼 '외삽(측정 범위의 4배 초과)'으로 표시한다.
2. **USL은 '대수에 비례한다'는 전제를 확인하는 보조 자료로 내린다(추천 적용).**
   - 설계 식은 진입 서버끼리 나눠 쓰는 것이 Redis 한 키뿐이라 처리량이 대수에 비례한다고 본다. USL은 이 전제가 잰 범위 안에서 맞는지 본다.
   - 판정은 비례 효율 E(N) = X(N) ÷ (N × X₁)로 한다(N대가 1대의 N배를 얼마나 내는지). 호스트가 포화하지 않은 점 가운데 가장 큰 N에서 E(N)이 0.9 [가정, 6.1.1에서 확정] 이상이면 '비례 전제는 N대까지 확인'으로 적는다.
   - E(N)이 0.9보다 낮으면 설계 식을 그대로 쓰지 않는다. 호스트 지표(결정 3)로 PC 탓인지 먼저 본다. PC로 설명되지 않으면(앱 안에 공유하는 것이 있다는 뜻) USL로 맞춘 값을 외삽에 쓰고, 그 원인을 찾아 고친다.
   - USL 계수(α·β)와 정점은 지금처럼 계산해 장부에 남기지만, 20만 RPS 판단의 근거로는 쓰지 않는다.
3. **점마다 호스트 지표를 남기고, 호스트가 포화한 점은 계산에서 뺀다(추천 적용).**
   - 남길 것: 호스트 전체 CPU 사용률, 실행을 기다리는 프로세스 수(`/proc/stat`의 `procs_running`), 발생기 CPU, 진입 파드별 CPU 스로틀 비율(받은 CPU 몫을 다 써서 멈춘 시간의 비율), 코어 배치.
   - 호스트 CPU 85% 이상이거나 실행을 기다리는 프로세스가 WSL에 준 논리 프로세서 수를 넘는 점 [가정, 6.1.1에서 확정]은 '호스트 포화'로 표시하고 계산에서 뺀다. 장부에서는 지우지 않는다.
   - 진입 파드·Redis·발생기에 준 CPU 합이 고성능 코어 수(8개, 스레드 16개)를 넘는 점은 '코어 혼합'으로 표시한다. WSL에서는 어느 코어에 놓일지 고를 수 없어서 표시만 한다.
   - 뺀 뒤 남은 점이 3개 미만이면 비례 전제는 '확인 못 함'으로 적고, 설계 식의 값에 그 사실을 붙인다.
4. **서비스 분리 효과는 세 구성을 같은 자원 합계로 잰다(소유자 결정, 세부는 추천 적용).**
   - (가) 한 프로세스 합본: 같은 v1 코드의 서비스를 Node.js 프로세스 하나에 함께 띄운다. 복제본마다 진입 서버 1대와 같은 CPU 몫을 주고, 복제본 수로 CPU 합계를 맞춘다.
   - (나) 역할별 배포: 같은 합본 이미지를 v1과 같은 열 갈래로 따로 띄운다. 갈래는 환경 변수로 켤 서비스를 고른다. 갈래별 CPU·메모리 몫은 (다)와 같다.
   - (다) 10개 서비스: v1 그대로다.
   - 같게 두는 것: 코드 커밋, 저장소(같은 Redis·PostgreSQL 컨테이너와 설정), CPU·메모리 합계, 부하 스크립트. 서비스 사이 호출은 세 구성 모두 v1과 같은 gRPC로 둔다. 같은 프로세스 안 함수 호출로 바꾸면 차이에 호출 방식이 섞이기 때문이다.
   - 부하: 결제 접수 300 TPS(결제사 시뮬레이터)를 고정으로 두고, 진입 폭주를 없음, PC에서 진입 SLO를 지킨 최대 도착률의 100%, 120% [가정] 세 단계로 겹친다. 재는 것은 결제 접수 p99·오류율(NFR-005), 진입 p99·오류율, 구성별 CPU 스로틀이다. 조건마다 3회 반복한다.
   - 읽는 법: (가)와 (나)의 차이는 실행을 나눈 것(프로세스와 자원 몫)의 효과다. (나)와 (다)의 차이는 코드를 서비스로 나눈 것(이미지·의존성·빌드)의 효과다. 3회 반복의 편차(최댓값 − 최솟값) 안의 차이는 '차이 없음'으로 적는다.
   - (나)와 (다)는 실행 모양이 같으므로 성능 차이는 작을 것으로 본다. 재서 차이가 없으면 '진입 폭주가 결제로 번지지 않게 하는 것은 실행 분리이고, 서비스로 나눈 것 자체의 성능 이득은 없다'고 적는다. 그때 10개 서비스로 나눈 이유는 성능이 아닌 근거(배포·장애·런타임 단위, 저장소 소유, ADR-0007 결정 1~6)로만 말한다. 이 결과도 실패가 아니며 장부와 ADR-0007 상태 줄에 그대로 남긴다.
   - (다)가 진입 폭주 100% 단계에서 NFR-005를 지키지 못하면 ADR-0007 결정 7의 목표가 깨진 것이다. 원인(공유 저장소, 같은 PC의 자원)을 찾아 다시 정한다.
5. **v1 합격은 NFR과 K의 절대값으로만 판정한다(소유자 결정).** v0 대비 비율은 보조 숫자로 장부에 적고 합격 판정에 쓰지 않는다.
   - K1: NFR-001(진입 p99 200ms, 오류율 0.1% 미만)과, 원 서버 요청이 설계 식(활성 대기 상태 파일 수 ÷ 캐시 수명)의 ±10% [가정] 안인지로 판정한다. 원 서버 요청 절감률은 보조 숫자다.
   - K4: NFR-004(종단 p99 300ms), 만료 좌석이 다시 보이는 시간 p99 3초, 연결 5,000개 합계 전송량이 설계 상한(묶음 델타 초당 약 10MB와 구역 상태 갱신 초당 최대 약 6MB, docs/architecture.md §9.1) 이하인지로 판정한다. 전송량 절감률은 보조 숫자다.
   - K5: INP 200ms 이하(4배 느린 CPU), 주요 조작 경로의 Long Task 0, 대기실 통과 뒤 첫 그림 1초 미만, 비트맵 캐시 64MB [가정] 이하로 판정한다. 힙 감축률은 보조 숫자다.
   - 나머지 K(K2·K3·K6~K10)는 목표가 이미 절대값이라 바꾸지 않는다.
6. **v0는 '유능한 팀이 처음 만들 법한 단순한 설계'로 정의한다(소유자 결정, K별 v0는 추천 적용).** 일부러 망가뜨리지 않는다.
   - K1: 대기 상태 API가 조회마다 Redis `ZRANK`로 앞 인원을 계산해 JSON으로 답한다. 폴링 주기는 v1과 같은 거리별 표(1초·5초·20초, queue-admission §4)를 쓴다. 그래서 차이는 '누가 답하나'(원 서버가 매번 계산 대 CDN의 구간 파일)와 순번 방식(`ZRANK` 대 `INCR`과 빠진 번호 비트맵)에서만 나온다. 서버가 화면을 그려 보내는 SSR 대기 페이지는 쓰지 않는다.
   - K2·K3: 그대로다. PostgreSQL `SELECT … FOR UPDATE`로 좌석 행을 잠그고, 요청이 고른 순서대로 잠근다. 많은 팀이 처음 고르는 방식이다.
   - K4: 바뀐 좌석의 변경분을 JSON으로 모든 연결에 보낸다. 구역 구독, 묶어 보내기, 바이너리 형식은 없다.
   - K5: 메인 스레드에서 Canvas 2D 한 장에 좌석 객체 배열로 그린다. Worker, TypedArray, 묶어 그리기는 없다. 그러면 v1과의 차이가 v1 설계가 더한 것(Worker로 옮겨 그리기, 바이너리 배열, 묶어 그리기)으로 좁혀진다.
   - K6~K10: 그대로다(레이트 리밋만, 동기 결제 체인, 정적 기준값 경보, CPU 기준 자동 확장, 온라인 전용 검표).
7. **계산만으로 실패가 분명한 방식은 만들지 않는다(추천 적용).** '좌석이 바뀔 때마다 5만 석 전체 JSON(약 2MB)을 5,000명에게 1초마다' 보내는 방식은 초당 약 10GB라 만들지 않는다. 이 값은 docs/architecture.md §9.1 용량 산정의 계산으로만 말하고, 잰 숫자의 기록인 성능 장부에는 넣지 않는다.
8. **일정(추천 적용).**
   - wbs 2.12.2에서 서비스 분리 효과 비교를 떼어 1.5일을 1일로 줄인다.
   - 새 2.12.5 '서비스 분리 효과 세 구성 비교'에 2일을 둔다(합본 빌드와 갈래 스위치 1일, 3구성 × 3단계 × 3회 측정과 기록 1일).
   - 6.1.1에 호스트 지표 수집, 포화 점 제외, 설계 식 계산을 더해 4일을 4.25일로 늘린다.
   - 1.1.1·1.1.2는 v0 정의만 바꾸고 일수는 그대로 둔다. 모두 1.75일 늘어난다.

## 검토한 대안

| 대안 | 기각 이유 |
| --- | --- |
| USL을 20만 RPS 판단의 주 근거로 둔다(지금) | 한 PC에서는 PC의 공유 자원이 곡선에 섞인다. 설계의 공유 자원인 Redis 한 키는 곡선 밖에 있다 |
| 클라우드 노드 여러 대에 진입 서버를 나눠 USL을 잰다 | 지출 상한 5만 원과 선택 보정 범위(환산 계수 1회, CDN 요청 묶기 확인)를 넘는다(ADR-0057). 선택 보정은 X₁의 환산 계수로만 쓴다 |
| 분리 효과를 두 구성(합본 대 10개 서비스)으로 잰다(지금) | 실행을 나눈 효과와 코드를 나눈 효과를 가를 수 없다 |
| 합본에서는 서비스 사이를 같은 프로세스 안 함수 호출로 바꾼다 | 평소 지연은 줄지만 차이에 호출 방식이 섞인다. 이 실험이 묻는 것은 진입 폭주가 결제로 번지는지다 |
| v0를 없애고 v1만 절대값으로 잰다 | 단순한 설계가 어디서 무너지는지(K2 잠금 경합, K7 동기 체인의 이중 결제)를 보이는 데 v0가 여전히 쓸모 있다 |
| 바꾼 v0 기준으로 비율 목표를 새로 둔다(예: 90% 절감) | 측정 전에 정할 근거가 없다. 다시 측정 전에 정해지는 숫자가 된다 |

## 결과와 트레이드오프

- 20만 RPS 판단이 PC의 공유 자원과 섞이지 않는다. 설계가 실제로 나눠 쓰는 자원(Redis 한 키)이 식에 그대로 들어간다.
- 분리 효과가 나와도 안 나와도 원인을 말할 수 있다. 면접에서 '모듈러 모놀리스를 역할별로 띄우면 되지 않느냐'에 측정으로 답한다.
- v1 합격이 v0를 어떻게 만들었는지에 기대지 않는다. v0는 '처음 만들 법한 설계'라서 '왜 그 v0인가'에 답할 수 있다.
- 대가:
  - 합본 빌드와 갈래 스위치를 만들어야 한다. 서비스가 저장소 여러 개(폴리레포)에 있어 같은 커밋들을 묶는 빌드가 필요하다. WBS는 1.75일 늘어난다.
  - v0와의 차이가 줄어 '99% 절감' 같은 큰 숫자를 앞세우지 못한다. 보조 숫자는 잰 대로 적는다.
  - 비례 전제는 잰 범위(최대 8대) 안에서만 확인된다. 필요한 대수가 그보다 많으면 그 구간의 비례는 여전히 외삽이다.

## 되돌릴 조건

- 선택 보정(docs/verification.md §6)이나 다른 기회에 클라우드 노드 여러 대로 진입 서버의 비례를 잴 수 있게 되면, 그 측정을 진입 용량의 주 근거로 올린다.
- 비례 효율이 0.9보다 낮은데 호스트 지표로 설명되지 않으면, 설계 식 대신 USL 외삽을 쓰고 이 ADR의 결정 1·2를 다시 본다.
- 세 구성 비교에서 (나)와 (다)의 차이가 편차보다 크게 나오면, 그 원인(이미지 크기, 의존성, 런타임 설정)을 찾아 ADR-0007 상태 줄에 적는다.

## 남는 한계

- 한 PC 측정이라 노드 사이 네트워크, 부하 분산기(NLB), 게이트웨이를 여러 대 거치는 동작은 재지 않는다. 이 부분은 문서 인용과 선택 보정으로만 다룬다(ADR-0057).
- 세 구성 비교는 성능만 말한다. 서비스로 나눈 것의 다른 이득(따로 배포, 장애 범위, 저장소 경계)은 이 실험이 재지 않는다.
- (가)의 합본도 서비스 사이를 gRPC로 부르므로, 실제로 함수 호출로 짠 모놀리스보다 평소 지연이 길다. 이 차이는 재지 않는다.
- 호스트 포화 기준(85%, 실행을 기다리는 프로세스 수)은 첫 측정 전에 정한 가정이다. 첫 측정에서 기준이 맞는지 보고 6.1.1에서 확정한다.
