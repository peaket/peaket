# ADR-0132: 기술 검토 중간 항목의 문서 수정 묶음 5 — 프론트엔드·디자인·기획·정책·guide(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 중간 항목(영역: 아. 프론트엔드·디자인·접근성, 자. 기획·정책·문서의 정확성)에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 방향은 소유자 결정(추천안 승인)이고, 검토가 안을 고르지 않은 곳의 선택과 값 같은 세부는 추천 적용이다. 측정 전 값은 [가정]으로 표시했다)
- **관련**: review/tech-review.md(중간-094·중간-095·중간-096·중간-097·중간-098·중간-099·중간-100·중간-101·중간-102·중간-103·중간-104·중간-105·중간-106·중간-107·중간-108·중간-109·중간-110), review/consistency-review.md R-150, 00-summary.md §6·질문 61, 같은 날 새 ADR-0100~0126(새 결정이 필요한 항목)

## 맥락

2026-10-27 기술 검토 2판은 설계의 모든 기술·기법을 시니어 개발자 관점에서 따져 높음·중간·낮음 항목으로 냈다. 2026-10-28 소유자가 남은 항목을 모두 추천안대로 고치라고 정했다. 새 결정이 필요한 항목은 따로 ADR(0100~0126)을 썼고, 이 ADR은 정본 문서를 고쳐 반영한 중간 항목 17건의 문제와 결정을 한곳에 모은다. 검토 문서에서는 이 항목들의 본문을 지우고 이 ADR을 가리키는 한 줄만 남겼다(지운 본문은 git 이력에 있다).

## 결정

항목마다 검토의 추천 수정을 따랐다(소유자 승인). 검토가 안을 여럿 내고 고르지 않은 곳은 고른 안과 이유를 적었고 '추천 적용'으로 표시했다. 정본에는 `(추천 적용 2026-10-28, 기술 검토 <번호>)`로 표시했다.

### 아. 프론트엔드·디자인·접근성

#### 중간-094 Cache Components(PPR 기본)와 nonce 화면을 한 Next 앱에 두는 조건이 PoC에 없다
- **문제**: 소비자 웹은 한 Next.js 앱에서 캐시 화면(ISR, Cache Components)과 nonce 화면(B·E·F: 좌석·결제·마이·로그인)을 함께 쓴다. Next 16에서 `cacheComponents`를 켜면 PPR이 App Router 전체의 기본 동작이 되고, Next CSP 문서는 PPR이 nonce CSP와 맞지 않는다(정적 셸 스크립트가 nonce를 받지 못함)고 적는다. 그래서 nonce 화면은 정적 셸이 생기지 않게 따로 그려야 하는데(예: 경로 묶음별 루트 레이아웃을 나누고, 그 레이아웃에서 요청 시점 값을 읽음), 문서의 PoC 목록(§6.3)은 캐시 화면의 해시 방식만 본다.
- **결정**: 소비자 웹의 헤더 묶음 A 화면은 `(cached)`, B·E·F 화면은 `(request)` 경로 묶음에 두고 루트 레이아웃을 따로 둔다. `(request)` 루트 레이아웃은 요청 nonce를 먼저 읽어 정적 셸 없이 그리고 `instant = false`를 둔다(추천 적용). PoC FE-T35(wbs 2.10.1)로 확정하고, 정적 셸이 남거나 nonce 없는 script가 나오면 B·E·F를 Cache Components를 끈 별도 Next.js 앱으로 나눈다(추천 적용). 두 묶음 사이 이동은 전체 이동이다.
- **바꾼 문서**: docs/frontend.md §2.2·§2.5·§5.17·§6.3·§6.4, docs/architecture.md §6.3, docs/security/asvs/frontend.md 3.4.3, ADR-0065·0079 상태 줄, planning/01 §5.2, guide/17 §5
- **남는 한계**: planning/01 §5.2 새 줄 '소비자 웹 화면 묶음 나누기와 SEED CSS 싣기의 남는 한계'(두 묶음 사이 전체 이동, PoC 전)

#### 중간-095 AbortSignal.any가 지원 범위(iOS 16.4~17.3)에 없다
- **문제**: api-client는 모든 호출의 시간 초과와 화면 떠남 신호를 `AbortSignal.any`로 묶는다. 이 기능은 Safari 17.4부터라 NFR-019가 지원한다고 한 iOS·iPadOS 16.4~17.3에서 호출 자체가 예외로 실패한다. §1.5의 '기능별 대체 동작' 표에도 빠졌다.
- **결정**: api-client는 `AbortSignal.any`가 없으면 공용 함수 `anySignal`로 시간 초과와 화면 떠남 신호를 묶는다(추천 적용). 새 브라우저 기능은 eslint-plugin-compat + browserslist(NFR-019)로 PR에서 막고, ES 내장 검사는 실험 설정을 켠다(추천 적용). FE-T15가 `AbortSignal.any`를 지운 페이지로 대체를 본다.
- **바꾼 문서**: docs/frontend.md §1.5·§4.1·§5.17·§6.4

#### 중간-096 중단점 이름이 SEED와 같은데 값이 달라 1024~1279px에서 부품이 다르게 바뀐다
- **문제**: tokens.json은 SEED와 같은 이름(sm·md·lg·xl)에 PEAKET 값(360·768·1024·1440)을 준다. SEED는 sm 480·md 768·lg 1280·xl 1440이다. SEED 부품의 반응형 속성(예: Box의 `hideFrom`, 반응형 스타일 값)과 SEED가 미리 만든 CSS의 매체 질의는 SEED 값으로 동작하고(매체 질의는 CSS 변수로 덮어쓸 수 없다), Tailwind의 `sm:`·`lg:`는 PEAKET 값으로 동작한다. 그래서 1024~1279px(태블릿 가로·작은 노트북, ADR-0061의 태블릿 범위)과 360~479px에서 같은 'lg'·'sm'이 서로 다르게 바뀐다.
- **결정**: 중단점을 SEED 값(480·768·1280·1440)으로 바꾸고 Tailwind 중단점도 같은 넷만 만든다(추천 적용, 검토 (가)안). 360은 휴대폰 시안 폭으로만 남기고, 콘솔 태블릿 배치는 768~1279, 데스크톱은 1280부터다(추천 적용, ADR-0061의 세 크기 지원은 소유자 결정 그대로).
- **바꾼 문서**: design/tokens.json, design/d1 §4, design/d2 §1, design/d3 §0, design/d4 #17, design/d5 §0.3·§3.9, docs/frontend.md §5.13, ADR-0040·0061 상태 줄

#### 중간-097 SEED CSS를 어떻게 싣는지 정하지 않아 경로 CSS 예산과 맞는지 알 수 없다
- **문제**: frontend.md §5.8의 경로별 CSS 예산은 20~30KB(gzip)인데, SEED CSS 전체 `all.min.css`는 같은 문서가 잰 42.2KiB다. SEED는 부품별 `recipes/*.css`, CSS 층(cascade layer) 판 `all.layered.css`·`base.layered.css`, 주석으로 부품 CSS를 넣어 주는 빌드 플러그인을 낸다. 어느 방식으로 쓰는 부품 CSS만 싣는지, Tailwind v4의 초기화(preflight)와 SEED base·부품 CSS의 층 순서를 어떻게 두는지(같은 요소에 SEED 클래스와 Tailwind 유틸이 겹칠 때 누가 이기는지) 정하지 않았다.
- **결정**: SEED 전체 CSS는 싣지 않고 쓰는 부품의 recipe만 층 판으로 싣는다. 층 순서는 `@layer theme, base, seed-base, seed-components, components, utilities;` 하나이고 첫 CSS 맨 앞에 둔다. 예산은 size-limit CSS 항목으로 지킨다(추천 적용, ADR-0040 이행). Next.js 앱이 층 판을 고르는지는 PoC FE-T36(wbs 0.6.1)으로 보고, 안 되면 SEED 부품 요소에 Tailwind 유틸을 겹치지 않는 린트로 바꾼다(추천 적용).
- **바꾼 문서**: design/d2 §1, docs/frontend.md §2.2·§5.8·§5.17·§6.3·§6.4, docs/architecture.md §6.5, ADR-0040 상태 줄
- **남는 한계**: planning/01 §5.2 094 줄에 함께(예산이 빠듯함, Next 앱이 층 판을 못 고르면 Tailwind로 SEED 모양을 못 덮음)

#### 중간-098 사용자를 막는 입력·접근성 패턴 셋(빠른 입력·반복 문자 차단, SeatList 구조, 인증 코드 칸 나누기)
- **문제**: (1) d2 §3.1은 '아주 빠른 키 연타, 같은 문자 10회 이상 반복'을 화면에서 막는다. 이는 붙여넣기·비밀번호 관리자·음성 입력처럼 한꺼번에 들어오는 입력과 'ㅋㅋㅋㅋㅋ' 같은 흔한 한국어 표현을 막고, 봇은 화면 검사를 거치지 않아 보안 효과가 없다. 성명을 한글·영문·공백으로만 받으면 ja·zh 로케일(NFR-024)과 하이픈·아포스트로피가 든 이름이 막힌다. (2) SeatList를 'treegrid 또는 중첩 listbox'로 적었는데, ARIA에서 listbox 아래에는 option과 group만 올 수 있어 중첩 listbox는 맞지 않는 구조다. 가상 스크롤이면 `aria-setsize`·`aria-posinset`도 있어야 낭독기가 위치를 읽는다. (3) 인증 앱 코드를 여섯 칸으로 나누면 붙여넣기·자동 채우기·낭독기가 깨지기 쉽다(frontend §5.11이 붙여넣기 허용을 규칙으로 둠).
- **결정**: 빠른 입력·반복 문자를 화면에서 막지 않고 악용 판정은 서버에 맡긴다. 성명은 문자 집합을 제한하지 않는다. SeatList는 ARIA `tree`로 하고 가상 스크롤 때 위치 속성을 둔다(시안 낭독기 시험에서 안 되면 구역 제목 + 열별 버튼 목록). 인증 앱 코드는 입력 칸 하나를 여섯 칸 모양으로 그린다(모두 추천 적용).
- **바꾼 문서**: design/d2 §3.1·CMP-007·CMP-022, docs/frontend.md §4.8·§5.11·§5.17, design/d4 §1 #25·§2, design/d5 SCR-020 그림
- **남는 한계**: planning/01 §5.2 094 줄에 함께(가상 스크롤이라 낭독기가 화면 밖 좌석을 미리 훑지 못함)

#### 중간-099 tokens.json이 따른다고 적은 DTCG 2025.10 형식과 다르고 점이 든 이름이 별칭을 깨뜨린다
- **문제**: (1) frontend.md §6.4와 d2 §1은 토큰 형식을 'W3C 커뮤니티 그룹 명세(2025.10 첫 안정판)'로 적는데, 파일은 그 전 초안 표기다: 색 64개가 16진 문자열, 치수·시간 51개가 단위 붙은 문자열, 그림자 안 값도 문자열이다. (2) 무늬 토큰 6개의 `$type: "string"`은 명세에 없는 형식이다(명세는 '모든 토큰은 정의된 형식 가운데 하나를 써야 한다'). (3) 간격 이름 `"0.5"`·`"1.5"`는 명세가 금지한 점(.)을 담고, 별칭 `{space.1.5}`(between-text)는 점으로 경로를 나누는 도구에서 space → 1 → 5로 읽혀 풀리지 않는다. 한편 Style Dictionary 문서는 '2025.10 형식은 아직 완전히 지원하지 않는다(v5에서 작업 중)'고 적어, 지금 문자열 표기를 쓰는 것 자체는 도구 사정상 이해할 만하다. 문제는 그 선택을 적지 않고 '안정판 준수'라고 쓴 것과, 어느 판에서도 허용되지 않는 점 든 이름이다.
- **결정**: tokens.json은 DTCG 형식이되 값은 이전 초안의 문자열 표기로 적고, 도구가 2025.10 객체 값을 지원하면 옮긴다(open-items 46). 이름에 마침표·중괄호를 쓰지 않고(`0_5`·`1_5`), 형식이 없는 무늬는 확장 칸 `com.peaket.pattern`으로 옮기며, 토큰 CI가 이름·형식·별칭을 검사한다(모두 추천 적용).
- **바꾼 문서**: design/tokens.json, design/d2 §1, docs/frontend.md §5.11·§6.4, docs/architecture.md §6.5, review/open-items.md 46, ADR-0040 상태 줄

#### 중간-100 '곧 입장합니다' 글자 모션의 aria-label 방식은 낭독기에서 읽히지 않을 수 있다
- **문제**: 글자를 감싼 span에 모두 `aria-hidden="true"`를 붙이고 원래 문장은 바깥 요소의 `aria-label`로 주는 방식인데, 바깥 요소가 span·div면 역할이 generic이라 aria-label이 금지되어 무시될 수 있다. 입장 직전이라는 가장 중요한 안내가 화면 낭독기 사용자에게 빠진다.
- **결정**: 글자 단위 모션의 원래 문장은 화면에서만 숨긴 글로 두고 글자 묶음은 `aria-hidden`이다. 역할 없는 span·div에는 `aria-label`을 쓰지 않는다(추천 적용).
- **바꾼 문서**: design/d1 §5, design/d2 CMP-015, design/d5 §5.8, design/d4 §1 #8, docs/frontend.md §5.11·§5.17

#### 중간-101 '비활성 버튼 + 툴팁'은 키보드·휴대폰에서 이유가 전달되지 않는다
- **문제**: 결제 버튼(필수 동의 전), 관리자 전용 버튼, 권한 없는 명령 카드(CMP-036 '툴팁 글자'), 요청자 본인의 승인 버튼, 판매 승인 버튼이 모두 '비활성 + 이유'다. 기본 `disabled` 버튼은 초점을 받지 못해 Tab으로 가면 건너뛰고, 마우스 이벤트도 막혀 툴팁이 뜨지 않으며, 휴대폰에는 마우스 올리기가 없다. 그래서 d4가 요구하는 '비활성 이유가 읽혀야 한다'를 지금 방식으로는 채우기 어렵다. 저장소 어디에도 `aria-disabled` 규칙이 없다.
- **결정**: 이유를 알려야 하는 비활성 버튼은 `aria-disabled`로 초점을 받게 하고 동작만 막으며, 이유는 버튼 옆에 늘 보이는 글로 두고 `aria-describedby`로 잇는다. 툴팁만으로 이유를 전하지 않는다(추천 적용, d2 §3.6).
- **바꾼 문서**: design/d2 §3.3·§3.6·CMP-001·CMP-003·CMP-036, design/d3 SCR-011·020·030·046·048·064, design/d5 §7.3, design/d4 §1 #26·§2, docs/frontend.md §4.8·§5.11·§5.17


### 자. 기획·정책·문서의 정확성

#### 중간-102 CloudFront 요청 단가를 HTTP 값으로 계산했다(약 198달러 → 약 264달러, 결론은 같음)
- **문제**: 100만 명 실측을 하지 않는 비용 근거가 HTTP 요청 단가(1만 건당 0.009달러)로 계산되어 있다. 대기 상태 조회는 HTTPS다(NFR-016 TLS 1.2 이상). 2026-10-10 첫 비용 조사(소유자 메모)는 100만 건당 1.20달러(HTTPS)를 썼는데, ADR-0057 작성 때 HTTP 단가로 바뀌었다.
- **결정**: 100만 명 실측을 하지 않는 비용 근거의 요청 단가를 HTTPS 값(한국, 가격표의 'Asia Pacific' 지역 1만 건당 0.012달러, AWS 가격표 2026-10-19 게시본, 2026-10-28 원문 확인)으로 고쳤다. ADR-0110 뒤 숫자로 다시 계산하면 약 2.3억 건에 약 273달러(1,400원/달러 가정 시 약 38만 원)이고, 지출 상한(5만 원)을 넘는다는 ADR-0057의 결론과 결정은 그대로다(소유자 승인 '추천안 동의', 숫자는 정정).
- **바꾼 문서**: docs/verification.md §1.2·§4, planning/01 §4.2·§5.2, planning/00-executive-summary §6, guide/12, ADR-0057·ADR-0110 상태 줄

#### 중간-103 공연법 과징금 대상을 플랫폼처럼 적었다
- **문제**: 경영 요약 §2가 '예매 플랫폼에 방지 조치 의무와 최대 50배 과징금을 두었다'고 써서, 경영진이 플랫폼이 판매금액 50배 과징금을 맞을 수 있다고 오해할 수 있다. 01 §1.1 표의 '매크로를 썼는지와 관계없이 부정구매 행위가 전면 금지'는 원문의 '재판매를 목적으로' 요건을 뺐다.
- **결정**: 경영 요약과 개요의 공연법 요약을 원문(공연법 2026-08-28 시행본, 2026-10-28 확인)대로 고쳤다. 금지 대상은 '되팔 목적'의 부정구매와 웃돈 부정판매이고(§4의2①), 판매자·통신판매중개업자에게는 방지 조치 의무가(§4의2②), 부정판매한 사람에게는 판매금액 50배 이하 과징금이(§4의4①) 있다. 과징금은 플랫폼의 조치 의무에 매기는 것이 아니다(원문 이어받음 문구 정정).

#### 중간-104 봇 점유율 계산이 '추가 검증을 통과한 봇'을 빼고 셈한다
- **문제**: K6의 '탐지'는 추가 검증 큐로 보내거나 차단한 것이다(perf-ledger §10.2). 추가 검증은 사람 확인과 본인확인을 다시 하는 것이라, 대여 명의와 사람 확인 풀이 서비스(문서가 1,000건에 1.45달러, 풀이 성공률 95% 설정까지 둠)를 쓰는 봇은 통과해 원래 순번으로 돌아갈 수 있다. 그런데 사업 지표의 봇 점유율 4.8%는 탐지된 봇이 모두 빠진다고 계산했다. 탐지율이 높아도 추가 검증 통과율이 높으면 봇 점유율 목표(5% 이하)를 지키지 못한다.
- **결정**: 탐지는 차단이나 추가 검증으로 보내는 것이고 대여 명의 봇은 추가 검증을 통과할 수 있으므로, 표준 시나리오의 봇 점유율을 '미탐지 봇 + 탐지 봇 × 추가 검증 통과율 r'로 계산한다(소유자 승인 '추천안 동의'). r은 [가정]으로 두고 K6가 풀이 성공률별로 재며, 끝에서 끝까지의 봇 성공률과 함께 Wilson 구간으로 보고한다. 합격 판정은 탐지율 그대로다. r이 약 0.25%를 넘으면 표준 시나리오에서 5%를 넘는다(추천 적용).
- **바꾼 문서**: planning/01 §3.2·§5.2, planning/02 NFR-022, docs/perf-ledger.md §10.2·§10.5, docs/features/analytics.md §9, guide/12
- **남는 한계**: planning/01 §5.2 '명의 대여 및 도용 봇 차단 한계' 행에 '추가 검증을 통과한 봇은 봇 점유율에 그대로 들어가고, r이 약 0.25%를 넘으면 표준 시나리오에서 목표를 넘으므로 K6에서 재어 보고한다'를 덧붙였다(새 줄은 만들지 않음)

#### 중간-105 매진 순간 '97만 명 동시 새로고침을 k6로' 문장이 100만 미실측 결정과 모순된다
- **문제**: POL-015 (6)과 queue-admission §8 6은 잔여 대기자 97만 명의 동시 새로고침을 k6로 흉내 내 원본 트래픽을 잰다고 한다. 소유자 결정 ADR-0057과 NFR-013은 100만 명 전체 실측을 하지 않고, 로컬 실측은 10만 명까지, CDN 동작은 '문서 인용', 원본 응답은 축소 실측과 설계 식 외삽으로 표시한다고 정했다. 면접에서 '97만 명을 돌렸다'로 읽힐 수 있다.
- **결정**: 매진 직후 몰림은 로컬 1만·10만 명 축소 실측으로 원본 요청 증폭 배수를 재고, 97만 명 규모는 그 배수와 설계 식으로 외삽해 '외삽(설계 식)'으로, CDN 엣지 동작은 문서 인용으로 표시한다. 97만 명 전체는 돌리지 않는다(소유자 승인 '추천안 동의', 판정 폭 ±10%는 추천 적용).
- **바꾼 문서**: planning/03 POL-015, docs/features/queue-admission.md §8·§11(Q-T14), docs/verification.md §3.1

#### 중간-106 용어 사전의 p99·번 레이트 등 기술 정의가 원문과 다르다
- **문제**: 지연 NFR 거의 전부가 p99로 적혀 있고 경보·자동 감축이 번 레이트 배수(2분 10배, 1시간 14.4배)로 돌아가는데, 사전 정의가 둘 다 원문과 다르다. p99를 '100건 중 99건(상위 99%)이 기준 시간 이내에 성공적으로 끝났다'로 적어 성공·실패와 섞었고 '상위 99%'는 반대로 읽힐 수 있다. 번 레이트는 '오류 예산이 시간에 따라 줄어드는 속도'로만 적어 '배수'라는 뜻이 없고, 에러 버짓을 '가용성 목표'에 한정했다(이 프로젝트의 예산은 지연 SLO에도 걸린다).
- **결정**: 용어 사전의 p99를 '지연 분포의 99번째 백분위수(빠른 순 99번째, 히스토그램 칸으로 어림)'로, 에러 버짓을 'SLO(가용성·지연)가 허용하는 나쁜 사건 총량(1 − 목표)'으로, 번 레이트를 '지금 나쁜 사건 비율 ÷ 허용 비율(1이면 기간 끝에 꼭 다 씀)'로 고쳤다(SRE Workbook 5장 원문 확인, 원문 이어받음 정정). 같은 묶음의 Outbox(원자적인 것은 상태 변경과 Outbox 행, 발행은 적어도 한 번), 구간(대기 상태 파일·CDN 캐시 단위), 펜싱 토큰(입장 제어 리더는 리더 세대), realtime-gw(구독한 구역만), 그림자 실행(규칙), 외삽(설계 식 주, USL N은 진입 서버 대수, 외삽 배수 정의)도 정본에 맞췄고, POL-017의 '(CRL)'은 X.509 이름과 겹쳐 뺐다.

#### 중간-108 data.md 경합 표의 '원자적 파이프라인'은 틀린 표현이다
- **문제**: data.md 경합 표 '1인 1순번 보장' 행은 진입 3단계를 "원자적 파이프라인으로 처리"한다고 적었다. Redis 파이프라인은 여러 명령을 한 번에 보내는 것일 뿐 원자적이지 않다. 또 `q:dup:{pid}:E`(사람 슬롯)와 `q:{event:E}:seq`(회차 슬롯)는 해시 슬롯이 달라 Redis Cluster에서 MULTI나 Lua 하나로 묶을 수 없다. queue-admission §3은 '차례로 실행하고, 기록 전에 실패하면 빠진 번호로 보정'으로 맞게 적었다. 구현자가 data.md를 보고 MULTI를 쓰면 교차 슬롯 오류가 난다.
- **결정**: 1인 1순번 진입 3단계는 차례로 실행하고(두 키의 해시 슬롯이 달라 MULTI·Lua 하나로 묶을 수 없고, 파이프라인은 원자적이지 않다), 기록 전에 실패한 번호는 빠진 번호 비트맵으로 보정한다고 고쳤다(queue-admission §3와 같은 뜻, 원문 이어받음 정정).
- **바꾼 문서**: docs/data.md §5

#### 중간-109 guide/가 오늘 정한 ADR-0092·0093·0094를 반영하지 않았다
- **문제**: 11편 ②의 1단계 항목은 '공연명, 아티스트, 장르, 관람 연령, 러닝타임, 설명·이미지, 공연예술통합전산망 항목'이다. 2026-10-27 정본(SCR-021, ADR-0093)은 1단계에 ① 공연장(목록에서 고르거나 새 공연장을 요청) ② 아티스트(목록에서 고르거나 새 이름) ③ 공연의 다른 이름(영문 표기 등 5개 [가정])을 두고, 2단계 회차는 '같은 공연장·같은 배치본'이어야 하며 판매 승인 뒤에도 회차를 더할 수 있고 더하면 재승인 대기가 된다. 판매 승인은 공연(회차 묶음) 단위이고 공연 규모와 대형 공연끼리의 30분 간격은 회차마다 정한다. guide는 아티스트를 글자 칸처럼 적고, 공연장 고르기·다른 이름·회차 더하기가 없다. 이 칸들은 오늘 다시 설계한 검색(아티스트·공연장 후보와 필터, 다른 이름 찾기)의 전제라서, 빠지면 검색 결과가 어디서 오는지 설명이 끊긴다.
- **결정**: guide를 정본에 맞췄다. 11편 공연 등록(공연장·아티스트·다른 이름, 같은 공연장·배치의 회차, 승인 뒤 회차 더하기, 승인은 공연·규모와 30분 간격은 회차), README 용어(공연·회차·공연장·다른 이름과 읽기 규칙), 단위가 규칙을 바꾸는 문장을 회차로(02 대기표, 03 동시 입장 목표, 10 결제사 지정, 14 사건 순서, 18 좌석맵·찜 주소), 검색 설명(14·17·18), 관제 원격 위젯의 읽기 전용 계약(17), ADR-0110의 좌석 델타 0.1초(12·17)(guide는 규범이 아니며 정본의 쉬운 번역이다).
- **바꾼 문서**: guide/README·02·03·10·11·12·14·17·18

#### 중간-110 guide/15가 비율 평균 문제를 '심슨의 역설'이라고 잘못 부른다
- **문제**: 15편 ④ 원칙 1은 "전환율을 직접 저장하면 회차를 합산할 때 왜곡(심슨의 역설)이 발생"한다며, A회차 90/100과 B회차 7,000/10,000의 단순 평균 80%와 합친 값 70.2%의 차이를 예로 든다. 이 예는 '크기가 다른 묶음의 비율을 그냥 평균하면 큰 묶음의 무게가 사라진다'는 비가산 측정값 문제다. 심슨의 역설은 묶음마다 보이는 경향(예: 두 회차 모두에서 AUTO가 PICK보다 높음)이 묶음을 합치면 뒤집히는 현상으로, 다른 이론이다. 정본은 이 규칙을 "킴볼의 비가산 측정값 처리"라고만 적었다. guide는 면접관이 읽는 문서라 통계 용어를 잘못 쓰면 설계 전체의 신뢰를 깎는다.
- **결정**: 비율을 저장하지 않는 이유를 '비가산 측정값(크기가 다른 회차의 비율을 그냥 평균하면 큰 회차의 무게가 사라짐)'으로 고치고, 심슨의 역설은 '같은 규모끼리 비교하는 이유'로 옮겼다(정본 ADR-0052는 바르다, guide 문구 정정).
