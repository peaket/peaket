# ADR-0211: 공연 상세에서 사전 검증 토큰을 받아 대기실로 넘기는 데 필요한 빈칸을 채운다

- **상태**: 채택(2026-11-05, 추천 적용). BUILD_ORDER HOT-342 ①.
- **관련**: [docs/frontend.md](../frontend.md) §3.1 화면 데이터 표(사전 검증 토큰)·§3.12 저장소·§4.2.1 3번·§4.8 CMP-047·§5.14.2 외부 스크립트, [docs/design/d5-screen-blueprint.md](../design/d5-screen-blueprint.md) §5.2 SCR-002 ⑦ 상태 표, [docs/api/openapi.yaml](../api/openapi.yaml) `POST /v1/queues/{eventId}/pre-verifications`·`PreverifyResult`·`BehaviorSummary`, ADR-0065 결정 9, ADR-0207, ADR-0208
- **관련 ID**: SCR-002, SCR-008, FE-T3

## 맥락

- HOT-340 ①·HOT-341 ①로 대기실은 저장소(`peaket.queue.{eventId}`)의 사전 검증 토큰으로 진입한다. 토큰이 없으면 공연 상세로 돌려보낸다(ADR-0207 결정 4).
- 그런데 공연 상세는 아직 사전 검증 토큰을 받지 않는다. [대기열 들어가기]를 누르면 공연 상세와 대기실 사이를 오갈 뿐 대기열에 들어가지 못한다.
- HOT-342는 이 경로와 함께 여러 일을 묶었다: 좌석 자원 미리 받기, HOT-340이 넘긴 매진 화면 취소표 알림·예매 제한 소명 링크·숫자 굴림, BAS-170이 넘긴 React QueuePanel 비교, BAS-210이 넘긴 세 엔진 브라우저 검사(FE-T3·FE-T15·FE-T4), HOT-311이 넘긴 예매 버튼의 예매 제한·선예매·판매 정책 상태.
- 개발 서버에서 공연 상세(3000)와 대기실(3004)은 출처가 달라 localStorage를 나누지 않는다. 운영은 둘 다 `www` 출처다.

## 결정

1. **HOT-342를 셋으로 나눈다.**
   - HOT-342 ①(이 단계): 공연 상세의 사전 사람 확인 카드(CMP-047)와 사전 검증 토큰 받기·저장·조용한 갱신, [대기열 들어가기]에서 대기실로 넘기기, 개발 서버의 같은 출처 흉내, 가짜 API의 사전 검증 경로.
   - HOT-344(새 단계): 예매 버튼의 예매 제한(`GET /v1/booking-restrictions/me`, ( 소명하기 › ) → SCR-042)·선예매 대상·판매 정책 자격 없음, 대기실 예매 제한 화면의 ( 소명하기 › ), 매진 화면(SCR-018)의 [취소표 알림 받기], 앞 인원 숫자 굴림.
   - HOT-345(새 단계): 대기실 좌석 자원 미리 받기(`seatmapLayoutPath`·`/_q/seat-preload.json`)와 대기실 세 엔진 브라우저 검사(FE-T3 T=0 두 호출의 사전 요청 0, FE-T15, FE-T4 브라우저 칸, FE-T6 세 엔진, React QueuePanel과 대기실 셸의 FE-T40 비교).
   - 까닭: ①이 없으면 오픈 뒤 경로를 쓸 수 없다. 나머지는 서로 다른 API(예매 제한·판매 정책·알림 신청)와 검사 틀(같은 출처로 두 앱을 띄우는 Playwright)이 필요하다.
2. **사전 사람 확인 카드(CMP-047)가 보이는 때**
   - 선착순(로비 없음) 공연의 오픈 전: "오픈 전에 확인을 마쳐 두세요" 카드(d5 §5.2 '사전 사람 확인'). 통과하면 '확인 완료'와 남은 시간이다.
   - 오픈 뒤(모든 정렬 방식): [대기열 들어가기]를 누를 때 유효한 토큰이 없으면 같은 카드를 띄우고, 통과하면 바로 대기실로 간다. 유효한 토큰이 있으면 바로 간다.
   - 로비 공연의 오픈 전에는 띄우지 않는다. 로비 참가의 사람 확인은 대기실이 한다(ADR-0208 결정 3).
   - 비로그인·가입 미완료·본인확인 전에는 띄우지 않는다. 개인 상태 버튼(로그인·가입·본인확인)이 먼저다.
3. **위젯과 본문**
   - 위젯은 Turnstile `render=explicit`, `action` `preverify`다(bot-defense §6). 공연 상세 CSP는 이미 사람 확인 출처를 허용한다(`/events/[id]`의 `humanCheck` 변형). 개발 서버는 대기실과 같은 모양의 시뮬레이터를 쓰고 운영 빌드에는 들지 않는다.
   - 본문은 `{humanCheckToken, deviceId, behaviorSummary, preverifyToken?}`(JSON, 자격 증명 포함)이다. 갱신할 때는 지금 가진 토큰을 실어 최초 발급 시각과 여정 ID를 잇는다(openapi).
   - 행동 신호 요약(`BehaviorSummary` v1)은 공연 상세가 열린 동안의 포인터 이동 수·방향 엔트로피(8방향)·입력 간격 평균과 표준편차·구간 길이만 잰다. 좌표·키 값·글자는 남기지 않는다(ADR-0065 결정 9). 계약의 나머지 칸은 [가정, wbs 3.2.1]이라 비운다.
4. **응답과 저장**
   - 201: `peaket.queue.{eventId}`에 `preverifyToken`·발급 시각·만료 시각을 쓴다(그 회차의 다른 값은 그대로 둔다). 화면은 '확인 완료'와 남은 시간이다.
   - 위젯은 카드 안이 아니라 대화상자 안 자리 하나에 그린다. 카드는 휴대폰 히어로와 데스크톱 패널에 하나씩 그려지므로 위젯을 두 번 그리지 않게 하려는 것이다.
   - 만료 2분 [가정] 전에 위젯을 화면 밖 숨긴 자리에서 보이지 않는 모드(`interaction-only`)로 다시 돌려 조용히 갱신한다. 숨겨져 있었으면 다시 보일 때 한다. 일시 실패(위젯을 못 불러옴·429·503·연결)는 만료 전까지 늘려 가며 다시 한다. 조작이 필요하면(위젯의 `before-interactive-callback`) 숨긴 자리에서 조작을 요구하지 않고 갱신을 멈춘다. 그러면 만료 뒤 카드가 다시 '사람 확인'과 [확인하기]로 돌아온다(§4.2.1 3번의 '조작이 필요하면 위젯을 보인다'를 이렇게 정한다). 대기실이 키를 지웠거나(입장) 이미 줄을 섰으면 갱신하지 않는다(키를 되살리지 않게).
   - 저장하는 시각 칸(`preverifyIssuedAt`·`preverifyExpiresAt`·`savedAt`)은 정수로 쓴다. 대기실 저장소는 정수가 아닌 칸이 있으면 값 전체를 버린다(브라우저 확인에서 찾음).
   - 계약의 응답은 201·400·403·404이다. queue-svc는 위험 판정이 장애여도(축소 운영) 토큰을 주므로 사람 확인 실패를 따로 거절하지 않는다(그 표시는 진입 때 추가 검증으로 간다).
   - 401(팬 토큰 만료): 갱신 한 번 뒤 다시, 또 401이면 로그인. 403 `identity-verification-required`: 개인 상태(팬 계정 요약)를 다시 읽는다(본인확인 버튼). 404 `queue-not-found`: "대기열이 아직 열리지 않았습니다. 잠시 뒤 다시 시도해 주세요". 400·그 밖 403: '사람 확인 실패'와 [다시 시도]. 게이트웨이의 429·503(차단기, guidelines §2)과 연결 실패: `Retry-After`(정수 초나 HTTP 날짜) 하한 위 지터의 실제 시각에 자동으로 다시 보낸다. 화면의 남은 초는 표시만 한다(d5 '진입 혼잡'과 같은 꼴).
   - 위젯을 불러오지 못한 것('사람 확인을 불러오지 못했습니다')과 사람 확인 실패를 나눠 보인다(§5.14.2). 저장하지 못하면 대기실로 가지 않고 안내한다.
   - 저장소에 이미 대기 진행(대기표·참가 토큰·진행 중 진입)이 있으면 [대기열 들어가기]는 사람 확인 없이 대기실로 간다.
   - 대기실은 진입 403 `preverify-invalid`를 받으면 사전 검증 세 칸도 지운다(남기면 공연 상세가 그 토큰으로 다시 보내 두 화면을 오간다).
5. **개발 서버의 같은 출처 흉내**: 소비자 웹 개발 서버(`next dev`)가 대기실 경로(`/queue/{id}`, `/shop/{id}/queue`)와 대기실 자산(`/_q/*`)을 대기실 개발 서버로 넘긴다(운영의 CloudFront 경로 나눔과 같다). 대기실 개발 서버도 자산을 `/_q/` 아래에 두고, 변경 반영(HMR)은 대기실 포트로 바로 잇는다. 그래서 개발에서도 [대기열 들어가기]는 같은 출처 `/queue/{id}`이고 저장소를 나눈다. 넘길 곳은 `PEAKET_DEV_QUEUE_ROOM_ORIGIN`(기본 `http://localhost:3004`)이다.

## 결과

- 공연 상세 → 사전 사람 확인 → 대기실 진입이 개발 서버에서 같은 출처로 이어진다. 가짜 API에 사전 검증 경로와 상태 바꾸기(`queuePreverify`)를 더한다.
- 남는 한계: 행동 신호 요약은 첫 판(v1)의 몇 칸만 잰다(나머지는 wbs 3.2.1). 대기실과 공연 상세는 사람 확인 불러오기 코드를 따로 갖는다(대기실은 React를 쓰지 않는다).

## 다른 선택지

- 개발에서만 토큰을 주소 조각(`#`)으로 넘기기: 운영과 다른 경로를 하나 더 두고, 토큰이 기록에 남을 수 있어 고르지 않았다.
- 공연 상세가 진입(`POST …/entries`)까지 하고 대기표를 넘기기: 진입 응답(202·409·429·503)을 두 화면이 나눠 다루게 되고, 대기실이 이미 그 상태표를 갖는다(ADR-0207 결정 4)라 고르지 않았다.
