# ADR-0219: 엣지 매진 표시는 queue-svc가 판매 상태 사건마다 판 번호와 함께 맞추고, 대기 상태 파일의 남은 좌석 수는 판매 상태 사건의 다시 내기로 받는다

- **상태**: 채택(2026-11-06, 추천 적용. wbs 2.2.3 세부는 추천 적용이라는 승인 2026-10-28을 따른다). 결정 4(엣지 저장소에 쓰는 권한)는 소유자 결정 대기다(docs/PROGRESS.md OPEN[25]). BUILD_ORDER HOT-011(wbs 2.2.3 ①-②). 실제 KeyValueStore 어댑터와 패키지 받기도 소유자 결정 대기다(OPEN[24], HOT-012). 같은 날 새 맥락 리뷰(높음 1, 중간 5, 낮음 9)로 결정 2·3·4·5·7·8을 고쳤다. 높음 1은 결정 4의 '같은 저장소에 쓰는 위험 수용'이었고, ADR-0053 결정 2를 뒤집는 일이라 소유자에게 돌렸다.
- **관련**: ADR-0053 결정 2(도착 시각 쿠키 키를 KeyValueStore에 둠, 그 저장소를 읽고 쓰는 IAM 주체는 배포 역할뿐), ADR-0102 결정 2(일시정지를 엣지에서 집행하지 않음), ADR-0122(회차 판매 상태와 매진 풀림, 엣지 응답을 queue-svc가 켬), ADR-0142(서비스 소비자의 키 단위 처리), ADR-0197(대기 상태 파일의 칸), ADR-0214(판매 상태를 판 번호로 씀), ADR-0216(좌석 자원 미리 받기), [docs/features/queue-admission.md](../features/queue-admission.md) §4 '엣지 매진 표시와 좌석 수 칸의 첫 구현'·§8, [docs/infra.md](../infra.md) §4.1 '엣지 매진 응답', [docs/data.md](../data.md) §3 `q:{event:E}:notice`·`q:{event:E}:cfg`, [docs/security/secrets-and-keys.md](../security/secrets-and-keys.md) 도착 시각·최초 방문 쿠키 서명 키 행, [docs/security/asvs/queue-admission.md](../security/asvs/queue-admission.md), [docs/review/open-items.md](../review/open-items.md) 54번
- **관련 ID**: FR-018, POL-015, Q-T51, Q-T54, Q-T63, Q-T64, ASVS v5.0.0-13.3.2, ASVS v5.0.0-15.4.2, ASVS v5.0.0-16.5.2

## 맥락

- 매진(`SOLD_OUT`) 판이 서면 새 진입을 엣지(사용자 가까이에 둔 CDN 서버)에서 410으로 바로 끝내고, 매진이 풀리거나 판매가 끝나면 그만둔다(POL-015 (2), queue-admission §8의 2·7). 켜는 쪽은 queue-svc다(ADR-0122 결정 4). 그런데 길(CDN 배포 설정을 바꾸나, 엣지 함수가 읽는 키·값 저장소를 바꾸나)과 값의 모양, 실패할 때의 동작이 정해지지 않았다(open-items 54번).
- 저장소에 엣지 함수 코드가 없다. 엣지 함수가 읽을 값의 꼴을 이 단계에서 정해야 한다.
- KeyValueStore(CloudFront 엣지 함수가 읽는 AWS의 키·값 저장소)를 부르는 AWS SDK 클라이언트가 저장소에 없고, 받는 일은 소유자 허락이 필요하다(OPEN[24]). 그래서 이 단계는 queue-svc 안의 포트(바깥 저장소와 맞닿는 연결부의 틀)와 시험 대역(진짜 대신 쓰는 시험용 구현)만 만든다.
- 대기 상태 파일의 세 칸이 비어 있다(BAS-042, openapi `QueueState`).
  - `remainingSeats`: 좌석 원장(좌석 Redis 비트맵과 purchase DB)에서 받은 남은 좌석 수. 받는 길이 없다.
  - `avgTicketsPerOrder`: 공연 평균 구매 매수(POL-015 (1)). 정하는 법이 없다.
  - `seatmapLayoutPath`: 그 회차 좌석맵 파일의 경로. queue-svc는 좌석맵 판 번호를 모른다.
- AWS 문서에서 확인한 것(2026-11-06):
  - CloudFront 한도 표: 함수 하나에 붙는 키 값 저장소는 1개다. 키는 512바이트, 값은 1KB, 저장소 하나는 5MB, 한 번에 바꾸는 키는 50개까지다(https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-limits.html ).
  - 서비스 권한 참조: KeyValueStore의 IAM(누가 무엇을 할 수 있는지 정하는 AWS 권한 체계) 자원은 저장소 하나이고, 키 이름으로 나누는 조건 키가 없다(https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazoncloudfrontkeyvaluestore.html ).
  - CloudTrail(AWS 호출 기록)은 KeyValueStore를 데이터 사건 종류(`AWS::CloudFront::KeyValueStore`)로 기록할 수 있고, 데이터 사건은 기본으로 꺼져 있으며 따로 요금이 든다(https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-data-events-with-cloudtrail.html , https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/logging_using_cloudtrail.html ).
  - 값이 모든 엣지에 퍼지는 시간은 AWS 블로그(2023-11)의 '몇 초 안에'뿐이고 보장 수치가 아니다(ADR-0122 상태 줄, 그대로 확인 필요).

## 결정

1. **길은 KeyValueStore 값이고, 값의 꼴은 아래로 정한다.**
   - 배포 설정을 바꾸는 길은 쓰지 않는다. 설정 변경은 퍼지는 시간이 문서에 없고, 세 큰 배포는 지속적 배포로 단계를 밟으며, 온세일 중에는 동결된다(docs/infra.md §4.1, docs/devops.md §5.4).
   - 키: `sale:{회차 ID}`(회차 ID는 키 조각 모양 1~64자라 512바이트 안이다).
   - 값: JSON `{"soldOut": 참·거짓, "version": 판 번호, "expireAtMs": 유닉스 밀리초}`. `version`은 그 회차 `notice`의 `saleVersion`이다. `expireAtMs`는 판매 종료(공연 시작 24시간 전) 시각이고, 일정 사본이 없으면 지금 + 2일 [가정]이다(`notice`의 대체 수명과 같다).
   - 엣지 함수: 대기열 API 배포의 진입 경로(`POST /v1/queues/{eventId}/entries`) 시청자 요청 함수가 그 키를 읽는다. `soldOut`이 참이고 `expireAtMs`가 함수 시작 시각보다 뒤일 때만 원본에 보내지 않고 410을 바로 낸다. 키가 없거나 값을 읽지 못하면(저장소 읽기 오류 포함) 원본으로 보낸다(원본 410이 마지막 방어다, ADR-0122). 410은 원본의 진입 410 `sold-out`과 같은 Problem JSON(`application/problem+json`, `type`·`title`·`status`)이고, `Cache-Control: no-store`·`nosniff`·`gw-queue`와 같은 교차 출처 머리를 싣는다.
   - 판매 종료 뒤에는 원본이 410 `sale-ended`를 내므로, 엣지는 `expireAtMs`가 지난 값을 무시한다. 지난 값은 어댑터가 지운다(저장소 5MB 안에 두려고, HOT-012).
2. **맞추는 때와 차례: 판매 상태 사건을 받을 때마다 `notice`의 지금 판으로 맞춘다.**
   - 매진 판이면 `notice`를 쓰기 전에 엣지를 먼저 켠다(POL-015 (2)·(3)의 차례, Q-T54 ①). 그 판이 `notice`보다 옛 판이어도 괜찮다. 바로 뒤의 맞추기가 `notice`의 지금 판으로 되돌린다.
   - `notice`를 쓴 뒤(쓰지 않은 STALE 포함), Lua가 돌려준 `notice`의 지금 판매 상태와 판 번호로 바라는 값(`SOLD_OUT`이면 켬, 그 밖은 끔)을 정해 쓴다. 판매 종료(`ENDED`)도 끔이다.
   - 파드는 마지막으로 쓴 값(켬·끔과 판 번호)을 메모리에 60초 [가정] 둔다. 같은 값이면 다시 쓰지 않는다. 60초가 지나면 다시 쓴다. 다른 파드가 그 사이 옛 값을 덮었을 때(소비자 재조정 동안 두 파드가 겹침) 1분 안에 바로잡힌다.
   - 저장소에는 끈 값도 판 번호와 함께 둔다(지우지 않는다). 그래야 늦게 쓴 옛 켬이 새 끔을 덮지 않는다. 포트는 저장된 판이 더 크면 바꾸지 않고 '저장된 판이 더 큼'(`NEWER_STORED`)을 돌려준다.
   - `notice`의 지금 판으로 쓰려는데 저장된 판이 더 크면 `notice`를 다시 읽는다. 읽은 뒤 처리기가 더 큰 판을 썼으면(이쪽이 옛 판을 쓰려던 것) 세지 않는다. 정말 `notice`보다 크면(꾸민 값이거나, 대기열 Redis 장애 전환으로 `notice`를 잃었다) 조용히 넘기지 않고 경고 한 줄과 함께 '앞선 회차 수'(`queue_edge_flag_ahead_events`)로 센다. 다시 읽지 못하면 셈에 넣지 않고 다음 다시 맞추기가 본다. `notice`가 따라오거나 운영자가 엣지 값을 지우면 다시 맞추기가 0으로 돌린다.
   - 실제 어댑터는 저장소 전체의 ETag(저장소가 바뀔 때마다 바뀌는 판 표시)를 읽고, `IfMatch`(그 판일 때만 쓰라는 조건)로 쓴다. 다른 쓰기가 먼저 끝나 판 표시가 바뀌면 조건 실패(412)가 나므로, 마감(2초) 안에서 판 표시를 다시 읽고 3번 [가정]까지 다시 쓴다(HOT-012).
3. **엣지 저장소가 안 되면 던지지 않고, 파드 안에서 다시 맞춘다.**
   - 쓰기 마감은 2초 [가정]이고 SDK 안에서 다시 시도하지 않는다(조건 실패의 다시 쓰기만 마감 안에서 한다). 실패하면 경고 한 줄(회차 ID, 켬·끔, 오류 요약)을 남기고 실패 수(`queue_edge_flag_failures_total`)를 센다.
   - 그래도 판매 상태(`notice`)는 쓴다. 던져 일시 실패로 다시 하면 그 파티션 전체가 멈춰 다른 회차의 매진 반영까지 늦어진다.
   - 쓰기는 차단기(계속 실패하는 호출을 잠시 끊는 장치, 의존성 `edge-kvs`) 안에서 한다. 30초 창에서 쓰기 3번 이상이고 실패가 절반 이상이면 10초 동안 부르지 않는다 [가정]. 그래서 엣지가 답하지 않을 때 늦어지는 것은 차단기가 열리기 전의 쓰기 몇 번(한 번에 최대 2초)뿐이다. 매진 판의 '엣지 먼저'가 그때 `notice` 쓰기를 최대 2초 늦출 수 있고, 차단기가 열린 뒤에는 늦추지 않는다.
   - 다시 맞추기: 맞추지 못한 회차와 앞선 회차는 파드 메모리에 따로 두고, 파드 안 반복이 5초 [가정]마다 `notice`의 지금 판매 상태와 판 번호를 다시 읽어 다시 쓴다. 엣지 값의 만료도 그때 일정 사본의 판매 종료로 다시 정한다. 한 번에 100회차 [가정]를 보고, 본 회차는 뒤로 보내 돌아가며 본다. 기록에는 그때 바라던 판 번호를 두고 그 판 이상을 쓴 때만 지운다(다시 맞추기의 옛 판 쓰기가 늦게 끝나 처리기의 새 판 실패 기록을 지우지 않게, 재검토 2026-11-06). 다른 파드로 파티션이 넘어간 회차도 같은 값을 쓰므로(판 번호로 차례를 지킨다) 저장소가 답하는 대로 셈에서 빠진다. `notice`가 사라진 회차(수명이 끝남)와 엣지 값의 만료(판매 종료)가 지난 회차도 뺀다. 그래서 내는 쪽의 다시 내기(PRF-144)가 없어도 다시 맞춘다. 처리기는 파티션을 언제 잃었는지 받지 않아(플랫폼 소비자가 넘기지 않는다), 잃은 회차를 따로 고르지 않고 이 다시 쓰기로 정리한다.
   - 맞추지 못한 회차 수(`queue_edge_flag_unsynced_events{want}`, `want`는 `on`·`off`)를 파드마다 낸다. 끔을 맞추지 못한 상태(엣지가 판매 중인 회차의 진입을 막고 있을 수 있다)가 1분 [가정] 이어지면 SEV2, 켬을 맞추지 못한 상태(원본 410이 막으므로 원본 부하만 는다)가 1분 [가정] 이어지면 SEV3이다. 앞선 회차가 1분 [가정] 넘게 있으면 SEV2다(엣지가 판매 중인 회차를 막고 있을 수 있고, queue-svc가 바로잡지 못한다).
   - 멈춤 스위치: 환경 값 `PEAKET_EDGE_SYNC`가 멈춤이면 queue-svc는 엣지를 쓰지 않는다(바꾸면 다시 시작한다). 앞뒤 공백을 빼고 소문자로 맞춘 뒤 `off`·`false`·`0`은 멈춤, `on`·`true`·`1`·빈칸·없음은 켬이고, 그 밖의 값은 시작에 실패한다(잘못 쓴 값이 조용히 켬이 되지 않게. 굴려 바꾸는 배포라 새 파드만 뜨지 못한다). 엣지 값을 손으로 바꾸는 런북이 먼저 켠다. 켜지 않으면 다시 맞추기가 1분 안에 손으로 바꾼 값을 되돌린다. 다시 시작 없이 바꾸는 스위치(관제 명령)는 HOT-012가 정한다.
4. **엣지 저장소에 쓰는 권한: 소유자 결정 대기(OPEN[25]).**
   - 함수 하나에 저장소는 하나뿐이다. 진입 경로의 시청자 요청 함수는 도착 시각 쿠키 서명(ADR-0053 결정 2, HOT-020)도 한다. 그래서 queue-svc 역할이 그 저장소에 바로 쓰면, 매진 표시와 서명 키가 같은 저장소에 든다. 최초 방문 쿠키 서명 키도 같은 함수·저장소에 두면 그것도 든다.
   - KeyValueStore의 IAM은 저장소 단위이고 키 이름으로 나누는 조건 키가 없다. 그래서 queue-svc 역할에 그 저장소의 `GetKey`·`PutKey`·`DeleteKey`를 주면 아래 위험이 생긴다.
     - (a) 읽기: queue-svc의 AWS 자격만 새도(예: 서버가 내부 주소를 부르게 하는 SSRF로 Pod Identity 자격을 가져감) `GetKey`로 도착 시각 쿠키 서명 키를 읽는다. 최초 방문 쿠키 서명 키가 같은 저장소면 그것도 읽는다. queue-svc가 두 키 원본을 Secrets Manager에서 읽는다는 것과는 다르다. 프로세스 메모리를 뚫지 않고 자격만으로 닿는다.
     - (b) 쓰기·지우기: `PutKey`로 서명 키를 바꿔 넣으면 공격자가 아는 키로 엣지가 서명하므로 쿠키를 꾸밀 수 있다. `DeleteKey`로 서명 키를 지우면 엣지 함수의 키 읽기(`kvs.get()`)가 오류를 내 진입 전체가 엣지에서 실패할 수 있다.
     - (c) 꾸민 매진 표시: 아주 큰 판 번호로 `soldOut` 참을 써 두면 queue-svc의 맞추기(저장된 판보다 작은 판은 쓰지 않음)가 바로잡지 못하고, 판매 중인 회차의 새 진입을 엣지가 판매 종료까지 막는다. 결정 2의 '앞선 회차 수' 경보(SEV2)로 드러나고 운영자가 손으로 지운다.
   - 지금 정본은 그대로다: 그 저장소를 읽고 쓰는 IAM 주체는 배포 역할뿐이다(ADR-0053 결정 2, secrets-and-keys.md). queue-svc 역할에는 IAM을 주지 않는다. IAM은 실제 어댑터를 붙이는 HOT-012에서 주므로, 결정이 나기 전에는 HOT-012를 하지 않는다.
   - 고를 수 있는 것은 아래 '다른 선택지' 표의 (가)~(라)와 지금 안(queue-svc 역할에 바로 줌)이다. 추천은 (다) + (라)다.
     - (다)로 queue-svc가 털려도 닿는 것은 `sale:` 키뿐이고, 함수 코드가 접두사·값 꼴·판 번호 증가 폭·만료 시각을 강제한다. 그래서 (a)(b)를 막고 (c)를 좁힌다.
     - (라)로 남은 길(함수 역할이나 배포 역할이 `sale:` 밖 키를 읽거나 씀)을 드러낸다. 쓰기는 회차마다 1분에 한 번쯤이라 데이터 사건 요금은 작다 [추정].
     - (나)는 저장소를 나눠 (a)(b)를 뿌리부터 없애지만 도착 시각 서명을 시청자 응답 함수로 옮겨야 한다. 그러면 '엣지 도착 시각'이 원본 응답 뒤의 시각이 되는데, 진입 Degraded(원본이 느릴 때)일수록 그 차이가 커진다. HOT-020이 요청 때 잡은 시각을 응답 함수에 넘길 길을 찾으면 (나)로 바꾼다(다시 볼 조건).
5. **남은 좌석 수는 판매 상태 사건의 다시 내기로 받는다.**
   - `EventSaleChanged`에 선택 칸 `countedAt`(그 셈을 한 시각)과 `avgTicketsPerOrder`를 더한다(asyncapi·Avro, 선택 칸이라 바뀐 소비자가 없다). `available`(가용 좌석)이 남은 좌석 수다.
   - 내는 쪽(PRF-144)은 판매 중·일시 매진·매진 회차의 같은 판을 5초 [가정]마다 그때의 셈(`available`·`held`·`paying`·`countedAt`·`avgTicketsPerOrder`)으로 다시 낸다. ADR-0214 결정 2의 '주기적으로 다시 낸다'를 이 주기로 정한다. 같은 판이라 `eventKey`는 그 판의 것 그대로다(다른 소비자는 지금처럼 판 번호나 중복 제거 키로 거른다).
   - queue-svc는 판 번호가 `notice`의 지금 판 이상이고 `countedAt`이 둔 셈 시각보다 늦을 때만, 같은 회차 슬롯 Lua에서 `remainingSeats`·`seatsAtMs`·`avgTicketsPerOrder`를 쓴다. 옛 판의 셈은 쓰지 않는다. `countedAt`이 없거나 queue-svc 시계보다 5초 [가정] 넘게 앞서면 셈을 쓰지 않는다(앞선 시각 하나가 뒤의 셈을 모두 막지 않게. 신선도 30초보다 작게 둔다).
   - 셈 칸(`countedAt`·`avgTicketsPerOrder`)의 모양만 틀리면(시각이 아님, 수가 아님) 처리기가 셈 칸을 버리고 판매 상태는 받는다. 선택 칸 하나 때문에 매진 판을 보류하지 않게 하려는 것이다. 그 밖의 칸이 틀리면 지금처럼 사건 전체를 `bad:<회차 ID>` 키로 보류한다(ADR-0214 결정 1).
   - 파일: 셈 시각이 생성 시각에서 30초 [가정] 안이면 `remainingSeats`와 `avgTicketsPerOrder`를 함께 싣고, 아니면 둘 다 뺀다. 셈 시각이 생성 시각보다 5초 [가정] 넘게 앞서도 뺀다. 두 칸이 없으면 화면은 '현재 순번으로는 구매가 어려울 수 있습니다'를 띄우지 않는다(docs/frontend.md §3.4 '구매가 어려울 수 있음'). 내는 쪽이 생기기 전(PRF-144 전)에는 늘 빠진다.
6. **평균 구매 매수는 그 회차의 이번 판매에서 센다.**
   - 내는 쪽은 그 회차에서 결제가 끝난 주문이 100건 [가정] 이상이면 그 주문들의 좌석 수 ÷ 주문 수(소수 둘째 자리)를 싣고, 아니면 싣지 않는다.
   - queue-svc는 값이 없거나 1~10 밖이면 기본값 2 [가정]을 쓴다(한 주문은 1~10석, openapi `HoldRequest.seatIds`).
   - 같은 공연의 지난 회차 평균으로 시작값을 두는 안은 분석 저장소(wbs 4.3)가 생긴 뒤 다시 본다.
7. **좌석맵 경로는 회차 일정 사본에서 만든다.**
   - `q:{event:E}:cfg`에 선택 칸 `layoutVersion`(그 회차의 지금 좌석맵 판 번호, 게시한 판이라 1 ~ 2^32 − 1의 정수 글)을 더한다. openapi `SeatMapLayout.layoutVersion`(1부터, 0은 게시하지 않는 저장 전 초안)과 같다. 쓰는 쪽은 판매 승인·회차 변경(LCH-080)이고, 좌석맵 판이 바뀌면 `rev`를 올려 다시 쓴다.
   - 있으면 파일에 `seatmapLayoutPath` = `/v1/events/{회차 ID}/seatmap-layouts/{layoutVersion}.json`을 싣는다. 없거나 정수 모양이 아니면(0 포함) 그 칸만 뺀다(대기열은 그대로 연다. 화면의 미리 받기만 쉰다, ADR-0216).
   - 대기실의 경로 검사(`apps/web/queue-room` `seatmapPath`)는 지금 1~999,999,999만 받는다. 계약 범위(1 ~ 2^32 − 1)와 같게 넓히는 일은 그 화면을 고치는 HOT-350(갈래 2)에 넘긴다.
8. **실제 어댑터는 나눈다.** 이 단계는 포트(`EdgeSaleFlags`)·시험 대역(`MemoryEdgeSaleFlags`)·맞추기(`EdgeFlagSync`: 차단기, 파드 안 다시 맞추기, 멈춤 스위치)·실패 처리·좌석 수 칸이다. KeyValueStore 어댑터(ETag 조건과 조건 실패의 다시 쓰기, 지난 값 지우기), SDK·서명 모듈 받기, 결정 4의 권한 구성(결정이 (다)면 쓰기 전용 함수), 엣지 함수 코드, 퍼지는 시간 재기, 손으로 끄는 런북과 다시 시작 없는 멈춤 스위치는 HOT-012(wbs 2.2.3 ①-③, 대기: OPEN[24]·OPEN[25])다. 그 전 queue-svc는 엣지 포트 없이 돌고 시작 때 경고 한 줄을 남긴다(엣지 410 없이 원본 410만).
9. **시험**: Q-T63(엣지 매진 표시 켜고 끄기: 매진 판의 엣지 먼저, 판 번호 차례, 앞선 판 세기, 실패해도 `notice`를 씀, 차단기, 파드 안 다시 맞추기, 멈춤 스위치, `sale:` 키만), Q-T64(대기 상태 파일의 좌석 수 칸: 셈 쓰기의 판·시각 차례, 앞선 셈 시각 5초, 셈 칸 모양이 틀린 사건, 30초 신선도, 기본 평균, 좌석맵 경로와 빼기).

## 결과

- 매진 판이 서면 엣지 표시(포트)가 `notice`보다 먼저 켜지고, 매진이 풀리거나 판매가 끝나면 꺼진다. 실제 어댑터가 생기면(HOT-012) 엣지 410이 돈다.
- 엣지 저장소가 안 되어도 판매 안전(원본 410)은 그대로이고, 매진 반영(파일)은 차단기가 열리기 전 몇 번의 마감(최대 2초)만큼만 늦는다.
- 내는 쪽이 셈을 다시 내면 대기 화면의 '구매가 어려울 수 있음' 안내와 좌석 자원 미리 받기가 서버 값으로 돈다.
- 남는 한계
  - 엣지 값이 모든 엣지에 퍼지는 시간을 모른다(확인 필요, open-items 54번). HOT-012가 잰다. 퍼지는 동안의 진입은 원본 410이 막는다.
  - 결정 4가 나기 전에는 queue-svc에 엣지 저장소 권한을 주지 않는다. 그래서 HOT-012도 그때까지 하지 않는다.
  - 내는 쪽(PRF-144)이 생기기 전에는 셈이 없어 좌석 수 칸이 늘 빠진다. 엣지 다시 맞추기는 파드 안 반복이 한다.
  - 파드 메모리의 마지막 값(60초)이라, 다른 파드가 옛 값을 덮은 경우 최대 약 1분 동안 엣지가 틀릴 수 있다. 끔이 틀리면 SEV2로 드러난다.
  - 남은 좌석 수는 최대 약 35초(다시 내기 5초 + 신선도 30초) 늦을 수 있다. 안내는 참고용이다(판단은 서버가 한다).
  - 평균 구매 매수는 판매 초반 100건 전까지 기본값 2다.
  - 멈춤 스위치는 지금 환경 값이라 바꾸면 다시 시작한다.

| 남은 좌석 수를 새 메시지 종류(`EventSeatCount`)로 낸다 | `trade.seats`를 읽는 모든 소비자(queue-svc·core-svc·purchase-svc 원장 적재·분석 적재)가 새 종류를 알아야 하고, 모르면 보류한다(ADR-0214 결정 1의 `bad:` 키). 판매 상태 사건의 다시 내기에 실으면 바뀌는 소비자가 없다 |
