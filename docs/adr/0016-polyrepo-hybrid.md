# ADR-0016: 리포는 프론트엔드 모노레포 + 백엔드 폴리레포 + 계약 리포의 하이브리드

- **상태**: 채택 (2026-10-05 설계서 §15에 기록, 2026-10-08 ADR로 옮김). 교차 PR 수·변경 리드타임을 기록해 사후 평가. 보완: ADR-0054(2026-10-13, 저장소 14개로 `peaket-docs`·`.github` 추가, 공개 저장소 원칙과 봇 시뮬레이터 저장소만 비공개, 공용 재사용 워크플로, GitHub 설정의 코드화). R-56(2026-10-13): 결정 3의 '호환성 파괴를 원천 차단'은 Buf가 잡는 proto 스키마 형식의 호환성 파괴를 CI에서 막는다는 뜻이다. 필드의 의미가 바뀌는 변경은 Buf가 잡지 못한다
- **관련**: 설계서 §15, 28장 Polyrepository, 17장 계약 테스트, docs/architecture.md §10
- **관련 ID**: NFR-023, 01-overview §3.3 조직 설계

## 맥락
- 1인 개발 환경이지만 대규모 엔터프라이즈 환경에서 복수 가상 조직이 독립 배포하는 거버넌스를 재현해야 폴리레포(Polyrepo)의 현실적 장단점을 증명할 수 있다(리드 엔지니어링 역량 산출물).
- 프론트엔드 4대 애플리케이션(소비자 웹, 파트너 콘솔, 관제 콘솔, 모바일 웹)은 공통 디자인 시스템 컴포넌트, OTel 텔레메트리, Zod 폼 검증 스키마를 밀접하게 공유한다.
- 마이크로서비스 간 통신 계약(Protocol Buffers, OpenAPI, AsyncAPI, Avro)은 특정 도메인 서비스에 종속되지 않는 플랫폼 공유 자산이다.

## 결정
1. **프론트엔드 애플리케이션 및 공통 UI 패키지는 Turborepo + pnpm 기반 모노레포(`peaket-frontend`)로 통합 구성한다.**
2. **백엔드 핵심 서비스는 도메인 책임별 6개 폴리레포(`queue`, `purchase`, `ticket`, `trust`, `core`, `platform`)와 인프라 2개 리포(`infra`, `gitops`), 그리고 데이터 및 부하 테스트 전용 리포로 분리한다.**
3. **서비스 간 API 계약은 `peaket-contracts` 전용 리포지토리에서 SemVer 버전 패키지로 빌드 및 배포하며, Buf Breaking Change 감지 CI 파이프라인으로 호환성 파괴를 원천 차단한다.**
4. v0 단계는 초기 단일 리포지토리로 출발하고 서비스 분리 기준(ADR-0007)이 안정화되는 시점에 독립 리포로 추출한다. 단일 서비스 내 복수 팀 모듈은 GitHub CODEOWNERS로 코드 소유권을 명확히 분리하고 배포는 서비스 단위로 통합 수행한다.

## 검토한 대안
| 대안 | 문제 |
| --- | --- |
| 전체 모노레포 | 독립 배포·팀 경계를 증명할 수 없음 |
| 전체 폴리레포 | 프론트 공유 패키지 버전 관리 부담 |

## 결과와 트레이드오프
- 폴리레포 환경의 구조적 비용(다중 리포 교차 변경 오버헤드, 종속성 버전 파편화)은 계약 우선(Contract-first) 개발 파이프라인, Renovate 기반 자동 종속성 갱신, 엄격한 계약 테스트(Pact, Buf Breaking, Schema Registry 호환성 검증)를 통해 최소화한다.
- 트레이드오프: 기능 추가 시 다중 리포 교차 PR 건수 및 변경 리드타임을 정량 계측하여 본 하이브리드 리포 구조의 생산성 트레이드오프를 사후 평가해야 한다.
