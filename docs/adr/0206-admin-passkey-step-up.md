# ADR-0206: 관리 계정 패스키는 콘솔마다 따로 묶고, 재인증 두 단계에서 확인한 요소만 토큰에 싣는다

- **상태**: 채택(2026-11-05, 추천 적용, BUILD_ORDER BOT-122). 확인 라이브러리는 소유자 결정(ADR-0205 결정 2, OPEN[20])을 따른다.
- **관련**: ADR-0050(토큰 서명 키 나누기), ADR-0119(콘솔 로그인 경로), ADR-0130(기술 검토 중간-051 패스키 단계 인증), ADR-0195(TOTP 시드 봉투), ADR-0205 결정 2, [docs/features/identity.md](../features/identity.md) §6 '관리 계정 패스키의 첫 구현', [docs/security/authz-matrix.md](../security/authz-matrix.md) §6, [docs/security/asvs/auth.md](../security/asvs/auth.md) 6.3.3·6.4.4·6.7.2·7.5.1
- **관련 ID**: I-T10, I-T53, POL-020, ASVS v5.0.0-6.3.3, ASVS v5.0.0-6.4.4, ASVS v5.0.0-6.7.2, ASVS v5.0.0-7.5.1

## 맥락

- 패스키는 기기 안의 키로 서명해 인증하는 표준 방식(WebAuthn)이다.
  - 패스키는 인증 정보를 만든 사이트의 RP ID(신뢰 당사자 식별자)에서만 쓰인다.
  - 그래서 가짜 로그인 페이지가 코드를 넘기는 실시간 중계 피싱에 TOTP보다 강하다.
- 정본은 패스키를 TOTP 대신 쓰지 않고, 위험한 작업 직전의 단계 인증에만 쓰기로 정했다(identity §6 'MFA' 행, 기술 검토 중간-051).
- 정본에 빈칸이 있었다.
  - 등록·확인·재인증 토큰 발급의 API 경로가 openapi에 없었다.
  - `admin_passkey` 표의 칸, 챌린지 보관, 서명 횟수가 뒤로 갈 때의 처리, 재인증 토큰 `factors`에 passkey를 싣는 조건이 없었다.
- 확인은 직접 만들지 않고 `@simplewebauthn/server`에 맡긴다(ADR-0205 결정 2).

## 결정

1. **라이브러리**: `@simplewebauthn/server` 14.0.3을 정확히 고정해 identity-svc에만 더한다.
   - 공급망 규칙(게시 뒤 3일, 신뢰 증거가 약해지지 않는 판, 설치 스크립트 허용 목록)을 예외 없이 통과했다. 함께 들어온 전이 의존성은 여섯이다.
   - 증명(attestation)은 받지 않는다(`none`). 동기화 패스키는 증명을 주지 않고, 인증기 모델을 고르는 정책도 없다.
   - 인증기 모델 번호(AAGUID)는 화면 표시와 감사용으로만 적는다.
   - 라이브러리가 보지 않는 셋은 어댑터가 더 본다. 다른 사이트 안(iframe)에서 부른 의식은 거절한다. 등록 때 자격 ID가 1~1023바이트이고 본문 rawId와 같은지 본다(새 맥락 리뷰 2026-11-05).
2. **RP ID와 출처**: 콘솔마다 따로 둔다.
   - 출처는 콘솔 출처 설정 하나다. 파트너는 `PEAKET_PARTNER_CONSOLE_ORIGIN`(기본 `https://partner.peaket.example`), 관제는 `PEAKET_OPS_CONSOLE_ORIGIN`(기본 `https://console.peaket.example`)이다.
   - RP ID는 따로 설정하지 않고 그 출처의 호스트로 정한다. 설정이 서로 어긋날 길을 없애기 위해서다.
   - 그래서 파트너 콘솔에서 만든 패스키는 관제 경로에서 통하지 않는다. 경로의 콘솔(`aud`)이 RP ID와 출처를 정한다.
   - 시작할 때 출처를 검사한다. 경로가 없는 출처여야 하고, local·ci 밖에서는 https만 받는다(local·ci는 `http://localhost`도 받는다).
3. **사용자 확인**: 등록과 확인 모두 `userVerification: "required"`다.
   - 확인할 때도 사용자 확인 표시(UV)가 없으면 거절한다.
   - 받는 서명 방식은 ES256·EdDSA·RS256이다.
4. **챌린지**: 서버가 보낸 문제 값(챌린지)은 32바이트 난수다.
   - 세션·캐시 Redis에 5분 [가정] 둔다. WebAuthn 권고 범위(사용자 확인을 요구하면 5~10분)의 아래 끝이고 로그인 단계 수명과 같다.
   - 확인할 때 꺼내며 지운다(`GETDEL`). 그래서 맞든 틀리든 한 번만 쓴다.
   - 키는 `id:wa:reg:{등록 ID의 SHA-256}`·`id:wa:rea:{재인증 단계의 SHA-256}`이고 유실 등급은 B다(잃으면 처음부터 다시 한다).
5. **재인증 두 단계**: 같은 경로 `POST /v1/partner/auth/reauthentications`·`POST /v1/ops/auth/reauthentications`가 받는다.
   - 1단계는 작업 묶음(`act`)·비밀번호·인증 앱 코드다. 틀리면 로그인과 같이 센다(auth-controls §3.1).
   - 패스키를 요청하지 않으면 바로 토큰을 준다. `factors`는 password·totp다.
   - 패스키를 요청하면 재인증 단계 값과 확인 옵션을 준다. 2단계에서 서명이 맞아야 토큰을 준다. `factors`는 password·totp·passkey다.
   - 패스키가 필요한 작업인지는 받는 서비스가 정한다. identity는 확인한 요소만 싣는다.
6. **factors에 passkey가 실리는 조건**: 다섯이 모두 맞아야 한다.
   - 같은 세션의 1단계를 지난 재인증 단계로, 5분 안에, 한 번만 낸 서명이다.
   - 그 계정의 패스키다(남의 자격 ID면 거절).
   - 출처와 RP ID가 그 콘솔의 값이다(다른 출처·RP ID의 서명은 거절, I-T53 ④).
   - 사용자 확인 표시가 있다.
   - 서명 횟수 규칙(결정 7)을 지났다.
7. **서명 횟수가 뒤로 가면**: 거절한다.
   - 저장한 값과 받은 값이 모두 0이면 받는다. 동기화 패스키는 0만 보내기 때문이다.
   - 받은 값이 저장한 값보다 크면 받고 새 값을 적는다.
   - 그 밖(같거나 작음, 세던 인증기가 0을 보냄)은 복제한 인증기의 신호로 보고 거절한다. SEV3 보안 경보를 내고, 패스키는 지우지 않는다 [가정].
   - 이 판정은 서명이 맞은 뒤에 한다. 위조한 응답으로 경보를 울리지 못하게 하려는 것이다.
8. **내 패스키 등록·지우기**: 새 작업 묶음 `ACCOUNT_SECURITY`(관리 계정 보안 설정)의 재인증 토큰을 받는다.
   - 패스키가 이미 하나라도 있으면 그 토큰에 passkey가 있어야 한다. 비밀번호·TOTP만 가로챈 사람이 자기 패스키를 더하지 못하게 하려는 것이다.
   - 토큰은 identity가 한 번만 받는다(`admin_reauth.used_at`).
   - 한 계정에 10개 [가정]까지 둔다.
   - 등록·지우기는 계정 주인 업무 이메일로 알린다(`PASSKEY_ADDED`·`PASSKEY_REMOVED`).
   - partner_admin·operator·commander는 마지막 하나를 지우지 못한다(409 `last-passkey`).
9. **잃었을 때**: 재초대 `CREDENTIAL_LOST`·`PROTECT_LOCK`과 삭제가 같은 트랜잭션에서 패스키 행을 모두 지운다(ASVS 6.4.4).
   - 하나만 잃었으면 남은 패스키로 재인증한 뒤 잃은 것을 지운다.
   - 재초대 뒤 다시 등록하는 길은 초대 수락 경로(wbs 0.2.3)다.
10. **재인증 기록**: 발급한 토큰마다 `admin_reauth` 행을 적는다.
    - 칸은 jti·계정·세션·콘솔·작업 묶음·factors·쓴 패스키·발급과 만료·쓴 때다.
    - 90일 [가정] 뒤 매일 정비가 지운다. 법정 접속기록(3개월~2년)은 접속기록 저장소 단계(FR-045)가 옮긴다.

## 결과

- 정본: identity §3·§6·§10.1·§11·§13, data.md(`admin_passkey`·`admin_reauth`·알림 종류·Redis 키·§5 경합), openapi(경로 여덟의 작업 열, 오류 이름 아홉), authz-matrix §6(`ACCOUNT_SECURITY`), auth-controls §3.1, guidelines §7·§12, data-classification(패스키 행), asvs/auth.md, verification.md §4.1을 고쳤다.
- 시험: I-T53 ②③④와 사용자 확인 표시·챌린지 재사용과 만료·남의 자격·서명 횟수 퇴행·재초대와 삭제 때 지우기를 메모리 저장소와 PostgreSQL·Valkey에서 본다. 시험용 소프트웨어 인증기는 node:crypto(P-256)와 작은 CBOR 인코더로 만든다.
- 대가:
  - 의존성이 일곱 늘었다(라이브러리 하나와 전이 의존성 여섯).
  - 처음 패스키는 비밀번호·TOTP만으로 등록된다. 패스키가 없는 계정은 실시간 중계 피싱으로 첫 패스키를 빼앗길 수 있다. 알림 메일로 줄이고, 패스키가 필수인 역할은 초대 수락 때 등록하게 해(wbs 0.2.3) 그 틈을 닫는다.
  - 서명 횟수를 세던 인증기가 고장으로 값을 잃으면 그 패스키는 쓰지 못한다. 지우고 다시 등록한다.

## 다른 선택지

| 선택지 | 판단 |
| --- | --- |
| RP ID를 `peaket.example` 하나로 두기 | 버림. 두 콘솔이 같은 패스키를 쓰게 되고, 하위 호스트 어디든 그 패스키를 요청할 수 있다 |
| RP ID 설정을 출처와 따로 두기 | 버림. 둘이 어긋나면 등록은 되고 확인이 늘 실패하는 고장이 생긴다 |
| 챌린지를 PostgreSQL 표에 두기 | 버림. 5분짜리 값이라 정비 작업이 하나 더 들고, Redis의 수명과 `GETDEL`이 한 번 쓰기를 바로 준다 |
| 서명 횟수 퇴행을 경보만 하고 받기 | 버림. 위험한 작업 직전의 확인이라 의심스러우면 막는 쪽이 낫다 |
| 패스키가 필요한 작업이면 identity가 passkey 없는 토큰을 주지 않기 | 버림. cs_lead 승인처럼 같은 작업 묶음에서 역할에 따라 요소가 다르다(authz-matrix §6). 받는 서비스가 정하고 identity는 확인한 요소만 싣는다 |
| 재인증의 2단계에 복구 코드도 받기 | 버림. 복구 코드는 인증 앱을 잃었을 때 계정을 되찾는 값이다. 매일의 재인증에 쓰면 금방 줄어든다 |
