# ADR-0179: 진입 ②(회차 슬롯 번호)를 파드별 2ms 묶음 Lua 한 번으로 한다 — ADR-0176 결정 1을 바꿈(추천 적용, 2026-11-03)

- **상태**: 채택(2026-11-03, 추천 적용. 바꿀 조건은 ADR-0176 '되돌릴 조건'과 Q-T5의 판정 기준에 미리 있던 것이고, 묶음 크기·실패 처리처럼 정본에 숫자가 없던 것만 아래에 '추천 적용'으로 적었다)
- **관련**: NFR-001, Q-T5, ADR-0176 결정 1, ADR-0041, [docs/features/queue-admission.md](../features/queue-admission.md) §3, [docs/architecture.md](../architecture.md) §9.4, BUILD_ORDER PRF-070·PRF-075, wbs 2.2.1, 성능 장부 `docs/perf-ledger/runs/2026-11-03-number-*`

## 맥락

- ADR-0176 결정 1은 한 키 `INCR` 20만/s를 묶음 없이 직접 하기로 했다. 순수 `INCR`이 p99 19.7~50.3ms로 기준(p99 200ms) 안이었기 때문이다. 다만 운영 진입은 진입 Lua 안의 `INCR`이라 'Lua가 생기면 같은 도구로 다시 재고, p99가 200ms를 넘으면 결정 1을 바꿔 파드별 `INCRBY` 묶음을 쓴다'고 적었다. 정본의 Q-T5도 '초과하면 배치 모드를 채택한다'고 적는다.
- 2026-11-03(BUILD_ORDER PRF-070) 실제 진입 ② Lua(queue-svc `NUMBER`: 서버 시각, 세대, 로비·묶음 표시 확인, `INCR`, 키 수명 늘리기)를 같은 도구(`node loadtest/poc/run.mjs number`, 진입 서버 넷, 초당 20만 건)로 쟀다. 샤드 엔진 스레드 CPU가 94~99%까지 차서 초당 약 8만~9만 건만 처리했다. 나머지는 100ms 마감을 넘겨 실패했고, 성공한 요청도 p50이 230ms를 넘었다(TLS 켬 3회 가운데 둘은 유효, 하나는 못 보낸 요청이 있어 무효). 엔진이 잰 스크립트 한 번은 7~8µs이고, 순수 `INCR` 하나는 약 1µs였다.
- 스크립트 한 번의 일을 줄여도 한 샤드 스레드 하나가 초당 20만 번 스크립트를 부르는 한 기준을 넘는다. 부르는 횟수를 줄여야 한다.

## 결정

1. **진입 ②를 파드마다 회차별로 모아 Lua 한 번으로 한다(ADR-0176 결정 1을 바꿈)**: queue-svc 파드는 같은 회차의 진입 ②를 첫 요청부터 2ms [가정] 동안, 또는 500건 [가정]이 찰 때까지 모아 묶음 Lua(`NUMBER_BATCH`) 한 번으로 보낸다. Lua는 서버 시각·세대·로비 표시·묶음 표시를 한 번만 보고, 번호를 받을 요청 수만큼 `INCRBY`해 받은 범위를 묶음 안 순서대로 나눠 준다. PoC에서 같은 2ms 묶음의 `INCRBY`는 p99 4.1ms, 엔진 CPU 12~14%였다(ADR-0176 결정 1의 표).
2. **요청마다 가르는 것은 그대로다**: 서버 시각으로 오픈 전이면 묶음 전체가 '오픈 전'이다. 오픈 직후 묶음 구간 안이면 묶음 대상(사전 검증 토큰의 최초 발급 시각이 오픈 전)은 요청마다 `SADD`하고 202, 그 밖은 503(`Retry-After` 구간 끝까지)이다. 구간이 지났는데 닫힘 표시가 없으면 먼저 닫고 `INCRBY`한다. 그래서 진입 ①·③과 묶음 기록(OPEN[14])은 바뀌지 않는다.
3. **순서**: 묶음 안 번호는 그 파드가 요청을 받은 순서다. 파드 사이 순서는 묶음 창(2ms)만큼 섞인다. 정본 §3이 이미 '파드 사이의 순서 차이는 1~2ms 이내로 줄어들므로 클라이언트 사이의 네트워크 지연 차이보다 작다'고 적은 대가다.
4. **실패와 빈 번호(추천 적용)**: 묶음 Lua가 일시 장애로 실패하면 그 묶음의 모든 요청이 503 `dependency-unavailable`(`Retry-After` 1초)이다. 선점 값(PENDING)이 남아 있어 같은 진입 요청 ID로 다시 오면 이어진다. 응답을 잃어 결과를 모르거나(마감 초과) 묶음을 받은 파드가 ③ 전에 죽으면, 받은 범위는 아무도 갖지 않는 번호가 된다. 지금의 ②와 ③ 사이 틈과 같은 한계이고 크기만 묶음만큼(파드 하나가 초당 5만 건이면 2ms에 약 100개) 커진다. 입장 쪽은 지금처럼 차례가 지나도 오지 않는 번호로 다룬다. 본문에 진입 요청 ID가 없는 요청(브라우저는 늘 싣는다, 정본 §3)은 503 뒤 선점 수명(10초 [가정]) 동안 409를 받는다. 전부터 있던 한계이고, 묶음 하나가 실패하면 함께 겪는 요청이 최대 500건으로 늘어난다.
5. **규칙 모델 명세는 바꾸지 않는다**: 묶음 Lua 한 번은 명세 `specs/queue.qnt`의 `enterNumber`를 다른 동작이 끼어들지 않게 여러 번 한 것과 같다. 끼어들 수 있는 경우가 줄어들 뿐 새 경우가 생기지 않으므로, 지금 검사한 불변식이 그대로 선다.
6. **다시 잰다**: 같은 도구에 파드별 묶음 방식(`--op number-batch`)을 더해 Q-T5의 기준(TLS 켬 3회, p99 200ms 이내)으로 잰다. 루프의 BSL-090 측정과 겹치지 않게 그 뒤에 잰다.

## 검토한 대안

| 대안 | 기각 사유 |
| --- | --- |
| Lua를 줄여 한 번의 일을 줄인다(수명 늘리기를 가끔만, 세대 읽기 빼기) | 한 번 7~8µs를 3µs로 줄여도 초당 20만 번이면 엔진 스레드가 60% 넘게 찬다. 꼬리 지연이 남고 표시 확인(중간-028)은 뺄 수 없다 |
| 회차 키를 여러 샤드로 나눈다(번호 범위를 샤드마다) | 한 회차의 번호가 하나의 순서로 나와야 한다(정본 §3, 1인 1순번과 묶음 표시가 한 슬롯을 전제한다). 바꾸는 범위가 너무 크다 |
| `INCR`만 따로 보내고 표시 확인은 파드 메모리에 둔다 | 표시는 리더와 진입이 함께 쓰므로 같은 Lua에서 봐야 한다(중간-028). 파드 메모리 값은 낡을 수 있다 |

## 결과와 트레이드오프

- 진입 ②의 Redis 호출이 회차 하나에 초당 20만 번에서 파드마다 약 500번(2ms마다 한 번)으로 준다(파드 넷이면 약 2,000번). 파드 하나가 초당 25만 건을 넘으면 500건이 찰 때마다 더 보낸다.
- 진입 응답이 묶음 창만큼(최대 2ms) 늦어진다.
- 파드가 죽거나 응답을 잃으면 빈 번호가 묶음만큼 생긴다(결정 4).

## 되돌릴 조건

- 결정 6의 측정에서 파드별 묶음도 p99 200ms를 넘으면, 회차 키를 나누는 방법을 새 ADR로 다시 본다.
- 운영 측정(K 시나리오)에서 빈 번호 비율이 입장 속도를 눈에 띄게 늦추면 묶음 크기를 줄인다.
