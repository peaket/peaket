# ADR-0153: 설계 문서는 실제 값 없이 공개하고, 클릭 시연은 만들지 않으며, 회차 상세는 저마다 정규 주소를 두고, 둘러보기 페이지는 출시 뒤 정한다(소유자 결정, 2026-10-29)

- **상태**: 채택 (2026-10-29. 소유자가 review/open-items.md의 남은 결정을 하나씩 정하면서, 공개·화면·검색 묶음(1·4·35·37번)의 추천(넷 모두 안 A)을 "추천대로 가겠습니다"라고 정했다. 네 방향은 소유자 결정이다. 점검 도구 `public` 검사의 규칙, 회차 상세의 제목·첫 화면 규칙, 둘러보기 페이지를 만드는 판단 기준의 표현은 추천 적용이다. 결정 2의 `public` 검사 허용 목록에 운영 주소가 될 수 없는 특수 용도 대역(이 망 `0.0.0.0/8`·프로토콜 할당 `192.0.0.0/24`·멀티캐스트 `224.0.0.0/4`·예약 `240.0.0.0/4`)을 더했다. 나가는 연결 제외 목록을 문서에 적기 위해서다(추천 적용 2026-11-09, BUILD_ORDER PRF-192, 코드 리뷰).)
- **관련**: ADR-0057(상시 데모 없음, 녹화와 재현 스크립트), ADR-0084(받는 사람별 문서, 질문 44), ADR-0093 결정 8(카드와 대표 회차), ADR-0094 결정 11(검색 결과 화면은 색인에서 뺌), POL-026(3단계 봇 코드 비공개), [docs/devops.md](../devops.md) §2.1, [docs/infra-handover.md](../infra-handover.md), [design/d5-screen-blueprint.md](../design/d5-screen-blueprint.md) §10, [docs/frontend.md](../frontend.md) §5.15, [docs/features/search.md](../features/search.md) §7.3, [tools/doc-check/README.md](../../tools/doc-check/README.md)

## 맥락

- **1번(문서 공개 범위)**: 문서 저장소 `peaket-docs`는 공개로 계획돼 있다(docs/devops.md §2.1). 인프라 인수 문서는 노드 풀, 권한, 네트워크 배치, 런북을 담는다. '공개 저장소에 넣지 않는 것'(비밀 값, 운영 데이터, 운영 계정의 내부 엔드포인트 목록)은 이미 정해져 있다. 2026-10-29에 문서 전체를 찾아보니 실제 계정 번호·공인 IP·실제 도메인은 없었다. 주소는 모두 자리표시값 `peaket.example`이고, 점 넷 숫자는 ASVS 항목 번호였다. 이를 지키는 기계 검사는 없었다.
- **4번(시연)**: 화면 검토는 새 디자인 도구(디자인 캔버스)로, 시연 영상은 v0·v1 실제 앱의 로컬 녹화와 재현 스크립트로 하는 것이 기본값이었다(design/d5 §10). 캔버스로 클릭 시연까지 만들지는 정하지 않았다.
- **35번(공연 대표 주소)**: 공연 상세는 회차 주소(`/events/[id]`)이고, 카드를 누르면 대표 회차로 간다(ADR-0093 결정 8). 같은 공연의 회차 상세들이 비슷한 페이지로 검색 엔진에 여럿 잡힐 수 있다는 것이 남는 한계였다. 구글 검색 센터 'Event structured data'(2026-10-29 원문 확인)는 이벤트마다 고유한 주소(하나의 이벤트만 다루는 끝 페이지)와 그 주소의 표시를 요구한다. 또 일정이나 여러 이벤트를 나열한 페이지보다 이벤트 페이지에 표시를 두라고 권하고, 여러 날에 따로 표를 파는 공연은 공연마다 Event를 따로 두라고 한다. 정규 주소 안내('How to specify a canonical URL')는 정규 주소를 '중복되거나 매우 비슷한 페이지' 묶음에 쓰라고 적는다.
- **37번(목록 페이지)**: 검색 결과 화면(`/search`)은 색인에서 빼고, 검색 엔진 유입은 공연 상세와 sitemap이 맡는다(ADR-0094 결정 11). 장르·공연장·아티스트 목록 페이지는 정하지 않았다.

## 결정

1. **설계 문서는 공개하고, 실제 값은 쓰지 않는다(소유자 결정, 1번)**: 인수 문서·런북·위협 모델을 포함한 설계 문서 묶음을 공개한다. 설계를 공개해도 안전해야 한다는 원칙(보안은 숨김이 아니라 키·권한·통제에 둔다)을 따르고, 봇 판정 기준값처럼 알려지면 효과가 줄어드는 값만 비공개 설정에 둔다(docs/devops.md §2.1 '비공개 예외'). 문서에는 실제 계정 번호, 공인 IP, 실제 도메인을 쓰지 않고 자리표시값만 쓴다. 운영 계정을 실제로 만들 때(wbs 2.11.2) 실제 값이 들어가는 인수 문서·런북의 부록(계정 번호, 실제 주소, 비상 연락처)은 비공개 운영 저장소에 두고, 공개 문서는 자리표시값 판을 그대로 둔다.
2. **점검 도구에 `public` 검사를 더한다(추천 적용)**: 12자리 계정 번호가 든 ARN, 쉼표 없는 12자리 숫자, `peaket.example`이 아닌 PEAKET 도메인, 사설·공유·링크 로컬·루프백·문서용(RFC 5737) 밖의 IPv4 대역을 오류로 본다. 쿠버네티스 레이블·주석 키 접두사(`peaket.io/pool` 등)는 주소가 아니라 이름이라 뺀다. 대역 표기(`/숫자`)가 없는 점 넷 숫자는 ASVS 항목 번호와 구분되지 않아 보지 않는다. 2026-10-29에 일부러 넣은 일곱 곳(ARN, 12자리 숫자, 하위 도메인이 붙은 주소, 국가 도메인, 공인 대역, 주소로 쓴 레이블 접두사 모양의 도메인, 메일 주소)을 모두 잡았고, 허용할 것(사설 대역, `0.0.0.0/0`, 쉼표 있는 금액, 레이블 접두사)은 통과시켰다. 저장소 문서에서는 0건이다.
3. **클릭 시연은 만들지 않는다(소유자 결정, 4번)**: 화면 검토는 디자인 캔버스로, 시연 영상은 v0·v1 실제 앱의 녹화와 재현 스크립트로 한다(design/d5 §10, docs/verification.md §7). 실제 앱 녹화가 더 강한 증거이고, 캔버스로 만든 클릭 흐름은 실제 앱과 같은 일을 두 번 하며, 캔버스와 정본을 맞추는 짐(planning/01 §5.3 기술 부채)을 늘린다.
4. **회차 상세는 저마다 자기 주소를 정규 주소로 두고, 공연 단위 주소는 두지 않는다(소유자 결정, 35번)**: 회차 상세는 자기 주소를 `<link rel="canonical">`로 두고, 그 회차 하나의 schema.org `Event` JSON-LD를 둔다. 같은 공연의 회차 상세가 비슷한 페이지로 묶이지 않도록, 페이지 제목과 첫 화면 위쪽에 회차마다 다른 정보(공연 일시, 판매 상태, 남은 등급)를 둔다(추천 적용). 카드는 지금처럼 대표 회차로 간다. 정본은 docs/frontend.md §5.15이다.
5. **아티스트·공연장 둘러보기 페이지는 출시 뒤 정한다(소유자 결정, 37번)**: 출시 뒤 Search Console에서 아티스트·공연장 이름만 친 검색어(공연 이름 없이)의 노출·클릭을 공연 상세와 견줘, 그런 검색어가 PEAKET 페이지로 잘 이어지지 않으면 만든다. 만들면 대상마다 둘러보기 페이지 하나(그 대상의 공연 목록과 설명)를 sitemap에 넣고, Event 표시는 회차 상세에만 둔다. 내용이 얇은 목록 페이지를 여럿 만들면 유입용 중간 페이지 남용(도어웨이)으로 보일 수 있어 장르별 목록은 만들지 않는다. 검색 결과 화면은 계속 색인에서 뺀다. 공연 단위 허브는 둘러보기 페이지를 만들 때 함께 다시 본다.

## 검토한 대안

- **1번: 인수 문서·런북·위협 모델을 지금 비공개 저장소로 나누기**: 포트폴리오에서 인프라 인수와 보안 설계를 보여 주기 어렵다. 띄운 시스템이 없어 배치를 공개해도 공격받을 대상이 없다. 기각.
- **1번: 문서 저장소 전체를 비공개로 하고 요약만 공개하기**: 설계의 깊이를 보여 주는 포트폴리오의 목적과 맞지 않는다. 기각.
- **4번: 디자인 캔버스 보드를 이어 클릭 흐름 시연 만들기**: 실제 앱이 생기기 전에 흐름을 보일 수 있다. 하지만 같은 흐름을 두 번 만드는 것이고, 정본이 바뀔 때마다 캔버스 흐름도 고쳐야 한다. 기각.
- **35번: 공연 단위 허브 페이지(`/productions/[id]`)를 지금 두기**: 공연 이름 검색의 입구가 되고 공유 주소가 낡지 않는다. 하지만 구글의 이벤트 표시는 회차 상세가 받고, 허브의 효과는 출시 전이라 알 수 없다. 37번의 둘러보기 페이지와 함께 다시 본다. 지금은 기각.
- **35번: 회차 상세의 정규 주소를 대표 회차로 모으기**: 나머지 회차가 검색에서 빠지고 회차별 이벤트 표시를 잃는다. 회차마다 일시와 표가 달라 '중복 페이지'도 아니다. 기각.
- **37번: 지금 만들기**: 출시 전이라 효과를 알 수 없고, 내용이 얇으면 도어웨이로 보일 위험이 있다. 기각.

## 결과와 트레이드오프

- 문서를 공개한 채로, 실제 값이 섞이면 점검 도구가 CI에서 막는다. 대역 표기 없는 IP 하나는 기계로 잡지 못한다.
- 시연은 실제 앱이 생긴 뒤에야 영상으로 보인다. 그 전의 화면 검토는 캔버스가 맡는다.
- 같은 공연의 회차 상세가 검색 결과에 여럿 나올 수 있다. 회차마다 일시와 판매 상태가 달라 이용자에게는 고를 거리이고, 구글의 이벤트 결과도 회차마다 나뉜다.
- 공연 이름만으로 찾는 사람의 입구는 지금 회차 상세와 홈뿐이다.

## 되돌릴 조건

- 운영 계정을 만들면 결정 1의 부록 나누기를 그때 한다(wbs 2.11.2).
- Search Console이 같은 공연의 회차 상세를 '중복, 구글이 다른 정규 주소를 고름'으로 묶으면, 회차마다 다른 정보를 더 늘리거나 공연 단위 허브를 다시 본다.
- 결정 5의 기준에 닿으면 둘러보기 페이지를 만들고, 그때 공연 단위 허브를 함께 정한다.
