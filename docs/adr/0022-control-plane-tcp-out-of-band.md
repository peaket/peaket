# ADR-0022: 운영 관제 제어 평면을 위한 TCP 대역 외(Out-of-Band) 통신 채널 채택

- **상태**: 채택 (2026-10-05 설계서 §6 및 18장에 최초 수립, 2026-10-08 아키텍처 결정 레코드(ADR)로 공식 이관). ADR-0053(2026-10-13)이 결정 4의 2인 서명을 운영자별 KMS 비대칭 키(ES256)로 정하고, 런북 CLI가 노트북에서 파드에 붙지 않고 클러스터 안 비상 Job에서 메시 신원으로만 제어 포트에 붙게 한다. 2026-10-22(ADR-0082): 메시는 Istio 앰비언트다. 제어 TCP 포트에는 웨이포인트를 두지 않고 노드 프록시의 L4 허용 목록만 둬 제어 명령이 L7 프록시 대기열을 지나지 않는다. '메시 프록시 과부하와 운명을 같이함'(검토한 대안)은 노드 프록시 몫만큼 남는다. 2026-10-26(4차 점검 3부): 결정 2의 'Cloudflare/CloudFront 제공 API'는 CloudFront 설정 API(엣지 함수·S3 사본 고정)와 AWS WAF API(대역 차단)다(docs/features/control-tower.md §5). 결과 첫 줄의 '주 서비스 인프라가 완전히 붕괴되는 극한의 부하 상황에서도'는 '주 데이터 경로(Kafka·gRPC·Redis)가 막혀도'로 읽는다. 같은 EKS 클러스터·리전을 쓰므로 클러스터·리전 전체 장애는 함께 받는다(docs/features/control-tower.md §1).
- **관련 문서**: 설계서 §6(운영 모니터링 및 관제), 18장(TCP 통신 계층), §9(운영 명령 SLO 및 축퇴 모드), ADR-0010, docs/features/control-tower.md
- **관련 ID**: FR-030, FR-032, POL-021, POL-029, NFR-008, SCR-030

## 맥락
- 티켓팅 시스템의 주 데이터 경로(gRPC 내부 통신망, Kafka 이벤트 브로커, Redis 대기열 클러스터)에 심각한 과부하나 메시지 지연, 혹은 인프라 장애가 발생하더라도 긴급 운영 제어 명령은 지연 없이 즉각 수신 및 집행될 수 있어야 한다.
- 시스템 제어 평면(Control Plane)은 데이터 평면(Data Plane)과 물리적·논리적으로 완전히 분리된 대역 외(Out-of-Band) 경로를 유지해야 하며, 제어 명령의 전파 시간은 정상 상태에서 p99 3초 이내, 중앙 관제 서비스(`ops-svc`) 자체가 다운된 재난 상황에서도 비상 런북 CLI를 통해 p99 10초 이내에 완료되어야 한다.

## 결정
1. 데이터 평면 장애 시에도 반드시 격리 작동해야 하는 최상위 비상 제어 명령(예: 동시 입장 목표 수치 변경, 대기열 인입 일시 정지, 예매 결제 일시 중단, 대기실 긴급 공지 송출 등)은 NestJS 내장 TCP 마이크로서비스 트랜스포터를 통해 `ops-svc`에서 대상 서비스(`admission-ctrl` 리더 Pod, `purchase-svc`, `queue-svc`)로 직접 전달한다. 프로토콜 버퍼 컴파일 없이 경량 직렬화로 신속하게 구동된다.
2. 실시간 긴급성이 상대적으로 낮은 일반 운영 명령(예: 봇 판정 강도 임계값 변경, 애플리케이션 로그 레벨 동적 조정, 부가 기능 비활성화, 축퇴 모드 전환 등)은 표준 보안 이벤트 토픽(Kafka) 또는 각 서비스의 전용 관리 REST API를 활용한다. CDN 경로 전환 및 엣지 보안 규칙은 Cloudflare/CloudFront 제공 API를 호출한다.
3. 명령 집행 결과(ACK)는 WebSocket(Socket.IO)을 통해 운영자 관제 콘솔로 실시간 피드백되며, 감사 추적을 위해 이벤트 소싱 불변 로그로 영구 기록된다.
4. 만일 중앙 관제 서버(`ops-svc`)가 완전 불능 상태에 빠진 경우, 사전에 배포된 비상 런북 CLI가 대상 파드의 TCP 포트에 직접 소켓을 연결하여 제어 패킷을 주입하며, 임의 남용을 방지하기 위해 상위 운영자 2인의 M-of-N 디지털 서명을 필수로 요구한다.

## 검토한 대안
| 대안 | 기각 사유 및 한계점 |
| --- | --- |
| 제어 명령을 Kafka 토픽으로 통일 | 티켓팅 폭주 시 Kafka 브로커 랙, 네트워크 포화, 또는 파티션 지연이 발생할 경우 운영자의 긴급 정지 명령이 큐 뒤편에 갇혀 제때 집행되지 못하는 심각한 가용성 결함이 발생한다. |
| gRPC 서비스 메시 경유 | Istio/Envoy 서비스 메시 및 인그레스 데이터 평면의 프록시 과부하 상태와 제어 경로가 운명을 같이하게 되므로 진정한 의미의 대역 외 격리를 달성할 수 없다. |

## 결과와 트레이드오프
- 주 서비스 인프라가 완전히 붕괴되는 극한의 부하 상황에서도 관제 센터가 즉시 밸브를 잠그거나 유량을 차단할 수 있는 강인한 생존성을 확보한다.
- 운영 명령의 성격에 따라 TCP 직접 채널과 비동기 메시지 채널의 두 가지 경로가 공존하므로, 명령별 전달 경로(POL-021 및 docs/features/control-tower.md)를 명확히 문서화하고 테스트 스위트로 지속 검증해야 한다.
