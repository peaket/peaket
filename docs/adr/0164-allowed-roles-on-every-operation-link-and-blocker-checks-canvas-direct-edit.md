# ADR-0164: openapi 작업마다 허용 역할을 적고 점검 도구가 검사하며, 링크·위치 표시와 차단 조건 목록을 검사하고, 캔버스는 아티팩트를 직접 고치며, 소명은 고객 문의와 같은 길로 받는다(소유자 결정, 2026-10-30)

- **상태**: 채택 (2026-10-30. 소유자가 review/open-items.md 71번(허용 역할의 기계 검사), 32·51번(점검 도구), 21번(WBS 근거 열), 6번(법률 검토 시점)을 "A B C 는 추천대로 해주시고요"라고 정했다. 25번은 "아티팩트에 있는걸 그대로 연결해서 사용할수있는거면 그걸로 해주시고요"라고 정했다. 방향은 소유자 결정이다. 역할 값의 표기, 검사 규칙과 예외, 소명 경로, 관리 계정을 지울 수 있는 상태는 추천 적용이다.) 2026-10-30(소유자 결정 "추천대로", open-items 82번): '결과와 트레이드오프'의 권한 표 어긋남 다섯을 정했다. viewer는 CS 처리함을 보지 않고(정산 건은 SCR-049의 건수 요약만), operator·commander는 지급·대사·KYC 정산 건만 처리하며, CS는 아티스트·공연장을 조회하고, 관리 계정은 모두 자기 세션을 다루며, operator의 후기 조치는 법정 통보에 따른 차단·복원뿐이다(planning/03 §3, review R-191).
- **관련**: ADR-0008(게이트웨이가 경로별 역할을 본다), ADR-0066(고객 문의는 support 모듈이 받는다), ADR-0091(콘솔 화면 상태), ADR-0153(설계 문서 공개), ADR-0157 결정 12(허용 역할 기계 검사 제안), ADR-0163(관리 계정 관리 API), [docs/security/authz-matrix.md](../security/authz-matrix.md) §5.5, [tools/doc-check/README.md](../../tools/doc-check/README.md), [docs/api/guidelines.md](../api/guidelines.md) §12

## 맥락

- 권한 표(authz-matrix)는 '허용 역할을 적지 않은 처리기가 있으면 서비스가 시작하지 않는다'는 규칙만 두었다. openapi 경로마다 허용 역할을 적고 검사하는 것은 제안이었다(ADR-0157 결정 12, open-items 71번). openapi 작업 241개 가운데 역할이 적힌 것은 22개였다.
- 점검 도구는 `file:///` 절대 경로 링크와 링크의 위치 표시(#제목)를 보지 않았다(open-items 32번).
- 같은 차단 조건 목록이 정책·상태도·화면 명세·API 네 곳에 흩어져 있었다. 그런데 서로 같은지 대조한 것은 2026-10-19가 마지막이었다(51번).
- 디자인 캔버스는 저장소 밖 아티팩트다. 2026-10-30에 다른 세션이 저장소로 받아 둔 사본은, 소유자 결정에 따라 지웠다(25번).
- 소명(`POST /v1/appeals`)을 받는 서비스가 정본에 없었다. 소명 표는 ops DB에 있는데, ops-svc는 팬 요청을 받지 않는다.

## 결정

1. **openapi의 모든 작업에 `x-peaket-roles`를 단다(소유자 결정, 71번)**
   - 역할 값의 정본은 docs/security/authz-matrix.md §5.5 표 하나다(추천 적용). planning/03 §3은 열 이름이 묶음('파트너', 'CS 담당자')이라 기계로 읽기 어렵다.
   - 값은 `public`, `fan`, `partner_admin`, `partner_member`, `viewer`, `operator`, `commander`, `cs_agent`, `cs_lead`, `scanner_device`, `gate_staff`, `gate_lead`이다.
   - 공개 작업도 `[public]`으로 단다. 칸을 생략하면 빠뜨린 작업과 구분되지 않는다.
   - 팬은 `fan` 하나로 적는다. 구매 권한(`ticket:buy`) 같은 세부는 security와 작업 설명에 둔다.
   - `scanner_device`를 새로 둔다. 기기 자격만으로 부르는 작업 셋(로그인 시작, 승인 확인, 남은 스캔 기록 올리기) 때문이다.
   - 자기 세션 작업(로그아웃, 토큰 갱신, 비밀번호 바꾸기)은 그 게이트웨이의 모든 역할로 둔다.
   - 정본에 주체가 없는 작업 셋(승인 업무 반려, 명령 되돌리기, 회차 취소 판정 전 반려)은 가장 좁은 역할을 [가정]으로 단다.
2. **점검 도구의 `roles` 검사**: 모든 작업에 칸이 있는지, 값이 §5.5 표 안에 있는지, 값이 그 작업의 security와 맞는지(표의 '알아보는 자격'과 '함께 오는 자격')를 본다. 하나라도 어긋나면 오류다. 일부러 틀린 예 열 가지를 넣어 모두 잡히는 것을 확인했다.
3. **링크 검사를 넓힌다(소유자 결정, 32번)**
   - 오류로 보는 것: 절대 경로 링크(`file:`·드라이브 경로), 없는 링크 대상(대소문자까지), 실제 제목과 다른 마크다운 위치 표시다.
   - 위치 표시는 GitHub 방식으로 제목을 바꿔 견준다. 소문자로 하고 문장 부호를 지우며 빈칸은 '-'로 바꾸고, 같은 제목은 -1·-2를 붙인다.
   - 이 변환은 저장소 제목 2,041개를 GitHub Markdown API로 그려 받은 id와 대조해 모두 같았다(2026-10-30). 제목은 공개하기로 한 설계 문서의 것이다(ADR-0153).
4. **차단 조건 목록 대조 `blockers` 검사(소유자 결정, 51번)**
   - openapi의 차단 사유 코드를 기준으로 견준다.
   - 대상 묶음은 둘이다. ① 계정 병합 차단 사유 7개와 그 자리 6곳, ② 입장 중 소유권 동결 `ENTRY_STARTED`와 그 자리 5곳이다.
   - 코드가 빠지거나 남으면 경고, 자리를 찾지 못하면 오류다. 대조하려고 정본의 조건 옆에 코드를 괄호로 적었다.
5. **캔버스는 아티팩트를 직접 읽고 고쳐 다시 게시한다(소유자 결정, 25번)**
   - 저장소에 사본을 두지 않는다. 두 곳에 두면 어긋나는 두 번째 원본이 생긴다.
   - 25번은 v83(1793312167-9744)으로 게시했다. '티켓팅' 표기는 0건이었다. 관제 셸의 '화면을 불러오지 못했습니다' 상태 둘과 SCR-026의 '최근 180분까지'를 더했다.
   - 2026-10-30 정본의 화면 변경은 아직 캔버스에 없다(open-items 81번).
6. **WBS 근거 열과 법률 검토 시점(소유자 결정, 21·6번)**
   - 화면 설계 작업 13개의 관련 ID에 ADR-0059와 ADR-0060을 모두 적는다.
   - 출시 전 법률 검토는 출시를 정하면 wbs 7.4.1 목록으로 한 번 받는다. 범위는 POL-027 확인 필요 27건, 약관, 처리방침, 내부 관리계획 승인이다.
7. **소명은 고객 문의와 같은 길로 받는다(추천 적용)**
   - core-svc support 모듈이 받아 core DB `appeal`에 두고, Outbox로 CS 처리함 `APPEAL` 건을 요청한다.
   - ops-svc는 support 내부 API로 원본을 읽어 확인한다.
   - 기한은 예매 제한 소명이 3영업일 [가정]이고, 양도 회수 소명은 그 승인 업무의 기한이다.
   - CS 처리함 건을 고치는 경로에는 operator·commander도 넣는다. 지급·대사·KYC 건은 CS가 보지 못해서, 빼면 아무도 닫지 못한다.
8. **관리 계정은 지우지 않은 다섯 상태 어디서든 지울 수 있다(추천 적용)**: 퇴직·업무 변경 통보 당일 삭제(내부 관리계획 §2 제5호)와, 업무 이메일이 탈취된 계정은 지운 뒤 새 이메일로 초대한다는 규칙(auth-controls §3.2)을 따른다. planning/03 §2.7에 전이 A13~A16을 더했다.

## 검토한 대안

- **역할 값의 정본을 planning/03 §3에 두기**: 열 이름이 묶음이라 기계로 읽으려면 표를 바꿔야 한다. 기각.
- **공개 작업은 칸을 생략하기**: 빠뜨린 작업과 구분되지 않는다. 기각.
- **위치 표시를 경고로만 보기**: 깨진 위치 표시는 읽는 사람을 엉뚱한 곳으로 보낸다. 고칠 수 있는 수(2곳)였다. 기각.
- **차단 조건을 뜻으로 대조하기**: 아무 문장에서나 맞아 쓸모가 없다. 기각.
- **캔버스를 저장소 사본으로 쓰기**: 어긋나는 두 번째 원본이 생기고, 캔버스는 사본만으로 그려지지 않는다(Design 형식의 실행 코드는 아티팩트에 있다). 기각.
- **소명을 ops-svc가 직접 받기**: 제어 평면을 팬 요청에서 떼어 두는 원칙에 어긋난다. 기각.
- **관리 계정을 활성 상태에서만 지우기**: 초대 중·잠긴 계정을 당일 지울 수 없다. 기각.

## 결과와 트레이드오프

- 권한 빈틈은 문서 단계에서 기계로 잡힌다. 경로를 더할 때마다 역할을 적어야 하고, 역할 표를 바꾸면 검사가 그 표를 따른다.
- 역할 칸이 정본끼리의 어긋남 다섯을 드러냈다. 예를 들어 CS 처리함을 viewer가 보는지가 planning/03 §3과 settlement·d5에서 다르다. 역할 칸은 planning/03 §3을 따랐고, 나머지는 review/open-items.md에 남긴다.
- 검사가 GitHub의 제목 변환 규칙을 흉내 내므로, GitHub가 규칙을 바꾸면 검사를 맞춰야 한다.

## 되돌릴 조건

- 게이트웨이 정책 파일과 서비스 가드 시험을 이 칸에서 만드는 생성기(wbs 3.6.1)가 생기면, 생성기가 이 칸을 읽도록 검사를 옮긴다.
- 차단 조건 묶음이 늘면 `BLOCKER_LISTS`에 자리를 더한다.
