# ADR-0382: SLO 규칙의 원천을 게이트웨이 지표가 생길 때까지 서비스 쪽 지표로 두고, 회차 상태는 진행 중인 회차마다 붙이며, 50% 소진선은 지난 70분으로 잰다(2026-11-23)

- **상태**: 채택(2026-11-23, 감독 결정. F-01-5 계획 '감독에게' 2의 물음). docs/observability.md §4 '측정 기준 지점'(SLI는 따로 적은 것이 없으면 인그레스 게이트웨이의 히스토그램으로 잰다)과 같은 절 NFR 표의 '수집 데이터 소스' 칸을, 아래 결정 4의 되돌릴 조건이 찰 때까지 바꾼다. 목표 기준 지점(게이트웨이·RUM)은 그대로 두고, 그 지표가 생기면 되돌린다. [ADR-0226](0226-aimd-safety-limits-and-control-input-first-implementation.md) 결정 5의 규칙 이름과 '요청이 없으면 0' 규칙, [ADR-0069](0069-ops-control-principles-audit-self-safety-alert-hygiene-wide-events.md) 결정 1의 '빈 값을 0으로 읽지 않는다', [ADR-0126](0126-error-budget-reduction-only-for-admission-bound-journeys.md) 결정 1의 연동 여정 넷은 그대로다.
- **관련**: [docs/observability.md](../observability.md) §4 'SLO 기록 규칙과 원천', 계획 `docs/review/plans/F-01-5.md`, 기능 F-01-5(OPS-090)
- **관련 ID**: V-T51, V-T9, V-T20 ④, NFR-001, NFR-003~NFR-006

## 맥락

- 온세일 번 레이트 경보와 자동 감축(AIMD, 입장 목표를 늘리고 줄이는 자동 조절)의 입력은 여정별 SLI(서비스 품질을 재는 지표: 정상 요청 ÷ 전체 요청)에서 나온다. 정본은 그 원천을 게이트웨이(Envoy) 히스토그램, RUM(실사용자 브라우저가 보내는 측정), CloudFront 지표로 적었다.
- 2026-11-23 F-01-5 계획 때 저장소를 보니 셋 다 없다. 게이트웨이 정의(`deploy/gateways/`)에는 지표 설정이 없고, RUM 수집 경로 `/_t/rum`은 아직 만들지 않았으며(OPS-070), CloudFront 지표 수집기(YACE)는 클라우드 계정이 생긴 뒤의 몫이다(INF-020).
- 정본은 회차마다 온세일 예산을 따로 두지만(§4 '측정 윈도우 체계'), SLI에 회차 라벨(`event_id`)을 붙이는 길을 적지 않았다. Envoy의 경로별 지표는 경로 틀만 갖고 경로 속 회차 ID를 라벨로 남기지 않는다.
- 50% 소진선은 '판매 창(T-10분 ~ T+60분)에서 쓴 예산 몫'인데, 판매 창이 시작한 시각을 내는 지표가 없다(admission-ctrl과 queue-svc 지표에 오픈 시각이 없다).
- admission-ctrl은 연동 여정 넷의 상태 규칙이 하나라도 없으면 '제어 입력 없음'으로 보고 목표를 그대로 둔다(ADR-0226 결정 4). 그래서 원천이 없으면 자동 감축이 판매 내내 돌지 않는다. 기한(2026-12-03, ADR-0373) 안의 측정(F-08-2·F-08-8)에서 자동 감축을 보이려면 지금 있는 지표로 규칙을 세워야 한다.

## 결정

### 1. SLI 원천은 서비스 쪽 지표로 두고 규칙 1층에만 쓴다

- 규칙은 세 층이다(docs/observability.md §4 'SLO 기록 규칙과 원천'). 원천 지표를 읽는 것은 1층(여정별 실패 비율 `peaket:slo_error_ratio:rate<창>{journey}`)과 28일 예산의 5분 증가량(`agg5m:slo_errors:increase5m`·`agg5m:slo_requests:increase5m`)뿐이다. 2층(회차 상태)과 3층(경보)은 1층만 읽는다.
- 원천은 다음과 같다. 여정별 선택자·실패 정의·목표는 정본 §4의 임시 원천 표에 둔다.
  - 좌석 홀드·결제 접수: purchase-svc의 서비스 템플릿 HTTP 히스토그램(그 경로 틀, 5xx가 실패)
  - 대기열 진입: queue-svc의 같은 지표
  - 결제 확정: payment-svc 확정 소요 `payment_confirm_resolution_seconds`(3초 넘김이 실패)
  - 좌석 상태 전파: realtime-gw 묶음 대기 `realtime_gw_batch_wait_ms`(300ms 넘김이 실패, 화면까지 걸린 시간의 하한)
  - 공연 상세·대기 순번 조회: 원천 없음. 규칙을 두지 않는다.
- 원천 서비스가 긁히면(`up{app="<서비스>"}`가 1) 요청이 없을 때 0을 내고, 긁히지 않으면 값을 내지 않는다.

### 2. 회차 상태는 진행 중인 회차마다 같은 값을 붙인다

- 진행 중인 회차는 admission-ctrl이 다루는 회차, 곧 `admission_target{event_id}`가 있는 회차다.
- 1층에 회차 라벨이 없으므로 여정 상태(`peaket:slo:budget_alert10x:state`·`peaket:slo:budget_burn50:state`)를 진행 중인 회차마다 같은 값으로 붙인다. 결제사 원인 상태(`peaket:payment:pg_cause:state`)도 같은 방식이다. 회차의 결제사를 지표로 알 수 없어 결제사 하나라도 원인이면 모든 진행 회차가 1이다.
- 온세일 경보(`slo_onsale_fast_burn`·`slo_onsale_slow_burn`)도 같은 회차 집합에 `event_id`를 달아 낸다.

### 3. 50% 소진선은 지난 70분으로 잰다

- `peaket:slo:budget_burn50:state` = 70분 창의 실패 비율 ÷ (1 − 목표)가 0.5 이상이면 1, 아니면 0이다. 그 창에서 쓴 예산 몫이고, 28일 남은 예산(`slo:error_budget_remaining:ratio28d`)과 같은 비의 정의다.
- admission-ctrl은 50% 소진선을 한 번 보면 기억하므로(ADR-0226 결정 8) 값이 다시 0이 되어도 감축은 한 번이다.

### 4. 되돌릴 조건과 바꿀 곳

| 생기는 것 | 되돌리는 것 | 바꿀 곳 |
| --- | --- | --- |
| 게이트웨이 SLI 히스토그램(gw-queue·gw-fan) | 결정 1의 좌석 홀드·결제 접수·대기열 진입 원천을 게이트웨이 지표로 | `deploy/platform/observability/rules/slo-onsale.yaml`·`slo-28d.yaml`의 1층 규칙, `rules/agg5m.yaml`의 5분 증가량 규칙, 정본 §4 임시 원천 표, 합성 시계열 시험 `deploy/platform/observability/test/*.test.yaml`의 원천 이름 |
| RUM `seat_delta_e2e_ms`·`queue_reflect_seconds`, 결제 확정 종단 지표 | 좌석 상태 전파·결제 확정 원천을 그 지표로 | 같은 곳 |
| CloudFront·CDN 지표(YACE, INF-020) | 공연 상세·대기 순번 조회 규칙을 더한다 | 같은 곳 |
| 회차 라벨이 붙은 원천(게이트웨이나 서비스가 `event_id`를 단 SLI) | 결정 2의 붙이기를 회차별 계산으로 | 2층 상태 규칙과 온세일 경보, 시험의 회차 경우 |
| 판매 창 시작 시각을 내는 지표 | 결정 3을 '판매 창 시작부터'로 | `budget_burn50` 규칙과 V-T51 ⑤ 시험 |

- 1층 이름·라벨과 2층·3층 이름은 되돌릴 때도 바꾸지 않는다. admission-ctrl(`prometheus-control-inputs.ts`)과 경보를 받는 쪽은 고치지 않아도 된다.
- 되돌리는 기능은 그 지표를 만드는 기능(게이트웨이 지표는 INF-020·INF-040, RUM은 OPS-070 행)이 맡고, 이 ADR의 상태 칸에 '일부 되돌림(날짜, 기능)'을 적는다.

## 결과

- 좋아지는 점: 지금 있는 지표로 온세일·28일 번 레이트 경보와 자동 감축 입력이 선다. 로컬 측정에서 자동 감축이 '입력 없음'으로 멈추지 않을 수 있다(다만 `seat_store_unavailable`과 로컬 Prometheus의 규칙 싣기는 따로 필요하다, F-01-5 계획 '감독에게' 3). 원천이 바뀌어도 1층만 고치면 된다.
- 잃는 점:
  - 게이트웨이가 낸 실패(게이트웨이 503·시간 초과, 서비스에 닿지 못한 요청)를 세지 못한다. 서비스가 통째로 죽으면 `up`이 0이 되어 실패 비율 대신 '입력 없음'이 된다(자동 감축은 목표를 지키고, 장애는 다른 경보가 본다).
  - 상태 코드를 `status_class`로만 나눠, 분모에서 빼야 할 423(판매 일시정지)도 센다.
  - 좌석 상태 전파는 서버 쪽 하한만 보므로 실패를 적게 센다.
  - 두 회차가 함께 온세일이면 한 회차의 실패가 다른 회차의 입장 목표도 줄인다. 줄이는 쪽이라 안전하지만 판매 속도를 잃는다.
  - 지난 70분 창은 판매 창 앞의 한산한 시간도 넣어, 판매 시작 직후의 몫을 실제보다 크거나 작게 잴 수 있다.
- 이 한계는 정본 §4에 함께 적고, 측정(F-08-2·F-08-8) 결과를 읽을 때 '임시 원천으로 잼'을 밝힌다.

## 고른 안과 버린 안

- (고름) 서비스 쪽 지표를 1층 임시 원천으로, 진행 회차마다 붙이기, 지난 70분. 기한 안에 지금 있는 지표만으로 돌고, 되돌릴 곳이 1층에 모인다.
- (버림) 게이트웨이 지표 설정을 먼저 만든다: Envoy Gateway의 지표 설정과 kind 검증이 필요한데 그것은 INF-020·INF-040 몫이고, Envoy 경로 지표에는 회차 라벨이 없어 회차 문제는 그대로 남는다.
- (버림) 서비스 HTTP 지표에 `event_id` 라벨을 더한다: 공용 서버 패키지(`packages/platform`)와 핫패스 서비스를 고쳐야 해 이 기능(규칙만 다룸) 밖이고, 게이트웨이 원천으로 되돌릴 때 버려진다.
- (버림) 원천이 없는 여정은 상태를 0으로 채운다: 빈 값을 0(건강함)으로 읽지 않는다는 ADR-0069 결정 1을 어긴다.
- (버림) 50% 소진선을 정본 70분 예산 표의 '허용 실패 건수'(100만 명 기준)로 잰다: 회차 규모가 다르면 기준이 틀리고, 표에 없는 여정(결제 접수·좌석 상태 전파·대기 순번 조회)이 있다.
