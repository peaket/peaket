# ADR-0156: 봇 탐지는 대기열 경로에서 막지 않고 '통과'나 '추가 확인'만 내며, 점수기 여섯을 모두 돌리고, 장애 때는 두 층으로 축소 운영하고, 이의 제기 경로를 정한다(2026-10-30)

- **상태**: 채택 (2026-10-30. 소유자가 ADR-0154 결정 3으로 봇 탐지 상세 설계를 지금 쓰기로 정했다. 이 ADR의 설계 판단은 모두 추천 적용이다. 정본은 docs/features/bot-defense.md다. 판정 기준값·가중치·3단계 봇 코드는 POL-026대로 비공개 설정에 두고 문서에 쓰지 않는다.)
- **관련**: ADR-0039(봇 등급과 그림자 실행), ADR-0071(봇 검증), ADR-0079 결정 5(기기 지문을 쓰지 않음), ADR-0099(스트림 작업자), ADR-0112(사람 오탐의 사람 단위 확인), ADR-0151(봇 방어는 품질 목표 4위), ADR-0154, POL-006(의심 사용자는 추가 검증 큐로), POL-026, FR-020·039·049, NFR-022, [docs/features/bot-defense.md](../features/bot-defense.md), [docs/security/asvs/bot-defense.md](../security/asvs/bot-defense.md), [docs/features/queue-admission.md](../features/queue-admission.md) §7·§9

## 맥락

- 봇 탐지는 '구현 직전 작성 대상'으로 목록만 있었다(점수기 목록, 재평가 작업자, 차단 기기 목록, 축소 운영, 허니팟). 상세 설계를 쓰면서 정본에 없는 계약 여섯을 찾았다.
  - 이의 제기 건을 만드는 길이 없었다. queue-svc에는 DB가 없다.
  - 격리 상한의 분모(대기 인원)를 trust-svc가 얻을 곳이 없었다.
  - 허니팟 적중이 판정으로 이어지는 길이 없었다.
  - 장애 때 축소 운영을 trust.proto 주석과 `degraded` 칸이 다른 층으로 설명했다.
  - 추가 검증 제출을 판정하는 맥락이 없었다.
  - 기기 신뢰 이력을 담을 키가 없었다.
- 정본끼리도 어긋났다. 허니팟을 architecture는 '확정 신호'로, FR-049·ADR-0039·queue-admission은 확정 라벨이 아니라고 적었다. 차단 기기 목록의 확정 출처 '운영 명령'은 운영 명령 12개 어디에도 없었다.
- Cloudflare Turnstile 서버 검증 문서와 CloudFront 헤더 문서를 2026-10-30에 원문으로 확인했다.
  - Turnstile 토큰은 300초 동안 한 번만 검증되고, `idempotency_key`로 안전하게 다시 시도할 수 있다.
  - `CloudFront-Viewer-ASN`은 원본 요청 정책에 넣을 수 있다.

## 결정

1. **대기열 경로의 판정은 `ALLOW`(통과)와 `CHALLENGE`(추가 확인)뿐이다**: `VERDICT_BLOCK`은 쓰지 않는다. 의심 사용자는 막지 않고 추가 검증 큐로 보낸다(POL-006).
2. **확정 신호(허니팟·차단 기기)는 판정을 `CHALLENGE`로 고정하지만 점수기는 모두 돌린다**: 그림자 실행과 기록에 점수가 필요하고, 책임 연쇄가 아니라는 규칙(기술 검토 낮음-063)을 지킨다. 허니팟은 봇 라벨이 아니라 '판정을 일찍 끝내는 신호'다.
3. **점수기 여섯**: `HumanCheck`·`DeviceTrust`·`BehaviorScore`·`NetworkScore`·`AgeScore`·`ConsistencyScore`이고, 모두 순수 함수다. 없는 값은 0으로 보고 가중치를 다시 맞추지 않는다(다시 맞추면 사람 오탐이 는다, NFR-022). `degraded`는 의존성 실패 때만 참이다.
4. **사람 확인 서버 검증은 확정 신호로 일찍 끝나도 매번 한다**: 토큰이 1회용이라 건너뛰면 결과를 영영 잃는다. 기한은 800 ms이고, 검증 호출은 500 ms에서 끊고 `idempotency_key`로 한 번 다시 시도한다. `hostname`·`action`을 확인한다.
5. **판정 프로필 = 강도(운영 명령 5) × 회차 정렬 방식**: 회차의 정렬 설정을 판정 요청에 싣는다. 이용자에게 보이는 사유는 사유 분류 코드 여섯 가운데 가장 큰 하나뿐이다.
6. **ASN(망 운영자 번호)은 `CloudFront-Viewer-ASN` 헤더에서 읽는다**: ASN 분류 파일을 매일 S3에 게시해 trust-svc와 queue-svc가 함께 읽는다. 축소 운영 때 queue-svc도 분류가 필요하기 때문이다.
7. **새 Redis 키 넷**: `tr:devacct`(기기별 계정), `tr:devhist`(기기 신뢰 이력), `tr:hp`(허니팟 적중), `tr:vb`(판정 근거). 로비 입장도 행동 신호를 내고 기기 공유 수(`tr:devshare`)에 센다.
8. **추가 검증 제출은 사람 확인만 보는 `VERIFICATION` 맥락으로 판정한다**: trust-svc가 장애면 통과로 보지 않는다(FR-020). 휴대폰 재인증만으로 통과시키면 빌린 신원으로 도는 봇이 지나간다.
9. **허니팟 링크는 www의 같은 출처 경로 `/_t/` → gw-fan → trust-svc로 받는다**: 적중은 24시간 남고 다음 판정의 확정 신호가 된다.
10. **격리 상한의 분모(대기 인원)는 queue-svc가 격리 Lua 안에서 센다**: 넘으면 '상한 도달'로 답한다.
11. **차단 기기 목록에는 사람이 확정한 것만 넣는다**: 표본 검토와 CS가 확정한 부정 사례다. 추가 검증에 실패했다고 자동으로 넣지 않는다. 자동 오판이 90일 동안 남기 때문이다.
12. **그림자 실행**: 점수만 다시 계산하는 그림자 세트 하나를 둔다. 승격은 온세일 1회 이상과 R2 대조가 필요하고, 온세일 창과 변경 동결 기간에는 바꾸지 않는다.
13. **축소 운영은 두 층이다**: ① trust-svc가 의존성 장애를 `degraded`로 답한다. ② trust-svc 자체가 장애면 queue-svc가 회로 차단기(20회, 50%, 5초)를 열고 캐시 규칙을 쓴다. 캐시 규칙은 기기·참가자당 10초 5회, IP 한도는 호스팅·프록시 대역에만 걸고, '검증 보류' 표시를 단다. 온세일 창에는 SEV2, 그 밖에는 SEV3다.
14. **이의 제기 경로**: queue-svc가 이의 글을 대기열 Redis에 잠시 두고 CS 처리함에 `VERIFICATION_APPEAL` 건을 요청한 뒤 202로 답한다(실패하면 503). 결과는 ops-svc가 queue-svc(인정이면 통과, 기각이면 차단)와 trust-svc(사람 라벨, 차단 키 지움)에 멱등으로 넣는다. 기각은 라벨을 남기지 않는다.
15. **지표·경보와 시험**: 운영 확인 표와 지표(docs/features/bot-defense.md §15·§16), 시험 B-T1~B-T14를 둔다.

16. **관리 로그인의 사람 확인 토큰은 identity-svc가 검증한다(2026-10-30 마지막 정리)**: 판정 맥락마다 허용 호스트를 둔다(팬 맥락은 www, 파트너 로그인은 partner, 운영자·CS 로그인은 console). 관리 로그인은 잠금 규칙의 관문이고, 사람 확인 서비스가 멈추면 받지 않아야 하므로 팬 트래픽을 받는 trust-svc에 기대지 않는다(docs/features/bot-defense.md §6, docs/security/auth-controls.md §2.3, I-T58).
17. **로그인 판정이 `CHALLENGE`여도 로그인은 막지 않고 세션에 남긴다**: 결과는 `session.login_verdict`(판정·사유·시각)다. 양도 요청과 환급·배상 계좌 입력은 판정이 `CHALLENGE`·`UNKNOWN`이고 재인증이 '요청만 함'이면 휴대폰 본인확인 재통과(REVERIFY) 뒤에만 재인증 토큰을 준다(docs/features/identity.md §7·§7.1, I-T55).
18. **새 호출 초안**: 본인확인 재통과는 queue-svc가 identity-svc의 `CheckReverification`으로 확인한다(추가 검증 시작 뒤 같은 사람의 REVERIFY, 답이 없으면 503, I-T56). 이의 심사 화면의 판정 근거는 ops-svc가 trust-svc의 `GetVerdictEvidence`로 읽고, 점수·가중치·기기 가명은 싣지 않는다(B-T15). 라벨 반영은 `ApplyLabel`, 이의 처리는 queue-svc의 `VerificationAppealService`다. 차단 키를 지운 처리자는 trust-svc 보안 로그와 처리함 건에 남기고 판정 기록(`TrustVerdict`)에는 싣지 않는다.
19. **계약 호환을 지킨다**: `VERDICT_BLOCK`과 옛 사유 칸은 지우지 않고 '쓰지 않음'으로 남기며, 사유 범주는 새 칸으로 옮긴다(buf 하위 호환 검사). 회차 정렬 설정은 세 값 열거로 싣는다. 로그인 판정에도 ASN을 쓰도록 공연 페이지 배포의 로그인 경로 원본 요청 정책에 ASN 헤더를 넣는다(docs/infra.md §4.1).
20. **허니팟 경로의 쿠키**: gw-fan이 팬 토큰을 검증해 참가자 ID만 내부 헤더로 넘기고, 쿠키 원문은 trust-svc로 보내지 않는다. 이 경로 하나만 GET을 예외로 받는다(docs/api/guidelines.md §9).

## 검토한 대안

- **확정 신호면 막기**: 의심 사용자를 추가 검증 큐로 보내는 POL-006과 어긋난다. 기각.
- **확정 신호면 바로 돌려주기**: 그림자 실행과 기록에 쓸 점수가 없어지고 책임 연쇄가 된다. 기각.
- **없는 값이 있으면 가중치 다시 맞추기**: 사람 오탐이 는다. 기각.
- **추가 검증에 실패하면 차단 기기 목록에 자동으로 넣기**: 오판이 90일 남는다. 기각.
- **Turnstile 비밀을 queue-svc와 나눠 장애 때 queue-svc가 직접 검증하기**: 비밀이 퍼지는 곳이 는다. 기각.
- **queue-svc → ops-svc 동기 호출로 이의 건 만들기**: 팬 요청을 ops-svc가 직접 받지 않는다는 규칙(ADR-0066)을 깬다. 기각.
- **JA4 TLS 지문 헤더 쓰기**: 기기 지문을 쓰지 않는다는 결정(ADR-0079 결정 5)과 어긋난다. 기각(나중 후보).

## 결과와 트레이드오프

- 봇은 막히지 않고 추가 확인으로 간다. 사람 오탐의 비용은 확인 한 번이지만, 봇이 확인을 통과하면 판정은 대기 중 재평가가 맡는다.
- trust-svc 장애 중에는 캐시 규칙만 남아 걸러지는 봇이 준다. '검증 보류' 표시로 장애 뒤에 다시 판정한다.
- 허니팟 적중을 참가자 ID에 잇는 것이 처리방침에 목적 줄을 따로 둬야 하는지는 [확인 필요]다(wbs 7.4.1).

## 되돌릴 조건

- 하한 집계에서 사람 오탐이 NFR-022 기준을 넘으면 프로필이나 점수기를 다시 본다.
- 축소 운영 중 봇이 통과한 비율이 높으면 캐시 규칙을 강화하거나 검증 비밀 공유를 다시 본다.
