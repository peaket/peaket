# ADR-0348: 감사 공개 앵커를 ADR-0075 꼴로 맞추는 첫 구현 — 머클 잎 바이트, 정규화한 체크포인트, KMS 서명, 공개 타임스탬프 파일, 게시 자리, 검증 도구와 검증 묶음(2026-11-22)

- **상태**: 채택(추천 적용, 2026-11-22, BUILD_ORDER BAT-360 OPS-280 계획). [ADR-0075](0075-public-audit-anchor-signed-merkle-checkpoints.md)의 결정(서명한 머클 체크포인트, OpenTimestamps 고정, 공개 게시, 검증 도구, 검증 묶음)은 그대로 두고, 정본에 없던 바이트 꼴·자리·권한·경보 기준만 정한다. 숫자는 측정 전 가정값이다.
- **관련**: [docs/features/control-tower.md](../features/control-tower.md) §7('공개 앵커의 표준 맞춤' 문단)·§14 C-T38~C-T42, [docs/data.md](../data.md) `audit_checkpoint`·`audit_signing_key`·§5, [docs/security/secrets-and-keys.md](../security/secrets-and-keys.md) '감사 체크포인트 서명 키', [docs/observability.md](../observability.md) '감사 공개 앵커 신호', [docs/api/guidelines.md](../api/guidelines.md) §8·§8.1, [docs/verification.md](../verification.md) §4, [docs/review/plans/BAT-360.md](../review/plans/BAT-360.md)
- **관련 ID**: OPS-280, FR-031, NFR-017, C-T38, C-T39, C-T40, C-T41, C-T42, ASVS v5.0.0-11.2.1·11.2.3·11.4.3·11.6.1

## 맥락

- 첫 구현(2026-11-15 R-584)은 구간 기록의 `seq:해시` 줄을 이어 붙인 SHA-256을 루트로 쓰고, API 프로세스가 환경 값의 Ed25519 키로 서명하며, 앵커는 `local:<id>`다. S3 Object Lock·OpenTimestamps 어댑터는 늘 503을 주는 껍데기다(`services/ops-svc/src/modules/audit/checkpoint.ts`·`anchor.ts`·`immutable-anchor.ts`).
- 정본(ADR-0075 결정 2~9, data.md `audit_checkpoint`, secrets-and-keys)은 잎 솔트를 섞은 RFC 9162 머클 트리, RFC 8785로 정규화한 체크포인트 JSON, KMS ECDSA P-256 서명(`kms:Sign`은 게시 잡만), 공개 타임스탬프 증명, 두 버킷 게시, 누구나 돌리는 검증 도구다. 정본이 이긴다.
- 공식 OpenTimestamps 자바스크립트 클라이언트는 LGPL-3.0이라 의존성 라이선스 검사(`tools/ci/vuln-deadline.mjs`의 허용 목록)를 지나지 못한다. 파이썬 표준 라이브러리에는 ECDSA 검증이 없다.

## 결정

1. **만들기와 서명·게시를 나눈다.** 체크포인트 행은 게시 작업(일·회차 마감)과 commander의 수동 생성(지금의 `POST /v1/ops/audit-checkpoints`)이 만든다. 서명, 공개 타임스탬프, 게시, 증명 갱신은 CronJob `audit-anchor`(ops-svc 이미지의 별도 진입점, 5분 [가정]마다, 겹쳐 돌지 않음)만 한다. API 프로세스는 서명 키를 갖지 않고, 수동 체크포인트는 다음 작업 실행 전까지 서명 칸이 비어 있다.
2. **잎 바이트.** 잎 입력은 ASCII `PEAKET-audit-leaf-v1`(20바이트) ‖ seq(부호 없는 64비트 big-endian) ‖ 기록 해시(`record_sha256` 32바이트) ‖ `leaf_salt`(32바이트)다. 잎 해시는 SHA-256(`0x00` ‖ 잎 입력), 안쪽 노드는 SHA-256(`0x01` ‖ 왼쪽 ‖ 오른쪽)이고, 나누는 자리와 포함 증명은 RFC 9162 §2.1 그대로다.
3. **체크포인트 JSON.** 칸은 ADR-0075 결정 3 그대로다. 해시는 16진 소문자 64자, `createdAt`은 UTC 밀리초 ISO 8601(`Z`)이다. 첫 체크포인트의 `prevCheckpointHash`는 빈 글이고, 해당 없는 칸(`accessLogDayAnchor`·`closedEvents`)은 뺀다. 정규화는 RFC 8785 라이브러리(`canonicalize`, Apache-2.0)로 하고, 만든 바이트를 그대로 저장·게시한다(다시 만들지 않는다). 번호 `no`는 1부터 빈틈 없이 붙고 수동 체크포인트도 같은 사슬에 든다. 번호가 없는 옛 행(0023 이전, local·ci 자료뿐)은 공개 사슬 밖의 옛 내부 체크포인트로 두고 `legacy`로 보인다. 공개 사슬은 seq 1부터 덮는다.
4. **서명.** 체크포인트 JSON 바이트의 SHA-256을 KMS `Sign`(`MessageType` `DIGEST`, `ECDSA_SHA_256`)으로 서명하고 DER을 base64로 둔다. 키 ID는 `PEAKET_AUDIT_CHECKPOINT_KMS_KEY_ID`이고, local·ci는 같은 알고리즘의 PEM 키(`PEAKET_AUDIT_CHECKPOINT_LOCAL_KEY`)나 시작 때 만든 임시 키를 쓴다. local·ci 밖에서 KMS 키 ID가 없으면 작업이 시작하지 않는다. 공개키는 `GetPublicKey`로 받아 표 `audit_signing_key`(키 ID, SPKI)에 두고 게시한다. Ed25519 서명기와 `PEAKET_AUDIT_ANCHOR_PRIVATE_KEY`는 없앤다.
5. **공개 타임스탬프.** 캘린더 목록은 `PEAKET_OTS_CALENDAR_URLS`(local·ci는 시험용 가짜 캘린더)다. 체크포인트 해시에 16바이트 난수를 덧붙여 SHA-256한 값을 보낸다(공식 클라이언트와 같은 꼴, 캘린더는 체크포인트 해시를 모른다). 요청은 캘린더마다 10초 [가정], 응답은 64KiB [가정] 상한이다. 증명 파일은 OpenTimestamps 파일 형식(머리 바이트, 판 1, SHA-256 대상 해시, 연산, 캘린더별 대기 증명 갈래)이고, 직렬화 한 벌을 ops-svc에 둔다. 공식 클라이언트(자바스크립트판)를 쓰지 않는 까닭은 라이선스다. LGPL-3.0은 `tools/ci/vuln-deadline.mjs`의 허용 목록 밖이라 `security-scan.yml`의 라이선스 검사가 그 의존성을 막는다(감독 결정 2026-11-22). 꼴은 공식 형식과 같게 쓰고, 완료 증명은 공식 클라이언트로 한 번 더 확인한다(결정 7). 하나라도 받으면 `PENDING`, 모두 실패하면 행은 그대로 두고 다음 실행에서 다시 보낸다. 1시간 [가정]마다 대기 증명을 캘린더에서 다시 받아 비트코인 증명이 붙으면 `COMPLETE`로 바꾼다.
6. **게시 자리.** 공개 게시 버킷(`PEAKET_AUDIT_PUBLIC_BUCKET`)과 감사 앵커 버킷(BAT-355가 정한 `PEAKET_AUDIT_ANCHOR_BUCKET`)에 같은 파일을 쓴다: `transparency/v1/checkpoints/<번호 10자리>.json`·`.sig`·`.ots`, 완료 증명은 `<번호>.complete.ots`(덮어쓰지 않는다), `transparency/v1/public-keys.json`, 목록 `transparency/v1/index.json`(새 판으로만 고친다). 같은 이름이 이미 있으면 바이트가 같은지만 보고 다르면 SEV2다. local·ci는 moto S3나 폴더(`PEAKET_AUDIT_PUBLIC_DIR`)다. 실제 공개 주소(`/transparency/`)에 거는 일과 공개는 소유자 몫이다.
7. **검증 도구.** ADR-0075 결정 7의 자리(`tools/audit-verify/`)에 둔 파이썬 스크립트 하나(3.11 이상, 표준 라이브러리, 구현 몫)가 내려받은 폴더를 읽어 번호 빈틈, 직전 해시, 같은 번호의 다른 체크포인트(둘 다 보고), 서명, 증명 파일의 대상 해시, 검증 묶음의 기록 → 기록 해시 → 잎 → 포함 증명 → 루트를 본다. 서명은 시스템 `openssl`을 불러 확인한다(곡선 계산을 손으로 만들지 않는다, ASVS 11.2.1). openssl이 없거나 비트코인 단계를 보지 못하면 그 단계는 '확인 못 함'이다. 끝 코드는 0 통과, 1 어긋남, 2 입력 오류, 3 일부 확인 못 함이다. 비트코인 단계는 공식 클라이언트로 하라고 안내한다.
8. **검증 묶음.** `POST /v1/ops/audit-checkpoints/{checkpointId}/verification-bundles`(commander만, 본문 `{seq, reason}`, 사유 1~2,000자)는 그 체크포인트가 덮는 기록 하나의 묶음(정규화 기록, 잎 솔트, 포함 증명, 체크포인트·서명·증명 파일, 키 ID)을 준다. seq가 그 구간 밖이면 422 `seq-not-in-checkpoint`, 체크포인트가 아직 서명되지 않았거나 옛 행이면 409 `checkpoint-not-ready`다. 내보내기는 같은 트랜잭션에서 감사 기록 `AUDIT_BUNDLE_EXPORTED`(seq, 사유)로 남는다. 잎 솔트가 실리는 외부 제공 자료라 viewer·operator는 403이다. 경로를 체크포인트 아래에 두어 게이트웨이 경로(`/v1/ops/audit-checkpoints` 접두사)를 더하지 않는다. 새 Problem type 둘(`checkpoint-not-ready`·`seq-not-in-checkpoint`)은 구현 커밋이 openapi 오류 목록에 더한다.
9. **일 앵커와 회차 마감.** 일 체크포인트는 그날 00:10 KST 뒤 첫 실행에서 만든다. `accessLogDayAnchor`는 접속기록 저장소(OPS-330)의 일 앵커를 포트로 읽고, 그 저장소가 생기기 전에는 칸을 뺀다(검증 도구는 '없음'으로 보고 실패로 세지 않는다). 회차 마감 체크포인트는 온세일 윈도우 끝(T+60분) + 10분 [가정] 안에 만들고, 같은 실행에서 끝난 회차를 한 체크포인트로 묶는다. 끝난 회차 목록은 core-svc 읽기 전용 내부 경로 `GET /internal/v1/events/onsale-closed`(구간 `closedFrom`·`closedTo`, 판매 시작 + 60분이 그 구간에 든 회차의 ID와 마감 시각만, 서비스 사이 토큰, 하루 [가정] 구간·500행 [가정] 상한)로 읽는다(감독 결정 2026-11-22, core-svc 한 곳은 이 묶음이 더한다). 읽지 못하면 그 실행의 회차 마감 체크포인트만 미루고 일 체크포인트는 그대로다.
10. **신호.** ops-svc 프로세스가 1분 [가정]마다 표를 읽어 지표 `audit_checkpoint_last_published_timestamp`·`audit_checkpoint_pending_ots`·`audit_checkpoint_mismatch_total`을 내고, 게시 안 된 가장 오래된 체크포인트가 6시간 [가정](정각 포함)이면 SEV3 `audit-checkpoint-publish-lag`, `PENDING`이 24시간 [가정](정각 포함)이면 SEV3 `audit-ots-incomplete`를 ops 경보로 낸다. 작업이 체인을 다시 모은 루트가 저장된 루트와 다르면 그 체크포인트를 게시하지 않고 SEV2 `audit-checkpoint-mismatch`와 `AUDIT_CHAIN_MISMATCH` 기록을 남긴다.
11. **권한.** 작업의 DB 역할 `ops_audit_anchor`는 `audit_chain`·`audit_chain_head` 읽기와 `audit_checkpoint`·`audit_signing_key` 쓰기만 갖는다. 그래서 작업이 만든 체크포인트는 감사 체인에 기록을 더하지 않는다(체크포인트가 공개 증거다). 수동 생성은 지금처럼 `AUDIT_CHECKPOINT_CREATED`를 남긴다. 작업의 밖 연결은 캘린더 주소, KMS, 두 버킷뿐이다.
12. **계약.** openapi `AuditCheckpoint`·`AuditAnchor`·`AuditCheckpointVerification`에 `no`·`leafCount`·`merkleRoot`·`checkpointHash`·`signatureAlg`(`ECDSA_P256_SHA256`)·`otsState`·`publishedAt`·`legacy`를 더하고 Ed25519 설명을 고친다(구현 커밋이 생성물과 함께).

## 결과

- 밖에서 피켓을 믿지 않고 체크포인트 사슬·서명·포함 증명을 확인할 수 있고, API 프로세스가 뚫려도 서명 키를 쓰지 못한다.
- 남는 한계: 실제 캘린더의 확정과 비트코인 단계, 실제 KMS·Object Lock·공개 주소는 local·ci에서 보지 못한다(C-T38 ②, 장부 미검증). 공개 타임스탬프 직렬화는 공식 클라이언트가 아니라 우리 코드라, 완료 증명은 공식 클라이언트로 한 번 더 확인해야 한다.
- 되돌릴 조건: 공식 클라이언트가 허용 라이선스로 나오거나 소유자가 예외를 주면 직렬화를 그 클라이언트로 바꾼다.
