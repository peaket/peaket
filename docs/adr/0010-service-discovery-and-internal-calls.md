# ADR-0010: 서비스 디스커버리는 쿠버네티스 Service 이름으로, 내부 호출은 메시가 요청 단위로 분산

- **상태**: 채택 (2026-10-08). 메시 제품은 측정 후 이 ADR에 덧붙임. 보완: ADR-0054(2026-10-13, 메시 PoC 비교 항목에 '오픈소스 판 갱신 주기와 고정 방법'을 더함. Linkerd는 2.15부터 오픈소스 안정판 아티팩트를 내지 않고 주간 edge 판만 낸다). ADR-0056(2026-10-13)이 결정 5의 Lease 재확인에 리더 세대 확인(펜싱)을 더한다. 재확인만으로는 확인 뒤 멈춘 옛 리더의 쓰기를 막지 못한다 2026-10-20(ADR-0070): 결정 1의 '엄격한 readiness probe'는 이 파드가 지금 받을 수 있는지만 보는 것으로 읽는다. 준비 상태에 공유 의존성(DB·Redis·Kafka·결제사)과 부하를 넣지 않고, 생존 프로브는 이벤트 루프 응답만 본다(docs/architecture.md §5 '프로브 규칙'). 2026-10-22(ADR-0082): 메시 제품은 Istio이고 기본은 앰비언트 모드다. 노드 프록시(ztunnel)가 L4 mTLS를 맡고, 서비스 사이 gRPC를 받는 서비스만 서비스 단위 웨이포인트가 결정 2의 요청 단위 분산을 맡는다. 본문의 '사이드카'는 '메시 프록시(노드 프록시와 웨이포인트)'로 읽고, 웨이포인트 지연이 기준을 넘는 서비스만 사이드카로 둔다. 결정 2의 벤치마크는 '앰비언트와 웨이포인트 대 사이드카' 비교(선택)로 바뀌고, 하지 않으면 Istio 공식 측정을 인용한다. 결정 3의 '내부 중앙 게이트웨이 없음'은 그대로이고 웨이포인트는 서비스마다 따로 둔다. 포트폴리오 실행(로컬·CI·데모)은 메시 없이 돈다. 2026-10-26(4차 점검 3부): 결정 4의 배포 금지는 POL-028과 docs/devops.md §8.1의 규모별 변경 동결 창으로 읽는다. 대형·중형은 T-90분부터 T+60분까지 모든 운영 변경을, 소형은 T-50분부터 T+60분까지 핫패스 묶음의 배포와 설정을 막는다. 동결 중에도 진행 중인 카나리 중단, 이전 다이제스트로 되돌리기, 릴리스 플래그 끄기 같은 긴급 변경은 RB-23 절차로 한다(devops §8.4, ADR-0054 결정 13). 2026-10-28(ADR-0102, 소유자 승인 '추천안 동의'): 결정 5의 'TCP 대역 외 관제 명령'을 웨이포인트를 붙이지 않은 제어 전용 gRPC(`peaket.control.v1.ControlReceiver/ApplyControl`)로 바꾼다. 리더 전용 Service는 제어 포트의 `admission-ctrl-control`이다. 2026-10-28(기술 검토 낮음-141, 소유자 승인 '추천안 동의'): 결정 6의 'Adaptive Topology Refresh'는 자바 클라이언트(Lettuce)의 옵션 이름이다. 정본 Redis 클라이언트(기본안 node-redis, ioredis·Valkey GLIDE와 비교, 기술 검토 중간-026)의 클러스터 동작으로 읽는다: `MOVED`·`ASK` 응답을 받으면 다시 보내고 슬롯 표를 다시 읽으며, 주기 갱신 같은 슬롯 갱신 설정을 켠다. 설정 이름과 값은 Redis 클라이언트 PoC(V-T33 ②, wbs 0.5.1)에서 정한다(docs/architecture.md §9.4). 2026-10-28(기술 검토 낮음-142, 소유자 승인 '추천안 동의'): 결정 5의 리더 라벨을 달려면 admission-ctrl 계정에 `queue` 네임스페이스 파드의 `patch` 권한이 든다. RBAC으로 '자기 파드만'으로 좁힐 수 없어, Kyverno 정책이 admission-ctrl 파드의 `role` 라벨과 파드 삭제 비용 주석만 바꾸게 막는다. 라벨을 잘못 옮겨도 Lease 재확인과 리더 세대 펜싱(ADR-0056)이 실행을 막는다(docs/infra.md §8).
- **관련**: 설계서 섹션 6 '서비스 디스커버리', 19장, ADR-0007, ADR-0008, ADR-0009
- **관련 ID**: FR-037, NFR-011, NFR-015, POL-028

## 맥락

- **초기 설계에는 서비스 디스커버리 및 내부 로드밸런싱 명세가 부재했다.** EKS 기본 클러스터 DNS에 암묵적으로 의존했으며, 서비스 메시는 'Istio 또는 Linkerd'라는 후보 나열 수준에 머물렀다.
- **MSA 분산 환경에서는 동적 파드 IP가 지속적으로 변동한다.** 수평 오토스케일링, 롤링 업데이트, 노드 장애 복구 시마다 파드가 재생성되며 IP가 변경된다.
- **서비스 간 내부 동기 통신은 고성능 gRPC 프로토콜을 사용한다.** 예: purchase-svc → payment-svc, purchase-svc → ticket-svc
- **admission-ctrl은 분산 락을 획득한 단일 리더 파드만 관제 명령을 수신해야 한다.** 그러나 관제 제어 평면의 명령 패킷이 어떤 경로로 활성 리더 파드에 정확히 라우팅되는지 정의되지 않았다.

공식 아키텍처 레퍼런스 원문 근거는 다음과 같다.

- **[쿠버네티스 DNS](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/)**: Service 리소스는 `서비스명.네임스페이스.svc.cluster.local` 표준 DNS 도메인을 부여받으며, CoreDNS가 고정 가상 IP(ClusterIP)로 해석한다.
- **[쿠버네티스 Service](https://kubernetes.io/docs/concepts/services-networking/service/)**: 셀렉터와 일치하는 활성 파드가 변경될 때마다 쿠버네티스 컨트롤 플레인이 EndpointSlice 목록을 실시간 갱신한다.
- **[쿠버네티스 블로그](https://kubernetes.io/blog/2018/11/07/grpc-load-balancing-on-kubernetes-without-tears/)**
  - gRPC는 단일 장기 지속 HTTP/2 TCP 연결 상에서 복수의 스트림을 다중화(Multiplexing)하므로, L4 연결 단위 부하 분산(kube-proxy iptables) 환경에서는 단일 파드로 트래픽이 집중되는 심각한 불균형이 초래된다.
  - 따라서 HTTP/2 프레임 단위로 스트림을 인터셉트하는 L7 요청 단위 로드밸런싱이 필수적이다.
- **[Linkerd 로드밸런싱](https://linkerd.io/2/features/load-balancing/)**: HTTP, HTTP/2, gRPC 프로토콜을 별도 복잡한 설정 없이 L7 요청 단위로 균등 분산하며, 지연시간이 가장 낮은 엔드포인트를 적응형으로 선택하는 EWMA(지수가중이동평균) 알고리즘을 기본 제공한다.

## 결정

1. **서비스 간 식별 및 호출은 쿠버네티스 표준 Service DNS 이름만 사용한다.** 하드코딩된 IP나 별도의 Eureka, Consul 같은 외부 레지스트리를 일절 배제한다. 트래픽 인입 준비가 검증된 파드만 엔드포인트 풀에 편입되도록 모든 서비스에 엄격한 readiness probe를 구성한다. BFF 계층(Next.js) 역시 클러스터 내부 워크로드이므로 동일 규칙을 따르며, identity 세션 생성 등 서버 간 호출은 서비스 메시 mTLS 신원으로 인가한다(ADR-0011).
2. **내부 gRPC 및 HTTP/2 트래픽은 서비스 메시 프록시가 L7 요청 단위로 분산한다.**
   - 서비스 메시 솔루션은 Linkerd와 Istio를 동일한 부하 시나리오로 벤치마크하여 최종 선정한다.
   - 선정 기준은 p99 지연시간 추가 오버헤드와 사이드카 메모리/CPU 소비량이 가장 경량인 제품이다.
   - 벤치마크 실측 결과는 본 ADR의 부록으로 공식 추적한다.
   - 서비스 메시는 파드 간 자동 mTLS 상호 인증 암호화와 재시도 예산(Retry Budget) 기반의 안전한 전송 재시도를 전담한다(ADR-0009).
3. **내부 통신용 중앙 '내부 API 게이트웨이'는 배치하지 않는다.**
   - 내부 마이크로서비스 간 통신을 중앙 프록시로 집중시킬 경우 단일 병목점(SPOF)이 되고 불필요한 네트워크 홉 지연이 누적된다.
   - 각 파드 사이드카 프록시가 분산 L7 프록시 역할을 자율 분담한다.
   - 외부 인입 트래픽에 한해서만 ADR-0008의 클라이언트 전용 게이트웨이를 경유한다.
4. **롤링 배포 시 트래픽 유실(Zero-downtime)을 보장한다.**
   - 파드 라이프사이클에 graceful shutdown 및 preStop 훅(슬립 대기)을 구성하여, EndpointSlice 제거 전파가 완료된 후 기존 인플라이트(In-flight) 요청을 완결하고 프로세스를 종료한다.
   - 온세일 윈도우(T-10분 ~ T+60분, docs/infra.md §7 배포 동결) 중에는 일체의 서비스 배포를 엄격히 금지한다.
5. **admission-ctrl 단일 활성 리더 전용 라우팅 경로를 수립한다.**
   - Kubernetes Lease 락을 획득한 파드가 본인 파드 메타데이터에 리더 식별 라벨(`role=leader`)을 동적으로 마킹한다.
   - 리더 전용 Service 리소스는 해당 라벨을 보유한 단일 파드만 셀렉터로 가리킨다.
   - TCP 대역 외 관제 명령 및 런북 CLI는 본 리더 Service를 타깃으로 직접 패킷을 전송한다.
   - 명령을 수신한 리더 파드는 비즈니스 실행 직전 Lease 토큰의 유효성을 재확인하여, 리더십 교체 경합 시 구(舊) 리더 파드의 잔류 명령 오실행을 방지한다.
6. **분산 저장소(Redis Cluster, Kafka)는 전용 클라이언트 드라이버가 토폴로지를 자동 갱신한다.** Redis 마스터 장애 조치(failover) 시 클러스터 구성을 즉시 재인식할 수 있도록 토폴로지 자동 갱신(Adaptive Topology Refresh) 옵션을 필수로 활성화한다.
7. **대외 외부 API는 퍼블릭 DNS 도메인으로 호출한다.** PG 결제사, Cloudflare Turnstile, 통신사 본인확인 대행사, 이메일/푸시 발송망, 소셜 로그인 IdP 엔드포인트가 대상이며, 호출부에는 2차 서킷 브레이커(ADR-0009)를 필수로 장착한다.

## Well-Architected 기둥 분석

| 기둥 | 아키텍처 영향 |
| --- | --- |
| 안정성 | 파드 스케일아웃 및 재시작 시에도 내부 서비스 호출이 단절되지 않는다. L7 요청 단위 분산으로 신규 프로비저닝된 파드에 즉각 트래픽이 고르게 유입된다. |
| 성능 효율성 | gRPC HTTP/2 연결 다중화 환경에서도 특정 단일 파드로 부하가 쏠리지 않는다. 사이드카 오버헤드는 벤치마크 실측을 통해 최소화한다. |
| 보안 | 서비스 메시가 클러스터 내부 파드 간 mTLS 상호 인증 및 트래픽 암호화를 투명하게 완결한다. |
| 운영 우수성 | 외부 레지스트리(Consul 등)를 별도 운영하지 않고 Kubernetes 네이티브 Service/DNS 생태계로 운영 단순성을 극대화한다. |

## 결과

- 동적 IP 관리가 Kubernetes 제어 평면으로 완전 위임되며, 서비스 비즈니스 코드는 내부 IP에 대한 결합 없이 논리적 서비스명만으로 통신한다.
- 트레이드오프: 서비스 메시 인프라를 상시 관리해야 하며, 네트워크 패킷이 사이드카 프록시를 홉마다 경유한다. 추가 레이턴시는 설계서 섹션 9의 엔드투엔드 지연 예산 내에서 관리한다.

## 재검토 조건

- 서비스 메시 사이드카의 p99 지연시간 증가폭이 내부 핫패스 통신 SLO(p99 20ms)를 초과할 때: 헤드리스 Service 및 gRPC 클라이언트 사이드 로드밸런싱 도입을 검토한다.
- 리더십 교체 상황에서 관제 명령 패킷의 유실이나 중복 실행 결함이 실측 모의 훈련에서 발견될 때
