# ADR-0144: 엣지·부하 분산의 공유 운명을 줄이고 장애 대응을 정한다 — 관제 원본 NLB 분리, AZ 여유와 영역 빼기, CloudFront 단계 배포, DNS·인증서(2026-10-29)

- **상태**: 채택 (2026-10-29. 소유자가 "로드 밸런서나 카프카는 단일 장애점이 아닌가"를 물었고, 분석을 본 뒤 "추천대로 반영"이라고 정했다(00-summary 질문 64). 방향은 소유자 결정이고, 배율·시간·이름은 추천 적용이다.) 2026-10-29(남은 일 반영): 결과 절의 '규칙 열둘'은 §9 규칙표와 맞지 않아 '규칙 열하나'(대기열 API 3, 화면·파트너·관제용 5, API 3. 관리 규칙 그룹도 하나에 월 1달러, AWS WAF 요금 안내 2026-10-29 확인)로 바로잡았다. 월 고정은 그대로 약 40달러 [추정]이다(docs/infra.md §11). 2026-10-29(원문 확인): 결정 4의 '서울 리전에서 영역 빼기가 되는지'는 된다(ARC 지원 리전 목록에 서울, 교차 영역을 켠 NLB도 지원. 대상 그룹 교차 영역 설정이 켬이나 기본값이어야 하고, 한 번 빼면 최대 72시간). 결정 5의 용량 예약 서울 미지원은 다시 확인했다. 결정 6의 지속적 배포는 원본 그룹·엣지 함수 변경을 지원하고 VPC 원본을 막는 조항은 없다(실제 동작은 PoC). 제약(HTTP/3 배포 불가, 정책이 붙은 동안 웹 ACL 연결 변경 불가, 가중치 15% 상한, 붐비는 시간에는 주 배포로, 함수는 새 이름으로 시험)은 docs/devops.md §6.6에 있다. 결정 7의 추가 지표는 배포마다 지표 8개에 지표당 월 고정 요금(배포 하나 약 2.4달러 [추정])이고, 502·504 비율에는 원본이 돌려준 502·504도 들어 있어 게이트웨이에서 센 몫을 빼고 더한다(review/open-items.md 61·63·64, docs/observability.md §4). 도쿄 VPC 원본은 apne1-az3에서 쓸 수 없어 도쿄 원본 NLB 서브넷을 그 밖에 둔다(docs/infra.md §6). 2026-10-30(open-items 61·64번, 추천 적용): 결정 7의 계산식을 정했다. 5분 [가정]마다 배포별로 `Requests` × (502 + 504 비율) ÷ 100에서 게이트웨이가 그 호스트로 돌려준 502·504를 빼고, 그 몫을 게이트웨이 요청 비율로 여정에 나눠 더한다. 28일·70분 예산과 R0에 넣고, 온세일 빠른 경보와 자동 감축에는 넣지 않는다. 추가 지표는 queue·api 배포만 켜고(월 약 7.4달러 [추정]), YACE는 `delay` 5분 [가정]으로 따로 모은다(docs/observability.md §4). 영역 빼기와 CloudFront VPC 원본의 관계는 AWS 문서에 없어 G-32에서 본다. 서울은 여전히 NLB 용량 예약 지원 리전이 아니다. 2026-11-01(정합 점검, ADR-0177 해설서 검토 네 번째 묶음): 위 2026-10-29(남은 일 반영) 줄의 '결과 절의 규칙 열둘'은 결정 3의 마지막 줄('웹 ACL 셋·규칙 열둘·Bot Control 하나로 약 40달러 [추정]')을 가리킨다. 그 줄의 '규칙 열둘'을 '규칙 열하나'로 읽는다.

## 맥락

- **물리적 단일 장애점은 아니지만 함께 쓰러지는 하나다**: NLB(네트워크 부하 분산기)는 AZ(같은 리전 안의 독립 데이터센터 묶음)마다 노드가 있고, 여러 AZ에 둔 부하 분산기의 SLA는 월 99.99%다(AWS ELB SLA, 2026-10-29 확인). 그러나 원본 NLB 하나가 gw-queue·gw-fan·gw-partner·gw-ops를 모두 받는다(docs/infra.md §1). 리스너·보안 그룹·대상 그룹 설정 실수 하나나 그 NLB의 문제 하나로 팬·파트너·관제 입구가 함께 막힌다. CloudFront도 배포마다 설정이 하나다.
- **문서에 없던 것**: DNS 제공자와 TTL, AZ 하나를 잃은 뒤의 남는 용량과 영역 빼기(zonal shift), CloudFront 설정의 단계 배포, 엣지에서 끝난 실패를 SLI에 세는 규칙, CloudFront 전체 장애·인증서 만료 런북, AZ 전체·엣지 설정 실수 Game Day.
- **문서끼리 어긋난 것**: CloudFront 배포 수(셋과 일곱), WAF 웹 ACL 수와 비용(약 75달러와 약 40달러), 관제 입구 경로(CloudFront 경유, 허용 IP만, 내부 LB의 세 서술), 게이트웨이 인증서 발급처(ACM과 cert-manager).
- **확인한 외부 사실(2026-10-29)**:
  - NLB 영역 빼기는 ARC(Application Recovery Controller) 기능이다. NLB마다 켜야 하고(기본은 꺼짐), 한 번에 AZ 하나만 뺀다. 빼면 그 AZ의 대상 용량도 빠진다. 기존 연결은 끊지 않는다. AWS는 여러 장애가 겹치면 영역 NLB 주소를 DNS에서 먼저 빼기도 한다.
  - NLB 용량 예약(LCU reservation)은 갑작스러운 이벤트 트래픽용이다. 하지만 지원 리전 목록에 서울이 없고, 최소 예약이 AZ마다 2,750 LCU다.
  - CloudFront 원본 장애 조치(원본 그룹)는 GET·HEAD·OPTIONS 요청만 넘기고 POST는 넘기지 않는다.
  - CloudFront 지속적 배포는 스테이징 배포에 헤더 기반(머리 `aws-cf-cd-` 접두사)이나 가중치 기반으로 일부 요청을 보낸 뒤 승격한다. 주 배포와 스테이징 배포는 캐시를 나눠 쓰지 않는다.
  - CloudFront는 원본 인증서도 Mozilla 포함 CA 목록의 CA가 발급한 것이어야 한다. 시청자용 ACM 인증서는 us-east-1에 둔다.
  - AWS WAF 웹 ACL 하나를 CloudFront 배포 여러 개에 연결할 수 있다. CloudFront는 시청자 주소 머리 `CloudFront-Viewer-Address`를 원본에 넘길 수 있다.
  - Route 53 별칭 레코드가 AWS 자원을 가리키면 TTL을 정할 수 없고 그 자원의 기본 TTL을 쓴다.

## 결정

1. **관제 입구용 원본 NLB를 따로 둔다**: NLB는 셋이 된다(추천 적용 2026-10-29).
   - ① 팬·파트너 원본 NLB: 사설, CloudFront VPC 원본, gw-queue·gw-fan·gw-partner.
   - ② 관제 원본 NLB: 사설, CloudFront VPC 원본, gw-ops.
   - ③ 스캐너 NLB: 공개, gw-scanner(지금과 같다).
   - 팬 쪽 NLB의 설정 실수·포화가 관제 입구를 같이 막지 않게 한다. 비용은 NLB 한 대(시간당 0.0225달러, 월 약 16달러)와 사용량이다.
2. **관제 입구 경로의 정본**: 관제 화면·`ops-api` → CloudFront 관제 배포 → 관제 원본 NLB → gw-ops다. 관제 배포에 연결한 웹 ACL의 맨 앞 규칙이 시청자 IP로 허용 목록을 거른다. gw-ops는 원본 확인 머리와 `CloudFront-Viewer-Address`로 허용 IP를 한 번 더 본다. VPN으로만 닿는 내부 로드 밸런서는 관리 도구(Grafana·ArgoCD·Alertmanager)용이다. CloudFront가 멈추면 관제 콘솔에도 닿지 못하므로, 그때 명령은 비상 런북 CLI(RB-08)로 낸다(추천 적용 2026-10-29).
3. **CloudFront 배포와 WAF 웹 ACL의 정본**: 배포는 일곱이다. www, queue, queue-files, api, partner, console, scanner다(추천 적용 2026-10-29).
   - 한도를 따로 올리는 것은 셋이다(www·queue-files·queue, ADR-0058).
   - `partner-api` 호스트는 partner 배포에, `ops-api` 호스트는 console 배포에 대체 도메인으로 둔다. 경로 `/v1/*`가 각 게이트웨이로 간다.
   - 웹 ACL은 셋을 배포끼리 나눠 쓴다. ① 대기열 API(queue) ② 화면·파트너·관제(www·partner·console·scanner) ③ API(api)다. queue-files에는 두지 않는다.
   - 관제 허용 IP 규칙은 ② 안에서 console 호스트로 범위를 좁힌다. Bot Control Common은 ②의 로그인 시작·소셜 콜백 경로에만 하나 둔다.
   - 월 고정 비용은 '웹 ACL 셋·규칙 열둘·Bot Control 하나로 약 40달러 [추정]'을 정본으로 한다.
4. **게이트웨이의 AZ 하나 몫 여유와 영역 빼기**: 대형 온세일 프리워밍 때 gw-queue·gw-fan(공연 당일은 gw-scanner도)의 복제 수를 '필요 복제 × 1.5 [가정]'으로 AZ 셋에 고르게 둔다. AZ 하나를 잃어도 남은 둘이 피크를 받게 하려는 것이다. 서비스(queue-svc 등)는 지금처럼 HPA·Karpenter(긴급 확장 60초 목표)로 회복한다. 게이트웨이 파드 절반을 잃는 경우의 '2배 여유는 두지 않는다'는 그대로다(추천 적용 2026-10-29).
   - NLB 셋 모두 영역 빼기를 켜 둔다. AZ 하나가 망가졌다고 판단하면 RB-13에서 사람이 그 AZ를 뺀다. 자동 영역 빼기(autoshift)는 쓰지 않는다. 온세일 중에 사람이 모르는 전환이 일어나지 않게 하려는 것이다.
   - 서울 리전에서 영역 빼기가 되는지는 운영 계정을 만들 때 확인한다 [확인 필요].
5. **NLB 용량 예약은 지금 쓰지 않는다**: 서울 리전이 지원 목록에 없고, 최소 예약도 크다. 원본 NLB가 T=0 급증을 받는지는 부하 시험 K1에서 NLB 지표(처리 바이트, 새 흐름 수, TCP 리셋)로 확인한다. CloudFront가 원본 연결을 다시 써서 NLB가 받는 새 연결은 엣지 수준으로 준다고 본다 [추정]. 서울이 지원 목록에 들면 대형 회차 T-40분 프리워밍 목록에 넣는다(되돌릴 조건).
6. **CloudFront 설정은 단계 배포한다**: 트래픽이 큰 세 배포(www·queue-files·queue)의 설정 변경은 CloudFront 지속적 배포로 한다. 헤더 기반 내부 시험 → 가중치 기반 일부 요청(5% [가정]) → 승격 순서다. 스테이징 배포는 캐시를 따로 쓰므로 온세일 윈도우와 동결 창에는 쓰지 않는다(지금 동결 규칙과 같다). 나머지 배포는 지금처럼 계획을 검토한 뒤 적용하고, 되돌리기는 되돌리는 커밋이다. 지속적 배포가 VPC 원본·원본 그룹·엣지 함수와 함께 되는지는 PoC(wbs 0.5.3)에서 확인한다 [확인 필요](추천 적용 2026-10-29).
7. **엣지에서 끝난 실패도 SLO 오류로 센다**: 지금 SLI(서비스 수준 지표)는 Envoy 게이트웨이에서 잰다. 그래서 CloudFront가 원본에 닿지 못해 낸 실패는 빠진다. 배포별 CloudFront 502·504 비율(원본 연결 실패·시간 초과)을 그 여정의 SLO 오류에 더한다. 503은 대부분 게이트웨이가 낸 것이라 Envoy 쪽에서 센다. 지표는 CloudFront 상태 코드별 추가 지표를 YACE로 가져오고(추가 지표 비용은 확인 필요), 외부 합성 점검과 RUM으로 맞춘다(추천 적용 2026-10-29).
8. **DNS**: Route 53 공개 호스팅 영역 `peaket.example`에 둔다(추천 적용 2026-10-29).
   - CloudFront와 NLB를 가리키는 레코드는 별칭 레코드라 TTL을 정하지 않는다. 그 밖 레코드의 TTL은 300초 [가정]다.
   - DNSSEC(이름 풀이 응답에 서명하는 것)는 v1에서 쓰지 않는다. 키 서명 키 회전과 잘못된 서명이 이름 풀이를 통째로 막는 위험이, 지금 얻는 이득보다 크다고 본다. 파트너 계약이나 보안 심사가 요구하면 다시 본다.
   - DNS 변경도 IaC 계획을 검토한 뒤 적용한다.
9. **인증서 발급처의 정본**: CloudFront 시청자 인증서는 ACM(us-east-1)이다. NLB 셋은 TCP 통과라 인증서가 없다. 게이트웨이(gw-*)가 TLS를 끝내고 CloudFront는 원본 인증서도 공인 CA 것만 믿으므로, cert-manager가 ACME(DNS-01, Route 53)로 공인 CA 인증서를 받는다. gw-scanner도 같다. 서비스 메시 안의 인증서는 지금처럼 사설 CA다(추천 적용 2026-10-29).
10. **엣지 장애 런북과 Game Day**: 아래를 정한다(추천 적용 2026-10-29).
    - RB-40 'CloudFront·DNS 전체 장애': 외부 합성 점검 3곳 중 2곳 실패로 확인한다. 클러스터 밖 상태 페이지(Upptime)에 공지한다. 판매 경로가 막히면 비상 런북 CLI로 명령 3을 낸다. 회복 뒤 재개를 판단한다. 다른 CDN으로 넘기는 길은 두지 않는다(받아들인 위험: 엣지 설정·보안 규칙을 두 벌 관리하는 부담이 더 크다).
    - RB-41 '인증서 만료': 게이트웨이 인증서를 강제로 갱신하고, CloudFront ACM 인증서 상태를 확인한다. 만료되면 TLS 단계에서 실패해 SCR-059(판매 일시 중단 화면)도 보이지 않으므로 상태 페이지에 공지한다.
    - Game Day G-32 'AZ 하나 전체 정지와 영역 빼기'(모의 진행), G-33 '엣지 설정 실수 되돌리기(스테이징 배포 실패, NLB 대상 그룹 실수)'(모의 진행).

## 검토한 대안

- **NLB 하나 유지**: 비용은 가장 낮지만 관제 입구가 팬 트래픽과 운명을 같이한다. 비상 런북 CLI가 남는 길이지만 콘솔 화면을 잃는다.
- **두 번째 CDN과 DNS 장애 조치**: CloudFront 전체 장애까지 버티지만 엣지 함수·캐시 규칙·WAF·인증서를 두 벌 맞춰야 하고 비용이 커진다. 상태 페이지 공지와 판매 일시정지로 받는다.
- **게이트웨이 2배 여유 상시**: 파드 절반 손실까지 버티지만 비용이 두 배다. AZ 하나(1/3) 몫만 온세일 때 둔다.
- **자동 영역 빼기(autoshift)**: AWS가 판단해 AZ를 빼므로 빠르지만, 온세일 중 사람이 모르는 용량 감소가 생긴다.

## 결과와 트레이드오프

- 팬 경로와 관제 입구가 NLB 단에서 나뉜다. CloudFront·리전·클러스터는 여전히 함께 쓴다.
- 온세일 때 게이트웨이 노드가 약 1.5배로 는다(평소에는 늘지 않는다).
- CloudFront 설정 변경이 단계를 거치므로 반영이 느려진다. 동결 창 밖에서만 하므로 온세일에는 영향이 없다.

## 되돌릴 조건

- 서울 리전이 NLB 용량 예약 지원 목록에 들거나, K1에서 원본 NLB가 T=0 급증을 받지 못하면 용량 예약이나 다른 구성을 다시 본다.
- 부하 시험에서 게이트웨이가 AZ 하나를 잃어도 1.5배 없이 SLO 안이면 배율을 낮춘다.

## 남는 한계

- CloudFront 전체 장애나 DNS 장애 때는 판매를 멈추는 것 말고 대체 경로가 없다.
- 원본 장애 조치는 GET·HEAD·OPTIONS에만 된다. 대기열 진입·결제 접수 같은 POST는 엣지에서 넘어가지 않는다(대기열 진입은 엣지 함수의 도착 시각 쿠키가 대신한다).
- 영역 빼기는 사람의 판단과 실행 시간만큼 늦다.
