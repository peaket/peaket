# ADR-0107: 결제하지 않은 주문을 만료로 끝낸다 — 티켓 주문 EXPIRED와 굿즈 재고 예약 유효 시간(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 높음-17 '결제하지 않고 떠난 주문이 끝나지 않는다(굿즈는 한정 재고까지 묶인다)'에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 방향은 소유자 결정(추천안 승인)이고, 만료 조건·시간·키 이름·시험 같은 세부는 추천 적용이다. 수치는 [가정]이다. ADR-0062 결정 12·31이 정한 상태도(planning/03 §2.4·§2.13)를 보완한다)
- **관련**: FR-011, FR-015, POL-009, POL-012, POL-013, POL-016, NFR-025, ADR-0044, ADR-0062, ADR-0085, ADR-0086, ADR-0106, planning/03 §2.2·§2.4·§2.13, [docs/features/payment.md](../features/payment.md) §3·§4.2·§10·§11, [docs/data.md](../data.md) §2·§3·§4·§5.1, docs/api/asyncapi.yaml·docs/api/avro(`OrderEvent`), docs/api/openapi.yaml(`Order.status`, `/v1/shop/orders`), planning/04 F-03·SCR-015, design/d5 §5.15, [docs/features/README.md](../features/README.md)(shop 행), wbs 2.7.1·7.1.1, [review/tech-review.md](../../review/tech-review.md)(높음-17)

## 맥락

- **티켓 주문**: planning/03 §2.4의 Created·Authenticated에서 끝 상태로 가는 전이가 없고, `purchase_order.status`에도 만료 값이 없다. 주문을 만들고 결제창을 닫은 사람의 주문은 영영 Created로 남는다. 좌석은 홀드 TTL(홀드를 유지하는 시간)로 풀리지만, 주문 원장·퍼널 집계·5년 보존 데이터에는 '진행 중'처럼 쌓인다.
- **구매 세션**: 같은 틈이 있다. §2.2 상태도의 Paying(주문 생성 뒤)에서 나가는 전이는 결제 확정·가상계좌 발급·과금 없는 실패뿐이라, 결제하지 않고 떠난 사람의 세션이 끝나는 길이 그림에 없다. 사건 계약에는 종료 사유 `LEFT`·`MAX_STAY`가 이미 있다(docs/api/asyncapi.yaml `PurchaseSessionEnded`).
- **굿즈 주문**: 주문을 만들 때 한정 재고를 Redis(메모리에 데이터를 두는 빠른 저장소)에서 먼저 깎는다(docs/data.md §4). 그런데 결제를 시작하지 않고 떠난 주문을 끝낼 시간 기준이 없다. '승인 기한 초과'는 결제창 인증 뒤에만 흐른다. 그래서 한정 재고가 남았는데도 매진으로 보이고, 결제하지 않는 주문을 대량으로 만드는 재고 묶기 공격에도 열린다.
- **문서끼리 다르다**: planning/04 F-03은 승인 기한을 넘긴 경우를 '주문 만료 처리'라고 쓰지만 주문 상태도는 그 경우를 Failed로 둔다. 굿즈 상태도에는 입금 기한이 지난 Expired만 있다.

## 결정

1. **티켓 주문에 EXPIRED(과금 없이 끝남)를 더한다(소유자 승인).** CREATED·AUTHENTICATED 주문은 아래 셋이 모두 끝나면 EXPIRED로 끝낸다. 셋 가운데 마지막 것이 오는 때가 만료 시각이다(추천 적용).
   - 구매 세션 종료: 사용자 나가기나 최대 체류(45분 [가정], POL-009). 주문을 만든 뒤에는 무활동으로 끝나지 않는다.
   - 그 주문의 홀드가 모두 풀림: 해제나 만료(홀드 TTL 7분 + 1회 연장 3분, POL-012).
   - 결제 시도 만료: 활성 결제 시도(READY)가 없다. READY는 만든 지 40분 [가정](결제창 인증 유효 시간 30분 + 인증 뒤 승인 기한 10분)이 지나면 EXPIRED가 된다. 토스페이먼츠의 두 시간은 확인됐고(docs/features/payment.md §2.1), 포트원은 같은 값으로 추정한다. 결제 시도를 만들지 않았으면 이 조건은 이미 끝난 것으로 본다.
   - 결제를 접수한 뒤(ACCEPTED부터)는 만료 대상이 아니다. 접수 뒤 승인 기한을 넘긴 주문은 지금처럼 FAILED(실패 범주 `EXPIRED`)다. 주문 상태 EXPIRED는 '접수하지 않고 끝남', FAILED는 '접수 뒤 과금 없이 실패'로 나눠 쓴다. 그래야 결제 실패율과 실패 범주 집계에 이탈한 주문이 섞이지 않는다.

2. **티켓 주문의 만료 처리(추천 적용).**
   - purchase-svc가 세 사건(구매 세션 종료, 홀드 해제·만료, 결제 시도 만료)을 처리할 때마다 그 주문의 조건을 다시 본다. 모두 끝났으면 주문 EXPIRED, 주문 사건 기록, Outbox(보낼 사건을 같은 트랜잭션으로 표에 먼저 적는 방식)를 한 트랜잭션으로 쓴다. 상태가 CREATED·AUTHENTICATED일 때만 바꾸는 조건부 UPDATE라, 같은 때 결제 접수가 먼저 들어오면 만료하지 않는다.
   - 사건이 빠질 때를 대비한 안전망: 10분 [가정]마다 만든 지 90분 [가정](최대 체류 45분 + 결제 시도 40분 + 여유 5분)이 지난 CREATED·AUTHENTICATED 주문을 찾아 끝낸다. 새 인덱스를 두지 않고 기본 키(UUIDv7, 앞부분이 만든 시각이다) 범위로 만든 지 하루 안의 주문만 읽는다(docs/data.md §5.1).
   - 만료된 주문의 결제 시도 시작과 결제 접수는 409(Problem type `order-expired`)로 거절하고 결제사 승인을 부르지 않는다. 과금은 없다.
   - `trade.orders`에 EXPIRED를 더한다. 계약은 BACKWARD_TRANSITIVE라 소비자를 먼저 배포한다(docs/api/avro/README.md §3).

3. **구매 세션 상태도에 Paying → Released(사용자 나가기·최대 체류 시각 경과)를 더한다(추천 적용).** 사건 계약에 이미 있는 종료 사유를 그림에 맞춘다. 결제하지 않은 주문은 결정 1대로 EXPIRED로 끝난다.

4. **굿즈 주문은 재고 예약 유효 시간을 둔다(소유자 승인, 값과 방법은 추천 적용).**
   - 예약 유효 시간은 주문 뒤 15분 [가정]이다. 결제 접수(결제창 인증이 끝난 뒤)에는 그 결제의 승인 기한(인증 뒤 10분)까지 늘린다.
   - 그 안에 결제가 끝나지 않으면 주문을 Expired로 바꾸고 Redis 재고를 돌린다. PostgreSQL `product_stock`은 결제 승인 직전에만 깎으므로, 접수 전에 끝난 만료에서는 돌릴 것이 없다. 접수 뒤의 실패는 지금처럼 Failed로 끝나고 두 곳의 재고를 돌린다.
   - 만료 회수는 홀드와 같은 정렬 집합(점수로 정렬되는 집합) 쓸기다. 주문 생성 Lua가 재고를 깎으면서 같은 해시 슬롯의 `shop:{product:P}:resv`(주문 ID, 점수 = 예약 만료 시각)와 `shop:{product:P}:resv_qty`(주문 ID → 수량)에 예약을 넣는다. core-svc shop 모듈의 만료 작업이 1초 [가정]마다 지난 예약을 찾는다. 먼저 PostgreSQL에서 주문을 조건부로 EXPIRED로 바꾸고(상태 CREATED이고 예약 만료 시각이 지났을 때만), 바뀐 주문만 Lua 하나로 예약을 지우며 재고를 돌린다. 예약이 이미 없으면 재고를 돌리지 않으므로 두 번 돌리지 않는다. 결제가 승인되면 예약만 지운다.
   - 같은 계정이 같은 상품에 결제하지 않은 주문을 동시에 하나만 둔다 [가정]. 새 주문을 만들면 이전 CREATED 주문을 먼저 만료로 끝내고 재고를 돌린다. 계정당 수량 제한(SCR-015 ⑦)과 함께 한 계정이 재고를 묶는 양을 줄인다.
   - 주문서 화면(SCR-015)은 예약이 끝나는 시각을 보이고, 끝나면 '결제 시간이 지나 주문이 끝났습니다. 재고가 남아 있으면 다시 주문할 수 있습니다'를 보인다.

5. **상태도·저장 값·계약(추천 적용).** planning/03 §2.2(Paying → Released), §2.4(Created·Authenticated → Expired), §2.13(Created → Expired), docs/data.md(`purchase_order.status`에 EXPIRED, `payment_attempt` EXPIRED 시각, `merch_order.stock_reserved_until`, Redis 키 두 줄, §4 경계 5, §5.1 쓸기 줄), openapi(`Order.status`에 EXPIRED, `/v1/shop/orders` 응답의 `stockReservedUntil`), asyncapi·Avro `OrderEventType`에 EXPIRED, planning/04 F-03, design/d5 §5.15, docs/features/README.md shop 행.

6. **시험(추천 적용).** P-T41(티켓 주문 만료: 결제창을 닫고 떠남, 결제 시도를 만들지 않고 떠남, 만료 직전 접수, 사건 유실 뒤 안전망)과 P-T42(굿즈 재고 예약 만료: 15분 경과, 접수 뒤 연장, 동시 승인과 만료, 같은 계정의 두 번째 주문, 재고 두 번 돌리기 0건)를 둔다.

7. **일정(WBS, 추천 적용).** 2.7.1에 티켓 주문 만료와 안전망 쓸기를 넣어 0.25일, 7.1.1에 굿즈 재고 예약 만료를 넣어 0.5일 늘린다.

## 검토한 대안

| 대안 | 기각 이유 |
| --- | --- |
| 주문을 끝내지 않고 둔다(좌석은 홀드 TTL로 풀린다, 지금) | 굿즈는 재고가 묶인다. 원장·집계에 끝나지 않은 주문이 쌓인다 |
| 주문 생성 뒤 고정 시간(예: 30분)에 한꺼번에 만료 | 결제창이 아직 열려 있거나 접수 직전인 주문을 끊을 수 있다. 결제가 실제로 불가능해진 때(세 조건)를 보는 편이 맞다 |
| 만료를 FAILED로 표시 | FAILED는 결제 접수 뒤의 실패라 결제 실패율·실패 범주 집계에 이탈한 주문이 섞인다 |
| 굿즈 재고를 결제 승인 때 깎는다(먼저 깎지 않음) | 승인 뒤 재고가 없으면 결제를 취소해야 한다(초과 판매 뒤 환불). 한정 재고는 먼저 깎고 만료로 돌려주는 편이 맞다 |
| 굿즈 예약을 Redis 키 수명(TTL)으로만 둔다 | 키가 사라져도 재고 카운터가 돌아오지 않고, 돌려놓을 수량도 알 수 없다 |

## 결과와 트레이드오프

- 결제하지 않은 주문이 끝 상태로 정리되어 원장·퍼널·보존 데이터에 진행 중 주문이 쌓이지 않는다. 한정 굿즈 재고는 15분 [가정] 안에 돌아온다.
- 대가:
  - 굿즈 결제창에서 15분 넘게 머문 사람은 인증을 마쳐도 주문이 끝나 있을 수 있다(과금 없음, 다시 주문해야 한다).
  - 상태 하나, 사건 종류 하나, Redis 키 둘, 쓸기 작업 둘이 늘어난다. WBS는 0.75일 늘어난다.

## 되돌릴 조건

- 굿즈 결제창에서 예약 유효 시간을 넘기는 주문이 접수 전 이탈의 2% [가정]를 넘으면 예약 유효 시간을 늘린다.
- 재고 묶기 시도가 보이면(같은 기기·결제하지 않은 주문이 몰림) 계정당 결제 전 주문 수를 더 줄이거나, 그 상품에 인기 MD 대기열 입장 토큰을 건다.

## 남는 한계

- 예약 유효 시간 동안은 결제하지 않는 주문이 재고를 묶는다. 계정당 한도와 '결제 전 주문 하나' 규칙은 한 계정의 몫만 줄일 뿐, 계정을 많이 만든 공격은 막지 못한다. 인기 MD 대기열과 봇 방어에 기댄다.
- 포트원의 결제창 인증 유효 시간은 확인하지 못했다 [가정]. 실제로 더 길면 READY 만료(40분)를 늘린다.
- 티켓 주문의 만료 시각은 사건이 빠지면 최대 90분 + 쓸기 주기 10분 [가정]까지 늦을 수 있다.
