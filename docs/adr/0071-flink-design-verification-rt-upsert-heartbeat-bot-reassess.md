# ADR-0071: Flink 설계 검증과 구체화 — 실시간 표 덮어쓰기, 빈 파티션과 심장 박동, 봇 대기 중 재평가, 지표 출처 표, 실행 기반(2026-10-20)

- **상태**: 채택 (2026-10-20. 소유자가 "flink 기술쪽 설계가 구체화 되었고 이게 타당한지 검증해주세요"라고 요청했다. 검증 보고(높음 4건·중간 5건·낮음 2건)의 판정은 '방향은 맞지만 잡 단위로 구체화된 것은 원본 적재 잡 하나이고, 나머지는 서술대로 만들면 문서 자신의 기준을 못 지킨다'였다. 봇 탐지(높음 3)는 A안(판정 피처는 trust-svc가 Redis에서 바로 계산하고 Flink는 대기 중 재평가)과 B안(Flink를 봇 탐지에서 뺌) 가운데 A안을 추천했다. 소유자는 "네 반영, 승인"이라고 했고, 이를 추천안 전체(높음 3은 A안) 승인으로 읽었다. 잡 이름, 표 모양, 패턴과 수치는 추천 적용 2026-10-20이고 수치는 [가정]이다.) 2026-10-20(ADR-0072): 상세 설계로 구체화하며 세부를 고쳤다. 누적의 버전은 처리 건수가 아니라 내보낸 처리 시각이고, 심장 박동은 별도 표(`rt.pulse`) 대신 같은 연산자를 지나 `_pulse` 행으로 남는다. 중복 제거는 판매류 사건과 대기열 집계만이고, 판매 좌석은 좌석 판매 상태 기계로 세며(입금 되돌림 포함), 잔여석은 판매 대상 − 판매 좌석이다. `SeatEvent`에 등급·구역을 더했다. 같은 날 검토 목록(재평가 기본 그림자와 적용 전환은 commander가 명령 5로, 재평가 격리 상한 대기 인원의 0.5%/10분, 패턴 기준(10분 안 기기 공유 5명·같은 요약값 20명), 관제 실시간 표 신선도 경보 SEV3, Flink 2.2.x 고정, 관제 실시간·재평가 잡은 온디맨드이고 원본 적재만 Spot)에 소유자가 "네"(추천대로)라고 해 승인으로 확정했다. 숫자는 측정 전 가정값으로 남는다. 2026-10-20(ADR-0072)에서 바뀐 값: `QueueAggregate` 중복 제거 수명은 1시간이 아니라 10분, 지연 예산의 최악 합은 약 3.9초(추정값)다. 2026-10-20(ADR-0073, 3차 전수 점검): 누락률에 읽지 못해 거절한 수를 더하고 판정은 '1분 p95 5초 미만'으로 맞췄다. 관제 판매 중 탭의 퍼널 다섯 단계는 결정 4대로 Prometheus 값이다. 결과 절에서 그리지 않았다고 한 디자인 캔버스의 SCR-029 신선도 표시는 같은 날 그렸다(캔버스 v43). 2026-10-26(4차 점검 3부): 결정 5의 신선도는 심장 박동 발행부터 ops-svc가 읽을 때까지로 재고, 화면 푸시·그리기 약 0.3초는 지연 예산에만 넣는다(ADR-0087 결정 36). 결정 5의 Prometheus 대체 표시는 신선도 p95 5초 미만이 5분 [가정] 이어지면 자동으로 실시간 표로 돌아간다(ADR-0078 결정 2, docs/streaming.md §4.5).

## 맥락

- Flink 설계는 21개 문서에 흩어져 있었고 가장 많은 문서(observability)도 10줄이었다. Flink만 다루는 절이 없었고, 잡 단위 명세는 원본 적재 잡(`analytics-ingest`, analytics §3·§5.5)뿐이었다. 관제 실시간 집계는 "1초 슬라이딩 윈도우 + 워터마크 허용 지연 2초 + ClickHouse 1초 비동기 삽입, 그 밖은 10초 텀블링"이라는 한 줄이었고, 봇 탐지는 "Flink 세션 윈도우·CEP"라는 이름뿐이었다.
- 잘 맞는 것: 잠정(`rt`)과 확정(골드)을 다른 표에 두는 원칙(ADR-0052), 원본 적재의 중복 허용과 실버의 `eventKey` 중복 제거, 확정 숫자의 중복 제거에 ReplacingMergeTree를 쓰지 않는 판단, 머티리얼라이즈드 뷰가 중복 전달분을 더한다는 인식(analytics §5.5), Degraded 모드의 Prometheus 대체 경로, 세이브포인트 업그레이드·연산자 UID 고정·동결 창 금지(ADR-0054), queue-svc의 1초 사전 집계(ADR-0026).
- 빈 곳:
  1. 판매 좌석·금액의 '실시간 대비 차이 0'(analytics §4.4)을 지킬 수 없다. 창의 허용 지연 기본값이 0이라 워터마크 뒤에 온 사건은 버려지고, ClickHouse 공식 Flink 싱크는 적어도 한 번 전달이라 재시작 뒤 다시 보낸 값을 뷰가 더한다. 가장 중요한 두 숫자의 결정 규칙이 자주 '판정 보류'가 된다.
  2. 거래 토픽은 키가 회차라 온세일 중 대부분 파티션이 비고, 워터마크는 모든 입력의 최솟값이라 빈 파티션 하나가 창을 멈춘다. 빈 입력 처리를 짧게 켜면 쉬다 돌아온 파티션(Outbox 중계가 잠깐 멈춘 경우 등)의 사건이 늦은 사건으로 버려진다. 문서에는 둘 다 없었다.
  3. 봇 탐지의 '세션 윈도우·CEP'는 판정 방식과 맞지 않는다. 판정은 사전 검증 요청 때 그 자리에서 하는데(queue-admission §7), 세션 창은 활동이 멈춘 뒤에야 결과를 내고 쉬지 않는 봇이면 닫히지도 않는다. CEP를 걸 순서 있는 클릭 기록은 개인정보 판단으로 보내지 않기로 했다(ADR-0065 결정 9, `BehaviorSignal`은 요약값). 기능 정본에는 Flink가 없었고 입력·출력·신선도 계약도 없었다. wbs 3.2.2(Phase 3)는 Flink 실행 기반이 생기는 4.3.1(Phase 4)보다 먼저였다.
  4. 같은 핵심 지표의 출처가 둘로 적혀 있었다. NFR-009는 입장 속도·입장 전환율·오류율·결제 성공률을 Flink로 만든다고 하고, ADR-0068 결정 2는 콘솔의 실시간 판단 위젯을 클러스터 안 Prometheus에서 읽는다고 했다.
  5. NFR-009를 워터마크로 재서 ClickHouse 반영·조회·푸시가 빠졌고, docs/verification.md에 시험이 없었다(G-07 로컬 역압 주입뿐). 지금 숫자(1초 칸 + 워터마크 2초 + 싱크 버퍼 1초 + 비동기 삽입 + 조회 주기 + 그리기)를 더하면 최악이 5초를 넘을 수 있었다[추정].
  6. 공식 싱크는 재시도해도 안 되면 묶음을 버리는데, 마감 커버리지 검사('적재 오프셋 = Kafka 끝 오프셋', analytics §7)는 중간에 버려진 묶음을 못 잡는다.
  7. 업그레이드 때 세이브포인트가 맞지 않으면 '최신 오프셋부터' 시작해 빈 구간을 일부러 만들고 다시 채우는 단계를 하나 더 두었다(devops §6.5). Spot은 '비핵심 무상태 워커(Flink TaskManager)'에 허용했는데(infra §4) TaskManager는 창·중복 제거 상태를 가진다. Operator 자동 확장을 쓸지 정하지 않았다.
  8. Flink 관리 화면(REST) 보호가 없었다.
  9. 버전 고정과 실행 기반 작업(WBS)이 없었다.
  10. `telemetry.purchase`·`telemetry.trust-verdicts`의 키가 회차라 ADR-0026 결정 1(대량 텔레메트리는 사용자 해시 키로 전 파티션에 분산)과 어긋났다. `telemetry.queue`는 키를 pid로 적었지만 `QueueAggregate`에는 pid가 없다. 지금 예상량(홀드 피크 초당 2,000건, NFR-003)으로는 성능 문제는 아니다.
  11. '1초 슬라이딩'의 창 크기, 체크포인트 간격, 상태 저장 방식이 정해지지 않았다.
- 확인한 사실(2026-10-20 원문):
  - Flink 2.2 문서: 창의 허용 지연 기본값은 0이고 워터마크 뒤에 온 사건은 버려진다. 슬라이딩 창은 간격이 크기보다 작으면 한 사건이 여러 창에 들어간다. 세션 창은 비활동 간격이 지나야 닫힌다. 워터마크는 병렬 입력 워터마크의 최솟값이라 빈 입력이 붙잡으며, `WatermarkStrategy#withIdleness`로 빈 입력을 표시한다. Kafka 소스는 병렬도가 파티션 수보다 크면 자동으로 유휴가 되지 않는다. Kafka 소스는 체크포인트가 끝날 때 오프셋을 Kafka에 커밋하고 장애 복구에는 이 커밋을 쓰지 않는다(`commit.offsets.on.checkpoint`). MiniBatch·Local-Global 최적화는 Window TVF 집계에 쓸 수 있고 세션 창은 빠진다. `web.submit.enable`·`web.cancel.enable`·`web.rescale.enable`은 기본 true이고, 화면 업로드를 꺼도 세션 클러스터는 REST로 잡을 받는다. `security.ssl.rest.authentication-enabled`는 기본 false다. `slotmanager.redundant-taskmanager-num`(기본 0)은 네이티브 쿠버네티스·YARN에서 예비 TaskManager를 띄워 TaskManager를 잃었을 때 복구를 빠르게 한다. 늦어서 버린 수는 `numLateRecordsDropped`다.
  - Flink Kubernetes Operator 1.16 문서(Job management): 업그레이드 모드는 stateless·last-state·savepoint이고 운영 권장은 뒤의 둘이다. savepoint 모드는 잡이 돌고 있어야 하고, 비정상이면 마지막 체크포인트로 대신하며(끌 수 있음) 체크포인트도 없으면 업그레이드가 실패한다. 모든 모드가 잡을 잠깐 멈추고, 그것도 안 되면 Blue/Green 배포가 있다. 자동 확장의 결정도 같은 업그레이드 주기로 반영된다. 영어 주소가 중국어 경로로 넘겨지며 내용은 영어다.
  - Flink 내려받기 페이지: 최신 안정판은 2.3.0이다. Kafka 커넥터 5.0.0과 JDBC 커넥터 4.1.0은 2.1.x·2.2.x와 호환이다. Operator 1.16.1은 2.3.x~1.19.x와 호환이다.
  - ClickHouse 문서: 공식 Flink 커넥터는 DataStream API만 지원하고(Table API·SQL은 계획), Flink 2.0 이상용 묶음은 2.0.0·2.0.1에서 시험했으며 Java 17 이상이 필요하다. 전달 보장은 적어도 한 번이고 데드 레터 큐가 없어 재시도에도 실패한 묶음은 버린다(`numOfDroppedBatches`·`numOfDroppedRecords`). 비동기 삽입은 크기·시간·건수 조건 중 먼저 닿는 때 쓰이고 그 전에는 조회되지 않는다. 24.2부터 적응형 시간(직접 운영 기본 최소 50ms·최대 200ms)을 쓴다. `wait_for_async_insert` 기본 1은 디스크에 쓴 뒤 응답하고, 0은 유실될 수 있다. ReplacingMergeTree는 병합 때만 중복을 지우고 중복이 없음을 보장하지 않는다.

## 결정

1. **Flink 설계 정본은 docs/streaming.md다(추천 적용).** 잡은 셋이고, 잡마다 입력·키·시간 기준·상태·출력·전달 보장·실패 처리·자원·운영 확인 표를 그 문서에 둔다.

   | 잡 | 저장소 | 하는 일 | 시간 기준 | 출력 |
   | --- | --- | --- | --- | --- |
   | `analytics-ingest` | peaket-data | 원본 적재(기존, analytics §3) | 쓰지 않음(창 없음) | 브론즈 |
   | `ops-rt` | peaket-data | 관제 실시간 표 | 누적은 처리 시각, 1초 칸은 이벤트 시각 | `rt.cumulative`·`rt.bucket`·`rt.pulse` |
   | `trust-reassess` | peaket-trust | 봇 대기 중 재평가와 행동 신호 원시 적재 | 처리 시각(상태 10분 [가정]) | `telemetry.trust-candidates`, 행동 신호 원시 표(30일) |

   심장 박동을 넣는 `rt-pulse`(peaket-data)는 Flink 잡이 아니라 작은 Deployment다.

2. **관제 실시간 표는 덮어쓰기다(추천 적용).** 숫자를 두 종류로 나눈다.
   - **누적**(판매 좌석·판매 금액·주문·발권, 퍼널 단계 누적, 대기열 진입·입장·빠진 번호 누적, 잔여석): 창을 쓰지 않는다. 거래 사건과 `QueueAggregate`는 `eventKey`로 중복을 지우고(상태 수명 거래 7일·`QueueAggregate` 1시간 [가정]), 회차·지표·차원 키마다 합계를 상태에 두며, 처리 시각 1초마다 바뀐 키만 '지금까지 합계'를 쓴다. 버전은 그 키가 처리한 건수다. 정의는 지표 사전(analytics §6)의 같은 이름 지표를 쓴다.
   - **1초 칸**(진입·입장·빠진 번호의 초당 수, 홀드 결과별 수, 판정 종류별 수): 이벤트 시각 1초 텀블링이다. 허용 지연 10초 [가정] 안에 늦게 온 사건은 같은 칸을 고쳐 다시 쓰고, 그보다 늦은 사건은 버리고 센다. '최근 10초·60초' 같은 이동 합과 10초 단위 보조 지표는 조회 때 칸을 더한다. 슬라이딩 창과 별도의 10초 텀블링은 쓰지 않는다.
   - 표는 `ReplacingMergeTree(version)`이고 읽을 때 `FINAL`이나 `argMax(value, version)`로 마지막 값을 읽는다. 병합 시점과 상관없이 읽기가 맞고, 다시 보낸 값은 더해지지 않으며, 빠진 누적 묶음은 다음 초 값이 메운다. 실시간 표 안에서 머티리얼라이즈드 뷰로 합산하지 않는다(analytics §5.5를 고침).
   - Flink는 체크포인트에서 상태와 Kafka 위치를 함께 되돌리므로 재시작 뒤에도 누적은 한 번만 센다. 그래서 판매 좌석·금액의 '실시간 대비 차이 0'은 원천 유실이 없으면 지킬 수 있는 기준이 된다.

3. **시간 기준과 빈 파티션 규칙(추천 적용).**
   - 거래 토픽(`trade.*`)은 이벤트 시각 창에 넣지 않는다(누적만). 원본 적재 잡과 `trust-reassess`도 워터마크를 쓰지 않는다.
   - 이벤트 시각 창에 들어가는 텔레메트리 토픽 셋(`telemetry.queue`·`telemetry.purchase`·`telemetry.trust-verdicts`)에는 `rt-pulse`가 1초마다 모든 파티션에 `PipelinePulse`를 넣는다. 파티션이 비지 않아 워터마크가 늘 나아가고, 같은 사건으로 신선도를 잰다(결정 5). 그 토픽의 다른 소비자는 `PipelinePulse`를 건너뛴다.
   - 워터마크는 이벤트 시각 − 0.5초 [가정]이다(이전 2초). 늦은 사건을 버리지 않고 고쳐 쓰므로 여유를 줄여 반영을 1.5초 앞당긴다. 빈 입력 표시는 30초 [가정]로 길게 두어 안전망으로만 쓴다.
   - 드문 `control.settings`는 `ops-rt` 입력에서 뺀다. 설정 바뀐 시각은 ops-svc 명령 기록에서 조회 때 붙인다.
   - 늦어서 버린 수(`numLateRecordsDropped`)는 NFR-009 누락률에 넣는다.

4. **지표 출처 표(추천 적용).** 관제 화면의 숫자마다 출처를 하나로 정하고 docs/observability.md §8에 둔다. 판단·제어에 쓰는 숫자(입장 속도, 퍼널 다섯 단계 카운터와 입장 전환율, 오류율, 결제 성공률, p99, 에러 버짓)는 클러스터 안 Prometheus다(ADR-0068 결정 2와 같음). 관제 실시간 표는 상세 퍼널(등급·구역별), 판매 누적, 잔여석, 홀드 경합 패배율, 봇 잠정 숫자(추가 검증 격리율, 판정 종류), 대기열 진입 누적과 지금 대기 인원, 파트너 판매 현황이다. NFR-009의 대상을 '관제 실시간 표 지표'로 고친다(목표 p95 5초, 누락률 0.1% 미만은 그대로).

5. **신선도는 심장 박동으로 끝에서 끝까지 잰다(추천 적용).**
   - SLI: ops-svc가 읽을 때마다 '지금 − 관제 실시간 표에 보이는 마지막 `PipelinePulse` 발행 시각'을 `rt_freshness_seconds`로 내고 콘솔에도 보인다. 1분 창 p95가 NFR-009 판정값이다. 누락률은 (늦어서 버린 수 + 싱크가 버린 수 + 텔레메트리 생산자가 버린 수) ÷ 전체다.
   - 지연 예산은 docs/streaming.md §4.5에 둔다. 싱크 버퍼 0.25초 [가정](이전 1초), ops-svc 조회 주기 0.5초 [가정]이고, 최악 합은 약 3초 [추정]다.
   - Degraded 전환은 이 신선도 p95가 5초를 3분 넘게 넘을 때다(조건 숫자는 그대로). 체크포인트 지연과 역압은 원인 패널로 남긴다.

6. **봇 탐지(소유자 승인 A안, 세부는 추천 적용).**
   - 판정 피처는 trust-svc가 사전 검증 요청 때 세션·캐시 Redis에서 바로 센다. 회차별 기기 공유 수는 `tr:{event:E}:devshare:{deviceRef}` HyperLogLog(10분), 호스팅·프록시 대역 ASN의 10초 진입 수는 `tr:{event:E}:asnhost:{asn}:{10초 칸}` 카운터(만료 30초)다 [가정]. 통신사 대역은 세지 않는다. 사람 대부분이 몇 개 통신사 대역에 몰려 있어 신호가 약하고 키가 뜨거워지기 때문이다.
   - Flink `trust-reassess`는 판정 밖에서 대기 중 재평가를 한다. 한 사람만 봐서는 안 보이는 사람 사이 패턴을 찾는다. R1 기기 공유 소급: 같은 회차·같은 기기 가명에 서로 다른 pid가 10분 안 5명 이상이면 그 기기의 pid 모두(이미 통과한 사람 포함). R2 행동 요약값 복제: 행동 요약값을 특징별 구간으로 나눈 지문이 같은 회차에서 10분 안 서로 다른 pid 20명 이상이면 그 pid 모두. 숫자는 [가정]이다. 처리 시각 상태(수명 10분)라 워터마크와 빈 파티션 문제가 없다.
   - 결과는 `telemetry.trust-candidates`(`TrustCandidate`, 키 pid)로 낸다. trust-svc가 명령 5(봇 판정 강도) 프로필의 재평가 모드(끔·그림자·적용, 기본 그림자)에 따라 처리한다. 그림자면 `TrustVerdict`(source `REASSESS`, action `NONE`, `shadow` true)만 낸다. 적용이면 아직 기다리는 사람만 queue-svc `IsolateWaiting`(gRPC, 메시 mTLS)으로 대기 중 격리(queue-admission §7의 격리 기록)를 건다. 이미 입장한 사람은 라벨만 남긴다. 재평가 격리는 회차의 지금 대기 인원의 0.5% [가정]를 10분 안에 넘지 않고, 넘는 몫은 그림자로만 남기며 SEV3를 띄운다(자동화가 사람을 한꺼번에 격리하는 사고를 막는 상한).
   - 격리는 차단이 아니다. 추가 검증(사람 확인과 본인확인 재통과)과 이의 제기·설명 요구(개인정보 보호법 §37의2) 절차는 그대로다. 그림자에서 적용으로 바꾸는 것은 ADR-0039 평가 절차의 그림자 실행 단계에서 사람 오탐 상한(NFR-022)을 확인한 뒤 명령 5로 한다.
   - 행동 신호 원시 표(ClickHouse, 30일 TTL)의 적재도 `trust-reassess`가 한다. `BehaviorSignal`에 회차 ID(`eventId`)와 네트워크 유형(`netClass`: HOSTING·PROXY·OTHER, 호스팅·프록시면 `asn`)을 더한다.
   - Flink 잡에는 세션 창과 CEP를 두지 않는다. 세션 단위 사후 분석은 확정 길(dbt, R2 표본 검토·사후 라벨)이 한다. CEP는 순서 있는 사건 계약을 따로 정하기 전에는 쓰지 않는다.

7. **텔레메트리 키(추천 적용, ADR-0026 결정 1 복원).** `telemetry.purchase` 키는 `purchaseSessionId`, `telemetry.trust-verdicts` 키는 `queueEntryId`(없으면 키 없음), `QueueAggregate` 키는 '회차:파드', `QueueEntryRecord` 키는 pid다. `PipelinePulse`는 파티션을 직접 지정한다. 부하 시험은 초당 3만 건을 한 회차에 몰아서 한다.

8. **싱크 버림과 커버리지(추천 적용).**
   - 두 잡 모두 싱크가 버린 수(`numOfDroppedRecords`)가 0보다 크면 SEV3다. 비동기 삽입은 `wait_for_async_insert=1`로 고정한다.
   - 원본 적재의 마감 커버리지는 '적재 오프셋 = 끝 오프셋'에서 '파티션마다 대상 오프셋 구간의 고유 (파티션, 오프셋) 수 = 구간 길이'로 바꾸고, 모자라면 그 구간을 Kafka 보관(7일) 안에서 다시 적재한다. 이 대조는 트랜잭션 생산자를 쓰지 않는 것(ADR-0026 결정 3)과 삭제 보존(압축 아님) 토픽을 전제로 한다. 트랜잭션을 켜면 대조 방법을 바꾼다.

9. **복구·업그레이드·자원(추천 적용).**
   - 세이브포인트가 맞지 않으면 새 잡은 옛 잡이 마지막 체크포인트 때 Kafka에 커밋한 오프셋부터 읽는다(같은 소비자 그룹). 빈 구간이 없고 겹침만 생기며, 겹침은 브론즈 중복 허용·실버 중복 제거와 실시간 표 덮어쓰기가 흡수한다. 다시 채우는 단계는 없앤다.
   - `ops-rt`의 누적은 그 오프셋 앞까지를 브론즈에서 다시 계산한 시작값 표로 채운 뒤 이어 간다(판매 기간이 Kafka 보관 7일보다 길 수 있어서). 절차는 docs/streaming.md §4.7이고 4.3.1 PoC로 확인한다. `trust-reassess`는 빈 상태로 시작한다(최대 10분 문맥을 잃음).
   - Operator 자동 확장은 끄고 병렬도를 고정한다(확장도 재시작이다). 병렬도 변경은 업그레이드와 같은 규칙(동결 창·마감 실행 중 금지)을 따른다.
   - `ops-rt`·`trust-reassess` TaskManager는 온디맨드이고 `ops-rt`는 예비 TaskManager 1대를 둔다. Spot은 원본 적재 잡에만 허용한다(지연을 견디고 적어도 한 번 + 커버리지 대조로 메운다).

10. **실행 기반·보안·버전(추천 적용).**
    - 버전: Flink 2.2.x, Kafka 커넥터 5.0.0, Operator 1.16.1, Java 17, ClickHouse 커넥터 `flink-connector-clickhouse-2.0.0`. 2.3.0은 Kafka 커넥터가 아직 지원하지 않아 쓰지 않는다. ClickHouse 커넥터의 2.2 동작은 확인 필요이고 4.3.1 PoC로 본다. 안 되면 Flink 1.20 LTS(Kafka 커넥터 3.4.0, ClickHouse 커넥터 1.17 묶음)로 내린다.
    - 잡은 DataStream API로 쓴다(싱크가 DataStream만 지원). 잡마다 FlinkDeployment(애플리케이션 모드)이고 세션 클러스터는 두지 않는다.
    - 관리 화면: `web.submit.enable`·`web.cancel.enable`·`web.rescale.enable`을 끄고, JobManager REST는 네트워크 정책으로 Operator 네임스페이스만 닿게 하며, 인그레스·외부 서비스를 두지 않는다. 운영 중 Flink 화면은 열지 않고 Operator 상태와 지표로 본다.
    - 체크포인트 간격은 `ops-rt` 10초, `trust-reassess` 30초, 원본 적재 60초 [가정]이고, 상태가 있는 두 잡은 RocksDB 상태 저장소를 쓴다. 지표는 Prometheus 리포터로 클러스터 Prometheus에 보낸다.

11. **검증(추천 적용).** docs/verification.md §3.7에 관제 실시간 표 시험을 둔다. 로컬(PC)에서 Kafka·Flink·ClickHouse 컨테이너로 초당 3만 건을 한 회차에 몰아 30분 [가정] 돌려 심장 박동 신선도 p95와 누락률을 재고(실측(PC)), TaskManager 강제 종료 뒤 누적이 정답과 같은지, 빈 파티션에서 멈추지 않는지, ClickHouse를 30초 멈춘 뒤 버림이 세어지고 커버리지 대조가 잡는지 본다(V-T12~V-T15). 비용은 0원이다. Game Day G-07의 기대 결과는 신선도 기준 Degraded 전환으로 고친다.

12. **일정(WBS).** 3.2.2를 'Redis 즉시 피처'로 바꾼다(0일). 4.3.1에 Flink 실행 기반과 `ops-rt` 재설계를 더한다(+1.5일). 4.3.4에 싱크 버림 경보·파티션별 연속성 대조·커밋 오프셋 재시작을 더한다(+0.5일). 4.3.8 봇 대기 중 재평가(1.5일)와 4.3.9 관제 실시간 표 시험(1일)을 새로 둔다. 4.3.3 계약 보강에 키·`PipelinePulse`·`TrustCandidate`·`BehaviorSignal` 필드를 더한다(0일). 합계 +4.5일 [가정]이다.

## 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 실시간 표를 지금처럼 뷰로 합산하고 '차이 0' 기준을 완화 | 기각. 판매 좌석·금액은 파트너와 운영이 가장 많이 보는 숫자이고, 덮어쓰기로 정확히 맞출 수 있는데 기준을 낮출 이유가 없다 |
| 정확히 한 번 싱크(2단계 커밋) 직접 구현 | 기각. 공식 커넥터는 적어도 한 번이고 정확히 한 번은 추적 중이다. 덮어쓰기면 같은 결과를 더 싸게 얻는다 |
| 빈 입력 표시만 짧게(예: 5초) | 기각. 쉬다 돌아온 파티션의 사건이 버려진다. 심장 박동으로 파티션을 비지 않게 하고 표시는 안전망으로만 둔다 |
| 봇 B안: Flink를 봇 탐지에서 뺌 | 기각(소유자 승인 A안). 대기 시간 동안 사람 사이 패턴(기기 공유 소급, 녹화 재생 의심)을 잡는 쓸모를 잃는다 |
| 세션 창을 사후 라벨용으로 Flink에 남김 | 기각. 사후 라벨은 확정 길(dbt, R2)이 이미 하고, 같은 일을 두 곳에 두면 정의가 갈린다 |
| 모든 실시간 숫자를 관제 실시간 표에서 | 기각. 제어 입력에 원격 경로·추가 지연이 들어온다(ADR-0068 결정 2) |
| 모든 실시간 숫자를 Prometheus에서 | 기각. 등급·구역·차원별 숫자는 시계열 수가 커진다(observability §8) |
| Flink 2.3.0 | 보류. Kafka 커넥터가 2.1·2.2까지만 지원한다 |
| Flink 1.20 LTS | 대안으로 남김. ClickHouse 커넥터가 2.2에서 안 되면 내린다 |

## 결과와 트레이드오프

- ADR 70 → 71개, 새 문서 docs/streaming.md, WBS 174 → 176개·389 → 393.5일(+4.5일), 용어 172 → 177개(워터마크, 심장 박동 사건, 실시간 표 덮어쓰기, 대기 중 재평가, 지표 출처 표), 문제 대장 R-80, 질문 29. NFR 수(27)와 목표값은 그대로이고 NFR-009·NFR-022의 수단과 측정 방법을 고친다.
- 부록 학습 지도(docs/appendix-learning-map.md)의 'Flink 세션 윈도우·CEP' 학습 항목 행과 면접 답변 문장의 '1초 간격 슬라이딩 윈도우'는 원문이라 고치지 않았고, 끝의 §13 ADR 대응 표(재구성 때 보완한 요약 표)에만 이 ADR을 더했다. 디자인 캔버스의 SCR-029 보드에는 신선도 표시를 그리지 않았다(화면 설계 d5 §7.2만 고침).
- 실시간 표는 읽을 때 `FINAL`·`argMax` 비용이 든다. 콘솔은 최근 몇 분만 읽어 작다[추정].
- `ops-rt`는 중복 제거 상태(거래 7일)를 RocksDB에 둔다. 거래 사건 양이 작아 수백 MB 이하로 본다[추정, 4.3.9에서 확인].
- 심장 박동은 토픽 셋 × 파티션 수 × 초당 1건이다.
- 판정 피처는 사전 검증 요청마다 세션·캐시 Redis 명령 2~3개를 더한다. 사전 검증은 로비 시간에 퍼진다(architecture §6.1).
- 재평가는 공용 기기(PC방, 가족 태블릿)를 잡을 수 있다. 격리는 추가 검증이라 사람은 통과하고, 상한과 그림자 시작으로 피해 규모를 묶는다.

## 되돌릴 조건

- 4.3.9 측정에서 신선도 p95가 5초를 넘으면 워터마크 여유·싱크 버퍼·조회 주기를 고치고, 그래도 넘으면 1초 칸을 ops-svc의 Prometheus 대체 표시로 돌리고 NFR-009를 다시 정한다.
- ClickHouse 커넥터가 Flink 2.2에서 안 되면 Flink 1.20 LTS로 내린다.
- 재평가 그림자 기간 표본 검토에서 사람 오탐이 NFR-022 상한(0.5%)을 넘으면 그 패턴은 적용으로 바꾸지 않고, 숫자를 고치거나 뺀다.
- 판정 피처 Redis 명령이 세션·캐시 클러스터 CPU 포화 경보를 일으키면 기기 공유 수를 표본으로 세거나 재평가로만 돌린다.

## 남는 한계

- 시작값 재계산 경계를 넘는 재발행 중복(같은 사건이 경계 앞뒤에 한 번씩 실린 경우)은 실시간 표에서 두 번 셀 수 있고 R0 대조에서 드러난다.
- 심장 박동 신선도는 관제 실시간 표 경로만 잰다. Prometheus 판단 숫자의 신선도는 제어 입력 없음 규칙(ADR-0069)이 맡는다.
- 공식 ClickHouse 커넥터의 Flink 2.2 동작은 확인 필요다.
- CEP를 쓰지 않으므로 일정 간격 반복 같은 순서 패턴은 브라우저 요약값(입력 간격 분산)과 서버 쪽 신호에만 기댄다.
- R1·R2의 숫자와 지문 구간, 격리 상한, 워터마크 여유, 허용 지연, 체크포인트 간격은 [가정]이고 4.3.8·4.3.9와 그림자 기간 표본 검토에서 정한다.
- 대기 중 재평가도 자동화된 결정의 입력이므로 기존 설명·재검토 절차(POL-006, 개인정보 보호법 §37의2)에 들어간다. 새 법률 해석은 더하지 않았고, 개인정보 처리방침의 자동화된 결정 공개 문구에 '대기 중 재평가'를 넣는 것은 법률 검토 때 함께 본다.
