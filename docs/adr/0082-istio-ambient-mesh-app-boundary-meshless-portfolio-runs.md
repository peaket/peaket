# ADR-0082: 서비스 메시는 Istio 앰비언트로 정하고, 메시와 앱의 일을 나누며, 포트폴리오 실행은 메시 없이 라이브러리 기본 기능과 정책으로 메운다(2026-10-22)

- **상태**: 채택 (2026-10-22. 소유자가 "이 프로젝트에 istio로 도입하는거에 대해 어떻게 생각하세요?"라고 묻고, 도입하면 재시도·시간 초과·서킷 브레이커·부하 분산·여러 언어 통신·서비스 사이 mTLS·관측 인터셉터 로직을 앱에서 빼야 하는지, 데이터 파티션·일관된 해싱·데이터 다중화·백업·가십 같은 분산형 장애 감지가 필요한지 물었다. 분석을 본 뒤 "근데 이 포트폴리오가 실제로는 istio로 안올리긴 하거든요"라며 일반 네트워크 재시도·클라이언트 쪽 부하 분산·파드 사이 TLS 공통 코드를 예비로 둘지 물었고, 두 답을 본 뒤 "앞의 Istio 분석과 메시 없는 실행 규칙을 묶어 추천대로 ADR-0082로 남기고 문서에 반영해 주세요"라고 승인했다. 결정의 방향은 소유자 승인이고, 값과 세부는 추천 적용이다. 추천 적용 목록은 아래 '소유자 검토 대상'에 모았다) 2026-10-23(4차 전수 점검): 결정 4의 '측정은 파드 하나로 잰다(ADR-0058)'의 근거는 부품별 측정을 정한 ADR-0057로 읽는다. 2026-10-27(ADR-0099): Flink 파드는 없어졌다. 스트림 작업자 파드는 다른 서비스처럼 메시 앰비언트 L4에 두고, gRPC를 받지 않으므로 웨이포인트를 두지 않는다. 업무 서비스와 작업자가 모두 Node.js라서 '여러 언어 통신'의 Flink(Java)는 없다. 2026-10-28(ADR-0102, 소유자 승인 '추천안 동의'): 결정 1의 '관제 제어 TCP 포트'를 제어 전용 gRPC 포트로 바꾼다. 업무 gRPC를 받는 서비스라도 제어 포트의 제어 전용 Service(`<서비스>-control`)에는 웨이포인트를 붙이지 않고, 노드 프록시의 L4 허용 목록(ops-svc·비상 런북 Job 신원)만 둔다. 2026-10-28(기술 검토 중간-071, 소유자 승인 '추천안 동의'): 결정의 '그 서비스에는 웨이포인트 신원만 받는 L4 정책'을 포트별 허용 표로 바꾼다. 업무 gRPC 포트는 그 서비스의 웨이포인트 신원만, REST 포트는 그 서비스로 경로를 보내는 게이트웨이 신원만, identity-svc 내부 엔드포인트 포트는 소비자 웹 앱 서버만(ADR-0011. 파트너 로그인은 ADR-0119로 gw-partner REST를 거친다), 제어 포트는 ops-svc·런북 Job만(ADR-0053 결정 11) 받는다. 부르는 쪽 신원은 웨이포인트 정책이 거른다. 게이트웨이 → 서비스 REST 허용, 다른 파드 → gRPC 직접 거부 같은 정책 시험은 D-T36이다(docs/architecture.md §5, docs/infra.md §9). 2026-10-28(기술 검토 낮음-166, 소유자 승인 '추천안 동의'): 검토한 대안 '앰비언트 L4 + 클라이언트 쪽 gRPC 분산'의 기각 이유 '분산 코드가 앱으로 돌아온다'는 약했다. grpc-js에서 `round_robin`은 채널 설정이고 재시도는 서비스 설정(JSON)이며, 이상 호스트 제외 정책(`outlier_detection`, `load-balancer-outlier-detection.ts`)도 있다(grpc-node 소스, 2026-10-28 확인). 헤지는 ADR-0117로 쓰지 않는다. 그래서 이 대안을 ADR-0010 재검토 조건의 '운영 비용 비교 항목'으로 둔다: 웨이포인트 쪽(수·자원·업그레이드 차례)과 클라이언트 쪽(DNS 다시 찾기 최소 30초와 `max_connection_age`로 새 파드를 아는 지연, 이상 호스트 제외 설정, L7 인가를 앱 가드·L4 허용 목록으로 옮기는 일)을 같은 시험(D-T36, 롤링 재시작 오류율)으로 견주고, 오류율·p99가 같은데 웨이포인트 비용이 크면 바꾸는 새 ADR을 쓴다(docs/architecture.md §5 메시 절). 2026-10-29(문서 대조 R-166): 포트 표의 '내부 엔드포인트 포트' 행은 없어졌다. 세션 생성은 웨이포인트 허용 목록 뒤의 identity-svc gRPC `SessionService`로 읽는다(docs/architecture.md §5, docs/features/identity.md). 2026-10-29(원문 확인): 인용한 Kafka 4.1 운영 문서의 '파티션을 늘려도 기존 데이터를 옮기지 않음'은 Kafka 3.9 문서에서도 같다(review/open-items.md 62). 2026-11-01(openspec 변경 add-breakers-purchase-auth-and-grpc-channel, BUILD_ORDER FND-100, R-226): 결정 4의 채널 생성 함수는 서비스 템플릿의 `createGrpcClient`다. 서비스 설정에는 부하 분산 방식만 넣고(`service` pick_first, `headless-round-robin` round_robin), DNS 서비스 설정을 읽지 않으며, 의존성마다 따로 연결하고, `grpc.enable_retries`를 넣지 않는다(바꾸려 하면 예외). 프로필은 `PEAKET_GRPC_LB_PROFILE`이고 `headless-round-robin`은 `local`·`ci`에서만 받는다. 서버 `grpc.max_connection_age_ms`는 30초 [가정]다(docs/api/guidelines.md §5).

## 맥락

- **소유자 질문(2026-10-22)**
  - Istio를 들이는 것이 합리적인가.
  - 들인다면 재시도, 시간 초과, 서킷 브레이커, 부하 분산, 여러 언어 환경의 통신, 서비스 사이 mTLS, 관측 인터셉터 로직을 앱에서 빼야 하는가.
  - 데이터 파티션, 일관된 해싱, 데이터 다중화, 백업, 가십 같은 분산형 장애 감지를 들여야 하는가, 들인다면 어떻게 하는가.
  - 실제 포트폴리오 실행에는 Istio를 올리지 않는다. 그러면 일반 네트워크 재시도·클라이언트 쪽 부하 분산·파드 사이 TLS 공통 코드를 예비로 갖고 있는 것이 좋은가.
- **지금 설계**
  - 메시는 이미 쓰기로 했고 제품만 같은 시나리오로 재서 고르기로 했다(ADR-0010, wbs 0.5.2). 메시의 일은 L7 요청 단위 gRPC 분산, 파드 사이 mTLS, 재시도 예산 안의 전송 재시도다.
  - 재시도는 메시 한 층에서 최대 1회이고, 게이트웨이와 앱은 네트워크 재시도를 하지 않으며, 상태를 바꾸는 요청은 멱등키가 있어도 재시도·헤지하지 않는다. 결제사 승인 재시도는 payment-svc의 업무 절차(10분)다(ADR-0009). 앱은 데드라인을 넘기고(홀드 40ms, 결제사 2초, 종단 3초), 의존성마다 opossum 차단기와 대체 응답(Degraded)을 둔다.
  - 메시 신원은 권한에도 쓴다: identity-svc 내부 엔드포인트는 웹·파트너 앱 서버만, 관제 제어 TCP 포트는 ops-svc와 런북 Job만 받는다(ADR-0053). Flink 파드도 메시에 넣는다(ADR-0073).
  - 데이터는 이미 나눠 담고(Redis 해시 태그, Kafka 키, 도메인별 Aurora 4개, 주문·결제·티켓 월 파티션, 커지면 셀 분할 ADR-0028), 복제하고(Aurora 다중 AZ 동기·ticket DB 다른 리전 읽기 복제본, Redis 샤드마다 비동기 복제본 1개, MSK 복제 3벌·`min.insync.replicas=2`·`acks=all`, ClickHouse 2벌, Mimir 3벌), 백업한다(시점 복구 35일, 다른 리전 스냅샷, 신선도 경보, 분기 복원 훈련, docs/infra.md §6).
  - 포트폴리오 기간에 운영·스테이징은 설계로만 두고, 실행은 로컬(kind/k3d)·CI·데모 오버레이에서 한다(ADR-0057). 이 실행 환경에 메시를 둔다는 말은 문서에 없었다.
- **확인한 외부 사실(2026-10-22, 원문)**
  - Istio(지금 1.31.2): 기본 분산은 최소 요청이고, HTTP 요청 시간 초과는 기본으로 꺼져 있으며, 재시도 정책이 없으면 메시 전체 기본은 `attempts: 2`·`retryOn: connect-failure,refused-stream,unavailable,cancelled`다(MeshConfig `defaultHttpRetryPolicy`로 바꿈). DestinationRule `retryBudget`은 진행 중 요청 대비 동시 재시도 상한이고 기본 20%다. 이상 호스트 퇴출은 설정하면 연속 5xx 5회·검사 10초·퇴출 30초·최대 10%가 기본이다. 일관된 해시(ring hash·Maglev)는 느슨한 고정이라 호스트가 늘거나 줄면 깨진다.
  - Istio 앰비언트: 노드마다 하나인 ztunnel은 L3·L4(mTLS, 인증, L4 인가, 텔레메트리)만 하고 HTTP를 해석하지 않는다. HTTP 라우팅·부하 분산·서킷 브레이킹·레이트 리밋·장애 주입·재시도·시간 초과, L7 인가, HTTP 지표·접근 로그·추적은 웨이포인트가 있어야 한다. 웨이포인트는 처음 보낸 주소가 서비스일 때 지나고(기본 `istio.io/waypoint-for: service`), 웨이포인트 정책은 거친 트래픽에만 걸린다. VirtualService는 앰비언트에서 알파이고 Gateway API와 섞으면 안 되며, EnvoyFilter는 웨이포인트에서 지원하지 않는다. 사이드카와 앰비언트는 한 메시에 섞을 수 있다. 앰비언트는 1.24(2024-11-07)에 정식이 됐다.
  - Istio 업그레이드: ztunnel을 제자리에서 올리면 리비전을 써도 그 노드의 앰비언트 통신이 잠깐 끊긴다(노드 비우기와 블루그린 노드 풀 권고). istio-cni는 리비전 카나리 업그레이드를 지원하지 않고, 제어 평면을 먼저 올린다(한 마이너 버전 차이 안).
  - Istio 성능(1.24, 초당 1,000요청·1KB): 사이드카 0.20 vCPU·60MB, 웨이포인트 0.25 vCPU·60MB, ztunnel 0.06 vCPU·12MB.
  - Istio 추적: 프록시가 스팬을 내도 앱이 받은 요청의 추적 헤더를 그 요청 때문에 나가는 요청에 넘겨야 한 추적으로 이어진다.
  - Istio 보안: PeerAuthentication 모드가 없으면 메시 전체는 PERMISSIVE(평문도 받음)다. 기본 CA는 자체 서명 루트이고, 운영은 오프라인 루트가 발급한 중간 CA를 `cacerts`로 꽂기를 권한다. ztunnel은 그 노드 파드의 신원(서비스 계정)마다 워크로드 인증서를 대신 받고, CA는 그 노드에 없는 신원 요청을 거절한다. 워크로드 최소 TLS 버전은 `meshConfig.meshMTLS.minProtocolVersion`으로 정한다(최대 1.3). 메시 지표의 칸은 주석 `sidecar.istio.io/statsHistogramBuckets`(알파)로 바꾼다.
  - Linkerd: 2024년 2월부터 오픈소스 프로젝트는 안정판 아티팩트를 내지 않고 업체 쪽이 낸다. 2.20(2026-06-23)도 대응 edge 판과 업체 배포판으로 나왔다.
  - Envoy Gateway: 백엔드로 보내는 방식 `routingType`은 `Service`(ClusterIP)와 `Endpoint`이고 기본은 `Endpoint`(파드 주소로 직접)다.
  - gRPC: 재시도 설계 A6는 클라이언트를 떠나지 못한 요청과, 서버 라이브러리에는 닿았지만 서버 앱이 보지 못한 요청(`REFUSED_STREAM`, GOAWAY의 마지막 스트림 ID 뒤)을 재시도 설정과 상관없이 투명하게 다시 보낸다(뒤의 것은 1회). grpc-js는 재시도·헤지 정책이 없으면 이 투명 재시도만 하는 상태로 동작하고(`grpc.enable_retries`를 0으로 하면 끔), pick_first(기본)·round_robin 분산과 서버 `grpc.max_connection_age_ms`를 지원한다. gRPC 상태 코드 문서는 UNAVAILABLE에 대해 멱등하지 않은 작업은 재시도가 늘 안전하지는 않다고 적는다.
  - NestJS: gRPC 서버의 `close()`는 `gracefulShutdown` 옵션이 없으면 `forceShutdown()`으로 진행 중 호출을 끊고, 켜면 `tryShutdown()`으로 마친 뒤 닫는다(nest 저장소 소스). 종료 훅은 `enableShutdownHooks()`를 불러야 SIGTERM에 돈다(자원 때문에 기본으로 꺼짐, 공식 문서).
  - kind는 v0.24.0(2024-08-15)부터 NetworkPolicy를 기본으로 지킨다(kube-network-policies).
  - Redis Cluster 명세: 노드는 클러스터 버스에서 가십으로 서로를 확인하고, `NODE_TIMEOUT` 넘게 응답이 없으면 PFAIL, 마스터 과반이 정해진 시간 안에 확인하면 FAIL로 확정한다. 키 공간은 16,384개 해시 슬롯이다.
  - Kafka 4.1 운영 문서: 파티션을 늘려도 기존 데이터는 옮기지 않고, `hash(key) % 파티션 수`로 나눈 데이터는 섞일 수 있다.
  - 쿠버네티스 노드 심장 박동은 Node `.status` 갱신과 `kube-node-lease`의 Lease 둘이다. KIP-631(KRaft)에서 브로커는 활성 컨트롤러에 심장 박동을 보내고 리스와 펜싱 상태를 받는다.
- **이 프로젝트의 사정**: 소유자는 실제 포트폴리오 실행에 Istio를 올리지 않는다. 메시는 운영 설계와 코드(매니페스트·정책)로만 있다.

## 결정

1. **운영 설계의 메시는 Istio이고 기본은 앰비언트 모드다(소유자 승인)**
   - 노드 프록시(ztunnel)가 모든 서비스 사이 연결을 L4 mTLS로 감싼다. 메시 전체 PeerAuthentication은 STRICT, 최소 TLS 버전은 `TLSV1_3`으로 정한다(앰비언트 노드 프록시에 같은 값이 걸리는지는 wbs 2.11.2에서 확인).
   - 서비스 사이 gRPC를 받는 서비스(docs/architecture.md §3.2 서비스 간 통신 매트릭스의 gRPC 행에서 받는 쪽)는 서비스 단위 웨이포인트를 둔다. 웨이포인트가 요청 단위 분산, 재시도, 시간 초과, 연결 상한, 이상 파드 퇴출을 맡는다. 서비스마다 따로 두고 여러 AZ에 여러 벌 띄운다(PDB, 오토스케일). 그 서비스에는 웨이포인트 신원만 받는 L4 정책을 짝으로 둔다.
   - 웨이포인트 경로의 p99 증가가 PoC 기준(docs/architecture.md §9.4, 2ms 이하)을 넘는 서비스만 사이드카로 둔다.
   - 게이트웨이(Envoy Gateway)는 그대로 두고 파드 주소로 보내는 기본 방식을 쓴다. 게이트웨이 네임스페이스도 앰비언트에 넣어 노드 프록시가 암호화만 더한다. 게이트웨이에서 서비스로 가는 구간은 웨이포인트를 지나지 않는다(파드 주소로 보낸 트래픽이라). 함께 동작하는지는 PoC로 확인한다.
   - 관제 제어 TCP 포트(ADR-0022)와 Flink 파드(ADR-0073)에는 웨이포인트를 두지 않고 노드 프록시의 L4 허용 목록만 둔다. 제어 명령은 L7 프록시 대기열을 지나지 않는다.
   - 설정은 Gateway API(HTTPRoute)와 DestinationRule·AuthorizationPolicy·PeerAuthentication으로만 쓴다. VirtualService와 EnvoyFilter는 쓰지 않는다.
2. **메시 기본값을 설계에 맞게 덮어쓴다(방향은 소유자 승인, 값은 추천 적용)**
   - 재시도: 메시 전체 기본을 1회, `connect-failure,refused-stream`(요청이 서버 앱에 닿지 않은 경우)으로 바꾼다. `unavailable`은 읽기 전용 경로에만 더한다.
   - 재시도 예산: 진행 중 요청의 10% [가정, wbs 4.6.1에서 확정].
   - 시간 초과: 호출 경로마다 앱 데드라인 상한보다 조금 길게 둬 앱 데드라인이 먼저 끝나게 한다.
   - 이상 파드 퇴출: 게이트웨이와 같은 원칙이다. 과부하 503을 퇴출 계산에서 빼는 설정과 최대 퇴출 비율은 wbs 4.6.1에서 함께 정한다(ADR-0069).
   - 부하 분산: 최소 요청(기본)을 그대로 쓴다. 일관된 해시는 핫패스에 쓰지 않는다.
   - 인증서: 운영은 오프라인 루트가 발급한 중간 CA를 `cacerts`로 꽂는다. 워크로드 인증서는 노드 프록시가 메모리에만 둔다.
   - 추적: 메시 추적은 끈다. 앱 OTel 스팬이 정본이다. 웨이포인트 HTTP 지표는 서비스 지도의 보조로만 쓰고 SLO 판단에 쓰지 않는다(칸을 바꾸는 주석이 알파라 ADR-0077의 표준 칸과 맞추기 어렵다).
   - 표는 docs/architecture.md §5 '메시 기본값 덮어쓰기'다.
3. **메시가 맡을 일과 앱에 남길 일을 나눈다(소유자 승인)**
   - 메시: 서버에 닿지 않은 요청의 전송 재시도, 호출 한 번의 시간 상한, 연결 상한과 이상 파드 퇴출, gRPC 요청 단위 분산, 파드 사이 mTLS와 서비스 신원 허용 목록, 서비스 쌍별 연결·요청 지표.
   - 앱: 업무 재시도(결제 승인 확인, 같은 멱등키), 데드라인 계산과 전달, 차단기와 대체 응답·벌크헤드, 메시 밖 대상의 TLS(관리형 저장소, 결제사·본인확인·알림 같은 외부 API), 사용자 인증·권한, 추적 헤더 전달과 업무 속성 스팬, SLO 지표와 업무 지표, 서비스 사이 계약(protobuf·Avro).
   - 앱 코드에는 일반 네트워크 재시도, 클라이언트 쪽 부하 분산, 파드 사이 TLS를 넣지 않는다. 메시와 함께 켜지면 재시도가 곱해지고(두 층이 2회씩이면 한 요청이 최대 9번), 파드 주소로 나누면 웨이포인트를 건너뛰며, 앱 TLS는 메시가 요청 내용을 보지 못하게 한다.
   - 여러 언어 통신은 메시가 언어와 상관없이 같은 암호화·정책을 주는 것으로 충분하다. 서비스 대부분이 Node.js이고 Flink(Java)가 있어 언어별 통신 공통 라이브러리는 만들지 않는다.
   - 표는 docs/architecture.md §5 '메시와 앱의 책임 경계'다.
4. **포트폴리오 실행(로컬·CI·데모)은 메시 없이 돌고, 예비 공통 코드는 두지 않는다(소유자 승인)**
   - 재시도: gRPC 라이브러리의 투명 재시도만 남긴다. 서비스 템플릿의 gRPC 채널은 `grpc.enable_retries`를 끄지 않고 재시도·헤지 정책을 넣지 않는다(docs/api/guidelines.md §5).
   - 부하 분산: 서비스 사이 gRPC는 Service 이름과 pick_first(기본)다. 데모는 서비스마다 1벌이고 측정은 파드 하나로 잰다(ADR-0058). 서비스 사이 gRPC를 여러 벌로 재야 하는 측정에서만 로컬 오버레이 설정으로 헤드리스 Service, `round_robin`, 서버 `grpc.max_connection_age_ms`를 켠다. 이 설정 프로필은 운영 오버레이에서 쓸 수 없다(결정 6).
   - 암호화와 호출자 제한: 로컬 클러스터 안은 평문이다(합성 데이터만). 호출자 제한은 NetworkPolicy가 파드 라벨로 대신한다.
   - 장애 주입은 메시 대신 Toxiproxy로 하고, 필요하면 서비스 사이에도 둔다(docs/verification.md §2.5).
5. **NestJS 종료 설정을 서비스 템플릿에 넣는다(추천 적용)**
   - 롤링 재시작 때 요청을 지키는 것은 우아한 종료와 투명 재시도다. 그래서 `app.enableShutdownHooks()`와 gRPC 마이크로서비스 옵션 `gracefulShutdown: true`를 템플릿에 넣고, 빼면 템플릿 시험이 실패하게 한다(docs/devops.md §6.4, D-T27). 메시가 있어도 필요한 설정이다.
6. **운영 배포물은 메시가 있어야 배포되게 막는다(추천 적용)**
   - 운영 오버레이 검사(gitops-check): ① 서비스 네임스페이스에 앰비언트 등록 라벨 `istio.io/dataplane-mode: ambient`가 있다, ② 메시 전체 STRICT PeerAuthentication이 들어 있다, ③ gRPC 부하 분산 프로필 `headless-round-robin`을 쓰지 않는다. 어기면 PR이 막힌다(docs/devops.md §4.3, D-T28). 로컬·데모 오버레이에는 걸지 않는다.
7. **데이터 관리 규칙 세 가지를 더한다(소유자 승인)**
   - ① Kafka 파티션 늘리기와 Redis 샤드 추가·슬롯 이동(리샤딩)은 정비 시간에만 한다(docs/devops.md §12.1). 키 순서가 필요한 거래 토픽은 파티션을 늘리지 않고, 판매가 없는 날 새 토픽으로 옮긴다(§7.5).
   - ② 핫패스에는 일관된 해시 부하 분산을 쓰지 않는다(공연 ID로 걸면 인기 공연 하나가 파드 몇 개에 몰린다).
   - ③ 앱 수준의 가십·멤버십 감지는 두지 않는다. 감지는 각 층의 제품이 한다(docs/architecture.md §5 '장애 감지 층').
   - 파티션·다중화·백업은 지금 설계를 그대로 둔다. 일관된 해싱은 Redis Cluster의 해시 슬롯이 이미 같은 일을 하므로 직접 만들지 않는다.
8. **메시 PoC는 선택이다(소유자 승인)**
   - wbs 0.5.2의 메시 비교는 하면 'Istio 앰비언트(gRPC 서비스만 웨이포인트) 대 사이드카'를 같은 시나리오로 재서 p99 증가 2ms 이하와 자원으로 판정한다. 하지 않으면 메시 지연은 Istio 공식 측정(1.24) 인용과 가정 표시로 둔다. 게이트웨이 차단 상한 PoC는 그대로 한다.

## 검토한 대안

| 대안 | 판단 |
| --- | --- |
| Linkerd를 계속 후보로 두기 | 기각. 오픈소스 프로젝트가 2024년 2월부터 안정판을 내지 않고(2.20도 업체 배포판), 우리 문서도 위험 구성 요소로 표시했다(devops §4.4). 지연이 낮아도 안정판 공급 문제를 풀지 못한다 |
| Istio 사이드카를 기본으로 | 기본으로는 기각. 게이트웨이 파드와 서비스 파드 양쪽에 프록시가 붙어 오픈 직후 진입 경로(초당 20만 건)의 프록시 CPU가 약 80 vCPU로, 노드 프록시 약 24 vCPU의 3배쯤이다 [추정: 공식 측정값을 그대로 곱함]. 버전을 올릴 때마다 앱 파드를 다시 띄워야 한다. 웨이포인트 지연이 기준을 넘는 서비스에만 쓴다 |
| 앰비언트 L4만 쓰고 앱이 gRPC를 직접 나누기 | 기각. 앱이 파드 주소로 보내 메시의 L7 정책·재시도가 빠지고 분산 코드가 앱으로 돌아온다. ADR-0010 재검토 조건의 대안으로만 남긴다 |
| 예비 공통 코드(재시도·클라이언트 분산·앱 TLS)를 꺼 둔 채 갖고 있기 | 기각. 메시와 함께 켜지면 결정 3의 세 가지 문제가 생기고, 꺼 둔 코드는 시험되지 않아 필요할 때 믿을 수 없다 |
| 포트폴리오 로컬에도 Istio를 늘 설치 | 기각. 소유자가 실제 실행에 메시를 올리지 않기로 했다. 비교 PoC(선택)에서만 kind에 올린다 |
| 앱 수준 가십 장애 감지(memberlist·SWIM 같은 라이브러리) | 기각. 직접 운영하는 상태 저장 클러스터가 없고, 쿠버네티스와 다른 두 번째 생존 판단은 둘이 엇갈릴 때 분할 판단 위험을 키운다. 리더가 둘이 되는 문제는 펜싱으로 막는다(ADR-0056) |
| 일관된 해시로 공연마다 파드 고정(캐시 적중) | 기각. 인기 공연 하나가 파드 몇 개에 몰린다 |
| 공연 ID 샤딩과 자체 해시 링 | 기각(ADR-0028 유지). 여러 DB에 걸친 트랜잭션으로 p99가 나빠진다 |

## 결과와 트레이드오프

- **좋은 점**
  - 메시 제품이 정해져 보안 추적 표·키 표·업그레이드 규칙이 한 제품 기준이 됐다.
  - 메시와 앱의 경계가 표로 고정돼 같은 일을 두 층이 하지 않는다.
  - 메시 없이 도는 포트폴리오도 롤링 재시작 때 요청을 지키는 장치(우아한 종료와 투명 재시도)가 명시됐고, NestJS 기본값 함정 두 개(종료 훅 꺼짐, gRPC 강제 종료)를 템플릿 시험이 막는다.
  - 운영 배포물에서 메시가 빠지면 배포 검사가 막는다.
- **남는 한계**
  - 포트폴리오 실행은 메시 아래 동작(웨이포인트 지연, 메시 재시도·시간 초과·L7 정책, mTLS와 신원 허용 목록)을 증명하지 못한다. PoC를 하지 않으면 공식 측정을 인용한다.
  - 로컬 클러스터 안은 평문이고, 호출자 제한은 인증서가 아니라 파드 라벨 기준이다.
  - 웨이포인트는 거치는 단계를 하나 더하고, 서비스마다 두는 작은 중앙 프록시라 ADR-0010 결정 3(내부 중앙 게이트웨이를 두지 않음)과 일부 겹친다.
  - 노드 프록시를 그 노드의 모든 파드가 함께 써서 문제와 업그레이드 영향이 노드 단위다.
  - 앰비언트의 L7 설정 일부는 알파이거나 지원 밖이다(VirtualService, EnvoyFilter).
  - 투명 재시도는 서버가 처리했을 수 있는 실패를 다시 보내지 않는다. 연결이 끊기는 순간 진행 중이던 호출은 실패로 보이고 차단기·대체 응답·사용자 재시도가 받는다.
- **반영 수치(2026-10-22)**: ADR 81 → 82, 검토 기록 R-91, 용어 195 → 197(서비스 메시, 투명 재시도), devops 시험 D-T27·D-T28. WBS 일정은 그대로다(0.3.3·0.3.6·0.4.4·0.5.2·2.11.2의 설명만 고침).

## 되돌릴 조건

- 측정에서 웨이포인트 경로와 사이드카 모두 p99 증가가 2ms를 넘으면 ADR-0010 재검토 조건(헤드리스 Service와 클라이언트 쪽 분산)을 새 ADR로 연다.
- Linkerd 오픈소스가 안정판을 다시 내면 비교를 다시 본다.
- Game Day에서 노드 프록시의 노드 단위 영향이 SLO를 깨면 그 노드 풀의 핫패스 서비스를 사이드카로 바꾸는 것을 본다.
- 포트폴리오를 클라우드에서 실제로 운영하게 되면(선택 데모 포함) 결정 4를 다시 본다. 운영 오버레이 검사(결정 6)가 메시를 요구한다.
- 직접 운영하는 상태 저장 클러스터를 들이면 그 제품에 들어 있는 장애 감지를 쓴다(결정 7 ③은 앱 코드에 대한 규칙이다).

## 소유자 검토 대상(추천 적용)

1. 재시도 예산 10%(Istio 기본 20%). SRE 책의 클라이언트 재시도 비율 10%를 따랐고 wbs 4.6.1에서 확정한다.
2. 메시 시간 초과는 앱 데드라인 상한보다 조금 길게 둔다(앱 데드라인이 먼저 끝나게).
3. 메시 추적은 끄고 앱 OTel 스팬만 정본으로 쓴다.
4. 운영 CA는 오프라인 루트의 중간 CA를 `cacerts`로 꽂는다(포트폴리오에는 적용하지 않음).
5. NestJS 종료 설정 두 개와 템플릿 시험(D-T27).
6. 운영 오버레이 검사 세 가지(D-T28)와 부하 분산 프로필 이름 `service`·`headless-round-robin`.
7. 읽기 전용 경로에만 메시 재시도 조건 `unavailable`을 더한다.
