# ADR-0075: 감사 기록을 피켓 밖에서도 확인하게 한다 — 서명한 머클 체크포인트를 공개 타임스탬프(OpenTimestamps·비트코인)에 고정해 게시하고, 누구나 돌리는 검증 도구를 둔다(2026-10-21)

- **상태**: 채택 (2026-10-21. 소유자 질문 "audit 같은 경우는 조작이 절대 되어서는 안되는데 블록체인을 활용해서 조작이 불가능한 장부 시스템을 만들어버리는건 어떤가요?"에, 블록체인 네트워크를 직접 운영하는 것은 과하고 요약값만 공개 장부에 고정하는 방식과 검증 도구를 추천했다. 소유자가 "네 승인"이라고 답했다. 방식은 소유자 승인이고 세부는 추천 적용(2026-10-21)이다. 숫자는 측정 전 가정값이다. ADR-0053 결정 12(키 건 해시 체인, 5분 S3 앵커, 1시간 검증)와 ADR-0073 결정 25(법정 접속기록 일 단위 해시 앵커)는 그대로 두고 그 위에 외부 앵커를 더한다.)
- **관련 ID**: FR-031, FR-045, FR-063, NFR-017, POL-025, ADR-0012, ADR-0050, ADR-0053, ADR-0073, SCR-031, review/consistency-review.md R-84, wbs 4.4.1
- **관련 문서**: docs/features/control-tower.md §7·§14·§15, docs/data.md, docs/observability.md §5·§9, docs/infra.md §4.1·§9, docs/devops.md §4.1·§6.1, docs/security/secrets-and-keys.md, docs/security/data-classification.md, docs/security/asvs/delivery.md, planning/01 §5.2, planning/02 NFR-017, planning/03(용어), planning/04 SCR-031, design/d5 §7.4, guide/10

## 맥락

- 지금 설계(ADR-0053 결정 12)는 감사 기록마다 키를 건 해시 체인을 잇고(키는 KMS 밖으로 나오지 않음), 5분마다 체인의 마지막 값을 S3 Object Lock 컴플라이언스 모드 버킷에 남기며, 1시간마다 다시 계산해 대조한다. 법정 접속기록은 하루 한 번 파일 목록의 SHA-256을 같은 버킷에 남긴다(ADR-0073 결정 25). 고치거나 지운 기록은 피켓의 검증에서 드러난다.
- 남은 빈틈은 planning/01 §5.2에 적혀 있다: 마지막 앵커 뒤 구간의 끝 기록 삭제, ops-svc의 KMS 권한까지 가진 내부자의 앵커 전 구간 수정. 여기에 하나가 더 있다. **검증을 피켓만 할 수 있다.** 앵커가 피켓의 AWS 계정 안에 있어서 파트너·규제기관·손님은 "피켓이 검증했다"를 믿을 수밖에 없다. 티켓팅은 순번·입장 조작 의혹이 핵심 불신이라 이 빈틈이 크다.
- 블록체인이 실제로 주는 것은 두 가지다. ① 기록을 앞 기록의 해시로 엮어 하나를 고치면 뒤가 어긋나게 하는 것(피켓은 이미 함), ② 서로 믿지 않는 여러 참여자가 같은 장부를 나눠 갖는 것. ②는 노드를 피켓 혼자 운영하면 사라진다. 관리형 원장 DB인 Amazon QLDB는 2025-07-31에 지원이 끝났고, AWS는 이전 대상으로 Aurora PostgreSQL을 안내했다(AWS 공식 블로그 일본어판 2024-10-08 글, 2026-10-21 확인). 공개 블록체인에 기록 원문을 쓰면 개인정보가 지울 수 없게 공개된다. 「개인정보의 안전성 확보조치 기준」(고시 제2026-9호) 제13조 제3항은 기술적 특성으로 파기가 현저히 곤란하면 복원이 불가능하도록 익명처리하라고 정하고, 제8조 제3항은 접속기록이 위·변조되지 않게 안전하게 보관하는 조치를 요구할 뿐 방법을 정하지 않는다(2026-10-21 국가법령정보센터 원문 확인).
- **외부 원문 확인(2026-10-21 열람)**: RFC 9162(Certificate Transparency 2.0) §2.1(머클 트리 해시: 잎은 `HASH(0x00 ‖ d)`, 안쪽 노드는 `HASH(0x01 ‖ 왼쪽 ‖ 오른쪽)`, k는 n보다 작은 가장 큰 2의 거듭제곱. 포함 증명의 생성과 검증), OpenTimestamps 공식 사이트와 클라이언트 README(비트코인 블록체인을 타임스탬프 공증으로 쓴다, 공개 캘린더 서버는 무료이고 등록·API 키가 없다, 서버는 의미 없는 해시만 받는다, 찍을 때는 비트코인 노드가 필요 없고 검증에는 로컬 Bitcoin Core 노드(가지치기 노드 가능)가 필요하다, 비트코인에 확정되기까지 몇 시간이 걸린다, `upgrade`가 비트코인 블록 헤더까지의 경로를 증명에 붙인다, 완료된 증명은 비트코인 51% 공격으로도 과거 것이 검증 불가능해지지 않는다), AWS S3 Object Lock 문서(컴플라이언스 모드에서는 루트 사용자를 포함해 누구도 보존 기간 동안 덮어쓰거나 지울 수 없고 보존 기간을 줄일 수 없다).

## 결정

1. **범위(소유자 승인).** 블록체인 네트워크는 운영하지 않는다. 감사 기록을 요약한 체크포인트의 해시 하나만 공개 타임스탬프(OpenTimestamps, 비트코인)에 고정하고, 체크포인트와 증명을 공개 위치에 게시한다. 기록 원문과 개인정보는 밖으로 나가지 않는다. 대상은 ops 감사 저장소의 `audit_chain` 기록 전부(운영 명령, 시스템 자동 조치, 승인 업무, 관리자 접속기록, 권한 변경, 법적 요청, 보안 사고, 가명정보 처리 기록 등)와 그날의 법정 접속기록 일 앵커 값이다. 기존 해시 체인·5분 앵커·1시간 검증은 그대로 둔다.
2. **잎과 머클 트리(추천 적용).** `audit_chain` 행마다 비공개 잎 솔트(`leaf_salt`, 32바이트 난수)를 같은 트랜잭션에서 저장한다. 잎 입력은 `"PEAKET-audit-leaf-v1" ‖ seq ‖ 기록 해시 ‖ leaf_salt`이고, 트리는 RFC 9162 §2.1의 머클 트리 해시(SHA-256, 잎 `0x00`, 안쪽 노드 `0x01`)다. 솔트가 있어서 포함 증명에 실린 옆 잎의 해시로 다른 기록의 내용을 짐작할 수 없다. 기록을 법정 보존 기간 뒤 파기하면 그 솔트도 함께 지운다. 그 뒤로는 공개된 루트로 어떤 기록이었는지 알 수 없다.
3. **체크포인트(추천 적용).** 체크포인트는 RFC 8785로 정규화한 JSON `{v: "PEAKET-checkpoint-v1", no, firstSeq, lastSeq, leafCount, merkleRoot, prevCheckpointHash, accessLogDayAnchor(일 체크포인트에만), closedEvents(온세일 윈도우가 끝난 회차 ID, 회차 마감 체크포인트에만), createdAt}`이고, 체크포인트 해시는 그 SHA-256이다. 직전 체크포인트 해시를 넣어 체크포인트끼리도 사슬로 잇는다. 만드는 때는 매일 00:10(KST) [가정, Phase 4 4.4.1에서 확정]과, 온세일 윈도우(T-10분~T+60분)가 끝난 회차가 있을 때 그 뒤 10분 [가정] 안이다. 같은 때 끝난 회차는 한 체크포인트로 묶는다. 각 체크포인트는 직전 체크포인트 뒤의 기록부터 그때까지의 기록을 덮는다.
4. **서명(추천 적용).** 체크포인트 해시에 피켓의 체크포인트 서명 키(KMS ECDSA P-256, 서명은 게시 잡만 `kms:Sign`)로 서명한다. 공개키는 공개 위치와 이 문서 묶음에 게시한다. 같은 번호에 서로 다른 체크포인트를 서명하면 그 두 서명이 피켓의 잘못을 증명하는 증거가 된다(사람마다 다른 장부를 보여 주는 '두 얼굴'을 드러냄).
5. **공개 타임스탬프(추천 적용).** 체크포인트 해시를 OpenTimestamps 공개 캘린더 서버 여럿에 보낸다. 처음 받는 증명은 '대기'이고, 게시 잡이 1시간마다 [가정] `upgrade`로 비트코인 블록 헤더까지의 경로를 붙여 '완료' 증명으로 바꿔 다시 게시한다. 24시간 [가정] 넘게 완료되지 않으면 SEV3다. 캘린더 서버가 모두 실패해도 체크포인트·서명·내부 앵커는 남기고 다음 실행에서 다시 보낸다.
6. **게시(추천 적용).** 체크포인트, 서명, 증명 파일(`.ots`)을 공개 위치 `https://www.peaket.example/transparency/`(공연 페이지 배포의 경로, 원본은 공개 게시 전용 S3 버킷, Object Lock 컴플라이언스 모드 7년)에 올리고, 같은 내용을 감사 앵커 버킷에도 남긴다. 체크포인트 파일은 바뀌지 않고, 목록 파일(`index.json`)만 짧게 캐시한다. 누구나 내려받아 보관할 수 있다. 회차의 파트너에게는 그 회차를 덮는 체크포인트 번호를 알린다.
7. **검증 도구(추천 적용).** 누구나 돌리는 공개 검증 도구 `audit-verify`를 문서 저장소 `tools/audit-verify/`(Python 표준 라이브러리, 공개)에 둔다. ① 체크포인트 사슬(직전 해시 연결, 번호 빈틈 없음), ② 서명(게시한 공개키), ③ 공개 타임스탬프(완료 증명은 공식 OpenTimestamps 클라이언트와 비트코인 노드나 공식 웹 검증기로 확인), ④ 검증 묶음이 있으면 기록 → 기록 해시 → 잎 → 포함 증명 → 루트를 확인한다.
8. **검증 묶음(추천 적용).** 운영자는 SCR-031에서 기록을 골라 검증 묶음(기록 정규화 값, 잎 솔트, 포함 증명, 체크포인트, 서명, `.ots`)을 내보낸다. 권한과 사유 기록은 원본 로그 내보내기와 같고, 내보내기도 감사 기록에 남는다. 묶음은 분쟁 당사자(그 회차의 파트너, 규제기관, 수사기관의 적법한 요청)에게만 주며 제공 절차는 POL-025와 CS 처리함을 따른다. 감사 기록은 사람을 이름이 아니라 계정 ID·가명 참조값으로 적으므로 묶음에도 그 값만 실린다.
9. **실패와 경보(추천 적용).** 체크포인트 만들기·서명·게시는 실패하면 다음 실행에서 다시 하고, 6시간 [가정] 넘게 밀리면 SEV3다. 내부 체인과 체크포인트 루트가 어긋나면 지금의 체인 검증 실패와 같이 SEV2와 보안 사고 기록(FR-063)이다. 게시 잡은 거래·온세일 경로와 떨어져 있고 실패해도 서비스에 영향이 없다. 잡은 ops-svc 이미지의 별도 명령으로 도는 CronJob `audit-anchor`이고, DB는 읽기와 `audit_checkpoint` 쓰기만, 외부 송신은 OpenTimestamps 캘린더 주소만 허용한다.
10. **함께 바뀌는 것(추천 적용).** 데이터에 `audit_chain.leaf_salt`와 `audit_checkpoint` 표를 더한다. 비밀·키 목록에 체크포인트 서명 키를, 개인정보 목록에 공개 체크포인트 행(개인정보 없음)을 더한다. SCR-031에 공개 앵커 상태와 검증 묶음 내보내기를 더한다. 시험 C-T38~C-T42, 용어 3개(공개 앵커, 감사 체크포인트, 포함 증명), WBS 4.4.1 +2일 [가정]을 더한다.

## 결과와 트레이드오프

- **얻는 것**: 파트너·규제기관·외부인이 피켓을 믿지 않고도 "그 시각에 그 기록 묶음이 있었고 그 뒤로 바뀌지 않았다"를 확인한다. 분쟁 때는 문제의 기록 하나와 포함 증명만 건네면 되고 장부 전체를 공개할 필요가 없다. 셔플 결과를 공개 비콘(drand)과 참가자 목록의 머클 루트로 검증하게 한 것(ADR-0012·0050)에 이어, 운영 개입도 '믿어 달라'가 아니라 '확인해 보라'가 된다.
- **비용**: OpenTimestamps 공개 캘린더 서버는 무료다. KMS 키 하나와 공개 게시 버킷의 작은 저장·전송 요금이 운영에서 든다(출시 전에는 로컬 kind와 LocalStack으로 보이고, 공개 타임스탬프는 실제로 찍을 수 있다). WBS 4.4.1 +2일 [가정].
- **남는 한계**(planning/01 §5.2, control-tower §15, 쉬운 설명서 10편):
  - 처음부터 기록하지 않거나 거짓으로 기록한 것은 막지 못한다. 명령 실행과 같은 트랜잭션에서 기록하고 CloudTrail·게이트웨이 기록과 교차 대조하는 것으로 줄인다.
  - 체크포인트 사이 구간(최대 하루, 온세일은 회차 마감 체크포인트로 끝난 뒤 10분)은 지금처럼 내부 앵커만 지킨다.
  - 비트코인에 확정되기까지 몇 시간이 걸리고, 그전까지는 '대기' 증명이다.
  - 공개 캘린더 서버는 기부로 운영된다. 오래 멈추면 RFC 3161 기관으로 대체를 검토한다.
  - 공개 위치를 피켓이 운영한다. 지우는 것은 Object Lock이 막지만 게시를 멈출 수는 있다. 파트너가 사본을 보관하고 번호 빈틈을 검증 도구가 드러내 줄인다.
  - '두 얼굴'은 서명이 증거를 남기지만, 들키려면 누군가 서로 받은 체크포인트를 비교해야 한다.
  - 외부인이 비트코인 단계까지 검증하려면 비트코인 노드나 공식 웹 검증기가 필요하다.

## 되돌릴 조건

- 캘린더 서버가 7일 [가정] 넘게 모두 응답하지 않으면 RFC 3161 기관 앵커를 더하는 새 ADR을 검토한다.
- 파트너나 규제기관이 회차별 운영 기록 요약의 공개를 요구하면, 공개 범위(명령 종류·시각·값)를 정하는 새 ADR로 회차 공정성 요약을 게시한다.
- 체크포인트 사이 구간이 분쟁에서 문제가 되면 체크포인트 주기를 줄인다(예: 1시간).
