# ADR-0005: 대기열은 서버가 옮기고, 입장 확정은 첫 예매 요청으로

- **상태**: 채택 (2026-10-08). 같은 날 입장 확정을 하는 곳을 edge-api에서 queue-svc로 바꾸고(ADR-0008), 자리 비우기를 구매 세션 종료 이벤트 방식으로 바꿈(ADR-0007의 저장소 공유 금지). ADR-0050(2026-10-13)이 대기표·참가 토큰의 '전자서명'을 HMAC 서명(대칭 키)으로 바로잡는다. ADR-0056(2026-10-13)이 입장 확정에 1인 1순번 재확인(사람별 입장 키, 다른 대기표면 409)을 더한다
- **관련**: 설계서 섹션 6 '입장 흐름', 섹션 8 '입장 확정', 10장 '세션 및 토큰 관리', ADR-0002(대기표 기준 앞 인원), ADR-0003(적응형 폴링), ADR-0008(게이트웨이)
- **관련 ID**: FR-008, FR-037, POL-008, POL-009, POL-010, NFR-001, SCR-008, SCR-010

## 맥락

전방 대기 인원을 대기표 발급 기준으로 정밀 산출하므로(ADR-0002), 브라우저 창을 닫아둔 사용자도 대기열에 계속 남아 있으며 자기 차례가 도래해도 즉시 진입하지 않을 수 있다. 따라서 admission-ctrl이 serving 번호를 전진시켰으나 해당 사용자가 즉각 진입하지 않을 때 유효 입장 자리를 어떻게 회수·처리할지 정의해야 한다.

- **서버는 개별 클라이언트의 화면 주시 여부를 알지 못한다.** 대기실 상태 조회는 CDN 에지에서 완충되는 정적 읽기 요청이며(ADR-0003), 접속 생존 여부를 실시간 확인하려면 클라이언트가 서버에 지속적인 쓰기 하트비트를 전송해야 한다.
- **백그라운드 탭 스로틀링으로 인해 차례 도래를 뒤늦게 인지하는 사용자가 발생한다.** Chrome 브라우저는 5분 이상 백그라운드에 숨겨져 있고 30초 이상 소리가 나지 않은 탭의 타이머 실행 주기를 1분당 1회로 강력히 스로틀링한다([Chrome 블로그](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)).
- **차례가 도래한 사용자는 어차피 서버에 확정 요청을 전송한다.** 예매 본 화면은 입장 토큰(Admission Token)이 인가되어야만 열리므로(설계서 5장 라우트 표), 대기표 토큰을 입장 토큰으로 교환하는 단일 요청이 필연적으로 발생한다.
- AWS Virtual Waiting Room 역시 동일한 메커니즘을 취한다. 대기 화면이 serving 번호를 주기적으로 폴링하다가 serving이 본인 번호에 도달하면 토큰 교환을 요청하여 본 사이트로 진입한다([GitHub 아키텍처 문서](https://github.com/aws-solutions/virtual-waiting-room-on-aws/blob/main/docs/software-architecture.md) 'Enter Waiting Room').

## 검토한 대안

| 대안 | 방식 | 문제 |
| --- | --- | --- |
| 1. 전진 번호 전량 점유 가정 | serving 번호를 올리면 번호마다 입장 자리를 차지하고 일정 시간 미접속 시 타임아웃 회수 | 미진입 사용자의 타임아웃 만료 시까지 입장 자리가 공회전하여 전체 입장 속도가 저하됨 |
| 2. 사전 준비 신호(Ready Heartbeat) | 입장 임박 사용자가 '생존 상태'를 서버에 주기적 쓰기 기록하고 신호 확인자만 입장 허용 | 대규모 쓰기 I/O 지속 발생. 백그라운드 탭 스로틀링 환경의 정상 사용자가 배제됨 |
| 3. 지속 연결 상태 추적 | WebSocket·SSE 연결이 유지된 사용자만 대기열 유효 잔류자로 인정 | 100만 지속 연결 관리 부담으로 ADR-0003과 충돌. 접속 기준 인원 산출로 B4(재접속 순번 보존)와 충돌 |
| 4. 만료 후 사후 보정 (AWS 옵션 모델) | 빈자리를 실제 토큰 발급 수 기반으로 역산하고 만료 순번 수만큼 사후 serving 번호 추가 전진 | 보정 주기가 만료 타임아웃(기본 900초)만큼 지연됨. AWS 템플릿에서도 기본 비활성화 옵션임 |
| **5. 첫 예매 요청 시 확정 + 입장 비율 동적 보정 (채택)** | 실제로 도달한 사용자만 첫 요청에서 원자적으로 입장 자리를 획득하고, 전진 번호 대비 실입장 비율로 차기 전진 폭을 동적 결정 | 비율 예측 오차 시 일시적 입장 자리 초과 또는 유휴 발생. '곧 입장' 버퍼링 및 초 단위 주기 보정으로 완충 |

대안 4의 기술적 근거는 AWS 공식 배포 템플릿 및 아키텍처 가이드에 명시되어 있다.

- `IncrSvcOnQueuePositionExpiry`: 만료 순번 수만큼 serving을 자동 전진시키는 파라미터이며, 기본값은 `false`이다([템플릿](https://github.com/aws-solutions/virtual-waiting-room-on-aws/blob/main/deployment/virtual-waiting-room-on-aws.json#L6129)).
- 해당 보정은 1분 주기로 기동되는 백그라운드 함수가 만료 순번을 합산하여 serving을 올리는 배치 방식이다(아키텍처 문서 'How does IncSCQP work?').
- 공식 예제 입장 전략(`max_size_inlet.py`)은 빈자리를 '최대 허용 인원 − 실제 발급 토큰 수'로 정량 산출한다([소스](https://github.com/aws-solutions/virtual-waiting-room-on-aws/blob/main/source/sample-inlet-strategies/max_size_inlet.py)).

## 결정

1. **대기 순번 제어는 서버가 주도하고 클라이언트는 조회만 수행한다.** admission-ctrl이 serving 번호를 전진시키며, 클라이언트는 CDN 대기 상태 파일을 폴링하여 본인 순번 도래 여부를 확인한다.
2. **입장 확정은 입장 토큰을 교환 발급받는 첫 HTTP 요청 시점에 단일 원자적으로 처리한다.** 해당 요청은 게이트웨이(gw-queue)를 거쳐 queue-svc로 인입되며, queue-svc는 단일 트랜잭션/스크립트 내에서 다음을 완결한다. 입장 확정은 대기열 인메모리 저장소의 상태를 변경하는 비즈니스 규칙이므로 게이트웨이 단에서는 수행하지 않는다(ADR-0008).
   - 대기표(사전 대기자는 참가 토큰) 전자서명 검증, '내 번호 ≤ serving 번호'(참가 토큰인 경우 Redis 셔플 결과 슬롯 조회, ADR-0012), 결번 및 만료 여부를 엄격히 대조한다.
   - 입장 토큰을 ECDSA 비대칭 키(ES256)로 서명하여 발급한다. 최종 만료는 세션 최대 체류 시각이며 첫 사용 유효 기한은 5분이다. 게이트웨이는 예매 경로 인입 시 공개키로 서명과 만료를 무상태 검증하고, 토큰을 최초 수신한 purchase-svc는 `jti`를 `SET NX`로 구매 세션에 귀속시켜 타 세션 재사용을 차단한다. 입장 토큰은 단일 구매 세션 전용이며 1회용 일회성 티켓이 아니다(ADR-0011).
   - 입장 자리 Sorted Set에 원소를 기록한다(점수 = 만료 시각. 초기에는 첫 사용 기한 5분, 구매 세션 진입 이벤트 수신 후에는 최대 체류 시각으로 갱신. 이벤트 유실 대비 백스톱).
   - 활성 입장 인원 원자 카운터를 증가시킨다.
3. **serving 번호 전진 폭은 `빈자리 ÷ 입장 비율` 공식으로 산출한다.**
   - 입장 비율은 '전진시킨 번호 수 대비 실제 인입된 입장 수'로 정의하며, 차례 도래 후 10초(초기 기본값)가 경과한 번호 풀을 표본으로 측정한다.
   - 세일 개시 초기에는 입장 비율을 100%로 보수적 가정한다.
   - 전체 동시 입장 목표치는 AIMD 알고리즘에 의해 유연하게 조절된다.
4. **빈자리는 200ms(초기 기본값) 주기로 재계산하여 해당 수치만큼만 단계적으로 전진시킨다.** 단일 순간에 과도한 트래픽이 한꺼번에 예매 진입점으로 쏟아지지 않도록 완충하기 위함이다. 클라이언트가 수신하는 대기 상태 파일은 1초 주기로 CDN 에지에 캐싱되므로 화면 표시 변화는 1초 단위이며, 사용자 유입은 개별 폴링 지터(±20%)에 의해 시간축으로 분산된다.
5. **입장 자리가 만석인 상태에서 첫 입장 교환 요청이 도달하면 HTTP 429와 함께 '곧 입장' 상태를 반환한다.** `Retry-After` 헤더를 동봉하며, 재시도 요청은 대기 번호 우선순위에 따라 빈자리 발생 즉시 선착순 배정된다. 시스템 동시 입장 절대 상한은 엄격히 준수된다.
6. **차례 도래 후 15분 이내에 복귀한 사용자는 빈자리 발생 시 정상 입장할 수 있다.** 15분이 경과하면 대기표 토큰은 최종 만료 처리된다. 15분은 AWS Virtual Waiting Room의 기본 순번 만료 기한과 동일하다(`QueuePositionExpiryPeriod`, [템플릿](https://github.com/aws-solutions/virtual-waiting-room-on-aws/blob/main/deployment/virtual-waiting-room-on-aws.json#L6114)).
7. **좌석 선택 단계의 입장 자리는 구매 세션이 종료되는 즉시 원자적으로 회수한다.**
   - purchase-svc가 구매 세션 생명주기를 전담 소유한다. 입장 토큰을 최초 사용하는 시점(통상 입장 직후 좌석 상태 스냅샷 요청)에 세션을 생성하며, 좌석 홀드 및 결제 시도가 인입될 때마다 유휴 만료 시한을 연장한다.
   - 세션은 구매 완료, 사용자 자진 퇴장, 유휴 제한 시간 초과 이벤트로 종결된다. 주문서 생성 완료 후 PG 결제창 체류 중에는 사용자 무조작 상태이더라도 세션을 강제 종료하지 않는다.
   - purchase-svc는 세션 개시 시 '구매 세션 시작', 종료 시 '구매 세션 종료' 이벤트를 발행한다(세션 상태 전이 Lua 스크립트에서 Redis Stream에 기록하고 릴레이가 트랜잭션 이벤트 토픽으로 전달). queue-svc는 시작 이벤트 수신 시 입장 자리 점수의 만료 시각을 첫 사용 기한(5분)에서 최대 체류 시각으로 확장하고, 종료 이벤트 수신 시 입장 자리를 즉시 삭제한다.
   - 입장 자리 점수(Score)는 메시지 유실에 대비한 안전장치(Safety Fallback)로만 동작한다. 입장 확정 시점에는 첫 사용 기한 5분(입장 토큰 수령 후 실제 예매 화면을 열지 않고 이탈한 유령 세션 정리용)이며, 최대 체류 시각은 PG 결제 유효 기한(30분)보다 여유 있게 설정한다.
   - 사용자 활동 감지는 purchase-svc의 책임이고 입장 자리 관리는 queue-svc(Redis)의 책임이므로, 저장소를 직접 공유하지 않고 도메인 이벤트를 매개로 느슨하게 결합한다(ADR-0007).

## 결과

- **실제 입장 확정을 수행하는 트래픽에 한해서만 쓰기 I/O가 발생한다.** 사용자 1인당 Redis 쓰기는 2~3회에 불과하며, 초당 평균 100건 미만으로 극히 안정적이다. 대기 중인 100만 사용자에게는 쓰기 부하가 일절 가해지지 않는다.
- **미진입 이탈자가 입장 자리를 독점하지 않으므로 타임아웃 회수 지연에 따른 병목이 없다.** ADR-0002에서 우려되었던 재검토 조건(입장 자리 회수 지연에 따른 전체 매진 소요 시간 연장)이 본 결정으로 완전히 해소된다.
- **예매를 마친 사용자의 입장 자리는 인덱스 만료를 기다리지 않고 이벤트 기반으로 즉각 반환된다.** 구매 세션 시작/종료 이벤트 발행량은 실제 입장자 1인당 각 1건(초당 약 28건) 수준이다.
- **백그라운드 스로틀링 등으로 뒤늦게 복귀한 정상 사용자도 15분 이내라면 순번을 보장받는다.** 재접속 순번 보존 원칙(B4)을 완벽히 충족한다.
- 트레이드오프: 입장 비율이 단기간에 급변할 경우(예: 다수의 지연 복귀자가 일시에 진입 시도) 순간적으로 입장 자리 정원이 가득 찰 수 있다. 이 경우 '곧 입장' 버퍼링을 통해 수 초 이내로 대기 제어되며, 동시 정원 상한은 절대 초과하지 않는다.
- 트레이드오프: 입장 비율을 과대 예측할 경우 일시적으로 입장 자리가 비어 있을 수 있으나, 다음 200ms 계산 주기에서 즉각 오차가 보정된다.
- 트레이드오프: 지금 차례인 사용자가 극히 짧은 순간 대기할 수 있다. 먼저 복귀한 선순위 사용자에게 빈자리가 우선 배정되기 때문이다.
- 실시간 관제 센터의 '판매 중' 대시보드에 실측 입장 비율 및 실시간 빈자리 지표를 표기하여 운영자가 알고리즘 보정 동작을 투명하게 모니터링한다.

## 재검토 조건

- K1 부하 시험에서 '곧 입장' 429 응답 비율이나 빈자리 공회전 비율이 시스템 허용 임계치를 초과할 때. 구체적 기준은 v0/v1 실측 벤치마크 후 확정한다.
- 복귀 지연자가 비정상적으로 집중되어 15분 유예 정책이 전체 매진 완료 시간을 유의미하게 지연시킬 때
- 브라우저 제조사의 백그라운드 탭 전원 관리 정책이 개정되어 타이머 스로틀링 특성이 근본적으로 변화할 때
