# ADR-0180: 실패 목록 셋(경합·외부 호출·자원 한도)을 정본 표로 두고, 기능을 더할 때 데이터 구조보다 먼저 줄을 쓴다(추천 적용, 2026-11-03)

- **상태**: 채택(2026-11-03, 소유자 지시 "빈틈 채워줘". 바깥 강의와 설계를 항목별로 대조해 찾은 빈틈을 채운다. 표의 자리·칸·줄 늘리기 규칙과 [가정] 값은 추천 적용). 2026-11-03(진행 파일 반영 때 대조): 결정 7의 한 문장 목표는 docs/planning/01-overview.md §3.2에 넣을 때 검토로 세 목표(① 팔 수 있는 좌석은 막힘 없이 판다 ② 사지 못하는 사람은 덜 기다리게 하고 빨리·정확하게 매진을 알린다 ③ 돈만 빠지고 좌석이 없는 손님을 남기지 않는다)로 풀었으니 그 셋으로 읽는다
- **관련**: ADR-0036(외부 한도 추정), ADR-0070(시간 초과 기본값), ADR-0109(발송 원장), ADR-0116(PgBouncer 배치), ADR-0119(얇은 OIDC 클라이언트), ADR-0127(결제사 읽기 시간 초과 60초), ADR-0168, ADR-0178, [docs/architecture.md](../architecture.md) §5·§8.7·§9.1, [docs/data.md](../data.md) §1.1·§5, [docs/api/guidelines.md](../api/guidelines.md) §8, [docs/verification.md](../verification.md) §4, [docs/features/identity.md](../features/identity.md) §10, [docs/features/notify.md](../features/notify.md) §10, [docs/planning/01-overview.md](../planning/01-overview.md) §3.2
- **관련 ID**: NFR-002, NFR-006, NFR-007, wbs 0.5.5(외부 한도 확정), wbs 2.11.2(풀 크기), wbs 2.12.1(성능 장부), V-T43

## 맥락

- 오픈 순간에만 드러나는 문제는 세 갈래다. ① 같은 데이터를 같은 순간에 고치는 요청(경합) ② 남의 서버가 늦거나 답하지 않는 것(외부 호출) ③ 숫자로 정해진 한도에 닿는 것(자원 한도)이다. 로컬에서 한 번씩 눌러 보는 개발로는 셋 다 보이지 않는다. 요청은 하나씩 오지 않고, 네트워크는 늘 답하지 않으며, 노트북에서는 한도에 닿지 않기 때문이다.
- PEAKET에는 비슷한 표가 이미 있다. 경합은 docs/data.md §5 '동시성 제어가 필요한 지점', 외부 호출은 docs/api/guidelines.md §8 외부 연동 표, 시간 초과는 docs/architecture.md §5 '시간 초과 기본값', 외부 한도는 docs/verification.md §4 '외부 한도 대조표'다.
- 2026-11-03 공연 예매 플랫폼의 백엔드 설계를 다룬 바깥 강의(한상훈 '백엔드 마스터클래스 맛보기 2강 공연 예매 플랫폼', 2026-11-02 게시)와 설계를 항목별로 대조했다. 강의는 근거가 아니라 대조의 계기다. 비어 있던 것은 다음이다.
  - 내부 자원(DB 연결, 파드 메모리, Redis 메모리, 샤드 처리량)의 한도를 한곳에서 설계 피크와 대 보는 표가 없다. 값은 docs/infra-handover.md, ADR-0116, ADR-0070, docs/features/seat-hold.md에 흩어져 있다. 일부는 아직 정하지 않았다(PgBouncer 풀 크기, 게이트웨이 동시 처리 상한).
  - 외부 연동 표에는 '어떻게 실패하는가(실패 모양)'와 '실패의 무게' 칸이 없다. 소셜 로그인 공급자와 본인확인 기관은 외부 한도 대조표와 시간 초과 표에 행이 없다.
  - 소셜 로그인의 인가 코드 교환은 웹 앱 서버가 한다(ADR-0119). 그래서 로비 개방 때 평균 초당 약 1,700건(첫 1분 몰림이면 약 3,500건 [추정], docs/architecture.md §9.1)의 토큰 요청이 AZ마다 하나인 NAT 고정 IP 셋에서 [가정] 공급자로 나간다. 공급자가 앱이나 보내는 IP 단위로 요청을 막을 위험을 다루지 않았다.
  - 알림이 실패해도 예매를 되돌리지 않는다는 것은 구조로만 보장된다(발송 원장이 예매 확정 사건을 받아 뒤에서 보낸다, ADR-0109). 규칙 문장은 없다.
  - 새 기능이 경합·외부 호출·자원 한도 표에 줄을 더한다는 규칙도, 그 줄을 데이터 구조보다 먼저 쓴다는 순서도 없다. 비슷한 규칙은 위협 모델 표(docs/architecture.md §8.2), Redis 키 표(docs/data.md §3), 운영 확인 표(docs/architecture.md §8.4)에만 있다. 실제로 좌석·결제 규칙 모델 검사(R-230·R-231)는 이미 정한 설계의 틈(OPEN[15]~[17])을 나중에 찾았다.
  - 공연 상세 한 번에 브라우저가 몇 번 부르는지 곱한 계산이 없고, NFR-007의 30만 RPS가 어떤 계산에서 나왔는지도 적혀 있지 않다.
  - 오픈 순간의 목표(좌석 수만큼 성공, 나머지는 빨리·정확하게 매진 안내, 돈만 빠진 손님 0명)는 지표 여럿에 흩어져 있고 한 문장으로 정한 곳이 없다.

## 결정

1. **세 목록의 정본 자리(추천 적용)**: 경합은 docs/data.md §5다. 외부 호출은 docs/api/guidelines.md §8 표와 새 §8.1 '외부 호출의 실패 모양과 무게'다. 자원 한도는 docs/verification.md §4(외부)와 새 §4.1 '내부 자원 한도 대조표'다. 시간 초과 값은 docs/architecture.md §5 표가 정본이다. 목록마다 새 파일을 만들지 않는다. 같은 내용이 두 곳에 생기면 어긋나기 때문이다(ADR-0168, ADR-0178).
2. **줄을 먼저 쓴다(추천 적용)**: 새 기능, 새 외부 연동, 새 저장소·연결 풀·큐·키 묶음을 더하는 단계는 표·키·마이그레이션을 정하기 전에 세 표에 그 줄을 쓴다(docs/architecture.md §8.7). 값을 모르면 [가정]과 정할 곳을 적는다. 실패 시 동작을 아직 정하지 못했으면 칸을 비우지 않고 '미정:'과 남은 질문을 적는다. 이미 있는 기능의 빈칸은 그 기능을 다음에 고치는 단계에서 채운다.
3. **내부 자원 한도 대조표(추천 적용)**: DB 연결, DB 쓰기, 앱 연결 풀, 파드 동시 처리와 메모리, 게이트웨이, Redis 메모리, Redis 샤드 처리량, 결제사 동시 승인 호출, 로그인 처리, NAT 연결을 행으로 둔다. 판정 규칙은 외부 표와 같다. 설계 피크가 한도의 80% [가정]를 넘으면 문제 대장에 올린다. 파드 메모리는 '파드당 동시 처리 상한 × 요청 하나의 메모리 ≤ V8 힙 상한의 50% [가정]'으로 본다.
4. **외부 호출의 실패 모양과 무게(추천 적용)**: 외부 시스템마다 실패 모양(무응답·지연·성공 뒤 응답 유실·거절·한도 초과), 무게(멈추면 무엇이 멈추는가. docs/infra-handover.md §3.4의 가용성 등급), 실패 시 동작이 적힌 정본 자리를 한 표로 둔다. 동작은 옮겨 적지 않는다(결정 1). 무게가 다르면 동작도 다르다. 결제 실패는 좌석을 묶은 채 결과를 확정하고, 알림 실패는 예매를 건드리지 않는다.
5. **소셜 로그인 공급자의 한도와 나가는 IP(추천 적용)**:
   - 외부 한도 대조표에 공급자 셋(카카오·네이버·구글)과 본인확인 기관 행을 더한다. 앱 단위 초당 한도의 숫자는 세 공급자 모두 공개 문서에 없다(카카오는 사용자 1명 기준 토큰 한도와 앱 월간 쿼터, 구글은 앱마다 정해지는 새 사용자 인가 한도만 적혀 있다, 2026-11-03 확인). 그래서 '판정할 수 없다'로 적고, 대형 온세일 전에 공급자에게 한도를 확인하는 일을 wbs 0.5.5의 외부 한도 확정에 넣는다.
   - 시간 초과 표에 토큰 교환·사용자 정보 조회 행을 더한다. 연결 2초·읽기 5초 [가정]이다. 시간 초과 뒤에는 같은 인가 코드로 다시 보내지 않는다. 인가 코드는 한 번만 쓸 수 있기 때문이다(RFC 6749 §4.1.2). 사용자에게는 로그인을 처음부터 다시 하게 한다.
   - 웹 앱 서버 파드마다 공급자별 동시 호출 상한(벌크헤드: 한 의존성이 자원을 다 쓰지 못하게 나눈 칸막이)을 둔다. 값은 '그 공급자의 초당 로그인 피크 × 호출 한 건의 평소 p99 × 여유 2배 ÷ 파드 수'다. 첫 1분 몰림 약 3,500건 [추정]이 한 공급자에 다 오면 3,500 × 0.5초 × 2 ÷ 15 ≈ 233건 [가정, wbs 2.12.1에서 확정]이다. 넘으면 기다리지 않고 429 `server-busy`와 `Retry-After`로 답한다.
   - 공급자가 429·403 같은 한도·차단 응답을 몰아 주면, 그 공급자의 새 로그인만 잠시 막는다(지금의 공급자 장애 동작과 같은 갈래). 이미 로그인한 사람의 예매는 이어진다. 제공자 오류 비율 경보(SEV2)에 이 두 응답도 센다(docs/observability.md §3·§5, docs/features/identity.md §10).
   - 로그인을 로비 전으로 흩는 지금의 장치(세션 유휴 만료 14일, 오픈 알림의 공연 상세 미리 열기, 로비 버튼 퍼뜨리기)는 그대로 둔다.
6. **알림 실패는 예매를 되돌리지 않는다(추천 적용)**: docs/features/notify.md §10에 규칙으로 적는다. 예매 완료 알림의 허용 지연은 5분 [가정]이다(낱건 발송 밀림 경보와 같은 값). 팬은 확정 화면과 내 티켓에서 결과를 바로 본다.
7. **오픈 순간의 목표를 한 문장으로(추천 적용)**: docs/planning/01-overview.md §3.2에 "좌석 수만큼은 확실히 성공시키고, 나머지 사람은 덜 기다리게 하며 빨리·정확하게 매진을 알리고, 돈만 빠진 손님은 0명이다"를 두고, 지금의 지표(오버셀 0건, NFR-006의 결제-발권 어긋남 0건, 매진 소요 22분, 매진 안내 최대 약 28초 설계 식)를 잇는다. 새 NFR은 만들지 않는다.
8. **페이지당 호출 수(추천 적용)**: docs/architecture.md §9.1에 공연 상세 한 번 열 때의 호출 목록과 셈 식을 둔다. NFR-007의 30만 RPS 근거 계산은 wbs 0.5.5에서 채운다.
9. **PgBouncer를 쓰지 못할 때의 연결 관리 대안(소유자 요청 2026-11-03 "만약 pgBouncer를 안쓰는경우 커넥션 풀과 DB 연결 한도에 대한 부분을 어떻게 해결할수있을지에 대한 대안도 설계에 적어두세요", 순서와 내용은 추천 적용)**: 기본안은 그대로 PgBouncer다(ADR-0028 결정 4, ADR-0116 결정 7). 쓰지 못하게 되면 ① 앱 연결 풀만 쓰고 '최대 파드 수 × 풀 크기 ≤ DB 연결 상한의 80% [가정] − 예비'로 예산을 고정한다(KEDA 최대 복제 수와 역할 `CONNECTION LIMIT`을 함께 건다) ② 예산이 모자라거나 장애 조치 뒤 다시 붙는 몰림이 문제면 Amazon RDS Proxy로 간다. 이때 PostgreSQL에서 연결을 한 사용자에게 묶는 쿼리(`SET`, prepared statement, `nextval`, 세션 advisory 잠금 등)를 먼저 점검한다 ③ PgBouncer 자체의 한계나 결함이 원인이면 다른 풀러(PgCat·Odyssey)를 같은 자리에 둔다 ④ DB 한도 키우기는 보조 수단이다. 순서의 이유는 PEAKET의 DB 쓰기가 앱 서버 대수가 아니라 입장 속도로 묶여 있어, 부품을 더하지 않는 ①로도 예산 안에 드는 것이 계산으로 보이기 때문이다. 정본은 docs/data.md §1.1이다.
10. **작은 빈칸(추천 적용)**: ① 경합 표에 '남은 좌석 수 숫자 한 칸' 행을 더한다. 그런 숫자를 두지 않고, 판매 대상 좌석 수에서 비트맵의 켜진 비트 수를 빼서 센다(docs/data.md §5) ② 홀드 7분을 고칠 때 볼 값(홀드에서 결제 접수까지 걸린 시간의 분포, 홀드 만료율)을 적는다(docs/features/seat-hold.md §13) ③ wbs 0.5.5 범위에 소셜 로그인 공급자·본인확인 기관의 한도 확인과 NFR-007 근거 계산을 더한다(추정 일수는 그대로).

## 검토한 대안

| 대안 | 기각 사유 |
| --- | --- |
| 목록마다 새 파일(예: `docs/failure-lists/`)을 만든다 | 같은 내용이 두 곳에 생겨 어긋난다. ADR-0178이 사본을 없앤 이유와 같다. 표가 이미 정본에 있다 |
| 외부 연동 표(§8)에 칸 둘을 더한다 | 행이 길어 읽기 어렵고, 한 행을 고칠 때 다른 작업과 부딪힌다. 짧은 요약 표를 옆에 두고 자세한 동작은 원래 표를 가리킨다 |
| 소셜 로그인 토큰 교환을 identity-svc로 옮겨 나가는 경로를 하나로 모은다 | ADR-0119를 되돌리는 방향 바꿈이다. 이번에는 한도를 확인하고 상한을 두는 데서 멈춘다 |
| 공급자 호출용 나가는 IP를 따로 늘린다 | 공급자가 IP 단위로 막는지 문서로 확인되지 않았다. NAT 연결 한도(같은 목적지마다 55,000)는 연결을 다시 쓰면 넉넉하다. 측정 뒤 다시 본다 |

## 결과와 트레이드오프

- 새 기능마다 표 셋에 줄을 쓰는 일이 는다. 대신 오픈 때 드러날 문제를 구현 전에 적는다.
- 내부 한도 대조표의 값은 대부분 [가정]이거나 미정이다. 표는 먼저 '무엇을 아직 모르는지'를 보이는 데 쓴다. 값은 wbs 2.11.2(풀 크기), 2.12.1(성능 장부), V-T43(게이트웨이)에서 채운다.
- 소셜 로그인 공급자의 앱 단위 초당 한도는 숫자가 공개 문서에 없어 판정할 수 없다. 공급자에게 확인하기 전까지 위험으로 남는다.
- PgBouncer 대안의 계산 예는 최대 복제 수와 풀 크기가 모두 [가정]이다. 대안으로 실제로 바꾸는 일은 이 ADR이 정하지 않는다. 바꿀 때 따로 ADR을 남긴다.
