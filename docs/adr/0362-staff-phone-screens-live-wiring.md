# ADR-0362: 현장 스태프 휴대폰 화면을 실제 서버에 이으며 계약의 빈칸을 채운다(2026-11-23)

- **상태**: 채택(2026-11-23, 추천 적용, BUILD_ORDER 기능 F-05-7 계획 `docs/review/plans/F-05-7.md`). 방향을 바꾸는 결정은 없다. 정본에 이미 있는 화면 규칙(d5 §5.17·§5.26·§5.27·§5.35, docs/planning/04-ia-flows-screens.md §3 SCR-050)과 서버 코드가 어긋난 곳을 정본 쪽으로 맞추고, 화면을 그리는 데 빠진 값과 상태를 정한다.
- **관련**: [ADR-0051](0051-gate-process-end-to-end.md), [ADR-0062](0062-open-items-delegated-decisions.md)(파트너 제공 동의 보유 기간), [ADR-0065](0065-web-frontend-security-after-asvs-v3.md) 결정 10(URL 조각의 비밀), [ADR-0089](0089-leftover-values-senior-engineer-decisions.md)(고지 문안의 판), [ADR-0209](0209-fan-device-sessions.md)(로그인한 기기), [ADR-0293](0293-fan-reauth-token-bound-to-receiving-operation.md)(재인증 토큰의 받는 쪽 작업), [ADR-0353](0353-staff-invitation-event-owner-lookup-via-core-internal-http.md), docs/features/identity.md §6.1·§8·§10.1·§12
- **관련 ID**: FR-046, POL-031, I-T21 ⑫, I-T47, I-T62, I-T89, I-T90, I-T91, I-T92, I-T93

## 맥락

- 현장 스태프(공연 당일 입장을 검표하는 사람)의 휴대폰 화면 넷, 곧 초대 수락(SCR-050)·스캐너 승인(SCR-051)·내 현장 배정(SCR-061)·계정 설정의 로그인한 기기 줄(SCR-017)은 지금 목업(정해 둔 가짜 값으로만 그린 화면)이다. 서버 쪽 경로(초대 조회·수락·거절, 내 배정, 기기 승인)는 GAT-210·GAT-220에서 끝났다.
- 화면을 실제 서버에 이으려고 코드를 대 보니 다음이 비어 있거나 정본과 달랐다(2026-11-23, `origin/develop` `450ab6cd7`).
  1. 초대 조회 응답(`StaffInvitationView`)에 회차 ID가 없다. 그래서 화면이 회차 공개 요약(`GET /v1/events/{eventId}`, 인증 없이 읽는 공연명·회차 시작·판매자 상호)을 읽지 못한다. 계약에는 `partnerName`·`eventTitle`·`eventStartsAt` 칸이 있지만 identity-svc는 회차·판매자 데이터를 갖지 않아([ADR-0007](0007-service-boundaries-by-load-availability-runtime.md)) 채우지 않는다.
  2. identity-svc의 두 동의 고지 문안(`staff-2026-11-13` 판)이 정본(04-ia §3 SCR-050 ③④)과 항목이 다르다. 정본은 수집 항목이 '계정 ID·닉네임·역할·스캔 기록', 파트너 제공 항목이 '닉네임·역할·수락 여부·스캔·예외 통과 건수'인데, 서버 문안은 '이메일·이름·역할·근무 회차'다.
  3. 검증된 이메일이 없는 계정(네이버만 연결)과 다른 이메일 계정이 같은 403 `staff-invitation-email-mismatch`라, 화면이 d5 §5.26의 '검증 이메일 없음' 상태를 가르지 못한다.
  4. d5 §5.26과 04-ia는 '[수락하지 않기]는 거절 API가 없어 닫기만 한다'고 적었지만, 거절 API(`POST /v1/staff-invitation-rejections`)가 생겼고 GAT-240이 초대 거절 화면을 맡는다.
  5. 계약에는 내 스캐너 세션 조회·끝내기(`GET /v1/identity/scanner-sessions`, `DELETE …/{sessionId}`)가 있지만 identity-svc에 받는 곳이 없다. 스캐너 세션 표(`scanner_session`)에 기기 이름 칸이 없어 계약의 `deviceName`과 내 배정의 `activeScannerDeviceName`은 늘 null이다.
  6. d5에 없는 응답이 있다: 스캐너 승인의 409(같은 기기에 다른 승인이 먼저 처리됨), 대리 승인 거절 문구([자리 표시]), 초대 수락 화면의 로그인 전 상태, 회차 공개 요약을 못 읽었을 때의 초대 수락 화면.

## 결정

1. **초대 조회는 회차 ID를 싣는다.** `StaffInvitationView`에 `eventId`(늘 싣는다)를 더한다. 화면은 그 ID로 회차 공개 요약을 읽어 판매자 상호·공연명·회차 시작을 보인다(스캐너 승인 화면과 같은 방식, open-items 78번). `partnerName`·`eventTitle`·`eventStartsAt`은 칸을 지우지 않고(응답 칸을 빼면 계약이 깨진다) 설명에 'identity-svc는 채우지 않는다'를 적는다.
2. **동의 고지 문안은 정본 항목과 같게 고치고 판을 올린다.** 새 판은 `staff-2026-11-23`이다. 두 문안은 줄마다 `이름: 내용` 꼴(줄바꿈 `\n`)이고, 줄의 이름과 내용은 04-ia §3 SCR-050 ③④의 다섯·넷 항목(목적·항목·보유 기간·거부권과 불이익, 제공은 받는 자를 앞에 더함)을 그대로 쓴다. 받는 자 줄은 정본처럼 '이 회차의 파트너'이고, 화면은 같은 화면 맨 위 초대 카드에 그 파트너의 상호를 함께 보인다. 화면은 받은 문안을 줄 그대로 글자로만 보이고(HTML로 해석하지 않는다) 화면 쪽 고정 문구로 바꾸지 않는다. 그래야 화면에 보인 글과 저장되는 판(`consent_version`)이 같다. 옛 판으로 보낸 수락은 지금 규칙대로 422 `consent-version-outdated`다(이미 수락한 배정의 판은 그대로 둔다).
3. **받는 자 상호를 못 읽으면 수락을 막는다.** 초대 수락 화면이 회차 공개 요약을 읽지 못하면(404·410·연결 실패) '파트너 이름을 읽지 못함' 상태로 [수락]을 끄고 [다시 불러오기]를 보인다. 개인정보 보호법 §17②는 제공받는 자를 알린 뒤 동의를 받게 하므로, 상호 없이 제공 동의를 받지 않는다. 스캐너 승인 화면은 지금 정본대로 이름 없이도 승인할 수 있다(동의를 받는 화면이 아니다).
4. **검증 이메일 없음은 따로 알린다.** 계정에 검증된 이메일이 없으면(네이버만 연결, 또는 제공자가 검증 표시를 주지 않음) 수락은 403 `staff-invitation-email-unverified`이고, 검증 이메일이 초대 이메일과 다르면 지금처럼 403 `staff-invitation-email-mismatch`다. 초대 쪽 이메일이 이미 파기된 행은 `staff-invitation-email-mismatch`로 둔다(그런 초대는 조회가 먼저 410이다).
5. **[수락하지 않기]는 거절 API를 부른다.** 버튼을 누르면 화면 안에서 한 번 확인('이 초대를 거절할까요? 거절하면 이 링크로 다시 수락할 수 없습니다', [거절]·[취소])한 뒤 `POST /v1/staff-invitation-rejections`를 보낸다. 204면 '거절함'("초대를 거절했습니다"), 410이면 '만료'다. [취소]는 아무 요청도 보내지 않는다.
6. **내 스캐너 세션 조회·끝내기를 identity-svc에 만든다.**
   - 조회는 그 계정의 스캐너 세션 가운데 끝나지 않았고(`terminated_at` 없음) 역할 유효 끝이 아직 오지 않은 것(`expires_at > now`)만 준다. 계정당 하나뿐이라 많아야 한 줄이다.
   - 끝내기는 다른 기기 로그아웃(`DELETE /v1/identity/sessions/{sessionId}`)과 같은 차례다: 재인증 토큰(5분, 한 번, 받는 쪽 작업 `SCANNER_SESSION_END`)을 먼저 확인해 틀리면 403 `reauth-required`, 이 계정의 살아 있는 세션이 아니면 404 `session-not-found`(토큰을 쓰지 않는다), 맞으면 `terminated_at`을 적고 같은 트랜잭션에 세션 종료 사건 `control.sessions-terminated`(사유 `LOGOUT`, 키 계정 ID)를 남긴 뒤 토큰을 쓴 것으로 적는다. 새 사유 값은 만들지 않는다(사유 열거를 늘리면 소비자 계약이 깨진다). 사유 `LOGOUT` 설명에 '스태프 본인이 휴대폰에서 끝낸 스캐너 세션'을 더한다.
   - 마이그레이션 `0038_scanner_session_device_name.sql`로 `scanner_session.device_name`(text, 비어도 됨)을 더하고, 기기 승인이 세션을 만들 때 기기 승인 요청에 든 기기 원장 이름을 복사한다. 옛 행은 채우지 않는다(null, 화면은 '현장 스캐너'로 보인다). 기기 이름은 '동문-03' 같은 장비 이름이라 개인정보가 아니고, 세션 행과 같이 보존한다. 내 배정 목록의 `activeScannerDeviceName`은 그 배정의 살아 있는 세션의 이 값이다.
7. **계정 설정의 스캐너 세션 줄은 기기 목록과 같은 재인증 길을 쓴다.** 탭 저장소 표시 `peaket.devices.reauth`의 범위 값에 `scanner`를 더하고(`device`·`others`·`scanner`), 재인증은 웹 `purpose` `scanner-session-end`로 시작한다. 새 저장소 키를 만들지 않는다. 스캐너 세션 목록 읽기가 실패해도 기기 목록은 그대로 그리고, 스캐너 줄 자리에만 실패 안내를 둔다.
8. **d5에 없던 상태 문구**(추천 적용): 스캐너 승인 409는 '다른 승인이 먼저 처리됨'("이 스캐너는 방금 다른 승인으로 처리되었습니다. 스캐너에서 새 QR을 띄워 주세요"), 대리 승인 403은 "대리 승인은 현장 책임자만 할 수 있습니다", 초대 수락의 로그인 전은 '로그인 필요'("초대를 받으려면 먼저 이 휴대폰에서 피켓에 로그인하세요" [로그인], 돌아와 같은 탭에서 잇는다)다. 문구의 정본은 d5 해당 절이다.

## 검토한 대안

- **identity-svc가 초대 조회에 상호·공연명을 채운다**: core-svc 내부 호출이 하나 더 는다. 스캐너 승인 화면이 이미 회차 공개 요약을 읽으므로 같은 방식을 고르지 않을 까닭이 없다.
- **동의 문안을 화면에 고정하고 서버 판만 맞춘다**: 화면과 서버가 같은 글을 따로 들고 있어 한쪽만 고치면 보인 글과 기록한 판이 어긋난다(ADR-0089가 막으려던 일). 서버 원문을 그대로 보이는 쪽을 골랐다.
- **스캐너 세션 끝내기에 새 사유 `SCANNER_LOGOUT`**: 사건 계약의 열거 값을 늘려야 하고 소비자(종료 세션 목록)는 사유로 가르지 않는다. `LOGOUT`의 설명만 넓혔다.
- **스캐너 세션 목록에서 기기 이름을 그때그때 ticket-svc에 묻는다**: 계정 설정을 열 때마다 gRPC 호출이 생기고 ticket-svc가 답하지 않으면 줄이 비는 경로가 생긴다. 승인 때 한 번 받은 이름을 복사한다.

## 결과와 트레이드오프

- **좋은 점**: 네 화면이 목업 값 없이 서버 응답만으로 그려진다. 동의 기록의 판과 보인 글이 같아진다. 스캐너 세션을 휴대폰에서 끝낼 수 있어 ASVS 7.5.2·10.4.9의 '스태프 본인의 SCR-017 종료'가 실제가 된다.
- **남는 한계**: 옛 스캐너 세션의 기기 이름은 null이다(세션은 길어야 역할 유효 시간만 산다). 회차 공개 요약이 판매 중지 중(410)이면 그 회차의 초대를 그동안 수락할 수 없다. 동의 판이 바뀌어 배포 직전에 조회한 화면의 수락은 한 번 422가 나고 화면이 다시 조회한다.

## 되돌릴 조건

- 회차 공개 요약을 읽지 못해 수락이 막히는 일이 운영에서 잦으면(판매 중지 회차의 초대 등) identity-svc가 core 판매 설정의 판매자 ID와 함께 상호를 받는 길을 새 ADR로 정한다.

## 확인

- 시험: I-T21 ⑫, I-T47, I-T62, I-T89~I-T93(docs/features/identity.md §12). 화면에서 실제 identity-svc까지 잇는 연결 시험은 계획 파일 '실제 서버 연결' 절이다.
