# ADR-0154: 미룬 문서 가운데 지금 쓸 것을 가르고, 카프카 재인증은 선택 보정에서 확인하며, 네트워크 큐는 튜닝하지 않고 측정 무효 규칙만 두고, 사라진 용어 풀이를 되살린다(소유자 결정, 2026-10-30)

- **상태**: 채택 (2026-10-30. 소유자가 review/open-items.md의 남은 결정 묶음(17~20·24·29·30·42번)을 정했다. 42·30·17~20·29번은 추천을 "추천대로"라고 정했다. 24번은 "네트워크 큐는 실제로 필요할까요?"라고 물었고, 정본을 다시 보고 낸 새 추천을 "추천대로 가겠습니다"라고 정했다. 네 방향은 소유자 결정이다. 측정 규칙의 카운터와 문구, 보정의 규모와 시간, 지금 쓸 문서와 나중에 쓸 문서를 가른 구체 목록은 추천 적용이다.)
- **관련**: ADR-0057(검증 전략, 선택 보정), ADR-0084·0090(C4 3단계 그림), ADR-0089('남는 한계'의 굿즈 주문 본문), ADR-0097·0098(원문은 판단 근거가 아님), ADR-0144 결정 7(엣지에서 끝난 실패를 SLO에 더함), ADR-0151(품질 목표 순서), [docs/verification.md](../verification.md) §3.5·§6, [docs/streaming.md](../streaming.md) ST-T14, [docs/features/README.md](../features/README.md), [00-summary.md](../../00-summary.md) §9, [docs/architecture.md](../architecture.md) §3.3, [planning/03-policies-glossary.md](../../planning/03-policies-glossary.md) §5

## 맥락

- **24번(네트워크 큐 튜닝)**: 2026-10-14 소유자 질문에 대화로 낸 제안이다. 진입 성공률(NFR-001)을 게이트웨이(Envoy)에서 세므로, 게이트웨이가 연결을 받기 전에 커널이 버린 연결은 성공에도 실패에도 잡히지 않는다는 사각지대를 들고, 노드 커널 설정 표·부하 분산기 대상 방식·실험 다섯 개를 제안했다. 2026-10-30에 정본을 다시 보니 사정이 달라져 있었다.
  - 사용자 연결은 CloudFront(사용자 가까이에서 대신 응답하는 전송망)에서 끝나고, 원본에는 CloudFront가 맺어 다시 쓰는 연결만 온다.
  - CloudFront가 원본에 닿지 못해 낸 502·504는 진입 SLO 오류에 더한다(ADR-0144 결정 7, docs/observability.md '엣지에서 끝난 실패').
  - 부하 발생기 k6는 사용자 쪽에서 재므로 연결 실패와 연결에 걸린 시간이 결과에 나온다.
  - Redis는 관리형(ElastiCache)이라 서버 커널을 만질 수 없고, 운영 경로에 Nginx가 없다.
  - 남는 빈틈은 하나다. 커널이 버린 연결이 재시도로 성공하면 실패가 아니라 1초 넘는 지연으로만 보인다(TCP가 첫 연결 요청을 다시 보내기까지 1초를 기다린다).
- **42번(카프카 재인증)**: 서비스는 MSK(AWS가 운영하는 Kafka)에 전용 역할을 고정 세션 이름으로 맡아 만든 토큰으로 붙는다(기술 검토 높음-26). 자격이 바뀔 때 재인증이 이어지는지는 실제 MSK와 EKS Pod Identity에서만 확인된다(ST-T14 ②). 2026-10-30 AWS 가격 목록(서울)은 EKS 클러스터 시간당 0.10달러, MSK kafka.t3.small 브로커 시간당 0.0569달러, kafka.m7g.large 0.2508달러다. MSK 할당량 문서는 IAM 새 연결 속도를 t3 브로커 초당 4개, M5·M7g 초당 100개로 적는다. EKS 문서와 API 참조에는 Pod Identity 자격의 유효 시간이 적혀 있지 않다(2026-10-30 확인).
- **17~20·29번(구현 직전으로 미룬 문서)**: 기능 설계 11묶음, 예정 보안 문서 다섯, 나머지 서비스의 C4 3단계 그림을 '구현 직전'에 쓰기로 해 두었다. 개발 양은 판단 기준이 아니므로(소유자 2026-10-27), 언제 쓸지는 그 문서가 무엇에 기대고 무엇이 그 문서에 기대는지로 가른다. 18번(웹 푸시 구독·찜 엔터티)은 이미 docs/data.md에 있었다(`wish`, `push_subscription`).
- **30번(사라진 용어 풀이)**: 2026-10-26 소유자가 직접 고친 문서 24개에서 괄호 설명 128곳이 빠졌다. 2026-10-30에 맞춰 보니 같은 글자로 다시 들어간 곳은 2곳이다. 그 사이 원문을 지웠고 판단 근거로 쓰지 않기로 해서(ADR-0097·0098), 머리 '원문 출처' 줄의 원문 장·절 설명은 되살릴 이유가 없어졌다.

## 결정

1. **네트워크 큐는 튜닝하지 않고, 측정 무효 규칙과 다시 볼 조건만 둔다(소유자 결정, 24번)**: 측정 정직성 규칙 8번을 더한다. 점마다 측정 전후로 게이트웨이 파드와 진입 서버 파드의 네트워크 공간에서 커널 카운터 `ListenOverflows`·`ListenDrops`(연결 대기열이 넘쳐 버린 연결 수)를 읽어 장부에 남기고, 늘었으면 그 측정은 무효다(추천 적용). 커널 큐 값과 네트워크 카드 설정은 기본값을 쓴다. 이 카운터가 PC 측정에서 늘거나, 운영에서 오픈 순간 CloudFront 원본 연결 실패(502)나 원본 지연이 튀면 그때 노드 커널 설정과 큐 튜닝 실험을 한다. 정본은 docs/verification.md §3.5다.
2. **카프카 재인증은 선택 클라우드 보정의 세 번째 항목으로 확인한다(소유자 결정, 42번)**: 서울 리전에 EKS 클러스터 1개(노드 c7g.xlarge 1대)와 MSK kafka.t3.small 2대를 9시간 [가정] 띄워, Pod Identity 자격과 MSK 토큰이 각각 한 번 이상 바뀌는 동안 재인증 실패·연결 끊김이 0건인지 본다(ST-T14 ②). 관측 전용 Kafka에 붙는 Go 도구(수집기·Tempo)의 역할 맡기 방식도 같은 실행에서 본다. 가격표로 약 3.5달러이고, 다른 두 보정(약 4달러, 무료)과 합쳐도 지출 상한 5만 원 안이다. 보정을 하지 않으면 운영 계정을 준비할 때 확인한다. 성능 장부 프로파일은 `cloud-msk-iam`이다. 정본은 docs/verification.md §6이다(규모·시간·결과 표시는 추천 적용).
3. **미룬 문서는 기댐 관계로 갈라, 일부를 지금 쓴다(소유자 결정, 17~20·29번)**: 기준은 '다른 정본이 이미 기대고 있는 계약·데이터, 상세 설계가 이미 있는 기능에 딸린 보안 추적 표와 그림, 100만 명 시나리오에 직접 닿는 기능은 지금 쓴다. 나머지 기능 설계는 그 기능을 만들기 직전에 쓴다'이다. 지금 쓰는 것(추천 적용):
   - 17번 굿즈 주문 요청 본문(택배 판매자 제공 동의 칸 포함, docs/api/openapi.yaml `POST /v1/shop/orders`)
   - 알림과 찜·오픈 알림 구독(docs/features/notify.md, 보안 추적 표 docs/security/asvs/notify.md를 먼저 쓴다). 인기 공연의 대기실 오픈 안내를 많은 구독자에게 한꺼번에 보내는 발송량·속도 설계가 없었다
   - 봇 탐지 상세(docs/features/bot-defense.md). 품질 목표 4위인 봇 방어의 중심이다(ADR-0151)
   - 예정 보안 문서 다섯: 인증 통제(docs/security/auth-controls.md), 권한 표(docs/security/authz-matrix.md), 내부 관리계획(docs/security/internal-management-plan.md), 좌석·관제 보안 추적 표(docs/security/asvs/seat-hold.md, asvs/control-tower.md)
   - C4 3단계 그림(서비스 안쪽을 모듈 단위로 확대한 그림): ops-svc, identity-svc, ticket-svc, trust-svc(docs/architecture.md §3.3)
   - 그 기능을 만들기 직전에 쓰는 것: 굿즈의 나머지, 공연 탐색의 나머지, 파트너 콘솔, 관람 후기, 고객 문의, 양도 화면 세부, 계정 설정, 런북 41종, core-svc의 C4 3단계 그림. 주요 규칙은 이미 목록·정책·ADR에 정해져 있고, 남은 것은 화면 칸과 문구처럼 실제 화면 부품과 함께 정해야 맞는 것이다. 런북은 실제 명령과 대시보드 이름이 생겨야 쓸 수 있다.
   - 18번은 이미 된 것으로 닫는다.
   - 새 문서들이 새로 정한 설계 판단은 따로 결정 기록으로 남긴다: 알림 ADR-0155, 봇 탐지 ADR-0156, 인증 통제·권한 표 ADR-0157, 내부 관리계획 ADR-0158, 좌석·관제 보안 추적 표에서 막은 빈틈 ADR-0159, 굿즈 주문 본문과 C4 구성 요소 ADR-0160.
4. **사라진 용어 풀이를 되살린다(소유자 결정, 30번)**: 처음 나온 용어의 풀이(planning/03 §5)는 그 용어가 본문에 처음 나오는 곳에 지금 풀이가 없을 때만 넣는다. design/d3-screens.md와 docs/devops.md 머리 줄의 [보완] 표시 설명 문장 둘을 되살린다. 날짜·ADR 번호·제품 이름 같은 그 밖의 괄호는 지금 그 자리에 없고 정본 기준으로 아직 맞을 때만 되살린다. 머리 '원문 출처' 줄의 원문 장·절 설명은 되살리지 않는다.

## 검토한 대안

- **24번: 원래 제안 전체(노드 커널 설정 표, 부하 분산기 대상 방식, 실험 다섯 개, 드롭 경보)**: 문제가 보인 적 없는 곳을 미리 튜닝하면 근거 없는 설정이 남는다. 이 프로젝트는 먼저 재고 문제가 보이면 고친다(v0→v1). 기각.
- **24번: 아무것도 넣지 않고 닫기**: 재시도로 성공한 연결의 1초 넘는 지연이 측정에서 가려진다. 카운터 두 개를 읽는 일은 측정마다 몇 초다. 기각.
- **42번: 운영 계정을 준비할 때까지 미루기**: 실패하면 모든 Kafka 연결이 자격이 바뀔 때마다 끊기는 위험(기술 검토 높음-26)을, 약 3.5달러로 미리 확인할 수 있다. 기각.
- **42번: 운영과 같은 kafka.m7g.large 2대**: 약 3.5달러가 더 든다. AWS 문서에서 브로커 크기에 따라 다른 것은 연결 수·속도 한도뿐이고, 작업자 몇 개라 t3의 한도(초당 4개)에 닿지 않는다. 기각.
- **42번: MSK Serverless**: 클러스터 시간당 0.92달러로 더 비싸고, 운영이 쓰는 프로비저닝 클러스터와 다른 제품이다. 기각.
- **17~20·29번: 전부 지금 쓰기**: 화면 칸·문구·런북 명령처럼 실제 부품과 명령이 생겨야 맞는 세부를 미리 정하면 구현 때 다시 쓰게 되고, 그동안 문서가 실제와 어긋난다. 기각.
- **17~20·29번: 지금처럼 전부 구현 직전에 쓰기**: 알림 발송량과 봇 탐지는 100만 명 시나리오에 닿고, 상세 설계가 이미 있는 좌석·관제의 보안 추적 표는 지금 판정해야 설계 빈틈을 지금 찾는다. 기각.
- **30번: 원문 출처 줄의 원문 장·절 설명까지 되살리기**: 원문은 판단 근거가 아니다(ADR-0097·0098). 기각.
- **30번: 되살리지 않기**: 처음 나온 용어를 풀어 쓰는 규칙(planning/03 §5)을 어긴 곳이 남는다. 기각.

## 결과와 트레이드오프

- 네트워크 큐는 기본값으로 둔다. 측정에서 커널이 버린 연결이 생기면 그 측정을 버리므로 가려진 지연으로 통과하지 않는다. 운영에서 노드별 이 카운터는 따로 모으지 않고, 엣지 지표(원본 연결 실패·원본 지연)로 본다.
- 카프카 재인증은 보정을 하면 실측(클라우드)이 되고, 하지 않으면 원문 근거의 설계로 남는다. 작은 브로커의 짧은 실행이라 재연결이 몰릴 때의 동작과 드문 실패는 재지 않는다.
- 지금 쓰는 문서가 늘어 '예정' 기능 요구사항과 예정 문서가 준다. 나중에 쓰는 기능의 정본은 계속 docs/features/README.md '구현 직전 작성 대상' 표다.

## 되돌릴 조건

- 결정 1의 카운터가 늘거나 오픈 순간 원본 연결 실패·지연이 튀면 노드 커널 설정과 큐 튜닝 실험을 설계한다.
- 결정 2의 실행에서 재인증이 끊기면 그 워크로드만 IRSA로 바꾸고(docs/devops.md §9.4), Go 도구가 역할을 맡지 못하면 관측 전용 클러스터의 인증 방식을 새 ADR로 다시 본다.
- 나중에 쓰기로 한 기능이 100만 명 시나리오에 닿는 것으로 드러나면(예: 인기 굿즈 오픈이 공연 오픈만큼 몰리면) 그 기능 설계를 앞당긴다.
