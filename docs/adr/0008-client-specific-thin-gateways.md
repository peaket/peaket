# ADR-0008: 게이트웨이는 클라이언트 유형별로 나누고 얇게 유지한다

- **상태**: 채택 (2026-10-08). ADR-0050(2026-10-13)이 도착 시각 '암호화 쿠키'를 HMAC 서명 쿠키로 바로잡고, '페이로드 복호화'를 구매 세션 요청 인증(소지 증명)으로 바꾸며, 게이트웨이별로 신뢰하는 토큰 서명 키를 나눈다. 프리워밍 시작은 2026-10-13 전수 점검에서 T-40분 [가정]으로 앞당겼다(T-30분 점검이 완료를 판정한다, docs/infra.md §5, POL-030) 2026-10-14: 기대평은 없앴고 후기는 관람 후기만 둔다(ADR-0063 결정 3). 본문의 '기대평'은 '관람 후기'로 읽는다. 2026-10-15(ADR-0065 결정 5): 쓰기 요청의 CSRF 확인은 Origin 허용 목록 대조, Origin이 없으면 Sec-Fetch-Site 확인, 둘 다 없으면 거절로 읽는다.
- **관련**: 설계서 섹션 6 'API 게이트웨이', 섹션 9(SLO 측정 지점, 지연 예산), ADR-0005(입장 확정 위치), ADR-0006(본인확인), ADR-0007, ADR-0009, `docs/security/secrets-and-keys.md`
- **관련 ID**: FR-005~FR-011, FR-028, FR-035, POL-019, NFR-001, NFR-003, NFR-005, NFR-011, NFR-016

## 맥락

- **초기 설계의 edge-api 계층은 공통 인프라 정책과 복잡한 비즈니스 로직을 혼용했다.** JWT 토큰 검증, 레이트 리밋과 같은 게이트웨이성 인프라 정책 외에도 입장 확정, 멱등키 보관 등 핵심 비즈니스 로직을 처리했으며, Redis 저장소에 직접 I/O를 수행했다. Envoy Gateway는 단순 명칭 수준으로만 언급되었다.
- **클라이언트 유형이 4종으로 분화되며 요구사항이 상이하다.**
  - 소비자 웹: 대기열 진입 핫패스는 초당 20만 건(TPS), 예매 진입은 5,000명 동시 세션 규모
  - 파트너 콘솔: B2B 멀티 테넌트 관리
  - 관제 콘솔: 대규모 시스템 장애 발생 시에도 반드시 생존해야 하는 제어 평면
  - 현장 게이트 스캐너: 오프라인 현장 통신 및 전용 단말기 mTLS 인증
- **게이트웨이 계층의 핵심 아키텍처 원칙**
  - 수행 역할: 인증·인가, 공통 보안 정책, 트래픽 라우팅, 헤더 변환, 분산 관측성 수집
  - 배제 대상: 데이터베이스 직접 접근, 분산 트랜잭션 처리, 비즈니스 룰 실행, 복잡한 서비스 간 응답 조합
  - 고가용성 운영: 단일 장애점(SPOF)을 제거하기 위한 다중 가용 영역(AZ) 이중화, 홉 수 추가에 따른 프록시 지연시간 최소화

업계 레퍼런스 원문 근거는 다음과 같다.

- **Sam Newman, [Backends For Frontends](https://samnewman.io/patterns/architectural/bff/)**: 단일 범용 API 대신 클라이언트 사용자 경험별로 독립 백엔드를 분리하는 'one experience, one BFF' 패턴을 권장한다.
- **[Envoy Gateway 배포 모드](https://gateway.envoyproxy.io/docs/tasks/operations/deployment-mode/)**: Gateway 리소스별로 전용 Envoy 데이터 평면 파드 풀을 물리 분리할 수 있다.
- **[Envoy Gateway JWT](https://gateway.envoyproxy.io/docs/tasks/security/jwt-authentication/)·[API 문서](https://gateway.envoyproxy.io/docs/api/extension_types/)**: HTTP 헤더, 쿠키, 쿼리스트링에서 토큰을 추출하여 원격 JWKS 엔드포인트의 공개키로 무상태 서명을 검증한다. 내장 CSRF 필터도 지원한다.
- **[Envoy Gateway 레이트 리밋](https://gateway.envoyproxy.io/docs/tasks/traffic/local-rate-limit/)**: Envoy 프록시 로컬 메모리 기반 카운터와 외부 분산 레이트 리밋 서비스 연동 모델을 제공한다.
- **[AWS API Gateway 한도](https://docs.aws.amazon.com/apigateway/latest/developerguide/limits.html)**: 계정 및 리전당 기본 처리 한도가 초당 1만 건으로 제한된다(별도 증액 신청 필요).

## 검토한 대안

| 대안 | 문제 |
| --- | --- |
| 1. edge-api 모놀리스 유지 | 게이트웨이 안티패턴(비즈니스 룰 및 DB 직접 접근) 발생. 단일 배포 묶음으로 대기열 진입 폭주가 예매 트랜잭션으로 전파됨 |
| 2. 단일 통합 게이트웨이 공유 | 진입 트래픽 폭주나 설정 오류가 관제, 파트너, 현장 스캐너 시스템 전체로 연쇄 전파됨 |
| 3. AWS API Gateway 관리형 서비스 | 기본 한도가 초당 1만 건에 불과하여 초당 20만 건 진입 처리를 위해 대규모 증액이 필수적이며, 호출 건수 비례 과금으로 운영 비용이 폭증함 |
| **4. 클라이언트 전용 경량 Envoy Gateway 분리 배포 (채택)** | 5개의 독립 게이트웨이 파드 풀을 선언형으로 배포 및 모니터링해야 함 |

## 결정

1. **외부 인입 네트워크 경로는 CloudFront(+AWS WAF) → NLB → Envoy Gateway → 백엔드 서비스 파이프라인으로 구성한다.** Envoy 프록시가 L7 HTTP/TLS 처리를 완결하므로 ALB(Application Load Balancer)를 이중으로 두지 않는다. 불필요한 프록시 홉 지연을 제거하기 위함이다. 실시간 WebSocket 세션 역시 게이트웨이가 직접 처리한다. 현장 스캐너 경로는 CloudFront를 거치지 않고 NLB(L4 TCP 통과) → gw-scanner로 직결하여 게이트웨이가 TLS를 종단하고 기기 클라이언트 인증서(mTLS)를 직접 검증한다. CloudFront 에지 함수(CloudFront Functions)는 매진 안내 응답 및 진입 감내 모드(Degraded Mode)의 도착 시각 암호화 쿠키 발급에만 국한하여 활용한다.
2. **게이트웨이는 클라이언트 역할에 따라 5개 전용 인스턴스로 격리 배포한다.**

   | 게이트웨이 | 대상 클라이언트 및 경로 | 인증 방식 | 분리 배포 근거 |
   | --- | --- | --- | --- |
   | gw-queue | 소비자 웹: 로비 입장(참가 토큰), 사전 검증 토큰 발급, 대기열 진입, 입장 확정, 대기 상태 파일·셔플 결과 파일(CDN 캐시 미스 시 origin) | 팬 액세스 토큰(쿠키) + 구매 권한. 대기 상태/셔플 결과 정적 파일 경로는 무인증 공개 및 쿠키 포워딩 차단으로 CDN 캐시 적중률 보존 | 초당 20만 건 핫패스. 독립 스케일아웃 및 폭주의 예매 전파 차단 |
   | gw-fan | 소비자 웹: 예매 구매(좌석 스냅샷·홀드·주문서·결제 접수), 좌석 델타(WebSocket), 티켓·월렛·양도, 굿즈, 기대평, 본인확인, 토큰 갱신, Next.js 내부 프록시 | 팬 액세스 토큰(쿠키). 예매 및 좌석 델타 경로는 입장 토큰 병행 요구. 토큰 갱신 경로는 리프레시 토큰 쿠키 전용 | 구매 경로는 동시 5,000명 한정이며 티켓·조회는 평시 부하. 진입 폭주(gw-queue)와 물리적 격리가 핵심 |
   | gw-partner | 파트너 콘솔, 외부 PG 웹훅 수신(토스페이먼츠 웹훅 → payment-svc) | B2B 관리 계정(MFA 필수). 웹훅 경로는 서명 확인 후 payment-svc가 PG 단건 조회 API로 교차 검증 | 멀티 테넌트 격리 및 보수적 레이트 리밋 |
   | gw-ops | 관제 센터 콘솔(GraphQL, Socket.IO, 운영자 인증 → identity-svc) | 운영자 계정(MFA 필수) + 허용 IP/사내 VPN 화이트리스트. 로그인 엔드포인트도 IP/VPN 격리 | 비상 장애 시에도 생존해야 하는 제어 평면 |
   | gw-scanner | 현장 검표 스캐너 동기화(CloudFront 바이패스) | 전용 기기 인증서(mTLS). 게이트웨이 TLS 종단 시 하드웨어 기기 인증서 직접 상호 검증 | 공연 당일 현장 통신 가용성 보장 |

3. **게이트웨이의 핵심 책임 범위를 명확히 규정한다.**

   | 책임 영역 | 세부 구현 내용 |
   | --- | --- |
   | 인증 (AuthN) | 요청 헤더 또는 httpOnly 쿠키의 JWT 서명을 로컬 캐시된 공개키(JWKS)로 검증한다. 저장소 조회가 없는 순수 무상태 검증이며, 조기 무효화된 세션의 토큰은 세션 종료 이벤트를 수신한 백엔드 서비스 계층에서 차단한다(ADR-0011). |
   | 인가 (AuthZ) | HTTP 경로 기반의 거시적 역할/스코프만 판정한다. 예: 대기열 및 예매 경로는 구매 권한(`ticket:buy`) 클레임을 검증한다. 주문 소유권 대조 등 세부 도메인 인가는 서비스 계층이 담당한다. |
   | 공통 정책 | 분산/로컬 레이트 리밋, CORS 제어, CSRF(Origin/Referer 대조), 요청 페이로드 크기 상한, 공통 보안 응답 헤더 주입을 수행한다. |
   | 라우팅 | 호스트명 및 URL 경로 기반 분기, 카나리(Canary) 가중치 라우팅을 지원한다. |
   | 변환 | 외부 내부 헤더 정제, 검증된 토큰의 사용자 ID·세션 ID·권한·사람 식별자(`pid`)를 내부 헤더로 변환 주입한다(서비스는 중복 검증 없이 해당 헤더와 로컬 종료 세션 캐시만 조회. 서비스 메시 mTLS로 헤더 위변조 차단). |
   | 관측성 | 경로별 4대 골든 시그널 수집, 프록시 자체 지연시간(전체 − 업스트림) 계측, 접근 로그 기록, OTel 분산 트레이스 ID를 주입한다. |
   | 1차 장애 차단 | 경로별 타임아웃, 동시 연결/대기 큐 상한 강제, 비정상 파드 서킷 제외, Fail-fast 조기 거절을 수행한다(ADR-0009). |

4. **게이트웨이가 절대 수행하지 않는 4대 금지 영역을 확립한다.**
   - 데이터베이스 및 공유 캐시에 직접 접근하지 않는다.
   - 분산 트랜잭션을 조율하지 않는다.
   - 도메인 비즈니스 규칙을 실행하지 않는다.
   - 복수 서비스의 응답을 조합(Aggregation)하지 않는다.

   해당 책임은 전담 계층으로 엄격히 위임한다.
   - 전역 레이트 리밋의 저장소 처리는 전용 레이트 리밋 서비스에 위임하고, 게이트웨이는 gRPC 호출로 판정만 요청한다.
   - 화면 렌더링을 위한 복합 데이터 조합은 BFF 계층(Next.js 서버, 파트너 tRPC 서버, ops-svc GraphQL)이 전담한다.
   - 서비스 간 백엔드 내부 통신(예: Auth.js → identity 세션 생성 및 자격 증명 대조)은 외부 게이트웨이를 거치지 않고 서비스 메시 mTLS 내부 경로로 직접 통신한다(ADR-0011).

5. **기존 edge-api의 비즈니스 로직을 각 전문 서비스로 전면 이관한다.**

   | 기능 | 이관 대상 서비스 | 이관 사유 |
   | --- | --- | --- |
   | 입장 확정(입장 토큰 발급, 입장 자리 인덱싱) | queue-svc | 대기열 도메인 규칙이며 대기열 저장소 쓰기 I/O 수반 |
   | 입장 토큰 재사용 차단(jti 소비) | purchase-svc | 구매 세션 원자적 바인딩 상태 저장 필요 |
   | 멱등키(Idempotency Key) 검증·저장 | purchase-svc(홀드/주문), payment-svc | 핵심 비즈니스 DB 트랜잭션과 동일 원자성 보장 필요 |
   | 판매 킬스위치 즉시 적용 | purchase-svc | 온세일 판매 라이프사이클 통제 규칙 |
   | 암호화 페이로드 복호화 | purchase-svc(공통 라이브러리) | 봇 방어 애플리케이션 계층 검증 및 대칭키 회전 |
   | 토큰 무상태 검증, 레이트 리밋 | Envoy Gateway | L7 인프라 프록시 고유 공통 정책 |

6. **게이트웨이는 암호화 대칭 비밀 키를 보관하지 않는다.**
   - 팬 액세스 토큰(identity 발급)과 입장 토큰(queue-svc 발급)은 비대칭 키(ES256) 알고리즘으로 전자 서명된다.
   - 게이트웨이는 공개키(JWKS) 세트를 메모리에 캐싱하여 무상태 서명 검증만 수행한다.
   - 대기표는 queue-svc가 독점 발급 및 검증하므로 대칭 HMAC 방식을 유지한다.
7. **본인확인 완료 자격은 JWT 클레임으로 무상태 전달한다.**
   - identity-svc는 본인확인을 마친 계정에 한해 액세스 토큰에 구매 권한(`ticket:buy`) 스코프를 탑재한다.
   - 게이트웨이는 고부하 진입 경로에서 해당 권한 클레임의 존재 여부만 로컬 검증한다.
   - 본인확인 인정 여부 및 법적 유효성 판정 책임은 identity-svc가 전담한다(ADR-0006).
8. **초고부하 핫패스 트래픽은 Next.js 서버를 우회한다.**
   - 대기열 진입, 좌석 홀드, 결제 승인 요청은 브라우저 → 게이트웨이 → 백엔드 서비스로 직결된다.
   - 액세스 토큰은 보안 httpOnly 쿠키로 전송되며, 게이트웨이가 쿠키에서 직접 추출하여 검증한다. 본 쿠키는 Next.js Auth.js 세션 쿠키 및 리프레시 토큰 쿠키와 명확히 분리된다(ADR-0011).
   - Next.js Route Handler는 SSR 페이지 렌더링 및 비(非)핫패스 백엔드 연동에만 국한된다.
9. **게이트웨이 인프라 다중 가용 영역 이중화 구성을 강제한다.**
   - 각 게이트웨이 파드는 최소 3개 이상의 복제본을 3개 AZ에 균등 분산 배치한다.
   - 상단 NLB는 교차 영역 부하 분산(Cross-Zone Load Balancing)을 필수로 활성화한다.
     - NLB는 각 AZ마다 노드를 프로비저닝하지만([AWS 공식 문서](https://docs.aws.amazon.com/elasticloadbalancing/latest/userguide/how-elastic-load-balancing-works.html)), 기본 모드에서는 동일 AZ 내부 타깃으로만 트래픽을 라우팅한다([NLB 문서](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/network-load-balancers.html)).
     - 따라서 특정 AZ의 게이트웨이 파드가 일시 고갈될 경우 해당 AZ로 인입된 요청이 드롭되는 결함이 발생한다.
     - 교차 영역 활성화 시 AZ 간 데이터 전송 비용이 소폭 발생하나, 오픈 시점의 진입 가용성(99.9%)을 최우선 보장하며 관련 비용은 K9에서 정량 검증한다.
   - PDB(Pod Disruption Budget)를 엄격히 설정하고 요청량 기반 HPA를 구성하며, 대형 티케팅 30분 전(T-30분, docs/infra.md §5) 사전 스케일아웃(Pre-warming)을 수행한다.
   - 게이트웨이 라우팅 설정 변경 역시 ArgoCD GitOps 카나리 배포 파이프라인을 거친다.
10. **프록시 지연시간 예산을 엄격히 통제한다.**
    - 게이트웨이 순수 지연시간(전체 왕복 지연 − 백엔드 업스트림 지연)을 독립 메트릭으로 수집하며, p99 3ms 이내의 지연 예산을 할당한다.
    - 지연 최소화 조치: 공개키 인메모리 캐싱, 핫패스 로컬 레이트 리밋 적용, 백엔드 커넥션 풀 재사용, 요청 본문 불필요 버퍼링 배제.
    - 좌석 홀드 지연 예산 중 과거 'edge-api 8ms' 할당분은 '게이트웨이 3ms + purchase-svc 페이로드 복호화 5ms'로 정밀 재분배한다.
    - 네트워크 홉 수는 기존 아키텍처(edge-api → inventory-svc)와 동일하게 유지된다.
11. **거버넌스 분리**: Gateway 인프라 리소스는 플랫폼 팀이 중앙 통제하고, 세부 라우팅 규칙(HTTPRoute)은 각 서비스 팀이 자체 리포지토리에서 선언적으로 관리한다.

## Well-Architected 기둥 분석

| 기둥 | 아키텍처 영향 |
| --- | --- |
| 안정성 | 클라이언트별 전용 게이트웨이 분리로 장애 반경을 최소화한다. 3개 AZ 이중화와 NLB 교차 영역 분산을 통해 특정 AZ 파드 장애 시에도 요청을 안전하게 처리한다. |
| 보안 | 게이트웨이에 대칭 비밀 키를 일절 적재하지 않는다(비대칭 공개키 검증). 관제 제어 평면은 별도 게이트웨이와 네트워크 IP/VPN 화이트리스트로 이중 격리한다. |
| 성능 효율성 | 네트워크 홉 수 증가 없이 프록시 지연시간 p99 3ms 예산을 엄격히 사수한다. |
| 운영 우수성 | 5대 게이트웨이의 운영 복잡도는 Kubernetes Gateway API 기반의 선언형 선언과 자동화 대시보드로 극복한다. |
| 비용 최적화 | 호출 건당 과금형 관리형 서비스 대신 자체 운영 파드 풀을 채택하여 티케팅 피크 시 비용 폭증을 방어한다. NLB 교차 영역 통신 비용은 K9 지표로 통제한다. |
| 지속 가능성 | 티케팅 피크 전후로만 파드를 탄력적으로 스케일링하여 상시 인프라 탄소 발자국을 감축한다. |

## 결과

- 외부 공개 경로의 공통 보안·인프라 정책이 표준 게이트웨이 계층으로 일원화되며, 비즈니스 서비스는 도메인 로직에만 전념할 수 있다.
- SLO 측정 기준점이 과거 edge-api 단일 지점에서 각 클라이언트 전용 게이트웨이 인입부로 정밀하게 재배치된다(설계서 섹션 9).
- 트레이드오프: Envoy Gateway 선언형 리소스(Gateway, HTTPRoute, SecurityPolicy)에 대한 엔지니어링 관리 역량이 요구된다.
- 트레이드오프: 5대 게이트웨이별 모니터링 대시보드와 알림 룰이 증가하며, 이는 서비스 템플릿 제너레이터를 통해 일괄 자동화한다.

## 재검토 조건

- 게이트웨이 순수 처리 지연시간이 p99 3ms 예산을 지속 초과할 때
- BFF 계층 대신 게이트웨이 단에서 복합 응답을 조합해야 하는 요구가 구조적으로 누적될 때
- 5대 게이트웨이의 운영 오버헤드가 실질 격리 이점을 상회할 때: 트래픽 특성이 유사한 파트너와 스캐너 게이트웨이의 통합 배포를 검토한다.
