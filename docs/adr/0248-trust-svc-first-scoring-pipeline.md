# ADR-0248: trust-svc 첫 위험 판정 구현의 경계(비공개 규칙 파일, 판정을 못 받을 때의 처리)

- **상태**: 채택(2026-11-09, 추천 적용). BUILD_ORDER BOT-050, wbs 3.2.1 ①.
- **관련**: POL-006, POL-026, FR-020, FR-039, NFR-022, ADR-0009, ADR-0039, ADR-0071, ADR-0147, ADR-0156, ADR-0171, ADR-0223, ADR-0231, [docs/features/bot-defense.md](../features/bot-defense.md) §4·§6·§11, [docs/features/identity.md](../features/identity.md) §7, [docs/security/secrets-and-keys.md](../security/secrets-and-keys.md).

## 맥락

정본은 판정 흐름과 축소 운영(trust-svc나 그 의존성이 멈출 때 모두 통과시키지 않고 이어 가는 방식)을 정했다. 코드로 옮기려면 정본에 없는 세부를 정해야 한다.

- 비공개 기준값과 가중치를 어떤 꼴로 주입하는가. 공개 저장소에는 값이 없어야 한다.
- ASN 분류표(인터넷 사업자·데이터센터마다 받은 네트워크 번호를 호스팅·프록시·그 밖으로 나눈 표)를 어디서 읽는가. S3 클라이언트 패키지가 저장소에 없고, 이 단계에서 새 패키지를 받지 않는다.
- 로그인 판정(`LOGIN`)을 세션 트랜잭션 안에서 부르는가, 밖에서 부르는가.
- trust-svc가 `degraded`(의존성 일부가 멈춘 채 답함)로 `ALLOW`를 주면 queue-svc는 어떻게 하는가.
- 판정을 못 받을 때 파드 메모리 한도(요청 수를 파드 안에서만 세는 상한)를 넘은 요청은 뭐라고 답하는가.
- 최초 방문 쿠키·세션 나이를 맡는 `AgeScore`의 사유 범주는 무엇인가. 정본의 사유 범주 표에 행이 없다.

## 결정

1. **규칙은 파일 하나로 주입한다.** trust-svc는 `PEAKET_TRUST_RULES_FILE`이 가리키는 JSON을 읽는다(External Secrets가 넣는 파일). 판 번호(`version`), 강도 셋(`RELAXED`·`BASE`·`STRICT`) × 정렬 방식 셋(`ON`·`OFF`·`NONE`)의 프로필(`threshold`·`weights`), 점수기 매개변수(`params`)다. 값은 저장소에 없고, 시험은 합성 값만 쓴다(B-T3). 처음부터 읽지 못한 파드는 준비 상태가 되지 않고, 다시 읽기는 5분 [가정]마다이며 실패하면 마지막 판을 쓴다.
2. **ASN 분류표는 파일로 읽는다.** `PEAKET_ASN_TABLE_FILE`(JSON: `version`, `hosting`, `proxy`)을 1시간 [가정]마다 다시 읽고, 읽지 못하면 마지막 판을 쓴다. 한 번도 읽지 못했으면 모두 '그 밖'이다. 공용 코드는 `packages/platform`의 `ReloadingAsnTable`이고 trust-svc와 queue-svc가 함께 쓴다. S3에서 받기(정본 §3.1)는 클라이언트 패키지가 저장소에 없어 뒤로 미룬다(소유자 허락 대상). 분류표를 만드는 작업과 그 원천 자료(wbs 3.2.1의 [가정])도 뒤 단계다.
3. **로그인 판정은 세션을 커밋한 뒤 응답과 떼어 뒤에서 부른다.** 계정·세션 행을 잠근 채 다른 서비스를 기다리지 않고, 정본의 '판정으로 로그인을 늦추지 않는다'대로 응답도 판정을 기다리지 않는다. 세션은 `UNKNOWN`으로 만들고, 판정을 받으면 `login_verdict`를 고친다. 파드가 그 사이 멈추거나 쓰기가 실패하면 `UNKNOWN`에 머문다(안전 쪽). 다시 보내기(같은 멱등 키)는 판정을 다시 받지 않는다.
4. **`degraded`인 `ALLOW`는 통과 표시를 하지 않는다.** queue-svc의 `RiskVerdict`에 `HELD`를 더한다. 토큰에 `hd`(사람 확인 검증 보류)를 서명하는 점은 `UNAVAILABLE`과 같고, 파드 메모리 한도는 걸지 않는다(trust-svc가 답했으므로 §11.1 ①층이다). 모르는 판정이나 사유 없는 `CHALLENGE`는 통과로 보지 않고 `UNAVAILABLE`로 처리한다. identity-svc는 `degraded`인 `ALLOW`를 `UNKNOWN`으로 적는다. trust-svc는 로그인 판정에서 근거 있는 점수기가 하나도 없으면 `degraded`를 참으로 둔다(계약에 칸을 더하지 않고 이미 있는 `degraded`로 알린다). 지난 30일 이력(사람 확인을 통과한 계정, 추가 검증 기록)이 없는 처음 보는 기기의 `DeviceTrust`는 위험 0이어도 근거로 세지 않는다. 훔친 비밀번호로 새 기기에서 로그인한 경우까지 `ALLOW`로 적히면 양도·환급 계좌 입력의 재확인을 건너뛰기 때문이다. 기기 라벨 키가 없거나 ASN 0에 기기 식별값이 없는 로그인도 같다. 로비·사전 검증에는 이 규칙을 쓰지 않는다. identity-svc의 판정 쓰기는 `login_verdict`가 `UNKNOWN`일 때만 바꾼다.
5. **파드 메모리 한도를 넘으면 429 `queue-request-limited`(Retry-After 10초)다.** `UNAVAILABLE`일 때만 센다. 기기·pid마다 5회/10초 [가정], ASN이 호스팅·프록시면 IP도 같은 한도다. 문구는 축소 운영 중임을 드러내지 않는다. 키 수는 파드마다 20만 개 [가정]까지다.
6. **`AgeScore`의 사유 범주는 `DEVICE_HISTORY`('이 기기의 이용 기록')다 [가정, 문구는 법률 검토 wbs 7.4.1].** 정본의 표에 행이 없었다. 최초 방문 쿠키와 세션의 나이는 이 기기의 이용 이력에 가장 가깝다.
7. **`HumanCheck`의 재시도 예산**: 호출은 500ms [가정]에 끊고, 남은 데드라인이 200ms [가정] 넘을 때만 같은 `idempotency_key`로 한 번 더 보낸다. 다시 보낼 때는 응답과 점수 계산에 50ms [가정]를 남긴다. Cloudflare 쪽 내부 오류(`internal-error`)와 우리 쪽 비밀 키 오류는 이용자 실패가 아니라 보류로 본다(키 설정 실수로 모두가 봇이 되지 않게).

8. **피처 읽기와 기기 이력을 이렇게 다룬다.** 키마다 성공·실패를 따로 받아 읽지 못한 피처만 값 없음으로 두고, 하나라도 실패하면 `degraded`다. `tr:devacct`는 정렬 집합(점수는 시각)으로, `tr:devhist`는 날짜 칸으로 바꿔 '지난 30일'을 지킨다. 쓰기는 사람 확인을 통과한 뒤로 미룬다. pid마다 하루 새 기기 수에 상한(`tr:pidnew`, 값은 비공개 설정)을 둔다. 있는지·꽉 찼는지는 30일 기준과 함께 기기 키의 Lua 한 번으로 보고, 꽉 찼거나 이미 있는 사람은 몫을 쓰지 않는다. 몫 키는 해시 슬롯이 달라 그 Lua에 묶을 수 없어, 겹친 요청은 몫이 하나 더 줄 수 있다. 판정 근거 키는 첫 판정을 남긴다(`SET NX`).

## 배포 단계의 필수 조건

이 저장소의 `deploy`·`infra`에는 아직 없다. trust-svc를 켜기 전에 함께 넣어야 한다.

- 메시 허용 정책: trust-svc의 업무 gRPC 포트를 부르는 신원을 queue-svc·identity-svc로 줄인다(docs/architecture.md §5 '포트별 허용 표'). 지금 코드는 호출자를 확인하지 않는다.
- 게이트웨이의 ASN·IP 머리 지우기: 게이트웨이가 바깥에서 온 `CloudFront-Viewer-ASN`을 원본 확인 헤더가 맞는 요청에서만 남기고 `x-forwarded-for`를 입구의 클라이언트 IP로 다시 쓴다(bot-defense §3.3). queue-svc는 이 머리를 그대로 믿는다.
- `PEAKET_TRUST_RULES_FILE`을 넣는 External Secrets와 `PEAKET_ASN_TABLE_FILE` 파일.

## 대안

- **세션 트랜잭션 안에서 판정**: 쓰기가 한 번으로 줄지만, 트랜잭션이 trust-svc 응답을 기다리는 동안 계정 잠금을 쥐어 로그인 처리량이 trust-svc에 묶인다.
- **`degraded`인 `ALLOW`를 그대로 통과**: 사람 확인을 못 본 채 통과 표시가 되어 토큰 갱신 때 다시 판정받을 표시가 사라진다.
- **ASN 분류표를 환경 변수로 받기**: 분류표가 커져 환경 변수에 맞지 않고, 다시 읽기를 할 수 없다.

## 결과

- 판정 흐름과 축소 운영이 코드로 이어진다. Kafka 판정 기록, 기기 공유 수·호스팅 대역 진입 수, KMS 라벨 키, 그림자 판, 쿠키 나이는 BOT-055·060·065·070이 더한다.
- 웹 앱 서버의 `asn`은 원본 확인 머리(게이트웨이 단계 HOT-400)가 생길 때까지 0이다. 그동안 로그인 판정의 `NetworkScore`는 '그 밖'이다.

### 되돌릴 조건

- Q-T57·Q-T58에서 800ms·500ms·차단기 값이 맞지 않으면 다시 정한다.
- 규칙 파일을 Secrets Manager 직접 읽기로 바꾸면 이 결정 1을 고친다.

## 남는 한계

- 차단 기기 목록·허니팟을 읽지 못하면(세션·캐시 Redis 장애) 로비·사전 검증은 그 확정 신호 없이 `ALLOW`+`degraded`(토큰에 `hd`)로 지나간다. 정본 §4.7·§11.4의 동작이다. Redis 장애 때 이를 막으면 전원이 추가 검증으로 몰리기 때문이다. 로비 참가 토큰은 나중에 다시 판정하지 않으므로, 장애 구간에 들어온 차단 기기는 그대로 남는다.
- 기기 라벨 키가 없으면 trust-svc는 운영에서도 경고만 남기고 뜬다. 그동안(BOT-060 전) 로비 판정은 전부 `degraded`이고 로그인은 전부 `UNKNOWN`이다.
- 추가 검증(`VERIFICATION`) 실패 수와 `CHALLENGE`의 보냄 수는 사람 확인 통과 없이 `tr:devhist`에 쓰인다. 남의 기기 이력을 더럽히려면 남의 128비트 `deviceId`를 알아야 해서 위험은 낮다고 본다.
