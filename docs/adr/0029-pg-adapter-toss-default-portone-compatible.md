# ADR-0029: 결제 게이트웨이 다중화를 위한 PG 어댑터 패턴 채택 (토스페이먼츠 기본, 포트원 V2 호환)

- **상태**: 채택 (2026-10-09 수립. ADR-0015의 선정 사유를 공식 보완하고 지원 PG 범위를 포트원까지 확장. 좌석 확정 후 승인이라는 2단계 결제 원칙은 불변 유지) ADR-0044(2026-10-13)가 결제사 선택 규칙(결제 시도마다 선택, 결제 접수 뒤 고정, 공연별 지정, 장애 시 운영자 승인 전환)과 포트원 결제 접수 계약을 더하고, 포트에 결제창 값 생성(`checkout()`)을 추가한다. ADR-0050(2026-10-13)이 맥락의 '토스는 서명 없음'을 '결제 웹훅은 서명이 없고 지급·셀러 웹훅은 서명이 있다'로 바로잡는다. ADR-0036(2026-10-09)이 미정으로 남았던 외부 한도(토스 운영 TPS, 포트원 승인 기한·호출 한도)를 확인·추정으로 보완한다
- **관련 문서**: ADR-0015, ADR-0036(외부 한도 추정), docs/features/payment.md §2.1·§5, docs/api/guidelines.md §4·§8, docs/security/secrets-and-keys.md, POL-013, POL-026, POL-032
- **관련 ID**: FR-011, FR-041, FR-047, POL-013, POL-026, POL-032, NFR-005, NFR-006, SCR-011, SCR-038

## 맥락
- ADR-0015에서는 토스페이먼츠(Toss Payments)를 기본 결제 대행사로 지정하였으나 구체적인 선정 근거와 대안 확장성이 명시되지 않았다. 이에 따라 국내 가맹점 점유율이 높은 포트원(PortOne V2)과의 호환성을 확보하고 서드파티 벤더 종속성을 제거해야 한다는 요구사항이 제기되었다.
- 공식 기술 문서 검토 결과 다음과 같은 특성 차이가 확인되었다:
  - **토스페이먼츠**: 테스트 환경에서 실제 승인 흐름과 실패 헤더(`TossPayments-Test-Code`)를 정교하게 모킹할 수 있으나, 샌드박스 API가 분당 100건으로 엄격히 제한되어 있어 대규모 부하 시험에는 활용할 수 없다. 운영 승인 TPS 상한은 영업 기밀로 미공개 상태이다.
  - **포트원 V2**: 채널 설정에서 '수동 승인'을 명시적으로 활성화해야만 티켓팅에 필수적인 '인증 완료 후 서버 승인' 흐름이 지원되며, 엑심베이·페이레터 등 일부 해외 채널은 수동 승인을 지원하지 않는다.
  - **스펙 불일치**: 멱등키 형식(포트원은 큰따옴표 포함 16~256자)과 유효 기간(토스 15일 vs 포트원 3시간), 승인 결과 코드 체계, 웹훅 서명 프로토콜(토스는 서명 없음, 포트원은 Standard Webhooks 규격)이 상이하다.

## 결정
1. 주문(`purchase-svc`) 및 결제(`payment-svc`) 서비스는 구체적인 외부 PG사를 직접 참조하지 않고 추상 인터페이스인 `PaymentGatewayPort`만을 의존하며, 외부 연동은 어댑터 패턴으로 격리한다. 제공 어댑터는 토스페이먼츠(기본), 포트원 V2, 그리고 자체 구현한 고속 PG 시뮬레이터(Simulator) 3종이다.
2. 각 어댑터는 초기화 시 자신의 기능 플래그(서버 수동 승인 지원 여부, 승인 제한 시간, 부분 취소 지원, 웹훅 서명 검증 지원, 멱등키 보관 주기 등)를 런타임에 반환하며, 서버 수동 승인을 지원하지 않는 PG 채널은 티켓 판매 결제 수단에서 원천 배제한다(POL-013).
3. 결제 상태는 도메인 표준 열거형(`APPROVED`, `ALREADY_APPROVED`, `IN_PROGRESS`, `DECLINED`, `UNKNOWN`)으로 상호 정규화한다. 상태가 불확실한 `UNKNOWN` 응답 시에는 결제를 중단하지 않고 항상 PG 거래 조회 API를 호출하여 최종 진위 여부를 재확인한다.
4. 멱등키는 양사의 제약을 모두 충족하는 포맷(`confirm-{orderId}`, `cancel-{cancellationId}`)으로 생성하며, 재전송은 양사 공통 보관 안전선인 3시간 이내에서만 수행하고 3시간 초과 건은 반드시 선조회 후 후승인 절차를 밟는다.
5. 웹훅 이벤트는 상태 변경의 확정 데이터가 아닌 '단순 트리거'로만 취급하며, 실제 상태 갱신은 웹훅 수신 즉시 서버가 직접 PG 조회 API를 호출하여 확인한 결과로 집행한다. 중복 수신 제거는 토스가 `tosspayments-webhook-transmission-id`, 포트원이 이벤트 종류·`paymentId`·`timestamp`를 키로 한다.
6. 테스트 전략을 다층화한다:
   - 모든 Pull Request CI 단계에서는 인메모리 고속 PG 시뮬레이터로 100% 계약 테스트를 통과시킨다.
   - 외부 샌드박스(토스, 포트원)는 일일 스모크 테스트(1일 1회 소량 트랜잭션)로만 점검하여 쿼터 고갈을 방지한다.
   - 피크 부하 시험(100만 대기열, 300 결제 TPS)은 자체 PG 시뮬레이터만을 배타적으로 사용한다.

## 검토한 대안
| 대안 | 기각 사유 및 한계점 |
| --- | --- |
| 토스페이먼츠 단일 전용 결합 | 추후 수수료 협상이나 파트너사 요청으로 PG사를 추가/변경할 때 핵심 결제 사가(Saga) 오케스트레이션 로직 전체를 재작성해야 하는 기술 부채가 발생한다. |
| 포트원 V2를 기본 PG로 지정 | 채널 설정에 따른 수동 승인 가변성과 모킹 실패 헤더 미제공으로 인해 카오스 엔지니어링 장애 주입 테스트(K7)의 자동화가 극히 어렵다. |
| PG사마다 독립적인 Saga 워크플로 구현 | '이중 결제 0건'과 '과금 없는 좌석 해제'라는 치명적 금융 불변식을 PG사 수만큼 중복 검증 및 증명해야 하여 결함 발생 위험이 배가된다. |

## 결과와 트레이드오프
- 단일 Saga 로직과 정규화된 계약 테스트만으로 모든 PG 연동의 무결성을 일관되게 증명할 수 있으며, 신규 PG사 확장이 어댑터 단위 구현으로 캡슐화된다.
- 다양한 PG사의 응답 코드 및 에러 타입을 단일 도메인 규격으로 변환하는 정규화 매핑 테이블을 지속적으로 유지보수해야 한다.
- 운영 승인 한도를 확인하기 전에는 합산 동시 입장 상한을 늘리지 않는다(docs/architecture.md §9.5). 공연별로 PG 채널을 나누는 것은 한도가 모자랄 때 쓰는 대안으로 남긴다. 포트원의 승인 기한·호출 한도는 추정치이므로(ADR-0036, POL-027 '추정') 포트원 경로의 운영 신뢰도는 토스보다 낮다.
