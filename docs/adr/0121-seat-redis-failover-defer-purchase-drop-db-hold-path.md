# ADR-0121: 좌석 Redis 장애 조치 동안 그 회차의 구매 요청을 잠시 미루고, PostgreSQL 비상 홀드 경로를 없앤다(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 중간-039 '좌석 Redis 페일오버 때 DB 비상 경로에 전환·복귀 규칙이 없어 이중 홀드가 날 수 있다'에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 검토는 (가) 장애 조치 동안 새 홀드를 미루는 안과 (나) DB 경로를 남기고 전환·복귀 규칙을 더하는 안을 내고 고르지 않았다. 장애 조치 때의 이중 홀드를 없앤다는 방향은 소유자 결정(추천안 승인)이고, (가)를 고른 것과 기준값·세부는 추천 적용이다. 숫자는 재기 전 가정값이다. ADR-0014 '결과와 트레이드오프'의 비상 경로(PostgreSQL 정렬 잠금, 홀드 p99 300ms)는 이 ADR로 대신한다. 장애 조치 뒤 화면을 맞추는 회차 세대(`seatEpoch`)의 클라이언트 규칙과 형식은 기술 검토 중간-040으로 같은 날 정본에 넣었다) 2026-10-29(문서 대조 R-166): 결정 3의 `seat_store_unavailable`은 회차 라벨 `{event_id}`를 단 지표로 읽는다. 이 감축의 사유 라벨은 `seat_store`다(ADR-0145 결정 8).
- **관련**: NFR-003, NFR-004, NFR-015, NFR-025, FR-010, FR-011, POL-012, ADR-0014(Soft Hold·Hard Sale), ADR-0056(리더 세대), ADR-0070(빠른 실패와 준비 상태), ADR-0083(결정 1 근거 ②, 결정 3), ADR-0085(결제 일시 정지 동안 홀드 멈춤), ADR-0086(쿼리·인덱스 규칙), ADR-0103(판매 일시정지 상태와 사본), [docs/features/seat-hold.md](../features/seat-hold.md) §1·§3·§6·§7·§9·§11·§12·§13, [docs/architecture.md](../architecture.md) §1·§5·§7·§9.3, [docs/data.md](../data.md) §2·§3·§5, [docs/frontend.md](../frontend.md) §4.4, docs/api/openapi.yaml(홀드 503), [docs/infra.md](../infra.md) §5·§6·RB-06, [docs/infra-handover.md](../infra-handover.md), [docs/observability.md](../observability.md) G-02·G-23, [docs/verification.md](../verification.md) §2·§5.3·V-T6, planning/02 NFR-003·NFR-015, planning/01 §5.2, guide/14, [review/tech-review.md](../../review/tech-review.md)(중간-039·중간-040)

## 맥락

- **지금 설계**: 좌석 Redis(메모리에 데이터를 두는 빠른 저장소)의 주 노드가 장애로 넘어가면, purchase-svc는 PostgreSQL 정렬 잠금 경로로 홀드(결제하는 동안 좌석을 잠시 잡아 두는 것)를 준다(docs/features/seat-hold.md §9).
  - 회차·좌석마다 한 행인 `event_seat_price`를 좌석 ID 순으로 `SELECT … FOR UPDATE`하고, 트랜잭션 첫 문장의 `SET LOCAL lock_timeout = '100ms'`로 잠금 대기를 끊는다(ADR-0083 결정 3).
  - `seat_sale`과 홀드 원장 `seat_hold`에 같은 좌석이 없을 때만 홀드 행을 넣는다. 홀드 p99는 300ms로 완화하고, 동시 입장 목표를 50% 줄인다. 복구되면 DB를 기준으로 비트맵을 다시 만든다.
- **기술 검토가 찾은 빈칸(중간-039)**:
  - ① 전환을 정하는 주체가 없다. Redis 클라이언트가 100ms 안에 실패하면 파드마다 따로 DB 경로로 가서, 일부 파드는 Redis로, 일부는 DB로 홀드를 주는 순간이 생긴다.
  - ② DB 경로는 홀드 원장으로 '이미 잡힌 좌석'을 본다. 그런데 원장은 Redis Stream → Kafka를 거쳐 늦게 들어오고, Redis 장애 때는 이 릴레이도 멈춘다. 장애 직전 몇 초의 홀드가 원장에 없어 같은 좌석을 다른 사람에게 또 준다. 오버셀(같은 좌석이 두 사람에게 팔리는 사고)은 Hard Sale의 유일 제약이 막지만, 진 사람은 결제창 인증까지 마친 뒤 실패를 본다.
  - ③ 복귀 규칙이 없다. 그 사이 들어오는 홀드를 막는지, 승격된 복제본에 남은 홀드를 DB 경로의 홀드와 어떻게 합치는지, 좌석 델타 번호를 어떻게 다시 시작하는지가 없다.
  - ④ DB 경로 동안 좌석 델타가 나가지 않아 화면이 멈춘다.
  - ⑤ 홀드 규칙(1인 한도, 펜싱 토큰, 만료)을 Lua와 SQL 두 곳에서 똑같이 지켜야 한다.
- **②는 규칙을 더해도 풀기 어렵다**: 마지막 몇 초의 홀드를 아는 것은 Redis의 주 노드와 복제본뿐이다. Redis를 읽지 못하는 동안 DB 경로가 '확인할 수 없는 좌석'을 막으려면 어느 좌석이 그런지 알아야 하는데, 원장에는 그 정보가 없다. 그래서 안전하게 막으면 모든 좌석을 막게 되고, 그것은 홀드를 주지 않는 것과 같다. 복제본의 비트맵을 읽으면 알 수 있지만, 그 복제본이 바로 몇 초 뒤 주 노드로 승격되는 노드다.
- **확인한 사실(2026-10-28 원문)**:
  - AWS ElastiCache 문서(Multi-AZ로 중단 시간 줄이기): 주 노드만 실패하면 복제 지연이 가장 짧은 복제본을 주 노드로 승격하고, 승격이 끝나면 쓰기가 다시 된다. 이 과정은 "보통 몇 초"다. 클러스터 전체가 실패하면 노드를 새로 만들고 데이터는 사라진다. Valkey 9.0 이상의 내구성(durability) 클러스터는 동기 쓰기를 장애 조치 때 잃지 않는다고 적는다.
  - AWS Builders' Library 'Avoiding fallback in distributed systems'(Jacob Gabrielson): Amazon은 대체 경로(fallback)를 거의 쓰지 않는다. 대체 경로는 시험하기 어렵고, 그 자체가 실패할 수 있으며, 장애를 더 키우는 일이 많고, 가장 어지러운 순간에만 돈다. 대신 주 경로를 더 튼튼하게 하고, 부른 쪽이 다시 시도하게 하며, 대체 경로를 꼭 두려면 평소에도 늘 돌려 장애 조치(failover)로 바꾸라고 한다.
  - NFR-015의 좌석 Redis RTO(복구까지 걸려도 되는 시간) 목표는 30초다.

## 결정

1. **장애 조치 동안 그 샤드의 회차는 구매 요청을 잠시 미룬다(방향은 소유자 승인, (가)를 고른 것은 추천 적용)**.
   - 그 회차의 좌석 샤드를 읽거나 쓰는 구매 세션 요청은 503 `seat-store-unavailable`과 `Retry-After: 2` [가정]로 답한다. 새 홀드(직접 선택·자동 배정), 홀드 해제·연장, 좌석 스냅샷, 주문 생성·결제 시도 시작·결제 접수의 홀드 확인이 여기에 든다. 검토 문구는 '새 홀드만'이었지만, 주문과 결제 접수도 같은 샤드의 홀드를 확인하므로 같은 답을 받는다.
   - 그 팬의 구매 세션 키(`s:session:{sid}` 등)가 장애 샤드에 있으면, 회차와 관계없이 같은 503을 받는다.
   - 그대로 이어지는 것: 이미 잡은 홀드(승격된 복제본에 남는다), 이미 접수한 결제의 Saga(Hard Sale·승인·발권은 PostgreSQL과 결제사만 쓴다), 결제 결과 조회, 대기열(다른 Redis 클러스터)이다. Saga가 Redis에 돌려야 할 좌석 해제는 소비자가 다시 시도해, 장애 조치가 끝난 뒤 반영된다.
   - 홀드 시간은 그대로 흐른다(만료는 절대 시각이다). 장애 조치가 목표 30초 안이면 홀드 TTL 7분에 견줘 짧아 따로 늘리지 않는다. 결제창 결과는 승인 기한(인증 뒤 10분) 동안 쓸 수 있어, 결제 접수를 몇 초 미뤄도 같은 멱등키로 다시 보내면 된다.
   - 고른 이유: 홀드를 주는 곳이 늘 Redis 하나라서 장애 조치 중 두 곳에서 홀드를 주는 순간이 없다(검토 ①②⑤가 함께 사라진다). 미루는 시간은 관리형 장애 조치의 승격 시간(보통 몇 초)이고, DB 경로를 두어도 복귀 때는 새 홀드를 잠깐 멈춰야 한다(검토 (나)③). 1년에 몇 번 도는 두 번째 홀드 구현은 Builders' Library가 경고한 대체 경로 그대로이고, 판매 확정(Hard Sale)이 쓰는 purchase DB의 쓰기 노드에 가장 바쁜 순간 홀드 쓰기를 더한다.
2. **전환 표시를 두지 않고 파드마다 판단한다(추천 적용)**: 쓰는 곳이 하나라 어느 파드가 언제 장애를 알아채든 결과가 같다. 파드는 Redis 클라이언트의 빠른 실패(핫패스 시간 초과 100ms, 오프라인 큐 없음, ADR-0070)를 받으면 503을 낸다. 준비 상태는 내리지 않는다(공유 의존성이 죽어도 파드를 빼지 않는다, ADR-0070). 미루기 시작하면 `seat_store_unavailable{event}`를 1로, 미룬 요청 수를 `seat_hold_deferred_total{reason}`로 내보낸다.
3. **동시 입장 목표는 지금처럼 줄인다(추천 적용)**: admission-ctrl은 `seat_store_unavailable`이 1인 회차(제어 입력 긁기 5초)의 동시 입장 목표를 바로 50% 줄인다. 회복 뒤에는 AIMD가 천천히 올린다. 이 503은 홀드 가용성(NFR-003)의 오류로 센다. 그래서 에러 버짓 연동 감축이 함께 걸릴 수 있고, 그때는 그 규칙을 따른다(docs/architecture.md §5).
4. **세대 키가 '좌석 저장소 준비됨' 표시다(추천 적용)**: 회차마다 `s:{event:E}:epoch`(Hash: 세대 `seatEpoch`, 그 세대를 연 주 노드)를 둔다. 비트맵을 처음 만들거나 다시 만들 때 마지막에 쓴다. 홀드·해제·연장·만료 Lua와 스냅샷 읽기는 이 키가 없으면 좌석을 읽거나 잡지 않고 `NOT_READY`를 돌려주고, purchase-svc는 503 `seat-store-unavailable`로 답한다. 그래서 전체 장애 뒤 빈 노드나 비트맵을 만들기 전의 회차에서, 팔린 좌석을 빈 좌석(비트 0)으로 읽고 홀드를 주는 일이 없다.
5. **장애 조치 뒤 세대를 올린다(추천 적용)**: 파드가 클러스터 토폴로지(어느 노드가 어느 슬롯의 주 노드인지)를 새로 읽다가 그 회차 슬롯의 주 노드가 바뀐 것을 보면, 새 주 노드에서 Lua 하나로 '세대 키의 주 노드가 지금 주 노드와 다를 때만 세대 = max(세대 + 1, Redis `TIME`의 초), 주 노드 = 지금 주 노드'를 한다. 대상 회차는 좌석 비트맵이 있는 회차 목록(`s:ctl:events`, ADR-0103)과 purchase-svc의 회차 캐시에서 그 슬롯에 드는 회차를 고른다.
   - 여러 파드가 거의 같이 불러도 한 번만 오른다.
   - 장애 전에 복제되지 못한 마지막 '올리기'를 잃어도, 새 세대는 그때보다 뒤의 초라서 값이 되돌아가지 않는다(노드 시계가 장애 조치 시간보다 크게 어긋나지 않는다는 전제).
   - 클라이언트는 세대가 바뀌면 구독한 구역을 모두 스냅샷으로 다시 맞춘다(docs/features/seat-hold.md §7, docs/frontend.md §4.4, 기술 검토 중간-040). 장애 조치 뒤 되돌아갔을 수 있는 번호를 세대로 가르는 생각은 대기표 세대 번호(docs/features/queue-admission.md §3)와 같다.
6. **전체 장애 뒤에는 DB로 다시 만든다(RB-06, 추천 적용)**: 주 노드와 복제본이 함께 사라져 회차 키가 비면, 세대 키가 없어 그 회차는 이미 503이다. purchase-svc의 다시 만들기 작업이 판매 중인 회차(purchase-svc의 회차 캐시) 가운데 세대 키가 없는 회차를 찾아 다음 순서로 한다. 회차마다 한 작업만 하도록 purchase DB 행 잠금을 잡는다.
   - ① 새 요청은 이미 멈춰 있다(세대 키 없음).
   - ② `seat_sale`의 PENDING·SOLD, 홀드 원장 `seat_hold`의 만료 전 HELD(소유자·펜싱 토큰·만료 시각 그대로), `purchase_quota`와 원장 홀드로 계정별 보유 수, 만료 인덱스를 만든다. 판매 일시정지 사본은 `sale_control`로 다시 쓴다(ADR-0103).
   - ③ 세대 키를 마지막에 쓴다(세대 = Redis `TIME`의 초).
   - ④ 세대 키가 서면 요청을 다시 받는다.
   - 원장에 적재되기 전에 사라진 홀드는 돌아오지 않는다(지금과 같다, seat-hold §6의 5).
7. **PostgreSQL 비상 홀드 경로를 없앤다(추천 적용)**: `event_seat_price`를 잠그는 홀드 경로와 그 경로의 `seat_hold` 직접 기록, 그 경로용 만료 쓸기 인덱스 `seat_hold (expires_at) WHERE status = 'HELD'`(ADR-0086), 비상 경로의 잠금 대기 100ms(ADR-0083 결정 3)를 뺀다.
   - `seat_hold`는 평소처럼 릴레이가 적재하는 감사 원장으로 쓰고, 전체 장애 뒤 다시 만들기의 입력이 된다. `event_seat_price`는 회차·좌석별 등급 정본으로 남는다.
   - K3(교착 0건)는 v0의 행 잠금 홀드와, v1 Hard Sale이 여러 좌석의 PENDING 행을 좌석 ID 순으로 넣는 것으로 잰다(seat-hold §6·S-T10).
   - 트랜잭션 범위 설정만 쓰고 세션 `SET`을 쓰지 않는 규칙(ADR-0083 결정 3의 뒷부분, ADR-0070)은 그대로다.
8. **시험(추천 적용)**: seat-hold S-T9를 '장애 조치 동안 503과 `Retry-After`, 이중 홀드 0건(복제되지 못한 쓰기는 따로 센다), 오버셀 0건, 미룬 시간, 장애 전 홀드 유지, 회복 뒤 세대 오름'으로 바꾼다. 세대·준비 표시·다시 만들기 순서는 S-T26이 본다. Game Day G-02·G-23, verification V-T6과 `seat` 명세 검사도 같은 동작으로 바꾼다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| (나) DB 경로를 남기고 회차별 전환 표시, 전환 직전 N초 홀드의 '확인 불가' 막기, 복귀 순서(멈춤 → 재구성 → 세대 → 재개), 두 구현의 같은 시험 묶음을 더한다 | '확인 불가' 좌석을 정할 자료가 Redis에만 있다. 복제본 비트맵을 읽으면 되지만 그 노드는 몇 초 뒤 주 노드가 된다. 복귀에도 홀드 멈춤이 든다. 1년에 몇 번 도는 두 번째 홀드 구현이 남는다(Builders' Library). 장애 전환의 깊이는 결정 4~6(준비 표시, 세대, 다시 만들기 순서)과 S-T9·S-T26·G-02로 보인다 |
| 지금처럼 파드마다 따로 DB 경로로 간다 | 검토 ①②의 이중 홀드가 남는다 |
| 장애 조치 동안 복제본에서 스냅샷만 준다 | 승격 중인 노드라 읽기도 끊긴다. 몇 초 동안 화면을 보이려고 읽기 경로를 하나 더 둔다 |
| `WAIT`로 복제를 확인한 뒤 답해 잃는 쓰기를 없앤다 | `WAIT`는 복제를 보장하지 않고, 시간 초과면 확인하지 못한 채 돌아온다(ADR-0014 상태 줄). 잃는 쓰기를 줄일 뿐이다. 쓸지는 지금처럼 PoC로 정한다(seat-hold §13) |
| 장애 조치 동안 홀드 남은 시간을 멈춘다(ADR-0085처럼) | 목표 30초는 TTL 7분에 견줘 작다. 멈춘 시간을 미는 쓰기를 장애 중인 Redis에 해야 한다 |
| 세대 없이 구역 번호를 처음부터 다시 센다 | 클라이언트가 '같거나 작으면 버린다'로 새 델타를 버린다(중간-040) |

## 결과와 트레이드오프

- **좋은 점**
  - 홀드를 주는 곳이 늘 하나라, 장애 조치 중에 두 곳이 같은 좌석을 주는 일이 없다. 남는 것은 복제되지 못한 쓰기뿐이다.
  - 홀드 규칙의 구현이 Lua 하나로 줄고, 평소에 도는 경로만 남는다.
  - 장애 조치나 다시 만들기 뒤 화면이 세대로 바로 맞춰진다(주기 스냅샷을 기다리지 않는다).
  - 비트맵이 없거나 빈 노드에서 팔린 좌석을 빈 좌석으로 읽는 일을 준비 표시가 막는다.
- **대가**
  - 장애 조치 동안(보통 몇 초, 목표 30초) 그 회차의 구매 요청이 멈춘다. 503은 홀드 가용성의 오류로 세므로, 온세일 중이면 NFR-003의 그 회 오류 버짓(약 75건)을 넘긴다(초당 2,000건 × 30초면 최대 약 6만 건). 이 손실은 숨기지 않고 NFR-003 위반으로 성능 장부에 적는다.
  - 전체 장애면 다시 만들기가 끝날 때까지(분 단위 [가정]) 멈춘다.
  - ADR-0083 결정 1의 PostgreSQL 유지 근거 ②(비상 경로의 밀리초 잠금 대기)는 더 이상 근거가 아니다. ①·③·④·⑤가 그대로라 PostgreSQL을 유지한다는 판단은 바뀌지 않는다.
- **반영 수치(2026-10-28)**: WBS 2.5.3에서 DB 비상 경로를 빼고(−0.5일 [가정]), 같은 작업에 503 미루기·세대 키·다시 만들기를 더한다(+0.5일 [가정]). 합은 그대로다. 0.9.2 좌석 명세의 'DB 경로'는 '장애 조치 동안 미룸'으로 읽는다.

## 되돌릴 조건

- S-T9·G-02와 운영의 장애 조치 기록에서 요청을 미룬 시간이 자주 30초를 넘거나, 온세일 중 좌석 Redis 장애 조치가 분기에 한 번보다 자주 생기면 (나)를 다시 본다. 그때는 복제본 비트맵을 '확인 불가' 목록으로 쓰는 DB 경로, 회차별 전환 표시, 두 구현의 같은 시험 묶음을 함께 둔다.
- 관리형 서비스의 동기 쓰기 보장(ElastiCache Valkey 9.0 이상의 내구성 클러스터)이 홀드 p99 50ms 예산과 비용 안에 들어오면, 잃는 쓰기를 없애는 쪽을 재서 다시 본다.

## 남는 한계

- 장애 조치 동안 그 회차의 구매 요청이 멈춘다. 그 사이 홀드 시간이 다 된 팬은 연장·주문을 못 해 좌석을 잃을 수 있다.
- 복제되지 못한 마지막 쓰기(홀드, 보유 수, 구역 일련번호)는 잃는다. 그 홀드의 팬은 결제 접수 때 좌석이 비어 있으면 그대로 살 수 있고(seat-hold §5), 다른 사람이 먼저 잡았으면 결제창 인증 뒤 실패를 본다(과금 없음). 보유 수는 판매 확정의 한도 행(`purchase_quota`)이 지킨다.
- 전체 장애면 원장에 적재되기 전에 사라진 홀드는 돌아오지 않는다.
- 세대는 노드 시계에 기댄다. 시계가 장애 조치 시간보다 크게 뒤로 가면 세대가 되돌아가, 그 회차 화면이 주기 스냅샷(5초·30초)까지 틀릴 수 있다.
- 구매 세션 키가 장애 샤드에 있는 팬은 다른 회차를 사는 중이어도 같은 시간 동안 멈춘다.
