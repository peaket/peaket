# ADR-0230: 결제 결과는 기계가 정하고, 주문 조회가 생길 때까지 주문 ID를 예매번호로 보인다

- **상태**: 채택(2026-11-09, 추천 적용). BUILD_ORDER HOT-363.
- **관련**: [docs/frontend.md](../frontend.md) §3.6·§3.12, [docs/design/d5-screen-blueprint.md](../design/d5-screen-blueprint.md) §5.12·§9.2, [docs/features/payment.md](../features/payment.md), ADR-0079 결정 8, ADR-0106, ADR-0221, ADR-0229
- **관련 ID**: SCR-012, FE-T24

## 맥락

- 결과 화면은 목업이었다. §3.6에 결제 결과 기계의 표가 있다.
- 정본에 빈칸이 있었다.
  - 확정 화면의 예매번호와 결제 금액을 어디서 얻는지 없다. `PaymentStatus`에 없고 주문 조회 API도 없다.
  - 접수되지 않은 주문을 보면(409 `payment-not-accepted`) 화면이 무엇을 보이는지 없다.
  - 결과 불명에서 다시 묻는 간격이 없다.

## 결정

1. **기계는 값만 다룬다**: XState로 조회 결과를 이벤트로 받아 상태를 정한다. 요청은 실행부(`result-runtime`)가 하고, `@xstate/graph`의 경로로 모든 상태와 전이를 시험한다(FE-T24). 기계와 실행부는 늦게 가져온다.
2. **다시 묻는 간격**(`nextPollMs`): 접수부터 120초 [가정]까지 0.5~1.5초 [가정] 지터, 그 뒤 화면이 보이는 동안 30초 [가정]마다 10분 [가정]까지다. 결과 불명도 확정으로 바뀔 수 있어 30초마다 묻는다. 끝난 상태에서는 묻지 않는다.
3. **예매번호 자리에 주문 ID를 보이고 결제 금액 줄은 뺀다**. 주문 조회 API가 생기면 바꾼다. 발권한 티켓은 `GET /v1/tickets`에서 그 회차만 골라 보이고, 받지 못하면 [마이 티켓 보기]로 충분하다.
4. **접수 전 주문**(409 `payment-not-accepted`)은 '결제가 끝나지 않았습니다'와 [다시 결제하기]다. 주문 만료는 '결제하지 않아 주문이 끝났습니다'와 [좌석 다시 고르기]다.
5. **저장물 정리**: 확정과 입금 대기는 구매 세션이 끝나므로 입장 저장값·서명 키·홀드·접수 기록을 지운다. 실패와 주문 만료는 세션이 이어져 홀드와 접수 기록만 지운다(§3.6). 이 탭의 접수 기록이 있는 주문일 때만 지워, 뒤로 가기로 옛 결과에 들어와 새 홀드를 지우지 않는다.
6. **401은 한 번 갱신한다**. 갱신 뒤에도 401이면 더 묻지 않고 주문 내역으로 안내한다. 일시 오류(429·504·연결)는 다음 간격에 다시 묻고, 429의 `Retry-After`보다 먼저 묻지 않는다.
7. **미리보기**는 개발 서버에만 남긴다(ADR-0228 결정 7과 같다).
8. **가짜 API**: `GET /v1/orders/{id}/payment-status`, `GET /v1/tickets`, `pay=` 상태.

## 결과

- 좌석 → 홀드 → 주문 → 결제 복귀 → 접수 → 결과까지 실제 화면으로 이어진다. 결제창(HOT-358)과 실시간 좌석(HOT-357)이 남았다.

## 검토한 다른 안

- **결과 불명에서 묻기를 멈추기**: 화면을 열어 둔 사람이 확정을 놓친다.
- **예매번호 칸을 비우기**: 고객센터 문의에 쓸 번호가 사라진다. 주문 ID는 주문 내역과 같은 값이다.
