# ADR-0069: 관제 운영 원칙 대조와 보강 — 자동 제어의 자기 안전, 경보 관리, 넓은 이벤트(2026-10-20)

- **상태**: 채택 (2026-10-20. 소유자가 디자인 캔버스의 SCR-029를 보며 "운영 관제 기획/디자인 점검 해주세요. 1. 현재 어떤 지표를 수집해서 어떻게 보여주고 어떤 판단을 내리는지 2. google sre 원칙에 맞는지 / release it 원칙에 맞는지 / observerbility enginerring 원칙에 맞는지"라고 요청했다. 점검 보고(빈 곳 14개와 화면 누락)를 본 뒤 "추천대로 가겠습니다. 승인"이라고 했다. 결정 1의 '입력이 없으면 현재 목표 유지'와 결정 6의 '명령 2·3·6부터'는 보고에서 물은 두 질문에 소유자가 추천안을 고른 것이다. 나머지 결정의 세부와 수치는 추천 적용이며 소유자 검토 대상이다. 외부 사실은 2026-10-20에 원문으로 확인했다) 2026-10-20(ADR-0070): 경보 종류에 `flow`(처리량 급감)를 더한다. 런북은 33종(RB-31~RB-33), Game Day는 25종(G-23~G-25)이 된다. 2026-10-26(4차 점검 3부): 결정 10의 명령 9 '배경 작업 멈춤' 묶음은 넷(일괄 환불의 새 묶음, 파트너 웹훅 재시도, 광고성 알림 묶음, 공연예술통합전산망 재전송)으로 읽는다. 정산 지급 묶음과 홈 랭킹 게시는 대형·중형 온세일 윈도우에 미루기만 하고 이 묶음에 넣지 않는다(ADR-0073 결정 19, docs/architecture.md §5). 2026-10-28(기술 검토 높음-12, 소유자 승인 '추천안 동의'): 결정 1의 제어 입력은 5초 긁기 작업의 값을 30초 창으로 읽고, 30초 입력 없음 판정은 긁기 간격의 3배 이상이어야 한다(설정 검사 V-T20). 표본 나이는 `timestamp()`로 본다. 결정 2의 감축 확인 시간은 '예매 단계 인원이 새 목표 아래로 오고 감축 뒤 35초가 지남, 또는 2분'으로 읽고, AIMD 증액은 새 30초 창마다 한 번 초기 목표의 2%로 한다. 결정 5의 경보 규칙 시험은 합성 시계열 간격과 평가 간격을 운영 값과 같게 두고, SEV1의 짧은 창은 20초다(docs/observability.md §4 '긁기·평가·알림 간격'). 2026-10-28(ADR-0105, 소유자 승인 '추천안 동의'): 결정 7의 `payment_confirm_resolution_seconds{pg}`에 경로 라벨 `path`(direct·retry_queue)를 더한다. RB-07 전환 검토와 새 결제 진입 정지의 시작은 direct의 p99만 보고, NFR-006 Degraded 측정은 두 경로를 합친다. 2026-10-28(기술 검토 높음-16, 소유자 승인 '추천안 동의'): 결정 7의 이유 '승인 호출은 2초 기한에서 끊기므로 호출 p99는 2초를 넘을 수 없다'는 더 맞지 않는다. 승인 호출은 2초에 끊지 않고 읽기 시간 초과 60초 [가정]까지 기다린다(ADR-0070 상태 줄). 임박 경보는 '1분 창 승인 호출 p99가 2초를 넘음(호출의 1% 이상이 2초 초과)'으로 읽는다. 전환 검토를 확정 소요 p99 5초로 두는 것은 그대로다. 호출 한 번이 빨라도 같은 멱등키 재시도와 결과 모름 조회가 쌓이면 확정이 늦기 때문이다. 2026-10-28(ADR-0106, 소유자 승인 '추천안 동의'): 인시던트 선언 기준의 '60초 넘은 결제-발권 불일치'는 '결제 승인 뒤 60초 안에 발권되지도 발권 재시도 큐에 들어가지도 않은 결제, 또는 발권 기한(승인 뒤 30분 [가정]) 초과'로 읽는다. 승인 뒤 발권 실패는 결제를 취소하지 않고 다시 발권한다. 2026-10-28(ADR-0126, 소유자 승인 '추천안 동의'): 결정 2의 에러 버짓 연동 감축(10배 소진 경보, 온세일 50% 소진선)은 입장 목표가 부하를 정하는 여정(좌석 홀드·좌석 상태 전파·결제 접수·결제 확정)의 예산으로만 한다. 공연 상세·대기열 진입·대기 상태 전파의 소진은 호출과 그 여정의 자동 보호만 부르고 목표를 바꾸지 않는다. 결제사 쪽 원인일 때의 감축은 콘솔과 감사 로그에 '노출 줄이기'로 남기고, `admission_target_decrease_total`에 `journey` 라벨을 더한다(Q-T49). 2026-10-28(기술 검토 낮음-161, 소유자 승인 '추천안 동의'): 결정 12의 '경로 템플릿마다 초당 1건은 비율과 관계없이 남긴다(`rate_limiting`·`composite` 정책)'는 그 정책으로 할 수 없다. `rate_limiting`은 정책 하나에 토큰 통 하나를 두고 초당 스팬 수로 세며, `composite`는 하위 정책마다 스팬 비율을 나눠 줄 뿐 경로 값마다 나눠 세지 않는다(수집기 문서, 2026-10-28 확인). 그래서 목적(드문 경로의 성공 사례 보존)대로 '드문 경로 목록(환불·양도·정산 등 [가정])의 경로마다 하위 정책 하나(`http.route` 거르기 + `rate_limiting`)와 초당 스팬 한도'로 읽는다. 목록은 OpenAPI에서 만들고, 한도는 게이트웨이 수집기 복제 수로 나눈 값이다. 모든 경로를 덮어야 하면 서비스 템플릿의 경로별 머리 표본 비율 안을 wbs 4.1.1에서 견준다(docs/observability.md §6). 2026-10-28(기술 검토 낮음-140, 소유자 승인 '추천안 동의'): 부하 관리 장치 표 '이상 파드 퇴출' 행의 '과부하 거절을 퇴출 계산에서 빼는 설정은 wbs 4.6.1에서 정한다'는, 서비스의 과부하 거절을 429 `server-busy`로 내고 최대 퇴출 비율 10%(기본값)를 쓰는 것으로 정했다. 분리 모드는 대안이다(docs/architecture.md §5).

## 맥락

- 관제는 지금까지 세 번 검토했다. ADR-0049는 지표와 경보 창을, ADR-0067은 콘솔과 관측 도구의 경계를, ADR-0068은 관측 스택의 선택 근거를 다뤘다. 이번 점검은 지금 설계를 세 묶음의 원칙에 대 보았다. Google SRE(Book 1판과 Workbook), Michael Nygard의 Release It! 2판(2018), Majors·Fong-Jones·Miranda의 Observability Engineering(1판 2022, 2판 2026-06)이다.
- 잘 맞는 것: 증상 기준 호출과 확실·임박한 원인 경보(Book 6장), 여정별 SLI·SLO·예산(Workbook 2장), 경보 시점 예산 소모 29%·21%로 맞춘 다중 창 경보(Workbook 5장, 10배×2분÷70분, 3배×5분÷70분), 오류 예산 정책(Workbook 부록 B), 원인을 모를 때 먼저 쓰는 되돌릴 수 있는 완화책(Workbook 9장의 일반 완화책), 데이터 경로와 떨어진 제어 경로(Release It!의 Control Plane), 대기열로 뒤쪽 부하를 대기 인원과 떼어 냄(Shed Load·Unbalanced Capacities), 셔플·조회 분산·폴링 지터(Self-Denial Attacks·Dogpile), OpenTelemetry 계측과 오류를 다 남기는 꼬리 표본, 직접 운영과 구매를 사람 시간까지 넣어 비교하는 측정(Observability Engineering의 Build vs Buy).
- 빈 곳:
  1. 자동 제어의 입력이 끊기거나 낡았을 때 할 일이 없다. AIMD는 클러스터 안 Prometheus 쿼리로 뒤쪽 p99·오류율을 읽는데(queue-admission §5, ADR-0068 결정 2), 빈 결과를 어떻게 읽을지 정하지 않았다. G-11은 관측 스택이 통째로 멈출 때 사람 쪽 대응만 정했다.
  2. 같은 신호에 감축을 거듭하지 않게 하는 규칙이 없다. 루프는 200ms마다 돌고 감축 효과는 이미 들어온 사람이 나가면서 천천히 나타나므로, 한 번의 지연 튐에 1초 안에 하한까지 내려갈 수 있다.
  3. 부하를 다루는 자동 장치가 여덟 가지인데(프리워밍·KEDA·Karpenter, AIMD, 에러 버짓 연동 감축, 진입 Degraded 자동 전환, 게이트웨이 동시 처리 상한, 이상 파드 퇴출, 서비스 안 서킷 브레이커, 클라이언트 폴링 간격) 서로의 관계와 순서를 적은 곳이 없다. 명령 11은 오토스케일을 빼지만 오토스케일을 멈추는 길은 없다.
  4. 경보 묶기·억제 규칙이 없다(문서 검색 0건). 결제사 장애 하나가 여러 경보로 동시에 울린다.
  5. 경보 규칙과 경로를 시험하지 않는다. Game Day로 처음부터 끝까지 확인할 뿐이다.
  6. 인시던트 선언 기준과 포스트모템 기준이 없다. '종료 뒤 48시간 안에 쓴다'만 있다.
  7. 결제사 지연 기준이 2초(observability §4 경보)와 5초(RB-07·POL-013·G-05·SCR-031 보드)로 갈린다. 승인 호출은 2초 기한에서 끊기므로(payment §2) 호출 p99로는 5초를 잴 수 없다.
  8. 판매 중 탭 위젯 가운데 운영자가 낼 명령이 없는 숫자(느린 쿼리·체감·네트워크)가 판단 숫자와 섞여 있다.
  9. 의도된 차단(403·429)은 진입 SLI 분모에서 빠지므로, 명령 4·5를 너무 넓게 걸어 사람을 막아도 SLO가 초록이다.
  10. 배경 작업(일괄 환불, 정산 지급, 웹훅 재시도, 광고성 알림 묶음 등)을 끄거나 미루는 수단이 없다.
  11~14. 처음 보는 문제를 파고들 데이터 형태가 약하다. 요청 하나를 넓게 담은 기록 표준이 없고, 표본 비율을 남기지 않으며, 경보에서 실패 사건으로 바로 가는 길이 없고, 기능 개발 절차에 계측 단계가 없다.
  15. 화면: SCR-029 '판매 중' 탭 본문이 캔버스에 없다(ADR-0067 반영 때 미룸). SCR-029의 탭들은 보드 안 숨은 상태로만 있었다.
- 확인한 원문(2026-10-20):
  - SRE Book 1판(sre.google). 6장: 대시보드는 서비스의 기본 질문에 답하고 4대 신호를 담는다. 호출 규칙을 만들 때 '같은 일로 다른 사람이 이미 호출되고 있는가'를 묻는다. 실제 사고를 가장 자주 잡는 규칙은 단순하고 예측 가능해야 하고, 드물게 쓰는 수집·경보 설정은 지울 후보다. 7장: 랙 폐기 자동화가 '남은 대상 없음(빈 집합)'을 '전체'로 해석해 CDN 서버 디스크를 거의 다 지운 사고(Diskerase). 14장: 역할은 지휘·운영·소통·계획 넷이고, 계획 역할은 시스템이 정상에서 어떻게 벗어났는지 추적해 끝나면 되돌리게 한다. 선언 조건으로 두 번째 팀이 필요한가, 고객에게 보이는가, 한 시간 집중 분석에도 안 풀렸는가를 든다. 15장: 포스트모템 트리거는 기준을 넘는 사용자 체감 저하, 모든 데이터 손실, 온콜의 개입(되돌리기·트래픽 우회 등), 기준을 넘는 해결 시간, 감시 실패(보통 사람이 먼저 발견)다. 기준은 사고 전에 정하고, 누구나 포스트모템을 요청할 수 있다. 22장: 연쇄 장애의 즉시 조치는 자원 늘리기, 헬스체크 실패·죽음 멈추기, 서버 재시작, 트래픽 버리기, Degraded 모드, 배치 부하 끄기, 나쁜 트래픽 막기다.
  - SRE Workbook. 4장: 의도한 변경(바이너리 판, 플래그, 동적 설정 판)을 감시한다. 경보 시험은 세 층이다(지표가 조건대로 바뀌는지, 규칙이 기대한 경보를 내는지, 경보가 정한 곳으로 가는지). 9장: 원인을 다 알기 전에 쓰는 일반 완화책(되돌리기, 지역 피하기 등), 인시던트 기준을 정해 둔다, 역할은 IC·CL·OL. 11장: 오토스케일에 최소·최대 한도와 긴급 정지·수동 고정을 둔다. 부하 거절과 부하 분산이 서로를 오해해 한 지역으로 트래픽을 몰아넣은 가상 사례에서, 장치 사이 교차점을 계측하고 긴급 정지를 장치 전체에 맞추며 확장이 거절보다 먼저 걸리게 하라고 한다. 부록 B(예시 오류 예산 정책): 사고 하나가 4주 예산의 20%를 넘게 쓰면 포스트모템을 하고 P0 후속 조치를 하나 이상 둔다. 같은 종류의 장애가 분기에 예산 20%를 넘게 쓰면 분기 계획에 P0 항목을 둔다.
  - Release It! 2판: 출판사(pragprog.com) 목차로 절 이름을 확인했다(안정성 반패턴의 Force Multiplier·Dogpile·Self-Denial Attacks, 안정성 패턴의 Governor·Shed Load·Create Back Pressure, Control Plane 장의 Command and Control·System-Wide Transparency 등). 본문은 대조하지 못했다. 이 ADR에서 Release It!의 요지로 적은 것(자동화는 잘못된 그림을 믿고 큰 힘으로 움직일 수 있다, 위험한 쪽 동작에 저항과 속도 제한을 둔다)은 책의 기억에 기댄 요약이다.
  - Observability Engineering: 1판(2022-05, 318쪽)과 2판(2026-06, 632쪽)의 목차를 O'Reilly에서 확인했다. 2판 6장은 'Making Structured Events Arbitrarily Wide', 9장은 관측 주도 개발, 11·12장은 SLO와 SLO 경보 디버깅, 15장은 표본, 29장은 Build vs Buy (vs Open Source)다. 원칙 내용은 저자 Charity Majors의 글 'Is it time to version observability?'(2024-08-07)로 대조했다. 저자는 여러 원천에 나눠 쓸 때 미리 집계하는 방식을 '1.0'으로, 임의로 넓은 구조화 로그 사건 하나를 기준 데이터로 두고 읽을 때 집계하며 SLO도 같은 데이터에서 내는 방식을 '2.0'으로 부른다. Honeycomb 문서: 표본으로 남긴 데이터는 표본 비율로 보정해 조회하고, 키별로 비율을 바꾸는 동적 표본과 오류 전수 보존을 함께 쓴다. 책 본문은 열지 못했다.
  - KEDA v2.21 문서: `autoscaling.keda.sh/paused: "true"`는 지금 복제 수로 즉시 멈추고, `autoscaling.keda.sh/paused-replicas: "<수>"`는 그 수로 맞춘 뒤 멈춘다. `fallback`(failureThreshold, replicas, behavior `static`·`currentReplicas`·`currentReplicasIfHigher` 등)은 스케일러가 지표를 연속으로 못 읽을 때 쓸 복제 수를 정한다. 없으면 HPA에 지표를 보내지 않는다(기본 오류 동작). CPU·메모리 트리거에는 없다.
  - Prometheus 문서: `promtool test rules`로 합성 시계열(`input_series`)을 넣고 `alert_rule_test`의 `eval_time`에서 기대 경보를 검사한다. Alertmanager: `amtool config routes test`로 레이블 조합의 경로와 수신자를 검사하고, `inhibit_rules`는 원천 경보가 있을 때 `equal` 레이블이 같은 대상 경보를 음소거한다.
  - Envoy 문서(이상 호스트 퇴출): 기본 모드에서 연속 5xx는 업스트림이 낸 5xx와 로컬 오류(시간 초과·연결 재설정)를 모두 센다. 앱이 과부하로 낸 503도 세어진다. 분리 모드(`split_external_local_origin_errors`)에서는 로컬 오류를 따로 셀 수 있다. 퇴출된 호스트 비율은 `max_ejection_percent` 아래로 묶인다.
  - OpenTelemetry Collector 꼬리 표본 처리기: `rate_limiting`·`composite` 정책, `probabilistic` 정책이 W3C `tracestate`의 확률 정보(`ot`의 `th`)를 읽고 쓰게 하는 기능 게이트(알파, 기본 꺼짐). Loki 문서: 구조화 메타데이터는 색인하지 않고 로그에 붙이는 높은 기수의 값이다(스키마 13 이상, tsdb).

## 결정

1. **자동 제어의 입력이 없으면 멈추고 목표를 유지한다(소유자 결정, 세부는 추천 적용)**:
   - 입력: AIMD가 읽는 뒤쪽 서비스 p99·오류율, 에러 버짓 연동 감축이 읽는 소진 신호.
   - 판정: 쿼리 실패, 빈 결과, 마지막 표본이 30초 [가정, Phase 2 2.3.2에서 확정]보다 오래됨 가운데 하나면 그 입력은 '입력 없음'이다. 빈 결과를 0으로 읽지 않는다.
   - 동작: 입력 없음 동안 AIMD는 목표를 늘리지도 줄이지도 않는다. 에러 버짓 연동 감축도 하지 않는다. 운영 명령(1·2·3·6 등)은 그대로 받고, 안전 한계와 결제사 상한(명령 6·12의 결과)에 따른 축소도 그대로 한다.
   - 알림: admission-ctrl이 입력 상태를 `q:{event:E}:ctl`에 쓰고, ops-svc가 읽어 콘솔 상태 바에 <입력 없음>을, 경보 패널에 SEV2를 띄운다. Alertmanager를 거치지 않으므로 관측 스택이 멈춰도 뜬다.
   - 회복: 입력이 10초 [가정] 이어서 들어오면 감축은 바로 다시 한다. 증액은 운영자가 확인한 뒤에 한다(기존 '자동 조절 복귀 확인', operator 1인).
   - KEDA: 지표를 3회 [가정] 연속 못 읽으면 지금 복제 수를 유지한다(`fallback`의 behavior `currentReplicas`). 온세일 창에는 크론 트리거가 프리워밍 최소 복제 수를 따로 지킨다. CPU·메모리 트리거는 fallback이 없어 쓰지 않는다.
   - 상태 바의 자동 제어 값은 다섯 가지가 된다: 정상, 일시정지 mm:ss, 자동 증액 멈춤, 입력 없음, 긴급 정지. 둘 이상이면 긴급 정지, 입력 없음, 일시정지, 자동 증액 멈춤 순으로 앞의 것을 보인다.
2. **감축은 효과를 확인할 시간을 둔다(추천 적용)**:
   - AIMD가 목표를 줄인 뒤에는 예매 단계 인원이 새 목표 아래로 내려오거나 2분 [가정, Phase 2 2.3.2에서 확정]이 지날 때까지 AIMD의 추가 감축을 하지 않는다. 감축은 새 입장만 멈추고 이미 들어온 사람은 평균 3분 머물러, 5,000 → 2,500 감축이면 새 목표에 닿기까지 약 1.5~2분 걸린다(남은 체류가 고르게 퍼지면 90초, 지수 분포면 3분 × ln 2 ≈ 125초).
   - 에러 버짓 연동 감축(10배 소진 경보, 온세일 50% 소진선)은 경보 하나·소진선 하나에 한 번만 한다. 같은 경보가 계속 울려도 다시 줄이지 않는다.
   - 두 감축은 서로의 확인 시간을 막지 않는다. 서로 다른 신호라 둘 다 오면 연달아 줄 수 있고, 안전 하한 아래로는 내려가지 않는다.
   - 지표: `admission_target_decrease_total{reason}`(aimd·budget_alert·budget_50·pg_cap·operator), `admission_decrease_suppressed_total`(확인 시간 동안 막은 감축). 감사 로그의 SYSTEM 기록에 사유를 남긴다.
3. **부하 관리 장치를 한 표로 두고 순서를 정한다(추천 적용)**:
   - 표는 docs/architecture.md §5에 둔다. 장치마다 읽는 것, 하는 일, 순서·관계, 끄는 법을 적는다.
   - 순서: 확장(프리워밍·KEDA·Karpenter)이 먼저 걸리고, 버티지 못할 때 입장 감축과 게이트웨이 거절이 걸린다. KEDA의 확장 기준(이벤트 루프 지연 등)을 AIMD 감축 기준보다 낮게 두고 설정 검사로 확인한다 [가정, Phase 4 4.6.1에서 값 확정].
   - 이상 파드 퇴출: Envoy 기본 모드는 앱이 과부하로 낸 503도 연속 5xx로 세어, 과부하로 거절하는 파드를 빼고 남은 파드로 부하를 몰 수 있다. 과부하 거절은 퇴출 계산에서 빼는 설정(분리 모드 등)과 최대 퇴출 비율 상한을 4.6.1에서 정한다 [가정]. 이 위험은 확인 필요 사항으로 ADR-0009 상태 줄에 남긴다.
   - 오토스케일이 잘못 움직이면(새 판이 일 없이 CPU를 쓰거나 실패하는 의존성에 요청이 쌓여 계속 늘리는 경우, Workbook 11장) 런북 RB-30으로 멈춘다. KEDA ScaledObject에 `autoscaling.keda.sh/paused-replicas`를 붙이는 미리 만든 패치만 쓴다. 동결 창에서도 쓸 수 있는 긴급 변경 종류로 더한다(POL-041, docs/devops.md §8.4). 명령 11(입장 제어 자동화 정지)과 함께 쓸 수 있다.
4. **경보는 회차·여정으로 묶고, 상위 경보가 울리면 하위 경보 알림을 억제한다(추천 적용)**:
   - 모든 경보에 레이블 `severity`, `kind`(slo·cause·invariant·control·hygiene·legal·field·change·security), 해당하면 `event_id`·`journey`·`dependency`를 붙인다.
   - Alertmanager는 온세일 경보를 `event_id`·`journey`·`severity`로, 그 밖을 `kind`·`severity`로 묶는다. 같은 의존성 경보는 `dependency`로 묶는다.
   - 억제: 예산 SEV1이 울리면 같은 `event_id`·`journey`의 SEV2 알림을 보내지 않는다(`inhibit_rules`, `equal: [event_id, journey]`). 억제된 경보는 지우지 않는다. ops-svc가 Alertmanager 경보 목록 API로 억제 상태를 30초 [가정]마다 읽어, 콘솔에서 그 SEV1 아래 접힌 줄("관련 경보 N건 접힘 · 알림은 보내지 않았습니다")로 보인다 [보완: 구현 방식은 4.2.4에서 확정].
   - 콘솔 경보 패널은 맨 위 SEV1 줄과 두 묶음으로 나눈다. '이 회차 판단'은 고른 회차의 `event_id`를 가진 경보와 온세일 경로 경보(의존성 원인, 입력 없음)이고, '플랫폼·위생·법정'은 그 밖(위생·변경·법정 기한·정산 등)이다. SEV1은 종류와 관계없이 맨 위 줄에 둔다.
5. **경보 규칙과 경로를 시험한다(추천 적용)**: Workbook 4장의 세 층을 따른다.
   - 지표 시험: 서비스 템플릿 단위 시험에서 5xx 응답이 오류 카운터를, 409 경합 패배가 정상 분기 카운터를 올리는지 본다.
   - 규칙 시험: `promtool test rules`로 경보마다 경계 사례를 고정한다. 10배 바로 아래는 안 울림, 2분 창만 넘고 10초 창은 안 넘으면 안 울림, 둘 다 넘으면 울림, 결제 임박 원인, 위생 기준(20ms·26시간·30일·7일), 차례 전 입장 1건, 입력 없음, 차단 비율 경보를 넣는다.
   - 경로 시험: `amtool config routes test`로 SEV1 → 온콜 호출·Slack, SEV2 → Slack·콘솔, SEV3 → GitHub Issues를 확인한다. 억제는 시험용 Alertmanager에 경보를 넣어 억제 결과를 본다 [보완].
   - 모든 경보 규칙에 `runbook_url`·`dashboard_url`이, SLO 경보에는 `explore_url`(결정 13)도 있는지 검사한다.
   - 경보 규칙과 Alertmanager 설정이 바뀌는 PR마다 CI에서 돌린다. 시험이 살아 있는지는 배수를 바꾸면 실패하는지로 본다(V-T9).
6. **인시던트 선언 기준과 포스트모템 기준을 미리 정한다(소유자 결정 '명령 2·3·6부터', 나머지는 추천 적용)**:
   - 선언(하나라도 해당): SEV1. 불변식 위반 의심 1건(오버셀, 이중 결제, 60초 넘은 결제-발권 불일치, 위조 통과, 차례 전 입장). 명령 2·3·6 실행(Go/No-Go의 No-Go로 시작한 명령 2 포함). SEV2가 15분 [가정] 넘게 풀리지 않음. 온세일 예산 50% 이상 사용. 상시 기능에서 사고 하나가 28일 예산의 20%를 넘게 씀(Workbook 부록 B). 경보보다 사람이나 외부(고객 문의·SNS·파트너)가 먼저 발견.
   - 명령 1(목표 조정)은 일상 조작이라 기준에 넣지 않는다.
   - 선언하면 Grafana Cloud IRM 인시던트와 Slack 인시던트 채널을 연다(SEV1은 자동). 선언한 사람이 넘길 때까지 인시던트 지휘관이다.
   - 포스트모템: 선언한 인시던트는 모두 48시간 안에 쓴다(기존 규칙). 사고 하나가 28일 예산의 20%를 넘게 썼으면 P0 후속 조치를 하나 이상 둔다. 같은 종류의 장애가 분기에 28일 예산의 20%를 넘게 쓰면 분기 계획에 P0 항목을 둔다(Workbook 부록 B). 누구나 포스트모템을 요청할 수 있고 commander가 받는다.
   - 탐지 경로: 포스트모템 초안에 첫 증상 시각, 첫 경보 시각, 사람이 안 시각, 탐지 경로(경보·사람·외부)를 둔다. 초안이 감사 로그와 경보에서 첫 경보 시각을 채운다. 분기마다 '경보가 먼저 잡은 비율'을 본다. 사람·외부가 먼저 잡은 장애는 감시 실패로 보고 경보를 고친다.
7. **결제사 기준을 두 단계로 나눈다(추천 적용)**:
   - 임박(SEV2 경보): 1분 창에서 승인 호출 p99가 호출 기한 2초에 닿음(호출의 1% 이상이 기한을 넘음), 결제사 서킷 열림, 결제사 오류율 상승, 한도 초과 응답. 지금 규칙의 뜻을 바꾸지 않고 이름만 분명히 한다.
   - 전환 검토(RB-07, POL-013의 결제 Degraded): 결제 확정 소요(승인 요청을 시작해 승인 결과가 정해질 때까지, 같은 멱등키 재시도와 결과 모름 조회를 포함) p99 5초 초과, 또는 서킷 열림.
   - 새 지표: payment-svc의 `payment_confirm_resolution_seconds{pg}`(히스토그램, 버킷 상한 60초 이상, observability §2).
   - 이유: 승인 호출은 2초 기한에서 끊기므로 호출 p99는 2초를 넘을 수 없다. 5초 기준은 재시도까지 합친 확정 소요로만 잴 수 있다.
8. **판단 위젯마다 연결 판단을 적는다(추천 적용)**: d5 §7.2에 위젯과 연결 판단(명령 번호, 런북, '엔지니어 호출')을 표로 둔다. 운영 명령이 없는 위젯(체감·느린 쿼리·네트워크)은 '진단 힌트' 줄로 모아 판단 숫자와 나눈다. ADR-0067의 위젯 구성과 링크는 그대로다.
9. **명령 4·5에 효과 줄을 둔다(추천 적용)**:
   - 명령 4(대역 차단)·5(봇 판정 강도)가 ack되면 명령 카드와 '적용 중 명령' 줄에 10분 [가정] 동안 효과 줄을 보인다. 차단 비율(엣지·진입 단계 차단 ÷ 진입 시도), 추가 검증 통과율, 이의 제기 수를 실행 전 5분과 나란히 보인다.
   - 실행 뒤 10분 안에 추가 검증 통과율이 실행 전보다 10%p [가정] 넘게 떨어지거나 이의 제기가 10분에 5건 [가정]을 넘으면 SEV2 '차단이 사람을 막고 있을 수 있음'을 낸다.
   - 지표: `entry_blocked_ratio{stage}`(stage: edge·entry). 추가 검증 통과율과 이의 제기 수는 trust-svc 지표를 쓴다.
10. **배경 작업은 대형·중형 온세일 윈도우에 미룬다(추천 적용)**:
    - 대상: 일괄 환불의 새 묶음, 정산 지급 묶음 실행, 파트너 웹훅 재시도, 광고성 알림 묶음, 공연예술통합전산망 재전송, 홈 랭킹 게시.
    - 대형·중형 온세일 윈도우(T-10분~T+60분) 동안에는 새 묶음을 시작하지 않는다. 이미 시작한 묶음은 그 묶음까지 끝낸다. 소형 온세일은 미루지 않는다 [가정].
    - 미루지 않는 것: 거래·안전 알림(발권, 결제 결과), 결과 모름 조회 워커, 감사·접속기록, 보안 사고 통지.
    - 창은 변경 동결 달력과 같은 온세일 일정에서 계산한다(docs/devops.md §8.2). 미루는 시간은 최대 70분이라 환급 3영업일과 지급일 기한에 영향이 없다.
    - 그 밖의 때(예: 소형 온세일 중 일괄 환불이 DB를 붙잡을 때)는 명령 9의 비핵심 목록에 더한 '배경 작업 멈춤' 묶음으로 멈춘다.
    - 결제사 취소 호출이 승인과 같은 한도를 쓰는지는 계약 때 확인한다.
11. **요청 하나를 한 줄의 넓은 기록으로 남긴다(추천 적용)**:
    - 서비스마다 요청이 끝날 때 정규 로그 한 줄을 남긴다. 필수 13필드에 더하는 것은 다음과 같다.
      - `az`·`pod`
      - `app`: 호출한 화면 앱(web·partner·console·scanner)
      - `client`: 브라우저 계열과 주 버전. User-Agent 원문은 쓰지 않는다.
      - `pg`
      - `queuePhase`: lobby·waiting·purchase
      - `flags`: 켜진 릴리스 플래그와 Degraded 모드 이름
      - `dep`: 의존성별 소요 ms
      - `sampleRate`
    - 이 필드는 Loki 라벨이 아니라 본문 필드나 구조화 메타데이터로 둔다 [가정, Phase 4 4.1.1에서 확정].
    - SLO 지표와 같은 경계값을 써서, 로그로 다시 센 값과 지표를 Game Day에서 대조한다.
    - 지표·로그·요청 기록을 나눠 쓰는 지금 저장 구조(ADR-0068)는 그대로다. 저자가 말하는 '넓은 사건 하나를 기준 데이터로' 쪽으로 다가가는 범위만 정한다.
12. **표본 비율을 남기고 경로별 최소 보존을 둔다(추천 적용)**:
    - 꼬리 표본으로 남긴 트레이스와 표본으로 남긴 로그에 표본 비율을 붙여, 집계할 때 비율로 다시 센다. 방법은 4.1.1에서 정한다(`tracestate`의 확률 정보나 정책별 속성 추가 [가정]).
    - 경로 템플릿마다 초당 1건 [가정]은 비율과 관계없이 남긴다(`rate_limiting`·`composite` 정책). 드문 경로(환불·양도)의 성공 사례도 남기기 위해서다.
13. **경보에서 실패 사건으로 바로 간다(추천 적용)**: `OpsAlert`에 `exploreUrl`을 더한다. 같은 시간 창과 그 SLI의 실패 조건으로 미리 채운 Grafana Explore 조회(로그·요청 기록)다. SLO 경보는 필수, 그 밖은 선택이다. 콘솔 경보 줄에 ( 실패 사건 보기 ↗ )를 둔다.
14. **기능 개발 절차에 운영 확인 계측을 둔다(추천 적용)**:
    - docs/architecture.md §8.4를 새로 둔다. 기능 설계서마다 '운영 확인' 표를 ASVS 추적 표와 같은 때(구현 착수 전) 쓴다.
    - 표에 적을 것: 이 기능이 운영에서 제대로 도는지 볼 사건과 필드, SLI, 대시보드 패널, 경보, 배포 뒤 확인 방법(카나리 분석과 배포 주석).
    - 기존 기능 설계서 9편은 wbs 0.3.5에서 채운다.
15. **화면(추천 적용)**:
    - SCR-029에 '판매 중' 상태(ADR-0067 위젯, 연결 판단 줄, 진단 힌트 줄, 차례 전 입장, 결제사 두 단계 기준)와 '제어 입력 없음' 상태를 그린다. 경보 패널을 두 묶음으로 바꾼다.
    - SCR-029의 탭(T-30분 점검·판매 중·종료 후·입장)과 제어 입력 없음은 보기용 보드로 원본 행 아래에 둔다(ADR-0066 결정 1과 같은 방식).
    - SCR-030 '적용 중 명령'에 명령 4 효과 줄을 그린다. SCR-031 리플레이 보드의 결제 그래프를 '결제 확정 소요 p99(재시도 포함)'와 'RB-07 전환 검토 5초' 선, 'SEV2 임박(승인 호출 2초 기한)' 사건으로 고친다.
    - 근거 표(observability §14)에 Release It!와 Observability Engineering 행을 더한다.

## 검토한 대안

| 대안 | 고르지 않은 이유 |
| --- | --- |
| 입력이 없으면 안전 하한으로 줄임 | 시스템은 안전하지만 관측 장애 하나로 판매가 크게 느려진다. 관측이 멀쩡한 실제 과부하는 게이트웨이 동시 처리 상한이 지표와 무관하게 막는다(소유자가 '현재 목표 유지'를 골랐다) |
| 입력이 없어도 마지막 값으로 계속 조절 | 낡은 값으로 늘리면 Force Multiplier·Diskerase와 같은 꼴이 된다 |
| 감축 사이에 고정 쿨다운(예: 30초) | 효과가 나타나는 시간은 체류 시간과 감축 폭에 달려 있다. '새 목표 아래로 내려옴'을 기준으로 하고 최대 시간으로 묶는 편이 덜 늦고 덜 이르다 |
| 오토스케일 정지를 명령 13으로 콘솔에 둠 | 화면·API·ASVS·2인 승인 흐름이 늘어난다. 드문 조작이라 긴급 변경(미리 만든 패치, commander 결정, 포스트모템)으로 충분하다 |
| 인시던트 기준에 명령 1 포함 | 대형 온세일마다 목표 조정이 흔해 거의 모든 회차가 포스트모템 대상이 된다(소유자가 '명령 2·3·6부터'를 골랐다) |
| 지표 저장을 넓은 사건 저장소(ClickHouse 기반)로 바꿈 | ADR-0068이 측정 뒤 판정으로 정했다. 이번에는 지금 구조 안에서 할 수 있는 것(정규 로그 줄, 표본 비율, 조회 링크)만 한다 |

## 결과와 트레이드오프

- 자동 제어가 스스로를 지키는 규칙(입력 없음, 감축 확인 시간)과 경보의 관리 규칙(묶기·억제·시험·인시던트 기준)이 생긴다.
- 입력 없음 동안에는 자동 감축이 없다. 그 사이 실제 과부하가 겹치면 게이트웨이 동시 처리 상한과 사람의 명령이 막는다. 이 한계를 planning/01 §5.2에 적었다.
- 억제는 알림만 줄이고 콘솔에는 접힌 줄로 남긴다. 원인이 다른 두 장애가 같은 여정에서 겹치면 하위 경보를 늦게 볼 수 있다.
- 넓은 로그 줄과 경로별 최소 보존은 로그·요청 기록 저장량을 늘린다. 비용은 4.1.1·4.8.2의 측정에 넣는다 [가정].
- 반영 수치(2026-10-20): ADR 68 → 69. 런북 29 → 30종(RB-30), Game Day 20 → 22종(G-21 제어 입력 끊김, G-22 부하 장치 상호작용). WBS 작업 170 → 172개(0.3.5·4.2.4 신설), 374 → 381.5일이다. 검토 기록은 R-78이다.

## 되돌릴 조건

- 입력 없음이 측정·Game Day에서 잦으면(예: 온세일당 1회 이상) 판정 시간 30초와 입력 경로를 다시 본다. 입력이 자주 끊기는 것이 관측 구조 때문이면 ADR-0068 결정 2(로컬 Prometheus)를 다시 본다.
- 감축 확인 시간 때문에 Game Day에서 SEV1 예산 경보가 더 늦게 꺼지면 최대 시간 2분을 줄인다.
- 억제로 접힌 경보가 포스트모템에서 탐지를 늦춘 원인으로 나오면 억제 규칙을 좁힌다.
- 정규 로그 줄의 저장 비용이 4.8.2 판정을 바꿀 만큼 크면 필드나 표본 비율을 줄인다.

## 남는 한계

- Release It!와 Observability Engineering은 목차와 저자의 공개 글로만 대조했다. 책 본문의 문장과 다를 수 있다.
- 포트폴리오 기간에는 인프라를 설계로만 두므로(ADR-0057), 입력 없음·감축 확인 시간·억제는 로컬 측정 환경의 시험(Q-T42·43, C-T31~34, G-21·22)으로만 확인한다.
- 1인 기간에는 인시던트 지휘관·운영자·소통 담당이 같은 사람이다. 역할 분담과 넘기기는 Game Day 모의 진행으로만 연습한다.
