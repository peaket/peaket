# ADR-0251: 기기 공유 수는 사람 확인 결과와 상관없이 세고, trust-svc의 기기 가명은 identity-svc와 같은 라벨 키 링으로 만든다

- **상태**: 채택(2026-11-09, 추천 적용). BUILD_ORDER BOT-060, wbs 3.2.2 ①.
- **관련**: POL-006, FR-039, FR-072, NFR-022, ADR-0053, ADR-0071, ADR-0147, ADR-0171 결정 4, ADR-0248, ADR-0249, [docs/features/bot-defense.md](../features/bot-defense.md) §3.2·§4.1·§4.9·§17, [docs/data.md](../data.md) §3·§5, [docs/security/secrets-and-keys.md](../security/secrets-and-keys.md) '조사용 가명 키', [docs/security/asvs/bot-defense.md](../security/asvs/bot-defense.md)
- **관련 ID**: B-T16, B-T22~B-T25, ASVS v5.0.0-2.4.1, 16.3.4

## 맥락

- 용어: 기기 가명(`deviceRef`)은 브라우저가 만든 무작위 값 `deviceId`를 비밀 키로 바꾼 값이다. 라벨 키는 KMS(암호 키를 보관하고 대신 계산해 주는 AWS 서비스)가 라벨마다 만들어 주는 비밀 값이고, 파드가 받아 메모리에만 둔다. Lua는 Redis 안에서 한 번에 도는 짧은 프로그램이다. 클러스터 슬롯은 Redis 클러스터가 키를 나눠 담는 칸이다.
- 정본은 `tr:devshare`를 입력 정리 단계에서 Lua 하나로 넣고 센다고 적었다. 첫 구현은 사람 확인을 통과한 pid만 넣도록 바꿨는데, 새 맥락 리뷰에서 봇이 사람 확인에 일부러 실패하면 집합이 커지지 않아 공유 수를 피한다는 지적을 받았다. 정본의 원안으로 되돌렸다.
- BOT-050까지 trust-svc의 기기 라벨 키는 local·ci·demo의 설정값뿐이었다(`hmacDeviceRefsFromEnv`). identity-svc는 BOT-045부터 KMS로 받는다(`InvRefKeyRing`).
- BOT-050이 넘긴 것: HOT-400 뒤 웹이 ASN(인터넷 사업자·데이터센터마다 받은 네트워크 번호)을 보내면 `NetworkScore`가 값을 가져, 통신사 대역의 새 기기 로그인이 다시 `ALLOW`로 적힌다.

## 결정

1. **기기 공유 수는 입력 정리 단계에서 사람 확인 결과와 상관없이 넣고 센다(실패·보류·토큰 없음 포함).** 키 하나만 쓰는 Lua로 넣기와 세기를 한 번에 하고, 다른 피처 읽기와 함께 보낸다(사람 확인 뒤의 Redis 왕복이 없다). 근거는 다음과 같다.
   - 사람 확인에 실패한 요청을 빼면 봇이 일부러 실패해 집합을 키우지 않을 수 있다. 공유 수가 잡으려는 것이 바로 그런 묶음이다.
   - 정상 사용자가 받는 영향은 작다. 자기 기기에서 자기 pid 하나면 수는 1이고, 사람 확인에 실패해도 같다.
   - 남의 기기 집합에 들어가려면 그 기기의 `deviceId`(128비트 무작위 값, 브라우저에만 있다)를 알아야 한다. 알더라도 자기 pid를 넣을 뿐이고, 결과는 차단이 아니라 추가 검증이며 집합은 10분 [가정]이면 사라진다.
   - 같은 판정의 `tr:devacct`는 30일 이력이라 사람 확인 통과 뒤에 쓴다(ADR-0248 결정 8). 공유 수는 10분 신호라 기준이 다르다.
2. **키의 크기와 수명을 묶는다.** 원소는 20개 [가정]까지이고 넘으면 넣지 않고 상한으로 센다. 수명은 첫 원소를 넣을 때 10분 [가정]으로 정하고 뒤 원소가 늘리지 않는다. 비공개 규칙의 `sharedAt`이 상한을 넘는 판은 읽지 않는다(위험이 끝값에 닿을 수 없다).
3. **호스팅·프록시 대역 진입 수는 분류표에 있는 ASN만 센다.** 10초 칸마다 `INCR`하고 칸의 첫 진입에만 수명 30초 [가정]를 둔다. 통신사 대역과 분류표에 없는 ASN은 키를 만들지 않는다. 로그인·추가 검증 제출은 두 키를 건드리지 않는다.
4. **실패는 값 없음과 구분해 드러낸다.** 세지 못한 칸은 `degraded`를 참으로 두고 `trust_feature_read_failures_total{feature}`(`shared`·`entries`)로 센다. 판정은 이어 간다.
5. **라벨 키 코드를 `packages/platform`(`InvRefKeyRing`)으로 옮겨 identity-svc와 trust-svc가 함께 쓴다.** 두 서비스의 값이 같아야 하고(B-T16), 받기·수명·실패 동작이 어긋나면 안 된다. identity-svc의 라벨과 설정 읽기는 그대로 둔다. KMS SDK를 부르는 짧은 어댑터는 서비스마다 둔다(공용 패키지가 SDK를 끌고 오지 않게). 두 서비스에서 함께 바뀌는 동작은 다음과 같다.
   - 받지 못한 라벨만 15·30·60초 [가정]에 흔들림(최대 20% [가정])을 더해 다시 받는다. 세 번 다 실패하면 정기 받기(5분 [가정])로 돌아간다. 정기 받기가 또 실패하면 다시 15초부터다.
   - 고정 문구(`PEAKET-inv-ref-fingerprint-v1`)의 `invRef` 앞 8자를 지문으로 시작 로그와 정보 지표 `inv_ref_key_info{service, label, version, fingerprint}`에 낸다. 키 값은 내지 않는다.
   - 운영·스테이징에 그 라벨의 키 설정이 없으면 `inv_ref_missing_total{reason="NO_KEY"}`로 센다. 시작은 막지 않는다(부가 신호 때문에 서비스를 멈추지 않는다).
6. **키 통일에 데이터 변환은 없다.** 두 서비스는 이미 같은 식을 썼고, 운영을 띄운 적이 없어 옮길 값이 없다. 기기 가명은 요청의 `deviceId`로 그때그때 계산해 토큰·세션에 실리지 않는다. 그래서 진행 중인 세션도 깨지지 않는다.
7. **로그인 판정의 근거는 기기 이력(`hasDeviceHistory`) 하나다.** `NetworkScore`·`ConsistencyScore`·`AgeScore`의 값은 근거로 세지 않는다. 이력이 없는 로그인은 `ALLOW`여도 `degraded`가 참이라 `UNKNOWN`으로 적힌다. 호스팅 대역처럼 위험이 기준값에 닿으면 `decide`가 어차피 `CHALLENGE`를 낸다.

## 배포 단계의 필수 조건

이 저장소의 `deploy`·`infra`에는 아직 없다. trust-svc를 켜기 전에 함께 넣어야 한다.

- `PEAKET_INV_REF_DEVICE_KMS_KEY`·`PEAKET_INV_REF_DEVICE_KEY_VERSION`을 identity-svc와 같은 값으로 넣는다.
- **지문 견주기**: 배포한 뒤 두 서비스의 `inv_ref_key_info{label="device"}`(또는 시작 로그의 지문)를 본다. 판과 지문이 같아야 한다. 다르면 두 서비스의 키가 다른 것이고 기기 가명이 어긋나므로, 온세일 전에 설정을 고친다.
- KMS 키 정책에서 `inv-ref-key-device`의 `kms:GenerateMac`을 trust-svc 신원에게 준다(docs/security/secrets-and-keys.md의 호출 주체).
- trust-svc 파드에서 KMS에 닿는 경로(VPC 엔드포인트 또는 경로)가 있어야 한다.

## 대안

| 선택지 | 고르지 않은 까닭 |
| --- | --- |
| 사람 확인을 통과한 pid만 넣는다(첫 구현) | 봇이 일부러 실패해 공유 수를 피한다. 사람 확인 뒤에 Redis 왕복도 한 번 는다 |
| 응답 뒤에 넣는다(`tr:devacct`처럼) | 왕복은 줄지만, 같은 순간에 몰린 여러 계정이 모두 '1명'으로 읽힌다. 기기 공유 수가 잡으려는 모양이 바로 이것이다 |
| pid마다 넣을 수 있는 기기 수에 상한을 하나 더 둔다 | 키와 왕복이 는다. 값을 바꿔 가며 보내도 키는 10분이면 사라지고, 사람당 호출은 게이트웨이 한도에 묶인다 |
| 라벨 키 링을 trust-svc에 복사한다 | 값이 같아야 하는 코드가 둘로 갈라진다. BOT-065·HOT-146도 같은 코드가 필요하다 |
| 키 설정이 없으면 시작하지 않는다 | 부가 신호 때문에 판정 전체를 멈춘다. 지표와 경보로 드러낸다 |

## 결과

- `DeviceTrust`와 `NetworkScore`가 공유 수·진입 수를 받는다. 운영에서는 KMS로 기기 라벨 키를 받는다.
- 판정마다 Redis 명령이 하나 또는 둘 늘지만 다른 읽기와 함께 보내므로 왕복은 늘지 않는다.
- 두 서비스의 라벨 키가 다르면 지문으로 알 수 있다.

### 되돌릴 조건

- Q-T57에서 공유 수 명령이 Redis CPU 포화를 낳으면 재평가로만 돌리는 안을 다시 본다(ADR-0071 되돌릴 조건).
- 상한 20과 수명 10분은 공유 기기 오탐을 잰 뒤(R2 표본 검토) 다시 정한다.

## 남는 한계

- **다시 받기**: 받지 못한 라벨은 15·30·60초에 다시 받고, 그래도 안 되면 다음 5분 정기 받기가 또 실패할 때 이 순서를 되풀이한다. KMS 장애가 이어지면 라벨마다 5분에 최대 4번 부른다. 지문은 고정 문구의 `invRef` 앞 8자이며 `k1.`로 시작하는 base64url 글자다(16진수가 아니다). 키 교체 실수로 같은 판의 지문이 바뀌면 옛 지문 시리즈가 지표에 남는다.
- **생략 경로**: `deviceId`를 보내지 않으면 기기 공유 수와 기기 이력을 건너뛴다. 값 없음이고 위험 0이며 `degraded`도 아니다. `deviceId` 없음에 위험을 줄지는 소유자 결정이다.
- 쿠키를 나눠 쓰고 `deviceId`를 새로 만드는 봇은 이 공유 수로 세지 못한다.
- 값을 바꿔 가며 보내면 요청 수만큼 공유 수 키가 생긴다. 키마다 10분이면 사라지고 사람당 호출은 게이트웨이 한도(일반 경로 로그인 사용자당 60회/분 [가정], 파드별)에 묶인다.
- 128비트 값을 아는 공격자는 자기 pid로 남의 기기 집합에 들어갈 수 있다. 결과는 추가 검증이다.
- 도쿄 복제 키로 넘기기(서울 KMS 장애 때)는 라벨 키 받기에 없다. identity-svc에도 trust-svc에도 넣지 않았다. 서울 KMS가 멈추면 10분 뒤 기기 신호가 값 없음으로 바뀌고 `degraded`로 드러난다.
- 키 회전의 이음(옛 판 값에서 옮기기)은 BOT-065다. 그때까지 회전하면 trust-svc의 기기 이력은 이어지지 않는다.
- B-T16의 identity 쪽은 두 서비스가 같은 고정 입력과 같은 기대값을 보는 시험으로 닫았다. 두 서비스를 한 프로세스에서 함께 돌리지는 않았다.
- **창 나누기**: 공유 수의 수명 10분은 첫 원소 때만 정하므로, 계정을 10분 경계 양쪽으로 나누면 최댓값이 절반쯤으로 보인다. `deviceId`를 새로 만드는 길보다 어려워 받아들인다.
- **정상 사용자**: 공유 수는 기기 단위라 통신사 NAT는 영향이 없다. 한 브라우저로 가족 계정을 번갈아 쓰는 대리 예매는 비공개 기준값(`sharedFrom`)에 달렸다. 프록시로 분류된 VPN 이용자는 남의 진입 때문에 진입 수가 함께 높아질 수 있다(분류표 내용에 달렸다).
- **분류표에 없는 ASN**: '그 밖'이라 위험 0이고 키를 쓰지 않으며 `degraded`도 아니다. 분류표에 없는 호스팅 대역은 신호가 없다.
- **기기 이력의 뜻**: 로그인 근거 `hasDeviceHistory`는 '이 계정을 아는 기기'가 아니라 '이력이 있는 아무 기기'다. 공격자가 자기 기기에 이력을 쌓을 수 있다. 계정과 묶을지는 뒤에 정한다.
