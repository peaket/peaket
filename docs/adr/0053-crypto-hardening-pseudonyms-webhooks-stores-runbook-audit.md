# ADR-0053: 암호 보강 제안 18건을 반영한다 (로그·탐지 가명 키, 도착 시각 쿠키, 결제사·파트너 웹훅 서명, 저장소 인증, 비상 런북 2인 서명, 감사 로그 해시 체인, 대기열 토큰 추적 표)

- **상태**: 채택 (2026-10-13. 소유자 승인: ADR-0050 검토 때 승인 범위 밖이라 기록만 해 둔 보강 제안 18건(review R-50)에 "반영해주세요." 방식과 세부 수치는 추천 적용(2026-10-13)이고, 측정으로 정할 값은 [가정]으로 둔다.) 2026-10-14 추천 적용(ADR-0062 결정 26): 결정 11의 런북 명령 형식은 `peaket-runbook draft → sign → run`이고 전파에 실패한 명령은 같은 명령 ID로 다시 보낸다(control-tower §5). 2026-10-21(ADR-0075, 소유자 승인): 결정 12의 체인과 5분 앵커·1시간 검증은 그대로 두고, 그 위에 서명한 머클 체크포인트를 매일과 회차 마감에 공개 타임스탬프(OpenTimestamps·비트코인)에 고정해 게시하는 공개 앵커를 더했다. `audit_chain` 행에 비공개 잎 솔트가 생긴다. 2026-10-22(ADR-0086): `audit_chain`의 빈틈 없는 번호와 직전 MAC은 DB 시퀀스가 아니라 머리 행 `audit_chain_head`를 같은 트랜잭션에서 올려 얻는다(docs/data.md §4). 2026-10-26(4차 점검 3부): 결정 1의 기기 식별값 `deviceId`는 브라우저가 처음 쓸 때 만든 128비트 무작위 값이고 기기 지문은 모으지 않으므로, P2로 옮기고 탐지 가명으로 바꾸는 대상은 이 `deviceId`다(docs/frontend.md §3.12, data-classification, ADR-0079 결정 5). 결정 10의 ClickHouse 백업 7일 [가정]은 wbs 4.3.7에서 확정한다(infra §6).

## 맥락

- ADR-0050(2026-10-13)은 암호 사용을 바로잡으면서 승인 범위 밖의 보강 제안 18건을 R-50에 기록만 했다. 소유자가 같은 날 이것을 반영하라고 했다.
- 그사이 같은 날 다른 결정이 일부를 이미 풀었다.
  - ADR-0052는 분석 저장소에 넣는 식별값을 회차별 키 HMAC 가명으로 바꿨다(보강 1 중 분석 쪽).
  - ADR-0051은 현장 스태프 초대 토큰과 기기 승인 확인 코드를 URL 경로에서 URL 조각과 요청 본문으로 옮겼다(보강 17 중 두 경로).
  - 남은 것을 이 ADR이 정한다.
- 문서끼리 대조해 찾은 빈칸은 다음과 같다.
  - 운영 로그의 `pidHash`·`sidHash`와 게이트웨이 접근 로그의 클라이언트 IP 해시가 키 없는 해시다. IPv4 주소는 2^32개뿐이라 모두 계산해 보면 원래 IP로 되돌릴 수 있다. 행동 신호의 `deviceHash`는 브라우저가 만든 값 그대로다. 데이터 분류는 '기기 지문 해시'를 P3(공개 식별자)로, identity는 pid를 '익명 식별자'로 적었다.
  - 도착 시각 쿠키는 'HMAC 서명'까지만 정했고 필드·만료·키 보관·재사용 방지가 없다.
  - 토스페이먼츠 지급 웹훅은 서명 확인만 정했고 발송 시각 허용 범위가 없다. OpenAPI에는 헤더가 하나만 적혀 있다.
  - 파트너로 보내는 웹훅은 'HMAC-SHA256 서명'까지만 정했고 형식과 키 교체 중 겹침 방식이 없다.
  - 포트원 예금주 조회는 URL 경로에 계좌번호 전체가 들어가는데, 나가는 호출의 트레이스·로그 URL을 가리는 규칙이 없다.
  - `PaymentEvent.pgPaymentRef`가 토스 `paymentKey`를 Kafka의 모든 구독자에게 보낸다.
  - TOTP 시드 암호문이 계정에 묶여 있지 않아, 다른 관리 계정 행으로 옮긴 암호문도 풀린다.
  - Auth.js 비밀 하나를 소비자 웹과 파트너 콘솔이 함께 쓴다.
  - MongoDB·ClickHouse·Pyroscope의 인증과 저장 암호화, ElastiCache·MSK의 인증, CloudFront에서 원본으로 가는 구간의 보호가 정해져 있지 않다.
  - ClickHouse 일일 스냅샷이 원시 IP(법정 접속기록)를 S3로 보내는데, data.md는 'S3에 원시 개인정보 저장 금지'다.
  - 비상 런북 2인 서명은 알고리즘과 키 보관이 없고, 런북 CLI가 메시 밖에서 파드의 TCP 포트에 붙는다.
  - NFR-017의 검증 방법은 '해시 체인 검사'인데 체인을 만드는 방법이 없다. 여러 문서가 감사 로그를 '위·변조 불가능' 또는 '위·변조 방지'라고 적었다.
  - 대기열·입장·구매 세션 토큰의 V9·V11 판정이 어느 ASVS 표에도 없고, 양도·취소·환불 표는 팬 재인증 토큰(V9)과 키 폐기(V11)를 판정하지 않았다.
  - 계정 연결·병합 제안 ID가 URL 경로에 있다.
- 원문으로 확인한 사실(2026-10-13):

## 결정

1. **로그·탐지 값은 키를 건 가명으로 남긴다(보강 1·2·3).**
   - 운영 로그와 트레이스의 식별값(pid, 세션 ID, 계정 ID)은 `HMAC-SHA256(로그 가명 키, 값)`의 앞 16바이트(base64url)로 남긴다. 필드 이름은 `pidRef`·`sidRef`·`accountRef`다.
   - 로그 가명 키는 Secrets Manager의 256비트 난수이고 peaket-platform 로거만 쓴다. 30일마다 바꾸고 옛 키는 그 키로 쓴 로그의 보존 기간(Loki 30일)이 끝나면 지운다(추천 적용, 2026-10-13). 키를 지운 뒤에는 그 기간 로그의 가명을 사람과 다시 이을 수 없다.
   - 게이트웨이 접근 로그와 트레이스의 클라이언트 IP는 해시하지 않고 앞부분만 남긴다(IPv4 /24, IPv6 /48, OTel Collector). 원문 IP는 법정 접속기록 저장소에만 둔다(POL-025).
   - 기기 식별값(`deviceId`, 브라우저가 보낸 기기 지문)은 trust-svc가 Kafka·Redis 피처 스토어·ClickHouse에 넣기 전에 `HMAC-SHA256(탐지 가명 키, 값)`으로 바꾼다. 탐지 가명 키는 Secrets Manager의 256비트 난수이고 trust-svc만 쓴다.
   - 탐지 가명 키는 정기 교체를 하지 않는다. 바꾸면 30일 행동 신호와 차단 기기 목록이 끊기기 때문이다. 노출이 의심될 때만 바꾸고, 그때 차단 기기 목록은 새로 쌓인다(추천 적용).
   - 기기 식별값과 기기 지문은 P3(공개 식별자)에서 P2로 옮긴다. 한 브라우저를 계속 가리키고 계정과 이어지기 때문이다. 대기표와 구매 세션에 함께 서명하는 `deviceId`는 짧게 쓰는 운영 값이라 그대로 두고, 로그에는 남기지 않는다.
   - pid를 '익명 식별자'라고 부르지 않고 '가명 식별자'라고 부른다. 키를 가진 쪽이 사람과 다시 이을 수 있는 값이다.

2. **도착 시각 쿠키를 정한다(보강 4).**
   - 엣지 함수가 `v1 ‖ kid ‖ 회차 ID ‖ 도착 시각(밀리초) ‖ CloudFront 요청 ID ‖ sid`를 `HMAC-SHA256(키, "PEAKET-arrival-v1" ‖ 필드)`로 서명해 `__Host-peaket_arr` 쿠키(Secure, HttpOnly, SameSite=Strict, 수명 10분 [가정, Phase 2 2.2.3에서 확정])로 준다. 도착 시각은 함수 시작 시각(`Date`)이다.
   - `sid`는 엣지가 액세스 토큰 쿠키에서 서명 확인 없이 읽는다(엣지 함수에는 ECDSA 검증이 없다). queue-svc는 게이트웨이가 확인한 `sid`와 같은지 본다. 그래서 다른 계정이 받은 쿠키를 넘겨받아 앞자리를 살 수 없다.
   - 엣지에는 추측할 수 없는 난수가 없으므로 무작위 값을 만들지 않는다. 쿠키마다 다른 값은 CloudFront 요청 ID가 맡고, queue-svc는 요청 ID를 `SET NX`로 한 번만 받는다.
   - queue-svc는 MAC(상수 시간 비교), 회차, 10분 이내, `sid` 일치를 확인한다. 하나라도 어긋나면 쿠키를 무시하고 일반 진입으로 처리한다.
   - 키는 kid별로 CloudFront KeyValueStore에 둔다. 원본은 Secrets Manager이고 배포 파이프라인이 넣는다. queue-svc는 Secrets Manager에서 같은 값을 읽는다. KeyValueStore에 쓰고 읽을 수 있는 IAM 주체는 배포 역할뿐이다. 교체(90일)는 함수 재배포 없이 현재 kid를 바꿔서 한다.

3. **토스페이먼츠 지급 웹훅의 헤더와 시각 창을 정한다(보강 5).**
   - OpenAPI에 네 헤더(`tosspayments-webhook-signature`, `-transmission-time`, `-transmission-retried-count`, `-transmission-id`)를 적는다.
   - 서명이 맞고 `transmission-time`이 지금과 5분 [추천 적용, 2026-10-13] 안이면 단건 조회를 바로 한다.
   - 5분을 넘으면 본문을 쓰지 않고 '늦은 웹훅' 보안 이벤트로 남기되, 단건 조회는 한다. 재전송이 발송 시각을 새로 찍는지 문서에 없어서, 창을 넘었다고 버리면 정상 재전송을 놓칠 수 있기 때문이다. 상태는 원래 단건 조회로만 정하므로, 오래된 웹훅을 다시 보내서 바뀌는 것은 조회 횟수뿐이다.
   - 같은 `transmission-id`는 한 번만 처리한다(지금과 같다).

4. **파트너 웹훅을 Standard Webhooks 형식으로 보낸다(보강 6).**
   - 헤더는 `webhook-id`(사건 키, 재전송에도 같음), `webhook-timestamp`(시도 시각, 유닉스 초), `webhook-signature`(`v1,` 뒤에 base64 `HMAC-SHA256(비밀, id.timestamp.본문)`)다.
   - 비밀은 웹훅 엔드포인트마다 따로 만든다. 32바이트 난수에 `whsec_`를 붙여 등록 화면에 한 번만 보여 주고 Secrets Manager에 둔다.
   - 교체: 파트너가 콘솔에서 새 비밀을 만들면 24시간 [추천 적용] 동안 옛 비밀과 새 비밀의 서명을 공백으로 이어 함께 보낸다. 정기 교체 1년(ADR-0050)도 같은 방식이다.
   - 연동 안내: 시각 차이가 5분을 넘으면 거부하고, `webhook-id`로 중복을 거르고, 받은 본문 바이트를 다시 직렬화하지 말고 그대로 검증하라고 적는다.
   - 비대칭 서명(`v1a`, Ed25519)은 지금은 쓰지 않는다. Ed25519는 이 프로젝트가 알고리즘을 고를 때 참고하는 KISA 검증대상 목록에 없다(ADR-0050). 대칭 서명도 엔드포인트마다 비밀을 달리하면, 한 파트너의 비밀이 새도 그 파트너에게 가는 웹훅만 위조된다.

5. **나가는 호출의 URL에서 개인정보를 가린다(보강 7).**
   - 나가는 HTTP 호출의 트레이스·로그에는 경로 템플릿만 남긴다. OTel HTTP 클라이언트 계측의 `url.full`·`url.path`를 경로 템플릿(예: `/platform/bank-accounts/{bank}/{accountNumber}/holder`)으로 바꾸고, 쿼리와 응답 본문은 남기지 않는다.
   - OTel Collector의 2차 가림에 이 경로의 계좌번호 자리를 지우는 규칙을 더한다.
   - 경로에 개인정보가 들어가는 외부 API는 settlement §8 호출 목록에 표시하고 시험(J-T17)으로 확인한다.

6. **Kafka 결제 이벤트에서 결제사 결제 참조를 뺀다(보강 8).**
   - `PaymentEvent`에서 `pgPaymentRef`(토스 `paymentKey`, 포트원 `paymentId`)를 빼고 주문 ID로 잇는다. 결제사 참조는 payment-svc DB에만 둔다.
   - 분석 적재의 금지 필드 검사(ADR-0052)는 그대로 둔다.

7. **TOTP 시드 암호문을 계정에 묶는다(보강 9).**
   - AWS Encryption SDK로 봉투 암호화할 때 암호화 컨텍스트 `{purpose: "peaket-admin-totp-v1", accountId}`를 넣고, 복호한 뒤 컨텍스트가 그 계정과 같은지 확인한다.
   - KMS 키 정책은 이 `purpose` 값이 있을 때만 identity-svc의 복호를 허용한다.
   - 다른 계정 행으로 옮긴 암호문은 풀리지 않는다.

8. **Auth.js 비밀을 앱별로 나눈다(보강 10).**
   - 소비자 웹과 파트너 콘솔이 서로 다른 비밀을 쓴다.
   - 교체는 Auth.js `secret` 배열로 한다. 새 비밀을 앞에 넣고 옛 비밀은 세션 절대 만료(소비자 웹 30일, 파트너 콘솔 24시간)까지 복호에만 쓴다.
   - 키 목록에는 쿠키 암호를 JWE `A256CBC-HS512`(HKDF 유도)로 적는다.

9. **저장소 인증과 저장 암호화를 정한다(보강 11).**

| 저장소 | 인증 | 전송 | 저장 |
| --- | --- | --- | --- |
| Aurora PostgreSQL | 서비스별 DB 사용자, Secrets Manager 관리 비밀번호 30일 자동 교체 | TLS(ADR-0050 결정 6) | KMS |
| ElastiCache(대기열·좌석·세션) | RBAC. 서비스·클러스터마다 사용자를 두고 접근 문자열로 명령과 키 접두사를 제한한다. 기본 사용자는 끈다. 비밀번호는 30일마다 바꾸며, 두 비밀번호를 겹쳐 두어 연결을 끊지 않는다 | TLS 1.2 이상(사용자 그룹의 전제) | KMS |
| MSK | IAM 접근 제어(SASL/IAM, 서비스 계정의 IAM 역할). 토픽별로 쓰기·읽기 권한을 준다. 비밀번호가 없다 | TLS 1.2 | KMS |
| MongoDB(오퍼레이터) | SCRAM-SHA-256. shop 모듈 전용 사용자 | TLS(내부 CA, 평문 연결 거부) | EBS KMS, 백업은 S3 SSE-KMS |
| ClickHouse | 역할별 사용자(원본 적재 잡, dbt, ops-svc 읽기, 분석 읽기, Grafana 읽기), Secrets Manager 비밀번호 | TLS 포트만 열고 평문 포트는 끈다 | EBS KMS, 백업은 S3 SSE-KMS(결정 10) |
| Pyroscope와 관측 백엔드 | 자체 인증을 켜지 않으므로 클러스터 내부 주소만 열고, 메시 정책으로 수집기와 Grafana만 허용한다 | 메시 mTLS | EBS·S3 KMS |

   - CloudFront에서 원본으로 가는 구간: 원본 프로토콜은 HTTPS만, 최소 TLS 1.2다. 원본 NLB 보안 그룹은 CloudFront 관리형 접두사 목록만 받는다. 게이트웨이는 CloudFront가 붙이는 원본 확인 헤더 값(256비트)을 확인한다. 이 값은 90일마다 바꾸고 바꾸는 동안 두 값을 함께 받는다(추천 적용).
   - 스캐너 경로(`gw-scanner`)는 CloudFront를 거치지 않으므로 다른 리스너로 두고 mTLS로 막는다(ADR-0051).

10. **백업에 든 원시 개인정보를 다룬다(보강 12).**
   - 'S3 원시 개인정보 저장 금지'는 분석 레이크와 리포트 버킷의 규칙으로 좁힌다. 저장소 백업은 별도 백업 버킷에 SSE-KMS로 두고, 백업 역할만 읽는다.
   - ClickHouse 백업에는 원시 IP가 든 접속기록 DB와 30일 행동 신호가 들어간다. 그래서 ClickHouse 백업은 7일 [가정, Phase 4 4.1.1에서 확정]만 둔다. TTL로 지운 원시 개인정보가 백업에 7일 넘게 남지 않게 하기 위해서다.
   - 접속기록 DB를 백업에서 빼지 않는다. 잃으면 3개월 보존(POL-025)을 지키지 못한다.

11. **비상 런북 명령에 KMS 2인 서명과 메시 신원을 쓴다(보강 13).**
   - 명령 묶음: `{v, commandId(UUIDv7), command, params, target, issuedAt, expiresAt}`를 JSON 정규화(RFC 8785)한다. 서로 다른 두 운영자가 각자의 KMS 비대칭 키(`ECC_NIST_P256`, `ECDSA_SHA_256`)로 서명한다. 운영자마다 키 하나이고 다중 리전 키다.
   - 서명 권한(`kms:Sign`)은 그 운영자의 IAM Identity Center 역할(MFA)에만 준다. 서명은 CloudTrail에 남는다. 묶음의 유효 시간은 5분 [추천 적용]이다.
   - 대상 서비스는 배포에 들어 있는 운영자 공개키 목록과 역할로 두 서명을 확인한다. 판매 일시정지(명령 3)는 commander 두 명이어야 한다. `expiresAt`과 `commandId` 중복(만료까지 메모리에 둠)도 본다.
   - 연결: 런북 CLI는 운영자 노트북에서 파드에 붙지 않는다. 클러스터 안 `ops-breakglass` 네임스페이스의 Job으로 돌고(서명을 확인한 고정 이미지, Kyverno), 메시 mTLS 신원으로 연결한다.
   - 제어 TCP 포트는 메시 정책과 NetworkPolicy로 `ops-svc`와 런북 Job의 신원만 받는다. Job을 만드는 권한은 비상 역할(MFA, CloudTrail 기록)에만 있다.
   - 기록: Job은 서명된 명령 묶음과 결과를 감사 앵커 버킷(S3 Object Lock)에 바로 쓴다. ops-svc가 복구되면 이것을 감사 체인(결정 12)에 넣는다.

12. **감사 로그에 키를 건 해시 체인과 외부 앵커를 둔다(보강 14·18).**
   - ops 감사 저장소의 감사 기록(운영 명령, 승인 업무, 관리자 접속기록, 권한 변경, 법적 요청, 보안 사고, 가명정보 처리 기록 등)은 같은 트랜잭션에서 `audit_chain`에 한 행을 더한다. 행에는 빈틈 없는 `seq`, 기록 종류·ID, 기록 정규화 값의 SHA-256, `mac = HMAC(감사 체인 키, "PEAKET-audit-v1" ‖ seq ‖ 직전 mac ‖ 기록 해시)`가 들어간다.
   - 감사 체인 키는 KMS HMAC 키(다중 리전)다. ops-svc만 `GenerateMac`, 검증 잡만 `VerifyMac`을 쓴다. DB만 고칠 수 있는 사람은 맞는 mac을 만들 수 없으므로 앵커 앞의 기록을 고치거나 중간 기록을 지우면 드러난다.
   - 앵커: 5분마다 [가정, Phase 4 4.4.1에서 확정] 마지막 `seq`와 `mac`을 S3 Object Lock(컴플라이언스 모드, 7년) 버킷에 쓴다. 기존 일 1회 WORM 사본은 그대로 둔다.
   - 검증: 검증 잡이 1시간마다 [가정] 마지막 검증 지점부터 다시 계산해 앵커와 대조한다. 어긋나면 SEV2 경보와 보안 사고 기록(FR-063)을 낸다.
   - 표현: '위·변조 불가능', '위·변조 방지'를 '변조 탐지(고치거나 지우면 검증에서 드러난다)'로 바꾼다.

13. **ASVS 추적 표를 보탠다(보강 15·16).**
   - `docs/security/asvs/queue-admission.md`를 새로 만든다. 대상은 대기열·입장 토큰, 도착 시각 쿠키, 셔플 커밋, 구매 세션 소지 증명이다. V9 전 절, V11 전 절, V12 전 절, V13.3, V14.3의 L1·L2 35개와 선별 L3 1개를 판정한다.
   - 양도·취소·환불 추적 표에 V9 전 절(팬 재인증 토큰)과 V11 전 절(기기 키 폐기, 1회용 값)을 더한다.
   - 표를 쓰면서 찾은 빈칸 두 개를 함께 정한다(추천 적용, 2026-10-13). 대기열 HMAC 토큰과 도착 시각 쿠키는 서명 대상 앞에 종류 문자열(`PEAKET-lobby-v1`, `PEAKET-preverify-v1`, `PEAKET-queue-v1`, `PEAKET-arrival-v1`)을 넣어 서로 바꿔 쓰지 못하게 한다. 입장 토큰에는 `aud` `purchase`를 넣어 `gw-fan`의 구매 경로만 받게 한다.

14. **URL 경로에 두지 않을 값을 다듬는다(보강 17).**
   - 그 값만으로 권한이 생기는 비밀(토큰, 코드, 비밀번호)은 URL 경로와 쿼리에 두지 않는다.
   - 계정 연결·병합 제안 ID는 경로에 둔다. 연결 제안은 만든 브라우저의 임시 쿠키가, 병합 제안은 로그인 세션과 재인증 토큰이 함께 있어야 쓸 수 있어 ID만으로는 아무것도 하지 못한다. 대신 로그에는 경로 템플릿만 남긴다(결정 5).
   - OAuth `code`·`state`는 프로토콜 규격상 예외다(지금과 같다).

## 대안

| 대안 | 판단 |
| --- | --- |
| 로그의 IP도 키를 건 HMAC으로 | 기각. 운영 로그에서 IP로 하는 일은 같은 망 묶음을 보는 정도라 앞부분이면 충분하고, 수집기에 키를 두지 않아도 된다. 원문 IP가 필요한 조사는 법정 접속기록 저장소로 한다 |
| 탐지 가명 키도 30일마다 교체 | 기각. 차단 기기 목록과 30일 신호가 끊겨 봇 탐지가 약해진다 |
| 엣지 함수가 쿠키마다 무작위 값을 만든다 | 기각. `Math.random()`은 실행 시각으로 시드해 추측될 수 있다 |
| 도착 시각 쿠키를 Lambda@Edge로 | 보류. Node.js `crypto`(난수, ECDSA 검증)를 쓸 수 있지만 CloudFront Functions보다 지연과 비용이 크다. PoC 0.5.3에서 함께 잰다 |
| 토스 지급 웹훅이 시각 창을 넘으면 버림 | 기각. 재전송이 발송 시각을 새로 찍는지 몰라 정상 재전송을 놓칠 수 있다 |
| 파트너 웹훅 비대칭 서명(`v1a`) | 보류. 위 결정 4의 이유. 파트너가 요구하면 다시 본다 |
| Kafka 결제 이벤트의 결제 참조를 암호화 | 기각. 구독자가 쓰지 않는 값이라 빼는 편이 단순하다 |
| 감사 체인을 키 없는 SHA-256으로 | 기각. DB 쓰기 권한만 있어도 앵커 사이의 기록을 다시 계산해 바꿀 수 있다 |
| 런북 서명을 운영자 하드웨어 키(PIV)로 | 기각. 장비와 분실 절차가 늘고, KMS 서명은 IAM 역할·MFA·CloudTrail로 같은 통제를 준다 |
| 런북 CLI를 노트북에서 mTLS 클라이언트 인증서로 연결 | 기각. 인증서 발급·보관이 따로 필요하고 메시 정책 밖의 입구가 생긴다 |
| ClickHouse 백업에서 접속기록 DB를 뺌 | 기각. 접속기록을 잃으면 3개월 보존(POL-025)을 지키지 못한다 |
| 계정 연결 제안 ID도 요청 본문으로 옮김 | 보류. ID만으로는 쓸 수 없어 이득이 작다. 쿠키 결속이 빠지는 일이 생기면 옮긴다 |

## 결과

### 대가
- 데이터: `audit_chain`(seq, 기록 종류·ID, 기록 해시, mac)과 감사 앵커 버킷(S3 Object Lock 7년)이 생긴다. `PaymentEvent`에서 `pgPaymentRef`가 빠지고, `BehaviorSignal.deviceHash`가 `deviceRef`(탐지 가명)로 바뀐다. 파트너 웹훅 비밀은 엔드포인트마다 생긴다.
- 키: 로그 가명 키, 탐지 가명 키, 감사 체인 키, CloudFront 원본 확인 헤더 값, 운영자 서명 KMS 키(운영자마다), 파트너 웹훅 비밀(엔드포인트마다), Auth.js 비밀 2개가 키 목록에 생긴다.
- 운영: 비상 역할과 런북 Job 이미지, 감사 체인 검증 경보, KeyValueStore 키 배포, 저장소별 사용자 관리가 생긴다.
- WBS가 4.5일 늘었다(합계 253.5일에서 258일).
  - 0.3.1 로그 가명(로그 가명 키, IP 앞부분만) 0.5일
  - 2.2.3 도착 시각 쿠키(엣지 함수 HMAC, KeyValueStore 키, 한 번만 받기) 0.5일
  - 2.11.2 저장소 인증·TLS와 CloudFront 원본 보호 1일
  - 4.4.1 감사 체인, 앵커, 검증 잡 1일
  - 4.4.2 런북 KMS 2인 서명, 비상 Job과 메시 정책 1일
  - 5.6.1 파트너 웹훅 Standard Webhooks 서명과 교체 0.5일

### 남는 한계
- 감사 체인: DB 쓰기 권한만 있어도 마지막 앵커 뒤(최대 5분 [가정])의 맨 끝 기록은 지울 수 있다. 지운 뒤 새 기록이 그 번호를 이어 쓰기 때문이다. ops-svc의 KMS 권한까지 있으면 그 구간의 기록을 바꿀 수도 있다. 그 밖의 변조는 다음 검증(최대 1시간 [가정]) 때 드러난다.
- 도착 시각 쿠키: 엣지 거점끼리의 시계 차이는 알 수 없다. 오픈 직후 2초는 어차피 묶음으로 무작위 정렬한다(ADR-0041). 쿠키는 도착 순서만 지키고, 브라우저를 조종하는 봇은 막지 못한다.
- 로그 가명: 로그 가명 키를 가진 운영자는 30일 안의 로그를 사람과 이을 수 있다.
- 파트너 웹훅: 파트너 쪽에서 비밀이 새면 그 파트너에게 가는 웹훅은 위조될 수 있다.
- 비상 런북: KMS나 IAM Identity Center가 멈추면 서명할 수 없어 런북도 쓸 수 없다.
- 탐지 가명 키는 정기 교체를 하지 않는다.

### 되돌릴 조건
