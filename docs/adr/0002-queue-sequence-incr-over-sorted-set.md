# ADR-0002: 대기열 순번은 INCR + 빠진 번호 비트맵, 앞 인원은 대기표 기준으로 정확히

- **상태**: 채택 (2026-10-07). 같은 날 '근사치 표시'에서 '정확한 인원 표시'로 개정. 2026-10-08 입장 자리 처리를 ADR-0005에 맞춰 수정. 2026-10-26(4차 점검 3부): 결과의 '완전히 정확하다'는 줄에서 빠지는 사건이 모두 기록될 때의 말이다. 순번 발급 응답을 잃은 번호는 서버가 바로 빠진 번호로 알 수 없어 작은 오차가 남는다(POL-007). 추가 검증을 통과해 원래 번호로 돌아온 사람은 빠진 번호 비트를 끄지 않으므로, 다른 대기자의 앞 인원에서 빠진 채 입장한다(planning/01 §5.2, docs/data.md §3, ADR-0062). 결과의 마이크로 배치 `INCRBY`는 단일 키 병목이 PoC(Q-T5)에서 재어질 때만 쓴다(docs/features/queue-admission.md §3). 2026-10-28(기술 검토 중간-030, 소유자 승인 '추천안 동의'): 결과의 '장애 조치 때 같은 번호가 다시 나가지 않게 세대 번호를 넣는다'에서 건너뛰는 양은 '장애 직전 초당 발급 × 측정한 복제 지연 p99.9 × 2 [가정]'이다. 건너뛴 구간은 `q:{event:E}:skipped`에 따로 적어, 앞 인원 계산과 입장 비율에서는 빠진 번호로 세고, 입장 확정에서는 그 구간의 옛 세대 대기표(장애 전에 받은 진짜 대기자)를 받는다. 그 진짜 대기자 수만큼 뒤 대기자의 실제 대기가 예상보다 길어지는 오차가 남는다(docs/features/queue-admission.md §3·§4·§5·§9, docs/data.md §3). 2026-10-28(기술 검토 낮음-135, 소유자 승인 '추천안 동의'): 결정 3의 '전용 비트맵(Roaring Bitmap 등)'은 Redis 문자열 비트맵으로 읽는다. 번호마다 1비트를 `SETBIT`로 켜고, 1초마다 대기 상태 파일을 만들 때 구간 1,000개 번호의 125바이트를 `GETRANGE`로 읽는다. 키는 `q:{event:E}:removed`이고(docs/data.md §3), Redis 기본 명령 밖의 모듈 자료 구조는 쓰지 않는다. 2026-10-29(원문 확인): ElastiCache 지원 명령 목록에 모듈을 올리는 명령이 없고 기본 밖 확장은 JSON·Bloom 필터·검색뿐이라, 결정 3을 Redis 문자열 비트맵으로 읽는 2026-10-28 상태 줄이 맞다. 2026-11-02(wbs 0.9.1 규칙 모델 검사): 장애 전환 뒤 카운터 건너뛰기·세대 올리기(RB-05)가 끝나기 전에 들어온 진입이 같은 세대의 번호를 다시 낼 수 있음을 명세 검사가 찾았다(`specs/queue.qnt`의 `queue_canon`, docs/verification.md §2.6). RB-05가 끝날 때까지 번호를 내지 않는 규칙을 더할지는 소유자 결정 대기다(PROGRESS OPEN[13]).
- **관련**: 설계서 섹션 6 '대기열'·'입장 흐름', ADR-0003(적응형 폴링), ADR-0005(입장 확정), 섹션 10 K1, 섹션 2 B4(재접속 순번 보존)
- **관련 ID**: FR-006, FR-007, POL-007, NFR-002, NFR-025, SCR-008

## 맥락

대기 화면은 '대기열에 잔류 중인 사용자 중 내 앞에 몇 명이 대기하고 있는지'를 **정확한 수치**로 표시해야 한다. 예약 단계로 진입 완료한 사용자는 집계 대상에서 제외한다. 상태 조회는 폴링 방식으로 동작하며, 대기열 후미일수록 주기를 길게, 입장 임박 구간일수록 짧게 차등 적용한다(ADR-0003).

정확한 인원을 산출하기 위해서는 우선 '대기열 잔류 인원'의 기술적 정의를 확립해야 한다.

| 기준 | 대기표 기준 | 접속 기준 |
| --- | --- | --- |
| 대기열에 있는 사람 | 대기표를 받았고 아직 입장·취소·무효 처리되지 않은 사람 | 최근 몇 초 안에 서버에 응답한 사람 |
| 화면을 끈 사람 | 포함. 돌아오면 자기 순서 그대로 | 제외. 돌아오면 다시 포함되어 다른 사람의 앞 인원이 늘어남 |
| 재접속 순번 보존(B4) | 맞음 | 충돌 |
| 쓰기 부하 | 줄에서 빠지는 사건이 생길 때만 기록 | 100만 명의 '살아 있음' 신호를 계속 기록(초당 수만 건) |

대기 순번을 관리하는 데이터 구조 및 연산 방식 역시 두 가지 후보를 비교 검증했다.

| 기준 | `INCR` 순번 + 빠진 번호 비트맵 | Sorted Set(`ZADD` + `ZRANK`) |
| --- | --- | --- |
| 줄 서기 비용 | O(1) | O(log N) ([Redis 문서](https://redis.io/docs/latest/commands/zadd/)) |
| 앞 인원 조회 | 번호 1,000개 구간마다 같은 파일을 만들어 CDN이 캐시. 브라우저가 계산 | 사람마다 `ZRANK`로 물어야 해 응답이 사람마다 다름. CDN 캐시 불가, 초당 약 5.3만 조회가 origin과 키 하나에 몰림 |
| 데이터 구조 | 숫자 하나 + 비트맵(100만 번호에 125KB) | 원소 100만 개짜리 큰 키 하나. 키 하나는 한 슬롯에만 있어 여러 서버로 나눌 수 없음 |
| 정확도(대기표 기준) | 정확함. 줄에서 빠지는 사건을 모두 서버가 처리하므로 빠짐없이 기록 | 정확함 |

## 결정

1. **'대기열 잔류 인원'은 대기표 발급 기준으로 정의한다.** 접속 여부를 지속 추적하지 않으므로 하트비트 성격의 대규모 쓰기 부하가 발생하지 않으며, 재접속 순번 보존 원칙(B4)과도 정확히 부합한다.
2. **대기 순번은 Redis 단일 원자 카운터 `INCR`로 발급한다.**
3. **대기열 이탈 번호는 전용 비트맵(Roaring Bitmap 등)에 기록한다.** 대상 이벤트는 대기 자진 취소, 의심 계정의 추가 검증 큐 분리 격리, 1인 1순번 규칙 위반에 따른 무효화, 네트워크 재시도에 따른 빈 번호 등이다. 쓰기 I/O는 해당 이탈 사건이 발생할 때만 국소적으로 일어난다.
4. **전방 대기 인원은 정확한 수치로 계산한다.** 계산식은 `(serving과 내 번호 사이의 번호 수) − (그 사이에서 빠진 번호 수)`이다.
   - 번호 1,000개 구간마다 대기 상태 정적 스냅샷 파일을 1초 주기로 생성하고, 클라이언트는 자신이 속한 대기 상태 파일만 폴링한다.
   - 파일 명세: serving 번호, serving까지 누적 결번 수, 구간 시작 전까지 누적 결번 수, 해당 구간 1,000개 번호의 결번 비트맵(125바이트).
   - 동일 구간 사용자는 완전히 동일한 정적 파일을 요청하므로 CDN 에지에서 효율적으로 캐싱된다.
5. **Sorted Set은 데이터 크기가 작고 개별 원소에 만료 시각이 바인딩되는 도메인에 한정하여 적용한다.** 예매 좌석 선택 단계에 진입한 최대 5,000명의 세션 관리(점수 = 만료 시각. 입장 확정 시점에는 첫 사용 기한, 구매 세션 진입 이벤트 이후에는 최대 체류 시각이며, 세션 종료 이벤트 시 즉시 제거, ADR-0005) 및 좌석 홀드 만료 인덱스에 국한한다.
6. Sorted Set + `ZRANK` 기반 설계는 v0의 실패 베이스라인으로 남겨 KPI K1 측정 시 비교 데이터로 활용한다.

## 결과

- 앞 대기 인원은 파일 갱신 시점(최대 1초 전) 기준으로 완전히 정확하다. 사용자 브라우저 화면에는 개별 폴링 주기(1~20초)에 따른 지연만큼 순차적으로 반영된다.
- 원본(origin) 서버 요청량은 사용자 전체 규모나 폴링 빈도와 무관하게 1초당 대기 상태 파일 개수(100만 번호 기준 약 1,000건) 수준으로 상한이 고정된다.
- 브라우저를 닫은 채 복귀하지 않는 사용자도 본인 순번이 도달할 때까지는 전방 대기 인원에 정량 산입된다. 이들은 순번이 도래해도 실제 입장을 수행하지 않으며, 좌석 선택 입장 자리는 첫 예매 API 요청 시점에만 원자적으로 배정되므로 유효 좌석 자원을 점유하지 않는다(ADR-0005).
- 예상 대기 시간은 실제 물리적 입장 속도가 아니라 serving 번호의 전진 속도를 기준으로 산출한다. 미진입 이탈자가 존재할 경우 serving 번호 전진 속도가 실제 입장 속도보다 빠르게 증가하기 때문이다.
- 단일 순번 카운터로의 요청 집중 현상은 초당 마이크로 배치 `INCRBY` 기법으로 분산한다. 인프라 장애 조치(failover) 시 동일 번호가 중복 재발급되지 않도록 대기표 페이로드에 세대 번호(generation)를 포함한다(설계서 섹션 6 'Redis 구성').

## 재검토 조건

- 실시간 접속 연결 유지 기준의 인원 표기가 비즈니스 핵심 요구사항으로 확정될 때
- 장기 이탈자가 급증하여 화면 표시 인원과 실제 유효 대기자 간 괴리로 인한 CS 문의가 시스템 허용치를 초과할 때. 단, 예상 대기 시간은 serving 진행 속도 기반으로 산출되므로 해당 편차의 영향이 제한적이다.
