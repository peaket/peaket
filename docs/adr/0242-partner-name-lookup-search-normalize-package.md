# ADR-0242: 파트너의 아티스트·공연장 찾기는 공용 한글 규칙 패키지와 파드 메모리 목록으로 한다

- **상태**: 채택(2026-11-09). 한글 검색을 이 단계에 함께 만드는 것은 소유자 결정("한글 검색 먼저 구현")이고, 세부는 추천 적용이다. BUILD_ORDER HOT-180 ①.
- **관련**: [docs/features/search.md](../features/search.md) §3·§4.1, ADR-0093, ADR-0094 결정 6, ADR-0127, ADR-0198
- **관련 ID**: FR-022, SR-T1, SR-T2, SR-T3

## 맥락

- 공연 등록 1단계의 공연장·아티스트 찾기는 계약에 '정규화·낱자·초성'으로 적혀 있다. 그 규칙의 공용 코드(`packages/search-normalize`)와 읽기 모델(`search_term`)은 검색 백엔드 HOT-270의 일로 남아 있었다.
- 아티스트·공연장은 운영자가 관리하는 짧은 목록이고, 파트너 등록 화면에서만 찾는다. 공연 검색처럼 트래픽이 몰리는 경로가 아니다.

## 결정

1. **`packages/search-normalize`를 지금 만든다**: 정규화, 비교 값(띄어쓰기 없앤 값·낱자·초성), 일치 등급, 이름 찾기를 §3·§4.1대로 둔다. 낱자·초성은 정본이 고른 es-hangul 2.4.0을 정확한 판으로 쓴다(출처 증명 있음). 브라우저와 서버가 같은 코드를 쓰고, 시험 벡터도 함께 쓴다. HOT-270은 이 패키지를 그대로 쓴다.
2. **이번 경로는 파드 메모리 목록에서 찾는다**: `artist`·`place`와 지우지 않은 `search_alias`를 읽어 비교 값을 미리 만들어 두고 30초 [가정] 뒤 새로 읽는다. 읽기가 실패하면 앞 목록을 그대로 쓴다. `search_term` 표를 지금 만들면 그 표를 채우는 쓰기(운영자의 아티스트·공연장 관리)가 아직 없어 빈 표가 된다.
3. **순서**: 일치 등급 → 가나다 → ID다(§4.1). 판매 상태·관심도는 공연 후보의 기준이라 쓰지 않는다. 대상 하나의 이름과 다른 이름이 함께 맞으면 더 높은 등급으로 한 번만 낸다.
4. **자음·모음만 친 입력의 중간 일치는 보지 않는다**: 낱자·초성은 앞부분(이름 전체 또는 낱말)으로만 본다(§3.2).
5. **커서는 마지막 항목의 (등급, 이름, ID)다**: 위치 값이면 파드마다 목록이 조금 달라 쪽 사이가 겹치거나 빠진다(guidelines §3).
6. **이름 목록을 나눠 만든다**: 비교 값은 500건마다 다른 요청에 차례를 넘겨 만들고, 가나다 차례로 미리 정렬해 찾을 때는 등급으로 모으기만 한다.
7. **낱말 앞부분은 그 낱말부터 이름 끝까지와 견준다**: 입력이 띄어쓰기를 넘어도(`체조 ㄱ`) 맞는다. 한/영 변환은 소문자로 바꾸기 전 값을 먼저 쓴다(Shift로 친 `Rhc` → `꽃`).

## 결과

- 파트너가 `ㄹㅁ`, 조합 중인 `룸`, 영문 표기, 한/영이 뒤바뀐 `fnaps`로도 찾는다.
- 파드마다 목록을 메모리에 둔다. 아티스트·공연장은 합쳐 수만 건 아래로 본다 [가정].
- 운영자가 이름을 고치면 찾기에는 30초까지 늦게 보인다.

### 넘긴 것

- `search_term` 표, 메모리 사전의 이분 탐색·역색인, 공연 검색은 HOT-270이다. 그때 이 경로를 사전으로 옮길지 정한다.

## 다른 선택지

| 길 | 고르지 않은 까닭 |
| --- | --- |
| 이름 포함 검색만 먼저 한다 | 소유자가 한글 검색을 먼저 만들기로 정했다. 계약과도 맞지 않는다 |
| `artist`·`place`에 낱자·초성 칸을 더한다 | 칸을 채우는 쓰기가 아직 없고, 정본의 `search_term`과 겹친다 |
| SQL에서 낱자를 푼다 | 브라우저와 같은 코드라는 정본 규칙을 지키지 못한다 |
