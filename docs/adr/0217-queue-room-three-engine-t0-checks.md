# ADR-0217: 대기실 T=0 세 엔진 검사를 같은 출처 검사 틀과 가짜 API의 검사 기록으로 한다

- **상태**: 채택(2026-11-06, 추천 적용). BUILD_ORDER HOT-347.
- **관련**: [docs/frontend.md](../frontend.md) §5.17 실행 도구 표·FE-T3·FE-T4·FE-T15, §5.1, §5.9, [tools/web-checks/README.md](../../tools/web-checks/README.md), ADR-0207, ADR-0208, ADR-0211 결정 5, ADR-0216 결정 1
- **관련 ID**: FE-T3, FE-T4, FE-T15

## 맥락

- HOT-345(ADR-0216 결정 1)가 다음을 이 단계로 넘겼다. 대기실의 T=0 두 호출(진입·입장 확정)과 대기열 파일 GET에 사전 요청이 없는지(FE-T3)를 세 엔진 실제 브라우저로 보는 일이다. `AbortSignal.any`가 없는 페이지의 시간 초과·화면 떠남(FE-T15)과 폴링 간격·셔플 고정 지연·200의 `Retry-After` 무시(FE-T4)도 넘겼다.
- 다음이 정해지지 않았다.
  - 운영 빌드를 같은 출처로 띄우는 검사 경로가 없다(ADR-0211 결정 5는 개발 서버만 다룬다).
  - Playwright 1.64.1은 경로를 가로채면 CORS 사전 요청에 스스로 답하고 사건을 내지 않는다. 그래서 브라우저 쪽에서는 사전 요청 수를 셀 수 없다.
  - §5.17 도구 표는 FE-T4를 jsdom 칸에, FE-T15를 Vitest 브라우저 모드 칸에 두었다. BUILD_ORDER는 'Playwright 세 엔진'이라 적었다.
  - 숨긴 탭을 만들 브라우저 API가 없다.

## 결정

1. **같은 출처 검사 틀**: `tools/web-checks/lib/same-origin.mjs`(127.0.0.1:4130)가 운영 www 배포처럼 경로를 나눈다.
   - 대기실 셸 경로와 `/_q/*`: 대기실 검사 빌드(`apps/web/queue-room/dist-check`, `node queue-room/build.mjs`). 이 빌드는 운영 빌드와 같고 대기열·대기열 파일·팬 API 출처만 검사용 가짜 API(127.0.0.1:4011)다. 셸에는 A′ 묶음 헤더를 붙인다.
   - 좌석맵 파일: 정적 원본(가짜 API)
   - 그 밖: 소비자 웹 운영 서버(4101). 이 검사 묶음은 웹을 띄우지 않아 그 경로는 502다(입장 뒤 좌석 화면으로 옮겨 가는지만 본다). 공연 상세에서 들어가는 검사가 생기면 webServer에 더한다.
   - 개발용 가짜 API(4010)와 포트를 나눠, 이미 떠 있는 개발 서버를 재사용하지 않는다.
2. **검사 기록**: 가짜 API가 받은 요청을 메서드·경로·출처·시각·끊긴 시각으로 남긴다(`GET /__mock/requests`, `logReset=1`, 최근 5,000건).
   - 사전 요청 수(FE-T3), 폴링 간격(FE-T4), 시간 초과로 끊긴 시각(FE-T15)을 서버 쪽에서 센다.
   - 이 검사는 `page.route`를 쓰지 않는다.
   - FE-T3에는 대조를 둔다. 사용자 머리가 있는 쓰기를 한 번 보내, 엔진마다 사전 요청이 기록에 남는지 확인한다.
   - 상태 바꾸기 둘을 더한다: 진입 멈춤(`queueEntry=hang`, 답하지 않음), 200 대기 상태 파일의 `Retry-After`(`queueStateRetryAfter`).
3. **도구 칸**: FE-T3·FE-T4·FE-T15의 브라우저 칸은 이 Playwright 세 엔진 검사(`tools/web-checks/queue-room/`)다.
   - §5.17 표의 jsdom(FE-T4)·Vitest 브라우저 모드(FE-T15) 칸은 대기실 밖 React 앱의 단위·Web API 시험으로 남는다.
   - 대기실의 상태 기계·fetch 층 단위 시험은 node 시험이 본다(`apps/web/queue-room/test`).
4. **숨긴 탭**: `visibilityState`·`hidden`을 덮어 흉내 낸다. 실제 숨긴 탭의 타이머 제한은 재현하지 못한다.
   - 숨긴 탭 최소 5초(§5.9)는 하한처럼 위로만 흔든다(5~6초). 정본 의사 코드가 바닥 뒤에 ±20%를 걸어 4초까지 내려가던 것을 이 단계에서 고쳤다(§5.1 nextDelayMs).
   - 간격 단언은 정본의 지터를 넣는다. 숨긴 탭은 4.9초 이상, 가까운 대기는 0.35~1.5초, 300초 안은 마지막 세 간격이 3.8~6.5초다(처음 몇 번은 진입 직후·보이게 될 때 깨워 묻기라 뺀다).
5. **셔플 고정 지연**: 저장소에 로비 참가 값을 두고(사람 확인 없이) 결과 파일 GET 시각을 '발표 시각 + 토큰 해시로 정한 지연'과 견준다.
   - 분산 창 60초와 5~15초 지연이 나오는 고정 토큰(결정적으로 고른다)을 쓰고, 저장소가 따로인 문맥 둘이 같은 시각에 받는지 본다.
   - 같은 PC의 벽시계이고 로비 경로는 서버 시각 표본을 받지 않아 보정이 0이므로, 오차는 타이머 지연뿐이다. −0.1초~+0.8초를 허용한다.
6. **화면 쪽 중단(FE-T15)**: 문서를 버리면 브라우저가 진행 중인 fetch를 모두 끊어 화면 신호를 잇는지 보지 못한다. 그래서 다시 보낸 진입이 걸린 동안 같은 브라우저의 다른 탭이 새 대기표를 저장하고 `stored`를 방송해, 이 탭이 문서를 버리지 않고 진행 중 일을 끊게 한다.
   - 1.5초 안에 끊기는지 본다(5초 시간 초과가 아니다).
   - fetch 거절 이름(시간 초과 TimeoutError, 화면 쪽 AbortError)을 본다. WebKit의 fetch는 신호의 이유를 넘기지 않고 늘 AbortError로 거절하므로, 대기실 fetch 층이 끊긴 요청을 신호의 이유로 바꿔 던진다(단위 시험이 본다).
7. **CI**: 화면 잡 `ci-web.yml`에 `queue-room` 잡을 둔다. 판을 고정한 Playwright 컨테이너에서 대기실 검사 빌드 뒤 세 엔진으로 돈다.
   - 이 PC의 Firefox는 정식 판 BiDi(`PEAKET_FIREFOX=system`)로 돈다(README '실행').

## 결과

- 대기실 T=0 경로가 세 엔진에서 사전 요청 없이 나가고, 옛 엔진에서도 시간 초과·화면 떠남을 오류 없이 다루며, 폴링·셔플 지연이 정본 간격 안임을 CI가 막는다.
- 남는 한계:
  - 숨긴 탭의 실제 타이머 제한
  - 요청 우선순위(`priority: "low"`)는 이 틀로 보지 않는다(Chromium 개발자 도구 프로토콜로만 보인다)
  - 여러 탭 세 엔진 검사는 HOT-348이다.

## 다른 선택지

- 브라우저의 요청 사건으로 사전 요청 세기: 경로를 가로채는 순간 Playwright가 사전 요청에 답해 0으로 보인다. Firefox(Juggler)는 가로채지 않은 OPTIONS 사건을 버린다. 그래서 서버에서 센다.
- 개발 서버로 검사: 개발 빌드는 사람 확인 시뮬레이터·개발 출처를 써 운영 빌드와 다르다. 운영 빌드에 출처만 바꾼 검사 빌드를 쓴다.
