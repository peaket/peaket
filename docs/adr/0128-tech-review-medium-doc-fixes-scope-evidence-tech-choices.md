# ADR-0128: 기술 검토 중간 항목의 문서 수정 묶음 1 — 범위·일정·증거와 기술 선택(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 중간 항목(영역: 가. 범위·일정·증거, 나. 원문 학습 지도에서 온 과한 선택(중간), 차. 소유자 전제로 높음에서 내린 것(2026-10-27))에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 방향은 소유자 결정(추천안 승인)이고, 검토가 안을 고르지 않은 곳의 선택과 값 같은 세부는 추천 적용이다. 측정 전 값은 [가정]으로 표시했다) 2026-10-30(ADR-0165, 소유자 결정): 중간-112의 '저장소 14개를 남긴다'는 저장소 4개(모노레포)로 바뀌었다. 작업 공간 스크립트와 저장소를 건너는 변경 시연은 없애고, 운영 판과의 호환 검사 시연으로 바꾼다. 2026-11-01(정합 점검, ADR-0177 해설서 검토 네 번째 묶음): 위 2026-10-30(ADR-0165) 줄의 저장소 4개는 같은 날 ADR-0169로 공개 모노레포 `peaket`과 비공개 봇 저장소 `peaket-bots` 둘이 됐다(docs/devops.md §2.1, docs/architecture.md §10).
- **관련**: review/tech-review.md(중간-001·중간-002·중간-003·중간-004·중간-005·중간-006·중간-007·중간-008·중간-009·중간-014·중간-015·중간-016·중간-020·중간-021·중간-023·중간-024·중간-025·중간-026·중간-111·중간-112·중간-113), review/consistency-review.md R-146, 00-summary.md §6·질문 61, 같은 날 새 ADR-0100~0126(새 결정이 필요한 항목)

## 맥락

2026-10-27 기술 검토 2판은 설계의 모든 기술·기법을 시니어 개발자 관점에서 따져 높음·중간·낮음 항목으로 냈다. 2026-10-28 소유자가 남은 항목을 모두 추천안대로 고치라고 정했다. 새 결정이 필요한 항목은 따로 ADR(0100~0126)을 썼고, 이 ADR은 정본 문서를 고쳐 반영한 중간 항목 21건의 문제와 결정을 한곳에 모은다. 검토 문서에서는 이 항목들의 본문을 지우고 이 ADR을 가리키는 한 줄만 남겼다(지운 본문은 git 이력에 있다).

## 결정

항목마다 검토의 추천 수정을 따랐다(소유자 승인). 검토가 안을 여럿 내고 고르지 않은 곳은 고른 안과 이유를 적었고 '추천 적용'으로 표시했다. 정본에는 `(추천 적용 2026-10-28, 기술 검토 <번호>)`로 표시했다.

### 가. 범위·일정·증거

#### 중간-001 WBS 일수와 ±20% 범위에 근거가 없고, 실제 개발 속도를 반영하지 않는다
- **문제**: 447일(±20%)은 템플릿 규칙에서 왔고, 관측 스택 전체(4.1.1) 4.5일, 메시 매니페스트 + Redis 3클러스터 + Aurora 구성(2.11.2) 5일, 명령 수명주기 + 2인 승인 + 이벤트 소싱 감사 + 해시 체인 + 앵커 + 검증 잡(4.4.1) 6.25일처럼 한 줄에 큰 일이 몰린 추정이 있다. 소유자 전제(AI로 빠르게 개발)라면 실제 속도는 이 일수와 크게 다를 수 있는데, 마일스톤 숫자(M2 40.4주, 전체 89.4주)가 문서에서 사실처럼 쓰인다.
- **결정**: WBS의 일수·누적 주를 '어림(실측 전)'으로, ±20%를 표시용 폭으로 밝힌다(소유자 승인). 처음 끝내는 묶음 뒤 실제 속도로 다시 어림하고 그때 버퍼·작업 성격별 범위를 정하며, 3일 넘는 작업은 착수 전 1~3일 단계로 나눈다(추천 적용).
- **바꾼 문서**: wbs/wbs.md §1·§3·§8, planning/00 §6, planning/01 §5.2, guide/12 §6
- **남는 한계**: planning/01 §5.2 'WBS 일수의 남는 한계' 행(실측 전 어림, ±20% 근거 없음, 다시 어림·단계 나누기)

#### 중간-002 비율·백분위 목표와 카나리 판정에 최소 표본 규칙이 없다
- **문제**: 봇 오탐(NFR-022)만 표본 수를 정했고, 다른 비율 목표는 시행 수 없이 판정한다. 실패 0건으로 '99.9% 이상'을 95% 신뢰로 말하려면 약 3,000번(3 ÷ n), '0.1% 미만'도 약 3,000번이 필요하다. 표본이 적은 백분위는 사실상 최댓값이다.
- **결정**: 비율·백분위 목표는 정확 이항 단측 95% 상한으로 판정하고 최소 시행 수를 적는다(원칙 6, 소유자 승인). 시험별 3,000번, K8 최댓값, 카나리 오류 5건·꼬리 10건·25% 단계 지연 비교는 추천 적용이다.
- **바꾼 문서**: planning/02 §3.1·NFR-004·008·010, planning/01 §3.1, perf-ledger §7·§8, devops §6.2·§14, control-tower·seat-hold·offline-gate 시험 표, observability §12, ADR-0054 상태 줄

#### 중간-003 좌석맵 성능(K5)을 포트폴리오에서 어떻게 판정할지 규칙이 없다
- **문제**: 정본은 'RUM p75가 판정, 랩 숫자는 회귀 방지'(frontend §5.8)인데 포트폴리오에는 실제 사용자가 없어 RUM 판정이 불가능하다. 결국 K5는 영원히 판정되지 않거나, 합성 세션을 RUM이라 부르게 된다. 또 측정 도구에 Lighthouse CI를 넣었지만 탐색 모드는 한 번의 페이지 적재만 봐서 INP를 내지 못한다.
- **결정**: 포트폴리오는 랩 p75, 운영은 RUM p75로 나눠 판정한다(소유자 승인). 프로필·반복 20회·INP 도구·LoAF 기록은 추천 적용이다.
- **바꾼 문서**: planning/01 §3.1 K5, planning/02 §3.1·NFR-012, docs/frontend.md §1·§5.8, planning/03 §4, guide/17
- **남는 한계**: guide/17 한계 표에만 더함(포트폴리오는 RUM 판정 불가 → 랩 판정). planning/01 §5.2 줄은 없음

#### 중간-004 본인확인 '실제 연동'이 1인 포트폴리오에서 가능한지와 대신할 방법이 없다
- **문제**: wbs Phase 3 마일스톤 M3의 완료 기준에 "본인확인 실제 연동"이 있고 3.1.1은 "본인확인 업체 실연동"이다. 휴대폰 본인확인기관(또는 대행 결제사 채널)은 일반적으로 사업자 계약을 요구하는데, 1인·5만 원 예산의 포트폴리오가 계약할 수 있는지 문서에 없다. 포트원 문서에서도 본인인증 시험 채널 안내를 찾지 못했다. 계약을 못 하면 M3를 끝낼 수 없다.
- **결정**: 포트폴리오 완료 기준을 모의 기관으로 끝까지 시험하는 것으로 바꾸고, 실제 기관 연동은 계약이 가능할 때 하는 조건부 작업으로 둔다(소유자 승인). 시험 채널은 확인 필요다.
- **바꾼 문서**: docs/features/identity.md §12·§13, planning/01 §5.2, review/open-items.md, wbs(메인 세션)
- **남는 한계**: planning/01 §5.2 '본인확인기관 연동의 남는 한계' 행(모의 기관과 실제 기관의 응답 형식·암호화·창 동작 차이)

#### 중간-005 FR → 시험 연결이 강제되지 않고, 판정 기준 없는 Then이 있다
- **문제**: §2는 모든 인수 조건이 하나 이상의 자동화 시험과 직접 연결되어야 한다고 하지만, 검사 도구(doc-check)는 이를 보지 않는다. 직접 대조하면 FR 71개 중 13개는 기능 설계서 시험 표에서 ID로 참조되지 않는다: FR-014, 018, 024, 032, 040, 043, 058, 061, 062, 068, 069, 070, 071(이 가운데 FR-032·040·043·062·069·070은 Must). '투명하게 안내', '안정적으로 전달', '안전하게 묶어 제출', '빠진 통계 자동 보정'은 통과 기준이 없다.
- **결정**: 모든 FR은 시험 행 1개 이상이 그 ID를 적고 doc-check가 검사한다(원문 이어받음). 빠진 21개에 시험 행을 달고, 네 FR의 Then에 판정 숫자를 넣는다(추천 적용).
- **바꾼 문서**: planning/02 §2·FR-020·026·027·034, queue-admission·control-tower·transfer-refund·analytics·settlement·forensic-replay·seat-hold 시험 표, verification §9, frontend §5.17

#### 중간-006 기술 블로그 10편이 맨 끝에 몰려 있다
- **문제**: 블로그·데모 영상·안내·RFC 정리·ADR 점검이 출시 준비 마지막 작업(7.6.1)에 묶여 있다. 블로그는 면접 전에 밖에서 보이는 거의 유일한 증거인데 가장 늦게 나오고, 측정 직후의 판단 과정(무엇을 왜 바꿨는지)이 흐려진 뒤에 쓰게 된다.
- **결정**: 블로그를 출시 준비에서 떼어 각 Phase 끝에 그 측정 결과로 1~3편씩 쓴다(원문 이어받음, 배치는 추천 적용).
- **바꾼 문서**: planning/01 §3.3, wbs/wbs.md §3, wbs 작업 표 8행(메인 세션)

#### 중간-007 첫 문제 정의('쓰기 경합')가 설계 결론과 어긋난다
- **문제**: §1.1은 티케팅을 '동시성 쓰기 경합' 문제라서 어렵다고 소개하는데, 설계의 용량 산정은 '진짜 병목은 데이터베이스 쓰기가 아니라' 대기 상태 조회·정각 진입·좌석 변경 방송이라고 결론 낸다. 대기열이 쓰기를 초당 판매 28건·홀드 최대 2,000건으로 묶기 때문이다. 면접관은 첫 문장과 설계의 숫자가 다른 이야기를 한다고 볼 수 있다.
- **결정**: 티케팅의 어려움을 '쓰기 경합'에서 '쓰기 경합과 진입·대기 조회 몰림의 겹침'으로 고쳐 용량 산정 결론과 맞춘다(추천 적용).
- **바꾼 문서**: planning/01 §1.1, guide/01 §2

#### 중간-008 프로토타입 계획과 WBS 0.10.x가 지워진 prototype/을 아직 전제한다
- **문제**: 머리말·§10.5·ADR-0060 상태 줄·00-summary §1은 `prototype/`이 2026-10-22에 지워졌다고 적었다. 그러나 §10.1(목적: 클릭해 보며 검토하고 시연 영상을 만든다), §10.2(범위), §10.4(데모 도구 막대), §10.6(시연 시나리오), §11.1 D10 행('코드는 `prototype/` 폴더에 둔다'), §5~§8의 화면마다 붙은 '프로토타입:' 줄(가짜 제공자·가짜 결제창·MSW 흉내 방법), 00-summary §2의 '프로토타입 제작자' 읽기 경로는 지금도 실행할 계획처럼 쓰여 있다. 무엇이 그 자리를 대신하는지(소유자가 바꾸는 중인 새 디자인 도구·디자인 캔버스 등)는 어느 문서에도 없다. WBS 0.10.4(시연 녹화와 피드백 목록, 2일)는 '진행'이고 녹화 방법은 소유자 결정 대기다(질문 44). 이대로면 시연 시나리오(S1~S9)와 데모 도구 막대가 실릴 곳이 없고, 상시 데모 없이 '녹화·재현 스크립트'로 보이기로 한 검증 전략(ADR-0057)의 화면 쪽 수단도 비어 있다.
- **결정**: d5 §10을 기록과 앞으로의 시연 계획으로 나누고, 시연은 실제 앱 녹화로, 0.10.4는 녹화 없이 닫는다(추천 적용). 새 디자인 도구로 시연할지는 질문 44(소유자)다.
- **바꾼 문서**: design/d5 §0·§5~§8·§10·§11.1, design/d3 §0, design/d4 §3, ADR-0060 상태 줄, review/open-items.md 4번

#### 중간-009 운영 설계의 상시 비용 어림이 없다
- **문제**: infra §11은 온세일 1회 비용(K9)과 데모 비용(월 약 133달러)은 다루지만, 운영 설계를 늘 켜 둘 때의 월 기본 비용(Aurora 넷, ElastiCache 셋, MSK 셋, 직접 운영하는 ClickHouse·MongoDB·Flink, 관측 풀, Global Database, CloudFront 배포, WAF)이 없다. 그래서 '저장소 하나·클러스터 하나를 줄이면 얼마가 주는가'를 판단할 근거가 없다. 예로 Aurora 인스턴스만 어림해도 purchase 2 × db.r7g.xlarge, 나머지 셋 × 2 × db.r7g.large, 도쿄 1대를 ADR-0083에 기록된 서울 가격(db.r7g.large 시간당 0.333달러, db.r7g.2xlarge 1.331달러이므로 xlarge는 약 0.666달러, 도쿄도 같은 값으로 가정)으로 계산하면 시간당 약 3.66달러, 월(730시간) 약 2,670달러다(저장 공간·I/O·Global Database 복제 요금 빼고, 어림).
- **결정**: 운영 설계를 늘 켜 둘 때의 월 기본 비용을 가격표로 어림해 infra §11에 두고, 줄일 후보마다 절감액과 잃는 것을 적는다(추천 적용).
- **바꾼 문서**: docs/infra.md §11, docs/infra-handover.md §3.2


### 나. 원문 학습 지도에서 온 과한 선택(중간)

#### 중간-014 차단 기기 목록에 Bloom filter를 쓸 이유가 없고 이의 인정 때 지울 수 없다
- **문제**: 차단 기기 목록은 '악성 봇으로 확정된 기기 가명'이라 많아야 수만 개다. 일반 키(기기 가명마다 TTL 90일) 하나면 정확하고 지울 수도 있다. Bloom filter는 메모리를 아끼는 대신 가끔 '있다'고 틀리는데, 이 틀림이 곧 사람 오탐(NFR-022 상한 0.5%)에 더해진다. 또 지울 수 없어 30일 묶음 회전이라는 운영 규칙이 따로 생겼고, CS가 이의를 인정해도 그 기기는 최대 90일 동안 계속 '차단 목록에 있음'으로 판정된다(다음 공연에서 다시 격리). Valkey Bloom 모듈을 쓸지, 앱이 비트맵으로 만들지도 정하지 않았다.
- **결정**: 차단 기기 목록을 Bloom filter(30일 단위 필터 묶음 회전)에서 trust-svc 세션·캐시 Redis의 키 `tr:block:{deviceRef}`(TTL 90일 [가정])로 바꾼다(소유자 승인 '추천안 동의'). 확정된 기기는 많아야 수만 개라 키로도 수 MB이고 틀린 '있다'가 없어 사람 오탐(NFR-022)에 더하지 않는다. CS가 이의를 인정하면 trust-svc가 그 키를 바로 지우고 기록을 남긴다. 유실 등급은 C(사람 확인·본인확인·1인 1순번·대기 중 재평가가 지킨다), 시험은 Q-T48이다(세부는 추천 적용 2026-10-28).

#### 중간-015 좌석맵의 SharedArrayBuffer 경로는 메시지 경로와 같은 일을 두 번 만든다
- **문제**: 좌석 상태 공유에 SharedArrayBuffer(교차 출처 격리일 때)와 메시지(격리가 없을 때) 두 길을 둔다. 메시지 길은 어차피 필요하고, 공유할 상태는 약 50KB, 접근성 목록은 지금 구역만 그린다. #### 중간-025 AWS WAF Bot Control의 적용 범위·비용·역할 분담이 없다
- **문제**: infra는 CloudFront에 'AWS WAF(Bot Control, rate-based)'를 단다고만 적었다. 출처는 appendix 학습 지도의 'AWS WAF(Bot Control, rate-based rule)' 줄이다. 어느 배포(공연 페이지·대기열 파일·대기열 API·api)·어느 경로에 거는지, Common과 Targeted 중 무엇인지, Targeted의 자체 챌린지·토큰이 Turnstile·trust-svc와 겹치지 않는지, 오픈 순간 요청(셔플 파일 12.5만/초, 상태 파일 5.3만/초, 진입 20만/초)마다 붙는 WAF·Bot Control 요금이 얼마인지가 없다. CloudFront의 WAF는 캐시 적중 요청도 검사하므로, 캐시로 원본을 지키는 대기열 파일 배포에 걸면 요금이 요청 수만큼 는다. WAF 로그 보존 기간도 '따로 정한다'로 비어 있다.
- **결정**: CloudFront 배포마다 웹 ACL과 규칙 순서를 규칙표로 정한다. 대기열 파일 배포에는 웹 ACL을 두지 않고, Bot Control은 소비자 웹 로그인 경로의 Common 단계 세기 모드로만 쓴다. 사람과 봇 판정은 Turnstile·trust-svc가 맡는다. WAF 요금을 K9에 넣고 WAF 로그 보존을 90일 [가정]으로 정한다(추천 적용).

#### 중간-111 증명 순서와 증거 수준이 문서에 드러나지 않는다(옛 높음-01)
- **문제**: WBS는 기반(Phase 0: 저장소·공용 워크플로·서명·출처 증명·GitOps·Kyverno·스테이징 Terraform 등) 뒤에 v0 → v1 증거(K1~K5·K7)가 나오는 순서다. AI로 빠르게 만들면 일정 위험은 줄지만, 가장 불확실한 것(핵심 증거)을 기반 작업 뒤에 확인하는 순서는 그대로다. 또 문서마다 무엇을 실제로 만들어 쟀는지(측정함), 만들기만 했는지(구현함), 설계만 했는지(설계만)를 가르는 표시가 없어, 인프라처럼 '설계만'(ADR-0057)인 부분과 실제로 잰 부분이 섞여 읽힌다. 그러면 '100만 동시접속' 같은 큰 주장이 과장으로 읽힐 수 있다. 상시 환경이 없는데 운영 도구 연동(합성 점검·상태 페이지·IRM, wbs 4.2.2)을 실제 작업으로 둔 것은 감시할 대상이 없다.
- **결정**: 증거 수준 네 가지를 FR·기능 문서·KPI에 붙이고(지금은 모두 설계만), 환경이 없는 연동과 G-26은 설계만으로 표시하며, 증명 핵심을 기반 작업보다 먼저 또는 함께 낸다(소유자 승인, 표와 작업 순서는 추천 적용). Phase 구성(C-04)은 그대로다.
- **바꾼 문서**: planning/01 §3.3·§5.2, planning/02 §2, planning/03 §4, perf-ledger §7, features/README, verification §1.3·§5.2, observability §5·§10, wbs(메인 세션)
- **남는 한계**: planning/01 §5.2 '증거 수준이 섞여 읽히는 위험' 행

#### 중간-112 저장소 14개의 근거가 정본 스스로와 어긋나고, 기각 이유가 틀리며, 공개 재현이 어렵다(옛 높음-04)
- **문제**: WBS는 가상 팀으로 '리포·CODEOWNERS·배포 경계를 재현'한다고 적어, 폴리레포는 가상 팀 거버넌스를 보이는 선택으로 일관될 수 있다. 그런데 ① architecture §3은 '1인 개발 환경이므로 콘웨이 법칙 같은 조직상의 이점을 분리 근거로 내세우지 않는다'고 하고, ADR-0016과 부록은 'Conway의 법칙을 의도적으로'를 근거로 든다. ② ADR-0016의 모노레포 기각 이유('독립 배포·팀 경계를 증명할 수 없다')는 사실과 다르다. 경로 필터 CI·서비스별 이미지·CODEOWNERS로 증명할 수 있고, 프런트엔드 Turborepo가 이미 그렇게 한다. ③ GitHub Packages는 공개 패키지도 설치에 개인 토큰이 필요해, 면접관이 공개 저장소를 받아 바로 빌드하기 어렵다.
- **결정**: 저장소 14개를 남기되 근거를 가상 팀 거버넌스 목표로 바로잡고, 모노레포 기각 이유를 고치며, 작업 공간 스크립트로 토큰 없이 공개 재현하게 한다(소유자 승인, 스크립트·시연·바꿀 조건은 추천 적용).
- **바꾼 문서**: docs/devops.md §2.1·§4.4, docs/architecture.md §3·§10, docs/security/secrets-and-keys.md, docs/verification.md §7, planning/01 §3.3, guide/16, ADR-0016·0054 상태 줄

#### 중간-113 4개 언어 목표가 한국 휴대폰 본인확인 필수와 부딪힌다(옛 높음-09)
- **문제**: 번역은 AI로 빠르게 할 수 있지만, ja·zh 사용자는 순번을 받기 전 한국 휴대폰 본인확인(POL-001, ADR-0006)에서 막혀 살 수 없다. 해외 팬 접근성(P-08)이 약속하는 것과 실제 흐름이 다르고, 정본 어디에도 해외 팬의 본인확인 경로가 없으며, 성명 허용 문자도 한글·영문·공백뿐이다.
- **결정**: 4개 언어를 유지하되 구매는 언어와 관계없이 국내 본인확인이 필요하다고 화면과 요구사항에 밝히고, 해외 팬 구매를 범위 밖으로 둔다(추천 적용, 안 (가)). 번역 검토 여부를 품질 한계로 적는다.
- **바꾼 문서**: planning/01 §1.2·§4.2·§5.2, planning/02 NFR-024, planning/03 POL-001, docs/frontend.md §5.12, docs/architecture.md §2, design/d1
- **남는 한계**: planning/01 §5.2 '해외 팬 구매와 번역 품질의 남는 한계' 행
