# ADR-0009: 장애 격리는 게이트웨이 1차, 서비스 내부 2차 차단기와 빨리 실패하기로

- **상태**: 채택 (2026-10-08) 2026-10-14: 기대평은 없앴고 후기는 관람 후기만 둔다(ADR-0063 결정 3). 본문의 '기대평'은 '관람 후기'로 읽는다. 2026-10-20(ADR-0069): Envoy 기본 모드의 이상 호스트 퇴출은 앱이 과부하로 낸 503도 연속 5xx로 센다(Envoy 문서 2026-10-20 확인). 그래서 결정 1의 '연속 실패 파드 30초 퇴출'은 과부하로 거절하는 파드를 빼고 남은 파드로 부하를 몰 수 있다. 과부하 거절을 퇴출 계산에서 빼는 설정과 최대 퇴출 비율 상한은 wbs 4.6.1에서 정한다(확인 필요, docs/architecture.md §5 부하 관리 장치 표). 2026-10-20(ADR-0070): DB·Redis 쪽 시간 초과 기본값(서비스 DB 사용자의 역할 기본값 `statement_timeout`·`idle_in_transaction_session_timeout`, PgBouncer 대기 상한, 연결 풀 대기 한도, Redis 명령 시간 초과와 핫패스 오프라인 큐 끔)을 docs/architecture.md §5 '시간 초과 기본값' 표로 더한다. 이 ADR의 경로별 시간 초과·데드라인 전파·재시도 예산은 그대로다. 2026-10-22(ADR-0082): 결정 3의 '서비스 메시(Linkerd) 계층'은 Istio(앰비언트)로 읽는다. Istio 기본 재시도(2회, `unavailable`·`cancelled` 포함)는 메시 전체 1회·연결 실패와 스트림 거절만으로 덮어쓰고 재시도 예산을 명시한다(docs/architecture.md §5 '메시 기본값 덮어쓰기'). 메시 없는 포트폴리오 실행에서는 gRPC 라이브러리의 투명 재시도만 남고 앱에 재시도 정책을 넣지 않는다. 2026-10-23(4차 전수 점검, ADR-0087): 좌석 스냅샷의 첫 요청은 입장 토큰을 처음 써서 구매 세션을 만드는 쓰기라 헤지하지 않고, 구매 세션이 열린 뒤의 스냅샷 재요청만 결정의 '멱등 읽기'로 보아 헤지한다(docs/features/seat-hold.md §2, openapi 스냅샷 경로). 앱의 '분당 60회' 재시도 예산은 브라우저 쪽 몫이고, 서비스 사이 네트워크 재시도 예산은 메시 `retryBudget`이다(docs/api/guidelines.md §5, ADR-0082). 2026-10-28(ADR-0117, 소유자 승인 '추천안 동의'): 결정 3의 '헤지 요청은 순수 멱등적 읽기(좌석 스냅샷)에만 국한한다'를 '헤지 요청은 쓰지 않는다'로 바꾼다. 보낼 곳(게이트웨이·메시·앱)이 없고, 스냅샷의 두 요청은 같은 회차 Redis 샤드를 읽어 느린 원인이 겹치기 때문이다. 바로 위 2026-10-23 줄의 '구매 세션이 열린 뒤의 재요청만 헤지한다'도 함께 없앤다. 스냅샷 재요청은 시간 초과 뒤 브라우저가 `Retry-After`와 지터를 지켜 다시 묻고, 같은 구역은 한 번에 하나만 묻는다. 시험 S-T17은 없앤다(docs/features/seat-hold.md §2·§8·§12, docs/frontend.md §4.4.2). 2026-10-28(기술 검토 낮음-140, 소유자 승인 '추천안 동의'): 위 2026-10-20 줄의 '확인 필요'(과부하 거절을 퇴출 계산에서 빼는 설정과 최대 퇴출 비율)를 닫는다. Envoy Gateway 수동 상태 검사에는 상태 코드별 제외가 없고, 분리 모드는 연결 실패·시간 초과를 따로 셀 뿐 앱의 5xx는 그대로 센다. 최대 퇴출 비율 기본값은 10%다(Envoy·Envoy Gateway 문서, 2026-10-28 확인). 그래서 서비스가 자기 과부하로 거절할 때는 429 `server-busy`와 `Retry-After`로 답해 연속 5xx에 들지 않게 하고, 최대 퇴출 비율은 기본 10%를 쓴다. 분리 모드(연속 5xx 문턱을 크게 올리고 연결 실패·시간 초과로만 퇴출)는 대안으로 둔다(docs/architecture.md §5 부하 관리 장치 표, docs/api/guidelines.md §2). 2026-11-01(openspec 변경 add-breakers-purchase-auth-and-grpc-channel, BUILD_ORDER FND-100, R-226): 결정 2·5의 서비스 안 차단기는 서비스 템플릿의 `createCircuitBreaker`(opossum 10)다. 공용 기본값은 10초 창·20건 이상·실패 50% 이상이면 열림·5초 뒤 시험 호출 하나 [가정]이고(docs/features/bot-defense.md §11의 수치), 열리면 503 `dependency-unavailable`과 `Retry-After`, 의존성마다 둘 수 있는 동시 호출 상한(벌크헤드)을 넘으면 429 `server-busy`다. 업무 거절은 실패로 세지 않고, 닫히면 창을 비운다. 상태와 끊은 수는 `circuit_breaker_state`·`circuit_breaker_rejected_total`이다(docs/observability.md §3). 2026-11-01(정합 점검, ADR-0175 해설서 검토): 결정 6의 '게이트웨이 파드 50% 강제 종료에도 SLO 준수 유지'는 'SLO를 지킨다고 약속하지 않는다'로 읽는다. 파드 절반을 잃으면 남은 파드가 상한을 넘는 요청을 503과 `Retry-After`로 덜어 내고, 덜어 낸 503은 그 여정 SLO의 오류로 센다. 검증할 것은 SLO 준수가 아니라 빠른 실패와 60초 [가정] 안의 복제 수 회복이다(docs/observability.md §12 G-16, docs/infra.md §4 Envoy Gateway 행, 기술 검토 낮음-011). 2026-11-01(정합 점검, ADR-0177 해설서 검토 네 번째 묶음): 결정 3의 '`Retry-After` 권고값 및 지터(±20%)'는 '`Retry-After`를 하한으로 지키고 위쪽으로만 0~20% 흔든다'(기다림 = 하한 × (1 + U(0, 0.2)))로 읽는다. 아래쪽으로도 흔들면 하한이 깨지고, 하한으로 자르기만 하면 503을 같은 1초에 받은 사람들이 같은 때 다시 온다. 하한이 없는 주기 요청은 ±20% 그대로다(기술 검토 중간-038, ADR-0129, docs/api/guidelines.md §5, docs/frontend.md §4.1).
- **관련**: 설계서 섹션 6 '장애 격리', 섹션 9(Degraded Mode, 검증), 29장, ADR-0007, ADR-0008, ADR-0010
- **관련 ID**: NFR-011, NFR-014, NFR-023, POL-029

## 맥락

- **초기 설계의 장애 격리 체계는 부분적으로만 적용되었다.**
  - 외부 결제사 및 Turnstile 통신 구간에만 Node.js opossum 라이브러리가 국소 적용되었다.
  - 서비스 메시 단의 이상 파드 퇴출(Outlier Detection) 메커니즘은 단순 언급 수준에 그쳤다.
  - 게이트웨이 인입단의 1차 서킷 브레이킹, 빠른 실패(Fail-fast), 표준 재시도 통제 규칙이 부재했다.
- **분산 시스템에서 단일 컴포넌트의 지연은 전체 장애로 증폭될 위험이 있다.** 서비스를 물리적으로 분리하면(ADR-0007) 프로세스 간 통신이 네트워크를 경유하므로, 특정 다운스트림 서비스가 지연될 때 업스트림 호출자의 커넥션 풀과 스레드 풀이 급격히 고갈된다.

공식 아키텍처 레퍼런스 원문 근거는 다음과 같다.

- **[Envoy 서킷 브레이킹](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/circuit_breaking)**
  - 대기 큐에 무한정 머물게 하는 것보다 즉시 실패(Fail-fast)시키고 시스템 상단에 명확한 역압(Backpressure)을 가하는 것이 압도적으로 안정적이다.
  - 최대 동시 연결 수, 보류(Pending) 요청 수, 동시 재시도 수에 절대 상한을 설정하고, 재시도에는 고정 예산(Retry Budget) 정책을 적용해야 한다.
- **[Envoy 장애 호스트 제외](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/outlier)**: 연속 에러를 유발하는 이상 호스트를 부하 분산 풀에서 일시 격리하며, 서비스 전체 고갈을 막기 위해 최대 제외 비율 상한을 강제한다.
- **[Envoy Gateway 서킷 브레이커](https://gateway.envoyproxy.io/docs/tasks/traffic/circuit-breaker/)**
  - 대기 큐 상한을 초과한 인입 요청은 즉시 HTTP 503 Service Unavailable로 종결한다.
  - 차단 카운터는 개별 Envoy 프록시 인스턴스 로컬 메모리 단위로 독립 계측된다.
  - 기본 상한값(1024)은 고처리량 시스템에 부족하므로 워크로드에 맞춰 정밀 튜닝해야 한다.
- **[Envoy Gateway API 문서](https://gateway.envoyproxy.io/docs/api/extension_types/)**: 이상 파드 퇴출 기본값은 연속 5xx 5회 발생 시 30초간 라우팅 제외이다.
- **[Google SRE Book 22장](https://sre.google/sre-book/addressing-cascading-failures/)**
  - 단일 요청당 최대 재시도 횟수를 엄격히 제한하고, 프로세스 단위 재시도 예산(예: 분당 최대 60회)을 초과하지 않도록 통제한다.
  - 요청 유효 기한(Deadline)을 최상단에서 정의하여 다운스트림 전체 파이프라인으로 전파해야 한다.
  - 과부하 상황에서는 인프라 앞단이든 뒷단이든 가장 저렴한 비용으로 조기 실패시키는 것이 핵심이다.
- **[opossum](https://github.com/nodeshift/opossum)**: Node.js 런타임용 비동기 서킷 브레이커 라이브러리로서 차단기 Open 시 즉시 폴백을 반환한다.

## 결정

1. **1차 방어선은 API 게이트웨이(Envoy Gateway) L7 계층에 구축한다.**
   - 엔드포인트 경로별 비즈니스 SLO에 최적화된 요청 타임아웃을 설정한다.
   - 업스트림 백엔드 서비스별 동시 처리 요청 상한 및 보류 대기 큐 상한을 강제한다(프록시 1대 기준 계산).
   - 임계 상한을 초과한 인입 요청은 대기시키지 않고 즉각 HTTP 503과 함께 `Retry-After` 헤더를 반환한다.
   - 연속 에러를 유발하는 비정상 파드는 부하 분산 엔드포인트에서 30초간 자동 축출한다.
   - 시스템 과부하 징후 감지 시 기대평·관람 후기, 추천 등 비핵심 경로의 인입 트래픽부터 선제 차단한다.
2. **2차 방어선은 서비스 프로세스 내부 애플리케이션 계층(opossum)에 구축한다.**
   - 프로세스 외부로 나가는 모든 외부 I/O 의존성마다 개별 서킷 브레이커를 배치한다(서비스 간 gRPC 호출, PG 결제망, Turnstile, 휴대폰 본인확인 대행사, 외부 알림 채널).
   - 의존성별 연결 풀을 물리 분리하여 특정 채널의 지연이 타 채널로 전이되지 않도록 벌크헤드(Bulkhead) 격리를 수행한다.
   - 서킷 브레이커 Open 상태 전이 시 설계서 섹션 9의 기능 감내 모드(Degraded Mode) 대체 로직으로 즉시 폴백한다.
3. **네트워크 재시도는 단일 계층에서만 배타적으로 수행한다.**
   - 서비스 간 내부 gRPC 통신의 일시적 전송 오류에 대한 재시도는 서비스 메시(Linkerd) 계층에서 재시도 예산 범위 내에서만 처리한다.
   - 외부 게이트웨이 및 서비스 비즈니스 코드는 전송 재시도를 수행하지 않는다. 상태 변경 트랜잭션(좌석 홀드, 주문서 생성, 결제 승인 요청)은 멱등키가 존재하더라도 게이트웨이 단에서 임의 재시도하거나 헤지 요청(Hedged Request)을 발송하지 않는다. 헤지 요청은 순수 멱등적 읽기(좌석 스냅샷)에만 국한한다.
   - PG 결제사 승인 재시도는 단순 네트워크 전송 재시도가 아닌 비즈니스 복구 절차이다. 발급된 멱등키 및 10분 유효 Deadline 한도 내에서 payment-svc가 책임지고 완결한다(설계서 섹션 6 결제 연동).
   - 브라우저 클라이언트는 수신한 `Retry-After` 권고값 및 지터(±20%)를 엄격히 준수하여 재시도한다.
4. **엔드투엔드 요청 Deadline을 하류로 강제 전파한다.** 게이트웨이가 인입 시점의 경로별 최대 유효 Deadline 헤더를 주입하고, 각 백엔드 서비스는 잔여 시간을 계산하여 다운스트림 gRPC Deadline으로 바인딩한다. 잔여 실행 시간이 부족한 경우 불필요한 작업을 시작하지 않고 즉시 연쇄 조기 종료한다.
5. **서킷 브레이커 상태를 4대 골든 시그널로 실시간 관측한다.** 게이트웨이 및 서비스 내부 차단기의 상태(Open/Half-Open/Closed)와 조기 거절(Fast-rejected) 트래픽 카운터를 관제 대시보드의 에러 및 포화도 패널에 실시간 바인딩한다.
6. **카오스 엔지니어링 Game Day에 3대 핵심 장애 주입 시나리오를 필수 편성한다.**
   - purchase-svc 전면 마비 상황에서도 대기열 진입(gw-queue) 및 운영 관제(gw-ops)가 완벽히 독립 생존하는지 검증
   - payment-svc에 인위적인 5초 레이턴시를 주입해도 purchase-svc의 스레드 풀과 연결 풀이 고갈되지 않는지 검증
   - 인그레스 게이트웨이 파드의 50%를 강제 종료해도 무중단 자동 페일오버 및 SLO 준수가 유지되는지 검증

## Well-Architected 기둥 분석

| 기둥 | 아키텍처 영향 |
| --- | --- |
| 안정성 | 국소 장애의 도메인 간 연쇄 확산을 원천 차단하며, 네트워크 재시도 폭주로 인한 뇌관 현상을 방어한다. |
| 성능 효율성 | 지연되는 요청을 붙잡지 않고 즉각 Fail-fast 처리하여 시스템 유휴 자원을 고갈시키지 않는다. 과부하 시 일부 트래픽에 503을 반환하는 것은 안정성을 위한 합리적 트레이드오프이다. |
| 운영 우수성 | 서킷 브레이커 차단 이벤트가 모니터링 알림과 직결되며, 정밀 임계치는 부하 테스트 벤치마크를 통해 지속 튜닝한다. |

## 결과

- 특정 마이크로서비스에 장애가 발생하더라도 게이트웨이 및 호출 서비스 경계에서 즉각 차단되며, 무관한 타 클라이언트와 핵심 사용자 여정은 정상 가동된다.
- 트레이드오프: 차단 임계치를 지나치게 보수적으로 잡을 경우 정상적인 스파이크 부하 상황에서도 503 에러가 반환될 위험이 있다. 초기 임계치는 k6 부하 시험을 거쳐 결정하며 성능 장부에 기록한다.

## 재검토 조건

- 정상 트래픽 유입 구간에서 차단기 조기 발동으로 인한 503 발생이 가용성 SLO의 에러 버짓을 유의미하게 소진할 때
- 카오스 엔지니어링 Game Day 모의 훈련에서 장애가 서비스 경계를 넘어 연쇄 파급되는 결함이 발견될 때
