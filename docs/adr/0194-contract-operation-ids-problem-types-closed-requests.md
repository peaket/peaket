# ADR-0194: 계약 보강 ① — 모든 작업에 이름을 달고, 오류 이름 목록을 계약에 두며, 요청 본문은 닫고 응답은 연다

- **상태**: 채택(2026-11-05, 추천 적용. wbs 0.2.3의 세부는 추천 적용으로 정한다는 소유자 승인 2026-10-21·2026-10-28을 따른다). BUILD_ORDER BAS-040을 셋으로 나눈 첫째다.
- **관련**: ADR-0079(프런트엔드 상세 설계), ADR-0081(REST 기준 점검), ADR-0133(기술 검토 나머지), ADR-0165(계약 패키지), ADR-0050 결정 8(구매 세션 요청 서명), ADR-0144(CloudFront 배포), [docs/api/guidelines.md](../api/guidelines.md) §1·§2·§10, [docs/frontend.md](../frontend.md) §4.1·§5.3·§5.12·§6.2, [docs/security/authz-matrix.md](../security/authz-matrix.md) §4, [docs/infra.md](../infra.md) §4.1
- **관련 ID**: FR-010, D-T38, D-T48, AZ-T1, ASVS v5.0.0-15.3.3

## 맥락

- 계약(`docs/api/openapi.yaml`)의 272개 작업에 `operationId`(작업 이름)가 하나도 없었다. 그래서 계약에서 만든 Zod·타입 이름이 경로에서 나왔고(`PostV1EventsEventIdHoldsBody`), 서비스는 경로가 바뀌면 이름도 바뀌는 생성물을 피해 모양을 따로 적었다. api-client의 훅 이름도 정할 수 없었다(docs/frontend.md §3 '훅 이름은 REST operationId에서 orval이 만든다').
- 지침 §2는 "한 `type`은 언제나 같은 상태 코드와 제목"이라 하면서 전체 목록을 wbs 0.2.3으로 미뤘다. 응답 설명에는 케밥 이름 약 130개가 흩어져 있었고, 서비스 코드는 같은 `type`을 다른 제목으로 내는 곳이 8개 있었다. 구매 경로의 401은 쿠키 만료·입장 토큰 만료·서명 불일치·일련번호 재사용을 가르지 못했다(FND-100 넘김, docs/frontend.md §6.2 23번).
- JSON 요청 본문 126개 가운데 70개 남짓이 닫혀 있지 않아 정의 밖 칸을 400으로 거절하지 않았다(FND-030 넘김, authz-matrix '요청 스키마는 허용한 칸만'). 핫패스(좌석 홀드)도 열려 있어 Fastify 경로 스키마 길은 정의 밖 칸을 처리기까지 넘겼다(FND-070 넘김). 거꾸로 응답에만 쓰는 스키마 넷(토스·포트원 결제창 값, 고소·고발 요약, 팬 좌석맵 파일)은 닫혀 있어, 응답에 칸을 더하면 그 스키마로 검사하는 옛 화면이 거절한다(지침 §1 '응답 칸 추가는 깨짐 아님'). 요청과 응답이 함께 쓰는 객체 스키마도 10개 있었다. 홈 구성 저장 본문은 `allOf`로 응답 스키마를 이어, orval이 읽기 전용 칸을 본문 Zod에 넣었다(FND-050 넘김, 계약 대조의 알려진 차이).

## 결정

1. **작업 이름 규칙**: 모든 작업에 camelCase `동사 + 경로 이름`의 `operationId`를 단다. ADR-0145 결정 3의 '동사 + 자원'을 구체화한 것이다. 자원을 마지막 단어만 쓰면(그 결정의 예 `createHold`) 같은 단어의 경로가 생길 때 이름을 바꿔야 해서 경로의 이름 단어를 모두 잇는다(`createEventHold`). 동사는 메서드로 정한다(POST `create`, PUT `put`, PATCH `update`, DELETE `delete`, GET은 목록이면 `list` 아니면 `get`). 경로 이름은 `v1`과 ID 자리를 빼고 잇되, ID·`me` 앞 컬렉션과 POST로 만드는 컬렉션은 단수로, `me`는 동사 뒤 `My`로 쓴다. 규칙대로면 어색한 셋(검색 `listSearchResults`, 웹훅 받기 `receiveTossWebhook`·`receivePortoneWebhook`)만 따로 정했다. 계약 Zod·타입 이름은 이 이름에서 나온다(`CreateEventHoldBody`). 문서 점검이 있음·겹침·동사를 본다(지침 §10).
2. **오류 이름 목록은 계약 안에 둔다**: openapi 맨 위 `x-peaket-problem-types`(이름 → `status`·`title`, 134개)가 정본이다. 문서 점검은 오류 응답 설명의 케밥 이름이 목록에 있는지 보고 상태 코드가 다르면 경고한다. `packages/platform/test/problem-types.test.ts`는 서비스 코드의 `{ type, status, title }` 글자가 목록과 같은지 본다. 처음 대조에서 남은 제목 차이 8개는 알려진 차이로 두고 각 갈래가 고친다(늘리지 않는다). v0 증명용 `v0-monolith`의 이름은 실제 서비스가 같은 일을 맡을 때 목록에 더한다. api-client의 `type` → 문구 키 표는 이 목록에서 만든다(②).
3. **구매 경로 401을 넷으로 가른다**: `purchase-signature-invalid`(서명 머리 없음·형식·불일치), `purchase-session-ended`(구매 세션 없음·끝남), `purchase-seq-reused`(일련번호 재사용), `admission-token-invalid`(입장 토큰 없음·서명·만료·첫 사용 기한). 팬 쿠키 401은 `about:blank` 그대로다. 앞의 셋은 공용 서버 패키지의 구매 세션 요청 서명 가드가 낸다(이 단계). 구매 서비스가 스스로 내는 401(스냅샷 첫 사용의 입장 토큰 거절, 홀드의 세션 없음)은 갈래 1이 PRF-190에서 이 이름으로 바꾼다. 화면은 일련번호 재사용만 번호를 건너뛰어 한 번 다시 보내고 나머지는 세션 종료로 본다(docs/frontend.md §4.1 '401').
4. **`type` 설명 문서를 올릴 곳**: 개발자 포털 정적 사이트를 `developers.peaket.example`(폐기 안내 `Link`가 이미 쓰는 호스트)의 S3·CloudFront 배포에 올린다. `type` URI(`https://peaket.example/problems/<이름>`)는 식별자라 바꾸지 않고, 맨 도메인을 같은 배포의 대체 도메인으로 두어 `/problems/*`를 포털로, 그 밖을 `www`로 301 이동한다. 배포는 쿠키·요청 머리를 원본에 넘기지 않는다. CloudFront 배포는 여덟이 된다(docs/infra.md §4.1). 자원은 클라우드 계정이 생긴 뒤 만든다.
5. **요청은 닫고 응답은 연다**: 요청 본문에서 닿는 객체 스키마는 모두 `additionalProperties: false`다(78개를 닫았다). 응답에서 닿는 객체는 닫지 않는다(다섯을 열었다). 서버가 정의한 칸만 내야 하는 응답은 응답 직렬화 스키마가 정의 밖 칸을 버리는 것으로 지킨다. 겸용 스키마 10개 가운데 9개는 요청용 `<이름>Input`(모든 층을 닫고 서버가 채우는 칸을 뺀다)으로 나눴다. 남은 하나(승인 요청 상세의 사건 요약)는 요청용 승인 요청에서 빠져 요청에서 닿지 않는다. 요청 본문은 `allOf`로 잇지 않는다(홈 구성 저장 본문을 `HomeLayoutInput` 하나로 바꿔 계약 대조의 알려진 차이를 비웠다). 칸이 없던 기기 공개키(`publicKeyJwk`)는 P-256 공개키 칸으로 닫아 개인키 칸(`d`)이 섞인 본문을 거절한다. 칸을 아직 정하지 못한 관제 명령 `params`만 `x-peaket-open-object`에 이유를 적어 연다. T=0 두 호출은 JSON 본문과 `text/plain`의 `contentSchema`가 같은 닫힌 구성 요소(`QueueEntryRequest`·`AdmissionRequest`)를 가리킨다. 서비스가 처리기 곁에 손으로 둔 같은 모양도 닫아야 계약이 지켜지므로, 핫패스 넷(좌석 홀드, 대기열 사전 검증·진입·입장 확정)의 서비스 스키마를 `.strict()`로 닫고 서비스 시험으로 본다. 서비스 대조 검사(D-T38)의 비교기는 요청 본문의 닫힘도 견준다(응답 쪽은 직렬화 스키마가 닫을 수 있어 견주지 않는다). 계약 전체 대조는 이것으로 모든 작업의 생성 Zod 요청 본문이 닫혔는지 본다. 읽은 응답을 고쳐 다시 보내는 화면은 요청용 스키마의 칸만 골라 보낸다(BAS-041이 도우미를 둔다). 문서 점검이 이 규칙을 본다(지침 §1).
6. **깨짐 검사**: oasdiff는 작업 이름 바꾸기와 본문 닫기를 깨짐으로 보지 않았다. 막은 것은 기기 공개키의 새 필수 칸 넷뿐이라 이유를 단 예외로 두었다(올바른 EC 공개키는 늘 그 칸을 가진다). 요청용 사본이 뺀 서버 칸(승인 요청·결정 기록)과 홈 구성 본문의 모양 바뀜은 경고다. 본문 닫기는 정의 밖 칸을 보내던 클라이언트에는 깨짐이지만, 우리 화면은 같은 계약의 생성 타입으로 보내고 v0.1.x에서 열린 경로는 v0-monolith가 이미 모양을 검사했다.
7. **BAS-040을 셋으로 나눈다**: ①은 이 ADR(작업 이름, 오류 목록과 구매 401, 본문 닫기, `PurchaseMac` 키 32바이트 설명). ②(BAS-041)는 api-client를 orval 생성물(호출 함수·훅·MSW 처리기)로 바꾸고 작업 종류·시간 초과·T=0 `text/plain`을 openapi에서 읽으며, 변이 함수의 ETag·`If-Match`·412 공통 처리와 `type` → 문구 키 표를 만든다. ③(BAS-042)은 화면이 쓰는 계약을 더한다(docs/frontend.md §6.2의 wbs 0.2.3 행 가운데 남은 것: 사전 검증 토큰 만료·입장 토큰 체류 시각, 대기 상태 파일의 더할 칸, 홀드 다시 읽기, 굿즈 결제 경로와 인기 MD 대기열 식별자, 빠진 읽기 경로 초안, 셔플·묶음 파일 형식. 부정 예매 운영자 취소 내부 호출의 계약과 공제 없는 환급의 정산 처리 결정).

## 결과

- 계약 Zod 이름이 경로가 아니라 작업 이름을 따른다. 생성 이름을 쓰던 시험·벤치 7개 파일을 새 이름으로 바꿨다. 서비스 소스는 생성 이름을 쓰지 않아 그대로다.
- 서비스가 새 오류 이름을 쓰려면 목록에 먼저 더해야 한다. 다른 갈래가 제목을 목록과 다르게 쓰면 코드 대조 시험이 실패한다.
- 요청 본문의 정의 밖 칸은 계약 생성 Zod와 경로 스키마 두 길, 그리고 핫패스 넷의 서비스 스키마에서 400이다(시험 표본에 더했다). 손으로 둔 스키마가 아직 열린 다른 처리기(identity-svc 탈퇴 본문의 환불 계좌 등)는 각 갈래가 닫는다(BOT-123에 넘김).
- 요청용 사본(`<이름>Input`)은 원래 스키마와 칸을 따로 적어 어긋날 수 있다. 원래 스키마를 고칠 때 사본도 같이 고친다.

## 다른 선택지

| 길 | 고르지 않은 까닭 |
| --- | --- |
| 작업 이름 없이 orval의 경로 이름을 쓴다 | 이름이 길고 경로를 바꾸면 바뀐다. 훅 이름으로 읽기 어렵다 |
| 생성기가 옛 경로 이름을 그대로 만들게 한다(`operationName` 덮어쓰기) | 화면 훅과 서버 Zod의 이름이 갈린다. 생성 이름을 쓰는 곳이 시험 7개뿐이라 바꾸는 값이 작다 |
| 오류 목록을 따로 파일로 둔다 | 계약이 둘이 된다. openapi 확장 칸이면 같은 도구가 함께 읽는다 |
| `type` 바탕 주소를 포털 호스트로 바꾼다 | 식별자가 바뀌고 코드 17곳이 바뀐다. 맨 도메인 이동으로 같은 효과를 낸다 |
| 겸용 스키마를 `allOf` + `unevaluatedProperties: false`로 닫는다 | orval의 Zod 생성기와 경로 스키마 검사기(Ajv draft-07)가 받지 않는다 |
| 생성기가 요청 쪽을 알아서 닫는다(계약 글은 열린 채) | 계약을 읽는 다른 도구와 사람이 닫힘을 볼 수 없다 |
