# ADR-0078: AIOps 관점으로 보강한다 — 수요 예측과 사후 대조, 자동 조치의 끝내는 조건, 운영 명령 주석·서비스 지도, 원인 유형, 경보 위생 보고, Grafana 조직 분리, 클러스터 규모 근거, 네임스페이스 지도(2026-10-21)

- **상태**: 채택 (2026-10-21. 소유자가 관측 가능성 책의 7장 '관측 가능성을 넘어 자동화로'를 보이며 앞 장들과 종합한 피드백을 요청했다. 7장은 AIOps 4단계(지능형 알람, 개체 간 상관관계, 이상 탐지·수요 예측, 자가 치유·자동 해결), AI와 운영 팀의 역할 나눔, 근본 원인 분석의 유형화, 멀티 클러스터·멀티 테넌트, SLO 규칙을 다룬다. 보강 제안 8건을 본 뒤 "피드백 ①~⑧을 추천대로 ADR로 남기고 반영해 주세요"라고 정했다. 결정 하나하나의 세부는 추천 적용이며 소유자 검토 대상이다. 외부 사실은 2026-10-21에 각 공식 문서로 확인했다) 2026-10-21(디자인 캔버스 v58): 판매 승인(SCR-048) 보드에 수요 예측 줄·[규모 올리기]와 상태 6개(기본 비율, 승인 뒤, 규모 올리기 검토, 올리기 간격 충돌 operator·commander, 규모 올리기 닫힘)를 그렸다. 휴대폰은 보기만 하고 규모 올리기는 태블릿·데스크톱에서 한다(추천 적용, design/d5 §3.9). 본문 '반영 수치'의 캔버스 문장은 채택 때의 기록이다. 2026-10-21(소유자 요청 '관제 화면에 지금 걸린 자동 조치와 풀리는 조건 표시를 d5에 정하고, 캔버스 SCR-029에도 그려 주세요'): 결정 2의 자동 조치를 관제 콘솔에 보이는 방식으로 위 상태 바 '자동 조치 n'과 SCR-029 '걸린 자동 조치' 위젯(탭 내용 맨 위, 이 회차·플랫폼 묶음, 상태 배지, 왜·풀림·막대, 명령은 SCR-030으로만 엶)을 design/d5 §3.3·§7.2에 정하고(추천 적용) 디자인 캔버스 v61에 새 상태와 보기 행 '자동 조치 걸림'으로 그렸다(렌더 확인은 하지 않음). 2026-10-22(소유자 요청): 캔버스와 같은 렌더러로 SCR-029 보드 22개를 실제 크기에 띄워 쟀다. 새 보드에는 잘림·가로 넘침이 없어 보기 행 높이만 내용에 맞춰 줄였다. 60판부터 휴대폰 두 보드(원본 T=0, '제어 입력 없음')에서 마지막 줄이 아래 탭 막대에 가리던 것은 보드 높이로 고쳐 캔버스 v62에 올렸다. 2026-10-22(ADR-0082): 본문의 '서비스 메시 선택(Linkerd와 Istio PoC)은 그대로다'는 메시를 Istio 앰비언트로 정한 것으로 읽는다. 2026-10-27(ADR-0093): 판매 승인이 공연 단위가 되어 수요 예측과 규모 올리기 경로를 회차 경로(`/v1/ops/events/{eventId}/demand-forecast`·`…/scale-changes`)로 옮겼다. 규모는 지금처럼 회차마다다. 2026-10-28(ADR-0105, 소유자 승인 '추천안 동의'): 결정 2 표의 '결제 신규 진입 일시 정지' 끝내는 조건을 바꾼다. 결제사 장애로 멈췄으면 정지 중의 확인 호출(1초 1건)이 3분 정상인 뒤 새 결제 시도의 5%만 받는 시험 재개를 거쳐, 시험 결제의 첫 승인 20건이 기준을 넘으면 모두 연다. 채널 상한 대기로 멈췄으면 예상 대기가 10초 아래로 1분 이어지면 연다. commander가 명령 6 해제로 바로 열 수도 있다. '서킷 닫힘과 p99 5초 아래 5분'은 정지 중에 표본이 생기지 않아 쓰지 않는다. 2026-10-28(기술 검토 높음-13, 소유자 승인 '추천안 동의'): 결정 2 표의 '28일 예산 소진 배포 잠금'은 Mimir `raw`에서 계산한 28일 남은 예산으로 판정하고, 그 값을 읽지 못하면 지금 상태를 유지한다(docs/observability.md §8). 2026-10-28(기술 검토 낮음-160, 소유자 승인 '추천안 동의'): 결정 6의 제한 조직 'PEAKET 제한'(PostgreSQL 쿼리 문장)은 로컬·포트폴리오 측정용으로 좁힌다. 운영 설계의 쿼리 문장은 Aurora Database Insights 표준 모드에서 IAM으로 DB 담당 역할에만 연다(ADR-0067 상태 줄, docs/observability.md §8·§9). 2026-10-28(기술 검토 낮음-163, 소유자 승인 '추천안 동의'): 결정 5의 '경보 위생 보고는 ops-svc가 만들어 GitHub Issues에 올린다'를 바꾼다. 보고는 플랫폼 네임스페이스의 쿠버네티스 CronJob `alert-hygiene-report`가 만들어 올리고, GitHub 쓰기 자격(운영 이슈 저장소 하나의 Issues 쓰기만 가진 GitHub 앱)은 그 작업만 받는다. ops-svc는 그 작업의 신원만 받는 읽기 전용 조회 경로만 열고 GitHub 토큰을 갖지 않는다. 운영 명령을 다루는 ops-svc가 뚫렸을 때 피해가 GitHub 조직까지 번지지 않게 하려는 것이다. 보고 항목과 검토 방식은 그대로다(docs/observability.md §5, docs/security/secrets-and-keys.md). 2026-10-28(기술 검토 낮음-164, 소유자 승인 '추천안 동의'): 결정 7 CNI의 '서브넷은 피크 파드 수의 2배 이상 IP'를 노드 수와 웜 풀을 넣은 식으로 바꾼다. VPC CNI는 노드마다 IP를 미리 잡아 두고(기본 `WARM_ENI_TARGET` 1은 빈 인터페이스 하나와 그 IP 전부), 노드와 인터페이스도 서브넷 IP를 쓰기 때문이다. 기본안은 접두사 위임(/28 묶음, 파드용 새 서브넷에 CIDR 예약)이고, 다른 안은 보조 IP에 `MINIMUM_IP_TARGET`·`WARM_IP_TARGET`이다. 고르기와 CIDR은 wbs 4.8.1 피크 추정 뒤에 정한다(docs/infra.md §1, docs/infra-handover.md §3).

## 맥락

- **AIOps 4단계에 대어 본 위치**(대조 결과)
  - 1단계(지능형 알람)는 강하다. 사용자 증상 중심 호출, 묶기·억제, 경보 규칙 시험이 있다. 다만 경보 소음 지표는 ADR-0049에서 보류했고, NFR-023 '미조치 알림 0건'을 셀 데이터 출처·검토 주기·담당이 없다.
  - 2단계(개체 간 상관관계)는 부분적이다. 지표 → 요청 기록 → 로그 연결, 배포 주석, 외부 의존성 라벨은 있다.
    - 운영 명령과 설정 변경은 감사 로그와 사고 재현 화면에만 있고 그래프에 보이지 않는다.
    - 내부 서비스 사이 호출 지도는 손으로 그린 그림뿐이다.
  - 3단계 가운데 이상 탐지는 규칙으로 한다(ADR-0076 결정 9, 소유자 확정). 수요 예측은 없다.
    - 규모 등급은 판매 승인 때 운영자가 버튼으로 고른다.
    - POL-030은 '알림 구독 수와 공연장 규모로 지정'이라고만 한다. 구독 수를 예상 인원으로 바꾸는 식이 없고, 구독 수를 보여 주는 화면도 없다.
    - 승인 뒤 등급을 바꾸는 길이 없다.
    - R1에서 등급을 실제 진입 인원으로 덮어써, 예측이 맞았는지 남지 않는다.
    - 그런데 이 등급이 변경 동결 창, 대형 공연 30분 간격, CDN 한도 대조를 정한다.
  - 4단계(자가 치유)는 줄이는 쪽으로는 이미 많다. 정원 감축, Degraded 전환, 차단기, 결제-발권 60초 자동 보상, 상태 미확정 자동 대사, 카나리 자동 중단 등 20여 개다.
    - 다음은 끝내는 조건이 비어 있다: 실시간 표의 대체 표시, 결제 신규 진입 멈춤의 해제, 결제사 채널 상한 복귀, 28일 예산 소진 배포 잠금의 해제, 실패 메시지(DLQ) 재처리.
    - 대기 상태 파일의 S3 우회는 문서마다 다르다. infra §4는 원본 장애 때 자동, control-tower와 RB-04는 명령 6으로 전환이라고 적었다. 이 어긋남은 2026-10-12에 찾고 아직 풀리지 않았다.
- **그 밖의 빈칸**(대조 결과)
  - POL-022의 '같은 종류의 장애'가 정의되지 않았다. 포스트모템 초안에 원인 유형 칸이 없고, 런북 36개는 유형별로 묶여 있지 않다.
  - Grafana는 직접 운영하는 무료판이다. 설계상 쿼리 문장을 PostgreSQL 읽기 전용 모니터링 계정으로 Grafana에서 본다. 그런데 무료판에는 데이터 소스별 권한이 없다.
  - Grafana 팀·폴더·역할과 SSO 연결이 정해지지 않았다. 사람 역할 표와 로그인 감사 목록에도 Grafana가 없다.
  - 운영 클러스터는 서울 하나다. 피크 노드·파드 수 추정이 없고 CNI가 적혀 있지 않다.
  - 네임스페이스 지도와 자원 할당량이 없다.
- **확인한 사실**(2026-10-21 원문)
  - **Grafana Tempo**
    - 서비스 그래프는 metrics-generator(또는 Alloy)가 추적에서 만든 지표다. 처리기는 한 trace의 span을 모두 한 인스턴스에서 봐야 짝을 맞춘다.
    - `traces_service_graph_connection_info`(기본 꺼짐)는 연결이 있는 동안 1인 게이지다. 공격적인 표본 추출 아래에서는 비율 계산이 아니라 위상(연결) 확인용이다.
    - metrics-generator는 지표를 원격 쓰기로 보낸다.
  - **OpenTelemetry 수집기**: servicegraph·spanmetrics 커넥터는 alpha다.
  - **Grafana 권한**
    - 데이터 소스 권한(조회·편집·관리)은 Grafana Enterprise와 Grafana Cloud에만 있다.
    - 기본 역할로 Viewer는 Explore를 못 쓰지만 데이터 소스를 직접 조회할 수는 있다. 주석 추가·편집은 Editor 이상이다.
    - 조직(organization)은 한 인스턴스 안에서 대시보드·데이터 소스·폴더·팀을 서로 격리한다.
  - **Prometheus**: 대기·발생 경보마다 합성 시계열 `ALERTS{alertname, alertstate="pending|firing", …}`을 저장한다. `keep_firing_for`가 있다.
  - **Kubernetes**(v1.37 문서): 클러스터당 노드 5,000개, 파드 15만 개, 컨테이너 30만 개, 노드당 파드 110개까지 지원한다. 7장의 '노드 500개 정도'는 운영 의견이다.
  - **Amazon VPC CNI**(EKS 기본 애드온): 노드에 ENI를 붙이고 파드마다 VPC의 사설 IP를 준다.
  - **CloudFront 원본 그룹**
    - 주 원본이 응답하지 않거나 장애 조치용으로 지정한 상태 코드(400·403·404·416·429·500·502·503·504 가운데 고름)를 내면, CloudFront가 그 요청을 자동으로 보조 원본으로 보낸다.
    - 다음 요청은 다시 주 원본으로 간다. GET·HEAD·OPTIONS 요청만 넘긴다.
    - 기본값으로는 주 원본 연결을 10초씩 3번 시도한 뒤(30초)에야 넘긴다. 연결 시간 초과(1~10초)와 시도 횟수(1~3회)를 줄여야 빨리 넘어간다.

## 결정

1. **수요 예측과 사후 대조를 둔다(추천 적용)**:
   - **식**(머신러닝 아님)
     - 예상 진입 인원 = 그 회차의 오픈 알림 구독 수 × 구독 대비 진입 비율이다.
     - 비율은 지난 회차(골드, 최근 2년) 가운데 오픈 30분 전 구독 수가 이 회차 구독 수의 0.5~2배 [가정]인 회차에서 '실제 진입 인원 ÷ 오픈 30분 전 구독 수'의 중앙값과 75번째 백분위로 잡는다. 규모 등급으로 나누지 않는 것은 등급을 정하기 전에 쓰는 값이기 때문이다.
     - 그런 회차가 10개보다 적으면 기본 비율로 중앙 2.0·상단 3.0 [가정, 실제 회차 10개로 교체]을 쓰고 화면에 '기본 비율'로 표시한다.
     - 구독 수는 core-svc가 회차별 수만 넘긴다(계정 없음).
   - **등급 제안**: 상단 값을 architecture §9.5의 경계(예상 대기 인원: 대형 50만 명 이상, 중형 10만~50만 명, 소형 10만 명 미만)와 비교해 등급을 제안한다. 오픈 직후 진입이 한꺼번에 몰리므로 진입 인원을 대기 인원으로 본다 [가정].
   - **판매 승인(SCR-048)**
     - 구독 수, 예상 진입 인원(중앙·상단), 비율에 쓴 회차 수, 제안 등급을 보인다. 등급은 운영자가 정한다.
     - 승인 때는 구독이 다 모이기 전이라(구독은 주로 오픈 7일 전부터 늘어난다, POL-030) 예측이 낮게 나온다. 그래서 운영자는 공연장 규모와 판단으로 제안보다 높게 정할 수 있다.
   - **다시 계산**
     - 승인 뒤 오픈 전까지 매일 09:00 [가정]과 T-30분에 다시 계산한다.
     - 상단 값이 지금 등급의 상한을 넘으면 '규모 올리기 검토' 경보(`kind` control)를 낸다. SEV3이고, 오픈 24시간 [가정] 안이면 운영자가 콘솔에서 바로 보도록 SEV2다.
     - T-30분 점검의 CDN 한도 대조는 그때의 예측 상단을 쓴다.
   - **규모 올리기**
     - 승인 뒤에는 T-30분 점검이 시작되기 전까지 올리기만 할 수 있다. operator 1인이 사유를 적고 감사 로그에 남는다. 내리기는 하지 않는다.
     - 올리면 변경 동결 달력이 다음 갱신(10분 안)에 창을 다시 계산한다(docs/devops.md §8.1).
     - 대형으로 올리면 다른 대형과의 30분 간격을 검사한다(409). 간격에 걸리면 commander가 재인증하고 사유를 적어 '간격 예외'로 올릴 수 있다. 이때 두 회차의 CDN 한도와 동결 창을 다시 확인한다.
     - 간격 예외를 올리기에만 두는 이유: 승인 뒤에는 오픈 시각이 이미 알려져 옮기기 어렵고, 올리지 못하면 준비가 모자란 채 열게 된다. 처음 승인 때의 간격 검사는 그대로 막는다(ADR-0062).
   - **사후 대조**
     - R1은 승인 때 등급과 T-30분 예측을 덮어쓰지 않고 그대로 둔다. 실제 진입 인원으로 정한 '실제 등급'은 따로 남긴다.
     - 지표 사전 31번 '수요 예측 오차'(실제 진입 인원 ÷ T-30분 예측 중앙·상단)를 두고, 다음 예측의 비율이 이 값으로 갱신된다.
   - **이번 범위 밖**: 프리워밍 크기나 초기 동시 입장 목표를 예측에 묶는 것은 하지 않는다. 오차가 쌓인 뒤 다시 본다.
   - **머신러닝 수요 예측**: 실제 운영 데이터가 쌓이고 식의 오차가 크면 새 ADR로 검토한다(되돌릴 조건).
2. **자동 조치마다 끝내는 조건을 정한다(추천 적용)**:
   - docs/architecture.md §5에 '상태가 남는 자동 조치와 끝내는 조건' 표를 둔다. 조치마다 시작 조건, 알림·효과 확인, 끝내는 조건(자동 해제 기준 또는 해제하는 사람과 명령)을 적는다. 한 번 실행하고 끝나는 조치(결제-발권 60초 자동 보상, 상태 미확정 자동 대사)는 대상이 아니다.
   - 이번에 새로 정한 끝내는 조건은 아래와 같다.

     | 자동 조치 | 끝내는 조건 |
     | --- | --- |
     | 실시간 표의 Prometheus 대체 표시 | 신선도 p95가 5초 미만으로 5분 [가정] 이어지면 자동으로 되돌아간다 |
     | 결제 신규 진입 일시 정지(결제사 장애, 채널 상한 대기 지연) | 그 결제사의 서킷이 닫혀 있고 결제 확정 소요 p99가 5초 아래로 5분 [가정] 이어지면 자동으로 푼다. 재시도 큐에 남은 건은 승인 기한으로 끝난다 |
     | 결제사 채널 상한 낮춤(429) | 그 회차 동안 낮춘 값을 유지한다. 다음 회차의 값은 R1 검토에서 정한다(ADR-0036 추정의 갱신) |
     | 28일 예산 소진 배포 잠금 | 28일 창의 남은 예산이 다시 0보다 크면 자동으로 풀린다. commander는 P0 후속 조치가 남았으면 사유를 적어 연장할 수 있다. 잠금 중에도 긴급 변경은 RB-23으로 한다 |
     | 실패 메시지(DLQ) 적재 | 1건이라도 쌓이면 SEV3(`kind` hygiene)다. 원인을 고친 뒤 엔지니어가 RB-11에 더한 재처리 절차로 다시 넣는다. 컨슈머가 멱등이라(docs/architecture.md §3) 이미 반영된 메시지는 건너뛴다 |

   - **대기 상태 파일의 S3 우회**는 두 가지로 나눈다.
     - 자동: CloudFront 원본 그룹이 원본 오류(500·502·503·504) 때 요청마다 S3 사본으로 넘기고, 다음 요청은 다시 원래 원본으로 간다. 연결 시간 초과 2초·시도 1회 [가정]로 줄인다. 보조 원본은 같은 요청 경로를 받으므로 S3 사본의 키를 요청 경로에 맞춘다 [가정, wbs 2.2.2에서 확인].
     - 수동: 명령 6은 원본이 살아 있어도 S3 사본으로 '고정'하는 조작이다. 해제도 명령 6이다(RB-04).
     - infra §4와 control-tower의 서술을 이렇게 맞춘다.
3. **운영 명령을 그래프에 남기고 내부 서비스 지도를 그린다(추천 적용)**:
   - **운영 명령 주석**
     - ops-svc는 명령의 요청·승인·ack·만료·되돌리기와 결정 2의 자동 조치의 시작·끝(ops-svc가 받은 알림과 상태로, 행위자 SYSTEM)을 운영 사건 줄(`ops_event`)로 로그에 남긴다. CloudFront 원본 그룹의 요청별 넘김은 CloudFront 지표로만 본다. 이 줄은 표본 대상이 아니다(전수).
     - 담는 값은 명령 번호와 이름, 회차, 단계, 행위자 역할이다. 사람 이름과 계정은 넣지 않는다.
     - 대시보드(Dashboards as Code)는 이 줄을 Loki 주석 조회로 그래프에 표시한다. 배포 주석과 함께 보인다.
     - 주석 쓰기 토큰을 새로 만들지 않으려고 이 방식을 고른다. 무료판의 주석 쓰기는 Editor 권한이 필요하다.
     - Loki 보존이 30일이라 그보다 오래된 명령은 감사 로그와 사고 재현 화면에서 본다.
   - **내부 서비스 지도**
     - Tempo metrics-generator의 서비스 그래프를 켠다. 위상(연결)만 보는 `traces_service_graph_connection_info`로 Grafana 노드 그래프 패널에 그린다.
     - 우리 요청 기록은 꼬리 표본이라 서비스 그래프의 요청 수와 지연은 왜곡된다. 그래서 그 값은 판단에 쓰지 않고, 요청 수와 지연은 지금처럼 Prometheus 지표로 본다.
     - metrics-generator는 Mimir `raw` 테넌트로 바로 원격 쓰기를 한다. '지표는 Prometheus가 긁는다'(ADR-0076 결정 2)의 예외다. 경보와 자동 제어에 쓰지 않는 지표라서 허용한다.
4. **원인 유형을 정해 포스트모템과 런북을 묶는다(추천 적용)**:

     - 더하는 칸: 주 원인 유형과 구성 요소(1개), 기여 원인 유형(여러 개), 계기, 영향(예산 사용, 영향 받은 회차), 쓴 손잡이(명령·런북), 후속 조치(GitHub Issues 링크, P0 여부)
   - **'같은 종류의 장애'**(POL-022): 주 원인 유형과 구성 요소가 같은 장애다.
   - **분기 검토**
     - 유형·구성 요소별 건수, 28일 예산 사용, 탐지 경로를 보고 새 경보·런북·설계 과제를 정한다.

5. **경보 위생 보고를 둔다(추천 적용)**:
   - **월간 보고**
     - ops-svc는 받은 모든 경보(`OpsAlert`)의 기록과 감사 로그로 월 1회 '경보 위생 보고'를 만들어 GitHub Issues에 올린다.
     - 보고 항목: 등급·종류별 경보 수, 온세일당 경보 수, 주당 호출(SEV1) 수, 조치 없이 닫힌 경보 목록.
     - '조치 없이 닫힌 경보'는 발생 뒤 24시간 안에 연결된 인시던트·명령·이슈가 없는 경보다.
   - **Grafana 패널**: Prometheus `ALERTS`로 대기→발생 전환과 대기만 하다 끝난 경보의 비율을 보여 `for:` 길이를 고르는 데 쓴다.
   - **검토**: NFR-023 '미조치 알림 0건'은 이 보고로 잰다. 담당은 플랫폼(SRE) 온콜 책임자다. 조치 없이 닫힌 경보마다 조정·삭제·사유를 적고 유지 가운데 하나를 고른다.
   - **ADR-0049와의 관계**: ADR-0049가 보류한 '온콜 부담·경보 정밀도'는 이 보고의 건수와 '조치 없이 닫힌 비율'로 잰다.

     | 조직 | 데이터 소스 | 구성원 |

7. **클러스터 규모의 근거를 적는다(추천 적용)**:
   - **추정 칸**
     - docs/architecture.md §9.5에 피크 노드·파드 수 추정 칸을 둔다.
     - Phase 2 측정(wbs 2.12.1)의 서비스별 피크 복제 수와 wbs 4.8.1의 비용 추정에서 채운다.
   - **판단 기준**
     - 노드 1,000개·파드 3만 개 [가정] 이하(쿠버네티스 공식 한계의 20%)면 클러스터 하나로 간다.
     - 넘으면 셀 분리(ADR-0028)를 새 ADR로 검토한다. 멀티 클러스터도 그때 같이 본다.
   - **CNI**
     - EKS 기본 Amazon VPC CNI를 쓴다고 적는다. 파드마다 VPC 사설 IP를 쓰므로, 서브넷은 피크 파드 수의 2배 [가정] 이상 IP를 갖게 정한다.
     - 서비스 메시 선택(Linkerd와 Istio PoC)은 그대로다.
   - **업그레이드**: 지금처럼 제자리 업그레이드(정비 시간, 스테이징 먼저)로 한다.
8. **네임스페이스 지도와 자원 할당량을 둔다(추천 적용)**:
   - **지도**
     - docs/devops.md에 네임스페이스 지도(네임스페이스, AppProject, 주요 워크로드, 노드 풀, 자원 할당량)를 둔다.
     - 네임스페이스는 ArgoCD AppProject(가상 팀)와 맞추고, 클러스터 애드온은 차트의 기본 네임스페이스를 쓴다. 세부 배치는 [가정, wbs 0.4.4에서 확정]이다.
   - **자원 할당량(ResourceQuota)**
     - `data`·`observability` 네임스페이스에만 둔다. 값은 그 노드 풀(Karpenter NodePool)의 `limits`의 80% [가정]다. 배치 작업이나 잘못된 설정이 그 노드 풀을 다 쓰는 것을 막는다.
     - 수집기(모든 노드에 뜨는 에이전트 DaemonSet 포함)와 exporter는 클러스터 애드온이라 `otel` 네임스페이스(platform 프로젝트)에 따로 둔다. 노드가 늘 때 새 노드의 에이전트가 `observability`의 할당량에 막히지 않게 하려는 것이다.
     - 핫패스와 서비스 네임스페이스, 플랫폼 컨트롤러에는 두지 않는다. 오픈 때 확장을 할당량이 막으면 안 되기 때문이다. 이들은 노드 풀 분리와 Kyverno의 requests·limits 강제로 지킨다.

## 결과와 트레이드오프

- **남는 한계**
  - 수요 예측은 구독 수에 기대므로 구독하지 않고 들어오는 수요(급히 화제가 된 공연)를 늦게 잡는다. 그래서 매일 다시 계산하고, 오차를 R1에 남긴다.
  - 판매 승인 때는 구독이 다 모이기 전이라 예측이 낮게 나온다. 운영자가 공연장 규모와 판단으로 더 높게 정할 수 있게 했다.
  - 규모를 올리면 이미 잡힌 다른 대형 공연과 30분 간격이 겹칠 수 있다. 그때는 commander의 간격 예외로만 간다.
  - 운영 명령 주석은 Loki 보존(30일) 동안만 그래프에 보인다.
  - 서비스 지도는 연결만 보이고 요청 수·지연은 보이지 않는다.
  - Grafana 조직 둘은 사람이 두 곳을 오가야 한다.
  - 클러스터 규모 추정 칸은 측정 전이라 비어 있다(wbs 2.12.1·4.8.1에서 채움).
  - 이 한계들은 planning/01 §5.2에 적었다.
- **반영 수치(2026-10-21)**
  - ADR 77 → 78, 지표 사전 30 → 31, 용어 2개(예상 진입 인원, 원인 유형), REST 경로 2개(수요 예측 조회, 규모 올리기), 시험 C-T43~C-T45
  - WBS +4.75일(407.75 → 412.5일): 0.4.4 +0.25, 2.7.5 +0.25, 4.1.2 +0.5, 4.1.4 +0.25, 4.2.1 +0.25, 4.2.4 +0.5, 4.3.5 +0.25, 4.4.1 +0.25, 4.4.3 +0.25, 4.5.2 +0.5, 4.7.1 +0.25, 4.8.1 +0.25, 7.2.2 +1
  - 검토 기록 R-87, 가정 표시 38곳·보완 표시 1곳 증가(점검 도구 집계)
  - 디자인 캔버스의 SCR-048 보드는 고치지 않았다. 수요 예측 줄과 [규모 올리기]는 design/d5 §7.9 와이어프레임에만 그렸다.

## 되돌릴 조건

- 실제 회차가 쌓인 뒤에도 수요 예측의 상단을 실제가 넘는 회차가 분기에 두 번 넘게 나오면 비율 식을 다시 정하거나 학습 모델 예측을 새 ADR로 검토한다.
- 피크 노드·파드 추정이 결정 7의 기준을 넘으면 셀 분리를 새 ADR로 검토한다.
- 원인 유형 가운데 '기타'로 적어야 하는 장애가 분기에 두 번 넘게 나오면 유형 목록을 고친다.
- Grafana 민감 데이터 소스가 셋을 넘으면 Enterprise의 데이터 소스 권한이나 AMG를 다시 본다.
