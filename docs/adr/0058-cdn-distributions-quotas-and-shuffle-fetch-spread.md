# ADR-0058: CloudFront 배포를 셋으로 나누고 배포별 한도를 미리 올리며, 셔플 결과는 공개 예정 시각 뒤 0~8초에 나눠 받는다

- **상태**: 채택 (2026-10-13. review R-58에서 찾은 CloudFront 배포 한도 충돌을 00-summary §7 질문 25로 올렸고, 소유자가 추천안 네 가지(배포 나누기, 배포별 한도 상향, 셔플 결과 분산 조회, 회차별 S3 접두사)에 '네'라고 답했다. 분산 창 8초, 상향 목표 1.5배, 오류 캐시 1초, 재시도 간격, 경고 기준 같은 수치는 추천 적용(2026-10-13)이고 [가정]으로 표시한다. ADR-0003·0012·0041을 보완하고, ADR-0057의 외부 한도 대조에서 나왔다.) 2026-10-26: 결정 7의 배포별 한도 사용률은 CloudWatch(us-east-1)의 CloudFront `Requests`를 YACE로 가져와 Prometheus·Mimir에서 계산한다(docs/observability.md §8 지표 출처 표, ADR-0089). 한도 상향은 Service Quotas 화면이 아니라 AWS Support 한도 상향 케이스로 요청한다(AWS 문서, 2026-10-26 확인).
- **관련**: ADR-0003(적응형 폴링), ADR-0008(게이트웨이 호스트), ADR-0012(로비 셔플), ADR-0041(동시 도착 구간 묶음), ADR-0050(셔플 비콘), ADR-0057(외부 한도 대조), docs/infra.md §1·§4·§5, docs/features/queue-admission.md §2·§3·§4·§5·§11, docs/verification.md §4, docs/api/openapi.yaml
- **관련 ID**: FR-005, FR-006, FR-007, FR-038, NFR-001, NFR-002, NFR-007, POL-004, POL-005, POL-030, SCR-007

## 맥락

- **배포 하나의 기본 한도가 설계 피크보다 작다.** CloudFront 배포 하나의 기본 한도는 초당 요청 250,000건과 전송 150 Gbps이고, 둘 다 상향을 요청할 수 있다(AWS 할당량 문서, 2026-10-13 확인). 공연 페이지 피크 30만 RPS(NFR-007)는 혼자서도 넘는다. 대기열 쪽은 T=0 직후 진입 20만 RPS(NFR-001)에 셔플 결과 조회(로비 100만 명 × 약 36 KB = 약 36 GB)와 대기 상태 조회(초당 약 5.3만 건, NFR-002)가 같은 배포에서 겹치면 넘는다(review R-58).
- **셔플 결과를 언제 받는지 정해져 있지 않았다.** 대기자 100만 명이 게시 전부터 결과 파일을 묻기 시작하면 그 요청만으로 한도를 넘는다. CloudFront는 원본이 돌려준 404를 오류 캐시 최소 TTL(기본 10초) 동안 캐시하므로(AWS 'How CloudFront processes HTTP 4xx and 5xx status codes', 2026-10-13 확인), 게시 직전에 물은 사람은 게시 뒤에도 최대 10초 동안 '셔플 전'을 받는다.
- **늦게 받는 사람이 불리하면 안 된다.** 순번은 셔플로 이미 정해지지만, 첫 입장이 시작된 뒤에 자기 순번을 알면 입장 확정과 좌석 선택이 그만큼 늦어진다.
- **대체 경로 파일의 S3 쓰기가 정해져 있지 않았다.** S3는 접두사(파티션)마다 초당 PUT 3,500건·GET 5,500건 이상을 내고, 요청률이 늘어나는 동안 503을 줄 수 있다(AWS S3 성능 문서).
- **확인하지 못한 것.** 상향 요청이 승인되는지와 처리에 걸리는 기간, 한도를 넘을 때 CloudFront가 어떤 응답을 주는지는 AWS 문서에서 확인하지 못했다.

## 검토한 대안

| 대안 | 문제 |
| --- | --- |
| 1. 배포 하나에 한도 상향만 | 공연 페이지·진입·파일이 한 한도를 나눠 쓰고, 한쪽 폭주가 다른 쪽을 막는다. 승인 여부와 기간을 모른다 |
| 2. 배포만 나누고 상향 없음 | 공연 페이지 30만 RPS는 배포 하나로도 넘는다 |
| 3. 셔플 파일을 1만 개로 쪼개 크기 줄이기 | 전송은 1/10이 되지만 요청 수는 그대로이고, T=0에 게시할 파일이 10배(S3 PUT 1만 건)가 된다. 분산 조회로 전송이 충분히 줄면 필요 없다 |
| 4. 엣지 함수가 순번을 계산해 응답 | 엣지 함수 요청도 배포 요청이라 한도를 풀지 못하고, 셔플 결과를 엣지 저장소에 둬야 한다 |
| **5. 배포 셋 + 배포별 상향 + 분산 조회와 첫 입장 지연 + 회차별 S3 접두사(채택)** | 배포가 셋이라 설정과 웹 방화벽 규칙도 셋을 맞춰야 한다. 순번을 늦게 받는 사람은 최대 8초 동안 자기 순번을 모른다 |

## 결정

1. **배포를 셋으로 나눈다.** 소비자 트래픽은 다음 세 배포로 받는다. 구매(`api`)·파트너·관제 호스트는 따로 배포를 두고, 피크가 기본 한도보다 훨씬 작다. 게이트 스캐너는 CloudFront를 거치지 않는다.

   | 배포 | 호스트 | 받는 것 | 원본 | 설계 피크(100만 기준) |
   | --- | --- | --- | --- | --- |
   | 공연 페이지 | `www.peaket.example` | 공연 페이지, 대기실 셸, 웹 정적 자산 | 웹 앱 서버(NLB → Envoy), 정적 자산은 S3 | 초당 30만 건(NFR-007) |
   | 대기열 파일 | `queue-files.peaket.example` | 대기 상태 파일, 셔플 결과 파일, 묶음 결과 파일 | gw-queue 파일 원본, 대체 원본은 S3 | 셔플 결과 분산 조회 초당 약 12.5만 건 + 대기 상태 조회 초당 약 5.3만 건 = 약 17.8만 건, 전송 약 36 Gbps |
   | 대기열 API | `queue.peaket.example` | 로비 입장, 사전 검증, 진입, 입장 확정, 엣지 함수(매진 응답, 도착 시각 쿠키) | NLB → gw-queue | 초당 20만 건(NFR-001) |

2. **배포별 한도를 미리 올린다.** 배포마다 그 배포 설계 피크의 1.5배 [가정] 이상으로 요청 한도 상향을 요청한다. 공연 페이지 45만, 대기열 API 30만, 대기열 파일 27만이다 [가정]. 전송은 대기열 파일 배포도 기본 150 Gbps 안이다(분산 조회 약 36 Gbps의 1.5배 = 54 Gbps). 승인 값과 요청일을 외부 한도 대조표(docs/verification.md §4)와 infra §4.1에 적는다. 처리 기간을 모르므로 출시 준비에서 운영 계정을 만들 때 요청한다. 대형 회차는 판매 승인 때 운영자가 그 회차 예상 피크가 승인 값 안인지 대조표로 확인하고, T-30분 점검이 다시 확인한다(필수 항목). 규모가 커지면 다시 요청한다. 200만(docs/architecture.md §9.2)이면 대기열 API는 60만, 3년차 합산 300만(§9.5)이면 대기열 파일은 약 43만이 필요하다 [가정].
3. **셔플 결과는 공개 예정 시각 뒤 0~8초에 나눠 받는다.**
   - 참가 토큰 발급 응답에 결과 공개 예정 시각(`shuffleResultAt`)과 분산 창(`shuffleSpreadSec`, 8초 [가정])을 싣는다. 공개 예정 시각은 공시한 drand 라운드의 예정 시각에 셔플·게시 목표 시간(Q-T6, [가정])을 더한 값이다. 대기실(SCR-007)은 '오픈 뒤 몇 초 안에 순번이 공개되고 사람마다 몇 초씩 나눠 받는다'고 미리 알린다. 순번을 떠올리게 하는 숫자는 쓰지 않는다(POL-004).
   - 브라우저는 참가 토큰 해시의 앞자리로 파일을 고르고, 해시의 다음 4바이트를 `shuffleSpreadSec × 1000`으로 나눈 나머지(밀리초)만큼 공개 예정 시각 뒤에 기다렸다가 받는다. 토큰마다 고정이라 새로고침해도 빨라지지 않는다.
   - 파일이 아직 없으면(404) 2초부터 두 배씩, 최대 20초 [가정] 간격으로 그 안에서 무작위 시각에 다시 묻는다. 그동안 대기실은 '순서 계산 중'을 보여 준다(비콘 지연 때와 같은 화면, queue-admission §2).
   - 대기열 파일 배포는 결과 파일 경로의 404 오류 캐시 최소 TTL을 1초 [가정]로 둔다. 기본값(10초)이면 게시 뒤에도 최대 10초 동안 '셔플 전'이 나간다.
   - 동시 도착 구간 묶음(ADR-0041)의 결과 파일도 같은 규칙을 쓴다. 202 `BATCHING` 응답에 결과 파일 경로, 결과 공개 예정 시각, 분산 창을 싣는다.
   - 효과: 100만 건을 8초에 나누면 초당 약 12.5만 건, 전송 약 36 Gbps다. 공개가 늦어지면 재시도 간격이 늘어나 묻는 횟수가 줄어든다.
4. **첫 입장은 분산 창이 끝난 뒤 시작한다.** admission-ctrl은 결과 파일로 순번을 알리는 구간(로비 셔플, 동시 도착 묶음)마다, 그 결과를 실제로 게시한 시각 + 분산 창이 지나기 전에는 serving을 그 구간의 첫 번호 위로 올리지 않는다. 그래서 순번을 늦게 받은 사람도 첫 입장 전에 자기 순번을 안다. 매진까지 걸리는 시간은 최대 약 8초 늘어난다.
5. **S3에는 회차별 접두사로 쓴다.** 셔플 결과 파일과 대체 경로용 대기 상태 파일은 `queue/{eventId}/shuffle/…`, `queue/{eventId}/fallback/…` 접두사에 쓴다. 대체 경로 파일은 원 파일과 같은 주기(거리별 캐시 수명)로 쓰며, 100만 기준 초당 수백 건 이하 [가정, 2.2.2에서 확인]로 접두사 기준치(초당 PUT 3,500건) 안이다.
6. **셔플 파일은 1,000개로 둔다.** 분산 조회로 전송이 약 36 Gbps에 그치므로 파일을 더 나누지 않는다. 분산 조회 실측에서 대기열 파일 배포의 전송이 승인 한도의 2/3를 넘으면 다시 본다.
7. **감시.** 배포별 요청 수 지표(CloudWatch)를 승인 한도로 나눈 한도 사용률이 80% [가정]를 넘으면 SEV3 경고를 낸다(docs/observability.md §5). 온세일 피크의 사용률은 공연 리포트에 남겨 다음 상향 요청의 근거로 쓴다.

## 남는 한계

- 상향 요청이 승인되는지와 처리 기간, 한도를 넘을 때의 응답은 AWS 문서에서 확인하지 못했다. 승인 전에는 공연 페이지 피크를 기본 한도로 받을 수 없다.
- 순번을 늦게 받는 사람은 최대 8초 동안 자기 순번을 모른다. 입장 순서는 바뀌지 않지만 매진까지 걸리는 시간이 최대 약 8초 늘어난다.
- 규칙을 어기고 일찍 묻는 브라우저(수정한 클라이언트, 봇)는 막지 못한다. 그 요청은 404 캐시(1초)와 웹 방화벽 요청률 규칙으로만 줄인다.
- 배포가 셋이라 설정, 인증서, 웹 방화벽 규칙을 셋에 맞춰야 한다.

## 되돌릴 조건

- 상향이 거절되면 공연 페이지 피크를 줄이는 쪽(정적 셸의 캐시 수명 늘리기)이나 배포를 더 나누는 쪽을 다시 본다.
- 분산 조회 실측에서 대기열 파일 배포의 전송이 승인 한도의 2/3를 넘으면 셔플 파일을 나눈다.
- 분산 창 8초가 입장 시작을 눈에 띄게 늦추면(공연 리포트의 첫 입장 시각) 창을 줄이고 상향 값을 다시 계산한다.
