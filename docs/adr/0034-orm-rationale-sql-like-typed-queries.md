# ADR-0034: ORM 기술 선정 근거 보강 (SQL 지향 타입 안전 쿼리 채택 및 런타임 성능 가설 검증)

- **상태**: 대체됨 (2026-10-09 채택, 같은 날 ADR-0035가 대체했고 확인 결과는 ADR-0037이 이어받는다. ADR-0017의 '이유 확인 필요'를 채운 기록으로 보존한다)
- **관련 문서**: ADR-0017, ADR-0035, ADR-0037, docs/architecture.md §6.1, docs/data.md §2·§4·§5, docs/features/seat-hold.md §6
- **관련 ID**: NFR-003, NFR-006, NFR-025, FR-010, FR-011, FR-047, K3

## 맥락
- ADR-0017은 Prisma·TypeORM을 '비교 후 기각'했다고만 적었고, 비교 사유는 원문에 없었다.
- 소유자 답변(2026-10-09): 성능이 유리하고, 쿼리를 쓰는 방식이 SQL과 비슷해 읽기 쉬워서 골랐다. 이것이 맞는 근거인지 확인해 달라고 했다.
- 공식 문서로 확인한 것(2026-10-09):

| ORM | 확인한 사실 |
| --- | --- |
| Drizzle | 'If you know SQL, you know Drizzle'을 내세우고, SQL에 가까운 방식으로 읽으면서 타입 안전성을 유지한다고 설명한다. 스키마에서 타입을 추론한다(`$inferSelect`). drizzle-kit이 SQL 마이그레이션 파일을 만든다. 인덱스 정의에 `.where(sql…)`로 부분 인덱스를 둔다. 잠금 절(`FOR UPDATE`, `SKIP LOCKED`) API는 문서 사이트에서 찾지 못했다(소스에는 있음이 ADR-0037에서 확인됨) |
| Prisma | 기본 쿼리 API는 SQL 형태가 아니고, SQL은 `$queryRaw`나 TypedSQL(Preview)로 따로 쓴다. 부분 인덱스는 `partialIndexes` Preview 기능이 필요하다. Prisma 7은 Rust 기반 쿼리 엔진 대신 Rust 없는 클라이언트와 드라이버 어댑터(node-pg)를 쓴다 |
| TypeORM | QueryBuilder가 SQL을 만드는 문법이고, `setLock('pessimistic_write')`와 `setOnLocked('skip_locked')`로 `FOR UPDATE SKIP LOCKED`를 지원한다. 조건은 `"user.name = :name"` 같은 문자열로 쓴다 |

- 세 ORM의 처리 성능을 비교한 공식 수치는 찾지 못했다. Drizzle 문서에는 성능 비교 수치가 없고 라이브러리 크기(약 7.4kb, 의존성 0)를 적는다.

## 결정
1. Drizzle 채택을 유지한다. 근거는 다음 두 가지로 명문화한다.
   - **SQL 지향성과 정적 타입 검증의 결합**: 핫패스 쿼리를 리뷰하고 튜닝할 때(K3의 EXPLAIN, 정렬 잠금, 1인 한도 조건부 갱신) 실행되는 SQL을 코드에서 바로 읽을 수 있고, 컬럼 이름 오타는 컴파일 때 잡힌다. Prisma는 SQL이 별도 경로이고, TypeORM은 SQL에 가깝지만 조건이 문자열이라 타입 검사를 받지 못한다.
   - **SQL 파일 기반 마이그레이션과 정식 부분 인덱스 지원**: 스키마와 마이그레이션이 SQL 파일로 남고, 취소표 재판매를 위한 `seat_sale`의 활성 상태 부분 유니크 인덱스(docs/data.md §2)를 Preview 플래그 없이 정식 기능으로 정의한다. Prisma에서는 같은 기능이 Preview다.
2. 잠금 절은 Drizzle 문서 사이트에 API 설명이 없으므로 `sql` 템플릿으로 쓰고 파라미터 바인딩을 지킨다(ADR-0017의 인젝션 방지 그대로). 쿼리 빌더가 잠금 절을 지원하는지는 서비스 템플릿 작업(wbs 0.3.2)에서 다시 확인한다.
3. 성능 우위는 결정 근거에서 뺀다.
   - 공식 비교 수치가 없다.
   - Prisma 7이 쿼리 엔진을 바꿔 예전 비교가 맞지 않을 수 있다.
   - PEAKET의 PostgreSQL 부하(판매 확정 초당 약 28건, 결제 피크 300 TPS)에서는 ORM 처리 시간보다 잠금 대기와 네트워크가 지배적일 가능성이 크다.
   - 그래서 Phase 2 After 측정(wbs 2.12.1)의 트레이스에서 ORM 구간 시간을 기록해 확인하는 검증 가설로 전환한다.

## 검토한 대안
| 대안 | 기각 사유 및 한계점 |
| --- | --- |
| Prisma 채택 | 기본 쿼리가 SQL 형태가 아니어서 핫패스 SQL을 따로 써야 한다. 부분 인덱스가 Preview(2026-10-09 문서)다. 성능 비교는 Prisma 7의 엔진 변경 뒤 다시 재야 한다. |
| TypeORM 채택 | QueryBuilder가 SQL에 가깝고 잠금 절도 지원하지만, 조건을 문자열로 써서 타입 검사를 받지 못한다. |

## 결과와 트레이드오프
- 소유자의 두 근거 중 '읽기 쉬움(SQL과 비슷한 쿼리)'은 공식 문서로 확인되어 유지하고, '성능'은 측정할 가설로 바꾼다.
- 대가: 잠금 절처럼 `sql` 템플릿으로 쓰는 부분은 타입 검사 밖에 있다. TypeORM의 잠금 API를 쓰지 않는다.
- 되돌릴 조건: 2.12.1 측정에서 ORM 구간이 결제 확정 예산 중 PG 밖 1초(NFR-006, payment §2)에서 의미 있는 비율을 차지하면, 핫패스만 드라이버 직접 호출로 바꾸는 것을 검토한다.
