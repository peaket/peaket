# ADR-0244: 공연 설명은 구조 문서와 글자판을 함께 저장하고, 전산망 항목은 파트너가 적는 두 칸만 받는다

- **상태**: 채택(2026-11-09, 추천 적용. wbs 2.9.1 세부는 추천 적용이라는 승인을 따른다). BUILD_ORDER HOT-183.
- **관련**: [docs/api/openapi.yaml](../api/openapi.yaml), [docs/features/transfer-refund.md](../features/transfer-refund.md) §2.4, [docs/security/asvs/catalog-review.md](../security/asvs/catalog-review.md) 1.3.1, ADR-0198, ADR-0200 결정 1, ADR-0204
- **관련 ID**: FR-022, FR-054, CMP-070, ASVS v5.0.0-1.3.1

## 맥락

- 공연 설명은 HTML이 아니라 허용 노드 다섯만 담은 구조 문서로 받기로 했고(asvs 1.3.1, ADR-0204), 등록 본문에는 아직 칸이 없었다.
- 공연예술통합전산망 10개 항목 가운데 대부분은 다른 칸(공연명·회차·공연장·가격)이나 판매 집계에서 온다. 파트너가 따로 적는 것은 화면 기준으로 기획사·제작사와 안내 사항뿐이다.

## 결정

1. **계약**: `PartnerProductionCreate`에 `description`(`ProductionDescriptionDoc`)과 `kopisFields`(`producer`·`notice`)를 선택 칸으로 더한다. 위저드가 임시저장하므로 등록 때는 필수가 아니고, 전산망 항목의 필수 여부는 판매 승인 요청이 본다. 공연 상세 `EventPublicSummary`에 `description`을 더한다.
2. **저장**: 구조 문서는 `production.description_doc`(jsonb)에 그대로 두고, 글자판은 서버가 문서에서 만들어 지금의 `description`에 둔다. 글자판은 검색과 서식 없는 화면이 쓴다.
3. **검사는 서버가 다시 한다**: 노드 다섯과 속성은 닫힌 스키마로, 블록 200개·글자판 20,000자·노드 5,000개 [가정]는 합계로 본다. 글자 수는 만들어진 글자판 전체로 재서(블록 사이 빈 줄 포함) 공연 상세가 글자판을 잘라 서식 문서와 어긋나지 않게 한다. 글자판의 블록 사이는 빈 줄이다(공연 상세 화면이 빈 줄로 문단을 나눈다). 화면 쪽 `doc.ts`와 같은 규칙이다.
4. **저장할 수 없는 글자를 막는다**: NUL 문자와 짝이 깨진 서로게이트는 PostgreSQL `jsonb`·`text`가 받지 못해 500이 되므로, 등록 본문의 글자 칸(공연명·관람 연령·새 공연장·새 아티스트·다른 이름·설명·전산망 항목)을 400으로 거절한다.
5. **내용 없는 문서는 설명이 없는 것이다**: 글자판이 비면 둘 다 저장하지 않는다. 공연 상세가 빈 설명 칸을 그리지 않는다.

## 결과

- 소비자 웹은 HOT-185부터 `description`으로 서식을 그릴 수 있다. 그때까지는 `descriptionText`를 그린다.
- 판매 승인 요청의 전산망 항목 필수 검사와 공연 정보 고치기는 그 경로를 만드는 단계의 일이다.

## 다른 선택지

| 길 | 고르지 않은 까닭 |
| --- | --- |
| 구조 문서만 저장하고 글자판은 읽을 때 만든다 | 공개 응답마다 변환하고, 검색 색인도 따로 문서를 풀어야 한다 |
| `description` 칸에 JSON 문자열을 넣는다 | 지금 글자판으로 읽는 경로가 깨진다 |
| 10개 항목을 모두 등록 본문에 받는다 | 회차·가격·집계 값을 두 번 적게 되어 어긋난다 |
