# ADR-0067: 관제 콘솔과 관측 도구의 역할 경계, 관측 백엔드는 재 보고 고른다(2026-10-19)

- **상태**: 채택 (2026-10-19. 소유자가 "운영 콘솔은 Sentry나 Datadog과 별반 차이 없지 않나, 직접 만들려면 합당한 이유가 있어야 한다"고 묻고, 이어진 답(역할 경계, 화면 원칙, 재 보고 고르는 방법)에 "대체로 동의합니다. 반영 해주시고요"라고 했다. 결정 1·2·3·5·7은 소유자 승인이고, 결정 4·6과 판정 규칙의 수치는 추천 적용으로 소유자 검토 대상이다. 외부 서비스와 법령 사실은 2026-10-19 각 공식 문서와 국가법령정보센터 원문으로 확인했다. 같은 날 보완(소유자 요청 "Sentry 무료 등급 제약을 … 결정 6의 판정 조건에 넣어 주세요"): Sentry 가격표(2026-10-19)상 무료 Developer는 사용자 1명·월 오류 5천 건·화면 녹화 50개이고 알림은 이메일이며, 'API·외부 연동'은 Team(연간 결제 기준 월 $26, 사용자 무제한·월 오류 5만 건) 기능이다. 그래서 결정 4의 콘솔 요약 연결은 클라우드라면 Team 이상에서만 된다고 보고(무료 등급의 실제 API 범위는 4.1.3에서 확인), 결정 6의 판정 조건에 다음을 더해 읽는다. ① 클라우드 쪽 비용에는 Team 이상 요금과 온세일 오류 피크에 따른 추가 이벤트 요금을 넣고, 직접 설치 쪽 비용에는 서버 비용과 운영 시간을 넣어 견준다. ② 포트폴리오 측정 기간에는 지출 상한(5만 원) 안에서 유료 등급을 쓰지 않는다. 오류 묶기는 무료 Developer로 확인하고, 콘솔 요약 연결 시험(C-T30)은 PC에 직접 설치한 Sentry로 한다. 직접 설치는 메모리 16GB + 스왑 16GB 이상이라 부하 시험과 같은 시간에 돌리지 않고, 자원이 모자라면 Team 체험(기간 확인 필요)으로 대신한다(②는 추천 적용). 2026-10-20 ADR-0068(소유자 요청)이 결정 5의 비교 대상에 AWS 관리형(AMP가 Mimir 자리, AMG가 Grafana 자리, 서울 리전)을 더하고, 판정 규칙을 세 후보에 함께 적용하도록 정리했다. R2는 R1·R3를 통과한 후보 가운데 연간 총비용이 가장 낮은 것을 고르는 규칙으로 읽는다. R1은 ADR-0068 결정 2(제어 입력과 실시간 위젯은 어느 후보든 클러스터 안 Prometheus를 읽는다)에 따라 콘솔의 장기 조회와 엔지니어 화면에만 적용해 읽는다) 2026-10-20(ADR-0069): 판단 위젯마다 연결 판단(명령 번호·런북·엔지니어 호출)을 적고, 운영 명령이 없는 체감·느린 쿼리·네트워크는 판매 중 탭의 '진단 힌트' 묶음으로 모은다. 위젯 구성과 '자세히 보기' 링크, iframe 없음 원칙은 그대로다. 디자인 캔버스의 SCR-029 판매 중 탭(R-76에서 미룸)을 그렸다. 2026-10-21(ADR-0076): 결정 5의 '체험 기간 확인 필요'를 닫는다. Datadog 무료 체험은 14일이고(공식 체험 페이지), 체험 뒤 사용분은 과금된다(Plan & Usage 문서). 그래서 4.8.2의 Datadog 측정은 14일 안에 끝내고 체험이 끝나기 전에 에이전트와 연동을 지운다. 같은 14일 안에 Watchdog 이상 탐지 힌트 비교(ADR-0076 상태 줄)도 한다. 2026-10-21(ADR-0078 결정 6): 직접 운영하는 Grafana 무료판에는 데이터 소스별 권한이 없어, 쿼리 문장을 보는 PostgreSQL 데이터 소스는 제한 조직 'PEAKET 제한'에만 두고 지정한 DB 담당 엔지니어만 넣는다(docs/observability.md §9). 2026-10-26(4차 점검 3부): 결정 4의 브라우저 화면 녹화는 운영에서 쓰지 않는 것으로 읽는다(ADR-0079 결정 15, docs/frontend.md §5.16).
- **관련**: ADR-0022(TCP 대역 외 제어), ADR-0032(온콜·상태 페이지 도구), ADR-0049(관제 지표), ADR-0053(감사 체인), ADR-0057(검증 방법), ADR-0061(콘솔 휴대폰·태블릿), ADR-0065(관제 콘솔 CSP), FR-029, FR-030, NFR-009, NFR-017, POL-021, POL-022, SCR-029, docs/observability.md §1, docs/features/control-tower.md §1·§2·§12

## 맥락

- 소유자 질문(2026-10-19, 요지): ① 관제 콘솔은 Sentry·Datadog과 별반 다르지 않은데, 직접 만들려면 합당한 이유가 있어야 한다 ② Grafana를 따로 열어야 하면 '통합'이라고 할 수 있나 ③ Sentry·Datadog이 필요한 부분을 따로 깔기보다 콘솔 안에서 다 보면 읽기 쉽지 않나 ④ Datadog을 쓰지 않고 직접 설치·운영할 만한 이유가 있나. 그 의문을 풀 수 있는 기획이면 좋겠다.
- 문서 상태: docs/architecture.md §11은 'Datadog 등 상용 SaaS 평가'를 작성 예정으로 두었고, 부록 §13은 Datadog에 'ADR 없음'이라고 적었다. observability §1은 "Grafana는 관찰 전용, 콘솔은 제어·권한·감사"라고만 했다. control-tower §1의 '통합 제어 평면'은 모든 관측을 한 화면에 둔다는 뜻으로 읽힐 수 있었다. 콘솔 대시보드 '판매 진행 중'에는 Grafana·Sentry와 겹치는 포화도·RUM 위젯이 있었다. Sentry는 브라우저에만 썼고, 클라우드와 직접 설치 중 어느 것인지 정하지 않았다.
- 확인한 사실(2026-10-19 원문):
  - Datadog: Workflow Automation은 HTTP 호출을 포함해 2,000개 넘는 동작을 묶고, 흐름 제어는 조건·분기·대기·반복이다(승인 단계 없음). App Builder는 대시보드에 넣는 사내 도구 화면이다. Private Action Runner는 우리 망 안에서 Datadog으로 나가는 연결로 작업을 받아 실행한다. Audit Trail 보존은 3·7·15·30·90일이고 S3 등으로 15분마다 내보낼 수 있다.
  - Datadog 리전: US1·US3·US5·EU1(독일)·AP1(일본)·AP2(호주)·정부용. 한국 리전은 없다. BYOC Logs는 로그를 우리 객체 저장소에 두지만, 화면(Datadog SaaS)이 조회를 보내고 결과를 받는다.
  - Datadog 장애(2023-03-08, Datadog 사후 분석): US1·EU1·US3·US4·US5의 모든 서비스가 영향을 받았다. 06:03 UTC에 시작해 웹 접속은 09:13 UTC부터 돌아왔고, 모든 서비스 정상은 3월 9일 08:58 UTC였다.
  - Datadog 요금(미국 사이트 정가, 연간 계약): 인프라 Pro 서버당 월 $15, APM Enterprise(APM·Data Streams·Profiler) $40, DB 모니터링 DB 서버당 $70, 지표 조합은 서버당 100개(Pro)·200개(Enterprise) 포함·초과 100개당 $5, RUM 1,000세션당 $0.15, 화면 녹화 1,000세션당 $2.50, 로그 수집 GB당 $0.10. 서버 대수는 시간별 사용량에서 상위 1%를 뺀 최댓값으로 센다. 무료 등급은 서버 5대·지표 1일 보존이다.
  - Datadog 조회 API 한도는 엔드포인트마다 다르고 공개 문서에 숫자가 없다. 응답 헤더(`X-RateLimit-*`)로 알려 주고 지원팀 요청으로 늘린다.
  - Sentry: 저장 위치는 미국(아이오와)·EU(프랑크푸르트)다. 직접 설치는 단일 서버 Docker Compose(메모리 16GB + 스왑 16GB 이상)이고 규모 확장 안내가 없으며 라이선스는 FSL이다. JavaScript SDK는 기본값으로 사용자 IP, 쿼리 문자열, 서버의 요청 본문, 쿠키(민감한 이름의 값은 거름)를 보내고, 화면 녹화는 글자·이미지·입력을 모두 가린다. 'Application Metrics'는 코드에서 보내는 카운터·게이지·분포다.
  - Grafana: 패널 actions는 기본적이고 인증 없는 API 호출이다(확인 문구 있음). `allow_embedding` 기본값은 false이고 `X-Frame-Options: deny`로 클릭재킹을 막는다. 패널 임베드는 Grafana 로그인이나 익명 접근이 필요하고 Grafana Cloud에서는 되지 않는다. 대시보드 최소 새로고침 기본값은 5초다. 데이터 링크에 시간 범위 변수(`__url_time_range`)를 실을 수 있다.
  - 대기실 제품: Cloudflare Waiting Room은 동시 활성 인원·분당 신규 인원 설정과 비상 정지용 Queue-all을 둔다. AWS Virtual Waiting Room 저장소에는 샘플 control panel 소스가 있다.
  - 수집기: postgres_exporter의 `stat_statements` 수집기는 기본 꺼짐이고 반환 개수(`limit`, 기본 100)와 쿼리 문장 포함(`include_query`, 기본 꺼짐)을 정한다. pg_stat_statements는 상수를 `$1` 같은 기호로 바꿔 보이지만, 항목이 자주 밀려나면 상수가 그대로 보일 수 있다(PostgreSQL 문서). node_exporter의 netstat 수집기는 기본 켜짐이고 `netstat -s`와 같은 정보를 낸다.
  - 개인정보 보호법 §28의8(2026-09-11 시행본): 국외 제공(조회 포함)·처리위탁·보관은 원칙적으로 금지하고, 계약 이행에 필요한 처리위탁·보관을 처리방침에 공개한 경우 등에 허용한다.

## 결정

1. **역할 경계(소유자 승인)**: 콘솔과 관측 도구는 쓰는 사람과 묻는 것이 다르다.

   | 도구 | 쓰는 사람 | 묻는 것 | 다루는 단위 |
   | --- | --- | --- | --- |
   | 관제 콘솔 | 운영자·CS | 지금 입장 인원을 줄일까, 판매를 멈출까, 법정 기한 안에 처리했나 | 공연·회차·명령·기한 |
   | Grafana 스택 | 엔지니어(콘솔 장애 때는 운영자도) | 어디가 왜 느리거나 아픈가 | 서비스·서버·요청 |
   | Sentry | 개발자 | 어떤 코드가 왜 깨졌고 어느 배포부터인가 | 오류 종류(이슈)·배포 |

   Grafana 스택은 창고(Prometheus·Mimir·Loki·Tempo·Pyroscope), 경보기(Alertmanager), 화면(Grafana)으로 이뤄진다. 콘솔은 화면만 따로 만들고 창고와 경보기는 함께 쓴다(ops-svc가 창고를 읽는다). Grafana 화면은 엔지니어의 원인 분석(로그 검색·요청 경로·프로파일), 서비스별 상세 대시보드, 콘솔 장애 때 비상 화면, Game Day와 인시던트 리플레이의 시간축에 쓴다.
2. **콘솔을 직접 만드는 이유(소유자 승인)**:
   - (a) 안전 한계, 2인 승인(요청자 ≠ 승인자, 재인증), ack, 자동 만료, 되돌리기는 우리 서버가 확인해야 한다. SaaS를 거치면 우리 서버가 받는 것은 실행기의 자격이고, 누가 눌렀는지는 SaaS가 전하는 값이 된다. Grafana actions는 인증 없는 단순 호출이고, Datadog 흐름 제어에는 승인 단계가 없다.
   - (b) 관측이 멈출 때 조작까지 멈추지 않게 한다(Datadog 2023-03-08 장애). 호출·상태 페이지는 일부러 클러스터 밖에 두고(ADR-0032), 명령은 대상에 직접 보낸다(ADR-0022).
   - (c) 감사 기록과 개인정보 업무(주문 역추적, 팬 조회·CS, 수사기관 자료, 보안 사고)를 서울 리전 한 곳에 둔다. Datadog·Sentry에는 한국 리전이 없고, 국외로 보내면 §28의8 요건이 붙는다.
   - (d) 법정 업무 화면(게시물 차단 기한, 보안 사고 신고·통지, 접속기록 점검)은 관측 도구의 범위가 아니다.
   - (e) 콘솔과 견줄 대상은 대기실 제품의 관리 화면이다. 대기실을 직접 만드는 이상 관리 화면도 직접 만든다.
   - 근거로 쓰지 않는 것: '실시간이라서'(Grafana도 5초마다 그린다), 'SaaS는 장애에 약해서'(우리 클러스터도 죽고, 호출은 오히려 외부에 둔다), '포트폴리오에서 보여 주고 싶어서'.
3. **화면 원칙: 판단과 조작은 한 화면, 원인 분석은 연결(소유자 승인)**: '통합 제어 평면'은 이 뜻이다.
   - 판단에 쓰는 숫자는 콘솔이 같은 창고에서 받아 직접 그린다(iframe이 아니다).
   - 위젯마다 '자세히 보기 ↗' 링크를 둔다. 누르면 같은 회차·시간대로 맞춘 Grafana 대시보드(오류 위젯은 Sentry)가 새 탭으로 열린다.
   - 로그 검색창, 요청 경로 그림, 프로파일 그림, 오류 묶기 엔진은 콘솔에 만들지 않는다.
   - Grafana 패널을 콘솔에 끼워 넣지 않고 `allow_embedding`은 기본값(false)을 지킨다.
   - '판매 진행 중'의 포화도·RUM 위젯은 정상·주의·위험 요약과 핵심 숫자로 줄이고, 그래프는 Grafana로 보낸다.
4. **빈칸 세 개는 요약을 콘솔에, 세부를 전문 도구에 둔다(추천 적용)**:
   - **서버 오류 묶기**: Sentry Node SDK를 peaket-platform 서비스 템플릿에 넣는다. 수집 설정을 잠근다: 사용자 IP 끔(`dataCollection.userInfo: false`), 요청 본문 끔(`httpBodies: []`), 쿠키·헤더·쿼리 문자열은 거름 목록, `beforeSend`에서 로그와 같은 마스킹 규칙(observability §7), 사용자 식별값은 `accountRef` 가명만. 브라우저 SDK도 같은 설정을 쓰고 화면 녹화의 기본 가림은 풀지 않는다. 콘솔에는 '배포 뒤 새로 생긴 오류 종류 수'와 '많이 난 오류 상위 5개'를 1분 [가정]마다 가져와 보인다. 가져오는 방식(API·웹훅)은 4.1.3에서 정한다.
   - **느린 DB 쿼리**: postgres_exporter의 `stat_statements` 수집기를 켜고 상위 20개 [가정]로 줄인다. 쿼리 문장은 지표에 싣지 않는다(`include_query` 꺼 둠. 상수가 그대로 남을 수 있어 개인정보가 섞일 수 있고 라벨 수가 는다). 콘솔에는 '느린 쿼리 상위 5개'(DB·queryid·호출 수·평균·최대 실행 시간)를 보이고, 문장은 엔지니어가 Grafana의 읽기 전용 모니터링 계정으로 본다.
   - **네트워크**: node_exporter netstat 수집기의 연결 대기열 넘침·TCP 재전송 통계를 쓴다. 콘솔 '판매 진행 중'에 '네트워크 정상·주의' 한 줄을 두고, 기준값은 [가정, 4.1.1에서 확정]이다.
5. **관측 백엔드는 재 보고 고른다(소유자 승인, 규칙의 수치는 추천 적용)**: 지금 설계(직접 운영하는 Grafana 스택)를 기본으로 두고, Phase 4에서 측정해 판정한다.
   - **방법**: OTel Collector로 같은 데이터를 우리 창고와 Datadog에 함께 보낸다(observability §1의 평가 용도). 비용은 무료 등급(서버 5대·지표 1일 보존)과 무료 체험으로 0원에 맞춘다. 무료 등급에 요청 추적·로그가 없으면 체험 기간 안에 끝낸다(체험 기간 확인 필요).
   - **잴 것**: ① 우리 규모로 환산한 Datadog 월 비용(서버 수, 지표 조합 수, 로그·추적·RUM 양. 로컬 측정값을 4.8.1 비용 추정의 규모로 외삽하고 ADR-0057의 표시 규칙을 따른다) ② 콘솔 판단 위젯의 갱신(5초 [가정])을 Datadog 조회 한도 안에서 맞출 수 있는지(응답 헤더 기록) ③ 직접 운영에 든 사람 시간(4.1.1부터 설치·장애 대응·업그레이드 시간을 성능 장부에 기록) ④ 결정 4의 빈칸을 메우는 데 든 시간.
   - **판정 규칙(측정 전에 고정)**:
     - R1: 콘솔 갱신을 Datadog 조회 한도 안에서 맞출 수 없으면 창고는 직접 운영한다. Datadog을 쓰더라도 엔지니어 분석용으로만 쓴다.
     - R2: 직접 운영의 연간 총비용(관측 노드 풀·저장소·전송 비용 + 운영 시간 × 시간 단가)이 Datadog 연간 추정 비용보다 크면, Datadog 전환을 새 ADR로 검토한다. 시간 단가는 4.1.1 착수 때 출처를 달아 고정한다 [가정].
     - R3: Datadog으로 보내는 데이터에 개인정보(가명정보 포함)가 남으면 §28의8 요건을 먼저 갖춘다. 갖출 수 없으면 전환하지 않는다.
   - **기록**: 결과는 성능 장부와 이 ADR의 상태 줄(전환이면 새 ADR)에 남긴다.
6. **Sentry 운영 방식도 같은 측정으로 정한다(추천 적용)**:
   - 클라우드를 쓰면 오류 데이터가 미국·EU로 나간다. 직접 설치는 단일 서버라 온세일 오류 폭주를 받는다는 근거가 없다.
   - Phase 4에서 온세일 시나리오의 오류 이벤트 피크(클라이언트 표본률 적용 뒤)를 잰다.
   - 직접 설치 단일 서버가 그 피크를 받으면 직접 설치(국내 보관)로 정한다.
   - 받지 못하면 클라우드를 쓴다. 이때 결정 4의 수집 설정으로 개인정보가 남지 않게 하고, 남는 항목은 국외 이전으로 처리방침에 공개한다.
   - 그 전까지 설계 문서는 'Sentry(운영 방식은 ADR-0067 결정 6에서 판정)'로 적는다.
7. **표현 정리(소유자 승인)**: control-tower §1의 '통합 제어 평면'을 결정 3의 뜻으로 고쳐 쓴다. observability §1, architecture §5·§11의 Datadog 문장은 이 ADR로 잇는다. 부록 본문의 '평가 전용' 행은 원문 보존 규칙대로 두고, 끝의 ADR 대응 표에만 이 ADR을 더한다.

## 검토한 대안

| 대안 | 고르지 않은 이유 |
| --- | --- |
| Datadog으로 콘솔을 대신함(App Builder·Workflow로 명령 버튼) | 결정 2 (a)~(c). 버튼은 만들 수 있지만 안전 규칙과 승인자 확인은 어차피 우리 서버에 있어야 하고, 기록이 두 곳에 생긴다 |
| 모든 관측을 콘솔에서 봄(로그 검색·요청 경로·오류 묶기까지) | Grafana·Sentry를 다시 만드는 일이다. 콘솔 장애 때 볼 비상 화면도 어차피 Grafana다 |
| Grafana 패널을 콘솔에 끼워 넣음(iframe) | `allow_embedding`을 켜면 클릭재킹 방어가 풀리고, 콘솔과 Grafana 로그인을 이어야 한다. 판단용 숫자는 직접 그리는 편이 매끄럽다 |
| Grafana 화면을 빼고 콘솔만 둠 | 원인 분석과 서비스별 상세를 콘솔에 새로 만들어야 하고, 콘솔 장애 때 볼 화면이 없다 |
| 지금 Datadog으로 정함, 또는 측정 없이 직접 운영으로 확정 | 어느 쪽도 숫자 근거가 없다. 계측이 OTel이라 재 보고 바꿀 수 있다 |
| Datadog Database Monitoring·Network Monitoring으로 빈칸을 메움 | 결정 5의 판정 전이다. 수집기 설정 둘로 요약에 필요한 숫자를 얻는다 |

## 결과와 트레이드오프

- 운영자는 판단과 조작을 콘솔 한 화면에서 한다. 원인 분석은 Grafana·Sentry 새 탭으로 옮겨 가므로 창이 둘이 된다. 이것을 남는 한계로 적는다(planning/01 §5.2, guide/10).
- 직접 운영 부담(창고·경보기 부품 8개 안팎의 설치·업그레이드·장애 대응)은 판정 전까지 우리가 진다.
- Sentry를 서버까지 넓히면 이벤트 양이 늘고, 클라우드로 정해지면 국외 이전 범위가 커질 수 있다(결정 6).
- 쿼리 통계 지표는 카디널리티 규칙(observability §8)의 예외로, 상위 20개 [가정]로 묶는다.
- 반영 수치(2026-10-19): ADR 66 → 67. WBS 작업 168 → 170개, 369.5 → 373.5일(4.1.1 +0.5, 4.1.3 신설 1, 4.5.2 +1, 4.8.2 신설 1.5). review R-76. architecture §11 ADR 목록에 빠져 있던 0061~0066 행도 더했다.
- 남김: 디자인 캔버스의 SCR-029 보드(판매 진행 중 위젯과 '자세히 보기' 링크)는 다음 캔버스 갱신 때 맞춘다.

## 되돌릴 조건

- 결정 5의 판정이 Datadog 쪽으로 나오면 새 ADR로 창고·경보기를 옮긴다. 계측 코드는 그대로 두고 수집기 설정과 콘솔의 데이터 연결부만 바꾼다.
- Game Day 기록에서 운영자가 원인 분석 창을 오가느라 판단이 늦었다는 결과가 나오면, 그 지표를 콘솔 위젯으로 올린다.
- 법률 검토(wbs 7.4.1)나 국외 이전 점검에서 Sentry 클라우드 이전이 막히면 직접 설치로 정한다.
