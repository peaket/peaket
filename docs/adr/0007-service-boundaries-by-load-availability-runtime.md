# ADR-0007: 서비스는 부하·가용성·실행 방식이 다른 경계로 나눈다

- **상태**: 채택 (2026-10-08). 2026-10-26(4차 점검 3부): 결정 3 표의 queue-svc 모듈 '셔플 결과 파일'은 admission-ctrl 리더가 만들고 게시한다. queue-svc는 대기 상태 파일을 게시한다(docs/architecture.md §3.1, ADR-0084). 결정 7의 '결제 승인 p99 지연시간 및 오류율'은 K1 정의대로 진입 폭주 중 '결제 접수 p99와 오류율'로 읽는다(planning/01 §3.1 K1, docs/architecture.md §3). 2026-10-27(ADR-0096): 결정 7의 비교는 세 구성((가) 한 프로세스 합본, (나) 같은 이미지를 역할별로 띄운 배포, (다) 10개 서비스)을 같은 CPU·메모리 합계로 재는 것으로 바꿨다. (가)와 (나)의 차이는 실행을 나눈 효과, (나)와 (다)의 차이는 코드를 서비스로 나눈 효과로 읽는다. (나)와 (다)의 차이가 3회 반복 편차 안이면, 서비스로 나눈 이유는 성능이 아닌 근거(결정 1~6)로만 말하고 그 결과를 이 줄에 적는다(docs/verification.md §3.8). 2026-10-28(기술 검토 낮음-144, 소유자 승인 '추천안 동의'): 검토한 대안 표에 없던 중간안 '핫패스 서비스 넷(queue-svc·admission-ctrl·realtime-gw·purchase-svc) + 나머지 하나'와 견준다. 이 안도 부하·실행 방식 경계는 지킨다. 그러나 결정 3 표의 나머지 근거(payment-svc의 결제 비밀과 결제사 장애 격리, identity-svc의 키 격리와 오픈 직전 로그인 몰림, ticket-svc의 현장 입장 가용성, ops-svc의 제어 평면 생존)를 한 프로세스에 모은다. 이 근거들은 성능이 아니라 장애 반경과 비밀 범위다. 그래서 나눌 조건은 위 세 구성 비교의 규칙을 그대로 쓴다. (나)와 (다)의 차이가 편차 밖이면 성능 근거로도 말하고, 편차 안이면 이 비성능 근거로만 말한다. 결론(10개 서비스)은 바꾸지 않는다. 2026-11-01(정합 점검, ADR-0175 해설서 검토): 결정 3 표 core-svc의 모듈 'catalog, notify, shop, review'는 support(고객 문의·소명)를 더한 다섯으로 읽는다(docs/architecture.md §3.1, ADR-0066). 결정 3 identity-svc 행과 결정 보안 줄의 'BFF/Auth.js'는 소비자 웹 앱 서버의 얇은 OIDC 클라이언트(oauth4webapi)로 읽는다. 소셜 로그인의 인가 코드 교환은 그 앱 서버가 하고, 파트너 로그인은 게이트웨이를 거쳐 identity로 간다(ADR-0119, docs/architecture.md §3.1).
- **관련**: 설계서 섹션 0(AWS Well-Architected), 섹션 6 '서비스 맵'·'서비스 분리 기준', 섹션 15(리포지토리), 19장, ADR-0008(게이트웨이), ADR-0009(장애 격리), ADR-0010(서비스 디스커버리)
- **관련 ID**: NFR-001, NFR-011, NFR-013, docs/architecture.md §3

## 맥락

- **초기 설계는 비즈니스 도메인마다 개별 서비스를 분리했다(NestJS 14개 마이크로서비스).** v0 단계는 모듈러 모놀리스로 출발하여 실측 근거가 확보된 도메인부터 분리하기로 했으나, 어떤 기준과 공학적 근거로 경계를 확정할지는 구체화되지 않았다.
- **도메인 간 트래픽 부하 편차가 극심하다.** 대기열 진입 트래픽은 피크 초당 20만 건(TPS)에 달하는 반면, 좌석 홀드는 2,000 TPS, 결제 승인 접수는 300 TPS, 대기열 입장 확정은 초당 평균 28건이다. 대기열 진입 경로 부하가 결제 트랜잭션의 약 670배에 이른다.
- **가용성 및 장애 격리 요구수준이 상이하다.** 오픈 개시 순간의 대규모 진입 폭주 장애가 결제 진행 중인 트랜잭션 세션, 운영 관제 콘솔, 공연 당일 게이트 통제 시스템으로 전이되어서는 안 된다.
- **실행 런타임 모델이 본질적으로 상이하다.** 무상태 고속 HTTP 인입(진입 큐), 장기 유지 대규모 WebSocket 세션(좌석 델타), 단일 액티브 리더 전용 제어 루프(입장 제어 엔진), 외부 PG 비동기 웹훅 수신(결제), 비동기 이벤트 워커(알림 발송)가 혼재되어 있다.
- **1인 엔지니어링 개발 환경이다.** 다수 팀이 병렬로 개발하는 조직적 MSA 장점은 부재하며, 서비스 분리에 수반되는 인프라 운영 비용을 1인이 전담해야 한다.

업계 표준 아키텍처 가이드라인의 핵심 원칙은 다음과 같다.

- **AWS Well-Architected [REL03-BP01](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_service_architecture_monolith_soa_microservice.html)**
  - 워크로드를 분할하여 단일 장애점을 최소화하고, 단일 모놀리스 구성은 지양할 것을 권고한다.
  - 구성 요소 간 가용성 요구사항이 상이할 경우 분리 배포를 통해 장애 반경(Blast Radius)을 제한할 수 있다.
  - 트레이드오프: 네트워크 지연 증가, 분산 디버깅 복잡도 심화, 인프라 운영 부담 가중.
  - 서비스 간 강한 결합으로 인해 연쇄 장애를 유발하는 이른바 'Death Star' 구조를 대표적 안티패턴으로 규정한다.
  - 초기에는 모놀리스로 시작하더라도 응집도 높은 모듈 경계를 갖추어 향후 유연하게 분리할 수 있도록 설계해야 한다.
- **AWS [REL03-BP02](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_service_architecture_business_domains.html)**: 서비스는 명확한 업무 도메인(Bounded Context)을 중심으로 설계하며, 내부 상태(State)를 직접 공유하지 않는다.
- **Martin Fowler, [Microservice Premium](https://martinfowler.com/bliki/MicroservicePremium.html)(2015)**
  - 마이크로서비스 아키텍처는 배포 자동화, 분산 모니터링, 분산 장애 처리, 최종 일관성 등 높은 기본 운영 비용(Premium)을 요구한다.
  - 따라서 시스템 복잡도와 트래픽 규모가 해당 비용을 정당화할 수 있는 경우에 한해 도입해야 한다.
- **Martin Fowler, [Monolith First](https://martinfowler.com/bliki/MonolithFirst.html)(2015)**
  - 프로젝트 초기에 완벽한 도메인 경계를 사전 정의하기는 어려우며, 잘못 분리된 서비스 간 기능 재배치는 모놀리스 리팩터링보다 훨씬 비용이 크다.
  - 소수의 굵직한 핵심 서비스로 시작하여 도메인 경계가 안정화된 이후 점진적으로 세분화하는 전략이 권장된다.
- **Martin Fowler, [Microservice Prerequisites](https://martinfowler.com/bliki/MicroservicePrerequisites.html)(2014)**: 마이크로서비스 도입의 필수 전제조건으로 신속한 환경 프로비저닝, 통합 모니터링, 신속한 배포 파이프라인을 제시한다.

## 검토한 대안

| 대안 | 문제 |
| --- | --- |
| 1. 단일 모놀리스 유지 | 대기열 진입 폭주 시 결제·관제·게이트 시스템까지 전면 마비됨. 진입 핫패스만 독립 오토스케일 불가. AWS 신뢰성 원칙(REL03-BP01) 위배 |
| 2. 세부 도메인별 전면 분리 (14개 마이크로서비스) | 1인 운영 환경에서 서비스 수만큼 운영 부하 폭증. 부하와 SLO가 동일한 inventory와 booking 간 불필요한 네트워크 홉 발생으로 결제 경로 지연 증가 및 Death Star 위험 초래 |
| **3. 부하·가용성·실행 방식 경계 기반 10대 서비스 분리 (채택)** | 단일 서비스 내에 복수 업무 모듈이 통합되는 영역 발생(core-svc). 단, 명확한 모듈 경계로 관리 가능 |

## 결정

1. **마이크로서비스 아키텍처(MSA)를 공식 채택한다.** 분리의 근거는 조직 규모가 아닌 극심한 트래픽 부하 편차, 가용성 및 장애 격리 요구수준의 차이, 런타임 실행 특성의 이질성이다. 암호화 비밀 키 접근 범위를 국소화하는 보안 경계 역시 서비스 분리의 핵심 기준으로 인정한다.
2. **독립 분리 기준을 충족하지 않는 일반 비즈니스 도메인은 단일 서비스 내 모듈(Module)로 응집한다.** Bounded Context를 서비스 내부 모듈 경계로 엄격히 유지하여 향후 필요 시 무중단 분리가 가능하도록 구현한다.
3. **핵심 프로덕션 서비스를 10개로 최종 확정한다.**

   | 서비스 | 모듈 | 분리 근거 |
   | --- | --- | --- |
   | queue-svc | 로비·사전 검증 토큰, 진입, 순번, 대기 상태 파일·셔플 결과 파일, 입장 확정 | 부하: 진입 초당 20만 건, 무상태 고속 처리 |
   | admission-ctrl | 입장 제어, T=0 셔플 실행 | 실행 방식: 단일 액티브 리더 전용 제어 루프 |
   | realtime-gw | 좌석 델타 브로드캐스트 | 실행 방식: 대규모 장기 지속 WebSocket 연결, 커넥션 풀 단위 수평 확장 |
   | purchase-svc | inventory, booking | 동시 입장 5,000명 대상 핫 트랜잭션 경로. 동일 부하 및 SLO를 공유하므로 단일 런타임으로 응집 |
   | payment-svc | 토스페이먼츠 및 PG 어댑터 | 외부 결제망 장애 격리, 웹훅 수신 엔드포인트, PG 비밀 키 격리 |
   | ticket-svc | 발권, 월렛, 양도, 스캐너 동기화 | 가용성 타임라인: 공연 당일 현장 게이트 및 모바일 월렛 트래픽 집중 |
   | identity-svc | 계정, 세션, 토큰 발급, 본인확인(OAuth 댄스는 프론트/BFF Auth.js 수행, ADR-0011) | 보안 격리(연계정보 HMAC 키, 토큰 서명 키, TOTP 암호화 키), 티켓 오픈 직전 로그인 집중 |
   | trust-svc | 위험 점수, 봇 판정, 추가 검증 큐 | 장애 격리 정책(장애 시 전면 바이패스가 아닌 캐시 룰 + 보수적 레이트 리밋), 룰 엔진 독립 배포 |
   | ops-svc | 운영 명령, 감사 로그, 관제 API | 제어 평면(Control Plane): 대규모 트래픽 장애(데이터 평면 고갈) 시에도 생존 보장 |
   | core-svc | catalog, notify, shop, review | 일반 트래픽 도메인. notify 백그라운드 워커는 동일 이미지 기반 별도 파드로 격리 배포 |

4. **과거 edge-api 계층을 전면 폐지한다.** 공통 보안·인가 정책은 API 게이트웨이로 통합하고, 비즈니스 도메인 로직은 각 서비스 계층으로 이관한다(ADR-0008).
5. **서로 다른 Bounded Context에 속한 서비스 간에는 데이터베이스 및 저장소를 절대 직접 공유하지 않는다.**
   - 타 도메인의 데이터는 API 호출이나 도메인 이벤트 발행을 통해서만 접근한다(REL03-BP02). 물리적 인프라 비용 절감을 위해 동일 Redis 클러스터나 Aurora 인스턴스를 공유하는 경우에도 논리적 키 접두사, 스키마, DB 계정 권한(Role/ACL)을 완전히 격리한다.
   - 단, 동일한 Bounded Context를 실행 모델의 차이로 인해 복수 배포 단위로 분할한 경우에는 내부 저장소를 공유한다.
     - 대기열 컨텍스트: queue-svc와 admission-ctrl이 동일 대기열 Redis 클러스터를 공유한다.
     - 좌석 컨텍스트: realtime-gw가 좌석 Redis의 델타 채널(샤드 Pub/Sub)을 직접 구독한다.
   - 예시: 예매 단계 세션 활동은 purchase-svc가 추적하고 대기열 입장 자리는 queue-svc(Redis)가 관리하므로, purchase-svc가 대기열 Redis를 직접 수정하지 않고 '구매 세션 시작/종료' 도메인 이벤트를 발행하여 연동한다(ADR-0005 결정 7).
6. **v0 단계는 동일한 모듈 경계를 갖춘 모듈러 모놀리스로 구축한다.** v1 단계로 진입하면서 위 10대 서비스 경계로 물리 배포를 분리한다. 이는 Fowler의 'Monolith First' 원칙 및 AWS Well-Architected 권고를 충실히 구현한 공학적 접근이다.
7. **서비스 분리의 아키텍처적 효과를 정량적 수치로 검증한다.** 동일한 v1 비즈니스 로직을 단일 배포 모놀리스로 기동했을 때와 10대 서비스로 분리 배포했을 때의 결제 승인 p99 지연시간 및 오류율을 KPI K1 부하 테스트에서 직접 비교 측정한다.
8. **단일 서비스 내 다중 모듈 소유권은 CODEOWNERS 규칙으로 엄격히 분할한다.** 예컨대 core-svc의 shop 모듈은 커머스 팀이 전담 소유하며, 배포 파이프라인만 core-svc 단위로 묶여 실행된다.

## Well-Architected 기둥 분석

| 기둥 | 아키텍처 영향 |
| --- | --- |
| 안정성 | 시스템 장애를 해당 서비스 경계 내에 격리한다(ADR-0009). 대기열 진입 폭주가 예매 결제, 관제 타워, 현장 게이트로 전파되지 않는다. |
| 성능 효율성 | 대기열 진입 핫패스 파드만 독립적으로 고속 수평 확장한다. 예매 경로는 inventory와 booking의 통합으로 불필요한 내부 네트워크 홉 1회를 제거한다. |
| 비용 최적화 | 서비스 개수를 14개에서 10개로 슬림화하여 CI 파이프라인, 모니터링 대시보드, 런북 유지 비용을 절감한다. 대기열 인프라는 오픈 전후로만 집중 스케일링한다. |
| 운영 우수성 | 분산 서비스 확장에 따른 운영 복잡도에 대응하기 위해 신속한 환경 배포, 4대 골든 시그널 모니터링, ArgoCD GitOps 파이프라인을 v0 단계에서 선제 구축한다. |
| 보안 | 대외 비밀 키를 취급하는 서비스 표면을 엄격히 축소한다(identity, payment, queue-svc의 토큰 서명 키). OAuth 클라이언트 시크릿은 BFF 웹 애플리케이션 계층(Auth.js)에만 배치한다. |
| 지속 가능성 | 호출 빈도가 낮은 일반 커머스 및 전시 도메인을 단일 core-svc로 통합하여 상시 유휴 컴퓨팅 자원을 최소화한다. |

## 결과

- 대기열 진입 핫패스를 독립 스케일아웃할 수 있으며, 시스템 장애를 경계 내에 가둘 수 있다.
- 분산 시스템 도입에 따른 고유 비용(네트워크 지연, 분산 추적 오버헤드, 최종 일관성 보장 로직)은 불가피하게 수반된다.
- 트레이드오프: core-svc 내부 모듈들은 동일 컨테이너로 빌드 및 배포되므로 릴리스 일정을 조율해야 한다.

## 재검토 조건

- 좌석 홀드 트래픽 급증이 동일 프로세스 내 주문서 생성 지연시간을 유의미하게 저해할 때: purchase-svc의 inventory/booking 분리를 재검토한다.
- 굿즈 커머스 온세일 배포 주기와 트래픽 부하가 catalog/notify와 간섭을 일으킬 때: shop 모듈의 독립 서비스 분리를 검토한다.
- K1 부하 테스트 벤치마크에서 모놀리스 대비 분리 배포의 정량적 격리 효과가 확인되지 않을 때: 서비스 통합을 재검토한다.
