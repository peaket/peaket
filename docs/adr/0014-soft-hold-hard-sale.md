# ADR-0014: 좌석은 Soft Hold(Redis Lua) + Hard Sale(PostgreSQL 유니크 제약)의 2단계로

- **상태**: 채택 (2026-10-05 설계서 §6 '좌석: 2단계 일관성'에 기록, 2026-10-08 ADR로 옮김). ADR-0050(2026-10-13)이 지연 예산의 '페이로드 복호화 5ms'를 '구매 세션 요청 인증 확인 1ms'로 바꾸고 남는 4ms를 버퍼에 더한다(버퍼 29ms) 2026-10-13 전수 점검(2026-10-14 2차): 결정 1의 '결제 진입 시 3분 연장'은 POL-012·seat-hold §5의 '사용자 1회 연장 3분'(2026-10-09 추천 적용)으로 대체되었다. 2026-10-22(ADR-0083): 비상 경로(Degraded Mode)의 짧은 잠금 대기는 트랜잭션 첫 문장의 `SET LOCAL lock_timeout = '100ms'` [가정]으로 걸고, 잠금을 얻지 못하면 409 `seat-already-held`로 끝낸다(docs/features/seat-hold.md §9). MySQL과 비교한 PostgreSQL 유지 근거의 첫째가 이 ADR의 부분 유니크 인덱스다. 2026-10-26(4차 점검 3부): 결정 1의 `WAIT 1 10`은 seat-hold §3의 값(복제본 1대, 시간 초과 5ms [가정, Phase 2 부하 시험에서 확정])으로 읽고, 쓸지 여부는 PoC로 정한다(seat-hold §13). `WAIT`는 복제를 보장하지 않는다. 시간 초과면 복제를 확인하지 못한 채 돌아오고 장애 전환에서 쓰기를 잃을 수 있으며, 빠진 홀드는 PostgreSQL 판매 확정이 흡수한다(docs/data.md §3). 결정 1의 홀드 TTL은 새 결제 일시 정지 동안 결제 접수 전 홀드의 남은 시간을 멈추고 다시 열리면 이어 센다(ADR-0085 결정 1).
- **관련**: 설계서 §6 '좌석', §9 좌석 홀드 지연 예산, §10 K2·K3, 18장(Hello Interview), docs/features/seat-hold.md, ADR-0021
- **관련 ID**: FR-010, FR-011, FR-042, POL-011, POL-012, POL-013, NFR-003, NFR-025, SCR-010

## 맥락
- 수천 개의 동일 데이터베이스 행에 수십만 사용자가 동시 쓰기를 시도하는 극한의 동시성 경합(Race Condition)이 티케팅 좌석 예매 도메인의 핵심 과제이다. 인기 구역 1석에 최대 1,000명이 동시에 홀드를 시도하는 상황에서도 좌석 홀드 응답 시간은 p99 50ms 이내를 유지해야 한다(NFR-003).
- 초과 판매(Oversell)는 직접적인 금전적 환불 손실과 법적 분쟁을 야기하므로 엄격한 데이터 일관성이 요구된다. 그러나 모든 홀드 요청을 관계형 데이터베이스의 행 레벨 잠금(Row-level Lock)으로 처리할 경우 잠금 경합으로 인해 p99 지연시간이 수 초 이상으로 치솟아 시스템 장애로 이어진다(v0 베이스라인 결함).
- 반면 Redis는 빠른 인메모리 처리 속도를 제공하지만 비동기 복제 구조로 인해 노드 장애 페일오버 시 홀드 상태가 유실될 위험이 상존한다.
- 글로벌 시스템 설계 레퍼런스인 Hello Interview는 'Redis TTL 락을 통한 1차 경합 완충 + RDBMS 유니크 제약을 통한 최종 일관성 보장' 패턴을 최적의 엔지니어링 해법(Great Solution)으로 제시한다.

## 결정
1. **1단계 Soft Hold는 Redis 인메모리에서 수행한다.** 좌석 점유 상태를 공연 회차당 비트맵(5만 석 기준 약 6.25KB)으로 압축 모델링하고, 원자적 Lua 스크립트를 통해 복수 좌석의 점유 여부 검사와 비트 설정을 단일 연산으로 완결한다. 홀드 레코드마다 7분 만료 TTL(결제 진입 시 3분 연장)과 펜싱 토큰(Fencing Token)을 부여하며, 데이터 안전성을 위해 `WAIT 1 10` 명령으로 복제 노드 동기화를 보장한다.
2. **1인당 예매 매수 제한 검증 역시 동일한 Lua 스크립트 내에서 원자적으로 처리한다.** 사용자별 예매 좌석 수 키에 공연 해시 태그(`{event:id}`)를 부여하여 좌석 비트맵과 동일한 Redis 샤드 슬롯에 배치함으로써, 좌석 상태 확인과 인당 한도 조회를 네트워크 홉 없이 단일 트랜잭션으로 판정한다. 요청 좌석 중 단 하나라도 홀드되었거나 매수 한도를 초과할 경우 모든 변경 사항을 롤백하고 실패를 반환한다.
3. **2단계 Hard Sale(최종 판매 확정)은 PostgreSQL 트랜잭션에서 수행한다.** 외부 PG 결제 승인 API를 호출하기 직전에 `(event_id, seat_id)` 복합 유니크 제약(Unique Constraint)이 선언된 판매 확정 테이블에 `PENDING` 상태의 행을 삽입한다. 이 데이터베이스 유니크 제약은 Redis 복제 지연이나 스크립트 이상 시에도 오버셀을 차단하는 플랫폼의 최후 방어선 역할을 수행한다. 동일 트랜잭션 내에서 사용자·공연별 누적 예매 수량 행을 원자적 조건문(`사용 수량 + 요청 수량 ≤ 인당 한도`)으로 갱신하여 1인당 매수 한도를 최종 확정한다.
4. **좌석 홀드 이벤트는 Redis Stream을 통해 Outbox 패턴으로 발행한다.** 홀드 성공 시 동일 Lua 스크립트 내에서 Redis Stream에 변경 이벤트를 기록하고, 백그라운드 릴레이 워커가 이를 Kafka를 거쳐 PostgreSQL 원장 테이블로 비동기 동기화함으로써 사용자 대면 홀드 응답 경로에서 무거운 RDBMS 디스크 쓰기 I/O를 원천 배제한다.
5. 데이터 파티셔닝 시 좌석 비트맵, 홀드 키 등 동일 트랜잭션에서 함께 수정되는 키에 한해서만 `{event:id}` 해시 태그를 적용하여 Redis 클러스터의 데이터 편향(Hot Shard)을 방지한다.

## 검토한 대안
| 대안 | 문제 |
| --- | --- |
| PostgreSQL `SELECT … FOR UPDATE` 홀드(v0) | 경합 시 p99 수 초, 잠금 대기 타임아웃, 교차 순서 데드락(K3) |
| Redis만으로 확정 | 페일오버 쓰기 유실 시 오버셀 가능 |
| CockroachDB 분산 트랜잭션 | 단일 리전이고 쓰기량이 적어 불필요(ADR-0021) |
| 다중 좌석을 클릭 순서로 잠금 | 데드락 → 좌석 ID 정렬 잠금으로 해결(K3) |

## 결과와 트레이드오프
- 홀드 p99 50ms 지연 예산(게이트웨이 3ms + 네트워크 왕복 5ms + 페이로드 복호화 5ms + Lua 실행 7ms + 직렬화 5ms + 버퍼 25ms)을 안정적으로 달성할 수 있다.
- Redis 페일오버로 홀드 및 보유 수량이 일시 유실되더라도 PostgreSQL 유니크 제약과 조건부 한도 갱신이 중복 결제를 원천 차단하며, 경합에서 밀린 요청은 PG 승인 호출 전 단계에서 거절되므로 복잡한 취소/환불 트랜잭션이 발생하지 않는다. 비상 시에는 PostgreSQL 정렬 잠금 경로(Degraded Mode, p99 300ms)로 유연하게 전환한다.
- 트레이드오프: Lua 스크립트, 펜싱 토큰, 스트림 릴레이 파이프라인의 운영 복잡도가 수반되며, 홀드와 최종 확정 사이의 일관성을 검증하기 위해 주기적 불변식 검사기(전체 판매 수량 ≤ 총 좌석 수량, 좌석당 단일 판매 불변식)를 상시 운용해야 한다.
