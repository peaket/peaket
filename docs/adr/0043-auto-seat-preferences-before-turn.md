# ADR-0043: 좌석 자동 배정 공연의 희망 조건 사전 입력과 차례 도래 자동 배정 (사람의 입력 시간을 배정 순서에서 분리)

- **상태**: 채택 (2026-10-12 수립, 소유자 질문·승인. ADR-0041 결정 3의 좌석 자동 배정을 보완한다. ADR-0041의 나머지 결정과 ADR-0005의 '첫 예매 요청 때 입장 자리' 원칙은 그대로다) 2026-10-14: 대기열(SCR-008)에서는 희망 조건 카드를 한 줄 요약과 [바꾸기](시트)로 줄였다(ADR-0063 결정 7). 로비(SCR-007)의 카드와 배정 규칙은 그대로다. 2026-10-21: 본문의 REST 경로는 ADR-0081의 옛 경로 대응표로 새 경로를 읽는다(경로 이름 규칙 점검).
- **관련 문서**: ADR-0041, ADR-0005, ADR-0003, ADR-0012, docs/features/queue-admission.md §4·§6·§11·§12, docs/features/seat-hold.md §2·§3·§12·§13, planning/02 FR-050, planning/03 POL-035, planning/04 SCR-007·SCR-008·SCR-010, design/d2 CMP-057, docs/api/openapi.yaml, docs/security/asvs/bot-defense.md, wbs 2.5.4
- **관련 ID**: FR-005, FR-006, FR-007, FR-008, FR-010, FR-050, POL-004, POL-011, POL-012, POL-035, NFR-002, NFR-012, SCR-007, SCR-008, SCR-010, CMP-057, K6

## 맥락
- 소유자 질문(2026-10-12): "좌석 자동 배정(AUTO)은 매크로를 대비한다고 하지만, 이런 옵션을 눌러도 사용자가 매크로를 이길 수는 없지 않나." 검토 결과 지적이 맞다. ADR-0041 결정 3의 AUTO는 좌석맵 클릭 경쟁과 좌석맵 탐색(스크래핑)을 없앴지만, 배정은 요청이 도착한 순서대로 즉시 처리된다. 입장 뒤 사람이 등급과 매수를 고르는 수 초에서 수십 초 동안 봇은 0.1초 안에 요청을 제출하므로, 같은 시간대에 입장한 사람보다 먼저 배정받는다. 차례 진행 속도 초당 약 28명 기준으로 사람의 입력 시간 10초는 약 280명분의 순서 차이가 된다.
- 소유자가 지적한 두 번째 문제(2026-10-12): 배정을 순번 순으로 처리하려고 앞 순번의 결정을 기다리면, 한 사람이 머뭇거리는 동안 뒤의 모든 사람이 묶인다. 요청을 짧은 라운드로 모아 순번 순으로 정렬하는 방식도 라운드가 사람의 입력 시간보다 짧으면 효과가 없고, 길면 모든 사람을 기다리게 한다.
- 따라서 배정 순서에서 '사람이 결정하는 시간' 자체를 빼야 한다. 결정은 차례가 오기 전, 대기하는 동안 미리 받을 수 있다. 대기 시간은 보통 수 분이다.
- 결정을 미리 받아도 차례를 아는 시점에는 차이가 남는다. 브라우저는 CDN에 1초 캐시된 대기 상태 파일을 1초마다 읽어 차례를 알지만(queue-admission §4), 봇은 입장 확정 API를 직접 호출해 원본의 serving 번호로 판정받는다. 대기 상태 파일의 묵은 정도(최대 약 1초)와 폴링 주기를 더하면 사람의 브라우저가 평균 1초 남짓 늦게 차례를 안다.
- 기존 문서의 과장: POL-035, planning/01 §5.2, 쉬운 설명서 4편이 AUTO가 클릭 경쟁을 '원천 차단'한다고 적었다. 클릭 경쟁은 없앴지만 제출 속도 경쟁은 남아 있었다.

## 결정
1. **희망 조건 사전 입력.** AUTO 공연은 로비(SCR-007)와 대기열(SCR-008) 화면에 희망 조건 카드(CMP-057 `preference`)를 둔다.
   - 입력 항목: 1순위 등급(필수), 매수(필수, 1인 매수 한도 이하), 휠체어석 필요 여부, 2순위 등급(선택), 분리 좌석 허용 여부(선택, 기본은 연석만).
   - 차례가 오기 전까지 언제든 고칠 수 있다. 대기 상태 파일의 등급별 매진 목록(`soldOutTiers`)에 1순위가 들어가면 카드가 2순위 입력을 권한다.
   - 희망 조건은 대기표와 함께 브라우저 저장소에만 두고 대기 중에는 서버로 보내지 않는다. 대기 중 origin 쓰기가 생기지 않으므로 대기실 무상태 원칙(ADR-0003)과 origin 초당 약 1,000건 설계가 유지된다.
   - 입력하지 않으면 차례가 왔을 때 수동 선택으로 넘어가며, 카드가 이를 미리 알린다.
2. **차례 도래 시 자동 요청 연쇄.** 차례가 오면 브라우저가 사람의 조작 없이 입장 확정(`POST /v1/queue/{eventId}/admission`)과 자동 배정 홀드(`POST /v1/events/{eventId}/holds`의 `auto`)를 연달아 보낸다.
   - AUTO 공연은 좌석맵 스냅샷을 받지 않으므로 자동 배정 요청이 입장 토큰의 첫 사용이 되어 구매 세션을 시작한다. 실제로 온 사람에게만 입장 자리를 주는 ADR-0005의 원칙은 그대로다.
   - 사람은 배정 결과(좌석, 금액, 홀드 남은 시간)를 보고 결제하거나 반납한다. 배정 이후 단계에는 경쟁이 없다.
3. **차례 직전 직접 확인.** AUTO 공연에서는 예상 대기가 10초 [가정, Phase 2 부하 시험에서 확정] 이내로 들어오면 브라우저도 입장 확정 요청을 직접 보낸다.
   - 첫 시도는 예상 도래 시각(앞 인원 ÷ 차례 진행 속도)에 맞춘다. 아직 차례가 아니면 queue-svc가 `NOT_YET`과 남은 예상 시간(밀리초, 원본의 serving 번호와 차례 진행 속도로 계산)을 돌려주고, 브라우저는 그 시각에 다시 보낸다.
   - 시도 간격은 1초 이상이며 게이트웨이 레이트 리밋(기기·사용자 단위) 안에 있다. 봇이 쓸 수 있는 것과 같은 정보, 같은 한도를 사람의 브라우저도 쓰게 하여 차례 인지 시점의 체계적인 차이를 없앤다.
   - 추가 부하는 10초 창 안의 약 280명이 초당 1건 이하로 보내는 origin 초당 수백 건이다.
   - 직접 선택(PICK) 공연에는 적용하지 않는다. PICK에서는 좌석을 고르는 클릭 속도 차이(수 초)가 차례 인지 지연(1초 남짓)보다 커서 효과가 작고, 그 영역은 세션당 홀드 간격과 연타 감지(seat-hold §13)가 맡는다.
4. **배정 규칙.** ADR-0041 결정 3의 배정 방식(파트너가 정한 선호 순, 같은 Lua 홀드, 경합 시 다음 후보로 최대 3회 [가정])을 유지하고 순서를 다음과 같이 정한다.
   - 1순위 등급의 연석, 분리 허용 시 1순위 등급의 분리 좌석, 2순위 등급의 연석, 분리 허용 시 2순위 등급의 분리 좌석 순으로 찾는다.
   - 모두 실패하면 아무 좌석도 홀드하지 않고 409 `manual-selection-required`로 응답하며, 화면은 수동 선택(CMP-057 `manual`: 남은 등급·매수 선택 후 서버 배정)으로 전환한다.
   - 응답에는 배정 결과 유형(`FIRST`, `FIRST_SPLIT`, `SECOND`, `SECOND_SPLIT`)을 담는다.
   - 결과 화면에서 반납하면 홀드를 풀고 수동 선택으로 간다. 다시 요청하면 그 시점의 남은 좌석으로 배정한다. 세션당 홀드 호출 최소 간격(seat-hold §13)이 그대로 적용된다.
   - 1인 매수 한도, 홀드 TTL(7분·연장 3분), 결제 흐름은 PICK과 같다. 희망 조건은 신뢰하지 않는 입력이므로 purchase-svc가 배정 요청마다 다시 검증한다(docs/security/asvs/bot-defense.md 2.2.1~2.2.3).
5. **배정 순서의 공정성.** AUTO 공연의 배정 순서는 입장 확정 순서이고, 입장 확정 순서는 순번(로비 추첨, 동시 도착 구간 무작위화, 그 뒤 도착 순)을 따른다. 결정 1~3으로 사람의 입력 시간과 차례 인지 지연이 배정 순서에서 빠진다. 남는 차이는 입장 제어 루프 주기(200ms) 안의 도착 지터와 네트워크 지연이다.
6. **표현 정정.** POL-035, planning/01 §5.2, 쉬운 설명서 4편의 '원천 차단' 표현을 이 ADR의 범위대로 바로잡고, 남는 한계를 각 문서에 적는다.
7. **측정.** seat-hold S-T19를 희망 조건(1순위·2순위·분리 허용·수동 전환)으로 넓히고, 새 시험 S-T20으로 배정 순서의 공정성을, queue-admission Q-T25로 차례 직전 직접 확인 규칙을 잰다.

## 검토한 대안
| 대안 | 기각 사유 및 한계점 |
| --- | --- |
| 앞 순번의 결정을 기다려 순번 순으로 배정 | 한 사람이 머뭇거리면 뒤의 모든 사람이 묶인다(소유자 지적, 2026-10-12). |
| 요청을 짧은 라운드로 모아 순번 순으로 정렬 | 라운드가 사람의 입력 시간보다 짧으면 봇은 계속 앞 라운드에 들고, 길면 모든 사람이 라운드만큼 기다린다. |
| serving이 전진할 때 서버가 희망 조건으로 미리 배정 | 오지 않은 사람에게도 좌석을 7분씩 홀드한다. 실제로 온 사람에게만 입장 자리를 주는 ADR-0005와 어긋난다. |
| 희망 조건을 대기 중 서버에 저장 | 100만 명의 입력·수정이 대기 중 origin 쓰기가 되어 대기실 무상태 원칙(ADR-0003)과 초당 약 1,000건 설계를 깬다. 차례가 올 때 요청에 실어 보내면 같은 효과를 얻는다. |
| Web Push를 받은 서비스 워커가 백그라운드에서 배정 요청 | 푸시 전달 지연이 보장되지 않고, 서비스 워커가 대기표와 페이로드 암호화 키를 다루게 되어 구현과 보안 검토가 커진다. 차례를 늦게 안 사람은 15분 유예(ADR-0005)로 입장할 수 있다. |
| 차례 직전 직접 확인을 PICK 공연에도 적용 | PICK의 속도 차이는 좌석 클릭에서 생기므로 차례 인지 지연을 줄여도 효과가 작다. |

## 결과와 트레이드오프
- 얻는 것: AUTO 공연에서 배정 순서가 순번을 따르고, 사람의 입력 시간과 차례 인지 지연이 봇과 같아진다. 봇에게 남는 수단은 계정 수뿐이고 이는 1인 1계정, 휴대폰 본인확인, 1인 매수 한도가 막는다. 앞 사람의 결정을 기다리는 사람은 없다.
- 대가
  - 로비·대기열 화면에 희망 조건 카드가 생긴다. 대기 화면 번들 예산(JS 50KB gzip, NFR-012) 안에서 구현하고 Lighthouse CI로 확인한다.
  - 차례 직전 직접 확인으로 origin에 초당 수백 건이 더해진다.
  - 입장 확정 응답에 `NOT_YET`, 자동 배정 응답에 결과 유형이 생겨 API가 바뀐다.
  - WBS 2.5.4가 1일 늘어난다(희망 조건 카드, 자동 요청 연쇄, 차례 직전 직접 확인, 수동 선택 전환).
- 남는 한계
  - 희망 등급이 모두 매진되었거나 조건을 입력하지 않아 수동 선택으로 넘어간 팬은 그 순간부터 다시 제출 속도 경쟁을 한다. 이때 남은 좌석은 대개 하위 등급이라 이득이 작다.
  - 브라우저를 닫았거나 탭이 백그라운드에서 스로틀된 팬은 차례를 늦게 알아, 그 사이 뒤 순번이 먼저 배정받는다. 15분 유예 안에서 입장은 보장되지만 좌석의 질은 떨어질 수 있다.
  - 희망 조건은 브라우저 저장소에 있으므로 기기나 브라우저를 바꾸면 다시 입력해야 한다.
  - 입장 제어 루프 주기(200ms) 안의 도착 지터는 남는다.
  - 타인 명의 계정을 여럿 쓰는 조직적 공격은 이 ADR의 범위 밖이다(queue-admission §7의 알려진 설계 한계).
- 되돌릴 조건
  - S-T20에서 봇의 평균 순위 이득이 기준을 넘으면 직접 확인 창과 시도 시각 규칙을 다시 정한다.
  - Q-T25에서 직접 확인 규칙의 origin 부하가 예상(초당 수백 건)을 크게 넘으면 창을 줄인다.
  - 수동 선택 전환 비율이 높으면(Phase 6 실측) 공연 상세 화면에서도 희망 조건을 미리 받는 것을 검토한다.
