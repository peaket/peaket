# ADR-0047: 파트너 정산 지급은 결제사 지급대행으로 한다 (PEAKET은 판매 대금을 받아 두지 않고, 결제사가 회차가 끝난 뒤 파트너에게 직접 보낸다)

- **상태**: 채택 (2026-10-13. 소유자 결정: 00-summary §7 질문 22에 "추천안대로 (b)로 가겠습니다." 등록·정산서·지급·보류의 세부 규칙은 추천 적용(2026-10-13)이다.) ADR-0050(2026-10-13)이 결정 8의 '`payment-svc` 지급 어댑터만 읽는다'를 '`payment-svc`가 읽는다'로 바로잡는다(파드 권한은 서비스 계정 단위라 한 파드 안의 모듈을 나누지 못한다). 토스페이먼츠 보안 키를 키 목록에 넣고 키 분리 원칙의 예외로 적는다. ADR-0053(2026-10-13) 결정 3이 지급 웹훅의 시각 창 검증을 더한다 2026-10-14 확인(ADR-0062 결정 23·48): 토스페이먼츠는 KYC 심사를 서류가 갖춰지면 2영업일 안에 마친다고, 지급대행 이용료를 월 고정 300,000원(부가세 별도)·월 1,000건 초과 건당 100원으로 공개 안내한다(블로그 2024-09-23·2024-09-24·2025-03-24). '남는 한계'의 'KYC 처리 기간'은 보완 요청·승인 보류 때의 기간으로, '지급대행 수수료'는 실제 계약 조건·결제 상점별 부과·포트원 이용료로 좁힌다(settlement §6·§14). 굿즈·부가 상품은 상품 정산서로 따로 낸다(결정 40). 2026-10-19(ADR-0066 결정 12): 결정 6의 상호·대표자 변경은 공연 재승인이 아니라 판매자 정보 변경 요청과 운영자 확인으로 읽는다(2026-10-20 3차 전수 점검에서 상태 줄에 적음).
- **관련 ID**: FR-027, FR-052, FR-062, POL-014, POL-027, POL-037, POL-038, POL-039, SCR-020, SCR-021, SCR-027, SCR-045, SCR-046, SCR-048, SCR-049, ADR-0044, ADR-0045, ADR-0046

## 맥락

- 문서에는 정산 리포트(FR-027)와 일일 대사(payment §8)만 있었고, 파트너에게 판매 대금을 보내는 지급 절차가 없었다. ADR-0045 결정 6이 지급 방식을 후속 결정으로 남겼다.
- 선택지는 두 가지였다(00-summary §7 질문 22).
  - (a) 직접 지급: PEAKET이 결제사 정산을 받아 파트너에게 이체한다.
  - (b) 결제사 지급대행: 결제사가 PEAKET 대신 파트너 계좌로 보낸다.
- 결제사 문서와 법령에서 확인한 사실(2026-10-13):

## 결정

1. **정산 지급은 결제사 지급대행으로 한다(소유자 결정).** PEAKET은 판매 대금을 자기 계좌로 받아 두지 않는다. 결제 시도가 간 결제사(ADR-0044)가 그 대금을 파트너 정산 계좌로 보낸다.
   - 토스페이먼츠 결제분: 토스페이먼츠 지급대행 API
   - 포트원 결제분: 포트원 지급대행(AGENCY), 콘솔 일괄 지급
2. **등록은 판매 승인 때 두 결제사에 모두 한다.** 결제사 전환(명령 6)이 판매 중에도 일어날 수 있어서다.
   - 파트너는 판매 승인 요청(SCR-021 5단계)에서 정산 계좌를 낸다. 계좌는 결제사 등록 요청에 바로 넘기고, PEAKET은 은행과 끝 4자리만 남긴다(POL-014와 같은 방식).
   - 포트원 예금주 조회로 예금주가 판매자 상호나 대표자와 같은지 본다. 다르면 판매 승인을 반려한다.
   - 토스페이먼츠 셀러가 지급 가능 상태(PARTIALLY_APPROVED 이상)이고 포트원 파트너가 등록돼야 판매 승인이 끝난다(SCR-048 확인 항목).
3. **정산서는 회차와 결제사 단위로 만든다(POL-039).**
   - 회차가 끝난 다음 영업일에 대사가 끝난 원장으로 계산한다. 판매 대금 − 환급 − 중개수수료(부가세 포함) − 상계 = 지급액이다.
   - 파트너에게 알리고 2영업일 동안 이의를 받는다. 이의가 오면 그 정산서만 멈추고 CS 처리함 건이 된다.
   - 정책 계산 그대로면 이의 기간이 끝날 때 자동 확정한다. 수기 조정은 승인 업무다(`cs_lead` 요청, commander 승인).
   - 지급액이 0 이하면 지급하지 않고 미수금으로 넘겨 다음 정산서에서 상계한다.
4. **지급은 회차가 끝난 뒤에만 한다.** 기본 지급일은 회차 종료일로부터 5영업일 뒤다. 결제사 지급 가능 잔액이 그때까지 생기지 않으면 생기는 날로 미룬다. 공연 전 선지급(선정산)은 하지 않는다.
   - 이유: 공연 전 취소와 회차 취소 환불, 배상 상계가 끝난 뒤 보내야 돌려받을 일이 줄어든다. 결제사는 지급한 돈을 되돌려 주지 않는다.
5. **지급 실행**
   - 지급일·결제사별로 확정 정산서를 지급 묶음으로 모은다. 지급 묶음은 되돌릴 수 없는 일괄 작업이라 승인 업무로 처리한다(POL-038). 운영자(operator)가 합계와 예외를 확인해 요청하고 commander가 승인한다(2인). 지급일 전 영업일 15시까지 승인되지 않으면 지급일을 다음 영업일로 미루고 파트너에게 알린다.
   - 토스페이먼츠: 확정 정산서를 10억 원 미만 건으로 나눠 예약지급(SCHEDULED)으로 요청한다. 요청 하나에 20건까지만 넣는다. 한 건이 틀리면 요청 전체가 실패하므로 실패 범위를 줄이려는 것이다.
     - `refPayoutId`는 `{정산서 ID}-{순번}`이고 멱등키는 바꾸지 않는다. 오류 응답이면 키를 바꿔 다시 보내지 않고 CS 처리함에 올린다(결제사 안내).
     - 상태는 서명을 확인한 `payout.changed` 웹훅과 단건 조회로 확정한다.
   - 포트원: 확정 정산서 금액을 수기 정산건(아이디 = 정산서 ID, 정산일 = 지급일)으로 올린다. 지급일에 CS 처리함에 '포트원 일괄 지급 실행' 건이 생기고, 운영자(operator)가 포트원 콘솔에서 지급대행 일괄 지급을 실행한다. 공개 API에 지급 생성이 없어서다.
     - PEAKET은 지급 내역 조회로 결과를 맞추고, 콘솔 실행 기록(실행자, 시각, 일괄 지급 ID)을 감사 로그에 남긴다.
   - 계산의 원본은 PEAKET 정산서 하나다. 포트원 주문 정산건(`transfers/order`)으로 포트원이 따로 계산하게 하지 않는다.
6. **보류**
   - KYC: 토스페이먼츠 셀러가 KYC_REQUIRED가 되면 그 셀러 지급이 멈춘다. 파트너에게 KYC 안내를 보내고 CS 처리함으로 추적하며, 승인되면(`seller.changed`) 다시 요청한다. 판매 승인 때 "주 1천만 원 이상 첫 지급에서 KYC 때문에 지급이 늦어질 수 있다"를 알린다.
   - 정산 계좌 변경: 파트너 관리자가 재인증(TOTP)한 뒤 새 계좌를 낸다. 예금주 조회로 예금주가 판매자 상호나 대표자와 같을 때만 받아 두 결제사에 바로 수정 요청한다. 다르면 받지 않는다. 상호나 대표자가 바뀌었으면 판매자 정보 변경과 재승인(SCR-048)을 먼저 한다. 그래서 계좌번호를 PEAKET에 둘 일이 없다.
   - 변경을 파트너의 등록 이메일과 전화로 알리고, 변경 뒤 3영업일 안에 잡힌 지급은 미룬다. 탈취한 계정으로 계좌를 바꾸는 경우 예금주 대조가 먼저 막고, 남는 경우(같은 명의의 다른 계좌)에 알아챌 시간을 주려는 것이다.
   - 토스페이먼츠는 사업자등록번호를 고칠 수 없으므로 사업자가 바뀌면 새로 등록한다.
7. **지급 뒤 환불과 카드 이의제기.** 결제사가 가맹점인 PEAKET의 정산에서 빼므로 PEAKET이 먼저 부담한다. 파트너에게는 ADR-0046의 재원 순서(다음 정산서 상계 → 보증 → 청구)로 돌려받는다. 이 금액은 미수금으로 관리한다.
8. **비밀과 보안(docs/security/asvs/settlement.md).**
   - 토스페이먼츠 보안 키·시크릿 키와 포트원 API 시크릿은 Secrets Manager에 두고 `payment-svc` 지급 어댑터만 읽는다.
   - JWE는 `dir`·`A256GCM`만 받는다. 웹훅 서명은 상수 시간으로 비교하고, 틀리면 버리고 보안 이벤트로 남긴다.
   - 계좌번호, 보안 키, JWE 원문은 로그에 넣지 않는다.
9. **PEAKET 몫.** 지급대행 뒤 남는 잔액(중개수수료와 상계로 남긴 금액)을 PEAKET이 받는 방식은 공개 문서에 없다. 지급대행 계약 때 정한다.
10. **배상 송금은 따로다.** 팬에게 보내는 배상금(ADR-0046)은 PEAKET 자기 돈으로 보내는 계좌 이체라 은행 이체 API를 따로 고른다(transfer-refund §12).
11. **법률 표시**
    - (b)에서는 결제사가 파트너에게 직접 지급하므로 PEAKET은 판매 대금을 받아 내주는 정산 대행을 하지 않는다.
    - 그래서 ADR-0045의 확인 필요 '2026-12-16까지의 정산 대행 지위'는 직접 지급을 할 때만 생기는 질문이 되어 목록에서 뺀다.
    - 대신 'PEAKET이 정산 금액을 계산해 결제사에 지급을 지시하는 일은 전자지급결제대행(전자금융거래법 §2 19호)이 아니다'를 해석으로 두고 출시 전 법률 검토 목록(POL-027)에 올린다.

## 결과

### 대가
- 요구사항 FR-062, 정책 POL-039, 화면 SCR-049가 늘었다. FR-027·052와 SCR-020·021·027·045·046·048이 넓어졌다.
- 데이터: `settlement_statement`, `payout`, `partner_receivable` 엔티티와 `promoter`의 결제사 등록 필드
- 운영: 지급일마다 지급 묶음 승인(2인)이 필요하고, 포트원 결제분은 운영자가 콘솔에서 지급을 실행해야 한다.
- WBS가 4일 늘었다: 7.2.3 정산서·토스페이먼츠 지급대행 2.5일, 7.2.4 포트원 지급대행·정산 계좌 변경·화면 1.5일

### 남는 한계
- 공개 문서에 없어 계약 때 확인할 것: PEAKET 몫을 받는 방식, KYC 처리 기간, 지급대행 수수료, 포트원 지급 생성 API 제공 여부, 포트원 지급대행이 되는 하위 결제사 범위, 결제사 정산 주기
- 주 1천만 원 이상 첫 지급은 KYC 때문에 늦어질 수 있다. KYC를 미리 받을 수 없다.
- 지급 뒤 환불과 카드 이의제기는 PEAKET이 먼저 부담한다. 다음 정산과 보증으로 못 메우면 청구하고, 받지 못하면 PEAKET 손실이다.
- 세무(중개수수료 세금계산서와 부가가치세)는 검토하지 않았다.
- 'PEAKET의 지급 지시는 전자지급결제대행이 아니다'는 해석이다.

### 되돌릴 조건
- 결제사가 지급대행 계약을 받아 주지 않거나 조건(수수료, KYC)이 맞지 않으면 다시 정한다. 직접 지급으로 바꾸면 2026-12-17 시행 개정법 이후에만 연다.
- 포트원이 지급 생성 API를 제공하면 콘솔 실행을 API로 바꾼다.
- 결제사 정산 주기와 이의 처리 경험에 따라 지급일(5영업일)과 이의 기간(2영업일)을 조정한다.
