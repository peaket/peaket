# ADR-0113: 주문은 '상태 + 덧붙이기 이력 + Outbox'로 두고, 이벤트 소싱은 운영 명령 기록에만 쓰며, CQRS라는 이름은 쓰지 않는다(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 중간-010 '주문 이벤트 소싱과 CQRS 세 곳은 이름과 실제 구조가 다르다'에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 검토는 (가) 주문을 진짜 이벤트 소싱으로 만들기와 (나) 이름을 실제 구조에 맞추기 가운데 하나를 고르라고 했고, (나)를 골랐다(추천 적용, 고른 이유는 결정 1). 방향은 소유자 결정(추천안 승인)이고, 칸 이름·검사 주기·경보·시험 같은 세부는 추천 적용이다)
- **관련**: ADR-0026(멱등 소비자), ADR-0053·0075·0102(감사 체인·공개 앵커·체인 작업자), ADR-0086(일련번호 규칙, `order_event` 기본 키), ADR-0094(검색 읽기 모델은 카탈로그와 같은 트랜잭션), ADR-0097(학습 목록을 근거로 쓰지 않는다), ADR-0099(퍼널 '처음' 표시, 관제 실시간 표), ADR-0116(Outbox 릴레이), FR-031, NFR-017, [docs/architecture.md](../architecture.md) §3.1·§3.3·§6.1·§7, [docs/data.md](../data.md) §1·§2·§4, [docs/features/payment.md](../features/payment.md) §2·§10·§11(P-T13), [docs/features/control-tower.md](../features/control-tower.md) §7, planning/02 FR-031, [review/tech-review.md](../review/tech-review.md)(중간-010)

## 맥락

- **지금 문서의 이름**
  - architecture §3.1: purchase-svc는 '주문은 Event Sourcing 적용', ops-svc는 'CQRS + Event Sourcing', core-svc catalog는 'Layered + CQRS'다. §6.1은 NestJS를 고른 근거에 'CQRS 모듈'을 적었다.
  - data.md는 purchase DB에 '주문 이벤트 소싱 스토어'를 두고, payment.md는 '주문 애그리거트는 이벤트 소싱 방식으로 저장한다'고 적었다. 시험 P-T13의 이름도 '이벤트 소싱 상태 역추적'이다.
- **실제 구조**
  - 주문: 지금 상태 칸 `purchase_order.status`를 조건부 UPDATE로 바꾸고, 같은 트랜잭션에서 `order_event`(기본 키 `order_id, seq`)에 전이를 덧붙이고 Outbox 행을 넣는다(data.md §4의 1·2·8번). 상태를 사건에서 다시 만들지 않는다. 스냅샷도, 사건 판 올림 규칙도, 재생하는 길도 없다. 이벤트 소싱(상태를 사건을 차례로 적용해서만 만드는 방식)이 아니라 '상태 + 덧붙이기 이력'이다.
  - catalog: Redis의 카탈로그 값은 캐시이고 Outbox 사건으로 지운다. 검색 읽기 모델은 카탈로그와 같은 트랜잭션에서 고친다(ADR-0094). 쓰기 저장소와 읽기 저장소를 나눠 읽기 쪽이 사건으로 늦게 따라잡는 CQRS(명령과 조회의 모델·저장소를 나누는 방식)가 아니다.
  - ops-svc: 운영 명령은 `command_event`에 덧붙이기만 하고, 키를 건 해시 체인 `audit_chain`이 사건을 묶는다(ADR-0053·0102). 명령의 상태(요청·승인·전달·ack·연장·사후 검토)는 그 명령의 사건으로 정해진다. 관제 지표 API가 읽는 ClickHouse·Prometheus는 다른 길로 채워지는 자료이고, 운영 명령 쓰기의 읽기 모델이 아니다.
- **왜 문제인가**: 면접에서 '사건을 어떻게 재생해 상태를 만드나', '읽기 모델은 언제 따라잡나'를 물으면 답이 문서와 어긋난다. 이 이름들은 원문에서 이어받았고, 고른 이유가 ADR에 없다(원문과 학습 목록은 판단 근거가 아니다, ADR-0097).
- **요구**: FR-031은 '주문 ID로 그 좌석의 점유·홀드 만료·결제 확정 이력을 시간 순서로 거슬러 추적'하고 '특정 과거 시점의 좌석 상태를 다시 만든다'를 요구한다. payment.md는 이 기록을 분쟁 해결의 증거로 쓴다고 적었다. 이 요구는 빠짐없는 전이 이력이 있으면 채워진다. 상태를 사건에서만 만들 필요는 없다.
- **크기**: 주문 하나의 사건은 생성·본인확인·결제 접수·좌석 예약·승인·확정과 취소·환급을 합쳐 10개 안팎이다 [추정]. 5년 누적 주문은 약 1,700만 건이다(architecture §9.5).

## 결정

1. **주문은 이벤트 소싱이 아니라 '상태 + 덧붙이기 이력 + Outbox'로 둔다(검토 안 (나), 추천 적용).**
   - 주문의 원본은 `purchase_order`의 지금 상태다. `order_event`는 같은 트랜잭션에서 덧붙이는 상태 전이 이력이다. Outbox 행도 같은 트랜잭션에서 넣고 릴레이가 Kafka로 보낸다(ADR-0116).
   - 고른 이유는 셋이다.
     - ① FR-031과 분쟁 증거는 빠짐없는 전이 이력으로 채워진다. (가)가 더 주는 것은 '상태가 사건에서만 나오므로 둘이 어긋날 수 없다'와 '사건으로 새 읽기 모델을 다시 만든다'다. 앞의 것은 결정 2의 규칙과 매일 검사로 가깝게 지킨다. 뒤의 것은 주문 사건이 이미 Kafka(`trade.orders`)와 분석 저장소로 흘러가 그쪽에서 한다.
     - ② (가)는 사건 판 올림 규칙(옛 모양의 사건을 새 코드로 읽는 변환), 핫패스 읽기마다 재생하거나 따로 고치는 투영, 재생 시험을 더한다. 주문 사건이 10개 안팎이라 스냅샷으로 얻을 것도 없다.
     - ③ 결과가 뻔한 비교를 하려고 (가)를 만들지 않는다(ADR-0097·0099와 같은 원칙). 깊이는 결정 2의 '어긋나지 않게 하는 장치'와 되돌릴 조건으로 보인다.
2. **상태와 이력이 어긋나지 않게 하는 규칙(추천 적용).**
   - 주문 상태를 바꾸는 길은 주문 전이 함수 하나다. 한 트랜잭션에서 ① `UPDATE purchase_order SET status = <새 상태>, event_seq = event_seq + 1 WHERE id = $1 AND status = <기대 상태> RETURNING event_seq` ② 돌려받은 번호로 `order_event`(주문, 번호, 이전 상태, 새 상태, 원인, 행위자, 시각)를 넣고 ③ Outbox 행을 마지막에 넣는다. 주문을 만드는 트랜잭션은 번호 1을 쓴다.
   - 번호는 주문 행의 카운터를 같은 UPDATE에서 올려 얻는다. 그래서 빈틈이 없고, 번호 순서가 커밋 순서와 같다(ADR-0086의 일련번호 규칙과 같은 방식이다).
   - CI가 purchase-svc 코드에서 `purchase_order`의 `status`를 바꾸는 SQL이 전이 함수 밖에 있으면 PR을 막는다.
   - `order_event`를 쓰는 DB 역할에는 UPDATE·DELETE 권한이 없다. 지우기는 보존 기간이 지난 행을 지우는 정비 잡 역할만 한다.
   - 정비 잡이 매일 전날 바뀐 주문을 검사한다. 마지막 사건의 새 상태가 지금 상태와 같은지, 번호에 빈틈이 없는지, `event_seq`가 마지막 번호와 같은지 본다. 어긋난 주문이 1건 이상이면 SEV3(`kind` hygiene) [가정]이고 담당 팀에 이슈를 연다.
   - 상태값과 전이의 정본은 planning/03 §2.4다.
3. **이벤트 소싱은 운영 명령 기록(ops-svc)에만 쓴다(추천 적용).**
   - 명령의 상태는 그 명령의 사건(`command_event`)을 차례로 적용해 정한다. 사건은 덧붙이기만 하고 감사 체인이 묶는다(ADR-0053·0102).
   - 콘솔의 목록·검색에 쓰는 지금 상태는 같은 트랜잭션에서 고치는 명령 상태 표에 둔다. 이 표는 사건에서 다시 만들 수 있는 사본이고, 감사의 원본은 사건과 체인이다. 지금 문서의 '최신 스냅샷 읽기 모델'·'주기적 상태 스냅샷'은 이 상태 표로 읽는다. 명령 하나의 사건은 많아야 수백 개(파드별 ack) [추정]라 주기적 스냅샷은 따로 두지 않는다.
   - 따로 떨어진 읽기 저장소는 두지 않는다.
4. **CQRS라는 이름을 쓰지 않는다(추천 적용).**
   - core-svc catalog는 'Layered + 읽기 캐시'다. Redis의 카탈로그 값은 캐시이고, 검색 읽기 모델은 같은 트랜잭션에서 고친다(ADR-0094).
   - ops-svc는 'Layered, 운영 명령 기록은 Event Sourcing'이다.
   - purchase-svc는 '클린 아키텍처 + DDD, 주문은 상태 + 덧붙이기 이력 + Outbox'다.
   - 관제 실시간 표(ClickHouse `rt`)는 여러 서비스의 사건을 모아 읽을 때 세는 관제용 읽기 모델이다(ADR-0099). 한 서비스가 자기 쓰기와 읽기를 나눈 구조가 아니므로 이것도 CQRS라고 부르지 않는다.
5. **@nestjs/cqrs의 명령·사건 버스는 쓰지 않는다(추천 적용).** 주문은 결정 1이다. 운영 명령은 저장소 함수 하나(사건 덧붙이기, 상태 표, 체인 행, Outbox를 한 트랜잭션에)로 충분해, 메모리 안 버스가 더하는 것이 없다. architecture §6.1의 NestJS 선정 근거에서 'CQRS 모듈'을 뺀다.
6. **시험(추천 적용).** P-T13을 '주문 상태 이력 역추적'으로 고친다.
   - 주문 ID로 `order_event`를 번호 순으로 읽고 홀드 원장과 합쳐 좌석의 시간대별 상태 전이를 다시 만든 결과가 실제 전이와 같다.
   - 시험 데이터의 모든 주문에서 마지막 사건의 새 상태가 지금 상태와 같고 빈 번호가 없다. 장애 주입 시험(wbs 2.12.3) 뒤에도 같다.
7. **문서(추천 적용).** architecture §3.1(세 서비스의 내부 구조 칸)·§3.3(그림의 주문 이력)·§6.1(NestJS 근거)·§7(NFR-017 수단), data.md §1·§2(`event_seq`)·§4, payment.md §2·§10·§11, control-tower §7, planning/02 FR-031의 이름을 고친다.

## 결과와 트레이드오프

- 이름이 실제 구조와 같아진다. '어떻게 재생하나'라는 질문에는 이렇게 답한다. 주문은 재생하지 않는다. 이력은 같은 트랜잭션에서 덧붙이는 기록이고, 매일 검사로 상태와 맞춘다. 운영 명령은 사건이 원본이고 체인이 묶는다.
- 'Event Sourcing을 썼다'는 줄은 주문에서 빠지고 운영 명령에만 남는다. 'CQRS를 썼다'는 줄은 빠진다.
- 새 칸 `purchase_order.event_seq`, CI 검사 하나, 매일 검사 하나가 생긴다.
- WBS에 주문 이벤트 소싱 작업 줄이 따로 없어 일수는 그대로다 [가정].

## 되돌릴 조건

- 서비스 안에서 주문 사건으로 새 읽기 모델을 자주 다시 만들어야 하고(예: 주문 상태별 머문 시간을 서비스가 실시간으로 써야 한다), 분석 저장소로는 늦을 때.
- 결정 2의 매일 검사에서 어긋남이 석 달 [가정] 안에 두 번을 넘을 때.
- 분쟁·법적 요청에서 사건만으로 '그 시각의 주문 전체 모습'을 증명해야 한다는 요구가 생길 때.
- 위가 오면 안 (가)를 다시 본다. 그때 주문 사건 수, 재생 시간, 저장 크기를 상태 + 이력 방식과 같은 데이터로 재서 정한다.

## 남는 한계

- 상태와 이력의 어긋남은 매일 검사로 찾을 뿐 막지는 못한다. 하루 안에 생긴 어긋남은 다음 검사까지 남는다.
- 주문 이력은 상태 전이만 담는다. 좌석 홀드 이력은 비동기로 쌓는 홀드 원장에서 오므로, Redis 장애 직전 원장에 쌓이지 못한 홀드는 빠질 수 있다(지금 FR-031의 한계와 같다).
