# ADR-0336: 월렛 기기 키 서버 등록을 늘 잇고, 같은 키 다시 등록은 바꾸지 않고 받으며, 런타임 캐시에 판을 붙인다(2026-11-21)

- **상태**: 채택(2026-11-21, 추천 적용. BUILD_ORDER GAT-010의 남은 몫 '서버 키 등록 잇기·스캐너 keyId 대조·런타임 캐시 판 번호'를 BAT-350 계획 담당이 정본 빈칸으로 모아 정했다. 방향을 바꾸는 결정은 없다. 감독이 다르게 정하면 이 ADR과 아래 정본 자리를 함께 고친다)
- **관련**: [docs/features/offline-gate.md](../features/offline-gate.md) §2 '서버 등록 잇기'·'같은 키 다시 등록'·§11 O-T44~O-T46, [docs/frontend.md](../frontend.md) §3.12 저장 표·§4.2.4 '입장용 휴대폰 등록 세부'·§5.4 '갱신'의 런타임 캐시 판, [docs/design/d5-screen-blueprint.md](../design/d5-screen-blueprint.md) §5.13 상태 표, [docs/api/openapi.yaml](../api/openapi.yaml) `createTicketDeviceKey`, [docs/review/plans/BAT-350.md](../review/plans/BAT-350.md), [ADR-0025](0025-rotating-qr-device-key-signature.md), [ADR-0050](0050-crypto-corrections-and-key-management.md) 결정 2, [ADR-0051](0051-gate-process-end-to-end.md) 결정 10, [ADR-0079](0079-frontend-radio-detailed-design.md) 결정 18
- **관련 ID**: GAT-010, O-T44, O-T45, O-T46, FR-012

## 맥락

- 월렛의 기기 키·회전 QR은 2026-11-14 첫 구현(R-554)으로 들어왔다. 그때는 ticket-svc에 등록 경로가 없어, 키를 이 기기에만 두고(`LOCAL`) 빌드 값 `NEXT_PUBLIC_WALLET_DEVICE_KEY_REGISTRATION=1`일 때만 서버 등록을 시도했다. 등록에 실패해도 QR을 그대로 보였다.
- 같은 날 ticket-svc에 `POST /v1/tickets/{ticketId}/device-keys`와 `device_key` 표가 생겼다(R-561). 스캐너 목록은 티켓별 유효 키와 폐기 keyId를 싣고, 스캔의 keyId를 유효·폐기·모름으로 대조한다. 그래서 서버에 등록되지 않은 키로 만든 QR은 현장에서 '모르는 키'(`KEY_UNKNOWN`)로 거절된다.
- 등록 규칙상 이미 유효 키가 있으면 ISSUE도 재인증과 24시간 1회 한도를 따른다. 그런데 월렛이 등록 응답을 잃고 같은 키로 다시 보내면, 서버에는 이미 그 키가 유효한데도 재인증(403)에 막힌다. 재인증 확인(GAT-020)이 아직 없어 그 티켓은 그 휴대폰에서 다시 등록할 길이 없어진다.
- 월렛 서비스 워커의 런타임 캐시 이름(`wallet-pages`·`wallet-assets`)에는 판이 없다. 새 판 워커가 옛 판이 담은 셸 HTML과 옛 덩어리를 그대로 낼 수 있다(BAT-350 첫 구현 정합 리뷰 중간). 정본 저장 표는 이미 `wallet-shell-{판}`, '다음 판까지', '새 판 활성화 때 지움'으로 정해 두었다.

## 결정

1. **등록은 팬 API 주소가 있으면 늘 한다.** 빌드 값 스위치를 없앤다. 운영 이미지는 한 번 빌드해 여러 환경에 올리므로 빌드 값으로 기능을 켜고 끄지 않는다. 주소가 없는 빌드(로컬 화면 개발)만 지금처럼 이 기기에만 둔 키로 QR을 보인다.
2. **QR은 서버가 같은 keyId로 등록을 확인한 뒤에만 보인다.** 201이고 응답 `keyId`가 이 기기 keyId와 같을 때 '등록됨'으로 바꾼다. 그 전에는 키를 '확인 전'으로 남기고 QR 대신 '등록 확인 전' 상태를 보인다.
3. **실패는 세 갈래로 나눈다.** 끊김·시간 초과·5xx·429·keyId 다름은 같은 공개키로 다시 보낸다(부품이 붙을 때, [다시 시도], `online` 사건). 403 `reauth-required`는 키를 두고 '다시 확인 필요'를 보인다(재인증 시트로 잇는 것은 GAT-020). 404·422·400과 그 밖의 403은 이 기기 키를 지운다. '등록됨' 키는 이 화면에서 지우거나 새로 만들지 않는다. 세부는 docs/frontend.md §4.2.4가 정본이다.
4. **서버는 같은 키 다시 등록을 바꾸지 않고 받는다.** 같은 티켓의 지금 유효 키와 keyId가 같으면 201(같은 keyId)이고, 새 행·폐기·스캐너 변경분 기록·24시간 한도 셈이 없다. ISSUE·TRANSFER는 보유자 확인(404) 바로 뒤에 보고 입장 시작·TRANSFER 확인보다 앞선다(바뀌는 것이 없다). REISSUE·BOOTH는 재인증·부스 허용 확인(403)을 지난 뒤 보유자 확인 다음에 본다(BAT-350 리뷰 RV350-1에서 구현의 차례에 맞춰 좁힘). 판정은 티켓 행 잠금 안에서 한다. 같은 키 요청 둘이 겹쳐도 하나는 등록, 하나는 바꾸지 않고 받게 하려는 것이다.
5. **런타임 캐시는 판을 붙인 이름 하나다.** 이름은 `wallet-shell-{판}`이고 판은 미리 저장 판과 같은 값이다. 새 판이 활성화되면 옛 판 캐시에 든 월렛 문서 주소를 네트워크로 다시 받아 넣고(10초 [가정] 안, 옛 응답은 옮기지 않음), 지금 판이 아닌 `wallet-shell-` 캐시와 옛 이름 둘을 지운다. 미리 저장 캐시·IndexedDB·웹 푸시 워커는 건드리지 않는다.
6. **월렛·서버·스캐너 목록은 같은 시험 벡터로 맞춘다.** 구현과 따로 계산한 공개키·keyId·압축 공개키·QR v1·서명 묶음(`docs/api/vectors/qr-v1-device-key.v1.json`)을 월렛 시험과 ticket-svc 시험이 함께 읽는다. 구매 세션 서명 벡터([ADR-0221](0221-booking-flow-split-and-purchase-signer-core.md))와 같은 방식이다.

## 결과

- 월렛에서 등록한 키만 QR이 되어, 현장에서 처음 '모르는 키'로 거절되는 일이 줄어든다. 응답을 잃어도 같은 키로 다시 보내 끝낼 수 있다.
- 남는 한계
  - 입장 시작 뒤 첫 등록과 다른 휴대폰에 이미 등록한 티켓은 GAT-020(재인증)이 붙을 때까지 '다시 확인 필요'에서 멈춘다.
  - 오프라인에서 새 판이 활성화되면 다시 받지 못한 티켓 펼침 주소는 다음 온라인 방문 때까지 캐시에 없다(미리 저장한 `/my/tickets`는 열린다).
  - 로컬·CI 빌드는 판이 개발 값 하나라 캐시 이름이 바뀌지 않는다.
  - 폐기된 키를 같은 티켓에 다시 보내는 경우는 이 결정이 다루지 않는다(유효 키와 같을 때만 바꾸지 않고 받는다).

## 다른 선택지

- **스위치를 기본으로 켠 채 둔다**: 끄는 길이 남지만, 빌드 값이라 한 이미지를 환경마다 다르게 둘 수 없다. 끌 까닭(서버 경로 없음)도 사라졌다.
- **등록 전에도 QR을 보인다(지금 동작)**: 오프라인에서도 바로 보이지만, 서버가 모르는 키라 현장에서 거절된다. 팬은 게이트에서야 안다.
- **다시 보낼 때 새 키를 만든다**: 응답을 잃은 경우 서버에는 이미 옛 키가 유효해 재인증(403)에 막힌다.
- **같은 키 판정을 응용 계층에서 행 잠금 밖으로 한다**: 겹친 두 요청이 모두 '키 없음'을 보고 하나가 403이 된다.
- **런타임 캐시 이름 둘에 판을 붙인다**: 정본 저장 표의 이름 하나와 어긋나고, 지울 대상만 늘어난다.
- **활성화 때 다시 받지 않고 지우기만 한다**: 간단하지만 온라인에서 새 판이 활성화돼도 펼쳐 본 티켓 주소가 모두 사라진다.
