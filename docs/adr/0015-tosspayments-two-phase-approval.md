# ADR-0015: 토스페이먼츠의 '인증 → 승인' 2단계를 좌석 일관성에 활용한다

- **상태**: 채택 (2026-10-05 설계서 §6 '결제 연동'에 기록, 2026-10-08 ADR로 옮김). PG 선택 근거와 포트원 호환은 ADR-0029(2026-10-09)가 보완한다. 운영 승인 한도는 ADR-0036(2026-10-09)의 추정치를 쓴다. R-56(2026-10-13)이 결정 5의 '전송 ID로 중복 수신을 완벽히 필터링'을 바로잡는다: 같은 전송 ID로 다시 온 웹훅만 한 번 처리되고(토스 문서는 재전송 때 같은 값인지 밝히지 않는다), 전송 ID가 다른 중복은 단건 조회 결과로만 상태를 바꾸는 규칙이 결과를 바꾸지 않게 한다(payment §5). 2026-10-26(4차 점검 3부): 결정 8은 교차 출처 격리(COOP `same-origin`과 COEP `require-corp`)를 좌석 경로와 그 Worker 스크립트, 출시 뒤 선택인 포렌식 리플레이 2단계 `/forensics`에만 둔다는 뜻으로 읽는다. COOP 자체는 모든 앱에 둔다. 소비자 웹과 결제 화면은 `same-origin-allow-popups`, 콘솔·스캐너는 `same-origin`이고, 결제 화면에는 COEP를 두지 않는다. 두 결제사 결제창은 페이지 이동으로 연다(docs/frontend.md §5.14.1, ADR-0065 결정 3, ADR-0079 결정 7, ADR-0080). 2026-10-28(ADR-0106, 소유자 승인 '추천안 동의'): 승인 뒤 발권이 실패하면 결제를 취소하지 않고 같은 주문 ID로 다시 발권한다. 결과의 '60초 이내 미보상 결제-발권 불일치 0건'은 NFR-006의 새 문구('결제 승인 뒤 60초 안에 발권되지도 발권 재시도 큐에 들어가지도 않은 결제 0건, 큐에 든 건은 발권 기한 안에 발권 또는 보상')로 읽는다. 결제 승인 호출은 2초에 끊지 않고 읽기 시간 초과 60초 [가정]까지 기다린다(기술 검토 높음-16, ADR-0070 상태 줄). 2026-10-28(기술 검토 중간-015, 소유자 승인 '추천안 동의'): 결정 8의 '교차 출처 격리 헤더(COOP, COEP)는 좌석맵 렌더링 라우트에 한정'에서 좌석맵 라우트의 COEP를 뺀다. 좌석 상태는 SharedArrayBuffer로 나누지 않고 Worker가 바뀐 구역만 메시지로 보낸다. 그래서 교차 출처 격리를 켜는 화면은 관제 호스트의 포렌식 리플레이 2단계 페이지(ADR-0080)뿐이다. 좌석 라우트에는 COOP `same-origin`만 두고, 결제 화면 헤더는 위와 같다(docs/frontend.md §2.5·§5.2·§5.14.1, ADR-0079 상태 줄). 2026-11-02(wbs 0.9.3 규칙 모델 검사): 결과 모름을 조회로만 확정하는 규칙(승인 응답 시간 초과·payment-svc 재시작)과 웹훅 본문을 믿지 않는 규칙이 전수 검사에서 '과금 없음으로 끝난 주문에 남은 승인 0'과 '승인 없는 발권 0'을 지킨다(각각 빼면 반례, docs/verification.md §2.6).
- **관련**: 설계서 §6 '결제: Saga'·'결제 연동: 토스페이먼츠', §9 결제 SLO, §10 K7, 24장 Webhook, docs/features/payment.md, docs/api/guidelines.md
- **관련 ID**: FR-011, FR-041, POL-013, POL-014, NFR-005, NFR-006, SCR-011, SCR-012

## 맥락
- 토스페이먼츠 결제 시스템은 구매자가 프론트엔드 결제위젯에서 결제 수단 인증을 마치더라도, 가맹점 서버가 승인 API를 최종 호출하기 전까지는 실제 결제가 확정되지 않는 2단계 인증-승인 구조를 취한다. 클라이언트 인증 완료 후 10분 이내에 서버 승인을 호출하지 않으면 해당 결제건은 자동 만료된다. 또한 브라우저 결제창 세션은 최대 30분간 유지될 수 있다.
- 좌석 홀드 경합에서 밀려난 사용자에게 결제 승인 후 사후 환불이 발생하는 구조는 막대한 고객지원(CS) 비용과 사용자 분쟁을 초래한다(P-02).
- 토스페이먼츠 결제 웹훅에는 자체 암호화 서명 헤더가 제공되지 않아 웹훅 페이로드 자체만을 신뢰할 수는 없다.
- 1차 PG사로 토스페이먼츠를 선정한 배경은 국내 결제 수단(간편결제, 앱카드) 최적화, 결제위젯 SDK의 높은 완성도, 개발자 친화적인 테스트 키 및 공식 문서 생태계에 기반한다(상세 PG 비교 및 포트원 호환 전략은 ADR-0029에서 기술함).

## 결정
1. **좌석 상태를 데이터베이스에서 PENDING으로 먼저 확정 예약한 후 PG 승인 API를 호출한다.** 좌석 경합에서 탈락한 주문은 PG 승인 호출 전 단계에서 트랜잭션이 중단되므로 결제 승인 자체가 발생하지 않아 사후 환불이 원천 차단된다.
2. **결제 접수(HTTP 202 Accepted)와 결제 승인 확정을 물리적으로 분리하여 2개의 독립 SLI로 계측한다.** 결제 접수 단계는 주문 금액 대조, `paymentKey` 임시 보관, 결제 Saga 오케스트레이션 기동까지만 수행하여 즉시 202 응답을 반환하며, 외부 PG사 승인 네트워크 통신은 클라이언트 대기 경로 밖의 비동기 트랜잭션으로 처리한다.
3. **승인 API 호출은 `POST /v1/payments/confirm` 엔드포인트를 시크릿 키 Basic 인증과 `Idempotency-Key: confirm-{orderId}`(15일간 유효) 헤더를 필수 동봉하여 수행한다.** 브라우저 인증 완료 후 10분을 절대적 Deadline으로 설정하며, 기한을 초과한 주문은 승인하지 않고 자동 취소 처리한다.
4. **승인 통신 응답 유실(Timeout) 발생 시 동일한 멱등키로 재전송을 수행한다.** PG사로부터 `409 IDEMPOTENT_REQUEST_PROCESSING` 응답을 수신하면 일정 지터 대기 후 재조회하며, 상태 불명 지속 시 `UNKNOWN` 상태로 전환한 후 백그라운드 단건 결제 조회 API를 호출하여 최종 상태를 원자적으로 확정한다.
5. **웹훅 이벤트(`PAYMENT_STATUS_CHANGED`)는 보조 동기화 트리거로만 수신한다.** 웹훅 본문 데이터를 직접 신뢰하지 않고 payment-svc가 토스 단건 결제 조회 API를 역호출하여 교차 검증하며, `tosspayments-webhook-transmission-id` 헤더를 기반으로 중복 수신을 완벽히 필터링한다.
6. **가상계좌 결제 방식은 고수요 온세일 티케팅 환경에서 비활성화한다.** 실시간 좌석 점유와의 시차 및 환불 계좌 정보 보관에 따른 개인정보 보호 리스크를 회피하기 위함이다.
7. **매일 새벽 토스페이먼츠 대사 파일과 내부 결제 원장을 자동 대사(Reconciliation)한다.** 개발 및 스테이징 환경에서는 테스트 API 키(`test_ck`, `test_sk`)와 실패 시뮬레이션 헤더를 활용하고, 대규모 부하 테스트 시에는 계약 기반 PG 시뮬레이터 어댑터(`PaymentGatewayPort`)로 투명하게 대체한다.
8. **브라우저 보안 격리 헤더 최적화**: 토스페이먼츠 결제창 팝업 차단 이슈를 방지하기 위해 전체 사이트에 일괄 적용하지 않고 교차 출처 격리 헤더(COOP, COEP)는 좌석맵 렌더링 라우트에 한정하여 적용한다.

## 검토한 대안
| 대안 | 문제 |
| --- | --- |
| 승인 후 좌석 확정 | 경합 패배 시 환불 필요, 결제-발권 불일치 창이 커짐 |
| 접수와 확정을 한 SLI로 | 어느 쪽이 느린지 알 수 없음 |
| 웹훅을 1차 신호로 | 서명이 없어 위조 가능 |

## 결과와 트레이드오프
- 멱등키 보장, 분산 결제 Saga, 일일 원장 대사를 통해 이중 결제 발생 0건과 60초 이내 미보상 결제-발권 불일치 0건을 엔지니어링 수준에서 보증한다(KPI K7).
- 트레이드오프: 승인 제한 시간(10분) 이내에 결제를 완결해야 하는 지연 큐 및 `UNKNOWN` 상태 복구 오케스트레이터의 구현 복잡도가 수반된다. 운영 승인 처리량 상한(추정 피크 300 TPS)은 ADR-0036에 근거하여 운영 모니터링한다.
