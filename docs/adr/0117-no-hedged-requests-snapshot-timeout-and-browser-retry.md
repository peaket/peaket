# ADR-0117: 헤지 요청을 쓰지 않는다 — 좌석 스냅샷 재요청은 시간 초과와 브라우저의 `Retry-After` 재요청으로 처리한다(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 중간-017 '헤지 요청은 학습 지도에서 왔고 보내는 주체와 전제가 맞지 않는다'에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 방향은 소유자 결정(추천안 승인)이고, 재요청 규칙과 시험 같은 세부는 추천 적용이다. ADR-0009 결정 3의 '헤지 요청은 순수 멱등적 읽기(좌석 스냅샷)에만 국한한다'와 ADR-0087 결정 21의 '구매 세션이 열린 뒤의 재요청만 헤지한다'를 이 ADR로 대신한다)
- **관련**: ADR-0009(결정 1·3), ADR-0079, ADR-0082, ADR-0087(결정 21), ADR-0097, FR-009, NFR-004, NFR-012, [docs/features/seat-hold.md](../features/seat-hold.md) §2·§8·§12, [docs/frontend.md](../frontend.md) §3.5·§4.1·§4.4.2·§5.17, docs/api/openapi.yaml(`/v1/events/{eventId}/seatmap-snapshot`), [docs/architecture.md](../architecture.md) §5, [docs/observability.md](../observability.md) §6, planning/01 §3.1, [review/tech-review.md](../../review/tech-review.md)(중간-017)

## 맥락

헤지 요청은 응답이 늦으면 같은 요청을 하나 더 보내, 먼저 온 응답을 쓰는 방식이다. 지금 정본은 좌석 스냅샷의 첫 요청(입장 토큰을 처음 써서 구매 세션을 여는 쓰기)은 헤지하지 않고, 구매 세션이 열린 뒤의 스냅샷 재요청만 헤지한다고 적었다. 재요청은 버전 갭 복구, 재연결, 전체 보기 구역의 5초 갱신 때 나간다(ADR-0009 결정 3, ADR-0087 결정 21, seat-hold §2·§8, 시험 S-T17, openapi 스냅샷 설명, docs/frontend.md §4.4.2, architecture §5, observability §6).

- **보내는 주체가 없다.**
  - 게이트웨이: Envoy Gateway의 정책 API에는 헤지 설정이 없다(확장 타입 문서, 2026-10-27·2026-10-28 확인). Envoy 자체에는 경로별 `hedge_policy`가 있다. 그 설정 `hedge_on_per_try_timeout`은 시도별 시간 초과에 걸리면 첫 요청을 끊지 않고 하나를 더 보낸다(Envoy 경로 API 문서, 2026-10-28 확인). 그러나 Envoy Gateway는 이 설정을 드러내지 않고, 이 프로젝트의 게이트웨이는 재시도하지 않는다(ADR-0009 결정 3).
  - 메시: Istio `VirtualService`의 재시도 설정(`retryOn`, `perTryTimeout`)에는 헤지 항목이 없다(Istio 문서, 2026-10-28 확인). 게이트웨이에서 서비스로 가는 구간은 웨이포인트를 지나지 않는다(ADR-0082).
  - 앱: 서비스 템플릿의 gRPC 채널에는 헤지 정책(`hedgingPolicy`)을 넣지 않는다(ADR-0082, docs/api/guidelines.md §5). 스냅샷은 브라우저 → gw-fan → purchase-svc의 HTTP 요청이라 gRPC 헤지와도 상관이 없다.
  - 남는 곳은 브라우저뿐이다. 그런데 언제 두 번째 요청을 보내는지, 몇 번까지인지, 부하 상한이 무엇인지 정한 곳이 없다.
- **효과가 작다.**
  - 헤지가 꼬리 지연(드물게 아주 느린 요청의 지연)을 줄이려면 두 번째 요청이 첫 요청과 다른 원인으로 느려지는 곳에 가야 한다. 스냅샷은 그 회차의 좌석 Redis 샤드(`{event:E}`)를 한 번 읽는다. 두 요청이 다른 purchase-svc 파드로 가도 같은 샤드를 읽고, 그 샤드는 같은 회차의 홀드 Lua도 처리한다. 샤드가 느린 것이 원인이면 두 요청이 함께 느리다. 파드 하나의 이벤트 루프나 GC가 원인이면 다른 파드로 간 두 번째 요청이 도움이 될 수 있지만, 그 이득을 잰 적이 없다.
  - 재요청은 첫 그림 경로 밖이다. 대기실 통과 뒤 1초 안의 첫 그림(NFR-012)을 좌우하는 것은 첫 요청인데, 첫 요청은 구매 세션을 여는 쓰기라 원래 헤지할 수 없다. 재요청이 늦는 동안 화면은 마지막 상태와 "실시간 연결 복구 중"을 보인다(docs/frontend.md §3.5).
  - 꼬리 지연이 늘어나는 때는 온세일 직후처럼 그 샤드와 purchase-svc가 가장 바쁠 때다. 그때 헤지는 여유가 가장 적은 곳에 읽기를 더한다.
- **출처**: 이 장치는 원문 학습 목록의 'Tail latency' 줄에서 왔다. 이 프로젝트는 원문과 학습 목록을 판단 근거로 쓰지 않는다(ADR-0097). 'The Tail at Scale'(Dean·Barroso, 2013)이 소개한 기법이라는 것만으로는 이 경로에 둘 이유가 되지 않는다.

## 결정

1. **헤지 요청을 쓰지 않는다(소유자 승인).**
   - 좌석 스냅샷의 첫 요청과 재요청 모두, 게이트웨이·메시·서비스·브라우저 어디에서도 같은 요청을 겹쳐 보내지 않는다.
   - ADR-0009 결정 3의 '헤지 요청은 순수 멱등적 읽기(좌석 스냅샷)에만 국한한다'와 ADR-0087 결정 21을 이 결정으로 대신한다.
   - 상태를 바꾸는 요청(홀드·주문·결제 접수)을 게이트웨이가 다시 보내지 않는다는 규칙과, 네트워크 재시도는 메시 한 층에서만 한다는 규칙은 그대로다(ADR-0009, ADR-0082).
2. **스냅샷 재요청은 시간 초과와 브라우저의 재요청으로 처리한다(추천 적용).**
   - 재요청은 api-client의 읽기 규칙을 그대로 따른다. 시간 초과는 10초 [가정]다. 네트워크 오류·시간 초과·`Retry-After`가 붙은 503이면 최대 2회 [가정] 다시 묻는다. 기다림은 `Retry-After`를 하한으로 ±20% 지터를 주고, 한 페이지의 자동 재시도는 분당 60회를 넘지 않는다(docs/frontend.md §4.1, guidelines §5).
   - 같은 구역의 스냅샷 재요청은 한 번에 하나만 보낸다. 앞 요청이 끝나기 전에 그 구역에 갭이 또 생기면 새 요청을 보내지 않고 앞 요청의 결과를 기다린다. 결과의 구역 판이 아직 낮으면 그때 한 번 더 묻는다.
   - 게이트웨이는 지금처럼 경로별 시간 초과와 동시 요청 상한을 지키고, 넘으면 바로 503과 `Retry-After`를 준다(ADR-0009 결정 1).
3. **시험(추천 적용).**
   - S-T17 '스냅샷 헤지 요청 검증'은 없앤다. 번호는 다시 쓰지 않는다.
   - 재요청 규칙은 지금 시험이 본다. 갭 복구 30초는 S-T13, 구독 전환 때의 재요청은 S-T21, 브라우저의 지터·`Retry-After` 하한은 FE-T4가 본다. '같은 구역 재요청은 한 번에 하나'는 FE-T11(좌석 연결 상태)의 통과 기준에 더한다.
4. **측정(추천 적용).** 스냅샷 경로의 p99·p99.9 지연과 재요청 비율은 경로별 골든 시그널(지연·트래픽·오류·포화)로 본다. planning/01 §3.1 보조 지표의 '헤지 요청 적용 전후의 p99.9 비교'는 뺀다.
5. **정본 반영.** docs/features/seat-hold.md(§2·§8·§12), docs/frontend.md(§4.4.2·§5.17 FE-T11), docs/api/openapi.yaml(스냅샷 경로 설명), docs/architecture.md §5, docs/observability.md §6 표, planning/01 §3.1을 고친다. ADR-0009·ADR-0087은 상태 줄에만 적는다.

## 검토한 대안

| 대안 | 고르지 않은 이유 |
| --- | --- |
| 지금처럼 재요청만 헤지한다(보내는 곳은 정하지 않는다) | 문서에만 있고 실행할 곳이 없다. S-T17도 무엇을 켜고 끄며 잴지 정할 수 없다 |
| 브라우저가 그 경로 p95 [가정] 뒤에 두 번째 GET을 보내고 먼저 온 응답을 쓴다. 늦은 쪽은 `AbortController`로 끊고, 추가 요청은 전체의 5% [가정] 이하로 둔다 | 기술 검토가 '남기려면' 조건으로 든 안이다. 재요청은 첫 그림 경로 밖이고, 두 요청이 같은 회차 샤드를 읽어 느린 원인이 겹친다. 브라우저가 끊어도 서버는 이미 받은 요청을 끝까지 처리한다. 이득을 재기 전에는 장치를 두지 않는다(아래 되돌릴 조건) |
| gw-fan의 Envoy에 `hedge_policy`를 덮어쓰기 정책(EnvoyPatchPolicy)으로 넣는다 | Envoy Gateway가 드러내지 않는 설정이라 판을 올릴 때마다 깨질 수 있다. Envoy의 헤지는 시도별 시간 초과 재시도에 걸려 있어서, 게이트웨이는 재시도하지 않는다는 ADR-0009 결정 3과 맞지 않는다 |
| 서비스 사이 gRPC에 `hedgingPolicy`를 넣는다 | 스냅샷은 gRPC가 아니다. 앱 gRPC에는 재시도·헤지 정책을 넣지 않기로 했다(ADR-0082) |
| 스냅샷 시간 초과를 짧게(예: 1초) 두어 빨리 다시 묻는다 | 바쁠 때 읽기를 늘린다는 점에서 헤지와 같다. 기본 읽기 시간 초과를 쓰고, 그동안 화면은 마지막 상태를 보인다 |

## 결과와 트레이드오프

- 문서에만 있던 장치가 빠져 설정·시험·관측에서 할 일이 준다. 바쁠 때 같은 읽기가 겹쳐 늘지 않는다.
- 같은 구역 재요청을 하나로 묶어, 갭이 잇따라 나도 요청이 쌓이지 않는다.
- 대가: 드물게 아주 늦은 재요청은 그만큼 늦게 끝난다. 그동안 화면은 마지막 상태와 "실시간 연결 복구 중"을 보이고, 홀드 판정은 서버가 하므로 헛클릭 409가 날 수 있다(지금도 같다).
- WBS는 바뀌지 않는다. S-T17은 시험 묶음 안의 한 줄이었다.

## 되돌릴 조건

- 측정에서 스냅샷 재요청의 p99.9가 갭 복구 30초(S-T13)나 전체 보기 구역의 5초 갱신을 지키지 못할 만큼 길고, 원인이 파드 하나의 이벤트 루프·GC처럼 다른 파드로 가면 피할 수 있는 것으로 확인되면, 브라우저 헤지(위 둘째 대안)를 새 ADR로 다시 본다.
- 그때는 두 번째 요청을 보내는 때(그 경로 p95 [가정]), 추가 요청 상한, 늦은 쪽을 끊는 방법을 정한다. 그리고 같은 조건에서 헤지 있음·없음의 p99.9와 샤드 부하를 재서 남긴다.

## 남는 한계

- 스냅샷 재요청의 꼬리 지연은 줄이지 않는다. 회차 샤드가 바쁠 때는 재요청도 함께 늦다.
- 이 경로에서 헤지가 꼬리 지연을 얼마나 줄였을지는 재지 않았다. 되돌릴 조건의 측정이 생기기 전에는 알 수 없다.
