# ADR-0200: 공연 상세 계약은 회차 공개 요약(`GET /v1/events/{eventId}`)에 칸을 더해 만든다 — 상세 화면의 정적 부분과 개인·실시간 부분 나누기

- **상태**: 채택(2026-11-05, 추천 적용. wbs 0.2.3·2.10.1 세부는 추천 적용이라는 승인 2026-10-14·2026-10-21·2026-10-28과 소유자 결정 2026-11-05 '화면 먼저'(ADR-0199)를 따른다). BUILD_ORDER HOT-310 ①.
- **관련**: ADR-0063(상세 2단·안내 모달), ADR-0093(공연 엔터티), ADR-0118(정렬 설정), ADR-0198(공연 등록 칸), ADR-0199(화면 먼저·이미지 파생본), [docs/design/d5-screen-blueprint.md](../design/d5-screen-blueprint.md) §5.2, [docs/frontend.md](../frontend.md) §2.5 `/events/[id]` 행, [docs/api/openapi.yaml](../api/openapi.yaml) `getEvent`·`EventPublicSummary`·`SellerInfo`
- **관련 ID**: FR-003, FR-046, FR-052, POL-003, POL-011, POL-018, POL-032, POL-035, POL-037, SCR-002

## 맥락

- 회차 공개 요약(`GET /v1/events/{eventId}`)은 공연명·회차 시작·판매자 상호만 준다. 그 설명은 "공연 상세의 다른 칸(가격 등급, 판매 정책, 고지, 이미지)은 공연 상세 계약과 함께 wbs 0.2.3에서 더한다"고 했다. 그런데 BAS-042는 그 일을 HOT-170에 넘겼고, HOT-170·171은 공연 데이터와 등록만 만들었다. 그래서 상세 화면이 읽을 계약이 없었다.
- 상세 화면(SCR-002)은 ISR(`cacheTag('event:{id}')`, 300초) 정적 셸 위에 개인 영역(본인확인·사람 확인·알림·찜·예매 제한)과 실시간 값(등급별 잔여석)을 얹는다(d5 §5.2, docs/frontend.md §2.5).

## 결정

1. **공연 상세는 회차 공개 요약에 칸을 더해 만든다(같은 경로, 같은 캐시)**:
   - 칸 더하기라 깨짐이 아니다. 처음 다섯 칸(스캐너 승인 화면 SCR-051은 그 가운데 공연명·회차 시작·판매자 상호를 읽는다)은 그대로 둔다.
   - 더하는 칸:
     - 공연: `genre`·`ageRating`·`runningMinutes`, 포스터 `posterUrl`·`posterAlt`(파생본 기준 주소, ADR-0199 결정 4), 설명 글의 글자판 `descriptionText`, 상세 이미지 `detailImages`(최대 10장, `url`·`alt` 필수), `artists`(20개까지), 공연장 `placeId`·`placeName`·`placeAddress`.
     - 이 회차: `openAt`·`lobbyOpensAt`(로비 셔플을 끈 회차는 null)·`entryOpensAt`·`endsAt`·`saleEndsAt`, 회차 상태 `status`, 정렬 방식 이름 `queueOrder`(HYBRID·PREQUEUE_SHUFFLE·FIFO, 두 값에서 계산, ADR-0118), `seatAssignment`, `perPersonLimit`, `reentryAllowed`, 판매 정보 배지 `badges`(카드와 같은 코드).
     - 같은 공연의 회차 목록 `rounds`(시작 순, `eventId`·`startsAt`·`openAt`·`saleEndsAt`·`status`): 취소 회차와 판매 종료가 지난 회차는 빼고(이 회차는 늘 넣는다) 60개 [가정]까지다. 승인 뒤 더한 회차(변경분, ADR-0198 결정 3)는 재승인 전까지 없다. 회차 칩(CMP-066)이 읽는다.
     - 등급별 정가 `priceTiers`(보이는 순서, `tierId`·`name`·`price`, 20개까지): 판매 상태 배지는 싣지 않는다. `tierId`로 실시간 상태(대기 상태 파일 `soldOutTiers`)를 맞춰 얹는다.
     - 판매자 신원정보 `seller`(`SellerInfo` 7항목, POL-037): 판매자 정보 모달이 읽는다. `sellerName`은 `seller.legalName`과 같다.
   - 설명 글: 기본안은 허용 노드 다섯만 담은 구조 문서(JSON)다(asvs/catalog-review 1.3.1, docs/frontend.md §5.14, 2026-10-28). 그 칸 `description`은 서식 글 편집기 PoC(FE-T41, HOT-320)와 등록 위저드(HOT-180)가 더한다. 이 단계는 글자판 `descriptionText`(줄바꿈만)만 둬서, 나중에 구조 문서 칸을 형 바꾸기 없이 더할 수 있게 한다. 화면은 글자판을 글자로만 그린다.
   - 판매 정책에서 오는 공개 값(선예매 창·일반 예매 시작 시각·단계별 1인 한도·회차별 취소 공제·가상계좌 허용)은 판매 정책 DSL 단계(HOT-250)가 이 응답에 요약 칸으로 더한다. 그 전까지 화면은 POL-032 기본 공제표와 `PRESALE` 배지만 보인다.
2. **응답에 싣지 않는 것(정적 캐시 밖)**:
   - 등급별 판매 상태(매진·판매 중): 공개 캐시(300초)로는 늦다. 대기열에 들지 않은 상세 화면이 읽을 실시간 출처(회차 단위 파일 경로)는 대기 상태 파일 단계(HOT-010)가 정하고, 상세 화면(HOT-311)이 `tierId`로 맞춰 얹는다. 그 출처를 읽는 호출 수는 docs/frontend.md §2.5와 architecture '페이지당 호출 수'에 그 단계가 적는다.
   - 평균 별점·후기 수: 후기 요약 경로(`GET …/review-summary`, CDN 60초)로 받는다.
   - 개인 값(본인확인·찜·알림·예매 제한·선예매 대상): 화면 스크립트가 같은 사이트 요청으로 받는다(docs/frontend.md §2.5).
3. **판매 승인 전·판매 중지 회차**: 승인 이력이 없는 회차와 없는 회차는 같은 404다(있는지조차 숨긴다). 한 번 공개된 뒤 판매 중지된 회차는 410 `event-suspended`다(사유는 싣지 않는다). d5 §5.2·planning/03 §2.14·ADR-0123 결정 1은 판매 중지 공연의 상세에 판매 중지 안내를 보이게 하는데, authz-matrix §3.5는 같은 404였다. 한 번 공개된 공연은 이미 알려진 공연이라 안내가 숨길 것을 드러내지 않아 정본 셋에 맞추고 §3.5를 고쳤다. 승인 전·반려 공연의 "공개 전인 공연입니다"는 404 화면 문구로 합친다(HOT-311).
   - 상태 코드 판정은 ADR-0201이 정한다(HOT-311에서 바꿈): 없는 회차는 `proxy.ts`가 서버 API에 물어 먼저 404로 거르고(시간 초과 300ms [가정], 실패하면 그대로 통과, 결과 60초 [가정]·1만 개 [가정] 기억), 판매 중지는 화면이 안내와 상태 표시를 그리고 앞 서버가 410으로 맞춘다. Next.js의 재작성이 상태 코드를 넘기지 않고, proxy가 머리로 알리면 본문과 상태가 잠깐 어긋나기 때문이다.
4. **채우는 쪽**: core-svc가 공연·회차·공연장·아티스트·판매자 칸을 채운다(새 단계 HOT-306). 이미지 칸은 이미지 단계(HOT-190)가, 등급별 정가와 `tierId`는 좌석맵·가격 단계(HOT-240)가 그 단계에서 이 응답에 더한다. 판매자 신원정보는 판매 승인(LCH-080)이 7항목을 확인한 공연에만 있으므로, 빠진 칸이 있으면 `seller`를 싣지 않는다. 그 전까지 화면 확인은 계약 모양 가짜 API로 한다(ADR-0199 결정 2).
5. **캐시 무효화**: 응답에 같은 공연의 회차 목록·공연 칸·판매자 정보가 들어가므로 태그를 둘 싣는다(`event:{eventId}`, `production:{productionId}`). 회차 하나의 변경은 그 회차 태그, 공연 칸·회차 목록·판매자 정보의 변경(재승인 반영·회차 연기·취소 포함)은 공연 태그로 그 공연의 모든 회차를 지운다(docs/infra.md §4.1은 태그 여러 개를 쉼표로 싣는다).

## 결과

- 상세 화면의 정적 부분을 한 번의 공개 캐시 응답으로 그린다. 무효화 태그는 `event:{eventId}`에 `production:{productionId}`를 더한 둘이다(결정 5).
- 판매 중지된 공연의 상세는 410으로 안내 화면을 보이고, 승인 전 공연은 지금처럼 404로 있는지조차 숨긴다(결정 3).
- 실시간·개인 값을 공개 캐시에 섞지 않는다.

## 다른 선택지

| 길 | 고르지 않은 까닭 |
| --- | --- |
| 공연 단위 상세 경로(`/v1/productions/{id}`)를 따로 둔다 | 화면 주소가 회차 단위(`/events/[id]`)이고, 회차 칸(오픈·로비·정렬 방식)이 함께 필요하다. 두 번 받고 두 캐시를 무효화해야 한다 |
| 등급별 판매 상태도 상세 응답에 싣는다 | 300초 공개 캐시로는 매진이 늦게 보인다. 실시간 값은 대기 상태 파일이 이미 낸다 |
| 설명 글을 HTML로 받아 그대로 그린다 | 서식 허용 목록과 정화 방식이 아직 정해지지 않았다(FE-T41). 정하기 전에는 글자로만 그려 스크립트 삽입 길을 두지 않는다 |
