# ADR-0038: 동일 이메일 기반 소셜 계정 연동 및 영구 병합 프로토콜 (OIDC 소유 증명 및 단방향 통합)

- **상태**: 채택 (2026-10-10 수립. ADR-0001 팬 단일 요소 인증 및 ADR-0011 로그인 담당 원칙을 계승하며 계정 연결·병합 워크플로를 공식 규정. 두 ADR의 결정은 그대로다) 2026-10-14: 기대평은 없앴고 후기는 관람 후기만 둔다(ADR-0063 결정 3). 본문의 '기대평'은 '관람 후기'로 읽는다.
- **관련 문서**: ADR-0001, ADR-0011, docs/features/identity.md §2.1, docs/data.md §2·§3·§4, docs/api/openapi.yaml, docs/security/asvs/auth.md, docs/security/data-classification.md 18번
- **관련 ID**: FR-001, FR-015, FR-017, FR-048, POL-001, POL-011, POL-019, POL-023, POL-027, POL-034, SCR-039, SCR-040

## 맥락
- 피켓은 사용자를 `(OAuth 제공자, 제공자별 고유 ID)`의 복합 키로 식별하며(FR-001), 동일한 이메일 주소라도 서로 다른 소셜 제공자(카카오, 구글, 네이버)로 로그인하면 별개의 독립 계정으로 생성되고 자동으로 합치지 않는다.
- 소유자 요청(2026-10-10): 같은 이메일의 다른 소셜 계정으로 가입하면 합칠지 묻고, 합치겠다고 하면 합치는 절차가 있어야 한다. 그 절차에서 사용자에게 무엇을 요구할지 정해 기획·설계에 넣는다.
- 공식 문서·표준으로 확인한 사실(2026-10-10):

| 항목 | 확인한 사실 |
| --- | --- |
| OIDC Core 1.0 §5.7 | `iss`와 `sub`를 합친 것만 최종 사용자의 안정된 식별자다. 이메일 같은 다른 클레임은 안정성·유일성이 보장되지 않고, 발급자는 같은 이메일 값을 시점을 달리해 다른 사용자에게 다시 쓸 수 있으며 한 사용자의 이메일은 바뀔 수 있다 |
| OWASP ASVS 5.0.0 | 6.8.1: 여러 IdP를 쓰면 IdP와 IdP 사용자 ID의 조합으로 등록·식별해 다른 IdP로 사칭할 수 없게 한다. 10.5.2: 클라이언트는 ID 토큰의 `sub`처럼 다른 사용자에게 다시 할당되지 않는 클레임으로 사용자를 식별한다 |
| 구글 | ID 토큰에 `email_verified` 클레임이 있다 |
| 카카오 | 사용자 정보의 `kakao_account`에 `is_email_valid`·`is_email_verified`가 있고, 이메일 제공에는 사용자 동의가 필요하다(`email_needs_agreement`) |
| 네이버 | 회원 프로필 API가 `email`을 주지만 검증 여부 값은 없다 |
| 개인정보 보호법 | §15①은 수집 목적 범위 안의 이용을 허용하고 4호에 '정보주체의 요청에 따른 조치'를 든다. §18①은 §15① 범위를 넘는 이용을 금지한다(2026-09-11 시행본, 국가법령정보센터) |

- 위협
  - 계정 탈취(Account Takeover): 이메일만 믿고 합치면, 이메일을 검증하지 않는 제공자나 재사용된 이메일로 남의 계정에 들어갈 수 있다.
  - 계정 존재 노출: "이 이메일로 가입한 계정이 있다"는 안내 자체가 정보다.
  - 한도 우회: 계정을 여럿 만들어 분산 구매한 뒤 합치면 1인 매수 한도(POL-011)와 계정당 수량 제한(FR-015)이 무너진다.
  - 되돌릴 수 없는 섞임: 병합 뒤 데이터를 두 계정으로 다시 나눌 수 없다.

## 결정
1. **식별의 단일 진실 공급원은 변함없이 `(제공자, 제공자 고유 ID)`다.** 이메일 주소는 연동 제안의 힌트로만 쓴다. 자동 병합은 절대 수행하지 않는다.
2. **가입 시 연동 제안(SCR-039).** 새 제공자로 처음 로그인했는데 그 (제공자, 사용자 ID)에 계정이 없고, 새 제공자가 이메일을 검증했다고 보증하며(구글 `email_verified=true`, 카카오 `is_email_verified=true`), 같은 이메일의 활성 계정이 정확히 하나일 때만 안내 화면을 띄운다. 이메일 검증 여부를 제공하지 않는 네이버는 제안 대상에서 배제한다. 같은 이메일 계정이 둘 이상이면 제안하지 않는다. 화면은 기존 계정의 제공자 종류만 보여 주고 닉네임·전체 이메일은 보여 주지 않는다. 선택지는 '기존 계정에 연결'과 '새 계정 만들기' 둘이며, 닫으면 아무것도 만들지 않는다.
3. **연결의 소유 증명은 기존 제공자 로그인뿐이다.** 이메일 인증 코드로 대신하지 않는다. 새 제공자가 메일함 소유를 이미 증명했고, 메일함 소유는 재사용된 이메일에서는 계정 소유가 아니기 때문이다. 기존 제공자 로그인 결과가 제안의 계정과 같은 (제공자, 사용자 ID)일 때만 새 제공자를 그 계정의 로그인 수단으로 추가하고 그 계정으로 로그인시킨다. 제안은 CSPRNG ID, 10분, 1회용이며 로그인 전 임시 쿠키로 브라우저에 묶는다. 다른 계정으로 3회 로그인하면 만료된다.
4. **설정에서 연결·해제(FR-017).** 재인증 토큰(POL-019, 5분)을 먼저 받고 새 제공자를 인증한다. 계정이 없으면 바로 연결한다. 해제는 마지막 로그인 수단에는 할 수 없다.
5. **설정에서 병합(SCR-040).** 인증한 제공자 계정이 이미 다른 PEAKET 계정이면 병합을 제안한다.
   - 대표(Primary) 계정은 본인확인을 한 계정이다. 둘 다 없으면 지금 로그인한 계정이고, 둘 다 있으면 병합하지 않는다(POL-001상 생길 수 없고, 생기면 CS가 본다).
   - 옮기는 것: 로그인 수단, 티켓(흡수 계정의 기기 키는 폐기해 월렛을 열 때 재발급), 굿즈·티켓 연동 부가 상품 주문과 배송지, 찜, 기대평·후기, 오픈 알림 구독.
   - 유지하는 것: 대표 계정의 닉네임과 동의. 마케팅 동의는 흡수 계정이 동의했어도 넓히지 않는다.
   - 파기하는 것: 흡수 계정의 이메일·닉네임. 계정 행은 병합됨 상태로 남겨 다음 로그인을 대표 계정으로 보낸다.
   - 막는 조건: 어느 계정에든 진행 중 온세일의 홀드·구매 세션·결제 대기 주문이 있음, 판매 종료 전 공연·한정 상품의 합산 보유 수가 한도를 넘음(POL-011, FR-015), 흡수 계정에 진행 중 탈퇴·이의 제기가 있음.
   - 사용자에게 요구하는 것: 옮겨지는 항목·개수와 대표 계정, 되돌릴 수 없음을 보여 주는 요약의 확인, 그리고 재인증. 확인 기록을 남긴다.
6. **실행과 알림.** 확인하면 한 트랜잭션으로 흡수 계정을 잠그고 로그인 수단을 옮긴 뒤 `identity.accounts-merged` 이벤트를 발행한다. 각 서비스가 자기 데이터의 계정 ID를 대표 계정으로 바꾼다(멱등, 재시도). 흡수 계정의 세션은 종료 이벤트로 끝낸다. 연결·병합·해제는 두 계정의 알림 채널에 알린다. 병합은 되돌리지 않으며 "이 작업을 하지 않았다면" 경로는 CS로 간다.
7. **법률 표기.** 본인이 요청한 같은 정보주체의 계정 병합은 수집 목적 안의 이용(§15①, 4호의 정보주체 요청에 따른 조치)으로 보아 별도 동의 항목(§18②1호)을 두지 않는다. 공식 해석을 찾지 못해 '해석'으로 표시하고 법률 검토 목록에 올린다(POL-027, data-classification 18번).

## 검토한 대안
| 대안 | 기각 사유 및 한계점 |
| --- | --- |
| 동일 이메일 발견 시 자동 병합 | OIDC §5.7과 ASVS 6.8.1에 어긋난다. 이메일을 검증하지 않는 제공자나 재할당된 이메일을 악용하여 타인의 티켓 지갑을 탈취할 수 있다. |
| 이메일 인증 코드로 소유 증명 대체 | 메일함 접근 권한만 증명할 뿐 소셜 계정의 적법한 소유권을 입증하지 못한다. 재사용된 이메일이면 남의 계정을 가져간다. |
| 연결·병합을 두지 않고 항상 별도 계정(기존 FR-001) | 소셜 계정을 여럿 쓰는 사람의 티켓·주문이 나뉜다. 소유자가 연결 절차를 요청했다. 별도 계정은 선택지로 남긴다. |
| 병합 후 분리 복원(Undo) 허용 | 옮긴 주문·티켓을 다시 나누려면 양쪽 서비스에 역이동 절차가 필요하고 그사이 생긴 데이터를 어디로 둘지 정할 수 없다. 대신 확인을 두 단계로 두고 알림을 보낸다. |

## 결과와 트레이드오프
- 얻는 것: 같은 사람의 소셜 계정이 한 계정으로 모이고, 이메일만으로는 누구도 남의 계정에 들어갈 수 없다. OIDC 및 OWASP 가이드라인을 준수한다.
- 대가
  - 화면 2개(SCR-039·040), 제안 저장소 2종, `account_provider` 테이블 분리, 서비스별 계정 ID 이동 처리가 늘어난다.
  - 네이버로 가입한 사람에게는 가입 때 제안이 뜨지 않아 설정에서 연결해야 한다.
  - 병합은 불가역적인 단방향 트랜잭션이므로 병합을 잘못 누른 사용자는 CS로 와야 한다.
- 되돌릴 조건
  - 제안 뒤 '다른 계정으로 로그인' 실패가 많으면 안내 문구와 제공자 로고 표시를 다시 본다.
  - 병합 관련 CS가 월 10건을 넘으면 요약 화면에 7일 유예(예약 뒤 실행)를 넣는 것을 검토한다.
  - 네이버가 이메일 검증 여부를 주기 시작하면 제안 조건에 넣는다.
