# ADR-0130: 기술 검토 중간 항목의 문서 수정 묶음 3 — 계정·보안·공급망·개인정보(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 중간 항목(영역: 마. 계정·보안)에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 방향은 소유자 결정(추천안 승인)이고, 검토가 안을 고르지 않은 곳의 선택과 값 같은 세부는 추천 적용이다. 측정 전 값은 [가정]으로 표시했다) 2026-10-29(원문 확인): 크롬이 사전 요청에 클라이언트 인증서를 싣는 버그(crbug.com/40089326)는 main 소스에 아직 남아 있다. `VerifyIfGiven` 설계를 유지한다(ADR-0065 상태 줄, docs/features/offline-gate.md §6.1).
- **관련**: review/tech-review.md(중간-051·중간-052·중간-053·중간-054·중간-055·중간-057·중간-058·중간-059·중간-060·중간-061·중간-062·중간-063·중간-064·중간-065·중간-066·중간-067·중간-068·중간-069·중간-070·중간-071), review/consistency-review.md R-148, 00-summary.md §6·질문 61, 같은 날 새 ADR-0100~0126(새 결정이 필요한 항목)

## 맥락

2026-10-27 기술 검토 2판은 설계의 모든 기술·기법을 시니어 개발자 관점에서 따져 높음·중간·낮음 항목으로 냈다. 2026-10-28 소유자가 남은 항목을 모두 추천안대로 고치라고 정했다. 새 결정이 필요한 항목은 따로 ADR(0100~0126)을 썼고, 이 ADR은 정본 문서를 고쳐 반영한 중간 항목 20건의 문제와 결정을 한곳에 모은다. 검토 문서에서는 이 항목들의 본문을 지우고 이 ADR을 가리키는 한 줄만 남겼다(지운 본문은 git 이력에 있다).

## 결정

항목마다 검토의 추천 수정을 따랐다(소유자 승인). 검토가 안을 여럿 내고 고르지 않은 곳은 고른 안과 이유를 적었고 '추천 적용'으로 표시했다. 정본에는 `(추천 적용 2026-10-28, 기술 검토 <번호>)`로 표시했다.

### 마. 계정·보안

#### 중간-051 관리 계정에 피싱에 강한 인증(패스키)의 자리가 없다(NIST 63B-4 AAL2의 '선택지 제공' SHALL)
- **문제**: 패스키는 '보조 수단'으로 등록만 되고 로그인·재인증 어디에도 쓰이지 않는다(d5 SCR-020 "패스키만으로는 로그인할 수 없습니다"). 그런데 identity §9와 ADR-0088 결정 8은 로그인 기록을 '비밀번호와 TOTP나 패스키'로 적어 대체처럼 읽힌다. NIST 63B-4는 AAL2에서 "Verifiers SHALL offer at least one phishing-resistant authentication option"이라 하는데, 문서는 AAL2를 세션 수명 근거로만 인용한다. TOTP는 실시간 중계 피싱에 약하고, 파트너 콘솔은 인터넷에 열려 있으며 예매자 명단·정산 계좌를 다룬다. 고시 §6②는 '인증서, 보안토큰, 일회용 비밀번호 등'으로 열린 목록이다.
- **결정**: TOTP 필수는 그대로 두고(소유자 승인), 패스키(WebAuthn)를 위험 운영 명령과 그 2인 승인·정산 계좌 변경·권한·역할 변경·예매자 명단 내려받기의 추가 요소로 쓴다(소유자 승인). `partner_admin`·`operator`·`commander`는 활성화 때 등록, RP ID는 콘솔 호스트, 사용자 확인 필수, 동기화 패스키 허용, 재인증 토큰 `factors`, 없으면 403 `reauth-required`, 분실 때 운영자 확인 재등록(추천 적용).
- **바꾼 문서**: planning/03 POL-020·§2.7·§3·§5.2, identity §1·§6·§9·I-T10·I-T53, asvs/auth.md 6.3.3·6.4.4·고시 §6②, data-classification 법률 #2, d5, planning/02 FR-021, planning/04 SCR-020·028, guide/11, openapi, ADR-0088 상태 줄
- **남는 한계**: planning/01 §5.2 '관리 계정 잠금과 패스키 단계 인증의 남는 한계'(일반 업무는 여전히 TOTP로 들어와 실시간 중계 피싱에 약함 등)

#### 중간-052 관리 계정 '5회 실패 영구 잠금 + 수동 재초대'가 표적 잠금 공격에 열려 있다
- **문제**: 실패를 계정 단위로 세고 5회면 잠그며 운영자 재초대로만 푼다. 파트너 관리자 이메일만 알면 누구나 5번 틀려 잠글 수 있다(3회 뒤 Turnstile은 사람이 직접 하면 넘는다). 공연 당일이면 파트너의 현장 운영(기기 배치·스태프 초대·SCR-037)이 운영자 확인을 기다리며 멈춘다. auth.md는 '악의적 계정 잠금을 막는 방법'을 요구하는 ASVS 6.1.1을 '적용'으로 판정했지만 근거 문서(auth-controls.md)는 '예정'이다. 고시 원문은 '일정 횟수 이상 인증에 실패한 경우 … 접근을 제한하는 등 필요한 조치'만 요구하고, auth.md 법률 표의 '정당한 사용자인지 확인한 뒤 해제한다'는 고시 원문에 없는 문장이다(안내서라면 출처를 적어야 함).
- **결정**: 계정·출발지 묶음으로 세고, 5회 연속 실패면 시간 잠금(15분, 24시간 안 다시면 1시간 [가정])과 업무 이메일 링크 + 인증 앱 코드 본인 해제(추천 적용). 운영자 재초대는 비밀번호가 맞은 뒤 인증 앱·복구 코드 5회 연속 실패의 보호 잠금에만(추천 적용, 추천 (4)의 '여러 IP 대량 실패'는 경보·사람 확인으로 바꿈). 시간 잠금은 고시 §5⑥에 든다(해석, POL-027).
- **바꾼 문서**: planning/03 POL-020·POL-027·§2.7·§3, data-classification 법률 #26, identity §6·§10·§11·I-T11·§13, asvs/auth.md 6.1.1·6.3.1·고시 §5⑥, d5, planning/02·04, guide/11, openapi, ADR-0062 상태 줄
- **남는 한계**: planning/01 §5.2 '관리 계정 잠금과 패스키 단계 인증의 남는 한계'(출발지를 바꿔 가며 반복 잠금, 업무 이메일과 인증 앱을 함께 잃은 사람)

#### 중간-053 리프레시 토큰 재사용 탐지에 응답 유실 재시도 유예가 없다
- **문제**: 쓸 때마다 새 토큰을 주고 옛 토큰이 다시 오면 패밀리 전체를 끝낸다. 탭 사이 동시 갱신은 Web Locks `token-refresh`로 막았지만(frontend §4.1), 갱신 응답(새 쿠키)이 모바일 망에서 사라지면 브라우저는 옛 쿠키로 다시 보내고 '탈취'로 처리돼 로그아웃된다. 대기 화면은 차례 1분 전에 미리 갱신하므로(frontend §5.1) 이 일이 구매 직전에 몰린다.
- **결정**: 바로 앞 토큰이 회전 뒤 30초 [가정] 안에, 새 토큰을 아직 쓰기 전에 다시 오면 탈취가 아닌 재시도로 보고 새 쌍을 한 번 더 주며 먼저 준 쌍은 폐기한다(추천 적용. 추천의 '같은 쌍 다시 주기' 대신, 해시만 저장하는 규칙을 지키려는 것). 그 밖은 지금처럼 패밀리 종료. 재시도 수 지표.
- **바꾼 문서**: identity §3·I-T4·I-T46, asvs/auth.md 7.4.1, openapi, planning/01 §5.2
- **남는 한계**: planning/01 §5.2 '리프레시 토큰 재시도 유예의 남는 한계'

#### 중간-054 계정 병합: 도달할 수 없는 단계가 있고, 법정 보존 기록·사건 기록의 계정 ID까지 덮어쓴다
- **문제**: 병합 때 "각 분산 서비스는 … 자기 DB의 `account_id` 외래키를 대표 계정 ID로 멱등하게 갱신"한다(data.md §4 9번). 그런데 purchase-svc의 주문은 이벤트 소싱(`order_event`, 재생으로 상태를 다시 만든다, payment §2 P-T13)이고, 주문·결제는 전자상거래법상 5년 보존하는 계약·대금결제 기록이다. 사건 기록의 계정 ID를 고치면 덧붙이기만 하는 기록이라는 전제가 깨지고, 고치지 않으면 사건을 재생한 주문과 갱신된 주문 행이 서로 다른 계정을 가리킨다. 봇·부정 조사에서도 '실제로 어느 계정이 샀는가'가 지워진다. 정본은 법정 접속기록만 원래 계정 ID로 둔다고 적었다(identity §2.1).
- **결정**: 소유·상태 값은 대표 계정으로 고치고, 사건·원장·법정 보존 기록은 원래 계정 ID를 두고 서비스별 대응표로 계정 묶음 조회·인가한다(추천 적용). 흡수 계정은 본인확인 전이라 티켓·후기가 없으므로 티켓 이전·후기 충돌 단계를 없애고 불변식 검사로 막는다(추천 적용).
- **바꾼 문서**: data.md §4 경계 9, identity §2.1·I-T32, payment.md §2, POL-034, planning/04, guide/08, ADR-0038 상태 줄
- **남는 한계**: planning/01 §5.2 '계정 병합 뒤 기록 조회의 남는 한계'

#### 중간-055 민감 작업 재인증의 강도가 제공자마다 다르고 '최근 인증' 확인 방법이 없다
- **문제**: ADR-0001의 핵심 보완 통제인 '민감 작업 전 제공자 재인증'은 제공자가 다시 로그인을 강제해 줄 때만 효과가 있다. 카카오는 `prompt=login`과 ID 토큰 `auth_time`이 있어 강제·확인이 된다(카카오톡 인앱 브라우저 제외). 네이버는 OIDC `prompt=login`은 받지만 ID 토큰 클레임에 `auth_time`이 없어 실제로 다시 로그인했는지 확인할 수 없다. 구글은 `prompt` 값이 `none`·`consent`·`select_account`뿐이라 다시 로그인을 강제할 수 없고, `auth_time`은 콘솔 설정을 켜고 `claims` 매개변수로 요청해야 나온다. 그래서 같은 브라우저에 구글 로그인이 살아 있으면 '재인증'이 사용자 입력 없이 통과될 수 있다(공유 기기, 잠금 풀린 휴대폰). ASVS 6.8.4는 기능별로 '최근성'을 요구하면 IdP 정보로 확인하고 없을 때의 대체 방식을 문서화하라고 하는데, ADR-0001·POL-019·identity.md 어디에도 재인증의 최근성 확인이 없다. asvs/auth.md는 6.8.4를 '적용'으로 적었다.
- **결정**: 제공자별 강제·최근성 확인 표를 두고(추천 적용), 재인증 토큰에 강도(`verified`·`requested`)를 남긴다. 양도·계좌 입력은 '확인됨' 제공자로 먼저 재인증, 안 되면 '요청만 함' + 알림·위험 점수(추천 적용). 팬 패스키 단계 인증은 다시 볼 조건과 함께 미룬다(추천 적용, 비교 결과).
- **바꾼 문서**: identity §2·§7.1·I-T54, POL-019, asvs/auth.md 6.8.4·요약, d5 CMP-064, ADR-0001 상태 줄, planning/01 §5.2, open-items 56
- **남는 한계**: planning/01 §5.2 '팬 제공자 재인증 강도의 남는 한계'

#### 중간-057 스캐너 mTLS가 '사전 요청에는 클라이언트 인증서를 싣지 않는다'는 표준과 맞지 않아 기본안을 기기 키 + DPoP로 바꾼다
- **문제**: 스캐너 화면(`scanner.peaket.example`)과 API(`scanner-api`)가 다른 출처라, JSON 쓰기(빈 본문도 `{}`)와 `Authorization` 헤더 요청은 모두 OPTIONS 사전 요청을 낳는다. Fetch 표준은 사전 요청을 자격(TLS 클라이언트 인증서 포함) 없이 보내게 한다. gw-scanner가 TLS에서 인증서를 '반드시' 요구하면 사전 요청이 TLS 단계에서 실패해 본 요청이 나가지 못한다. 크롬이 지금 사전 요청에도 인증서를 싣는다면 그것은 표준 위반이고, 크롬 쪽도 '고쳐야 할 버그'로 봤다(2021). PoC ⑤는 '실리는지'만 보고 이 표준 규칙과 서버 설정을 다루지 않는다.
- **결정**: Fetch 표준이 사전 요청에 TLS 클라이언트 인증서를 싣지 않으므로, 교차 출처 스캐너 API의 기본 기기 자격을 기기 키 + DPoP로 바꾼다(추천 적용, ADR-0051 결정 1·ADR-0065 결정 10 보완). mTLS는 하드웨어 키가 필요한 운영 환경의 선택지로, `VerifyIfGiven`과 OPTIONS를 뺀 경로의 `mtls_authenticated` 정책을 함께 쓰고, PoC는 선택 작업(추천 적용). DPoP 검증 세부와 기기 키 수명(만료 없음, 폐기·재등록)은 추천 적용.
- **바꾼 문서**: offline-gate §0·§6·§6.1·§6.5·§8·§10·§11·§12, identity §1·§6.1·I-T39, asvs/offline-gate.md(다시 판정), frontend, openapi, architecture, infra, infra-handover, secrets-and-keys, threat-model, data-classification, data.md, guidelines, planning/01~04, d3·d5, guide/06·14, ADR-0051·0065 상태 줄
- **남는 한계**: planning/01 §5.2 '현장 입장의 남는 한계'(소프트웨어 키, 루팅 기기에서 옮김)·'스캐너 기기 등록 경로의 남는 한계'(이제 늘 해당)를 고침

#### 중간-058 스캐너 전체 목록과 마지막 일련번호를 한 스냅샷에서 만든다는 규칙이 없다
- **문제**: 목록은 '회차마다 미리 만들어 두고' `lastSeq`를 함께 준다. 내용(티켓·키·입장 상태)을 읽은 뒤 `scanner_seq`를 따로 읽으면, 그 사이 커밋된 변경(키 폐기·입장 상태)은 목록에도 없고 `after=lastSeq` 변경분에도 없어 그 스캐너는 영영 모른다. 문서는 변경분 쪽의 커밋 순서는 꼼꼼히 따졌지만('변경이 빠지지 않는다') 목록 쪽 규칙이 없다.
- **결정**: 전체 목록은 REPEATABLE READ 한 트랜잭션에서 `scanner_seq`와 내용을 함께 읽어 만든다(추천 적용, ADR-0051 결정 6·ADR-0086 세부). 스캐너는 반영한 번호 이하의 변경을 무시한다.
- **바꾼 문서**: offline-gate §6.3·O-T38, data.md §4 경계 14

#### 중간-059 스캔 큐 쓰기의 IndexedDB 내구성을 정하지 않아 '유실 0건'이 약하다
- **문제**: 크롬은 121부터 IndexedDB 쓰기 트랜잭션 기본 내구성을 strict에서 relaxed로 바꿨다. relaxed는 변경이 OS 버퍼에 닿으면 '완료'를 알리고 디스크 기록은 보통 몇 초 뒤다. 스캐너 배터리가 갑자기 꺼지면(문서가 든 '휴대폰 방전' 상황) 통과시킨 마지막 기록을 잃을 수 있다. 문서는 '기기에 남은 기록 유실 0건'이라 적고 내구성 설정이 없다.

#### 중간-060 스캐너 인증서 수명(30일)과 만료 경보 기준(30일·7일)이 맞지 않아 경보가 늘 켜진다

#### 중간-061 파트너 웹훅의 SSRF 방지를 구체화하고 추적 표에 넣는다
- **문제**: 파트너가 등록한 주소로 서버가 요청을 보내는 것은 대표적인 SSRF 길이다. 그런데 정본에는 '사설망 대역과 허용하지 않은 리디렉션으로 가는 요청을 막는다' 한 줄뿐이다. 등록 때 주소만 검사하면 DNS 재바인딩(나중에 사설 IP로 바뀜)을 못 막고, IPv6·IPv4 사상 주소·링크 로컬(169.254.169.254 메타데이터) 처리도 없다. 발송 워커는 임의의 인터넷 호스트로 나가야 해서 asvs/delivery 13.2.4의 '나가는 통신 허용 목록'과도 어떻게 맞출지 없다. 웹훅 발송을 판정하는 ASVS 기능 표(1.3.6·15.3.2)도 없다.

#### 중간-063 포트폴리오 기간에 서명된 이미지를 둘 레지스트리가 정해지지 않았다

#### 중간-069 사전조치의무사업자 해당 여부를 별표 3의2 원문으로 다시 판정한다(해석, 법률 검토 필요)
- **문제**: 법률 행은 '별표 3의2를 확인하지 못해 해당 여부는 확인 필요'로 두고 게재 제한(비교·식별 기술)과 사전 고지를 '부분 적용'으로 남겼다. 원문을 보면 별표 3의2는 사회관계망·온라인 커뮤니티·대화방, 개인방송, 검색 서비스를 대상으로 하고, 비고 1에서 '재화의 판매 또는 … 서비스의 제공(판매를 포함한다)을 주된 목적으로 하는 부가통신서비스'를 뺀다. PEAKET의 후기는 판매 중개 서비스에 딸린 기능이라 빠진다고 볼 근거가 생겼다. 그대로 두면 구현자가 국가기관 기술이나 성능평가를 통과한 비교·식별 기술 연동(시행령 §30의6②3호)까지 범위로 오해할 수 있다.
- **결정**: 전기통신사업법 시행령 별표 3의2 비고 1(판매가 주된 목적인 부가통신서비스 제외)에 따라 PEAKET 후기는 사전조치의무 대상이 아니라고 본다(해석, 소유자 승인). 상시 신고 유지와 다시 판정할 조건은 추천 적용(2026-10-28). 조치의무사업자(①) 여부는 확인 필요로 남긴다.
- **바꾼 문서**: docs/security/asvs/catalog-review.md, planning/03 POL-027·POL-044, docs/security/data-classification.md, planning/01 §5.2, design/d5, guide/13, ADR-0066 상태 줄
- **남는 한계**: planning/01 §5.2 기존 행 고침(사전조치는 해석으로 빠진다고 봄)

#### 중간-070 백업에 남는 파기 대상 개인정보의 처리 규칙이 ClickHouse에만 있다
- **문제**: ADR-0053 결정 10은 'TTL로 지운 원시 개인정보가 백업에 오래 남지 않게' ClickHouse 백업을 7일로 줄였다. 같은 논리가 필요한 다른 백업에는 규칙이 없다. Aurora는 PITR 35일과 일 스냅샷 교차 리전 복제(스냅샷 보존 기간은 적혀 있지 않음), MongoDB는 일 스냅샷, S3 백업 버킷은 버전 관리를 켜 두었다(지운 객체의 옛 판이 수명 규칙 없이는 남는다). 탈퇴·파기한 회원 정보가 백업에 얼마 동안 남는지, 백업에서 복원한 뒤 그 사이의 파기를 다시 적용하는지(파기 기록을 다시 돌리기)가 정본에 없다.
- **결정**: 저장소별 백업 보존 상한을 두고 복원하면 파기 감사 로그로 그 사이의 파기를 다시 적용한 뒤에 서비스에 붙인다(소유자 승인). 상한 값(교차 리전 7일, 수동 35일, S3 옛 판 7일, 대상 ID 40일)은 추천 적용·[가정](2026-10-28). 백업 속 정보의 법적 파기 시점은 확인 필요(POL-027). 시험 V-T32.
- **바꾼 문서**: docs/security/data-classification.md, docs/infra.md §6·§10, planning/03 POL-027, planning/01 §5.2, guide/13, docs/verification.md §9, ADR-0053 상태 줄
- **남는 한계**: planning/01 §5.2에 '백업에 남는 파기 대상 개인정보'(최대 35일, 법적 기준 확인 필요, 대응은 접근 제한·복원 뒤 다시 적용)

#### 중간-071 '웨이포인트 신원만 받는 L4 정책'이 게이트웨이 직접 요청과 부딪친다(운영 설계)
- **문제**: 같은 결정에서 ① gRPC를 받는 서비스는 웨이포인트 신원만 받는 L4 정책을 두고 ② 게이트웨이는 파드 주소로 바로 보내 웨이포인트를 지나지 않는다고 했다. gRPC를 받는 서비스 대부분(purchase-svc·payment-svc·identity-svc·queue-svc·core-svc)은 게이트웨이 REST도 받으므로, 글자 그대로 설정하면 게이트웨이 요청이 노드 프록시에서 거절된다. 웹·파트너 앱 서버의 identity-svc 직접 호출, 런북 Job 신원 같은 다른 허용 규칙과도 겹친다.
- **결정**: 'gRPC 받는 서비스는 웨이포인트 신원만'을 포트별 허용 표로 바꾼다(방향 소유자 승인, 표의 칸과 지표 포트는 추천 적용 2026-10-28). 시험 D-T36.
- **바꾼 문서**: docs/architecture.md §5, docs/infra.md §9, docs/devops.md §14, ADR-0082 상태 줄
