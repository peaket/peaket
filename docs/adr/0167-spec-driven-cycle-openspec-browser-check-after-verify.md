# ADR-0167: 코드는 OpenSpec 사이클로 만든다 — Verify 뒤 Claude in Chrome 브라우저 확인, E2E는 따로(소유자 결정, 2026-10-30)

- **상태**: 채택 (2026-10-30. 소유자가 "구현전에 스펙주도개발을 위한 스펙문서를 만드는게 좋은지, 만약 그렇다면 어떤 스킬을 쓸지(spec kit, bmad, gsd, 등등) 추천해주세요"라고 물었다. 이어서 포프TV 영상 둘을 보이며 그 관점으로 하나를 골라 달라고 했다. OpenSpec 추천을 듣고 "apply 이후에 브라우저를 열어서 기능을 LLM이 직접 눌러 테스트 해보는 방식의 과정을 추가"하자고 했다. 그다음 "브라우저 확인은 Verify 다음에", "브라우저 컨트롤은 Claude in Chrome", "e2e 테스트는 이 사이클을 이용한 구현 이후에 따로"라고 정하고 "네, 써 주세요"라고 했다. 소유자 결정은 다섯이다: 도구(OpenSpec), 브라우저 확인 단계를 둔다는 것, 그 자리(Verify 다음), 조종 도구(Claude in Chrome), E2E 분리. 나머지는 추천 적용이다: 정본 우선 규칙, 명세의 근거 ID, 시험 규칙, 브라우저 확인을 적는 칸과 결과 파일, 시험용 Chrome 프로필, 보관 시점, 설정 파일 자리, 첫 시험 작업.) 보완(2026-10-30, 소유자 "네 진행"): 결정 7의 설치·초기화를 같은 날 했다. OpenSpec 1.15.0(개발 의존성), pnpm 12.16.0(`packageManager`, 12.16.1은 게시 3일 전), devops §4.4 공급망 설정의 `pnpm-workspace.yaml`. 초기화는 미리 쓴 `config.yaml`을 그대로 두었다. OpenSpec 명령은 PATH에 없어 `pnpm exec openspec`으로 부르고, 개발 PC의 전역 설정은 '기본 묶음 + verify'와 사용 통계 끔이다(architecture §8.6 7번, R-196). 보완(2026-10-30, 소유자 "이제 부터는 archive 까지의 사이클 단위로 한번에 진행을 하도록 해주세요.(웬만하면 중간에 묻지 않기)"): 결정 2의 3단계(계획 리뷰)를 1인 기간에는 AI가 정본과 대조해 스스로 하고, 탐색부터 보관·커밋까지 한 번에 진행해 끝에 한 번 보고한다. 방향을 바꾸는 결정, 공개 게시·원격 푸시, 계정·저장소 만들기, 비용, 되돌리기 어려운 일, 보안 규칙에 걸리는 일만 멈추고 묻는다(architecture §8.6, R-201).
- **관련**: ADR-0057(운영은 설계만, 측정은 PC), ADR-0074(git flow), ADR-0165(모노레포 `peaket`), [docs/architecture.md](../architecture.md) §8.2·§8.4·§8.5·§8.6, [docs/devops.md](../devops.md) §3.3, [docs/frontend.md](../frontend.md) §5.17, wbs 0.1.1·0.6.2·2.10.3·4.5.4·7.2.6

## 맥락

- 설계 문서는 이미 크다. 요구사항(FR·NFR), 화면 정본(design/d5), 계약 원본(`docs/api/`), 기능 설계서, ASVS 추적 표가 있고, 시험도 ID와 통과 기준으로 정해 두었다(FE-T, D-T, ASVS 태그 등).
- 스펙 주도 개발은 코드를 쓰기 전에 기능 명세(바깥에서 보이는 행동과 '다 됐다'의 기준)를 먼저 쓰고, 사람이 확인한 뒤 그대로 구현하는 방식이다. 이 프로젝트에서 남은 물음은 두 가지였다. AI가 구현할 때 계획을 어떻게 미리 맞출 것인가, 그리고 이미 큰 정본과 명세를 어떻게 겹치지 않게 할 것인가.
- 소유자가 고를 기준으로 든 영상의 관점(포프TV, 2022-09·2025-07)은 다음과 같다.
  - 자동 시험은 쓰되, 코드보다 시험을 먼저 쓰는 방법론(TDD)을 강제하지 않는다. 입력과 출력이 분명한 계산만 예외로 먼저 쓴다.
  - 버그가 나면 그 버그를 재현하는 시험을 먼저 만들어 실패를 보고, 고친 뒤 남긴다.
  - 시험하려고 내부 함수를 공개해 캡슐화(내부를 숨겨 서로의 코드를 망가뜨리지 않게 하는 원칙)를 깨지 않는다. 대부분은 처음부터 끝까지 실제처럼 돌려 보는 시험(E2E)으로 확인한다.
  - 이것은 한 실무자의 주장이고, TDD의 효과를 다룬 연구 결과는 엇갈린다. 그래서 이 ADR은 TDD를 금지하지 않는다. 강제하지 않을 뿐이다.
- 후보 넷의 원문을 2026-10-30에 확인했다(GitHub 저장소의 최신 출시와 원본 파일).
  - **Spec Kit v1.2.5**: 설명서(spec-driven.md)의 원칙 3조가 "Test-First Imperative … NON-NEGOTIABLE"이고, 헌법 양식의 예시 3조도 "Test-First (NON-NEGOTIABLE)"이다. 구현 명령(implement)은 시험 작업을 구현보다 먼저 하라고 한다. 다만 작업 목록에 시험을 넣을지는 선택이다. 계획 단계는 기능마다 data-model.md, contracts/, research.md, quickstart.md를 만든다.
  - **BMAD v6.12.4**: 개발 단계(dev-story)가 "Write FAILING tests first"(실패하는 시험 먼저)로 정해져 있다. 스킬이 50개쯤이고, 그 가운데 분석가·PM·설계자·개발자·UX 역할 스킬이 PRD·에픽·스토리 문서를 만든다.
  - **GSD(open-gsd/gsd-core) v1.19.0**: 시험 먼저 모드(`workflow.tdd_mode`)는 기본이 꺼짐이다. 켜도 입출력이 분명한 업무 규칙·API 계약·변환에만 적용하고, 화면·설정·연결 코드·CRUD(만들기·읽기·고치기·지우기만 하는 코드)는 보통 흐름으로 둔다. 대신 프로젝트·요구사항·로드맵·상태 문서를 따로 둔다.
  - **OpenSpec v1.15.0**: 명세 규칙이 "명세는 행동 계약이지 구현 계획이 아니다. 내부 클래스·함수 이름은 쓰지 않는다"이다. 작업마다 확인 방법을 적고, 시험은 그 작업 묶음과 함께 넣는다. 기존 프로젝트에는 지금 바꿀 부분만 쓰고, 기존 요구사항 문서는 옮겨 적지 말고 재료로 쓰라고 한다. `openspec/config.yaml`의 규칙과 스키마 포크로 바꿔 쓸 수 있다.
- OpenSpec 자체는 코드 리뷰 도구가 아니다(문서 'Reviewing a Change', 2026-10-30 확인). 사람이 리뷰하는 것은 코드 전의 계획이다. 코드는 확장 명령 `/opsx:verify`가 계획과 대조할 뿐이다. 이 대조는 완결성·정확성·일관성 셋을 AI가 읽어서 판단하고, 결과는 치명·경고·제안으로 알릴 뿐 보관(Archive)을 막지 않는다. 버그·보안·품질 리뷰는 따로 있어야 한다.
- 정본의 시험 배치(devops §3.3)에서 E2E(Playwright, 브라우저 엔진 셋)는 프론트엔드 PR마다 CI에서 '실패 0'을 보는 관문이다. E2E를 만드는 일은 WBS 2.10.3·4.5.4·7.2.6에 있다.

## 결정

1. **스펙 주도 개발 도구는 OpenSpec이다(소유자 결정)**
   - 코드(`apps/`, `services/`, `packages/`, `data/`, `infra/`)를 바꾸는 일에 쓴다. 문서만 고치는 일은 지금처럼 문서 점검 도구로 확인한다.
   - 동작이 바뀌지 않는 변경(구조 정리, 도구, 의존성)은 OpenSpec 규칙대로 `skip_specs: true`로 명세 없이 제안과 작업 목록만 쓴다(추천 적용).
   - CLI는 저장소 뿌리의 개발 의존성으로 판을 정확히 고정하고 `pnpm exec openspec`으로 부른다. 그래야 누가 받아도 같은 판을 쓴다(추천 적용).

2. **사이클(소유자 결정: 브라우저 확인 단계와 그 자리. 나머지 순서는 OpenSpec 기본값)**

   | 단계 | 하는 일 | 누가 |
   | --- | --- | --- |
   | 0. 시작 전 | ASVS 추적 표(architecture §8.2)와 운영 확인 표(§8.4)를 쓰고, 작업 가지를 만든다(§8.5) | 사람과 AI |
   | 1. 탐색(Explore) | 정본을 읽고 무엇을 바꿀지 따진다. 코드는 쓰지 않는다 | 사람과 AI |
   | 2. 제안(Propose) | `openspec/changes/<이름>/`에 제안, 명세, 설계(필요할 때만), 작업 목록을 만든다 | AI |
   | 3. 계획 리뷰 | 제안 → 명세 → 작업 목록 순서로 읽고 고친다 | 사람 |
   | 4. 구현(Apply) | 작업 목록대로 코드를 쓰고 하나씩 체크한다 | AI |
   | 5. 대조(Verify) | 코드가 명세·작업 목록대로인지 읽어서 대조한다(`/opsx:verify`) | AI |
   | 6. 브라우저 확인 | 명세의 시나리오를 Claude in Chrome으로 하나씩 눌러 보고 결과를 남긴다(결정 5) | AI(사람이 지켜볼 수 있다) |
   | 7. 코드 리뷰와 CI | PR에서 코드 리뷰(사람, Claude Code `/code-review`)와 공용 CI(devops §3)를 거친다 | 사람과 CI |
   | 8. 보관(Archive) | 명세의 바뀐 요구사항을 `openspec/specs/`에 합치고 변경 폴더를 보관함으로 옮긴다 | AI |

   - 대조(Verify)를 먼저 두는 것은 싼 검사로 빠진 작업과 요구사항을 걸러 낸 뒤 느린 브라우저 확인을 하려는 것이다(소유자 결정).
   - `/opsx:verify`는 기본 묶음(core)에 없다. 그래서 `openspec config profile`로 확장 묶음을 켠다.
   - 브라우저 확인에서 실패가 나오면 결정 4의 버그 규칙대로 고친다. 그 뒤 대조를 다시 하고, 실패했던 시나리오만 다시 눌러 본다.
   - 보관은 PR 검토와 CI가 끝난 뒤 같은 작업 가지에서 하고, 그 커밋까지 함께 스쿼시 병합한다. 그래야 `develop`의 `openspec/specs/`가 병합된 코드와 같은 때를 가리킨다(추천 적용). 원격 저장소를 만들기 전까지는 PR 대신 `/code-review`로 리뷰한다(§8.5의 예외와 같다).

3. **정본이 이긴다(추천 적용)**
   - `openspec/specs/`는 구현해 확인한 행동의 목록이다. 정본이 아니다.
   - 명세의 요구사항 글에 정본의 규칙을 옮겨 적지 않는다. 바깥에서 보이는 행동만 쓰고, 근거 ID를 괄호로 단다. 근거 ID는 FR·NFR·POL·SCR 번호, openapi `operationId`, ASVS 항목, 시험 ID다.
   - 제안의 '영향(Impact)'에는 이 변경이 기대거나 고치는 정본 문서와 ID, WBS ID를 적는다.
   - 정본에 없는 결정이 필요하면 구현 전에 정본과 ADR을 먼저 고친다. 명세와 정본이 다르면 정본이 이기고 명세를 고친다.
   - 문서 점검 도구는 `openspec/`의 마크다운도 읽는다(링크, 공개 범위). 맞지 않는 규칙이 나오면 첫 시험(결정 7) 때 정한다.

4. **시험 규칙(추천 적용, 영상의 관점을 규칙으로 옮김)**
   - 시험을 먼저 쓰라고 강제하지 않는다. 입력과 출력이 분명한 계산(금액·수수료 계산, 좌석 배정 규칙, 서명 검증 등)은 먼저 써도 된다.
   - 작업마다 확인 방법(시험, 명령, 보이는 결과)을 적는다. 정본에 그 시험 ID가 있으면 그 ID를 쓰고, 그 시험은 이 변경에서 만든다. E2E는 예외다(결정 6).
   - 버그를 고칠 때는 그 버그를 재현하는 시험을 먼저 만들어 실패를 본다. 고친 뒤 통과를 보고, 그 시험을 CI에 남긴다. 재현되는 가장 낮은 단계(단위, 통합)에 쓴다.
   - 시험하려고 내부 함수를 공개하거나 인터페이스로 바꾸지 않는다. 바깥 경계(API, 화면, 이벤트)에서 시험한다.

5. **브라우저 확인(소유자 결정: Verify 다음, Claude in Chrome. 세부는 추천 적용)**
   - **적는 자리**: 화면이 바뀌는 변경은 tasks.md 끝의 `## Workflow follow-up` 칸에 '브라우저 확인'을 적는다. 이 칸은 OpenSpec 규칙상 진행률에 세지 않는 참고 항목이다. 체크 칸으로 두면 그보다 먼저 도는 대조(Verify)가 '끝나지 않은 작업'으로 세기 때문이다.
   - **실행**: 프로젝트 스킬 `peaket-browser-check`(`.claude/skills/peaket-browser-check/SKILL.md`)가 맡는다. 그 변경의 명세 시나리오('~하면 ~된다')를 하나씩 눌러 보고, 결과를 `openspec/changes/<이름>/browser-check.md`에 남긴다. 남기는 것은 시나리오별 통과·실패·확인 못 함, 본 것, 콘솔 오류, 실패한 요청이다.
   - **환경**: 개발 PC의 로컬 실행(wbs 0.4.1)에서 합성 데이터와 고정 시드로 한다. 결제·본인확인·사람 확인은 정본의 대역(시뮬레이터 결제사, 본인확인 모의 기관, 사람 확인 시뮬레이터)을 쓴다. 실제 계정, 실제 결제, 실제 키는 쓰지 않고, 캡차를 풀지 않는다. 실제 결제사·본인확인기관 화면이 뜨면 멈추고 알린다.
   - **Chrome**: Claude in Chrome은 사용자의 Chrome을 AI가 조종하는 확장 기능이다. 실제 Chrome의 로그인 상태를 그대로 쓰므로, 시험용 Chrome 프로필을 따로 만들어 그 프로필에만 확장을 설치한다. 그 프로필에는 개인 계정으로 로그인하지 않는다. 로그인은 시드 파일의 시험 계정만 쓴다. 로컬 주소(localhost)의 사이트 허용은 소유자가 한다.
   - **판정**: 관문이 아니라 참고 증거다. 같은 화면도 AI가 누를 때마다 결과가 다를 수 있다. 통과는 '이번에 눌러 보니 됐다'이고, 실패는 재현 시험으로 확인한 뒤 사실로 본다. 보관 전에는 `browser-check.md`에 고치지 않은 실패가 없어야 한다. 이것은 설정의 보관 안내(권고)와 사람의 확인으로 지킨다. OpenSpec이 기계로 막지는 않는다.
   - **다루지 않는 것**: 패스키 창(브라우저·운영체제가 띄우는 창이라 확장이 다룰 수 없다. I-T53 같은 시험 코드로 본다), 브라우저 엔진별 차이(E2E), 부하(`peaket-loadtest`), 접근성 판정(CI의 axe·Storybook).
   - **화면이 없는 변경**: 서버만이나 도구만 바뀌면 브라우저 확인을 건너뛰고 `browser-check.md`에 '해당 없음'과 까닭만 적는다.
   - **증거**: 화면 캡처는 개발 PC에 저장하고 저장소에는 넣지 않는다. 실패 캡처만 PR 설명에 붙인다. GIF 녹화는 파일 내려받기라 그때마다 소유자 허락을 받는다.

6. **E2E는 따로 한다(소유자 결정)**
   - 이 사이클의 기능 변경은 E2E 시험을 새로 쓰지 않는다. 브라우저에서만 재현되는 버그의 재현 시험 한 건은 예외다(결정 4의 버그 규칙).
   - E2E는 화면 묶음을 이 사이클로 만든 뒤 따로 쓴다. WBS의 E2E 작업(2.10.3 Playwright 3엔진 매트릭스, 4.5.4·7.2.6 뷰포트 E2E)과 docs/frontend.md §5.17의 E2E 시험 ID가 그 일이다. 그 일도 OpenSpec 변경 하나로 돌린다. 제안에 어느 시험 ID를 쓰는지 적고, 브라우저 확인은 '해당 없음'으로 둔다(추천 적용).
   - CI의 E2E 관문(devops §3.3: 프론트엔드 PR, 실패 0)은 그대로다. 그사이에는 이미 쓴 E2E만 돈다.

7. **설정 파일과 첫 시험(추천 적용)**
   - `openspec/config.yaml`(배경과 단계별 규칙)과 `.claude/skills/peaket-browser-check/SKILL.md`(브라우저 확인 절차)를 2026-10-30에 초안으로 둔다. 규칙의 정본은 architecture §8.6이고, 설정이 그와 다르면 §8.6이 이긴다.
   - wbs 0.1.1에서 OpenSpec을 설치하고 `openspec init --tools claude`로 초기화한다. 초기화는 `openspec/specs/`, `openspec/changes/`, OpenSpec 자신의 스킬(`.claude/skills/openspec-*`)과 명령(`.claude/commands/opsx/`)을 만든다(OpenSpec CLI 문서, 2026-10-30 확인). 이미 있는 `config.yaml`을 그대로 두는지는 그때 확인한다.
   - 사이클의 첫 시험은 Phase 0의 첫 코드 변경 하나로 한다. 브라우저 확인의 첫 시험은 화면이 처음 생기는 wbs 0.6.2(Storybook)에서 한다. 첫 시험에서 고칠 점이 나오면 §8.6과 설정을 함께 고친다.

## 검토한 대안

- **Spec Kit**: GitHub이 만들어 이름이 가장 널리 알려졌다. 하지만 설명서와 헌법 예시가 시험 먼저를 '협상 불가'로 둔다. 계획 단계가 기능마다 데이터 모델과 API 계약 문서를 다시 만들어 docs/data.md·`docs/api/`와 겹친다. 프리셋으로 좁혀 쓸 수는 있지만 기본 성향을 거슬러 써야 한다. 기각.
- **BMAD**: 개발 단계가 실패하는 시험을 먼저 쓰게 정해 두었다. 역할별 문서(PRD, 에픽, 스토리)가 기획 문서와 WBS를 다시 쓴다. 기각.
- **GSD**: 시험 먼저를 입출력이 분명한 곳에만 켜는 방식은 영상의 관점과 가장 가깝다. 하지만 프로젝트·요구사항·로드맵·상태 문서를 따로 두어 WBS·기획과 이중이 된다. 기각.
- **이 저장소 전용 스킬만**: 가장 가볍고 딱 맞는다. 하지만 바깥 사람이 아는 관례가 없고, 변경 폴더·보관·대조를 모두 직접 만들어 관리해야 한다. 기각.
- **브라우저 확인을 tasks.md의 마지막 작업 묶음으로**: 보관이 그 체크를 기다리게 할 수 있다. 하지만 대조(Verify)가 먼저 돌아 '끝나지 않은 작업'으로 센다. 기각.
- **브라우저 확인을 구현 바로 다음(대조 전)에**: 빠진 작업을 싼 대조로 먼저 거르는 편이 낫다(소유자 결정). 기각.
- **Playwright MCP나 Playwright Test Agents로 조종**: E2E와 같은 엔진이라 찾은 버그를 그대로 시험 코드로 옮기기 쉽고 CI에서도 돈다(Playwright v1.64.1의 planner·generator·healer, Playwright MCP v0.0.83, 2026-10-30 확인). 소유자가 Claude in Chrome을 골랐고, 브라우저 확인은 시험이 아니라 E2E와 나눴다. healer는 기능이 고장 났다고 보면 시험을 건너뛰게 만들 수 있어, E2E에서 쓴다면 건너뜀을 실패로 세야 한다. 기각.
- **Claude 앱의 내장 브라우저**: 개인 Chrome과 떨어진 프로필이라 실수가 개인 계정에 닿지 않는다. 소유자가 Chrome을 골라 시험용 프로필로 같은 효과를 낸다. 기각.

## 결과와 트레이드오프

- 얻는 것: 사람이 코드 전에 계획을 고친다. 명세가 바깥 행동만 적어 구현을 바꿔도 덜 깨진다. 이미 큰 정본을 다시 쓰지 않는다. 눈에 띄는 고장은 E2E보다 먼저 브라우저 확인에서 잡히고, 버그마다 재현 시험이 남는다.
- 두 곳에 같은 행동이 적히는 위험: `openspec/specs/`와 정본이 어긋날 수 있다. 결정 3의 규칙(정본 우선, ID만 인용)으로 줄이지만 기계로 막지는 않는다.
- 브라우저 확인은 느리고, 결과가 매번 같지 않으며, Chrome 하나로만 본다. 소유자의 Chrome이 켜져 연결되어 있어야 해서 CI나 무인 실행에서는 돌지 않는다.
- E2E를 뒤로 미룬 동안, Safari·Firefox에서만 나는 화면 고장과 지난 화면의 되돌아감(회귀)은 단위·통합 시험과 뒤 변경의 브라우저 확인으로만 잡힌다. 그 E2E 작업을 할 때 처음 드러날 수 있다.
- 변경마다 제안·명세·작업 목록을 쓰는 비용이 든다. 동작이 바뀌지 않는 변경은 명세를 건너뛴다(결정 1).
- OpenSpec은 1.x에서 판이 빠르게 오른다(2026-10-24에 v1.15.0). 판을 고정하고 올릴 때 바뀐 점을 확인한다.
- WBS 작업 일수는 바꾸지 않았다. 0.1.1과 0.6.2의 작업 설명에만 더했다.

## 되돌릴 조건

- `openspec/specs/`와 정본을 맞추는 일이 자주 생겨 비용이 커지면, 명세를 쌓지 않는 전용 스키마(제안·작업 목록만)로 바꾸는 새 ADR을 쓴다.
- 브라우저 확인이 잡는 고장이 거의 없고 시간만 들면, 화면을 크게 바꾸는 변경에만 하도록 줄인다.
- Claude in Chrome을 쓸 수 없게 되면(확장 지원 중단, 연결 불가), 내장 브라우저나 Playwright MCP로 바꾸는 새 ADR을 쓴다.
- OpenSpec이 깨지는 판을 내거나 관리가 멈추면, 고정한 판으로 버티며 대안을 다시 본다.
