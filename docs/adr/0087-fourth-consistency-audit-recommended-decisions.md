# ADR-0087: 4차 전수 정합성 점검의 추천 적용 — 계약 예외, 데이터 보존, 세션·상태 규칙, ASVS 요약 통일(2026-10-23)

- **상태**: 채택 (2026-10-23. 소유자 요청 "이 프로젝트의 기획 설계 문서 전체를 읽고 정합성을 검증해서 안맞는 부분은 모두 고쳐주세요."에 따른 4차 전수 정합성 점검이다. 정본이 분명한 어긋남은 정본 쪽으로 고쳤고(review R-99), 정본에 값이 없거나 같은 순위의 두 정본이 다르게 말한 것만 이 ADR에 추천 적용으로 정했다. 추천 적용은 소유자가 방향을 승인하고 세부를 맡긴 부분에서 제안해 적용한 값으로, 바꾸고 싶으면 언제든 바꾼다. ASVS 요구사항 요약을 ID마다 한 문장으로 맞춘 것(결정 30)은 소유자 결정(2026-10-22, 00-summary 질문 45-5 (가))을 실행한 것이다). 2026-10-26: 남은 문서를 읽은 3부(review R-101)의 추천 적용은 ADR-0088에 둔다.
- **관련**: ADR-0009, ADR-0038, ADR-0041, ADR-0046, ADR-0047, ADR-0051, ADR-0055, ADR-0056, ADR-0063, ADR-0066, ADR-0073, ADR-0079, ADR-0081, ADR-0082, ADR-0083, ADR-0084, ADR-0085, ADR-0086

## 맥락

- 3차 점검(2026-10-20, ADR-0073) 뒤 이틀 사이에 ADR-0074~0086이 반영되고, 기획·설계 문서 48개를 쉬운 말로 다듬었다(R-94). 3차 점검은 관점별 검색이라 못 본 곳(ASVS 구현 위치, 데이터 표 칸과 API 스키마, 화면 설계 d5 §5·§8·§9, 기능 문서 일부 절)이 남았다.
- 이번에는 맡은 문서를 처음부터 끝까지 읽는 점검 에이전트 13개와, 다듬기 전후 줄을 짝지어 부정·조건·비교 표지가 바뀐 조각 491개를 판정하는 에이전트, ASVS 요약을 원문(OWASP ASVS 5.0.0 공식 배포 파일) 기준으로 맞추는 에이전트를 돌렸다. 기계 대조(개수 숫자, ID 참조와 이름, 용어 사전의 쓰지 않을 말, ADR 상태 줄과 architecture §11, 상태 값·Redis 키·ASVS ID와 레벨, 추적표)는 상위 세션이 했다.
- 지적은 약 330건이었고, 대부분은 나중 결정을 따라가지 못한 옛 문장, 같은 규칙의 다른 서술, 계약 빈칸이었다. 아래는 정본만으로 정할 수 없어 고른 것이다.

## 결정

### 가. API·이벤트 계약

1. **정적 파일 404는 Problem 예외다**: ADR-0081 결정 12대로 셔플 결과 파일·묶음 결과 파일·좌석맵 파일의 404는 Problem 본문을 약속하지 않는다. openapi의 세 응답에서 Problem 참조를 빼고, guidelines §2·§12의 개수 문장을 고쳤다.
2. **조건부 필수 값이 빠지면 422다**: 형식이 틀리거나 코드 밖이면 400, 형식은 맞는데 조건부 필수 값이 빠졌거나 업무 규칙에 어긋나면 422로 맞췄다(guidelines §12). 정산서 이의(OTHER인데 설명 없음), 수기 조정(근거 메모 없음 등), 지급 묶음 확인 요청(포트원 잔액 없음), settlement J-T13을 고쳤다.
3. **짧은 확인 코드 조회는 없음과 만료를 같은 404로 답한다**: 스캐너 승인 확인 코드와 계정 연결·병합 제안처럼 짧아서 추측할 수 있는 코드는, 410으로 '있었지만 만료됨'을 알려 주지 않는다(guidelines §12 예외).
4. **개인정보가 든 기록은 다른 테넌트에 404다**: 예매자 명단 다운로드 이력은 다른 테넌트 회차에 403이 아니라 404로 답한다.
5. **정산서의 회차 필드는 `eventId`다**: 저장 칸이 `event_id`가 된 뒤(ADR-0086) REST 정산서·`trade.settlements` 사건·Avro 초안의 `performanceId`를 `eventId`로 맞췄다. 첫 스키마 등록 전 초안이라 지금 바꾼다.
6. **승인 대기 저장 값은 `PENDING_APPROVAL` 하나다**: 지급 묶음만 `APPROVAL_PENDING`으로 쓰던 것을 승인 업무·운영 명령·회차 취소 요청과 같게 맞췄다.
7. **판매자 정보 변경 요청의 상태 값은 openapi 값이다**: `IN_REVIEW`·`APPLIED`·`REJECTED`(파트너 화면 계약이 먼저 쓰던 값)로 data.md를 맞췄다.
8. **판매 승인 '변경 취소' 작업을 둔다**: planning/03 §2.14의 Submitted·Rejected → Approved 전이에 맞는 API가 없어 `DELETE /v1/partner/events/{eventId}/sale-review`(파트너 관리자만)를 더했다. REST 작업은 182개가 됐다.
9. **접속기록 점검 목록은 커서로 나눈다**: 자동 탐지 이상 건 수가 정해지지 않으므로 `cursor`·`limit`을 더했다.
10. **결제 승인 재시도는 payment-svc가 한다**: 결제사 어댑터·채널 호출 상한·재시도 큐가 payment-svc에 있으므로 `IN_PROGRESS` 재시도는 payment-svc가 같은 멱등키로 하고 주문 Saga는 결과를 기다린다. 승인 요청 직전 표시 `CONFIRM_SENT`는 밖으로 내보내는 사건이 아니라 결제 상태 전이 기록(`payment_event`)에 남긴다.
11. **내부 gRPC 초안의 값은 정본 이름을 따른다**: 게시물 조치는 REST와 같은 `NO_ACTION`·`TEMP_BLOCK`·`BLOCK`·`RELEASE`에 위반 종류·끝 시각 칸을 더했고, 봇 판정은 사건과 같은 `CHALLENGE`, 회차 취소 귀책은 `ORGANIZER`다. 초안에 없던 호출 셋(일괄 환불 수동 일시정지, 배상금 송금, 정산 계좌 변경 뒤 등록 갱신)은 proto README §4에 적었다.
12. **판매 요약 등급별 표는 판매·환불·순 판매·매출이다**: openapi `byTier`에 등급별 환불 매수를 더하고 화면 문서 둘을 같은 열로 맞췄다.

### 나. 데이터와 보존

13. **`scan_event` 5년 보존은 입장 기록 마감부터 센다**: 파티션 달이 아니라 그 파티션 회차들의 입장 기록 마감 가운데 가장 늦은 때부터 세고, 티켓 파티션은 그 범위를 가리키는 `scan_event` 파티션을 지운 뒤에 뗀다.
14. **`gate_flag_scan`은 `ticket_id` 범위로 나눈다**: ADR-0086 결정 4 ①(자식 표는 부모와 같은 범위)에 맞췄다.
15. **법정 통보는 ops, 그 조치 기록은 core에 둔다**: `takedown_notice`는 ops 논리 DB, 후기를 가리는 `takedown_action`은 core 후기 모듈이고, 둘 사이에는 외래 키를 두지 않는다.
16. **명단 다운로드 기록은 최소 2년 이상 보존한다**: 보존 기간 정본(data-classification '관리자 시스템 접속기록')대로 '영구'와 '2년'을 '최소 2년 이상'으로 맞췄다.
17. **흡수 계정과 병합 감사 이력은 대표 계정이 탈퇴할 때까지 보존한다**: '영구 보존'은 목적을 이루면 파기한다는 원칙(개인정보 보호법 §21)과 data-classification에 맞지 않아 고쳤다.
18. **탈퇴 계정의 1인 1순번 중복 확인 키는 5일 안에 지운다**: 법정 파기 기한(docs/data.md §3, ADR-0056)을 앞세운다. 그 뒤에는 같은 공연에 다시 줄을 설 수 있다(남는 한계). 탈퇴하면 쓰지 않은 티켓은 모두 취소·환급되므로 한 사람이 표를 두 몫 갖지는 않는다.

### 다. 규칙·상태·화면

19. **관리 계정 세션이 2개를 넘으면 가장 오래 쓰지 않은 세션을 끝낸다**: 팬과 같은 방식이고 보안 알림을 보낸다(POL-019). 강제 종료 사유 `DEVICE_LIMIT`의 설명도 넓혔다.
20. **구매 세션 시작·종료 사건은 세션 Lua 뒤에 따로 보낸다**: 세션 키와 Stream 키는 Redis 해시 슬롯이 달라 한 Lua로 묶을 수 없다(data.md 키 설계를 유지). 사건이 빠지면 입장 자리 5분 회수와 최대 체류 정리가 덮는다.
21. **좌석 스냅샷의 첫 요청은 헤지하지 않는다**: 입장 토큰을 처음 써서 구매 세션을 만드는 쓰기라서다. 구매 세션이 열린 뒤의 재요청만 헤지한다(ADR-0009 상태 줄).
22. **`/verify/return`은 요청마다 처리하는 서버 처리기다**: 본인확인기관이 결과를 POST 본문으로 보내므로 CDN 정적 셸로는 받을 수 없다(identity §5). 응답은 `no-store`이고 결과 값은 저장·로그하지 않는다.
23. **좌석맵 가져오기 파일은 서버가 해석한다**: 계약(`seatmap-imports`)과 ASVS 판정(1.3.4·1.5.1)을 따르고, 에디터 Worker는 서버가 돌려준 도형·좌표만 그린다.
24. **판매 승인 뒤 휠체어석을 바꾸면 다시 승인 대기다**: 좌석맵 변경은 무엇이든 다시 승인 대기라는 정본(data.md §2, openapi 좌석맵, ADR-0063)을 따른다.
25. **티켓은 입장 키가 없으면 Issued다**: 돌려주기와 양도 수락 뒤에는 키가 폐기되므로 Issued로 돌아가고, 새 보유자가 '입장용으로 등록'을 누르면 Active가 된다.
26. **티켓이 무효가 되면 걸린 양도 요청은 Withdrawn으로 끝난다**(가상계좌 입금 오류 무효).
27. **대기실 탭 사이 메시지는 형식을 검사해 받는다**: BroadcastChannel 메시지를 Zod로 검사하므로 ASVS 3.5.5를 '해당 없음'에서 '적용'으로 바꿨다.
28. **브라우저 지표의 시각은 수집 게이트웨이가 받은 때다**: 지표 묶음에는 브라우저 시각을 싣지 않는다(frontend §5.16). 화면의 시계 보정은 표시와 타이머에 쓴다.
29. **세부 값 몇 가지**: 게시하는 프론트엔드 패키지는 devops §3.2의 다섯(ds·telemetry·validation·api-client·console-contract), 지연 히스토그램 칸에 0.8초·1.8초(NFR-012 FCP·TTFB 기준값), 보안 사고 통지 기록은 본문이 아닌 내용 요약과 의무 종류 `NOT_LEAKED_NOTICE`(미유출 확인 통지)를 둔다.

### 라. ASVS

30. **ASVS 요구사항 요약은 ID마다 한 문장이다**: 추적 표 13개에서 같은 ID인데 문장이 다르던 196개를 ASVS 5.0.0 원문의 요소를 빠짐없이 담은 한 문장으로 맞췄다(기존 문장을 고른 것 118개, 원문에 맞춰 고쳐 쓴 것 76개, 바뀐 칸 707개). 용어 사전이 쓰지 않는 '소비자'는 '호출자'로 썼다. doc-check에 `asvs` 검사(같은 ID의 요약이 다르면 오류)를 더했다.

### 마. 2부(남은 문서 통독, 2026-10-23) 추가 결정

31. **결제 송신 NAT는 AZ마다 하나다**: 결제사 방화벽에 등록하는 고정 IP를 셋으로 두어 결제 송신이 한 AZ에 묶이지 않게 한다(infra §9를 인수 문서의 배치 규칙에 맞춤).
32. **ops-svc의 분석 DB 사용자는 둘이다**: 골드 지표 뷰를 읽는 `an_ops_reader`와 실시간 표를 읽는 `an_rt_reader`다(ADR-0086·docs/streaming.md §4.3의 사용자 분리).
33. **모든 저장소 유형에 보안 검사(`security-scan`)를 둔다**: devops §3.1의 '전체'에 맞춰 §3.2 유형별 필수 검사 표에 더했다. 변경 동결 달력 같은 플랫폼 작업은 네임스페이스 `platform`에 둔다.
34. **보안 문서의 빈 주체를 채운다**: 사람 확인 비밀 키는 관리 계정 로그인 때 identity-svc도 쓴다. 위험 명령 재인증 토큰은 받는 서비스(ops-svc 등)가 공개키로 검증한다. 가상계좌 입금 확인 비밀의 해시는 입금 확정뿐 아니라 입금 기한 만료 때도 지운다. 회원 코드와 저장된 예매자 정보는 `account` 칸으로 둔다. 브라우저 저장물을 처리방침에 고지하는 방식은 기존 '확인 필요' 항목(최초 방문 쿠키)에 묶는다.
35. **화면 문구와 컴포넌트**: 발권 실패 자동 취소는 '결제를 자동으로 취소(환불)했습니다'로 안내하고 요금이 청구되지 않는다고 쓰지 않는다. 사용자에게 묻는 확인 질문('~할까요?')은 화면 문구 문체의 예외로 둔다. 콘솔의 휴대폰 본문은 1열이다. 대기 취소와 순번 안내는 모양은 글자 링크지만 요소는 버튼이다.
36. **관제 실시간 표의 신선도는 ops-svc가 읽는 때까지 잰다**(ADR-0071 결정 5): 화면 푸시·그리기 약 0.3초는 지연 예산에만 넣고, planning/02 NFR-009 측정 칸도 맞췄다.

## 검토한 대안

- 결정 1: 정적 파일 404도 Problem 본문을 내게(CloudFront 사용자 정의 오류 응답) 할 수 있었지만, ADR-0081이 일부러 예외로 둔 결정과 부딪치고 배포 설정이 늘어 계약 쪽을 고쳤다.
- 결정 18: 판매 종료까지 키를 남기면 탈퇴 뒤 재가입 부정은 더 막지만, 보관할 법적 근거(목적·기간)가 없어 택하지 않았다.
- 결정 20: 구매 세션 키를 회차 해시 태그 아래로 옮겨 한 Lua로 묶을 수 있지만, 키 설계 세 문서를 바꾸고 회차 샤드에 쓰기가 더 몰려 택하지 않았다.
- 결정 22: 정적 셸을 지키려면 기관이 GET 쿼리로 결과를 넘겨야 하는데, 기관 연동 방식(POST 본문)과 맞지 않는다.
- 결정 24: 휠체어석 같은 좌석 속성은 재승인에서 빼는 안도 있었지만, 그러려면 planning/03 §2.14·data.md·openapi·seat-hold를 함께 바꾸는 정책 결정이 필요해 정본을 따랐다.
