# ADR-0161: 로비 참가 버튼을 기기마다 0~60초 사이에 열고, 방금 놓은 좌석은 30초 동안 다시 잡지 못하며, 예매 제한은 입장 확정과 주문 생성에서 막고, 좌석맵 해석은 따로 뗀 작업이 한다(소유자 결정, 2026-10-30)

- **상태**: 채택 (2026-10-30. 소유자가 review/open-items.md 66·67·75번과 70번 ②의 추천을 "A B C 는 추천대로 해주시고요"라고 정했다. 방향은 소유자 결정이다. 열림 시각 계산식, 재홀드 단위(계정), 상태를 퍼뜨리는 길, 작업의 크기 상한은 추천 적용이다.)
- **관련**: ADR-0058(셔플 결과 받기의 기기별 고정 지연), ADR-0080·중간-068(이미지 처리 작업 `image-worker`), ADR-0151, ADR-0155(로비 열림 푸시), ADR-0159(좌석 빈틈), POL-004(로비 안에서는 들어온 때와 순번이 무관), [docs/features/queue-admission.md](../features/queue-admission.md) §2·§6, [docs/features/seat-hold.md](../features/seat-hold.md) §3·§5·§10, [docs/features/payment.md](../features/payment.md) §2, [docs/api/proto/README.md](../api/proto/README.md)

## 맥락

- 로비 참가가 로비가 열린 10분 동안 고르게 온다고 가정했지만, 그렇게 퍼뜨리는 장치가 없었다. 공연 상세를 열어 둔 채 기다리던 사람이 로비가 여는 순간 함께 누를 수 있다(ADR-0155에서 찾음). 위험 표의 등급은 높음이었다.
- 홀드를 풀자마자 다시 잡으면 유지 시간이 새로 시작해, 한 사람이 좌석을 구매 세션의 최대 체류 45분까지 붙잡을 수 있었다(ADR-0159에서 찾음).
- 운영자가 계정의 예매를 제한해도 어디서 막는지 정본에 없었다.
- 좌석맵 가져오기 파일(SVG)의 해석을 core-svc가 직접 해서, 해석기의 결함이 DB 자격 증명을 가진 프로세스 안에서 터질 수 있었다.

## 결정

1. **로비 참가 버튼은 기기마다 정해진 시각에 연다(소유자 결정, 66번)**
   - 시각은 로비 개방 시각에 `u32be(SHA-256("PEAKET-lobby-open-v1" ‖ 회차 ID ‖ deviceId)[0..4]) mod 60000` ms를 더한 것이다(추천 적용). 기기마다 고정이라 새로고침해도 빨라지지 않는다.
   - 화면에는 로비 안에서는 언제 들어와도 순번이 같다고 보인다(POL-004).
   - 버튼이 열리기 전에 API로 바로 보낸 참가는 막지 않고 센다(`lobby_join_before_open_total`). 일찍 와도 얻는 것이 없고, 열림 시각이 브라우저가 만든 기기 ID로 정해져 서버가 막아도 쉽게 피하며, 시계가 어긋난 정상 기기가 거절당하는 새 오류가 생기기 때문이다. 첫 1분 참가의 5% [가정]를 넘으면 다시 본다.
   - 로비 열림 푸시(ADR-0155 결정 1 ③)는 버튼이 퍼지는 60초가 끝난 뒤부터 보낸다. 창 끝은 오픈 3분 전을 넘지 않는다.
   - 효과는 Q-T57 ②(첫 1분 30% 몰림)로 잰다. 위험 표의 '로비 개방 순간 몰림'은 높음에서 중간으로 다시 매겼다.
2. **방금 놓은 좌석은 30초 [가정] 동안 다시 잡지 못한다(소유자 결정, 67번)**
   - 단위는 계정이다(`s:{event:E}:rel:{account}`, 추천 적용). 소유자 결정의 표현은 '같은 구매 세션'이었다. 하지만 세션을 끝내고 같은 대기표로 다시 입장하면 새 세션이 되어 세션 단위로는 피할 수 있다. 1인 매수 한도 키와 같은 단위이기도 하다.
   - 해제·만료·자동 배정 반납을 모두 '놓은 것'으로 센다.
   - 응답은 409 `seat-recently-released`다. 다른 사람이 잡은 좌석이 섞이면 기존 경합 409를 먼저 답한다. 자동 배정은 그 좌석을 같은 계정에게만 건너뛴다.
   - 위험 표의 '홀드를 풀고 다시 잡아 붙잡기'는 중간에서 낮음이 되었다.
3. **예매 제한은 입장 확정에서 queue-svc가, 주문 생성에서 purchase-svc가 막는다(소유자 결정, 75번)**
   - 제한 상태는 ops-svc가 gRPC `SetBookingRestriction`(판 번호 포함)으로 두 서비스에 보낸다(초안, ADR-0148 표시). 두 서비스는 각자 Redis에 사본을 둔다(대기열 `q:rst:{account}`, 좌석 `s:rst:{account}`).
   - ops-svc 작업 워커가 실패한 호출을 다시 보내고, 10분 [가정]마다 살아 있는 제한을 다시 보낸다. 승인 업무의 '제한 반영'(T14)은 두 서비스가 모두 반영해야 끝난다.
   - 주문 생성에서 막으면 그 구매 세션의 홀드를 풀되 세션은 끝내지 않는다. 남은 시간 동안 홀드를 다시 잡을 수 있는 것은 남는 한계다.
4. **좌석맵 해석은 따로 뗀 작업 `seatmap-worker`가 한다(소유자 결정, 70번 ②)**
   - 파일을 gRPC 본문으로 받고 해석 결과를 응답으로 돌려준다(`SeatmapImportService.ParseSeatmapImport`, 새 seatmap.proto). 저장소를 거치지 않아 원본을 저장하지 않는 규칙(ADR-0159 결정 5)과 맞는다.
   - 자격 증명, AWS 권한, 나가는 통신이 모두 없다. 그래서 image-worker보다 권한이 좁다.
   - 상한은 요청 12MiB, 응답 8MiB, 기한 10초, 메모리 512MiB다(모두 [가정]). gRPC Node 라이브러리의 기본 받기 상한은 4MiB라 받는 쪽 설정을 올린다(2026-10-30 원문 확인).
   - core-svc는 결과를 스키마로 다시 검사한다.

5. **함께 정한 것(2026-10-30 후속 정리, 추천 적용)**
   - 팬이 자기 예매 제한과 소명 기한을 보는 경로는 `GET /v1/booking-restrictions/me`다. gw-fan → core-svc support가 받고, ops-svc가 `SetBookingRestrictionView`로 화면용 사본(`sup:rst:{account}`)을 보낸다. 이 사본은 집행에 쓰지 않아 '제한 반영'(T14)을 기다리게 하지 않는다. 대기열·좌석 사본을 읽게 하면 공연 상세를 여는 모든 팬의 조회가 온세일의 가장 바쁜 저장소에 닿는다.
   - '방금 놓은 좌석'은 새 색 토큰 없이 `seat.available` 색의 테두리만 그린다(design/d2 CMP-021, tokens.json 무늬 `recently-released`). 30초짜리 화면 상태에 새 색을 두면 두 테마의 대비 검증 부담이 크다.
   - 자동 배정 Lua는 찾은 좌석의 홀드 Hash 하나만 같은 해시 태그로 스크립트 안에서 이름을 만든다(docs/data.md §3 KEYS 규칙의 예외). 슬롯을 옮기는 동안의 실패 모양은 [확인 필요]다.
   - 좌석맵 가져오기는 무시한 SVG 요소를 경고 `SVG_IGNORED`로 알리고, 413·422·503을 답한다.

## 검토한 대안

- **66번: 서버가 열리기 전 참가를 425·429로 거절하기**: 기기 ID로 정한 시각은 쉽게 피하고, 시계가 어긋난 정상 기기만 막힌다. 기각.
- **66번: 매번 새로 뽑는 무작위 지연**: 새로고침으로 빨리 열리는 기기를 찾을 수 있다. 기각.
- **67번: 구매 세션 단위**: 세션을 다시 시작하면 피한다. 기각.
- **67번: 좌석별 누적 홀드 시간 상한**: 좌석마다 누적 시간을 세는 키와 정리가 더 든다. 기각.
- **75번: Kafka 사건으로 퍼뜨리기**: 승인 업무가 '반영됨'을 알 수 없다. 기각.
- **75번: 토큰 클레임으로 싣기**: 액세스 토큰 수명(15분)만큼 늦고, 구매 권한 클레임의 뜻이 바뀐다. 기각.
- **75번: 두 서비스가 ops-svc에 물어보기**: ops-svc는 업무 gRPC를 받지 않는다. 기각.
- **70번 ②: image-worker처럼 격리 버킷을 거치기**: 원본을 저장하지 않는 규칙과 동기 응답에 맞지 않고, 버킷 권한이 생긴다. 기각.

## 결과와 트레이드오프

- 로비 개방 첫 1분의 몰림은 60초로 퍼진다. 그 평균이 진입 용량 안인지는 Q-T57 ② 전에는 모른다.
- 다시 잡기를 막는 30초 동안, 같은 계정은 놓은 좌석을 마음을 바꿔도 다시 잡지 못한다.
- 예매 제한은 ops-svc가 두 서비스에 보내는 사이 잠깐 어긋날 수 있다. 다시 보내기와 판 번호로 좁힌다.

## 되돌릴 조건

- 버튼이 열리기 전 API 참가가 첫 1분 참가의 5%를 넘으면 서버 쪽 처리를 다시 본다.
- Q-T57 ②가 진입 용량을 넘으면 퍼뜨리는 창을 넓히거나 엣지에서 고르게 받는 안을 본다.
- 좌석맵 파일이 상한을 자주 넘으면 상한이나 해석 방식을 다시 잰다.
