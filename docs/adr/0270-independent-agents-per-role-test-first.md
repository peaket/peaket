# ADR-0270: 계획·시험·구현·리뷰·검증을 서로 다른 에이전트가 맡고, 시험을 먼저 쓴다(2026-11-16)

- **상태**: 채택(2026-11-16, 소유자 지시 "작업플랜, 구현, 테스트, 리뷰 이 4가지 틀의 작업은 독립적인 에이전트가 수행해야 합니다"와 결정 "추천대로 고쳐 줘"). [ADR-0256](0256-feature-batches-completion-ledger-risk-grades.md) 결정 4(시험은 '먼저 쓰기'보다 '실패를 봤는가')를 아래 결정 3으로 바꾸고, 결정 5의 ③(구현과 시험)·⑤(리뷰)와 결정 9 '생각 강도 나누기'의 모델 문장을 아래 결정 1·2·4·6으로 바꾼다. [ADR-0267](0267-wave-delivery-group-batches-expensive-gates-at-end.md)(웨이브 끝에 비싼 검사·푸시)은 그대로이고, 결정 4의 묶음마다 짧은 대조 리뷰를 더한다. ADR-0256의 장부·등급·지시서 규칙(결정 1~3·6~10)은 그대로다. 보탬(같은 날, 감독 결정): 결정 5의 꼬리말 역할 값에 `review`(리뷰 담당이 계획 파일 '리뷰' 절을 커밋할 때)를 더하고, 차례는 계획 → 시험 → 구현 → 리뷰 → 리뷰 반영 → 검증 → 기록이다(docs/architecture.md §8.6의 4 '역할 나누기'). 보탬(2026-11-16, 추천 적용, 계획 [W7-L1-roles-check](../review/plans/W7-L1-roles-check.md)): 결정 5의 검사는 꼬리말 `Batch`로 묶음을 가르고, 리뷰 반영은 `Fix-By: test|impl`, 문서만 고치는 묶음의 작성 담당은 `Role: doc`을 단다. 코드를 쓰지 않는 역할의 커밋은 결정 8의 코드 경로를 바꾸지 않고, 세션 하나는 한 역할만 맡는다. 세부는 docs/architecture.md §8.6의 4 '역할 나누기'.
- **관련**: [docs/architecture.md](../architecture.md) §8.6, [docs/PROGRESS.md](../PROGRESS.md) 턴 규칙, [docs/review/audit/wave6.md](../review/audit/wave6.md), [docs/review/plans/](../review/plans/)
- **관련 ID**: 없음(진행 절차만 바꾼다)

## 맥락

- ADR-0256 결정 5는 묶음 안의 일을 계획 담당, 구현 담당(구현과 시험을 함께 씀), 관점 넷 리뷰, 틀린 구현 검사 담당으로 나눴다. 시험과 구현은 처음부터 한 담당이었다. 결정 4는 2026-10-31의 'TDD 필수'(시험을 먼저 써서 실패를 본 뒤 구현하는 방식)를 풀어, 시험을 먼저 쓰는 것은 돈·좌석·순번의 불변식과 버그 재현만 남겼다.
- 2026-11-11~11-15 웨이브 1~5는 OpenCode 앱의 감독 세션이 갈래마다 에이전트(일을 맡아 하는 AI 작업자) 하나를 띄워 돌렸다. 2026-11-16 작업 기록을 보니 실제로는 갈래 에이전트 하나가 계획 파일, 구현, 시험, '관점 넷 리뷰', 틀린 구현 검사(일부러 결함을 넣어 시험이 잡는지 보는 변이 검사)를 모두 했다.
  - 갈래 세션 12개가 하위 에이전트를 띄운 횟수는 0이었다.
  - 감독이 보낸 하위 작업 지시 315번 가운데 265번은 이미 있던 세션에 이어 보냈고, 대부분이 갈래 세션이었다. 리뷰 지시 86번과 변이 검사 지시 60번도 대부분 그 갈래 세션으로 갔다. 새 세션은 갈래 담당을 처음 만들 때와 웨이브 6 감사 때만 띄웠다.
  - 손댄 묶음 58개 가운데 22개는 계획 파일(`docs/review/plans/<묶음>.md`)이 없다. 그중에는 A등급(돈·좌석·순번) 묶음 BAT-415·420·425·430·465가 들어 있다.
  - 감독·갈래·감사·수정·시험·검증 담당이 모두 같은 모델이었다.
- 그 묶음들의 커밋은 자기 리뷰 결과를 "높음 0~1"로 적었다. 그런데 웨이브 6에서 구현에 참여하지 않은 에이전트 17개가 같은 코드를 감사하자 높음 결함이 23건 더 나왔다([wave6.md](../review/audit/wave6.md)). 웨이브 6은 감사·수정·시험 작성·검증 담당을 나눴고, 이 방식에서는 결함이 걸러졌다.
- 2026-11-16 소유자가 물었다: 계획·구현·시험·리뷰 넷은 독립된 에이전트가 해야 하는데 지금 그렇게 되어 있는가, TDD와 코드 리뷰를 하는 절차(superpowers와 비슷한)를 돌리고 있는가. 답은 '아니다'였고, 소유자가 추천안대로 바꾸라고 했다.

## 결정

1. **역할은 다섯이고, 역할마다 다른 에이전트가 맡는다.** 한 에이전트가 두 역할을 맡지 않는다. 감독은 지휘·합치기·기록만 하고 코드와 시험을 쓰지 않는다.

   | 역할 | 하는 일 | 받는 것 | 하지 않는 것 |
   | --- | --- | --- | --- |
   | 계획 | 장부 범위와 지시서로 작업 목록을 만든다: 손댈 파일, 공개 인터페이스(밖에서 부르는 함수·API·이벤트의 모양), 판정 항목마다 쓸 시험, 차례, 정본 빈칸. 정본 빈칸은 구현 전에 정본·ADR에 쓴다 | 지시서, 정본의 줄 범위, 기존 코드 | 시험·제품 코드를 쓰지 않는다 |
   | 시험 | 계획의 시험 목록대로 시험을 먼저 쓰고, 공개 인터페이스의 빈 뼈대(동작 없이 '아직 없음'을 던지는 함수)만 더해 실패를 본다. 리뷰·검증이 찾은 결함의 재현 시험도 쓴다 | 지시서, 계획, 정본, 기존 공개 인터페이스와 기존 시험 | 제품 코드의 동작을 쓰지 않는다. 고친 코드를 보고 시험을 맞추지 않는다 |
   | 구현 | 시험을 통과시키는 제품 코드를 쓴다 | 계획, 시험, 지시서 | 시험 담당이 쓴 시험 파일을 고치지 않는다. 시험이 정본과 어긋나 보이면 계획 파일의 '시험 이의' 절에 적고 그 항목을 멈춘다 |
   | 리뷰 | 바뀐 부분(`git diff`)을 계획·정본과 맞춰 본다(결정 4) | 바뀐 부분, 지시서, 계획 | 구현 담당의 설명이나 요약을 받지 않는다. 코드를 고치지 않는다 |
   | 검증 | 등급대로 틀린 구현을 넣어 시험이 실패하는지 보고, 판정 기준과 시험 단언을 맞춰 본다(ADR-0256 결정 3) | 지시서, 계획, 바뀐 부분 | 살아남은 결함을 잡는 시험은 쓰지 않는다(시험 담당에게 넘긴다) |

   - 역할마다 새 세션(앞선 대화를 모르는 새 맥락)으로 띄운다. 같은 갈래·같은 웨이브의 같은 역할이면 세션을 이어 써도 된다. 다른 역할의 세션에 일을 보내지 않는다. 리뷰·검증 담당은 웨이브마다 새로 띄운다.
   - 감독은 담당끼리 파일(지시서·계획 파일·바뀐 부분·발견 목록)로만 넘긴다. 자기가 요약한 코드 설명을 넘기지 않는다.
2. **묶음 안 차례**: 계획 → 정본 빈칸 → 시험(실패 확인) → 구현(통과) → 대조 리뷰 → 지적 반영 → 게이트·기록. 웨이브 끝에는 ADR-0267대로 통합 시험·검증(변이)·관점 넷 리뷰·측정·브라우저 확인·CI를 한 번 돈다.
   - 리뷰·검증이 찾은 결함은 시험 담당이 재현 시험을 먼저 써서 실패를 보고, 구현 담당이 고치고, 리뷰 담당이 고친 곳만 다시 본다.
   - 한 갈래 안에서 구현 담당이 묶음 N을 하는 동안 계획·시험 담당은 묶음 N+1을 준비해도 된다(손대는 파일이 겹치지 않을 때). 무거운 측정은 지금처럼 한 번에 한 갈래만 한다(ADR-0267 결정 6).
3. **행동 시험은 시험 담당이 구현 전에 먼저 쓰고 실패를 본다(ADR-0256 결정 4를 바꾼다).** 업무 규칙·계산·상태 전이·권한·API·이벤트·화면 동작의 시험이 모두 대상이다. 2026-10-31의 'TDD 필수'를 역할 나누기와 함께 되살린다.
   - 실패 확인은 시험 담당이 계획 파일의 '실패 확인' 절에 적는다: 돌린 명령, 실패한 시험 수, 실패 까닭(뼈대가 '아직 없음'을 던져서인지, 단언이 틀려서인지). 시험 파일을 고르지 못해 실행조차 안 되는 실패는 실패로 세지 않는다.
   - 먼저 쓰지 않아도 되는 것: 시각 비교의 기준 그림, 측정, 문서 점검, 빈 시험만 도는 뼈대. 이것들도 검증 담당이 틀린 구현으로 한 번은 실패를 본다.
   - 이미 있는 동작을 묶는 시험이 처음부터 통과하면 '처음부터 통과(이미 있는 동작)'라고 적고, 검증 담당의 틀린 구현으로 실패를 본다. 실패를 한 번도 본 적 없는 시험은 지금처럼 완료 근거로 세지 않는다.
4. **리뷰는 두 겹이다.** 묶음마다 리뷰 담당 하나가 짧은 대조 리뷰를 한다: 계획의 항목이 모두 구현됐는가, 정본과 어긋나는가, 구현 커밋이 시험 파일을 건드렸는가, '자주 놓친 결함'에 걸리는가. 웨이브 끝에는 ADR-0267대로 관점 넷(정확성, 동시 실행·장애, 보안, 화면과 서버 잇기) 리뷰를 함께 돌린다. 높음·보안·통과 기준 지적은 그 웨이브에서 고치고, 나머지는 구간 끝 정리 목록에 적는다(ADR-0256 결정 5 그대로).
5. **역할을 지켰는지 기계로 본다.** 규칙만 적으면 웨이브 1~5처럼 소리 없이 한 에이전트로 뭉친다.
   - 묶음 가지의 커밋을 역할별로 나눈다: 계획(정본 빈칸 포함) → 시험 → 구현 → 리뷰 반영(시험·구현이 각각 커밋) → 기록. 커밋 본문 끝에 커밋 꼬리말(커밋 메시지 끝에 붙는 `키: 값` 줄) `Role: plan|test|impl|review-fix|verify|record`와 `Agent-Session: <세션 ID>`를 단다. 모델을 알면 `Agent-Model: <모델>`도 단다.
   - 묶음은 지금처럼 최신 `origin/develop` 위로 올린 뒤 앞으로 감기(`merge --ff-only`)로 합치므로 역할별 커밋이 그대로 남는다. 묶음을 커밋 하나로 뭉치지 않는다.
   - 합치기 전 검사 `tools/ci/roles-check.mjs`를 웨이브 7의 첫 일로 이 ADR의 방식(역할 다섯)대로 만든다. 검사 항목: 역할 꼬리말이 빠진 커밋이 없다, 차례가 계획 → 시험 → 구현이다, 구현·리뷰 반영(구현) 커밋이 시험 파일(`*.test.*`·`*.spec.*`·`test/`·`test-int/`·`__tests__/`·`e2e/`)을 바꾸지 않는다, 계획·시험·구현·리뷰·검증의 `Agent-Session`이 서로 다르다, 계획 파일에 '실패 확인'·'리뷰'·'검증' 절과 담당 표가 있다. 검사가 실패하면 그 묶음을 합치지 않는다.
   - 검사 스크립트가 생기기 전에는 감독이 같은 항목을 손으로 보고 웨이브 보고서에 적는다.
6. **리뷰·검증 담당은 쓸 수 있으면 구현 담당과 다른 모델을 쓴다(추천 적용 2026-11-16).** 같은 모델은 같은 곳을 놓치기 쉽다. 다른 모델을 쓸 수 없으면 같은 모델의 새 세션으로 하고, 그 사실을 담당 표에 적는다. 구현 담당이 쓰는 기본 모델은 이 ADR이 정하지 않는다(docs/PROGRESS.md 미해결).
7. **기록**: 계획 파일 하나에 역할마다 자기 절을 쓴다(계획, 실패 확인, 시험 이의, 리뷰, 검증). 계획 파일 끝의 담당 표에 역할·세션 ID·모델·시작과 끝 시각을 적는다. 웨이브 보고서에는 묶음별 담당 표 요약과 결정 5 검사 결과를 적는다. 진행 로그 한 줄, 정합 점검 한 줄, 장부 다시 쓰기는 기록 커밋 하나에 넣는다(ADR-0256 결정 7 그대로).
8. **적용 범위**: 웨이브 7부터 코드(`apps/`·`services/`·`packages/`·`data/`·`infra/`·`tools/`·`.github/`)를 바꾸는 모든 묶음과 버그 수정에 쓴다. 문서만 고치는 묶음은 계획·작성·리뷰 세 역할로 하고, 시험 대신 문서 점검을 돌린다.

## 결과

- 시험이 구현을 따라 쓰이지 않고 정본과 계획을 따라 쓰인다. 구현 담당이 시험을 맞춰 고쳐 통과시키는 일이 막힌다.
- 리뷰가 구현 담당의 설명이 아니라 바뀐 부분과 정본을 본다. 자기 리뷰가 놓친 결함(웨이브 6의 높음 23건)이 묶음과 웨이브 안에서 걸러지기를 기대한다.
- 차례가 이어져 묶음 하나가 느려지고, 역할마다 지시서를 다시 읽어 토큰이 늘어난다 [가정]. 2026-11-04 비슷한 삼자 절차(구현 → 시험 작성 → 시험 검토)는 한 바퀴에 1시간 반을 넘었고, 2026-11-10 시범에서 강화 검증을 넣으면 토큰이 약 2배였다. 결정 2의 겹쳐 돌리기로 기다림을 줄인다.
- 묶음 가지에 커밋이 여러 개 남아 기록이 길어지지만, 역할마다 누가 무엇을 했는지 커밋으로 따라갈 수 있다.

## 되돌릴 조건

- 웨이브 7·8의 웨이브 끝 리뷰·검증이 찾은 높음 결함이 웨이브 6 감사 수준(구현 묶음 55개에 23건)에서 줄지 않으면, 역할마다 받는 것(결정 1 표)을 다시 본다.
- 묶음당 시간이 웨이브 1~5의 3배를 넘으면 소유자에게 알리고, B·C등급 묶음의 묶음마다 대조 리뷰를 웨이브 끝으로 미룰지 정한다.

## 확인

- 웨이브 7이 끝나면 묶음당 토큰·시간·결함 수와 결정 5 검사 결과를 여기에 적는다.
