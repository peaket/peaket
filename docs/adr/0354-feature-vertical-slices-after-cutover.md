# ADR-0354: 전환점 뒤에는 2~5일 수직 기능 단위로 만들고 기능마다 합친다(2026-11-22)

- **상태**: 채택(2026-11-22, 소유자 승인 "승인"). [ADR-0256](0256-feature-batches-completion-ledger-risk-grades.md) 결정 1의 작업 단위(같은 갈래·같은 구간의 이웃한 단계 2~6개를 한 묶음으로 묶기)와 [ADR-0270](0270-independent-agents-per-role-test-first.md) 결정 5의 합치기 단위(묶음마다 `develop`에 합치기)를 **전환점 뒤의 새 작업에 한해** 아래 결정 1~3으로 바꾼다. 역할 다섯(계획·시험·구현·리뷰·검증)과 역할별 커밋, `roles-check`, 완성 장부, 위험 등급, 5일 상한은 그대로다.
- **관련**: [docs/architecture.md](../architecture.md) §8.6, [docs/PROGRESS.md](../PROGRESS.md) 턴 규칙, [docs/BUILD_ORDER.md](../BUILD_ORDER.md), [docs/lanes/lane1.md](../lanes/lane1.md)~[lane5.md](../lanes/lane5.md), `tools/ci/brief.mjs`, `tools/ci/ledger.mjs`, `tools/ci/records.mjs`
- **관련 ID**: 없음(진행 절차만 바꾼다)

## 맥락

- 2026-11-22 기준 `docs/BUILD_ORDER.md`는 651줄·256KB이고, '기능 묶음' 표에 묶음 188개가 있다. 남은 일은 대부분 구간 3·4에 몰려 있다. 그런데 지금의 묶음은 **가로로 자른 조각**인 경우가 많다.
  - 서버만 하는 묶음과 화면만 하는 묶음이 따로 있다. 예: 현장 스태프 초대는 서버가 BAT-450B·450C에서 끝났고, 화면(GAT-230·240·360)은 아직 다른 묶음이다. 그래서 "현장 스태프 초대"라는 기능은 여러 주 동안 미완으로 남는다.
  - 같은 기능의 남은 몫이 여러 묶음에 흩어져 있다. 예: 정산은 LCH-100(정산서)·LCH-110(지급)·LCH-120(포트원 지급)·LCH-170(법정 고지)로 나뉘고, 코드가 일부 합쳐졌어도 단계 줄은 체크되지 않은 채 남아 있다.
  - 진행을 말할 때 "묶음 136개가 남았다"는 말은 할 수 있지만, "정산이 끝났는가"에는 바로 답하기 어렵다. 소유자는 기능 단위의 완료를 보고 싶어 한다.
- 2026-11-22 소유자 결정: **지금 진행 중인 작업까지는 그대로 끝내고, 그 뒤로는 기능 단위로 개발·시험·커밋한다.** 기능 하나를 2~5일에 끝내고, 기능마다 한 번 합치는 방식을 골랐다.
- 지금의 묶음 표와 도구는 그대로 쓸 수 있다. `brief.mjs`·`ledger.mjs`는 `묶음`·`장부 범위` 칸이 있는 표를 여러 개 훑어 ID로 행을 찾고, `records.mjs`는 단계 줄(`- [ ] ID …`)을 센다. 표를 하나 더 두고 ID만 새로 붙이면 도구를 고치지 않아도 된다.

## 결정

### 1. 전환점과 동결

- **전환점은 2026-11-22이다.** 전환점에서 이미 시작한 작업만 옛 규칙(묶음 단위)으로 끝낸다. "이미 시작한 작업"은 다음 둘 중 하나다.
  - 작업 폴더(`git worktree`)나 작업 가지·초안 PR이 있고, 그 가지에 아직 합치지 않은 커밋이 있는 묶음.
  - 갈래 파일(`docs/lanes/lane1.md`~`lane5.md`)의 '다음 할 일'에 "진행 중"·"시험 중"·"검증 중"으로 적힌 묶음.
- 전체 감독은 전환점 목록을 `docs/BUILD_ORDER.md`의 `## 전환점` 절에 한 번 적는다. 목록에 든 묶음만 옛 표의 순서대로 끝내고, **새 묶음은 옛 표에서 시작하지 않는다.**
- 옛 표는 삭제하지 않고 `## 전환 전 실행 기록(2026-11-22까지)`로 제목을 바꾼다. 지난 묶음 ID는 커밋·ADR·계획 파일이 가리키므로 기록으로 남긴다. 옛 표의 행 가운데 시작하지 않은 것은 실행하지 않으며, 새 기능 표가 같은 단계 ID를 다시 묶는다.
- 전환점 목록에 든 묶음이 끝나기 전이라도, 그 묶음이 닿지 않는 다른 갈래는 새 기능을 시작할 수 있다. 단, 전환점 목록의 묶음과 같은 파일·마이그레이션 번호를 건드리지 않는다.

### 2. 기능 하나의 정의

- **기능은 2~5일 [가정] 안에 끝나는 수직 조각이다.** 화면이 있으면 화면, API, DB, 시험, 브라우저 확인까지 한 기능에 든다. 화면과 서버를 다른 기능으로 나누지 않는다.
- 기능은 다음을 모두 만족할 때 `완료`다.
  1. 기능 표의 `완료 정의`에 적은 사용자·운영 동작이 실제 서버로 동작한다(가짜 API로 끝내지 않는다).
  2. 그 기능이 닿는 정본의 판정 항목을 시험이 검사한다. 시험 이름에 요구사항·시험 ID와 세부 번호를 단다.
  3. `node tools/ci/ledger.mjs --batch <기능 ID> --require`가 통과한다(빈칸·`ID만` 없음).
  4. 화면이 바뀌면 브라우저 확인을 한다. 사람·실기기 확인은 확인 목록으로 남긴다.
  5. 기능 가지의 역할 커밋이 `roles-check.mjs`를 통과한다.
- **5일을 넘을 것 같으면 기능을 둘로 나눈다.** 각각이 독립적으로 시험·합치기 가능한 수직 조각이어야 한다. 한 기능 안에 "나중에 할 반쪽"을 남기지 않는다.
- **부분 단계**는 기존 규칙을 그대로 쓴다. 한 WBS 단계의 일부만 끝냈으면 단계 줄에 '일부 구현(R-…): 끝낸 몫. 남은 것: …' 한 구절을 남기고, 단계 줄은 마지막 몫이 끝날 때 체크한다. 기능 표의 `상태`는 `완료`·`일부 완료`·`막힘`으로 구분하고, `일부 완료`면 남은 몫을 `비고`에 적는다.

### 3. 기능 표와 ID

- `docs/BUILD_ORDER.md`에 `## 기능 단위 계획(2026-11-22 전환)` 절을 더하고, 그 아래에 기능 표를 둔다. 표의 첫 칸 이름은 `묶음`, `장부 범위` 칸을 포함해 기존 도구가 그대로 읽게 한다.

  | 묶음 | 영역 | 등급 | 단계 | WBS 일 | 장부 범위 | 완료 정의 | 선행 | 상태 | 비고 |
  | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

- 기능 ID는 `F-<영역 번호>-<기능 번호>`로 쓴다(예: `F-05-2`). 영역 번호는 아래 결정 4의 표를 따른다. 기존 `BAT-` ID와 섞이지 않아 전환 전후를 구분할 수 있다.
- `단계` 칸에는 그 기능이 끝내는 WBS 단계 ID를 적는다. 단계 줄은 기존 `Phase 1~7` 절에 그대로 두고, 기능이 끝날 때 체크한다.
- `완료 정의`는 "누가 무엇을 하면 무엇이 보이고, 서버가 무엇을 보장하며, 어떤 시험·브라우저 확인으로 증명하는가"를 한 문장으로 적는다. 정본의 값은 옮겨 적지 않고 `docs/features/…`의 절과 시험 ID만 가리킨다.
- `상태`는 `대기`·`진행`·`완료`·`일부 완료`·`막힘` 가운데 하나다. 기능을 시작할 때 `진행`, 끝낼 때 `완료`, 막히면 `막힘`과 까닭을 적는다.
- 옛 표와 새 표는 같은 `묶음`·`장부 범위` 머리를 쓰므로 `brief.mjs --batch F-05-2`와 `ledger.mjs --batch F-05-2`가 그대로 동작한다. 도구를 먼저 고치지 않는다.

### 4. 기능 영역 아홉 개

기능 표는 아래 아홉 영역으로 묶는다. 영역은 읽기와 갈래 배치를 위한 것이고, 실행 단위는 그 아래 기능이다.

| 번호 | 영역 | 남은 단계(예) | 첫 기능의 예 |
| --- | --- | --- | --- |
| F-01 | 관측·경보 | OPS-010~140 | 관측 3신호 → 대시보드·Sentry → SLO·경보 → 인시던트·DORA |
| F-02 | 관제 명령·감사 | OPS-300~330 (OPS-260~290은 끝남) | 제어 gRPC·WAF 명령 → 동결 달력·접속기록 저장소 |
| F-03 | 관제 콘솔 | OPS-340~420 | 콘솔 호스트·원격 위젯 → 대시보드·명령/감사 화면 → 법정·공지·모바일 |
| F-04 | 분석·포렌식 | OPS-150~250, LCH-210~340 | 실시간 관제 표 → 분석 적재 → dbt·지표 → 사후 포렌식 |
| F-05 | 현장 입장 | GAT-020~060, GAT-135~220 | 월렛·QR → 양도 → 스캐너 오프라인 판정 → 현장 스태프 |
| F-06 | 고객·CS·법정 | GAT-250~330 | 알림 → CS 처리함 → 승인 업무·예외 환불 → 예매 제한·소명 |
| F-07 | 정산·커머스·파트너 | LCH-030~130 | 판매 승인 마감 → 정산서 → 지급 승인·실행 → 파트너 화면 |
| F-08 | 출시·측정 | LCH-200·340·350, MSR-010~080 | 프론트 성능 → 100만 외삽 → Game Day → 용량·비용 |
| F-09 | 기반·보안 | BAS-120·130, BOT-140·152·161, BAS-250 | 스테이징 Terraform → 운영 인프라 → DAST·관리 계정 → 봇 시뮬레이터 |

- 영역 경계는 2026-11-22의 남은 일을 기준으로 나눴다. 새 기능이 영역 둘에 걸치면 **끝나는 쪽 기능 하나에 넣고**, 다른 영역은 `선행`으로 가리킨다.
- 한 영역의 기능이 모두 끝나면 그 영역은 닫는다. 영역이 닫혔는지는 기능 표의 `상태`로 본다.

### 5. 전환 매핑(한 번만)

- 전환점 직후 전체 감독이 **남은 단계 줄을 하나씩 기능에 배정**한다. 모든 체크되지 않은 단계 줄은 정확히 한 기능에 속해야 한다. 어느 기능에도 속하지 않는 단계가 남으면 안 된다.
- 매핑 결과는 새 표의 `단계` 칸과 `## 전환 대조` 표(WBS 단계 → 기능 ID)에 함께 적는다. 대조 표는 매핑이 끝난 뒤 감사용으로만 둔다.
- 한 단계의 남은 몫이 5일을 넘으면 기능을 둘로 나누고, 각 기능이 그 단계의 어느 몫을 끝내는지 `비고`에 적는다. 단계 줄은 마지막 몫이 끝날 때 체크한다.
- 소유자 결정·클라우드 계정·외부 서비스가 없어 막힌 단계는 `막힘` 기능으로 두고 까닭과 풀리는 조건을 적는다. 매핑에서 조용히 빼지 않는다.
- 매핑은 코드를 쓰는 역할이 아니라 전체 감독이 하고, 첫 기능을 시작하기 전에 소유자가 한 번 본다.

### 6. 실행·합치기·갈래

- 갈래는 지금처럼 다섯이다. 갈래마다 **한 번에 기능 하나**를 맡는다. 영역은 갈래에 고정하지 않고, 웨이브마다 겹치는 파일을 줄이도록 배치한다(예: 갈래 1은 임계 경로·분석, 갈래 2는 콘솔·화면, 갈래 3은 현장·CS, 갈래 4는 관측·관제 명령, 갈래 5는 정산·커머스).
- 기능 가지는 `feature/<갈래>-<기능 ID>`다. 그 안에 계획·시험·구현·리뷰·검증 역할 커밋을 쌓는다(ADR-0270). 기능 하나를 커밋 하나로 뭉치지 않는다.
- **`develop`에는 기능이 끝날 때 한 번만 합친다.** 기능 도중의 중간 결과는 기능 가지에만 둔다. 합치기 전에 최신 `develop` 위로 올리고(rebase), 그 기능이 닿는 통합 시험과 `ledger --require`를 다시 본다. 합치기 잠금·마이그레이션 번호·웨이브 규칙은 그대로다.
- 기능이 막히면 그 가지는 합치지 않고 `막힘`으로 표시한다. 같은 갈래는 막힌 기능을 기다리지 않고 다음 기능을 시작할 수 있다. 단, 막힌 기능의 파일·마이그레이션 번호를 건드리지 않는다.
- 기능을 끝낼 때 기록 커밋 하나에 기능 표의 `상태`, 단계 줄 체크(전체가 끝난 경우), 장부 다시 쓰기, 진행 로그 한 줄을 넣는다. 기능 단위의 커밋 요약에는 `Feature: F-05-2` 꼬리말을 붙여 나중에 기능별로 찾을 수 있게 한다.

### 7. 측정과 기능의 관계

- 그 기능을 증명하는 측정(예: 스캐너 판정 지연, 정산 지급 성공률)은 그 기능의 `완료 정의`에 넣고 기능 안에서 한다.
- 여러 기능을 가로지르는 측정(100만 외삽, Game Day 전체, KPI 최종)은 `F-08 출시·측정` 영역의 독립 기능으로 둔다. 측정 창의 Docker 잠금·한 갈래만 측정 규칙은 그대로다.

### 8. 도구와 확인

- `brief.mjs`·`ledger.mjs`·`records.mjs`는 고치지 않아도 새 표를 읽는다. 새 표를 더한 뒤 `node tools/ci/ledger.mjs --batch F-01-1`과 `node tools/ci/brief.mjs --batch F-01-1`이 동작하는지 첫 기능에서 확인한다.
- 매핑이 끝나면 `tools/ci/feature-map.mjs --check`(가칭)를 더해 다음을 기계로 본다: 체크되지 않은 단계가 정확히 한 기능에 속한다, 모든 기능에 `완료 정의`와 `상태`가 있다, 기능 표의 단계 ID가 실제 단계 줄과 맞는다. 도구를 더하기 전에는 전체 감독이 손으로 대조하고 `## 전환 대조` 표에 결과를 적는다.
- `records.mjs --check`의 기록 크기 규칙은 그대로다. 기능 표는 간결하게 유지하고, 자세한 계획은 `docs/review/plans/<기능 ID>.md`에 쓴다.

### 9. 함께 고치는 문서

- 이 ADR, `docs/architecture.md` §8.6('기능 묶음' 절차의 작업 단위·합치기 문장), `docs/PROGRESS.md` 턴 규칙('묶음'을 '기능'으로 바꾸는 문장), `docs/lanes/lane1.md`~`lane5.md`의 '다음 할 일', `docs/BUILD_ORDER.md`(새 절·새 표·옛 표 제목·전환점).
- `docs/wbs/wbs.md`·`wbs.csv`는 고치지 않는다. WBS는 단계 내용·일수의 정본으로 남고, 기능 표가 그 단계 ID를 참조한다.

## 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 지금 묶음에 `기능` 이름만 붙이고 순서만 바꾼다 | 기각. 서버·화면이 따로 떨어진 가로 조각이 그대로 남아, 기능이 언제 끝나는지 보이지 않는다. |
| WBS Phase 3~7을 기능별 Phase로 다시 쪼갠다 | 기각. WBS ID·일수·선행 관계를 모두 다시 매겨야 하고, 끝난 단계의 기록·참조가 끊긴다. 전환 비용이 이득보다 크다. |
| 기능 영역 하나를 통째로(2~4주) 끝내고 합친다 | 기각. 가지가 오래 살아 충돌·병합 대기가 커지고, 소유자가 중간에 기능 완료를 볼 수 없다. |
| 기능 하나를 커밋 하나로 뭉친다 | 기각. 역할 다섯을 분리한 ADR-0270과 `roles-check`를 깨고, 리뷰·검증 기록을 잃는다. 역할 커밋은 기능 가지 안에 그대로 둔다. |

## 결과

- **좋은 점**: `develop`에 합쳐지는 단위가 "끝난 기능"이 된다. 기능별 진행(대기·진행·완료·막힘)을 한 표에서 볼 수 있고, 커밋·시험·계획 파일을 기능 ID로 찾을 수 있다. 서버만 끝나고 화면이 몇 주 뒤에 붙는 일이 줄어든다.
- **나쁜 점**: 기능 가지가 2~5일 살아 있어 지금(묶음마다 합치기)보다 충돌·병합 대기가 늘 수 있다. 같은 서비스(payment·core)를 여러 갈래가 만질 때 마이그레이션 번호·계약 생성물 충돌이 커진다. 전환 매핑에 한 번 큰 비용이 든다.
- **줄이는 방법**: 기능을 5일 이하로 짧게 유지하고, 기능 가지를 매일 `develop` 위로 올린다(rebase). 갈래마다 영역을 겹치지 않게 배치하고, 합치기 잠금·마이그레이션 번호 나누기 규칙을 그대로 지킨다. 기능이 막히면 가지를 오래 쥐지 않고 `막힘`으로 표시한 뒤 다음 기능으로 간다.
- **위험**: 기능 하나가 여러 영역에 걸치면 `완료 정의`가 흐려질 수 있다. 그때는 끝나는 쪽 기능 하나를 정하고 다른 영역은 `선행`으로만 가리킨다. 측정이 기능 안에 들어오면 측정 창의 Docker 잠금과 충돌할 수 있으므로, 측정이 필요한 기능은 웨이브 배치 때 측정 창과 겹치지 않게 놓는다.

## 되돌릴 조건

- 첫 기능 셋 가운데 둘 이상이 5일을 넘거나, 기능 가지의 병합 대기·충돌이 지금 묶음 방식의 두 배를 넘으면 기능을 더 잘게 나누거나 B·C등급은 묶음 단위 합치기로 되돌린다.
- 전환 매핑에서 체크되지 않은 단계의 5% 넘게 어느 기능에도 붙지 않으면 영역 경계를 다시 잡는다.
- 기능 단위 합치기 뒤 CI 실패·결함이 지금보다 늘면 첫 다섯 기능의 기록을 보고 소유자에게 다시 묻는다.
