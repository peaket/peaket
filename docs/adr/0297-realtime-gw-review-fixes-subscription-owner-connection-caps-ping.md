# ADR-0297: realtime-gw의 구독 상태는 구독기 하나가 들고 물러서며 맞추고, 연결 수에 상한을 두며, 클라이언트 Ping은 받지 않는다(2026-11-18)

- **상태**: 채택(추천 적용, 2026-11-18, BAT-052 리뷰 반영 계획). [ADR-0296](0296-realtime-gw-first-build-own-token-check-section-count-from-layout-file.md)을 보탠다. BAT-052 관점 리뷰의 높음 셋(SEC-01·CON-01·CON-02)과 정본 빈칸(SEC-02·SEC-03~05·CON-03·CON-04·COR-06)을 정한다.
- **관련**: [docs/features/seat-hold.md](../features/seat-hold.md) §7 'realtime-gw의 첫 구현', [docs/frontend.md](../frontend.md) §4.4.1, [docs/api/asyncapi.yaml](../api/asyncapi.yaml) `ws.seat-delta`, [docs/security/asvs/seat-hold.md](../security/asvs/seat-hold.md) 2.4.1·13.2.2·13.3.2, `docs/review/plans/BAT-052.md` '리뷰'·'리뷰 반영 계획'
- **관련 ID**: S-T42, S-T31, ASVS v5.0.0-2.4.1·13.2.2·13.3.2

## 맥락

- 첫 구현은 원하는 구독 상태를 허브(연결 수)와 구독기(채널별 listener) 두 곳에 들었다. 붙은 채 구독·해제가 한 번 실패하면 둘이 어긋나, 구독자가 있는데 메시지를 버리거나 아무도 없는데 구독이 남았다(CON-01). 다시 붙은 뒤 다시 맞추기가 실패하면 다시 시도하지 않았다(CON-02).
- `ws`는 클라이언트 Ping에 기본으로 Pong을 보낸다. 보내기 버퍼 1MiB 검사는 묶음을 보낼 때만 해서, 받지 않는 클라이언트가 Ping을 퍼부으면 파드 메모리가 찬다(SEC-01).
- 토큰 하나로 연결을 몇 개든 열 수 있었고 파드 전체 상한도 없었다(SEC-02). 구독 연결이 살아 있는지 보지 않았고(CON-03), 내릴 때 끝없이 기다릴 수 있었다(CON-04). Redis ACL은 필요보다 넓었다(SEC-03~05).

## 결정

1. **원하는 구독 상태는 구독기 하나가 든다**: 허브는 채널별 연결 수가 0→1, 1→0으로 바뀔 때 `subscribe`·`unsubscribe`를 한 번 부르기만 하고 결과로 상태를 정하지 않는다. 구독기는 부른 순간 원하는 상태를 적고 곧 돌려준다. 실제와 원하는 상태가 다른 채널은 구독기가 물러서며(0.2초에서 두 배씩, 상한 5초 [가정]) 맞춘다. 실패 뒤의 실제 상태는 '모름'으로 보고 원하는 쪽 명령을 꼭 다시 보낸다. 다시 붙은 뒤 다시 맞추기가 실패해도 같은 고리가 잇는다. 어긋난 채널 수를 게이지 `realtime_gw_subscribe_mismatch`로 낸다.
2. **클라이언트 Ping은 받지 않는다**: `autoPong`을 끄고 Ping 프레임이 오면 4403 `bad frame`으로 닫는다. 브라우저 WebSocket은 Ping을 보낼 수 없고 살아 있음은 앱 하트비트로 본다(frontend §4.4.1). 겹친 가드로 박자마다 모든 연결의 보내기 버퍼를 보고 1MiB [가정]를 넘으면 1013으로 닫는다(보낼 묶음이 없어도).
3. **연결 수 상한**: 같은 입장 토큰(`jti`)의 동시 연결은 파드마다 2개 [가정]까지다(다시 붙는 동안 옛 연결이 잠깐 겹친다). 셋째는 맺은 뒤 4429 `too many`로 닫는다. 파드 전체 연결은 `PEAKET_REALTIME_MAX_CONNECTIONS`(기본 5,000 [가정], 좌석 단계 동시 인원 docs/architecture.md §9.1)까지이고 넘으면 핸드셰이크를 503으로 거절한다. 파드 사이의 합은 세지 않는다(저장소를 두지 않는다). 계정 전체의 상한은 게이트웨이 몫이다(HOT-415). 값은 S-T12에서 파드당 연결 수를 재 정한다.
   - **곧 닫는 연결(보안 다시 보기 SEC-R01·R02, 추천 적용 2026-11-19)**: 맺은 뒤 곧 닫는 연결(4403 `bad event`·4429 `too many`)은 닫기로 정한 때 파드 상한 셈에서 빼고, 닫기 인사를 1초가 아니라 100ms [가정]만 기다린 뒤 끊는다. 회차가 다른 연결도 그 `jti`의 닫히는 중 연결로 세고, 같은 `jti`의 닫히는 중 연결이 4개 [가정]이면 그 `jti`의 새 핸드셰이크는 업그레이드 전에 503으로 거절한다. 닫힘 코드(4403·4429)를 화면이 받아야 하므로 맺기 전 거절로 바꾸지는 않는다. 그래서 토큰 하나로 닫히는 중 소켓을 쌓아 남의 새 연결을 503으로 막는 길이 없다.
4. **구독 연결 살핌**: 구독 연결에 5초 [가정]마다 PING을 보내고 2초 [가정] 안에 답이 없으면 끊긴 것으로 보아 `realtime_gw_redis_up`을 0으로 두고 다시 붙는다. node-redis가 구독 모드에서 PING을 보내지 못하면 RESP3로 붙거나 명령 시한을 같은 값으로 둔다(구현이 고르고 계획에 적는다).
5. **내리기 마감**: 연결을 1012로 닫은 뒤 구독 해제 응답은 1초 [가정]까지만 기다리고, `close()` 전체는 10초 [가정] 안에 끝낸다(쿠버네티스 기본 종료 유예 30초보다 짧게). 넘으면 로그 한 줄을 남기고 종료 코드 1로 끝낸다.
6. **ACL을 좁힌다**: `resetchannels &s:{event:*}:sec:* -@all +ssubscribe +sunsubscribe +ping +hello +auth +client|setinfo +cluster|slots`. node-redis 6.3.0이 쓰는 `CLIENT`는 `SETINFO`, 클러스터 노드 찾기는 `CLUSTER SLOTS`뿐이다(ADR-0296 뒤의 J3 판정을 좁힌다).
7. **`ws`가 스스로 거절하던 핸드셰이크를 앞에서 본다**: 메서드가 `GET`이 아니거나 `Upgrade`가 `websocket`이 아니거나 `Sec-WebSocket-Key`·`Sec-WebSocket-Version`이 틀리거나 하위 프로토콜 값에 token 밖 글자·빈 값이 있거나 겹치면 우리 차례에서 본문 없는 400으로 거절하고 센다(ASVS 16.5.1).
8. **닫힘 이유 글은 계약이다**: `server restart`(1012), `slow consumer`(1013), `token expired`(4401), `bad event`·`bad section`·`bad frame`(4403), `too many`(4429). 화면은 4403의 이유 글로 frontend §4.4.1 표의 세 줄을 가른다.

## 결과

- 구독 상태가 한 곳에만 있어 허브의 `dirty`·실제 상태 추적이 없어진다. 시험은 구독기 단위(가짜 Pub/Sub 클라이언트)와 장애 주입으로 본다.
- 토큰 하나로 파드 메모리를 고갈시키는 길이 막힌다. 파드 사이 합계는 여전히 게이트웨이가 아니면 세지 못한다.
- `StreamHubDeps.onSubscribeError`가 필요 없어진다(구독기의 오류 알림이 맡는다).

## 다른 선택지

| 길 | 고르지 않은 까닭 |
| --- | --- |
| 허브를 그대로 두고 실패한 채널만 '모름'으로 둔다(CON-01 고칠 것 2) | 두 층이 원하는 상태를 계속 따로 들어 같은 종류의 어긋남이 다른 길로 다시 생긴다 |
| Ping에 답하지 않기만 한다 | 닫지 않으면 받기를 멈춘 연결이 다른 프레임으로 버퍼를 키우는 것은 박자 검사에만 기댄다. 정상 브라우저는 Ping을 보내지 않으므로 닫아도 잃는 것이 없다 |
| 연결 상한을 좌석 Redis에 두고 파드 사이 합계를 센다 | realtime-gw는 데이터 키에 닿지 않는다(ADR-0007) |
