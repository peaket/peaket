# ADR-0092: 전역 클라이언트 상태 도구를 Zustand 하나로 줄인다 — 파트너 에디터는 정규화한 문서 저장소, 관제는 호스트 저장소와 원격마다 저장소, 원격에는 읽기 전용(2026-10-27)

- **상태**: 채택 (2026-10-27. 소유자가 "zustand, zotai, redux toolkit 전부다 쓰는건 과하지 않나요? 셋중 하나만 써도 되는거 아닌가요?"라고 물었다. 세 안(셋 그대로, Zustand와 Redux Toolkit 둘, Zustand 하나)을 비교한 답을 본 뒤 "추천대로 상태 관리 도구를 Zustand 하나로 줄이는 안(C)을 결정 기록과 함께 문서에 반영해 주세요."라고 했다. 도구를 Zustand 하나로 줄이는 것은 소유자 결정이다(소유자 승인 2026-10-27, '추천대로'). 아래 결정 2~5의 세부(에디터 문서 모양, 관제 계약, 이름 규칙, 린트)는 추천 적용(2026-10-27)이다. 추천 적용은 소유자가 방향을 승인하고 세부를 맡긴 부분에서 제안해 적용한 것으로, 바꾸고 싶으면 언제든 바꾼다.) 2026-10-28(기술 검토 낮음-097, 소유자 승인 '추천안 동의'): 결정 1의 '스트림 결합은 RxJS'와 결정 3의 'RxJS 어댑터가 묶어(`auditTime`)'는 호스트 스트림 어댑터의 작은 함수 둘(`latestEvery`·`shareByKey`)로 읽는다. 둘 이상의 흐름을 시간 창으로 합치는 곳이 없어서이고, `rxjs`는 공유 싱글턴에서 뺀다. 그런 곳이 생기면 RxJS를 호스트 안에서만 쓰는 안을 다시 본다(docs/frontend.md §3.1, architecture §6.4).
- **관련**: ADR-0024(상태 소유권), ADR-0079(프론트엔드 RADIO 설계: 결정 16·31), ADR-0091(콘솔 실행 중 성능: 결정 3·6), NFR-012, [docs/frontend.md](../frontend.md) §2.3·§2.4·§3.1·§3.9·§3.10·§4.5·§4.7·§5.14·§6, [docs/architecture.md](../architecture.md) §6.2·§6.4

## 맥락

- **지금까지의 나눔**: 원문 설계서 4장·§13은 전역 클라이언트 상태(화면 여러 곳이 함께 읽고 바꾸는 브라우저 안의 값) 도구를 앱마다 골랐다. 소비자 웹과 스캐너는 Zustand, 파트너 콘솔의 좌석맵 에디터는 Jotai, 관제 콘솔은 Redux Toolkit(이하 RTK)이다(ADR-0024). 한 앱이 두 도구를 싣지는 않아서 이용자가 받는 코드가 늘지는 않는다. 대신 만드는 쪽은 사용법·판 올리기·린트 규칙·시험 방법을 셋 따로 익히고 지켜야 하고, 앱 사이에서 상태 코드를 같이 쓰지 못한다.
- **2026-10-27에 고른 이유를 지금 설계와 대조했다**
  - Jotai: 고른 이유는 "수천 개 좌석 노드 가운데 바뀐 하나만 원자 단위로 다시 그린다"였다(architecture §6.4). 원자는 Jotai가 상태를 잘게 나눠 담는 단위다. 그런데 에디터는 좌석을 캔버스(한 장의 그림판에 그리는 방식)에 그린다(frontend §5.6, design/d5 §6.5). 좌석마다 화면 부품이 있지 않으므로, 원자 단위로 다시 그리는 장점은 트리와 속성 패널처럼 화면에 보이는 몇십 줄에만 쓰인다. 반면 에디터의 주된 편집(구역 채우기 600석, 번호 다시 매기기, 고른 좌석 옮기기)은 많은 좌석을 한 번에 바꾼다. 또 Jotai 3.0.0(2026-09-08)은 `atomFamily`를 `jotai/utils`에서 `jotai-family` 패키지로 옮기고 `loadable`과 `setSelf`를 뺐다(Jotai v3 이전 안내). 에디터가 쓰는 기능이 큰 판에서 바뀐 셈이다.
  - RTK: 고른 이유는 셋이었다. ① "액션 기록이 곧 감사·리플레이 기록": 2026-10-21에 바로잡았다. 감사 기록과 인시던트 리플레이의 정본은 서버 감사 로그와 관측 기록이다(ADR-0079, control-tower §7). ② "고빈도 지표 스트림의 결합·스로틀링": 실제로는 RxJS 어댑터가 위젯마다 250ms 단위로 묶는다(`auditTime`, frontend §5.7). 그래서 architecture §6.4의 Zustand 기각 사유 '복잡한 시계열 비동기 스트림 처리에 한계'는 맞지 않는다. RTK 문서도 listener 미들웨어를 saga·observable 같은 비동기 미들웨어의 가벼운 대안이라고 적는다. ③ "원격 위젯 리듀서의 동적 주입"(`combineSlices().inject`): RTK가 실제로 잘하는 기능이다. 다만 원격 위젯이 자기 상태를 호스트 저장소에 넣어야 할 까닭은 정본에 없다. 오히려 지금 계약은 원격에 `inject`·`dispatch`·`select`를 모두 넘겨, 원격이 호스트의 `session`·`control` 슬라이스에도 액션을 보낼 수 있다.
  - ADR-0024가 'Redux 하나로 통일'을 기각한 두 이유 가운데 '모바일 대기실에 큰 번들'은 대기실을 라이브러리 없는 경량 페이지로 바꿔(ADR-0079 결정 2) 더는 맞지 않는다. '단순한 UI 상태에도 써야 할 코드(상용구)가 많다'는 지금도 맞다. 그래서 하나로 줄인다면 RTK보다 Zustand가 맞다.
- **크기**(2026-10-27 bundlephobia, 압축 기준): Zustand 5.0.16은 490B, Jotai 3.0.1은 3,329B에 jotai-family 1.1.0이 757B, RTK 2.13.0은 14,546B에 react-redux 9.3.0이 3,771B다. 판은 같은 날 npm 레지스트리의 `latest`다(Zustand 5.0.0은 2024-10-14, RTK 2.0.0은 2023-12-04에 나왔다).
- **Zustand가 공식 문서로 지원하는 것**(2026-10-27 확인): React 밖에서 만들고 구독하는 저장소(`zustand/vanilla`의 `createStore`, `subscribe`), 선택자로 고른 값만 구독하기(`subscribeWithSelector` 미들웨어), 다시 그리지 않고 구독하기(transient updates), 큰 저장소를 기능별 조각으로 나누기(slices pattern), Redux DevTools 연결(`devtools` 미들웨어. `set`의 셋째 인자로 액션 이름을 붙이고, `actionsDenylist`로 거르고, 여러 저장소를 한 연결에서 이름으로 나눠 본다).

## 결정

1. **전역 클라이언트 상태 도구는 네 앱(소비자 웹·파트너 콘솔·관제 콘솔·스캐너) 모두 Zustand 5 하나다(소유자 결정).** Jotai·`jotai-family`·RTK·`react-redux`·`redux`는 쓰지 않는다. ADR-0024의 '앱 × 상태 종류마다 도구 하나' 원칙과 가져오기 제한 린트는 그대로다. 종류가 다른 도구는 바꾸지 않는다: 서버 데이터는 TanStack Query·urql·Dexie, 흐름 상태 기계는 XState, 스트림 결합은 RxJS, 폼은 React Hook Form + Zod, 테마·로케일은 React Context다. 대기실 경량 페이지는 계속 라이브러리 없이 손으로 쓴 상태표다.
2. **파트너 좌석맵 에디터의 문서 저장소(추천 적용)**
   - 문서(`SeatMapLayout`)는 Zustand 저장소 하나에 정규화해(같은 값을 한 곳에만 두고 ID로 찾게 나눠) 둔다. 구역은 ID로 찾는 표, 좌석은 구역마다 배열이다.
   - 한 번의 편집(채우기·옮기기·줄 맞추기·번호 다시 매기기·지우기)은 저장소를 한 번만 바꾼다. 바뀐 구역만 새 배열을 만들고 나머지 구역은 그대로 같이 쓴다. 바뀐 구역·좌석 ID 묶음을 함께 남긴다.
   - 캔버스는 저장소를 React 밖에서 구독해(`subscribeWithSelector`) 그 묶음에 든 좌석만 다시 그린다. 트리는 화면에 보이는 줄만 그리고(가상 스크롤), 줄마다 그 줄의 값만 선택자로 읽는다. 속성 패널은 고른 것만 읽는다.
   - 되돌리기는 명령 객체(바꾼 구역·좌석과 앞뒤 값)를 쌓은 스택 그대로다(frontend §3.9).
3. **관제 콘솔(추천 적용)**
   - 호스트 상태(`session`·`scope`·`control`·`autoActions`·`alerts`·`commands`·`presence`)는 호스트의 Zustand 저장소 하나에 슬라이스(기능별 조각)로 나눠 둔다. GraphQL 구독·Socket.IO·REST에서 온 값은 RxJS 어댑터가 묶어(`auditTime`) 저장소의 동작으로 쓴다. 명령 수명주기(CMP-036의 상태)는 `commands` 슬라이스에 그대로 둔다.
   - 원격 위젯은 자기 상태를 원격 안의 Zustand 저장소에 둔다. 위젯 자리마다 하나를 만들고 자리가 없어지면 버린다. 호스트 저장소에 끼워 넣지 않는다.
   - 계약(`ConsoleServices`)의 `store`(`inject`·`dispatch`·`select`)를 읽기 전용 `host`로 바꾼다. `host`는 호스트 상태 가운데 `scope`·`control`·`autoActions`·`alerts`·`presence`의 값만 선택자로 읽게 하고(`use`·`get`·`subscribe`), `session`과 `commands`는 넘기지 않는다. 권한은 `can()`이 알려 주고, 명령은 호스트 화면이 맡는다. 원격은 호스트 상태를 바꾸지 못하고, 바꿀 일은 `WidgetProps`의 콜백으로 호스트에 알린다. 아직 배포한 원격이 없으므로 계약 판은 `contractMajor: 1` 그대로다.
   - 원격과 함께 쓰는 공유 싱글턴에서 `react-redux`·`@reduxjs/toolkit`을 빼고 `zustand`를 넣는다.
   - 개발 도구: 개발 빌드에서만 `devtools` 미들웨어를 켠다. 액션 이름을 붙이고, 초당 여러 번 오는 스트림 동작은 `actionsDenylist`로 거른다. 호스트와 원격 저장소는 한 연결에서 이름으로 나눠 본다. 운영 빌드에는 넣지 않는다(운영 묶음에 개발 도구가 0건인지 FE-T21이 본다).
4. **액션 이름 규칙을 하나로 한다(추천 적용).** Zustand 동작 이름은 `슬라이스/동작`이다. 사람이 한 동작은 동사(예: `seat/select`)로, 바깥에서 온 사건은 과거형(예: `alerts/received`)으로 짓고, `set`의 셋째 인자로 넘겨 개발 도구 기록에 남긴다. 원격 위젯 저장소의 이름은 `widgets/<원격 이름>`으로 시작한다. 상태는 저장소가 내보낸 동작으로만 바꾸고, 저장소 밖에서 `setState`를 부르지 않는다. XState 이벤트 이름(대문자 뱀 표기, 예: `HOLD_SUCCEEDED`)은 그대로다.
5. **가져오기 제한 린트(추천 적용).** 모든 앱과 원격 위젯 저장소에서 `jotai`·`jotai-family`·`@reduxjs/toolkit`·`react-redux`·`redux`를 가져오면 공용 ESLint 설정(`packages/config`)이 막는다.
6. **정본 반영.** docs/frontend.md(§2.3·§2.4·§3.1·§3.9·§3.10·§4.5·§4.7·§5.14·§6), docs/architecture.md §6.2·§6.4, docs/features/control-tower.md, design/d2 §3.3을 고친다. ADR-0024·ADR-0079·ADR-0091은 상태 줄에만 적는다. 원문 설계서(archive)와 docs/appendix-learning-map.md 본문은 쓴 그대로 두는 문서라 고치지 않고, 부록 끝의 ADR 대응표에만 이 ADR을 더한다.

## 검토한 대안

| 대안 | 기각 이유 |
| --- | --- |
| 셋 그대로 | 고칠 문서가 없다. 하지만 익히고 지킬 도구가 셋이고, Jotai와 RTK를 고른 이유 가운데 둘(에디터의 원자 단위 다시 그리기, RTK의 스트림 처리)이 지금 설계와 맞지 않아 이유를 다시 써야 한다 |
| Zustand + RTK(관제만) | RTK의 끼워 넣기와 정해진 틀(상태는 리듀서로만 바꾸고 액션은 객체로 남는다)이 관제에 남고, Redux 경험을 포트폴리오에서 보일 수 있다. 하지만 도구가 둘이고, 끼워 넣기는 원격마다 저장소를 두면 필요 없다 |
| Jotai 하나 | 원자는 원격마다 나눠 두기 쉽다. 하지만 이미 Zustand를 쓰는 소비자 웹·스캐너를 바꿔야 해 고칠 곳이 더 많고, 3.0.0이 나온 지 7주라 판 변화가 크다 |
| RTK 하나 | 단순한 UI 상태에도 써야 할 코드가 많다(ADR-0024의 기각 이유 그대로). 소비자 웹의 좌석·결제 화면 예산(첫 JS 200KB·180KB, frontend §5.8)에 압축 약 18KB를 더한다 |
| 전역 UI 상태를 React Context로 | 값이 바뀔 때마다 그 아래 부품이 모두 다시 그려진다(ADR-0024의 기각 이유 그대로) |

## 결과와 트레이드오프

- 익힐 전역 상태 도구가 하나가 된다. 시험 방법, 린트 규칙, 판 올리기도 하나로 준다. 관제 호스트의 공유 싱글턴에서 압축 약 18KB(RTK + react-redux)가 빠지고 약 0.5KB가 든다(호스트 첫 JS 예산 250KB [가정], frontend §5.8).
- 원격 위젯이 호스트 상태를 바꿀 길이 없어진다. 위젯의 결함이 세션·자동 제어 상태를 건드리지 못한다.
- RTK가 틀로 강제하던 것(리듀서로만 바꾸기, 액션 객체 기록)이 없어진다. 그래서 결정 4의 이름 규칙과 '저장소 밖에서 `setState`를 부르지 않는다'를 리뷰 규칙으로 지킨다.
- 개발 도구의 동작 기록은 저장소마다 나뉜다. 한 연결에서 이름으로 나눠 본다.
- 포트폴리오에서 Redux·Jotai를 쓴 경험은 보이지 않는다.

## 되돌릴 조건

- 에디터: 5만 석 템플릿에서 채우기·되돌리기·고른 좌석 옮기기의 INP(누르고 화면이 반응하기까지 걸린 시간)가 200ms(NFR-012)를 넘고, 원인이 저장소 갱신(선택자 다시 계산·배열 복사)으로 측정되면 에디터 문서만 원자 단위 도구나 저장소 밖 열 배열(`packages/seatmap` 방식)로 옮기는 것을 새 ADR로 다시 본다.
- 관제: 원격 위젯끼리 상태를 함께 써야 하는 요구가 생기거나, 여러 팀이 원격을 만들며 동작 규칙을 지키지 않는 일이 되풀이되면 RTK(저장소 하나와 정해진 틀)를 다시 본다.

## 남는 한계

- 에디터의 갱신 비용은 아직 재지 않았다. 구독하는 곳(캔버스 하나, 보이는 트리 줄, 속성 패널)이 적다는 설계에 기댄다. 좌석맵 에디터를 만들 때(wbs 2.9.2)와 프론트엔드 측정 캠페인(wbs 7.5.2)에서 위 INP를 잰다.
- Zustand는 RTK처럼 틀을 강제하지 않아, 결정 4의 규칙은 리뷰와 린트로만 지킨다.
- 원문 설계서 4장·§13과 부록 본문의 '앱마다 다른 상태 도구' 문장은 원문이라 그대로 남는다. 읽을 때는 이 ADR이 앞선다.
