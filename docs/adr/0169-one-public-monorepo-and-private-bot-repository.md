# ADR-0169: 저장소를 공개 모노레포 하나와 비공개 봇 저장소 하나로 줄인다 — 포트폴리오에 맞춘 구성(소유자 결정, 2026-10-30)

- **상태**: 채택 (2026-10-30. 소유자가 "이건 실 서비스는 아니고 포트폴리오거든요. 그래서 웬만하면 모노레포로 관리하는게 좋을거 같은데 정말로 별로인가요? 솔직히 면접관이 모노레포 아니면 딱히 레포 왔다갔다 하면서 확인할 확률은 거의 없단말이죠"라고 물었다. 저장소를 따로 둔 근거 셋을 다시 확인한 결과를 보고 "네, 바꿔요"라고 정했다. 저장소를 둘(공개 모노레포, 비공개 봇)로 줄이는 것은 소유자 결정이다. `deploy/`·`loadtest/` 폴더 구성, 승격 PR의 대상 가지, 빌드 절차 변경을 따로 하는 검사, 봇 저장소의 이름과 시점은 추천 적용이다.) ADR-0165 결정 1(저장소 4개)과 결정 2의 `.github`·`peaket-gitops`·`peaket-loadtest` 부분을 대체한다.
- **관련**: ADR-0165(저장소 4개, 모노레포 `peaket`), ADR-0074(git flow), ADR-0054(배포 파이프라인), ADR-0057(운영은 설계만), ADR-0168(문서를 `docs/`로), POL-026(봇 코드 비공개), [docs/devops.md](../devops.md) §2·§3·§4·§5, [docs/architecture.md](../architecture.md) §10

## 맥락

ADR-0165는 모노레포 `peaket` 말고 셋을 따로 두었다. 2026-10-30에 그 근거를 다시 확인했다.

| 저장소 | 따로 둔 이유 | 다시 본 결과 |
| --- | --- | --- |
| `.github`(조직 공용 워크플로) | 빌드·서명 절차를 다른 저장소에 두고 검토한 커밋 SHA로 고정해, 입장 검사가 '검토한 그 판의 절차로 만든 이미지'만 받게 한다. 조직 첫 화면 소개도 이 저장소에만 둘 수 있다 | GitHub 문서('Using artifact attestations and reusable workflows to achieve SLSA v1 Build Level 3', 2026-10-30 확인)는 재사용 워크플로로 빌드하고 출처 증명을 만들면 SLSA v1 Build L3에 이를 수 있다고 한다. 재사용 워크플로가 부르는 쪽과 다른 저장소일 때만 확인 명령에 `--signer-repo`를 더하라고 할 뿐, 다른 저장소를 요구하지 않는다. 절차를 따로 고정하는 이점은 절차 변경을 검토할 사람이 따로 있어야 생기는데, 혼자 일하는 동안에는 형식뿐이다 |
| `peaket-gitops`(클러스터 상태) | git flow에서 `main`은 릴리스·핫픽스만 받는데 승격은 수시로 들어가야 한다. Argo CD 문서도 설정 저장소를 떼라고 권한다 | 포트폴리오에는 늘 켜 둔 운영·스테이징이 없고 배포는 로컬 kind 데모뿐이다(ADR-0057). CI는 바뀐 범위만 고르므로(ADR-0165 결정 3) 배포 상태만 바꾼 커밋은 이미지를 다시 빌드하지 않는다. 그래서 판 올림이 빌드를 다시 부르는 반복도 생기지 않는다 |
| `peaket-loadtest`(비공개) | 봇 시뮬레이터 비공개(POL-026). 공개 저장소 안에서 폴더 하나만 숨길 수 없다 | 그대로 맞다. POL-026은 3단계(사람 입력 재생형) 봇 코드를 무력화한 형태로도 공개하지 않는다. 다만 k6 부하 시나리오와 카오스 실험은 공개해도 되는 것이라, 비공개로 둘 것은 봇 시뮬레이터뿐이다 |

- 포트폴리오를 읽는 사람은 저장소를 오가며 보지 않는다. 한 저장소에서 문서·코드·배포 상태·부하 시험을 함께 보는 편이 읽기 쉽다.

## 결정

1. **저장소는 둘이다(소유자 결정)**

   | 저장소 | 공개 | 담는 것 |
   | --- | --- | --- |
   | `peaket` | 공개 | 문서(`docs/`), 화면 앱, 서버, 공용 패키지, 데이터 모델, 인프라 코드, 점검 도구, 스펙 주도 개발 기록, 그리고 새로 배포 상태(`deploy/`), 부하 시험(`loadtest/`), 빌드·서명 절차(`.github/workflows/`) |
   | `peaket-bots` | 비공개 | 합성 봇 시뮬레이터(봇 등급표 1~3단계의 봇 코드, POL-026)만 |

   - 조직 `peaket`은 그대로 둔다. 가상 팀 아홉(CODEOWNERS의 팀)을 쓰려면 조직이 필요하다. 조직 첫 화면 소개(공개 `.github` 저장소가 있어야 한다)는 두지 않는다.
   - `peaket-bots`는 봇 시뮬레이터를 처음 만드는 작업(wbs 1.2.2)에서 만든다. 저장소는 Terraform이 만들고, 기본 가지는 `main` 하나다. 운영으로 배포하지 않는 비공개 저장소라 git flow와 규칙 세트를 걸지 않는다(무료 등급에는 비공개 저장소 규칙 세트도 없다).
   - 봇 실행 결과는 공개 성능 장부(`docs/perf-ledger/`)에 남는다. 봇 탐지 규칙의 기준값은 지금처럼 비공개 설정(Secrets Manager 매개변수)에 둔다.
2. **배포 상태는 `deploy/`에 둔다(추천 적용)**
   - 옛 `peaket-gitops`의 구성을 그대로 옮기되, 서비스 기본 값 폴더 이름은 화면 앱 폴더(`apps/`)와 헷갈리지 않게 `workloads/`로 바꾼다: `deploy/charts/`, `deploy/workloads/<배포 단위>/values.yaml`, `deploy/envs/<환경>/`, `deploy/platform/`, `deploy/policies/`, `deploy/projects/`, `deploy/calendar/`.
   - Argo CD는 `peaket`의 `develop` 가지에서 `deploy/envs/<환경>/*`를 읽는다. 배포 상태의 정본 가지는 `develop`이다. `main`의 `deploy/`는 출시 때의 사본일 뿐 Argo CD가 읽지 않는다. 운영에서 무엇이 도는지는 git 가지가 아니라 `deploy/envs/prod`에 적은 다이제스트가 정한다(출시 후보 다이제스트만 승격한다, devops §5.3).
   - 승격·달력 변경은 봇이 `promote/*`·`calendar/*` 가지에서 `develop`으로 PR을 연다. 가지 규칙 검사(`branch-policy`)의 허용 쌍에 둘을 더한다. 데모 승격 PR은 검사를 통과하면 자동 병합하고, 운영 승격 PR은 사람이 병합한다(지금 규칙과 같다).
   - `deploy/`만 바꾼 PR은 CI의 바뀐 범위 고르기가 배포 상태 검사(`gitops-check`, 경보 규칙이 바뀌면 `alert-check`)만 돌린다. 이미지는 출시 후보에서만 빌드하므로 판 올림이 빌드를 다시 부르지 않는다.
3. **부하 시험은 `loadtest/`에 둔다(추천 적용)**: k6 시나리오와 카오스 실험 스크립트를 둔다. 봇 시뮬레이터는 넣지 않는다. 부하 시험이 봇을 함께 돌릴 때는 `peaket-bots`를 따로 받아 쓴다.
4. **빌드·서명 절차는 `peaket`의 재사용 워크플로다(추천 적용)**
   - `build-image.yml` 같은 공용 절차를 `peaket/.github/workflows/`에 재사용 워크플로(`workflow_call`)로 두고 `ci.yml`·`release.yml`이 같은 저장소 안 경로로 부른다. 다른 저장소의 판을 SHA로 고정해 부르는 일과 그 SHA를 올리는 Renovate PR은 없어진다. 제3자 액션의 SHA 고정과 3일 대기는 그대로다.
   - SLSA 목표는 그대로 Build L3다(위 GitHub 문서). 서명 신원은 `peaket` 저장소의 `build-image.yml`이고, 입장 검사는 그 워크플로 경로와 출시·핫픽스 가지 ref를 본다.
   - 잃는 것: 빌드 절차의 판을 코드와 따로 고정하는 보호. 그 대신 가지 규칙 검사가 `.github/workflows/`를 바꾸는 PR에 다른 코드 변경이 섞이면 실패시킨다(절차 변경은 따로, 추천 적용). CODEOWNERS에서 `.github/`의 주인은 플랫폼 팀이다.
   - OIDC 주체 사용자화(`repo`, `context`, `job_workflow_ref`)는 그대로 쓴다. 이미지 게시 역할은 `peaket`의 출시 후보 환경에서 `build-image.yml`의 게시 잡만 받는다.
5. **GitHub 설정 코드(`infra/stacks/global/github`)를 고친다(추천 적용)**: 저장소 둘, 규칙 세트는 `peaket`에만, 팀은 모두 `peaket`에 쓰기, 플랫폼 팀은 `peaket-bots`에도 쓰기. 이 수정은 아직 보관하지 않은 OpenSpec 변경 `add-repo-skeleton`을 고쳐서 한다.

## 검토한 대안

- **저장소 4개 유지(ADR-0165)**: 실서비스의 권한 경계와 공급망 보호를 그대로 보인다. 하지만 혼자 하는 포트폴리오에서는 그 보호가 형식에 가깝고, 읽는 사람은 여러 저장소를 오가지 않는다. 기각.
- **봇 시뮬레이터까지 공개 모노레포에 넣기**: POL-026과 개정 공연법 위반 소지(상용 예매처 대상 매크로) 때문에 3단계 봇 코드는 공개하지 않는다. 기각.
- **봇 시뮬레이터를 git에 넣지 않고 개발 PC에만 두기**: 저장소가 하나로 줄지만, 이력과 백업이 없고 측정을 다시 하기 어렵다. 기각.
- **배포 상태를 `main` 가지에서 읽기**: git flow에서 `main`은 릴리스·핫픽스만 받으므로, 승격 하나마다 출시가 필요해진다. 기각.
- **배포 상태 전용 가지(`deploy` 가지)**: 승격 PR의 대상이 따로 생겨 가지 규칙이 늘고, 코드와 배포 상태를 함께 보는 이점이 줄어든다. 기각.

## 결과와 트레이드오프

- 면접관은 링크 하나로 문서·코드·배포 상태·부하 시험을 모두 본다. 공개 재현도 저장소 하나로 끝난다.
- 잃는 것:
  - 빌드 절차의 판을 코드와 따로 고정하는 보호. 절차 변경 PR을 따로 하게 하는 검사와 CODEOWNERS로 일부를 메운다.
  - 설정 저장소를 떼라는 Argo CD 권고. `develop`의 `deploy/` 이력에 승격 커밋이 섞인다. 바뀐 범위 고르기로 빌드 반복은 막는다.
  - 저장소 단위 권한 경계. 원래 ADR-0165에서도 쓰기 권한이 모든 서비스 코드에 걸쳤다.
- 운영 상태(어느 다이제스트가 도는지)가 `develop`에 있다. git flow의 '`main`은 운영 출시본' 원칙과 어긋나 보이지만, 출시 단위는 `main`의 태그와 출시 후보 다이제스트이고 `deploy/`는 그 다이제스트를 어느 환경에 올렸는지만 적는다.
- WBS 작업 일수는 바꾸지 않는다. 0.1.1·0.1.2·0.4.4·1.2.2의 설명만 고친다.

## 되돌릴 조건

- 실제 운영을 시작하거나 실제 팀이 생겨 절차 변경을 따로 검토할 사람이 있으면, 빌드 절차와 배포 상태를 다시 저장소로 떼는 새 ADR을 쓴다. 그때 ADR-0165의 구성(조직 공용 `.github`, `peaket-gitops`)이 출발점이다.
