# ADR-0024: 프론트엔드 상태 관리 도구의 영역별 단일 소유권 원칙 (상태 소유권 매트릭스)

- **상태**: 채택 (2026-10-05 설계서 4장 및 §13에 최초 수립, 2026-10-08 아키텍처 결정 레코드(ADR)로 공식 이관) 2026-10-21(ADR-0079): 대기실 칸의 SWR을 손으로 쓴 상태표(대기실 경량 페이지)로, 관제의 redux-observable을 RTK listener + RxJS 어댑터로, 파트너 에디터를 Jotai 3 + jotai-family로 고쳐 읽는다(docs/frontend.md §3.1). 2026-10-26(4차 점검 3부): 결정 3의 '원천 차단한다'는 '가져오기 제한 린트로 막는다'로 읽는다(docs/frontend.md §3.1). 2026-10-27(ADR-0092, 소유자 결정): 전역 UI 상태 도구는 네 앱 모두 Zustand 하나로 읽는다. 결정 2의 좌석맵 에디터 Jotai와 실시간 관제 Redux Toolkit(위 2026-10-21의 Jotai 3와 RTK listener 포함)은 쓰지 않는다. '검토한 대안'의 'Redux 단일화' 기각 이유 가운데 모바일 대기실 번들은 대기실을 라이브러리 없이 만들어 더는 맞지 않고, 상용구 코드 이유는 그대로다(docs/frontend.md §3.1, architecture §6.4). 2026-10-28(ADR-0100, 소유자 승인 '추천안 동의'): 결정 2의 '관제 조회 GraphQL, 파트너 내부 도구 tRPC'를 쓰지 않는다. 관제는 REST(OpenAPI)와 SSE 흐름 둘, 파트너 콘솔은 orval이 만든 TanStack Query 훅으로 `partner-api`를 직접 부르고 여러 호출을 묶는 화면만 서버 컴포넌트가 묶는다(docs/frontend.md §3.1·§4.6, architecture §6.4).
- **관련 문서**: 설계서 4장(상태 소유권 매트릭스), §13(상태 관리 기술 비교), docs/architecture.md §6.4
- **관련 ID**: NFR-012, SCR-008, SCR-010, SCR-022, SCR-029

## 맥락
- 프론트엔드 생태계에는 TanStack Query, SWR, Zustand, Jotai, XState, Redux Toolkit, redux-observable, RxJS, GraphQL, tRPC, React Context 등 다양한 상태 관리 도구가 존재한다.
- 모든 도구를 무분별하게 혼용하면 번들 크기가 비대해지고 코드베이스가 파편화되는 문제가 발생한다. 반대로 단일 상태 관리 도구(예: Redux 단일화)만을 강제할 경우, 번들 크기에 극도로 민감한 모바일 웹 대기실이나 아토믹 렌더링이 필수적인 캔버스 좌석 배치도 편집기 등 각 화면의 특화된 기술적 요구를 충족할 수 없다.

## 결정
1. 프론트엔드 상태 관리는 '애플리케이션 영역 × 상태 유형'의 교차점마다 오직 하나의 전용 도구만 소유권을 갖도록 규정하는 `상태 소유권 매트릭스`(docs/architecture.md §6.4)를 엄격히 적용한다.
2. 각 영역별 책임 도구는 다음과 같이 명확히 격리한다:
   - **모바일 대기실 웹**: 극소 번들 크기와 적응형 지수 백오프 폴링 최적화를 위해 `SWR` 채택.
   - **소비자 웹**: 풍부한 캐시 무효화 및 서버 동기화 제어를 위해 `TanStack Query`, 전역 클라이언트 UI 상태에는 `Zustand` 채택.
   - **좌석맵 에디터**: 수만 개 좌석 노드의 독립적 아토믹 렌더링 최적화를 위해 `Jotai` 채택.
   - **결제 및 복합 전환 흐름**: 유한 상태 기계(FSM) 엄격성을 위해 `XState` 채택.
   - **실시간 관제 대시보드**: 초고빈도 웹소켓 스트림 및 리액티브 버퍼링 처리를 위해 `Redux Toolkit` + `redux-observable` + `RxJS` 채택.
   - **관제 조회 및 파트너 내부 도구**: 스키마 안전성과 신속한 개발 생산성을 위해 각각 `GraphQL`과 `tRPC` 채택.
   - **테마 및 환경설정**: 프레임워크 네이티브 `React Context` 채택.
3. 이 소유권 분리는 ESLint의 `no-restricted-imports` 규칙으로 빌드 타임에 강제하여 도구의 오용 및 중복 침범을 원천 차단한다.

## 검토한 대안
| 대안 | 기각 사유 및 한계점 |
| --- | --- |
| 단일 Redux 생태계로 전사 통일 | 1초가 급한 모바일 대기실 페이지에 과도한 번들 크기(수십 KB 이상)가 전송되어 초기 로딩 및 FCP를 저해하며, 단순 UI 상태 변경에도 지나친 상용구(Boilerplate) 코드가 강제된다. |
| React Context API로 고빈도 상태 제어 | 상태 일부가 변경될 때마다 Context 하위 트리의 모든 컴포넌트가 무조건 재렌더링되므로, 좌석 선택 및 실시간 대시보드 같은 고빈도 인터랙션 환경에서 브라우저 프레임 드롭을 유발한다. |

## 결과와 트레이드오프
- 각 도구가 가장 잘하는 최적화 영역에만 집중 배치되므로 사용자 경험과 렌더링 성능이 극대화된다.
- 프론트엔드 개발팀이 숙지해야 할 상태 관리 라이브러리의 스펙트럼이 넓어지므로, 신규 엔지니어 온보딩 가이드와 ESLint 규칙 기반의 정적 분석 가드가 필수적이다.
