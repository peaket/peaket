# ADR-0102: 제어 평면의 '독립'을 실제 의존에 맞춘다 — 제어 명령은 웨이포인트 없는 제어 전용 gRPC로, 관제 전용 노드 풀과 ops 전용 Aurora를 두고, 감사 체인은 커밋 뒤 작업자가 잇고, 비상 접근 전용 계정을 둔다(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 높음-08 ''독립 제어 평면'과 'TCP 대역 외 채널'의 약속이 실제 의존과 다르다(공유 저장소·노드, KMS·신원 제공자)'에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 방향은 소유자 결정(추천안 승인)이고, 안 고르기(제어 gRPC로 옮기기, ops 전용 Aurora)와 기준값 같은 세부는 추천 적용이다. ADR-0022 결정 1·4의 NestJS TCP 트랜스포터와 '대역 외' 설명, ADR-0053 결정 12와 ADR-0086의 '같은 트랜잭션에서 mac을 계산한다', ADR-0054 결정 15의 'IAM 사용자를 두지 않는다'(비상 접근 계정만 예외)를 바꾼다) 2026-10-28(기술 검토 낮음-013, 소유자 승인 '추천안 동의'): 결정 3의 관제 노드 풀을 관제·시스템 풀로 넓힌다. 클러스터 애드온(Kyverno·KEDA·istiod·Karpenter 컨트롤러·Envoy Gateway 컨트롤러·ArgoCD·Argo Rollouts·External Secrets·cert-manager)도 일반 풀에서 이 풀로 옮겨, 오픈 순간 확장 길과 마지막 제어 길을 업무 서비스 부하와 노드 축출에서 뗀다. 이 풀은 Karpenter가 만들지 않는 EKS 관리형 노드 그룹이다(Karpenter 안내서, 2026-10-28 확인). 비상 런북 Job은 이 풀을 먼저 고르고 멈추면 일반 풀에서 뜬다(결정 3의 '어느 쪽에도'를 선호 순서로 읽는다). 우선순위 클래스 `peaket-control`(확장·제어 길)과 `peaket-addon`, requests 예약을 둔다. 크기는 m7g.large 셋에서 시작해 requests 합이 70% [가정]를 넘으면 한 단계 올린다(추천 적용, docs/infra-handover.md §3.1, docs/infra.md §1·§4, docs/devops.md §5.2).
- **관련**: ADR-0010, ADR-0022, ADR-0028, ADR-0053, ADR-0054, ADR-0056, ADR-0062, ADR-0070, ADR-0073, ADR-0082, ADR-0086, ADR-0095, ADR-0100, ADR-0103, NFR-008, NFR-017, POL-021, [docs/features/control-tower.md](../features/control-tower.md) §1·§3·§5·§14, [docs/architecture.md](../architecture.md) §3.1·§3.2·§5·§7, [docs/data.md](../data.md) §1·§4, [docs/infra.md](../infra.md) §1·§4·§9, [docs/infra-handover.md](../infra-handover.md) §3, [docs/devops.md](../devops.md) §9.2·§10, [docs/security/secrets-and-keys.md](../security/secrets-and-keys.md), docs/api/proto/peaket/control/v1/control.proto, wbs 0.4.4·2.11.2·3.5.1·4.4.1·4.4.2·4.7.1, [review/tech-review.md](../../review/tech-review.md)(높음-08)

## 맥락

- **'대역 외 TCP' 채널의 실제**: ADR-0022는 제어 평면을 데이터 평면과 '물리적·논리적으로 완전히 분리'한다고 적었다(상태 줄로 일부 고쳤다).
  - NestJS TCP 채널도 같은 EKS 클러스터·VPC·노드 프록시(ztunnel)·Service DNS를 쓴다. 받는 서비스 안에서는 데이터 요청과 같은 Node.js 이벤트 루프가 명령을 처리한다.
  - ADR-0022가 gRPC를 기각한 이유('메시 프록시와 운명을 같이한다')는 ADR-0082 뒤로 성립하지 않는다. 웨이포인트(서비스 하나 앞에 두는 작은 L7 프록시)를 붙이지 않은 별도 Service·포트의 gRPC도 노드 프록시의 L4만 지난다.
  - 문서의 '단순한 바이너리 프로토콜'은 실제로 '길이#JSON'이다(NestJS `json-socket.ts`, 기술 검토 §9). 그래서 RPC 방식이 하나 더 늘고, 데드라인·상태 코드·계약 검사·TLS를 따로 붙여야 하며, 프로토콜 비교 시험(REST·gRPC·Nest TCP)까지 생겼다. 격리 이득은 'Kafka·게이트웨이·웨이포인트를 거치지 않는다'로, 같은 gRPC 스택의 별도 포트로도 얻는다.
- **ops-svc의 배치**:
  - 명령 이벤트 스토어와 감사 로그가 identity·core와 같은 Aurora 공유 쓰기 인스턴스(db.r7g.large [가정])에 있다. identity는 오픈 직전 로그인과 토큰 갱신(팬 액세스 토큰 15분)이 몰리는 서비스다.
  - Socket.IO 어댑터가 공유 세션·캐시 Redis에 있다(ADR-0100이 뺀다).
  - gw-ops는 초당 20만 건을 받는 핫패스 노드 풀에, ops-svc는 일반 노드 풀에 있다(docs/infra-handover.md §3.1). 인수 문서는 ops-svc·콘솔을 2등급('대역 외 런북이 대신')으로 둔다.
- **KMS·신원 제공자 결합**:
  - 감사 체인의 KMS `GenerateMac` 호출이 운영 명령 트랜잭션과 머리 행 잠금 안에 있다(docs/data.md §4, ADR-0086). KMS(암호 키를 보관하고 대신 써 주는 AWS 서비스)가 느리거나 멈추면 입장·판매 일시정지 같은 안전 쪽 명령도 커밋되지 않는다. 플랫폼 전체의 감사 쓰기가 잠금 하나와 KMS 왕복 하나씩으로 줄 선다.
  - 운영자 로그인과 재인증도 KMS에 기댄다. 비밀번호 페퍼는 KMS HMAC(`VerifyMac`)이고 TOTP 시드는 KMS 봉투 암호화다(docs/security/secrets-and-keys.md).
  - 비상 런북 서명(`kms:Sign`)과 긴급 접근이 평소와 같은 IAM Identity Center에 기댄다. ADR-0053은 '남는 한계'로만 적었다. AWS Well-Architected SEC03-BP03은 비상 접근이 평소와 같은 신원 제공자에 기대는 구성을 흔한 잘못으로 든다(기술 검토 §9).
- **확인한 사실(2026-10-28 원문, AWS KMS 개발자 안내서 'Multi-Region keys')**: 다중 리전 키는 같은 키 재료와 키 ID를 가져, 한 리전에서 암호화한 것을 다른 리전의 복제 키로 리전 사이 호출 없이 복호할 수 있다. 대칭·비대칭·HMAC 키 모두 다중 리전으로 만들 수 있다. 복제 키는 키 정책·권한·켜짐 상태를 따로 가지며, 주 키와 다른 복제 키가 모두 꺼져도 쓸 수 있다.

## 결정

1. **제어 명령은 제어 전용 gRPC 단항 호출로 보낸다(소유자 결정 '추천안 동의', 세부는 추천 적용).** NestJS TCP 트랜스포터와 프로토콜 비교 시험(REST·gRPC·Nest TCP)을 뺀다.
   - **계약**: `peaket.control.v1.ControlReceiver/ApplyControl`(docs/api/proto/peaket/control/v1/control.proto). 요청은 명령 ID, 범위(전체·회차), 종류, 판 번호(그 범위·종류에서 늘어나기만 하는 수, ADR-0103), 바라는 상태, 서명 묶음(비상 런북일 때만)이다. 응답은 적용한 판 번호, 파드 이름, 적용 시각이다.
   - **포트와 Service**: 받는 서비스(admission-ctrl·purchase-svc·queue-svc)는 업무 포트와 다른 제어 포트를 연다. 제어 전용 Service(`<서비스>-control`)를 따로 두고 웨이포인트를 붙이지 않는다(노드 프록시의 L4 mTLS와 허용 목록만, ADR-0082). admission-ctrl은 리더 파드만 엔드포인트로 내놓는 Service(지금 그대로), purchase-svc·queue-svc는 파드마다 부를 수 있는 헤드리스 Service다.
   - **호출 규칙**: 데드라인 1초 [가정]. 같은 명령 ID와 판 번호로 다시 보내면 같은 결과다(멱등). ops-svc는 ack 시간 초과(10초 [가정], ADR-0073)까지 다시 보낸다. gRPC 상태 코드와 `buf breaking` 규칙은 다른 내부 계약과 같다(docs/api/proto/README.md §2).
   - **받는 쪽 제한**: 제어 포트는 ops-svc와 비상 런북 Job의 메시 신원만 받는다(L4 정책과 NetworkPolicy, 지금 그대로). 메시가 없는 포트폴리오 실행은 NetworkPolicy가 대신한다(ADR-0082).
   - **비상 런북**: CLI는 같은 gRPC로 서명 묶음을 보낸다. 받는 쪽은 배포에 든 공개키로 서명을 확인한다(서명 수는 지금 그대로, ADR-0053 결정 11·ADR-0095).
   - **낱말**: '대역 외', '완전 분리', '바이너리'를 이 채널에 쓰지 않는다. 이 채널은 **직접 제어 채널**이다. Kafka·게이트웨이·웨이포인트를 거치지 않지만, 같은 클러스터 네트워크·노드 프록시와 받는 프로세스의 이벤트 루프는 데이터 요청과 함께 쓴다.
   - **받는 쪽이 과부하일 때**: 판매 일시정지의 효력은 받는 서비스 저장소의 제어 상태로 정해진다(ADR-0103). 파드 하나가 상태를 쓰면 다른 파드의 홀드 Lua가 바로 그 상태를 본다. 과부하 중의 ack 지연은 C-T48로 잰다.

2. **판매·입장 일시정지를 게이트웨이나 엣지에서도 집행하는 안은 두지 않는다(추천 적용).**
   - 게이트웨이(Envoy)에서 회차별로 바로 켜고 끄려면 요청마다 외부 판정(ext_authz)을 부르거나 경로 설정을 바꿔 퍼뜨려야 한다. 앞의 것은 핫패스에 호출을 하나 더하고, 뒤의 것은 GitOps와 게이트웨이 제어기를 거쳐 퍼지는 시간이 든다(반영 시간 확인 필요).
   - 엣지(CloudFront 함수 + KeyValueStore)는 앱과 다른 실패 범위라 클러스터가 멈춰도 막는다는 장점이 있다. 그러나 KeyValueStore 값이 모든 엣지에 퍼지는 시간을 확인하지 못했고(확인 필요), 홀드·결제 접수 경로가 지나는 배포마다 함수를 둬야 하며, 원자적 홀드 판정과 같은 순간을 맞출 수 없다.
   - 그래서 집행은 앱(purchase-svc의 홀드 Lua와 결제 경로, admission-ctrl 리더, queue-svc)에 둔다. 클러스터 전체가 멈추면 판매도 함께 멈춘다. 엣지에 둘째 스위치가 필요한 경우는 '클러스터는 살았는데 제어 경로만 막힌' 경우인데, 그때는 비상 런북이 같은 제어 상태를 쓴다. 원본 장애 때의 판매 일시 중단 정적 응답(SCR-059)은 그대로다.

3. **관제 전용 노드 풀을 둔다(추천 적용).** gw-ops의 Envoy 프록시와 ops-svc는 관제 노드 풀(테인트 `peaket.io/pool=ops:NoSchedule`, m7g.large [가정], AZ 셋에 한 대씩, 온디맨드만)에서만 돈다. 핫패스 노드의 CPU 포화와 그 노드의 노드 프록시 부하가 관제 입구와 ops-svc에 번지지 않는다. 비상 런북 Job은 관제 풀과 일반 풀 어느 쪽에도 놓일 수 있다(한쪽이 멈춰도 뜬다). 받는 서비스(purchase-svc 등)는 핫패스 풀에 있으므로, 그 노드의 노드 프록시 몫은 남는다.

4. **ops 논리 DB를 ops 전용 Aurora 클러스터로 옮긴다(추천 적용).**
   - 쓰기 1 + 읽기 1(다른 AZ), db.r7g.large [가정]. identity·core는 공유 클러스터에 남는다. ADR-0100의 알림 표(`ops_push_event`·`ops_presence`)도 여기에 둔다.
   - 이유: 오픈 직전 로그인과 토큰 갱신이 공유 쓰기 인스턴스에 몰리는 바로 그때 명령 접수 p95 500ms(NFR-008)를 지켜야 한다. 공유를 남기면 'NFR-008이 공유 인스턴스 포화에 묶인다'는 한계가 제어 평면의 첫 약속과 맞지 않는다.
   - 비용: Aurora 인스턴스 둘이 는다. 월 비용은 운영 비용 측정(wbs 4.8.1)에서 잰다. 다시 합칠 조건은 '되돌릴 조건'에 둔다.
   - 세션·캐시 Redis에서 Socket.IO 어댑터 상태를 뺀다(ADR-0100 결정 4). 이제 ops-svc는 공유 Redis에 쓰지 않는다. 자동 제어 상태는 대기열 Redis의 `q:{event:E}:ctl`을 읽기만 한다.

5. **명령 기록과 감사 체인 계산을 떼어 놓는다(추천 적용, ADR-0053 결정 12와 ADR-0086의 같은 트랜잭션 규칙을 바꾼다).**
   - 감사 기록을 쓰는 트랜잭션은 기록(`command_event` 등)과 체인 행(`audit_chain`: 머리 행에서 받은 빈틈 없는 `seq`, 기록 종류·ID, 기록 해시, 비공개 잎 솔트)을 쓰고, `mac`은 비운 채 커밋한다. KMS를 부르지 않는다. 머리 행 잠금은 번호를 받는 동안만이라 짧다.
   - 체인 작업자 하나(ops-svc 안에서 Lease로 고른 하나)가 `seq` 순서대로 `mac = HMAC(감사 체인 키, "PEAKET-audit-v1" ‖ seq ‖ 직전 mac ‖ 기록 해시)`를 채운다. 5분 앵커와 1시간 검증은 mac을 채운 마지막 `seq`까지를 다룬다. 체인 모양과 앵커·검증 규칙은 그대로다.
   - KMS가 늦거나 멈추면 mac이 빈 행이 쌓인다. 가장 오래된 빈 행이 1분 [가정]을 넘으면 SEV2, KMS가 돌아오면 따라잡는다. 서울 KMS가 응답하지 않으면 도쿄의 다중 리전 복제 키로 계산한다(같은 키 재료라 같은 mac이다).
   - **원칙(소유자 승인 방향)**: 안전 쪽 명령(명령 2·3, 명령 6과 11의 멈추는·줄이는 방향)은 KMS나 신원 제공자 가운데 하나가 멈춰도 낼 길이 있다.
     - KMS 장애: 명령 커밋은 KMS를 부르지 않는다(위). identity-svc의 KMS 호출(비밀번호 페퍼 `VerifyMac`, TOTP 시드 복호)은 서울이 응답하지 않으면 도쿄 복제 키로 넘긴다. 비상 런북 서명도 도쿄 복제 키로 할 수 있다.
     - 신원 제공자 장애: 관제 콘솔 로그인은 identity-svc의 관리 계정이라 IAM Identity Center를 쓰지 않는다. AWS 쪽 비상 경로(런북 Job과 서명)는 결정 6의 비상 접근 계정으로 한다.
     - 두 리전의 KMS를 함께 쓰지 못하거나 키 자체를 잘못 껐으면, 재인증과 런북 서명을 할 수 없다(남는 한계). 그때는 이미 받은 5분짜리 재인증 토큰으로만 낼 수 있다.

6. **비상 접근 전용 계정을 둔다(추천 적용, ADR-0054 결정 15의 'IAM 사용자를 두지 않는다'의 유일한 예외).**
   - AWS 조직에 비상 접근 계정 하나를 더한다(관리·비운영·운영에 비상을 더해 4계정). 그 안에 하드웨어 MFA(FIDO 보안 키)를 건 IAM 사용자 둘을 두고, 비밀번호와 보안 키는 봉인해 서로 다른 곳에 보관한다. 두 사용자는 각각 commander 한 명에 묶인다.
   - 운영 계정으로 넘어가는 교차 계정 역할 하나를 둔다. 할 수 있는 일은 `ops-breakglass` 네임스페이스의 비상 런북 Job 만들기와, 묶인 commander의 비상 런북 서명 키로 `kms:Sign`뿐이다. 진단 증거 복호나 데이터 읽기는 넣지 않는다.
   - 쓰는 때: IAM Identity Center가 멈추거나 잘못 설정돼 평소 경로(긴급 접근 역할 포함, docs/devops.md §10.2)로 들어오지 못할 때만이다. 로그인하는 순간 CloudTrail 이벤트로 SEV1이 나고, 사용 뒤 사후 검토와 비밀번호·보안 키 교체와 다시 봉인하기가 필수다. 분기마다 [가정] 로그인만 해 보는 점검을 한다(RB-37).
   - 운영 설계 범위다. 포트폴리오에는 Terraform 코드와 런북(RB-37)으로만 둔다(ADR-0057).

7. **Game Day를 더한다(추천 적용).**
   - G-27 'KMS 정지 중 명령 2': KMS 호출을 막은 채 명령 2·3을 내면 커밋·전파되고, mac이 빈 행이 쌓였다가 KMS를 되살리면 따라잡으며 검증 잡이 통과한다. 운영자 재인증은 복제 키로 넘어간다.
   - G-28 '신원 제공자 정지 중 명령 2': IAM Identity Center를 막은 채 콘솔로 명령 2를 낸다. ops-svc도 함께 멈춘 시험에서는 비상 접근 계정(RB-37)으로 런북 Job을 돌려 명령 2를 낸다.
   - 포트폴리오에서는 로컬 대체 장애(LocalStack KMS 차단)와 모의 진행으로 한다(docs/verification.md §5.2).

8. **시험(추천 적용).**

## 결과와 트레이드오프

- 제어 명령의 RPC 방식이 gRPC 하나가 되고, 프로토콜 비교 시험이 빠진다. 제어 채널을 '대역 외'라고 과장하지 않고, 실제로 무엇을 피하고 무엇을 함께 쓰는지 적는다.
- 관제 입구와 ops-svc가 핫패스 노드와 공유 DB 쓰기 인스턴스·공유 Redis에서 떨어진다. 명령 접수 SLO가 로그인 몰림에 묶이지 않는다.
- KMS가 멈춰도 명령은 커밋되고, 감사 체인은 회복 뒤 따라잡는다. 신원 제공자가 멈춰도 콘솔 경로와 비상 계정 경로가 남는다.
- 대가:
  - 관제 노드 세 대와 Aurora 인스턴스 두 대의 상시 비용이 는다(운영 설계, 포트폴리오 기간에는 띄우지 않는다).
  - KMS 장애 동안 mac이 빈 행은 변조 탐지를 받지 않는다.
  - 비상 계정의 봉인 보관과 정기 점검이라는 사람의 절차가 생긴다.

## 되돌릴 조건

- 운영 측정에서 공유 클러스터의 쓰기 여유가 로그인 몰림 중에도 넉넉하고(쓰기 CPU 50% [가정] 아래), 비용을 줄여야 하면 ops를 공유 클러스터로 되돌리고 'NFR-008이 공유 인스턴스 포화에 묶인다'를 남는 한계로 적는다.
- 체인 작업자가 따라잡지 못할 만큼 감사 쓰기가 많아지면(빈 행이 평시에도 10초 [가정] 넘게 남으면) 묶음 mac을 검토한다.
- 엣지 반영 시간이 몇 초 안으로 확인되면 결정 2의 엣지 집행을 둘째 스위치로 다시 본다.

## 남는 한계

- 직접 제어 채널은 같은 클러스터·리전과 노드 프록시를 쓴다. 클러스터·리전 전체 장애는 함께 받는다.
- 받는 프로세스의 이벤트 루프가 막히면 ack가 늦다. 효력은 저장소의 제어 상태로 바로 나지만(ADR-0103), ack 지연은 남는다.
- 두 리전의 KMS를 함께 쓰지 못하면 재인증과 비상 런북 서명을 할 수 없다.
- mac이 빈 감사 행은 채워질 때까지 변조 탐지를 받지 않는다(KMS 장애 동안 길어진다).
- 비상 계정의 두 사용자를 한 사람이 쥐는 1인 기간에는 '다른 사람의 확인'이 아니다(ADR-0095와 같은 한계).
