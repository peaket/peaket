# ADR-0371: 관제 대시보드의 회차 단계·T-30분 점검·Go/No-Go 판정을 서버가 정하고, 자동 제어 상태를 대기열 Redis에서 직접 읽으며, 경보 목록 REST를 더한다(F-03-3, OPS-380)

- **상태**: 채택(2026-11-23, 추천 적용. 기능 F-03-3 계획 `docs/review/plans/F-03-3.md`의 '정할 것과 추천'(6-1~6-10)과 시험 먼저 절차(ADR 0372번, 감독이 develop에 올림)에서 시험이 정한 공개 인터페이스를 구현 담당이 정본에 옮겼다). 결정 3(판정 규칙)을 방향 결정으로 보면 소유자 확인이 필요하다.
- **관련**: ADR-0049, ADR-0054, ADR-0067, ADR-0069, ADR-0078, ADR-0100(결정 2), ADR-0126, ADR-0141, ADR-0360(결정 1·9·10), [docs/features/control-tower.md](../features/control-tower.md) §2·§6의 6·§8·§12·§13·§16, [docs/design/d5-screen-blueprint.md](../design/d5-screen-blueprint.md) §7.2, [docs/observability.md](../observability.md) §8, [docs/data.md](../data.md) `ops_go_no_go_judgement`, [docs/security/asvs/control-tower.md](../security/asvs/control-tower.md) 1.2.2·3.7.2·13.1.1·13.2.2·16.2.2, docs/api/openapi.yaml(`/v1/ops/events/{eventId}/readiness`·`/v1/ops/events/{eventId}/go-no-go-judgements`·`/v1/ops/alerts`), docs/api/asyncapi.yaml(`OpsControl`·`OpsAlert`), BUILD_ORDER F-03-3·OPS-380

## 맥락

- 관제 대시보드(SCR-029)는 원격 위젯 둘만 실제 값이고, 단계 탭·T-30분 점검·Go/No-Go 판정·남은 허용 실패·포화도·제어 입력 없음·경보 목록은 서버 원천이 없었다(d5 §1.6 13번 '판정 기록 API 없음', asyncapi `OpsControl` 본문 미정, 경보 목록 REST 없음).
- 같은 시각 갈래 4(F-02-1)가 ops-svc `app.module.ts`·`main.ts`·`modules/commands/**`·마이그레이션 0025를 고친다. 이 기능은 그 파일을 고치지 않고, alerts 모듈에는 읽기 함수만 더한다(감독 결정 2026-11-23).
- 시험 먼저 절차(ADR 0372번, 감독이 develop에 올림)라 시험이 경로·본문·항목 키·원천 이름을 먼저 정했다(계획 '실패 확인' 절 '시험이 정한 공개 인터페이스'). 아래 이름은 그것을 따른다.

## 결정

1. **회차 단계의 원천**: ops-svc 새 컨텍스트 `modules/readiness/`가 core-svc 내부 판매 설정(`GET /internal/v1/events/{eventId}/sale-config`, 서비스 사이 토큰)의 `opensAtMs`·`saleEndsAtMs`·`entryOpensAtMs`·`entryClosedAtMs`를 읽는다(commands 모듈의 어댑터는 가져오지 않는다). 5초 [가정] 한도, 회차마다 30초 [가정] 캐시. 단계는 입장 창(entryOpensAt 이상·entryClosedAt 미만)이면 `entry`, 판매 시작 30분 전부터 시작 전까지 `t30`, 시작부터 10분 전까지 `t0`, 그 뒤 판매 끝 전까지 `live`, 판매 끝부터 `after`, 판매 시작 30분 전보다 앞이거나 입장이 끝났거나 판매 설정이 없으면(core 404) `none`(d5 '대상 없음')이다. core를 못 읽으면 503 `readiness-source-unavailable`. 화면은 `?tab=`이 없을 때 이 단계의 탭을 연다.
2. **점검 항목(필수 13 · 권고 2 · 표시 1)**: 키는 `prewarm`·`datastores`·`payment-provider`·`identity-providers`·`cdn-limits`·`synthetic`·`oncall-test`·`clock-offset`·`credentials`·`cross-region-backup`·`deployments`·`freeze-window`·`managed-maintenance`(필수), `cdn-hit-ratio`·`demand-forecast`(권고), `pg-assignment`(표시). 원천은 넷으로 나눈다. ① 지표 고정 쿼리: `clock-offset`(`max(abs(node_timex_offset_seconds))`, 20ms 이하 통과), `datastores`(Redis·PostgreSQL `up`과 Kafka `UnderMinIsrPartitionCount` 0), `payment-provider`(결제사 서킷 닫힘·5분 한도 초과 0), `synthetic`(합성 점검 `probe_success`). ② 클라우드 전용(`prewarm`·`cdn-limits`·`cross-region-backup`·`managed-maintenance`·`cdn-hit-ratio`): local·ci·demo는 '이 환경에 없음'(`not-in-env`), 그 밖은 기록 규칙. ③ 원천 기능의 기록 규칙 `peaket:readiness:<키의 -를 _로>`(1 통과·0 실패): `identity-providers`·`oncall-test`·`credentials`·`deployments`·`freeze-window`·`demand-forecast`. 규칙이 아직 없으면 '확인할 수 없음'(`unknown`, reason `source-not-built`). ④ 표시만(`display-only`). 쿼리는 서버에 고정하고 화면이 쿼리를 보내지 못한다. 원천은 서비스 시계 시각에 묻고, 빈 결과·NaN·5분 넘게 표본 없음은 `unknown`(reason `no-sample`), 지표 창고에 닿지 못하면 `unknown`(reason `source-unavailable`)이다. 이름은 docs/observability.md §8 'T-30분 점검 원천'에 둔다.
3. **판정 규칙(방향이면 소유자 확인)**: 필수 중 `fail`·`unknown`은 실패로 센다(원천을 못 읽은 필수 항목을 통과로 보지 않는다, control-tower §6의 6 '입력이 없으면 멈춘다'와 같은 뜻). 권고 중 `fail`은 사유를 받아 계속한다. `not-in-env`·`deferred`(CDN 적중률 요청 1,000건 [가정] 미만)·`display-only`는 판정에 들지 않는다. 필수 실패가 하나라도 있으면 No-Go. staging·prod(local·ci·demo 밖의 모든 환경 이름)에서 `PEAKET_PROMETHEUS_URL`·`PEAKET_QUEUE_REDIS_URL`(또는 `…_CLUSTER_URLS`)·`PEAKET_CORE_HTTP_URL` 가운데 하나라도 없으면 ops-svc가 그 이름을 담은 오류로 시작하지 않는다.
   - **알려 둔 어긋남(시험 담당이 찾음)**: 원천 기능 전 항목(`oncall-test`·`freeze-window` 등)이 `unknown`이고 필수 `unknown`은 실패라, 원천 기능들(F-02-3·OPS-090 등)이 기록 규칙을 내기 전에는 어느 환경에서도 Go가 나오지 않는다. 시험은 재판정을 '시계 오프셋이 실패 목록에서 빠지고 판정이 그때 미리 보기와 같다'로 본다. 이 결정은 규칙을 느슨하게 하지 않는다(No-Go가 안전한 쪽이다). 리허설에서 Go를 보려면 그 기록 규칙을 먼저 둔다.
4. **판정 창**: 판정·재판정은 판매 시작 30분 전부터 20분 전까지(두 끝 포함) 받고 그 밖은 409 `judgement-window-closed`다. 20분 전까지 판정이 없으면 No-Go로 본다(`readiness`의 `lastJudgement` 없음과 `judgeableUntil` 지남, 명령 쪽 C-T25 ②가 읽는다).
5. **판정 기록과 권한**: `POST /v1/ops/events/{eventId}/go-no-go-judgements`는 operator·commander만 받는다(commander는 operator를 포함하는 상위 역할, d5 §3.3). 본문은 실패한 권고 항목의 사유(`recommendedReasons`)만 읽고, `verdict`·`items` 같은 다른 칸은 400으로 거절하지 않고 버린다(서버가 다시 계산한다, ASVS 8.2.3). 실패한 권고 항목에 사유가 없으면 422 `recommended-reason-required`, 판매 설정이 없으면 404 `not-found`. 기록은 새 표 `ops_go_no_go_judgement`(마이그레이션 0029, 같은 회차 안에서 `sequence`가 1씩 는다)에 쓰고 같은 트랜잭션에서 감사 체인 `GO_NO_GO_JUDGED`(`record_id` = 판정 ID, payload = 회차·판정·실패 항목·권고 사유·순번·판정자 로그 가명)에 남긴다. 판정자 계정 ID는 표·감사·응답 어디에도 두지 않는다. 멱등 키 저장소는 두지 않는다: 판정은 덧붙이기만 하는 기록이라 같은 요청을 다시 보내면 다음 순번의 재판정으로 남는다(화면은 [판정] 단추를 누를 때 한 번만 보낸다).
6. **`control`은 알림 표에 넣지 않는다**: 지금 값이라 다시 붙을 때 빠진 것을 메울 필요가 없고, 파드마다 같은 Redis를 읽어 같은 값을 낸다. 늘 여는 흐름(`/v1/ops/live?eventId=`)이 고른 회차의 값을 붙을 때 한 번과 바뀔 때마다 순번(id) 없이 보낸다. 본문은 asyncapi `OpsControl`(`eventId`·`kind`·`since`·`inputStaleKinds`·`targetNow`·`budgetHoldAt`·`lastDecrease`·`updatedAt`)이다. 알림 표 `kind` CHECK는 바꾸지 않는다.
7. **대기열 Redis 읽기**: live 모듈의 제어 감시가 파드마다 1초 [가정]마다 `q:{admission}:events`(점수가 지금보다 큰 회차, 500개 [가정]까지)와 회차마다 `q:{event:E}:ctl`, 회차와 무관한 `q:{admission}:ctl`을 읽기 명령(`ZRANGE`·`HGETALL`)으로만 읽는다. 다섯 값의 우선순위는 긴급 정지(`autoStopped`) → 입력 없음(`inputStale`) → 일시정지(만료 전 `admitPaused`·`paused`·`suspended`·전체 범위 `allPaused`) → 자동 증액 멈춤(`budgetHoldAt`) → 정상이고, 1·0이 아닌 칸이나 숫자가 아닌 시각은 없는 것으로 보며, 회차 키가 없거나 읽지 못하면 `unknown`(정상 아님)이다. 칸 이름은 쓰는 쪽(admission-ctrl `memoryToFields`, F-02-1 운영자 칸)과 같다. 입력 없음이 켜지면 경보 기록 표에 (회차, `control`) SEV2(제목 '관측 경로와 별개로 입장 제어가 알린 경보입니다')를 열고 꺼지면 푼다. 같은 (회차, 종류)는 한 건이라 파드가 여럿이어도 한 건이고, Prometheus·Alertmanager를 거치지 않는다(§8). 읽기 실패가 1분 [가정] 이어지면 SEV3(`control`)를 연다. 운영은 읽기 전용 Redis 사용자로 붙는다(ASVS 13.2.2, ACL·NetworkPolicy는 구간 5). 주소는 `PEAKET_QUEUE_REDIS_URL` 또는 `PEAKET_QUEUE_REDIS_CLUSTER_URLS`이고 없으면 local·ci는 `unknown`이다.
8. **관제 판단 위젯 키 넷**(ADR-0360 결정 9의 `WidgetSource` 포트): `ops-readiness.checklist`(T-30분 탭의 실시간 항목, readiness 조회와 같은 `items`·`preview`), `ops-budget.journeys`(여정 일곱의 허용·사용·남은 건수와 짧은·긴 창 소진 배수, 연동 여정 넷만 `linked`, 원천은 기록 규칙 `peaket:slo:onsale_allowed`·`onsale_used`·`onsale_burn_short`·`onsale_burn_long{event_id,journey}` — OPS-090이 만든다), `ops-saturation.summary`(CPU `node_cpu_seconds_total` idle 비율, Redis 메모리 `redis_memory_used_bytes / redis_memory_max_bytes`, Kafka 밀림 `kafka_consumergroup_lag`, 이벤트 루프 `nodejs_eventloop_lag_p99_seconds`. 칸마다 `{ value, level }`, 기준 [가정]은 CPU 0.7·0.85, Redis 메모리 0.75·0.9, Kafka 1,000·10,000건, 이벤트 루프 0.1·0.5초, 요약은 가장 나쁜 칸이고 값이 없는 칸이 있으면 정상이 아니다), `ops-diagnostics.summary`(진단 힌트, 원천 OPS-050·OPS-090 전이라 늘 원천 실패 값). 값을 못 읽은 칸은 `null`과 까닭이고 0으로 읽지 않는다. openapi 응답은 ADR-0360 결정 10대로 `OpsWidgetValue`(공통 네 칸)를 두고 키별 모양은 `OpsWidgetOps*` 스키마 이름으로 가리킨다.
9. **경보 목록 REST와 다시 읽기**: `GET /v1/ops/alerts?eventId=`(viewer·operator·commander, CS 403, `no-store`)가 걸린 경보 전부와 풀린 지 60분 [가정] 안의 경보를 500건 [가정]까지(걸린 것 먼저, 넘치면 오래 전에 풀린 것부터 뺀다) `{ items, seq }`로 준다. 경보는 alerts 컨텍스트의 공개 읽기 `OpsAlertList.list({ eventKey?, resolvedSinceMs, limit })`로 읽고(alerts 모듈은 읽기 함수만 더했다. 기존 `open`·`resolve`와 (eventKey, kind) 멱등 규칙은 그대로), 본문은 live 모듈의 `alertBodyOf`가 만든다. 알림 표 트리거 함수(0029가 0028의 함수를 바꾼다)와 `alertBodyOf`는 같은 규칙이다: 시각은 UTC 밀리초 ISO(`…Z`), `kind`는 계약 열거 밖이면 `hygiene`(내부 종류는 `sourceKind`), 회차 ID는 UUID 꼴일 때만, 경보 기록 `detail`의 글 칸 `journey`(여정 일곱만)·`foldedUnder`·`runbookUrl`·`dashboardUrl`·`exploreUrl`·`dependency`만 옮긴다. 그래서 같은 경보의 목록 본문과 흐름 `alert` 본문이 같다. `seq`는 목록을 읽기 직전의 커밋된 알림 표 마지막 순번이다. 콘솔은 늘 여는 흐름을 처음 열 때와 `reset`을 받을 때 이 목록으로 경보 슬라이스를 갈아 끼우고, 그동안 들어온 `alert` 사건 가운데 순번이 `seq`보다 큰 것만 목록 위에 다시 얹는다(ADR-0100 결정 2의 '경보를 REST로 다시 읽는다'를 채운다). 메모리 조립의 목록은 live 모듈만의 메모리 저장소라 비어 있다(DB 조립이 실제 표를 읽는다).
10. **콘솔 밖 도구 링크**: '자세히 보기 ↗'는 빌드 값 `PEAKET_CONSOLE_GRAFANA_URL`(오류 위젯은 `PEAKET_CONSOLE_SENTRY_URL`) 틀에 회차 ID·시작·끝 시각(과 패널 이름)만 `URLSearchParams`로 넣은 새 탭 링크(`target="_blank"`, `rel="noopener noreferrer"`)다. 경보의 런북·대시보드·'실패 사건 보기' 주소는 `https`이고 호스트가 `PEAKET_CONSOLE_LINK_HOSTS`(쉼표) 가운데 하나와 정확히 같을 때만 링크, 아니면 글자로만 보인다(앞부분 일치·사용자 정보·`javascript:`·`data:` 거절, ASVS 1.2.2·3.7.2). 관제 콘솔은 정적 앱이라 실행 때 설정 파일 없이 빌드 값으로 넣는다. 원천이 없는 위젯은 실제 값 화면에서 고정 숫자 대신 '원천 연결 전' 카드로 둔다(미리보기 `?state=`는 그대로).

## 검토한 대안

- **판정 규칙에서 필수 `unknown`을 빼기**(정본 글 '실패하면 No-Go'만 보기): 원천이 끊긴 채 Go가 나올 수 있어 버렸다. local·ci에서 Go를 못 보는 불편은 기록 규칙 대역으로 푼다.
- **`control`을 알림 표 `kind`로 넣기**: 다시 붙기로 메울 이유가 없는 지금 값이고 1초마다 행이 쌓여 버렸다.
- **입력 없음을 Prometheus `admission_control_input_stale`로 읽기**: 지표 창고가 멈추면 같이 멈춘다(§8 '관측 경로와 별개'). Redis를 직접 읽는다.
- **live 모듈이 `ops_alert`를 직접 읽거나 자기 알림 표(1시간)로 목록 답하기**: 앞은 컨텍스트 경계 위반, 뒤는 1시간 넘게 울린 경보를 잃는다(계획 '감독에게' 10).
- **readiness를 AppModule에서 싣기**: 갈래 4가 고치는 파일이라 LiveModule.register의 imports로 싣는다. F-02-1이 합쳐진 뒤 옮기려면 `app.module.ts` 한 줄이다.
