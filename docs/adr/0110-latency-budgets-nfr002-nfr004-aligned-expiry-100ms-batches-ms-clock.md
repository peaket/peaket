# ADR-0110: 대기 반영(NFR-002)과 좌석 전파(NFR-004)의 지연 예산을 단계별로 나누고 설계를 맞춘다 — 입장 임박 구간은 캐시 만료를 생성 시각에 맞추고 0.5초 폴링, 좌석 델타는 100ms 묶음, 반영 지연은 밀리초 서버 시각으로 잰다(2026-10-28)

- **상태**: 채택 (2026-10-28. 기술 검토(review/tech-review.md)의 높음-24 'NFR-002(입장 임박 p99 2초)와 NFR-004(좌석 상태 p99 300ms)를 지금 설계값으로는 지킬 수 없고, 재는 방법도 판정할 만큼 정밀하지 않다'에 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정했다. 방향은 소유자 결정(추천안 승인: 두 목표는 그대로 두고 설계를 바꾼다)이고, 기준값과 같은 세부는 추천 적용이다. 같은 검토의 중간-036(대기실 시계 보정이 CDN 캐시 응답의 낡은 `Date`를 쓴다)도 결정 5가 함께 다룬다) 2026-10-28(기술 검토 중간-102, 소유자 승인 '추천안 동의'): 결정 2 '비용'의 요청 요금(약 198달러 → 약 205달러)은 HTTP 단가로 셈한 값이다. 대기 상태 조회는 HTTPS라 HTTPS 단가(1만 건당 0.012달러)로 약 264달러에서 약 273달러로 읽는다. 늘어난 몫(약 3%)과 결정은 그대로다(docs/verification.md §1.2·§4). 2026-10-29(원문 확인): 캐시 층의 `Age` 처리는 CloudFront 안내서에서 찾지 못했다. 안내서는 '요청 때 동적으로 판단된 요청은 리전 캐시를 거치지 않는다'고 적고, Origin Shield 요금은 TTL 3,600초 미만 GET을 동적 요청으로 친다. 둘을 이으면 입장 임박 1초 파일은 리전 캐시를 건너뛸 가능성이 크다(해석, review/open-items.md 41번). 그러면 엣지가 Origin Shield로 넘기는 요청마다 Origin Shield 요금이 붙는다(docs/infra.md §11).
- **관련**: NFR-002, NFR-004, NFR-013, FR-007, FR-009, K4, ADR-0003, ADR-0005, ADR-0027(좌석 델타 WebSocket), ADR-0043, ADR-0058, ADR-0063, ADR-0065(결정 7), ADR-0079(결정 3·10·15), ADR-0104(도착 지연 지표), [docs/features/queue-admission.md](../features/queue-admission.md) §4·§11(Q-T47)·§12, [docs/features/seat-hold.md](../features/seat-hold.md) §7·§12·§13, [docs/frontend.md](../frontend.md) §1.4·§1.6·§3.3·§4.4.1·§5.1·§5.16·§5.17(FE-T32)·§6.3, docs/api/openapi.yaml(`QueueState`, 대기열 API 응답), docs/api/asyncapi.yaml(`ws.seat-delta`), [docs/architecture.md](../architecture.md) §7·§9.1, [docs/verification.md](../verification.md) §1.2·§3.1·§3.4·§4, [docs/observability.md](../observability.md) §4·§11, [docs/infra.md](../infra.md) §4.1, planning/02 NFR-002·NFR-004·NFR-013·FR-009, planning/01 §3.1·§5.2, planning/00-executive-summary, planning/03 §4, guide/02·guide/12·guide/17, wbs 0.2.3·2.2.2·2.6.1·2.6.4·2.10.6, [review/tech-review.md](../review/tech-review.md)(높음-24, 중간-036), review/open-items.md 41번

## 맥락

1. **NFR-002(입장 임박 대기자의 serving 반영 p99 2초)**: serving이 오른 때부터 화면에 보일 때까지 세 기다림이 더해진다.
   - 다음 대기 상태 파일이 만들어질 때까지 0~1초(1초 주기).
   - 엣지(CDN이 사용자 가까이에 둔 서버)에 남은 옛 파일의 캐시 수명 0~1초. 낡은 값 허용(`stale-while-revalidate=2`)이 걸리면 더 길다.
   - 브라우저의 다음 폴링까지 0~1.2초(1초 ±20%). 여기에 왕복과 그리기가 더해진다.
   - 셋이 고르게 퍼진다고 보면 p99가 약 2.7~2.8초, 최악은 약 3.3초다(모형 계산, 측정 아님. 검토 묶음 셋이 따로 계산해 같은 결론을 냈고, 이 ADR을 쓰며 몬테카를로 계산(무작위로 20만 번 뽑아 분포를 어림하는 계산)으로 다시 확인했다).
   - 단계별 지연 예산을 나눠 적은 곳이 없어 이 충돌이 드러나지 않았다. 로컬 측정에서부터 실패한다.
2. **NFR-004(좌석 상태 변경 → 다른 예매자 화면 p99 300ms)**: realtime-gw가 250ms마다 묶어 보내므로 묶음 대기만으로 p99 약 248ms다. 남은 약 52ms에 서버 처리·망·그리기가 들어가야 한다. 망 한쪽 지연 p99가 60~100ms(흔한 모바일 망 [가정])면 종단 p99가 약 300~330ms다. 그러면 '300ms 넘김 3분이면 감내 모드' 규칙이 평소에도 걸리기 쉽다.
3. **재는 방법**:
   - 대기실 시계 보정은 최근 8개 표본 가운데 왕복이 가장 짧은 표본의 `Date`를 쓴다(docs/frontend.md §3.3). 가장 빠른 표본은 대개 CDN 캐시 적중 응답이다. CloudFront는 캐시 응답의 `Date`를 바꾸지 않고 `Age`를 붙인다(검토 §9, 실제 응답 확인). 그래서 보정 시계가 캐시 나이만큼 늦게 잡힌다(중간-036).
   - `queue_reflect_ms`는 초 단위 `Last-Modified`와 초 단위 `Date`로 잰다. 두 번 버림한 오차가 각각 최대 1초라, 2초 목표를 판정할 정밀도가 없다.
   - `seat_delta_e2e_ms`는 묶음을 보낸 시각(`serverTimeMs`)부터 잰다. 그래서 묶음 대기(0~250ms)가 빠진다. 시계는 서버가 보내기만 하는 하트비트로 맞춘다. 그러면 시계가 망 한쪽 지연만큼 늦게 잡혀, 종단 지연이 그만큼 작게 나온다.

## 결정

1. **단계별 지연 예산 표를 둔다(추천 적용).** queue-admission §4와 seat-hold §7에 둔다. 측정이 목표를 넘으면 어느 단계가 넘었는지 이 표로 찾는다.

   NFR-002(입장 임박 구간, 목표 p99 2초):

   | 단계 | 지금 | 바꾼 뒤(예산) |
   | --- | --- | --- |
   | serving 전진 → 다음 파일 생성 | 0~1초 | 0~1초(생성 주기 1초 그대로) |
   | 파일 생성 → 엣지가 새 파일을 가짐 | 0~1초(낡은 값 허용이면 더) | 0.1초 이하 [가정](만료를 생성 시각에 맞춤, 결정 2) |
   | 엣지 → 브라우저의 다음 폴링 | 0~1.2초 | 0~0.6초(0.5초 ±20%) |
   | 왕복·그리기 | 0.05~0.2초 | 0.3초 이하 |
   | 합(모형 p99) | 약 2.7~2.8초 | 약 1.5~1.6초(최악 약 1.8초) |

   NFR-004(목표 p99 300ms):

   | 단계 | 지금 | 바꾼 뒤(예산) |
   | --- | --- | --- |
   | 홀드 Lua → 샤드 Pub/Sub → realtime-gw | 약 5~10ms | 10ms 이하 |
   | 묶음 대기 | 0~250ms | 0~100ms(결정 3) |
   | 묶음 만들기·보내기 | 수 ms | 10ms 이하 |
   | 망 한쪽 지연 | p99 20~100ms [가정] | p99 120ms 이하 [가정] |
   | Worker 해독·다음 프레임 그리기 | 20ms 이하 | 20ms 이하 |
   | 합(모형 p99) | 약 280~330ms | 약 130~190ms |

2. **NFR-002는 목표 p99 2초를 그대로 두고 입장 임박 구간의 설계를 바꾼다(소유자 승인, 세부는 추천 적용).**
   - **대상**: 그 구간의 첫 번호까지 예상 대기가 60초 이내인 구간이다(serving을 품은 구간 포함). 100만 명 기준 파일 2~3개, 약 1,700명이다.
   - **캐시 만료를 생성 시각에 맞춘다**: 원본은 그 파일의 생성 시각 + 1초(다음 생성 시각)를 `Expires`로 준다. `Cache-Control`에는 `public`만 두고 `max-age`·`stale-while-revalidate`는 넣지 않는다. S3 대체 원본 사본에도 같은 `Expires`를 메타데이터로 넣는다.
     - CloudFront는 `max-age`가 없으면 `Expires`의 시각까지 캐시하고(최소 TTL 0일 때), 둘이 다 있으면 `max-age`만 쓴다. 그래서 대기 상태 파일 경로의 캐시 정책은 최소 TTL 0으로 직접 만든다. 관리형 정책 CachingOptimized는 최소 TTL이 1초라 쓰지 않는다(AWS CloudFront 개발자 안내서 'Expiration', 'Managed cache policies', 2026-10-28 확인).
     - 검토 추천은 '`max-age`를 다음 생성 시각까지 남은 시간으로'였다. 그런데 `max-age`는 초 단위 정수이고, 그 층이 받은 때부터 세는 상대 시간이다. 남은 시간이 1초보다 짧으면 0이나 1밖에 쓸 수 없다. 엣지가 새 파일을 받는 때도 주기마다 조금씩 밀려 생성 시각과 어긋난다. `Expires`는 절대 시각이라 같은 뜻을 정확히 낸다. 엣지·리전 캐시·Origin Shield가 같은 `Expires`로 같은 순간에 만료하는지는 확인 필요다(review/open-items.md 41번).
     - 생성은 서버 시계로 매초 경계에 한다(생성 주기 1초 그대로). 엣지가 새 파일이 다 만들어지기 전에 받으면 옛 파일의 `Expires`가 이미 지났으므로, 다음 요청에서 다시 받는다.
   - **폴링**: 예상 대기 1분 이내는 0.5초(±20%)로 줄인다. 1~5분 5초, 그 밖 20초는 그대로다.
     - 폴링은 `fetch(…, {cache: "no-store"})`로 보내 브라우저 HTTP 캐시를 건너뛴다. 브라우저는 `Expires`를 초 단위 `Date`로 계산하므로, 같은 파일을 생성 뒤 최대 1초 더 내줄 수 있기 때문이다.
     - 이때 브라우저가 스스로 붙이는 `Cache-Control: no-cache`·`Pragma: no-cache`는 사전 요청을 만들지 않는다(Fetch 표준은 사전 요청 여부를 정한 뒤 이 두 헤더를 붙인다). CloudFront는 시청자 요청의 두 헤더를 무시한다(Fetch 표준, AWS 개발자 안내서, 2026-10-28 확인).
   - **그 밖 구간**: 지금 규칙(캐시 1초와 낡은 값 허용 2초, 거리별 캐시 수명은 Phase 2에서 정함) 그대로다.
   - **비용**: CDN 요청이 초당 약 1,700건 는다(100만 기준 약 5.3만 → 약 5.4만 건, 약 3%). 원본 요청은 그대로다(파일마다, 캐시 층마다 초당 1회 이하). 10만 명 로컬 측정의 도착률은 초당 약 7,600건에서 약 9,300건이 된다. 100만 명 70분 대기 조회는 약 2.2억에서 약 2.3억 건, 요청 요금은 약 198달러에서 약 205달러다.
   - **모형 계산**(측정 아님): 왕복 0.05~0.15초, 엣지가 새 파일을 받는 시간 0.03~0.08초 [가정]이면 p99 약 1.5~1.6초, 최악 약 1.8초다.
   - **그 밖 대기자 문구**: NFR-002의 '그 밖의 일반 대기자는 각자의 폴링 주기 + 1초 이내'는 지금 설계로도 맞지 않는다. 지터(최대 1.2배), 생성 주기 1초, 그 구간의 캐시 수명이 더해지기 때문이다. 그래서 '폴링 주기 × 1.2 + 생성 주기 1초 + 그 구간 캐시 수명(낡은 값 허용 포함) 안'으로 고친다. 이 문구는 설계 식으로만 확인하고 SLO(팀이 정한 서비스 품질 목표)로 재지 않는다.

3. **NFR-004는 목표 p99 300ms(변경 → 화면)를 그대로 두고, 묶음 간격을 250ms에서 100ms로 줄인다(소유자 승인, 값은 추천 적용 [가정, K4·S-T12에서 확정]).**
   - 한 연결에 보내는 묶음 하나에 그 연결이 구독한 구역을 모두 싣는다(이진 형식의 `sectionCount`). 바뀐 것이 없는 연결에는 보내지 않는다.
   - 비용: 연결마다 초당 묶음이 최대 4개에서 10개로 는다. 연결 5,000개면 최대 초당 5만 개다. 바이트는 변경 데이터가 같고 묶음 머리만 는다. 그래서 묶음 하나를 약 200B로 잡은 지금 상한(연결마다 초당 10개, 전체 초당 약 10MB, docs/architecture.md §9.1) 안이다. realtime-gw의 CPU는 S-T12에서 잰다.
   - 감내 모드의 기준(300ms 넘김 3분)과 동작(1초 묶음, 완화 SLO p99 1.5초)은 그대로다.
   - 모형 계산(측정 아님): 망 한쪽 지연 p99가 20~100ms면 종단 p99 약 130~190ms다. 250ms 묶음이면 같은 조건에서 약 280~330ms다.
   - 검토가 함께 든 '목표를 서버 송신까지 p99 300ms + 망 구간 별도로 나눈다'는 쓰지 않는다. 사용자에게 보이는 약속이 줄어든다.

4. **반영 지연을 밀리초 서버 시각으로 잰다(추천 적용).**
   - **대기 상태 파일**: 본문(`QueueState`)에 `generatedAtMs`(생성 시각, 밀리초)를 싣는다. 입장 임박 구간 파일에는 `servingSteps`(최근 5초 [가정]의 serving 전진 기록: [전진 시각(밀리초), 그때의 serving] 묶음)도 싣는다.
   - **`queue_reflect_ms`(NFR-002의 SLI: 실제로 재는 서비스 품질 값)**: '내 차례(serving ≥ 내 번호)를 화면에 그린 시각(보정 시계) − serving이 내 번호를 넘은 전진의 시각(`servingSteps`)'이다.
     - 사람마다 차례가 올 때 한 번 잰다. 대기실 표본(1%)과 상관없이 모두 보낸다(초당 약 28건). 좌석 화면으로 넘어가기 전에 `keepalive`로 보낸다.
     - 넘은 시각이 기록 밖이면(5초 넘게 파일을 받지 못함, 곧 '연결 확인 중') 재지 않는다. 숨긴 탭도 재지 않는다. 숨긴 탭은 최소 5초 간격으로 묻도록 정해져 목표 밖이다(ADR-0079 결정 3).
   - **서버 쪽 보조 숫자**: `admission_arrival_delay_seconds`(차례 → 입장 확정 요청 도착, ADR-0104 결정 6). 시계 보정 없이 서버 혼자 잰다. 올리는 쪽 망 지연이 더해져 반영 지연보다 조금 크다.
   - **`seat_delta_e2e_ms`(NFR-004의 SLI)**: 묶음 대기를 넣어 잰다.
     - 홀드 Lua가 샤드 Pub/Sub 메시지에 변경 시각(Redis `TIME`, 밀리초)을 싣는다.
     - realtime-gw는 묶음 머리에 `u16 maxWaitMs`(묶음 안에서 가장 먼저 바뀐 변경이 보내질 때까지 기다린 시간)를 싣는다.
     - 종단 지연 = 그린 시각(보정 시계) − (`serverTimeMs` − `maxWaitMs`). 그 묶음에서 가장 오래 걸린 변경을 기준으로 하므로 실제보다 조금 크게 잰다.

5. **시계 보정 표본 규칙을 고친다(추천 적용, 중간-036도 이것으로 다룬다).**
   - CDN이 캐시한 응답(`queue-files`, 캐시하는 공개 카탈로그 읽기)의 `Date`는 어느 화면도 쓰지 않는다. 그래서 `queue-files`와 S3 대체 원본의 `Access-Control-Expose-Headers`에서 `Date`를 빼고 `Retry-After`만 둔다.
   - 대기실은 본문에 `serverTimeMs`(밀리초 서버 시각)가 실린 대기열 API 응답(로비 입장·진입·입장 확정. 모두 캐시하지 않는다)만 표본으로 쓴다. 보정값 = `serverTimeMs` + 왕복 ÷ 2 − 받은 시각이고, 최근 8개 [가정] 가운데 왕복이 가장 짧은 표본을 쓴다. 보정 시계는 '그 표본의 서버 시각 + 단조 시계(`performance.now()`)로 잰 경과'로 계산한다. 기기 시계가 그사이 바뀌어도 흔들리지 않게 하려는 것이다. 대기 중에 다시 연 탭은 입장 확정 전까지 대기열 API를 부르지 않으므로, 보정값을 30분 [가정] 동안 브라우저 저장소(`peaket.clock`)에 두고 쓴다. 값이 없으면 다음 대기열 API 응답까지 반영 지연을 재지 않는다.
   - 좌석 화면은 WebSocket 왕복으로 맞춘다. 브라우저가 연결 직후와 60초 [가정]마다 `TimeSync{u64 clientTimeMs}`(type 18)를 보내면, 서버는 `Heartbeat`에 `u64 echoClientTimeMs`를 실어 돌려준다. 브라우저는 왕복을 재서 보정한다. 서버가 보내기만 하던 하트비트는 망 한쪽 지연만큼 늦게 잡혔다.
   - 그 밖의 화면(홀드 남은 시간 등)은 캐시하지 않는(`no-store`) `api` 응답의 `Date`(초 단위)를 써도 된다.
   - 남는 오차는 왕복이 한쪽으로 치우친 몫의 절반(대개 수십 ms [추정])과 표본 뒤 단조 시계의 흔들림(수십 ppm [추정])이다. 두 목표의 10% 안이다.

6. **검증을 더한다(추천 적용).**
   - **Q-T47(새)**: 로컬에서 입장 임박 구간의 반영 지연을 잰다. nginx 캐시가 원본의 `Expires`를 따르고(nginx 문서 확인, 2026-10-28) 그 경로에서 낡은 값 내주기(`proxy_cache_use_stale updating`)를 끈 설정으로, 합성 대기자 1,700명이 0.5초마다 묻는다. 같은 PC 시계로 재므로 시계 오차가 없다. 통과 기준은 p99 1.8초 [가정] 이하다(CDN 계층 몫 0.2초를 남긴다). 단계(생성 대기·캐시 나이·폴링 대기·왕복)를 나눠 성능 장부에 남긴다.
   - **S-T12**: '묶음 대기를 넣은 종단 지연'과 망 지연 주입(한쪽 p99 100ms [가정], 리눅스 `tc netem`)을 더한다. 통과 기준은 p99 300ms 이하다. realtime-gw의 초당 묶음 수와 CPU를 함께 적는다.
   - **FE-T32(새)**: 브라우저의 시계 표본 규칙을 본다. 시계를 3초 [가정] 어긋나게 한 기기에서 캐시 응답만 받는 동안 보정값이 바뀌지 않고, 대기열 API 응답의 `serverTimeMs`로만 바뀌는지 본다. `queue_reflect_ms` 계산은 가짜 시계 기준 ±20ms [가정] 안이어야 한다. 폴링에 사전 요청(OPTIONS)이 0인지도 본다.
   - docs/verification.md §3.4에 지연 백분위 판정을 더한다.
   - CloudFront 계층 동작은 선택 보정(`cloud-cdn`, docs/verification.md §6) 때 무료 범위 안에서 본다(review/open-items.md 41번).

## 검토한 대안

| 대안 | 기각 이유 |
| --- | --- |
| NFR-002 목표를 p99 3초로 고친다 | 약속을 낮추는 쪽이다. 설계를 바꾸면 CDN 요청 약 3%로 2초를 낸다. 2초의 근거(차례를 늦게 알면 입장 자리가 논다, planning/02 §3.3)는 그대로다 |
| `max-age=1`을 두고 폴링만 0.5초로 줄인다 | 엣지의 캐시 나이(0~1초)가 남아 p99 약 2.2초다 |
| `max-age`를 '다음 생성까지 남은 초'로 준다 | 초 단위 정수라 0이나 1밖에 못 쓰고, 상대 시간이라 엣지가 받는 때마다 만료가 밀린다 |
| 입장 임박 구간 파일을 캐시하지 않는다(원본 직행) | 원본 요청이 초당 약 3,400건 는다. 원본 요청을 파일 수로 묶는다는 설계(ADR-0003) 밖이다 |
| 직접 선택 공연에도 차례 직전 직접 확인(ADR-0043 방식)을 쓴다 | 입장 확정 API에 초당 수백 건이 더 온다. 화면의 앞 인원·진행 막대는 여전히 CDN 지연을 받는다. 자동 배정 공연에 이것을 둔 근거(봇과 같은 출발선)가 직접 선택 공연에는 없다. Q-T47이 실패하면 다시 본다 |
| NFR-004를 '서버 송신까지 p99 300ms + 망 구간 별도'로 나눈다 | 사용자에게 보이는 약속이 줄어든다. 100ms 묶음으로 종단 목표를 낼 수 있다 |
| 좌석 변경을 묶지 않고 바뀔 때마다 보낸다 | 프레임이 변경 수만큼 늘어 묶음의 이득(대역폭·CPU)을 잃는다 |
| 시계 보정에 `Date + Age`를 쓴다(`Age`를 노출) | 둘 다 초 단위라 정밀도가 ±1초 그대로다. 캐시 층마다 `Age`를 어떻게 다루는지도 확인 필요다 |

## 결과와 트레이드오프

- 두 목표를 바꾸지 않고 지연 예산 안에 든다(모형 계산). 측정이 목표를 넘으면 어느 단계가 넘었는지 예산 표로 찾는다.
- 반영 지연을 밀리초 서버 시각으로 재므로, 2초·300ms 목표를 판정할 정밀도가 생긴다.
- 대가:
  - CDN 요청이 약 3% 늘고, 100만 명 70분 기준 요청 요금이 약 7달러 는다.
  - 좌석 묶음 프레임이 최대 2.5배 늘어 realtime-gw CPU가 는다.
  - 계약이 바뀐다(`QueueState` 두 칸, 대기열 API 응답의 `serverTimeMs`, 좌석 델타의 `maxWaitMs`와 `TimeSync`, `queue-files` 노출 헤더). wbs 0.2.3에서 서버와 맞춘다.
  - 원본은 매초 경계에 맞춰 파일을 만들어야 한다. 서버 시계가 어긋나면 그만큼 만료가 어긋난다(노드 시계 오프셋 20ms 위생 경보, observability §5).

## 측정(2026-11-03, BUILD_ORDER PRF-085)

- **Q-T47 실패**: queue-svc(운영 코드, 대기 상태 파일 원본) 앞에 nginx 1.27 캐시(낡은 값 허용 없음, `proxy_cache_lock`)를 두고 serving을 200ms마다 올리며(초당 28번호) 차례 1분 안의 대기자 1,700명이 0.5초 ±20%로 3분 폴링했다(`pnpm --filter @peaket/queue-svc sim reflect`, 성능 장부 `2026-11-03-qt47-*-r1`. 대기자는 프로세스 넷, 예열 15초 뒤·끝 3초 전까지 넘은 번호 4,536개 모두). 반영 지연 p99는 제때 생성 2.48초, 0.3초 늦은 생성 2.22초로 기준 1.8초 [가정]을 넘었다. 제때 생성의 단계 p99는 생성 대기 1.00초, 캐시 나이 1.02초, 폴링 대기 1.50초, 왕복 0.42초다. 캐시가 `Expires`보다 50ms 넘게 늦은 요청에 낸 HIT가 제때 생성 55%(339,024건), 늦은 생성 93%(580,868건)이고 가장 늦은 것은 1초 가까이 늦었다. 그래서 '생성이 늦어도 옛 파일이 `Expires` 뒤에 다시 쓰이지 않는다'도 깨졌다. 처음 돌린 도구는 이 검사에 1초 여유를 두어 0으로 잘못 셌다(새 맥락 리뷰로 고침, 첫 결과는 장부에 넣지 않음).
- **원인(캐시 계층 몫)**: nginx는 `Expires`를 초 단위로 받아 그 초가 끝날 때까지 캐시를 살린다(만료 판정이 `valid_sec < now`). 원본이 요청마다 지금 초의 내용을 주는 따로 한 측정(`pnpm --filter @peaket/queue-svc sim nginx-expiry`, 장부 `2026-11-03-nginx-expiry-*-r1`)에서, `Expires`를 다음 초 경계로 주면 nginx는 같은 내용을 약 2초 냈다(받은 내용의 나이 최대 1.97초, 1초 넘은 응답 49%, 원본 요청 초당 0.6번). 그래서 매초 경계에 만드는 파일과 캐시의 다시 받기가 같은 경계에서 겹치고, 캐시가 옛 파일을 1초 더 든다. 같은 측정에서 `Expires`를 생성한 그 초로 주면 nginx는 다음 경계에 정확히 만료했다(나이 최대 0.97초, 원본 요청 초당 1.1번). 이 방법은 nginx의 버릇에 기대는 것이고, 표준(RFC 9111)대로면 `Expires`가 응답 시각 이하인 응답은 받자마자 낡은 것이라 다른 캐시는 아예 캐시하지 않을 수 있다. CloudFront의 동작은 41번이 모른다.
- **되돌릴 조건에 걸렸다**: 첫 항목의 'CDN 계층 몫'이다. 직접 확인 확대와 목표 3초 안, 그리고 이 측정이 새로 보인 안 가운데 무엇으로 할지는 소유자 결정으로 남겼다(docs/review/open-items.md 104번). 정하기 전까지 입장 임박 구간은 지금 규칙(`Expires` = 다음 생성 시각)을 그대로 쓴다.

## 되돌릴 조건

- Q-T47에서 p99가 1.8초를 넘으면 단계별 시간을 본다. 생성·폴링 몫이면 입장 임박 구간만 생성 주기를 0.5초로 줄이는 안을, CDN 계층 몫이면 직접 확인 확대나 목표 3초 안을 다시 본다.
- 선택 보정에서 CloudFront 계층이 `Expires`에 맞춰 만료하지 않는 것으로 나오면 위와 같이 다시 본다.
- S-T12에서 100ms 묶음의 realtime-gw CPU가 파드 한도의 70% [가정]를 넘으면 묶음 간격을 150ms로 늘리고 종단 지연을 다시 잰다.
- 어느 브라우저가 `cache: "no-store"` 폴링에 사전 요청을 붙이게 바뀌면(FE-T32) 다시 본다. 쿼리 문자열로 캐시를 깨는 방식은 CDN 캐시 키가 사람마다 갈라져 쓰지 않는다.

## 남는 한계

- 숫자는 모형 계산이다. CloudFront 계층의 실제 만료 동작, 엣지가 원본에서 새 파일을 받는 시간, 모바일 망 지연의 실제 분포는 재지 않았다.
- RUM은 보이는 탭의 차례 순간만 잰다. 숨긴 탭(최소 5초 간격)과 '연결 확인 중'인 사람은 목표 밖이다.
- 시계 보정 오차(수십 ms [추정])가 남는다. 로비에서 다시 연 탭에 저장한 보정값이 없으면, 셔플 결과를 받는 시각이 기기 시계의 오차만큼 어긋난다(이르면 404 뒤 다시 받기가 덮는다).
- 100ms 묶음은 묶음 머리 몫만큼 전송량을 늘린다.
- 먼 구간의 반영은 설계 식으로만 보고 SLO로 재지 않는다.
