# ADR-0372: 시험 먼저 쓰고 시험 리뷰로 고정한 뒤, 구현은 그 시험만 통과하면 합친다(2026-11-23)

- **상태**: 채택(2026-11-23, 소유자 지시). [ADR-0270](0270-independent-agents-per-role-test-first.md)·[ADR-0281](0281-implementation-first-independent-tests.md)의 역할 다섯(계획·시험·구현·리뷰·검증)과 정방향 차례, [ADR-0331](0331-trim-per-batch-checks-defer-kind.md)의 기능마다 하는 리뷰·틀린 구현 검사를 이 결정이 바꾼다. 역할을 서로 다른 에이전트가 맡는 규칙(ADR-0270 결정 1)과 완성 장부(ADR-0256), 기능 단위(ADR-0354)는 그대로다. 결정 3의 '구현 뒤의 리뷰는 하지 않는다'는 A등급 코드 기능에 한해 [ADR-0381](0381-agrade-post-impl-review.md)이 바꾼다(2026-11-23, 소유자 결정). 검증 없앰은 그대로다.
- **관련**: [docs/architecture.md](../architecture.md) §8.6, `tools/ci/roles-check.mjs`, 계획 `docs/review/plans/FIX-roles-tdd.md`
- **관련 ID**: 없음(진행 절차만 바꾼다)

## 맥락

- 2026-11-16부터 기능 하나는 계획 → 구현 → 시험 → 리뷰 → 리뷰 반영 → 검증 → 기록으로 갔다(정방향, ADR-0281). 시험은 구현 뒤에 썼고, 구현 뒤에 리뷰와 틀린 구현 검사(검증)를 따로 돌렸다.
- 2026-11-23 첫 기능 웨이브에서 기능마다 구현 뒤 리뷰·검증이 가장 긴 대기였다. 리뷰 지적이 시험과 구현을 다시 돌게 했고, 검증은 통합 시험 전체를 다시 돌려 Docker 잠금을 오래 잡았다.
- 같은 날 소유자 지시: "TDD로 할텐데 테스트 작성후 테스트 리뷰만 하면 그 리뷰의 피드백만 통과하면 테스트는 고정, 그 이후 구현은 테스트만 통과하면 되고 통과한 이후의 리뷰는 안할게요." 감독의 물음에 두 가지를 더 답했다. 검증 역할도 없앤다. 이미 진행 중인 기능에도 바로 적용한다.

## 결정

### 1. 차례

- 코드 기능은 **계획 → 시험 → 시험 리뷰 → (지적 반영) → 시험 고정 → 구현 → 게이트 → 기록·합치기**로 한다. TDD(시험 주도 개발: 시험을 먼저 쓰고, 그 시험을 통과하도록 구현하는 방식)다.
- 계획은 지금과 같다. 장부로 범위를 뽑고, 지시서를 만들고, 정본 빈칸을 구현 전에 정한다. 계획은 시험이 기대할 공개 인터페이스(함수·API·이벤트·화면의 모양)도 정한다. 구현 전에 시험을 쓰려면 그 모양이 먼저 있어야 하기 때문이다.
- 시험 담당은 구현 전에 계획·지시서·정본으로 시험을 쓴다. 단언 값은 정본에서 가져온다. 기준 트리(기능 가지의 시작 커밋)에서 새 동작의 시험이 실패하는 것을 보고, 돌린 명령과 결과를 계획 파일 '실패 확인' 절에 남긴다.

### 2. 시험 리뷰와 고정

- 시험도 구현도 맡지 않은 리뷰 담당이 시험의 바뀐 부분·계획·지시서·정본·장부만 보고 시험을 리뷰한다. 결과는 계획 파일 '리뷰' 절에 적는다(`Role: review`). 보는 것은 다음과 같다.
  - 판정 기준과 시험 단언의 대조(이름만 달고 판정 기준을 단언하지 않는 시험이 없는지)
  - 장부 범위에 빈칸과 'ID만'이 없는지(`node tools/ci/ledger.mjs --batch <기능> --require`)
  - 위험 등급별 실패 상황. A등급(돈·좌석·대기 순번)은 경계값 양쪽, 되돌림, 장애 주입 시험이 있는지
  - §8.6 4의 '자주 놓친 결함' 목록과 시험 안티패턴(초록인데 아무것도 검증하지 않음, 고정 대기, 내부 업무 로직 모킹)
- 지적은 시험 담당이 고친다(`Role: review-fix`, `Fix-By: test`). 리뷰 담당이 반영을 확인해 '리뷰' 절에 적으면 **시험은 고정된다.**
- 고정 뒤 시험을 바꿔야 하면(구현 중 시험이 정본과 어긋나 보일 때) 구현 담당은 계획 파일 '시험 이의' 절에 적고 그 항목을 멈춘다. 감독이 시험 담당에게 넘기고, 시험 담당이 고친 부분은 다시 시험 리뷰를 받은 뒤 고정된다. 시험 파일을 바꾼 마지막 시험 쪽 커밋 뒤에는 늘 시험 리뷰 커밋이 있어야 한다.

### 3. 구현과 합치기

- 구현 담당은 고정된 시험이 통과할 때까지 구현한다. **구현 담당은 시험을 고치지 못한다**(소유자 지시 2026-11-23 "구현담당은 테스트를 고치지 못해요"). 시험 파일을 더하거나 고치거나 지우거나 옮기지 않고, 시험을 건너뛰게 하는 표시(`skip`·`only`·`todo`)나 시험 설정(시간 한도, 대상 목록)도 바꾸지 않는다. 시험이 틀려 보이면 결정 2의 '시험 이의'로만 다룬다. `roles-check.mjs`는 구현 커밋과 `Fix-By: impl` 커밋이 시험 파일을 바꾸면 실패로 잡는다.
- **구현 뒤의 리뷰와 검증(틀린 구현 검사, 판정 기준과 단언의 사후 대조)은 하지 않는다.** 그 대조는 시험 리뷰가 구현 전에 한다.
- 게이트는 지금과 같다. 시험 통과, 그 기능이 닿는 CI 잡, 장부 `--require`, 린트, 문서 점검, 역할 확인(`roles-check.mjs`)을 통과하면 기록하고 `develop`에 합친다.
- 버그를 찾으면 지금처럼 시험 담당이 재현 시험을 먼저 쓴다. 그 재현 시험도 짧게 시험 리뷰를 받은 뒤 구현 담당이 고친다.

### 4. 진행 중인 기능(2026-11-23 기준)

- 구현과 시험이 다 있는 정방향 기능(`Batch-Order: impl-first`)은 남은 리뷰·검증을 하지 않고 게이트 → 기록 → 합치기로 간다. 이미 나온 리뷰 지적 가운데 고친 것은 그대로 둔다. 열린 지적 가운데 높음·보안은 시험 담당이 재현 시험을 쓰고(그 시험만 시험 리뷰), 구현 담당이 고친다. 나머지 열린 지적은 갈래 정리 목록에 넘긴다.
- 구현은 있고 시험이 아직인 기능은 시험 → 시험 리뷰 → (시험이 실패하면 구현 고침) → 합치기로 간다.
- 구현 전인 기능은 결정 1의 차례로 한다. 새 기능의 계획 커밋에는 `Batch-Order` 꼬리말을 달지 않는다. 시험 먼저가 기본이다.

### 5. 역할 확인(`roles-check.mjs`)

- 시험 먼저 코드 기능(꼬리말 없음): 계획·시험·리뷰·구현 커밋이 하나 이상씩 있다. 처음 나온 커밋끼리 계획 < 시험 < 리뷰 < 구현이다. 검증 커밋은 없어도 된다.
- 시험 고정: 시험 파일을 바꾼 마지막 시험 쪽 커밋(`Role: test` 또는 `Fix-By: test`) 뒤에 리뷰 커밋이 있다. 시험 먼저 코드 기능과 시험만 기능에 적용한다.
- 정방향 기능(`Batch-Order: impl-first`, 진행 중인 것만): 계획·시험·구현이 있으면 된다. 리뷰·검증은 없어도 되고, 있으면 지금의 차례 규칙을 따른다.
- 시험만 기능(`Batch-Kind: test-only`): 계획·시험·리뷰가 있으면 된다. 검증은 없어도 된다.
- 계획 파일의 '검증' 절은 검증 커밋이 있을 때만 요구한다. '리뷰' 절은 리뷰 커밋이 있거나, 리뷰가 꼭 있어야 하는 기능(시험 먼저 코드, 시험만)일 때 요구한다.
- 문서 기능(계획·작성·리뷰)은 그대로다.

## 결과

- 좋아지는 점: 구현 뒤의 리뷰·검증 대기와 통합 시험 재실행이 없어진다. 시험이 구현 전에 고정되므로 구현 담당이 시험에 맞춰 시험을 바꾸는 일이 구조적으로 막힌다.
- 잃는 점: 틀린 구현 검사가 없어져, 시험이 실제로 결함을 잡는지 구현으로 확인하지 않는다. 시험이 구현 전 트리에서 실패한다는 확인('실패 확인' 절)과 시험 리뷰의 판정 기준 대조가 그 자리를 일부 맡는다. 구현 코드를 사람이나 다른 에이전트가 읽는 리뷰도 없어져, 시험이 덮지 않은 곳(보안 설정, 로그에 개인정보, 성능)의 결함은 구간 마무리(SEG)의 관점별 리뷰(§8.6 4의 5)에서야 잡힌다.
- 그래서 구간 마무리의 관점별 새 맥락 리뷰(정확성, 동시 실행·장애, 보안, 화면과 서버 계약)는 그대로 둔다. A등급 기능은 시험 리뷰가 경계값·되돌림·장애 주입 시험을 꼭 확인한다.

## 고른 안과 버린 안

- (고름) 시험 리뷰 뒤 고정, 구현 뒤 리뷰·검증 없음: 소유자 지시 그대로다.
- (버림) 구현 뒤 검증만 남기기: 감독이 물었고 소유자가 '검증도 없앰'을 골랐다.
- (버림) 새 기능부터만 적용: 소유자가 '바로 적용'을 골랐다.
