# 기술 검토(시니어 개발자 관점)

- **독자와 용도**: 소유자와 리드 엔지니어가 설계의 모든 기술·기법·이론이 시니어 개발자 관점에서도 합리적인지 본 결과를 보고, 고칠 것을 골라 반영하며 진행을 적는다. 문서를 고치는 다음 세션도 이 문서를 따른다.
- **원문 출처**: 2026-10-27 기술 검토(소유자 요청 "이 프로젝트 설계 전체에 설계된 모든 기술과 기법, 이론이 모두 시니어 개발자 관점에서도 합리적으로 적용되었는지 모두 검토해주세요. 하나도 빠짐없이 고려해야해요."). 같은 날 소유자 전제("개발 양이 많지만 AI를 이용해서 빠르게 개발할수 있습니다. 합리성과 깊이, 역량을 보여주면 돼요.")를 반영한 2판이다. 검토 세션의 노트 폴더에서 소유자가 저장소로 옮겼다(§12).
- **기준 기획 버전**: v1.0.
- **쓰는 법**: 항목을 반영하면 본문을 지우고, 번호 자리에 '반영해 본문을 지웠다(날짜, ADR·R-번호)'는 한 줄만 남긴다. 다른 문서가 번호로 가리키므로 번호는 다시 쓰지 않는다. 문제와 판단은 그 ADR에 있고, 지운 본문은 git 이력에 있다(2026-10-27 소유자 제안). 하지 않기로 하면 본문을 두고 '상태: 하지 않음(날짜, 이유)'을 적는다. 결정은 ADR과 review/consistency-review.md(R-번호)에 남기고, 값은 정본 문서에 넣는다. 새 판단(소유자 제안, 다시 본 판정)은 §12 진행 기록에 날짜순으로 더한다. 부록 A·B와 원자료는 저장소 밖에 있다(§11).
- **상태**: 모든 항목을 반영했다(2026-10-28). 2026-10-27에 높음-02·03·07, 중간-077·090, 낮음-041·043을 반영했고(ADR-0095~0099), 2026-10-28 소유자가 "나머지 건수들은 모두 추천안에 동의합니다. 그렇게 모두 수정해주세요."라고 정해 남은 319건(높음 23·중간 111·낮음 185)을 추천 수정대로 정본에 반영했다(ADR-0100~0137, review/consistency-review.md R-118~R-155, 00-summary 질문 61). 새 결정이 필요한 27건은 ADR-0100~0126, 문서만 고친 292건은 등급·영역별 묶음 ADR-0127~0137에 문제와 결정을 남겼다. 반영한 항목은 본문을 지우고 번호 자리에 한 줄만 남겼다(지운 본문은 git 이력의 2026-10-27·28판에 있다). §12.1~§12.3은 진행 기록이라 남겨 둔다.

- **잘못 적용**: 설계대로 만들면 동작하지 않거나, 사실·계산이 틀렸거나, 다른 결정과 부딪친다.
- **근거 부족**: 왜 골랐는지 문서에 근거(대안 비교, 측정 계획)가 없다.

### 소유자 전제 반영(2026-10-27)

소유자가 "개발 양이 많지만 AI를 이용해서 빠르게 개발할 수 있습니다. 합리성과 깊이, 역량을 보여주면 돼요"라고 알려 주어 판정을 다시 봤다.

- **거둔 것**: 이유가 개발량·일정(1인이 감당하기 어렵다, WBS 일수가 모자란다, 번역 비용)뿐이던 판정.
  - '과함' 90행 가운데 26행을 '조건부'로 바꿨다. 저장소 14개, Module Federation, Flink, 주문 이벤트 소싱, 4개 언어, 월 파티션, Iceberg, 오퍼레이터 수, 좌석맵 에디터 직접 구현, Game Day 26종 등이다.
  - 일정 조건만 붙었던 '조건부' 3행을 '합리적'으로 바꾸고, 4행은 조건만 고쳤다.
  - 높음-01(증명 순서와 범위)·04(저장소 14개)·09(4개 언어)는 중간-111~113으로 내렸다. 번호는 비워 두어 1판의 번호가 그대로 통한다.
  - 높음-05(Module Federation 부분)·07(Flink)은 추천을 '빼자'에서 '남기되 이유와 비교를 증거로 남기자'로 바꿨다. 높음-07은 같은 날 소유자 질문으로 잡마다 다시 따져, 추천을 'Flink를 빼고 단순한 길을 기본으로 두되, 그 길이 한계에 닿는 지점을 재서 바꿀 조건으로 적자'로 다시 바꿨다(§12.3). 소유자가 이 B안으로 정해 ADR-0099로 반영했다.
  - 중간-001·006·010·011·012·016·017·039와 높음-11·낮음-092의 한 구절도 같은 기준으로 고쳐 썼다.
- **그대로 둔 것**: 요구사항에 비해 풀 문제가 없거나, 같은 일을 하는 장치가 둘이거나(관제 콘솔의 실시간 통로 둘), 이유가 사라졌거나(파트너 tRPC), 사실·계산이 틀렸거나(MongoDB 백업), 다른 결정과 부딪치는 판정. 개발이 빨라져도 면접관은 '왜 이것인가'를 묻는다. 설계 결함(높음-10~29)도 그대로다. 1인 프로젝트에서 2인 승인이 자기 확인이 된다는 한계도 그대로다(AI는 두 번째 승인자가 아니다). 시연 방법은 §12의 소유자 제안을 본다.
- **판정 기준 한 줄**: 깊이는 기술의 수가 아니라 기술마다 '왜 이것인가(대안 비교) · 얼마나 나은가(측정) · 언제 바꾸나(바꿀 조건)'가 적혀 있는지로 보인다. 이 셋이 적힌 기술은 많을수록 강점이고, 빠진 기술은 많을수록 약점이다.

## 1. 총평

### 잘된 것: 핵심 경로의 기법 선택은 시니어가 봐도 맞다

100만 명이 한꺼번에 몰리는 순간을 버티는 핵심 경로는 기법을 잘 골랐다.

- **대기열**: 번호표를 Redis `INCR`(숫자 하나를 끼어들기 없이 1씩 올리는 명령) 한 번으로 나눠 주고, 버려진 번호는 결번 비트맵(빠진 번호를 칸 하나로 표시하는 표)으로 건너뛴다. 대기 상태는 1초마다 파일로 만들어 CDN(사용자 가까이에서 같은 응답을 대신 나눠 주는 캐시 서버)이 나눠 주게 해, 새로고침 대부분이 원본 서버까지 오지 않는다.
- **좌석**: 홀드(결제 전에 좌석을 잠시 잡아 두기)를 Redis Lua 스크립트(여러 명령을 끼어들기 없이 한 번에 실행)로 처리하고, 마지막에 DB의 부분 유일 인덱스(조건에 맞는 행은 하나만 허용하는 규칙)로 같은 좌석이 두 번 팔리는 것을 한 번 더 막는다.
- **한 곳에서만 도는 일**: 입장 제어처럼 하나만 돌아야 하는 루프는 쿠버네티스 Lease(잠깐 빌리는 이름표)와 세대 번호(펜싱 토큰: 옛 리더가 늦게 쓴 값을 거르는 번호)로 맡긴다.
- **결제**: 토스페이먼츠 2단계(결제창 인증 → 서버 승인), Saga(여러 서비스에 걸친 일을 단계로 나누고 실패하면 앞 단계를 되돌리는 방식), 멱등키(같은 요청이 두 번 와도 한 번만 처리하게 하는 열쇠), '결과 모름' 조회를 갖췄다.
- **시간 초과·준비 확인·재시도**를 층마다 따로 정했고, 용량 계산(architecture §9)은 다시 계산해도 맞았다.

다만 높음 몇 건(높음-11·15·24)은 이 기법들의 **세부값과 경계**(지연 예산, 고비 단계 뒤의 처리, '불렀지만 아직 안 온 사람' 계산)에서 나왔다. 기법을 바꿀 일은 아니고 값과 규칙을 고칠 일이다.

### 문제가 몰린 곳 셋

1. **이유가 빠졌거나 같은 일을 두 번 하는 구조**(높음-03·05~08, 중간 '나' 묶음. 높음-03은 2026-10-27 반영, ADR-0097).
   - '과함' 64행 가운데 23행, '근거 부족' 128행 가운데 31행이 부록(원문 학습 지도) 대조에서 나왔다.
   - 여기에 드는 것: 같은 API에 WebSocket을 두 개 여는 관제 콘솔, 이유가 사라진 파트너 tRPC, 사실이 틀린 근거(MongoDB 백업), 단순한 대안과 비교하지 않은 선택(Flink, Iceberg, 월 파티션), 고른 ADR이 없는 Module Federation, 약속과 실제가 다른 '독립 제어 평면'.
   - 대부분 원문에서 '재구성'으로 이어받아, ADR이 '그 기술 안에서의 선택'만 비교하고 '그 기술 없이'는 비교하지 않았다. 오늘 ADR-0092에서 소유자가 쓴 잣대를 그대로 대면 된다.
   - 쇼케이스로 남길 기술은 그렇다고 밝히고, 단순한 대안을 기준선으로 함께 잰다. 그러면 그 비교가 곧 깊이를 보이는 증거가 된다.
2. **핵심 증거의 실험 설계**(높음-02, 2026-10-27 반영, ADR-0096). 100만 외삽(한 PC에서 잰 확장 곡선), 서비스 분리 효과(중간안 없음), v0 대비 개선(일부러 약하게 만든 v0)의 실험이 결론을 받치기에 약하다. 개발이 빨라질수록 포트폴리오를 가르는 것은 이 증거의 질이다.
3. **구현 전에 잡을 설계 결함과 계산·사실 오류**(높음-10~29).
   - 판매 일시정지가 새로 뜬 파드에 안 걸린다.
   - 입장 제어가 같은 빈자리를 여러 번 부른다.
   - 결제 정지가 스스로 풀리지 않고, 발권이 실패하면 바로 환불한다.
   - 미결제 주문이 끝나지 않고, 키 교체가 1인 1순번을 깬다.
   - 결제사 콘솔로 2인 승인을 우회할 수 있고, 승인 금액 칸이 int다.
   - 28일 예산을 15일 보존에서 계산하고, 법정 접속기록이 유실될 수 있으며, 작업 큐가 '유실 허용' 캐시에 있다.
   - NFR-002·004를 지금 설계로 못 지키고, 정규화가 초성 검색을 깬다.
   - CSP와 SEED가 부딪치고, WCAG 기준이 빠졌으며, 오탐 표본의 독립 전제가 깨진다.
   - 대부분 '추천 적용' 세부값에서 생겼다. 코드가 없는 지금 고치면 비용이 작다.

### 시니어 면접관이 볼 한 줄

AI로 많이 만들 수 있으니 기술의 수는 문제가 아니다. 면접관이 보는 것은 기술마다 '왜 이것인가, 더 단순한 방법과 무엇이 다른가, 그 차이를 쟀는가, 언제 바꾸나'다. 지금 문서는 핵심 경로에서는 이 넷이 대부분 있고, 원문 학습 지도에서 온 선택에서는 자주 빠져 있다. 빠진 칸을 채우는 것이 이번 수정의 중심이다.

## 2. 먼저 고를 순서(제안)

> 2026-10-28 소유자가 남은 항목을 모두 추천안대로 정해, 이 절의 순서와 고르는 방법은 지난 기록으로 남는다(질문 61, ADR-0100~0137).

1. **구현 전에 고칠 설계 결함**(높음-10~23·25·26). 방향을 고를 일이 거의 없고 추천 수정이 사실상 하나라, '추천대로'로 한 번에 반영할 수 있다. 다만 높음-15는 NFR-006 문구가, 높음-22는 저장 방식(가·나·다 중 하나)이 바뀌니 확인한다.
2. **이유와 증거**(높음-05·06·08, 중간-010~026. 높음-02·03·07은 2026-10-27 반영). 기술을 남기든 빼든, 대안 비교·측정·바꿀 조건을 ADR로 남긴다. 남기는 쪽을 고르면 '단순한 기준선과 함께 재기' 작업이 WBS에 더해진다.
3. **목표 숫자와 시험 기준**(높음-24·27·28·29). NFR 문구나 합격 기준이 바뀌거나 안을 골라야 한다.
4. **중간·낮음**(소유자 전제로 내린 중간-111~113 포함). 영역별로 묶어 정합성 점검처럼 한 번에 고친다. 낮음 대부분은 문장·표·작은 값 수정이다.

**고르는 방법**: 번호로 말하면 된다. 예: "높음 10~23은 추천대로, 22는 나안, 중간-113은 가안". '추천대로'로 고른 것은 문서에 '(추천 적용, 날짜)'로 표시해 반영하고 00-summary §6 목록에 올린다. 번호(ADR·R-·질문·open-items)는 반영할 때 그때의 마지막 번호를 확인해 정한다.

## 8. 확인 필요(원문을 확인하지 못한 외부 사실·법령)

판정에 쓰였지만 이번에 원문을 확인하지 못한 것이다. 고칠 때 먼저 확인한다. 괄호는 후보 번호다.

> 2026-10-28 반영 때 원문으로 확인한 사실(예: NIST SP 800-57 표 1, PgBouncer 변경 기록, 정보통신망법·공연법 조문)은 각 ADR과 정본에 출처와 함께 적었다. 아래 목록은 2026-10-27 검토 때의 것이고, 확인하지 못해 남은 것은 정본에 '확인 필요'로, 정할 때가 있는 것은 review/open-items.md에 있다.

**클라우드·CDN·네트워크**
- AWS WAF Bot Control이 CloudFront 캐시에서 바로 응답한 요청도 검사(과금)하는지와 요청당 금액(A00-I09·A01, 중간-025). → 2026-10-29 확인: 금액은 그대로다(검사한 요청 100만 건당 0.60달러, Bot Control Common 월 1,000만 건 넘는 몫 1달러·Targeted 월 100만 건 넘는 몫 10달러, AWS 가격 자료 2026-09-14판). 캐시 응답의 검사·과금은 WAF·CloudFront 안내서·가격 페이지·DDoS 백서에서 찾지 못해 확인 못 함(open-items 50번에 남김).
- CloudFront가 `Expires`로 엣지 만료를 맞추는지, 리전 캐시가 `Age`를 반영하는지(A06-I04·A13-I02, 높음-24). → 2026-10-29 확인: `Expires`는 맞춘다(최소 TTL < `Expires` < 최대 TTL이면 그 시각까지 캐시, AWS 안내서 'Manage how long content stays in the cache'). `Age` 처리는 안내서에서 찾지 못해 확인 못 함. 다만 '요청 때 동적으로 판단된 요청은 리전 캐시를 거치지 않는다'는 문장과 Origin Shield 요금의 'TTL 3,600초 미만 GET은 동적'을 이으면 1초 파일은 리전 캐시를 건너뛸 가능성이 크다(해석).
- CloudFront 배포 설정 변경이 모든 엣지에 반영되는 데 걸리는 시간(A05-I23). → 2026-10-29 확인: AWS 안내서에 수치가 없다('모든 엣지에 동시에 퍼지지 않는다', 상태가 Deploying에서 완료 시각으로 바뀐다). 키 값 저장소 값은 AWS 블로그(2023-11)가 '몇 초 안에'라고 적었을 뿐 보장 수치는 아니다.
- MSK에서 IAM 인증과 클라이언트 할당량을 함께 쓸 수 있는지(A01). → 2026-10-29 확인: 쓸 수 있다. 사용자 이름은 `arn:aws:sts::<계정>:assumed-role/<역할>/<세션 이름>`이고 할당량은 브로커마다 센다(MSK 개발자 안내서 'Managing throughput with Kafka quotas', AWS 빅데이터 블로그). 세션 이름 고정이 전제다.
- 초당 20만 건 ES256 서명 검증에 드는 게이트웨이 CPU(A01, 측정 대상).
- Envoy Gateway에서 메서드를 좁힌 경로가 CORS 사전 요청(OPTIONS)을 404로 만드는지(A02-I16), 게이트웨이가 만드는 오류 본문에 `traceId`를 넣을 수 있는지(A02-I23). → 2026-10-29 확인: ①404가 된다. SecurityPolicy CORS는 대상 라우트가 OPTIONS를 받아야 동작한다(EG CORS 안내서). HTTPRoute CORS 필터는 v1.6.0부터 OPTIONS를 스스로 더하고, SecurityPolicy용 같은 처리(이슈 #7372)는 아직 열려 있다. ②`responseOverride` 본문은 Envoy 치환 형식 문자열로 넘어가(PR #6297, 소스) `%TRACE_ID%`를 넣을 수 있어 보인다. 실제로 채워지는지는 D-T43 PoC로 본다.
- 2026년 현재 Chrome이 CORS 사전 요청에 클라이언트 인증서를 싣는지(A07). → 2026-10-29 확인: 싣는다(소스 기준). 크롬 main의 `CredentialsMode::kOmit` 주석이 '인증서가 있으면 보내고 없으면 고르게 하려고 연결을 끊는다'는 버그(crbug.com/40089326)를 아직 적고 있고, 사전 요청은 그 모드를 쓴다. Fetch 표준은 그대로이고 whatwg/fetch #869도 열려 있다. 실제 기기 동작은 PoC ⑤.
- ElastiCache에서 Roaring 비트맵 모듈을 쓸 수 있는지(A13-I05). → 2026-10-29 확인: 쓸 수 없다고 본다. 지원 명령 목록에 모듈을 올리는 명령이 없고, 기본 명령 밖의 확장은 JSON·Bloom 필터·검색뿐이다(ElastiCache 안내서 'Supported and restricted ... commands'). 정본은 이미 Redis 문자열 비트맵으로 정했다(ADR-0137 낮음-135).
- AWS가 노드 기동 시간을 보장 수치로 공개하는지(A11, K9). → 2026-10-29 확인: 공개하지 않는다. EC2 SLA(2022-05-25판)와 EKS SLA(2026-03-20판)는 가동률만 약속한다.
- AWS KMS HMAC 키 교체 지원의 오늘 상태(A14). → 2026-10-29 확인: HMAC 키는 자동 교체도 즉시 교체(on-demand)도 안 되고 수동 교체만 된다(KMS 개발자 안내서 'Rotate AWS KMS keys'). 즉시 교체는 대칭 암호화 키(AWS 생성·가져온 키 재료)만 된다.
- ClickHouse Kafka Connect 최신 판, `flink-connector-aws` 목록, Glue 스키마 레지스트리 형식이 Flink 2.2에서 도는지(A15) 2026-10-27 ADR-0099로 Flink를 쓰지 않아 Flink 부분은 확인할 필요가 없어졌다.

### 12.1 2인 승인 시연 방법(소유자 제안 검토, 2026-10-27)

- **제안**: 2인 승인은 그대로 구현한다. 대상은 명령 3·5·6, 명령 4의 넓은 대역 차단, 지급 묶음, 수수료율 변경 등이다. 그리고 포트폴리오 데모에서 두 번째 승인을 통과시키는 버튼을 따로 둔다.
- **판단**: 시연이 쉬워야 한다는 방향은 맞다. 다만 그 버튼이 '두 번째 승인을 건너뛰는' 길이면 안 된다.
  - 서버에 '데모면 요청자와 승인자가 같아도 허용' 같은 분기를 두면, 그 분기는 운영 빌드에도 들어간다. 그러면 설정 하나로 켜지는 우회로가 된다.
  - 이것은 ASVS 13.4.2·15.2.3(운영에는 개발 기능을 두지 않는다)과 어긋난다.
  - 데모가 정작 보여야 할 '서버가 다른 계정인지 확인한다'를 보여 주지도 못한다.
- **추천**: 버튼을 '데모 승인자 계정으로 실제 승인을 하는 데모 도구'로 만든다.
  1. 데모 시드 데이터(시연용으로 미리 넣는 가짜 데이터)에 두 번째 관리 계정(데모 승인자, 역할 operator 또는 commander)을 둔다. 운영 데이터에는 만들지 않는다. 그 계정의 비밀번호·TOTP 비밀은 데모 비밀(로컬 `.env`, 커밋 금지)에만 둔다.
  2. 데모 막대에 '데모 승인자로 승인' 버튼을 둔다. 데모 막대는 이미 있는 장치다. 운영 묶음에 들어가면 CI가 실패한다(FE-T21).
     - 버튼을 누르면 데모 오버레이에만 배포되는 작은 데모 도우미가 그 계정으로 로그인·재인증하고, 보통의 승인 API를 부른다. 도우미는 보통 사용자처럼 공개 API만 쓰고 DB에는 닿지 않는다.
     - 서버의 검사(요청자 ≠ 승인자, 역할, 재인증, 10분 기한)는 운영과 똑같이 돈다.
     - 버튼이 없어도 되는 더 단순한 방법도 있다. 두 번째 브라우저 창(다른 프로필)에서 데모 승인자로 로그인해 직접 누르면 같은 장면이 된다.
  3. 같은 막대에 '요청자 본인으로 승인 시도'도 둔다. 서버가 거절하는 장면(요청한 사람은 두 번째 승인을 할 수 없다)을 함께 보이기 위해서다. 기한이 지난 승인의 거절도 데모 시계로 보인다.
  4. 감사 로그에는 두 계정이 따로 남고, 데모 환경 표시가 붙는다.
  5. 운영 배포에 데모 도우미가 들어가지 않게 배포 정책 검사를 둔다. 데모 전용 이미지와 네임스페이스는 운영 오버레이에서 막는다.
  6. 자동 시험은 Playwright 브라우저 맥락 둘(요청자·승인자)로 같은 흐름을 매번 돌린다.
- **남는 한계**: 두 계정을 한 사람이 쥐고 있다. 그래서 데모는 '시스템이 다른 계정을 요구한다'를 보일 뿐, '다른 사람이 확인했다'를 보이지는 않는다. planning/01 §5.2의 '1인 운영의 승인과 공급망의 한계' 행과 docs/devops.md의 1인 기간 한계는 그대로 둔다.
- **함께 볼 것**: 중간-077(멈추는 쪽인 판매 일시정지에 2인 승인이 걸려 대응이 늦다). 시연할 명령을 고를 때, '멈춤은 1인, 재개는 2인'으로 바꿀지도 함께 정하면 좋다.

### 12.3 Flink를 둘 가치와 대안(소유자 질문 검토, 2026-10-27)

- **질문**: "지금 현재 Flink를 사용하고 있는데요. 자바를 백엔드에 사용하지도 않는 프로젝트에서 Flink를 도입할 가치가 충분히 있을까요? 아니면 더 합리적인 대안이 있나요?"
- **사실**:
  - 백엔드는 NestJS(Node.js) 서비스 10개다. 자바로 짜는 코드는 Flink 잡 셋(`analytics-ingest`, `ops-rt`, `trust-reassess`)뿐이고, 이 잡들만 Gradle·Java 17·공용 Maven 패키지(`flink/common`)를 쓴다(docs/streaming.md §13).
  - 자바로 만든 완제품 서버는 이미 있다. Kafka(MSK), Kafka Connect에서 도는 Outbox 릴레이 Debezium(docs/data.md §4), Confluent Schema Registry다. 이것들은 설정만 하므로 언어가 문제 되지 않는다. Flink 잡은 다르다. DataStream API(연산자를 코드로 짜는 방식)로 쓰는 우리 업무 코드다(docs/streaming.md §2.2). 다만 Flink는 SQL과 Python(PyFlink)으로도 잡을 쓸 수 있어, 백엔드 언어 하나만으로 넣고 뺄 일은 아니다.
  - 일의 크기: 입력은 피크 약 1만 건/초, 시험 3만 건/초다(docs/streaming.md §11). 초당 20만 건의 진입은 queue-svc가 1초 단위로 미리 합쳐 보내므로 Flink까지 오지 않는다(ADR-0026). 상태는 `ops-rt` 약 0.5GB, `trust-reassess` 약 0.25GB다[추정].
  - 일의 모양: 원본 적재는 상태가 없다. 관제 실시간 표는 중복을 지우고 누적과 1초 칸을 센다. 재평가는 10분 안에 같은 기기나 같은 행동 요약값으로 들어온 서로 다른 사람을 센다. 세션 창과 CEP(순서 있는 사건에서 패턴을 찾는 기능)는 일부러 쓰지 않는다(ADR-0071 결정 6, docs/streaming.md §5.7).
  - Flink를 써서 생긴 장치: 빈 파티션이 워터마크(이 시각 전 사건은 다 왔다고 보는 표시)를 붙잡지 않게 하는 규칙(docs/streaming.md §3), Kafka 보관 7일보다 긴 누적을 다시 만드는 시작값 절차(docs/streaming.md §4.7, RB-34), 세이브포인트 호환 시험(D-T20), 대기 JobManager와 예비 TaskManager, 상태 버킷, 그리고 제공사가 시험하지 않은 판(Flink 2.2)에서 도는지 봐야 하는 ClickHouse 커넥터와 자바 MSK IAM 라이브러리의 PoC다. 남는 한계 가운데 '재시작 직후 누적이 잠깐 뒤로 간다', '시작값 경계를 넘는 재발행이 두 번 세어질 수 있다', '지표 규칙을 dbt(SQL)와 자바 두 곳에 둔다'도 여기서 나온다(docs/streaming.md §15, 높음-07).
  - 자원: 운영 설계의 Flink 파드는 합쳐 CPU 15.5개·메모리 31GiB다(docs/streaming.md §2.5)[가정]. 포트폴리오 PC는 24코어·메모리 약 32GB이고, 같은 PC에서 Kafka·ClickHouse·서비스·부하 발생기를 함께 띄운다(docs/verification.md §3.2).
- **판단**: 지금 요구에는 Flink를 둘 가치가 부족하다. '자바라서'가 첫 이유는 아니다. 첫 이유는 Flink가 다른 도구보다 확실히 잘하는 일을 이 설계가 쓰지 않는다는 것이다. 그 일은 초당 수십만 건이 넘는 입력, 수십 GB가 넘는 상태, 사건 시각 기준의 복잡한 창, 순서 패턴, 여러 흐름을 시간으로 맞붙이기(조인), 과거를 같은 상태로 다시 계산하기다. 남은 일은 세기와 합하기이고, 이 일에서는 Flink가 오히려 장치를 늘린다. 자바는 이 판단을 굳히는 둘째 이유다. 같은 규칙(가명 처리, 지표 규칙, `eventKey`, Avro 계약 클래스)이 TypeScript·SQL·자바 세 곳에 생기고, 빌드·시험·보안 패치·MSK IAM 클라이언트도 한 갈래씩 더 생긴다. 개발량은 소유자 전제대로 이유에 넣지 않았다.
  - 2판의 추천('남기고 단순한 기준선과 비교해 잰다')을 바꾼 이유: 잡마다 따져 보니, 단순한 길이 정확도와 부품 수에서 '같거나 낫다'를 측정 전에도 구조로 보일 수 있다(아래 표). 질 것이 보이는 비교를 하려고 Flink를 만드는 것은 소유자가 높음-03에서 정한 '기술을 끼워 맞추지 않는다'와 맞지 않는다. 그래서 단순한 길을 만들고, 그 길이 어디서 한계에 닿는지 재서 바꿀 조건으로 적는 쪽이 더 나은 증거다.
- **비교**:

- **추천(B안)**:
  1. **원본 적재 → TypeScript 적재 작업자(peaket-data)**: Confluent 공식 JavaScript 클라이언트(`@confluentinc/kafka-javascript`, librdkafka 기반)와 레지스트리 라이브러리(`@confluentinc/schemaregistry`)로 같은 Avro 계약을 읽는다. 서비스와 같은 가명 처리 라이브러리로 식별값을 바꾸고, ClickHouse 공식 Node 클라이언트(`@clickhouse/client`)로 브론즈에 쓴다. ClickHouse가 받았다고 답한 뒤에만 오프셋을 커밋하고, 삽입마다 `insert_deduplication_token`(토픽·파티션·첫 오프셋·끝 오프셋)을 붙여 다시 보낸 묶음을 ClickHouse가 거르게 한다. 지금처럼 '적어도 한 번'과 (파티션, 오프셋) 커버리지 대조를 쓴다. Flink 커넥터와 달리 묶음을 버리지 않는다. ClickHouse가 멈추면 소비를 멈췄다가 커밋한 곳에서 이어 간다.
  2. **관제 실시간 표 → 원시 사건 + 조회 시점 집계**: 실시간용 작업자(같은 코드, 다른 소비자 그룹·배포, 온디맨드)가 판매류·대기열·홀드·판정 사건을 `rt` 원시 표에 쓴다. ops-svc가 회차마다 0.5초에 한 번 SQL로 센다. `eventKey`로 중복을 지우고, 좌석은 마지막 판매 상태를, 퍼널은 주문·구매 세션마다 한 번을, 1초 칸은 `toStartOfSecond`로 센다. 규칙은 회차를 매개변수로 받는 ClickHouse 매개변수 뷰에 둔다. 늦게 온 사건도 버리지 않고 제 칸에 들어간다. 워터마크·허용 지연·시작값 절차·세이브포인트가 없어진다. 심장 박동(`rt-pulse`)은 신선도를 재려고 그대로 둔다. 정확해야 하는 판매 숫자는 늘 읽을 때 중복을 지우고, 읽기 비용이 크면 1초 칸만 미리 합산한다.
  3. **봇 재평가 → trust-svc 옆 TypeScript 작업자 + Redis(peaket-trust)**: 회차·기기와 회차·요약값 지문마다 '시각을 점수로 둔 정렬 집합'에 pid를 넣고, 10분보다 오래된 것을 지운 뒤, 서로 다른 pid가 문턱(5·20)에 닿으면 모두 후보로 낸다. 이 과정은 Lua 스크립트 하나로 원자적으로 한다. 후보 형식·`eventKey`·그림자 모드·격리 상한·trust-svc의 처리는 그대로다(docs/streaming.md §5.4~§5.6). trust-svc는 이미 같은 Redis로 기기 공유 수를 센다(docs/streaming.md §5.5).
  4. **같이 얻는 것**:
     - 자바 코드와 Flink 실행 기반(Operator, JobManager·TaskManager, RocksDB, 상태 버킷)이 없어진다.
     - MSK IAM 클라이언트가 TypeScript 한 갈래로 준다. 높음-26의 규칙(잡별 전용 역할과 고정 세션 이름)은 JavaScript 서명 도구의 `generateAuthTokenFromRole`로 같게 적용한다[확인 필요, wbs 0.5.1 PoC].
     - 실시간 지표 규칙이 dbt와 같은 SQL이 되어, '실시간과 배치가 같은 지표 정의를 쓴다'(docs/features/analytics.md §1.2 원칙 3)에 가까워진다.
     - docs/streaming.md §15의 남는 한계 가운데 셋(시작값 경계의 재발행 중복, 재시작 직후 누적이 뒤로 감, 커넥터·자바 MSK IAM 확인)이 없어지고, 규칙 두 벌 문제는 SQL 한 언어로 줄어든다.
     - 신선도 어림은 누적 약 1.3초, 1초 칸 약 2.3초다[추정](반영 때 조회 시간 0.05초를 더해 약 1.4초·2.4초로 적었다, ADR-0099 결정 7). 생산 0.05초 + 소비자 묶음 0.25초[가정] + 비동기 삽입 반영 0.2초 + 조회 주기 0.5초 + 푸시·그리기 0.3초이고, 1초 칸은 끝난 칸만 보여 1초를 더한다. 지금 설계는 2.3초·3.9초다[추정](docs/streaming.md §4.5).
- **걸리는 점과 정할 것**:
  - 읽을 때 계산하는 비용: 대형 회차의 판매류 사건은 약 27만 개다(docs/streaming.md §11). 0.5초마다 회차마다 한 번 세면 한 번에 수십 ms로 어림한다[추정]. V-T12(초당 3만 건, 30분)에서 ClickHouse 조회 p95와 CPU를 함께 잰다. ops-svc는 회차마다 한 번만 계산해 여러 화면에 나눠 준다.
  - '적어도 한 번' 소비자: 커밋 순서, 재조정(소비자 그룹 안에서 파티션을 다시 나누는 일) 중 처리, 읽지 못하는 메시지 처리를 직접 짠다. 다른 서비스의 Kafka 소비자와 같은 공용 모듈로 두고, 클라이언트 선택은 wbs 0.5.1 PoC(kafkajs와 Confluent 공식 클라이언트 비교)에서 함께 정한다.
  - 실시간 원시 행의 식별값: 퍼널은 주문·구매 세션마다 한 번만 세야 해서 그 값이 행에 남는다. 가명으로 바꿀지, 생산자가 '처음 본 단계' 표시를 실을지 정한다. 지금 Flink 설계도 이 값들을 상태와 체크포인트(S3)에 들고 있다. 어느 쪽이든 데이터 분류표에 행을 더한다.
  - 보존: 원시 표는 적재 시각이 아니라 회차 종료를 기준으로 지운다. 중간-090이 짚은 '판매 기간이 보존 기간보다 긴 경우'를 같이 푼다.
  - 처리량: Node.js 소비자 하나는 한 스레드라, 파티션마다 얼마나 처리하는지 잰다. 토픽마다 파티션 12개[가정]라 소비자를 12개까지 늘릴 수 있다.
  - 포트폴리오: 'Flink를 썼다'는 줄이 빠진다. 대신 'Flink로 자세히 설계했다가(ADR-0071·0072) 잡마다 비교해 더 단순한 길을 골랐고, 그 길의 한계를 재서 언제 스트리밍 엔진으로 가는지 적었다'가 남는다. §0의 판정 기준('왜 이것인가 · 얼마나 나은가 · 언제 바꾸나')을 그대로 채운다.
- **바꿀 조건(B안에서 스트리밍 엔진으로)** [가정, 측정으로 숫자를 정한다]:
  1. 조회 시점 집계가 신선도 목표를 위협할 때: 회차당 조회 p95가 조회 주기(0.5초)의 절반을 넘거나, 온세일 중 ClickHouse CPU가 경보 기준을 넘을 때다. 먼저 1초 칸 미리 합산과 회차별 조회 묶기를 하고, 그래도 넘으면 스트리밍 엔진으로 간다.
  2. 순서 패턴(CEP)이나 세션 창이 필요해질 때: 예를 들어 개인정보 판단을 다시 해 순서 있는 서버 사건(홀드 시도 간격 등)의 계약을 새로 정할 때다. 그때는 Flink SQL의 `MATCH_RECOGNIZE`가 진짜 이유가 된다.
  3. 여러 흐름을 시간 기준으로 맞붙이는 실시간 기능이 생길 때: 예를 들어 결제·좌석·봇 신호를 합친 실시간 위험 점수다.
  4. 재평가 상태가 Redis 예산을 넘거나, 입력이 초당 수십만 건으로 커질 때다.
  - 그때 후보는 Flink SQL(관리형 포함)과 RisingWave다. 그 시점의 사실로 다시 비교한다.
- **측정(증거)**: V-T12~V-T15를 B안으로 돌린다. 기준은 그대로다(신선도 1분 p95 5초 미만, 누락률 0.1% 미만, 작업자 강제 종료 뒤 정답과 같음, 빈 파티션, ClickHouse 30초 정지). 여기에 입력을 3만 건에서 늘려 가며, 신선도 p95가 5초를 넘거나 ClickHouse가 포화되는 지점을 성능 장부에 남긴다. 그 값이 바꿀 조건 1의 숫자가 된다.

- **추가 비교: Kafka Connect + ClickHouse 머티리얼라이즈드 뷰(G안)와 B안(소유자 질문, 2026-10-27)**:
  - 질문: "Kafka Connect + ClickHouse Materialized View 와 B는 비교해보면 어떤게 나은가요?"
  - 판단: B가 낫다. G안은 부품을 나눠 보면 평가가 다르다. 머티리얼라이즈드 뷰(넣는 순간 도는 집계)는 B 안에서 '읽기 비용이 크면 미리 합산한다'로 이미 열어 둔 선택지이고, 중복에 안전한 숫자에만 쓸 수 있다. Kafka Connect는 이 설계의 가명 처리·거절 기록 규칙과 맞지 않는다.
  - '정확히 한 번'이 막는 범위: ClickHouse Kafka Connect 싱크(1.7.0)의 정확히 한 번은, 다시 보낼 때 똑같은 묶음을 만들어 ClickHouse의 같은 묶음 거르기에 맡기는 방식이다(진행 상태는 KeeperMap 표에 둔다). 그래서 'Kafka 메시지 한 줄은 ClickHouse에 한 번만 들어간다'까지 막는다. Kafka 안에 같은 사건이 두 줄 있으면 둘 다 들어간다. 이 설계는 그런 중복을 전제로 한다. 카프카 트랜잭션을 쓰지 않고 소비자가 중복을 처리하며(ADR-0026 결정 3), Debezium FAQ도 Kafka Connect가 갑자기 멈췄다 다시 뜨면 같은 사건을 다시 보낸다고 적는다. 뷰는 넣는 묶음만 보고 계산하므로 이 중복을 그대로 더한다.
  - 숫자별로 보면 이렇다.

| 숫자 | 뷰로 미리 합산 | 이유 |
| --- | --- | --- |
| 판매 좌석, 지금 확정된 주문, 유효한 티켓 | 조건부로 된다 | 좌석·주문·티켓마다 마지막 상태를 남기는 집계(`argMax`)는 같은 사건이 두 번 와도 결과가 같다. 다만 '마지막'을 가르는 값이 생산자가 붙인, 늘어나기만 하는 순번이어야 한다. Kafka 위치로 가르면 다시 보낸 옛 사건이 더 늦은 위치로 들어와 이긴다 |
| 퍼널 단계(주문·구매 세션마다 한 번) | 된다 | 고유 개수 세기(`uniqExact`)는 중복에 안전하다. 행에 주문·구매 세션 값이 있어야 한다(위 '실시간 원시 행의 식별값') |
| 1초 칸(홀드 결과, 판정 종류) | 된다 | 칸마다 `eventKey`의 고유 개수로 세면 중복에 안전하다 |
| 판매 금액 | 안 된다 | 합계는 같은 사건을 두 번 더한다. `eventKey`로 중복을 지운 뒤 더해야 하는데, 뷰는 들어온 묶음만 본다 |
| 대기열 진입·입장·빠진 번호 누적 | 안 된다 | 같은 이유다. 1초 집계 메시지(`QueueAggregate`)를 다시 받으면 두 번 더한다 |

  - 그래서 G안도 판매 금액과 대기열 누적은 원시 행을 읽을 때 중복을 지워 세야 하고, 이 부분은 B와 같아진다. 남는 차이는 적재를 Kafka Connect로 하느냐 TypeScript 작업자로 하느냐다.
  - 적재를 Kafka Connect로 하면 걸리는 점:
    1. 원본 적재의 가명 처리(회차 키를 KMS에서 받아 메모리에만 둔다, docs/features/analytics.md §3.3)를 기본 변환(SMT, Kafka Connect가 레코드를 옮기며 고치는 작은 단계)으로 할 수 없다. Apache Kafka의 기본 변환 16종 가운데 가리기(MaskField)는 빈 값이나 정해 둔 값으로 덮을 뿐이다. 그래서 자바로 변환기를 짜야 하고, 자바 업무 코드를 없애려던 목적이 다시 깨진다.
    2. 실패 레코드: 데드 레터 토픽은 처리에 실패한 메시지를 그대로 옮긴다. 그러면 가명 처리 전 식별값이 다른 토픽에 한 벌 더 생긴다(ADR-0072가 기각한 방식). 데드 레터를 끄면(기본값) 레코드 하나 때문에 작업이 멈춘다. 지금 설계는 위치만 `bronze.brz_rejected`에 남기고 이어 간다(docs/streaming.md §6.3).
    3. 토픽 하나가 표 하나로 간다. 한 토픽에 실린 여러 종류의 레코드(심장 박동, 구매 세션 시작·종료)는 변환이나 뷰로 다시 나눠야 한다.
    4. MSK IAM은 자바 클라이언트를 쓰므로 높음-26의 규칙이 그대로 걸린다. Debezium이 도는 Kafka Connect에 함께 두면 분석 싱크의 문제(재조정, 자원 다툼)가 거래 이벤트 릴레이에 번질 수 있어, 클러스터를 따로 두는 편이 낫다. AWS가 운영해 주는 Kafka Connect(MSK Connect)도 있다.
    5. 원본 적재에는 결국 TypeScript 작업자(또는 자바 변환기)가 필요하다. 그러면 적재 길이 둘이 된다. B는 같은 코드에 설정만 달리해 원본 적재·실시간·행동 신호를 모두 싣는다.
  - 뷰를 쓰면 걸리는 점:
    1. 뷰는 넣는 순간에만 계산한다. 규칙을 고치면 지난 숫자는 다시 넣어(`INSERT … SELECT`) 채워야 한다. 읽을 때 계산하면 고친 규칙이 지난 숫자에도 바로 맞는다. 판매 기간이 몇 주인 회차에서는 이 차이가 크다.
    2. 뷰에서 오류가 나면 기본값(`materialized_views_ignore_errors` 끔)에서는 원본 표의 삽입도 실패로 돌아오고, 이미 원본 표에 쓴 것을 되돌리지도 않는다. 관제용 뷰를 브론즈 표에 걸면 관제 숫자의 버그가 분석 원본 적재를 멈출 수 있으니, 쓰더라도 실시간 원시 표에만 건다.
  - 봇 재평가: 넣을 때 도는 뷰는 들어온 묶음만 보므로 '10분 안에 5명'을 셀 수 없다. 주기적으로 다시 계산하는 뷰(refreshable MV, 예: 10초마다)와 Kafka로 내보내는 표(Kafka 엔진, MSK IAM 지원)로 흉내 낼 수는 있다. 그러나 봇 판단이 분석 저장소의 부하와 장애에 묶이고, 다시 계산할 때마다 문턱을 넘은 사람 전체를 다시 낸다. B의 Redis 작업자가 낫다.
  - G안이 더 나은 경우: 적재하면서 바꿀 일(가명 처리 등)이 없고, Kafka 위치 말고는 중복을 가릴 필요가 없는 데이터(바뀌지 않는 로그 같은 것)를 많이 싣는 경우다. 적재 코드를 짜지 않아도 되고, 싱크가 위치 기준 정확히 한 번을 준다.
  - B에 들이는 것: 위 표에서 '된다'인 숫자는, 읽기 비용이 커지면 실시간 원시 표에 건 뷰로 미리 합산한다(바꿀 조건 1의 첫 단계). 판매 금액과 대기열 누적은 계속 읽을 때 중복을 지운다. 좌석·주문의 마지막 상태를 뷰로 모으려면 생산자가 늘어나기만 하는 순번을 실어야 한다(계약 보강).
