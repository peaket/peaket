- **묶음이 넘치면 503(무거운 부하, 1만 1회, 11:01:55~11:03:55)**: 요청 58,331건 가운데 검색 200은 1건, 검색 503은 28,357건(몰림 13,915·무작위 14,442)이었다. `search_pool_saturated` 줄도 28,357건(모두 `pool-timeout`)이다. 게이지는 94개 표본 가운데 81개가 0이 아니었다(최대 322). **넘치면 503이 설계대로 나온다.**

- k6 끝 코드와 `verdict: measured`는 판정에 쓰지 않았다(계획 §6).

### 5.1 읽는 줄 수

`EXPLAIN (ANALYZE, BUFFERS)`를 `core_search` 로그인으로 쉬는 DB에서 돌렸다. 어댑터의 `#nameRows`·`#gradedTargets`·`#documentsFor`와 같은 질의·같은 차례로 쟀고, 등급은 `nameGradeOf`(사전 비교 값)로 매겼다. 괄호는 실행 시간이다.

## 6. 오염 회차가 무너진 까닭(측정 중 관찰. 고치지 않았다)

1. **DB는 빠르다.** 20k에 `log_min_duration_statement=30`을 걸고 가벼운 부하를 돌렸는데 30ms를 넘는 질의가 한 줄도 없었다. `pg_stat_activity`를 0.5초마다 읽은 값도 `active` 0~4, 가장 긴 질의 51ms였고, 연결 여럿은 7초 넘게 idle이었다. DB가 연결을 쥐고 있지 않다.
2. **core-svc 이벤트 루프가 멈춘다.** 오염 회차에서 `nodejs_eventloop_lag_p99`의 중앙값이 55~136ms, 최댓값 334~855ms였다(조용한 판정 회차는 21~27ms·최대 26~111ms). 힙은 부하 30초에 210MB → 675~812MB로 자랐고, 그 뒤 major GC가 돌며 100~600ms씩 멈췄다. 힙 상한 1024MB를 걸면 503이 30%대 → 6%대로 줄고 CPU는 97%가 됐다(§3.3 r4).
3. **새 경로 탓이 아니다.**
   - 두 글자 `바다`만 초당 20회 보낸 진단(새 경로를 타지 않는다)에서도 592건 가운데 445건이 503이었다.
   - `keysOf`를 끄고 지금(합친) 질의만 쓰게 한 진단은 더 나빴다(503 91.6·93.0%, p95 4.5·4.4초). 새 경로는 오히려 적게 읽는다(§5.1).
   - 조용한 창에서 같은 코드로 다시 잰 2만 r5~r7은 0% 503이다.
4. **남은 설명: 이 PC의 다른 갈래 부하 + 큰 힙의 GC.** 2만의 사전 색인과 후보 줄은 1만의 2배라 힙이 2배로 크고, major GC 한 번이 100~600ms다. 그동안 Node가 pg 콜백(연결 반환)을 처리하지 못해 100ms 연결 대기를 넘긴 요청이 503이 된다. 같은 시간에 다른 갈래의 vitest·변이 시험이 CPU를 나눠 쓰면 GC 정지가 더 길어진다. BAT-166 다시 재기 2(04:03~04:08, 새벽)는 이 정지가 짧아 통과했고, 이번 낮의 오염 회차에서는 재현됐다.
5. **판정 밖 관찰**: 20k 서버를 띄울 때 첫 검색이 0.7~2.2초 걸렸다(사전 색인 `#built()` 첫 계산). 무거운 부하에서는 11:02:07~09에 2초 남짓 연결이 거부됐다(동시 연결이 많을 때 listen backlog로 보인다).

## 8. 한계

1. **한 PC 한 프로세스**다(BAT-166 §7 1과 같다). 운영의 읽기 전용 복제본·여러 파드·CDN은 없다.
2. **이 PC가 측정 내내 조용하지 않았다.** 다른 갈래의 변이 시험·vitest 일꾼이 10:40~11:00에, node 일꾼이 11:20~11:30에 돌았다. 판정 회차는 그 사이의 조용한 창에서 잡았고, 오염 회차는 §3.3에 근거와 함께 뺐다. 판정 회차의 PC CPU는 9.5~23%였다.
3. **힙 상한 1024MB·`keysOf` 끔 진단은 판정 회차가 아니다.** 원인을 가르려고 조건을 바꾼 회차이고, 그 값으로 통과·미달을 말하지 않는다.
4. **예열 회차를 뺀 것**은 BAT-166이 회차 앞에서 PC가 조용해지길 기다린 것과 같은 셈법이다. 예열 회차의 503 폭풍은 JIT·사전 색인·첫 GC가 겹친 값이고, 운영 배포 직후의 위험으로는 따로 볼 일이다(§6 5).
5. 컨테이너는 이름마다 `docker rm -f -v`로 지웠고, 띄운 core-svc 프로세스는 PID로 끝냈다. Docker 잠금 폴더도 지웠다.
6. **사전 준비 게이지를 측정 중에 읽지 않았다.** 리뷰 RV-01이 제안한 `/metrics`의 `search_dictionary_entries` 확인은 하지 않았고, 1초 표본에도 넣지 않았다. 닫는 근거는 판정 회차 서버 로그의 `dictionaryVersion`(원천 판과 같은 값 → `#loaded` true)과 EXPLAIN 원자료 10,970줄이다(§1). 이 값은 게이지와 같은 상태를 보면서 어느 판을 읽었는지까지 남기지만, 측정 전에 절차로 확인하지 못한 흠은 남는다.
