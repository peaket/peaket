## 2. 명령

```bash
# 크기마다(10000·20000) 새 DB
docker run -d --name lane2-measure-pg-<크기> --cpus 4 --memory 4g -e POSTGRES_PASSWORD=… -e POSTGRES_DB=peaket -p 127.0.0.1::5432 postgres:18-alpine -c log_autovacuum_min_duration=0
PEAKET_DATABASE_URL=<슈퍼유저> node services/core-svc/scripts/migrate.mjs      # + 로그인 사용자 넷(roles.ts와 같은 문장)
PEAKET_ENV=local PEAKET_DATABASE_URL=<슈퍼유저> node services/core-svc/scripts/fill-search.mjs --count <크기>
psql -c "ANALYZE" -c "CHECKPOINT"                                               # 이번에 더한 CHECKPOINT
# 서버(위 §1 환경) → /ready 200 → 로그 search_reconciled를 기다린 뒤
docker run --rm --cpus 4 --memory 2g -v <결과 폴더>:/out -v loadtest/scenarios:/scn:ro -w /out grafana/k6:1.4.2 run -q \
  -e BASE=http://host.docker.internal:3001 -e CROWD_RATE=<20|200> -e RANDOM_RATE=<20|200> -e DURATION_S=<60|120> --out csv=/out/raw.csv.gz /scn/v1-search.js
```

셈법은 다음과 같다.

- **받는 쪽 p95**: k6 원본 CSV의 `http_req_duration`을 구간(`phase`)×경로(`route`)×상태로 나눠, 상태가 200인 것만으로 셌다.
- **503 비율**: 그 구간 검색 요청 전체(200·503·그 밖)에 대한 503의 비율이다.
- **그 밖 5xx**: 검색·자동완성의 503 아닌 5xx, 자동완성의 503, 연결 실패를 모두 더한 수다.
- **놓친 반복**: k6 `dropped_iterations`다.
- **서버 p95**: 앞뒤 `/metrics`의 `http_server_request_duration_seconds` 차이로 셌다(칸 사이는 선형 보간).
- **게이지**: k6 첫 요청과 끝 요청 사이의 1초 표본 가운데 0이 아닌 것의 비율이다.
- **503 까닭**: 서버 로그 `search_pool_saturated`의 `reason`으로 셌다.

원본 자료(CSV·표본·지표·로그·EXPLAIN)는 측정 담당의 임시 폴더에만 있고 저장소에 넣지 않았다.

## 5. 2만 미달의 원인을 가른 수치(측정 중 관찰. 고치지 않았다)

1. **DB 쪽 멈춤이 아니다.**
   - 2만 판정 회차(04:03:58~04:08:04)에 PostgreSQL checkpoint·autovacuum 기록이 없다. 시간 checkpoint(03:57:21~04:00:09, 1,676 버퍼)는 뺀 dup 회차와만 겹쳤다.
   - 1만 판정 회차(03:42~03:48)에도 없다. 1만의 시간 checkpoint는 03:22:18(100 버퍼)뿐이다.
   - 503 까닭은 모두 `pool-timeout`(연결 대기 100ms 넘음)이고 `statement-timeout`은 0이다.
2. **이 PC의 다른 일도 아니다.**
   - 2만 503이 난 초들의 PC 전체 CPU는 15~39%였다. 가장 큰 몰림은 l6 04:07:27의 503 20건이고, 그 초의 PC CPU는 14.9%였다.
   - 반면 1만 l6의 몰림(03:46:53의 10건, 03:47:14의 4건)은 PC CPU 69~71%인 초와 겹쳤다. 다른 갈래 일이 1만 l6을 경계(0.92%)까지 밀었다고 본다.
3. **주 스레드 계산이 공연 수에 비례해 늘었다.** core-svc CPU가 1만 39~47%에서 2만 66~70%로 올랐다. 서버 로그 `search_query`의 `durationMs`를 입력 종류별로 나누면 아래와 같다(p50·p95).

   | 크기 | 로마자 한 글자 | 한글 한 글자 | 그 밖 |
   | --- | --- | --- | --- |
   | 1만(l4~l6) | 94~109·144~472ms | 43~53·76~219ms | 22~26·58~154ms |
   | 2만(l4~l6) | 230~260·393~573ms | 87~91·254~265ms | 42~51·177~233ms |

4. **몰림 직전에는 결과가 상한(1,000)에 닿는 검색이 겹쳤다.**
   - 2만 l6 04:07:25~27의 3초 동안 걸린 검색이 줄지었다. 몰림 두 글자 키(`은하`·`바다`·`노을`·`별빛`)와 한 글자(`노`·`봄`·`새`), 로마자 한 글자(`f`·`g`·`s`·`z`)다. 모두 결과 1,000이고, 서버 시간은 한 건에 250~813ms였다.

## 7. 한계

1. **한 PC 한 프로세스**다(BAT-165 측정 §7 1과 같다). 운영의 읽기 전용 복제본·여러 파드·CDN은 없다.
2. **다른 갈래가 쉬지 않았다.**
   - 측정 내내 다른 갈래의 시험이 이 PC에서 돌았다(갈래 3·5의 vitest). 회차 앞에서 PC CPU의 10초 평균이 15% 아래가 되길 기다렸다. 그래도 판정 회차 안에서 PC CPU가 44~72%까지 오른 초가 있었다(§3.1·§3.2의 PC CPU 칸).
   - 1만 l6의 503은 그런 초와 겹친다. 2만의 미달은 PC CPU가 낮은 초에서도 났다(§5 2).
3. **2만 미달은 폭이 작다**(첫째 조건 +1~4ms, 자동완성 +2~10ms, 셋째 6.7% 대 5%). 그래서 회차를 더 돌리면 통과 회차가 섞일 수 있다. 판정은 기준대로 '유효 회차마다'로 내렸다.
4. **게이지 표본은 1초에 한 번 읽은 순간값**이다. 그 사이의 짧은 기다림은 보이지 않는다. 표본을 읽는 일은 같은 프로세스의 관리 포트에 1초에 한 번 더해지는 요청이다.
5. K3(따라잡기 계산량)은 이번 측정의 할 일이 아니라 다시 재지 않았다.
6. 컨테이너는 이름마다 `docker rm -f -v`로 지웠다. 띄운 core-svc 두 프로세스는 PID로 끝냈다. 망은 만들지 않았다.
