# 웨이브 7 갈래 2 끝 리뷰: 동시 실행·장애

> 검토 기록이고 규범이 아니다. 정본은 계획 파일이 가리킨 문서(ADR-0271·0272, docs/features/search.md, docs/frontend.md, docs/data.md, docs/architecture.md)다. 고칠지와 차례는 감독·계획 담당이 정한다.

- **누가·언제**: 웨이브 끝 리뷰 담당 `l2w7-rev-concurrency`(ADR-0270 결정 4, ADR-0267), 2026-11-16. 계획·시험·구현·묶음 리뷰에 관여하지 않은 새 맥락이다.
- **본 것**: 커밋 `29034c57`의 코드(`git show 29034c57:<경로>`), 바뀐 범위 `982a78a8..29034c57`의 `apps`·`services`·`packages`·`tools`·`loadtest`. 기준은 `docs/review/plans/BAT-165.md`·`BAT-170.md`·`BAT-040.md`의 '## 웨이브 7 계획'과 '정한 것' 절, ADR-0271·0272, 그리고 그 절이 가리킨 정본 줄이다. 줄 번호는 모두 커밋 `29034c57`의 것이다.
- **관점**: 동시 실행·장애. 여러 파드·여러 탭·동시 요청의 경합, 트랜잭션 경계와 잠금, 임대 만료와 넘겨받기, 시간 한도와 다시 하기, 바깥 저장소(Redis·DB·CDN)가 실패할 때 조용히 틀린 값을 내는지, 시작·종료 차례, 주기 일 겹침, 메모리가 끝없이 느는지, 장애를 넣는 시험이 실제로 그 길에 닿는지.
- **겹치지 않게 뺀 것**: 각 묶음 '## 리뷰'·'## 검증'에 이미 있는 지적은 다시 적지 않았다. 특히 R165-9(정리 일의 동시 실행)·R165-14·R165-15(시작 따라잡기가 시작 일을 미룸)·R165-19(세션 잠금)·R165-20(늦게 뜬 파드의 다시 따라잡기)·R165-23(건너뛴 정리의 창), R170-4(`getExpiration`이 실패 때 0), R040-4·R040-6(다시 보임 차례)은 뺐다.
- **시험은 돌리지 않았다.** Docker는 다른 담당과 함께 쓰는 자원이라 이 리뷰에서 띄우지 않았고, 판정은 코드를 읽고 했다. 아래 '재현 시험 아이디어'는 시험 담당이 먼저 써서 실패를 볼 거리다.

## 지적

### W7L2-K1 (높음, BAT-170) 공유 캐시가 클러스터 모드에 한 노드용 연결로 붙는다

- **위치**: `apps/web/server/cache-store.mjs:8`(`import { createClient }`), `:105~135`(`createLazyRedis`, 특히 `:109`의 `createClient({ url, … })`), `:57~65`·`:68~95`(실패를 모두 '없음'·'버림'으로 삼킴). 커밋 29034c57.
- **무엇이**: 세션·캐시 클러스터는 클러스터 모드(Redis를 여러 조각(샤드)으로 나눠 키마다 맡는 노드가 정해진 방식)이고 샤드가 셋이다(docs/infra.md:176 '노드 기반 클러스터 모드', :599 '샤드 3 × 주·복제'). 정본도 이 전제로 태그 키를 해시 태그 `{tag}`로 한 조각에 모았다(docs/frontend.md:1674 '세션·캐시 클러스터는 클러스터 모드다'). 그런데 처리기는 클러스터용 연결(`createCluster`)이 아니라 노드 하나에만 붙는 `createClient`를 쓴다. 클러스터 모드 노드는 자기가 맡지 않은 키를 받으면 '다른 노드로 가라'(MOVED) 오류를 돌려준다. 그 오류는 `run`·`within`이 거절로 받아 읽기는 `null`, 쓰기는 버림이 된다. 그래서 운영에서는 값 키의 약 3분의 2가 늘 캐시 빗나감이고, 태그 키가 든 조각을 그 노드가 맡지 않으면 모든 `tagTimes`가 `null`(값을 없는 것으로 봄)이고 모든 `markTags`(무효화)가 버려진다. 로그·지표가 없어 아무도 모른다. 같은 저장소의 핫패스 연결은 이미 `createCluster`를 쓴다(`packages/platform/src/redis.ts:5`·`:253`).
- **정본과 어긋남**: docs/frontend.md:1674(같은 Redis를 두 처리기가 나눠 쓰고, 무효화는 다른 파드에 닿는다. '늦거나 끊기면'만 없음·버림이고 늘 그런 것이 아니다), docs/infra.md:176·:599, docs/data.md:20(키 등급 A '다시 만든다'는 가끔 빠질 때의 이야기다).
- **왜 시험이 못 봤나**: `apps/web/test-int/cache-handler.int.test.mjs`는 클러스터가 아닌 Valkey 컨테이너 하나를 띄운다. 그 위에서는 모든 키를 한 노드가 맡아 MOVED가 생기지 않는다.
- **재현 시험 아이디어**: (D) 같은 Valkey 이미지로 클러스터 모드 노드 셋(`--cluster-enabled yes`, `valkey-cli --cluster create`)을 띄우고 처리기 둘을 그 시작 주소로 만든다. ① 서로 다른 조각에 떨어지는 값 키 100개를 A가 쓰고 B가 읽으면 100개 모두 맞는다(지금은 약 33개). ② A의 `revalidateTag('t')` 뒤 B의 `get`이 `null`이다. ③ 쓴 키가 모두 TTL을 가진다. 대조군으로 지금 코드가 ①에서 100개보다 적게 읽는 것을 먼저 본다. 비용·외부 계정 없이 로컬 컨테이너로 된다.

### W7L2-K2 (중간, BAT-170) Redis 연결이 멈추거나 읽기 전용이 되면 바꾸지 않고, 끊기면 쉬지 않고 다시 붙는다

- **위치**: `apps/web/server/cache-store.mjs:29~44`(`within`), `:105~135`(`createLazyRedis`: `reconnectStrategy: false`, `disableOfflineQueue: true`, 소켓 시간 한도 없음, `error`·`end` 때만 버림). 커밋 29034c57.
- **무엇이**: 세 가지 장애 꼴에서 회복이 정본의 뜻과 다르다.
  1. **답 없이 멈춘 연결**(장애 조치 중 옛 노드가 패킷을 버림, 네트워크 끊김처럼 연결 끊김 신호(RST)가 오지 않는 경우): 명령은 소켓에 쓰이고 답을 영영 기다린다. `within`이 100ms 뒤 '없음'으로 끝내 주지만 명령 자체는 클라이언트의 대기 줄에 남는다. `error`가 나지 않으므로 연결을 버리지 않고, 요청마다 대기 줄이 늘어난다(메모리가 끝없이 는다). 운영체제의 연결 생존 확인이 끊을 때(대개 수 분)까지 모든 요청이 캐시 빗나감이라 원본(SSR과 core-svc API)에 부하가 몰린다.
  2. **장애 조치 뒤 읽기 전용**: 주 노드가 복제 노드로 내려가도 연결은 살아 있고, 쓰기는 `READONLY` 응답 오류로 거절된다. 응답 오류는 `error` 사건이 아니라 연결을 버리지 않으므로, 다시 붙을 때까지 모든 쓰기와 무효화(`markTags`)가 조용히 버려진다. 다른 파드는 무효화를 못 보고 옛 값을 낸다.
  3. **연결 거절**(Redis 재시작 중): 연결이 실패할 때마다 `current`를 비우고, 다음 요청이 곧바로 새 연결을 연다. 쉬는 시간(지수 백오프)이 없어 파드마다 요청 수만큼 연결 시도가 나간다. 이 클러스터는 identity 세션과 전역 요청 한도 카운터도 함께 쓰므로(docs/data.md:20) 회복 중인 Redis에 다른 서비스까지 영향을 준다.
- **정본과 어긋남**: docs/frontend.md:1674 'Redis가 100ms 안에 답하지 않거나 끊기면 읽기는 없는 것으로, 쓰기는 버린 것으로'는 한 번의 명령에 대한 규칙이고, 회복 없이 그 상태가 이어지는 것을 정한 것이 아니다. 같은 저장소의 공용 연결은 '응답 없이 사라진 노드는 호출 쪽 마감이 끊는다', '연결이 끊긴 동안 명령을 쌓지 않는다'를 규칙으로 둔다(`packages/platform/src/redis.ts:3~7`). 회복 규칙(연속 시간 초과 몇 번이면 연결을 버린다, 다시 붙기 간격)은 정본 빈칸이다.
- **장애 주입 시험이 닿는 곳**: T14(`cache-handler.int.test.mjs`)의 'Valkey를 멈추면'은 3번(거절)만 본다. 1·2번 꼴과 회복(다시 살아난 뒤 적중이 돌아오는지)은 보지 않는다.
- **재현 시험 아이디어**: (단위) 답을 영영 주지 않는 가짜 클라이언트로 `getEntry` 1,000번을 부른 뒤, ⓐ 클라이언트의 미해결 명령 수가 상한 이하이고 ⓑ 연속 시간 초과 N번 뒤 새 연결을 연다. 응답 오류 `READONLY`를 주는 가짜로 `markTags`를 부르면 연결을 바꾸고 기록 한 줄을 남긴다. 연결이 늘 거절되는 가짜로 초당 500번 부르면 연결 시도가 백오프 간격만큼만 는다. (D) 컨테이너에 `REPLICAOF`를 걸어 읽기 전용으로 만든 뒤 되돌리면, 되돌린 뒤 1초 안에 쓰기·무효화가 다시 닿는다. `docker network disconnect`로 답 없는 연결을 만들고 다시 이으면 정한 시간 안에 적중이 돌아온다.

### W7L2-K3 (중간, BAT-165) 따라잡기 끊음과 1시간 관심도가 공연 수만큼 커지는 계산을 잠금 안에서 한 번에 한다

- **위치**: `services/core-svc/src/modules/catalog/adapters/db/drizzle-search-read-model.ts:232~237`(끊음 첫머리의 `search_version … for update`), `:251~258`(커서 질의가 `search_document_source_at(${atIso}::timestamptz)`를 공연 ID 없이 부름), `:185~195`(`recountInterest`의 한 문장 `UPDATE … FROM search_document_source_at(at)`), `services/core-svc/migrations/0023_search_read_model_tables.sql:24~107`(`:49~50`: 원천 함수가 `SECURITY DEFINER`·`SET search_path`라 SQL 함수 펼치기(인라인)가 되지 않는다). 커밋 29034c57.
- **무엇이**:
  - 끊음마다 '다음 500개 ID'를 고르려고 원천 함수를 모든 승인 공연에 대해 계산한다(회차 묶기, 대표 회차·다음 오픈·판매 상태 하위 질의, 찜 수, 포스터). 끊음이 N/500개이므로 따라잡기 전체 일은 공연 수의 제곱에 비례한다. 함수는 펼쳐지지 않아 `production_id > 커서`·`limit`이 안쪽으로 내려가지 않는다.
  - 이 무거운 질의를 도는 동안 그 트랜잭션은 이미 `search_version` 한 줄을 `for update`로 잡고 있다. 판매 승인(core_ops)과 포스터 게시·지우기(core_partner) 트랜잭션의 동기화는 같은 줄을 `update`하므로 그동안 기다린다. R165-14가 '판 줄을 잡는 시간을 끊음 하나로' 줄였지만, 끊음 하나의 길이가 공연 수에 비례하게 남았다.
  - 서버의 역할 문장 상한은 일반 API 역할 5초다(docs/architecture.md:832). 끊음 문장이 5초를 넘으면 그 끊음은 `57014`로 되돌려지고(`55P03`만 '멈춤'으로 받는다, `:281`), `#catchUp`이 1분마다 다시 부른다(`application/search-maintenance.ts:122`·`:167~178`). 그러면 따라잡기는 끝나지 않으면서 1분마다 몇 초씩 판 줄을 잡아 카탈로그 쓰기를 막는다. 기다리던 포스터 문장도 5초 상한에 걸려 실패할 수 있다.
  - `recountInterest`도 모든 공연을 한 문장으로 다시 계산한다. 5초를 넘으면 1시간마다 같은 자리에서 실패하고 경고 줄만 남아, 인기순 정렬과 관련 공연의 관심도가 조용히 멈춘다.
- **정본과 어긋남**: ADR-0271 결정 12(끊음 500개 [가정]과 끊음마다 트랜잭션: 끊음을 둔 까닭이 트랜잭션을 짧게 하려는 것), docs/architecture.md:832(역할 문장 상한 5초·쉬는 트랜잭션 10초), docs/features/search.md:56·§2.2(관심도 1시간 [가정]).
- **왜 시험이 못 봤나**: 검색 test-int는 공연 30~300개, 끊음 10개이고 역할 상한을 걸지 않는다(같은 저장소의 `test-int/sale-eligibility-scale.int.test.ts:55`는 `ALTER ROLE … SET statement_timeout = '5s'`를 건다). 측정 M-1의 채우기 스크립트(`services/core-svc/scripts/fill-search.mjs:96`)는 `reconcileAll`을 부르지만 상한 없는 연결이고 끊음 시간을 적지 않는다. `loadtest/scenarios/v1-search.js`는 검색만 잰다.

### W7L2-K4 (중간, BAT-165) 검색 복제본이 아프면 core-svc 파드 전체가 준비되지 않는다

- **위치**: `services/core-svc/src/modules/catalog/application/search.ts:49~55`(사전 첫 통째로 읽기가 끝나야 준비 작업 `search-dictionary`가 끝남), `services/core-svc/src/main.ts:87`(검색 연결 묶음: 운영은 읽기 전용 복제본), `:120`·`:125~127`(시작 따라잡기 → 사전 첫 읽기), `application/search-maintenance.ts:139~153`. 커밋 29034c57.

- **재현 시험 아이디어**: (D, 시작 파일을 따로 띄우는 시험) `PEAKET_SEARCH_DATABASE_URL`을 닫힌 포트로 두고 `node dist/main.js`를 띄운다. 기대(정본을 고친 뒤): 정한 시간 안에 `/ready`가 200이고 검색과 상관없는 경로(예 공개 회차 요약)가 200이며, `/v1/search`는 503·`no-store`, 자동완성은 빈 후보·`no-store`다. 지금 코드는 `/ready`가 끝까지 503인 것을 먼저 본다.

## 맞게 된 것(지적 아님)

- **판과 줄의 차례**: 판 올리기가 `search_version` 한 줄의 `update`라 판 번호는 커밋 차례와 같고, 사전은 한 `REPEATABLE READ READ ONLY` 트랜잭션에서 판을 먼저 읽으므로 복제본 지연이 있어도 줄을 빠뜨리지 않는다. 읽기 전용 복제본이 여럿이라 판이 잠깐 뒤로 가면 통째로 읽기로 바뀌어 틀린 값이 남지 않는다(`domain/search.ts:698`).
- **임대 넘겨받기**: 끊음 사이에 임대가 지나 다른 파드가 넘겨받아도, 원래 파드는 다음 끊음에서 주인이 아님을 보고 멈춘다(`drizzle-search-read-model.ts:240`). 넘겨받는 파드는 같은 열쇠의 트랜잭션 잠금을 먼저 잡아야 하므로 끊음이 도는 도중에는 넘겨받지 못한다.
- **커밋 뒤 일**: `withSearchSync`는 트랜잭션이 되돌려지면 무효화·로그를 하지 않고, 무효화 실패는 경고 줄만 남긴 채 처리를 성공으로 둔다(`application/search-maintenance.ts:16~37`).
- **주기 일 겹침**: 같은 이름의 주기 일은 앞 차례가 끝나기 전에 다시 돌지 않는다(`search-maintenance.ts:182~189`). 다른 이름끼리의 겹침은 R165-23 고침으로 창을 잃지 않는다.
- **품질 사건 묶음**: 라벨 값이 정해진 목록 밖이면 버려 모으는 표가 자라지 않는다(`apps/web/src/widgets/app-shell/model/search-quality.ts:53~78`).
- **QR 잠금**: 공유·기다리지 않는 잠금이라 탭 여럿이 함께 쥐고, 부품이 잠금을 받기 전에 떨어져도 바로 놓는다(`update-hold.ts:13~27`).
- **상태 파일 받기**: 세대 번호로 늦게 온 앞선 답을 버리고, 30초는 보낸 시각부터 세어 받기가 쌓이지 않는다(`live-sale-store.ts:30~67`).
