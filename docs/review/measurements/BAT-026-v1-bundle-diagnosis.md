# BAT-026 v1 합본 병목 진단

- 날짜: 2026-11-11
- 대상: BAT-025(PRF-220) 측정 창 1의 v1 합본. 장부 실행 `docs/perf-ledger/runs/2026-11-11-*` 16개를 다시 읽고, 작은 비교 실험 3회를 더했다.
- 결론: **K2·K7의 첫 포화점은 합본 CPU**다. CPU 2/replica(6코어)로 올리면 K2 1,000/s가 p99 25ms로 목표를 지킨다. 다만 K2 2,000/s는 CPU 6코어에서도 p99 131ms라 코드/목표 rate를 더 봐야 한다. K1 1만은 합본 자원이 아니라 queue-svc 진입 경로(또는 그 측정 방법) 문제다. A/A는 대상 포화 때문에 성립하지 않았고, S-T35 ⑥는 자원과 무관한 Lua 코드 차이다(단, 기준 판 문제로 입증은 불완전).

## 1. 실제 자원과 10개 서비스 비교

`deploy/envs/local/v1-bundle.yaml`·`v1-objects.mjs`·`deploy/charts/peaket-service`에서 읽은 값이다.

| 대상 | 복제 | CPU request | CPU limit | 메모리 request | 메모리 limit |
| --- | --- | --- | --- | --- | --- |
| 합본(bundle) | 3 | 1 | 1 | 512Mi | 512Mi |
| 합본 합계 | 3 | **3** | **3** | **1.5GiB** | **1.5GiB** |
| purchase 릴레이 | 2 | 100m | 없음 | 256Mi | 512Mi |
| payment 릴레이 | 2 | 100m | 없음 | 256Mi | 512Mi |
| Valkey 대기열·좌석 | 2 | 500m | 없음 | 512Mi | 1Gi |
| PostgreSQL | 1 | 500m | 없음 | 1Gi | 2Gi |
| nginx 상태 캐시 | 1 | 500m | 없음 | 128Mi | 256Mi |
| pg-simulator | 1 | 500m | 없음 | 256Mi | 512Mi |
| **v1 무대 합계(위 표)** | | **5.9** | 3(합본만) | **약 4.9GiB** | **약 8.3GiB** |

- 합본은 복제 3 × 1 CPU = 3 CPU를 네 서비스(queue-svc·admission-ctrl·purchase-svc·payment-svc)가 나눠 쓴다. 복제 하나의 1 CPU를 네 서비스가 공유하므로, 한 프로세스의 이벤트 루프·GC·CPU 경합이 그대로 네 서비스에 걸린다.
- **10개 서비스를 같은 자원 합계(3 CPU·1.5GiB)로 배포하면**: 서비스 하나당 **300m CPU·153.6Mi 메모리**다. 합본의 서비스 인스턴스 하나(3 복제 × 4 서비스 = 12개)가 약 250m를 쓰는 것과 비슷하다. 즉 같은 합계로 나누면 서비스별 CPU는 크게 늘지 않는다.
- **차트 기본값(100m/256Mi request, 메모리 limit 512Mi)로 10개를 배포하면**: **1 CPU·2.5GiB request**, 메모리 limit 5GiB다. 합본보다 CPU가 적다.
- **서비스마다 1 CPU(합본 복제 하나와 같은 몫)를 주면**: 10 CPU·5GiB request, 메모리 limit 5GiB다. 합본의 3 CPU보다 3.3배 많다.
- 그래서 '10개로 나누기'만으로는 CPU 총량이 늘지 않는다. 같은 3 CPU를 나누면 서비스별 몫은 비슷하고, 프로세스가 분리되어 이벤트 루프·GC 경합은 줄지만 hot path의 CPU 총량은 그대로다. 10개로 나누면서 CPU를 10코어로 늘리면 자원은 3.3배가 든다.

## 3. 작은 비교 실험(K2, 같은 클러스터에서 CPU만 바꿈)

전체 측정을 다시 하지 않고, K2 인기 좌석을 1,000/s로 낮춰 CPU 1(3코어)과 CPU 2(6코어)를 같은 조건으로 견줬다. 실험 산출물은 `.cache/peaket-bat025/diagnosis/`에 있고, 요약·발생기 판정은 `docs/review/measurements/BAT-026/`에 커밋했다. 장부에는 넣지 않았다.

| 실험 | 합본 CPU(복제당) | 발생기 | p99 | 오류 | 놓침 | 판정 |
| --- | --- | --- | --- | --- | --- | --- |
| K2 1,000/s, CPU 1 | 1 (합 3) | 2대 | **113.4~114.5ms** | 0 | 0 | 유효, 목표(50ms) 미달 |
| K2 1,000/s, CPU 2 | 2 (합 6) | 2대 | **25.3~25.4ms** | 0 | 0 | 유효, 목표 통과 |
| K2 2,000/s, CPU 2 | 2 (합 6) | 4대 | **131.0~132.6ms** | 0 | 56 | 무효(놓침 56), 목표 미달 |
| K2 2,000/s, CPU 1 (기존) | 1 (합 3) | 2대 | 270.9~318.2ms | 1.3~2.4% | 920~1,504 | 무효, 목표 미달 |

- 1,000/s에서 CPU를 2배로 올리자 p99가 **113ms → 25ms(약 4.5배 개선)**, 오류 0이 됐다. **자원 부족이 맞다.**
- 2,000/s에서는 CPU 6코어로도 p99 131ms로 목표의 2.6배다. 같은 CPU 6코어에서 1,000/s(25ms)와 2,000/s(131ms)의 차이는 부하가 2배일 때 지연이 5배가 된 것으로, hot seat 409 경로의 직렬화·Redis/DB 왕복·이벤트 루프 큐가 함께 커진 결과로 본다. CPU만 더 늘리면(예: 4/replica=12코어) 50ms에 가까워질 수 있지만, 코드 쪽에서 409 경로를 줄이는 편이 비용이 낮을 수 있다.
- K2 2,000/s CPU 2 실험은 놓침 56으로 무효다. p99·오류 비교에는 쓰되 통과로 세지 않는다.

## 4. A/A와 S-T35 ⑥

- **A/A 무효 원인**: K2 2,000/s에서 대상이 포화되어(p99 250~346ms) 발생기가 반복을 놓쳤다. 2·4·8대 모두 놓침이 났고, A/A 네 실행은 같은 조건에서 쌍을 이룰 수 없었다. '정밀 측정 동안 다른 갈래 시험 금지'는 아직 풀 수 없다. K2가 유효해진 뒤(예: CPU 2에서 1,000/s) 조용한 쌍과 다른 갈래 함께 쌍을 다시 재야 한다.
- **S-T35 ⑥**: `lua-compare`는 합본이 아니라 전용 Valkey 컨테이너에서 도는 마이크로 측정이라 합본 CPU 포화와 무관하다. A/A p50 ±2.1~6.7%·p99 ±4.6~15.9% 안에서 `end-session-1hold` p50 1.583, `end-session-5holds` 1.769, `order-hold-4` p99 1.216로 A/A 폭을 넘었다. 이는 Lua 원문 차이에 따른 코드 비용이다.
- 다만 계획한 기준 판 `af7ceef7`에는 `pin.ts`가 없어 `lua-compare`가 실행되지 않았고, `1a85da7a`로 바꿔 돌렸다. `1a85da7a`는 PRF-136(구매 세션) 이후 판이라 **PRF-136 앞뒤 비교가 아니다.** S-T35 ⑥의 '구매 세션 칸을 더하기 전' 증거로 쓰려면 도구가 옛 판에서도 돌도록 `pin.ts` 의존을 빼거나, PRF-136 앞판과 호환되는 시나리오만 골라 다시 재야 한다.

## 5. 결론과 다음 배치 추천

1. **자원 증설(즉시, 낮은 위험)**: 측정 무대 합본 CPU를 **2/replica(합 6코어)**로 올린다. K2 1,000/s는 p99 25ms로 목표를 지킨다. K2 2,000/s 목표를 그대로 두려면 6코어로는 부족하므로, 목표 rate를 1,000/s로 낮추거나 CPU를 4/replica(합 12코어)까지 올리는 비용을 견줘야 한다. 10개 서비스로 나누는 것은 같은 3 CPU 합계면 서비스당 300m라 CPU 총량이 늘지 않는다. 서비스마다 1 CPU를 주면 10코어/5GiB가 든다.
2. **코드 수정(다음 진단/수정 배치)**: K2 hot seat 409 경로(purchase-svc 홀드)와 K7 결제 확정·`payment_status` 롱 폴링(payment-svc·purchase-svc), K1 진입 경로(queue-svc `preempt`·번호 묶음·Redis)에 구간별 시간을 넣어 어디서 200ms/3초를 넘는지 본다. K1은 합본 CPU가 10%라 코드/경로 쪽이 우선이다.
3. **측정 방법 수정**: A/A는 K2가 유효해진 rate에서 다시 잰다. K1 진입은 200ms 목표와 `unknown`(5xx·연결 실패) 처리, 발생기 수를 다시 정한다. S-T35 ⑥는 기준 판/시나리오를 고친 뒤 다시 잰다.
4. **권장 순서**: (가) 합본 CPU 2/replica로 K2 1,000/s·K1 측정을 다시 해 유효한 기준을 얻고, (나) K2 2,000/s와 K7 ②는 코드 구간 계측 뒤 목표 rate·CPU를 정한다. 전체 5시간 재측정은 코드 계측 전에는 하지 않는다.

## 6. 남은 문제

- K2 2,000/s CPU 2 실험은 놓침 56으로 무효다. p99 131ms는 참고값이고, 통과 판정에 쓰지 않는다.
- K7은 CPU 포화와 장애 주입·강제 종료가 겹쳐 있어, CPU만 올린 실험으로 분리하지 않았다. 다음 배치는 K7을 빼고 K2/K1을 먼저 유효하게 만드는 것이 좋다.
- `metrics-summary.json`에 Valkey·PostgreSQL·Kafka CPU/지연 시계열이 없다. 다음 진단에는 `valkey-queue` CPU, Redis 명령 지연, PG CPU·풀 대기, nginx 요청률을 추가한다.
- `lua-compare` 기준 판 문제는 S-T35 ⑥ 증거를 아직 완성하지 못했다.
