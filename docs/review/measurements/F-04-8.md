## 8. 남은 위험과 하지 못한 것

1. **ops-svc `/metrics`·C-T14 미판정**: 하네스는 `rt.pulse` 두 길(누적·1초 칸)로만 신선도를 잰다. NFR-009의 'ops-svc가 읽을 때까지' 끝은 이 창에서 재지 못했다. `rt.v_freshness` 직접 조회는 했다(조회 p95 23~37ms). 다음 창에서 ops-svc 기동·`rt_freshness_seconds{path}` 긁기를 하네스에 더해야 한다.
2. **시계 차**: 새 실행은 −1~−8ms로 20ms 안이다. 다만 Windows 타이머 흔들림과 1초 미만 차이는 남는다.
3. **중단 때 manifest**: 10초 주기 쓰기를 넣었으나, 이 창에서 발생기를 강제로 죽여 확인하지 못했다. 다음 창에서 SIGKILL 시험으로 확인한다.
4. **15k r2 환경 무효**: ClickHouse HTTP `fetch failed`가 9분 지속돼 두 그룹이 함께 밀렸다. Docker Desktop/WSL 네트워크의 일시 장애로 보인다. 같은 조건 r3는 재현되지 않았지만, 측정 창에서 한 번 더 보이면 그 실행은 invalid로 두고 다시 잰다.
5. **hash 조건의 뜻**: 이 결과는 한 회차를 파티션 0에 몰아 넣는 **가장 나쁜 경우**다. 12파티션에 회차를 고르게 나누는 `spread` 조건은 재지 않았다. NFR-009의 30,000건/초가 정상 분포를 뜻한다면 `spread`로 다시 재야 한다. 이 창의 결론을 운영 전체의 처리량으로 일반화하지 않는다.
6. **S3 회복 시간**: 관제 작업자를 죽이면 신선도가 5초 아래로 돌아오는 데 3~5분이 걸린다. 계획의 60초 회복 구간은 이 PC에서 너무 짧다. 정본에 넣을 값인지 감독이 정한다.
7. **S4 30분·S5 저장소 정지**: 하지 못했다. S4는 정본 입력이 한계를 넘어 30분 실행이 무의미하고, S5는 보조다.
8. **디스크**: 빈 84.8GB에서 시작했다. 실행 사이 컨테이너를 지워 공간은 유지했고 디스크 부족 실패는 없었다.
