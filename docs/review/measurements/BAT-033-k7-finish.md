- 날짜: 2026-11-12

- 선행: BAT-032(HOT-466, R-477, OPEN[38])
- 결론: **K7 결제 확정 p99(confirmMs)는 3회 모두 3초 안에 들었지만, 공식 `payment_p99_3000ms` 경로 점검은 3회 모두 미달이다.** 원인을 나눠 보면 실제 끝 상태에서 3초를 넘긴 결제는 70~78건(0.76~0.84%)뿐이고, PENDING 396~438건(본구간 끝에서 잘림)과 `payment` 접수 실패 343~375건(빠른 비끝 답, M6)이 대부분이었다. 측정 방법을 본구간 마지막 3초 안에 시작한 반복은 끝 상태 여부와 무관하게 초과에서 빼도록 고쳤다(다음 K7부터). K2는 p99 50ms 안이지만 발생기 dropped_iterations가 0이 아닌 실행이 많아 A/A를 성립시키지 못했다. 홀드는 k6 p99가 50ms를 넘고 서버 `hot_path` p99는 50ms 안이다(OPEN[39]).

### 2.1 공식 `payment_p99_3000ms` 실패의 분해

| 실행 | `over_target` | PENDING(끝 상태 아님) | `payment` 접수 실패 | 실제 3초 초과(끝 상태) |
| --- | ---: | ---: | ---: | ---: |
| r4 | 827 | 406 | 343 | **78** |
| r5 | 864 | 438 | 356 | **70** |
| r6 | 847 | 396 | 375 | **76** |

- `over_target` = PENDING + `payment` 접수 실패 + 실제 3초 초과로 맞는다. PENDING은 모두 `countOverTarget(..., over=true)`로 세고, 접수 실패도 M6 규칙으로 초과로 센다.
- PENDING 406·438·396은 각 실행의 **마지막 2초에 승인된 결제 수 427·436·488**와 거의 같다. 본구간 종료와 함께 끝나지 못한 반복이 PENDING으로 남은 것이다.
- 실제 끝 상태에서 3초를 넘긴 결제는 78·70·76건(0.76~0.84%)뿐이다. `confirmMs` p99가 2.65~2.85초인 것과 맞는다.
- 따라서 공식 점검 실패의 큰 몫은 **끝에서 잘린 PENDING**과 **빠른 비끝 답(접수 실패)**이지, 결제 확정 3초 초과가 아니다.

### 2.2 접수 실패의 성격과 코드 분포 한계

- `payment` 접수 실패는 본구간 343·356·375건이다. `결제 접수 202` 점검 실패 382·392·383건은 예열 구간 39·36·8건을 더한 값이다.

| 실행 | 본구간 접수 호출 | 본구간 접수 실패 | 본구간 202 | 전체 202(예열 포함) | 상태 코드 분포 |
| --- | ---: | ---: | ---: | ---: | --- |
| r4 | 9,253 | 343 | 8,910 | 9,803 | 원자료 없음 |
| r5 | 9,166 | 356 | 8,810 | 9,728 | 원자료 없음 |
| r6 | 9,350 | 375 | 8,975 | 9,936 | 원자료 없음 |

- r4~r6 원자료에는 **응답 코드 분포가 없다**. `summary.json`은 `http_req_failed{route:payment}`의 합계만 남겼고, `records.ndjson`은 PG 시뮬레이터의 `pg_charge` 9,803·9,728·9,936건뿐이다(전체 202와 같은 수). `k6.log`·`console.ndjson`에도 상태 코드가 없다. 클러스터를 회차 뒤 제거해 서버 로그·트레이스도 남아 있지 않다. 따라서 409·429·500·503의 정확한 분포는 **사후 복원할 수 없다**.
- 429도 이 경로의 응답이 될 수 있다. 플랫폼 DB 풀 대기 한도(핫패스 100ms)를 넘으면 `429 server-busy`다. 접수 경로는 purchase-svc이고, DB 읽기·쓰기와 Redis 좌석 저장소를 거치므로 429·503·500·504가 모두 제품 쪽 답이다. payment-svc 서킷은 202 뒤 Saga 확정에 영향을 주고, 그 몫은 PENDING·지연으로 나타난다(접수 실패와 별개).
- 시나리오가 만든 중복·재시도도 아니다. 반복마다 주문과 결제 시도를 새로 만들고 접수는 **한 번만** 부르며, 멱등 키도 호출마다 새 UUID다. `pay()`에는 재시도 경로가 없고, 예열·본구간의 사용자 번호도 겹치지 않는다. 따라서 409 `payment-already-accepted`·422 `idempotency-key-reused`는 이 시나리오에서 나올 수 없다.
- 남는 것은 제품 쪽 답이다. 접수 경로가 Redis 좌석 저장소를 읽다 실패하면 503 `seat-store-unavailable`, 구매 DB 풀 대기·질의가 넘으면 429 `server-busy` 또는 500, 좌석 호출 마감이면 504다. 같은 실행에서 주문 95~294건·결제 시도 시작 541~557건도 실패한 점이 제품 과부하 쪽을 가리킨다. **이 실패는 실제 미확정 답이므로 M6대로 초과에 그대로 센다.**
- 다음 K7부터 코드 분포를 남기도록 `v1-payment.js`에 `payment_accept_status{phase,status}` 카운터를 더했다. 이번 r4~r6 값은 소급해 채우지 않는다. 초과에서 뺀 반복 수는 `payment_end_truncated{phase:main}`로 남기고, 그중 끝 상태와 비끝 상태를 `payment_end_truncated_terminal`·`payment_end_truncated_pending`으로 나눴다. old PENDING 406~438과 like-for-like로 비교할 값은 `_pending`이다.

### 2.3 측정 방법 수정

- `loadtest/lib/targets.mjs`에 `paymentOverTarget`을 더했다. **끝 상태 여부와 무관하게** 본구간 마지막 3초 안에 시작했으면 초과에서 뺀다(끝에서 잘린 반복). 그 밖에서 끝 상태가 아니면 초과(M6 유지), 그 밖은 결제 확정 시간 3,000ms 초과로 센다.
- `v1-payment.js`는 `exec.scenario.startTime + MAIN_S * 1000`을 본구간 끝으로 쓰고 이 함수로 `over_target`을 센다. 초과에서 뺀 반복 수는 `payment_end_truncated{phase:main}`에, 그중 끝 상태/비끝 상태는 `payment_end_truncated_terminal`·`payment_end_truncated_pending`에, 접수 응답 코드는 `payment_accept_status{phase:main,status}`에 남긴다.
- k6 `gracefulStop`/드레인 대신 이 좁은 경계 제외를 골랐다. 드레인은 본구간 뒤 최대 4×40초 폴링까지 기다려 측정 창이 달라지고, 이번에 문제가 된 것은 끝에서 잘린 PENDING뿐이었다. 접수 실패·비끝 답은 M6대로 그대로 초과로 센다. 접수 실패는 202를 받지 못해 `paymentOverTarget`을 부르지 않으므로 끝 경계 제외 대상이 아니다.
- 새 시험: `loadtest/test/v1.test.mjs`의 BAT-033 끝 경계 시험(마지막 3초 경계·3,000ms 경계·M6). `terminal:false`도 마지막 3초 안이면 false, 3,001ms 전이면 true다.
- r4~r6은 수정 전 측정이다. 다음 K7 재측정에서 PENDING 몫이 줄고, 접수 실패 몫이 남으면 그대로 fail로 기록한다. r4~r6 값을 그대로 적용하면 끝 3초 안의 PENDING이 모두 빠진다고 해도 접수 실패 343~375 + 실제 3초 초과 70~78 = 413~453건(4.5~4.8%)이 남아, 접수 실패가 줄지 않으면 공식 1% 점검은 다시 fail이다. 이번 수정은 측정 artifact(끝에서 잘린 PENDING)만 걷어낸다.

- 세 실행 모두 발생기 dropped 0, 시나리오 오류 0, `startSkewS=0`이다. r1~r3은 시나리오 오류 15·6·19건으로 무효라 표에서 뺐다.
- `confirmMs`(결제 접수 시작 → 끝 상태) p99는 2.65~2.85초로 3초 안이다.
- 그러나 공식 경로 점검 `payment_p99_3000ms`는 r4 827/9,253(8.94%), r5 864/9,166(9.43%), r6 847/9,350(9.06%)로 **허용 1%를 넘었다**. 이 점검은 끝 상태가 아닌 답(UNKNOWN·PENDING 등)을 시간과 무관하게 목표 초과로 세기 때문에, `confirmMs` p99와 다른 값이 된다. **공식 점검 기준으로는 미달**이다.
- 홀드는 k6 p99 199~224ms로 50ms를 넘고, 서버 `hot_path` p99는 r6에서 9.84ms로 50ms 안이다. BAT-032의 서버 값 43.4ms보다 좋아졌다. 50ms 게이트 기준은 **OPEN[39]**로 남긴다.

## 5. 남은 문제

1. **공식 K7 점검 미달**: `confirmMs` p99는 3초 안이지만 `payment_p99_3000ms`는 9%대로 fail. 실제 3초 초과는 70~78건뿐이고, 끝에서 잘린 PENDING과 빠른 비끝 답(접수 실패)이 대부분이었다. 측정 방법은 마지막 3초 경계 제외로 고쳤지만, 접수 실패 몫은 남으면 그대로 fail이다. 접수 실패 343~375건의 상태 코드 분포는 r4~r6 원자료에 없어 사후 복원하지 못했다. 시나리오 중복·재시도는 아니며, 다음 K7부터 `payment_end_truncated_terminal`·`payment_end_truncated_pending`·`payment_accept_status`로 남긴다.
2. **K2/A/A 미완**: p99는 50ms 안이나 dropped_iterations가 0인 실행을 3회 채우지 못했다. A/A는 성립하지 않았다.
3. **OPEN[39]**: 추천은 k6 `hold_p99_50ms`를 정본, 서버 `hot_path` p99를 진단으로 두는 것이다. 서버 r6 9.84ms·k6 199~224ms. 정본 변경은 소유자 결정 전에는 하지 않는다.
4. **K7 서버 홀드 p99**: r4·r5는 클러스터를 제거하기 전에 Prometheus 값을 수집하지 못했다. r6만 9.84ms를 남겼다.
5. 다음 웨이브는 감독이 이 결과를 보고 지시한다. 이 배치에서는 다음 웨이브를 시작하지 않는다.
