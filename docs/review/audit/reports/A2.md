### [높음] A2-01: 상품 정산 원천 HTTP가 `from`·`to`를 쿼리로 보내지 않아 상품 정산서 계산이 항상 503이다
- 영역/배치: payment-svc 상품 정산(R-588), core-svc shop 상품 정산 원천
- 위치: `services/payment-svc/src/modules/settlement/adapters/http-product-source.ts:19`, `packages/platform/src/http-client.ts:70-81`
- 증거:
  ```ts
  // http-product-source.ts
  path: '/internal/v1/shop/product-settlement-items',
  params: { from, to },
  ```
  `createExternalHttpClient`에서 `params`는 경로 틀의 `{name}` 치환에만 쓰이고(`r.path.replace(PARAM, ...)`), 실제 쿼리는 `r.query`만 붙는다(`for (const [k, v] of Object.entries(r.query ?? {}))`). 따라서 요청은 쿼리 없이 나가고, core-svc `InternalMerchSettlementController.list`가 `from`·`to` 누락으로 400을 돌려준다. payment-svc는 `!res.ok`를 503 `product-settlement-source-unavailable`로 바꾼다.
- 왜 문제인가: 운영 배선(`PEAKET_CORE_HTTP_URL`)에서 상품 정산서를 한 장도 만들 수 없다. 상품 판매 대금이 정산·지급으로 이어지지 않아 파트너 돈이 묶인다. 시험은 가짜 `ProductSettlementSource`를 주입해 이 경로를 보지 않는다.
- 재현/확인: `services/payment-svc/test-int/settlement.int.test.ts:50`은 `products: { listProductItems: async (from,to) => ... }` 가짜를 쓴다. 실제 `HttpProductSettlementSource`를 쓰는 시험은 없다. `rg "params: \\{ from, to \\}"` 결과가 위 한 곳.
- 제안 수정: `query: { from, to }`로 바꾸고, core-svc 응답 400/503을 구분하는 통합 시험(실제 HTTP)을 더한다. 같은 패턴이 `services/ops-svc/src/modules/payouts/adapters/payment-http.ts:36,63,68`에도 있어 목록 필터가 전부 무시된다(별도 후속).
- 확신도: 높음

### [높음] A2-05: `HELD`·`DISPUTED` 정산서가 다시 `CONFIRMED`로 돌아오는 경로가 없어 보류된 파트너가 영구 미지급된다
- 영역/배치: payment-svc 정산 상태 전이(R-574·R-588)
- 위치: `services/payment-svc/src/modules/settlement/application/settlements.ts:196-208,240-246`, `services/payment-svc/src/modules/settlement/domain/settlement.ts:259`
- 증거: `CONFIRMED`를 쓰는 곳은 `confirmDue` 하나이고, 그 조건은 `s.status === 'NOTIFIED'`다. `createPayoutBatch`는 KYC 미확인 정산서를 `HELD`(KYC), 계좌 변경 보류를 `HELD`(ACCOUNT_CHANGE)로 바꾼다. `dispute`는 `DISPUTED`로 바꾼다. `HELD`/`DISPUTED`를 `NOTIFIED`/`CONFIRMED`로 되돌리는 메서드·내부 경로가 없다. `recordKyc`는 `seller_kyc`만 고친다.
- 왜 문제인가: KYC가 계산 시점에 없던 파트너(대부분의 첫 정산)는 KYC를 나중에 마쳐도 정산서가 `HELD`에 남아 영원히 지급되지 않는다. 이의가 처리된 정산서도 `DISPUTED`에 남는다. 문서 §4.4는 `HELD → CONFIRMED(사유가 풀린 뒤 다음 지급 묶음으로)`, `DISPUTED → NOTIFIED`를 명시한다. 돈이 파트너에게 가지 않는 결함이다.
- 재현/확인: `test-int/settlement.int.test.ts:106-110`은 HELD 정산서를 **손으로** `store.saveStatement(..., status:'CONFIRMED')`로 바꿔 시험을 통과시킨다. 공개 경로로는 그 전이가 불가능하다.
- 제안 수정: `releaseHold(statementId)`(KYC/계좌 보류 해제 시 `HELD→CONFIRMED`)와 이의 처리 결과(`DISPUTED→NOTIFIED`, 1영업일 이의) 경로를 내부 API/ops 업무로 넣고, 상태 전이 시험을 더한다.
- 확신도: 높음

- 영역/배치: core-svc export(R-588), openapi SCR-027
- 위치: `services/core-svc/src/modules/export/inbound/partner-attendee-export.controller.ts:36-39`, `packages/contracts/src/gen/openapi/partner.ts:3639-3644`
- 증거: 컨트롤러가 `q.limit`·`q.cursor`만 넘기고 `q.orderId`·`q.tier`를 버린다. 애플리케이션도 해당 인자를 받지 않는다.
- 왜 문제인가: "예매번호 찾기"·"좌석 등급" 필터가 동작하지 않아 전체 명단이 나온다. 계약과 구현이 어긋난다.
- 제안 수정: 필터를 저장소까지 전달하거나, 계약에서 이번 웨이브에 미지원임을 명시한다.
- 확신도: 높음
