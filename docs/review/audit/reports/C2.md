## 요약

- **높음 1**: 회원 탈퇴·계정 병합이 현장 스태프 배정·스캐너 세션을 끝내지 않는다. 삭제된 계정의 스캐너 토큰이 배정 유효 끝까지 계속 통한다.
- **중간 4**: 초대 수락이 설계·ASVS가 요구하는 휴대폰 본인확인을 보지 않는다. 내부 토큰 가드가 운영에서도 조용히 열린다(fail-open). 리프레시 재시도 유예의 세 번째 조건(`refresh_used`)이 구현되지 않아 문서와 다르다. 스캐너 세션의 '계정당 1개' 불변식이 DB에 없다.
- **낮음 6**: 사용자 확인 코드 색인 덮어쓰기, 승인 뒤 기기 코드 미폐기(ASVS 6.5.1 문구와 불일치), mTLS 정적 비밀·비상수시간 비교, DPoP `htu`가 클라이언트 제어 머리에서 만들어짐, `staff_assignment.promoter_id` 백필 없음, 배정 상태가 시간 경과로 바뀌지 않음.

- 확신도: 높음(코드), 중간(영향도 — 초대 대상 이메일을 파트너가 정하므로 공격 표면은 제한적)

- 확신도: 높음(코드), 중간(운영 영향 — 네트워크 정책이 1차 방어)

### [중간] C2-04: 리프레시 재시도 유예의 세 번째 조건(`refresh_used`)이 구현되지 않아 문서와 코드가 다르다

- 영역/배치: identity-svc 토큰 회전·재사용 탐지(PRF-030, BOT-130), `docs/features/identity.md` §3
- 위치:

  - `services/identity-svc/src/modules/admin/application/refresh-admin-session.ts:38,53-64`
  - `services/identity-svc/src/modules/admin/adapters/db/drizzle-admin-account-store.ts:860-868` (`rotateRefresh`는 `refreshUsed=false`만 쓴다)
  - 같은 패턴: `services/identity-svc/src/modules/session/adapters/db/drizzle-session-store.ts:565`, `memory-session-store.ts:581`
  - 시험: `services/identity-svc/test/admin-token-refresh.test.ts:82-85` (30초 안 같은 앞 토큰을 **세 번째**로 써도 `retried`로 통과)
- 증거:
  - 저장소 전체에서 `refreshUsed`를 `true`로 쓰는 코드가 없다(grep: 선언·초기화·`false` 대입뿐). 따라서 `decideRefresh`의 `!s.refreshUsed`는 항상 참이다.
  - 문서 `docs/features/identity.md:184` ②③은 "그때 준 새 리프레시 토큰이 아직 한 번도 쓰이지 않았다"를 재시도 조건으로, "재시도로 폐기된 것"을 재사용(탈취)으로 적는다. 코드는 회전 시각(`rotatedAt`)이 재시도에서 늘지 않으므로, 앞 토큰 하나로 30초 동안 **무제한** 새 토큰 쌍을 받을 수 있다.
- 왜 문제인가: 훔친 '바로 앞' 리프레시 토큰 하나로 30초 동안 계속 액세스 토큰을 갱신할 수 있다(정당한 클라이언트가 새 토큰을 쓰는 순간 패밀리가 끝나지만, 그 전까지 연장). 문서가 보장하는 "한 번 더"와 다르고, `identity_refresh_retry_reuse_total` 지표의 의미도 흐려진다. 다만 창이 30초이고 정당한 사용 시 탐지되는 남는 한계가 문서에 적혀 있어 높음은 아니다.
- 재현/확인: `test/admin-token-refresh.test.ts:71-86`이 세 번째 사용을 `retried`로 단언해 이 동작을 고정하고 있다(29건 통과). 즉 결함이 아니라 의도된 구현이지만, 문서·`refreshUsed` 필드와 불일치한다.
- 제안 수정: 재시도에서 `refreshUsed=true`(또는 `retryUsedAt`)를 같은 트랜잭션에 적고, 두 번째 재시도부터 `reuse`로 판정한다. 시험 `:82-85`를 `REUSED`로 바꾸고 문서 ②의 "한 번 더"를 코드에 맞춘다. `refreshUsed`를 쓰지 않을 거면 필드와 조건을 지우고 문서를 정정한다.
- 확신도: 높음(코드·시험), 중간(영향도)

## 확인했으나 결함으로 보지 않은 것(범위·근거)

- **RFC 8628 사용자 코드 엔트로피**: 20자 집합 8자(약 34.5비트), CSPRNG(`randomInt`), 5분 TTL, 계정당 10분 5회·기기당 시간당 10회. RFC 8628 §5.1·§6.1 최소치를 넘는다.
- **DPoP 증명 검증**: `typ`·`alg`·공개 EC JWK(`d` 거부)·서명·`htm`·`htu`(쿼리 제외)·`iat` ±5분·`ath`·`jti` 10분 1회(`SET NX PX`)를 모두 본다. `jti` 재사용은 Redis에서 원자적으로 막는다.
- **스태프 토큰 바인딩**: `cnf.jkt`(mTLS는 `x5t#S256`)와 요청 증명/인증서 지문을 비교하고, 토큰에 역할을 싣지 않으며 요청마다 `CheckScannerSession`의 역할로 판정한다(ADR-0172). `deviceOnly` 경로에 사람 토큰을 붙이면 401이다.
- **기기 폐기**: `TerminateScannerSessions`가 기기별 세션을 끝내고 `control.sessions-terminated`(`DEVICE_REVOKED`)를 남기며, 스캐너 가드는 요청마다 기기 `ACTIVE`와 세션을 다시 본다. (단, 계정 탈퇴·병합은 C2-01.)
- **관리 authz·테넌트**: `GetAdminAuthz`가 세션·계정 상태·역할/콘솔 일치를 원본 DB로 보고, `AuthGuard`가 5초 캐시·`fresh` 무캐시·`password:change` 제한·종료 세션 목록을 적용한다. `PartnerTeamAccountsController`는 `me.tenantId`만 쓰고 경로·본문의 `promoterId`를 쓰지 않는다.
- **관리 계정 관리 규칙**: 자기 자신 금지, 마지막 `partner_admin` 보호, 역할 묶음 일치, commander 부여·회수 2인 승인 ID 요구, 지정 대상·충돌·90일 냉각, 역할 변경 시 지정 회수. 코드와 authz-matrix §6.1이 일치한다.
- **관리 로그인**: 비밀번호 1단계 → TOTP/복구 코드 2단계, 계정·묶음·출발지·전체 실패 제한, 보호 잠금, 사람 확인, 계정 열거 방지(가짜 상태·같은 응답), TOTP 시간 칸 1회, 복구 코드 80비트 PHC. 쿠키는 `Secure`·`HttpOnly`·`SameSite=Strict`, `__Host-`/`__Secure-` 규칙과 Path가 설계와 맞다.
- **리프레시 회전**: 현재 토큰 회전, 바로 앞 토큰 30초 유예, 그 밖은 패밀리 종료(`REFRESH_REUSE`)와 세션 종료 사건. 회전 전 액세스 토큰 서명, 계정 상태·역할 재확인. (유예 세 번째 조건은 C2-04.)
- **재인증 토큰**: `typ reauth+jwt`·`iss`·`aud`·`sid`·`act`·`exp`·`jti` 1회, `factors` 검사, 패스키 서명 횟수 퇴행 거부, 챌린지 1회. identity가 직접 받는 `ACCOUNT_SECURITY` 경로는 토큰을 쓰기 전에 세션·계정을 다시 본다.
- **Problem 유형**: `ProblemError`가 케밥 표기·상태·제목·확장 필드 예약어를 강제하고, 필터가 5xx에 경로·원문을 싣지 않으며 `debug`는 설정으로만 켠다. `PURCHASE_REJECTION_PROBLEMS`도 401 `WWW-Authenticate`와 함께 이름 붙은 유형을 낸다.
- **역할 데코레이터**: `RolesCheck`가 시작 때 모든 HTTP 처리기의 `@Roles`·스캐너 포트·멱등/구매 서명·관리 authz 포트를 확인해 하나라도 빠지면 시작을 막는다(AZ-T1).
- **문서-코드 일치(예외)**: 위 C2-01·C2-02·C2-07·C2-04에서 지적한 문구 말고, §6.1의 승인 조건(배정 파트너·유효 시간·대리 승인 강등)과 §3의 쿠키·토큰 수명은 코드와 맞는다.
