## 3. 놓친 변이 = 시험 공백

### [중간] M05: KYC 대표자 확인 플래그가 단위 시험에 없다
- 바꾼 것: `kycVerified = status==='VERIFIED' && businessVerified && representativeVerified`에서 `representativeVerified` 제거.
- 왜 위험: 대표자 확인이 빠져도 정산서가 NOTIFIED가 되어 지급으로 갈 수 있다.
- 왜 못 잡나: 기존 시험은 `businessVerified=false`만 본다. `representativeVerified=false` 조합이 없다. test-int에도 없다.
- 제안: `kyc(A,'VERIFIED')`에 `representativeVerified:false`를 넣어 HELD/KYC를 단언한다.

### [중간] M12: 중복 지급 묶음 차단 시험이 없다
- 바꾼 것: 같은 `pg·pgStore·payoutDate`의 PENDING_APPROVAL/APPROVED/SUBMITTED 묶음이 있으면 409를 내는 줄 제거.
- 현재 코드는 정상이다. 별도 확인에서 두 번째 요청은 `409 payout-batch-exists`였다.
- 왜 위험: 이 가드가 사라지면 DB 유일 인덱스(`payout_batch_key`)가 막아도 500으로 새고, 동시 요청에서는 상계가 두 번 적용될 수 있다(§4 F1).
- 제안: 같은 날짜로 두 번 `createPayoutBatch` → 409를 단언. test-int에서 동시 요청도.

### [중간] M13: 지급 묶음 단계의 KYC 플래그 재확인이 시험에 없다
- 바꾼 것: 묶음 생성 시 `status==='VERIFIED' && businessVerified && representativeVerified`를 `status==='VERIFIED'`만으로 약화.
- 왜 위험: 정산서 계산 뒤 KYC 기록이 바뀌어도 묶음이 지급을 진행할 수 있다(방어선 상실).
- 왜 못 잡나: 묶음 시험의 A는 모든 플래그가 true, B는 PENDING뿐이다.
- 제안: `status='VERIFIED'`, `businessVerified=false`인 KYC로 묶음 생성 → 409 `payout-kyc-required`.

### [중간] M17: 포트원 잔액 필수 검사가 시험에 없다
- 바꾼 것: `pg==='PORTONE' && !portoneBalance`이면 422를 내는 줄 제거.
- 현재 코드는 정상이다. 별도 확인에서 잔액 없이 호출하면 `422 invalid-query`였다.
- 왜 위험: 잔액 확인 없이 지급 묶음이 만들어져 결제사 잔액 부족·지급 실패로 이어질 수 있다.
- 제안: 포트원 묶음 생성에서 `portoneBalance`를 빼고 422를 단언.

### [중간] M16: 전액 상계된 0원 정산서의 처리 시험이 없다
- 바꾼 것: `remaining > 0`일 때만 묶음에 넣는 조건을 `>= 0`으로 바꿔 0원 정산서도 넣게 함.
- 왜 위험: 0원 지급 건이 결제사로 나가거나 `statementCount`가 부풀 수 있다. 상태는 CARRIED_OVER인데 묶음에 들어가는 모순도 생긴다.
- 왜 못 잡나: 시험은 전액 상계 1건만 보고 `statementCount`·지급 건 수를 단언하지 않는다.
- 제안: 전액 상계 뒤 `statementCount`와 `listPayouts`에 0원 건이 없음을 단언.

### [중간] M19: COMPLETED 지급의 PAID 전이가 시험에 없다
- 바꾼 것: `nextStatus==='COMPLETED' ? 'PAID' : 'SCHEDULED'`를 항상 SCHEDULED로.
- 왜 위험: 결제사가 완료를 돌려줘도 정산서가 PAID로 끝나지 않아 재지급·상태 불일치가 생긴다.
- 왜 못 잡나: 시험 게이트웨이(`ManualPortonePayoutGateway`)가 SUBMITTED만 돌려준다. COMPLETED를 돌려주는 가짜 게이트웨이 시험이 없다.
- 제안: COMPLETED를 돌려주는 게이트웨이로 실행 → 정산서 PAID, 묶음 COMPLETED를 단언.

### [낮음] M21: `confirmDue` 경계 시험이 없다
- 바꾼 것: `now >= disputeDueAt`을 `now > disputeDueAt`으로.
- 왜 위험: 이의 기한이 정확히 끝난 시각의 확정 여부가 달라진다. `dispute`는 같은 시각에 `>`를 써서, 그 순간 이의와 확정이 둘 다 가능한 경계 불일치도 있다.
- 왜 못 잡나: `confirmDue`를 부르는 시험이 없다(호출자도 없다, §4 F3).
- 제안: 기한 1ms 전·정각·1ms 뒤 3케이스. `dispute`와 같은 경계 규칙으로 맞춘다.

### [중간] M22: 포트원 일괄 지급 실행의 상태 가드 시험이 없다
- 바꾼 것: `recordPortoneExecution`에서 `status`가 APPROVED/SUBMITTED인지 보는 줄 제거.
- 왜 위험: 승인 대기(PENDING_APPROVAL)나 실패 묶음도 SUBMITTED로 바뀌어, 승인 없이 실행된 것처럼 보일 수 있다.
- 왜 못 잡나: `recordPortoneExecution` 단위 시험이 없다.
- 제안: PENDING_APPROVAL 묶음에 실행 기록 → 409, APPROVED/SUBMITTED만 허용.

### [낮음] M24: 예금주 대표자명 대체 시험이 없다
- 바꾼 것: 출금 대사에서 예금주가 법인명과 다를 때 대표자명도 비교하는 대체 경로 제거.
- 왜 위험: 개인사업자처럼 예금주가 대표자명인 정상 출금이 MISMATCH로 잘못 잡혀 CS 건이 생긴다.
- 왜 못 잡나: 시험의 `holderName`이 항상 법인명과 같다.
- 제안: `holderName='김대표'`, `legalName='주식회사 피켓엔터'`, `representative='김대표'` → MATCHED.

### [낮음] M26: 배상 송금 gRPC 오류 매핑 시험이 없다
- 바꾼 것: `NOT_FOUND`를 `INVALID_ARGUMENT`로 뭉갬.
- 왜 위험: ops-svc가 없는 송금 건을 잘못된 입력으로 오해해 재시도·안내가 달라진다.
- 왜 못 잡나: gRPC 시험은 성공·멱등만 본다.
- 제안: 없는 `transfer_id`로 Get → `NOT_FOUND`를 단언. 잘못된 ID로 Request → `INVALID_ARGUMENT`도.

## 4. 실제 결함 후보

### [높음] M1-F1: 미수금 상계와 지급 묶음 저장이 한 트랜잭션이 아니다
- 영역/배치: payment 정산·미수금 상계(BAT-610 잔여, settlement §7).
- 위치: `services/payment-svc/src/modules/settlement/application/settlements.ts:254-299` (상계 루프와 `insertPayoutBatch`), 저장 포트 `services/payment-svc/src/modules/settlement/domain/ports.ts:33-66`.
- 증거: 실패 주입 확인. `insertPayoutBatch`가 던지게 한 뒤 `createPayoutBatch`를 부르면:
  - `receivableRemaining: 0`, `receivableStatus: "CLOSED"`
  - `statementOffset: 445000`, `statementPayout: 8455000`
  - `moves: 1`
  - 배치 행은 없음.
  즉 미수금은 이미 닫히고 정산서 금액은 이미 깎였는데 지급 묶음은 만들어지지 않았다. `docs/features/settlement.md:293`는 “남은 금액은 같은 트랜잭션에서 … 함께 고치고”라고 요구한다.
- 왜 문제인가:
  - 배치 저장 실패(유일 인덱스 충돌, DB 오류) 때 상계만 남아, 지급 묶음 없이 미수금이 회수 처리되고 정산서 지급액이 깎인다. 파트너 화면에는 “왜 깎였는지”를 설명할 배치가 없다.
  - 같은 날짜 동시 요청이 둘 다 사전 검사를 통과하면 둘 다 상계 이동 기록을 남기고, 한쪽 배치만 유일 인덱스로 살아남아 **이동 기록 합이 미수금 금액을 넘는** 장부 불일치가 된다.
  - 실패한 묶음이 재시도되지 않으면 파트너는 그 지급을 받지 못한 채 정산서만 깎인 상태로 남는다. 복구·감사가 수동 DB 조작에 기대게 된다.
- 재현/확인: 임시 시험에서 `MemorySettlementStore`를 상속해 `insertPayoutBatch`만 던지게 하고 위 값을 기록했다(시험 파일은 실행 뒤 삭제, `git status` 깨끗).
- 같은 클래스의 다른 곳: `dispute`는 `insertDispute` 뒤 `saveStatement`를 따로 써서 이의 행만 남고 상태가 DISPUTED가 아닐 수 있다(`settlements.ts:86-87`). `executeBatch`도 묶음 상태 저장 뒤 정산서 상태를 따로 저장한다(`settlements.ts:350-352`). 돈이 걸린 `createPayoutBatch`를 먼저 고치고, 같은 트랜잭션 경계를 나머지에도 적용한다.
- 제안 수정: `createPayoutBatch` 전체를 DB 트랜잭션으로 감싼다. `SettlementStore`에 `transaction(fn)` 또는 `withTransaction`을 추가하고, 상계·이동 기록·정산서 저장·배치 insert를 같은 `tx`로 보낸다. 유일 인덱스 충돌은 409 `payout-batch-exists`로 매핑하고 롤백한다. test-int에 실패 주입·동시 요청 시험을 둔다.
- 확신도: 높음

### [중간] M1-F2: 배상금 미리 지급(COMPENSATION_ADVANCE)이 다른 결제사 정산서에서 상계되지 않는다
- 영역/배치: payment 정산·미수금, 배상 송금(BAT-425 GAT-130, settlement §7).
- 위치: `services/payment-svc/src/modules/settlement/application/settlements.ts:259` — `listOpenReceivables(s.promoterId, input.pg)`가 모든 미수금을 지급 묶음의 결제사로 제한한다.
- 증거: 별도 확인에서 A의 TOSS 미수금 `COMPENSATION_ADVANCE` 100,000원을 만든 뒤 PORTONE 지급 묶음을 만들었다.
  - `portonePayoutAmount: 8,900,000`
  - `batchTotal: 8,900,000` (상계 0)
  - `receivableRemaining: 100,000` (그대로)
  같은 결제사(TOSS) 미수금은 기존 시험에서 정상 상계된다.
- 왜 문제인가: `docs/features/settlement.md:287`는 “PEAKET이 자기 계좌로 보낸 배상금 미리 지급은 결제사와 무관하게 상계한다”고 정한다. 지금은 배상금을 먼저 보낸 결제사와 다음 정산서의 결제사가 다르면 회수되지 않고 미수금으로 남는다. 회수 지연·손실로 이어진다.
- 재현/확인: 위 확인은 `MemorySettlementStore`·`MemorySettlementPaymentSource`로 실제 유스케이스를 돌린 결과다.
- 제안 수정: 상계 대상을 `listOpenReceivables(s.promoterId)` 전체로 읽고, `r.pg === input.pg || r.cause === 'COMPENSATION_ADVANCE'`만 적용한다. `recordReceivable`의 `pg`는 원 결제사로 남기되 상계 범위를 원인별로 나눈다. 시험: TOSS 배상 미수금 + PORTONE 묶음 → 상계.
- 확신도: 높음

### [중간] M1-F3: 이의 기간 끝 자동 확정(`confirmDue`)이 어디에도 연결되지 않았다
- 영역/배치: payment 정산 상태 전이(settlement §4.2·§4.4).
- 위치: `services/payment-svc/src/modules/settlement/application/settlements.ts:196` (`confirmDue`), `:230` (`createPayoutBatch`는 CONFIRMED만 조회), `services/payment-svc/src/modules/settlement/adapters/db/drizzle-settlement-store.ts:282`.
- 증거:
  - 저장소 전체에서 `confirmDue` 호출자는 정의 1곳뿐이다(컨트롤러·워커·cron 없음).
  - 정산서는 계산 직후 NOTIFIED가 되고, `createPayoutBatch`는 CONFIRMED만 모은다. 그런데 CONFIRMED로 바꾸는 경로가 `confirmDue`(호출자 0)와 테스트의 수동 `saveStatement`뿐이다.
  - 따라서 운영에서 정상 흐름만으로는 지급 묶음이 `payout-batch-empty`로 막힌다. 누군가 DB 상태를 직접 CONFIRMED로 고쳐야 한다.
- 왜 문제인가: 이의 없이 기간이 끝나면 자동 확정한다는 정본과 달리, 자동 확정이 실행되지 않아 지급이 진행되지 않는다. 수동 DB 조작은 감사·재현이 어렵다.
- 덧붙임: `confirmDue`는 `now >= disputeDueAt`, `dispute`는 `now > disputeDueAt`을 써서 정각에 둘 다 가능한 경계 불일치가 있다. 자동 확정을 연결할 때 같이 맞춘다.
- 재현/확인: `grep -R "confirmDue"` 결과 정의 1건. `createPayoutBatch`의 `listConfirmed`와 store의 `status='CONFIRMED'` 조건 확인.
- 제안 수정: ① 주기 워커(예: 1분)나 내부 엔드포인트로 `confirmDue`를 호출하고, ② `createPayoutBatch` 전에 기한 지난 NOTIFIED를 확정하는 단일 트랜잭션 경로를 둔다. 시험: 기한 전·정각·후, 그리고 자동 확정 뒤 묶음 생성.
- 확신도: 높음(저장소 안 호출자 0). 저장소 밖 외부 스케줄러가 있다면 중간.
