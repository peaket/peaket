- **증거**:
  - `approvalModeOf`는 `KILL_SWITCH`·`AUTOMATION_STOP`을 `NONE`(즉시 실행), `SALE_STOP`·`SALE_RESUME`·`BOT_LEVEL`·`DEGRADED_MODE`를 `TWO`로 둔다.

  - `canApprove`도 `state === 'PENDING_APPROVAL' && requestedBy !== me`만 본다.
  - `services/ops-svc/test-int/sale-stop-control.int.test.ts:100-114`는 operator가 요청하고 commander가 승인하는 경우만 본다. operator가 승인하는 경우의 시험이 없다.
- **왜 문제인가**: 문서 `docs/features/control-tower.md` §3은 판매 일시정지(명령 3)를 commander 1인 실행, 판매 중지·재개를 "요청자가 아닌 commander가 승인"으로 정한다. 지금은 operator 두 명이면 commander 없이 `SALE_STOP`·`SALE_RESUME`을 승인해 판매를 멈추거나 다시 열 수 있다. `KILL_SWITCH`·`AUTOMATION_STOP`은 operator가 접수하면 `APPROVED`로 만들어 곧바로 실행을 시도한다(현재 대상 미연결로 `target-not-wired` FAILED). 대상이 연결되는 순간 operator가 commander 권한의 비상 정지를 실행하게 된다. 감사 기록에도 승인자·요청자가 operator로 남아, commander 승인을 거친 것처럼 보이지 않는다.
- **재현/확인**: 코드 대조. `SALE_STOP`은 실제 집행 경로가 연결되어 있으므로(구매·대기열 내부 HTTP/제어 gRPC), operator A가 요청하고 operator B가 `POST /v1/ops/commands/{id}/approvals`를 부르면 200·`SUCCEEDED`가 된다. 기존 시험은 commander 승인만 본다.
- **제안 수정**: `type → { requesterRoles, approverRoles }` 표를 도메인에 두고 `CreateCommand`·`#decide`·`RetryCommand`·`canApprove`에서 함께 검사한다. 예: `SALE_STOP`·`SALE_RESUME` 승인자는 `commander`, `KILL_SWITCH`·`AUTOMATION_STOP` 접수자는 `commander`, `BOT_LEVEL`·`DEGRADED_MODE` 접수자는 `commander`. operator가 `SALE_STOP`을 승인하면 403, operator가 실패한 `KILL_SWITCH`를 재시도하면 403인 시험을 더한다.

### [높음] B3-H03: 감사 체인 검증이 기록 내용·연쇄를 다시 계산하지 않아 원본 행 변조를 탐지하지 못한다
- **영역/배치**: ops-svc 감사 체인·체크포인트, BAT-465 GAT-310·R-584
- **위치**:
  - `services/ops-svc/src/modules/audit/audit.ts:78-89`(`appendAuditIn`: 해시만 저장)
  - `services/ops-svc/migrations/0000_ops_command_audit.sql:49-57`(`audit_chain` 칸: `record_type`, `record_id`, `record_sha256`, `mac`, `leaf_salt`, `created_at`)
  - `services/ops-svc/src/modules/audit/checkpoint.ts:188-220`(`verify`: 저장된 해시의 루트만 재계산)
  - `services/ops-svc/test-int/command-execution.int.test.ts:218-222`(변조 시험은 `record_sha256` 한 칸만 바꾼다)
- **증거**:
  - `appendAuditIn`은 `auditHash(prevHash, record)`로 `record_sha256`을 만들지만, 정규화한 기록 JSON과 `prevHash`를 `audit_chain`에 저장하지 않는다. `leaf_salt`는 난수로 넣기만 하고 해시에 섞지 않는다.
  - `verify`는 `entriesBetween`이 돌려준 `(seq, hash)`로 `auditCheckpointRoot`를 다시 계산해 `root_hash`와 비교하고, 직전 체크포인트의 `root_hash`와 `prev_hash`를 비교한다. 각 기록의 `record_sha256`을 원본 행(예: `ops_command.reason`, `command_event.actor_ref`)에서 다시 계산하지 않고, `hash(prev, record)` 연쇄도 검사하지 않는다.
  - 통합 시험은 `audit_chain.record_sha256`을 `00…`로 바꿔 `rootValid:false`를 보는 것까지만 한다. `ops_command.reason`을 바꾸는 시험은 없다.
- **왜 문제인가**: 감사 체인의 목적은 DB 접근자가 원본 기록을 고쳐도 탐지하는 것이다. 지금은 `ops_command.reason`이나 `command_event.actor_ref`를 `UPDATE`해도 `audit_chain` 행은 그대로이므로 `/v1/ops/audit-checkpoints/{id}/verification`이 `valid:true`를 돌려준다. "감사 기록이 변조되지 않았다"는 API·문서의 주장이 성립하지 않는다. HMAC `mac`·외부 앵커가 후속이라는 점과 별개로, 원본 내용을 다시 계산하지 않는 것은 지금 구현의 구조적 공백이다.
- **재현/확인**: 코드 대조. DB가 있으면 `update ops_command set reason='조작' where id=<commandId>;` 뒤 `GET /v1/ops/audit-checkpoints/<cp>/verification`이 `valid:true`인지 보면 된다. 현재 시험은 이 경우를 덮지 않는다.
- **제안 수정**: `audit_chain`에 정규화 기록 JSON(또는 원본 행을 가리키는 불변 참조와 내용 해시)을 저장하고, `verify`에서 `prev_hash`와 내용으로 각 `record_sha256`을 다시 계산한다. 원본 행의 `UPDATE`를 막는 트리거/권한을 두고, `ops_command.reason` 변조 시 `valid:false`가 되는 통합 시험을 더한다. `mac`·S3/OTS 앵커는 별도 후속으로 둘 수 있다.
- **확신도**: 높음

## 문서화된 후속으로 확인했으나 이번 보고서의 발견으로 세지 않은 것

아래는 코드·문서에 이미 "후속"으로 적혀 있어 새 결함으로 세지 않았다. 다만 배포 전 위험도가 높은 항목은 위 발견과 함께 다시 판단해야 한다.

- 감사 체인의 HMAC `mac` 미채움, `audit_chain_head.mac_seq`/`last_mac` 없음(`docs/features/control-tower.md:219`, `docs/data.md`).
- S3 Object Lock·OpenTimestamps 앵커 미연결, `anchorRef`가 항상 `local:<checkpointId>`, `immutable-anchor.ts`는 어댑터 경계만 있고 `AuditCheckpointService`에 연결되지 않음(`docs/review/measurements/BAT-465-R584-wave.md:67`).
- SSE 1회 100건 상한, 제어 판 번호 `updatedAtMs` 충돌, SSE 프록시 차단 시 수동 새로고침, 제어 gRPC 한 파드 ack(`docs/review/measurements/BAT-465-R584-wave.md:53,68`). 이 가운데 한 파드 ack는 B3-M16으로, SSE 계약은 B3-M13으로 따로 적었다.
- 명령 재인증·멱등키 미적용(`docs/review/measurements/R-552-wave.md:43`, `R-558-wave.md:48`) — B3-M02로 적었다.
- 회차 취소 판매 중지 확인·재인증 미강제(`docs/review/measurements/BAT-425-wave5.md:29,52`) — B3-M03으로 적었다.
- 지급 승인 감사 체인 미연결(`docs/review/measurements/BAT-610-remainder.md:55,77`) — B3-H02로 적었다.
- 승인 업무 EXECUTING 고착(`docs/review/measurements/BAT-610-remainder.md:58`) — B3-M07로 적었다.
- SCR-048 판매 승인 화면·core-svc `RecordSaleReviewResult`·정산 보류는 아직(`docs/features/transfer-refund.md:54`).
- `notification_job`·`notification_delivery` 원장, Kafka `trade.orders` 소비자, 실제 푸시·이메일 연결은 후속(`docs/features/notify.md:150`).
- mTLS 선택지·관리형 기기·사설 CA PoC는 후속(`docs/features/offline-gate.md:158`).
- `PEAKET_INTERNAL_TOKEN`이 비면 내부 경로 검사를 끄는 규약(`packages/platform/src/auth.ts:83-95`). 운영에서 비어 있으면 내부 명령·경보·CS 경로가 열리므로, 배포 설정 검사가 필요하다.

- **proto**: `peaket.control.v1.ControlReceiver.ApplyControl`, `peaket.purchase.v1.EventRefundService`, `peaket.ticket.v1.ScannerDeviceService`.
