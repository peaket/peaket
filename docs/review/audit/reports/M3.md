## 3. 놓친 변이 = 시험 공백

### [중간] M3-G1: 판매 상태 Redis Lua의 판 비교·TTL·셈 신선도를 test-int가 단언하지 않는다
- 영역/배치: queue-svc 판매 상태(B2, `docs/features/queue-admission.md` §4, ADR-0214·0219).
- 위치: `services/queue-svc/src/modules/sale/adapters/redis-sale-states.ts:14-40`, `services/queue-svc/test-int/sale-state.int.test.ts:56-109`.
- 증거: test-int는 판 5 → 6 → 7만 쓴다(56-79행). 같은 판 재적용(STALE), 옛 판, `notice`의 `PEXPIRETIME`, `notice.soldOutLastSeq` 쓰기, 같은 판의 더 이른 셈을 **한 번도 단언하지 않는다**. 98-109행도 셈을 한 번만 쓴다. 그래서 `cur >= v` → `>`(같은 판 덮어씀), `extend()` 제거(TTL 미연장), `at >= seatsAtMs` → `>`(같은 시각 셈 덮어씀), 매진 시 `soldOutLastSeq` HSET 제거가 test-int를 통과할 것으로 보인다. 단위 시험은 `MemorySaleStates`만 보므로 이 Lua를 실행하지 않는다.
- 왜 문제인가: 실제 Valkey에서 도는 규칙이 바뀌어도 초록이 유지된다. 같은 판 사건이 다시 오면서 `SOLD_OUT`을 `ON_SALE`로 되돌리거나, `ENDED`를 덮으면 번호 발급·매진 차단이 흔들린다. 좌석·대기 순번에 닿는 고위험 경로다.
- 재현/확인: Docker 금지라 실행하지 못했다. 정적 대조로 확인했다. 2단계에서 `sale-state.int.test.ts`에 ① 같은 판 재적용 STALE ② `notice` PEXPIRETIME = 판매 종료+1일 ③ 같은 판의 더 이른 셈 무시 단언을 먼저 넣고 변이를 돌리는 것을 제안한다.
- 제안 수정: `sale-state.int.test.ts`에 위 3개 단언 추가. 그 뒤 Lua 변이 3개를 실행해 잡힘을 확인.
- 확신도: 중간(정적 확인, 실행 전).

### [낮음] M3-G2: HMAC 종류 문자열이 실제로 MAC에 묶이는지 시험이 확인하지 않는다
- 영역/배치: queue-svc 진입 토큰(ASVS v5.0.0-9.2.2, ADR-0053 결정 13).
- 위치: `services/queue-svc/src/modules/entry/adapters/hmac-tokens.ts:85`, `services/queue-svc/test/tokens.test.ts:64-70`.
- 증거: `#mac`에서 `${kind}.`를 빼도 12개 시험이 모두 통과했다. “종류문자열이달라 서로 바꿔 쓰지 못한다” 시험은 토큰을 서로의 자리에 넣어 null을 보는데, 그 null은 MAC 불일치가 아니라 **Zod 스키마 불일치** 때문이다(사전검증 `i0`·`exp`, 대기표 `s`·`g`·`seg`·`rq`, 참가 `iat`만).
- 왜 문제인가: 지금은 스키마가 달라 실제 우회가 되지 않는다. 그러나 클레임 모양이 비슷해지는 순간 종류 분리가 조용히 사라진다. 시험 이름이 보장을 주장하지만 실제로는 다른 것(스키마)을 검증한다.
- 재현/확인: 변이 #26. `pnpm.cmd --filter @peaket/queue-svc exec vitest run test/tokens.test.ts` → 12 통과.
- 제안 수정: 같은 본문이 두 종류 스키마를 모두 만족하도록 만든 뒤(또는 테스트 전용으로 `#mac`을 노출해) 같은 본문·다른 종류의 MAC이 다름을 단언한다. 최소안: `HmacQueueTokens`에 테스트용 `macForTest(kind, signed)`를 두고 `kind`가 다르면 결과가 다름을 확인.
- 확신도: 높음.

### [낮음] M3-G3: 우선 구매 권리의 정확한 만료 경계(`now === expiresAtMs`)를 아무 시험도 보지 않는다
- 영역/배치: queue-svc `q:prio` 사본(GAT-135, ADR-0171).
- 위치: `services/queue-svc/src/modules/admission/domain/priority-grant.ts:33`, `test/priority-grant.test.ts:135-138`, `test-int/priority-grant.int.test.ts:125-130`.
- 증거: `nowMs < expiresAtMs` → `<=` 변이가 단위 9개·test-int 모두 통과할 것으로 보인다. 단위는 `+1_000` 뒤 `+2_000`, 통합은 `+150` 뒤 400ms 대기만 본다.
- 왜 문제인가: 만료 시각과 같은 1ms 동안 권리가 살아 있다. 영향은 작지만 “만료 전”의 경계가 계약과 어긋난다.
- 재현/확인: 변이 #8. `test/priority-grant.test.ts` 9 통과.
- 제안 수정: fakeClock을 `expiresAtMs`와 정확히 같게 둔 사례를 추가해 404를 단언.
- 확신도: 높음.

### [낮음] M3-G4: 메모리 우선 구매 저장소가 만료 사본을 지우는지 시험이 보지 않는다
- 영역/배치: queue-svc 시험 대역(`MemoryPriorityGrantStore`).
- 위치: `services/queue-svc/src/modules/admission/adapters/memory-priority-grants.ts:10`.
- 증거: 만료 시 `delete`를 빼고 `{changed:false}`만 돌려도 9개가 통과한다. 입장은 도메인의 만료 검사로 404라 겉보기 같다.
- 왜 문제인가: 시험 대역이 실제 Redis(만료 시 `DEL`)와 달라져, 저장소 정리·키 누수를 단위에서 못 본다.
- 재현/확인: 변이 #10. 9 통과.
- 제안 수정: 만료 뒤 `grants.copies.size`가 0임을 단언하거나, 실제 구현처럼 `delete`를 유지하고 그 결과를 시험에 넣는다.
- 확신도: 높음.

### [낮음] M3-G5: 같은 셈 시각(`countedAtMs`)의 덮어쓰기 규칙을 단위·통합 모두 보지 않는다
- 영역/배치: queue-svc 판매 상태 셈(ADR-0219 결정 5).
- 위치: `services/queue-svc/src/modules/sale/adapters/memory-sale-states.ts:42`, `redis-sale-states.ts:20`.
- 증거: `at >= countedAtMs` → `>` 변이가 `test/sale-state.test.ts` 19개를 통과한다. test-int도 셈을 한 번만 쓴다.
- 왜 문제인가: 같은 ms에 늦게 도착한 낡은 셈이 새 셈을 덮어 `remainingSeats`가 한 사건만큼 뒤로 갈 수 있다. 화면·파일의 잔여 좌석이 흔들린다.
- 재현/확인: 변이 #15. 19 통과.
- 제안 수정: 같은 `countedAtMs`·다른 `available` 두 사건을 보내 첫 값이 남는지 단언(단위와 Lua 양쪽).
- 확신도: 높음.

### [낮음] M3-G6: 축소 운영 한도의 정확한 10초 경계를 보지 않는다
- 영역/배치: queue-svc 축소 운영 rate limit(B-T6②, ADR-0248).
- 위치: `services/queue-svc/src/modules/entry/adapters/memory-degraded-limits.ts:40`, `test/degraded-limits.test.ts:22`.
- 증거: 창 조건 `< WINDOW_MS` → `<=` 변이가 18개를 통과한다. 시험은 `advance(10_001)`만 쓴다.
- 왜 문제인가: 경계에서 1ms 더 막는 보수적 동작이라 보안 구멍은 아니다. 다만 계약(“10초에 5회”)의 경계가 시험으로 고정되지 않는다.
- 재현/확인: 변이 #21. 18 통과.
- 제안 수정: 정확히 `advance(10_000)`에서 허용되는지(또는 막히는지) 계약을 정해 단언.
- 확신도: 높음.

### [낮음] M3-G7: 예매 제한 gRPC의 LIFTED 매핑·나노초 변환을 단위 시험이 보지 않는다(통합이 덮음)
- 영역/배치: queue-svc `BookingRestrictionService`(Q-T59, GAT-310).
- 위치: `services/queue-svc/src/modules/admission/inbound/booking-restriction.grpc.ts:14,26`, `test/booking-restriction.test.ts:20-33`.
- 증거: LIFTED를 ACTIVE로 바꾸거나 `nanos`를 ms로 나누지 않아도 단위 2개가 통과한다. test-int `booking-restriction.int.test.ts:79-84`가 `nanos:200_000_000`과 LIFTED를 실제로 보내 덮는다.
- 왜 문제인가: 단위만 도는 빠른 피드백에서 매핑 회귀를 못 잡는다. 통합이 있으니 배포 위험은 낮다.
- 재현/확인: 변이 #6·#7. 2 통과.
- 제안 수정: 단위 gRPC 시험에 LIFTED 요청과 `nanos: 200_000_000`을 추가.
- 확신도: 높음.

### [낮음] M3-G8: 우선 구매 입장 경로가 “ACTIVE + 미래 until”을 보지 않는다
- 영역/배치: queue-svc 입장 확정의 예매 제한(GAT-310).
- 위치: `test/priority-grant.test.ts:160-169`.
- 증거: 이 시험은 `{st:'ACTIVE'}`(끝 없음)와 `{st:'ACTIVE', untilMs: NOW-1}`(과거)만 둔다. `untilMs: NOW+1h`인 ACTIVE가 403인지 보지 않는다. 변이 #2(끝 시각이 있으면 무조건 막기)를 이 시험은 놓쳤고, 도메인 단위 `booking-restriction.test.ts`가 잡았다.
- 왜 문제인가: 입장 확정과 도메인 판정의 조합에서 미래 끝 시각이 실제로 막히는지 통합적으로 고정되지 않는다.
- 재현/확인: 변이 #2 1차 실행. `priority-grant.test.ts` 9 통과.
- 제안 수정: `restrictions.rows.set(ACCOUNT, { st:'ACTIVE', untilMs: NOW + 3_600_000 })`로 403을 단언.
- 확신도: 높음.

## 5. 원복·재현

- 마지막 확인: `git status --short` → 출력 없음. `git diff --stat` → 출력 없음.
- 변이 때마다 `git checkout -- <파일>`로 원복했고, 마지막에 `admission-lua.ts`까지 원복했다.
- 빌드한 `packages/shuffle/dist`는 `.gitignore` 대상이라 상태에 나타나지 않는다. 추적 파일은 바뀌지 않았다.
- 재현 명령 예: `pnpm.cmd --filter @peaket/queue-svc exec vitest run test/priority-grant.test.ts`.
- Docker 명령은 한 번도 실행하지 않았다. 2단계는 go 신호를 기다린다.
