## 발견

### [중간] B2-1: 예매 제한 사본 `q:rst:{account}`에 TTL이 없어 문서가 정한 보존 기간을 지키지 않는다
- 영역/배치: `q:rst` 만료·보존(HOT/GAT-310 계열, R-575·R-593)
- 위치: `services/queue-svc/src/modules/admission/adapters/booking-restriction-lua.ts:3-13`, `services/queue-svc/src/modules/admission/domain/booking-restriction.ts:26`
- 증거: 쓰기 Lua는 `HSET`만 하고 `PEXPIREAT`·`EXPIRE`를 부르지 않는다. `RedisBookingRestrictions.apply`도 TTL을 넘기지 않는다. 반면 `docs/data.md:2470`의 `q:rst:{account}` 행은 "수명은 ACTIVE면 끝 시각 + 1일(끝이 없으면 30일 [가정]), LIFTED면 30일 [가정]이다"라고 못박는다. 키 이름에 해시 태그도 없고, 정비 작업에서 지우는 코드도 찾지 못했다(`q:rst` 문자열은 위 두 파일에만 있다).
- 왜 문제인가: 예매 제한은 개인정보(계정 ID + 제한 ID + 사유의 근거)다. 제한이 풀린 뒤(LIFTED)에도 키가 영구히 남아, 문서가 정한 파기 기한을 넘겨 보존된다. 또 `maxmemory-policy noeviction`(docs/data.md §3)이라 키가 쌓이면 지워지지 않고 메모리를 계속 먹는다. 기능적으로는 LIFTED라 입장을 막지 않으므로 좌석·돈 손실은 없다.
- 재현/확인: `booking-restriction-lua.ts` 전문에 만료 명령이 없음. `docs/data.md:2470`의 TTL 문장과 직접 어긋난다.
- 제안 수정: 쓰기 Lua에서 `until`이 있으면 `PEXPIREAT = until + 1일`, 없으면 `PEXPIREAT = now + 30일`, LIFTED면 `now + 30일`을 건다(판 번호가 클 때만). 문서의 [가정] 값을 그대로 상수로 두면 된다.
- 확신도: 높음

### [중간] B2-2: 우선 구매 입장이 입장 토큰 `lst`(판매 자격 명단 키)를 싣지 않는다
- 영역/배치: 우선 구매 입장(GAT-135, R-561·R-575) · 판매 자격 명단(HOT-253, ADR-0265)
- 위치: `services/queue-svc/src/modules/admission/application/confirm-admission.ts:197-220`(`#priority`), 대조: 같은 파일 `:140-152`(`candidateEligibilityLists`)
- 증거: 일반 입장 경로는 `candidateEligibilityLists(schedule)`을 구해 `store.admit`에 넘기고, `ADMIT_LUA`의 `eligKeys()`가 `lst`를 채운다. `#priority`는 `signer.sign({...})`에 `lists`를 넘기지 않아 `prio`만 실린다. `docs/features/queue-admission.md:261`은 "입장 토큰 `lst`: … 우선 구매 입장(GAT-135)도 같다"라고 적는다. `docs/features/seat-hold.md:177`은 홀드의 `buyer.lists`가 입장 토큰의 `lst`라고 적는다.
- 왜 문제인가: 문서대로라면 명단이 걸린 선예매 회차에서 우선 구매 권리자는 `lst` 없는 토큰을 받는다. 그 토큰으로 일반 홀드를 하면 `evaluateSalePolicy`가 `PRESALE_ONLY`로 거부해(=`sale-policy-denied`) 취소표 배상으로 받은 권리가 무산될 수 있다. 다만 purchase-svc의 `modules/priority` 경로에는 `lists`·`salePolicy` 참조가 없어, 현재 구현된 PRIORITY 홀드·주문은 정책 평가를 거치지 않는다(그래서 지금 당장의 매출 손실은 확인되지 않는다). 그 경우에도 계약(문서)과 코드가 어긋나 있고, 이후 우선 주문이 정책 평가를 타게 되면 바로 깨진다.
- 재현/확인: `#priority`가 만든 토큰 클레임에 `lst`가 없다(코드 대조). purchase-svc `modules/priority` 전체에서 `lists|salePolicy|entryGate` 검색 결과 0건.
- 제안 수정: `#priority`에서도 `candidateEligibilityLists(schedule)`을 구해 `ADMIT_LUA`의 `eligKeys()`와 같은 규칙(계정이 든 키만, 글자 차례, 최대 10개)으로 `lists`를 채워 `sign`에 넘긴다. Redis 읽기가 늘어나는 것이 부담이면 `q:{event:E}:elig:*`를 `SISMEMBER`로 한 번에 보는 작은 Lua를 쓴다.
- 확신도: 중간(코드·문서 불일치는 확실, 실제 매출 영향은 우선 주문 경로가 정책을 타는지에 달림)

### [낮음] B2-3: 입장 확정이 계정 ID 모양을 먼저 보지 않아, UUID가 아닌 계정에서 500이 난다

## 확인했으나 문제 없음으로 본 것

- **HMAC 토큰**: 종류 문자열(`PEAKET-preverify-v1`·`PEAKET-queue-v1`·`PEAKET-lobby-v1`)이 서명 대상 앞에 붙어 토큰 자리 바꿔치기를 막고, MAC을 상수 시간으로 견준 뒤에만 본문을 읽으며, kid는 설정된 키에서만 찾고, 같은 바이트로 읽히는 base64url 변형(`=`, 끝 비트)을 거절한다. 대기표에 발급 시각이 없어 같은 요청 ID의 재시도가 같은 문자열·같은 해시를 받는다.
- **도착 시각 쿠키**: 엣지와 queue-svc의 MAC 계산이 같은 바이트열(`PEAKET-arrival-v1.` + 앞 여섯 칸)이고, 키를 utf8 바이트로 쓰는 점도 양쪽이 같다. 회차·sid·10분·5초 미래 허용을 확인하고, `q:arr:{reqId}:E`의 `SET NX`로 한 번만 받는다. Degraded가 아닐 때는 `x-peaket-arrival` 머리를 먼저 지운다.
- **1인 1순번·입장 재확인**: 진입 ①이 `q:adm`을 먼저 보고, 입장 확정 ②가 `q:adm`을 `{대기표 해시}:{요청 표지}`로 잡아 다른 대기표면 `DUP`으로 거절하며 그 번호를 빠진 번호로 돌린다. `SOON` 되돌리기는 표지가 같을 때만 지워, 늦게 온 되돌리기가 입장 기록을 지우지 못한다.
- **Lua 원자성·다중 키**: 사람 키(`{pid}` 태그)와 회차 키(`{event:E}` 태그)를 한 Lua로 묶지 못하는 제약을 지키고, 각 단계가 자기 키 안에서만 원자적이다. 실패 시 되돌리기(`release`·`dropOwn`·`markRemoved`)가 값이 이 요청의 것일 때만 동작한다. 클록은 판단이 갈리는 곳(오픈 전·묶음 구간·차례·칸)에서 Redis `TIME`을 쓴다.
- **장애 전환(세대)**: `q:{event:E}:epoch`의 노드 표지와 `pend`(복제 확인 전)를 진입 ②가 먼저 보고, 다르면 아무것도 쓰지 않고 `RB05`로 끝낸다. `RB05_LUA`는 `pend`를 켠 뒤에야 카운터를 올리고, 복제 확인은 `CLIENT INFO` 연결 표지 → 표시 Lua → `WAIT` → 표지 재확인 → 지우기 순서다. 건너뛴 구간의 옛 세대 대기표는 입장 확정이 받는다.
- **PAUSED·매진**: 진입 ②가 번호를 내기 전에 같은 Lua에서 `notice.saleState`를 보고 `SOLD_OUT`·`ENDED`면 선점을 풀고 410으로 끝낸다(매진 판 뒤에 번호가 나가지 않는다). 판매 상태 쓰기는 판 번호가 클 때만 반영하고, 매진이면 `seq`를 읽어 `soldOutLastSeq`를 남기며 지우지 않는다. 엣지 매진 표시는 `SOLD_OUT`일 때 `notice`보다 먼저 켠다.
- **`q:prio`**: 판 번호가 저장한 판보다 클 때만 쓰고, 만료가 지났으면 키를 지우며, TTL을 권리 만료에 맞춘다. 입장 확정은 같은 계정·회차 사본이 같은 권리 ID의 `OFFERED`이고 만료 전일 때만 통과하고, 없음·남의 것·만료·이미 산 것을 같은 404로 답한다. 받는 층(gRPC·내부 HTTP)이 계정·회차·권리 ID 모양을 먼저 검증해 키 조각을 깨지 못한다.
- **`q:rst` 판독**: ACTIVE이고 `until` 전일 때만 막고, 칸이 망가졌으면 '제한 없음'으로 숨기지 않고 오류로 드러낸다(닫힌 쪽). 우선 구매 입장도 같은 검사를 먼저 받는다.
- **축소 운영 한도**: trust-svc 판정을 받지 못했을 때(`UNAVAILABLE`)만 기기·pid(호스팅·프록시 대역은 IP도) 10초 5회를 파드 메모리에서 세고 429 `queue-request-limited`로 끝낸다. 로비 참가와 사전 검증 두 경로 모두에 걸려 있다. 통신사 대역은 IP로 막지 않는다.
- **queue-room XSS**: `innerHTML`·`insertAdjacentHTML`·`document.write` 사용이 0건이고, 값은 전부 `textContent`(dom.ts `append`)로 들어간다. 운영 공지(`banner`)·매진 등급·오류 문구도 텍스트 노드다. 링크는 `encodeURIComponent`를 거치고, 허니팟 경로는 `^\/_t\/[A-Za-z0-9_-]{8,64}$`로 모양을 검사한다. `style="…"` 속성도 쓰지 않는다.
- **요청 본문**: 진입·입장 확정은 `text/plain`·`application/json`만 받고(그 밖은 415), 본문 스키마는 `.strict()`로 닫혀 있으며, 진입 본문의 `deviceId`는 사전 검증 토큰의 `d`와 같아야 한다.

## 요약

- 높음 0, 중간 2, 낮음 2.
- 가장 먼저 볼 것: **B2-1**(`q:rst` 무만료 — 개인정보 파기 기한 위반, 고치기 쉬움), **B2-2**(우선 구매 입장의 `lst` 누락 — 문서가 명시한 요구, 선예매 회차에서 우선 구매가 정책 평가를 타면 즉시 깨짐).
