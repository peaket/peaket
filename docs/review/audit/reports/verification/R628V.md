## 4. 시험 공백

1. **prod/staging 무토큰 시작 차단을 고정하는 커밋된 시험이 없다.**
   - `internal-sale-config-token.test.ts`와 `.http.test.ts`는 둘 다 `PEAKET_ENV: 'ci'`에 토큰을 설정한 경우만 본다.
   - `internal-token-boot.test.ts`는 부모 `InternalTokenGuard`를 별도 컨트롤러에 붙여 403/200을 본다. subclass의 `onModuleInit` 상속을 보지 않는다.
   - 따라서 M1(`onModuleInit` 제거)이 기존 시험을 모두 통과한다. R-628의 핵심 주장이 회귀 시험으로 고정되지 않았다.
2. **prod에서 토큰이 설정된 경우의 401/200을 고정하는 커밋된 시험이 없다.**
   - 커밋된 core 시험은 모두 `ci`다. 동작은 prod와 같지만, `INTERNAL_TOKEN_REQUIRED=true`인 prod 경로를 직접 보지 않는다.
3. **상수 시간 비교를 고정하는 시험이 없다.**
   - `internal-token.test.ts`는 “맞음/틀림/길이 다름”만 보고, `timingSafeEqual` 사용 여부는 보지 않는다.
   - M3가 모든 기능 시험을 통과한다.
4. **R-628은 시험을 추가하지 않았다.**
   - 커밋 메시지의 “기존 `internal-sale-config-token.test.ts`는 없어 실행하지 않았고”는 현재 `3a261a47` 기준으로 사실이 아니다. R-625가 추가한 파일이 존재하고 4/4 통과한다. 커밋 시점의 브랜치 상태와 현재 develop이 달랐던 것으로 보이나, 기록은 현재 기준으로 갱신하는 편이 좋다.
5. **`INTERNAL_TOKEN` 공급원 일관성(낮음).**
   - `CatalogModule`은 여전히 `process.env.PEAKET_INTERNAL_TOKEN`을 읽는다. `createService({env})`에 토큰을 넣고 process.env에는 넣지 않으면, prod에서는 fail-closed로 시작이 막히고 ci/local에서는 토큰이 없는 것으로 취급된다. core `main.ts`는 process.env를 쓰므로 현재 배포 경로는 일관되지만, R-620처럼 env 주입으로 통일할 여지가 있다.

## 7. 권고

1. **R-628의 핵심 시험을 추가한다.** 실제 `InternalSaleConfigController`를 최소 Nest 모듈에 넣고 `createService`로 띄워:
   - `prod`/`staging` + 토큰 없음 → 시작 거절
   - `local`/`ci` + 토큰 없음 → 시작 성공
   - `prod` + 토큰 설정 → 헤더 없음/틀림 401, 맞음 200
   이 시험이 M1을 죽인다.
2. **상수 시간 비교를 고정한다.** `sameSecret`이 `timingSafeEqual`을 쓰는지 확인하는 단위 시험(모의/스파이) 또는 정적 시험을 더한다. 이 시험이 M3를 죽인다.
3. 기존 `internal-sale-config-token.test.ts`를 `prod`/`ci` 양쪽으로 매개변수화해 prod 토큰 설정 경로도 커밋된 시험에 넣는다.
4. 가능하면 `CatalogModule`의 `INTERNAL_TOKEN`도 `createService`가 받은 env에서 읽도록 통일한다(현재 core main은 process.env라 급하지 않음).
5. 커밋 메시지의 “기존 시험 없음” 문구를 현재 기준으로 정정한다.

## 8. 결론

R-628의 production 변경은 요구 동작을 만족한다. `onModuleInit` 상속으로 prod/staging 무토큰 시작이 막히고, local/ci는 허용되며, 토큰 설정 시 401/200과 `timingSafeEqual` 비교도 코드상 맞다. 다만 **R-628은 시험을 추가하지 않았고**, 핵심 시작 차단 변이(M1)와 상수 시간 비교 변이(M3)가 기존 시험을 통과한다. 따라서 **조건부 합격**이며, 위 1~2번 시험을 보강한 뒤 완료로 닫는 것이 맞다.
