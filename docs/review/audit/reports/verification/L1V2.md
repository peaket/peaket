## 1. 판정 요약

L1V에서 지적한 네 잔여가 모두 코드와 동작에서 닫혔다.

1. **jti fail-closed**: `reauthJtiStoreFromEnv`가 Redis·local/ci 메모리·그 밖의 닫힌 저장소를 고른다. prod에서 `claim()`이 `false`이고, ops 지급 승인·payment 정산 계좌·core export 재인증이 실제로 403 `reauth-required`로 닫힌다.
2. **core·ops 시작 차단**: `assertInternalGrpcToken`이 두 `main.ts` 맨 앞에서 돈다. `PEAKET_ENV=prod`·토큰 없음이면 두 프로세스 모두 토큰 오류로 exit 1, `ci`면 토큰 게이트를 통과한다.
3. **R-618 noindex**: `generateMetadata`가 `draft`일 때 `robots: { index:false, follow:false }`를 직접 낸다. `?state=` 미리보기 경로도 같은 `doc` 판정을 쓴다.
4. **R-619**: `finish.run`이 실패해도 `finally`가 배정·세션 정리를 계속하고, 한 계정 실패도 다음 계정을 막지 않는다. `accountStatusOf`는 status 칸 없음/NULL/모르는 값을 `null`로 닫고, 메모리 저장소도 세션 저장소 상태 콜백으로 비ACTIVE를 거절한다.

## 5. 남은 위험

1. **회귀 시험 공백**: 이번 수정의 네 경로는 임시 탐침으로만 검증됐다. 저장소에는 `reauthJtiStoreFromEnv`, 세 verifier의 403, core/ops 시작 차단, `generateMetadata` noindex, `withdrawal-finish` finally, `accountStatusOf` 실제 SQL을 직접 검증하는 시험이 없다. 시험 작성자가 추가해야 한다. 특히 변이 5는 실제 SQL 시험이 필요하다.
2. **`jti` 생성자 파라미터가 여전히 선택**: `JwksBookersReauth`·`JwksApprovalVerifier`·`JwksReauthVerifier`는 `jti?: ReauthJtiStore`를 받고 `if (this.#jti)`로 검사한다. 현재 세 배선은 항상 주입하지만, 새 호출자가 `jti`를 빠뜨리면 fail-open이 다시 열린다. 생성자에서 필수로 만들거나 기본값을 `UnavailableReauthJtiStore`로 두는 편이 안전하다.
3. **문서 주석 불일치**: `ReauthJtiStore.claim` 인터페이스 주석은 "저장소를 쓸 수 없으면 던진다"고 하지만, `UnavailableReauthJtiStore`는 이제 `false`를 돌려준다. 동작은 맞고 주석만 낡았다.
4. **`createScannerSession`의 status 칸 없음**: `accountStatusOf`는 칸 없음/NULL/모르는 값을 null로 닫지만, `createScannerSession`은 typed `account.status` 조회라 칸 자체가 없으면 SQL 오류(일반 5xx)로 거절한다. 운영 스키마는 `status NOT NULL`이라 실제 위험은 낮지만, 403 `StaffAccountInactive`로 통일하려면 별도 처리가 필요하다.
5. **noindex 검증 수준**: `generateMetadata` 소스와 타입은 확인했지만, Next.js가 실제 HTML `<meta name="robots">`를 내는지 렌더링/메타데이터 수준 시험은 없다. 기존 web 시험도 소스 기반이다.
6. **메모리 저장소 테스트 준비값**: `MemoryStaffAssignmentStore`는 `accounts` 지도에 `status`가 없는 항목이 있으면 콜백으로 내려가고, 콜백도 없으면 null로 닫는다. 기존 시험 2개는 `status:'ACTIVE'`를 넣도록 수정됐다. 앞으로 메모리 저장소를 쓰는 시험은 ACTIVE를 명시하거나 콜백을 줘야 한다(의도된 fail-closed).
7. **정비 실패 관측성**: `finally` 안의 계정별/목록 실패는 조용히 삼키고 다음 정비 일에 맡긴다. 로그·지표가 없어 운영에서 재시도 지연을 알기 어렵다.
8. **배치 상한**: `inactiveAccountIdsWithStaff(100)`은 하루 100계정이다. 대량 탈퇴·병합 뒤 정리가 밀릴 수 있다.
9. **배포 Secret**: `PEAKET_INTERNAL_GRPC_TOKEN`이 이제 core·ops 시작도 막는다. 운영 배포에서 모든 서비스에 토큰 Secret이 주입되지 않으면 롤아웃이 실패한다. `PEAKET_REAUTH_REDIS_URL`이 없으면 jti는 닫히지만 지급 승인·정산 계좌·export 재인증이 전부 403이 되므로, 운영에서는 Redis 주소를 주입해야 한다. 저장소 `deploy/`에서는 두 env를 확인하지 못했다.
