## 과결합·기존 시험 약화·production 변경

### 과결합

대체로 계약 수준이다. 금액·상태·에러 타입·감사 필드·HTTP 상태를 공개 API로 확인하고, 메모리 어댑터는 시험 대역으로만 쓴다. 다만 다음은 구현 세부에 가깝다.

- A1V-10이 `calculateDueEvents('2026-11-13', 100)`처럼 **기본 limit 100**과 `ticked({ through, calculated })` 로그 모양을 고정한다. 정본 계약은 through 날짜와 실행 시각이지 limit 기본값·로그 payload가 아니다.
- A1V-04/A1V-12가 `MemorySettlementStore.statementAudits`, A1V-01이 `store.receivableMoves` 같은 메모리 어댑터 필드를 직접 본다. 어댑터를 바꾸면 시험이 함께 고쳐야 한다.
- A1V-10이 `ManualTimer`를 주입해 타이머 포트를 시험한다. 포트 자체는 공개 계약이라 허용 범위다.
- A1V-10의 `until()`은 200회×1ms(≈200ms)로, 부하가 큰 CI에서 flaky할 수 있다.
- A1V-02의 `events.listDue` 스텁이 `through >= '2026-11-13'` 같은 기대 날짜를 품고 있어 다소 자기참조적이다. 그래도 워커가 다른 날짜를 보내면 `seen` 단언에서 잡히므로 회귀 가치는 유지된다.

## 남은 공백

1. **R627V-01(차단)**: core 토큰 시험의 403 기대값. 403→401 수정 필요. `87798c80`이 이미 같은 수정을 한다.
2. **미수금 동시성**: `drizzle-settlement-store.ts`의 `FOR UPDATE` + `payout-batch-statement-conflict` 409 경로를 직접 실행하는 시험이 없다. 변이 1은 메모리 저장소의 가드가 간접적으로 잡았을 뿐, 두 배치가 동시에 같은 미수금을 소진하는 경합은 재현하지 않는다.
3. **A1V-03 다건 이의**: 이의 2건 중 1건만 결과가 입력된 경우(`some(result === null)`)를 시험하지 않는다. 또 `reconfirmStatement`의 DISPUTED 성공 경로(모두 결과 입력 → NOTIFIED)는 시험하지 않고, 성공 경로는 `resolveDispute`로만 확인한다. 같은 이의를 두 번 해소할 때의 409도 없다.
4. **A1V-04 잘못된 증빙**: BALANCE에 `saleResumed`만 주는 식의 "다른 사유 증빙"을 거절하는지 보지 않는다. KYC 재확정은 기존 `test/settlement.test.ts:323`이 덮지만, ACCOUNT_CHANGE 재확정은 기존 시험에서 직접 보이지 않는다(이번 4파일 범위 밖).
5. **A1V-12 중복 감사**: `expect.arrayContaining`이라 같은 전이의 감사가 두 번 쌓여도 통과한다. DISPUTED 재확정 감사도 직접 확인하지 않는다.
6. **A1V-10 운영 경계**: `leader=false`, 동시 tick 재진입(`#running`), `stop()`이 진행 중 tick을 기다리는지, 기본 interval 30분은 시험하지 않는다. `until` 200ms는 flaky 위험.
7. **A1V-02 수동 계산 경로**: `POST /internal/v1/settlements/event-calculations`에서 `eventEndsAt` 누락 → 422 계약을 시험하지 않는다. 워커 경로만 덮는다.
8. **A1V-09 원천 오류**: `settlement-due-source.test.ts`는 정상 200·토큰·query만 본다. core가 403/503을 돌려줄 때 payment가 `event-settlement-source-unavailable` 503으로 바꾸는지는 시험하지 않는다.
9. **공휴일**: 지급일 계산이 주말만 건너뛰고 공휴일 달력을 쓰지 않는 것은 문서화된 한계다. 시험도 그 한계를 그대로 고정한다(결함 아님).
10. **환경 변수**: core 시험이 `process.env.PEAKET_INTERNAL_TOKEN`을 직접 바꾼다. Vitest 파일 격리 덕에 지금은 안전하지만, 같은 worker에서 파일을 합치면 누출될 수 있다.
