## 6. 남은 공백

1. **(주요) `decideRefresh`의 `refreshUsed` 결정 가드가 시험되지 않는다.** `refresh-used.test.ts`는 재시도 뒤 `prevRefreshHash === null`과 `refreshUsed === true`를 단언하고 세 번째 요청이 `REUSED`인지 본다. 그런데 두 번째 재시도에서 `setRefreshHash`가 `prevRefreshHash`를 이미 NULL로 지우므로, 세 번째 요청은 `match: 'previous'`가 아니라 `match: 'history'`가 되어 `refreshUsed`를 보지 않고도 `REUSED`가 된다. 그래서 `domain/session.ts`의 `&& !s.refreshUsed`를 지워도 시험이 통과한다(변이 M4b). 이 가드가 방어적 이중화라면 수용 가능하지만, 시험 이름/주장이 "refreshUsed 가드"를 고정한다고 말하기에는 부족하다. 보강안: `decideRefresh({ match: 'previous', rotatedAt: now, refreshUsed: true, alive: true }, now)`를 직접 단언해 `'reuse'`를 기대하거나, `prevRefreshHash`를 유지하는 가짜 저장소로 두 번째 재시도를 구성한다.
2. **탈퇴 사건의 reason·시각 단언이 얕다.** 새 다중 세션 시험은 `SessionTerminated.safeParse` 성공과 세션 ID만 본다. 사건의 `reason === 'STAFF_REVOKED'`와 사건별 `terminatedAt`을 단언하지 않아, reason이 `DELETE`로 바뀌어도 이 시험은 통과할 수 있다. 기존 단일 세션 시험이 reason을 단언하므로 전체 커버리지는 있지만, 새 시험의 이름이 약속하는 범위보다 단언이 좁다.
3. **초대 HTTP 시험이 컨트롤러 매핑까지만 본다.** `staff-invitation-http.test.ts`는 `StaffInvitationController.accept`를 직접 호출해 `ProblemError`가 던져지는지 본다. Fastify 라우트·`ProblemFilter` 직렬화·응답 본문까지는 보지 않는다. 매핑 표 자체는 고정되지만 라우트 배선 회귀는 이 시험으로 잡히지 않는다.
4. **내부 토큰 시작 시험이 합성 모듈을 쓴다.** `createService`의 `PEAKET_ENV → INTERNAL_TOKEN_REQUIRED` 배선과 가드 동작은 고정하지만, 실제 identity/ops 등 서비스 모듈이 `INTERNAL_TOKEN`을 주입하는지는 이 시험 범위 밖이다. 플랫폼 공통 배선이므로 위험은 낮다.
5. **`refresh-used.test.ts`는 기존 `refresh-cases.ts`의 재시도 시험과 흐름이 겹친다.** 새로 더한 가치는 `prevRefreshHash`/`refreshUsed` 플래그 단언이다. 중복 자체는 결함은 아니나, 위 1번 공백을 메우지 못한다.
