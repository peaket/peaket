- 코드 경로

  - 같은 시나리오에서 `batchTotal=128,000`, 미수금 0/CLOSED, `receivable_move` 1행 50,000.

- 남은 위험: `FOR UPDATE` 잠금 순서를 미수금 ID로 정렬하지 않는다. 여러 미수금이 겹치는 두 배치가 서로 다른 순서로 잠그면 PostgreSQL 교착(40P01)이 나 409가 아니라 500이 될 수 있다. 또한 잔액 충돌의 오류 type이 `payout-batch-statement-conflict`라 의미가 넓다.

- **부분인 이유**
  1. 내부 HTTP `POST /internal/v1/settlements/event-calculations`는 `EventBody`에 `eventEndsAt`이 없고 `calculateEvent`를 그대로 부른다(`services/payment-svc/src/modules/settlement/inbound/internal-settlement.controller.ts:20,70-72`). 스케줄러가 놓친 회차를 수동 계산하면 여전히 `계산일+5영업일`이 지급일이 된다. R-620 문서의 "지급일은 종료일+5영업일"은 스케줄러 경로에만 참이다.

  4. core `settlement-due`는 `through`를 `T23:59:59.999Z`(UTC)로 해석한다(`services/core-svc/src/modules/catalog/inbound/internal-sale-config.controller.ts:63`). KST 날짜로 넘긴 `through`보다 9시간 넓어, 다음 날 08:59 KST까지 끝난 회차를 앞당겨 포함할 수 있다.
  5. 스케줄러가 늦게 돌면(예: core 장애로 11-14 실행) `payoutDate=2026-11-13`처럼 과거 날짜가 그대로 저장된다. 지급일을 다음 영업일로 미루는 처리가 없다.

### A1V-03 DISPUTED — 통과

- 코드 경로
  - `settlements.ts:259-266`: `DISPUTED`는 `listDisputes`가 비었거나 `result === null`인 이의가 있으면 409 `settlement-dispute-open`. 모두 결과가 있으면 `NOTIFIED`로 돌리고 `disputeDueAt = now+1영업일`, 감사 insert.
  - `settlements.ts:292-306`: `resolveDispute`가 이의 결과(`ADJUSTED`/`DISMISSED`)를 저장하고 `DISPUTED → NOTIFIED`, 새 1영업일 이의 기간, 감사 insert.
  - `settlements.ts:234-237`: 이의 기간이 끝난 `NOTIFIED` 자동 확정에 `dispute-window-ended` 감사 insert.
- 임시 시험
  - 이의 row 없이 `DISPUTED` 재확정 → 409 `settlement-dispute-open`, 상태 `DISPUTED` 유지.
  - 실제 `svc.dispute()`로 row를 만들고(result null) 재확정 → 409.
  - `resolveDispute(..., 'DISMISSED', 'tester')` → `NOTIFIED`, dispute `result=DISMISSED`, 감사 `DISPUTED→NOTIFIED/dispute-dismissed/tester`.
  - `disputeDueAt`을 과거로 바꾸고 `confirmDueStatements()` → `CONFIRMED`, 감사 `NOTIFIED→CONFIRMED/dispute-window-ended/system`.
  - 이의 결과를 먼저 `saveDispute`한 뒤 `reconfirmStatement` → `NOTIFIED`, 감사 `dispute-resolved`.
- 실제 PostgreSQL: 0020 테이블에 위 두 감사 행이 그대로 들어갔다.
- 변이: `DISPUTED` 409 가드 블록 제거 → A1V-03·03b **2개 시험 잡힘**(409 사유가 `settlement-not-reconfirmable`로 바뀜). 원복 SHA 일치.
- 남은 위험: `ADJUSTED` 결과는 상태만 바꾸고 금액을 조정하지 않는다(문서상 수기 조정 전제). `HELD` 상태에서 이의가 들어온 경우 `resolveDispute`가 `holdReason`을 지우고 `NOTIFIED`로 만들므로, 밑에 있던 KYC/계좌 보류를 다시 평가하지 않는다. 다만 `createPayoutBatch`가 KYC/계좌를 다시 보므로 실제 지급은 막힌다.

### A1V-04 HELD — 통과(조건부)

- 코드 경로 `settlements.ts:267-283`
  - `KYC`: `status=VERIFIED && businessVerified && representativeVerified` 필요.
  - `ACCOUNT_CHANGE`: 저장된 `holdUntil`이 지나야 한다.
  - `ACCOUNT_MISMATCH`: `evidence.accountReconciled === true` 또는 저장된 계좌가 `holderVerified && holdUntil <= now`여야 한다.
  - `BALANCE`: `evidence.balanceConfirmed === true` 필요.
  - `SALE_SUSPENDED`: `evidence.saleResumed === true` 필요.
  - 그 밖의 사유(null 포함): 409 `settlement-not-reconfirmable`.
- 임시 시험: 위 5개 사유 각각 증빙 없이 409, 증빙/저장 상태가 있으면 `CONFIRMED`. 사유 없음은 409. 재확정 감사 5건이 남았다.
- 남은 위험: `balanceConfirmed`·`saleResumed`·`accountReconciled`는 호출자가 보내는 boolean이다. 서버가 PG 잔액이나 판매 중지 상태를 독립적으로 확인하지 않는다. 내부 토큰을 가진 운영자/서비스가 true를 보내면 증빙 없이도 통과한다. `ACCOUNT_CHANGE`는 시간 경과만 본다.

### A1V-07 리더 첫 tick·06시 — 부분 통과

- 코드 경로
  - `services/payment-svc/src/start.ts:344-346`: `LeaseElector`의 `onChange(leader)`가 true일 때 `settlementDueWorker?.tick(true)`.
  - `packages/platform/src/lease.ts:77-81,126-129`: `setLeader(true)`가 `onChange(true)`를 부르고, 첫 `step()` 성공 시 `lastRenewAt`을 먼저 갱신한 뒤 리더가 된다.
  - `settlement-due-worker.ts:53-57`: `start()`는 interval만 걸고 즉시 tick하지 않는다. 첫 실행은 onChange가 맡는다.
- 임시 시험: `LeaseElector.step()` 첫 성공에 `onChange(true)`, `stop()`에 `onChange(false)`. 통과.
- **결함: 06시 전 force tick이 06시 정기 실행을 막는다.**
  - `tick(force=true)`는 `settlement-due-worker.ts:72`의 06시 검사를 건너뛴다. 그리고 `lastRunDay=today`를 `settlement-due-worker.ts:91`에서 기록한다.
  - 리더가 02:00 KST에 뽑히면 02:00에 `tick(true)`가 돌아 `through=어제`로 정산서를 만들고 `lastRunDay=오늘`이 된다. 06:00의 `tick(false)`는 `lastRunDay === today`라 즉시 반환한다.
  - 임시 특성 시험(02:00 force → 06:00 정기)에서 `calculateDueEvents` 호출이 1회에 그쳤다(기대 2회). **06시 실행이 실제로 사라진다.**
  - 이는 문서 `docs/features/settlement.md:93`의 "회차가 끝난 다음 영업일 06시"와 `:176`의 "원장은 일일 대사가 끝난 것만 쓴다"를 어긴다. 02:00에는 전날 대사가 끝나지 않았을 수 있는데, `calculateEvent`는 기존 정산서가 있으면 다시 계산하지 않으므로(`settlements.ts:98-99`) 대사 전 원장으로 만든 정산서가 그대로 남는다.
  - `lastRunDay`는 `calculateDueEvents`/`confirmDueStatements`가 모두 실패해도 기록된다(`:91`). 06시 실행이 실패하면 06:30 재시도 없이 다음 날까지 기다린다.
- **주말에도 06시에 돈다.** `#schedule`은 요일을 보지 않는다. 금요일 종료 회차는 토요일 06:00(`through=금요일`)에 계산된다. 문서의 "다음 영업일"은 월요일인데 토요일에 계산되어, `disputeDueAt = 계산시각+2영업일`이 화요일로 잡혀 월요일 계산(수요일)보다 이의 기간이 하루 짧아진다.
- `stop()`은 `#tickPromise`(정기 tick)만 기다린다(`:59-64`). onChange의 `tick(true)`는 `#tickPromise`에 들어가지 않아 종료 중 force tick이 남을 수 있다(A1V-14 일부 잔존).
- 커밋된 시험은 `start.ts` 배선, 06시 gate, 06시 전 force tick을 보지 않는다. `settlement.test.ts:373-401`은 `worker.tick()` 기본값(force=true)으로 09:00 KST에 돌린다. `start.ts`의 `onChange`를 지우는 변이는 payment 시험 전체를 통과할 것으로 보인다(A1V-10 잔존).

## 남은 위험

1. **A1V-09 cross-service 회귀(가장 큼, 배포 차단)**: core에 토큰을 넣으면 purchase-svc 홀드/예매와 ticket-svc 스캐너 정책이 403으로 깨진다. 토큰을 빼면 내부 경로가 열린다. purchase-svc·ticket-svc의 `sale-config` 클라이언트에 토큰을 배선하고 실제 HTTP 403/200 시험을 넣어야 한다.
2. **A1V-07 06시 전 force tick**: 02:00 리더 선출이 대사 전 원장으로 정산서를 만들고 `lastRunDay`로 06시 정기 실행을 막는다. force tick은 06시 이후에만 허용하거나, 06시 전 force tick은 `lastRunDay`를 기록하지 않아 06시에 다시 돌게 해야 한다.
3. **A1V-07 주말 실행**: 타이머가 매일 06시에 돌아 금요일 종료 회차를 토요일에 계산한다. 문서의 "다음 영업일"과 다르고 이의 기간이 하루 짧아질 수 있다. 영업일 gate를 두거나 `through`를 영업일 기준으로 계산해야 한다.
4. **A1V-02 수동 HTTP 경로**: `event-calculations`가 `eventEndsAt`을 받지 않아 수동 계산은 여전히 `now+5영업일`이다. 공휴일 달력과 UTC/KST 경계도 남아 있다.
5. **A1V-04 증빙 신뢰**: `balanceConfirmed`·`saleResumed`·`accountReconciled`는 호출자 주장이다. PG 잔액·판매 중지 상태를 서버가 확인하지 않는다.
6. **A1V-03 ADJUSTED**: 결과만 기록하고 금액을 조정하지 않는다. 수기 조정 절차와 연결되지 않으면 파트너가 본 금액과 실제 지급이 어긋난다.
7. **A1V-12 감사 원자성**: 상태 변경과 감사 insert가 한 트랜잭션이 아니다. 감사 insert 실패 시 상태만 바뀐다. 감사 조회 API/시험도 없다.
8. **A1V-01 잠금 순서**: `FOR UPDATE`를 미수금 ID 순으로 정렬하지 않아 다중 미수금 동시 배치에서 교착(500) 가능. 잔액 충돌 type 이름도 넓다.
9. **A1V-08/A1V-14 재시도·종료**: 실패해도 `lastRunDay`를 기록해 당일 재시도가 없고, `stop()`은 force tick을 기다리지 않는다.
10. **범위 잡음**: R-620에 A1V와 무관한 `packages/api-client` 생성물(`putPartnerPayoutAccount200` 등)과 문서 요약 변경이 함께 들어갔다. 기능 결함은 아니지만 커밋 범위가 넓다.
