## 놓친 변이 = 시험 공백

### [중간] M4-01: 지급 승인 기한이 '전 영업일'이 아니라 '전날'로 계산되고, 이를 고정하는 시험도 없다
- 영역/배치: 지급 승인(BAT-610 잔여, FR-062, POL-038·039, settlement §5.1)
- 위치: `services/ops-svc/src/modules/payouts/domain/payout-approval.ts:84-87`
- 증거:
  - 구현은 `payoutDate T00:00+09:00 - 24시간 + 15시간`이다. 즉 **달력상 전날 15시**다.
  - 정본 `docs/features/settlement.md:186`은 "지급일 전 영업일 15시까지 승인되지 않으면…"이라고 적는다. 월요일 지급이면 금요일 15시가 기한이어야 하는데, 코드는 일요일 15시를 준다.
  - 변이 30(16시로 변경)을 넣어도 `payout-approval.test.ts` 5개가 모두 통과했다. `dueAt`/`approvalDueAt`을 단언하는 시험이 없다.
- 왜 문제인가: 지급일이 월요일인 묶음의 승인 마감이 실제보다 이틀 늦게 표시된다. 운영자가 마감을 넘겨 승인하면 정본이 정한 "다음 영업일로 미루기"가 일어나지 않고, 지급·정산 일정과 파트너 공지가 어긋난다. 지금은 표시값이지만 향후 마감 집행에 쓰이면 돈 일정이 틀어진다.
- 재현/확인:
  - `approvalDueAt('2026-11-20')` → `2026-11-19T06:00:00.000Z`(목요일 15시 KST). 정상.
  - 월요일 `approvalDueAt('2026-11-23')` → `2026-11-22T06:00:00.000Z`(일요일 15시 KST). 정본은 금요일 15시를 요구한다.
  - 변이: `+ 15 * 60 * 60 * 1000` → `+ 16 * 60 * 60 * 1000`, `vitest run test/payout-approval.test.ts` → 5 passed.
- 제안 수정:
  1. 영업일 달력(공휴일 포함)으로 지급일 전 영업일을 구하고 그날 15시 KST를 반환한다.
  2. `payout-approval.test.ts`에 월요일·연휴 전날 사례를 넣어 `dueAt`을 정확히 단언한다.
- 확신도: 높음(코드와 정본 문구가 직접 어긋남). 영업일 계산을 어디서 가져와야 하는지는 중간.

### [중간] M4-02: 체크포인트 검증이 서명 불일치를 잡는지 시험하지 않는다
- 영역/배치: 감사 체크포인트(BAT-465 R-584, ADR-0075)
- 위치: `services/ops-svc/src/modules/audit/checkpoint.ts:194-207`
- 증거: `signatureValid` 계산을 `true`로 바꿔도 `audit-anchor.test.ts` + `command-execution.test.ts` 15개가 모두 통과했다. 기존 시험은 (a) 서명기를 직접 호출해 변조 루트를 거부하는지, (b) 정상 체크포인트의 `service.verify`가 참인지만 본다. **서명 필드만 변조한 체크포인트**를 `service.verify`에 넣는 시험이 없다.
- 왜 문제인가: 공개 검증 경로 `GET /v1/ops/audit-anchors/{id}/verification`이 서명이 틀려도 `valid:true`를 줄 수 있다. 감사자·외부 검증자가 "서명 검증 통과"를 신뢰하게 되므로 감사 무결성 주장이 약해진다.
- 재현/확인: 변이 16 적용 → `vitest run test/audit-anchor.test.ts test/command-execution.test.ts` → 15 passed.
- 제안 수정: 체크포인트를 만든 뒤 `signature`만 다른 base64로 바꾼 사본을 저장소에 넣고 `verify`가 `signatureValid:false, valid:false`를 주는 시험을 추가한다. `createdAtMs`만 1ms 바꿔도 서명이 깨지는지도 함께 본다.
- 확신도: 높음

### [중간] M4-03: 서명 대상 필드 집합을 고정하는 시험이 없어 체크포인트 ID가 서명에서 빠져도 통과한다
- 영역/배치: 감사 앵커 서명(BAT-465 R-584, ADR-0075)

- 왜 문제인가: 서명이 체크포인트 ID를 묶지 않으면, 같은 구간·루트·시각을 가진 다른 체크포인트 행에 서명을 복사해도 검증이 통과한다. 체크포인트 ID는 `local:<id>` 앵커 참조와 공개 URL의 신원인데, 그 신원이 서명에 결속되지 않는다. 필드가 하나 빠지거나 순서가 바뀌는 회귀를 시험이 잡지 못한다.

- 제안 수정:
  1. `auditAnchorMessage`의 정확한 출력(줄 순서·구분자 포함)을 황금 문자열로 단언한다.

- 영역/배치: 지급 2인 승인(BAT-610 잔여, FR-062, POL-038)

- 왜 문제인가: 재인증 토큰이 다른 계정(다른 commander)의 것이어도 승인이 통과할 수 있다. 2인 승인의 핵심인 "승인자 본인이 방금 다시 인증했다"가 깨지고, 토큰만 확보한 공격자가 다른 commander 세션으로 지급을 승인할 수 있다. 재인증 검증기가 세션에 토큰을 결속한다면 완화되지만, 코드가 명시적으로 계정 비교를 두는 만큼 시험이 있어야 한다.
- 재현/확인: 변이 29 적용 → `vitest run test/payout-approval.test.ts` → 5 passed.
- 제안 수정: `TestReauth`가 승인자와 다른 계정을 돌려주는 경우를 만들고 `403 reauth-required`를 단언한다. 토큰 없음·만료·다른 세션 사례도 함께.

### [중간] M4-05: 회차 취소 확정이 환불 작업 상태(COMPLETED/REFUND_WINDOW)를 반영하는지 시험하지 않는다
- 영역/배치: 회차 취소(BAT-425 GAT-130 잔여, FR-055, POL-038, ADR-0046)
- 위치: `services/ops-svc/src/modules/event-cancellations/application/event-cancellations.ts:80`

- 왜 문제인가: 환불이 이미 끝났는데(`COMPLETED`) 화면·API는 계속 진행 중(`RUNNING`)으로 보인다. 연기 회차의 `REFUND_WINDOW`도 사라져 운영자가 환불 신청 창을 놓치거나, 끝난 작업에 `pause`를 걸 수 있다.

- 확신도: 높음

### [낮음] M4-07: 승인 대기 명령을 직접 실행하지 못하게 하는 가드가 시험되지 않는다

- 재현/확인: 변이 7 적용 → 29 passed.

### [중간] M4-08: 지급 승인 저장에 낙관적 잠금이 없어 동시 승인 시 이중 실행될 수 있다 (추정)
- 영역/배치: 지급 승인(BAT-610 잔여)
- 위치: `services/ops-svc/src/modules/payouts/adapters/db/drizzle-store.ts:69-82`, `payouts/adapters/memory-store.ts:17-19`
- 증거: `save`는 `approvalId`만 조건으로 전체 행을 덮어쓴다. `version`을 비교하지 않는다. `PayoutApprovals.approve`는 `find`로 `PENDING_APPROVAL`을 읽고 `EXECUTING`을 저장한 뒤 결제사 `approveBatch`·`executeBatch`를 부른다. 두 요청이 동시에 읽으면 둘 다 통과할 수 있다.
- 왜 문제인가: 같은 지급 묶음에 `executeBatch`가 두 번 나갈 수 있다. payment-svc가 묶음 상태로 멱등하게 막아 주면 피해가 없지만, ops 쪽에서 보장하지 않고 아래 서비스에 의존한다. 한 요청이 `DONE`, 다른 요청이 `FAILED`로 덮어써 상태가 뒤집힐 수도 있다.
- 재현/확인: 코드 대조. 동시성 시험(test-int)은 Docker 허용 뒤 제안 목록에 넣었다. 변이로는 재현하지 않았다.

- 확신도: 중간(코드상 가능. payment-svc 멱등성 여부는 이 worktree에서 확인하지 않음)
