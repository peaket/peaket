## 1. 한눈에 보는 결론

이번 범위의 핵심 보안 관문은 대부분 시험이 잡았다. 특히 **mTLS 게이트웨이 비밀 값**, **인증서 지문↔토큰 cnf 결속**, **DPoP jti 재전송**, **ath 결속**, **iat 창**, **기기 폐기**, **등록 코드 문자 집합**, **다른 파트너 기기 배치**, **근무 준비 stale**, **스태프 세션 없는 업로드의 회차 배치 확인**, **승인 화면 파트너 필터**, **기기 코드↔키 지문 결속**, **slow_down**, **stale 경계**는 변이를 넣으면 곧바로 시험이 빨개졌다.

## 4. 놓친 변이 = 시험 공백 (발견 9개)

### [중간] M5-01: 기기 지문(jkt) 시험이 자기 자신과만 비교한다
- 영역/배치: scanner DPoP 기기 키, GAT-170 / BAT-435
- 위치: `apps/scanner/src/api/dpop.ts:23`, 시험 `apps/scanner/test/dpop.test.ts:11-18`
- 증거: 지문의 JSON 키 순서를 RFC 7638 정본(`crv,kty,x,y`)에서 `kty,crv,x,y`로 바꿔도 시험 2개가 모두 통과했다. 시험은 `jktOf(key.publicJwk) === key.jkt`만 보고, `key.jkt`도 같은 `jktOf`가 만든 값이라 **자기 참조**다. 별도 확인: 같은 키로 두 순서를 계산하면 `l7ws…V14` vs `JW8W…Yos`로 달라지고, jose `calculateJwkThumbprint`는 정본 순서와만 일치했다.
- 왜 문제인가: 서버(가드·등록)는 jose의 RFC 7638 지문으로 기기를 찾는다. 클라이언트 키 순서가 한 번 틀리면 등록 때 묶은 jkt와 이후 DPoP 증명의 jkt가 영원히 달라져 **모든 스캐너 기기 로그인이 실패**한다(가용성). 지금은 코드가 맞아서 괜찮지만, 시험이 이 회귀를 못 잡는다.
- 재현/확인: `dpop.test.ts`만으로는 못 잡음(위 표 S06). jose 대조 스크립트로 순서 차이 확인.
- 제안 수정: 시험에 RFC 7638 고정 벡터(또는 `jose.calculateJwkThumbprint`)와의 대조를 넣는다. 예: 알려진 EC 공개키 → 기대 jkt 문자열을 상수로 단언.
- 확신도: 높음

### [중간] M5-02: DPoP htu의 호스트를 바꿔도 잡는 시험이 없다
- 영역/배치: scanner DPoP, GAT-170 / ADR-0065
- 위치: `packages/platform/src/scanner-auth.ts:186`, 시험 `packages/platform/test/scanner-auth.test.ts:236-245`
- 증거: htu 비교를 `withoutQuery(payload.htu) !== withoutQuery(o.url)`에서 **pathname만 비교**로 바꿔도 21개가 모두 통과했다. 시험은 같은 호스트에서 경로만 `/v1/other`로 바꾼 경우만 본다.
- 왜 문제인가: DPoP 증명은 "이 HTTP 요청"에 묶여야 한다. 호스트를 무시하면 `https://evil.example/v1/scanner/shift`용으로 만든 증명이 `https://scanner-api.peaket.example/v1/scanner/shift`에서 통과한다. 악성 출처로 토큰·증명이 새는 상황에서 재전송 문턱이 낮아진다(전제: 출처 설정 오염·중간자). 지금 코드는 정확히 비교하므로 실제 결함은 아니고 **회귀 감시 공백**이다.
- 재현/확인: 표 P07. 변이 상태에서 기존 시험 전부 초록.
- 제안 수정: 같은 경로·다른 호스트(`https://evil.example/v1/scanner-test/shift`) 증명이 401인 시험을 추가한다. 질의 문자열이 붙은 htu가 통과하는 시험도 함께.
- 확신도: 높음(코드), 중간(공격 전제)

### [중간] M5-03: 근무 시작 전(validFrom) 세션 판정 시험이 없다
- 영역/배치: identity 스캐너 세션 확인, GAT-170 / ADR-0051
- 위치: `services/identity-svc/src/modules/session/application/check-scanner-session.ts:25`, 시험 `services/identity-svc/test/check-scanner-session.test.ts:53-60`
- 증거: `row.validFrom > now`를 지워도 6개가 모두 통과했다. 시험은 `validUntil` 뒤(3시간 뒤)만 본다.
- 왜 문제인가: 배정 유효 시작 전인데도 세션이 유효하다고 답하면, 다른 경로로 만들어진 세션이 근무 시작 전에 현장 스캔에 쓰일 수 있다. 지금은 승인 단계가 창 안에서만 세션을 만들지만, 세션 확인은 마지막 관문이므로 시작 경계도 시험으로 고정해야 한다.
- 재현/확인: 표 I10.
- 제안 수정: `validFrom: NOW + HOUR`로 둔 세션을 `NOW`에 확인해 `valid:false`인 시험, 그리고 `validFrom`과 정확히 같은 시각은 유효(경계) 시험을 추가한다.
- 확신도: 높음

### [중간] M5-04: `valid:false`+role 조합을 가드가 거절하는지 시험이 없다
- 영역/배치: platform ScannerGuard, GAT-170 / ADR-0172
- 위치: `packages/platform/src/auth.ts:540`, 시험 `packages/platform/test/scanner-auth.test.ts:279-293`
- 증거: `if (!session.valid || !session.role)`을 `if (!session.role)`로 바꿔도 21개가 모두 통과했다. 시험의 무효 세션은 `{ valid: false }`(role 없음)뿐이라, role이 같이 오는 형태를 보지 않는다.
- 왜 문제인가: identity가 장애·회귀 때 `valid:false`인데 role을 함께 돌려주면 가드가 통과시킨다. 지금 identity 구현은 무효 경로에서 role을 싣지 않아 실제 결함은 아니지만, **서비스 경계의 계약**을 가드 시험이 고정하지 않는다.
- 재현/확인: 표 P10.
- 제안 수정: `{ valid:false, role:'gate_staff', eventId:'ev-1' }` 답을 주는 시험을 추가해 401을 단언한다.
- 확신도: 높음

### [낮음] M5-05: DPoP `typ` 거절 시험이 없다
- 영역/배치: platform DPoP, RFC 9449 §4.2
- 위치: `scanner-auth.ts:165,173`, 시험 `scanner-auth.test.ts` 전체
- 증거: 수동 검사와 `jwtVerify`의 `typ` 옵션을 모두 없애도 21개가 통과했다. 시험의 `proofOf`는 항상 `typ:'dpop+jwt'`를 쓴다.
- 왜 문제인가: 다른 종류의 JWT(예: 일반 access token)를 DPoP 증명 자리에 넣는 혼동 공격을 막는 첫 조건이다. 서명·ath·htm·htu·jti가 남아 있어 단독 악용은 어렵지만, RFC 필수 검사가 시험에 없다.
- 제안 수정: `typ`를 `JWT` 또는 빈 값으로 만든 증명이 401인 시험.
- 확신도: 높음

### [낮음] M5-06: 헤더 jwk에 개인키(`d`)가 든 경우 거절 시험이 없다
- 영역/배치: platform DPoP, RFC 9449 §4.3
- 위치: `scanner-auth.ts:129`
- 증거: `typeof jwk.d !== 'string'` 조건을 지워도 21개가 통과했다.
- 왜 문제인가: 서버는 공개 부분으로 검증하므로 즉시 권한 상승은 없지만, 클라이언트가 개인키를 헤더에 실어 보내는 구현을 서버가 받아들이면 키 유출·로그 노출 위험이 커진다. RFC는 개인키 포함 jwk를 명시적으로 거절한다.
- 제안 수정: `d`가 있는 jwk 헤더 증명이 401인 시험.
- 확신도: 높음

### [낮음] M5-07: 등록 jkt 모양(43자 base64url) 거절 시험이 없다
- 영역/배치: ticket 기기 등록, GAT-170
- 위치: `services/ticket-svc/src/modules/scanner/domain/scanner-device.ts:113`, 시험 `scanner-device.test.ts`
- 증거: `JKT_PATTERN.test(v)`를 지워도 7개가 통과했다. 시험은 항상 `'A'.repeat(43)`만 쓴다.
- 왜 문제인가: 아무 문자열이나 기기 지문으로 저장되면 원장에 쓸모없는 값이 남고, 이후 조회·감사가 오염된다. 권한 상승은 아니지만 입력 계약이 시험에 없다.
- 제안 수정: `jkt:'x'`, 42자, `+`/`=` 포함 값이 `ScannerDeviceInputError('JKT')`인 시험.
- 확신도: 높음

### [낮음] M5-08: 승인(`decide`)의 근무 창 밖 승인 거절 시험이 없다
- 영역/배치: identity 기기 승인, identity §6.1
- 위치: `services/identity-svc/src/modules/session/application/device-approvals.ts:118`, 시험 `device-approval.test.ts:114-129`
- 증거: `decide`의 `active = byPartner.filter(inWindow)`를 `active = byPartner`로 바꿔도 10개가 통과했다. 시험은 **조회(lookup)** 의 `OUTSIDE_STAFF_HOURS`만 본다.
- 왜 문제인가: 조회를 건너뛰고 승인 API를 직접 부르면 근무 창 밖 배정으로 세션을 만들 수 있다. `expiresAt`이 `validUntil`이라 지난 창이면 즉시 무효지만, 시작 전 창이면 근무 시작과 함께 유효해진다. 정책 위반이 가능하다.
- 제안 수정: `validFrom: NOW + HOUR`(또는 `validUntil: NOW - 1`) 상태에서 `decide(APPROVE)`가 `OUTSIDE_STAFF_HOURS`인 시험.
- 확신도: 높음

### [낮음] M5-09: version vector 비교에서 `flagSeq`가 빠져도 잡는 시험이 없다
- 영역/배치: scanner 오프라인 동기화, GAT-160
- 위치: `apps/scanner/src/storage/version-vector.ts:17`, 시험 `apps/scanner/test/version-vector.test.ts:41-61`
- 증거: `FIELDS`에서 `flagSeq`를 빼도 4개가 통과했다. `vector()`는 `flagSeq:3`을 넣지만 값을 바꿔 비교하는 경우가 없다.
- 왜 문제인가: 이상 표시(FLAG)만 서버와 갈라져도 `needsResync`가 `same`으로 답해 재동기화를 건너뛴다. 표시는 판정 자체를 막지 않아 피해는 작지만, "모든 종류의 변경을 벡터로 본다"는 계약이 시험에 없다.
- 제안 수정: `flagSeq`만 다른 두 벡터가 `diverged`/`behind`가 되고 `needsResync`가 `true`인 시험. 각 필드를 하나씩 바꾸는 표 구동 시험을 권한다.
- 확신도: 높음

## 5. 잘 잡힌 것 (회귀 감시가 실제로 작동)

- **mTLS**: 게이트웨이 비밀 값 위조, 인증서 지문↔`x-user-x5t` 불일치, 인증서 머리 누락, `wiring.mtls` 없을 때 가짜 머리 무시, 폐기 인증서 기기.
- **DPoP**: iat 창, jti 재전송, ath 불일치, cnf.jkt 불일치, htm/htu 경로 불일치, 기기 전용 경로의 사용자 토큰 거절.
- **가드**: 미등록/폐기 기기 403, 세션 무효 401, 역할 밖 403, 5초 세션 캐시 만료.
- **등록/기기**: 등록 코드 문자 집합, 1회용 코드, 키 지문 충돌(KEY_IN_USE), 폐기 기기 코드 재발급 거절, `request_id` 멱등, 폐기 시 identity 세션 종료.
- **배치/근무**: 다른 파트너 기기·폐기 기기·다른 회차 거절, OUT 재입장 정책, If-Match 428/412, stale(나이·packageSeq), 준비 보고.
- **업로드/벡터**: 다른 회차 스캔 403, 세션 없는 업로드의 배치 확인, stale 벡터 표시, stale 경계(정확히 24시간은 신선).
- **기기 승인**: ACTIVE만 코드 발급, 시간당 10회, 파트너 필터, 근무 창(조회), 대리 승인 역할 강등, assignmentId 필수, ALREADY_HANDLED, jkt 결속, 승인 뒤 폐기, slow_down.
- **클라이언트**: `needsResync`의 behind/diverged, htu 질의 문자열 제거.

## 6. 2단계(Docker 허용 뒤) test-int 변이 제안 — **대기 중**

Docker가 허용되면 아래를 실제 PostgreSQL·Redis로 돌려, 단위 시험이 못 보는 **동시성·원자성·교차 서비스**를 본다. 지금은 실행하지 않았다.

| # | 대상 | 넣을 변이 | 잡아야 하는 것 |
|---|---|---|---|
| 1 | `RedisDpopReplayStore` | `SET NX PX` → `SET PX`(NX 제거) | 파드 2개가 같은 jti를 동시에 받아들임 |
| 2 | `RedisEnrollmentCodeStore` | `GETDEL` → `GET`+`DEL` 분리 | 같은 등록 코드로 두 기기가 동시에 등록 |
| 3 | `RedisEnrollmentAttemptLimiter` | `INCR` 뒤 `PEXPIRE`를 첫 회에만 | 창 만료 뒤 카운터가 초기화되지 않아 영구 차단/우회 |
| 4 | `RedisDeviceAuthorizations.notePoll` | slow_down 비교·TTL을 Lua 밖에서 | 동시 폴링이 slow_down을 우회 |
| 5 | `scanner_device` 유니크 인덱스 | 테스트 DB에서 `credential_thumbprint` 유니크 제거 | 같은 jkt가 두 기기에 묶임(KEY_IN_USE 누락) |
| 6 | `scanner_placement` 낙관적 판(If-Match) | `WHERE version = expected` 제거 | 동시 배치 덮어쓰기(갱신 손실) |
| 7 | 스캔 업로드 트랜잭션 | `acceptScans`의 트랜잭션·유니크 제거 | 같은 scanId 재전송이 FLAG·변경분을 중복 생성 |
| 8 | 기기 폐기→identity 종료 | gRPC 종료 호출을 삼키고 성공 처리 | 다른 스캐너 화면이 SESSION_TERMINATED를 못 받음 |
| 9 | `changes(after, limit)` | `after`를 `>=`로 바꿈 | 경계 일련번호 누락/중복 |
| 10 | 준비 보고 upsert | `ON CONFLICT` 제거 | event+device 행 중복, stale 판정이 오래된 행을 봄 |
| 11 | 승인 원자성 | `approve` 실패 시 세션 종료(보상) 제거 | 고아 스캐너 세션이 남음 |
| 12 | mTLS 게이트웨이 | 클라이언트가 보낸 `x-peaket-mtls-*` 머리를 지우지 않음 | 가짜 mTLS 머리로 DPoP 없이 통과 |
