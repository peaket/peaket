# 묶음 계획: BAT-011(HOT-161·PRF-173 보상 세 걸음과 발권 막기, PRF-175 분리)

- **무엇**: 묶음을 시작할 때 만든 작업 목록이다(docs/architecture.md §8.6 4의 1·2, '역할 나누기'의 계획). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다. 정본의 값은 옮겨 적지 않고 자리(문서·절)만 가리킨다.
- **바탕**: 작업 폴더 `D:/ticketpass-b011`, 가지 `feature/lane1-BAT-011`, 출발점 `origin/develop` `c65cb00ea`. 구현 전 트리는 `D:/ticketpass-b011-base`(`c65cb00ea`, 커밋하지 않음)다. 지시서는 `brief.mjs --batch BAT-011`(만든 때 `c65cb00ea`).
- **등급**: A(docs/BUILD_ORDER.md 묶음 표 BAT-011). 돈(결제 취소)·좌석(판매 확정)·발권의 핵심 로직과 그 복구에 닿는다. 짧은 고리(ADR-0283 결정 2)를 쓰지 않는다: 계획 → 구현 → 독립 시험(구현 전 트리 실패 확인) → 리뷰 → 리뷰 반영(시험 먼저, 그다음 구현) → 고친 곳 다시 리뷰 → 검증(틀린 구현·기준 대조) → 기록.
- **차례**: 정방향 묶음이다(계획 커밋에 `Batch-Order: impl-first`). 구현 커밋이 시험 파일을 건드리지 않는다.

## 감독에게

1. **PRF-173 분할(승인됨)**: PRF-173은 보상 핵심만 하고, CS 처리함 건으로 닫는 길은 새 단계 **PRF-175**로 뺀다. PRF-175의 선행은 GAT-280이다. BAT-011은 `HOT-161·PRF-173`, 새 배치 **BAT-012**는 `PRF-175`다.
2. **HOT-161을 새 단계로 더한다**: ticket-svc의 주문 단위 발권 막기 RPC. WBS 2.8.1(HOT-160)이 하기로 했으나 BAT-050에 빠진 몫이다. HOT-160은 체크를 유지하고, 2.8.1에 HOT-161(0.5일 [가정])을 더해 2.8.1을 다시 `진행`으로 둔다.
3. **BAT-460의 선행 표시 고침**: BAT-460의 `선행 OPS-260·OPS-270·OPS-280·OPS-290(갈래 2)`에서 `(갈래 2)`를 `(갈래 4)`로 고친다. OPS-280·OPS-290은 BAT-360(R-751)에서 코드가 끝났는데 단계 줄이 `[ ]`이라, BAT-360 기록 커밋에서 함께 `[x]`로 고친다.
4. **P-T39 ③의 정할 곳**: ledger-notes의 `P-T39 ③`을 `PRF-170·GAT-280`에서 `PRF-173`으로 바꾼다. ②·④는 PRF-175(선행 GAT-280)로 남긴다.
5. **`COMPENSATING` 상태**: 주문 상태에 더하지 않고 `order_compensation` 표로 둔다(아래 결정 3). 공개 `Order.status` 계약을 늘리지 않는다.

## 계획

### 1. 범위

- **하는 것**
  - **HOT-161**: ticket-svc에 `BlockTicketIssuance`(주문 단위 발권 막기) RPC를 더한다. 같은 주문의 `IssueTickets`와 한 줄 잠금으로 갈라, 막은 뒤의 발권은 `FAILED_PRECONDITION`이고, 이미 만든 티켓은 폐기한다.
  - **PRF-173**: 회차 취소 확정으로 발권 대기(APPROVED) 주문을 보상한다. 세 걸음이다: ① `compStart` — 큐 행을 잠그고 지운 뒤 주문을 보상 중으로 표시 ② `compFence` — ticket-svc에 그 주문의 발권을 막게 하고 ③ `compCancel` — 그 답을 받은 뒤 payment-svc `CancelPayment`로 결제를 취소하고 주문을 COMPENSATED로 끝낸다.
  - `payment-model` 하네스가 흉내 내던 `compStart`·`compFence`·`compCancel`을 운영 코드 호출로 바꾸고 `docs/verification.md` §2.4의 흉내·알려진 차이를 고친다.
- **뺀 것과 까닭**
  - **PRF-175**: `CHARGED_ON_CLOSED_ORDER`·`TICKET_NOT_ISSUED` CS 처리함 건을 열고 '시스템 잘못이 확인된 환불'로 닫는 길, asyncapi `CaseRequestedKind`에 `TICKET_NOT_ISSUED` 더하기, `ReceiveCaseRequested`가 그 종류를 받기. GAT-280의 CS 건 요청 계약이 먼저다(선행).
  - GAT-280 전체(SCR-045, 건 종류별 기한·재발송, 실패한 승인 업무 재실행)는 BAT-460에 그대로 둔다.
  - 실제 결제사 계정이 필요한 검증(P-T33·P-T38)은 이 묶음 범위 밖이다.

### 2. 장부 범위(좁힌 뒤 BAT-011 줄의 범위 칸)

```text
P-T15, P-T39 ③, V-T40, payment:v5.0.0-2.3.1, payment:v5.0.0-2.3.3, payment:v5.0.0-8.2.1
```

- `P-T15`: 발권 gRPC 재시도·중복 전달에서 티켓이 정확히 1회. HOT-161이 같은 주문 잠금을 바꾸므로 함께 본다.
- `P-T39 ③`: 발권 대기 중 회차 취소 2인 확정 → 발권 멈춤·결제 취소·COMPENSATED·좌석 반환. PRF-173의 핵심 판정이다.
- `V-T40`: 결제 모델 기반 시험. 하네스의 보상 세 걸음을 운영 코드로 바꾸므로 다시 본다.
- ASVS 2.3.1(상태 기계·건너뛰기), 2.3.3(트랜잭션·보상), 8.2.1(내부 RPC 호출자 제한: `BlockTicketIssuance`는 purchase-svc만).
- **범위 밖(빼는 것, 다른 단계로 미루는 것이 아님)**: P-T39 ②·④(PRF-175), P-T39 ①·⑤(PRF-170 완료), payment.md의 나머지 P-T, ASVS payment의 나머지 행.

### 6. 위험·열린 질문

- **위험 1**: `IssueTickets`가 `ticket_issue` 행을 먼저 넣는 지금 구조에 guard 행 잠금을 더하면 잠금 차례가 늘어난다. `ticket_issue`·`ticket_issue_guard` 모두 같은 트랜잭션 안에서 잠그므로 교착은 없지만, 경합 시험(T3)으로 확인한다.
- **위험 2**: 보상 실행기가 회차 취소 실행기와 같은 틱에 돌면 `order_compensation` 임대가 겹칠 수 있다. `FOR UPDATE SKIP LOCKED`와 `lease_until`로 하나만 잡는다.
- **위험 3**: `payment-svc` `CancelPayment`의 취소 사유 목록에 보상 사유가 없다. 새 사유를 더하지 않고 기존 `EXCEPTION`·`EVENT_CANCELLED`를 쓰는지, 새 사유를 더하는지는 payment.proto 주석과 B6에서 정한다.
- **열린 질문**: `order_compensation`을 `purchase_order` 상태 `COMPENSATING`으로 둘지. 이 계획은 표로 두는 쪽을 추천한다(공개 계약을 늘리지 않고, 최종 T20 하나로 끝낸다).

## 구현 메모

- **`ticket_issue_guard.blocked_at`은 널을 허용한다.** 지시서의 마이그레이션 칸은 `NOT NULL`이었지만, 그러면 `IssueTickets`가 만든 잠금 자리 행도 곧바로 '막힘'이 되어 발권과 막기를 가를 수 없다(지시서의 `issue` 차례도 "blocked_at이 있으면 거절"을 전제한다). 값이 없으면 발권이 먼저 만든 잠금 자리, 있으면 막힌 주문으로 읽는다.
- **보상 행의 끝 상태 이름은 `COMPENSATED`다.** 독립 시험 역할이 `COMPENSATION_STATUSES`를 `STARTED·FENCED·COMPENSATED·FAILED`로 고정해 두었으므로 마이그레이션·도메인·문서를 그 값으로 맞췄다. `CANCELED`는 쓰지 않는다. `canceled_at` 칸 이름은 유지하되 뜻은 '보상 완료(결제 취소·T20) 시각'이다.
- **`payment_id`의 출처.** purchase-svc `payment_attempt`에는 `APPROVED` 상태가 없다(READY·ACCEPTED·SUPERSEDED·EXPIRED). 그래서 도메인 순수 함수 `compensationPaymentIdOf`는 시험이 주는 'APPROVED 결제 시도 목록'에서 마지막 승인 결제를 고르고, 운영 `StartCompensation`은 마지막 ACCEPTED 결제 시도를 거쳐 payment-svc `GetPayment(주문 ID)`가 원장의 payment_id를 찾는다. 원장도 없으면 `NO_PAYMENT`로 FAILED다(ADR-0354 결정 4의 뜻을 이 데이터 모델에 맞게 옮긴 것).
- **T20은 한 번만, 결제 취소가 성공한 뒤.** `StartCompensation`은 주문을 잠그고 APPROVED만 확인하며 T20을 쓰지 않는다. `CancelCompensation`이 결제 취소 답을 받은 저장소 `compensated` 트랜잭션에서 T20과 행 COMPENSATED를 함께 쓴다. 이미 COMPENSATED인 행의 다시 부름은 결제를 같은 취소 ID로 다시 부르되 T20을 다시 쓰지 않는다(이중 환급·이중 이력 0).
- **마이그레이션 기록.** purchase-svc는 drizzle `_journal.json`·`meta/0032_snapshot.json`을 쓴다(`db:generate`로 만들고 태그만 `0032_order_compensation`으로 맞췄다). ticket-svc는 `scripts/migrate.mjs`가 폴더 이름 순으로 적용하며 별도 기록 파일이 없다.
- **`docs/verification.md` §2.4는 이 커밋에서 고치지 않았다.** `payment-model` 하네스 전환(`test-int/payment-model/system.ts`·`compensation-adapter.ts`)은 독립 시험 역할의 작업 트리에 있고, 구현 역할은 시험 파일을 고치지 않는다. 하네스가 합쳐진 뒤 그 문단을 갱신한다.
- **이름 맞춤.** 독립 시험이 쓰는 `StartCompensation.run`·`FenceCompensation.run`·`CancelCompensation.run`, `DrizzleCompensation({ database })`, `COMPENSATION_MAX_ATTEMPTS`, `compensationPaymentIdOf`, `compensationRetryDelayMs(attempts)`를 그대로 따랐다. 운영 어댑터 쪽 이름은 `GrpcTicketFence.block`, `GrpcPaymentCompensator.cancel`이다.
- **결제 취소 사유.** payment-svc `CancelPayment`는 승인 결제의 일반 취소(`confirmedCancel`)를 이미 지원하고 사유는 1~200자 글이다. 새 사유·계약 변경 없이 `EVENT_CANCELLED`를 쓴다(2.3.3·8.2.1 구현 위치만 갱신).
- **검증에서 남은 것.** 독립 시험이 쓴 새 시험 넷(`compensation-domain.test.ts`·`ticket-block.test.ts`·`ticket-block.int.test.ts`·`compensation.int.test.ts`)을 시험 작업 트리에서 임시로 복사해 이 구현에 돌려 모두 통과했다(각 4·5·3·7건, 끝나고 복사본은 지웠다). 기존 `test/purchase-schema.test.ts`의 폴더·기록 대조는 `_journal.json`을 읽으므로 0032를 자동으로 포함해 통과한다. 다만 같은 파일의 '마지막 스냅샷 표 목록' 시험은 시험 안에 고정한 표 목록(`SHAPES`·`ORDER_SHAPES` 등)에 `order_compensation`이 없어 `expected 22, received 23`으로 실패한다. 시험 역할이 목록에 `order_compensation`을 더해야 한다(구현 역할은 시험 파일을 고치지 않는다). 기존 `test/payment-confirm.test.ts`·gRPC 어댑터 시험 몇 건은 전체 병렬 실행에서 데드라인으로 한 번씩 실패했고 단독 실행에서는 모두 통과했다(이 묶음과 무관한 시간 의존 시험).
