### 5. 공개 인터페이스

- **게이트웨이 정의 파일의 모양**: 쿠버네티스 객체 YAML(여러 문서를 `---`로 이음). 시험은 `kind`·`metadata.name`·`spec`만 본다. 객체 이름 규칙: Gateway `gw-<이름>`, 정책은 `<게이트웨이>-<종류>`(예 `gw-fan-client`, `gw-fan-security`), 공개 경로 라우트 `<게이트웨이>-public`, 앱 서버 라우트 `<게이트웨이>-app`. 네임스페이스는 Envoy Gateway 차트 기본(docs/devops.md §5.2 네임스페이스 지도).
- **`node tools/local/cluster.mjs gateways`**: `up` 뒤에 부른다. Envoy Gateway 설치(판·다이제스트 고정), 대역 백엔드와 시험 키 Secret, 원본 확인 값 Secret(이 PC의 `.cache/peaket-tools/`에만, 저장소에 없음), `deploy/gateways` + 로컬 덧씌우기 적용. `gateways-forward`(또는 같은 명령의 선택지)가 게이트웨이를 이 PC 포트로 낸다. 정확한 인자는 구현 담당이 `tools/local/README.md`에 적는다.
- **시험 대역 백엔드**: 받은 요청의 머리 전부를 JSON으로 돌려준다(`GET`·`POST` 아무 경로). 공개키 묶음 대역은 `/internal/jwks/{fan|admin|staff}.json`.
- **`@peaket/platform`**: `BROWSER_TRACEPARENT_HEADER = 'x-peaket-browser-traceparent'`(`@peaket/platform/telemetry`에서 내보냄). `startTelemetry({ inbound: 'untrusted' })`의 추출은 이 머리를 먼저, 없으면 `traceparent`를 링크 후보로 읽는다. 기존 `InboundTrust`·`startTelemetry` 모양은 그대로다.
- **앱 서버 계측**: `apps/web/instrumentation.ts`·`apps/partner/instrumentation.ts`의 `register()`가 Node 실행기에서만 텔레메트리를 앱 서버 모드로 시작한다(서비스 이름은 `OTEL_SERVICE_NAME`, 없으면 `web`·`partner`). `PEAKET_TRACE_INBOUND`가 `untrusted`가 아닌 값으로 적혀 있으면 시작하지 않고 던진다(아래 8의 6). 빌드 작업자와 개발 서버는 지금처럼 건너뛴다.
- **identity**: `sourceAddressOf(ip: string): string`의 모양은 그대로이고 맞추기 규칙만 늘어난다(docs/features/identity.md §6 '출발지'). `clientIpOf`는 쉼표가 든 값이나 IP가 아닌 값이면 연결 상대 주소를 쓴다.

### 7. 차례

1. **계획**(이 커밋): 이 파일, 정본 빈칸(아래 8), 묶음 표 한 줄.
2. **시험**(시험 담당): 위 6의 정·단 시험을 먼저 쓰고 실패를 본다. 뼈대는 `BROWSER_TRACEPARENT_HEADER` 상수(값만)와 두 앱 계측의 빈 `register()`뿐이고, 게이트웨이 정의 폴더는 비워 둔다(정적 시험이 읽기는 하고 단언에서 실패해야 실패로 센다). K·B 시험은 써 두고, 실패 확인은 Docker 잠금을 받아 한 번 돌리거나 감독이 웨이브 끝 차례에 돈다('실패 확인' 절에 어느 쪽인지 적는다).
3. **구현**(구현 담당): ① 게이트웨이 정의 → 정적 시험 통과 ② platform·앱 서버·identity·웹 로그인 → 단위 시험 통과 ③ `cluster.mjs gateways`와 대역 백엔드 → K·B 시험(Docker 잠금) ④ 정본의 [확인 필요] 여섯(아래 8의 끝)을 kind에서 본 결과로 그 줄에 적는다 ⑤ CI 잡 잇기.
4. **리뷰** → **리뷰 반영** → **검증**(아래 10의 목록) → **기록**(감독).

3. 게이트웨이가 넘기는 클라이언트 IP 꼴과 identity의 맞추기(BOT-111이 넘긴 질문): docs/features/identity.md §6 '출발지'(`grep -n "게이트웨이가 넘기는 꼴과 identity의 맞추기" docs/features/identity.md`).

5. `deploy/` 구조에 `gateways/`: docs/devops.md §5.2 나무 그림.

8. gw-fan 검색 경로의 IP별 요청 한도 첫 값(SR-T13 ②): docs/features/search.md §8 '무작위 입력' 줄 끝 '첫 값'.

남은 [확인 필요](구현 담당이 kind에서 보고 그 줄에 결과를 적는다. 안 되면 줄에 적힌 대안으로 하고, 대안도 안 되면 '시험 이의'에 적고 그 항목을 멈춘다):
- `earlyRequestHeaders` 값에 `%REQ(traceparent)%`를 쓸 수 있는지(observability §6, 대안: 브라우저 계측이 머리를 직접 싣기).
- Lua에서 프록시 환경 값(원본 확인 값)을 읽을 수 있는지, Lua가 JWT 확인 뒤에 도는지(infra §4.1, 대안: Wasm).
- `numTrustedHops: 1`이 CloudFront 맨 오른쪽 값을 고르는지(kind에서는 시험 클라이언트가 붙인 값으로 본다).
- `%REQ_WITHOUT_QUERY(:PATH)%`에 필요한 포매터 설정(infra §9·§4.1, 대안: `EnvoyPatchPolicy`).
- 공개키 묶음을 한 번도 받지 못했을 때 503으로 바꿀 수 있는지(못 하면 남는 차이로 적는다. 이 묶음의 판정 항목은 아니다).
- IP마다 따로 세는 한도를 로컬 한도로 걸 수 있는지(search §8, 대안: 전역 레이트 리밋 HOT-410. 그러면 SR-T13 ②의 정·K 시험은 HOT-410으로 옮기고 '시험 이의'에 적는다).
- CORS 응답의 `Vary: Origin`을 Envoy CORS 필터가 붙이는지(안 붙이면 응답 머리 고치기로 더한다. Q-T41·3.4.2 시험이 본다).

### 11. 시험·구현 지시문에 넣을 것

- docs/architecture.md:1144~1158 '자주 놓친 결함'을 그대로 넣는다. 이 묶음에 특히 닿는 것: 허용·거부 목록은 목록 밖 값마다(허용 출처 밖 넷, 다른 키 셋 둘, 다른 `typ` 둘) 거부를 본다. 시간·한도 상수(캐시 300초, `Max-Age` 7200, HSTS 31536000)는 코드에서 가져오지 말고 정본 값을 시험에 적는다. 판정 함수(Lua)만 보지 말고 백엔드가 받은 머리와 접근 로그(바깥 경계)에서 본다. 다섯 게이트웨이에 같은 규칙이 있으면 다섯 각각을 단언한다(한 곳만 빠진 결함).
- kind 시험은 끝나면 `docker rm -f -v`로 지우고 Docker 잠금 폴더를 지운다(PROGRESS 턴 규칙 'Docker 차례').
