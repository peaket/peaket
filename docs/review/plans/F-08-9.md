# 기능 계획: F-08-9(장애 주입 기록 검사·검색 측정·NFR-028, 동결 로컬 트랙)

- **진행**: 계획·시험(측정 준비)·리뷰·지적 반영·재리뷰·재리뷰 2·재리뷰 3 끝, **시험 리뷰 닫힘**(2026-11-27). 구현은 시험 고정점 `f1f707a8f`에서 시작하고, 실제 측정·보고서·기록은 구현 뒤 측정 창에서 한다. 이 파일의 측정 결과는 모두 `미측정`이다.
- **무엇**: BUILD_ORDER '기능 단위 계획' F-08-9(갈래 4, 등급 B, HOT-480·HOT-490, WBS 4.00일, 단계 줄 `HOT-480 wbs 2.12.3`·`HOT-490 wbs 2.12.4`)의 작업 목록이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **쉬운 말**: 두 가지를 잰다. ① 거래 사건을 보내는 릴레이(Outbox에 쌓인 사건을 Kafka로 옮기는 일꾼)에 부하를 걸고, 일부러 리더를 멈추거나 Kafka 브로커를 세우거나 DB 연결을 끊었을 때 사건이 빠지거나 순서가 뒤집히지 않는지, 그 장애가 실제로 일어났다는 기록이 남는지 본다. ② 검색과 자동완성이 오픈 직전 몰림·무작위 입력에서 목표 시간 안에 답하는지 재고, 골든 세트(기대 결과를 정한 검색어 묶음) 정답률·사전 판 지연과 함께 NFR-028을 판정한다.
- **바탕**: 작업 폴더 `D:/ticketpass-freeze-F-08-9`, 가지 `freeze/lane4-F-08-9`, 기준 `origin/feature/lane4-F-08-2-refresh` `19b33ba85`(F-08-2·F-08-8 보고서 포함). 계획·시험 담당은 Docker·kind·측정을 하나도 돌리지 않았고 Docker 잠금도 잡지 않았다.
- **차례(감독 지시 2026-11-26)**: 계획 → 시험(측정 준비) → 리뷰(새 세션) → 반영 → 측정/문서 → 기록. ADR-0373의 B등급 차례는 계획 → 시험 → 구현 → 시험 통과면 합침이고 시험 리뷰가 없다. 이 기능은 **'측정이 통과로 새지 않는가'가 핵심**이라 감독이 리뷰를 한 번 더 붙였다. 리뷰는 코드가 아니라 측정 설계·판정·시험을 본다. 이번 동결 트랙은 계획과 시험을 한 세션이 맡았다(감독 지시). 역할 꼬리말은 `Role: plan`·`Role: test`로 나눠 남긴다.
- **동결 로컬 범위**: ADR-0373·ADR-0386에 따라 `freeze/lane4-F-08-9` 가지와 이 워크트리에서만 만든다. `develop`·`release/1.0.0`에 합치지 않고, 릴리스 가지·`main`에 체리픽하지 않는다. 마이그레이션·릴리스 플래그를 만들지 않고, `deploy/`의 출시 환경 값도 고치지 않는다. 이 기능의 결과는 v1 출시 계약의 근거로 쓰지 않는다.
- **수치**: 이 파일과 시험은 정본의 목표·판정 값을 **인용만** 한다. 측정 전이라 이 기능이 내는 값은 전부 `미측정`이다. 정본에 없는 새 수치를 주장하지 않는다.
- **한 줄 결론**: 릴레이 Outbox 발생기·DB 증거·장애 주입·Toxiproxy/시뮬레이터 원장 대조·검색 실행기·판정기가 없다. 있는 v1 무대(2GiB)·`v1-search.js`·`fill-search.mjs`·불변식 검사기·`bat025-plan.mjs --plan`에 이것들을 더하고 호스트 core-svc 무대를 따로 띄우면 측정 창 약 3시간 30분~3시간 45분이다. 장부 범위는 측정 7항목으로 좁힌다.

## 2. 감독에게

1. **장부 범위를 측정 7항목으로 좁혔다** — `V-T27`, `V-T28 ①②③`, `P-T1`, `SR-T13 ①②`다. 지금 범위(46항목)는 이 기능이 닫지 못하는 것을 포함한다: `docs/security/asvs/verification-tools.md`의 18행 가운데 7행은 다른 곳 시험에 `[ASVS v5.0.0-x.y.z]` 꼬리표가 없어 'ID만', 2행은 해당 없음, 9행은 자동 시험이다. `docs/features/search.md`의 23행 가운데 SR-T11 ②는 CDN 배포 구성(HOT-450) 몫이라 '다른 단계', SR-T15 ③은 AWS 계정이 필요해 '미검증'이다. `NFR-028`은 SR-T12·SR-T13이 가리켜 별도 장부 항목이 아니다. 좁힌 뒤 `node tools/ci/ledger.mjs --batch F-08-9 --require`가 통과한다(5절). ASVS 꼬리표 붙이기와 SR-T15 ③은 이 기능이 하지 않는다.
2. **P-T1은 A등급 항목인데 이 기능은 부분만 잰다** — P-T1의 돈 경로 A 증명(이중 결제·P3·P6·좌석 누수)은 F-08-8 K7 ②가 이미 맡았고, 이 기능은 그 위에 **장애 주입 기록 검사**(Toxiproxy 지연·끊김, 시뮬레이터 원장 대조, 웹훅 중복)를 더한다. ticket-svc 5분 중단·이중 발권·일일 대사 불일치는 v1 합본 무대에 ticket-svc가 없어 **미측정**으로 남긴다. P-T1의 장부 상태는 '측정' 그대로 두고 결과는 '부분'으로 적는다.
3. **F-08-8과의 경계** — F-08-8이 잰 K1·K2·K7과 P-T1의 기본 K7 ②는 다시 재지 않는다. 이 기능은 릴레이(V-T27·V-T28)와 결제 경로의 추가 장애 모드, 검색(SR-T13 ①)만 한다. F-08-8의 보고서·실행 ID를 인용하고 새 수치를 주장하지 않는다.
4. **F-08-10과의 경계** — F-08-10(V-T18, 서비스 분리 효과 비교)은 동결이고 이 기능이 만들지 않는다. 세 구성 비교·M2 블로그도 하지 않는다.
5. **측정할 수 없는 것** — 실제 MSK 패치(로컬 Strimzi로 흉내), Aurora 읽기 전용 복제본(SR-T15 ③), CloudFront CDN, ticket-svc 5분 중단·일일 대사, 운영 28일 윈도우. 보고서에 '미측정'과 까닭을 적고 통과로 세지 않는다.
6. **측정 창** — 약 3시간 30분~3시간 45분(무대 올리기 포함, 무효 재측정 여유 별도). 동결 로컬 트랙의 창이라 v1 릴리스 측정 창과 섞지 않는다. 이번 턴에는 열지 않는다. 감독이 열고, Docker 잠금은 **`docker` 한 자리**(`lock.sh take docker lane4-F-08-9`, `docker-all` 금지)를 쓴다. kind 이름은 `lane4-f09`로 다른 갈래와 겹치지 않게 한다.
7. **리뷰** — 새 세션이 계획·시험만 보고 본다. 보는 곳: 측정 판정이 빈 결과·SKIPPED·0건을 통과로 만들지 않는가, 장애 주입이 실제로 일어났다는 증거를 요구하는가, 정본 값과 시험 단언이 맞는가, F-08-8/F-08-10 경계를 넘지 않는가, 이 기능이 수치를 미리 주장하지 않는가. 지적은 시험 담당이 고치고(`Fix-By: test`), 리뷰 담당이 확인한다.
8. **정할 것** — 14절. 추천대로 정하고 측정 전에 이 파일에 적는다.

## 3. 범위

### 3.1 하는 것

- **V-T27(릴레이 부하 측정)**: v1 무대의 purchase DB에 정본 V-T27 행이 정한 2배 [가정] 도착률로 30분 동안 Outbox 행을 넣고, purchase-svc 릴레이(복제 2·리더 하나)를 돌린다. 발생기는 `relayLoadPlan`이 정한 `COPY` 묶음으로 넣고, 보낸 행은 DB 표 `f089_sent`, 받은 행은 소비자가 DB 표 `f089_received`에 적는다(메모리 배열 금지). 같은 부하에 같은 좌석 키를 빠르게 뒤집는 주문을 섞고(`maxKeyRepeats`로 증거), 같은 30분 안에 P-T5 결제 접수→확정 p99도 잰다. 잰 것: 릴레이 지연 p50·p99, 묶음 p99, DB CPU 증가분(같은 도착률로 릴레이를 끈 기준 실행과의 차이), Outbox 일 파티션의 죽은 행·자동 청소, P-T5 p99. 로컬 Kafka 브로커 하나를 다시 시작한 구간의 릴레이 지연·P-T5 p99는 평소 구간과 나눠 남긴다.
- **V-T28 ①②③(순서·유실)**: 같은 V-T27 부하에서 ① 묶음을 보내는 중일 수 있는 리더를 SIGSTOP으로 멈춰 Lease를 넘긴다 ② Kafka 브로커를 30초 멈춘다 ③ 릴레이의 DB 연결을 끊는다. 세 경우 모두 `f089_sent`와 `f089_received`의 DB 안티조인·스트리밍 집계로 빠진 행 0, 같은 키 `seq` 순서 뒤집힘 0, 다시 보낸 사건의 `eventKey` 같음, 깨어난 옛 리더가 새 리더와 같은 행을 동시에 보내지 않음, 리더가 바뀐 시간을 장부에 남긴다. 장애마다 `faults.ndjson`에 종류·계획 시각·길이·적용 여부·증거를 남기고, `적용=false`·증거 없음·계획과 다른 시각/길이는 그 실행을 무효로 한다.
- **P-T1의 추가 몫(결제 장애 기록 검사)**: `v1 payment-fault` 하위 명령으로 결제 1만 건을 보내며, 결제 시뮬레이터 앞 Toxiproxy에 응답 지연·시간 초과·연결 끊김을 넣고 시뮬레이터가 같은 `webhook-id`를 중복 발송한다. 시뮬레이터 원장(`GET /sim/ledger`, NDJSON `pg_charge`의 `payment_ref`·`status`)과 payment 원장을 대조해 P6(승인인데 원장에 없음) 0, 이중 결제 0, 웹훅 중복 `sent=2·processed=1`, 불변식 결과를 남긴다. 발생기 `dropped=0`일 때만 유효다. **이중 발권 0은 주장하지 않는다**: v1 합본의 S3가 SKIPPED라 ticket-svc 5분 중단·이중 발권·일일 대사는 `미측정`으로 적는다(2절 2).
- **SR-T13 ①·NFR-028(검색 측정)**: v1 합본에는 core DB가 없으므로, 호스트에서 core-svc(`:3001`)와 core PostgreSQL을 띄우고 `fill-search.mjs`로 채운 뒤 k6 검색 부하를 `host.docker.internal:3001`로 보낸다. `loadtest/scenarios/v1-search.js`의 가벼운 부하(몰림·무작위 각각 초당 20회, 60초)를 공연 1만·2만에서 크기마다 3회 보낸다. 유효 회차 2회 이상, 구간별 검색 200 1건 이상, 받는 쪽 p95·503 비율·그 밖의 5xx·`search_pool_waiting` 비율을 정본 SR-T13 ①의 판정으로 본다. 같은 실행 묶음에서 SR-T12 골든 세트 보고(`search-golden-report.json`)와 사전 판 지연 게이지(`search_dictionary_version_lag_seconds`)를 읽어 NFR-028의 다섯 수치와 '판매 승인 취소 공연이 같은 트랜잭션으로 빠짐'(SR-T15 ① 인용)을 판정한다.
- **SR-T13 ②**: 새로 재지 않는다. BAT-056의 2026-11-18 측정 결과와 `tools/local/e2e/gateways.e2e.mjs`의 설정 시험을 근거로 보고서에 인용하고, 장부 notes를 그대로 둔다.

### 3.3 수용 기준·완료의 정의·실패 시나리오

**완료의 정의(동결 로컬 트랙의 자체 완료)** — 아래를 모두 만족할 때 이 기능을 끝낸다. v1 출시 완료와는 별개다.

1. 계획·시험·리뷰·반영·구현·측정·보고서·기록 커밋이 이 가지에 있다.
2. V-T27을 30분 실행으로 재고, 릴레이 지연 p50·p99, 묶음 p99, DB CPU 증가분, 죽은 행·자동 청소, 브로커 재시작 구간, **P-T5 결제 접수→확정 p99(전체·브로커 재시작 구간)**를 보고서에 적었다.

## 6. 측정 설계(측정 전에 못박는다)

정본 값은 옮겨 적지 않고 자리만 가리킨다. 측정을 시작한 뒤 규칙을 바꾸지 않는다. 바꿔야 하면 멈추고 감독에게 묻고 보고서에 적는다.

### 6.1 무대와 공통 규칙

- **v1 무대(릴레이)**: 새 kind 클러스터(`PEAKET_CLUSTER=lane4-f09`, `cluster.mjs up` → `observability` → `v1 --redis-tls on --replicas 3 --memory-mi 2048`), Prometheus(`cluster.mjs prometheus`), 불변식 검사기 빌드. F-08-8의 512Mi·1GiB OOM을 피해 2GiB로 올린다(추천 적용 2026-11-26, RV089-23). 무대 값의 나머지는 `docs/verification.md` §3.8 그대로다.
- **호스트 검색 무대**: v1 합본에 core DB가 없으므로 호스트에서 core PostgreSQL과 core-svc(`:3001`)를 띄우고, 마이그레이션·`fill-search.mjs`로 공연 1만·2만을 채운다. k6 파드는 `host.docker.internal:3001`로 보낸다. 이 무대는 릴레이 무대와 같은 클러스터에 있지만 서로 다른 프로세스·DB다.
- **릴레이 부하 발생기**: `relayLoadPlan`이 정한 `COPY` 묶음으로 purchase DB의 `f089_sent`에 보낸 행을 먼저 적고 Outbox에 넣는다. 한 묶음은 같은 좌석 키를 여러 번 뒤집는 행을 포함한다. 소비자는 받은 행을 `f089_received`에 적는다. 30분 2배 [가정] 분량을 메모리에 올리지 않는다. 검색은 `v1-search.js`를 그대로 쓰고 시나리오·판정 기준을 바꾸지 않는다.
- 판정: 실패·무효·SKIPPED는 통과가 아니다. 빈 결과(요청 0·표본 0·장애 0·발생기 dropped > 0)는 통과가 아니라 무효다.
- 반복: V-T27 1회(무효면 1회만 더), V-T28 ①②③은 그 1회 안에서 차례로 넣는다. 검색은 크기마다 3회(정본 SR-T13 ①의 유효 회차 규칙). P-T1 추가 몫 1회(무효면 1회만 더), 발생기 유효 회차만 센다.
- 장부: V-T27·V-T28·검색·P-T1 실행은 `--record --run-id <ID> --profile <프로파일> --prom-url http://127.0.0.1:9090 --out <폴더>`로 남긴다. 실행 ID 끝에 `-f089`를 붙인다. 검색 1만 실행은 `--golden`으로 SR-T12 보고를 같은 폴더에 남긴다.
- 측정 중에는 다른 시험·빌드를 돌리지 않는다. Docker 잠금은 `docker` 한 자리다(2절 6).

### 6.3 장애 주입 시각과 기록

- V-T28 ①은 30분 본구간의 약 3분의 1 지점, ②는 약 3분의 2 지점, ③은 끝나기 약 5분 전에 넣는다. ①은 SIGSTOP 전에 최근 보내기 활동(묶음 카운터·발행 카운터)을 확인해 '묶음을 보내는 중일 수 있는' 창을 고른다. 고르지 못하면 ①을 한 번 다시 넣는다. ③ 뒤 다시 붙어 이어 보내는 것을 볼 드레인 창을 5분 이상 둔다.
- ②는 브로커를 30초 멈춘다(정본 V-T28 ②). ③은 PostgreSQL에서 릴레이 사용자의 연결을 `pg_terminate_backend`로 끊는다. 끊긴 연결 수가 0이면 무효다.
- 부하에는 같은 좌석·주문 키를 빠르게 뒤집는 행을 섞고, `f089_sent`의 키별 반복 최댓값(`maxKeyRepeats`)이 2 이상인지 확인한다. 1 이하면 순서 검사가 공허하므로 무효다.
- 장애마다 `faults.ndjson`에 `{kind, atSecond, durationSeconds, startedAt, endedAt, applied, evidence}`를 남긴다. `atSecond`·`durationSeconds`는 `faultPlan`과 같아야 하고, ②는 정확히 30초여야 한다. 증거는 SIGSTOP한 파드·PID, 브로커 정지·재개 시각, 끊긴 DB 연결 수, Toxiproxy 토글 결과다.
- Toxiproxy는 `ghcr.io/shopify/toxiproxy:2.13.0`으로 고정하고, 제어 API는 루프백(`127.0.0.1:8474`)에만 묶으며 `TOXIPROXY_AUTH_TOKEN`을 켠다(정본 §2.5). 데이터 프록시만 시뮬레이터 앞에 둔다.
- P-T1은 `v1 payment-fault`의 발생기 `dropped=0`일 때만 유효로 센다. 시뮬레이터가 같은 `webhook-id`를 두 번 보내고 payment-svc가 한 번만 처리했는지(`sent=2·processed=1`)를 `faults.ndjson`에 적는다. 다르면 그 몫은 통과가 아니다.
- `faults.ndjson`에 ①②③이 모두 없거나 `applied`가 거짓이거나 증거가 비면 그 실행은 무효다. 빠진 행·순서 뒤집힘·`eventKey` 불일치가 1건이라도 있으면 실패다. 실패를 숨기려고 다시 재지 않는다.

### 6.4 검색 판정과 NFR-028

- SR-T13 ①의 판정은 `docs/features/search.md` SR-T13 줄의 '측정 판정'을 그대로 쓴다. 크기마다 유효 회차 2회 이상, 구간별 검색 200 1건 이상, 받는 쪽 p95·503 비율·그 밖의 5xx·`search_pool_waiting` 비율. 무거운 부하(503 확인)는 BAT-167이 이미 했고, 이 기능은 가벼운 부하(몰림·무작위 각각 초당 20회, 60초)만 다시 잰다. `v1 search`는 이 세기를 `v1-search.js`에 그대로 넘긴다.
- NFR-028의 다섯 수치는 `docs/planning/02-requirements.md` NFR-028 행과 `docs/features/search.md` §8·§10에서 가져온다. 하나라도 값이 없으면 그 부분은 `미측정`이고 전체는 통과가 아니다. p95는 유효 회차·구간 가운데 **가장 나쁜 값**으로 보수적으로 적는다(추천 적용 2026-11-26).
- NFR-028의 '판매 승인이 취소된 공연은 같은 트랜잭션으로 검색 읽기 모델에서 빠진다'는 SR-T15 ①(자동 시험, 장부 밖)을 근거로 인용한다. 인용하지 못하면 그 부분은 `미측정`이고 NFR-028 전체는 `pass`가 아니다.
- 골든 세트는 SR-T12 시험을 먼저 돌려 순서 경우까지 통과한 `search-golden-report.json`만 받는다. 경우 수·목표 값이 정본과 다르면 무효다. `w2-search-10k`가 `--golden`으로 이 보고서를 측정 폴더에 남긴다.
- 사전 판 지연은 측정 중 Prometheus에서 `search_dictionary_version_lag_seconds`를 읽어 최댓값을 쓴다. 시계열이 없으면 0이 아니라 `미측정`이다.

### 6.5 멈춤 규칙(측정 전 등록)

- 무대가 15분 안에 준비되지 않으면 멈추고 감독에게 알린다. 검색 무대(core DB·core-svc·채우기)가 준비되지 않아도 멈춘다.
- V-T28 주입이 적용되지 않거나 빠진 행이 1건이라도 나오면 그 실행을 멈추고 실패로 적는다. 같은 조건으로 한 번만 더 재고, 또 나오면 원인 조사 없이 보고서에 적고 다음으로 간다.
- 검색 유효 회차가 2회 미만이면 같은 크기로 한 번만 더 재고, 그래도 모자라면 '무효'로 적는다.
- P-T1 발생기 dropped가 1건이라도 나오면 그 회차는 무효다. F-08-8 K7 ②처럼 3회 연속 무효면 P-T1 추가 몫은 '미측정(발생기 무효)'으로 적고 더 재지 않는다.
- 전체가 계획의 1.3배를 넘게 밀리면 감독에게 알리고 14절 '줄일 곳' 차례대로 뺀다.

### 7.2 공개 인터페이스(시험이 가정한 꼴)

- `loadtest/runner/relay-fault.mjs`:
  - `RELAY_RULES` — `{ mainSeconds: 1800, designPeakPerSecond: 6300, rateMultiplier: 2, brokerStopSeconds: 30, lagP99Seconds: 0.2, batchP99Seconds: 0.05, dbCpuIncreasePctPoints: 5, paymentP99Ms: 3000, drainSeconds: 300 }`. 정본 V-T27·V-T28·NFR-006의 값이다.
  - `relayLoadPlan({ mainSeconds, rate })` → `{ rows, batchRows, writer: 'copy', sentTable: 'f089_sent', receivedTable: 'f089_received', hotKeyEvery, sentColumns, receivedColumns }`. `rows = rate × mainSeconds`이고 메모리 배열을 만들지 않는다. `hotKeyEvery`마다 같은 좌석 키를 뒤집는 행을 넣는다.
  - `parseRelayFaultArgs(argv)` → `{ mainSeconds, rate, relay, paymentRate, paymentMode, out, record, runId, promUrl }`. `mainSeconds`는 60~3600 정수, `rate`는 1 이상 정수(기본 `RELAY_RULES.designPeakPerSecond × rateMultiplier`), `--relay on|off`(기본 on)는 릴레이를 끈 기준 실행(`w2-relay-baseline`)에 쓴다. `--payment-rate`(기본 300)·`--payment-mode load`는 같은 30분 실행에서 P-T5 결제 접수→확정 부하를 만든다. 모르는 인자·범위 밖은 `name === 'UsageError'`.
  - `relayConsumerPlan({ topic, table })` → `{ group, table: 'f089_received', columns: ['id','key','seq','event_key','publisher','received_at'], maxBatch }`. `f089_received`를 채우는 소비자 계약이다. `relayLoadPlan`의 `receivedTable`과 같아야 한다.
  - `faultPlan({ mainSeconds })` → `[{ kind: 'leader-stop'|'kafka-stop'|'db-cut', atSecond, durationSeconds }]`. 세 종류가 한 번씩, 서로 60초 이상 떨어지고, ②는 30초, 마지막 ③은 끝나기 `drainSeconds`(300초) 전에 끝나 드레인 창을 남긴다.
  - `validateFaultRecords(records, plan)` → `{ ok, problems }`. 세 종류가 정확히 한 번씩, `applied === true`, `atSecond`·`durationSeconds`가 계획과 같고, ②는 30초, `startedAt`·`endedAt` ISO, `evidence` 비지 않음. 종류 중복·계획과 다른 시각/길이·빈 증거는 거부한다.
  - `RELAY_EVIDENCE_SQL` — `{ missing, order, eventKey, oldLeader, hotKeys, payment }`의 SQL 글. `missing`은 `f089_sent`/`f089_received` 안티조인, `order`는 키별 `lag(seq)`, `eventKey`는 행별 `count(distinct event_key)`, `oldLeader`는 재개 뒤 옛 리더 발행, `hotKeys`는 키별 반복 최댓값, `payment`은 P-T5 p99다. 측정 경로는 이 SQL만 쓴다(행 배열 금지).
  - `missingRowIds(sent, received)`·`oldLeaderSendCount(received, oldLeader, takeoverAt)` — **표본 시험 전용** 작은 배열 함수. 측정 경로는 `RELAY_EVIDENCE_SQL`을 쓴다.
  - `summarizeSamples(samples)` → `{ count, p50, p99, max }`. 표본이 없으면 `count: 0`이고 p50·p99·max는 `null`(0이 아니다).
  - `judgeRelayRun(o)` → `{ verdict: 'pass'|'fail'|'invalid', problems, triggers, summary }`. `o`는 `{ runId, mainSeconds, rate, sentRows, receivedRows, missingRows, orderViolations, eventKeyMismatches, oldLeaderSends, maxKeyRepeats, payment: { runId, mode, rate, p99Ms, p99BrokerRestartMs, pullCount }, lagSeconds, batchSeconds, faults, leaderChangeMs, relayCpuPctPoints }`. `summary`는 `{ sentRows, receivedRows, missing, order, eventKey, oldLeaderSends, maxKeyRepeats, p50, p99, batchP99, paymentP99Ms, paymentP99BrokerRestartMs, paymentPulls, leaderChangeMs }`. `rate !== 12600`이거나 `payment.runId !== runId`·`payment.mode !== 'load'`·`payment.rate <= 0`·`payment.pullCount`가 0 이상 정수가 아님·`payment.p99Ms` 없음·`maxKeyRepeats <= 1`·`validateFaultRecords`가 거부하는 기록이면 `invalid`(다른 실행 값·상수·결제 부하 0을 P-T5로 넣지 못하게 한다). 빠진 행·순서·`eventKey`·옛 리더 보내기 > 0은 `fail`. V-T27 문턱을 넘으면 `triggers`에 `relay-lag`·`batch`·`db-cpu`·`payment-p99`·`payment-p99-broker`, 그것만으로 `fail`로 만들지 않는다. `payment.pullCount`는 ADR-0140 당기기 반영 수다.
  - `TOXIPROXY_RULES` — `{ image: 'ghcr.io/shopify/toxiproxy:2.13.0', controlListen: '127.0.0.1:8474', authTokenEnv: 'TOXIPROXY_AUTH_TOKEN' }`.
  - `buildToxiproxy({ name, listen, upstream, toxics })` → Toxiproxy API 꼴. `toxics[].type`은 `latency`·`reset_peer`·`timeout`만, 값은 0 이상 정수, 모르는 종류·음수는 `RangeError`. `timeout`은 P-T1의 PG 시간 초과에 쓴다.
  - `reconcileSimLedger({ simNdjson, payment })` → `{ approved, recorded, missing, duplicatePayments, verdict }`. `simNdjson`은 `GET /sim/ledger`의 NDJSON(`kind:'pg_charge'`, `payment_ref`, `status`)이고 승인 상태는 `DONE`·`PARTIAL_CANCELED`다. `CANCELED`·`WAITING_FOR_DEPOSIT`는 승인으로 세지 않는다. 빈 원장은 `invalid`, `missing`·`duplicatePayments` > 0은 `fail`.
  - `webhookDuplicatePlan({ webhookId, duplicates })` → `{ webhookId, sendCount, events }`(같은 `webhook-id`를 `duplicates`회). `judgeWebhookDuplicates({ sent, processed })` → `{ verdict }`: `sent=2·processed=1`만 `pass`, `processed>1`은 `fail`, `sent<2`는 `invalid`.
  - `parsePaymentFaultArgs(argv)` → `{ payments, rate, generators, webhookDuplicates, invariants, out, record, runId, promUrl }`. `payments` 1~100000, `rate` 1~1000, `generators` 1~16, `webhookDuplicates` 2~10, `--invariants`는 불변식 검사 플래그다(계획 `w2-pt1-fault`가 쓴다). 모르는 인자·범위 밖은 `UsageError`.
  - `judgePaymentFaultRun(o)` → `{ verdict, problems, summary }`. `o`는 `{ generator: { valid, dropped }, simNdjson, payment, webhook: { sent, processed }, invariants }`. 발생기 `valid !== true`이거나 `dropped > 0`이면 `invalid`; P6·이중 결제·웹훅 중복 초과는 `fail`; 불변식 SKIPPED를 0으로 세지 않고 `summary.duplicateIssue`를 `미측정`으로 낸다.
- `loadtest/runner/search-measure.mjs`:
  - `SEARCH_RULES` — `{ sizes: [10000, 20000], reps: 3, validReps: 2, suggestP95Ms: 50, searchP95Ms: 300, top1: 0.9, top3: 0.98, versionLagSeconds: 60, unavailableRatio: 0.01, poolWaitingRatio: 0.05, crowdRate: 20, randomRate: 20, durationS: 60 }`.
  - `parseSearchArgs(argv)` → `{ size, reps, golden, crowdRate, randomRate, durationS, base, out, record, runId, promUrl }`. `size`는 10000·20000만, `reps`는 1~3 정수, `--golden`은 SR-T12 보고를 같은 폴더에 남긴다. 기본 세기는 `crowdRate 20`·`randomRate 20`·`durationS 60`이고, `--base`는 `http://host.docker.internal:3001`(호스트 core-svc)이다. 모르는 인자·범위 밖은 `UsageError`.
  - `parseK6Csv(text)` → `{ requests, dropped, phases: { crowd, random } }`. k6 `--out csv`의 표본을 머리 칸 이름으로 읽어 `http_req_duration`의 `route`·`phase`·`len`·`status` 꼬리표별로 센다. 구간·경로마다 `{ count, ok, unavailable, other5xx, p95 }`를 낸다. CSV에 없는 구간은 `count: 0`이고 0으로 통과시키지 않는다.
  - `judgeSearchRep({ samples, poolWaiting })` → `{ valid, verdict, problems, metrics }`. 놓친 반복 > 0, 네 구간·경로 가운데 요청 0, `poolWaiting` 표본 0은 `invalid`. p95·503·5xx·대기 비율이 정본 밖이면 `fail`.
  - `judgeSearchRun(reps)` → `{ validReps, verdict, sizes, worst }`. 유효 회차 2회 미만은 `invalid`, 유효 회차 하나라도 `fail`이면 `fail`, 모두 통과면 `pass`. `worst`는 구간·회차별 p95의 최댓값이다.
  - `parseGoldenReport(json)` → `{ cases, top1, top3, rates, valid }`. 경우 수 100·목표 값이 정본과 다르면 `valid: false`.
  - `nfr028Verdict({ search, golden, versionLag, removal })` → `{ parts: { suggest, search, top1, top3, versionLag, removal }, verdict }`. `search`는 `{ crowd: { suggestP95, searchP95 }, random: { suggestP95, searchP95 } }`이고 함수가 구간별 최악을 고른다. `removal`은 SR-T15 ① 인용 글이나 `null`이다. 값이 없으면 그 부분은 `미측정`, 전체는 `pass`가 아니다.
  - `parsePromSeries(json, name)` → `{ values, missing }`. Prometheus 응답이 비었거나 `NaN`이면 `missing`에 이름을 남긴다.
- `loadtest/plan/f09-plan.json`: `plan`·`title`·`created`·`basis`·`state_file`·`start_gate`·`gates`(객체)·`runs`. 실행마다 `n`(1부터 차례)·`key`·`group`·`title`·`estimate_min`·`stage`·`conditions`·`commands`(`{label, argv}`)·`criteria`(정본 자리 글 목록)·`ledger`·`artifact`·`gate`. `state_file`은 `.cache/peaket-f09/state.json`, `gates`는 `{ "WINDOW-F089": "감독이 연다" }`, 모든 실행의 `gate`는 `WINDOW-F089`다. `bat025-plan.mjs`의 `validatePlan`을 지난다.
- `loadtest/run.mjs v1 relay-fault …`, `v1 payment-fault …`, `v1 search …`: 인자는 7.2의 파서와 같다.

**관점별 확인**
- ① 공허 통과: 19/19는 모듈·계획 파일 없음 때문에 실패한다(재현). 그러나 F089-5 ②는 모듈이 생겨도 fixture가 200/503을 뒤집어 실패한다(RV089-07). 함수 존재만 보는 곳(`oldLeaderSendCount`, `missingRows`의 빠진 행, `RELAY_RULES`·`SEARCH_RULES`)과 0건을 0으로 바꾸는 곳(시뮬레이터 원장, P-T1 이중 발권)을 지적했다. `judgeSearchRep`·`parsePromSeries`·`judgeRelayRun`의 빈 표본 무효는 잘 되어 있다.
- ② 판정 기준: V-T27은 도착률·P-T5·행 배열·발생기가, V-T28은 같은 좌석 섞기·30초·적용/증거·옛 리더가, P-T1은 시뮬레이터 원장 꼴·이중 발권/SKIPPED·웹훅 중복 모드·발생기 유효가, SR-T13 ①·NFR-028은 부하 세기·빈 구간·최악 p95·경계 반대쪽이 빠졌다. 정본 값 자체를 새로 주장한 곳은 없다.
- ③ 경계: 계획과 시험은 K1·K2·K7·V-T18을 다시 재지 않고, ASVS 18행·SR-T11 ②·SR-T15 ③을 닫지 않는다. 다만 F089-9 ②의 경계 검사가 P-T1 결제 명령을 `v1 payment`로 못 만들게 해 P-T1 추가 몫과 충돌한다(RV089-02).
