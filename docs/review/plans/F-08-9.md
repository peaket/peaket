# 기능 계획: F-08-9(장애 주입 기록 검사·검색 측정·NFR-028, 동결 로컬 트랙)

- **진행**: 계획·시험(측정 준비) 끝, **리뷰 준비에서 멈춤**(2026-11-26). 실제 측정·보고서·기록은 리뷰 반영 뒤 측정 창에서 한다. 이 파일의 측정 결과는 모두 `미측정`이다.
- **무엇**: BUILD_ORDER '기능 단위 계획' F-08-9(갈래 4, 등급 B, HOT-480·HOT-490, WBS 4.00일, 단계 줄 `HOT-480 wbs 2.12.3`·`HOT-490 wbs 2.12.4`)의 작업 목록이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **쉬운 말**: 두 가지를 잰다. ① 거래 사건을 보내는 릴레이(Outbox에 쌓인 사건을 Kafka로 옮기는 일꾼)에 부하를 걸고, 일부러 리더를 멈추거나 Kafka 브로커를 세우거나 DB 연결을 끊었을 때 사건이 빠지거나 순서가 뒤집히지 않는지, 그 장애가 실제로 일어났다는 기록이 남는지 본다. ② 검색과 자동완성이 오픈 직전 몰림·무작위 입력에서 목표 시간 안에 답하는지 재고, 골든 세트(기대 결과를 정한 검색어 묶음) 정답률·사전 판 지연과 함께 NFR-028을 판정한다.
- **바탕**: 작업 폴더 `D:/ticketpass-freeze-F-08-9`, 가지 `freeze/lane4-F-08-9`, 기준 `origin/feature/lane4-F-08-2-refresh` `19b33ba85`(F-08-2·F-08-8 보고서 포함). 계획·시험 담당은 Docker·kind·측정을 하나도 돌리지 않았고 Docker 잠금도 잡지 않았다.
- **차례(감독 지시 2026-11-26)**: 계획 → 시험(측정 준비) → 리뷰(새 세션) → 반영 → 측정/문서 → 기록. ADR-0373의 B등급 차례는 계획 → 시험 → 구현 → 시험 통과면 합침이고 시험 리뷰가 없다. 이 기능은 **'측정이 통과로 새지 않는가'가 핵심**이라 감독이 리뷰를 한 번 더 붙였다. 리뷰는 코드가 아니라 측정 설계·판정·시험을 본다. 이번 동결 트랙은 계획과 시험을 한 세션이 맡았다(감독 지시). 역할 꼬리말은 `Role: plan`·`Role: test`로 나눠 남긴다.
- **동결 로컬 범위**: ADR-0373·ADR-0386에 따라 `freeze/F-08-9` 가지와 이 워크트리에서만 만든다. `develop`·`release/1.0.0`에 합치지 않고, 릴리스 가지·`main`에 체리픽하지 않는다. 마이그레이션·릴리스 플래그를 만들지 않고, `deploy/`의 출시 환경 값도 고치지 않는다. 이 기능의 결과는 v1 출시 계약의 근거로 쓰지 않는다.
- **수치**: 이 파일과 시험은 정본의 목표·판정 값을 **인용만** 한다. 측정 전이라 이 기능이 내는 값은 전부 `미측정`이다. 정본에 없는 새 수치를 주장하지 않는다.
- **한 줄 결론**: 릴레이 장애 주입 도구·Toxiproxy/시뮬레이터 원장 대조·검색 측정 실행기·판정기가 없다. 있는 v1 무대(릴레이 둘 포함)·`v1-search.js`·`fill-search.mjs`·불변식 검사기·`bat025-plan.mjs --plan`에 넷을 더하면 측정 창 약 3~4시간이다. 장부 범위는 측정 7항목으로 좁힌다.

## 2. 감독에게

1. **장부 범위를 측정 7항목으로 좁혔다** — `V-T27`, `V-T28 ①②③`, `P-T1`, `SR-T13 ①②`다. 지금 범위(46항목)는 이 기능이 닫지 못하는 것을 포함한다: `docs/security/asvs/verification-tools.md`의 18행 가운데 7행은 다른 곳 시험에 `[ASVS v5.0.0-x.y.z]` 꼬리표가 없어 'ID만', 2행은 해당 없음, 9행은 자동 시험이다. `docs/features/search.md`의 23행 가운데 SR-T11 ②는 CDN 배포 구성(HOT-450) 몫이라 '다른 단계', SR-T15 ③은 AWS 계정이 필요해 '미검증'이다. `NFR-028`은 SR-T12·SR-T13이 가리켜 별도 장부 항목이 아니다. 좁힌 뒤 `node tools/ci/ledger.mjs --batch F-08-9 --require`가 통과한다(5절). ASVS 꼬리표 붙이기와 SR-T15 ③은 이 기능이 하지 않는다.
2. **P-T1은 A등급 항목인데 이 기능은 부분만 잰다** — P-T1의 돈 경로 A 증명(이중 결제·P3·P6·좌석 누수)은 F-08-8 K7 ②가 이미 맡았고, 이 기능은 그 위에 **장애 주입 기록 검사**(Toxiproxy 지연·끊김, 시뮬레이터 원장 대조, 웹훅 중복)를 더한다. ticket-svc 5분 중단·이중 발권·일일 대사 불일치는 v1 합본 무대에 ticket-svc가 없어 **미측정**으로 남긴다. P-T1의 장부 상태는 '측정' 그대로 두고 결과는 '부분'으로 적는다.
3. **F-08-8과의 경계** — F-08-8이 잰 K1·K2·K7과 P-T1의 기본 K7 ②는 다시 재지 않는다. 이 기능은 릴레이(V-T27·V-T28)와 결제 경로의 추가 장애 모드, 검색(SR-T13 ①)만 한다. F-08-8의 보고서·실행 ID를 인용하고 새 수치를 주장하지 않는다.
4. **F-08-10과의 경계** — F-08-10(V-T18, 서비스 분리 효과 비교)은 동결이고 이 기능이 만들지 않는다. 세 구성 비교·M2 블로그도 하지 않는다.
5. **측정할 수 없는 것** — 실제 MSK 패치(로컬 Strimzi로 흉내), Aurora 읽기 전용 복제본(SR-T15 ③), CloudFront CDN, ticket-svc 5분 중단·일일 대사, 운영 28일 윈도우. 보고서에 '미측정'과 까닭을 적고 통과로 세지 않는다.
6. **측정 창** — 약 3~4시간(무대 올리기 포함, 무효 재측정 여유 별도). 동결 로컬 트랙의 창이라 v1 릴리스 측정 창과 섞지 않는다. 이번 턴에는 열지 않는다. 감독이 열고, Docker 잠금은 **`docker` 한 자리**(`lock.sh take docker lane4-F-08-9`, `docker-all` 금지)를 쓴다. kind 이름은 `lane4-f09`로 다른 갈래와 겹치지 않게 한다.
7. **리뷰** — 새 세션이 계획·시험만 보고 본다. 보는 곳: 측정 판정이 빈 결과·SKIPPED·0건을 통과로 만들지 않는가, 장애 주입이 실제로 일어났다는 증거를 요구하는가, 정본 값과 시험 단언이 맞는가, F-08-8/F-08-10 경계를 넘지 않는가, 이 기능이 수치를 미리 주장하지 않는가. 지적은 시험 담당이 고치고(`Fix-By: test`), 리뷰 담당이 확인한다.
8. **정할 것** — 14절. 추천대로 정하고 측정 전에 이 파일에 적는다.

## 3. 범위

### 3.1 하는 것

- **V-T27(릴레이 부하 측정)**: v1 무대의 purchase DB에 정본 V-T27 행이 정한 2배 [가정] 도착률로 30분 동안 Outbox 행을 넣고, purchase-svc 릴레이(복제 2·리더 하나)를 돌린다. 잰 것: 릴레이 지연(행을 넣은 때부터 Kafka 확인까지) p50·p99, 묶음 처리 시간 p99, DB CPU 증가분(같은 도착률로 릴레이를 끈 기준 실행과의 차이), Outbox 일 파티션의 죽은 행과 자동 청소. 같은 30분 안에 로컬 Kafka 브로커 하나를 다시 시작하고, 그 구간의 릴레이 지연과 결제 확정 p99를 평소 구간과 나눠 남긴다.
- **V-T28 ①②③(순서·유실)**: 같은 V-T27 부하에서 ① 묶음을 보내는 중일 수 있는 리더를 SIGSTOP으로 멈춰 Lease를 넘긴다 ② Kafka 브로커를 30초 멈춘다 ③ 릴레이의 DB 연결을 끊는다. 세 경우 모두 빠진 행 0, 같은 키의 `seq` 순서 뒤집힘 0, 다시 보낸 사건의 `eventKey` 같음, 깨어난 옛 리더가 새 리더와 같은 행을 동시에 보내지 않음, 리더가 바뀐 시간을 장부에 남긴다. 장애마다 `faults.ndjson`에 종류·시작·끝·적용 여부·증거를 남기고, `적용=false`나 증거 없음은 그 실행을 무효로 한다.
- **P-T1의 추가 몫(결제 장애 기록 검사)**: 결제 시뮬레이터 앞에 Toxiproxy를 두어 응답 지연·연결 끊김을 넣고, 시뮬레이터가 payment-svc로 웹훅을 보내게 해 같은 `webhook-id`를 중복 발송한다. 결제 1만 건 실행 1회(무효면 1회만 더)에서 시뮬레이터 원장(`GET /sim/ledger`)과 payment 원장을 대조해 P6(승인인데 원장에 없음) 0, 이중 발권 0, 불변식 결과를 남긴다. ticket-svc 5분 중단·일일 대사는 미측정(2절 2).
- **SR-T13 ①·NFR-028(검색 측정)**: 현재 v1 무대의 core-svc 원본에 `loadtest/scenarios/v1-search.js`의 가벼운 부하(몰림·무작위 각각 정본이 정한 세기, 60초)를 공연 1만·2만에서 크기마다 3회 보낸다. 유효 회차 2회 이상, 구간별 검색 200 1건 이상, 받는 쪽 p95·503 비율·그 밖의 5xx·`search_pool_waiting` 비율을 정본 SR-T13 ①의 판정으로 본다. 같은 실행 묶음에서 SR-T12 골든 세트 보고(`search-golden-report.json`)와 사전 판 지연 게이지(`search_dictionary_version_lag_seconds`)를 읽어 NFR-028의 다섯 부분(자동완성 p95·검색 p95·1위 정답률·3위 안 정답률·사전 판 지연)을 판정한다.
- **SR-T13 ②**: 새로 재지 않는다. BAT-056의 2026-11-18 측정 결과와 `tools/local/e2e/gateways.e2e.mjs`의 설정 시험을 근거로 보고서에 인용하고, 장부 notes를 그대로 둔다.

### 3.3 수용 기준·완료의 정의·실패 시나리오

**완료의 정의(동결 로컬 트랙의 자체 완료)** — 아래를 모두 만족할 때 이 기능을 끝낸다. v1 출시 완료와는 별개다.

1. 계획·시험·리뷰·반영·구현·측정·보고서·기록 커밋이 이 가지에 있다.
2. V-T27을 30분 실행으로 재고, 릴레이 지연 p50·p99, 묶음 p99, DB CPU 증가분, 죽은 행·자동 청소, 브로커 재시작 구간을 보고서에 적었다.
3. V-T28 ①②③이 모두 실제로 적용됐다는 증거가 있고, 빠진 행 0·같은 키 순서 뒤집힘 0·`eventKey` 불일치 0·옛 리더 재개 뒤 보내기 0이며, 리더 변경 시간을 장부에 남겼다.
4. P-T1의 추가 몫(시뮬레이터 지연·끊김, 웹훅 중복)을 1회 이상 적용하고, P6 0·이중 발권 0·불변식 결과를 적었다. ticket-svc 5분 중단·일일 대사는 `미측정`으로 적었다.
5. SR-T13 ①을 공연 1만·2만에서 각각 유효 회차 2회 이상으로 재고, 구간별 p95·503·그 밖의 5xx·`search_pool_waiting`을 정본 판정으로 적었다. NFR-028의 다섯 부분을 `pass`·`fail`·`미측정` 가운데 하나로 적었다(유효 회차의 가장 나쁜 p95).
6. `node tools/ci/ledger.mjs --batch F-08-9 --require`가 통과하고, notes에 실행 ID·결과가 들어갔다. 이 기능의 결과를 v1 정본 판정 칸이나 출시 계약에 쓰지 않았다.

### 6.1 무대와 공통 규칙

- 새 kind 클러스터(`PEAKET_CLUSTER=lane4-f09`, `cluster.mjs up` → `observability` → `v1 --redis-tls on --replicas 3`), Prometheus(`cluster.mjs prometheus`), 불변식 검사기 빌드(`corepack pnpm --filter @peaket/invariant-checker build`). 무대 값은 `docs/verification.md` §3.8 그대로다.

- 판정: 실패·무효·SKIPPED는 통과가 아니다. 빈 결과(요청 0·표본 0·장애 0)는 통과가 아니라 무효다.
- 반복: V-T27 1회(무효면 1회만 더), V-T28 ①②③은 그 1회 안에서 차례로 넣는다. 검색은 크기마다 3회(정본 SR-T13 ①의 유효 회차 규칙). P-T1 추가 몫 1회(무효면 1회만 더).

- 측정 중에는 다른 시험·빌드를 돌리지 않는다. Docker 잠금은 `docker` 한 자리다(2절 6).

### 6.3 장애 주입 시각과 기록

- V-T28 ①은 30분 본구간의 약 3분의 1 지점, ②는 약 3분의 2 지점, ③은 끝나기 약 5분 전에 넣는다. ①은 SIGSTOP 전에 최근 보내기 활동(묶음 카운터·발행 카운터)을 확인해 '묶음을 보내는 중일 수 있는' 창을 고른다. 고르지 못하면 ①을 한 번 다시 넣는다.
- ②는 브로커를 30초 멈춘다(정본 V-T28 ②). ③은 PostgreSQL에서 릴레이 사용자의 연결을 `pg_terminate_backend`로 끊는다. 끊긴 연결 수가 0이면 무효다.
- 장애마다 `faults.ndjson`에 `{kind, startedAt, endedAt, applied, evidence}`를 남긴다. 증거는 SIGSTOP한 파드·PID, 브로커 정지·재개 시각, 끊긴 DB 연결 수, Toxiproxy 토글 결과다.
- `faults.ndjson`에 ①②③이 모두 없거나 `applied`가 거짓이거나 증거가 비면 그 실행은 무효다. 빠진 행·순서 뒤집힘·`eventKey` 불일치가 1건이라도 있으면 실패다. 실패를 숨기려고 다시 재지 않는다.

### 6.4 검색 판정과 NFR-028

- SR-T13 ①의 판정은 `docs/features/search.md` SR-T13 줄의 '측정 판정'을 그대로 쓴다. 크기마다 유효 회차 2회 이상, 구간별 검색 200 1건 이상, 받는 쪽 p95·503 비율·그 밖의 5xx·`search_pool_waiting` 비율. 무거운 부하(503 확인)는 BAT-167이 이미 했고, 이 기능은 가벼운 부하만 다시 잰다.
- NFR-028의 다섯 부분은 `docs/planning/02-requirements.md` NFR-028 행과 `docs/features/search.md` §8·§10에서 가져온다. 하나라도 값이 없으면 그 부분은 `미측정`이고 전체는 통과가 아니다. p95는 유효 회차 가운데 **가장 나쁜 값**으로 보수적으로 적는다(추천 적용 2026-11-26).
- 골든 세트는 CI 시험의 `search-golden-report.json`을 측정 폴더로 복사해 쓴다. 경우 수·순서 경우가 정본과 다르면 무효다.
- 사전 판 지연은 측정 중 Prometheus에서 `search_dictionary_version_lag_seconds`를 읽어 최댓값을 쓴다. 시계열이 없으면 0이 아니라 `미측정`이다.

### 6.5 멈춤 규칙(측정 전 등록)

- 무대가 15분 안에 준비되지 않으면 멈추고 감독에게 알린다.
- V-T28 주입이 적용되지 않거나 빠진 행이 1건이라도 나오면 그 실행을 멈추고 실패로 적는다. 같은 조건으로 한 번만 더 재고, 또 나오면 원인 조사 없이 보고서에 적고 다음으로 간다.
- 검색 유효 회차가 2회 미만이면 같은 크기로 한 번만 더 재고, 그래도 모자라면 '무효'로 적는다.
- 전체가 계획의 1.3배를 넘게 밀리면 감독에게 알리고 14절 '줄일 곳' 차례대로 뺀다.

### 7.2 공개 인터페이스(시험이 가정한 꼴)

- `loadtest/runner/relay-fault.mjs`:
  - `RELAY_RULES` — 정본 V-T27·V-T28의 값(30분, 2배 [가정], 지연 p99·묶음 p99·CPU 증가분 [가정], 브로커 30초).
  - `parseRelayFaultArgs(argv)` → `{ mainSeconds, rate, relay, out, record, runId, promUrl }`. `mainSeconds`는 60~3600 정수, `rate`는 1 이상 정수, `--relay on|off`(기본 on)는 릴레이를 끈 기준 실행(`w2-relay-baseline`)에 쓴다. 모르는 인자·범위 밖은 `name === 'UsageError'`.
  - `faultPlan({ mainSeconds })` → `[{ kind: 'leader-stop'|'kafka-stop'|'db-cut', atSecond, durationSeconds }]`. 세 종류가 한 번씩, `atSecond`는 1~`mainSeconds-1`, 서로 60초 이상 떨어짐, `kafka-stop`의 `durationSeconds`는 30.
  - `validateFaultRecords(records, plan)` → `{ ok, problems }`. 세 종류가 모두 있고 `applied === true`, `startedAt`·`endedAt` ISO, `evidence` 비지 않음.
  - `missingRows(sent, received)` → 빠진 행 ID 배열. `orderViolations(received)` → 같은 키의 `seq` 뒤집힘 수. `eventKeyMismatches(received)` → 한 행에 다른 `eventKey`가 둘 이상인 수. `oldLeaderSendCount(received, oldLeader)` → 옛 리더가 새 리더 뒤에 보낸 수.
  - `summarizeSamples(samples)` → `{ count, p50, p99, max }`. 표본이 없으면 `count: 0`이고 p50·p99·max는 `null`(0이 아니다).
  - `judgeRelayRun(o)` → `{ verdict: 'pass'|'fail'|'invalid', problems, triggers, summary }`. `o`는 `{ mainSeconds, rate, sent, received, lagSeconds, batchSeconds, faults, leaderChangeMs, oldLeaderPublishedAfterResume, relayCpuPctPoints }`. `summary`는 `{ missing, order, eventKey, p50, p99, batchP99, leaderChangeMs }`이고 `missing`·`order`·`eventKey`는 건수다. 빈 입력·장애 기록 없음·30분 아님은 `invalid`. 빠진 행·순서·`eventKey`·옛 리더 보내기 > 0은 `fail`. 정본 V-T27의 지연·묶음·CPU 문턱을 넘으면 `triggers`에 `relay-lag`·`batch`·`db-cpu` 코드로 적고(ADR-0116 결정 6으로 간다는 표시), 그것만으로 `fail`로 만들지 않는다.
  - `buildToxiproxy({ name, listen, upstream, toxics })` → Toxiproxy API 꼴. `toxics[].type`은 `latency`·`reset_peer`·`timeout`만, 값은 0 이상 정수, 모르는 종류·음수는 `RangeError`.
  - `reconcileSimLedger({ sim, payment })` → `{ approved, recorded, missing, duplicatePayments, verdict }`. 시뮬레이터 원장 승인과 payment 원장 기록을 결제 키로 맞춘다. 시뮬레이터 원장이 비면 `verdict: 'invalid'`.
- `loadtest/runner/search-measure.mjs`:
  - `SEARCH_RULES` — 정본 NFR-028·SR-T13의 값(자동완성·검색 p95, 1위·3위, 사전 판 지연, 503·대기 비율, 크기 둘, 회차 3, 유효 2).
  - `parseSearchArgs(argv)` → `{ size, reps, out, record, runId, promUrl }`. `size`는 10000·20000만, `reps`는 1~3 정수. 모르는 인자·범위 밖은 `UsageError`.
  - `parseK6Csv(text)` → `{ requests, dropped, phases: { crowd, random } }`. k6 `--out csv`의 표본을 머리 칸 이름으로 읽어 `http_req_duration`의 `route`·`phase`·`len`·`status` 꼬리표별로 센다. 구간·경로마다 `{ count, ok, unavailable, other5xx, p95 }`를 낸다. k6 요약만으로는 구간별 p95가 나오지 않아 CSV를 쓴다(부하·시나리오는 바꾸지 않는다).
  - `judgeSearchRep({ samples, poolWaiting })` → `{ valid, verdict: 'pass'|'fail'|'invalid', problems, metrics }`. `samples`는 `parseK6Csv` 결과, `poolWaiting`은 1초마다 읽은 게이지 값 배열이다. 놓친 반복 > 0, 네 구간·경로 가운데 요청 0, `poolWaiting` 표본 0은 `invalid`. p95·503·5xx·대기 비율이 정본 밖이면 `fail`.
  - `judgeSearchRun(reps)` → `{ validReps, verdict, sizes }`. 유효 회차 2회 미만은 `invalid`, 유효 회차 하나라도 `fail`이면 `fail`, 모두 통과면 `pass`.
  - `parseGoldenReport(json)` → `{ cases, top1, top3, rates, valid }`. 골든 세트 시험(SR-T12)을 먼저 돌려 순서 경우까지 통과한 보고서만 받는다. 경우 수·목표 값이 정본과 다르면 `valid: false`.
  - `nfr028Verdict({ search, golden, versionLag })` → `{ parts: { suggest, search, top1, top3, versionLag }, verdict }`. `search`는 `{ suggestP95, searchP95 }`, `golden`은 `parseGoldenReport` 결과, `versionLag`은 초 수나 `null`이다. 값이 없으면 그 부분은 `미측정`, 전체는 `pass`가 아니다.
  - `parsePromSeries(json, name)` → `{ values, missing }`. Prometheus 응답이 비었거나 `NaN`이면 `missing`에 이름을 남긴다.
- `loadtest/plan/f09-plan.json`: 실행마다 `key`·`group`·`title`·`estimate_min`·`stage`·`conditions`·`commands`(`{label, argv}` 목록)·`criteria`(정본 자리 글 목록)·`ledger`·`artifact`. `state_file`은 `.cache/peaket-f09/state.json`. 게이트는 `WINDOW-F089` 하나(감독이 연다).
- `loadtest/run.mjs v1 relay-fault …`, `loadtest/run.mjs v1 search …`: 인자는 7.2의 파서와 같다.
