## 계획

계획 담당 `lane3-f055-plan`(claude-opus-5-5), 2026-11-23. 제품 코드·시험은 쓰지 않았다.

### 1. 끝내는 것과 넘기는 것

단계 줄(BUILD_ORDER GAT-170)은 '단계 범위는 기록상 끝났다'고 적고 남은 셋(W7-WIR-02, 감사 C1-14·C1-19)을 든다. 코드를 직접 보니 판정 시험도 A 등급 기준(경계 양쪽·장애 주입·바깥 경계에서 '기록이 저장되지 않는다')에 못 미친다. 그래서 이 기능은 **남은 셋 + 판정 시험 보강 + 화면 한 군데 잇기 + 거절 지표**다.

- **끝내는 것**
  1. W7-WIR-02: ticket-svc의 옛 관제 HTTP 처리기(`/v1/ops/scanner-devices*`)를 지운다. 관제 기기 경로는 ops-svc → ticket-svc gRPC `ScannerDeviceService`만 남는다.
  2. C1-14: `POST /v1/scanner/scans`와 `POST /v1/scanner/device-enrollments`도 `Origin`(스캐너 PWA 출처)과 JSON만 받는다(O-T35). 기기 승인 요청·토큰(identity-svc)과 같은 platform 함수를 쓴다.
  3. C1-19: 등록 코드를 꺼낸 뒤 기기 키를 묶는 저장이 일시 실패하면 코드를 처음 만료 시각 안에서 되살린다(O-T42 ⑤).
  4. O-T37 ①~⑨, O-T21 ①②를 바깥 경계(ticket-svc HTTP, 실제 PostgreSQL·Valkey)에서 '응답 + 기록이 저장되지 않음'까지 단언하고, DPoP `iat` 창·`jti` 보관·세션 5초 캐시 경계와 identity·원장·Redis 장애 때 닫힘을 시험한다.
  5. 거절 지표 `scanner_auth_rejections_total{service, reason}`(O-T37 ⑨, ASVS 16.3.4, offline-gate §6.6).
  6. 화면: 관제 콘솔 SCR-053의 등록 QR(`/enroll#code=…`)을 스캐너 앱이 실제로 받는다. 지금은 앱이 `#code=`를 읽지 않고, `?live=1`이 없으면 디자인 보드가 뜬다.
- **이미 있는 것(고치지 않고 시험으로 고정)**: platform `ScannerGuard`·`verifyDpopProof`·`ScannerAuthState`(5초 캐시)·시작 확인(RolesGuard 막음은 스캐너 포트가 있으면 풀림, AZ-T1), ticket-svc 기기 원장·등록 코드·IP 실패 제한·SEV3 경보·폐기 때 세션 종료·`last_seen_at`, identity-svc `CheckScannerSession`, ops-svc `/v1/ops/scanner-devices*`(권한·감사), 콘솔 SCR-053 연결 화면(`ConnectedPage.tsx`, ops-api), 스캐너 앱 `LiveEnrollScreen`(코드 입력)·`credentials: 'omit'`, gw-scanner CORS(`Allow-Headers`에 `DPoP`, `Expose-Headers`에 `Date`·`WWW-Authenticate`, `allowCredentials` 없음).
- **넘기는 것**
  - O-T21 ③(앱이 401 뒤 토큰을 지우고 기기 인증만으로 다시 올리기)과 O-T37 ⑧의 서비스 워커·비행기 모드 몫: 앱 업로드 큐가 없다(BAT-430 B7, `uploadScans`를 부르는 곳 없음). F-05-4 몫이다. BUILD_ORDER F-05-4 행 장부 범위에 `O-T21 ③`을 더했다.
  - d5 §1.6 22번(기기 이름·배정 파트너 변경, 회수 기기 다시 등록, 퇴역): API가 없다. 이 기능의 '배정'은 등록 때 배정 파트너와 기존 기기 배치(GAT-140 몫으로 이미 있음)다. 감독이 coord '범위 늘어남'에 한 줄로 적기를 권한다.
  - 감사 C1-12(폐기 뒤 같은 키 재등록 불가)·C1-23(앱의 `invalid_dpop_proof` 구분)은 각각 R-610·F-05-4 몫. mTLS 운영 PoC(O-T36)는 wbs 일수 밖.

### 3. 이 계획 커밋이 정본에 쓴 것(모두 추천 적용, 2026-11-23, F-05-5)

1. O-T37 ⑥: 미등록 키 증명은 **403 `device-unregistered`**(기록 저장 없음). 시험 표만 401이라 적었고 authz-matrix §5.2·openapi 문제 이름·지금 코드·스캐너 앱(재등록 안내)은 403이었다. 정본 셋이 맞는 쪽으로 시험 표를 고쳤다.
2. O-T37 ⑨(새): 거절마다 지표가 이유 이름표로 하나씩 오른다. 지표 이름·이름표 18가지는 offline-gate §6.1 'GAT-170 마감 규칙'.
3. O-T21을 ①②③으로 나눴다. ①에 5초 캐시 경계(5초가 '되는' 요청부터 다시 묻는다)를 적었다. ③은 F-05-4.
4. O-T35에 기기 등록 경로를 더했고 '경로마다'를 적었다. offline-gate §6.1 위조 요청 방어 줄·asvs 3.5.1도 같다. openapi `device-enrollments`에 403·415·503을 더했다(계약 생성물은 구현 담당이 `gen`).
5. O-T42 ⑤(새, C1-19): 첫 요청 503 `scanner-auth-unavailable`·실패로 안 셈·재시도 201·만료 시각 안 늘어남·새 코드가 나왔으면 되살리지 않음(410).
6. offline-gate §6.1 'GAT-170 마감 규칙' 줄: 옛 관제 처리기 지움, 출처 환경 변수 `PEAKET_SCANNER_PWA_ORIGIN`(identity와 같은 기본값), 코드 되살리기, 거절 지표, 등록 QR 조각 처리.
7. offline-gate §6.6 운영 확인 표(새). asvs 16.3.4에 지표를 적었다. authz-matrix §5.2의 관제 경로 주인을 ops-svc로 고쳤다.
8. BUILD_ORDER F-05-5 행(범위·선행 `-`·상태 `진행`), F-05-4 행(`O-T21 ③`).

새 ADR·마이그레이션은 필요 없다(DB 표가 바뀌지 않는다. identity 0039·0041, ticket 0013·0015~0017은 쓰지 않는다).

### 5. 공개 인터페이스(시험이 바로 쓴다. 이름은 이대로)

```ts
// packages/platform (index.ts에서 내보냄)
export type ScannerAuthRejection = DpopRejectReason | 'proof_missing' | 'token' | 'session' | 'role' | 'device_unregistered' | 'device_revoked' | 'unavailable';
export const SCANNER_AUTH_REJECTIONS: readonly ScannerAuthRejection[]; // 18개, 차례는 offline-gate §6.1 'GAT-170 마감 규칙'의 차례
interface ScannerAuthWiring { /* 기존 칸 */ onRejected?: (reason: ScannerAuthRejection) => void }
export const SCANNER_PWA_ORIGIN_ENV = 'PEAKET_SCANNER_PWA_ORIGIN';
export function scannerPwaOriginFromEnv(env?: Record<string, string | undefined>): string; // 없거나 빈 값이면 'https://scanner.peaket.example'
export function assertScannerOrigin(origin: unknown, expected: string): void; // 문자열이고 expected와 정확히 같을 때만 통과. 아니면 ProblemError 403 'scanner-origin-forbidden'
```

- `ScannerGuard`의 이유 사상: 증명 헤더 없음 → `proof_missing`(401 `invalid_dpop_proof`), `DpopRejected(r)` → `r`(401 `invalid_dpop_proof`), 신원 없음·토큰 모양·`X-User-Jkt` 없음·`X-User-Ath` 불일치·기기 전용 경로에 토큰·mTLS 비밀 불일치·자격 종류 불일치 → `token`(401 `invalid_token`), 세션 `valid:false`·역할 없음 → `session`(401 `invalid_token`), 처리기 허용 역할 밖 → `role`(403), 미등록 → `device_unregistered`(403 `device-unregistered`), ACTIVE 아님 → `device_revoked`(403 `device-revoked`), 원장·세션·`jti` 저장소에 닿지 못함 → `unavailable`(503 `scanner-auth-unavailable`, `Retry-After: 1`). 통과는 부르지 않는다.
- ticket-svc:

```ts
// domain/ports.ts
export interface EnrollmentCodeStore {
  put(i: { codeHash: string; deviceId: string; ttlMs: number }): Promise<void>;
  /** 한 번만 꺼낸다. 남은 수명으로 만료 시각을 함께 준다 */
  take(codeHash: string): Promise<{ deviceId: string; expiresAtMs: number } | undefined>;
  /** 되살린다. 만료 시각이 지났거나 그 기기의 지금 코드가 다른 코드면 false(되살리지 않음) */
  restore(i: { codeHash: string; deviceId: string; expiresAtMs: number }): Promise<boolean>;
}
// application/scanner-devices.ts
export class ScannerEnrollmentUnavailable extends Error {} // 묶기 저장의 일시 오류(되살림 뒤 던짐)
// config.ts: TicketServiceConfig.scannerPwaOrigin: string
```

- `enroll`의 규칙: `ScannerDeviceKeyConflict` → 지금처럼 `KEY_IN_USE`(409, 코드 소모, 실패로 셈). `bindCredential`이 `null`(ACTIVE 아님) → `DEVICE`(410, 코드 소모). 그 밖에 던지면 → `restore`(만료 시각 = `take`가 준 값) → `ScannerEnrollmentUnavailable`. 이 경우 `limiter.failed`를 부르지 않는다.
- Redis 어댑터 `take`: `PTTL` 뒤 `GETDEL`(같은 키), `expiresAtMs = now + pttl`. `restore`: 남은 ms가 1 이상이고 `scanner:enroll-device:{deviceId}`가 없거나 같은 해시일 때만 두 키를 `SET … PX <남은 ms>`로 다시 쓴다. 키 이름은 지금 것 그대로.
- 스캐너 앱 `apps/scanner/src/api/enrollment-link.ts`:

```ts
/** '#code=KDTW-BMQX-HLRP'(URL 인코딩 가능)에서 코드를 꺼낸다. 없거나 비었거나 64자를 넘으면 undefined */
export function enrollmentCodeFromHash(hash: string): string | undefined;
/** 조각에 code가 있으면 replace(pathname + search)를 한 번 부른다(주소창에서 지움). 없으면 부르지 않는다 */
export function stripEnrollmentFragment(loc: { pathname: string; search: string; hash: string }, replace: (url: string) => void): void;
```

- 화면 상태(SCR-036 `/enroll` 실제 연결, 이름은 지금 화면 것): '기기 등록'(입력 칸에 조각 코드), '등록하는 중', 오류 글(`DeviceLoginError.message`, 410이면 만료·사용 문구), 성공이면 `/login?live=1`로 간다. 조각 코드가 있으면 `?live=1` 없이도 실제 연결이다. 코드를 `localStorage`·`sessionStorage`·IndexedDB에 쓰지 않는다.

### 7. 실패 확인 방법(시험 담당)

- 구현 전 트리 = 기준 커밋 `82c200304`(임시 worktree에 이 기능 시험 파일만 복사). 새 동작 시험은 실패해야 한다: `assertScannerOrigin`·`onRejected`·`enrollment-link` 없음(불러오기 실패), 출처 틀린 업로드 200, `bindCredential` 일시 오류 뒤 재시도 410, ticket-svc `/v1/ops/scanner-devices` 201, `route-contract` 예외 줄 있음.
- 이미 되는 동작(`iat` 경계·`jti`·5초 캐시·장애 503·⑥⑦ 403·415)은 구현 전에도 통과한다. '회귀 고정'으로 적고, 그중 둘 이상을 코드 한 줄 바꿔(예: `>`를 `>=`, 캐시 `<`를 `<=`) 실패하는지 보여 단언이 실제로 잡는다는 것을 남긴다(고친 줄은 되돌린다).
- 명령 예: `pnpm --filter @peaket/platform test test/scanner-auth-f055.test.ts`, `pnpm --filter @peaket/ticket-svc test test/scanner-origin.test.ts`, 통합은 Docker 잠금을 잡고 `pnpm exec turbo run build --filter=@peaket/ticket-svc^...` 뒤 `pnpm --filter @peaket/ticket-svc test:integration test-int/scanner-f055.int.test.ts`, 앱은 `pnpm --filter @peaket/scanner exec node --test test/enrollment-link.test.ts`.

### 8. 실제 서버 연결(§8.6 4의 4)

- 서버 사이: `scanner-f055.int.test.ts`가 ticket-svc를 `start()`로 실제로 띄운다(PostgreSQL·Valkey 컨테이너, HTTP·관리·gRPC 포트). ops-svc 쪽은 `services/ops-svc/src/modules/scanner-devices/adapters/grpc-ticket-scanner-devices.ts`를 상대 경로로 가져와 실제 gRPC로 부른다(의존 선언 밖 가져오기: ops-svc를 고치면 ticket-svc도 타입 검사, CLAUDE.md). identity는 `CheckScannerSession`·`TerminateScannerSessions` 계약 모양 gRPC 대역 서버(답을 시험이 바꾼다, 멈출 수 있다). identity 실제 판정은 기존 `test-int/scanner.int.test.ts`의 identity 응용 층 가져오기가 본다.
- 화면: 콘솔 SCR-053 → ops-api → ops-svc → ticket gRPC, 스캐너 `/enroll#code=` → scanner-api → ticket-svc. 로컬 데모 무대(tools/local/demo)에서 브라우저로 본다(§10).

### 10. 브라우저 확인 대본(마지막 날 감독이 한 번, `peaket-browser-check`, 결과는 브라우저 확인 폴더의 GAT-170 이름 파일)

1. 로컬 데모 무대에서 관제 콘솔 `operator`로 SCR-053을 연다. [기기 등록]으로 이름·배정 파트너를 넣으면 등록 코드와 QR, '…KST까지 10분 동안 한 번 쓸 수 있습니다'가 보인다.
2. QR 주소(`…/enroll#code=…`)를 스캐너 탭에서 연다(`?live=1` 없이). 입력 칸에 코드가 들어 있고 주소창에 `#code`가 없다. 새로고침하면 칸이 비고(저장 안 함) 디자인 보드가 아니라 실제 등록 화면이다.
3. [기기 등록] → 로그인 화면(SCR-036). 콘솔 목록에 기기 키 등록 시각이 보인다. 같은 QR을 한 번 더 열어 등록하면 '등록 코드가 만료되었거나 이미 사용되었습니다'.
4. 휴대폰 화면(SCR-051)으로 승인 → 근무 준비(SCR-033)가 뜬다. 네트워크 탭에서 `scanner-api` 요청마다 `DPoP` 머리가 있고 사전 요청(OPTIONS)에 쿠키가 없다.
5. 콘솔에서 그 기기를 사유와 함께 [즉시 폐기] → 스캐너의 다음 요청(60초 변경분이나 새로고침)이 '폐기된 스캐너 기기입니다'로 끝나고 로그인 화면으로 간다.
6. 콘솔 화면 폭 1440·태블릿 폭에서 등록 코드·QR이 잘리지 않는다(d5 §7.11).

### 11. 자주 놓친 결함(docs/architecture.md §8.6 4, 시험·구현 지시문에 넣는다)

- 저장소 응답은 정확한 값까지(되살린 코드의 `PTTL`, 지표 값, `WWW-Authenticate`의 `error`). '성공'만 보지 않는다.
- 경계값 양쪽(`iat` ±300,000/±300,001ms, 캐시 4,999/5,000ms, 코드 만료 직전/만료). 시험 값은 정본에서 적고 코드 상수를 가져오지 않는다.
- 허용·거부 목록은 목록 밖 값마다(출처: 다른 사이트·없음·끝 `/`·대소문자·포트). 세 상태(유효·무효·확인 못 함)의 가운데(확인 못 함 = 503)를 꼭.
- 판정 함수만 말고 부르는 쪽이 결과를 쓰는지 바깥 경계에서(401 뒤 `scan_event` 행 0, 지표 1 오름).
- 장애 주입은 끊긴 사례가 실제로 있었는지 단언(대역 호출 수, 멈춘 서버).
- 시작 파일(`start.ts`)의 조립(지표 연결, 출처 환경 변수)은 시험 조립과 따로 띄워서 본다.
- 화면 저장값: 등록 코드는 저장소에 남지 않고, 실패 뒤에도 입력 칸 값은 남는다.

### 12. 남는 위험

- 업로드에서 출처 확인은 가드 뒤 처리기에서 하므로, 출처가 틀린 요청도 `jti`를 소모하고 세션 확인을 한 번 부른다. 저장은 안 된다. 순서가 중요하면 가드 옵션으로 옮긴다(이번엔 단순한 쪽을 골랐다).
- 서비스 워커 업로드가 같은 키를 쓰는지는 서비스 워커가 생기는 F-05-4에서야 본다.
