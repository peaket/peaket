# 작업 계획: W12-prf192(서비스 코드의 오류 이름·상태 코드·제목을 오류 목록에 맞춘다)

- **무엇**: 감독이 찾은 문제(2026-11-21)를 고친다. `develop` `de4d6a67`에서 공용 서버 패키지 시험 `PRF192_서비스 코드의 이름 붙은 오류는 모두 목록에 있고 상태 코드와 제목이 같다`가 `ops-svc invalid-query 422≠400`으로 실패한다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane4-prf`(가지 `feature/lane4-W12-prf192`, 출발점 `origin/develop` `de4d6a67`).
- **등급·차례**: C, 시험 먼저(버그 재현 시험 먼저, `docs/architecture.md` §8.6 5), ADR-0283 결정 2의 짧은 고리.
- **정본**: `docs/api/guidelines.md` §2 '`type`·상태 코드·`title`은 한 묶음이다'(한 오류 이름은 늘 같은 상태 코드와 제목, 같은 원인을 두 상태 코드로 내지 않는다), 오류 목록 `docs/api/openapi.yaml` 맨 위 `x-peaket-problem-types`(오류 이름마다 상태 코드와 제목을 적은 표).
- **급한 까닭**: `develop` CI는 `packages/platform`이 안 바뀌면 이 시험을 돌리지 않는다. 갈래 1 BAT-059가 platform을 고치므로 그쪽 게이트에서 빨갛게 된다.

## 계획

### 1. 범위와 바른 동작

1. **역할 변경 승인의 반려 사유가 공백뿐일 때(뜻 바꿈)**: `role-change-approvals.ts` 139줄은 `invalid-query` 422 '반려 사유가 필요합니다'를 낸다. 목록의 `invalid-query`는 400 '목록 조건이 올바르지 않습니다'(목록 조회 조건 오류)라 뜻이 다르다. `approval-reason-required` 422도 고르지 않는다. 그 이름은 FRAUD_ACTION 승인에서 선택 칸이 종류 규칙으로 필수가 되는 경우다(openapi 705·5567줄). 반려 경로(5569줄)는 본문 스키마가 `required: [reason]`이고, 빈 글자 `''`는 지금도 본문 검사에서 400으로 막힌다(`approvals.controller.ts` 11줄 `min(1)`, `payout-approval.test.ts` 182줄). 공백만 있는 값도 같은 원인이라 같은 400이어야 한다. 그래서 **`invalid-body` 400 '요청 본문이 올바르지 않습니다'**(목록 150줄)를 쓴다. 같은 서비스의 `event-cancellations.ts` 160줄, 계약의 판매 승인 반려 400 `invalid-body`(openapi 5665줄)도 같은 꼴이다.
2. **같은 반려 경로의 다른 두 종류**: `POST /v1/ops/approval-requests/{approvalId}/rejections`는 승인 종류에 따라 셋으로 갈린다(`approval-router.ts` 42~44줄). 지급 묶음(`payout-approvals.ts` 169줄)과 계약 조건 변경(`contract-approvals.ts` 191줄)도 공백 사유에 `invalid-query` 422를 낸다. 같은 경로·같은 입력이 종류마다 다르게 답하지 않게 둘 다 `invalid-body` 400으로 바꾼다. 이 둘은 위치 인자 꼴(`new XProblem('이름', 상태, '제목')`)이라 PRF192가 못 본다.
3. **계약 설명(구현 커밋 몫)**: 반려 경로(openapi 5569줄) 응답에는 `'200'`만 있다. `'400': { $ref: '#/components/responses/Problem', description: "본문 형식 오류. reason이 없거나 빈 글자면 about:blank, 앞뒤 공백을 빼면 비면 invalid-body(승인 종류와 상관없다)" }`를 더한다. 생성물이 바뀌므로 구현이 `pnpm --filter @peaket/contracts gen`·`pnpm --filter @peaket/api-client gen`을 돌려 함께 커밋한다. 목록 줄은 바꾸지 않는다.
4. **다른 뜻 바꿈 둘**:
   - `admin-accounts.ts` 63줄(관리 계정 역할 변경·삭제 등의 본문 사유 1~500자) `invalid-query` 400 → `invalid-body` 400과 목록 제목.
   - core-svc `request-sale-review.ts` 80·84·85줄(관제 판매 승인 목록의 상태 값·limit·커서) `invalid-body` 400 → `invalid-query` 400과 목록 제목. 경로 설명(openapi 6663줄 근처 '모르는 상태 값, limit 100 초과')은 이름을 적지 않아 그대로 둔다.
5. **제목만 다른 것(같은 뜻이라 목록 제목을 그대로 쓴다)**: PRF192가 상태 코드 다음에 보는 제목 대조에서 걸린다. grep으로 읽은 줄(2026-11-21):
   - ops-svc `admin-accounts.ts` 28·30·42·92·119·121·123·124·125·155·156·177·180·181·198·296, `role-change-approvals.ts` 19·136·137·147, `commands/inbound/commands.controller.ts` 23·24, `payouts/adapters/jwks-approval-verifier.ts` 33·42.
   - purchase-svc `inventory/inbound/internal-sale-open.controller.ts` 24·26, `refund/inbound/compensation.controller.ts` 62.
   - 자리마다 다른 말은 `ProblemError`의 `detail`(그 일에만 붙는 설명 칸)로 옮겨도 된다. 시험은 `detail`을 단언하지 않는다.
6. 끝나면 PRF192가 통과한다. 시험 파일 `packages/platform/test/problem-types.test.ts`는 고치지 않는다.

### 5. 범위 밖

- 위치 인자 꼴 오류의 어긋남: grep으로 120건 남짓(예 `grpc-identity-admin-accounts.ts` 20건, `contract-approvals.ts`의 `invalid()` 도우미가 `invalid-query` 422, 같은 파일 211줄 철회 사유), core-svc 리뷰·파트너사 모듈의 목록에 없는 이름(`review-invalid`·`contract-terms-invalid` 등). PRF192가 이 꼴을 읽지 않는다. 시험을 넓히고 고치는 것은 다른 묶음 몫으로 감독에게 넘긴다.
- 목록 제목이 쓰임보다 좁은 것: `admin-role-not-allowed` '이 역할로는 초대할 수 없습니다'(역할 변경·삭제에도 씀), `approval-self-not-allowed`·`approval-role-required`('승인'이라 적었지만 반려에도 씀). 목록 제목을 넓히는 것은 계약 결정이라 이번에 하지 않는다.
