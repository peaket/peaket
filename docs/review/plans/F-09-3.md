## 감독에게

막는 물음은 1 하나다. 나머지는 추천대로 계획에 적었다. 다르게 정하면 이 계획과 그 정본 줄을 고친다.

1. **[결정 요청] F-09-3의 장부 범위를 6개로 좁힌다.** 지금 행의 범위(`D-T30, D-T34, docs/data.md, docs/security/secrets-and-keys.md, docs/security/asvs/delivery.md`)는 81항목(자동 52·ID만 18·다른 단계 2·해당 없음 3·빈칸 6)이다. 문서 토큰 셋이 문서 전체의 판정 항목을 끌어오지만, 이 기능이 실제로 닿는 판정은 D-T30·D-T34 ①~③·ASVS 13.2.2·13.3.4다. 나머지 74개는 다른 기능(예: 13.1.1은 F-09-4, 15.2.3·16.4.3은 시험 산출물·감사 로그 분리)의 몫이고 장부에서 사라지지 않는다. 그래서 행의 범위를 `D-T30, D-T34, delivery:v5.0.0-13.2.2, delivery:v5.0.0-13.3.4`로 바꾼다(§2). `docs/architecture.md` §8.6 2의 "범위가 넓어 닿지 않는 항목이 들면 시작할 때 좁힌다"에 따른다.
2. **[확인] 산출물은 Terraform이 아니라 기계가 읽는 데이터 계층 기준이다.** F-09-1(스테이징 Terraform·MSK/NLB/CloudFront)은 providers lock 때문에 막혀 있고, F-09-4는 TLS·KMS·비밀 교체를 맡는다. 이 기능은 그 둘이 읽을 **원천**(`deploy/data/peaket-data.yaml`)과 검사기·생성 파일을 만든다. 그래서 AWS 계정 없이도 "Redis 3클러스터·Aurora 5·MSK 3·Schema Registry·PgBouncer·역할 기본값"이 코드로 검증된다. 실제 프로비저닝은 F-09-1·F-09-4 몫이다.
3. **[확인] D-T30·D-T34는 F-09-4와 겹친다.** 두 기능 행 모두에 들어 있다. 이 기능은 D-T30의 **정적 검사**(Pod Identity 역할에 MSK 권한 없음·MSK 전용 역할의 신뢰 정책·고정 세션 이름)와 D-T34의 **교대 인증 구성**(두 사용자·SCRAM `auth_file`·RELOAD·재시작·실패 지표)까지 한다. 실제 MSK 재인증, Aurora 실제 `pg_authid` 제약 확인, 교체 함수 3종·Secrets Manager·KMS는 F-09-4 몫이다. D-T34 ①~③의 실제 실행(Docker PostgreSQL·PgBouncer)은 이번 턴 `미실행`이고, 구현 차례에 Docker 잠금을 잡으면 한다.
4. **[확인] DDL 역할 기본값은 정본에 없다.** `docs/architecture.md:833`은 핫패스·일반·배치·릴레이 네 줄만 정한다. DDL 역할은 마이그레이션 실행기가 문장마다 `lock_timeout` 3초·`statement_timeout` 30초를 거는 것이 정본(`docs/devops.md:617~618`)이라, 역할 기본값은 안전망으로 `statement_timeout` 30초·`idle_in_transaction_session_timeout` 60초 [가정]을 둔다(추천 적용, 2026-11-27). 정본 표에 DDL 줄을 더하지 않고, 생성 파일에만 [가정]으로 적는다.
5. **[알림] 생성 파일은 저장소에 커밋한다.** `deploy/data/generated/` 아래 `pgbouncer.ini`·`schema-registry.properties`·`msk-configurations.yaml`·`redis-parameter-group.yaml`·`aurora-parameter-group.yaml`·`role-defaults.sql`·`topics.yaml`·`msk-iam.yaml`이다. 생성 파일은 `node tools/ci/data-platform.mjs --write`로만 고친다. 비밀 값은 넣지 않고, 사용자 목록은 `<SCRAM-SHA-256$…>` 자리 표시자만 둔다.
6. **[알림] 이번 턴은 Docker·kind·AWS를 쓰지 않았다.** 그래서 실제 Redis·Aurora·MSK·PgBouncer 연결과 D-T34 ①~③ 실행은 파일만 쓰고 `미실행`이다. 다음 구현·검증 차례에 Docker 잠금을 잡고 돌린다. 정적 시험은 YAML·생성 문자열·가짜 스펙만 본다.
7. **[알림] `roles-check.mjs`는 이번 정지점의 게이트가 아니다.** 리뷰·구현 커밋이 아직 없어 구성 실패(exit 1)가 정상이다. ADR-0373 결정 3이 막지 않는 종류지만, 차례가 아니므로 마지막 기록 커밋 뒤에 돌린다. 까닭은 `## 검증`에 적었다.

## 계획

### 1. 범위

- **P1 원천**: `deploy/data/peaket-data.yaml` 하나에 Redis·Aurora·MSK·Schema Registry·PgBouncer·역할·MSK IAM의 값을 적는다. 정본 값의 기계가 읽는 형태이고, 정확한 칸은 §5와 `data-platform.test.mjs`가 정한다.
- **P2 검사기·생성기**: `tools/ci/data-platform.mjs`가 원천을 검사(`--check`)하고 생성 파일을 다시 쓴다(`--write`). 내보내는 함수는 `loadDataSpec`·`validateData`·`render*` 아홉이다.
- **P3 Redis**: `queue`·`seat`·`session-cache` 세 클러스터, 노드 기반 클러스터 모드, 3 AZ, 전송·저장 암호화, RBAC(기본 사용자 끔), `maxmemory-policy=noeviction`, `latency-tracking`, 슬로 로그, 세션·캐시 모든 키 TTL, 메모리 70/85% [가정]·`Evictions > 0` 경보다.
- **P4 Aurora**: `purchase`·`payment`·`ticket`·`ops`·`shared` 다섯 클러스터, `rds.force_ssl=1`·`verify-full`, 진단 매개변수 다섯, PITR 35일·교차 리전 7일 [가정]·삭제 보호 [추천], 연결 예산 purchase 850·payment 404.
- **P5 MSK·Schema Registry**: 세 클러스터(6·3·3브로커), 거래·텔레메트리 RF 3·min ISR 2·`acks=all`·`unclean=false`·자동 생성 끔, 관측은 기본값, 보존 7일(탈퇴·조사 3일), Schema Registry 2복제 [가정]·PDB 1·`_schemas` 3·BACKWARD_TRANSITIVE·TopicRecordNameStrategy·`kafkastore.*`.
- **P6 PgBouncer·역할 기본값**: 1.26.1·transaction·`max_prepared_statements=200`·5/15/65초·600/3600초·SCRAM `auth_file`·`auth_query` 없음·TLS, 교대 사용자 둘·30일·목록 1분·앱 1시간 [가정]·30일 안 재시작·실패 SEV2 [가정]. 역할 기본값은 핫패스 1/10·일반 5/10·정비 60/60·릴레이 5/30·DDL 30/60 [가정]초와 정비 `work_mem=64MB`다.
- **P7 MSK IAM(D-T30)**: 워크로드마다 Pod Identity 역할과 MSK 전용 역할의 짝, 신뢰 정책은 그 워크로드의 Pod Identity 역할만, Pod Identity 역할에 `kafka-cluster:*` 없음, 고정 세션 이름, 역할을 못 맡으면 실패, Outbox 쓰기는 릴레이에만.
- **범위 밖(다른 기능)**: F-09-1(Terraform·스테이징 스택·MSK 실물), F-09-4(TLS 인증서·KMS·MSK 역할 실제 생성·교체 함수·Secrets Manager·CloudFront/WAF), F-09-2(실행기·역할 생성/GRANT·플래그), F-09-10(KEDA·Karpenter·Rollouts), F-09-8(kind). 이 기능은 역할을 만들지 않고 **기본값만** 정의한다.

### 8. 실패 시나리오와 완료의 정의

- **실패 시나리오**:
  - Redis: `volatile-lru`가 남아 키가 조용히 지워진다. 클러스터 하나가 단일 노드·TLS 끔·기본 사용자 켬이 된다.
  - Aurora: `rds.force_ssl`이 꺼져 평문이 열리거나, 삭제 보호가 꺼지거나, 백업이 35일보다 짧다.
  - MSK·Schema Registry: `unclean=true`로 받은 메시지가 빠지거나, 자동 토픽 생성으로 오타 토픽이 생기거나, 호환성이 BACKWARD가 아니라 소비자가 옛 스키마를 못 읽는다.
  - PgBouncer: `idle_transaction_timeout`·`query_timeout`이 역할 상한보다 짧아 정상 배치를 끊거나, `auth_query`를 써서 Aurora `pg_authid`를 읽지 못하거나, 교대 사용자가 하나뿐이라 교체 순간 옛 파드가 모두 거절된다.
  - IAM: Pod Identity 역할에 MSK 권한이 있어 기본 자격으로 붙거나, MSK 역할의 신뢰 정책이 다른 워크로드까지 믿거나, 요청 처리 파드에 Outbox 쓰기 권한이 있다.
  - 역할·생성: DDL 기본값이 너무 길어 잠금을 쥔 마이그레이션이 핫패스를 막거나, 생성 파일을 손으로 고쳐 원천과 어긋나거나, 생성 파일에 비밀번호·계정 ID가 들어간다.
- **완료의 정의(구현·기록 차례에 확인)**:
  1. `node --test tools/ci/data-platform.test.mjs` 통과(37개, D-T30 ①~⑤·D-T34 ①~③·ASVS 13.2.2·13.3.4·음성 일곱·생성 대조).
  2. `node tools/ci/data-platform.mjs check`가 0이고, 여덟/아홉 생성 파일이 원천과 같다.
  3. `node tools/ci/ledger.mjs --batch F-09-3 --require`가 항목 6·빈칸 0·ID만 0이다. D-T34 실제 실행 전에는 완료로 보고하지 않는다(아래 4).
  4. Docker 잠금을 잡고 `pnpm --filter @peaket/platform test:integration`(또는 새 통합 시험 전용 명령)으로 `secret-rotation.int.test.ts`의 D-T34 ①~③을 실행해 통과한다. 이 시험은 PostgreSQL 직접 인증으로 SCRAM 세대·옛 세대 거절을 보고, PgBouncer 컨테이너의 RELOAD 경로는 별도 시험으로 남긴다(그 시험 전에는 D-T34를 완전히 닫지 않는다). Docker를 못 쓰면 `미실행`과 까닭을 기록하고 통과로 세지 않는다.

### 9. 남는 위험·외부 자원

- 실제 Aurora의 `pg_authid` 제약(open-items 53번)은 Aurora를 띄워야 확인된다. 이 기능은 RDS와 같은 관리형 권한 모델이라는 설계를 따르고, 실제 확인은 F-09-4·선택 클라우드 보정 몫이다.
- 실제 MSK 재인증(ST-T14 ②)은 작은 MSK·EKS가 필요하다(ADR-0154). D-T30은 정적 검사까지다.
- Redis 메모리·노드 사양·샤드 수는 측정으로 확정한다. 이 기능은 정본의 [가정]을 그대로 두고 새 수치를 만들지 않는다.
- PgBouncer 풀 크기·파드 상한은 KEDA 최대 복제 수와 함께 정해진다(F-09-10·wbs 2.12.1). 이 기능은 예산 식만 두고 서비스 값은 바꾸지 않는다.
- DDL 역할 기본값 30/60초는 정본에 없어 [가정]이다. 실제 마이그레이션 시간을 재면 조정한다.
- 생성 파일을 CI에 잇는 일(`tools-check` 잡)은 다른 기능과 같은 파일을 만진다. 기록 차례에 한 줄만 더하고, 그전에는 손으로 `check`를 돌린다.
