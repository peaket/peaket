- **무엇**: 묶음을 시작할 때 계획 담당이 만든 작업 목록이다(docs/architecture.md §8.6 4의 1, ADR-0256 결정 10). 검토 기록이고 규범이 아니다. 정본 값은 옮겨 적지 않고 자리만 가리킨다. 정본과 다르면 정본이 이긴다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane2`, 가지 `wave/lane2-BAT-160-165`, 출발점 `origin/develop` `434cb126`(R-495). 웨이브 2 커밋은 R-497부터 쓴다(R-496은 갈래 1 몫). 2026-11-12 작성.
- **등급**: 묶음은 B다(docs/BUILD_ORDER.md:68). 검색은 공개 읽기이고 결제·좌석·권한을 바꾸지 않는다.
- **이 계획과 함께 정본에 쓴 것**: ADR-0268(검색 읽기 모델을 뷰로 두는 1차 구현과 순위 결정), docs/data.md `search_document` 칸, docs/security/asvs/catalog-review.md 16.5.2의 검색 응답 캐시 머리 위치, docs/BUILD_ORDER.md BAT-165 범위, docs/review/ledger-notes.md의 다른 단계·측정·사람 확인 줄.

## 1. 묶음 나누기와 BAT-160

**결정**: 웨이브 2에서 BAT-160(HOT-260·HOT-200)은 시작하지 않고 BAT-165(HOT-270·HOT-280)를 먼저 한다.

- **BAT-160이 막힌 까닭**: HOT-200은 새 `image-worker` 배포, S3 어댑터(격리·준비·공개 버킷), 악성 코드 검사기, 이미지 코덱 의존을 요구한다. 지금 `develop`에 `image-worker` 배포와 `@aws-sdk/client-s3`가 없고, 이 묶음의 싼 게이트 범위 밖에서 인프라를 새로 세워야 한다. HOT-260만 해도 묶음의 절반이라 BAT-160을 완료로 적지 않는다.
- **BAT-165를 고른 까닭**: 선행 HOT-171(공연 등록·회차)·HOT-180(검색 정규화 패키지)·HOT-312(검색 결과 화면)가 이미 `develop`에 있다. HOT-270의 검색 포트·읽기 모델·자동완성 사전과 HOT-280의 순위·쪽·0건 제안·관련 공연을 core-svc 안에서 끝낼 수 있다.
- **더 나눌 때**: 1차는 `search_document`를 뷰로 둔다. 공연 수가 늘어 뷰 스캔이 느려지면 materialized view·증분 동기화를 후속 묶음으로 나눈다(ADR-0268 되돌릴 조건).

## 3. 구현

1. **도메인**(`services/core-svc/src/modules/catalog/domain/search.ts`): `SearchDocument`·`SearchQuery`·`SearchOutcome`·`SearchSuggestions`, `SearchIndex` 포트. `searchDocuments`는 등급 → 판매 상태 → 관심도 → 이름 → ID 순으로 정렬하고, 장르·공연장·아티스트·기간·상태 필터, 20개씩 50쪽(1,000건 상한), 0건 `didYouMean`·`relaxedTotal`, 관련 공연(같은 아티스트 → 같은 공연장 → 다가오는 인기)을 만든다. `suggestDocuments`는 공연 5·아티스트 2·공연장 1 몫을 먼저 채우고 빈 몫을 다른 종류로 채운다.
2. **유스케이스**(`application/search.ts`): `SearchCatalog`. 검색은 매번 `SearchIndex.documents()`를 읽고, 자동완성 사전은 판(`version`)이 같고 10초 [가정] 안이면 메모리 사본을 쓴다.
3. **어댑터**: 메모리(`MemorySearchIndex`)는 `MemoryCatalogRepository`의 공연·회차·이미지·찜에서 문서를 만든다. PostgreSQL(`DrizzleSearchIndex`)은 `search_document` 뷰를 읽고 `search_version`의 판을 쓴다.
4. **마이그레이션**(`0009_search.sql`): `search_version`(한 줄)·`search_term`(자리) 표와 `search_document` 뷰. 뷰는 `production`·`event`·`place`·`artist`·`production_artist`·`search_alias`·`production_image`·`wish`를 모아 항상 지금 값을 보여 준다. 판매 승인 공연만 넣고 `SUSPENDED`는 뺀다. 판매 상태는 시각으로 `UPCOMING`·`ON_SALE`·`ENDED`를 만들고, `SOLD_OUT`은 purchase-svc `event_sale` 사본이 생길 때까지 만들지 않는다.
5. **HTTP**(`inbound/search.controller.ts`): `GET /v1/search`·`GET /v1/search/suggestions`. 인증 없음, 계약 스키마가 검색어·필터·쪽을 먼저 검사한다. `Cache-Control`에 `stale-if-error`를 단다.
6. **정규화 패키지**: `packages/search-normalize`가 `convertQwertyToHangul`을 내보내고 core-svc가 한/영 변환에 쓴다. `noConvert=true`면 변환하지 않으며, 변환으로 찾았으면 응답 `query.converted`에 원문과 바꾼 값을 싣는다.
7. **조립**: `catalog.module.ts`에 `SEARCH_INDEX` 제공자(운영 Drizzle·시험 메모리)와 `SearchController`를 더하고, `index.ts`가 새 공개 이름을 내보낸다.

### 2. 결정

1. **COV2-02(다회차 판매 상태)**: 0018은 판매 상태를 회차별 `EXISTS`로 고쳐 `cardSaleStatus`와 같은 규칙이고, 경계(`open_at <= now`, `starts_at − 24시간 > now`)도 메모리 `saleOf`와 같다. 통합 시험은 '지난 회차 + 오픈 전 회차' 한 경우뿐이고 이름에 장부 ID가 없다(`test-int/search-sale-status.int.test.ts`). **남은 결함**: 0018의 `representative_event_id`가 판매 중 회차를 오픈 시각 순, 지난 회차를 오래된 순으로 골라 ADR-0093 결정 8·`representativeEvent`(판매 중이면 판매 종료가 가장 이른 것, 지난 회차뿐이면 가장 최근에 공연한 것)와 어긋난다. 고침은 ADR-0271 결정 1, 시험은 아래 T-04.
2. **COV2-07(요청마다 전체 문서 읽기)**: 정본(docs/features/search.md §2.2·§2.3·§4.4·§7.1, docs/data.md:2813·2814)대로 표·후보 검색·증분 사전으로 간다(ADR-0271). 정본이 처음부터 정한 설계이고 ADR-0268이 'HOT-280 이후 바꾼다'고 적어 둔 길이라 방향 변경으로 보지 않았다. 검색을 메모리 사전에서 답하게 바꾸는 다른 길은 정본 §7.1·§7.2와 ASVS 2.4.1·16.3.3의 문장을 바꾸는 방향 변경이라 고르지 않았다(아래 11의 질문 1).
3. **작은 세부(추천 적용, 2026-11-16)**: 동기화 함수 한 자리와 부르는 자리 셋, 1분 정리 작업과 1시간 관심도, 원천 함수 `search_document_source_at`, 검색 전용 연결 묶음의 503·`no-store`·`search_pool_saturated`, CDN 경로 무효화 포트, `lc_ctype` 점검, 원본 404·`no-store`, 브라우저 거르기 함수를 `@peaket/search-normalize`로 옮기기. 모두 ADR-0271 결정 1~11에 적었다.
4. **세부 번호 나눔**: SR-T8 ①②③, SR-T11 ①②, SR-T13 ①②, SR-T15 ①②③(docs/features/search.md:299·302·304·306). 범위에서 뺀 것: SR-T8 ③ → BAT-620(LCH-090)·BAT-420(GAT-110), SR-T11 ② → BAT-070(HOT-450), SR-T13 ② → BAT-055(HOT-400), SR-T15 ③ → 미검증(AWS 계정 뒤). 기존 `SR-T11` 이름의 시험은 세부 번호가 없어 'ID만'이 되었다(아래 T-24).
5. **SR-T10·SR-T14**: notes는 '사람 확인'이었지만 정본 방법 칸은 화면 단위 시험·빌드 검사다(docs/features/search.md:301·305). 자동 시험으로 바꾸고 notes 줄을 지웠다. 브라우저 확인은 참고 증거로 웨이브 끝에 한 번 한다.

### 5. 공개 인터페이스

시험 담당은 아래 이름의 빈 뼈대(동작 없이 `Error('아직 없음')`을 던지는 함수)만 더한다. 이름·모양을 바꿔야 하면 구현 담당이 '시험 이의'에 적는다.

```ts
// domain/search.ts — 검색(질의 쪽)
export interface SearchIndex {
  /** 한 번의 검색. 후보만 읽는다(ADR-0271 결정 4). 연결 묶음이 넘치면 SearchUnavailable을 던진다 */
  search(q: SearchQuery): Promise<SearchOutcome>;
}
export class SearchUnavailable extends Error { readonly reason: 'pool-timeout' | 'statement-timeout' }

// 자동완성 사전(메모리)과 그 원천
export interface SearchTermRow { id: string; kind: 'PRODUCTION' | 'ARTIST' | 'PLACE'; targetId: string; displayName: string; aliasOf: string | null; norm: string; normNospace: string; jamo: string; chosung: string; updatedVersion: number }
export interface DictionarySnapshot {
  version: number;
  full: boolean;                 // 통째로 읽었는가
  documents: SearchDocument[];   // updated_version > since(통째면 전부)
  terms: SearchTermRow[];        // 같은 조건
  removals: { version: number; kind: 'DOCUMENT' | 'TERM'; targetId: string }[];
}
export interface SearchDictionarySource {
  /** 한 읽기 전용 REPEATABLE READ 트랜잭션에서 판을 먼저 읽는다. since가 null이면 통째로 */
  read(since: number | null): Promise<DictionarySnapshot>;
  version(): Promise<number>;
}
export declare class SuggestionDictionary {
  constructor(source: SearchDictionarySource, clock: Clock);
  refresh(): Promise<{ version: number; full: boolean; applied: number; removed: number }>;
  suggest(input: string): SearchSuggestions;   // DB를 부르지 않는다
  correct(input: string): string | null;       // didYouMean
  readonly version: number;
  readonly entries: number;
}

// 쓰기 쪽(같은 트랜잭션)
export interface SearchReadModelSync {
  sync(tx: DbTransaction, productionIds: readonly string[], at: Date): Promise<{ version: number; removed: string[] }>;
  syncTimed(at: Date, since: Date): Promise<{ version: number | null; productions: number }>; // 1분 정리
  recountInterest(at: Date): Promise<number>;   // 1시간
  purgeRemovals(at: Date): Promise<number>;      // 하루 지난 지운 표시
}
export const SEARCH_READ_MODEL_SYNC: unique symbol;

// 로그·품질
export function maskSearchQuery(normalized: string): string;
export function zeroResultQueries(lines: readonly { query: string; results: number; at: string }[], o: { weekStart: string }): { query: string; count: number }[];

// domain/media-ports.ts
export interface CdnInvalidation { invalidate(tags: string[]): Promise<void>; invalidatePaths(paths: string[]): Promise<{ requestId: string }> } // 2026-11-16 시험 뒤 바꿈(§12)

// packages/search-normalize(apps/web에서 옮김, 모양 그대로)
export function refineLocally<T>(last: LastAnswer<T> | undefined, q: string, label: (t: T) => string, limit?: number): T[] | undefined;
export function inputKind(q: string): 'chosung' | 'hangul' | 'roman';

// apps/web/src/widgets/app-shell/model/search-quality.ts
export function createSearchQuality(o: { send(path: string, body: string): Promise<void>; now(): number }): {
  resultsShown(zero: boolean): void; suggestShown(): void; suggestSelected(kind: 'PRODUCTION' | 'ARTIST' | 'PLACE', position: number): void;
  resultClick(position: number): void; requery(): void; flush(): Promise<void>;
};
```

1. 시험 담당: T-24(이름만) → 단위 T-12·T-13·T-16·T-18·T-22·T-23 → HTTP·단위 T-06~T-10·T-17·T-19(메모리) → 뼈대를 더하고 실패 확인 → D 시험 T-01~T-05·T-11·T-14·T-15·T-19(PostgreSQL)·T-25를 Docker 잠금 안에서 한 번에 → T-20·T-21. '실패 확인' 절에 명령·실패 수·까닭을 적는다.

### 12. 시험 뒤 정한 것(2026-11-16)

1. **DB 문자 분류는 `pg_database.datctype`으로 본다**(어긋난 점 3). PostgreSQL 16부터 읽기 전용 설정 값 `lc_ctype`이 없다. #### R165-1(높음): 이미 있는 DB 채우기와 내려가 있던 동안의 시각 경계

- **정함**: ADR-0271 결정 12. 서버가 뜰 때 주기 일을 걸기 전에 `reconcileAll(at)`을 한 번 부른다. 1분 정리와 같은 권고 잠금 안에서 원천과 표의 모든 공연을 500개 [가정]씩 끊어 동기화하고, 원천에 없는 표 줄은 지우며 지운 표시를 적는다. 잠금을 못 잡으면 건너뛴다. 1분 정리의 시각 창은 따라잡기를 시작한 시각에서 이어 가고, 정리가 성공했을 때만 앞으로 옮긴다. 마이그레이션은 계속 빈 표만 만든다.
- **공개 인터페이스(더함)**: `SearchReadModelSync.reconcileAll(at: Date): Promise<{ ran: boolean; productions: number; version: number | null }>`. `SearchReadModelTimers`의 시작 함수가 이것을 먼저 기다린 뒤 주기 일을 건다.
- **시험 담당 몫(D, `services/core-svc/test-int/search-read-model.int.test.ts`)**:
  1. `HOT-270 표 마이그레이션 전부터 승인돼 있던 공연은 서버가 뜰 때의 따라잡기 한 번으로 검색·자동완성에 나오고 어긋난 줄이 0이다(R165-1)`. 검색 표 마이그레이션 바로 앞까지 올린 DB에 승인된 공연 둘(아티스트·다른 이름 포함)과 승인 전 공연 하나를 SQL로 넣고, 검색 표 마이그레이션을 올린 뒤 `SearchReadModelTimers`(또는 서비스)를 띄운다. 단언: 검색 API와 사전 `suggest`에 승인된 둘이 나오고 승인 전 공연은 없다. `search_term` 줄의 정규화 칸이 `nameKeys` 값과 같다. 원천과 표의 어긋난 줄이 0이다. 띄우기 전에는 두 공연이 검색에 없었다는 것을 먼저 단언한다(대조군).
  2. `HOT-270 모든 파드가 내려가 있던 동안 오픈 시각이 지난 공연은 다시 뜰 때 판매 중으로 바뀐다(R165-1)`. 가짜 시계로 정리 주기를 세운 상태에서 `open_at`이 지나게 하고, 새 `SearchReadModelTimers`를 만들어 띄운다. 단언: 띄운 뒤 첫 정리 전에 `sale_status`가 `ON_SALE`이고 판이 1 이상 올랐다. 판매 종료 시각을 지난 경우(→ `ENDED`)도 같은 시험에 둔다.
  3. `HOT-270 두 파드가 함께 떠도 시작 따라잡기는 한 번만 돈다(R165-1)`. 연결 둘로 `reconcileAll`을 장벽(둘이 같은 자리에서 기다리게 하는 장치)에 맞춰 동시에 부른다. 단언: 정확히 하나가 `ran: true`, 다른 하나가 `ran: false`이고, 판은 끊음 수만큼만 올랐다.
  4. 단위(`services/core-svc/test/search-maintenance.test.ts`, 가짜 원천·가짜 시계): `HOT-270 1분 정리의 시각 창은 따라잡기 시작 시각에서 잇고, 정리가 실패하면 창을 앞으로 옮기지 않는다(R165-1)`. 단언: 첫 `syncTimed`의 `since`가 따라잡기 시작 시각, 실패한 다음 정리의 `since`가 실패 전과 같다.

#### R165-19(높음): 세션 권고 잠금이 PgBouncer 트랜잭션 풀링과 맞지 않음

- **정함**: ADR-0271 결정 12 '잠금과 임대'(추천 적용, 2026-11-16). §14 R165-14의 '따라잡기 전용 연결의 세션 권고 잠금'을 바꾼다. PgBouncer 예외는 만들지 않는다(정본 예외를 새로 만들지 않으므로 멈추지 않았다). 감독이 추천한 방향 그대로다. 다른 방식(따라잡기만 PgBouncer를 거치지 않는 정비 연결로 돌리기)은 ADR-0083 결정 4의 예외를 넓히는 일이라 고르지 않았다.
  - **열쇠 하나, 트랜잭션 잠금만**: 따라잡기 끊음·1분 정리·관심도 다시 세기·지운 표시 정리가 저마다 자기 트랜잭션 첫 문장에서 같은 열쇠의 트랜잭션 권고 잠금을 잡는다. 정리 셋은 `pg_try_advisory_xact_lock`(못 잡으면 그 차례를 건너뜀. 1분 정리는 `skipped: true`를 돌려주고 시각 창을 옮기지 않는다, R165-23), 따라잡기는 한 번 부름의 첫 끊음만 `pg_try_advisory_xact_lock`(못 잡으면 `ran: false`)이고 둘째 끊음부터 `SET LOCAL lock_timeout`(2초 [가정]) 안에서 `pg_advisory_xact_lock`(추천 적용, 2026-11-16, 리뷰 R165-24에서 구현에 맞춰 고침). 관심도·지운 표시 정리에 잠금이 없던 것(R165-9 ①)도 이로써 함께 풀린다.
  - **따라잡기 임대**: `search_version`의 새 칸 넷(`reconcile_owner`·`reconcile_lease_until`·`reconcile_started_at`·`reconcile_cursor`, data.md). 끊음마다 잠금을 잡은 뒤 '주인 없음·내가 주인·만료(DB `now()` 기준)' 가운데 하나일 때만 주인을 나로, 만료를 `now() + 60초` [가정]로 적고 그 끊음을 한다. 아니면 멈추고 `ran: false`. 끊음은 공연 ID 차례이고 커서를 같은 트랜잭션에 적는다. 넘겨받은 파드는 커서 뒤부터 잇는다. 마지막 끊음이 `reconciled_at`에 `reconcile_started_at`을 적고 임대 칸을 비운다.
- **공개 인터페이스(바꿈)**: `reconcileAll(at: Date, o?: { chunkSize?: number; owner?: string; leaseMs?: number }): Promise<{ ran: boolean; productions: number; version: number | null; chunks: number; resumedFrom: string | null }>`. `owner` 기본은 겹치지 않는 이름(호스트 이름 + 어댑터 인스턴스마다 새 UUID, 추천 적용, 2026-11-16, R165-24), `leaseMs` 기본 60,000 [가정](시험이 짧게 준다). 따라잡기 전용 연결(`release(true)` 처리 포함)은 없앤다.
- **PgBouncer 대역**: 이 저장소의 test-int에는 PgBouncer 컨테이너가 없다. 새 외부 이미지를 들이지 않고, 트랜잭션마다 다른 DB 연결을 주는 풀 대역(연결 둘 이상을 번갈아 내주는 `Database` 감싸개, 시험 받침)으로 트랜잭션 풀링을 흉내 낸다. 실제 PgBouncer 컨테이너 시험은 갈래 정리 목록 후보로 둔다.
- **시험 담당 몫**:
  1. 단위 `services/core-svc/test/search-read-model-locks.test.ts`(새 파일): `HOT-270 서비스 코드는 세션 권고 잠금 함수를 쓰지 않는다(트랜잭션 풀링, R165-19)`. `services/core-svc/src/` 아래 모든 `.ts`에서 `pg_advisory_lock(`·`pg_try_advisory_lock(`·`pg_advisory_unlock`·`pg_advisory_unlock_all`이 0번이고, `scripts/migrate.mjs`(PgBouncer를 거치지 않는 마이그레이션 잡)는 셈에서 뺀다. 대조군: 같은 검사가 `pg_try_advisory_xact_lock`은 찾는다(검사가 빈 결과로 통과하지 않게).
  2. D `services/core-svc/test-int/search-read-model.int.test.ts`: `HOT-270 트랜잭션마다 DB 연결이 바뀌어도 따라잡기는 끝까지 마치고 권고 잠금을 남기지 않는다(R165-19)`. 위 풀 대역(연결 둘을 번갈아 내줌)으로 공연 30개·`chunkSize` 10을 따라잡는다. 단언: 끊음 트랜잭션들이 실제로 서로 다른 `pg_backend_pid()`에서 돌았다(먼저 단언), `ran: true`, `chunks` 3, 끝난 뒤 `pg_locks`의 `locktype = 'advisory'` 줄이 0, 임대 칸 넷이 비고 `reconciled_at`이 적혔다, 원천과 표의 어긋난 줄 0. 바로 뒤 1분 정리가 `ran: true`다(잠금이 남지 않았다).
  3. D 같은 파일: `HOT-270 임대가 살아 있으면 다른 파드는 따라잡기를 하지 않고, 만료되면 넘겨받아 커서 뒤부터 잇는다(R165-19)`. 파드 A(`owner` 'a', `leaseMs` 1,500)가 첫 끊음 커밋 뒤 멈춘 채 돌아오지 않게 한다(죽은 파드 흉내). 단언: 그때 임대 주인 'a'·커서가 첫 끊음 마지막 공연 ID. 파드 B(`owner` 'b')가 만료 전(1,499ms 안)에 부르면 `ran: false`이고 임대·커서가 그대로. 만료 뒤에 부르면 `ran: true`, `resumedFrom`이 A의 커서, B가 동기화한 공연 수가 전체 − 첫 끊음 수, `reconciled_at`이 A의 `reconcile_started_at`, 임대 칸이 빈다. 만료 판정은 DB `now()`로 하므로 시험은 실제 시간을 기다리거나 `reconcile_lease_until`을 SQL로 지난 시각으로 바꿔 둘 다 본다.

     - §13 R165-1 ③(`두 파드가 함께 떠도 시작 따라잡기는 한 번만 돈다`): 잠금 대신 임대로 판정이 바뀌어도 단언(하나만 `ran: true`)은 그대로다. 세션 잠금 상태(`pg_locks`)를 보는 단언이 있으면 임대 칸을 보게 바꾼다.
     - 단위 `search-maintenance.test.ts`의 R165-14 다시 하기 시험은 그대로 둔다(임대가 살아 있으면 `ran: false`로 곧 돌아오는 경우를 하나 더: 주기에 `reconcileAll` 1번, `ran: false`, 다음 주기에도 다시 부른다).

#### W7L2-S3(중간·보안): 파트너 역할이 검색 표를 행 보안 없이 씀

  2. `[ASVS v5.0.0-8.4.1] 파트너 포스터 게시는 정의자 함수로 자기 공연의 검색 줄만 고치고 남의 공연은 권한 오류다(W7L2-S3)`. 테넌트 A 연결로 A 공연 포스터를 바꾸는 파트너 경로(HTTP 또는 어댑터)를 부르면 `search_document.poster_image_id`가 새 그림이고 판 +1(정확히 1), 원천과 어긋난 줄 0. 같은 연결로 `select search_sync_poster(<B 공연>)` → 권한 오류, B 줄과 판 그대로. 포스터가 그대로인 호출은 판이 그대로(바뀐 것 없으면 판 안 올림). 공개 전(검색 줄 없는) 공연은 아무것도 하지 않는다.

### 시험이 정한 모양(구현이 다르면 '시험 이의'에 적는다)

1. **관련 공연: 결과가 있는데 근거 공연이 없으면 인기 공연으로 채우지 않고 숨김(`relatedOf`)**: 정본과 맞다. search.md:213이 '남는 공연이 없으면 관련 공연 자리를 숨긴다'고 했고, 인기 공연은 '결과가 0건이면'(search.md:214, §5.5 4)뿐이다. 옛 코드가 인기 공연으로 채운 것이 정본과 어긋났었다. 함께 바뀐 '검색어 없는 목록은 결과가 있으면 관련 공연 없음'도 맞다. 정본 §6은 '맨 위 결과가 아티스트나 공연장으로 **맞았으면**'인데, 검색어가 없으면 맞은 이름이 없다. 다만 이 바깥 행동의 변화(관련 공연 자리가 비는 경우가 늘어남)는 커밋 메시지에만 있고 계획·ADR에는 적지 않았다. 남은 §6 차이는 R165-18에 적었다.
2. **오타 제안: 같은 거리면 가나다 → ID(`didYouMeanOf`)**: 정본에 어긋나지 않는다. search.md §5.5·§4.4(145줄)는 같은 거리일 때의 차례를 정하지 않았다. 그래서 두 어댑터가 이름 목록의 차례와 상관없이 같은 답을 내는 이 규칙은 빈칸을 채운 것이다. 다만 계획 §6 '정본에 없던 세부'처럼 정본(§5.5) 또는 ADR-0271에 옮겨 적어야 한다(R165-18). 거리 판정 자체가 §4.4의 규칙(초성 첫 글자가 같고 낱자 길이 ±2 안, 낱자 단위 편집 거리, 기준 '낱자 길이 ÷ 4, 최소 1')이 아니라 정규화 글의 거리 2 이하인 것은 이 묶음 전부터 있던 차이다(R165-18).

**구현 담당이 계획과 다르게 한 두 곳**

1. **이번 부름의 첫 끊음은 기다리지 않는 `pg_try_advisory_xact_lock`**: 받아들인다. 계획(ADR-0271 결정 12 '잠금과 임대' 둘째 줄)은 모든 따라잡기 끊음을 `lock_timeout` 안의 `pg_advisory_xact_lock`으로 정했다. 그 경우 함께 뜬 두 파드에서 뒤 파드가 잠금을 기다렸다가, 앞 파드가 한 끊음짜리 따라잡기를 마치고 임대를 비운 뒤 새로 시작해 두 번 돈다. 이 결함을 시험(R165-1 ③)이 잡았다. 첫 끊음만 시도로 바꿔도 '하나만 돈다'와 '다시 하기'(못 잡으면 다음 정리 주기에 또 부른다)가 지켜진다. 대가는 그 순간 다른 파드의 정리·관심도 트랜잭션이 돌고 있으면 시작 따라잡기가 1분 미뤄지는 것뿐이다. 다만 정본 문장이 코드와 다르므로 ADR-0271 결정 12와 계획 '### 15'를 '첫 끊음은 시도, 이어 가는 끊음은 `lock_timeout` 안에서 기다림'으로 고쳐야 한다(R165-24).
2. **`owner`를 프로세스마다가 아니라 어댑터마다 새 UUID**: 받아들인다. 정본(data.md `reconcile_owner`)은 '파드마다 겹치지 않는 이름'만 요구한다. 어댑터마다 이름이 다르면 더 잘게 나뉠 뿐이라 겹치지 않는다는 조건은 그대로다. 따라잡기를 부르는 것은 `main.ts`의 `SearchReadModelTimers`가 가진 어댑터 하나뿐이라, 같은 파드 안 두 어댑터가 서로의 임대를 기다리는 일도 지금은 없다. 계획 '### 15'의 '프로세스마다'라는 말만 고친다(R165-24).
