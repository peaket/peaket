## 감독에게

정하지 않고 올리는 것과, 이 계획이 정한 것을 알린다. **아래 1~7이 풀리기 전에는 구현을 시작하지 않는다.**

1. **BOT-152는 이 묶음으로 끝나지 않는다.** 확인한 것: ① OPS-260 줄은 미체크이나 명령 수명주기·2인 승인 코드는 BAT-420에서 develop에 들어왔고, 남은 것은 **위험 명령 재인증**과 dry-run 비교다(그 재인증을 BOT-140이 한다). ② identity 관리 계정 **초대 수락 경로**(`/v1/{partner,ops}/auth/invitation-*`)는 openapi 계약과 화면 목업만 있고 identity-svc 받는 층이 없다. ③ SCR-064 화면은 `apps/console-host/src/pages/accounts`에 목업 보드만 있고 API에 잇지 않았다. **안**: BAT-045는 BOT-152의 **서버 REST·세션 강제 종료·권한 변경 승인·감사**만 하고, 초대 수락 경로와 화면은 새 묶음 `BAT-046` 후보로 뺀다. 그래서 구현 커밋에서 BOT-152 줄을 '끝'으로 체크하지 않고 어디까지 했는지 적는다. 이 좁힘을 승인해 달라.
2. **BOT-140의 클라우드 자원은 빼고 클라우드 밖만 한다.** WAF 규칙·보안 그룹·CloudFront 관제 웹 ACL·VPN 출구·WAF 로그 탐지는 AWS 계정과 실제 IP 값이 없어 못 한다. 이 묶음은 **gw-ops 허용 IP(원본 확인 헤더가 맞을 때만 `CloudFront-Viewer-Address`를 본다)** 와 **위험 명령 재인증**만 한다. '탐지'는 허용 IP 거절 지표·경보와 CloudTrail/WAF 로그 자리만 정하고 실제 경보는 클라우드 계정 뒤로 남긴다. 이 좁힘을 승인해 달라.
3. **gw-ops 허용 IP의 구현 모양을 확인해 달라.** Envoy Gateway `SecurityPolicy.authorization.clientCIDRs`는 환경별 CIDR을 정적으로 적어야 하고 기존 라우트별 JWT 인가와 겹치면 어느 정책이 이기는지가 라우트마다 달라진다. **안**: 공통 Lua가 프록시 환경 값 `PEAKET_OPS_ALLOWED_IPS`(쉼표로 이은 IPv4 CIDR, 최대 32개)를 읽어 `CloudFront-Viewer-Address`를 견주고, 값이 없거나 틀리면 **모두 거절**한다(닫힌 쪽). local·ci는 시험 값(`127.0.0.0/8`, `203.0.113.0/24`)을 넣고, 운영 값은 소유자가 채운다. IPv6 허용 목록은 이 묶음에서 받지 않는다([가정], 필요하면 다음 묶음). 이 모양과 IPv4만 먼저 하는 것을 승인해 달라.
4. **BOT-161은 CI kind 야간 점검까지 하고, 출시 후보 데모 점검은 미룬다.** ZAP 공식 이미지를 판·다이제스트로 고정해(OPEN[46], 2026-11-16 R-651) `develop` 야간에 kind의 공개 입구(`www`·`api`·`partner`)를 기준선 점검하고, High 이상 0을 판정 도구로 막는다. `ops-api`·`scanner-api`는 허용 IP·기기 인증 뒤라 점검 대상에서 뺀다. 출시 후보 데모 점검은 데모 클러스터가 생긴 뒤 같은 워크플로를 `workflow_call`로 부르게만 두고 이 묶음에서는 돌리지 않는다. 그래서 BOT-161도 '끝'으로 체크하지 않는다. 이 좁힘을 승인해 달라.
5. **번호를 확인해 달라.** ADR은 **0321**(관리 인증 게이트웨이의 쿠키·출처·운영 IP), **0322**(관리 계정 REST·권한 변경 승인·세션 강제 종료), **0323**(DAST 기준선과 판정) 후보이고, 0324는 보안 게이트 경보를 ADR로 남길 때만 쓴다. 마이그레이션은 **ops 0019**(`approval_request`·`approval_vote`·`audit_chain(record_id, seq)` 인덱스), **identity 0035**(`admin_account_request.kind`에 `TERMINATE_SESSIONS` 추가)다. develop 최신은 ops 0016·identity 0034이고, BAT-615가 ops 0018을 쓴다(coord 21~24행의 번호를 옮긴다). 시험은 기존 ID(I-T46 ④⑤, I-T52 ①②③, I-T53 ②③⑤, I-T61 ①~④, AZ-T14 ①~⑦, C-T69)만 쓰고 새 ID를 만들지 않는다.
6. **범위 밖으로 빼는 것을 확인해 달라.** ① BOT-152 화면(SCR-064)과 관리 계정 초대 수락 경로 ② 관리 계정 관리 외의 일반 승인 업무(환불·지급·수사기관 자료 등) ③ AWS WAF·보안 그룹·CloudFront 웹 ACL·VPN 출구·WAF 로그 탐지 ④ auth-controls §2.1 C1·C2의 웹 ACL IP 속도 규칙과 게이트웨이 파드별 로그인 한도 ⑤ ZAP 전체 점검(Full Scan)·인증된 점검·외부 침투 시험 ⑥ 데모·운영 환경의 실제 점검. 이 여섯은 다른 묶음이나 소유자 몫으로 남긴다.
7. **크기**: BOT-132 0.75, BOT-140 1.0, BOT-152 1.5, BOT-161 1.0, 정본·게이트 0.25 = **4.5일 [가정]** 로 BUILD_ORDER의 4일을 0.5 넘는다. BOT-152의 권한 변경 승인(0.5)을 BAT-046으로 미루면 4.0일이다. 어느 쪽을 택할지 정해 달라.

## 계획

### 1. 범위

**하는 것**:

1. **BOT-132 관리 인증 게이트웨이 경로**: gw-partner·gw-ops의 로그인(`POST /v1/{partner,ops}/auth/sessions`)·갱신(`POST /v1/{partner,ops}/auth/access-tokens`)·로그아웃(`DELETE /v1/{partner,ops}/auth/sessions/me`)이 이미 라우트에 있고, identity가 주는 `Set-Cookie`를 그대로 돌려준다. 쿠키로 인증하는 쓰기의 `Origin`을 콘솔 출처와 대조하고(Envoy Gateway `csrf`), **gw-ops는 갱신 경로가 아니면 `__Host-peaket_ops_rt`를 안쪽으로 넘기지 않는다**. 파트너 리프레시 쿠키 `__Secure-peaket_partner_rt`도 같은 규칙으로 한 번 더 막는다(브라우저 Path 밖 전송에 기대지 않는 깊은 방어). 공통 Lua에 쿠키 이름·갱신 경로 설정을 더하고, `Cookie` 머리가 여럿이거나 값이 큰따옴표로 묶인 경우도 다룬다.
2. **BOT-140 gw-ops 허용 IP**: 공통 Lua가 `originVerify`가 맞은 요청에서만 `CloudFront-Viewer-Address`를 읽어 `PEAKET_OPS_ALLOWED_IPS`(IPv4 CIDR 목록)와 견준다. 헤더가 없거나 틀리거나 값이 없으면 403 Problem이고 백엔드에 닿지 않는다. 원본 확인 헤더가 없거나 틀린 직접 호출도 403이다(지금은 머리만 지우고 통과한다). 거절 수를 지표·로그로 남긴다.
3. **BOT-140 위험 명령 재인증**: `POST /v1/ops/commands`·`POST /v1/ops/commands/{id}/approvals`·`POST /v1/ops/commands/{id}/retries`가 정본이 정한 위험 명령(2인 승인 명령, 멈추는 쪽 명령 3·11, 명령 4의 2인 조건)에 `X-Reauth-Token`을 요구한다. 토큰은 `aud=ops`, 그 세션 `sid`, `act=OPS_COMMAND`, `factors`에 `passkey`가 있어야 하고 `jti`를 한 번만 쓴다. 없거나 틀리면 403 `reauth-required`, 확인기·jti 저장소 장애는 503 `reauth-unavailable`이고 명령 행·감사 기록을 쓰지 않는다.
4. **BOT-152 관제 관리 계정 REST(서버 몫)**: `GET·POST /v1/ops/admin-accounts`, `GET /v1/ops/admin-accounts/{id}`(ETag), `PUT …/role`(If-Match, commander 역할 부여·회수는 202 승인 업무), `POST …/invitation`(재초대), `POST …/removal`(삭제), `POST·DELETE …/designations*`, `DELETE …/sessions`·`…/sessions/{sessionId}`(ADMIN_FORCE), `GET …/permission-changes`, `GET /v1/ops/auth/sessions/me`를 ops-svc에 둔다. 역할·대상 조건·Problem 값은 openapi와 authz-matrix §6.1 그대로다.
5. **BOT-152 세션 강제 종료**: identity-svc가 `AdminSessionService.TerminateAdminSessions`를 구현한다. `request_id`로 멱등이고, 계정의 모든 세션 또는 하나를 끝내며, 끝낸 세션마다 `control.sessions-terminated(reason ADMIN_FORCE)`를 낸다. 다른 계정의 세션 ID는 404, 이미 끝난 세션은 `already_done`이다. 계정 상태는 바꾸지 않는다.
6. **BOT-152 권한 변경 승인**: commander가 되거나 commander에서 내려가는 역할 변경은 ops-svc가 `COMMANDER_ROLE_CHANGE` 승인 업무를 만들고 202로 답한다. 요청자가 아닌 commander가 `POST /v1/ops/approval-requests/{approvalId}/approvals`를 `act=APPROVAL`·패스키 재인증으로 승인하면, ops-svc가 `approval_id`를 실어 identity `ChangeAdminRole`을 부른다. 그 밖의 역할 변경은 200이다. 승인 업무의 첫 구현은 이 한 종류이고, 표·자식 표는 data.md `approval_request`·`approval_vote`를 따른다.
7. **BOT-152 감사·권한 변경 내역**: 초대·재초대·역할 변경·지정·지정 거두기·삭제·세션 강제 종료를 ops 감사 체인에 남긴다. 권한 부여·변경·말소 내역은 감사 체인에서 그 계정 기록을 최근 순으로 읽어 3년 보관을 전제로 준다(고시 제5조 제3항). 요청자·승인자는 관리 계정 ID와 역할로 싣고, 실패한 호출은 성공 내역에 넣지 않는다.
8. **BOT-161 DAST 기준선**: ZAP 공식 이미지를 판·다이제스트로 고정하고, 기준선 점검 결과 JSON을 SARIF로 바꿔 `tools/ci/scan-gate.mjs`가 High 이상(보안 등급 7.0 이상)을 막는다. 결과 파일이 없거나 비었거나 형식이 틀리면 막는다. `develop` 야간에 kind의 공개 입구를 점검하는 워크플로와 출시 후보가 부를 수 있는 `workflow_call` 자리를 만든다. 점검 대상은 `www`·`api`·`partner`이고 `ops-api`·`scanner-api`는 뺀다.
9. **BOT-161 보안 게이트 판정 검토**: SAST(CodeQL)·의존성(`pnpm audit`·`vuln-deadline`)·이미지(Trivy)·비밀(gitleaks) 게이트가 0.1.4의 판정과 맞는지 표로 대조하고, 예약 실행이 실패했을 때 아무도 모르는 구멍(정리 목록 BAT-202)을 SEV3 이슈로 남기는 길을 더한다. 승격 차단은 BAT-080의 승격 자동화가 이미 맡는다.
10. **정본·장부**: 구현·기록 커밋에서 `docs/security/auth-controls.md`(게이트웨이 출처 확인·쿠키 전달·운영 IP), `docs/features/identity.md`(§6 관리 계정 관리 구현 상태·§12), `docs/security/authz-matrix.md` §6.1 구현 상태, `docs/features/control-tower.md` §3·§4·§13(위험 명령 재인증), `docs/infra.md` §4.1·§9(gw-ops 허용 IP), `docs/devops.md` §3(DAST), ASVS 행, BUILD_ORDER 장부 범위, `docs/review/ledger-notes.md`를 고친다. 이 계획 커밋은 정본을 고치지 않는다.

**크기(어림, 모두 [가정])**: BOT-132 0.75, BOT-140 1.0, BOT-152 1.5, BOT-161 1.0, 정본·게이트 0.25 = **4.5일**. BUILD_ORDER의 4일을 0.5 넘는다. BOT-152의 권한 변경 승인(0.5)을 빼면 4.0일이다(감독에게 7).

**빼는 것과 까닭**:

- **BOT-152의 화면(SCR-064)과 관리 계정 초대 수락 경로**: 화면은 갈래 2 몫이고(`apps/console-host/src/pages/accounts`는 목업 보드만 있다), 초대 수락 경로는 identity-svc 받는 층이 없어 이 묶음에 넣으면 1일 이상 더 든다. 서버 REST는 초대 행을 만들 수 있고, 수락은 BAT-046 후보로 뺀다. BOT-152 줄은 '끝'으로 체크하지 않는다.
- **일반 승인 업무(환불·지급·수사기관 자료·부정 예매 조치)**: 이 묶음은 `COMMANDER_ROLE_CHANGE` 한 종류만 만든다. 나머지 종류는 각 기능 묶음(GAT-280·GAT-300·COMPLIANCE)이 맡는다.
- **AWS WAF·보안 그룹·CloudFront 관제 웹 ACL·VPN 출구·WAF 로그 탐지**: 클라우드 계정과 실제 IP 값이 없다. gw-ops 허용 IP의 값도 소유자가 채운다.
- **auth-controls §2.1 C1·C2의 웹 ACL IP 속도 규칙과 게이트웨이 파드별 로그인 한도**: WAF는 클라우드 계정 뒤이고, 게이트웨이 로컬 한도는 이 묶음의 정본 값이 아직 `[가정]`뿐이라 넣지 않는다. BOT-132는 출처 확인·쿠키 전달까지만 한다.
- **ZAP Full Scan·인증된 점검·외부 침투 시험**: 기준선 점검만 한다. 로그인 뒤 화면·결제 흐름은 인증 시험과 브라우저 확인이 필요해 별도다.
- **출시 후보 데모·운영 점검**: 데모 환경이 없다. 워크플로의 `workflow_call` 자리만 만들고 실제 실행은 데모가 생긴 뒤다.
- **화면·브라우저 확인**: 화면을 바꾸지 않는다. SCR-064 연결은 BAT-046 후보다.
- **실제 AWS 계정·클라우드 자원 생성**: 소유자 몫이다.

- **BOT-152**: identity `AdminAccountService`·`AdminDesignationService`는 구현돼 있고 `admin_account_request`로 `request_id` 멱등을 한다. `AdminSessionService`는 proto에만 있고 identity 받는 층이 없다. `GET /v1/ops/auth/sessions/me`는 openapi·게이트웨이 라우트만 있고 서비스 코드가 없다. ops-svc에는 관리 계정 모듈·승인 업무 모듈이 없다. `approval_request`는 data.md에만 있고 ops DB에 없다. `apps/console-host/src/pages/accounts`는 목업 보드다.

### 5. 공개 인터페이스(시험 담당이 기댄다. 이름은 구현이 이대로 쓴다)

- **게이트웨이 Lua 설정**(`filterContext`):
  - `requireOriginVerify: true`(gw-ops만), `opsAllowedIpsEnv: "PEAKET_OPS_ALLOWED_IPS"`, `refreshCookie: "__Host-peaket_ops_rt"`, `refreshPath: "/v1/ops/auth/access-tokens"`(gw-ops), `refreshCookie: "__Secure-peaket_partner_rt"`, `refreshPath: "/v1/partner/auth/access-tokens"`(gw-partner).
  - 환경 값 `PEAKET_OPS_ALLOWED_IPS`: 쉼표로 이은 IPv4 CIDR 1~32개. 빈 값·형식 오류는 모두 거절.
- **ops-svc HTTP**: openapi 그대로. 새 경로를 만들지 않는다. 응답 상태는 200·201·202·204·400·403·404·409·412·422·503이고, Problem `type`은 openapi 목록을 쓴다(`reauth-required`, `reauth-unavailable`, `self-target-forbidden`, `last-partner-admin`, `role-group-mismatch`, `commander-removal-needs-role-change`, `precondition-failed`, `admin-account-state-conflict`, `designation-conflict`, `designation-target-not-commander`, `designation-target-not-eligible`, `approval-self-not-allowed`, `approval-role-required`). 승인 대기 아님·만료는 openapi가 정한 409 Problem을 쓰고, 새 `type`을 만들지 않는다.
- **ops-svc 응용 층**:
  - `AdminAccounts.list/get/invite/changeRole/reinvite/remove/designate/revokeDesignation/terminateSessions/permissionChanges/mySession`.
  - `AdminReauth.verify(token, { sessionId, act })` → `{ accountId, factors }`, 실패는 `ReauthRequired`·`ReauthUnavailable`.
  - `Approvals.create/get/approve/reject` — `COMMANDER_ROLE_CHANGE`만.
- **identity gRPC**: `AdminSessionService.TerminateAdminSessions`(기존 proto). `request_id`는 ops 감사 기록 ID다.
- **도구 CLI**:
  - `node tools/ci/dast-gate.mjs --report <zap.json> --out <sarif> [--event <사건>]` → 종료 코드 0 통과, 1 막음.
  - `node tools/ci/scan-tools.mjs dast --target <url> --out <폴더>` → ZAP JSON. `PINS.zap.image/tag/digest`.
- **계약 변경 없음**: openapi·proto·생성물을 고치지 않는다. 시험은 기존 계약의 경로·헤더를 쓴다.

### 7. 구현 전 실패 확인(구현 전 트리에서 실패를 볼 수 있는 것과 없는 것)

- **진짜로 실패해야 하는 것(출발점 `19d132303`)**:
  - **I-T46 ⑤·BOT-140 허용 IP**: 지금 공통 Lua는 `Cookie`를 다시 쓰지 않고 허용 IP를 보지 않는다. kind에서 `rt`가 echo 대역에 그대로 닿고, 목록 밖 IP가 통과한다.
  - **I-T53 ②③⑤**: ops-svc 명령·관리 계정 경로가 재인증을 보지 않는다. 관리 계정 경로는 404다. 토큰 없이 명령을 만들면 지금 201이다.
  - **I-T61 ①~④**: `AdminSessionService`가 없어 실행할 수 없고, ops 경로도 404다. M10으로 실패를 본다.
  - **AZ-T14 ①~⑤·C-T69(ops)**: 관리 계정 REST가 없어 404다. M9·M11로 실패를 본다.
  - **BOT-161**: `dast-gate.mjs`·`dast-nightly.yml`·`PINS.zap`이 없어 실행조차 안 되고, `check-workflows`는 워크플로가 없어 실패한다.
- **처음부터 통과할 수 있는 것**: I-T46 ④·I-T52 ②(`csrf`가 이미 있다), I-T52 ③(Auth.js가 이미 없다), AZ-T14 ⑦(doc-check 규칙이 이미 있다), AZ-T14 ④·⑥·C-T69(identity가 이미 구현). 이 부류는 계획 §9의 M3·M4·M9로 한 번씩 실패를 본다.
- **실행조차 안 되는 것(세지 않음)**: I-T61·AZ-T14 ⑤·C-T69(ops)는 경로·gRPC가 없어 모듈을 읽지 못한다. 시험 담당은 구현 커밋에서 통과를 보고, §9의 해당 M으로 실패를 본다.
- **공용 함수는 develop에 있다**: `JwksApprovalVerifier`(ops-svc), `TokenVerifier.verifyReauth`(platform), `admin_account_request` 멱등, audit chain, gateway `edge()` 도우미. 함수가 없어 실행하지 못하는 시험은 없다.

### 11. 시험·구현 지시문에 넣을 '자주 놓친 결함'

docs/architecture.md §8.6 '자주 놓친 결함' 목록 전부를 지시문에 넣고, 이 묶음에서 특히:

- **쿠키는 정확한 값까지 본다**: `Cookie` 머리 여럿, 큰따옴표, 세미콜론 뒤 빈칸, 이름 대소문자, 헤더가 비었을 때. `rt`만 빠지고 `at`은 남는지, 갱신 경로에서는 둘 다 남는지.
- **출처는 세 상태**: `Origin`이 맞음·다름·없음. `null`·빈 값·다른 콘솔·끝 슬래시도 넣는다. 사전 요청과 실제 요청을 나눈다.
- **허용 목록은 경계 양쪽**: CIDR `/32`·`/0`·목록 밖, IPv6, 빈 값, 형식 오류, `CloudFront-Viewer-Address` 없음. 꾸민 `x-forwarded-for`로 통과하지 않는지.
- **재인증은 토큰의 모든 축**: `aud`·`act`·`sid`·`sub`·`exp`·`factors`·`jti`. 다른 세션 토큰, 만료, 재사용, 확인기 장애(503), 막힌 뒤 행·감사 0.
- **위험 명령의 범위**: 2인 명령·3·11·4의 2인 조건만 재인증. `LOG_LEVEL` 같은 비위험 명령은 그대로. 접수·승인·재시도 세 길을 모두 본다. 내부 사건 수신은 사용자 경로가 아니다.
- **관리 계정 REST의 답**: 남의 계정·없는 계정 같은 404, 자기 자신 403, 마지막 `partner_admin` 409, 판 불일치 412, 역할 묶음 422. viewer·CS 403. 이메일 가림.
- **감사와 실제 변경의 차례**: identity 호출 전 `REQUESTED`, 성공 뒤 `SUCCEEDED`, 실패 뒤 `FAILED`. 권한 변경 내역에 실패가 섞이지 않는지, 같은 `Idempotency-Key`에 감사가 두 번 안 쌓이는지.
- **세션 종료의 세 상태**: 전체·하나·이미 끝남. 다른 계정 세션 404, 세션 종료 사건 `ADMIN_FORCE`, 계정 상태 불변, 가드 401.
- **DAST 결과의 빈 값**: 결과 파일 없음·빈 파일·깨진 JSON·점검 흔적 없음은 통과가 아니다. High/Medium을 `riskcode`로 가르고 `riskdesc` 문자열을 파싱하지 않는다. 중복은 규칙·URL로 합친다. 보고서에 본문·쿠키·토큰 0.
- **고정 표**: 이미지 태그만 쓰지 않고 다이제스트를 쓴다. `latest` 거부. 미끼 점검이 High를 못 찾으면 대상 점검을 하지 않는다.
- **시작 파일 조립**: ops-svc `main.ts`의 관리 계정 gRPC·재인증·jti·감사, identity gRPC 서버 등록, gw-ops 프록시 환경 값. 시험 조립과 따로 띄워 본다.
- **시험 값이 코드 상수와 같으면 상수를 잘못 쓴 결함이 숨는다**: 승인 `due_at`·캐시 5초·Retry-After 5초·High 7.0은 정본 값으로 적고, 시험은 다른 값에서 시작한다.

## 감독 결정(2026-11-20)

1. **BOT-152는 서버 몫만 이 묶음에서 끝낸다.** ops 관리 계정 REST·identity `AdminSessionService`·`COMMANDER_ROLE_CHANGE` 승인·감사·권한 변경 내역까지 한다. 관리 계정 초대 수락 경로와 SCR-064 화면은 **BAT-046**으로 나누고, BOT-152 줄은 '끝'으로 체크하지 않는다.
2. **BOT-140의 AWS 자원은 뺀다.** WAF·보안 그룹·CloudFront 웹 ACL·VPN 출구·WAF 로그 탐지·CloudTrail 경보는 클라우드 계정 뒤로 남긴다. BOT-140은 위험 명령 재인증(`act=OPS_COMMAND`·패스키·jti)과 gw-ops 원본 확인·허용 IP까지다.
3. **gw-ops 허용 IP는 공통 Lua + `PEAKET_OPS_ALLOWED_IPS`(IPv4 CIDR)** 로 한다. 값이 없으면 모두 거절(닫힌 쪽). `SecurityPolicy.clientCIDRs`는 쓰지 않고, IPv6는 다음 묶음으로 미룬다. ADR 0321.
4. **BOT-161은 CI kind 야간 점검까지 한다.** `www`·`api`·`partner` 기준선, High 7.0 이상 차단, 예약 실패 SEV3 이슈. 출시 후보 데모·운영 실제 점검은 데모 환경 뒤로 미루고 BOT-161도 '끝'으로 체크하지 않는다.
5. **번호**: ADR **0321**(관리 인증 게이트웨이), **0322**(관리 계정 REST·승인·세션), **0323**(DAST), 보안 게이트 경보 ADR을 남길 때만 **0324**. 마이그레이션 **ops 0019**(BAT-615가 0018을 씀)·**identity 0035**. coord 21~24행을 이 번호로 고친다.
6. **범위 밖 확인**: SCR-064·초대 수락(BAT-046), 일반 승인 업무, AWS 자원, WAF·게이트웨이 로그인 한도, ZAP Full/인증 점검, 데모·운영 실제 점검.
7. **크기 4.5일**로 한다. 권한 변경 승인(0.5일)은 BOT-152의 핵심이라 BAT-046으로 미루지 않는다. OPS-260의 dry-run 비교는 BAT-465/OPS-260 잔여로 남기고, BOT-140은 위험 명령 재인증만 채운다.
