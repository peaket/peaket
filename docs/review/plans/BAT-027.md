# 묶음 계획 BAT-027(HOT-462, 핫패스 구간 계측)

- 무엇: BAT-026 진단이 남긴 K2 2,000/s p99 53.6ms(목표 50ms)와 웜 구간 놓침 12건의 원인을 코드 안 구간별로 가른다. 묶음은 갈래 1·구간 1, 등급 B, 단계 HOT-462, 0.5~1일 [가정], 장부 범위 `-`다.
- 만든 때: 2026-11-11, `origin/develop` `71ccbccb`에서 가지 `feature/BAT-027-hot-path-instrumentation`.
- 정본: [docs/verification.md](../../verification.md) §3.8~§3.10, [docs/observability.md](../../observability.md) §3·§8, [docs/PROGRESS.md](../../PROGRESS.md) 턴 규칙 '측정이 도는 동안', [BAT-026 보고서](../measurements/BAT-026-v1-bundle-diagnosis.md).
- 선행: BAT-026(R-470·R-471). CPU 4/replica K2 2,000/s는 p99 53.6ms·놓침 12·오류 0이었고, 합본 CPU는 12코어 중 최대 3.13코어·event loop p99 24.7ms로 자원 포화가 아니었다.

## 1. 질문

1. K2 인기 좌석 2,000/s의 p99 53.6ms 가운데 어느 구간(구매 세션 읽기·좌석맵·홀드 Lua·시도 기록·HTTP 앞 대기)이 가장 크게 기여하는가?
2. 409 경합 응답은 홀드 Lua·시도 기록·응답 생성 가운데 어디에서 시간을 쓰는가?
3. 웜 구간 놓침 12건은 대상 서비스 구간인가, 발생기 시작인가?
4. payment-svc 승인 실행기와 purchase-svc `payment_status` 롱 폴링, queue-svc 진입은 각각 어느 구간이 긴가? (이번 K2에는 결제·진입 부하가 없으므로 단위 시험으로 계측만 확인한다.)

## 2. 계측 설계

- 공용 `packages/platform/src/hot-path.ts`의 `HotPathMetrics`가 두 지표를 낸다.
  - `hot_path_stage_seconds{service, stage}`: 구간 시간 히스토그램(표준 지연 칸).
  - `hot_path_outcomes_total{service, outcome}`: 요청 하나의 최종 결과 카운터.
- 이름표는 `service`·`stage`·`outcome`의 고정 목록뿐이다. 계정·주문·좌석·회차 ID는 싣지 않는다(docs/observability.md §8).
- 계측은 동작을 바꾸지 않는다. 구간 시간은 주입 Clock이 아니라 `process.hrtime` 단조 시계로 재고, 지표가 던져도 요청을 막지 않는다. `HotPathMetrics`를 넘기지 않으면 원래 함수만 부른다.
- 구간:
  - purchase-svc `HoldSeats`: `hold.session`, `hold.seat_config`, `hold.seat_resolve`, `hold.replay`, `hold.lua`, `hold.attempts`, `hold.session_record`, `hold.total`.
  - purchase-svc `GetPaymentStatus`: `payment.status.read`, `payment.status.deposit_read`, `payment.status.wait`, `payment.status.total`.
  - payment-svc `PaymentConfirmRunner`: `payment.confirm.claim`, `read`, `mark`, `gateway`, `finish`, `reschedule`, `drop`, `release`.
  - queue-svc `EnterQueue`: `queue.entry.schedule`, `preempt`, `arrival`, `number`, `batch_record`, `record`, `batch_result`, `mirror`, `release`, `total`.
- 합본은 서비스마다 논리 이름(`purchase-svc`·`payment-svc`·`queue-svc`)을 `service` 이름표로 두어 관리 포트에서 합쳐도 구분된다.

## 3. 검증

- 단위 시험: `packages/platform/test/hot-path.test.ts`, purchase-svc `hold-seats.test.ts`·`get-payment-status.test.ts`, payment-svc `payment-confirm-runner.test.ts`, queue-svc `enter-queue-hot-path.test.ts`.
- 작은 틀린 구현 검사(변이)로 시험이 잡는지 본다.
  - 계측 결과 호출 제거: HoldSeats의 `hotPath.outcome(holdOutcomeOf(err))`를 빼면 409 outcome 시험이 실패해야 한다.
  - 구간 이름 바꾸기: `payment.status.read`를 `payment.status.total`로 바꾸면 read 구간 시험이 실패해야 한다.
- K2 2,000/s를 CPU 4/replica에서 **한 번** 다시 잰다. 같은 클러스터·같은 방법(사용자 1,000명, hot 1, keep, 예열 30초·본구간 60초, 발생기 4대)이다. `docker ps`로 다른 시험 컨테이너가 없는지 확인하고, 끝나면 발생기 파드를 정리하며 합본 CPU를 1/replica로 되돌린다.
- 결과는 `docs/review/measurements/BAT-027-hot-path-instrumentation.md`와 `docs/review/measurements/BAT-027/`에 남긴다. 원자료는 k6 summary·generator, Prometheus 구간 지표, crictl 자원 표본이다.

## 4. 판정

- 구간 지표의 평균·p99(또는 표준 칸 비율)와 `>50ms` 관측 수를 견줘 상위 기여 구간을 고른다.
- K2 홀드 경로는 HTTP 앞 대기(이벤트 루프·서버 큐)와 계측 구간의 합을 견준다. 구간 합이 p99보다 훨씬 작으면 남은 시간은 계측 밖(대기·응답)이다.
- 웜 구간 놓침은 본구간 놓침과 발생기별 시각·CPU를 함께 본다. 본구간 0이면 발생기 시작 문제로 적고 대상 p99 판정에 쓰지 않는다.
- 실패·무효를 통과로 세지 않는다. 이번에도 정본 목표(2,000/s·p99 50ms)는 바꾸지 않는다.
- 다음 최적화 배치는 상위 구간마다 무엇을 얼마나 줄일지, 예상 이득과 비용을 적어 제안한다. 이번 묶음에서는 동작을 고치지 않는다.

## 6. 예상과 위험

- 계측 구현·시험 2~3시간, 합본 이미지 빌드·배포 40분, K2 1회 10분, 분석·보고서 1~2시간. 합 0.5~1일 [가정].
- 위험: 계측 오버헤드가 p99를 조금 올릴 수 있다. 같은 조건의 BAT-026 CPU 4 값(53.6ms)과 비교하되, 계측 전후 차이를 함께 적는다. 계측 때문에 동작이 달라지면 되돌린다.
- 위험: 표준 히스토그램 칸이 50ms·100ms라 p99 53.6ms를 정밀하게 가르지 못한다. 평균·구간별 `>50ms` 관측 수와 HTTP 전체 지연을 함께 본다.
- 위험: 합본 이미지 재빌드가 길어지면 K2 한 번을 못 할 수 있다. 그때는 계측·단위 시험·변이 결과만 남기고 측정 실패를 보고한다.
