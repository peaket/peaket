## 3. 이번에 하는 것

차례: I-01(표·도메인) → I-02(업로드) → I-03(붙이기) → I-04(지우기·정리) → I-05(화면) → I-06(조치 규칙·상세 사진) → I-07(관제 패널) → I-08(문서·기록). 구현 담당은 시험 고정 뒤에 시작한다.

1. **I-01 `review_image` 표·도메인 규칙**(G-01·G-02, AC-01·AC-03):
   - 새 `review/domain/review-image.ts`: 사진 상태(`UPLOADED·SCANNING·READY·REJECTED·DELETED`), 거절 사유, 크기·화소·설명 상한, 파생본 이름 둘(`240.webp`, `1280.webp`), 키(`quarantine/review/{id}`, `staging/review/{id}/{name}`, `review/{id}/{name}`), 주소 함수(`{이미지 출처}/review/{id}/240.webp`·`/1280.webp`), `reviewImageSpecViolation(width,height)`(짧은 변 320 미만이면 `TOO_SMALL`, 긴 변 20,000·4,000만 화소 넘으면 `TOO_LARGE`), `normalizeReviewImageAlt`(NFC, 제어·양방향 제어 문자 제거, grapheme 100자), `reviewImageDerivativeKeys(id)`.

2. **I-02 업로드 유스케이스·컨트롤러**(G-03, AC-01·AC-02·AC-12):
   - `review/application/review-images.ts`: 한 장 받기 → 크기·형식 검사(415가 아니라 422 `UNSUPPORTED_TYPE`) → 계정당 시간당 30장 세기(429) → 격리 원본 쓰기 → `ImageProcessing.process({kind:'REVIEW_PHOTO'})`(데드라인은 공연 이미지와 같은 `processingBudget`) → 결과가 ACCEPTED이고 폭·높이·파생본 키가 정확하면 준비 위치 두 객체의 크기·WebP 앞부분을 확인해 공개 위치로 게시 → 원본·준비 위치 지우기 → `review_image` READY 행 넣기. 어느 단계가 실패해도 남긴 객체를 지우고, DB가 실패하면 공개 객체도 지운다.

3. **I-03 후기 저장·고치기의 사진 붙이기**(G-04, AC-03·AC-04):

   - `validateReviewWrite`가 images 3장·imageId UUID·alt를 검사한다(더 이상 `review-images-unavailable`을 던지지 않는다).

   - `cs-inbox/model/live.ts`에 `reviewIdOf(case)`, `reviewDetailOf(raw)`(모르는 칸·신고자·계정·주문 참조 버림, 사진 주소·설명·폭·높이), `reviewActionsFor(detail, role)`(cs_agent·cs_lead만, 공시로 가림→`RELEASE`, 보임→`TEMP_BLOCK`·`BLOCK`·`NO_ACTION`, 통보·같은 내용 가림→없음), `reviewModerationPlan(input, nowMs)`(사유 1~2,000, TEMP_BLOCK 위반 사유·끝 시각 30일 이내, BLOCK 위반 사유, RELEASE는 사유만)을 더한다. `FILTER_KINDS`에 `CONTENT_REPORT`·`RIGHTS_REQUEST`를 더한다.

## 4. 장부 범위

```text
C-T22, catalog-review:v5.0.0-1.3.3, catalog-review:v5.0.0-2.2.3, catalog-review:v5.0.0-2.3.2, catalog-review:v5.0.0-2.3.3, catalog-review:v5.0.0-2.4.1
```

- BUILD_ORDER F-07-10 줄의 장부 범위 그대로 6항목이다(문서 통째 여섯 → 이 기능에 닿는 항목). 상태 `동결`과 `frozen-local` 분류는 그대로다(ADR-0386). `node tools/ci/ledger.mjs --batch F-07-10`: 항목 6, 자동 시험 6, 빈칸 0, 등급 B 6. **기준 트리에서 이미 `--require`가 통과한다**(기존 시험이 이름표를 갖고 있다). 이번 시험은 그 이름표를 새 동작(사진·409)으로 채운다.
- **왜 이 6개인가**: `C-T22`는 통보로 가린 후기와 같은 내용의 새 후기를 저장할 때 바로 숨김(기존 시험 회귀), `1.3.3`은 후기 본문·사진 설명·신고 내용의 길이와 제어 문자(사진 설명 100자 추가), `2.2.3`은 사진이 같은 계정 READY인지·후기와 사진의 조합, `2.3.2`는 후기당 사진 3장·시간당 30장·신고 하루 10건, `2.3.3`은 후기 저장+사진 붙이기·신고 저장+즉시 가림·조치+신고 완료의 트랜잭션, `2.4.1`은 업로드·신고의 남용 제한이다.
- 장부에 넣지 않는 것: `8.2.3`·`14.2.6`(운영자 상세의 필드 가림은 이번에 시험하지만 F-07-10 장부 범위가 아니다. F-07-11 장부가 본다), `5.3.2`·`5.4.3`(사진 키·악성 코드는 이번에 시험하지만 장부 범위 밖, ASVS 표의 다른 행이 본다), `3.5.1`(X-Requested-With는 시험하지만 장부 범위 밖), 신고기관 링크(F-07-11).

- **신고 → CS 건**: `support` 모듈·`support.cases-requested` Outbox·ops-svc 소비자가 없어 신고가 CS 처리함 건을 만들지 않는다. I-07 패널은 `targetRef`가 후기 ID인 `CONTENT_REPORT`·`RIGHTS_REQUEST` 건이 생긴 뒤에 쓰는 화면이다. 건 생성은 F-06-5(동결)·후속 몫이다.
- **실제 브라우저**: SCR-016 사진 업로드·관제 패널은 실제 Chromium으로 누르지 않는다. 웨이브 끝 브라우저 확인(F-08-7)에서 본다.
- **멱등 키·닉네임·명령 9**: G-12~G-15로 남는다.
- **설명 길이**: 정본은 100자 [가정]이고 grapheme으로 센다. DB CHECK는 `char_length`(코드 포인트)라 이모지 결합 글자에서 서버 검사와 DB가 다를 수 있다. 서버 검사가 먼저라 DB는 최후 방어이고, 100 grapheme은 100 코드 포인트보다 짧거나 같다.
