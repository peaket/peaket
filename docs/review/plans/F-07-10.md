## 3. 이번에 하는 것

차례: I-01(표·도메인) → I-02(업로드) → I-03(붙이기) → I-04(지우기·정리) → I-05(화면) → I-06(조치 규칙·상세 사진) → I-07(관제 패널) → I-08(문서·기록). 구현 담당은 시험 고정 뒤에 시작한다.

1. **I-01 `review_image` 표·도메인 규칙**(G-01·G-02, AC-01·AC-03):
   - 새 `review/domain/review-image.ts`: 사진 상태(`UPLOADED·SCANNING·READY·REJECTED·DELETED`), 거절 사유, 크기·화소·설명 상한, 파생본 이름 둘(`240.webp`, `1280.webp`), 키(`quarantine/review/{id}`, `staging/review/{id}/{name}`, `review/{id}/{name}`), 주소 함수(`{이미지 출처}/review/{id}/240.webp`·`/1280.webp`), `reviewImageSpecViolation(width,height)`(짧은 변 320 미만이면 `TOO_SMALL`, 긴 변 20,000·4,000만 화소 넘으면 `TOO_LARGE`), `normalizeReviewImageAlt`(NFC, 제어·양방향 제어 문자 제거, grapheme 100자), `reviewImageDerivativeKeys(id)`.
   - core `0052_review_image.sql`: data.md §2의 칸 그대로. `status`·`reject_reason` CHECK, `alt_text` 100자, `sort` 0~2, `review_id`가 있으면 `attached_at`이 있고 없으면 `attached_at`이 NULL인 CHECK, `review_id`별 `sort` 유일(부분), `(account_id, created_at)` 색인, `(review_id)` 색인, 정리용 `(status, created_at)` 색인. `core_app`에 읽기·넣기·`alt_text`·`sort`·`review_id`·`attached_at`·`status`·`deleted_at` 고치기, `core_maintenance`에 읽기·행 지우기. 행 지우기는 팬 역할에 주지 않는다. `migrations/meta/_journal.json`에 idx 52·tag `0052_review_image`·0047보다 큰 `when`을 넣는다.
   - drizzle `reviewImage` 표와 `ReviewImageRecord`를 `review/domain/review-image.ts`에 둔다.
2. **I-02 업로드 유스케이스·컨트롤러**(G-03, AC-01·AC-02·AC-12):
   - `review/application/review-images.ts`: 한 장 받기 → 크기·형식 검사(415가 아니라 422 `UNSUPPORTED_TYPE`) → 계정당 시간당 30장 세기(429) → 격리 원본 쓰기 → `ImageProcessing.process({kind:'REVIEW_PHOTO'})`(데드라인은 공연 이미지와 같은 `processingBudget`) → 결과가 ACCEPTED이고 폭·높이·파생본 키가 정확하면 준비 위치 두 객체의 크기·WebP 앞부분을 확인해 공개 위치로 게시 → 원본·준비 위치 지우기 → `review_image` READY 행 넣기. 어느 단계가 실패해도 남긴 객체를 지우고, DB가 실패하면 공개 객체도 지운다.
   - `review/inbound/review-image.controller.ts`: `POST /v1/review-images`, `@AcceptMultipart`(10MB + 64KB 봉투, 팬 multipart 칸막이), `requireXRequestedWith`, 팬 역할. 응답은 계약 `ReviewImageUpload`.
   - `catalog`의 `ImageProcessing` 종류에 `'REVIEW_PHOTO'`를 더하고 gRPC 클라이언트가 `IMAGE_KIND_REVIEW_PHOTO`로 보낸다. `MemoryImageObjectStore`·`LocalFolderImageStore`의 키 정규식에 후기 경로를 더한다(서버가 만든 ID만 받는 규칙은 그대로).
3. **I-03 후기 저장·고치기의 사진 붙이기**(G-04, AC-03·AC-04):
   - `ReviewStore.insertReview(r, images?)`·`updateReview(id, patch, images?)`가 사진 연결을 같은 트랜잭션에서 한다. 사진마다 그 계정·READY·(미부착 또는 이 후기)를 잠그고 확인하며, `sort`를 0부터 매기고 `alt_text`·`attached_at`을 쓴다. 하나라도 틀리면 트랜잭션째 되돌린다.
   - `Reviews.list/get/summary/update/create`가 사진을 읽어 `ReviewView.images`에 싣는다. 목록은 `imagesByReviews(ids)` 한 번으로 모아 N+1을 피한다. 가린 후기(`status HIDDEN`)와 공시 자리는 사진을 싣지 않는다.
   - `validateReviewWrite`가 images 3장·imageId UUID·alt를 검사한다(더 이상 `review-images-unavailable`을 던지지 않는다).
4. **I-04 지우기·정리**(G-05·G-06, AC-05·AC-06):
   - `softDeleteReview`가 같은 트랜잭션에서 그 후기 사진을 `DELETED`·`deleted_at`으로 바꾸고 공개 키를 돌려준다. 유스케이스가 공개 객체를 지우고, 실패는 로그만 남긴다.
   - 탈퇴 파기(`purgeWithdrawnAccount`)·손으로 처리(`purgeHeldWithdrawal`)·이전 판 고치기(`purgeLegacyRows`)도 같은 트랜잭션에서 그 후기(또는 그 계정) 사진을 `DELETED`로 바꾼다.
   - `reviewMaintenanceTasks`에 `review-image-cleanup`(매일)을 더한다: `review_id IS NULL AND status='READY' AND created_at <= 지금−24시간`과 `status='DELETED'`인 행을 100개씩 잡아 공개 객체를 지운 뒤 행을 지운다. 객체 삭제가 실패한 행은 남겨 다음 날 다시 한다.
5. **I-05 SCR-016 사진 칸 실제 업로드**(G-07·G-08, AC-07·AC-13):
   - `ImageUploaderItem`에 `imageId?: string`을 더하고, `ImageUploader`에 `upload?: (file: File) => Promise<{ imageId: string }>`를 더한다. 파일을 고르면 항목을 `uploading`으로 두고 `upload`를 부르며, 응답 전에는 `scanning`, 성공하면 `ready`+`imageId`, 422면 `error`+까닭, 429·503·네트워크면 `error`+[다시 시도]다. `max`(3)와 설명 100자는 그대로다.
   - `ReviewModalsClient`가 `uploadReviewPhoto`를 만들어 `createReviewImage({file}, { headers: { 'X-Requested-With': 'XMLHttpRequest' } })`를 부르고, 422 `reason`을 d5 문구로 바꾼다. 문구·재시도 판정은 `entities/review/model.ts`의 `photoUploadFailure(reason)` 한 곳에 둔다(정본 d5 §5.16: `JPEG·PNG·WebP 사진만 올릴 수 있습니다`, `한 장에 10MB까지 올릴 수 있습니다`, `사진이 너무 작습니다. 짧은 변이 320px 이상인 사진을 올려 주세요`, `올리지 못했습니다. 다시 시도해 주세요`). 형식·크기·작음·악성 코드는 다시 시도해도 같으므로 `retryable:false`, 429·503·네트워크는 `retryable:true`다.
   - `WriteModal`이 사진 항목을 상태로 들고, 등록·고치기에서 `reviewImagePayload(items)`(READY+`imageId`만 순서대로 `{imageId, alt}`)를 보낸다. `canSubmitWrite(items)`가 false(올리는 중·오류·`imageId` 없음)면 오류 요약으로 막는다. 고치기 초기값은 `editing.photos`를 `imageId·caption`으로 되살린다. `entities/review/model.ts`의 `ReviewPhoto`에 `imageId`를 더하고 `mapReview`가 보존하며, `reviewImagePayload`·`photoAltText`도 여기에 둔다.
6. **I-06 운영자 조치 규칙·상세 사진**(G-09·G-10, AC-08~AC-10):
   - `Reviews.moderate`의 판정 차례는 ① 후기 없음 404 ② `RELEASE`인데 보이는 후기면 409 `review-not-hidden` ③ **가림 사유가 `SAME_CONTENT`뿐이면(법정 통보·불법 촬영물·공시 가림이 없으면)** `RELEASE`도 409 `review-not-moderation-target` ④ `NO_ACTION`·`BLOCK`인데 신고가 0건이면 409 `review-no-reports` ⑤ 같은 조치가 이미 적용돼 있으면 저장 없이 200 ⑥ 그 밖은 반영이다. **`TEMP_BLOCK`은 신고가 없어도 받는다**(정보통신망법 §44의3, POL-044 ③ "신고가 없어도 권리를 침해한다고 인정되면 임의로 할 수 있다"). `NOTICE`가 살아 있는 가림의 `RELEASE`는 기존 `review.http.test.ts` 회귀대로 200으로 두고, `FILMING_HOLD`의 `RELEASE`도 openapi 설명대로 200이다. `SAME_CONTENT`만 남은 가림은 법정 통보 경로(F-07-11)로 넘긴다. 판정은 저장소의 현재 값으로 하고, 저장은 지금처럼 한 트랜잭션이다.
   - `reportedReview`가 `imagesByReview`와 살아 있는 조치를 읽어 `images`·`takedownReason`을 싣는다. openapi `OpsReviewDetail.review`에 `images`(최대 3, `ReviewImage`)와 `takedownReason`(`NOTICE|SAME_CONTENT|RIGHTS_TEMP|POLICY|FILMING_HOLD`)을 더하고 `packages/contracts`·`packages/api-client` 생성물을 다시 만든다.
7. **I-07 관제 CS 처리함 후기 패널**(G-11, AC-08·AC-09·AC-11):
   - `cs-inbox/model/live.ts`에 `reviewIdOf(case)`, `reviewDetailOf(raw)`(모르는 칸·신고자·계정·주문 참조·팬 이름 버림, 사진 `imageId·url·thumbnailUrl·alt`, `takedownReason`·`notice` 보존), `reviewActionsFor(detail, role)`(cs_agent·cs_lead만: 보임+신고 있음→`NO_ACTION`·`TEMP_BLOCK`·`BLOCK`, 보임+신고 없음→`TEMP_BLOCK`, 공시(`RIGHTS_TEMP`/`POLICY`)·`FILMING_HOLD` 가림→`RELEASE`, `NOTICE`·`SAME_CONTENT` 가림→없음(법정 통보 경로)), `reviewModerationPlan(input, nowMs)`(사유 1~2,000, TEMP_BLOCK 위반 사유·끝 시각 30일 이내, BLOCK 위반 사유, RELEASE는 사유만), `reviewPanelFor(detail, role)`(사진 설명이 비면 `후기 사진 n/전체`, 신고 사유 이름·내용, 조치 목록)을 더한다. `FILTER_KINDS`에 `CONTENT_REPORT`·`RIGHTS_REQUEST`를 더한다.
   - `ConnectedPage`가 `CONTENT_REPORT`·`RIGHTS_REQUEST` 건에서 `reviewIdOf`가 후기 ID를 줄 때만 `getOpsReview`를 불러 `reviewPanelFor`로 본문·별점·상태·사진·신고 요약·조치를 그리고, `createOpsReviewModeration`으로 조치한 뒤 상세·목록을 다시 읽는다. 409·422는 까닭을 화면에 보인다. 사진은 72px `<img>`(alt는 사진 설명 또는 `후기 사진 n/전체`), 신고 내용은 글자 노드다.
8. **I-08 문서·기록**(구현 뒤): `docs/lanes/lane5.md` 진행 로그, BUILD_ORDER F-07-10 줄 비고(동결 로컬 범위·남은 몫), 이 파일 §7~§10. `data.md` §2 `review_image` 권한 표는 TR-06 반영으로 이미 고쳤고, openapi는 구현에서 두 칸을 더한다. POL-042·044·d5의 법정 문구는 바꾸지 않고 새 법정 문구를 만들지 않는다.
