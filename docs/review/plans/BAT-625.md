# 묶음 계획: BAT-625(LCH-100 정산 지급 승인 대조·정산 보류)

- **무엇**: 묶음을 시작할 때 만든 작업 목록이다(docs/architecture.md §8.6 4의 1, ADR-0256 결정 10). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane5`, 가지 `feature/lane5-BAT-625`, 출발점 `origin/develop` `2a48ecb47`(R-763). 2026-11-22 작성.
- **등급**: 묶음은 A다(docs/BUILD_ORDER.md BAT-625). 돈이 움직이는 지급 묶음 승인 경로를 고치고, 승인 위조·재사용·실패 원자성을 다룬다.
- **정본**: `docs/features/settlement.md` §5.1·§6·§13, `docs/security/asvs/settlement.md` V2·V8·V16, `docs/planning/03-policies-glossary.md` POL-038, ADR-0047, ADR-0123, W12-mesh 리뷰 RV-01(2026-11-22, 감독 결정으로 이 묶음에서 고친다), R-T23 ②.

## 1. 선행 확인과 이번 범위

**선행 확인(2026-11-22)**:
- payment-svc `settlements.ts`의 `approveBatch`는 받은 `approvalId`를 문자열로만 받아 `payout_batch.approval_id`에 적고 상태를 `APPROVED`로 바꾼다. ops-svc의 승인 기록을 읽지 않는다. 그래서 payment-svc REST 8080에 닿는 내부 신원(메시상 ops-svc·purchase-svc)과 공유 내부 토큰만 있으면, ops-svc의 2인 승인 없이 지급 묶음을 승인하고 이어서 실행할 수 있다(W12-mesh RV-01, 보안 높음).
- ops-svc의 지급 승인 기록은 `payout_approval` 표다(0009, BAT-610). `approval_request`·`approval_vote`는 계약 조건 변경·권한 변경이 쓰는 공통 승인 표이고, 두 모양을 합치는 일은 GAT-290에 남아 있다. 이 묶음은 `payout_approval`의 요청자·승인자·상태·금액·대상 배치를 정본으로 삼아 payment-svc가 대조하게 한다.
- ops-svc에는 지급 승인 한 건을 내부에 보여 주는 경로가 없다. payment-svc는 ops-svc가 부르는 쪽이고, 지금은 ops-svc REST 8080의 부르는 쪽에 payment-svc가 없다. 그래서 새 내부 경로와 포트 허용 표(원천 `deploy/platform/mesh/port-allow.yaml`)를 함께 고친다.
- 판매 중지(`SALE_SUSPENDED`) 정산 보류는 BAT-620 리뷰 RV-03이 LCH-100·BAT-625로 넘겼고, `ledger-notes.md`의 R-T23 ②도 `다른 단계`로 비켜 두었다. payment-svc에는 `HoldReason`과 재확정 갈래만 있고, 지급 묶음을 만들거나 실행할 때 판매 중지된 공연 회차를 빼는 코드는 없다.
- core-svc에는 회차 하나의 판매 승인 상태를 읽는 `GET /internal/v1/events/{eventId}/sale-review-scope`가 있다. 여러 회차를 한 번에 읽는 경로는 없어, 지급 묶음 하나에 든 회차 수만큼 부르지 않도록 묶음 조회 경로를 더한다.

**이번에 하는 것**:
1. **승인 ID 대조(보안 높음)**: payment-svc `approveBatch`가 ops-svc 내부 경로 `GET /internal/v1/payout-approvals/{approvalId}`로 승인 기록을 읽어 ① 종류 `PAYOUT_BATCH` ② 대상 `batchId`·`targetRef` ③ 결제사·상점·지급일 ④ 금액 ⑤ 통화 `KRW` ⑥ 정산서 건수 ⑦ 2인 승인·정족수(요청자≠승인자, 승인자 1명 이상) ⑧ 상태(`APPROVED`·`EXECUTING`만) ⑨ 승인 시각을 대조한다. 어긋나면 4xx로 거절하고 `payout_batch` 상태를 바꾸지 않는다. ops-svc가 5xx·시간 초과·응답 모양 위반이면 503이고 아무것도 바꾸지 않는다.
2. **재사용·멱등**: 같은 승인 ID로 같은 배치를 다시 승인하면 처음 결과를 그대로 돌려준다(ops-svc를 다시 부르지 않는다). 같은 승인 ID를 다른 배치에 쓰면 ops 기록의 `batchId`가 달라 409이고, payment DB에는 `payout_batch.approval_id` 부분 유일 인덱스를 더해 두 겹으로 막는다. 이미 다른 승인 ID로 승인된 배치도 409다.
3. **감사·실패 로그**: `payout_batch_audit`(payment 0025)에 배치·승인 ID·요청자·승인자·금액·통화·성공/거절·사유·시각을 남긴다. 성공은 배치 상태 저장과 같은 트랜잭션(CAS)에 쓰고, 거절은 상태를 바꾸지 않은 채 따로 남긴다. 서비스 로그에는 `payout_batch_approved`·`payout_batch_approval_rejected`를 구조화해 남기고 계좌번호·내부 토큰은 싣지 않는다.
4. **판매 중지 정산 보류(R-T23 ②)**: core-svc에 `GET /internal/v1/events/sale-suspensions?eventIds=…`(한 번에 100개)를 더하고, payment-svc가 지급 묶음을 만들 때 판매 중지된 회차의 정산서를 `HELD`·`SALE_SUSPENDED`로 빼고, 실행 직전에도 다시 확인해 하나라도 중지면 409로 멈춘다. 재확정은 증빙 플래그만 믿지 않고 core에 판매 재개를 다시 확인한다. core가 5xx·시간 초과면 503이고 묶음·정산서 상태를 바꾸지 않는다.
5. **문서·계약·정책**: ADR-0345(승인 기록 대조와 부르는 쪽 확인), ADR-0285 결정 9 표·되돌릴 조건, `docs/architecture.md` §5 포트 표, `docs/api/guidelines.md` 내부 HTTP 실패 표, `docs/features/settlement.md`, `docs/security/asvs/settlement.md`, BUILD_ORDER BAT-625 줄.

**이번에 하지 않는 것**:
- `payout_approval`을 `approval_request`·`approval_vote`로 합치는 일(GAT-290).
- 메시 L7 경로 정책(ADR-0285 대안 2). 이번 대조는 앱 층에서 하고, 경로 단위 거르기는 그대로 후속이다.
- SCR-049 정산 지급 화면, SCR-046 승인 업무 화면.
- 보증금·이행보증보험 징수·충당, 잔액 부족을 `HELD`로 남기는 증빙 흐름, KYC 예고·토스 셀러 조회(LCH-110·LCH-120).
- 판매 중지 시 이미 만든 예약지급을 결제사에서 취소하는 일(지금은 실행 직전 409로 멈춘다. 취소·재예약은 LCH-110).
- `payout_batch` 승인 뒤 정산서가 바뀌는 경합(A1·A2 감사 보고서의 묶음 결속)은 이 묶음에서 고치지 않는다.

## 2. 장부 범위

```text
J-T31, R-T23 ②
```

- BUILD_ORDER BAT-625 줄의 장부 범위를 이 묶음이 실제로 증명하는 시험 ID 둘로 바꾼다. 지금 그 칸은 문서 경로라 장부가 빈칸으로 센다.
- `J-T31`은 이번에 `docs/features/settlement.md` §13에 더하는 새 시험 ID다. 승인 기록 대조·4xx/503·멱등·재사용·감사를 덮는다.
- `R-T23 ②`는 `docs/review/ledger-notes.md`의 `다른 단계`(LCH-100·BAT-625)를 지우고 자동 시험으로 바꾼다. 판매 중지된 회차의 정산서 지급 보류·재개 뒤 재확정을 덮는다.
- `J-T3`(지급 묶음 2인 승인)은 ops-svc 시험이 이미 자동 시험으로 덮고 있어 이 묶음의 장부 범위에는 넣지 않는다. 다만 `approveBatch` 계약이 바뀌므로 ops-svc·payment-svc 기존 시험을 함께 고친다.
