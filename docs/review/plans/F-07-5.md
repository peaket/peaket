## 3. 이번에 하는 것

구현 담당 할 일은 열한 개다(I-01~I-11). 차례는 I-10(마이그레이션·토픽) → I-01 → I-02 → I-03 → I-04 → I-05 → I-06 → I-07 → I-08 → I-09 → I-11이다. 일수 [가정]: 구현 1.6일, 시험 0.6일, 리뷰·검증 0.3일, 합 2.5일.

1. **I-01 조건부 전이와 Outbox**(ADR-0368 결정 2·3): `SettlementStore`에 `transitionStatement(input)` 하나를 더한다. 입력은 정산서 ID, 출발 상태 목록, 도착 상태, 바꿀 칸(보류 사유·이의 기한·조정 합계·지급액·상계), 감사 레코드, 사건 목록(`SettlementEventValue[]`), 같은 트랜잭션에 넣을 행(이의·조정·미수금, 선택)이다. drizzle은 `UPDATE … WHERE id = $1 AND status = ANY($2)`가 0행이면 롤백하고 `false`를 돌려준다. 사건은 플랫폼 `writeOutbox`로 마지막 문장에 쓴다(토픽 `trade.settlements`, 키 = 파트너 ID, 값은 asyncapi `SettlementEvent` 칸 그대로, `eventKey`는 `sha256('<statementId>:<사건 종류>:<전이 감사 ID>')` 앞 16바이트 UUID 꼴). 응용 층은 `false`면 409 `settlement-state-conflict`다. `dispute`·`confirmDue`·`reconfirmStatement`·기각·조정 적용·묶음 때의 보류(`createPayoutBatch`의 `statementUpdates`·`applyStatementUpdates`)를 모두 이 길로 바꾸고, 정산서 상태를 바꾸는 `saveStatement` 호출을 응용 층에서 없앤다(지급 실행 쪽 `executeBatch`의 `SCHEDULED`·`PAID`는 LCH-110 몫이라 그대로 두되 출발 상태 `SCHEDULED`·`CONFIRMED` 조건만 건다). 메모리 저장소도 같은 의미로 만든다.
2. **I-02 계산 = 통지**(ADR-0368 결정 1·10): `calculateEventStatement`·`calculateProductStatement`는 늘 `CALCULATED`·보류 없음으로 레코드를 만든다. `insertStatement`는 같은 트랜잭션에서 `NOTIFIED`로 바꾸고 감사 `CALCULATED→NOTIFIED`(행위자 `system`, 사유 `calculated`)와 `STATEMENT_NOTIFIED`를 쓴다. 이의 기한은 I-03의 달력으로 통지 시각 + 2영업일이다. 확정(`confirmDue`·`reconfirmStatement`)은 지급액 0 이하면 `CARRIED_OVER`·`STATEMENT_CARRIED_OVER`로 끝내고, 0 아래면 `partner_receivable`(`NEGATIVE_STATEMENT`, 그 정산서의 결제사, 금액 = −지급액, `source_ref = negative-statement:{statementId}`, 회차)과 `RECEIVABLE_OPENED`를 같은 트랜잭션에 쓴다. `createPayoutBatch`의 `listConfirmed`는 지급액 0 이하를 담지 않는다.
3. **I-03 KST 공휴일 달력**(ADR-0368 결정 4): `domain/business-calendar.ts`에 KST 날짜 기준 `addBusinessDays(at, n, holidays)`를 두고 이의 기한(2영업일)·다시 알림(1영업일)에 쓴다. 공휴일은 `PEAKET_HOLIDAY_CALENDAR_FILE`(`start.ts`에서 읽음, purchase-svc `parseHolidayCalendar`와 같은 형식)이고 없으면 주말만 뺀다. 형식이 틀리면 시작하지 않는다. 지급일 계산(`payoutDate`)은 지금 함수를 그대로 쓴다.
4. **I-04 이의 받기와 CS 건**(ADR-0368 결정 5): `dispute`는 `NOTIFIED`이고 `now < disputeDueAt`일 때만 받는다(그 밖 409 `settlement-not-disputable`, 기한 시각 이후 409 `settlement-dispute-window-closed`). 이의 행·`DISPUTED`·감사·`STATEMENT_DISPUTED`를 I-01 한 트랜잭션으로 쓰고, 커밋 뒤 새 포트 `SettlementCaseNotice.openDispute({ disputeId, statementId, createdAt })`를 부른다. 어댑터 `adapters/http-cs-case-notice.ts`는 ops `POST /internal/v1/cs-cases`(본문 `{ eventKey: disputeId, kind: 'STATEMENT_DISPUTE', sourceId: statementId, category: 'SETTLEMENT', createdAt }`, 내부 토큰, 3초)를 부르고 2xx면 `statement_dispute.case_requested_at`을 채운다. 실패는 로그만 남기고 이의 응답은 201이다. ops-svc `ReceiveCaseRequested`의 `ACCEPTED`에 `STATEMENT_DISPUTE`를 더한다.
5. **I-05 기각**(ADR-0368 결정 6): payment 내부 `POST /internal/v1/settlements/statements/{statementId}/dispute-dismissal`(본문 `{ reason: 1~2,000자, actorId: uuid }`)이 열린 이의 하나(`result null`)를 `DISMISSED`·`resolution_note`·`resolved_by`·`resolved_at`으로 닫고 `DISPUTED → NOTIFIED`(기한 + 1영업일), `STATEMENT_NOTIFIED`(판본 그대로)를 한 트랜잭션에 쓴다. 옛 `…/disputes/{disputeId}/resolution` 경로와 `resolveDispute(…, 'ADJUSTED')`를 없앤다. `reconfirmStatement`의 `DISPUTED` 갈래도 없앤다(이의는 기각·조정으로만 푼다). ops-svc `POST /v1/ops/settlements/{statementId}/dispute-dismissal`(`@Roles(['cs_lead'])`, `no-store`, 본문 openapi 그대로)이 이 경로를 부르고 payment 4xx를 그대로, 5xx·시간 초과는 503으로 전한다. 감사(ops `audit`)에 행위자·정산서·사유 길이만 남긴다(사유 원문은 payment에만).
6. **I-06 수기 조정**(ADR-0368 결정 7·8·9):
   - payment: `domain/adjustment.ts`(사유 코드 8종, 이의 코드 다섯, 검사 함수), 표 `statement_adjustment`(I-10), 포트 `AdjustmentApprovalVerifier.verify(approvalId)`와 어댑터 `adapters/http-adjustment-approval-verifier.ts`(ops `GET /internal/v1/approval-requests/{approvalId}`, 3초, 응답 Zod 검사, 404는 `undefined`, 그 밖 실패는 503). 내부 경로 셋: `POST /internal/v1/settlements/statements/{statementId}/adjustments`(본문 `{ approvalId, amount, reasonCode, disputeId?, evidenceNote?, requestedBy }`, 같은 `approvalId` 재요청은 같은 행, 201), `POST /internal/v1/settlements/adjustments/{approvalId}/application`(200, 대조 뒤 적용, 재적용은 처음 결과), `POST /internal/v1/settlements/adjustments/{approvalId}/void`(반려, `PENDING`만 `VOID`). 검사·상태 규칙은 settlement §4.3 그대로다. 적용은 I-01 한 트랜잭션에서 정산서 행을 잠그고 출발 상태 `NOTIFIED`·`DISPUTED`·`CONFIRMED`를 조건으로 건다. `PENDING`이 7일 [가정] 지난 행은 일꾼이 `VOID`로 닫는다.
   - ops: `approvals` 모듈에 `SettlementAdjustmentApprovals`(계약 승인 `ContractApprovals`와 같은 모양, 표는 `approval_request`·`approval_vote`만, 마이그레이션 없음)를 둔다. 요청 `POST /v1/ops/settlements/{statementId}/adjustments`(`@Roles(['cs_lead'])`, `Idempotency-Key` 필수)는 승인 ID를 `sha256('settlement-adjustment:<accountId>:<key>')` 앞 16바이트 UUID 꼴로 정하고 → payment 등록 → `approval_request`(kind `SETTLEMENT_ADJUSTMENT`, `target_ref` = 정산서 ID, `amount`, `reason_code`, `reason_text` = 근거 메모 앞 200자 [가정], `required_approvals = 2`)를 넣어 202 `ApprovalRequest`를 준다. `ApprovalRouter`의 list·get·approve·reject가 이 종류를 나눈다. 승인은 요청자가 아닌 commander만, `X-Reauth-Token` act `APPROVAL`(기존 `ApprovalReauthVerifier`), 투표·상태 `EXECUTING`·감사를 한 트랜잭션에 쓴 뒤 payment 적용을 부르고 성공이면 `DONE`, 실패면 `FAILED`(같은 승인을 다시 부르면 다시 적용). 반려는 `REJECTED` 뒤 payment `void`. 보기는 요청자·commander만(그 밖 404, 계약 승인과 같다). 새 내부 경로 `GET /internal/v1/approval-requests/{approvalId}`(`InternalTokenGuard`, `no-store`)는 ADR-0368 결정 8의 사실만 싣는다.
7. **I-07 일꾼**(ADR-0368 결정 12): `SettlementDueWorker`의 30분 tick마다(06시 조건 없이) `confirmDueStatements`, CS 건 다시 보내기(한 번에 50건 [가정]), 오래된 `PENDING` 조정 닫기를 돈다. 06시 정기 tick은 지금처럼 회차 계산을 하고, 그날이 그 주의 첫 영업일(I-03 달력)이면 지난주 월~일(KST)로 `calculateProduct`를 부른다. 상품 원천이 없으면 건너뛰고 로그만 남긴다. 리더일 때만 돈다.
8. **I-08 모두 보류된 묶음**(ADR-0368 결정 11): `createPayoutBatch`에서 `included.length === 0`이면 409를 던지기 전에 `statementUpdates`의 보류를 I-01 조건부 전이(출발 `CONFIRMED`)로 저장한다. 잔액 부족 `HELD`(BAT-630)도 같은 길로 바꾼다.
9. **I-09 테넌트 격리 로그**(J-T10): 파트너 정산서 목록·상품 정산서·이의에서 남의 정산서 ID(다른 `promoter_id`)면 404이고, `SettlementApprovalLog`와 같은 어댑터에 `settlement_authz_denied`(파트너 ID·계정 ID·정산서 ID·동작, 정산서 금액·계좌 없음) 보안 로그 한 줄을 남긴다. 없는 ID와 남의 ID의 응답 본문은 같다.
10. **I-10 마이그레이션·토픽**: payment `0027_settlement_adjustment_dispute.sql`(아래 §5)과 `meta/_journal.json`·`0027_snapshot.json`(drizzle-kit 생성). `tools/local/v1-objects.mjs`·`tools/local/demo-objects.mjs`의 Kafka 토픽 목록에 `trade.settlements`(파티션·보존은 `trade.payments`와 같게 [가정])를 더하고 각자 `*.test.mjs`를 맞춘다. 토픽이 없는 무대에서 릴레이가 `trade.payments`까지 멈추지 않는지 확인한다.
11. **I-11 문서**: 구현 뒤 settlement §4.5 '구현 상태'에 한 줄, `docs/security/asvs/settlement.md` 해당 행 구현 위치, BUILD_ORDER LCH-100 단계 줄의 '일부 구현'을 기록 커밋에서 고친다(기록 담당). 정본 규칙(§4.2·§4.3·§13, 03 §2.12, data.md, guidelines §8.1, architecture §3.2, ADR-0368)은 이 계획 커밋에서 이미 썼다.

## 4. 장부 범위

```text
J-T31, R-T23 ②, J-T1, J-T2, J-T10, J-T12, J-T35, J-T36
```

- BUILD_ORDER F-07-5 줄의 장부 범위와 완료 정의의 판정 목록을 이 계획 커밋에서 위처럼 바꿨다. `J-T31`·`R-T23 ②`는 BAT-625가 자동 시험으로 덮었고 이번에는 회귀로 본다.
- `J-T1`·`J-T2`·`J-T10`·`J-T12`는 지금 장부에서 '빈칸'이고 F-07-7의 문서 경로 범위(`docs/features/settlement.md`)에만 걸려 있었다. 이 기능의 통과 기준(계산·이의·확정·조정)에 걸리므로 여기서 닫는다.
- `J-T35`·`J-T36`은 이번에 settlement §13에 더한 새 시험 ID다(2026-11-23 `origin/develop`의 마지막은 J-T34, docs/lanes/coord.md '정본 시험 ID' 규칙). 세부 번호는 '연결: …' 앞에 두었다.
- 장부에 넣지 않는 것: `J-T11`·`J-T23`(F-07-8로, Q-01·Q-02), `J-T7`(F-07-6), `J-T27`(CS 처리함 화면, GAT-110 후속). ASVS 행은 이미 자동 시험이라 범위에 넣지 않고, 새 시험 이름에 `[ASVS v5.0.0-2.3.1]`·`[ASVS v5.0.0-2.3.3]`·`[ASVS v5.0.0-2.3.4]`·`[ASVS v5.0.0-8.2.1]` 태그만 단다.

- 조건부 전이: `transitionStatements`는 출발 상태·기한(`>`·`<=`)·조정 합계·상계·묶음 없음 조건을 `UPDATE … WHERE`에 걸고, 이의 넣기·이의 닫기(`result is null`)·조정 `PENDING→APPLIED`·미수금(부분 유일 + `on conflict do nothing`, 그때 `RECEIVABLE_OPENED`를 뺌)·감사·Outbox를 한 트랜잭션에 쓴다. 0행이면 롤백하고 `false`(409)다. 묶음 만들기의 보류·상계도 출발 `CONFIRMED`·묶음 없음 조건이다. 이의(`now < due`)와 자동 확정(`due <= now`)의 경계가 겹치지 않는다.

- 영업일: KST 날짜로 다음 날부터 주말·공휴일을 뺀다(금 06:00 + 2 = 화 06:00, 토 08:00 + 1 = 월 08:00). 지급일 계산은 바꾸지 않았다. 틀린 공휴일 파일이면 듣기 전에 시작에 실패한다.

## 8.1 리뷰 반영 계획

계획 담당 `lane5-f075-plan`(2026-11-23). 리뷰 커밋 `bbd7478f1`의 §8.2 지적을 나눈다. 차례는 정방향이다: 이 계획(정본 고침 포함) → review-fix 담당이 코드를 고침 → 시험 담당이 아래 재현 시험을 쓰고 **review-fix 전 트리(`bbd7478f1`)에서 실패**를 본 뒤 고친 트리에서 통과를 본다 → 리뷰 담당이 고친 곳만 다시 본다. review-fix 담당은 시험 파일을 고치지 않는다.

**RV-01 판단(계획 담당이 코드로 확인)**: 리뷰가 맞다. 정본 §4.1은 판매 대금을 '그 회차·결제사로 승인된 결제 금액의 합'으로 두고 '취소·환불은 여기서 빼지 않고 환급으로 따로 센다'고 적었다. 코드 `services/payment-svc/src/modules/settlement/domain/settlement.ts` 366~367행은 `CANCELED`의 판매 대금을 0(`grossOf`), 환급을 원금 전액(`refundOf`)으로 세어 같은 돈을 두 번 뺀다. 승인 2,800만 + 승인 뒤 전액 취소 200만 회차에서 정본은 판매 대금 3,000만·환급 200만·지급 2,492만(J-T1 예)인데 코드는 판매 대금 2,800만·환급 200만·수수료 260만·부가세 26만·지급 2,314만을 낸다(리뷰 표의 3,000만 + 200만 예도 같은 꼴로 178만 덜 준다). 이 식은 R-613(A1-H3 고침)이 '승인된 적 없이 대사가 닫은 취소'를 막으려다 승인 뒤 취소까지 0으로 만든 것이다. A1-H3의 원래 경우는 정본상 '승인된 결제'가 아니므로 판매 대금·환급 양쪽에서 빼는 것이 맞다. 정본 §4.1에 이 둘을 가르는 줄과 J-T1의 섞인 예를 이 커밋에서 더했다. 상품 정산서(`calculateProductStatement`)는 항목의 결제 금액을 판매 대금, `refundedAmount`를 환급으로 따로 세어 같은 꼴의 이중 차감은 없다. 다만 core 원천이 정산 기준일 전 전액 환급 항목을 넘기지 않는지(정본 §4.5 '판매·환급 모두 빠진다')는 review-fix가 core `GET /internal/v1/shop/product-settlement-items` 질의에서 확인한다.

## 브라우저 확인(기능 끝에 감독)

SCR-049(BAT-630 화면, `apps/console-host/src/pages/settlements`, 경로 `/settlements`)를 실제 서버로 본다. 이번 기능은 화면을 바꾸지 않지만, 정산서가 계산 때 `NOTIFIED`이고 묶음 때 보류가 저장되도록 바뀌어 SCR-049의 목록·보류 표시에 닿는다.

- **실제 서버(기본)**: 로컬 데모 무대(`tools/local/README.md` '로컬 데모 무대', 클러스터 `lane4-demo`)를 이 가지에서 쓴다. ① Docker 잠금을 잡고 `node tools/local/demo-images.mjs --build`로 이미지를 만든다. `bundle`(payment-svc 포함)과 `ops-svc` 이미지는 기존 것을 다시 쓰므로 이 가지에서 다시 빌드해야 한다(`node tools/local/cluster.mjs image` 또는 데모 이미지 계획의 재빌드). ② `node tools/local/cluster.mjs demo` → `node tools/local/cluster.mjs demo-seed --apply`. ③ hosts에 `127.0.0.1 console.peaket.example ops-api.peaket.example`(README 표)를 두고 `https://console.peaket.example:18444/settlements`를 연다. ④ 로그인 값은 `node tools/local/demo-auth.mjs admin <키>`로 받는다: commander `sujin`·`second-commander`, operator `minho`, viewer `seoyeon`, cs_agent `daeun`, cs_lead `jun`(`deploy/envs/demo/seed/base.yaml`). ⑤ 정산서 자료: 데모 시나리오 S1(`node tools/local/demo.mjs all --scenarios S1 --keep`)로 결제 한 건을 만든 뒤, bundle 파드 안에서 내부 토큰으로 `POST /internal/v1/settlements/event-calculations`(그 회차, `eventEndsAt`)를 부른다. KYC·정산 계좌와 이의 기한 당기기는 공개 API가 없어 로컬 데모 전용 예외로 SQL을 쓴다(통합 시험 `settlement.int.test.ts`와 같은 방식, 결과 문서에 예외로 적는다). ⑥ 볼 것: 지급일 탭·묶음 카드(키보드로도), operator 확인 요청 → KYC 미확인이면 409와 `HELD` 목록, commander 승인 버튼은 요청자 본인에게 없음, viewer 읽기만, CS 두 역할 메뉴·경로 차단, 계좌 끝 4자리만. 결과는 브라우저 확인 폴더(`docs/review/browser-check/`)의 `F-07-5.md`에 남긴다(스킬 `peaket-browser-check`).
- **가짜 API는 실제 서버 확인이 아니다**: `PEAKET_OPS_API_ORIGIN`을 저장소 밖 가짜 ops API로 잇는 방법(`docs/review/browser-check/R-568.md`·`GAT-310.md`)은 화면 배선만 본다. 데모 무대를 못 올리면(응용 프로그램 제어·Docker 잠금) 그 사실과 까닭을 결과 문서에 적고 '실제 서버 미확인'으로 남긴다.

- **Q-01**: LCH-100 단계 줄에 붙은 ADR-0197 결정 2의 뒤 몫('계산 뒤에 끝난 FRAUD 환급은 §7 미수금')을 이 기능에서 닫지 않고 F-07-8(GAT-130 '정산 상계')로 옮겨도 되는가. 계산 뒤 환급의 미수금은 FRAUD만이 아니라 모든 환급의 공통 길이고(J-T11), 환급의 PEAKET 부담분(재량 면제분·시스템 잘못 환불, POL-038 ①②)을 빼려면 purchase-svc의 환급 부담 구분이 원천으로 필요하다. 옮기면 기록 커밋에서 그 문장을 GAT-130 줄로 옮기고 F-07-8 장부 범위에 `J-T11`을 더한다. 옮기지 않으면 LCH-100 단계 줄을 체크할 수 없고 이 기능이 0.75일 [가정] 늘어난다(추천: 옮김).
- **Q-02**: 다시 계산(판본 +1·`SUPERSEDED`, J-T23 ①②)과 대사 미완 결제가 풀린 뒤의 자동 처리(J-T23 ③)를 F-07-8 범위에 더하는가. 둘 다 회차 취소·연기 일괄 환불과 대사 결과가 원천이다(추천: 더함, F-07-8이 4.0일에서 늘면 기능 표에서 나눔).
- **Q-03**: 이의 없는 수기 조정이 `CONFIRMED`를 `NOTIFIED`로 되돌리는 새 전이 T18(ADR-0368 결정 9)을 받아들이는가. 받지 않으면 조정 뒤 파트너가 바뀐 금액에 이의할 길이 없다(추천: 받아들임. 이 계획 커밋에서 정본에 적었다).
