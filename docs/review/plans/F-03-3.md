# F-03-3 계획(OPS-380 대시보드 4단계·Go/No-Go·남은 허용 실패·판단 위젯·경보 패널·제어 입력 없음)

- **무엇**: `docs/BUILD_ORDER.md` '기능 단위 계획' 표의 F-03-3 행(58행)과 단계 줄 `OPS-380 wbs 4.5.2 ①`(687행)를 끝내는 B 등급 수직 기능의 작업 목록이다(docs/architecture.md §8.6 4의 1·2, ADR-0270 '계획', ADR-0354). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다. 정본 값은 옮겨 적지 않고 자리만 가리킨다.
- **쉬운 말**: 관제 대시보드(SCR-029)는 지금 위젯 둘(입장 비율·빈자리, 결제사)만 실제 값이고 나머지는 디자인 시안의 고정 숫자다. 이 기능은 운영자가 온세일 때 실제로 판단하는 숫자를 서버에서 받아 그리게 한다. ① 회차의 판매 시각으로 지금이 어느 단계(T-30분 점검·T=0·판매 중·종료 후·입장)인지 서버가 정해 그 탭을 연다. ② T-30분 점검의 필수 항목(시계 오프셋, 저장소 상태, 결제사 상태 등)을 서버가 지표 창고(Prometheus)에서 읽어 통과·실패·확인할 수 없음으로 보이고, 운영자가 [Go/No-Go 판정]을 누르면 서버가 다시 계산해 판정과 사유를 감사 로그(바꿀 수 없게 사슬로 묶은 기록)에 남긴다. ③ 여정별 '남은 허용 실패 건수'(목표가 허용하는 실패 가운데 몇 건을 썼는지)와 포화도 요약(CPU·Redis 메모리·Kafka 밀림·이벤트 루프)을 보이고, 위젯마다 '자세히 보기 ↗'(Grafana 새 탭)와 '판단:' 한 줄(이 숫자로 무엇을 하나)을 단다. ④ 입장 제어 리더가 Redis에 적어 둔 '제어 입력 없음'을 ops-svc가 직접 읽어(지표 창고·경보 관리자를 거치지 않는다) 상태 바와 경보 패널에 띄운다. ⑤ 경보 패널을 '이 회차 판단'과 '플랫폼·위생·법정'으로 나누고, 억제된 경보를 위 경보 아래 접힌 줄로 보인다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane2-F-03-3`, 가지 `feature/lane2-F-03-3`, 출발 `78e3bd2be`(F-03-2 계획 커밋. 그 아래 F-03-1 구현 커밋 `677ffd0f3`, 둘 다 아직 develop에 없음, 2026-11-23). 계획 담당 `lane2-f033-plan`(claude-opus-5-5). 제품·시험 코드는 쓰지 않았고 빌드·Docker·브라우저도 쓰지 않았다. 지시서는 `node tools/ci/brief.mjs --batch F-03-3 --out <작업 폴더 밖>`로 뽑는다(이 계획 커밋 뒤 10항목). 2026-11-23 감독 답(ADR 번호, alerts 읽기 함수, HOT-030 넘김, OPS-370 떼기)을 둘째 계획 커밋에 반영했다.
- **등급·차례**: B. **정방향**(`Batch-Order: impl-first`, ADR-0281 결정 5)이고 B 짧은 고리다(ADR-0283 결정 2). 차례: 계획 → 구현(정본 빈칸·ADR 포함) → 시험 → 리뷰 → 리뷰 반영 → 검증(틀린 구현 표본 10개) → 기록. 판단: B 기능은 구현 전 트리 실패 확인 없이 틀린 구현 표본으로 실패를 본다(ADR-0331 결정 2·3). 점검 항목 목록·위젯 값 모양·`control` 사건 본문·판정 응답처럼 공개 인터페이스가 구현 중에 정해지는 몫이 많아, 시험 먼저로 하면 시험이 두 번 쓰인다.
- **차례 바꿈(2026-11-23, ADR 0372(감독이 develop에 올림), 소유자 결정)**: 위 정방향을 버리고 **시험 먼저**로 간다(`Batch-Order: test-first`). 계획 → 시험(구현 전, 기준 트리 실패 확인) → 시험 리뷰 → 지적 반영(Fix-By: test) → 시험 고정 → 구현(시험 파일을 더하거나 고치거나 지우거나 옮기지 않는다) → 게이트·기록·합치기. 구현 뒤 리뷰·검증과 틀린 구현 표본(7절)은 하지 않는다. 아래 절의 리뷰·검증 차례 문장은 이 줄이 이긴다.
- **한 줄 결론**: 서버에 이 숫자들의 원천이 거의 없다. ops-svc는 회차 단계·T-30분 점검·Go/No-Go 판정 경로가 없고(openapi에도 없다, d5 §1.6 13번 '판정 기록 API 없음'), 늘 여는 흐름의 `control` 사건은 이름만 있고 내는 쪽이 없으며(asyncapi `OpsControl` 본문 미정), 에러 버짓 기록 규칙(`peaket:slo:*`)은 저장소 어디에도 없다(OPS-090 몫). 그래서 이 기능은 ops-svc에 **새 바운디드 컨텍스트 `readiness`(단계·점검·판정)**, live 모듈의 **제어 상태 감시**와 **위젯 키 넷**, 마이그레이션 0029를 더하고, 화면은 데스크톱 보드의 실제 값 자리를 늘린다. 갈래 4 파일(`app.module.ts`·`main.ts`·`modules/commands/**`·0025)은 고치지 않고, alerts 모듈에는 감독 승인대로 읽기 함수 하나만 더한다('감독에게' 3·10). 경보 목록을 읽는 REST도 없어(F-03-1 시험이 찾은 빈칸, '감독에게' 10) 처음 열 때와 `reset` 뒤 경보를 다시 읽지 못한다. OPS-370(FE-T29 측정)은 감독 결정으로 새 기능 F-03-6으로 뗐고, 크기는 **4.75일 [가정]**이다('감독에게' 1).

10. **경보 목록 REST와 `reset` 뒤 다시 읽기(감독 지시 2026-11-23 반영)**: ADR-0100 결정 2는 `reset`을 받으면 '명령·경보·승인 대기를 REST로 다시 읽는다'고 적었지만 openapi에 경보 목록 경로가 없다(F-03-1 시험이 찾음). 늘 여는 흐름은 처음 열 때 지금 순번만 주므로, 콘솔을 열기 전부터 울리던 경보도 지금은 보이지 않는다. 이 기능이 `GET /v1/ops/alerts`(아래 1-15, 4)와 처음 열 때·`reset` 뒤 다시 읽기를 맡는다.
   - **alerts 모듈 읽기 함수(감독 결정 2026-11-23: 이 기능이 더한다)**: 경보 기록 표 `ops_alert`는 alerts 컨텍스트의 표이고, 공개 저장소 포트 `OpsAlertStore`에는 `open`·`resolve`만 있다. 다른 컨텍스트는 그 모듈의 `index.ts`로만 가져오므로(`pnpm lint`) 이 기능이 alerts 세 파일 — `src/modules/alerts/domain/ops-alert.ts`(포트에 `list({ eventKey?, resolvedSinceMs, limit })`), `adapters/db/drizzle-ops-alert-store.ts`·`adapters/memory-ops-alert-store.ts`(구현) — 에 읽기 함수를 더한다. **조건 셋**: ① 읽기 함수만 더한다(쓰기·표·마이그레이션·처리기는 alerts에 더하지 않는다) ② 기존 `open`·`resolve` 서명과 사건 키(`(eventKey, kind)` 멱등 규칙, `alertId`)는 바꾸지 않는다 ③ 새 함수는 모듈 `index.ts`로만 내놓는다(지금 `index.ts`가 포트 타입과 두 저장소 클래스를 내보내므로 메서드만 더하면 고칠 것 없음, 새 이름이 생기면 `index.ts`에 한 줄). 받는 처리기와 응답 모양 바꾸기는 live 모듈(`inbound/ops-alerts.controller.ts`)에 둔다. live가 `ops_alert`를 직접 읽거나 자기 알림 표(1시간 보관)만으로 답하는 길은 고르지 않는다(앞은 컨텍스트 경계 위반, 뒤는 1시간 넘게 울린 경보를 잃는다).
   - openapi에 경로를 더하므로 `packages/contracts`(`gen`)·`packages/api-client`(`gen`) 생성물이 함께 바뀌고 같은 커밋에 넣는다(CLAUDE.md 절대 규칙). F-02-1·F-02-5의 생성물과 부딪치면 '감독에게' 3 (바) 규칙대로다. 크기 0.25일 [가정]은 1에 넣었다.

### 4. 공개 인터페이스

- **`GET /v1/ops/events/{eventId}/readiness`**(viewer·operator·commander·cs_agent·cs_lead, `Cache-Control: no-store`): `{ eventId, stage: 't30'|'t0'|'live'|'after'|'entry'|'none', schedule: { opensAt, saleEndsAt, entryOpensAt?, entryClosedAt? }, scale?, items: ReadinessItem[], preview: { verdict: 'go'|'no-go', failedRequired: string[], failedRecommended: string[] }, judgeableUntil, lastJudgement? }`(제안). 판매 설정이 없으면(core 404) `stage: 'none'`, core를 못 읽으면 503 `readiness-source-unavailable`(제안).
- **`GET /v1/ops/alerts`**(viewer·operator·commander, `Cache-Control: no-store`, 제안): 쿼리 `eventId?`(없으면 모든 회차와 회차 밖 경보). 응답 `{ items: OpsAlert[], seq }`. `items`는 걸린 경보 전부와 풀린 지 60분 [가정] 안의 경보, 500건 [가정]까지(넘으면 풀린 것 가운데 오래된 것부터 뺀다, frontend §3.10). `OpsAlert`는 asyncapi `OpsAlert`와 같은 칸이고 openapi `components.schemas`에 같은 모양으로 둔다. `seq`는 응답을 만든 때의 알림 표 마지막 순번이라 콘솔이 그 뒤 사건만 다시 얹는다. 목록 규칙(커서 페이징 등)은 docs/api/guidelines.md §3을 따르되 화면은 한 번에 상한까지 받는다. cs_agent·cs_lead는 403(흐름의 `alert`도 받지 않는다).
- **alerts 공개 읽기(제안)**: `OpsAlertStore.list({ eventKey?, resolvedSinceMs, limit }): Promise<OpsAlert[]>`, `index.ts`로 내보낸다.
- **`ReadinessItem`**(제안): `{ key, group: 'required'|'recommended'|'display', status: 'pass'|'fail'|'unknown'|'not-in-env'|'deferred'|'display-only', value?, unit?, at?, reason? }`. `key`는 영문 소문자·`-`(예 `clock-offset`), 글자는 화면이 만든다. 기준 숫자는 응답에 싣지 않고 정본 자리(control-tower §2)를 따른 서버 상수다.
- **`POST /v1/ops/events/{eventId}/go-no-go-judgements`**(operator·commander, 6-5): 본문 `{ recommendedReasons?: Record<itemKey, string> }`만 받는다(항목 결과·판정 값은 받지 않는다, ASVS 8.2.3). 응답 201 `{ judgementId, verdict, failedRequired, failedRecommended, items, judgedAt, sequence }`. 오류(제안): 403 역할, 404 회차, 409 `judgement-window-closed`(판정 창 밖), 422 `recommended-reason-required`(실패한 권고 항목에 사유가 없음), 503 `readiness-source-unavailable`. 멱등 키 등 POST 공통 규칙은 docs/api/guidelines.md를 따른다.
- **SSE `control`**(asyncapi `OpsControl`, 제안): `{ eventId, kind: 'ok'|'paused'|'raise-stopped'|'no-input'|'emergency-stop'|'unknown', since?, inputStaleKinds?, targetNow?, budgetHoldAt?, lastDecrease?: { reason, journey?, from, to, exposureReduction? }, updatedAt }`. 알림 표 `id`가 없다(접속자처럼 지금 값, 붙을 때 한 번 + 바뀔 때). 화면 계약 `HostState.control`의 다섯 값과 `unknown`은 그대로.
- **위젯 키(제안, '위젯이름.대상')**: `ops-readiness.checklist`(값 = `items`·`preview`), `ops-budget.journeys`(`journeys: [{ journey, linked, allowed, used, remaining, burnShort?, burnLong? }]`), `ops-saturation.summary`(`{ level, cpu, redisMemory, kafkaLag, eventLoop }`, 칸마다 `{ value, level }`), `ops-diagnostics.summary`(`{ rumInpP75Ms, rumLcpP75Ms, slowQueries, network }`). 모두 F-03-1의 공통 네 칸(`widgetKey`·`source`·`at`·`eventId`)과 `source-unavailable` 규칙을 따른다.
- **ops-svc 모듈 공개 면**: `modules/readiness/index.ts`(`ReadinessModule`, 점검 계산기 — live의 위젯 원천이 쓴다), `modules/live/index.ts`(제어 감시를 시험이 바꿔 끼울 손잡이: 읽기 주기·Redis·경보 기록기).
- **콘솔**: 링크 만들기 `detailHref({ kind: 'grafana'|'sentry', panel, eventId, fromMs, toMs })`와 `safeAlertHref(url)`(허용 목록 밖이면 `null`), 경보 나누기 `groupAlerts(alerts, eventId)`(이 회차·플랫폼, 접힌 줄, 펼친 SEV 수). 빌드 값(제안): `PEAKET_CONSOLE_GRAFANA_URL`·`PEAKET_CONSOLE_SENTRY_URL`·`PEAKET_CONSOLE_LINK_HOSTS`.

### 5. 판정 항목별 시험

시험 이름에 ID와 세부 번호를 단다(§8.6 7). 단언 값은 정본(control-tower §2·§6·§8, d5 §7.2, observability §4·§8, ADR-0049·0069·0100)에서 가져오고 코드 상수를 옮기지 않는다. 시간 경계는 가짜 시계로 양쪽(T-30분·T-20분·오픈·+10분·판매 끝, 입력 없음 반영 시간)을 본다. 시험 값은 정본 예와 다르게(예 시계 오프셋 −30ms, 목표 1,234명) 넣는다.

| 시험 | 판정 | 자리 |
| --- | --- | --- |
| `F-03-3 T1 C-T25 ① …(No-Go와 기록)` | 대역 Prometheus가 시계 오프셋 +30ms(또는 −30ms)를 주면 필수 항목 `clock-offset`이 `fail`이고 판정이 No-Go, 20ms·−20ms면 `pass`(경계 양쪽), 판정과 실패 항목·권고 실패 사유가 판정 표와 감사 체인(`GO_NO_GO_JUDGED`, 해시 사슬 검증 통과)에 한 트랜잭션으로 남고, 오프셋을 고친 뒤 T-20분 전 재판정이 Go가 되며 그것도 다음 순번으로 남는다 | ops-svc 통합(PostgreSQL, 대역 Prometheus·core) + 단위 |

### 6. 정할 것과 추천(구현 커밋이 새 ADR과 정본에 적는다)

1. **단계의 원천**: core-svc 내부 판매 설정을 readiness가 읽는다(commands 모듈의 어댑터를 가져오지 않는다, 칸이 모자라고 다른 컨텍스트 내부다). 5초 [가정] 한도, 회차마다 30초 [가정] 캐시. 탭 기본값만 정하고 운영자는 다른 탭을 볼 수 있다.
2. **점검 항목 원천(추천 표, 이름·쿼리는 구현이 ADR에)**: 시계 오프셋(노드 지표), Redis·Kafka·PostgreSQL 상태(내보내기 지표와 Kafka `UnderMinIsrPartitionCount`), 결제사 상태·한도 초과 응답(F-03-1의 `payment_pg_*`), 본인확인·사람 확인 제공자, 종합 합성 점검(합성 점검 지표), 진행 중 배포(배포 도구 지표, 소형 회차는 표시만), 인증서·서명 키 만료 SEV2(경보 기록 표의 열린 경보)와 배치 기기 자격 → Prometheus 또는 ops DB. 프리워밍·CloudFront 한도·NLB 영역 빼기·교차 리전 백업·관리형 유지보수 → 클라우드 전용(이 환경에 없음). 변경 동결 창(F-02-3)·온콜 시험 발송(ADR-0152) → 원천 기능 전에는 확인할 수 없음. 권고 CDN 적중률·수요 예측, 표시 결제사 기본·대체.
3. **판정 규칙(추천 적용, 방향이면 소유자에게)**: 정본은 '필수 항목이 하나라도 실패하면 No-Go'만 적었다. 추천: 필수 `unknown`(원천을 못 읽음·빈 결과·낡음)은 실패로 센다(control-tower §6의 6 '입력이 없으면 멈춘다'와 같은 뜻). '이 환경에 없음'은 local·ci·demo에서만 판정에서 빼고 화면에 배지로 보이며, staging·prod에서 필수 항목 원천이 없으면 ops-svc가 시작하지 않는다(저장소의 'local·ci만 닫힌 대역' 규칙과 같은 꼴). 권고 실패는 사유를 받아 계속(정본). 표시 항목은 판정에 들지 않는다.
4. **판정 창(추천 적용)**: 판정·재판정은 T-30분부터 T-20분까지 받는다(정본 'T-20분까지 실패 항목이 회복되면 다시 판정해 Go로 바꿀 수 있다'). 그 뒤는 409. T-20분까지 판정이 없으면 No-Go로 본다(명령 쪽 C-T25 ②가 읽는 값. 이 기능은 `readiness`의 `lastJudgement` 없음과 `judgeableUntil` 지남으로 그 뜻을 낸다).
5. **판정 권한**: d5 §3.3 관제 셸의 메뉴별 권한 표는 operator '읽기·Go/No-Go', commander '읽기·결정 기록'이다. 추천: commander도 판정할 수 있다(operator 권한을 포함하는 상위 역할, 명령 표와 같은 꼴). 다르게 읽으면 감독이 정한다.
6. **`control`은 알림 표에 넣지 않는다**: 지금 값이라 다시 붙을 때 빠진 것을 메울 필요가 없고(붙을 때 한 번 보냄), 파드마다 같은 Redis를 읽어 같은 값을 낸다. 알림 표 `kind` CHECK를 바꾸지 않는다. 경보는 경보 기록 표에 남긴다(13개월, 월 위생 보고 원천).
7. **대기열 Redis 읽기**: 클러스터면 `PEAKET_QUEUE_REDIS_CLUSTER_URLS`, 아니면 `PEAKET_QUEUE_REDIS_URL`. 없으면 local·ci는 `control` `unknown`과 경고 로그, staging·prod는 시작하지 않는다. 1초 [가정] 주기에 진행 중 회차 수만큼 `HMGET` 한 번씩(회차 키는 해시 태그로 슬롯이 달라 묶지 않는다). 읽기 실패는 `unknown`이고 1분 [가정] 이어지면 SEV3(§16 줄).
8. **기록 규칙 이름(추천 [가정])**: 여정·회차별 온세일 70분 예산의 허용 건수·쓴 건수와 짧은·긴 창 소진 배수를 `peaket:slo:onsale_*{event_id,journey}` 꼴로 observability §8에 적는다. 이름을 바꾸면 위젯 원천 어댑터를 함께 고친다(리더 입력 규칙과 같은 문장).
9. **원천이 없는 위젯(추천)**: 실제 값 화면에서는 고정 숫자를 그리지 않고 '원천 연결 전 · {원천 기능}' 카드로 둔다. 운영자가 시안 숫자를 실제 값으로 읽는 일을 막는다. 미리보기(`?state=`)는 그대로 시안을 그린다.
10. **링크 주소**: Grafana·Sentry 주소 틀과 허용 호스트는 빌드 값(관제 콘솔은 정적 앱이라 실행 때 설정 파일이 없다). 주소 틀에 넣는 값은 회차 ID·시작·끝 시각뿐이다(ASVS 1.2.2 글).

**소유자 결정이 필요할 수 있는 것**: (1) 6-3의 판정 규칙을 방향 결정으로 볼 때. (2) `OpsControl` 본문을 정한 것이나 위젯 응답 스키마가 계약 깨짐 검사(`docs/api/breaking/`)에 걸려 예외 허용이 필요할 때(2026-11-22 선례). (3) 가상 스크롤에 새 의존성이 필요할 때(devops §4.4). 셋 다 아니면 묻지 않는다.

### 10. F-03-6에 넘기는 메모(OPS-370, FE-T29 측정. 이 기능에서 하지 않는다)

첫 계획 커밋에서 세운 측정 방법이다. F-03-6 계획 담당이 다시 확인해 쓴다(선행 F-03-3이 끝난 대시보드를 잰다). 첫 계획의 정할 것 6-11·6-12도 여기로 옮겼다.

- **무엇을 견주나**: 같은 커밋·같은 위젯 판의 MF 빌드(기본)와 한 앱 빌드(`PEAKET_CONSOLE_BUILD=single`). 둘 다 운영 빌드다. 같은 관제 API(메모리 ops-svc + 대역 Prometheus, 두 빌드 같은 값)에 붙인다.
- **무대**: 정적 파일은 데모 이미지와 같은 nginx 설정(`deploy/local/demo/nginx/console-host.conf`, 원격 sha 경로 긴 캐시·`remotes.json` no-cache)의 로컬 컨테이너로 내고, 브라우저는 판을 고정한 Playwright 컨테이너(`ci-web.yml`의 `mcr.microsoft.com/playwright:v1.64.1-noble@sha256:2f05…`)의 Chromium을 개발자 도구 규약으로 움직인다. 데스크톱 xl 1440 화면, 네트워크는 느리게 하지 않고 CPU만 4배 느리게(`Emulation.setCPUThrottlingRate` 4, frontend §5.8 Lighthouse 규칙과 같은 뜻). 선례는 K5 `local-lab`(docs/perf-ledger.md 119행).
- **잴 것 넷(ADR-0100 결정 6, frontend FE-T29 행)**: ① 대시보드 첫 그림(아래 '첫 그림 표시 지점'까지, 참고로 FCP·LCP): 빈 캐시(새 브라우저 맥락 + 캐시 지움)와 채운 캐시(같은 맥락 다시 열기) ② 첫 화면 JS와 화면별 덩어리 크기(gzip, `node:zlib`, 첫 그림까지 받은 스크립트 목록과 빌드 산출물) ③ 격리(T1과 같은 막기, 두 빌드 모두 셸·경보 패널·다른 위젯이 그대로인지를 기록) ④ 위젯 하나(예: 입장 비율 위젯 글 한 줄)를 고쳐 내기까지 다시 빌드하는 폴더 수와 시간(MF는 그 원격 하나 빌드 + 목록 만들기, 한 앱은 호스트 전체 빌드, 정적 자리에 올리기까지. 클라우드 올리기는 구간 5라 미측정으로 적는다).
- **횟수·통계**: 넷마다 빌드마다(①은 캐시 둘마다) 3회, 중앙값과 가장 늦은 값(아래 'p75'). 앞에 MF 대 MF A/A 3회를 재 이 PC의 흔들림을 함께 적는다(PROGRESS '측정이 도는 동안'의 A/A 규칙).
- **차례와 잠금**: F-03-6 안에서 리뷰 반영 커밋 뒤, 검증 앞. 측정(약 50분 [가정]) 동안 다른 갈래가 이 PC에서 시험·빌드를 멈추게 감독에게 알린다(2026-11-19 BAT-058 측정 창 선례). ① `bash D:/ticketpass-locks/lock.sh who docker`로 비었는지 보고 `take docker lane2-F-03-6`(차 있으면 기다림), `owner.txt`에 일·시작·예상 끝(약 50분 [가정]). ② 감독에게 측정 창을 알려 다른 갈래가 이 PC에서 시험·빌드를 멈추게 한다. ③ 이 작업 폴더에서 두 운영 빌드를 먼저 만들고(측정 중 빌드 금지, ④의 다시 빌드 시간 재기는 따로 순서를 정해 그것만 돈다), 메모리 ops-svc·대역 Prometheus는 이 PC 프로세스로, 정적·브라우저는 컨테이너로 띄운다. ④ 끝나면 띄운 컨테이너를 `docker rm -f -v`로 지우고 자기 PID만 끝낸 뒤 `drop docker lane2-F-03-6`.
- **장부**: `python tools/perf-ledger/collect.py --run-id 2026-11-<일>-fe-t29-console-<mf|single> --kpi FE-T29 --version v1 --profile local-lab --closed-model --bench-summary <요약 JSON> --evidence 측정함 --verdict baseline --notes "<증거 수준 실측(PC), 클라우드 올리기 미측정>"`(빌드마다 한 실행, 인자는 구현 담당이 `collect.py --help`로 맞춘다). 결과 해석(바꿀 조건에 닿았나)은 장부 `notes`와 기록 커밋 본문에 적고, 닿으면 새 ADR을 쓰는 것은 소유자 보고 뒤다(정본 '판정이 아니라 기록').
- **누가**: 측정 도구는 구현 담당, 격리 시험(두 빌드에서 원격 진입 파일·위젯 덩어리 하나를 막아도 셸·경보 패널·다른 위젯이 그대로, `FE-T29 ③`)과 측정 도구 자기 시험(SKIPPED·0건이 통과로 새지 않음)은 시험 담당, 측정 실행과 장부 기록은 리뷰 반영 뒤 감독이 띄우는 담당(시험 담당 세션을 이어 써도 된다. 역할 커밋은 `test`, 바꾸는 파일은 `docs/perf-ledger/` 아래뿐).
