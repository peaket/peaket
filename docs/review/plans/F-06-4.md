# F-06-4 계획 — 예매 제한 집행·FRAUD_CASE 소명·화면 사본 (동결 로컬)

- **무엇**: 기능 F-06-4(고객·CS·법정, A등급, GAT-310)의 동결 로컬 작업 계획이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **등급·차례**: A등급(`Batch-Grade: A`). ADR-0372·ADR-0373·ADR-0381의 A 차례를 따른다. **계획 → 시험 → 시험 리뷰(새 세션) → 시험 고정 → 구현 → 게이트 → 구현 리뷰(새 세션) → 지적 반영 → 고친 곳 다시 보기 → 기록.** 이번 작업은 **계획·시험·기준 트리 실패 확인·게이트까지** 하고 시험 리뷰를 받을 준비에서 멈춘다. 구현은 시험 리뷰 뒤에 시작한다.
- **동결 로컬 범위**: v1 출시 범위 밖이다(ADR-0373 결정 2, ADR-0386 결정 4·5, `docs/release/v1-scope.md` F-06-4). `freeze/lane2-F-06-4` 가지와 `D:/ticketpass-freeze-F-06-4` 워크트리에서만 개발하고 `develop`·`release/1.0.0`에 합치지 않는다. 출시 마이그레이션·릴리스 플래그·`deploy/` 값은 건드리지 않는다.
- **바탕**: 출발 `94e9e3621`(`origin/freeze/lane2-F-06-3`, 2026-11-26). 가지 `freeze/lane2-F-06-4`. 시험은 Docker 없이 단위·HTTP·gRPC 경계로 돌린다(통합 시험은 구현 뒤 게이트에서 Docker 잠금을 잡고 돌린다).
- **정본**: `docs/features/transfer-refund.md` §3.2·§4.1·§7.1~§7.4·§11, `docs/features/queue-admission.md` §6, `docs/features/forensic-replay.md` §6.7.5(부정 예매 소명 입구), `docs/data.md` `approval_request`·`approval_vote`·`booking_restriction`·`appeal`·`cs_case`·`fraud_case`, `docs/api/openapi.yaml` `/v1/appeals`·`/v1/booking-restrictions/me`·`/v1/fraud-appeal-requests`·`/v1/ops/approval-requests*`·`/v1/ops/cases*`·`ApprovalRequestInput`·`BookingRestrictionStatus`·`FraudAppealView`·`CsCase`, `docs/api/proto/peaket/core/v1/core.proto`(`BookingRestrictionViewService`·`FraudAppealViewService`), `docs/api/proto/peaket/{queue,purchase}/v1/*.proto`(`SetBookingRestriction`), `docs/api/proto/peaket/identity/v1/identity.proto`(`SetAccountHold`), `docs/planning/03-policies-glossary.md` POL-038 ⑤·POL-046 ⑥, `docs/security/asvs/transfer-refund.md`, ADR-0046·0062·0161·0164·0171·0173·0320·0372·0373·0381·0386. 값은 이 파일에 옮기지 않고 위치만 가리킨다.

### 1.3 장부 범위 좁히기

기준 트리의 F-06-4 장부 범위는 `docs/features/transfer-refund.md`·ASVS 문서 전체라 **322항목**이다(기준 트리 `node tools/ci/ledger.mjs --batch F-06-4`: 자동 207·ID만 39·빈칸 56, 그 밖에 F-06-3·F-07·F-05의 항목이 섞인다). §8.6 3의 "장부 범위가 넓어 닿지 않는 항목이 들면 기능을 시작할 때 범위를 좁힌다"에 따라 BUILD_ORDER F-06-4 줄의 **장부 범위 칸만** 다음으로 좁힌다. 판정 칸(정본 목록)과 상태 칸은 그대로 둔다.

```
R-T13, R-T32 ①~③, R-T32 ⑥, R-T34 ①~②, R-T34 ④~⑥, Q-T59 ①~⑥, transfer-refund:v5.0.0-1.2.4, transfer-refund:v5.0.0-2.2.1, transfer-refund:v5.0.0-2.2.2, transfer-refund:v5.0.0-2.3.1, transfer-refund:v5.0.0-2.3.3, transfer-refund:v5.0.0-2.3.4, transfer-refund:v5.0.0-3.5.3, transfer-refund:v5.0.0-8.2.1, transfer-refund:v5.0.0-8.2.2, transfer-refund:v5.0.0-8.3.1, transfer-refund:v5.0.0-14.2.1, transfer-refund:v5.0.0-14.2.2, transfer-refund:v5.0.0-14.3.2, transfer-refund:v5.0.0-15.4.2, transfer-refund:v5.0.0-16.3.2, transfer-refund:v5.0.0-16.5.3
```

- **R-T32 ⑥은 이 가지에서 시험한다**: 제한 행의 `reason_code`가 `FRAUD`이고 `fraud_case_id`가 있으면 소명을 그 사건에 잇고 담당을 그 사건의 조사관으로 정한다. 조사관을 읽는 어댑터는 F-04-13 표가 없는 이 가지에서 **포트**로 두고 시험은 대역으로 넣는다. 실제 표 읽기는 합성 때 F-04-13 어댑터가 붙는다(§6).
- **R-T32 ④·⑤·⑦과 R-T34 ③, Q-T59 ⑦은 범위에서 뺀다**. ④·⑤·⑦은 F-04-13 사건 상태 기계, ③은 FRAUD_ACTION 승인, ⑦은 부하 측정이다. §10에 "이 가지에서 닫지 않는 몫"으로 한 줄씩 적고, 합성 때 확인할 목록(`docs/lanes/lane2-cleanup.md`)에 넘긴다.
- 나머지 뺀 항목(`R-T5`·`R-T6`~`R-T12`·`R-T14`~`R-T29`·`R-T30`·`R-T31`·`R-T33`·`R-T35`~`R-T47`, ASVS의 그 밖 행)은 다른 기능(F-05-2·F-06-2·F-06-3·F-06-5·F-06-7·F-07-5~8, F-04-13)의 장부 범위이거나 이미 그 기능이 닫았다.
- `Q-T59 ①~⑥`은 받는 쪽 시험이 이미 있다. 이 기능은 **보내는 쪽**(ops) 시험 이름에 세부 번호를 달고, 받는 쪽 기존 시험(§5의 목록)과 짝을 적는다. `R-T34`는 엔진·승인 시험으로, `R-T13`은 일반 남용 제한 시험으로 닫는다.

## 2. 정본 빈칸과 이번에 정하는 것(추천 적용, 2026-11-26)

정본에 없어 구현이 임의로 정할 수 없는 것만 적는다. 구현 전에 정본(괄호의 위치)에 쓴다. 방향을 바꾸는 결정은 없다.

1. **일반 남용 제한의 요청자·승인자**(`docs/planning/03` POL-038 ⑤, `docs/features/transfer-refund.md` §7.2): 시스템은 `ABUSE_FLAG` CS 건만 연다(자동 제한 없음). `cs_agent`가 그 건에서 사유 코드·끝 시각·사유를 붙여 `BOOKING_RESTRICTION` 승인 업무를 요청하고, 요청자가 아닌 `cs_lead` 1인이 확인해 승인한다(`requiredApprovals` 2 = 요청자 + cs_lead). 승인 전에는 제한 행·사본이 0이다. `cs_lead`가 직접 요청해도 다른 `cs_lead`가 승인한다(자기 승인 403).
2. **사유 코드**(`docs/data.md` `booking_restriction.reason_code`, openapi `ApprovalRequestInput.reasonCode`): 일반 남용은 `ABUSE_CANCEL`(반복 취소)·`ABUSE_TRANSFER`(반복 양도)·`ABUSE_MULTI_ACCOUNT`(다계정)·`ABUSE_RESALE`(재판매 목적) 넷 [가정]이다. `FRAUD`는 일반 요청 경로에서 422 `restriction-reason-not-allowed`이고 FRAUD_ACTION 경로만 쓴다. 그 밖 값은 422다.
3. **끝 시각·소명 기한·판 번호**(`docs/features/transfer-refund.md` §3.2·§7.2, `docs/data.md` `booking_restriction`): 요청 본문에 `restrictionEndsAt`(ISO 시각)을 더한다. `BOOKING_RESTRICTION`에만 필수이고 다른 종류에 보내면 400 `invalid-body`다. 요청 시각보다 뒤이고 요청 시각 + 1년 [가정]을 넘지 않아야 한다(넘으면 422 `restriction-too-long`, 승인 업무 0). `starts_at`은 집행 시각, `ends_at`은 요청 값, `appeal_due_at`은 `starts_at` + 1일 [가정]이다. `version`은 그 계정의 앞선 행 최대값 + 1이고 사본에 같은 값을 싣는다. 해제는 `LIFTED`, 끝이 지나면 정비가 `EXPIRED`로 바꾼다(복구용 사본은 끝 시각으로 판정하므로 사본을 따로 지우지 않는다).
4. **집행 순서와 실패**(`docs/features/transfer-refund.md` §7.2 T14, `docs/features/queue-admission.md` §6): 승인 뒤 ① 지역 `booking_restriction` 행을 ACTIVE로 쓴다(같은 트랜잭션에 감사) ② queue-svc `SetBookingRestriction` ③ purchase-svc `SetBookingRestriction` ④ core-svc `SetBookingRestrictionView`(화면용, 늦거나 실패해도 DONE을 막지 않는다). ②나 ③이 실패하면 승인 업무는 `EXECUTING`으로 두고 작업이 1분→2분→…→10분 [가정] 간격으로 같은 판을 다시 보낸다. 처리 기한(`due_at`) 안에 끝나지 않으면 `FAILED`로 바꾸고 `APPROVAL_EXECUTION_FAILED` CS 건을 연다. 같은 판 재전송은 `changed:false`를 성공으로 본다.
5. **해제**(같은 절): 일반 사유는 `cs_lead`가 혼자 풀 수 있다(감사·사본 두 곳·화면 사본), `FRAUD` 사유는 FRAUD_ACTION 승인 뒤에만 엔진의 `lift`가 불리고 그 밖 경로는 403 `fraud-restriction-requires-approval`이다. 해제도 두 사본이 모두 반영돼야 DONE이다.
6. **정비와 다시 보내기**(`docs/data.md` §3 `q:rst`·`s:rst`·`sup:rst`): 10분 [가정]마다 ① 끝이 지난 ACTIVE를 `EXPIRED`로 ② ACTIVE 행의 화면용 사본과 두 집행 사본을 같은 판으로 다시 보낸다. 실패는 세지 않고 다음 바퀴에 다시 한다. 사본 저장소가 잃어도 이 작업이 다시 세운다.
7. **소명 접수 종류**(`docs/features/transfer-refund.md` §7.1, openapi `createAppeal`): 이 기능은 `RESTRICTION`·`FRAUD_CASE`만 받는다. `RECLAIM`은 422 `appeal-kind-not-supported`다(양도 회수 소명은 support 뒤 몫). `RESTRICTION`은 화면용 사본(`sup:rst`)으로 기한이 지났으면 409 `appeal-deadline-passed`로 먼저 막는다. `FRAUD_CASE`는 미리 막지 않고 ops가 사건에 이을 때 판정한다. 본문은 NFC 정규화한 코드 포인트 1~2,000자이고 빈 글·초과는 400 `invalid-body`다.
8. **소명의 CS 건과 결과**(`docs/features/transfer-refund.md` §7.1): 소명은 core DB `appeal`에 저장하고 같은 트랜잭션의 Outbox로 `support.cases-requested`(kind `APPEAL`, category = `RESTRICTION`|`FRAUD_CASE`, sourceId = appealId)를 낸다. ops는 건을 열고 core 내부 API로 소명을 읽어 ① 예매 제한: 그 제한이 그 계정의 것이고 `appeal_due_at` 전이면 잇고 담당을 `cs_lead`로, `SetAccountHold(APPEAL, OPEN, source_ref = caseId)`를 보낸다. 아니면 소명을 `INVALID`(대상 아님·기한 경과)로 닫고 팬에게 알린다 ② FRAUD 사건: core가 `sup:far` 사본의 `party`(없으면 `PAYER`)로 ops의 F-04-13 입구 `POST /internal/v1/fraud-cases/{caseId}/appeals`를 부른다. 답이 403/404면 `INVALID`(대상 아님), 200 `{result: EXPIRED}`면 `INVALID`(기한 경과), 5xx·연결 실패면 `SUBMITTED`로 두고 다시 보낸다(1분→10분 [가정]). `HOLDER`는 계정 단위 판단이 없으므로 소명 행만 `DECIDED` 없이 `SUBMITTED`로 남기고 ops가 사건 기록한다.
9. **소명 판단과 결과 기록**(`docs/features/transfer-refund.md` §7.1): 예매 제한 소명은 `cs_lead`가 CS 건 상세에서 `ACCEPT`(해제) 또는 `REJECT`(유지)와 사유(1~1,000자)를 적는다. `ACCEPT`는 제한 엔진의 해제를 먼저 실행하고(두 사본 Done), 성공하면 core 내부 API로 `{status:'DECIDED', result:'LIFTED', resultNote}`를 쓴다. `REJECT`는 `{status:'DECIDED', result:'KEPT', resultNote}`다. 건은 `RESOLVED`, `SetAccountHold(CLOSED)`를 보내고 팬에게 결과를 알린다. 같은 결정을 다시 보내면 같은 결과다(결정은 건 판으로 한 번).
10. **화면용 사본 두 갈래**(`docs/data.md` §3 `sup:rst`·`sup:far`, core.proto): `SetBookingRestrictionView`는 `(account_id, restriction_id)`마다 판이 클 때만 쓰고, 없으면 새로 쓴다. `SetFraudAppealView`는 `(account_id, case_id)`마다 판이 클 때만 쓴다. `party=HOLDER` 사본은 `reason_categories`·`locked_ticket_ids`·`restricted_until`·`priority_purchases`·`lock_expires_at`·`objection_due_at`을 비우고 `lock_active=false`, `held_ticket_ids`만 쓴다(POL-046, ADR-0173 결정 4). 두 표면은 TTL을 두지 않고 판으로만 거른다(사본 저장소가 잃으면 ops가 10분마다 다시 보낸다). `GET` 응답은 `private, no-store`다.
11. **화면 연결 없음**(§7): SCR-042·공연 상세·계정 설정의 실제 API 연결은 이 기능에 넣지 않는다. 이 기능의 완료 판정은 API·사본·CS 처리 행동이고, 화면은 기존 보드를 그대로 둔다. 브라우저 확인은 웨이브 끝에 화면 기능이 연결된 뒤에 한다(이 기능은 대본만 §7에 남긴다).

## 4. 공개 인터페이스(시험이 기대는 모양)

### 4.1 ops HTTP

- `POST /v1/ops/approval-requests` — 본문 `{kind:'BOOKING_RESTRICTION', targetRef:<계정 UUID>, amount:0, reasonCode:'ABUSE_CANCEL'|'ABUSE_TRANSFER'|'ABUSE_MULTI_ACCOUNT'|'ABUSE_RESALE', reasonText, restrictionEndsAt:<ISO>}`. 201 `ApprovalRequest`(`requiredApprovals:2`·`canApprove`는 요청자가 아닌 `cs_lead`만). 422 `restriction-too-long`·`restriction-reason-not-allowed`·`approval-kind-not-allowed`, 400 `invalid-body`(끝 시각 없음·다른 종류에 보냄·amount≠0), 403 `approval-role-required`.
- `…/{approvalId}/approvals` — F-06-3 그대로(`If-Match`, 재인증). 승인되면 집행. `…/rejections`·`…/withdrawals` 그대로.
- `POST /v1/ops/cases/{caseId}/restriction-appeal-decision` — `cs_lead`, 본문 `{decision:'ACCEPT'|'REJECT', reason:1~1000자}`, 200 `CsCase`. `APPEAL`+`RESTRICTION`만 받고 아니면 409 `case-action-not-applicable`, 이미 결정됐으면 409 `case-already-resolved`, 남의/없는 건 404.
- `POST /internal/v1/restriction-copies/tick`은 두지 않는다. 정비·다시 보내기는 시작 조립의 배경 작업이 부르고 시험은 키트의 `tick()`을 직접 부른다.

### 4.2 core HTTP

- `POST /v1/appeals` — `{kind:'RESTRICTION'|'FRAUD_CASE', targetId, body}` → 201 `Appeal`(`status:'SUBMITTED'`) + `Location`. 400 `invalid-body`(빈 글·2,001자·모르는 칸), 422 `appeal-kind-not-supported`(`RECLAIM`), 409 `appeal-deadline-passed`(`RESTRICTION` 화면용 사본의 `appealDueAt`이 지남).
- `GET /v1/appeals` — `AppealPage`(내 것만 최근 제출 순, 본문·CS 건·담당 없음), `private, no-store`.
- `GET /v1/booking-restrictions/me` — `BookingRestrictionStatus`(`status:'NONE'|'ACTIVE'`, `restrictionId`, `reasonCode`, `startsAt`, `endsAt`, `appealDueAt`), `private, no-store`. `sup:rst`가 없거나 LIFTED·EXPIRED면 `NONE`.
- `GET /v1/fraud-appeal-requests` — `FraudAppealViewPage`(`caseId`·`eventId`·`party`·`heldTicketIds`·`excludedTicketIds`·`reasonCategories`·`dueAt`·`objectionDueAt`·`objectionStatus`·`actionResult`·`priorityPurchases`·`lockExpiresAt`·`lockActive`), `private, no-store`. `HOLDER`는 사유 범주·잠금·우선 구매가 빈 값이다.
- 내부 `GET /internal/v1/appeals/{appealId}` — 내부 토큰, `{appealId, accountId, kind, targetId, body, submittedAt, status, caseId}`. 없으면 404.
- 내부 `POST /internal/v1/appeals/{appealId}/result` — 내부 토큰, `{status:'DECIDED'|'INVALID', result?:'LIFTED'|'KEPT'|'ACCEPTED'|'REJECTED', resultNote?:string, caseId?:string}`. 200 `Appeal`(같은 본문 재호출은 같은 답, 다른 본문은 409 `appeal-result-conflict`).

### 4.3 gRPC

- `peaket.core.v1.BookingRestrictionViewService/SetBookingRestrictionView` — core.proto 그대로. 내부 토큰 + 호출자 `ops-svc`(메타데이터 `x-peaket-caller`)가 아니면 `PERMISSION_DENIED`, 판이 같거나 작으면 `changed:false`.
- `peaket.core.v1.FraudAppealViewService/SetFraudAppealView` — core.proto 그대로. 같은 가드. `party=HOLDER`면 사유 범주·잠금·우선 구매·이의 칸을 비우고 `held_ticket_ids`만 쓴다.
- `peaket.queue.v1.BookingRestrictionService/SetBookingRestriction`·`peaket.purchase.v1.BookingRestrictionService/SetBookingRestriction` — 기존 계약을 그대로 부른다(바꾸지 않는다).

### 4.4 시험과 구현이 함께 따르는 키트·포트 모양

```ts
// ops-svc AppModule.register({ memory:true, restrictions, csAppeals })에 더한다
interface OpsRestrictionWiring {
  copies: {
    queue(i: CopyInput): Promise<{ changed: boolean }>;
    purchase(i: CopyInput): Promise<{ changed: boolean }>;
    view(i: CopyInput & { reasonCode: string; startsAtMs: number; appealDueAtMs: number; state: 'ACTIVE'|'LIFTED' }): Promise<{ changed: boolean }>;
  };
  store?: BookingRestrictionStore;          // 없으면 메모리
  appeals?: { read(appealId: string): Promise<AppealSourceRecord | undefined>; result(appealId: string, r: AppealResult): Promise<void> };
  fraudCases?: { investigatorOf(caseId: string): Promise<{ assigneeId: string } | undefined> };
  notifier?: { send(i: { appealId: string; accountId: string; event: 'INVALID'|'DECIDED'; result?: string }): Promise<void> };
  holds?: { set(i: { accountId: string; caseId: string; state: 'OPEN'|'CLOSED'; version: number }): Promise<{ changed: boolean }> };
  now?(): number;
}
// 전역 키트: Symbol.for('peaket.ops.restriction-kit') → { rows(), seed(row), applyFraud(i), tick(nowMs) }
// applyFraud는 F-04-13의 FRAUD_ACTION 실행기가 같은 엔진으로 FRAUD 행을 집행할 때 쓰는 표면이다(계획 §6 합성 경계).
// core-svc AppModule.register({ memory:true, support })
interface CoreSupportWiring {
  store?: AppealStore;
  outbox?: CaseRequestOutbox;
  fraudAppeals?: { send(i: { caseId: string; appealId: string; accountId: string; party: 'PAYER'|'HOLDER'; submittedAtMs: number }): Promise<{ result: 'ACCEPTED'|'EXPIRED'|'NOT_TARGET'|'RETRY' }> };
  notifier?: { send(i: { appealId: string; accountId: string; event: 'INVALID'|'DECIDED'; result?: string }): Promise<void> };
  views?: { restriction?: RestrictionViewStore; fraud?: FraudAppealViewStore };
  now?(): number;
}
// 전역 키트: Symbol.for('peaket.core.support-kit') → { appeals, outbox, views, dispatchOnce(nowMs), grpcHandlers }
```

- `CopyInput`은 `{ accountId, restrictionId, state:'ACTIVE'|'LIFTED', endsAtMs?: number, version }`이다.
- `AppealSourceRecord`는 `{ appealId, accountId, kind, targetId, body, submittedAtMs }`이다.
- `FraudAppealClient`(core)는 실제 HTTP 어댑터가 `PEAKET_OPS_HTTP_URL`로 `POST /internal/v1/fraud-cases/{caseId}/appeals`를 부르고, 403·404는 `NOT_TARGET`, 200 `{result:'EXPIRED'}`는 `EXPIRED`, 2xx 그 밖은 `ACCEPTED`, 5xx·연결 실패는 `RETRY`로 옮긴다. 내부 토큰과 `x-peaket-caller: core-svc`를 싣는다.
- `RestrictionViewStore`·`FraudAppealViewStore`는 `apply(i): Promise<{changed:boolean}>`·`get(accountId, id)`·`clear()`를 둔다. 메모리와 Redis 어댑터가 같은 계약이다.
- 시작 조립(`main.ts`)은 시험 조립과 따로 본다. 이 기능의 단위 시험은 앱 조립(키트)으로, 시작 조립 시험은 env만 읽는 얇은 시험 하나로 확인한다(§5).

## 6. 실제 서버 연결과 차례

- **서버 ↔ 저장소**: core-svc `test-int/support-appeals.int.test.ts`(구현 뒤)가 실제 PostgreSQL 18에서 0049의 표·CHECK·인덱스와 접수·결과·다시 보내기를 본다. **ops `booking_restriction`은 이 가지에 표가 없어 통합 시험을 돌리지 않는다.** 합성 트리(F-04-13 0037 + 이 기능 0040)에서 `restriction.int.test.ts`를 한 번 돌려 행·판·CHECK·EXPIRED 정비를 본다(Docker `lane2-F-06-4` 잠금, `docker-all` 금지).
- **서비스 사이**: ops→queue/purchase/core gRPC는 단위 시험에서 **proto 설명자로 세운 실제 gRPC 서버**로, core→ops HTTP는 **문서화된 입구 계약을 구현한 로컬 HTTP 서버**로 본다. 가짜 업무 포트로 끝내지 않는다.
- **화면 ↔ 서버**: 이 기능은 화면을 바꾸지 않는다. 화면이 읽을 API·사본 모양은 openapi·proto 시험으로 본다.
- **합성 경계**: F-04-13 가지가 만드는 `booking_restriction` 표·`fraud_case`·`POST /internal/v1/fraud-cases/{caseId}/appeals`와 이 기능이 만드는 core 소명·ops 제한 엔진은 **같은 트리에서만** 끝까지 돈다. 두 freeze 가지는 서로 합치지 않고, 합성은 감독이 마지막에 한다(§9).

## 7. 브라우저 확인 대본(웨이브 끝)

이 기능은 화면을 바꾸지 않으므로 브라우저 확인을 하지 않는다(ADR-0331 결정 6). 화면 연결 뒤 웨이브 끝에 다음 대본으로 한 번 본다.

1. 예매 제한이 걸린 팬이 공연 상세에서 "예매가 제한되어 있습니다 · 소명 기한"과 [소명하기]를 본다.
2. SCR-042에서 사유·기한·잠긴 표(부정 예매)를 보고 2,000자 안의 소명을 낸다. 기한이 지났으면 "소명이 닫혔습니다"가 보인다.
3. `cs_lead`가 SCR-045에서 소명 본문을 읽고 [제한 해제] 또는 [제한 유지]를 고른다. 남의 건은 404다.
4. 팬이 결과 배지(해제·유지)와 사유를 본다. 부정 예매 받은 사람은 사유 범주가 보이지 않는다.
5. 콘솔 오류·CSP 위반 0, 브라우저 저장소에 소명 초안 0.

## 9. 정리 목록으로 보낼 것

- **합성 때 확인할 몫**: F-04-13 `0037` 뒤 이 기능 `0040`을 적용해 `booking_restriction` 행·판·CHECK·`EXPIRED` 정비·Drizzle 저장소를 실제 PostgreSQL에서 한 번 본다(이 가지 단독에는 표가 없다). ops `0040`의 `DO $$` 가드가 0037 앞에서도 안전한지 같은 시험에서 확인한다.
- **합성 때 확인할 몫**: F-04-13의 `POST /internal/v1/fraud-cases/{caseId}/appeals` 계약(403/404/200 EXPIRED/HOLDER)과 core `HttpFraudAppealClient`의 실제 짝. 이 가지는 문서화된 계약을 구현한 로컬 서버로만 본다.
- **합성 때 확인할 몫**: R-T32 ④·⑤·⑦(조사관 404·이의 OBJECTED·받은 사람 진술), R-T34 ③(LIFT_RESTRICTION 승인 대기). F-04-13 가지의 사건 상태·조사관 지정이 필요하다. `docs/lanes/lane2-cleanup.md`에 적는다.
- F-04-13의 `FraudActions.restrict`/`lift`와 이 기능의 제한 엔진이 같은 표를 두 번 쓰지 않게 합성 때 하나로 모은다(어느 쪽이 남의 것을 부르는지 정한다). 지금은 각 가지가 자기 경로만 만들고, 표·판 규칙을 공유한다.
- `queue-svc`·`purchase-svc` `SetBookingRestriction`의 호출자 검사는 메시 L7 허용 목록뿐이다(핸들러는 신원을 보지 않는다). 코드 가드가 필요하면 뒤 기능.
- `approval_request.requested_by`는 NOT NULL이고 `approval_vote.requester_id`도 NOT NULL이다. 시스템이 요청자인 종류를 만들려면 스키마 변경이 필요하다. 이 기능은 cs_agent 요청으로 피했다.
- core `appeal`의 `dispatch_state`·`next_dispatch_at`은 이 기능이 더하는 [가정] 칸이다. 소명 본문 3년 파기 작업은 이 기능에 넣지 않는다(F-06-5 support).
- 소명 결과 팬 알림은 포트(로그 어댑터)까지만 만들고 실제 이메일·푸시 문안은 notify 기능(F-06-1·F-06-6) 몫이다.
- 콘솔 SCR-045의 APPEAL 상세 칸(본문 읽기·[제한 해제]/[제한 유지])은 화면 연결 뒤 몫이다.
