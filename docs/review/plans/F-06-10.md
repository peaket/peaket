# F-06-10 계획 — 알림함(SCR-072)

- 기능 F-06-10(고객·CS·법정), 등급 B, 단계 `GAT-253`(wbs 5.6.6), WBS 1.5일 [가정]. 상태 **동결**(ADR-0373, 2026-11-26 등록).
- 장부 범위: `N-T33`, `N-T34`(`node tools/ci/ledger.mjs --batch F-06-10`).
- 정본: [notify.md](../../features/notify.md) §4.11, [ADR-0390](../../adr/0390-notification-inbox-design.md), openapi `/v1/notifications`·`/v1/notification-unread-count`·`/v1/notification-read-all`·`/v1/notifications/{notificationId}/read`, data.md `notification_inbox`, d5 §5.36·d3 SCR-072, planning/04 SCR-072.
- 선행: F-06-8(알림 intake). F-06-9·F-06-11과 독립이다.

## 끝내는 것

1. `notification_inbox` 한 표에 `(account_id, logical_key)` 유일로 논리 알림 하나를 둔다. intake가 `notification_dedup`·`notification_job`과 같은 트랜잭션에서 넣고, 쓰기 실패는 그 알림 적재 실패로 보고 재시도한다.
2. `logical_key`는 채널을 뺀 키다(예 `BOOKING_CONFIRMED:{orderId}:CONFIRMED:{accountId}`). 같은 알림이 이메일·웹 푸시·문자로 여러 번 가도, CS 다시 보내도 항목은 하나다.
3. `vars`는 §12 허용 목록만 갖고 본문·주소·전화번호·판매자 정보를 넣지 않는다. 제목·본문은 읽을 때 템플릿·catalog로 만들고, 템플릿 판이 없으면 지금 판으로 그리며 `notify_template_fallback_total`을 올린다.
4. API: `GET /v1/notifications`(커서·limit 기본 20 [가정]·최대 50, `unreadOnly`, `category`), `GET /v1/notification-unread-count`, `POST /v1/notification-read-all`, `POST /v1/notifications/{notificationId}/read`(204·멱등·남의 항목 404). 팬 쿠키, `Cache-Control: private, no-store`.
5. 화면 SCR-072 `/my/notifications`: 머리 종 배지(안 읽은 수), 탭 [전체]·[읽지 않음], 분류 칩, 목록(분류·제목·본문 2줄·상대 시각·안 읽음), [모두 읽음], 더 보기. 401·오프라인·대상 없어짐·에러 상태는 d5 §5.36.
6. 보존·병합·탈퇴: 1년 [가정] 뒤 `created_at` 기준 묶음 삭제, 탈퇴 즉시 삭제, 계정 병합 때 대표 계정으로 옮기고 `logical_key`가 겹치면 하나(하나라도 읽었으면 읽음).
