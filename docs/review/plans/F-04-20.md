# F-04-20 계획 — queue-svc 관제 1초 대기 집계 `QueueAggregate` (빠른 길)

- **무엇**: F-04-2(OPS-190)가 남긴 queue-svc 발행 몫 가운데 `QueueAggregate`(파드마다 1초 집계, `telemetry.queue`)만. 검토 기록이고 규범이 아니다.
- **누가·왜**: 감독 결정(2026-11-23). 파트너 SCR-026 실시간 판매 현황의 '지금 대기·대기열 진입 누적'과 관제 '구역별 잔여석' 칸의 '지금 대기'가 F-04-1 `rt` 표로 이 값을 읽는데, 발행이 없어 0으로 뜬다. `QueueEntryRecord`(사람별 대기 기록)는 F-04-7 범위를 정할 때 함께 정한다.
- **절차**: 빠른 길(ADR-0373 결정 3). 감독 조건: A등급(대기 순번) 경로에는 세는 줄만 더한다(순번·판정·Lua·Redis 키는 그대로), 생산이 막혀도 진입·입장 확정이 느려지거나 실패하지 않는다(그 시험 하나를 꼭 둔다), 11-26·27 부하 측정 전에 합치고 CPU 비용을 한 줄 적는다, 조립은 한 줄 등록.
- **장부 범위**: A-T26 ④의 `QueueAggregate` 몫. `QueueEntryRecord` 몫은 빈칸(F-04-7 때).
- **이 출력을 읽는 곳**: F-04-1 `ops-rt` → `rt.queue_aggregate` → ops-svc 보드 → 파트너 `live-snapshot`(`waiting`·`queueEntries`)과 관제 위젯 `rt-sales.summary`(`waiting`). 분석 원본 적재(F-04-3)는 이 레코드를 건너뛴다.

## 정본 빈칸과 고른 안

1. 세는 때: 진입 = 새 번호를 받은 응답(이미 받은 번호를 다시 준 것·묶음 대기 202는 세지 않는다), 입장 확정 = ADMITTED 가운데 `again`이 아닌 것(저장소의 입장 수와 같은 규칙), 곧 입장 응답 = SOON 응답 수, 빠진 번호 = queue-svc가 직접 빼는 것(대기 취소의 번호 기록, 중복 입장 거절) (추천 적용, 2026-11-23)
2. 남는 한계: 차례 뒤 미입장(NO_CONFIRM)·로비 셔플 묶음이 낸 번호는 queue-svc 요청 길 밖이라 이 집계에 들지 않는다. 그래서 관제·파트너의 '지금 대기'(진입 − 입장 − 빠진 번호)는 그만큼 다를 수 있다. 로비 참가 취소는 번호가 없어 세지 않는다 (추천 적용, 2026-11-23)
3. eventKey: SHA-256('QueueAggregate:파드:회차:칸 밀리초') 앞 16바이트를 UUID 판 8로(같은 칸을 다시 보내면 같은 값, asyncapi) (추천 적용, 2026-11-23)
4. 칸 상한 10,000(회차 × 칸) [가정]: 넘으면 새 칸을 버리고 `telemetry_dropped_total{record="QueueAggregate"}`로 센다 (추천 적용, 2026-11-23)
5. 종료: 서비스를 닫은 뒤 남은 칸(지금 칸 포함)을 내고 버퍼를 2초 [가정] 안에 닫는다 (추천 적용, 2026-11-23)
6. 배포 값: 텔레메트리 Kafka 주소(`PEAKET_TELEMETRY_KAFKA_BROKERS`)와 생산자 스키마 ID 파일(`PEAKET_SCHEMA_IDS_FILE`, 주제 `telemetry.queue-peaket.telemetry.QueueAggregate`)이 queue-svc에 있어야 낸다. 차트 값은 F-09-8(로컬 클러스터) 몫으로 남긴다 (추천 적용, 2026-11-23)
