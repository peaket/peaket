### 1. 끝내는 것과 넘기는 것

- **끝내는 것**

  8. C1-16·GAT-190 잔손: 책임자 이상 표시 목록을 배치 구역으로 거르고 `OVERRIDE_REVIEW`를 빼기.

### 7. 실패 확인 방법

- 기준 트리(계획 커밋, 제품 코드는 `0797989c9`와 같음)에 시험만 더해 돌린다. 새 이름(`decideEntryClose` 등)이 없어 불러오기에서만 실패하는 파일은 동적 불러오기로 시험마다 단언에서 실패하게 쓰거나, 틀린 임시 구현(보고 시각 R−1을 셈, `>=` 대신 `>`, 갈림을 지금 마지막 번호로)으로 단언 실패를 보고 적는다(F-05-5 TR-07). 이미 있는 동작(OVERRIDE 403 등)은 '회귀 고정'으로 통과를 적는다.
- 통합 시험은 `pnpm exec turbo run build --filter=@peaket/ticket-svc^...`(core·purchase도 같다) 뒤 Docker 잠금을 잡고 돌린다. 준비 단계 오류 없이 기대한 까닭(경로 404, 마감 행 없음, 표시 없음)으로만 실패하는지 '실패 확인' 절에 적는다. 한 번도 돌지 않은 통합 시험은 고정하지 않는다(F-05-5 시험 리뷰 2).

### 12. 자주 놓친 결함(docs/architecture.md §8.6 4에서 고름)

- 경계 양쪽(R−1ms·R, R+24h−1ms·R+24h, `knownSeq` s−1·s, `refund_due_at` 같음·뒤, `closedAt` ends+2h−1ms). 시험 값은 상수와 다르게 고른다(예 `ends_at`이 분 경계가 아닌 값).
- 지우거나 옮기는 연산은 건드린 행을 모두(purchase 조건부 갱신, 미보고 건 행).
- 겹친 가드: 마감 한 번은 기본 키와 회차 잠금 둘이 지킨다. 둘 다 있는지 보는 시험(동시 판단)과 업로드 겹침 시험을 둔다.
- 부르는 쪽이 결과를 쓰는지 바깥에서: 마감 행이 업로드 판정에 닿는지, core 값이 ticket 판매 설정 읽기에 닿는지, purchase가 실제로 환급하는지.
- 장애 주입은 실패가 실제로 났는지 단언(대역 호출 수, 트리거 실행 수). '0건'·건너뜀이 통과로 새지 않게 한다(판단에서 건너뛴 회차 수를 단언).
- 시작 파일 조립을 따로 띄워 본다(배경 작업이 실제로 등록되는지).

### 13. 남는 위험

- 역할 유효 끝 전의 보고를 세지 않아, 모든 기기가 온라인이어도 마감은 역할 유효 끝 뒤 첫 판단(최대 1분 [가정])과 앱의 보고(F-05-12) 뒤다. 앱이 보내기 전에는 늘 TIMEOUT으로 마감된다.
- 큐 보고를 믿는다. 기기가 0이라 거짓 보고하면 남은 기록은 '마감 뒤 도착'으로 올라온다(정본 §7.3의 알려진 한계와 같은 종류).
- purchase 연결은 대역으로만 본다. 마감 뒤 이미 환급된 취소 티켓의 늦은 기록은 되돌리지 않는다(d5 §7.6, 정본 그대로).

**정본 빈칸 셋 판정(계획 담당에게)**

1. purchase '오래된 차례'의 정렬 기준: 정본이 정하지 않았다. 추천 — 회차마다 기다리는 행의 가장 이른 `refund_due_at` 차례, 같으면 회차 ID(상한 행은 공연 시작 + 50시간이라 공연 시작 차례와 같고, 환급이 급한 회차가 먼저 온다). 지금 계약 시험(`entry-close-due-store-contract.ts:77-91`)은 접수 시각과 `refund_due_at`을 같은 차례로 심어 어느 기준이든 통과하므로 구현을 묶지 않는다. 다만 RV-06의 머리 막힘을 함께 정해야 한다.
2. 마감 시각은 알지만 당길 행이 0일 때 지표 결과: 정본 `moved·not_closed·unavailable` 어디에도 꼭 맞지 않는다(기다리는 행은 `refund_due_at` > 지금 ≥ 마감 시각이라 보통 0이 될 수 없고, 동시 변경이나 두 서비스 시계 차이에서만 생긴다). 추천 — 회차 판단 결과로 보고 `moved`로 센다(새 이름표를 만들지 않는다). 지금 시험은 이 경우를 단언하지 않으므로 정본을 한 줄 정한 뒤 단위 시험 한 경우를 더한다.
3. core 경로 틀린 본문 400/422: guidelines §12가 이미 정한다 — 형식 틀림(빠짐·타입·오프셋 없는 시각)은 400, 422는 `closedAt` < `ends_at` + 2시간뿐. 정본 빈칸이 아니라 시험이 넓게 받은 것이므로 RV-04로 고친다. offline-gate §7.3 'core 알림'에 '본문 형식이 틀리면 400(guidelines §12)' 한 마디를 더하면 더 분명하다.

- 경계값: 보고 받은 시각 R−1·R, 기기 0대 판단 R−1·R, R+86,400,000−1·R+86,400,000, 마감 시각은 잠금 뒤 시각(`clockNow`를 판단 시각과 다르게 골랐다), `closedAt` = 역할 유효 끝 −1ms 422·= 200, `refund_due_at` 같음·1ms 뒤, 회차 50·20개 경계. 값은 모두 정본에서 숫자로 적었고 `ends_at`은 분 경계가 아니다.
