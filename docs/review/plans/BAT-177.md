# BAT-177 계획·기록(월렛 첫 화면 LCP 층 원인 고침: OPEN[52] (나))

- **무엇**: OPEN[52] (나)다. 월렛 첫 화면(`/my/tickets`)의 Lighthouse LCP가 회차마다 몇 개의 층(약 5,400~6,200 / 6,990 / 7,290 / 8,040ms)으로 갈리는 원인을 고친다. ① Lighthouse 기록 파일에 LCP 요소와 분해(TTFB·불러오기 지연·불러오기·그리기 지연)를 남기고 ② 첫 화면의 LCP가 늦게 오는 요청(동적 QR 덩어리·서비스 워커 미리 저장·그림)에 기대지 않게 고친 뒤 ③ BAT-176의 임시 알림을 되돌린다. 한도 7,255ms와 기준선 5,804ms는 그대로 둔다.
- **쉬운 말**: LCP는 화면에서 가장 큰 글·그림이 그려지기까지의 시간이다. 지금 월렛 첫 화면은 서버가 먼저 그리는 QR 뼈대 그림이 가장 큰 요소인데, 그 그림과 첫 화면이 ① 300ms 뒤 받는 QR 덩어리 ② 1.5초 뒤 받는 오프라인 배너·서비스 워커 덩어리 ③ 서비스 워커가 한꺼번에 받는 100여 개 파일과 네트워크를 다툰다. 그래서 같은 코드로도 잴 때마다 LCP가 몇 층으로 갈린다. 이 묶음은 QR 뼈대를 첫 HTML에 넣어 그림 요청을 없애고, 무거운 덩어리는 첫 화면이 다 그려진(`load`) 뒤에 받게 한다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane2`, 가지 `feature/lane2-BAT-177`, 출발 `origin/develop` `ebfb61e2`. 2026-11-19 계획 담당이 썼고 시험·제품 코드는 쓰지 않았다. 읽은 것: `docs/lanes/lane2.md` 8~10줄, `docs/BUILD_ORDER.md` BAT-174~176 행, `docs/review/plans/BAT-176.md`, `docs/frontend.md` §5.8(1236~1262줄), `docs/PROGRESS.md` OPEN[52] 줄, `apps/web` 월렛 화면(목록·티켓 펼침·서비스 워커 등록), `tools/web-checks/budgets`(spec·limits·report·pages·기준선), `docs/review/measurements/R-562-budget.md`·`R-563-budget.md`.
- **등급**: C(`docs/BUILD_ORDER.md` '기능 묶음' 표에 넣을 BAT-177 행). 화면의 첫 그림 시점과 검사 도구의 기록 칸을 바꾸지만 돈·좌석 홀드·대기 순번에 닿지 않는다. 단계는 `-`, 장부 범위는 `-`, WBS는 0.25일 [가정]이다(감독이 나중에 BUILD_ORDER에 넣는다).
- **차례**: 정방향(`Batch-Order: impl-first`, ADR-0281 결정 5). 계획 → 구현 I1(첫 화면 고침 + `lcp.mjs` + `report.mjs` 표, 알림은 그대로) → 시험(LCP 기록 칸·판정 고리·시험, 실패 확인) → 초안 PR CI에서 LCP 요소·분해·다섯 회 값 확인 → 구현 I2(한도 안이면 알림 되돌리기) → 시험 결과 → 리뷰 → 검증 → 기록(감독). `lighthouse.spec.mjs`는 시험 파일이라 시험 담당이 맡는다. I1 측정이 7,255ms를 넘으면 I2를 하지 않고 감독에게 보고한다(한도를 바꾸지 않는다).
- 이 파일은 역할마다 자기 절만 쓴다: 계획(아래), 실패 확인·시험 결과(시험), 시험 이의(구현), 리뷰, 검증, 담당 표·기록(감독). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.

## 감독에게

1. **BAT-176 측정 파일과 감독 공유 노트가 이 작업 폴더에 없다.** `docs/review/measurements/BAT-176*`과 `lane2-open-wallet-lcp-2026-11-19.md`를 찾지 못했다(`feature/lane2-BAT-176` 가지에도 계획 파일만 있다). 그래서 최신 44회 값의 LCP 요소·분해와 러너 CPU 상관(−0.58)의 원자료를 직접 읽지 못했다. 이 계획은 `R-563-budget.md`(LCP 요소가 QR 뼈대 그림 48,672px², 3회 값 4,508 / 6,236 / 7,893ms)와 `docs/frontend.md` §5.8의 층 값으로 썼다. 노트가 있으면 구현 전에 이 파일에 붙이거나 구현 담당에게 주기 바란다. 없으면 I1과 시험 커밋을 올린 초안 PR CI 산출물이 그 자리를 대신한다.
2. **새 ADR을 쓰지 않는다.** 방향은 소유자 결정 OPEN[52]와 `docs/frontend.md` §5.8이 이미 정했고, 이 묶음은 그 문장을 코드로 옮긴다. ADR 0304~0306은 비워 둔다. 구현 중 방향을 바꾸는 결정(예: 한도·기준선 변경, HTML 압축· critical CSS 파이프라인 개편)이 나오면 멈추고 묻는다.
3. **알림 되돌리기는 측정을 통과한 뒤에만 한다.** I1은 BAT-176의 `WARN_ONLY`를 그대로 두고, 시험 커밋이 넣은 LCP 기록 칸과 함께 초안 PR CI를 돌린다. 월렛 LCP 다섯 회 가운데 값이 7,255ms 이하이고 값의 층이 눈에 띄게 줄면 I2에서 알림을 지운다. 넘으면 알림을 남기고 감독에게 보고한다(강제로 지우지 않는다).
4. **첫 JS 예산이 빠듯하다.** `/my/tickets` 첫 JS는 2026-11-14 R-563에서 161.4kB, 웨이브 7 측정에서 161.5kB였고 한도는 161.6kB(기준선 160.6 + 1)다. `load` 뒤로 미루는 작은 도우미가 첫 묶음에 들어가므로 `web / budgets` 첫 JS 검사에서 161.6kB를 넘지 않는지 본다. 넘으면 도우미를 `WalletClient.tsx` 안으로 인라인하거나 기존 코드를 줄여 맞춘다. 기준선을 올리지 않는다(올려야 하면 감독에게 묻는다).
5. **화면 변경이므로 브라우저 확인이 필요하다.** 첫 HTML(인라인 그림, preload 없음), `load` 전후 네트워크, QR·서비스 워커 등록, 오프라인 새로고침을 본다(아래 11). 기록은 `docs/review/browser-check/` 폴더에 묶음 ID BAT-177 이름으로 남긴다.
6. **BUILD_ORDER는 손대지 않았다.** BAT-177 행 문안은 보고에 적었다. 감독이 나중에 '기능 묶음' 표 BAT-176 행 아래에 넣는다.
7. **정본은 고치지 않았다.** 고칠 자리와 내용만 아래 10에 적었다. 계획 단계에서 정본을 고치지 않는 규칙(이번 지시)을 따랐다. 구현·기록 담당이 그 자리를 고친다.

## 계획

### 1. 범위

- **한다**:
  - Lighthouse `web / budgets`의 기록 파일(`reports/lighthouse/<화면>.json`)에 회차마다 LCP 요소(`selector`·`snippet`·`nodeLabel`·`boundingRect`)와 네 구간(TTFB·불러오기 지연·불러오기·그리기 지연)을 남긴다. 잡 요약(`report.mjs`)에도 화면별 가운데 값 회차의 LCP 요소·분해 표를 더한다.
  - 월렛 첫 HTML의 QR 뼈대 그림을 `public/wallet-qr-skeleton.png` 요청이 아니라 data URI로 인라인한다. 첫 화면의 LCP 후보가 그림 요청에 기대지 않게 한다.
  - QR 덩어리(`DeviceQr`)와 오프라인 배너·서비스 워커 덩어리(`OfflineBanner`/`WalletPwa`)를 고정 300ms·1,500ms 타이머가 아니라 `window.load` 뒤에 받는다. 첫 화면이 다 그려지기 전에 늦은 스크립트가 네트워크·메인 스레드를 다투지 않게 한다. `load`가 이미 지났으면 바로 받는다.
  - BAT-176의 월렛 LCP 임시 알림(`WARN_ONLY`·`loadVerdict`·기록의 `verdict`/`warnOnly`·`report.mjs`의 '알림만')을 지우고, 한도를 넘으면 다시 그대로 실패하게 되돌린다. **I1 측정이 7,255ms 이하일 때만 한다.**
  - 위 동작을 `node --test` 단위 시험과 브라우저 확인으로 고정한다.
- **그대로 둔다**:
  - `lighthouse-baseline.json`의 월렛 `lcpMs` 5,804, `LOAD_MARGIN`(시간 25%·CLS 0.02), `RUNS` 5, `loadLimit`·`median`, CLS 0.1·총 차단 시간 200ms, 다른 일곱 화면의 세 지표 판정. 한도 7,255ms는 계산 결과 그대로다.
  - 서비스 워커의 범위(`/my/tickets`), 미리 저장 목록, 갱신 보류·`no-store` 거르기, 오프라인 새로고침 동작. 바뀌는 것은 **등록을 시작하는 때**뿐이다.
  - 월렛 화면의 눈에 보이는 모양(QR 뼈대 그림·문구·자리·400px 높이). 인라인은 같은 PNG 바이트를 HTML에 넣는 것이라 그림은 같아야 한다.
  - 첫 JS 예산 161.6kB와 `/my/tickets` 경로의 다른 성능 예산.
- **하지 않는다**:
  - (가) 기준선 다시 잡기·한도 넓히기. I1이 7,255ms를 넘으면 한도를 바꾸지 않고 감독에게 보고한다.
  - HTML 압축·해시 서버 스트리밍·critical CSS 인라인·글꼴 파이프라인 개편. 이 묶음은 첫 화면이 **늦은 요청에 기대지 않게** 하는 데까지만 한다. I1 산출물이 `그리기 지연`이 아니라 `TTFB`/`불러오기 지연` 지배를 보이면 그 자료와 함께 별도 묶음으로 넘긴다(아래 12의 정할 것 4).
  - 서비스 워커 미리 저장 목록을 줄이거나 범위를 바꾸는 일. 오프라인 동작을 바꾸지 않는다.
  - BAT-178(바로가기 초점), BAT-179(Next.js 16.4.5), BAT-167, BAT-173, BAT-172, BAT-182, BAT-421. 이번에 계획하지 않는다.
  - 마이그레이션·새 표·새 인덱스·새 외부 연동·새 저장소. 없다.
  - Docker. 웹 빌드·Lighthouse 예산은 로컬에서 계획만 하고, 실제 실측은 초안 PR CI에서 한다.

### 4. 공개 인터페이스(시험 담당이 기댄다. 이름은 구현이 이대로 쓴다)

- **`afterLoad(run: () => void): () => void`** (`apps/web/src/shared/lib/after-load.ts`)
  - `document.readyState === 'complete'`면 그 자리에서 `run()`을 부르고 빈 정리 함수를 돌려준다.
  - 아니면 `window.addEventListener('load', run, { once: true })`로 한 번만 부른다. 정리 함수는 아직 `load` 전이면 듣기를 뗀다.
  - `run`이 던져도 `load` 듣기는 이미 `once`로 빠졌다. `run`의 예외를 삼키지 않는다.
  - `window`·`document`가 없는 곳(SSR)에서는 부르지 않는다. 호출은 `useEffect` 안에서만 한다.
- **`WALLET_QR_SKELETON: string`** (`apps/web/src/widgets/ticket-wallet/ui/qr-skeleton.ts`)
  - `data:image/png;base64,`로 시작하고, 디코드하면 PNG 서명(`89 50 4E 47 0D 0A 1A 0A`)이다. 길이는 2,000자 미만 [가정].
  - 이 파일은 서버 컴포넌트(`Wallet.tsx`)만 가져간다. 클라이언트 컴포넌트가 가져가면 첫 JS에 1.2KB가 더해지므로 금지한다.
- **Lighthouse 기록 칸**(`reports/lighthouse/<화면>.json`)
  - `runs[]`마다 `lcp: { element: { selector, snippet, nodeLabel, boundingRect: { width, height } } | null, phases: { ttfbMs, loadDelayMs, loadDurationMs, renderDelayMs } | null, discovery: { label, value }[] | null, renderBlocking: { url, totalBytes, wastedMs }[] | null }` 또는 `lcp: null`.
  - `lcpSummary: { run: number(1부터), lcpMs: number, element: … | null, phases: … | null, elements: string[] } | null`. `run`은 다섯 회를 `lcpMs` 작은 차례로 늘어놓았을 때 가운데(셋째) 회차다. `elements`는 회차마다 selector를 중복 없이 모은 것이다.
  - `lcp`가 없거나 `lcp-breakdown-insight`가 오류면 `lcp: null`로 두고 기록 파일은 쓴다. 월렛만 기록 뒤 `expect.soft`로 실패한다. 다른 화면은 기록만 하고 실패하지 않는다.
- **`readLcp(audits)`·`lcpSummary(runs)`** (`tools/web-checks/budgets/lcp.mjs`)
  - `readLcp`는 `lcp-breakdown-insight`의 `details.items`에서 `type === 'table'`(네 구간)과 `type === 'node'`(요소)를 찾는다. 구간 표의 `duration`은 ms다(초가 아니다). 요소가 없어도 구간만 있으면 구간을 돌려준다.
  - `lcpSummary`는 `runs`의 `lcpMs`로 가운데 회차를 고르고 그 회차의 `element`·`phases`를 쓴다. 회차 값의 평균을 쓰지 않는다(요소가 섞이면 평균이 뜻을 잃는다). 모든 회차가 `lcp: null`이면 `null`.
  - `snippet`의 `data:image/…;base64,…`는 `data:image/png;base64,…`로 줄이고 300자에서 자른다(산출물이 수 KB로 불어나지 않게).
- **`lcpTable(records)`** (`tools/web-checks/budgets/report.mjs`)
  - 표 머리: `화면 | 가운데 회차 | LCP(ms) | 요소 | TTFB(ms) | 불러오기 지연(ms) | 불러오기(ms) | 그리기 지연(ms)`.
  - `lcpSummary`가 없는 기록은 빼고, 모두 없으면 `(LCP 분해 기록이 없다)` 한 줄.
- **`limits.mjs` 공개 이름**: `RUNS`(5)·`LOAD_MARGIN`({ ms: 0.25, cls: 0.02 })·`loadLimit`·`median`·`jsLimit`은 그대로다. `WARN_ONLY`·`kstDate`·`loadVerdict`는 I2 뒤에 없어진다.
- **HTTP·gRPC·DB·API 계약 변경 없음**.

### 11. 브라우저 확인

**필요하다.** 화면의 첫 HTML(인라인 그림·preload 제거)과 동적 조각을 받는 때가 바뀐다. 눈에 보이는 그림은 같아야 하지만, 브라우저에서 첫 화면·QR·서비스 워커·오프라인을 확인해야 한다. 기록은 `docs/review/browser-check/` 폴더에 BAT-177 이름으로 남긴다.

1. 운영 빌드(`apps/web/server/start.mjs`, `web / budgets`와 같은 서버)에서 `/my/tickets`를 처음 연다.
2. 첫 HTML에 `data:image/png;base64,` QR 뼈대 `<img class="wallet-qr-skeleton">`가 있고 `wallet-qr-skeleton.png` preload가 없다. 그림은 지금과 같은 312×156 자리다.
3. DevTools Network에서 `load` 전에 `/serwist/sw.js`·`/serwist/…` 미리 저장 요청과 QR 동적 덩어리(`DeviceQr`)가 없고, `load` 뒤에 나타난다. `sw.js` 등록은 `load` 뒤 시작한다.
4. QR 자리에 처음에는 서버가 그린 등록 안내·뼈대 그림이 보이고, `load` 뒤 실제 `DeviceQr`(키 없음 카드 또는 QR)로 바뀐다. 400px 높이가 유지되어 layout shift가 없다.
5. 월렛 워커가 활성화된 뒤 오프라인으로 새로고침해도 월렛·안내·오프라인 배너가 남고 콘솔 오류가 0이다. 기존 `reflow/wallet-sw.spec.mjs`와 같은 시나리오다.
6. 412×823(모바일)와 데스크톱 폭에서 그림·문구·자리가 시각 회귀 기준과 같다. 다르면 인라인 data URI가 같은 PNG인지, `className` 추가가 레이아웃을 건드리지 않았는지 본다.
7. 브라우저 확인에서 LCP를 판정하지 않는다. LCP 요소·분해·다섯 회 값은 초안 PR CI `budgets-reports` 산출물로 본다(브라우저 확인은 '첫 화면이 늦은 요청을 기다리지 않는가'를 본다).

### 8. 판정

C등급 표본 25개 가운데 **18개를 잡고 7개를 놓쳤다**. 값 판정(T3·T5·T8)과 LCP 읽기(T1·T2)는 촘촘하다. 반면 **spec이 실제로 그 판정을 쓰는지**를 보는 시험(T7·T9·T10)과 **첫 JS 번들 경계**(T6)가 약하다. 놓친 넷(N2·N4·N5·N7)은 CI가 초록이어도 실제 회귀를 막지 못하는 결함이고, 이 묶음이 만든 새 결함이 아니라 **시험이 집행 경로를 묶지 못한 빈틈**이다.
