# 작업 계획: BAT-061(HOT-420 메시 매니페스트·포트별 허용 정책과 같은 표의 NetworkPolicy)

- **무엇**: HOT-420(wbs 2.11.2 ①)의 작업 목록이다. Istio 앰비언트(노드마다 도는 프록시가 서비스 사이 연결을 암호화하는 메시 방식) 매니페스트와 정책(메시 전체 STRICT, 최소 TLS 1.3, `cacerts`), 디스커버리(웨이포인트를 붙일 Service), 포트별 인가 정책, 같은 표로 만드는 메시 없는 실행의 NetworkPolicy(쿠버네티스가 파드 사이 연결을 막는 규칙)를 다룬다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **바탕**: 작업 폴더 `D:/ticketpass-b061`, 가지 `feature/lane1-BAT-061`, 출발점 `d686e49d`. 구현 전 트리(분리 HEAD, 커밋하지 않음)는 `D:/ticketpass-b061-base`. 두 폴더 모두 `pnpm install --frozen-lockfile`을 했다(뿌리 개발 의존성 `yaml`이 있다). 지시서는 `node tools/ci/brief.mjs --batch BAT-061`(만든 때 `d686e49d`). 2026-11-18 계획 담당 `bat061-plan-ce02fed3`(claude-opus-5-5)가 썼고, 시험·제품 코드는 쓰지 않았다.
- **동시에 도는 묶음**: BAT-010(identity-svc·purchase-svc 탈퇴 참여자, `D:/ticketpass-b010`). 그쪽 파일(`services/identity-svc`·`services/purchase-svc` 코드, `docs/api/proto`, `docs/api/openapi.yaml`)은 고치지 않는다. 이 묶음은 proto를 읽기만 한다.
- **등급**: B(배포·운영). 실패 증명은 실패 상황 시험, 틀린 구현 표본(아래 8, 28개), 판정 기준 대조 표본이다(docs/architecture.md §8.6 3).
- **차례**: 정방향 묶음이다(이 계획 커밋에 `Batch-Order: impl-first`). ADR-0283 결정 2의 짧은 고리: 계획 → 구현 → 시험(구현 전 트리에서 실패 확인을 같은 커밋에) → 리뷰 → 리뷰 반영 시험(재현 시험과 실패 확인 한 커밋) → 리뷰 반영 구현(고침과 시험 결과 한 커밋) → 검증(고친 곳 확인 포함) → 기록. 리뷰 반영 계획 커밋은 없고(리뷰 절의 지적 목록이 고칠 목록), 다시 리뷰는 보안 높음만 한다. 목표 커밋 8개 안팎.
- **정본**: [ADR-0285](../../adr/0285-mesh-port-allow-source-generated-policies.md)(이 커밋에서 새로 씀), [ADR-0082](../../adr/0082-istio-ambient-mesh-app-boundary-meshless-portfolio-runs.md) 결정 1·2·4·6, docs/architecture.md §5 '메시와 앱의 책임 경계'·'포트별 허용 표'·'메시 기본값 덮어쓰기'·'메시 없는 실행', docs/devops.md §14 D-T36·§5.2 '네임스페이스 지도', docs/api/proto/README.md §2·§3, docs/architecture.md §8.6 4 '묶음 절차'·'역할 나누기'·'자주 놓친 결함'.

## 감독에게

방향을 바꾸는 결정은 정하지 않았다. 아래는 고르지 않은 것과 알릴 것이다.

1. **Istio CRD 스키마 검사 도구(새 외부 도구)는 받지 않았다.** 정적 시험은 YAML을 읽어 구조와 값을 견준다(ADR-0285 결정 13). 그래서 Istio·Gateway API 객체의 칸 이름 오타(예 `principal`과 `principals`)는 시험이 그 칸을 직접 읽는 곳에서만 잡힌다. kubeconform 같은 검사기와 Istio CRD JSON 스키마를 받기로 하면 새 도구 결정이다(BAT-060 계획 13절이 넘긴 것).
2. **kind에 Istio를 올리지 않는다(묶음 표 비고 그대로).** 메시 아래 동작(mTLS, 신원 인가, TLS 판, `cacerts`가 없을 때 istiod의 동작)은 운영 확인 몫으로 남는다(ADR-0285 결정 11·12). kind는 메시 없는 NetworkPolicy만 본다.
3. **업무 gRPC는 전용 Service `<워크로드>-grpc`로 받는다(ADR-0285 결정 5, 추천 적용).** 표의 REST 행('웨이포인트를 지나지 않는다')을 지키려면 웨이포인트를 기본 Service에 붙일 수 없어서다. 그래서 업무 gRPC를 부르는 쪽의 배포 값 주소가 `<워크로드>-grpc:<포트>`로 바뀐다. 지금 저장소에서는 `deploy/workloads/ops-svc/values.yaml`의 `PEAKET_IDENTITY_GRPC_URL` 한 줄이고(구현 몫), 나머지는 배포 상태 단계(BAS-140)가 값을 쓸 때 따른다.
4. **BAT-010과의 합치기.** 생성기는 `docs/api/proto/peaket/**/*.proto`의 서비스·메서드를 읽고, 원천에 없는 proto 서비스나 메서드가 있으면 `--check`가 실패한다(fail closed). BAT-010이 proto에 서비스·메서드를 더하면 다시 쌓은 트리에서 `node tools/ci/mesh-policies.mjs --check`와 정적 시험이 실패한다. 합칠 때 원천에 그 줄(부르는 쪽)을 더해야 한다(이 묶음의 구현 담당이나 다음 묶음).
5. **정본의 낡은 문장 하나를 고쳤다.** docs/architecture.md §3.2 REST 행은 내부 HTTP 예외가 '하나'라고 적었지만, 코드에는 내부 HTTP 호출이 14쌍 있다. 목록을 ADR-0285 결정 9에 두고 §3.2 REST 행에 한 구절을 더했다. §3.2의 나머지 문장(내부 서비스끼리는 REST를 쓰지 않는다)을 다시 쓸지는 정리 목록 후보다(아래 11).

### 2. 장부 범위 다시 보기(2026-11-18)

- **결과: 범위는 D-T36 ①~⑦ 일곱 그대로다.** 묶음 표 BAT-061 줄의 범위 칸은 바꾸지 않았고 비고에 다시 본 결과를 적었다(docs/BUILD_ORDER.md:60). `node tools/ci/ledger.mjs --batch BAT-061`: 빈칸 7, 등급 B 7.
- 메시·mTLS·TLS 1.3·NetworkPolicy를 적은 ASVS 행(`docs/security/asvs/*.md`, '메시지'는 뺌)을 장부 판정과 함께 모두 봤다. 빈칸·ID만인 행과 다른 단계인 행을 나누면:
  - **'(운영 설계만)'이라 '다른 단계'인 행(뺌)**: auth·control-tower·forensic-replay·payment·queue-admission·seat-hold의 `v5.0.0-12.1.3`(mTLS 인증서를 믿은 뒤 신원으로 인가), `12.3.3`(내부 연결을 평문으로 돌리지 않음), `12.3.4`(내부 CA만 믿음). 이 행들이 판정하는 것은 메시가 실제로 연결을 암호화하고 인증서를 검증하는 동작이다. 이 묶음은 매니페스트와 정적 시험만이고 kind에 Istio를 올리지 않으므로 그 동작을 실패할 수 있게 보이지 못한다. 매니페스트는 만들지만 행의 판정은 운영 확인 몫이다.
  - **아직 코드가 없는 기능의 행(뺌)**: analytics·notify·settlement의 `12.1.3`·`12.3.3`(빈칸), analytics `12.1.1`(ID만). 장부의 기본 코드 영역이 빈 목록이라 어느 시험도 세지 않는다(`tools/ci/ledger.mjs` `ASVS_DEFAULT_AREA`). 그 기능의 서비스가 생길 때 판정한다.
  - **내용이 '운영 설계만'과 같은데 표시가 없는 행(뺌, 정리 목록 후보)**: offline-gate `12.3.3`·`12.3.4`(auth의 같은 행과 글이 같다), offline-gate·control-tower·forensic-replay·queue-admission `12.3.2`(TLS 클라이언트가 서버 인증서를 검증. 앱의 Aurora·외부 API TLS와 '서비스 사이는 메시가 검증'이라 이 묶음의 정책이 아니다). 코드 영역(apps/scanner 등)도 이 묶음의 파일과 닿지 않는다. '(운영 설계만)' 표시를 맞추는 일은 아래 11.
  - **다른 묶음의 행(뺌)**: delivery `13.2.4`(나가는 연결 허용 목록, PRF-192), delivery `13.2.1`(Pod Identity·MSK 역할, BAT-065 D-T30), control-tower `13.2.2`(제어 포트를 ops-svc·런북 Job만 받음)는 이미 '자동 시험'이다. 이 묶음의 D-T36 ④⑤가 같은 규칙을 더 본다.
- 새 ASVS 행을 더하지 않았다. delivery 문서는 V3·V13~V16을 판정 범위로 두고 V12(통신 보안)는 기능 문서가 판정한다. 새 행을 두면 묶음 범위가 늘고 같은 요구를 두 곳에서 판정하게 된다(ADR-0283 결정 6).
- §8.7 실패 목록 셋: 새 외부 연동·저장소가 없어 쓸 줄이 없다. `cacerts`를 넣는 External Secrets·Secrets Manager는 정본에 이미 있는 애드온이고(docs/devops.md §5.2, docs/architecture.md §8 '소스코드 내 시크릿'), 앱이 부르는 외부 호출이 아니다.

### 4. 바른 동작과 정본 근거

값은 옮겨 적지 않고 위치만 적는다. 기대값(부르는 쪽 목록)은 시험 담당이 아래 정본에서 직접 뽑는다.

**4.1 원천(G1)** — ADR-0285 결정 1·6·7·9

1. 원천에 담는 것과 그 출처:
   - 워크로드 목록: docs/architecture.md:743(업무 gRPC를 받는 아홉), :744(게이트웨이 뒤의 서비스: 라우트 `backendRefs`가 가리키는 것 전부. 화면 앱 서버 web·partner 포함, trust-svc), :745(제어 gRPC를 받는 넷). 이 묶음의 워크로드는 그 합(core-svc·identity-svc·payment-svc·purchase-svc·queue-svc·ticket-svc·trust-svc·ops-svc·admission-ctrl·image-worker·seatmap-worker·web·partner)이다. 표 밖 워크로드(알림·웹훅 발송 워커, 릴레이, realtime-gw)는 넣지 않는다(ADR-0285 결정 4).
   - 네임스페이스: docs/devops.md §5.2 '네임스페이스 지도'(docs/devops.md:422-436). 라우트 `backendRefs`의 네임스페이스와 같아야 한다.
   - 업무 gRPC 부르는 쪽: proto 서비스마다 docs/api/proto/README.md:39('부르는 쪽 확인'), 메서드마다 :65-122('호출 목록' 표의 첫 칸), docs/architecture.md:743 넷째 칸과 :290('ADR-0171·0172가 더한 gRPC 호출'). 한 서비스 안에서 메서드마다 부르는 쪽이 다르면 메서드마다 적는다(예 `peaket.ticket.v1.TicketService`, `peaket.payment.v1.PaymentService`, `peaket.identity.v1.SessionService`). 정본끼리 다르면 '시험 이의'로 올린다.
   - `AdminAuthzService`(identity-svc) 부르는 쪽: docs/architecture.md:290, docs/api/proto/README.md:39 끝 문장(여덟 서비스와 admission-ctrl).
   - REST 포트의 내부 HTTP 부르는 쪽: ADR-0285 결정 9 표. trust-svc REST는 gw-fan 하나(같은 결정 끝, docs/architecture.md:744).
   - 제어 gRPC 부르는 쪽: docs/architecture.md:745(ops-svc·비상 런북 Job).
   - 지표 포트 부르는 쪽: docs/architecture.md:746(클러스터 Prometheus).
   - 포트 번호: ADR-0285 결정 6. 업무 gRPC 기본값의 출처는 서비스 코드의 기본 상수(identity·payment·queue·trust는 50051, ticket-svc `DEFAULT_TICKET_GRPC_PORT`)다.
   - 신원: ADR-0285 결정 7. 게이트웨이 프록시의 서비스 계정 이름은 구현 담당이 Envoy Gateway v1.10.0 소스(`internal/infrastructure/kubernetes/proxy`의 자원 이름 규칙)에서 확인해 원천에 적고, 그 규칙과 확인 날짜를 docs/infra.md:535 끝에 한 구절로 적는다.

   ```yaml
     <이름>:
       principal: cluster.local/ns/<네임스페이스>/sa/<서비스 계정>
       meshless:                 # 메시 없는 NetworkPolicy의 출처 칸 하나(둘 다 맞아야 한다)
         namespace: <네임스페이스>
         podLabels: { <키>: <값> }   # 없으면 네임스페이스만 본다(비상 런북 Job)
   workloads:
     <워크로드>:
       namespace: <네임스페이스>
       serviceAccount: <서비스 계정>   # 기본은 워크로드 이름
       podLabels: { app.kubernetes.io/name: <워크로드>, app.kubernetes.io/component: service }
       ports:                    # 받는 통신이 없으면 {}
         rest:    { port: 8080, callers: [<이름>, …] }     # 게이트웨이는 적지 않는다(생성기가 라우트에서 더한다)
         grpc:    { port: 50051, services: { <proto 전체 이름>: [<이름>, …] | { methods: { <메서드>: [<이름>, …] } } } }
         control: { port: 50061, callers: [ops-svc, ops-breakglass] }
         metrics: { port: 9464, callers: [prometheus] }
   ```

   - 원천이 부르는 쪽으로 적은 이름은 모두 `callers`에 있어야 한다. 워크로드도 부르는 쪽이면 `callers`에 같은 이름으로 있다.
   - 게이트웨이(`gw-queue`·`gw-fan`·`gw-partner`·`gw-ops`·`gw-scanner`)는 `callers`에 있고, 메시 없는 고르개는 네임스페이스 `envoy-gateway-system`과 라벨 `gateway.envoyproxy.io/owning-gateway-name: <게이트웨이>`·`gateway.envoyproxy.io/owning-gateway-namespace: envoy-gateway-system`이다(ADR-0285 결정 7, 지금 `tools/local/cluster.mjs`가 같은 라벨로 프록시를 고른다).

**4.2 생성기(G1)** — ADR-0285 결정 1·2·4·8

1. 읽는 것: 원천, `deploy/gateways/` 맨 위의 `*.yaml`(하위 폴더 `routes/`·`controller/`·`test/`는 읽지 않는다)의 모든 `HTTPRoute`(생성 파일 `*.routes.yaml`과 손으로 쓴 `gw-*.yaml` 둘 다. 예 `gw-fan.yaml`의 web 백엔드, `gw-queue.yaml`의 queue-svc 백엔드)와 `SecurityPolicy`의 `jwt.providers[].remoteJWKS.uri`, `docs/api/proto/peaket/**/*.proto`의 `package`·`service`·`rpc` 이름.
2. REST 포트의 허용 게이트웨이: HTTPRoute의 `parentRefs` 게이트웨이마다, 그 라우트 규칙의 `backendRefs`(종류 Service, 네임스페이스·이름·포트)가 가리키는 워크로드. `remoteJWKS.uri`가 `http://<워크로드>.<네임스페이스>.svc.cluster.local:<포트>/…`이면 그 SecurityPolicy가 붙은 게이트웨이도 그 워크로드의 그 포트에 더한다. 백엔드 Service 이름 = 워크로드 이름이다. 원천에 없는 워크로드, 원천과 다른 네임스페이스·포트면 오류(끝 코드 1).
3. proto 대조: proto의 모든 서비스(`peaket.control.v1.ControlReceiver` 뺌)가 원천의 어느 한 워크로드 `grpc.services`에 있고, 그 워크로드는 패키지로 정한 받는 쪽이다(ADR-0285 결정 1). 원천의 서비스·메서드 이름이 proto에 없으면 오류. 메서드로 나눈 서비스는 proto의 모든 메서드가 적혀 있어야 한다(빠진 메서드가 있으면 오류. 새 메서드를 더하면 부르는 쪽을 정하게 한다). 정본에 부르는 쪽이 없는 메서드(예 `TicketService/VoidTickets`, docs/api/proto/README.md §3 표에 없음)는 빈 목록으로 적고 규칙을 만들지 않는다(아무도 부르지 못함). 그런 메서드는 '시험 결과'에 목록으로 남긴다.
4. 운영 오버레이 출력(`policies.yaml`), 워크로드마다:
   - 받는 쪽 노드 프록시 정책 `<워크로드>-ports`: `security.istio.io/v1` `AuthorizationPolicy`, 네임스페이스 그 워크로드, `spec.selector.matchLabels` = 원천 `podLabels`, `action: ALLOW`, 규칙은 포트마다 하나(`to: [{ operation: { ports: ["<포트>"] } }]`, `from: [{ source: { principals: [...] } }]`, 주체는 이름 차례로 정렬). 업무 gRPC 포트의 주체는 그 워크로드의 웨이포인트 하나다. 받는 통신이 없으면 `rules` 없는 정책이다. 규칙에 `from`이나 `to.operation.ports`가 빠진 것은 만들지 않는다. `namespaces`·`ipBlocks` 출처는 쓰지 않는다(주체만).
   - 업무 gRPC를 받는 워크로드: 웨이포인트 `<워크로드>-waypoint`(`gateway.networking.k8s.io/v1` `Gateway`, `gatewayClassName: istio-waypoint`, 라벨 `istio.io/waypoint-for: service`, 듣는 곳 `{ name: mesh, port: 15008, protocol: HBONE }`), Service `<워크로드>-grpc`(업무 gRPC 포트 하나, 포트 이름 `grpc`, `appProtocol: grpc`, `targetPort` 같은 번호, 고르개 = 원천 `podLabels`, 라벨 `istio.io/use-waypoint: <워크로드>-waypoint`), 웨이포인트 정책 `<워크로드>-waypoint-callers`(`targetRefs: [{ group: gateway.networking.k8s.io, kind: Gateway, name: <워크로드>-waypoint }]`, `action: ALLOW`, 서비스(또는 메서드)마다 규칙 하나: `to: [{ operation: { paths: ["/<패키지>.<서비스>/*"] } }]`(메서드면 `/<패키지>.<서비스>/<메서드>`), `from` 주체 목록).
   - 생성한 객체는 모두 라벨 `peaket.io/generated-by: mesh-policies`·`peaket.io/workload: <워크로드>`(ADR-0285 결정 3).
5. 메시 없는 출력(`meshless-networkpolicies.yaml`), 워크로드마다 NetworkPolicy `<워크로드>-ports`: `podSelector.matchLabels` = 원천 `podLabels`, `policyTypes: [Ingress]`, 규칙은 포트마다 하나(`ports: [{ protocol: TCP, port: <포트> }]`). 출처는 부르는 쪽마다 한 칸이고, 그 칸 안에 `namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: <ns> } }`와 (있으면) `podSelector: { matchLabels: … }`를 함께 둔다(같은 칸 = 둘 다 맞아야 함). 업무 gRPC 포트의 출처는 그 워크로드의 모든 서비스·메서드 부르는 쪽의 합이다(웨이포인트 없음, ADR-0285 결정 8). 받는 통신이 없으면 `ingress: []`. 출처나 포트가 빈 규칙은 만들지 않는다.
6. 출력은 정해진 차례(워크로드 이름, 포트 번호, 이름)로 쓰고, 두 번 `--write`해도 바이트가 같다. 파일 머리에 '생성 파일이다. 손으로 고치지 않는다(원천과 만드는 명령)' 주석을 단다(`deploy/gateways/gw-fan.routes.yaml` 머리와 같은 꼴).
7. 명령줄: `node tools/ci/mesh-policies.mjs --write|--check [--root <저장소>]`. 끝 코드 0(`--write`는 씀, `--check`는 같음), 1(`--check` 다름, 또는 원천·라우트·proto 대조 오류. 까닭을 `막음: <파일>: <까닭>` 줄로 모두 찍는다), 2(인자 오류, 모르는 인자, `--write`·`--check`가 둘 다 없거나 둘 다 있음). 정책을 하나도 만들지 못했거나 라우트를 하나도 읽지 못하면 1이다(빈 결과가 통과로 새지 않게).

**4.3 메시 바탕 매니페스트(G4)** — ADR-0285 결정 10~12

1. `deploy/platform/mesh/namespaces.yaml`: Namespace 객체마다 라벨 `istio.io/dataplane-mode: ambient`(네임스페이스 목록은 ADR-0285 결정 10). `istio-system`·`kube-system`은 없다.
2. `deploy/platform/mesh/peer-authentication.yaml`: `security.istio.io/v1` `PeerAuthentication` `default`, 네임스페이스 `istio-system`, `spec.mtls.mode: STRICT`, 고르개·`portLevelMtls` 없음. `deploy/` 아래에 다른 PeerAuthentication은 없다.
3. `deploy/platform/mesh/istiod-values.yaml`: `meshConfig.meshMTLS.minProtocolVersion: TLSV1_3`, `meshConfig.trustDomain: cluster.local`. 다른 메시 기본값 덮어쓰기(재시도·추적 등)는 이 묶음에서 넣지 않는다(아래 11).
4. `deploy/platform/mesh/cacerts.yaml`: `external-secrets.io/v1` `ExternalSecret`, 네임스페이스 `istio-system`, `target.name: cacerts`, `secretStoreRef: { kind: ClusterSecretStore, name: aws-secrets-manager }`, `data`가 키 넷(`ca-cert.pem`·`ca-key.pem`·`root-cert.pem`·`cert-chain.pem`)을 Secrets Manager 경로 `peaket/<환경>/mesh/cacerts`의 같은 이름 칸에서 받는다(환경 이름 자리는 오버레이가 채운다는 주석). 파일에 Secret 객체·`stringData`·PEM 글(`-----BEGIN`)이 없다.

### 6. 시험 목록

- 이름은 ID로 시작하고, D-T36 항목을 보는 시험은 `D-T36 ①`처럼 ID 바로 뒤에 번호를 붙인다(장부가 세는 꼴). 정적 시험과 kind 시험이 같은 번호를 함께 본다.
- 단언 값(포트 번호, 부르는 쪽 목록, 이름)은 정본(위 4.1의 위치, ADR-0285)에서 시험 안에 글로 적는다. 원천 파일이나 생성기 코드에서 가져오지 않는다(원천은 시험의 대상이다).

### 7. 구현 전 트리에서 실패할 것과 볼 수 없는 것

- **실행조차 안 되는 실패라 세지 않는 것**: MS 전부와 MG-01~09(구현 전 트리 `D:/ticketpass-b061-base`에는 원천·생성 파일·생성기가 없다. 파일 없음·모듈 없음으로 끝난다, docs/architecture.md §8.6 7). 이 시험들의 실패는 아래 8의 틀린 구현(검증 담당)과 시험 담당이 손으로 넣는 틀린 구현 몇 개(예 M4·M12·M14·M16·M23)로 본다.
- **구현 전 트리에서 뜻 있게 실패해야 하는 것**: MS-11의 배포 값 사례(`deploy/workloads/ops-svc/values.yaml`이 `identity-svc:50051`이라 실패), MG-10(`tools-check.yml`·`ci-kind.yml`에 줄이 없고, `changes.mjs`가 `deploy/platform/mesh/`를 `tools`·`kind`로, `docs/api/proto/`를 `tools`로 고르지 않는다). 시험 담당은 시험 파일을 구현 전 트리에 복사해 돌리고, 결과(실패 수·까닭)를 '실패 확인'에 적은 뒤 복사한 파일을 지운다(`git -C D:/ticketpass-b061-base status` 깨끗하게).
- **이 PC에서 볼 수 없는 것**: MK-01~08(kind·Docker. 지시서대로 이 PC에서 돌리지 않고, 감독이 초안 PR의 CI `kind / kind`로 돌린다). 구현 전 트리의 kind 실패도 볼 수 없다(무대 명령이 없다). kind 몫의 실패 증명은 같은 번호의 정적 시험(MS-01~07)과 틀린 구현 M14·M15(출처 칸 꼴)가 맡고, CI에서 MK가 연결 사례와 거부 사례를 함께 내는지(한쪽만 나오면 실패)를 본다.
- **어디서도 볼 수 없는 것**: 메시 아래 동작(STRICT가 평문을 거절하는지, ztunnel이 포트 규칙을 지키는지, TLS 판, `cacerts`가 없을 때 istiod 동작, 게이트웨이 프록시가 실제로 그 서비스 계정 신원으로 보이는지). 운영 확인 몫이다(ADR-0285 결정 11·12, 위 2).

### 10. 시험·구현 지시문에 넣을 '자주 놓친 결함'

docs/architecture.md:1156-1170의 목록을 그대로 넣고, 이 묶음에서 특히 걸리는 것은 아래다.

- 허용·거부 목록은 한 값만 시험하지 말고 목록 밖의 값마다 거부를 본다(게이트웨이 다섯, 부르는 쪽이 아닌 서비스들, 네임스페이스는 같고 라벨이 다른 파드, 라벨은 같고 네임스페이스가 다른 파드).
- 빈 결과가 통과로 새지 않게 한다: 정책 0개, 라우트 0개, 시험 파드 결과 없음, 대역이 죽어 모든 연결이 실패한 실행은 '거부 통과'가 아니라 실패다(같은 실행에 연결 사례가 있어야 한다).
- 단언 값은 정본에서 적고 원천·생성기·코드 상수에서 가져오지 않는다. 포트 번호도 ADR-0285 결정 6의 글로 적는다.
- 판정 함수만 보지 말고 바깥 경계를 본다: CI 파일이 실제로 명령을 돌리는지, `changes.mjs`가 새 폴더를 실제로 고르는지, kind에서 실제 NetworkPolicy로 연결이 막히는지.
- 표준 NetworkPolicy의 출처 칸: 한 칸 안의 `namespaceSelector`와 `podSelector`는 둘 다 맞아야 하고, 두 칸으로 나누면 둘 중 하나만 맞아도 된다. `podSelector`만 있으면 같은 네임스페이스만 본다. 칸이나 포트를 비우면 모두 허용이다(docs/infra.md §9 '나가는 연결 허용 목록의 첫 구현'에서 같은 함정을 막았다).
- Istio ALLOW 정책: 규칙의 `from`이나 `to`를 비우면 그 부분이 '모두'가 된다. 규칙이 하나도 없는 정책은 '아무것도 받지 않음'이다. 이 둘을 헷갈리지 않는다.
- 같은 규칙을 두 곳에서 겹쳐 지키면 하나를 빼는 결함이 가려진다: 운영 쪽은 노드 프록시 정책(포트)과 웨이포인트 정책(경로)이 겹친다. 둘을 따로 단언한다(MS-02와 MS-09).
- 시험의 값이 코드 상수와 같으면 상수를 잘못 쓴 결함이 숨는다: kind 시험의 시간 한도(3초)는 대역·생성기 상수와 상관없이 정한다.
- kind에서 게이트웨이 라벨을 단 시험 파드는 로컬 NodePort Service(고르개가 `gateway.envoyproxy.io/owning-gateway-name` 하나)의 끝점이 될 수 있다. 짧게 띄우고, 게이트웨이 kind 시험이 끝난 뒤에 돈다.

## 구현 메모

구현 담당(`bat061-impl-ad4eb26e`)이 구현 전에 적었다. 정본에 없던 세부와 그 근거, 계획과 달리 한 것이다.

1. **게이트웨이 프록시의 서비스 계정 이름(ADR-0285 결정 7).** Envoy Gateway v1.10.0 소스(태그 `v1.10.0`, 2026-11-18 GitHub 원본으로 읽음)의 규칙이다.
   - `internal/infrastructure/kubernetes/proxy/resource_provider.go`: 프록시 Deployment의 `ServiceAccountName`은 `serviceAccountName()`이다. EnvoyProxy `provider.kubernetes.envoyServiceAccount.name`이 있으면 그 이름, 없으면 `Name()`이다. `Name()`은 게이트웨이 네임스페이스 배치 방식이면 `infra.Name`, 아니면 `ExpectedResourceHashedName(infra.Name)`이다. 자원의 네임스페이스는 기본 배치에서 컨트롤러 네임스페이스(`envoy-gateway-system`)다.
   - `internal/infrastructure/kubernetes/proxy/resource.go`: `ExpectedResourceHashedName(name)` = `envoy-` + `utils.GetHashedName(name, 48)`(`config.EnvoyPrefix`가 `envoy`).
   - `internal/utils/misc.go`: `GetHashedName(nsName, 48)`은 `/`를 `-`로 바꾸고(48자를 넘으면 잘라 끝의 `-`를 뗀다) `-`와 `nsName`의 SHA-256 16진 앞 8자를 붙인다.
   - `internal/gatewayapi/translator.go`: `infra.Name`(`Proxy.Name`)은 `IRKey` = `<게이트웨이 네임스페이스>/<게이트웨이 이름>`이다(`mergeGateways`면 GatewayClass 이름).
   - 이 저장소는 컨트롤러 설정(`deploy/gateways/controller/envoy-gateway.yaml`)에 배치 방식이 없고(기본), EnvoyProxy 둘에 `mergeGateways`·`envoyServiceAccount`가 없다. 그래서 이름은 `envoy-envoy-gateway-system-<게이트웨이>-<sha256("envoy-gateway-system/<게이트웨이>") 앞 8자>`다: gw-fan `…-gw-fan-2f99f311`, gw-ops `…-gw-ops-72791c8c`, gw-partner `…-gw-partner-9b6ecb24`, gw-queue `…-gw-queue-38f088e6`, gw-scanner `…-gw-scanner-1784b03e`. 실제 파드의 이름은 MK-08이 본다.
   - ADR-0285 '되돌릴 조건' 첫째(이름을 정하는 설정): v1.10에 `envoyServiceAccount.name`이 있다. 그런데 EnvoyProxy `peaket-proxy`를 게이트웨이 넷이 GatewayClass로 함께 쓰므로, 거기에 이름을 적으면 넷이 한 신원이 되어 '그 경로의 게이트웨이만'을 지키지 못한다. 게이트웨이마다 EnvoyProxy를 나눠야 하고 게이트웨이 정의(BAT-060 몫)를 바꾸는 일이라 이 묶음에서는 하지 않았다(감독에게 알림, 정리 목록 후보).
2. **원천 꼴에 더한 칸 하나(4.1의 2).** `rest.gatewaysWithoutRoute`: 라우트가 저장소에 없는 게이트웨이 경로(trust-svc의 gw-fan, ADR-0285 결정 9 끝의 '예외 한 줄')를 적는 칸이다. `rest.callers`에 게이트웨이를 적으면 생성기가 막는다(게이트웨이는 라우트에서 뽑는다). 라우트가 이미 주는 게이트웨이를 이 칸에 적어도 막는다. 게이트웨이인지는 `deploy/gateways/` 맨 위 YAML의 Gateway 이름이거나, 메시 없는 고르개에 `gateway.envoyproxy.io/owning-gateway-name`이 있는 부르는 쪽이다. 새 게이트웨이도 `callers`에 있어야 한다(없으면 막음).
3. **부르는 쪽 표에 더한 표 밖 이름 둘.** `core-notify-sender`(core, `RecipientQueryService`, docs/api/proto/README.md:39)와 `inv-ingest`(trust 네임스페이스는 docs/streaming.md:43, `InvestigationRefService`)다. 둘 다 받는 쪽이 아니라 원천 `workloads`에는 없다. 파드 라벨은 공용 차트 꼴(`app.kubernetes.io/name`·`app.kubernetes.io/component: service`) [가정, 그 배포가 생길 때 확정]이다.

- **kind 시험의 '연결 안 됨'**: 이름 풀이 실패·답 없는 연결·끊김 없는 닫힘은 거부로 세지 않고 무대 결함으로 실패한다. 거부(`timeout`·`ECONNRESET`·`ECONNREFUSED`·`EHOSTUNREACH`·`ENETUNREACH`)는 같은 실행에서 그 대상(워크로드·포트)에 연결된 사례가 있어야만 받는다. 대상 쪽 고장(대역이 죽음, Service에 포트 없음)은 이것으로 막힌다. 부르는 쪽 파드의 고장은 RV-08이다.
- **구현 커밋이 시험 파일을 건드렸나**: 아니다. 구현 커밋 `7152faa9`의 19개 파일에 시험 파일(`*.test.*`·`test/`·`e2e/`)이 없고, 시험 커밋 `851ac21e`는 시험 파일 셋과 이 계획만 바꿨다. `node tools/ci/roles-check.mjs --base d686e49d --head 851ac21e`는 시험 파일 위반 없이 '리뷰·검증 커밋 없음'만 낸다(이 리뷰 전이라 맞다).
- **CI 잇기**: `tools-check.yml`에 정적 시험과 `--check`가 주석이 아닌 `run`으로, `ci-kind.yml`에 게이트웨이 시험 뒤 무대와 kind 시험이 있다. `changes.mjs`는 `deploy/platform/`·`deploy/gateways/`·`docs/api/proto/`·`deploy/workloads/`·`tools/`에서 `tools`를 고른다. 다만 정적 시험이 `deploy/` 전체를 훑는 가드(MS-11·12·13)는 그 밖의 `deploy/` 아래가 바뀌면 돌지 않는다(RV-01).
- **자주 놓친 결함**: 허용·거부를 목록 밖 값마다(게이트웨이 다섯, 열두 네임스페이스의 표에 없는 파드·라벨 없는 파드, 릴레이 파드, 라벨만 같은 다른 네임스페이스 파드), 빈 결과가 통과로 새지 않음(생성기·시험·kind 대조군), 단언 값을 정본에서 적음, 겹친 가드(노드 프록시 정책과 웨이포인트 정책을 MS-02·MS-09로 따로), kind 시간 한도 3초를 상수와 따로 정함, 바깥 경계(명령줄·CI 줄·`changes.mjs`를 명령줄로)를 지킨다. 걸리는 것은 '바깥 경계'의 RV-01, '겹친 가드'의 RV-09다.
