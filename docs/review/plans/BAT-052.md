# 묶음 계획: BAT-052(HOT-090 realtime-gw 실시간 좌석 전파)

- **무엇**: 묶음을 시작할 때 만든 작업 목록이다(docs/architecture.md §8.6 4의 1·2, '역할 나누기'의 계획). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다. 정본의 값은 옮겨 적지 않고 자리(문서·절)만 가리킨다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane4`, 가지 `feature/lane4-BAT-052`, 출발점 `origin/develop` `f04f286e`. 구현 전 트리(분리 HEAD, 커밋하지 않음)는 `D:/ticketpass-lane4-base`(`f04f286e`)다. 지시서는 `brief.mjs --batch BAT-052`(만든 때 `f04f286e`). 2026-11-18 계획 담당 `bat052-plan-31d7`(claude-opus-5-5)가 썼고 시험·제품 코드는 쓰지 않았다.
- **등급**: A(docs/BUILD_ORDER.md 묶음 표 BAT-052). 좌석 상태를 화면에 나르는 길이다. 짧은 고리(ADR-0283 결정 2)를 쓰지 않는다: 리뷰 → 리뷰 반영(시험 먼저, 그다음 구현) → 고친 곳 다시 리뷰 → 검증.
- **차례**: 정방향 묶음이다(이 계획 커밋에 `Batch-Order: impl-first`). 계획 → 구현 → 시험(구현 전 트리에서 실패 확인) → 리뷰 → 리뷰 반영 → 다시 리뷰 → 검증 → 기록.
- **정본**: [ADR-0296](../../adr/0296-realtime-gw-first-build-own-token-check-section-count-from-layout-file.md)(이 커밋), docs/features/seat-hold.md §7 'realtime-gw의 첫 구현'(이 커밋)·§7의 나머지(구독 범위·구독 요청 검사·묶음 간격·구역별 일련번호와 회차 세대·전파 지연 예산)·§12 S-T31·S-T42(이 커밋)·§13, docs/frontend.md §4.4.1(바이트 형식·닫힘 코드·구독 상한 표), docs/api/asyncapi.yaml `ws.seat-delta`, docs/data.md §3 `s:{event:E}:sec:{section}` 행(Pub/Sub 메시지 글)·§5 이 커밋 행, ADR-0110 결정 3·4·5, ADR-0240 결정 10, docs/security/asvs/seat-hold.md의 이 커밋 행 23개.

### 1. 범위

- **하는 것**: HOT-090(docs/BUILD_ORDER.md 389행)의 서버 몫. 새 서비스 `services/realtime-gw`: 핸드셰이크(경로·출처·하위 프로토콜·입장 토큰·판 파일), 연결 직후 `BatchInterval` 한 번, 받는 프레임 검사와 구독 상한(S-T31 ①~⑤), 좌석 Redis 샤드 Pub/Sub 구독 관리, 100ms 묶음(`changedAtMs`·`maxWaitMs`, 세대마다 끊기, 같은 구역 메시지 차례 지키기), `TimeSync` 답과 주기 하트비트, 토큰 만료 4401, 느린 연결 1013, 내릴 때 1012, 지표·로그, 시작 파일. `packages/platform`에 입장 토큰 확인 함수.

### 5. 공개 인터페이스(시험 담당이 기댄다. 이름은 구현이 이대로 쓴다)

- **WebSocket**: `ws://127.0.0.1:<app 포트>/v1/events/{eventId}/seats/stream`, 하위 프로토콜 `["peaket.seats.v1", "peaket.auth." + 토큰]`, 머리 `Origin`. 프레임은 frontend §4.4.1. 해독은 `@peaket/seatmap`의 `decodeFrame`·`encodeSubscribe`·`encodeTimeSync`를 써도 된다(화면과 같은 해독기라 서로 맞는지도 본다). 바이트를 손으로 만들 때는 frontend §4.4.1 표를 따른다.
- **시작**: `start({ env, logDestination?, clock? }: { env: Record<string, string | undefined>; logDestination?: Writable; clock?: Clock })` → `Promise<{ ports: { app: number; management: number }; close(): Promise<void> }>`. `clock`이 없으면 시스템 시계. 박자(100ms)는 실제 타이머다.
- **허브(단위 시험의 바깥 경계, `src/modules/stream/index.ts`)**:
  - `createStreamHub(d: StreamHubDeps): StreamHub`
  - `interface StreamHubDeps { clock: Clock; subscriber: ChannelSubscriber; sectionCount(eventId: string): number | undefined; onMetric?(name: string, labels: Record<string, string>, value: number): void; onSubscribeError?(channel: string, error: unknown): void }`(`onSubscribeError`는 구현이 더한 선택 칸, 받아들임)
  - `interface ChannelSubscriber { subscribe(channel: string, onMessage: (message: string) => void): Promise<void>; unsubscribe(channel: string): Promise<void> }`
  - `interface StreamConnection { send(frame: Uint8Array): void; close(code: number, reason: string): void; readonly bufferedAmount: number }`
  - `interface StreamHub { open(c: StreamConnection, s: { eventId: string; accountId: string; expiresAtMs: number }): void; receive(c: StreamConnection, data: Uint8Array, isBinary: boolean): void; gone(c: StreamConnection): void; tick(): void; shutdown(): Promise<void> }`. `open`이 곧 `BatchInterval`을 보낸다. `tick()`이 박자 하나(묶음·하트비트·만료)다. 회차 다름 4403은 핸드셰이크 층이 `open` 전에 닫는다.
- **메시지 해석**: `parseSeatDeltaMessage(channel: string, text: string): { eventId: string; sectionIndex: number; seatEpoch: number; sectionVersion: number; changedAtMs: number; seats: Array<{ offset: number; state: 0 | 1 | 2 }> } | undefined`(틀리면 undefined).
- **설정**: `loadRealtimeGwConfig(env)` → 설정 값, 틀리면 `Error`(글에 비밀번호 없음).
- **platform**: `verifyAdmissionToken(token: unknown, o: { keys: AdmissionKeys; issuer: string; nowMs: number }): AdmissionClaims`, `parseAdmissionJwks(raw: string): AdmissionKeys`, `class AdmissionTokenRejected { reason }`(purchase-svc `admission-token.ts`와 같은 모양).
- **지표·로그 이름**: seat-hold §7 'realtime-gw의 첫 구현' '지표와 로그'. 관리 포트 `/metrics`.

### 7. 구현 전 트리에서 실패를 볼 수 없는 시험과 그 까닭

- 이 묶음의 시험은 모두 새 서비스 `services/realtime-gw`와 새 platform 모듈을 부른다. 구현 전 트리(`f04f286e`)에는 그 폴더·모듈이 없어 시험 파일을 읽지도 못한다. 이런 실패는 세지 않는다(§8.6 7). 그래서 모든 시험은 아래 9의 틀린 구현으로 한 번은 실패를 본다.
- 시험 담당은 '실패 확인' 절에 (가) 구현 전 트리에서 시험 파일이 '모듈 없음'으로만 멈추는 것을 한 번 돌려 적고, (나) 틀린 구현 표본(M1·M9·M15·M22 [가정]) 넷을 작업 트리에 넣어 실패를 본 뒤 되돌린 결과를 적는다. 나머지는 검증 담당의 9 전부가 본다.

### 11. 시험·구현 지시문에 넣을 '자주 놓친 결함'

docs/architecture.md §8.6 4의 '자주 놓친 결함' 전부. 이 묶음에서 특히:

- 시간 한도(1초 창, 1,000ms, 15초, 토큰 `exp`)는 경계 − 1ms와 경계를 가짜 시계로 재고, 단언 값은 정본에서 적는다. 시험 값은 상수와 다르게 고른다(박자 배수가 아닌 시각).
- 허용·거부 목록은 목록 밖 값마다 거부를 본다(출처 없음·다른 출처, `type` 1·17·19, `PEAKET_ENV` `prod`·`staging`·`demo`).
- 판정 함수만 보지 말고 바깥(실제 소켓의 닫힘 코드, Valkey의 실제 구독 수)에서 본다. 장애 주입은 끊긴 사례가 실제로 있었는지 단언한다(S-T42 ⑩).
- 시작 파일 조립은 시험 조립과 따로 띄워 본다(S-T42 ⑫⑬).
- 같은 구역 메시지 둘, 세대가 다른 메시지 같은 '합치면 가려지는' 경우를 꼭 둔다.

- **단언 값**: 시험의 `SPEC`(hub-fixtures·gateway·layout-sections·redis-subscriber 시험)과 config 시험의 값이 정본(seat-hold §7 'realtime-gw의 첫 구현'·§13, frontend §4.4.1 '닫힘 코드'·'닫힘 이유 글', ADR-0296·0297)과 같다: 닫힘 코드 1012·1013·4401·4403·4429, 이유 글 일곱(`server restart`·`slow consumer`·`token expired`·`bad event`·`bad section`·`bad frame`·`too many`), 박자 100ms, 하트비트 15초, 보내기 버퍼 1MiB, 받는 프레임 1,024바이트, 구역 16개, 1초 창·2번, TimeSync 1,000ms, 같은 jti 2개, 파드 5,000개(1~1,000,000), 곧 닫는 연결 유예 100ms·닫히는 중 4개, 해제 대기 1초, 물러서기 0.2~5초, 없음 기억 1초·1,024개, `maxWaitMs` 65,535. 구현 상수를 가져온 시험은 없다. 경계 결함(M1·M2·M8b·M11b·M14a·M21·M26b·M37·V1·V5·V14·V18)은 모두 잡혔다.

**구현이 정본보다 넓힌 것 둘의 판정**

1. **업그레이드 머리 400 셋**(메서드가 `GET` 아님, `Upgrade`가 `websocket` 아님, 하위 프로토콜의 빈 값·token 밖 글자): 정본 seat-hold §7 '핸드셰이크' ④와 §12 S-T42 ②에 그대로 반영됐다(SEC-R03). 구현·정본·시험(gateway 단위, stream 통합)이 같고 M48이 잡혔다. **정본과 같음, 그대로 둔다.**
2. **4429 `too many`로 닫는 모든 연결에 100ms 유예·jti 닫히는 중 셈**: 구현은 닫힘 이유 글(`CLOSING_FAST_REASONS`)로 고르므로, 맺은 뒤 곧 닫는 4403 `bad event`·같은 jti 셋째 4429뿐 아니라 오래 열려 있다가 구독 빈도(②)·구역 17개(③)로 4429를 받는 연결도 같은 길을 탄다. 정본은 '맺은 뒤 곧 닫는 이 두 연결'이다. **판정: 해가 없어 받아들이고, 정본 문장과 맞추는 일은 정리 목록에 둔다.** 까닭: 그 연결은 이미 닫기 프레임을 보낸 뒤라 유예가 짧아져도 화면은 4429를 받는다. 화면은 4429 뒤 10초 넘게 기다려 다시 붙으므로(frontend §4.4.1) 정상 화면이 같은 토큰으로 100ms 안에 닫히는 중 넷을 만들 수 없다. 셈이 넓어지는 쪽이라 SEC-R01·R02의 막음은 더 세진다. 고칠 방법은 둘 중 하나다: (가) seat-hold §7 '핸드셰이크' 뒤 문장을 '4403 `bad event`와 4429 `too many`로 닫는 연결'로 넓힌다, (나) 이유 글 대신 '맺은 뒤 곧 닫음' 표시로 고른다. 닫힘 이유 글(계약)에 서버 내부 판단이 묶이는 것을 줄이려면 (나)가 낫다.
