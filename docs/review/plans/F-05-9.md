# F-05-9 계획 — K10 시나리오 6종·전환 판정·레인 처리량 측정 (측정 창 3)

- 기능: F-05-9(현장 입장), 등급 **B**. 단계 `GAT-350`(wbs 5.7.1: K10 시나리오 6종, 스캐너 1대 처리량, 전환 중 판정과 레인 처리량 비교, O-T40·O-T41)과 `GAT-370`(wbs 5.7.3: 기술 블로그 1편 M5 초안, 게시는 소유자 몫)이다.
- **동결 로컬 범위**: 이 기능은 v1 배포 범위 밖이다(ADR-0373, BUILD_ORDER 상태 `동결`). 이 가지(`freeze/lane3-F-05-9`)는 `develop`·`release`에 합치지 않고, 이 가지에만 쌓아 로컬에서 확인 가능한 몫을 남긴다. 배포 차트·운영 값·v1 완성 판정에는 넣지 않는다.
- 기준: `origin/freeze/lane3-F-05-8` `86c02f129`(F-05-8 완료 포함). 작업 폴더 `D:/ticketpass-freeze-F-05-9`, 가지 `freeze/lane3-F-05-9`.
- 차례(B등급, ADR-0372·ADR-0373): **계획 → 시험/측정 준비 → 리뷰(새 세션) → 반영 → 측정/문서 → 기록**. 이번 턴은 계획과 시험(측정 준비)을 끝내고, 기준 트리 실패를 확인한 뒤 **리뷰 준비**에서 멈춘다. 실제 측정·Docker·kind는 쓰지 않는다.
- 담당: 이 freeze 가지는 계획·시험을 한 세션이 이어서 맡는다(동결 로컬 범위, `Agent-Session: lane3-freeze-F-05-9-opencode`). 그래서 담당 표의 plan·test 세션 ID가 같고, 역할 확인의 '서로 다른 세션' 조건은 이 가지에서 통과하지 못한다. 합치지 않는 가지라 그 조건을 적용하지 않는다(§14). 리뷰는 새 세션이 맡는다.

> **수치 주장 금지(이 계획이 지키는 규칙)**
>
> - 이번 턴에는 새 측정값을 하나도 주장하지 않는다. O-T40·O-T41과 K10 시나리오 6종의 상태는 모두 **미측정**이다.
> - 30k/s(F-04-8), 100만·K1·K2·K7(F-08-2·F-08-8)은 이 기능이 새로 재지 않는다. 필요하면 그 계획·보고서의 값을 위치와 함께 인용만 하고, F-05-9의 결과처럼 쓰지 않는다.
> - 정본의 목표·[가정] 값(판정 150ms, 오프라인 90%, 게이트 분당 60명, O-T40의 2초·300건·150번째, O-T41의 20명·10분)은 정본 위치만 가리킨다. 측정 전에는 "미측정"으로 적는다.
> - 측정 결과의 표시는 `실측(PC)`로 하되 무대 칸에 **"Chromium 흉내(실제 관리형 기기·실제 공연장 망 아님)"**를 붙인다(docs/verification.md §3.5·perf-ledger §7).

## 3. 정본에 쓴 것(계획 커밋)

- `docs/BUILD_ORDER.md` F-05-9 행의 **장부 범위를 좁힌다**: `O-T40, O-T41, docs/features/offline-gate.md` → `O-T40, O-T41`. 문서 통째 범위는 이 기능이 닿지 않는 O-T1~O-T53(127항목)까지 끌어와, 이 기능이 판정하지 않는 스캐너 인증·재입장·마감 항목을 빈칸으로 만든다. K10 시나리오 6종은 장부 범위 밖 보조 시험이고, 실제 판정은 O-T40·O-T41 둘이다.
- 같은 행 비고에 **동결 로컬 범위**(이 가지에만 쌓고 develop·release에 합치지 않음), 이 계획 경로, 측정 창 3을 적는다.
- 정본에 새 값을 더하지 않는다. 목표값은 `docs/planning/02-requirements.md` NFR-010·`docs/quality/quality-requirements.md` QR-SA-1·QR-PE-4, 절차는 `docs/features/offline-gate.md` O-T40·O-T41, 표시 규칙은 `docs/verification.md` §3.5와 `docs/perf-ledger.md` §7에 이미 있다. 이 계획은 위치만 가리킨다.

**정본에 없는 측정 정의 셋(이 계획에서 추천안으로 정한다, 2026-11-27)**

1. **O-T40의 '판정 지연'의 시작점**: 주 지연은 **QR을 대는 순간(present) → 판정 화면이 뜨는 순간(verdict)** 이다. 스태프가 체감하는 값이기 때문이다. 함께 **디코더가 QR을 넘긴 순간(decoded) → verdict** 를 남겨, 지연이 카메라 루프(150ms 주기)·화면 스레드 디코딩·판정·큐 쓰기 가운데 어디서 늘었는지 가른다. 150ms의 최종 판정은 워커 전환 뒤 F-05-10이 다시 본다(§1).
2. **O-T41의 QR을 대는 간격**: 사람 20명이 차례로 대는 흐름을 **닫힌 고리**로 흉내 낸다. 앞사람의 판정 화면(2초 유지)이 사라진 뒤 다음 QR을 넣는다. 실제 레인에서 스태프가 판정을 확인하고 다음 사람을 부르는 것과 같다. 온라인·오프라인 모두 같은 규칙을 쓴다. 10분 창은 첫 QR을 넣은 시각부터 10분이다.
3. **비행기 모드 흉내**: Playwright `context.setOffline(true/false)`와 가짜 API 라우트 중단을 함께 쓴다. 실제 무선 전파·기지국 포화를 재현하지 않는다. 보고서의 무대 칸에 그 한계를 적는다.

이 셋은 측정 방법의 세부라 `docs/features/offline-gate.md`를 고치지 않고 이 계획·보고서에 적는다(F-04-8 §3과 같은 방식). 리뷰에서 정본에 올릴 만하다고 판단되면 그때 정본에 옮긴다.

| 표시 | `실측(PC)` + 무대 "Chromium 흉내(실제 관리형 기기 아님)" | docs/verification.md §3.5, perf-ledger §7 |
| 자원 | 브라우저 1개·페이지 1개. 실행 전 호스트 CPU·메모리·실행 시각을 `env.json`에 남긴다 | 같은 PC에서 다른 부하가 돌면 무효(§5.5) |

### 5.2 O-T40 — 온라인 → 오프라인 전환 중 판정

**절차(한 실행)**

1. 스캐너 빌드를 띄우고 근무 준비(SCR-033)에서 [스캔 시작]을 누른다. 목록·키·시계 보정이 끝나 '판정 대기'가 된 것을 확인한다.
2. 예열 10건을 온라인에서 판정한다(세지 않는다).
3. 목표 2초 간격으로 300건을 판정한다. 150번째 무렵(149건 뒤)에 `setOffline(true)`와 가짜 API 중단을 함께 켠다. 판정 화면이 남아 있으면 사라진 뒤 다음 QR을 넣고, 목표 간격을 넘긴 시간을 기록한다.
4. 300건 뒤 `setOffline(false)`로 다시 켜고 30건을 더 판정한다. 끊긴 동안 큐에 남은 기록이 다시 연결되면 올라가는지, 큐가 0이 되는지 본다.
5. 전환 원인을 바꾼 **짧은 실행**을 따로 둔다: (a) 판정 사이에 끊기(위 300건 실행), (b) 업로드 POST가 진행 중일 때 끊기(가짜 API가 1.5초 늦게 답하게 하고 그 사이에 끊는다), (c) 변경분 GET이 진행 중일 때 끊기(60초 주기의 요청을 3초 늦게 답하게 하고 그 사이에 끊는다). (b)·(c)는 300건을 반복하지 않고 한 건·한 번의 요청으로 큐·재동기화만 본다.

**측정량(건마다)**

| 칸 | 뜻 |
| --- | --- |
| `presentedAtMs` | QR을 `window.__peaketQr`에 넣은 순간(`performance.now()`) |
| `decodedAtMs` | 가짜 BarcodeDetector가 QR을 앱에 넘긴 순간 |
| `verdictAtMs` | `[aria-label="판정 결과"]`가 처음 뜬 순간 |
| `presentLatencyMs` | `verdictAtMs - presentedAtMs`(주 지연) |
| `decodeLatencyMs` | `verdictAtMs - decodedAtMs`(앱 파이프라인) |
| `result` | `PASS`·`REJECT`·`CHECK`·`RETRY`(정상 티켓이므로 `PASS`만 정상) |
| `queueCountAfter` | 판정 뒤 스캔 큐 건수 |

**판정(O-T40)**

- 300건 + 30건 가운데 **결과가 없거나 오류인 판정 0건**.
- 전환 앞뒤 1분(2초 간격이므로 30건 창)의 **최대 `presentLatencyMs` ≤ 150ms**, 그리고 같은 실행의 평소(전환 전 온라인 구간) p95 ≤ 150ms. 평소 p95가 이미 150ms를 넘으면 "미달(평소 p95 초과)"로 적고, 원인을 `decodeLatencyMs`와 함께 F-05-10으로 넘긴다. 150ms를 넘긴 값을 F-05-9가 고치지 않는다.
- **판정이 멈춘 시간 0초**: QR을 댄 뒤 3초가 지나도 판정이 없던 시간의 합이 0. (판정 화면 2초 유지와 다음 QR을 넣는 시간은 멈춘 시간이 아니다.)
- 끊긴 동안 올리지 못한 기록이 **다시 연결되면 모두 올라가고**(큐 0), 같은 기록이 두 번 저장되지 않는다(가짜 API가 받은 ID의 중복 0).
- (b)·(c) 실행은 큐에 남았다가 다시 올라가고(또는 다음 동기화가 이어지고) 같은 기록이 두 번 저장되지 않는 것을 지켜야 한다. 150ms 판정은 (a) 3회로 본다. 하나라도 어기면 O-T40은 실패다.

**무효(통과·실패로 세지 않는다)**

- 300건+30건을 채우지 못함, 티켓 ID가 겹침, 예열·전환 시각이 계획과 다름, 페이지 새로고침, Playwright 시간 초과, 호스트 CPU 80% 초과, 다른 부하가 함께 돎, 가짜 API가 예상 밖 경로를 부름, 전환 동안 네트워크 상태가 계획과 다름. 무효는 원인을 적고 다시 잰다.

**반복**: (a) 3회(중앙값과 편차), (b)·(c) 각 1회. 3회 가운데 무효가 있으면 그 자리를 다시 채운다.

### 5.3 O-T41 — 레인 처리량

**절차(한 실행)**

1. 사람 역할 20명 [가정]이 동시에 줄을 서는 흐름을 흉내 낸다. 지나가는 사람마다 **새 티켓**을 준비한다(같은 20명이 다시 들어오는 것이 아니다. 재입장 허용 회차가 아니다). 스캐너 1대·스태프 1명의 레인을 흉내 낸다.
2. 온라인 실행: 30초 예열 뒤 10분 [가정] 동안 닫힌 고리로 QR을 대고 판정 화면이 사라지면 다음 사람 QR을 댄다. 20명이 차례로 돌아 다시 줄을 선다. 변경분(60초)·업로드(5초)는 평소처럼 돈다.
3. 오프라인 실행: 같은 방식으로 시작하되 `setOffline(true)`와 가짜 API 중단을 켠다. 업로드는 큐에 쌓이고 변경분은 실패한다. 10분이 끝나면 다시 연결해 큐를 비우고, 비우는 데 걸린 시간과 건수를 기록한다(처리량에는 넣지 않는다).
4. 온라인 3회·오프라인 3회. 실행마다 새 context·page로 시작한다.

**측정량**

| 칸 | 뜻 |
| --- | --- |
| `windowMs` | 첫 QR을 넣은 시각부터 10분(±5초 허용) |
| `verdicts` | 창 안에서 결과가 나온 판정 수 |
| `perMinute` | `verdicts × 60,000 ÷ windowMs` |
| `presentLatencyMs` 분포 | p50·p95·최댓값 |
| `holdMs` | 판정 화면이 떠 있던 시간(2초 유지) |
| `queueDrainMs`·`queueDrainCount` | 오프라인 실행 뒤 다시 연결해 큐를 비운 시간·건수 |
| `nonPass` | 정상 티켓인데 `PASS`가 아닌 판정 수 |

**판정(O-T41)**

- 유효한 온라인 3회와 오프라인 3회의 **분당 통과 인원 중앙값**을 구한다.
- **오프라인 중앙값 ÷ 온라인 중앙값 ≥ 90% [가정]**. 비교는 나눗셈의 부동소수 오차를 피하려고 `오프라인 × 100 ≥ 온라인 × 90`으로 센다.
- 90% 미만이면 **어디서 늘었는지**를 적는다: `present → decoded`(카메라 루프·디코딩), `decoded → verdict`(판정·큐 쓰기), 판정 화면 유지, 다음 QR까지의 간격. 큐 쓰기를 따로 가르려면 측정 창에서만 쓰는 Chrome trace를 쓰고, 제품 코드에 계측을 더하지 않는다.
- 정상 티켓의 `nonPass`가 0이어야 한다.

**무효**: 10분 ±5초를 벗어남, 20명 가운데 한 명도 나오지 않음, `nonPass` > 0, 판정 없음 > 0, 페이지 새로고침, 네트워크 상태가 계획과 다름, 호스트 포화. 무효는 다시 잰다.

### 5.5 측정 창 3일의 뜻과 시작·끝 조건

**뜻**: 기능 표의 `측정 창 3`은 이 기능에 배정한 **작업일 3일**이다. 72시간 연속 부하가 아니다. F-04-8도 같은 측정 창 3을 쓰므로, 그 실행이 Docker를 오래 잡는 동안에는 이 측정을 시작하지 않는다(ADR-0189 결정 3). O-T40·O-T41은 브라우저만 쓰므로 Docker가 필요 없지만, K10 시나리오 S2의 서버 판정을 실제 스택에서 다시 보려면 Docker 잠금이 필요하다. 그때는 `take docker lane3-F-05-9`를 쓰고 **`docker-all`은 쓰지 않는다**.

**예상 소요**

| 날 | 하는 일 | 부하 시간 | 준비·정리 |
| --- | --- | --- | --- |
| 1일 | 빌드, `tools/web-checks` 의존성 설치, 하네스 스모크(짧은 실행), K10 시나리오 6종 | 약 1시간 | 약 3시간 |
| 2일 | O-T40 (a) 3회 + (b)·(c) 각 1회, O-T41 온라인·오프라인 각 3회 | 약 2시간 | 약 2시간 |
| 3일 | 무효·실패 다시 재기, 보고서·성능 장부·장부 notes·블로그 초안 | 약 1시간 | 약 3시간 |

**시작 조건(모두 참일 때만 연다)**

1. 이 가지의 계획·하네스가 커밋되어 있고, 측정 대상 트리가 깨끗하다. 측정 중에는 제품 코드를 바꾸지 않는다.
2. `tools/web-checks`에서 `pnpm install --frozen-lockfile`이 끝났고 Playwright Chromium이 설치되어 있다.
3. `pnpm --filter @peaket/scanner build`가 같은 트리에서 재현된다.
4. 다른 정밀 측정(F-04-8 등)이 돌지 않는다. 겹치면 감독이 순서를 정하거나 이 측정을 미룬다.
5. 호스트 CPU 80%·메모리 90%를 넘지 않고, 브라우저 외 부하가 없다.
6. 실행 폴더 이름 규칙·보고서 경로·성능 장부 행을 정했다.

**끝 조건(모두 끝나야 닫는다)**

1. O-T40·O-T41이 `pass`·`fail`·`invalid` 가운데 하나로 판정됐고, `invalid`를 남기지 않았다.
2. K10 시나리오 6종이 각각 통과·실패·제외(까닭)로 기록됐다.
3. 보고서·성능 장부 행·`docs/review/ledger-notes.md` 측정 기록·블로그 초안이 있다.
4. `docs/BUILD_ORDER.md` GAT-350·GAT-370 줄과 `docs/lanes/lane3.md` 진행 로그가 실제와 같다.
5. 브라우저·서버·Docker 잠금을 놓았다.

## 6. 블로그 초안 범위(M5)

- 파일: `docs/blog/m5-offline-gate.md`(예정, 새 파일). `docs/blog/README.md` M5 표의 상태를 `초안(날짜), 게시 전`으로 바꾼다. 게시는 소유자 몫이다.
- 독자: 네트워크가 끊기는 현장 시스템을 만드는 엔지니어. 전문 용어는 처음 나올 때 푼다(docs/planning/03 §5).
- 뼈대:
  1. 문제: 공연장 망이 끊기면 온라인 전용 검표가 멈춘다(K10). v0 기준선은 `docs/blog/m1-v0-breaking-point.md`와 `docs/verification.md` §3.10의 값을 **인용**만 한다.
  2. 설계: 단말 로컬 ECDSA P-256 회전 QR, 판정 10단계, IndexedDB strict 큐, 5초 묶음 업로드, 60초 변경분. 정본 위치를 가리킨다.
  3. 측정: F-05-9 보고서의 O-T40·O-T41 결과만 쓴다. 무대는 "PC Chromium 흉내"이고 실제 기기·공연장 망이 아님을 밝힌다.
  4. 전환에서 배운 것: 끊긴 순간 업로드·변경분이 진행 중이어도 판정이 멈추지 않았는지, 큐가 다시 올라갔는지.
  5. 한계: 실제 관리형 기기·iPhone·iOS 저장소·서비스 워커·판정 워커는 이 글의 범위가 아니다(F-05-1·F-05-10). 100만·30k/s·K1·K2·K7은 이 글의 숫자가 아니다.
  6. 근거: 성능 장부 실행 ID와 보고서 경로.
- 숫자 규칙: 모든 숫자에 `실측(PC)`·`설계 목표`·`[가정]`·`문서 인용` 가운데 하나를 붙인다. F-05-9가 재지 않은 값은 인용만 하고, 출처 위치를 붙인다. **측정 전에는 어떤 수치도 쓰지 않는다.**

3. 판정 함수 단위 시험이 통과하고, 기준 트리에서 하네스 모듈이 없어 실패한 기록과 일부러 틀린 판정에서 실패한 기록이 §13에 있다. 실제 파일 계약 시험 4/4도 통과한다.
4. `tools/web-checks`에 `pnpm install --frozen-lockfile`로 Playwright 1.64.1을 설치하고 `--list`로 17개 시험이 잡히는 것을 확인한다. 실제 실행(측정)은 하지 않고, 측정 창에서 처음 돌린다.
5. 게이트: 뿌리 lint, doc-check, `ledger --batch F-05-9 --require`. `release-scope --check`는 이 가지에 도구(`tools/ci/release-scope.mjs`)와 manifest(`docs/release/v1-scope.*`)가 없어 실행하지 못했고, §13에 그 사실을 적는다. Docker·kind·실제 측정 없음.
6. 제품 코드·계약·마이그레이션을 바꾸지 않는다.

**기능 완료(측정 창 뒤)**

1. O-T40·O-T41이 유효한 실행으로 판정됐고, 보고서·성능 장부·ledger-notes에 남았다.
2. K10 시나리오 6종이 모두 기록됐고, 빼는 셋의 까닭이 적혔다.
3. M5 블로그 초안이 측정값만으로 쓰였고, 게시하지 않았다.
4. 이 가지는 `develop`·`release`에 합치지 않는다.

## 9. 실패 시나리오(이 기능이 반드시 다루는 것)

- 전환 중 업로드가 진행 중: 요청이 끊겨도 기록은 큐에 남고, 다시 연결되면 같은 ID로 한 번만 올라간다.
- 전환 중 변경분 받기가 진행 중: 요청이 끊겨도 다음 60초 동기화가 이어지고, 목록·키·입장 상태가 깨지지 않는다.
- 전환 중 판정 화면이 떠 있음: 다음 QR은 화면이 사라진 뒤 들어가고, 그 대기 시간을 '멈춘 시간'으로 세지 않는다(단, 3초를 넘으면 센다).
- 판정이 없거나 오류: O-T40 실패. 화면·콘솔·스크린샷을 남기고 원인을 `decodeLatency`·`presentLatency`로 가른다.
- 평소 p95가 이미 150ms 초과: O-T40 "미달(평소 p95 초과)"로 적고 F-05-10으로 넘긴다. F-05-9가 앱을 고치지 않는다.
- 오프라인 레인이 90% 미만: O-T41 실패. 판정 지연·화면 갱신·큐 쓰기·간격 가운데 어디서 늘었는지 적는다.
- 20명 가운데 일부가 창 안에 한 번도 안 나옴, 10분 ±5초 이탈, 페이지 새로고침, 호스트 포화: 무효로 적고 다시 잰다.
- 실제 기기·iPhone·실제 공연장 망이 아님: 보고서 무대 칸과 블로그 한계에 적는다. 실제 기기 값으로 주장하지 않는다.
- S2의 중복 표시를 브라우저 하네스가 판정하지 못함: 기존 `scanner-f054.int.test.ts` 결과를 인용하고, 하네스는 두 기록이 올라간 것까지만 적는다.
- Docker가 필요할 때 `docker-all`을 쓰려 함: 금지. `take docker lane3-F-05-9`만 쓴다.
- 측정 중 다른 정밀 측정이 돎: 시작하지 않고 감독에게 알린다.

## 14. 검증

**역할 확인(roles-check) 예외**

- 이 freeze 가지는 계획·시험을 한 세션(`lane3-freeze-F-05-9-opencode`)이 맡는다. ADR-0372의 '역할마다 다른 세션' 조건을 만족하지 못한다. 합치지 않는 동결 로컬 가지라 그 조건을 적용하지 않는다(F-05-8과 같은 예외).
- 시험 커밋은 시험 파일(`*.test.mjs`·`*.spec.mjs`) 밖에 하네스 지원 파일(`k10-lib.mjs`·`fixture.mjs`)과 시험 설정(`playwright.scanner-k10.config.mjs`)을 바꾼다. 이 파일들은 제품 코드가 아니라 **측정 도구**다. `roles-check.mjs`의 '시험 커밋은 시험 파일과 문서만' 규칙에는 걸리므로, 이 가지에서는 예외로 기록한다. 리뷰 담당이 이 예외와 파일 성격을 확인한다.
- 리뷰는 새 세션(`lane3-freeze-review-opencode`, 2026-11-27)이 맡고, 담당 표에 그 줄을 더한다. 리뷰 커밋은 이 계획의 '리뷰' 절·담당 표와 `docs/lanes/lane3-cleanup.md`만 바꾼다.
- `roles-check.mjs`는 이번 턴에 돌리지 않는다(합치지 않는 가지, 도구가 요구하는 리뷰 커밋이 아직 없다). 측정 창 뒤 기록 담당이 전체 이력으로 한 번 돌려 결과를 적는다.

**확인했으나 문제 없음**

- 90.0% 경계: `meetsRatio`가 `part × 100 ≥ whole × 90`으로 세고, 27/30=90.0% 통과·26.9/30=89.7% 실패를 단위 시험이 단언한다. `judgeLane`은 유효 실행의 분당 값 중앙값으로 같은 비교를 한다.
- 멈춘 시간: 3초 경계(3000ms→0, 3500ms→500ms), 결과 없음은 10초 상한을 대입해 7초로 세는 것을 단위 시험이 단언한다.
- 남은 큐: `queueAfter !== 0`이면 실패(0이 아니거나 없음), 단위 시험이 1건을 잡는다. 끊긴 동안 큐가 실제로 쌓였는지는 RV059-01이 본다.
- 업로드·변경분 중단: (b)·(c) 실행이 있고, 큐 1건→0·업로드 1건·다음 변경분 비중단을 본다. 중복·상태 확인의 빈틈은 RV059-04·06.
- 오프라인 3회: 온라인 3·오프라인 3 실행이 있고, `judgeLane`이 유효 실행 3회씩을 요구한다.
- 사람 20명: `lanePlan` 20명과 실행의 `cursor % 20` 역할, 유효성 검사가 있다. 역할이 항상 채워지는 점은 RV059-17.
- 빈 표본·0건: `judgeTransition`·`judgeLane`은 빈 표본에서 실패한다. 그 갈래를 단언하는 시험이 없는 점은 RV059-09.
