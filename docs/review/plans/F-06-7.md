# F-06-7 계획 초안 — GAT-280 추가 검증 이의 처리 행동(SCR-045 이의 심사)

- 기능: F-06-7(고객·CS·법정), 등급 A(대기 순번·봇 라벨·권한), 단계 `GAT-280`의 이의 처리 몫, WBS 0.75일 [가정]. 선행 F-06-2.
- 장부 범위: `Q-T48 ②, B-T10 ③④⑥, B-T28`(11항목, `node tools/ci/ledger.mjs --batch F-06-7`). B-T10 ③④는 queue-svc·trust-svc 시험이 이미 자동 시험으로 보고, 이 기능은 ops-svc가 부르는 쪽을 같은 번호로 더 본다. B-T28은 bot-defense 시험 표의 새 ID다.
- 나눈 까닭: 2026-11-23 감독 결정으로 이의 인정·기각이 GAT-280 몫이 됐다. F-06-2와 합치면 5일을 넘어 나눴다(docs/review/plans/F-06-2.md §12, ADR-0364 결정 8).
- 이 파일은 **F-06-2 계획 담당이 쓴 초안**이다. F-06-7을 시작할 때 계획 담당이 다시 보고, §3의 정본 빈칸을 구현 전에 정본에 쓴 뒤 그 커밋을 계획 커밋으로 한다(`Batch-Order: impl-first`). 담당 표는 그때 쓴다.
- 정본: bot-defense §12 '처리함 건'·'판정에 쓰는 자료'·'결과 반영', B-T10·B-T28, queue-admission Q-T48, queue.proto `VerificationAppealService`, trust.proto `TrustEvidenceService.GetVerdictEvidence`·`TrustLabelService.ApplyLabel`, identity.proto `SetAccountHold`, d5 §7.6 '추가 검증 이의' 줄, ADR-0364 결정 8. 값은 옮기지 않고 위치만 가리킨다.

## 계획

### 1. 끝내는 것과 넘기는 것

- **끝내는 것**: `cs_agent`가 SCR-045에서 `VERIFICATION_APPEAL` 건을 열면 이의 글과 판정 근거(범주 값만)가 보인다. 인정·기각을 누르면 결정과 해결이 ops DB에 한 번 저장되고, queue-svc 대기 참여·trust-svc 라벨·차단 키 지우기가 한 번씩 반영된다. 건이 열려 있는 동안 계정 병합이 막힌다. 호출이 실패하면 배경 작업이 다시 보낸다.
- **넘기는 것**: 결과·설명 통지 문구(법률 검토 wbs 7.4.1), 분쟁(`DISPUTE`)·소명(`APPEAL`)의 `SetAccountHold`(계정을 문의·소명 기록에서 읽어야 해 F-06-5·F-06-3), 메시 L7 허용 목록(B-T10 ⑦, HOT-400).

### 3. 정본 빈칸(F-06-7 계획 커밋에서 쓴다. 방향은 ADR-0364 결정 8)

1. openapi 새 경로 `POST /v1/ops/cases/{caseId}/verification-appeal-decision`: 역할 `cs_agent`·`cs_lead`, `If-Match`·`Idempotency-Key`, 본문 `{ outcome: ACCEPTED|REJECTED, resultNote }`, 202 `CsCase`, 403·404·409·412·422·428. 오류 이름은 F-06-2가 더한 `case-*` 넷을 다시 쓴다. gw-ops 경로는 `/v1/ops/cases` 접두로 이미 덮인다.
2. openapi `CsCaseDetail.verificationAppeal`: 이의 글, 사유 범주, 확정 신호 여부, 판정 출처, 판정 시각, 지난 30일 추가 검증 보냄·통과·실패 수, 대기 참여 상태, 결정(있으면 결과·처리 시각·차단 목록 변화)과 호출 반영 상태(`PENDING`·`APPLIED`·`FAILED`). pid·계정 ID·점수 원값·가중치·기기 가명은 싣지 않는다(bot-defense §12 '판정에 쓰는 자료').
3. data.md ops 새 표(마이그레이션 0031): 건마다 보낼 호출 한 줄씩(건 ID, 호출 종류 `QUEUE_RESOLVE`·`TRUST_LABEL`·`ACCOUNT_HOLD_OPEN`·`ACCOUNT_HOLD_CLOSE`, 판 번호, 상태, 시도 수, 다음 시도 시각, 마지막 오류 코드, 응답의 차단 목록 변화). data.md의 `verification_case.appeal_result`와의 관계(그 표를 쓸지, 새 표로 갈음할지)를 정한다. 추천: 새 표, `verification_case`는 정본 설명에 '이의 결과는 CS 건과 보낼 호출 표에 있다'를 더한다.
4. 다시 보내기 간격·상한과 '반영 실패' 경보 등급: bot-defense §13 운영 확인의 '라벨 반영이 한 번만 된다' 행(SEV3)을 따른다. 간격은 1분·5분… [가정], 상한 뒤에도 건은 열어 두지 않고 해결 상태로 두되 '반영 실패' 표시와 경보를 남긴다(추천).
5. `SetAccountHold`의 계정: `GetVerificationAppeal.account_id`로 정한다. 건이 열릴 때(F-06-2의 받기 뒤) 보낼 호출에 `ACCOUNT_HOLD_OPEN`을 적는다.

### 7. 실제 서버 연결과 브라우저

- 서버 사이: `test-int`에서 queue-svc gRPC 서버를 실제로 띄워(그 서비스의 `grpc-server.ts`, 시험 Redis) ops-svc 클라이언트가 부른다. trust-svc·identity-svc는 이미 각자 시험에서 같은 RPC를 본다(B-T27, identity hold 시험).
- 브라우저: 로컬 데모 무대(F-06-2 계획 §7과 같은 계정 `daeun`·`jun`)에서 추가 검증 이의 하나를 내고(SCR-009) 처리함에서 인정해 대기실에서 통과로 바뀌는지 본다.

### 8. 겹침

- F-06-2와 같은 `cases` 모듈·화면 파일을 고친다. F-06-2를 합친 뒤에 시작한다.
- bot-review 라벨 클라이언트를 넓히면 BAT-197(F-11-2 표본 검토 마감)과 겹친다. 넓히지 않고 cases 모듈에 같은 꼴로 따로 두는 쪽을 추천한다.
