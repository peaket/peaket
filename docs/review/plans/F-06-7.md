## 계획

### 1. 끝내는 것과 넘기는 것

- **끝내는 것**: `VERIFICATION_APPEAL` 건이 열리면 이의 내용을 ops DB로 옮기고 계정 병합을 막는다. CS 담당자가 SCR-045 이의 심사 패널에서 근거(범주 값만)를 보고 인정·기각하면 결정·해결·보낼 호출이 한 트랜잭션에 저장되고, queue-svc 대기 참여(`PASSED`/`BLOCKED`)·trust-svc 사람 라벨과 차단 키 지우기(인정만)·병합 막기 풀기가 같은 건 ID·판으로 한 번씩 반영된다. 실패하면 배경 작업이 다시 보내고, 끝내 못 보내면 '반영 실패'와 SEV3 경보다.
- **넘기는 것**(bot-defense §12 'CS 처리 첫 구현'의 '넘긴 것'): 결과·설명 통지, SCR-009 '검토 중' 배지, 메시 L7 허용 목록(B-T10 ⑦, HOT-400), `verification_case` 파기 작업, d5 §7.6의 진입·홀드 타임라인과 나이 범주. 분쟁(`DISPUTE`)·소명(`APPEAL`)의 `SetAccountHold`는 F-06-5·F-06-3.

### 3. 정본 빈칸 결정(이 계획 커밋에서 정본에 씀, 추천 적용 2026-11-23)

모두 ADR-0364 결정 9에 모았다. 방향은 결정 8 그대로라 새 ADR은 필요 없다.

1. 결정 경로·차례·오류: openapi 새 경로와 bot-defense §12 '결정'. 경로 역할은 넷(operator·commander가 `case-update-not-allowed`를 받게), 결정은 CS 둘, 담당자가 아니어도 됨. 메모 없음이 본문 스키마 400이 아니라 422가 되게 `resultNote`를 필수에서 뺐다(B-T28 ②).
2. 새 오류 `case-action-not-applicable` 409: 다른 종류 건에 결정 경로, 이의 건에 PATCH `RESOLVED`(호출 없이 닫는 길을 막음).
3. `CsCaseDetail.verificationAppeal` 모양(가린 칸 목록 포함)과 읽는 때(상세마다 `GetVerificationAppeal`·`GetVerdictEvidence`, 1초 데드라인, 실패해도 200).
4. ops 0031: `verification_case`(칸 정함, `status` 다섯 값은 소유자 결정 그대로 두고 뜻을 붙임)와 `cs_case_dispatch`(기본 키 (case_id, call), 판, 상태, 시도, 다음 시각, 잡음 끝, 마지막 오류, 답, 경보 시각), 보낼 호출 쿼리·인덱스(data.md §5.1).
5. 다시 보내기: 간격·상한·다시 보내지 않는 gRPC 상태·'반영 실패' 뒤에도 다시 보냄·경보 이름과 열고 푸는 때(bot-defense §12 '다시 보내기', §15 새 행).
6. 건 상태: 결정 트랜잭션에서 바로 RESOLVED(반영 실패여도 건은 다시 열지 않고 `reflectState`로 보인다).
7. 판: OPEN은 연 때의 판, 결정 셋은 해결한 새 판(늦은 OPEN이 CLOSED를 되돌리지 않음).
8. 감사: `CS_CASE_UPDATED`에 `appealOutcome`(메모·이의 글·pid 없음).
9. pid 보관: `verification_case.pid`(라벨 다시 보내기용, 응답·로그·감사 없음, data-classification 행에 더함).
10. 시작 조건: staging·prod는 queue·trust 주소가 없으면 ops-svc가 시작하지 않는다.
11. Q-T48 ②·queue-admission §7의 '지운 기록에 기기 가명'을 bot-defense §9 '기록'(2026-11-10 정합)에 맞춰 고쳤다(`ApplyLabel` 응답에 기기 가명이 없고 운영 로그에 쓰지 않음).

막힘: 없다. 소유자 몫 결정 없음.

### 4. 공개 인터페이스(시험이 이 이름을 쓴다)

**HTTP**(openapi 그대로): `POST /v1/ops/cases/{caseId}/verification-appeal-decision`(머리 `If-Match`·`Idempotency-Key`, 본문 `{ outcome: 'ACCEPTED'|'REJECTED', resultNote? }`, 202 `CsCase` + `ETag`), `GET /v1/ops/cases/{caseId}`의 `verificationAppeal`, `PATCH`의 409 `case-action-not-applicable`. 건을 여는 길은 F-06-2의 내부 HTTP `POST /internal/v1/cs-cases`와 Kafka `support.cases-requested`(같은 처리기).

**ops-svc 포트**(`services/ops-svc/src/modules/cases/domain/verification-appeal.ts`, `index.ts`로 내보냄):

```ts
type AppealOutcome = 'ACCEPTED' | 'REJECTED';
type DispatchCall = 'APPEAL_COPY' | 'ACCOUNT_HOLD_OPEN' | 'QUEUE_RESOLVE' | 'TRUST_LABEL' | 'ACCOUNT_HOLD_CLOSE';
type DispatchState = 'PENDING' | 'APPLIED' | 'FAILED';
interface AppealContent { appealId: string; eventId: string; accountId: string; pid: string; text: string; reasonCategory: string; receivedAtMs: number; entryState: 'VERIFYING' | 'PASSED' | 'ENDED' }
interface VerificationAppeals { get(appealId: string): Promise<AppealContent>; resolve(i: { appealId: string; caseId: string; caseVersion: number; outcome: AppealOutcome }): Promise<'APPLIED' | 'UNCHANGED' | 'NOT_ISOLATED'> }
interface AppealLabels { apply(i: { caseId: string; version: number; eventId: string; pid: string; actedBy: string }): Promise<{ changed: boolean; blockList: 'NONE' | 'ADDED' | 'REMOVED' | 'DEVICE_NOT_FOUND' }> }
interface VerdictEvidence { get(i: { eventId: string; pid: string }): Promise<{ found: false } | { found: true; reason: string; hardSignal: 'NONE' | 'BLOCK_LIST' | 'HONEYPOT'; source: 'REALTIME' | 'REASSESS'; decidedAtMs: number; sent: number; passed: number; failed: number }> }
interface AccountHolds { set(i: { accountId: string; caseId: string; state: 'OPEN' | 'CLOSED'; version: number }): Promise<{ changed: boolean }> }
class CsDispatchCallError extends Error { readonly code: string } // gRPC 상태 이름(UNAVAILABLE 등), 주소 없음은 NOT_CONFIGURED
interface CsDispatchSignals { dispatch(call: DispatchCall, result: 'applied' | 'retry' | 'failed'): void } // ops_cs_case_dispatch_total
```

- 어댑터(`modules/cases/adapters/`): `GrpcVerificationAppeals`·`GrpcAppealLabels`·`GrpcVerdictEvidence`·`GrpcAccountHolds`(정본 설명자 `@peaket/contracts/proto`, `createGrpcClient`, 호출마다 데드라인, `GrpcAppealLabels`는 내부 gRPC 토큰·호출자·처리자 증명). 시작 조립 `services/ops-svc/src/cs-appeal-wiring.ts`의 `csAppealPortsFromEnv(env): { appeals?, labels?, evidence?, holds?, close(): void }`(주소 없으면 그 칸 없음, staging·prod에서 queue·trust가 없으면 던진다).
- 쓰임새: `application/verification-appeal-decision.ts` `VerificationAppealDecision.handle(actor, caseId, ifMatch, idemKey, body) → { view: CsCaseView; version: number }`, `application/verification-appeal-detail.ts`(`CsCaseDetailReader` 구현, `detailReaders`에 `VERIFICATION_APPEAL`로 건다), `application/cs-case-dispatch.ts` `CsCaseDispatch.run(nowMs) → { applied: number; retried: number; failed: number }`와 `sendCase(caseId, nowMs)`(결정 뒤 한 번).
- 배경 작업: `CsCaseDispatchJob`(`cases.module.ts`, `runOnce(): Promise<void>`, `CsCaseDeadlineJob`과 같은 꼴). 시험은 `service.app.get(CsCaseDispatchJob).runOnce()`로 한 바퀴를 돈다.
- `AppModule.register` 칸: `csAppeals?: { appeals?; labels?; evidence?; holds?; signals? }`, `background.csCaseDispatchMs?`. memory·database 두 조립 모두(메모리 저장소도 보낼 호출·이의 표를 갖는다).
- 경보: `CS_CASE_DISPATCH_FAILED`(SEV3, 열쇠는 건 ID·호출, `RecordOpsAlert`). 지표 `ops_cs_case_dispatch_total{call,result}`(`PromCsDispatchSignals`).
- `main.ts`: `csAppealPortsFromEnv(process.env)`를 `AppModule`에 넘기고, 종료 때 닫는다.

**화면**(`apps/console-host/src/pages/cs-inbox/`):
- `model/live.ts` 새 내보냄: `verificationAppealOf(raw): VerificationAppealView | null`(상세 응답의 `verificationAppeal`만 옮기고 모르는 칸·모양 틀린 값은 버림), `canDecideAppeal(role)`(cs_agent·cs_lead), `appealReasonLabel`·`hardSignalLabel`·`entryStateLabel`·`blockListChangeLabel`·`dispatchCallLabel`·`reflectBadge(state)`, `errorOf`에 409 `case-action-not-applicable` → kind `'not-applicable'`(그 밖 409는 지금처럼 `'resolved'`).
- `ui/ConnectedPage.tsx`: `VERIFICATION_APPEAL` 건이면 `AppealPanel`(d5 §7.6 상태 표 네 줄의 글), [ 해결로 닫기 ] 대신 [ 이의 인정 ]·[ 이의 기각 ] → 확인 대화상자(`role="dialog"`, `aria-modal`, 처음 초점 [ 취소 ], Esc 취소) → 생성 호출 `createOpsCaseVerificationAppealDecision(caseId, { outcome, resultNote }, { headers: { 'If-Match': ifMatchOf(version), 'Idempotency-Key': key } })`. 키는 대화상자를 열 때 `crypto.randomUUID()`로 하나 만들고 네트워크 실패·503 뒤 다시 누름에는 같은 키, 성공·4xx 뒤에는 버린다. 202 뒤 상세를 다시 읽는다. 이의 글·서버 글은 글자 노드로만.
