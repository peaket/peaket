# 작업 계획: BAT-408(재인증 토큰의 받는 쪽 작업, GAT-045)

- **무엇**: 묶음 BAT-408(갈래 3, 구간 3, 등급 B, 단계 GAT-045)의 작업 목록이다. 소유자 결정 OPEN[50] (나)(2026-11-18)대로 팬 재인증 토큰에 받는 쪽 작업(새 클레임 `op`)을 싣고, 웹이 재인증 `purpose`로 고르며, 받는 서비스는 자기 작업의 토큰만 받게 한다. 배경은 BAT-415-reauth 리뷰 RV-01(같은 `FAN_SENSITIVE` 토큰을 identity 작업과 팬 취소에 한 번씩 쓸 수 있음)이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane3`, 가지 `feature/lane3-BAT-415`(BAT-415 커밋들이 합치기를 기다리는 가지 위에 얹는다), 출발점 `4aaf2762`. 2026-11-18~19 계획 담당 `l3-b408-plan`(claude-opus-5-5)이 썼고 시험·제품 코드는 쓰지 않았다. 지시서는 `node tools/ci/brief.mjs --batch BAT-408`(만든 때 `4aaf2762`, 장부 범위가 `-`일 때라 판정 항목이 없었다)이다. 이 커밋에서 장부 범위를 정했으므로 다음 담당은 지시서를 다시 만든다.
- **묶음 ID와 차례**: 정방향 묶음이다(이 계획 커밋에 `Batch-Order: impl-first`). 계획 → 구현 → 시험(구현을 맡지 않은 시험 담당, 구현 전 트리 = 이 계획 커밋에서 실패 확인) → 리뷰 → 리뷰 반영 → 검증 → 기록. B 등급이라 짧은 고리다(ADR-0283 결정 2: 리뷰 반영 계획 커밋 없음, 다시 리뷰 없음, 고친 곳 확인은 검증이). 권한 묶음이라 보안 높음 지적은 리뷰 담당이 고친 곳을 다시 본다.
- **정본(이 커밋에서 먼저 씀, 모두 '추천 적용, 2026-11-18')**: ADR-0293(새), docs/security/authz-matrix.md §6 '받는 쪽 작업 `op`의 값'(새 문단과 표), docs/features/identity.md §3 '재인증 토큰의 묶음'·§7.1 '재인증 흐름과 토큰' ①③④·§12 I-T85(새 줄), docs/features/transfer-refund.md §3.1 '팬 취소의 재인증 확인'(확인하는 것·작업 묶음·답·거절 기록·남는 한계)·§11 R-T39 ①④ 문구와 ⑧(새 세부), docs/frontend.md §4.1 '재인증' 줄, docs/data.md §3 `reauth:jti:{jti}` 줄, docs/api/guidelines.md §7 '재인증 토큰', docs/security/asvs/auth.md 9.2.2 줄, docs/security/asvs/transfer-refund.md 'BAT-408 계획 메모', docs/architecture.md ADR 목록 0293 줄, docs/BUILD_ORDER.md BAT-408 '장부 범위'.

### 2. 바른 동작(정본 ADR-0293, authz-matrix §6 '받는 쪽 작업 `op`의 값')

- B1 웹 앱 서버: `POST /reauth/{provider}`의 `purpose`가 표의 웹 값(열다섯)이면 그 작업을 로그인 진행 쿠키에 봉인하고, 아니면(빈 값, 칸 없음, `high-risk`, 대문자 이름, 모르는 값) 400이며 제공자로 보내지 않고 쿠키를 만들지 않는다. 콜백은 봉인한 작업으로 `IssueReauthToken.operation`을 채운다. 쿠키에 작업이 없으면 identity를 부르지 않고 '그 밖의 실패'.
- B2 identity 발급: `operation`이 UNSPECIFIED·모르는 값이면 `INVALID_ARGUMENT`. 토큰 `op` = 그 작업, `act` = 표의 값. 본인확인 재통과 판정의 '고위험'은 그 작업의 `act`가 `FAN_HIGH_RISK`일 때. 옛 칸 `purpose`는 읽지 않는다.
- B3 공용 확인기: 팬 키 셋은 기대 `op`가 꼭 있고 토큰의 `op`가 같은 문자열이어야 한다(없음·문자열 아님·다름은 `TokenRejected('claims')`). 팬 키 셋에 기대 `op`가 없거나 관리 키 셋에 있으면 `TokenRejected`가 아닌 오류(부르는 쪽 결함).
- B4 identity 받는 다섯: 탈퇴 `ACCOUNT_WITHDRAW`, 다른 기기 로그아웃 `SESSION_END`, 로그인 수단 해제 `LOGIN_METHOD_REMOVE`·추가 `LOGIN_METHOD_ADD`, 계정 합치기 `ACCOUNT_MERGE`만 받는다. 거절은 지금처럼 403 `reauth-required`이고 `jti`를 적지 않는다.
- B5 purchase-svc 팬 취소: 계좌 없으면 `FAN_SENSITIVE`·`TICKET_CANCEL`, 있으면 `FAN_HIGH_RISK`·`TICKET_CANCEL_REFUND_ACCOUNT`. 기대값은 본문으로 정한다. 거절 까닭 이름표는 `claims`.
- B6 웹 화면: 탈퇴 `account-withdraw`, 다른 기기 로그아웃 `session-end`, 로그인 수단 해제 `login-method-remove`·추가 `login-method-add`, 계정 합치기 `account-merge`를 재인증 양식에 싣는다.
- 이음 기간 없음(ADR-0293 결정 6): `op` 없는 토큰은 어느 받는 쪽도 받지 않는다.

### 4. 갈래 나누기 판단: 나누지 않는다

- 웹 몫은 파일 일곱(§3의 14~19, 앱 서버 셋과 흐름·화면 연결 넷), 바뀌는 줄은 30줄 안팎 [가정]이다. 화면 모양·문구·흐름 차례는 바뀌지 않고, 이미 있는 재인증 양식 함수에 작업 값 하나를 넘기는 것뿐이다. 새 화면이 없고 첫 JS 크기에도 거의 닿지 않는다.
- 나누면 identity·받는 쪽(갈래 3)과 웹(갈래 2)이 따로 합쳐지는 사이에 상태가 깨진다. 웹이 먼저면 identity가 `operation`을 모르고, identity가 먼저면 웹이 `operation`을 비워 모든 재인증이 `INVALID_ARGUMENT`가 된다(이음 기간을 두지 않기로 했다, ADR-0293 결정 6). 한 묶음으로 한 번에 합치는 것이 맞다.
- 다른 갈래 영향은 §11에 적는다(감독이 전체 감독에게 알린다).

- 구현 전 트리에서 실패를 볼 수 없는 시험: I-T85 ④의 관리 키 셋 회귀, R-T39 ⑧의 `act`만 다른 경우(구현 전에도 403)는 구현 전에도 같은 결과다. 그 시험은 검증 담당의 틀린 구현(§7)으로 실패를 한 번 본다. 나머지(웹 400, 발급 토큰의 `op`, identity·purchase의 `op` 다른 토큰 거절, 화면의 `purpose`)는 구현 전 트리에서 단언 실패가 나야 한다.
- 통합(선택, Docker는 감독이 잠금을 잡은 때만): identity `test-int`의 탈퇴·로그아웃 통합 시험이 `op` 있는 토큰으로 다시 통과하는지. 이 묶음의 필수는 단위다. 통합은 초안 PR CI로 본다(ADR-0283 결정 3).

### 6. 정본 빈칸과 정한 것(이 커밋에서 정본에 씀)

| 빈칸 | 정한 것 | 쓴 곳 |
| --- | --- | --- |
| `op` 값 목록(받는 작업 이름) | 열다섯 값. 값 하나 = 받는 API 작업 하나, 본문으로 `act`가 갈리는 API(예매 취소)만 둘. 아직 받는 쪽이 없는 작업도 지금 정한다 | ADR-0293 결정 2, authz-matrix §6 표 |

| 받는 서비스의 확인 규칙 | 기대 `op`는 요청에서 정하고 토큰에서 읽지 않음. `act`와 `op`를 따로 봄. 거절 까닭 `claims`. 공용 확인기에 팬 키 셋이면 `op` 필수(빠지면 부르는 쪽 결함 오류) | ADR-0293 결정 5, identity §7.1 ④, transfer-refund §3.1 |

### 8. 자주 놓친 결함 가운데 해당하는 것(docs/architecture.md §8.6)
