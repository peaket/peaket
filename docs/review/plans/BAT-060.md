## 계획

### 1. 선행 확인과 이번 범위

**선행 확인(2026-11-16)**:
- WBS 선행: wbs 2.11.1(HOT-400·HOT-410)의 선행 2.7.4는 HOT-150~153이고 모두 develop에 있다(docs/BUILD_ORDER.md 'HOT-150'~'HOT-153' 줄, 체크됨). HOT-150의 웹훅 받기(payment-svc 앱 포트의 `POST /v1/webhooks/toss`·`/portone`)도 develop에 있다.
- 실제 선행은 게이트웨이 다섯(HOT-400 게이트웨이 층)이고, 그것은 **BAT-055 가지에만 있다**(develop에 없음, BAT-055는 다른 폴더에서 아직 구현 중). 그래서 **BAT-060은 BAT-055가 develop에 들어간 뒤 합친다.** BAT-055가 리뷰·검증에서 `deploy/gateways/` 정의를 더 고치면, BAT-060의 시험·구현 담당은 그 고침을 받은 가지 위에서 일한다(감독이 BAT-055 가지 끝을 다시 받아 올린다).
- BAT-057(HOT-400의 나머지: 입장 토큰 공개키 묶음 등)과 BAT-056(측정)은 선행이 아니다.
- `gitops-check`(docs/devops.md §3)는 아직 없다(BUILD_ORDER BAS-150, BAT-085). 그래서 생성 대조는 그전까지 `tools-check`가 돈다(정본에 씀, 아래 8의 1).
- 경보 규칙 파일은 아직 없다(경보 규칙을 처음 두는 단계는 wbs 4.1.1, BUILD_ORDER OPS-010 등). 그래서 '열림 경보'는 통계 이름과 조건을 정본에 정하고, 이 묶음은 kind에서 그 통계가 느는지만 본다. 규칙 파일은 다른 단계다.
- 클라우드·비용·소유자 몫: 운영 Redis(ElastiCache Valkey 클러스터 모드·TLS·RBAC 사용자)에 레이트 리밋 서비스가 붙는 설정, CloudFront 뒤의 실제 출발지 IP는 이 묶음의 판정 항목이 아니다. 운영 쪽 설정은 정적 시험으로 모양만 보고, 실제로 붙는지는 클라우드 계정이 생긴 뒤의 일이다(판정 항목으로 세지 않으므로 미검증 줄도 만들지 않는다).
- 소유자 몫·OPEN 대기: 파트너 테넌트당 한도(D-T50 ⑦)를 어느 쪽이 맡을지는 방향을 바꾸는 결정이라 정하지 않았다. 대기: OPEN[41](감독이 develop의 `docs/PROGRESS.md` '미해결'에 넣었다. 문안은 아래 8의 끝). 새 이미지 하나를 kind에 받는 것은 감독이 승인했다(2026-11-16, 아래 13).

**크기**: 지시서의 장부 범위는 83개(D-T36, `docs/infra.md`, ASVS delivery 문서 전체)였고 두 단계 합이 WBS 3.25일이다. delivery 문서의 행은 대부분 CI·공급망·GitOps·운영 진단 행이라 HOT-410·HOT-420이 닿지 않는다. HOT-410(1.75일)만 해도 BAT-055(1.25일)와 비슷하게 kind 시험이 많고, HOT-420(1.5일)은 메시 정책 생성기·NetworkPolicy 생성기·kind 연결 시험이 따로 크다. 한 웨이브에 둘을 함께 끝낼 수 없다고 보고, §8.6의 3대로 범위를 좁히고 묶음을 나눴다(아래 2·3).

**이번에 하는 것(HOT-410)**:
1. openapi → API 호스트의 HTTPRoute를 경로·메서드 단위로 만드는 생성기(`tools/ci/gateway-routes.mjs`)와 생성 대조(`--check`), 생성한 라우트 파일, 라우트 원천 폴더.

### 5. 공개 인터페이스

- **`node tools/ci/gateway-routes.mjs --write | --check [--root <폴더>]`**: `--write`는 생성 파일을 쓰고, `--check`는 쓰지 않고 견줘 다르면 바뀐 파일 이름과 첫 차이 줄을 보이고 1로 끝난다. 멈추는 경우(docs/infra.md §4.1 '생성기가 멈추는 경우')는 2로 끝나고 까닭을 한 줄씩 보인다. `--root`는 시험이 임시 폴더를 가리킬 때 쓴다(기본은 저장소 뿌리). 모듈로도 부른다: `export function generateRoutes({ openapi, sources }): { files: Map<string, string>, problems: string[] }`(`openapi`는 해석한 객체, `sources`는 게이트웨이 이름 → 원천 객체 목록, `files`는 상대 경로 → 글). 시험은 이 함수와 CLI 두 길로 본다.
- **생성 파일의 모양**: 쿠버네티스 HTTPRoute 여러 문서(`---`). 맨 위 주석 두 줄: 생성 파일 표시, `openapi info.version`과 SHA-256(64자리 16진수). 라우트 이름은 원천 이름 그대로(나뉘면 `-2`부터), 이름표 `peaket.io/route: <원천 이름>`. 규칙의 맞춤 조건은 `{ path: { type: Exact | RegularExpression, value }, method }`이고 차례는 경로 글자 차례 → 메서드 차례로 고정한다(다시 만들 때 같은 글이 나와야 한다).
- **라우트 원천의 모양**: HTTPRoute 그대로. 규칙의 `matches`에는 `PathPrefix` 경로만 적는다(메서드 없음). 규칙에 주석 `# cdn-cache` 같은 뜻은 두지 않는다(그것은 openapi `x-peaket-cdn-cache`가 정한다).
- **openapi 확장**: 작업(operation)의 `x-peaket-cdn-cache: true`. 없으면 거짓. 생성기는 이 작업을 같은 원천 규칙에서 따로 규칙으로 모으고 `X-Trace-Id` 응답 머리를 붙이지 않는다.
- **컨트롤러 설정 파일**: `EnvoyGateway` 객체 하나(YAML). `cluster.mjs`는 설치 파일 안의 컨트롤러 설정 자리에 이 객체를 넣고(로컬 덧씌우기는 Redis 주소·CA만 바꾼다), 자리를 못 찾으면 던진다(지금 `gatewayInstall`과 같은 법).
- **`node tools/local/cluster.mjs gateways`**: 지금 하는 일에 더해 TLS Valkey(`peaket-ratelimit-redis`, 게이트웨이 네임스페이스)와 레이트 리밋 서비스를 올린다. 접속 정보 파일(`.cache/peaket-tools/gateways-e2e.json`)에 칸을 더한다: 서로 다른 시험 계정의 팬 토큰 둘, 파트너 토큰 하나, 웹훅 경로를 받는 대역 백엔드 표시, 레이트 리밋 서비스 Deployment 이름(시험이 복제를 0으로 줄인다), Redis 접속(시험이 키 접두사를 본다). 정확한 칸 이름은 구현 담당이 `tools/local/README.md`에 적는다.
- **대역 백엔드**: `POST /__test/conflict`(이름은 구현 담당이 정해 README에)는 409와 `application/problem+json` 본문 `{ type, title, status, traceId }`를 돌려주고, `traceId`는 받은 `traceparent`의 trace-id다(서비스 템플릿 Problem의 `traceId`와 같은 규칙, docs/api/guidelines.md §2 '서비스 템플릿의 Problem').

**Docker가 필요한 것을 줄이는 법**:
- 생성기의 규칙은 모두 단위 시험(임시 폴더의 작은 openapi·원천)으로 본다. kind는 '라우트가 실제로 그렇게 도는가'(D-T42 ③④)만 본다.
- 정책의 값(한도·버킷·대상 라우트·`responseOverride`·TLS)은 정적 시험이 정본 값을 직접 적어 본다. kind는 Envoy가 그 값대로 도는지만 본다.
- K 시험은 한 파일(`gateway-limits.e2e.mjs`)에 모으고, `cluster.mjs gateways` 한 번 띄운 클러스터에서 차례로 돈다(레이트 리밋 서비스 복제 0은 맨 끝). BAT-055의 `tools/local/e2e/gateway-client.mjs`를 다시 쓴다.
- Istio는 이 묶음에 없다(HOT-420은 BAT-061이고, 거기서도 kind에 Istio를 올리지 않는다).

### 7. 차례

1. **계획**(이 커밋): 이 파일, 정본 빈칸(아래 8), 묶음 표 두 줄.
2. **시험**(시험 담당): 위 6의 단·정 시험을 먼저 쓰고 실패를 본다. 뼈대는 `tools/ci/gateway-routes.mjs`의 빈 `generateRoutes`(‘아직 없음’을 던짐)와 CLI(같은 뜻으로 2로 끝남)뿐이다. 저장소 상태 대조(`D-T42 ①②` 저장소 사례, 3.5.3 저장소 사례)는 생성 파일이 없어서 단언에서 실패해야 실패로 센다. K 시험은 써 두고, 실패 확인은 아래 (나)로 한다.
3. **구현**(구현 담당): ① 생성기 → 단위 시험 통과 ② 라우트 원천 옮기기·생성 파일 만들기 → BAT-055 정적 시험과 생성기 저장소 사례 통과 ③ 정책·컨트롤러 설정 → 정적 시험 통과 ④ openapi `x-peaket-cdn-cache`와 생성 대조 ⑤ `cluster.mjs gateways`(TLS Valkey·레이트 리밋 서비스)와 대역 백엔드 → K 시험(Docker 잠금) ⑥ 정본의 [확인 필요](아래 8의 끝)를 kind에서 본 결과로 그 줄에 적는다 ⑦ CI 잡 잇기.
4. **리뷰** → **리뷰 반영** → **검증**(아래 10의 목록) → **기록**(감독).

**kind 시험의 실패 확인(BAT-055의 (가)(나)(다)와 같은 법)**:
- (가) 구현 3의 ⑤ 가운데 바탕만 먼저: TLS Valkey, 레이트 리밋 서비스를 켠 컨트롤러 설정, 대역 백엔드의 409 경로, 접속 정보 파일의 새 칸. 이때 라우트는 아직 BAT-055의 손으로 쓴 앞부분 라우트이고, 이 묶음의 정책(전역 한도·웹훅 라우트와 IP 한도·`responseOverride`·`X-Trace-Id`)은 걸지 않는다.
- (나) 시험 담당: 그 클러스터에서 K 시험을 돌려 단언 실패를 본다(앞부분 라우트라 GET이 백엔드에 닿는다, 전역 한도가 없다, 웹훅 경로가 없다, 오류 본문이 Envoy 기본이다, `X-Trace-Id`가 없다). 바탕이 안 돼 돌지도 못하는 시험, 정책이 없는데도 통과하는 시험은 '시험 이의'에 적는다. 결과는 '실패 확인' 절에 명령·실패 수·까닭으로 적는다.
- (다) 구현: 정책을 건 뒤 같은 시험의 통과를 본다.
- D-T42 ③(사전 요청 204)은 BAT-055 상태에서도 통과할 수 있다(앞부분 라우트는 OPTIONS도 맞는다). 그러면 '처음부터 통과(이미 있는 동작)'로 적고, 검증 담당이 '생성기가 OPTIONS를 빼는' 틀린 구현(아래 10의 1)으로 실패를 본다.

- `responseOverride`의 '게이트웨이가 만든 응답만' 칸 이름과, 라우트에 맞지 않은 요청에도 닿는지(대안: API 호스트마다 맨 뒤 모든 경로 라우트의 직접 응답 404).
- 라우트 규칙의 응답 머리 고치기에서 `%TRACE_ID%`가 채워지는지, 게이트웨이가 만든 429·404에도 붙는지(대안: `EnvoyPatchPolicy`).
- 웹훅 본문 상한을 거는 v1.10 칸 이름(요청 버퍼 상한).
- 레이트 리밋 서비스가 자체 서명 CA의 Valkey TLS를 믿게 하는 법(컨트롤러 설정의 인증서 참조로 되는지, 안 되면 배치의 환경 값으로 CA를 넣음)과 키 접두사를 배치 환경 값으로 줄 수 있는지.
- 429에 `Retry-After`가 붙는지(전역 한도 쪽. 로컬 한도 쪽은 BAT-055 SR-T13 ②가 봤다).
- `shared`로 두 라우트가 한 버킷을 쓰는지(docs/architecture.md §4 '버킷' 줄의 '[가정, PoC에서 확인]'. D-T50 ①의 결과로 그 줄을 고친다).
- docs/verification.md §4.1 새 행의 '레이트 리밋 서비스의 Redis 풀 크기'(v1.10 기본값을 읽어 그 칸에 적는다).

감독 답(2026-11-16)을 반영했다: 게이트웨이 Problem의 '`detail` 없음'은 추천 적용으로 두고, 파트너 테넌트당 한도는 '남는 차이'로 닫지 않고 요구로 둔다.

**OPEN 문안(감독이 develop의 `docs/PROGRESS.md` '미해결'에 OPEN[41]로 넣었다. 정본·notes의 그 문장은 '대기: OPEN[41]')**: 파트너 API의 '테넌트당 600회/분'(docs/api/guidelines.md §6)을 누가 셀지 정해 주세요. 토큰에 파트너 테넌트가 없어(ADR-0172) 게이트웨이(BAT-060)는 계정당 600회/분만 첫 겹으로 겁니다. (가) 파트너 API를 받는 서비스 층이 셉니다. 파트너 경로는 core-svc·payment-svc 등 여러 서비스로 나뉘므로 테넌트마다 공용 카운터(세션·캐시 Redis)와 그것을 부르는 공용 가드를 새로 둡니다. 토큰 계약은 그대로이고, 서비스가 identity에 물어 이미 아는 테넌트로 셉니다. (나) 파트너 토큰에 테넌트를 싣고 게이트웨이가 셉니다. ADR-0172(역할·테넌트를 토큰에 싣지 않음)를 바꾸는 일이고, 테넌트를 옮긴 계정의 옛 토큰이 15분 동안 남습니다. (다) 테넌트당 한도를 요구에서 빼고 계정당 한도만 둡니다. 추천은 (가)입니다(토큰 계약을 바꾸지 않고, 테넌트 판정이 이미 서비스 쪽에 있다). 정해지면 D-T50 ⑦의 정할 곳을 그 묶음으로 바꿉니다. 새 ADR은 쓰지 않았다(작은 세부라 정본에 추천 적용으로 적음. 쓴다면 0275~0277. 2026-11-16 이 가지의 마지막 ADR은 0270이다). 이미 있는 ADR 본문은 고치지 않았다.

### 9. 실패 목록 셋·ASVS·운영 확인

- **§8.7 실패 목록 셋**: 새 저장소 연결(레이트 리밋 서비스 → 세션·캐시 Redis)과 새 키 묶음(`rl:*`)이 생긴다. 그래서 둘에 줄을 썼다. 경합: docs/data.md §5의 `tr:devacct` 줄 바로 뒤('한 계정의 요청이 여러 게이트웨이 파드에서 … `rl:*`를 올림'). 자원 한도: docs/verification.md §4.1 '전역 레이트 리밋 서비스 호출과 카운터 키' 행(처리량은 미정과 정할 곳). 외부 호출 표(docs/api/guidelines.md §8·§8.1)에는 줄을 더하지 않았다. 레이트 리밋 서비스와 Redis는 남의 서버가 아니고, 실패 때 동작(열림)은 docs/architecture.md §4가 이미 정했다. 웹훅은 들어오는 요청이고 결제사 표의 행(§8 토스·포트원)이 이미 있다.
- **ASVS 추적 표(§8.2)**: 범위 행 둘(delivery 3.5.3·16.5.1)은 이미 있다. 이 커밋은 두 행의 구현 위치에 이 단계의 자리를 더했다.
- **운영 확인 표(§8.4)**: 게이트웨이에는 기능 설계서가 없어 docs/infra.md §4.1 같은 블록 끝에 다섯 줄을 썼다(계정 한도, 열림, 웹훅 한도, 메서드 제한, 오류 본문·추적 머리. 앞 둘·뒤 둘의 확인 불가 까닭을 적음).

### 11. 시험·구현 지시문에 넣을 것

- docs/architecture.md §8.6 4 '자주 놓친 결함'을 그대로 넣는다. 이 묶음에 특히 닿는 것:
  - 한도·시간 값(60·600·30회/분, 웹훅 초당 100건, 64KB, `Max-Age` 7200, 판정 시간 상한 20ms)은 코드·YAML에서 가져오지 말고 정본 값을 시험에 직접 적는다. 경계는 양쪽(60번째 통과·61번째 거절, 64KB 통과·64KB+1바이트 413)을 둔다.
  - 허용·거부 목록은 목록 밖 값마다 본다: 전역 한도를 걸지 않는 라우트 여섯 각각, `responseOverride`가 있어야 하는 게이트웨이 다섯 각각, 계약에 없는 메서드 셋(GET·PUT·DELETE) 각각.
  - 판정 함수(생성기)만 보지 말고 바깥 경계(생성 파일, Envoy가 실제로 돌려준 응답, 대역 백엔드가 받은 요청)에서 본다. 측정·대조 도구는 빈 결과(생성한 라우트 0개, openapi 경로 0개)가 '통과'로 새지 않는지 단언한다.
  - 같은 규칙을 두 곳(정적 시험의 값과 kind의 동작)에서 지키면, 하나만 빼는 결함이 다른 쪽에 가려진다(위 10의 끝).
- kind 시험은 끝나면 `docker rm -f -v`로 지우고 Docker 잠금 폴더를 지운다(PROGRESS 턴 규칙 'Docker 차례'). 레이트 리밋 서비스 복제는 시험 끝에 되돌린다.
- 생성 파일은 손으로 고치지 않는다. 구현 담당은 원천이나 생성기를 고치고 `--write`로 다시 만든다(리뷰 담당이 생성 파일만 바뀐 커밋을 본다).

1. **'웹훅 경로에 GET은 없다' 단언(시험 이의 1)**: 이의를 받아들인다. **시험 쪽이다. 시험 담당이 고친다.** 정본은 API 호스트마다 어느 라우트에도 맞지 않는 요청을 `<게이트웨이>-not-found`(직접 응답 404 Problem, 백엔드 없음)가 받게 한다(docs/infra.md §4.1 '호스트와 내부 경로', BAT-055 RV-01). 정본이 지키려는 뜻은 '계약에 없는 메서드는 서비스에 닿지 않고 게이트웨이 404로 끝난다'(같은 절 '메서드가 맞지 않는 요청', D-T42 ④)이고, 'GET에 맞는 라우트가 하나도 없다'가 아니다. 고칠 단언: `GET /v1/webhooks/toss`·`/portone`(그리고 PUT·DELETE도 각각)에 맞는 라우트 규칙이 없거나, 맞은 규칙에 `backendRefs`가 없고 그 규칙의 필터가 404 Problem 직접 응답이다. 맞은 규칙이 백엔드를 가지면 실패한다. 동작은 kind의 D-T42 ④가 본다. 이 고침은 구현을 보고 시험을 맞추는 것이 아니라 정본(RV-01)과 시험의 어긋남을 바로잡는 것이다.
2. **원천 맞춤의 `Exact`(시험 이의 2)**: 받아들인다. 같은 앞부분 아래를 백엔드·정책이 다른 라우트로 나누는 다섯 곳은 BAT-055가 정한 라우트 나눔이고, `PathPrefix`만으로는 '두 규칙이 한 경로를 함께 맡으면 멈춘다'에 걸려 적을 수 없다. `Exact`는 그 계약 경로 하나만 맡으므로 겹침 규칙과 부딪히지 않는다. 정본 docs/infra.md §4.1 '경로별 메서드 생성기'의 원천 문장을 'PathPrefix(그 아래 전부)나 Exact(그 경로 하나), 경로 값은 openapi 꼴'로 고쳤다(추천 적용 2026-11-16, 이 커밋). 시험 담당은 생성기 단위 시험에 `Exact` 원천 사례(그 경로만 맡고 아래 경로는 맡지 않음, 같은 경로를 `PathPrefix`가 함께 맡으면 멈춤)가 없으면 더한다.
3. (참고 두 줄) 처음 라우트한 계약 경로 50짝의 백엔드와 그대로 둔 BAT-055 나눔은 정본에 경로 → 서비스 표가 없어 생긴 판단이다. 리뷰 담당이 docs/architecture.md §3.1과 서비스 처리기에 맞춰 본다. 계획은 지금 정본을 더 쓰지 않는다(이 묶음 범위 밖의 RV-04 ① 등은 BAT-055 쪽 판단을 따른다).
