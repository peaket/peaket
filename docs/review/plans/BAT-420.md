**이미 한 것(다시 하지 않는다)**

대상 고르기(`DrizzleEventRefundTargets.list`): 진행 중 취소가 없는 표 + 진행 중 취소가 `REQUESTED`인 표(`pendingCancellationId`). `REFUND_PENDING`·`REFUNDED`·`VOIDED`가 아닌 다른 진행 중 상태는 빼고, `VOIDED`만 있는 표는 '진행 중 취소 없음'이다. POSTPONE에서 부를 때는 `REQUESTED` 표를 넣지 않는다(목록 함수에 `kind` 인자를 선택으로 더하거나 서비스가 거른다. 구현 담당이 고른다).

`approve`: REQUESTED면 409 `judgement-required`, JUDGED면 409 `preview-required`, PENDING_APPROVAL만 다음 → 판정자 403 → 재인증 → `refunds` 없으면 503 → RUNNING 조건부 저장 → CANCEL이면 `stopper.stop`(던지면 PENDING_APPROVAL로 되돌리고 503 `sale-stop-unavailable`, 시작 호출 0. `stopper`가 없으면 같은 503) → `refunds.start`(POSTPONE이면 `postponedToMs` = `new_starts_at`) → 지금처럼. 시작이 실패하면 지금처럼 되돌리되 돌아가는 상태는 PENDING_APPROVAL이다(지금 코드는 JUDGED. 미리보기를 지우지 않는다).

`reject`: REQUESTED → commander만(아니면 403 `rejection-not-allowed`), REJECTED·`rejection_reason` 저장. JUDGED·PENDING_APPROVAL → 판정자면 403 `approver-ineligible`, 아니면 JUDGED·`dry_run` null. APPROVED 이후 409 `already-approved`.

`get`(관제 상세): 뷰에 `dryRun`, RUNNING·PAUSED·REFUND_WINDOW·COMPLETED면 `reader.job`의 `progress { state, total, done, failed, perPg }`(실패면 `{ state }`만). 목록은 지금처럼 `dryRun`·`perPg` 없음.

`EventSaleStopper` 어댑터(`src/adapters/event-sale-stopper.ts`): `HttpCommandExecutor.execute`에 `type: 'SALE_STOP'`, `commandId: requestId`, `params: { eventId, suspensionRef: requestId }`, `reason: 'EVENT_CANCELLATION'`, `updatedAtMs: now`인 합성 명령을 넘기고 결과가 `FAILED`면 던진다. `SUSPENSION_REASON_CODES` 검사는 `reasonCode`를 비워 지난다. `CancelledEventGuard` 어댑터는 event-cancellations 저장소를 읽는다. `CreateCommand`: `type === 'SALE_RESUME'`이고 `guard.isCancelled(params.eventId)`면 409 `event-cancelled`. `ExecuteCommand`: 같은 확인이 참이면 실행기를 부르지 않고 `markDispatchFailed(…, 'event-cancelled')`.

`SaleSuspensionLookup` Drizzle 어댑터: `select type from ops_command where event_id = $1 and type in ('SALE_STOP','SALE_RESUME') and state = 'SUCCEEDED' order by updated_at desc, id desc limit 1`(같은 시각이면 ID로 정해지게). 메모리 어댑터는 메모리 명령 저장소를 읽는다.

`EventOwnerLookup` 어댑터: core `GET /internal/v1/events/{eventId}/sale-config`(내부 토큰 머리, 5초). 404 → undefined, 2xx → `{ promoterId, startsAtMs, endsAtMs }`, 그 밖·시간 초과 → 던짐.

### 9. 자주 놓친 결함을 이 묶음에 대 본 것

- 저장소 응답은 정확한 값까지: 결제사 호출 금액·멱등키(R-T24), `dry_run` 깊은 비교(R-T37 ①), `entry_recorded_at` 값(P-T19 ①), 상태 응답의 칸 유무(R-T36 ⑧).
- 지우거나 옮기는 연산의 건드린 것: 회차 취소의 ticket 상태·키·버전·`transfer_pending`·`scanner_change`·`ticket_cancellation`(E2·R-T24), 좌석 `seat_sale`·비트맵·변경분·한도가 그대로인지(R-T37 ⑦), 대조된 행의 `refund_due_at`(P-T19 ①).
- 경계 양쪽: 마감 179,999,999/180,000,000ms, 공연 종료 −1ms/정각, 끝 시각 없음 86,399,999/86,400,000ms, 연기 일시 = 시작/+1ms, 100/101장, 200/201장, 1,000/1,001자, 200/201자, 예상 시간 300/301장.
- 계정 대조를 뺀 요청: 세션 테넌트(R-T36 ③·P1), 판정자 ≠ 확정자(R-T23 ⑥·R-T37 ③), 재인증 계정(Q1).
- 장애 주입은 끊긴 사례가 실제로 있었는지 단언: A2(두 실행기 모두 조회까지 감), A3(결제사 호출 뒤 VOIDED), R-T37 ④(첫 확정의 멈춤 실패), E4(두 경우 모두 나옴).
- 허용·거부 목록은 목록 밖 값마다: CS 받는 종류(A4), 끝난 상태 둘·끝낼 상태 다섯(E2), 진행 중 상태 일곱(Q3), 판매 재개를 막는 상태 넷과 막지 않는 상태(R-T37 ⑤), 끝나지 않은 주문 일곱·끝난 주문 여섯(R-T37 ⑥). 세 상태(있음·없음·모름)의 가운데 값: 입장 기록 `found` 거짓(A1).
- 부르는 쪽이 결과를 실제로 쓰는지: 실행기가 집기 결과·조회 결과를 쓰는지(A2·A1), 확정이 멈춤 실패를 쓰는지(R-T37 ④), 서비스가 `NOT_SENT`를 결제사 실패로 세지 않는지(E7).
- 겹친 가드: ① 보류 취소의 집기(조건부 갱신)와 결제사 쪽 같은 멱등키 — M-A2a만 넣으면 결제사 대역이 같은 키를 한 번으로 셀 수 있어 A2는 '결제사 호출 수'(멱등 대역이 아니라 호출 기록)로 센다 ② `order_cancellation` 진행 중 1건 유일과 결정적 취소 ID — M-RT37-6d·M-RT24c는 하나씩 넣는다 ③ ticket-svc 행 잠금과 (취소 ID, 표) 기록 — M-E4·M-E3a를 따로 ④ ops 판매 재개 막기의 만들 때·실행 때 — M-RT37-5a·5b를 따로.
- 시험 값이 상수와 같아 숨는 결함: 권면 33,333(공제 29,999·환급 3,334·배상 6,667/3,334), 시각 상수는 정본 값을 글자로.
- 시작 파일 조립은 시험 조립과 따로(A6·E9·P4).
- 정본 시험 표에 세부 번호를 더할 때 '연결' 칸 앞: R-T36·R-T37은 새 행이고 번호는 시나리오·기대 결과 칸에 있다. P-T19는 기대 결과 칸에 ①②③을 넣었다(`node tools/ci/ledger.mjs --scope "P-T19"`로 세부 셋이 보이는지 확인함).

- purchase `dueRefunds`·`claimDue`: `REQUESTED` 갈래에 `NOT EXISTS (event_refund_hold h WHERE h.event_id = 주문의 회차 AND h.released_at IS NULL AND h.expires_at > 지금)`와 `NOT EXISTS (event_cancellation_request r WHERE r.event_id = 주문의 회차 AND r.kind = 'CANCEL' AND r.status IN ('RUNNING','PAUSED'))`를 같은 문장에 둔다. `claimDue`는 조건부 갱신 한 문장(`UPDATE … WHERE id = $1 AND status = 'REQUESTED' AND entry_recorded_at IS NULL AND NOT EXISTS (…) AND NOT EXISTS (…)`)이라 확인과 집기 사이에 걸린 미룸도 지킨다. `REFUND_PENDING` 갈래에는 두지 않는다. 미룸으로 건너뛴 행은 결과 `held`로 센다.
- `RefundAfterEntry.run` 맨 앞: `holds.releaseExpired(지금, 100)`의 줄마다 SEV2 로그 `event-refund-hold-expired`(회차 ID·요청 ID만). 그 뒤 위 조회.
- `EventRefundService.start`(CANCEL): 요청·항목을 만드는 저장 트랜잭션에서 그 회차의 열린 미룸을 푼다(`released_at`, 요청 ID와 관계없이). 처음 만들 때만(다시 부르기에는 하지 않는다) `gaps.list(eventId, entryOpensAtMs)`마다 `gapNotice.open`. 회차 설정에 입장 시작이 없으면 차액 건을 찾지 않는다(경고 로그). 전환에서 진 항목(`cancellation-in-progress`)은 일반 '일괄 환불 실패' 알림 대신 `gapNotice.open`(공제액 = 그 행의 `deduction_amount`) 하나만 연다.
- purchase gRPC `SetEventRefundHold`: 내부 토큰이 있으면 `verifyInternalGrpcActor(metadata, token, { caller: 'ops-svc' })`. `EventRefundHoldError` INVALID → INVALID_ARGUMENT, ALREADY_EXISTS → ALREADY_EXISTS, 그 밖 INTERNAL(원문 없이).
- ops `request`(commander)와 `requestByPartner`의 CANCEL: 모든 검사(재인증·판매 중지·소속·종료·연기 일시)가 끝난 뒤, 진행 중 요청 확인 바로 앞에서 새 요청 ID로 `holds.hold({ held: true, expiresAtMs: 지금 + 259,200,000 })` → 던지면 503 `event-refund-unavailable`(행·CS 건 0) → 진행 중이면 같은 요청 ID로 풀고 409 → insert 실패도 같은 요청 ID로 풀기(풀기 실패는 경고 로그만). `holds`가 없으면 CANCEL 요청은 503(조립 시험 P4에 더함). POSTPONE은 부르지 않는다.
- ops `judge`·`approve`(재인증까지 지난 뒤, 판매 멈춤 앞): CANCEL이면 같은 요청 ID로 다시 걸어 기한을 늘린다. 실패하면 그 호출을 503 `event-refund-unavailable`로 끝내고 상태를 바꾸지 않는다(judge는 JUDGED도 남기지 않는다). `reject`의 REQUESTED → REJECTED 뒤: 같은 요청 ID로 푼다(실패는 경고 로그만, 기한에 저절로 풀린다). 판정 뒤 반려(JUDGED로)는 풀지 않는다(판정이 끝나지 않았다).

### 2. 지적

**D1 (높음) 다른 길이 먼저 REFUNDED로 끝낸 행에도 환급 실행기가 SEV1 '무효 뒤 환급' 경보를 낸다**
- 파일: `services/purchase-svc/src/modules/refund/application/refund-after-entry.ts:99`~`101`, `services/purchase-svc/src/modules/refund/adapters/db/drizzle-cancellation.ts:238`(REFUND_PENDING 갈래), 계획 §3 173줄 문장.
- 틀린 점: 실행기는 `REFUND_PENDING`이고 `next_refund_at`이 빈 행을 바로 집는다(BAT-415 F). 회차 취소 전용 표 취소기(`event-ticket-canceller.ts`의 쓰기 → `#pay`), 보류 취소 전환, 팬 즉시 환급(`cancel-ticket.ts`)은 모두 행을 그 상태로 만든 뒤 같은 요청 안에서 결제사를 부르고 `updateStatus(REFUNDED)`를 쓴다. 실행기가 틱 처음에 읽은 목록에 그런 행이 들면, 실행기가 같은 `cancel-{ID}`로 다시 부를 때 다른 쪽이 이미 REFUNDED로 끝냈을 수 있다. 결제사(payment-svc 같은 키 재호출)가 `CANCELLED`로 답하면 `updateStatus(REFUNDED)`가 0행이고, 실행기는 무효(VOIDED)가 없는데도 `cancellation-refunded-after-void`(SEV1)를 남긴다. 회차 취소 일괄 환불이 도는 동안은 틱마다 여러 건이 날 수 있다.
- 근거: 이 경보는 '결제사는 환급했는데 그사이 무효로 끝났다(이중 처리 위험)'를 알리는 유일한 신호다. 거짓 경보가 쌓이면 진짜 이중 처리를 놓친다. 같은 상황을 전용 표 취소기는 'REFUNDED로 본다'(시험 이의 §6)로 다르게 다룬다. 0행이면 곧 무효라는 가정은 계획 §3 문장에만 있고 정본(§3.1 ⑤)은 '무효를 덮지 않는다'만 정한다.
- 고칠 쪽: 계획(§3 문장: 0행이면 그 행을 다시 읽어 VOIDED일 때만 SEV1, REFUNDED면 끝난 것으로 셈) → 시험(다른 길이 먼저 REFUNDED로 끝낸 행은 SEV1 0, VOIDED면 1) → 구현.
- 확인 필요: payment-svc가 끝난 같은 키 재호출에 `CANCELLED`로 답하는지(대역은 그렇게 답한다). `UNKNOWN`으로 답하면 경보는 안 나지만 재시도 예약이 0행으로 끝난다(문제 없음).
