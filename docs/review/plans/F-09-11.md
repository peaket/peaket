## 계획

### 1. 범위

- **A. 카나리 분석(D-T6·D-T7)**
  - A1. `deploy/platform/argo-rollouts/analysis-templates.yaml`에 `ClusterAnalysisTemplate` 셋을 둔다: `peaket-canary-error-ratio`, `peaket-canary-latency`, `peaket-canary-event-loop`. 클러스터 범위 템플릿이라 서비스 네임스페이스마다 복사하지 않는다.
  - A2. 템플릿은 `tools/ci/canary-analysis.mjs --write`가 만든다. 임계값·최소 표본·분석 간격은 그 도구의 `CANARY_POLICY` 한 곳에 두고, `--check`가 생성 파일과 대조한다. 사람이 생성 파일을 고치지 않는다.
  - A3. 지표별 판정(정본 `docs/devops.md:528~537`):
    - **오류 비율**: 카나리 5xx 비율이 안정판의 2배를 넘고, 동시에 안정판보다 0.5%p 이상 높고, 카나리 오류가 5건 [가정] 이상일 때 실패. 카나리 요청이 200건 [가정] 미만이면 판정 불가.
    - **지연**: 카나리 p99가 안정판 × 1.2 + 5ms를 넘을 때 실패. 카나리 요청 1,000건 [가정] 이상이면 p99, 200~999건이면 같은 식을 p95로 본다. 200건 미만이면 판정 불가. 5% 단계에서는 지연을 보지 않고 25% 단계부터 본다(정본 `:531`·`:537`).
    - **이벤트 루프**: 카나리 p99가 안정판 × 1.5를 넘을 때 실패(정본 `:533`).
  - A4. 판정 불가는 Argo Rollouts의 **Inconclusive**로 만든다. 템플릿 질의는 0(통과)·1(실패)·2(판정 불가)를 내고, `successCondition: len(result) > 0 && result[0] == 0`, `failureCondition: len(result) > 0 && result[0] == 1`로 둔다. 2는 어느 조건도 만족하지 않아 Inconclusive가 되고, 롤아웃은 그 단계에서 멈춰 사람의 결정을 기다린다(Argo Rollouts 분석 문서, 2026-11-27 확인). 200건 미만이 판정 불가로 멈춘다는 D-T7의 요구와 같다.
  - A5. 분석 주기: `count: 2`, `interval: 1m`, `failureLimit: 1` [가정]. 5분보다 짧은 간격이고(정본 `:536`), 두 번째 실패에서 분석이 실패해 G-18의 '분석 두 구간 안에 자동 중단'과 맞는다.
  - A6. 차트 `service.rollout.analysis.enabled`가 켜지면 분석 단계를 낸다: 5% 단계 뒤에는 오류·이벤트 루프, 25%·50% 단계 뒤에는 오류·지연·이벤트 루프, 100% 단계에는 분석을 두지 않는다. 각 분석은 `setWeight` → `pause: 300s`(측정 창) → `analysis` 순서다. 분석 인자는 `service`, `canary-hash`(`podTemplateHashValue: Latest`), `stable-hash`(`Stable`)다.
  - A7. 실패 경보: `analysis_run_phase{phase="Failed"} == 1`을 0분에 SEV2로 울리고 RB-23 링크·G-18을 단다. 판정 불가(`phase="Inconclusive"`)는 5분에 SEV3로 울려 사람이 결정하게 한다 [가정].
  - A8. 롤아웃 컨트롤러 지표를 긁도록 `deploy/platform/argo-rollouts/values.yaml`의 `controller.metrics.serviceMonitor.enabled: true`를 켠다(차트 2.43.0 값, 2026-11-27 `helm show values` 확인).
  - A9. 이 기능이 넣지 않는 것: 온라인 불변식 지표(지금 `services/invariant-checker`는 DB 대조 도구이고 Prometheus 지표를 내지 않는다), 절대 SLO 판정(기존 SLO 기록 규칙·경보가 맡는다), Gateway API 트래픽 플러그인. 셋은 '남은 몫'에 적는다.
- **B. 리더 인지 롤링**
  - B1. 차트에 `service.rollingUpdate`(`maxUnavailable`·`maxSurge`)를 더해 Deployment `strategy.rollingUpdate`로 낸다. 둘 다 0이면 롤링이 멈추므로 렌더를 멈춘다.
  - B2. 차트 PDB에 `service.pdb.minAvailable`을 더한다. `minAvailable`과 `maxUnavailable`을 함께 주면 렌더를 멈춘다(쿠버네티스 PDB는 하나만 받는다).
  - B3. `deploy/workloads/admission-ctrl/values.yaml`(새): 복제 3, `rollingUpdate: { maxUnavailable: 1, maxSurge: 0 }`, PDB `minAvailable: 2`(3 가운데 2를 남겨 정족수 유지), `leaderLease: admission-ctrl`, 제어 gRPC 50061, 관리 포트 9464. Rollout·KEDA·HPA는 켜지 않는다(리더 하나가 쓰고 나머지는 대기한다).
  - B4. 리더 선출·펜싱 코드는 바꾸지 않는다. 이미 `LeaseElector`·`AdmissionLeader`가 있고(ADR-0056·0182), 이 기능은 배포 순서·정족수만 정한다. `pod-deletion-cost`·Kyverno 제한·리더 전용 Service는 F-09-8 몫이다.
  - B5. D-T31(리더 교체 횟수·serving 멈춤)은 kind와 `pod-deletion-cost`가 필요해 이 기능에서 닫지 않는다. [가정]만 기록한다: 주석이 없으면 복제 3에서 최악 3번, 주석이 있으면 보통 1번.

  - C1. `AdmissionLeader`에 `shadowTick()`을 더한다. Lease에 참여하지 않고, `activeEvents`·`schedule`·`control`·`platformControl`·제어 입력을 읽어 `decideAimd`로 목표를 계산만 하고, 리더가 `ctl`의 `targetNow`에 남긴 목표와의 차이를 `admission_shadow_diff{event_id}`(절댓값)와 `admission_shadow_target{event_id}`로 낸다. 쓰기(`bump`·`tick`·`close`·`rb05`)는 부르지 않는다.

### 3. 바른 동작과 근거(값은 정본에서 읽는다)

- **오류 비율의 세 조건**: 정본은 2배·0.5%p·5건을 모두 만족할 때만 실패로 본다(`docs/devops.md:530`). 200건에서 1건(0.5%)만으로 중단되는 헛판정을 막는 것이 5건 하한의 뜻이다(같은 줄, 기술 검토 중간-002). 질의는 세 조건을 곱해 1(실패)로 만들고, 요청 200건 미만은 2(판정 불가)로 만든다.
- **분모**: 정본은 4xx를 빼고 의도된 403·429·409를 정상으로 본다(`:530`). 서비스 지표의 `status_class` 라벨로 4xx를 분모에서 빼고(`status_class!="4xx"`), 분자는 `http_server_errors_total`(5xx만 센다, `docs/observability.md:173`)을 쓴다.
- **지연의 두 경로**: 요청 1,000건 이상이면 p99, 200~999건이면 p95, 200건 미만이면 판정 불가(`:531`·`:537`). 질의는 세 구간을 배타적으로 곱해 0·1·2를 낸다. 5% 단계에서는 지연 템플릿을 붙이지 않는다.
- **성공한 요청만**: 지연은 `status_class!="5xx"`인 요청만 본다(`:531`).
- **파드 구분**: Argo Rollouts가 분석 인자로 주는 `stable-hash`·`latest-hash`를 파드 이름 접두(`<서비스>-<해시>-`)로 써서 카나리·안정판을 가른다. 서비스 지표의 `pod` 라벨은 Prometheus가 긁을 때 붙는다.
- **분석 실패의 결과**: Argo Rollouts는 분석 실패 시 롤아웃을 자동 중단(abort)하고 안정판 100%로 돌린다(`:538`). 롤아웃은 Degraded가 되고, 경보가 RB-23을 가리킨다.
- **판정 불가의 결과**: Inconclusive 분석은 롤아웃을 그 단계에서 멈추고 사람이 resume/abort를 정한다(Argo Rollouts 분석 문서). 200건 미만에서 자동 통과하지 않는다.
- **리더 롤링**: 복제 3, `maxUnavailable: 1`, `maxSurge: 0`(`docs/devops.md:543`). PDB `minAvailable: 2`는 노드 정비 때 리더 하나가 남을 정족수다. 리더는 Lease를 놓고 대기 파드가 이어받는다(ADR-0056). `maxSurge: 0`이라 새 파드를 먼저 띄우지 않아 롤링이 순차적이다.
- **그림자**: Lease에 참여하지 않는 `admission-ctrl-shadow`가 같은 입력으로 결정을 계산만 하고 차이를 `admission_shadow_diff`로 남긴다(`:545`). 쓰기 권한이 없는 Redis 계정을 쓴다. 온세일 1회 이상에서 차이를 본 뒤 승격한다.
- **트래픽 미러링 아님**: Gateway API 트래픽 플러그인의 미러링 단계는 오류 없이 무시되므로 쓰지 않는다(`:521`). 그림자는 요청 복제가 아니라 제어 입력을 같은 프로세스 코드로 다시 계산하는 것이다.

### 5. 공개 인터페이스(시험 담당이 이 모양으로 시험을 먼저 쓴다)

- **생성 도구**: `node tools/ci/canary-analysis.mjs --write|--check`. `--check`는 생성 파일이 없거나 정책과 다르면 exit 1. 정책은 도구 안 `CANARY_POLICY`에 있고, 값은 정본 `docs/devops.md:525~537`과 G-18에서 온다.
- **생성 파일**: `deploy/platform/argo-rollouts/analysis-templates.yaml`. 세 문서 모두 `apiVersion: argoproj.io/v1alpha1`, `kind: ClusterAnalysisTemplate`, `metadata.name`은 위 셋. `spec.args`: `service`, `canary-hash`, `stable-hash`. `spec.metrics[0]`:
  - `name`: `error-ratio`·`latency`·`event-loop`
  - `interval: 1m`, `count: 2`, `failureLimit: 1`
  - `successCondition: len(result) > 0 && result[0] == 0`
  - `failureCondition: len(result) > 0 && result[0] == 1`
  - `provider.prometheus.address: http://prometheus.observability.svc:9090`, `timeout: 30s`
  - 질의는 오류·지연·이벤트 루프 각각 위 §3의 0/1/2를 낸다.
- **차트 값**:
  - `service.rollout.analysis.enabled`(bool, 기본 false). 켜면 `service.rollout.enabled`도 참이어야 하고, 아니면 렌더를 멈춘다.
  - `service.rollingUpdate.maxUnavailable`·`maxSurge`(int, 0 이상). 둘 다 0이면 렌더를 멈춘다. 하나라도 있으면 Deployment `strategy.type: RollingUpdate`와 `strategy.rollingUpdate`를 낸다.
  - `service.pdb.minAvailable`(int, 1 이상) 또는 `service.pdb.maxUnavailable`(int, 1 이상) 가운데 하나만. 둘 다 있으면 렌더를 멈춘다.
- **롤아웃 분석 단계**: `setWeight` 뒤 `pause: { duration: 300s }`, 그 뒤 `analysis.templates`가 온다. 5%는 `[peaket-canary-error-ratio, peaket-canary-event-loop]`, 25%·50%는 `[peaket-canary-error-ratio, peaket-canary-latency, peaket-canary-event-loop]`, 100%는 분석 없음. 템플릿 참조는 `{ templateName: <이름>, clusterScope: true }`, 인자는 `{ name: service, value: <서비스 이름> }`·`{ name: canary-hash, valueFrom: { podTemplateHashValue: Latest } }`·`{ name: stable-hash, valueFrom: { podTemplateHashValue: Stable } }`.
- **경보 이름·라벨**:
  - `peaket_canary_analysis_failed`: `analysis_run_phase{phase="Failed"} == 1`, `for: 0m`, `severity: sev2`, `kind: cause`, `runbook_url` RB-23, `game_day: G-18`.
  - `peaket_canary_analysis_inconclusive`: `analysis_run_phase{phase="Inconclusive"} == 1`, `for: 5m`, `severity: sev3`, `kind: cause`, `runbook_url` RB-23.
  - `admission_shadow_diverged`: `admission_shadow_diff > 0`, `for: 10m`, `severity: sev3`, `kind: cause`, `runbook_url` `docs/devops.md#63-admission-ctrl활성-리더-1`.
- **admission-ctrl 값**: `deploy/workloads/admission-ctrl/values.yaml`이 `name: admission-ctrl`, `service.replicas: 3`, `service.rollingUpdate: { maxUnavailable: 1, maxSurge: 0 }`, `service.pdb: { enabled: true, minAvailable: 2 }`, `service.leaderLease: admission-ctrl`, `service.extraPorts`에 `{ name: control, port: 50061 }`, `managementPort: 9464`를 갖는다. `service.rollout.enabled`·`service.autoscaling.enabled`·`service.keda.enabled`는 거짓이다.
- **그림자 값**: `deploy/workloads/admission-ctrl-shadow/values.yaml`이 `name: admission-ctrl-shadow`, `worker.enabled: true`, `service.replicas: 1`, `service.leaderLease: ""`, `secretEnvFrom: admission-ctrl-shadow-secrets`, `service.env.PEAKET_ADMISSION_SHADOW: "1"`, `service.env.PEAKET_PROMETHEUS_URL`을 갖는다. `service.networkPolicy.egress.internal`에 Redis·Prometheus 대상이 있다. 리더의 `admission-ctrl-secrets`를 쓰지 않는다.
- **서비스 공개 동작**: `AdmissionLeader.startShadow()`와 `shadowTick(): Promise<void>`가 있다. 그림자는 `admission_shadow_diff{event_id}`(절댓값, 리더 목표가 없으면 내지 않는다)·`admission_shadow_target{event_id}`를 낸다. `bump`·`tick`·`close`·`rb05`를 부르지 않는다.

- 실제 클러스터·Argo Rollouts 분석·그림자 트래픽을 쓰지 않았다는 사실과 미실행 항목이 측정 기록에 있다. 처리량·비용·리더 교체 시간을 새로 주장하지 않는다.
- `develop`·`release/1.0.0`에 합치지 않고 freeze 가지만 푸시한다.

### 11. 동결 로컬 범위와 한계

- 이 기능의 "완료"는 **정적 설정·생성 파일·단위 시험**까지다. 실제 `AnalysisRun` 실행, Prometheus 질의 응답, 자동 중단, 리더 교체 횟수·serving 멈춤, 그림자 차이는 클러스터가 필요해 `미실행`이다.
- `pod-deletion-cost`·Kyverno 제한·리더 전용 Service·`<서비스>-control` Service는 F-09-8 몫이다. 그 전에는 리더가 롤링 중 최악 3번 바뀔 수 있다 [가정].
- 그림자는 목표만 비교하고 입장 비율·serving은 비교하지 않는다. `slotsUsed`·`gated`를 같은 값으로 읽지 못한다 [가정].
- 읽기 전용 Redis 계정은 아직 없다. 그림자 값 파일은 다른 Secret 이름을 가리킬 뿐이고, 실제 ACL 사용자 생성·교체는 F-09-4/F-09-8 몫이다.
- 온라인 불변식 지표·절대 SLO 판정·Gateway API 트래픽 플러그인은 이 기능에 없다. 불변식은 `services/invariant-checker`와 SEV1 경로(RB-36), SLO는 F-01-5 기록 규칙·경보가 맡는다.
- `release/1.0.0`·`main`에는 어떤 커밋도 넣지 않는다. 체리픽하지 않는다(ADR-0386 결정 4).

### 12. 정본 빈칸

- **분석 주기·횟수·실패 허용**: 정본은 "집계 간격이 5분보다 짧다"(`docs/devops.md:536`)와 "분석 두 구간 안에 자동 중단"(G-18)만 적는다. `interval: 1m`, `count: 2`, `failureLimit: 1`로 정한다(추천 적용, 2026-11-27).
- **오류 질의의 분모**: `status_class!="4xx"`로 4xx를 뺀다. 개별 403·429·409를 라벨로 가르지 못하는 첫 구현의 한계다(추천 적용, 2026-11-27).
- **이벤트 루프 최소 표본**: 정본에 없다. 요청 수 하한 없이 값이 있으면 비교하고, 안정판 값이 없으면 판정 불가로 둔다(추천 적용, 2026-11-27).
- **판정 불가 경보**: 정본은 "사람의 결정을 기다린다"만 적고 심각도를 정하지 않는다. SEV3·5분으로 정한다(추천 적용, 2026-11-27).
- **그림자 불일치 경보**: 정본에 심각도·기간이 없다. SEV3·10분으로 정한다(추천 적용, 2026-11-27).
- **그림자 비교 범위**: 정본은 "입장 비율, 목표치"를 비교한다고 적지만(`:545`), 첫 구현은 리더가 `ctl.targetNow`에 남기는 목표만 비교한다. 비율 비교는 후속이다(추천 적용, 2026-11-27).
- **경보 대시보드 링크**: 롤아웃 대시보드가 아직 없다. `dashboard_url`은 정본 §6.2 절을 가리키고, 대시보드는 후속이다(추천 적용, 2026-11-27).
- **Redis 읽기 전용 계정 소유자**: F-09-4(비밀)·F-09-8(배포) 가운데 정본에 없다. 이 기능은 Secret 이름 분리까지만 하고 소유자는 남은 몫으로 둔다(추천 적용, 2026-11-27).
