## 감독에게

막는 물음은 없다. 아래는 추천대로 계획에 적었다. 다르게 정하면 이 계획과 그 정본 줄을 고친다.

1. **[결정 요청] 장부 범위를 `D-T6, D-T7`로 좁힌다.** 지금 범위 `D-T6, D-T7, docs/devops.md`는 항목 130개(빈칸 42·미검증 1·다른 단계 1)를 끌어온다. 나머지는 다른 기능(동결 달력·마이그레이션·WAF·MSK·취약점·kind 리더 교체) 몫이고, 리더 롤링·그림자를 가리키는 장부 항목은 없다. `docs/architecture.md` §8.6 2에 따라 좁히고 비고에 적는다. 좁히지 않으면 `ledger.mjs --batch F-09-11 --require`가 빈칸 42로 실패한다.
2. **[알림, 한계] 실제 클러스터·Argo Rollouts 분석·그림자 트래픽은 쓰지 않는다.** 분석 실행·자동 중단·리더 교체·그림자는 `미실행`/[가정]이다. 30k/s·100만·K1/K2/K7 같은 새 처리량 주장은 하지 않는다.
3. **[알림, 경계] F-09-10은 설치 값·카나리 단계·되돌리기 창까지다.** 이 기능은 그 위에 분석 템플릿·단계별 분석·경보·리더 롤링 값·그림자를 더한다. F-09-10의 차트 판(2.43.0)·컨트롤러 값과 차트 `service.rollout.steps`(5/25/50/100, 300초)는 그대로 쓴다.
4. **[알림, 경계] F-09-2(마이그레이션·Squawk·릴리스 플래그)·F-09-4(TLS/KMS/MSK·비밀 교체·CloudFront/WAF)는 건드리지 않는다.** Redis 읽기 전용 계정 생성·교체는 F-09-4/F-09-8 몫이고, 이 기능은 그림자 워크로드가 다른 Secret 이름을 쓰는 것까지만 정적으로 본다.
5. **[알림, 경계] F-09-8(INF-020)은 admission-ctrl 차트의 Lease RBAC·리더 전용 Service·`pod-deletion-cost`·`<서비스>-control` Service·kind 리더 교체(D-T31)를 맡는다.** 이 기능은 3복제·`maxUnavailable: 1`·`maxSurge: 0`·PDB `minAvailable: 2`·그림자 워크로드 값을 더한다. `pod-deletion-cost`가 없으면 리더 교체가 최악 3번 [가정]이고 D-T31은 이 기능에서 닫지 않는다.
6. **[알림, 경계] Gateway API 트래픽 플러그인은 켜지 않는다.** 정본은 플러그인이 맞지 않으면 복제본 비율 카나리를 허용하고(`docs/devops.md:507`), 미러링은 오류 없이 무시되므로 쓰지 않는다(`:521`). 그림자는 요청 미러링이 아니라 같은 제어 입력을 비리더가 계산만 하는 것이다(§6.3).
7. **[알림] B인데 새 세션 리뷰를 한다.** ADR-0373 결정 3은 B의 시험 리뷰를 빼지만, 이 트랙은 감독 지시로 새 세션 리뷰를 거친다. 리뷰 담당은 계획·시험·구현에 관여하지 않고, 계획 파일 '리뷰' 절과 담당 표 자기 줄만 고친다.
8. **[알림] `roles-check.mjs`는 이번 정지점의 게이트가 아니다.** 리뷰·구현 커밋이 없어 구성 실패(exit 1)가 정상이다. 까닭은 `## 검증`에 적었다.

## 계획

### 1. 범위

- **A. 카나리 분석(D-T6·D-T7)**
  - `deploy/platform/argo-rollouts/analysis-templates.yaml`에 `ClusterAnalysisTemplate` 셋(`peaket-canary-error-ratio`·`-latency`·`-event-loop`)을 둔다. 클러스터 범위라 서비스 네임스페이스마다 복사하지 않는다. `deploy/platform/argo-rollouts/analysis-application.yaml`이 이 파일만 적용한다(`directory.include`).
  - 템플릿은 `tools/ci/canary-analysis.mjs --write`가 만들고, 임계값·최소 표본은 그 도구의 `CANARY_POLICY` 한 곳에 둔다. `--check`가 생성 파일과 대조하며 사람이 생성 파일을 고치지 않는다.
  - 지표별 판정은 정본 `docs/devops.md:528~537` 그대로다: 오류는 2배·0.5%p·5건·요청 200건, 지연은 p99 1,000건/p95 200~999건/200건 미만 판정 불가·×1.2+5ms·5% 단계 제외, 이벤트 루프는 ×1.5.
  - 질의는 0(통과)·1(실패)·2(판정 불가)를 내고 `successCondition`은 0, `failureCondition`은 1만 본다. **200건 미만 가지는 `(<count> < bool 200) * 2 + (<count> >= bool 200) * (…)` 꼴로 `+` 결합**해, 200건 미만에서 0이 나와 성공으로 새는 길을 없앤다. 오류의 세 조건은 `*`(AND)로 잇고 `or`를 쓰지 않는다. 시험은 이 구조와 순서를 고정한다(RV0911-05).
  - `count: 2`, `interval: 1m`, `failureLimit: 1` [가정]. 5분보다 짧고 두 번째 실패에서 자동 중단해 G-18과 맞는다.
  - 차트 `service.rollout.analysis.enabled`가 켜지면 5% 뒤에 오류·이벤트루프, 25%·50% 뒤에 오류·지연·이벤트루프, 100%에는 분석을 두지 않는다. `setWeight` → `pause: 300s`(측정 창) → `analysis` 순서이고, 인자는 `service`·`canary-hash`(Latest)·`stable-hash`(Stable)다. 템플릿 `spec.args`가 셋을 선언하고 질의가 `{{args.<이름>}}`으로 파드 이름 접두를 가른다(RV0911-06).
  - 실패는 `analysis_run_phase{phase="Failed"}` 0분 SEV2(RB-23·G-18), 판정 불가는 같은 지표 5분 SEV3 [가정]. 롤아웃 컨트롤러 지표는 `controller.metrics.serviceMonitor.enabled: true`로 긁는다(차트 2.43.0, `helm show values` 확인).
  - 넣지 않는 것: 온라인 불변식 지표(지금 invariant-checker는 DB 대조 도구다. 불변식 1건 즉시 실패는 RB-36·SEV1 경로가 맡는다), 의도된 좌석 경합 409(정상 분기 카운터가 맡는다), 절대 SLO(기존 SLO 규칙·경보), Gateway API 트래픽 플러그인. '남은 몫'에 적는다.
- **B. 리더 인지 롤링**
  - 차트에 `service.rollingUpdate.enabled`(기본 false)와 `maxUnavailable`·`maxSurge`를 더한다. 기본 렌더는 전략을 내지 않고, 켤 때만 둘 다 0이 아닌 정수로 받아 Deployment `strategy`를 낸다(RV0911-08). `service.pdb.minAvailable`을 더하고 `maxUnavailable` 기본값은 null로 둔다. 둘 다 없으면 기존처럼 `maxUnavailable: 1`, 둘 다 있으면 렌더를 멈춘다(RV0911-09).
  - `deploy/workloads/admission-ctrl/values.yaml`(새): 복제 3, `rollingUpdate: { enabled: true, maxUnavailable: 1, maxSurge: 0 }`, PDB `minAvailable: 2`(3 가운데 2 유지), 관리 9464. Rollout·KEDA·HPA는 끈다.
  - 제어 gRPC 50061·`leaderLease`·리더 전용 Service·`<서비스>-control` Service는 F-09-8(OPS-300) 몫이라 이 값 파일에 넣지 않는다. 일반 Service에 제어 포트를 열어 3복제 가운데 비리더로 가게 하지 않는다(RV0911-10). 리더 선출·펜싱 코드도 바꾸지 않는다(`LeaseElector`·`AdmissionLeader`, ADR-0056·0182).
- **C. 그림자 계산**
  - `AdmissionLeader.shadowTick()`: Lease에 참여하지 않고 `activeEvents`·`schedule`·`control`·`platformControl`·제어 입력을 읽어 `decideAimd`로 목표를 계산만 하고, 리더의 **`ctl.memory.aimdTarget`**(나누기 전 AIMD 목표)과의 차이를 `admission_shadow_diff{event_id}`(절댓값)·`admission_shadow_target{event_id}`로 낸다. `targetNow`(TICK이 나누기 뒤에 쓰는 값)와 비교하지 않는다(RV0911-03). 쓰기(`bump`·`tick`·`close`·`rb05`)는 부르지 않는다.
  - 그림자가 읽는 `activeEvents`는 만료 회차를 지우지 않는 **읽기 전용**이어야 한다. 지우기는 리더 쪽 정리 경로가 맡고, 그림자는 `ZRANGE`/`ZRANGEBYSCORE`만 부른다(RV0911-01).
  - 첫 그림자는 목표만 비교한다. `slotsUsed`·`gated`는 리더의 tick 결과에만 있어 그림자가 같은 값을 읽지 못하므로 `undefined`·`false`로 계산한다 [가정]. 비율·serving 비교는 후속이다.
  - `start.ts`는 `startPlanOf(env)`를 내보내 `PEAKET_ADMISSION_SHADOW=1`이면 `elector`·`leader`·`control`·`rb35`·`batch`를 모두 끄고 `shadow`만 켠다. `start()`는 이 계획을 따라 선출·제어 gRPC·RB-35·묶음 결과 폴더를 열지 않고 `startShadow()`만 켠다(RV0911-02). Redis는 읽기 전용 계정 URL을 받는다.
  - `deploy/workloads/admission-ctrl-shadow/values.yaml`(새): 작업자 모드(앱 포트·Service 없음), 복제 1, `leaderLease` 없음, `secretEnvFrom: admission-ctrl-shadow-secrets`(리더와 다른 이름), `PEAKET_ADMISSION_SHADOW=1`, `PEAKET_PROMETHEUS_URL`, Redis·Prometheus egress(목적지 namespace/podLabels 포함).
  - `LeaderMetrics.shadow(eventId, diff, target)`은 `admission_shadow_diff`에 **절댓값**을 넣고 `admission_shadow_target`과 함께 등록·방출한다(RV0911-04). 불일치 경보는 `admission_shadow_diff > 0` 10분 SEV3, 런북 §6.3 [가정]. 읽기 전용 Redis ACL 생성·교체는 F-09-4/F-09-8 몫이고 로컬 Valkey에는 ACL 사용자가 없어 실제 그림자는 미실행이다.

### 2. 장부 범위

- 지금 `ledger.mjs --batch F-09-11`은 130개(자동 시험 84·측정 2·미검증 1·다른 단계 1·빈칸 42)를 낸다. `docs/devops.md`가 문서 전체를 끌어오기 때문이다.
- 이 기능이 닫을 항목은 **D-T6·D-T7 둘**이다. D-T31은 F-09-8(kind·`pod-deletion-cost`), D-T1~D-T5는 OPS-320, D-T8~D-T10·D-T44는 F-09-2, D-T30·D-T34는 F-09-4, D-T37·D-T46은 다른 인프라 기능 몫이다.
- `docs/BUILD_ORDER.md:146`의 장부 범위를 `D-T6, D-T7`로 좁히고 비고에 "장부 없음: 리더 인지 롤링·그림자 계산은 OPS-440 정적 시험·미실행 기록으로 본다(2026-11-27)"를 더한다(§8.6 2). 좁힌 뒤 `--require`는 두 항목이 시험 이름으로 자동 시험이 되면 통과한다. 빈칸을 `통과`로 바꾸거나 다른 기능 항목을 닫지 않는다.

### 3. 바른 동작과 근거(값은 정본에서 읽는다)

- **오류 비율**: 2배·0.5%p·5건을 모두 만족할 때만 실패다(`docs/devops.md:530`). 5건 하한은 200건에서 1건(0.5%)만으로 중단되는 헛판정을 막는다. 세 조건은 `*`(AND)로 잇고, 200건 미만은 `(<count> < bool 200) * 2`로 2를 내 성공(0)과 구분한다. `or`를 쓰지 않는다.
- **분모**: 4xx를 빼고(`status_class!="4xx"`) 분자는 `http_server_errors_total`(5xx만, `docs/observability.md:173`)을 쓴다. 의도된 403·429·409는 정상으로 본다.
- **지연**: 1,000건 이상 p99, 200~999건 p95, 200건 미만 판정 불가, ×1.2+5ms(`:531`·`:537`). 200건 미만은 `(<count> < bool 200) * 2`, 두 경로는 `+`로 결합한다. 성공한 요청(`status_class!="5xx"`)만 보고, 5% 단계는 지연을 보지 않는다.
- **파드 구분**: `ClusterAnalysisTemplate.spec.args`가 `service`·`canary-hash`·`stable-hash`를 선언하고, 질의가 `{{args.service}}-{{args.canary-hash}}-`·`{{args.service}}-{{args.stable-hash}}-`로 파드를 고른다. 전체 트래픽을 비교하지 않는다.
- **결과**: 분석 실패는 Argo가 롤아웃을 자동 중단하고 안정판 100%로 돌린다(`:538`). Inconclusive는 그 단계에서 멈춰 사람이 resume/abort를 정한다(Argo 분석 문서). 200건 미만이 자동 통과하지 않는다.
- **리더 롤링**: 복제 3, `maxUnavailable: 1`, `maxSurge: 0`(`:543`). PDB `minAvailable: 2`가 노드 정비 때의 정족수다. 리더는 Lease를 놓고 대기 파드가 이어받는다(ADR-0056). `maxSurge: 0`이라 새 파드를 먼저 띄우지 않는다. 제어 포트는 리더 전용 Service(F-09-8)로만 내보낸다(`docs/infra.md:534`).
- **그림자**: Lease에 참여하지 않는 `admission-ctrl-shadow`가 같은 입력으로 결정을 계산만 하고 차이를 `admission_shadow_diff`로 남긴다(`:545`). 쓰기 권한 없는 Redis 계정을 쓰고, 읽는 `activeEvents`도 지우지 않는다. 비교는 리더의 `aimdTarget`(나누기 전)과 그림자의 AIMD 목표다. 온세일 1회 이상에서 차이를 본 뒤 승격한다.

### 5. 공개 인터페이스(시험 담당이 이 모양으로 시험을 먼저 쓴다)

- **생성 도구**: `node tools/ci/canary-analysis.mjs --write|--check`. `--check`는 생성 파일이 없거나 정책과 다르면 exit 1. 정책은 도구 안 `CANARY_POLICY`에 있고 값은 정본 `docs/devops.md:525~537`·G-18에서 온다.
- **생성 파일**: `deploy/platform/argo-rollouts/analysis-templates.yaml`. 셋 다 `apiVersion: argoproj.io/v1alpha1`, `kind: ClusterAnalysisTemplate`, 이름은 위 셋. `spec.args`: `service`·`canary-hash`·`stable-hash`(질의는 `{{args.service}}`·`{{args.canary-hash}}`·`{{args.stable-hash}}`). `spec.metrics[0]`:
  - `name`: `error-ratio`·`latency`·`event-loop`, `interval: 1m`, `count: 2`, `failureLimit: 1`
  - `successCondition: len(result) > 0 && result[0] == 0`, `failureCondition: len(result) > 0 && result[0] == 1`
  - `provider.prometheus.address: http://prometheus.observability.svc:9090`, `timeout: 30s`

- **적용 Application**: `deploy/platform/argo-rollouts/analysis-application.yaml`이 `source.path: deploy/platform/argo-rollouts`·`directory.include: analysis-templates.yaml`로 생성 템플릿만 적용한다(차트 Application과 분리, RV0911-07).
- **차트 값**:
  - `service.rollout.analysis.enabled`(bool, 기본 false). 켜려면 `service.rollout.enabled`도 참이어야 하고 아니면 렌더를 멈춘다.

- **롤아웃 분석 단계**: `setWeight` → `pause: { duration: 300s }` → `analysis.templates`. 5%는 오류·이벤트루프, 25%·50%는 오류·지연·이벤트루프, 100%는 분석 없음. 참조는 `{ templateName: <이름>, clusterScope: true }`, 인자는 `service` 값과 `canary-hash`/`stable-hash`의 `podTemplateHashValue: Latest|Stable`.
- **경보**: `peaket_canary_analysis_failed`(`analysis_run_phase{phase="Failed"} == 1`, 0m, SEV2, `kind: cause`, RB-23, G-18), `peaket_canary_analysis_inconclusive`(같은 지표 `Inconclusive`, 5m, SEV3, RB-23), `admission_shadow_diverged`(`admission_shadow_diff > 0`, 10m, SEV3, §6.3). 셋 다 `summary`·`dashboard_url`을 갖고 묶음에 `interval`이 있다.

- **그림자 값**: `deploy/workloads/admission-ctrl-shadow/values.yaml`이 `name`, `worker.enabled: true`, 복제 1, `leaderLease: ""`, `secretEnvFrom: admission-ctrl-shadow-secrets`, `PEAKET_ADMISSION_SHADOW: "1"`, `PEAKET_PROMETHEUS_URL`을 갖고, egress에 Redis·Prometheus 목적지(namespace/podLabels)가 있다. 리더의 `admission-ctrl-secrets`를 쓰지 않는다.

- **start 분기**: `start.ts`가 `startPlanOf(env)`를 내보내 `PEAKET_ADMISSION_SHADOW=1`이면 `{ elector:false, leader:false, control:false, rb35:false, batch:false, shadow:true }`, 아니면 앞의 다섯이 true·`shadow:false`다.

### 11. 동결 로컬 범위와 한계

- "완료"는 **정적 설정·생성 파일·단위 시험**까지다. `AnalysisRun` 실행, Prometheus 응답, 자동 중단, 리더 교체·serving 멈춤(D-T31), 그림자 차이는 클러스터가 필요해 `미실행`이다.

### 12. 정본 빈칸

- **분석 주기·횟수·실패 허용**: 정본은 "집계 간격이 5분보다 짧다"(`docs/devops.md:536`)와 G-18의 "분석 두 구간 안"만 적는다. `interval: 1m`, `count: 2`, `failureLimit: 1` [가정].
- **오류 질의의 분모**: `status_class!="4xx"`로 4xx를 뺀다. 개별 403·429·409를 가르지 못하는 첫 구현의 한계다.
- **이벤트 루프 최소 표본**: 없다. 값이 있고 안정판 비교가 가능할 때만 판정한다.
- **판정 불가·그림자 경보**: 정본은 심각도·기간을 정하지 않는다. 판정 불가 SEV3·5분, 그림자 SEV3·10분 [가정].
- **그림자 비교 범위**: 정본은 "입장 비율, 목표치"를 적지만(`:545`) 첫 구현은 리더의 `ctl.aimdTarget`(나누기 전)만 비교한다. `targetNow`(나누기 뒤)와 섞지 않는다. 비율·serving은 후속이다.
- **경보 대시보드**: 롤아웃 대시보드가 아직 없다. `dashboard_url`은 정본 §6.2 절을 가리킨다.
- **Redis 읽기 전용 계정 소유자**: 정본에 없다. F-09-4(비밀)·F-09-8(배포)로 두고, 이 기능은 Secret 이름 분리까지만 한다.
