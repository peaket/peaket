### 3. 바른 동작과 근거(값은 정본에서 읽는다)

- **받는 곳과 비밀**(observability.md:510, secrets-and-keys.md:67~69·:96): 받는 곳 이름은 `irm-oncall`·`slack-ops`·`github-issues`·`deadman`·`evidence-collector` 다섯이다. 주소·토큰은 설정에 적지 않고 파일에서 읽는다(Alertmanager의 `url_file`·`api_url_file`·`http_config.authorization.credentials_file`). 파일은 `/etc/alertmanager/secrets/` 아래 일곱 개: `irm-oncall-url`, `slack-ops-url`, `alert-issue-relay-url`, `alert-issue-relay-token`, `healthchecks-ping-url`, `evidence-collector-url`, `evidence-collector-token`. 해제 알림(`send_resolved`)은 IRM·Slack·티켓은 켜고 데드맨·증거 수집기는 끈다(증거 수집기는 해제를 세기만 한다, :446).
- **경로**(:511, §5 표 :388~392, verification.md:162): 위에서부터 차례로 맞춘다.
  1. `alertname="Watchdog"` → `deadman`. 묶음 대기 0초, 다시 보내기 1분 [가정](:514). 여기서 멈춘다(아래로 내려가지 않는다).
  2. 증거 수집기: `severity="sev1"`, `severity="sev2"`이면서 `kind="cause"`, `alertname="IncidentDeclared"` 셋 → `evidence-collector`. 셋 다 아래로 이어 간다(`continue: true`).
  3. `severity="sev1"` → `irm-oncall`(이어 감)과 `slack-ops`. 묶음 대기 5초·묶음 간격 1분(:356, :401).
  4. `severity="sev2"` → `slack-ops`. 묶음 대기 5초·묶음 간격 1분.
  5. `severity="sev3"` → `github-issues`. 묶음 값은 Alertmanager 기본값(:357).
  6. 맨 위 받는 곳(어디에도 맞지 않음: 심각도 없음·모르는 값) → `slack-ops`.
  - 묶기 기준(`group_by`)은 지금 `[alertname, severity, kind, event_id, journey, dependency]`로 둔다 [추천]. 온세일·그 밖·의존성별 묶기와 억제(`inhibit_rules`)는 OPS-130(F-01-7)이 바꾼다.
- **문구에 싣는 칸**(:512, ADR-0139 결정 4): Slack 문구(틀 `peaket.slack.title`·`peaket.slack.text`)와 티켓 본문에는 경보 이름과 라벨 `severity`·`kind`·`event_id`·`journey`·`dependency`, 주석 `summary`·`runbook_url`·`dashboard_url`·`explore_url`만 싣는다. 그 밖의 라벨과 `description`은 싣지 않는다. 티켓 중계는 그 글을 `maskPiiText`(`@peaket/platform`, 원천 `pii-patterns.json`)로 한 번 더 가린다. 데모의 티켓은 공개 저장소의 Issues라 이 가림이 공개 범위다.
- **티켓 중계**(:513, guidelines.md:174·:239):
  - 받기: `POST /v1/alerts`, 몸은 Alertmanager 웹훅 판 4(`version` "4", `alerts[]`의 `status`·`labels`·`annotations`·`startsAt`·`endsAt`·`fingerprint`). Bearer 토큰은 `@peaket/platform`의 시간 일정 비교(`secret-compare.ts`)로 본다.
  - 고르기: `labels.severity`가 `sev3`인 경보만 다룬다. 그 밖은 `ignored`로 센다.
  - 발생(`firing`): 열린 티켓 가운데 라벨 `peaket-alert`이고 본문에 `peaket-alert-fingerprint: <지문>` 줄이 있는 것이 있으면 `duplicate`, 없으면 하나 열고 `created`. 열린 경보 티켓은 100건 [가정] 넘게 쌓이지 않는다고 보고 목록을 쪽(100건)마다 끝까지 읽는다. 같은 지문을 동시에 두 번 받아도 하나만 열리게 파드 안에서 지문마다 차례로 처리한다(복제 1).
  - 해제(`resolved`): 그 지문의 열린 티켓에 해제 시각 댓글을 달고 닫는다(`closed`). 열린 티켓이 없으면 `ignored`.
  - GitHub 호출은 `@peaket/platform`의 공용 외부 호출 클라이언트(`createExternalHttpClient`, 추적 전파 헤더 없음·리디렉트 안 따름)로 한다. 하나라도 실패하면(무응답·5xx·401·403·429) 그 웹훅에 502 Problem으로 답한다. Alertmanager가 다시 보내고, 다시 받은 발생 경보는 지문 확인으로 겹치지 않는다.
  - 인증: GitHub 앱 JWT(RS256, `iat` 60초 전·`exp` 9분 뒤 [가정], `iss` 앱 ID)로 설치 토큰을 받고, 만료 5분 전까지 다시 쓴다. 401이면 토큰을 버리고 한 번 다시 받는다.
  - 거절: 토큰 없음 → `reason` missing, 틀림 → mismatch. 401 Problem, 보안 사건 로그 줄 하나, `alert_relay_rejected_total{reason}` 하나. 로그 어디에도 받은 토큰 값을 쓰지 않는다(D-T51 ④와 같은 꼴).
  - 환경 값이 하나라도 없거나 키 파일을 읽지 못하면 듣기 전에 시작이 실패한다.
- **데드맨**(:514·:649): 규칙 `Watchdog`은 `expr: vector(1)`, 라벨 `severity: none`·`kind: control`, 주석 `summary`·`runbook_url`·`dashboard_url`(F-01-7의 주석 검사가 요구하는 둘을 미리 둔다). 묶음 이름 `watchdog`, 평가 간격 30초(§4 '그 밖의 규칙 평가 간격', :355). Prometheus가 1분마다 다시 보내고(`resend_delay` 기본) 경로 1의 다시 보내기가 1분이라 핑이 1분마다 간다. Healthchecks 점검 주기·유예(각 1분 [가정])는 소유자가 계정에서 맞춘다.
- **배포 기록**(devops.md:894, :892, secrets-and-keys.md:93): ArgoCD 알림 ConfigMap `argocd-notifications-cm`에 GitHub 서비스(ArgoCD 알림의 GitHub 앱, 값은 `$` 비밀 참조)와 템플릿 둘(`peaket-deploy-success`·`peaket-deploy-failure`, `github.deployment`의 `state`·`environment`·`reference`), 트리거 셋(`on-deployed` → success, `on-sync-failed`·`on-health-degraded` → failure)을 둔다. 환경 이름은 `{{index .app.metadata.labels "peaket.io/environment"}}/{{.app.metadata.name}}`, `reference`는 동기화한 커밋(`.app.status.operationState.syncResult.revision`). Grafana 주석 서비스는 두지 않는다(:892). 데모·운영 ApplicationSet의 앱 틀에 구독 주석 셋(`notifications.argoproj.io/subscribe.<트리거>.github: ""`)을 더한다. 로컬·CI·스테이징에는 더하지 않는다(DORA는 데모·운영 배포만 센다).
- **DORA 산출**(:895~902, :879~885 정의 표, :890 포트폴리오 정의): 다섯 값의 식은 정본 그대로다. 구현 담당이 정할 남은 세부는 이렇다. 중앙값은 개수가 짝수면 가운데 둘의 평균, 시간 단위는 시간(소수 둘째 자리 반올림 [추천]). 한 배포는 처음 `success`나 `failure`를 받은 시각의 주에 한 번만 센다. 실패한 배포의 회복은 같은 서비스의 다음 `success`이고, 주 밖에 있어도 그 실패의 주에 센다(아직 없으면 미회복). 리드타임은 그 서비스에 처음 배포된 PR만 센다(같은 PR이 다음 배포에 다시 세지지 않게, 앞 태그와의 비교로 고른다).
- **GitHub에서 읽기**(:895): 저장소 `--repo <owner/name>`, API 주소 `GITHUB_API_URL`(기본 `https://api.github.com`), 토큰 `GITHUB_TOKEN`(있으면). 읽는 경로는 §5의 목록뿐이다. 쪽 나눔은 `per_page=100`과 `page`로 끝까지 읽는다. 어느 하나라도 실패하면 끝 코드 2이고 보고 파일을 쓰지 않는다(빈 보고를 '자료 없음'으로 꾸미지 않는다).
