# 작업 계획: BAT-058(HOT-405 게이트웨이 프록시 Envoy 일꾼 수를 파드 CPU에 맞추고 V-T43 M-A를 다시 재 운영 차단 상한을 다시 센다)

- **무엇**: HOT-405(wbs 2.11.1 ③)의 작업 목록이다. 게이트웨이 프록시(Envoy Gateway가 띄우는 Envoy 파드)의 일꾼(요청을 처리하는 작업 스레드) 수를 파드 CPU 2 [가정]에 맞추는 설정을 `deploy/gateways`에 넣고, 그 무대(측정용 kind 클러스터)에서 V-T43 M-A(정상 부하 503 0건이 되는 가장 작은 동시 상한 찾기)를 다시 재 여유 배수 k를 정하고, k와 BAT-056이 잰 포화 처리량으로 운영 차단 상한(gw-queue와 나머지 넷)을 다시 센다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다. 정본의 값은 옮겨 적지 않고 자리만 가리킨다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane1`, 가지 `feature/lane1-BAT-058`, 출발점 `a383d344`. 구현 전 트리(분리 HEAD, 커밋하지 않음)는 `D:/ticketpass-lane1-base`. 두 폴더 모두 `pnpm install --frozen-lockfile`을 했다. 지시서는 `node tools/ci/brief.mjs --batch BAT-058`(만든 때 `a383d344`). 2026-11-18 계획 담당 `bat058-plan-960802c8`(claude-opus-5-5)가 썼고, 시험·제품 코드는 쓰지 않았다.
- **등급**: B(배포·운영, docs/BUILD_ORDER.md:60). 실패 증명은 실패 상황 시험(틀린 판 측정 M-W, 일꾼 수를 못 읽은 단계), 틀린 구현 표본(아래 9, 28개), 판정 기준 대조 표본이다(docs/architecture.md §8.6 3).
- **차례**: 정방향 묶음(이 계획 커밋에 `Batch-Order: impl-first`). ADR-0283 결정 2의 짧은 고리: 계획 → 구현 ①(설정·덧씌우기·측정 도구) → 감독에게 알림 → 감독의 '측정 시작' → 구현 담당의 측정 → 구현 ②(측정 결과 파일·정본 값·`deploy/gateways` 상한 값) → 시험(구현 전 트리에서 실패 확인을 같은 커밋에) → 리뷰 → 리뷰 반영 시험(재현 시험과 실패 확인 한 커밋) → 리뷰 반영 구현(고침과 시험 결과 한 커밋) → 검증(고친 곳 확인 포함) → 기록. 리뷰 반영 계획 커밋은 없고 다시 리뷰는 보안 높음만 한다. 시험 담당은 구현 ① 뒤에 일꾼·도구 시험을 먼저 쓰고, 상한 값 시험(S2·S3·K3)은 구현 ② 뒤 정본 값으로 고친다.
- **정본**: [ADR-0287](../../adr/0287-gateway-proxy-workers-match-pod-cpu-remeasure-k.md)(이 커밋에서 새로 씀), docs/infra.md §4.1 '게이트웨이 차단 상한'(:408~416, 이 커밋에서 '프록시 일꾼 수와 파드 CPU' 줄을 더하고 '값의 식'·'첫 값'·'측정(V-T43)'에 이어 씀), docs/verification.md:653 V-T43·:482 '게이트웨이 동시 처리·보류 큐', docs/architecture.md:1297 §9.4 행, docs/perf-ledger.md:117 `local-gw`, 앞선 측정 docs/review/measurements/BAT-056-gateway-breaker.md §4.2·§6·§7·§9, 앞선 계획 docs/review/plans/BAT-056.md §5, 소유자 결정 docs/PROGRESS.md 'OPEN[49] 닫음'(:62).

## 감독에게

방향을 바꾸는 결정은 정하지 않았다(파드 CPU 2 그대로, 새 이미지·도구 없음, kind 무대는 BAT-056과 같은 `cluster.mjs gateways`). 아래는 고른 것 가운데 알릴 것과 감독이 할 일이다.

1. **CPU 요청 2·한도 없음으로 골랐다(ADR-0287 결정 3, 추천 적용).** 일꾼 수만 적는 길(대안 3)은 '파드 CPU 2'가 설정 어디에도 없어 맞는지 시험할 것이 없고, 한도까지 2로 두는 길(대안 2)은 CPU 몫을 다 쓸 때 파드 스레드 전체가 잠깐 멈춰 3ms 빠른 실패와 지연 꼬리에 몰림을 더한다. 메모리 요청 512Mi는 Envoy Gateway 기본값을 다시 적은 것이다(`resources`를 적으면 기본값이 통째로 바뀐다, v1.10.0 소스 확인). 운영 쪽에서 한도를 두기로 하면 wbs 4.6.1에서 바꾼다.
2. **로컬·CI kind는 CPU 요청만 100m으로 낮춘다(ADR-0287 결정 4).** 다섯 파드 × CPU 2 = 10이 `kind / kind`의 `ubuntu-24.04` 표준 러너(vCPU 4)에 들어가지 않아 파드가 뜨지 않는다. 일꾼 수 2는 kind에서도 그대로다.
3. **포화 처리량은 다시 재지 않는다(ADR-0287 결정 8).** 단계 줄대로 BAT-056의 vCPU 하나 2,600/s(CPU 0.5·일꾼 1의 선형 추정)를 쓴다. CPU 2·일꾼 2에서 바로 재려면 도착률 6,000/s까지 발생기 6대(CPU 24·메모리 12GiB)가 들어 이 PC의 kind에 들어가지 않고 대역 백엔드(Node 프로세스 하나)가 먼저 찰 위험이 있다. 바로 재기를 원하면 무대를 크게 바꾸는 방향 결정이다(아래 12의 정리 목록 후보 1).
4. **측정 창(아래 6)**: 구현 담당이 설정·도구 커밋(구현 ①) 뒤 감독에게 알리고 '측정 시작'을 받은 뒤에만 잰다. Docker를 쓰는 시간은 약 1시간 20분이고 잠금은 1시간 30분으로 잡는다. **조용한 창(다른 갈래가 무거운 시험·빌드를 멈추는 시간)은 2시간을 부탁한다.** 이와 따로 시험 담당의 kind 실패 확인(약 25분, 측정 창과 겹치지 않게, 아래 8)도 Docker 잠금이 든다. 검증 담당은 Docker를 쓰지 않는다.
5. **운영 값이 내려간다.** 일꾼 2에서 k가 BAT-056 진단(약 2.6)과 비슷하면 gw-queue 동시·연결은 지금 2,400에서 1,600대로, 나머지 넷은 6,000에서 4,000대로 내려간다(식: docs/infra.md §4.1 '값의 식'). 결제 결과 롱 폴링 규칙은 gw-fan 게이트웨이 값을 따르므로 함께 내려가고, 그 줄의 '서비스가 먼저 덜어 내는 조건(gw-fan 파드 수 ≥ purchase-svc 파드 수의 1/3)'도 새 값으로 다시 셈해야 한다(구현 ②가 같은 줄을 고친다).
6. **멈출 조건**(구현 담당이 측정 중 만나면 운영 값을 고치지 않고 보고서와 함께 감독에게): A/A 두 번째도 잡음 판정선을 넘음, r_min을 정하지 못함(96까지 통과 없음, 경계를 세 번 옮겨도 3회 통과 없음, 무효가 한 값에 세 번), 잰 k(올리기 전)가 5보다 큼(ADR-0287 '되돌릴 조건'), 고친 운영 값의 정상 부하에서 503이나 넘침, 틀린 판 측정 M-W가 통과함.
7. **잠금 규칙(감독 지시 그대로, 아래 6·8에 다시 적음)**: 잡기 `bash D:/ticketpass-locks/lock.sh take docker lane1-BAT-058`(1로 끝나면 잠김: 시험·측정을 하지 않고 기다린다), 놓기 `bash D:/ticketpass-locks/lock.sh drop docker lane1-BAT-058`, 보기 `bash D:/ticketpass-locks/lock.sh who docker`. 지울 수 있는 잠금은 자기 갈래·묶음의 것뿐이다(도우미가 남의 잠금은 2로 거절한다). 갈래마다 한 담당만 잠금을 잡고, 하위 에이전트·포크에게 Docker 일을 나눠 맡기지 않으며, 잠금 없이 컨테이너를 띄우지 않는다(몇 초짜리 `docker run --rm`도).

### 4. 바른 동작과 정본 근거

값은 옮겨 적지 않고 위치만 적는다. 시험 담당은 단언 값을 아래 위치에서 직접 적는다.

**4.1 설정(G1)** — docs/infra.md §4.1 '프록시 일꾼 수와 파드 CPU', ADR-0287 결정 1~3

1. `deploy/gateways/00-common.yaml`의 EnvoyProxy `peaket-proxy`(GatewayClass `peaket`이 가리킴, gw-fan·gw-partner·gw-ops·gw-scanner)와 `peaket-proxy-queue`(Gateway gw-queue의 `infrastructure.parametersRef`) 둘 다:
   - `spec.concurrency`: 정본 '파드 CPU' 값(지금 2).
   - `spec.provider.kubernetes.envoyDeployment.container.resources`: `requests.cpu`가 같은 값(`"2"`, `2000m`도 같은 값으로 본다), `requests.memory` `512Mi`, `limits` 없음(CPU·메모리 모두).
   - 지금 있는 칸(`container.env`, `lua`, `filterOrder`, `telemetry`)은 그대로다.
   - `spec.extraArgs`가 없거나, 있어도 `--concurrency`·`--cpuset-threads`가 없다.
2. 다섯 게이트웨이가 받는 EnvoyProxy(자기 `infrastructure.parametersRef`, 없으면 GatewayClass의 것)가 모두 위 값을 갖는다. 게이트웨이 프록시용 Helm 차트는 없다(`deploy/charts/peaket-service`는 서비스 차트). `deploy/gateways/controller/envoy-gateway.yaml`(컨트롤러 설정)에는 일꾼 수 칸이 없어 고치지 않는다.
3. 파일 머리·그 객체 위 주석에 정본 자리(docs/infra.md §4.1 '프록시 일꾼 수와 파드 CPU', ADR-0287)를 한 줄 적는다.

**4.2 덧씌우기(G2)** — 같은 줄 끝, ADR-0287 결정 4

1. `localGatewayObjects`는 EnvoyProxy마다 envoy 컨테이너 `resources.requests.cpu`만 `100m`으로 바꾼다. `spec.concurrency`는 입력 값 그대로(상수로 덮어쓰지 않는다), `requests.memory`는 입력 값 그대로, `limits`를 새로 만들지 않는다. 입력 객체는 바꾸지 않는다(지금처럼 깊은 복사). 지금 하는 일(Service ClusterIP, 이미지, 추적 백엔드)은 그대로다.
2. 머리 주석의 '로컬 덧씌우기' 목록에 이 줄과 까닭(vCPU 4 러너)을 더한다.

**4.3 측정 도구: 실제 일꾼 수와 평균 지연(G3)** — docs/infra.md §4.1 '측정(V-T43)' 끝 ①·⑤, ADR-0287 결정 6·10

1. 읽는 값: 프록시 파드마다 지금 통계를 읽는 자리(`kubectl get --raw /api/v1/namespaces/envoy-gateway-system/pods/<파드>:19001/proxy/stats/prometheus`)의 게이지 `envoy_server_concurrency`(Envoy 통계 `server.concurrency`). 줄 꼴(`이름 값`, `이름{} 값`)은 구현 담당이 무대에서 확인하고 '구현 메모'에 적는다. 이름이 앞부분만 같은 다른 지표는 읽지 않는다. 그 줄이 없거나 값이 음이 아닌 정수가 아니면 오류(0으로 두지 않는다).
2. 기대 값: `gw sweep --workers <n>`(1~64 정수)이 있으면 n, 없으면 그 게이트웨이 EnvoyProxy의 `spec.concurrency`(있을 때), 둘 다 없으면 기대 값 없음(읽은 값을 적기만 함). `gw capacity`는 자기가 묶은 일꾼 수(⌊CPU⌋, 1 이상)가 기대 값이고 `--workers`를 받지 않는다(인자 오류 2).
3. 언제: 단계마다 상한이 실린 것을 본 뒤, 부하(발생기)를 띄우기 전에 그 게이트웨이의 모든 프록시 파드를 읽는다. 한 파드라도 기대 값과 다르면 그 단계는 부하를 넣지 않고 무효(까닭 `일꾼 수가 <기대>가 아님(<파드> <값>)`), 못 읽으면 무효(까닭 `일꾼 수를 못 읽음: …`). 무효 단계는 성능 장부에 판정 없이(무효 까닭으로) 넘긴다(지금 무효 단계와 같다).
4. 결과 파일 단계 줄에 `workers: { expected: <n|null>, source: 'flag'|'envoyproxy'|'capacity'|null, pods: { <파드>: <값> } }`를, 장부 `notes`에 `일꾼 수(관리 포트) <파드> <값>…, 기대 <n>(<출처>)` 한 줄을 더한다. 지금의 `proxyText`(EnvoyProxy 칸 값)도 그대로 둔다.
5. 평균 지연: 단계 줄의 흐름마다 2xx 응답 시간에 `avg`를 더한다. 값은 발생기마다의 k6 요약 `gw_dur_2xx`의 `avg`를 그 발생기의 그 흐름 2xx 수로 가중한 평균이다(합친 요약 `merge`의 trend 통계는 발생기 가운데 큰 값이라 쓰지 않는다, `loadtest/runner/merge.mjs` 머리 주석). 발생기마다의 값을 못 얻으면 `avg`는 `null`이고 `gw limits`가 그 단계를 쓰지 못한다(아래 4.4).

**4.4 측정 도구: `gw limits`(G4)** — docs/infra.md §4.1 '값의 식'·'측정(V-T43)' ④⑤, ADR-0287 결정 7

1. 명령: `node loadtest/run.mjs gw limits --from <sweep.json>[,<sweep.json>…] --saturation <vCPU 하나의 초당 건수, 정수> --pod-cpus <코어, 정수> [--out <폴더>]`. `--from`·`--saturation`·`--pod-cpus`는 꼭 있어야 한다(기본값을 숨기지 않는다). 끝 코드 0(정해서 씀), 1(파일을 못 읽음, 입력이 섞임, r_min을 정하지 못함. 까닭을 한 줄씩 찍고 결과 파일에 `determined: false`와 까닭·더 재야 할 것을 쓴다), 2(인자 오류).
2. 입력 거르기: 단계마다 정상 부하(`delay` normal, `mix` normal)이고 게이트웨이 gw-queue·라우트 gw-queue-buy이며, 모든 단계의 도착률이 같고, 보류가 ⌈동시 ÷ 8⌉이고, 연결 = 동시이어야 한다. 하나라도 어기면 1(섞인 입력을 조용히 버리지 않는다). 무효 단계는 통과로도 실패로도 세지 않는다.
3. r_min: 후보(동시 값)마다 유효 단계의 통과·실패 수를 센다. '실패한 가장 큰 후보'의 바로 위 후보가 c이고(실패가 없으면 가장 작은 후보), c의 유효 단계가 3개 이상이고 모두 통과면 r_min = c. 아니면 정하지 못함(까닭과 '<c>를 <n>번 더 잰다' 같은 다음 할 일). 가장 작은 후보가 c인데 실패가 없으면 정하지 못함('더 작은 후보를 잰다'). 통과가 하나도 없으면 정하지 못함.
4. 평균 지연 L̄ = r_min 유효 단계들의 진입 2xx `avg` 평균(그 단계 `avg`가 `null`이면 정하지 못함). 계산은 마이크로초 정수로 반올림한 뒤 한다.
5. 셈(모두 정수로, 마지막에 한 번 올림): k10 = ⌈10 × r_min × 1,000,000 ÷ (도착률 × L̄µs)⌉, k10 < 20이면 20. 동시·연결 = ⌈k10 × 6 × 포화 처리량 × 파드 CPU × L_gw(ms) ÷ 100,000⌉(0.6 = 6/10, k = k10/10, L_gw는 ms/1,000을 한 분모로 묶은 것), L_gw는 gw-queue 200ms, 나머지 넷 500ms(docs/infra.md '값의 식'). 보류 = ⌈동시 ÷ 8⌉. r_pc = ⌈k10 × 도착률 × L̄µs ÷ 10,000,000⌉.
6. 결과 파일 `limits.json`: `determined`, `inputs`(파일, 포화 처리량, 파드 CPU, 도착률), `runs`(후보마다 통과·실패·무효 수), `rMin`, `meanLatencyMs`, `kRaw`(올리기 전, 소수), `k`(k10 ÷ 10), `rPod`(0.6 × 포화 처리량 × 파드 CPU), `rPc`, `limits: { 'gw-queue': { maxConnections, maxParallelRequests, maxPendingRequests }, others: {…} }`, `reasons`. 콘솔에 같은 내용을 한국어 몇 줄로.
7. 0.6·L_gw·1/8·k 하한 2는 정본 값이라 도구 상수로 두고 머리 주석에 정본 자리를 적는다. 시험은 이 상수를 가져오지 않는다.

**4.5 측정 뒤 값 고침(G5, 구현 ②)** — ADR-0287 결정 9

1. `gw limits` 결과가 멈출 조건(위 '감독에게' 6)에 걸리지 않으면, `deploy/gateways` 다섯 파일의 `gw-<이름>-responses` `circuitBreaker` 세 칸을 결과 값으로 고친다(gw-queue는 `gw-queue`, 나머지 넷은 `others`). 관제 SSE 규칙의 65,536과 결제 결과 롱 폴링(게이트웨이 값을 따름)의 구조는 그대로다.
2. 정본: docs/infra.md §4.1 '첫 값(측정 전)'을 '잰 값으로 고친 값'으로(입력·k·결과 값·보고서 경로·실행 ID, 첫 값 줄은 이력으로 한 구절 남김), '길게 쥐는 라우트'의 'gw-fan 게이트웨이 값(동시·연결 6,000, 보류 750)'과 '서비스가 먼저 덜어 내는 조건'(gw-fan 파드 수 ≥ (purchase-svc 파드 수 × 2,000) ÷ 새 gw-fan 값)을 새 값으로, docs/verification.md:482(값·일꾼 수·성격 '실측(PC)')·:653 끝 결과 한 문장, docs/architecture.md:1297 끝 한 문장, docs/review/ledger-notes.md V-T43 ①·② 줄(위 2).
3. 측정 보고서와 성능 장부 실행 폴더(`docs/perf-ledger/runs/<날짜>-bat058-*`)를 같은 커밋에 넣는다(측정을 한 담당의 커밋).

- **판정**: ② A/A는 두 번 모두 503 0·넘침 0이고 진입 2xx 평균 차이 ≤ 두 평균의 5%이면 조용함. 넘으면 A/A를 한 번 더, 또 넘으면 멈춘다. ③④ 각 단계는 정본 판정 ①(503 0건·넘침 0, 무효가 아님). ⑥의 운영 값은 ① 통과, 과부하 둘은 정본 판정 ②(503 p99 ≤ 3ms, 503 모두 `Retry-After`·Problem, 처리 중 최대 ≤ 상한, 무효가 아님). ⑦은 503 > 0 또는 넘침 > 0이어야 '틀린 판을 잡음'이다.
- **k와 운영 상한**: 정본 docs/infra.md §4.1 '값의 식'(식과 반올림 규칙)과 '첫 값' 끝(포화 처리량 2,600, 파드 CPU 2). 셈은 `gw limits`가 하고, 보고서에 손 셈 한 줄(r_min ÷ (1,500 × L̄) → k → 두 상한)을 함께 적어 같은지 본다. 다르면 멈추고 '구현 메모'에 적는다(도구 결함).
- **BAT-056과 견줌(보고서에만)**: 일꾼 32의 k 10.6·r_min 128, 일꾼 2 진단의 약 2.6(BAT-056 보고서 §4.2·§6)과 새 k. A/A 잡음 폭 밖으로 다른지를 적는다.
- **결과를 남길 곳**: ① 보고서 docs/review/measurements/ 아래 `BAT-058-gateway-workers.md`(무대, 명령, 실행 ID, A/A 표와 판정선, 후보 표(동시·보류·503·넘침·처리 중 최대·진입 2xx 평균·읽은 일꾼 수·판정), r_min 경계, `limits.json` 값과 손 셈, 운영 값 정상 부하, 과부하 둘, 틀린 판, BAT-056과 견줌, 한계, 원자료 위치 `.cache/peaket-loadtest/…`) ② 성능 장부 `docs/perf-ledger/runs/<날짜>-bat058-*`(프로파일 `local-gw`) ③ 위 4.5의 정본 자리.
- **걸리는 시간(Docker 잠금)**: 무대 10분, A/A 4분, 후보 열 18분, 경계 5~10분, 운영 값·과부하 둘 6분, 틀린 판 5분(롤아웃 포함), 정리 5분, 여유 20분. **합 약 1시간 20분, 잠금은 1시간 30분, 조용한 창은 2시간을 부탁한다.** 보고서·정본·`deploy` 값 고치기와 커밋은 약 40분이고 잠금 밖이다.

### 11. 시험·구현 지시문에 넣을 '자주 놓친 결함'

docs/architecture.md:1156-1170의 목록을 그대로 넣고, 이 묶음에서 특히 걸리는 것은 아래다.

- 측정 도구는 빈 결과·못 읽음이 '통과'로 새지 않게 한다: 일꾼 수 지표가 없음, `avg`가 없음, r_min을 정하지 못함은 무효나 끝 코드 1이다(BAT-022의 조용한 SKIPPED와 같은 모양).
- 판정 함수만 시험하지 말고 부르는 쪽을 본다: 일꾼 수가 다르면 발생기를 띄우는 명령이 실제로 나가지 않는지, 장부에 판정 대신 무효 까닭이 넘어가는지.
- 경계값은 양쪽을 다 둔다: k가 정확히 0.1 단위인 값(2.6)과 바로 위(2.614), 하한 2 아래·위, 보류 나눗셈이 딱 나눠지는 값(4,056 ÷ 8)과 아닌 값.
- 소수 곱셈 뒤 올림은 끝자리 오차로 하나 커진다(k 2.2 × 3,120 × 0.5 → 3,433). 셈은 정수로.
- 시험 값이 코드 상수와 같으면 상수를 잘못 쓴 결함이 숨는다: 덧씌우기 입력 일꾼은 3, `--workers`는 5처럼 운영 값 2와 다르게.
- 같은 규칙을 두 곳에서 지키면 하나를 빼는 결함이 가려진다: 일꾼 수는 형식 칸과 `extraArgs` 두 길이 있다(WS1과 WS4를 따로). EnvoyProxy가 둘이라 하나만 맞는 판을 따로 본다.
- 허용·거부 목록은 목록 밖 값마다: `--workers`의 0·음수·소수·글자·상한 넘음, 다른 하위 명령에서의 `--workers`.
- 측정 보고서의 숫자는 도구 결과와 손 셈이 같은지 적는다(BAT-056 보고서 §7 (나) 줄의 k 2.6과 2.66처럼 섞이지 않게).
- Docker·잠금: 잠금 도우미로만 잡고 놓는다(위 6). 남의 잠금은 지우지 않는다. 잠금 없이 컨테이너를 띄우지 않는다. 하위 에이전트에게 Docker 일을 나누지 않는다.

구현 ①(2026-11-19, `bat058-impl-b245b167`, 설정·덧씌우기·측정 도구. 측정과 구현 ②는 감독의 '측정 시작' 뒤).

1. **일꾼 수 지표 줄 꼴**: 도구는 `envoy_server_concurrency <값>`과 `envoy_server_concurrency{} <값>` 두 꼴만 읽는다(값은 0 이상 10진수 정수, 꼬리표가 붙은 줄·이름이 앞부분만 같은 지표는 읽지 않음, 서로 다른 값으로 두 줄 이상이면 못 읽음). 무대 확인(2026-11-19 측정 첫 단계 전): 다섯 프록시 파드 모두 `# TYPE envoy_server_concurrency gauge` 다음 줄이 `envoy_server_concurrency{} 2`였다(`이름{} 값` 꼴, 측정 보고서 §4). 도구를 고치지 않았다.
2. **읽는 자리와 차례**: 일꾼 수는 통계 읽기와 같은 kubectl 인자 `get --raw /api/v1/namespaces/envoy-gateway-system/pods/<파드>:19001/proxy/stats/prometheus`의 글에서 읽는다(파드마다 따로, 하나를 못 읽어도 나머지를 읽음). sweep 단계 차례: 임시 정책 적용 → `/clusters`에 상한이 실림(`readAdmin`) → 일꾼 수 읽기 → 문제가 없을 때만 `runLoad`. capacity 단계 차례: CPU 묶기·롤아웃 → 단계마다 EnvoyProxy 읽기 → 일꾼 수 읽기(기대 = 묶은 값 ⌊CPU⌋, 1 이상, 출처 `capacity`) → `runLoad`.
3. **내보낸 함수(시험이 써도 되는 공개 인터페이스)**:
   - `loadtest/runner/gw.mjs`: `parseServerConcurrency(text)` → 정수(아니면 Error), `expectedWorkers({ flag, concurrency })` → `{ expected, source: 'flag'|'envoyproxy'|null }`(flag가 앞섬, EnvoyProxy 값이 0 이상 정수가 아니면 Error), `workersProblem({ expected, pods, errors? })` → 무효 까닭 글 또는 null, `workersText(w)` → 장부 notes 글, `weightedMean2xx(summaries, stream)` → ms 또는 null, `limitsSteps(files)`·`limitsRMin(steps)`·`limitsValues({ rMin, meanLatencyUs, rate, saturation, podCpus })`·`gwLimits(files, { saturation, podCpus, paths?, readErrors? })`·`limitsLines(result)`. `judgeSweepStep`·`judgeSweepStreams`는 입력 `workersError`(무효 까닭)를 받는다(상한이 실리지 않음 다음, 통계 못 읽음 앞에서 무효).
   - `loadtest/runner/gw-run.mjs`: `readWorkers(deps, pods, { expected, source })` → `{ workers, problem }`, `runLimits(a, deps)`(deps = `{ readFile(path), save(name, value), log }`, 끝 코드 0·1).
   - `parseGwArgs`: sweep 결과에 `workers: number|null`(`--workers`, 1~64 정수. 0·음수·소수·글자·65·값 없음은 인자 오류). `--workers`는 sweep에만 있어 capacity·ip-limit에 주면 '<명령>에 없는 인자'로 끝 코드 2. limits 결과는 `{ command: 'gw', sub: 'limits', from: string[], saturation, podCpus, out? }`.
4. **결과 파일 칸**: sweep 단계 줄 `workers: { expected, source, pods: { <파드>: 값|null }, errors?: { <파드>: 까닭 } }`(부하를 넣은 단계와 일꾼 수로 무효인 단계 모두), 흐름마다 `streams.<흐름>.latency2xx: { p50, p99, max, avg }`, 재는 흐름이 하나면 `latency['2xx'].avg`도 같은 값, 맨 위 `workersFlag`(`--workers` 값 또는 null). capacity 단계 줄에도 `workers`. 일꾼 수로 무효인 sweep 단계 줄은 `sent: 0`, `valid: false`, `verdict: 'invalid'`, `item`, `invalid_reason`, `reasons: [까닭]`이고 `streams`가 없다. 까닭 글은 계획 4.3의 3 그대로 `일꾼 수가 <기대>가 아님(<파드> <값>[, …])`(다른 파드만, 이름 차례. 조사는 계획 글대로 '가')과 `일꾼 수를 못 읽음: <파드>: <까닭>[; …]`. 장부 notes 줄은 `일꾼 수(관리 포트) <파드> <값>[, …], 기대 <n>(<출처>)`(기대가 없으면 `기대 없음`)과 재는 흐름마다 `<흐름> 2xx 평균 <ms>ms(발생기 2xx 수로 가중)`.
5. **발생기마다의 요약**: `runLoad`가 돌려주는 값에 `summaries`(발생기마다의 k6 요약, 합치기 전)를 더했다(`loadtest/run.mjs`는 `evs.map((e) => e.summary)`). 가중 평균은 요약마다 `gw_dur_2xx{phase:main,stream:<흐름>}`의 `values.avg`를 `gw_reqs{phase:main,stream:<흐름>,cls:2xx}`의 `values.count`로 가중한다. `summaries`가 없거나, 한 요약이라도 그 2xx 수 지표가 없거나, 2xx가 1건 이상인 요약에 avg가 없으면 `null`이다. 지금 시험의 가짜 `runLoad`는 `summaries`를 주지 않아 avg가 null이다(WU6은 가짜가 `summaries: [요약 둘]`을 준다).
6. **계획과 달리 하거나 더 정한 것**:
   - (가) 일꾼 수로 무효인 단계는 성능 장부에 넘기지 않는다(`deps.record`를 부르지 않음). 부하가 없어 k6 요약·본구간 시각이 없고 `collect.py`는 `--k6-summary`가 꼭 있어야 하기 때문이다. 지금의 '상한이 실리지 않음' 무효 단계와 같은 처리이고, 그래서 장부에 판정(`--verdict pass`)으로 남는 일이 없다. 결과 파일에는 무효 줄이 남는다.
   - (나) capacity는 일꾼 수로 무효인 단계에서 멈춘다(지금 capacity가 무효 단계에서 멈추는 것과 같다). 원래 EnvoyProxy로 되돌리는 패치·주석 지우기·롤아웃은 정리가 그대로 낸다.
   - (다) r_min의 '바로 위 후보'는 입력에 있는 후보 가운데 '실패한 가장 큰 후보'보다 큰 가장 작은 값이다(정본 그리드는 도구에 두지 않음). 다음 할 일 글은 `동시 상한 <c>에서 <n>번 더 잰다`, `동시 상한 <c>보다 작은 후보를 잰다`, `동시 상한 <F>보다 큰 후보를 잰다`다.

- **자주 놓친 결함**: 경계 양쪽(5 정확히와 바로 위), 빈·섞인 결과가 통과로 새지 않음, 겹친 가드, 시험 값과 상수(WU8 손 셈 넷은 정본 식에서 적었고 도구 상수를 가져오지 않는다)를 봤다. 걸리는 것은 경계의 RV-03, 섞인 입력의 RV-04다. RV-04를 고치면 sweep의 일꾼 수 무효와 겹친 가드가 되므로 `gw limits` 쪽을 따로 잡는 시험이 있어야 한다.

**운영 상한을 올리는 것에 대한 판단: 보류(이 값으로 올리지 않는다)**

- 까닭: ① r_min 64는 60초 안에 멈칫이 드는지에 크게 기대는 값이고, 그 멈칫의 출처는 재지 않았으며 어느 쪽이든 운영 파드와 다른 무대의 성질인데 정본 식이 그것을 곱으로 키운다(RV-01). ② 되돌릴 조건(k > 5)이 잡음 안에서 갈렸다(RV-02). ③ 올려서 얻는 것이 없다. 운영 파드에서 같은 멈칫의 몫은 k 2의 상한으로도 덮이고, 올리면 과부하 차단만 늦어진다(RV-07).
- 위험이 커서 보류하는 것이 아니다(3,120·7,800에서도 V-T43 ①②는 통과했다). 근거가 멈출 선과 잡음 안에서 갈려서다.
- 권하는 처리: `deploy/gateways` 다섯 파일과 정본의 운영 값은 지금 develop 값(gw-queue 2,400·300, 나머지 6,000·750)으로 두고, 이번 결과는 '잰 값(적용 보류)'로 적는다(BAT-056이 잰 입력만 정본에 적고 첫 값을 두던 법과 같다). 아래 '다시 잴 것' 뒤에 감독이 정한다. 감독이 규칙대로 받기로 하면 RV-01·02는 보고서·ADR-0287의 '남는 한계'로 적고 나머지 지적만 고친다.

계획 담당 `bat058-plan-960802c8`(claude-opus-5-5)가 2026-11-19에 감독 결정을 받아 적었다. **감독 결정**: 리뷰 권고대로 새 운영 상한(gw-queue 3,120·390, 나머지 7,800·975)은 적용을 보류한다. `deploy/gateways`와 정본의 운영 값은 develop 값(gw-queue 2,400·300, 나머지 6,000·750) 그대로 두고, 첫 측정 결과는 '잰 값(적용 보류)'로 남긴다. 운영 값은 이 묶음 안에서 진단 측정 하나로, 재기 전에 정한 규칙대로 정한다. 짧은 고리라 이 절이 고칠 목록이고 리뷰 반영 계획 커밋은 이것 하나다(정본 빈칸을 정해야 해서 계획 담당이 썼다). 다시 리뷰는 없고(보안 지적 없음), 고친 곳은 검증이 본다.

### 이 커밋에서 정본에 쓴 것(모두 '감독 결정·추천 적용, 2026-11-19, BAT-058 리뷰 반영')

- docs/infra.md §4.1: '잰 값으로 고친 값' 줄을 '지금 값과 잰 값(적용 보류)'로 바꿨다. 지금 운영 값은 첫 값이고, BAT-058 첫 측정 값과 보류한 까닭을 적었다. 새 줄 '진단 측정으로 정함'에는 무대, 차례, 결정 규칙, 성능 장부 표시를 적었다. '측정(V-T43)' ⑤에는 RV-03·RV-04의 두 가드를 더했다. '길게 쥐는 라우트'의 gw-fan 값과 '서비스가 먼저 덜어 내는 조건'은 지금 값(6,000, 1/3·14개)으로 되돌렸고, 값이 바뀌면 같은 식으로 다시 센다는 구절을 더했다.
