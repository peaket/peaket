# F-04-6 계획 — 마감 실행기 R0~R3와 정산 대조 (빠른 길, 파트너 정산 몫)

- **무엇**: 기능 표 F-04-6(OPS-240) 작업 목록이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **절차**: 빠른 길(ADR-0373 결정 3)이다. 갈래 6이 구현과 시험을 함께 하고, 완료 정의의 동작을 돌려 보인 명령과 숫자를 '시험 결과'에 남긴다.
- **완료 정의**: 마감 실행기 R0~R3와 동결·정산 대조가 돈다(BUILD_ORDER F-04-6 행).
  - 장부: docs/features/analytics.md, docs/features/settlement.md, docs/observability.md, docs/security/asvs/analytics.md.
- **감독 지시(2026-11-23)**: F-04-6은 파트너 정산 숫자에 필요한 몫만 한다. 파트너 판매 요약(SCR-027)은 R3 확정 뒤 게시되고(analytics §8.4), 그 판매 대금·환불은 회차 정산서와 원 단위로 맞아야 한다(§7 '정확성(돈)').
- **이 출력을 읽는 곳**:
  - 파트너 판매 요약(SCR-027, F-04-7의 `partner_sales_gold`)이 R3 현재 판·F15·F8을 읽는다.
  - 관제 공연 리포트(SCR-029 ④, F-04-7)가 마감 단계·'데이터 품질'(정산 대조 결과)을 읽는다.

두 번에 나눈 빌드는 다음 차례로 돈다.

1. dbt를 고정 인자 목록으로 부른다. 셸을 거치지 않는다.
2. 사실·차원을 먼저 만든다.
3. R3이면 정산 대조를 한다.
4. 대조에서 실패한 지표를 `quality_failed`로 넘겨 지표·판정을 만든다.
5. 모두 통과하면 `swap_current_run`을 부른다.

실패하면 판을 바꾸지 않고 `close_run_log`에 FAILED를 남긴다('마감 지연').

R3 정산 대조는 두 가지를 본다.

- 회차 × 결제사의 F15(판매 금액 − 되돌림 금액)와 그 결제사 정산서(STATEMENT_NOTIFIED, 판본 가장 큰 것)의 판매 대금.
- 회차의 F8 환급 합과 정산서 환급 합.

어긋나면 `sales_amount`·`refunds`의 판정을 보류하고, 품질 표에 FAIL로 남긴다.

R2 뒤에는 두 가지 방법으로 숫자를 지킨다. 원시(실버)가 90일 뒤 지워져도 R3 판매 대금이 맞게 하려는 것이다.

- 매일 한 번 다시 만들 때, 80일 [가정]보다 오래된 날의 F15·F8 행은 앞 판에서 옮긴다.
- 온세일 사실 F1~F7은 R2 판에서 옮긴다.

빼는 것(이번 몫 아님, 감독 지시에 따라 '남긴 것'에 적는다):

- 커버리지로 마감 보류(A-T17)
- 실시간 대비 대조(A-T8)
- SLO·비용·운영 기록 파일 적재
- 동결 아카이브(S3 Parquet, A-T19)
- 장르 랭킹(동결)
- S3 수집 버킷 경로(배포 F-09-8)

## 정본 빈칸과 고른 안

1. 실행기는 TypeScript 작업자 `services/close-runner`(pnpm 작업 공간)이다. dbt는 Python이라, 운영 이미지에 dbt 가상 환경을 함께 담는 것은 배포(F-09-8) 몫이다. 경로는 `PEAKET_DBT_BIN`·`PEAKET_DBT_PROJECT_DIR`이다 (추천 적용, 2026-11-23)
2. 단계 예정 시각 (추천 적용, 2026-11-23):
   - R0 = 오픈 + 90분, R1 = 오픈 KST 날짜의 다음 영업일 10:00, R2 = 오픈 + 7일, R3 = 공연 시작 KST 날짜의 다음 영업일 10:00이다.
   - 기준 자료에 회차 종료 시각 칸이 없어 공연 시작 날로 R3를 잡는다. 입장 기록 마감 뒤로 미루는 조건(ADR-0051)은 아직 보지 않는다.
   - 영업일은 KST 주말과 공휴일 파일(`PEAKET_HOLIDAY_CALENDAR_FILE`, payment·purchase와 같은 꼴)로 센다.
3. 할 일 고르기 (추천 적용, 2026-11-23):
   - 예정이 지난 가장 높은 단계가 현재 판의 마감 단계(F11 `close_stage`)보다 높으면 그 단계를 마감한다. 공연이 오픈 뒤 7일 안이면 R3가 R2보다 먼저 온다.
   - R2를 마쳤고 R3 전이면 KST 날짜마다 한 번 같은 단계로 다시 만든다(매일 쌓기).
   - 오래된 예정부터 한 회차씩 처리한다.
4. 두 번에 나눈 빌드 (추천 적용, 2026-11-23):
   - `dbt build --exclude path:models/metrics`로 사실·차원을 만든다.
   - R3 정산 대조 결과를 `dbt build --select path:models/metrics --vars quality_failed`로 넘긴다.
   - 모두 통과하면 `swap_current_run`을 부른다.
   - 회차당 상한은 20분이다(넘기면 끝내고 TIMEOUT).
5. 실행 기록 `gold.close_run_log`(회차·판·단계·종류·시작·끝·결과 DONE·FAILED·TIMEOUT·요약·품질 실패 지표)는 실행기가 먼저 만든다. dbt가 돌기 전에 실패해도 남게 하려는 것이다 (추천 적용, 2026-11-23)
6. R3 정산 대조 (추천 적용, 2026-11-23):
   - 정산서는 회차 정산서(`kind` EVENT)의 STATEMENT_NOTIFIED 가운데 결제사마다 판본이 가장 큰 것이다.
   - 판매 대금은 결제사별로 F15(판매 금액 − 되돌림 금액)와 견준다.
   - 환급은 F8에 결제사 칸이 없어(§5.2 그레인) 회차 합으로 견준다.
   - 정산서가 없으면 둘 다 실패로 본다.
   - 실패해도 판은 바꾼다. R3 리포트의 '데이터 품질'에 실패가 보이게 하려는 것이다. 조사 건 만들기(A-T9 뒷부분)는 리포트·관제(F-04-7) 몫이다.
7. 판 잇기 (추천 적용, 2026-11-23):
   - 날짜별 사실 F15·F8은 실행 시각보다 80일 [가정] 앞선 날의 행을 앞 현재 판에서 옮긴다(`carry_run`·`carry_before`). 그 뒤의 날은 실버에서 다시 센다.
   - 온세일 사실 F1~F7은 R3·매일 실행에서 R2 판의 행을 옮긴다(`onsale_run`, R2 동결).
   - F11의 매진 시각·풀림 횟수는 R2 판 값으로 잇는다.
   - R3의 F11 판매 좌석·금액은 F15 합이다(§4.4).
8. 브론즈 기준 자료도 적재 뒤 90일에 지워진다(§5.5). 그래서 판매 기간이 긴 회차를 다음처럼 다룬다 (추천 적용, 2026-11-23):
   - 회차 차원 `dim_event`·`dim_tier`·`dim_section`은 브론즈에 그 회차가 없으면 앞 판에서 옮긴다.
   - 실행기는 브론즈와 골드 현재 판 `dim_event`를 합쳐 회차 시각을 읽는다.
   - `dim_venue`·`dim_partner`는 회차 열이 없어 옮기지 않는다.
9. 기준 자료 파일 싣기 (추천 적용, 2026-11-23):
   - 수집 폴더의 `ref-event/`·`ref-seat-map/` 아래 `.json`·`.jsonl`(JSONEachRow)을 싣는다.
   - 열 밖 칸이 있으면 파일 전체를 거절한다(`input_format_skip_unknown_fields = 0`).
   - 크기 상한은 50MB다.
   - `bronze.brz_intake_log`에 경로·SHA-256·행 수·결과를 남기고, 같은 파일은 다시 싣지 않는다.
   - 운영의 S3 버킷(`s3()` 표 함수, ETag)은 배포(F-09-8) 몫이다.
   - core-svc가 파일을 쓰는 쪽은 아직 없다.

남은 빈칸 0.

빠른 길이라 구현과 시험을 함께 썼다. 유닛·정적 검사는 통과했고, **통합은 아직 통과하지 못했다**. Docker 잠금을 다른 갈래(F-05-4 통합)에 넘기려고 2026-11-23 밤에 멈췄다(측정 창 11-26, 감독 지시).

- `corepack pnpm --filter @peaket/close-runner test`: **9/9 통과**(파일 1).
- `corepack pnpm --filter @peaket/close-runner typecheck`: 통과.
- `corepack pnpm --filter @peaket/close-runner build`: 통과.
- `corepack pnpm exec eslint services/close-runner`: 통과.
- `dbt parse --vars '{…, holidays: ["2026-03-10"]}'`: 통과.
- `corepack pnpm install --frozen-lockfile`: 통과(잠금 파일 최신).
- 통합 `cd data && PYTHONUTF8=1 .venv/Scripts/python.exe -m unittest tests_int.test_close_runner -v`(실제 ClickHouse 24.12): **실패**(다섯 번 모두 같은 지점, 약 4~8분). 일일 쌓기 뒤 `gold.fct_sales_minute`의 현재 판 판매 좌석 합이 0이었다(기대 2).
  - ①~③은 통과했다: 기준 자료 파일 두 개 적재, dim_date 공휴일(3/10)과 영업일(3/9), M R3의 정산서 1원 차이 → 품질 FAIL, R1 dbt 실패 주입 뒤 현재 판 유지·같은 시각 재실행 DONE, R2.
  - 원인: `macros/close.sql`의 판 잇기 복사 SQL이 `select * except (run_id, built_at), '<새 판>' as run_id … from … where run_id = '<앞 판>'` 꼴인데, ClickHouse가 WHERE의 `run_id`를 SELECT의 **새 별칭**으로 읽어 앞 판 행을 하나도 고르지 않았다(쿼리 로그 written_rows 0, R2 판 행 2개는 존재). `src.run_id` 자격 이름을 붙여 고쳤다.
  - 같은 원인이 `with_carry`(F15·F8·dim_event·dim_tier·dim_section 잇기)에도 있어 함께 고쳤다.
  - **고친 뒤 통합은 아직 다시 돌리지 않았다.** 다음 시험은 일일 쌓기의 F2 2석(현재 판), 6/15 앞 판 잇기(F15 3/6·3/16), 7/6 R3 정산 0원 차이까지 봐야 한다. M의 1원 차이 품질 FAIL과 R1 실패 주입은 이미 통과했다.
  - F-04-4·F-04-5 회귀 통합도 아직 다시 돌리지 않았다.
- 장부: `node tools/ci/ledger.mjs --batch F-04-6` → 범위 313항목, 자동 시험 111·ID만 125·다른 단계 1·해당 없음 29·**빈칸 47**. B등급이라 막지 않는다(ADR-0373 결정 3). Python 통합 시험이 덮는 A-T18은 장부가 시험 이름을 읽지 못해 빈칸으로 센다.
