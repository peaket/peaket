# 묶음 계획: BAT-075(BAS-080 운영 진단 기본값)

- **무엇**: 묶음을 시작할 때 만든 작업 목록이다(docs/architecture.md §8.6 4). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다. 값은 되도록 옮겨 적지 않고 자리(문서:줄)를 가리킨다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane4`, 가지 `feature/lane4-BAT-075`, 출발점 `origin/develop` `cf6427f6`. 구현 전 트리는 `D:/ticketpass-lane4-base`(`cf6427f6`, 분리 HEAD, 커밋 안 함). 2026-11-19 계획 담당 `bat075-plan-5e3a`(claude-opus-5-5)가 썼고 시험·제품 코드는 쓰지 않았다. 이 PC에서 시험·Docker를 돌리지 않았다.
- **등급·차례**: B(운영 진단·배포 기본값). 정방향(`Batch-Order: impl-first`). ADR-0283 결정 2의 짧은 고리: 계획 → 구현 → 시험(구현 전 트리에서 실패 확인을 같은 커밋에) → 리뷰 → 리뷰 반영 시험(재현 시험과 실패 확인을 한 커밋) → 리뷰 반영 구현(고침과 시험 결과를 한 커밋) → 검증 → 기록. 리뷰 반영 계획 커밋은 없고(리뷰 절의 지적 목록이 고칠 목록), 다시 리뷰는 하지 않는다(보안 높음 지적만 보안 리뷰 담당이 다시 본다).
- **이 계획의 몫**: 묶음 표의 단계 둘 가운데 **BAS-080만** 쓴다. 넘침의 까닭과 나누는 안은 아래 '감독에게' 1이다. 묶음 표(docs/BUILD_ORDER.md 67행)는 고치지 않았다.
- **정본(이 커밋)**: docs/devops.md §6.4 '일반 서비스'의 종료 문장, §14 D-T18(①② 나눔)·D-T19(①~④ 나눔)·D-T27 행, §15 '운영 진단 경로' 행. docs/architecture.md §5 '프로브 규칙'의 준비 프로브 끝 문단. docs/observability.md §3 'gRPC 서버 지표' 표(새)와 'DB 풀이 꽉 차도 기다리지 않는다' 행의 경보 칸. docs/security/asvs/delivery.md 14.2.1·14.2.2·15.1.3·15.2.2·16.5.2 행의 구현 위치. docs/review/ledger-notes.md `D-T19 ④`(측정)·`D-T18 ②`(다른 단계 BAS-150). 모두 '추천 적용 2026-11-19, BAT-075 계획'. 장부(docs/review/ledger/)를 다시 썼다.

## 감독에게(첫 계획 커밋, 위에서 모두 답함)

1. **묶음 나누기(BAS-080 / BAS-120)**: 4일·남은 항목 101개를 한 묶음으로 끝내기 어렵다. BAS-080만으로도 kind 시험 둘(진단 수집·이벤트 루프 막기), 공용 gRPC 서버로 서비스 여섯 옮기기, 측정 둘이 있어 2.25일 [가정]을 채운다. BAS-120은 성격이 달라(Terraform 모듈·생성·삭제 스크립트·TTL 자동 삭제·계정 구조·S3 잠금 파일·예산 경보·ArgoCD) 같은 시험·리뷰 담당이 이어 보기 어렵다. 그리고 도구 결정이 먼저 필요하다: 저장소에는 Terraform 1.16.2의 `fmt`·`validate`(`.github/workflows/iac-check.yml`)만 있고, tflint·Trivy 설정 검사·checkov는 없다(그 워크플로 주석이 '클라우드 스택이 생기는 변경에서 더한다'고 적었다). AWS 제공자(`hashicorp/aws`)의 잠금 파일을 만들려면 `terraform providers lock`을 어딘가에서 돌려야 한다(CI의 `init`은 레지스트리에서 받는다). **안**: BAT-075는 BAS-080만(2.25일), BAS-120은 새 묶음 하나(갈래 4, 1.75일, 번호는 감독)로 떼고, 그 계획 전에 정적 검사 도구(tflint·Trivy 설정 검사 중 무엇을, 판·받는 곳)를 정한다.
2. **장부 범위 좁히기(BAT-205와 같은 방식)**: 이 묶음의 장부 범위는 `docs/devops.md`·`docs/security/asvs/delivery.md` 전체라, 다른 단계 몫(동결 달력·카나리·마이그레이션·Kyverno·IAM·WAF·MSK 등)이 남은 항목 101개의 대부분이다. BAS-080이 채우는 것만 남기는 안: `D-T18 ①, D-T19, D-T27, D-T29, D-T45, delivery:v5.0.0-14.2.1, delivery:v5.0.0-14.2.2, delivery:v5.0.0-15.1.3, delivery:v5.0.0-15.2.2, delivery:v5.0.0-16.5.2`. 나머지의 정할 곳 후보는 아래 8.2 표다. 같은 문서 전체를 범위로 단 BAT-070(갈래 1)·BAT-080·BAT-085(갈래 4)도 같은 문제를 만난다.
3. **ADR 번호**: 이 계획이 정한 것 가운데 셋은 결정에 가깝다. ① 종료 방식(NestJS `enableShutdownHooks()`·gRPC `gracefulShutdown`을 켠다는 옛 문장을 공용 gRPC 서버·공용 종료 차례·`createService`의 SIGTERM 준비 내림으로 바꿈, ADR-0082 연결) ② 진단 수집의 구현 값(주석 파일 읽기 5초, 준비를 내린 뒤 30초 기다림, 표시 파일, 저장소 설정이 없을 때의 동작, ADR-0070 결정 1 연결) ③ gRPC 서버 지표 이름. 지금은 정본에 '추천 적용 2026-11-19, BAT-075 계획'으로만 적었다. ADR 하나로 남길지 정해 달라(번호를 주면 계획 담당이 ADR을 쓰고 정본 문구에 번호를 붙인다).
4. **프로브 값의 확정 자리**: 정본은 준비 프로브 값(5초·3초·6회)을 '0.3.6에서 온세일 부하의 이벤트 루프 지연 p99로 정한다'고 한다. 온세일 부하 무대가 이 묶음에 없어, kind 비교(D-T19 ③④)를 근거로 남기고 p99로 다시 보는 일은 '온세일 부하를 재는 측정 창'으로 미뤘다(architecture §5에 적음). 그 측정 창이 어느 묶음인지(예: HOT-460) 정해 달라. 정하면 ledger-notes에 한 줄을 더한다.
5. **알림(묻지 않아도 되면 그대로)**: 진단 증거 업로드에 `@aws-sdk/client-s3`를 `packages/platform` 의존성으로 더한다. 판은 서비스들이 이미 쓰는 `@aws-sdk/client-kms`와 같은 3.1159.0이고 npm 공개 레지스트리에서 받는다(devops §4.4의 범위 안). D-T45 ①~⑥은 BAS-080 일이 아니지만 시험이 이미 있고 이름 표기(`D_T45_`)만 틀려 장부가 빈칸으로 본다. 이름만 고치므로 이 묶음에 넣었다(빼라고 하면 뺀다).

**구현 보고 판정(2026-11-19, 구현 커밋 `1c4ec5de`·`6a357ce0`의 '계획과 다르게 한 것' 여덟, 정본 대조)**: 모두 받아들인다. 정본 자리는 ADR-0303이다.

1. 진단 수집은 `PEAKET_DIAG_ANNOTATIONS_FILE`이 있을 때만 켜진다(차트가 넣는다). B14의 '그 밖의 환경은 시작하지 않는다'도 그때만이다. local·ci는 버킷(`PEAKET_DIAG_BUCKET`)과 moto 주소(`PEAKET_DIAG_S3_ENDPOINT`)가 둘 다 있어야 켠다. 까닭: 차트 밖에서 띄운 프로세스(시험·합본 자식)에는 주석 파일이 없다. ADR-0303 결정 3. DG-06 단언을 이대로 고쳤다.
2. `PEAKET_GRPC_PORT=0`(빈 포트)은 local·ci에서 받는다. GS-05의 '0이면 시작 실패'는 그 밖의 환경에서만이다. 까닭: payment-svc·ticket-svc 설정과 같은 규칙이고 시험이 띄운 포트를 읽는다. ADR-0303 결정 1.
3. payment-svc(50051)·ticket-svc(50052)는 자기 설정 포트를 그대로 쓴다. 공용 기본값 50051은 설정이 없는 서비스의 것이다. ADR-0303 결정 1.
4. 진단 기다리기(30초·10초)는 `setTimeout`이고 시험은 `sleep`을 주입한다. 가짜 시계 대신 주입이라도 경계 단언(29,999/30,000ms)은 주입한 `sleep`이 받은 값으로 본다(DG-01).
5. 등록 밖 메서드 지표는 grpc-js 1.14 내부 `_retrieveHandler`를 감싸서 센다. 내부 함수가 없어지면 GS-06(등록 밖 `method="unknown"` 1)이 실패해 판 올림 때 알아챈다(`@grpc/grpc-js`는 1.14.6으로 고정). ADR-0303 결정 2.

### TO-3 진짜 SIGTERM은 리눅스에서만(시험 담당, 2026-11-19): 이의 아님, 알림

- GS-03·GS-04(`packages/platform/test-int/shutdown.int.test.ts`)는 리눅스(CI)에서 자식 프로세스에 진짜 SIGTERM을 보낸다. Windows는 다른 프로세스에 처리기를 부르는 SIGTERM을 보낼 수 없어(`kill`이 처리기 없이 끝낸다) 자식에게 `term` 줄을 보내 `process.emit('SIGTERM')`으로 같은 처리기를 부른다. 이 PC의 결과는 이 길이다. 진짜 신호로 본 결과는 CI `node` 잡의 platform 통합 시험이 낸다. 자식(`shutdown-child.mjs`)은 빌드한 `dist`를 쓴다(`st18-child.mjs`와 같다).

- RV-02(중간): 어느 서비스도 `onStopWork`를 넘기지 않는다(SEC-07 ②와 같은 결함). 그래서 수집 중에도 Kafka 소비·승인/정산 실행기가 새 일을 잡고, 마감 10초는 0초가 된다. 동기 스냅샷이 루프를 막으면 Kafka 재조정이나 임대 만료가 날 수 있다. Kafka·실행기가 있는 서비스(purchase·queue·payment)에 잇거나, 잇지 않는 까닭을 ADR-0303 '남는 것'에 적는다.
- RV-04(중간): `/diag`의 디스크 여유를 보지 않는다. 올리기 실패가 쌓이면 emptyDir 한도(메모리 한도의 2배)를 넘겨 파드가 축출되고 증거도 사라진다. statfs로 여유를 보고 모자라면 `heap_skipped_low_disk`로 건너뛴다.
- RV-05(중간): 부르는 쪽 마감(DEADLINE_EXCEEDED)으로 끝난 호출이 `code="CANCELLED"`로 세진다. grpc-js `server-interceptors.js:444-449`의 마감 타이머가 가로채기를 거치지 않기 때문이다. `onCancel`에서 `call.getDeadline()`이 지났으면 DEADLINE_EXCEEDED로 센다.
- RV-06(낮음): `createHotRedis` 12곳 모두 `cluster`를 넘기지 않아 `redis_command_timeout_total`이 모두 `cluster="default"`다.
- RV-07(낮음): GS-01(500ms)·GS-02(100ms)·GS-03/04(300ms)가 호출이 처리기에 닿았는지 보지 않고 고정 시간 뒤 닫는다. 처리기 진입 신호를 기다리게 한다(RV-11과 같은 꼴).
- RV-09(낮음): grpcLbProfile 정적 시험의 정규식이 purchase-svc의 `startPurchaseGrpcServer`를 보지 못한다. `/await start\w*GrpcServer\(\{/`로 넓히고 서비스 수를 6으로 한다.
- RV-10(낮음): RD-01 시험 이름('20번모두…50ms안')이 단언(가운데 50ms·가장 느린 1,000ms)과 다르다.
- RV-12(낮음): 합본(v1-bundle) 측정 무대에 V8 힙 상한 75%가 새로 걸린다. 또 버킷을 켜면 서비스마다 수집기가 표시 파일·보고서 이름을 다투고 각자 SIGTERM을 보낸다. 합본 시작은 `diagnose: false`로 둔다.
- RV-13(낮음): ticket-svc는 50052에 여는데 `service.config.grpcPort`는 50051이라고 한다.
- SEC-08(낮음, BAT-076으로): `PutObject`가 서버 쪽 암호화 머리를 붙이지 않는다. 버킷 정책이 머리 없는 PUT을 거부하면 운영 올리기가 모두 실패한다. BAT-076 계획에서 정책과 머리 가운데 하나를 정한다.
- SEC-09(낮음): `/diag` emptyDir에 맞춘 `ephemeral-storage` 요청이 없다. 두거나, 두지 않는 까닭을 devops §15에 적는다.
- SEC-10(낮음): kind e2e 셋은 각 15분까지 허용되는데 잡 상한은 20분만 늘었다. 또 아직 한 번도 돌지 않았다. 첫 CI의 실제 시간으로 상한을 다시 정한다.

### 감독에게

- **RV-08(G7 측정 R-223)**: M-01(새 연결 맺기 p99)·M-02(`set_config(…, true)` 왕복 비용)의 측정 스크립트와 `docs/review/measurements` 폴더의 `BAT-075-pool.md`가 없다. 장부 항목이 없어 `ledger --require`는 통과한다. 하지만 §7의 'M-01·M-02 판단'과 architecture §5 표에 한 구절 적기가 남는다. 이 묶음 검증 전에 잴지, 측정 창(예: BAT-095)으로 옮길지 정해 달라.
