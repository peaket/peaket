# 작업 계획: W7-L1-roles-testonly(역할 확인이 '시험만 묶음'을 받게 하기)

- **무엇**: `tools/ci/roles-check.mjs`(시험 `tools/ci/roles-check.test.mjs`)가 제품 코드를 바꾸지 않고 시험만 고치는 묶음을 받게 하는 일의 작업 목록이다(docs/architecture.md §8.6 4의 1, ADR-0270 결정 5). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane1-v`, 가지 `wave/lane1-w7-rc2`, 출발점 `origin/develop` `92448f1d`(roles-check가 들어 있다). 2026-11-16 작성.
- **까닭(감독 결정, 2026-11-16)**: develop CI를 깬 날짜 박힌 시험을 고치는 일처럼 제품 코드는 그대로이고 시험만 고치는 일이 있다. 지금 역할 확인은 코드 묶음에 구현 커밋이 꼭 있어야 해서, 이런 일을 하려면 할 일 없는 구현 담당을 띄우거나 빈 구현 커밋을 만들어야 한다. 그래서 이런 묶음은 계획·시험·리뷰·검증으로 꾸리고 구현이 없게 한다. 조건: 그 묶음의 어느 커밋도 시험 파일 밖의 코드 파일을 바꾸지 않을 때만 구현 없음을 받고, 그때도 리뷰·검증은 있어야 한다.
- **묶음 ID**: 묶음 표에 없는 일이라 이 파일 이름 `W7-L1-roles-testonly`를 쓴다. 이 일 자신은 코드 묶음이다(역할 다섯, `roles-check.mjs`를 바꾼다).
- **등급**: B(배포·운영 도구). 틀린 구현 표본은 아래 '틀린 구현 목록'이다.
- **정본**: ADR-0270 결정 1·5·8, docs/architecture.md §8.6 4 '합치기 전 역할 확인'의 세부(이 계획이 '시험만 묶음' 줄을 더했다), 지난 계획 [W7-L1-roles-check](W7-L1-roles-check.md)의 검사 ①~⑩과 출력 꼴.

## 계획

### 1. 규칙(정본 빈칸과 정한 것)

1. **알아보는 법: 꼬리말로 밝힌다 (추천 적용, 2026-11-16)**: 시험만 묶음은 그 묶음의 `plan` 커밋 가운데 하나 이상이 꼬리말 `Batch-Kind: test-only`를 단다. 커밋 내용으로 짐작하지 않는다.
   - 짐작하지 않는 까닭: 구현 담당이 아직 커밋하지 않았거나 빠뜨린 코드 묶음도 '시험 파일만 바뀌고 구현 없음'으로 보인다. 짐작하면 그 묶음이 조용히 시험만 묶음으로 통과한다. 계획 담당이 처음에 밝혀 두면 시험·리뷰·검증 담당도 계획 파일과 커밋에서 그것을 본다.
   - 밝히지 않은 묶음에 구현 커밋이 없으면 지금처럼 `[구성]` 실패다(코드 묶음의 구현 없음).
   - 꼬리말 규칙(①, `[꼬리말]`): 키는 대소문자까지 그대로 `Batch-Kind`, 값은 정확히 `test-only`(앞뒤 공백은 지움). 한 커밋에 하나만, `plan` 커밋에만 단다. 다른 역할 커밋에 달거나, 값이 다르거나, 둘이면 실패다.
   - 계획 파일 머리에도 사람이 읽게 '시험만 묶음'이라고 적는다(검사하지 않는다).
2. **종류 가르기(④) (추천 적용, 2026-11-16)**: 묶음 종류는 이 차례로 정한다.
   1. `Batch-Kind: test-only`를 단 plan 커밋이 있으면 **시험만**.
   2. 아니고 `doc` 커밋이 있으면 **문서**.
   3. 아니고 record만 있으면 **기록만**.
   4. 그 밖은 **코드**.
   - 묶음 줄의 종류 이름은 `시험만`이다(예 `묶음 BAT-950: 시험만 커밋 5개(plan 1·test 1·impl 0·…)`).
3. **구성(④, `[구성]`)**: 시험만 묶음에는 plan·test·review·verify 커밋이 하나 이상씩 있다. 다음이 하나라도 있으면 실패다.
   - `impl` 커밋, `review-fix`+`Fix-By: impl` 커밋: 구현이 있으면 시험만 묶음이 아니다(밝힌 것을 지우고 코드 묶음으로 한다).
   - `doc` 커밋: 문서 작성 담당은 시험만 묶음에 없다.
   - `review-fix`+`Fix-By: test`는 된다(리뷰·검증 지적을 시험 담당이 고친다).
4. **차례(③, `[차례]`)**: 역할마다 처음 나온 커밋끼리 견준다(지금 꼴과 같다). 시험만 묶음은 첫 plan < 첫 test < 첫 review < 첫 verify이고, 리뷰 반영은 첫 review나 첫 verify 뒤다. 첫 test 전의 plan·test 섞기, test 뒤의 plan(허용 경로 안)과 test 커밋은 코드 묶음처럼 막지 않는다.
5. **바꾸는 파일(⑥의 보탬, `[코드 경로]`) (추천 적용, 2026-11-16)**: 시험만 묶음에서 `test` 커밋과 `review-fix`+`Fix-By: test` 커밋은 **시험 파일**(⑤의 정의: `*.test.*`·`*.spec.*`·`test_*.py`, 폴더 마디 `test`·`test-int`·`test-sim`·`__tests__`·`e2e`)과 **문서 경로**(⑥의 허용 목록: `docs/` 아래와 코드 경로 밖의 `.md`)만 바꾼다. 다른 역할은 지금처럼 문서 경로만 바꾼다. 그래서 묶음 전체가 시험 파일과 문서 밖을 바꾸지 않는다.
   - 감독의 조건('시험 파일 밖의 코드 경로 일곱을 바꾸지 않는다')보다 조금 더 막는다. 뿌리 설정(`package.json`·잠금 파일·`turbo.json`), `deploy/`·`loadtest/`·`specs/`의 시험 아닌 파일도 막는다. 시험만 고친다던 일이 설정을 바꿔 시험을 빼거나 실행 방식을 바꾸는 길(지난 리뷰 RV-04와 같은 꼴)을 닫기 위해서다. 설정까지 바꿔야 하면 구현이 있는 코드 묶음으로 한다.
   - 코드 경로 안의 시험 설정(`services/*/vitest*.config.mjs` 등)은 시험 파일이 아니므로 막힌다.
   - 실패 줄은 `[코드 경로] <묶음> <그 커밋 해시> 시험만 묶음의 시험 쪽 커밋이 시험 파일·문서 밖 경로 <경로>를 바꿨다`이다. 경로마다 한 줄이다.
   - 코드 묶음의 `test` 커밋은 지금처럼 보지 않는다(빈 뼈대가 제품 파일에 들어간다).
6. **계획 파일(⑧)·담당 표(⑨)**: 시험만 묶음은 코드 묶음과 같이 '실패 확인'·'리뷰'·'검증'·'담당 표' 절이 차 있어야 한다. '실패 확인'에는 고치기 전 시험이 어떻게 실패했는지(예: develop CI 실행 번호와 실패한 시험 이름)와 고친 뒤 통과를 적는다. 담당 표에는 plan·test·review·verify 줄이 있다(커밋의 역할·세션 쌍마다).
7. **세션(⑦)·시험 파일(⑤)**: 바뀌지 않는다. 시험만 묶음에는 구현 쪽 커밋이 없으므로 ⑤는 걸릴 커밋이 없다.
8. **CI·package.json**: 지금처럼 잇지 않는다.
9. **ADR**: ADR-0270 본문은 고치지 않는다. 정본 문장은 §8.6 '합치기 전 역할 확인' 세부의 '시험만 묶음' 줄이다. ADR-0270 결정 8의 '코드를 바꾸는 모든 묶음은 역할 다섯' 문장에 대한 예외이므로, 감독이 기록 커밋에서 ADR-0270 상태 줄 보탬에 한 문장을 더할지 정한다.

### 2. 공개 인터페이스

명령줄·끝 코드·출력 꼴은 바뀌지 않는다(지난 계획 1). 더하는 것은 다음뿐이다.

- 꼬리말 `Batch-Kind: test-only`(위 1의 1).
- 묶음 줄의 종류 `시험만`.
- `[구성]`·`[코드 경로]`의 새 까닭 문장(위 1의 3·5).
- 내놓는 함수는 없다. 시험은 지금처럼 명령을 자식 프로세스로 돌린다.

### 5. 차례

1. 계획(이 커밋): 이 파일과 §8.6 세부의 '시험만 묶음' 줄.
2. 시험: RC-52~RC-59. '실패 확인' 절에 명령(`node --test tools/ci/roles-check.test.mjs`)·실패 수·까닭·처음부터 통과한 시험.
3. 구현: `roles-check.mjs`와 README 한 구절. 시험 파일은 고치지 않는다(어긋나 보이면 '시험 이의').
4. 리뷰 → 리뷰 반영(`Fix-By`·`Finding`) → 검증 → 기록(감독).
- 감독은 이 일의 합치기 전에 새 스크립트로 이 일 자신을 본다(`node tools/ci/roles-check.mjs --base origin/develop --head wave/lane1-w7-rc2`).

### 6. 기계로 보지 않는 것

- 시험만 묶음이라고 밝힌 까닭이 맞는지(정말 제품 코드를 고칠 일이 아닌지)는 리뷰 담당이 본다.
- 고친 시험이 정본의 판정 기준과 맞는지(날짜를 고치며 단언을 느슨하게 하지 않았는지)는 리뷰·검증 담당이 본다. 시험만 묶음의 '검증' 절에는 고친 시험마다 틀린 구현으로 실패를 본 결과를 적는다.

### 7. 검증 차례 바꾸기(감독 결정, 2026-11-16)

감독 결정: 차례 규칙의 '검증은 리뷰 뒤'를 '검증은 마지막 코드 고침 뒤'로 바꾼다. 리뷰와 검증은 서로의 결과를 보지 않고 같은 때 따로 돌 수 있다. 지킬 것은 검증이 고친 코드 위에서 돌았는가다(갈래 3 W8-ci-fix 사례). 정본 문장은 §8.6 '합치기 전 역할 확인' 세부의 '차례'와 '시험만 묶음' 줄이다. 아래가 위 1의 4와 지난 계획 3의 ③을 바꾼다.

1. **마지막 검증이 마지막 코드 고침보다 뒤 (추천 적용, 2026-11-16)**: 묶음의 마지막 verify 커밋이 마지막 코드 고침 커밋보다 뒤여야 한다.
   - '첫 verify'로 보지 않는 까닭: 첫 verify로 견주면 검증 → 고침 → 다시 검증(BAT-055처럼 여러 바퀴)이 첫 검증 뒤의 고침 때문에 실패한다. 마지막 verify로 견주면 여러 바퀴는 되고, 고침 뒤에 다시 검증하지 않은 경우만 막힌다.
   - 실패 줄: `[차례] <묶음> <마지막 코드 고침 커밋 해시> 마지막 코드 고침 커밋 뒤에 verify 커밋이 없다`.
2. **코드 고침으로 세는 커밋 (추천 적용, 2026-11-16)**: 코드 묶음에서는 `impl` 커밋과 `review-fix`+`Fix-By: impl` 커밋이다. 바꾼 파일이 모두 `.md`인 것은 세지 않는다(행동이 바뀌지 않아 검증 결과가 그대로다. 지난 계획 8의 3의 문서 예외와 같은 선).
   - 시험 쪽 커밋(`test`, `Fix-By: test`)은 코드 묶음에서 세지 않는다. 검증 뒤에 더한 시험(살아남은 틀린 구현을 잡는 시험)은 검증이 본 코드를 바꾸지 않는다.
3. **첫 verify는 첫 impl 뒤 (추천 적용, 2026-11-16)**: 지금 꼴(첫 plan < 첫 test < 첫 impl < 첫 verify)에서 verify를 review 뒤에 두던 것만 뺀다. 코드가 없는데 검증한 커밋은 그대로 막는다. 첫 review도 지금처럼 첫 impl 뒤다.
4. **review와 verify가 섞인 차례 (추천 적용, 2026-11-16)**: 둘 사이의 차례는 보지 않는다(review → verify, verify → review, review → verify → review 모두 된다). 리뷰 반영은 지금처럼 첫 review나 첫 verify 가운데 이른 것보다 뒤다.
5. **시험만 묶음 (추천 적용, 2026-11-16)**: 코드 고침이 없으므로 고친 시험이 검증받을 대상이다. 마지막 verify가 시험 파일을 바꾼 마지막 시험 쪽 커밋(`test`, `Fix-By: test`)보다 뒤여야 한다. 문서 경로만 바꾼 시험 쪽 커밋은 세지 않는다. 첫 review·첫 verify는 첫 test 뒤이고, 둘 사이의 차례는 보지 않는다.
6. **문서 묶음**: verify가 없으므로 이 규칙이 걸리지 않는다(계획 < 작성 < 리뷰 그대로).
7. **바뀌는 기존 시험(시험 담당 몫, `Fix-By: test`)**:
   - 좋은 코드 묶음 BAT-901은 지금 review → verify → `Fix-By: test` → `Fix-By: impl`(`services/a/src/x.ts`) 차례라 새 규칙에서는 실패한다. 마지막 `Fix-By: impl` 뒤에 verify를 옮기거나 하나 더 둔다. 이 사건을 쓰는 다른 시험도 같이 맞춘다.
   - RC-16의 'verify가 첫 review 앞'과 RC-57의 'verify가 첫 review 앞'은 이제 통과다. 실패 사례에서 빼고 아래 RC-60의 통과 사례로 옮긴다.
