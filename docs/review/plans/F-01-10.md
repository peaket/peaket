# 기능 계획: F-01-10(OPS-100 — 나머지 경보 규칙과 예산 50% SEV2)

- **무엇**: 기능 F-01-10(docs/BUILD_ORDER.md '기능 단위 계획' 표)의 작업 목록이다(docs/architecture.md §8.6 4의 1·2, ADR-0354). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다. 정본 값은 옮겨 적지 않고 자리(docs/observability.md §3·§5, 이 커밋)만 가리킨다.
- **바탕**: 작업 폴더 `D:/ticketpass-freeze-F-01-10`, 가지 `freeze/lane1-F-01-10`, 출발점 `4777bce89`(최신 develop). 지시서 `node tools/ci/brief.mjs --batch F-01-10`(같은 커밋).
- **동결 로컬 범위**: 이 기능은 v1 배포 범위 밖이다(ADR-0373 결정 2, ADR-0386, docs/release/v1-scope.md §2의 F-01-10 `frozen-local`). `develop`·`release/1.0.0`에 합치지 않고 release에 체리픽하지 않는다. 규칙 파일은 freeze 가지에만 두고, 실제 배포(INF-020·INF-040)에 넣지 않는다. 마이그레이션·릴리스 플래그는 없다.
- **등급과 차례**: B(docs/BUILD_ORDER.md). ADR-0373 결정 3의 B 차례대로 **계획 → 시험 → 구현 → 시험 통과면 끝**이다. 시험 리뷰와 구현 뒤 리뷰는 하지 않는다. 이 freeze 트랙은 지시에 따라 계획·시험·구현을 한 세션이 맡되, 커밋은 `Role: plan|test|impl`로 나눈다.
- **선행**: F-01-5(끝남, `bd537ea58`). 규칙 시험 실행기 `tools/ci/prom-rules.mjs`, 합성 시계열 시험 꼴(`deploy/platform/observability/test/*.test.yaml`), 1층 실패 비율(`peaket:slo_error_ratio:*`), 28일 예산 규칙 위에 쌓는다. F-01-1·F-01-3·F-01-4·F-04-1이 넘긴 지표 이름과 규칙 몫을 받는다.
- **정본**: docs/observability.md §3(외부 의존·플랫폼 공통·현장·대기 순서 신호), §4('엣지에서 끝난 실패', '긁기·평가·알림 간격'), §5(심각도 표, 외부 의존·위생·현장·대기 순서·보안 사고 법정 기한·브로커·결제 결과 당기기·보류 사건·설정형 명령·진단 증거·관제 실시간 표·수집기 자체 신호), §7(구조화 로그), §8(허용 라벨·히스토그램 칸), docs/verification.md §2.7, ADR-0049·0069·0070·0073·0076·0116·0140·0141·0142·0143·0180·0373·0386.
- **ADR**: 이 기능은 정본의 결정을 바꾸지 않는다. 정본에 이름이 없던 지표 이름·세부 임계는 이 계획과 docs/observability.md §5에 '(추천 적용, 2026-11-24, F-01-10 계획)'으로 적었다(ADR-0373 결정 3). ADR 새 번호는 쓰지 않는다.

## 감독에게

1. **[알림] 엣지 502·504 몫은 이번에 넣지 못했다.** 정본 §4 '엣지에서 끝난 실패' ③④는 배포별 CloudFront 502·504 비율과 게이트웨이 응답 수를 5분마다 빼고 여정 몫으로 나눠 28일 예산에 더하라고 정한다. 그런데 (가) 저장소의 YACE 설정은 CloudFront 원천 작업만 있고 실제 배포·`delay` 값은 INF-020 몫이며, (나) 게이트웨이 쪽 502·504 지표는 아직 없다(ADR-0382가 '게이트웨이 지표가 생길 때까지 임시 원천'이라 적었다). (다) 배포별로 나누려면 `by (distribution)`이 필요한데 `distribution`은 §8 허용 라벨 목록에 없어 `alert-check`가 막는다. 지표가 생기고 §8 목록을 넓히는 결정이 선 뒤에 별도 몫으로 한다. 이번 기능은 28일 예산의 기존 입력(`agg5m:slo_*:increase5m`)을 건드리지 않는다.
2. **[알림] 설정형 명령 '적용 확인 안 됨'은 규칙이 아니라 ops-svc 동작이다.** 정본 §5는 명령 뒤 30초 안에 받는 서비스의 준비된 파드 판을 클러스터 Prometheus로 확인해 콘솔 카드에 표시하고 SEV3을 낸다고 정한다. 이 판정 코드는 F-02-5(동결)의 몫이고, `control_settings_applied_version`을 읽는 쿼리·카드 표시도 그 기능이 만든다. Prometheus 경보 규칙으로 옮기면 '확인할 수 없음'과 '적용 확인 안 됨'을 가를 수 없어 여기서 만들지 않았다. F-02-5가 다시 열릴 때 함께 한다.
3. **[알림] 조사 수집 신호 경보 셋(ADR-0171)은 동결을 따른다.** F-01-5 계획 '감독에게' 1의 추천과 ADR-0373 결정 2(포렌식 동결, 넘겨받은 몫도 동결)에 따라 `inv_copy_dropped_total`·`inv_ref_missing_total`·KMS 한도 경보는 만들지 않는다. 포렌식이 다시 열릴 때 F-04-10·F-04-11이 맡는다.
4. **[알림] 지표 원천이 아직 없는 규칙이 있다.** 규칙은 정본이 정한 지표 이름을 그대로 읽고 합성 시계열로 시험한다. 실제로 내는 코드가 없는 것은 다음과 같고, 각 기능·배포 몫이 붙이면 규칙이 바로 동작한다: `dependency_requests_total`(서비스 템플릿 외부 호출 계측, 맡을 기능 미정), `cdn_quota_utilization_ratio`·`aws_kafka_*`(YACE·MSK, INF-020), `scanner_last_sync_timestamp_seconds`·`scanner_duplicate_entry_total`(스캐너 업로드·ticket-svc, F-05-4·F-05-6 몫), `security_incident_duty_*`(ops-svc 법정 기한 기능, 맡을 기능 미정), `backup_*`·`certificate_*`(exporter·플랫폼 공통, INF-020), `evidence_*`(F-01-1 구현됨), `rt_*`(F-04-1 구현됨), `otelcol_*`(F-01-3 설정, 수집기 배포는 INF-020). 정본에 이름이 없던 지표는 `backup_cross_region_last_success_timestamp_seconds`·`backup_last_success_timestamp_seconds{store}`·`certificate_renewal_overdue`·`certificate_renewal_due_timestamp_seconds`·`certificate_expiry_timestamp_seconds`·`scanner_last_sync_timestamp_seconds`·`scanner_duplicate_entry_total`이고, 이름·라벨 모양을 docs/observability.md §5에 적었다. 감독이 다른 이름을 고르면 정본과 규칙을 함께 고친다.
5. **[알림] Docker를 쓴다.** `prom-rules check`·`test`는 promtool이 없으면 `deploy/local/observability.yaml`의 prom/prometheus 이미지를 Docker로 띄운다. `docker-2` 잠금을 잡고 돌린 뒤 바로 놓는다. 11-26 08:30~11-27 저녁(갈래 4 측정 창)과 11-28~30(F-04-8 창)에는 잡지 않는다.

## 계획

### 1. 범위

- **P1 경보 규칙**(`deploy/platform/observability/alerts/ops-100.yaml`, PrometheusRule 하나, 묶음 여덟, 모두 평가 30초): 아래 3절 표의 규칙 34개. 기존 파일(`alerts/realtime-gw.yaml`, `rules/slo-*.yaml`, `rules/agg5m.yaml`, `rules/watchdog.yaml`)은 고치지 않는다. 규칙 이름·라벨이 겹치지 않게 새 파일에만 둔다.
- **P2 합성 시계열 시험**(`deploy/platform/observability/test/ops-100.test.yaml`): V-T52 ①~⑪ 묶음 11개. 입력 간격 15초(§4 '그 밖의 긁기 작업'), 평가 30초(규칙 묶음 평가). 경계는 정본 임계의 바로 아래·위를 넣는다.
- **P3 정적 시험**(`tools/ci/alert-rules.test.mjs`에 절 추가): 규칙 파일의 묶음·이름·`severity`·`kind`·`for`·임계값·주석·중복 없음·비밀값 없음을 읽는다. `alert-check`가 보는 것과 겹치되, 시험 ID V-T52의 정적 몫을 남긴다.
- **P4 정본·장부**: docs/verification.md에 V-T52 행(①~⑪), docs/BUILD_ORDER.md F-01-10 '장부 범위'를 `V-T52 ①`~`V-T52 ⑪`로 좁힌다. docs/observability.md §5 끝에 규칙 파일 자리와 이름이 없던 지표 이름을 적는다.
- **어림**: 규칙 34개(약 1.5일 [가정]) + 시험 11묶음(약 1일) + 문서·게이트(0.25일) = 2.75일 [가정]. 4일 안이다.
- **하지 않는 것**: 엣지 502·504 몫(감독에게 1), 설정형 명령 적용 확인(2), 조사 수집 신호 셋(3), 실제 Prometheus·Mimir·YACE·Alertmanager 배포(INF-020·INF-040), 대시보드 패널 추가(F-01-4 뒤 몫), 런북 본문 작성(F-08-11 동결).

- **주석**: 모든 경보에 `summary`·`runbook_url`·`dashboard_url`. `kind` slo 경보가 없으므로 `explore_url`은 필수가 아니다. 런북은 RB-07(결제사)·RB-11(Kafka·보류·당기기)·RB-34(스트림·관제 실시간 표)·RB-36(불변식·차례 전 입장)·RB-38(법정 접속기록은 아니고 접속기록 계열 아님, 위생·인증서는 RB-37·RB-23을 가리키지 않고 운영 점검 절로)을 가리키고, 해당 런북이 없는 위생 신호는 `docs/infra.md` §10 표를 가리킨다. `dashboard_url`은 기존 대시보드 uid(`/d/peaket-observability-pipeline`, `/d/peaket-svc-admission-ctrl`, `/d/peaket-svc-payment-svc`)를 쓴다.
