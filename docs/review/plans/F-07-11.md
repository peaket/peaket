## 3. 이번에 하는 것

차례: I-01(ops 통보 모듈) → I-02(core 내부 적용·결과) → I-03(core 철회·지문 정리) → I-04(신고 보관 정리) → I-05(신고 누리집 링크) → I-06(콘솔 통보 탭) → I-07(계약·문서·기록). 구현 담당은 시험 고정 뒤에 시작한다.

1. **I-01 ops 통보 모듈**(G-01, AC-02·AC-03·AC-10):
   - 새 `ops/compliance/`: `domain/compliance-notice.ts`(상태 `OPEN|TAKEN_DOWN|WITHDRAWN`, 기한 `H24|H10`, `dueAtOf(receivedAtMs, deadline)`, `normalizeNoticeText`, `validateNoticeCreate`, `validateNoticeReason`, `viewFor(role)`), `domain/ports.ts`(`ComplianceNoticeStore`, `ComplianceNotice`, `ComplianceNoticeAction`, `ComplianceCore`), `application/compliance-notices.ts`(등록·목록·상세·차단·철회), `inbound/compliance-notice.controller.ts`(`/v1/ops/compliance/notices*`), `adapters/{memory,drizzle}-compliance-notice-store.ts`, `adapters/db/schema.ts`, `adapters/http-core-compliance.ts`, `compliance.module.ts`, `index.ts`.
   - `POST`는 `@Idempotent({operation:'CREATE_OPS_COMPLIANCE_NOTICE'})`을 쓰지 않고 ops 자체 `takedown_notice.requested_by+idempotency_key`로 같은 키·같은 본문을 같은 201로 되돌린다(플랫폼 멱등 표는 memory 조립이 없어 이 모듈은 자기 표로 닫는다). `Idempotency-Key`는 UUID v4만 받는다.
   - `takedown`·`withdrawal`은 `takedown_notice_action`에 `(notice_id, action, idempotency_key)` 유일·`request_hash`·`reason`·`actor_ref`·`created_at`을 남긴다. `reason`은 `normalizeNoticeText`(NFC·제어·양방향 제어 문자 제거)를 거친 값이고, 200 응답도 `{noticeId, status, takenDownAt|withdrawnAt, reason}`으로 정규화한 사유를 돌려준다. 같은 키·같은 본문은 저장된 결과를 200으로 되돌리고, 같은 키·다른 본문은 422, 다른 키로 이미 끝난 상태를 다시 바꾸면 409다.
   - 역할: 쓰기는 `operator|commander`, 읽기는 `operator|commander|cs_agent|cs_lead`(view SUMMARY). viewer 403. 목록은 `next_due_at`(due_at) 차례 DUE_ASC, `created_at` 차례 LATEST, `limit` 1~100.
   - `AppModule`에 `compliance?: { store?: ComplianceNoticeStore; core?: ComplianceCore; audit?: ComplianceAudit }`를 더하고, `main.ts`가 `PEAKET_CORE_HTTP_URL`·`PEAKET_INTERNAL_TOKEN`으로 `HttpCoreCompliance`를 만든다. 주소가 없으면 차단·철회가 503 `compliance-core-unavailable`이다.
   - 감사: `ComplianceAudit.record({action, noticeId, actorId, role, atMs})`를 등록·상세 열람·차단·철회 뒤에 부른다. 동작 이름은 `NOTICE_CREATED`·`NOTICE_VIEWED`·`NOTICE_TAKEN_DOWN`·`NOTICE_WITHDRAWN`이고, `main.ts`는 기존 `AuditChain`에 `COMPLIANCE_NOTICE_*` 기록으로 남긴다(control-tower §9 '모든 열람과 파일 다운로드 행위는 불변 접속기록'). 감사 쓰기가 실패하면 쓰기(등록·차단·철회)는 503으로 닫고 상태를 바꾸지 않는다.
2. **I-02 core 내부 통보 적용·결과 조회**(G-02·G-09, AC-04·AC-06):
   - 새 `review/inbound/internal-notice.controller.ts`: `POST /internal/v1/reviews/notice-takedowns`, `POST /internal/v1/reviews/notice-takedowns/{noticeId}/withdrawal`, `GET /internal/v1/reviews/notice-takedowns/{noticeId}`. `InternalToken401Guard`(없거나 틀리면 401)를 쓴다.
   - `POST` 본문 `{noticeId, reviewIds, receivedAt, deadline, reason}`. `reviewIds` 1~100·중복 없음, `noticeId` UUID, `reason` NFC·제어 문자 제거 뒤 1~2,000자. 응답 `{noticeId, applied, skipped, deadlineAt}`. `deadlineAt = receivedAt + 24h|10h`(NOTICE_DEADLINE_MS). 없는·지운·이미 이 통보로 가린 후기는 `skipped`로 세고, 나머지는 한 트랜잭션으로 `HIDDEN`+`notice` 지움+`takedown_action`+지문 등록. 같은 통보·후기는 다시 넣지 않는다.
   - `GET`은 `{noticeId, reviews:[{reviewId, reason, fingerprint, hiddenAt, restoredAt}], counts:{notice, sameContent, restored, activeSameContent}}`를 준다. `sameContent`는 그 통보의 지문과 같은 `SAME_CONTENT` 조치다. 이 응답이 C-T22의 '조치 결과서' 자리다(공개 계약 아님).
3. **I-03 core 철회·지문 정리**(G-03·G-04·G-06, AC-05·AC-07·AC-08):
   - `Reviews.withdrawNotice(noticeId, reason)`가 그 통보의 살아 있는 `NOTICE` 조치에서 지문을 모으고, 같은 지문의 살아 있는 `SAME_CONTENT` 조치와 후기를 함께 복구한다. 다른 통보(`NOTICE`)·다른 사유(`FILMING_HOLD`·`RIGHTS_TEMP`·`POLICY`)가 살아 있는 후기는 `HIDDEN`을 유지한다. 지문은 그 지문에 살아 있는 `NOTICE`가 하나도 없을 때만 지운다. 저장소 메서드는 `withdrawNotice(noticeId, nowMs)` 하나로 트랜잭션을 닫고 `{restored, sameContentRestored, fingerprintsCleared}`를 돌려준다.
   - `Reviews.moderate`의 `RELEASE`는 `NOTICE`·`SAME_CONTENT`만 남은 가림이면 409 `review-not-moderation-target`으로 닫는다. `FILMING_HOLD`·`RIGHTS_TEMP`/`POLICY` 가림의 RELEASE는 기존대로 200이고, 그때 지문은 `hasActiveNoticeFingerprint`가 거짓일 때만 지운다.
   - 같은 내용 자동 숨김 후기를 작성자가 다른 본문으로 고쳐 `VISIBLE`이 될 때, 그 지문에 살아 있는 `NOTICE`·다른 `SAME_CONTENT`가 없으면 지문을 지운다(지문 정리).
4. **I-04 신고 보관 정리**(G-05, AC-09):
   - `resolveReports`가 `status='RESOLVED'`, `outcome`, `resolved_at`, `purge_at = 처리 시각 + 365일`을 한 문장으로 쓴다. `insertReport`는 처리 전 행의 `purge_at`을 `created_at + 365일`로 두되, 처리 때 다시 잡는다.
   - `ReviewStore.purgeExpiredReports(nowMs, limit)`(메모리·Drizzle)와 정비 작업 `review-report-retention`(daily)을 더한다. `purge_at <= nowMs`이고 `status='RESOLVED'`인 행을 100개씩 지운다. `core_maintenance`에 `content_report` 행 지우기 권한을 준다(0053).
   - `review-temp-block-expire`는 그대로 두고, `review-report-retention`을 `reviewMaintenanceTasks`에 더한다.
5. **I-05 신고 누리집 링크**(G-07, AC-01):
   - `ticket-transfer/ui/TicketTransferLive.tsx`의 법정 고지 아래에 `SCALPING_REPORT_CENTER_URL` 링크를 더한다. `target="_blank"`, `rel="noopener noreferrer"`, `aria-label="온라인 암표신고센터, 새 창"`. 링크는 받는 분을 확인한 뒤(법정 고지와 같은 자리)에만 보이고, 주소에 게시물·티켓 정보를 싣지 않는다. 문구는 후기 모달과 같은 '온라인 암표신고센터'다.
   - `ReviewModalsClient`·DS `ReportDialog`의 기존 링크는 그대로 두고 회귀 시험만 둔다. `LEGAL_RESALE_NOTICE`의 공연법 §41·§4의4 문구는 바꾸지 않는다.
6. **I-06 콘솔 통보 탭**(G-08, AC-02~AC-05):
   - `compliance/ui/Page.tsx`를 `cs-inbox`처럼 `__PREVIEW__ && ?state=`일 때만 정적 보드, 그 밖에는 `ConnectedPage`로 바꾼다. `ConnectedPage`는 통보 탭만 실제 API에 잇고(목록·상세·등록·차단·철회), 자료 요청·보안 사고·접속기록 점검 탭은 "이번 동결 범위 밖" 안내를 둔다.
   - `compliance/model/notice.ts`에 `noticeViewOf`, `noticeFilterOf`, `noticeCreatePlan`, `noticeActionPlan`, `noticeDetailOf`(계정·신고자·주문·본문 원문 버림), `noticeActionsFor(detail, role)`(operator·commander만 차단·철회)를 둔다. 화면 글은 글자 노드로만 넣고, 사유는 1~2,000자, 철회는 확인 대화상자를 거친다. 409·503은 까닭을 보이고 목록·상세를 다시 읽는다.
7. **I-07 문서·기록**: `docs/data.md` §2 ERD에 `takedown_notice_action` 표와 `takedown_notice`의 `requested_by`·`idempotency_key`, `content_report` 정리 권한(`core_maintenance` SELECT(`purge_at`,`status`)·DELETE)을 **이번 시험 고정 전에** 적었다. 구현 뒤에는 `docs/lanes/lane5.md` 진행 로그, BUILD_ORDER F-07-11 줄 비고(동결 로컬 범위·남은 몫), 이 파일 §7~§10을 고친다. POL-024·044·d5의 법정 문구는 바꾸지 않고 새 법정 문구를 만들지 않는다.

## 4. 장부 범위


- BUILD_ORDER F-07-11 줄의 장부 범위 그대로 6항목이다(문서 통째 여섯 → 이 기능에 닿는 항목). 상태 `동결`과 `frozen-local` 분류는 그대로다(ADR-0386). `node tools/ci/ledger.mjs --batch F-07-11`: 항목 6, 자동 시험 6, 빈칸 0, 등급 B 6. **기준 트리에서 이미 `--require`가 통과한다**(BAT-585·F-07-10 시험이 이름표를 갖고 있다). 이번 시험은 그 이름표를 새 동작(통보·철회·보관)으로 채운다.
- **왜 이 6개인가**: `C-T22`는 통보로 가린 후기와 같은 내용의 새 후기를 저장할 때 바로 숨김·철회 때 함께 복원, `1.3.3`은 통보 요약·사유·신고 내용의 길이와 제어 문자, `2.2.3`은 통보 대상 후기·같은 내용 지문·기관 요청의 조합, `2.3.2`는 통보 후기 100개·신고 하루 10건·통보 요청 멱등, `2.3.3`은 통보 적용·철회·신고 처리·보관 정리의 트랜잭션, `2.4.1`은 통보·신고의 남용 제한과 내부 토큰 경계다.
- 장부에 넣지 않는 것: `8.2.3`·`14.2.6`(통보 응답의 필드 가림·개인정보는 이번에 시험하지만 F-07-11 장부 범위가 아니다), `5.4.3`(통보 원본 검사는 G-10으로 넘김), `3.5.1`(양도 링크는 시험하지만 장부 범위 밖), `C-T16`(조치 결과서 파일은 G-11).
