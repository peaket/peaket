# 묶음 계획: BAT-617(LCH-080 잔여 화면 — SCR-021 5단계·SCR-048)

- **무엇**: 묶음을 시작할 때 만든 작업 목록이다(docs/architecture.md §8.6 4의 1, ADR-0256 결정 10). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다. 정본의 값은 옮겨 적지 않고 자리(문서·절)만 가리킨다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane5`, 가지 `feature/lane5-BAT-617`, 출발점 `origin/develop` `97b47ca81`(2026-11-22, R-756). BAT-616(R-726)이 서버·저장소·대기열·purchase를 넣었고, 이 묶음은 그 위의 화면과 계약 정합만 한다.
- **등급**: B(docs/BUILD_ORDER.md BAT-617 행). A등급 대상(돈·좌석·대기 순번)의 핵심 로직을 바꾸지 않는다. 화면·권한·개인정보·계약 정합이라 B 증명(실패 상황 시험, 틀린 구현 표본 8개)으로 한다. 구현 전 트리 실패 확인은 ADR-0331 결정 3에 따라 하지 않는다.
- **차례**: 시험 먼저(계획 → 시험 → 구현 → 리뷰 → 검증 → 기록). `Batch-Order` 꼬리말은 달지 않는다.

## RV-05·RV-06 결정(계획 전)

### RV-05 승인 본문 `artistIds`·`aliases` 계약 어긋남 — 계약을 구현에 맞춘다

- **정한 것**: `POST /v1/ops/sale-reviews/{productionId}/approvals` 본문에서 `artistIds`(필수)와 `aliases`를 **뺀다**. `placeId`는 **선택**으로 바꾸고, `accessibleSeatingCheck`(선택)를 계약에 적는다. 화면은 계약 생성 클라이언트가 만드는 `{ scales, placeId?, accessibleSeatingCheck? }`만 보낸다.
- **까닭**: 구현 `SaleApprovalBody`(`services/core-svc/src/modules/catalog/inbound/ops-sale-review.controller.ts`)는 `.strict()`로 `scales`·`placeId`·`accessibleSeatingCheck`만 받고, `artistIds`·`aliases`를 저장하는 코드가 없다. 운영자가 기존 아티스트·공연장을 잇거나 새로 만드는 `POST /v1/ops/artists`·`POST /v1/ops/places`도 아직 없다. 1.5일 화면 묶음에서 아티스트 연결 저장·검색 색인·감사를 새로 만들면 이 묶음의 범위를 넘고, 계약을 지키는 생성 클라이언트 본문이 400이 되는 결함을 남긴다. 정본(openapi 설명)도 "아티스트·공연장 연결"을 승인 본문의 필수 항목으로 적고 있어 함께 고친다.
- **화면이 승인에 싣는 것**: 회차별 `scales`와, 상세가 준 `placeId`가 있으면 그 값. `placeId`가 없으면(새 공연장 요청) 보내지 않고 서버가 지금 값을 그대로 둔다. 화면은 "등록된 공연장" 또는 "새 공연장 요청 — 운영자 연결은 다음 단계"를 읽기 전용으로 보인다.
- **남는 것**: 아티스트·다른 이름 연결(기존 행에 잇기·새로 만들기)과 공연장 새로 만들기는 **LCH-080 잔여**로 남긴다. 이 묶음은 승인 본문에서 그 칸을 없애 화면과 서버가 같은 계약을 쓰게 하고, 잔여를 BUILD_ORDER LCH-080 줄·ADR-0327 보충·기록에 적는다. 그래서 LCH-080 단계 줄은 이 묶음에서 체크하지 않는다.
- **생성물**: `docs/api/openapi.yaml`을 고친 뒤 `pnpm --filter @peaket/contracts gen`·`pnpm --filter @peaket/api-client gen`을 돌려 `packages/contracts/src/gen/**`·`packages/api-client/src/gen/**`을 같은 시험 커밋에 넣는다. 손으로 고치지 않는다.

### RV-06 메모리/DB 갈림 — 메모리를 DB에 맞춘다

- **관제 상세의 회차 목록**: DB(`drizzle-sale-store.ts` `opsReviewDetail`)는 취소 회차를 포함하고, 메모리(`memory-sale-store.ts` `#events`)는 뺀다. 계약 `OpsSaleReviewEvent.status`가 CANCELLED를 허용하므로 **상세는 취소 회차를 포함**한다. 메모리 상세만 취소 회차를 포함하고, 목록·파트너 현황은 지금처럼 취소 회차를 뺀다.
- **목록 정렬 폴백**: DB는 `coalesce(sale_submitted_at, sale_approved_at, created_at)`, 메모리는 `new Date(0)`이다. 메모리 `Production`에 `createdAt`을 더하고 등록 때 채워, 폴백을 `createdAt`으로 맞춘다. 실제 PostgreSQL 통합 시험에 ① 취소 회차가 상세에 있는지 ② 제출·승인 시각이 없는 SUBMITTED 행이 `created_at` 차례로 오는지 한 줄씩 더한다.

## 계획

### 1. 범위

**하는 것**

1. **SCR-021 5단계 실제 화면(파트너)**: `/events/[id]/sale-review`에서 공연 ID가 목업이 아니면 실제 API로 그린다. 판매자 정보 6칸+통신판매업 신고번호/면제 근거, 정산 계좌 모양(저장하지 않음), 휠체어석 확인, 상태·반려 사유·제출 시각을 보이고 `partner_admin`이 요청·변경 취소한다. 계좌는 화면·요청 본문 밖으로 남기지 않는다(응답에 없다).
2. **SCR-048 실제 화면(관제)**: `/sale-reviews/:productionId`에서 목록(상태 필터·커서)과 확인 패널(판매자 정보, 회차·규모, 판매 정책 읽기 전용, 제출 시각, 재승인, 반려 사유, 휠체어 확인, 공연장)을 실제 API로 그린다. operator·commander만 승인·반려하고 viewer·CS는 읽기만 한다. 409·403·503과 반려 사유를 구분해 보인다.
3. **계약 정합(RV-05)**: openapi 승인 본문 정리, `OpsSaleReviewDetail`에 `placeId`·`placeName`·`requestedPlace`·`accessibleSeatingCheck` 추가, `PartnerSaleReviewStatus`에 `title` 추가. core-svc DB·메모리 저장소와 응답 스키마를 맞춘다.
4. **RV-06**: 메모리 저장소의 상세 취소 회차·정렬 폴백을 DB와 같게 맞추고, PostgreSQL 통합 시험을 더한다.
5. **정본·장부**: d5 §6.4·§7.9, settlement §9·§15, control-tower §4·§16, ADR-0327 보충, BUILD_ORDER BAT-617 비고, ASVS settlement/transfer-refund 표의 화면 행, `docs/lanes/lane5.md` 진행 로그(기록 커밋).

**뺀 것과 까닭**

- 아티스트·다른 이름 연결, 새 아티스트·공연장 만들기: LCH-080 잔여(RV-05 결정). 화면은 읽기 전용 안내만 둔다.
- 판매 중지·재개(2인 승인), 회차 취소 요청, 결제사 지정: LCH-090·LCH-110·다른 묶음. 자리와 안내만 둔다.
- 지급대행 등록·예금주 조회·KYC: LCH-110. 화면은 "지급대행 연동 전"만 적고 가짜 상태를 만들지 않는다.
- 휠체어석 수·위치 재계산: LCH-090. 요청 본문의 `confirmed`와 상세의 `accessibleSeatingCheck`만 보인다.
- 1~4단계 실제 저장, 휴대폰 입력: 지금 목업/안내 카드를 유지한다.
- 영업일·수요 예측 계산: 수요 예측은 `demandForecastPath` 링크만 둔다(ops-svc 화면·API는 BAT-616 밖).

### 2. 장부 범위

```text
S-T41
```

- BUILD_ORDER BAT-617 행의 장부 범위는 `S-T41`이다. BAT-616이 ①~⑪을 채웠고, 이 묶음은 **⑫ 화면**의 자동 시험을 더한다. `S-T41`의 A 판정(판매 열기·UPCOMING·대기열)은 BAT-616 시험이 그대로 맡는다.
- 시험 이름에 `S-T41 ⑫`와 `[ASVS v5.0.0-8.2.2]`·`[ASVS v5.0.0-8.2.3]`를 단다. `ledger --batch BAT-617 --require`가 12개 항목을 모두 자동 시험으로 읽는지 확인한다.
- LCH-080은 단계 ID라 장부 토큰이 아니다. 단계 줄 체크는 이 묶음의 기록 커밋 뒤에 한다(계획 §RV-05 결정에 따라 아티스트 연결 잔여가 있어 체크하지 않는다).

### 3. 공개 인터페이스(시험 담당이 기댄다)

**HTTP(core-svc, 계약 변경)**

- `POST /v1/ops/sale-reviews/{productionId}/approvals` 본문: `{ scales: {eventId, scale}[], placeId?: uuid, accessibleSeatingCheck?: boolean }`. 정의 밖 칸(특히 `artistIds`·`aliases`)은 400. `scales`가 빠지거나 회차가 빠지면 422.
- `GET /v1/ops/sale-reviews/{productionId}` 응답에 `placeId: uuid|null`, `placeName: string|null`, `requestedPlace: boolean`, `accessibleSeatingCheck: boolean|null`을 더한다.
- `GET /v1/partner/productions/{productionId}/sale-review` 응답에 `title: string`을 더한다.

**파트너 화면 모델(`apps/partner/src/_pages/event-wizard/model/sale-review-live.ts`)**

- `emptySaleReviewForm()`, `formFromStatus(status)`, `validateSaleReview(form): {field, message}[]`, `toSaleReviewBody(form)`, `saleReviewView(status)`, `saleReviewProblem(e)`.
- `toSaleReviewBody`는 `{seller, payoutAccount, accessibleSeating}`만 내고, `confirmed`는 참, 신고번호/면제 근거는 하나만 낸다. 계좌번호는 어디에도 저장하지 않는다.

**관제 화면 모델(`apps/console-host/src/pages/sale-review/model/sale-review.ts`)**

- `mapSaleReviewList(page)`, `mapSaleReviewDetail(detail)`, `statusLabel`, `formatKst`, `initialScales(events)`, `validateApproval(detail, scales)`, `approvalBody(detail, scales)`, `validateRejection(reason)`, `saleReviewProblem(e)`, `canAct(role)`, `canRead(role)`.
- `approvalBody`는 `{scales, ...(placeId ? {placeId} : {})}`만 낸다. `artistIds`·`aliases`를 넣지 않는다.

## 리뷰

### 확인한 것

- **계획 대조**: RV-05(승인 본문 `artistIds`·`aliases` 제거, `placeId` 선택, 상세·현황 읽기 칸)와 RV-06(메모리 상세 취소 회차·`createdAt` 폴백)이 구현·계약·시험에 모두 반영됐다. 파트너 5단계는 실제 `GET/POST/DELETE /v1/partner/productions/{productionId}/sale-review`만 쓰고, 관제는 `listOpsSaleReviews`·`getOpsSaleReview`·`createOpsSaleReviewApproval`·`createOpsSaleReviewRejection`만 쓴다. 목업은 `?state=` 미리보기에만 남았다.
- **계약**: openapi 승인 본문은 `scales` 필수, `placeId`·`accessibleSeatingCheck` 선택이고 `artistIds`·`aliases`가 없다. 생성 Zod·TS·MSW 처리기가 같은 모양이며, api-client 계약 시험이 생성 모델에 두 칸이 없는 것까지 본다.
- **권한·개인정보**: 파트너 요청·변경 취소는 `partner_admin`, 현황은 실무자도 읽는다. 관제는 viewer·CS 읽기, operator·commander 승인·반려다. 화면은 미리보기 역할로 단추를 숨기고, 실제 세션은 서버 403을 받은 뒤 단추를 잠근다. 목록에는 판매자 상호만 있고, 상세·현황의 판매자 정보는 권한 있는 역할에게만 보인다. 계좌는 요청 본문에만 있고 저장·응답·브라우저 저장소에 남지 않는다.
- **접근성**: 입력마다 레이블·`aria-invalid`, 오류 요약의 칸 링크와 첫 오류 초점, 회차 규모 라디오의 fieldset·legend, 확인 대화상자의 초점 가두기(파트너 Modal·관제 Overlay), 읽기 전용 안내가 있다. 오류 문구는 409(간격·상태)·422(규모·명단)·403·503을 구분한다.
- **RV-06**: 메모리 상세가 취소 회차를 포함하고 목록 정렬 폴백이 `createdAt`이며, 실제 PostgreSQL 시험에 취소 회차·정렬 폴백·새 상세 칸이 들어 있다. 요청이 `accessibleSeatingCheck=true`를 남기는 것도 DB와 같다.
- **자주 놓친 결함**: 승인·반려·요청·변경 취소 뒤 `await load()`로 서버를 다시 읽고, 실패하면 이전 상태를 유지한다. `artistIds`가 본문에 새지 않고, 계좌를 localStorage·sessionStorage에 두지 않는다. 구현 커밋이 시험 파일을 바꾸지 않았고, 시험 커밋이 생성물을 함께 넣었다.
