# BAT-038 계획 — 결제 접수 전용 HTTP 칸막이

- 작성: 2026-11-13
- 묶음: BAT-038(HOT-472, 갈래 1, 구간 1, **A등급**, 0.5~1일 [가정])
- 장부 범위: `P-T1`, `P-T23`
- 선행: BAT-037(HOT-471, R-508). 공유 `purchase-write` 칸막이(기본 64)는 주문·결제 시작·접수가 함께 써서, K7 r1에서 접수 429 158건 중 **106건이 칸막이 즉시 거절**이었다.

## 1. r1 귀속

K7 r1(칸막이 64, 유효) 메인 구간:

| 경로 | 429 | 칸막이 즉시(<10ms) | 핫풀 200~400ms | 성공 p50/p99 |
| --- | ---: | ---: | ---: | ---: |
| 주문 | 544 | 535 | 9 | 394.76 / 711.38ms |
| 결제 시작 | 130 | 117 | 6 | 378.25 / 931.87ms |
| **접수** | **158** | **106** | **17** | 354.29 / 813.17ms |
| 결제 상태 | 53 | 0 | 41 | 1,260.88 / 2,757.42ms |

- 접수 429 158 = 칸막이 즉시 106 + 핫풀·기타 52.
- 주문·결제 시작이 공유 `purchase-write` 자리를 먼저 먹어 접수가 즉시 거절된다.
- 128·192는 칸막이 즉시 거절을 0으로 만들었지만 핫풀 429가 늘어 429 2.67%·3.47%, p99 3,831·3,977ms로 더 나빠졌다. **R-508 기본값은 64로 유지한다.**

## 2. 고른 수정 — (가) 접수 전용 칸막이

- 결제 접수만 다른 이름 `purchase-accept`의 `@Bulkhead`를 쓴다.
- 주문 생성·결제 시도 시작은 기존 `purchase-write`(기본 64)를 그대로 쓴다.
- 접수 칸막이 기본 64, `Retry-After: 1`, 환경 값 `PEAKET_PURCHASE_ACCEPT_BULKHEAD_LIMIT`(1~1,024).
- 주문 폭주가 접수 몫을 먹지 않게 하는 가장 작은 수정이다. 접수 자신의 폭주는 접수 칸막이가 따로 막는다.

### 왜 (나)·(다)가 아닌가

- (나) 접수 전용 DB 풀(8~16 분리): r1 접수 핫풀 429는 52/9,326 = **0.56%**다. (가)가 즉시 106건을 없애면 접수 429는 52건(0.56%)으로 1% 아래가 될 수 있다. 전용 풀은 더 큰 변경이라, K7에서 핫풀 429가 1% 이상으로 남을 때 다음 후보로 둔다.
- (다) 공유 칸막이에서 접수 몫 예약/우선순위: 공유 한도 안에서 접수 몫을 예약하는 복잡한 규칙이 필요하고, 접수가 핫풀을 더 쓰게 되면 풀 429는 그대로다. (가)가 더 작고 분명하다.

## 3. 짧은 프로파일 — p99 3.7초는 CPU/event loop가 아니다

BAT-038 빌드로 30초(예열 5초·본구간 30초, 100/s, 같은 장애 주입) 프로파일:

| 지표 | 값 |
| --- | ---: |
| 번들 CPU(3파드 합) | **1.09코어** |
| 이벤트 루프 지연 max / p99 / 평균 | **52.5ms / 14.6ms / 4.8ms** |
| `payment.status.wait` p50 / p99 | 1.37s / **2.80s** |
| `payment.status.read` p50 / p99 | 23ms / **274ms** |
| `payment.status.poll` p50 / p99 | 14ms / 55ms |
| `saga.total` p99 | 793ms |
| `payment.result.total` p99 | 497ms |
| `hold.total` p99 | 18ms |

- p99 3.5초의 대부분은 **결제 상태 롱 폴링 대기**(`payment.status.wait` p99 2.80s)다. CPU·이벤트 루프는 여유가 있다.
- 핫풀 대기는 `payment.status.read` p99 274ms와 429(200~400ms)로 나타나지만, 3.7초 전체를 설명하지는 않는다.
- p99 <3초는 429와 별도 문제다. 다음 후보는 롱 폴링 대기 꼬리(장애 주입·재시도·wake 간격)와 `payment.status.read` 핫풀 대기다.

## 4. 시험

- 플랫폼 `@Bulkhead` 시험: 기존 9건 유지.
- purchase-svc 설정 시험: `purchase-write`·`purchase-accept` 기본 64·1~1,024·같은 객체 적용.
- 접수 HTTP 시험: 주문 생성이 `purchase-write` 자리를 쥐고 있어도 접수는 `purchase-accept`라 429가 아니고 202다.
- 기존 주문·결제 시작 HTTP 시험과 전체 단위 시험으로 동작 불변 확인.
- 관련 test-int: `accept-e2e`·`orders-e2e`·`order-accepts`.

## 5. K7 재측정(measurement go 뒤)

- K7 진단 1회, 같은 조건(split·2Gi·relay 정상·CPU 4·새 클러스터), 기본 64.
- 확인: **접수 429 <1%**, 칸막이 즉시/핫풀 200~400ms 구분, `purchase-accept` 거절 수, dropped/오류/`startSkewS`, truncated terminal/pending.
- 접수 429가 1% 이상이고 핫풀 200~400ms가 대부분이면 **(나) 접수 전용 DB 풀(8~16)**을 다음 후보로 검토한다.
- p99 <3초는 별도로 보고한다. 롱 폴링 대기·장애 주입 꼬리가 주원인이면 429와 분리해 다음 배치를 정한다.
