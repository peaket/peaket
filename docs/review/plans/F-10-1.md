# 기능 계획: F-10-1(탐색·콘텐츠 — 홈 피드·검색 읽기 모델·순위·골든 세트)

- **무엇**: 기능을 시작할 때 만든 작업 목록이다(docs/architecture.md §8.6 4의 1, ADR-0256 결정 10, ADR-0354). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **바탕**: 작업 폴더 `D:/ticketpass-freeze-F-10-1`, 가지 `freeze/lane1-F-10-1`, 출발 `origin/develop` `8a7081d94`(2026-11-26). **동결 로컬 갈래**다(ADR-0386 결정 4·5). `develop`·`release/1.0.0`에 합치지 않고, 릴리스 가지·`main`에 체리픽하지 않는다.
- **등급**: B다(docs/BUILD_ORDER.md F-10-1). 돈·좌석·대기 순번이 아니다. 사용자 지시로 B등급도 **계획 → 시험 → 시험 리뷰(새 세션) → 지적 반영 → 구현 → 기록** 차례로 한다(ADR-0373의 B등급 최소 차례에 시험 리뷰를 더한 동결 로컬 차례). 이번 중간 보고는 계획·시험·기준 실패 확인에서 멈춘다.
- **단계**: HOT-305(홈 피드 서버)·HOT-270(검색 백엔드)·HOT-280(순위·0건·골든 세트). 다만 HOT-270·HOT-280은 이미 대부분 구현됐고(§1), 이 기능의 새 동작은 HOT-305의 홈 피드 서버·읽기 모델·캐시 무효화다.
- **정본**: `docs/features/search.md` §2.2~§2.4·§5·§12(SR-T1~SR-T17), `docs/frontend.md` §2.5 '/' 행·§5.15·§5.17, `docs/api/openapi.yaml` `getHome`·`HomeFeed`·`ProductionCard`, `docs/data.md` §2 `home_banner`·`home_theme`·`home_theme_item`·`search_document`, `docs/design/d5-screen-blueprint.md` §5.1, `docs/security/asvs/catalog-review.md` 해당 행, `docs/BUILD_ORDER.md` HOT-305·HOT-270·HOT-280 단계 줄, ADR-0063·0064·0093·0094·0118·0199·0261·0271·0373·0386.
- **경계**: F-07-8(일괄 환불·정산)은 돈 갈래이고 이 기능이 건드리지 않는다. F-07-9(파트너 콘솔 모바일·고지)는 화면 갈래이고 이 기능이 건드리지 않는다. F-10-2(image-worker·파생본·모의 검사기·D-T35)는 이미지 처리 갈래이고, 이 기능은 `home_banner.image_key`를 기준 주소로 바꾸는 자리만 둔다. OPS-410(SCR-068 홈 구성 화면·저장)은 F-03-5(동결) 몫이고, 이 기능은 그 표를 읽기만 한다. 장르별 랭킹 파일 게시는 F-04-5·OPS-230(동결) 몫이다.

## 3. 이번에 하는 것

구현 담당 할 일은 다섯이다(I-01~I-05). 차례: I-01 → I-02 → I-03 → I-04 → I-05. **시작 조건: 시험이 고정되고 시험 리뷰 지적이 반영된 뒤.**

1. **I-01 홈 구성 읽기 표(마이그레이션 0051)**:
   - `services/core-svc/migrations/0051_home_layout_read.sql`: `home_banner`(id, production_id, image_key, alt_text, title, subtitle, sort_order, display_from, display_until, created_by, updated_by, updated_at), `home_theme`(id, name, sort_order, display_from, display_until, created_by, updated_by, updated_at), `home_theme_item`(theme_id, production_id, sort_order)을 docs/data.md §2 모양대로 만든다. 색인 이름은 `home_banner_display_idx`(display_from, display_until)·`home_theme_display_idx`(display_from, display_until)·`home_theme_item_order_idx`(theme_id, sort_order)로 고정한다. 홈 구성은 공개 콘텐츠라 행 보안을 걸지 않는다. `core_app`에 세 표의 `GRANT SELECT`만 주고 쓰기 권한은 OPS-410이 붙일 때 정한다.
   - `migrations/meta/_journal.json`을 같은 커밋에 잇는다(번호 0051, 기존 0047 다음). 스냅숏은 기존 마이그레이션 관례를 따른다(0032 뒤 스냅숏 파일이 없다. 이 기능도 새 스냅숏을 만들지 않는다).
   - `services/core-svc/src/modules/catalog/adapters/db/schema.ts`에 세 표의 Drizzle 정의를 더한다.
   - `home_banner`에는 `event_id` 칸이 없다. 응답 `eventId`(대표 회차)는 같은 공연의 `search_document.representative_event_id`를 쓴다(추천 적용, TR-09·TR-17).
2. **I-02 홈 피드 읽기 경로**:
   - 새 `domain/home-feed.ts`: `HomeBanner`, `HomeTheme`, `HomeFeedData`, 상한 상수(`HOME_UPCOMING_MAX=10`, `HOME_ON_SALE_MAX=9`, `HOME_PLACES_MAX=10` [가정]), 고르기·정렬 순수 함수.
   - 새 `domain/home-ports.ts`: `HomeFeedSource { documents(now): Promise<SearchDocument[]>; banners(now): Promise<HomeBannerRow[]>; themes(now): Promise<HomeThemeRow[]> }`, `HomeLayoutSource`, `HOME_FEED_SOURCE` 토큰.
   - 새 `application/home-feed.ts`: `HomeFeed.get(): Promise<HomeFeed>` — `search_document` 문서에서 오픈 예정·지금 판매 중·공연장을 고르고, `home_banner`·`home_theme`·`home_theme_item`을 붙여 `ProductionCard`로 만든다. 줄별 상한·정렬·빈 줄은 §2.4 그대로. `banners()`·`themes()` 실패는 그 줄만 비우고 경고 로그 `home_feed_source_degraded`를 남긴다.
   - 새 `inbound/home.controller.ts`: `GET /v1/home`, `@Roles(['public'])`, `Cache-Control: public, max-age=30, stale-while-revalidate=30, stale-if-error=86400`, 200 JSON에만 캐시 머리. `/v1/home` 아래 정의 밖 경로는 404·`no-store`(검색과 같은 모듈 미들웨어).
   - 새 `adapters/memory-home-feed-source.ts`: 메모리 저장소에서 `documentOf`로 문서를 만들고, `AppModule.register({ memory: true, home })`로 받은 배너·테마 씨앗을 쓴다. `home` 씨앗 모양은 §5.1.
   - 새 `adapters/db/drizzle-home-feed-source.ts`: `search_document` 뷰를 정렬 질의로 읽는다(오픈 예정은 `sale_status = 'UPCOMING'`이고 `next_open_at > now`, 차례는 `next_open_at`·ID / 판매 중은 `sale_status = 'ON_SALE'`, 차례는 `sale_ends_at`·ID). 줄 고르기는 `sale_status`로만 하고 `sale_ends_at`은 표시·정렬에만 쓴다(TR-04). `home_banner`·`home_theme`·`home_theme_item`을 읽고 `documentOfRow`를 재사용한다.
   - `catalog.module.ts`·`index.ts` 조립. `main.ts`의 의존성 주입은 새 포트를 쓴다.
3. **I-03 홈 캐시 무효화**:
   - 새 `application/home-cache.ts`: `HomeCacheInvalidator.invalidate(reason)`가 `CdnInvalidation.invalidate(['home'])`를 기존 event·production 태그 호출과 **따로** 한 번 부르고, 이어서 `NextCacheInvalidator.revalidate('home')`을 부른다. 둘 다 `await`하고, 하나가 실패해도 다른 쪽을 부른다. 실패는 경고 로그 `home_cache_invalidate_failed`로 남긴다(응답을 바꾸지 않는다). `reason`은 `SALE_APPROVED`·`SALE_SUSPENDED`·`EVENT_CANCELLED`·`HOME_LAYOUT_SAVED`·`SOLD_OUT` [가정 이름]. 판매 승인 시험은 CDN 호출 수를 1~2로만 보고 태그 합집합에 `home`이 있는지 본다(TR-02).
   - 새 `domain/next-cache-ports.ts`: `NextCacheInvalidator { revalidate(tag: string): Promise<void> }`, `NEXT_CACHE_INVALIDATOR` 토큰. `adapters/http-next-cache.ts`: `PEAKET_WEB_INTERNAL_URL`이 있으면 `POST /internal/v1/home-cache`(내부 토큰, 3초 [가정]), 없으면 아무것도 하지 않는다(로컬·CI). 실패는 `HomeCacheInvalidator`가 삼킨다.
   - `approve-sale-review.ts`·`change-sale-suspension.ts`·`apply-event-cancellation-status.ts`가 커밋 뒤 `HomeCacheInvalidator.invalidate(...)`를 부른다. 기존 CDN 태그 호출과 같은 자리다.
   - 새 `inbound/internal-home-cache.controller.ts`: `POST /internal/v1/home-cache/revalidate`(내부 토큰, 204, `no-store`). OPS-410·매진 알림이 쓰는 자리다. 같은 요청을 두 번 불러도 같은 결과다.
4. **I-04 `apps/web` 내부 처리기**:
   - 새 `apps/web/src/_pages/home/api/home-cache.ts`: `createHomeCacheHandler({ revalidate, token })`가 `(request: Request) => Promise<Response>`를 돌려준다. POST만 받고, `x-peaket-internal-token`이 `token`과 같을 때만 `revalidate('home')`을 한 번 부르고 204·`Cache-Control: no-store`. 토큰이 없거나 틀리면 401·`no-store`, 다른 메서드는 405·`no-store`.

   - `apps/web/src/_pages/home/api/load-home.ts`는 그대로 둔다. `revalidateTag('home')`이 ISR 캐시를 비우면 다음 요청이 새 피드를 읽는다.

### 5.1 시험이 쓰는 공개 인터페이스

시험 담당은 이 모양만 보고 시험을 쓰고, 구현 담당은 이 모양대로 만든다. 이름·인자·돌려주는 값·오류 이름을 바꿔야 하면 구현 담당은 바꾸지 않고 계획 담당에게 '인터페이스 이의'를 낸다.

**(가) 메모리 씨앗(`AppModule.register`의 `home`)**

```ts
interface HomeBannerSeed {
  bannerId: string;
  productionId: string;
  eventId: string;
  title?: string;
  subtitle?: string;
  imageUrl: string;
  alt: string;
  displayFrom: string; // ISO 8601
  displayUntil: string;
  sortOrder: number;
}
interface HomeThemeSeed {
  themeId: string;
  name: string;
  productionIds: string[];
  displayFrom: string;
  displayUntil: string;
  sortOrder: number;
}
```

- 시험은 `AppModule.register({ memory: true, catalog: repo, home: { banners, themes } } as never)`로 넘긴다. 기준 트리에서는 이 칸이 무시되어 `GET /v1/home`이 404다. 구현은 메모리 모드에서 이 씨앗을 `MemoryHomeFeedSource`에 넣는다.
- 장애 주입은 `home: { source: { documents, banners, themes } }` 꼴을 받는다. `source`가 있으면 씨앗 대신 그것을 쓴다. `banners`·`themes`는 위 `HomeBannerSeed`·`HomeThemeSeed`와 같은 모양을 돌려준다. 시험은 한쪽만 던지는 대역을 넣어 다른 줄이 살아 있는지 본다(AC-08, TR-05).
- `imageUrl`은 시험이 정한 절대 주소다. 구현은 DB 모드에서 `home_banner.image_key`와 `PEAKET_IMAGE_ORIGIN`으로 같은 꼴의 주소를 만든다(파생본 경로 규칙은 F-10-2가 정한다).

**(나) HTTP**

| 경로 | 메서드 | 응답 |
| --- | --- | --- |
| `/v1/home` | GET | 200 `HomeFeed`, `Cache-Control: public, max-age=30, stale-while-revalidate=30, stale-if-error=86400`. 정의 밖 `/v1/home/*`은 404·`no-store` |
| `/internal/v1/home-cache/revalidate` | POST | 200/204, `no-store`. 토큰 없음·틀림 401. 본문 없음 |

**(다) `apps/web` 처리기**

```ts
function createHomeCacheHandler(o: {
  revalidate: (tag: string) => void | Promise<void>;
  token: string | undefined;
}): (request: Request) => Promise<Response>;
```

- POST + `x-peaket-internal-token` 일치 → `revalidate('home')` 한 번, 204, `Cache-Control: no-store`.
- 토큰 없음·틀림 → 401, `Cache-Control: no-store`.
- POST 밖 → 405, `Cache-Control: no-store`.

### 6.3 실패 시나리오·경계값

- 홈 피드 원천 실패: `banners()`가 던지면 200·배너만 빈 배열, `themes()`가 던지면 200·테마만 빈 배열. 다른 줄(오픈 예정·판매 중·공연장)은 살아 있는 것을 본다. 둘 다 던져도 200. `search_document` 원천이 던지면 503·`no-store`(검색과 같은 `dependency-unavailable`, `Retry-After` 1초). **검색 원천 장애는 홈 전체 장애다.**
- 빈 데이터: 공연 0개 → 모든 줄 빈 배열, 200. 배너 0개·테마 0개 → 그 줄만 빈 배열.
- 상한: 오픈 예정 11개 → 10개, 판매 중 10개 → 9개, 공연장 11개 → 10개, 배너 11개/12개 → 10개, 테마 6개 → 5개, 테마 항목 21개 → 20개.
- 시각 경계: `display_from` = now → 포함, `display_until` = now → 제외(반열린 구간). `next_open_at` = now → 오픈 예정 아님(이미 오픈). `sale_ends_at = now`인 회차는 DB 뷰가 `ENDED`로 계산하며, 줄 고르기는 `sale_status`로만 해서 그 공연이 판매 중에 들지 않는다(TR-04).
- 공개 경계: `saleReview = SUBMITTED`·`REJECTED`·`SUSPENDED`, `saleApprovedAt = null`은 어느 줄에도 없다. 예외로 **승인 뒤 재승인 대기**(`saleReview = SUBMITTED`이고 `saleApprovedAt`이 있음)는 `isPublic`이 참이라 공개 줄에 든다. `APPROVED`여도 `saleApprovedAt = null`이면 빠진다. `SUSPENDED`는 배너·테마에서도 빠진다(TR-11).
- 정렬 동점: 같은 `next_open_at`·`sale_ends_at`·공연 수·공연장 이름이면 공연/공연장 ID 오름차순으로 안정적이다. 테마·테마 항목·배너는 적힌 `sort_order`(같으면 ID)를 지킨다. 두 번 불러도 같은 차례다.
- 캐시: 200 JSON만 `public` 캐시 머리. 404·401·405·503과 내부 경로의 다른 메서드는 `no-store`. 내부 처리기는 토큰 비교를 문자열 완전 일치로 하고, 토큰이 `undefined`면 늘 401이다(빈 문자열 토큰을 허용하지 않는다). Fetch Headers가 앞뒤 공백을 지우므로 `'secret '`는 실제로 `'secret'`이다(TR-01).
- 캐시 무효화: CDN `['home']` 호출과 웹 재검증을 따로 부르고 둘 다 기다린다. CDN이 던져도 웹 재검증을 부르고, 웹이 500이어도 CDN을 부른다. 판매 승인 응답은 200 그대로다. 로그에 `home_cache_invalidate_failed`가 남는다(TR-02·TR-03).
- 내부 경로: 본문 없이 POST, 같은 요청 두 번 → 둘 다 204, 태그 호출 두 번(멱등은 '같은 결과'이지 '한 번만'이 아니다). 토큰 틀림 401, `no-store`. GET 같은 다른 메서드는 2xx가 아니고 `no-store`다(TR-13).
- 개인정보: 홈 피드 응답 원문과 로그에 계정 ID·쿠키·IP·검색어가 없다. `HomeFeed`는 공개 값만 싣고, 쿠키·인증 머리를 실은 요청도 같은 본문·캐시 머리를 준다(TR-07).

**② 장부**: `node tools/ci/ledger.mjs --batch F-10-1 --require` → 항목 35개(자동 시험 33·측정 1·해당 없음 1), 빈칸 0·ID만 0, 통과(미검증 0·다른 단계 0). 다만 `[ASVS v5.0.0-1.2.1]`(T-H01)과 `[ASVS v5.0.0-2.1.1]`(T-H05)는 그 행을 실제로 단언하지 않는 시험에 붙어 있다(TR-15). 두 태그를 빼도 다른 시험 11·16개 파일이 그 행을 덮어 장부는 통과한다.

**③ B등급 실패 상황**: 노출 기간의 `display_from = now` 포함·`display_until = now` 제외, 상한 11→10·10→9·11→10·12→10·6→5·21→20, 토큰 없음·틀림, CDN 실패·웹 실패, 검색 원천 503을 본다. 빠진 것은 `next_open_at = now`(TR-13에 함께 적음), `sale_ends_at = now`의 올바른 쪽(TR-04), 회차 둘인 공연의 마지막 회차(TR-12), 승인 뒤 재승인 대기 공연(TR-11)이다. 악의 입력·권한 경계는 공개 읽기라 해당 없음이고, 내부 경로 토큰 한 갈래만 있다.

**④ 안티패턴**: 고정 대기 없이 `fakeClock`을 쓰고, 업무 로직을 모킹하지 않으며, 웹 재검증은 `node:http` 대역 서버로 실제 HTTP를 부른다. 타입 탈출은 `AppModule.register({ … home … } as never)` 한 곳이고 계획 §5.1이 구현 전 임시 씨앗이라고 밝혔다. T-H08의 기준 트리 실패는 `ERR_MODULE_NOT_FOUND`라 단언 실패가 아니다(TR-16). 시험 값이 코드 상수와 같아지는 안티패턴은 없다.

**⑤ 시험이 계획 밖에서 고른 것**: `home: { source: { documents, banners, themes } }` 장애 주입, `MemoryCdnInvalidation.calls`, `PEAKET_WEB_INTERNAL_URL` 대역 서버는 계획 §5.1·§6.1과 맞는다. `'secret '`를 401로 보는 대역 값(TR-01)과 판매 승인 CDN 호출을 한 번으로 못 박는 값(TR-02)은 계획과 부딪친다.

3. **판매 중지·회차 취소는 홈 캐시를 부르지 않는다**: 계획 I-03은 `SALE_SUSPENDED`·`EVENT_CANCELLED`도 적었지만, 이번 구현은 판매 승인만 연결했다(사용자 구현 차례 4). 기존 `sale-suspension.int.test.ts`의 CDN 호출 단언과 부딪치지 않게 남겼다. 후속에서 연결한다.
4. **web route의 실제 Next 런타임 미확인**: route 소스·순수 처리기 시험은 통과했지만 실제 Next 서버에서 `revalidateTag('home')`이 ISR 캐시를 비우는 것은 브라우저/빌드 확인 몫이다.
5. **배너 이미지 기준 주소**: `home_banner.image_key`를 `PEAKET_IMAGE_ORIGIN/{key}`로 바꾸는 규칙은 [가정]이다. F-10-2가 파생본 경로를 정하면 맞춘다.
6. **랭킹 파일 없음**: `rankingsPath`만 싣는다. `mtr_genre_ranking_daily`·게시 잡은 F-04-5(동결) 몫이다.
7. **`search_document` 읽기 부하**: 홈 피드는 매 요청 뷰를 읽는다. 인덱스·부하·EXPLAIN은 측정하지 않았다.
