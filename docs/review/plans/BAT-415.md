### 1. 범위: 한 몫과 남은 몫

**장부 범위·단계 줄 고칠 점(BUILD_ORDER·ledger-notes는 감독이 고친다)**

- 장부 범위 `R-T3, R-T4`는 묶음과 닿는다. 다만 이번 몫 P는 **P-T21**(ledger-notes 63줄 '다른 단계 · 미정')을 판정 기준까지 채운다. BAT-415 범위에 `P-T21`을 더하고 ledger-notes의 P-T21을 GAT-080으로 바꾸기를 제안한다.

### 3. 공개 인터페이스(시험 담당이 빈 뼈대를 만들 만큼)

빈 뼈대는 typecheck를 지나고 호출하면 `new Error('아직 없음')`을 던진다. 이름·인자·값은 아래 그대로 쓴다.

**P. payment-svc**

```ts
// domain/confirmed-cancel.ts (더함)
export const CONFIRMED_CANCEL_BUSY_WINDOW_MS = 600_000;          // 10분 [가정]: 이보다 어린 진행 중 건이 있으면 보내지 않는다
export const CONFIRMED_CANCEL_QUERY_AFTER_MS = 10_800_000;       // 3시간 [가정]: 이 이상 지난 재시도는 먼저 조회한다(P-T21)
export type PaymentCancelStatus = 'REQUESTED' | 'CANCEL_PENDING' | 'CANCELED' | 'FAILED';
export interface ConfirmedCancelRecord {
  readonly idemKey: string;          // cancel-{cancellationId}
  readonly amount: number;
  readonly reason: string;
  readonly fullCancel: boolean;
  readonly expectedBalance: number;
  readonly status: PaymentCancelStatus;
  readonly createdAtMs: number;
}
export type ConfirmedCancelBegin =   // 기존 'BEGUN'|'DONE'|'NOT_CONFIRMED' 문자열을 바꾼다
  | { readonly status: 'BEGUN'; readonly record: ConfirmedCancelRecord; readonly replay: boolean } // replay = 이 취소 ID의 행이 이미 있었다
  | { readonly status: 'DONE'; readonly cancelledAmount: number }       // 그 행이 CANCELED
  | { readonly status: 'BUSY' }                                          // 같은 결제의 다른 진행 중 행이 10분 안
  | { readonly status: 'NOT_CONFIRMED' }                                 // 원장이 APPROVED·PARTIAL_CANCELED가 아니다
  | { readonly status: 'NO_BALANCE' }                                    // 새 취소인데 남은 금액 0 이하
  | { readonly status: 'OVER_REMAINING' }                                // 요청액 > 결제 금액 − 누적 취소액 − 진행 중 다른 취소 합
  | { readonly status: 'AMOUNT_MISMATCH' };                              // 같은 취소 ID에 다른 금액
/** 3시간 지난 재시도의 조회 대조. 잔액 = 기대 잔액 − 금액이면 APPLIED, = 기대 잔액이면 NOT_APPLIED, 그 밖 UNKNOWN */
export function settleByBalance(record: Pick<ConfirmedCancelRecord, 'amount' | 'expectedBalance'>, balanceAmount: number): 'APPLIED' | 'NOT_APPLIED' | 'UNKNOWN';

// domain/ports.ts PaymentConfirmedCancels (바꿈)
readConfirmedCancelTarget(paymentId: string, budget?: CallBudget): Promise<ConfirmedCancelTarget | undefined>;        // 그대로
beginConfirmedCancel(target: ConfirmedCancelTarget, q: { cancellationId: string; amount?: number; reason: string }, budget?: CallBudget): Promise<ConfirmedCancelBegin>;
finishConfirmedCancel(target: ConfirmedCancelTarget, cancellationId: string, budget?: CallBudget): Promise<{ readonly status: 'APPLIED' | 'STALE'; readonly cancelledAmount: number }>; // 금액은 행에서 읽는다. 행이 이미 CANCELED면 더하지 않고 APPLIED
markConfirmedCancel(target: ConfirmedCancelTarget, cancellationId: string, status: 'CANCEL_PENDING' | 'FAILED', budget?: CallBudget): Promise<void>;
```

`CancelConfirmedPayment.execute(input, budget)`의 바깥 모양(`ConfirmedCancelAnswer`)과 gRPC `CancelPayment`는 그대로다. 오류: `OVER_REMAINING`·`AMOUNT_MISMATCH` → `PaymentInputError('amount')`(INVALID_ARGUMENT), `NOT_CONFIRMED`·`NO_BALANCE` → `PaymentCancelStateError`(FAILED_PRECONDITION), `BUSY` → `{ result: 'UNKNOWN' }`(결제사 부르지 않음). 결제사 호출은 `gateway.cancel({ paymentRef, amount: record.fullCancel ? 'ALL' : record.amount, reason: record.reason, idemKey: record.idemKey, expectedBalance: record.expectedBalance })`. 3시간 이상이면 그 앞에 `gateway.query(paymentRef, { timeoutMs, ...(txId ? { expectedTxId: txId } : {}) })`. 결과별: `CANCELLED` → finish, `CANCEL_PENDING` → mark CANCEL_PENDING, `REJECTED` → mark FAILED, `UNKNOWN` → 그대로(행은 REQUESTED). 기존 `CONFIRMED_CANCEL_SENT` 내부 표시 쓰기는 그대로 둔다.

마이그레이션 0021 `payment_cancel`: `id uuid PK`, `payment_id uuid NOT NULL REFERENCES payment(id)`, `idempotency_key text NOT NULL`, `amount integer NOT NULL CHECK (amount > 0)`, `reason text NOT NULL`, `full_cancel boolean NOT NULL`, `expected_balance integer NOT NULL CHECK (expected_balance >= amount)`, `status text NOT NULL CHECK (status IN ('REQUESTED','CANCEL_PENDING','CANCELED','FAILED'))`, `created_at timestamptz NOT NULL`, `canceled_at timestamptz`, `UNIQUE (payment_id, idempotency_key)`, 진행 중 색인 `(payment_id) WHERE status IN ('REQUESTED','CANCEL_PENDING')`.

**E. purchase-svc 일괄 환불**: 공개 모양은 그대로다(`EventRefundService`). `#run`이 대기 항목을 `orderId`로 묶고, 작업자(동시 `concurrency`, 기본 8)는 묶음 하나를 받아 그 안의 표를 차례로 처리한다. 묶음 안 차례는 지금 큐 차례다.

**S. purchase-svc 예매 취소**

- `POST /v1/tickets/{ticketId}/cancellation`: `CancelTicketResult`가 `TRANSFER_PENDING`·`TICKET_NOT_HELD`면 409 `ProblemError({ type: 'transfer-pending', status: 409, title: '양도 요청을 철회한 뒤 취소할 수 있습니다' })`. `NOT_PAYER`는 지금처럼 403 `not-payer`, `EVENT_STARTED`는 409 `entry-started`, 그 밖(`ALREADY_ENDED`·`CONFLICT`)은 409 `cancellation-conflict`.
- `CancelTicket.execute`: ticket-svc 답이 `ALREADY_CANCELLED`면 `{ status: 'ALREADY_ENDED' }`를 돌려주고 좌석 되돌리기·`order_cancellation`·결제사 호출을 하지 않는다. 같은 취소 ID 재요청은 ticket-svc가 처음 결과(`REFUND_NOW` 등)를 주므로 영향이 없다.

### 9. 자주 놓친 결함을 이 묶음에 대 본 것

- 저장소 응답은 정확한 값까지 본다: 결제사 본문 깊은 비교(P2), `cancelled_amount`·행 수(P5·F16), 결과 배열 전체(F4).
- 지우거나 옮기는 연산의 건드린 것: 운영자 취소의 상태·키·버전·`scanner_change`·`transfer_pending`(F1·F7), 좌석 `seat_sale`·Redis 비트(F15, R-T3 통합).
- 경계 양쪽: 10분(599,999/600,000), 3시간(10,799,999/10,800,000), 마감(−1ms/정각), 500/501장, 128/129자, 금액 딱 맞음/+1.
- 계정 대조를 뺀 요청: 호출자·처리자 증명(F14), 기대 보유자(F2).
- 장애 주입은 끊긴 사례가 실제로 있었는지 단언(P5 호출 2회, P6 첫 답 UNKNOWN·cancels 1, F5 두 경우 모두 나옴, F12 첫 호출 실패).
- 시간 상수는 가짜 시계로, 단언 값은 정본 값(10분·3시간·2시간)을 글자로 적는다.
- 허용·거부 목록은 목록 밖 값마다: 이미 끝난 상태 넷 모두(F2), 스캔 방향·결과 조합(F3), 실패 까닭·결과 CHECK(F19·P8).
- 부르는 쪽이 결과를 실제로 쓰는지: 일괄 환불이 BUSY를 피하는지(E1), HTTP가 새 오류 이름을 내는지(R-T3).
- 겹친 가드: `order_cancellation` 유일 색인과 결정적 취소 ID가 겹쳐 지킨다. M-F8c는 결정적 ID만 빼 보고 F16이 잡아야 한다(유일 색인이 가리면 F16의 '결제사 호출 표마다 1회'가 잡는다). payment는 BUSY와 진행 중 합 검사가 겹친다. M-P3a·M-P7a를 하나씩 넣어 본다.
- 시험 값이 상수와 같아 숨는 결함: 금액은 33,333·26,667·80,000처럼 상수와 다른 값, 판 번호 쓰는 곳 없음.
- 시작 파일 조립은 시험 조립과 따로 본다(F18. F15는 시험이 서버를 직접 띄운다).
- 정본 시험 표에 세부 번호를 더하지 않았다(새 시험 ID 없음).

### 10. 보충(2026-11-16, 시험 담당 '실패 확인' §3에 답함)

계획 담당 `l3w8-415-plan`. 고칠 정본 둘(docs/features/payment.md, docs/features/transfer-refund.md)은 지금 같은 폴더에서 BAT-420 계획 담당이 커밋하지 않은 채 고치는 중이라 건드리지 않았다. 아래 '정본 반영 대기' 문장은 그 파일이 풀리면 정본에 옮긴다. 그때까지 시험·구현은 이 절을 정본과 같게 본다.

① **계획 빈칸: 금액을 비운 요청과 진행 중인 다른 취소(추천 적용 2026-11-16)**. 같은 결제에 10분 [가정] 안의 진행 중 취소가 있으면 금액과 관계없이 결과 모름(BUSY)이 먼저다. 10분이 지난 진행 중 취소만 있으면, 금액을 비운 요청은 '결제 금액 − 누적 취소액 − 진행 중인 다른 취소의 금액 합'을 이번 금액으로 쓰고 금액을 적어 보낸다(`full_cancel` 거짓, 기대 잔액은 지금처럼 결제 금액 − 누적 취소액). 그 값이 0 이하면 행을 만들지 않고 결제사도 부르지 않은 채 `NO_BALANCE`(FAILED_PRECONDITION)다. 진행 중 취소가 없으면 지금처럼 남은 전부를 금액 생략 전액 취소로 보낸다. 공개 인터페이스는 그대로다(저장소 `beginConfirmedCancel`이 이 금액을 정해 `record`에 싣는다).
   - 정본 반영 대기(payment.md §4.1 '취소 건 기록과 기대 잔액', '금액을 생략한 전액 취소는…' 줄 뒤에 더할 문장): "금액을 비운 요청은 남은 금액 전부를 뜻한다. 같은 결제에 10분 [가정]이 지난 진행 중 취소가 있으면 '결제 금액 − 누적 취소액 − 진행 중인 다른 취소의 금액 합'을 금액으로 적어 보내고, 그 값이 0 이하면 결제사를 부르지 않고 `FAILED_PRECONDITION`이다. 10분 안의 진행 중 취소가 있으면 금액과 관계없이 결과 모름이 먼저다(추천 적용 2026-11-16)."
② **F13(다른 회차 표·없는 표)**: 정본 §7.4 '입력'("아무것도 쓰지 않고 `INVALID_ARGUMENT`")이 맞다. 계획 §3의 차례를 고쳤다(표 확인 → 요청 기록). 시험 담당의 '요청 기록 0건' 단언 그대로다.
③ **F16(겹친 같은 요청)**: proto의 "끝난 표(받음·건너뜀)는 저장한 결과를 그대로, 실패한 표만 다시"에서 저장 결과가 아직 없는 표는 끝난 표가 아니다. 계획 §3을 고쳤다: 마감 전 다시 부르기는 `FAILED` 표와 저장 결과가 아직 없는 표를 한다. 둘이 겹쳐도 ticket-svc (승인, 표) 기록과 정해지는 취소 ID가 하나로 모은다. 시험 담당의 관찰 값 단언 그대로다.
   - 정본 반영 대기(transfer-refund.md §7.4 '취소 마감' 줄): "마감 전이면 `FAILED`인 표만 다시 하고"를 "마감 전이면 `FAILED`인 표와 저장 결과가 아직 없는 표(앞 호출이 처리 중이거나 도중에 멈춘 표)를 다시 하고"로 바꾼다.
④ **대문자 UUID**: 정본 '소문자 UUID'가 맞다. 계획 §3 ticket-svc 주석에 "대문자는 바꾸지 않고 거절"을 적었다(purchase-svc도 같다). 시험 그대로다.
⑤ **새로 찾은 빈틈(계획 담당이 위를 고치다 찾음, 감독 확인 필요)**: 계획 담당이 쓴 정본 §7.4의 "마감 뒤면 다시 하지 않고 저장한 결과(`FAILED` 포함)를 그대로 준다"는, ticket-svc가 이미 키를 폐기하고 REFUNDED로 바꾼 뒤에 난 실패(`SEAT_RETURN_FAILED`·`CANCELLATION_CONFLICT`·`ORDER_STATE`)를 마감 뒤에 버린다. 그러면 표는 없어졌는데 환급 행이 없는 채로 남는다(돈). 고칠 규칙(추천): 마감 뒤 다시 부르기는 새 취소를 하지 않지만, 티켓 단계가 끝난 뒤 실패한 그 세 까닭의 표는 나머지 단계(좌석 되돌리기·`order_cancellation`)를 마친다. 그 표로 ticket-svc를 다시 불러도 (승인, 표) 기록이 처음 결과 `CANCELED`를 주므로 새 취소가 아니다. `TICKET_UNAVAILABLE`·`INTERNAL`인 표와 저장 결과가 없는 표는 티켓 단계가 됐는지 모르므로 마감 뒤에는 다시 하지 않는다(결과 없는 표는 `FAILED`·`INTERNAL`로 저장해 준다). 남는 한계: 티켓 단계가 커밋된 뒤 응답이 끊긴 `TICKET_UNAVAILABLE`이 마감 뒤까지 남으면 표만 취소되고 환급이 없다. ticket-svc `ticket_operator_cancellation`의 `CANCELED`와 purchase `order_cancellation`을 견주는 대사로 찾아 CS로 넘긴다(known gap, GAT-090 '실제 CS 건').
   - 이 규칙은 이미 쓴 시험 `GAT-080 F10 마감 전 첫 호출에 FAILED가 남으면 마감 뒤 다시 부르기는 ticket-svc를 부르지 않고 저장한 결과(FAILED 포함)를 그대로 준다`(FAILED 까닭으로 `SEAT_RETURN_FAILED`를 씀)와 어긋난다. 감독이 받아들이면 시험 담당이 그 시험의 FAILED 까닭을 `TICKET_UNAVAILABLE`로 바꾸고 아래 F20을 더한다. 그 전까지 구현 담당은 ⑤의 몫을 멈춘다(지금 시험대로 구현하지 않는다).
   - 정본 반영 대기(transfer-refund.md §7.4 '취소 마감' 줄): "마감 뒤면 다시 하지 않고 저장한 결과(`FAILED` 포함)를 그대로 준다"를 "마감 뒤면 새 취소를 하지 않는다. 다만 티켓 단계가 끝난 뒤 실패한 표(`SEAT_RETURN_FAILED`·`CANCELLATION_CONFLICT`·`ORDER_STATE`)는 나머지 단계를 마친다. 그 밖의 `FAILED`와 저장 결과가 없는 표는 `FAILED`로 준다(결과 없는 표는 `INTERNAL`)"로 바꾼다.

### 3. 계획과 다르게 쓴 것·계획 빈칸(구현 전에 감독·계획 담당이 볼 것)

1. **P1의 '진행 중 다른 행이 있으면 80,000이어도 금액으로'**: 통합에서 만들 입력이 없다. 진행 중 다른 건이 있으면 남은 전부(80,000)는 P7 규칙으로 `OVER_REMAINING`이다. 그래서 이 경우는 단위(저장소가 `fullCancel: false`라고 적은 건을 쓰임새가 금액으로 보내는지)로만 두었다. **계획 빈칸**: 진행 중 다른 건이 있을 때 금액을 비운 요청의 금액(남은 − 진행 중 합인지, `OVER_REMAINING`인지)이 정본에 없다. 시험하지 않았다.
2. **F13 '다른 회차 표·없는 표'**: 계획 §3 차례는 `store.create` 뒤에 `orders.findByTicket`을 두지만, 정본 §7.4 입력은 "아무것도 쓰지 않고 `INVALID_ARGUMENT`"다. 시험은 정본대로 요청 기록 0건을 단언한다(표 확인을 요청 기록보다 먼저 해야 통과한다).
3. **F16 겹친 같은 요청**: 두 답이 같으려면 다시 부르기가 'FAILED 표'뿐 아니라 '저장 결과가 아직 없는 표'도 다시 해야 한다(앞 호출이 끝나기 전에 둘째 호출이 `EXISTS`를 받는 경우). 시험은 정본의 관찰 값(두 답이 같다, 표마다 취소 행·운영자 취소 기록·환급이 하나)만 단언한다.

- 시작 파일 조립: start.ts가 `database && refund && refundTickets`일 때 서비스·내부 토큰 목록을 넣는다(F18이 글로 본다). ticket-svc start의 토큰 목록은 B6.
