# 묶음 계획 BAT-025(PRF-220 증명 핵심 측정, 측정 창 1)

- 무엇: 기능 묶음 BAT-025의 작업 목록이다(docs/architecture.md §8.6 4번 표 '1. 범위와 계획', ADR-0256 결정 10). 정본의 값은 옮겨 적지 않고 `문서:줄`로 가리킨다. 정본과 다르면 정본이 이긴다.
- 만든 때: 2026-11-10, 커밋 46afd4fd(가지 `feature/BAT-025-measure-window-1`). 지시서는 `node tools/ci/brief.mjs --batch BAT-025`의 출력이다.
- 등급: 묶음은 B다. 다만 아래 범위의 항목은 모두 A등급 문서(대기열·좌석·결제)에서 왔으므로, A등급 대상에 닿는 항목은 A로 증명한다(docs/architecture.md §8.6 3번).
- 용어: '합본'은 같은 v1 코드의 여러 서비스를 Node.js 프로세스 하나에 함께 띄운 실행 형태다(docs/verification.md:265). 'kind'는 이 PC의 Docker 안에 띄우는 연습용 쿠버네티스 클러스터다. 'k6'는 부하 시험 도구이고, '발생기'는 k6를 돌려 요청을 만드는 파드다. 'A/A'는 같은 것을 두 번 재어 잡음 폭을 보는 측정이다. '장부'는 성능 장부(`docs/perf-ledger.md`)와 완성 장부(`tools/ci/ledger.mjs`) 둘이 있어, 앞의 것은 '성능 장부', 뒤의 것은 '완성 장부'라고 적는다.

## 0. 한 줄 결론

측정할 무대가 저장소에 없다. 합본, kind 위 v1 배포, v1 k6 시나리오, 실행 도구의 v1 경로가 모두 없다(§2.1). 그래서 이 묶음을 둘로 나누기를 추천한다: 먼저 무대를 만드는 묶음(새 BAT-022, 새 단계 PRF-215), 그다음 지금의 측정 묶음(BAT-025, PRF-220). 나누는 근거는 docs/PROGRESS.md 턴 규칙 '묶음 크기'(한 턴에 끝나지 않으면 둘로 나눈다)와 docs/PROGRESS.md 턴 규칙 '측정 창과 구간 마무리'(정밀 측정은 코드가 확정되고 새 맥락 리뷰를 반영한 뒤 시작한다)다.

### 2.5 측정에 Kafka가 필요한가

필요하다. 결제 결과는 payment-svc Outbox → Kafka → purchase-svc 소비자로 오고(당기기는 받침), 구매 세션 끝 사건이 queue-svc의 입장 자리를 비운다(`services/queue-svc/src/main.ts` 소비자 조립). K7 ②의 1만 건은 입장 자리가 돌아야 지나간다. 이 PC에서 막힌 것은 Windows 쪽 Node가 Kafka 네이티브 모듈을 불러오는 일이다(docs/PROGRESS.md:32 '응용 프로그램 제어'). kind 안의 합본은 Linux 이미지라 영향이 없고, 실행 도구는 Kafka를 쓰지 않는다. 이미지 빌드도 Linux 컨테이너 안에서 한다. 다만 Kafka를 부르는 통합 시험 6개 파일은 계속 CI로만 본다.

## 3. 환경과 위험

- **kind와 PC 자원**: Docker Desktop(WSL2)에 CPU 32·메모리 약 15.5GiB(2026-11-10 `docker info`). `peaket-control-plane`이 2시간째 떠 있고, 다른 갈래의 시험 컨테이너(postgres:18-alpine) 하나가 돌고 있었다. v1 무대는 v0보다 무겁다(Strimzi Kafka, 두 Valkey, 두 DB, Prometheus, 합본 복제, 릴레이, nginx 캐시). K1 1만 명은 발생기가 여럿(CPU 2·메모리 1GiB씩, docs/verification.md:310)이라 메모리가 빠듯하다. 측정 전에 `docker system df`와 C: 남은 자리를 보고, 시험 컨테이너는 `docker rm -f -v`로 지운다(docs/PROGRESS.md:32).
- **한 번에 한 세션**: kind를 띄우는 시험과 성능 측정은 한 세션만 한다(docs/PROGRESS.md 턴 규칙 '갈래'). 정밀 측정 동안 다른 갈래는 시험을 돌리지 않는다(docs/adr/0189-execution-order-segments-and-lanes.md:49). A/A 두 쌍으로 이 규칙을 풀 수 있는지 본다(§2.3). 측정 세션은 다른 세션을 멈출 수 없으므로, 감독 세션이 측정 창 시각을 갈래 2·3에 알려야 한다(§5의 2).
- **새 클러스터 반복**: K7 ②는 회마다 클러스터를 지우고 다시 올린다(docs/verification.md:306). kind 조작은 측정 세션만 한다. 다른 갈래의 kind 시험(ci-kind와 같은 것)이 그 클러스터를 쓰고 있으면 기다린다.
- **Windows 도구 함정**: 포트 전달 끊김(불변식 검사가 PostgreSQL 포트 전달을 쓴다, `loadtest/run.mjs` 587줄), `kubectl exec -i` 표준 입력 잘림(docs/verification.md:282), `taskkill /F`면 정리를 건너뜀(그때는 `node loadtest/run.mjs cleanup`).
- **비용 없음**: 결제는 결제 시뮬레이터만 쓴다(docs/verification.md:197). 큰 원본의 S3 올리기와 OpenTimestamps 고정은 소유자 몫이거나 소유자가 맡긴 차례대로 한다(docs/verification.md:313~314, docs/PROGRESS.md:32 ②).
- **이어 돌기**: 측정 계획 파일과 상태 파일로 한 실행씩 끝난 것을 적고 다시 시작하면 다음 실행부터 돈다. 이 파일은 PRF-215(BAT-022)에서 만들지 않아 PRF-220이 처음에 만든다(§2.2 ④의 '상태 파일로 이어 도는 측정 계획' 칸은 PRF-220 몫, 추천 적용 2026-11-10, BUILD_ORDER PRF-215, 코드 리뷰, BUILD_ORDER PRF-220 줄). 측정이 도는 동안에는 시험·빌드를 하지 않고, 다음 묶음(BAT-030)의 글만 작업 트리에 쓴다(docs/PROGRESS.md 턴 규칙 '측정이 도는 동안').

## 4. 정본 빈칸과 정할 것(추천안)

구현 전에 한 번에 정본·ADR에 쓴다(§8.6 4번 표 2). 방향이 바뀌는 것은 §5로 묻는다.

1. **합본에 넣을 서비스와 릴레이 자리**: 정본은 '같은 v1 코드의 서비스'만 말한다(docs/verification.md:265). 추천: §2.2의 넷을 한 프로세스에, Outbox·좌석 Stream 릴레이는 같은 이미지의 따로 뜬 릴레이 파드로(차트의 릴레이 배포 꼴, `deploy/README.md` 차트 줄). 릴레이는 세 구성 모두 같은 자리라 비교하는 변수가 아니다. 새 ADR로 적는다.
2. **합본 복제 수와 CPU·메모리**: 정본은 '복제본마다 진입 서버 1대와 같은 CPU 몫'(docs/verification.md:265, 값은 docs/verification.md:203의 [가정])뿐이다. 추천: 고정 복제 3 [가정], HPA 끔(K9는 범위 밖), 메모리는 리허설에서 잰 최대의 두 배 [가정]. K7 ②에서 하나를 끝내도 둘이 남는다. `infra.txt`에 적는다.
3. **서비스별 환경 값이 겹치는 것**: 서비스마다 같은 이름의 환경 값(포트, 파드 이름 등)이 있다. 추천: 서비스별 환경 파일을 합본이 읽어 `start({ env })`로 넘기고 `process.env`는 공통 값만. OTel은 프로세스에 하나이므로 서비스 이름을 합본 하나로 두고 `notes`에 적는다.
4. **리더 임대**: 합본 파드가 여러 Lease를 잡는다(admission-ctrl, purchase-svc 실행기, payment-svc 정지 판정자). 차트의 `service.leaderLease`는 하나만 준다(`deploy/README.md` 차트 줄). 추천: 차트 값을 목록으로 받게 고친다(닿는 CI 잡 kind·image).
5. **게이트웨이 없음**: v1 게이트웨이는 wbs 2.11.1 몫이라 없다. 추천: k6가 합본 Service와 nginx 캐시로 바로 보낸다. 가상 사용자 IP 붙이기는 v0처럼 하되, 입구의 IP 한도 규칙(docs/verification.md:283)은 v1 합본에 걸리지 않는다고 `notes`에 적는다. 구매 경로의 계정·세션 한도에 맞춰 가상 사용자 수를 고르는 것은 리허설에서 확인한다.
6. **K1의 로비·셔플**: v0에는 로비가 없다. 추천: '같은 시나리오'(docs/verification.md:303)를 지키려고 로비 없이 오픈 뒤 진입으로 잰다. 로비·셔플은 다른 측정 몫으로 적는다.
7. **v1 준비 구간의 입장 자리**: K2·K7 ②는 가상 사용자를 준비 구간에 입장시켜야 하는데(docs/verification.md:289), v1은 동시 입장 목표와 입장 속도가 입장을 묶는다. 추천: 시험 회차 하나에만 동시 입장 목표와 입장 속도를 가상 사용자 수 이상으로 두는 시드 설정(운영 값은 그대로), `notes`에 적는다. K1은 정본의 입장 속도(docs/verification.md:319) 그대로다.

## 5. 소유자에게 물을 것(OPEN 후보)

1. **나누기와 WBS 늘림**: PRF-220 앞에 무대 단계 PRF-215(약 4.25~4.5일 [추정])를 새 묶음 BAT-022로 두고, 2.12.5의 합본 빌드 몫을 옮겨 WBS가 약 3~3.5일 늘어나는 것. 규칙상 나누기는 추천 적용으로 할 수 있으나, 범위가 커지는 것을 소유자가 전에 물은 적이 있어 묻는다. 추천 답: 승인. 대안: (나) 역할별 배포(시작 파일을 고치지 않는 같은 이미지·서비스별 파드)로 먼저 재고 합본은 HOT-500에서(정본의 '한 프로세스 합본'을 바꾸는 결정이라 ADR이 든다).
2. **측정 창 동안 갈래 2·3 멈춤**: A/A의 조용한 쌍과 정밀 측정(약 5시간 [추정]) 동안 다른 갈래가 무거운 시험을 돌리지 않게 감독 세션이 시각을 정해 달라는 것.
3. **Docker 메모리**: 15.5GiB가 모자라면 WSL 메모리를 늘릴지(시스템 설정이라 소유자가 직접 바꾼다). 무대 리허설에서 모자람이 보일 때만 묻는다.

## 6. 차례와 담당

### 6.1 BAT-022(무대, B등급, 장부 범위 '-' 추천: 시험 도구라 판정 항목이 없고 판정은 BAT-025)

1. 정본 빈칸 먼저(계획 담당 뒤 구현 담당): §4의 1~10·13을 docs/verification.md §3.8·§3.9·§3.10, 새 ADR, wbs 나눔, BUILD_ORDER(새 줄 PRF-215와 묶음 표 BAT-022, BAT-025 범위 칸)에 쓴다. §8.7 실패 목록 셋은 새 저장소·외부 연동이 아니라 해당 없음을 적는다. 운영 확인 표(§8.4)는 '해당 없음: 운영에 배포하지 않는 시험 도구'(docs/verification.md:299의 꼴). ASVS 문서는 만들지 않되, 합본은 local·ci 밖에서 시작하지 않는다(보안 리뷰 관점).
2. 구현(구현 담당 하나): §2.2 ①→②→③→④→⑤. 지시문에 지시서 7절 '자주 놓친 결함'을 넣고, 특히 '시작 파일 조립은 시험 조립과 따로 띄워 본다'(서비스별 `main.ts`와 합본 둘 다 실제 저장소로 띄우는 시험)와 '시험 값은 코드 상수와 다르게'를 강조한다.
3. 실제 서버 연결: v1 리허설 e2e를 작은 규모로 끝까지(K1·K2·K7 ② 각 한 번, 장부에 넣지 않음).
4. 리뷰 관점 넷(동시에, `git diff`와 지시서·이 계획을 먼저): 정확성(측정 판정·무효 판정·점검 수 세기·발생기 합치기), 동시 실행·장애(합본 종료 차례, 파드 강제 종료, 정리·잠금, 신호 처리), 보안(시험 키는 PC에만, 토큰·키가 산출물·장부에 없음, local·ci 밖 시작 거부, TLS 시험 인증서), 화면과 서버 잇기(화면이 없어 '실행 도구 ↔ 합본 ↔ 저장소 잇기'로 읽는다).
5. 틀린 구현 검사(새 담당, high): 표본 20~30개 [가정](§6.3).
6. 게이트(§6.4) → 기록·커밋.

### 6.2 BAT-025(측정, 이 계획의 범위)

0. 시작: 직전 CI(`gh run list … --workflow ci --limit 3`), `docker ps`에 `bench-*`·다른 갈래 시험 컨테이너가 없는지, 감독 세션에 측정 창 시각 알림.
1. 새 클러스터 → `observability` → `v1`, 보정 확인.
2. A/A 두 쌍(§2.3) → 결과를 ADR-0190 '확인'에 적을 글로 남긴다.
3. Q-T5 `numberbatch` → (§4의 11을 하면) S-T27.
4. K2 인기 좌석 TLS 켬 3·끔 1 → S-T35 ⑥의 Lua 전후 비교.
5. K1 1천·1만(못 지키면 사이 규모).
6. K7 ② 3회(회마다 새 클러스터, 마지막에, docs/verification.md:306).
7. 측정이 끝난 뒤: 규칙 검사(`pr`, 모델 기반 시험), 그 뒤 시험·빌드.
8. 기록(기계적 담당, high): `--record`로 모은 실행, `index.py`, 하루 해시 묶음(`--stamp --no-ots`), verification §3.10 'v1 합본 결과' 문단, ledger-notes 다섯 줄(§1.3), 장부 다시 쓰기, BUILD_ORDER PRF-220 체크, PROGRESS 진행 로그 한 줄. 측정 단계의 커밋에서는 `node tools/ci/records.mjs`를 돌리지 않는다(docs/PROGRESS.md 턴 규칙 '측정이 도는 동안' 둘째 줄).
9. 리뷰: 이 묶음에서 바뀌는 코드가 없으면 기록 글과 장부 값의 대조 한 관점만(성능 장부 원본 ↔ verification 문단 ↔ notes).

### 6.4 게이트와 닿는 CI 잡

- 로컬로 미리: `loadtest-check / loadtest`(loadtest 시험·k6 형식), `tools-check / tools`(tools/ci·perf-ledger·local), `node / node`(바뀐 서비스와 새 패키지의 typecheck·test·build·lint, 바뀐 서비스의 `test:integration`. Kafka 네이티브 6개 파일은 CI만), `image / build`(합본 이미지와 네트워크 없는 스모크를 build-image.yml에 더함), `kind / kind`(`cluster.mjs`·차트를 고치면), `docs-check / docs`(`python -I -X utf8 tools/doc-check/check_all.py`), 계약을 바꾸지 않으면 `contract-check`는 생성물 대조만.
- 대조: `node tools/ci/trace-check.mjs --ids "Q-T2,Q-T5,S-T1,S-T2,S-T35,P-T1" --report <시험 보고서>`, `node tools/ci/ledger.mjs --batch BAT-025 --require`.
- 측정 묶음(BAT-025) 자체는 측정이 끝난 뒤 위 가운데 기록이 닿는 `docs-check`·`tools-check`와 장부 확인만 다시 돈다.

## 7. 가장 큰 위험 셋

1. **무대가 없다**: 측정 전에 약 4일 [추정]의 구현(시작 파일 나누기, 합본, kind v1, v1 시나리오)이 든다. 시작 파일을 나누다 운영 조립이 바뀌면 돈·좌석·순번 경로가 흔들리므로, 서비스별 시작 시험을 먼저 둔다.
2. **PC 자원과 다른 세션**: 메모리 약 15.5GiB에 v1 무대와 발생기 여럿, 다른 갈래 시험 컨테이너가 겹치면 놓친 반복·호스트 포화로 무효가 난다. A/A와 측정 창 조정이 필요하다.
3. **v1 흐름을 k6로 재현하기**: 구매 요청 소지 증명(ECDH·HKDF·HMAC), 입장 토큰, 입장 자리, 결과 롱 폴링을 k6 런타임에서 맞추는 일과, core-svc 없이 좌석 배치·판매 상태를 시드로 넣는 일이 리허설 전에는 확인되지 않는다.
