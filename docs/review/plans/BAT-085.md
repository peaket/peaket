# 묶음 계획: BAT-085(BAS-150 — Kyverno 입장 정책·gitops-check·오버레이 레지스트리)

- **무엇**: 묶음을 시작할 때 만든 작업 목록이다(docs/architecture.md §8.6 4). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다. 값은 되도록 옮겨 적지 않고 자리(문서:줄)를 가리킨다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane4`, 가지 `feature/lane4-BAT-085`, 출발점 `origin/develop` `f6d046087`. 구현 전 트리는 `D:/ticketpass-lane4-base-BAT-085`(`f6d046087`, 분리 HEAD, 커밋 안 함)로 만든다. 2026-11-20 계획 담당 `ses_pending_plan_bat085`(deepseek-v4.1-flash)가 썼고 제품·시험 코드는 쓰지 않았다. 이 PC에서 시험·Docker·kind를 돌리지 않았다.
- **등급·차례**: B(배포 기반·환경, docs/BUILD_ORDER.md:70). 짧은 고리(ADR-0283 결정 2)를 쓴다: 계획 → 구현 → 시험(구현 전 트리에서 실패 확인을 같은 커밋에) → 리뷰 → 리뷰 반영 시험(재현 시험과 실패 확인을 한 커밋) → 리뷰 반영 구현(고침과 시험 결과를 한 커밋) → 검증 → 기록. `Batch-Order: impl-first`로 시작한다.
- **이 계획의 몫**: BAT-085는 **BAS-150의 Kyverno CEL 정책·`gitops-check`·오버레이 레지스트리·노드 배치 값**만 한다. **BAS-160(데모 재현 스크립트)은 새 묶음 BAT-086으로 뗀다.** BAS-150의 사람 접근(Identity Center·비상 접근·SSM 중계, Terraform)은 BAT-081로 넘긴다. 까닭은 아래 '감독에게' 1·2다. 묶음 표(docs/BUILD_ORDER.md:70)는 이 커밋에서 계획 경로·범위만 적고, 단계 나누기는 감독이 정한다.

## 감독에게

정하지 않고 올리는 것과, 이 계획이 정한 것을 알린다.

1. **BAS-160을 BAT-085에서 뺀다(새 묶음 BAT-086)**: BAS-160은 로컬 kind 전체 기동·합성 데이터·시연 S1~S9 재생·임시 클라우드 데모 절차·운영 판 호환 검사 시연이다(docs/BUILD_ORDER.md:419, wbs 0.4.3, docs/design/d5-screen-blueprint.md:4430~4444). 지금 저장소에는 앱 서버 이미지가 없고(`apps/*/Dockerfile` 없음), 서비스 이미지도 다섯만 만든다(`ci.yml` 이미지 행: v0-monolith·pg-simulator·ops-svc·example-svc·bundle). `deploy/envs/`에는 `local`만 있고 `demo`·`staging`·`prod` 값이 없으며, S1~S9가 지나는 웹·파트너·관제·스캐너·티켓·결제 흐름의 합성 시드도 없다. 1.25일로는 앱·서비스 이미지와 데모 오버레이·시드를 함께 만들 수 없다. **안**: BAT-085는 BAS-150만 하고, BAS-160은 서비스·앱 이미지와 `deploy/envs/demo`가 생긴 뒤의 새 묶음 **BAT-086**으로 뗀다. BAT-086에서 ① 데모 오버레이+합성 시드, ② S1~S9 재생 스크립트, ③ 임시 클라우드 데모 절차(TTL·예산 경보, 소유자 몫), ④ `contract-check` 차단 시연을 다시 나눈다. `docs/lanes/lane4.md:12`의 차례도 BAT-086을 BAT-085 뒤에 두게 고친다.
2. **BAS-150의 사람 접근은 BAT-081로 넘긴다**: Identity Center·비상 접근 계정·교차 계정 역할·SSM 포트 포워딩 중계는 Terraform이다(docs/infra.md:556, docs/devops.md:292~298, wbs 0.4.4). 지금 `infra/`에는 `stacks/global/github`만 있고 AWS 스택이 없으며 `iac-check.yml`은 `terraform fmt`·`validate`만 돈다. BAT-076(BAS-120 스테이징 Terraform)이 새 도구·`terraform providers lock` 결정으로 막혀 있어(docs/lanes/lane4.md:12), 사람 접근 코드를 지금 넣어도 검증할 스택이 없다. **안**: 사람 접근은 BAT-081(BAS-130 뒤)이나 BAT-076 뒤의 새 묶음으로 넘기고, BAT-085는 Kyverno·gitops-check·레지스트리·노드 배치 값만 한다. 노드 풀 가운데 **배포 값**(핫패스 온디맨드 `nodeSelector`, 관제 풀 toleration·우선순위)은 Terraform이 아니라 지금 할 수 있으므로 BAT-085에 남긴다. Terraform NodePool/NodeGroup 자체는 BAT-076·BAT-081 몫이다.
3. **장부 범위를 좁힌다(BAT-075·BAT-080과 같은 방식)**: 지금 BAT-085 줄의 범위 `D-T28, D-T32, D-T33, docs/devops.md, docs/security/asvs/delivery.md`를 그대로 읽으면 항목 195개(자동 시험 108, ID만 28, 측정 1, 미검증 1, 다른 단계 2, 해당 없음 3, 빈칸 52)다. 대부분 다른 단계 몫이다. 이 묶음이 채우는 것만 남기는 안:
   ```text
   D-T11, D-T18 ②, D-T28, D-T32 ②, D-T32 ③, D-T33 ①, D-T33 ②, D-T33 ③, delivery:v5.0.0-13.2.5
   ```
   이 범위는 항목 9개이고, 지금 상태는 `자동 시험 0, ID만 3(D-T32 ②③·delivery 13.2.5), 다른 단계 1(D-T18 ②, BAS-150), 빈칸 5`이다. **D-T11**은 서명·출처 없는 이미지 거부이고, **D-T18 ②**는 `--disable-sigusr1` 없는 Node 파드 거부인데, 둘 다 BAT-075 계획이 BAS-150으로 넘겼고(docs/review/plans/BAT-075.md:236) 장부도 BAS-150을 가리킨다. **D-T32 ①**은 이미 자동 시험이라 빼고 ②③만 남긴다. **delivery 13.2.5**는 오버레이별 허용 레지스트리의 ASVS 행이라 이 묶음의 정책 시험이 구현 위치가 된다. `D-T33 ③`은 아래 6처럼 측정으로 남는다. 감독이 줄의 세 ID만 원하면 `D-T11·D-T18 ②·delivery 13.2.5`를 빼고 `D-T28, D-T32 ②, D-T32 ③, D-T33 ①~③`(6항목)로 두며, 뺀 셋은 ledger-notes에 '다음 묶음'으로 적는다.
4. **새 도구(Kyverno) 승인**: 이 묶음은 Kyverno v1.20.0 [가정, 구현 때 게시 3일이 지난 판인지 확인]을 쓴다. 정책 CRD(`policies.kyverno.io/v1`의 `ImageValidatingPolicy`·`ValidatingPolicy`)와 kind 입장 시험에 Kyverno 공식 Helm 차트와 이미지(다이제스트 고정)가 필요하다. 새 외부 도구를 받는 일이라 소유자 결정 범위다(OPEN[31]의 gitleaks·Trivy 때와 같은 자리, ADR-0263). **안**: Kyverno v1.20.0 + 공식 차트(판·이미지 다이제스트 고정), kind에만 설치. `kubeconform`(스키마 검사)·ArgoCD 차이 미리보기·동결 게이트는 이 묶음에서 받지 않고 뒤로 미룬다. Kyverno CLI는 받지 않는다(정적 시험은 YAML 읽기, 행동 시험은 kind의 실제 admission).
5. **ADR 번호**: 이 계획이 정하는 것 가운데 둘은 결정에 가깝다. ① Kyverno CEL 입장 정책의 모양·모드(데모 감사, 스테이징·운영 거부)·오프라인 검증 PoC와 실패 시 폴백(승격 단계 검증 + 승격 다이제스트 허용 목록, ADR-0054 결정 4) ② `gitops-check`의 몫(정책·레지스트리·서명/출처 검증)과 출시 후보 캐시 금지 규칙. **안**: 0318(① 'Kyverno 입장 정책과 오프라인 검증'), 0319(② '`gitops-check`의 몫과 공급망 검증'). 번호를 주면 구현 담당이 ADR을 쓰고 정본 문구에 '추천 적용 2026-11-20, BAT-085 계획'으로 번호를 붙인다.
6. **D-T33 ③(GHCR 익명 끌어오기)**: ③은 "로컬 kind가 끌어오기 비밀 없이 GHCR 다이제스트를 받는다"인데, 우리 GHCR 패키지가 공개 패키지인지 이 PC에서 확인하지 못했다(조직 패키지 목록은 GitHub 인증이 필요하다). 첫 푸시는 GitHub 조직에서 **비공개 패키지가 기본**이라 소유자가 패키지 공개 설정을 바꿔야 익명 끌어오기가 된다. **안**: 이 묶음은 ③을 ①정적 시험(로컬·데모 매니페스트에 `imagePullSecrets` 없음, 다이제스트 참조) ②kind 측정(공개 GHCR 이미지의 다이제스트를 비밀 없이 받기, 예: Kyverno 이미지)으로 남기고, 우리 이미지의 실제 익명 끌어오기는 첫 출시 후보 게시 뒤로 미룬다. 결과는 `docs/review/measurements/` 폴더의 새 파일 `BAT-085-ghcr.md`에 적고, 장부에는 측정으로 둔다. 소유자가 패키지 공개를 먼저 해 줄 수 있으면 첫 출시 뒤 한 번 더 잰다. 이 항목을 지금 닫으려면 출시 후보 이미지와 패키지 공개 설정이 먼저 필요하다.
7. **오프라인 검증 PoC의 범위**: 정본은 "서명 묶음(번들)의 투명성 로그 증명으로 오프라인 확인" **또는** "검증 결과 캐시"를 PoC로 확인하고, 실패하면 승격 단계 검증+승격 다이제스트 허용 목록으로 바꾼다고 한다(docs/devops.md:298, ADR-0054 결정 4). **안**: 0.5일 [가정] 안에 kind에서 ① 같은 다이제스트를 한 번 온라인으로 통과시킨 뒤 Kyverno egress를 막고 다시 띄워 캐시로 통과하는지, ② 새 다이제스트를 오프라인 번들로 통과시키는지(키 기반 시험 서명)를 잰다. ①이 통과하면 온세일 확장(K9) 위험은 줄고, ②까지 통과해야 "오프라인 번들 검증"이라 부를 수 있다. 둘 다 실패하면 위 폴백을 쓴다. 키 없는(keyless) 서명의 오프라인 번들은 첫 출시 이미지가 생긴 뒤 G-20에서 한 번 더 잰다(이 묶음의 한계로 기록).

### 5. 공개 인터페이스(시험이 기댄다. 이름을 바꾸면 '시험 이의'에 적는다)

- **정책 이름**: `peaket-image-admission`(ImageValidatingPolicy), `peaket-registry-allowlist`·`peaket-pod-baseline`·`peaket-hotpath-placement`(ValidatingPolicy). 모두 클러스터 범위이고 `deploy/policies/kyverno/envs/<환경>/policies.yaml`에 생성된다.
- **정책 값 파일**:
  ```yaml
  environments:
    demo:   { mode: Audit, failurePolicy: Ignore, registries: ["ghcr.io/peaket/"] }
    staging:{ mode: Deny,  failurePolicy: Fail,   registries: ["<ECR_ACCOUNT>.dkr.ecr.ap-northeast-2.amazonaws.com/"] }
    prod:   { mode: Deny,  failurePolicy: Fail,   registries: ["<ECR_ACCOUNT>.dkr.ecr.ap-northeast-2.amazonaws.com/"] }
  demoImages: ["pg-simulator", "identity-simulator", "demo-helper", "bundle", "example-svc"]
  hotPathWorkloads: ["queue-svc", "admission-ctrl", "purchase-svc", "realtime-gw", "web"]
  systemNamespaces: ["kube-system", "kyverno", "kube-node-lease", "kube-public"]
  ```
- **생성기 CLI**: `node tools/ci/kyverno-policies.mjs --write|--check [--root <저장소>]`. 끝 코드 0 같음(또는 씀), 1 다름·값 오류, 2 인자 오류.
- **`gitops-check` CLI**: `node tools/ci/gitops-check.mjs --check [--root <저장소>] [--env <환경>] [--image <이름>=<repo>@<digest>]`. 출력은 검사별 `ok`/`skip(까닭)`/`fail(까닭)` 한 줄과 마지막 요약. 끝 코드 0/1/2.
- **공급망 CLI**: `node tools/ci/supply-chain-verify.mjs --image <repo> --digest <sha256:…> [--attestation <파일>] [--json]`. `--attestation`은 시험용 고정물을 읽고, 없으면 cosign을 부른다.
- **차트 값**: `service.nodeSelector`(map, 기본 `{}`), `service.tolerations`(list, 기본 `[]`). 빈 값이면 지금 렌더와 같다.
- **환경 값 계약**: `deploy/envs/<환경>/<서비스>.yaml`은 `name`·`image.digest`·`env.PEAKET_ENV`·`diagnose.bucket`을 갖는다(승격 CLI가 만든다). `gitops-check`는 이 파일의 `image.digest`만 서명 검증 입력으로 쓴다.
- 제품 API·계약·DB 변경은 없다.

### 7. 구현 전 트리에서 실패를 볼 수 없는 시험과 그 까닭

- **파일이 없어 실행조차 안 되는 것**: KV-01·04~07, GV-01·03~07. §8.6 7로 세지 않는다. 시험 담당은 구현 커밋에서 통과를 보고, 9의 틀린 구현을 손으로 하나 이상 넣어 실패를 '실패 확인'에 적는다.
- **동작 고정이라 기준 트리에서 통과하는 것**: GV-02의 '캐시가 없으니 통과', GV-08. GV-02는 시험을 먼저 넣고 M8·M9를 넣어 실패를 본다.
- **kind가 필요한 것**: D-T11 ②, D-T18 ②, D-T33 ①·②(kind 부분), GH-01. 이 PC에서 돌리지 않는다. 첫 실행은 초안 PR CI의 kind 잡이나 Docker 잠금 안의 로컬 kind에서 하고, 결과를 '실패 확인'·'시험 결과'에 적는다.
- **측정**: D-T33 ③·오프라인 PoC는 시험이 아니라 측정이다. 측정 파일에 시각·판·결과·한계를 적고, 장부에는 자동 시험으로 세지 않는다.
- **실제 이미지**: `deploy/envs/staging|prod` 값이 없어 실제 ECR·GHCR 이미지 서명 검증은 이 묶음에서 돌지 않는다. 고정물·픽스처로 판정 함수를 시험하고, 첫 승격 PR에서 실제 다이제스트로 한 번 더 본다.

### 11. 자주 놓친 결함

- **초기·임시 컨테이너**: `images.containers`만 보면 `initContainers`·`ephemeralContainers`의 이미지·보안 설정을 놓친다. 정책과 시험이 셋 다 본다(M13).
- **`NODE_OPTIONS` 자리**: 공용 차트는 `--disable-sigusr1`을 `command`가 아니라 `NODE_OPTIONS`에 넣는다. `command`만 보는 정책은 정상 파드를 거부하거나, 반대로 플래그 없는 파드를 통과시킨다(M12).
- **fail-open**: 운영 정책의 `Audit`·`failurePolicy: Ignore`는 조용히 통과시킨다. 정책 파일·값·kind 시험 셋에서 모드를 본다(M1·M2).
- **네임스페이스 제외**: `kube-*`·`*-system` 같은 넓은 제외는 서비스 네임스페이스를 피해 갈 수 있다. 시스템 네임스페이스는 이름 목록으로 고정하고, 서비스 네임스페이스가 실제로 검사되는지 kind에서 본다.
- **레지스트리 접두사**: `ghcr.io/peaket`(슬래시 없음)는 `ghcr.io/peaket-evil`을 받는다. ECR `*.dkr.ecr…`는 다른 계정을 받는다. 글롭 경계값을 시험한다(M3·M4).
- **태그 vs 다이제스트**: `validationConfigurations.verifyDigest`·`required`가 없으면 태그 이미지가 통과한다. 값 파일·정책·승격 PR 셋에서 본다(M5).
- **cosign 정규식 앵커**: `--certificate-identity-regexp`를 앵커하지 않으면 `...build-image.yml.evil@...`이 통과한다. `^...$`를 쓰고 고정물로 시험한다.
- **캐시의 다른 얼굴**: `actions/cache`·`cache-from`·`cache-to`·`--mount=type=cache`는 모두 캐시 복원이다. `--no-cache`는 OCI 빌드뿐 아니라 스모크 다시 빌드에도 붙여야 한다(M8·M9).
- **조용한 skip**: 승격 PR에 digest가 없는데 '파일 없음'으로 성공하면 서명 검증이 한 번도 돌지 않는다. '까닭을 남긴 skip'과 '검증 실패'를 가른다(M10).
- **GHCR 기본 비공개**: 첫 푸시는 비공개 패키지다. 익명 끌어오기는 소유자가 공개로 바꾼 뒤에만 된다. 정책·측정에서 이 한계를 적는다.
- **서드파티 이미지**: `data`·`observability`·`otel`·애드온 네임스페이스에는 ClickHouse·Prometheus·Kyverno 같은 서드파티 이미지가 있어 우리 서명 정책을 걸 수 없다. 이 묶음은 우리 서비스 네임스페이스만 본다. 우리 스트림 작업자(`analytics-ingest`·`ops-rt`)의 이미지 정책은 남은 몫으로 적는다.
- **`PEAKET_ENV`를 Secret으로**: env에 직접 두지 않고 `envFrom` Secret으로 넣으면 정책이 값을 못 본다. 정책은 `PEAKET_ENV`가 env에 직접 있고 값이 맞는지 보고, 없으면 거부한다.

## 시험 이의

- **`actions/cache` 하위 경로 구멍(2026-11-20, 시험 담당)**: `check-workflows.mjs`의 빌드 잡 캐시 금지 규칙은 `uses: actions/cache@…`만 보고 `actions/cache/restore@…`·`actions/cache/save@…` 하위 경로는 잡지 못한다. 같은 액션의 캐시 복원·저장이라 D-T32 ②의 취지에 걸린다. 시험은 이 구멍을 `skip` 시험 하나로 표시해 두고(실패로 세지 않음), 제품 코드는 시험 담당이 고치지 않았다. 리뷰 반영 때 `actions\/cache(\/|@)` 꼴로 넓히고 skip을 실제 단언으로 바꾼다.
- **kind e2e의 무대(2026-11-20, 시험 담당)**: `tools/local/e2e/kyverno.e2e.mjs`는 (a) `registry:2.8.3` 컨테이너를 kind 도커 네트워크에 붙이고 `default` 네임스페이스의 `peaket-registry` Service·Endpoints로 클러스터 안 이름을 만든다. (b) `busybox:1.36`을 밀고 `ghcr.io/sigstore/cosign/cosign:v2.4.1` 컨테이너(`--network host`)로 테스트 키 서명을 한다. (c) 정책은 생성 파일의 사본에 `-e2e` 이름과 Deny/Fail만 바꿔 임시로 걸고 지운다. `--network host`는 Linux CI를 전제한다(Windows Docker Desktop에서는 이 시험을 돌리지 않는다). 로컬 레지스트리는 HTTP라 이미지 정책에 `credentials.allowInsecureRegistry: true`를 주고, 파드가 실제로 이미지를 받는지는 보지 않는다(입장 여부만 본다).
- **오프라인 PoC는 시험이 아니라 측정**: `kyverno.e2e.mjs`의 마지막 시험은 같은 다이제스트(온라인 선통과 뒤 egress 차단)와 새 다이제스트(오프라인 번들 없음)의 입장 결과를 `docs/review/measurements/BAT-085-offline-verify.md`에 적기만 하고 통과/실패를 단언하지 않는다(계획 §7). 새 다이제스트는 레지스트리 접근이 막히면 거부되는 것이 정상이며, 오프라인 번들은 이 묶음에서 만들지 않았다.
- **D-T33 ③(GH-01)**: 익명 GHCR 끌어오기 측정은 이번 e2e에 넣지 않았다. `docs/review/measurements/BAT-085-ghcr.md`의 계획대로 첫 출시 뒤/검증 담당이 잰다. 정적 시험은 데모 정책의 `imagePullSecrets` 금지와 GHCR 접두사만 본다.
- **`gitops-check --env local`**: `deploy/envs/local`은 로컬 kind용 태그(`peaket/bundle:local`)를 쓰고 승격 값이 아니라서 `--check --env local`은 D-T33·digest에서 실패한다. 기본(prod)과 staging·demo만 검사 대상으로 두었고, 이 동작을 시험으로 고정하지 않았다.


### 구현 메모(impl, 2026-11-20, deepseek-v4.1-flash)

- **ECR 계정 표기**: 원천은 `<ECR_ACCOUNT>` 대신 `0000-0000-0000` [가정]과 `{ecr}` 자리 표시를 쓴다. 생성기는 4-4-4를 12자리로 바꾸고 `{ecr}`를 채우며, 꺾쇠(`<…>`) 자리 표시는 그대로 거부한다. 까닭: 문서 점검(`tools/doc-check`)이 12자리 숫자를 AWS 계정 번호로 보고 공개 문서에서 막는다. 시험 KV-04의 `<ECR_ACCOUNT>` 거부 단언은 그대로 성립한다.
- **Helm 없는 로컬**: `gitops-check`는 환경 값이 있으면 Helm으로 렌더하고, Helm이 없으면 배포 단위 값과 환경 값을 합친 가벼운 Deployment로 검사하며 `skip render(Helm): …`을 남긴다. CI(`gitops-check.yml`)는 Helm을 고정 판으로 받으므로 렌더한다.
- **`changes.test.mjs`**: `deploy/` 규칙에 `gitops` 범위가 더해져 기존 정확 배열 단언이 실패한다. 시험 담당이 `gitops`를 배열에 더하고 `deploy/policies/`의 `kind`·새 도구의 `gitops` 단언을 더한다(시험 파일은 구현 담당이 고치지 않았다).
- **새 시험 파일 이름**: `deploy/policies/test/kyverno-policies.test.mjs`, `tools/ci/gitops-check.test.mjs`, `tools/ci/supply-chain-verify.test.mjs`, `tools/ci/kyverno-policies.test.mjs`, `tools/local/e2e/kyverno.e2e.mjs`(kind). `ci-kind.yml`·`gitops-check.yml`·`tools-check.yml`은 파일이 있으면 돌리는 훅을 두었다.
- **워크플로 분리 커밋**: branch-policy(ADR-0169)가 `.github/workflows/` 변경과 다른 경로가 섞인 PR을 막으므로, 워크플로 넷을 develop-선행 분리 커밋(`feat(ci): BAT-085 GitOps·Kyverno 검사 워크플로`)으로 뗐다. 그 커밋만 먼저 develop에 넣은 뒤 나머지를 rebase해 합친다. 분리 커밋이 단독으로 CI를 깨지 않게, 참조 스크립트·정책이 아직 없으면 건너뛰는 가드를 두었다.
