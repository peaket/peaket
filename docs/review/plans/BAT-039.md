# BAT-039 계획 — UNKNOWN 조회 꼬리 단축

- 작성: 2026-11-13
- 묶음: BAT-039(HOT-473, 갈래 1, 구간 1, **A등급**, 0.5~1일 [가정])
- 장부 범위: `P-T1`, `P-T23`
- 선행: BAT-038(HOT-472, R-509). K7 r1에서 접수 429 0.75% <1%를 통과했지만 `payment_confirm_ms{phase:main}` p99 3,609.8ms로 목표 <3초에 미달했다.

## 1. 느린 결제 1% 분해

### 원장 결제 시각

`records.ndjson`의 `pg_charge` 10,153건에서 주문 ID(UUIDv7) 시각 → 결제 승인 시각의 차이:

| 백분위 | 값 |
| --- | ---: |
| p50 | 1,425ms |
| p90 | 2,438ms |
| p95 | 2,753ms |
| **p99** | **3,976ms** |
| p99.5 | 10,800ms |
| p99.9 | 17,912ms |
| max | 18,664ms |

| 구간 | 건수 | 비율 |
| --- | ---: | ---: |
| 10~20초 | 53 | **0.52%** |
| 3~5초 | 248 | 2.44% |
| 5~10초 | 19 | 0.19% |
| 3초 이상 합계 | 320 | 3.15% |

- **16초 지연 0.5%**는 10~20초 구간 53건(0.52%)으로 확인된다. 이들은 p99.5~p100에 있고, **p99 경계(3.976초)보다 위**다.
- p99 3.976초는 10~20초 지연군이 아니라 **나머지 99.48%의 느린 꼬리**(3~5초 구간)가 만든다.
- 느린 1%(102건) = 16초 지연 53건 + 정상/드롭 49건. 정확한 드롭/정상 분리는 K7 산출물에 없다(시뮬레이터 장애 로그를 모으지 않았다). `sim_fault` 516건(5.55%) 중 드롭 5%(~463)·지연 0.5%(53)이므로, p99 경계의 49건은 **드롭 쪽이 유력**하지만 단정하지 않는다.

### 상태 대기

| 지표 | p50 | p99 |
| --- | ---: | ---: |
| `payment.status.wait` | 1.319s | **3.825s** |
| `payment.status.read` | 21.9ms | **240.3ms** |
| `payment.status.poll` | 13.2ms | 71.3ms |
| `saga.total` | 266.9ms | 797.6ms |
| `payment.result.total` | 217.2ms | 490.0ms |
| `hold.total` | 3.0ms | 18.3ms |

- 느린 `payment-status` 200의 상위 표본: 17.6~19.2초 3건(지연군), 4.9초·4.07초·3.47초·3.27초·3.01초, 그 아래는 매끄러운 2.9초 꼬리다.
- `payment.status.wait` p99 3.825s가 `payment_confirm_ms` p99 3.61s의 대부분이다. wait table 깨우기(`poll` p99 71ms)와 `read` 핫풀 대기(240ms)는 작은 몫이다.
- 번들 CPU 0.98코어, 이벤트 루프 지연 p99 12.6ms·max 29.9ms로 CPU/event loop 병목이 아니다.
- 드롭 5%는 UNKNOWN으로 남고, UNKNOWN 조회의 기존 간격은 250ms에서 두 배씩(250+500+1,000+2,000=3.75초)이다. p99 3.6초 꼬리와 맞는다. 드롭군이 p99 경계를 만드는 유력한 원인이다.

### 0.5% 16초 지연의 구조적 영향

- 16초 지연은 0.52%라 **p99(상위 1%) 경계를 직접 만들지 않는다.** p99.5 이상을 10~19초로 끌어올린다.
- 따라서 `payment_confirm_ms` p99 <3초 목표는 0.5% 지연 때문에 구조적으로 불가능하지 않다. 나머지 99.48%의 느린 꼬리를 줄이면 된다.
- 다만 공식 `payment_p99_3000ms` **≤1%** 점검은 0.5% 지연군만으로 0.5%가 초과로 잡혀, 다른 느린·비끝 답에 0.5% 여유밖에 없다. 공식 점검을 목표로 삼으면 목표·장애 주입 조정이 필요할 수 있다. 이 배치의 목표는 `payment_confirm_ms` p99 <3초로 둔다.

## 2. 고른 수정 — (가) UNKNOWN 조회 백오프·주기 단축

- `UNKNOWN_QUERY_BASE_MS` 250 → **100ms**.
- `UNKNOWN_QUERY_POLL_INTERVAL_MS` 250 → **100ms**.
- `DELAY_EXPONENT_CAP` 8 → **10**: 기준이 100ms로 작아져도 상한 60초에 닿게 한다.
- 입금 통보 경로의 5초 기준·2배는 그대로 둔다(`DEPOSIT_NOTIFIED_RETRY_BASE_MS`·`UNKNOWN_QUERY_FACTOR`).
- 드롭 5%가 UNKNOWN이 된 뒤 첫 조회와 재조회가 빨라져, 3.75초까지 쌓이던 꼬리를 줄인다. 16초 지연군은 여전히 p99.5에 남는다.

### 왜 (나)·(다)·(라)가 아닌가

- (나) 종결 알림·wait table wake 간격: `payment.status.poll` p99 71ms로 작다. 깨우기가 늦어서 3.6초가 된 것이 아니다.
- (다) `payment-status` 전용 읽기 풀: `payment.status.read` p99 240ms로, 3.6초의 작은 몫이다.
- (라) 정상 쓰기 경로/핫풀: `saga.total` p99 798ms·`payment.result` 490ms로 1초 안이다. p99 경계의 주원인은 UNKNOWN 조회 꼬리로 본다. K7에서 p99가 남으면 정상 쓰기 경로·전용 풀을 다음 후보로 본다.
