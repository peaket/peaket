# BAT-173 계획(파트너 API 테넌트당 600회/분: 서비스 층 공용 Redis 카운터)

- **무엇**: 파트너 API를 받는 서비스가 테넌트마다 1분에 600회까지만 받고 601번째부터 429를 내는 공용 가드를 만든다. 게이트웨이의 계정당 600회/분(BAT-060)은 첫 겹으로 그대로 두고, 토큰에 테넌트가 없어(ADR-0172) 게이트웨이가 셀 수 없는 **테넌트 합계**를 서비스 층에서 센다. 범위는 BUILD_ORDER 95행·441행의 HOT-173(wbs 2.9.5 ⑥)이다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane2`, 가지 `feature/lane2-BAT-173`, 기준 `509d3e860`(develop). 지시서 `node tools/ci/brief.mjs --batch BAT-173`(만든 때 `509d3e86`). 계획 담당 `ses_pending_plan_bat173`(deepseek-v4.1-flash), 2026-11-20. 제품·시험 코드는 쓰지 않았고 Docker·부하·측정도 돌리지 않았다. 정본 빈칸은 이 커밋에서 `docs/api/guidelines.md` §6, `docs/data.md` §3·§5, `docs/architecture.md` §4, `docs/verification.md` §4.1, `docs/observability.md` §3에 썼다.
- **등급·차례**: B(docs/BUILD_ORDER.md:95). 장부 범위는 `D-T50 ⑦` 하나이고 지금은 '다른 단계(HOT-173)'다. 정방향(`Batch-Order: impl-first`, ADR-0281)이고 B 묶음 짧은 고리다(ADR-0283 결정 2): 계획 → 구현 → 시험(구현 전 트리 실패 확인을 같은 시험 커밋에) → 리뷰 → 리뷰 반영 시험(재현 시험·실패 확인 한 커밋) → 리뷰 반영 구현(고침·시험 결과 한 커밋) → 검증 → 기록.
- **한 줄 결론**: 요청 문구의 "좌석맵 600회/s"는 BUILD_ORDER와 다르다. 실제 요구는 **파트너 API 테넌트당 600회/분(초당 10회)**이고, 좌석맵·CDN·부하 시험과 무관하다. 병목은 처리량이 아니라 "토큰에 테넌트가 없어 게이트웨이가 테넌트로 셀 수 없다"는 구조다. 서비스 층 공용 가드가 세션·캐시 Redis의 `rl:tenant:{tenantId}`를 Lua 한 번으로 세고, 601번째에 429 `about:blank`·`Retry-After`를 내며, Redis 판정 실패는 열림으로 둔다.

- **왜 초당 600이 아닌가**: `docs/api/guidelines.md` §6의 값은 "테넌트당 600회/분"이고, BUILD_ORDER 441행도 "1분에 601번째 429"다. 초당 600회로 읽으면 1분에 36,000회가 되어 정본과 60배 다르다.
- **왜 게이트웨이에서 못 세나**: ADR-0172가 역할·테넌트를 토큰에 싣지 않기로 했다. 게이트웨이는 `aud`·`scope`·계정만 알고, 테넌트는 서비스가 identity `GetAdminAuthz`로 요청마다(5초 캐시) 받는다. 그래서 테넌트 합계는 서비스 층에서만 셀 수 있다.

## 4. 감독에게

1. **범위 바로잡기**: 요청 문구의 "좌석맵 600회/s 공용 가드"는 BUILD_ORDER 95·441행과 lane2 노트의 "파트너 테넌트당 600회/분 공용 가드"와 다르다. 이 계획은 정본 문장을 따른다. 좌석맵 600회/s를 실제로 재는 일이 필요하면 그것은 다른 묶음이고, 이 묶음에서 좌석맵·CDN·`loadtest/scenarios`를 건드리지 않는다.
2. **시험 층**: D-T50 ⑦은 정본에 "로컬 kind에서"라고 적혀 있지만, 로컬 `cluster.mjs gateways` 무대에는 대역 백엔드(`gateway-echo`)만 있고 실제 파트너 서비스가 서지 않는다. 이 계획은 **플랫폼 통합 시험**(실제 Valkey 8.1, 서비스 두 인스턴스, 계정 둘)으로 판정하는 안을 제안한다. kind에서 실제 서비스까지 세우려면 무대를 더 만드는 일이 붙어 1일을 넘는다. 감독이 kind를 고집하면 그 몫을 더해 일정을 다시 잡는다.
3. **배선 범위**: 파트너 역할 처리기가 있는 서비스는 core-svc·payment-svc·ticket-svc·ops-svc·identity-svc 다섯이다. 한 서비스라도 빠지면 그 경로가 테넌트 한도를 빠져나간다. 다섯을 모두 배선하고, 서비스마다 배선 시험을 둔다. 1일이 빠듯하면 core·payment·ticket부터 하되, 끝을 "다섯 모두"로 잡는다.
4. **고정 창의 경계**: 첫 요청에 60초 수명을 거는 고정 창이라, 창 경계에서 짧은 시간에 최대 2배(1,200회)가 지나갈 수 있다. 게이트웨이의 분 창과 같은 성질이고, 600회/분 요구를 넘는 것은 아니다. 정확한 매끄러움이 필요하면 토큰 버킷으로 바꾸는 결정이 필요하다(이 계획은 하지 않는다).
5. **429 본문**: 게이트웨이의 429는 `type`·`title`·`status`만 싣는다. 서비스의 Problem은 표준대로 `instance`·`traceId`를 더 싣는다. "같은 모양"을 세 칸으로 보고 `instance`·`traceId`는 서비스 표준으로 둔다. 감독이 게이트웨이와 완전히 같기를 원하면 `instance`·`traceId`를 빼는 예외를 정해야 한다.
6. **운영 시작 규칙**: `local`·`ci`는 세션·캐시 Redis가 없어도 뜨게 두고(시험·개발), 그 밖의 환경에서 파트너 역할 처리기가 있는데 테넌트 한도 가드가 없으면 시작을 막는 안을 제안한다. 이렇게 하지 않으면 배포에서 조용히 한도가 꺼진다.
7. **WBS 1일**: 다섯 서비스 배선·플랫폼 통합 시험·정본·게이트를 합치면 1일은 빠듯하다. 1.25일 [가정]을 제안한다. 감독이 1일을 고정하면 시험 표본을 12개에서 8개로 줄이고, kind e2e는 넣지 않는다.
8. **ADR**: 새 ADR을 쓰지 않았다. 소유자 결정 OPEN[41]과 BUILD_ORDER가 방향을 정했고, 키·창·열림은 정본에 '(추천 적용)'으로 썼다. 별도 ADR을 원하면 번호를 주면 옮긴다.
9. **배포 Redis 주소**: ops-svc·payment-svc의 `PEAKET_REAUTH_REDIS_URL`이 세션·캐시 클러스터가 아니라 재인증 전용 Redis라면, 그 두 서비스의 테넌트 키가 core·ticket·identity와 쪼개진다. 배포 값이 같은 클러스터를 가리키는지 먼저 확인한다. 다르면 `PEAKET_TENANT_REDIS_URL` 같은 새 값을 정해야 하는데, 이 묶음은 새 값을 만들지 않는 안(기존 세션·캐시 주소 재사용)을 먼저 본다. 확인 결과를 계획 파일에 적는다.

## 5. 범위

### 5.1 하는 것

1. **공용 테넌트 한도 모듈**(`packages/platform/src/tenant-rate-limit.ts` 새 파일): `TenantRateLimitPort`(테넌트 ID 하나로 `{allowed, retryAfterSeconds}`를 답한다), `redisTenantRateLimiter`(세션·캐시 `HotRedis`를 받아 Lua 한 번으로 `INCR`+첫 증가 `PEXPIRE` 60초+`PTTL`), 키 만드는 함수(`rl:tenant:{tenantId}`), 상수(600회/분·60초 창·20ms [가정]).
2. **가드 배선**(`packages/platform/src/auth.ts`): `AuthGuard.canActivate`에서 `judgeIdentity`가 끝난 뒤, `principal.aud === 'partner'`이고 `principal.tenantId`가 있으면 한도 판정을 부른다. `allowed=false`면 `Retry-After`와 `Cache-Control: no-store`를 응답에 달고 `about:blank` 429를 낸다. `judgeIdentity` 안에는 넣지 않는다(칸막이 경로의 `admitBeforeBody`가 같은 함수를 불러 두 번 세는 것을 막는다).
3. **판정 실패는 열림**: Redis 마감 초과·연결 오류·스크립트 오류면 세지 않고 통과하고 `tenant_rate_limit_total{result="unavailable"}`를 올린다. 5xx로 바꾸지 않는다.
4. **서비스 조립**(`packages/platform/src/service.ts`): `CreateServiceOptions.tenantRateLimit?: { redis: HotRedis; limit?: number; windowMs?: number; timeoutMs?: number }`를 더하고, `createService`가 `PlatformMetrics.tenantRateLimit`를 `onResult`로 묶은 `TenantRateLimitPort`를 만들어 `AuthState`에 넘긴다. `local`·`ci` 밖에서 파트너 역할 처리기가 있는데 이 값이 없으면 시작을 막는다.
5. **다섯 서비스 배선**: core-svc(`shopRedis`)·payment-svc(`reauthRedis`)·ticket-svc(`redis`)·ops-svc(`reauthRedis`)·identity-svc(`cache`)가 이미 만드는 연결을 쓴다. 다만 ops·payment의 `PEAKET_REAUTH_REDIS_URL`이 세션·캐시 클러스터가 아니면 키가 쪼개지므로, 배포 값이 같은 클러스터인지 먼저 확인한다(감독에게 9·정할 것 9). 같은 클러스터면 새 환경 값·새 Redis 연결을 만들지 않는다.
6. **지표**(`packages/platform/src/metrics.ts`): `tenant_rate_limit_total{service,result}`를 `PlatformMetrics`에 더한다. 테넌트 ID·계정 ID는 라벨에 싣지 않는다.
7. **정본·기록**: 위 '정본 빈칸' 표의 문서, BUILD_ORDER 95행, 이 계획 파일.
8. **시험**: 아래 10. 플랫폼 통합(실제 Valkey), 서비스별 배선 시험, 단위(키·경계·열림·429 모양).

### 5.2 빼는 것

- **좌석맵 API·캐시·CDN·`loadtest/scenarios`의 좌석맵 시나리오**: 이 묶음의 요구가 아니다. 좌석맵 600회/s를 재는 일은 별도 묶음이다.
- **게이트웨이 계정당 600회/분·리포트 30회/분·웹훅 IP 한도(BAT-060)**: 바꾸지 않는다. 첫 겹이다.
- **토큰 계약 변경**(파트너 토큰에 `tenant` 클레임 싣기, ADR-0172): 하지 않는다.
- **계정당 한도·경로별 한도·IP 한도**: 이 묶음은 테넌트 합계만 센다.
- **팬·관제·스캐너·공개 파트너 로그인·토큰 갱신·웹훅 경로**: 세지 않는다(테넌트 신원이 없거나 대상이 아니다).
- **슬라이딩 창·토큰 버킷·GCRA**: 고정 창 하나로 시작한다. 매끄러움이 필요하면 별도 결정이다.
- **새 Redis 클러스터·새 환경 값·새 연결**: 기존 세션·캐시 Redis 연결을 쓴다.
- **OpenAPI 응답 계약 변경**: 429는 공통 `TooManyRequests`로 이미 표현된다. 파트너 작업마다 429를 더하는 일은 하지 않는다.
- **화면·파트너 콘솔·관리 화면**: 화면은 429를 받으면 재시도 안내만 하면 되고, 이 묶음은 서버만 바꾼다.
- **kind e2e 무대 확장**: 기본은 플랫폼 통합 시험이다. 감독이 kind를 고르면 별도 몫으로 더한다.
- **Redis 장애 조치·클러스터 재구성 시의 정확한 카운터 보존**: 판정 실패는 열림으로 받아들인다. 유실 등급 C다.

## 6. 장부 범위

```text
D-T50 ⑦
```

- `node tools/ci/ledger.mjs --batch BAT-173`은 항목 1개(다른 단계, B)다. `docs/api/guidelines.md`는 장부 범위 토큰이지만 시험 표·ASVS 표의 행이 없어 항목이 아니다(도구가 경고한다).
- 시험 담당이 이름에 `D-T50 ⑦`을 단 시험을 더하면 상태가 '자동 시험'이 된다. 그 커밋에서 `docs/review/ledger-notes.md:97`의 D-T50 ⑦ 줄을 지운다(남기면 시험 이름과 부딪힌다).
- 판정은 "같은 테넌트 계정 둘이 합쳐 1분 창 안에 601번째 429"다. 600번째까지 통과, 601번째 429, 다른 테넌트는 통과, Redis 판정 실패는 통과까지 이 묶음의 판정으로 본다.
- `--require`는 시험 커밋 뒤에 통과해야 한다. 계획 커밋에서는 '다른 단계' 1개라 실패하는 것이 정상이다.

## 9. 공개 인터페이스

- `export interface TenantRateLimitPort { check(tenantId: string): Promise<{ allowed: boolean; retryAfterSeconds: number }> }`
- `export function redisTenantRateLimiter(o: { redis: HotRedis; limit?: number; windowMs?: number; timeoutMs?: number; onResult?: (r: 'allowed' | 'limited' | 'unavailable') => void }): TenantRateLimitPort`
- `export function tenantRateLimitKey(tenantId: string): string` → `rl:tenant:{tenantId}`. 테넌트 ID는 identity가 준 UUID이고, 빈 값이면 호출하지 않는다.
- `export const TENANT_RATE_LIMIT_PER_MINUTE = 600`, `TENANT_RATE_LIMIT_WINDOW_MS = 60_000`, `TENANT_RATE_LIMIT_TIMEOUT_MS = 20`.
- `CreateServiceOptions.tenantRateLimit?: { redis: HotRedis; limit?: number; windowMs?: number; timeoutMs?: number }`. `createService`가 이 값을 `TenantRateLimitPort`로 바꾸고 지표를 잇는다.
- HTTP 계약은 바뀌지 않는다. 429는 `about:blank`, `Too Many Requests`, `status: 429`, `instance`, `traceId`, `Retry-After`(정수 초), `Cache-Control: no-store`다. 플랫폼에 공통 `no-store` 규칙이 없으므로 가드가 직접 단다.
- 새 지표 `tenant_rate_limit_total{service,result}`. 테넌트·계정·경로 라벨은 없다.
- 새 환경 값은 만들지 않는 안을 먼저 본다. 각 서비스가 이미 쓰는 세션·캐시 Redis 주소를 쓴다. ops·payment의 `PEAKET_REAUTH_REDIS_URL`이 다른 Redis면 새 값을 정해야 한다(정할 것 9).
- 시작 규칙: `local`·`ci` 밖에서 파트너 역할 처리기가 있는데 `tenantRateLimit`이 없으면 시작하지 않는다. 이 검사는 `RolesCheck`와 같은 시작 확인에 둔다.

| T7 | `D-T50 ⑦ Redis가 20ms 안에 답하지 않으면 통과하고 unavailable로 센다` | 단위(가짜 Redis)·통합 | 응답이 없는 Redis로 요청 하나를 보내면 200이고 100ms 안에 끝나며, `tenant_rate_limit_total{result="unavailable"}`가 1 오른다. 5xx는 없다(architecture §4) | 통과할 수 있음. 틀린 구현 M6(닫힘)로 실패를 본다 |
| T8 | `D-T50 ⑦ Redis가 끊겨도 통과하고 돌아오면 다시 센다` | 통합 | Valkey를 멈춘 동안 파트너 요청은 200·`unavailable`, 다시 띄운 뒤 601번째는 429다(data §3 유실 등급 C) | 통과할 수 있음. M6로 실패를 본다 |
| T9 | `D-T50 ⑦ 카운터 키는 60초 수명을 갖고 창이 끝나면 다시 센다` | 통합 | 600건 뒤 `PTTL`이 0보다 크고 60,000 이하이며 `TTL`이 -1이 아니다. 키를 `PEXPIRE 1`로 줄여 기다린 뒤 다음 요청은 200이다(data §3) | 실패(키가 없다) |
| T10 | `D-T50 ⑦ 파트너 역할이 있는 다섯 서비스가 모두 공용 가드를 조립한다` | 서비스별 단위 | core-svc·payment-svc·ticket-svc·ops-svc·identity-svc에서 파트너 요청 1건은 한도 Redis 호출을 하고, 팬 요청은 하지 않는다. `local`·`ci` 밖에서 값이 없으면 `createService`가 던진다(service.ts) | 실패(배선이 없다) |
| T11 | `D-T50 ⑦ 동시 601건에서도 600건만 통과한다` | 통합 | `Promise.all`로 601건을 동시에 보내면 200이 정확히 600, 429가 1 이상, 5xx가 0이다. 카운터는 601 이상이고 600을 넘는 통과는 없다(data §5) | 실패(모두 200) |
| T12 | `D-T50 ⑦ 429는 게이트웨이와 같은 about:blank 모양이고 이름 붙은 Problem이 아니다` | 단위·통합 | `content-type: application/problem+json`, `type: about:blank`, `title: Too Many Requests`, `status: 429`, `Retry-After` 정수. `server-busy` 같은 이름이 붙지 않는다(guidelines §2·§6) | 실패(429가 없다) |

- **실패 확인 방법**: 단위는 기준 커밋 트리에서 새 시험만 복사해 돌린다. 통합은 Docker 차례 잠금 `lane2-BAT-173`을 잡고 Valkey만 띄워 그 파일만 돌린다. 두 인스턴스는 같은 모듈·같은 Valkey, 가짜 `AdminAuthzPort`가 계정 A1·A2에 테넌트 A, B1에 B, 관제·스캐너에 각자의 신원을 답하게 한다.

## 11. 실패 확인

이 묶음의 판정은 성능이 아니라 정확성이다. 600회/분은 초당 10회라 처리량 병목이 아니고, `loadtest/scenarios`에 파트너 시나리오도 없다. 아래를 구현 전에 한 번 재어 원인과 기준선을 남긴다.

1. **이미 있는 실패 근거**: 기준 트리에는 테넌트 카운터가 없다. 같은 테넌트 계정 둘로 601건을 보내면 601건 모두 200이고 `rl:tenant:*` 키가 0개다. 이것이 D-T50 ⑦의 실패다.
2. **작은 측정(기준 트리)**: Valkey 8.1 하나와 서비스 인스턴스 둘을 띄우고, 가짜 identity로 계정 A1·A2(테넌트 A)를 만든다. 60초 동안 601건을 고르게 보낸다(약 10건/초). 셀 것: 200·429·5xx 수, 받는 쪽 p50·p95, Redis `rl:tenant:*` 키 수·값, 프로세스 CPU. 기대: 200 601·429 0·키 0.
3. **작은 측정(구현 트리)**: 같은 무대로 200 600·429 1 이상, 키 `rl:tenant:{A}` 값 601·`PTTL` 0~60,000, 429 p95가 1ms 안팎, 전체 p95 증가가 5ms 이하인지 적는다. 5ms를 넘으면 20ms 마감·Lua 모양을 다시 본다.
4. **동시성 측정**: 601건을 `Promise.all`로 한꺼번에 보내 200이 정확히 600인지, 429가 1 이상인지, 5xx가 0인지 적는다. 이것이 `INCR` 원자성의 증거다.
5. **판단**: 2의 기준선과 3의 결과가 계획과 다르면(예: 429가 600번째에 나오거나, 601번째에도 200이거나, p95가 5ms를 크게 넘으면) 구현을 멈추고 감독에게 낸다. 부하를 키워 600/s를 재는 일은 하지 않는다(요구가 아니다).
6. **Docker 차례**: 잠금 이름 `lane2-BAT-173`. 끝나면 Valkey 컨테이너와 잠금 폴더를 지운다.

## 14. 자주 놓친 결함

- **센 뒤에 인가하지 않는다**: 한도 판정은 `judgeIdentity` 뒤에 둔다. 앞에 두면 토큰 없는 요청이 남의 테넌트 몫을 먹거나 테넌트 존재를 드러낸다. `admitBeforeBody`와 같은 함수 안에 넣으면 칸막이 경로가 두 번 센다.
- **테넌트는 identity 값만**: `x-tenant-id`·본문 `tenantId`·게이트웨이 머리를 믿지 않는다(ADR-0172). `principal.tenantId`가 빈 값이면 세지 않고 처리기에 맡긴다.
- **계정이 아니라 테넌트**: 같은 테넌트의 두 계정이 각각 600회를 받으면 안 된다. 키에 계정·세션·경로를 넣지 않는다.
- **키는 하나**: `rl:tenant:{tenantId}`. 서비스 이름·파드·경로를 넣으면 카운터가 쪼개진다. 게이트웨이의 `rl:*` 키와 같은 접두사지만 `tenant` 자리는 게이트웨이 서술자에 없다.
- **원자성**: `INCR`와 `PEXPIRE`를 두 번 왕복하면 그 사이에 죽어 TTL 없는 키가 남는다. Lua 한 번으로 하고, `PTTL` -1이면 60초를 다시 건다.
- **경계는 `> 600`**: 600번째는 통과, 601번째가 429다. `>=`로 쓰면 600번째가 막힌다.
- **429 모양**: `ProblemError`는 `about:blank`를 만들 수 없다(슬러그 규칙). `HttpException(429)`와 `Retry-After` 머리로 내고, 전역 필터가 `about:blank`·`Too Many Requests`로 바꾸게 한다.
- **`Retry-After`는 남은 창**: 늘 60이나 0이 아니라 `PTTL`을 올림한 1~60이다. `PTTL`이 -2(키 없음)면 1이다.
- **열림**: Redis 마감·연결·스크립트 오류는 5xx가 아니라 통과다. `unavailable` 지표를 올리고, 요청을 막지 않는다. 닫힘으로 바꾸면 Redis 장애가 파트너 API 전체 장애가 된다.
- **팬·관제·스캐너·공개 로그인**: `aud`가 `partner`가 아니거나 신원이 없으면 세지 않는다. 공개 파트너 로그인·갱신·웹훅은 테넌트가 없어 대상이 아니다.
- **다섯 서비스**: core-svc만 배선하면 payment·ticket·ops·identity 경로가 빠져나간다. 서비스마다 배선 시험을 둔다. `local`·`ci` 밖에서 빠지면 시작을 막는다.
- **같은 Redis**: 서비스별 환경 값 이름은 달라도 같은 세션·캐시 클러스터를 가리켜야 한다. 두 인스턴스가 다른 Redis를 보면 T2가 잡는다. 배포 값이 다르면 D-T50 ⑦은 통과해도 운영에서 쪼개진다.
- **동시 601**: `Promise.all`로 보내 200이 정확히 600인지 본다. Lua가 원자적이지 않으면 601·602가 통과한다.
- **시작 조립**: `main.ts`/`start.ts`가 실제로 `tenantRateLimit`을 넘기는지 `dist/main.js`로 본다. 단위 시험만 통과하고 시작 파일이 빠지는 결함이 있다(BAT-195).
- **지표 라벨**: 테넌트 ID·계정 ID를 라벨에 넣지 않는다. 카디널리티와 개인정보 규칙(observability §8)을 지킨다.
- **429 캐시**: 플랫폼에 공통 `no-store` 규칙이 없다. 429를 내는 가드가 `cache-control: no-store`를 직접 달았는지 본다. 붙지 않으면 중간 캐시가 막힌 응답을 재사용할 수 있다.
- **시험 값이 코드 상수와 같지 않게**: 600·60초를 코드에서 가져오지 말고 정본 값으로 적는다. 경계는 599·600·601로 본다(BAT-195).

## 15. 정할 것

지금 멈춰 묻는 것은 없다. 다음이 나오면 그 항목만 멈추고 감독에게 넘긴다.

1. **좌석맵 600회/s를 실제로 원할 때**: 이 계획의 범위가 아니다. BUILD_ORDER 95·441행과 다르므로 그 묶음을 새로 만들지, 이 묶음을 멈출지 감독이 정한다.
2. **D-T50 ⑦을 kind에서 돌려야 할 때**: 실제 파트너 백엔드를 kind에 올리는 무대(서비스 이미지·시드·identity 대역)를 더해야 한다. 일정과 무대를 다시 정한다.
3. **고정 창의 2배 경계가 문제일 때**: 토큰 버킷·슬라이딩 창으로 바꾸는 방향 결정이 필요하다. 이 묶음은 고정 창으로 간다.
4. **429에 `instance`·`traceId`를 빼야 할 때**: 게이트웨이와 글자 그대로 같게 하려면 서비스 Problem 표준을 깨는 예외를 정해야 한다.
5. **운영에서 세션·캐시 Redis가 없을 때**: 시작을 막는 안(제안)과 경고만 남기는 안 가운데 감독이 정한다. 한도가 조용히 꺼지는 것을 막으려면 시작 실패가 낫다.
6. **다섯 서비스 배선이 1일에 안 들어갈 때**: core·payment·ticket만 먼저 하고 ops·identity를 다음 묶음으로 뗄지, 1.25일로 늘릴지 정한다. 한 서비스라도 빠지면 D-T50 ⑦의 '서비스 층' 뜻이 반쪽이 된다.
7. **새 ADR 번호가 필요할 때**: 이 커밋은 정본에 '(추천 적용)'만 썼다. 별도 ADR을 원하면 다음 빈 번호(지금 0315 다음)를 감독이 정한다.
8. **파트너 리포트 30회/분과 테넌트 600회/분의 관계**: 리포트 조회는 게이트웨이 계정당 30회/분과 테넌트 600회/분에 함께 든다(guidelines §6). 이 묶음은 테넌트 합계만 세고 30회/분은 건드리지 않는다. 둘을 합치는 새 한도가 필요하면 별도 결정이다.
9. **ops·payment의 `PEAKET_REAUTH_REDIS_URL`이 세션·캐시 클러스터가 아닐 때**: 새 `PEAKET_TENANT_REDIS_URL`을 다섯 서비스에 더할지, 기존 세션·캐시 주소를 하나 더 받을지 정한다. 정하지 않고 각자의 Redis를 쓰면 테넌트 키가 서비스마다 쪼개져 D-T50 ⑦이 운영에서 반쪽이 된다.

### 확인(2026-11-20, 구현)

- **재인증 Redis(정할 것 9)**: 저장소의 `deploy/`는 이 주소들을 Secret(`secretEnvFrom`)으로만 받아 실제 값을 확인할 수 없다. 정본 `docs/data.md` §3은 `reauth:jti:{jti}`를 세션·캐시 클러스터의 키로 적고 ops-svc·payment-svc의 `PEAKET_REAUTH_REDIS_URL`을 그 저장소로 지목한다. 그래서 두 서비스의 재인증 Redis를 세션·캐시 클러스터로 보고, 다섯 서비스 모두 이미 만드는 연결(core `PEAKET_SHOP_REDIS_URL`·payment `PEAKET_REAUTH_REDIS_URL`·ticket `PEAKET_TICKET_REDIS_URL`·ops `PEAKET_REAUTH_REDIS_URL`·identity `PEAKET_IDENTITY_REDIS_URL`)을 그대로 쓴다. 새 환경 값·새 Redis 연결은 만들지 않았다. 배포 Secret이 실제로 다른 클러스터를 가리키면 `PEAKET_TENANT_REDIS_URL` 같은 새 값을 정하는 일이 남는다(운영 확인 몫).
- **시작 규칙**: `local`·`ci` 밖에서 파트너 역할 처리기가 있는데 `tenantRateLimit`이 없으면 `RolesCheck`가 시작을 막는다. `createService`가 `PEAKET_ENV`로 그 요구를 켠다.
