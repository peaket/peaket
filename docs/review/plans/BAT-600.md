# 묶음 계획: BAT-600(LCH-010·LCH-020 굿즈 주문·한정 재고·재고 예약·부가 상품·수령 방식·미수령 자동 취소)

- **무엇**: 묶음을 시작할 때 만든 작업 목록이다(docs/architecture.md §8.6 4의 1, ADR-0256 결정 10). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane5`, 가지 `feature/lane5-BAT-600`, 출발점 `origin/develop` `08120a67`. 구현 전 트리(분리 HEAD, 커밋하지 않음)는 `D:/ticketpass-lane5-base`. 묶음 지시서는 감독이 준 `brief-BAT-600.md`(작업 폴더 밖)다. 2026-11-18 작성.
- **등급**: A(돈: 굿즈 결제 전 주문·한정 재고·결제 취소. 권한: 남의 주문·남의 티켓). 틀린 구현 목록은 아래 7, 장애 주입은 8이다.
- **차례**: 정방향 묶음이다(이 계획 커밋에 `Batch-Order: impl-first`). 계획 → 구현 → 시험(구현 전 트리 실패 확인을 같은 커밋 '실패 확인' 절에) → 리뷰 → 리뷰 반영(지적마다 `Fix-By: test` 먼저, 그다음 `Fix-By: impl`) → 검증 → 기록(감독). A 등급이라 B·C의 짧은 고리(ADR-0283 결정 2)를 쓰지 않는다.
- **정본(이 커밋에서 정한 빈칸 포함)**: [ADR-0299](../../adr/0299-merch-payments-order-kind-nullable-event-id.md)(굿즈 결제의 원장 길, PRF-180이 넘긴 `event_id` 문제), [ADR-0300](../../adr/0300-merch-order-stock-reservation-first-implementation.md)(굿즈 주문·한정 재고·재고 예약·유형 스키마·속성 검증 잡), [ADR-0301](../../adr/0301-ticket-addons-fulfillment-unclaimed-auto-cancel.md)(부가 상품·수령 방식·미수령 자동 취소). 방향의 정본은 ADR-0101, ADR-0107 결정 4, docs/planning/03 §2.13(O1~O7, I1~I18), docs/data.md §2 `merch_order`·`product`·`pickup_slot`, §3 굿즈 재고 키, §4 경계 5, §5, docs/api/openapi.yaml `shop` 태그와 `/v1/tickets/{ticketId}/addons`, docs/features/payment.md §2 '승인 명령 접수의 첫 구현'·'선택기의 첫 구현', §11 P-T42·P-T56~58, docs/verification.md V-T26·V-T35·V-T46·§4.1, docs/security/asvs/payment.md.
- **시험 ID 옮김(2026-11-19)**: 갈래 1 BAT-010이 develop에 P-T55(탈퇴 참여자와 탈퇴 미룸 409)를 먼저 써서, 이 묶음의 P-T55·P-T56·P-T57을 P-T56·P-T57·P-T58로 옮겼다(정본·이 파일). 이 묶음의 커밋 제목·메시지에 남은 옛 ID(P-T55~57)는 새 ID(P-T56~58)로 읽는다. 장부 범위의 V-T35는 ③이 BAT-605 몫이라 'V-T35 ①, V-T35 ②'로 좁혔다.

## 계획

### 1. 범위

**장부 범위(좁힘)**: BUILD_ORDER BAT-600 행의 장부 범위가 `docs/features/payment.md`·`docs/features/settlement.md`·`docs/security/asvs/payment.md` 전체(252개)라, LCH-010·LCH-020이 실제로 닿는 항목만 남겼다(이 커밋에서 BUILD_ORDER 행을 고침).

```text
P-T42, P-T56, P-T57, P-T58, V-T26, V-T35, V-T46, payment:v5.0.0-2.2.1, payment:v5.0.0-2.3.1, payment:v5.0.0-2.3.3, payment:v5.0.0-2.3.4, payment:v5.0.0-8.2.2
```

- `node tools/ci/ledger.mjs --batch BAT-600`(이 커밋 뒤): 항목 36개(A 27·B 9). 자동 시험 5(ASVS 다섯 행, 이미 다른 시험이 있음), 측정 1(V-T26), 다른 단계 1(V-T35 ③ → BAT-605), 빈칸 29(P-T42 ①~⑤, P-T56 ①~⑥, P-T57 ①~⑧, P-T58 ①~⑤, V-T35 ①②, V-T46 ①~③). 이 묶음이 끝나면 빈칸 29개가 모두 자동 시험이어야 한다.
- 정본에 판정 기준 ID가 없던 몫은 이 커밋에서 시험 표에 더했다: P-T56(굿즈 결제의 결제창 준비·승인 명령), P-T57(굿즈 주문과 한정 재고의 결제 흐름), P-T58(미수령 자동 취소)은 docs/features/payment.md §11, V-T46(상품 유형 스키마·속성 검증 잡)은 docs/verification.md(V-T26 아래).
- `docs/review/ledger-notes.md`: P-T42를 '다른 단계(미정)'에서 등급 A·정할 곳 LCH-010으로, V-T26을 측정(미정: 셋째 유형 PR과 데모 배포 단계가 없음), V-T35 ③을 다른 단계(LCH-030), V-T35 ①②를 등급 A로 적었다. 장부 파일(`docs/review/ledger/`) 다시 쓰기는 기록 커밋(감독) 몫이다.
- 뺀 것: payment.md·settlement.md의 나머지 항목(티켓 결제·정산·지급, 이 묶음이 바꾸지 않음), P-T53(승인 명령 접수, 티켓 쪽 동작은 그대로이고 굿즈 몫은 P-T56로 따로 둠).

### 2. 바른 동작과 근거

값은 옮겨 적지 않는다. 시험의 단언 값은 아래 정본 자리에서 가져온다.

### 4. 구현 차례(제안)

1. G1 payment-svc 마이그레이션·`ConfirmPayment`·`PrepareCheckout`·사건 계약과 purchase-svc 건너뛰기(소비자 먼저라 purchase-svc 고침을 같은 커밋에).
2. G2 유형 표·스키마·파트너 검사·속성 검증 잡.
3. G3 Redis 어댑터와 Lua(실제 Valkey로 짧게 확인).
4. G4·G5 주문·결제·당기기·만료(core-svc 마이그레이션 주문 표 몫).
5. G6 ticket-svc `ListHeldTickets`, 부가 상품 주문·목록.
6. G7 수령 방식 규칙과 `pickup_slot`.
7. G8 미수령 자동 취소.
8. 조립(main·relay·정비 일)과 시작 파일을 시험 조립과 따로 띄워 본다(§8.6 '자주 놓친 결함').

### 6. 구현 전 트리에서 실패를 볼 수 없는 시험과 그 까닭

- **대부분 '바탕이 없어 실행조차 안 되는 실패'다(§8.6 7, 세지 않는다)**: core-svc의 주문·결제·만료·부가 상품·미수령 시험(경로·모듈·Lua·표가 없음), `ListHeldTickets` 시험(ticket-svc가 `UNIMPLEMENTED`로 답하므로 '실패'는 보이지만 그 실패는 새 동작의 판정이 아니다), V-T46의 유형 스키마 시험(스키마 묶음이 없음). 이 시험들은 아래 7의 틀린 구현(검증 담당)으로 한 번은 실패를 본다. 시험 담당은 구현 커밋에서 통과를 본 뒤 할 수 있으면 7의 표본 몇 개(예 M-03·M-12·M-21)를 손으로 넣어 실패를 보고 '실패 확인'에 덧붙인다.
- **구현 전 트리에서 진짜로 실패해야 하는 것**: P-T56 ①③⑤(지금 `ConfirmPayment`는 `MERCH`를 몰라 회차 빈 요청을 `INVALID_ARGUMENT`로, `PrepareCheckout`은 `MERCH`를 `INVALID_ARGUMENT`로 답한다), P-T56 ⑥의 purchase-svc 건너뛰기(지금은 굿즈 사건을 반영하려 든다)와 사건 부호화(지금 스키마는 `eventId` null을 받지 않는다), P-T57 ⑧(지금 코드는 남은 수를 새 수량으로 덮어써 식의 결과와 다르다), V-T46 ①의 '표에 없는 유형 422'(지금은 아무 유형이나 201이다). 시험 파일을 `D:/ticketpass-lane5-base`에 복사해 돌린다(실행되는 시험만 센다).
- **구현 전 트리에서 처음부터 통과할 수 있는 것**: P-T56 ④(`UNSPECIFIED`+회차 빔은 지금도 `INVALID_ARGUMENT`), P-T56 ②의 같은 요청 다시(티켓 규칙과 같은 꼴이라면). 7의 M-04·M-05로 실패를 본다.

### 9. 필요한 마이그레이션(번호는 감독이 준다)

- **payment-svc 하나**: `payment.order_kind text NOT NULL DEFAULT 'TICKET'` + CHECK(`TICKET`·`MERCH`), `event_id` NULL 허용, CHECK `(order_kind = 'TICKET') = (event_id IS NOT NULL)`(ADR-0299 결정 1).
- **core-svc 둘(하나로 합쳐도 된다)**:
  - 주문 몫: `merch_order` 상태 CHECK를 정본 값으로 바꾸고 있는 행을 옮김(`PENDING` → `CREATED`, `CANCELLED`·`REFUNDED` → `PAID`), 칸 더하기(`account_id`·`fulfillment`·`amount`·`stock_reserved_until`·`payment_id`·`consent_version`·`recipient_name`·`recipient_phone`·`delivery_address`·`pickup_slot_id`·`escrow`), `pg`·`buyer_name`·`buyer_phone` NULL 허용(`pg` CHECK에 시뮬레이터 값이 필요하면 `SIMULATOR`를 더함), 부분 인덱스 `(stock_reserved_until) WHERE status = 'CREATED'`·`(account_id, created_at)`, `merch_order_item`에 `option_snapshot jsonb`·`linked_ticket_id uuid`(+인덱스)·`cancel_reason text`, 새 표 `merch_payment_attempt`(부분 유일 인덱스 둘)·`merch_confirm_job`·`merch_refund`(ADR-0300 결정 9, ADR-0301 결정 2·5).
  - 상품 몫: 새 표 `product_type`과 행 `MERCH`·`PARKING`(판 1), 새 표 `pickup_slot`(docs/data.md ERD, CHECK `(fulfillment = 'PICKUP') = (pickup_slot_id IS NOT NULL)`은 `merch_order`에), 권한(`core_app`만 새 표를 읽고 쓰고, `core_partner`는 새 표를 읽지 않음. 있는 행 보안 정책과 맞춤).
- **ticket-svc**: 없음(읽기만. 보유자·회차 읽기에 맞는 인덱스가 없으면 구현 담당이 감독에게 번호를 받는다).

### 10. 막힌 몫

- **묶음 전체는 막히지 않는다.** develop에 결제 원장·승인 실행기·결과 당기기·결제 취소(`CancelPayment` 승인 뒤 취소 포함)·시뮬레이터가 있다.
- **파트너가 수령 시간대를 만드는 길**: openapi에 경로가 없다(`pickup_slot`은 ERD에만 있음). 이 묶음은 표와 주문 쪽 규칙만 만들고, 시험·개발은 시험 데이터로 시간대를 넣는다. 파트너 경로와 화면은 BUILD_ORDER에 단계가 없다(아래 12).
- **Kafka 소비 시험**: 이 PC에서 Kafka 네이티브 모듈이 막혀 purchase-svc 건너뛰기는 처리기에 값을 넘기는 시험으로 보고, 실제 소비자 시험은 초안 PR CI가 본다.

### 11. 범위 밖

- 택배 주문의 결제(결제대금예치 상점 값)와 굿즈 가상계좌(O2~O4), 구매자 취소·반품 상태 기계, 부가 상품 구매자 취소(V-T35 ③): BAT-605(LCH-030). 이 묶음은 택배 주문을 만들기까지 하고 결제 시도 시작은 503 `pg-unavailable`이다(ADR-0299 결정 3).
- 인기 MD 대기열(입장 토큰 확인, 대기열 설정 사본): BUILD_ORDER에 단계가 없다.
- 주문서·결제·결과 화면(SCR-015·SCR-055), 월렛의 이용권 표시, 굿즈 복귀 화면(`/shop/checkout/return`): 화면 묶음(갈래 2).
- core-svc의 `trade.payments` 소비자(ADR-0299 결정 5), 계정 병합 뒤의 '계정 묶음' 소유 확인(ADR-0300 결정 8), 공휴일 달력(ADR-0301 결정 5).
- V-T26 리드타임 측정(셋째 유형 PR과 데모 배포 뒤).
- 상품 정산서 계산(BAT-610에서 끝남). 이 묶음은 정산 기준일 계산이 정본 상태 값을 읽게만 고친다.

### 12. 정할 것

- **소유자 결정이 필요한 것은 없다.** 빈칸은 모두 작은 세부라 ADR-0299~0301에 '(추천 적용, 2026-11-18, BAT-600 계획)'으로 적었다. 바꿀 만한 값: 재고 예약 15분과 접수 뒤 연장(ADR-0107 그대로), 만료 작업 1초, 당기기 2초, 미수령 취소 10:00 KST·다음 영업일, 환급 다시 부르기 10분·3일, 옵션 0~10개, `perAccountLimit` 1~99.
- **감독에게(단계 배치)**: (가) 파트너 수령 시간대 만들기 API·화면, (나) 인기 MD 대기열이 BUILD_ORDER에 단계가 없다. 어느 묶음에 넣을지 감독이 정한다.
- (구현 중 추천 적용) 만료 작업은 한정 상품의 Redis 예약 원소에 더해 DB 부분 인덱스(`stock_reserved_until`, `status = 'CREATED'`)로 기한이 지난 결제 전 주문도 쓸어 같은 조건부 `EXPIRED`로 바꾼다(한정이 아닌 주문은 원소가 없다). 풀기는 원소가 있을 때만 돌리므로 두 길이 겹쳐도 한 번만 돌아온다.
- (구현 중 추천 적용) `RESERVE`는 `unpaid`가 가리키는 다른 주문의 예약 원소가 이미 없으면 풀린 칸으로 보고 덮어쓴다(계정을 모르는 'DB에 없는 주문'의 칸이 남아 그 계정이 막히지 않게). `RELEASE`·`EXTEND`는 계정 ID를 받아 그 칸을 지운다.
- (구현 중 추천 적용) 표 칸 더함: `merch_order.paid_at`(승인 시각), `merch_confirm_job.sent`·`tries`(받아 적음·보낸 횟수), `merch_refund.item_ids`(취소한 항목)·`alerted`(3일 넘김 SEV2를 한 번만). `merch_order_item.cancel_reason` CHECK는 `UNCLAIMED`만. `product.type`에는 외래키를 두지 않는다(옛 행은 속성 검증 잡이 잡는다).
- (구현 중 추천 적용) 주문번호 `orderNumber`는 `M` + 주문 ID 앞 12자리 16진 대문자 [가정]. 택배 배송비는 한 판매자 상품 가운데 가장 큰 배송비 한 번. 계정당 한도의 기존 수량에서 `CANCELLED`·`REFUNDED` 항목은 뺀다.
- (구현 중 추천 적용) 결제 상태: 접수 전이면 409 `payment-not-accepted`(openapi), 실패면 `FAILED`와 `reason` `PAYMENT_FAILED`. 결제 시도 시작: 시작 조건 409를 먼저 보고 택배 503 `pg-unavailable`, `VIRTUAL_ACCOUNT`는 payment-svc를 부르지 않고 400. 승인 명령이 `REJECTED`(INVALID_ARGUMENT 등)여도 승인 기한까지 다시 보낸다.
- (구현 중 추천 적용) `PEAKET_MERCH_CONSENT_VERSION`이 없으면 택배 주문은 503 `dependency-unavailable`과 SEV2 줄(`kind` merch-consent-version-unset). core-svc 릴레이의 shop 반복 셋·정비 일 둘은 서비스 역할 연결 `PEAKET_DATABASE_URL`(core_app)이 있을 때만 돈다. 환급 다시 부르기 반복은 60초마다 다음 시각이 된 환급을 본다(같은 환급은 10분 [가정]마다).
- (구현 중 추천 적용) 정비 일: `merch-unclaimed-cancel`은 `daily`로 10:00 KST 전이면 미룸(`deferred`), 영업일이 아니면 그날은 건너뜀(`skipped`), 한 번에 1,000항목 [가정]. `product-attributes-check`는 `window`로 04:40 KST 전이면 미룸, 경고 줄의 상품 목록은 100건까지(건수는 따로).

### 13. 구현·시험 지시문에 넣을 것

- docs/architecture.md §8.6 '자주 놓친 결함' 전부. 이 묶음에서 특히: Lua·저장소 응답의 정확한 값(카운터·원소 수·돌려준 주문 ID), 지우는 연산이 건드린 키 넷 모두(`stock`·`resv`·`resv_qty`·`unpaid`), 경계 양쪽(15분 − 1ms·15분, 한도 2·3, 남은 수 0·−1, 영업일 금·토·월), 계정 대조를 뺀 요청 거절, 세 상태(보유 있음·없음·확인 못 함), 겹친 가드 하나씩 빼기(만료 조건과 접수 잠금, Redis와 PostgreSQL 재고), 시험 값을 코드 상수와 다르게, 시작 파일 조립을 따로 띄워 보기.
- 구현 커밋은 시험 파일을 건드리지 않는다. 지금 시험 가운데 옛 상태 값(`PENDING`·`CANCELLED`·`REFUNDED`)이나 `buyerName` 필수를 쓰는 것(`services/core-svc/test/merch-settlement*.test.ts`·`export*.test.ts`·`shop-notify.migration.test.ts`, `test-int/shop-notify.int.test.ts`)이 구현 뒤 형 검사나 마이그레이션 시험에서 깨지면 시험 담당이 고친다(구현이 정본 값으로 바꾼 결과다).

시험 담당(2026-11-18)이 정본이 애매하다고 본 곳이다. 고르는 것은 감독 몫이다.

- **E-1 P3 불변식이 굿즈 결제를 세는가**: invariant-checker(결제 원장 사본을 읽는 불변식 검사기, 토픽 소비자는 아니다)의 P3 '승인했는데 발권 대상이 아님'이 원장 `order_kind` `MERCH` 승인 결제를 위반으로 센다(`src/tables.ts`가 `order_kind`를 읽지 않고 `sql/p3_approved_not_enqueued.sql`이 모든 승인 결제를 본다). ADR-0299 결정 1은 굿즈를 원장에서 가르기로 했지만 docs/verification.md §2.5 P3는 '모든 승인 결제'로도 읽힌다. 시험 `P-T56 ⑥ ADR-0299 결정 1_굿즈·부가 상품 결제(원장 order_kind MERCH, event_id NULL)는 purchase 주문·발권이 없어도 P3·P4 위반이 아니고, 같은 때의 티켓 결제 위반은 그대로 센다`(`services/invariant-checker/test-int/invariants.int.test.ts`)는 결정 1 쪽으로 쓰여 지금 실패한다. 이 결함은 구현 전 트리에도 있다(굿즈 결제가 생기는 것이 이 묶음이라 이 묶음에서 드러난다). 정본에 'P3·P4는 `order_kind` `TICKET`만'을 더하고 구현이 고칠지, 시험을 미룰지 정한다.
  - 판정(계획, 2026-11-19): **정본 빈칸 → 구현 결함**. docs/verification.md §2.5에 'P3·P4는 원장 `order_kind` `TICKET`만, P1·P2·P6은 모든 결제'를 지금 적었고(추천 적용) P-T56 ⑥ 판정 칸에도 더했다. 시험은 맞다. 구현 담당이 D-1대로 고친다.
- **E-2 수령 방식이 다른 상품을 한 주문에**: 택배만 받는 상품과 현장 수령만 받는 상품을 한 주문에 담으면 openapi `createShopOrder` 422 ①(`merch-order-mixed`)과 ⑥(`merch-product-unavailable`, 그 수령 방식을 받지 않는 상품)에 함께 걸린다. 구현은 ⑥을 답한다. 시험(`services/core-svc/test/shop-order.http.test.ts`의 'P-T57 ⑦ 수령 방식이 다른 상품…')은 422이고 type이 둘 가운데 하나인지만 본다. 판매자 섞임은 P-T57 ⑦대로 `merch-order-mixed`로 단언한다.
  - 판정(계획, 2026-11-19): **정본 빈칸 → 시험 결함**. ADR-0300 결정 4에 '수령 방식은 본문 하나라 그 수령 방식을 받지 않는 상품은 ⑥ `merch-product-unavailable`, ①은 판매자가 다를 때'를 적었다. 구현(⑥)이 맞고, 시험 담당이 그 사례의 type을 `merch-product-unavailable` 하나로 단언하게 고친다.
- **E-3 거절된 환급 행을 '그대로 둔다'**: ADR-0301 결정 5는 `REJECTED`면 '환급 행을 그대로 둔다'인데 구현은 행 상태를 `REJECTED`로 바꾼다. 시험은 행이 남고 금액이 같고 `CANCELLED`가 아니며 다시 부르지 않는 것까지만 본다(`shop-unclaimed.int.test.ts`). '그대로'가 상태 값까지 뜻하는지 정본에 적을지 정한다.
  - 판정(계획, 2026-11-19): **정본 빈칸(구현이 맞음)**. ADR-0301 결정 5에 '그대로 = 지우거나 `CANCELLED`로 끝내지 않고 금액을 남기며 다시 부르지 않음, 행 상태는 `REJECTED`'를 적었다. 구현은 그대로 두고, 시험 담당은 행 상태 `REJECTED`까지 단언을 더한다(시험 보강).

  - 판정(계획, 2026-11-19): **시험이 맞음(고칠 것 없음)**. ADR-0301 결정 5에 '3일 정각은 아직 아니고 넘긴 뒤 처음 실행에서 한 번'을 적어 시험의 읽기를 정본으로 굳혔다.

### 다시 리뷰(2026-11-19)

같은 리뷰 담당이 고친 곳만 다시 봤다. 보는 범위는 리뷰 반영 계획 `dde568d6`(정본), 재현 시험 `2db7c4a7`(`Fix-By: test`), 구현 고침 `273bbe6d`(`Fix-By: impl`, RV-01·RV-02·RV-09)다. 시험 ID 옮김 `78394cc9`·`a74b2729`·`03c396df`(옛 P-T55~57 → P-T56~58)는 훑기만 했다. 측정 창이라 시험은 돌리지 않고 코드만 읽었다. 줄 번호는 `03c396df` 기준이다.

- **RV-01(고쳐짐)**: `merch-payment-results.ts:58-99`에서 받아짐을 모르는 작업은 승인 기한 전에만 다시 보낸다. 기한이 지나면 다시 보내지 않고 `BatchGetPayments`로 묻는다. 답에 결제가 없을 때만 `#fail`(조건부 `CREATED → FAILED`와 두 재고 복구)로 끝내고, 있으면 '받아짐'으로 바꿔 결과대로 반영한다. 묻지 못하면 5초 뒤 다시 묻는다. 정본 ADR-0300 결정 5·6에 고친 글과 맞다. 새 결함이 있는지는 아래처럼 봤다.
  - 이중 과금: 기한 뒤에는 `ConfirmPayment`를 보내지 않는다(60·65줄). payment-svc의 결제사 셋(토스·포트원·시뮬레이터)도 같은 10분 기한과 `>=` 경계를 쓴다(`confirm-runner.ts:261`). 그래서 core-svc가 `FAILED`로 끝낸 뒤 늦게 적힌 명령이 있어도 결제사를 부르지 않고 만료(EXPIRE)로 끝난다.
  - 재고 이중 되돌림: `applyFailed`와 `applyPaid`가 `status = 'CREATED'` 조건부라 한 번만 바뀐다. Redis 풀기는 원소가 있을 때만 돌린다.
  - 영원히 미뤄짐: payment-svc가 계속 답하지 못하면 5초마다 미루고, 그동안 주문은 `CREATED`로 재고를 쥔다. 정본(묻지 못하면 끝내지 않음)이 정한 동작이고, 당기기 실패 지표와 경고 줄이 남는다.
  - BatchGetPayments 읽기: 결제 원장 주 DB에서 읽는다(읽기 사본이 없다).
- **RV-01 재현 시험**: `shop-order.int.test.ts`의 P-T57 ⑨ 세 사례가 결함을 잡는다. 가짜 서버가 명령을 적고 `DEADLINE_EXCEEDED`로만 답하면 기한에 `FAILED`가 아니고, 그 뒤 승인되면 `PAID`, `product_stock` 2·카운터 2이며 기한 뒤 `ConfirmPayment`는 0건이다. 기한에 당기기가 실패하면 4,999ms에는 다시 묻지 않고 5초에 다시 묻는다. 기한 뒤 답에 없으면 다시 보내지 않고 `FAILED`다. 옛 구현(묻지 않고 FAILED)은 첫 사례에서 실패한다.
