## 3. 이번에 하는 것

차례: 계획 → 시험(기준 실패) → 구현 → 게이트 → 기록.

1. **I-01 core 0055 마이그레이션·사본 표**:
   - `event_sale_state`(회차 판매 상태 사본): `event_id uuid PK REFERENCES event(id) ON DELETE CASCADE`, `production_id uuid NOT NULL`, `status text NOT NULL CHECK (status in ('UPCOMING','ON_SALE','ALL_HELD','SOLD_OUT','ENDED'))`, `version integer NOT NULL CHECK (version >= 1)`, `changed_at timestamptz NOT NULL`, `updated_at timestamptz NOT NULL DEFAULT now()`. `production_id` 색인을 둔다.
   - `search_document_sale_status_check`를 지우고 `ALL_HELD`를 더해 다시 만든다.
   - `search_document_source_at(at, ids)`를 `CREATE OR REPLACE`로 교체한다. 회차마다 `event_sale_state.status`가 있으면 그 값을, 없으면 지금처럼 `open_at`·`starts_at - 24h`로 계산한 값을 쓴다. 공연 합성은 ① `ON_SALE`이 하나라도 있으면 `ON_SALE` ② 없고 `ALL_HELD`가 있으면 `ALL_HELD` ③ 없고 `UPCOMING`이 있으면 `UPCOMING` ④ 남은 것이 모두 `SOLD_OUT`이면 `SOLD_OUT` ⑤ 그 밖은 `ENDED`다. 사본이 없는 회차만 있는 공연은 지금과 같은 값이 나온다.
   - `search_apply_event_sale(p_event_id, p_status, p_version, p_changed_at) RETURNS text`를 만든다. `SECURITY DEFINER`이고 `search_path = public, pg_temp`다. ① 회차의 `production_id`를 찾고 없으면 `unknown` ② `INSERT … ON CONFLICT (event_id) DO UPDATE … WHERE event_sale_state.version < excluded.version`로 판 번호가 클 때만 쓴다(0행이면 `stale`) ③ `search_document` 줄이 있으면 `search_version` 판을 1 올리고 그 공연 줄의 `sale_status`·`updated_version`을 `search_document_source_at(now(), ARRAY[production])` 값으로 고친다 ④ `applied`를 돌려준다. 한 트랜잭션이다.
   - 권한: `event_sale_state`는 `core_app`에 `SELECT`만 준다(파트너 목록·검색이 읽는다). `search_apply_event_sale`은 `core_app`에 `EXECUTE`만 준다(소비자 풀이 부른다). `PUBLIC`은 회수한다. `core_partner`·`core_search`에는 주지 않는다.
   - **백필 없음**: core에는 과거 purchase `event_sale` 값이 없다. 대신 ㉠ 사본이 없는 회차는 질의·원천 함수가 시간으로 계산해 지금 동작을 유지하고, ㉡ purchase-svc는 `ON_SALE`·`ALL_HELD`·`SOLD_OUT` 회차의 같은 판을 5초 [가정]마다 다시 내므로 배포 뒤 첫 다시 내기가 사본을 채운다(EventSaleChanged 다시 내기, ADR-0219 결정 5). 이 사실을 §8 남은 위험에 적는다.
   - 저널 idx 55·tag `0055_event_sale_state`·when을 54보다 크게 넣고 `0055_snapshot.json`을 만든다(prevId = 0054 snapshot id).
2. **I-02 core 소비자·저장소**:
   - `catalog/inbound/event-sale-changed.handler.ts`: `trade.seats` 값에서 `EventSaleChanged`를 읽는 `CoreEventSaleChangedHandler`(`KeyedHandler`). `type` 칸이 있으면 좌석 사건으로 보고 건너뛴다. `EventSaleChanged.pick({ eventId, status, version, changedAt, eventKey })`만 읽어 셈 칸(`available`·`held`·`paying`·`soldOutTiers`·`countedAt`·`avgTicketsPerOrder`)이 틀려도 상태 사건은 받는다. 업무 키는 회차 ID, 중복 제거 키는 `eventKey`다. 모양이 틀린 값은 `bad:<회차 ID>` 키로 돌려 `RangeError`를 던져 플랫폼이 보류하게 한다.
   - `catalog/adapters/db/drizzle-event-sale-state.ts`: `DrizzleEventSaleStateStore`가 `search_apply_event_sale($1,$2,$3,$4)`를 한 번 부르고 `applied|stale|unknown`을 돌려준다. DB 일시 장애는 그대로 던져 소비자가 다시 한다.

   - `main.ts`: 같은 소비자 풀(`consumerDatabase`, core_app)로 `DrizzleEventSaleStateStore`와 `CoreEventSaleChangedHandler`를 만들고, `CoreEventsHandler`에 탈퇴 처리기와 함께 넘긴다. 종료 차례는 그대로다.

   - `docs/data.md`의 `search_document.sale_status` 문장과 core ERD에 `event_sale_state`를 더한다(기록 커밋). 공개 카드는 `ALL_HELD`를 `ON_SALE`로 접는다는 점을 적는다.

## 8. 남은 위험과 열린 질문

- **RV2-R1(백필 없음)**: core에는 과거 purchase `event_sale` 값이 없다. 배포 전에 이미 `ALL_HELD`인 회차는 배포 뒤 purchase의 5초 [가정] 다시 내기가 도착할 때까지 DB 목록에서 `ON_SALE`로 보인다. 그동안 파트너 목록의 `saleStatus=ALL_HELD`는 그 공연을 반환하지 않는다. `UPCOMING`·`ENDED`는 시간 계산으로 정확하다.
- **RV2-R2(사본 지연)**: 소비자가 멈추거나 밀리면 사본이 낡는다. 판 번호로 늦은 사건을 거르므로 값이 거꾸로 가지는 않지만, 목록은 잠정 값일 수 있다. `consumer_held_events{topic="trade.seats"}`와 applied 로그로 본다.
- **RV2-R3(PostgreSQL) — 닫힘(2026-11-27 18:42)**: 실제 PostgreSQL 18에서 0055 적용·`search_document_source_at` 교체·`search_apply_event_sale`·파트너 목록 질의를 확인했다. `partner-home` 7/7, 기존 `search-sale-status`·`catalog` 10/10. 실행 ID `INT-F07-12-RV02-20261127-1840`.
- **RV2-R4(공개 검색 의미 변화)**: DB의 `sale_status`가 `ALL_HELD`를 담게 되어 공개 카드 매핑·검색 필터·순위를 함께 고친다. 매핑을 빠뜨리면 openapi 계약 위반이므로 RV2-11·12가 막는다. 실제 검색 API 응답의 `ALL_HELD` 0건은 PostgreSQL 통합에서 다시 본다.
- **RV2-R5(모르는 회차)**: core `event`에 없는 회차의 사건은 `unknown`으로 버린다. 회차가 나중에 생기면 그 회차의 다음 판이 와야 반영된다. purchase는 core가 판매를 연 회차만 팔므로 정상 경로에서는 생기지 않아야 한다.
- **열린 질문 Q-RV2-01**: `search_document.sale_status`를 내부적으로 다섯 값으로 넓히는 대신 별도 칸(`event_sale_status`)을 더할 수도 있다. 이번에는 기존 한 칸을 넓히고 공개 층에서 접는 쪽을 골랐다(색인·질의 변경이 작고, `ALL_HELD`가 판매 중이라는 뜻을 한 칸에 담는다). 검색 계약을 다섯 값으로 넓힐지는 F-07-3·검색 후속에서 정한다.
