# 기능 계획: F-02-4(접속기록 전용 저장소와 보존 만료 파기 — 3개월 파기·관리 계정 2년 사본·백업 뒤 다시 적용)

- **진행**: 계획(2026-11-24). 다음은 시험(기준 트리 실패 확인)이다.
- **무엇**: BUILD_ORDER '기능 단위 계획' F-02-4(갈래 2, 등급 A, OPS-330, WBS 2.50일, 단계 줄 `OPS-330 wbs 4.4.4`)의 작업 목록이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **동결 범위**: ADR-0373 결정 2로 F-02-4는 v1 완성 범위 밖(`동결`)이다. 동결 기능은 `freeze/lane2-F-02-4` 가지와 이 워크트리에서만 진행하고 `develop`·`release`에 합치지 않는다(릴리스 범위 결정, 이 가지에 그 ADR 파일은 없다). 기능 표 상태는 `동결` 그대로 둔다.
- **쉬운 말**: 법이 요구하는 접속기록(누가·언제·어디서 접속했는지)은 업무 데이터와 떨어진 전용 저장소에 3개월 둔다. 3개월이 지난 날짜의 저장 칸(파티션)은 정해진 잡이 통째로 지우고, 지운 사실을 파기 감사 로그에 남긴다. 관리자 계정의 접속기록은 3개월 뒤 지워지기 전에 매일 밤 운영 감사 저장소로 복사해 최소 2년 둔다. 또 하루 사본(Object Lock)과 7일짜리 백업에서 되살렸을 때, 백업 시점 뒤에 이미 지운 날짜를 파기 기록과 대조해 다시 지운다. 이 기능은 그 파기·복사·다시 적용이 설정과 로컬 실행기에서 실제로 도는지 확인한다.
- **바탕**: 작업 폴더 `D:/ticketpass-freeze-F-02-4`, 가지 `freeze/lane2-F-02-4`, 출발점 `8e19e3c55`(F-01-8 가지 끝, 2026-11-24). F-01-8이 만든 `access_log` 표·TTL·사용자 넷·하루 사본 설정을 입력으로 쓰고 그 시험을 깨지 않는다.
- **차례**: A등급 시험 먼저(ADR-0372·ADR-0373·ADR-0381): 계획 → 시험(기준 트리 실패 확인) → 시험 리뷰 → 시험 고정 → 구현 → 게이트 → **새 세션 구현 리뷰**. 구현 리뷰는 이 세션이 하지 않는다.
- **한 줄 결론**: 보존 판정·파기 계획·다시 적용 계획을 `tools/ci/access-log-retention.mjs`의 순수 함수로 모으고, 실제 지우기·관리 계정 복사는 `tools/local/access-log-jobs.mjs`가 ClickHouse HTTP와 ops-svc 감사 접수 경로로 한다. 설정은 `retention.yaml`·`003_purge.sql`·경보 규칙에 두고, 정적 검사가 정본 값(3개월·2년·7일·40일·`P3M7D`)과 하나씩 어긋날 때 막는다. 장부 범위는 ASVS 다섯 행으로 좁힌다.

## 2. 감독에게(정할 것)

1. **장부 범위 좁히기(이 커밋에서 적용)**: 기능 표 F-02-4 행의 `장부 범위`를 `offline-gate:v5.0.0-14.1.2, -14.2.4, -16.1.1, -16.4.2, -16.4.3` 다섯으로 좁혔다. 좁히기 전 302항목(자동 137·ID만 101·빈칸 43)은 `docs/features/offline-gate.md`의 스캐너 시나리오와 ASVS 나머지 행이 대부분이라 이 기능과 닿지 않는다. `docs/observability.md`·`docs/security/data-classification.md`는 장부 항목이 없어(도구 경고) 바탕 문서로만 두고 범위에서 뺐다. 판정 문구는 그대로 두었다.
2. **단계 줄의 '월 파티션'과 F-01-8 표의 '하루 파티션'이 다르다**: OPS-330 단계 줄은 '월 파티션 DROP'이라 적혀 있으나, F-01-8이 만든 `access_log` 표는 `PARTITION BY toYYYYMMDD(ts)`(하루)이고 일 해시 앵커·하루 사본도 하루 단위다. 표를 다시 만들지 않고 **하루 파티션을 지운다**. 단계 줄 문구는 이 기능에서 고치지 않고 이 계획에만 남긴다(정본 문구를 바꾸려면 감독 결정).
3. **실제 클라우드·클러스터 연결은 INF-020**: 버킷·Object Lock 수명 주기·KMS·CronJob·IAM 역할·실제 ClickHouse 배포는 INF-020(구간 5)이다. 이 기능은 설정 원천·정적 검사·로컬 실행기·가짜 HTTP 시험까지 만든다(F-01-8과 같은 처리).
4. **관리 계정 2년 사본의 경로(추천)**: 파기·복사 작업은 `tools/local/access-log-jobs.mjs`가 맡고, 관리 계정 줄은 ops-svc의 내부 감사 접수 경로 `POST /internal/v1/ops/audit-records`로 보낸다. 감사 기록 종류 `ADMIN_ACCESS_LOG`와 파기 기록 `ACCESS_LOG_PARTITION_PURGE`를 ops-svc 접수 허용 목록에 더한다. 실제 CronJob·내부 토큰 주입은 INF-020이다.
5. **하루 사본의 '보존 만료 파기'**: 하루 사본 버킷의 3개월+7일 삭제는 S3 수명 주기 규칙이 한다(이미 F-01-8의 `copy.retention: P3M7D`). 이 기능은 그 값이 정본과 같은지 검사하고, 파기 잡이 **ClickHouse 표**의 3개월 만료 파티션을 지우는 몫을 더한다. 사본 버킷 객체를 잡이 직접 지우지 않는다.
6. **파기 일정·유예(추천 적용 2026-11-24, F-02-4 계획)**: 파기는 매일 05:00 KST(하루 사본 04:00 뒤, 사본 지연 경보 06:00 전), 관리 계정 복사는 매일 04:30 KST. 파티션은 `오늘(UTC) − 3개월`보다 **엄격히 이른 날짜**만 지운다(3개월이 지난 날 전체가 끝난 뒤). 유예 일수는 0이다.
7. **백업 다시 적용의 범위(추천 적용)**: ClickHouse 스냅샷 보존 7일, 파기 감사 대상 ID 40일을 읽어, 복원 시점 뒤에 실행된 파기 기록의 날짜 파티션만 다시 지운다. 40일보다 오래된 대상 ID는 남기지 않는다(정본 '백업 보존 상한과 파기').
8. **Docker·측정 창**: 계획·시험·정적 검사는 Docker 없이 된다. 실제 ClickHouse 통합 시험은 `lane2-F-02-4`로 Docker 잠금을 잡고 돌린다. 2026-11-25 15:35~ 잠금이 `lane6-F-04-10`에 있어 대기 중이며, `single` 정책은 건드리지 않는다. 잠금을 잡으면 끝난 뒤 바로 놓는다.

## 3. 범위

### 3.1 하는 것

- **보존 판정(`tools/ci/access-log-retention.mjs`)**: UTC 달력 기준 3개월 컷오프, 하루 파티션 만료 목록, 관리 계정 줄 2년 보존 끝, Object Lock `P3M7D` 보존 끝, 파기 계획(한 번에 지울 상한), 복원 뒤 다시 적용 계획, 파기 기록 검증을 순수 함수로 둔다. 값은 정본에서 읽고 코드에 상수로 복사하지 않는다.
- **전용 저장소·파기 권한(`data/clickhouse/access-log/003_purge.sql`)**: 파기 작업 사용자 `al_purger`를 더한다. `access_log`·`access_log_otel`의 `ALTER`(DROP PARTITION)와 `system.parts`의 `SELECT`만 주고, 접속기록 행 `SELECT`는 주지 않는다. 기존 사용자 넷의 권한은 바꾸지 않는다.
- **작업 설정(`deploy/platform/observability/access-log/retention.yaml`)**: 파기·관리 계정 복사·백업 다시 적용·지표·감사 기록 종류를 적는다. 일정·상한·기록 종류는 이 계획의 추천안, 보존 값은 정본을 가리킨다.
- **경보 규칙(`deploy/platform/observability/alerts/access-log.yaml`에 더함)**: `AccessLogPurgeOverdue`(만료 파티션이 24시간 넘게 남음), `AccessLogPurgeFailed`(마지막 성공 36시간 초과·기록 없음), `AccessLogAdminCopyLate`(전날 관리 계정 복사가 06:00까지 없음), `AccessLogPurgeAuditFailed`(파기 기록 쓰기 실패)를 SEV2 `kind: legal`로 둔다.
- **로컬 실행기(`tools/local/access-log-jobs.mjs`에 더함)**:
  - `--purge`: ClickHouse `system.parts`에서 파티션 목록을 읽어 만료 날짜를 `ALTER TABLE … DROP PARTITION`으로 지우고, 파기 계획·결과를 ops 감사 접수 경로에 `ACCESS_LOG_PARTITION_PURGE`로 남긴다. 지우기 전에 `PLANNED`, 지운 뒤 `DROPPED`를 남기며, 이미 없어진 파티션은 `reconciled`로 남긴다.
  - `--admin-copy`: 전날(KST) `is_admin = 1` 줄만 ClickHouse에서 읽어 `ADMIN_ACCESS_LOG`로 ops 감사 접수 경로에 한 줄씩 보낸다. 같은 줄은 `eventKey`로 한 번만 받힌다.
  - `--reapply`: `--snapshot-at` 뒤에 실행된 파기 기록을 읽어, 되살아난 파티션 가운데 해당 날짜를 다시 지운다.
  - `--metrics`: 만료 파티션 수·마지막 성공 시각·관리 복사 행 수를 Prometheus 글자 꼴로 낸다(배포는 INF-020).
- **ops-svc 감사 접수**: `ADMIN_ACCESS_LOG`(관리 계정 접속기록)와 `ACCESS_LOG_PARTITION_PURGE`(파기 계획·결과)를 받는 좁은 payload 스키마를 더한다. 개인정보 금지 칸(비밀번호·토큰·쿠키·본문)은 받지 않는다.
- **정적 검사**: `checkAccessLogRetention(root)`가 표·TTL·`al_purger` 권한·`retention.yaml`·경보 규칙·감사 기록 종류·복원 다시 적용·문서 값의 일치를 본다. `node tools/ci/access-log-retention.mjs --check`는 0/1/2로 끝난다.
- **문서**: 이 계획, BUILD_ORDER F-02-4 범위·비고. `docs/review/ledger-notes.md`는 바꿀 항목이 없으면 건드리지 않는다.

## 7. 공개 인터페이스(시험 담당이 이 모양으로 시험을 먼저 쓴다. 구현은 이 이름을 그대로 쓴다)

- **`tools/ci/access-log-retention.mjs`**
  - `monthCutoff(dayIso: string, months: number): string` — UTC 날짜에서 개월을 뺀 `YYYY-MM-DD`. 월말·윤달은 그 달 마지막 날로 보정한다(`2026-05-31, 3 → 2026-02-28`).
  - `expiredPartitionDays({todayIso, partitionDays, retentionMonths}): string[]` — `partitionDay < monthCutoff(today, retentionMonths)`인 날짜만 오름차순.
  - `retentionUntil(dayIso: string, months: number, extraDays: number): string` — Object Lock 보존 끝(UTC ISO).
  - `adminRetainUntil(accessTsIso: string, years: number): string` — 관리 계정 줄 보존 끝(UTC ISO, 2월 29일 보정).
  - `purgePlan({todayIso, partitionDays, retentionMonths, maxDropPerRun}): {expired, drop, overdue, truncated}`.
  - `reapplyPlan({snapshotAtIso, records, partitionDays}): {drop, skipped}` — `records`는 `{day, table, executedAt}`.
  - `checkAccessLogRetention(root: string): string[]` — 위반 목록, 읽기 실패는 던짐.
  - CLI `node tools/ci/access-log-retention.mjs [--check] [--root <저장소>] [--plan --today <YYYY-MM-DD> --partitions <csv>]` → 0/1/2.
- **`tools/local/access-log-jobs.mjs`(기존 CLI에 더함)**
  - `--purge --clickhouse <URL> [--clickhouse-user <u> --clickhouse-password <p>] --ops-audit <URL> [--token <t>] [--today <YYYY-MM-DD>] [--max-drop <n>] [--metrics <파일>]`
  - `--admin-copy --date <YYYY-MM-DD> --clickhouse <URL> [--clickhouse-user <u> --clickhouse-password <p>] --ops-audit <URL> [--token <t>]`
  - `--reapply --snapshot-at <ISO> --purges <파일> --clickhouse <URL> [--clickhouse-user <u> --clickhouse-password <p>] --ops-audit <URL> [--token <t>]`
  - ClickHouse HTTP는 `FORMAT JSON` 응답을 읽고, ops 감사 접수는 `POST <ops-audit>`에 `{eventKey, recordType, recordId, payload, occurredAt}`를 보낸다.
- **`deploy/platform/observability/access-log/retention.yaml`의 칸**
  - `purge.{timeZone,schedule,retentionMonths,graceDays,maxDropPerRun,auditRecordType,auditStates}`
  - `adminCopy.{timeZone,schedule,lookbackDays,retentionYears,recordType,sourceUser,sourceFilter}`
  - `backup.{snapshotRetentionDays,reapplyWindowDays,objectLockRetention}`
  - `metrics.{overdue,lastSuccess,adminCopyLastSuccess,adminCopyRows}`
- **`data/clickhouse/access-log/003_purge.sql`**: `CREATE USER IF NOT EXISTS al_purger … '${PEAKET_AL_PURGER_PASSWORD}'`, `GRANT ALTER ON access_log.access_log`, `GRANT ALTER ON access_log.access_log_otel`, `GRANT SELECT ON system.parts TO al_purger`. 접속기록 표 `SELECT`를 주지 않는다.
- **ops-svc 감사 접수 recordType**
  - `ADMIN_ACCESS_LOG`: `{source, accessTs, requestId, event, result, provider, factors, failure, clientIp, userAgent, adminAccountId, pod, seq, retainUntil}` (모두 필수, `clientIp`·`adminAccountId`·`seq`는 null 허용).
  - `ACCESS_LOG_PARTITION_PURGE`: `{day, table, state: PLANNED|DROPPED|FAILED, rows: number|null, reconciled: boolean, reason: string|null}`.
- **경보 이름**: `AccessLogPurgeOverdue`·`AccessLogPurgeFailed`·`AccessLogAdminCopyLate`·`AccessLogPurgeAuditFailed`. 모두 `severity: sev2`, `kind: legal`.

## 11. 자주 놓친 결함(docs/architecture.md §8.6 4의 목록에서 골름, 시험·구현 지시문에 넣는다)

- 경계값은 양쪽을 둔다: 3개월 컷오프의 같은 날짜·하루 전, 월말(5/31·3/31), 윤달(2/29), 2년 보존 끝의 2/28·2/29·3/1, 백업 7일·파기 기록 40일, Object Lock `P3M7D`.
- 빈 결과가 통과로 새지 않게 한다: 파티션 0개·관리 계정 0줄·파기 기록 0건은 각각 '할 일 없음'과 '확인 불가'를 가른다. 읽기 실패는 2이고, 만료 파티션이 없어도 마지막 성공 시각은 남긴다.
- 같은 규칙을 두 곳에서 지키면 하나만 빼는 결함이 숨는다: 파기 금지(파기 기록 실패 시 지우지 않음)를 실행기와 정적 검사 양쪽에서 본다. TTL 축소 금지를 표 검사와 실행기 계획 양쪽에서 본다.
- 판정 함수만 보지 말고 부르는 쪽을 본다: `expiredPartitionDays`만이 아니라 ClickHouse에 나가는 DROP 문장·감사 접수 본문·종료 코드를 본다.
- 시험 값은 코드 상수가 아니라 정본에서 적는다(3개월·2년·7일·40일·`P3M7D`).
- 예외 목록은 정확한 집합으로 본다: `al_purger`의 권한을 늘리거나 `al_admin_reader` 행 정책을 빼면 잡는다.
- 개인정보가 두 갈래로 새지 않게 한다: 관리 복사 payload에 일반 계정 줄·본문·토큰이 없는지, 파기 기록에 행 내용이 없는지.
- 닫힘 실패를 본다: 감사 접수 실패·ClickHouse 응답 없음·복원 기록 읽기 실패에서 지우지 않고 끝나는지.
