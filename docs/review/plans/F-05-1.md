**넘기는 것(이 기능이 하지 않는다)**

- 부스 재발급 버튼과 그 뒤 흐름(대조 목적 동의, `POST /v1/identity/booth-reverifications`, `booth-requests`, `booth-authorizations`, BOOTH 등록 허용): GAT-190(F-05-6, A). 서버가 하나도 없어 화면만 만들면 가짜 API로 끝나기 때문이다. 이 계획 커밋이 GAT-190 단계 줄에 '넘긴 것'을 적었다. 월렛은 안내 글까지(ADR-0363 결정 9).
- 월렛 목록 `GET /v1/tickets`·`GET /v1/tickets/{ticketId}`: 받는 서비스가 없다(어느 단계 줄에도 없다). 월렛 화면의 티켓은 목업 그대로이고, '키가 폐기된 뒤' 안내는 그 경로가 생길 때. A·보안 높음·통과 기준이 아니라 구간 끝 정리 목록에 한 줄로 올린다(§8.6 '맡기기'). 이 기능의 실제 서버 확인은 화면 흐름 모듈 연결 시험이다(§8).
- Kafka `trade.tickets` 발행·소비자: GAT-250(F-06-1) 남은 것. 그때 보낼 표를 옮긴다.
- 운영 VAPID 키·메일 대행: OPEN[10]·GAT-250.
- 키 증명 채택 결정과 실기기 확인: 소유자(막힘, §3).
- 입장 시작 판정이 `ticket.event_starts_at`(회차 시작)으로 대신 보는 지금 규칙(core `entry_opens_at`이 아님): 양도·취소도 같은 칸을 쓴다. 이 기능은 바꾸지 않고 §12에 위험으로 적는다.

### 5. 공개 인터페이스

- 서버: openapi `createTicketDeviceKey`(403 세 이름·429·503), 헤더 `X-Reauth-Token`. 내부 `POST /internal/v1/notify/ticket-events`(notify §4.7). 표 `device_key_notice`(data.md).

### 7. 차례

1. 구현 ①: 계약 고침과 생성물 → ticket-svc(재인증 꽂기·403 셋·0012·반복) → core-svc 내부 입구 → 각 서비스 `typecheck`·`test`.
2. 구현 ②: 웹 월렛 워커 위치·킬 스위치 → 재발급 흐름·안내 → 웹 푸시 → 로그아웃 루틴 → 게이트웨이 대역·가짜 API → `pnpm --filter @peaket/web` 타입 검사·`test`, `pnpm lint`.
3. 구현 ③: GAT-030 PC 측정(§9) → `docs/review/measurements/F-05-1-key-proof-poc.md`(예정, 구현 담당이 만든다).
4. 시험(구현을 맡지 않은 담당): §6 표, 시험 이의 고침, §8 연결 시험.
5. 리뷰(짧은 대조, B 짧은 고리) → 검증(틀린 구현 표본 최소 8개, §10) → 게이트(§10) → 기록.
- 커밋마다 `Role`·`Agent-Session`·`Batch: F-05-1`(모델을 알면 `Agent-Model`). 구현 커밋은 시험 파일을 바꾸지 않는다.

### 8. 실제 서버 연결(§8.6 4의 4)

가짜 API로 끝내지 않는다. 앞선 예(`services/identity-svc/test-int/`의 F-05-7 연결 시험 계획, `services/core-svc/test-int/local-partner-stack.int.test.ts`, `services/payment-svc/test-int/purchase-path-e2e.int.test.ts`의 웹 스크립트 동적 가져오기)를 따른다.

- **월렛 재발급** `services/ticket-svc/test-int/wallet-reissue-wiring.int.test.ts`: 실제 PostgreSQL 18(`test-int/postgres.ts`, 0012까지), 실제 Valkey(재인증 `jti`), ticket-svc HTTP 앱(시작 파일과 같은 조립, 실제 Drizzle·`JwksFanReauthGate`), 시험이 띄운 팬 공개키 묶음 서버(시험 키로 `op` `DEVICE_KEY_ISSUE`·`act` `FAN_SENSITIVE` 토큰을 서명), 웹 게이트웨이 대역(`apps/web/scripts/local-fan-gateway.mjs`를 `/* @vite-ignore */ new URL(…)` 동적 가져오기, `ticketUrl`), 웹 흐름 모듈(`wallet-device-key/register.ts`·`reauth-return.ts`·상태 함수)을 같은 방식으로 가져와 팬 쿠키를 실은 `fetch`로 부른다. 씨앗: 티켓 둘(입장 시작 전·뒤)과 기기 A 키. 대본: 기기 B 키 ISSUE → 403 `reissue-required`(상태 '저장소 유실, 입장 시작 전') → 토큰으로 REISSUE → 201·옛 키 폐기·`device_key_notice` 한 행 → 보내기 반복이 core 내부 입구 대역으로 한 번 보냄 → 23시간 뒤 다시 → 429 → 입장 시작 뒤 티켓 → `reissue-at-booth`. core 내부 입구 대역은 core-svc의 본문 Zod를 상대 경로로 가져와 받은 본문을 검사한다(짝 맞춘 대역, CLAUDE.md '의존 선언 밖 상대 경로'). ticket-svc를 고치면 core-svc도 타입 검사한다.
- **웹 푸시·로그아웃 차례** `services/core-svc/test-int/web-push-wiring.int.test.ts`: 실제 PostgreSQL(core 마이그레이션), core-svc HTTP 앱(notify 실제 저장소), 게이트웨이 대역(`coreUrl`), 웹 `features/web-push/flow.ts`·`session-cleanup/routine.ts`를 동적 가져와 고정 구독으로 등록 201 → 다른 계정 다시 묶기 200 → 정리 루틴이 `DELETE` 204를 서버 로그아웃 대역보다 먼저 보냄 → `push_subscription` 행이 없음. `POST /internal/v1/notify/ticket-events`도 같은 앱에 보내 작업 행 수를 본다(O-T48 core 쪽).
- **실제가 아닌 것(커밋 본문·검증 절에 적는다)**: 브라우저의 푸시 서비스, 메일 대행(파일 대역), Kafka. 이 PC에서 Kafka 통합은 돌지 않는다(갈래 메모, CI 몫). 월렛 화면의 티켓 목록은 목업이라 브라우저에서 실제 ticket-svc 재발급은 볼 수 없다(§1 넘기는 것).
- 컨테이너 이름 머리 `lane3-f051-`, 끝나면 `docker rm -f -v`. Docker는 `bash /d/ticketpass-locks/lock.sh take docker lane3-F-05-1`로 잡고 `drop`.

### 10. 틀린 구현 표본과 게이트

검증 담당이 관련 시험만 돌리고 `git checkout -- <파일>`로 되돌린다. 최소 8개, 후보:
1. 기기 키 등록에 재인증 확인기를 꽂지 않음(시작 파일, O-T47 ②·연결).
2. 확인기가 `op`를 보지 않음(`TICKET_RETURN` 통과, O-T47 ④).
3. 입장 시작 뒤 유효 키+재인증 ISSUE를 교체로 받음(메모리·Drizzle 하나씩, O-T47 ⑥).
4. 24시간 경계 `>`를 `>=`로(23시간 59분·24시간 정각, O-T47 ⑤).
5. 알림 행을 트랜잭션 밖에서 쓰거나 같은 키 다시 등록에도 씀(O-T48).
6. 월렛이 `reissue-required`에 키를 지움, 또는 돌아와 새 키를 만듦(O-T49 ②).
7. `peaket.wallet.reauth`에 토큰을 넣거나 10분 지난 표시를 믿음(O-T49 ③).
8. 워커 범위를 `/`로, 또는 킬 스위치가 `peaket-wallet`·`/push/` 등록을 지움(FE-T14·FE-T43).
