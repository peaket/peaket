## 1. 진단 — K7 ② 한 번

- 현재 클러스터(합본 CPU 4/replica 3)에서 K7 ②를 같은 조건(결제 1만 건, 100/s, 예열 10초·본구간 100초, 응답 버림 5%·16초 늦춤 0.5%, 본구간 50초에 앱 파드 하나 강제 종료)으로 한 번 잰다.
- `HotPathMetrics`의 `payment.confirm.*`와 `payment.status.*`를 Prometheus에서 본구간 창으로 뽑아 표로 가른다.
- 실행이 발생기 놓침·시나리오 오류로 무효여도 진단에는 쓴다. 무효 사유와 수치는 숨기지 않는다.
- 1차 진단(2026-11-11, `.cache/peaket-bat029/k7-diag`): 무효(dropped 561·시나리오 오류 1). 결제 확정 p99 38.05초. `payment.status.wait` 평균 10.9초·p99 29.6초가 상위이고, `payment.confirm.gateway` 평균 473ms·p99 1.86초, `mark` 48ms, `finish` 57ms다. 같은 회차의 DB 전이 시각을 조인하면 결제 원장 승인은 `created_at → approved_at` p50 0.43초·p99 1.89초인데, `payment.approved_at → purchase_order APPROVED`가 p50 6.45초·p90 13.44초·p99 21.11초다. 즉 상위 구간은 결제사 호출이 아니라 **결제 결과 반영 소비자(trade.payments)의 지연**이다. 소비자는 본구간 100초에 2,318건만 처리(23/s)했고, 같은 풀을 쓰는 홀드 원장 소비자는 3,419건(34/s)을 처리했다. Kafka 메시지 키가 회차라 인기 회차의 결제 사건이 한 파티션에 몰리고, 파드의 소비자 전용 DB 풀 4개를 두 소비자가 나눠 쓰는 것이 처리량 상한으로 보인다. 이 가설을 계측으로 확인한 뒤 고친다.

## 2. 계측 — 결제 결과 반영과 대기 표

- `ApplyPaymentResult`에 `HotPathMetrics`를 선택 인자로 넣고 다음 구간을 잰다: `payment.result.total`, `payment.result.read`, `payment.result.write`, `payment.result.after_commit`. 결과 이름은 `applied`·`skipped`·`held`·`conflict`·`error`로 낮춘다.
- `PaymentStatusWaitTable`에 `hotPath`를 선택 인자로 넣고 `payment.status.poll`(틱 하나)과 `payment.status.poll.read`(묶음 조회)를 잰다. 묶음 조회 실패는 기존 `purchase_payment_status_poll_failures_total`과 함께 본다.
- 라벨은 `service`·`stage`·`outcome`뿐이고 주문·계정·회차 ID를 싣지 않는다. 지표가 던져도 반영·대기를 막지 않는다.
- 시험: 구간이 기록되는지, 지표가 던져도 `execute`·`wait`가 그대로 끝나는지, 기존 반환·던짐이 바뀌지 않는지.

## 3. 최적화 — 동작 불변

- **결제 결과 소비자 DB 풀 분리·확대**: 지금은 `trade.payments`와 `trade.seats` 소비자가 한 풀(연결 4개 [가정])을 나눠 쓴다. 결제 결과 소비자에 전용 풀(연결 8~12개 후보)을 주고, 홀드 원장 소비자는 기존 풀을 쓴다. `held_event` 표는 같은 DB라 어느 풀이나 써도 된다. 연결 수는 PostgreSQL `max_connections` 600과 파드 수(3) 안에서 정한다.
- **대기 표 전용 풀**: `PaymentStatusWaitTable`의 200ms 묶음 조회가 핫패스 풀을 빼앗지 않게 전용 일반 풀(연결 2개 후보)을 준다. 요청 경로의 단건 `read`는 기존 핫패스 풀 그대로다.
- **`readMany` 질의**: 주문마다 `payment_attempt` 상관 하위 질의를 도는 대신 `status = 'ACCEPTED'` 부분 유일 색인을 쓰는 조인으로 바꾼다. 반환 모습·정렬·404·기다림 판정은 바꾸지 않는다.
- **소비자 동시 처리 키**: 전용 풀이 커진 뒤 `maxKeys`를 32에서 늘릴지 측정으로 정한다. 늘리지 않아도 32개 키가 12연결을 채울 수 있으면 그대로 둔다.
- 바꾸지 않는 것: Kafka 메시지 키(회차), 토픽 파티션 수, 주문 전이·결제 결과 반영 순서, 롱 폴링 200ms·25초·2,000건 상한, API 응답·Problem type, 불변식 P1~P4·P6.
- 시험 먼저: 소비자 풀 분리가 두 소비자의 처리·보류를 바꾸지 않는지, 대기 표 전용 풀이 `readMany`·`read` 결과를 바꾸지 않는지, `readMany` 새 질의가 기존과 같은 모습을 돌려주는지(빈 배열·UUID 아님·500건 상한 포함).
- A등급 변이: 결제 결과 소비자 풀을 다시 공유로 되돌리기, 대기 표 풀을 핫패스 풀로 되돌리기, `readMany`의 `status = 'ACCEPTED'` 조건 빼기, 소비자 동시 처리 키 상한을 1로 낮추기 가운데 항목마다 1개(경계·되돌림은 2개)를 넣어 시험이 잡는지 본다.

## 4. A/A 측정 고정

- 조용한 쌍(quiet) 동안 다른 시험·빌드·다운로드·부하를 돌리지 않는다. 실행 전에 `Get-CimInstance Win32_Process`로 pnpm·node·k6·docker pull이 없는지 확인하고, 조용한 쌍이 도는 동안에는 도구 호출도 최소화한다.
- 발생기 사전 시작·`WARM_START_AT_MS`·`startSkewS=0`을 확인한다. 발생기별 `cpuMeanPctMax`·`memMaxPctMax`도 함께 남긴다.
- 호스트 부하를 고정한다: Docker Desktop·kind·Prometheus·Grafana·Postgres·Valkey·Kafka 외에 새 컨테이너를 띄우지 않고, Windows 업데이트·백신·다른 pnpm 작업이 겹치지 않는 시간에 잰다.
- `noise2` pnpm 실패를 고친다: `pnpm.CMD`가 Corepack의 `pnpm-native.exe`를 찾다 실패한 것이므로, 잡음 부하는 pnpm을 거치지 않는 `node --test loadtest/test/args090.test.mjs` 반복으로 바꾼다. 잡음 강도는 1~2개 반복으로 정하고, 대상이 무너지지 않으면서 p99가 조용한 쌍보다 유의하게 커지는지 확인한다.
- 조용한 쌍 2회가 p99 비율 ±9.6% 안이면 A/A 성립으로 본다. 안 되면 발생기(`startSkewS`·dropped·VU)·호스트(CPU·메모리·다른 프로세스)·대상(앞 실행의 정리·HPA·JIT·연결 풀) 가운데 어디인지 가른다.
- 원자료는 `docs/review/measurements/BAT-029/aa/`에, 요약은 `aa-summary.json`에 남긴다.

## 5. 재측정

- A/A가 성립하면 K7 ② 3회를 회마다 새 클러스터(`cluster.mjs down/up/observability/v1`)에서 잰다. 조건은 BAT-028과 같다.
- 3회 모두 유효(놓침 0·시나리오 오류 0)이고 결제 확정 p99가 3초 안이면 통과다. 무효·미달은 원인과 지표를 남긴다.
- 코드가 K2 경로에 닿으면(소비자·대기 표·readMany는 K2 홀드 경로와 다른 풀이라 닿지 않을 후보) K2 3회도 잰다. 닿지 않으면 그 사실을 근거와 함께 적는다.
- 성능 장부: K7 3회는 `docs/perf-ledger/runs/2026-11-11-k7-v1-fault-r*-bat029/`에 기록한다.

## 7. 예상과 위험

- 계측·진단 4시간, 최적화·시험 8시간, A/A 4시간, K7 3회 3~4시간, 게이트·기록 4시간. 합 2~3일 [가정].
- 위험: 소비자 DB 풀을 늘리면 PostgreSQL 연결·CPU 경합이 커져 핫패스가 느려질 수 있다. 전용 풀로 나누고 연결 수를 작게 시작해 K7 한 번으로 확인한 뒤 늘린다.
- 위험: Kafka 키가 회차라 한 파티션에 몰리는 구조는 이 묶음에서 바꾸지 않는다. 파티션을 늘리거나 키를 주문 ID로 바꾸는 것은 별도 설계·계약 변경이다.
- 위험: A/A 조용한 쌍이 호스트 열·백그라운드 작업으로 다시 34% 벌어질 수 있다. 실행 전후 프로세스·CPU·발생기 skew를 남기고, 안 되면 원인을 가른 뒤 다음 턴으로 넘긴다.
- 위험: K7 3회가 모두 유효해도 p99 3초를 넘으면 최적화가 부족한 것이다. 상위 구간 표와 함께 남기고 다음 배치로 넘긴다.
