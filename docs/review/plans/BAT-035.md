# BAT-035 계획 — purchase-svc 세 경로 트랜잭션 DB 연결 보유 시간 줄이기

- 작성: 2026-11-12
- 묶음: BAT-035(HOT-469, 갈래 1, 구간 1, **A등급**, 0.5~1일 [가정])
- 장부 범위: `P-T1`, `P-T23`
- 선행: BAT-034(HOT-468, R-501) — 핫패스 연결 대기 250ms. K7 진단에서 429 2.82%·confirm p99 4,065ms·시나리오 오류 16으로 미달.
- 웨이브: 갈래 2·3이 CI 회귀를 고치는 동안 K7을 돌리지 않는다. CI가 초록이 되고 `measurement go`를 받은 뒤 수정 후 K7 진단 1회만 돈다.

## 1. 목표

- purchase-svc의 세 경로 트랜잭션이 DB 연결을 잡고 있는 시간을 줄인다.
  - `POST /v1/orders`
  - `POST /v1/orders/{orderId}/payments`
  - `POST /v1/orders/{orderId}/payment-acceptance`
- BAT-034의 250ms 연결 대기는 **유지**한다. 대기 한도를 더 늘리지 않고, 트랜잭션 문장 수와 왕복을 줄여 같은 250ms 안에 더 많은 요청이 끝나게 한다.
- 목표: K7 100/s에서 접수 429 **<1%**, `payment_confirm_ms{phase:main}` p99 **3초 안**.
- 응답 계약·좌석·주문·접수 동작·멱등·Outbox 마지막 문장 규칙은 바꾸지 않는다.

## 2. 진단 증거

K7 진단 1회(2026-11-12, `.cache/peaket-bat033/k7-diag-bat034/`):

- 접수 9,402건: 202 9,136, **429 265(2.82%)**, 503 1, 409·422·500·504 0.
- 429 `durationMs`: 접수 p50 385ms·p90 673ms·p99 811ms, 주문 p50 476ms·p90 589ms, 결제 시작 p50 502ms·p90 790ms.
- 성공 202 p50 533ms·p90 838ms·p99 1,049ms. 250ms를 기다리고도 실패하는 요청이 남았다.
- `payment_confirm_ms` p99 4,065.35ms, `payment_end_truncated_terminal` 452·`_pending` 19, PENDING 총계 378 중 끝 구간 밖 359.
- 유효 조건: dropped 0, `startSkewS=0`, **시나리오 오류 16**(진입 201 실패 16).

### 문장 수·시간(실제 PostgreSQL 18, max 1 경로 시험)

| 경로 | 고치기 전 문장 | 고치기 전 시간(로컬) | 고친 뒤 문장 | 고친 뒤 시간(로컬) |
| --- | ---: | ---: | ---: | ---: |
| 주문 생성 | 8 | 18.2ms | **6** | 18.0ms |
| 결제 시도 시작 | 9 | 8.8ms | **8** | 9.3ms |
| 결제 접수 | 14 | 13.3ms | **11** | 10.9ms |

- 세 경로 모두 멱등 기록 4문장(락 한도 설정·키 INSERT·기본값 복원·결과 참조 UPDATE)이 공통이다.
- 접수의 `itemsOf`·`reachedBeforeOf`는 **중복이 아니었다**. T3(AUTHENTICATED)는 사건이 없어 Outbox·항목·도달 이력을 읽지 않고, T4(ACCEPTED)만 한 번씩 읽는다. 실제 로그도 `itemReads=1`, `reachedBeforeReads=1`이다. 그래서 “중복 읽기 제거”가 아니라 **T3·T4를 한 UPDATE·한 이력 묶음으로 합치는 것**이 맞는 수정이다.
- 접수는 T3 UPDATE → T4 UPDATE, T3 이력 INSERT → T4 이력 INSERT, 별도 `seat_gen` UPDATE로 왕복이 많았다. 주문 생성은 주문·항목·이력 INSERT가 세 번, 결제 시작은 시도 수 SELECT·대체 UPDATE·새 시도 INSERT가 세 번이었다.

### 시나리오 오류 16건

- 16건은 모두 `409 already-admitted`였고, 계정은 16개 모두 서로 달랐다. 같은 계정이 두 번 진입한 것이 아니다.
- 16건 모두 본구간 끝(21:13:21.879~.947)에 몰렸다.
- 원인: k6 `exec.scenario.iterationInTest`는 **시나리오별 0부터 세는 번호**다. 예열 10초×100/s는 1,000번, 본구간 100초×100/s는 10,000번이 계획인데, k6가 끝에서 몇 번을 더 돌면(진단 실행은 11,020번) 예열의 꼬리 번호가 `USERS-1-it`로 내려와 본구간의 끝 번호 `it`와 같은 사용자를 가리킨다. BAT-034 진단은 예열·본구간이 계획보다 9번씩 더 돌아 16명이 겹쳤고, 예열에서 이미 입장한 사람이 본구간 진입에서 409를 받았다.
- 수정: `loadtest/lib/v1.mjs`의 `paymentUserOf`는 예열은 뒤에서(`USERS-1-it`), 본구간은 앞에서(`it`) 세되, 계획한 반복 수(`RATE*WARM_S`, `RATE*MAIN_S`)를 넘는 꼬리 번호는 `-1`로 돌려보낸다. `pay()`는 이미 `i < 0`이면 요청을 보내지 않는다. 계획 밖 꼬리 반복만 버리고 제품 요청을 줄이는 것이 아니다. 계획+8 꼬리까지 넣은 단위 시험으로 두 범위가 겹치지 않고 꼬리가 -1이 되는지 확인했다. 제품 문제가 아니라 **측정 방법 문제**다.

## 3. 고른 수정

1. **주문 생성**: 주문 행·항목·이력 1을 한 CTE 문장으로 묶는다. Outbox는 기존처럼 마지막 업무 문장이다. 8→6문장.
2. **결제 시도 시작**: 이전 READY 대체는 순서를 지켜 별도 문장으로 두고, 시도 수 SELECT와 새 시도 INSERT를 한 CTE로 묶는다. 9→8문장.
3. **결제 접수**: T3·T4를 한 조건부 UPDATE(`event_seq + 2`, `seat_gen` 병합)와 한 `order_event` 다중 행 INSERT로 쓴다. T4 사건은 `acceptTransitions`가 만들고, Outbox는 결제 시도 UPDATE·Saga INSERT 뒤 **업무 문장의 마지막**에 쓴다. 14→11문장.
4. 250ms 연결 대기는 그대로 둔다.

줄이지 않은 것:

- 멱등 기록 4문장은 같은 트랜잭션 원자성(ADR-0146)과 락 한도 복원 때문에 유지한다.
- `itemsOf`·`reachedBeforeOf`는 T4 한 번뿐이라 없앨 중복이 없다.
- max 풀 확대(가)는 BAT-031이 32까지 재 봤지만 429가 줄지 않아 제외한다. HTTP 백프레셔(라)는 p99 4,065ms를 더 악화시킬 수 있어 이번 배치에서 제외한다.

## 4. 시험

- 단위: 주문 생성·결제 시작·접수 7파일 459건, 주문 상태 SQL 검사.
- 통합(실제 PostgreSQL): `order-writes`·`start-payment`·`order-accepts` 102건 + BAT-035 문장 수·순서 시험 1건 + BAT-034 풀 시험 2건.
- 문장 수 회귀 시험: create 6, start 8, accept 11, 접수 `itemsOf`/`reachedBeforeOf` 각 1, Outbox가 Saga INSERT 뒤·멱등 결과 UPDATE 앞.
- 시나리오: `paymentUserOf` 단위 시험(계획+8 꼬리까지 두 범위 겹침 0, 꼬리는 -1), loadtest v1 시험.
- 싼 게이트: typecheck(영향 패키지), lint, doc-check, `ledger --batch BAT-035 --require`, trace-check P-T23, records.

## 6. 위험

- CTE로 문장을 합치면 SQL 오류·잠금 차례·Outbox 마지막 규칙이 깨질 수 있다. 주문·접수 test-int의 문장 순서 시험이 막는다.
- T3·T4를 한 UPDATE로 합치면 상태 이력 두 행과 `firstInStage`가 어긋날 수 있다. 기존 주문 이력·사건 시험이 막는다.
- 문장 수를 줄여도 250ms 포화가 남으면 429가 1%를 넘을 수 있다. 그때는 (라)를 다음 배치로 제안한다.
- K7 진단은 CI 초록 뒤에만 돌린다.
