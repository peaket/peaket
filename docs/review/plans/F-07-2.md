# 기능 계획: F-07-2(주문 내역·파트너 계약 화면·수수료/보증 2인 승인)

- **무엇**: 동결 로컬 트랙의 기능 작업 목록이다(docs/architecture.md §8.6 4의 1, ADR-0354·ADR-0386). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **바탕**: 작업 폴더 `D:/ticketpass-freeze-F-07-2`, 가지 `freeze/lane5-F-07-2`, 출발 `7a75cd17a`(2026-11-24 최신 develop, ADR-0386으로 나눈 freeze 가지). 2026-11-24 작성.
- **동결 범위**: 이 기능은 ADR-0373으로 v1 완성 범위 밖이고 ADR-0386으로 `frozen-local`이다. **`develop`·`release/1.0.0`에 합치지 않고, release에 체리픽하지 않는다.** 이 가지에서만 커밋하고 `freeze/lane5-F-07-2`로 원격에 둔다. 마이그레이션·플래그는 로컬에만 둔다(ADR-0386 결정 5).
- **등급**: B다(docs/BUILD_ORDER.md F-07-2). 돈의 계산·전이를 새로 만들지 않고, 읽기 화면과 이미 있는 2인 승인 길을 화면에 잇는다. 그래도 계약 조건 변경은 돈에 닿는 승인이라 시험은 먼저 쓰고 기준 트리에서 실패를 본다(작업 지시).
- **정본**: `docs/features/transfer-refund.md` §6(계약 보증)·§11, `docs/features/settlement.md` §4.1(수수료율)·§9(수수료율·보증 변경 2인 승인)·§10(계약 기간 이력)·§13(J-T29·J-T30)·§15, `docs/frontend.md` §4.1(결제 결과·예매 확인서), `docs/design/d5-screen-blueprint.md` §5.29(SCR-055)·§7.7(SCR-046)·§7.13(SCR-065), `docs/api/openapi.yaml` `GET /v1/orders`·`GET /v1/orders/{orderId}`·`GET/POST /v1/shop/orders`·`/v1/ops/promoters/*`·`/v1/ops/approval-requests/*`, `docs/security/asvs/settlement.md`(8.2.2·8.2.3·16.3.3), ADR-0060·0062·0086·0320·0368.
- **선행**: 없음. LCH-070의 서버 몫(계약 기간 이력·2인 승인·판매 승인 때 수수료율 고정)은 BAT-615(R-719)로 이미 `develop`에 있다. F-07-5·F-07-7·F-07-8도 `develop`에 있어 이 가지에서 그대로 쓴다.

## 3. 이번에 하는 것

구현 담당 할 일은 다섯이다(I-01~I-05). 차례: I-01 → I-02 → I-03 → I-04 → I-05. 시험은 구현 전에 쓴다.

1. **I-01 포트·쓰임새**: `booking/domain/ports.ts`에 읽기 포트 `OrderHistoryReads`(목록·단건·취소 이력)와 선택 포트 `OrderSeatLabels`(좌석 이름·등급 이름)를 더한다. `booking/domain/order-history.ts`에 순수 함수를 둔다: `bookingNumberOf(orderId)`(UUID 앞 8자리 날짜 대신 주문 ID에서 만드는 13자리 표시 번호), `orderHistoryCursor`(createdAt+id), `historySummaryOf`(등급별 매수 묶기), `historyVisible`(EXPIRED 제외 규칙). `booking/application/list-orders.ts`·`get-order.ts`가 계정 대조·404·limit 검사를 맡는다.
2. **I-02 저장소·조립**: `booking/adapters/db/drizzle-order-history.ts`가 `purchase_order`·`order_item`·`order_cancellation`을 읽는다(쓰기 없음). `inventory`의 `EventSaleConfigOverlay`에 `title`·`startsAtMs`를 더하고 `LayoutSeatMap.config`·`SeatMapSaleConfigs`·`SaleConfig`에 선택 칸으로 잇는다. `LayoutSeatMap.resolve`를 `OrderSeatLabels`로 잇는 얇은 어댑터를 만든다. `BookingModuleDeps`에 `orderHistory?: { reads; seats?; clock }`를 더하고, 없으면 새 경로가 404가 되게 한다(기존 선택 쓰임새와 같은 규칙). `start.ts`에서 `DrizzleOrderHistory`·`seatMap`을 넘긴다. **마이그레이션은 만들지 않는다**(번호를 쓰지 않는다. 표를 더할 정본 결정이 없다).
3. **I-03 컨트롤러**: `OrdersController`에 `GET /v1/orders`(팬, 커서·limit)와 `GET /v1/orders/{orderId}`(팬)를 더한다. 응답 모양은 openapi `OrderSummaryPage`·`OrderDetail`을 따르고, 정본에 원천이 없는 선택 칸(`placeName`·`seller`·`payment`)은 싣지 않는다. 두 경로 모두 `Cache-Control: private, no-store`, 404는 남의 주문과 없는 주문을 가리지 않는다. 인증은 `@Roles(['fan'])`와 플랫폼 팬 쿠키를 쓴다.
4. **I-04 SCR-055 화면(목록 몫)**: `apps/web/src/_pages/orders/model/live.ts`(두 목록 합치기·부분 실패·배지)와 `ui/LiveOrders.tsx`를 만든다. `listOrders`·`listShopOrders`를 `Promise.allSettled`로 부르고, API가 설정되지 않은 프리뷰에서는 지금 목업을 그대로 둔다. 굿즈 왕복은 정본이 "한 커서로 묶지 않는다 [가정]"이므로 화면이 두 목록을 `createdAt`으로 합친다. **상세 경로(`getOrder`·`getShopOrder`)와 굿즈 취소·반품 버튼은 다음 몫이다**(AC-06).
5. **I-05 SCR-046 계약 승인 카드**: `apps/console-host/src/pages/cs-approvals/model/contract-approval.ts`(승인 가능 역할·요청자 본인 판정·현재 값↔바꿀 값 줄·오류 문구)와 `ui/ContractApprovalCard.tsx`를 만든다. `GET /v1/ops/approval-requests?kind=CONTRACT_TERMS_CHANGE`로 대기 목록을, 상세로 `contractTerms`를 읽고, `POST /v1/ops/approval-requests/{approvalId}/approvals`(재인증 토큰) 또는 `.../rejections`(사유)를 부른다. SCR-065 계약 탭에 "승인 대기"에서 이 카드로 가는 링크를 더한다. 카드가 목록에 나타나는 조건은 `kind === 'CONTRACT_TERMS_CHANGE' && status === 'PENDING_APPROVAL'`이다.

**② 주문 조회 소유권**

- **확인했으나 문제 없음**: 목록은 `purchase_order.account_id = 세션 계정`으로 좁히고, 상세는 주문을 읽은 뒤 `order.accountId !== me.accountId`면 404다. 없는 주문·UUID가 아닌 주문·남의 주문이 모두 같은 `not-found` 본문이고(ORD-HIST ②), 응답에 존재 여부를 싣지 않는다. 두 경로에 `@Roles(['fan'])`가 붙고, 처리 전에 `Cache-Control: private, no-store`를 단다. 카드·계좌 원문을 고르는 칸이 없다.
- **지적**: IR-02(계정 묶음). 상세는 주문 ID로 먼저 읽고 계정을 앱에서 대조하므로, 다른 계정의 주문 행을 메모리에 읽기는 한다. 응답에는 싣지 않아 정보 노출은 없지만, SQL에서 `account_id`까지 걸러 읽는 편이 방어에 낫다.

**③ 커서·limit·EXPIRED·좌석/등급 이름·공연명/회차**

- **확인했으나 문제 없음**: 목록 SQL의 `(created_at, id) < (커서)` 키셋과 `order by created_at desc, id desc`가 같은 방향이다. 어댑터는 `limit+1`을 받고 `orderHistoryPageOf`가 자른다. `limit`은 계약 스키마가 1~100을 검사해 0·101·`abc`가 400이다(ORD-HIST ④). EXPIRED는 SQL과 쓰임새 두 곳에서 빼고 실패·결과 불명·입금 대기는 남긴다(ORD-HIST ①). 좌석 이름은 `LayoutSeatMap.resolve`, 등급 이름은 판매 설정 `tierNames`에서 오고 없으면 좌석 ID·등급 ID로 떨어진다(ORD-HIST ③⑤). 공연명·회차 시작은 지금 판매 설정 사본의 `title`·`startsAtMs`를 표시용으로만 읽는다(RV-02, 금액·계약에는 쓰지 않는다). 상세의 `entryOpensAt`도 같은 사본에서 읽는다.
- **지적**: IR-03(깨진 커서가 500), IR-04(발권 지연 판정), IR-11(포트 주석의 정렬 방향).

**④ 계약 승인 카드**

- **지적**: IR-01(높음, 승인·반려가 모든 요청에서 잠김), IR-06(`kind` 필터가 서버에서 무시됨), IR-09(목록 읽기 실패를 숨김), IR-10(파트너 이름 대신 ID).
- **확인했으나 문제 없음**: `contractRowsOf`가 10,000bp=100%로 현재 값과 바꿀 값을 나란히 보이고 바뀐 칸만 강조한다(CON-APR ①). 반려 사유는 비었거나 1,000자를 넘으면 보내지 않고, 서버의 2,000자 상한 안이다(CON-APR ④). 승인은 `ReauthDialog`의 기본 `act=APPROVAL` 토큰을 `x-reauth-token`으로 붙여 `POST .../approvals`로만 나가고, 반려는 `POST .../rejections`로만 나간다. 요청자 본인 판정 함수 자체는 역할·상태·계정을 차례로 보고 정본 문구를 낸다(CON-APR ②). 서버의 요청자 403·409·재인증 검증은 기존 J-T29가 덮는다.
- **주의**: 카드는 계획과 달리 상세(`GET /v1/ops/approval-requests/{approvalId}`)가 아니라 목록의 `contractTerms`를 쓴다. 지금 서버 목록이 그 칸을 실어 동작하지만, 목록에서 빠지면 `if (!terms) return null`로 카드가 조용히 사라진다. 계약이 바뀌면 상세를 읽도록 다시 본다.

**⑤ 화면 조립**

- **확인했으나 문제 없음**: `LiveOrders`가 두 경로를 `Promise.allSettled`로 부르고, 한쪽만 실패하면 그 목록만 빼고 `partialFailureNotice` 문구를 보인다(WEB-ORD ③). 둘 다 실패하면 오류 상태와 [다시 시도], 401이면 로그인 안내를 보인다. 로딩 스켈레톤·빈 목록은 `OrderHistoryTabs`가 맡고, API 주소가 없는 프리뷰는 기존 목업을 그대로 그린다(WEB-ORD ④). `liveRows`는 `createdAt` 내림차순, 같으면 주문 ID 내림차순으로 섞는다(WEB-ORD ①).
- **지적**: IR-05(실주문 링크가 목업 상세로 가 404), IR-07(입금 대기 가상계좌 정보 없음), IR-08(FAILED를 모두 '입금 오류'로 표시).
- **남는 것**: 두 API 모두 첫 100건만 읽고 더 보기·커서가 없다. d5에 목록 페이지 규칙이 없어 이번 범위에서 정하지 않았지만, 100건을 넘는 사용자는 오래된 주문을 볼 수 없다.

**⑥ 시험이 덮지 않는 곳**

- **Docker 통합을 돌리지 않았다**: 새 어댑터의 SQL(계정·EXPIRED 필터, `order by created_at desc, id desc`, `order_item`·`order_cancellation` 조인)과 실제 키셋 페이지네이션을 PostgreSQL에서 확인하지 않았다. HTTP 시험의 `FakeHistory`는 메모리에서 정렬하므로 SQL의 정렬·인덱스·캐스트 오류를 잡지 못한다. 이 공백은 남는 위험으로 둔다.
- **화면을 실행하는 시험이 없다**: `WEB-ORD ④`와 `CON-APR ⑥`은 소스 문자열만 본다. 그래서 IR-01(카드 자격 계산)처럼 컴포넌트가 조립되는 순간의 결함이 초록불을 통과했다. 브라우저 확인도 하지 않았다.
- **어댑터 연결 시험이 없다**: `overlayOf`의 `title`·`startsAtMs` 추가와 `LayoutSeatMap.config`·`SeatMapSaleConfigs`·`LayoutOrderSeatLabels`의 이름 맞추기는 회귀 시험 `core-sale-configs`의 기대 값 한 줄 말고는 직접 보는 시험이 없다. 필드 이름이 하나 틀려도 HTTP 시험은 가짜 `configs`를 써서 통과한다.
- **정본에 원천이 없는 칸**: `placeName`·`seller`·`payment`·`compensation`은 이번 응답에 없고(계획 RV-01), `virtualAccount`는 늘 null이다. 상세 화면의 판매자 고지·결제수단·배상 줄은 다음 몫이다.
- **넘긴 몫**: SCR-055 상세(`getOrder`·`getShopOrder`)와 굿즈 취소·반품(AC-06), SCR-065 '승인 대기'에서 이 카드로 가는 링크는 계획 §11대로 아직 없다. `bookingNumber`는 UUIDv7 주문만 시험했고, UUIDv4·잘못된 ID의 14자리 가능성은 시험하지 않았다.

**확인했으나 문제 없음**

- 남의 주문·없는 주문·UUID가 아닌 주문이 모두 같은 404 `not-found`이고, 응답에 주문 존재 여부나 계정 원문을 싣지 않는다(ORD-HIST ②).
- 두 경로 모두 `@Roles(['fan'])`이고 `Cache-Control: private, no-store`를 단다. 401은 인증 가드가 먼저 낸다.
- `limit` 1~100, 커서 왕복, EXPIRED 제외, 티켓 없는 주문 포함, `createdAt` 내림차순은 시험과 코드가 맞는다(ORD-HIST ①④).
- `bookingNumber`는 정상 UUIDv7 주문에서 늘 같은 13자리이고 KST 날짜 8자리를 쓴다(ORD-HIST ①).
- 상세의 등급별 매수·좌석 줄·입장 시작·취소 이력·좌석/등급 이름 폴백이 정본 모양과 맞는다(ORD-HIST ③⑤).
- 두 목록 `Promise.allSettled`, 부분 실패 문구, 로딩·오류·빈 목록, 프리뷰 목업 폴백이 있다(WEB-ORD ①~④).
- 계약 값 10,000bp=100% 표시, 바뀐 칸 강조, 반려 사유 필수, 재인증 승인 경로, 요청자 본인 판정 함수 자체는 맞다(CON-APR ①~⑤).
- 마이그레이션을 만들지 않았고, 이 기능 커밋은 `freeze/lane5-F-07-2`에만 있다. 장부 `--require`도 통과한다.

**판정**

- **미완료.** 높음 IR-01이 AC-07·AC-08을 막고, 통과 기준 IR-02·IR-03이 남는다. IR-01·IR-03은 이 freeze 가지에서 시험을 먼저 고친 뒤 구현을 고친다. IR-02는 identity-svc 계정 묶음 계약과 정본 결정이 필요해 이 가지에서 닫을 수 없다(감독 결정). IR-04~IR-11은 `docs/lanes/lane5-cleanup.md`의 F-07-2 절로 넘겼다.
- **남는 위험**: Docker 통합을 돌리지 않아 새 어댑터 SQL·정렬·키셋·조인을 실제 PostgreSQL에서 확인하지 않았다. 브라우저 확인도 하지 않아 화면의 실제 동작(특히 IR-01)은 시험으로만 보았다. 다음 몫에서 Docker 통합과 화면 확인을 먼저 한다.

- **AM-T9 상세**: `merged_account`의 A·B 두 행이 모두 대표 C이고, `accountIdsOf(A/B/C)`는 코드상 대표 먼저 `[C, A, B]`다. C·A·B 각각의 `history.list`가 `[C주문, B주문, A주문]`을 주고, `history.find`가 A·C 주문을 찾으며, 묶음 밖 주문은 목록에 없다. AM-T5~T8(같은 사건 두 번 1행, 한 단계 양방향, 묶음 밖 미노출, 섞인 키셋 커서·정렬)도 5/5 안에서 그대로 통과했다.
- **기준 트리 확인**: 구현 담당 기록은 "구현 stash 상태에서 AM-T9 1개 실패·4개 통과"다. 이번 세션은 기준 트리를 다시 실행하지 않았지만, 9a1e10db2의 `record`(`do nothing`)·`accountIdsOf`(한 단계)와 새 AM-T9의 단언(양쪽 행 C, `accountIdsOf` C, C 목록에 A)을 코드로 대조하면 AM-T9만 실패하고 AM-T5~T8은 통과하는 것과 맞다. **직접 기준 실행은 하지 않았다**는 점을 남긴다.
- **확인했으나 문제 없음**: `record`는 트랜잭션 하나에서 최종 대표를 정하고 insert/update를 함께 한다. 새 대표가 이미 흡수된 계정이면 `finalRepresentative`가 최종 대표를 주므로, 뒤바뀐 순차 처리(B→C 다음 A→B)도 A→C로 접힌다. `accountIdsOf`의 재귀 조회는 A·B를 조회할 때 C를 찾는 방어로 맞다.
- **남은 위험**: ① `accountIdsOf(C)`는 `representative_account_id = C`인 직접 행만 모으므로, `record`의 접기가 실패한 비정상 표(A→B가 남은 표)에서는 C가 A를 놓친다. 재귀 조회는 위로 올라가는 방어이고, 아래로 내려오는 낡은 사슬을 모으지는 않는다. ② A→B와 B→C가 **다른 키**로 동시에 처리되면 `record`에 사슬 잠금이 없어 경합할 수 있다(AM-T9는 순차 처리만 본다). 정본은 사건 순서를 보장하지 않고, 계획 §11도 이 점을 남은 위험으로 적었다. ③ AM-T9는 `accountIdsOf`를 정렬해 집합만 단언하므로 `[C, A, B]` 순서는 시험이 고정하지 않는다(코드는 대표 먼저). ④ 브라우저 확인은 여전히 하지 않았다.
