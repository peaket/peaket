# FIX-agrade-impl-review 계획 — A등급 코드 기능은 구현 뒤 리뷰를 한다(ADR 0381)

- 기능 ID: FIX-agrade-impl-review(기능 표 밖의 고침, 갈래 감독)
- 가지: `coord/FIX-agrade-impl-review`(기준 `origin/develop` = `b6a3077a7`), 작업 폴더 `D:/ticketpass-coord-agrade`
- 근거: 소유자 결정(2026-11-23, 이 세션에서 소유자가 직접 고름), [ADR-0372](../../adr/0372-tdd-frozen-tests-no-post-impl-review.md) '결과' 절의 잃는 점, [ADR-0270](../../adr/0270-independent-agents-per-role-test-first.md) 맥락(웨이브 6 독립 감사의 높음 23건), [docs/architecture.md](../../architecture.md) §8.6 4 '자주 놓친 결함'(BAT-020·022·195)
- 종류: 문서 기능(계획 → 작성 → 리뷰, §8.6 '역할 나누기'의 '문서만 고치는 기능'). 시험 대신 문서 점검을 돌린다.
- 등급: B(진행 절차)
- 표기: 새 ADR은 번호 0381이다(감독 결정 2026-11-23, 5절). 이 계획은 ADR 파일이 생기기 전에 커밋되므로 문서 점검의 ID·경로 검사에 걸리지 않게 'ADR 0381'(붙임표 없이)로 적는다. 작성 담당은 정본과 ADR에 붙임표를 넣은 보통 꼴로 쓴다(아래 따옴표 안의 문장도 같다).
- 말 풀이: '구현 리뷰'는 구현이 고정된 시험을 통과한 뒤, 구현을 맡지 않은 리뷰 담당이 구현 코드의 바뀐 부분을 읽고 결함을 찾는 일이다. '시험 리뷰'는 ADR-0372 결정 2의 구현 전 리뷰다. 꼬리말은 커밋 메시지 끝의 `키: 값` 줄이다.

## 1. 정한 것

소유자 결정 1~4(지시서)는 그대로 옮기지 않고 따른다. 아래는 지시서가 계획 담당에게 맡긴 세부다. 모두 정본에 없는 작은 세부라 추천안으로 정했다.

### 1.1 구현 리뷰의 자리와 차례 (추천 적용, 2026-11-23)

- 대상은 A등급 코드 기능뿐이다. A등급이라는 표시는 계획 커밋 꼬리말 `Batch-Grade: A`다(소유자 결정 3). 꼬리말이 없는 기능은 ADR-0372·ADR-0373 그대로다.
- A등급 코드 기능의 차례: 계획 → 시험 → 시험 리뷰 → (지적 반영) → 시험 고정 → 구현 → **구현 리뷰 → (지적 반영) → 고친 곳 다시 보기** → 게이트 → 기록·합치기.
- 구현 리뷰는 구현 담당이 고정된 시험을 모두 통과시키고 계획 파일 '시험 결과' 절을 적은 뒤에 시작한다. 시험이 빨간 구현은 리뷰하지 않는다.
- 게이트(§8.6 4의 8)는 구현 리뷰 지적 반영이 끝난 뒤 한 번만 돈다. 합치기 직전 통합 시험 전체를 두 번 돌리지 않으려는 것이다.
- 한 바퀴만 돈다. 지적을 고친 뒤 리뷰 담당은 고친 곳만 다시 본다(시험 리뷰와 같다, §8.6 4의 5).
- 정방향 기능(`Batch-Order: impl-first`)이 A등급이면, 이미 시험이 있으므로 같은 차례로 구현 리뷰를 한다. 시험만 기능(`Batch-Kind: test-only`)과 문서 기능에는 `Batch-Grade`를 달지 않는다(구현이 없다).

### 1.2 리뷰 담당이 받는 것과 받지 않는 것 (추천 적용, 2026-11-23)

- 받는 것
  - 구현의 바뀐 부분: `git diff <시험 고정 커밋>..<구현 끝 커밋>`(시험 고정 커밋은 구현 전 마지막 시험 리뷰 커밋). 고정된 시험 파일은 읽기만 한다.
  - 지시서, 계획 파일 전체(시험 리뷰 절·실패 확인·시험 결과 포함), 장부(`node tools/ci/ledger.mjs --batch <기능>`), 정본의 지시서가 가리킨 줄 범위, 그 기능의 ASVS 추적 표(`docs/security/asvs/<기능>.md`)
- 받지 않는 것: 구현 담당의 설명·보고·대화, 감독이 요약한 코드 설명(§8.6 '역할 나누기'의 '파일로만 넘긴다'와 같다).
- 할 수 있는 것: 읽기, 이미 있는 시험과 읽기 전용 명령(시험 실행, 쿼리 계획 보기 같은 것)을 돌리기.
- 하지 않는 것: 코드·시험·정본을 고치지 않는다. 바꾸는 파일은 계획 파일 '리뷰' 절의 '구현 리뷰' 하위 절과 담당 표 자기 줄뿐이다. 틀린 구현을 넣어 보는 검사(옛 검증)는 하지 않는다(ADR-0372 결정 3의 '검증 없앰'은 그대로).
- 세션: 같은 기능의 시험 리뷰 담당과 다른 새 세션으로 띄운다. 시험 리뷰의 결론에 끌려가지 않게 하려는 것이다. 모델은 Opus 5.5 새 맥락, 생각 강도는 지금 강도다(§8.6 '읽는 양 줄이기').

### 1.3 결과를 적는 계획 파일 절 (추천 적용, 2026-11-23)

- A등급 코드 기능의 계획 파일은 `## 리뷰` 절 아래에 하위 절 둘을 둔다: `### 시험 리뷰`, `### 구현 리뷰`.
- 따로 `## 구현 리뷰` 절을 두지 않는 까닭: 지금 `roles-check.mjs`는 리뷰 커밋이 '리뷰' 절(하위 제목 포함)을 바꿔야 리뷰 커밋으로 센다(§8.6 '리뷰·검증 커밋의 내용'). 하위 절이면 지금 도구로도 센다.
- 지적 번호: 시험 리뷰는 지금처럼 `RV-NN`, 구현 리뷰는 `IR-NN`(구현 리뷰)으로 가른다. 리뷰 반영 커밋의 `Finding:` 값과 재현 시험 이름(예 `F-07-8 IR-01 ①`)에 그대로 쓴다.
- '구현 리뷰' 하위 절의 꼴: 지적 표(번호·등급(높음·중간·낮음)·종류(보안·통과 기준·그 밖)·자리(파일:줄)·내용·정본 근거), '확인했으나 문제 없음' 목록(아래 1.5의 관점마다 한 줄), '판정'(합쳐도 되는지 한 줄), 지적 반영 뒤 '다시 보기'(고친 곳만).

### 1.4 커밋 역할과 꼬리말 (추천 적용, 2026-11-23)

- 구현 리뷰 커밋도 `Role: review`다. 새 역할 값을 만들지 않는다. 지금 `roles-check.mjs`는 역할 목록 밖의 `Role` 값을 실패로 잡기 때문이다.
- 시험 리뷰와 구현 리뷰는 꼬리말 `Review-Of: test|impl`로 가른다. 리뷰 커밋에만, 하나, 값은 소문자 그대로다. `Batch-Grade: A` 기능의 리뷰 커밋에는 꼭 단다. 그 밖의 기능에는 달지 않는다.
- `Batch-Grade: A`: 계획 커밋에만, 한 커밋에 하나, 값은 대문자 `A` 그대로다(`Batch-Order`·`Batch-Kind`와 같은 방식). B·C 값은 두지 않는다(꼬리말이 없으면 A가 아닌 것으로 본다).
- 지금 `roles-check.mjs`는 모르는 꼬리말 키를 넘어가므로(`readTrailers`, 2026-11-23 확인) 두 꼬리말을 달아도 지금 검사가 깨지지 않는다.
- 꼬리말 덩이에서는 `Role` 바로 뒤에 둔다(예 `Role: review` 다음 줄 `Review-Of: impl`).

### 1.5 구현 리뷰가 보는 것 (추천 적용, 2026-11-23)

정본 값은 옮겨 적지 않고 자리만 가리킨다. 리뷰 담당은 관점마다 '지적' 또는 '확인했으나 문제 없음' 한 줄을 남긴다.

1. 판정 기준과 구현의 대조: 장부 범위 항목마다 정본 판정 기준을 구현이 실제로 지키는지 본다. 시험이 통과해도 구현이 틀릴 수 있는 곳(시험이 값을 덜 단언한 곳)을 먼저 본다.
2. A 대상 불변식(늘 참이어야 하는 조건): §8.6 3 위험 등급 표의 A 행(돈 합계, 좌석 수, 대기 순번)과 그 기능 장부 범위의 정본. 같은 좌석이 두 번 팔리는 오버셀, 이중 결제, 순번 건너뜀·겹침이 생길 길이 있는지, 시험 뒤 대조 도구 `services/invariant-checker`가 세는 항목과 어긋나지 않는지 본다.
3. 동시 실행·되돌림·장애 경로: §8.7의 실패 목록 셋(경합은 data.md §5, 외부 호출은 api/guidelines.md §8·§8.1·§5, 자원 한도는 verification.md §4·§4.1)에 적힌 동작을 구현이 따르는지, 트랜잭션 경계와 발행 대기 표(Outbox) 쓰기가 한 트랜잭션인지, 되돌림이 건드린 키·행을 모두 되돌리는지.
4. 멱등(같은 요청을 여러 번 보내도 한 번 처리한 것과 같은 결과): api/guidelines.md §4 '멱등성 키'와 그 기능 정본. 재시도·중복 이벤트·순서 바뀐 이벤트에서 결과가 같은지.
5. 시험이 덮지 않는 곳: 보안 설정(§8.3 보안 기본 원칙, 그 기능 ASVS 추적 표의 적용 행), 로그·오류 응답의 개인정보(docs/planning/03-policies-glossary.md §1.2 POL-023 개인정보 처리 표), 쿼리·Lua(Redis 안에서 도는 짧은 스크립트) 성능(인덱스, 한 요청의 쿼리 수, Lua가 훑는 키 수. Lua·빠른 경로를 바꿨으면 §8.6 4의 7 비교).
6. '자주 놓친 결함' 목록(§8.6 4): 목록의 모양마다 이 구현에 해당하는지 본다. 특히 겹친 가드(BAT-195), 부르는 쪽이 판정 결과를 실제로 쓰는지(BAT-022), 시간 한도·상수(BAT-020), 시작 파일 조립(BAT-195).

### 1.6 지적 처리 (추천 적용, 2026-11-23)

- 그 기능에서 고치는 것: 높음, 보안, 통과 기준(판정 기준을 어김) 지적만이다(§8.6 첫머리의 ADR-0331 줄, ADR-0331 결정 5). 나머지(중간·낮음)는 갈래 정리 목록(`docs/lanes/lane<N>-cleanup.md`)에 한 줄씩 넘긴다.
- 고치는 차례는 버그와 같다(§8.6 5, ADR-0372 결정 3): 시험 담당이 재현 시험을 먼저 쓰고 실패를 본다(`Role: review-fix`, `Fix-By: test`, `Finding: IR-NN`) → 시험 리뷰 담당이 그 재현 시험만 짧게 본다(`Role: review`, `Review-Of: test`) → 구현 담당이 고친다(`Role: review-fix`, `Fix-By: impl`, `Finding: IR-NN`) → 구현 리뷰 담당이 고친 곳만 다시 본다(`Role: review`, `Review-Of: impl`).
- 시험으로 재현할 수 없는 지적(설정 값, 쿼리 계획, 로그 문구처럼 시험이 단언하기 어려운 것): 구현 리뷰 담당이 '구현 리뷰' 절의 그 지적에 '시험 없음'과 까닭 한 줄을 적는다. 구현 담당이 `Fix-By: impl`로 바로 고치고, 감독이 기록 커밋 본문에 예외로 적는다(F-03-1 기록의 감독 예외와 같은 꼴). 시험으로 재현할 수 있으면 이 예외를 쓰지 않는다.
- 고친 뒤 다시 보기에서 새 높음·보안·통과 기준 지적이 나오면 같은 차례를 한 번 더 한다. 세 바퀴째가 필요하면 감독이 멈추고 소유자에게 묻는다.

### 1.7 진행 중인 A 기능에 쓰는 때 (추천 적용, 2026-11-23)

- 이 문서 기능이 `develop`에 합쳐진 때부터 쓴다.
- 새로 시작하는 A등급 코드 기능: 첫 계획 커밋에 `Batch-Grade: A`를 단다.
- 이미 시작했지만 아직 `develop`에 합치지 않은 A등급 코드 기능(구현 전·구현 중·구현 끝 모두): 합치기 전에 구현 리뷰를 한다. 그 기능의 계획 담당(같은 역할이면 새 세션도 된다)이 계획 커밋 하나를 더한다. 그 커밋은 계획 파일 '리뷰' 절에 `### 시험 리뷰`(이미 있는 시험 리뷰 내용을 그 아래로 옮긴다)와 `### 구현 리뷰`(빈 줄 대신 '구현 리뷰 담당이 채운다' 한 줄)를 두고, 꼬리말 `Batch-Grade: A`를 단다. 이미 한 시험 리뷰 커밋에 `Review-Of`를 소급해 달지 않는다(커밋을 고쳐 쓰지 않는다). 그 뒤의 리뷰 커밋부터 단다.
- `Batch-Order`와 달리 `Batch-Grade`는 구현 뒤의 계획 커밋에 달아도 된다. 일을 늦게 무겁게 하는 표시라서 차례를 피하는 데 쓸 수 없기 때문이다.
- 이미 `develop`에 합친 A 기능(예: F-02-1·F-02-2·F-07-5)은 소급해 구현 리뷰를 하지 않는다. 구간 마무리(SEG)의 관점별 새 맥락 리뷰(§8.6 4의 5)가 맡는다.
- 2026-11-23 기준 대상 후보: 기능 표 등급 A이고 상태가 `대기`인 F-05-2~F-05-6, F-06-7, F-07-6~F-07-8. 기능 표 상태는 갈래가 바꾸므로 감독이 적용할 때 다시 본다.

### 1.8 완성 기간(ADR-0373)과의 관계 (추천 적용, 2026-11-23)

- 2026-11-23~12-03 동안에도 A등급 코드 기능은 구현 리뷰를 한다. ADR-0373 결정 3의 'A등급: ADR-0372 그대로' 줄에 구현 리뷰가 더해진다. B·C 기능과 분석 적재 빠른 길은 그대로다.
- 합치기를 막는 것: 구현 리뷰가 없거나, 높음·보안·통과 기준 지적이 열려 있으면 합치지 않는다. 이 둘은 감독의 손 확인(아래 2.2의 ⑦)으로 본다.
- 합치기를 막지 않는 것: ADR-0373 결정 3대로 `roles-check.mjs`의 차례·구성 실패는 그대로 막지 않는다. 시험 없음 예외(1.6)도 기록에 적고 합친다.
- 넷째 날(2026-11-26)의 빼는 차례(ADR-0373 결정 4)는 그대로다. 기한이 모자라도 감독이 구현 리뷰를 빼지 않고, 빼야 하면 소유자에게 묻는다. 기간이 끝난 뒤에도 이 결정은 그대로다.

## 3. 나중 기능 메모: roles-check 자동 검사

- 기능 ID(가칭): `FIX-roles-agrade`. 종류는 코드 기능(진행 도구, 등급 B). `FIX-roles-tdd`(같은 `tools/ci/roles-check.mjs`·`roles-check.test.mjs`를 고친다)를 `develop`에 합친 뒤 시작한다. 먼저 하면 같은 파일이 충돌한다(소유자 결정 4).
- 초안이 FIX-roles-tdd가 합친 규칙과 어긋나면 그 규칙이 이긴다.
- 검사할 규칙 초안
  - 꼬리말: `Batch-Grade`는 `plan` 커밋에만, 한 커밋에 하나, 값은 `A` 그대로. 어기면 `[꼬리말]` 실패이고 밝힌 것으로 세지 않는다. `Review-Of`는 `review` 커밋에만, 하나, 값은 `test`·`impl`. `Batch-Grade: A` 기능에서 그 꼬리말을 단 첫 계획 커밋 뒤의 리뷰 커밋에 `Review-Of`가 없으면 실패다(그 앞의 리뷰 커밋은 보지 않는다, 1.7).
  - 구성: `Batch-Grade: A`는 코드 기능(시험 먼저 또는 `Batch-Order: impl-first`)에만 단다. `Batch-Kind: test-only` 기능과 문서 기능(`doc` 커밋이 있음)에 있으면 `[구성]` 실패다. `Batch-Grade: A` 기능에는 `Review-Of: impl` 리뷰 커밋이 하나 이상 있다. 출력의 묶음 종류 이름에 등급을 붙인다(가칭 `코드(A)`).
  - 차례: 첫 `Review-Of: impl`은 첫 구현 커밋 뒤다. 마지막 `Review-Of: impl`은 마지막 코드 고침 커밋(구현, `Fix-By: impl`. 바꾼 파일이 모두 `.md`인 것은 뺀다) 뒤다. 시험 고정 규칙(시험 파일을 바꾼 마지막 시험 쪽 커밋 뒤의 리뷰 커밋)은 `Batch-Grade: A` 기능에서는 `Review-Of: test` 리뷰 커밋으로만 채운다. `Finding`마다 시험 쪽 먼저라는 지금 규칙은 그대로이고, '시험 없음' 예외(1.6)는 감독이 본다.
  - 계획 파일 절: `Batch-Grade: A` 기능의 '리뷰' 절에 하위 절 '시험 리뷰'·'구현 리뷰'가 있고 비지 않는다. `Review-Of: impl` 커밋은 '구현 리뷰' 하위 절을, `Review-Of: test` 커밋은 '시험 리뷰' 하위 절을 바꿔야 그 리뷰 커밋으로 센다(지금의 '리뷰 커밋의 내용' 비교를 하위 절로 좁힌다).
  - 세션: `Review-Of: impl` 커밋의 세션은 같은 기능의 `Review-Of: test` 커밋 세션과 다르다. 담당 표에는 두 세션이 모두 `review` 역할로 있다.
