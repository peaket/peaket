# 기능 계획: F-02-7(런북 CLI KMS 서명 묶음 전송·받는 쪽 검증)

- **진행**: 계획·시험(정적·서명 계약) 완료, 기준 트리 실패 확인, **리뷰 준비**(2026-11-28). 리뷰는 계획·시험을 맡지 않은 새 세션이 맡는다. 리뷰 반영 뒤 구현·문서·기록으로 간다. 구현은 아직 시작하지 않았다.
- **무엇**: BUILD_ORDER '기능 단위 계획' F-02-7(갈래 2 동결 트랙, 등급 A, OPS-310, WBS 2.00일, 장부 범위 `C-T7, C-T13, C-T28, control-tower:v5.0.0-4.1.5, control-tower:v5.0.0-16.3.3, control-tower:v5.0.0-16.5.2`)의 작업 목록이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **쉬운 말**: 관제 서버(ops-svc)가 멈춘 비상 상황에서도 운영자는 클러스터 안 비상 Job의 `peaket-runbook` CLI로 판매 일시정지·재개, 입장 일시정지·재개, 자동 제어 정지·재개, 대체 결제사 전환/해제를 낼 수 있어야 한다. 명령은 운영자 두 명(또는 정해진 한 명)의 KMS 서명을 묶어 받는 쪽에 보내고, 받는 쪽(admission-ctrl·purchase-svc·queue-svc·payment-svc)은 서명·역할·유효 시간·이미 쓴 명령 ID를 확인한 뒤에만 적용한다. 이번 동결 로컬 범위는 **실제 AWS KMS·S3를 부르지 않고 포트·가짜·정적 계약으로 그 길을 확인하는 데까지**다. 실제 KMS·S3 Object Lock·클러스터 배포는 `미실행`이고 `[가정]`이다.
- **바탕**: 작업 폴더 `D:/ticketpass-freeze-F-02-7`, 가지 `freeze/lane2-F-02-7`, 출발 `origin/develop` = `75771324e`(2026-11-24). F-02-1·F-02-2는 이 기준에 이미 합쳐져 있다(`ControlDispatcher`, 네 서비스의 `ApplyControl` 받는 쪽, `control.proto`의 `RunbookBundle`). F-02-6(명령 4 WAF·명령 6 진입/상태 Degraded·S3 사본·RB-03/04)은 다른 작업 폴더 `D:/ticketpass-freeze-F-02-6`에서 같은 기준으로 동시에 진행 중이다.
- **동결 로컬 범위**: ADR-0386 결정 4·5. `develop`·`release/1.0.0`·`main`에 합치거나 체리픽하지 않는다. 출시 마이그레이션 목록·출시 환경 값(`deploy/envs/{demo,staging,prod}`)·출시 플래그에 넣지 않는다. 이 가지에서만 포트·가짜·정적 시험·런북 글을 만든다. 실제 AWS API 호출, KMS 서명, S3 Object Lock 쓰기, Job 배포, 메시 정책 적용은 이번 턴 `미실행`·`[가정]`이다.
- **차례(동결 지시 2026-11-28)**: A등급이므로 **계획 → 시험(정적·서명 계약) → 시험 리뷰(새 세션) → 반영 → 구현 → 구현 리뷰(새 세션) → 반영 → 검증 → 기록**이다(ADR-0372·ADR-0381). 이번 턴은 계획·시험을 끝내고 기준 트리 실패를 확인한 뒤 리뷰 준비에서 멈춘다.
- **수치 주장 금지**: 이 계획과 시험은 `30k/s`·`30,000건/초`·`100만`·K1/K2/K7 0을 주장하지 않는다. 인용할 수 있는 것은 F-08-5 `무효·미측정`, F-08-9 `판정 못 함(무효·부분)`, F-08-10 `미측정`뿐이다. C-T13의 p99 ≤ 10초도 이 동결 로컬 범위에서는 **미측정**이며, 경로가 ops-svc를 거치지 않는다는 것만 시험한다.
- **한 줄 결론**: 지금 `runbook_bundle`은 계약에만 있고 네 받는 쪽은 그 칸을 읽지 않으며, `peaket-runbook`은 RB-35 셔플만 대기열 Redis에 넣는다. 이 기능은 (a) 정규화·서명·역할·재생을 확인하는 공용 묶음 검증기, (b) 네 받는 쪽의 적용 전 관문, (c) 제어 명령을 직접 보내는 CLI와 감사 sink, (d) ack 시간 초과 명령의 런북 한 줄을 놓고, 실제 KMS·S3는 포트와 가짜로만 확인한다.

## 2. 감독에게

올린 것에 대한 답은 아직 없다. 아래는 이 계획이 정한 추천안이며, 다르게 정하면 계획·시험을 고친다.

1. **묶음 모양은 `requests` 지도(추천 적용, 2026-11-28)** — `canonical_bundle`은 `{v:1, commandId, kind, scope, version, reason, issuedAt, expiresAt, requests}`이다. `requests`는 받는 서비스 이름마다 그 서비스가 받을 바라는 상태 객체다. 명령 3 판매 일시정지는 세 서비스(purchase-svc·admission-ctrl·queue-svc)가 같은 `{paused:true}`를, 명령 6 대체 결제사 전환은 payment-svc의 `{switched:true,toPg}`와 admission-ctrl의 `{switched:true,pgKey,pgTps}`처럼 **서비스마다 다른 값**을 받기 때문이다. 버린 안: 서비스마다 따로 서명한 묶음(한 논리 명령이 여러 `commandId`가 되어 재생·2인 정책이 갈린다).
2. **판 번호는 `issuedAt`(밀리초)(추천 적용, 2026-11-28)** — ops-svc가 멈췄을 때 원장(`control_version`)을 읽을 수 없으므로, CLI가 만든 시각을 판으로 쓴다. F-02-1의 규칙 `max(마지막+1, 보낸 시각 ms)`와 같은 눈금이라, 복구 뒤 ops-svc가 더 늦은 시각으로 보내면 자연히 더 큰 판이 된다. 한계: 같은 범위·종류에 런북과 ops-svc 명령이 같은 밀리초에 겹치면 판이 같아 뒤 명령이 무시될 수 있다. 그때는 1ms 뒤 다시 만든다(`[가정]`). 버린 안: 판을 0이나 1로 고정(낡은 판이 되어 적용되지 않는다), 시각×1000(이후 ops-svc 판보다 커져 영원히 앞선다).
3. **CLI가 다루는 명령 아홉(추천 적용, 2026-11-28)** — `sale-pause`(명령 3 정지, commander 1명)·`sale-resume`(명령 3 재개, commander 2명)·`admission-pause`(명령 2, 운영자 2명)·`admission-resume`(운영자 2명)·`automation-stop`(명령 11 정지, 운영자 2명)·`automation-resume`(운영자 2명)·`pg-switch`(명령 6 대체 결제사 전환)·`pg-switch-off`(명령 6 해제)·`entry-pause-release`(명령 6 새 결제 진입 정지 해제). 명령 1(동시 입장 목표)은 올리는 방향도 있어 비상 런북에서 빼고, 명령 7(대기실 공지)은 승인 템플릿 글을 싣는 꼴이 아직 없어(F-03-5) 뺀다. `pg-switch`는 ops-svc의 `ResolvePgSwitch`를 부를 수 없으므로 `--param toPg`·`--param pgTps`를 필수로 받는다(운영자가 결제사 승인 상한을 안다).
4. **RB-35의 제어 gRPC 이전은 이 트랙에서 하지 않는다(추천 적용, 2026-11-28)** — `rb35.*`(비상 셔플·더 기다리기·다시 공시)은 지금처럼 대기열 Redis 전달 칸과 admission-ctrl 리더가 검증·적용하는 길을 그대로 둔다. 제어 gRPC로 옮기려면 `control.proto`에 새 `ControlKind`(예: 비상 셔플)를 더해야 하는데, **F-02-6이 같은 파일에 `CONTROL_KIND_STATE_DEGRADED = 10`을 더할 계획**이다. 같은 파일의 enum을 두 동결 트랙이 동시에 고치면 경계가 무너지므로, F-02-6이 합쳐진 뒤(또는 동결을 풀 때) 후속으로 넘긴다. C-T13은 명령 2·3·11·6의 비상 길로 판정한다. 이 넘김은 감독이 확인해야 한다.
5. **감사 앵커·복구 편입은 포트·가짜까지(추천 적용, 2026-11-28)** — CLI는 보내기 전에 `RunbookAuditSink.writeIntent`, 끝나면 `writeResult`를 부른다. 실제 S3 Object Lock 어댑터는 `미실행` 골격만 두고, 시험은 메모리 sink로 한다. ops-svc가 복구된 뒤 결과를 감사 체인에 넣고 `control_version`을 맞추는 일은 S3·ops DB가 필요해 이 트랙 밖이다. 판 번호는 2번 규칙 때문에 다음 ops-svc 명령이 자연히 더 커지므로, 복구 편입이 없어도 받는 쪽 상태는 앞으로 간다. 남는 것은 감사 체인의 연속성이다.
6. **운영자 키 목록은 기존 환경 값 하나(추천 적용, 2026-11-28)** — `PEAKET_RUNBOOK_COMMANDER_KEYS`를 그대로 쓴다. 형식은 `[{ "id": "commander-a", "operatorId": "commander-a", "role": "commander", "publicKey": "<SPKI DER base64>", "kmsKeyArn": "arn:aws:kms:..." }, ...]`이고 `operatorId`·`kmsKeyArn`은 없으면 `id`·`--key`로 대신한다. 네 받는 쪽과 CLI가 같은 목록을 읽는다. 운영(prod)은 commander 둘 이상이 없으면 시작하지 않고, local·ci는 목록이 없어도 평소 경로만 받는다.
7. **C-T13의 p99 ≤ 10초는 `미측정`(추천 적용, 2026-11-28)** — 이번 턴은 Docker·kind를 쓰지 않고, 동결 로컬 범위에 실클러스터가 없다. 시험은 "ops-svc 없이 CLI가 세 받는 쪽에 같은 명령 ID·판으로 보내고 감사 sink에 남긴다"는 경로만 본다. p99는 동결을 풀고 실클러스터에서 잰다. 이 계획은 그 수치를 달성했다고 적지 않는다.
8. **C-T7 ③ 런북 한 줄은 세 프리셋만(추천 적용, 2026-11-28)** — `KILL_SWITCH`(→ `sale-pause`/`sale-resume`), `ADMISSION_PAUSE`(→ `admission-pause`), `AUTOMATION_STOP`(→ `automation-stop`)만 ops-svc가 채운 한 줄을 만든다. `DEGRADED_MODE` 결제 갈래는 `pgTps`를 ops-svc가 알 수 없어(멈춘 상황을 가정) 한 줄을 만들지 않고 RB-08 링크만 둔다.

합치는 차례도 적는다. **F-02-6이 먼저** 합쳐지면 F-02-7은 그 위로 rebase해 ① `Command.params`·16.5.2 문장·F-02-6의 생성물을 보존하고 ② `CommandState.runbookCommand`·자기 ASVS 근거만 더한 뒤 ③ `packages/contracts`와 `packages/api-client`의 `gen`을 다시 돌려 두 변경을 함께 만든다. **F-02-7이 먼저** 합쳐지면 F-02-6이 같은 방식으로 `runbookCommand`·자기 hunks를 보존하고 `Command.params`를 더한 뒤 두 `gen`을 다시 돈다. 어느 쪽도 상대의 스키마·행 문장을 지우지 않는다.

기능 경계도 적는다. F-02-6은 **명령 4·6의 전송·집행(바깥 WAF/CDN/작은 함수)**이고, F-02-7은 **그 명령을 ops-svc 없이 내는 비상 길과 받는 쪽 서명 관문**이다. F-02-7은 새 명령 모드·`params` 칸·제어 종류를 만들지 않는다. 두 기능이 함께 닿는 것은 `Command` 원장과 `ApplyControl` 계약뿐이고, F-02-7은 그 계약의 기존 칸(`runbook_bundle`)만 쓴다.

## 6. 공개 인터페이스

### 6.1 묶음

`RunbookBundle.canonical_bundle`은 아래 객체를 RFC 8785로 정규화한 UTF-8 바이트다. 수는 안전한 정수만 쓴다.

```json
{
  "v": 1,
  "commandId": "0193a000-0000-7000-8000-00000000ab01",
  "kind": "CONTROL_KIND_SALE_PAUSE",
  "scope": "0193a000-0000-7000-8000-0000000000e1",
  "version": 1764288000000,
  "reason": "결제사 장애로 판매를 멈춘다",
  "issuedAt": 1764288000000,
  "expiresAt": 1764288300000,
  "requests": {
    "purchase-svc": { "paused": true },
    "admission-ctrl": { "paused": true },
    "queue-svc": { "paused": true }
  }
}
```

- 받는 쪽은 먼저 `canonical_bundle`이 정규화 바이트인지 보고(아니면 `not-canonical`), 통과한 바이트의 모양을 본다(모르는 칸·빠진 칸이면 `bundle-malformed`). 그다음 `requests[<자기 서비스 이름>]`을 꺼내 `desired_state_json`과 정규화 값이 같은지 본다. 요청의 `command_id`·`kind`·`scope`·`version`도 묶음과 같아야 한다.
- `version`은 `issuedAt`과 같다. `expiresAt - issuedAt`은 5분(300,000ms)이고, `issuedAt`은 지금보다 30초 넘게 앞서면 안 된다.
- `reason`은 1~200자 한 줄이고 제어 문자·줄 구분자를 받지 않는다.
- 모르는 칸·서비스 이름·빠진 서비스는 거부한다(모르는 칸이 서명 대상 밖에서 해석이 갈리지 않게).

### 6.3 서명 정책

| 상황 | 서명 |
| --- | --- |
| `sale-pause`(판매 일시정지의 정지) | 정확히 commander 1명 |
| `sale-resume`(판매 재개) | 서로 다른 commander 정확히 2명 |
| 그 밖(명령 2·6·11 포함) | 서로 다른 운영자(commander·operator) 정확히 2명 |

- 같은 `operatorId`가 두 번이면 거부한다. 서명 수가 정책보다 많거나 적어도 거부한다.
- 모르는 `key_id`, 역할이 맞지 않는 키, DER이 아닌 서명, P-256이 아닌 키는 거부한다.
- 거부 사유는 `signature-count`·`same-operator`·`unknown-key`·`not-authorized-role`·`bad-signature`·`expired`·`not-yet-valid`·`window`·`not-canonical`·`mismatch`·`replayed`·`bundle-malformed` 가운데 하나다.
- 재생: 적용에 성공한 `commandId`는 `expiresAt + 5분` [가정] 동안 기억한다. 같은 `commandId`·같은 묶음이 다시 오면 `replayed`(gRPC `ALREADY_EXISTS`), 같은 `commandId`·다른 묶음이면 `conflict`(같은 `ALREADY_EXISTS`)다. 적용 전에 실패한 요청(리더 아님·저장소 오류)은 기억하지 않아 같은 ID로 다시 보낼 수 있다. 동시에 두 요청이 오면 하나만 `in-flight`로 잡고 다른 하나는 `UNAVAILABLE`이다.

### 6.5 받는 쪽 연결

네 `ControlDeps`에 `runbook?: { keys: ReadonlyMap<string, RunbookOperatorKey>; service: 'admission-ctrl'|'purchase-svc'|'queue-svc'|'payment-svc'; replay: MemoryRunbookReplayGuard; security: (e: RunbookSecurityEvent) => void; nowMs: () => number }`를 더한다. 값이 없으면 이 기능이 꺼진 것이 아니라 **평소 경로만** 받는 것이고, `runbook_bundle`이 오면 `bundle-malformed`로 거부한다(설정 누락이 서명 없는 비상 명령을 통과시키지 않는다). 시작 파일은 `PEAKET_RUNBOOK_COMMANDER_KEYS`가 있으면 이 값을 조립하고, prod에서 없으면 시작하지 않는다. **이 시험 범위**는 CLI의 `commanderKeysFromProcess` 계약(prod 무키 거부·local 허용)과 네 받는 쪽의 관문(설정 없음→`bundle-malformed`)까지이고, 네 서비스 `start.ts`의 실제 조립은 Docker·DB가 필요한 통합 시험이라 이 트랙에서 하지 않는다. 구현 리뷰가 `start.ts`의 조립과 prod 검사를 읽는다.

### 6.6 감사 기록

```ts
interface RunbookAuditIntent { v: 1; type: 'intent'; commandId: string; services: string[]; canonicalBundle: string /* base64 */; signatures: { keyId: string; signature: string /* base64 */ }[]; issuedAt: number; expiresAt: number; writtenAtMs: number }
interface RunbookAuditResult { v: 1; type: 'result'; commandId: string; outcome: 'APPLIED'|'REJECTED'|'PARTIAL'|'TIMEOUT'; applied: { service: string; address: string; podName: string; appliedVersion: number; appliedAtMs: number }[]; failed: { service: string; address: string; reason: string }[]; postReviewRequired: boolean; finishedAtMs: number }
interface RunbookAuditSink { writeIntent(i: RunbookAuditIntent): Promise<void>; writeResult(r: RunbookAuditResult): Promise<void>; readResult(commandId: string): Promise<RunbookAuditResult | null> }
```

`outcome`은 모두 적용이면 `APPLIED`, 일부 실패면 `PARTIAL`, 받는 쪽 보내기 시한(DEADLINE_EXCEEDED)이면 `PARTIAL`이고 `failed[].reason`에 `send-deadline`을 싣는다. 결과 대기 30초 [가정]를 넘기면 `TIMEOUT`이다. `REJECTED`는 모든 받는 쪽이 거부했을 때다. S3 키는 `runbook/v1/<yyyy>/<mm>/<dd>/<commandId>/intent.json`·`result.json` [가정]이고 Object Lock 준수 모드다. 실제 어댑터는 `미실행`이며, local CLI는 `PEAKET_RUNBOOK_AUDIT_DIR` 아래 같은 모양으로 쓴다.

### 6.7 ops-svc 런북 한 줄

`CommandState.runbookCommand`(문자열, 선택)를 상세에만 싣는다. 예:

```
peaket-runbook draft sale-pause --event 0193a000-0000-7000-8000-0000000000e1 --reason "결제사 장애로 판매를 멈춘다" --command-id 0193a000-0000-7000-8000-00000000ab01 --out runbook-0193a000-0000-7000-8000-00000000ab01.json
```

`PLATFORM` 범위는 `--scope platform`, `ADMISSION_PAUSE`는 `--param expiresInSec=600`, `AUTOMATION_STOP`은 `automation-stop`이다. 사유는 큰따옴표로 감싸고 `\`·`"`·`$`·`` ` ``를 역슬래시로 인용한다. 새 줄·제어 문자는 이미 명령 접수에서 거부된다. 명령 사유는 2,000자까지 받지만 런북 사유는 200자까지이므로, **200자를 넘으면 한 줄을 만들지 않고**(운영자가 RB-08에서 직접 채운다) `CommandState.runbookCommand`를 싣지 않는다. `FAILED`가 아닌 명령과 목록(`baseViewOf`)에도 싣지 않는다.

### 6.8 CLI 종료 코드

기존 `0`(성공)·`2`(사용법)·`3`(검증 실패)·`4`(결과 시간 초과)·`5`(받는 쪽 거부)에 `6`(KMS·키 목록·감사 sink·주소 같은 외부 자원 실패)을 더한다. RB-35 갈래의 기존 코드는 바꾸지 않는다.

## 9. 실패 시나리오

| # | 실패 | 바른 동작 |
| --- | --- | --- |
| S1 | KMS가 응답하지 않는다 | `sign`이 6으로 끝나고 묶음 파일의 서명을 바꾸지 않는다. 서명이 모자란 묶음은 받는 쪽이 거부한다 |
| S2 | S3 Object Lock이 응답하지 않는다 | `run`이 `writeIntent` 실패로 6으로 끝나고 명령을 보내지 않는다(fail closed). `writeResult`만 실패하면 명령은 이미 적용됐을 수 있으므로 commandId를 남기고 6으로 끝난다 |
| S3 | ops-svc가 모두 멈췄다 | CLI가 제어 포트로 직접 보낸다. ops-svc 주소·DB·Kafka를 읽지 않는다 |
| S4 | 키 목록이 없다 | 받는 쪽은 `bundle-malformed`로 거부하고 평소 경로만 받는다. CLI는 3으로 끝난다 |
| S5 | 받는 쪽 일부가 응답하지 않는다 | 보낸 곳의 ack만 결과에 싣고 `PARTIAL`·4로 끝난다. 보내기 시한이면 `failed[].reason`에 `send-deadline`을 싣는다. 같은 파일로 다시 실행하면 같은 commandId·판으로 다시 보낸다 |
| S6 | 같은 묶음을 다시 보낸다 | 적용한 받는 쪽은 `ALREADY_EXISTS`로 거부하고 보안 이벤트를 남긴다. CLI는 감사 sink의 이전 결과를 먼저 본다 |
| S7 | 시계가 뒤로 간다 | `issuedAt > now + 30초`면 `not-yet-valid`. 판 번호가 낡지 않게 CLI는 지금 시각으로 다시 만든다 |
| S8 | 묶음 파일을 고친다 | 서명이 맞지 않아 `bad-signature`다. 서명을 뗀 채 보내도 `signature-count`다 |
| S9 | 정규화하지 않은 바이트에 서명했다 | `not-canonical`로 거부한다. 해석이 갈리는 바이트를 받지 않는다 |
| S10 | 같은 밀리초에 두 묶음을 만든다 | 판이 같아 뒤 묶음이 무시될 수 있다. CLI는 1ms 뒤 다시 만들도록 안내한다(`[가정]`) |
| S11 | 받는 쪽이 리더가 아니다 | `UNAVAILABLE`이고 재생 기록을 남기지 않는다. 같은 commandId로 다시 보낼 수 있다 |
| S12 | 감사 결과 쓰기만 실패한다 | 명령은 적용됐을 수 있으므로 "적용됐을 수 있다"와 commandId를 알리고 6으로 끝난다. 되돌리지 않는다 |
