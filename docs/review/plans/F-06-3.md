# F-06-3 계획 — 승인 업무 1·2인·철회·만료·예외 환불·양도 회수·미성년자 취소 (동결 로컬)

- **무엇**: 기능 F-06-3(고객·CS·법정, A등급, GAT-290·GAT-300)의 동결 로컬 작업 계획이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **등급·차례**: A등급(`Batch-Grade: A`). ADR-0372·ADR-0373·ADR-0381의 A 차례를 따른다. **계획 → 시험 → 시험 리뷰(새 세션) → 시험 고정 → 구현 → 게이트 → 구현 리뷰(새 세션) → 지적 반영 → 고친 곳 다시 보기 → 기록.** 이번 작업은 **계획·시험·기준 트리 실패 확인·게이트까지** 하고 시험 리뷰를 받을 준비에서 멈춘다. 구현은 시험 리뷰 뒤에 시작한다.
- **동결 로컬 범위**: v1 출시 범위 밖이다(ADR-0373 결정 2, ADR-0386 결정 4·5, `docs/release/v1-scope.md` F-06-3). `freeze/lane2-F-06-3` 가지와 `D:/ticketpass-freeze-F-06-3` 워크트리에서만 개발하고 `develop`·`release/1.0.0`에 합치지 않는다. 출시 마이그레이션·릴리스 플래그·`deploy/` 값은 건드리지 않는다.
- **바탕**: 출발 `8a7081d94`(최신 `origin/develop`, 2026-11-26). 가지 `freeze/lane2-F-06-3`. 시험은 Docker 없이 단위·HTTP 경계로 돌린다(통합 시험은 구현 뒤 게이트에서 Docker 잠금을 잡고 돌린다).
- **정본**: `docs/features/transfer-refund.md` §3.1~§3.2·§4·§7.1~§7.4·§11, `docs/features/settlement.md` §4.2~§4.4·§5.1·§9·§13, `docs/features/identity.md` §5·§7, `docs/data.md` `approval_request`·`approval_vote`·`payout_approval`·`order_cancellation`·`ticket_cancellation`, `docs/api/openapi.yaml` `/v1/ops/approval-requests*`·`ApprovalRequest`·`payout-batches`·`createIdentityMinorContractCheck`, `docs/planning/03-policies-glossary.md` §2.10·POL-032·POL-038·POL-039, `docs/security/asvs/transfer-refund.md`, ADR-0046·0086·0171·0173·0320·0345·0364·0368·0369·0372·0373·0381·0386. 값은 이 파일에 옮기지 않고 위치만 가리킨다.

### 1.3 장부 범위 좁히기

기준 트리의 F-06-3 장부 범위는 `docs/features/transfer-refund.md`·ASVS 문서 전체라 **323항목**이다(기준 트리 `ledger --batch F-06-3`: 자동 198·ID만 39·빈칸 66, 그 밖에 이 기능과 닿지 않는 R-T5·R-T8·R-T10·R-T11·R-T13~R-T19·R-T27·R-T28·R-T30·R-T31·R-T35와 ASVS 전 절이 섞인다). §8.6 3의 "장부 범위가 넓어 닿지 않는 항목이 들면 기능을 시작할 때 범위를 좁힌다"에 따라 BUILD_ORDER F-06-3 줄의 **장부 범위 칸만** 다음으로 좁힌다. 판정 칸(정본 목록)과 상태 칸은 그대로 둔다.

- 뺀 `R-T32`·`R-T34`·`Q-T59`는 BUILD_ORDER F-06-4 줄의 장부 범위에 이미 있다. 이 기능은 그 셋의 **승인 수명주기 부품**만 만들고, 판정은 F-06-4가 한다(§1.2).

## 2. 정본 빈칸과 이번에 정하는 것(추천 적용, 2026-11-26)

정본에 없어 구현이 임의로 정할 수 없는 것만 적는다. 구현 전에 정본(괄호의 위치)에 쓴다. 방향을 바꾸는 결정은 없다.

1. **`requiredApprovals`의 뜻과 3인 허용**(`docs/data.md` `approval_request`, `docs/api/openapi.yaml` `ApprovalRequest.requiredApprovals`): 지금은 1·2만 허용하고, 지급 승인은 "요청자 + commander"를 2로 센다. 이 기능은 **요청자를 포함한 승인 관여 인원 수**로 유지하고, 재량 면제의 2인 승인(요청자 `cs_agent` + `cs_lead` + `commander`)만 **3**을 허용한다. CHECK·enum을 1~3으로 넓힌다. 승인 투표 수는 `requiredApprovals − 1`이고, 요청자가 아닌 사람의 표만 센다.
2. **종류별 요청자·승인 역할과 기한**(`docs/features/transfer-refund.md` §7.2에 표로 더한다):
   - `SYSTEM_FAULT_REFUND`: `cs_agent` 요청, `cs_lead` 1인, 기한 = 요청 + 5영업일(환급은 승인 뒤 3영업일 안).
   - `DISCRETIONARY_WAIVER`: `cs_agent` 요청. 면제액 30만 원 이하·주문 1건·같은 결제자의 90일 안 두 번째가 아니면 `cs_lead` 1인(2), 하나라도 걸리면 `cs_lead`+`commander` 2인(3). 기한 = 요청 + 5영업일.
   - `TRANSFER_RECLAIM`: `cs_lead` 요청, `commander` 승인(2). 기한 = min(요청 + 5영업일, 입장 시작). 승인은 요청 + 1일(소명 기한) 뒤부터 받는다. 소명 기한 전 승인은 409 `reclaim-appeal-window`.
   - `MINOR_CONTRACT_CANCEL`: `cs_agent` 요청, `cs_lead` 1인(2), 기한 = 요청 + 5영업일. 증빙 확인 사실(`evidenceChecked`: `PHONE_VERIFICATION` 또는 `DOCUMENT:<서류 종류>`)이 필수다.
   - 나머지 종류는 지금처럼 요청자 + 승인자 2다(지급·계약·역할·조정·판매 중지·부정 예매).
3. **30만 원·90일 판정의 입력**(§7.2): 금액은 면제분(원). "같은 결제자의 90일 안 두 번째"는 그 주문의 결제자 계정으로 센다. 요청할 때 purchase-svc 내부 `GET /internal/v1/orders/{orderId}/approval-basis`로 결제자·환급 가능 금액·결제 승인 시각·입장 시작·입장 기록 유무를 읽고, `approval_request.target_account_id`에 결제자를 복사한다. 그 계정의 `DISCRETIONARY_WAIVER` 가운데 `REJECTED`·`WITHDRAWN`·`EXPIRED`가 아닌 것이 지난 90일 안에 하나라도 있으면 2인이다.
4. **기한·만료·상위 알림의 작업**(§7.2): 5분 [가정]마다 한 바퀴. ① `PENDING_APPROVAL`이고 요청 + 1영업일이 지났으면 `ESCALATED`와 운영 경보 `APPROVAL_ESCALATED`(같은 승인 ID로 한 번). ② `dueAt`이 지났거나 대상이 바뀌었으면 `EXPIRED`(까닭 `DEADLINE_PASSED`·`TARGET_CHANGED`). ③ 만료·대상 변경 판정은 승인 직전에도 다시 한다(늦게 온 승인은 실행하지 않는다). 철회는 요청자만, `REQUESTED`·`PENDING_APPROVAL`·`ESCALATED`에서만. 이미 `WITHDRAWN`·`EXPIRED`면 200으로 그대로 돌려준다(openapi `…/withdrawals`). `WITHDRAWN`과 `EXPIRED` 뒤에는 상위 알림을 다시 열지 않는다.
5. **대상 변경의 뜻**(§7.2): `TRANSFER_RECLAIM`은 입장 시작·입장 기록·보유자 변경·티켓 종료, `SYSTEM_FAULT_REFUND`·`MINOR_CONTRACT_CANCEL`은 주문이 이미 환급·취소됨(또는 미성년은 입장 기록 있음), `PAYOUT_BATCH`는 지급일 전 영업일 15시, 그 밖의 종류는 요청 때 저장한 대상 상태가 달라짐이다.
6. **15시 만료의 지급 쪽 동작**(`docs/features/settlement.md` §5.1): 만료 작업이 payment-svc 내부 `POST /internal/v1/settlements/payout-batches/{batchId}/expiry`를 부른다. payment는 `PREPARED`·`PENDING_APPROVAL`이고 지급 건이 없는 묶음만 푼다. 정산서의 `payout_batch_id`를 비우고(상태는 `CONFIRMED` 그대로), 묶음을 `EXPIRED`, 감사 한 줄(`payout-batch-expired`, 행위자 `system`)과 `PAYOUT_HELD`(금액 = 지급액)를 같은 트랜잭션에 쓴다. 지급일은 다음 은행 영업일로 미루고, 다음 영업일 09시에 F-07-6의 09시 작업이 새 묶음을 만든다(새 묶음 ID는 새 작업이 정한다). ops는 승인을 `EXPIRED`로, 파트너 알림 `PAYOUT_POSTPONED` 한 번, 운영 경보 `settlement_batch_unapproved{pg}` 한 번. 경계는 15:00 정각부터 만료다.
7. **지급 대상 지문**(settlement §5.1): `payeeDigest` = 정산서를 정산서 ID 차례로 정렬해 `statementId|payoutAmount|promoterId|payeeBankCode|payeeAccountLast4`를 줄바꿈으로 이은 UTF-8 바이트의 SHA-256 16진(소문자 64자)이다. 결제사 계좌가 없으면 그 자리에 `NO_PAYEE`를 쓴다. payment-svc가 묶음을 만들 때 계산해 응답에 싣고, ops는 `payout_approval.payee_digest`에 저장한다. 승인·실행 직전에 payment가 다시 계산해 다르면 409 `payout-batch-payee-mismatch`이고 아무 상태도 바꾸지 않는다.
8. **미성년자 확인의 토큰**(`docs/features/identity.md` §5): `purpose=MINOR_CONTRACT`의 본인확인 결과 응답(확인 POST)에만 `resultToken`(ES256 JWS, 10분, `aud=identity-minor-contract`, `sub=계정 ID`, `jti`, `birth`)을 더한다. 다른 목적에는 싣지 않는다. `POST /v1/identity/minor-contract-checks`는 이 토큰·동의(`true`)·주문 ID 1~20개를 받아 서명·`aud`·`sub`·`exp`·동의를 보고, purchase-svc 내부 `GET /internal/v1/orders/{orderId}/minor-contract-basis`로 주문별 결제 승인 시각(KST)을 읽어 만 19세 미만이었는지 계산한다. 모두 미성년이면 `{under19AtContract:true}`, 하나라도 아니면 `false`다. 섞인 주문은 422 `minor-contract-mixed-orders`다. 생년월일·연계정보는 저장·로그하지 않고, 토큰도 저장하지 않는다.
9. **예외 환불 실행의 경계**(§3.2·§7.2): 시스템 잘못 환불은 `EXCEPTION` 사유로 티켓을 취소하고 공제 0원 전액 환급한다(입장 뒤면 기존처럼 `REQUESTED`로 두고 마감 뒤 환급 실행기가 처리한다). 미성년자는 `MINOR_CONTRACT_CANCEL` 사유로 공제 0원 전액 환급하고 좌석을 취소표로 돌린다(입장 시작·입장 기록이 있으면 409). 재량 면제는 티켓을 취소하지 않고 **면제분만** payment-svc 부분 취소로 추가 환급한다(공제 뒤 기본 환불은 자동이라 승인 대상이 아니다). 세 갈래 모두 승인 ID가 멱등키다.
10. **이상 표시·`csConfirm`의 처리 행동**(GAT-300, §7.1): `FLAGGED`(`ENTRY_AFTER_CANCEL`) 건에서 `cs_lead`가 ① `VOID`(취소 무효, 티켓 상태를 `VOIDED`로) 또는 ② `REFUND`(기록 오류로 보고 환급 실행)를 고른다. `TICKET_NOT_ISSUED` 건에서는 `csConfirm`으로 시스템 잘못 환불 승인 업무를 만든다. 두 행동 모두 CS 건 상세에서 시작하고 감사에 남는다. `VOID`는 입장 기록이 있는 취소만 받고, `REFUND`는 실행기가 집기 전·후 모두 같은 승인 ID로 멱등이다.

## 4. 공개 인터페이스(시험이 기대는 모양)

### 4.1 ops HTTP

- `POST /v1/ops/approval-requests` — 본문 `{kind, targetRef, amount, reasonCode, reasonText, evidenceChecked?}`, 201 `ApprovalRequest`. 이 경로로 받는 새 종류는 §2.2의 넷이다. `COMMANDER_ROLE_CHANGE`·`FRAUD_ACTION`·`CONTRACT_TERMS_CHANGE`는 지금처럼 422다.
- `POST /v1/ops/approval-requests/{id}/approvals` — 재인증 `act=APPROVAL` 필수, 본문 `{reason?}`. 200 `ApprovalRequest`. 이미 끝났으면 409 `approval-not-pending`, 기한·대상이 바뀌었으면 409 `approval-expired`·`approval-target-changed`, 요청자면 403 `approval-self-not-allowed`, 역할이 아니면 403 `approval-role-required`, 소명 기한 전 양도 회수면 409 `reclaim-appeal-window`.
- `…/rejections` — `{reason}` 필수, 200.
- `…/withdrawals` — 요청자만, `{reason}` 필수, 200. 이미 `WITHDRAWN`·`EXPIRED`면 200 그대로, `APPROVED`·`EXECUTING`·`DONE`·`FAILED`면 409, 요청자가 아니면 403.
- `POST /internal/v1/approval-requests/tick` — 내부 토큰, `{escalated, expired}`. 5분 작업과 시험이 같은 함수를 부른다.
- `POST /v1/ops/cases/{caseId}/cancellation-decision` — `cs_lead`, 본문 `{decision:'VOID'|'REFUND', reason}`. `FLAGGED`만 받고, `VOID`는 입장 기록이 있어야 한다. 200 `CsCase`.
- `POST /v1/ops/cases/{caseId}/system-refund` — `cs_lead`, `TICKET_NOT_ISSUED`만. 시스템 잘못 환불 승인 업무를 만들고 201 `ApprovalRequest`.

### 4.2 purchase 내부 HTTP

- `POST /internal/v1/approval-refunds/{approvalId}` — 내부 토큰 + `x-peaket-caller: ops-svc`, 본문 `{kind, orderId, amount, reasonText?}`. 200 `{status:'REFUNDED'|'REFUND_PENDING', cancellationId, refundAmount}`. 같은 승인 ID·같은 본문은 처음 답, 다른 본문은 409 `approval-refund-conflict`. 주문 없음·남의 주문 404, 환급 불가 상태 409, 금액 불일치 422 `approval-refund-amount-mismatch`.
- `GET /internal/v1/orders/{orderId}/approval-basis` — 내부 토큰, `{orderId, payerAccountId, paidAt, orderStatus, eventStartsAt, entryOpensAt, entryRecorded, refundableAmount}`. 좌석·연락처·카드 없음.
- `GET /internal/v1/orders/{orderId}/minor-contract-basis` — 내부 토큰, 위에서 `refundableAmount`를 뺀 같은 모양.

### 4.3 ticket gRPC

- `TicketService.ReclaimTransfer({approval_id, ticket_id, expected_payer_account_id, expected_holder_account_id, deadline_ms})` → `{result: RECLAIMED|SKIPPED_ENTRY_STARTED|SKIPPED_ENTRY_RECORDED|SKIPPED_NOT_TRANSFERRED|SKIPPED_HOLDER_CHANGED, ticket_id, previous_holder_account_id?}`. 내부 토큰 + 호출자 `ops-svc`, (승인 ID, 티켓) 멱등.

### 4.4 identity HTTP

- `POST /v1/identity/verifications` — `purpose=MINOR_CONTRACT` 허용(동의는 `confirm` 앞 화면이 받는다).
- `POST /v1/identity/verifications/{id}/result` — `purpose=MINOR_CONTRACT`이면 응답에 `resultToken`(10분 JWS)을 더한다.
- `POST /v1/identity/minor-contract-checks` — `{orderIds, consent:true, verificationResultToken}` → `{under19AtContract}`. 403 `identity-required`, 409 `minor-contract-not-owner`, 422 `minor-contract-mixed-orders`, 400 `invalid-body`(동의 false·주문 0/21개·토큰 모양).

### 4.5 payment 내부 HTTP

- `POST /internal/v1/settlements/payout-batches/{batchId}/expiry` — 내부 토큰, `{approvalId, postponedPayoutDate}`. 200 `{batchId, status:'EXPIRED', postponedPayoutDate}`. 지급 건이 있으면 409 `payout-batch-not-expellable`, 이미 만료면 200 같은 답.
- `POST /internal/v1/settlements/payout-batches/{batchId}/approvals`(기존 `approveBatch` gRPC/internally) 요청에 `payeeDigest`를 더한다. 다르면 409 `payout-batch-payee-mismatch`.

### 4.6 시험과 구현이 함께 따르는 포트 모양

```ts

  };
  executors: {
    refund(i: { approvalId: string; kind: 'SYSTEM_FAULT_REFUND' | 'DISCRETIONARY_WAIVER' | 'MINOR_CONTRACT_CANCEL'; targetRef: string; targetAccountId: string | null; amount: number; reasonText: string }): Promise<{ status: 'REFUNDED' | 'REFUND_PENDING'; cancellationId: string; refundAmount: number }>;
    reclaim(i: { approvalId: string; targetRef: string; targetAccountId: string | null }): Promise<{ result: 'RECLAIMED' | 'SKIPPED_ENTRY_STARTED' | 'SKIPPED_ENTRY_RECORDED' | 'SKIPPED_NOT_TRANSFERRED' | 'SKIPPED_HOLDER_CHANGED'; previousHolderAccountId?: string }>;

  notifier: { send(i: { approvalId: string; event: 'EXPIRED' | 'ESCALATED' | 'WITHDRAWN' | 'PAYOUT_POSTPONED'; targetRef: string }): Promise<void> };
  alerts: { open(i: { approvalId: string; kind: 'APPROVAL_ESCALATED' | 'settlement_batch_unapproved'; pg?: 'TOSS' | 'PORTONE' }): Promise<void> };
}
// purchase-svc refund 모듈(RefundModuleDeps.entryRecords)
interface EntryRecords { hasEntry(ticketId: string): Promise<boolean> }
// identity-svc verification 모듈(VerificationModuleOptions.minorContractOrders)
interface MinorContractOrders { basis(orderId: string): Promise<{ payerAccountId: string; paidAtMs: number } | undefined> }
// ops-svc payouts(PayoutPaymentClient에 더한다)
```

- tick 응답은 `{ escalated: number; expired: number; failed: number }`이다. `failed`는 payment가 만료를 거절한 수(409)이고 승인 상태는 그대로다.
- `ApprovalLifecycleDeps`는 `ApprovalsModuleDeps.lifecycle`으로 넘긴다. 없으면 닫힌 대역(요청·승인 503)이고 시작 조립(`main.ts`)은 실제 HTTP/gRPC 어댑터를 꽂는다.

- 자주 놓친 결함(architecture §8.6 4): 값까지 단언, 경계 양쪽(15:00·1영업일·90일·30만 원·만 19세), 계정 대조(요청자·승인자·결제자·보유자), 허용 목록 밖 역할, 같은 승인 ID의 다른 본문, 겹친 승인·철회·만료, 화면이 서버 판을 싣는지, 이중 가드 하나씩 빼기(승인 상태 조건과 승인 투표 유일), 시작 조립(`main.ts`) 대신 시험 조립만 보지 않기.
- B·C가 아니라 A라서 구현 전 기준 트리 실패를 **모든 새 시험**에서 본다. 단, 새 모듈을 직접 import하는 화면 시험은 기준 트리에서 "모듈 없음"으로 읽히므로 그 까닭을 '실패 확인'에 적고, 서버 경계 시험(HTTP·gRPC)이 실제 동작 실패를 본다.

## 6. 실제 서버 연결과 차례

- **서버 ↔ 저장소**: ops-svc `test-int/approval-lifecycle.int.test.ts`(구현 뒤)가 실제 PostgreSQL 18에서 0038의 CHECK·칸·인덱스와 승인·철회·만료 경합을 본다. purchase·ticket 통합은 Docker 잠금을 잡고 한 번씩.
- **서비스 사이**: ops→purchase 내부 HTTP, ops→ticket gRPC, ops→payment 내부 HTTP, identity→purchase 내부 HTTP를 단위 시험에서는 가짜 포트로, 통합 시험에서는 실제 서버로 본다. 가짜 API로 끝내지 않는다.
- **화면 ↔ 서버**: 콘솔 `cs-approvals`는 생성 클라이언트(`listOpsApprovalRequests`·`getOpsApprovalRequest`·`createOpsApprovalRequestApproval`·`…Rejection`·`…Withdrawal`)만 부른다. 화면 시험은 `model/live.test.mjs`(해석·오류·판·카드)와 `ui/wiring.test.mjs`(호출·If-Match·저장소 0·`dangerouslySetInnerHTML` 0)로 본다. 브라우저 확인은 웨이브 끝에 `docs/review/browser-check/` 아래 `GAT-290-GAT-300.md`로 한다(합치기 조건 아님).

## 7. 브라우저 확인 대본(웨이브 끝)

준비: 무대 S9로 `cs_agent`·`cs_lead`·`commander` 계정을 만들고, 예외 환불·미성년·양도 회수·지급·조정 승인을 하나씩 연다.

1. `cs_agent`가 SCR-046에서 예외 환불을 요청하면 1인·2인 배지와 사유·증빙 확인 사실이 보인다. 자기 요청은 승인 버튼이 비활성이다.
2. `cs_lead`가 승인하면 재인증 뒤 결과·감사가 보이고, 철회는 요청자에게만 보인다. 남이 열면 403 안내다.
3. 15시가 지난 지급 묶음은 `만료`로 보이고 다음 영업일 지급일이 보인다.
4. 정산 조정 카드에서 금액 항목·사유·정산서 ID가 보이고, 승인 뒤 상태가 바뀐다.
5. 콘솔 오류·CSP 위반 0, 브라우저 저장소에 승인 값 0, 첫 JS 예산은 로컬에서 잰다.

## 9. 정리 목록으로 보낼 것

- `role-change-approval.ts`의 `addBusinessDays`가 UTC 요일로 세고 공휴일을 보지 않는다(F-06-2 RV-11과 같은 결함). 이 기능은 `cases`의 `BusinessCalendar`를 쓴다.
- `approval_request`의 `close_reason`·`approver_id`가 한 칸뿐이라 2인 승인의 두 번째 승인자를 담지 못한다. `approval_vote`가 정본이고 화면은 배열로 읽는다.
- `payout_approval`과 `approval_request`가 지급 승인을 두 표에 나눠 갖는다(공통 표 이관 BAT-625 RV-05). 이 기능은 이관하지 않고 `payee_digest`만 `payout_approval`에 더한다.
- `FLAGGED` 취소 무효 뒤 티켓 상태(`VOIDED`)와 환급 실행기(`VOIDED`를 덮지 않음)의 연결은 purchase-svc 틱과 ops 행동을 함께 봐야 한다. 통합 시험은 구현 뒤 Docker로 한 번.
- 콘솔 첫 JS 예산·시각 비교는 웨이브 끝에 잰다.
