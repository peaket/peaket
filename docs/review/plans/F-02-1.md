# 기능 계획: F-02-1(제어 gRPC `ApplyControl` 전면 — 판 번호 원장·받는 파드 ack·받는 쪽 저장)

- **진행**: 계획 끝, 감독 결정 반영(2026-11-23). 다음은 구현.
- **무엇**: BUILD_ORDER '기능 단위 계획' F-02-1(갈래 4, 등급 A, OPS-300, WBS 2.5일, 단계 줄 `OPS-300 wbs 4.4.2 ①`)의 작업 목록이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **쉬운 말**: 관제 명령(입장 목표, 입장 멈춤, 판매 멈춤, 공지, 자동 제어 멈춤)을 받는 서버마다 '판 번호'를 붙여 저장하게 하고, 관제 서버가 준비된 모든 파드에게서 "그 판을 적용했다"는 답(ack)을 받아야 끝난 것으로 친다. 판 번호는 그 범위·종류에서 늘어나기만 하는 수라, 늦게 온 옛 명령이 새 명령을 덮지 못한다. 카프카로 퍼지는 설정형 명령의 적용 확인과 사전 모의 센 값은 F-02-5가 한다.
- **바탕**: `D:/ticketpass-lane4-F-02-1`, 가지 `feature/lane4-F-02-1`, 기준 `origin/develop` `450ab6cd7`(BAT-355·BAT-360 포함). 계획 담당은 제품·시험 코드를 쓰지 않았고 시험·Docker를 돌리지 않았다.
- **차례**: A 정방향(ADR-0281, ADR-0354): 계획 → 구현 → 시험(기준 커밋 트리에서 실패 확인) → 리뷰 → 리뷰 반영 → 검증 → 기록. 계획 커밋에 `Batch-Order: impl-first`.
- **한 줄 결론**: 제어 gRPC는 판매 중지 한 종류를 purchase·queue 한 파드씩에만 보낸다. admission-ctrl에는 제어 포트가 없고, 판 번호는 명령의 바뀐 시각이다. 빈칸은 ADR-0365로 정했다. 크기가 5일 어림이라 감독 결정으로 설정형 명령·적용 확인·`PreviewControl` 몫을 F-02-5로 나눴다(2절 1).

## 2. 감독에게

올린 것에 감독이 2026-11-23에 답했다(감독 결정 2026-11-23). 이 계획은 그대로 따른다.

1. **크기와 나누기** — (가) 지금 나눈다. 어림은 모두 약 5일 [가정]이었다(이 기능 몫 약 3일, 나눈 몫 약 2일). F-02-1은 ADR-0365 결정 1~8(장부 C-T50·Q-T30·ASVS 넷)이다. 결정 9~11(설정형 명령 5·7·8·9 내기, 적용 확인, `PreviewControl`, 장부 C-T6 ①·C-T51·C-T54·ASVS 1.3.6·2.3.3)은 새 기능 **F-02-5**(A, OPS-300, 2.00일, 선행 F-02-1)로 갔고, 이 계획 결정 반영 커밋이 기능 표에 그 행을 더했다. 단계 줄 OPS-300은 F-02-5가 끝날 때 체크한다. 아래 절의 'F-02-5' 표시는 그 기능 계획이 쓸 참고다.
2. **명령 3의 ops 쪽 전송** — (가) F-02-1이 명령 3을 세 받는 쪽에 보내고 ACKED까지 한다(C-T50이 '명령 3이 ACKED인 회차'를 요건으로 한다). F-02-2에는 명령 3의 비상 런북 길과 명령 6이 남는다. 대기 상태 파일은 이미 notice의 `paused`를 읽는다(HOT-010).
3. **kind·배포 차트는 구간 5로(ADR-0331 결정 9)** — 그대로 미룬다. 단계 줄의 admission-ctrl 배포 차트(Lease RBAC, 리더 전용 Service·`role=leader` 라벨, `pod-deletion-cost`), 차트의 `PEAKET_PROMETHEUS_URL`, 서비스마다 `<서비스>-control` Service, kind의 리더 교체 시험(Q-T12·G-09, Q-T30의 'API 서버 연결만 끊기')은 kind e2e가 곧 시험인 배포 몫이라 F-09-8(INF-020, 구간 5)이다. Q-T12는 이미 '자동 시험'이라 상태는 그대로 두고 범위에서만 뺐다(결정 9 '장부는 정직하게'). F-09-8 비고는 감독 몫이라 고치지 않는다.
4. **온세일 `LOG_SAMPLING` 내기·C-T75 ①④** — 받는 쪽은 갈래 1 BAT-215(아직 `develop`에 없음)다. 이 기능에서 빼고, BAT-215가 합쳐진 뒤 감독이 정할 기능이 한다.
5. **번호** — ADR-0365(0366·0367은 비워 둠). 마이그레이션 ops-svc **0025**(`control_version`·`command_delivery`), purchase-svc **0033**(`sale_control` 칸 셋). 0026·0027·0034는 쓰지 않는다. admission-ctrl·queue-svc는 Redis만 써서 마이그레이션이 없고, 다른 서비스 마이그레이션도 없다.
6. **갈래 2 F-03-1(관제 콘솔 호스트·ops-svc REST/SSE)과 겹칠 파일** — ops-svc에서 이 기능이 고친다. 겹칠 위험이 큰 것에 ★.
   - ★ `services/ops-svc/src/app.module.ts`(`CommandsModuleExtras` 손잡이: 대상 찾기), ★ `src/main.ts`(환경 값 조립)
   - ★ `src/modules/commands/inbound/command-view.ts`(`delivery` 칸을 채운다), `commands.module.ts`, `index.ts`
   - `src/modules/commands/domain/`: `ports.ts`, 새 `control-kinds.ts`, `command.ts`(판 칸)
   - `src/modules/commands/application/`: `execute-command.ts`, 새 `dispatch-control.ts`, `maintain-commands.ts`, `revert-command.ts`·`retry-command.ts`
   - `src/modules/commands/adapters/`: `db/drizzle-command-store.ts`, `memory-command-store.ts`, `command-store-base.ts`
   - `src/adapters/grpc-control-sender.ts`, `http-command-executor.ts`, 새 `src/adapters/control-targets.ts`

   - 고치지 않는다: `src/modules/live/`, openapi ops 경로(`delivery`는 이미 계약에 있다), `control.proto`(F-02-5가 고친다). 갈래 2와의 겹침은 감독이 알렸다: 먼저 합친 쪽을 뒤가 rebase로 받는다(감독 결정 2026-11-23).
7. **넘겨받은 것 확인** — FND-080(ops Outbox `writeOutbox`·`CONTROL_TOPICS.settings`)은 BAT-360이 일반 `publishSetting`·릴레이로 끝냈다. 이 기능은 그것을 쓴다. PRF-090·HOT-030·PRF-138·HOT-010의 넘긴 것은 3.1에 모두 넣었다. BAT-355의 `PreviewControl`(ADR-0340 결정 11)은 F-02-5다.

## 3. 범위

### 3.1 하는 것

- **판 원장과 퍼뜨리기(ADR-0365 결정 1~4)**: ops DB `control_version`·`command_delivery`(0025), 처음 `DISPATCHED` 때 판 매기기, 대상 찾기 포트(헤드리스 DNS·주소 목록), 준비된 모든 파드에 동시에 보내기·1초마다 같은 판으로 다시 보내기·다시 풀기·10초 실패, 배경 작업과 정비 바퀴의 이어 보내기, `delivery`(ACK) 보이기. 명령 1·2(연장·만료 되돌림 포함)·3(감독 결정 2)·7·11 전송과 되돌리기. 판매 중지·재개를 같은 원장·찾기로 옮김.
- **admission-ctrl 받는 쪽(결정 5·6)**: 제어 포트(`PEAKET_ADMISSION_CONTROL_GRPC_PORT`), 리더만 쓰기·세대 확인 Lua, 종류 1·2·3(회차·전체)·11과 판·명령 칸, 리더 루프가 `q:{admission}:ctl` `allPaused`를 읽어 전진 0. PRF-090·HOT-030의 칸(`target`·`targetUntil`·`admitPaused`·`admitPausedUntil`·`paused`·`aimdResumeAt`·`autoStopped`).
- **purchase-svc 받는 쪽(결정 6~8)**: `SALE_PAUSE`(회차·`PLATFORM`)를 `sale_control`(0033 칸 셋)과 `s:{event:E}:ctl`(`paused`·`pausedRev`, 전체는 `s:ctl:events`의 회차마다 `allPaused`·`allRev`)에, 시작 작업의 제어 상태로 넘기기, 2초 다시 맞춤(메모리와 사본), 결제 시도·접수의 메모리 확인, `SessionSweeper`의 유휴 시계(PRF-138).

## 8. 공개 인터페이스

- **gRPC**: `ControlReceiver.ApplyControl` 종류 `ADMISSION_TARGET`·`ADMISSION_PAUSE`·`SALE_PAUSE`·`LOBBY_BANNER`·`AUTOMATION_STOP`(받는 쪽 65 2 표), 오류 `INVALID_ARGUMENT`·`UNIMPLEMENTED`·`UNAVAILABLE`(`not-leader`·`fenced`). 메시 쌍은 그대로(MS-09·MS-19 변화 없음).
- **REST**: 바뀌는 경로 없음. `CommandState.delivery`를 채운다(계약 그대로). 승인·실행 응답의 상태가 카탈로그 명령에서 `DISPATCHED`가 될 수 있다(계약 열거 안).
- **모듈 공개 면**: ops-svc commands `ControlDispatcher`(`dispatch(command)`, `resume(commandId)`), `ControlTargets` 포트, `controlKindOf(command)`. F-02-2가 명령 6·런북 길에 쓴다. admission-ctrl `ApplyLeaderControl`, purchase-svc `SetSalePause`·`SaleControlReconciler`, queue-svc `SetQueueNotice`.
- **지표·로그**: 새 지표 이름은 정본에 없으면 만들지 않는다. 로그는 명령 ID·판·서비스·파드·결과 한 줄(계정·가명 참조 없음).

### 10.1 시험이 기댄 공개 이름과 가정(구현이 맞출 것)

시험 담당이 정한 꼴이다. 다르게 만들면 '시험 이의'로 알려 준다(구현 커밋은 시험 파일을 고치지 못한다).

- **ops-svc**: commands `index.ts`가 `ControlDispatcher`·`type ControlTargets`·`controlKindOf`를 내놓는다. `new ControlDispatcher({ store, targets, senderFor(service, address), clock, sleep })`(저장소는 `CommandStore`, 보내기는 지금 `src/adapters/grpc-control-sender.ts`의 `ControlSender` 꼴, 시계는 플랫폼 `Clock`, 대기는 주입). `dispatch(command)`는 `DISPATCHED`인 명령을 받아 `ACKED`·`FAILED`까지 끝내고 마지막 명령을 돌려준다. `resume(commandId)`는 남은 `DISPATCHED`를 같은 판으로 잇는다. `ControlTargets.resolve(service)`는 `'admission-ctrl'|'purchase-svc'|'queue-svc'`의 주소 목록. 판은 `store.markDispatched`(처음 `DISPATCHED`)가 매기고 요청의 `version`이 그 판이다. `controlKindOf`는 proto 열거 이름 또는 `undefined`(설정형 명령). 새 `src/adapters/control-targets.ts`의 `controlTargetsFromEnv(env)`: `PEAKET_{PURCHASE,QUEUE,ADMISSION}_CONTROL_GRPC_ADDRS`(쉼표)·`…_ADDR`, `PEAKET_ENV=prod`에 설정이 없으면 던진다. 실패 사유 `ack-timeout:<서비스>`, 다시 보내기는 처음 보낸 때부터 1초 간격, 처음 보낸 때 + 10,000ms에 온 ack는 늦음. 바라는 상태: 명령 1 `{target, untilMs: 처음 DISPATCHED + 15분}`, 명령 2 칸 `paused`·`expiresAtMs` 둘, 명령 3 `{paused: true}`(회차마다·`PLATFORM`), 명령 11 `{stopped: true}`(params `{}`, 범위 `PLATFORM`). `delivery.unackedTargets`의 글에 그 파드 이름(또는 주소)이 든다.
- **admission-ctrl**: 환경 값 `PEAKET_ADMISSION_CONTROL_GRPC_PORT`(호스트는 다른 서비스처럼 `PEAKET_CONTROL_GRPC_HOST`), 파드 이름은 `PEAKET_POD`. leader `index.ts`가 `ApplyLeaderControl`을 내놓는다: `new ApplyLeaderControl(store: LeaderStore, elector: Elector, clock: Clock)`, `run({ commandId, scope, kind, version, desiredStateJson })` → `{ appliedVersion }`, 거절은 `code`(gRPC 상태 14·3·12)와 글에 `not-leader`·`fenced`(gRPC 답의 details도). FENCED를 받은 세대로는 다른 회차에도 쓰지 않는다(리더 루프의 기존 규칙과 같다). `LeaderStore.platformControl()`이 `{ autoStopped, allPaused }`. 명령 11 회차 범위·명령 2 전체 범위는 `INVALID_ARGUMENT`, 판매 중지(`SALE_SUSPENSION`)는 받지 않는다(14절 4). gRPC·계약 의존(`@grpc/grpc-js`·`@grpc/proto-loader`·`@peaket/contracts`)을 더해야 한다(시험 클라이언트는 queue-svc 자리의 의존을 쓴다).
- **purchase-svc**: 기존 결함 — `src/control/control-server.ts`의 `server.addService(controlPackage().ControlReceiver, …)`가 서비스 정의(`.service`)가 아니라 클라이언트 생성자를 넘겨 제어 포트를 주면 시작이 실패한다(queue-svc는 `.service`). Kafka 브로커가 없는 ci에서도 `sale_control`을 읽어야 `/ready`가 200이다. 범위는 회차 UUID 또는 `PLATFORM`(`platform`·빈 글은 거절). 기존 단위 시험의 `applyControl(req, { setSuspension, podName, nowMs })`가 계속 받혀야 한다(새 의존은 선택으로). 정지 중 유휴 세션은 정리 색인 점수를 뒤로 미루고, 풀린 뒤 처음 볼 때 `idle`을 풀린 시각 + 5분(받은 파드 기준, 다시 맞춤 2초 안)으로 다시 쓴다.
- **queue-svc**: 배너 1~500자·제어 문자 거절·`null`이면 칸 지움, 범위는 회차 ID 모양 또는 `PLATFORM`.
- **층 바꿈**: 받는 쪽의 ASVS 1.4.2·15.3.5·2.1.1은 단위 대신 시작 함수 + 실제 gRPC 통합 시험으로 둔다(정본 계약 그대로 부르고 저장소 칸까지 본다). 시험 지원 변경(package.json)은 없다. 받는 쪽 넷의 gRPC 클라이언트는 `services/queue-svc/test-int/control-client.ts` 하나를 상대 경로로 함께 쓴다(계약 원본 `docs/api/proto`를 읽는다).
- **빈칸(이 커밋이 덮지 않음)**: 결제 시도·결제 접수의 423 HTTP(주문이 있어야 한다), 명령 7의 ops 쪽(params 꼴이 정본에 없다), 판매 중지·재개 경로의 원장 판(B18 ops 쪽, 기존 단언만 풀었다), 되돌리기·연장·만료 되돌림의 새 판(B2 일부), 접수·승인 응답의 `DISPATCHED`(B8)와 정비 바퀴 이어 보내기(`resume`로 대신 봄), F021-IDLE의 −1ms·정각 경계(가짜 시계를 넣을 이음매가 공개 면에 없다), C-T50의 '여섯으로'(셋으로)·강제 재시작.
- **CI**: `ci-node.yml`에 ops-svc `test:integration` 단계가 없어 새 ops 통합 시험(원장·e2e)이 CI에서 돌지 않는다(TA-V15). 더할 때 받는 쪽 의존 dist도 빌드해야 한다(`--filter=@peaket/ops-svc^... --filter=@peaket/purchase-svc^... --filter=@peaket/queue-svc^... --filter=@peaket/admission-ctrl^...`). 감독 몫.

## 13. 자주 놓친 결함(시험·구현 지시문에 넣는다)

- Lua·저장소 응답은 정확한 값까지: 받는 쪽이 돌려준 판, 쓴 칸의 값과 판·명령 칸 모두, `delivery`의 수와 파드 이름.
- 건드린 키를 모두 확인: 전체 범위 명령 3은 `s:ctl:events`의 회차마다 사본, `q:{admission}:ctl`, `q:{event:PLATFORM}:notice`. 다른 종류의 칸(`suspended`·`suspRev`)은 그대로인지.
- 경계는 양쪽: 10초(− 1ms·정각), 2초 다시 맞춤, 풀린 시각 + 5분. 가짜 시계, 시험 값은 코드 상수와 다르게, 판은 9 → 10 두 자리.
- 허용 목록은 밖의 값마다: 종류(받지 않는 종류 셋 이상), 범위(`PLATFORM`·회차·빈 글·대문자 UUID), 환경(local·ci·demo·staging·production에서 주소 설정 없음).
- 판정만 보지 말고 부르는 쪽이 쓰는지: 받는 쪽 거절 → ops 명령이 ACKED가 되지 않음, 423이 실제 HTTP 응답으로 나옴.
- 장애 주입은 끊긴 사례 수를 단언(9절 끝).
- 시작 파일(`start.ts`·`main.ts`)의 조립은 시험 조립과 따로 띄워 본다: 제어 포트가 열리고 `controlState`가 넘어가는지.
- 정본 시험 표에 세부 번호를 더하면 '연결: …' 앞에 둔다.

- **purchase-svc 시작 작업**: platform `startServiceControlSync`는 Kafka가 없는 local·ci에서 뜨지 않아 제어 상태 작업도 돌지 않는다. platform을 고치지 않고 purchase-svc `SaleControlReconciler`가 같은 준비 표시 이름(`control-state`)·같은 주기(platform `CONTROL_SYNC_DEFAULTS.reconcileMs`·`retryMs`)로 따로 돈다. `ControlStateSource.read`도 내놓는다.
- **사본 다시 쓰기 범위**: 다시 맞춤은 `paused`(명령 3, 판 > 0)·`suspended`인 회차 행과 전체 `paused` 행만 다시 쓴다. 명령 3 사본은 판 칸(`pausedRev`·`allRev`)보다 클 때만, 판매 중지 사본은 원본 값 그대로(옛 규칙) 쓴다.
- **`paused_changed_at`**: `paused` 값이 실제로 바뀔 때만 옮긴다(같은 값의 새 판은 그대로). 유휴 시계의 '풀린 시각'은 회차·전체 가운데 늦은 값이다. 처음 받은 명령이 풀기(`paused: false`)였던 행도 그 시각을 풀린 시각으로 본다(5분 안의 세션 유휴를 늘릴 뿐이다).
- **유휴 시계**: 정지 동안은 SWEEP Lua가 `pay`와 같은 갈래로 LIVE(다음 점검 = min(최대 체류, 지금 + 5분))다. 풀린 뒤 '풀린 시각 + 5분' 전에 보는 세션은 같은 Lua가 `idle`을 그 값으로 올린다. 선택값이 없으면 Lua ARGV는 예전 그대로(유휴 ms 하나)다. '+ 5분'은 `SESSION_IDLE_RESUME_GRACE_MS = SESSION_IDLE_MS`.
- **결제 시도·결제 접수의 메모리 확인**: `start.ts`의 `pauseAwareSlots`가 회차 슬롯 읽기 앞에서 메모리 정지(명령 3 회차·전체, 판매 중지)면 `PAUSED`(423)로 답한다. 홀드는 예전대로 사본을 읽는 홀드 Lua다.
- **받는 쪽 범위 글자**: 새 종류(명령 1·2·3·7·11)의 회차 범위는 소문자 UUID만 받는다(대문자는 INVALID_ARGUMENT). 판매 중지는 예전 규칙(대소문자 무관) 그대로다. 판은 네 종류 모두 1 이상 안전 정수(판매 중지의 0도 이제 거절).
- **queue-svc 판매 중지 사본**: 제어 gRPC 판(> 0)이면 notice의 `suspRev`보다 클 때만 쓰고 쓴 뒤의 판을 돌려준다. 내부 HTTP 경로(판 0)는 예전처럼 늘 쓴다.
- **명령 7 배너 값**: 명령 7 params는 아직 닫히지 않았다. ops는 `{eventId?, templateId}`를 읽어 `{"banner": templateId}`를 보낸다(회차가 없으면 PLATFORM). 템플릿 글 풀기는 화면 몫이다. `templateId` 꼴은 openapi NoticeTemplate과 같다.
- **admission-ctrl**: 꼴 검사를 리더 확인보다 먼저 한다(대기 파드도 틀린 값은 INVALID_ARGUMENT). FENCED면 루프와 같은 `#fence`로 그 세대의 쓰기를 멈춘다(Lease는 놓지 않는다). 리더 키 수명은 회차 일정이 있으면 판매 종료 + 1일로 다시 건다. 명령 1 되돌리기는 `target`·`targetUntil`을 지우고 `aimdResumeAt`을 쓴다. 명령 2 만료가 null이면 `admitPausedUntil`을 지운다.
- **`allPaused` 읽기(정할 것 1)**: `autoStopped`와 같은 1초 캐시. 이제 자동 제어 입력이 없어도 읽는다(그때 autoStopped는 늘 거짓). 읽기 실패면 autoStopped·allPaused 모두 참(닫힌 쪽)이다.
- **판 원장 범위 여럿**: 명령 3 EVENT처럼 범위가 여럿이면 판 하나 = max(범위들의 마지막 판 + 1, 지금 ms)를 모두에 쓴다. 매기기 전에 판 0 행을 넣고 정렬한 차례로 잠근다.
- **10초 기준**: `control_sent_at` = 그 판을 보내기 시작한 시각(DISPATCHED마다 지금). 다시 하기는 같은 판이고 10초를 새로 센다. 정비 바퀴는 이 프로세스가 보내지 않고 `control_sent_at` + 10초가 지난 DISPATCHED만 이어 보내므로, 이어 보내기는 한 바퀴를 보낸 뒤 모두 ack가 아니면 바로 FAILED다.
- **ack 판정 차례**: 바퀴마다 주소를 다시 풀고 → ack하지 않은 주소에 보내고 → 모두 ack면 한 번 더 풀어 확인한다. ack를 다 받은 시각이 시작 + 10초보다 이르면 성공, 정각 이상이면 `ack-timeout:<서비스>`. 기다림은 min(1초, 남은 시간)이라 마지막 확인이 10초 정각에 온다. 받는 쪽 거절(INVALID_ARGUMENT 등)도 다시 보내기 대상이다(빨리 끝내지 않는다).
- **되돌리기·연장·만료 되돌림**: 원장 새 판을 매겨 `control_version`에 쓴 뒤 응답 안에서 보내고 10초까지 기다린다(`ControlAwareExecutor` → `ControlDispatcher.sendNew`). 그래서 되돌리기 요청이 길면 10초 걸린다. 명령 2 만료(AUTO_EXPIRED) 되돌림은 정비 바퀴가 기다리지 않고 보낸다(받는 쪽도 만료 시각으로 스스로 푼다).
- **`delivery`**: 상세(GetCommand)에만 지금 판의 줄로 싣는다. 줄 = (서비스, 범위, 부른 주소). `unackedTargets`는 `<서비스>/<파드 이름 또는 주소>@<범위>`. 목록·SSE에는 싣지 않는다.
- **대상 설정 이름**: `PEAKET_<PURCHASE|QUEUE|ADMISSION>_CONTROL_GRPC_ADDRS`(쉼표, `…_ADDR` 하나도), 운영 `…_CONTROL_GRPC_DNS`(이름:포트). local·ci만 없이 뜬다(그 받는 쪽으로 가는 명령은 10초에 FAILED). 판매 중지·재개는 purchase·queue 설정이 다 있을 때만 퍼뜨리기 길이고 아니면 HTTP 호환 경로다. 옛 주소 하나씩의 `control` 선택값은 실행기에 남겼다(시작 파일은 쓰지 않는다). 판은 원장 판이 있으면 그 판이다.
- **원장 없는 저장소**: 쓰기 객체에 `assignControlVersion`이 없으면 판을 적지 않고, 배경 보내기가 있으면 `control-ledger-not-wired`(범위를 못 읽으면 `invalid-command`)로 FAILED다. 배경 보내기를 조립하지 않은 모듈(`extras.control` 없음)은 예전처럼 실행기가 부른다.

- **RV-01 결정**: 명령 7은 승인된 템플릿만 받는다(ADR-0365 결정 2 '바꿈' 줄). 템플릿 ID를 `banner` 글로 싣는 길은 없애고, 승인 템플릿 저장소와 `banner`에 싣는 것은 F-03-5(OPS-410)가 정한다.
  - 고칠 자리(구현): ops-svc `domain/control-kinds.ts`의 명령 7 → `{"banner": <templateId>}` 바꾸기를 지우고, `domain/ports.ts`에 승인 템플릿 찾기 포트, 기본 어댑터(늘 없음), 명령 만들기·미리보기 검사(`create-command.ts`·`compute-dry-run.ts` 쪽 매개변수 검사)에 422 `invalid-command`(detail `templateId`). queue-svc `LOBBY_BANNER` 받는 쪽은 그대로 두고 F-03-5가 꼴을 바꾼다.
  - 재현 시험(시험): `RV-01 ① 승인 템플릿이 없으면 명령 7 만들기는 422 invalid-command이고 명령·사건·감사 0`(HTTP 경계, 미리보기도 같은 422), `RV-01 ② 명령 7의 바라는 상태에 templateId 글이 실리지 않는다`(제어 종류 바꾸기가 명령 7을 보내는 꼴로 만들지 않음). 지금 트리에서 ①은 201, ②는 `banner`에 ID가 실려 실패해야 한다.
- **RV-02·RV-03·RV-04**: 표대로(고칠 방향·재현은 각 행의 '막는 지적' 칸).
- **RV-06**: 표대로 고치되, 바른 동작은 정본 자리대로 한 줄로 못박는다. **카탈로그 명령의 처음 실행만 응답 밖이다**(접수·승인 응답은 `DISPATCHED`로 바로, 퍼뜨리기·ack는 배경, ADR-0365 결정 4). **되돌리기·연장·판매 중지·재개는 정본이 응답 안의 ack를 요구한다**(openapi `createOpsCommandExtension` 'ack를 받은 뒤 200'·502 `command-dispatch-failed`, `createOpsCommandReversion` 200 REVERTED·502, ADR-0365 결정 4 '판매 중지·재개는 응답 안에서 차례대로', ADR-0123 차례). 그래서 이 셋은 응답 안에서 기다리되 시한은 명령 하나에 하나다: 처음 보낸 때 + 10초(서비스마다 새로 잡지 않음)와 요청의 남은 시간 가운데 짧은 것. 넘으면 되돌리기·연장은 502 `command-dispatch-failed`(명령은 그대로, `REVERT_FAILED`·`EXTEND_FAILED` 사건), 판매 중지·재개는 `FAILED`(`ack-timeout:<서비스>`)다. 재현 시험: 남은 시간 3초짜리 요청의 판매 중지에서 queue-svc가 답하지 않으면 응답이 3초 + 여유 안에 끝나고, 두 서비스 합쳐 10초를 넘기지 않는다(가짜 시계).

### 다시 보기(리뷰 담당 f021-review-9b4f, 2026-11-23, `d7461716e`(재현 시험)·`1126a16b8`(고침))

두 커밋만 읽었다(시험·Docker는 돌리지 않았다). 재현 시험이 고치기 전 트리에서 실패하는 모양인지는 코드로 따져 봤다.

- **RV-01 닫힘**: 명령 만들기·미리보기가 승인 템플릿 찾기 포트(기본 '없음')로 명령 7을 저장 전에 422 `invalid-command`(detail `templateId`)로 막고, `controlDeliveriesOf`의 적용은 거절이라 `banner`에 ID가 실리지 않는다(되돌림 `{"banner": null}`만). ADR-0365 결정 2에 '바꿈' 줄이 있다. 재현 ①(HTTP 201 → 422, 목록 0건, 미리보기 422)과 ②(보낼 꼴에 `entry-delay` 없음)는 고치기 전 트리에서 실패한다. 남은 일: 명령 7은 F-03-5까지 쓸 수 없다(감독 결정대로). 명령 7을 예로 쓰던 기존 시험 셋(`command-lifecycle-http.test.ts`)은 시험 담당이 고치는 중이다.
- **RV-02 닫힘**: 리더 루프가 새 세대마다 회차 일보다 먼저 `q:{admission}:leader`를 올리고(`PLATFORM_BUMP_LUA`), 회차 범위 제어 쓰기는 쓰기 전에 그 키와 견준다(`PLATFORM_CHECK_LUA`, 올리지 않음). 전체 범위 쓰기는 `CONTROL_WRITE_LUA`의 `FENCE`가 같은 키로 막는다. 재현 ①(새 리더 `tick()` 뒤 옛 세대의 명령 11·명령 3 전체 FENCED, `q:{admission}:ctl` 그대로)과 ②(오픈 전 회차 FENCED, 쓰기 0)는 실제 리더 루프로 세대를 올리고, 고치기 전 트리에서는 APPLIED라 실패한다. 남는 창 둘은 막지 않는다(RV-16): 리더가 된 뒤 첫 `tick()` 전의 한 주기 동안 옛 세대가 통과하는 것은 회차 BUMP와 같은 모양이다. 회차 범위의 '견주기 → 회차 Lua 쓰기'는 슬롯이 달라 한 Lua로 묶을 수 없어 사이에 경주가 남는다. 두 창 모두 받는 쪽 판 비교가 늦은 명령이 새 명령을 덮지 못하게 막는다.
- **RV-06 닫힘**: `ControlFanout.deliver`의 시한이 min(처음 보낸 때 + 10초, `untilMs`)이다. 판매 중지·재개는 명령 하나에 시작 시각 하나를 서비스 둘이 함께 쓰고, 되돌리기·연장은 요청의 남은 시간(`requestUntilMs`)을 넘긴다. 재현 ①(purchase 9초 ack 뒤 queue 무응답 → 10초 안 FAILED `ack-timeout:queue-svc`)과 ②(남은 시간 3초 → 4초 안 FAILED)는 고치기 전 트리에서 각각 약 19초·10초라 실패한다. 남은 것(RV-15, 막지 않음): 되돌리기·연장의 시한은 재현 시험이 없다.
- **RV-03 닫힘**: 늘린 파드와 같은 이름으로 다시 띄운 파드에서 결제 시도·결제 접수 423을 실제 HTTP로 보고, 사본을 정지가 아닌 채로 두어 파드 메모리 확인(`pauseAwareSlots`)을 지나게 했다. 정본 '강제로'(죽이기)가 아니라 닫고 다시 띄우기이고 파드 수도 넷이다. 이것은 정리 목록감이다.
- **RV-04 닫힘**: ①은 답하지 않는 실제 gRPC 받는 쪽에 1,000ms(0.9초 전에는 끊지 않고 1.8초 안에 끊음) `DEADLINE_EXCEEDED`를 본다. 데드라인을 10초로 바꾼 틀린 구현을 잡는다. ②는 명령 3 접수 응답 `DISPATCHED`, 받는 쪽이 답한 뒤 `ACKED`를 본다.
- **새로 더한 지적(막지 않음, 정리 목록감)**:
  - RV-15(낮음, 통과 기준): `untilMs`가 요청 남은 시간 전부라 FAILED를 쓰고 답할 여유가 없다. 남은 시간 3초 시험도 승인 응답의 상태 코드를 단언하지 않는다. 몇백 ms 여유를 빼고 응답 코드를 단언하길 권한다. 되돌리기·연장의 시한 시험도 같이 둔다.
  - RV-16(낮음, 동시 실행): RV-02에서 남은 두 창. ADR-0365 결정 5에 한계로 적는다.
- **막는 지적**: 남은 것 없음. 새 막는 지적 없음.
