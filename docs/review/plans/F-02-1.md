# 기능 계획: F-02-1(제어 gRPC `ApplyControl` 전면 — 판 번호 원장·받는 파드 ack·받는 쪽 저장)

- **진행**: 계획 끝, 감독 결정 반영(2026-11-23). 다음은 구현.
- **무엇**: BUILD_ORDER '기능 단위 계획' F-02-1(갈래 4, 등급 A, OPS-300, WBS 2.5일, 단계 줄 `OPS-300 wbs 4.4.2 ①`)의 작업 목록이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **쉬운 말**: 관제 명령(입장 목표, 입장 멈춤, 판매 멈춤, 공지, 자동 제어 멈춤)을 받는 서버마다 '판 번호'를 붙여 저장하게 하고, 관제 서버가 준비된 모든 파드에게서 "그 판을 적용했다"는 답(ack)을 받아야 끝난 것으로 친다. 판 번호는 그 범위·종류에서 늘어나기만 하는 수라, 늦게 온 옛 명령이 새 명령을 덮지 못한다. 카프카로 퍼지는 설정형 명령의 적용 확인과 사전 모의 센 값은 F-02-5가 한다.
- **바탕**: `D:/ticketpass-lane4-F-02-1`, 가지 `feature/lane4-F-02-1`, 기준 `origin/develop` `450ab6cd7`(BAT-355·BAT-360 포함). 계획 담당은 제품·시험 코드를 쓰지 않았고 시험·Docker를 돌리지 않았다.
- **차례**: A 정방향(ADR-0281, ADR-0354): 계획 → 구현 → 시험(기준 커밋 트리에서 실패 확인) → 리뷰 → 리뷰 반영 → 검증 → 기록. 계획 커밋에 `Batch-Order: impl-first`.
- **한 줄 결론**: 제어 gRPC는 판매 중지 한 종류를 purchase·queue 한 파드씩에만 보낸다. admission-ctrl에는 제어 포트가 없고, 판 번호는 명령의 바뀐 시각이다. 빈칸은 ADR-0365로 정했다. 크기가 5일 어림이라 감독 결정으로 설정형 명령·적용 확인·`PreviewControl` 몫을 F-02-5로 나눴다(2절 1).

## 2. 감독에게

올린 것에 감독이 2026-11-23에 답했다(감독 결정 2026-11-23). 이 계획은 그대로 따른다.

1. **크기와 나누기** — (가) 지금 나눈다. 어림은 모두 약 5일 [가정]이었다(이 기능 몫 약 3일, 나눈 몫 약 2일). F-02-1은 ADR-0365 결정 1~8(장부 C-T50·Q-T30·ASVS 넷)이다. 결정 9~11(설정형 명령 5·7·8·9 내기, 적용 확인, `PreviewControl`, 장부 C-T6 ①·C-T51·C-T54·ASVS 1.3.6·2.3.3)은 새 기능 **F-02-5**(A, OPS-300, 2.00일, 선행 F-02-1)로 갔고, 이 계획 결정 반영 커밋이 기능 표에 그 행을 더했다. 단계 줄 OPS-300은 F-02-5가 끝날 때 체크한다. 아래 절의 'F-02-5' 표시는 그 기능 계획이 쓸 참고다.
2. **명령 3의 ops 쪽 전송** — (가) F-02-1이 명령 3을 세 받는 쪽에 보내고 ACKED까지 한다(C-T50이 '명령 3이 ACKED인 회차'를 요건으로 한다). F-02-2에는 명령 3의 비상 런북 길과 명령 6이 남는다. 대기 상태 파일은 이미 notice의 `paused`를 읽는다(HOT-010).
3. **kind·배포 차트는 구간 5로(ADR-0331 결정 9)** — 그대로 미룬다. 단계 줄의 admission-ctrl 배포 차트(Lease RBAC, 리더 전용 Service·`role=leader` 라벨, `pod-deletion-cost`), 차트의 `PEAKET_PROMETHEUS_URL`, 서비스마다 `<서비스>-control` Service, kind의 리더 교체 시험(Q-T12·G-09, Q-T30의 'API 서버 연결만 끊기')은 kind e2e가 곧 시험인 배포 몫이라 F-09-8(INF-020, 구간 5)이다. Q-T12는 이미 '자동 시험'이라 상태는 그대로 두고 범위에서만 뺐다(결정 9 '장부는 정직하게'). F-09-8 비고는 감독 몫이라 고치지 않는다.
4. **온세일 `LOG_SAMPLING` 내기·C-T75 ①④** — 받는 쪽은 갈래 1 BAT-215(아직 `develop`에 없음)다. 이 기능에서 빼고, BAT-215가 합쳐진 뒤 감독이 정할 기능이 한다.
5. **번호** — ADR-0365(0366·0367은 비워 둠). 마이그레이션 ops-svc **0025**(`control_version`·`command_delivery`), purchase-svc **0033**(`sale_control` 칸 셋). 0026·0027·0034는 쓰지 않는다. admission-ctrl·queue-svc는 Redis만 써서 마이그레이션이 없고, 다른 서비스 마이그레이션도 없다.
6. **갈래 2 F-03-1(관제 콘솔 호스트·ops-svc REST/SSE)과 겹칠 파일** — ops-svc에서 이 기능이 고친다. 겹칠 위험이 큰 것에 ★.
   - ★ `services/ops-svc/src/app.module.ts`(`CommandsModuleExtras` 손잡이: 대상 찾기), ★ `src/main.ts`(환경 값 조립)
   - ★ `src/modules/commands/inbound/command-view.ts`(`delivery` 칸을 채운다), `commands.module.ts`, `index.ts`
   - `src/modules/commands/domain/`: `ports.ts`, 새 `control-kinds.ts`, `command.ts`(판 칸)
   - `src/modules/commands/application/`: `execute-command.ts`, 새 `dispatch-control.ts`, `maintain-commands.ts`, `revert-command.ts`·`retry-command.ts`
   - `src/modules/commands/adapters/`: `db/drizzle-command-store.ts`, `memory-command-store.ts`, `command-store-base.ts`
   - `src/adapters/grpc-control-sender.ts`, `http-command-executor.ts`, 새 `src/adapters/control-targets.ts`
   - `migrations/0025_control_dispatch.sql`과 Drizzle journal
   - 고치지 않는다: `src/modules/live/`, openapi ops 경로(`delivery`는 이미 계약에 있다), `control.proto`(F-02-5가 고친다). 갈래 2와의 겹침은 감독이 알렸다: 먼저 합친 쪽을 뒤가 rebase로 받는다(감독 결정 2026-11-23).
7. **넘겨받은 것 확인** — FND-080(ops Outbox `writeOutbox`·`CONTROL_TOPICS.settings`)은 BAT-360이 일반 `publishSetting`·릴레이로 끝냈다. 이 기능은 그것을 쓴다. PRF-090·HOT-030·PRF-138·HOT-010의 넘긴 것은 3.1에 모두 넣었다. BAT-355의 `PreviewControl`(ADR-0340 결정 11)은 F-02-5다.

## 3. 범위

### 3.1 하는 것

- **판 원장과 퍼뜨리기(ADR-0365 결정 1~4)**: ops DB `control_version`·`command_delivery`(0025), 처음 `DISPATCHED` 때 판 매기기, 대상 찾기 포트(헤드리스 DNS·주소 목록), 준비된 모든 파드에 동시에 보내기·1초마다 같은 판으로 다시 보내기·다시 풀기·10초 실패, 배경 작업과 정비 바퀴의 이어 보내기, `delivery`(ACK) 보이기. 명령 1·2(연장·만료 되돌림 포함)·3(감독 결정 2)·7·11 전송과 되돌리기. 판매 중지·재개를 같은 원장·찾기로 옮김.
- **admission-ctrl 받는 쪽(결정 5·6)**: 제어 포트(`PEAKET_ADMISSION_CONTROL_GRPC_PORT`), 리더만 쓰기·세대 확인 Lua, 종류 1·2·3(회차·전체)·11과 판·명령 칸, 리더 루프가 `q:{admission}:ctl` `allPaused`를 읽어 전진 0. PRF-090·HOT-030의 칸(`target`·`targetUntil`·`admitPaused`·`admitPausedUntil`·`paused`·`aimdResumeAt`·`autoStopped`).
- **purchase-svc 받는 쪽(결정 6~8)**: `SALE_PAUSE`(회차·`PLATFORM`)를 `sale_control`(0033 칸 셋)과 `s:{event:E}:ctl`(`paused`·`pausedRev`, 전체는 `s:ctl:events`의 회차마다 `allPaused`·`allRev`)에, 시작 작업의 제어 상태로 넘기기, 2초 다시 맞춤(메모리와 사본), 결제 시도·접수의 메모리 확인, `SessionSweeper`의 유휴 시계(PRF-138).
- **queue-svc 받는 쪽(결정 6)**: `SALE_PAUSE`·`LOBBY_BANNER`를 `q:{event:E}:notice`(전체는 `q:{event:PLATFORM}:notice`)에(HOT-010 칸과 판·명령 칸).

## 7. 손댈 파일(구현 담당 몫, 시험 파일 제외)

- ops-svc: 2절 6의 목록. 새 환경 값은 `PEAKET_<서비스>_CONTROL_GRPC_ADDRS`(지금의 `…_ADDR` 하나도 받음)와 운영의 헤드리스 이름. `migrations/0025_control_dispatch.sql`(`control_version`, `command_delivery`, 명령 기록의 판 칸, `ops_app` 권한).
- admission-ctrl: 새 `src/control/control-server.ts`, `src/modules/leader/`의 `adapters/leader-lua.ts`(제어 쓰기 Lua, `FENCE` 재사용)·`adapters/redis-leader-store.ts`(쓰기·`allPaused` 읽기)·`domain/ports.ts`·새 `application/apply-control.ts`·`application/admission-leader.ts`(전체 정지 반영, 쓰기 전 세대 확인)·`index.ts`, `src/start.ts`(포트).
- purchase-svc: `src/control/control-server.ts`(`SALE_PAUSE`), `src/modules/sale-control/`(새 `application/set-sale-pause.ts`, `domain/ports.ts`·`sale-control.ts`, `adapters/db/schema.ts`·드리즐 저장소, `adapters/redis-sale-control-copies.ts`, 새 다시 맞춤 `application/reconcile-sale-control.ts`, `index.ts`), `src/modules/inventory/application/session-sweeper.ts`(유휴 시계), `src/start.ts`(`controlState`·다시 맞춤·조립), `migrations/0033_sale_control_pause_revision.sql`과 journal.
- queue-svc: `src/control/control-server.ts`, `src/modules/sale/`(notice 쓰기 Lua·`domain`·새 쓰임새), `src/start.ts`.
- 계약은 고치지 않는다(`control.proto`의 `PreviewControl`과 core-svc 설정 읽기는 F-02-5).
- `packages/platform`은 고치지 않는 것이 기본이다. 고쳐야 하면 구현 메모에 까닭을 적는다(전체 node 잡이 돈다).

## 8. 공개 인터페이스

- **gRPC**: `ControlReceiver.ApplyControl` 종류 `ADMISSION_TARGET`·`ADMISSION_PAUSE`·`SALE_PAUSE`·`LOBBY_BANNER`·`AUTOMATION_STOP`(받는 쪽 65 2 표), 오류 `INVALID_ARGUMENT`·`UNIMPLEMENTED`·`UNAVAILABLE`(`not-leader`·`fenced`). 메시 쌍은 그대로(MS-09·MS-19 변화 없음).
- **REST**: 바뀌는 경로 없음. `CommandState.delivery`를 채운다(계약 그대로). 승인·실행 응답의 상태가 카탈로그 명령에서 `DISPATCHED`가 될 수 있다(계약 열거 안).
- **모듈 공개 면**: ops-svc commands `ControlDispatcher`(`dispatch(command)`, `resume(commandId)`), `ControlTargets` 포트, `controlKindOf(command)`. F-02-2가 명령 6·런북 길에 쓴다. admission-ctrl `ApplyLeaderControl`, purchase-svc `SetSalePause`·`SaleControlReconciler`, queue-svc `SetQueueNotice`.
- **지표·로그**: 새 지표 이름은 정본에 없으면 만들지 않는다. 로그는 명령 ID·판·서비스·파드·결과 한 줄(계정·가명 참조 없음).

## 10. 실패 확인

- A 기능이라 시험 담당이 기능 가지의 기준 커밋 `450ab6cd7` 트리(구현 전)에서 새 동작의 시험이 실패하는 것을 본다(ADR-0281 결정 3, ADR-0331 결정 2).

- 이 절에는 명령·시험 수·실패 수·실패 까닭 한 줄만 적는다(ADR-0331 결정 8).

## 13. 자주 놓친 결함(시험·구현 지시문에 넣는다)

- Lua·저장소 응답은 정확한 값까지: 받는 쪽이 돌려준 판, 쓴 칸의 값과 판·명령 칸 모두, `delivery`의 수와 파드 이름.
- 건드린 키를 모두 확인: 전체 범위 명령 3은 `s:ctl:events`의 회차마다 사본, `q:{admission}:ctl`, `q:{event:PLATFORM}:notice`. 다른 종류의 칸(`suspended`·`suspRev`)은 그대로인지.
- 경계는 양쪽: 10초(− 1ms·정각), 2초 다시 맞춤, 풀린 시각 + 5분. 가짜 시계, 시험 값은 코드 상수와 다르게, 판은 9 → 10 두 자리.
- 허용 목록은 밖의 값마다: 종류(받지 않는 종류 셋 이상), 범위(`PLATFORM`·회차·빈 글·대문자 UUID), 환경(local·ci·demo·staging·production에서 주소 설정 없음).
- 판정만 보지 말고 부르는 쪽이 쓰는지: 받는 쪽 거절 → ops 명령이 ACKED가 되지 않음, 423이 실제 HTTP 응답으로 나옴.
- 장애 주입은 끊긴 사례 수를 단언(9절 끝).
- 시작 파일(`start.ts`·`main.ts`)의 조립은 시험 조립과 따로 띄워 본다: 제어 포트가 열리고 `controlState`가 넘어가는지.
- 정본 시험 표에 세부 번호를 더하면 '연결: …' 앞에 둔다.
