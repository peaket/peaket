# F-04-11 계획 — 기록 고정·해시 사슬·후보 R1~R6·결과 지문 (동결 로컬)

- **무엇**: 기능 표 F-04-11(LCH-250)의 동결 로컬 트랙 계획이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **등급**: B(`Batch-Grade: B`). 빠른 길(ADR-0373 결정 3)이라 역할 나누기 없이 계획 → 시험 → 구현 → 기록을 한 세션이 한다. 다만 시험을 먼저 쓰고 기준 트리에서 실패를 본 뒤 구현한다.
- **동결 로컬 범위**: 이 기능은 v1 출시 범위 밖이다(ADR-0373 결정 2, ADR-0386 결정 4·5, `docs/release/v1-scope.md` F-04-11). `freeze/lane6-F-04-11` 가지와 `D:/ticketpass-freeze-F-04-11` 워크트리에서만 개발하고 `develop`·`release/1.0.0`에 합치지 않는다. 출시 마이그레이션·릴리스 플래그·`deploy/` 값을 건드리지 않는다.
- **바탕**: `8d2aeab72`(F-04-10 가지 끝, 2026-11-25). F-04-10이 만든 `inv` 표 넷·`inv_ingest_progress`·시험 시드와 F-04-9가 만든 사건 형식 v2·생성기를 입력으로 쓴다.
- **이번 턴에 하는 것**: 순수 계산(해시 사슬·후보 규칙·지문)과 실제 ClickHouse `inv` 읽기까지. ops DB 쓰기·`ops_event`·모니터링·2시간 첫 후보 측정은 F-04-12와 측정 창 뒤로 미룬다(§10).

### 1.1 장부 범위를 FX-T11·FX-T14로 좁힌다

- F-04-11의 장부 범위 칸은 `docs/features/forensic-replay.md, FX-T11, FX-T14, docs/security/asvs/forensic-replay.md`였다. 장부 도구는 정본 문서 경로가 있으면 그 문서의 판정 항목을 모두 끌어와 FX-T1~FX-T24와 ASVS L1~L3 행까지 **100개 이상**을 F-04-11 범위로 잡았다.
- 이 기능이 만드는 것은 기록 고정·해시 사슬·후보 R1~R6·지문이고, 그 판정은 FX-T11·FX-T14다. FX-T12·FX-T13·FX-T15~FX-T24는 F-04-12~F-04-19가, ASVS 행은 각 기능의 추적 표가 맡는다. §8.6 3의 "장부 범위가 넓어 그 기능과 닿지 않는 항목이 들면 기능을 시작할 때 범위를 좁힌다"에 따라 장부 범위 칸을 `FX-T11, FX-T14`로 좁힌다. 정본 문서는 '완료 정의'의 판정 칸에 그대로 남는다.
- 상태(`동결`)·분류(`frozen-local`)는 바꾸지 않으므로 `node tools/ci/release-scope.mjs --check`의 대조에 영향이 없다.

### 1.2 정본에 없는 값과 이번에 정한 것(추천 적용 2026-11-25)

1. **해시에 넣는 칸**: `ingest_rank`는 저장 판 칸이고 `retain_until`은 보존 메타데이터라 뺀다. 나머지 칸을 넣는다. `DateTime64(3)` 칸은 서버 출력 모양에 기대지 않도록 `toUnixTimestamp64Milli`로 정수 밀리초로 바꿔 읽는다. 칸 목록은 `snapshot.ts`의 `HASH_COLUMNS`에 표마다 고정한다.
2. **정규화 모양**: RFC 8785(JSON을 한 가지 모양으로 적는 규칙)를 따르는 정규 JSON은 키를 UTF-16 순으로 정렬하고 공백 없이 적는다. 숫자는 ECMAScript `JSON.stringify`의 수 표기를 쓴다. `NaN`·`Infinity`·`undefined`는 거절한다.
3. **표 해시**: 표의 정렬 키 순으로 행을 늘어놓고, 행마다 정규 JSON 한 줄을 만든 뒤 `\n`으로 잇고 마지막에 `\n`을 붙인 UTF-8 바이트의 SHA-256이다. 해시 함수 안에서 정렬하므로 입력 행 순서가 달라도 같다.
4. **판 해시**: `SHA-256("PEAKET-fraud-snapshot-v1" ‖ "\n" ‖ 회차 ID ‖ "\n" ‖ 판 ‖ "\n" ‖ 직전 판 해시(판 1은 빈 글) ‖ "\n" ‖ 표 해시 넷을 `inv_request`·`inv_step`·`inv_behavior`·`inv_link` 순으로 `\n`으로 이은 글)`. 16진 소문자로 적는다.
5. **고정 기다리기**: 목표는 온세일 끝 + 5분(T+65분), 마지막 기한은 목표 + 30분(T+95분)이다. 적재 진행이 목표 이상이면 바로 고정하고 `late=false`, 목표에 못 미치고 지금이 기한 이상이면 `late=true`로 고정한다. 그 사이는 기다린다. 목표와 같은 값은 '따라왔다', 기한과 같은 값은 '늦은 적재'다.
6. **판 범위**: 판 1은 `ingested_at ≤ frozen_at`, 판 N은 `range_from < ingested_at ≤ frozen_at`이다. `range_from`은 직전 판 `frozen_at`이다.
7. **후보 규칙 값**: R1 강한 연결 3·약한 연결 1, R2 2, R3 2(같은 입장 링크를 다른 기기에서 다시 씀은 3), R4 1, R5 4, R6 4. 구매 점수는 `P > L`이면 3, `P ≥ 3L`이면 5. 범주는 8 이상 `HIGH`, 5~7 `MEDIUM`, 4 이하 `LOW`다. 모두 §6.7.3의 [가정] 값이다.
8. **약한 연결 묶음 상한**: 결제 수단은 정확히 2계정일 때만 약한 연결이고 3계정 이상이면 강한 연결이다. 같은 IP는 10분 창에 그 IP를 쓴 계정이 20개 이하일 때만 약한 연결이다(정본). 같은 호스팅·프록시 ASN도 **20계정 이하일 때만** 약한 연결로 센다. 정본은 ASN에 상한을 적지 않았지만, 큰 호스팅 ASN 하나로 수천 계정이 약한 연결 한 종류를 갖게 되면 규칙의 뜻이 사라지므로 IP와 같은 상한을 둔다(추천).
9. **후보 조건**: R5는 계정 하나도 후보고, R3의 다시 쓴 입장 링크와 R6은 계정이 둘 이상일 때 후보로 올린다. `P > L`도 계정이 둘 이상일 때다. 그 밖의 묶음은 결과에만 남기고 `candidate=false`로 둔다.
10. **R5 판정**: 같은 여정에 `ADMIT` 단계가 없는데 `HOLD_TRY`가 있으면 '입장 토큰 없는 홀드 시도'로 본다. 시드의 `plant-acct-bypass`가 이 모양이다.
11. **R3 다시 쓴 입장 링크**: `ADMIT` 단계의 `queue_entry_id`가 같은데 여정별 기기 가명(`inv_link` `DEVICE`)이 둘 이상이면 다시 쓴 것으로 본다.
12. **R4 기준선**: 판매 시작부터 단계까지의 첫 소요 시간을 단계별로 모아 하위 0.1%보다 짧은 단계가 둘 이상이면 신호를 준다. 표본이 100개 미만인 단계는 기준선을 만들지 않는다(작은 시드에서 우연한 신호를 막는다).
13. **구매 수**: `SALE` 좌석 수 합에서 `CANCEL` 좌석 수 합을 뺀다. 좌석 목록이 빈 `SALE`은 1장으로 센다.
14. **대상 계정**: 그 회차에서 `HOLD_TRY`를 했거나 표를 산 계정만 후보 계산 대상이다. 요청·행동 요약에만 나오는 계정(시드의 이동통신 50·행동 10)은 대상이 아니다(§6.7.3 첫 문단).
15. **지문**: `result_fingerprint`는 `{eventId, snapshotVersion, ruleVersion, clusters[]}`를 정규 JSON으로 적은 SHA-256이다. 묶음은 가장 작은 계정 ID 순, 묶음 안 계정·신호·공유 속성은 정렬한다. 점수 원값은 지문에도 공개 결과에도 넣지 않고 범주만 넣는다.
16. **바깥 출력**: 이번 턴의 실행기는 계산 결과를 JSON 한 줄로 낸다. ops DB `fraud_snapshot`·`fraud_cluster_run`·`fraud_cluster`·`fraud_cluster_member` 쓰기와 `ops_event` 줄은 F-04-12가 ops-svc 조사 모듈에 붙인다(§10).
17. **외부 게시물**: R6 입력은 이번 턴에 JSON 파일로 받는다. `external_post` 표는 F-04-12·F-04-19 몫이다.

## 2. 목표와 비목표

**목표**

1. `inv` 표 넷을 `inv_reader`로 읽어 표 해시 넷과 판 해시를 만들고, 직전 판 해시를 이어 사슬을 만든다. 같은 판을 다시 계산하면 같은 해시가 나온다.
2. 판 범위를 `ingested_at`으로 가르고, 고정 대기·늦은 적재를 순수 상태 기계로 판정한다. 판매 종료 뒤 판 더하기를 멈춘다.
3. 후보 규칙 R1~R6을 순수 함수로 만든다. 강한·약한 연결의 연결 요소가 묶음이 되고, R2~R6은 묶음에 근거 신호로 붙는다.
4. 구매 수 대 한도·점수 범주·공유 속성·후보 여부를 정본 값으로 계산하고, 같은 입력이면 같은 결과 지문을 낸다. 입력 행 순서를 섞어도 같다.
5. 실제 ClickHouse에 F-04-9 생성기 시드(F-04-10 `inv` 표)를 넣고, 해시 사슬과 후보 묶음(결제 수단 9계정 27장)을 끝에서 끝까지 확인한다.
6. 해시 검증이 불일치를 내면 SEV2·보안 사고 기록 대상임을 나타내는 결과를 돌려준다.

**비목표(이번 턴에 하지 않는다)**

- ops DB 쓰기·마이그레이션·`fraud_snapshot`/`fraud_cluster*` 영속화, `ops_event` 로그 파이프라인, 관제 감사 기록·공개 체크포인트.
- 후보 실패의 자동 세 번 재시도·`fraud-run-retrying`·다시 돌리기 API(F-04-12·F-04-19).
- 1시간마다 판 더하기 스케줄러·외부 게시물 등록 10분 안 판 더하기·공연 날짜 정비 잡.
- 첫 후보 2시간·p95 20분, 기록 고정 30분·해시 10분 측정(FX-T22, 측정 창 뒤).
- 화면(SCR-069~071), 조사 API, 사건 상태 전이, 증거 묶음.
- 증거 묶음 내보내기 차단의 실제 호출(F-04-19).

## 5. 실패 시나리오와 엣지 케이스

1. **모듈이 없다**: 시험 첫 실행은 `ERR_MODULE_NOT_FOUND`다. 이 실패는 세지 않는다. 빈 껍데기를 두고 단언 실패를 본 뒤 구현한다.
2. **행 순서**: 같은 행을 섞어 넣어도 표 해시가 같아야 한다. 정렬 키가 같은 행이 둘 이상이면 정규 JSON 줄 순으로 한 번 더 정렬해 결정적으로 만든다.
3. **한 행 바꾸기**: 판을 계산한 뒤 같은 키의 행을 더 이른 `ingested_at`으로 바꿔 넣으면 `verifySnapshot`이 그 표를 불일치로 낸다.
4. **판 경계**: `ingested_at = range_from`인 행은 다음 판에 들지 않고, `= frozen_at`인 행은 든다.
5. **판 1의 `range_from`**: `null`이고 `prev_hash`도 `null`이다. 판 2의 `prev_hash`는 판 1의 `inv_hash`와 같아야 한다.
6. **대기 경계**: 적재 진행이 T+65분과 같으면 `late=false`, T+64분 59.999초면 기다림, T+95분과 같으면 `late=true`다. T+95분인데 진행이 T+65분을 넘었으면 `late=false`다.
7. **판매 종료**: `now = saleEndsAt`이면 새 판·새 후보를 만들지 않는다. 그 전이면 만든다.
8. **점수 경계**: 8은 `HIGH`, 7은 `MEDIUM`, 5는 `MEDIUM`, 4는 `LOW`다. 구매 점수는 `P = L`이면 0, `P = L+1`이면 3, `P = 3L`이면 5다. `L = 0`은 입력 오류다.
9. **강한·약한 연결**: 결제 수단 3계정은 강한 연결, 2계정은 약한 연결 하나다. 약한 연결 하나만으로는 묶이지 않고, 서로 다른 종류 둘이 같은 두 계정에 있으면 묶인다. 강한 연결 하나는 그것만으로 묶인다.
10. **같은 IP 상한**: 10분 창에 21계정이 같은 IP를 쓰면 그 IP는 어떤 약한 연결도 만들지 않는다. 20계정이면 만든다. 창 밖(10분 + 1ms)은 다른 창이다.
11. **ASN 상한**: 호스팅·프록시 ASN 20계정 이하는 약한 연결, 21계정 이상은 세지 않는다. `net_class`가 `OTHER`인 ASN은 세지 않는다.
12. **R2**: 같은 단계를 200ms 안에 밟은 계정이 여럿인 단계가 3개 이상이면 신호를 준다. 2개면 신호가 없다. 200ms와 같은 차이는 포함한다.
13. **R3**: 같은 IP·기기에서 10분 안에 5계정 이상을 오가면 근거 신호다. 같은 `queue_entry_id`의 `ADMIT`가 기기 둘 이상에서 나오면 다시 쓴 입장 링크다(점수 3).
14. **R4**: 표본 100개 미만이면 기준선을 만들지 않는다. 하위 0.1%와 같은 값은 '짧다'로 세지 않는다(엄격 미만).
15. **R5**: `ADMIT` 없는 `HOLD_TRY`가 있는 여정의 계정은 계정 하나여도 후보다. 여정 ID가 빈 사건은 R5로 세지 않는다.
16. **R6**: 묶음이 산 좌석과 외부 게시물 좌석이 하나라도 맞으면 신호를 준다. 좌석 번호는 문자열로 견준다.
17. **행동 요약**: 후보 입력에 `inv_behavior`를 넣지 않는다. 넣어도 규칙이 읽지 않는다. 행동만 비슷한 10계정은 대상 계정이 아니므로 묶음이 없다.
18. **지문**: 같은 입력이면 같고, 규칙 판·고정 판·계정 ID 집합·신호·구매 수 가운데 하나가 달라지면 다르다. 묶음 순서·계정 순서를 섞어도 같다.
19. **정수·범위**: 한도는 1 이상, 구매 수·계정 수는 0 이상 정수, 시각은 유한한 밀리초다. 아니면 던진다(ASVS 1.4.2).
20. **순수성**: `computeClusters`는 입력 배열을 바꾸지 않고, 팬 계정·티켓 상태를 만드는 코드가 없다. 시험은 입력의 깊은 복사 전후를 견준다.

## 10. 미룬 것과 남는 위험

1. **ops DB 영속화**: `fraud_snapshot`·`fraud_cluster_run`·`fraud_cluster`·`fraud_cluster_member` INSERT와 마이그레이션은 F-04-12가 ops-svc 조사 모듈에 붙인다. 이번 턴은 JSON 결과까지다. FX-T14의 '남기는 곳'은 그때 완성된다.
2. **운영 사건·감사**: `ops_event` `FRAUD_SNAPSHOT`·`FRAUD_CLUSTER_RUN`, 관제 감사 기록, 공개 체크포인트(ADR-0075)는 F-04-12·F-04-19 몫이다.
3. **하루 검증·SEV2**: `verifySnapshot`이 불일치와 SEV2 대상 결과를 돌려주는 데까지 했다. 하루 한 번 실행·보안 사고 기록·증거 묶음 내보내기 차단은 F-04-12·F-04-19가 잇는다.
4. **스케줄러**: T+60분 고정, 1시간마다 판 더하기, 외부 게시물 등록 10분 안 판 더하기는 CronJob·배포 몫이다. 이번 턴은 한 번 실행하는 명령이다.
5. **측정**: 첫 후보 2시간·p95 20분, 고정 30분·해시 10분, 1천만 행 규모는 FX-T22·측정 창 뒤에 잰다. 이번 통합 시험은 1,000석 시드다.
6. **외부 게시물 표**: R6 입력을 JSON 파일로 받았다. `external_post` 표와 등록·대조 경로는 F-04-12·F-04-19 몫이다.
7. **자동 재시도**: 실패 시 세 번 다시 하기와 `fraud-run-retrying`은 F-04-12 몫이다.
8. **ASN 상한**: 정본에 없는 20계정 상한을 두었다(§1.2 8). 큰 호스팅 ASN의 오탐을 막으려는 추천이고, 운영 값은 규칙 판 설정으로 다시 정한다.
