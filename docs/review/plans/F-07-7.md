- **무엇**: 기능을 시작할 때 만든 작업 목록이다(docs/architecture.md §8.6 4의 1, ADR-0256 결정 10, ADR-0354). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane5-F-07-7`, 가지 `feature/lane5-F-07-7`. 2026-11-23 작성. 감독이 이 가지를 F-07-6 계획 최신 커밋 `ee16969f5`(그 아래 develop: F-07-5 합침 `f0c0206da` R-781, FIX-payment-int R-780, FIX-problem-types R-784, FIX-invariant-m3 R-785) 위로 다시 쌓았다. 차례는 새 개발 차례다(소유자 결정, ADR 0372·ADR 0373 A 등급): 계획 → 시험(구현 전, 기준 트리 = 이 계획의 마지막 커밋에서 새 동작 시험이 실패하는 것을 봄) → 시험 리뷰(새 세션) → 반영(시험 담당) → 시험 고정 → 구현(고정한 시험만 통과하면 되고, 구현 담당은 시험을 고치지 못함) → 게이트(시험·타입 검사·린트·`gen:check`·develop CI node 잡)·합치기. 구현 뒤 리뷰·검증·틀린 구현 표본은 없다. **시험은 지금 쓸 수 있다**(§5.1과 F-07-6 계획 §5.1의 모양으로, F-07-6 구현이 없으니 기준 트리에서는 가져오기부터 실패한다). **구현은 F-07-6 구현이 develop에 합쳐지고 이 가지를 그 위로 다시 쌓은 뒤 시작한다.** 기한은 2026-11-30이다(ADR 0373, §3.1). ADR 0372·0373은 develop(`549d7f0c7`·`29427d73c`)에 있고 이 가지에는 다시 쌓을 때 들어오므로, 문서 점검의 ID 대조를 피하려고 번호를 띄어 적었다.
- **등급**: A다(docs/BUILD_ORDER.md F-07-7). 판매 승인의 지급대행 조건, 정산 계좌 변경(남의 계좌로 돈이 나가는 길), 이미 접수된 예약지급 취소, 포트원 지급 결과와 콘솔 우회를 잡는 사후 대사에 돈이 걸린다.

## 브라우저 확인

브라우저 확인은 기한의 마지막 날 한 번 한다(ADR 0373 결정 3). §3.1의 줄인 안으로 화면(SCR-020·027·048)을 모두 빼면 이 절은 하지 않고, 서버 경계는 HTTP 시험으로만 본다.

SCR-020 정산 계좌(`/settings/payout`)와 SCR-027(`/events/[id]/settlement` 정산서 탭)을 실제 서버로 본다(내 계정·SCR-048은 동결이라 보지 않는다). 기능 끝에 감독이 스킬 `peaket-browser-check`로 하고 결과는 브라우저 확인 폴더(`docs/review/browser-check/`)의 `F-07-7.md`에 남긴다.

- **실제 서버(기본)**: 로컬 데모 무대(`tools/local/README.md` '로컬 데모 무대', 클러스터 `lane4-demo`)를 이 가지에서 쓴다. 차례는 F-07-5 계획 '브라우저 확인'의 ①~④와 같고, 다시 빌드할 이미지는 `bundle`(payment)·`core-svc`·`ops-svc`·`pg-simulator`·`partner`다. ① Docker 잠금 → `node tools/local/demo-images.mjs --build`(기존 이미지 셋은 다시 빌드). ② `node tools/local/cluster.mjs demo` → `demo-seed --apply`(판매 승인은 포트원·토스가 꺼진 기본 무대라 지금처럼 통과하고, core가 payment에 판매자 확인을 쓴다). ③ 포트원 플랫폼 켜기(로컬 데모 전용 예외, 결과 문서에 적는다): bundle에 `PEAKET_PAYOUT_PORTONE_ENABLED=true`·`PEAKET_PAYOUT_PORTONE_CONTRACT_ID=<흉내 계약>`을 넣고(데모 값 파일에 꺼진 채 두고 `kubectl set env`로 켬, 또는 구현 담당이 데모 값에 켜 둘지 정해 이 절을 고침) pg-simulator에 `/sim/portone/bank-account-holders`로 스텔라의 시험 계좌 → '(주)스텔라엔터테인먼트'를 넣는다(`kubectl exec`로 클러스터 안에서 부름). ④ hosts에 `127.0.0.1 partner.peaket.example console.peaket.example`(README 표)를 두고 파트너 콘솔 주소(README 표의 partner 포트)를 연다. 로그인은 `node tools/local/demo-auth.mjs admin stella-admin`(파트너 관리자), 패스키는 `node tools/local/demo-auth.mjs passkey stella-admin`이 주는 자격·개인키로 넣는다.

## 열린 질문(소유자·감독 결정)

- **Q-01(소유자, 감독이 보고)**: 실제 포트원 플랫폼(예금주 조회·파트너·수기 정산건·지급 내역)과 토스 지급대행 시험 서버를 부르는 잡을 켤지. 판단: 저장소의 포트원 시험 시크릿(`PEAKET_PG_PORTONE_SECRET` 등, GitHub 비밀 값과 로컬 `pg-secrets..env`)은 결제 채널용으로 발급된 것이다. 포트원 파트너 정산(플랫폼) 기능은 상점에 따로 신청·계약해야 켜지고 기본 계약 ID도 그때 생기므로, 지금 키로 예금주 조회·파트너 등록을 부를 수 있다고 보지 않는다(불러 보지 않았다). 예금주 조회는 건당 비용이 붙을 수도 있다(확인 필요, C-02). 토스 지급대행은 F-07-6 Q-01과 같다(보안 키가 계약 뒤). 그래서 이 계획은 결제사를 한 번도 부르지 않고, 공개 명세 모양 대역 서버와 pg-simulator로만 시험한다. 계약이 생기면 pg-smoke처럼 '매일 + 손으로' 도는 포트원 플랫폼 시험 잡(예금주 조회 1건·파트너 조회, 등록·정산건은 시험 상점에서만 [가정])을 켤지 정해 주기 바란다(추천: 계약 뒤 켬, 지금은 켜지 않음).
- **Q-02(감독, 풀림 2026-11-23)**: 감독 결정으로 나누지 않는다. 포트원 사후 대사를 I-13~I-15로 이 기능에 두고 일수는 4.25일(상한 5일 안)이다. 아래는 처음 물은 글이다. 포트원 사후 대사(출금 대사 J-T20, 파트너 계좌 대조와 `ACCOUNT_MISMATCH` J-T21, 원장 잔액 대조와 대사 멈춤 J-T22, 지표 넷, 15시 실행 기록 없음 경보, 포트원 결제분 잔액 대사)를 이 기능에서 빼고 새 기능 행으로 둘지. ADR-0108의 주 통제라 A이지만, 이 계획의 다른 A 항목(지급대행 등록·판매 승인 조건·계좌 변경·예약 취소·포트원 실행·화면)과 함께 2.75일에 들지 않는다. 포트원 실제 지급은 계약 전이라 일어나지 않는다. (가) 새 기능 행(A, 1.5일 [가정], 선행 F-07-7, 장부 범위 J-T20·J-T21·J-T22와 asvs 2.2.3·13.2.2 포트원 몫) (나) 이 기능을 4.25일로 늘림. 추천: (가). 감독이 번호를 정하면 기록 커밋에서 BUILD_ORDER에 한 줄을 더한다.
- **Q-03(감독, 추천대로 받아들임 2026-11-23)**: 판매 승인 조건을 '켜진 결제사만'으로 다시 거는 정본 결정(ADR-0370 결정 3·4, settlement §3 새 줄)을 받아들이는가. 계약·키가 없는 지금은 두 결제사가 꺼져 있어 승인은 지금처럼 되고, 그 파트너의 결제분은 지급 묶음에서 보류된다(ADR-0369 결정 4). 결제사 설정과 상관없이 켜면 로컬 데모와 모든 판매 승인이 멈춘다(추천: 받아들임, 이 계획 커밋에서 정본에 적었다).
- **Q-04(감독, 풀림 2026-11-23: 새 단계 LCH-125·새 기능 F-07-13)**: SCR-020 '내 계정'의 인증 앱 다시 등록·복구 코드 다시 만들기·로그인 기기 줄(d5 §6.1 ⑦)을 어느 단계가 맡는가. identity에 파트너용 경로가 없고 BOT-122는 패스키 줄만 넘겼다. 이 기능은 그 줄을 실제 화면에서 그리지 않는다(추천: identity 단계(F-03 계열) 한 줄로 받고, 그 전까지 C-03).
- **Q-05(감독, 추천대로 받아들임 2026-11-23)**: core-svc가 payment-svc 내부 HTTP를 부르는 새 쌍(메시 허용·ADR-0285 결정 9 표 보충)을 이 기능에서 더하는 것을 받아들이는가. 판매 승인이 지급대행 등록과 판매자 확인을 payment에 맡기려면 필요하다(ADR-0370 결정 4, 추천: 진행).
