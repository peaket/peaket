  - M-17 변경 행을 다른 트랜잭션에 쓴다 → J-T40 ⑦.
  - M-18 수기 정산건을 다시 실행 때마다 새로 만든다 → J-T41 ①.
  - M-19 09시 tick을 08:59에 돈다, 또는 보류 정산서를 빼지 않는다 → J-T41 ②.
  - M-20 포트원 FAILED에 자동 재요청한다 → J-T41 ③.

- **시험 담당에게(지시서 '자주 놓친 결함')**: 저장 결과와 사건은 칸 값까지 단언한다(은행·끝 4자리·판·보류 끝·결과·결제사별 결과·사건 금액). 시간 한도(3영업일, 09:00, 30분)는 가짜 시계로 경계 직전(−1ms)과 경계를 둘 다 재고, 기대값은 정본 값으로 적고 코드 상수를 가져오지 않는다. 시험의 판 번호는 9 → 10처럼 두 자리를 한 번 넣는다. 허용 목록(셀러 상태 여섯 가운데 둘, 결과 셋, CS 종류, 감사 칸)은 목록 밖 값마다 거부를 본다. 세 상태(켜짐·꺼짐·등록 있는데 꺼짐)를 모두 둔다. 판정 함수만이 아니라 바깥 경계(파트너 PUT 주입 → 대역 서버가 받은 요청·DB 행, core 승인 → payment 대역이 받은 호출)에서 결과가 실제로 쓰이는지 본다. 겹친 가드(If-Match 판과 jti, 지급 건 조건부 갱신과 정산서 조건부 전이)는 하나씩 빼서 각각을 잡는 시험을 둔다. `start.ts`의 포트원 플랫폼 조립과 core의 payment 주소 조립은 시험 조립과 따로 띄워 본다. 통합 시험은 실제 PostgreSQL에서 두 연결로 경합을 끼워 넣는다. 빈 결과(대역 서버가 받은 요청 0건, 감사 보낸 행 0)가 '통과'로 새지 않게 건수를 단언한다. 화면은 운영 빌드의 첫 JS 예산을 로컬에서 잰다.

## 브라우저 확인

SCR-020(`/settings/payout`·`/settings/account`)과 SCR-027(`/events/[id]/settlement` 정산서 탭), SCR-048 확인 패널을 실제 서버로 본다. 기능 끝에 감독이 스킬 `peaket-browser-check`로 하고 결과는 브라우저 확인 폴더(`docs/review/browser-check/`)의 `F-07-7.md`에 남긴다.

- **실제 서버(기본)**: 로컬 데모 무대(`tools/local/README.md` '로컬 데모 무대', 클러스터 `lane4-demo`)를 이 가지에서 쓴다. 차례는 F-07-5 계획 '브라우저 확인'의 ①~④와 같고, 다시 빌드할 이미지는 `bundle`(payment)·`core-svc`·`ops-svc`·`pg-simulator`·`partner`·`console-host`다. ① Docker 잠금 → `node tools/local/demo-images.mjs --build`(기존 이미지 셋은 다시 빌드). ② `node tools/local/cluster.mjs demo` → `demo-seed --apply`(판매 승인은 포트원·토스가 꺼진 기본 무대라 지금처럼 통과하고, core가 payment에 판매자 확인을 쓴다). ③ 포트원 플랫폼 켜기(로컬 데모 전용 예외, 결과 문서에 적는다): bundle에 `PEAKET_PAYOUT_PORTONE_ENABLED=true`·`PEAKET_PAYOUT_PORTONE_CONTRACT_ID=<흉내 계약>`을 넣고(데모 값 파일에 꺼진 채 두고 `kubectl set env`로 켬, 또는 구현 담당이 데모 값에 켜 둘지 정해 이 절을 고침) pg-simulator에 `/sim/portone/bank-account-holders`로 스텔라의 시험 계좌 → '(주)스텔라엔터테인먼트'를 넣는다(`kubectl exec`로 클러스터 안에서 부름). ④ hosts에 `127.0.0.1 partner.peaket.example console.peaket.example`(README 표)를 두고 파트너 콘솔 주소(README 표의 partner 포트)를 연다. 로그인은 `node tools/local/demo-auth.mjs admin stella-admin`(파트너 관리자), 패스키는 `node tools/local/demo-auth.mjs passkey stella-admin`이 주는 자격·개인키로 넣는다.
- **패스키 확인의 한계**: Claude in Chrome은 패스키 창(WebAuthn)을 대신 누를 수 없다. 그래서 정산 계좌 바꾸기·패스키 등록·지우기의 끝까지는 `tools/web-checks`의 Playwright(1.64.1)로 CDP `WebAuthn.enable`·`addVirtualAuthenticator`·`addCredential`(위 개인키, rpId `partner.peaket.example`)을 써서 누른다(일회용 스크립트는 scratchpad에, 결과 문서에 명령을 적는다). Chrome으로는 화면 모양·키보드 이동·문구·실무자 보기·패스키 창이 열리는 데까지 본다.
- **볼 것**: 정산 계좌(은행 이름·끝 4자리·예금주 확인·보류 없음) → [계좌 바꾸기] → 비밀번호·인증 앱 코드 → 패스키 → 다른 예금주 계좌는 422 문구·저장 안 됨(새로 읽어도 그대로) → 맞는 계좌는 완료 배너·보류 끝 날짜(3영업일 뒤)·새로 읽어도 같음 → 같은 재인증으로 한 번 더 바꾸면 재인증부터 다시. 내 계정 패스키 목록·등록·마지막 하나 지우기 비활성. 정산서 탭은 데모 시나리오 S1로 결제 한 건 → F-07-5 방식의 회차 정산 계산 뒤 결제사별 정산서·이의 제기 대화상자. SCR-048은 포트원을 켠 뒤 새 판매 승인 요청의 확인 패널 항목 5(예금주 확인·포트원 파트너 등록·토스 "연동 전"). 실무자(`stella-member`가 시드에 있으면)로 비활성·이유 글. 계좌번호 전체가 화면·네트워크 응답에 0건.
- **가짜 API는 실제 서버 확인이 아니다**: 데모 무대를 못 올리면(응용 프로그램 제어·Docker 잠금) 그 사실과 까닭을 결과 문서에 적고 '실제 서버 미확인'으로 남긴다. `/preview` 화면과 `?state=` 보드는 모양 확인일 뿐이다.

## 열린 질문(소유자·감독 결정)

- **Q-01(소유자)**: 실제 포트원 플랫폼(예금주 조회·파트너·수기 정산건·지급 내역)과 토스 지급대행 시험 서버를 부르는 잡을 켤지. 판단: 저장소의 포트원 시험 시크릿(`PEAKET_PG_PORTONE_SECRET` 등, GitHub 비밀 값과 로컬 `pg-secrets..env`)은 결제 채널용으로 발급된 것이다. 포트원 파트너 정산(플랫폼) 기능은 상점에 따로 신청·계약해야 켜지고 기본 계약 ID도 그때 생기므로, 지금 키로 예금주 조회·파트너 등록을 부를 수 있다고 보지 않는다(불러 보지 않았다). 예금주 조회는 건당 비용이 붙을 수도 있다(확인 필요, C-02). 토스 지급대행은 F-07-6 Q-01과 같다(보안 키가 계약 뒤). 그래서 이 계획은 결제사를 한 번도 부르지 않고, 공개 명세 모양 대역 서버와 pg-simulator로만 시험한다. 계약이 생기면 pg-smoke처럼 '매일 + 손으로' 도는 포트원 플랫폼 시험 잡(예금주 조회 1건·파트너 조회, 등록·정산건은 시험 상점에서만 [가정])을 켤지 정해 주기 바란다(추천: 계약 뒤 켬, 지금은 켜지 않음).
- **Q-02(감독)**: 포트원 사후 대사(출금 대사 J-T20, 파트너 계좌 대조와 `ACCOUNT_MISMATCH` J-T21, 원장 잔액 대조와 대사 멈춤 J-T22, 지표 넷, 15시 실행 기록 없음 경보, 포트원 결제분 잔액 대사)를 이 기능에서 빼고 새 기능 행으로 둘지. ADR-0108의 주 통제라 A이지만, 이 계획의 다른 A 항목(지급대행 등록·판매 승인 조건·계좌 변경·예약 취소·포트원 실행·화면)과 함께 2.75일에 들지 않는다. 포트원 실제 지급은 계약 전이라 일어나지 않는다. (가) 새 기능 행(A, 1.5일 [가정], 선행 F-07-7, 장부 범위 J-T20·J-T21·J-T22와 asvs 2.2.3·13.2.2 포트원 몫) (나) 이 기능을 4.25일로 늘림. 추천: (가). 감독이 번호를 정하면 기록 커밋에서 BUILD_ORDER에 한 줄을 더한다.
- **Q-03(감독)**: 판매 승인 조건을 '켜진 결제사만'으로 다시 거는 정본 결정(ADR-0370 결정 3·4, settlement §3 새 줄)을 받아들이는가. 계약·키가 없는 지금은 두 결제사가 꺼져 있어 승인은 지금처럼 되고, 그 파트너의 결제분은 지급 묶음에서 보류된다(ADR-0369 결정 4). 결제사 설정과 상관없이 켜면 로컬 데모와 모든 판매 승인이 멈춘다(추천: 받아들임, 이 계획 커밋에서 정본에 적었다).
- **Q-04(감독)**: SCR-020 '내 계정'의 인증 앱 다시 등록·복구 코드 다시 만들기·로그인 기기 줄(d5 §6.1 ⑦)을 어느 단계가 맡는가. identity에 파트너용 경로가 없고 BOT-122는 패스키 줄만 넘겼다. 이 기능은 그 줄을 실제 화면에서 그리지 않는다(추천: identity 단계(F-03 계열) 한 줄로 받고, 그 전까지 C-03).
- **Q-05(감독)**: core-svc가 payment-svc 내부 HTTP를 부르는 새 쌍(메시 허용·ADR-0285 결정 9 표 보충)을 이 기능에서 더하는 것을 받아들이는가. 판매 승인이 지급대행 등록과 판매자 확인을 payment에 맡기려면 필요하다(ADR-0370 결정 4, 추천: 진행).
