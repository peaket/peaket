# 기능 계획: F-07-3(판매 승인 요청·SCR-021/048·공연 단위 승인 — LCH-080 잔여)

- **무엇**: 동결 로컬 트랙의 기능 작업 목록이다(docs/architecture.md §8.6 4의 1, ADR-0354·ADR-0386). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **바탕**: 작업 폴더 `D:/ticketpass-freeze-F-07-3`, 가지 `freeze/lane5-F-07-3`, 출발 `7d86f231a`(2026-11-24 최신 `origin/develop`, ADR-0386으로 나눈 freeze 가지). 2026-11-24 작성.
- **동결 범위**: 이 기능은 ADR-0373으로 v1 완성 범위 밖이고 ADR-0386으로 `frozen-local`이다. **`develop`·`release/1.0.0`에 합치지 않고, release에 체리픽하지 않는다.** 이 가지에서만 커밋하고 `freeze/lane5-F-07-3`로 원격에 둔다. 마이그레이션·플래그는 로컬에만 둔다(ADR-0386 결정 4·5). `docs/BUILD_ORDER.md`의 상태 `동결`은 그대로 두고 release-scope manifest도 고치지 않는다.
- **등급**: B다(docs/BUILD_ORDER.md F-07-3). 돈의 계산·전이를 새로 만들지 않는다. 판매 승인은 공연 공개와 판매 열기를 부르는 문이라 승인 전 확인(아티스트·공연장 연결, 지급대행 상태 표시)이 빠진 채 승인되면 안 된다. 그래서 재현·회귀 시험을 먼저 쓰고 기준 트리에서 실패를 본다(작업 지시, ADR-0372).
- **정본**: [docs/features/transfer-refund.md](../../features/transfer-refund.md) §2.1(판매 승인 확인 항목 6·공연 단위 승인), §3.2(판매 승인 권한), [docs/features/settlement.md](../../features/settlement.md) §3(지급대행 등록과 판매 승인 조건), §9(SCR-048·SCR-021), §13(S-T41), §15, [docs/design/d5-screen-blueprint.md](../../design/d5-screen-blueprint.md) §6.4(SCR-021 5단계)·§7.9(SCR-048), [docs/api/openapi.yaml](../../api/openapi.yaml) `listOpsArtists`·`createOpsArtist`·`listOpsPlaces`·`createOpsPlace`·`createOpsSaleReviewApproval`·`getOpsSaleReview`, [docs/security/authz-matrix.md](../../security/authz-matrix.md) §4.1, [docs/security/asvs/settlement.md](../../security/asvs/settlement.md) 8.2.2·8.2.3, [ADR-0093](../../adr/0093-production-entity-place-artist-units.md) 결정 4·7, [ADR-0198](../../adr/0198-production-registration-event-add-wish-api.md) 결정 3·4, [ADR-0327](../../adr/0327-sale-review-request-and-sale-open.md), [ADR-0370](../../adr/0370-portone-payout-agency-account-change-registration.md) 결정 4.
- **선행**: BAT-616(R-726)·BAT-617(R-758)이 판매 승인 요청·관제 목록·승인·반려·SCR-021/048 화면을 이미 `develop`에 넣었다. F-07-5(R-781)·F-07-6(R-796)·F-07-7(R-803)·F-07-8(R-804)도 `develop`에 있다. 이 기능은 그 위의 잔여만 닫는다.

## 3. 이번에 하는 것

구현 담당 할 일은 다섯이다(I-01~I-05). 차례: I-01 → I-02 → I-03 → I-04 → I-05. 시험은 구현 전에 쓴다.

1. **I-01 관제 찾기·만들기 저장소와 유스케이스**: `catalog/domain/ops-catalog.ts`에 값·검사·정규화 비교(`sameName`)를, `catalog/domain/ops-catalog-ports.ts`에 `OPS_CATALOG_STORE` 포트(`listArtists(q, limit, cursor)`, `listPlaces(...)`, `createArtist`, `createPlace`, `artistIdsExist`, `placeUsable`)를 둔다. `catalog/application/ops-catalog.ts`의 `OpsCatalog`가 q·limit·커서 검사, 중복 409, 감사 로그(operator 계정·사유·만든 ID)를 맡는다. DB 어댑터 `catalog/adapters/db/drizzle-ops-catalog.ts`는 `OPS_DATABASE`(core_ops)로 읽고 쓴다. 메모리 어댑터는 `MemoryCatalogRepository`의 `artistNames`·`placeNames`·`artists`·`places`를 쓴다. 컨트롤러 `catalog/inbound/ops-catalog.controller.ts`는 openapi operationId 넷을 그대로 잇고 `Cache-Control: no-store`를 단다. core 0048이 `core_ops`에 `artist` SELECT·INSERT, `place` SELECT(id·name·address·region·status)·INSERT, `production` UPDATE(`requested_artists`), `production_artist` SELECT·INSERT·DELETE를 연다(로컬 번호).
2. **I-02 조립**: `catalog.module.ts`에 `OPS_CATALOG_STORE`를 DB·메모리 두 갈래로 넣고 `OpsCatalog`·`OpsCatalogController`를 등록한다. 메모리에서는 `OPS_CATALOG_STORE`가 `CATALOG_REPOSITORY`와 같은 `MemoryCatalogRepository`를 쓰게 한다. DB에서는 `OPS_DATABASE`로 만든 `DrizzleOpsCatalog`를 쓴다. `index.ts`가 새 공개 이름을 내보낸다.
3. **I-03 승인 연결 규칙**: `catalog/domain/sale-approval.ts`의 `SaleApprovalInput`에 `artists?: { name: string; artistId: string }[]`를 더하고, `sale-review.ts`에 `OpsSaleReviewArtist`·`requestedArtists`를 더한다. `catalog/domain/sale-review-linkage.ts`(새)의 순수 함수 `checkLinkage(state, body)`가 ① 요청 아티스트마다 정확히 하나, ② 모르는 이름·중복 이름, ③ `artistId` 존재, ④ 새 공연장 요청이면 `placeId` 필수와 공연장 사용 가능을 검사하고 422 `sale-review-artists-missing`·`sale-review-place-missing`을 낸다. `ApproveSaleReview`가 저장 전에 이 검사를 부르고, 저장소 `approve`가 `production_artist`를 요청 순서로 쓰고 `requested_artists`·`requested_place`를 비운다. 메모리 저장소도 같은 제약을 흉내 내어 새 공연장 요청을 연결하지 않은 승인을 422로 막는다(회귀 재현).
4. **I-04 저장소·계약**: `drizzle-sale-store.ts`의 `readState`가 `requested_artists`와 `production_artist`(이름 조인)를 읽고, `approve`가 트랜잭션 안에서 `production_artist`를 지우고 다시 넣으며 `requested_artists`·`requested_place`를 비운다. `memory-sale-store.ts`에 `productionArtists` 관계를 더하고 등록 때 `requestedArtists`·`artists`를 보존한다. `ops-sale-review.controller.ts`의 `SaleApprovalBody`에 `artists`를 더하고 상세 응답 스키마에 `artists`를 더한다. openapi를 고친 뒤 `pnpm --filter @peaket/contracts gen`·`pnpm --filter @peaket/api-client gen`을 돌린다.
5. **I-05 SCR-048 화면**: `apps/console-host/src/pages/sale-review/model/sale-review.ts`에 `mapArtists`, `mapPayout`, `validateLinkage`, `linkageBody`, `artistOptions`, `placeOptions`를 더한다. `approvalBody`는 `scales`·`placeId`(고른 값)·`artists`(요청 이름마다 고른 ID)만 낸다. `ui/ConnectedPage.tsx`는 확인 패널에 ① 아티스트 줄(요청 이름 → 검색·고르기·새로 만들기), ② 공연장 줄(요청 이름 → 검색·고르기·새로 만들기), ③ 지급대행 등록 줄(은행·끝 4자리·예금주 확인·보류 끝·토스 두 상점 상태·포트원 파트너)을 더한다. `role`이 CS 두 역할이면 계좌를 그리지 않는다. `ops` 엔드포인트 `listOpsArtists`·`createOpsArtist`·`listOpsPlaces`·`createOpsPlace`를 api-client에서 부른다. 새로 만들기는 사유 입력 대화상자를 거친다.

## 8. 공개 인터페이스(시험 담당이 기댄다)

**HTTP(core-svc, 계약 변경)**

- `GET /v1/ops/artists?q=&cursor=&limit=` → `{ items: [{ artistId, name, aliases }], nextCursor }` (viewer·operator·commander·cs_agent·cs_lead, `no-store`)
- `POST /v1/ops/artists` `{ name, reason }` → 201 `{ artistId }`, 409 `artist-exists`(확장 `artistId`)
- `GET /v1/ops/places?q=&cursor=&limit=` → `{ items: [{ placeId, name, address, region, status, aliases }], nextCursor }`
- `POST /v1/ops/places` `{ name, address, region, reason }` → 201 `{ placeId }`, 409 `place-exists`(확장 `placeId`)
- `POST /v1/ops/sale-reviews/{productionId}/approvals` 본문에 `artists?: { name: string; artistId: uuid }[]`를 더한다. `placeId?`는 새 공연장 요청이면 필수다. 정의 밖 칸은 400.
- `GET /v1/ops/sale-reviews/{productionId}` 응답에 `artists: { artistId: uuid|null, name: string }[]`를 더한다(등록 아티스트 뒤에 요청 이름, 보이는 순서).

**화면 모델(`apps/console-host/src/pages/sale-review/model/sale-review.ts`)**

- `mapArtists(detail)`, `payoutSummary(raw)`, `validateLinkage(detail, resolved)`, `linkageBody(detail, resolved, scales)`, `artistOptions`, `placeOptions`.
- `resolved` 모양: `{ artists: Record<string, string>; placeId: string|null }`(요청 이름 → 고른 artistId, 공연장 ID).
- `payoutSummary`는 `{ bankCode, last4, holderVerified, holdUntil, tossSellers, portonePartnerRegistered, tossEnabled, portoneEnabled } | null`을 준다. CS 역할이면 `payoutAccount`가 null이라 계좌 줄을 그리지 않는다.

## 11. 남은 몫(동결 로컬)

- **다른 이름 고치기**: `PUT /v1/ops/artists/{artistId}/aliases`, `PUT /v1/ops/places/{placeId}/aliases`, `PUT /v1/ops/productions/{productionId}/aliases`, `PATCH /v1/ops/places/{placeId}`. `artist`·`place`에 판(version) 칸과 If-Match 규약, `search_alias` 쓰기·검색 사전 갱신, 감사 로그가 함께 필요하다. 계약(openapi)은 이미 있으나 저장 규약이 없어 이번에 만들면 계약과 DB가 어긋난다. 다음 동결 몫의 첫 항목으로 둔다.
- **브라우저 확인**: 측정 창 뒤 `docs/review/browser-check/` 대본으로 SCR-048의 아티스트·공연장 고르기와 지급대행 표시를 누른다. 화면 시험(모델·배선)과 빌드는 이번에 통과했다.
- **전체 `pnpm typecheck`**: 이 기능 밖의 `@peaket/bundle`·`tools/local/v1-objects.mjs` 암시적 any 두 건이 막는다. 그 파일을 고치는 일은 동결 트랙 정리 목록으로 넘긴다(이 기능의 네 작업 공간 typecheck는 통과).
- **F-07-7 I-10 잔여**: SCR-048의 판매자 확인·지급대행 값 표시는 이 기능이 닫았다. 계좌 변경·KYC 예고의 다른 화면은 F-07-7이 이미 닫았다.
- **Docker 통합**: 완료(7/7, 위 §5.1).

## 12. 동결 기록

- 이 기능은 ADR-0373(7일 완성 범위 밖)·ADR-0386(`frozen-local`)에 따라 `develop`·`release/1.0.0`에 합치지 않는다. release 체리픽 금지. 마이그레이션 core 0048은 로컬·CI 전용이며 release 마이그레이션 목록에 넣지 않는다.
- 측정 창이 시작되면 Docker 잠금을 잡지 않고, 긴 통합 시험을 새로 시작하지 않는다. 안전한 체크포인트에서 커밋·push하고 감독 보고 뒤 측정 뒤에 재개한다.
