# BAT-031 계획 — K7 결제 확정 p99 3초·홀드 p99 50ms

- 작성: 2026-11-12
- 소유자 결정: BAT-029를 A/A 고정·1차 최적화(K7 38→5.4초)로 닫고, 남은 K7 3초 목표를 BAT-031(HOT-465, A등급)로 이어 간다.
- 작업 가지: `feature/BAT-031-k7-unknown-tail` (`origin/develop` d8a52234)
- 장부 범위 후보: `P-T1, P-T47`

## 1. 목표와 경계

- 목표: v1 합본 3복제·CPU 4/한도 4에서 K7 ② 혼합 100/s(응답 버림 5%·16초 늦춤 0.5%) 결제 확정 p99 3초 안, 홀드 p99 50ms 안, 실행 유효(놓침 0·`startSkewS=0`).
- 동작·계약·불변식은 바꾸지 않는다. 시간 초과·풀 크기·재시도 간격처럼 측정에 드러난 운영 값만 근거와 함께 조정한다.
- 회마다 새 클러스터(`cluster.mjs down/up/observability/v1`), v1 합본 CPU 4는 `cluster.mjs v1 --cpus 4`로 만든다. 합본 복제 3은 `docs/verification.md` §3.8에 고정 [가정]이므로 바꾸지 않는다.

## 2. ① 측정 도구화

- `tools/local/v1-objects.mjs`: `v1Plan`에 `--cpus`(1~16)·`--memory-mi`(256~32768), `v1HelmArgs`가 합본 `service.replicas`·`service.resources.requests/limits.cpu`·`memory`를 `--set`으로 덮는다.
- `tools/local/cluster.mjs`: `v1 [--redis-tls on|off] [--replicas N] [--cpus N] [--memory-mi N]` 사용법과 helm 전달.
- `loadtest/runner/args.mjs`: v1 세 시나리오에만 `--target-cpus`를 허용하고 parse 결과에 싣는다. v0는 계속 거부한다.
- `loadtest/run.mjs`: v1 합본의 실제 `requests.cpu`·`limits.cpu`가 `--target-cpus`와 다르면 k6를 시작하기 전에 실패한다. `infra.txt`에 `(목표 N)`을 기록한다.
- 시험: `node --test tools/local/v1-stage.test.mjs tools/local/cluster.test.mjs`(51 통과·3 skip), `node --test loadtest/test/args090.test.mjs loadtest/test/runner.test.mjs`(157 통과). 실제 무대에서 `--target-cpus 3`이 즉시 실패하고 `--target-cpus 4`가 통과하는 것을 확인했다.

## 3. ② 진단 — 어디서 3초를 잃는가

진단은 `docs/review/measurements/BAT-031-k7-tail.md`에 표로 남겼다. 요지는 셋이다.

1. **이벤트 루프 포화**: 3복제×4 CPU에서 프로세스 CPU는 약 1.13코어/파드, `nodejs_eventloop_utilization`은 1.0이다. 요청당 약 6.2ms CPU를 쓰며 한 프로세스의 JS 스레드가 한계다. 4 CPU 한도는 남지만 Node 이벤트 루프 하나가 쓰지 못한다.
2. **Saga 승인 명령 재시도**: `RESERVED → payment.created`가 p99 4.2초까지 밀렸다. 500ms gRPC 데드라인을 넘긴 호출이 3.2%였고, Saga가 1·2·4초 뒤로 미뤘다. 1,000ms로 올리자 p99 0.24초가 됐다(2,000ms는 오히려 6.9초로 나빠졌다 — 느린 호출을 오래 기다린다).
3. **결과 소비자·승인 실행기 풀**: 결제 결과 소비자 32키·32연결이 꽉 차 `RESERVED → APPROVED`가 p99 7초까지 밀렸다. 48로 올리자 소비자 적체가 사라졌다. 승인 실행기 DB 풀 8개는 read·mark·finish가 줄을 서 p95 428~451ms였고, 24개로 올리자 결제 확정 p99가 5.2→4.7초로 내려갔다.

## 4. ③ 수정

- UNKNOWN 해소: `UNKNOWN_QUERY_BASE_MS` 1,000→250ms, `UNKNOWN_QUERY_POLL_INTERVAL_MS` 1,000→250ms, 지수 상한 6→8. 5% 응답 버림의 첫 조회를 빨리 잡는다.
- Saga 승인 명령 gRPC 데드라인 500→1,000ms(`CONFIRM_CALL_DEADLINE_MS`, `CONFIRM_CAP_MS`).
- 결제 결과 소비자 48키·48 DB 연결(`PAYMENT_CONSUMER_DB_MAX`, `maxKeys: 48`). 결제 결과 소비자만 대상이고 홀드 원장 소비자는 32·4 그대로다.
- 승인 실행기 전용 DB 풀 8→24(`CONFIRM_RUNNER_DB_MAX`).
- 승인 `finish`가 세 번 실패하면 75초 임대를 그대로 두지 않고 `releaseLease`로 임대 시간만 지금으로 당긴다. 소유자는 남겨 다음 실행기가 잔해로 보고 결제사를 다시 부르지 않고 단독 조회로 맞춘다.
- 로그 가명 HMAC 키를 `KeyObject`로 한 번만 만들어 요청마다 만들지 않는다(38.8→13.3µs/회, 값 동일).
- purchase 핫패스 풀은 32로 올렸던 것을 16으로 되돌린다. 100/s에서 429를 줄이지 못하고 이벤트 루프·연결 압박만 키웠다.
- 합본 메모리 512Mi→1Gi, `NODE_OPTIONS=--max-semi-space-size=64`는 GC를 21.8→5.2초/100초로 줄였지만 이벤트 루프 포화는 그대로였다. 최종 무대 조건은 별도로 기록한다.

## 5. ④ 재측정

- 40초 유효 실험(코드 수정 누적, 1Gi·semi64): 결제 확정 p99 4,694.8ms·p95 2,797.1ms, 홀드 p99 259.6ms, 놓침 0. `RESERVED → CONFIRMED` p99 2.86초까지 내려왔다.
- 100초 진단(같은 코드): 결제 확정 p99 14,054ms, 놓침 495(VU 1,648 고갈)로 **무효**. 100/s를 100초 유지하지 못한다.
- K7 ② 3회(회마다 새 클러스터)·A/A 쌍·K2 3회는 이번 가지에서 **완료하지 못했다**. 40초 실험과 100초 무효 진단으로 원인과 개선 폭만 남긴다.

## 6. 남은 일 — BAT-032로 넘긴다

- 이벤트 루프 하나가 3복제×4 CPU의 병목이다. 복제 3 고정을 지키면서 3초·50ms를 채우려면 (a) 합본 프로세스를 워커/클러스터로 나눠 4 CPU를 쓰게 하거나, (b) 요청당 트랜잭션 수(승인 claim·read·mark·finish, Saga reserve·confirm, 결과 소비)를 줄여 CPU를 절반 가까이 낮춰야 한다.
- 홀드 p99 50ms는 K7 혼합 부하에서 결제·소비자 작업과 같은 이벤트 루프를 쓰는 한 불가능에 가깝다. 홀드 경로를 별도 실행 단위로 분리하는 설계 결정이 필요하다.
- K7 3회·A/A·K2 3회, 변이·복구 장애·trace-check·test-int·4관점 리뷰는 BAT-032에서 새 무대 기준으로 다시 한다.
