# BAT-034 계획 — purchase-svc 핫패스 DB 풀 포화(429 server-busy)

- 작성: 2026-11-12
- 묶음: BAT-034(HOT-468, 갈래 1, 구간 1, **A등급**, 0.5~1일 [가정])
- 장부 범위: `P-T1`, `P-T23`
- 선행: BAT-033(HOT-467, R-496) — K7 진단에서 429 `server-busy`를 확인했다.
- 웨이브: 갈래 1의 제품 수정 배치. 갈래 2가 heavy gate를 쓰는 동안 K7 진단은 돌리지 않고, `measurement go` 뒤에 수정 후 K7 진단 1회만 돈다.

## 1. 목표

- purchase-svc 핫패스 DB 풀(`profile: hot`, max 16, 연결 대기 100ms) 포화로 나는 **429 `server-busy`**를 줄인다.
- 대상 경로:
  - `POST /v1/orders`
  - `POST /v1/orders/{orderId}/payments`
  - `POST /v1/orders/{orderId}/payment-acceptance`
- K7 결제 확정 p99 3초와 기존 좌석·주문·결제 접수 동작을 해치지 않는다. 계약·응답 코드·멱등 동작은 바꾸지 않는다.
- 수정 후 K7 진단 1회에서 접수 429 비율 **<1%**와 p99를 확인한다. 공식 3회는 그 결과를 보고 소유자가 정한다.

## 2. 배경 — 진단 수치

2026-11-12 K7 진단 1회(`.cache/peaket-bat033/k7-diag-r1/`, 공식 유효 조건은 dropped 170·시나리오 오류 59로 미달):

- 접수 호출 6,557건: 202 5,759, **429 794(12.11%)**, 503 4(0.06%), 409·422·500·504 0.
- 같은 429 `server-busy`가 `/v1/orders` 2,545건, `/v1/orders/{orderId}/payments` 1,296건에도 났다(3개 bundle 파드 로그, 예열 포함).
- 429는 시나리오 중복·재시도가 아니다. 주문·시도마다 새로 만들고 접수는 한 번만 부르며 멱등 키도 새로 만든다. 409·422가 0건이다.
- purchase-svc 메인 DB는 `profile: hot`, max 16, `connectionTimeoutMillis: 100`이다(`services/purchase-svc/src/start.ts`, `packages/platform/src/database.ts`). 풀 대기 한도를 넘으면 `429 server-busy`다.
- 503 4건은 Redis 좌석 저장소(`seat-store-unavailable`)이고, 500·504는 없었다.
- 이 진단은 과부하 상태라 공식 K7 수치가 아니다. 수정 후 진단은 같은 조건에서 429 비율과 p99를 다시 본다.

## 3. 증거 수집(수정 전)

K7을 다시 돌리지 않고 다음 순서로 작은 증거를 모은다.

1. 기존 진단 산출물(`summary.json`, `generator.json`, bundle 파드 로그)에서 세 경로의 429 건수·비율·`durationMs` 분포를 다시 뽑는다.
2. 관측 스택이 살아 있으면 Prometheus에서 같은 창의 DB 풀 지표를 읽는다: active/idle/waiting, 대기 시간, 연결 획득 실패 수. 지표 이름이 없으면 `database.ts`에 낮은 카디널리티 풀 지표를 더할지 판단한다(이번 배치에서 계측만 더하는 것은 최소 수정 범위에 넣지 않는다).
3. 세 경로의 트랜잭션 보유 시간을 코드와 기존 `hot_path_stage_seconds`로 가른다. 비DB 작업(서명 검증·직렬화·로그·Redis 호출)이 트랜잭션 안에 있는지 확인한다.
4. 필요하면 purchase-svc test-int에 작은 풀 포화 시험을 더해, 풀 대기 한도·max·트랜잭션 보유 시간이 429로 바뀌는 조건을 재현한다. Docker/K8s가 필요한 무거운 실행은 하지 않는다.

## 4. 수정 후보와 선택 기준

| 후보 | 내용 | 기대 | 위험 |
| --- | --- | --- | --- |
| (가) | hot 풀 max 16→32 | 대기 열을 줄인다 | PostgreSQL 연결·경합 증가, PgBouncer 배치와 어긋날 수 있다 |
| (나) | hot 연결 대기 100ms→250ms | 순간 포화를 흡수한다 | 요청 지연이 늘어 K7 p99 3초를 해칠 수 있다 |
| (다) | 주문·결제 시작·접수 트랜잭션에서 DB 보유 시간 줄이기(비DB 작업 밖으로, 쿼리 묶기) | 근본 원인을 줄인다 | 변경 범위가 가장 크고 계약·동시성 시험이 필요하다 |
| (라) | HTTP 입구 백프레셔(동시 처리 상한·큐) | 429를 더 이르고 일정하게 만든다 | 정상 요청을 거절할 수 있고 K7 처리량이 줄 수 있다 |

선택 기준:

- 증거가 가리키는 병목(대기 열 vs 보유 시간 vs 입구 폭주)에 가장 직접 닿는 **가장 작은 수정**을 고른다.
- K7 p99 3초를 해치지 않는다. p99를 늘리는 대기 한도 확대는 증거가 강할 때만 고른다.
- 좌석 홀드·주문·접수 동작과 응답 계약을 바꾸지 않는다.
- 설정 변경이면 환경 변수·기본값·문서를 함께 맞춘다.
- 수정 하나를 고르고, 나머지는 결과를 보고 다음 배치로 넘긴다.

## 5. 시험

- 단위: 풀 설정·환경 변수 기본값·문서 일치, 429 `server-busy` 분류, 트랜잭션 밖으로 뺀 작업의 순서.
- 통합(purchase-svc test-int): 주문·결제 시작·접수 정상 201/202, 같은 주문 중복 접수 409, 멱등 재생 202, 좌석 홀드·주문 상태 불변.
- 풀 포화 조건: 풀 대기 한도 안에 연결을 못 얻으면 429 `server-busy`가 나고, 수정 뒤 같은 조건에서 429가 줄어드는지 확인한다.
- 기존 시험: purchase-svc test-int 전체 또는 이 배치가 닿는 범위, 관련 단위 시험, typecheck, lint, doc-check.
- 변이: 수정한 설정·분기마다 시험이 실패하는지 확인한다.
- trace-check: `P-T1`, `P-T23`이 가리키는 증거를 확인한다.
- `ledger --batch BAT-034 --require`.

## 6. K7 재측정

- 이 배치에서는 K7을 돌리지 않는다. 갈래 2 heavy gate가 끝나고 소유자가 `measurement go`를 보낸 뒤 **수정 후 K7 진단 1회**만 돈다.
- 진단에서 확인할 것: 접수 `payment_accept_status{phase:main,status}`의 429 비율 <1%, `payment_confirm_ms{phase:main}` p99, `payment_end_truncated_pending`/`_terminal`, 세 경로의 429 `server_busy` 로그.
- 진단이 유효(놓침 0·시나리오 오류 0)하고 429 <1%이면 공식 K7 3회를 소유자가 정한다. 미달이면 수정을 더 하지 않고 원인을 기록한다.

## 7. 위험

- 풀 max를 늘리면 PostgreSQL 연결 수·경합이 늘어 다른 경로가 느려질 수 있다. PgBouncer 배치와 `max_connections`를 함께 본다.
- 대기 한도를 늘리면 429는 줄지만 p99가 늘 수 있다. K7 p99 3초를 넘으면 되돌린다.
- 트랜잭션 축소는 동시성·멱등·정합 시험을 깨기 쉽다. 가장 작은 변경부터 한다.
- 진단 1회는 과부하로 무효가 될 수 있다. 무효면 429 비율만 참고하고 공식 수치로 쓰지 않는다.

## 9. 선택한 수정(2026-11-12)

증거:

- 진단 실행의 429 `durationMs`: 접수 p50 228ms·p90 368ms·p99 535ms, 주문 p50 259ms·p90 428ms, 결제 시작 p50 248ms·p90 514ms. 성공 201/202는 p50 524~563ms로 429보다 느리다. 429는 풀 대기 100ms에서 빨리 실패한 것이다.
- 실제 PostgreSQL에 max 1 풀을 두고 200ms 점유를 만들었다. 100ms 대기는 **108ms에 `timeout exceeded when trying to connect`(429)**, 250ms 대기는 **206ms에 성공**, max 2는 7ms에 성공했다.
- DB는 `max_connections` 600, 진단 뒤 idle 36·active 0, `purchase-svc` 핫패스 연결 0(10초 idle 뒤 닫힘), deadlock 0, disk read 47 vs cache hit 6.3M으로 I/O·연결 여유가 있었다.
- BAT-031은 핫풀 16/32를 모두 재 봤지만 32는 429를 줄이지 못하고 이벤트 루프·PostgreSQL 연결 압박만 커져 16으로 되돌렸다. 그래서 max 확대는 다시 고르지 않는다.

선택: **(나) purchase-svc 핫패스 연결 대기 100ms→250ms**. `PEAKET_DB_HOT_CONNECT_TIMEOUT_MS` 기본 250ms, 풀 max 16 유지.

- 가장 작은 변경(설정 하나)이고, 200ms 남짓 점유를 흡수하는 것을 실제 PostgreSQL로 확인했다.
- 성공 요청 p50 524ms에 최대 150ms를 더해도 K7 p99 3초와 거리가 멀다. 429로 실패하던 요청이 202로 바뀌는 쪽이 낫다.
- 트랜잭션 축소(다)는 세 경로가 이미 짧은 DB 문장으로 되어 있어 이번 증거의 직접 원인(100ms 대기)보다 큰 변경이다. 250ms로 부족하면 다음 배치에서 (다)·(라)를 검토한다.
- 시험: 플랫폼 단위 시험(설정 적용·429 매핑), purchase-svc 단위 시험(기본값·범위), purchase-svc test-int(100ms 429 / 250ms 성공), 기존 주문·접수 test-int.
