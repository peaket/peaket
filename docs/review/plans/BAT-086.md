3. **S7 2인 승인은 데모 도우미 없이 브라우저 맥락 둘로 한다**: ADR-0095의 더 단순한 방법(두 번째 브라우저 프로필에서 데모 승인자로 직접 로그인)을 쓴다. 재현 스크립트가 요청자 맥락과 승인자 맥락을 따로 열고, ① 요청자가 자기 명령을 승인하면 403 ② 승인자 맥락이 승인하면 성공 ③ 감사 기록에 두 계정이 따로 남는지를 본다. 이렇게 하면 OPS-290의 데모 도우미를 기다리지 않고 S7을 재생할 수 있다. 데모 도우미·데모 막대 자체는 OPS-290 몫으로 남긴다.

4. **장부 범위는 `V-T7` 하나로 좁힌다**: BAT-086 줄의 범위 칸은 지금 `-`다(docs/BUILD_ORDER.md:71). BAS-160에 대응하는 장부 항목은 `V-T7`(빈 PC에서 데모 재현 스크립트 실행 — 한 명령으로 시연 흐름이 뜨고 걸린 시간이 기록된다)뿐이다(docs/review/ledger/verification.md:21, docs/verification.md:622). **D-T48**(운영 판과의 계약 호환)은 이미 자동 시험이다(docs/review/ledger/devops.md:125). 이 묶음은 D-T48을 **시연**할 뿐 제품 검사나 시험을 바꾸지 않으므로 범위에 넣지 않는다. 넣어도 장부 상태는 그대로 `자동 시험`이라 손해는 없지만, 이 묶음이 바꾸는 것이 없어 범위를 넓히지 않는다. 감독이 `V-T7, D-T48`을 원하면 그대로 적는다.

5. **Playwright를 `tools/web-checks`에서 빌려 쓴다(새 의존성 없음)**: 재현 스크립트는 브라우저를 실제로 몰아야 한다(S1~S9는 화면 순서가 정본이다). `tools/web-checks`는 뿌리 작업 공간과 다른 잠금 파일을 쓰고 Playwright 1.64.1을 이미 고정한다. `tools/local/e2e/queue-cors.e2e.mjs:9`의 설치 명령과 `:14`의 `createRequire`처럼 그 패키지를 읽는다. 그래서 '빈 PC'의 한 명령은 ① `pnpm --dir tools/web-checks install --frozen-lockfile` ② `npx playwright install chromium`(한 번)을 먼저 하거나, `demo.mjs doctor`가 없으면 그 명령을 알려 준다. 새 패키지를 늘리지 않는 쪽을 추천한다.

6. **1.25일은 S1~S9 모두에 빠듯하다 — 우선순위를 정해 달라**: 화면 순서 아홉을 실제 앱에서 끝까지 몰면 시나리오마다 대기·결제·승인·검표 상태가 필요하다. **안**: S1·S4·S6·S7·S8(프로토타입이 끝까지 눌렀던 다섯, docs/design/d5-screen-blueprint.md:4419)을 먼저 끝내고, S2·S3·S5·S9는 같은 틀에 정의와 검사를 더한다. 시간이 모자라면 ① WBS 일수를 늘리거나 ② S2·S3·S5·S9를 다음 묶음으로 뺀다. 이 계획은 아홉을 모두 판정 대상으로 적되, 차례를 그렇게 나눈다.

7. **임시 클라우드 데모는 절차만 쓰고 실행하지 않는다**: 클라우드 계정·비용·TTL·예산 경보는 소유자 몫이다(docs/devops.md:803~814). 이 묶음은 `deploy/demo/cloud-plan.yaml`(TTL·예산·시간당 추정·정리 차례)과 `docs/devops.md` §5.1의 절차를 만들고, `node tools/local/demo.mjs cloud-plan --check`로 값의 산술과 필수 항목만 본다. 실제 `up`은 하지 않는다. TTL 기본 6시간 [가정], 예산은 소유자 지출 상한 5만 원 안에서 정한다(docs/devops.md:809·814).

8. **ADR 번호**: 이 묶음은 기존 결정(ADR-0057·0095·0153·0165)의 구현이라 새 ADR이 꼭 필요하지 않다. 다만 '로컬 데모는 로컬 이미지·로컬 오버레이, 클라우드 데모는 `deploy/envs/demo`의 서명 다이제스트'로 **두 경로를 가르는 것**은 새 결정이다. 감독이 번호를 주면 구현 담당이 새 ADR(번호는 감독이 정한다)로 쓰고, 주지 않으면 계획 12의 추천 적용으로 둔다.

### 5. 공개 인터페이스(시험이 기댄다. 이름을 바꾸면 '시험 이의'에 적는다)

- **명령줄**:
  ```text
  node tools/local/demo.mjs doctor [--root <저장소>] [--json]
  node tools/local/demo.mjs plan [--check] [--json]
  node tools/local/demo.mjs up [--cluster <이름>] [--keep]
  node tools/local/demo.mjs seed [--reset]
  node tools/local/demo.mjs play [--scenarios S1,S2|all] [--headed] [--video] [--keep]
  node tools/local/demo.mjs compat [--work <폴더>] [--json]
  node tools/local/demo.mjs cloud-plan [--check] [--json]
  node tools/local/demo.mjs down [--cluster <이름>]
  node tools/local/demo.mjs all [--scenarios all] [--keep] [--headed] [--video]
  ```
  끝 코드 0 통과, 1 실패·선행 없음, 2 인자·설정 오류. 출력은 사람이 읽는 줄과 `--json`(시험이 읽는 칸) 둘 다.
- **환경 값**: `PEAKET_DEMO_CLUSTER`(기본 `lane4-demo`), `PEAKET_DEMO_SEED`(기본 `deploy/envs/demo/seed/base.yaml`), `PEAKET_DEMO_OVERLAY`(BAT-087이 정하는 로컬 오버레이 경로), `PEAKET_DEMO_PLAYWRIGHT`(기본 `tools/web-checks`), `PEAKET_DEMO_BASE_URL`(기본 `https://127.0.0.1:18441`). 비밀 값은 환경 값이나 `.cache/peaket-tools/`에만 두고 저장소·측정 파일에 쓰지 않는다.
- **`plan --json` 모양**(시험이 읽는다):
  ```json
  { "scenarios": [
    { "id": "S1", "title": "지민 씨의 하이브리드 공연 예매", "screens": ["SCR-001", "SCR-002", "..."],
      "accounts": ["jimin"], "needs": ["E-1"], "checks": ["seat-hold-2", "payment-approved", "ticket-qr"] }
  ] }
  ```
  `S1`~`S9`가 이 순서로 모두 있고, 화면 번호는 d5 §10.6의 표와 같다. `checks`는 결과 확인 이름이고, 시나리오마다 하나 이상이다.
- **시드 파일 계약**(BAT-087이 만들고 BAT-086이 읽는다):
  ```yaml
  version: 1
  accounts: [{ key, role, provider, email, passwordEnv, totpEnv }]
  events:   [{ key, title, mode, openAt, seatMap }]
  seatMaps: [{ key, eventKey, sections: [...] }]
  partner:  { orgKey, sellerKey, userKey }
  staff:    { eventKey, gateLead, gateStaff, devices: [...] }
  ```
  실제 개인정보·실제 이메일·전화번호·비밀 키를 넣지 않는다. 비밀번호·TOTP는 값이 아니라 환경 값 이름만 적는다.
- **측정 파일 계약**(사람이 읽는 Markdown, 시험이 머리 줄을 읽는다): `커밋`·`날짜`·`PC/OS`·`Docker/kind/Node/Playwright 판`·`콜드 스타트 초`·`시나리오별 시작/끝/결과/실패 단계`·`정리 결과`. 실패면 `결과: 실패`와 까닭이 있다.
- **로컬 오버레이 계약**(BAT-087): `deploy/workloads/<서비스>/values.yaml` + 데모 덧씌우기로 만든 `deploy/envs/local/demo/<서비스>.yaml`(안). 각 파일은 `name`·`image.repository: peaket/<서비스>`·`image.tag: demo`·`image.pullPolicy: Never`·`env.PEAKET_ENV: demo`를 갖는다. `deploy/envs/demo/*.yaml`(클라우드)과 섞지 않는다.
- 제품 API·계약·DB 변경은 없다.

### 7. 구현 전 트리에서 실패를 볼 수 없는 시험과 그 까닭

- **파일이 없어 실행조차 안 되는 것**: V-T7 ①~③·⑥·⑦, DM-08~CP-01. §8.6 7로 세지 않는다. 시험 담당은 구현 커밋에서 통과를 보고, 9의 틀린 구현을 손으로 하나 이상 넣어 실패를 '실패 확인'에 적는다.
- **무대가 없어 실행할 수 없는 것**: V-T7 ④·⑤. BAT-087의 이미지·오버레이·기본 시드가 develop에 들어온 뒤 첫 실행을 한다. 그때까지는 `doctor`의 가짜 뿌리 시험으로 닫힌 실패만 본다. 첫 실행 결과는 `docs/review/measurements/` 폴더의 `BAT-086-demo.md`에 적는다.
- **Docker가 필요한 것**: DM-08·DM-09(`contract-breaking`이 oasdiff·AsyncAPI 이미지를 돌린다). 이 PC에서는 Docker 잠금 안에서만 돌린다. 도구가 없으면 exit 2(오류)로 끝나고 통과로 세지 않는다.
- **이미 있는 동작이라 기준 트리에서 통과하는 것**: D-T48의 기존 시험(`tools/ci/contract-breaking.test.mjs`)과 `tools/local/*.test.mjs` 회귀. 이 묶음은 그 시험을 고치지 않는다.
- **측정**: V-T7 ④의 콜드 스타트·시나리오별 시간은 시험이 아니라 측정이다. 측정 파일에 적고, 장부에는 V-T7의 자동 시험과 별도로 남긴다.
