### 2.3 수치

이 기능은 처리량·지연 수치를 주장하지 않는다. 초당 한도·재시도 간격·시간 초과는 대행사 계약과 정본의 `[가정]` 값이고, 시험은 작은 시험 값을 따로 준다(예: `ratePerSec: 2`, `Retry-After: 300초`). 측정하지 않은 값을 완료 근거로 쓰지 않는다.

- local·ci·demo만 `file`·`fake`·`off`를 쓸 수 있다. staging·prod에서 `file`·`fake`가 오면 시작 실패다(지금 파일 대역은 `demo`를 허용하므로 그대로 두되, provider 이름이 `file`인 경우만 본다).
- `PEAKET_NOTIFY_SMS_PROVIDER`와 `PEAKET_NOTIFY_ALIMTALK_PROVIDER`는 운영에서 **명시**를 요구한다. 값이 없으면 '꺼짐'으로 조용히 넘어가지 않는다.
- VAPID `sub`는 `mailto:`(한 개의 `@`) 또는 `https://`만 받는다(RFC 8292가 연락처를 권한다). 공개키는 개인키에서 유도한 값과 같아야 하고, 다르면 시작 실패다(기존 검사 유지).
- `providerConfigSummary(config)`는 로그·기동 보고에 쓰는 요약으로 `{ mail: 'ses'|'file'|'fake'|'unset', mailRegion?, mailFromDomain?, sms: 'solapi'|'off'|..., alimtalk: boolean, vapid: boolean }`만 돌려준다. VAPID 설정을 받으면 `{ vapid: true, subject }`를 돌려준다. API 키·비밀·웹훅 비밀·개인키·발신번호 원문은 절대 넣지 않는다.
- `redactProviderText(text, secrets)`는 대행사 오류·로그 문구에서 `Authorization` 머리 값과 설정 비밀 값을 지우고 그 자리에 `[redacted]`를 남긴다. 어댑터는 던지는 오류와 `log` 콜백에 이 함수를 쓴다. 오류 문구에는 키·비밀·`signature=`가 남지 않는다.

### 3.2 SES 어댑터

- **인증**: IAM 역할(Pod Identity)로 `ses:SendEmail`만 쓴다. 정적 액세스 키를 두지 않는다(ASVS 13.2.1, notify §4.4 ④). EKS 밖 시험은 주입한 클라이언트로만 돈다.
- **클라이언트**: `@aws-sdk/client-sesv2`(구현 턴에 의존성 추가, 버전 고정). SDK 자체 재시도는 끈다(`maxAttempts: 1`). 재시도는 워커의 원장 스케줄 하나만 쓴다(두 번 재시도하지 않는다). 연결 3초·전체 10초 [가정].
- **발신 도메인**: `FromEmailAddress`는 `PEAKET_NOTIFY_MAIL_FROM` 하나이고, `@` 뒤가 `PEAKET_NOTIFY_MAIL_FROM_DOMAIN`과 정확히 같아야 한다. 도메인이 다르면 시작 실패다. SPF·DKIM·DMARC·도메인 검증은 소유자 몫이다.
- **본문**: `Content.Simple.Subject`·`Content.Simple.Body.Text`만 쓴다(HTML 없음). 인코딩은 UTF-8이다. `Message-ID`·`Date`는 SES가 만든다.
- **머리**: `MailMessage.headers` 가운데 `List-Unsubscribe`·`List-Unsubscribe-Post`만 `Content.Simple.Headers`로 옮긴다. 그 밖의 머리는 버린다(대행사에 사용자 값이 새지 않게). 값에 CR·LF가 있으면 `PERMANENT`로 실패한다(헤더 주입).
- **메시지 태그**: `EmailTags`에 `peaket-dedup` **하나만** 넣고 값은 `base64url(SHA-256(messageKey))` 43자로 한다. 중복 키 원문(계정·주문 ID)을 대행사에 보내지 않는다. 태그로 같은 발송을 찾는 데는 쓰지 않고, 결과 웹훅의 `mail.messageId`를 원장의 `provider_message_id`와 맞춘다.
- **결과 분류**: 400(메시지 거절·발신 도메인 미검증)은 `PERMANENT`, 401·403·404·409·429·5xx·시간 초과·연결 실패는 `RETRYABLE`(설정을 고치면 남은 TTL 안에 다시 보낼 수 있다), 300·418처럼 모르는 상태는 `UNKNOWN`이다. SES의 `MessageRejected`처럼 400인데 주소 문제인 경우도 `PERMANENT`다. 429·5xx 응답의 `Retry-After`(초)를 `MailTransportError.retryAfterMs`에 싣는다(`$response.headers['retry-after']`, 없으면 `Retry-After`).
- **한도**: `PEAKET_NOTIFY_MAIL_RATE_PER_SEC` 토큰 버킷(1초 창)을 어댑터 안에서 지킨다. 다 쓰면 대행사를 부르지 않고 `RETRYABLE`('rate-limited')로 실패해 워커가 다음 간격에 다시 집는다. `Retry-After`가 있으면 그 값을 `MailTransportError.retryAfterMs`에 싣는다.
- **설명**: `SesMailTransport.describe()`는 `{ provider:'ses', region, from, fromDomain, configurationSet, snsTopicArn, ratePerSec }`를 돌려준다(비밀 없음). 조립 시험이 전달 값을 확인하는 데 쓴다.
- **남는 한계**: SES 평판·반송 억제 목록·샌드박스 해제는 소유자 몫이다. 실제 발송 시험은 자격 증명이 없어 하지 않는다.

### 3.3 Solapi 어댑터(문자·알림톡)

- **인증**: `Authorization: HMAC-SHA256 apiKey=…, date=…, salt=…, signature=…`(Solapi v4 규격, 구현 턴에 계약 문서로 확인). API 키·비밀은 Secrets Manager에서만 읽고 로그·요약에 넣지 않는다. 나가는 요청은 `https://api.solapi.com` 443만이다.
- **문자**: `POST /messages/v4/send`에 `{message:{to, from, text}}`를 보낸다. `from`은 `PEAKET_SOLAPI_SENDER_NUMBER`(숫자만, 하이픈은 설정에서 지운다), `to`는 identity가 준 전화번호, `text`는 워커가 만든 `[피켓] ` 머리 본문이다. 응답의 `messageId`를 `providerMessageId`로 돌려준다.
- **알림톡**: 같은 경로에 `kakaoOptions:{pfId, templateId, variables}`를 싣는다. 템플릿 ID는 `PEAKET_NOTIFY_ALIMTALK_TEMPLATES`에서 종류로 찾고, 변수는 `SmsMessage.templateVariables`(호출자가 허용 목록으로 만든 값)만 보낸다. 템플릿이 없는 종류는 `PERMANENT`('template-missing')다.
- **연결 범위**: 이번 구현은 **문자(SMS)만 워커에 연결**한다. 알림톡은 템플릿 심사·변수 계약이 없으므로 어댑터·설정 계약·payload 시험까지만 두고, `ALIMTALK` 작업은 지금처럼 `DEAD`다(미실행). 소유자 키와 템플릿 ID가 오면 `ALIMTALK_ALLOWED_KINDS` 검사를 지나 워커에 연결한다.
- **결과 분류**: 400(번호·발신번호·템플릿 오류)은 `PERMANENT`, 401·403·404·409·429·5xx·시간 초과·연결 실패는 `RETRYABLE`, 300·418처럼 모르는 상태는 `UNKNOWN`. 429·5xx 응답의 `Retry-After`(초)를 `SmsTransportError.retryAfterMs`에 싣는다.
- **한도**: `PEAKET_NOTIFY_SMS_RATE_PER_SEC` 토큰 버킷. 초과는 `RETRYABLE`. `Retry-After`는 `SmsTransportError.retryAfterMs`에 싣는다.
- **설명**: `SolapiSmsTransport.describe()`는 `{ provider:'solapi', senderNumber, ratePerSec, alimtalk: { pfId, templateCount } | null }`를 돌려준다(API 키·비밀·웹훅 비밀 없음).
- **남는 한계**: Solapi의 실제 결과 웹훅 서명 규격은 계약 문서로 확인하지 못했다. 우리 수신기는 `X-Peaket-Timestamp`·`X-Peaket-Signature`(아래)를 요구하는 [가정]안으로 두고, 계약 때 대행사 규격이 확인되면 검증 함수만 바꾼다(수신 경로·지표는 그대로).

### 3.4 대행사 결과 웹훅

- **SES(SNS)**: `POST /internal/v1/notify/provider-events/ses`. 본문은 SNS JSON이다. `verifySnsNotification`은 **인증서를 비동기로 받아 기다린 뒤** 서명을 확인한다. 다음을 모두 통과해야 받는다.
  - `SigningCertURL`은 `https:`이고 호스트가 `sns.<PEAKET_SES_REGION>.amazonaws.com`과 정확히 같고, 경로가 `/SimpleNotificationService-*.pem` 꼴이다. 리디렉션을 따르지 않는다. 인증서는 짧게 캐시한다. **호스트·경로·프로토콜이 틀리면 인증서 해석기를 부르지 않는다**(SSRF·불필요한 바깥 호출 방지).
  - `TopicArn`이 `PEAKET_SES_SNS_TOPIC_ARN`과 같다.
  - `SignatureVersion` 1(SHA-1) 또는 2(SHA-256)의 서명이 메시지 종류별 canonical string과 맞는다. `Notification`은 `Message`·`MessageId`·(`Subject`)·`Timestamp`·`TopicArn`·`Type`, `SubscriptionConfirmation`은 `Message`·`MessageId`·`SubscribeURL`·`Timestamp`·`TopicArn`·`Type` 순서다.
  - `Timestamp`가 1시간 [가정] 안이고 미래로 5분 [가정]을 넘지 않는다. 본문은 256KiB [가정] 이하다(경계 포함).
  - `SubscriptionConfirmation`은 **자동 확인하지 않는다**(소유자가 콘솔에서 한 번 확인한다). `SubscribeURL`을 호출하지 않고 403으로 거절한다. `UnsubscribeConfirmation`도 받지 않는다.
- **사건 분류**: configuration set 이벤트의 최상위 `eventType`을 먼저 읽고, 옛 알림 호환으로 `notificationType`도 받는다. `Bounce`·`Complaint`·`Delivery`만 `BOUNCE`·`COMPLAINT`·`DELIVERY`로 바꾸고 `mail.messageId`를 `providerMessageId`로 둔다. 받는 사람 주소는 결과·로그·지표에 싣지 않는다. 이번 턴에는 지표·경보만 올리고 원장 상태를 바꾸지 않는다(신청 삭제 같은 상태 변경은 아래 '남는 것').
- **Solapi**: `POST /internal/v1/notify/provider-events/sms`. `X-Peaket-Timestamp`(초)와 `X-Peaket-Signature: v1=<hex HMAC-SHA256(키, timestamp + "." + 원문 본문)>`를 요구한다. **HMAC 키는 `PEAKET_NOTIFY_SMS_WEBHOOK_SECRET`을 base64url로 푼 바이트**다(문자열 그대로가 아니다). 비교는 상수 시간이다. 5분 [가정] 밖의 timestamp·서명 불일치·모양 오류는 401로 거절하고 지표만 센다. 사건은 `DELIVERED`·`FAILED` 두 가지로 분류한다([가정] 봉투). 오류 문구에 비밀·서명 값을 넣지 않는다.
- **HTTP**: SES·Solapi 모두 받으면 **202**, 서명 불일치는 **401**, 토픽·인증서 호스트·구독 확인·모양·상한 위반은 **403**이다. 두 경로는 게이트웨이에 공개하지 않는다(`/internal/*`).
- **지표**: 받은 사건은 `notify_provider_events_total{provider, kind, result}`, 거절은 `notify_provider_webhook_rejected_total{provider, reason}`로 센다. 라벨은 이 다섯 이름만 쓰고 계정·주소·전화번호·메시지 ID를 라벨 값으로 쓰지 않는다. 연속 거절은 SEV3 후보로 observability 문서에 적는다(구현 턴).
- **남는 것**: 반송·스팸 신고로 신청을 지우는 일(notify §10)은 `notification_delivery.provider_message_id` 조회 인덱스가 필요해 이번 턴에 하지 않는다. 동결 마이그레이션을 새 번호로 만들지 않는다(ADR-0386 결정 5). F-06-9·소유자 몫으로 남긴다.

### 3.5 재시도·한도

- 대행사 `Retry-After`(초)를 `MailTransportError.retryAfterMs`·`SmsTransportError.retryAfterMs`에 싣는다. 워커는 `max(정본 재시도 간격, retryAfterMs)`로 다음 시각을 잡고, 그 시각이 `expiresAt`을 넘으면 `EXPIRED`다. `Retry-After`가 없으면 지금 규칙 그대로다.
- 대행사 SDK/HTTP 클라이언트의 자동 재시도는 끈다. 재시도는 원장 하나에서만 센다(중복 발송을 줄인다).
- 한도 값은 계약 값이고 이 계획은 수치를 주장하지 않는다. 시험은 `ratePerSec: 2`, `retryAfterMs: 300_000` 같은 작은 값으로 경계만 본다.

### 3.6 국외 이전

- SES·SNS는 `ap-northeast-2`(서울)만 쓴다. 다른 리전이 설정되면 staging·prod 시작 실패다. 리전을 바꾸려면 국외 이전 여부를 ADR-0139 등록부와 처리방침에 먼저 적고 소유자가 정한다.
- Solapi는 국내 사업자로 계약하되, 재위탁·보관 위치는 계약 때 확인해 data-classification 국외 이전 목록에 적는다. 확인 전에는 `[확인 필요]`다.
- 이메일 본문·받는 주소·전화번호는 대행사에 가는 것이 불가피하다. 로그·원장에는 남기지 않는 지금 규칙(notify §12)을 그대로 지킨다.

### 3.7 POL-034 흡수 계정 주소의 다중 파드·재시작 위험(후보만)

- 지금은 gRPC를 받은 파드와 워커 파드가 다르거나 프로세스가 다시 뜨면 주소가 없어 `ACCOUNT_MERGED_ABSORBED`가 `FAILED`다(notify §16).
- 후보: 주소를 짧은 수명 큐(디스크·DB에 남기지 않고 TTL이 끝나면 사라지는 큐)로 넘겨 같은 파드 밖에서도 한 번 처리한다. 그러나 POL-034의 "흡수 계정 프로필 즉시 파기"와 주소 비보관 경계를 바꾸는 **정책 결정**이라 이번 계획·구현에서 바꾸지 않는다. 소유자 확인 뒤 별도 ADR·기능으로 다룬다.
- 이번 시험은 기존 경계를 건드리지 않았는지(기존 `N-T23 ③` 재실행)만 본다.

### 3.8 광고 수신 동의·밤 금지 경계

- 공급자 어댑터는 알림 작업을 만들지 않는다. 작업을 만드는 곳은 `NotificationIntake` 하나이고, 광고(`AD`) 작업을 만드는 광고 묶음은 마케팅 수신 동의를 한 계정만 넣는다(정본 §7.2, F-06-9). notify는 동의 저장소가 아니므로 동의를 추측하지 않는다.
- **문자·알림톡으로 광고를 보내지 않는다**: `SMS_ALLOWED_KINDS`에 `AD`가 없고, 새 `ALIMTALK_ALLOWED_KINDS`에도 넣지 않는다. 인테이크가 `AD`+SMS/알림톡을 `INVALID`로 거절한다.
- **광고 문안 필수 값**: `AD` 작업은 `sender`(전송자 명칭)·`contact`(연락처)·`unsubscribeUrl`(수신 거부 방법)이 모두 있어야 만들어진다. 없으면 `INVALID`다(정보통신망법 §50④).
- **밤 금지**: 워커가 보내는 순간 21:00~08:00 KST이면 `AD`는 어느 채널로도 보내지 않고 작업을 지우며 `suppressed`로 센다. 다음 낮으로 미루지 않는다(§7.3).
- 광고의 14일 처리 결과 통지·2년 재확인·동의 철회는 F-06-9 범위다. 이 기능은 발송 경계만 지킨다.

## 10. 완료의 정의

- 계획·시험·리뷰·지적 반영·구현·문서·기록 커밋이 이 가지에 있고, 꼬리말(`Batch: F-06-6`, `Feature: F-06-6`, `Role`, `Agent-Session`, `Agent-Model`)이 맞다.
- 새 시험과 기존 F-06-1·notify 시험이 모두 통과하고, 타입 검사·린트·문서 점검(오류 0)·장부 `--require`·release-scope가 통과한다.
- 운영 설정이 없을 때 staging·prod가 시작하지 않고, 설정이 있을 때 SES·Solapi·VAPID가 조립된다. 실제 발송은 **미실행**으로 남고, 소유자 키가 온 뒤 별도 배포·확인으로 켠다.
- 정본(notify·secrets-and-keys·data-classification·ASVS·observability)이 구현과 같다. POL-034 메모리 inbox·gRPC·원장 경계는 그대로다.
- F-06-6은 `막힘` 그대로이고, 이 가지는 `develop`·`release/1.0.0`에 합치지 않는다(ADR-0386 결정 4).
