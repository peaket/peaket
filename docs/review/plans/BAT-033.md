# BAT-033 계획 — K7 마무리(3초·홀드 50ms)

- 작성: 2026-11-12
- 묶음: BAT-033(HOT-467, 갈래 1, 구간 1, **A등급**, 1~2일 [가정])
- 장부 범위: `P-T1`, `P-T47`
- 선행: BAT-032(HOT-466, R-477) — 부분 완료·중단, OPEN[38]
- 웨이브: ADR-0267에 따라 갈래 1의 첫 웨이브. 이 배치가 측정 창을 혼자 쓴다. 다음 웨이브는 감독이 합친 뒤 시작한다.

## 1. 목표

- K7 ②(v1 합본 100/s 혼합 부하, 100초)를 **회마다 새 클러스터**에서 3회 재어 3회 모두 유효(놓침 0·시나리오 오류 0)이고 결제 확정 p99가 **3,000ms 이하**인지 본다.
- 홀드 p99 목표 **50ms**를 k6 `route:hold`로 볼지 서버 `hot_path`로 볼지 정본 결정이 필요하면 `OPEN[39]`로 남기고, 이번 보고에는 **k6 값과 서버 라우트 값을 함께** 기록한다.
- A/A 조용한 쌍이 ±9.6% 안에 드는지 확인하고, K2(2,000/s·4발생기)를 3회 재어 50ms 목표와 A/A 기준을 함께 본다.
- 목표 미달이면 숨기지 않고 원인·지표·다음 갈래를 기록한다.

## 2. 배경

- BAT-032 r1은 유효했지만 결제 확정 p99 **3,039.9ms**(목표 3초를 40ms 초과), 홀드 k6 p99 243.9ms·서버 라우트 p99 43.4ms였다.
- BAT-032는 K7 3회·A/A·K2 3회·A등급 게이트를 중단하고 OPEN[38]로 넘겼다.
- 50ms 게이트의 측정 기준(k6 vs 서버 `hot_path`)이 정본에 없다. BAT-032는 둘을 함께 기록하고 결정을 OPEN[38] (마)로 넘겼다.

## 3. 측정 조건

- 환경: Windows 11, i9-14900HX 24코어/32스레드, Docker 32 CPU·16GiB. 다른 갈래의 무거운 시험·빌드·부하를 돌리지 않는다.
- 클러스터: kind `peaket` 단일 노드, v1 네임스페이스. K7 3회는 **회마다** `cluster.mjs down/up/observability/v1`로 새로 만든다.
- v1 합본: 복제 3, CPU 요청=한도 4, 메모리 요청=한도 2Gi, `PEAKET_BUNDLE_MODE=split`, HPA 끔, relay purchase·payment 각 2.
- K7: `loadtest/run.mjs v1 payment --users 11002 --rate 100 --seats-per-order 2 --warm 10 --main 100 --fault-drop-pct 5 --fault-delay-pct 0.5 --target-cpus 4`.
- K2/A/A: `loadtest/run.mjs v1 seat-hold --users 1000 --rate 2000 --generators 4 --warm 60 --main 60 --target-cpus 4 --mode hot`.
- 유효 판정: 놓침 0, 시나리오 오류 0, `startSkewS=0`. A/A는 조용한 쌍의 p99 비율이 ±9.6% 안.
- 서버 라우트 홀드 p99는 `hot_path_stage_seconds`의 홀드 구간(또는 기존 BAT-032와 같은 수집 경로)에서 같은 창으로 뽑는다.

## 4. 실행 순서

1. 기준선 확인: 현재 `origin/develop`(c4f4aa0e)에서 v1 무대를 새로 만들고 이미지·릴레이·split 구성을 확인한다.
2. K7 ② 100초 r1~r3을 회마다 새 클러스터에서 잰다. 각 실행의 `infra.txt`·`summary.json`·`checks.json`·`notes.txt`를 남긴다.
3. K2 quiet 3회를 잰다. 처음 두 번을 A/A 조용한 쌍으로 쓰고, 세 번 모두 K2 50ms 판정에 쓴다.
4. k6 홀드 p99와 서버 라우트 홀드 p99를 같은 실행에서 함께 뽑아 OPEN[39] 판단 근거를 만든다.
5. A등급 게이트를 돌린다: 변이(바꾼 코드가 없으면 “바꾼 코드 없음”을 근거로 남김), 복구 장애 주입, trace-check, test-int, 4관점 리뷰, 성능 장부, `ledger --batch BAT-033 --require`.
6. 결과를 `docs/review/measurements/BAT-033-k7-finish.md`에 기록하고 BUILD_ORDER·PROGRESS·계획을 갱신한다. 커밋은 웨이브 커밋 하나(R-484, `records.mjs --next-r`로 확인).

## 5. A등급 게이트

- typecheck, 관련 단위 시험, test-int 전체(또는 이 배치가 닿는 서비스의 test-int 전체), lint, doc-check.
- 변이: 이번 배치에서 코드를 바꾸면 항목마다 변이를 만들고 단위 시험이 실패하는지 확인한다. 코드 변경이 없으면 그 사실과 근거를 남긴다.
- 복구 장애 주입: K7 ②의 장애 주입(응답 버림 5%·지연 0.5%)과 프로세스 강제 종료 복구 시험을 확인한다.
- trace-check: `P-T1`·`P-T47`이 가리키는 측정·시험 증거를 확인한다.
- 4관점 리뷰: 정확성, 동시 실행/장애, 보안, 화면-서버 연결. 이번 배치가 측정·문서 중심이면 바뀐 diff만 본다.
- 성능 장부: K7 3회를 `docs/perf-ledger/runs/`에 기록한다.
- `ledger --batch BAT-033 --require`.

## 6. OPEN[39] — 홀드 50ms 기준

- 선택지: (가) k6 `route:hold` p99, (나) 서버 `hot_path` 홀드 p99, (다) 둘 다 게이트로 두고 하나는 참고.
- 이번 기록: 두 값을 함께 남긴다. BAT-032 기준 k6 243.9ms·서버 43.4ms.
- 추천: 서버 `hot_path`를 제품 SLI로, k6를 종단 참고로 두는 (나) 또는 (다). k6는 발생기·네트워크·시나리오 대기까지 포함해 제품 경로 밖 몫이 섞인다.
- 결정은 소유자 몫으로 남기고, 결정 전까지는 두 값을 모두 보고한다.

## 7. 위험

- K7 100초는 VU 고갈로 무효가 될 수 있다. 무효면 놓침·VU·발생기 skew를 기록하고 재실행 여부를 판단한다.
- 새 클러스터마다 이미지 적재·relay 준비가 필요하다. relay가 없으면 결제 결과가 5초 pull로 밀려 p99가 9초까지 악화된다.
- A/A 조용한 쌍 동안 다른 작업을 하지 않는다. 백그라운드 빌드·다운로드·도구 호출을 최소화한다.
- 목표 미달이면 미달로 기록하고 다음 웨이브를 시작하지 않는다.

## 9. 진행 결과(2026-11-12, R-485)

- K7 ② 100초 3회(회마다 새 클러스터, split·2Gi·relay 정상·CPU 4): r4 2,846.6ms·r5 2,649.9ms·r6 2,794.3ms로 모두 유효(놓침 0·오류 0·`startSkewS=0`), confirmMs p99 3초 안. 공식 `payment_p99_3000ms` 경로 점검은 8.9~9.4%로 fail이었다.
- 원인 분해(R-496): `over_target` 827·864·847 = PENDING 406·438·396(본구간 끝에서 잘림) + `payment` 접수 실패 343·356·375(M6의 빠른 비끝 답) + 실제 3초 초과 78·70·76. 실제 3초 초과는 1% 미만이었다.
- 측정 방법 수정(R-496): `paymentOverTarget`으로 본구간 마지막 3초 안에 시작한 반복은 끝 상태 여부와 무관하게 초과에서 뺀다. 그 밖의 비끝 상태는 M6대로 항상 초과다. `loadtest/test/v1.test.mjs`에 끝 경계 시험을 더했고, `v1-payment.js`에 `payment_end_truncated`를 `_terminal`·`_pending`으로 나눈 카운터와 `payment_accept_status`를 더했다. 접수 실패 343·356·375건의 응답 코드 분포는 r4~r6 원자료에 없어 사후 복원하지 못했고, 시나리오 중복·재시도는 아니라고 가렸다. 끝 3초 안의 PENDING이 모두 빠진다고 해도 접수 실패 + 실제 3초 초과 413~453건(4.5~4.8%)이 남아, 접수 실패가 줄지 않으면 공식 1% 점검은 다시 fail이다.
- 측정 방법 갱신(R-511, 2026-11-13, ADR-0269): 위 3초 끝 경계 제외를 **20초 드레인**으로 대체한다. 본구간 뒤 새 결제를 시작하지 않고(`gracefulStop: '20s'`), 드레인 중 끝난 결제는 접수 시작→끝 상태 실제 시간으로 판정하며(3초 이하 통과), 20초가 지나도 끝나지 않은 결제는 위반으로 센다. `payment_end_truncated*`는 없애고 `payment_drain_finished*`·`payment_drain_unfinished`로 남긴다. 4회 고정 상태 조회도 없애고, 빠른 비끝 답이면 100ms 쉬었다 다시 묻고 **최소 3초까지** 묻는다(전체 상한 20초). 3초 전에 포기한 결제는 `payment_pending_before_3s`로 남긴다.
- R-511 드레인 진단(2026-11-13): PENDING 278(3.09%)가 남았고, `payment-status` 10,076건은 8,901건보다 1,175건 많아 278건이 4회를 다 쓴 모양과 맞는다. 4회 고정 루프가 3초 전에 끝냈는지 가리려고 위 최소 3초 폴링과 PENDING 진단(`payment_pending_last_status`·`payment_status_calls`·`payment_pending_last_call_ms`)을 더했다.
- 홀드: k6 p99 199~224ms, 서버 `hot_path` r6 p99 9.84ms. 추천은 k6 `hold_p99_50ms` 정본·서버 진단이며, 정본 변경은 소유자 결정 전에는 하지 않는다(OPEN[39]).
- K2 2,000/s: p99 23~32ms로 50ms 안이지만 dropped_iterations 40~98인 실행이 많아 A/A 미성립.
- A등급 게이트: typecheck·lint·doc-check, test-int(payment-grpc 95·payment-process 11), trace-check P-T47, 성능 장부(r4~r6), `ledger --batch BAT-033 --require` 통과. 제품 코드 변경이 없어 변이 대상은 없었다.
- 보고서: `docs/review/measurements/BAT-033-k7-finish.md`.
