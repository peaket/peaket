# 작업 계획: F-09-2 N-1 — identity 앱이 N 스키마에서 계속 동작하는지 묶는다

- **무엇**: F-09-2 장부의 D-T8이 요구하는 **identity-svc N-1 앱 통합 묶음**이다. F-09-2 계획(`docs/review/plans/F-09-2.md` §2·§6·§8)과 `docs/devops.md` §7.1 원칙 2·§7.3 적용 시험 ③은 "확장 마이그레이션을 적용한 DB에서 N-1 앱의 통합 시험 묶음이 통과"해야 한다고 정했다. 그동안 이 몫은 `미실행`이었다(같은 계획 §9, `docs/review/ledger-notes.md` 386~390줄).
- **바탕**: 작업 폴더 `D:/ticketpass-freeze-F-09-2-n1`, 가지 `freeze/lane1-F-09-2-n1`, 출발점 `origin/freeze/lane1-F-09-2` `1b552c61d`(2026-11-27). 소유자 결정(2026-11-27) "N-1은 마이그레이션 직전 develop 커밋"과 감독 지시, F-09-2 계획, `packages/platform/src/migrations.ts`, `services/identity-svc`의 마이그레이션·test-int·`scripts/migrate.mjs`, `docs/devops.md` §7. 이 문서는 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **N-1 기준(소유자 결정)**:
  - **N-1 = `713b522a7f4566a7b9ef047012783f9be50bf675`** (2026-11-23, develop, identity 마이그레이션 0000~0037).
  - **migration = `0346eded88e7de8ba108c4288f5aa1c9cd478ffe`** (N-1의 다음 커밋, `0038_scanner_session_device_name.sql`을 더한다).
  - **N = 이 가지의 0000~0038.** 별도 릴리스 태그가 없으므로 출시 태그 대신 이 두 SHA를 쓴다.
- **정본**: `docs/devops.md`:599(모든 스키마 변경은 N-1과 N에 함께 맞는다)·:608~610(PreSync 마이그레이션 잡)·:633(적용 시험 ③ N-1 앱 통합 묶음)·:918(D-T8), `docs/data.md`의 identity 표·키 회전 절, `docs/features/identity.md` §5·§6·§8(본인확인 키·관리 계정·탈퇴), `docs/architecture.md` §8.6(계획·시험·기록 차례), `docs/BUILD_ORDER.md`:139(F-09-2), `docs/security/asvs/delivery.md`:75(13.2.2 DDL·DML 역할 분리).
- **등급과 차례**: B(F-09-2). 동결 기간이라 계획 → 시험 → 기록만 한다. 제품 코드·마이그레이션은 바꾸지 않는다(시험만 기능, `Batch-Kind: test-only`). 구현이 없으므로 구현 담당·구현 리뷰는 두지 않는다(ADR-0372·ADR-0373, `docs/architecture.md` §8.6 4).
- **동결 로컬 범위**: ADR-0386 결정 4·5. `develop`·`release/1.0.0`에 합치지 않고 이 가지에만 커밋·푸시한다. 출시 마이그레이션 목록·출시 환경 플래그·차트·Argo CD에 넣지 않는다. 실제 Aurora·PgBouncer·identity 기동, 30k/s·100만·K1/K2/K7 수치는 하지 않는다.

## 감독에게

1. **[확인] N-1을 `713b522a`로, migration을 `0346eded`로 고정했다.** 소유자 결정대로 "마이그레이션 직전 develop 커밋"을 N-1로 쓴다. `0346eded`가 0038을 더한 커밋이고 그 부모가 `713b522a`다. `713b522a`의 identity 마이그레이션은 0000~0037(38개)이고 관리 계정·본인확인 키 회전이 모두 들어 있다. 출발점 `1b552c61d`는 이미 0038을 포함해 N 스키마와 같으므로 "N-1"로 쓰지 않는다(§2).
2. **[확인] 이번 턴은 실제 `713b522a` 앱 프로세스를 띄우지 않는다.** 출시 이미지·태그가 없고, 그 트리를 설치해 시험 묶음을 돌리려면 별도 `pnpm install`과 38개 마이그레이션 기록을 N 실행기 기록과 맞추는 작업이 필요하다. Docker도 F-08-5 6시간 측정이 쥐고 있다. 대신 **`713b522a` 저장소 코드가 보내던 SQL 모양을 고정한 DB 계약**(`test-int/n1/contract.ts`)을 0000~0037 스키마에서 먼저 돌려 옛 스키마의 것임을 증명하고, 같은 계약을 N 스키마에서 다시 돌린다(§3). 실제 앱 묶음을 돌리는 절차는 §3.3에 설계만 해 두고 `미실행`으로 남긴다.
3. **[알림] 이 계약이 보장하는 것과 아닌 것.** 보장: 로그인·세션 생성/갱신/종료·관리 계정 로그인·pid/연락처 키 회전의 표·칸·값, N 앱과 N-1 앱의 양방향 읽기. 보장하지 않음: 앱 프로세스 기동, gRPC/HTTP 처리, 업무 규칙, KMS·Valkey 호출, 트랜잭션 순서(§9).
4. **[알림] 새 시험은 Docker 없이 도는 단위 3개와 실제 PostgreSQL 통합 4개다.** 단위는 N-1 기준 파일 38개의 SHA-256 고정과 계약 표 검사를 맡고, 통합은 두 DB(0000~0037, 0000~0038)에서 계약을 돌린다. 통합 4개는 이번 턴 `미실행`이다(§8).
5. **[알림] F-09-4와 경계.** 이 묶음은 identity DB 호환만 본다. D-T37(WAF 규칙표)·SR-T11 ②(CDN 캐시 키)·delivery v5.0.0-3.4.4(CloudFront `nosniff`)는 F-09-4 몫이라 건드리지 않는다. 릴리스 플래그·출시 환경 값·출시 마이그레이션도 만들지 않는다(§5).

## 2. 판단 1: N-1은 무엇인가

- **N-1 = 마이그레이션 직전 develop 커밋 `713b522a`.** 소유자 결정에 따라 출시 태그 대신 "새 마이그레이션 커밋의 부모"를 쓴다. 후보를 실제 저장소에서 견줬다.

| 후보 | identity 마이그레이션 | 관리 계정 | 키 회전 | 쓸 수 있나 |
| --- | --- | --- | --- | --- |
| `v0.2.0`(2026-11-04) | 0000~0003(4개) | 없음 | pid 초기 | 아니오. 관리 계정 경로를 볼 수 없다 |
| `origin/release/0.3.0` `99acb96b`(2026-11-09) | 0000~0029(30개) | 있음 | 있음 | 아니오. 출시 태그가 없고, 소유자 결정의 "마이그레이션 직전 develop 커밋"이 아니다 |
| **`713b522a`(2026-11-23, `0346eded`의 부모)** | **0000~0037(38개)** | **있음(0016~0028)** | **있음(0008·0014·0015)** | **예. 이 묶음의 N-1** |
| `1b552c61d`(2026-11-27, 이 가지 출발점) | 0000~0038(39개) | 있음 | 있음 | 아니오. 이미 0038을 포함해 N 스키마와 같다. 새 마이그레이션 경계를 볼 수 없다 |

- **N = 이 가지의 0000~0038(39개).** `0038`이 N-1 뒤에 더해진 마이그레이션이다.
- `git diff 713b522a HEAD -- services/identity-svc/migrations`로 확인한 결과 0000~0037은 **바이트까지 같다**(추가된 파일은 `0038_scanner_session_device_name.sql`과 journal뿐, snapshot은 0038 파일이 없다). 그래서 N-1 스키마는 지금 저장소의 0000~0037 파일을 그대로 실행해 만들 수 있고, 그 사실을 `manifest-713b522a.json`의 SHA-256으로 고정한다.
- **N-1 앱의 SQL 출처**: `713b522a`의 `src/modules/session/adapters/db/drizzle-session-store.ts`, `admin/adapters/db/drizzle-admin-account-store.ts`, `verification/adapters/db/drizzle-verification-store.ts`가 보내는 SQL 모양을 `contract.ts`에 옮겼다. 네 경로(로그인·세션 갱신/종료·관리 계정 로그인·pid/연락처 키 회전)는 0.3.0에서 바뀌지 않았고, `713b522a`에서도 같은 표·칸을 쓴다. 새 표·새 칸을 쓰지 않는다는 사실은 0000~0037 스키마에서 먼저 돌려 증명한다.

## 3. 판단 2: N-1을 어떻게 띄우나

### 3.1 이번 턴에 고른 방법: 고정 SQL 계약

1. 0000~0037 스키마를 만든 DB에서 계약을 먼저 돌린다. 여기서 실패하면 계약이 `713b522a`의 것이 아니다(새 칸을 썼다는 뜻).
2. 0000~0038 스키마를 새 실행기(`migrateIdentity`)로 만든 DB에서 같은 계약을 돌린다.
3. N 앱의 저장소(`DrizzleSessionStore`·`DrizzleAdminAccountStore`·`DrizzleVerificationStore`)가 1·2가 쓴 행을 읽는다.
4. N 앱이 쓴 행을 N-1 계약의 읽기 SQL이 읽는다.

### 3.2 왜 이번 턴에 실제 앱을 띄우지 않나

- `713b522a`는 이미지 태그가 아니라 develop 커밋이다. 출시 이미지가 없다.
- 그 트리를 `git worktree`로 꺼내 `pnpm install`한 뒤 시험 묶음을 돌리려면 38개 마이그레이션 기록을 N 실행기 기록과 맞추는 작업이 필요하다. `713b522a`의 `scripts/migrate.mjs`는 Drizzle migrator라 N 실행기의 `peaket_migration` 39행을 보면 `OUT_OF_ORDER`로 멈춘다.
- 이번 턴 Docker 잠금이 F-08-5에 있다. 그래서 계약만 먼저 고정하고 실제 앱 묶음은 `미실행`으로 둔다.

### 3.3 실제 `713b522a` 앱 묶음을 돌리는 절차(설계, 미실행)

Docker가 비고 설치 시간을 쓸 수 있을 때 다음 차례를 쓴다. 이 절차는 시험 파일이 아니라 운영자용 기록이다.

1. `git worktree add D:/ticketpass-n1-713b522a 713b522a`로 N-1 트리를 꺼내고 그 폴더에서 `corepack pnpm install --frozen-lockfile`을 돌린다.
2. 빈 PostgreSQL 18 컨테이너를 띄우고, **이 가지의** `migrateIdentity`로 N 스키마(0000~0038)를 적용한다.
3. `713b522a`의 `meta/_journal.json`에 있는 38개 `when` 값을 `drizzle.__drizzle_migrations`(`id`, `hash`, `created_at`)에 넣는다. Drizzle migrator는 마지막 `created_at`보다 늦은 파일만 적용하므로, 이 기록이 있으면 0000~0037을 다시 적용하지 않는다. `hash`는 그 파일의 SHA-256을 넣는다(마이그레이터는 기존 행의 해시를 검사하지 않는다).
4. `713b522a` 트리의 `test-int/postgres.ts`가 컨테이너를 새로 띄우지 않고 2의 DB 주소를 쓰게 하고, `scripts/migrate.mjs`는 3의 기록을 확인한 뒤 아무것도 적용하지 않게 임시로 바꾼다(작업 폴더 사본에서만, 저장소에는 남기지 않는다).
5. `corepack pnpm --filter @peaket/identity-svc test:integration`을 돌린다. 이 묶음이 `docs/devops.md`:633의 "N-1 앱의 통합 시험 묶음"이다.
6. 끝나면 컨테이너와 worktree를 지운다. 결과(시험 수·실패·시간)를 이 계획의 '시험 결과'에 적는다.

- **계약의 한계를 숨기지 않는다**: 계약은 "DB에 닿는 모양"만 본다. 앱이 기동해 로그인·관리 로그인·키 회전을 실제로 끝내는지는 보지 않는다. 그래서 이 묶음의 완료를 "실제 `713b522a` 앱 묶음 통과"로 부르지 않는다. 저장소 코드가 보내는 SQL을 그대로 옮겼다는 것과 양방향 읽기를 완료로 부른다.

## 4. 판단 3: 배포 순서와 되돌리기

`docs/devops.md` §7.1~§7.3의 확장 → 이전 → 축소를 identity에 적용하면 다음과 같다. 이 묶음은 1~3을 시험으로 확인할 뿐, 배포하지 않는다.

| 단계 | 스키마 | 앱 | 이 묶음이 보는 것 |
| --- | --- | --- | --- |
| 0. 기준 | 0000~0037 | N-1(713b522a) | 계약이 옛 스키마에서 돈다 |
| 1. 확장 | 0000~0038 PreSync | N-1 그대로 | 계약이 N 스키마에서 다시 돈다. N-1 쓰기·읽기 성공 |
| 2. 카나리 | 0000~0038 | N-1 + N | N이 N-1 행을 읽고, N-1이 N 행을 읽는다 |
| 3. 전환 | 0000~0038 | N 100% | N 앱 통합 묶음(기존 test-int)이 N 스키마에서 돈다 |
| 4. 축소 | N+1 | N | 이 묶음 밖(다음 출시) |

- **되돌리기 조건**: 앱만 되돌리고 스키마는 되돌리지 않는다(`docs/devops.md`:598, ADR-0054 결정 8). 다음 중 하나면 N 배포를 멈추고 N-1 이미지를 100%로 돌린다.
  1. N-1 파드의 로그인·세션 갱신·관리 로그인 5xx가 [가정] 1%를 5분 넘는다.
  2. N-1 SQL이 `42P01`(표 없음)·`42703`(칸 없음)·`23502`(NOT NULL 위반)·`23505`(유일 위반)·`23514`(CHECK 위반)·`23503`(외래 키 위반)로 실패한다.
  3. 관리 계정 로그인 1단계/2단계가 실패하거나, pid 키 회전이 `pid_rows_below`에서 줄지 않는다.
  4. PreSync 마이그레이션 잡이 실패한다. 이때는 롤아웃이 시작되지 않는다(`docs/devops.md`:610).
- **되돌릴 수 없는 것**: 0000~0038 중 하나라도 DROP·RENAME·SET NOT NULL·좁히는 TYPE 변경이면 N-1이 깨진다. 지금 0038은 NULL 허용 칸 추가라 확장이다. 하나라도 축소가 섞이면 `tools/ci/migration-check.mjs n1`이 먼저 막고, 이 시험이 뒤에서 잡는다.
- **수치 기준은 [가정]**: 1%·5분은 이번 턴에 재지 않았다. 실제 배포 판정은 관제 지표와 함께 소유자가 정한다. 이 문서는 그 자리를 비워 두고 수치를 주장하지 않는다.

### 6.2 시험 이름과 단언

시험 이름은 `D-T8 …`로 시작한다. D-T8은 장부에서 세부 번호가 없는 한 항목이라 ①을 붙이지 않는다(붙이면 장부에 없는 세부를 만든 것처럼 읽힌다).

| 이름 | 단언(정본·N-1에서 온 값) |
| --- | --- |
| `D-T8 identity N-1 기준 스키마 0000~0037이 713b522a와 같다` | 출처가 `713b522a`(N-1)·`0346eded`(migration)이고 파일 38개, 각 SHA-256이 manifest와 같다 |
| `D-T8 identity N-1 기준 스키마 파일이 하나라도 바뀌면 막는다` | 0037을 한 줄 고친 사본에서 `assertN1Baseline`이 그 파일 이름으로 던진다(음성 대조) |
| `D-T8 identity N-1 계약이 713b522a에 없는 표를 쓰면 막는다` | `N1_TABLES`는 통과하고 `receivable_movement`(payment 표)를 더하면 던진다(음성 대조) |
| `D-T8 identity N-1 계약이 713b522a 스키마에서 로그인·세션·관리 계정·키 회전을 마친다` | 제공자 조회 0→1, 지금/앞/지난 리프레시 해시 각 1행, 관리 이메일 1행, 로그인 1단계 1행, 진행 중 pid 회전 1행, pid 판 [2], 연락처 `k2.contact-bbbb`·옛 값 `k1.contact-aaaa`, 로그아웃 뒤 `terminated_reason='LOGOUT'` |
| `D-T8 identity N 스키마에서 N-1 계약이 그대로 돈다` | 위와 같은 값이 N 스키마에서도 나온다 |
| `D-T8 identity N 앱이 N-1 앱이 쓴 세션·관리 계정·키 회전 행을 읽는다` | `sessionOf`가 계정·기기·패밀리·`ALLOW`·`terminatedAt=null`, `refreshOwner`가 두 해시 모두 같은 계정, `liveSessionsOf`가 기기 이름·마지막 활동, `investigationRefsOf`가 연락처 둘·기기 가명, 관리 `get`/`findForLogin`이 `operator`·`INVITED`, `claimsOf`가 새 pid, `pidKeyVersionsInUse`에 2가 있다 |
| `D-T8 identity N-1 앱이 N 앱이 쓴 세션·관리 계정·키 회전 행을 읽는다` | N 앱이 만든 세션·리프레시·관리 계정·본인확인을 N-1 계약의 `select`가 정확한 값으로 읽는다 |

- **두 DB를 쓴다**: 한 컨테이너 안에 `identity_n1`(0000~0037)과 `identity_n`(0000~0038)을 만든다. 한 DB에서 스키마를 지웠다 다시 만들면 `retention`·`drizzle` 스키마와 outbox 파티션이 섞여 시험 사이가 오염된다.
- **N 스키마는 새 실행기로 만든다**: `migrateIdentity`(`@peaket/platform/migrations`)를 부른다. N-1 스키마만 713b522a 파일을 직접 실행한다. 그래야 "새 실행기가 만든 N 스키마"와 "N-1이 기대한 스키마"를 가른다.
- **실패를 숨기지 않는다**: `passWithNoTests: false`, Docker가 없으면 `startPostgres()`가 던진다(건너뛰지 않는다). `try/catch`로 삼키지 않는다.
- **CI**: `pnpm --filter @peaket/identity-svc test:integration`은 `.github/workflows/ci-node.yml`의 통합 잡에 이미 있다. 새 파일은 그 묶음에 자동으로 들어간다.

## 수용 기준

1. 계약이 **0000~0037 스키마에서 먼저** 통과한다. 여기서 실패하면 계약이 `713b522a`의 것이 아니므로 N 스키마 결과를 근거로 쓰지 않는다.
2. 같은 계약이 **0000~0038 스키마에서** 통과한다.
3. N 앱이 N-1이 쓴 세션·관리 계정·키 회전 행을 정확한 값으로 읽고, N-1 계약이 N 앱이 쓴 같은 행을 읽는다.
4. N-1 기준 파일 38개의 SHA-256이 `713b522a` manifest와 같고, 계약이 쓰는 표가 모두 0000~0037에 있다.
5. 제품 코드·마이그레이션·계약·차트·출시 환경 값·출시 플래그를 바꾸지 않는다.
6. 시험 이름에 `D-T8`이 있고, 통합 시험은 `ci-node.yml`의 identity 통합 잡에 들어간다.
7. §10의 게이트가 통과하고, 통합 시험을 돌리지 못했으면 `미실행`과 까닭을 기록한다.

## 7. 손댈 파일

- 이 계획 문서와 기록 커밋의 `docs/review/ledger-notes.md` 한 절.

## 9. 남은 위험

1. **계약은 앱이 아니다.** `713b522a` 앱 프로세스·gRPC·HTTP·업무 규칙·KMS·Valkey는 이 묶음이 보지 않는다. 실제 앱 시험 묶음을 돌리려면 §3.3의 절차가 필요하다.
2. **N-1은 출시 이미지가 아니라 develop 커밋이다.** 이 저장소에는 `v0.3.0` 이후 출시 태그가 없어 소유자 결정대로 커밋을 썼다. 나중에 출시 태그가 생기면 그 태그의 커밋이 `713b522a`와 같은 뿌리인지 확인하고, 다음 출시부터는 직전 출시 태그를 N-1로 쓴다.
3. **0038은 NULL 허용 칸 추가라 N-1 계약이 통과했다**(3차, 4/4). 다만 실제 `713b522a` 앱 묶음은 아직 돌리지 않았다.
4. **전체 identity 통합 묶음**은 N 스키마에서 37파일 227/227(1 skip)로 통과했다(3차). 1 skip은 `PEAKET_LOCAL_STACK=1`일 때만 도는 로컬 스택 도우미다. 이 묶음의 4개와 전체 N 앱 묶음이 모두 통과해도, 실제 `713b522a` 앱 프로세스 묶음(§3.3)은 별도다.
5. **실제 Aurora·PgBouncer·TLS**는 이 묶음 밖이다. N-1 앱이 PgBouncer를 거쳐 N 스키마를 읽는 경로는 로컬 컨테이너와 다를 수 있다.
6. **되돌리기 수치(1%·5분)**는 [가정]이다. 실제 관제 지표·SLO와 맞추는 일은 배포 단계 몫이다.

## 실패 시나리오

1. 0038이 계약이 쓰는 칸을 지우거나 이름을 바꾼다 → N-1 계약이 `42703`(칸 없음)으로 실패한다.
2. 기본값 없는 `NOT NULL` 칸을 더한다 → N-1 insert가 `23502`로 실패한다.
3. 기존 값과 맞지 않는 `CHECK`를 더한다 → N-1 insert/update가 `23514`로 실패한다.
4. N-1이 만들 수 있는 중복 행을 막는 유일 인덱스를 더한다 → `23505`로 실패한다(예: 살아 있는 행이 둘인 상태에서 유일 인덱스 생성).
5. N-1이 부모 없이 넣는 행에 외래 키를 더한다 → `23503`으로 실패한다.
6. 적용한 N-1 기준 파일을 고친다 → 단위 manifest 시험이 파일 이름으로 막는다.
7. 계약이 N-1에 없는 표·칸을 쓴다 → 0000~0037 계약 실행이 먼저 실패하거나 표 검사가 막는다.
8. N 앱이 N-1 행을 못 읽는다 → N 앱 읽기 시험이 `null`/다른 값으로 실패한다.
9. N-1 계약이 N 앱 행을 못 읽는다 → N-1 읽기 시험이 실패한다(되돌리기 때 옛 앱이 새 데이터를 못 읽는 경우).
10. Docker가 없는데 시험을 건너뛴다 → `passWithNoTests: false`와 `startPostgres()`의 예외로 막는다. `try/catch`로 삼키지 않는다.
11. N-1 기준을 `v0.2.0`으로 잘못 잡는다 → 관리 계정·키 회전 표가 0000~0003에 없어 계약이 실패한다(§2의 후보 비교).
12. PreSync 마이그레이션 잡이 실패한다 → 롤아웃이 시작되지 않는다(`docs/devops.md`:610). 이때도 스키마를 되돌리지 않는다.
13. 스키마를 되돌리려 한다 → §7.1 원칙 1(앞으로만)과 ADR-0054 결정 8을 어긴다. 앱만 되돌린다.
