## 감독에게

막는 물음은 없다. 아래는 추천대로 계획에 적었다. 다르게 정하면 이 계획과 그 정본 줄을 고친다.

1. **[결정 요청] 장부 범위를 11항목으로 좁힌다.** 지금 F-07-13 행의 `I-T53, docs/security/asvs/auth.md`는 장부 140항목(자동 74·ID만 26·빈칸 29·해당 없음 7·다른 단계 4)을 낸다. auth.md 전체는 다른 기능 몫이 섞여 있어 이 기능이 다 닫을 수 없다. `docs/architecture.md` §8.6 3의 "기능을 시작할 때 범위를 좁힌다"에 따라 **I-T53과 이 기능이 닿는 ASVS 행 여섯**(6.3.3·6.4.4·7.4.3·7.5.1·7.5.2·8.2.2)으로 좁힌다. 좁힌 뒤 장부는 11항목 모두 자동 시험이라 `--require`가 지금도 통과한다. 이 기능의 새 시험은 그 11항목의 상태를 바꾸지 않고 판정 근거를 두텁게 한다.
2. **[결정 요청] 계약을 넓힌다.** SCR-020 '내 계정'의 네 줄은 openapi에 경로가 없다(`docs/review/plans/F-07-7.md` G-19). 파트너 인증 경로 여섯(`GET /v1/partner/auth/security-settings`, `POST /v1/partner/auth/totp-enrollments`, `POST /v1/partner/auth/totp-confirmations`, `POST /v1/partner/auth/recovery-codes`, `GET /v1/partner/auth/sessions`, `DELETE /v1/partner/auth/sessions/{sessionId}`)을 더하고 `packages/contracts`·`packages/api-client` 생성물을 함께 커밋한다. 새 외부 계정·비용은 없다. 관제 콘솔의 같은 화면(SCR-028)은 이 기능에 넣지 않는다.
3. **[알림] 저장 칸을 넷 더한다.** 기기 이름을 보이려면 `admin_session.device_label`, 재등록을 시작한 세션에만 확인을 허용하려면 `admin_account.totp_pending_session_id`, 확인 코드 실패를 세려면 `admin_account.totp_pending_failures`가 필요하다. 마이그레이션 `services/identity-svc/migrations/0040_admin_account_security.sql`(번호는 구현 때 비어 있는 번호로 확인)은 **동결 로컬 전용**이다. `docs/data.md`의 `admin_session`·`admin_account`에 칸을 적는다.
4. **[가정] 화면 QR은 이번에 그리지 않는다.** 파트너 앱에 QR 라이브러리가 없다. 인증 앱 다시 등록은 `otpauth://` 주소와 비밀 키를 글로 보이고, 사용자가 인증 앱에 직접 넣는다. d5 §6.1 ⑦의 QR 그림과 다른 점이며, QR은 화면 후속으로 남긴다. 이번 판정은 "다시 등록이 실제 API로 끝난다"까지다.
5. **[알림] 프로필·비밀번호·패스키 줄은 이번 범위 밖이다.** F-07-7이 '내 계정 패스키 줄'을 동결했고(감독 결정 2026-11-23), 비밀번호 바꾸기와 프로필은 기존 화면 그대로 둔다. 이 기능은 **인증 앱·복구 코드·로그인 기기** 세 줄만 실제 API로 잇는다. `AccountPage`의 나머지 줄은 미리보기와 같은 목업을 유지한다. 화면 전체를 실제 API로 바꾸는 일은 하지 않는다.
6. **[알림] 실제 TOTP 기기·브라우저·운영 세션 저장소는 `미실행`/`[가정]`이다.** 이번 턴은 Docker·kind·AWS·브라우저를 쓰지 않는다. TOTP 앱 실기기, 브라우저 패스키 창, 실제 Redis·PostgreSQL 세션 저장소는 시험 대역(메모리·소프트웨어 인증기)으로만 본다. `docker`는 F-08-5 6시간 측정이 쥐고 있다.
7. **[알림] F-09-6 구현은 아직 구현 리뷰 전이다.** 이 기능은 F-09-6의 `BeginTotpEnrollment`·`ConfirmTotpEnrollment`·`ManagePasskeys`·`ReauthenticateAdmin`을 재사용한다. F-09-6 구현 리뷰가 이 부분을 바꾸면 이 가지를 다시 쌓는다.
8. **[알림] 새 A 기능 구현 리뷰를 한다.** 계획 커밋에 `Batch-Grade: A`를 단다. 구현이 고정 시험을 모두 통과한 뒤, 구현을 맡지 않은 새 세션이 바뀐 코드를 보고 `IR-NN` 지적을 남긴다(ADR-0381).

#### 1.2 이 기능이 하는 것

**A. 인증 앱(TOTP) 다시 등록**

- A1. `POST /v1/partner/auth/totp-enrollments`: `ACCOUNT_SECURITY` 재인증 토큰(그 세션·그 콘솔·jti 한 번·패스키가 있으면 passkey 요소)을 확인하고, 새 시드를 `totp_pending_enc`에 암호화해 두며 `totp_pending_session_id`에 그 세션 ID를 적는다. 응답은 `otpauthUri` 하나이고 `Cache-Control: no-store`다. 기존 `totp_seed_enc`는 건드리지 않는다.
- A2. `POST /v1/partner/auth/totp-confirmations`: 그 세션이 시작한 대기 시드에 대해서만 코드를 본다. 틀리면 `totp_pending_failures`를 하나 올리고 422 `reauth-code-invalid`(`remainingAttempts`)다. 5번 [가정]째 틀리면 대기 시드·세션·실패 수를 지우고 410 `totp-enrollment-invalid`다. 이 실패는 계정의 `secondFactorFailures`·`lockKind`·`failedAttempts`를 건드리지 않는다.
- A3. 맞으면 한 트랜잭션에서 `totp_seed_enc`를 새 시드로 바꾸고 `totp_pending_enc`·`totp_pending_session_id`·`totp_pending_failures`를 비우며 `totp_last_step`을 확인한 시간 칸으로 적고, 옛 복구 코드를 모두 지우고 새 복구 코드 10개 [가정]를 넣는다. 응답은 `{ recoveryCodes }`로 한 번만 준다. 세션은 만들지 않는다.
- A4. 확인 전에는 옛 인증 앱 코드가 그대로 로그인 2단계에 쓰인다. 확인 뒤에는 옛 시드·옛 복구 코드가 모두 무효다. 다른 세션에서 확인을 부르면 410이다(대기 시드가 그 세션에 묶여 있다).

**B. 복구 코드 다시 만들기**

- B1. `GET /v1/partner/auth/security-settings`: 로그인한 계정의 `totpRegistered`(시드 있음), `recoveryCodesRemaining`(남은 행 수), `passkeyCount`, `sessionLimit`(2)를 준다. `Cache-Control: no-store`다.
- B2. `POST /v1/partner/auth/recovery-codes`: `ACCOUNT_SECURITY` 재인증을 확인하고, 인증 앱이 등록되어 있지 않으면 409 `totp-not-registered`, 등록되어 있으면 옛 복구 코드를 모두 지우고 새 10개 [가정]를 넣는다. 응답은 `{ recoveryCodes }`로 한 번만 준다. 세션은 끝내지 않는다.

**C. 로그인 기기 목록**

- C1. `GET /v1/partner/auth/sessions`: 그 계정의 살아 있는 관리 세션을 `pairRef`(출발지 묶음)마다 한 줄로 묶어 준다. 줄은 `{ sessionId, deviceName, lastActiveAt, current, otherSessions }`이고 지금 세션이 들어 있는 줄이 맨 앞, 나머지는 마지막 활동이 늦은 순이다. `deviceName`은 로그인 때 User-Agent에서 뽑은 화면용 이름(없으면 null), `lastActiveAt`은 `idle_expires_at − 유휴 1시간` [가정]이다. 원문 User-Agent·IP·`pairRef`·토큰·시드·해시는 싣지 않는다. 부른 세션이 이미 끝났으면 401 `session-ended`다. `Cache-Control: no-store`다.
- C2. 세션 상한 2와 목록의 관계: 같은 기기에서 두 번 로그인하면 한 줄에 `otherSessions: 1`로 보인다. 다른 기기면 두 줄이다. 목록은 세션을 줄이거나 늘리지 않는다.

**D. 기기 끊기**

- D1. `DELETE /v1/partner/auth/sessions/{sessionId}`: `ACCOUNT_SECURITY` 재인증을 확인하고, 대상 세션과 같은 `pairRef`의 살아 있는 세션을 **현재 세션만 남기고** 모두 끝낸다(이유 `LOGOUT`, 세션마다 `control.sessions-terminated`). 지금 세션이 든 줄의 대표 세션 ID를 보내면 같은 기기의 다른 로그인만 끝내고 204다(팬의 같은 규칙). 그 줄에 다른 로그인이 없으면 404 `session-not-found`이고 지금 세션은 그대로다(로그아웃은 `DELETE /v1/partner/auth/sessions/me`가 맡는다).
- D2. 다른 계정의 세션·없는 ID·이미 끝난 세션·같은 기기의 다른 로그인이 없는 지금 기기 줄은 모두 같은 404 `session-not-found`다. 404는 재인증 토큰을 쓰지 않으며, 같은 토큰으로 다시 유효한 대상을 끊을 수 있다. 이미 끝난 세션을 다시 끊어도 404다(목록에서 사라졌으므로 204 멱등을 주지 않는다).
- D3. 대상 세션 ID의 꼴이 UUID가 아니면 토큰을 보기 전에 404다.

**E. 저장·계약·화면**

- E1. identity 마이그레이션 `0040`(동결 로컬): `admin_session.device_label text`(1~40자 CHECK), `admin_account.totp_pending_session_id uuid`, `admin_account.totp_pending_failures integer NOT NULL DEFAULT 0`. `docs/data.md`에 적는다.
- E2. openapi: 경로 여섯, 스키마 `PartnerSecuritySettings`·`PartnerDeviceSessionList`·`PartnerDeviceSession`·`PartnerTotpEnrollment`·`PartnerTotpConfirmation`·`PartnerRecoveryCodes`, 오류 이름 `totp-not-registered`·`totp-enrollment-invalid`. `packages/contracts`·`packages/api-client` 생성물을 `gen`으로 만든다.
- E3. 파트너 화면: `AccountPage`가 `?state=`가 없으면 `AccountSecurityLive`를 그리고, 미리보기는 지금 목업을 그대로 그린다. 새 부품은 인증 앱 줄·복구 코드 줄·로그인 기기 줄만 실제 API로 잇는다. 재인증은 `ACCOUNT_SECURITY`이고 `passkeyCount > 0`일 때만 `withPasskey: true`다. 복구 코드 10개는 한 번만 보이고 "저장했습니다" 확인 전에는 닫지 않는다. 비밀번호·패스키·프로필 줄은 고치지 않는다.

#### 1.3 하지 않는 것과 경계

- **F-09-6(관리 계정 초대 수락·세션·DAST)**: 초대 수락 14경로, `confirmInvitationTotp`, 초대 단계 토큰, `ops-svc` 관리 계정 REST, DAST는 건드리지 않는다. 이 기능은 **활성 계정의 자기 보안 설정**만 다룬다. F-09-6의 구현 리뷰가 이 기능이 쓰는 유스케이스를 바꾸면 다시 쌓는다.
- **F-07-7(정산 지급 ②·SCR-020 정산 계좌·SCR-027)**: `PayoutPage`·`PayoutLive`·정산 API·`requestReauth('PAYOUT_ACCOUNT'|'BOOKER_EXPORT')`의 기존 동작을 바꾸지 않는다. `reauth.ts`에 `ACCOUNT_SECURITY` 길을 더하되 기존 두 작업 묶음의 `withPasskey: true` 동작은 그대로 둔다.
- **F-07-11(신고·통보·중복 글 차단)**: 동결 기능이고 identity 관리 계정 경로를 쓰지 않는다. 건드리지 않는다.
- **F-07-9(파트너 전 화면·판매자 정보·팀 계정)**: `SellerPage`·`TeamPage`·판매자 정보·팀 계정 API를 건드리지 않는다. '내 계정'의 프로필·소속 표시도 그대로 둔다.
- **F-07-15(청구·회수·SCR-047)**: 범위 밖이다.
- **관제 콘솔 SCR-028의 같은 줄**: 이 기능은 파트너 경로만 만든다. 관제 콘솔의 내 계정 보안 줄은 다른 기능 몫으로 남긴다.
- **비밀번호 바꾸기·패스키 등록/지우기 줄**: 기존 화면·API 그대로다. 이 기능은 그 줄을 실제 판으로 바꾸지 않는다.
- **실제 TOTP 앱·브라우저 패스키 창·Redis·PostgreSQL·kind·DAST·AWS**: **미실행**이다. 시험은 메모리 저장소·소프트웨어 인증기·정적 검사로 돈다.
- **부하·성능 수치**: 이 기능은 핫패스가 아니다. 처리량·지연 수치를 주장하지 않는다.

#### 1.4 크기(어림, 모두 [가정])

서버 경로·저장·계약 0.35일, 화면 0.2일, 시험·리뷰 0.15일, 게이트·기록 0.05일 = **0.75일**. 기능 표의 0.75일 안이다.

### 2. 장부 범위

```text
I-T53, auth:v5.0.0-6.3.3, auth:v5.0.0-6.4.4, auth:v5.0.0-7.4.3, auth:v5.0.0-7.5.1, auth:v5.0.0-7.5.2, auth:v5.0.0-8.2.2
```

- **좁힌 까닭**: `docs/BUILD_ORDER.md:121`의 지금 범위 `I-T53, docs/security/asvs/auth.md`는 140항목(자동 74·ID만 26·빈칸 29·해당 없음 7·다른 단계 4)이다. auth.md 전체에는 이 기능과 닿지 않는 다른 서비스·화면의 행이 들어 있다. §8.6 3의 "기능을 시작할 때 범위를 좁힌다"에 따라 이 기능이 실제로 건드리는 행만 남긴다.
- **계획 시점 장부**: 좁힌 범위에서 `node tools/ci/ledger.mjs --batch F-07-13`는 **11항목 모두 자동 시험**(A 0·B 11·C 0, ID만 0·빈칸 0·미검증 0·다른 단계 0)이다. `--require`는 지금도 통과한다. 이 기능의 새 시험은 그 11항목의 상태를 바꾸지 않고 근거를 더한다.
- **완료 판정**: ① 11항목이 계속 자동 시험 ② 이 계획의 `## 시험` 표가 모두 통과 ③ 게이트 통과 ④ 실제 TOTP·브라우저·PostgreSQL·kind·AWS가 `미실행`으로 기록됨. `--require`만으로 F-07-13을 끝으로 적지 않는다.

### 4. 공개 인터페이스(시험 담당이 이 모양으로 시험을 먼저 쓴다)

**HTTP(새 경로 여섯, 파트너만)**

- `GET /v1/partner/auth/security-settings` → 200 `{ totpRegistered: boolean, recoveryCodesRemaining: integer, passkeyCount: integer, sessionLimit: 2 }`, `Cache-Control: no-store`. 401(세션 없음·끝남), 403 `password-change-required`, 503 `admin-login-unavailable`.
- `POST /v1/partner/auth/totp-enrollments` `X-Reauth-Token` → 201 `{ otpauthUri }`, `Cache-Control: no-store`. 400 `invalid-body`(본문·모르는 칸), 401, 403 `reauth-required`·`password-change-required`, 503.
- `POST /v1/partner/auth/totp-confirmations` `{ code }` → 200 `{ recoveryCodes: string[] }`(10개), `no-store`. 400, 401, 410 `totp-enrollment-invalid`(대기 없음·다른 세션·5번 실패 뒤), 422 `reauth-code-invalid`(`remainingAttempts`), 503.
- `POST /v1/partner/auth/recovery-codes` `X-Reauth-Token` → 200 `{ recoveryCodes: string[] }`(10개), `no-store`. 401, 403 `reauth-required`·`password-change-required`, 409 `totp-not-registered`, 503.
- `GET /v1/partner/auth/sessions` → 200 `{ items: PartnerDeviceSession[] }`, `no-store`. 401(부른 세션 끝남), 403 `password-change-required`, 503.
- `DELETE /v1/partner/auth/sessions/{sessionId}` `X-Reauth-Token` → 204, `no-store`. 400(모양 오류), 401, 403 `reauth-required`·`password-change-required`, 404 `session-not-found`, 503.

`PartnerDeviceSession = { sessionId: uuid, deviceName: string|null(≤40), lastActiveAt: date-time, current: boolean, otherSessions: integer }`

**저장(동결 로컬 마이그레이션 0040)**

- `admin_session.device_label text`: 로그인 때 User-Agent에서 뽑은 화면용 이름. 1~40자 CHECK. 끝난 세션은 같은 트랜잭션에서 비운다.
- `admin_account.totp_pending_session_id uuid`: 대기 시드를 시작한 관리 세션. 확인은 이 세션에서만 된다. 완료·재시작·5번 실패 때 비운다.
- `admin_account.totp_pending_failures integer NOT NULL DEFAULT 0`: 재등록 확인 코드 실패 수. 5 [가정]이면 대기 시드를 버린다. 로그인 2단계 실패 수와 별개다.

**응용 층(시험이 의존하는 이름)**

- `ManageAccountSecurity.settings({ accountId })` → `PartnerSecuritySettings`.
- `ManageAccountSecurity.beginTotp({ aud, accountId, sessionId, reauthToken })` → `{ otpauthUri }` 또는 `{ kind: 'REAUTH_REQUIRED' }`.
- `ManageAccountSecurity.confirmTotp({ accountId, sessionId, code })` → `{ recoveryCodes }` 또는 `{ kind: 'ENROLLMENT_INVALID' | 'CODE_INVALID', remainingAttempts? }`.
- `ManageAccountSecurity.recreateRecoveryCodes({ aud, accountId, sessionId, reauthToken })` → `{ recoveryCodes }` 또는 `{ kind: 'REAUTH_REQUIRED' | 'TOTP_NOT_REGISTERED' }`.
- `ManageAccountSecurity.listSessions({ accountId, sessionId })` → `PartnerDeviceSession[]` 또는 `{ kind: 'SESSION_ENDED' }`.
- `ManageAccountSecurity.endSession({ aud, accountId, sessionId, reauthToken, targetSessionId })` → `{ kind: 'OK' | 'REAUTH_REQUIRED' | 'SESSION_NOT_FOUND' }`.

**화면 모델(파트너, `node --test`)**

- `accountSecurityView(raw)` → `{ totpText, recoveryText, passkeyCount, sessionLimit }`.
- `deviceSessionsView(items, now)` → `{ sessionId, label, lastActiveText, current, otherSessions }[]`(지금 기기 먼저, KST).
- `accountSecurityProblemMessage(problem)` → 화면에 보일 글.
- `requestAccountSecurityReauth({ password, code, withPasskey })` → 재인증 토큰.
- `partner-live.ts`의 `getPartnerAuthSecuritySettings`·`getPartnerAuthSessions`·`beginPartnerTotpEnrollment`·`confirmPartnerTotpEnrollment`·`recreatePartnerRecoveryCodes`·`deletePartnerAuthSession`.
