# BAT-174 계획·기록(CI 흔들림 고침: Lighthouse 가운데 값·S-T34 ④)

- **범위 둘**(감독 결정 2026-11-19, 같은 날 감독 보탬으로 넓힘): (가) `web / budgets`의 Lighthouse 판정을 다섯 번 가운데 값으로(NFR-012, 아래 '계획' 1~10). (나) core-svc 통합 시험 `S-T34 ④` 시간 상한 시험의 흔들림 원인 찾기와 고침(아래 '계획' 11). 두 쪽 모두 **한도·상한을 넓히지 않는다**. 넓혀야 할 것 같으면 '정할 것'에 적고 감독이 묻는다.
- **무엇(가)**: CI `web / budgets`의 Lighthouse 판정이 흔들려 develop이 반쯤 빨갛다. 월렛 LCP 한도 7,255ms(기준선 5,804ms × 1.25)를 0.5~11% 넘는 실패가 2026-11-18 CI 22잡 중 11번 나왔고, 웹 코드가 같은 머리에서도 통과와 실패가 갈렸다(감독 조사 2026-11-19, 같은 머리를 다시 돌리면 통과한 사례 셋). 이 묶음은 **한도를 그대로 두고** 주소마다 재는 횟수를 세 번에서 다섯 번으로 늘려 가운데 값(작은 차례로 늘어놓은 셋째 값)으로 판정한다. 기준선 다시 잡기(한도 넓히기)는 하지 않는다(감독 결정 2026-11-19).
- **쉬운 말**: '가운데 값'은 여러 번 잰 값을 작은 것부터 늘어놓았을 때 한가운데 값이다. 세 번 재면 두 번만 튀어도 가운데 값이 튀지만, 다섯 번 재면 세 번은 튀어야 튄다. 한 잡 안에서도 실행마다 ±30%쯤 흔들려(R-563 로컬 컨테이너 세 번 값 4,508 / 6,236 / 7,893ms) 횟수를 늘리는 것이 흔들림을 직접 줄인다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane2-b174`, 가지 `feature/lane2-BAT-174`, 기준 커밋 `17c55c32`. 지시서는 감독 지시다. `node tools/ci/brief.mjs --batch BAT-174`는 이 묶음의 단계 칸이 `-`(WBS 단계 없음)라 '단계 줄이 없다'로 멈춘다. 이 계획이 지시서를 대신한다.
- **등급**: C(docs/BUILD_ORDER.md '기능 묶음' 표 BAT-174 행). (가)는 검사 도구의 측정 횟수만 바꾸고, (나)는 좌석맵 가져오기 해석 작업(`seatmap-worker`)의 시험과, 원인에 따라 그 시간 재기 방식만 바꾼다. 돈·좌석 홀드·대기 순번 로직에 닿지 않는다. 다만 (나)는 격리(ASVS 15.2.5)의 시험이라 틀린 구현 표본에 상한 검사를 끄는 꼴을 넣는다(아래 11). 장부 범위는 `-`다.
- **차례**: 정방향(`Batch-Order: impl-first`, ADR-0281 결정 5). 결함 재현이 아니라 측정 방법 고침이라 구현이 먼저다. 계획 → 구현 → 시험(실패 확인·시험 결과) → 리뷰 → 검증 → 기록(감독).
- 이 파일은 역할마다 자기 절만 쓴다: 계획(아래), 실패 확인·시험 결과(시험), 시험 이의(구현), 리뷰, 검증, 담당 표·기록(감독). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.

### 1. 범위((가) Lighthouse)

- **월렛 `sw.ts` 빌드 오류 줄은 이 묶음 몫이 아니다**: `web / budgets` 로그의 `Could not resolve .../standalone/apps/web/app/sw.ts`(27줄)는 BAT-171 커밋('월렛 워커를 빌드 때 .next/serwist/sw.js로 만들고 경로 처리기는 읽기만', 가지 `feature/lane2-BAT-171`)이 고친 결함이다. BAT-171이 합쳐지면 사라진다. 검증 담당(또는 기록 때 감독)이 BAT-171을 합친 뒤 develop CI의 `web / budgets` 로그에서 그 줄이 0인지 본다.
- **한다**: `tools/web-checks/budgets/limits.mjs`의 `RUNS`를 3에서 5로. `median`은 지금도 홀수 길이에서 정렬한 가운데 값을 돌려주므로 바꾸지 않는다(바꿀 까닭이 생기면 '시험 이의'에 적는다). 주석의 '세 번'을 '다섯 번'으로 맞춘다.
- **판정 대상**: LCP·CLS·총 차단 시간(TBT) 셋 모두 같은 `median(runs…)`을 쓰므로 셋 다 다섯 번 가운데 값이 된다(`lighthouse.spec.mjs` 68줄).
- **그대로 둔다**: 한도 계산(`loadLimit`, `LOAD_MARGIN` 시간 25%·CLS 0.02), 기준선 파일 `lighthouse-baseline.json`(세 번 가운데 값으로 잰 값이지만 다시 잡지 않는다), 주소 목록(`pages.mjs`), 시험 하나의 시간 한도(`playwright.budgets.config.mjs` 180초), 잡 시간 한도(`ci-web.yml` budgets 50분).

### 12. (다) 시작 파일 조립 시험의 'core-svc 준비' 시간 초과(감독 보탬 2026-11-19)

**본 실패**(계획 담당이 CI 로그로 확인): 실행 44401816769 첫 시도의 `node / node` 잡(2026-11-18T21:36Z). `test-int/seatmap-save.int.test.ts`의 '시작 파일(main.ts) 조립 > PEAKET_PUBLIC_FILE_DIR이 없으면 뜨지 않고, 있으면 운영 시작 파일로 띄운 앱이 그 폴더에 쓴다'가 31,582ms 만에 `기다리다 시간이 지났다: core-svc 준비`(`test-int/media-support.ts:113`의 `until`, 부른 곳 1434줄)로 실패했다. 앞의 '빠진 환경 값이면 뜨지 않는다' 몫은 약 1.5초에 끝났고, 나머지 30초를 관리 포트 `/ready` 200을 기다리다 다 썼다. 아이 프로세스(`dist/main.js`)의 출력은 실패 메시지에 없다. 다시 돌리면 통과한다. **기다림 30초(1434줄 `30_000`)와 `until` 기본 5초(`media-support.ts` 110줄)는 넓히지 않는다.**

**정본의 시작·준비 조건 자리**: 준비 프로브는 메모리의 준비 표시만 읽고 의존성을 부르지 않는다(`packages/platform/src/readiness.ts` 머리, `service.ts` 203줄, D-T19·D-T29, ADR-0070·0103, docs/architecture.md §5 '프로브 규칙'). 검색 사전의 시작 따라잡기와 첫 읽기는 준비 확인에 넣지 않는다(ADR-0271 결정 14, `services/core-svc/src/main.ts` 153줄 주석). core-svc는 준비 표시에 시작 작업을 하나도 등록하지 않는다(`readiness.register`·`startControlSync` 부름 없음). 그래서 `/ready`는 관리 포트가 열리는 순간 200이고, 기다림은 **프로세스가 관리 포트를 열기까지**다.

**그때까지 기다리는 것**(`main.ts` 차례): `dist` 모듈 싣기 → DB 연결 다섯 묶음과 역할 확인 다섯 번(`assertDatabaseRole`, 113~117줄) → Nest 앱 만들기(`createService`, 120줄) → `service.listen()`(152줄). 대기열 Redis·Kafka는 이 시험 환경 값에 없어 건너뛴다. 검색 따라잡기(154줄)는 `listen` 뒤라 들지 않는다. 마이그레이션은 시험 앞(`beforeAll`)에서 하고 시작 파일은 하지 않는다. 작업자 스레드(좌석맵 해석)는 core-svc가 아니라 `seatmap-worker` 프로세스 몫이라 이 시작에 들지 않는다(시험은 그 주소를 `127.0.0.1:1`로 준다).

**의심 원인(코드 읽기, 큰 것부터)**:
1. **같은 `dist/`를 여러 시험 파일이 동시에 다시 빌드한다.** `buildDist()`(`media-support.ts` 18~26줄)는 모듈 안 `built` 깃발로 한 번만 돌지만, vitest는 시험 파일마다 모듈을 따로 실으므로 `dist/main.js`를 띄우는 파일 넷(`seatmap-save`·`seatmap-editor`·`sale-eligibility`·`search-bat166`, 그리고 `media-support.ts` 54줄을 부르는 곳)이 저마다 `tsc -p tsconfig.build.json`을 돌린다. 한 파일의 아이 프로세스가 `dist`를 싣는 동안 다른 파일의 `tsc`가 같은 파일을 다시 쓰면, 반쯤 쓰인 파일을 읽어 아이가 오류로 끝날 수 있다. 같은 잡에서 다른 파일의 '시작 파일(main.ts)' 시험이 21:35:57·21:36:14에 돌았다(나란히 돌았다는 정황).
2. **아이가 죽어도 시험이 모른다.** `until`은 `/ready`만 보고 `ok.exited`를 보지 않아, 아이가 1초 만에 죽어도 30초를 다 기다린 뒤 원인 없는 시간 초과로 끝난다. 그래서 원인 1·3을 로그로 가릴 수 없었다.
3. **포트 경합.** `freePort()`(`media-support.ts` 28~36줄)는 포트를 잡았다 놓고 번호만 돌려준다. 놓은 뒤 아이가 그 번호를 열기 전에, 나란히 도는 다른 파일이 같은 번호를 잡으면 아이는 `EADDRINUSE`로 끝난다(원인 2와 겹쳐 시간 초과로 보인다).
4. 바쁜 러너에서 DB 연결·역할 확인·Nest 만들기가 느린 것만으로 30초를 넘길 가능성은 낮다(앞 몫 '뜨지 않는다'가 1.5초, 같은 잡의 다른 시작 파일 시험은 통과).

**고칠 길(기다림을 넓히지 않는 것만, 차례대로)**:
- (ㄱ) **원인 보이기(시험 담당, 먼저)**: 기다리는 동안 아이가 끝나면 바로 실패하고, 실패 메시지에 끝 코드와 아이 출력 끝부분(예: 마지막 4KB)을 싣는다. `boot()`이 돌려주는 `exited`·`output()`을 쓰면 되고, 같은 꼴의 다른 파일 셋에도 맞춘다. 이것만으로 다음 흔들림 때 원인 1·3 중 무엇인지 보인다.
- (ㄴ) **빌드는 한 번만(시험 담당)**: 통합 시험 실행 전체에서 `dist`를 한 번만 빌드한다. 예: `vitest.integration.config.mjs`의 `globalSetup`이 `tsc -p tsconfig.build.json`을 한 번 돌리고 파일들의 `buildDist()`는 빌드가 있는지만 본다. 또는 CI가 통합 시험 앞 단계에서 빌드한다. 어느 쪽이든 '시험 도중 `dist`를 다시 쓰지 않는다'가 지킬 것이다.
- (ㄷ) **포트를 아이가 고르게(구현, (ㄱ)이 원인 3을 보일 때만)**: 아이가 `PORT=0`·`PEAKET_MANAGEMENT_PORT=0`으로 뜨고 실제 번호를 시작 로그 한 줄에 적으면 시험은 고정 대기 대신 그 신호(로그 줄)를 기다린 뒤 `/ready`를 본다. `@peaket/platform`의 `listen`이 0을 받는지와 로그 꼴은 구현이 본다 [확인 필요]. 운영 시작 동작은 바뀌지 않는다.
- 준비 신호 자체(`/ready`)는 정본대로 맞다(core-svc에 준비 전 시작 작업이 없다). 바꾸지 않는다.
- (ㄱ)·(ㄴ)을 짧게(시험 담당 한 번의 시도 안에) 못 끝내면 고치지 않고 `docs/lanes/lane2-cleanup.md` 정리 목록으로 넘긴다(본 로그·원인 후보·고칠 길을 적는다). (ㄷ)은 (ㄱ)의 결과로 원인 3이 보일 때만 하고, 아니면 정리 목록에 둔다.

- **잘린 스레드를 기다리는 동안 다른 가져오기**: 파드마다 동시 해석 1(docs/verification.md 476줄)이라 다음 차례는 원래 앞 해석이 끝날 때까지 기다린다. `terminate()`가 끝나는 동안(보통 수 ms) 더 기다릴 뿐이고, 기다리는 요청은 차례가 오면 `alive()`로 데드라인을 다시 보므로(`pool.ts` 67~69줄) 막힘이 쌓이지 않는다. 잘린 스레드와 새 스레드가 함께 돌지 않게 된 것은 힙 상한 1개분(ADR-0257 47줄, 컨테이너 512MiB 안 384MiB)의 뜻에 맞다. 스레드가 끝나지 않는 경우는 R174-2.
- **Lighthouse 다섯 번의 시간**: 시험 하나(`lighthouse.spec.mjs` 57~68줄)가 한 주소의 다섯 번을 다 돈다. 가장 긴 홈이 세 번에 29.8초(계획 7)라 다섯 번이면 약 50초로 한도 180초의 약 3.6분의 1이고, 한 번이 세 배로 늘어도 한도 안이다. 잡은 약 11분 어림으로 50분 한도 안이다. 재시도 설정이 없어 한 번의 `runtimeError`가 시험을 떨어뜨리는 것은 세 번일 때와 같다(횟수만큼 확률이 조금 는다). 검증 담당이 초안 PR CI에서 주소별 시험 시간을 함께 적으면 된다.
