# 기능 계획: F-08-6(Game Day 전체 재실행·포스트모템·SLO/KPI ADR)

- **진행**: 계획·시험(측정 준비) 끝, 리뷰 대기(2026-11-27). Game Day 33종·K8·포스트모템·SLO/KPI ADR은 모두 **`미측정`**이다. 이번 세션은 Docker·kind·k6·브라우저를 쓰지 않았다.
- **무엇**: BUILD_ORDER '기능 단위 계획' F-08-6(갈래 4, 등급 B, MSR-060·MSR-070, WBS 4.00일, 단계 줄 `MSR-060 wbs 6.3.1 ①`·`MSR-070 wbs 6.3.1 ②`, 측정 창 4)의 작업 목록이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **쉬운 말**: Game Day는 일부러 장애를 내고 경보·운영 명령·불변식이 제때 도는지 확인하는 날이다. 이 기능은 33개 시나리오를 로컬에서 다시 돌리고, 주입·탐지·전파 증거를 남기고, 선언한 인시던트의 포스트모템과 SLO·세션 시간·비즈니스 KPI 최종 목표 ADR 초안을 만든다. 이번 세션은 **재는 도구와 판정 규칙**만 준비하고 숫자를 만들지 않는다.
- **바탕**: 작업 폴더 `D:/ticketpass-freeze-F-08-6`, 가지 `freeze/lane4-F-08-6`, 출발 `origin/freeze/lane4-F-08-5` = `b6affdf13`(F-08-5 구현·queue 4a 무효 기록 포함). 동결 트랙이라 `develop`·`release/1.0.0`·`main`에 합치지 않는다(ADR-0386 결정 4).
- **차례**: B등급이지만 이번 동결 트랙 지시로 **계획 → 시험(측정 준비) → 리뷰(새 세션) → 반영 → 구현/측정/문서 → 기록**으로 돈다. 이번 세션은 계획·시험·기준 실패 확인까지만 하고 리뷰 준비에서 멈춘다.
- **한 줄 결론**: 33종은 로컬 실행 21·대체 장애 8·모의 진행 4다. demo 스택도 `bundle` 한 파드가 queue·admission·purchase·payment를 덮고 Valkey가 단일이며 ops-rt·ClickHouse·Schema Registry·브라우저가 없어, G-02·G-07·G-09·G-14·G-25·G-29·G-30은 이 계획 무대에서 **`판정 못 함`**이다. 무대가 있는 시나리오도 기대 대응 증거·발생기·시간선이 없으면 `통과`가 아니다. F-08-5 queue 4a의 `무효`, F-08-9의 `판정 못 함(무효·부분)`은 인용만 하고 Game Day 통과로 쓰지 않는다. 30,000건/초·100만·K1/K2/K7 0의 새 수치를 주장하지 않는다.

## 2. 감독에게(정할 것과 이 계획의 답)

1. **창을 4d~4g로 나눈다.** 4d=G-01~G-10, 4e=G-11~G-20, 4f=G-21~G-30, 4g=G-31~G-33+문서다. 창마다 6~9시간, 합계 약 31시간 + 여유로 WBS 4.00일과 크게 어긋나지 않는다.
2. **무대는 demo 스택이지만 부품이 모자란다.** demo 스택은 `bundle` 한 파드가 queue·admission·purchase·payment를 덮고, Valkey는 복제본이 없으며, ops-rt·ClickHouse·Schema Registry가 없고, 브라우저를 쓰지 않는다. 그래서 G-02(좌석 Redis 승격)·G-07(ClickHouse 밀림)·G-09(admission-ctrl 리더 교체)·G-14(purchase 전면 종료)·G-25(Playwright SDK 차단)·G-29(세션 Redis 승격)·G-30(Schema Registry 정지)은 **`판정 못 함`**이다. 무대를 갖추는 일은 이 기능이 하지 않는다.
3. **로컬에 없는 부품은 새로 만들지 않는다.** Argo Rollouts·Argo CD(동결 달력)·KEDA·외부 데드맨·실제 MSK/AWS는 동결 기능이나 소유자 자원이다. G-18·G-19·G-20·G-22·G-26·G-32·G-33은 **`판정 못 함`** 또는 **`설계만`**으로 남기고, 할 수 있는 부분(파드 종료·Kyverno·503 덜어 내기·로컬 Kafka 정지)만 잰다.
4. **K8은 G-01~G-10만.** 탐지는 주입→경보, 전파는 승인→ack다. `slo-fast`는 긁기 5초, 그 밖은 15초, G-08~G-10은 `for` 30초까지다(약 55초). 축 하나라도 줄이면 `무효`다. 소진 배수 27 미만은 60초 탐지를 주장하지 않는다(`판정 못 함`). 로컬 Alertmanager가 없으면 `판정 못 함`이고, 측정 준비에서 더한다(제품 코드 아님).
5. **F-08-5·F-08-9 값을 인용만 한다.** queue 4a는 `dropped_iterations` 2,014로 `무효`, purchase 이하·V-T10은 `미측정`; F-08-9는 릴레이 OOM·브로커 CrashLoop·토픽 소실로 `판정 못 함(무효·부분)`이다. K1/K2/K7·SLO 통과로 바꾸지 않는다.
6. **포스트모템은 선언한 인시던트만.** 끝난 뒤 48시간 안에 쓰고, 28일 예산 20% 초과 사고는 P0를 하나 이상 둔다. 주 원인 유형 하나·구성 요소 하나이고, 후속 조치마다 GitHub Issues 링크가 있어야 한다. 보고서 §3에 인시던트와 포스트모템 경로·48시간·P0를 대조한다.
7. **SLO/KPI ADR은 초안만.** NFR-001~012·세션 시간·비즈니스 KPI 7개를 덮고, 측정 전에는 모두 `보류`·`미측정`이다. 목표 변경은 실행 ID나 문서 인용과 '되돌릴 조건'이 있어야 하고, 최종 ADR 번호는 측정 뒤 감독이 준다.
8. **장부 범위를 `-`로 좁힌다.** `docs/observability.md`는 시험 표가 아니라 장부 항목이 0개이고 도구가 '범위가 너무 큼' 경고를 낸다. BUILD_ORDER F-08-6 행을 `-`로 고치고 판정 정본 표시는 남긴다.
9. **Docker는 `docker` 한 자리만.** `lock.sh take docker lane4-F-08-6`→`drop docker lane4-F-08-6`. `docker-all` 금지, 창은 감독이 연다, 브라우저는 쓰지 않는다.
10. **수치 주장 금지.** 30,000건/초·100만·K1/K2/K7 0을 결과로 쓰지 않는다. 필요한 값은 `문서 인용` 또는 `미측정`으로만 적는다.

### 6.3 기록과 증거

- 실행 폴더 `.cache/peaket-f086/<날짜>-<시나리오>-r<회>/`에 `timeline.csv`(T0 주입 계획·T1 주입·T1p Prometheus firing·T2 첫 경보·T3 명령·T4 복구), `alerts.ndjson`(Prometheus `ALERTS`·Alertmanager), `commands.ndjson`, `faults.ndjson`(종류·계획 시각·길이·적용·증거), `invariants.csv`, `host.json`, `run.json`, `generator.json`, `manifest.json`을 남긴다.
- 실행이 끝나면 `docs/perf-ledger/runs/<실행 ID>/`로 `timeline.csv`·`manifest.json`·요약을 옮긴다. 보고서의 `실측(PC)` 줄은 그 폴더가 있어야 한다.
- **주입은 적용 증거가 있어야 한다.** `applied: true`는 실제 신호·PID·컨테이너·정책·응답으로 확인한 것만이다. F-08-9처럼 PID를 잘못 잡고 `applied: true`를 남기면 `무효`다. Kafka 정지는 PID를 확인해 컨테이너에 직접 신호하고 **토픽을 지우지 않는다**.
- **발생기**: 부하가 있는 시나리오는 k6 `constant-arrival-rate`. `dropped_iterations` 1건, 발생기 CPU 80% 초과·메모리 90% 초과, `http_reqs` 0이면 `무효`. 호스트 CPU 85% 이상, `procs_running` > 논리 프로세서도 `무효`.
- **불변식**: 시나리오마다 `invariants.csv`. 오버셀·이중 결제·차례 전 입장이 1건이라도 있으면 `미달`이고 같은 창의 나머지를 멈춘다.
- **롤백**: 되돌린 증거를 `run.json`에 남긴다. 못 되돌리면 다음을 시작하지 않고 창을 닫는다.

### 6.4 K8 판정

- **대상**: G-01~G-10만.
- **탐지**: 주입→첫 경보. `detectionPath='경보'`만 센다. 사람·외부가 먼저 알면 K8 `미달`(감시 실패로 따로 적는다).
- **전파**: 명령 승인→대상 파드 ack. 명령이 없는 시나리오는 `null`이고 전파를 보지 않는다.
- **간격**: `slo-fast` 대상(G-01~G-07)은 긁기 5초·평가 5초·묶음 대기 5초, G-08~G-10은 긁기 15초·평가 5초·묶음 대기 5초·`for` 30초다(약 55초). 축 하나라도 줄이면 `무효`. 로컬 Alertmanager가 없거나 알림을 못 받으면 `판정 못 함`.
- **소진 배수**: 60초 안 탐지는 소진 약 27배 이상에서만 성립한다. 27은 통과, 26.9는 그 세기로 60초 탐지를 주장하지 않는다(`판정 못 함`). 주입 세기를 함께 적는다.
- **경계**: 60.000초 통과·60.001초 미달, 3.000초 통과·3.001초 미달. 밀리초 ISO 8601로 남긴다.
- **종합**: `judgeK8Results`가 10종 결과를 모은다. 하나라도 `무효`면 `판정 못 함`, 하나라도 `미달`이면 `미달`, 10종 모두 `통과`면 `통과`. 10종이 다 없어도 `판정 못 함`.

### 6.5 시나리오 판정과 중단 규칙

- **판정값**: `통과`·`미달`·`판정 못 함`·`무효`·`미측정`. `통과`는 무대 준비·기대 대응 확인(경보·대응·불변식 증거)·발생기·시간선이 모두 있을 때만이다.
- **무대**: `GAMEDAY_SCENARIOS.stageReady`가 `false`인 시나리오는 `판정 못 함`이다. G-02·G-07·G-09·G-14·G-25·G-29·G-30이 그렇다. 실행 방식·증거 수준이 정본과 달라도 `판정 못 함`이다.
- **기대 대응**: `responseChecks`의 `expectedAlert`·`expectedAction`·`invariantHeld`가 모두 있고 증거가 비지 않아야 한다. 없으면 `판정 못 함`, `ok:false`면 `미달`이다.
- **모의·설계만은 `통과`가 아니다.** G-17·G-28·G-32·G-33은 모의 진행, G-26은 대체 장애라도 `설계만`이다. `판정 못 함` 또는 `설계만`으로 적는다.
- **중단 규칙(STOP-01~10)**: ① 무대 미준비 ② 잠금 없음·`docker-all` ③ 호스트 포화 ④ 주입 증거 없음 ⑤ 불변식 위반 ⑥ 롤백 실패 ⑦ 디스크 15GB 미만·메모리 압박 ⑧ 경보·기록 파이프라인 끊김 ⑨ 같은 시나리오 두 번 연속 `무효` ⑩ 감독 중단. 걸리면 창을 멈추고 감독에게 알린다. 수치를 만들지 않는다.
- **부분 실행**: 부품이 없어 못 한 부분은 `판정 못 함`과 까닭을 적는다. 할 수 있는 부분만 `부분`이고 전체를 `통과`로 쓰지 않는다.

### 6.6 포스트모템

- **대상**: POL-022 기준으로 선언한 인시던트. 선언하지 않은 주입은 대상이 아니지만 왜 선언하지 않았는지 한 줄 적는다.
- **기한**: 끝난 뒤 48시간 안에 완료. 넘기면 `미달`.
- **필수 칸**: 첫 증상·첫 경보·사람이 안 시각, 탐지 경로(경보·사람·외부), 주 원인 유형(9가지 중 하나), 구성 요소(하나), 기여 원인 유형, 계기, 영향(28일 예산 비율·영향 회차), 쓴 손잡이, 후속 조치(이슈 링크·P0 여부). 후속 조치마다 `#번호`나 이슈 URL이 있어야 한다.
- **탐지 경로 대조**: `detectionPath='경보'`인데 사람이 첫 경보보다 먼저 알았으면 `미달`이다. 시각과 경로를 함께 본다.

## 9. 실패 시나리오

- 무대·Alertmanager·Toxiproxy가 준비되지 않으면 창을 시작하지 않는다. 시작 뒤 없어졌으면 그 시나리오는 `판정 못 함`이다.
- `faults.ndjson`에 적용 증거가 없거나 PID가 틀리면 `무효`다. F-08-9처럼 `applied: true`를 증거 없이 남기지 않는다. Kafka 정지에서 토픽을 지우거나 브로커를 CrashLoop로 만들면 그 창은 `무효`다.
- `dropped_iterations` 1건, 발생기 CPU 80% 초과·메모리 90% 초과, `http_reqs` 0이면 그 실행은 `무효`다. 세기를 낮춰 다시 돌리지 않고 `무효`로 적는다. 호스트 포화(CPU 85% 이상, `procs_running` > 논리 프로세서)면 그 표본이 든 실행도 `무효`다.
- 무대가 없는 시나리오(G-02·G-07·G-09·G-14·G-25·G-29·G-30)는 `판정 못 함`이다. 실행 방식·증거 수준이 정본과 달라도 `판정 못 함`이다.
- 기대 대응 증거(`responseChecks`)가 없거나 비면 `판정 못 함`, `ok:false`면 `미달`이다. `timeline.csv`의 T0·T1·T1p·T2·T3·T4가 없어도 `판정 못 함`이다.
- 경보가 울리지 않았거나 사람이 먼저 알았으면 K8은 `미달`이다. 사람이 먼저인데 `detectionPath='경보'`로 적어도 `미달`이다. 간격 축소·소진 배수 27 미만은 K8 `무효`·`판정 못 함`이다.
- 불변식 위반(오버셀·이중 결제·차례 전 입장) 1건이면 그 시나리오는 `미달`이고 창을 멈춘다. 숨기려고 다시 재지 않는다. 끝까지 못 돌았거나 롤백하지 못했으면 `무효`다.
- 선언한 인시던트에 포스트모템이 없거나 48시간을 넘겼으면 `미달`이다. 20% 초과에 P0가 없거나 후속 조치에 이슈 링크가 없어도 실패다.
- 측정 전 ADR 초안에 목표·통과·숫자를 적으면 계획 위반이다. 30,000건/초·100만·K1/K2/K7 0을 주장하면 보고서 검증이 실패한다.
- 잠금을 못 잡으면 기다린다. 남의 잠금을 지우거나 `docker-all`을 쓰지 않는다. 시간이 모자라면 수치를 만들지 않고 범위를 줄인다. 줄인 시나리오는 `미측정` 또는 `판정 못 함`이다.
