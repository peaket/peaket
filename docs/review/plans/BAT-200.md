### 3.1 차례

1. **정본 빈칸 먼저**(4장 전부, 한 커밋 안에서 코드보다 앞): 정본 고침, ADR 하나(가칭 '추가 검증 제출·이의 접수 첫 구현', 다음 빈 번호는 커밋 직전 다른 갈래를 보고 정한다), §8.7 실패 목록 셋의 줄, ledger-notes 줄(1.4), BUILD_ORDER '장부 범위' 칸. 나안이면 BUILD_ORDER에 BAS-011 줄과 BAT-202 행을 더한다. openapi·proto를 고치면 `packages/contracts`와 `packages/api-client` 생성물을 둘 다 다시 만든다(이 PC는 pnpm이 막혀 생성기를 `node`·`npx`로 부른다).
2. **불변식 시험 먼저 쓰고 실패를 본다**(A등급, Q-T34): 차례 전 입장 0, `PASSED`일 때만 빠진 번호 통과, 15분 유예의 두 기준, 1인 1순번 위반 때 `PASSED` 칸 지우기, 기각·취소 뒤 거절. Valkey Lua 시험과 메모리 저장소 시험을 같은 사례 파일로 둔다(지금 `leave-cases.ts`·`admission-cases.ts` 모양).
3. **queue-svc 입장 확정**: 회차 슬롯 확인 Lua(`PRECHECK_LUA`)에 `PASSED` 예외와 '차례와 통과 가운데 늦은 때' 유예, 1인 1순번 위반 길에 `verify` 칸 지우기.
4. **identity-svc**: `ReverificationCheckService.CheckReverification` 서버(I-T56 ①~④). 기존 `Reverifications` 포트는 세션 단위라 계정·사람 대조(`ci_hmac`)와 `not_before_ms`로 묻는 읽기를 더한다.
5. **queue-svc 추가 검증 제출**: 사용 사례(제출)와 처리기, identity 클라이언트(`CheckReverification`), trust 클라이언트의 `VERIFICATION` 맥락, `verify` 칸을 `PASSED`로 바꾸는 Lua, 통과 응답의 유예 마감.
6. **queue-svc 이의 접수**: `q:appeal`·`q:appealid` 쓰기(처음 것만), Kafka 생산자(거래·제어 클러스터 `support.cases-requested`), 발행 실패 503과 다시 보내기.
7. **queue-svc gRPC 서버**: `VerificationAppealService`(`Get`·`Resolve`). queue-svc의 첫 업무 gRPC 포트다. 시작 파일 `main.ts`의 조립(포트, 생산자, 클라이언트)을 따로 띄워 보는 시험을 둔다.

9. **admission-ctrl**: 셔플 뒤 정규화가 `PASSED` 참가자를 빠진 번호로 돌리지 않는지 시험(Q-T34 ①). 코드가 이미 `VERIFYING`만 돌리면 이름 고치기와 사례 더하기다.
10. **화면 SCR-009**: 퍼블리싱 자리(`?state=` 미리보기)와 데이터에 잇는 화면을 나눈다(결제 화면 `CheckoutPreview`·`CheckoutLive`가 선례). 사람 확인 `action`에 `verify`를 더하고, 본인확인 재확인 창, 제출·이의 보내기, 새로고침 뒤 되살리기, 통과 뒤 대기실로 돌아가기. 대기실(`apps/web/queue-room`)이 돌아온 뒤 이어 가는지 본다.
11. **BAS-010(나안이면 ①만)**: `packages/config/eslint`에 화면 보안 규칙(HTML 넣기 금지, 창 메시지 금지를 옮김)과 서비스 외부 호출 규칙, 취약점 조치 기한·예외 만료 판정 도구(`tools/ci`), `security-scan.yml`(pnpm 내장 의존성·라이선스 검사와 판정 도구. 허락받은 도구는 가안에서만), `ci.yml` 잇기.
12. 실제 서버 연결(3.4 끝) → 관점 넷 리뷰 → 틀린 구현 검사(5장) → 성능 비교(3.7) → 게이트(3.5) → 브라우저 확인(3.6) → 기록과 커밋.

### 3.3 인터페이스

- **REST**: `POST /v1/queues/{eventId}/verification`(openapi 3670~3681. 정본은 200·202·503만 적었다. 응답 모양·오류·본문 칸은 4장 G4~G8), 추천으로 더할 읽기 `GET /v1/queues/{eventId}/verification`(G7). `POST /v1/queues/{eventId}/admission`의 `PASSED` 통과와 기각 410(G9).
- **gRPC**: queue `VerificationAppealService.GetVerificationAppeal`·`ResolveVerificationAppeal`(서버, 새로), identity `ReverificationCheckService.CheckReverification`(identity 서버·queue 클라이언트, 새로), trust `TrustEvidenceService.GetVerdictEvidence`(서버, 새로), trust `ScoreRisk`(맥락 `SCORE_CONTEXT_VERIFICATION`, queue 클라이언트 넓힘), trust `TrustLabelService.ApplyLabel`(있음. 시험이 ops-svc 자리에서 `LABEL_SOURCE_APPEAL_ACCEPTED`로 부른다).
- **이벤트**: `support.cases-requested`의 `CaseRequested`(kind `VERIFICATION_APPEAL`, 키 `sourceId` = 이의 ID, `eventKey`는 `q:appeal`에 처음 둔 값을 다시 쓴다). queue-svc의 첫 Kafka 생산자이고 Outbox 없이 바로 낸다(asyncapi 208).
- **Lua(대기열 Redis)**: 회차 슬롯 `PRECHECK_LUA` 고침, 새 '추가 검증 통과'(`VERIFYING`일 때만 `PASSED:{시각}:{사유}`), 새 '이의 결과'(인정은 `VERIFYING`일 때만 `PASSED`, 기각은 `VERIFYING`일 때만 `BLOCKED`, 판 번호 비교는 사람 슬롯), 사람 슬롯 '이의 접수'(`HSETNX`, 보낸 표시, 색인). 사람 키와 회차 키는 슬롯이 달라 한 Lua로 묶지 못한다(queue-admission §6 '순서'와 같다). 겹치는 차례와 경합은 4.1의 data.md 줄로 먼저 적는다.
- **키**: `q:{event:E}:verify`(값 형식은 지금 코드의 `VERIFYING:{시각}:{사유}`를 따른다), `q:appeal:{pid}:E`, `q:appealid:{appealId}`, 추천으로 더할 `q:appealcase:{caseId}`(G10)와 제출 횟수 키(G11). 대기표를 찾는 값은 `q:dup:{pid}:E`의 대기표 해시다(대기 취소와 같은 길, ADR-0233).

### 3.6 화면: 첫 JS 예산과 브라우저 확인

- SCR-009(`/queue/[eventId]/verify`)는 docs/frontend.md §5.8 '그 밖 소비자 화면' 행의 예산을 받는다. 운영 빌드(`node seed-css/build.mjs web`, `PEAKET_BUILDS=prod`)를 만들고 `tools/web-checks/budgets/js.spec.mjs`로 로컬에서 잰다(R-439). 사람 확인 위젯·본인확인 흐름은 누를 때 싣는다(결제 화면의 늦게 싣기와 같은 방법). 대기실 경량 페이지를 고치면 size-limit(FE-T1)과 시각 회귀도 돈다.
- 브라우저 확인은 게이트 뒤에 skill `peaket-browser-check`로 한다. 대본은 d5 §5.9의 상태 표(챌린지 실패, 통과 차례 전·지남, 재검토 접수, 인정, 기각)와 B-T10·Q-T34·I-T56의 판정 기준이다. 인정·기각은 시험 도구가 ops-svc 자리에서 `ResolveVerificationAppeal`을 불러 만든다. 결과는 `docs/review/browser-check/` 아래 단계 ID 이름의 파일(BOT-090)이다. 연결된 Chrome이 시험용 프로필인지 확인할 수 없으면 BOT-055처럼 Playwright로 대신하고 그 사실을 적는다.

### 3.7 성능 비교

입장 확정의 회차 슬롯 확인 Lua를 고치므로 §8.6 4의 7 대상이다. `loadtest/micro/lua-compare.mjs`는 지금 좌석 Lua만 견준다. 그래서 queue Lua(`PRECHECK_LUA`와 새 통과 Lua)를 고를 수 있게 넓히고, A/A로 판정선을 정한 뒤 일부러 느리게 한 판을 잡는지 본다(G20). 시험·빌드와 겹치지 않게 맨 뒤에 돌린다.

### 3.8 구현 지시문에 넣을 '자주 놓친 결함'(docs/architecture.md:1129~1140)의 이 묶음 판

- Lua 응답은 정확한 값까지 본다: `PRECHECK_LUA`가 `PASSED`에 돌려주는 차례 시각, 통과 응답의 유예 마감 값, 이의 결과의 `APPLIED`·`UNCHANGED`·`NOT_ISOLATED`.
- 지우거나 바꾸는 연산은 건드린 키를 모두 확인한다: `verify` 칸, 빠진 번호 비트(바뀌지 않아야 한다), `q:adm`, `q:appeal`·`q:appealid`·(G10) `q:appealcase`.
- 경계 양쪽: 유예 마감 직전·직후, 이의 글 0자·1,000자·1,001자(합친 글자 포함), 판 번호 같음·작음·큼, `not_before_ms`와 같은 시각.
- 계정 대조를 뺀 요청이 거절되는지: 다른 pid의 대기 참여에 제출·이의, pid 없는 계정.
- 화면 저장값: 이의를 보낸 뒤 새로고침하면 '접수됨'이 되살아나고 양식이 다시 열리지 않는다. 통과 뒤 대기실이 옛 '추가 검증으로 이동' 상태에 묶이지 않는다.
- 장애 주입은 끊는 자리가 커밋 뒤에 닿는지: `HSETNX` 뒤 발행 실패, `PASSED` 쓰기 뒤 응답 유실, 결과 반영의 사람 슬롯 기록 뒤 회차 슬롯 쓰기 전 실패.
- 겹친 가드는 하나씩 빼 본다: '처음 것만'을 Lua `HSETNX`와 앱의 존재 확인 두 곳에서 지키면 하나씩 뺀 판을 각각 잡는 시험(동시 두 요청)을 둔다.
- 시험 값은 상수와 다르게: 유예·보관 기간은 ARGV·설정으로 넣어 기본값과 다른 값으로도 한 번 돌린다. 판 번호는 9 → 10을 넣는다.
- 시작 파일 조립은 따로 띄워 본다(3.4 끝 줄).
- 정본 시험 표에 세부 번호를 더할 때는 '연결: …' 앞에 둔다(4장 G1~G3·G14).

### 4.1 §8.7 실패 목록 셋에 더할 줄(표·키·Lua보다 먼저)

- **경합(docs/data.md §5, 2491~)**: ① 같은 대기 참여에서 추가 검증 통과·이의 결과 반영·대기 취소·입장 확정이 `verify` 칸을 동시에 바꾼다 → 회차 슬롯 Lua가 지금 값이 `VERIFYING`일 때만 바꾸고, 취소는 `VERIFYING`·`PASSED`만 지운다(지금 코드). 시험 Q-T34 ④⑥⑦, B-T10 ④. ② 같은 사람의 이의 두 요청이 겹친다 → `HSETNX` 하나만 남고 둘 다 같은 202. 시험 B-T10 ①. ③ 결과 반영의 사람 슬롯 기록(판 번호)과 회차 슬롯 쓰기가 한 Lua가 아니다 → 회차 쓰기를 먼저 하고 사람 슬롯 판 번호를 뒤에 올려, 중간에 끊기면 다시 보낸 호출이 같은 결과를 낸다(회차 Lua가 이미 바뀐 값이면 `NOT_ISOLATED`·같은 결과). 시험 B-T10 ⑤. ④ 통과(`PASSED`)와 1인 1순번 위반 판정이 겹친다 → 사람 슬롯 `q:adm`이 먼저 정하고 위반이면 회차 슬롯에서 칸을 지운다. 시험 Q-T34 ⑧.
- **외부 호출(docs/api/guidelines.md §8·§8.1)**: 거래·제어 Kafka 클러스터로 queue-svc가 요청 경로에서 바로 내는 이의 건 요청(무응답·지연·성공 뒤 응답 유실). 무게는 2등급(판단·보조): 멈추면 새 이의 접수만 503이고 대기·입장은 그대로다. 동작의 정본은 bot-defense §12. 내부 gRPC(trust `ScoreRisk`, identity `CheckReverification`)의 실패는 openapi 503과 bot-defense §5.2가 정본이라 §8 표가 아니라 §8.1의 '동작의 정본' 칸에서 가리킨다.
- **자원 한도(docs/verification.md §4.1)**: 대기열 Redis의 `q:appeal` 메모리(이의 수 × 이의 글 최대 크기, 설계 피크는 사람 오탐 상한의 대기 인원 몫 [추정]), queue-svc 생산자 연결(파드마다 하나). 판정은 한도의 80% [가정] 기준.
