## 감독에게

막는 물음은 없다. 아래 1·2는 추천대로 계획을 세웠다(이 기능 안의 일은 바뀌지 않는다). 다르게 정하면 이 계획과 ADR-0357 결정 9를 고친다.

1. **[결정 요청] queue-svc 발행 몫을 맡을 기능이 없다(5일 상한).** OPS-190 줄(docs/BUILD_ORDER.md:650)의 PRF-080·HOT-060이 넘긴 것(대기가 끝날 때의 `QueueEntryRecord` — 입장 확정·빠진 번호·`LEFT`·판매 종료 `SALE_END` 정리 — 와 파드마다 1초 집계 `QueueAggregate`, RB-05의 K 재검토)은 queue-svc에 Kafka 생산자, 사람별 칸(`enteredAt`·`firstEtaSec`·`entryMode`·`verifyRoute`) 저장, 판매 종료 정리 작업이 새로 필요하다. 이 기능의 구현 어림 2.5일 [가정]에 2일 [가정]이 더해져 시험·리뷰·검증까지 5일을 넘는다.
   - (가) **(추천)** 새 기능 하나로 뗀다(가칭 `F-04-20` 'queue-svc 대기 끝 기록·1초 집계 발행', B, 선행 F-04-2). 판정 항목은 A-T26 ④(이 커밋, ledger-notes '다른 단계, 미정')다. 그 기능의 계획이 사람별 칸의 자리(docs/data.md §3의 대기열 키)와 업무 키(ADR-0357 결정 6)를 정한다. OPS-190 단계 줄은 그 기능이 끝날 때 체크하고, F-04-2는 기록 커밋에서 '일부 구현(R-…)'만 남긴다. F-04-3(원본 적재)의 `선행`에 이 기능을 더해 달라.
   - (나) F-04-2에 넣는다. 한 기능이 5일을 넘으므로 ADR-0354 결정 2에 어긋난다.
2. **[결정 요청] 서비스 안에 JSON 소비자가 있는 토픽의 Avro 전환을 맡을 기능이 없다.** 지금 모든 생산자가 JSON 대역을 낸다(ADR-0357 맥락). 이 기능은 서비스 소비자가 없는 토픽만 바꾼다(결정 9). 남는 것: `trade.payments`(purchase-svc 결과 반영), `trade.seats`(purchase-svc 홀드 원장·queue-svc 판매 상태, Redis Stream 릴레이와 Outbox 둘), `trade.purchase-sessions`(queue-svc), `identity.*`(queue-svc·core-svc), `control.*`(공용 제어 동기화 `control-codec.ts`), `support.cases-requested`, `audit.data-accessed`·`ops.command-events`(ops-svc). BAS-030 기록(docs/progress-archive.md:322)이 넘긴 FND-080·FND-090·PRF-030·HOT-010 몫이 이것이다. 이것이 없으면 F-04-1(`ops-rt`)·F-04-3(`analytics-ingest`)은 결제·좌석·구매 세션 사건을 시험용 바이트로만 시험한다.
   - (가) **(추천)** 새 기능 하나(가칭 `F-04-21` '서비스 소비자가 있는 사건의 Avro 전환', B, 2~4일 [가정], 선행 F-04-2)로 두고 F-04-1·F-04-3의 `선행`에 더한다. 생산자와 그 소비자를 같은 기능에서 바꾼다(결정 9의 '한 토픽 한 형식').
   - (나) 기반 영역(F-09)에 둔다. 분석 영역의 다음 기능들이 그 기능을 기다린다.
3. **[알림] A-T21은 이 기능 범위에 넣지 않았다.** A-T21(docs/features/analytics.md:628)의 판정은 브론즈·실버의 값과 dbt 빌드 실패라, 원본 적재(F-04-3)와 dbt(F-04-4)가 있어야 닫힌다. 그 두 행의 장부 범위에 A-T21이 이미 있다. 이 기능은 asyncapi info '필수 여부'가 말한 '생산자 단위 시험'을 새 시험 A-T26(①~⑤, 이 커밋)으로 두었다.
4. **[알림] 계약 깨짐 없음.** 이 커밋은 docs/api의 yaml·proto·avsc를 바꾸지 않는다(avro README에 문장 하나). `node tools/ci/contract-breaking.mjs --target origin/develop`가 통과했다(이 커밋 전 트리, 경고만). 구현도 계약을 바꾸지 않는다. 구현이 계약을 바꿔야 한다고 보면 멈추고 감독에게 넘긴다(BAT-215와 같은 소유자 결정 길).
5. **[알림] 마이그레이션 없음.** DB 표는 바꾸지 않는다. 좌석 Redis의 구매 세션 Hash에 칸 `hn` 하나를 더한다(docs/data.md:2793, ADR-0357 결정 7). 새 ADR은 0357 하나다(갈래 1 몫 0358은 비워 둔다).
6. **[알림] 생산자가 아직 없는 분석 원천.** `TicketEvent`(`trade.tickets`)와 `SettlementEvent`(`trade.settlements`)는 저장소에 생산자가 없다. OPS-190 줄의 '티켓·정산 필드 발행 서비스 반영'은 그 생산자를 만드는 기능(현장 입장 F-05, 정산 F-07)이 이 기능의 인코더로 처음부터 Avro로 낸다. 그 기능 계획에 이 한 줄을 넘겨 달라.

## 계획

### 1. 범위

- **P1 계약 판 스키마 생성물**: `packages/contracts` 생성기가 docs/api/avro/의 `.avsc`를 `src/gen/avro/`로 옮겨 `@peaket/contracts/avro`로 낸다(ADR-0357 결정 2).
- **P2 공용 Avro 인코더(`@peaket/platform/avro`)**: 인코딩 규칙(결정 3), 설정 파일 읽기(결정 4), 시작 확인과 그 신호(결정 5), 인코딩 오류(결정 8).
- **P3 주문 사건(`trade.orders`)**: purchase-svc의 주문 사건 Outbox와 회차 환급 팬 알림 Outbox를 Avro로 바꾸고, 시작할 때 설정을 읽고 확인한다(ST-T16 ②).
- **P4 홀드 시도(`telemetry.purchase`)**: 버리던 `HoldAttempt`를 텔레메트리 버퍼로 낸다. `retryNo`·`autoResult`·`eventKey`를 채운다(결정 6·7).
- **P5 판정 기록·행동 신호(`telemetry.trust-verdicts`·`telemetry.behavior`)**: trust-svc 기록기와 purchase-svc 행동 신호 둘을 Avro로 바꾼다.
- **P6 배포·로컬 조립**: 서비스 차트가 ConfigMap `schema-ids`를 붙이고, 로컬 클러스터·합본에 고정 설정 파일을 준다(결정 4).
- **나누기**: 구현 어림 2.5일 [가정](P1 0.25, P2 0.75, P3 0.5, P4 0.5, P5 0.25, P6 0.25)에 시험·리뷰·검증을 더해 5일 안이다. queue-svc 몫은 이미 뗐다(감독에게 1). 구현이 시작 뒤 4일을 넘기면 감독에게 알리고 **(앞) P1·P2·P3(A-T26 ①⑤의 주문 몫, ST-T16 ②, payment 16.5.2)** 과 **(뒤) P4·P5·P6(A-T26 ②③⑤의 텔레메트리 몫, seat-hold 14.2.4·16.2.5)** 로 나눈다. 뒤는 앞의 인코더에만 기댄다.

### 3. 바른 동작과 근거(값은 정본에서 읽는다)

- **바이트 모양**: 매직 바이트·스키마 ID·본문은 docs/api/avro/README.md:73(§3), 주제 이름은 같은 표의 '주제(subject) 이름' 줄(`TopicRecordNameStrategy`), Kafka 키는 UTF-8 문자열(§2 'Kafka 키', docs/streaming.md §7). 다섯 바이트 껍데기는 `packages/platform/src/avro.ts`의 `encodeConfluent`를 쓴다.
- **칸**: 필수·조건부·기본값은 docs/api/avro/README.md §6과 각 `.avsc`(그 생성물). 날짜·시각 변환과 조건부 칸 검사, `UNRECOGNIZED` 금지는 ADR-0357 결정 3, docs/api/avro/README.md §3 '열거 기호 더하기'.
- **설정과 시작 확인**: 설정 파일 자리·없을 때·로컬 고정 번호는 결정 4, 확인의 시간 한도·견주는 법·404·닿지 못할 때의 로그와 게이지·주소와 자격·주소가 없을 때는 결정 5. 레지스트리 조회 규칙(https만, 3xx 안 따름, 자격을 로그에 넣지 않음)은 ADR-0335 결정 3이고 `schemaRegistrySource`를 그대로 쓴다. 준비 상태에 넣지 않는다(README §3). 설정에 없는 주제는 시작하지 않는다(D-T39 ③, docs/devops.md:941).
- **`eventKey`**: 결정 6. 주문 사건은 `services/purchase-svc/src/modules/booking/domain/order.ts:199` `orderEventKey`, 환급 팬 알림은 `outbox-event-refund-fan-notifier.ts`의 `eventRefundNoticeKey`, 판정 기록은 지금 식 그대로다. 홀드 시도는 UUIDv7.
- **홀드 시도**: 칸의 뜻은 docs/api/asyncapi.yaml:566~586과 docs/features/seat-hold.md:144~150, `retryNo`와 `hn`은 결정 7·docs/data.md:2793, 버림은 결정 8과 docs/streaming.md §2.6 필수 설정 표의 '생산자(텔레메트리)' 두 줄. 응답 경로에 Redis 왕복을 더하지 않는다(seat-hold §2의 홀드 p99 상한, S-T35 ⑥).
- **판정 기록·행동 신호**: 칸은 asyncapi(:587~606, `BehaviorSignal`), 싣지 않는 것(점수 원값·가중치)은 docs/features/bot-defense.md §4.1 ⑤. 기록기가 지금 고르는 칸은 바꾸지 않고 바이트 형식만 바꾼다.
- **운영 확인**: docs/features/analytics.md:678(이 커밋). 버림 경보의 꼴은 docs/features/bot-defense.md:471과 같다.

### 4. 손댈 파일(구현 담당. 시험 파일은 건드리지 않는다)

### 5. 공개 인터페이스(시험 담당이 기댄다. 이름은 구현이 이대로 쓴다)

  - `export function createAvroEncoder(o: { schemaIds: Readonly<Record<string, number>>; schemas: Readonly<Record<string, unknown>>; produces: readonly { topic: string; record: string }[] }): AvroEncoder`(만들 때 주제가 설정에 없거나 스키마가 없으면 던진다).

  - `export async function checkProducerSchemas(o: { env: Record<string, string | undefined>; encoder: AvroEncoder; schemas: Readonly<Record<string, unknown>>; registry?: SchemaSource; metrics: Registry; logger: { info(o: object): void; warn(o: object): void }; timeoutMs?: number }): Promise<{ subject: string; result: 'ok' | 'unavailable' | 'skipped' }[]>`(다르거나 404거나, local·ci 밖에서 주소가 없으면 던진다. `registry`를 주지 않으면 환경 값으로 `schemaRegistrySource`를 만든다). 게이지 `schema_startup_check_unavailable{subject}`.

### 10. 자주 놓친 결함(docs/architecture.md:1168~1182에서 고름, 시험·구현 지시문에 넣는다)

- 저장소 응답은 정확한 값까지 단언한다: 시도 세기는 0·1·2와 null, 바이트의 스키마 ID는 파일의 그 주제 값.
- 허용·거부 목록은 목록 밖 값마다 본다: 시작 확인의 결과 넷(같음·다름·404·닿지 못함)과 주소 없음의 환경 둘(local·staging) 모두, 텔레메트리 토픽 셋 모두.

### 12. 범위 밖과 막힘

- **다른 기능(감독에게 1·2·6)**: queue-svc의 `QueueEntryRecord`·`QueueAggregate`(A-T26 ④)와 RB-05의 K 재검토, 서비스 소비자가 있는 토픽의 Avro 전환(결제·좌석·구매 세션·계정·제어·문의·감사·관제 명령 사건과 그 소비자), `TicketEvent`·`SettlementEvent` 생산자.
- **구간 5(INF)**: 실제 레지스트리·ArgoCD PreSync 등록 Job과 `schema-ids` 마운트를 실제 클러스터에서 확인(D-T39 ①②④의 배포 몫), `schema_startup_check_unavailable` 경보 규칙을 실제 경보 관리자에 올리는 일(F-01-5 OPS-100이 경보 규칙을 모은다).
- **좌석 시험 S-T35 ⑤(ID만, A 등급)**: 자동 배정 성공·실패의 `seatIds`·`heldAt`은 A-T26 ②가 바이트 쪽에서 보지만, S-T35 ⑤ 항목 자체는 이 기능 범위가 아니다(A 등급 항목을 B 기능에서 닫지 않는다). 좌석 영역 기능이 닫는다.
- 분석 원본 적재의 조사 칸 버리기·브론즈·실버(A-T21, ST-T22)는 F-04-3·F-04-4다.
- **AUTO 거절 시도의 `autoResult`(구현에서 찾음, 2026-11-23)**: 계약은 mode AUTO면 `autoResult`가 있어야 하는데(`x-present-when`) '배정을 시도하지 못함' 기호가 없다. 그래서 AUTO의 ERROR·LIMIT 시도는 늘 버려지고 센다. 기호를 더할지는 **감독 결정**이다(정하면 asyncapi·avsc·`hold-seats.ts`를 함께 고치는 작은 기능).
- **등록 도구 출력 키(구현에서 찾음, 2026-11-23)**: `tools/ci/avro-schema.mjs` `registerToRegistry`는 `ids[topic]`(토픽 키)로 쓰는데 `parseSchemaIds`·인코더·ADR-0357은 주제(`<토픽>-<레코드>`) 키다. 이대로면 실제 등록 Job이 쓴 ConfigMap으로는 생산자가 시작하지 않는다(D-T39 ③). 기존 시험(`tools/ci/avro-schema.test.mjs:120·156`)이 토픽 키를 단언한다. **구간 5 전 배포 묶음**(D-T39 ①②④의 실제 클러스터 확인과 같은 묶음)이 고친다.

### 구현 의심점

1. **고객 취소의 REFUNDED가 인코딩 오류로 취소 트랜잭션을 깬다(높음 의심).** asyncapi `OrderEvent.refundAmount`는 `x-present-when: [{ type: [REFUNDED] }]`(R-583)인데, 주문 전이 사건(`buildOrderEvent`, T23·T24·T26)은 `refundAmount`를 싣지 않는다. 운영 조립(start.ts)은 팬 취소의 `DrizzleCancellationWrites`에 Avro 코덱을 준 `DrizzleOrderStore`를 넘기므로, 전액 취소(T24)·남은 표 취소(T23)마다 `AvroEncodeError`로 취소 트랜잭션이 실패한다(결정 8). 실패 시험: `services/purchase-svc/test/order-events-avro.test.ts` 'A-T26 ① 고객 취소로 끝난 주문의 REFUNDED(T23·T24·T26)도 공통 판정을 만족한다' — `AvroEncodeError … 칸 refundAmount`. 정본 쪽 모순도 있다: asyncapi type 설명은 'REFUNDED는 회차 취소·연기 환급 완료'인데 주문 상태 REFUNDED(고객 취소)도 같은 사건 종류로 낸다. 고침은 (가) 주문 전이 사건에 취소 환급액을 싣거나 (나) 계약의 조건·뜻을 고치는 것(감독 결정). 기존 취소 통합 시험은 저장소 기본값(JSON 대역)으로 조립해 이것을 보지 못한다.
2. 팬 알림의 `eventKey`(`eventRefundNoticeKey`)는 SHA-256 hex를 UUID 모양으로 자른 값이라 버전·변형 비트가 없다(계약 `logicalType: uuid`). 인코더는 uuid를 검사하지 않아 통과한다. 결정 6이 '지금 식 그대로'라 결함으로 두지 않고 적어만 둔다.
3. 홀드 시도는 계약을 채우지 못하면 세기 전에 버린다(구현 메모). 그래서 '버린 시도는 retryNo를 올리지 않는다'를 A-T26 ⑤ 시험에 넣었다(결정 7 '그 시도 앞에 낸 시도의 수'). 리뷰가 다르게 읽으면 그 단언을 고친다.

### 정한 작은 세부

- 키 차례 무시 견주기(`sameJson`): 객체는 키 집합과 값이 같으면 같고, 배열은 차례까지 같아야 한다. 레지스트리 응답은 `schemaRegistrySource`가 푼 JSON 그대로 견준다.
- 시작 확인: 주제마다 따로 2초 한도로 함께 묻는다(`schemaRegistrySource` 자체 한도도 같은 값). 다름·404가 하나라도 있으면 그 주제 이름을 적고 던진다. 닿지 못한 주제마다 경고 한 줄 `{ kind: 'schema-startup-check', subject, result: 'unavailable' }`과 게이지 1, 맞은 주제는 게이지 0. 주소가 없을 때(local·ci) 정보 로그 한 줄에 주제 목록을 싣고 게이지는 0이다. 자격은 `PEAKET_SCHEMA_REGISTRY_USER`·`_PASSWORD` 둘 다 있거나 둘 다 없어야 한다(하나만 있으면 시작 실패).
- 인코더: 갈래가 여럿인 유니온은 처음으로 모든 칸을 채우는 갈래를 쓴다(`avsc` `wrapUnions: 'never'`). `date-time`은 RFC 3339(시간대 필수) 글만 받고 숫자 밀리초·`Date`도 받는다. 칸 경로는 `avro-reader.ts`와 같은 꼴(점으로 잇고 번호 없음). 기본값 없는 칸은 null 갈래가 있어도 필수로 본다(ADR-0150). 레코드 이름이 계약 판 이름과 다르면 만들 때 던진다.
- 내는 주제: purchase-svc는 purchase DB가 있으면 `trade.orders`/`OrderEvent`와 `telemetry.behavior`/`BehaviorSignal`(결제 화면), 텔레메트리 Kafka가 켜졌으면 `telemetry.purchase`/`HoldAttempt`와 `telemetry.behavior`. 낼 주제가 없으면 설정 파일을 읽지 않는다(DB·텔레메트리 없이 뜨는 시작 시험은 그대로 뜬다). trust-svc는 텔레메트리 Kafka가 켜졌을 때만 `telemetry.trust-verdicts`/`TrustVerdict`·`telemetry.behavior`/`BehaviorSignal`.
- 릴레이 프로세스(`relay.ts`): 주문 만료 안전망·보상·환불 쓰기가 `trade.orders`를 쓰므로 설정 파일을 늘 읽고 `startPurchaseRelay`의 새 옵션 `orderEventCodec`으로 넘긴다. 시작 확인은 프로세스 레지스트리가 생긴 뒤(릴레이 프로세스를 띄운 뒤) 관리 포트를 열기 전에 하고, 실패하면 종료 코드 1로 끝낸다. 그래서 리더 반복이 확인 동안(최대 2초) 먼저 돌 수 있다.
- 홀드 시도: 계약을 채우지 못하는 시도는 세기(hn) 전에 버린다(버린 시도가 다음 시도의 `retryNo`를 올리지 않게. 인코딩을 두 번 한다). 세기가 null·실패, 인코딩 실패는 모두 `telemetry_dropped_total{record="HoldAttempt"}` 1과 경고 `{ kind: 'telemetry-dropped', record, reason, fields? }`(값 없음). `seatIds`는 PICK이거나 HELD일 때만 싣는다(AUTO 실패는 null).
- 자동 배정 시도: `autoResult`는 HELD면 배정 결과, 수동 선택으로 넘긴 409(`manual-selection-required`)면 `MANUAL_REQUIRED`, 그 밖 거절(ERROR·LIMIT)은 비운다. 그런 시도는 `x-present-when` mode AUTO 때문에 인코더가 버리고 센다(아래 '정본 빈칸' 2). 잡지 못한 AUTO 시도의 `tierId`는 희망 1순위 등급 `firstTierId`로 채웠다(정본은 PICK의 '첫 좌석 등급'만 정한다. 이것이 없으면 MANUAL_REQUIRED 시도도 필수 칸이 비어 모두 버려진다).
- 꺼진 텔레메트리: HoldAttempt·BehaviorSignal은 인코딩하지 않고 `telemetry_dropped_total`만 올린다(지금까지와 같은 셈).
- JSON 대역 `jsonOrderEventCodec`은 저장소 어댑터(`DrizzleOrderStore`·`DrizzleTicketIssue`)의 기본값으로 남겼다. 코덱을 주지 않는 시험 조립이 30곳 남짓이라서다. 운영 조립(start.ts, relay.ts→relay-app.ts)은 늘 Avro 코덱을 준다. 기본값을 없애려면 시험 조립을 함께 고친다(리뷰 몫).
- 차트 값: `schemaIds.enabled`(기본 false)·`schemaIds.configMapName`(기본 `schema-ids`). 켜면 앱·Outbox 릴레이 컨테이너에 `PEAKET_SCHEMA_IDS_FILE=/etc/peaket/schema-ids/schema-ids.json`과 읽기 전용 볼륨(키 `schema-ids.json`만)을 붙인다. 로컬은 `deploy/envs/local/v1-purchase-relay.yaml`만 켠다(`tools/local/cluster.mjs v1`이 고정 번호 ConfigMap을 만든다). staging·prod 값 파일은 아직 없어 켜지 않았다(구간 5에서 `schemaRegistry`와 함께). `helm template`로 켬·끔 렌더를 확인했다.
- 합본: 공통 값에 `PEAKET_SCHEMA_IDS_FILE`이 없으면 `localSchemaIds`를 임시 폴더(`peaket-bundle-schema-ids-<pid>.json`)에 쓰고 `process.env`에 둔다(split 자식·relay 자식도 받는다). 합본 의존에 `@peaket/contracts`(workspace)를 더했다(잠금 파일 3줄).
- 시험 별칭: purchase-svc·trust-svc 단위·통합 Vitest 설정에 `@peaket/platform/avro` → `src/avro-entry.ts`, purchase-svc 통합 설정에 `@peaket/contracts/avro` → `src/gen/avro/index.ts`(CI 통합 단계는 빌드하지 않는다).

### 회차 환급 팬 알림(멈췄다가 끝냄, 2026-11-23 감독 지시)

- 처음에는 계약 판 `OrderEvent.avsc`에 asyncapi(2026-11-15 R-583)의 기호 `EVENT_POSTPONED`·`REFUND_FAILED`와 칸 `refundAmount`·`fanNoticeReason`·`postponedTo`·`refundWindowClosesAt`이 없어 멈췄다. 감독 지시로 avsc를 asyncapi에 맞췄다: 열거 끝에 기호 둘, `amount` 뒤에 칸 넷(asyncapi와 같은 차례, null 첫 갈래·기본값 null, `x-present-when`은 asyncapi와 같음). docs/api/avro/README.md §1 바꿈 기록·§6 세기(227 → 231칸)·`OrderEvent` 줄도 고쳤다. `pnpm --filter @peaket/contracts gen`으로 `src/gen/avro/peaket-trade-OrderEvent.ts`만 바뀌었다(api-client 생성물은 그대로).
- 깨짐 확인: `node tools/ci/avro-schema.mjs`·`--base origin/develop`·`--base v0.2.0` 통과, `node --test tools/ci/avro-schema.test.mjs` 10 통과, `node tools/ci/contract-breaking.mjs --target origin/develop` 오류 0(OpenAPI 경고 22·AsyncAPI Avro 경고 8, 모두 이번 전부터 있던 열거 더하기 경고).
- `OutboxEventRefundFanNotifier(codec?)`가 코덱(`EventRefundNoticeCodec`, `encode(message: object)`)을 받는다. start.ts·relay-app.ts는 주문 사건과 같은 `avroOrderEventCodec`을 넘겨 `trade.orders`가 한 형식이 됐다(결정 9). 주지 않으면 JSON 대역(시험 조립). `relay-app.ts`의 `orderEventCodec` 옵션 형은 `AvroOrderEventCodec`이다. 이제 §6의 'A-T26 ① 회차 환급 팬 알림도 같은 형식이다'를 쓸 수 있다.
- 정한 것: REFUND_FAILED는 계약이 사유를 늘 요구하므로 `item.lastError`가 없으면 `'failed'`를 싣는다(환급 실패 기록의 `cancellationFailure.lastError ?? 'failed'`와 같다).
- 리뷰가 볼 것: 회차 취소·연기 확정에 `fanNoticeReason`이 없으면 이제 인코딩 오류로 확정 트랜잭션이 실패한다(결정 8). ops-svc 판정 경로는 그 칸을 필수로 받지만 purchase-svc 내부 HTTP·gRPC 확정 요청은 선택으로 받는다(`inbound/event-refund.controller.ts:27·70`, `inbound/event-refund.grpc.ts:170`). 그 길로 사유 없이 확정하면 500이다.

### REFUNDED의 환급액(시험 결함 고침, 2026-11-23)

- 시험 담당(`4a1d0d463`)이 찾은 결함: 주문 상태 전이로 만드는 REFUNDED(T23·T24, T26은 아직 부르는 곳이 없다)가 계약 필수 칸 `refundAmount`(`x-present-when` type REFUNDED)를 싣지 않아 Avro 코덱에서 취소 트랜잭션이 실패했다. 고침: `TransitionInput.refundAmount`·`BuildOrderEventInput.refundAmount`(도착이 REFUNDED인 전이에만, 0 이상 정수, 다른 전이에 주면 RangeError)를 더하고, 취소 쓰기(`drizzle-cancellation.ts` create·updateStatus)가 T23·T24에 그 취소의 `refund_amount`를 넘긴다. asyncapi의 REFUNDED·`refundAmount` 설명에 고객 취소를 넣었다(설명만, avsc `doc`도 같게). 시험 하나는 이의('시험 이의')로 멈췄다.
