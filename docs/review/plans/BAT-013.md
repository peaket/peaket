# 묶음 계획: BAT-013(PRF-174 탈퇴 참여자의 결제한 미사용 티켓)

- **무엇**: 묶음을 시작할 때 만든 작업 목록이다(docs/architecture.md §8.6 4의 1·2, '역할 나누기'의 계획). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다. 정본의 값은 옮겨 적지 않고 자리(문서·절)만 가리킨다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane1`, 가지 `feature/lane1-BAT-013`, 출발점 `origin/develop` `6e975f55`. 지시서는 `brief.mjs --batch BAT-013`(만든 때 `6e975f55`). 2026-11-19 계획 담당이 썼고 시험·제품 코드는 쓰지 않았다.
- **등급**: A(docs/BUILD_ORDER.md 묶음 표 BAT-013). 결제한 미사용 티켓의 취소·환급이 돈(공제·환급·이중 환급)에 닿는다. 짧은 고리(ADR-0283 결정 2)를 쓰지 않는다: 리뷰 → 리뷰 반영(시험 먼저, 그다음 구현) → 고친 곳 다시 리뷰 → 검증.
- **차례**: 정방향 묶음이다(이 계획 커밋에 `Batch-Order: impl-first`). 계획 → 구현 → 시험(구현 전 트리에서 실패 확인) → 리뷰 → 리뷰 반영 → 다시 리뷰 → 검증 → 기록.
- **정본**: [ADR-0284](../../adr/0284-withdrawal-participant-contract-and-deferred-finish.md) 결정 7(이 커밋), docs/features/identity.md §8 '미사용 티켓 확인과 취소'·'탈퇴 화면 연결'·§10.1·§12 I-T26 ①~③, docs/features/payment.md §4.1 '탈퇴 참여자의 첫 구현'(‘미사용 티켓 견적’·‘미사용 티켓 취소’·‘답’·‘지표·로그’·‘남는 한계’), docs/planning/03-policies-glossary.md §1.5 ①⑤⑧, `docs/api/openapi.yaml` `deleteIdentityAccount` 409·503·`unusedTickets`, `docs/api/proto/peaket/purchase/v1/account.proto` `WithdrawalParticipantService.QuoteAccountWithdrawal`·`ProcessAccountWithdrawal`·`TICKET_REFUND_PENDING`, docs/security/asvs/payment.md 2.3.1·8.2.1·8.2.2.

## 감독에게

정하지 않고 올리는 것과, 이 계획이 정한 것을 알린다.

1. **화면(SCR-017)을 이 묶음에 넣었다.** 서버가 새 409 `unusedTickets`를 내는데 지금 화면(`apps/web/src/features/account-withdraw/flow.ts`)은 그 409를 `error`로 처리한다. 화면을 고치지 않으면 실제 흐름에서 탈퇴가 막힌다. 그래서 최소한 ① 409를 읽어 환급 예상(CMP-054)을 최종 확인 버튼보다 먼저 보이고 ② `confirmCancelUnusedTickets: true`를 실어 다시 보내는 일을 넣었다. 화면이 바뀌므로 브라우저 확인(docs/architecture.md §8.6 8)이 붙는다(기록 파일 이름은 단계 ID `PRF-174`). 빼려면 서버 계약을 바꿔야 한다(화면은 오류로 남는다). 그래서 묶음 표의 0.5일 [가정]보다 걸릴 수 있다(화면·브라우저 확인 몫).
2. **코드와 정본이 어긋난 곳을 고친다.** `services/purchase-svc/src/modules/refund/application/cancel-ticket.ts`의 `zeroDeductionFor`가 `ACCOUNT_WITHDRAWAL`을 공제 없음(0원)으로 본다. 정본은 POL-032 공제율을 쓴다(docs/planning/03 §1.5 ①, payment §4.1 '회원 탈퇴 연동', FR-017). 방향을 바꾸는 결정이 아니라 정본에 맞추는 고침이고, 돈 A 대상이라 이 묶음에서 고친다.
3. **양도·굿즈의 경계.** 받은 티켓·보낸·받은 양도 요청은 GAT-050, 굿즈는 커머스 단계 몫이다. 지금 양도 단계가 없어 결제자 = 보유자이고, '양도 가능 여부'는 양도 마감(공연 시작 2시간 전과 입장 시작 가운데 이른 때)만 본다. 양도 단계가 생기면 견적에 ticket-svc 보유자 대조와 상품 유형·잠금을 더한다(ADR-0284 되돌릴 조건).
4. **확인을 따로 저장하지 않는다.** `confirmCancelUnusedTickets`를 지난 요청만 미룸 표시를 하므로, 다시 하기 고리는 미룬 계정을 '확인을 받은 계정'으로 본다. 배포 전에 이미 미룬 계정이 있으면 확인 없이 티켓이 취소될 수 있다(운영 전이라 수용, ADR-0284 결정 7에 적음).
5. **장부**: I-T26을 ①②③으로 나눴다(정본 표). `ledger-notes.md`의 '다른 단계' 줄을 지우고 '## 등급'에 A 줄을 넣었다. 계획 시점 장부는 `I-T26 ①②③` 빈칸 3(모두 A)이고, 시험 커밋 뒤 자동 시험이 된다.

## 계획

### 1. 범위

- **하는 것**: PRF-174(docs/BUILD_ORDER.md 283행, wbs 2.7.1 ③, 0.5일 [가정]). 탈퇴 참여자가 **결제한 미사용 티켓**을 가지고 있으면 ① 안내(보유 장수·결제 금액·POL-032 공제액·환불 예상액·지금 양도 가능한 수·입장 기록 마감 뒤 환급 수) ② 사용자 최종 확인(`confirmCancelUnusedTickets`) ③ 표마다 기존 취소·환급 Saga(사유 `ACCOUNT_WITHDRAWAL`, POL-032 공제) ④ 환급이 끝난 뒤 탈퇴 완료 순서가 되게 한다. 지금은 그런 티켓이 있어도 탈퇴가 그대로 끝난다(identity §8 '탈퇴 참여자와 탈퇴 미룸의 첫 구현'의 남는 한계).
- **뺀 것과 까닭**: 굿즈·부가 상품(§1.5 ⑦)은 커머스 단계 몫이라 하지 않는다. 받은 티켓(②)·보낸·받은 양도 요청(③④)은 GAT-050, 가상계좌 지연 환급(⑤의 나머지)은 GAT-090 몫이다. 결제 결과 대기·입금 대기 주문(BAT-010, I-T84·P-T55)은 건드리지 않고 회귀만 본다.
- **새 ADR 없음**: 방향은 POL-033·ADR-0062가 이미 정했고, 구현 길만 ADR-0284 결정 7로 정한다.
- **화면**: SCR-017 실제 흐름의 탈퇴 확인 창에 409 견적을 잇는다(위 '감독에게' 1). 목업 흐름은 그대로다.
- **현재 상태(출발점 `6e975f55`)**: `DELETE /v1/identity/account`는 재인증 → 보관 409 → 미룸 표시 → 참여자(결제 대기·입금 대기) 순서이고, 결제한 미사용 티켓은 참여자가 없어 그대로 탈퇴가 끝난다(identity §8 '탈퇴 참여자와 탈퇴 미룸의 첫 구현'의 남는 한계). `WithdrawInput.body.confirmCancelUnusedTickets`는 컨트롤러가 넘기지만 `WithdrawAccount`가 보지 않는다. purchase `ProcessAccountWithdrawal`은 주문·입금 대기만 본다. `CancelTicket`의 `zeroDeductionFor`는 `ACCOUNT_WITHDRAWAL`을 공제 0원으로 본다(정본과 다름). 화면 실제 흐름은 새 409를 `error`로 처리하고, 목업 견적만 보여 준다.

### 2. 장부 범위

```text
I-T26
```

- 이 커밋의 정본 표를 ①②③으로 나눠 장부가 세 항목으로 읽는다(`node tools/ci/ledger.mjs --batch BAT-013`: 항목 3, A 3, 빈칸 3, '다른 단계' 0). 묶음 표의 '장부 범위' 칸은 그대로 `I-T26`이다.
- **범위 밖(빼는 것, 다른 단계로 미루는 것이 아님)**: I-T43(받은 티켓·양도 요청·가상계좌 지연 환급)은 GAT-050·GAT-090, P-T55(BAT-010의 결제 대기·입금 대기 참여자)는 이 묶음이 바꾸지 않는 동작이라 회귀만 본다. ASVS 행(payment 2.3.1·8.2.1·8.2.2)은 이미 시험이 있어 범위에 넣지 않고, 새 시험에 같은 태그를 달아 근거를 더한다.
- **장부 notes**: '다른 단계'의 I-T26 줄을 지우고 '## 등급'에 `I-T26 | | A | BAT-013 | ...` 줄을 넣었다. 기록 담당은 장부를 다시 쓴다.

### 5. 공개 인터페이스(시험 담당이 기댄다. 이름은 구현이 이대로 쓴다)

- **HTTP**: `DELETE /v1/identity/account`(요청 `X-Reauth-Token`) → 204(끝냄)·202(미룸)·403 `reauth-required`·409 `withdrawal-confirmation-required`(`fraudHold` 또는 `unusedTickets`)·503 `dependency-unavailable`(견적 실패, `Retry-After: 1`). 본문 `confirmCancelUnusedTickets?: boolean`은 이미 있다.
- **gRPC**: `peaket.purchase.v1.WithdrawalParticipantService/QuoteAccountWithdrawal({ account_id })` → `{ unused_tickets, ticket_amount, deduction_amount, refund_amount, transferable_tickets, refund_deferred_tickets }`. `ProcessAccountWithdrawal` 답에 `unused_tickets_cancelled`(6)·`unused_tickets_pending`(7), 이유 `WITHDRAWAL_PENDING_REASON_TICKET_REFUND_PENDING = 3`. 두 RPC 모두 내부 토큰·호출자 `identity-svc`·소문자 UUID 검사를 한다.
- **identity 응용 층**:
  - `interface WithdrawalParticipant { readonly name: string; process(accountId, { deadlineMs }): Promise<WithdrawalParticipantAnswer>; unusedTickets?(accountId, { deadlineMs }): Promise<UnusedTicketsQuote | undefined> }`.
  - `interface UnusedTicketsQuote { count: number; ticketAmount: number; deductionAmount: number; refundAmount: number; transferableCount: number; deferredRefundCount: number }`.
  - `WithdrawalSignals`에 `ticketQuote?(result: 'ok' | 'none' | 'error')`를 선택으로 더한다(옛 대역을 깨지 않는다). `WITHDRAWAL_QUOTE_DEADLINE_MS = 2_000` [가정]. 견적은 미룸 표시 전에 동시에 부르고, 하나라도 실패하면 `AccountError('DEPENDENCY_UNAVAILABLE')`(503)이다. 값은 참여자마다 더한다(지금은 purchase 하나).
  - `WithdrawAccount.run(i)`의 입출력 모양은 그대로다. `AccountError`에 `unusedTickets?: UnusedTicketsQuote`를 더한다.
- **purchase 응용 층**:
  - `QuoteAccountWithdrawal.run({ accountId, deadlineAtMs })` → `UnusedTicketsQuote`(위와 같은 이름). DB에 닿지 못하면 `WithdrawalOrdersUnavailable`.
  - `ProcessAccountWithdrawal.run`의 답에 `unusedTicketsCancelled: number`, `unusedTicketsPending: number`를 더하고 `WithdrawalPendingReasonName`에 `'TICKET_REFUND_PENDING'`.
  - 포트 `WithdrawalTickets`:
    - `quote({ accountId, nowMs, statementTimeoutMs })` → `UnusedTicketsQuote`
    - `cancel({ accountId, nowMs, deadlineAtMs, limit, minRemainingMs, marginMs, cancelDeadlineCapMs })` → `{ cancelled, pendingUncanceled, skipped }`. `pendingUncanceled`은 이번 호출에 취소 행을 만들지 못한 표(부르지 못함·`TRANSFER_PENDING`·`CONFLICT`·행 쓰기 전 실패)만 센다. 행을 쓴 뒤 실패한 표는 `pendingRefunds`가 세므로 `pendingUncanceled`에 넣지 않는다(취소 ID로 행 존재를 확인한다). `REFUND_PENDING`·`REQUESTED`는 행이 있으므로 `pendingRefunds`가 센다(두 번 세지 않는다).
    - `pendingRefunds({ accountId, statementTimeoutMs })` → `number`(그 계정 주문의 `order_cancellation` 가운데 사유 `ACCOUNT_WITHDRAWAL`이고 상태가 `REQUESTED`·`REFUND_PENDING`인 표 수)
  - `unused_tickets_pending` = `pendingRefunds` + `pendingUncanceled`. `unused_tickets_cancelled`는 이번 호출에서 `cancelled`로 센 수다.
  - `WithdrawalTickets` 포트가 없는 조립(옛 시험)은 티켓 몫을 건너뛴다(견적 0장, `DONE`에 영향 없음). 운영 `start.ts`는 늘 넣는다.
  - 받는 층 `withdrawalParticipantHandlers(service: Pick<ProcessAccountWithdrawal,'run'> & { quote?: Pick<QuoteAccountWithdrawal,'run'> }, o)` — 시작은 `service`에 `quote`를 붙여 넘기고, 옛 시험(quote 없음)은 Process만 부른다.
  - 서비스 `AccountWithdrawalTickets`(refund 모듈)가 위 포트를 구현한다. `CancelTicket`의 기존 공개 계약은 그대로다.
  - `withdrawalTicketCancellationId(ticketId: string): string` — sha256(`WithdrawalCancel:${ticketId}`) 앞 16바이트를 UUID 버전 8 모양으로. 같은 표는 늘 같은 값이다.
  - 상수(이름 그대로): `WITHDRAWAL_TICKET_CANCEL_LIMIT = 10`, `WITHDRAWAL_TICKET_CANCEL_MIN_REMAINING_MS = 50`, `WITHDRAWAL_TICKET_CANCEL_MARGIN_MS = 100`, `WITHDRAWAL_TICKET_CANCEL_DEADLINE_MS = 5_000` [가정]. 문장 시간 한도는 기존 `WITHDRAWAL_STATEMENT_TIMEOUT_MS = 400`을 쓴다.
- **web**:
  - `WithdrawApi.withdraw(token, acknowledgeFraudHold: boolean, o?: { confirmCancelUnusedTickets?: boolean }): Promise<WithdrawAnswer>`(기존 두 인자 호출을 깨지 않게 세 번째 선택 인자로 더한다).
  - `WithdrawAnswer`에 `{ kind: 'unusedTickets'; count: number; ticketAmount: number; deductionAmount: number; refundAmount: number; transferableCount: number; deferredRefundCount: number }`.
  - `afterWithdraw(r, { closed })`가 `'tickets'` 단계를 돌려준다(창을 닫았으면 지금처럼 버린다).
- **지표 이름**: `identity_withdrawal_ticket_quote_total{result}`(`ok`·`none`·`error`), `purchase_withdrawal_ticket_cancel_total{result}`(`cancelled`·`refund_pending`·`skipped`·`error`).

### 7. 구현 전 트리에서 실패를 볼 수 없는 시험과 그 까닭

- 새 RPC·메시지·칸(`QuoteAccountWithdrawal`, `TICKET_REFUND_PENDING`, `unused_tickets_*`, Problem `unusedTickets`)을 쓰는 시험은 구현 전 트리(`6e975f55`)의 `docs/api/proto`와 `@peaket/contracts`에 설명자가 없어 실행조차 안 된다. 이런 실패는 세지 않는다(§8.6 7).
- purchase의 새 파일(`quote-account-withdrawal.ts`·`account-withdrawal-tickets.ts` 등)을 import하는 시험은 파일이 없어 실행조차 안 된다. `process-account-withdrawal.test.ts`의 새 시험은 포트가 없어 TypeError다.
- **실패를 볼 수 있는 것**: identity `withdrawal-http.test.ts`·`withdrawal.test.ts`·`withdrawal-retry.test.ts`(지금은 409가 없고, 티켓 이유를 DONE으로 접는다), web `flow.test.mjs`(지금은 409를 error로 본다). 시험 담당은 이것을 구현 전 트리에 복사해 돌리고 '실패 확인'에 적은 뒤 복사본을 지운다.
- 처음부터 통과하는 시험(지금 동작): 0장이면 409가 없는 길, 보관 409가 먼저인 길, 503·403·닫은 창 처리. 9의 틀린 구현 M8·M5·M17로 한 번 실패를 본다.

### 8. 차례

1. 구현: 계약 생성물 → identity(타입·견적·409·503·어댑터·지표) → purchase(포트·SQL·견적·취소·gRPC·start·공제 고침) → web(flow·화면). 형 검사와 이 묶음이 바꾸지 않는 동작의 기존 시험이 통과하는 상태로 구현 커밋. 응답 칸이 늘어 깨지는 기존 시험(예: `withdrawal-participant.grpc.test.ts`의 응답 전체 비교)은 시험 담당이 시험 커밋에서 고친다(구현은 시험 파일을 고치지 않는다).
2. 시험: 위 6을 쓰고 7대로 실패 확인 → 구현에서 통과(시험 결과).
3. 리뷰 → 리뷰 반영(지적마다 `Fix-By: test` 먼저) → 고친 곳 다시 리뷰 → 검증(아래 9 전부, 판정 기준과 단언 대조 전수) → 브라우저 확인(SCR-017 실제 흐름) → 기록.

### 11. 시험·구현 지시문에 넣을 '자주 놓친 결함'

docs/architecture.md §8.6 '자주 놓친 결함' 목록 전부를 지시문에 넣고, 이 묶음에서 특히:

- 금액은 정확한 값까지 단언한다: 티켓별 공제액·환급액·합계, 결제사 취소 금액, `order_cancellation`의 `deduction_bp`·`refund_amount`. '성공'만 보지 않는다.
- 취소 ID는 표마다 고정이고 재시도에서 바뀌지 않는지, 결제사가 받은 취소가 표마다 1건인지(대역의 요청 수) 본다.
- 경계는 양쪽: 10·9·7·6·3·2·1·0일, 24시간 − 1ms/정각, 양도 마감 − 1ms/정각, 입장 시작 − 1ms/정각(마감 뒤 환급), 공연 시작 − 1ms/정각, 50ms·49ms, 10건·11건.
- 소유자·계정 대조: 다른 계정의 주문·표를 읽거나 취소하지 않는지, 두 RPC 모두 내부 토큰·호출자·UUID 검사를 하는지.
- 확인 우회가 없는지: `confirmCancelUnusedTickets` 없이 미룸 표시·취소에 닿는 길이 0인지(409는 토큰을 쓰지 않는다).
- 되돌림·차례: 미룸 표시 커밋 전에 결제사 취소가 나가지 않는지, 환급 완료 전에 계정이 `DELETED`가 되지 않는지.
- 장애 주입은 끊는 자리가 커밋 뒤까지 닿는지, 끊긴 사례가 실제로 있었는지 단언한다(답 유실·DB 시간 초과·ticket-svc 멈춤).
- 화면: 실제 흐름에서 목업 수를 보이지 않는지, 견적이 최종 확인 버튼보다 먼저 낭독되는지, 닫은 창의 늦은 409를 버리는지.
- 시험의 기간·한도 값이 코드 상수와 같으면 상수를 잘못 쓴 결함이 숨는다. 시험 값은 상수와 다르게 고른다.
- 시작 파일(`start.ts`)의 조립(티켓 포트·주소 없음 경고·새 RPC)은 시험 조립과 따로 띄워 본다.
