## 감독에게

1. **갈래 1과 겹침 없음**: 고칠 파일은 `packages/platform/test-int/tenant-rate-limit.int.test.ts` 하나다. BAT-059가 고치는 auth·control·service·stream-worker 쪽과 제품 코드(`src/`)는 건드리지 않는다. 검증 담당의 틀린 구현 표본(아래 6)은 `src/tenant-rate-limit.ts`·`src/redis.ts`에 잠깐 넣고 되돌리며 커밋하지 않는다.
2. **로컬에서도 재현된다**: 고치기 전 시험 파일만 부하 없이 20회 돌려 1회(`'597'≠'600'`, 같은 162행), CPU 부하 16스레드로 10회 돌려 1회(`'599'≠'600'`, CI와 같은 모습) 실패했다. 이 PC는 Docker Desktop을 거치고 다른 세션도 함께 돌아 같은 시험이 CI보다 훨씬 느리다(T1 9.4초, CI 0.6~1.1초). CPU 부하를 건 반복은 아래 2의 근거 3.
3. **정본 문구 하나(이 묶음에서 고치지 않음, 정리 목록 후보)**: `docs/api/guidelines.md` §6 '판정 시간과 장애'와 `docs/architecture.md` §4는 '20ms를 넘기면 세지 않고 통과한다'고 적는다. 실제로는 마감을 넘긴 요청이라도 이미 Valkey에 닿은 증가 명령은 서버에서 돌아 센다(아래 2의 표 '캐시 있음·막힘'). 세지 않는 것은 스크립트를 다시 보내기 전에 마감이 지난 경우뿐이다. '그 답으로 판정하지 않고 통과한다'로 읽으면 맞고, 한도가 덜 풀리는 쪽이라 위험은 없다. A 대상·보안 높음·통과 기준이 아니므로 정리 목록에 한 줄 적기를 권한다(ADR-0283 결정 6). 문안: "D-T50 ⑦ 열림 문구(W12-dt50): '세지 않고 통과'는 '판정에 쓰지 않고 통과'가 정확하다. 마감 뒤에 도착한 증가는 남을 수 있다(guidelines §6·architecture §4)".
4. **CI 확인**: 흔들림 판정의 근거는 여러 번 돌린 결과라 초안 PR CI 한 번보다 로컬 반복이 낫다. 그 파일의 반복은 로컬에서 하고(아래 5), 닿는 CI 잡(`node / node`의 platform 통합 단계 전체, Kafka 시험 포함)은 초안 PR CI 하나로 본다(ADR-0331 결정 7). 이 PC는 Kafka 네이티브 모듈이 응용 프로그램 제어에 막힐 수 있어 platform 통합 전체를 로컬에서 돌리지 않는다.

### 2. 원인과 근거

**원인: Valkey의 스크립트 캐시(서버가 한 번 받은 Lua 스크립트를 SHA-1 이름으로 기억해 두는 곳)가 빈 상태에서 판정 마감 20ms를 넘긴 요청은 카운터를 올리지 않고 통과한다.**

- 가드는 판정 하나를 `evalScript`에 마감 20ms로 맡긴다(`src/tenant-rate-limit.ts:116`). `evalScript`는 먼저 `EVALSHA`(이름으로 부르기)를 보내고, 서버가 `NOSCRIPT`(그 스크립트를 모름)로 답하면 같은 마감 안에서 `EVAL`(원문을 보내 돌리기)을 보낸다. 마감이 이미 지났으면 `EVAL`을 보내지 않는다(`src/redis.ts:156~165`, 163행). 가드는 마감·오류를 모두 열림으로 바꿔 200을 준다(`src/tenant-rate-limit.ts:118~123`).
- 그래서 새로 띄운 Valkey의 첫 요청이 20ms를 넘기면 `INCR`가 한 번도 돌지 않은 채 200이 나가고, 스크립트가 아직 없으니 다음 요청도 같은 길을 탄다. 한 요청이 마감 안에 `NOSCRIPT → EVAL`을 마칠 때까지 잃는 수가 이어진다(CI는 1건, 로컬은 3건).
- 스크립트가 서버에 있으면 마감을 넘겨도 이미 보낸 `EVALSHA`가 서버에서 돌아 센다. 수가 맞는다. `FLUSHDB`(`beforeEach`, 93~96행)는 키만 지우고 스크립트 캐시는 두므로, 새 컨테이너를 쓰는 파일의 첫 시험 T1만 이 꼴로 실패한다. 같은 실행에서 T1만 실패한 것과 맞는다.
- **정본과 대조**: `docs/api/guidelines.md` §6 '판정 시간과 장애'와 `docs/architecture.md` §4 '전역 레이트 리밋 서비스'는 20ms [가정]를 넘기면 통과(열림)이고 `tenant_rate_limit_total{result="unavailable"}`로 센다고 정한다. 제품은 그대로 한다. 시험이 '모든 요청이 20ms 안에 판정된다'를 전제로 정확한 수(600·601·429)를 단언하면서 그 전제를 잡지 않았다. BAT-173 계획 '동시 시험의 마감'은 T11(동시 601건)에서 같은 까닭으로 `timeoutMs: 5_000`을 주고 "20ms 열림은 T7(단위)·T8(실제 Valkey 멈춤)이 본다"고 정했는데, 나머지 셈 시험에는 그 처리가 빠졌다.

**다른 후보를 뺀 까닭**:

- **두 인스턴스의 연결 준비 경쟁**: `createHotRedis`는 연결이 끝난 뒤에 돌아오고(`src/redis.ts` `createHotRedis`), `bootPair`는 인스턴스를 차례로 띄운다. 연결이 없을 때의 `ClientOfflineError`는 마감 안에서 한 번 다시 보낸다. 이 길로 잃으려면 연결이 끊겨야 하는데 그 흔적이 없다. 아래 4의 ③(열림 없음 단언)이 이 길도 드러낸다.
- **시험의 셈 방법**: 요청은 하나씩 기다리고, 키는 다 끝난 뒤 다른 연결로 읽는다. 열림이 없으면 모든 `INCR` 답을 받은 뒤 읽으므로 순서 문제가 없다. 다만 **같은 뿌리의 두 번째 꼴**이 있다: 마지막 요청이 마감으로 먼저 답하고 그 `EVALSHA`가 서버에서 늦게 돌면 검사용 연결의 `GET`이 먼저 돌아 잠깐 599를 읽을 수 있다.
- **같은 뿌리의 세 번째 꼴(CI에서는 아직 안 났음)**: 캐시가 있어도 429여야 하는 요청(601번째 등)이 20ms를 넘기면 열림으로 200이 나가 429 단언이 깨진다. 이 PC에서 3,000회 중 1회 꼴이라 드물지만, 429 단언이 T1·T2·T3·T4·T8·T12에 있다. CPU 부하 반복에서 실제로 났다(근거 3).
- **시험 쪽 연결의 마감(같은 꼴, 부하에서만 봄)**: 시험이 키를 읽고 지우는 검사용 연결(`inspector`, 85행)도 명령마다 기본 마감 100ms(`REDIS_CALL_DEADLINE_MS`)로 부른다. CPU 부하 반복에서 `RedisDeadlineError: Redis 호출이 마감 100ms를 넘겼다`가 시험 파일 줄 없이 났다. 가드는 판정 마감을 열림으로 삼키므로 이 오류가 시험까지 올라올 길은 검사용 연결의 명령(`FLUSHDB`·`GET` 등)뿐이다. 제품 판정과 상관없는 시험 장치의 마감이다.

**운영 영향(결함이 아닌 까닭)**: 파드마다 Valkey 스크립트 캐시가 빈 뒤(재시작·장애 조치) 첫 판정이 20ms를 넘기면 그 몇 건이 세지지 않는다. 정본이 받아들인 열림이고, 이 카운터의 유실 등급은 C(`docs/data.md` §3 유실 등급 표: 잃으면 그 창의 테넌트 한도가 풀리고 게이트웨이의 계정당 600회/분이 지킨다)다.

### 4. 흔들림을 없애는 방법(시험 담당)

① **셈 시험의 판정 마감을 넉넉히 준다.** `boot()`(103~117행)가 `timeoutMs`를 받지 않으면 5,000ms를 넘긴다(T11과 같은 값, 이름 붙은 상수와 까닭 주석 한두 줄). 이 파일의 셈 시험은 `INCR` 원자성·600/601 경계·두 인스턴스 합계·키 수명·배선을 보지 20ms 열림을 보지 않는다. 20ms 기본값과 그 열림은 단위 시험 'D-T50 ⑦ 한도는 600회/분, 창은 60초, 판정 마감은 20ms다'(`test/tenant-rate-limit.test.ts:67`)·'D-T50 ⑦ 판정 마감은 넘겨 받은 값(기본 20ms)이고 답이 없으면 통과하며 unavailable로 센다'(같은 파일 106행)와 아래 ②가 본다.

② **T8 'D-T50 ⑦ Redis가 끊겨도 통과하고 돌아오면 다시 센다'는 열림이 주제라 마감을 짧게 따로 준다**: `boot('partner-int', { timeoutMs: 250 })` [가정]. 멈춘 Valkey는 답하지 않으므로 어떤 유한한 마감에서도 열림이 반드시 난다. 1초 안에 끝난다는 단언(252행)과 `unavailable` 1·5xx 없음 단언은 그대로 둔다. 250ms는 복구 뒤 600건+429 단언의 여유(판정 p99의 100배 이상)를 위한 값이다.

③ **열림이 없었음을 먼저 단언한다.** 셈을 단언하는 시험(T1·T2·T3·T4·T5·T6·T9·T12. T11은 298행에 이미 있음)에서 키 값(`keyOf`)이나 429를 단언하기 앞에, 그 시험이 띄운 인스턴스마다 `tenant_rate_limit_total{service,result="unavailable"}` 표본이 없음을 본다. T11 297~299행 꼴을 도우미 하나로 묶어 쓴다. 열림이 또 나면 '599≠600' 대신 '열림 n건'으로 실패해 원인이 바로 보인다.

④ **시험마다 스크립트 캐시를 비운다.** `beforeEach`(93~96행)의 `FLUSHDB`(94행) 다음에 `SCRIPT FLUSH`를 더한다. 그러면 모든 시험의 첫 요청이 `NOSCRIPT → EVAL` 길을 지나고(지금은 파일의 첫 시험만), 시험 차례나 `-t`로 골라 돌리기와 상관없이 바탕이 같아진다. ①의 넉넉한 마감이 있어 이 길도 결정적으로 센다. T11의 첫 요청(294행)은 그대로 스크립트를 올리는 몫이다(주석의 'NOSCRIPT로 실패하지 않게'는 그대로 맞다).

⑤ **검사용 연결의 명령에도 넉넉한 마감을 준다.** `inspector.command(…)`(94·140·141·218·219·222·223·267·278·280행과 ④의 `SCRIPT FLUSH`)를 `{ deadlineMs: 5_000 }`을 넘기는 도우미 하나로 바꾼다. 시험이 상태를 읽고 바꾸는 장치이지 판정 대상이 아니다. T8의 복구 확인 `PING` 반복(259~266행)은 멈춤이 풀렸는지 보는 자리라 짧은 마감을 그대로 둔다.

- 시험 이름은 바꾸지 않는다(장부·대조 스크립트가 이름으로 찾는다). 새 시험은 없다. ④로 T5('401·403 요청은 세지 않고 유효한 요청만 센다')의 마지막 단언이 '캐시가 빈 서버의 첫 유효 요청도 1로 센다'를 겸한다.

### 7. 이번에 안 함

- **제품 코드**: 20ms [가정]와 열림은 정본대로다. 서비스 시작 때 스크립트를 미리 올리는 것(`SCRIPT LOAD`)은 Valkey 재시작·장애 조치 뒤 캐시가 다시 비므로 근본 해결이 아니고 정본에 없는 변경이라 하지 않는다.

- 다른 통합 시험의 같은 꼴(짧은 Redis 마감 아래 정확한 수 단언) 전수 점검: 정리 목록 후보.
