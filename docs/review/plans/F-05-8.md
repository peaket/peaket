# F-05-8 계획 — 찜 목록·CS 모바일 배치·공연 당일 입장 탭

- 기능: F-05-8(현장 입장), 등급 B(화면·일반 기능. 장부 항목 모두 B). 단계 `GAT-260`(wbs 5.6.2: 관심 공연·알림 신청 화면 SCR-054, 찜 목록 서버, 탈퇴·병합 때 찜 정리)·`GAT-340`(wbs 5.8.5: CS 처리함·승인 업무·회차 취소 판정·팬 조회의 휴대폰·태블릿 배치)·`GAT-360`(wbs 5.7.2: 공연 당일 관제 입장 탭 SCR-029, 파트너 현장 운영 탭 SCR-037, 신선도·중복 입장 급증 경보).
- **동결 로컬 범위**: 이 기능은 v1 배포 범위 밖이다(ADR-0373, BUILD_ORDER 상태 `동결`). 이 가지(`freeze/lane3-F-05-8`)는 `develop`·`release`에 합치지 않고, 이 가지에만 쌓아 로컬에서 확인 가능한 몫을 남긴다. 배포 차트·운영 값·v1 완성 판정에는 넣지 않는다.
- 기준: `origin/develop` `333da1253`. 작업 폴더 `D:/ticketpass-freeze-F-05-8`, 가지 `freeze/lane3-F-05-8`.
- 차례: 시험 먼저(계획 → 시험 → 기준 트리 실패 확인 → 구현 → 게이트). B등급이라 구현 뒤 리뷰·틀린 구현 검사는 하지 않는다(ADR-0372·ADR-0373). 이 파일은 단계마다 그 절만 고친다.
- 담당: 이 freeze 가지는 한 세션이 계획·시험·구현을 이어서 맡는다(동결 로컬 범위, `Agent-Session: lane3-freeze-opencode`). 그래서 담당 표의 세션 ID가 같고, 역할 확인의 '서로 다른 세션' 조건은 이 가지에서 통과하지 못한다. 합치지 않는 가지라 그 조건을 적용하지 않는다.

## 3. 정본에 쓴 것(이 계획 커밋)

- `docs/BUILD_ORDER.md` F-05-8 행: 장부 범위를 이 기능이 닿는 항목으로 좁힌다. 동결 로컬 범위 문구와 이 계획 경로를 적는다.
  - 새 범위: `FE-T37, FE-T43, O-T20, FE-T31, auth:v5.0.0-8.2.2, frontend:v5.0.0-3.5.4`.
  - 뺀 것: `docs/features/offline-gate.md`·`docs/features/notify.md`·`docs/security/asvs/offline-gate.md`·`docs/security/asvs/auth.md`·`docs/frontend.md` 문서 통째 범위(563항목). 이 기능이 닿지 않는 스캐너 판정·발송 원장·법정 ASVS 행을 뺀다. GAT-340·360의 배치는 FE-T31이, GAT-360의 신선도 경보는 O-T20이, 찜 화면은 FE-T37이 판정한다. 탈퇴·병합 찜 정리는 새 시험 이름을 `FE-T37`에 붙이지 않고 `GAT-260` 시험 이름으로 따로 둔다(장부 범위 밖의 보조 시험).
- 정본에 새 값을 더하지 않는다. 서버 경로·응답 모양은 openapi `listWishes`가, 화면 상태·문구는 d5 §5.28이, 저장소 키는 docs/frontend.md §3.12(`peaket.wishQueue`)가 이미 정한다.
- **정본 빈칸 하나(추천안으로 정한다)**: `GET /v1/wishes` 커서의 뜻이 정본에 없다. `(찜한 시각, 공연 ID)` 내림차순의 마지막 줄을 base64url `v1:<epoch ms>:<productionId>`로 싣는다(guidelines §3, 같은 시각이면 공연 ID로 가른다). 화면은 커서를 해석하지 않고 그대로 돌려준다.
- **정본 빈칸 둘(추천안으로 정한다, 2026-11-24 IR-07로 다듬음)**: 오프라인 찜 대기열의 재전송 간격·횟수. `online` 사건과 화면이 다시 보일 때(`visibilitychange`) 한 번씩, 지수 백오프 없이 줄마다 최대 3회 [가정] 보낸다. 줄에 시도 횟수(`attempts`)를 두고 보낼 때마다 1씩 올리며, 3에 닿으면 자동 전송에서 건너뛰고 '저장 대기'로 남긴다. 다시 누르면 횟수가 0으로 돌아간다. **지우는 때는 서버가 204를 준 뒤뿐이다.** 401은 지우지 않고 멈추며, 4xx·5xx·끊김도 지우지 않고 시도 횟수를 올린 뒤 멈춘다. docs/frontend.md §4.2.4에 이미 있는 '오프라인에서 누른 찜' 문구와 충돌하지 않는다.
- **정본 빈칸 셋(추천안으로 정한다)**: 찜 목록 카드의 `badges`. `search_document`에 배지 원천이 없으므로 이번에는 싣지 않는다(계약에서 선택 칸). 필요하면 `ProductionCard.badges`를 채우는 몫을 뒤로 넘긴다.

## 4. 손댈 파일(구현 담당)

**core-svc(GAT-260 서버)**

- `domain/ports.ts`: `WishRow`·`WishQuery`와 `listWishRows(accountId, query)` 포트. `after`는 `(createdAt, productionId)`, `productionIds`·`limit`을 받는다.
- `adapters/memory-catalog-repository.ts`: 계정의 찜을 `createdAt` 내림차순·공연 ID 내림차순으로 고르고, 공개(`isPublic`)이며 취소되지 않은 회차가 있는 공연만 남긴다. `productionIds`가 있으면 그 교집합만. `limit+1`까지 준다.
- `adapters/db/drizzle-catalog-repository.ts`: `wish`를 `production`과 잇고 `sale_approved_at is not null and sale_review <> 'SUSPENDED'`, `exists(event status <> 'CANCELLED')`로 거른다. 커서는 `(w.created_at, w.production_id) < (after.createdAt, after.productionId)`(내림차순), `limit+1`. `productionIds`는 `= any(...)`.
- `domain/search.ts`·`adapters/memory-search-index.ts`·`adapters/db/drizzle-search-index.ts`: `cardsByIds(ids): Promise<SearchCard[]>`. DB는 `search_document_source_at(now(), ids)`를 읽어 지금 값으로 만든다(동기화 지연 없음). 메모리는 스냅숏 문서에서 고른다.
- `migrations/0048_wish_list_read.sql`: `GRANT EXECUTE ON FUNCTION search_document_source_at(timestamptz, uuid[]) TO core_search`(읽기 전용 검색 연결이 카드 원천을 부를 수 있게). 표·칸 변경 없음.
- `application/wish.ts`: `list(accountId, q)` — 커서 해석·limit 1~100·`productionIds` 50개 검사(400 `invalid-query`), 찜 줄과 카드를 잇고 빠진 카드는 건너뛴다. `nextCursor`는 마지막으로 돌려준 줄.
- `inbound/wish.controller.ts`: `@Get('wishes')`, `@Roles(['fan'])`, `@Header('Cache-Control','private, no-store')`, `@ContractQuery(ListWishesQueryParams)`.
- `catalog.module.ts`: `Wishes`에 `SEARCH_INDEX` 주입(이미 `shared`에 있다). `WISH_LIST` 포트를 새로 만들지 않고 `CATALOG_REPOSITORY`에 메서드를 더한다.

**core-svc(탈퇴·병합)**

- `consumers/index.ts`·`consumers/start.ts`: 한 토픽에 처리기 여럿을 부르는 합성 처리기(후기 + 찜). 보류 표는 그대로 `held_event` 하나다.
- 새 `catalog/inbound/account-withdrawn.handler.ts`: `ReviewWithdrawnEvent`와 같은 세 칸만 읽고 `wishes.purgeWithdrawn(accountId)`를 부른다. 계정 ID는 소문자로 맞춘다.
- 새 `catalog/inbound/account-merged.handler.ts`: `identity.accounts-merged`(asyncapi `AccountMerged`)를 읽어 `Wishes.moveMerged(primary, absorbed, mergeId)`를 부른다. `merge_id` 멱등 표(새 `account_merge_wish` 표) 또는 `wish`의 `(accountId, productionId)` 유니크와 `ON CONFLICT DO NOTHING`으로 두 번 처리해도 한 번과 같다. 표를 더하면 마이그레이션 0049와 docs/data.md에 적는다.
- `adapters/db/drizzle-catalog-repository.ts`·memory: `purgeWithdrawn`·`moveMerged`.
- `main.ts`·`consumers/start.ts`: `CORE_TOPICS`에 `identity.accounts-merged`를 더하고 그룹 하나로 읽는다(파티션 키 계정 ID).
- gRPC `AccountMergeCheckService`(`CheckAccountMerge`): 이 기능에서 `absorbed_wishes`를 채운다. `services/core-svc/src/main.ts`에 gRPC 서버를 새로 띄우는 몫은 `PEAKET_CORE_GRPC_PORT`·헬스·종료 차례·웨이포인트가 함께 필요해 이 freeze 가지에서는 **시험과 구현을 서버 조립까지** 하고, 실제 포트 기동은 다음 몫으로 넘긴다(§10). proto·계약은 이미 있다.

## 5. 공개 인터페이스

- HTTP: `GET /v1/wishes?productionIds=&cursor=&limit=`(openapi `listWishes`). 응답 `{ items: ProductionCard[], nextCursor: string | null }`. 401, 400 `invalid-query`.
- 저장소: `peaket.wishQueue`(localStorage, docs/frontend.md §3.12). 항목은 `{ productionId, action: 'PUT' | 'DELETE', at, attempts }`이고 `attempts`는 자동 재전송 시도 횟수(0~3)다.
- 서버 포트(시험이 부르는 모양): `CatalogRepository.listWishRows(accountId, { productionIds?, after?, limit })`, `SearchIndex.cardsByIds(ids)`, `Wishes.list(accountId, query)`. 이름은 구현 담당이 정하고 `catalog/index.ts`로만 내보낸다.
- Kafka: `identity.accounts-withdrawn`(기존), `identity.accounts-merged`(새 소비).

## 7. 실패 시나리오(이 기능이 반드시 다루는 것)

- 로그인하지 않은 요청·토큰 갱신이 실패한 요청: 401. 화면은 찜 줄을 숨기고 목록 대신 로그인으로 보내지 않는다(찜 목록은 개인 화면이라 401이면 로그인 화면).
- 남의 찜·없는 공연 ID를 `productionIds`에 넣음: 내 찜만 돌아온다(남의 찜 존재 여부를 알리지 않는다, ASVS 8.2.2).
- 찜한 공연이 그사이 판매 승인 취소·중지·회차 취소: 목록에서 빠진다. 커서가 그 줄을 가리켜도 다음 쪽은 이어진다.
- 같은 찜을 두 번 저장(오프라인 재전송): 처음 찜한 시각이 유지되고 목록에 한 번만 나온다.
- 오프라인에서 찜/해제를 누름: 화면은 바로 바뀌고 `peaket.wishQueue`에 남는다. 온라인이 되면 다시 보내고, 401이면 큐를 지우지 않고 로그인으로 보낸다. 4xx·5xx·끊김이면 시도 횟수를 올려 남겨 두고 다음 기회에 다시 보낸다. 3회에 닿으면 자동 전송만 멈추고 카드에 '저장 대기'로 남긴다(지우는 때는 204를 받은 뒤뿐).
- 같은 공연을 오프라인에서 찜했다 풀었다: 마지막 동작만 남아 서버 저장이 0건이거나 삭제 1건이다(중복 저장 0건).
- 탈퇴·병합 사건이 두 번 옴: 찜은 한 번만 지워지거나 옮겨진다(멱등). 병합에서 대표 계정에 같은 찜이 이미 있으면 하나만 남는다.
- 목록 조회 중 DB·검색 원천 장애: 5xx(Problem 형식). 화면은 저장된 목록이 없으면 '불러오지 못했습니다'와 [다시 시도], 있으면 저장된 목록과 오프라인 배너다.
- 화면 폭 320px·태블릿 2열: CS 화면·관제 입장 탭·파트너 현장 운영 탭에 가로 스크롤이 생기지 않는다(FE-T31).

## 8. 완료의 정의

1. `GET /v1/wishes`가 openapi대로 동작한다(목록·`productionIds`·커서·limit·400·401·`no-store`). 단위·통합 시험이 통과한다.
2. SCR-054 관심 공연 탭이 실서버 목록과 오프라인 대기열로 동작한다. 목업은 API 주소가 없는 퍼블리싱 빌드에만 남는다.
3. 탈퇴·병합 사건의 찜 정리·이동이 멱등하게 동작한다(단위·통합). `CheckAccountMerge.absorbed_wishes`는 유스케이스까지 구현한다(포트 기동은 다음 몫).
4. GAT-340·360 화면이 정본 배치·실제 값으로 바뀌고, 원천이 없으면 표지를 남긴다.
5. 게이트: 닿는 단위·통합, typecheck, lint, doc-check, `ledger --batch F-05-8 --require`(가능한 범위), 계약 생성물이 바뀌면 `gen:check`·api-client 시험.
6. 이 가지는 `develop`·`release`에 합치지 않는다. v1 배포 판정에도 넣지 않는다.

## 9. 기존 찜·월렛·SW와의 경계

- 찜은 공연 단위 개인 값이다(ADR-0093). 홈·공연 상세는 이미 같은 `GET /v1/wishes`를 부르므로 이 기능은 서버만 채우면 그 화면들이 함께 살아난다. 홈은 401이면 찜한 공연 줄만 숨긴다.
- 월렛(`/my/tickets`)의 `peaket-wallet` IDB·월렛 서비스 워커(`/my/tickets/sw.js`)에는 찜을 넣지 않는다. 찜은 `localStorage` `peaket.wishQueue`(보내지 못한 동작만)와 서버 목록으로만 다룬다. 서비스 워커 캐시에 개인 찜 목록을 넣지 않는다.
- 웹 푸시 워커(`/push/sw.js`)와 구독은 이 기능이 건드리지 않는다. FE-T43는 회귀만 본다.
- 관제 입장 탭은 팬 트래픽과 다른 경로다. gw-fan·gw-ops 경계를 넘지 않고, ops-svc가 ticket-svc에서 읽은 값을 콘솔에 준다.

**확인했으나 문제 없음**

- ① 판정 기준·구현: 목록 차례(최근 찜, 같은 시각이면 공연 ID 내림차순), `productionIds` 교집합·커서 없음, `nextCursor`가 마지막으로 **읽은** 줄, 400(limit 101·커서·50개 초과)·401·`Cache-Control: private, no-store`가 정본과 같다. 메모리·DB가 `isPublic`·취소 회차 조건을 같게 건다. 단위 5/5·통합 4/4(계획 기록)가 차례를 단언한다.
- ② 소유권·인증: `@Roles(['fan'])`과 `me.accountId`로만 거르고, 남의 찜·남의 공연 ID를 `productionIds`에 넣어도 내 찜만 온다(ASVS 8.2.2 시험). PUT·DELETE도 계정 ID로만 지운다. 커서에는 공개 값만 있고 다른 계정 값이 없다. limit 100·productionIds 50의 거절 경계(101·51)는 시험이 본다(허용 경계는 IR-11).
- ③ 탈퇴·병합: 탈퇴는 그 계정만 지우고 다시 받아도 0건이다. 병합은 두 계정 잠금을 ID 차례로 잡고 `INSERT … ON CONFLICT DO NOTHING`+흡수 행 삭제로 같은 찜을 하나만 남기며 처음 시각을 지킨다. 두 번 처리해도 흡수 계정 0건·대표 계정 중복 0건(단위·실제 DB). 합성 처리기는 후기·찜을 차례로 부르고 한쪽 실패 시 사건을 보류해 둘 다 다시 부른다(둘 다 멱등). 계정 ID는 소문자로 맞춘다.
- ④ 오프라인 대기열: 같은 공연은 마지막 동작 하나만 남고(찜→해제 DELETE, 해제→찜 PUT), 깨진 저장값은 버린다. 401은 큐를 지우지 않고 멈추며 5xx·예외(끊김)는 그 동작부터 남긴다. 204만 지우는 기본 경로와 중복 0건은 시험이 본다(4xx 규칙은 IR-07).
- ⑤ 로그·개인정보·캐시: 처리기 로그에는 `eventKey`·`mergeId`·`purged`/`moved` 수만 있고 계정 ID·pid·토큰·쿠키가 없다. `GET /v1/wishes`는 개인 응답에 `private, no-store`를 붙이고, 찜 목록은 클라이언트 요청으로만 받아 서버 HTML·서비스 워커 캐시(범위 `/my/tickets`)에 들어가지 않는다. `peaket.wishQueue`에는 공연 ID·동작·시각만 있고 로그아웃 정리 목록(`features/session-cleanup/keys.ts`)이 지운다.
- ⑥ 시험이 덮지 않는 곳: IR-01·02·03·04·10·11이 그 목록이다. 그 밖에 `putWish`와 `moveWishes`의 겹침, 두 병합의 반대 방향 동시 실행은 시험이 없으나 잠금 차례(ID 정렬)와 `ON CONFLICT`를 읽어 교착·중복은 없어 보인다. gRPC 미기동은 IR-04다.
