# BAT-350 계획(GAT-010 남은 몫: 월렛 기기 키 서버 등록 잇기·스캐너 keyId 맞물림·런타임 캐시 판)

- **무엇**: `docs/BUILD_ORDER.md:542` GAT-010의 '남은 것' 세 가지를 끝낸다(ADR-0282: 단계 줄이 범위의 정본). ① 월렛 등록 스위치를 없애고 ticket-svc `POST /v1/tickets/{ticketId}/device-keys`에 늘 등록하며, 실패를 나눠 처리한다. ② 월렛이 만든 공개키의 keyId가 서버·스캐너 목록·스캔 대조까지 같은 값으로 맞물리는지 시험 벡터로 끝까지 확인한다. ③ 서비스 워커 런타임 캐시에 빌드 판을 붙이고, 새 판이 활성화될 때 옛 판 캐시를 정리한다.
- **쉬운 말**: 지금 월렛은 '입장용 등록'을 눌러도 키를 휴대폰에만 두고, 서버에 알리지 않은 채 QR을 보인다. 서버가 모르는 키라 게이트에서 거절된다. 이 묶음은 키를 서버에 등록한 뒤에만 QR을 보이게 하고, 등록이 끊겼을 때 같은 키로 다시 보내도 서버가 막지 않게 한다. 또 새 판 워커가 옛 판 화면 조각을 섞어 내지 않게 캐시 이름에 판을 붙인다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane2`, 가지 `feature/lane2-BAT-350`, 출발 `origin/develop` `de4d6a67e`(2026-11-21). 계획 담당 `lane2-bat350-plan`(claude-opus-5-5). 제품·시험 코드는 쓰지 않았고 Docker·브라우저·측정도 돌리지 않았다. 읽은 것은 지시서가 가리킨 정본 줄 범위와 §1 표의 코드다.
- **등급·차례**: B(BUILD_ORDER 144행). 정방향(`Batch-Order: impl-first`, ADR-0281 결정 5), B 짧은 고리(ADR-0283 결정 2), ADR-0331(구현 전 트리 실패 확인은 버그 재현 시험만, B 틀린 구현 표본 10개 이하, 리뷰 중간·낮음은 정리 목록, 브라우저 확인은 웨이브 끝).
- **한 줄 결론**: 서버 경로·표·게이트웨이 경로·스캐너 목록의 `keys`·keyId 대조는 이미 있다. 남은 일은 월렛 잇기, 서버의 '같은 키 다시 등록' 한 규칙, 런타임 캐시 판이다. 정본 빈칸 다섯을 이 커밋에서 추천 적용으로 정했다(ADR-0336). 2.5일 안에 든다(월렛 0.75·서버 0.25·캐시 0.5·시험 0.75 [가정]).

## 감독에게

1. **장부 범위를 좁혔다(이 커밋, `docs/BUILD_ORDER.md:144`)**: `docs/features/offline-gate.md`·`docs/security/asvs/offline-gate.md` 전체(232항목, BAT-395·400·405·430 등과 겹치고 `--require`가 183개로 실패)에서 `O-T13, O-T44, O-T45, O-T46`(17항목)으로 바꿨다. §8.6 3의 '범위를 좁혀 뺀다'와 BAT-182(104행) 선례를 따랐다. 뺀 항목은 위 묶음들의 범위에 그대로 남아 외톨이가 없다.
2. **notes 두 줄의 정할 곳(이 커밋은 고치지 않았다)**: `docs/review/ledger-notes.md:93` O-T23(온라인 스캐너끼리 입장 상태 공유)은 '다른 단계 → BAT-350'인데, 월렛이 아니라 GAT-180 '입장 상태 공유'(BAT-440, 갈래 3) 몫이다. BAT-440으로 옮기기를 추천한다. 그대로 두면 이 묶음이 닫힌 뒤 가리킬 곳이 없다. 같은 표 94행 O-T32는 사유('ticket-svc 경로가 없어')가 낡았다. 데스크톱 안내는 GAT-030(→ GAT-020, BAT-395) 몫이라 정할 곳을 GAT-020으로 바꾸기를 추천한다. 승인하면 시험 담당이 시험 커밋에서 두 줄을 고친다.
3. **ticket-svc를 고친다(갈래 3 서비스)**: '같은 키 다시 등록'(offline-gate §2)은 이 묶음의 통과 기준(응답을 잃은 월렛의 다시 보내기)에 걸려 여기서 한다. 표·마이그레이션은 바꾸지 않는다(0010~0011 안 씀). 갈래 3의 지금 묶음(BAT-450·455)은 이 파일들을 건드리지 않는다.
4. **ticket-svc 통합 시험은 CI가 돌리지 않는다**: `ci-node.yml`의 통합 시험 목록에 ticket-svc가 없다. 그래서 Drizzle 저장소 고침은 로컬 Docker(잠금 `lock.sh`)로 본다. CI에 넣는 일은 정리 목록 후보다(§12).
5. **꼬리말**: `Co-Authored-By`를 다른 꼬리말과 같은 덩이에 둔다. 빈 줄로 떼면 `tools/ci/roles-check.mjs`가 마지막 문단만 꼬리말로 읽어 `Role` 등을 못 찾는다(갈래 5 BAT-600 선례).
6. **OPEN 후보는 없다.** '확인 뒤에만 QR'(ADR-0336 결정 2)을 방향 변경으로 본다면 문안: "OPEN: 월렛이 서버 등록 확인 전에도 QR을 보일까? (가) 확인 뒤에만(추천, 모르는 키의 QR은 게이트에서 `KEY_UNKNOWN`) (나) 바로 보이고 '등록 확인 전' 표시".

## 3. 범위

### 3.1 하는 것

1. **월렛 등록 잇기**(frontend §4.2.4 세부대로): 스위치 없앰, 버튼 → 키 만들기 → `LOCAL` 저장 → ISSUE 보내기 → 응답 keyId 대조 → `REGISTERED`일 때만 QR. 실패 세 갈래(다시 보내기·다시 확인·거절), 부품이 붙을 때·[다시 시도]·`online` 사건 때 같은 공개키로 다시 보내기, 등록된 키는 이 화면에서 지우지 않기.
2. **서버 같은 키 다시 등록**(offline-gate §2): Drizzle·메모리 저장소 둘 다, 티켓 행 잠금 안에서.
3. **keyId 맞물림 확인**: 시험 벡터로 월렛 keyId·QR v1·서명 = 서버 keyId·압축 공개키 = 스캐너 목록 `keys` = 스캔 대조 `PASS`/`KEY_UNKNOWN`.
4. **런타임 캐시 판**(frontend §5.4 세부대로): `wallet-shell-{판}` 하나, 판은 미리 저장 판과 같은 값을 빌드 때 워커에 넣기, 꼴 검사, 활성화 때 다시 받기·지우기 뒤 `clients.claim()`.
5. **개발용 가짜 API**: `apps/web/scripts/mock-api`에 `POST /v1/tickets/{ticketId}/device-keys`를 더한다. 스위치를 없애면 가짜 API를 쓰는 개발 서버·웨이브 끝 브라우저 확인에서 등록이 404(거절 → 키 지움)로 끝나기 때문이다.

### 3.2 빼는 것(범위 밖)

- 재발급(REISSUE)·재인증 시트(CMP-064)·부스·iOS 홈 화면 PoC·데스크톱 안내('그래도 이 기기에 등록')는 GAT-020(BAT-395) 몫이다. 403 `reauth-required`는 '다시 확인 필요'에서 멈춘다.
- 스캐너 앱의 QR v1 풀기·서명 확인·압축 공개키 가져오기는 GAT-140 '오프라인 판정 10단계'(갈래 3) 몫이다. 이 묶음의 벡터 파일을 그 시험이 쓰면 된다.
- 양도·돌려주기의 TRANSFER 등록(BAT-410), 취소된 티켓의 등록 막기·폐기된 같은 키 다시 등록(§12 정리 목록 후보).
- ASVS offline-gate 표 행(장부 범위에서 뺐다. 행의 코드 영역이 대부분 스캐너·identity·ticket이고 다른 묶음 범위에 남는다).
- codeql #32는 갈래 4 W12-ci-sec 몫이다. 초안 PR CI의 security-scan 실패는 이 묶음 탓으로 보지 않는다.

### 3.3 장부 범위와 확인 명령

- 범위 칸: `O-T13, O-T44, O-T45, O-T46` → `node tools/ci/ledger.mjs --batch BAT-350`: 17항목(자동 시험 1(O-T13), 빈칸 16, 등급 B 17). 이 커밋에서는 빈칸 16이라 `--require`가 실패하는 것이 정상이다.
- 게이트: `node tools/ci/ledger.mjs --batch BAT-350 --require`(시험 커밋 뒤 통과해야 한다). 근거: §8.6 2(`--batch <묶음> --require`), BAT-182 선례(범위 칸을 ID로 좁힌 뒤 `--batch`로 확인).
- O-T13은 이미 자동 시험(`qr-v1.test.mjs`)이고 이 묶음이 서명 경로를 바꾸지 않는다. 회귀로만 본다.

- `scripts/service-worker.mjs`: `swRevision(env)`는 꼴 밖이면 던진다. `serwistOptions(env).esbuildOptions.define`에 판 하나(이름은 구현이 정하고 이 절에 적는다).
- HTTP: `POST /v1/tickets/{ticketId}/device-keys`의 모양은 바뀌지 않는다(S1은 201 `{keyId}`).
- 가짜 API: `GET /__mock/state?deviceKey=…`, 응답은 계약 Zod를 지난다.
- 구현 담당이 정한 것(2026-11-21, `lane2-bat350-impl`. 위 이름·모양은 그대로이고 아래를 더했다):
  - 판 이름: `serwistOptions(env).esbuildOptions.define.__WALLET_CACHE_VERSION__ = JSON.stringify(판)`. 이름은 `scripts/service-worker.mjs`의 `WALLET_CACHE_VERSION_DEFINE`로도 내보낸다. `swRevision`은 지금처럼 빈 값을 없는 것으로 보고 다음 값으로 넘어간다(`{ PEAKET_DEPLOYMENT_ID: '' }` → 커밋 → `wallet-dev`). 그래서 '빈 값'은 `walletCacheName('')`·`isWalletCacheVersion('')`이 거절하고, `swRevision`은 `' '`·`a/b`·65자 같은 꼴 밖 값에서 던진다.
  - `enrollDeviceKey(ticketId, options?)`·`syncDeviceKeyRegistration(ticketId, options?)`의 둘째 인자 `{ offline?: boolean }`(화면의 오프라인 미리보기). 생략하면 `navigator.onLine === false`만 본다. 같은 티켓의 `sync`가 겹치면 요청 하나로 묶는다. 이미 이 티켓 키가 있으면 `enrollDeviceKey`는 새 키 없이 `sync`와 같다.
  - `register.ts`는 api-client를 거치지 않는 손 호출이다(frontend §4.1 'api-client 밖의 호출', `shared/lib/timed-fetch`·`token-refresh`·`refresh-lock`). 그래서 `globalThis.fetch`만 바꿔 시험한다. 요청은 `POST {ORIGINS.api}/v1/tickets/{id}/device-keys`, `credentials: 'include'`, 401이면 `POST {ORIGINS.api}/v1/identity/access-tokens` 한 번 뒤 다시 한 번. 더 내보낸 것: `contractPublicKeyJwk(jwk)`(계약 칸 `kty·crv·x·y·ext·key_ops·alg`만), 형 `DeviceKeyRetryReason`. `ORIGINS.api`는 부를 때마다 읽는다(시험은 `shared/config/origins.ts`의 `ORIGINS.api`를 바꿔 B10을 본다).
  - 정본이 정하지 않은 응답: 201이 아닌 2xx·409 같은 계약 밖 상태는 키를 지우지 않고 `retry`(`server`)다. 토큰 갱신이 일시 장애(갱신 401이 아님)면 `retry`(`network`)다. 403은 `type`이 `reauth-required`일 때만 `needs-reauth`이고 그 밖(`booth-not-authorized`·`transfer-not-allowed`·`type` 없음)은 `rejected`다.
  - `rotateWalletCaches`는 주소를 옛 캐시에서 읽은 차례로 하나씩 받는다. 시작부터 `now()`로 재고, 본문까지 받은 뒤 `경과 >= budgetMs`면 넣지 않으며(9,999ms는 넣고 10,000ms는 넣지 않는다), 한도가 지나면 남은 주소는 받지 않는다. 받은 응답은 200·이동 아님·`no-store` 없음일 때만 넣는다. `warmed`는 넣은 주소(차례 그대로), `deleted`는 지운 캐시 이름이다.
  - 가짜 API: `apps/web/scripts/mock-api/tickets.mjs`의 `deviceKeyIdOf(jwk)`(keyId 계산)·`createTicketsMock({ state })`. 같은 티켓의 다른 키는 403 `reauth-required`(ticket-svc와 같다), `deviceKeyReset=1`은 등록한 키를 잊는다. 비로그인(`fan=guest`)은 401.

### 확인했으나 문제 없음

- **권한(다른 계정·같은 키 순서)**: Drizzle·메모리 저장소 모두 티켓 행을 읽고(`for update`) 보유자를 견준 **뒤에** 같은 키를 본다. 다른 계정·없는 티켓은 같은 JWK여도 404이고, 같은 키 판정으로 남의 티켓의 유효 키 여부를 알아낼 길이 없다(단위·HTTP·Drizzle 시험이 다른 계정 404를 본다). 같은 키는 keyId(SPKI SHA-256 앞 8바이트)로 견주며 정본 글과 같다. 같은 keyId의 다른 공개키를 만들려면 2^64 수준의 두 번째 역상이 필요하고, 그래도 보유자 자신의 요청이라 바뀌는 것이 없다.
- **동시 실행**: 같은 키 판정과 유효 키 읽기가 티켓 행 잠금 안이고(READ COMMITTED에서 잠금 뒤 문장은 앞 트랜잭션의 커밋을 본다), 부분 유니크 `device_key_active_key`가 둘째 가드다. 응용 계층 머리 주석이 잠금 밖에서 보지 않는 까닭을 적었다. 메모리 저장소는 같은 순서다.
- **같은 키의 부수 효과 없음**: 새 행·폐기·`scanner_change`·24시간 셈을 건너뛰고 입장 시작 확인보다 앞이다(정본 §2). 응답 모양은 201 `{keyId}` 그대로라 계약 생성물은 설명 한 줄만 바뀌었다.
- **개인키**: 키 만들기(`extractable=false`)는 바뀌지 않았고, 보내는 JWK는 계약 칸(`kty·crv·x·y·ext·key_ops·alg`)만 고른다. 시험 벡터 파일에 개인키 칸이 없다.
- **화면과 서버 잇기**: 운영 빌드의 `ORIGINS.api`는 값이 없으면 `https://api.peaket.example`이라 비지 않고, 주소 없는 경우(`localOnly`)는 `next dev`뿐이다. 요청은 `credentials: 'include'`·`cache: 'no-store'`·`redirect: 'error'`·쓰기 15초이고, 401은 갱신 잠금 안에서 한 번 갱신 뒤 한 번 더, 갱신 거절은 로그인, 갱신 일시 장애는 다시 보내기다. gw-fan 경로와 CORS 허용 헤더(`Content-Type`·`X-Reauth-Token`)가 있다. 오프라인(`navigator.onLine === false`·미리보기)에서는 보내지 않고, `REGISTERED` 키는 오프라인에서도 바로 QR이다(O-T13 회귀 없음).
- **QR은 등록 확인 뒤에만**: `DeviceQr`의 `qrKey`는 `phase === 'status' && status.phase === 'ready'`일 때만이고, d5 §5.13 세 상태의 글이 정본과 같다. 늦게 끝난 앞 흐름이 뒤 결과를 덮지 않게 실행 번호를 본다.
- **서비스 워커 범위·캐시**: 범위는 그대로 `/my/tickets`, `/v1/`·`/serwist/`는 네트워크로만, 팬 API는 다른 출처라 규칙에 걸리지 않는다. 다시 받기는 월렛 문서 두 꼴만, 200·이동 아님·`no-store` 없음일 때만 넣는다. 지우기는 `wallet-shell-` 접두와 옛 이름 둘만이고 미리 저장 캐시·대소문자 다른 이름·비슷한 이름은 남는다.
- **판 교체가 오프라인 진입을 깨는가**: 오프라인 활성화에서 옛 판 런타임 캐시를 지우면 다시 받지 못한 티켓 펼침 주소는 캐시에 없다. 다만 Serwist가 같은 활성화에서 새 목록에 없는 미리 저장 항목(옛 덩어리)을 지우므로(`serwist` `handleActivate`) 옛 판 HTML을 남겨도 화면이 붙지 않는다. 그래서 옛 응답을 옮기지 않는 정본 결정이 맞고, 미리 저장한 `/my/tickets`는 남아 열린다(정본 '남는 한계'). 진입 지연은 RV350-3으로 따로 적었다.
- **로그아웃 정리**: 대기실 로그아웃(`queue-room/src/live/logout.ts:31`)은 `wallet-shell-` 접두로 캐시를 지운다. 판 없는 옛 이름에서는 이 정리가 닿지 않았는데, 이 묶음으로 런타임 캐시가 그 접두를 따르게 됐다.
- **빌드 판 넣기**: `@serwist/turbopack` 9의 스키마가 `esbuildOptions.define`을 받고 빌드가 그 값을 매니페스트 주입과 합친다(원본 확인). 꼴은 frontend §5.18 빌드 칸 `[A-Za-z0-9_-]{1,64}`와 같다.
- **가짜 API**: 계약 Zod를 지나고 keyId를 `node:crypto`로 따로 계산하며, 같은 키 201·다른 키 403 `reauth-required`가 ticket-svc 규칙과 같다.
- **ADR 번호**: 로컬의 갈래 가지들에 0336을 쓴 다른 ADR이 없다(갈래 1 0333, 갈래 4 0339).
