# BAT-032 계획 — 합본 이벤트 루프 격리와 홀드 경로 분리

- 작성: 2026-11-12
- 앞 작업: BAT-031(HOT-465)은 도구화·진단·1차 꼬리 수정까지 했다. 40초 유효 K7 p99 4.7초, 100초 무효(놓침 495), 홀드 p99 227~321ms로 3초·50ms에 미달했다.
- 근거: `docs/review/measurements/BAT-031-k7-tail.md`

## 1. 목표

- v1 합본 3복제·CPU 4/한도 4에서 K7 ② 100/s를 100초 유지해도 유효하고, 결제 확정 p99 3초·홀드 p99 50ms 안.
- 동작·계약·불변식 불변. 복제 3 고정은 유지한다.

## 2. 왜 BAT-031에서 못 끝냈나

- 프로세스 CPU는 파드당 1.13코어인데 `nodejs_eventloop_utilization`은 1.0이다. Node 이벤트 루프 하나가 4 CPU 중 1개만 쓴다.
- 요청당 약 6.2ms CPU. 결제 한 건에 승인 claim·read·mark·finish, Saga reserve·confirm, 결과 소비, 발권 트랜잭션이 겹친다.
- 홀드는 결제·소비자와 같은 이벤트 루프를 써서 K7 혼합 부하에서 p99 227~321ms다. 조용한 K2의 44ms와 다르다.

## 3. 갈래

1. **합본 실행 단위 분리**: 합본을 여러 워커/클러스터 프로세스로 나눠 4 CPU를 쓰게 한다. HTTP는 워커가 받고, 리더·소비자·Saga 실행기는 한 곳에만 둔다. 인메모리 기다림 표·rate limit·bulkhead가 워커별로 갈라지는 영향을 계약·불변식으로 확인한다.
2. **요청당 트랜잭션 축소**: 승인 실행기의 read를 claim에 합치고, finish·mark·claim을 줄인다. 결과 소비·발권의 트랜잭션 수를 계측해 줄인다. 이 갈래만으로 CPU를 절반 가까이 줄일 수 있는지 먼저 잰다.
3. **홀드 경로 분리**: 홀드·세션 확인을 별도 실행 단위로 두거나, 결제·소비자 작업이 홀드 이벤트 루프를 막지 않게 한다. Redis 지연이 아니라 이벤트 루프 대기라는 BAT-031 진단을 전제로 한다.

## 3.5 이번 배치 실행 결과(부분 완료·중단)

- ① 트랜잭션 축소: 승인 실행기 `claimDue`가 원장(`payment`·`CONFIRM_SENT`)을 같은 트랜잭션에서 읽어 `payment.confirm.read`를 없앴다. `payment.confirm.read` 표본이 사라지고 claim p95 13.7ms·mark 45.8ms·finish 31.5ms(40초 split)가 됐다.
- ② 홀드 분리: `PEAKET_BUNDLE_MODE=split`으로 payment-svc·purchase-svc 전체·purchase-svc 홀드 전용(DB·Kafka 없음, 8083)을 자식 프로세스로 나눴다. 합본 관리 포트가 자식들의 `/ready`·`/metrics`를 모은다.
- K7 100초 r1(새 클러스터·split·2Gi·relay 정상): **유효(놓침 0·`startSkewS=0`)**, 결제 확정 p99 **3,039.9ms**(목표 3초를 40ms 초과), p95 2,079.2ms, 홀드 k6 p99 243.9ms·서버 라우트 p99 43.4ms.
- K7 100초 r2(상태 조회 100ms): **무효(놓침 294)**, p99 9,090ms. 100ms는 되돌려 200ms로 커밋한다.
- K2 스모크 1,000/s: 홀드 p99 11.1ms로 50ms 안. 정본 2,000/s·4발생기 K2 3회는 아직이다.
- 소유자 지시로 **추가 K7/A/A/K2 측정을 중단**했다. 남은 K7 3회·A/A·K2 3회·A등급 게이트는 OPEN[38]로 넘긴다.
