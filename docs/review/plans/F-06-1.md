## 3. 정본 빈칸과 이번에 정하는 값

정본에 아직 없는 세부를 여기서 정한다. 구현 담당은 코드보다 먼저 정본(notify.md·identity.md·core.proto·streaming.md)에 같은 내용을 적는다. **2026-11-28 소유자 결정**으로 흡수 계정 이메일은 보관하지 않고 병합 트랜잭션 안에서 내부 gRPC로 한 번 전달한다. 이 결정은 POL-034의 즉시 파기를 그대로 지키므로 data.md·data-classification.md·secrets-and-keys.md에 새 보유 행이나 키를 만들지 않는다.

### 3.1 POL-034 흡수 계정 이메일 계약(소유자 결정 2026-11-28)

**정한 것**: identity는 흡수 계정 주소를 **저장하지 않는다**. 병합 확정 트랜잭션 안에서 흡수 계정 이메일을 읽어, core-svc notify의 내부 gRPC `MergeNoticeService.SendAbsorbedNotice` 요청에만 싣는다. notify는 그 주소로 기존 발송 큐에 `ACCOUNT_MERGED_ABSORBED` 작업을 한 번 넣고, 주소는 프로세스 메모리에만 둔다.

- `MergeNoticeService`는 core-svc가 구현하고 identity가 부르는 내부 서비스다. `docs/api/proto/peaket/core/v1/core.proto`에 둔다. 요청은 `{mergeId, absorbedAccountId, absorbedEmail}`, 응답은 `{accepted}`이다. `absorbedEmail`은 요청에만 있고 어느 표에도 쓰지 않는다.
- identity 병합 확정 트랜잭션: 두 계정을 잠근 뒤 `mergeAccounts` 전에 흡수 계정 주소를 읽는다. `mergeAccounts`가 프로필을 지운 뒤, 트랜잭션이 끝나기 전에 `mergeNotice.sendAbsorbedNotice(...)`를 한 번 부른다. 실패(무응답·기한 초과·거절)는 `merge_notice_failed` 지표(`reason`)로 남기고 **병합은 막지 않는다**. 재시도·보관·정비 작업은 없다.
- notify gRPC 처리기: `NotificationIntake.accountMergedAbsorbed({mergeId, absorbedAccountId, absorbedEmail})`를 부른다. 인테이크는 `ACCOUNT_MERGED_ABSORBED` 이메일 작업을 중복 키 `ACCOUNT_MERGED_ABSORBED:{mergeId}:{absorbedAccountId}:EMAIL`로 하나 적고, 주소를 **프로세스 안의 `AbsorbedNoticeInbox`**(키 = 중복 키, 값 = 주소, 최대 10,000건 [가정], 디스크·DB·로그 없음)에 넣는다.
- 워커: `ACCOUNT_MERGED_ABSORBED`를 보낼 때 `AbsorbedNoticeInbox`에서 주소를 꺼내 이메일을 보낸다. identity에 다시 묻지 않는다(재조회 없음). 주소가 없으면(다른 파드가 gRPC를 받았거나 프로세스가 다시 떴거나) 재시도 없이 `FAILED`(사유 `recipient-unavailable`)로 기록하고 `notify_absorbed_notice_missing_total{reason}`을 센다. 주소는 작업·기록·로그에 남기지 않는다.
- 흡수 계정은 사건 시점에 이미 `MERGED`이고 이메일·전화번호가 지워져 있다. 워커는 `ACCOUNT_MERGED_ABSORBED`에서 **받는 사람 조회(identity)를 하지 않고** 전달받은 주소로만 보낸다. 그래야 `MERGED` 거절보다 먼저 처리된다.
- `identity.accounts-merged`의 asyncapi 모양은 **바꾸지 않는다**(mergeId·primaryAccountId·mergedAccountId·confirmedAt 넷, 주소 없음). 주소는 Kafka에 없다. 계약 시험이 이 점을 고정한다.
- gRPC는 트랜잭션 안에서 부르므로, gRPC가 성공한 뒤 트랜잭션이 되돌려지면 병합되지 않은 계정에 통지가 먼저 갈 수 있다. 소유자 결정의 받아들이는 위험으로 적고, 알림은 상태를 바꾸지 않는다. 기한은 300ms [가정]이고 실패는 위 지표로만 남긴다.
- **여러 파드 위험**: gRPC를 받은 파드와 워커를 도는 파드가 다르면 메모리 주소가 없어 `FAILED`다. 동결 로컬 시험은 한 프로세스이고, 운영 전 대책(같은 파드에서 바로 보내기, 전용 큐 등)은 F-06-6·소유자 몫으로 남긴다.

**이유**: POL-034는 두 계정 모두에 완료를 알리라고 정본에 적혀 있는데, 지금은 흡수 계정 주소가 트랜잭션에서 지워진다. 주소를 Kafka에 실으면 개인정보 최소화(ADR-0139)에 어긋나고, 24시간 암호문 보관은 "흡수 계정 프로필은 병합 즉시 파기"와 어긋난다. 저장 없는 한 번 전달이 즉시 파기와 두 계정 통지를 함께 지킨다.

### 3.2 notify Kafka 소비자 배선

- 소비자 그룹은 지금과 같은 `peaket.core-svc.<환경>` 하나다. 읽는 주제를 넷으로 늘린다: `identity.accounts-withdrawn`(기존 후기 파기), `identity.accounts-merged`, `identity.login-methods-changed`, `trade.orders`.
- 업무 키: 탈퇴 = 계정 ID, 로그인 수단 = 계정 ID, 병합 = `mergeId`, 주문 = `orderId`(docs/streaming.md §2.6 'core-svc 알림'). 같은 키의 사건은 한 번에 하나씩 처리한다.
- 값 해독은 `@peaket/contracts/asyncapi`의 Zod 스키마(`AccountMerged`·`LoginMethodChanged`·`OrderEvent`)로 한다. 계약에 맞지 않는 값은 처리하지 않고 던져 플랫폼이 5회 뒤 `held_event`에 보류하게 한다. 데드 레터 토픽은 두지 않는다(ADR-0142).
- `trade.orders` 가운데 알림 대상은 `EVENT_CANCELLATION_CONFIRMED`·`EVENT_POSTPONED`·`REFUNDED`·`REFUND_FAILED` 넷뿐이다. 나머지 `OrderEvent.type`은 인테이크를 부르지 않고 성공으로 끝낸다(오프셋 커밋, no-op 빠른 길).
- 처리기는 `NotificationIntake`를 부른다. 인테이크가 DB에 다 쓴 뒤에 반환하고, 플랫폼이 그 뒤 오프셋을 커밋한다(적어도 한 번 + 중복 키). 같은 사건이 다시 와도 중복 키가 작업을 하나로 막는다.
- `main.ts`는 `NotificationIntake`로 `NotifyEventHandler`를 만들어 `startCoreConsumers`에 넘긴다. 브로커 주소가 없으면 지금처럼 local·ci만 소비자 없이 뜨고, 내부 HTTP 입구(`/internal/v1/notify/identity-events`·`/internal/v1/notify/trade-events`)는 local·ci 대체로 남긴다. 운영에서 브로커 주소가 없으면 시작하지 않는다(기존 규칙).
- 같은 그룹에 주문 사건이 더해져 후기 탈퇴 정리가 밀릴 수 있다. no-op은 바로 끝내고, 그룹 밀림은 기존 `stream_consumer_lag_records`로 본다. 부하 수치는 이 기능에서 주장하지 않는다.

### 3.3 문자(SMS) 채널

- `SmsTransport` 포트(이메일 포트와 같은 모양): `send({to, body, messageKey}) -> {providerMessageId?}`. 실패는 `kind: RETRYABLE | PERMANENT | UNKNOWN` 칸으로 나눈다(`SmsTransportError` 또는 같은 `kind`를 가진 오류).
- local·ci·demo 대역: `FakeSmsTransport`(보낸 것만 기록)와 `FileSmsTransport`(`PEAKET_NOTIFY_SMS_DIR/notification-sms.jsonl`). 운영 대행 어댑터는 F-06-6. 설정이 없으면 `unavailableSms`(보내지 않고 실패).
- 받는 사람: identity `RecipientQueryService`에 `include_phone`을 더하고 `Recipient.phone`을 `include_phone=true`일 때만 채운다. 전화번호는 계정에 저장된 값(가입 때 선택 동의를 받은 경우만 저장됨)이고, 병합·탈퇴 계정은 비운다. notify는 문자 작업을 보낼 때만 `include_phone=true`로 묻는다.
- 허용 종류: **문자는 d5 §9.1의 두 자리뿐**이다. ⑴ 공연 전날·당일 아침 월렛 열기·입장 24시간 전 키 미등록(d5 4144)을 위한 새 종류 `WALLET_OPEN_REMINDER`는 `SMS_ALLOWED_KINDS`에 들어 `intake.notice`의 `FAN_NOTICE_KINDS`·`VARS_ALLOWED` 검사를 지나 만든다. ⑵ 웹 푸시가 주 채널인 거래·안전 알림(`WEB_PUSH_PRIMARY_KINDS`: `LOGIN_METHOD_LINKED`·`LOGIN_METHOD_UNLINKED`·`ACCOUNT_MERGED`)은 웹 푸시가 끝내 실패한 뒤 `intake.smsFallback({kind,targetId,accountId})`로만 대체 작업을 만든다. 대체 작업의 중복 키는 `{kind}:{targetId}:{accountId}:SMS:fallback`이고, 워커는 이 꼬리가 붙은 작업만 `WEB_PUSH_PRIMARY_KINDS`의 SMS를 허용한다. 회차 취소·연기·환급은 이메일·알림톡이고, 입장 키 재발급·지연은 이메일만이며, 신청 알림·광고는 문자를 쓰지 않는다. 인테이크는 SMS가 허용되지 않은 종류를 `INVALID`(문구에 '문자')로 거절하고, 워커도 방어적으로 `FAILED`로 끝낸다.
- 본문: `[피켓] ` + 제목 + 줄바꿈 + 본문(d5 4190). 2,000자 [가정]를 넘으면 보내지 않고 `FAILED`(사유 `sms-too-long`)로 기록한다. 주소·전화번호는 본문에 넣지 않는다.
- 재시도: 이메일과 같다(429·5xx는 남은 TTL 안에서 1분·5분·30분·2시간·6시간·12시간 [가정], 400은 DEAD, 결과 모름은 돈·보안·법정·**월렛·입장 키 미등록** 통지만 한 번 더). `WALLET_OPEN_REMINDER`는 입장에 꼭 필요해 `DUBIOUS_RETRY_KINDS`에 든다. 전화번호가 없거나 `include_phone` 응답이 비면 재시도 없이 `FAILED`다.
- 밤: SMS는 신청 알림에 쓰지 않으므로 `nightPush`와 무관하다. 광고는 SMS로 만들지 않으므로 밤 광고 금지와 겹치지 않는다.

### 3.4 세 갈래를 한 줄기로 보는 시험

- 신청(HTTP) → 이메일·웹 푸시 작업 → 한 번 누름 수신 거부 → 대기 작업이 보내지지 않음(suppressed)을 한 시험에서 본다.
- 거래·안전 알림은 이메일·웹 푸시로, 월렛 안내는 문자로 보내 가짜 발송기 셋이 각각 정확한 주소·전화번호·본문(`[피켓] ` 머리)으로 한 번씩 받는 것을 본다.
- 문자는 전화번호 조회가 `include_phone=true`일 때만 일어나고, 작업·기록·로그에 전화번호·이메일이 없는 것을 함께 본다.

## 10. 완료의 정의

- 계획·시험·리뷰·지적 반영·재리뷰·구현·문서·기록 커밋이 이 가지에 있고, 꼬리말(`Batch: F-06-1`, `Feature: F-06-1`, `Role`, `Agent-Session`, `Agent-Model`)이 맞다.
- 새 시험과 기존 notify·identity 시험이 모두 통과하고, 타입 검사·린트·문서 점검(오류 0)·장부 `--require`·release-scope가 통과한다. 새 시험이 기준 트리에서 실패한 기록이 `## 실패 확인`에 있다.
- 정본(notify·identity·core.proto·streaming)이 구현과 같고, `packages/contracts gen:check`가 통과한다. data.md·data-classification.md·secrets-and-keys.md에 흡수 계정 주소 보유 행·키를 만들지 않는다.
- 실제 SES·Solapi·VAPID 운영 키와 대행사 계약은 **미실행**으로 남고, F-06-6은 `막힘` 그대로다. F-06-1은 `동결`을 유지하며 `develop`·`release/1.0.0`에 합치지 않는다.
- 이 기능은 동결이라 완성 판정(전체 장부 빈칸 0)에 넣지 않는다. 완성 보고에는 '동결로 미검증'으로 따로 적는다.

## 11. 동결 로컬 범위

- **identity 마이그레이션을 만들지 않는다.** 흡수 계정 주소를 저장하는 표·칸·키가 없으므로 `0039_merge_notice.sql`도 없다(RV061-11 해소).
- core notify도 표 구조를 바꾸지 않는다(`notification_job`의 채널 값은 이미 SMS를 허용한다).
- 릴리스 플래그를 만들지 않는다(v1에 플래그 기구가 없다, ADR-0386 결정 5).
- 실제 발송 대행 어댑터·운영 키·대행사 계약은 이 가지에 넣지 않는다. local·ci 파일/가짜 대역만 넣는다.
- gRPC를 받은 파드와 워커 파드가 다른 경우의 대책(같은 파드 처리·전용 큐)은 F-06-6·소유자 몫으로 남긴다. 동결 로컬 시험은 한 프로세스다.
- `release-scope --release`는 릴리스 가지에서만 도는 검사라 이 가지에서는 돌리지 않는다. `--check`로 표·manifest·BUILD_ORDER의 분류가 그대로인지 본다.

**판정과 차례**
- 높음·통과 기준 RV061-01~09는 **시험 담당이 먼저** 고친다(`Fix-By: test`). RV061-01은 정본·ADR/data-classification을 먼저 정하고 그 계약을 시험이 단언한다. RV061-02~05는 시험 픽스처·단언을 바꾸고, RV061-06~09는 실패·로그·만료 갈래를 더한다. 고친 곳은 리뷰 담당이 다시 본 뒤 시험을 고정한다. 그다음 구현이다.
- RV061-10~15는 이 기능에서 고치지 않고 `docs/lanes/lane2-cleanup.md`에 옮겼다. RV061-11(마이그레이션 번호)은 구현 전에 정하는 편이 안전하고, RV061-12(키 꼴)는 `secrets-and-keys.md`를 쓸 때 함께 정한다.
- 이 기능은 B등급이고 ADR-0373은 B·C 시험 리뷰를 필수로 두지 않지만, 이 동결 가지의 지시가 독립 리뷰를 요구해 한 바퀴 돌렸다. 시험 리뷰는 여기서 끝내고, 구현 뒤 코드 리뷰는 하지 않는다(ADR-0372·0373).

**역할 확인**
- 이 리뷰 커밋 전에 `node tools/ci/roles-check.mjs --base 75771324e --head HEAD`를 돌린 결과는 `[구성] F-06-1 … plan과 test를 같은 세션 …`과 `[구성] … impl·review·verify 커밋이 없다`를 낸다. 뒤엣것은 이번이 시험 리뷰라서 당연하고, 앞엣것은 ADR-0270의 "한 에이전트가 두 역할을 맡지 않는다"를 어긴 것이다. **남은 위험**
- RV061-01의 24시간 보유는 소유자·법률 검토가 필요한 새 보유다. 정본 개정 없이 구현하면 POL-034의 즉시 파기와 어긋난다.
