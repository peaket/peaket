# 묶음 계획: BAT-360(감사 공개 앵커·공개 검증 도구, 결제사 지정 명령 12·결제 감내 모드·사후 검토·운영 사건 줄·만료 차단 정리·2인 승인 시연 서버 몫)

- **진행**: 리뷰 막는 지적 3(RV-01~03) 고침 → 검증 끝(2026-11-22, 통합 25파일 161건·틀린 구현 10/10). 남은 것은 기록(R-751)과 합치기(감독 몫). 합치지 않고 가지에만 둔다.
- **무엇**: BUILD_ORDER 146행 BAT-360(갈래 4, 구간 3, 등급 B, 3.25일, OPS-280·OPS-290, 단계 줄 545·546행)의 작업 목록이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **쉬운 말**: 감사 기록을 묶은 요약(체크포인트)에 서명하고 비트코인에 기대는 공개 시각 증명(OpenTimestamps)을 붙여 내놓는다. 누구나 받은 파일로 '그때 그 기록이 있었고 바뀌지 않았다'를 확인하는 도구도 둔다. 운영 명령 쪽 남은 일(결제사 지정, 감내 모드, 사후 검토, 운영 사건 줄, 만료된 IP 차단 거두기)도 만든다.
- **바탕**: `D:/ticketpass-lane4-360`, 가지 `feature/lane4-BAT-360`, 출발 `fb75fe2c0`. BAT-355(`feature/lane4-BAT-355` `98a224523`, 리뷰·검증 중) 위에 쌓는다. 계획 담당은 제품·시험 코드를 쓰지 않았고 시험·Docker를 돌리지 않았다.
- **차례**: B 정방향 짧은 고리(ADR-0281 결정 5, ADR-0283 결정 2, ADR-0331): 계획 → 구현 → 시험 → 리뷰 → 리뷰 반영 → 검증 → 기록. 계획 커밋에 `Batch-Order: impl-first`.
- **한 줄 결론**: 체크포인트 표·서명·공개 읽기 경로는 있으나 ADR-0075와 다른 꼴이다. 명령 12·감내 모드는 유형만, 사후 검토는 계약만 있고, `ops_event`·`waf-block-expirer`는 없다. 세부는 ADR-0348·0349로 정했고, 데모 도우미·결제사 판정 경로·회차 마감 목록은 감독이 정했다(2절).

## 2. 감독에게

올린 것에 감독이 2026-11-22에 답했다(감독 결정 2026-11-22). 이 계획은 그대로 따른다.

1. **데모 도우미(C-T47)** — (가) 승인. C-T47 ①(두 계정, 요청자 403, 감사 기록의 데모 표시)은 시험용 가상 인증기(소프트웨어 패스키)로 받은 재인증으로 이 묶음이 증명한다. 데모 막대와 도우미(②)는 BAT-375(BUILD_ORDER BAT-375 비고).
2. **명령 12의 받는 쪽** — 추천대로. payment-svc 세 곳(`payment.proto` `CheckEventPgAssignment`, `src/grpc-server.ts` 처리기, `PG_ASSIGNMENT` 설정 사건 처리기와 `src/start.ts` 조립)을 이 묶음이 고친다. proto를 고친 구현 커밋이 contracts 생성물과 메시 정책(7절)을 함께 맞춘다. core-svc 회차 칸은 LCH-080·090, admission-ctrl 상한은 BAT-365.
3. **끝난 회차 목록** — (가) 승인. core-svc 읽기 전용 내부 경로 `GET /internal/v1/events/onsale-closed`(갈래 3 영역, 회차 ID·마감 시각만)를 이 묶음이 더한다. ops-svc → core-svc 내부 REST 쌍은 ADR-0285 결정 9 표와 `port-allow.yaml`에 이미 있어 규칙은 그대로다. 표의 '쓰는 곳'에 '보충(2026-11-22, BAT-360)'으로 경로를 적었고 원천 주석은 구현 커밋이 더한다. 실패 줄은 guidelines §8.1.
4. **승인 역할** — 명령 6은 이 묶음이 정본('요청자 아닌 operator 이상')대로, 명령 5는 BAT-365(정리 목록 몫, 그 행은 고치지 않음).
5. **새 의존성** — `@aws-sdk/client-wafv2` 3.1159.0·`canonicalize`(Apache-2.0) 허락. devops §4.4 `trustPolicy`·라이선스 검사를 게이트에 넣었다. 공식 OpenTimestamps 클라이언트(LGPL-3.0)를 쓰지 않는 까닭은 ADR-0348 결정 5.
6. **합칠 때 충돌** — BUILD_ORDER 146·147행, asvs/control-tower.md 84·157·168·170·179행은 BAT-355가 고친 줄과 같거나 이웃이다. rebase 때 양쪽을 다 남긴다(기록은 감독 세션).
7. **번호** — ADR-0348·0349, 마이그레이션 ops-svc 0023·0024.
8. **설정 사건 내는 쪽(감독 알림)** — 갈래 1 BAT-215가 `LOG_SAMPLING`의 받는 쪽을 만들고 내는 쪽을 갈래 4에 넘겼다. 이 묶음은 ops Outbox 표·릴레이·`publishSetting`을 설정 사건 일반의 꼴(asyncapi `control.settings`)로 만든다(ADR-0349 결정 5, B27). 온세일 구간에 내는 일과 C-T75 ①④는 BAT-365(BUILD_ORDER BAT-365 비고).

## 3. 범위

### 3.1 하는 것

## 10. 실패 확인

- B 묶음이라 구현 전 트리의 실패 확인을 하지 않는다(ADR-0331 결정 2·3). 11절 틀린 구현 표본(10개, 권한·개인정보 포함)으로 검증 담당이 실패를 본다.
- 시험 담당 몫: 바뀐 계약에 걸리는 기존 시험(`audit-anchor.test.ts`·`audit-chain-tamper.test.ts`의 Ed25519·직선 루트 단언, 명령 6 승인을 commander만으로 보는 단언)을 시험 커밋에서 정본대로 고친다. 구현 커밋은 시험 파일을 바꾸지 못한다.
- 이 절에는 까닭 한 줄과 명령·시험 수·실패 수·실패 까닭 한 줄만 적는다.
- 시험 담당(2026-11-22): B 등급 정방향 묶음이라 구현 전 트리의 실패 확인은 하지 않는다(ADR-0331) — 틀린 구현 표본으로 대신(11절, 검증 담당). 공개 검증 도구 시험은 작업 폴더 밖 도구 사본에 결함 아홉(M5·M6·M7, 끝 코드 3→0, 같은 번호 하나만 보고, 직전 해시 안 봄, P-256 확인 뺌, OTS 대상 해시 안 봄)을 하나씩 넣어 해당 시험이 실패하는 것을 봤다.

## 13. 자주 놓친 결함(시험·구현 지시문에 넣는다)

- 바이트는 정확한 값까지: 잎·루트·JSON·서명 입력은 시험이 정본 식으로 따로 만든 값과 견준다. 기록 수 1·2·3·5·8을 모두.
- 경계는 양쪽: 00:10, T − 10분·T + 60분, 6·24·48시간·7일, 만료의 − 1ms와 정각. 가짜 시계, 시험 값은 코드 상수와 다르게.
- 허용 목록은 밖의 값마다: 결제사, 명령 6 모드·범위, 계기(명령 3용·11용 엇갈림), 역할, 환경(local·ci·demo·staging·production).
- 겹친 가드는 하나씩 뺀다: 서명과 직전 해시, 실행자 대조와 조건부 갱신, 작업 겹침 금지와 번호 유일 제약.
- 빈 결과가 통과로 새지 않게: 도구의 '확인 못 함', `unavailable`, 캘린더 0개 성공. 장애 주입은 끊긴 사례 수를 단언한다.
- 부르는 쪽이 판정을 쓰는지 HTTP 경계에서 본다(판정 RPC 거절 → 422, 1인 기간 → 응답).
- 작업 진입점은 따로 띄운다: 운영에 KMS 키 ID·버킷·IP 집합이 없으면 시작하지 않는다.

### 정한 세부(정본에 없던 것)

- **두 사슬**: 공개 사슬(DAILY·EVENT_CLOSE·MANUAL)은 `no`·RFC 8785 JSON이 있고 직전 해시는 직전 공개 행의 `checkpointHash`다. 내부 사슬(EXECUTION과 `kind`가 빈 옛 행 = `legacy`)의 직전 해시는 직전 내부 행의 루트이고, 옛 행은 `seq:해시` 줄 루트로 검증하며 옛 Ed25519 서명은 확인하지 않는다(해당 없음). 번호 다툼은 트랜잭션 잠금(`pg_advisory_xact_lock`) 안에서 이어지는지 보고 세 번까지 다시 계산하며, `no`에 유일 색인이 있다. 작업 겹침 금지는 세션 잠금(`pg_try_advisory_lock`, 못 잡으면 끝 코드 0)이다(작업 역할이 `ops_worker_lease`를 쓰지 못한다).
- **파일 꼴**: OTS 직렬화는 `ots.ts` 머리 주석, 게시 파일(`public-keys.json`·`index.json`)은 `publisher.ts` 머리 주석, 검증 묶음은 `bundle.ts` 머리 주석이 정본 자리다. 공개 JSON·`.sig`에는 키 ID가 없어 도구는 `public-keys.json`의 키를 모두 시도한다.
- **작업 끝 코드**: `audit-anchor` 0 끝·1 SEV2 조건(루트 어긋남·같은 이름 다른 바이트)·2 설정·시작 실패, `waf-block-expirer` 0 끝·1 실패(두 번 충돌·WAF·DB 오류)·2 설정 실패. 운영(local·ci 밖)에 KMS 키 ID·두 버킷·캘린더·core 주소, 또는 IP 집합이 없으면 2로 끝난다.
- **환경 값(정본에 이름이 없는 것)**: `PEAKET_PAYMENT_GRPC_ADDR`(ops-svc → payment 판정, 없으면 명령 12가 503), `PEAKET_WAF_IPSET_V4`·`_V6`(꼴 `<이름>|<ID>`)·`PEAKET_WAF_SCOPE`(REGIONAL 기본, CLOUDFRONT면 us-east-1)·`PEAKET_WAF_ENDPOINT`(local·ci만), `PEAKET_PG_APPROVAL_TPS`(payment-svc, JSON `{"TOSS":n,"PORTONE":n}`, 없으면 승인 상한 빈 목록 → dry-run `unavailable`, 정본 값은 코드에 없다). 기록 단계에서 정본(secrets-and-keys·배포 값 표)에 적을지 정한다.
- **설정 사건**: 값은 생성물 `SettingChanged`로 쓰기 전에 꼴을 보고, 종류 목록은 그 열거를 그대로 쓴다. `eventKey`는 SHA-256(`PEAKET-setting-event-v1\n명령ID\n종류\n범위`) 앞 16바이트에 판 8 비트를 넣은 UUID다(결정 5 글자대로 대상은 넣지 않아, 한 명령이 대상만 다른 사건 둘을 내면 같아진다 — BAT-365가 볼 몫). 릴레이 역할은 `ops_outbox_relay`, Outbox 행 ID는 실제 시계의 UUIDv7이다(파티션을 실제 시계로 만든다). 명령 12의 actor는 요청자 가명 참조다.
- **판정 순서(명령 12)**: 역할 403 → 꼴 422 → 온세일 창 → 하위 결제사 판정 → dry-run. 창의 T는 core 판매 설정의 `opensAtMs`(마감 회차 경로와 같은 칸)이고, 원천을 잇지 않았으면 503(닫힌 쪽)이다. 실행 직전에 걸리면 FAILED이고 사유는 그 Problem 이름이다. 명령 6 dry-run은 판정 RPC로 지금 지정과 승인 상한만 읽는다(기본 칸이 필수라 `toPg`, 없으면 TOSS를 넣는다).
- **사후 검토**: 실행자는 요청한 commander(명령 3·11은 1인 즉시 실행)다. 1인 기간은 identity 활성 OPS commander 목록이 정확히 `[실행자]`일 때뿐이고, 읽지 못하면 503 `admin-account-unavailable`이다. 검토 의견은 `POST_REVIEW_CONFIRMED` 사건의 사유에 둔다(표에 칸이 없다). 정본 넷 밖의 Problem 둘(409 `post-review-conflict`, 422 `post-review-invalid`)을 더했다. 보고서 글은 줄바꿈·탭을 받고, 정규화 전 8,000자 넘으면 400이다. `followUps.issueUrl`은 https만 받는다.
- **ops_event**: 감싼 저장소 `OpsEventStore` 한 곳이 트랜잭션이 끝난 뒤에만 낸다. 사람 접수는 REQUESTED, 시스템 접수는 AUTO_ACTION_STARTED다.
- **명령 4 만료**: 덮음은 대역 키가 정확히 같을 때만이다(포함 관계는 보지 않는다). ASN 항목이 있는 명령 4는 AUTO_EXPIRED로 적지 않는다(규칙 만료는 OPS-310). 0024 ③은 `command_event.type`에 CHECK가 없어 주석뿐이다.
- **정본과 달리 읽은 곳(리뷰가 볼 것)**: ① B7 — 작업 역할은 체인·경보를 쓰지 못하므로(48 11) 작업은 SEV2 로그를 남기고 서명·게시를 멈추고, SEV2 경보 `audit-checkpoint-mismatch`·`AUDIT_CHAIN_MISMATCH` 기록(한 번)·지표는 ops-svc 1분 신호가 같은 검증으로 낸다. ② 검증 묶음은 묶음을 만든 뒤 감사 기록을 붙이고 기록이 실패하면 묶음을 주지 않는다(한 DB 트랜잭션은 아니다, 48 8). ③ PENDING 24시간은 체크포인트를 만든 시각부터 잰다. ④ 데모 표시는 0015의 SQL 함수 `ops_append_audit`(파트너 경로)로 남는 기록에는 붙지 않는다. ⑤ 완료 증명 올리기는 설정한 캘린더 주소와 같은 URI만 부른다. ⑥ 검증 도구의 `--skip-bitcoin`(비트코인 단계를 공식 클라이언트로 따로 봤음): 없으면 비트코인 단계가 늘 '확인 못 함'이라 끝 코드 0이 나오지 않는다.

### 남은 위험

- **구간 5까지 미검증**: C-T38 ②(실제 OpenTimestamps 캘린더·KMS·Object Lock), C-T61 ⑦⑧(kind CronJob 성공 시각 경보·IP 집합 IAM/Terraform). `ledger --require`가 1로 끝나는 까닭은 이 셋뿐이고, 셋 다 계획 5.1·ledger-notes에 적힌 대로 이 묶음 밖이다.
- **RV-04**: 정리 작업이 '만료 전 다른 명령 4'를 ACKED만으로 본다. 지금은 명령 4 전송이 없어 닿지 않지만 BAT-365가 전송을 붙이면 새 차단이 조용히 풀릴 수 있다(위 주입 참고).
- **RV-05~RV-11**: 계획 15절의 정리 목록 그대로다. 특히 RV-06(키 ARN을 공개 키 ID로 쓸 수 있음), RV-08(Windows 역슬래시 경로), RV-09(정본과 다르게 읽은 곳을 ADR·secrets-and-keys에 아직 안 적음)는 기록 뒤 다음 손질이다.
- **클라우드**: moto가 KMS `ECC_NIST_P256` DIGEST 서명을 흉내 내지 못해 통합 시험은 local P-256 서명기로 게시 흐름을 본다(앞선 시험 커밋). 실제 KMS·S3·WAF·캘린더 호출은 구간 5다.
- **화면·배포**: 이 묶음은 화면을 바꾸지 않아 브라우저 확인이 없고, CronJob 둘의 배포·IAM·경보 규칙도 구간 5다.
