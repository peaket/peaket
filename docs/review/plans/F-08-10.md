# 기능 계획: F-08-10(서비스 분리 효과 비교·M2 블로그 3편 초안, 동결 로컬 트랙)

- **진행**: 계획·시험(측정 준비) 끝, 기준 트리 실패 확인, **리뷰 준비에서 멈춤**(2026-11-27). 측정·보고서·블로그 본문·기록은 다음 역할이 한다. 이 파일의 측정 결과는 모두 `미측정`이다.
- **무엇**: BUILD_ORDER '기능 단위 계획' F-08-10(갈래 4, 등급 B, HOT-500·HOT-510, WBS 2.75일, 단계 줄 `HOT-500 wbs 2.12.5`·`HOT-510 wbs 2.12.6`)의 작업 목록이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **쉬운 말**: 같은 v1 코드를 세 가지 모양으로 띄워 본다. ① 서비스 넷을 Node 프로세스 하나에 함께 올린 합본, ② 같은 합본 이미지를 서비스(역할)별 파드로 나눠 올린 배포, ③ v1처럼 서비스마다 이미지를 따로 올린 배포다. **로컬에서는 ①·②만 견주고 ③은 미측정으로 남긴다.** 결제 접수 부하를 같은 값으로 고정하고 진입 폭주를 0·100·120%로 겹쳐, 두 모양의 결제 접수 지연·오류율·진입 지연·오류율·CPU 스로틀을 견준다. 차이가 3회 반복의 편차 안이면 '차이 없음'으로 적는다. M2 블로그 3편은 이 비교가 아니라 F-08-2·F-08-8이 이미 잰 진입·좌석·결제 이야기를 초안으로 정리한다(게시는 소유자 몫).
- **바탕**: 작업 폴더 `D:/ticketpass-freeze-F-08-10`, 가지 `freeze/lane4-F-08-10`, 기준 `origin/freeze/lane4-F-08-9` `b5be6b76a`(F-08-9 구현·측정 기록 포함). 계획·시험 담당은 Docker·kind·브라우저·k6·측정을 하나도 돌리지 않았고 Docker 잠금도 잡지 않았다. **작업 중 `origin/freeze/lane4-F-08-9`가 `618f3b042`(검색 전용 창)로 앞섰다.** 이 가지는 지시된 출발점 `b5be6b76a`에 그대로 있고, 그 뒤 두 커밋은 아직 없다. 합칠 때 최신 F-08-9 위로 다시 쌓는다(강제 푸시하지 않는다).
- **차례(감독 지시 2026-11-26)**: 계획 → 시험(측정 준비) → 리뷰(새 세션) → 반영 → 측정/문서 → 기록. ADR-0373의 B등급 차례는 계획 → 시험 → 구현 → 시험 통과면 합침이고 시험 리뷰가 없다. 이 기능은 **'비교 결과가 통과로 새지 않는가'가 핵심**이라 감독이 리뷰를 한 번 더 붙였다. 리뷰는 코드가 아니라 측정 설계·판정·시험을 본다. 이번 동결 트랙은 계획과 시험을 한 세션이 맡았다(감독 지시). 역할 꼬리말은 `Role: plan`·`Role: test`로 나눠 남긴다.
- **동결 로컬 범위**: ADR-0373·ADR-0386에 따라 `freeze/lane4-F-08-10` 가지와 이 워크트리에서만 만든다. `develop`·`release/1.0.0`에 합치지 않고, 릴리스 가지·`main`에 체리픽하지 않는다. 마이그레이션·릴리스 플래그를 만들지 않고, `deploy/`의 출시 환경 값도 고치지 않는다. 이 기능의 결과는 v1 출시 계약의 근거로 쓰지 않는다.
- **수치**: 이 파일과 시험은 정본의 목표·판정 값을 **인용만** 한다. 측정 전이라 이 기능이 내는 값은 전부 `미측정`이다. 정본에 없는 새 수치를 주장하지 않는다. F-08-9의 V-T27·V-T28·P-T1 결론은 '판정 못 함'으로만 인용하고, F-08-9의 어떤 값도 이 비교의 근거로 쓰지 않는다. F-08-2의 규모 목표와 F-08-8의 KPI 결과를 이 기능이 주장하지 않는다.
- **한 줄 결론**: 합본(한 프로세스)과 역할별 배포를 같은 코드·같은 자원 합계·같은 부하로 견주는 측정 도구·무대·계획이 없다. 새 실행기(`v1 compare`)·역할별 무대(`compare-stage.mjs`)·판정기(`split-compare.mjs`)·계획 파일(`f10-plan.json`)·장부 `experiment` 칸을 더하고, 로컬에서 잴 수 있는 두 구성만 측정 창에서 18회 돌린다. 세 번째 구성(10개 서비스)은 로컬 v1 무대에 배포가 없어 `미측정`으로 남기고 V-T18은 '부분'으로 적는다.

## 2. 감독에게

1. **V-T18의 세 구성 가운데 로컬은 둘만 잰다** — 정본 §3.8은 (가) 한 프로세스 합본, (나) 역할별 배포, (다) 10개 서비스 v1 그대로를 견준다. 그런데 로컬 v1 무대(`cluster.mjs v1`)는 합본 이미지 하나와 릴레이 둘만 올리고, 10개 서비스를 따로 올리는 배포·이미지·주소가 없다. 그래서 이 기능은 **(가) 합본과 (나) 역할별 배포만 재고 (다)는 `미측정`**으로 남긴다. V-T18은 '세 구성 실행이 같은 묶음에 있다'를 요구하므로 결과는 **부분**이고, `미측정`을 통과로 세지 않는다. (다)까지 하려면 로컬 10개 서비스 무대를 새 기능으로 만들어야 하고 이 동결 트랙의 2.75일 밖이다. **감독 확인 필요.**
2. **진입 100·120% 단계는 F-08-2의 값을 인용한다** — 정본은 'PC에서 진입 SLO를 지킨 최대 도착률의 100%·120% [가정]'을 요구한다. 이 기능이 그 도착률을 새로 찾으면 K1 재측정이 되어 F-08-2 경계를 넘는다. 그래서 계획 파일에 `{entryRate}` 자리만 두고, 측정 창 전에 F-08-2 MSR-020의 유효 실행 ID와 값을 성능 장부에서 확인해 `set entryRate <값>`으로 채운다. **유효한 값이 없으면 100·120% 단계는 `skip`·`미측정`**이고 진입 폭주 없음(0%)만 잰다. 값을 이 파일에 옮겨 적지 않는다.
3. **자원 합계를 맞추는 방법** — (가) 합본 파드 하나의 CPU·메모리를 네 역할 몫의 합(CPU 4·메모리 2GiB [가정])으로 두고 복제 3, (나) 역할별 배포는 역할마다 CPU 1·메모리 512Mi [가정]로 복제 3을 둔다. 두 구성의 합계는 CPU 12·메모리 6GiB로 같다. 현재 `v1-bundle.yaml`의 합본 CPU 1과 다르므로 측정 창에서 합본 값만 올린다(값 파일은 고치지 않고 `--set`). 로컬 네 역할의 몫을 (다)의 대역으로 두고 (가)·(나) 합계를 같게 하는 것이며, **(다)를 재지 않으므로 (다)와 같다는 주장은 하지 않는다.** 자원이 F-08-8과 다르므로 F-08-8의 K1·K2·K7 수치와 직접 비교하지 않는다. **감독 확인 필요.**
4. **측정 창 길이** — 무대 50분 + 18회×5분(90분) + 구성 전환 15분 + 보고 20분 + 여유 20분 = **약 3시간 15분**이다. F-08-9처럼 무효 재측정 여유를 별도로 둔다. 동결 로컬 트랙의 창이라 v1 릴리스 측정 창과 섞지 않는다. 이번 턴에는 열지 않는다.
5. **Docker 잠금** — 측정 창에서 `docker-all` 두 자리를 잡는다(`lock.sh take docker-all lane4-F-08-10`). 다른 갈래의 Docker 통합 시험·kind·이미지 빌드를 멈춰야 비교의 잡음이 줄어든다. kind 이름은 `lane4-f10`, kubeconfig는 `.cache/peaket-tools/kubeconfig-lane4-f10`이다. **이번 턴에는 Docker를 쓰지 않는다.**
6. **블로그 3편의 범위** — HOT-510은 M2 초안 셋이다: ① 진입과 대기 상태 파일(K1), ② 좌석 홀드와 변경 방송(K2·K4·K5), ③ 결제 멱등과 결과 모름(K7). 셋 다 **F-08-2·F-08-8의 측정 결과를 인용**하고, 이 기능의 비교 실험이나 F-08-9의 무효 값을 새 근거로 쓰지 않는다. 게시·공개는 소유자 몫이다.
7. **장부** — V-T18은 측정 항목 하나다. 이번 계획 커밋에서 `docs/review/ledger-notes.md`에 '측정 전(미측정), 로컬은 (가)·(나)만, (다) 미측정'을 적어 `--require`가 빈칸으로 막지 않게 한다. 측정·기록 커밋에서 결과(부분·미측정)를 더한다. V-T18을 '통과'로 바꾸지 않는다.
8. **리뷰** — 새 세션이 계획·시험만 보고 본다. 보는 곳: 빈 결과·`미측정`·`skip`이 통과로 새는가, 세 구성 중 둘만 잰 사실이 결과에 드러나는가, F-08-2의 진입 도착률을 새로 재거나 값을 옮겨 적지 않는가, F-08-9의 무효·부분 값을 쓰지 않는가, F-08-8(F-08-8 K1·K2·K7)·F-08-5·F-08-6의 몫을 침범하지 않는가, 이 기능이 수치를 미리 주장하지 않는가. 지적은 시험 담당이 고치고(`Fix-By: test`), 리뷰 담당이 확인한다. 번호는 `RV0810-NN`으로 적는다.
9. **정할 것** — 14절. 추천대로 정하고 측정 전에 이 파일에 적는다.

## 3. 범위

### 3.1 하는 것

- **측정 준비(이번 턴)**:
  - `loadtest/runner/split-compare.mjs`: 세 구성 이름·진입 단계·반복 수·결제 접수 기준(NFR-005)·진입 기준(NFR-001)·비교 규칙(중앙값·편차), 인자 해석, 실행 하나의 유효 판정, 실험 묶음 판정, '차이 없음' 표시, M2 초안 계약.
  - `tools/local/compare-stage.mjs`: 같은 합본 이미지로 (가) 한 프로세스 합본과 (나) 역할별 배포를 만드는 무대 계획. 네 역할의 자원 합계가 두 구성에서 같은지 검사하고, 구성별 k6 대상 주소와 payment gRPC 주소를 낸다. (다) 10개 서비스는 로컬에서 거부한다.
  - `loadtest/plan/f10-plan.json`: 무대·구성 전환·18회 측정·보고의 차례. 게이트 `WINDOW-F0810`, 잠금 `docker-all lane4-F-08-10`.
  - `tools/perf-ledger/collect.py --experiment <묶음>:<구성>`: manifest `experiment` 칸(정본 §2.2)을 쓴다.
  - 시험 4파일(아래 8절).
- **측정(다음 역할)**:
  - (가) 합본: 복제 3, 파드 CPU 4·메모리 2GiB [가정], `PEAKET_BUNDLE_MODE=single`. (나) 역할별 배포: 역할마다 복제 3, CPU 1·메모리 512Mi [가정], 같은 합본 이미지에 `PEAKET_BUNDLE_SERVICES=<역할 하나>`, `PEAKET_BUNDLE_MODE=single`.
  - 결제 접수 300 TPS를 고정하고 진입 폭주 0%·100%·120% [가정]을 겹친다. 조건마다 3회 반복한다. 진입 100·120%의 도착률은 F-08-2의 유효 값 `{entryRate}`를 쓴다(2절 2).
  - 재는 것: 결제 접수 p99(`route:payment`, 202 응답, NFR-005 150ms)·오류율(NFR-005 가용성 99.95%), 진입 p99(NFR-001 200ms)·오류율(0.1% 미만), 구성별 CPU 스로틀 비율. 결제 확정 p99(NFR-006)는 이 기능의 판정 대상이 아니며 참고로도 새로 주장하지 않는다.
  - 두 구성의 실행을 `experiment.id = split-3way`로 묶고, 구성 사이 차이가 3회 반복 편차 안이면 '차이 없음'으로 표시한다. 편차 밖 차이는 '차이'로 표시하며 그 자체를 실패로 세지 않는다.
  - (다) 10개 서비스가 없으므로 `미측정`으로 적는다. (다)가 진입 100%에서 NFR-005를 지키는지도 `미측정`이고, ADR-0007 결정 7의 결론을 내지 않는다.
- **블로그 초안(다음 역할, 문서)**:
  - `docs/blog/` 아래 `m2-entry-wait-state.md`(K1 진입·대기 상태 파일), `m2-seat-hold-delta.md`(K2·K4·K5 좌석 홀드·변경 방송), `m2-payment-idempotency.md`(K7 결제 멱등·결과 모름). 셋 다 쓸 예정이다.
  - 각 글은 `상태: 초안`, `근거: F-08-2/F-08-8 보고서·실행 ID`, `숫자 표시: 실측(PC) 인용`을 머리에 두고, 이 기능의 비교 실험을 근거로 쓰지 않는다. 게시는 소유자 몫이다.

## 6. 측정 설계(측정 전에 못박는다)

정본 값은 옮겨 적지 않고 자리만 가리킨다. 측정을 시작한 뒤 규칙을 바꾸지 않는다. 바꿔야 하면 멈추고 감독에게 묻고 보고서에 적는다.

### 6.1 무대와 공통 규칙

- **무대**: 새 kind 클러스터(`PEAKET_CLUSTER=lane4-f10`, `cluster.mjs up` → `observability` → `v1 --redis-tls on --replicas 3 --memory-mi 2048`), Prometheus(`cluster.mjs prometheus`, 127.0.0.1:9090). 합본은 2GiB에서 뜬 F-08-8 창 1의 무대 값을 따르고, 역할별 배포도 같은 총 메모리 6GiB 안에서 역할마다 512Mi [가정]로 둔다.
- **같게 두는 것**: 코드 커밋(`b5be6b76a` 뒤 이 기능의 구현 커밋 하나), 저장소(같은 Valkey·PostgreSQL·Kafka·시뮬레이터), CPU·메모리 합계(2절 3), 부하 스크립트(같은 `v1-payment.js`·`v1-queue.js` 경로와 인자), 게이트웨이 없음, TLS 켬. 서비스 사이 호출은 두 구성 모두 gRPC로 둔다(같은 프로세스 안 함수 호출로 바꾸지 않는다).
- **구성**:
  - **`bundle`(가)**: 합본 이미지 하나, `PEAKET_BUNDLE_MODE=single`, `PEAKET_BUNDLE_SERVICES=payment-svc,purchase-svc,admission-ctrl,queue-svc`, 복제 3, 파드 CPU 4·메모리 2GiB [가정].
  - **`by-role`(나)**: 같은 합본 이미지, 역할마다 Deployment 하나(네 개), 각 Deployment `PEAKET_BUNDLE_SERVICES=<역할 하나>`, `PEAKET_BUNDLE_MODE=single`, 복제 3, CPU 1·메모리 512Mi [가정]. queue-svc Service 8080, purchase-svc Service 8081·8083, payment-svc Service 50051, admission-ctrl은 내부용. k6는 `queue-svc`·`purchase-svc` 주소로 보낸다. purchase-svc 역할 파드는 single 모드가 홀드 전용 자식을 함께 띄우므로 그 몫도 역할 자원 안에 든다.
  - **`services`(다)**: v1 10개 서비스. 로컬에 배포가 없어 실행하지 않고 `미측정`으로 적는다.
- **판정**: 실패·무효·SKIPPED·`미측정`은 통과가 아니다. 빈 결과(요청 0·표본 0·회차 0)는 통과가 아니라 무효다.
- **반복**: 조건마다 3회. 3회 미만이면 그 조건은 `미측정`이다. 재측정은 무효 회차에만 1회 더 하고, 같은 조건 3회를 넘기지 않는다.
- **장부**: 실행마다 `--record --run-id <ID> --profile local-10k --prom-url http://127.0.0.1:9090 --out <폴더>`로 남기고, 실행 ID 끝에 `-f0810`을 붙인다. `collect.py --experiment split-3way:<구성>`으로 묶는다. stage·report 실행은 장부에 넣지 않는다.
- **측정 중 규칙**: 다른 시험·빌드를 돌리지 않고, Docker 잠금은 `docker-all` 두 자리다. 다른 갈래의 Docker 작업을 멈추게 한다.

### 6.2 실행 목록(창 안 차례)

| 차례 | 무엇 | 횟수 | 판정 자리 |
| --- | --- | --- | --- |
| 0 `w2-stage` | kind·관측·v1 2GiB·Prometheus, (가) 합본 single 모드로 맞추기 | 1 | 6.1 |
| 1~3 | `bundle` × 진입 없음 × 3회 | 3 | V-T18 |
| 4~6 | `bundle` × 진입 100% × 3회 | 3 | V-T18 |
| 7~9 | `bundle` × 진입 120% × 3회 | 3 | V-T18 |
| 10 `w2-stage-by-role` | (나) 역할별 배포로 전환, 같은 저장소·시드 | 1 | 6.1 |
| 11~13 | `by-role` × 진입 없음 × 3회 | 3 | V-T18 |
| 14~16 | `by-role` × 진입 100% × 3회 | 3 | V-T18 |
| 17~19 | `by-role` × 진입 120% × 3회 | 3 | V-T18 |

- 실행 사이 1분 쉰다. 같은 구성 안에서는 시드를 새로 열지 않고 회차만 바꾼다(같은 부하·같은 데이터 조건). 구성 전환 때만 시드를 새로 연다.
- `w2-stage-by-role`는 합본 Deployment를 0으로 줄이고 `bundle` Service를 지운 뒤 역할별 Deployment·Service를 만든다. 두 구성의 파드가 동시에 뜨면 자원 합계와 대상 주소가 깨진다. 되돌릴 때도 역할별 Deployment·Service를 먼저 지운다.
- 진입 100·120% 실행은 `--entry-max-rate {entryRate}`를 쓴다. F-08-2의 유효 값이 없으면 4~9·14~19를 `skip`하고 까닭을 적는다.
- (다) 실행은 계획에 넣지 않는다. 계획에 넣으면 계획 도구가 실행하라고 보여 주므로, `미측정`을 계획 파일에 실행으로 두지 않는다.

### 6.3 부하와 재는 것

- **결제 접수**: `v1-payment.js`의 결제 접수(`route:payment`, 202)를 300 TPS 고정으로 보낸다. 결제 확정(`payment_confirm_ms`)은 이 기능의 판정 대상이 아니고, 같은 실행에서 참고로만 남기되 새 KPI 판정으로 쓰지 않는다.
- **진입 폭주**: `v1-queue.js`의 진입·대기 상태·입장 확정 경로를 0%·100%·120% [가정]로 겹친다. 0%는 진입 부하를 보내지 않고 결제만 보낸다. 100·120%의 도착률은 `{entryRate}`와 1.2배다.
- **재는 것**: 결제 접수 p99·오류율(202 아닌 5xx·429·연결 실패, 423 정지 거절은 이 무대에서 나오지 않아야 한다), 진입 p99·오류율(진입 시행·실패 포함), 구성별 CPU 스로틀 비율(파드별 `container_cpu_cfs_throttled_seconds_total` 증가분 ÷ 기간).
- **NFR 값**: 결제 접수 p99 150ms·가용성 99.95%(NFR-005), 진입 p99 200ms·오류율 0.1% 미만(NFR-001). 값은 정본 `docs/planning/02-requirements.md`와 `docs/verification.md` §3.10 K1·K7 행을 가리킨다.
- **무효 조건**: 발생기 `dropped_iterations` > 0, 시나리오 오류 > 0, 발생기 CPU 평균 80% 초과·메모리 최대 90% 초과, 호스트 포화 표시, 결제 300 TPS 아님, 3회 미만. 하나라도 걸리면 그 회차는 `invalid`이고 통과로 세지 않는다.
- **P-T5/K7**: 결제 확정 p99는 F-08-8·F-08-9의 몫이다. 이 기능은 같은 실행에서 나온 값을 성능 장부 `notes`에 참고로 남길 수 있지만, P-T5·K7 판정이나 F-08-8 결과를 바꾸지 않는다.

### 6.4 비교 규칙과 '차이 없음'

- **표본**: 조건(구성 × 진입 단계)마다 유효 회차 3개의 지표 값. 중앙값·최솟값·최댓값·편차(최댓값 − 최솟값)를 낸다.
- **차이**: 두 구성의 중앙값 차이의 절댓값. **편차**는 두 구성의 편차 가운데 큰 값이다. `차이 <= 편차`이면 '차이 없음', `차이 > 편차`이면 '차이'다. 경계값(같음)은 '차이 없음'이다. 이 규칙은 정본의 '3회 반복의 편차 안'을 두 구성에 적용한 이 계획의 선택이다(추천 적용, 2026-11-27).
- **유효 회차 3회 미만**: 비교하지 않고 `미측정`이다. 1회·2회로 '차이 없음'을 만들지 않는다.
- **(다)**: 실행이 없으므로 `미측정`이다. (다)와 (나)의 비교, (다)의 NFR-005 판정, ADR-0007 결정 7 결론을 내지 않는다.
- **결과 표시**: 결제 접수 p99·오류율, 진입 p99·오류율, CPU 스로틀 비율마다 조건별 표를 만들고, '차이 없음'·'차이'·`미측정`을 적는다. 표시는 '실측(PC)'이다.

### 6.5 멈춤 규칙(측정 전 등록)

- 무대가 15분 안에 준비되지 않으면 멈추고 감독에게 알린다.
- (나) 역할별 배포에서 네 역할이 모두 Ready가 되지 않으면 멈추고, (가) 결과만으로 V-T18을 통과시키지 않는다.
- 같은 조건에서 무효가 2회 연속 나오면 그 조건은 `미측정`으로 적고 다음으로 간다. 원인 조사는 측정 뒤 보고서에 적는다.
- 전체가 계획의 1.3배를 넘게 밀리면 감독에게 알리고 14절 '줄일 곳' 차례대로 뺀다. 3회 반복과 진입 0%는 줄이지 않는다.

### 7.2 공개 인터페이스(시험이 가정한 꼴)

- `loadtest/runner/split-compare.mjs`:
  - `SPLIT_RULES` — `{ experiment: 'split-3way', configs: ['bundle', 'by-role', 'services'], localConfigs: ['bundle', 'by-role'], entryLevels: [{ key: 'none', ratio: 0 }, { key: '100', ratio: 1 }, { key: '120', ratio: 1.2 }], reps: 3, paymentTps: 300, paymentP99Ms: 150, paymentAvailability: 0.9995, entryP99Ms: 200, entryErrorRate: 0.001, noDifference: 'max-spread' }`. 값은 정본 NFR-005·NFR-001과 §3.8에서 가져온다.
  - `UsageError` — `name === 'UsageError'`인 오류. 모르는 인자·범위 밖은 이 오류다.
  - `parseCompareArgs(argv)` → `{ config, entry, rep, paymentTps, entryMaxRate, entryRate, warmupSeconds, mainSeconds, drainSeconds, out, record, runId, promUrl }`. `--config bundle|by-role|services`(기본 없음, 필수), `--entry none|100|120`(기본 `none`), `--rep 1|2|3`(기본 1), `--payment-tps`(기본 300, 1 이상 정수), `--entry-max-rate`(100·120에서 필수, 1 이상 정수. `none`에는 주지 않는다), `--warmup`(기본 30, 0~600), `--main`(기본 120, 30~600), `--drain`(기본 20, 0~120), `--out`, `--record`, `--run-id`, `--prom-url`. `entryRate`는 `none`이면 0, 100·120이면 `Math.round(entryMaxRate × ratio)`다.
  - `assertLocalConfig(config)` — `bundle`·`by-role`은 통과, `services`는 '로컬 v1 무대에 10개 서비스 배포가 없다'는 `UsageError`.
  - `experimentFor({ config, runId })` → `{ id: 'split-3way', config }`. manifest `experiment` 칸의 꼴이다.
  - `manifestNotes({ config, entry, rep, runId })` → `'V-T18 비교: 구성 <config>, 진입 <entry>%, 회차 <rep>, 실행 <runId>'`(KPI ID를 쓰지 않는다).
  - `judgeCompareRun(o)` → `{ valid, verdict: 'pass'|'invalid', reasons, summary }`. `o`는 `{ config, entry, rep, paymentTps, entryMaxRate, entryRate, generator: { valid, dropped, cpuAvgPct, memMaxPct }, scenarioErrors, hostSaturated, metrics: { paymentP99Ms, paymentErrorRate, entryP99Ms, entryErrorRate, cpuThrottleRatio } }`. `config === 'services'`·`paymentTps !== 300`·진입 100·120인데 `entryRate`가 `Math.round(entryMaxRate × ratio)`와 다름·`generator.valid !== true`·`dropped > 0`·`scenarioErrors > 0`·`cpuAvgPct > 80`·`memMaxPct > 90`·`hostSaturated`·지표 없음이면 `invalid`. 아니면 `pass`(값이 목표 밖인 것은 비교 결과이지 이 판정의 실패가 아니다. NFR 판정은 `(다)`에만 한다).
  - `compareSamples(values)` → `{ count, median, min, max, spread }`. 빈 배열은 `count: 0`이고 나머지는 `null`(0이 아니다). 짝수 개는 가운데 두 값의 평균이다.
  - `judgeNoDifference(a, b)` → `{ valid, noDifference, diff, spread, reason }`. 두 표본이 3개 미만이면 `valid: false`, `noDifference: null`. 아니면 `diff = |medianA − medianB|`, `spread = max(spreadA, spreadB)`, `noDifference = diff <= spread`.
  - `compareExperiment(runs)` → `{ verdict: 'complete'|'partial'|'invalid'|'fail', problems, missing, comparisons, services, adr0007 }`. `runs`는 `{ config, entry, rep, valid, metrics }`의 배열이다. `valid !== true`인 실행은 그 회차가 없는 것으로 센다. 구성·진입 단계마다 유효 3회가 없으면 `missing`에 넣고 `invalid`. `(다)` 실행이 없으면 `services: '미측정'`, `adr0007: '미측정'`, `verdict: 'partial'`. `(다)` 실행이 있으면 `(나)`와 `(다)`를 비교하고, `(다)`의 진입 100% 3회 가운데 하나라도 결제 접수 p99 `>= 150ms`(NFR-005 '150ms 미만') 또는 오류율 `> 0.0005`이면 `adr0007: 'fail'`, `verdict: 'fail'`. 모두 갖추고 `(다)`가 기준 안이면 `complete`. 편차 밖 차이는 `comparisons[].noDifference: false`일 뿐 `verdict`를 `fail`로 만들지 않는다.
  - `renderComparison(result)` → 긴 글. 조건별 중앙값·편차·'차이 없음'·'차이'·`미측정`을 적고, `K1`·`K2`·`K7`·`30,000`·`100만`을 쓰지 않는다.
  - `M2_DRAFTS` — `[{ id: 'm2-entry-wait-state', title: '진입과 대기 상태 파일', kpis: ['K1'], evidence: ['F-08-2'], status: 'draft', publish: 'owner' }, { id: 'm2-seat-hold-delta', title: '좌석 홀드와 변경 방송', kpis: ['K2', 'K4', 'K5'], evidence: ['F-08-2', 'F-08-8'], status: 'draft', publish: 'owner' }, { id: 'm2-payment-idempotency', title: '결제 멱등과 결과 모름', kpis: ['K7'], evidence: ['F-08-8'], status: 'draft', publish: 'owner' }]`.
  - `validateDrafts(drafts)` → `{ ok, problems }`. 3편 정확히, ID 겹침 없음, `status === 'draft'`, `publish === 'owner'`, `evidence`가 F-08-2·F-08-8만, `claims`가 없거나 비었음. 아니면 `ok: false`와 까닭.
- `tools/local/compare-stage.mjs`:
  - `LOCAL_ROLES` — `['payment-svc', 'purchase-svc', 'admission-ctrl', 'queue-svc']`(합본 켜는 차례).
  - `ROLE_RESOURCES` — 역할마다 `{ cpu: 1, memoryMi: 512 }` [가정].
  - `compareStagePlan({ config, replicas = 3, roles = ROLE_RESOURCES })` → `{ config, mode: 'single', replicas, deployments, totals }`. `bundle`은 Deployment 하나(`name: 'bundle'`, `services: LOCAL_ROLES`, `cpu: 4`, `memoryMi: 2048`), `by-role`은 역할마다 Deployment 하나(`name: <역할>`, `services: [<역할>]`, `cpu: 1`, `memoryMi: 512`). `totals`는 `{ cpu, memoryMi }`이고 두 구성이 같아야 한다. `config === 'services'`는 `RangeError`, 복제 0·역할 빠짐·모르는 역할·CPU/메모리 0 이하도 `RangeError`.
  - `assertSameTotals(a, b)` — 두 계획의 `totals`가 다르면 `RangeError`.
  - `stageUrls(config, namespace = 'v1')` → `{ queueUrl, purchaseUrl, holdUrl, paymentGrpc }`. `bundle`은 `bundle.<ns>` 세 주소, `by-role`은 `queue-svc.<ns>:8080`, `purchase-svc.<ns>:8081`, `purchase-svc.<ns>:8083`, payment gRPC `payment-svc.<ns>:50051`. `services`는 `RangeError`.
  - `stageEnv(config)` → `{ payment: { PEAKET_GRPC_HOST }, purchase: { PEAKET_PAYMENT_GRPC_ADDR } }`. `bundle`은 payment `127.0.0.1`·purchase `127.0.0.1:50051`, `by-role`은 payment `0.0.0.0`·purchase `payment-svc.<ns>:50051`이다. 같은 프로세스가 아닌 역할별 배포에서 gRPC가 파드 밖으로 열리게 한다. `services`는 `RangeError`.
- `loadtest/plan/f10-plan.json`: `plan`·`title`·`created`·`basis`·`state_file`·`start_gate`·`gates`(객체)·`runs`. 실행마다 `n`·`key`·`group`·`title`·`estimate_min`·`stage`·`conditions`·`commands`(`{label, argv}`)·`criteria`·`ledger`·`artifact`·`gate`. `bat025-plan.mjs`의 `validatePlan`을 지난다.
- `loadtest/run.mjs v1 compare …`·`v1 compare-report …`: 인자는 7.2의 파서와 같다. `v1 compare`는 두 k6 실행(결제·진입)을 같은 시작 표시로 띄우고, 두 요약을 한 `summary.json`으로 합친다. `v1 compare-report`는 실행 폴더들을 읽어 `comparison.json`과 긴 글을 쓴다.
- `tools/perf-ledger/collect.py --experiment <묶음>:<구성>`: `manifest.experiment = { id, config }`. `묶음`·`구성`은 `[a-z0-9-]+`이고 콜론 하나로 가른다. 없으면 `experiment: null`.
