# 기능 계획: F-08-3(MSR-030·MSR-080 — M6 블로그·용량 산정서·비용 리포트·DORA 추세)

- **진행**: 계획·시험(측정 대조)·리뷰·문서 끝(2026-11-26). TR-01~14 반영, 문서 6종 작성·검증 완료.
- **문서**: 사실 대장 → 용량 → 비용 → DORA → M6 → `docs/blog/README.md` M6 행을 작성했다. 8/8·trace-check 통과.
- **무엇**: BUILD_ORDER '기능 단위 계획' F-08-3(갈래 4, 등급 B, MSR-030·MSR-080, WBS 3.50일, 단계 줄 `MSR-030 wbs 6.1.2`·`MSR-080 wbs 6.4.1`, 측정 창 4)의 작업 목록이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **쉬운 말**: 이 기능은 새로 부하를 걸지 않는다. F-08-2의 MSR-020(진입 서버 비례)과 F-08-8의 K1·K2·K7 After는 끝났지만, F-08-2의 MSR-010(100만 외삽)은 **V-T4 '판정 못 함'**이고 보고서가 없다. 이 기능은 그 보고서들과 정본의 설계 목표를 읽어 ① 기술 블로그 M6 한 편의 초안, ② 용량 산정서, ③ 비용 리포트, ④ DORA 추세 보고서를 만든다. 새 숫자를 만들지 않고, 잰 것과 못 잰 것을 구분해 적는 것이 핵심이다.
- **바탕**: 작업 폴더 `D:/ticketpass-freeze-F-08-3`, 가지 `freeze/lane4-F-08-3`, 출발 `origin/feature/lane4-F-08-2-refresh` = `19b33ba85`(F-08-2 측정 보고서 포함). 동결 트랙이라 `develop`·`release/1.0.0`에 합치지 않는다(ADR-0386 결정 4).
- **차례**: F-08-3은 B등급이지만 이번 동결 트랙에서는 소유자 지시로 **계획 → 시험(측정 대조) → 리뷰(새 세션) → 지적 반영 → 구현/문서 → 기록**으로 돈다. ADR-0373의 B등급 차례(계획 → 시험 → 구현)에 리뷰를 더한 것이다. 리뷰 담당은 계획·시험·구현을 맡지 않은 새 세션이고, 구현 담당은 시험을 고치지 못한다.
- **한 줄 결론**: 이 기능의 일은 새 측정이 아니라 **인용과 경계 짓기**다. F-08-2·F-08-8 보고서와 정본의 설계 목표를 한 곳(사실 대장)에 모으고, 그 값만 보고서에 쓰게 하는 정적 시험을 먼저 만든다. 새 수치 주장·Docker·kind·k6는 없다.

## 2. 감독에게(정할 것과 이 계획의 답)

1. **새 측정을 하지 않고, 산출물은 정본이 아니라 검토 기록에 둔다** — 창 1(F-08-8)과 창 2(MSR-020)의 결과만 읽는다. MSR-010(100만 외삽)은 재지 않았고 보고서가 없으며 V-T4는 '판정 못 함'이다. Docker·kind·k6·Docker 잠금을 쓰지 않는다. 용량·비용·DORA 보고서는 `docs/review/measurements/`, M6 초안은 `docs/blog/`에 두고, 정본(`docs/infra.md` §11·`docs/verification.md` 등)은 고치지 않는다.
2. **DORA는 '추세 판단 불가'가 정직한 답이고, 비용은 전부 [추정]이다** — DORA 값은 GitHub Deployment 기록에서 나오는데 이 트랙에는 없고 GitHub API를 부르지 않는다. 주별 표를 `자료 없음`으로 채우고 추세선을 그리지 않는다. 비용 단가는 `docs/infra.md` §11의 2026-10-28 표만 쓰고, CloudFront처럼 단가가 없는 항목은 '단가 없음: 미계산'으로 적는다.
3. **200만은 설계 목표이고, M6는 F-08-7의 숫자 카드 다섯 개만 쓴다** — NFR-021·architecture §9.5의 200만·250만·300만, 합산 동시 입장은 설계 목표다. F-08-2의 100만 외삽을 2배 해서 '200만 외삽'을 만들지 않는다. M6는 카드 1~5 밖의 숫자를 쓰지 않고, 값이 없으면 '판정 못 함'·'미달'·'무효'로 적는다.
4. **블로그 게시는 소유자 몫이고, 구현 전에 리뷰 지적을 반영한다** — 초안과 상태 줄까지만 한다. TR-01~10을 계획·시험에 반영한 뒤 새 고정점을 만들고, 구현 담당이 사실 대장 → 용량 → 비용 → DORA → M6 → README 순서로 쓴다.

## 5. 장부 범위

- `node tools/ci/ledger.mjs --batch F-08-3`: **항목 0개, 빈칸 0, 등급 B**. BUILD_ORDER F-08-3 행의 '장부 없음: 시험·측정으로 본다'와 같다. `--require`는 통과한다(2026-11-26 확인).
- 이 기능은 장부 항목을 더하거나 바꾸지 않는다. F-08-2의 V-T4·V-T5·V-T17, F-08-8의 Q-T2·S-T1·P-T1 상태도 바꾸지 않는다. `docs/review/ledger-notes.md`를 고치지 않는다.
- 판정은 정적 시험 `MSR-030 ①~②`·`MSR-080 ①~⑥`과 문서 점검으로 한다. 구현 뒤 `node --test --test-reporter=junit --test-reporter-destination=<보고서> tools/ci/f083-reports.test.mjs`로 보고서를 만들고, `node tools/ci/trace-check.mjs --ids "MSR-030,MSR-080" --report <보고서>`로 시험 이름과 ID를 대조한다. 기준 트리에서는 통과한 시험이 없으므로 이 대조는 구현 뒤에 한다.
