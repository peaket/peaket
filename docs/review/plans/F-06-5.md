# F-06-5 계획 — 팬 조회·문의·계좌번호 탐지·담당자 가림 (동결 로컬)

- **무엇**: 기능 F-06-5(고객·CS·법정, B등급, GAT-320·GAT-330, wbs 5.8.4)의 동결 로컬 작업 계획이다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다.
- **등급·차례**: B등급(`Batch-Grade: B`). 감독 지시(2026-11-27)에 따라 **계획 → 시험 → 시험 리뷰(새 세션) → 반영 → 구현 → 기록**으로 한다. ADR-0373 결정 3의 B등급 기본 차례(계획 → 시험 → 구현)에 시험 리뷰를 더한 것은 이 동결 트랙의 지시다. 이번 작업은 **계획·시험·기준 트리 실패 확인·게이트**까지 하고 시험 리뷰를 받을 준비에서 멈춘다. 구현은 시험 리뷰 뒤에 시작한다.
- **동결 로컬 범위**: v1 출시 범위 밖이다(ADR-0373 결정 2, ADR-0386 결정 4·5, `docs/release/v1-scope.md` F-06-5 `frozen-local`). `freeze/lane2-F-06-5` 가지와 `D:/ticketpass-freeze-F-06-5` 워크트리에서만 개발하고 `develop`·`release/1.0.0`에 합치지 않는다. 출시 마이그레이션·릴리스 플래그·`deploy/` 값은 건드리지 않는다.
- **바탕**: 출발 `51e814fe`(`origin/freeze/lane2-F-06-4`, F-06-4 완료 포함, 2026-11-27). 가지 `freeze/lane2-F-06-5`. 시험은 Docker 없이 단위·HTTP·gRPC 경계로 돌린다(통합 시험은 구현 뒤 게이트에서 Docker 잠금을 잡고 돌린다).
- **정본**: `docs/features/transfer-refund.md` §7.1·§7.3·§11(R-T27), `docs/security/data-classification.md` '고객 문의'·'은행 계좌번호' 행, `docs/security/asvs/support.md`, `docs/planning/03-policies-glossary.md` POL-038·POL-027, `docs/data.md` `inquiry`·`inquiry_message`·`admin_data_access`, `docs/api/openapi.yaml` `support` 태그의 `/v1/inquiries*`·`/v1/ops/cases/{caseId}/replies`·`/v1/ops/fan-lookups`·`/v1/ops/fans*`·`Inquiry*`·`OpsFan*`·`CaseReply`, `docs/api/proto/peaket/core/v1/core.proto` `SupportCaseService`, `docs/design/d5-screen-blueprint.md` §5.30(SCR-056)·§7.6(SCR-045)·§7.14(SCR-066), `docs/planning/04-ia-flows-screens.md` SCR-066, `docs/security/authz-matrix.md` §4.1·§4.3·AZ-T8, ADR-0066·0148·0173·0238·0372·0373·0381·0386. 값은 이 파일에 옮기지 않고 위치만 가리킨다.

## 2. 정본 빈칸과 이번에 정하는 것(추천 적용, 2026-11-27)

정본에 없어 구현이 임의로 정할 수 없는 것만 적는다. 구현 전에 정본(괄호의 위치)에 쓴다. 방향을 바꾸는 결정은 없다.

1. **접수 번호와 하루 한도**(`docs/data.md` `inquiry.number`, openapi `createInquiry`): 접수 번호는 KST `YYMM` + 그 달 일련번호 4자리(`Q-2611-0042`)이고 `inquiry.number` 유일이다. 일련번호는 그 달 1부터 시작해 9,999를 넘으면 500 `inquiry-number-exhausted`다(시험은 9,999를 만들지 않는다). 계정당 하루 접수는 10건 [가정]이고 11번째는 429 `inquiry-daily-limit`이다. 한도는 KST 날짜로 세고 상태를 가리지 않는다. **`Idempotency-Key`는 정본 그대로 필수다**(openapi `IdempotencyKey` `required: true`, `POST /v1/inquiries`·`POST /v1/inquiries/{id}/messages`). 없거나 UUIDv4가 아니면 400 `idempotency-key-invalid`, 같은 키 같은 본문은 같은 결과를 다시 주고(201), 같은 키 다른 본문은 422 `idempotency-key-reused`, 첫 요청이 처리 중이면 409 `idempotency-request-in-progress`다. 보관은 24시간 [가정]이다(guidelines §4).
2. **길이·정규화**(openapi `InquiryCreate`, ASVS 1.1.1·1.3.3): 제목은 NFC 정규화 뒤 grapheme 5~50자, 내용·추가 문의·답변은 NFC 정규화 뒤 grapheme 10~2,000자(답변은 1~2,000자)다. C0/C1 제어 문자와 양방향 제어 문자(U+202A~U+202E·U+2066~U+2069)는 지운다. 요청 본문 상한은 openapi 그대로 제목 200자·내용 8,000자이고 넘으면 422 `invalid-body`다. `additionalProperties: false`이고 모르는 칸은 400 `invalid-body`다.
3. **기한**(transfer-refund §7.1, openapi `Inquiry`): 영업일은 KST 날짜로 토·일과 공휴일 파일(`PEAKET_HOLIDAY_CALENDAR_FILE`, purchase-svc·ops-svc와 같은 파일)의 날을 뺀다. 'N영업일'은 접수 시각의 같은 KST 시각에서 영업일을 N번 넘긴 때다. 일반·`MINOR_CONTRACT_CANCEL`·`RESALE_POST_REPORT`는 결과 3영업일 [가정], `SELLER_DISPUTE`는 진행 3영업일·결과 10영업일이다. 응답의 `dueAt`은 결과 기한이다.
4. **관련 주문**(openapi `InquiryCreate.orderRef`, ASVS 2.2.3): `orderRef`는 이 계정의 예매번호·굿즈 주문번호만 받는다. 다른 계정·없는 번호는 422 `order-not-owned`, 주문 원천을 확인하지 못하면 503 `order-lookup-unavailable`이다. `orderSummary`는 서버가 주문 원천에서 만들어 싣고 요청 값은 저장하지 않는다.
5. **CS 건 잇기**(transfer-refund §7.1, `docs/data.md` `cs_case`): 같은 트랜잭션에 문의·첫 기록·Outbox `support.cases-requested`를 쓴다. `eventKey`와 `sourceId`는 문의 ID, `kind`는 `SELLER_DISPUTE`면 `DISPUTE`, `MINOR_CONTRACT_CANCEL`이면 같은 이름, 그 밖(외부 되팔이 신고 포함)은 `INQUIRY`이고 `category`는 문의 유형이다. Outbox에는 본문·제목·계정·주문 번호를 싣지 않는다(본문 없음, ASVS 14.2.1). ops-svc가 건을 열면 core 내부 API로 건 ID를 되적어 `inquiry.case_id`를 채운다.
6. **상태 기계와 추가 문의**(ASVS 2.3.1, openapi `Inquiry.status`·`createInquiryMessage`, asyncapi `CaseRequested.followUp`): `RECEIVED` → `IN_PROGRESS` → `ANSWERED` → `CLOSED`. 추가 문의는 `ANSWERED`에서 `IN_PROGRESS`로 되돌리고, `CLOSED`는 주인에게도 409 `inquiry-closed`다. 담당자의 진행 경과(`PROGRESS`)는 `RECEIVED`·`ANSWERED`를 `IN_PROGRESS`로, 답변(`ANSWER`)은 `ANSWERED`로 만든다. 추가 문의를 받으면 같은 트랜잭션에 Outbox `support.cases-requested`를 한 건 더 쓰고 `followUp: true`, `eventKey`는 그 기록의 `messageId`, `sourceId`는 문의 ID로 둔다(ops가 기존 건을 다시 처리 중으로 돌린다). 답변 뒤 14일 [가정] 동안 추가 문의가 없으면 배경 작업이 닫고 `purge_at`을 `closed_at + 3년`으로 쓴다(파기는 F-02-4).
7. **CS 답변 경로**(openapi `createOpsCaseReply`, core.proto `SupportCaseService`): `cs_agent`만 부른다(`x-peaket-roles` 그대로. `cs_lead`·operator·commander·viewer는 403). 문의가 이어진 건(`INQUIRY`·`DISPUTE`·`MINOR_CONTRACT_CANCEL`이고 `target_ref`가 문의 ID)만 받고 그 밖은 409 `case-not-inquiry`, 해결된 건은 409 `case-already-resolved`, 닫힌 문의는 409 `inquiry-closed`다. `Idempotency-Key`가 필요하고(없거나 틀리면 400 `idempotency-key-invalid`), 그 값을 core `AddInquiryReply.request_id`로 쓴다. 감사 체인에 `CS_CASE_REPLIED`(건·문의·종류·길이, 본문 없음)를 남기고, core가 실패하면 503 `support-unavailable`이다. 건 해결(`PATCH` RESOLVED)은 core `CloseInquiry`를 먼저 부르고 성공해야 지역 건을 닫는다(실패 503).
8. **담당자 가림**(transfer-refund §7.3, ASVS 8.1.2): 팬 응답의 `authorDisplay`는 `AGENT`면 늘 '피켓 고객센터'이고, 응답·알림에 담당자 관리 계정 ID·이름·이메일을 싣지 않는다. ops→core `acted_by`와 감사 기록에만 둔다. ops의 건 상세는 담당자 계정 ID를 실을 수 있지만(콘솔이 이름을 보인다), 팬 문의 응답·문의 상세에는 싣지 않는다.
9. **계좌번호 꼴 탐지·가림**(data-classification '고객 문의', 법률 행): 하이픈·공백을 뺀 10~14자리 [가정]이고 `01x` 휴대폰·`20`으로 시작하는 13자리 예매번호·`ord-` 뒤 주문번호는 뺀다. 공용 부품 `@peaket/validation/account-number`(`findAccountNumbers`·`maskAccountNumbers`)를 서버·콘솔·웹이 함께 쓴다. **저장값은 바꾸지 않는다**(저장 전 가림은 법률 검토 wbs 7.4.1). 로그·Outbox·감사에는 본문을 싣지 않으므로 숫자가 남지 않는다. ops가 콘솔에 주는 문의 기록 응답은 같은 패턴을 `(계좌번호 지움)`으로 바꿔 보낸다. 찾는 값은 URL·쿼리에 싣지 않는다(팬 찾기는 POST 본문, 문의는 ID만 경로).
10. **팬 찾기와 열람**(openapi `/v1/ops/fan-lookups`·`/v1/ops/fans*`, authz-matrix §4.3): 찾는 값은 `orderNo`·`reservationNo`·`memberCode` 가운데 정확히 하나다(0·2개 이상 400). `operator`·`commander`·`cs_agent`·`cs_lead`가 찾기·요약·열람을 하고, 목록 넷(주문·티켓·양도·대기 참여)은 `cs_agent`·`cs_lead`만, **건 탭은 openapi `listOpsFanCases` 그대로 네 역할 모두** 본다(operator·commander 포함, viewer 403). 대기 참여 탭은 openapi 그대로 `caseId`가 필수이고, 그 계정의 본인 확인 요청 건(`selfRequestCaseIds`)일 때만 200이다(`caseId` 없음 400 `invalid-query`, 그 계정의 것이 아니면 403 `self-request-required`, 없는 계정 404). 원문 열기는 `fields` 1~3개(중복 불가)·`reason` 5~500자·선택 `orderId`이고, `EMAIL`+`orderId`는 422, 고른 칸 밖의 값은 싣지 않는다. `orderId`가 그 계정의 주문이 아니면 404, 보존이 끝난 주문이면 410 `retention-ended`다. 서버는 원문을 주기 전에 `admin_data_access`(action `VIEW_UNMASKED`, target_kind `FAN_PROFILE`, `sourceIp`·`sourceService`·`targetCount`·`recordedAt`)와 감사 체인(`ADMIN_DATA_ACCESS_RECORDED`, 행 ID)을 같은 트랜잭션에 쓰고, 쓰지 못하면 503 `access-log-unavailable`로 원문을 주지 않는다. 계정당 하루 200회 [가정]를 넘으면 429 `fan-lookup-rate-limited`다. 응답은 `private, no-store`다.
11. **팬 조회 원천**(openapi `OpsFanOrder`·`OpsFanTicket`·`OpsFanTransfer`·`OpsFanQueueEntry`): ops-svc는 원천 포트(`FanProfileSource`·`FanOrderSource`·`FanTicketSource`·`FanTransferSource`·`FanQueueSource`)로만 읽고, 시작 조립이 내부 HTTP 어댑터를 잇는다. 이 기능은 포트·메모리/DB 집계·가림·열람 기록·화면 값을 끝내고, 실제 원천 서비스의 내부 읽기 경로는 §9의 합성 몫으로 남긴다. 원천이 없으면 목록은 503 `fan-lookup-unavailable`이고 빈 목록으로 속이지 않는다.
12. **화면 연결 범위**(d5 §5.30·§7.6·§7.14): SCR-066 콘솔 화면과 SCR-045 문의 스레드·답변은 실제 API에 잇는다. 팬 SCR-056 세 화면은 기존 목업을 이번에 실제 API로 바꾸지 않고, 서버 응답 모양·오류 문구를 시험으로 고정한다(화면 연결은 같은 영역의 뒤 화면 묶음). 브라우저 확인은 마지막 날 §7 대본으로 한 번 한다.

## 4. 공개 인터페이스(시험이 기대는 모양)

### 4.1 core HTTP

- `POST /v1/inquiries` — `Idempotency-Key`(UUIDv4) **필수**, 본문 `{category, orderRef?, title, body}`. 201 `{inquiryId, number, dueAt}` + `Location`. 400 `invalid-body`(모르는 칸)·`idempotency-key-invalid`(없음·UUID 아님), 422 `invalid-body`(유형·길이·남의 주문)·`idempotency-key-reused`(같은 키 다른 본문), 409 `idempotency-request-in-progress`, 429 `inquiry-daily-limit`, 503 `order-lookup-unavailable`. `private, no-store`.
- `GET /v1/inquiries?status=&page=&limit=` — `InquiryPage`(`items`·`total`·`page`·`limit`). 내 것만 최근 순, `messages` 없음, `authorDisplay` 없음. 400 `invalid-query`(모르는 상태·page<1·limit 1~50 밖).
- `GET /v1/inquiries/{inquiryId}` — `Inquiry`(상세, `messages` 시간 순, `authorDisplay` '피켓 고객센터' 또는 '나', 담당자 ID·이름 없음). 남의 것·없는 것 같은 404. 열면 `fan_viewed_at`을 남긴다. `private, no-store`.
- `POST /v1/inquiries/{inquiryId}/messages` — `Idempotency-Key` **필수**, 본문 `{body}`. 201 `InquiryMessage`. 400 `idempotency-key-invalid`·404·409 `inquiry-closed`·422 `invalid-body`·`idempotency-key-reused`. 추가 문의면 Outbox `followUp: true`(eventKey = messageId).
- 내부 HTTP `POST /internal/v1/inquiries/{inquiryId}/case` — 내부 토큰, `{caseId}`. 200 `{changed}`. ops가 건 ID를 되적을 때 쓴다(멱등).

### 4.2 core gRPC(`SupportCaseService`, core.proto 그대로)

- `GetInquiryRecord` — 내부 토큰 + `x-peaket-caller: ops-svc`. 문의·기록·계정 ID를 준다. 없으면 `NOT_FOUND`, 신원 틀리면 `PERMISSION_DENIED`.
- `AddInquiryReply` — `request_id`(멱등)·`kind`·`body`·`acted_by`. `RECORDED`·`INQUIRY_CLOSED`·`INVALID_ARGUMENT`. 같은 `request_id` 같은 본문은 같은 답, 다른 본문은 `ALREADY_EXISTS`. `acted_by`·담당자 ID는 응답 기록에 싣지 않는다.
- `CloseInquiry` — `request_id`·`acted_by`. `CLOSED`·`closed_at`. 같은 요청은 같은 답.

### 4.3 ops HTTP

- `POST /v1/ops/cases/{caseId}/replies` — `cs_agent`, `Idempotency-Key` 필수, 본문 `{kind:'ANSWER'|'PROGRESS', body}`. 201 `InquiryMessage`(`authorDisplay:'피켓 고객센터'`, 담당자 ID 없음). 403·404·409(`case-not-inquiry`·`case-already-resolved`·`inquiry-closed`)·422 `invalid-body`·503 `support-unavailable`.
- `PATCH /v1/ops/cases/{caseId}` — 기존 그대로. `status: RESOLVED`이고 문의가 이어진 건이면 `CloseInquiry`를 먼저 부르고 성공해야 200. 실패 503.
- `GET /v1/ops/cases/{caseId}` — 기존 `CsCaseDetail.messages`(정본 칸, 새 객체를 더하지 않는다)에 문의 기록을 시간 순으로 싣는다. `body`는 계좌번호 꼴을 가린다. `actedBy`·담당자 ID·이름은 없다.
- `POST /v1/ops/fan-lookups` — 본문 셋 중 하나. 200 `OpsFanSummary`(가린 값). 400·403·404·429 `fan-lookup-rate-limited`.
- `GET /v1/ops/fans/{accountId}` — `OpsFanDetail`(가린 값만, `selfRequestCaseIds`). 404.
- `POST /v1/ops/fans/{accountId}/unmaskings` — `{fields, reason, orderId?}`. 200 `OpsFanUnmasking`(고른 칸만·사유·시각). 400·403·404(그 계정의 주문이 아님)·410 `retention-ended`·422·429·503 `access-log-unavailable`. `private, no-store`.
- `GET /v1/ops/fans/{accountId}/orders|tickets|transfers` — cs_agent·cs_lead, 페이지. `queue-entries`는 `caseId` 필수(400 `invalid-query`)이고 그 계정의 본인 확인 요청 건일 때만 200(아니면 403 `self-request-required`). `cases`는 네 역할 모두. 원천이 없으면 503 `fan-lookup-unavailable`(빈 목록으로 속이지 않는다).

### 4.4 시험과 구현이 함께 따르는 키트·포트 모양

```ts
// core-svc AppModule.register({ memory:true, support })에 더한다
interface CoreSupportInquiryWiring {
  inquiries?: InquiryStore;                 // 없으면 메모리
  orders?: OrderDirectory;                  // {ownerOf(orderRef), summaryOf(orderRef)}
  inquiryNotifier?: FanNotifier;            // {send({inquiryId, accountId, event:'ANSWER'|'PROGRESS'})}
  holidays?: string[];                      // 'YYYY-MM-DD' KST 공휴일(시험)
  now?(): number;
}
// 전역 키트: Symbol.for('peaket.core.support-kit') → { inquiries:{rows(), messages(), failNext(op:'saveInquiry'|'saveMessage'|'saveOutbox'), closeIdle(nowMs)}, inquiryGrpcHandlers }
// ops-svc AppModule.register({ memory:true, supportCases, fanLookup })에 더한다
interface OpsSupportCasesWiring {
  reply(i: { requestId: string; inquiryId: string; kind: 'ANSWER'|'PROGRESS'; body: string; actedBy: string }): Promise<{ result: 'RECORDED'|'CLOSED'; message?: InquiryMessageRecord; status: string }>;
  close(i: { requestId: string; inquiryId: string; actedBy: string }): Promise<{ status: 'CLOSED'; closedAtMs: number }>;
  read(inquiryId: string, actedBy: string): Promise<InquiryRecord | undefined>;
}
interface OpsFanLookupWiring {
  profile?: { get(accountId: string): Promise<FanProfile | undefined>; resolve(i: { orderNo?: string; reservationNo?: string; memberCode?: string }): Promise<string | undefined> };
  orders?: { list(accountId: string, page: { cursor?: string; limit: number }): Promise<{ items: FanOrder[]; nextCursor: string | null }>; unmask(accountId: string, orderId: string): Promise<{ name?: string; phone?: string } | { error: 'not-found'|'gone' }>; };
  tickets?: { list(accountId: string, page: { cursor?: string; limit: number }): Promise<{ items: FanTicket[]; nextCursor: string | null }> };
  transfers?: { list(accountId: string, page: { cursor?: string; limit: number }): Promise<{ items: FanTransfer[]; nextCursor: string | null }> };
  queueEntries?: { list(accountId: string, page: { caseId: string; limit: number }): Promise<{ items: FanQueueEntry[]; nextCursor: string | null }> };
  access?: AdminDataAccessStore;            // {append({adminAccountId, actorRole, action, targetKind, reason, fields, sourceIp, sourceService, targetCount, occurredAtMs, recordedAtMs, retainUntilMs})}
  now?(): number;
}
```

- 위 `InquiryMessageRecord`는 `{messageId, authorKind, kind, body, createdAtMs}`이고, `InquiryRecord`는 core.proto `GetInquiryRecordResponse`와 같은 칸이다.
- `CsCase`에 `accountId`(nullable)를 더한다. `POST /internal/v1/cs-cases`로 `INQUIRY`·`DISPUTE`·`MINOR_CONTRACT_CANCEL` 건을 열 때 core `GetInquiryRecord`의 `account_id`를 같은 트랜잭션에 채운다. `CsCase` 응답에는 싣지 않고 팬 조회 건 탭만 읽는다.
- `CsCaseDetail.messages`는 정본 칸이다. ops는 core `GetInquiryRecord`의 기록을 이 칸에 옮기고, 본문의 계좌번호 꼴만 `(계좌번호 지움)`으로 바꾼다. `authorDisplay`는 `AGENT`면 '피켓 고객센터'다.
- 원천 포트가 하나라도 없으면 그 탭은 503 `fan-lookup-unavailable`이고 빈 목록을 주지 않는다. 찾기·요약은 `profile`이 없으면 503이다.
- 시작 조립(`main.ts`)은 시험 조립과 따로 본다. 단위 시험은 앱 조립(키트)으로, 시작 조립 시험은 env만 읽는 얇은 시험으로 확인한다(§5).

## 6. 실제 서버 연결과 차례

- **서버 ↔ 저장소**: core-svc `test-int/support-inquiries.int.test.ts`(구현 뒤)가 실제 PostgreSQL 18에서 0055의 표·CHECK·인덱스·유니크·`purge_at`과 접수·답변·닫기를 본다. ops-svc `test-int/fan-lookup.int.test.ts`가 0041의 `admin_data_access`·`cs_case.account_id`와 열람 기록을 본다. Docker 잠금은 `lane2-F-06-5` 하나만 잡고 `docker-all`은 쓰지 않는다(F-08-4 측정 중).
- **서비스 사이**: ops→core `SupportCaseService`는 단위 시험에서 **proto 설명자로 세운 실제 gRPC 서버**로 본다. core→purchase 관련 주문·core→ops 건 ID 되적기는 문서화된 계약을 구현한 로컬 HTTP 서버로 본다. 팬 조회 원천은 이 기능의 포트 계약을 구현한 로컬 서버로 본다(§9 합성 몫).
- **화면 ↔ 서버**: SCR-066·SCR-045 문의 스레드는 ops-svc 실제 HTTP로, SCR-056 팬 세 화면은 서버 응답 모양을 해석 시험으로 고정한다. 브라우저 확인은 마지막 날.
- **경계**: F-06-4 core support 모듈에 문의를 더하되 `appeal` 표·경로·시험은 그대로 둔다. F-06-2 CS 건 종류·기한·배정 규칙은 그대로 쓰고 `cs_case.account_id`만 더한다. F-06-8 알림은 `FanNotifier` 포트로만 닿는다.

## 7. 브라우저 확인 대본(마지막 날)

이 기능은 화면을 바꾸므로 마지막 날 한 번 본다(ADR-0373 결정 3). 이번 턴에는 하지 않는다.

2. 내용에 `110-123-456789`를 넣으면 확인 창이 뜨고, '지우고 보내기'를 고르면 `(계좌번호 지움)`으로 바뀐다. 그대로 보내도 접수된다.
3. `cs_agent`가 SCR-045에서 그 문의를 열어 진행 경과·답변을 보내고, 팬 SCR-056 상세에 '피켓 고객센터'로 보인다(담당자 이름 없음).

5. 콘솔 오류·CSP 위반 0, 브라우저 저장소에 문의 본문·원문 개인정보 0, URL에 회원 코드·계좌번호 0.

## 9. 정리 목록으로 보낼 것

- **합성 때 확인할 몫**: 팬 조회 원천 넷(identity 프로필·회원 코드, purchase 주문·예매자 원문, ticket 티켓·양도, queue 대기 참여)의 내부 읽기 API. 이 기능은 포트와 로컬 서버 시험까지 하고, 실제 원천 연결은 합성 때 서비스 소유자와 경로·권한을 맞춘다. 원천이 없으면 503이고 빈 목록으로 속이지 않는다.
- **합성 때 확인할 몫**: core `inquiry.case_id`를 ops가 되적는 내부 HTTP와 F-06-2 건 열기(`receive-case-requested`)의 `account_id` 채우기. 두 가지가 같은 트랜잭션·재전송에서 한 번만 도는지.
- 문의 닫힘 뒤 3년 파기 작업은 F-02-4(동결). 이 기능은 `purge_at`만 남긴다.
- 외부 되팔이 게시물 수집본 등록·조사 화면은 F-04-13(동결).
- 팬 문의 화면(SCR-056) 실제 API 연결과 브라우저 확인은 뒤 화면 묶음·마지막 날.
- `apps/web/src/_pages/inquiry-new/model/account.ts`를 공용 부품으로 바꾼 뒤 웹 단위 시험이 그대로인지 확인한다(중복 구현 금지).
- CS 답변 본문에 계좌번호 꼴이 들어오면 콘솔 표시에서 가리지만 저장값은 바꾸지 않는다. 담당자에게 입력 전 안내를 띄우는 일은 뒤 화면 묶음.
- `admin_data_access`의 2년 보존·정리 작업과 법정 접속기록 대조는 F-02-4·F-01-8(동결).
- 이 기능이 더하는 problem type 넷(`case-not-inquiry`·`support-unavailable`·`fan-lookup-unavailable`·`account-number-in-reply`)은 구현 첫 커밋에서 `x-peaket-problem-types`에 넣는다.
- `csrf`: 팬 문의·답변은 `gw-fan` Origin 검사·`Idempotency-Key`를 그대로 따르고, 이 기능은 새 쿠키를 만들지 않는다(3.5.1·3.5.2는 게이트웨이 공통 시험이 이미 본다).
