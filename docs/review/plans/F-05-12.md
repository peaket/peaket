## 계획

계획 담당 `lane3-freeze-F-05-12-opencode`(deepseek-v4.1-flash), 2026-11-26. 시험·제품 코드는 쓰지 않았다.

### 1. 끝내는 것과 넘기는 것

- **끝내는 것**
  1. **부스 재발급 서버 전부**
     - identity `POST /v1/identity/booth-reverifications`: 대조 목적 동의(`consent: true`) 없는 요청 422, 본인확인 시작(purpose `BOOTH`, 티켓 ID 묶음), 결과가 보유 계정의 `ci_hmac`과 다르면 409 `booth-mismatch`, 같으면 `reverificationToken`(5분).
     - ticket `POST /v1/tickets/{ticketId}/booth-requests`: 부스 대조 토큰 확인(계정·티켓 묶임), 보유자·입장 시작 뒤만, 8자 부스 코드(10분), 티켓당 하루 3회 [가정].
     - ticket `POST /v1/scanner/booth-authorizations`: `gate_lead`만, 코드를 찍으면 그 티켓의 BOOTH 등록을 10분 허용, 만료·모르는 코드 410, 다른 회차 기기 403.
     - ticket `POST /v1/tickets/{ticketId}/device-keys` `reason: BOOTH`: 허용 안 됐거나 10분이 지났거나 이미 한 번 성공했으면 403 `booth-not-authorized`; 허용 안에서 **한 번만** 성공.
  2. **월렛 부스 흐름**: `[ 부스 재발급 요청 ]` → 대조 목적 동의 → 본인확인 → `booth-requests` → 부스 코드 QR 10분 → 스캐너 허용 뒤 `reason: BOOTH` 등록 → QR. 409(불일치·입장 시작 전)·429·403(허용 전·만료)을 d5 §5.13 네 상태로 가른다.
  3. **SCR-052 실제 API 연결**: `[기기]` `GET /v1/scanner/events/{eventId}/devices`(`GateStatus`), `[이상 표시]` `GET …/flags`·`POST …/flags/{flagId}/resolution`·확인 스캔, `[부스]` `POST /v1/scanner/booth-authorizations`, `[내 예외 통과]` 새 `GET …/override-passes`(아래 §3 결정 6).
  4. **좌석 이름**: 발권 때 좌석 이름을 ticket에 스냅샷하고 스캐너 목록·이상 표시·파트너 콘솔 명단에 보인다. O-T2 ②.
  5. **스캐너 앱 큐 비움 보고**: 업로드 큐가 0이 되는 순간·근무 준비 때 `PUT /v1/scanner/queue-reports/{eventId}` `{pendingUploads: 0}`을 보낸다(F-05-6이 만든 서버 경로를 앱이 실제로 쓴다).
- **이미 있는 것**(그대로 쓴다): identity 본인확인 시작·결과 확정·`ci_hmac` 대조·키 판·만 14세 처리, ticket 기기 키 등록(ISSUE·REISSUE·TRANSFER·BOOTH 갈래·재인증·24시간 한도·`scanner_change`), `device_key.reason` CHECK에 `BOOTH`, scanner package·flags·resolution·placement·shift, `GateFlag`·`GateStatus` 계약 모양, purchase `SeatMap.resolve`(좌석 `label`), attendee export 경로, scanner 앱 QR 판독·업로더·`live-runtime`, 월렛 `BoothReissue` 목업과 `registerDeviceKey({ boothRequestId })` 자리, ops CS '이상 표시'.
- **넘기는 것 / 하지 않는 것**
  - 본인확인기관 실제 계약·비용: 시험 기관(`testAgency`)으로만 본다. O-T28의 기관 몫은 대역이다.
  - mTLS 선택지·관리형 기기·실기기 카메라: 기존 PoC/환경 몫.
  - 예외 통과 **생성** 자체(스캔 `method: OVERRIDE`): F-05-4가 이미 만들었다. 이 기능은 '내 예외 통과' 목록·사후 검토 상태만 보여 준다.
  - `OVERRIDE_REVIEW`를 이상 표시 목록에서 빼는 일: F-05-6이 끝냈다(C1-16). 이 기능은 그 표시를 '내 예외 통과' 탭에서만 읽는다.
  - Kafka `trade.tickets` `BOOTH` 사건 생산자: 기존 `KEY_REGISTERED`·`KEY_REVOKED` 변경분으로 충분하다. 새 토픽 생산자는 만들지 않는다.
  - `ticket.seat_label` 과거 행 채우기(backfill): 옛 행은 `seatId`로 물러난다. 발권 뒤 새 행부터 이름이 있다.
  - 월렛 목록의 `seatLabel` 노출: FIX-wallet-tickets 고정 시험이 'ticket 데이터에 없다'를 단언한다. O-T2 ②는 책임자 스캐너·파트너 콘솔만이라 월렛 계약은 건드리지 않는다(§3 결정 5).
- 정본에 쓴 것(이 계획 커밋, 추천 적용 2026-11-26): §3의 자리 그대로. 방향을 바꾸는 결정은 없어 새 ADR을 쓰지 않는다(ADR-0373 결정 3). 막힘 없음.

### 3. 정본 빈칸 결정(이 계획 커밋에서 정본에 씀, 추천 적용 2026-11-26)

1. **부스 대조 토큰**: 32바이트 불투명 토큰(URL-safe base64), identity `booth_reverification`에 SHA-256 해시·계정·티켓·만료(5분)를 남긴다. 같은 토큰을 5분 안에 여러 번 확인해도 된다(요청 재시도·네트워크 재전송). '한 번만'은 BOOTH 등록 성공 쪽에서 지킨다. ticket-svc는 새 identity gRPC `ReverificationCheckService.VerifyBoothReverification`으로 확인한다(기존 `PEAKET_IDENTITY_GRPC_URL`을 그대로 쓴다. 새 HTTP 주소·환경 값을 만들지 않는다). offline-gate §9.1 2·3단계, identity §6.1에 한 줄씩 쓴다.
2. **부스 코드**: 알파벳 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`(혼동 글자 I·O·0·1 제외) 8자, 티켓당 활성 코드 하나, 새 요청은 옛 코드를 무효로 한다. 코드 수명 10분(만들 때부터), 책임자가 찍은 뒤 허용 수명 10분(찍은 때부터). 하루 3회 [가정]는 KST 날짜(`Asia/Seoul`)로 센다. offline-gate §9.1에 쓴다.
3. **부스 요청의 갈래**: 입장 시작 전 409 `booth-before-entry`(‘입장 시작 전에는 온라인으로 다시 받으세요’), 대조 불일치 409 `booth-mismatch`, 하루 한도 429, 남의 표·없는 표 404 `not-found`(가르지 않는다). 201 본문 `{boothRequestId, boothCode, expiresAt}`. scanner 허용 200 본문 `{ticketId, seatLabel, allowUntil}`. openapi 설명을 구현 때 채운다(계획 커밋에서는 openapi를 고치지 않는다: 계획 커밋은 문서만 바꾸고 생성물을 만들 수 없다).
4. **BOOTH 등록 한 번**: 기기 키 저장과 부스 허용 사용 표시를 **한 트랜잭션**에서 한다. 허용 행은 `authorized_at`이 있고 `allow_until > now`이며 `used_at`이 비었을 때만 쓴다. 동시 등록 둘 중 하나만 201, 다른 하나는 403 `booth-not-authorized`. 키 저장이 실패하면 사용 표시도 남기지 않는다(같은 트랜잭션). offline-gate §9.1 4단계, data.md `booth_authorization`에 쓴다.
5. **좌석 이름 스냅샷**: 발권 gRPC `IssueTicketsRequest`에 `repeated string seat_labels`를 더한다(`seat_ids`와 같은 차례·같은 수, 없으면 서버가 `seatId`로 채운다). purchase는 발권 직전에 `SeatMap.resolve`로 이름을 읽어 보내고, 읽지 못하면 칸을 비워 `seatId`로 물러난다(발권을 막지 않는다). ticket은 `ticket.seat_label text NULL`에 저장하고 스캐너 목록·이상 표시는 `coalesce(seat_label, seat_id::text)`를 준다. 월렛 목록 계약은 바꾸지 않는다(§1 '넘기는 것'). 파트너 콘솔 명단은 purchase `DrizzleAttendeeReader`가 읽을 때 `SeatMap.resolve`로 채우고, 없으면 `seatId`다. offline-gate §9.1 4단계와 data.md `ticket`에 쓴다.
6. **내 예외 통과 경로**: `GET /v1/scanner/events/{eventId}/override-passes`(gate_lead, 기본 50건)를 더한다. 그 회차·그 스태프 계정(`scan_event.staff_account_id`)이 남긴 `method = 'OVERRIDE'` 기록만, 최신순. 항목 `{scanId, at, ticketId, seatLabel, reason, note, reviewStatus}`이고 `reviewStatus`는 연결된 `OVERRIDE_REVIEW` `gate_flag`의 상태(`OPEN`→`WAITING`, `OK`→`OK`, `SUSPECT`→`SUSPECT`, `UNDETERMINED`→`UNDETERMINED`, 없으면 `WAITING`). d5 §8.5 ⑥이 정본이고, openapi 설명은 구현 때 채운다.
7. **큐 비움 보고 앱 규칙**: 앱은 (가) 시작 뒤 첫 근무 준비 보고 때, (나) 업로드 큐가 1 이상에서 0이 된 순간에 한 번 보낸다. 같은 '비었음' 동안 다시 보내지 않고, 다시 큐가 차면 다음 0에서 또 보낸다. 실패는 삼키고 다음 0/재연결에서 다시 시도한다. offline-gate §7.3 '큐 비움 보고' 끝에 앱 몫 한 줄로 쓴다.
8. **월렛 부스 재등록 시도**: 부스 코드를 보인 뒤 앱은 10초 [가정]마다, 그리고 `online` 사건에 `reason: BOOTH` 등록을 시도한다. 403 `booth-not-authorized`는 '아직 책임자가 찍지 않음'으로 보고 화면을 바꾸지 않는다. 201이면 QR을 보이고, 코드 만료 시각이 지나면 시도를 멈추고 '부스 코드가 만료되었습니다. 다시 요청해 주세요'를 보인다. 429·409·404는 d5 §5.13 네 상태로 가른다. frontend §4.2.4에 쓴다.
9. **권한·출처**: 부스 요청은 팬 쿠키, 부스 허용·내 예외 통과·기기 현황은 `gate_lead`, BOOTH 기기 키 등록은 팬 쿠키+재인증. 부스 허용·내 예외 통과는 스캐너 PWA `Origin`·JSON 확인(기존 `ScannerAuth`·`assertScannerOrigin`). ASVS offline-gate 2.2.3(업무 이름 맞춤)·2.3.1(상태 전이)·2.3.2(시도 한도)·3.5.2(JSON)·16.3.2(권한별 거절)에 판정 시험을 잇는다.
10. **데이터**: ticket 마이그레이션 **`0021_booth_reissue_and_seat_label.sql`**(`booth_authorization` 표 + `ticket.seat_label` 칸), identity 마이그레이션 **`0039_booth_reverification.sql`**(`booth_reverification` 표 + `verification_attempt.ticket_id`·purpose CHECK에 `BOOTH`). 근거: 이 가지의 ticket 마지막은 `0020_entry_close_candidates.sql`, identity 마지막은 `0038_scanner_session_device_name.sql`이고, 동결 가지 가운데 표를 더한 것은 F-05-8의 core `0048`·`0049`뿐이다(F-05-10은 표 없음, 나머지 동결 가지는 ticket·identity 마이그레이션 0). 다른 freeze 가지와 번호가 겹치지 않는다. purchase·core 마이그레이션 없음.
11. **계약 생성물**: openapi·proto를 고치므로 구현 담당이 contracts·api-client `gen`을 돌려 함께 커밋한다(계획·시험 커밋에서는 생성물을 만들지 않는다).
12. **시험 값**: 토큰 5분·코드 10분·허용 10분·하루 3회·재시도 10초는 시험이 코드 상수를 가져오지 않고 정본 숫자로 적는다. 경계는 `만료−1ms`/`만료` 양쪽을 둔다.

### 7. 실패 확인 방법

### 13. 남는 위험

- 본인확인기관 실제 계약·비용은 대역이다. O-T28의 기관 몫은 운영 전 실제 기관으로 다시 본다.
- 부스 코드는 종이·화면에 보이는 8자라 어깨너머로 볼 수 있다. 10분·1회·책임자 확인으로 줄이지만, 코드를 본 다른 사람이 먼저 스캐너에 보여 줄 수 있다(정본 §9.1의 알려진 한계와 같은 종류). 필요하면 코드에 티켓 뒷자리 확인을 더한다(범위 밖).
- 부스 재등록은 팬이 화면을 닫으면 멈춘다(웹 푸시 없음). 10분 안에 다시 열어야 한다. 운영 안내로 보완한다.
- 좌석 이름은 발권 뒤 스냅샷이라 좌석맵 판이 바뀌어도 옛 이름이 남는다(의도). 좌석맵에서 사라진 좌석의 이름은 빈 값이 아니라 옛 이름이다.
- `GET …/devices`의 `entriesByZone`·`rejectsByReason`은 `scan_event` 집계라 회차가 크면 비싸다. 1분 캐시 [가정]를 두고, 규모 측정은 F-05-9/IR로 넘긴다.
- purchase가 발권 gRPC로 `seat_labels`를 싣는 얇은 어댑터는 단위 시험이 `TicketIssueCommand` 조립을 보지 않는다(시험은 ticket 쪽 `seatLabels` 저장과 명단 읽기를 본다). 구현 리뷰에서 `ticket-issue` 실행기의 라벨 조립을 읽고, 실제 두 서비스 연결은 F-05-12 뒤 통합 무대에서 한 번 본다.
- F-05-10이 `live-runtime.ts`를 먼저 합치면 이 기능은 그 위로 다시 쌓는다.
