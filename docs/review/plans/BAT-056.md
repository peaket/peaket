# BAT-056 계획·기록(BAS-090 게이트웨이 차단 상한 PoC, 메시 웨이포인트 지연은 문서 인용)

- **무엇**: 게이트웨이(Envoy Gateway)가 뒤의 서비스에 동시에 보내는 요청 수와 기다리는 요청 수에 상한을 걸고, 그 값을 이 PC의 kind에서 바꿔 가며 재서(스윕) 고르는 묶음이다. 메시(서비스끼리의 통신을 앱 대신 처리하는 층) 웨이포인트 지연은 재지 않고 Istio 공식 측정을 인용한다. 같은 측정 창에서 검색 IP 한도(SR-T13 ②)의 k6 측정도 한다. 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다. 정본의 값은 옮겨 적지 않고 자리만 가리킨다(값이 이 계획에서 처음 나오는 것만 정본에 쓰고 여기서는 그 자리를 가리킨다).
- **바탕**: 작업 폴더 `D:/ticketpass-lane1`, 가지 `wave/lane1-BAT-056`, 출발점 develop `6e00c730`. 지시서는 `brief.mjs --batch BAT-056`(만든 때 `6e00c730`).
- **등급**: B(docs/BUILD_ORDER.md:56). 항목 넷 모두 B다(돈·좌석·대기 순번의 핵심 로직이 아니다. 게이트웨이 상한은 운영·배포 설정이다).
- **차례**: 정방향이다(`Batch-Order: impl-first`, ADR-0281, docs/architecture.md §8.6 '정방향 묶음'). 계획 → 구현(스윕 도구·게이트웨이 설정) → 독립 시험(구현 전 트리에서 실패 확인) → 리뷰 → 검증 → 측정 실행 → 기록. 측정 뒤 값이 바뀌면 아래 6의 '측정 뒤 값이 바뀔 때'대로 한 바퀴 더 돈다.
- 이 파일은 역할마다 자기 절만 쓴다: 계획(아래 '계획'·'정할 것'), 실패 확인·시험 결과(시험), 시험 이의(구현), 리뷰, 검증, 측정 결과(측정), 담당 표·기록(감독).

## 계획

계획 담당 `l1-bat056-plan-ca28de08`(claude-opus-5-5), 2026-11-17. 시험·제품 코드는 쓰지 않았다. 정본 빈칸은 이 커밋에서 정본에 썼다(아래 8, 모두 '추천 적용 2026-11-17, BAT-056'). 방향을 바꾸는 결정은 없다. 다만 멈출 조건 셋을 '정할 것'에 적었다.

### 2. 손댈 파일과 공개 인터페이스(구현 담당)

**게이트웨이 설정**(`deploy/gateways/`, 정본 docs/infra.md §4.1 '게이트웨이 차단 상한'):
1. 다섯 게이트웨이 파일의 `gw-<이름>-responses` `BackendTrafficPolicy`에 `circuitBreaker` 세 칸을 정본 '첫 값'대로 넣는다(gw-queue와 나머지 넷의 값이 다르다). 칸 이름은 v1.10.0 CRD에서 확인한다(지금 계획이 쓰는 이름 `maxConnections`·`maxParallelRequests`·`maxPendingRequests`가 틀리면 정본 줄의 '[칸 이름은 구현 담당이 v1.10 CRD에서 확인]'을 맞는 이름과 확인 날짜로 바꾼다).
2. 같은 정책의 503 응답 고치기(`responseOverride`, `source: Local`)의 `header.set`에 `Retry-After: 2`를 더한다(다섯 모두). 429의 두 갈래(60·1)는 그대로 둔다.
3. 길게 쥐는 규칙(gw-ops SSE `getOpsLive`·`getOpsEventLive`. 처음 계획은 gw-fan 결제 결과 롱 폴링 `GET /v1/orders/{orderId}/payment-status`도 넣었으나 '정할 것' 4의 감독 결정, 2026-11-18로 그 규칙은 게이트웨이 값 6,000을 둔다)에만 닿는 `BackendTrafficPolicy`(`mergeType: StrategicMerge`)로 세 칸 65,536. 규칙 하나만 겨누는 법은 v1.10에서 확인한다: 규칙 이름(`sectionName`)으로 겨눌 수 있으면 그것, 안 되면 라우트 원천(`deploy/gateways/routes/`)에서 그 규칙을 따로 라우트로 떼고 `node tools/ci/gateway-routes.mjs --write`로 다시 만든다. 이미 그 라우트를 겨눈 정책(gw-fan-api의 전역 한도 등)과 부딪히지 않게 한다(같은 대상을 둘이 겨누면 Envoy Gateway가 하나를 버린다). 고른 법과 까닭을 정본 같은 줄의 '구현 담당이 v1.10에서 확인한다'에 이어 적는다.
4. 재시도(`retry`)는 어디에도 넣지 않는다.

**측정 도구**(`loadtest/`, 기존 실행 도구 `loadtest/run.mjs`의 발생기 파드·실행 잠금·기록·성능 장부 옮기기를 다시 쓴다):

| 명령 | 하는 일 | 인자(기본값) |
| --- | --- | --- |
| `node loadtest/run.mjs gw sweep` | 라우트 하나에 임시 상한 정책을 걸고(단계마다 값 바꿈) 부하를 넣어 단계마다 결과를 낸다 | `--gateway gw-queue` `--route gw-queue-buy` `--rate 1500` `--mix normal\|single`(normal은 정본 '측정(V-T43)'의 진입·홀드·결제 접수 비율) `--delay normal\|fixed:<ms>`(normal은 정본의 5/20/100ms 분포) `--max-parallel <목록>` `--max-pending <수 또는 목록>`(1024) `--max-connections same\|<수>`(same = max-parallel) `--warm 10` `--main 60` `--repeat 1` `--generators`(⌈rate ÷ 1,000⌉) `--record --run-id-prefix <접두>` `--out <폴더>` |
| `node loadtest/run.mjs gw capacity` | 프록시 파드 하나의 CPU를 묶고(`EnvoyProxy` 자원과 Envoy 일꾼 수) 도착률을 올려 포화 처리량을 잰다 | `--gateway gw-queue` `--route gw-queue-buy` `--proxy-cpus 0.5` `--rates 500,1000,1500,2000,3000` `--delay fixed:5` `--warm 10` `--main 30` |
| `node loadtest/run.mjs gw ip-limit` | 검색 IP 한도(SR-T13 ②)를 `X-Forwarded-For` 값을 바꿔 가며 잰다 | `--case single\|many\|mixed\|v6-64` `--rate` `--ips` `--main 60` |

- 임시 정책: 이름 `peaket-sweep-<라우트>`, 이름표 `peaket.io/sweep: "true"`, 네임스페이스 `envoy-gateway-system`, 대상은 그 HTTPRoute 하나, `mergeType: StrategicMerge`(게이트웨이 정책의 503 응답 고치기가 그대로 닿아야 한다), 칸은 `circuitBreaker`뿐. 단계를 시작하기 전에 프록시 관리 포트의 `/clusters`에서 그 라우트 규칙 묶음의 상한이 새 값으로 보일 때까지 기다리고(시간 넘김은 그 단계 무효), 끝나면(신호·오류 포함) 임시 정책과 CPU 묶음을 되돌린다. `node loadtest/run.mjs cleanup`도 이름표로 지운다. `deploy/` 아래 파일은 읽기만 한다.
- 순수 함수(단위 시험 자리, `loadtest/runner/gw.mjs` 등 이름은 구현 담당이 정한다): 단계 목록 펼치기(인자 검사 포함), 임시 정책 객체 만들기, Envoy 통계 글에서 그 묶음의 값 뽑기(`*_overflow` 카운터 전부, `upstream_rq_active`·`upstream_rq_pending_active` 최대, 없으면 오류), 단계 판정, 성능 장부 `checks` 만들기, SR-T13 ② 판정.
- 결과 파일 `sweep.json`(capacity·ip-limit도 같은 꼴)의 단계 줄: 단계 번호, 세 상한 값, 도착률, 지연 꼴, 보낸 수, 상태별 수(2xx·503·429·그 밖), 넘침 카운터, 처리 중·보류 최대, 2xx와 503 각각의 응답 시간 p50·p99·최대, 503 가운데 `Retry-After` 있음·없음·값 목록, Problem 본문이 맞는 수, 접근 로그 503 줄의 `durationMs` 3 이하 비율, 발생기 CPU·`dropped_iterations`, `valid`·`invalid_reason`, 판정(`pass`·`fail`·`invalid`). 끝 코드는 실행 도구와 같다(0 실행을 마치고 결과를 씀(판정이 실패·무효여도), 1 k6가 못 돎·도구 오류, 2 인자 오류, 128+신호).
- 발생기는 클러스터 안 k6 파드이고 게이트웨이 프록시 Service로 바로 보낸다(포트 전달·이 PC 포트 매핑을 거치지 않는다. BAT-055에서 포트 전달이 몰아 보내기에 끊겼다, docs/infra.md §4.1 '로컬 kind에서 이 PC로 잇는 법'). 토큰은 접속 정보의 시험 키로 도구가 만든다(`ticket:buy`, 수명은 실행 길이 + 10분).
- 성능 장부: `--record`이면 단계마다 실행 하나를 `tools/perf-ledger/collect.py`로 남긴다. 프로파일 `local-gw`(이 커밋에서 docs/perf-ledger.md §4에 더함), `kpi` NFR-001(ip-limit는 NFR-028), `scenario`에 세 상한 값·지연 꼴·도착률, `notes`에 프록시 복제·CPU, 단계 판정.

**CI**: 정적 시험은 `tools-check`(`deploy/gateways/test/*.test.mjs`), 도구 단위 시험은 `loadtest-check`(`loadtest/test/*.test.mjs`), kind 시험은 `ci-kind`의 `tools/local/e2e/gateway-limits.e2e.mjs`가 이미 돈다. 새 kind 시험은 그 파일에 더해 워크플로를 고치지 않는다.

| U7 | 단위 | `V-T43 스윕은 끝날 때 임시 정책과 CPU 묶음을 되돌린다` | 가짜 kubectl로 정상 끝·오류·신호 셋 모두 지우기 명령이 나가는지 | 같음 |
| U8 | 단위 | `V-T43 새 상한이 /clusters에 보이기 전에는 단계를 시작하지 않는다` | 가짜 관리 포트가 옛 값을 계속 주면 그 단계는 부하를 넣지 않고 무효(사유 '상한이 실리지 않음') | 같음 |
| K1 | K | `V-T43 ② 상한을 넘은 요청은 바로 503·Retry-After: 2·Problem이고 백엔드에 닿지 않는다` | 시험이 gw-queue-buy에 임시로 동시 1·보류 1을 걸고 클러스터 안에서 2초 지연 요청 20개를 한꺼번에 보냄: 503 ≥ 18, 모두 `Retry-After: 2`·Problem 본문, 503 응답 시간 < 100ms(K의 느슨한 값. 3ms는 측정), 그 묶음의 업스트림 요청 수 증가 ≤ 2. 끝나면 임시 정책을 지운다 | 실패(`Retry-After` 없음) |
| K2 | K | `V-T43 ① 동시 + 보류 상한까지는 503이 없고 하나 넘으면 503이다` | 임시로 동시 4·보류 1. 2초 지연 요청 5개 → 503 0건, 6개 → 503 정확히 1건(경계 양쪽) | 처음부터 통과(Envoy 동작) → 틀린 구현으로 |
| K3 | K | `V-T43 ② 운영 정의의 상한이 프록시 설정에 실린다` | gw-queue·gw-fan 프록시 `/clusters`에서 진입·홀드 규칙 묶음의 상한이 정본 첫 값, gw-ops 관제 SSE 두 규칙(`ops-event-live`·`ops-live`)은 65,536, gw-fan 결제 결과 롱 폴링 규칙은 게이트웨이 값 6,000(감독 결정, 2026-11-18) | 실패(기본 1024) |

- K 시험의 임시 상한 값(1·4)은 운영 첫 값과 다르게 골랐다(값이 같으면 상수를 잘못 쓴 결함이 숨는다).
- 시험 지시문에 넣을 '자주 놓친 결함'(지시서 7): 경계값 양쪽(3ms·동시+보류), 측정 도구의 빈 결과가 통과로 새지 않기, 판정 함수만 보지 말고 부르는 쪽(끝 코드·`valid`·성능 장부 옮기기)이 판정을 실제로 쓰는지, 시험 값을 코드 상수와 다르게, 겹친 가드(결제 결과 롱 폴링은 게이트웨이 값 6,000과 서비스의 파드당 2,000건이 겹친다. 롱 폴링 규칙에 65,536을 거는 결함과 전역 한도를 덮는 결함은 S3이 잡는다).
- **실패 확인**: 시험 담당은 묶음 가지의 계획 커밋 트리(제품 코드는 `6e00c730` 그대로)에서 정 시험을 돌리고, Docker 차례 잠금을 잡은 때 새 kind 클러스터(`PEAKET_CLUSTER=lane1-b056t…`)에서 K1~K3을 돌려 실패를 본다. 단위 시험(U1~U7)은 도구가 없어 실행조차 안 되므로 실패로 세지 않고 검증의 틀린 구현으로 실패를 본다(§8.6 7).

### 4. V-T44: 하지 않고 문서 인용으로

- **까닭**: ① ADR-0082 결정 8이 선택으로 두었고 '하지 않으면 공식 측정 인용'이다. ② kind에 Istio를 올리면 새 이미지(제어부·노드 프록시·웨이포인트)를 받아야 하는데, BAT-061 비고가 같은 까닭으로 Istio를 kind에 올리지 않기로 했다. ③ 로컬·CI·데모는 메시 없이 돌아 결과가 운영 판정의 근거로만 쓰인다(V-T44 판정 칸). PC 한 대의 kind에서 잰 몇 ms 차이는 잡음에 묻히기 쉽다.
- **구현 담당이 할 일**(문서만): Istio 공식 성능 문서('Performance and Scalability' 쪽. ADR-0082는 1.24를 인용했다)를 열어 판·확인 날짜·조건(초당 요청, 본문 크기, 연결 수)과 메시 없음 대비 ① 노드 프록시만(L4) ② 웨이포인트 ③ 사이드카의 지연 증가(p99, 없으면 문서가 내는 백분위)를 옮긴다. **수치는 지어내지 않고 문서에 있는 값만 쓴다**. 적는 곳: docs/verification.md 'V-T44' 행 끝 '결과(문서 인용, 날짜)'(주소·판·조건·수치·판정), docs/architecture.md §9.4 '서비스 메시 프록시 지연 오버헤드' 행 끝 한 문장(판정과 V-T44 가리킴).
- **판정**: 웨이포인트 p99 증가가 2ms 이하면 '앰비언트를 쓴다(문서 인용)'로 적는다. 공식 문서에 p99가 없거나 2ms를 넘으면 판정하지 않고 '정할 것' 2로 멈춘다.
- **장부가 세는 법**: 기록 커밋이 notes '측정' 표에 `| V-T44 | 측정 |  | BAT-056 | 문서 인용: Istio <판> 공식 성능 문서(<주소>, <확인 날짜>), 결과는 docs/verification.md V-T44 행 끝 |`을 더한다. '미검증'이 아니라 '측정'으로 세는 까닭은 판정 칸이 정한 근거(공식 측정 인용)로 판정을 마쳤기 때문이다(docs/perf-ledger.md §2.2 `evidence`의 '문서 인용'과 같은 뜻). 성능 장부에는 실행 폴더가 없으므로 남기지 않는다.
- **검증 담당**: 옮긴 수치가 그 주소·판의 문서와 같은지 대조한다(판정 기준 대조 표본).

### 5. 측정 방법(측정 담당, 측정 창)

정본: docs/infra.md §4.1 '게이트웨이 차단 상한'의 '측정(V-T43)'(정상 부하·지연 분포·과부하·판정 지점)과 docs/features/search.md SR-T13 ② '측정 판정'. 아래는 차례와 스윕 값이다.

- **무대**: Docker 차례 잠금(`D:/ticketpass-locks/docker`)을 잡고 새 클러스터 `PEAKET_CLUSTER=lane1-b056m`로 `node tools/local/cluster.mjs up` → `gateways`. 프록시 복제 1(로컬 덧씌우기 기본, 결과에 적음). 다른 갈래 시험이 겹치지 않을 때만(측정 창). 끝나면 `kind delete cluster`, 남은 컨테이너 `docker rm -f -v`, 잠금 폴더 지움.
- **M0 발생기**: 새로 보정하지 않고 2026-11-03 보정(`local-gen`, CPU 4 발생기 하나가 초당 1,000건 왜곡 없음)을 쓴다. 그래서 발생기 수는 ⌈도착률 ÷ 1,000⌉이다. 단계마다 발생기 CPU·`dropped_iterations`로 무효를 가른다.
- **M1 포화 처리량**(`gw capacity`): gw-queue 프록시를 CPU 0.5·일꾼 1로 묶고 진입 경로(토큰 확인·Lua·접근 로그를 다 지나는 진짜 경로)에 지연 5ms 고정으로 500·1,000·1,500·2,000·3,000/s. 포화는 프록시 CPU가 한도의 90% 이상이거나 '응답 시간 p99 − 5ms'가 3ms를 넘는 첫 단계이고, 그 앞 단계 도착률 × 2를 'vCPU 하나의 포화 처리량'으로 적는다(선형 [추정]). 3,000까지 포화가 안 오면 '3,000 × 2 이상'으로 적고 정본의 [추정] 5,000을 그대로 둔다(아래 쪽으로만 고친다. 낮은 하한을 쓰면 상한이 너무 작아져 운영 정상 부하에서 503이 날 수 있다).
- **M-A 동시 상한 스윕(V-T43 ①)**: `gw sweep --mix normal --delay normal --rate 1500`, 보류는 운영 꼴대로 ⌈동시 ÷ 8⌉(리뷰 반영 R8로 1024 고정에서 바꿈), 동시 = 연결 ∈ {4, 8, 12, 16, 24, 32, 64}. 평균 동시 요청 수는 약 1,500 × 7.3ms ≈ 11이다. 503이 0건인 가장 작은 값 r_min과 그 아래 값을 2번 더 재(3회) 경계를 굳힌다. k = r_min ÷ (도착률 × 잰 평균 지연)이고 2보다 작으면 2로 둔다. ①의 판정은 'PC에서 고른 값 r_pc = ⌈k × 도착률 × 평균 지연⌉에서 3회 모두 503 0건'과 '운영 첫 값(동시 2,400)에서 503 0건' 둘이다.
- **M-B 보류 큐 확인**(리뷰 반영 R8로 줄임): 동시 = r_pc로 두고 보류 ∈ {1, ⌈r_pc ÷ 8⌉, ⌈r_pc ÷ 2⌉}를 정상 부하로 한 번씩 잰다. q를 재서 고르지 않고, 셋의 503 수가 같은지(보류 큐가 막는 값을 바꾸지 않는지)만 본다. 다르면 그 결과를 보고서에 적고 q를 고칠지 계획 담당에게 넘긴다.
- **M-C 과부하(V-T43 ②)**: 동시 r_pc·보류 ⌈r_pc × q⌉에서 진입 지연을 모두 50ms(평균 동시 약 75, 상한을 조금 넘김)와 500ms(약 750, 크게 넘김)로, 각각 3회. 정본 판정 넷(503 p99 ≤ 3ms, 503 모두 `Retry-After`·Problem, 처리 중 최대 ≤ 상한, 무효가 아님)을 본다. 접근 로그 `durationMs`로 교차 확인한다.
- **M-S 검색 IP 한도(SR-T13 ②)**: `gw ip-limit`. 경우 넷: (가) `single` 한 IP가 초당 150건 60초 (나) `many` IP 1,000개가 각자 초당 1건 (다) `mixed` IP 2만 개가 돌아가며 합쳐 초당 1,000건 + 한 IP가 초당 150건(버킷 수 상한 1만을 넘겨도 한 IP의 상한이 같은지) (라) `v6-64` 한 /64 안 주소 100개가 각자 초당 10건. (가)~(다)는 정본 '측정 판정'으로 판정하고, (라)는 판정에 넣지 않는 관찰이다(주소마다 따로 세므로 429 0건이 예상. 결과를 W7-CON-05 줄에 근거로 붙인다).
- **예상 측정 시간(Docker 잠금 시간)**: 무대 15분, M1 10분, M-A 15분, M-B 5분, M-C 10분, M-S 10분, 정리 5분, 여유 20분. **합 약 1시간 30분(잠금은 2시간으로 적는다)**. 보고서 쓰기 약 1시간은 잠금 밖이다. 이와 따로 시험 담당의 K 실패 확인과 구현 뒤 확인(약 40분), 검증의 K 틀린 구현(약 30분)도 Docker 잠금이 든다.
- **결과를 남길 곳**: ① 측정 보고서 docs/review/measurements/ 아래 `BAT-056-gateway-breaker.md`(무대, 단계 표, 고른 k·q·포화 처리량, 운영 값 다시 계산, SR-T13 ②, 원자료 위치 `.cache/peaket-loadtest/…`) ② 성능 장부 `docs/perf-ledger/runs/<날짜>-gw-…`(collect.py) ③ docs/verification.md §4.1 '게이트웨이 동시 처리·보류 큐' 행(성격을 '실측(PC)'와 식으로, 잰 k·q·포화 처리량) ④ docs/infra.md §4.1 '게이트웨이 차단 상한'의 '첫 값'을 '잰 값'으로 ⑤ docs/verification.md V-T43 행 끝 '결과(실측(PC), 날짜)' 한 문장 ⑥ `docs/review/ledger-notes.md` '측정' 표에 V-T43 ①·② 두 줄(정할 곳 BAT-056, 근거 보고서 경로)과 SR-T13 ② 근거 칸 고침 ⑦ docs/architecture.md §9.4 'API 게이트웨이 장애 차단 임계값' 행 끝 한 문장.
- **측정 커밋의 역할**: 측정 담당은 새 세션으로 띄우고 `Role: record`로 커밋한다(문서와 `docs/perf-ledger/runs/`만 바꾼다. 역할 확인의 허용 경로 안). 계획·시험·구현·리뷰·검증 세션과 다르다. 감독이 다르게 정하면 그대로 따른다.
- **측정 뒤 값이 바뀔 때**: 잰 k·q·포화 처리량으로 운영 값이 정본 첫 값과 달라지면, 측정 커밋이 정본 값을 고치고 → 시험 담당이 S2·K3의 값을 고치고(시험 커밋) → 구현 담당이 `deploy/gateways`를 고치고(구현 커밋) → 검증 담당이 바뀐 곳만 다시 본다(S2·K3을 틀린 값으로 되돌려 실패를 봄) → 측정 담당이 M-A의 운영 값 확인 1회와 M-C 한 번을 다시 잰다. 역할 확인의 '마지막 검증은 마지막 코드 고침 뒤'를 지키기 위해서다.

## 정할 것

지금 멈춰 묻는 것은 없다. 다음 셋이 나오면 그 항목만 멈추고 계획 담당(또는 감독)에게 넘긴다.

1. Envoy Gateway v1.10에서 503 응답 고치기(`source: Local`)가 차단 상한이 만든 503에 닿지 않아 `Retry-After`를 붙일 수 없을 때(K1에서 드러난다). `EnvoyPatchPolicy` 같은 다른 길은 판 올림에 약해 BAT-055가 피했던 길이라, 그 길로 갈지는 방향 결정이다.
2. V-T44 인용에서 공식 문서에 p99가 없거나 웨이포인트 p99 증가가 2ms를 넘을 때. ADR-0082 '결과'가 ADR-0010 다시 보기 조건으로 적은 일이라 새 ADR 거리다.
3. M-A에서 상한을 1024까지 올려도 정상 부하에서 503이 0건이 되지 않을 때(상한 말고 다른 원인 — 프록시 포화, 발생기 — 이 있다는 뜻). 원인을 가른 보고서와 함께 멈춘다.
4. **(구현 담당이 멈춤, 2026-11-17, l1-bat056-impl-e78e008e) 결제 결과 롱 폴링 규칙(gw-fan-api `GET /v1/orders/{orderId}/payment-status`)의 65,536을 어떻게 걸까.** 계획 §2 3의 '이미 그 라우트를 겨눈 정책(gw-fan-api의 전역 한도 등)과 부딪히지 않게 한다'를 v1.10.0에서 지킬 길이 없다. v1.10.0 번역기(`internal/gatewayapi/backendtrafficpolicy.go`)는 규칙을 겨눈 정책(`sectionName`)이 있으면 그 규칙에서 라우트 전체를 겨눈 정책을 덮어 쓰고(둘을 합치지 않음, 정책 상태에 'overridden'), `mergeType`이 있어도 게이트웨이·리스너 정책하고만 합친다. 공유 버킷(`shared: true`)의 열쇠는 정책 이름이다(`<네임스페이스>/<정책>/rule/<번호>`, `internal/xds/translator/ratelimit.go`). gw-fan-api에는 계정당 60회/분 한 버킷 정책 `gw-fan-account-rate-limit`(gw-fan-api·identity·optional 셋)이 라우트 전체를 겨눈다. 라우트를 떼어 새 라우트로 옮겨도 그 새 라우트를 전역 한도 정책과 차단 상한 정책이 함께 겨누면 하나가 버려진다. 고를 길(정본 docs/infra.md §4.1 '길게 쥐는 라우트' 끝에 같은 내용을 적었고, 지금 이 규칙은 게이트웨이 값 6,000이다):
   - (가) 규칙 정책에 65,536과 함께 같은 전역 한도(60회/분)를 다시 적는다. 이 규칙만 따로 60회/분 버킷이 된다(계정당 한도가 이 경로와 나머지에 따로 60회씩). 롱 폴링은 한 번에 27초를 쥐어 계정당 분당 2~3회라 버킷을 거의 쓰지 않고, 나머지 일반 API 몫을 깎지 않는 장점도 있다. 정본 D-T50 ①('세 라우트 한 버킷')의 예외 한 줄과 정적 시험 고침이 따른다. **추천**(판 올림에 약한 길이 없고 겉보기 동작 변화가 가장 작다).
   - (나) 규칙 정책에 65,536만 두고 이 규칙은 전역 한도에서 뺀다. 서비스 쪽 기다림 상한(docs/features/payment.md §2)이 덜어 내기를 맡는다. 계정 단위 남용 방어가 이 경로에서 빠진다.
   - (다) 65,536을 걸지 않고 게이트웨이 값(6,000)을 둔다. 파드 하나·규칙 하나 6,000개의 롱 폴링이 넘치면 503과 `Retry-After: 2`로 빠르게 실패한다. 정본 '길게 쥐는 라우트'를 고친다.
   - (라) `EnvoyPatchPolicy`로 그 묶음의 상한만 고친다. 묶음 이름이 규칙 번호(`httproute/…/gw-fan-api/rule/3`)라 계약이 바뀌면 깨지고, BAT-055가 피했던 길이다.
   - 영향: 정 시험 S3(길게 쥐는 규칙 셋 모두 65,536)은 이 규칙에서 실패한다. 결정 뒤 구현 담당이 그 길대로 `deploy/gateways`를 고친다. 관제 SSE 두 규칙은 규칙 이름(`ops-event-live`·`ops-live`)으로 겨눈 정책 `gw-ops-long-hold`로 걸었다(gw-ops-api를 겨눈 다른 BackendTrafficPolicy가 없다).
   - **결정(감독 결정, 2026-11-18, 계획 담당 `l1-bat056-plan-ca28de08`이 반영)**: (다)다. 결제 결과 롱 폴링 규칙에 65,536을 걸지 않고 gw-fan 게이트웨이 값(6,000·6,000·750)을 둔다. 까닭: (가)는 계정당 남용 방어 버킷(D-T50 ① '세 라우트 한 버킷')을 쪼개 보안 한도의 뜻을 바꾸고, (나)는 이 경로의 계정 단위 방어를 빼며, (라)는 BAT-055가 피한 판 올림에 약한 길이다. (다)는 보안 한도를 건드리지 않고, 넘치면 503과 `Retry-After: 2`로 빠르게 실패해 화면이 다시 묻는 짧은 폴링으로 내려앉는다(정본 '넘치면'의 과부하 동작과 같다). 정본은 docs/infra.md §4.1 '길게 쥐는 라우트'에 적었다. D-T50 등 다른 정본은 바꾸지 않았다.
   - **서비스 쪽 기다림 상한이 먼저 덜어 내는가(확인 2026-11-18)**: 조건부로만 맞다. 설계 피크(파드 전체 동시 수천, docs/verification.md §4.1)에서는 게이트웨이 6,000과 서비스 2,000건 어느 쪽에도 닿지 않는다. 넘칠 때 서비스는 파드마다 2,000건을 넘는 몫에 기다리지 않고 바로 200을 주므로, gw-fan 파드 하나에 쌓이는 롱 폴링은 (purchase-svc 파드 수 × 2,000) ÷ gw-fan 파드 수 이하다. 그래서 서비스가 먼저 덜어 내는 것은 gw-fan 파드 수가 purchase-svc 파드 수의 1/3 이상일 때뿐이다(purchase-svc 최대 40 [가정, docs/data.md §1.1]이면 gw-fan 14개 이상). gw-fan 복제 수는 아직 정본에 없다(W7-CON-04, wbs 4.6.1). 이 조건을 정본에 그대로 적고 감독에게 알린다. 조건을 못 채워도 게이트웨이가 먼저 503과 `Retry-After: 2`로 실패할 뿐이라 결정 (다)의 까닭은 그대로라고 본다.
   - **구현 영향**: 없다. `deploy/gateways`의 결제 결과 롱 폴링 규칙은 지금도 규칙을 겨눈 정책 없이 게이트웨이 값 6,000이다(gw-fan 파일에 `long-hold` 정책 없음, 2026-11-18 확인). 시험 담당은 위 S3·K3 단언대로 쓴다.

- **K2를 계획과 다르게 단언했다(시험 쪽 판단, 구현 결함 아님)**: 계획 §3 K2는 '임시 동시 4·보류 1에서 5개 → 503 0건, 6개 → 정확히 1건'이었다. 그런데 보류 자리로 받아야 할 5번째 요청을 Envoy(v1.10.0 설치의 프록시)가 늘 받아 주지 않는다. 구현 전 트리에서 같은 조건으로 돌린 결과는 이렇다. 5개 묶음은 일곱 번 가운데 한 번 503 0건, 여섯 번 1건이었다. 그 1건은 통계 `upstream_rq_active_overflow`나 `upstream_rq_pending_overflow`로 셌다. 6개 묶음은 200·503 수가 '4·2'와 '5·1'로 나왔고, 5번째가 503이고 6번째가 닿은 때도 있었다. 구현 트리에서는 5개 '4·1', 6개 '4·2'였다. 시험 바탕 탓이 아님은 이렇게 확인했다. 묶음마다 7초를 쉬어(대역 Node http가 쉬는 연결을 5초 뒤 닫음) 빈 연결 묶음에서 시작했고, 150ms 간격으로 보냈으며, 연결 오류는 0이었다. 그래서 결정적인 두 쪽만 단언한다. 동시 상한(4개)까지는 503 0건이다. 동시 + 보류(5)를 넘는 6개에는 503이 1건 이상이고, 대역에 닿은 수는 5 이하이며, 앞 4개는 닿는다. 5개 묶음은 진단(`t.diagnostic`)으로만 남긴다. 시험 이름도 `V-T43 ① 동시 상한까지는 503이 없고 동시 + 보류 상한을 넘은 요청은 503이다(보류 경계의 5번째는 관찰)`로 바꿨다. 틀린 구현 M24(라우트 정책이 겹쳐 임시 정책이 버려짐)는 그대로 잡는다. 그 경우 상한이 실리지 않아 `waitLimits`가 실패하고, 실려도 6개에 503이 0건이다.
- **측정에 넘길 것(감독·측정 담당 판단)**: 위 관찰은 연결 = 동시일 때 보류 큐가 경계 요청을 늘 받아 주지 않는다는 뜻이다. 실제로 막는 값은 '동시 + 보류'가 아니라 '동시'에 가깝다. 계획 §5 M-B(보류 큐 비율 q)와 M-C의 '처리 중 최대 ≤ 상한'을 읽을 때 이 점을 함께 본다. 정본 docs/infra.md §4.1 '값의 식'은 바꾸지 않았다(시험 담당 몫이 아니다).
- **K의 바탕**: K1·K2는 대역 백엔드 파드 안의 Node에서 gw-queue 프록시 Service로 보낸다(포트 전달 없음). 임시 정책은 `peaket-e2e-breaker-gw-queue-buy`(이름표 `peaket.io/sweep`)이고 끝나면 지운다. 다음 시험이 임시 상한을 물려받지 않게, 지운 뒤 그 묶음의 상한이 임시 값에서 벗어날 때까지 기다린다. K3과 상한 확인은 관리 포트 `/clusters`를 `kubectl port-forward`로 잠깐 열어 읽는다. K1의 503 시간(100ms 미만)은 TLS 연결이 선 뒤부터 잰다.

## 시험 이의

구현 담당 `l1-bat056-impl-e78e008e`(claude-opus-5-5), 2026-11-17. 시험이 기대는 공개 인터페이스와, 계획 표와 다르게 고른 곳이다. 시험 담당은 이대로 쓰거나 다르게 원하면 여기에 이어 적는다.

- **(가) 보류 기본 1024와 '보류 > 동시는 인자 오류'(U1)**: 계획 §5 M-A는 '보류 1024 고정, 동시 ∈ {4, 8, …}'라 U1 규칙과 부딪힌다. `--max-pending`을 준 경우에만 보류 > 동시를 인자 오류로 하고, 주지 않은 기본 1024(`pendingDefault: true`)는 검사하지 않는다(`loadtest/runner/gw.mjs` `expandSweepSteps`). U1은 `--max-pending`을 준 경우로 쓴다.
- **(나) 과부하 단계를 정하는 법(U4)**: 계획에 정하는 법이 없어, 재는 흐름의 '도착률 × 지연 꼴의 평균(ms) ÷ 1000'이 '동시 + 보류'를 넘으면 과부하(②), 아니면 정상 부하(①)로 했다(`isOverload`). `judgeSweepStep`은 그 결과를 `overload` 칸으로 받는다.
- **(다) 판정·장부 함수의 입력 꼴(U4·U5·U6)**: `judgeSweepStep({ step, overload, limitsLoaded, statsError?, stats(statsWindow 결과: overflow·overflowTotal·rqActiveMax·rqPendingActiveMax), m(streamMetrics 결과: sent·status{2xx,503,429,other}·latency{2xx,503,429}{p50,p99,max}·overFast·retryAfter{503,429}{num,missing,nonnum}·problem{503,429}{ok,bad}), generator{valid,reasons,dropped}, accessLog?(accessLogDurations 결과) })` → `{ item, verdict, valid, invalid_reason, reasons }`. `sweepChecks(흐름 이름, overload, m)` → `{ checks: [{ name, allowed, trials, violations, target }] }`(정상 부하 `<흐름>_503` 허용 0, 과부하 `<흐름>_503_p99_3ms` 허용 0.01·어김은 3ms를 넘은 503 수, 503이 있으면 `_retry_after`·`_problem` 허용 0). `judgeIpLimit({ case, mainS, replicas, streams: { one|many|pool|v6: m }, generator })`. 3ms 경계는 '넘으면 실패'(3.0 통과)이고 k6가 `gw_over_fast`로 '3ms 초과'를 센다.
- **(라) 정리·신호(U7)와 상한 기다림(U8)**: 실행 조립은 `loadtest/runner/gw-run.mjs` `runGw(a, deps)`이고 클러스터를 deps로 받는다(머리 주석에 칸 목록). 임시 정책 지우기는 `deps.kubectl(['-n','envoy-gateway-system','delete','backendtrafficpolicies','-l','peaket.io/sweep=true','--ignore-not-found'])`(`SWEEP_DELETE_ARGS`), CPU 묶음 되돌리기는 `kubectl patch envoyproxy <이름> --type merge -p <restore>`다. 신호는 `deps.signal`(AbortSignal, `reason.exitCode`, 없으면 130)로 흉내 낸다: 다음 확인 지점에서 멈추고 정리한 뒤 `{ exitCode }`를 돌려준다. 실제 실행에서는 `deps.onCleanup`으로 맡긴 정리를 run.mjs의 신호 처리기가 돌린다. 상한 기다림은 `waitLimits(deps, pods, cluster, step, { timeoutMs, pollMs })`이고 `deps.readAdmin(pod, '/clusters')`가 옛 값을 주면 `{ loaded: false }` → 그 단계는 `deps.runLoad`를 부르지 않고 무효('상한이 실리지 않음')다.

### 보안 관점에서 본 것(지적 밖)

- `gw-ops-long-hold`가 덮는 다른 BackendTrafficPolicy는 지금 없다. deploy/gateways의 BackendTrafficPolicy 10개를 모두 읽었고, gw-ops-api를 겨눈 것은 이것뿐이며 `targetSelectors`를 쓰는 정책도 없다. gw-fan 결제 결과 롱 폴링 규칙에는 규칙을 겨눈 정책이 없어 `gw-fan-account-rate-limit`이 그대로 닿는다(S3·K3이 본다).
- 503 응답 고치기의 변경은 `header.set`에 `Retry-After` 한 줄을 더한 것뿐이고 `source: Local`이라 서비스가 낸 503은 건드리지 않는다. 다른 상태(401·403·405·413·429)의 본문·머리는 바뀌지 않았다(diff와 S1 곁 시험).
- 측정 도구는 deploy/ 아래 파일을 읽기만 하고, 임시 정책은 이름표 `peaket.io/sweep`으로 시작 전·끝에 지운다. 재는 라우트를 이미 겨눈 운영 정책이 있으면 시작하지 않아, 측정 중에 운영 한도가 덮이지 않는다(단위 시험이 본다). S5가 운영 정의에 임시 객체가 섞이지 않는지 본다.
