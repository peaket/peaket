## 1. 끝내는 것

1. purchase-svc `trade.orders`의 `CONFIRMED`만 소비해 알림을 적재한다. 같은 사건은 `notification_dedup`으로 한 번만 적고, `APPROVED`·`ISSUE_DELAYED`·`AWAITING_DEPOSIT`·`PARTIALLY_REFUNDED`로는 보내지 않는다. 가상계좌는 입금이 확인되어 `CONFIRMED`가 된 때 처음 보내고, 입금 오류로 `AWAITING_DEPOSIT`로 돌아갔다 다시 `CONFIRMED`가 되어도 한 번만 보낸다.
2. `GET /internal/v1/orders/{orderId}/notice-view`(purchase-svc, 내부 토큰)로 예매번호·주문 상태·알림 허용 여부·회차·등급 ID를 읽는다. 예매번호는 KST `YYYYMMDD` + 5자리 일련번호(예 `2026101400123`)이고, 하루 99,999건을 넘으면 주문 생성을 503 `booking-number-exhausted`로 닫고 SEV2를 올린다.
3. `notice-view`·core catalog로 vars를 조립한다. 허용 목록은 `productionName`·`eventStartsAt`·`venueName`·`seatSummary`·`amount`·`bookingNoLast4`·`orderId` 일곱뿐이다. 판매자 7항목·이름·전화번호·좌석 번호는 `vars`에 넣지 않는다.
4. 이메일은 코드에 고정한 HTML+text 판(ko/en/ja/zh)으로 Amazon SES 서울 리전(`ap-northeast-2`)에서 보낸다. 판매자 7항목·중개자 고지·미성년자 계약 취소 고지·취소·환불 안내를 넣고, 외부 이미지·추적 픽셀·JavaScript를 쓰지 않는다. 번역이 없으면 ko로 대체하고 `notify_template_missing_total{locale}`을 올린다.
5. 웹 푸시는 그 계정의 살아 있는 `push_subscription` 구독마다 작업 하나를 만들어 한 번씩 보낸다. 확정 사건을 받은 뒤 5분 [가정] 안에 보낸 비율을 잰다. 알림이 실패해도 주문·결제·발권 상태를 바꾸지 않는다.
6. 지표 5종: `delivery_job_due_backlog{kind="BOOKING_CONFIRMED"}`, `notification_dedup.created_at`→`notification_delivery.sent_at` 지연(`notify_delivery_latency_seconds{kind,channel}`), `notify_template_missing_total{locale}`, `notify_email_send_total`, `notify_email_failures_total`.

- HTTP `GET /internal/v1/orders/{orderId}/notice-view`: `InternalTokenGuard`, 내부 서비스 계정만, 200 `{bookingNo, status, noticeAllowed, phoneE164, eventId, tierIds}`, 없으면 404 `not-found`. 이름·좌석 번호는 응답에 없고, `phoneE164`는 내부 응답에만 있으며 작업·기록·로그에 남기지 않는다. 내부 경로라 공개 openapi에는 넣지 않고 `docs/api/guidelines.md` §8의 내부 HTTP 목록과 `docs/architecture.md` §3.2에 적는다(구현 때).
- 주문 생성은 멱등 재생(`COMMITTED`)에서는 번호를 새로 잡지 않는다. 새로 만들 때 가격 계산 뒤·`writes.create` 앞에서 잡는다. 트랜잭션이 실패하면 번호는 건너뛴다(빈틈 허용).
- `booking_no_sequence(day, next)`는 `INSERT … ON CONFLICT (day) DO UPDATE SET next = next + 1 RETURNING next`로 잡는다(data.md).

### 4.2 core-svc notify

```ts

```

- `NotificationIntake.bookingConfirmed` 차례: ⑴ `type !== 'CONFIRMED'` → `suppressed: 'not_confirmed'`(notice-view를 부르지 않는다) ⑵ `noticeReader.get(orderId)` — 없거나 `noticeAllowed=false` → `suppressed: 'not_allowed'` ⑶ 예매번호가 없거나 모양이 틀리면 `bookingNoInvalid()`(SEV3)이고 작업을 만들지 않는다 ⑷ `catalog.getBookingNotice(eventId, tierIds)`로 이름·장소·시각·등급 이름을 읽는다(없으면 재시도, 3회 뒤 `held`) ⑸ vars를 만든다 ⑹ 이메일 하나와 살아 있는 웹 푸시 구독마다 하나를 `store.enqueue`로 적는다(한 트랜잭션, Kafka 오프셋 커밋은 구현).
- 중복 키: `BOOKING_CONFIRMED:{orderId}:CONFIRMED:{accountId}:{channel}`, 웹 푸시는 `:{subscriptionKey}`를 더 붙인다. 사건 ID 대신 `CONFIRMED`를 쓴다.
- `expiresAt`은 사건 시각 + 24시간 [가정]. `templateVersion`은 `v1`.
- `seatSummary`: `tierId`별 매수를 catalog 등급 이름으로 바꿔 `"R석 2매, S석 1매"`처럼 만든다. 이름이 없으면 `"좌석 {n}매"`(전체 매수)와 `tierNameMissing()`.
- 웹 푸시 작업은 `webPushTargetOf`가 `BOOKING_CONFIRMED`의 구독 키를 읽도록 넓힌다. 워커는 그 구독 하나에만 보낸다.
- 워커는 보내기 전에 `noticeReader.get(orderId)`를 다시 본다. `noticeAllowed=false`면 작업을 지우고 `suppressed('not_allowed')`를 올린다. 이메일은 catalog에서 판매자를 읽어 템플릿을 그린다. 판매자가 없으면 이메일만 재시도한다. 웹 푸시는 catalog를 기다리지 않는다.
- 이메일 성공: `emailSent()`·`deliveryLatency(job.createdAt→now)`·`templateVersion`을 기록. 실패: `emailFailed()`. DEAD 1건 이상 SEV3.
- `MailMessage.headers['content-type']`는 어댑터가 multipart로 정한다. `html`이 없으면 지금처럼 text/plain.

- 판은 `ko.ts`·`en.ts`·`ja.ts`·`zh.ts`로 나누고, 공통 조립은 `index.ts`가 한다. 값은 자리표시자로만 넣고 HTML 이스케이프한다.
- HTML: 600px 표, 인라인 CSS, `<!doctype html>`, `lang`, 제목 h1/h2, 링크는 `PEAKET_PUBLIC_ORIGIN` 절대 주소. 외부 이미지·추적 픽셀(`<img>` 금지)·JavaScript·폼·`on*` 속성 금지. 판매자 블록과 고지 글씨는 14px 이상으로 하고 판매자 표시보다 작지 않게 한다.
- text: 같은 내용·같은 링크를 담는다. 이메일 버튼 링크는 `/my/orders/{orderId}`.
- 번역이 없으면 ko 판을 쓰고 `templateMissing(locale)`을 올린다. 법정 고지 번역은 검토를 마친 판만 쓴다(이번엔 ko 고정).

### 8.2 확인한 것(문제 없음)

- **시험 실패는 실제 실패다**: core 10/10·purchase 4/4가 기준 트리에서 단언/TypeError로 실패했다. import·바탕 없음으로 실행조차 안 된 실패는 없다. 계획 §7의 6·1·3, 3·1 분류와 일치한다. 다만 이 실패 확인은 첫 단언만 보므로 RV068-02처럼 401 뒤의 틀린 단언은 잡지 못했다.
- **시험 재료**: `example.test`만 쓴다(`fan@example.test`·`seller@example.test`). 실제 수신자 주소·전화번호가 없다. `fakeClock`, `FakeMailTransport`, `FakePushTransport`, `MemoryFanNotifyStore`를 쓰고 고정 대기·실제 네트워크가 없다. `010-1234-5678`·`A01` 같은 값은 금지 값 예시다.
- **장부**: `ledger --batch F-06-8 --require`가 9항목(자동 시험 9, 빈칸 0, ID만 0, 미검증 0)으로 통과한다. 다만 RV068-12의 실제 경계 공백은 장부가 세지 못한다.
- **게이트**: lint, doc-check(오류 0·경고 15), ledger `--require`, `contracts gen:check`, api-client 116이 통과했다. release-scope는 계약 105/38/0/67과 가지 BUILD_ORDER 109/38/0/71의 충돌로 **실패**하며(9건), 통과로 세지 않는다(RV068-01 원복 뒤).
- **번호**: origin/develop은 ADR-0386까지이고 이 가지의 0387~0392는 겹치지 않는다. ADR-0392 머리·notify §4.8 제목·계획 링크가 모두 0392를 가리키며, 원안 0386을 0392로 옮긴 판단과 맞다. 0387·0388 링크도 맞다.
- **경계**: F-06-9(알림톡·문자·제공자 웹훅·CS 다시 보내기), F-06-10(알림함), F-06-11(템플릿 심사), F-06-6(막힘)을 이 기능이 닫지 않는다. 실제 SES·발신 도메인·IAM Pod Identity·Solapi는 `미실행`/소유자 몫이고 `notify.peaket.example`은 [가정]이다.
- **정직성**: 30k/s·100만·K1/K2/K7 0 같은 새 측정 주장이 없다. 5분·24시간·2,048바이트·99%는 [가정]으로 표시되어 있다. `CONFIRMED`만 소비, `APPROVED`·`ISSUE_DELAYED`·`AWAITING_DEPOSIT`·`PARTIALLY_REFUNDED` 억제, `notification_dedup` 1회(메모리), vars 7키, 구독별 푸시 1회, 5분−1ms 지연은 시험으로 확인된다. 100,000 경계·법정 고지 내용·HTML 이스케이프는 재리뷰에서 닫혔고, 실제 DB/Kafka는 미실행으로 남는다.

- 이 계획 커밋은 동결 범위 정본과 계약 생성물을 주 폴더의 로컬 `develop`에서 그대로 가져왔다. `roles-check.mjs`의 '계획 커밋은 문서만' 규칙에는 생성물(`packages/*/src/gen`)과 `tools/ci/release-scope.*`가 걸린다. 범위 동기화라 기능 구현이 아니며, 합칠 때 감독이 이 예외를 확인한다. 다만 리뷰 RV068-01에 따라 v1 릴리스 계약(105/38/0/67→109/38/0/71) 변경은 소유자 승인 전에는 합치지 않는다.

## 10. 게이트(이번 턴)

```bash
pnpm lint
python tools/doc-check/check_all.py
node tools/ci/ledger.mjs --batch F-06-8 --require
node tools/ci/release-scope.mjs --check
pnpm --filter @peaket/contracts gen:check
pnpm --filter @peaket/api-client test
```

- 계약(openapi)을 이번 턴에 고치지 않는다. 구현 때 `Order.bookingNumber`의 `[가정]` 문구를 고치면 `packages/contracts`·`packages/api-client`의 `gen`을 함께 돌린다.
- **`release-scope --check`는 실패가 정상이다**: 계약 파일은 `origin/develop`의 105/38/0/67로 되돌렸고, 이 가지 `docs/BUILD_ORDER.md`는 F-06-8~11이 등록된 109/38/0/71이다. F-06-8~11 등록과 계약 109 변경은 소유자 결정 몫이며, 이 가지는 합치지 않는다. 이 실패를 통과로 세지 않는다.
- Docker·kind·AWS는 쓰지 않는다. 통합 시험이 필요하면 `take docker-2 lane2-F-06-8`(docker는 다른 측정 중), `docker-all` 금지.
- 이번 턴 결과: lint·doc-check(오류 0)·ledger `--require`(9)·`gen:check`·api-client 116·core/purchase typecheck 통과. `release-scope --check`는 105 vs 109로 실패(통과로 세지 않음). 구현 뒤 core **10/10**·purchase **4/4** 통과.

## 11. 위험과 남은 몫

- **소유자·외부**: SES production access, 발신 도메인 `notify.peaket.example` 인증(SPF·DKIM·DMARC·custom MAIL FROM), IAM Pod Identity 역할, Solapi 계약(F-06-9), 법정 고지 번역·법률 검토, 실제 수신자 주소 확인.
- **F-06-6(막힘)**: 운영 메일·문자 대행사·VAPID 운영 키. 이 기능은 local·ci 흉내 발송기로만 끝까지 돈다.
- **F-06-9 경계**: 알림톡·문자, 제공자 웹훅(SES SNS·Solapi), CS 다시 보내기, 발신번호·카카오 채널, 관측·예산. 이 기능은 이메일·웹 푸시만 보낸다.
- **수치 주장 금지**: 30k/s·100만·K1/K2/K7 0 같은 측정 수치를 이 계획·시험·보고에 쓰지 않는다. 5분·24시간·99%·2,048바이트는 정본의 [가정] 값이다.
- **번호 충돌**: 원안 ADR-0386이 출시 범위 ADR-0386과 겹쳐 이 트랙에서 0392로 옮겼다. 합칠 때 감독이 ADR 번호를 다시 확인한다.
- **Kafka 소비자**: 구현 때 `trade.orders` 소비자 그룹 `peaket.core-svc-notify.<환경>`과 `held_event`·오프셋 커밋을 함께 만든다. 이번 시험은 intake 경계로만 보고, PostgreSQL·Kafka 경계는 **미실행**이다.
- **릴리스 계약 충돌(RV068-01)**: 계약은 105/38/0/67, 가지 BUILD_ORDER는 109/38/0/71이다. `release-scope --check`는 실패하며, F-06-8~11 등록과 계약 변경은 소유자 승인 전에는 합치지 않는다. 이 가지는 동결 로컬 트랙이다.

## 13. 완료의 정의

`CONFIRMED` 주문에서 이메일 한 통과 구독마다 웹 푸시 한 번이 5분 [가정] 안에 나가고, 같은 사건·재확정에도 늘지 않으며, `APPROVED`·`ISSUE_DELAYED`·`AWAITING_DEPOSIT`·`PARTIALLY_REFUNDED`로는 가지 않는다. 예매번호가 KST 날짜+5자리로 만들어지고 99,999 상한에서 503으로 닫힌다. `notice-view`가 내부 토큰 없이는 401이고 이름·좌석 번호를 싣지 않으며, `phoneE164`는 내부 응답에만 있고 작업·기록·로그에 남지 않는다. vars가 일곱 키뿐이고 판매자 7항목·법정 고지가 네 언어 HTML·text에 있으며 외부 이미지·추적 픽셀·JavaScript가 없다. 알림 실패가 주문·결제·발권을 바꾸지 않는다. N-T25·N-T27·N-T28이 통과하고 lint·doc-check·ledger `--require`·`gen:check`·api-client 116이 통과한다. `release-scope --check`는 계약 105/67과 가지 109/71의 충돌로 실패하며 통과로 세지 않는다. PostgreSQL·Kafka 경계는 미실행이라 완료 정의에 넣지 않는다.
