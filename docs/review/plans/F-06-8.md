## 1. 끝내는 것

1. purchase-svc `trade.orders`의 `CONFIRMED`만 소비해 알림을 적재한다. 같은 사건은 `notification_dedup`으로 한 번만 적고, `APPROVED`·`ISSUE_DELAYED`·`AWAITING_DEPOSIT`·`PARTIALLY_REFUNDED`로는 보내지 않는다. 가상계좌는 입금이 확인되어 `CONFIRMED`가 된 때 처음 보내고, 입금 오류로 `AWAITING_DEPOSIT`로 돌아갔다 다시 `CONFIRMED`가 되어도 한 번만 보낸다.
2. `GET /internal/v1/orders/{orderId}/notice-view`(purchase-svc, 내부 토큰)로 예매번호·주문 상태·알림 허용 여부·회차·등급 ID를 읽는다. 예매번호는 KST `YYYYMMDD` + 5자리 일련번호(예 `2026101400123`)이고, 하루 99,999건을 넘으면 주문 생성을 503 `booking-number-exhausted`로 닫고 SEV2를 올린다.
3. `notice-view`·core catalog로 vars를 조립한다. 허용 목록은 `productionName`·`eventStartsAt`·`venueName`·`seatSummary`·`amount`·`bookingNoLast4`·`orderId` 일곱뿐이다. 판매자 7항목·이름·전화번호·좌석 번호는 `vars`에 넣지 않는다.
4. 이메일은 코드에 고정한 HTML+text 판(ko/en/ja/zh)으로 Amazon SES 서울 리전(`ap-northeast-2`)에서 보낸다. 판매자 7항목·중개자 고지·미성년자 계약 취소 고지·취소·환불 안내를 넣고, 외부 이미지·추적 픽셀·JavaScript를 쓰지 않는다. 번역이 없으면 ko로 대체하고 `notify_template_missing_total{locale}`을 올린다.
5. 웹 푸시는 그 계정의 살아 있는 `push_subscription` 구독마다 작업 하나를 만들어 한 번씩 보낸다. 확정 사건을 받은 뒤 5분 [가정] 안에 보낸 비율을 잰다. 알림이 실패해도 주문·결제·발권 상태를 바꾸지 않는다.
6. 지표 5종: `delivery_job_due_backlog{kind="BOOKING_CONFIRMED"}`, `notification_dedup.created_at`→`notification_delivery.sent_at` 지연(`notify_delivery_latency_seconds{kind,channel}`), `notify_template_missing_total{locale}`, `notify_email_send_total`, `notify_email_failures_total`.

### 4.1 purchase-svc

- HTTP `GET /internal/v1/orders/{orderId}/notice-view`: `InternalTokenGuard`, 내부 서비스 계정만, 200 `{bookingNo, status, noticeAllowed, eventId, tierIds}`, 없으면 404 `not-found`. 이름·전화번호·좌석 번호는 응답에 없다. 내부 경로라 공개 openapi에는 넣지 않고 `docs/api/guidelines.md` §8의 내부 HTTP 목록과 `docs/architecture.md` §3.2에 적는다(구현 때).
- 주문 생성은 멱등 재생(`COMMITTED`)에서는 번호를 새로 잡지 않는다. 새로 만들 때 가격 계산 뒤·`writes.create` 앞에서 잡는다. 트랜잭션이 실패하면 번호는 건너뛴다(빈틈 허용).
- `booking_no_sequence(day, next)`는 `INSERT … ON CONFLICT (day) DO UPDATE SET next = next + 1 RETURNING next`로 잡는다(data.md).

### 4.2 core-svc notify

```ts
// domain/fan-notify.ts
export type FanNoticeKind = ... | 'BOOKING_CONFIRMED';
VARS_ALLOWED.BOOKING_CONFIRMED = ['productionName','eventStartsAt','venueName','seatSummary','amount','bookingNoLast4','orderId'];

// application/notification-intake.ts
export interface BookingConfirmedEvent {
  type: OrderEventType;          // 'CONFIRMED'만 보낸다. 다른 값은 억제
  eventKey: string;
  orderId: string;
  eventId: string;
  accountId: string;
  occurredAtMs: number;
  amount: number;
  items: readonly { tierId: string }[];
}
export interface BookingIntakeResult {
  created: number;
  duplicate: number;
  suppressed?: 'not_confirmed' | 'not_allowed';
  held?: boolean;
}
class NotificationIntake {
  bookingConfirmed(e: BookingConfirmedEvent): Promise<BookingIntakeResult>;
}

// domain/fan-notify-ports.ts
export interface BookingNoticeReader {
  get(orderId: string): Promise<BookingNoticeView | undefined>; // UNAVAILABLE는 던진다
}
export interface NoticeCatalogView {
  getBookingNotice(eventId: string, tierIds: readonly string[]): Promise<{
    productionName: string;
    venueName: string;
    eventStartsAt: string; // ISO 8601
    tierNames: Readonly<Record<string, string>>;
    seller: SellerNoticeInfo | null;
  } | undefined>;
}
export interface SellerNoticeInfo {
  legalName: string; representative: string; address: string; phone: string;
  email: string; businessRegNo: string; mailOrderReportNo: string;
}
export interface NotifyHeldEvents {
  hold(e: { eventKey: string; kind: string; payload: Record<string, unknown>; attempts: number }, now: Date): Promise<void>;
}

// MailMessage에 html?: string
// NotificationJob.templateVersion?: string, NotificationDeliveryRecord.templateVersion?: string

// domain/notify-signals.ts (새 포트)
export interface NotifySignals {
  dueBacklog(kind: string, count: number): void;
  deliveryLatency(kind: string, channel: NotificationChannel, seconds: number): void;
  templateMissing(locale: string): void;
  emailSent(): void;
  emailFailed(): void;
  suppressed(reason: 'not_confirmed' | 'not_allowed'): void;
  tierNameMissing(): void;
  bookingNoInvalid(): void;
}
```

- `NotificationIntake.bookingConfirmed` 차례: ⑴ `type !== 'CONFIRMED'` → `suppressed: 'not_confirmed'`(notice-view를 부르지 않는다) ⑵ `noticeReader.get(orderId)` — 없거나 `noticeAllowed=false` → `suppressed: 'not_allowed'` ⑶ 예매번호가 없거나 모양이 틀리면 `bookingNoInvalid()`(SEV3)이고 작업을 만들지 않는다 ⑷ `catalog.getBookingNotice(eventId, tierIds)`로 이름·장소·시각·등급 이름을 읽는다(없으면 재시도, 3회 뒤 `held`) ⑸ vars를 만든다 ⑹ 이메일 하나와 살아 있는 웹 푸시 구독마다 하나를 `store.enqueue`로 적는다(한 트랜잭션, Kafka 오프셋 커밋은 구현).
- 중복 키: `BOOKING_CONFIRMED:{orderId}:CONFIRMED:{accountId}:{channel}`, 웹 푸시는 `:{subscriptionKey}`를 더 붙인다. 사건 ID 대신 `CONFIRMED`를 쓴다.
- `expiresAt`은 사건 시각 + 24시간 [가정]. `templateVersion`은 `v1`.
- `seatSummary`: `tierId`별 매수를 catalog 등급 이름으로 바꿔 `"R석 2매, S석 1매"`처럼 만든다. 이름이 없으면 `"좌석 {n}매"`(전체 매수)와 `tierNameMissing()`.
- 웹 푸시 작업은 `webPushTargetOf`가 `BOOKING_CONFIRMED`의 구독 키를 읽도록 넓힌다. 워커는 그 구독 하나에만 보낸다.
- 워커는 보내기 전에 `noticeReader.get(orderId)`를 다시 본다. `noticeAllowed=false`면 작업을 지우고 `suppressed('not_allowed')`를 올린다. 이메일은 catalog에서 판매자를 읽어 템플릿을 그린다. 판매자가 없으면 이메일만 재시도한다. 웹 푸시는 catalog를 기다리지 않는다.
- 이메일 성공: `emailSent()`·`deliveryLatency(job.createdAt→now)`·`templateVersion`을 기록. 실패: `emailFailed()`. DEAD 1건 이상 SEV3.
- `MailMessage.headers['content-type']`는 어댑터가 multipart로 정한다. `html`이 없으면 지금처럼 text/plain.

### 4.3 템플릿

```ts
// templates/booking-confirmed/index.ts

  seller: SellerNoticeInfo | null;
  customerCenterUrl: string;
  publicOrigin: string;
}): { version: string; subject: string; text: string; html: string };
```

- 판은 `ko.ts`·`en.ts`·`ja.ts`·`zh.ts`로 나누고, 공통 조립은 `index.ts`가 한다. 값은 자리표시자로만 넣고 HTML 이스케이프한다.
- HTML: 600px 표, 인라인 CSS, `<!doctype html>`, `lang`, 제목 h1/h2, 링크는 `PEAKET_PUBLIC_ORIGIN` 절대 주소. 외부 이미지·추적 픽셀(`<img>` 금지)·JavaScript·폼·`on*` 속성 금지. 판매자 블록과 고지 글씨는 14px 이상으로 하고 판매자 표시보다 작지 않게 한다.

## 12. 완료의 정의

`CONFIRMED` 주문에서 이메일 한 통과 구독마다 웹 푸시 한 번이 5분 [가정] 안에 나가고, 같은 사건·재확정에도 늘지 않으며, `APPROVED`·`ISSUE_DELAYED`·`AWAITING_DEPOSIT`·`PARTIALLY_REFUNDED`로는 가지 않는다. 예매번호가 KST 날짜+5자리로 만들어지고 99,999 상한에서 503으로 닫힌다. `notice-view`가 내부 토큰 없이는 401이고 이름·전화번호를 싣지 않는다. vars가 일곱 키뿐이고 판매자 7항목·법정 고지가 네 언어 HTML·text에 있으며 외부 이미지·추적 픽셀·JavaScript가 없다. 알림 실패가 주문·결제·발권을 바꾸지 않는다. N-T25·N-T27·N-T28이 통과하고 lint·doc-check·ledger `--require`·release-scope·`gen:check`·api-client 116이 통과한다.
