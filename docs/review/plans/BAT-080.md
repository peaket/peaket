# 묶음 계획: BAT-080(BAS-130·BAS-140 — 진단 e2e 복귀와 배포 상태)

- **무엇**: 묶음을 시작할 때 만든 작업 목록이다(docs/architecture.md §8.6 4). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다. 값은 되도록 옮겨 적지 않고 자리(문서:줄)를 가리킨다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane4`, 가지 `feature/lane4-BAT-080`, 출발점 `origin/develop` `ebfb61e2`. 구현 전 트리는 시작할 때 `D:/ticketpass-lane4-base`(`ebfb61e2`, 분리 HEAD, 커밋 안 함)로 만든다. 2026-11-19 계획 담당 `bat080-plan-e0d0`(deepseek-v4.1-flash, 세션 `ses_e0d057f2cffeIjiRDeA32bwPJx`)가 썼고 시험·제품 코드는 쓰지 않았다. 이 PC에서 시험·Docker·kind를 돌리지 않았다.
- **등급·차례**: B(배포 기반·환경, docs/BUILD_ORDER.md:70). 짧은 고리(ADR-0283 결정 2)를 쓴다: 계획 → 구현 → 시험(구현 전 트리에서 실패 확인을 같은 커밋에) → 리뷰 → 리뷰 반영 시험(재현 시험과 실패 확인을 한 커밋) → 리뷰 반영 구현(고침과 시험 결과를 한 커밋) → 검증 → 기록. `Batch-Order: impl-first`로 시작한다.
- **이 계획의 몫**: 첫 일은 BAT-075가 넘긴 진단 e2e 둘의 복귀와 원인 고침이다(docs/lanes/lane4.md:10, docs/review/plans/BAT-075.md '시험 이의' TO-2·TO-5, '정리 목록' SEC-10). 그다음 BAS-140(배포 상태·공용 차트 확장·identity/realtime-gw 배포 값·승격 자동화)을 쓴다. **BAS-130은 BAT-081로 뗐다**(감독 결정 2026-11-19, 아래 '감독 결정 반영'). 묶음 표(docs/BUILD_ORDER.md:70)는 고치지 않았다(감독이 BAT-080 행 범위와 BAT-081 행을 넣는다).
- **정본**: [ADR-0070](../../adr/0070-incident-response-evidence-probes-timeouts-throughput-soak.md)(진단 증거), [ADR-0078](../../adr/0078-aiops-review-demand-forecast-action-exits-correlation.md) 결정 8(네임스페이스 지도·자원 할당량), [ADR-0169](../../adr/0169-one-public-monorepo-and-private-bot-repository.md)(배포 상태 `deploy/`), [ADR-0285](../../adr/0285-mesh-port-allow-source-generated-policies.md)(메시 포트 허용·생성 NetworkPolicy), [ADR-0296](../../adr/0296-realtime-gw-first-build-own-token-check-section-count-from-layout-file.md)·[ADR-0297](../../adr/0297-realtime-gw-review-fixes-subscription-owner-connection-caps-ping.md)·[ADR-0298](../../adr/0298-realtime-gw-degraded-switch-excess-wait-pod-window-connection-buffer.md)(realtime-gw), [ADR-0303](../../adr/0303-graceful-shutdown-shared-grpc-server-pod-diagnose-defaults.md)(진단 수집 구현 값). docs/devops.md §5.2 '배포 상태 구조'·§5.3 '승격 흐름'·§6.2 '카나리'·§3.1 'CI 잡', docs/infra.md §10 RB-31·§4.1 게이트웨이, docs/features/identity.md §2 '메시 신원 허용 목록'·§12 I-T15 ②·I-T50 ③, docs/observability.md §5 SEV2·G-06, docs/features/seat-hold.md §7 '전파 Degraded 자동 전환', docs/security/asvs/delivery.md 13.1.4·13.3.4, docs/security/secrets-and-keys.md '팬 액세스 토큰 서명 키' 행. 장부는 `docs/review/ledger/`를 본다.

## 감독 결정 반영(2026-11-19)

- **'감독에게' 1(묶음 나누기)**: 승인. **BAT-080 = BAS-140 + 진단 e2e 복구**만 한다. BAS-130(MSK/NLB/CloudFront/Route 53/cert-manager, D-T46)은 새 묶음 **BAT-081**로 떼어 BAT-076 뒤에 둔다. `docs/BUILD_ORDER.md`의 BAT-080 행 범위 조정과 BAT-081 행은 감독이 넣는다. 이 커밋은 BUILD_ORDER를 고치지 않는다.
- **'감독에게' 2(장부 범위)**: 승인. 이 묶음의 장부 범위는 `I-T15 ②, I-T50 ③, delivery:v5.0.0-13.1.4, delivery:v5.0.0-13.3.4`(4항목)다. BAT-080 줄의 범위 칸은 감독이 고친다.
- **'감독에게' 3(ADR 번호)**: 승인. 번호 0310(배포 상태·승격)·0311(차트 배포 종류·기본값)·0312(e2e 실패 수집·남은 증거 키)를 쓴다.
- **'감독에게' 4~7**: 계획안대로 진행한다(초안 PR CI 먼저, 할당량 [가정], demo·prod 빈 디렉터리, `alert-check`는 OPS-010).

## 감독에게

정하지 않고 올리는 것과, 이 계획이 정한 것을 알린다.

1. **묶음 나누기(BAS-130 / BAS-140)**: BAS-130은 MSK 사용자 지정 설정·NLB 셋·CloudFront 일곱·Route 53·cert-manager ACME의 Terraform 코드와 D-T46 정적 검사다(docs/BUILD_ORDER.md:413, docs/devops.md:925). 지금 `infra/`에는 `stacks/global/github`만 있고 AWS 스택이 없으며, `iac-check.yml`은 `terraform fmt`·`validate`만 돈다(`terraform plan` 없음). D-T46은 Terraform plan을 읽어야 하고, 그 스택은 BAT-076(BAS-120)이 만든다. BAT-076은 새 도구 이미지(tflint·checkov 등)·`terraform providers lock`의 소유자 결정으로 막혀 있다(docs/BUILD_ORDER.md:68). 그래서 **안**: BAT-080은 BAS-140과 넘겨받은 e2e만(약 2.5일 + e2e), BAS-130은 BAT-076 뒤의 새 묶음 하나(번호는 감독)로 뗀다. BAT-076이 먼저 끝나지 않으면 BAS-130의 D-T46은 쓸 수도, 시험할 수도 없다. 두 단계를 한 묶음에 두라고 하면 D-T46·NLB·CloudFront·Route 53·cert-manager는 BAT-076 뒤로 미루고, 이 계획의 나머지만 먼저 한다.
2. **장부 범위 좁히기(BAT-075와 같은 방식)**: 지금 BAT-080 줄의 범위 `D-T46, I-T15, I-T50, docs/infra.md, docs/devops.md, docs/security/asvs/delivery.md`를 장부가 읽으면 항목 201개(자동 시험 109, ID만 29, 측정 1, 미검증 1, 다른 단계 2, 담당 없음 3, 빈칸 56)다. 대부분 다른 단계 몫(D-T1~D-T17·D-T20~D-T44, delivery 3.x·14.x·15.x·16.x)이다. BAS-130을 떼면 이 묶음이 채우는 것만 남기는 안: `I-T15 ②, I-T50 ③, delivery:v5.0.0-13.1.4, delivery:v5.0.0-13.3.4`(항목 4, 모두 빈칸). BAS-130을 남기면 `D-T46`을 더한다(항목 8, D-T46 네 줄). I-T15 ①은 메시 운영 설계라 포트폴리오에서 재지 않고(docs/features/identity.md:729), I-T50 ①②④는 이미 자동 시험이라 뺀다. delivery 13.1.4·13.3.4는 '정할 곳: deploy, infra, tools/ci'인 빈칸이고, 이 묶음의 identity 토큰 키 셋 교체 값·realtime-gw ACL 비밀 교체가 그 자리다. 나머지 ASVS 행은 다른 단계 몫이라 뺀다(예: 14.1.1·14.1.2·14.2.7은 BAS-120·운영 확인, 16.2.x·16.4.x는 관측 단계).
3. **ADR 번호**: 이 계획이 정하는 것 가운데 셋은 결정에 가깝다. ① 배포 상태의 모양(ApplicationSet·AppProject·환경 값·승격 PR 흐름) ② 공용 차트의 배포 종류와 기본값(Rollout·PDB·KEDA·ExternalSecret·우선순위 클래스, local·CI는 Deployment 유지) ③ 진단 e2e 실패 수집과 남은 증거의 객체 키(요청 시각). **안**: 번호 0310(① '배포 상태와 승격 흐름'), 0311(② '공용 차트의 배포 종류와 기본값'), 0312(③ '진단 e2e 실패 수집과 남은 증거 키'). 번호를 주면 구현 담당이 ADR을 쓰고, 정본 문구에 '추천 적용 2026-11-19, BAT-080 계획'으로 번호를 붙인다. ③이 작으면 ADR-0303의 '남는 것' 한 줄로 접어도 된다.
4. **진단 e2e 첫 실행 경로**: **초안 PR CI 먼저**(ADR-0286 결정 5). 실패는 GitHub의 kind에서 났고(초안 PR peaket/peaket#36, 실행 44432753692의 kind 잡), 이 PC에서 같은 무대를 만들려면 Docker 잠금과 40분 이상이 든다. 첫 CI 실행은 **실패를 예상**하고, 새로 넣은 실패 수집이 낸 파드(전·현재 컨테이너)·moto 로그로 원인을 가른다. 그 로그로도 모자라면 그때 Docker 잠금(`lane4-BAT-080`)을 잡고 로컬 kind(`PEAKET_CLUSTER=lane4-b080`)로 좁힌다. 첫 실행이 초록이면 그 자체가 증거이므로 기록에 남기고 넘어간다.
5. **네임스페이스 자원 할당량 값**: docs/devops.md §5.2의 표는 `data`·`observability` 할당량을 'Karpenter NodePool 한도의 80% [가정, wbs 0.4.4에서 확정]'이라고 한다. 그 NodePool 한도는 BAT-076의 Terraform에 있다. **안**: 이 묶음은 `deploy/policies/resource-quotas.yaml`의 틀과 정적 시험만 만들고, 숫자는 [가정]으로 두며, NodePool 값이 생기는 BAT-076(또는 BAS-130 묶음)에서 80%로 맞춘다. wbs 0.4.4에서 지금 확정하라고 하면 숫자 결정을 감독이 준다(현재 문서에는 NodePool 최대 대수가 없다).
6. **demo·prod 환경 값**: 아직 출시 후보 다이제스트가 없다. **안**: `deploy/envs/demo/`·`deploy/envs/prod/`는 빈 디렉터리(README만)로 두고, 첫 승격 PR이 `<서비스>.yaml`을 만든다. 차트는 local·ci 밖에서 `image.digest`가 없으면 렌더를 멈추므로 빈 값 파일을 미리 두지 않는다. 승격 워크플로의 첫 실행은 가짜 출시 태그로 `--dry-run`만 하고, 실제 PR은 출시(BSL-050) 뒤에 연다.
7. **경보 규칙 파일과 `alert-check`**: BAT-053이 realtime-gw 경보 규칙을 BAS-140에 넘겼다(docs/review/plans/BAT-053.md '감독에게' 3). 그런데 저장소에는 아직 경보 규칙 파일이 없고, `docs/devops.md` §3.1의 `alert-check`(promtool·amtool)도 없다. **안**: 이 묶음은 `deploy/platform/observability/alerts/realtime-gw.yaml`과 YAML 정적 시험만 만들고, `promtool test rules`를 도는 `alert-check` 잡은 경보 규칙을 처음 두는 OPS-010(wbs 4.1.1)에 붙인다. 이 묶음에서 `alert-check`까지 원하면 promtool을 담은 이미지·판·다이제스트 결정이 먼저 필요하다.

### 2. 장부 범위

```text
I-T15 ②, I-T50 ③, delivery:v5.0.0-13.1.4, delivery:v5.0.0-13.3.4
```

- 이 커밋의 트리에서 `node tools/ci/ledger.mjs --batch BAT-080`를 돌리면 아직 BAT-080 줄의 넓은 범위(201항목)를 읽는다. 감독이 2의 안을 받아들이면 BAT-080 줄의 범위 칸을 위 네 항목(또는 BAS-130을 남기면 `D-T46`을 더한 여덟 항목)으로 좁힌다. 계획 담당은 BUILD_ORDER를 고치지 않았다.
- **I-T15 ②**: 메시 없는 실행에서 identity-svc gRPC 포트(50051)가 docs/features/identity.md §2의 허용 목록 밖 파드에 닿지 않는다. 지금 `deploy/platform/mesh/port-allow.yaml`의 identity-svc가 그 목록을 갖고 있고, `tools/ci/mesh-policies.mjs`가 `meshless-networkpolicies.yaml`을 만든다. 정적 시험 `mesh-policies.test.mjs`의 MS-03이 web→SessionService와 web 밖 서비스의 거부를 이미 보지만, 시험 이름이 `D-T36 ③`이라 장부가 I-T15 ②를 빈칸으로 본다. I-T15 ② 이름의 시험을 더하고, purchase-svc→SessionService 거부·web→IdentityService 거부를 채운다.
- **I-T50 ③**: waypoint L7 정책이 `SessionService`는 web만, `IdentityService`는 purchase-svc만 받는다. MS-03이 web 쪽은 보지만 purchase-svc가 `SessionService`에 닿지 않는 단언이 없다. 같은 시험에 그 두 방향을 더한다. kind 쪽은 `mesh-netpol.e2e.mjs`의 MK-03이 web→identity-svc 연결과 게이트웨이·image-worker·seatmap-worker·partner의 거부를 이미 본다. 그 판정을 I-T15 ② 이름으로도 내고, `stranger@core`·`gw-queue`가 여전히 거부되는지 함께 본다.
- **delivery 13.1.4·13.3.4**: 비밀·키 교체 절차가 위협 모델과 문서에 맞고, 문서대로 만료·교체되는지를 본다. 이 묶음은 identity 토큰 키 셋(`PEAKET_<FAN|ADMIN|STAFF>_TOKEN_KEY`, `…_NEXT`, `…_PREVIOUS`, `…_PREVIOUS_UNTIL`)과 realtime-gw 좌석 Redis ACL 비밀의 ExternalSecret 값·교체 차례를 시험한다. 실제 교체 실행은 운영 환경이 생긴 뒤다(런북 RB-26·RB-41).
- **범위 밖(빼는 것, 다른 단계로 미루는 것이 아님)**: D-T46(MSK 설정 정적 검사)은 BAS-130(BAT-076 뒤), I-T15 ①은 메시 운영 설계(docs/features/identity.md:729), I-T50 ①②④는 이미 자동 시험, delivery 13.2.4·13.2.5·13.3.2는 이미 ID만/자동 시험이라 이 묶음이 바꾸지 않는 동작의 회귀만 본다. docs/devops.md·docs/infra.md·delivery.md 전체를 범위로 두지 않는다(BAT-075와 같은 문제).

### 8. 차례

1. **G1 먼저**: `ci-kind.yml`에 e2e 복귀·실패 수집을 넣고 초안 PR을 올려 첫 진단 실행을 한다. 로그를 읽고 원인을 가른다. 이 실행은 실패해도 된다(진단이 목적).

5. **리뷰**: 정확성·동시 실행(배포), 보안·GitOps(승격·비밀) 둘. 리뷰 반영은 짧은 고리대로.

7. **기록**: BUILD_ORDER 체크·비고, R 기록, 번호 0310~0312(감독 승인 뒤).

### 11. CI/kind 실행 계획

- **초안 PR CI(1차, 진단)**: 가지를 push하고 초안 PR을 연다(자기 가지 강제 푸시가 막히면 `feature/lane4-BAT-080-r2`). `ci`의 `changes`가 `.github/workflows/ci-kind.yml`·`deploy/charts`를 보고 kind를 부른다. kind 잡은 `cluster up` → `image` → 기존 e2e → **새 diagnose e2e** → 실패 때 수집 순서로 돈다. 1차는 실패를 예상하고 kind 잡 로그에서 `diagnose-e2e` 파드 로그·`/diag`·버킷 전체·moto 로그를 읽는다. 산출물 `kind-bat075-measurements`(측정 파일 둘)도 내려받아 기록 담당에게 넘긴다.
- **초안 PR CI(2차, 고침)**: 원인을 고친 뒤 같은 PR에서 다시 돌린다. kind·node·tools가 모두 초록이어야 한다. kind 잡 상한 90분(ci-kind.yml 17행)은 그대로 두고, diagnose 두 시험의 실제 시간을 재어 상한을 다시 정한다(BAT-075 SEC-10).

## 시험 이의

- **DP-03: ApplicationSet이 값 파일을 찾지 못한다(제품 결함, 고치지 않음)**. 계획 5의 공개 계약과 6의 DP-03은 Git 디렉터리 생성기가 `deploy/envs/<환경>/*`를 읽어 local 값 파일을 모두 찾는다고 했는데, 구현 `deploy/projects/applicationsets.yaml`은 Kubernetes Git **디렉터리** 생성기(`directories: - path: deploy/envs/local/*`)를 쓴다. 이 생성기는 폴더만 만들므로 `deploy/envs/local/*.yaml` 파일 여섯(v0-gateway·v0-monolith·v1-bundle·v1-payment-relay·v1-purchase-relay·v1-realtime-gw)은 Application이 되지 못한다(시험이 본 생성 결과 `[]`, 기대 여섯). 같은 이유로 `template.spec.source.helm.valueFiles: ['{{ .path.path }}']`는 값 **파일**이 아니라 폴더 경로를 받게 된다. 구현 커밋 메시지도 이 한계를 적었다. 시험은 계획의 판정을 그대로 단언해 실패로 두었다. 고치는 길: ① Git 파일 생성기(`files: - path: deploy/envs/<환경>/*.yaml`)로 바꾸고 `{{ .path.path }}`를 valueFiles로 쓴다(계획·정본 416행의 '디렉터리 생성기' 문구도 함께 고친다). ② 또는 환경 값을 `deploy/envs/<환경>/<서비스>/values.yaml` 폴더로 재구성하고 valueFiles를 `{{ .path.path }}/values.yaml`로 쓴다(정본 407행의 파일 구조를 고쳐야 한다). 정본이 이기므로 ①이 작다.
- **감독 결정 ① 반영(2026-11-19)**: Git 파일 생성기(`files: - path: deploy/envs/<환경>/*.yaml`)로 고치고 `{{ .path.path }}`를 `valueFiles`로 쓴다. 정본 `docs/devops.md` 416행 문구도 'Git 파일 생성기'로 고쳤다. DP-01은 통과한다. DP-02·03은 시험 파일이 아직 `git.directories`를 읽어 실패하므로, 시험 담당이 `files`·`path.path`로 갱신한 뒤 DP-03 통과를 확인한다.
- **계획 7의 변이 번호**: "ID-05·ID-06 ... 9의 M14·M15로 실패를 본다"는 9의 표에서 M14(CH-02 Rollout 기본값)·M15(PDB maxUnavailable)라 ID-05·06과 맞지 않는다. ID-05·06의 틀린 구현은 M19·M20이다. 시험 담당이 M19·M20을 손으로 넣어 실패를 봤다(아래 '실패 확인').
- **RG-02의 자리**: 지시대로 경보 규칙 시험을 `tools/ci/alert-rules.test.mjs`에 두었다. `deploy/workloads/test/workloads.test.mjs`는 RG-01·RG-03만 본다(계획 6의 파일 배치와 조금 다르다).
- **DP-01의 `platform` 목적지(알고 둠)**: 여덟 서비스 팀 AppProject가 자기 네임스페이스와 함께 `platform`도 목적지로 받는다. 정본 지도는 `platform`을 platform 프로젝트 몫으로 적지만, 지금 ApplicationSet이 모든 환경 값을 `namespace: platform`으로 배포하고 환경 값 파일에 project·namespace 칸이 없어(구현 주석) 그렇게 두었다. 시험은 '자기 팀 네임스페이스와 공용 `platform`만 받는다'로 단언해 통과시켰다. 서비스별 project·namespace를 환경 값에 더하는 묶음에서 좁힌다(계획 BAT-080 범위 밖).
- **감독 결정 ①, 파일 생성기 시험으로 갱신(2026-11-19)**: 구현 담당이 `1f29132e`에서 `deploy/projects/applicationsets.yaml`을 Git 파일 생성기(`git.files`, `deploy/envs/<환경>/*.yaml`)로 바꾸고 `docs/devops.md` §5.2 416행을 'Git 파일 생성기'로 고쳤다. 그래서 DP-02·03을 새 계약(`git.files`·`{{ .path.path }}` valueFiles·`{{ .path.basename | trimSuffix ".yaml" }}` 이름)으로 갱신했고 DP-01~03이 모두 통과한다. 위 DP-03 결함은 닫혔다.
