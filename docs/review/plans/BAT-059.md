# 묶음 계획: BAT-059(HOT-401 끝난 세션의 토큰 거부와 탈퇴 15분 미루기 빼기)

- **무엇**: HOT-401(wbs 2.11.1 ④) 줄을 하는 A 등급 정방향 묶음의 작업 목록이다(docs/architecture.md §8.6 4의 1·2, ADR-0270 '계획'). 검토 기록이고 규범이 아니다. 정본과 다르면 정본이 이긴다. 정본 값은 옮겨 적지 않고 자리(문서:줄, 이 커밋 기준)만 가리킨다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane1`, 가지 `feature/lane1-BAT-059`, 출발점 `de4d6a67`(지시서 `node tools/ci/brief.mjs --batch BAT-059`, 같은 커밋). 2026-11-21 계획 담당 `bat059-plan-e47a4ddc`(claude-opus-5-5)가 썼고 시험·제품 코드는 쓰지 않았다. 앞 묶음은 docs/review/plans/BAT-057.md('감독에게' 1 (나)로 이 묶음이 나왔다).
- **등급**: A(docs/BUILD_ORDER.md:62). 항목 7개(I-T3 ①~④, I-T48 ①~③)는 장부에서 B지만 묶음 등급대로 모두 A로 증명한다: 항목마다 틀린 구현(기본 1, 경계·되돌림은 2), 복구 경로의 장애 주입, 판정 기준과 단언의 대조 전수(§8.6 3). 짧은 고리를 쓰지 않는다.
- **차례**: 정방향(이 계획 커밋에 `Batch-Order: impl-first`). 계획 → 구현 → 시험(구현 전 트리 `de4d6a67`에서 실패 확인) → 리뷰 → 리뷰 반영 계획 → 재현 시험 → 고침 → 다시 리뷰 → 검증 → 기록.
- **정본**: [ADR-0333](../../adr/0333-service-pods-consume-terminated-sessions-drop-queue-withdrawal-delay.md)(이 커밋), docs/features/identity.md:180~183(§3 '세션 즉시 무효화 전파', :183 '서비스에 잇기'는 이 커밋)·:551 '남는 한계'·:697 운영 확인 줄·:725 I-T3(①~④는 이 커밋)·:771 I-T48, docs/features/queue-admission.md:251·:310·:311, docs/adr/0103-control-as-state-startup-sync-broadcast-topics-compacted-settings.md 결정 2·3, docs/adr/0214-queue-sale-state-consumers-redis-held.md:50~58(결정 7), docs/observability.md:420·:429, docs/verification.md:474~475, docs/data.md:2672·:2933, docs/security/asvs/auth.md:123(7.4.1).

## 감독에게

방향을 바꾸는 결정은 정하지 않았고 계획은 아래 1의 (가)로 썼다. 1은 답을 받기 전에도 구현을 시작해도 된다(다른 답이면 §4의 한 줄이 는다).

1. **[결정 요청] 핫패스 파드의 Kafka 연결이 는다.** 종료 세션 목록 소비는 파드마다 Kafka 클라이언트 셋(방송형 소비자 둘 + 관리 연결 하나)을 더한다(packages/platform/src/control.ts:279 `topicTask`가 토픽마다 `read`를 따로 돌리고, packages/platform/src/stream-worker.ts:420 `kafkaBroadcastSource`가 `read`마다 소비자를 만든다). queue-svc는 T=0에 파드가 크게 늘어 클라이언트가 파드당 하나에서 넷이 된다. ADR-0214가 토픽마다 그룹을 두지 않은 까닭이 바로 '연결 세 배'였다. 정본 ADR-0103 결정 2·3은 모든 파드의 방송형 읽기와 준비 상태가 Kafka(30초 뒤 포기)에 기대는 것을 이미 받아들였으므로 그 부분은 묻지 않는다. 묻는 것은 연결 수다.
   - (가) **(추천)** 지금 구조로 켜고, 자원 한도 표에 줄을 두어(docs/verification.md:475, 이 커밋) MSK 연결 한도·HPA 최대 파드 수가 정해지는 구간 5에 판정한다. 넘으면 두 토픽을 소비자 하나로 읽는다(ADR-0333 '되돌릴 조건' 첫째).
   - (나) 이 묶음에서 플랫폼 방송형 읽기를 두 토픽 소비자 하나로 다시 짠다(+0.5~1일 [가정], `topicTask`·준비 작업·D-T29 시험이 함께 바뀐다).
   - (다) queue-svc만 켜지 않는다: 미루기를 뺄 근거가 사라져 ②를 할 수 없다. 고르지 않았다.
2. **[확인] 범위를 넓혔고 크기가 WBS 0.25일보다 크다.** 범위 칸을 `I-T3, I-T48`로 고쳤다(docs/BUILD_ORDER.md:62, 이 커밋). I-T3을 ①~④로 나누고(docs/features/identity.md:725), 어느 묶음에도 없던 I-T48 ①~③(새 파드의 종료 세션, 빈칸)을 더했다. 새 파드의 되감기와 Kafka 끊김 뒤 다시 읽기가 이 묶음이 켜는 바로 그 복구 경로라서다. D-T29(플랫폼 시작 작업, 이미 자동 시험)·I-T27(탈퇴 기준 자체는 그대로)·I-T83(후기 다시 정리는 남김)은 닿지 않아 뺐다. 크기는 플랫폼 0.5 + 서비스 일곱 잇기 0.5 + 탈퇴 미루기 빼기 0.5 + 시험 1~1.5 ≈ **3일 [가정]**로 5일 안이다.
3. **[나누기 안, 추천은 나누지 않음]** 신원을 받는 서비스를 코드로 셌다: 공용 가드(packages/platform/src/auth.ts:381 `state.terminated.has`)는 이미 모든 서비스에 있고, 빠진 것은 `startControlSync`를 부르는 곳뿐이다(`git grep startControlSync -- services` 0줄). 신원 역할 처리기가 있는 서비스는 core·identity·ops·payment·purchase·queue·ticket 일곱이다(trust-svc는 공개 처리기만, realtime-gw·admission-ctrl은 없음). 도우미 하나를 부르는 일이라 서비스마다 10줄 안팎이다. 한 턴에 벅차면 (나) BAT-059 = 플랫폼 + queue-svc + 미루기 빼기(I-T3 ①③④, I-T48), 새 묶음 = 나머지 여섯 서비스(I-T3 ②)로 나눈다. 나누면 I-T3 ②가 새 묶음으로 가고 HOT-401 체크도 그 뒤다.
4. **[확인] 미루기 빼기는 정본대로다.** ADR-0214 결정 7 끝 줄이 '종료 세션 목록이 생기면 뺀다'고 정해 두었으므로 뒤집는 결정이 아니다. 남는 틈(두 토픽 도착 차이, 이미 가드를 지난 요청, 보통 1초 안 [가정])은 ADR-0333 '결과'에 적었다. 그 틈까지 덮으려면 후기처럼 '탈퇴 + 16분 다시 정리'를 두는 길이 있으나 처리할 때 집합을 다시 들이는 일이라 하지 않았다(되돌릴 조건 둘째).
5. **[확인] 배포 쪽은 구간 5.** 두 제어 토픽 만들기(`control.settings`는 압축), 새로 Kafka에 닿는 서비스(identity 앱·payment·ticket)의 브로커 주소, MSK 권한(파드마다 다른 그룹 이름), 로컬 무대 토픽 목록(tools/local/v1-objects.mjs:24)은 이 묶음에서 하지 않는다(§13). 그동안 브로커 주소를 준 무대에서는 파드가 30초 뒤 준비되고 `control_sync_lagging=1`이 남는다.
6. **[알림] Docker와 Kafka 통합 시험.** 2026-11-21 이 작업 폴더에서 Kafka 네이티브 모듈이 로드되고 Docker(29.8.1)가 돈다. I-T3 ①·I-T48과 서비스 통합 시험은 로컬에서 돌릴 수 있다. 잠금은 감독 지시서의 `lock.sh`로만. 게이트(§10)의 통합 시험이 서비스 여덟 묶음(플랫폼 + 일곱)이라 길다(약 60~90분 [가정]). 초안 PR CI로 돌리려면 develop 밖 원격 가지 푸시라 소유자 확인이 든다.
7. ADR은 0333 하나만 썼다. 마이그레이션은 없다.

## 계획

### 1. 범위

- **P1 플랫폼**: 운영 해독기, 종료 시각을 읽지 못한 사건의 처리, 건너뛴 레코드 셈, 브로커 설정 읽기와 시작 도우미, 빠뜨림 막기(ADR-0333 결정 2~4).
- **P2 서비스 일곱 잇기**: core·identity·ops·payment·purchase·queue·ticket의 시작 파일이 듣기 전에 도우미를 부르고 닫을 때 끈다(결정 1·2). 서비스 틀(packages/platform/template)도 같다.
- **P3 queue-svc 탈퇴 미루기 빼기**: 처리기는 받자마자 처리, 처리할 때 집합·반복·지표 셋을 없앤다(결정 5·6).

### 5. 공개 인터페이스(시험 담당이 기댄다. 이름은 구현이 이대로 쓴다)

- `@peaket/platform`
  - `controlEventCodec: ControlCodec`. `sessionTerminated(value)`: JSON. `sessionId`가 비지 않은 글이 아니면 던진다. `terminatedAt`은 ISO 시각 글이면 그 밀리초, 수면 그대로, 그 밖은 `NaN`. `reason`·`accountId`는 글이 아니어도 던지지 않는다. `setting(value)`: asyncapi `SettingChanged`(contracts Zod)로 읽고 `occurredAt`·`expiresAt`을 밀리초로 바꾼다. 틀리면 던진다.
  - `startControlSync`(모양 그대로): 해독기가 던지면 그 레코드를 건너뛰고 `control_sync_skipped_total{service,topic}`을 1 올린다. 종료 시각이 유한한 수가 아니면 받은 때를 종료 시각으로 쓴다.
  - `PlatformService.listen()`: `PEAKET_ENV`가 local·ci가 아니고, 신원 역할(공개 말고) 처리기가 하나라도 있고, `startServiceControlSync`를 부르지 않았으면 `PlatformConfigError`로 던지고 듣지 않는다.
- `@peaket/platform/stream-worker`
  - `controlSyncConfigFromEnv(service: string, env: Record<string, string | undefined>): { enabled: false; warning: string } | { enabled: true; brokers: string[]; auth?: KafkaAuth; env: string; pod: string }`. 브로커가 없거나 빈칸뿐이면 local·ci만 꺼진 설정, 그 밖은 `PlatformConfigError`. 틀린 조각은 몇 번째인지만 알린다(원문을 싣지 않는다). `pod`는 `PEAKET_POD` → `HOSTNAME` → 호스트 이름, 64자까지.
  - `startServiceControlSync(service: PlatformService, env: Record<string, string | undefined>, o?: { degradeAfterMs?: number; retryMs?: number; measureMs?: number; reconcileMs?: number }): { sync: ControlSync; close(): Promise<void> } | undefined`. 꺼진 설정이면 경고 한 줄(`dep: 'kafka'`, `kind: 'control-sync'`)을 남기고 `undefined`. 켜지면 `kafkaBroadcastSource` + `controlEventCodec`으로 `startControlSync`를 부르고 시작 표시를 남긴다. `close()`는 `sync.stop()` 뒤 읽기 연결을 닫고 두 번 불러도 한 번만 한다. `o`는 시험이 시간을 줄일 때만 쓴다(서비스 시작 파일은 넘기지 않는다).
- 준비 프로브 `GET /ready`(관리 포트): 소비가 켜진 서비스는 두 토픽을 다 읽기 전에 503이고 `pending`에 `settings`·`sessions`가 있다(packages/platform/src/service.ts의 `/ready`).
- queue-svc: `new AccountWithdrawnHandler(purge, codec?, o?: { clock?: Clock })`. `WITHDRAWN_DELAY_MS`·`WITHDRAWN_CLOCK_SKEW_MS`·`WithdrawnDueWorker`·`WITHDRAWN_DUE_DEFAULTS`·`RedisWithdrawnDue`·`MemoryWithdrawnDue`·`wdrKeys`·`DUE_LEASE_MAX_MS`·`WithdrawnDue`·`DueWithdrawal`은 없어진다. `MAX_PURGE_AFTER_MS`·`jsonAccountWithdrawnCodec`·`ACCOUNTS_WITHDRAWN_TOPIC`은 그대로. 지표 `queue_withdrawn_due_*`는 없다.

### 7. 구현 전 트리에서 실패를 볼 수 없는 시험과 까닭

- `controlEventCodec`·`controlSyncConfigFromEnv`·`startServiceControlSync`를 직접 부르는 단위 시험: 구현 전에는 이름이 없어 가져오기에서 깨진다(실행조차 안 되는 실패라 세지 않는다). 실패 증명은 §9 M3·M6·M7·M8·M9·M11로 한다. 같은 판정을 바깥 경계(서비스의 `/ready`, HTTP 401)로도 하나씩 두면 그것은 구현 전에 실패를 본다(구현 전에는 `/ready`가 바로 200이고 401이 아니라 200).
- I-T3 ③의 15분 경계: `TerminatedSessions`(packages/platform/src/auth.ts:176)가 이미 맞게 한다. 구현 전에도 통과하므로 §9 M10으로 실패를 본다.
- I-T48 ③의 30초 기본값 자체: 플랫폼 D-T29 ④가 이미 본다(구현 전 통과).
- I-T3 ④의 '`q:{wdr}:` 키 없음'과 '받자마자': 구현 전 처리기는 미루므로 실패를 본다(세는 실패).

### 8. 차례(구현 담당)

1. 플랫폼: 해독기 → control.ts 고침과 셈 → 설정 읽기·도우미 → 빠뜨림 막기 → `pnpm --filter @peaket/platform build`(서비스는 dist를 읽는다).
2. queue-svc: 도우미 잇기 → 미루기 빼기(처리기·start.ts·지운 파일·index.ts).
3. 나머지 여섯 서비스와 틀: 도우미 잇기.
4. 바꾼 패키지마다 타입 검사·`pnpm lint`. 지운 이름을 쓰는 시험의 타입 오류는 시험 담당 몫으로 '구현 메모'에 목록만 남긴다.
5. 빠뜨림 막기에 realtime-gw·admission-ctrl·trust-svc가 걸리면(신원 처리기가 있다는 뜻) 그 항목을 멈추고 '구현 메모'에 적는다(정본 ADR-0333 결정 1과 어긋남).

### 11. 시험·구현 지시문에 넣을 '자주 놓친 결함'(docs/architecture.md:1166~1182에서 고름)

- 저장소 응답은 정확한 값까지: `PEXPIREAT`의 값, `control_sync_skipped_total`의 정확한 증가, `pending` 목록의 내용.
- 지우는 연산은 건드린 키를 모두: `q:dup`·`q:adm` 둘과 다른 pid·다른 회차는 그대로, `q:{wdr}:` 키 없음.
- 경계값 양쪽: 15분 − 1ms와 15분, 준비 시간 한도 직전과 직후. 단언 값은 코드 상수를 가져오지 말고 정본 값(15분, 5초 [가정], 30초)을 적는다. 시험의 기간 값은 코드 상수와 다르게 골라 상수 오용이 숨지 않게 한다(예: `o.degradeAfterMs`는 30초가 아닌 값).
- 허용·거부 목록: 이유 값은 목록의 값마다와 목록 밖 값까지 모두 거절을 본다.
- 판정 함수만이 아니라 부르는 쪽: `isTerminated`가 아니라 실제 HTTP 처리기의 401을 본다.
- 겹친 가드: identity-svc는 자기 경로가 DB로 끝난 세션을 막는다(identity.md:551). identity의 I-T3 시험은 DB 확인이 없는 처리기(목록만 막는 곳)로 보거나, DB 확인을 둔 채 목록만 뺀 틀린 구현이 잡히는지 확인한다.
- 장애 주입은 끊김이 실제로 있었음을 단언한다(게이지 1, 연결 실패).
- 시작 파일의 조립은 시험 조립과 따로 본다(§6 I-T3 ② (a)(b)).
- 측정·통합 시험이 Docker 없음으로 조용히 넘어가지 않는다(통합 시험은 Docker가 없으면 실패한다, CLAUDE.md).

## 리뷰 반영 계획

계획 담당 `bat059-plan2-fc835edc`(claude-opus-5-5)가 리뷰 `6690402a` 뒤에 썼다(등급 A라 따로 커밋, docs/architecture.md §8.6 5). 감독 판정대로 R059-1만 이 묶음에서 고친다. R059-2~11은 정리 목록으로 가고 감독이 기록 커밋에서 옮긴다. 차례: 재현 시험(시험 담당) → 고침(구현 담당) → 고친 곳 다시 리뷰(리뷰 담당, 고침·재현 시험 커밋의 차이만) → 검증(검증 담당, §9 M20a~M26을 함께).

### 1. 바른 동작(정본: ADR-0333 결정 4 둘째~넷째·여섯째 줄과 '결과' 남는 한계, identity.md:183·:697·:725 ③, observability.md:420. 모두 이 커밋, '추천 적용, 2026-11-21, BAT-059 리뷰 반영 R059-1')

- 기준 `k`는 그 레코드의 Kafka 시각(`BroadcastRecord.timestamp`)이다. 0 이하이거나 유한한 수가 아니면 받은 때(파드 시계 `n`)로 견준다.
- 종료 시각 `t`를 그대로 쓰는 범위는 `k − 15분 < t ≤ k + 1분 [가정]`이다. 그 밖(`t + 15분 ≤ k`이거나 `t > k + 1분`)과 읽지 못한 값(지금의 NaN 갈래)은 받은 때부터 15분 막고 `control_sync_skipped_total{service,topic="control.sessions-terminated",reason="time_replaced"}`를 1 올린다. 해독기가 던져 건너뛴 레코드는 `reason="unreadable"`이다(두 토픽). 세 줄은 0으로 미리 낸다.
- 15분은 목록 기간(= 액세스 토큰 수명, identity.md:180, ADR-0011 결정 2)이다. Kafka에 들어간 때 이미 목록 기간이 끝난 값은 늦게 보낸 사건이든 틀린 값이든 가를 수 없어 닫힌 쪽으로 간다. 미래 1분은 노드 시계 차이(20ms 경보, observability.md:393)에 넉넉히 둔 값이고 ADR-0214 결정 7이 두었던 시계 허용 차이와 같다. 받은 때 기준이 아닌 까닭은 되감기 끝자락·릴레이 지연으로 받은 때 이미 지난 정상 사건을 틀린 값으로 세지 않기 위해서다(그 사건은 지금처럼 `TerminatedSessions.add`가 넣지 않는다).
- 방향을 바꾸지 않는다. 결정 4의 '읽지 못하면 받은 때'의 범위를 정하고 셈에 까닭 라벨을 더했을 뿐이다. 바뀌는 기존 단언: ③-4의 `control_sync_skipped_total` 0 → `time_replaced` 6(값 여섯 모두 받은 때로 바꾼 것), ③-3·③-5의 셈은 `reason` 라벨을 붙여 본다(fixture `sample`은 라벨이 일부만 맞아도 첫 줄을 돌려주므로 라벨 셋을 다 준다).

### 2. 장애 주입(계획 §9 R1~R5)

- R1(준비 뒤 읽기 끊김): 커밋된 ③-2는 컨테이너 일시 정지로 끊는다. 그러면 읽기가 던지지 않아 다시 재는 갈래를 지나지 않는다(M18b가 산다). 그래서 임시 단위 시험을 만들어 돌린 뒤 지웠다(커밋하지 않음). 그 시험에서는 읽기 포트의 메모리 대역이 던지며 끊기고, 끊긴 동안 토픽에 사건이 들어간다. 지금 트리는 되살린 뒤 그 사건의 sid를 401로 막았고, 앞서 받은 sid도 401 그대로였다. 끊김이 실제로 있었는지는 `read`가 1번 이상 던졌다는 단언으로 확인했다. M18과 M18b 둘 다 이 시험에 잡혔다. 복구 경로 자체는 맞고, 그 경로를 보는 시험만 빠졌다.
- R2(시작 때 Kafka에 닿지 못함): I-T48 ③이 막힘이 실제로 있었음을 단언한다(막힌 동안 그 sid는 200, `lagging`은 1). M3·M18·M19를 잡았다.
- R3(깨진 레코드 사이의 정상 사건): ③-5가 깨진 값 일곱마다 바로 뒤의 정상 사건이 401인지와 `unreadable`이 정확히 1씩 오르는지를 본다. M13a·M13b·X5를 잡았다.
- R4(탈퇴 처리 중 Redis 일시 장애): ④-4가 TransientError를 본 뒤, 다시 할 때 정확한 기한으로 한 번 거는지 본다.
- R5(같은 탈퇴 사건 두 번): ④-3이 두 번 모두 같은 기한인지 본다.
- 이 묶음 밖의 흔들림이 두 번 있었다. 처음 기준 실행에서 queue-svc consumers의 Q-T51이 Redis 100ms 마감으로 한 번 실패했고, 다시 돌리니 4/4였다. M18b 첫 실행의 ③-2는 생산자 시간 초과로 실패했다(위 1). 둘 다 이 묶음이 바꾼 코드가 아니다.

### 3. 판정 기준 대조(identity.md:725 I-T3 ①~④, :771 I-T48 ①~③)

이름만 달린 시험은 없다. 항목마다 기준 문장을 단언이 실제로 본다.

- I-T3 ①: 맞다. control-sync 통합 I-T3 ①은 실제 Kafka를 쓰고, 파드 이름이 다른 인스턴스 둘을 띄운다. 기다림 한도는 사건을 넣은 때부터 5초다. 둘 다 그 sid를 401로 막고 다른 sid는 200임을 보고, 소비자 그룹이 파드마다 다른지도 본다. M1·M2를 잡았다.
- I-T3 ②: 맞다. 다만 덮는 폭이 좁은 곳이 둘 있다.
  - 일곱 서비스의 소스 경계 시험 ②-8·②-9가 '시간 옵션 없이 부른다, 듣기 전에 부른다, 서비스를 닫은 뒤 끈다'를 본다. ②-10·②-11(queue·purchase 실제 시작)은 /ready 503과 남은 작업 `sessions`를 본다. 플랫폼 ②-1·②-5는 브로커가 없으면 시작에 실패함을, ②-6은 소비 없이 듣지 않음을 본다.
  - 남은 작업 `sessions`를 실제 시작으로 보는 서비스는 일곱 중 둘뿐이다(R059-11).
  - 신원 처리기 판정은 공개와 신원을 함께 허용한 처리기를 보지 않는다(X1).
- I-T3 ③: 맞다. 기준 문장의 각 부분을 시험이 하나씩 본다.
  - 종료 시각 + 15분 − 1ms에는 401, 15분에는 200: ③-1·③-2·③-6. ③-6은 identity가 실제로 Outbox에 남긴 값을 쓴다.
  - 이유 값이 목록 안의 값마다, 그리고 목록 밖이어도 401: ③-3.
  - 시각을 읽지 못하거나 범위 밖이면 받은 때부터 15분 막고 `time_replaced`를 정확한 수만큼 센다: ③-4·③-7·③-8.
  - 범위의 두 끝 바로 안쪽은 그 종료 시각대로 두고 세지 않는다: ③-7 (다)·③-8 (다).
  - 범위는 받은 때가 아니라 Kafka 시각으로 견준다: ③-9. 실제 Kafka의 레코드 시각으로는 ③-10이 본다.
  - `sessionId`가 없으면 `unreadable`을 1씩 올리고 뒤 사건은 401로 받는다: ③-5.
- I-T3 ④: 맞다.
  - ④-6(통합)은 DELETE 사건 뒤 5초 안에 진입과 입장 확정이 모두 401인지 본다. 두 키의 `PEXPIRETIME`이 정확히 `purgeBy`이고 끝난 세션이 다시 요청해도 늘지 않는지, `q:{wdr}:*` SCAN이 비었는지도 본다.
  - ④-1·④-2는 `withdrawnAt`이 지금, 지금 − 1분, 지금 + 2분, 먼 미래인 경우에 '지금 + 5일로 자른 값'이 정확한지 본다.
  - ④-5는 오프셋을 커밋한 때 이미 만료가 걸렸는지 본다.
- I-T48 ①: 맞다. 사건 뒤 1초 안에 인스턴스를 띄운다. 첫 /ready가 503이고 남은 작업이 `sessions`·`settings`인지, 준비 직후 첫 요청이 401인지 본다. M3·M17을 잡았다.
- I-T48 ②: 맞다. 인스턴스 셋 모두가 401인지 본다. 소비자 그룹을 하나로 합친 M1을 잡았다.
- I-T48 ③: 맞다. 막힌 채 띄우면 정한 시간 전에는 503, 뒤에는 200이다. `control_sync_lagging{kind="sessions"}`가 1이고, 되살린 뒤 막기 전의 사건이 401이 되며, 게이지가 0으로 돌아오는지 본다. 시험의 한도는 정본 30초 대신 4초다. 30초는 D-T29 ①의 상수 단언만 보므로 도우미 경로의 30초는 시험되지 않는다(X7).

### 4. 게이트

바꾼 패키지 여덟의 타입 검사는 통과했다. identity·ticket·core는 사본에 없던 search-normalize·identity dist를 빌드한 뒤 통과했다. 이 묶음의 단위 시험 파일(platform 셋, identity 둘, queue 둘, 서비스 다섯의 wiring)도 통과했다. 통합은 platform control-sync 6/6, queue start-control-sync 2/2, consumers 4/4(다시 돌린 결과)다. 뿌리 `pnpm lint`는 통과했고, 문서 점검은 작업 폴더 `45fca706`에서 오류 0이다. `node tools/ci/trace-check.mjs --ids "I-T3,I-T48"`은 위 보고서 11개로 통과했다(I-T3 39, I-T48 4, 시험 64개). `node tools/ci/ledger.mjs --batch BAT-059 --require`도 통과했다(자동 시험 7). 돌리지 않은 것: 서비스 여덟의 통합 시험 전부(계획 §10대로 합치기 직전 다시 쌓은 트리에서 한다), purchase-svc ②-11, platform 단위 시험 전체.

### 5. 시험 담당에게 넘길 시험

- M18b(R1): 준비 뒤 읽기가 던지며 끊기고 끊긴 동안 사건이 들어오면, 되살린 뒤 그 sid가 401인지 본다. 읽기 포트 대역이 던지는 단위 시험이면 된다(위 2의 임시 시험 꼴). 리뷰 R059-5와 같은 빈틈이다.

### 공개 이름(§5와 다르거나 더한 것)

- **설정 해독기는 계약 Zod를 쓰지 않는다**: `controlEventCodec.setting`은 asyncapi `SettingChanged`의 칸 이름과 모양만 본다. 플랫폼의 `@peaket/contracts`는 개발 의존성이고 플랫폼만 담는 이미지(서비스 틀·realtime-gw 등)가 계약을 빌드하지 않아, 실행 때 싣는 의존으로 바꾸면 그 이미지가 깨진다. 그래서 `key`·`value` 갈래 목록은 보지 않는다(목록 밖 `key`도 던지지 않고 저장한다). 던지는 경우: JSON·객체가 아님, `commandId`·`actor`·`eventKey`가 글이 아님, `key`·`scope`가 빈 글, `value` 없음, `occurredAt`이 오프셋 있는 ISO 시각도 수도 아님, `expiresAt`이 ISO·수·`null`·없음 밖. 정본 ADR-0333 결정 4에 적었다(추천 적용, 2026-11-21, BAT-059 구현).
- `sessionTerminated`: `terminatedAt`의 ISO 글은 오프셋 있는 꼴만 받는다(그 밖의 글은 `NaN`). `accountId`·`reason`이 글이 아니면 빈 글로 돌려준다.
- `startControlSync`: 종료 시각이 유한하지 않거나 `Date` 범위 밖이면 `terminateSession({ sessionId })`(시각 없이)로 넘긴다. `control_sync_skipped_total{service,topic}`은 두 토픽 모두 0으로 미리 낸다.
- 형 이름: `ControlSyncConfig`(설정), `ServiceControlSync`(도우미 반환), `ServiceControlSyncOptions`(시간 옵션). 모두 `@peaket/platform/stream-worker`.
- 빠뜨림 막기: `PlatformService.controlSync: { started: boolean }`가 시작 표시이고 도우미가 켠다. 신원 처리기 목록은 `AuthState.identityHandlers`(`컨트롤러.메서드`)이고 `RolesCheck`가 시작 때 채운다. 신원 역할은 `public` 밖의 모든 역할(스캐너 역할 포함)이다. 메시지는 처리기를 셋까지 대고 나머지는 수만 적는다.
- 도우미의 꺼진 설정 경고는 `{ dep: 'kafka', kind: 'control-sync' }`, 켜진 소비자 그룹은 `<서비스>-<파드>.<토픽>`(기존 `kafkaBroadcastSource`), 클라이언트 ID는 `<서비스>-<PEAKET_ENV>-<파드>`다.

### 구현에서 정한 세부(정본에 넣지 않은 작은 것)

- 시작 파일: queue·purchase·ops·틀은 `@peaket/platform/stream-worker`를 정적으로 가져오고(이미 네이티브 모듈을 싣던 곳), identity·payment·ticket·core는 `createService` 뒤 `await import(…)`로 싣는다. 도우미는 꺼진 설정에서도 부르므로 이 넷도 local·ci에서 네이티브 모듈을 싣는다(core-svc의 '켤 때만 싣는다' 주석은 후기 탈퇴 소비자에만 맞게 고쳤다).
- 닫기: 일곱 모두 서비스 닫기 뒤 연결 닫기 단계에서 `controlSync?.close()`. queue-svc는 `listen`이 실패하면 이미 연 것을 닫고 던지는 정리를 더했다(소비 타이머가 남지 않게). ticket-svc는 시작 실패 정리에도 넣었다.
- 서비스 타입 검사·시험 설정: `@peaket/platform/stream-worker`를 원본으로 잇는 경로를 queue·payment·ticket·identity·core·ops의 `tsconfig.json`에, 별칭을 payment(단위)·ticket·identity·core·ops(단위·통합)의 vitest 설정에 더했다(purchase-svc와 같은 꼴). 까닭: 원본 `PlatformService`와 dist 형이 `#private`로 맞지 않아 타입 검사가 깨지고, 시험에서 `PlatformConfigError` 같은 클래스가 원본·dist 둘로 갈라지지 않게.
