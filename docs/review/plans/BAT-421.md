## 감독에게

정하지 않고 올리는 것과, 이 계획이 정한 것을 알린다. **1이 풀리기 전에는 SCR-038의 취소 POST를 구현하지 않는다. 2~10은 추천안이며, 다르게 정하면 그 값으로 고친다.**

1. **막힘: 예매 취소 POST가 살아 있는 구매 세션 서명을 요구한다.** `services/purchase-svc/src/modules/refund/inbound/ticket-cancellation.controller.ts` 89~95행의 `POST /v1/tickets/{ticketId}/cancellation`에 `@PurchaseSigned()`가 붙어 있다. 그 훅은 `X-Purchase-Seq`·`X-Purchase-Mac`과 **살아 있는 구매 세션**을 요구하고(`packages/platform/src/purchase-auth.ts` 124~146행, 세션은 `StoredPurchaseSessions.resolve`가 입장 토큰·최대 체류로 판정), 없으면 401 `purchase-session-ended`다. 그런데 SCR-038은 SCR-013(마이 티켓)에서 며칠 뒤에 열리고, 팬의 구매 세션은 좌석 구매 여정에서만 산다. 즉 **지금 서버로는 이 화면(며칠 뒤 방문)의 취소가 언제나 401**이다. 반대로 docs/frontend.md §4.1 '구매 세션'은 서명하는 여섯 작업(홀드·해제·연장·주문·결제 시도·결제 접수)만 열거하고, §4.2.4는 예매 취소를 `견적 → 재인증 → POST`로 적는다. 두 정본이 어긋나 있고, 화면 쪽 정본(frontend)이 맞다고 본다.
   - **추천**: 이 한 처리기에서 `@PurchaseSigned()`를 떼고(계약 머리도 그대로), transfer-refund §3.1 '차례'의 '구매 요청 서명' 구절을 '재인증' 앞에서 지운다. 근거: (가) 이미 `X-Reauth-Token`이 5분·한 번·세션·계정·`op`에 묶여 있고, (나) gw-fan이 쿠키 쓰기에서 `Origin`을 보고, (다) 취소는 구매 세션의 일련번호로 지키는 종류의 작업이 아니다. 서버 변경은 한 줄 + 계약 주석 + 정본 한 줄 + 회귀 시험 하나다.
   - **허용하지 않으면**: SCR-038은 견적·계좌·오류 문구·결과 상태까지만 잇고 마지막 POST는 열지 못한다(화면이 늘 401). 그러면 이 묶음은 SCR-044·SCR-047만 끝내고 SCR-038은 계획에서 멈춘다. 대안(앱 서버가 취소용 입장 토큰을 발급)은 새 계약이라 0.9일 밖이다.
2. **0.9일은 어림이 낮다.** 화면 셋 다 지금은 API를 부르지 않는 목업이다(web `_pages/ticket-cancel` 400줄, partner `_pages/cancellation-request` 440줄, console `pages/cancellation` 보드 1,000줄 ×3). 잇는 일은 새 모델·새 live 화면·재인증 흐름·시험이라 [가정] SCR-038 0.55 + SCR-044 0.30 + SCR-047 0.45 + 정본·시험·브라우저·게이트 0.30 = **1.60일**이다. **추천: 1.5일로 늘리거나, SCR-044를 상태 읽기만(요청 폼은 다음 묶음)으로 잘라 1.30일로 한다.** 어느 쪽인지 정해 달라.
3. **계좌를 재인증 왕복 동안 어디에 두는가.** 팬 재인증은 앱 서버 `/reauth/{provider}`로 **같은 창이 떠났다 돌아오는** 흐름이라, 계좌를 먼저 받으면 돌아온 뒤 값이 사라진다. frontend §4.2.4는 "환불 계좌는 저장하지 않고 요청 본문으로만 보낸다"고 못 박는다. 그래서 이 계획은 ① 견적의 `refundAccountRequired`(참·거짓)로 **purpose만 먼저 정하고**, ② 재인증에서 돌아온 뒤 계좌를 한 번 받아 POST 본문에만 싣는 안을 쓴다. 대신 d5 §5.20의 ⑦(계좌 칸) 자리가 ⑤(재인증 버튼) 뒤로 간다. **추천: 이 안.** 대안은 (나) 왕복 동안 `sessionStorage`에 계좌를 두는 것(저장 금지와 부딪힌다), (다) 재인증을 새 창에서 하고 여는 창이 `/reauth/token`을 폴링하는 것(계좌는 메모리에 남지만 새 반환 페이지·팝업 UX가 늘어난다)이다.
4. **202 `REFUND_PENDING`·`refundAccountRequired`의 SCR-060 안내.** SCR-060(`/my/refunds/[refundId]/account`)은 아직 목업이고, 서버에는 취소 한 건을 읽는 `GET /v1/cancellations/{id}`가 없다(계좌를 다시 넣는 `POST`만 있다). 그래서 이 묶음은 (가) 문구 "환급할 때 알림으로 계좌를 다시 받습니다"와 (나) 주문 내역으로 가는 링크까지 두고, SCR-060 링크는 걸지 않는 안을 쓴다. **SCR-060을 실제로 이을 묶음(읽기 API 또는 취소 ID만으로 그리는 화면)을 정해 달라.** 정하지 않으면 팬은 안내만 받고 계좌를 넣을 길이 없다(서버는 BAT-425가 열어 두었다).
5. **관제 admin 재인증 UI가 이 묶음에서 처음 생긴다.** SCR-047의 확정 승인은 `X-Reauth-Token`(act `APPROVAL`·패스키)을 요구하는데(openapi approvals, `event-cancellations.ts` 307~318행), console-host에는 실제 admin 재인증 화면이 아직 없다(보드 목업만 있다). 파트너의 `apps/partner/src/shared/api/reauth.ts`(두 단계: 비밀번호·TOTP → 패스키)를 그대로 옮겨 `apps/console-host/src/features/admin-reauth/`에 공용으로 둔다. **추천: 승인한다.** 다른 관제 화면(승인 업무·계정)도 뒤에 같은 부품을 쓴다.
6. **파트너 '실무자 보기'의 역할을 아는 길이 없다.** partner-api에는 '내 파트너 세션'을 읽는 경로가 없다(로그아웃·갱신·재인증·패스키는 있지만 역할을 돌려주는 읽기가 없다). 화면은 지금 `?role=` 미리보기로만 실무자를 안다. 이 묶음은 (가) 요청 버튼을 그대로 두고, (나) 403 `partner_member`를 받으면 d5 §6.12 문구를 띄우고 그 방문 동안 버튼을 끄는 안을 쓴다. **파트너 세션 읽기 경로를 다음에 만들 묶음을 정해 달라.** 정하지 않으면 첫 방문에 실무자도 버튼이 활성으로 보인다(서버가 403으로 막는다).
7. **`dryRun`이 계약에서 열린 객체다.** openapi `EventCancellationRequest.dryRun`은 `{ type: object }`라 생성 형이 `{ [key: string]: unknown }`이고, ops-svc는 `targetOrders`·`refundTotal`·`compensationTargets`·`compensationTotal`·`perPg[{pg,orders,estimatedSeconds}]`를 싣는다(`services/ops-svc/src/modules/event-cancellations/inbound/views.ts` 12~18행). **추천: 계약을 고치지 않고 화면 모델에 런타임 해석기(모르는 키·모양 틀린 값은 버림)를 둔다.** 계약을 닫힌 형으로 바꾸려면 openapi·생성물·ops 계약 시험이 함께 움직인다.
8. **장부 2항목과 ASVS 3.5.3의 코드 영역.** 지금 `node tools/ci/ledger.mjs --batch BAT-421`은 "자동 시험 2, B 2"다. 두 항목은 transfer-refund ASVS 행인데, 근거가 된 태그는 **다른 기능의 시험**(partner 좌석맵 편집기·core 좌석맵 템플릿)에서 왔다. 3.2.2 행은 `web`·`partner`·`console`을 구현 위치로 적어 앱 영역을 보지만, 3.5.3 행은 코드 경로가 없어 기본 영역(services 다섯)만 본다. **추천: 구현 커밋에서 3.5.3 행의 구현 위치에 세 앱 경로를 더하고(기존 서비스 경로도 남김), 새 화면 시험에 두 태그를 단다.** 이렇게 해야 장부 근거가 이 화면을 가리킨다.
9. **같은 주문의 좌석 여럿을 고르는 길이 계약에 없다.** `Ticket`에 `orderId`가 없고 `listTickets`에 주문 필터가 없다(`docs/api/openapi.yaml` 4431~4440행, `Ticket` 644행). `bookingNumber`로 묶으려면 지갑 목록 전체를 받아 같은 값을 골라야 한다. **추천: 이 묶음은 URL의 티켓 한 장만 취소하고, 좌석 목록도 그 한 장만 보여 준다.** d5 §5.20 ①의 체크박스 둘은 지갑·주문 읽기 계약이 생기는 다음 묶음으로 미룬다. 그러면 S6(좌석마다 재인증)도 한 번으로 줄어 §2의 어림에 가까워진다.
10. **카드 끝 4자리를 그릴 계약이 없다.** d5 §5.20 ③은 "결제한 카드(끝 1234)로"를 보이지만 `Ticket`·`CancellationQuote`·`Cancellation` 어디에도 결제 수단·끝 4자리가 없다. **추천: 이 묶음은 "원결제 수단으로 환급합니다"로만 쓰고 끝 4자리는 그리지 않는다.** 꼭 필요하면 payment-svc 읽기 칸을 계약에 더하는 서버 묶음이 먼저다.

## 계획

### 1. 범위

**하는 것**

1. **SCR-038 예매 취소 잇기(web)**: URL의 티켓 상세·견적을 실제 API로 읽고, `refundAccountRequired`가 참일 때만 계좌를 받고, 견적으로 재인증 `purpose`를 정하고, 재인증 왕복 뒤 취소 POST를 보내고, 202의 세 상태(`REFUNDED`·`REQUESTED`·`REFUND_PENDING`)와 403·503·422·409를 d5 문구로 가른다. 결과 카드는 `refundAccountRequired`가 참이면 SCR-060 안내 문구를 보인다.
2. **SCR-044 파트너 회차 취소·연기 요청과 상태(partner)**: 실제 공연·회차를 읽어 회차를 고르고, `kind`·`newStartsAt`(KST→ISO)·`reason`·`evidenceRef`·`faultOpinion`을 서버 규칙대로 보내고, `GET` 상태를 판정 대기 → 판정 → 확정 대기 → 진행률 → 일시정지 → 완료/반려로 그린다. 실무자 403을 d5 문구로 바꾼다.
3. **SCR-047 관제 판정·미리보기·2인 확정·진행률(console)**: 요청 상세를 읽어 파트너 요청·판정·미리보기를 그리고, commander가 판정(귀책·사유·팬 통지 사유)을 저장하고, 판정자가 아닌 operator/commander가 admin 재인증(비밀번호·TOTP·패스키) 뒤 확정한다. 진행률에 `done`·`failed`·`accountPending`·결제사별 몫을 그린다.
4. **관제 admin 재인증 부품**: `POST /v1/ops/auth/reauthentications` 두 단계(비밀번호·TOTP → 패스키)를 부르는 공용 부품. 파트너 구현(`apps/partner/src/shared/api/reauth.ts`)을 옮긴다.
5. **공용 은행 목록**: 토스 두 자리 코드 26개와 한국어 이름을 `packages/validation`에서 내보내 화면과 서버 검사가 같은 표를 쓰게 한다(지금은 서버 검사 안에만 있다).
6. **정본**: docs/frontend.md §4.3에 503 `reauth-unavailable` 줄, d5 §9.2에 취소 422·503 문구 두 줄, (감독에게 1을 승인하면) transfer-refund §3.1 '차례' 한 줄, d5 §5.20 계좌 칸 자리(감독에게 3), ASVS 3.5.3 구현 위치(감독에게 8).
7. **브라우저 확인 대본**: `docs/review/browser-check/` 아래 `GAT-090-GAT-110.md`(d5 §5.20·§6.12·§7.8과 R-T36·R-T37·R-T39로 만든다).

**뺀 것과 까닭**

- **SCR-038 연기 환급 모드(`?mode=postponed`)**: 팬 신청 HTTP 계약이 정본에 없다(transfer-refund §5 '연기', BAT-420.md §1의 'SCR-038 … 연기 모드의 팬 신청 HTTP는 GAT-120'). 목업만 남긴다.
- **SCR-038 다중 좌석**: 이 묶음은 URL의 티켓 한 장만 취소한다. 계약에 `Ticket.orderId`가 없고 `listTickets`에 주문 필터가 없어 같은 주문의 좌석을 확실히 모을 수 없다(감독에게 9). 계좌도 재인증 왕복을 넘겨 저장하지 않는다(감독에게 3).
- **SCR-047 일괄 환불 일시정지·재개**: d5 §7.8 ⑤의 두 버튼이지만, 재개 조건 줄이 요구하는 '최근 5분 실패율·서킷 상태'를 읽는 계약이 없다(transfer-refund §5 '재개'). 지금 상태를 보여 주고 버튼은 이유 글과 함께 비활성으로 둔다. 서버 경로(pauses·resumptions)는 이미 있다.
- **SCR-047 통지 문안 전문 미리보기(d5 §9.3 네 문안)**: 확정 알림은 서버 Outbox가 보낸다. 화면은 `fanNoticeReason`(≤200자)과 고정 안내 한 줄만 보인다. 전문 복제는 알림 단계와 함께.
- **SCR-060 실제 잇기**: 감독에게 4.
- **SCR-045(CS 처리함)에서 SCR-047로 들어오는 링크**: SCR-045는 목업이다. SCR-047은 요청 ID로 열리고, 없으면 요청 목록에서 고르는 자리를 둔다.

**코드로 확인한 사실(계획 시점)**

- `packages/api-client/src/gen/endpoints/tickets/tickets.ts`에 `getTicketCancellationQuote`(1179행)·`createTicketCancellation`(1317행)이 있고, `CancellationQuote.refundAccountRequired`·`Cancellation.refundAccountRequired`가 생성 형에 있다(`gen/model/cancellationQuote.ts` 35행, `cancellation.ts` 19행).
- 취소 202의 `status`는 서버가 `REFUNDED`·`REQUESTED`·`REFUND_PENDING` 셋으로 답한다(`ticket-cancellation.controller.ts` 129~134행). `REFUND_PENDING`에만 `refundAccountRequired`가 붙고, 계좌 거절도 422가 아니라 이 202다(같은 파일 132~134행).
- 403 `reauth-required`·503 `reauth-unavailable`(`Retry-After: 5`)·422 `refund-account-required`·400 `invalid-body`(계좌 모양)가 서버에 있다(같은 파일 50~62행). 409는 `transfer-pending`·`entry-started`·`event-cancelled`·`cancellation-conflict` 넷이다(같은 파일 50~59행, 138~141행).
- 재인증 `purpose` 두 값은 웹 앱 서버 표에 이미 있다(`apps/web/src/features/social-login/server/identity-client.ts` 79~95행: `ticket-cancel`→`TICKET_CANCEL`, `ticket-cancel-refund-account`→`TICKET_CANCEL_REFUND_ACCOUNT`).
- 재인증 토큰은 한 번 쓰고, api-client는 `Retry-After`가 붙은 503을 같은 머리(같은 토큰)로 자동 재시도한다(`packages/api-client/src/client.ts` 265~278행). 그래서 503 뒤에는 새 재인증이 필요할 수 있다.
- 예매 취소 POST에 `@PurchaseSigned()`가 붙어 있다(`ticket-cancellation.controller.ts` 94행). 이 훅은 머리가 없으면 401 `purchase-signature-invalid`, 세션이 없으면 401 `purchase-session-ended`다(`packages/platform/src/purchase-auth.ts` 97~103·127~132행). 감독에게 1.
- 파트너 POST `createPartnerEventCancellation`은 202에 ops의 `View`(생성 시 `dryRun`·`judgedBy` 없음)를, GET은 `PartnerEventCancellationStatus`를 준다(`services/ops-svc/src/modules/event-cancellations/inbound/partner-event-cancellation.controller.ts` 32~61행). 상태에는 `dryRun`·결제사별 몫·판정자·내부 사유가 없다(openapi 3499~3539행). `judgementDueAt`은 GAT-280 전까지 null이다(openapi 3513행).

- `progress.done`은 `REFUNDED`만 센다. `accountPending`은 따로 세고 `ACCOUNT_PENDING`도 끝난 항목으로 완료 판정에 든다(`services/purchase-svc/src/modules/refund/domain/event-refund.ts` 247~284행). 그래서 화면 퍼센트를 `(done+failed+accountPending)/total`로 계산하면 안 된다.

### 2. 장부 범위(2항목)

```text
transfer-refund:v5.0.0-3.2.2, transfer-refund:v5.0.0-3.5.3
```

- **계획 시점의 장부**: `node tools/ci/ledger.mjs --batch BAT-421` = 항목 2, 상태 **자동 시험 2**(B 2). `--require`는 지금도 통과한다. 그러나 근거 파일은 이 묶음의 화면이 아니라 다른 기능의 시험이다(3.2.2는 `apps/partner/src/_pages/seatmap-editor/model/import-check.test.mjs`, 3.5.3은 `services/core-svc/test/seatmap-templates.http.test.ts`). 이 계획은 범위를 늘리지 않고, 새 화면 시험에 두 태그를 달아 근거를 이 화면으로 넓힌다.
- **v5.0.0-3.2.2**(글로 보일 내용은 안전한 렌더링): 세 화면이 서버·사용자가 쓴 글(공연명·사유·증명 참조·반려 사유·판정 사유·팬 통지 사유·오류 `title`/`detail`)을 React 텍스트 노드로만 그린다. `dangerouslySetInnerHTML`·`innerHTML`을 쓰지 않고, 모르는 칸·모양 틀린 값은 화면 값으로 옮기지 않는다. 계좌번호는 입력 칸 밖(URL·로그·저장소)으로 내지 않는다.
- **v5.0.0-3.5.3**(민감 기능은 POST 등 비안전 메서드): 취소·회차 취소 요청·판정·확정·재인증은 POST만 쓴다. GET(견적·티켓·파트너 상태·관제 상세·목록)은 읽기 전용이고 화면은 GET으로 상태를 바꾸지 않는다. 이 묶음은 화면 쪽 증거를 더하고, 장부가 그 증거를 세도록 3.5.3 행의 구현 위치에 세 앱 경로를 더하는 안을 올린다(감독에게 8).
- **범위 밖**: R-T36·R-T37·R-T39·P-T72는 서버 판정 항목이라 BAT-420·BAT-415의 장부에 남는다. 이 묶음은 그 화면 쪽만 본다. 새 시험 ID는 만들지 않는다.

### 7. 실패 확인

- **어디서**: 시험 담당이 구현 뒤에 시험을 쓰고, 구현 전 트리(이 계획 커밋)에서 돌린다. 통합·Docker는 필요 없다(화면 묶음). 화면에서 실제 서버까지는 브라우저 확인(감독이 시드·API를 띄운다)으로 본다.
- **무엇이 실패해야 하나**: 새 모델 모듈을 import하는 시험은 구현 전 트리에서 **모듈이 없어 실행조차 안 된다**(§8.6 7의 '실행조차 안 되는 실패는 세지 않는다'). 그래서 ① 소스 배선 시험(목업 `TicketCancelPage`·`CancellationRequestPage`·`cancellation/Page.tsx`에 API 호출이 없음)은 구현 전 트리에서 **단언 실패**로 남고, ② 새 모듈 시험은 아래 §8의 틀린 구현으로 한 번씩 실패를 본다. ③ 이미 있는 동작(예: 카드 결제에 계좌 칸이 안 보임)은 목업에서도 통과할 수 있으므로 틀린 구현으로 본다.
- **명령(예)**: `cd apps/web && node --test "src/_pages/ticket-cancel/**/*.test.mjs"`, `cd apps/partner && node --test "src/_pages/cancellation-request/**/*.test.mjs"`, `cd apps/console-host && node --test "src/pages/cancellation/**/*.test.mjs" "src/features/admin-reauth/**/*.test.mjs"`, `cd packages/validation && node --test "test/**/*.test.ts"`(또는 패키지 시험 명령).
- **계획 파일에 적을 것**: 돌린 명령, 실패한 시험 수, 실행조차 안 된 시험 수와 까닭, 처음부터 통과한 시험과 그 실패를 본 틀린 구현 번호.

## 감독 결정(2026-11-20)

1. **취소 POST의 `@PurchaseSigned`를 이 처리기에서만 뗀다.** `POST /v1/tickets/{ticketId}/cancellation`은 살아 있는 구매 세션 서명 대신 **재인증 토큰·Origin 검사**로 지킨다. 다른 다섯 서명 작업은 그대로 두고, ADR **0328**에 이유·되돌릴 조건을 적는다.
2. **1.6일**로 한다. SCR-044를 상태 읽기만으로 자르지 않고 세 화면을 실제로 잇는다.
3. **계좌는 재인증 왕복 뒤에 받는다.** `purpose`는 견적의 `refundAccountRequired`로 먼저 정하고(`ticket-cancel`/`ticket-cancel-refund-account`), 재인증은 한 번만 한다. d5 §5.20 ⑦ 자리를 ⑤ 뒤로 옮긴다.
4. **SCR-060은 안내 문구만** 둔다. 취소 한 건 GET이 없어 실제 연결은 다음 화면 묶음(**BAT-422 후보**)으로 미룬다.
5. **관제 admin 재인증 UI는 공용 부품**으로 만든다(파트너 `reauth.ts` 이식).
6. **파트너 '실무자 보기' 역할 API가 없으므로** 403 뒤 문구·버튼 끔으로 처리한다.
7. **`dryRun`은 화면 디코더**로 다룬다(계약 유지).
8. **ASVS 3.5.3 구현 위치에 세 앱 경로**를 더한다.
9. **이 묶음은 URL의 티켓 한 장만 취소**한다(같은 주문 여러 좌석을 모을 `Ticket.orderId` 계약이 없다).
10. **카드 끝 4자리는 그리지 않고 '원결제 수단'**으로만 표기한다.
11. 장부는 `transfer-refund:v5.0.0-3.2.2`·`transfer-refund:v5.0.0-3.5.3` 두 항목 그대로다.

### 판정 기준과 단언의 대조

- **정본 예를 그대로 쓴다**: 진행률 `737/1,152`→63, `accountPending` 2·12, 202 세 상태, KST `2026-10-31T18:00`→`2026-10-31T09:00:00.000Z`, 사유 1,000/1,001자·증빙 200/201자, `total=0`. 시험이 구현 상수에서 값을 가져오지 않는다(은행 26개만 공용 표를 센다).
- **문구**: 취소 403·422·503·409 문구가 d5 §9.2 4234·4235·4237행과 같고, 파트너 아홉 이름·관제 아홉 이름이 d5 §6.12·§7.8과 같다. 다만 d5와 시험 문자열을 자동으로 맞추는 검사는 없다.
- **경계·세 상태**: `REFUND_PENDING`+참/거짓/모름, 모르는 상태·모양 틀린 값, `total=0`, `accountPending` 없음(옛 응답 0) vs 모양 틀림(null), 미리보기 모양 틀림(null) vs 없음. 시험이 있다.
- **부르는 쪽**: `resultViewOf`→결과 카드, `errorOf`→오류 배너, `previewOf`→③, `percentOf`→진행 막대까지 소스로 이어지는 것을 배선 시험이 본다. 다만 `errorOf`의 503 분기가 화면 상태를 실제로 바꾸는지는 M4처럼 약하다.

### 남은 위험

1. **M4 시험 구멍(가장 중요)**: 503 `reauth-unavailable` 뒤 새 재인증을 받는 규칙이 시험으로 고정되지 않았다. 제품은 지금 맞지만 다음 수정이 깨도 1,026개가 통과한다. 머지 전에 시험 한 줄(토큰 폐기·확인 화면 소멸)을 더하는 편이 좋다.
2. **G3 traceId**: 5xx에서 문의용 `traceId`를 그리는 코드·시험이 없다. `ApiError.traceId`는 있으므로 화면 문구 한 줄과 시험을 더할 수 있다.
3. **web 첫 JS 213.3KB > 200KB**: 위 표. 이 묶음의 새 화면 때문인지 출발점부터 그랬는지는 재지 않았다. wbs 7.5.2에서 기준선을 잡고 줄인다.
4. **부분으로 남긴 판정 기준 9개**: S1(③ 스켈레톤), S2([다시]), S9(403 뒤 키 유지), S11(422 뒤 재인증 차례), S12(재인증 시작 안 함), P1(`events[]` 선택), P5(`judgementSummary` 표시), C7(실제 세션 역할), G3(5xx traceId)는 동작은 있으나 단언이 약하거나 없다. 다음 정리에서 시험을 더한다.
5. **실제 세션·브라우저 미확인**: 카드·가상계좌 티켓 두 장의 계좌 칸 차이, `/reauth/{provider}`의 `purpose`, 재인증 토큰 없이 POST가 나가지 않는지, 실제 202 세 상태·`accountPending`, 실무자·판정자 본인 403은 시드가 있는 스택에서 봐야 한다.
6. **관제 역할**: 실제 viewer·CS 세션 역할을 읽는 계약이 없어 `?role=` 미리보기에서만 읽기 화면이 확인된다(RV-10, 대본 '이 묶음의 한계').

**검증 결과: 게이트는 모두 통과했고 제품 변경은 0이다. 다만 M4가 시험에 잡히지 않아 503 뒤 새 재인증 규칙은 아직 시험으로 증명되지 않았다. 머지 전 시험 보강을 권하고, 브라우저 확인은 시드가 있는 스택에서 이어받는다.**
