# BAT-182 계획(HOT-357 실시간 구역 구독·좌석 델타 화면 잇기 + S-T13·S-T21·S-T31 ⑥ 판정)

- **무엇**: HOT-357(wbs 2.10.2 ⑰, docs/BUILD_ORDER.md:366)의 남은 몫을 화면에 잇는다. 첫 그림 뒤 좌석맵 Worker가 좌석 델타 WebSocket을 열고, 화면에 보이는 구역만 1초 머문 뒤 구독하며, 델타를 `SeatMapEngine.applyDelta`로 반영한다. 세대·일련번호 갭은 그 구역 스냅샷으로, 다시 붙을 때는 구독 구역 스냅샷으로 맞춘다. 닫힘 코드별 다시 붙기·`TimeSync`·`BatchInterval`(Degraded)을 연결 상태 기계(XState)와 화면 배너에 잇는다. 함께 S-T13(버전 갭 회복)·S-T21(확대와 구역 구독)·S-T31 ⑥(정상 화면 시나리오)을 판정한다.
- **쉬운 말**: 지금 좌석 화면은 처음 받은 좌석 상태만 보여 준다. 이 묶음은 화면을 '살아 있는 지도'로 만든다. 내가 보고 있는 구역만 서버가 알려 주고, 메시지가 중간에 빠지면 그 구역만 다시 받아 맞춘다. 연결이 끊기면 스스로 다시 붙고, 서버가 느려지면 화면 위에 '실시간 반영이 느려졌습니다' 배너를 띄운다.
- **바탕**: 작업 폴더 `D:/ticketpass-lane2`, 가지 `feature/lane2-BAT-182`, 출발 `develop` `2943d73c7`(2026-11-20). 계획 담당 `ses_pending_plan_bat182`(deepseek-v4.1-flash), 2026-11-20. 제품·시험 코드는 쓰지 않았고 Docker·브라우저·측정도 돌리지 않았다. 읽은 것: `docs/BUILD_ORDER.md` 52·56·104·366·404행, `docs/lanes/lane2.md` 8~10행, `docs/lanes/lane4.md` BAT-052 행, `docs/review/plans/BAT-040.md` §1·§2·§10, `docs/review/plans/BAT-052.md` 7·17·47~48행, `docs/frontend.md` §3.5(490~497행)·§4.4.1(775~809행)·§4.7(952행부터)·§5.2(1077~1103행)·§5.10(1289~1296행)·§5.17 FE-T11(1621행), `docs/features/seat-hold.md` §7(399~460행)·§12 S-T13·S-T21·S-T31(578·586·596행), `docs/design/d5-screen-blueprint.md` §5.10(1213~1284행), `docs/verification.md` §4.1·§5.2, `docs/security/asvs/frontend.md` 4.4.1~4.4.4행, `docs/review/ledger-notes.md` 74·77·79행, `docs/architecture.md` §8.6, 코드 `packages/seatmap/src/{protocol,worker,connection,delta-sync,engine,client,wire}.ts`, `apps/web/src/_pages/seats/{ui/SeatsLive.tsx,model/connection-machine.ts,model/live.ts,model/view.ts}`, `services/realtime-gw/src/{config,start}.ts`, `apps/web/scripts/mock-api*`, `tools/web-checks/seatmap/{setup,layout,seatmap.spec}.mjs`, `tools/web-checks/budgets/pages.mjs`, `.github/workflows/ci-web.yml`.
- **등급·차례**: BUILD_ORDER 104행의 B, 0.75일 [가정]. 장부 범위는 아래 5의 네 항목이다. 그 가운데 S-T13·S-T21·S-T31 ⑥은 **A등급**이라, 묶음 등급이 B여도 §8.6 3의 A 증명(항목마다 틀린 구현, 복구 경로 장애 주입, 판정 기준과 시험 단언의 대조)을 적용한다. 정방향(`Batch-Order: impl-first`, ADR-0281 결정 5)이고 B 짧은 고리다(ADR-0283 결정 2): 계획 → 구현(정본 빈칸 포함) → 시험(구현 전 트리 실패 확인·장부 notes 지움) → 리뷰 → 검증(틀린 구현) → 기록.
- **한 줄 결론**: 선행 HOT-090은 develop에 들어와(BAT-052, R-690) 막히지 않는다. 남은 일은 `packages/seatmap`의 연결·갭 복구 부품을 Worker와 화면에 잇는 것이다. S-T13은 클라이언트 경계에서 델타 프레임을 떨어뜨리는 시뮬레이션 3,000번으로, S-T21·S-T31 ⑥은 5만 석 화면 시나리오 한 번으로 판정한다. 셋 다 A등급이라 0.75일은 빠듯해 1.25일 [가정]을 제안한다.

## 3. 감독에게

1. **A등급 셋을 B 묶음에 넣은 일정**: S-T13·S-T21·S-T31 ⑥은 장부 등급 A다. §8.6 3대로 항목마다 틀린 구현과 복구 경로 장애 주입, 판정 기준 대조를 붙이면 0.75일로는 빠듯하다. **1.25일 [가정]을 제안한다.** 0.75일을 고정하면 ① 실 서비스 smoke를 빼고 ② Chromium 한 엔진만 돌리고 ③ S-T21의 Long Task·p99 표본을 100번에서 30번으로 줄인다. 셋 다 '판정'의 뜻은 유지하지만 근거가 약해진다.
2. **S-T13 판정 방법**: 정본은 '네트워크 패킷 드롭을 주입'이라고 적었지만(`docs/features/seat-hold.md:578`), 판정 대상은 화면의 자가 치유 비율이다. **클라이언트 경계에서 델타 프레임을 떨어뜨리는 시뮬레이션 3,000번**(가짜 시계, 실제 `createSeatConnection`+`createDeltaSync`+`SeatMapEngine`)을 추천한다. 실제 `tc netem` 망 드롭은 측정 창(HOT-460)이나 별도 묶음으로 미룬다. 이 해석이 정본과 다르면 시험을 쓰기 전에 알려 달라.
3. **S-T21·S-T31 ⑥의 서버**: 5만 석 화면 시나리오의 서버로 ① **같은 바이트·상한·닫힘 코드를 지키는 realtime-gw 대역**(Node, Docker 없음)과 ② **실제 realtime-gw + Valkey + JWKS**(Docker 차례 잠금, 0.5일 안팎 추가) 가운데 하나를 골라야 한다. 추천은 ①이다. 서버 자체의 동작은 BAT-052의 S-T31 ①~⑤·S-T42가 이미 실제 Valkey로 봤고, 이 묶음은 화면 쪽 구독·반영·닫힘 0을 본다. §8.6 4('가짜 API로 끝내지 않는다')를 엄격히 적용하려면 ②가 필요하다.
4. **CI 잡 추가**: 새 화면 시나리오를 `ci-web.yml`의 새 `seats` 잡으로 돌릴지, 이 묶음에서는 로컬에서만 돌리고 잡은 다음 묶음으로 뺄지 정해 달라. 새 잡은 운영 빌드 + 브라우저 + 5만 석 파일이라 10분 안팎이 더 든다. 이 묶음은 로컬 실행 결과를 측정 보고서에 남기는 안을 추천한다.
5. **장부 범위 축소 승인**: BAT-040이 넘긴 132항목 가운데 `docs/security/asvs/frontend.md` 128항목은 이 화면 잇기와 닿지 않는다(4.4.x는 이미 다른 시험이 보고, 나머지는 다른 갈래 화면이다). **네 항목(FE-T11·S-T13·S-T21·S-T31 ⑥)으로 좁히는 것을 승인해 달라.** 좁히지 않으면 `--require`가 이 묶음에서 통과할 수 없다.
6. **4401의 두 까닭**: `token-expired`는 '예매 시간이 끝났습니다'(`ended`), `token-invalid`·`forbidden`은 '세션 무효'(`invalid`)로 보내는 안을 추천한다. 둘 다 입장 저장값을 지우고 2.5초 뒤 대기실로 옮긴다. d5 §5.10은 4401을 한 줄로만 적어 빈칸이다.
7. **전체 보기 5초 갱신의 요청 모양**: 구역마다 스냅샷을 부르면 5,000화면에서 요청이 폭발한다. **전체 보기(좌석 단계 아님)에서는 전체 스냅샷을 5초에 한 번** 받는 안을 추천한다(6.25KB×5,000/5초 ≈ 6.25MB/s, 초당 1,000요청 [가정]). 16개를 넘는 좌석 단계 구역은 가운데 가까운 16개만 구독하고 나머지는 5초에 하나씩 돌아가며 구역 스냅샷을 받는다.
8. **FE-T11의 장부 상태**: FE-T11은 이미 자동 시험이다(연결·갭·재시도·상태 기계). 이 묶음은 '화면에 잇는 부분'의 시험을 더할 뿐이라 장부 상태를 바꾸지 않는다. 이 해석으로 진행해도 되는지 확인해 달라.

## 4. 범위

### 4.1 하는 것

1. **Worker 스트림 배선**: 첫 그림(`ready`) 뒤 화면이 `stream{url, expiresAtMs}`을 보내면 Worker가 `createSeatConnection`을 만든다. 입장 토큰은 `init`의 `admission.token`을 쓰고, 하위 프로토콜은 `peaket.seats.v1`·`peaket.auth.{토큰}`이다. 쿠키는 쓰지 않는다.
2. **보이는 구역만 구독**: `SeatMapEngine`에 `visibleSections()`를 더해 화면 폭 1/3 [가정] 이상으로 보이는 구역을 찾는다. 전체 보기에서는 0개다. 새로 보인 구역이 1,000ms 이어지면 구독 집합에 넣고, 화면 밖으로 나가면 뺀다. 구독 집합이 바뀌면 **전체 집합**을 보내고, 바꾸기는 1,000ms에 많아야 한 번이다(서버 상한 초당 2번보다 보수적). 16개를 넘으면 화면 가운데에 가까운 16개만 보낸다.
3. **델타 반영**: 받은 `SeatDeltaBatch`를 `createDeltaSync`를 거쳐 `SeatMapEngine.applyDelta`로 반영한다. 바뀐 구역의 비트맵만 버리고 다시 그린다. 접근성 목록이 그 구역을 열고 있으면 `stateChanged{section, version, offsets, states}`를 보낸다.
4. **갭·세대·재연결 복구**: 일련번호가 건너뛰면 그 구역 스냅샷을 다시 받는다. 같은 구역 요청은 한 번에 하나만 보내고, 기다리는 동안 온 델타는 쌓아 두었다가 스냅샷 뒤에 다시 얹는다. 세대가 오르면 구독 구역 전체를 0~1초 무작위로 늦춰 다시 받는다. 다시 붙으면 `SubscribeSections`를 먼저 보내고 구독 구역 스냅샷을 받는다.
5. **연결 상태·Degraded·끝**: Worker가 `connection{state, degraded?, reason?}`을 보내고 화면은 `connectionEvent`로 XState 기계에 넣는다. `BatchInterval` 1,000ms면 '실시간 반영이 느려졌습니다' 배너, `reconnecting`이면 '실시간 연결 복구 중' 배너, `ended`면 까닭별 화면(§12-1)이다. 35초 무프레임이면 다시 붙고, 1012·1013·1009·그 밖의 비정상 종료는 지터 백오프로, 4429는 10초 넘게 기다린 뒤 다시 붙는다. 4401은 다시 붙지 않는다.
6. **전체 보기 5초 갱신**: 좌석 단계가 아니면 5,000ms마다 전체 스냅샷을 한 번 받아 구역 상태를 갱신한다. 숨긴 탭에서는 멈추고, 다시 보이면 바로 한 번 받는다. 16개를 넘는 좌석 단계 구역은 5초에 하나씩 구역 스냅샷을 돌아가며 받는다(같은 구역 한 번에 하나).
7. **화면**: `SeatsLive`가 `ready`에서 `stream`을 보내고, `connection`·`sections`·`metrics` 메시지를 받아 배너·상태·측정값을 처리한다. 판매 일시정지·판매 종료 배너와 겹치면 위쪽에 하나씩 쌓는다.
8. **판정**: S-T13 시뮬레이션 3,000번, S-T21·S-T31 ⑥ 5만 석 화면 시나리오 1회, FE-T11 화면 잇기 시험. 결과는 `docs/review/measurements/` 아래 새 `BAT-182-wave.md`에 남긴다.
9. **개발·확인 도구**: `apps/web/scripts/mock-api`에 좌석 스트림 대역(WS 업그레이드)을 더해 개발 서버·브라우저 확인에서도 배너·구독을 눌러 볼 수 있게 한다. `tools/web-checks/seats/`에 5만 석 시나리오 서버·Playwright 설정을 둔다.

### 4.2 빼는 것

- **HOT-415·BAT-066**: 게이트웨이가 핸드셰이크에서 토큰을 확인하는지, `/v1/events/*/seats/stream` HTTPRoute를 두는 일. 화면은 realtime-gw에 직접 붙는 로컬 무대만 본다.
- **S-T31 ①~⑤·S-T42·S-T12·S-T14**: realtime-gw 서버 시험과 측정 창 몫이다. 이 묶음은 S-T31 ⑥만 본다.
- **실제 `tc netem` 망 드롭**: S-T13은 클라이언트 경계 시뮬레이션으로 본다(§3-2).
- **3엔진·실기기**: S-T21·S-T31 ⑥은 Chromium 한 엔진, 이 PC에서 돈다. WebKit·Firefox·iOS 실기기는 별도 몫이다.
- **전체 E2E**: 대기실 → 좌석 → 결제 → 결과를 처음부터 끝까지 도는 시험(wbs 4.5.4·7.2.6)은 이 묶음이 아니다.
- **ASVS frontend 128항목**: 다른 갈래·서비스 몫이다(§2).
- **좌석맵 렌더링·성능**: 5만 석 첫 그림·INP·힙은 BAS-190·S-T15·FE-T10 몫이다. 이 묶음은 그리기 코드를 바꾸지 않는다.
- **계약·서버**: `docs/api/asyncapi.yaml`·`docs/api/openapi.yaml`·realtime-gw·purchase-svc·queue-svc를 바꾸지 않는다.
- **새 저장소·새 의존·새 ADR**: 없다. 방향을 바꾸는 결정이 나오면 멈추고 감독에게 묻는다.

## 9. 실패 확인

구현 전 실패 확인 방법: 계획 시점에는 아직 시험이 없다. 시험 담당이 정방향(`impl-first`)대로 구현 뒤에 시험을 쓰고, **기준 커밋 `2943d73c7` 트리**에서 새 시험을 돌려 실패를 본 뒤 이 절에 명령·실패 수·까닭을 적는다.

1. **Worker·화면 시험(T1~T6·T8·T12)**: 기준 트리에는 `stream` 메시지·`visibleSections`·`connection` 메시지가 없다. 시험 파일은 기존 `createHandler`·`connection-machine`을 불러 실행되므로 **단언 실패**로 끝난다(모듈이 없어 실행조차 안 되는 실패는 세지 않는다). `apps/web/scripts/mock-api` 대역도 없어 T12는 404/무응답 단언으로 실패한다.
2. **S-T21·S-T31 ⑥(T9~T11)**: 기준 트리 앱은 `stream`을 보내지 않아 서버 기록의 구독 집합이 비고, `connection` 배너가 없다. 브라우저 시험은 **단언 실패**로 끝난다. 시험용 서버·5만 석 파일은 시험 파일 쪽에 있으므로 기준 트리에서도 실행된다.
3. **S-T13(T7)**: `createSeatConnection`·`createDeltaSync`는 기준 트리에 이미 있어 **처음부터 통과할 수 있다**. 그 사실을 적고, §10의 M1~M3으로 실패를 본다(§8.6 7의 '이미 있는 동작').
4. **장부**: 시험 커밋에서 `docs/review/ledger-notes.md:74·77·79`를 지운 뒤 `node tools/ci/ledger.mjs --batch BAT-182 --require`가 통과해야 한다. 계획 커밋에서는 '다른 단계' 3개라 실패가 정상이다.
5. **A등급 증명**: T7·T9~T11은 구현 전 실패만으로 끝내지 않는다. 검증 담당이 §10의 틀린 구현을 하나씩 넣어 각 항목의 단언이 잡는지 본다. S-T13은 3,000번 중 실패 수를, S-T21은 p99·Long Task·구독 집합을, S-T31 ⑥은 최대 구독·닫힘 코드를 표로 남긴다.
6. **적는 곳**: 시험 담당이 '실패 확인' 절에, 검증 담당이 '검증' 절에 적는다. 이 계획 커밋은 아직 결과를 모른다.
