## 1. 배경과 경계

- HOT-250(BAT-157, develop `3027a3e5`)이 판매 정책 규칙·판매 자격 명단·사본 포트를 만들고, queue-svc 로비·진입 대조와 입장 토큰 `lst`를 갈래 3 몫으로 나눴다(docs/review/plans/BAT-157.md §8.2 ①).
- 사본은 core-svc가 대기열 Redis에 직접 쓴다(소유자 결정 2026-11-10, OPEN[33] (가), ADR-0261 결정 9). 그 어댑터는 HOT-251(갈래 2)이다. **이 묶음은 읽기만 하고, 시험이 사본 키를 직접 넣는다.**
- 화면 몫(Q-T36 ⑧: 403 `sale-eligibility-required`를 공연 상세의 예매 제한 안내로 돌리기)은 HOT-346(갈래 3)이다. 이 묶음은 정본(docs/frontend.md §3.4)만 맞추고 화면 코드·브라우저 확인은 하지 않는다.
- 성능 비교(ADR-0265 결정 10)는 갈래 1 몫이라 하지 않는다. 지시서 '하지 말 것'에 따라 kind·성능 측정도 하지 않는다. Lua 모양은 측정 도구가 읽는 `entry-lua.ts`에 두되, 옛·새 비교는 감독이 갈래 1과 맞춘다.

## 2. 차례

1. **정본 빈칸 먼저**: ADR-0265와 정본 여섯 곳(위 '이 계획과 함께 정본에 쓴 것')을 구현 전에 확정한다. 구현 중 새 세부가 나오면 코드보다 ADR-0265를 먼저 고친다.
2. **불변식·버그 재현 시험 먼저**(A): `test/eligibility-cases.ts`에 Q-T36 ① 창 경계·닫힌 쪽·번호 발급 0·묶음 섞임, Q-T36 ② `lst` 값, ASVS 2.3.2·15.4.2·16.5.2 사례를 쓴다. 메모리 저장소에서 먼저 실패를 보고 구현한다.
3. **정본 해석·순수 함수**: `parseSchedule`의 `eligGates`·`eligLists` 모양 검사와 `eligibilityAt`·`candidateLists`(domain/queue.ts). 경계·빈 목록·10개 상한·정의 밖 칸을 단위 시험으로 먼저 본다.
4. **로비**: `LOBBY_WINDOW_LUA`에 자격 대조를 넣고 `lobbyWindow`가 `OPEN`·`DENIED`·`COPY_MISSING`(없는 명단 키)을 돌려준다. `JoinLobby`가 403·지표·경고 로그를 남기고 선점을 푼다.
5. **진입**: `NUMBER_BATCH_LUA`의 판매 상태 확인 뒤·묶음 넣기·번호 내기 앞에서 요청마다 계정 ID로 대조한다. `NumberBatcher`는 고른 명단 키가 같은 요청끼리만 모은다. 403이면 번호·묶음 자리를 쓰지 않고 `EnterQueue`가 선점을 푼다.
6. **입장 확정**: `ADMIT_LUA`의 ADMITTED 길에서 후보 명단 키(=`eligLists`+모든 창 `lists`)를 읽어 `lst`를 돌려주고, `Es256AdmissionTokens.sign`이 토큰에 싣는다. 같은 jti 재발급도 그때 사본으로 다시 읽는다.
7. **지표·경고**: `queue_sale_eligibility_checks_total{path,result}`와 `sale_eligibility.copy_missing`·`config_invalid` 경고(회차·명단 키만, 파드마다 회차·명단 키당 1분에 한 번)를 붙인다.
8. **실제 Valkey 시험 작성**(실행은 감독 허가 뒤): 같은 `eligibility-cases.ts`를 `test-int/entry-store.int.test.ts`에서 Valkey로 돈다. 시험이 사본 Set·표지를 직접 넣고, 대조와 사본 갈아끼우기를 번갈아 부른다.
9. 리뷰 4관점 → 틀린 구현 검사 → 게이트(통합 시험 제외) → 기록·커밋.

### 3.2 인터페이스

- **cfg**(docs/data.md:2318 `q:{event:E}:cfg`): `eligGates`는 `[{fromMs,toMs,lists}]` JSON, `eligLists`는 명단 키 JSON 배열. 둘 다 선택이고 모양이 틀리면 `config_invalid`로 그 회차 로비·진입을 모두 403. 창 고르기: 로비는 `opensAtMs`, 진입은 지금(파드 주입 시계). 경계 `fromMs ≤ t < toMs`, 겹치면 합집합.
- **사본 키**(docs/data.md:2354~2355): `q:{event:E}:elig:{listKey}`(Set, 계정 ID)와 `q:{event:E}:eligv:{listKey}`(문자열, 사본 판). queue-svc는 표지가 있을 때만 사본이 있다고 본다(0명 명단은 표지만).
- **EntryStore.lobbyWindow**: `{ kind: 'OPEN' } | { kind: 'NOT_OPEN' } | { kind: 'CLOSED' } | { kind: 'DENIED' } | { kind: 'COPY_MISSING'; listKeys: string[] }`.
- **EntryStore.numberBatch**: `eligibility?: { listKeys: readonly string[] }`, `NumberItem.accountId?`, `NumberResult`에 `{ kind: 'ELIGIBILITY_REQUIRED'; cause: 'denied' | 'copy_missing' }`.
- **AdmissionStore.admit**: `eligibilityLists?: readonly string[]`(후보 키, 모양이 틀리면 넘기지 않는다), `AdmitResult` ADMITTED에 `lists?: string[]`.
- **AdmissionTokens.sign**: `lists?: string[]` → 토큰 클레임 `lst`(글자 차례, 중복 없음, 1~10개). 빈 배열은 넣지 않는다.
- **HTTP**: 403 Problem type `sale-eligibility-required`, 제목 '이 판매 단계의 예매 대상이 아닙니다', 확장 칸·`Retry-After` 없음. 명단 밖·사본 없음·설정 틀림이 같은 본문.
- **Lua**: `NUMBER_BATCH_LUA`는 `KEYS` 뒤에 명단 키마다 표지·Set 두 키를 더하고, ARGV 뒤에 `gateFlag`·`listCount`·요청마다 계정 ID를 더한다(옛 인수만 넘기면 예전과 같다: 측정 도구 호환). `ADMIT_LUA`는 `KEYS` 뒤에 후보 Set 키를 더하고 ARGV 뒤에 후보 키 이름을 더한다.
- **지표**: `queue_sale_eligibility_checks_total{path,result}`(`path` = `lobby`·`entry`, `result` = `allowed`·`denied`·`copy_missing`·`config_invalid`). 경고 로그 줄 이름은 `sale_eligibility.copy_missing`·`sale_eligibility.config_invalid`.

## 5. 틀린 구현 검사(A, 기본 1개·경계/되돌림 2개)

구현에 관여하지 않은 담당이 넣는다. 최소 목록:

1. 창 경계를 `<=`로 바꾼다(toMs 포함) — 경계 시험이 잡아야 한다.
2. 로비 판정 시각을 `now`로 바꾼다 — 오픈 전 로비 시험이 잡아야 한다.
3. 겹친 창에서 첫 창만 쓴다 — 합집합 시험이 잡아야 한다.
4. 표지 없음을 '구성원 0명'으로 본다(copy_missing 미검출) — 닫힌 쪽 시험이 잡아야 한다.
5. 대조를 pid로 바꾼다 — 계정 대조 시험이 잡아야 한다.
6. 자격 거절 뒤 선점을 풀지 않는다 — 바로 다시 시도 시험이 잡아야 한다.
7. 거절된 요청도 카운터를 올린다(번호 발급 0 위반) — 카운터 단위 시험이 잡아야 한다.
8. 거절된 요청을 묶음 참가자에 넣는다 — 묶음 참가자 수 시험이 잡아야 한다.
9. `lst`에 후보 전체를 싣는다(명단에 안 든 키 포함) — `lst` 정확값 시험이 잡아야 한다.
10. `lst`를 입장 시점 창의 키만 싣는다 — 창 밖 입장·eligLists 시험이 잡아야 한다.
11. 설정이 틀렸는데 창을 버리고 연다 — config_invalid 시험이 잡아야 한다.
12. 묶음 공통 값에서 명단 키를 빼서 다른 자격을 한 묶음에 모은다 — 묶음 분리 시험이 잡아야 한다.
13. 경고 로그에 계정 ID를 싣는다 — 로그 칸 시험이 잡아야 한다.
14. 경고를 요청마다 남긴다 — 1분 가림 시험이 잡아야 한다.

놓친 것은 재현 시험을 더하고 결과를 커밋 본문에 적는다.

## 6. 리뷰 4관점에서 볼 것

- **정확성**: 창 경계 양쪽, 로비·진입 판정 시각, 겹친 창, 빈 `lists`, 후보 10개 상한, `lst` 글자 차례·중복, 같은 jti 재발급.
- **동시 실행·장애**: 사본 갈아끼우기와 대조(같은 회차 슬롯 Lua), 묶음 안 자격 섞임, 표지·Set이 어긋난 순간(쓰는 쪽 Lua 하나), 대기열 Redis 일시 장애 때 503(자격 403과 섞이지 않게), 선점 풀기 실패.
- **보안**: 계정 ID 대조(pid·기기 값 아님), 403 본문에 명단·사본 상태 없음, `lst`를 로그·사건·분석에 싣지 않음, 경고 로그에 계정 없음, 설정 틀림의 닫힌 쪽.
- **화면–서버 잇기**: 이 묶음은 화면을 고치지 않는다. openapi 403 본문과 docs/frontend.md §3.4의 Q-T36 ⑧이 HOT-346과 맞는지만 본다.
