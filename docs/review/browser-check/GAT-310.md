# 브라우저 확인: GAT-310 BAT-465 SCR-030 SSE(운영 명령 화면)

- 날짜: 2026-11-15
- 결과: **통과**(가짜 ops API로 UI 확인). 실제 ops-svc HTTP·Kafka·gRPC 경로는 test-int가 확인했다.
- 환경: `D:/ticketpass-lane3`, console-host 정적 빌드(`PEAKET_OPS_API_ORIGIN=http://127.0.0.1:18080`, `dist`를 18081에서 정적 서빙), 저장소 밖 가짜 ops API 18080. 가짜 API는 `GET /v1/ops/commands`(승인 대기 `SALE_STOP` 1건), `GET /v1/ops/audit-checkpoints`, `GET /v1/ops/live`(SSE)를 답한다. 인터넷으로 나간 요청은 없다.
- **browse 확장이 연결되어 있지 않아**(relay `127.0.0.1:19988` 닿지 않음) Chrome headless + CDP로 대신했다. 사유: 이 세션에서 browse relay가 뜨지 않았고, 화면은 정적 빌드와 가짜 API만으로 확인할 수 있었다.

## 확인한 것

- `/commands`가 열리고 `운영 명령` 화면과 승인 대기 `SALE_STOP`(판매 중지) 행이 보인다.
- 헤더의 SSE 연결 배지가 **실시간**이다(EventSource 연결됨).
- 서버가 SSE로 민 `SALE_RESUME`(판매 재개) 행이 **폴링 없이** 목록에 붙는다.
- 서버가 1.2초 뒤 연결을 끊자 EventSource가 **`Last-Event-ID: 100`**으로 다시 붙었다(`sseConnections: 2`, `lastEventIds: [null, "100"]`).
- 다시 붙은 연결에서 서버가 `event: reset`을 보내자 화면이 **REST로 다시 읽었다**(`GET /v1/ops/commands` 호출 2 → 4).
- 콘솔 오류는 없었다.

## 실제 ops-svc 경로 확인 범위

- 브라우저는 **가짜 ops API**만 불렀다. 실제 관리자 쿠키·identity 경로를 브라우저에서 열지 않았다.
- 실제 경로는 `services/ops-svc/test/command-execution-http.test.ts`(메모리)와 `test-int/sale-stop-control.int.test.ts`(실제 PostgreSQL 18 + 가짜 purchase-svc/queue-svc HTTP)가 확인했다: `SALE_STOP`/`SALE_RESUME` 2인 승인, 중지 purchase→queue·재개 queue→purchase 차례, 실패·재시도, 실행 전후 감사 체크포인트, Ed25519 공개 앵커·검증.
- SSE 사건의 서버 쪽(1초 훑기·`Last-Event-ID` 1시간 창·reset)은 `services/ops-svc/test/ops-live.test.ts`가 본다.
- 스크린샷은 headless라 남기지 않고 DOM 텍스트·서버 쪽 연결 기록으로 확인했다.
