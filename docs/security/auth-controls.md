## 1. 범위: 누가 무엇으로 로그인하는가

이 문서의 통제는 비밀번호로 로그인하는 관리 계정에 건다. 팬은 소셜 로그인만 쓴다. identity §1과 FR-001에 따라 팬은 카카오·네이버·구글의 OAuth 2.0(다른 서비스 계정으로 로그인하게 하는 표준) 인가 코드 흐름과 PKCE(로그인 중 가로챈 코드를 못 쓰게 하는 보강 방식)로만 로그인하고, PEAKET은 팬 비밀번호를 저장하지 않는다(2026-10-30 확인).

| 계정 | 로그인 방식 | 비밀번호 대입을 막는 곳 | 이 문서에서 다루는 것 |
| --- | --- | --- | --- |
| 팬 | 소셜 로그인만. 자체 비밀번호가 없다(identity §1, FR-001) | 소셜 제공자, 곧 IdP(로그인을 대신 처리해 주는 쪽)의 정책(POL-020의 예외 칸) | §2.4 계정 탈취를 어디서 줄이는지만 |
| 파트너(`partner_admin`·`partner_member`) | 업무 이메일 + 비밀번호 + TOTP(인증 앱이 시간에 따라 새로 만드는 일회용 코드). 로그인 화면 SCR-020은 인터넷에 열려 있다 | 이 문서 §2~§4 | 전부. 크리덴셜 스터핑의 주된 대상이다 |
| 운영자(`viewer`·`operator`·`commander`), CS 담당자(`cs_agent`·`cs_lead`) | 파트너와 같다. 로그인 화면 SCR-028과 `ops-api`는 관제 배포의 허용 IP 안에서만 닿는다(identity §6 '관리망 접근 통제') | 허용 IP + 이 문서 §2~§4 | 전부. 허용 IP 밖의 대입은 로그인 API(프로그램끼리 요청과 응답을 주고받는 창구)에 닿기 전에 막힌다 |
| 현장 스태프(`gate_staff`·`gate_lead`) | 휴대폰은 팬과 같은 소셜 로그인, 스캐너는 등록 기기의 기기 키와 기기 승인 로그인(RFC 8628)의 확인 코드(identity §6.1) | 확인 코드 시도 제한(계정당 10분에 5회, 기기당 시간당 10회 [가정, wbs 5.5.2에서 확정]) | §3.6 잠그지 않는 이유만. 비밀번호가 없어 §4 대상이 아니다 |

인증 경로가 여럿일 때 모든 경로와 그 통제를 함께 적으라는 ASVS 6.1.3의 목록은 identity §1·§2·§6에 있다. 이 문서는 그 가운데 비밀번호가 있는 경로의 통제를 정한다. ASVS는 웹 보안 기준을 만드는 비영리 단체 OWASP가 만든 웹 앱 보안 검증 항목 목록이다.

## 2. 크리덴셜 스터핑 방어

크리덴셜 스터핑은 계정마다 한두 번씩만 넣어 본다. 다른 사이트에서 샌 (이메일, 비밀번호) 쌍을 하나씩 대입하기 때문이다. 그래서 계정마다 세는 잠금(§3)만으로는 거의 걸리지 않는다. 출발지 단위 계수, 비밀번호 자체의 대조, 2단계 인증, 전체 실패율 경보를 함께 둔다. 아래 C1~C8은 요청이 들어오는 순서다.

### 2.1 층별 통제

| # | 층 | 통제 | 막는 것 | 남는 것 |
| --- | --- | --- | --- | --- |
| C1 | 엣지(CDN, 곧 사용자 가까운 곳에서 대신 응답하는 전송망의 서버)의 웹 ACL(WAF: 악성 요청을 걸러 내는 웹 방화벽의 규칙 묶음) | 파트너·관제 배포의 웹 ACL에 AWS 관리 IP 평판 목록을 둔다(identity §6 '관리망 접근 통제'). 관리 계정 로그인 경로(`POST /v1/partner/auth/sessions`, `POST /v1/ops/auth/sessions`)에는 IP 단위 속도 규칙을 걸어 5분에 50회 [가정]를 넘으면 막고 429를 준다. AWS WAF 속도 규칙의 평가 창은 60·120·300·600초 중 하나이고 한도의 최솟값은 10이며, 정확히 그 수에서 끊기지는 않는다(AWS 문서, 2026-10-30 확인). 관제 배포는 허용 IP 규칙이 먼저 거른다 | 한 IP에서 많이 넣는 대입 | IP를 계속 바꾸는 느린 대입. 한 사무실이 NAT(여러 기기가 공인 주소 하나를 나눠 쓰는 방식)로 주소 하나를 함께 쓰면 그 사무실의 로그인도 같은 한도를 나눠 쓴다 |
| C2 | 게이트웨이(gw-partner·gw-ops) | 로그인 요청의 `Origin`(요청을 보낸 페이지의 출처를 알리는 헤더)을 자기 콘솔 출처와 대조한다(ADR-0065 결정 5). 로그인 경로에 파드(쿠버네티스에서 앱이 실행되는 가장 작은 단위)별 로컬 한도를 둔다(docs/api/guidelines.md §6의 원칙, 값은 wbs 3.5.1) | 다른 사이트가 사용자 브라우저로 로그인 요청을 보내는 것, 한꺼번에 몰리는 요청 | 로컬 한도는 파드별이라 '파드 수 × 한도'만큼 받는다 |
| C3 | identity 출발지 계수 | 한 IP 주소에서 1시간에 서로 다른 이메일 5개 [가정] 이상으로 로그인이 실패하면(없는 이메일 포함), 그 IP에서 하는 모든 관리 계정 로그인에 1시간 [가정] 사람 확인을 건다(추천 적용 2026-10-30) | 한 IP가 여러 계정에 한 번씩 넣는 대입 | IP를 매번 바꾸면 계정마다 사람 확인 없이 3번까지 넣을 수 있다(그 뒤로는 계정 단위 사람 확인, §2.3) |
| C4 | identity 계정 계수 | §3의 잠금 규칙 | 한 계정에 거듭 넣는 대입 | §3.7 |
| C5 | 비밀번호 자체 | 15자 이상, 흔한 비밀번호·유출 비밀번호·맥락 금칙어 대조(§4). 비밀번호를 정할 때 대조하므로 유출 목록에 있는 비밀번호는 처음부터 쓸 수 없다. 로그인에 성공할 때 30일 [가정]마다 유출 목록을 다시 본다(§4.3 8, 추천 적용 2026-10-30) | 이미 샌 쌍 대부분 | 유출 목록에 아직 없는 유출. 같은 비밀번호를 다른 곳에 쓰다가 새면 다음 확인까지(길어야 30일) 모른다 |
| C6 | 2단계 인증 | 비밀번호가 맞아도 TOTP 없이는 세션을 주지 않는다(I-T10, POL-020) | 비밀번호만 가진 공격자 | 가짜 로그인 페이지가 TOTP까지 바로 넘기는 실시간 중계 피싱. 위험 작업은 패스키(기기 안의 키로 서명해 인증하는 표준 방식. 등록한 사이트 주소에서만 쓰여 피싱에 강하다) 단계 인증으로 한 번 더 막는다(identity §6 '다중 요소 인증') |
| C7 | '비밀번호만 맞은 로그인' 알림 | 지난 30일 [가정] 동안 로그인에 성공한 적이 없는 출발지(IP 주소와 브라우저 기기 식별값)에서 비밀번호가 맞았는데 10분 [가정] 안에 2단계를 끝내지 않으면, 비밀번호가 샌 신호로 본다. 계정 주인의 업무 이메일로 바로 알리고, 다음 로그인 뒤 비밀번호를 바꾸게 한다(§3.5, 추천 적용 2026-10-30) | 대입 도구가 2단계 화면에서 멈추고 '맞는 비밀번호'를 챙겨 가는 것 | 알림 전에 그 비밀번호를 다른 서비스에 쓰는 것은 막지 못한다. 새 기기에서 로그인하다 그만둔 본인에게도 알림이 간다 |
| C8 | 전체 실패율 경보 | 관리 계정 로그인 실패가 5분에 100건 [가정] 이상이거나 지난 7일 같은 시간대 평균의 10배 [가정]를 넘으면 SEV3(장애 심각도 등급으로, 숫자가 작을수록 심각하다) 보안 경보를 내고, identity가 모든 관리 계정 로그인에 1시간 [가정] 사람 확인을 건다. 경보에 끝나는 시각을 싣는다(추천 적용 2026-10-30. 'POL-020의 비정상 침입탐지'에 값을 붙였다) | 넓게 퍼진 대입 | 사람 확인을 사람이나 풀이 서비스로 푸는 공격은 느려질 뿐이다 |

검토한 다른 안: AWS WAF의 계정 탈취 방지 규칙 묶음(`AWSManagedRulesATPRuleSet`)은 로그인 요청의 이메일·비밀번호 쌍을 AWS의 유출 자격 목록과 대조하고, CloudFront 배포에서는 로그인 응답의 성공·실패도 본다(AWS 문서, 2026-10-30 확인). 추가 요금이 들고 금액은 [확인 필요]다. 관리 계정 수가 적고 C5·C6·C7이 같은 위험을 덜어 내므로 지금은 쓰지 않는다. 운영에서 C8 경보가 분기에 두 번 [가정] 넘게 울리면 다시 본다.

### 2.2 계정이 있는지 알리지 않는다(추천 적용 2026-10-30)

- 없는 이메일도 있는 계정과 같은 수로 센다. 상태 코드, 본문, 남은 시도, 잠금 문구가 모두 같다. 해제 링크만 보내지 않는다(받을 곳이 없다). 그래서 docs/design/d5 SCR-020·SCR-028의 잠금 문구("업무 이메일로 보낸 링크")는 없는 이메일에도 그대로 보인다.
- 없는 이메일에도 비밀번호 해시(원래 값으로 되돌릴 수 없게 바꾼 고정 길이 값) 계산을 같은 반복 횟수로 한 번 한다(가짜 솔트). 그래서 응답 시간으로 가입 여부를 가리기 어렵다.
- 남는 차이: 있는 계정만 KMS(암호 키를 안전하게 보관하고 대신 써 주는 클라우드 서비스) 페퍼 확인(`VerifyMac`, ADR-0050 결정 9)을 부른다. 그 호출 시간(수 ms [추정])만큼 차이가 남고, 많이 재면 구별할 수 있다. 응답 시간까지 같게 하라는 ASVS 6.3.8은 L3라 지금 목표 레벨(L2) 밖이고 판정 표에 넣지 않았다.

### 2.3 사람 확인을 거는 때

사람 확인(Cloudflare Turnstile)은 로그인 첫 단계를 보내기 전에 받는다(docs/design/d5 SCR-020 '사람 확인' 행). 다음 가운데 하나면 건다.

1. 그 계정의 계정 실패 수가 3 [가정] 이상이다(§3.1, ADR-0062).
2. 그 계정에 24시간 안에 시간 잠금이 걸린 적이 있다. 잠금을 걸 때 계정 실패 수를 0으로 돌리므로, 이 조건이 없으면 잠금이 풀린 뒤 첫 세 번은 사람 확인 없이 넣을 수 있다(추천 적용 2026-10-30).
3. 그 계정에 여러 출발지 경보가 걸려 있다(§3.4).
4. 그 IP에 출발지 경보가 걸려 있다(§2.1 C3).
5. 전체 경보가 걸려 있다(§2.1 C8).

사람 확인 서비스에 닿지 못하면, 사람 확인이 필요한 로그인은 받지 않는다. 필요 없는 로그인은 그대로 한다(추천 적용 2026-10-30).

토큰의 서버 검증은 identity-svc가 Cloudflare 검증 API(siteverify)로 직접 한다. trust-svc의 위험 판정(`ScoreRisk`)을 거치지 않는다. 응답의 `hostname`은 파트너 로그인이면 `partner.peaket.example`, 운영자·CS 로그인이면 `console.peaket.example`이어야 하고 `action`은 `login` [가정]이어야 한다. 다르면 실패다. 그래서 한 콘솔에서 받은 토큰을 다른 콘솔 로그인에 옮겨 쓰지 못한다. 토큰은 300초 1회용이고, 답이 늦으면 같은 `idempotency_key`로 한 번만 다시 묻는다(docs/features/bot-defense.md §6 표, 추천 적용 2026-10-30).

### 2.4 팬 계정 탈취는 어디서 줄이는가

팬 비밀번호의 대입과 실패 차단은 소셜 제공자가 한다(POL-020). PEAKET은 제공자 세션과 따로 세션을 두고, 쿠키(브라우저가 사이트별로 저장했다가 요청마다 함께 보내는 작은 값) 탈취나 소셜 계정 탈취의 피해를 identity §7의 보완 통제로 줄인다. 새 기기 로그인 알림, 민감 작업 전 제공자 재인증과 그 강도 기록, 위험 점수, 연계정보로 묶은 1인 1계정이 그것이다(ADR-0001). 로그인 시작과 콜백이 한꺼번에 몰리는 것은 처리 용량의 문제라 identity §10 '오픈 직전 로그인 폭주'가 다룬다.

## 3. 관리 계정 로그인 잠금 규칙

이 절이 잠금 규칙의 정본이다(추천 적용 2026-10-14·2026-10-28에 정한 규칙을 옮겼다, ADR-0062, 기술 검토 중간-052). 두 기준을 함께 지킨다.

- 「개인정보의 안전성 확보조치 기준」 제5조 제6항은 정당한 권한을 가진 자만 접근하도록, 일정 횟수 이상 인증에 실패하면 '접근을 제한하는 등 필요한 조치'를 하라고 한다. 횟수와 푸는 방법은 정하지 않는다(고시 제2026-9호 원문, 2026-10-30 확인). 이 항은 제2025-9호로 고친 조항이고, 그 부칙에 따라 발령 1년 뒤부터 시행한다(시행일은 data-classification 머리의 기준 법령 줄을 따른다). 횟수는 위험 분석으로 스스로 정한다(data-classification 법률 #8). 시간이 지나면 풀리는 잠금도 그 조치에 든다는 판단은 해석이다(data-classification 법률 #26, POL-027). 고친 항의 대상은 '정당한 권한을 가진 자'라서, 정보주체를 뺀다고 적은 제6조 제2항·제8조 제1항과 달리 정보주체를 빼지 않는다(앞 판과의 대조는 docs/security/internal-management-plan.md §1.3). 팬 로그인은 PEAKET이 비밀번호를 확인하지 않고 소셜 제공자가 인증하므로 실패 제한도 제공자에 맡긴다(POL-020 예외 칸, asvs/auth.md '고시 제5조 제6항' 행). 이것으로 팬 쪽 조치를 다한다는 판단은 [확인 필요]다(법률 검토 wbs 7.4.1).
- NIST SP 800-63B-4 §3.2.2는 한 계정에서 한 인증 수단의 연속 실패를 100회 이하로 제한하고, 넘으면 그 인증 수단을 정지해 다시 묶게(rebind) 하라고 한다(SHALL). 100은 상한이고 더 낮게 정해도 된다. 정당한 사용자가 잠기지 않게 사람 확인, 실패할수록 길어지는 대기, IP·기기 같은 위험 신호를 더할 수 있다고 한다(2026-10-30 원문 확인).

지금까지의 시간 잠금은 15분이나 1시간이 지나면 다시 넣을 수 있어서, 로그인 성공 없이 이어지는 연속 실패에 끝이 없었다. 그래서 '비밀번호 연속 실패 누계'를 더해 NIST 상한을 실제로 지킨다(§3.1, 추천 적용 2026-10-30).

### 3.2 잠금 종류와 푸는 방법

- 보호 잠금 화면은 잠긴 원인을 말하지 않는다. 비밀번호가 맞았다는 사실을 알리지 않기 위해서다(docs/design/d5 SCR-028 '보호 잠금' 행).
- 비밀번호 연속 실패 누계로 건 보호 잠금은 docs/planning/03 §2.7 관리 계정 상태의 A7(보호 잠금)과 같은 상태로 간다. A7의 조건에 이 경우를 2026-10-30 더했다. 해제 링크에서 2단계가 5회 틀려 거는 보호 잠금은 같은 날 더한 전이 A10이다.
- 스스로 하는 비밀번호 재설정은 두지 않는다. 비밀번호를 잊으면 운영자에게 재초대를 요청한다(asvs/auth.md 6.4.3의 정본). 그래서 보호 잠금도 재초대로만 푼다.
- 재초대의 까닭은 셋이다(추천 적용 2026-10-30, docs/features/identity.md §6 '관리 계정 관리 API'). `RESEND`는 초대됨·초대 만료 계정에 링크를 다시 보내고, `PROTECT_LOCK`은 보호 잠금을 풀며, `CREDENTIAL_LOST`는 활성 계정이나 시간 잠금 중인 계정의 주인이 비밀번호나 인증 앱을 잃었을 때다(docs/planning/03 §2.7 A11·A12). 시간 잠금만 걸린 계정에 `PROTECT_LOCK`을 보내면 409다(시간 잠금은 §3.3의 본인 해제로 푼다). 뒤의 둘은 업무 이메일 밖의 길로 신원을 확인한 뒤 하고, 어떻게 확인했는지 사유에 적는다(ASVS 6.4.4). 운영자가 재초대해도 링크는 계정에 등록된 업무 이메일로만 가고, 운영자가 받을 주소를 바꾸지 못한다. 그래서 운영자 한 사람이 남의 계정을 가로채려면 그 업무 이메일도 손에 넣어야 한다. 업무 이메일이 탈취된 계정은 재초대로 되찾을 수 없고, 계정을 지운 뒤 새 이메일로 초대한다. 삭제는 잠금과 상관없이 된다(시간 잠금·보호 잠금 중에도, docs/planning/03 §2.7 A15·A16, 추천 적용 2026-10-30).

### 3.3 본인 해제 링크

- 시간 잠금이 걸리면 계정의 업무 이메일로 1회용 해제 링크를 보낸다. 운영자를 기다리지 않게 하려는 것이다.
- 링크 토큰은 32바이트 난수이고 SHA-256 해시만 저장한다. 수명은 30분 [가정]이다. 현장 스태프 초대 링크처럼 토큰을 URL 조각(`#` 뒤)에 두고, 화면이 읽자마자 주소에서 지운 뒤 요청 본문으로 보낸다(identity §6.1 'URL 조각의 비밀 처리'와 같다, 추천 적용 2026-10-30).
- 링크 화면에서 인증 앱 코드나 복구 코드를 맞게 넣으면 시간 잠금만 풀린다. 묶음 잠금, 2단계 실패 수, 비밀번호 연속 실패 누계는 그대로다. 그 뒤 비밀번호와 TOTP로 로그인한다.
- 링크에서 코드가 틀리면 2단계 실패 수에 센다. 한 링크는 코드가 3번 [가정] 틀리면 무효가 된다(추천 적용 2026-10-30). 업무 이메일만 손에 넣은 공격자가 2단계 실패를 5번 채우면 보호 잠금이 걸린다(§3.7).
- [ 해제 링크 다시 받기 ]는 계정당 1시간에 3번 [가정]까지다. 새 링크를 보내면 옛 링크는 무효다(추천 적용 2026-10-30). 메일을 퍼부어 업무 메일함을 어지럽히는 것을 막는다.
- NIST SP 800-63B-4 §4.2는 이메일로 보내는 복구 코드를 24시간 이하, 10진수 6자리 이상과 같은 세기로 정한다. 이 링크는 30분이고 256비트라 그 기준보다 짧고 세다. 해제는 계정 복구가 아니라 잠금을 푸는 일이고, 그 뒤에도 비밀번호와 TOTP를 모두 거친다.

| 출발지 경보·전체 경보(§2.1 C3·C8) | — | 전체 경보는 SEV3 [가정] 보안 경보 |

계정 주인 메일에 싣는 시각은 모두 발송 고리가 보낸 시각이다(사건 시각이 아니다, 2026-11-05, BOT-123이 넘긴 것). 경보의 심각도 값은 처음 값이고 [가정, wbs 3.5.1에서 확정]이다(추천 적용 2026-10-30). 모든 로그인 시도의 성공·실패와 쓴 인증 요소는 법정 접속기록에 남는다(identity §9).

### 3.5 비밀번호를 바꾸게 하는 경우(추천 적용 2026-10-30)

- 비밀번호만 맞은 로그인(§2.1 C7)이 있었거나, 로그인 때 다시 본 유출 목록에서 비밀번호가 나왔으면(§4.3 8) 다음에 비밀번호와 TOTP로 로그인한 세션은 비밀번호 바꾸기와 로그아웃만 할 수 있다. 액세스 토큰의 `scope`를 비밀번호 바꾸기 하나로 준다. 표시가 켜질 때 이미 열려 있던 세션도 다음 토큰 갱신(15분 안)부터 같다(추천 적용 2026-11-05, BUILD_ORDER BOT-130). NIST SP 800-63B-4 §3.1.1.2는 인증 수단이 샌 증거가 있으면 바꾸게 하라고 한다(SHALL).
- 바꾸면 그 계정의 다른 세션을 모두 끝낸다(`control.sessions-terminated`, identity §3).
- 새 비밀번호가 지금 비밀번호와 같으면 거절한다. 같은 비밀번호로 바꾸기 필요 표시만 꺼지면 샌 비밀번호가 그대로 남는다(추천 적용 2026-11-05).
- 비밀번호를 바꾸는 화면에서 지금 비밀번호를 넣을 때도 로그인 1단계와 같이 잠김(§3.2)을 먼저 보고, 틀리면 §3.1대로 세며 §3.4의 알림과 경보도 같다. 세션을 가진 사람이 잠금을 피해 비밀번호를 추측하는 길이 되지 않게 한다(추천 적용 2026-11-05).
- 정기 변경은 강제하지 않는다(ASVS 6.2.10, NIST §3.1.1.2).

### 3.6 현장 스태프는 잠그지 않는다

- 현장 스태프에게는 비밀번호가 없다. 휴대폰 로그인은 소셜 제공자가 하고, 스캐너 로그인은 등록 기기의 기기 키와 기기 승인 로그인의 확인 코드로 한다(identity §6.1).
- 확인 코드 승인에 실패하면 계정을 잠그지 않고 그 코드를 무효로 할 뿐이다(identity §6.1, I-T37). 공연 당일 입장 업무를 잠금으로 멈추지 않기 위해서다.
- 그래도 맞혀 들어갈 가능성은 작다. 확인 코드는 문자 20개로 만든 8자(20^8 = 약 2.6 × 10^10가지)이고 수명이 5분이다. 한 계정이 10분에 5번까지 틀릴 수 있으므로, 코드 하나를 맞힐 확률은 약 2 × 10^-10 [추정]이다. 코드 발급은 기기당 시간당 10회로 묶인다 [가정, wbs 5.5.2에서 확정].
- 이 절 밖의 규칙(§3.1~§3.5)은 현장 스태프에게 쓰지 않는다.

### 3.7 남는 위험

- 이메일을 아는 공격자는 사람 확인을 다섯 번 풀 때마다 그 계정을 1시간 잠글 수 있다. 계정 주인은 매번 업무 이메일 링크와 인증 앱 코드로 바로 풀 수 있고, 이미 열린 세션은 잠금과 상관없이 이어진다. 피해는 새 로그인의 번거로움이다.
- 이런 공격이 주인의 로그인 성공 없이 이어지면, 1시간 잠금마다 5번씩이라 약 20시간 [추정] 뒤 비밀번호 연속 실패 누계가 100에 닿는다. 그때는 보호 잠금이 걸려 운영자 재초대를 기다린다. 50에서 미리 알리고, 주인이 그 사이 한 번 로그인하면 0으로 돌아간다.
- 업무 이메일만 손에 넣은 공격자는 해제 링크에서 2단계를 다섯 번 틀려 보호 잠금을 걸 수 있다. 메일함 탈취는 그 자체로 큰 사고라 보호 잠금을 그대로 둔다.
- 출발지가 든 값은 Redis에 있어 장애 조치 때 처음부터 다시 센다. 그동안 출발지 단위 통제가 잠시 약해진다. 계정 단위 값은 DB에 있어 남는다.
- 사람 확인 서비스가 멈추면 사람 확인이 필요한 로그인은 받지 않는다. 그동안 잠긴 적이 있는 계정의 주인도 로그인하지 못한다.
- 관제 허용 IP 안(사내망·VPN)에서 하는 대입은 허용 IP로 걸러지지 않고 C2~C8만 남는다.

## 4. 비밀번호 금칙어 목록과 대조 방식

ASVS 6.1.2(L2)는 비밀번호로 쓰지 못하게 할 맥락 단어 목록을 문서에 두라고 하고, 그 예로 조직 이름·제품 이름·시스템 식별자·프로젝트 코드 이름·부서와 역할 이름의 변형을 든다. 6.2.11은 그 목록을 실제로 쓰라고, 6.2.4는 흔한 비밀번호 3,000개 이상과, 6.2.12는 유출 비밀번호와 대조하라고 한다(ASVS 5.0.0 원문, 2026-10-30 확인). NIST SP 800-63B-4 §3.1.1.2는 정하거나 바꾸는 비밀번호를 흔한·예상되는·유출된 비밀번호 목록과 대조하되, 비밀번호 전체를 대조하고 "not substrings or words that might be contained therein"(그 안에 든 부분이나 낱말로 대조하지 말라)고 한다. 목록의 예로 서비스 이름, 사용자 이름과 그 파생형을 들고, 거절할 때는 이유를 알리고 고르는 방법을 안내하라고 한다(SHALL). 지나치게 큰 목록은 이득이 작다고 한다(2026-10-30 원문 확인).

그래서 이 문서는 '맥락 말이 들어 있으면 막는다'가 아니라 '맥락 말과 쉬운 덧붙임만으로 된 비밀번호를 막는다'로 정한다(§4.3, 추천 적용 2026-10-30). 지난 판의 identity §6 '서비스 이름이 든 단어'와 I-T14의 '금칙어가 든 비밀번호'는 이 뜻으로 고쳤다.

### 4.3 대조 방식

1. **원문은 그대로 다룬다**: 저장하는 해시와 로그인 확인은 받은 원문으로 한다. 유니코드 NFC 정규화(같은 글자를 한 가지 바이트 꼴로 맞추는 것, NIST §3.1.1.2 권고)만 하고, 자르거나 대소문자를 바꾸지 않는다(ASVS 6.2.8). 아래 사본은 대조에만 쓰고 바로 버린다.
2. **대조용 사본 셋을 만든다**: ① 기본 사본은 NFKC로 전각·반각 같은 겉모양 차이를 맞추고, 소문자로 바꾸고, 공백·`-`·`_`·`.`을 지운 것이다. ② 바꿈 사본은 ①에서 흔히 바꿔 쓰는 글자를 되돌린 것이다(`0`→`o`, `1`→`l`, `3`→`e`, `4`→`a`, `5`→`s`, `7`→`t`, `@`→`a`, `$`→`s`). ③ 자판 사본은 ①의 한글을 두벌식 자판에서 누르는 영문 키로 바꾼 것이다('피켓' → `vlzpt`). 맥락 말도 같은 방법으로 사본을 만들어 맞댄다.
3. **전체 대조(L1·L2)**: 사본 ①이나 ②가 L1의 비밀번호와 같거나, 사본 전체가 L1 꼴 규칙의 조각(키보드 한 줄 연속, 같은 글자 반복, 연속 숫자)만 이어 붙인 것이면 막는다. L2는 원문(NFC)을 UTF-8로 바꾼 SHA-1 해시의 앞 5자만 `https://api.pwnedpasswords.com/range/{앞 5자}`로 보내고, 돌아온 뒷부분 목록(보통 약 800줄)에 나머지가 있으면 막는다(한 번이라도 나온 것). 요청에 `Add-Padding: true`를 붙여 응답을 800~1,000줄로 채우게 한다. 응답 크기로 어느 접두어를 물었는지 짐작하지 못하게 하려는 것이다. 이 API는 가입이나 API 키 없이 쓴다(HIBP API v3 문서, 2026-10-30 확인).
4. **맥락 말 대조(L3~L5)**: 사본 ①②③마다 맥락 말을 긴 것부터 모두 지운다. 하나 이상 지웠고 남은 부분이 '쉬운 덧붙임'이면 막는다. 쉬운 덧붙임은 남은 부분에서 숫자·기호·공백을 뺀 글자가 3자 [가정] 이하이거나, 그 글자가 L1 꼴 규칙(키보드 한 줄 연속, 같은 글자 반복)뿐인 것이다. 덧붙인 숫자가 연도나 날짜여도 숫자이므로 같다. 남은 글자 수는 NFC 원문의 글자(사람이 한 글자로 보는 단위: 결합 문자는 앞 글자와 한 글자)로 센다. 사본은 원문 글자마다 만들어 잇는다. 사본 ①②③에서 한 글자가 둘 이상으로 늘어난 것(㎏ → kg, İ → i̇, 한글 한 음절 → 자판 키 2~3자)은 원문 한 글자이고, 문자(한글·로마자 등)가 없는 원문 글자(㎏, 이모지, 키캡 숫자)는 글자로 세지 않는다. 따로 쓴 자모(ㄱㅏ)는 사본에서 합치지 않아 두 글자다(2026-11-05, BOT-110이 넘긴 것).
5. **들어 있기만 한 것은 받는다**: 맥락 말을 지우고도 다른 글자가 4자 이상 남으면 맥락 말 때문에는 막지 않는다. NIST가 금지한 부분 문자열 대조를 하지 않고, 맥락 말에서 파생한 꼴만 막기 위해서다.

   | `peaket2026` | 10 | 막는다 | 15자 미만(I-T14) |

7. **거절 이유와 안내(NIST §3.1.1.2 SHALL)**: 화면에 거절 이유의 종류를 보인다. "너무 흔한 비밀번호입니다", "유출된 적이 있는 비밀번호입니다", "서비스·회사·계정 이름에 숫자나 기호만 붙인 비밀번호는 쓸 수 없습니다", "15자 이상이어야 합니다"의 넷이다. 그리고 "서로 관계없는 낱말 여러 개를 이은 문장이나 비밀번호 관리자가 만든 값을 쓰세요"를 함께 보인다. 유출 횟수는 보이지 않는다. 붙여넣기와 비밀번호 관리자는 막지 않는다(ASVS 6.2.7). 문구는 추천 적용 2026-10-30이고 docs/design/d5 SCR-020·SCR-028 상태 표의 '비밀번호 거절' 행에 옮겼다(2026-10-30).
8. **언제 대조하나**: 초대를 수락하며 비밀번호를 정할 때, 비밀번호를 바꿀 때, 보호 잠금 뒤 재초대에서 다시 정할 때 L1~L5를 모두 본다. 로그인에 성공할 때는 L2만, 마지막으로 본 지 30일 [가정]이 지났으면 다시 본다. 원문은 로그인할 때만 메모리에 있고, 저장한 값은 PBKDF2(비밀번호를 일부러 느리게 해시하는 방식, ADR-0033) 해시라 나중에 대조할 수 없기 때문이다. 걸리면 §3.5대로 바꾸게 한다(추천 적용 2026-10-30).
9. **유출 목록에 닿지 못할 때**: 비밀번호를 정할 때는 2초 [가정] 안에 답이 없으면 그 비밀번호를 받지 않고 503과 `Retry-After`로 다시 하게 한다. 유출 대조 없이 받지 않는다는 뜻이다. 초대 링크는 24시간이라 다시 할 시간이 있다. 로그인 때의 다시 보기는 건너뛰고 다음 로그인에 한다(추천 적용 2026-10-30).
10. **보내고 남기는 것**: 밖으로는 SHA-1의 앞 5자만 나간다. 비밀번호, 대조 사본, SHA-1과 그 앞 5자는 로그·트레이스(요청 하나가 여러 서비스를 거친 길과 시간을 남긴 기록)·오류 보고에 남기지 않는다(data-classification '관리자 비밀번호' P1). 거절 이유의 종류와 계정 ID만 보안 이벤트로 남긴다. 범위 조회 호출의 추적 기록은 경로를 지운 틀(`/range/{prefix}`)로만 남긴다: 플랫폼 바깥 호출 클라이언트(`createExternalHttpClient`)로 불러 자동 계측의 호출 span을 만들지 않고, 추적 머리(`traceparent` 등)도 싣지 않는다(2026-11-05, BOT-110이 넘긴 것. 메모리 span 처리기로 범위 조회를 돌려 어느 span에도 앞 5자가 없고 경로 틀 span 하나만 남는 것을 시험으로 본다). 이 호출은 identity-svc에서만 나가므로, 나가는 연결 허용 대상에 `api.pwnedpasswords.com`이 필요하다. 2026-10-30 docs/infra.md §9 '네트워크 격리 계층'과 위협 모델 경계 5(docs/security/threat-model.md §1)에 더했다.

### 4.4 남는 위험

- 맥락 말 목록 밖의 말(그 파트너의 공연·아티스트 이름, 사무실 주소)로 만든 비밀번호는 L1·L2에 없으면 받는다. 목록을 지나치게 늘리면 정상 비밀번호만 막히므로 넓히지 않는다(NIST §3.1.1.2).
- 상호나 업무 이메일이 바뀌어도 이미 정한 비밀번호는 다시 대조하지 못한다(해시만 있다). 다음에 바꿀 때 대조한다.
- 유출 목록에 아직 없는 유출은 막지 못한다. 2단계 인증(§2.1 C6)과 '비밀번호만 맞은 로그인' 알림(C7)이 다음 방어다.
- 사본 규칙(바꿈 표, 자판 변환)에 없는 꼴은 빠져나간다. 예를 들어 맥락 말을 거꾸로 쓴 것은 잡지 않는다.
- 3자 이하의 짧은 말(`ops`, `api`, `cs`)에 숫자·기호만 붙인 비밀번호는 맥락 말 대조에 걸리지 않는다. L1·L2에 없으면 받는다. 숫자·기호가 많은 비밀번호를 일반 규칙으로 막으면 NIST가 금지한 문자 구성 규칙이 되기 때문이다.

## 7. 미결정·[가정]

- §5의 [가정] 값은 wbs 3.5.1에서 정한다. 정할 때 운영 데이터(관리 계정 수, 하루 로그인 수, 사무실 NAT 공유)를 보고 웹 ACL 속도 규칙과 출발지 계수를 함께 맞춘다.
- L1 흔한 비밀번호 목록의 출처와 판은 wbs 3.5.1에서 고정한다.
- 잠금 해제 링크, 비밀번호 바꾸기, 해제 링크 다시 받기의 API 계약은 2026-10-30 docs/api/openapi.yaml에 더했다(`POST /v1/partner/auth/unlocks`·`/unlock-links`·`/password-changes`와 같은 ops 경로). 응답 코드와 한도의 [가정] 값은 wbs 3.5.1에서 정한다.
- 내부 관리계획(docs/security/internal-management-plan.md)은 허용 실패 횟수와 잠금 규칙으로 이 문서 §3과 §5를 가리킨다(고시 제4조 제1항, POL-020). 값을 바꾸면 두 문서를 같은 PR에서 고친다.
- 관리 계정에 의심스러운 인증 시도 알림(ASVS 6.3.5, L3)과 응답으로 계정 유무를 알리지 않기(6.3.8, L3)를 L3 선별 채택 항목으로 판정 표에 올릴지는 asvs/auth.md를 고칠 때 정한다. 지금 설계(§2.1 C7, §2.2)는 두 항목의 대부분을 이미 채운다.
