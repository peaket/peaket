# ASVS 추적 표: 전달 파이프라인과 운영 플랫폼(CI·공급망·GitOps·배포·운영 접근·운영 진단)

- **독자와 용도**: 전달 파이프라인과 운영 플랫폼(CI·공급망·GitOps·배포·운영 접근·운영 진단)을 만들거나 검토하는 플랫폼 엔지니어와 보안 검토자가, ASVS 5.0.0 항목마다 적용 여부·구현 위치·시험 결과·미적용 사유를 확인할 때 참조한다. 구현 전에 이 표를 먼저 쓴다(docs/architecture.md §8.2).
- **대상 기능 범위**: 코드가 저장소에서 운영 환경까지 가는 길과, 그 길을 받치는 플랫폼 설정이다. 공용 CI 워크플로, 산출물 증명(소프트웨어 부품 목록인 SBOM, 서명, 어느 커밋에서 어떤 빌드 절차로 만들었는지 서명해 남긴 출처 증명), 의존성 관리와 취약점 조치 기한, GitOps(배포 상태를 저장소에 적어 두고 클러스터를 그대로 맞추는 운영 방식) 승격과 클러스터 입장 정책(Kyverno), 배포와 마이그레이션 실행, 변경 동결 달력, 인프라 코드, 사람의 운영 접근과 감사 기록, 비용 상한 장치, 응답 보안 헤더(CloudFront 응답 헤더 정책과 게이트웨이 공통 정책)와 게이트웨이(클라이언트 종류별로 앞에 둔 입구 서버)의 CORS·출처 검사, 프런트엔드 공용 린트, 운영 진단(진단 증거의 수집·저장소, 프로브, 시간 초과 기본값, ADR-0070)을 다룬다. 각 서비스의 업무 기능은 기능별 추적 표(auth, payment, settlement, transfer-refund, offline-gate, bot-defense, analytics, queue-admission, catalog-review, support, frontend, forensic-replay, notify, seat-hold, control-tower)가 맡는다. 이 표는 그 표들이 '공통'이나 'CI'로 미룬 항목이 실제로 어디에 구현되는지 정한다.
- **보안 검증 기준**: OWASP ASVS 5.0.0(웹 보안 기준을 만드는 비영리 단체가 펴낸 웹 앱 보안 검증 항목 목록), 목표 레벨 Level 2. 웹 프런트엔드(V3)의 공통 설정, 설정(V13), 데이터 보호(V14, 운영 진단 증거 범위), 안전한 코딩과 구조(V15), 보안 로그와 오류 처리(V16)의 L1·L2 항목을 하나하나 모두 판정한다. Level 3는 위험이 큰 7개 항목만 골라 채택한다. 요구사항 원문은 OWASP ASVS `v5.0.0_release` 태그의 `0x22-V13-Configuration.md`, `0x24-V15-Secure-Coding-and-Architecture.md`, `0x25-V16-Security-Logging-and-Error-Handling.md`와 대조했다(2026-10-13). V14와 V13·V15·V16의 운영 진단 행은 같은 태그의 `0x23-V14-Data-Protection.md`와 함께 다시 대조했다(2026-10-20, ADR-0070). V3는 OWASP ASVS 저장소 `v5.0.0` 태그의 V3 원문과 대조했다(2026-10-15). 요구사항 요약은 2026-10-23에 ID마다 원문 기준 한 문장으로 맞춰, 다른 추적 표의 같은 ID와 같은 문장이다(ADR-0087 결정 30). 기능별 추적 표의 V3 행이 '공통'으로 미룬 응답 헤더·출처 검사·린트는 이 표가 판정한다. 쿠키(브라우저가 사이트별로 저장했다가 요청마다 함께 보내는 작은 값)의 이름과 속성은 [계정·인증 추적 표](auth.md)가 판정한다.
- **아키텍처 설계 근거**: [docs/devops.md](../../devops.md), [ADR-0054](../../adr/0054-delivery-pipeline-change-freeze-and-safe-deploys.md), [docs/infra.md](../../infra.md) §4.1·§7·§9, [docs/architecture.md](../../architecture.md) §4·§6.3, [ADR-0008](../../adr/0008-client-specific-thin-gateways.md), [docs/security/secrets-and-keys.md](../secrets-and-keys.md), [docs/observability.md](../../observability.md) §5·§9, [ADR-0070](../../adr/0070-incident-response-evidence-probes-timeouts-throughput-soak.md), [docs/security/data-classification.md](../data-classification.md)
- **문서 상태 및 일정**: 항목 선정을 마쳤고 구현 직전 단계다(2026-10-13에 세움, ADR-0054 반영. 2026-10-20 운영 진단 반영, ADR-0070. 같은 날 git flow 가지 규칙과 릴리스 봇 권한 반영, ADR-0074). 공용 워크플로·보안 검사 게이트·가지 규칙 검사·릴리스 워크플로(wbs 0.1.2·0.1.4), 마이그레이션 실행기(0.3.4), 운영 진단 기본값(0.3.6), GitOps·입장 정책·접근 통제(0.4.4), 진단 증거 저장소·증거 수집기(4.1.1), 변경 동결 달력(4.4.3), 프런트엔드 배포(2.10.4), CloudFront 배포와 응답 헤더 정책(2.11.2)을 구현할 때 테스트 결과를 채운다.

**작성 및 판독 가이드**

- **적용 여부**: 적용, 부분 적용, 미적용 중 하나로 적는다.
- **구현 위치**: 예정 위치를 적는다.
  - `.github/workflows/`: `peaket` 안의 재사용 워크플로(ADR-0169), (`ci-node`, `security-scan`, `build-image`, `migration-check`, `contract-check`, `iac-check`, `gitops-check`, `promote`, `branch-policy`, `merge-tree`, `release`, `docs-check`, `tools-check`, `build-remote`). 모노레포(코드 전부를 저장소 하나에 폴더로 나눠 담는 방식) `peaket`의 `ci.yml`이 모든 PR에서 돌며 이것들을 같은 저장소 안 경로(`./.github/workflows/…`)로 부르고, 바뀐 범위의 잡만 돌린다(ADR-0165 결정 3, ADR-0169). 판단은 CI가 부르는 점검 스크립트 `tools/ci/`가 하고 시험이 함께 있다. 지금 있는 것은 `ci.yml`, `docs-check`, `tools-check`, `iac-check`(형식·정적 검증만), `branch-policy`, `merge-tree`다(2026-10-31, R-202)
  - `deploy/`(`peaket` 안의 배포 상태, ADR-0169): Kyverno(쿠버네티스에 들어오는 설정을 규칙으로 검사하는 도구) 정책, ArgoCD AppProject·ApplicationSet, 공용 Helm 차트, 변경 동결 달력 파일, Envoy Gateway(요청을 받아 안쪽 서비스로 넘기는 프록시 서버를 바탕으로 한 게이트웨이) 공통 정책(보안 응답 헤더, 다른 주소에서 온 요청을 브라우저가 허용할지 정하는 CORS 규칙, 출처 검사)과 라우트
  - `infra/`: `peaket`의 Terraform 폴더. AWS 계정·조직 정책·IAM(OIDC 로그인 표준으로 받는 역할, Identity Center 권한 세트), GitHub 조직 설정, CloudFront(AWS의 CDN) 배포와 응답 헤더 정책
  - `apps/`·`packages/config`: `peaket`의 화면 쪽 폴더. 공용 ESLint 설정(`packages/config`), 앱(web·partner·관제 콘솔·스캐너 PWA)의 화면 보안 헤더 값(`apps/`)
  - `packages/platform`: `peaket`의 서버 공용 패키지. 마이그레이션 실행기, OpenFeature 감싸개, 공용 린트·Semgrep 규칙, HTTP 클라이언트 기본값, 공용 시작 코드(컨테이너 상태를 주기적으로 묻는 검사인 프로브 세 종류, 진단 주석 수집, Node 실행 옵션, DB·Redis 시간 초과 기본값). 서비스 시작 코드의 네 신호 계측·Problem 필터·남은 시간 전파·시작 설정 검사·관리 포트는 2026-11-01에 생겼다(openspec 변경 `add-service-template`, wbs 0.3.1 ①). 같은 날 정규 로그 줄·로그 가명·가림 규칙·OTel SDK 시작·외부 호출 클라이언트(추적 헤더 없음, 리디렉트 안 따름)·V-T31 ③ 탐침이 더해졌다(openspec 변경 `add-service-logging`, wbs 0.3.1 ②)
  - `freeze-calendar`: 변경 동결 달력과 자동 중단(플랫폼 네임스페이스)
  - `evidence-collector`: 경보 웹훅(일이 생기면 상대 서버가 우리 주소를 불러 알려 주는 방식)을 받아 DB·Redis(메모리에 데이터를 두는 빠른 저장소)의 순간 상태를 진단 증거 저장소에 올리는 증거 수집기(플랫폼 네임스페이스)
- **테스트 결과**: 손으로 적지 않는다. CI(코드를 올릴 때마다 자동으로 검사하고 빌드하는 과정) 테스트에 붙은 `[ASVS v5.0.0-x.y.z]` 태그를 읽어 만든 리포트로 갱신한다. 태그를 붙일 수 있는 검사는 자동 시험, 정적 정책 검사(conftest·Kyverno 정책 시험 등), doc-check 규칙, 설정 검사다. 운영 설계로만 있는 행은 결과를 '설계 검사'로 적고, 운영을 띄우지 않는 동안은 통과로 세지 않는다(docs/architecture.md §8.2 4, 추천 적용 2026-10-28, 기술 검토 낮음-089).
- **미적용 사유 분류**: 해당 없음, 나중 Phase로 미룸, 위험 수용(아키텍처 결정과 그 이유를 남기는 ADR 작성 필수)으로 나눈다.

## V3 웹 프런트엔드 보안(V3.2 의도치 않은 해석, V3.3 쿠키, V3.4 브라우저 보안 헤더, V3.5 브라우저 출처 분리, V3.7 기타 브라우저 보안)

응답 보안 헤더는 두 곳에서 붙인다. CloudFront를 거치는 응답(파일 저장소 S3를 원본으로 하는 정적 자산과 대기열 파일 포함)에는 배포·캐시(자주 쓰는 값을 가까운 곳에 복사해 둔 것) 동작마다 단 응답 헤더 정책이 붙인다. 게이트웨이 응답에는, CloudFront를 거치지 않는 `gw-scanner`를 포함해, 게이트웨이 공통 정책(architecture §4 '공통 인프라 정책')이 붙인다. 응답 헤더 정책에서 원본 값 재정의를 끄면, 원본이 보낸 헤더는 그대로 두고 원본에 없을 때만 정책의 값을 붙인다(CloudFront 응답 헤더 정책 문서, 2026-10-15 확인). 그래서 화면마다 다른 CSP(페이지가 실행할 수 있는 스크립트의 출처를 정하는 브라우저 규칙)·Referrer-Policy는 앱이 보내고, 모든 응답에 같아야 하는 HSTS와 `nosniff`는 정책 값으로 덮어쓴다.
