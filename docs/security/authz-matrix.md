# 권한 표: 데이터·칸 단위 접근 규칙과 검사 위치

- **독자와 용도**: 게이트웨이(클라이언트 종류별로 앞에 둔 입구 서버로, 인증·공통 정책·안쪽 서비스로 넘기기를 맡는다) 정책, 서비스 공통 인가 가드(peaket-platform), 각 서비스의 데이터 조회 계층을 만드는 엔지니어와 보안 검토자가 읽는다. 어떤 역할이 어떤 데이터에, 어떤 칸까지, 어떤 상태와 시간에 닿는지와, 그 검사를 어느 층에서 하는지 확인할 때 참조한다.
- **원문 출처**: 원문에 없다. 전체가 [보완]이다.
- **기준 기획 버전**: v1.0.
- **정본 관계**: 역할 × 기능 권한(누가 어떤 기능을 조회·생성·수정·삭제·최종 승인하는가)의 정본은 planning/03 §3 '권한 매트릭스'다. 이 문서는 그 표를 옮겨 적지 않는다. 이 문서는 그 표의 칸에 붙는 조건(어느 데이터, 어느 칸, 어떤 상태와 시간), 검사 위치, 기본 거부, 재인증·2인 승인과의 묶음, 테넌트를 넘는 접근 시험의 정본이다(ASVS v5.0.0-8.1.1·8.1.2). 운영 명령의 역할과 승인 요건은 POL-021 B(planning/03 §1.1), 승인 업무는 POL-038과 docs/features/transfer-refund.md §3.2·§7, 결제자·보유자 조건은 transfer-refund §3.1, 관리 계정 로그인과 잠금은 docs/security/auth-controls.md가 정본이다. 기능마다 어느 응답 칸을 빼는지는 각 기능의 ASVS 추적 표 8.x 행이 정본이고, 이 문서 §4가 묶어 가리킨다. 이 문서에서 새로 정한 판단에는 '(추천 적용 2026-10-30)'을 붙였다.
- **관련 ID**: FR-021, FR-026, FR-027, FR-028, FR-046, FR-057, FR-058, FR-064 · POL-019, POL-020, POL-021, POL-023, POL-031, POL-038, POL-039, POL-045 · SCR-045, SCR-046, SCR-064, SCR-066 · ADR-0008, ADR-0011, ADR-0046, ADR-0050, ADR-0051, ADR-0062, ADR-0082, ADR-0083, ADR-0095, ADR-0102, ADR-0123, ADR-0149 · ASVS v5.0.0-8.1.1·8.1.2·8.2.1·8.2.2·8.2.3·8.3.1·8.4.1 · 시험 AZ-T1~AZ-T13, I-T19, I-T25, I-T44, J-T10, A-T13.
- **원문으로 확인한 외부 문서(2026-10-30)**: OWASP ASVS 5.0.0 V8(저장소 `v5.0.0` 태그의 `0x17-V8-Authorization.md`), Envoy Gateway의 JWT 클레임 인가 안내(https://gateway.envoyproxy.io/docs/tasks/security/jwt-claim-authorization/ )와 API 문서(https://gateway.envoyproxy.io/docs/api/extension_types/ ), PostgreSQL 18 문서의 행 보안 정책(https://www.postgresql.org/docs/18/ddl-rowsecurity.html )과 설정 함수(https://www.postgresql.org/docs/18/functions-admin.html ).

## 1. 이 문서가 맡는 것

ASVS(웹 보안 기준을 만드는 비영리 단체 OWASP가 만든 웹 앱 보안 검증 항목 목록) 8.1.1은 호출자의 권한과 자원 속성에 따라 기능 수준과 데이터 수준의 접근을 제한하는 규칙을 문서에 정하라고 한다. 8.1.2는 같은 기준으로 칸(필드) 수준의 읽기·쓰기를 제한하는 규칙을 정하라고 한다(ASVS 5.0.0 원문, 2026-10-30 확인). 기능 수준 규칙은 planning/03 §3에 이미 있다. 이 문서는 나머지를 맡는다.

| 묻는 것 | 정본 |
| --- | --- |
| 이 역할이 이 기능을 할 수 있는가 | planning/03 §3(운영 명령은 §1.1) |
| 어느 데이터에 할 수 있는가(본인, 소속 테넌트, 배정 회차, 지정) | 이 문서 §3.2~§3.4·§3.7 |
| 어떤 상태·시간에 할 수 있는가 | 이 문서 §3.5·§3.6이 묶고, 조건 자체는 각 기능 정본(transfer-refund §3.1 등) |
| 어느 칸을 보고 쓸 수 있는가 | 이 문서 §4가 묶고, 기능별 세부는 각 ASVS 추적 표 8.1.2·8.2.3 행 |
| 어디서 검사하는가 | 이 문서 §5 |
| 재인증과 2인 승인이 붙는가 | 이 문서 §6(요소와 인원의 정본은 identity §6·POL-021·POL-038) |
| 테넌트를 넘지 못하는지 어떻게 시험하는가 | 이 문서 §7 |

## 2. 기본 원칙

1. **기본 거부**: 허용 규칙이 없는 경로·기능·데이터·칸은 막는다. 게이트웨이는 허용 규칙이 없는 경로를 넘기지 않고(§5.1), 서비스는 허용 역할을 적지 않은 처리기를 띄우지 않으며(§5.2), DB는 테넌트 값이 없는 파트너 요청에 행을 보이지 않는다(§5.3). 응답은 허용 목록에 있는 칸만 내보내고, 요청은 허용 목록에 있는 칸만 받는다(§4).
2. **신원 값은 세션에서만 읽는다**: 계정·역할·테넌트·회차·사람 식별값(pid)은 게이트웨이가 검증한 토큰(권한이나 상태를 증명하려고 주고받는 서명된 문자열)에서 만든 내부 헤더에서만 읽는다. 경로·쿼리·본문에 같은 값이 와도 판정에 쓰지 않는다. 경로의 자원 ID는 그 신원 값의 범위 안에서 찾는 열쇠로만 쓴다.
3. **두 번 검사한다**: 게이트웨이는 토큰 대상과 역할을 거칠게 보고, 서비스가 자원 속성(소유, 테넌트, 상태, 시간)을 자세히 본다. 게이트웨이는 DB를 보지 않으므로(ADR-0008 결정 4) 자원 검사는 서비스의 몫이다. 화면에서 버튼을 숨기거나 끄는 것은 안내일 뿐 통제로 세지 않는다(ASVS 8.3.1).
4. **없는 것처럼 답한다**: 권한이 없는 비공개 자원은 없는 자원과 같게 404로 답한다. 공개 자원(예: 관람 후기)을 남이 고치려 하거나 기능 권한이 없으면 403으로 답한다. 지금 정본의 예와 같다(catalog-review.md 8.2.2의 후기 403·본인확인 결과 404, support.md 8.2.2의 문의 404, settlement J-T10의 정산서 404). 스캐너의 다른 회차는 회차 ID가 공개 값이라 403이다(offline-gate.md 8.2.2).
5. **원래 요청자의 권한으로 판정한다**: 서비스가 서비스 계정으로 다른 저장소를 읽을 때도 요청한 사람의 역할·테넌트·회차 범위로 좁힌다(ASVS 8.3.3, analytics.md·forensic-replay.md 8.3.3 행).
6. **권한이 바뀌면 바로 반영한다**: 역할이나 테넌트가 바뀌면 그 계정의 세션을 끝내고(§5.4), 위험 작업의 재인증 토큰은 발급할 때 DB의 지금 역할을 다시 본다(§6). 현장 스태프는 요청마다 배정 상태를 본다(ADR-0051 결정 4).
7. **거절도 남긴다**: 인가로 거절한 403과, 테넌트·소유 조건으로 찾지 못한 404는 보안 이벤트로 남긴다(사유 코드, 계정, 경로 틀. 개인정보 원문은 넣지 않는다). 한 계정의 거절이 10분에 20건 [가정]을 넘으면 SEV3(장애 심각도 등급으로, 숫자가 작을수록 심각하다)로 알린다(추천 적용 2026-10-30). 남의 ID를 넣어 보는 공격을 일찍 보려는 것이다.

## 3. 데이터 단위 규칙

자원의 속성으로 거르는 규칙이다. 각 행의 '판정 식'은 서비스가 조회 조건으로 쓰는 식이고, 검사 위치의 자세한 내용은 §5에 있다.

### 3.1 호출자의 신원 값

| 호출자 | 역할 값 | 판정에 쓰는 신원 값 | 토큰 대상(`aud`)·게이트웨이 |
| --- | --- | --- | --- |
| 팬 | 역할 없음. 본인확인을 마친 계정에만 구매 권한 `ticket:buy` | 계정 ID(`sub`), 세션 ID(`sid`), 사람 식별값 `pid`(전환 기간에는 옛 pid도, identity §5) | `fan`, gw-fan·gw-queue |
| 파트너 관리 계정 | `partner_admin`, `partner_member` | 계정 ID, 세션 ID, 역할 `role`, 테넌트 `tid`(= `promoter_id`) | `partner`, gw-partner |
| 관제 관리 계정 | `viewer`, `operator`, `commander`, `cs_agent`, `cs_lead` | 계정 ID, 세션 ID, 역할 `role` | `ops`, gw-ops |
| 현장 스태프 | `gate_staff`, `gate_lead`(대리 승인은 `gate_staff`로 낮춘다) | 스태프 계정 ID, 회차, 역할, 기기 키 지문 `cnf.jkt`(identity §6.1) | `scanner`, gw-scanner |
| 시스템 | 서비스 계정 | 서비스 메시(서비스끼리 주고받는 통신을 앱 대신 처리하는 층)의 신원(서비스 이름, ADR-0082) | 내부 gRPC(서비스끼리 함수를 부르듯 빠르게 호출하는 통신 방식) |

- **관리 토큰에 역할과 테넌트를 싣는다(추천 적용 2026-10-30)**: 관리 계정 액세스 토큰에 `role`(문자열 하나)과, 파트너 토큰에는 `tid`를 싣는다. identity §3의 클레임 목록과 내부 헤더 목록에 2026-10-30 더했다. 게이트웨이가 경로마다 역할을 보려면(ADR-0008 결정 3 '인가') 토큰에 역할이 있어야 하기 때문이다. 게이트웨이 제품 Envoy Gateway(Envoy 프록시를 쿠버네티스, 곧 컨테이너로 만든 앱을 여러 서버에서 실행하고 관리하는 플랫폼의 게이트웨이로 쓰게 하는 제품)의 클레임 → 헤더 변환은 문자열·정수·실수·참거짓 클레임만 받고 배열은 받지 않으므로(Envoy Gateway API(프로그램끼리 요청과 응답을 주고받는 창구) 문서, 2026-10-30 확인), 역할은 배열이 아니라 하나다. 관리 계정의 역할도 하나다(docs/data.md `admin_account.role`).
- **지정은 토큰에 싣지 않는다(추천 적용 2026-10-30)**: 가명정보 취급자와 접속기록 점검자는 commander에게 붙는 지정이다(planning/03 §3 관리 계정 행). 토큰에 싣지 않고, ops-svc가 요청마다 identity의 지정 기록을 본다(캐시 5초 [가정]). 그래서 지정을 거두면 다음 요청부터 막힌다.
- 게이트웨이는 바깥 요청에 붙은 같은 이름의 내부 헤더를 먼저 지우고 검증 결과로 다시 쓴다(identity §3 '게이트웨이 무상태 고속 검증', ASVS 4.1.3). 내부 헤더는 `X-User-Id`, `X-Session-Id`, `X-User-Pid`, `X-User-Pid-Prev`에 `X-User-Role`, `X-Tenant-Id`를 더한다(추천 적용 2026-10-30).

### 3.3 파트너 테넌트

테넌트 격리(여러 고객의 데이터와 자원이 서로 보이거나 섞이지 않게 나누는 일)의 판정 식은 하나다: `자원.promoter_id = X-Tenant-Id`.

- **테넌트 값의 출처**: 파트너 토큰의 `tid`를 게이트웨이가 `X-Tenant-Id`로 옮긴 값만 쓴다(§3.1). 경로·쿼리·본문의 `promoterId`는 무시하거나 400으로 거절한다(catalog-review.md 8.2.3의 '템플릿에서 만들기의 `promoter_id`'와 같다).
- **하위 자원**: 회차·공연 이미지·좌석맵 배치본·현장 스태프 배정·예매자 명단·판매 요약처럼 부모를 거치는 자원은 부모의 `promoter_id`로 판정한다. 회차 행에는 검사용 사본이 있다(docs/data.md `event.promoter_id` '테넌트 검사용 사본').
- **테넌트 표**: docs/data.md에서 `promoter_id`를 가진 표는 `production`, `event`, `venue`(배치본), `promoter_contract`, `seller_profile_change`, `event_cancellation_request`, `product`, `merch_order`, `webhook_endpoint`, `scanner_device`, `settlement_statement`, `partner_receivable`이다. 분석 저장소에서는 골드의 회차 행이 `promoter_id`를 가진다(analytics.md 8.4.1).
- **파트너 관리자만 하는 일**: planning/03 §3에서 '관리자'가 붙은 칸은 `role = partner_admin`일 때만 통과한다. 파트너사마다 활성 관리자가 1명 이상 남아야 한다(identity §6, I-T44).
- **모든 파트너가 읽는 공용 자료**: 좌석맵 템플릿은 공용 읽기 전용 자료라 테넌트 조건이 없다. 쓰는 경로는 없다(catalog-review.md 8.4.1, ADR-0066).
- **관제 역할**: 관제 역할은 테넌트를 가리지 않고 본다(전체 운영). 대신 §4의 칸 규칙이 걸리고, 바꾸는 작업은 §6의 재인증·승인과 감사 기록이 걸린다.

### 3.6 시간 창

- 시간 조건(예매 취소는 공연 시작 전, 양도 요청은 양도 마감 전, 수락·돌려주기·회수는 입장 시작 전, 후기는 공연 종료 예정 시각 뒤, 결제사 지정은 온세일 윈도우 밖, 판매 종료는 공연 시작 24시간 전)의 정본은 각 기능 문서와 planning/03 §3이다.
- 판정은 서버 시각으로만 한다. 요청에 실린 시각은 쓰지 않는다.
- 상태와 시간은 그 자원의 행 잠금(`SELECT … FOR UPDATE`) 안에서 다시 확인한다. 양도·취소·회수·스캔 수신이 한 티켓에서 겹쳐도 하나만 성공한다(transfer-refund §3.1).

### 4.2 쓰는 칸

- 서버가 정하는 칸(상태, 소유 계정, 테넌트, 작성자, 시각, 계산한 금액, 판)은 요청 본문에서 받지 않는다. 요청 스키마(데이터의 구조 정의)는 허용한 칸만 두고(`additionalProperties: false`), 그 밖의 칸이 오면 400으로 거절한다(support.md·catalog-review.md 8.2.3과 같다).
- 역할에 따라 쓸 수 있는 칸이 다른 곳은 그 기능의 ASVS 추적 표 8.2.3 행이 정본이다. 예: 후기는 별점·본문·사진만, 홈 구성의 `updatedBy`·`updatedAt`은 읽기 전용, 판매 승인 뒤 재승인 대상 항목은 `partner_admin`만.

### 4.3 가린 값을 여는 절차

1. 화면은 가린 값(예: 휴대폰 번호 가운데 자리)을 먼저 보인다.
2. 원문이 필요하면 열람 사유를 넣는다. 서버는 사유가 없는 원문 요청을 거절한다.
3. 원문 열람과 사유, 대량 내려받기의 건수는 관리 계정 접속기록으로 남고(POL-023, NFR-017), 접속기록 정기 점검(FR-064)의 대상이 된다.
4. 예매자 명단 내려받기는 여기에 패스키 재인증이 더해진다(§6).

### 5.1 게이트웨이(ADR-0008)

- 게이트웨이는 클라이언트별로 다섯이다(gw-queue, gw-fan, gw-partner, gw-ops, gw-scanner). 각자 자기 대상의 서명 키만 믿으므로, 다른 대상의 토큰은 역할과 상관없이 401이다(I-T19, I-T36).
- 경로마다 허용하는 대상·역할·`scope`를 Envoy Gateway `SecurityPolicy`의 `authorization` 규칙으로 적는다. `defaultAction`은 `Deny`로 적는다. Envoy Gateway는 이 값을 적지 않아도 기본이 `Deny`이고, 규칙은 처음 맞는 것이 이긴다(API 문서, 2026-10-30 확인). 그래도 읽는 사람이 헷갈리지 않게 적는다(추천 적용 2026-10-30).
- 공개 경로(로그인 없이 부르는 경로)는 따로 묶은 경로 정의에 두고, docs/api/openapi.yaml의 공개 표시(`security: []`)와 같은 목록으로 맞춘다.
- 게이트웨이가 보지 않는 것: 자원의 소유·테넌트·상태·시간. DB와 공유 캐시를 보지 않는 것이 게이트웨이의 원칙이다(ADR-0008 결정 4).
- **역할 목록을 한곳에 두기(제안)**: 작업마다 허용 역할을 openapi 확장 칸(예: `x-peaket-roles`)으로 적고, 게이트웨이 정책과 서비스 가드의 시험을 이 칸에서 만든다. 공개가 아닌 작업에 이 칸이 없으면 doc-check가 오류를 낸다. openapi와 doc-check는 통합 담당이 고친다(추천 적용 2026-10-30).

### 5.2 서비스

- **역할 가드**: 공통 가드 `RolesGuard`(asvs/auth.md 8.2.1)는 처리기마다 허용 역할을 적게 한다. 허용 역할을 적지 않은 처리기가 있으면 서비스가 시작하지 않는다. 이를 시험 하나로 확인한다(AZ-T1).
- **범위가 든 조회 계층**: 데이터 조회 함수는 범위 값(본인 계정 묶음, 테넌트, 회차, 지정)을 인자로 받고, 그 값은 요청 맥락(게이트웨이 헤더)에서만 만든다. 범위 없이 테넌트 표나 개인 데이터를 읽는 함수는 일괄 작업 모듈에만 둔다(추천 적용 2026-10-30). Drizzle(조건까지 타입 검사되는 SQL형 쿼리 도구)의 타입으로 범위 인자를 빠뜨리지 못하게 한다.
- **상태·시간**: 행 잠금 안에서 다시 확인한다(§3.6).
- **2인 승인과 재인증**: §6.

### 5.3 DB

- **테넌트 표의 행 보안 정책(추천 적용 2026-10-30)**: 파트너 요청 경로는 그 서비스의 파트너 전용 DB 사용자로 접속한다. §3.3의 테넌트 표에는 PostgreSQL의 행 보안 정책(RLS: 표의 행마다 누가 보고 바꿀 수 있는지 DB가 거르는 규칙)을 켜고, 이 사용자에게는 `promoter_id = current_setting('app.tenant_id', true)::uuid`인 행만 보이게 한다. 파트너 요청을 처리하는 트랜잭션(여러 변경을 한꺼번에 반영하거나 한꺼번에 취소하는 작업 단위)은 첫 문장으로 `SET LOCAL app.tenant_id = <X-Tenant-Id>`를 건다. `SET LOCAL`은 그 트랜잭션에만 걸리므로 PgBouncer(DB 연결을 모아 여러 요청이 나눠 쓰게 하는 도구)의 트랜잭션 풀링에서도 다음 요청에 남지 않는다(ADR-0083 결정 3과 같은 방식).
  - 값을 걸지 않으면 `current_setting(…, true)`가 NULL을 돌려주어 아무 행도 보이지 않는다(PostgreSQL 문서, 2026-10-30 확인).
  - 행 보안을 켠 표에 맞는 정책이 없으면 기본 거부라 아무 행도 보이지 않는다. 표 소유자와 `BYPASSRLS` 사용자는 정책을 건너뛴다(PostgreSQL 문서, 2026-10-30 확인). 그래서 앱 사용자는 표 소유자가 아니게 두고, 팬·관제 경로의 사용자에게는 전체를 보는 정책을 따로 둔다. 정산 계산 같은 일괄 작업은 테넌트를 넘는 일이라 그 사용자로 돈다.
  - 왜 두는가: 조회 계층(§5.2)이 1차이고 행 보안은 2차다. 쿼리 하나에서 테넌트 조건이 빠져도 다른 파트너의 행이 나오지 않게 하려는 것이다.
  - 비용과 확인: 파트너 요청은 핫패스(요청이 가장 많이 지나는 경로)가 아니다. PgBouncer 풀은 DB 사용자마다 따로 생기므로 파트너 전용 사용자만큼 풀이 하나 늘어난다. 쿼리 계획이 바뀌지 않는지와 `SET LOCAL` 비용은 wbs 3.6.1에서 잰다 [가정].
- **요청자 ≠ 승인자**: 운영 명령은 `command_actor`의 유일 제약이 같은 사람의 두 번 승인과 요청자 본인 승인을 막는다(ADR-0149 결정 2).
- **P1 칸**: 비밀번호·TOTP 시드·연계정보 같은 P1 칸은 그 항목을 맡은 서비스의 파드에 준 권한으로만 읽는다(data-classification '보호 등급 분류 체계').
- **분석 저장소**: ClickHouse(대량 이벤트 집계에 강한 분석용 데이터베이스)는 읽는 주체마다 사용자를 나누고, 파트너 조회의 테넌트 필터는 서버가 강제한다(analytics §11).

### 5.4 권한 변경의 반영(추천 적용 2026-10-30)

- 관리 계정의 역할을 바꾸거나 거두거나, 파트너 계정의 테넌트가 바뀌거나, 계정을 지우면 identity가 그 계정의 모든 세션을 끝낸다. 세션 종료 이벤트(`control.sessions-terminated`)로 모든 파드가 수 초 안에 그 세션을 거절한다(identity §3, ADR-0103). 종료 사유 값 `ROLE_CHANGED`는 2026-10-30 docs/api/asyncapi.yaml `SessionTerminated.reason`에 더했다.
- 그래서 옛 역할이 든 액세스 토큰(15분)이 남아도 세션 종료 목록이 막는다. 이벤트가 늦으면 최대 15분 통할 수 있는 것은 identity §3·§10의 남는 한계와 같다. 위험 작업은 재인증 토큰을 받을 때 DB의 지금 역할을 다시 보므로 이 틈에도 막힌다(§6).
- 자기 역할은 바꾸지 못한다. commander 역할의 부여·회수는 2인이다(planning/03 §3, POL-038 ⑨).

- 재인증 토큰은 5분 동안 한 번 쓴다(`typ` reauth+jwt, `X-Reauth-Token`, docs/api/guidelines.md §7). 패스키가 필요한 작업에 `factors`에 passkey가 없으면 403 `reauth-required`다(identity §6, I-T53).
- **재인증 토큰을 세션과 작업 묶음에 묶는다(추천 적용 2026-10-30)**: 토큰에 그 세션(`sid`)과 작업 묶음 `act`(운영 명령, 승인 업무, 권한 변경, 정산 계좌, 명단 내려받기, 팬 민감 작업)을 싣는다. 받는 서비스는 요청의 세션·작업 묶음과 같은지 본다. 정산 계좌를 바꾸려고 받은 토큰을 5분 안에 명단 내려받기에 쓰지 못하게 하려는 것이다. identity §3('재인증 토큰의 묶음')·§6('위험 운영 명령 재인증')에 2026-10-30 더했다.
- identity는 재인증 토큰을 줄 때 DB의 지금 역할과 잠금 상태를 다시 본다. 역할을 거둔 직후나 보호 잠금 중에는 토큰을 주지 않는다(auth-controls.md §3.2).
- 2인 승인의 두 사람은 서로 다른 관리 계정이고 둘 다 재인증한다. 승인자의 역할은 승인하는 때의 DB 역할로 본다.

## 8. 남는 위험

- 게이트웨이와 허용된 내부 파드는 내부 헤더를 쓸 수 있다. 운영 설계에서는 메시 신원과 허용 정책으로 줄이지만, 메시 없는 포트폴리오 실행에서는 허용된 파드가 뚫리면 헤더를 꾸밀 수 있다(identity §3의 남는 한계와 같다). 행 보안 정책(§5.3)은 꾸민 테넌트 값까지는 막지 못한다.
- 세션 종료 이벤트가 늦으면 옛 역할의 토큰이 최대 15분 통한다. 위험 작업은 재인증 때 DB 역할을 다시 보므로 막히지만, 조회는 그동안 옛 권한으로 될 수 있다.
- 일괄 작업 사용자는 행 보안 정책을 건너뛴다. 이 사용자는 파트너 요청 경로에서 쓰지 않고, 쓰는 모듈을 코드 검토로 묶는다.
- 칸 규칙은 응답 허용 목록이 지킨다. 허용 목록에 칸을 잘못 더하면 그대로 나간다. AZ-T8과 응답 스키마 검토로 줄인다.
- 파트너 관리자가 정당하게 내려받은 예매자 명단을 밖에서 잘못 쓰는 것은 막지 못한다. 사유·건수 기록과 월 점검(FR-064)으로 사후에 찾는다.

## 9. 미결정·[가정]

- 관리 토큰의 `role`·`tid` 클레임과 내부 헤더 `X-User-Role`·`X-Tenant-Id`, 재인증 토큰의 `sid`·`act`, 역할이 바뀌면 세션을 끝내는 규칙은 identity §3·§6에 2026-10-30 더했다. 같은 날 docs/api/asyncapi.yaml에 세션 종료 사유 `ROLE_CHANGED`가, docs/api/openapi.yaml의 관리 계정 쿠키 설명(`partnerCookie`·`opsCookie`)에 `role`·`tid` 클레임과 내부 헤더가 들어갔다.
- openapi 작업별 허용 역할 칸(§5.1)과 doc-check 규칙은 통합 담당이 정한다. 들어가기 전까지는 게이트웨이 정책 파일과 planning/03 §3을 사람이 맞춘다.
- 행 보안 정책의 비용과 쿼리 계획은 wbs 3.6.1에서 잰다. 쿼리 계획이 나빠지거나 `SET LOCAL` 비용이 파트너 요청 p95(요청 백 건 중 아흔다섯 건이 이 시간 안에 끝난다는 뜻)를 10% [가정] 넘게 늘리면 조회 계층만 두는 안으로 돌아가고, 그 결정을 ADR(아키텍처 결정과 그 이유를 남긴 기록)로 남긴다.
- 지정 기록은 identity DB의 표 `admin_designation`(지정 종류, 지정한 사람, 해제 시각)에 둔다(docs/data.md §2 ①, 2026-10-30 더함). ops-svc가 요청마다 묻는 호출은 identity.proto 초안 `AdminDesignationService.GetAdminDesignations`다(ops-svc 신원만, 캐시 5초 [가정]. 답이 없으면 지정이 없는 것으로 보고 403, 추천 적용 2026-10-30, docs/api/proto/README.md §3).
- 인가 거절 경보 기준(10분에 20건)과 지정 확인 캐시(5초)는 [가정, wbs 3.6.1에서 확정]이다.
