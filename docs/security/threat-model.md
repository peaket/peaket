# 위협 모델: 신뢰 경계별 STRIDE

- **독자와 용도**: 기능을 설계·구현하는 엔지니어와 보안 검토자가, 데이터가 신뢰 경계(믿는 정도가 다른 두 구역 사이의 선)를 넘는 곳마다 어떤 공격을 생각했고 어디서 막으며 무엇이 남는지 볼 때 참조한다. ASVS 추적 표(웹 보안 기준을 만드는 비영리 단체 OWASP의 웹 앱 보안 검증 항목 목록 ASVS 5.0.0을 기능별로 판정한 표, `docs/security/asvs/`)의 v5.0.0-13.1.4 '위협 모델에 따라' 판정이 이 문서를 근거로 삼는다.
- **범위**: [docs/infra.md](../infra.md) §2 데이터 흐름도의 경계 0~5와, 그 그림에 없는 전달 경로(코드가 저장소에서 운영 클러스터까지 가는 길, [docs/devops.md](../devops.md) §3~§5)다. 운영 설계 기준으로 쓰고, 포트폴리오 실행(로컬·CI·데모)이 다른 곳은 그 행에 적는다.
- **방법**: STRIDE로 경계마다 위협을 여섯 갈래로 나눠 빠진 것이 없는지 본다. S는 위장(남인 척하기), T는 변조(데이터를 몰래 바꾸기), R은 부인(한 일을 안 했다고 우기기), I는 정보 노출, D는 서비스 거부(서비스를 못 쓰게 만들기), E는 권한 상승(받지 않은 권한 얻기)이다. 표마다 '대응'에는 정본의 장치와 그것을 판정한 ASVS 행이나 절을, '남는 위험'에는 대응이 막지 못하는 것을 적는다. 막는 것과 남는 것을 함께 적고, 완전히 막는다고 쓰지 않는다.
- **문서 상태**: 2026-10-28에 처음 썼다(추천 적용 2026-10-28, 기술 검토 중간-065). 새 기능의 ASVS 추적 표를 쓸 때(docs/architecture.md §8.2), 신뢰 경계나 외부 연동이 바뀌는 ADR을 쓸 때, 분기마다 [가정] 다시 본다. 경계를 새로 만들면 표를 더한다.

## 1. 경계 지도

| 경계 | 무엇이 있나 | 들어오는 것을 얼마나 믿나 |
| --- | --- | --- |
| 0. 사용자 기기 | 브라우저·PWA(설치형 앱처럼 쓰는 웹 앱), 게이트 스캐너 | 믿지 않는다. 모든 입력을 서버가 다시 검증한다 |
| 1. 엣지 | CDN(사용자 가까운 곳에 파일을 복사해 두고 대신 응답하는 전송망) CloudFront, WAF(악성 요청을 걸러 내는 웹 방화벽), 엣지 함수 | 바깥 요청을 받는 첫 관문. 캐시와 정적 응답만 스스로 판단한다 |
| 2. 게이트웨이 | 클라이언트 종류별 입구 서버 `gw-fan`·`gw-queue`·`gw-partner`·`gw-ops`·`gw-scanner` | 토큰을 검증한 요청만 안으로 넘긴다. 넘기는 내부 헤더는 게이트웨이가 다시 쓴다 |
| 3. 서비스 메시 | 업무 서비스와 작업자. 서비스 메시(서비스끼리의 통신을 앱 대신 처리하는 층, 운영 설계는 Istio 앰비언트)가 서로 인증서를 확인하는 암호화 통신 mTLS로 감싼다 | 메시 신원으로 '어느 서비스가 불렀나'를 안다. 사용자 권한은 앱이 따로 본다 |
| 4. 데이터 저장소 | Aurora(PostgreSQL), Redis 셋, Kafka(MSK), ClickHouse, 접속기록 저장소, 감사 로그 | 서비스별 사용자로만 붙는다. 저장은 KMS(암호 키를 보관하고 대신 써 주는 클라우드 서비스)로 암호화한다 |
| 5. 외부 | 결제사(토스페이먼츠·포트원), 본인확인 기관, 소셜 로그인 제공자, 사람 확인(Turnstile), 발송 대행, 파트너 웹훅 수신처, 공연예술통합전산망(KOPIS), 신고기관·수사기관 | 계약한 상대지만 우리 통제 밖이다. 받은 결과는 서명이나 조회 API로 다시 확인한다 |
| 전달 경로 | GitHub Actions, 이미지 레지스트리(운영 ECR, 포트폴리오 GHCR), Sigstore, GitOps 저장소, ArgoCD, 클러스터 입장 정책 Kyverno | 서명과 출처 증명(어느 커밋을 어떤 빌드가 만들었는지 서명한 기록)이 맞는 산출물만 클러스터에 들인다 |

## 2. 경계 0: 사용자 기기

| 갈래 | 위협 | 대응(위치) | 남는 위험 |
| --- | --- | --- | --- |
| S | 남의 세션 쿠키·입장 토큰을 훔쳐 그 사람인 척한다 | 쿠키는 `HttpOnly`·`Secure`·`SameSite=Strict`와 이름 접두사(docs/features/identity.md §3, asvs/auth.md V3·V7). 구매 세션 쓰기는 기기에서 만든 키로 요청에 서명해야 받는다(소지 증명, ADR-0050 결정 8). 입장 토큰은 처음 쓸 때 한 구매 세션에 묶인다(docs/api/guidelines.md §7) | 화면에 스크립트를 끼워 넣는 공격(XSS)이 성공하면, 키를 꺼내지는 못해도 그 화면 안에서 요청을 보낼 수는 있다. CSP(페이지가 실행할 스크립트의 출처를 정하는 브라우저 규칙)와 출력 규칙(docs/frontend.md §5.14)으로 줄인다 |
| S | 위조 스캐너가 입장을 처리한다 | 스캐너는 관리 기기에 등록한 기기 키의 DPoP 증명(요청마다 그 키로 서명, RFC 9449)과 그 키에 묶인 현장 스태프 토큰을 함께 쓴다. 하드웨어 키가 필요한 운영 환경은 mTLS 기기 인증서가 선택지다(ADR-0051, asvs/offline-gate.md, 기술 검토 중간-057) | 기기를 통째로 빼앗기면 기기가 폐기될 때까지 쓸 수 있다. 기기 키는 소프트웨어 키라 루팅 기기에서 옮길 수 있다. 배정 해제, 요청마다 하는 기기 상태 확인과 즉시 폐기로 줄인다 |
| T | 브라우저에 둔 대기표·순번·도착 시각을 고쳐 앞줄로 간다 | 순번과 대기표·도착 시각 쿠키는 서버나 엣지 함수가 서명하고(secrets-and-keys '대기표 서명 키'·'도착 시각 쿠키 서명 키'), 입장 확정 때 서버가 다시 확인한다(docs/features/queue-admission.md) | 정상 기기 여러 대로 줄을 여러 번 서는 것은 1인 1순번(ADR-0056)과 봇 방어가 줄일 뿐 모두 잡지는 못한다 |
| R | 결제·양도·취소를 하고 나서 안 했다고 한다 | 법정 접속기록(로그인·진입·주문·결제, POL-025)과 주문·결제 원장, 동의 기록(docs/security/data-classification.md) | 기기를 함께 쓰는 가족처럼 같은 계정 안의 다른 사람은 가리지 못한다 |
| I | 공용 PC나 잃어버린 기기에서 개인 데이터가 보인다 | 로그아웃 정리 루틴과 탭 사이 알림(docs/frontend.md §5.14.4), 저장 허용 목록(§3.12), 월렛에는 표시 값만 둔다 | 로그아웃하지 않은 공용 PC와 월렛에 기본으로 남기는 입장 키(asvs/offline-gate.md 14.3.1 위험 수용) |
| D | 봇이 대기열·좌석 요청을 쏟아 사람이 못 들어온다 | 사람 확인과 사전 검증, 1인 1순번, 레이트 리밋, CDN 정적 대기 파일(ADR-0039, asvs/bot-defense.md V2.4) | 사람과 구별되지 않는 봇은 남는다. 오탐·미탐 비율은 측정으로만 안다(ADR-0112) |
| E | 브라우저에서 숨은 관리 기능이나 남의 주문 ID를 불러 권한 밖 데이터를 본다 | 서버가 역할·스코프와 소유자를 확인한다(남의 ID를 넣어 보는 IDOR 막기, asvs/auth.md V8, docs/architecture.md §8.1 A01) | 소유자 확인을 빠뜨린 새 API. 기능별 ASVS 표의 V8 행과 계약 시험으로 줄인다 |

## 3. 경계 1: 엣지

| 갈래 | 위협 | 대응(위치) | 남는 위험 |
| --- | --- | --- | --- |
| S | 원본 서버 주소로 바로 요청해 CDN·WAF를 건너뛴다 | 원본 NLB는 사설 서브넷의 CloudFront VPC 원본이라 공인 주소가 없고, CloudFront 서비스 관리 보안 그룹에서 오는 연결만 받으며, 게이트웨이가 원본 확인 헤더를 한 번 더 본다(ADR-0053 결정 9와 상태 줄, docs/infra.md §9, 추천 적용 2026-10-28, 기술 검토 낮음-009). 스캐너 경로는 CloudFront를 거치지 않고 기기 키 DPoP 증명으로 받는다(mTLS는 운영 선택지, 기술 검토 중간-057) | 원본 확인 헤더 값이 새면 우회할 수 있다. 값을 정기적으로 바꾼다(secrets-and-keys 'CloudFront 원본 확인 헤더 값') |
| T | 캐시를 오염시키거나 개인 응답을 캐시에 남기게 한다(웹 캐시 기만) | 경로별 캐시 정책과 정규화한 캐시 키, 인증이 필요한 경로는 `no-store`(docs/api/guidelines.md §9, asvs/catalog-review.md 14.2.5) | 새 경로에 캐시 정책을 잘못 붙이는 실수. 경로별 정책을 코드로 두고 검토한다 |
| R | 엣지에서 막은 요청을 나중에 따질 근거가 없다 | CloudFront·WAF 로그를 남긴다(docs/infra.md §9) | 엣지 로그에는 사람 식별값이 없어 계정 단위로 잇지 못한다 |
| I | 캐시된 대기 파일·셔플 결과에서 다른 사람의 정보가 보인다 | 대기 파일과 셔플 결과는 쿠키 없이 내고 사람을 알 수 없는 값만 싣는다(docs/api/guidelines.md §9) | 순번 구간 같은 공개 값으로 대기 규모는 알 수 있다(의도한 공개) |
| D | 대량 요청(DDoS)이나 캐시를 피하는 요청으로 원본을 쓰러뜨린다 | AWS Shield Standard, WAF 속도 규칙, 대기열 파일 캐시와 대체 원본(docs/infra.md §4.1·§9) | 캐시 키를 계속 바꾸는 요청은 원본까지 간다. 캐시 키에 넣는 값을 허용 목록으로 묶어 줄인다 |
| E | 엣지 함수의 서명 키를 얻어 도착 시각·최초 방문 쿠키를 지어낸다 | 서명 키는 Secrets Manager에 두고 엣지 함수 배포에만 넣는다(secrets-and-keys) | 엣지 함수 코드나 키가 새면 그 회차의 줄 순서가 흔들린다. 키 교체 절차로 줄인다 |

## 4. 경계 2: 게이트웨이

| 갈래 | 위협 | 대응(위치) | 남는 위험 |
| --- | --- | --- | --- |
| S | 위조하거나 다른 대상의 토큰(JWT, 서명된 정보 묶음 형식의 토큰)을 낸다 | ES256 서명·만료·`typ`·`iss`·`aud`를 검증하고 게이트웨이마다 자기 대상의 키만 믿는다(ADR-0050 결정 9, docs/features/identity.md §3, asvs/auth.md V9) | 서명 키가 새면 위조 토큰이 통한다. 키는 KMS에 두고 교체 절차를 둔다(§9) |
| T | 바깥에서 `X-User-Id` 같은 내부 헤더나 추적 헤더(`traceparent`·`baggage`)를 넣어 신원이나 추적을 조작한다 | 게이트웨이가 바깥 헤더를 지우고 다시 쓴다(asvs/frontend.md·catalog-review.md 4.1.3). 추적 문맥은 라우팅·추적 전에 지우고 새 trace를 시작한다(docs/observability.md §6 '신뢰 경계의 추적 문맥', 기술 검토 중간-066) | 게이트웨이 설정 실수로 헤더 정리가 빠지는 것. 정책 시험과 V-T31로 줄인다 |
| R | 요청을 보내고 나서 안 보냈다고 한다 | 게이트웨이 접근 로그가 법정 접속기록이 되고, 잃지 않는 갈래로 따로 보낸다(docs/observability.md §7, 기술 검토 높음-21) | 기록은 '그 세션이 보냈다'까지만 증명한다 |
| I | 오류 응답에 내부 정보(스택, 내부 주소)가 나온다 | 오류는 Problem 형식(RFC 9457)으로만 답하고 스택을 숨긴다(docs/api/guidelines.md §2, 각 ASVS 표 V16.5) | 업무 오류 문구가 존재 여부를 흘리는 경우(예: 가입 여부). 문구 키 검토로 줄인다 |
| D | 요청 폭주로 게이트웨이나 뒤쪽 서비스가 멈춘다 | 로컬 레이트 리밋, 동시 요청·대기 큐 상한과 503 + `Retry-After`, 경로별 시간 초과(ADR-0009, docs/architecture.md §5) | 정상 사용자도 503을 받는다. 대기열이 앞에서 들어오는 수를 줄인다 |
| E | 다른 사이트가 사용자 몰래 쓰기 요청을 보내게 한다(CSRF) | 쿠키로 인증하는 쓰기 요청의 `Origin` 확인(없거나 다르면 403, Envoy Gateway 내장 CSRF 필터, ADR-0065 결정 5, 기술 검토 낮음-139, asvs 각 표 3.5.1) | 사전 요청 없는 T=0 두 호출은 본문의 사전 검증 토큰에 기댄다(docs/api/guidelines.md §9) |

## 5. 경계 3: 서비스 메시(내부)

| 갈래 | 위협 | 대응(위치) | 남는 위험 |
| --- | --- | --- | --- |
| S | 한 서비스가 다른 서비스인 척하거나, 게이트웨이를 건너뛰고 서비스 포트를 직접 부른다 | 메시 전체 STRICT mTLS(ADR-0082)와 포트별 허용 표: 업무 gRPC(서비스끼리 함수를 부르듯 호출하는 통신 방식)는 웨이포인트(서비스마다 둔 요청 단위 대리인)만, REST는 그 경로의 게이트웨이만, 내부 포트는 정한 신원만(docs/architecture.md §5, D-T36, 기술 검토 중간-071) | 포트폴리오 실행은 메시가 없어 신원 대신 파드 라벨로 거른다(NetworkPolicy, docs/verification.md §5.1) |
| T | 메시 안에서 운영 명령이나 원장을 몰래 바꾼다 | 운영 명령은 감사 체인(키를 건 해시 체인, 5분 앵커)과 공개 체크포인트로 고치면 드러나게 한다(ADR-0053·0075). 비상 런북은 서로 다른 두 운영자의 KMS 서명이 있어야 돈다(ADR-0053 결정 11) | 드러나게 할 뿐 고치는 순간을 막지는 못한다. 1시간 대조와 경보로 늦게라도 찾는다 |
| R | 운영자가 명령을 내리고 나서 부인한다 | 명령마다 요청자·승인자·재인증·서명이 감사 로그에 남는다(docs/features/control-tower.md, asvs/delivery.md V16) | 한 사람이 두 역할을 하는 1인 기간에는 2인 승인이 형식에 그친다(docs/devops.md §15) |
| I | 로그·요청 기록·Baggage(서비스 사이로 함께 전파하는 이름표 값)에 개인정보가 섞여 나간다 | 로그·추적에는 키를 건 가명 참조값만 쓴다(ADR-0053 결정 1, docs/observability.md §7). 외부 호출에는 Baggage·추적 헤더를 싣지 않는다(docs/observability.md §6) | 개발자가 새 필드에 원문을 넣는 실수. 공용 로거의 마스킹과 리뷰로 줄인다 |
| D | 한 서비스의 장애나 느림이 다른 서비스로 번진다 | 서킷 브레이커와 벌크헤드, 재시도 예산, 시간 초과 기본값(ADR-0009·0070, docs/architecture.md §5) | 공유 저장소(같은 Aurora 클러스터)가 느려지면 묶인 서비스가 함께 느려진다 |
| E | 탈취한 파드가 그 파드에 없는 권한(다른 서비스의 DB, AWS 자원)을 쓴다 | 서비스별 DB 사용자와 Pod Identity(파드에 주는 AWS 권한) 최소 권한(docs/security/secrets-and-keys.md 관리 규칙 1). 꾸민 이미지로 터질 수 있는 이미지 디코딩은 DB 자격 증명이 없는 `image-worker`에서만 한다(asvs/catalog-review.md 15.2.5, 기술 검토 중간-068) | 탈취한 파드는 자기 권한 안의 일은 할 수 있다. 권한을 서비스 단위로 더 쪼개지는 않는다 |

## 6. 경계 4: 데이터 저장소

| 갈래 | 위협 | 대응(위치) | 남는 위험 |

| T | 사람이 운영 DB에서 원장을 직접 고친다 | 사람이 운영 DB에 직접 쓰는 길은 두지 않는다. 쓰기는 마이그레이션과 작업으로만 하고, 긴급 조회는 SSM 세션·IAM DB 인증·pgAudit 기록으로 하며 월 점검 대상이다(docs/devops.md §10.3). 앱은 데이터를 읽고 쓰는 DML 역할만, 표 구조를 바꾸는 DDL은 마이그레이션 역할만 한다(asvs/delivery.md 13.2.2) | 마이그레이션·작업 코드를 거친 잘못된 변경은 들어갈 수 있다. 코드 검토·N-1 시험과 불변식 검사(RB-36)로 찾는다 |
| R | 관리 계정이 개인정보를 열람·내려받고 부인한다 | 관리 계정 접속기록과 내려받기 사유를 남기고 월 1회 점검한다(FR-064, data-classification 법률 #20) | 점검은 사후 확인이라 열람 자체는 막지 못한다 |
| I | 백업·스냅샷이 새거나, 지운 개인정보가 백업에 오래 남는다 | 저장소와 백업은 KMS로 암호화하고 백업 역할만 읽는다. 백업 보존 상한을 두고 복원하면 파기를 다시 적용한다(data-classification '백업 보존 상한과 파기', 기술 검토 중간-070) | 상한(최대 35일) 동안은 백업에 남는다. 그 법적 기준은 확인 필요(POL-027)다 |

| E | 앱 사용자가 표 구조를 바꾸거나 다른 서비스 DB를 읽는다 | 논리 DB와 역할을 서비스마다 나누고 DDL은 마이그레이션 역할만 가진다(docs/devops.md §7.2) | 같은 클러스터를 쓰는 서비스는 클러스터 장애를 함께 겪는다 |
