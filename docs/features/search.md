# 기능 설계: 검색(자동완성·검색 결과·관련 공연)

- **독자와 용도**: 소비자 웹의 검색을 구현하는 엔지니어와 QA가 함께 보는 문서다. 다루는 것은 다음과 같다.
  - 머리 검색창의 자동완성(입력하는 동안 아래에 뜨는 공연·아티스트·공연장 후보)
  - 검색 결과 화면(SCR-003)의 결과·필터·정렬·쪽·결과 0건 처리, 관련 공연
  - 한글 입력 처리(조합 중 글자, 초성, 한/영 키 실수, 띄어쓰기, 다른 이름)
  - 검색 대상과 갱신, 검색 포트(엔진을 바꿔 끼울 수 있게 정한 이음매)와 엔진을 바꿀 조건
  - 구현하는 쪽은 core-svc catalog 모듈, gw-fan, CDN 캐시 정책, 소비자 웹(머리 검색창·`/search` 화면)이다.
- **원문 출처**: 원문 설계서는 공연명·아티스트 검색과 pg_trgm(3글자 조각 비교) 인덱스만 적었다. 화면은 2026-10-14 소유자 피드백(ADR-0063)에서, 이 문서의 설계는 2026-10-27 소유자 요청과 결정(ADR-0093·ADR-0094)에서 나왔다. 전체가 [보완]이다.
- **기준 기획 버전**: v1.0.
- **관련 ID**: FR-003 · NFR-028 · POL-043, 045 · SCR-001, 002, 003, 068 · CMP-004, 072 · API(프로그램끼리 요청과 응답을 주고받는 창구) `GET /v1/search`, `GET /v1/search/suggestions` · ADR-0063, 0081, 0083, 0086, 0093, 0094 · 보안 추적 표 [docs/security/asvs/catalog-review.md](../security/asvs/catalog-review.md)

## 1. 기능 셋과 이름

| 이름 | 무엇인가 | 어디에 |
| --- | --- | --- |
| 자동완성 | 머리 검색창에 입력하는 동안 아래 창에 뜨는 공연·아티스트·공연장 후보다. 영문 표기는 `search_suggestion`이다 | 전역 머리 검색창(CMP-004 search), §4 |
| 최근 검색어 | 입력하기 전에 검색창을 누르면 보이는, 이 기기에서 찾은 검색어다. 서버로 보내지 않는다 | 같은 창, docs/frontend.md §3.12 |
| 검색 결과 | 공연 하나가 한 줄인 목록과 필터·정렬·페이지 번호다 | SCR-003, §5 |
| 관련 공연 | 검색어와 맞은 아티스트·공연장의 다른 공연, 결과가 없을 때의 오픈 예정 인기 공연이다. 카탈로그 관계로만 고른다 | SCR-003 결과 아래, §6 |
| 연관 검색어 | 다른 사람들이 이어서 찾은 검색어를 검색 기록으로 만드는 기능이다. **지금은 없다**(ADR-0094 결정 2). 넣게 되면 그 기능만 이 이름으로 부른다 | — |

- 개인화와 유료 노출은 없다. 같은 검색은 누구에게나 같은 결과다(POL-045).
- 머리 검색창은 굿즈를 찾지 않는다. 굿즈는 굿즈 스토어 안에서 찾는다(docs/review/open-items.md 36번).

## 2. 대상과 데이터

### 2.1 대상

- 판매 승인된 공연과 그 공연의 아티스트·공연장, 그리고 그 셋의 다른 이름(별칭)이다(ADR-0093). 승인 전·반려된 공연, 판매 중지된 공연(docs/planning/03 §2.14), 회차가 모두 취소된 공연은 검색·자동완성 어디에도 나오지 않는다.
- 공연은 같은 파트너가 같은 공연장에서 같은 배치본으로 여는 회차의 묶음이다. 결과 한 줄은 공연이고, 누르면 대표 회차의 상세(`/events/[id]`)로 간다(대표 회차 규칙은 ADR-0093 결정 8).
- 다른 이름: 공연의 다른 이름은 파트너가 등록 때 5개 [가정]까지 적고, 운영자도 고친다(`PUT /v1/ops/productions/{productionId}/aliases`, 사유 필수, 감사 로그. 판매 승인 뒤에도 고치고 재승인 대상이 아니다, 2026-11-02 정합 점검, docs/api/openapi.yaml, core.proto `SetProductionAliases`). 아티스트·공연장의 다른 이름은 운영자가 판매 승인 화면(SCR-048)에서 더하고 지운다(사유 필수, 감사 로그). 예: 공연장 'KSPO DOME'의 다른 이름 '올림픽체조경기장'(2018년 리모델링 뒤 바뀐 이름이고 옛 이름도 계속 쓰인다, 위키백과 2026-10-27 확인), 공연 '루멘 콘서트 2026 서울'의 다른 이름 'LUMEN CONCERT 2026 SEOUL'.

### 2.2 검색 읽기 모델

카탈로그 표(`production`·`event`·`artist`·`place`·`search_alias`, docs/data.md §2)를 검색에 맞게 미리 모아 둔 사본 표(읽기 모델) 둘, 지운 줄을 적는 작은 표 하나, 판 번호 하나다. 모두 core 논리 DB 안이고, 카탈로그를 바꾸는 같은 트랜잭션에서 고친다.

2026-11-12 1차 구현(BAT-165, ADR-0268)은 `search_document`를 사본 표가 아니라 뷰로 둔다. `production`·`event`·`place`·`artist`·`production_artist`·`search_alias`·`production_image`·`wish`를 모아 항상 지금 값을 보여 주므로, 카탈로그를 바꾸는 트랜잭션이 읽기 모델을 따로 고치지 않아도 된다. `search_term`·`search_removal`·`search_version`은 위 표 모양으로 자리만 잡고, 사전 확장·증분 읽기는 후속 배치가 쓴다. 공연 수가 늘어 뷰 스캔이 느려지면 materialized view·증분 동기화로 바꾼다.

| 표 | 한 줄 | 칸 |
| --- | --- | --- |
| `search_document` | 공연 하나 | 공연 ID, 공연명, 장르, 공연장 ID·이름, 아티스트 ID 목록, 포스터 키, 공연 기간(첫 회차 시작·마지막 회차 종료), 대표 회차 ID, 다음 오픈 시각과 그 회차 ID, 판매 상태, 판매 종료(마지막 회차), 최저가, 배지(대표 회차의 판매 방식), 관심도와 그 근거(오픈 알림 신청 수 또는 최근 7일 확정 판매 매수), 바꾼 판 |
| `search_term` | 이름 하나 | 종류(공연명·아티스트·공연장), 대상 ID, 화면 이름, 다른 이름이면 원래 이름, 정규화한 값, 띄어쓰기 없앤 값, 낱자, 초성, 바꾼 판 |
| `search_removal` | 지운 줄 하나(추천 적용 2026-10-28, 기술 검토 중간-089) | 종류(공연 줄·이름 줄), 대상 ID(공연 ID 또는 `search_term` ID), 지운 판, 지운 시각 |
| `search_version` | 한 줄 | 판 번호. 위 세 표를 바꾸는 트랜잭션마다 1 올린다 |

- 지운 표시: 읽기 모델에서 줄을 지우는 트랜잭션(판매 승인 취소·회차 전부 취소로 공연이 빠질 때, 다른 이름을 지울 때, 이름이 바뀌어 옛 이름 줄이 없어질 때)은 같은 트랜잭션에서 `search_removal`에 (종류, 대상 ID, 판)을 적는다. 지운 줄은 '판 뒤에 바뀐 줄' 조회에 나오지 않으므로, 자동완성 사전은 이 표로 지운 것을 안다(§2.3). 검색 질의는 이 표를 읽지 않는다. 지운 줄은 읽기 모델에 남지 않기 때문이다. 하루 [가정] 지난 표시는 1분 정리 작업이 지운다.

- 관심도는 하루 한 번(장르별 랭킹과 같은 때, docs/features/analytics.md §8.5) 판매 매수를, 1시간 [가정]마다 오픈 알림 신청 수를 다시 센다. 오픈 전 공연은 다음 오픈 회차의 신청 수, 그 밖은 최근 7일 확정 판매 매수를 쓴다.
- 판매 상태·대표 회차·다음 오픈은 회차의 오픈·판매 종료 시각이 지날 때 바뀐다. 1분 [가정]마다 도는 정리 작업이 시각이 지난 공연만 다시 계산한다.
- 인덱스: 띄어쓰기 없앤 값·낱자·초성에 앞부분 일치용 B-tree 인덱스(`text_pattern_ops`)를 둔다. 중간 일치는 행이 수만 개라 훑기로 하고, NFR-028을 넘으면 두 글자 조각 인덱스(pg_bigm, Aurora PostgreSQL 18.3~18.6 지원, ADR-0086)를 먼저 넣는다.
- DB 설정: DB를 만들 때 문자 분류 설정(LC_CTYPE)을 C·POSIX로 두지 않는다. 그 설정에서는 조각 비교 확장이 한글을 단어 글자로 보지 않는다(PostgreSQL 18 소스 `ts_locale.c`). 조각 비교 확장을 넣으면 `show_trgm('루멘')`이나 `show_bigm('루멘')`이 비지 않는지 시험한다(SR-T7).

### 2.3 갱신과 내리기

- 자동완성 사전은 core-svc 파드(서버 실행 단위)마다 메모리에 둔다(§4.4). 10초 [가정]마다 `search_version`을 읽고, 바뀌었으면 그 판 뒤에 바뀐 줄과 그 판 뒤에 적힌 지운 표시(§2.2 `search_removal`)를 함께 읽는다. 판 순서대로 반영하고, 같은 판 안에서는 지운 표시를 먼저 반영한다. 판·바뀐 줄·지운 표시는 같은 읽기 전용 복제본에 붙은 한 연결의 한 읽기 전용 트랜잭션(`REPEATABLE READ`, 한 스냅숏)에서, 판을 먼저 읽는다. 판을 쓰기 인스턴스에서, 줄을 복제본에서 읽으면 복제가 늦은 만큼 줄을 놓치기 때문이다. PostgreSQL 18은 복제본에서 직렬화 격리만 막고 `REPEATABLE READ`는 받는다(PostgreSQL 18 문서 '핫 스탠바이', 2026-10-28 확인). Aurora 읽기 전용 복제본에서도 같은지는 SR-T15에서 확인한다. 처음 뜰 때, 판이 1,000 [가정] 넘게 뛰었을 때, 마지막 갱신이 1시간 [가정]보다 오래됐을 때는 통째로 읽는다. 지운 표시는 하루만 남기 때문이다(추천 적용 2026-10-28, 기술 검토 중간-089).
- 판매 승인·재승인 반영·회차 추가·회차 취소·공연 정보 변경·다른 이름 변경·판매 승인 취소(판매 중지, 다시 열면 판매 재개. docs/planning/03 §2.14, ADR-0123)가 모두 같은 트랜잭션으로 읽기 모델을 고친다. 승인 취소와 회차 전부 취소로 공연이 빠지면, 그 트랜잭션이 끝난 뒤 CDN의 검색 경로를 비운다(CloudFront 무효화 경로 `/v1/search*`. 끝의 `*`가 모든 검색어 변형과 자동완성 경로를 덮는다, AWS 문서 2026-10-27 확인). 홈 캐시 무효화와 같은 작업에서 부른다.
- 검색 질의는 공유 Aurora 클러스터의 읽기 전용 복제본(Reader)으로 보낸다. 복제가 늦는 시간(보통 1초 아래 [가정])만큼 빠진 공연이 더 보일 수 있다. 법적 이유처럼 바로 빼야 할 때도 이 지연과 CDN 무효화 시간 안에서 빠진다. 자동완성 사전에서는 지운 표시 덕분에 다음 판 확인(10초 [가정]) 한 번 안에 빠진다(SR-T15).

## 3. 한글 입력 처리

### 3.1 정규화

정규화 함수 하나를 브라우저와 서버가 같은 코드(`packages/search-normalize`, 2026-11-09 만들었다, ADR-0242)로 쓴다. 차례는 다음과 같다.

1. 유니코드 NFKC(전각 'ＬＵＭＥＮ' → 'LUMEN', 호환 문자를 표준 문자로). 바로 이어 첫소리·가운뎃소리·끝소리 자모(U+1100~U+11FF)를 호환 자모(U+3131~U+318E. 입력기가 만드는 'ㄱ'·'ㅏ' 같은 낱자)로 되돌린다(고정 표, 추천 적용 2026-10-28, 기술 검토 높음-25)
2. 소문자
3. 제로폭 문자(보이지 않는 공백 문자)와 보이지 않는 한글 채움 문자(U+115F·U+1160·U+3164) 지움
4. 안쪽 연속 공백을 하나로
5. 앞뒤 공백 지움

결과가 캐시 키와 비교의 출발점이다.

- 1단계에서 자모를 되돌리는 이유: NFKC는 호환 자모를 첫소리·가운뎃소리·끝소리 자모로 바꾼다. 초성만 친 'ㄹㅁ'(U+3139·U+3141)은 U+1105·U+1106이 되고, 'ㄳ'(U+3133)은 끝소리 U+11AA가 된다. 그러면 es-hangul `canBeChoseong`(호환 자모 목록만 본다)이 'ㄹㅁ'을 초성으로 보지 않는다. `disassemble`도 이 자모를 풀지 않아, 낱자만 친 입력('ㄹ'·'ㄳ')이 저장된 낱자 키(호환 자모)와 앞부분이 맞지 않는다. 브라우저와 서버가 같은 함수를 쓰므로 공유 시험(SR-T1)은 통과하고 초성 시험(SR-T3)에서만 드러난다(Python 3·Node.js v24.18.0 계산, es-hangul 2.4.0 소스, 2026-10-28 확인).
- 되돌리는 표는 호환 자모 94자를 하나씩 NFKC로 바꾼 값의 역표다. 94자의 결과는 서로 겹치지 않아 표가 하나로 정해진다. 반각 한글('ﾡ' U+FFA1)과 동그라미·괄호 한글('㉠')도 NFKC를 거치면 같은 자모가 되므로 이 표로 호환 자모가 된다. 표에 없는 옛 자모는 그대로 둔다.
- NFKC는 따로 친 자음과 모음('ㄱ'·'ㅏ')을 음절('가')로 합치기도 한다. 낱자로 풀면 같은 값이라 비교 결과는 같다.
- 서버는 받은 값을 다시 정규화한다. 그래서 정규화는 두 번 해도 결과가 같아야 하고, SR-T1이 이것도 본다.
- 같은 내용 차단 지문(docs/data.md `content_fingerprint`)은 저장할 때와 비교할 때 모두 같은 NFKC를 쓰므로 이 되돌리기를 더하지 않는다.

비교에는 다음 세 값을 더 만든다.

- 띄어쓰기 없앤 값: '루멘 콘서트' → '루멘콘서트'
- 낱자: 한글 음절을 호환 자모로 풀고 겹받침·겹모음도 푼다('값' → 'ㄱㅏㅂㅅ'). 토스가 공개한 es-hangul(MIT, 2.4.0)의 `disassemble`을 쓴다(2026-10-27 확인). 유니코드 NFD로 풀면 받침 ㅁ(U+11B7)과 첫소리 ㅁ(U+1106)이 다른 문자라, 조합 중인 '룸'이 '루멘'의 앞부분과 맞지 않는다(계산 확인). 그래서 NFD를 쓰지 않는다.
- 초성: 음절마다 첫소리만 모은 값(`getChoseong`, '루멘' → 'ㄹㅁ')

| --- | --- | --- | --- |
| ① | 늘 | 정규화한 값과 띄어쓰기 없앤 값 | '루멘콘서트' → '루멘 콘서트 2026 서울' |
| ② | 늘 | 입력의 낱자가 이름 낱자의 앞부분(이름 전체 또는 낱말) | 조합 중 '룸'(ㄹㅜㅁ) → '루멘'(ㄹㅜㅁㅔㄴ) |
| ③ | 입력이 초성만일 때 | 초성 앞부분 | 'ㄹㅁ' → '루멘' |
| ④ | 입력이 로마자만이고 ①~③의 결과가 0건일 때 | 한/영 변환 값(`convertQwertyToHangul`)으로 ①~③을 다시 | 'fnaps' → '루멘'. 화면은 "'루멘'으로 찾은 결과입니다 · 'fnaps'로 찾기"를 보인다 |

- ③의 '초성만'은 정규화한 입력을 낱자로 푼 값(공백 제외)이 모두 초성이 될 수 있는 자모(es-hangul `canBeChoseong`)일 때다. 그래서 겹자음 한 글자('ㄳ' → 'ㄱㅅ')도 초성으로 본다. 이어 친 자음을 겹자음 한 글자로 합치는 입력기가 있는지는 확인 필요다(wbs 2.10.1 입력기 시험). 모음이 하나라도 섞이면('ㄹㅏ', '루ㅁ') 초성이 아니고 ②로 찾는다(추천 적용 2026-10-28, 기술 검토 높음-25).
- 'LUMEN'처럼 로마자 이름이 실제로 맞으면 ④를 하지 않는다.
- 검색 결과 요청에 `noConvert=true`가 있으면 ④를 하지 않는다. 바꿔 찾은 결과 위의 '{입력}(으)로 찾기'가 원래 값으로 찾을 때 쓴다(추천 적용 2026-11-05, HOT-312).
- 오타('루맨')는 질의에서 받지 않는다. 결과가 0건일 때 비슷한 이름 하나를 제안한다(§5.5).

### 3.3 길이와 특수 문자

- 자동완성은 정규화한 입력에 한글 음절이 하나라도 있으면 1자부터, 로마자·숫자·낱자만이면 2자부터 보낸다 [가정]. 한글 한 음절은 영문 한 글자보다 정보가 많다(예: 가수 '비'). 이보다 짧으면 서버는 400 `query-too-short`다. 검색 결과는 0자(필터만)도 받는다. 최대는 둘 다 50자다.
- LIKE 패턴에 사용자 값을 넣을 때는 `\`·`%`·`_`를 이스케이프하고 `ESCAPE '\'`를 쓴다. 바인드 변수로 넘겨도 LIKE 안에서 `%`·`_`는 '아무 글자'로 동작하기 때문이다. 정규식은 쓰지 않는다(ReDoS 방지, catalog-review 1.3.12).

### 3.4 한글 입력기와 키보드

- keydown에서 `isComposing`이 참이거나 `keyCode`가 229면 Enter·↑↓·Esc를 처리하지 않는다. MDN은 조합(한글 입력기가 글자를 만드는 중)에 속한 keydown을 이렇게 거르라고 권하고, 마지막 글자를 끝내는 키에서는 `isComposing`이 거짓이어도 `keyCode`가 229일 수 있다고 적는다(2026-10-27 확인). 거르지 않으면 덜 끝난 글자로 검색하거나 Enter가 두 번 처리된다.
- 조합 중에도 입력 값이 바뀌면(`input` 사건) 자동완성은 보낸다. §3.2 ②가 조합 중 글자를 받쳐 준다.
- 입력 요소: `type="search"`, `enterkeyhint="search"`, `autocomplete="off"`, `autocapitalize="off"`, `spellcheck="false"`. 바깥은 `<form role="search">`다.

## 4. 자동완성

### 4.1 후보와 순서

- 후보는 이름(공연명·아티스트·공연장과 그 다른 이름)이다. 공연 후보는 기본 범위(§5.1)의 공연만, 아티스트·공연장 후보는 기본 범위의 공연이 하나 이상 있을 때만 낸다.
- 일치 등급: 정확히 같음 > 이름 앞부분 > 낱말 앞부분 > 중간 일치. 중간 일치는 입력이 두 음절 이상일 때만 본다.
- 순서: 일치 등급 → 판매 상태(판매 중·오픈 예정 > 매진) → 관심도 → 이름 가나다순 → ID.
- 종류별 몫: 공연 5·아티스트 2·공연장 1 [가정]. 빈 몫은 다른 종류로 채워 모두 8개 [가정]까지다. 한 대상의 이름과 다른 이름이 함께 맞으면 그 대상은 한 번만 나온다(더 높은 등급으로).

### 4.2 일치 표시

서버가 화면 이름 위의 일치 위치(`matches`, UTF-16 위치와 길이)를 준다. 화면은 그 부분만 굵게 하고 글자 노드로 그린다(HTML로 넣지 않는다).

| 맞은 방식 | 굵게 할 부분 |
| --- | --- |
| 글자 그대로 | 맞은 글자 |
| 낱자(조합 중) | 입력 낱자가 걸친 음절('룸' → '루멘'의 '루멘') |
| 초성 | 초성이 맞은 음절 |
| 띄어쓰기 없앤 값 | 맞은 글자(사이 공백 포함) |
| 다른 이름 | 원래 이름에서 대응하는 부분. 대응이 없으면 이름 전체('루멘' → 'LUMEN 콘서트 2026 서울'의 'LUMEN'은 파트너가 적은 짝으로 안다) |

### 4.3 응답

`GET /v1/search/suggestions?q=`의 응답(openapi `SuggestResult`)은 정규화한 입력과 후보 목록이다. 후보는 종류(`PRODUCTION`·`ARTIST`·`PLACE`), 화면 이름, 일치 위치를 갖고, 종류에 따라 다음을 더한다.

- 공연: 공연 ID, 대표 회차 ID, 작은 포스터, 다음 오픈 일시, 판매 상태. 고르면 대표 회차 상세로 간다.
- 아티스트: 아티스트 ID. 고르면 `/search?artistId=`로 간다.
- 공연장: 공연장 ID. 고르면 `/search?placeId=`로 간다.

### 4.4 메모리 사전

- core-svc 파드마다 둔다. `search_term`과 카드에 필요한 `search_document` 값만 싣는다. 공연 1~2만 개면 몇 MB다(어림).
- 구조: ① 낱자 키를 정렬한 배열(이름 앞부분을 이분 탐색) ② 낱말마다의 낱자 키(낱말 앞부분) ③ 음절 두 글자 조각의 역색인(중간 일치, 입력이 두 음절 이상일 때). 한 요청이 사전 전체를 훑지 않게 한다.
- 비슷한 이름 제안(§5.5)도 이 사전에서 한다. 초성 첫 글자가 같고 낱자 길이가 ±2 안인 이름만 낱자 단위 편집 거리(글자를 넣고 빼고 바꾸는 최소 횟수)로 견준다. 거리 기준은 '낱자 길이 ÷ 4, 최소 1' [가정]이고 골든 세트로 정한다.
- DB와 Redis를 부르지 않는다. 지금까지의 Redis 키 `cat:suggest`는 없앤다.

### 4.5 브라우저

- 정규화한 값으로 요청한다. 매개변수는 정해진 순서로 싣고 기본값은 싣지 않는다. CloudFront는 매개변수의 순서나 대소문자만 달라도 다른 캐시로 보기 때문이다(AWS 문서 2026-10-27 확인).
- 입력이 멈추고 0.3초 [가정] 뒤 보낸다. 입력이 바뀌면 앞 요청을 취소한다(`AbortController`). 응답이 늦게 와도 지금 입력과 다르면 버린다.
- 받은 후보가 8개보다 적으면, 그 입력으로 시작하는 더 긴 입력은 받은 후보 안에서 거르고 다시 요청하지 않는다. 다만 아래를 모두 지킬 때만 거른다. 입력이 길어져도 후보가 줄기만 한다는 전제가 이때만 맞기 때문이다(추천 적용 2026-10-28, 기술 검토 낮음-036).
  - 앞선 입력이 이미 두 글자(한글은 두 음절) 이상이다. 중간 일치는 두 음절부터 켜지므로(§4.1), '루'에서 받은 목록에는 '루멘'에서 새로 생기는 중간 일치('빛나는루멘' 같은 이름)가 없다.
  - 입력 종류(초성만·한글·로마자)가 앞선 입력과 같다. 'ㄹㅁ'(초성 비교, §3.2 ③)에서 'ㄹㅁㅏ'(낱자 비교)로 넘어가면 비교 방식이 바뀐다.
  - 거른 결과가 0건이 아니다. 0건이면 다시 요청한다. 로마자 입력이 길어져 로마자 이름과 더는 맞지 않으면, 서버는 한/영 변환 값으로 다시 찾기 때문이다(§3.2 ④).
- 실패하면 창을 띄우지 않는다(catalog-review 16.5.2).
- 접근성: ARIA combobox 패턴(docs/design/d5 §5.3, CMP-004)과 후보 수가 바뀔 때 `aria-live="polite"`로 한 번 알리기는 그대로다.

### 4.6 운영 원칙

- 후보는 판매 승인된 카탈로그와 운영자가 확인한 다른 이름에서만 만든다. 사람들의 검색 기록으로 만들지 않는다. 국내 포털은 사생활 침해·명예훼손·개인정보 노출·욕설·자동화된 수단 같은 이유로 자동완성 제외 요청 창구를 따로 운영한다(네이버 검색어 고객센터 2026-10-27 확인). PEAKET은 후보를 기록으로 만들지 않아 그런 요청이 생길 길을 좁힌다.
- 다른 이름이 문제가 되면 운영자가 지운다. 지우는 트랜잭션이 지운 표시를 남기므로(§2.2) 다음 판 확인(10초 [가정]) 때 사전에서 빠지고, CDN 캐시(60초 [가정])가 지나면 화면에서도 빠진다. 급하면 검색 경로 무효화를 함께 부른다.

## 5. 검색 결과

### 5.1 범위

- 기본: 판매 중·오픈 예정·매진 공연.
- '지난 공연 포함'(`includePast=true`)을 켜면 끝난 공연(모든 회차가 판매 종료)도 보인다. 예매 상태 필터에서 '끝남'을 고르면 끝난 공연만 보인다.
- 일부 회차만 취소된 공연은 남은 회차로 판매 상태와 기간을 셈한다.

### 5.2 필터

| 필터 | 매개변수 | 뜻 |
| --- | --- | --- |
| 장르 | `genre` | 정본 장르 7개 가운데 하나 |
| 공연 일정 | `dateFrom`·`dateTo` | 공연 기간(첫 회차 시작~마지막 회차 종료, KST 날짜)이 고른 범위와 겹치는 공연 |
| 예매 상태 | `status` | 오픈 예정·판매 중·매진·끝남 |
| 공연장 | `placeId` | 그 공연장의 공연(홈 공연장 줄과 자동완성 공연장 후보가 쓴다) |
| 아티스트 | `artistId` | 그 아티스트가 나오는 공연(자동완성 아티스트 후보가 쓴다) |

### 5.3 정렬

| 정렬 | 기본인 때 | 순서 |
| --- | --- | --- |
| 정확도(`RELEVANCE`) | 검색어가 있을 때 | 일치 등급(공연명 정확 > 아티스트 정확 > 공연장 정확 > 공연명 앞부분 > 아티스트 앞부분 > 공연장 앞부분 > 중간 일치, 다른 이름은 원래 이름과 같은 등급) → 판매 상태(판매 중 > 오픈 예정 > 매진 > 끝남) → 관심도 → 공연 ID |
| 오픈 임박(`OPEN_SOON`) | 검색어가 없을 때(필터만) | 다음 오픈 시각(없는 공연은 뒤에, 판매 종료가 이른 순) → 공연 ID |
| 인기(`POPULAR`) | — | 최근 7일 확정 판매 매수(공연 합) → 공연 ID. 순위가 없는 공연은 뒤에 오픈 임박 순(POL-043과 같은 집계) |

모든 정렬의 끝을 공연 ID로 두어, 같은 검색에서 쪽을 넘겨도 같은 공연이 두 번 나오거나 빠지지 않는다.

### 5.4 쪽

- 한 쪽 20개 [가정]로 고정한다. `limit`는 20만 받고 다른 값은 400이다. 같은 검색이 `limit` 값마다 다른 캐시로 쪼개지지 않게 하려는 것이다.
- `page × 20`은 1,000 [가정]을 넘지 않는다(넘으면 400). 결과 수가 1,000을 넘으면 `total`은 1000이고 `totalCapped`가 참이다.
- 없는 쪽으로 들어오면 화면은 마지막 쪽을 보인다(docs/design/d5 §5.3).

### 5.5 결과 0건

차례대로 본다.

1. 입력이 로마자만이면 한/영 변환 값으로 다시 찾는다(§3.2 ④). 결과가 있으면 그 결과와 안내를 보이고, 응답의 `query.converted`에 바꾼 값을 싣는다.
2. 그래도 0건이면 비슷한 이름 하나를 `didYouMean`으로 준다. 화면은 "혹시 '루멘'을 찾으셨나요?"를 링크로 보인다.
3. 필터가 걸려 있으면 필터를 뺀 결과 수를 `relaxedTotal`로 준다. 화면은 "필터를 풀면 12개가 있습니다 [필터 풀기]"를 보인다.
4. 관련 공연으로 오픈 예정 인기 공연을 보인다(§6).

### 5.6 응답

`GET /v1/search`의 응답(openapi `SearchResultPage`)은 공연 카드(`ProductionCard`) 목록, 쪽 정보, `query`(정규화한 값, 실제로 찾은 값, 한/영 변환), `didYouMean`, `relaxedTotal`, `related`(근거와 카드), `filterNames`(주소로 받은 공연장·아티스트 필터의 화면 이름, 없는 ID면 null, 추천 적용 2026-11-05, HOT-312)다.

## 6. 관련 공연

- 결과 1쪽의 맨 위 결과가 아티스트나 공연장으로 맞았으면, 그 아티스트의 다른 공연이나 그 공연장의 오픈 예정 공연을 6개 [가정]까지 결과 아래에 보인다(근거: 'LUMEN의 다른 공연', 'KSPO DOME에서 열릴 공연'). 이미 결과에 있는 공연은 빼고, 기본 범위 안에서 관심도 순이다. 여기서 '이미 결과에 있는 공연'은 지금 필터를 건 결과 전체(모든 쪽)다. 아티스트·공연장 이름이 정확히 맞으면 그 아티스트·공연장의 공연은 기본 범위 안에서 모두 결과에 들어가므로(§5.3 일치 등급), 관련 공연은 필터(장르·공연 일정·예매 상태)로 결과에서 빠진 공연이 있을 때만 생긴다. 남는 공연이 없으면 관련 공연 자리를 숨긴다(추천 적용 2026-10-28. 디자인 캔버스를 그리다 찾은 틈, 보드는 장르 필터를 건 경우로 그림).
- 결과가 0건이면 오픈 예정 인기 공연(관심도 순) 6개 [가정]다.
- 검색 기록은 쓰지 않는다. 같은 검색은 누구에게나 같은 관련 공연을 보여, 검색 결과와 함께 CDN에 캐시된다.

## 7. 구조

### 7.1 검색 포트

catalog 모듈 안에 검색 포트 `SearchIndex`를 둔다. API 처리기와 화면은 포트만 안다.

| 하는 일 | 포트 함수 | 지금 어댑터 |
| --- | --- | --- |
| 자동완성 | `suggest(query)` | `MemorySuggestIndex`(메모리 사전) |
| 검색 | `search(query, filters, sort, page)` | `PgSearchIndex`(읽기 모델, 읽기 전용 복제본) |
| 관련 공연 | `related(basis)` | `PgSearchIndex` |
| 비슷한 이름 | `correct(query)` | `MemorySuggestIndex` |

- 바꿀 조건: ① 공연 설명 글·후기 본문 검색 요구 ② 검색 대상 10만 건 [가정] 초과 ③ 골든 세트 정답률이 NFR-028에 못 미치고 순위 규칙 조정으로 안 풀림 ④ 검색 원본 p95가 NFR-028을 넘고 쿼리·인덱스 조정으로 안 풀림. 하나라도 생기면 로컬에서 OpenSearch(+한국어 형태소 분석기 nori) 어댑터를 같은 골든 세트와 부하로 비교 측정하고 새 ADR로 정한다(ADR-0094 결정 4).
- 어댑터를 바꿔도 정규화(§3.1)와 낱자·초성 값은 그대로 쓴다. nori는 형태소 분석기라 낱자·초성 비교가 없기 때문이다(Elasticsearch 문서 2026-10-27 확인).

### 7.2 요청 흐름

```text
브라우저(정규화·순서 고정) ─▶ CloudFront(쿠키 뺀 캐시 키, 자동완성 60초·검색 30초 [가정])
   └ 빗나감 ─▶ gw-fan(IP별 요청 한도) ─▶ core-svc catalog
                 ├ 자동완성·비슷한 이름: 메모리 사전(DB·Redis 안 부름)
                 └ 검색·관련 공연: 검색 전용 연결 묶음 ─▶ Aurora 읽기 전용 복제본(읽기 모델)
```

- 검색 전용 연결 묶음(벌크헤드: 한 의존성이 다른 기능의 연결을 다 쓰지 못하게 나눈 묶음)은 파드마다 연결 10개 [가정], 대기 100ms [가정], 질의 시간 상한 300ms [가정]다. 넘치면 503을 내고, CDN은 `stale-if-error`로 직전 응답을 낸다. 같은 클러스터의 로그인(identity) 쓰기를 지키려는 것이다.
- 캐시 수명: 자동완성 `public, max-age=60, stale-while-revalidate=60, stale-if-error=600` [가정], 검색 `public, max-age=30, stale-while-revalidate=30, stale-if-error=600` [가정]. 캐시 키는 정규화한 `q`와 정해진 매개변수뿐이고 쿠키는 넣지 않는다(guidelines §9).

### 7.3 화면 그리기와 검색 엔진 노출

- `/search`는 캐시되는 정적 셸(헤더 묶음 A, docs/frontend.md §2.5)이다. 브라우저가 주소의 매개변수를 읽어 검색 API를 부르고 결과를 그린다. 요청마다 서버가 그리지 않으므로, 오픈 직전 검색이 몰려도 화면 서버로 가지 않는다.
- `/search`는 검색 엔진 색인에서 뺀다. 셸에 `<meta name="robots" content="noindex, follow">`를 두고 sitemap에 넣지 않는다. 구글 스팸 정책은 '분명한 둘러보기 구조보다 검색 결과에 가까운 비슷한 페이지 만들기'를 도어웨이(유입용 중간 페이지) 남용의 예로 든다(2026-10-27 원문 확인). 검색 엔진 유입은 공연 상세(구조화 데이터)와 sitemap이 맡는다. 회차 상세는 저마다 자기 주소를 정규 주소로 두고, 아티스트·공연장 둘러보기 페이지는 출시 뒤 Search Console의 검색어를 보고 만들지 정한다(소유자 결정 2026-10-29, ADR-0153, docs/frontend.md §5.15).

## 8. 성능과 용량

- 목표(NFR-028): 자동완성 원본 응답 p95 50ms [가정], 검색 원본 응답 p95 300ms [가정](상시 운영 28일, gw-fan 서버 측), 골든 세트 1위 정답률 90% [가정]·3위 안 98% [가정].
- 오픈 직전 몰림(어림, 설계 목표): 대형 공연 오픈 10분 전에 100만 명 가운데 20% [가정]가 머리 검색으로 공연을 찾고, 한 사람이 자동완성 3번·검색 1번 [가정]을 보낸다고 보면 자동완성 60만·검색 20만 건이다. 고르게 오면 초당 1,000·333건이고 다섯 배로 몰리면 초당 5,000·1,700건이다. 같은 아티스트 이름의 앞부분은 가짓수가 수십 개라 CDN이 거의 다 받는다. 원본에 오는 것은 '서로 다른 키 × 엣지 수 ÷ 캐시 수명' 정도다(키 50개 × 엣지 20곳 [가정] ÷ 60초 ≈ 초당 17건). 대기실 화면(집중 셸)에는 검색창이 없어 대기 중에는 검색이 없다.
- 무작위 입력(캐시 우회): 요청마다 원본으로 온다. 자동완성은 메모리 사전이 답해 DB에 닿지 않는다. 검색은 IP별 요청 한도와 검색 전용 연결 묶음으로 막는다. 휴대폰 통신망처럼 많은 사람이 공인 IP 하나를 나눠 쓰는 경우를 생각해 IP별 한도는 넉넉히 두고 [가정], 원본의 처리 비용을 싸게 만드는 쪽으로 버틴다.
- 부하 분해(docs/verification.md §3.1)에 이 두 시나리오를 넣고 로컬에서 잰다(SR-T13).

## 9. 보안과 개인정보

- 보안 추적 표는 [docs/security/asvs/catalog-review.md](../security/asvs/catalog-review.md)다(입력 길이·정규화, 바인드 변수와 LIKE 이스케이프, 정렬·필터는 허용 열거값, 글자 노드로 그리기, 리퍼러 정책, 요청 한도, 로그 주입 방지).
- 검색어는 계정과 잇지 않는다. 검색 요청은 쿠키 없이 CDN을 지나므로 서버가 누가 찾았는지 모른다. 다만 검색어는 주소의 쿼리라 CDN·게이트웨이 접근 기록과 검색 원본의 요청 기록에 남는다(docs/security/data-classification.md '최근 검색어와 검색어 기록').
- 최근 검색어는 이 기기(localStorage)에만 둔다(10개 [가정], 하나씩·전체 지우기).
- 검색어와 결과를 외부 분석·추적 도구에 보내지 않는다. 품질 비율(§11)은 같은 출처 수집 경로로 검색어 없이 보낸다.

## 11. 관측

- 원본 지연·오류는 서비스 기본 지표(경로 템플릿 라벨의 요청 지연 히스토그램, docs/observability.md §3)로 본다. 엣지 적중률·지연은 CloudFront 지표로 본다.
- 품질 비율: 브라우저가 검색어 없이 사건 수만 같은 출처 수집 경로(`/_t/rum`, ADR-0076)로 60초 [가정]마다 묶어 보낸다. 게이트웨이 수집기가 지표로 바꾸고 원본 사건은 남기지 않는다(docs/observability.md §11 RUM과 같은 경로). 라벨은 가짓수가 적은 것만 쓴다(docs/observability.md §8 카디널리티 규칙, 2026-11-01 정합 점검).
  - `search_results_shown_total{zero}`(결과를 보였는가, 0건인가)
  - `search_suggest_shown_total`, `search_suggest_selected_total{kind, position}`(종류 3·위치 1~8)
  - `search_result_click_total{position_bucket}`(1~3, 4~10, 11~20)
  - `search_requery_total`(결과를 누르지 않고 10초 [가정] 안에 다시 찾음)
  - 비율: 결과 0건 비율, 자동완성 선택률, 결과 클릭률, 바로 다시 찾은 비율
- 0건 검색어 목록: 정규 로그 줄 `search_query` 가운데 결과 0건인 것을 주마다 모아 정규화한 검색어 상위 50개를 운영자에게 보인다. 운영자는 이를 보고 다른 이름을 더한다. CDN이 같은 검색을 받아 주므로 횟수는 대략이다. 로그 보존 기간이 지나면 함께 지워진다.
- 검색어 가리기와 최소 빈도(추천 적용 2026-10-28, 기술 검토 낮음-173): 검색어에는 전화번호·이메일 같은 개인정보가 섞일 수 있다. 계정과 잇지 않아도 그 값 자체가 개인정보다. 그래서 검색 원본은 `search_query` 줄을 남기기 전에, 정규화한 검색어에서 이메일 꼴(`…@….…`)을 `[이메일]`로, 전화번호 꼴(0으로 시작하는 9~11자리 숫자, 사이의 하이픈·점·공백 허용)을 `[전화]`로, 그 밖의 이어진 숫자 5자리 이상을 `[숫자]`로 바꾼다. 검색 자체는 가리기 전 값으로 한다(공연 이름의 4자리 연도 같은 숫자는 그대로 남는다). 0건 목록은 그 주에 서로 다른 요청(원본 로그 줄)으로 5번 [가정] 이상 나온 검색어만 보인다. 드문 개인정보는 한두 번 나오고 끝나므로 목록에 오르지 않는다. 가리기 규칙은 SR-T17로 시험한다. CDN·게이트웨이 접근 로그에는 주소의 쿼리가 원래대로 남는다. 그 로그는 접속기록 보존 기준과 권한을 따른다(docs/security/data-classification.md).

| SR-T15 | 판이 바뀌면 10초 [가정] 안에 사전에 반영된다. 판매 승인 취소·회차 전부 취소로 빠진 공연과 지운 다른 이름이, 통째로 읽기 없이 증분 갱신 한 번 안에 사전에서 빠진다. 지운 뒤 다시 승인된 공연은 다시 나온다. 판은 새것이고 줄은 옛것인 복제본 지연을 흉내 내도(판과 줄을 다른 연결로 읽게 만든 판) 같은 트랜잭션 규칙을 지키는 판은 빠짐이 없다. Aurora 읽기 전용 복제본에서 `REPEATABLE READ` 읽기 전용 트랜잭션이 되는지도 본다(기술 검토 중간-089) | 통합 시험, Aurora는 wbs 2.10.8 |
| SR-T17 | 검색어 가리기와 0건 목록의 최소 빈도(추천 적용 2026-10-28, 기술 검토 낮음-173): `010-1234-5678`·`01012345678`·`a@b.kr`·`1234567`이 든 검색어의 `search_query` 줄에는 `[전화]`·`[이메일]`·`[숫자]`만 남고, '2026 루멘'의 연도와 '루멘 2회'는 그대로 남는다. 검색 결과는 가리기 전 값으로 찾은 것과 같다. 한 주에 4번 나온 0건 검색어는 목록에 없고 5번이면 있다 | 단위 시험(가리기 함수), 통합 시험(주간 목록 집계) |

## 13. 예외 상황 대응

| 상황 | 대응 |
| --- | --- |
| 검색 원본 장애 | CDN이 `stale-if-error`로 직전 응답을 낸다. 없으면 화면은 "검색하지 못했습니다. 다시 시도해 주세요" [다시 시도]를 보인다(docs/design/d5 §5.3) |
| 자동완성 실패 | 창을 띄우지 않는다. Enter는 결과 화면으로 간다 |
| 사전 판이 늦음 | 직전 사전으로 답한다. 60초 [가정] 넘게 늦으면 SEV3로 알리고 파드를 다시 띄워 통째로 읽게 한다 |
| 사전이 DB와 어긋남 | `search_dictionary_drift_entries`가 0이 아니면 그 파드가 다음 갱신 때 통째로 읽는다. 10분 [가정] 넘게 이어지면 SEV3로 알리고 지운 표시를 남기지 않은 변경 경로를 찾는다(추천 적용 2026-10-28, 기술 검토 중간-089) |
| 읽기 전용 복제본 지연 | 검색이 몇 초 늦은 값을 보일 수 있다. 판매 상태는 상세 화면에서 다시 확인되므로 판매에 영향이 없다 |
| 검색 연결 묶음 포화 | 503 → CDN 직전 응답. 계속되면 요청 한도를 낮추고 원인(무작위 입력, 느린 질의)을 본다 |
| CDN 무효화 실패 | 캐시 수명(30·60초 [가정])이 지나면 빠진다. 실패는 SEV3로 알리고 다시 부른다 |

## 14. 남는 한계

- 공연 설명 글·후기 본문·굿즈는 찾지 않는다.
- 오타 바로잡기는 결과 0건일 때의 제안 하나다. 오타 섞인 검색어로도 결과가 나오면 바로잡지 않는다.
- 품질은 검색어 없는 비율과 대략의 0건 검색어 목록으로만 본다. 검색어마다의 정확한 횟수는 모른다. 검색어를 계정과 잇지 않는 원칙을 지키려는 선택이다.
- 수치(최소 길이, 종류별 몫, 0.3초, 10초, 6개, 20개, 1,000, 캐시 수명, 연결 묶음, NFR-028 목표)는 아직 재지 않은 가정이다(wbs 2.10.8·2.12.4).
- 디자인 캔버스는 아직 고치지 않았다(docs/review/open-items.md 25번). 아티스트·공연장 둘러보기 페이지는 출시 뒤 Search Console의 검색어를 보고 만들지 정하고, 장르별 목록 페이지는 만들지 않는다. 그때까지 공연 이름만으로 찾는 사람의 입구는 회차 상세와 홈뿐이다(소유자 결정 2026-10-29, ADR-0153, §7.3).
- 읽기 전용 복제본의 지연과 CDN 무효화 시간만큼, 빠진 공연이 잠시 더 보일 수 있다.

## 15. 확인한 외부 사실(2026-10-27)

- PostgreSQL 18 pg_trgm 문서: 단어가 아닌 글자는 무시하고, 낱말 앞에 공백 둘·뒤에 하나를 붙여 조각을 만들며, 유사도 기본 기준은 0.3이다. 조각을 뽑지 못하는 패턴은 인덱스 전체를 훑는다.
- PostgreSQL 18 소스(`src/backend/tsearch/ts_locale.c`, `contrib/pg_trgm/trgm.h`): 단어 글자 판정은 DB 문자 분류가 C면 여러 바이트 글자도 첫 바이트로만 한다.
- MDN `keydown`: 조합에 속한 keydown은 `isComposing || keyCode === 229`로 거르고, 조합을 끝내는 키에서는 `isComposing`이 거짓일 수 있다.
- 구글 검색 스팸 정책 'Doorway abuse'의 예: 분명한 둘러보기 구조보다 검색 결과에 가까운 비슷한 페이지 만들기. 크롤링 예산 문서: 정렬만 다른 같은 페이지는 robots.txt로 막을 수 있다.
- CloudFront 문서: 쿼리 매개변수의 순서와 대소문자가 다르면 다른 캐시이고 알파벳 순서처럼 늘 같은 순서를 권한다. 무효화 경로 끝의 `*`는 쿼리 문자열 변형을 모두 덮는다.
- ElastiCache 매개변수: `maxmemory-policy` 기본값은 `volatile-lru`다.
- es-hangul 2.4.0(MIT, 토스): `disassemble('값')` = 'ㄱㅏㅂㅅ', `getChoseong('사과')` = 'ㅅㄱ', `convertQwertyToHangul('dkdlvhs16')` = '아이폰16'.
- es-hangul 2.4.0 소스(2026-10-28 확인): `canBeChoseong`은 호환 자모 초성 19자 목록(`CHOSEONGS`)만 본다. `disassembleToGroups`는 완성 음절과 호환 자모 겹자음·겹모음('ㄳ' → 'ㄱㅅ')만 풀고, 그 밖의 글자(첫소리·끝소리 자모 U+1100대 포함)는 그대로 둔다.
- 유니코드 NFKC 계산(Python 3 `unicodedata` 15.0·Node.js v24.18.0, 2026-10-28): 'ㄹㅁ'(U+3139·U+3141) → U+1105·U+1106, 'ㄳ'(U+3133) → U+11AA, 반각 'ﾡ'(U+FFA1) → U+1100, '㉠'(U+3260) → U+1100, 따로 친 'ㄱ'·'ㅏ' → '가'. NFC는 호환 자모를 바꾸지 않는다. 호환 자모 94자의 NFKC 결과는 모두 U+1100~U+11FF 안의 한 글자이고 서로 겹치지 않는다(기술 검토 높음-25).
- 위키백과 'KSPO DOME': 올림픽체조경기장이 2018년 리모델링 뒤 KSPO DOME으로 이름이 바뀌었고 옛 이름도 쓰인다.
- 네이버 검색어 고객센터: '자동완성' 메뉴(서비스 소개, 초성 입력 시 제공 여부, 제외 요청: 사생활 침해·명예훼손·개인정보 노출·청소년 유해·음란·저작권·욕설·자동화된 수단).
- 엔진 비교에 쓴 가격과 문서(Elastic 라이선스, nori, AWS OpenSearch 가격표 2026-10-20판·권장 구성·서버리스, Algolia 가격표·언어·오타 허용)는 ADR-0094 맥락에 있다.
