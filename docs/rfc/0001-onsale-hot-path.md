# RFC 0001: 온세일 핫패스 — 100만 대기, 20만 진입 RPS, 5만 석을 한 흐름으로

- **상태**: 초안(2026-11-12, BUILD_ORDER BAS-230, wbs 0.8.1). 규범이 아니다. 정본은 [docs/architecture.md](../architecture.md) §9.1·§9.2·§9.5, [docs/features/queue-admission.md](../features/queue-admission.md), [seat-hold.md](../features/seat-hold.md), [payment.md](../features/payment.md), [docs/verification.md](../verification.md) §3이다.
- **독자**: 대기열·구매·결제·플랫폼을 구현하는 엔지니어, 운영자, 기술 방향을 검토하는 이해관계자.
- **요약**: PEAKET은 오픈 순간의 읽기 폭주와 좌석 쓰기 경합을 같은 데이터베이스로 받지 않는다. 대기 상태는 CDN의 정적 파일로, 진입 순번은 Redis의 원자 연산으로, 좌석 홀드는 Redis Lua와 PostgreSQL의 판매 확정으로, 결제는 멱등 접수와 Outbox로 나눈다. 목표는 100만 명 대기, T=0 진입 20만 RPS, 5만 석, 결제 피크 300 TPS다.

## 1. 문제

- 티켓 오픈은 짧고 센다. 100만 명이 같은 시각에 몰리고, 70분 안에 5만 석이 팔린다. 평소 트래픽의 수백 배가 10분 안에 몰리는 모양이라, 평균 처리량보다 **꼬리와 실패 반경**이 문제다.
- 병목은 DB 쓰기가 아니다. ① 수십만 명이 동시에 대기 상태를 조회하는 것, ② 오픈 정각에 진입이 한꺼번에 몰리는 것, ③ 좌석 변경을 접속한 5,000명에게 보내는 것이다([docs/architecture.md](../architecture.md) §9.1).
- 결제는 외부 결제사(PG)의 한도와 지연에 묶인다. 토스 300 TPS·포트원 초당 50건은 계약 전 추정이고, 실제 한도가 낮으면 동시 입장 목표도 낮춰야 한다(ADR-0036·0044).

## 2. 목표와 비목표

| 목표 | 값 | 정본 |
| --- | --- | --- |
| 대기 인원 | 100만 명 | docs/planning/01 §5 |
| T=0 진입 피크 | 20만 RPS(로비 셔플을 끈 공연의 상한) | NFR-001, docs/architecture.md §9.1 |
| 공연 상세 페이지 피크 | 30만 RPS(CDN 요청, 100만 × 30% × 2회 ÷ 10초 × 5건 [가정]) | NFR-007, docs/architecture.md §9.1 |
| 좌석 규모 | 5만 석, 1인 최대 4매 | docs/architecture.md §9.1 |
| 동시 좌석 선택 | 5,000명 | C-03, docs/architecture.md §9.1 |
| 결제 피크 | 300 TPS(토스 추정), 포트원 채널 초당 50건 | ADR-0036·0044 |
| 결제 확정 p99 | 3초(정상), 60초(감내 모드) | NFR-006 |

비목표:

- 대기실에 WebSocket을 열지 않는다. 100만 개의 지속 연결 대신 거리별 폴링과 CDN 정적 파일을 쓴다(ADR-0003).
- 핫패스에서 PostgreSQL을 읽지 않는다. 좌석 상태는 Redis, 판매 확정만 DB다.
- 분산 잠금을 두지 않는다. Redis Lua의 단일 스레드 실행과 DB의 조건부 갱신으로 순서를 맞춘다.
- 100만 명 전 구간을 실측하지 않는다. PC·소규모 측정과 설계 식으로 외삽하고, 그 사실을 성능 장부에 남긴다(ADR-0057).

## 3. 설계

### 3.1 진입과 대기

1. **로비**: 오픈 T-10분에 연다. 참가자는 소셜 로그인과 휴대폰 본인확인을 마치고, 사람 확인(Cloudflare Turnstile)을 통과한다. 로비 참가 자체는 순번을 정하지 않는다(POL-004).
2. **셔플**: 공연별 설정에 따라 로비 참가자에게 무작위 순번을 준다. 시드는 오픈 60분 뒤 공개하고, 누구나 검증할 수 있게 한다.
3. **진입**: T=0에 브라우저가 `POST /v1/queues/{eventId}/entries`를 보낸다. 진입 경로는 토큰 서명 검증, Redis `SET NX`·`INCR`, 대기표 HMAC 서명만 한다. 본문은 `text/plain`이고 safelisted 헤더만 써서 CORS 사전 요청을 만들지 않는다(ADR-0065 결정 6).
4. **순번 발급**: 공연별 `INCR` 키 하나에 몰리므로, 파드별 2ms [가정] 마이크로 배치 `INCRBY`로 나눈다. 파드 사이 순번 편차는 2ms 이내라 공정성 영향은 0에 가깝다(ADR-0179).
5. **대기 상태 조회**: 대기자는 0.5초·5초·20초의 거리별 간격으로 조회한다(ADR-0110). 응답은 CDN이 1초마다 갱신하는 구간별 정적 파일(100만 명 기준 약 1,000개)이다. 원본 요청은 파일 수준으로 고정된다.
6. **입장 확정**: 차례가 온 사람이 `POST /v1/queues/{eventId}/admission`을 보낸다. 서버는 serving 번호와 순번을 견주고, 통과하면 입장 토큰을 준다. 차례 전 입장은 0건이어야 한다(불변식).

### 3.2 좌석 홀드와 판매

- **홀드**: 5만 석 비트맵과 1인 매수 한도를 Redis Lua 하나로 원자 처리한다. 여러 좌석은 좌석 ID 순으로 잡아 DB 잠금 순서를 맞춘다. 경합 패배는 409로 정상 분기 처리하고 오류율에 넣지 않는다(NFR-003).
- **만료·연장**: 홀드 TTL과 최대 체류를 두고, 만료는 서버가 회수한다. 만료 직전 1분 경고와 1회 연장을 준다.
- **판매 확정**: 홀드가 끝나면 PostgreSQL이 PENDING 행을 좌석 ID 순으로 잠그고 SOLD로 바꾼다. Redis와 DB의 상태가 다르면 DB가 최종 판정이다.
- **실시간 전파**: 접속한 5,000명에게 100ms 주기로 구독 구역의 바이너리 델타만 보낸다. 전체 좌석 JSON을 모두에게 보내지 않는다(ADR-0063·0110).

### 3.3 결제와 발권

1. **주문 생성**: 구매 세션과 홀드를 확인하고 주문을 만든다. 같은 멱등 키의 재요청은 처음 결과를 그대로 준다.
2. **결제 접수**: `POST /v1/orders/{orderId}/payment-acceptance`가 202로 접수하고, 결제 시도마다 결제사를 고정한다(ADR-0044). 접수 뒤에는 결제사를 바꾸지 않는다.
3. **승인**: payment-svc가 결제사 어댑터로 승인한다. 같은 멱등 키로 다시 보내고, 결과 모름(UNKNOWN)은 단건 조회로만 확정한다. 본문 웹훅은 상태를 바꾸지 않고 조회 시각만 앞당긴다(ADR-0015·0029).
4. **발권**: 승인 뒤 ticket-svc가 티켓을 만든다. 발권이 실패하면 결제를 취소하지 않고 같은 주문으로 다시 발권한다(ADR-0106). 60초 안에 발권되지도 재시도 큐에 들어가지도 않은 결제는 0건이어야 한다.
5. **Outbox**: 주문·결제·티켓 사건은 같은 트랜잭션의 Outbox에 먼저 쓰고, 릴레이가 `acks=all`로 Kafka에 보낸다. 릴리스 리더는 Lease로 하나만 둔다(ADR-0116).

### 3.4 관측과 제어

- **입장 제어**: admission-ctrl이 목표 동시 입장과 serving 전진 속도를 조절한다. 뒤쪽 p99·오류율·에러 버짓·좌석 저장소 신호를 읽고, 입력이 없으면 목표를 유지한 채 멈춘다(ADR-0069).
- **관제**: T-30분 점검, T=0 집중, 판매 중, 종료 후의 네 단계로 본다. 판단 숫자는 Prometheus, 실시간 잔여석·퍼널은 ClickHouse `rt` 표에서 읽는다.
- **경보**: 온세일 70분 예산을 기준으로 다중 창 경보를 건다. 결제 확정은 70분 허용 실패가 약 12건이라 임박 원인 경보를 따로 둔다(ADR-0049).

## 4. 용량과 지연

| 구간 | 설계값 | 근거 |
| --- | --- | --- |
| 진입 피크 | 20만 RPS | 100만 × 2배 ÷ 10초 |
| 순번 발급 | 파드 수 × 초당 약 500회 | 2ms 마이크로 배치, ADR-0179 |
| 셔플 결과 조회 | 초당 약 12.5만 건, 약 19 Gbps [추정] | 100만 명이 0~8초에 1회, 약 19KB |
| 대기 상태 조회 | CDN 초당 약 5.4만 건 | 거리별 폴링, ADR-0110 |
| 좌석 홀드 | 평시 170/s, 피크 1,000~2,000/s | docs/architecture.md §9.1 |
| 결제 접수 | 최대 300 TPS(토스), 포트원 50/s | ADR-0036·0044 |
| 판매 확정 | 초당 약 28건 | 5,000명 ÷ 180초 |

- 위 값은 설계 목표이거나 [가정]이다. 실측·외삽 구분은 [docs/verification.md](../verification.md) §3과 성능 장부를 따른다.
- 30만 RPS 공연 페이지 피크의 셈은 [docs/architecture.md](../architecture.md) §9.1 '페이지당 호출 수'에 있다.

## 5. 실패 처리

| 실패 | 동작 | 남는 것 |
| --- | --- | --- |
| Redis 대기열 장애 | 진입·상태 조회가 503과 `Retry-After`로 끝난다. 이미 발급한 순번은 Redis 복구 뒤 이어진다 | 복구 전 진입은 실패로 센다 |
| 좌석 Redis 장애 | 구매 요청을 미루고 503으로 끝낸다. 세대 키로 옛 리더의 쓰기를 막는다(ADR-0121) | 미룬 시간만큼 판매가 늦어진다 |
| Kafka 거래 토픽 지연 | 결제 결과가 5초 [가정] 안에 오지 않으면 payment-svc에 직접 묻는다(ADR-0140) | 결과가 늦으면 당기기가 받친다 |
| 결제사 한도 초과 | 첫 승인 호출의 429로 그 채널 상한을 낮추고, admission-ctrl이 serving 전진도 낮춘다 | 낮춘 상한은 70분 [추측] 뒤 돌아온다 |
| 결제사 결과 모름 | 단건 조회로만 확정한다. 웹훅 본문은 신뢰하지 않는다 | 조회가 끝날 때까지 UNKNOWN으로 남는다 |
| CDN 한도 초과 | 배포를 공연 페이지·대기열 파일·대기열 API로 나누고, 각 배포를 설계 피크의 1.5배 [가정]로 올린다 | 상향 승인 전에는 엣지에서 거절될 수 있다 |

## 6. 보안·개인정보

- 진입·입장 토큰은 queue-svc가 자체 HMAC로 발급·검증한다. 핫패스에서 KMS를 부르지 않는다.
- 대기 상태 파일과 셔플 결과에는 계정 ID·이름·연락처를 싣지 않는다. 순번과 회차 ID만 둔다.
- 좌석 홀드와 결제 로그의 식별자는 가명 참조값(`pidRef`·`sidRef`)만 쓴다(ADR-0053).
- 결제 웹훅은 포트원 Standard Webhooks 세 머리(`webhook-id`·`webhook-timestamp`·`webhook-signature`)와 5분 창을 검증하고, 토스 결제 웹훅은 서명이 없으므로 단건 조회로 확인한다.

## 7. 검토한 대안

| 대안 | 고르지 않은 이유 |
| --- | --- |
| 대기실 WebSocket | 100만 지속 연결은 파일 디스크립터·로드밸런서 연결·팬아웃 비용이 크다. 폴링과 CDN 파일이 같은 신선도를 더 싸게 준다 |
| 대기 상태를 DB에서 조회 | 100만 명의 0.5~20초 폴링을 DB가 받을 수 없다. CDN 정적 파일이 원본 요청을 파일 수로 고정한다 |
| 좌석 홀드에 분산 잠금 | 잠금 대기와 교착이 생긴다. Redis Lua의 단일 스레드와 좌석 ID 정렬로 충분하다 |
| 결제 승인을 동기로 오래 기다리기 | 결제사 지연이 HTTP 연결을 붙잡고, 결과 모름을 다루기 어렵다. 202 접수 + 멱등 재시도 + 조회가 낫다 |
| 모든 사건을 DB 트랜잭션으로 | 외부 결제사 호출을 DB 트랜잭션에 넣을 수 없다. Outbox와 Saga로 나눈다 |

## 8. 열린 질문·가정

- 30만 RPS의 30%·2회·5건은 [가정]이다. 실제 공연의 공연 상세 재방문률과 캐시 적중률로 다시 맞춘다.
- 토스 300 TPS·포트원 초당 50건은 계약 전 추정이다. 실제 계약 한도가 오면 동시 입장 목표와 80% 판정을 다시 한다.
- CDN 한도 상향 승인 기간과 한도를 넘었을 때의 응답은 AWS 문서에서 확인하지 못했다(ADR-0058).
- 100만 명 전 구간은 실측하지 않는다. PC·소규모 측정과 설계 식의 외삽이며, 그 한계를 성능 장부에 남긴다.
