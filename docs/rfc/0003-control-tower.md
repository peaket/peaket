# RFC 0003: 관제 — 데이터 경로와 떨어진 제어 평면, 5초 실시간 표, 2인 승인

- **상태**: 초안(2026-11-12, BUILD_ORDER BAS-230, wbs 0.8.1). 규범이 아니다. 정본은 [docs/features/control-tower.md](../features/control-tower.md), [docs/observability.md](../observability.md) §3~§9, [docs/streaming.md](../streaming.md) §4, [docs/devops.md](../devops.md) §8이다.
- **독자**: 관제 콘솔·ops-svc·제어 명령을 받는 서비스·관측 저장소를 구현하는 엔지니어, 온세일 운영자, 장애 대응을 검토하는 이해관계자.
- **요약**: 관제 콘솔은 판매 데이터 경로와 다른 제어 평면이다. 운영자는 T-30분 점검, T=0 집중, 판매 중, 종료 후의 네 단계로 시스템 상태를 보고, 12개 운영 명령을 2인 승인과 감사 기록 아래 실행한다. 실시간 표는 Kafka → `ops-rt` → ClickHouse → ops-svc → SSE로 이어지고, 종단 p95 5초 미만을 목표로 한다. ops-svc가 죽어도 판매는 계속되고, 관제 자체의 상실은 SEV1로 알린다.

## 1. 문제

- 온세일 70분 동안 운영자는 "지금 시스템이 정상인가"를 즉시 판단하고, 필요하면 안전하게 개입해야 한다. 대시보드가 예쁜 것보다 **판단과 조작이 한 화면에서** 이어지는 것이 중요하다.
- 판매 경로와 관제 경로가 같은 저장소·같은 게이트웨이를 쓰면, 관제 장애가 판매를 막거나 판매 폭주가 관제를 늦춘다. 그래서 제어 평면을 데이터 경로와 떼어 둔다.
- 관제 명령은 잘못 실행하면 매출·좌석·법정 의무에 직접 영향을 준다. 그래서 사유·dry-run·2인 승인·감사 기록·되돌리기가 필요하다.
- 실시간 숫자는 늦으면 쓸모가 없다. 목표는 이벤트 발생부터 화면 표시까지 p95 5초 미만이다(NFR-009).

## 2. 목표와 비목표

| 목표 | 값 | 정본 |
| --- | --- | --- |
| 실시간 표 신선도 | 종단 p95 5초 미만 | NFR-009 |
| T-30분 점검 | 필수 항목 전부 통과해야 Go | docs/features/control-tower.md §2 |
| 운영 명령 | 12개, 사유 필수·dry-run·ack·되돌리기 | FR-030, POL-021 |
| 2인 승인 | 위험 명령은 요청자와 다른 commander | POL-021, ADR-0086 |
| 감사 기록 | 불변 해시 체인, KMS 서명, 공개 앵커 | ADR-0053·0075·0102 |
| 관제 자체 상실 | 준비 파드 0이 30초 [가정]면 SEV1 | docs/features/control-tower.md §5 |

비목표:

- Grafana 패널을 iframe으로 끼워 넣지 않는다. 콘솔은 ops-svc가 읽은 값을 직접 그린다(ADR-0067).
- 콘솔에 로그 검색·요청 경로 그림·프로파일·오류 묶기를 만들지 않는다. 원인 분석은 Grafana·Sentry가 맡는다.
- 관제 명령을 데이터 경로의 동기 호출에 넣지 않는다. 제어 gRPC·Kafka 설정 사건으로 보낸다.
- 모든 지표를 실시간 표에 넣지 않는다. 판단·제어 숫자는 Prometheus, 잔여석·퍼널은 ClickHouse `rt`다.

## 3. 구조

| 층 | 구성 | 하는 일 |
| --- | --- | --- |
| 콘솔 | Module Federation 호스트와 리모트 위젯, 정적 SPA(S3) | 단계별 패널, 명령 카드, 승인·감사 화면, SSE 구독 |
| ops-svc | REST·SSE, 제어 gRPC 클라이언트, ops DB | 위젯 조회, 명령 접수·승인·전파, 감사 기록, 경보 |
| 실시간 표 | Kafka → `ops-rt` → ClickHouse `rt` → ops-svc | 잔여석·퍼널·판정 종류, 심장 박동 |
| 판단 지표 | 클러스터 Prometheus | 입장 속도, 퍼널 카운터, 오류율, p99, 에러 버짓 |
| 원인 분석 | Grafana·Sentry·Loki·Tempo | 위젯의 '자세히 보기 ↗'로 새 탭 |

- ops-svc는 업무 gRPC를 받지 않는다. 다른 서비스에 묻는 쪽이고, 제어 명령만 gRPC로 보낸다.
- ops DB는 판매 DB와 분리한다. 관제 장애가 주문·결제 트랜잭션을 붙잡지 않는다.
- 관제 노드 풀과 ops 전용 Aurora를 따로 둔다(ADR-0102). 비상 접근 계정은 봉인 보관하고, 쓰면 SEV1이다.

## 4. 화면과 지표

| 단계 | 핵심 | 보는 것 |
| --- | --- | --- |
| T-30분 점검 | 오픈 준비가 끝났나 | 프리워밍, Redis·Kafka·PostgreSQL 헬스, MSK `UnderMinIsrPartitionCount` 0, NLB 영역 빼기, 결제사·본인확인·사람 확인 상태, CloudFront 배포별 한도, 합성 점검, 온콜 시험, 노드 시계 20ms 이하, 인증서·키 만료, 백업, 진행 중 배포 0, 동결 창 |
| T=0 집중(최초 10분) | 몰림을 견디나 | 진입 RPS·p99, 셔플 결과 게시, serving 전진, 상태 조회량·CDN 적중률, 에러 버짓 소진, 봇 차단, 추가 검증 유입·통과, 본인확인·사람 확인 성공률 |
| 판매 중 | 판매가 원활한가 | 퍼널 다섯 단계, 입장 비율·빈자리, 구역별 잔여석, 결제사 승인 성공률·p99·한도, 에러 버짓 잔량, 차례 전 입장 0, 자원 포화도, RUM INP·LCP, 새 오류 종류, 느린 쿼리, 네트워크 |
| 종료 후 | 무엇을 배우나 | 매진 소요, 봇 점유율 하한, 에러 버짓 사용, 명령·경보 타임라인, 결정 규칙 대조, 공연 리포트, 포스트모템 초안 |
| 입장 탭(공연 당일) | 현장이 도나 | 로그인·준비 기기, 마지막 동기화 2분 [가정], 구역별 입장, 거부 사유, 오거부 후보, 이상 표시, 부스 재발급·예외 통과, 업로드 대기, 마감 상태 |

- 모든 패널에 SLO 기준선을 함께 그린다. 위젯마다 '이 숫자로 무엇을 하는가'(명령 번호·런북·엔지니어 호출)를 한 줄로 적는다.
- 판단 숫자와 진단 힌트를 나눈다. 체감·느린 쿼리·네트워크는 명령이 없는 숫자라 '진단 힌트' 줄에 모은다.
- Go/No-Go는 필수 항목 하나라도 실패하면 No-Go다. T-20분까지 회복하면 재판정해 Go로 바꿀 수 있고, 재판정도 감사 로그에 남긴다.

## 5. 운영 명령과 감사

- **명령 12개**: 동시 입장 목표, 입장 일시정지, 판매 일시정지(킬스위치), ASN·IP 차단, 봇 판정 강도, 대체 결제사 전환, 공지, 로그 레벨, 기능 플래그, 대기열 배포 전환, 자동화 정지, 회차 취소·환불. 세부는 [docs/features/control-tower.md](../features/control-tower.md) §3.
- **공통**: 사유 필수, dry-run으로 예상 영향 범위 확인, 대상 서비스의 명시적 ack, 되돌리기, 불변 감사 기록.
- **승인**: 위험 명령은 요청자와 다른 commander가 승인한다. 판매 일시정지는 1인 실행·2인 재개다(ADR-0095). 2인 승인은 `command_approval` 자식 표에 남긴다.
- **감사 체인**: 명령 트랜잭션은 기록과 체인 행(`seq`, 기록 해시)만 쓰고 mac은 비운 채 커밋한다. 체인 작업자가 `seq` 순서대로 KMS mac을 채운다. mac이 빈 행이 1분 [가정]을 넘으면 SEV2다(ADR-0102).
- **공개 앵커**: 매일 00:10과 온세일 윈도우 끝 뒤 10분 안에 [가정] RFC 9162 머클 체크포인트를 만들어 KMS로 서명하고 OpenTimestamps에 고정한다. 누구나 `audit-verify`로 확인한다(ADR-0075).
- **설정형 명령**: 명령 5·7·8·9·12는 Kafka 설정 사건으로 퍼진다. 받는 파드가 적용한 판 번호를 `control_settings_applied_version{service,key}`로 내고, 30초 [가정] 안에 확인되지 않으면 SEV3다(ADR-0143).

## 6. 안전 장치

1. **자동 제어보다 사람이 먼저**: 운영자가 동시 입장 목표를 직접 정하면 AIMD 자동 조정이 15분간 멈춘다. 시간이 끝난 뒤 운영자가 확인해야 자동으로 돌아간다.
2. **입력이 없으면 멈춘다**: 자동 제어가 읽는 지표가 실패·빈 결과이거나 30초 [가정]보다 오래되면 '제어 입력 없음'이다. 빈 결과를 0으로 읽지 않고 목표를 유지한다.
3. **감축은 효과를 확인한 뒤 다시 한다**: 목표를 줄인 뒤 예매 단계 인원이 새 목표 아래로 내려오고 35초 [가정]가 지나거나 2분 [가정]이 지날 때까지 추가 감축을 하지 않는다.
4. **에러 버짓 연동**: 연동 여정(좌석 홀드·좌석 상태 전파·결제 접수·결제 확정)의 버짓 50%를 쓰면 동시 입장 목표를 자동으로 낮춘다. 다른 여정은 SEV2만 띄운다.
5. **긴급 정지**: 명령 11은 입장 제어의 모든 자동 알고리즘을 멈춘다. 오토스케일링은 계속한다. 사후 검토 보고서 작성이 48시간 안에 필요하다.
6. **사후 검토**: SEV1·SEV2와 위험 명령은 실행자가 아닌 commander가 7일 안에 검토한다. 보고서 항목의 ★는 시스템이 감사 로그·지표에서 채운다.

## 7. 실패 처리

| 실패 | 동작 | 남는 것 |
| --- | --- | --- |
| ops-svc 준비 파드 0 | 30초 [가정] 뒤 SEV1(`kind` control, RB-08). 판매는 계속 | 그동안 콘솔 조작 불가, Grafana 읽기 전용으로 대체 |
| Kafka 거래 토픽 끊김 | 판매 누적·잔여석 옆에 '거래 사건 끊김', 60초 [가정] 뒤 SEV3 | 실시간 표의 판매 숫자가 낡는다 |
| ClickHouse 지연 | 5초 초과가 3분 [가정] 이어지면 Prometheus 대체 표시 | 잔여석·퍼널 상세가 줄어든다 |
| KMS 정지 | 명령은 mac 빈 채 커밋·전파되고, 체인 작업자가 복구 뒤 따라잡는다 | mac 빈 행 1분 [가정] 초과 시 SEV2 |
| Alertmanager 정지 | 외부 합성 점검이 콘솔 확인 실패를 잡는다 | 경보 전달이 늦는다 |
| SSE 끊김 | 35초 [가정] 안에 재연결, `Last-Event-ID`로 이어 받는다 | 끊긴 동안 화면이 낡는다 |

## 8. 검토한 대안

| 대안 | 고르지 않은 이유 |
| --- | --- |
| Grafana iframe을 콘솔에 넣기 | 콘솔이 Grafana 장애에 묶이고, 판단·조작 흐름이 끊긴다. 콘솔은 ops-svc가 읽은 값을 직접 그린다 |
| 관제와 판매가 같은 게이트웨이·DB | 관제 장애가 판매를 막고, 판매 폭주가 관제를 늦춘다. 제어 평면을 따로 둔다 |
| 모든 명령을 2인 승인 | 입장 일시정지 같은 긴급 조작이 느려진다. 위험도에 따라 1인·2인을 나눈다 |
| 명령을 Kafka 하나로만 | Kafka가 멈추면 명령이 퍼지지 않는다. 긴급 명령은 제어 gRPC, 설정형은 Kafka로 나눈다 |
| 실시간 표를 Prometheus만으로 | 잔여석·퍼널처럼 원시 사건 집계가 필요한 숫자가 있다. ClickHouse `rt`를 따로 둔다 |

## 9. 열린 질문·가정

- T-30분 점검 항목과 Go/No-Go 기준은 [가정]이 많다. 첫 온세일 리허설과 Game Day에서 고친다.
- 신선도 5초, 입력 없음 30초, 감축 확인 35초·2분, SSE 재연결 35초는 [가정]이다.
- 공개 앵커의 게시 지연 6시간 [가정]과 캘린더 장애 처리는 첫 운영에서 확인한다.
- 관제 콘솔의 원격 위젯 배포는 온세일 윈도우(T-10분~T+60분) 동안 바꾸지 않는다(ADR-0079).
