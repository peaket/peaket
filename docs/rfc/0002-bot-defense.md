# RFC 0002: 봇 방어 — 로비에서 미리 판정하고, 축소 운영에서도 대기열을 막지 않는다

- **상태**: 초안(2026-11-12, BUILD_ORDER BAS-230, wbs 0.8.1). 규범이 아니다. 정본은 [docs/features/bot-defense.md](../features/bot-defense.md), [queue-admission.md](../features/queue-admission.md) §2·§3·§7, [docs/features/analytics.md](../features/analytics.md) §13, [docs/streaming.md](../streaming.md) §5·§11이다.
- **독자**: 대기열·신뢰·계정·분석을 구현하는 엔지니어, 운영자, 봇 대응 정책을 검토하는 이해관계자.
- **요약**: PEAKET은 오픈 순간의 진입 경로에서 봇을 판정하지 않는다. 로비와 공연 상세의 사전 검증에서 미리 판정하고, T=0에는 이미 받은 토큰만 확인한다. 판정은 사람 확인·기기 이력·네트워크·행동 요약·일관성·공유 패턴의 여섯 점수기와 확정 신호(차단 기기 목록·허니팟)로 한다. trust-svc가 멈추면 통과시키지 않고, queue-svc가 캐시한 기기·IP 한도로 줄인다.

## 1. 문제

- 온세일에는 사람과 봇이 같은 화면을 두고 경쟁한다. 매크로는 사람보다 빠르고, 한 사람이 여러 계정을 만들 수 있고, 대기열 자체를 공격할 수도 있다.
- 봇을 100% 막는 것은 불가능하다. 목표는 ① 정상 사용자를 막지 않으면서 ② 봇의 이득을 줄이고 ③ 사후에 근거를 남기는 것이다.
- 판정을 오픈 순간에 하면 진입 피크 20만 RPS에 판정 부하가 더해진다. 그래서 판정은 로비(T-10분)와 사전 검증으로 앞당긴다.

## 2. 목표와 비목표

| 목표 | 값 | 정본 |
| --- | --- | --- |
| 로비 판정 피크 | 초당 약 1,700건(고르게 온 경우), 첫 1분 평균 약 3,500건 [추정] | docs/features/bot-defense.md §4.6 |
| 판정 데드라인 | 800ms [가정] | 같다 |
| 사람 확인 검증 | 500ms [가정]에 끊는다 | 같다 |
| T=0 판정 | 없음(로비·사전 검증에서 끝낸다) | 같다 |
| 축소 운영 | trust-svc가 멈춰도 대기열 진입은 막지 않는다 | docs/features/bot-defense.md §11 |
| 사람 오탐 상한 | 0.5% 이하(NFR-022, 출시 뒤 확인) | docs/features/bot-defense.md §13 |

비목표:

- 모든 봇을 실시간에 막지 않는다. 사후 라벨·조사·이의 제기로 보완한다.
- 점수 원값·가중치·기준값을 응답이나 화면에 싣지 않는다. 봇이 기준을 거꾸로 알아내지 못하게 한다.
- 기기 지문·행동 원시값을 서버로 모으지 않는다. 브라우저가 낸 요약값만 받는다.
- 데드 레터 토픽을 두지 않는다. 처리 못 한 사건은 서비스 DB의 보류 표에 둔다(ADR-0142).

## 3. 판정 흐름

1. **입력 정리**: 부르는 쪽(queue-svc·identity-svc)이 판정하는 때(`LOBBY_ENTRY`·`PREVERIFY`·`VERIFICATION`·`LOGIN`)와 기기 가명·IP·ASN·UA·Client Hints·최초 방문 쿠키 나이·세션 나이를 넘긴다.
2. **확정 신호**: 차단 기기 목록(`tr:block`)과 허니팟 적중(`tr:hp`)을 먼저 본다. 있으면 `CHALLENGE`다.
3. **점수기**: 여섯을 모두 돌린다. `HumanCheck`는 여기서 한 번만 검증한다(토큰 수명 300초, 1회용).
4. **가중합**: 비공개 설정의 강도·정렬 방식별 기준값과 견준다. 기준값 이상이면 `CHALLENGE`, 아니면 `ALLOW`다.
5. **기록**: 판정 기록과 행동 신호를 Kafka로 낸다. 응답 뒤로 미루는 쓰기(기기 이력·판정 근거·추가 검증 결과)는 실패해도 판정을 바꾸지 않고 지표로 센다.

- 응답은 `ALLOW`·`CHALLENGE`, 사유 범주 하나, `degraded`만 싣는다. 사유 범주는 `RAPID_REQUESTS`·`DEVICE_HISTORY`·`NETWORK`·`INTERACTION`·`HUMAN_CHECK`·`SHARED_PATTERN`이다.

## 4. 신호와 점수기

| 점수기 | 보는 것 | 저장 |
| --- | --- | --- |
| `HumanCheck` | Cloudflare Turnstile 서버 검증 | 결과만, 토큰 원문 없음 |
| `DeviceTrust` | 기기 신뢰 이력·차단 목록·새 기기 수 | `tr:devacct`·`tr:devhist`·`tr:block`(가명) |
| `NetworkScore` | IP·ASN·호스팅 대역·요청 속도 | `tr:devshare`·`tr:asnhost`(10분·30초) |
| `BehaviorScore` | 화면 조작 요약(원시 좌표 없음) | 행동 신호 원시 30일(ClickHouse) |
| `ConsistencyScore` | 입력·화면 전환의 일관성 | 같은 요약 |
| `SharedPattern` | 여러 계정이 같은 기기·결제 수단을 쓰는 모양 | 재평가 R2, `tr:devacct` |

- 확정 신호는 점수와 별개다. 차단 기기 목록은 이의 인정 때 바로 지우고, 허니팟은 숨긴 링크를 누른 계정을 기록한다.
- 기기 라벨 키는 KMS로 만들고 90일 [가정]마다 회전한다. 회전 중에는 옛 키와 새 키를 함께 읽어 이력을 옮긴다(ADR-0258).

## 5. 결과가 이어지는 곳

- **대기열**: `ALLOW`는 로비 참가·사전 검증 토큰 발급으로 이어진다. `CHALLENGE`는 추가 검증 큐로 보내고, 통과하면 토큰을 준다. `degraded`인 `ALLOW`는 토큰에 `hd`를 넣지만 한도는 걸지 않는다.
- **추가 검증**: `POST /v1/queues/{eventId}/verification`이 사람 확인 토큰을 다시 검증한다. 실패·재검증 필요·사람 불일치·한도 초과를 구분해 센다.
- **로그인**: identity-svc가 로그인 판정을 부른다. 로그인 화면에는 사람 확인 위젯이 없어 `HumanCheck`는 원래 값 없음이다.
- **이의 제기**: 추가 검증 화면에서 `appeal`을 받아 CS 처리함 `VERIFICATION_APPEAL`로 보낸다. 기한은 온세일 중 30분 [가정] 판정, 결과 통지 10영업일 [가정]이다.
- **사후 라벨**: 허니팟·표본 검토·사후 라벨·추가 검증 결과로 봇 점유율 하한을 R2에 확정한다. 정답이 없으므로 하한으로만 적는다(FR-049).

## 6. 축소 운영

| 상황 | 판정하는 쪽 | 쓰는 것 | 대기열 |
| --- | --- | --- | --- |
| trust-svc는 살아 있고 의존성 일부가 멈춤 | trust-svc | 남은 점수기, 마지막 설정 판, 마지막 ASN 표 | 그대로 |
| trust-svc 전체가 응답하지 않음 | queue-svc | 캐시한 기기·pid 한도(10초 5회 [가정]), 호스팅·프록시 IP 한도 | 진입은 막지 않고 더 통과하는 봇을 받아들인다 |

- queue-svc는 사람 확인 비밀 키를 갖지 않는다. 토큰에 '검증 보류'를 서명하고, trust-svc가 돌아오면 사전 검증 토큰 갱신 때 다시 판정한다.
- 서킷 브레이커는 10초 창 20건 [가정] 이상, 실패 50% [가정] 이상이면 열고, 5초 [가정]마다 시험 호출을 보낸다. 열림·닫힘은 `circuit_breaker_state{dependency="trust-svc"}`와 보안 로그로 남긴다.
- 축소 운영은 탐지 정밀도를 떨어뜨린다. 온세일 중이면 SEV2, 밖이면 SEV3로 알린다.

## 7. 사후 확인과 이의

- **봇 점유율 하한**: 허니팟 적중, 통과 세션 표본 200건 [가정], 그림자 추가 검증 표본 200건 [가정], 사후 라벨, 추가 검증 결과를 합쳐 Wilson 95% 하한으로 센다.
- **사람 오탐**: 그림자 판과 표본 검토로만 확인한다. 판정·묶음을 가린 검토 화면(SCR-067)을 쓰고, 판단 불가는 오탐을 크게 보는 쪽으로 센다. 상한 0.5% 이하가 적용 전환의 조건이다.
- **이의**: 판정 근거 키의 사유 범주·확정 신호 여부·판정 출처·시각·지난 30일 추가 검증 이력만 CS에 보인다. 점수 원값·가중치·기기 가명은 보이지 않는다.
- **라벨 반영**: 이의 인정·표본 검토·사후 라벨은 `ApplyLabel`로 반영하고, 차단 기기 목록에서 지운다. 같은 라벨이 두 번 반영되지 않게 판 가드를 둔다.

## 8. 개인정보·보존

- 기기 식별값 원문은 브라우저 localStorage에만 둔다. 서버에는 가명 `deviceRef`만 쓴다.
- 행동 신호는 요약값만 받고, 원시 좌표·키 값·입력한 글자는 브라우저 밖으로 나가지 않는다.
- 보존: 판정 피처 10분·30초, 기기 신뢰 이력 30일, 차단 목록 90일 [가정], 허니팟 24시간 [가정], 판정 근거 30일 [가정], 행동 원시 30일, 이의 심사 1년.
- 봇 판정은 자동화된 결정으로 다뤄 처리방침에 판정 사실·목적·주요 유형·처리 절차·권리 행사 방법을 공개한다(POL-006).

## 9. 검토한 대안

| 대안 | 고르지 않은 이유 |
| --- | --- |
| 오픈 순간 진입에서 판정 | 20만 RPS에 판정 부하가 더해지고, 판정이 늦으면 정상 사용자가 줄을 서지 못한다 |
| trust-svc가 멈추면 모두 통과 | 봇이 장애를 유도해 통과할 수 있다. 대신 기기·IP 한도로 줄이고 대기열은 연다 |
| 기기 지문을 서버에 모으기 | 개인정보·오탐·우회 비용이 커진다. 브라우저 요약값과 가명 이력으로 충분하다 |
| 점수 원값을 화면에 보여 주기 | 봇이 기준을 거꾸로 알아낸다. 사유 범주 하나만 보인다 |
| 봇을 실시간에 모두 차단 | 불가능하고 오탐이 커진다. 사후 조사·이의·라벨로 보완한다 |

## 10. 열린 질문·가정

- 로비 판정 피크 1,700/s·첫 1분 3,500/s, 데드라인 800ms·사람 확인 500ms는 [가정]이다. Q-T57·Q-T58에서 잰다.
- 축소 운영 한도(10초 5회)와 서킷 문턱(20건·50%·5초)은 [가정]이다.
- 표본 검토 200건과 사람 오탐 0.5% 상한의 정확한 식은 wbs 3.7.1에서 확정한다.
- 실제 사람 기준의 오탐은 첫 온세일 뒤에만 확인할 수 있다.
