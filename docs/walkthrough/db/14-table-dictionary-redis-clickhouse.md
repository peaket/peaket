# DB 설계 편 14: 표 사전 ② — Redis 키, ClickHouse 표, S3, 기기 안 저장소

- **기준 시점**: ADR-0177까지, 2026-11-02. 2026-11-03에 대기열 키 넷(`epoch`·`cfg`·`q:batch`·회차 목록)을 더했다(정본에는 ADR-0181·0182와 BUILD_ORDER PRF-050·060이 더한 키)
- **지금 판의 근거**: [docs/data.md](../../data.md) §1·§3·§6, [docs/features/analytics.md](../../features/analytics.md), [docs/streaming.md](../../streaming.md), [docs/features/forensic-replay.md](../../features/forensic-replay.md)
- **규범이 아니다**: 해설서는 정본을 풀어 쓴 것이고 새 결정을 담지 않는다. 숫자와 규칙이 정본과 다르면 정본이 맞고, 해설서를 고친다([ADR-0177](../../adr/0177-walkthrough-explain-in-interview.md)).
- **함께 읽기**: [DB 설계 편 12 '전체 지도'](12-whole-map.md)(먼저 읽는다), [DB 설계 편 8 'Redis 키 설계'](08-redis-keys.md), [DB 설계 편 10 '분석 저장소'](10-analytics-store.md), [표 사전 ①](13-table-dictionary-postgres.md)(PostgreSQL 표)

## 1. 읽는 법

이 편은 PostgreSQL 밖의 저장소를 하나도 빼지 않고 풀이한다. Redis는 docs/data.md §3 키 표의 행 67개를 클러스터별로 모두 적는다. ClickHouse는 정본이 이름을 적은 표를 데이터베이스별로 모두 적는다. S3와 기기 안 저장소는 버킷과 저장소마다 한 줄씩 적는다.

- **먼저 [전체 지도](12-whole-map.md)를 본다**: 세 Redis 클러스터와 ClickHouse 데이터베이스가 전체 구조의 어디에 있는지 본 다음, 이 사전에서 키와 표를 하나씩 찾는다.
- **Redis 키 이름 읽기**: `{event:E}`처럼 중괄호로 싼 부분은 해시 태그(Redis 클러스터가 키를 어느 칸(슬롯)에 둘지 정할 때 이 부분만 보게 하는 표시)다. 같은 태그를 가진 키는 한 샤드에 모여 Lua 스크립트(Redis 안에서 한 번에 도는 짧은 프로그램) 하나로 함께 바꿀 수 있다.
- **'왜 따로 두나'가 `—`인 키·표**: 정본이 이유를 적지 않은 것이다. 해설서가 이유를 지어내지 않는다.

## 2. Redis 대기열 클러스터

이 클러스터는 대기열 서비스 queue-svc와 입장 인원을 조절하는 admission-ctrl만 쓰는 Redis(메모리에 데이터를 두는 빠른 저장소. 이 설계는 호환 엔진 Valkey를 AWS 관리형 ElastiCache로 쓴다) 묶음이고, 샤드(키를 나눠 맡는 주 노드와 복제본 한 쌍) 3개 × 복제본 1개로 두어 정각 진입 폭주가 좌석 예매로 번지지 않게 물리적으로 따로 둔다(docs/infra.md §4). 메모리 규칙은 메모리가 차도 키를 지우지 않고 쓰기를 오류로 돌려주는 `noeviction`이고, 같은 Lua 스크립트(Redis 안에서 다른 명령과 섞이지 않고 한 번에 도는 짧은 프로그램)에서 함께 쓰는 회차 키에는 회차 해시 태그 `{event:E}`(키 이름의 `{…}` 안만 보고 같은 해시 슬롯, 곧 같은 샤드에 모으는 표시)를 붙이며, 사람·토큰 단위 키(`q:dup`·`q:adm`·`q:lobby:{hash}`·`q:arr`)는 회차 태그 없이 샤드 전체에 흩는다. 복제가 비동기라 장애 조치(고장 난 주 노드 대신 복제본을 올리는 일) 때 수백 ms 이내의 마지막 쓰기를 잃을 수 있어, 새 주 노드의 순번 카운터를 넉넉히 건너뛰고 세대 번호를 올리며(`q:{event:E}:skipped`), 사람별 입장 키 `q:adm`이 사라져 다시 줄을 선 사람도 1인 매수 한도는 PostgreSQL 원장 `purchase_quota`가 지킨다(docs/infra.md §6. 되살리는 목표 시간 RTO 30초, 영구 백업 없음).

표의 `E`는 회차 ID, `pid`는 본인확인을 마친 사람의 식별값이다. 키 표에 수명이 따로 없는 회차 키는 '회차 키 공통'으로 적었다. docs/infra.md §6이 대기열 회차 키를 그 회차의 판매 종료(공연 시작 24시간 전) TTL(키를 쓸 수 있는 시간. 지나면 지워진다)로 지운다고 적기 때문이다.

헷갈리기 쉬운 것:

- **`q:dup:{pid}:E`와 `q:adm:{pid}:E`**: 둘 다 사람 태그라 같은 슬롯이다. `q:dup`은 줄을 서는 동안 두 번째 번호를 막고 입장 확정 때 지워진다. 그 뒤로는 `q:adm`이 판매 종료까지 다시 줄 서기를 막는다.
- **`q:lobby:{hash}`와 `q:{event:E}:lobby_members`**: 앞의 것은 셔플 결과(토큰 해시 → 순번)라 샤드 전체에 흩는다. 뒤의 것은 셔플 전 참가자 목록이라 회차 슬롯에 모은다.
- **`q:{event:E}:ctl`과 `q:{event:E}:notice`**: `ctl`은 admission-ctrl 리더가 serving 전진을 정하는 상태이고, `notice`는 queue-svc가 대기 화면에 싣는 상태다. 판매 일시정지와 판매 중지는 둘에 따로 적힌다.

## 3. Redis 좌석 클러스터

이 클러스터는 좌석·주문 서비스 purchase-svc가 혼자 쓰고, 실시간 전파 입구 realtime-gw는 바뀐 좌석을 보내는 채널을 구독만 하는 Redis 묶음이다. 좌석 예매 장애가 대기열로 번지지 않게 따로 두고, 한 회차의 비트맵·홀드(결제하는 동안 다른 사람이 가져가지 못하게 좌석을 잠시 잡아 두는 것)·1인 한도·멱등키·정지 사본에 회차 해시 태그 `{event:E}`를 붙여 한 샤드에 모은다. 그래서 Lua 하나로 '비었나, 한도 안인가, 멈추지 않았나, 같은 요청인가'를 한 번에 본다. 메모리 규칙은 `noeviction`이지만 `s:ctl:events`처럼 TTL을 두지 않는 키가 있어 키마다 수명을 따른다. 복제가 비동기라 장애 조치 때 복제되지 못한 마지막 쓰기(수백 ms 이내)를 잃을 수 있어, 장애 조치 동안 그 회차 구매를 503으로 미루고, 되돌아갔을 수 있는 구역 일련번호는 회차 세대 `s:{event:E}:epoch`를 올려 가른다(docs/infra.md §6, data §3). 같은 좌석의 두 번째 판매는 PostgreSQL `seat_sale`의 활성 상태 부분 유니크 인덱스(조건에 맞는 행끼리만 값이 겹치지 않게 하는 제약) `UNIQUE (event_id, seat_id) WHERE status IN ('PENDING','SOLD')`가 막는다(ADR-0121, data §4).

헷갈리기 쉬운 것:

- **만료 계열 정렬 집합 넷**: `s:{event:E}:expiry`는 보통 홀드의 7분 만료, `ordered`는 주문을 만들고 결제 접수 전인 홀드(정지 대상 찾기), `paused`는 새 결제 일시 정지로 시간을 멈춘 홀드, `prio`는 우선 구매 보류(권리 만료)다.
- **`s:{event:E}:ctl`과 `q:{event:E}:ctl`**: 좌석의 것은 판매 일시정지의 사본이라 원본 `sale_control`대로 다시 쓰고 홀드를 423으로 거절한다. 대기열의 것은 admission-ctrl 리더의 상태라 serving 전진을 멈춘다.
- **홀드 멱등키와 주문 멱등키**: 홀드는 `s:{event:E}:idem:{account}:{key}`에 홀드 TTL(7분)만 둔다. 영구 보관하는 주문·결제 멱등키는 PostgreSQL `order_idempotency`에 둔다.

## 4. Redis 세션·캐시 클러스터

이 클러스터는 여러 서비스가 함께 쓰는 Redis 묶음이라, 키 접두사와 ACL(사용자마다 쓸 수 있는 명령·키를 정한 권한 목록)로 영역을 나누고 다른 영역의 키를 허가 없이 읽고 쓰지 못하게 한다. 메모리 규칙은 `noeviction`이고 이 클러스터는 모든 키에 TTL을, 캐시 값에는 크기 상한(ISR(미리 그려 둔 화면을 정한 주기로 다시 그리는 방식) 항목 1MB [가정])을 두며, 메모리 사용률이 70% [가정]를 넘으면 SEV3, 85% [가정]를 넘으면 SEV2 경보다(SEV는 장애 등급, 숫자가 작을수록 무겁다). 지워지거나 장애 조치로 잃는 일은 '데이터 유실 허용' 하나로 묶지 않고, 키마다 유실 등급(A 다시 만든다·B 사람이 다시 한다·C 다른 층이 마지막을 지킨다)과 마지막을 지키는 장치를 정해 두었다(ADR-0109, data §3 유실 등급 표).

이 클러스터에 두지 않는 것도 있다. 알림·파트너 웹훅 발송 작업은 2026-10-28에 core DB 발송 원장으로 옮겼고(ADR-0109), ops-svc의 파드 사이 전달(Socket.IO 어댑터 상태)은 ops DB로 옮겼다(ADR-0100·0102).

헷갈리기 쉬운 것:

- **예매 제한 사본 셋**: 원본은 ops DB `booking_restriction` 하나다. `q:rst:{account}`(대기열)는 입장 확정을, `s:rst:{account}`(좌석)는 주문 생성을 막는다. `sup:rst:{account}`(세션·캐시)는 팬 화면에 답하기만 하고 집행하지 않는다.
- **`tr:devshare`와 `tr:devacct`**: 둘 다 '한 기기의 여러 사람'을 센다. `tr:devshare`는 회차별 10분 창이고, `tr:devacct`는 회차를 넘는 30일 이력이다.
- **`id:devauth`와 `scanner:enroll`**: `id:devauth`는 스태프가 휴대폰으로 스캐너 로그인을 승인하는 코드(identity-svc, 5분 [가정])다. `scanner:enroll`은 운영자가 기기를 처음 등록하는 코드(ticket-svc, 10분 [가정])다.

## 5. ClickHouse

ClickHouse(대량 사건 집계에 강한 분석용 데이터베이스) 26.8 LTS는 쿠버네티스 클러스터 안에서 직접 운영하고, 복제 2벌을 서로 다른 AZ(같은 리전 안의 따로인 데이터센터 묶음)에 두며 복제를 조율하는 Keeper를 셋(정족수 2) 둔다(docs/infra-handover.md §3.2). 한 ClickHouse 안에 목적이 다른 데이터베이스를 나눠 두고(분석 층 `bronze`·`silver`·`gold`와 아카이브 뷰 `archive`, 관제 실시간 `rt`, 행동 신호 `trust`, 부정 예매 조사 `inv`, 법정 접속기록 DB), 주체마다 ClickHouse 사용자를 따로 둬 분석 사용자는 `inv`를, `inv` 사용자는 분석 DB를 읽지 못한다(ADR-0171 결정 2). RPO(잃어도 되는 시간 폭)는 1일, RTO(되살리는 데 걸려도 되는 시간)는 1시간이고, 하루 1회 S3 스냅샷(7일 [가정])을 복원한 뒤 그 뒤 구간은 Kafka를 다시 읽어 브론즈를 채우고 dbt(SQL 변환 모델을 짜고 시험하는 도구)로 실버·골드를 다시 만든다(docs/infra.md §6).

표 엔진은 모두 복제 엔진(ReplicatedMergeTree 계열: 정렬 키 순으로 저장하고 복제본끼리 맞추는 엔진)이다. 파티션은 지우거나 다시 쓸 때 통째로 다루는 칸이다. 같은 키의 행을 병합 때 하나로 줄이는 ReplacingMergeTree는 병합 시점을 보장하지 않아, 확정 숫자의 중복 제거에는 쓰지 않고 SQL(`eventKey`)로 지운다(analytics §5.5).

### 5.1 `bronze`: 원본 층

원본 적재 작업자 `analytics-ingest`가 Kafka 토픽을, 마감 실행기 `close-runner`가 분석 수집 버킷의 파일을 싣는 층이다. 식별값은 적재 때 회차별 가명(회차마다 다른 키로 HMAC한 값. 회차가 다르면 같은 사람도 가명이 다르다)으로 바꾸고, 이름·연락처·IP·결제 토큰과 조사용 칸(`journeyId`·`deviceRef` 등)은 버린다. 공통 물리 규칙은 `ORDER BY (event_id, occurred_at)`, 파티션 `toYYYYMMDD(loaded_at)`, TTL `loaded_at + 90일`, 비동기 일괄 삽입이고 중복을 허용한다. 표의 R0~R3은 마감 단계(회차 숫자를 영역별로 차례로 확정하는 네 시점)다. R0은 온세일 윈도우(오픈 10분 전~60분 뒤) 종료 + 30분, R1은 다음 영업일 10시, R2는 오픈 + 7일, R3은 회차 종료 다음 영업일 10시다 [가정, Phase 4 4.3.6에서 확정](analytics §4.2).

### 5.2 `silver`: 가명 사건 층

마감 실행기가 회차마다 그 회차 행을 지우고 다시 넣는(dbt delete+insert) 층이다. 공통 물리 규칙은 `ORDER BY (event_id, event_key)`, 파티션 `toYYYYMM(open_date)`, 적재 뒤 90일(가명정보 처리 기간, 개인정보 보호법 §28의4②)이고, 중복은 `LIMIT 1 BY event_key`로 지운다. TTL을 거는 칸은 아직 정하지 않았다(open-items 95번). 가장 작은 단위(원자 단위) 표를 2년 보관하는 골드에 두지 않으려고 실버에 90일만 두는 대신, 90일이 지나면 골드에 없는 기준으로 지난 회차를 다시 나눠 보지 못한다(analytics §5.4).

### 5.3 `gold`와 `archive`: 확정 숫자 층

스타 스키마(가운데 측정값을 담는 사실 표와 둘레의 나눠 볼 기준인 차원 표로 짠 모양)로 짠 확정 숫자 층이고, 사람 단위 행이 없으며 2년 둔다. 공통 물리 규칙은 회차가 앞인 정렬 키, 파티션 `toYYYYMM(open_date)`, 2년이고, 실행마다 `run_id`를 붙여 넣은 뒤 시험을 통과하면 회차별 현재 판 표를 바꾸는 판 바꾸기다(ADR-0086 결정 8). 사실 표는 업무 과정마다 그레인(한 행이 무엇인지)이 달라 나눈다. 넓은 표 하나로 두면 그레인이 달라 대기 인원 같은 값을 잘못 더한다(ADR-0052 대안). 비율과 분위수는 저장하지 않고 분자·분모와 히스토그램 버킷을 저장해, 회차를 합칠 때 평균이 틀리지 않게 한다. ### 5.4 `rt`: 관제 실시간 표

### 5.6 `inv`: 부정 예매 조사 저장소

부정 예매 사후 조사(판매가 끝난 뒤 실제 기록으로 한 사람이나 조직이 여러 계정으로 산 표를 묶어 찾는 일)의 원천이다. 가명 처리를 하지 않고 실명 계정·원문 IP를 그대로 담으므로 분석 저장소·`rt`·법정 접속기록 DB와 따로 두고, 조사 갈래와 연구 갈래를 잇는 키·권한·파일을 두지 않는다(ADR-0171 결정 2). 적재는 `inv-ingest`만 하고, 공통 물리 규칙은 `ReplicatedReplacingMergeTree`, `PARTITION BY event_id`, 정렬 키 `(event_id, 아래 키 칸)`, 행마다 `retain_until`(그 회차 공연일 + 30일 [가정])과 `ingested_at`(적재 시각)이다. 지우기는 ops-svc 파기 작업 `inv-partition-purge`가 하루 한 번 [가정] 보존이 끝난 회차 파티션을 `DROP PARTITION`으로 지우는 것이고, `TTL retain_until DELETE`는 보조다. TTL은 백그라운드 병합 때 지워져 지우는 때가 보장되지 않기 때문이다(ADR-0173 결정 7).

### 5.7 법정 접속기록 DB

통신비밀보호법 시행령 §41②2호를 준용해(POL-025) 3개월 보관하는 시스템 접속기록(접속 일시, 원문 IP, 단말 정보)을 업무 DB와 물리적으로 나눠 둔 데이터베이스다. 데이터베이스 이름과 표 이름은 정본에 없다.

| 표 | 담는 것 | 왜 따로 두나 | 키·정렬·보존 | 쓰는 곳 | 근거 |
| --- | --- | --- | --- | --- | --- |
| 접속기록 표(이름 정본에 없음, 열린 일 101번) | 게이트웨이 접근 로그의 법정 사본(일시, 원문 IP, 단말 정보, 요청 경로·상태, 요청 ID)과 identity-svc 접속기록 줄(로그인·재인증·로그아웃·토큰 갱신, 파드별 일련번호 `seq`) | 법령이 보존을 요구해 잃으면 의무를 지키지 못하는 2등급 기록이라, 잃지 않는 갈래(읽은 위치 저장, 디스크 큐, 끝없는 재시도, 원천 건수 대조)로 싣는다. 조사 칸(토큰의 `sub`·`pid`·`jny`, JA4, WAF 라벨)은 지운 뒤 싣는다 | ReplicatedMergeTree, `PARTITION BY toYYYYMMDD(ts)`(약 92개), `ORDER BY (ts)`, 원문 IP 조회용 bloom filter 건너뛰기 색인 [가정, 4.1.4], 3개월. 하루 파티션 사본을 S3에 둔다(§6) | `al_ingest`(에이전트 수집기, `INSERT`만), `al_admin_reader`(ops-svc, 행 정책으로 관리 계정 줄만 읽어 매일 감사 저장소로 옮겨 최소 2년), `al_investigation`(수사 대응, 사람마다 개인 계정) [가정] | data §6 '시스템 접속기록', observability §7·§9, ADR-0076 결정 7, ADR-0077 결정 8, ADR-0089, ADR-0146 결정 6, 기술 검토 높음-21 |

지우기·표 바꾸기는 따로 둔 마이그레이션 역할만 한다. 이 DB와 30일 행동 신호가 들어 있어 ClickHouse 일 백업은 7일 [가정]만 둔다(ADR-0053). `inv`가 그 백업에 드는지는 정하지 않았다(open-items 97번).

헷갈리기 쉬운 것:

- **`rt`와 `gold`**: 둘 다 판매 좌석·금액을 센다. `rt`는 원시 사건을 읽을 때 세는 잠정 숫자(관제·파트너 판매 현황)이고, `gold`는 마감 단계 R0~R3를 거친 확정 숫자(리포트·결정)다. 다른 표에 두고 섞지 않는다(ADR-0052 결정 1).
- **`trust.behavior_raw`와 `inv_behavior`**: 같은 `telemetry.behavior`에서 온다. 앞의 것은 탐지용 가명 기록(30일, `journeyId` 없음)이고, 뒤의 것은 조사용 실명 갈래 기록(공연일 + 30일 [가정], `journeyId` 있음)이다.
- **원문 IP를 적재해 조회하는 두 곳**: 법정 접속기록 DB(3개월, 수사 대응)와 `inv_request`(공연일 + 30일 [가정], 부정 예매 조사)다. 둘 사이에 복사하지 않는다. 이 밖에 AWS WAF 로그(90일 [가정])와 조치한 사건의 증거 묶음(증거 버킷)에도 원문 IP가 든다(§6 표, data §2 '원문 IP의 자리').
- **없어진 `rt` 표**: Flink 때의 `rt.cumulative`·`rt.bucket`·`rt.seed`는 ADR-0099로 없앴다. 지금은 원시 표 다섯과 매개변수 뷰 셋이다.

## 6. S3와 CDN 원본

S3(AWS의 파일·객체 저장소)는 화면이 CDN CloudFront로 받는 공개 원본과, 분석·백업·법정·감사·증거 기록을 두는 비공개 버킷으로 나뉜다. 공개 원본에는 개인정보 없는 파일만 두고, 분석 레이크와 리포트 버킷에는 원시 개인정보를 두지 않으며, 저장소 백업은 따로 둔 백업 버킷에 SSE-KMS(키 보관 서비스 KMS의 키로 하는 서버 쪽 암호화)로 두고 백업 역할만 읽는다(ADR-0053). 분석 아카이브와 백업 버킷은 버전 관리를 켜고, 개인정보가 들 수 있는 버킷은 지우거나 덮어쓴 객체의 옛 판을 7일 [가정] 뒤 지우며, Object Lock(정한 동안 누구도 지우거나 덮어쓰지 못하게 하는 잠금) 버킷은 그 법정·감사 보존 기간을 따른다(docs/infra.md §6).

헷갈리기 쉬운 것:

- **백업 전용 버킷과 접속기록 사본 버킷**: ClickHouse 백업은 7일 [가정]만 두어 3개월 보관 의무를 덮지 못한다. 그래서 법정 접속기록만 하루 파티션 사본을 따로 Object Lock 버킷에 둔다.
- **격리 버킷과 증거 버킷**: 격리 버킷은 검사 전 원본을 받는 곳이고, 증거 버킷은 검사를 통과한 캡처와 증거 묶음을 법적 보존으로 잠가 두는 곳이다.
- **분석 아카이브와 리포트 버킷**: 아카이브는 동결한 골드 표의 파일(ClickHouse 뷰로 다시 읽는다)이고, 리포트 버킷은 사람이 읽는 리포트 문서다.

## 7. 브라우저·기기 안 저장소

브라우저 안 저장소에는 docs/frontend.md §3.12 표에 있는 값만 두고, 그 표에 없는 값은 저장하지 않는다(ADR-0079 결정 5). 이름·전화·이메일·주소·계좌번호·카드 값·결제사 토큰·인증 앱 코드·비밀번호·문의·신고·소명 본문·본인확인 결과 값은 브라우저에 두지 않는다. 기기 서명용 개인키는 WebCrypto(브라우저가 주는 암호 기능)로 꺼낼 수 없게(`extractable=false`) 만들어 IndexedDB(브라우저 프로필 안의 데이터 저장소)에만 두는데, 스크립트가 꺼낼 수 없을 뿐 하드웨어에 보관하는 것은 아니다(ADR-0050). 표의 localStorage는 출처마다 남는 작은 키-값 저장소, sessionStorage는 탭을 닫으면 지워지는 저장소, Dexie는 IndexedDB를 감싸는 라이브러리, 서비스 워커는 페이지 뒤에서 돌며 오프라인 응답 등을 맡는 스크립트다. 괄호의 P1·P2는 보호 등급이다(P1 인증·연계 기밀, P2 일반 개인정보, docs/security/data-classification.md).

| 쿠키(브라우저가 사이트별로 저장했다가 요청마다 함께 보내는 작은 값) | 팬·파트너·운영자의 액세스·리프레시 토큰, 로그인 진행 `__Host-peaket_oidc`(10분 [가정]), 계정 연결 제안 `__Host-peaket_link`(10분), 도착 시각 `__Host-peaket_arr`, 최초 방문 `__Host-peaket_fv` | 모두 `Secure`·`HttpOnly`라 스크립트가 읽지 못한다. 프론트엔드 코드는 쿠키를 쓰지 않는다(`document.cookie` 쓰기를 린트로 막는다) | 쿠키마다 다르다(identity §3) | 앱 서버, 게이트웨이, 대기열 엣지 함수 | identity §3, frontend §3.12, queue-admission §7·§10 |

헷갈리기 쉬운 것:

- **기기 키 셋**: 월렛 기기 키(`peaket-wallet`, 티켓 QR 서명), 스캐너 기기 키(`peaket-scanner`, DPoP 증명 서명), 구매 세션 키(`peaket-purchase`, 구매 요청 HMAC)는 모두 꺼낼 수 없는 `CryptoKey`지만 쓰임과 수명이 다르다. 앞의 둘은 서명 키라 공개키를 서버에 등록하고, 구매 세션 키는 서버와 ECDH로 맞춘 비밀 키라 구매 세션이 끝나면 지운다.
- **`peaket-scanner`와 `peaket-scanner-queue`**: 같은 스캐너 출처의 Dexie DB 둘이다. 스캔 큐만 디스크에 쓴 뒤 완료를 알리는 `strict`로 따로 열고, 나머지 표는 기본 내구성으로 둔다.
- **localStorage와 sessionStorage의 대기열 값**: 대기표·참가 토큰(`peaket.queue.{eventId}`)은 판매 종료까지 남는 localStorage에, 입장 토큰(`peaket.admission.{eventId}`, P1)과 처음 앞 인원은 탭을 닫으면 지워지는 sessionStorage에 둔다.
